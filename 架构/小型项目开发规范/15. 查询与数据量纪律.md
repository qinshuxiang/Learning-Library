## 查询与数据量纪律

> **全章主脉**：**查询问题的规律是开发期数据少一切正常，上线后随数据量增长逐条恶化**。本篇给出四条纪律：查询必带行数上限、列名写全、深分页走游标、统计与导出限流，全部是建表之后零迁移成本的写法约束。

### 核心原则

- **查询必带 LIMIT**：任何 SELECT 默认带行数上限，无上限的全表查询只允许出现在明确知情的一次性运维脚本里。
- **列名写全**：不用 SELECT 星号。加列即改变结果结构，按需取列还能吃到覆盖索引。
- **深分页走游标**：OFFSET 大时数据库仍要扫过并丢弃跳过的行，翻页深了改用「上一页最后一条的 ID」定位。
- **客户端不决定查询规模**：页大小、导出行数由服务端定上限，不信客户端参数。



### 推荐做法

**列表分页的基础写法**，页浅时够用：

```sql
SELECT id, name, created_at FROM user ORDER BY id DESC LIMIT 20 OFFSET 40;
```

**深分页改游标法**，把「第几页」换成「上一页最后一条的 ID」：

```sql
SELECT id, name, created_at FROM user WHERE id < ? ORDER BY id DESC LIMIT 20;
```

前端每页记录最后一条的 ID，翻下一页时作为参数传入；跳页需求用页码加 OFFSET 的浅分页兜底即可。

**能判断「还有没有」就别数总数**：多取一条判断 HasMore，省掉每次翻页的全量 COUNT：

```js
// services/user.js
const pool = require('../db')

async function listBefore(lastId) {
  const limit = 21
  const [rows] = await pool.query(
    'SELECT id, name, created_at FROM user WHERE id < ? ORDER BY id DESC LIMIT ?',
    [lastId, limit]
  )
  const hasMore = rows.length === limit
  return { list: rows.slice(0, 20), hasMore }
}

module.exports = { listBefore }
```

**页大小服务端钳制**，客户端传多大都封在合理上限内：

```js
function clampPageSize(size) {
  const n = Number(size) || 20
  return Math.min(Math.max(n, 1), 100)
}
```

**导出当异步任务做**，行数超阈值一律走任务表加后台进程，见 分布式边界规范 篇；同步导出给硬上限，超限拒绝并引导走异步。

**排序字段必须有索引支撑**：ORDER BY 的列与 WHERE 的列联合考虑建索引，跑不动的查询先看执行计划再改写，不靠加机器。

**大结果集流式处理**：确需逐行处理大结果时用连接查询的流式接口逐行消费，不把全量结果攒进内存。

```js
const conn = await pool.getConnection()
const stream = conn.query('SELECT id, name FROM user ORDER BY id').stream()
stream.on('data', (row) => {
  console.log(row.id, row.name)
})
stream.on('end', () => conn.release())
```



### 注意事项

- **上线前自查星号查询**：全局搜索 SELECT 加星号，逐一改成显式列名，统计脚本与一次性运维除外。
- **排序不加列名白名单**：允许客户端传排序字段时用白名单校验，防注入与全表排序。
- **数据量评估提前做**：预估写入速率与一年后的量级，量级过大的表（日志、流水类）在设计期就想好归档方案，别等撑爆再动。

> [!TIP]
> **建议内容**：**用接近真实量级的数据做一次上线前演练**。本地插十万行模拟数据跑一遍核心列表与导出，慢查询会自己现形，比上线后看用户投诉便宜得多。
