## 金额与数据精度

> **全章主脉**：**金额与小数精度问题的根源是 IEEE 754 浮点无法精确表示多数十进制小数，对策是库里 DECIMAL、运算用整数、转换点收敛到一处**。本篇同时收口大数 ID 的序列化精度，这是前后端联调期最隐蔽的一类截断 Bug。

### 核心原则

- **金额不进浮点**：库里用 DECIMAL 或按分存整数，运算全程整数分，只在展示层转元。
- **大数 ID 全程字符串**：可能超过 JavaScript 安全整数（2 的 53 次方减 1）的 ID，序列化一律转字符串。
- **转换点唯一**：DECIMAL 与 BIGINT 从数据库取出后是字符串，转数字与转展示的代码只允许出现在收敛后的工具函数里。



### 推荐做法

**金额字段两种合法形态**，全项目择一并贯穿：

```sql
-- 形态一：DECIMAL，直观可读，适合以元展示为主的业务
amount DECIMAL(12, 2) NOT NULL DEFAULT 0.00;

-- 形态二：按分存整数，运算无舍入，适合对账、计费类业务
amount_fen BIGINT NOT NULL DEFAULT 0;
```

**mysql2 读取 DECIMAL 默认返回字符串**，这个默认必须保持，不要开 decimalNumbers 选项（它把 DECIMAL 转 Number，精度当场丢失）：

```js
// db.js——保持默认，不写 decimalNumbers: true
const pool = mysql.createPool({
  ...config.db,
  timezone: '+08:00',
  waitForConnections: true,
  connectionLimit: 10,
})
```

**金额运算用整数分**，加减乘全程整数，只在除法（分摊、均值）处定死舍入规则：

```js
// services/billing.js
function calcTotal(priceFen, quantity) {
  return priceFen * quantity
}

function fenToYuanString(fen) {
  return (fen / 100).toFixed(2)
}

module.exports = { calcTotal, fenToYuanString }
```

**浮点的不可靠是事实不是猜想**，以下为 Node 22 实跑输出：

```bash
node -e "console.log(0.1 + 0.2); console.log(0.1 + 0.2 === 0.3); console.log(0.1 + 0.2 > 0.3)"
```

```text
0.30000000000000004
false
true
```

**大数 ID 的两条防线**：连接层让 BIGINT 直接出字符串，序列化层不再手工转：

```js
// db.js——超过安全整数的 BIGINT 以字符串返回
const pool = mysql.createPool({
  ...config.db,
  timezone: '+08:00',
  supportBigNumbers: true,
  bigNumberStrings: true,
  waitForConnections: true,
  connectionLimit: 10,
})
```

自增主键从 1 起步的项目短期到不了安全整数上限，但雪花 ID 一类的大数 ID 从第一天生成的就是超限值，联调前先确认 ID 形态。

**金额比较用整数分比较**，禁止用等号比较浮点：

```js
if (balanceFen < amountFen) {
  const err = new Error('余额不足')
  err.status = 400
  throw err
}
```



### 注意事项

- **toFixed 是展示工具不是计算工具**：它做的是展示层四舍五入，参与运算的中间值一律保持整数分。
- **金额精度改标是伤筋动骨的迁移**：DECIMAL 的标度、按分还是按元，建表时一次定对，事后改字段类型要全链路核对代码与历史数据。
- **利率、汇率类字段另定标度**：多位小数业务用 DECIMAL(12, 6) 一类标度，不套用金额的两位小数模板。
- **前端展示只在一处转元**：fenToYuanString 一类函数收敛格式化，组件里不各自写除一百。

> [!CAUTION]
> **注意内容**：**接口返回大数 ID 时任何一处走了 Number 都会静默截断**，且截断后的值看起来完全合法，测试通过、上线后对不上号。联调前用真实大数 ID 过一遍全链路，是唯一可靠的验证方式。
