## 状态与字典建模

> **全章主脉**：**状态类字段的错误模式是魔法值散落各处、状态流转没有任何约束**，结果是无法回答「这个状态还能变成哪些状态」。本篇给出状态常量收敛、条件更新流转、字典表判据三件事的落地写法。

### 核心原则

- **取值单一来源**：状态取值收敛到常量定义文件，代码里不出现裸写的状态魔法值。
- **流转必带前置条件**：改状态的 UPDATE 一律带当前状态条件，无条件的状态改写视为缺陷。
- **字典形态二选一**：取值少且稳定用 TINYINT 加代码常量；需要运营配置或频繁增项用字典表。同一类数据全项目只用一种形态。



### 推荐做法

**状态常量收敛到一个文件**，取值含义与流转关系写在注释里：

```js
// constants/order.js
const ORDER_STATUS = {
  PENDING: 0,
  PAID: 1,
  SHIPPED: 2,
  DONE: 3,
  CLOSED: 9,
}

module.exports = { ORDER_STATUS }
```

**状态流转用条件更新**，目标状态与前置状态都进 WHERE，非法流转天然失败：

```js
// services/order.js
const pool = require('../db')
const time = require('../lib/time')
const { ORDER_STATUS } = require('../constants/order')

async function shipOrder(orderId) {
  const [result] = await pool.query(
    'UPDATE orders SET status = ?, shipped_at = ? WHERE id = ? AND status = ?',
    [ORDER_STATUS.SHIPPED, time.now(), orderId, ORDER_STATUS.PAID]
  )
  if (result.affectedRows === 0) {
    const err = new Error('订单当前状态不可发货')
    err.status = 409
    throw err
  }
}

module.exports = { shipOrder }
```

已关闭订单再发货这类非法流转，在这套写法下不会发生，不需要额外的检查代码。

**字典表给需要配置的数据**，区域、类目这类运营要维护的取值进表：

```sql
CREATE TABLE dict_region (
  code VARCHAR(16) NOT NULL,
  name VARCHAR(64) NOT NULL,
  parent_code VARCHAR(16) DEFAULT NULL,
  PRIMARY KEY (code),
  KEY idx_parent (parent_code)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**字典表判据三问**，全过才建表，否则用常量：

- 取值会不会由运营或用户增改：会，进表。
- 取值要挂展示名、排序、层级等属性：要，进表。
- 取值超过一屏且持续增长：是，进表。

**关联存储用键不存名**：业务表存字典的 code 或常量值，展示时再取名称，改字典名不触碰业务表。



### 注意事项

- **TINYINT 状态库里看不出含义**：这是常量文件与文档存在的意义，排查线上数据时对照常量定义读值。
- **状态机文档化一处即可**：常量文件头部注释写清合法流转（如 PAID 可到 SHIPPED 与 CLOSED），不另写独立设计文档。
- **历史脏数据处理**：引入常量收敛时盘点一次存量数据的状态分布，非法值单独迁移，不留给条件更新静默漏掉。

> [!NOTE]
> **提醒内容**：**状态字段的 Bug 多数表现为「看似无关的入口改了状态」**。全项目只有常量文件认识状态值、只有条件更新能改状态，这两条立住，非法流转就失去了入口。
