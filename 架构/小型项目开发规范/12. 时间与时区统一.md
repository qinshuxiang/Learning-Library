## 时间与时区统一

> **全章主脉**：**本规范采用全链路东八区策略——数据库、传输、日志、定时任务统一存取东八区墙上时间，服务器时区显式声明，格式化与解析收敛到一个时间工具**。中国单时区无夏令时，时间问题只剩纪律问题：本篇给出五处边界（设置、存库、传输、展示、日志）的直接可用做法。

### 核心原则

- **单一基准**：全链路只认东八区墙上时间（YYYY-MM-DD HH:mm:ss），不存在第二种存储与传输基准。
- **时区显式化**：服务器时区、数据库连接时区一律显式设置并断言，不依赖任何环境的默认值。
- **单一出口**：时间的格式化与解析只经时间工具函数，业务代码不手拼时间字符串、不用原生 Date 解析字符串。
- **字段只用 DATETIME**：TIMESTAMP 会随连接时区换算，单时区策略下徒增心智负担，不使用。



### 推荐做法

**服务器时区先设后断言**，装机第一步设置，部署脚本里断言兜底：

```bash
sudo timedatectl set-timezone Asia/Shanghai
timedatectl | grep "Time zone"
```

```bash
[ "$(date +%Z)" = "CST" ] || { echo "服务器时区不是东八区，停止部署"; exit 1; }
```

**MySQL 连接时区显式声明**，不依赖进程本地时区的隐式行为：

```js
// db.js
const pool = mysql.createPool({
  ...config.db,
  timezone: '+08:00',
  waitForConnections: true,
  connectionLimit: 10,
})
```

**表字段统一 DATETIME**，时间戳三件套写法与 数据库规范 篇建表模板一致：

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**时间工具函数收敛到一个文件**，格式化与解析全走这里，用 dayjs 单库：

```bash
npm install dayjs
```

```js
// lib/time.js
const dayjs = require('dayjs')

const FORMAT = 'YYYY-MM-DD HH:mm:ss'

function now() {
  return dayjs().format(FORMAT)
}

function toDb(value) {
  return dayjs(value).format(FORMAT)
}

function forDisplay(value) {
  return dayjs(value).format('YYYY-MM-DD HH:mm')
}

function today() {
  return dayjs().format('YYYY-MM-DD')
}

module.exports = { now, toDb, forDisplay, today }
```

**传输层禁传 Date 对象**：前端提交前统一转成东八区字符串，后端存库前只做格式校验不再换算：

```js
// 前端：提交前统一转换
import dayjs from 'dayjs'

function toServer(value) {
  return dayjs(value).format('YYYY-MM-DD HH:mm:ss')
}
```

**解析用户输入统一走 dayjs**，规避原生 Date 的解析歧义：

- 原生 Date 解析 ISO 日期串（2026-09-25）按 UTC 处理，解析带空格的串按本地处理，同一写法两种基准。
- dayjs 对两种写法一律按本地时区解析，日期串落到当天零点，行为一致。

**业务自然日按日期字符串判断**，「今天」「昨天」与日结统计用 today 一类的日期串做等值比较，不做小时差换算。

**日志与数据库同基准**：日志时间戳取自同一个时间工具，不用 toISOString（它输出 UTC 的 Z 串，与库内东八区差八小时，排错时两条时间线对不上）。

**定时任务自然对齐**：crontab 跟随系统时区，服务器时区设置正确后无需额外处理；任务脚本内部取时间同样走时间工具。

**应用与数据库分开部署时两台都设**：数据库服务器的系统时区决定 DATETIME 默认值 CURRENT_TIMESTAMP 的取值，必须与应用服务器同为东八区，并开启 NTP 校时。

> [!WARNING]
> **警告内容**：**换服务器、重建容器、迁移云厂商是时间错位的高发场景**。新环境默认时区常为 UTC，部署脚本开头的时区断言一条都不能省，断言不过就不发版。



### 注意事项

- **toISOString 与 toJSON 只用于跨时区交换**：两者输出 UTC 的 Z 串，本链路内禁作存储与展示格式。
- **容器部署补一个环境变量**：Docker 内设 TZ 环境变量为 Asia/Shanghai，Node 与多数镜像都认它；容器内 crontab 行为同样跟随该变量。
- **TIMESTAMP 的适用场景辨析**：它存 UTC 并按连接时区换算，适合多时区读写；旧版本还有 2038 年上限问题。本策略统一 DATETIME，写进建表评审项。
- **历史数据留意夏令时**：中国曾在 1986 至 1991 年实行夏令时，涉该时段的历史档案数据换算需专项核对，不能按当前无夏令时规则倒推。

> [!NOTE]
> **提醒内容**：**时间统一是部署期问题不是编码期问题**。代码写错一处好查，服务器时区错位会让日志、数据库、定时任务整体偏移且相互矛盾，排查成本远高于落笔时多写一行断言。
