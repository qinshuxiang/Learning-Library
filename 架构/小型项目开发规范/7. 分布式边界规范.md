## 分布式边界规范

> **全章主脉**：**小项目默认单机，分布式是具体问题出现之后的解法而不是架构预设**。本篇给出拆分的判定信号，以及异步任务、定时任务、缓存三类需求的单机起步方案与升级判据。

### 核心原则

- **单机优先**：加内存、加 CPU、加磁盘永远先于加机器，纵向扩容的天花板没到之前不谈横向。
- **每个中间件对应一个具体痛点**：引入 Redis、消息队列这类组件时，必须写得出它解决的那个已经发生的问题，写不出就不引。
- **能塞进数据库的不单独引入组件**：MySQL 本身就是可靠的队列与协调者，量级到之前不必另起炉灶。



### 推荐做法

**拆分的判定信号**，出现对应信号才评估引入对应组件：

- **请求被慢操作阻塞**：导出、发信、推送等操作拖慢接口响应，需要异步任务队列。
- **周期任务失控**：crontab 条目多且互相依赖时序，需要任务调度统一管理。
- **读多写少且查询变慢**：加索引、改查询之后仍慢，才考虑缓存层。
- **单表量级过大**：先做归档与分页优化，分库分表是最后手段。

**异步任务用 MySQL 任务表起步**，生产者写表，常驻 worker 领取执行：

```sql
CREATE TABLE job (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  type VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  status ENUM('pending', 'running', 'done', 'failed') NOT NULL DEFAULT 'pending',
  retry_count INT UNSIGNED NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_status (status)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

```js
// worker.js
const pool = require('./db')

async function claimJob() {
  const conn = await pool.getConnection()
  try {
    await conn.beginTransaction()
    const [rows] = await conn.query(
      "SELECT id FROM job WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED"
    )
    if (rows.length === 0) {
      await conn.commit()
      return null
    }
    await conn.query("UPDATE job SET status = 'running' WHERE id = ?", [rows[0].id])
    await conn.commit()
    return rows[0].id
  } catch (err) {
    await conn.rollback()
    throw err
  } finally {
    conn.release()
  }
}

async function handleJob(jobId) {
  const [[job]] = await pool.query('SELECT type, payload FROM job WHERE id = ?', [jobId])
  console.log(`processing job ${jobId} type=${job.type}`)
}

async function runWorker() {
  for (;;) {
    const jobId = await claimJob()
    if (jobId === null) {
      await new Promise((resolve) => setTimeout(resolve, 3000))
      continue
    }
    try {
      await handleJob(jobId)
      await pool.query("UPDATE job SET status = 'done' WHERE id = ?", [jobId])
    } catch (err) {
      console.error(`job ${jobId} failed`, err)
      await pool.query(
        "UPDATE job SET status = 'failed', retry_count = retry_count + 1 WHERE id = ?",
        [jobId]
      )
    }
  }
}

runWorker()
```

**定时任务优先用系统 crontab**，任务少时不需要进程内调度器：

```bash
*/5 * * * * cd /var/www/app && node jobs/clear-expired.js >> /var/log/app_cron.log 2>&1
```

**缓存从进程内存起步**，带过期时间即可覆盖多数读多写少场景：

```js
// cache.js
const store = new Map()
const TTL = 5 * 60 * 1000

function setCache(key, value) {
  store.set(key, { value, expires: Date.now() + TTL })
}

function getCache(key) {
  const hit = store.get(key)
  if (!hit || hit.expires < Date.now()) {
    store.delete(key)
    return null
  }
  return hit.value
}

module.exports = { setCache, getCache }
```

**Redis 的引入判据**：多进程需要共享缓存、需要比 Map 复杂的淘汰策略、或需要分布式锁时再上；上了就同时定下内存上限与淘汰策略，不给它无限膨胀的机会。



### 注意事项

- **多进程下进程内存缓存各一份**：PM2 的 instances 多于一个时，各进程的 Map 互不可见，需要一致性就一步到位上 Redis，不要在进程间同步 Map。
- **单机先吃满多核**：PM2 多进程已是横向的第一步，它不需要任何分布式组件配套。

> [!WARNING]
> **警告内容**：**小项目禁止按微服务拆分部署**。一至三人的团队拆出多个服务，结果是没人能完整排障；唯一例外是已有明确的团队边界或合规隔离要求，且拆出的服务由专人负责。
