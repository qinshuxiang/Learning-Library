## 写操作三防线

> **全章主脉**：**一切写接口按「会重复被调用、会部分失败、会被并发执行」设计，防线分别是幂等、事务、原子条件更新**。这三类错误的特点是测试环境难复现、生产环境直接赔钱赔数据，本篇给出 Express 加 MySQL 下可直接落地的三种防线写法。

### 核心原则

- **幂等**：同一操作执行多次与执行一次效果相同。按钮连点、网络重试、支付回调重发都是常态而非异常，防线必须建在后端。
- **事务**：一次业务动作涉及多行变更时必须同生同死。单条 UPDATE 天然原子，跨表跨行的写必须显式包事务。
- **先到先得靠约束**：并发下的资源归属靠数据库的唯一索引与原子条件更新裁决，不靠「先查一遍再决定」的两步写法。



### 推荐做法

**防重复提交用唯一索引兜底**，前端禁用按钮只是体验优化，后端用业务唯一键让重复插入自然失败：

```sql
ALTER TABLE orders ADD UNIQUE KEY uk_out_no (out_trade_no);
```

```js
// services/order.js
const pool = require('../db')
const time = require('../lib/time')

async function createOrder(userId, outTradeNo, amountFen) {
  try {
    const [result] = await pool.query(
      'INSERT INTO orders (user_id, out_trade_no, amount_fen, status) VALUES (?, ?, ?, 0)',
      [userId, outTradeNo, amountFen]
    )
    return result.insertId
  } catch (err) {
    if (err.code === 'ER_DUP_ENTRY') {
      const [rows] = await pool.query('SELECT id FROM orders WHERE out_trade_no = ?', [
        outTradeNo,
      ])
      return rows[0].id
    }
    throw err
  }
}

module.exports = { createOrder }
```

**支付回调按状态条件更新实现幂等**，影响行数为零说明已处理过，直接应答成功：

```js
// services/payment.js
const pool = require('../db')
const time = require('../lib/time')

async function markPaid(outTradeNo) {
  const [result] = await pool.query(
    "UPDATE orders SET status = 1, paid_at = ? WHERE out_trade_no = ? AND status = 0",
    [time.now(), outTradeNo]
  )
  return result.affectedRows > 0
}

module.exports = { markPaid }
```

回调入口拿到 false 时照常返回成功应答，不报错，让渠道停止重发。

**多行变更包事务**，连接从池里取、用完必还，失败必回滚：

```js
// services/account.js
const pool = require('../db')

async function transfer(fromId, toId, amountFen) {
  const conn = await pool.getConnection()
  try {
    await conn.beginTransaction()
    await conn.query('UPDATE account SET balance_fen = balance_fen - ? WHERE id = ?', [
      amountFen,
      fromId,
    ])
    await conn.query('UPDATE account SET balance_fen = balance_fen + ? WHERE id = ?', [
      amountFen,
      toId,
    ])
    await conn.commit()
  } catch (err) {
    await conn.rollback()
    throw err
  } finally {
    conn.release()
  }
}

module.exports = { transfer }
```

**并发扣减用原子条件更新**，把「够不够」压进 WHERE 里，让数据库裁决：

```js
const [result] = await pool.query(
  'UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0',
  [goodsId]
)
if (result.affectedRows === 0) {
  const err = new Error('库存不足')
  err.status = 409
  throw err
}
```

**多字段并发编辑用乐观锁**，带上读到的版本号，更新失败即提示刷新：

```js
const [result] = await pool.query(
  'UPDATE doc SET content = ?, version = version + 1 WHERE id = ? AND version = ?',
  [content, docId, baseVersion]
)
if (result.affectedRows === 0) {
  const err = new Error('内容已被他人修改，请刷新后重试')
  err.status = 409
  throw err
}
```

**冲突率极高的场景用悲观锁**：同一事务内先 SELECT 加 FOR UPDATE 锁行再改，例如秒杀的热点行；小项目默认用条件更新，锁行是兜底手段不是首选。



### 注意事项

- **事务里不发网络请求**：HTTP 调用、发短信这类慢操作放在事务提交之后，事务内只做数据库变更，避免长时间占连接持锁。
- **「先查再改」是并发缺陷的标志**：业务代码里先 SELECT 某行再无条件 UPDATE 同一行，两步之间状态就可能被别人改掉；自查时按这个模式搜索。
- **重复提交的体验处理**：后端幂等兜底之后，前端再补提交即禁用与防抖，顺序不能反。

> [!WARNING]
> **警告内容**：**支付类回调必须幂等**。渠道的重试机制是默认行为，回调处理不幂等的结果是重复入账、重复发货；上线前用同一笔单号连发两次回调做验证。
