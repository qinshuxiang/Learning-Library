## 版本控制与协作

> **全章主脉**：**小项目的分支策略以「主干永远可发布」为唯一硬约束，流程越短越好**。本篇给出单人与多人两种规模的分支模型、提交信息规范与常用命令。

### 核心原则

- **主干可用**：main 分支任何时刻构建可过、部署不炸；达不到这一点的项目先修质量，再谈流程。
- **提交小而完整**：一个提交只做一件事，做完一件事就提交，提交信息让半年后的自己看得懂。
- **历史不轻改**：已推送到远端的提交不重写；改历史只发生在自己的未推送分支上。



### 推荐做法

**单人项目直接在 main 开发**，功能完成即提交，发布时打标签：

```bash
git switch main
git add -A
git commit -m "feat: 用户列表支持按状态筛选"
git tag v0.3.0
git push origin main --tags
```

**多人协作加一条短命特性分支**，做完当天合回：

```bash
git switch -c feat-user-filter
git add -A
git commit -m "feat: 状态筛选的前端交互"

git switch main
git pull origin main
git merge --no-ff feat-user-filter
git push origin main
git branch -d feat-user-filter
```

**提交信息用类型前缀**，一行说清做了什么：

```text
feat:     新功能
fix:      缺陷修复
docs:     文档变更
refactor: 既不改行为也不修缺陷的重构
chore:    构建、依赖、配置类杂项
```

**敏感文件提交前隔离**，.gitignore 基线见 安全基础 篇；提交前用 git status 兜底扫一遍，确认没有环境变量文件与日志混入。

**撤销已发布变更用 revert**，不改历史只加反向提交：

```bash
git revert --no-edit <提交号>
git push origin main
```



### 注意事项

- **合并前先拉远端**：merge 前必先 git pull，避免制造无谓的冲突提交。
- **大文件不进库**：二进制大文件走对象存储或网盘，仓库只存代码与配置。

> [!WARNING]
> **警告内容**：**强推会让其他人的本地历史与远端错位**，每个协作者都要重新核对并恢复自己基于旧历史的工作，恢复成本远高于多写一次 revert 提交。
