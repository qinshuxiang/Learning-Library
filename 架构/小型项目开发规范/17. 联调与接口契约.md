## 联调与接口契约

> **全章主脉**：**联调期返工的根源是契约后置——前后端各写各的，见面才对字段**。本篇给出契约定稿形式、命名转换纪律、错误码约定与联调协作的四条规则，目标是联调期只处理真 Bug，不对字段名与结构。

### 核心原则

- **契约先行**：接口的路径、方法、入参、出参、错误码在两端动手前定稿；改动当天同步契约文件，禁止口头改。
- **命名单一纪律**：数据库字段 snake_case，接口字段 camelCase，转换只发生在服务层一处，前端永远不见下划线字段。
- **两层状态码各管各的**：HTTP 状态码表达传输层结果（4xx 参数问题、5xx 服务问题），业务结果用响应体的 code 字段表达，不用 HTTP 200 包裹业务失败之外的语义混搭。
- **前端不等后端**：契约定稿后前端立即用 mock 数据开发，后端就绪后只换 baseURL。



### 推荐做法

**契约定稿文件进仓库**，一个接口一段，五要素写全：

```text
docs/api.md

## 创建订单
- 方法与路径：POST /api/orders
- 鉴权：需要登录
- 入参：goodsId（数字）、quantity（数字，1 到 99）、remark（字符串，可空）
- 出参：orderId（字符串）
- 错误：40001 库存不足；401 未登录
```

**服务层集中做命名转换**，数据库行进、接口对象出：

```js
// services/user.js
function toUserVO(row) {
  return {
    id: row.id,
    name: row.name,
    createdAt: row.created_at,
  }
}

async function getUser(id) {
  const [rows] = await pool.query('SELECT id, name, created_at FROM user WHERE id = ?', [id])
  return rows[0] ? toUserVO(rows[0]) : null
}
```

**业务错误码收敛到常量**，契约文件里的码值与代码同源：

```js
// constants/errors.js
module.exports = {
  STOCK_NOT_ENOUGH: { code: 40001, message: '库存不足' },
  USER_NOT_FOUND: { code: 40401, message: '用户不存在' },
}
```

**前端侧 mock 一步到位**：契约定稿后先写返回固定数据的 mock 路由（或本地 JSON），组件按契约开发，后端就绪后整包切换，写法见 测试与质量保障 篇。

**联调验收三查**，两端各自过一遍再约联调：

- 出参与契约逐字段核对，含字段类型（尤其字符串形态的 ID 与金额）。
- 错误路径真实触发一遍（空参、越权、库存不足），不只测成功路径。
- 分页与空列表返回结构一致，空数据不是 null 而是 []。



### 注意事项

- **字段增删只加不删**：兼容期内接口字段只增不改义，废弃字段标注后留一个版本周期再清，客户端发版不受服务端发版钳制。
- **契约变更走同一条纪律**：改代码必改 docs/api.md，同一个提交完成；发现代码与契约不符时，先核对再改，不确定谁对就停下问。
- **时间与金额字段在契约里写明形态**：时间用东八区字符串、金额用整数分、大数 ID 用字符串，三件事分别见 时间与时区统一 篇与 金额与数据精度 篇。

> [!IMPORTANT]
> **重要内容**：**联调期对不上的第一反应是查契约文件而不是改代码**。两端现场口头对出一个新字段就各改各的，契约会迅速作废，下一个人接手时面对的是三份互相矛盾的事实。
