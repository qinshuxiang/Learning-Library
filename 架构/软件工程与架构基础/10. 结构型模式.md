## 结构型模式

> **全章主脉**：**结构型模式关注类与对象如何组合成更大的结构**，共 7 种：适配器、桥接、组合、装饰器、外观、享元、代理。它们的共同手段是**用组合与转发代替继承**，从而在不修改既有代码的前提下改变结构。按目的可归为三组——**接口转换**（适配器、外观）、**结构组织**（桥接、组合、装饰器）、**访问控制与共享**（代理、享元）。全部代码示例均已在 Node 环境实测通过。

### 结构型模式概述

#### 结构型模式的共同目标

结构型模式都在解决同一类问题：**已有的类或对象结构不满足新需求，但不希望直接修改它们**。常用手段有四：

- **增加间接层**：在调用方与被调用方之间插入一层，用于转换、转发或拦截。
- **用组合代替继承**：把能力委托给持有的对象，而不是继承父类，使结构在运行期可变。
- **统一递归结构**：让单个对象与组合对象具有一致的接口，使客户端无需区分。
- **控制对象访问**：在不改变对象本身的前提下增加访问控制、延迟加载或共享机制。

> [!IMPORTANT]
> **重要内容**：**结构型模式的本质是「包装」**。适配器包装不兼容的接口，装饰器包装以叠加功能，代理包装以控制访问，外观包装多个对象以简化接口，享元通过共享减少对象数量。理解「包装的是什么、暴露的是什么、隐藏的是什么」，就抓住了结构型模式的共同逻辑。

**考察形式**：综合知识选择题。



#### 七种模式的分类

按目的把 7 种结构型模式分为三组：

- **接口转换组**：**适配器**把不兼容接口转换为可用的接口；**外观**为一组子系统提供统一的高层接口。
- **结构组织组**：**桥接**把抽象与实现分离使二者独立变化；**组合**把对象组织为树形结构并统一单个与组合对象的接口；**装饰器**动态地给对象添加职责。
- **访问控制与共享组**：**代理**为其他对象提供替身以控制访问；**享元**通过共享细粒度对象减少内存占用。

> [!TIP]
> **建议内容**：**结构型模式的记忆口诀——「配桥组装外享代」**。展开为：适配器、桥接、组合、装饰器、外观、享元、代理。其数量为 7，与创建型 5、行为型 11 构成 23 种总数。

**考察形式**：综合知识选择题。



### 接口转换组：适配器与外观

#### 适配器模式

**适配器模式**把一个类的接口**转换成客户端所期望的另一种接口**，使原本因接口不兼容而无法协同工作的类可以一起工作。它分为**类适配器**（通过继承实现，多继承语言可用）与**对象适配器**（通过组合实现，通用性强）两种。

```js
// 遗留系统的接口与目标系统要求的接口不一致
class LegacyLogger {
  writeLog(level, message) { return `[${level}] ${message}`; }
}

// 适配器把 writeLog 接口转换为 info、error 接口
class LoggerAdapter {
  constructor(legacy) { this.legacy = legacy; }
  info(message) { return this.legacy.writeLog('INFO', message); }
  error(message) { return this.legacy.writeLog('ERROR', message); }
}

const logger = new LoggerAdapter(new LegacyLogger());
console.log(logger.info('服务启动'));
console.log(logger.error('连接超时'));

// 输出：
// [INFO] 服务启动
// [ERROR] 连接超时
```

- **角色构成**：**目标接口**（客户端期望的接口）、**被适配者**（已有的不兼容实现）、**适配器**（完成转换）。
- **优点**：复用既有实现而不改动它，符合开闭原则；把兼容性处理集中在一处，客户端无需知道差异。
- **缺点**：引入额外一层导致调用开销；适配器数量随不兼容接口对的数量增长；过度使用会让系统接口风格混杂。

**对比适配器与外观**：**目的**：适配器解决**接口不兼容**，外观解决**使用复杂**。**包装数量**：适配器通常包装一个对象，外观包装一组子系统。**接口变化**：适配器改变接口形式但保留原有能力语义，外观提供全新的简化接口并可能改变语义（如把多步合并为一步）。

> [!NOTE]
> **提醒内容**：**适配器常被误用为「万能胶」**。如果系统内部大量出现适配器，说明接口设计本身出了问题——应当在源头统一接口规范，而不是在调用处层层转换。适配器的正当场景是**对接无法修改的遗留系统或第三方接口**。

**考察形式**：综合知识选择题。



#### 外观模式

**外观模式**为**子系统的一组接口提供一个统一的高层接口**，使子系统更易使用。它不禁止直接访问子系统，只是提供一个更便捷的入口。

```js
class InventoryService { check() { return '库存已锁定'; } }
class PaymentService { charge() { return '支付已完成'; } }
class ShippingService { arrange() { return '物流已下单'; } }

class OrderFacade {
  constructor() {
    this.inventory = new InventoryService();
    this.payment = new PaymentService();
    this.shipping = new ShippingService();
  }
  placeOrder() {
    return [this.inventory.check(), this.payment.charge(), this.shipping.arrange()].join('，');
  }
}

console.log(new OrderFacade().placeOrder());

// 输出：
// 库存已锁定，支付已完成，物流已下单
```

- **优点**：降低客户端与子系统的耦合，客户端只需了解一个接口；把子系统的调用顺序与依赖关系封装在内部；为分层提供天然的层间接口。
- **缺点**：外观可能成为「上帝类」，把过多职责集中在一处；若不谨慎，外观会逐渐膨胀成难以维护的巨型接口。

> [!TIP]
> **建议内容**：**外观是分层架构得以成立的关键机制**。每层对外只暴露一个（或少数几个）外观接口，上层只依赖外观而不依赖层的内部结构，这样层内重构就不会影响上层。因此「层间只通过外观通信」应当作为架构硬约束写入代码检查规则。

**考察形式**：综合知识选择题。



### 结构组织组：桥接、组合与装饰器

#### 桥接模式

**桥接模式**把**抽象部分与它的实现部分分离，使二者可以独立变化**。它把继承层次由「二维爆炸」改为「两个独立维度加一条桥」。

```js
// 维度一：颜色（实现部分）
class Red { paint() { return '红色'; } }
class Blue { paint() { return '蓝色'; } }

// 维度二：形状（抽象部分），通过持有颜色对象建立桥接
class Circle {
  constructor(color) { this.color = color; }
  describe() { return `${this.color.paint()}的圆形`; }
}
class Square {
  constructor(color) { this.color = color; }
  describe() { return `${this.color.paint()}的方形`; }
}

console.log(new Circle(new Red()).describe());
console.log(new Square(new Blue()).describe());

// 输出：
// 红色的圆形
// 蓝色的方形
```

- **多维度爆炸问题**：若用继承实现「形状加颜色」，需要为每种组合都建一个子类（红圆、蓝圆、红方、蓝方……），维度增加时子类数量呈乘积增长。桥接把乘积关系变为相加关系。
- **优点**：抽象与实现可独立扩展、避免类爆炸、实现可在运行期替换、对客户端隐藏实现细节。
- **缺点**：增加了系统的抽象层次与理解成本；需要正确识别出「哪两个维度是独立的」，识别错误会导致桥接失去意义。

**对比桥接与适配器**：**使用时机**：桥接在**设计阶段**用于分离两个将独立演化的维度；适配器在**集成阶段**用于兼容已有接口。**目的**：桥接让二者独立变化，适配器让二者能一起工作。**结构**：桥接是稳定持久的组合关系，适配器是兼容性的转换层。

> [!IMPORTANT]
> **重要内容**：**识别桥接的时机是设计阶段，不是补救阶段**。如果两个维度已经用继承写成了大量子类，再引入桥接就变成了一次重构。因此在开始设计时就应问一句：**这个继承层次的变化是来自一个维度还是两个独立维度**？若答案是两个，就直接用桥接。

**考察形式**：综合知识选择题。



#### 组合模式

**组合模式**把对象组织成**树形结构**以表示「整体与部分」的层次，并**使客户端对单个对象和组合对象的调用具有一致性**。

```js
class FileNode {
  constructor(name, size) { this.name = name; this.size = size; }
  totalSize() { return this.size; }
  list(depth = 0) { return ['  '.repeat(depth) + this.name]; }
}

class FolderNode {
  constructor(name) { this.name = name; this.children = []; }
  add(node) { this.children.push(node); return this; }
  totalSize() { return this.children.reduce((sum, child) => sum + child.totalSize(), 0); }
  list(depth = 0) {
    const lines = ['  '.repeat(depth) + this.name + '/'];
    for (const child of this.children) lines.push(...child.list(depth + 1));
    return lines;
  }
}

const rootFolder = new FolderNode('src')
  .add(new FileNode('index.js', 12))
  .add(new FolderNode('utils').add(new FileNode('date.js', 8)));

console.log(rootFolder.totalSize());
console.log(rootFolder.list().join('\n'));

// 输出：
// 20
// src/
//   index.js
//   utils/
//     date.js
```

- **角色构成**：**抽象构件**（定义统一接口）、**叶子构件**（无子节点，实现基本行为）、**容器构件**（持有子节点，转发并聚合子节点结果）。
- **优点**：客户端无需区分单个对象与组合对象，简化调用；便于递归处理树形结构；新增构件类型符合开闭原则。
- **缺点**：设计过于抽象，若叶子与容器行为差异大，强行统一接口会使叶子被迫实现无意义的方法（违反接口隔离原则）。

> [!WARNING]
> **警告内容**：**组合模式中的递归必须设置终止条件或深度上限**。上例中容器的 list 方法通过「叶子返回自身、容器递归子节点」自然终止，但若数据结构出现环（如目录软链接成环、父子互相引用），递归将无限展开并导致栈溢出。凡是用组合模式处理用户可维护的树形数据，都要显式检测环或限制深度。

**考察形式**：综合知识选择题。



#### 装饰器模式

**装饰器模式**动态地给一个对象**添加额外职责**，且比继承更灵活。装饰器与被装饰对象实现同一接口，并可层层嵌套。

```js
class BaseService { request() { return '原始数据'; } }

class LogDecorator {
  constructor(inner) { this.inner = inner; }
  request() { return `[日志]调用前 -> ${this.inner.request()} -> [日志]调用后`; }
}

class RetryDecorator {
  constructor(inner) { this.inner = inner; }
  request() { return `${this.inner.request()}（失败自动重试 3 次）`; }
}

console.log(new RetryDecorator(new LogDecorator(new BaseService())).request());

// 输出：
// [日志]调用前 -> 原始数据 -> [日志]调用后（失败自动重试 3 次）
```

- **优点**：功能按需叠加、可任意组合顺序、动态增删职责、每个装饰器职责单一便于复用。
- **缺点**：产生大量小对象使调试与排查变复杂；装饰层级过深时调用链难以追踪；装饰器顺序影响最终结果，需要明确约定。

**对比装饰器与继承**：**扩展时机**：继承在编译期静态扩展，装饰器在运行期动态叠加。**组合方式**：继承是单层或多层固定扩展，装饰器可按需任意组合与嵌套。**类数量**：为覆盖全部组合，继承需要为每种组合建类，装饰器只需为每种职责建一个类。**共同点**：二者都在扩展对象能力，装饰器是合成复用原则对继承的替代方案。

**对比装饰器与代理**：**目的**：装饰器意在**增强功能**，代理意在**控制访问**。**对象创建**：装饰器由客户端传入被装饰对象，代理通常自行创建被代理对象。**接口**：二者都与被包装对象实现同一接口，因此结构相似、语义不同。

> [!TIP]
> **建议内容**：**装饰器与代理、适配器的结构都是由「实现同一接口加持有内部对象」构成的**，三者靠**意图**区分：**装饰器加功能**、**代理控访问**、**适配器换接口**。考试中遇到结构相同的图，必须读题目对意图的描述才能判断是哪一个。

**考察形式**：综合知识选择题。



### 访问控制与共享组：代理与享元

#### 代理模式

**代理模式**为其他对象**提供一种代理以控制对这个对象的访问**。代理与真实对象实现同一接口，客户端通过代理间接访问真实对象。

```js
class RealSubject { query(user) { return `${user} 查询到全部数据`; } }

class ProtectionProxy {
  constructor(real, allowedRole) { this.real = real; this.allowedRole = allowedRole; }
  query(user, role) {
    if (role !== this.allowedRole) return `拒绝访问：${user} 的角色 ${role} 无权限`;
    return this.real.query(user);
  }
}

const dataProxy = new ProtectionProxy(new RealSubject(), 'ADMIN');
console.log(dataProxy.query('张三', 'ADMIN'));
console.log(dataProxy.query('李四', 'GUEST'));

// 输出：
// 张三 查询到全部数据
// 拒绝访问：李四 的角色 GUEST 无权限
```

代理的常见类型按用途划分：

- **远程代理**：为位于其他地址空间的对象提供本地代表，隐藏网络通信细节。
- **虚拟代理**：延迟创建开销大的对象，在真正需要时才初始化，如大图占位符。
- **保护代理**：控制对对象的访问权限，如上的角色校验。
- **缓冲代理**：为操作结果提供临时存储，避免重复计算或重复访问。
- **智能引用代理**：在访问对象时附加额外动作，如引用计数、加锁、写时复制。

> [!NOTE]
> **提醒内容**：**代理在静态语言中可细分为静态代理与动态代理**——静态代理为每个被代理类手工编写代理类，动态代理在运行期通过反射或字节码技术自动生成代理。动态代理是许多框架实现声明式事务、日志与权限的基础，其核心价值是**不必为每个类重复编写代理代码**。

**考察形式**：综合知识选择题。



#### 享元模式

**享元模式**运用共享技术**有效支持大量细粒度对象的复用**。它把对象状态分为**内部状态**与**外部状态**：内部状态可共享且不随环境改变，外部状态随环境改变且不可共享。

```js
class GlyphFactory {
  constructor() { this.cache = new Map(); }
  get(char) {
    if (!this.cache.has(char)) this.cache.set(char, { char, font: 'SimSun' });
    return this.cache.get(char);
  }
  get size() { return this.cache.size; }
}

const glyphFactory = new GlyphFactory();
const glyphs = [...'abcabcabc'].map((char) => glyphFactory.get(char));

console.log(glyphs.length);
console.log(glyphFactory.size);
console.log(glyphs[0] === glyphs[3]);

// 输出：
// 9       —— 字符位置共 9 个，需要 9 次引用
// 3       —— 实际只创建了 a、b、c 三个共享对象
// true    —— 首尾同字符复用同一个对象
```

- **角色构成**：**抽象享元**（规定接口）、**具体享元**（可共享的对象）、**享元工厂**（管理共享对象的缓存池）、**外部状态**（由客户端保存并传入的部分）。
- **关键前提**：**必须能区分内部状态与外部状态**。上例中字符本身与字体是内部状态（可共享），字符在页面上的坐标是外部状态（每次使用都不同，由客户端持有）。
- **优点**：大幅减少对象数量与内存占用，适合文本编辑器、地图图元、游戏粒子等高对象密度场景。
- **缺点**：引入缓存与状态拆分使设计复杂；缓存本身占用内存，不当使用可能得不偿失；外部状态需由客户端管理，增加了使用成本。

**对比享元与单例**：**实例数量**：单例保证全系统只有一个实例，享元保证每种内部状态只有一个实例、总体可有多个。**关注点**：单例关注唯一性与访问点，享元关注共享与内存占用。**共同点**：二者都通过缓存与复用减少对象创建，享元工厂本身常实现为单例。

> [!CAUTION]
> **注意内容**：**享元的收益来自「可共享状态占比高」，若拆分不当会反向恶化**。把本应属于内部状态的数据错误地划为外部状态，会使客户端每次调用都要传递大量参数，代码复杂度上升而内存节省有限。判断标准是：**该状态在全部使用场景中是否都相同且不变**，只有答案为是时才可作为内部状态共享。

**考察形式**：综合知识选择题。



### 结构型模式的横向比较

#### 结构相似的模式的区分

若只从类图看，多个结构型模式长得几乎一样，区分只能靠意图：

- **适配器、装饰器、代理**：三者都持有被包装对象并实现同一接口。**适配器换接口**（客户端期望与既有实现不一致）、**装饰器加功能**（在调用前后追加行为）、**代理控访问**（拦截并决定是否放行）。
- **外观与适配器**：**外观包装一组子系统并提供简化接口**，**适配器包装单个对象并转换接口**。
- **桥接与策略**：结构上都把变化部分抽出并委托，但**桥接是结构型模式、解决二维变化的组合问题**，**策略是行为型模式、解决算法的可替换问题**。
- **组合与装饰器**：组合的容器持有**多个**子节点并递归聚合，装饰器通常持有**一个**被装饰对象并串行转发。

**考察形式**：综合知识选择题。



#### 选用要点

选择结构型模式的判断链如下：

- **接口不兼容且无法改来源**：用**适配器**。
- **子系统调用复杂、需要统一入口**：用**外观**。
- **两个维度会独立演化、继承层次爆炸**：用**桥接**。
- **树形结构且需统一对待单个与组合对象**：用**组合**。
- **需要动态、可叠加地增强对象功能**：用**装饰器**。
- **需要控制访问、延迟加载或增加间接层**：用**代理**。
- **需要创建海量细粒度对象而内存吃紧**：用**享元**。

> [!IMPORTANT]
> **重要内容**：**结构型模式的选择首先问「变化点在哪里」**。若变化点是接口形式，选适配器或外观；若变化点是结构维度，选桥接或组合；若变化点是对象的附加行为或访问方式，选装饰器或代理；若变化点是对象数量与内存，选享元。**先定位变化点，再选模式**，比背口诀更可靠。

**考察形式**：综合知识选择题。
