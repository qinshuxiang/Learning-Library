## UML 结构建模

> **全章主脉**：**结构建模回答系统由什么构成、元素之间如何关联**，其核心是类图，外围是对象图、包图、组件图、部署图、组合结构图与轮廓图。掌握结构建模的关键有三条：**分清七种结构图的用途**、**分清四种基本关系的强弱与方向**、**正确表达多重性与依赖方向**。本章按图的种类逐一展开，并给出可对照的表示法骨架。

### 类图

#### 类的表示

**类**是类图的基本元素，用一个矩形表示，矩形分为三栏：**类名、属性、操作**。类名居中书写；属性与操作左对齐；可见性用符号前缀表示。

```text
类的基本表示法

+-------------------------------+
|          OrderService         |   <- 类名（居中，抽象类名用斜体）
+-------------------------------+
| - orderRepository : Repo      |   <- 属性：可见性 名称 : 类型
| - retryLimit : Integer = 3    |   <- 属性可带默认值
+-------------------------------+
| + submit(order : Order) : Bool|   <- 操作：可见性 名称(参数) : 返回类型
| + cancel(orderId : String)    |
| # validate(order : Order)     |   <- 受保护操作
+-------------------------------+

可见性符号：
  +  公有（public）      -  私有（private）
  #  受保护（protected） ~  包内可见（package）

其他表示：
  抽象操作或抽象类名 用斜体
  静态成员 加下划线
  类名后用构造型标注，如 <<interface>>、<<entity>>、<<service>>
```

> [!NOTE]
> **提醒内容**：类的三栏可以按需省略——只画名称的称为**简单类**，画名称与属性的称为**属性类**，三栏齐备的称为**完整类**。在需求阶段的领域模型中，通常只画名称与关键属性；在详细设计中才画到操作级别。

**考察形式**：综合知识选择题。



#### 类之间的关系

类之间的关系共六种，按耦合由弱到强依次为**依赖、关联、聚合、组合、泛化、实现**。判断关系类型是类图题的核心考点。

```text
六种关系的表示法（连线形状与方向）

依赖    A - - - - - > B        虚线 + 开放箭头，箭头指向被依赖方
关联    A ----------> B        实线 + 可选开放箭头，箭头指向被关联方
聚合    A <>---------> B       空心菱形在 A 端（A 是整体）
组合    A <#>---------> B      实心菱形在 A 端（A 是整体）
泛化    B ------|> A           实线 + 空心三角，三角指向父类 A
实现    B - - - |> A           虚线 + 空心三角，三角指向接口 A
```

- **依赖**：一个类的变化会影响另一个类，表现为方法参数、局部变量或静态调用。是最弱的关系。
- **关联**：两个类之间存在结构性连接，通常表现为一方持有另一方的引用。可标注角色名与多重性。
- **聚合**：整体与部分的弱关系，部分可独立于整体存在，菱形在整体端且为空心。
- **组合**：整体与部分的强关系，部分的生命周期由整体决定，菱形在整体端且为实心。
- **泛化**：一般与特殊的关系，子类继承父类的属性与操作，可覆盖父类操作。
- **实现**：类实现接口所规定的操作集合。

> [!IMPORTANT]
> **重要内容**：**箭头方向是类图最常出错的地方**。三条定则必须记牢：**泛化与实现的空心三角一律指向父类或接口**；**依赖的箭头指向被依赖者**（即箭头指向「被使用」的一方）；**聚合与组合的菱形一律画在整体那一端**。方向画反会使整张图的语义反转。

**考察形式**：综合知识选择题。



#### 多重性与关联类

**多重性**标注在关联线的两端，表示该端可以有多少个实例参与这条关联，是表达业务约束的关键。

```text
多重性表示法（标注在关联线靠近该类的一端）

1        恰好一个
0..1     零个或一个（可选用）
1..1     恰好一个（与 1 等价）
*        零个或多个（等价于 0..*）
0..*     零个或多个
1..*     一个或多个
n..m     指定区间的整数个，如 2..5
n        恰好 n 个
```

**关联类**用于表达「关联本身带有属性」的情形。当两个类之间的关联需要记录额外信息（如「学生选修课程」需要记录成绩与选课时间），应把成绩与选课时间放进关联类，而不是塞进任何一端。

```text
关联类示例

  Student --------------- * Course
       |  1                    1 |
       |                          |
       +------> Enrollment <------+
                 - grade : Grade
                 - enrolledAt : Date

说明：Enrollment 是关联类，它依附于 Student 与 Course 之间的关联，
      表达「某个学生修某门课」这一关系的附加属性。
```

> [!TIP]
> **建议内容**：见到「两个类之间的关系本身需要记录数据」时，第一反应应是**关联类**而不是硬加字段。判断口诀是：**属性描述的是「关系」，不是「某一端」，就抽出关联类**。这一模式在考试与实践中都高频出现。

**考察形式**：综合知识选择题。



#### 类图的典型应用

类图在不同阶段承担不同职责：

- **领域建模**：刻画业务概念及其关系，只保留业务含义，不涉及技术实现。
- **详细设计**：补充接口、抽象类、可见性与方法签名，直接指导编码。
- **数据建模**：用类表示表、用属性表示字段、用关系表示外键约束，可导出数据库结构。
- **模式表达**：用类图表达设计模式的静态结构，如工厂、策略、观察者的类图形态。

> [!NOTE]
> **提醒内容**：同一份业务，领域模型与设计模型**不应混淆在一张图里**。领域类图里出现数据库连接、缓存管理器这类技术概念，说明抽象层次已被打破，图会迅速臃肿到无人愿意看。

**考察形式**：综合知识选择题。



### 对象图

**对象图**描述**某一时刻系统中对象实例及其链接的快照**，是类图的实例化。对象名采用「对象名 : 类名」的形式，若省略对象名则写作「: 类名」（匿名对象）。

```text
对象图示例（订单提交后的瞬时状态）

  order1 : Order                customer1 : Customer

  +----------------------+      +----------------------+
  | order1 : Order       |      | customer1 : Customer |
  +----------------------+      +----------------------+
  | orderNo = "A20260910"|      | name = "Zhang San"   |
  | status = "SUBMITTED" |      | level = "GOLD"       |
  +----------------------+      +----------------------+
            |                             |
            +--------places---------------+

说明：方括号内可写属性值；对象之间的连线称为链接，是关联的实例。
```

- **对象图与类图的关系**：类图是模板与类型层面，对象图是实例与取值层面；对象图必须在类图规定的结构内取值。
- **主要用途**：说明复杂数据结构的实例形态、调试时记录现场、验证类图设计能否支撑具体场景。
- **常见误区**：对象图不是「带数据的类图」，它不描述类型之间的关系定义，只描述实例之间的实际链接。

> [!TIP]
> **建议内容**：对象图最适合表达**结构递归或复杂嵌套**的数据，如树形目录、组织架构、多层组合关系。用一张对象图往往比文字描述清楚得多，而且能直接暴露「类图设计是否支持该场景」。



### 包图

**包图**用于组织模型元素并表达包之间的依赖关系。包用带标签页的文件夹形状表示，包内元素可以画在包内，也可以用全限定名引用。

```text
包图示例（分层的包依赖，箭头表示「依赖」方向）

  +-------------+        +-----------------+
  |   ui        | - - -> |   application   |
  +-------------+        +-----------------+
                                  |
                                  v
                         +-----------------+        +-------------+
                         |    domain       | - - -> |  infra      |
                         +-----------------+        +-------------+

依赖方向的约束：依赖必须单向，从上层指向下层，禁止反向依赖与循环依赖。
```

- **包的依赖**：表达包之间的使用关系，方向从使用者指向被使用者。
- **包的导入与访问**：导入使包内可直接引用对方元素；访问要求使用全限定名，用于表达较弱的耦合。
- **包的划分依据**：按功能内聚划分、按层次划分或按变更频率划分，三者可结合。
- **循环依赖的处理**：提取公共部分形成新包、引入接口反转依赖方向、合并应当合并的包。

> [!IMPORTANT]
> **重要内容**：**包之间的循环依赖是架构腐化的最重要信号**。它的危害不是「不好看」，而是使两个包无法独立理解、独立测试、独立部署，并让变更影响无法预测。因此包图应配合依赖检查工具使用，把「禁止循环依赖」变成构建环节的硬约束。



### 组件图

**组件图**描述**构件及其接口与依赖**，用于表达系统的模块化结构与可替换单元。构件是逻辑或物理上可替换的部分，封装内部实现并通过接口对外提供服务。

```text
组件图示例（球棍符号表达接口）

                +---------------------+
                |    OrderComponent   |
                |  +---------------+  |
                |  |  <<component>>|  |
     o----------|  | OrderService  |--o
     (               +---------------+  )
     ) 提供的接口                            (  需求的接口
     (  IOrderApi                            )  IPaymentApi
     o----------+                     +-----o
                +---------------------+
                          |
                          v
                +---------------------+
                |   PaymentComponent  |
                +---------------------+

表示法：
  球（圆加实线）  = 提供的接口（provided interface）
  棍（半圆）      = 需求的接口（required interface）
  端口            = 构件上与外部交互的显式交互点
```

- **构件**：系统中可替换的模块化部分，如服务、模块、库、可执行单元。
- **提供接口**：构件对外暴露的能力，用球表示。
- **需求接口**：构件依赖的外部能力，用棍表示。
- **端口**：构件边界上的显式交互点，用于把接口与构件内部结构关联起来。
- **连接件**：构件之间通过接口的装配关系，体现「谁实现了谁需要的接口」。

**对比组件图与类图**：**抽象层次**：类图面向逻辑设计，组件图面向实现与部署单元。**接口表达**：类图用实现关系与抽象类，组件图用球棍符号并区分提供与需求接口。**可替换性**：组件图显式表达可替换边界，类图不表达这一语义。**主要读者**：类图面向开发者，组件图面向架构师与集成者。

> [!NOTE]
> **提醒内容**：**提供接口与需求接口必须成对检查**。组件图中每个需求接口（棍）都应当能在其他构件上找到对应的提供接口（球），否则系统装配不起来。这种「接口缺口」用图表达比用文字描述更容易发现，是组件图最实用的价值。



### 部署图

**部署图**描述**节点、制品及它们之间的通信路径**，用于表达系统的物理部署拓扑。节点是运行时存在的计算资源，制品是部署到节点上的物理文件。

```text
部署图示例

  +---------------------------+          +---------------------------+
  |   <<device>> WebServer    |          |   <<device>> DBServer     |
  |  +-----------------------+|          |  +-----------------------+|
  |  | <<artifact>>          ||          |  | <<artifact>>          ||
  |  | app.war               ||=========||  | schema.sql            ||
  |  +-----------------------+|  TCP/3306 |  +-----------------------+|
  |  <<executionEnvironment>> ||          |  <<executionEnvironment>> ||
  |  Tomcat 9                 ||          |  MySQL 8.0               ||
  +---------------------------+          +---------------------------+

  ===== 表示通信路径，可标注协议与端口
  <<device>>                 物理计算设备（服务器、移动终端、传感器）
  <<executionEnvironment>>   运行环境（操作系统、容器、应用服务器）
  <<artifact>>               部署到节点上的物理文件（可执行文件、库、脚本、数据文件）
```

- **节点**：运行时存在的计算资源，分为设备与执行环境两类，支持嵌套。
- **制品**：物理信息载体，如可执行文件、库文件、配置文件、数据文件，可标注其来源构件。
- **通信路径**：节点之间的物理连接，可标注协议与端口。
- **多重性**：节点可标注多重性，表示存在多个同类实例，如三台应用服务器。

> [!TIP]
> **建议内容**：部署图的实用价值在于**暴露部署层面的质量属性问题**——单点、带宽瓶颈、跨网段调用、跨机房延迟。做可用性与性能分析时，把部署图画出来，问题往往一目了然。这也是它比类图更贴近运维与架构评审的原因。



### 组合结构图与轮廓图

#### 组合结构图

**组合结构图**描述**类或协作的内部结构**，包括内部部件、端口与连接件，用于表达复杂对象内部的装配方式，而不必展示整个系统的类关系。

- **部件**：类内部的组成元素，在运行时由类实例化并持有。
- **端口**：类边界上的显式交互点，规定外部只能通过端口与内部部件交互。
- **连接件**：内部部件之间或端口与部件之间的连接，表达内部的协作路径。
- **协作**：一组共同完成特定任务的元素集合，组合结构图可用来表达协作内部的角色与连接。

> [!NOTE]
> **提醒内容**：**组合结构图与类图的区别在于「内」与「外」**——类图描述类之间的关系，是「外部视角」；组合结构图描述一个类内部由哪些部件组成、如何连接，是「内部视角」。当某个类内部结构复杂到值得单独说明时，才需要组合结构图。

**考察形式**：综合知识选择题。



#### 轮廓图

**轮廓图**（Profile Diagram）通过**构造型、标记值与约束**扩展 UML 元模型，用于把 UML 裁剪到特定领域，如实时系统、业务流程、安全攸关系统。

- **构造型**：为既有 UML 元素定义新的语义标签，用双尖括号表示，如实体、服务、控制器。
- **标记值**：为构造型元素附加的额外属性，用于承载领域特有的信息。
- **约束**：对模型施加的规则，通常用对象约束语言表达，可被工具自动检查。

> [!TIP]
> **建议内容**：轮廓图在考试中通常只考「作用是什么」，即**扩展 UML 以适应特定领域**。实践中它的常见用途是定义团队统一的构造型词汇（实体、服务、仓储、控制器），使类图一眼能看出元素在分层架构中的角色。

**考察形式**：综合知识选择题。



### 结构建模的常见错误

结构建模的错误高度集中于几类，逐条对照可显著提高图的正确性：

- **关系选错**：把组合误写成聚合或关联，导致部分被人为绑死或生命周期失控。
- **方向画反**：泛化三角指向子类、依赖箭头指向使用者、菱形画在部分端。
- **多重性缺失或错标**：未标注多重性，或把「一个订单对应多个明细」标成一对一。
- **抽象层次混杂**：在同一张图里混入业务概念与技术实现细节。
- **接口与实现不分**：用类代替接口，导致可替换性无法表达。
- **循环依赖**：包或组件之间形成环，破坏独立部署与测试能力。
- **过度建模**：为每个类都画全套图，成本远超收益。

> [!WARNING]
> **警告内容**：**结构建模中最常见的实质错误是关系强弱判断错误**，尤其在聚合与组合之间。牢记唯一的判据——**部分能否脱离整体独立存在**。此外，若两个类之间的「关系」需要记录时间、数量、状态等数据，应引入关联类，而不是把字段塞进任何一端，这属于建模语义错误而非风格问题。

> [!CAUTION]
> **注意内容**：**图必须服务于沟通，不应追求形式完备**。一张只画了关键类与关系、标注清晰的手绘图，其价值远高于一张元素齐全但无人解读的机绘图。判断建模是否过度，只看一个问题——**这张图有没有帮助某个具体的人做出某个具体判断**。
