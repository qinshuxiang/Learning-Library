## UML 行为建模

> **全章主脉**：**行为建模回答系统如何运行**，用七种图从不同侧面描述动态行为：**用例图**刻画系统边界与功能，**活动图与状态机图**刻画流程与生命周期，**序列图、通信图、交互概览图、定时图**合称交互图，刻画对象之间的消息往来。掌握行为建模的关键是分清「流程视角」与「状态视角」，以及分清四种交互图各自强调什么。

### 用例图

#### 参与者与用例

**用例图**用于描述**系统的功能与边界**，由参与者、用例以及它们之间的关系构成，是需求阶段最常用的 UML 图。

- **参与者**（Actor）：与系统交互的外部实体，可以是人、外部系统、定时器或设备。参与者用简笔画小人表示，**位于系统边界之外**。
- **用例**（Use Case）：系统执行的一系列动作集合，对参与者产生可观察的价值结果，用椭圆表示。
- **系统边界**：用矩形框表示，框内为用例，框外为参与者，**边界的位置即系统职责的界限**。
- **关联**：参与者与用例之间的连线，表示该参与者参与了该用例，可标注多重性表示参与程度。

```text
用例图基本形态

        +-------------------------------------------+
        |              订单系统                      |
        |                                           |
   O----|----> (提交订单)                           |
  /|\   |                                           |
  用户  |----> (查询订单)                            |
        |                                           |
        |----> (取消订单) <----<<extend>>--- (申请退款)|
        |                                           |
        |----> (登录) <-------<<include>>---+
        |                                    |
        +-------------------------------------------+
             ^
             |  外部系统
        O----+
      支付网关

说明：方框是系统边界，椭圆是用例，连线是参与者与用例的关联。
```

> [!NOTE]
> **提醒内容**：**参与者不一定是人**。定时器、外部系统、硬件设备只要与系统交互，都可以是参与者。判断某个外部实体是否为参与者，只看一条：**它是否直接与系统交换信息或触发系统行为**。若它只是被系统查询的数据源，则不作为参与者，而作为系统内部的构件。

**考察形式**：综合知识选择题。



#### 用例之间的关系

用例之间有三种关系，方向与语义各不相同，是用例图最常出错的地方：

- **包含**（include）：基用例**总是**执行被包含用例，被包含用例是被复用的公共步骤。方向由基用例指向被包含用例。例如「提交订单」总包含「登录校验」。
- **扩展**（extend）：扩展用例在**特定条件下**才插入基用例，基用例本身是完整且可独立执行的。方向由扩展用例指向基用例。例如「申请退款」扩展「取消订单」。
- **泛化**（generalization）：子用例继承父用例的行为并可覆盖或补充。方向由子用例指向父用例。例如「信用卡支付」与「余额支付」泛化自「支付」。

```text
包含与扩展的方向（最易画反）

包含：基用例 - - - - <<include>> - - - -> 被包含用例
扩展：扩展用例 - - - <<extend>> - - - -> 基用例

记忆：箭头永远从「补充方」指向「被补充方」。
      包含中补充方是基用例（它调用了公共步骤）；
      扩展中补充方是扩展用例（它在特定条件下插入）。
```

**对比包含与扩展**：**执行条件**：包含无条件必然执行，扩展只在满足条件时执行。**基用例完整性**：包含的基用例离开被包含用例不完整，扩展的基用例本身已经完整。**复用方向**：包含用于抽取公共步骤，扩展用于描述可选或异常分支。**箭头方向**：包含由基用例指向被包含用例，扩展由扩展用例指向基用例。

> [!IMPORTANT]
> **重要内容**：**判断用包含还是扩展，只问两个问题**——第一，这段行为是不是**每次都要执行**？是则用包含。第二，基用例**离开这段行为还能不能独立完成**？能独立完成则用扩展。此外，泛化只用于「是一」的父子关系，不要用泛化代替包含来复用公共步骤。

**考察形式**：综合知识选择题。



#### 用例描述与用例规约

用例图只表达「有哪些用例」，不表达用例内部逻辑。用例的细节必须用**用例描述**（用例规约）补充，常见要素如下：

- **用例名与编号**：唯一标识，便于追踪。
- **参与者**：主要参与者与次要参与者，指明谁触发、谁协助。
- **前置条件**：用例开始前必须成立的状态。
- **后置条件**：用例成功结束后系统所处的状态。
- **主事件流**：最常规的成功路径，按步骤编号书写。
- **备选事件流**：异常与分支路径，标明触发条件。
- **业务规则与非功能要求**：约束条件、性能要求与安全要求。

> [!TIP]
> **建议内容**：写用例描述时，**主事件流只写「系统与参与者交替的动作」**，不要混入界面细节与实现方案。判断一条描述该不该写进去，看它是否对参与者可观察——可观察则写，属内部实现则不写。

**考察形式**：综合知识选择题。



#### 用例图的常见错误

用例图的错误高度模式化，逐条对照即可避免：

- **把内部功能当用例**：把数据库备份、日志切分这类系统内部动作画成用例，混淆了系统边界。
- **包含与扩展方向画反**：把箭头从被包含用例指向基用例。
- **用例粒度过细或过粗**：细到把每个界面操作都画成用例，或粗到只画一个「管理系统」。
- **用关联表达先后顺序**：参与者与用例之间的连线不表示顺序，顺序应写入用例描述。
- **缺少用例描述**：只有图没有描述，导致用例无法指导设计。

> [!WARNING]
> **警告内容**：**用例图的常见误用是把它当成流程图**。用例图回答「系统为谁提供哪些价值」，不回答「步骤如何先后执行」。若要表达流程顺序，应改用活动图；若要表达交互时序，应改用序列图。混淆三者会让图既说不清功能边界，也说不清执行顺序。

**考察形式**：综合知识选择题。



### 序列图

#### 序列图的组成

**序列图**（Sequence Diagram）是最常用的交互图，按**时间顺序自上而下**描述对象之间的消息交换。

- **生命线**：参与者或对象的垂直虚线，表示该对象在时间轴上的存在，顶部为矩形标识框。
- **激活**：生命线上的窄矩形，表示该对象正在执行处理，也称执行说明。
- **消息**：对象之间的水平箭头，按时间从上到下排列，是序列图的核心元素。
- **同步消息**：实线实心箭头，发送者等待接收者返回，即阻塞调用。
- **异步消息**：实线开放箭头，发送者不等待返回，即非阻塞调用。
- **返回消息**：虚线开放箭头，表示控制流返回结果。
- **自关联消息**：箭头回到自身生命线，表示对象调用自身方法。

```text
序列图示例（提交订单的主成功路径）

 :User        :OrderUI      :OrderService   :PaymentApi   :OrderRepo
   |              |               |              |              |
   |--submit----->|               |              |              |
   |              |--create------>|              |              |
   |              |               |--validate--->|              |
   |              |               |<--approved---|              |
   |              |               |--save---------------------->|
   |              |               |<--saved---------------------|
   |              |<--orderNo-----|              |              |
   |<--confirm----|               |              |              |

读法：从左到右是对象，从上到下是时间，箭头是消息。
```

> [!NOTE]
> **提醒内容**：**生命线与激活的区别**常被混淆——**生命线**表示对象在这段时间内存在，**激活**表示对象正在执行。一个对象的生命线可能从图顶贯穿到底，但激活条只在它处理消息的那段时间出现，中间可能有空档。

**考察形式**：综合知识选择题。



#### 消息类型与控制片段

序列图通过**交互片段**表达条件与循环，片段的左上角标注操作符：

- **alt**：多分支选择，等价于条件判断的多个分支，至少两个分支。
- **opt**：可选片段，等价于单分支条件，条件不成立则不执行。
- **loop**：循环片段，按条件或次数重复执行。
- **par**：并行片段，多个分支可并发执行。
- **break**：中断片段，条件成立时跳出并终止当前交互。
- **critical**：临界区片段，片段内不可被中断，用于表达原子性要求。
- **ref**：引用片段，引用另一个交互定义，用于把大交互拆分为可复用的子交互。

> [!TIP]
> **建议内容**：序列图上出现分支与循环时**必须用交互片段显式标注**，不能靠「如果有多个箭头就说明是分支」来暗示。片段不仅表达控制流，也直接对应实现中的条件语句与循环结构，因此是设计与测试的重要依据——**每个 alt 分支都应有对应的测试用例**。

**考察形式**：综合知识选择题。



#### 序列图的应用与取舍

序列图以时间顺序表达对象之间的消息交互，其用途与局限都源于这一表达方式。

- **主要用途**：细化用例的实现方案、表达跨模块的调用时序、发现接口设计问题、作为测试用例设计的输入。
- **优势**：时间顺序直观、消息语义显式、便于对照代码检查。
- **局限**：参与者较多时横向拥挤；无法表达对象之间的拓扑关系（改看通信图）；对状态迁移的表达能力弱。

> [!NOTE]
> **提醒内容**：序列图天然适合**发现接口缺失**。画完一张序列图后逐条检查每个消息——**接收方是否真的定义了对应的操作**？若某个消息在类图中找不到承载它的操作，说明设计存在缺口。这是序列图重要的验证价值。

**考察形式**：综合知识选择题。



### 通信图

**通信图**（Communication Diagram）与序列图语义等价，但**强调对象之间的连接结构**，消息用序号标注顺序，链路线表示对象之间的关联。

```text
通信图示例（与前面的序列图表达同一交互）

             1: submit()                2: create()
   +----------+ --------> +----------+ --------> +-------------+
   | :User    |           | :OrderUI |           |:OrderService|
   +----------+           +----------+           +-------------+
                                                       |  3: validate()
                                                       v
                                                 +---------------+
                                                 | :PaymentApi   |
                                                 +---------------+
                                                       |  4: save()
                                                       v
                                                 +---------------+
                                                 | :OrderRepo    |
                                                 +---------------+

序号表示消息顺序，可嵌套表示，如 3.1、3.2 表示消息 3 内部的子消息。
```

- **对象与链路**：对象用矩形表示，对象之间的连线称为链路，是关联的实例。
- **消息与序号**：消息沿链路传递，用编号表示先后顺序，编号可嵌套。
- **优势**：对象之间的拓扑关系一目了然，适合表达多个对象之间的整体协作结构。
- **局限**：消息顺序不如序列图直观，消息数量多时序号可读性下降。

> [!TIP]
> **建议内容**：**序列图与通信图按「关注顺序还是关注结构」来选**。要看「谁先调用谁、耗时在哪」，用序列图；要看「这几个对象彼此如何连接、消息总量如何分布」，用通信图。二者可相互转换，因此不必同时维护两张图，选其一即可。



### 活动图

#### 活动图的基本元素

**活动图**用于描述**活动的控制流与数据流**，形似增强版流程图，但支持并发、泳道与对象流，表达能力强于传统流程图。

- **初始结点与终止结点**：初始结点为实心圆，表示流程起点；终止结点为实心圆外套空心圆，表示流程结束。
- **活动结点与动作**：圆角矩形表示活动或原子动作，是流程中的处理步骤。
- **控制流**：带箭头的实线，表示活动之间的执行顺序。
- **判定结点与合并结点**：菱形表示判定，一个入边多个出边按守卫条件选择；合并结点把多个分支汇合。
- **分叉结点与汇合结点**：粗横线表示分叉，把一条流拆为多条**并发**流；汇合结点等待所有并发流到达后继续。
- **对象结点**：矩形表示活动之间传递的数据对象，用虚线箭头表示对象流。
- **泳道**：把活动按执行者分区，用于表达职责归属。

```text
活动图示例（订单处理流程，含并发）

        (start)
           |
           v
   +---------------+
   | 校验订单合法性 |
   +---------------+
           |
           v
        <decision>
        /        \
  合法 /          \ 不合法
      v            v
  ====== 分叉 ======      +-------------+
  |               |      | 记录拒绝原因 |
  v               v      +-------------+
+--------+   +--------+          |
| 扣减库存|   | 发起支付|         |
+--------+   +--------+          |
  |               |              |
  ====== 汇合 ======             |
  |                              |
  v                              |
+--------+                       |
| 生成订单|                       |
+--------+                       |
  |                              |
  v                              v
   \-------------> (end) <------/

说明：粗横线为分叉与汇合结点，菱形为判定结点，圆角矩形为活动。
```

> [!IMPORTANT]
> **重要内容**：**分叉与判定不要混用**。判定结点（菱形）表达**互斥分支**，同一时刻只有一条路径被走；分叉结点（粗横线）表达**并发分支**，多条路径同时执行并需在汇合结点等待全部完成。把并发画成判定、或把互斥画成分叉，是最常见的语义错误。

**考察形式**：综合知识选择题。



#### 泳道、分支与并发

活动图通过泳道、守卫条件、并发同步与对象流表达流程中的职责划分与控制结构。

- **泳道**：横向或纵向分区，每个分区代表一个执行者（部门、角色或系统），活动落在哪条泳道即表示由谁执行。泳道使跨部门的职责交接一目了然。
- **守卫条件**：判定结点出边上的方括号条件，如「库存充足」「库存不足」，条件必须互斥且穷尽。
- **并发与同步**：分叉出的多条流在汇合结点同步，汇合结点要求**所有入边都到达**才继续。
- **对象流**：用虚线箭头表示数据在活动之间的传递，避免用控制流表达数据依赖。

> [!TIP]
> **建议内容**：**泳道是活动图最有业务价值的元素**。跨部门业务流程的瓶颈往往在泳道交界处——交接次数越多、往返越频繁，效率越低。用泳道画完流程图后，数一数跨泳道的箭头数量，通常就能定位流程改进的重点。

**考察形式**：综合知识选择题。



#### 活动图与流程图的区别

**对比活动图与流程图**：**并发表达**：活动图支持分叉与汇合表达并发，传统流程图不支持。**职责表达**：活动图用泳道表达执行者，流程图无此概念。**数据表达**：活动图可表达对象流，流程图只表达控制流。**语义严格度**：活动图有严格的形式化语义（基于令牌流），流程图语义较宽松。**共同点**：二者都以流程顺序为主线，适合表达业务流程与算法步骤。

> [!NOTE]
> **提醒内容**：活动图与状态机图都描述动态行为，但**视角不同**——**活动图描述「活动之间的流转」**，关注做事的步骤；**状态机图描述「对象所处的状态及其迁移」**，关注对象在不同条件下处于什么状态。同一业务用两种图表达，得到的信息完全不同，应根据关注点选择。

**考察形式**：综合知识选择题。



### 状态机图

#### 状态、转移与事件

**状态机图**（又称状态图）描述**一个对象或系统在生命周期内的状态及其转移**，适用于事件驱动型行为，如订单状态、设备状态、协议状态。

- **状态**：对象在生命周期中满足某条件、执行某活动或等待某事件的状况，用圆角矩形表示，可包含入口动作、出口动作与内部活动。
- **初始状态**：实心圆，表示开始点。
- **终止状态**：实心圆外套空心圆，表示生命周期结束。
- **转移**：状态之间的有向边，表示状态变化。
- **事件**：触发转移的条件，写在转移线上，如「提交」「取消」「支付成功」。
- **守卫条件**：方括号内的布尔条件，事件满足且守卫成立时才触发转移。
- **动作**：转移发生时执行的操作，写作斜线后的表达式。

```text
状态机图示例（订单状态）

      (start)
         |
         v
   +-----------+   提交    +-----------+
   |  已创建   |---------->|  已提交   |
   +-----------+           +-----------+
         ^                       |    \
         |  取消                 |支付 \ 超时
         |                       v      v
   +-----------+  取消    +-----------+  +-----------+
   |  已取消   |<----------|  已支付   |  |  已关闭   |
   +-----------+           +-----------+  +-----------+
                                 | 发货
                                 v
                           +-----------+
                           |  已发货   |
                           +-----------+
                                 | 签收
                                 v
                              (end)

转移标注格式：事件 [守卫条件] / 动作
```

> [!NOTE]
> **提醒内容**：**状态机图的状态必须是「对象所处的状况」，不是「正在做什么动作」**。把「校验订单」这类活动画成状态是错误的，它应出现在活动图里。判断方法：状态通常用形容词或完成时表达（已提交、已支付），而活动用动词表达（校验、计算）。

**考察形式**：综合知识选择题。



#### 复合状态与历史状态

复合状态与历史状态用于表达状态机的层次结构与恢复行为，可显著减少重复转移。

- **复合状态**：状态内部再嵌套子状态机，用于表达层次化的状态结构，减少重复转移。
- **进入点与退出点**：复合状态上与外部连接的显式交互点。
- **历史状态**：用带 H 的圆表示，记录复合状态上次退出时所处的子状态；再次进入复合状态时从历史状态恢复，而不是从初始子状态开始。分为浅历史与深历史。
- **区域**：复合状态内部可划分为多个并发区域，各区域独立迁移，用于表达正交状态。

```text
复合状态与历史状态示例

   +-------------------------------------------+
   |  通话中（复合状态）                         |
   |                                           |
   |   (start) --> [拨号中] --> [振铃中] --> [通话] |
   |                    ^            |          |
   |                    |  对方接听   |          |
   |                    +------------+          |
   |                                           |
   |   (H) 历史状态：记录上次退出时的子状态       |
   +-------------------------------------------+
         |                 ^
   重新拨号|                 | 恢复
         v                 |
   +-----------+     +-----------+
   |  保持中   |---->|  恢复通话 |
   +-----------+     +-----------+
```

> [!IMPORTANT]
> **重要内容**：**历史状态是状态机图中最容易被忽略也最有用的机制**。它解决「中断后如何回到原处」的问题——例如用户拨打客服电话时中途保持，恢复后应回到保持前的子状态而不是重新开始选菜单。凡是存在「可中断且需恢复」的场景，都应考虑历史状态。

**考察形式**：综合知识选择题。



#### 状态机图与活动图的辨析

**对比状态机图与活动图**：**描述对象**：状态机图描述**一个对象**的状态变化，活动图描述**一个流程**的活动流转。**核心元素**：状态机图的核心是状态与转移，活动图的核心是活动与控制流。**触发方式**：状态机图的转移由事件触发，活动图的流转由活动完成触发。**适用场景**：状态机图适合协议、设备、订单等有明确状态集合的对象；活动图适合业务流程、算法步骤等以步骤为主线的场景。**并发表达**：二者都支持并发，状态机图用并发区域，活动图用分叉与汇合。

> [!TIP]
> **建议内容**：遇到「该画状态机还是活动图」的困惑，用一句话判断——**「系统在等什么」用状态机，「系统在做什么」用活动图**。前者关注等待与响应，后者关注步骤与推进。

**考察形式**：综合知识选择题。



### 交互概览图与定时图

#### 交互概览图

**交互概览图**用**活动图的结构组织多个交互引用**，把复杂的交互拆成若干片段并以高层流程串联，用于表达大范围交互的整体框架。

- **交互引用**：用 ref 框引用具体的序列图或通信图，形成层次化的交互描述。
- **控制结点**：沿用活动图的初始、终止、判定、分叉等结点表达片段之间的流转。
- **主要用途**：当一个场景的交互过于复杂、一张序列图无法容纳时，用交互概览图在高层次组织，再逐片段展开细节。

> [!NOTE]
> **提醒内容**：**交互概览图是「图的地图」而不是「图的细节」**。它本身不含消息细节，只有对子交互的引用。因此只在交互规模大到需要分层时才有价值，小型场景直接画序列图即可，不必额外增加一层。

**考察形式**：综合知识选择题。



#### 定时图

**定时图**以**线性时间轴**描述对象状态与时间约束的变化，适合表达实时系统与性能敏感场景的时序关系。

- **生命线**：横向排列，每条生命线表示一个对象，时间轴从左向右推进。
- **状态线**：生命线上的水平线段表示该对象在某状态下的持续时间。
- **消息**：对象之间的消息用箭头表示，可标注发送与接收的时间约束。
- **时间约束**：用花括号标注时长约束或时刻约束，如「不超过 100 毫秒」。
- **持续时间约束**：标注某状态必须持续的最短或最长时间。

> [!TIP]
> **建议内容**：**定时图与序列图的区别在于量化程度**——序列图只表达消息的先后顺序，定时图还能表达「间隔多久」「必须持续多长」。因此在提出响应时间、超时阈值、抖动范围这类硬性时序要求时，定时图是唯一能精确表达的手段。

**考察形式**：综合知识选择题。



### 行为图的选择与组合

#### 按关注点选择行为图

七种行为图对应不同的关注点，选择规则可归纳如下：

- **关注系统边界与功能范围**：用**用例图**。
- **关注业务步骤与分支并发**：用**活动图**。
- **关注单一对象的状态迁移**：用**状态机图**。
- **关注消息的先后顺序**：用**序列图**。
- **关注对象之间的连接与消息分布**：用**通信图**。
- **关注多个交互的整体编排**：用**交互概览图**。
- **关注精确的时间约束与持续时间**：用**定时图**。

> [!IMPORTANT]
> **重要内容**：**行为图之间不是替代关系而是互补关系**。同一系统通常需要多张图——用用例图定边界，用活动图定流程，用序列图定调用时序，用状态机图定关键对象生命周期。判断某张图是否有必要，只看它是否回答了其他图回答不了的问题。

**考察形式**：综合知识选择题。



#### 行为图的组合使用

行为图常见的组合路径如下：

- **需求阶段**：用例图界定功能与参与者，每个关键用例配一份用例描述。
- **分析阶段**：用序列图走查各用例的交互，验证领域模型是否支撑这些交互。
- **设计阶段**：用活动图表达复杂流程与分支，用状态机图表达状态复杂对象，用序列图固定跨模块调用协议。
- **测试阶段**：用用例描述与序列图导出功能测试用例，用活动图的分支与状态机图的转移导出路径覆盖用例。

> [!CAUTION]
> **注意内容**：**行为图的价值在于暴露不一致**，而不在于产出图本身。画序列图时发现的接口缺失、画活动图时发现的职责重叠、画状态机图时发现的非法状态迁移，这些发现才是建模的真正成果。若画完一套图却没有改动任何设计，要么是设计已足够好，要么是图只做了形式上的复制。

**考察形式**：综合知识选择题。
