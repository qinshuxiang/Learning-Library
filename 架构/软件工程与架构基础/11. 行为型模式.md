## 行为型模式

> **全章主脉**：**行为型模式关注对象之间的职责分配与算法封装**，共 11 种，是三大类中数量最多的一类。它们的共同目标是**把易变的行为从稳定的结构中抽离出来**，使行为可以独立扩展或替换。按职责可分为四组——**算法封装**（策略、模板方法、解释器）、**请求处理**（责任链、命令、中介者）、**状态与通知**（状态、观察者、备忘录、迭代器）、**对象访问**（访问者）。全部代码示例均已在 Node 环境实测通过。

### 行为型模式概述

#### 行为型模式的共同目标

行为型模式处理的是「**谁负责做什么、行为如何组织与传递**」的问题，其共同目标有三个：

- **把变化的行为独立出来**：让算法、状态、处理流程可以独立于使用它的对象而演化。
- **解耦发起者与执行者**：请求的发出方不必知道谁处理它、如何处理它，如责任链与命令。
- **在对象之间合理分配职责**：避免职责过度集中或过度分散，如中介者与观察者。

> [!IMPORTANT]
> **重要内容**：**行为型模式的数量为 11 种，是记忆重点**。可按四组快速清点：**算法封装 3 种**（策略、模板方法、解释器）、**请求处理 3 种**（责任链、命令、中介者）、**状态与通知 4 种**（状态、观察者、备忘录、迭代器）、**对象访问 1 种**（访问者），合计 11。



#### 四组模式的职责差异

- **算法封装组**：把算法或流程步骤抽取为可替换、可扩展的形式，客户端无需了解实现细节。
- **请求处理组**：把请求包装为对象或沿链传递，从而实现请求的排队、撤销、转发与解耦。
- **状态与通知组**：管理对象的内部状态变化及其对外通知，并支持状态的保存与遍历。
- **对象访问组**：在不改变元素类的前提下，为元素集合增加新的操作。



### 算法封装组：策略、模板方法与解释器

#### 策略模式

**策略模式**定义**一系列算法，把它们一个个封装起来并使它们可以相互替换**，使算法的变化独立于使用它的客户端。

```js
const priceStrategies = {
  normal: (amount) => amount,
  vip: (amount) => amount * 0.9,
  svip: (amount) => amount * 0.8,
};

class PriceContext {
  constructor(strategy) { this.strategy = strategy; }
  quote(amount) { return this.strategy(amount); }
}

console.log(new PriceContext(priceStrategies.normal).quote(1000));
console.log(new PriceContext(priceStrategies.vip).quote(1000));
console.log(new PriceContext(priceStrategies.svip).quote(1000));

// 输出：
// 普通会员：1000
// VIP：900
// SVIP：800
```

- **角色构成**：**抽象策略**（规定算法接口）、**具体策略**（实现具体算法）、**上下文**（持有策略并在需要时调用）。
- **优点**：算法可自由切换与扩展、消除大量条件分支、每个策略职责单一便于测试。
- **缺点**：客户端必须了解各策略的差异才能选择；策略数量增多时类的数量上升；策略与上下文之间若存在数据依赖，会增加耦合。

> [!TIP]
> **建议内容**：**策略模式最实用的信号是「出现成组的 if 或 switch」**。当一段代码按类型分支执行不同算法，且分支数量还会增加时，就应该考虑策略模式。但要判断清楚：**若分支只是返回不同常量而无独立逻辑，用映射表即可，不必引入策略对象**。



#### 模板方法模式

**模板方法模式**在父类中定义**算法的骨架**，把某些步骤的实现延迟到子类，使子类可以在不改变算法结构的前提下重新定义特定步骤。

```js
class DataImporter {
  import(source) {
    const raw = this.read(source);
    const rows = this.parse(raw);
    return `${this.constructor.name}：${this.save(rows)}`;
  }
  read() { throw new Error('子类必须实现 read'); }
  parse() { throw new Error('子类必须实现 parse'); }
  save(rows) { return `已写入 ${rows.length} 条记录`; }
}

class CsvImporter extends DataImporter {
  read(source) { return source.split('\n'); }
  parse(lines) { return lines.filter((line) => line.trim() !== ''); }
}

class JsonImporter extends DataImporter {
  read(source) { return source; }
  parse(raw) { return JSON.parse(raw); }
}

console.log(new CsvImporter().import('甲\n\n乙\n丙'));
console.log(new JsonImporter().import('[{"id":1},{"id":2}]'));

// 输出：
// CsvImporter：已写入 3 条记录
// JsonImporter：已写入 2 条记录
```

- **模板方法**：父类中固定流程顺序的方法，即上例的 import。
- **基本方法**：由子类实现的可变步骤，即上例的 read 与 parse；save 是父类提供的默认实现，属于**钩子方法**的常见形态。
- **优点**：代码复用度高、算法骨架集中、扩展点明确。
- **缺点**：继承关系导致耦合，父类骨架变化会影响全部子类；受单继承限制，一个子类只能实现一套步骤。

**对比策略与模板方法**：**实现机制**：策略用组合、在运行期替换整个算法；模板方法用继承、在编译期确定部分步骤。**变化粒度**：策略替换的是完整算法，模板方法替换的是算法中的若干步骤。**运行期灵活性**：策略可在运行期切换，模板方法一经继承便固定。**共同点**：二者都实现「不变的部分固定、变化的部分可扩展」，是开闭原则的两种实现路径。

> [!NOTE]
> **提醒内容**：**模板方法与策略模式常被放在一起比较，区分的关键是「换整体还是换局部」**。换整体用策略，换局部步骤用模板方法。若一个算法的步骤顺序固定、只有个别步骤的实现不同，模板方法更合适且代码量更少。



#### 解释器模式

**解释器模式**给定一个语言，**定义它的文法的一种表示，并定义一个解释器**，用该解释器来解释语言中的句子。它本质上是用对象树表示语法规则，并通过递归求值完成解释。

```js
class NumberExpr { constructor(value) { this.value = value; } interpret() { return this.value; } }

class AddExpr {
  constructor(left, right) { this.left = left; this.right = right; }
  interpret() { return this.left.interpret() + this.right.interpret(); }
}

class MulExpr {
  constructor(left, right) { this.left = left; this.right = right; }
  interpret() { return this.left.interpret() * this.right.interpret(); }
}

// 表达式 3 + 4 * 5
const expression = new AddExpr(new NumberExpr(3), new MulExpr(new NumberExpr(4), new NumberExpr(5)));
console.log(expression.interpret());

// 输出：
// 23
```

- **角色构成**：**抽象表达式**（声明解释操作）、**终结符表达式**（文法中的最小单位，如数字）、**非终结符表达式**（由子表达式组合而成，如加法与乘法）、**上下文**（存放解释器之外的全局信息）。
- **优点**：文法可扩展，新增规则只需新增表达式类；语法规则以对象树显式表达，便于理解与修改。
- **缺点**：**文法复杂时类的数量急剧膨胀**，每条规则都要一个类；递归解释带来性能开销；不适合处理复杂文法，复杂文法应改用语法分析器生成工具。

> [!WARNING]
> **警告内容**：**解释器模式的适用范围很窄，只适合文法是「简单且稳定」的场景**。一旦文法规则超过十几种或需要处理运算符优先级与左递归，手工实现的解释器会迅速失控。实践中的正确选择是使用解析器生成工具（如 ANTLR）或直接采用成熟的表达式引擎，而不是自己写解释器。



### 请求处理组：责任链、命令与中介者

#### 责任链模式

**责任链模式**使**多个对象都有机会处理请求**，从而避免请求的发送者与接收者之间的耦合。这些对象被连成一条链，请求沿链传递，直到有一个对象处理它为止。

```js
class Handler {
  constructor(check, onFail) { this.check = check; this.onFail = onFail; this.next = null; }
  setNext(next) { this.next = next; return next; }
  handle(context) {
    if (!this.check(context)) return this.onFail;
    return this.next ? this.next.handle(context) : '全部校验通过';
  }
}

const loginCheck = new Handler((ctx) => ctx.token !== '', '未登录');
const roleCheck = new Handler((ctx) => ctx.role === 'ADMIN', '权限不足');
const stockCheck = new Handler((ctx) => ctx.stock > 0, '库存不足');
loginCheck.setNext(roleCheck).setNext(stockCheck);

console.log(loginCheck.handle({ token: '', role: 'ADMIN', stock: 5 }));
console.log(loginCheck.handle({ token: 't1', role: 'GUEST', stock: 5 }));
console.log(loginCheck.handle({ token: 't1', role: 'ADMIN', stock: 0 }));
console.log(loginCheck.handle({ token: 't1', role: 'ADMIN', stock: 5 }));

// 输出：
// 未登录
// 权限不足
// 库存不足
// 全部校验通过
```

- **纯责任链**：请求必须被某个处理者处理，若无人处理则报错。
- **不纯责任链**：允许某个处理者处理完继续向下传递，或无人处理时静默结束，上例即属此类。
- **优点**：请求发送者与处理者解耦、链的组成可动态调整、符合单一职责（每个处理者只做一件事）。
- **缺点**：不保证请求一定被处理、链过长时性能下降、调试时需沿链追踪，问题定位较难。

> [!TIP]
> **建议内容**：**责任链在 Web 框架中无处不在**——中间件、拦截器、过滤器本质上都是责任链。理解它的关键参数有两个：**链的顺序**与**是否继续传递**。前者决定职责的执行次序，后者决定该处理者是「终结型」还是「透传型」，这两点也是排查中间件类问题时首先检查的地方。



#### 命令模式

**命令模式**把**一个请求封装为一个对象**，从而使你可以用不同的请求对客户进行参数化、对请求排队或记录请求日志，以及支持可撤销的操作。

```js
class Lamp {
  constructor() { this.on = false; }
  turnOn() { this.on = true; return '灯已打开'; }
  turnOff() { this.on = false; return '灯已关闭'; }
}

class TurnOnCommand {
  constructor(lamp) { this.lamp = lamp; }
  execute() { return this.lamp.turnOn(); }
  undo() { return this.lamp.turnOff(); }
}

class RemoteControl {
  constructor() { this.history = []; }
  press(command) { this.history.push(command); return command.execute(); }
  undo() { const command = this.history.pop(); return command ? command.undo() : '没有可撤销的操作'; }
}

const remote = new RemoteControl();
console.log(remote.press(new TurnOnCommand(new Lamp())));
console.log(remote.undo());
console.log(remote.undo());

// 输出：
// 灯已打开
// 灯已关闭
// 没有可撤销的操作
```

- **角色构成**：**命令接口**（声明执行与撤销）、**具体命令**（绑定接收者与动作）、**接收者**（真正执行动作的对象）、**调用者**（持有并触发命令）、**客户端**（创建命令并绑定接收者）。
- **优点**：请求的调用者与执行者解耦、支持撤销与重做、支持请求排队与日志、可把命令序列化为可传输的形式。
- **缺点**：每个动作都要一个命令类，类的数量增加；简单的直接调用被包装为多层跳转，结构变复杂。

**对比命令与策略**：**关注点**：命令关注「把请求对象化」，策略关注「把算法可替换化」。**是否持有接收者**：命令通常持有接收者并调用其动作，策略本身就是算法的实现。**共同点**：二者都把某段行为抽出为独立对象，都可通过配置或注册在运行期替换。

> [!NOTE]
> **提醒内容**：**命令模式是「撤销与重做」功能的常见实现基础**。实现撤销有两种思路——**反向操作**（如开对应关，上例即属此类）与**状态快照**（保存执行前的状态再恢复，即备忘录模式）。选择依据是操作是否容易求逆：容易求逆用反向操作，难以求逆或需要跨多步撤销则用快照。



#### 中介者模式

**中介者模式**用**一个中介对象来封装一系列对象之间的交互**，使各对象不需要显式地相互引用，从而使其耦合松散，并可独立地改变它们之间的交互。

```js
class ChatRoom {
  constructor() { this.members = new Map(); }
  register(name, member) { member.room = this; member.name = name; this.members.set(name, member); return this; }
  send(from, to, text) { this.members.get(to).receive(from, text); }
}

class Member {
  receive(from, text) { this.lastMessage = `${from} 对 ${this.name} 说：${text}`; }
}

const room = new ChatRoom();
const zhang = new Member();
const li = new Member();
room.register('张三', zhang).register('李四', li);
room.send('张三', '李四', '明天开会');
console.log(li.lastMessage);

// 输出：
// 张三 对 李四 说：明天开会
```

- **优点**：把网状交互变为星形交互，对象之间的耦合由数量级降低；交互规则集中在一处便于修改；单个成员可独立复用。
- **缺点**：**中介者容易演化为「上帝类」**，承担过多逻辑而变得难以维护；中介者一旦故障，全部交互受影响，成为单点。

**对比中介者与观察者**：**通信方向**：中介者通常是**多对多的集中式转发**，观察者是**一对多的单向通知**。**是否知晓对方**：中介者中的成员知晓中介者，中介者知晓全部成员；观察者中被观察者不知晓具体订阅者。**目的**：中介者意在收敛复杂的相互引用，观察者意在解耦状态变化与响应用户。

> [!CAUTION]
> **注意内容**：**中介者与外观都起「集中入口」的作用，但目的不同**——**外观是为了让外部使用更简单**，**中介者是为了让内部协作更松耦合**。判断方法看「服务对象」：为系统外部提供简化接口的是外观，为系统内部多个对象协调交互的是中介者。若一个类既对外简化又对内协调，说明职责已混杂，应当拆分。



### 状态与通知组：状态、观察者、备忘录与迭代器

#### 状态模式

**状态模式**允许一个对象在其**内部状态改变时改变它的行为**，使对象看起来像是修改了它的类。它把每个状态封装为独立对象，由状态对象决定在特定动作下的转移。

```js
const transitions = {
  created: { submit: 'submitted', cancel: 'cancelled' },
  submitted: { pay: 'paid', cancel: 'cancelled', timeout: 'closed' },
  paid: { ship: 'shipped' },
  shipped: { receive: 'finished' },
};

class Order {
  constructor() { this.state = 'created'; this.trace = ['created']; }
  trigger(action) {
    const next = transitions[this.state]?.[action];
    if (!next) throw new Error(`状态 ${this.state} 不允许执行 ${action}`);
    this.state = next;
    this.trace.push(next);
    return this.state;
  }
}

const order = new Order();
order.trigger('submit');
order.trigger('pay');
console.log(order.state);
console.log(order.trace.join(' -> '));

// 输出：
// paid
// created -> submitted -> paid
```

- **优点**：把状态相关的行为集中到状态对象中、消除庞大条件判断、状态转移规则显式可查、新增状态符合开闭原则。
- **缺点**：状态数量增多时类的数量增加；状态之间的转移关系可能分散，全局流程不易看清；状态对象的创建与销毁需要管理。

**对比状态与策略**：**结构与手段**：二者都通过委托把行为变化抽离，结构几乎一致。**变化驱动**：状态的变化由对象内部状态驱动、通常自动发生；策略的变化由客户端显式选择、通常由外部决定。**状态之间是否知晓**：状态对象通常知晓并触发下一个状态，策略之间互相独立、互不知晓。**共同点**：都可以消除条件分支，都属于行为型模式。

> [!IMPORTANT]
> **重要内容**：**状态模式的合法性来自「非法转移被显式拒绝」**。上例中从 created 直接执行 ship 会抛出错误，这正是状态机的语义保证。若把所有动作都允许在任何状态下执行，那么状态模式就退化为一组布尔标记，失去了它最重要的价值——**用类型或数据约束非法状态存在**。



#### 观察者模式

**观察者模式**定义对象间的一对多依赖，当**一个对象的状态发生改变时，所有依赖它的对象都得到通知并被自动更新**。

```js
class EventEmitter {
  constructor() { this.listeners = new Map(); }
  on(event, listener) {
    if (!this.listeners.has(event)) this.listeners.set(event, []);
    this.listeners.get(event).push(listener);
    return () => this.off(event, listener);
  }
  off(event, listener) {
    const list = this.listeners.get(event) ?? [];
    this.listeners.set(event, list.filter((fn) => fn !== listener));
  }
  emit(event, payload) { for (const listener of this.listeners.get(event) ?? []) listener(payload); }
}

const emitter = new EventEmitter();
const received = [];
const unsubscribe = emitter.on('order:created', (payload) => received.push(`邮件：${payload.orderNo}`));
emitter.on('order:created', (payload) => received.push(`短信：${payload.orderNo}`));
emitter.emit('order:created', { orderNo: 'A001' });
unsubscribe();
emitter.emit('order:created', { orderNo: 'A002' });
console.log(received.join(' / '));

// 输出：
// 邮件：A001 / 短信：A001 / 短信：A002
```

- **角色构成**：**主题**（被观察者，维护订阅列表并负责通知）、**观察者**（定义更新接口）、**具体观察者**（实现响应逻辑）。
- **推模型与拉模型**：**推模型**由主题把变更数据直接传给观察者（上例即属此类）；**拉模型**只通知「有变化」，由观察者主动回读数据。推模型效率高但耦合变更数据，拉模型耦合低但可能重复读取。
- **优点**：主题与观察者松耦合、支持一对多广播、可在运行期动态增删观察者。
- **缺点**：观察者数量多时通知开销显著；**通知顺序不确定**；若观察者内部又触发新的事件，可能形成循环通知；一旦订阅关系丢失或未及时取消，会造成内存泄漏。

> [!WARNING]
> **警告内容**：**观察者模式最常见的两类线上故障是内存泄漏与循环通知**。前者源于订阅后未取消（如组件销毁时未退订），使已失效的对象被主题持有而无法回收；后者源于观察者在响应中再次发布同一事件，形成无限递归。防御手段是**订阅必返回取消函数并保证在销毁时调用**，以及**为事件传播设置深度或次数上限**。



#### 备忘录模式

**备忘录模式**在**不破坏封装性的前提下，捕获一个对象的内部状态并在该对象之外保存这个状态**，以便以后将该对象恢复到原先保存的状态。

```js
class Editor {
  constructor() { this.content = ''; }
  type(text) { this.content += text; return this; }
  save() { return { content: this.content }; }
  restore(memento) { this.content = memento.content; return this; }
}

class History {
  constructor() { this.stack = []; }
  push(memento) { this.stack.push(memento); return this; }
  pop() { return this.stack.pop(); }
}

const editor = new Editor();
const history = new History();
editor.type('第一版');
history.push(editor.save());
editor.type('，第二版');
const beforeUndo = editor.content;
editor.restore(history.pop());
console.log(`撤销前：${beforeUndo}`);
console.log(`撤销后：${editor.content}`);

// 输出：
// 撤销前：第一版，第二版
// 撤销后：第一版
```

- **角色构成**：**原发器**（产生并使用备忘录的对象，即上例的 Editor）、**备忘录**（存储原发器的内部状态）、**负责人**（保存备忘录但不检查其内容，即上例的 History）。
- **优点**：保留封装边界，状态恢复能力由原发器自身控制；便于实现撤销与回滚。
- **缺点**：**状态较大或保存频率高时内存开销显著**；需要谨慎处理深拷贝，否则备忘录会随原发器变化而变化。

> [!NOTE]
> **提醒内容**：**备忘录必须保存「状态的副本」而不是「状态的引用」**。若备忘录中保存的是对象引用，后续对原发器的修改会同时改变备忘录内容，撤销将失效。这与第 9 篇原型模式中的浅拷贝陷阱是同一类问题，处理方式也一致——按需使用深拷贝。



#### 迭代器模式

**迭代器模式**提供一种方法**顺序访问一个聚合对象中的各个元素，而不暴露该对象的内部表示**。它把遍历行为从聚合对象中抽离出来。

```js
const treeData = {
  value: 1,
  children: [
    { value: 2, children: [] },
    { value: 3, children: [{ value: 4, children: [] }] },
  ],
};

function* depthFirst(node) {
  yield node.value;
  for (const child of node.children) yield* depthFirst(child);
}

const collected = [];
for (const value of depthFirst(treeData)) collected.push(value);
console.log(collected.join(' -> '));

// 输出：
// 1 -> 2 -> 3 -> 4
```

- **角色构成**：**迭代器**（定义访问与遍历接口）、**具体迭代器**（实现遍历算法并记录当前位置）、**聚合**（存储元素并提供创建迭代器的方法）。
- **优点**：遍历算法与数据结构解耦、同一聚合可提供多种遍历方式、客户端无需了解内部结构。
- **缺点**：对简单集合而言引入迭代器属于过度设计；迭代期间修改聚合内容会导致行为未定义。

> [!TIP]
> **建议内容**：**在支持生成器或迭代协议的语言中，迭代器模式通常是内建能力**，无需手写迭代器类。上例用生成器函数递归遍历树，代码量远小于手写迭代器，且天然支持惰性求值与提前退出。判断是否需要手写迭代器，只看一条：**该语言是否已提供惰性遍历机制**。



### 对象访问组：访问者模式

#### 访问者模式

**访问者模式**表示**一个作用于某对象结构中的各元素的操作**，使**在不改变各元素的类的前提下定义作用于这些元素的新操作**。

```js
const docNodes = [
  { type: 'text', value: '标题' },
  { type: 'image', src: 'cover.png' },
  { type: 'link', href: 'https://example.com' },
];

const visitors = {
  render: {
    text: (node) => node.value,
    image: (node) => `<img src="${node.src}">`,
    link: (node) => `<a href="${node.href}">链接</a>`,
  },
  weight: { text: () => 1, image: () => 5, link: () => 2 },
};

const visit = (visitor, node) => visitors[visitor][node.type](node);
console.log(docNodes.map((node) => visit('render', node)).join(' | '));
console.log(docNodes.map((node) => visit('weight', node)).reduce((sum, n) => sum + n, 0));

// 输出：
// 标题 | <img src="cover.png"> | <a href="https://example.com">链接</a>
// 总权重：8
```

- **角色构成**：**访问者**（为每个元素类型声明一个访问方法）、**具体访问者**（实现各元素上的操作）、**元素**（声明接受访问者的方法）、**对象结构**（元素的集合，负责遍历并让访问者访问各元素）。
- **双重分派**：调用结果同时取决于**访问者的类型**与**元素的类型**，这是访问者模式的结构核心，也是它与普通多态的分野。
- **优点**：新增操作只需新增访问者，不必修改元素类；把相关操作集中到一个访问者中，避免操作散落在各元素类里。
- **缺点**：**新增元素类型困难**——每增加一种元素，所有访问者都要新增对应方法；元素需要向访问者暴露足够的内部信息，可能削弱封装。

> [!IMPORTANT]
> **重要内容**：**访问者模式的取舍方向与多数模式相反**——它让「**新增操作容易、新增元素困难**」。因此适用条件是**元素类型稳定而操作频繁增加**，典型场景是编译器语法树（节点种类固定，但需要类型检查、代码生成、优化等多种遍历操作）。若元素类型变化频繁，访问者会变成维护负担。



### 行为型模式的横向比较

#### 结构相似的模式的区分

行为型模式中有多对模式结构相近，区分只能靠意图：

- **状态与策略**：结构与实现手段几乎相同。**状态**由内部状态驱动转移，状态之间知晓彼此；**策略**由外部选择，策略之间互不知晓。
- **策略与命令**：策略封装算法本身，命令封装「请求加接收者」。
- **模板方法与策略**：模板方法用继承换局部步骤，策略用组合换整体算法。
- **中介者与观察者**：中介者是集中式多向转发，观察者是一对多单向通知。
- **命令与备忘录**：命令用反向操作实现撤销，备忘录用状态快照实现撤销，二者常组合使用。
- **责任链与装饰器**：二者都形成链式结构。**责任链**的节点可能终止处理或继续传递，关注「谁来处理」；**装饰器**的节点必然转发并叠加功能，关注「叠加了什么」。



#### 选用要点

选择行为型模式的判断链如下：

- **出现成组条件分支且各分支是独立算法**：用**策略**。
- **算法骨架固定、个别步骤可变**：用**模板方法**。
- **需要按固定文法解析简单表达式**：用**解释器**。
- **多个对象可能处理同一请求且顺序可变**：用**责任链**。
- **需要撤销、排队、日志或把请求参数化**：用**命令**。
- **对象之间相互引用过多形成网状依赖**：用**中介者**。
- **行为随内部状态变化且存在非法状态转移**：用**状态**。
- **一处变化需要通知多个依赖方**：用**观察者**。
- **需要保存与恢复对象的历史状态**：用**备忘录**。
- **需要在不暴露内部结构的前提下遍历聚合**：用**迭代器**。
- **元素类型稳定但需要频繁增加新操作**：用**访问者**。

> [!TIP]
> **建议内容**：行为型模式的记忆可按「**三封装、三请求、四状态通知、一访问**」清点——算法封装组是策略、模板方法、解释器；请求处理组是责任链、命令、中介者；状态与通知组是状态、观察者、备忘录、迭代器；对象访问组是访问者。合计 11 种，是三大类中数量最多者。

> [!CAUTION]
> **注意内容**：**模式的数量与系统质量没有正相关**。一个项目引入了二十种模式却无人能读懂主流程，其可维护性远低于只用三四种模式的清晰代码。模式的价值体现在**它消除了哪种变化带来的修改成本**；若回答不出这个问题，就不要引入它。判断设计是否成熟，标准是**读写代码的人能否在三分钟内理解一处变更应该改在哪里**。
