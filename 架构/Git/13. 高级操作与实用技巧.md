## 高级操作与实用技巧

### 拣选提交 cherry-pick

#### cherry-pick 的定义与使用场景

**cherry-pick（拣选提交）**：把提交历史中某个指定的提交复制到当前分支顶端，产生一个内容相同但哈希不同的新提交。

- 它复制的是该提交引入的变更，在新分支上重新生成提交；原分支上的提交原样保留，两个分支随后各自独立演进。
- 典型场景：某个缺陷修复先提交在了开发分支上，需要单独带到发布分支，而不想把整个开发分支合并过去。
- 另一常见场景：从功能分支里只挑出一个已经稳定的提交进入主干，其余提交仍在开发中。

> 辨析：merge 带来的是一个分支的全部提交与历史，cherry-pick 只带来指定的一个或一段提交。正因为是复制而非移动，它适合补丁式的跨分支搬运，不适合大规模的整体同步。



#### cherry-pick 的写法与冲突处理

cherry-pick 既接受单个提交哈希，也接受一段连续区间，冲突处理流程与合并冲突一致。

```bash
git cherry-pick a1b2c3d              # 把单个提交复制到当前分支顶端
git cherry-pick a1b2c3d^..e4f5g6h    # 复制从 a1b2c3d 到 e4f5g6h 的连续提交
git cherry-pick --no-commit a1b2c3d  # 只把变更放进暂存区，不自动生成提交
```

- 区间写法 起点..终点 表示应用起点之后、直到终点为止的提交；想连起点本身一起应用，把起点写成 起点哈希^ 的形式。
- 使用 --no-commit 时变更停留在暂存区，允许拆分或修改后再自行提交。
- 应用时若与当前分支冲突，Git 会停下并标记冲突文件；手工解决冲突后执行 git add 标记已解决，再执行 git cherry-pick --continue 继续剩余拣选；执行 git cherry-pick --abort 可放弃整次拣选、回到开始前的状态。

> 速记：**单给哈希摘一个，给区间摘一串；卡在冲突就 continue，后悔就 abort**。



### 二分定位 bisect

#### bisect 的定义与原理

**bisect（二分定位）**：用二分法在提交历史中自动定位引入缺陷的那个提交的排查工具，把逐个提交的人工核对压缩成对数次数的判定。

- 使用前提：缺陷可以被明确判定——某个提交之后出现，而更早的提交正常。
- 它不分析代码内容，只负责在好与坏之间自动切换工作区；每一次是好是坏完全由使用者给出。
- 历史越长收益越大：一千个提交通常十次左右判定即可锁定目标。



#### bisect 的完整流程

```bash
git bisect start          # 开始二分
git bisect bad            # 当前所在的提交已经出问题
git bisect good v1.4.0    # 指定一个确认正常的提交（哈希或标签均可）
# Git 自动切换到好与坏之间的中间提交，逐个检查后给出结论
git bisect good           # 中间提交正常，问题在它之后
git bisect bad            # 中间提交已出问题，问题在它之前
# 重复判定，直到 Git 打印出第一个引入缺陷的提交
git bisect reset          # 结束二分，回到出发前的分支
```

- good 与 bad 可以多次交替执行，Git 每次都把范围折半；最终剩下的那个提交就是引入缺陷的提交。
- 定位到目标提交后，再用日志与差异查看它改动了什么，缺陷原因通常一目了然。

> 速记：**start 开局、bad 标坏、good 标好、反复折半、reset 收尾**。全程判定标准必须一致，否则二分结果不可信。



### 子模块 submodule

#### 子模块的定义与添加

**子模块（submodule）**：在一个 Git 仓库里嵌入对另一个 Git 仓库的引用；主仓库只记录子模块仓库的地址与它指定的那一个提交，不复制其文件内容。

- 适合把公共组件、第三方库作为独立仓库引用，各仓库保持各自独立的提交历史与权限。
- 添加命令：git submodule add 仓库地址 本地路径；完成后主仓库多出两处记录——一个 .gitmodules 配置文件和一个指向子模块当前提交的记录。



#### 子模块的克隆与更新

```bash
git submodule add https://example.com/libs/ui.git libs/ui   # 添加子模块
git clone https://example.com/project.git                   # 克隆主仓库
git submodule update --init                                 # 拉取子模块的实际内容
git submodule update --remote                               # 更新到子模块上游的最新提交
```

- 克隆主仓库后，子模块目录默认是空的；必须执行 submodule update --init 才会把内容检出到本地。
- 更新的基本流程：进入子模块目录，拉取上游并切换到目标提交，回到主仓库把子模块指针的变化作为一个提交保存。

> [!CAUTION]
> **注意内容**：clone 默认不包含子模块的内容，只留下空目录与引用记录；可在克隆时加 --recurse-submodules 参数，让 Git 一次性完成主仓库与全部子模块的检出。

> 速记：**主仓库存地址加提交号，内容要靠 update 拉下来；clone 不带子模块，init 之后才有货**。



### 工作树 worktree

#### worktree 的定义与常用命令

**工作树（worktree）**：让同一个仓库同时检出多个工作目录的机制，每个工作目录对应一个分支，彼此互不干扰。

- 典型用法：一个目录检出稳定版随时可发布，另一个目录检出开发版继续写代码；或者一边修复线上缺陷，一边开发新功能，免去 stash 或反复切换分支。
- git worktree add 路径 分支名：在指定路径新建工作树并检出该分支。
- git worktree list：列出主工作树与全部附加工作树及其所在分支。
- git worktree remove 路径：删除不再需要的工作树，分支与提交历史仍保留在仓库中。

```bash
git worktree add ../release-check v2.3   # 在 ../release-check 检出 v2.3 分支
git worktree list                        # 查看全部工作树
git worktree remove ../release-check     # 用完移除该工作树
```

> 辨析：多个工作树共享同一个仓库对象库，磁盘占用远小于多份完整克隆；但同一分支同一时刻只能被一个工作树检出，避免两处同时编辑互相覆盖。

> 速记：**一个仓库、多个目录、各占一个分支；add 开、list 看、remove 收**。



### 钩子 hooks

#### 钩子的定义与常用钩子

**钩子（hooks）**：存放在 .git/hooks 目录下、在提交与推送等特定动作前后由 Git 自动执行的脚本，用于在关键节点强制执行检查。

- **pre-commit**：提交前执行，用于校验代码风格、阻止提交遗留调试代码的快照。
- **commit-msg**：以提交消息文件为参数执行，校验消息是否符合团队格式。
- **pre-push**：推送前执行，是推送前的最后一道检查，如运行测试。
- **post-merge**：合并或拉取完成后执行，常用于自动安装依赖。



#### 最小 pre-commit 示例

一个只做一件事的 pre-commit 钩子：发现暂存区里遗留调试输出就退出非零，阻止这次提交。

```bash
#!/bin/sh
# .git/hooks/pre-commit：暂存区出现调试残留时阻止提交
if git diff --cached | grep -q "console.log"; then
  echo "暂存区存在 console.log，请先移除调试代码"
  exit 1
fi
```

- 保存后需赋予可执行权限：chmod +x .git/hooks/pre-commit。
- 钩子脚本退出码非零即中止当前操作：pre-commit 失败，提交就不会发生。
- 钩子脚本位于仓库的 .git 目录内，不属于工作区文件，因此不进入版本控制、也不随 clone 传播；团队通常用 husky 等工具把钩子纳入项目依赖统一管理。

> [!WARNING]
> **警告内容**：钩子只在本地生效且不随 clone 传播，本机配置好的检查到了同事机器上并不存在；团队级的强制检查应交给 husky 等工具或服务端校验，不能只依赖个人本地钩子。

> 速记：**钩子按动作命名，前置可拦截、后置只通知；本地私有、不随 clone，团队统一交给 husky**。
