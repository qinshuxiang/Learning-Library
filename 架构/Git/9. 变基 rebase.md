## 变基 rebase

### 变基的定义

#### 变基与合并的历史形态差异

**变基（rebase）**：是**把当前分支的一系列提交摘下来，在目标分支的最新提交之上重新播放一遍**的操作，播放完成后历史呈一条直线。

- **变基改写为线性历史**：分叉消失，提交像从未分出过一样排成一列，仓库历史干净可读。
- **合并保留分叉历史**：分叉如实保留，另加一个合并提交记录汇合点，历史真实但视觉上复杂。
- **共同目的**：合并与变基都是**整合分支**的手段，最终内容一致，差别只在历史形态。

> [!IMPORTANT]
> **重要内容**：变基是重放而非搬运：重放产生的是一批内容等价但提交哈希全新的提交，原来的旧提交依然留在对象库中。理解这一点是掌握变基黄金法则（见下文）的前提。



### 变基的原理与操作

#### 变基的三步原理

变基的内部过程可以拆成三步：

1. **找共同祖先**：定位当前分支与目标分支的最近共同祖先提交。
2. **提取差异**：把当前分支自共同祖先之后的每个提交依次做成临时补丁。
3. **切换基底重放**：把当前分支的基点移到目标分支的末端，逐一应用补丁，生成一串新提交。

基本用法：

```bash
git checkout dev      # 站在要被变基的分支上
git rebase main       # 把 dev 的提交变基到 main 之上

# 也可以一步完成，含义与上面两行相同
git rebase main dev
```

变基完成后，dev 的历史变为 main 之后直排一串新提交；此时回到 main 执行 git merge dev，只会发生快进，得到完全线性的历史。

> 变基的判定标准：**谁变基，谁的历史被改写**。在 dev 上执行 git rebase main，被重放的是 dev 的提交，main 不受影响；先把要改写的工作线检出，再执行变基。



### 交互式变基

#### rebase -i 的四种用法

**交互式变基（rebase -i）**：在变基的同时打开一份待办清单，允许对目标区间内的提交逐个处置，是**整理尚未推送的本地提交**的核心工具。

- **调整提交顺序**：交换待办清单中各行的顺序，重放即按新顺序进行。
- **squash 合并提交**：把一个提交并入它的上一个提交，多个小提交缩成一个。
- **reword 修改提交消息**：保留提交内容，重写提交消息。
- **edit 拆分提交**：重放暂停在该提交处，可用 reset 把它拆成多个更小的提交。

执行 git rebase -i main 后打开的待办清单示例：

```text
pick a1b2c3d 添加登录表单
squash e4f5a6b 修正表单样式
pick b7c8d9e 接入登录接口

# 命令含义：
# pick：保留该提交，原样重放
# squash：把该提交并入上一个提交，提交消息合并
# reword：保留该提交，但修改它的提交消息
# edit：重放暂停在该提交，便于拆分或修改
# 各行自上而下就是提交的先后顺序，直接编辑清单即可调整
```

保存退出清单后，Git 按编辑后的安排重放提交。

> 交互式变基只应作用于**尚未推送的私有提交**：它会改写提交哈希，一旦这些提交已被他人拉取，就落入变基黄金法则的禁区（见下文）。



### 变基黄金法则

#### 不要对公共提交变基

**变基黄金法则**：**不要对已推送到公共仓库、且他人可能基于其工作的提交执行变基**。

原因在于变基产出的是**等价但哈希不同的新提交**：

- 他人基于旧提交 C2 开发并推送了自己的工作；你把 C2 变基成内容相同但哈希不同的 C2 加撇号。
- 对方的仓库里同时存在旧 C2 与新 C2 加撇号，Git 视它们为两个不同的提交，同一份工作在两条历史里重复出现。
- 这些重放出来的副本被称为**幽灵提交**，随后的每次合并都要反复处理同一批等价提交，历史一片混乱。

> [!WARNING]
> **警告内容**：对公共提交变基的后果是全队历史污染：协作者的仓库会出现成对的幽灵提交，每次拉取与合并都纠缠不清，修复成本远超变基带来的整洁收益。推送之前变基随便用，推送之后变基要停手。

**补救方式**：变基已经发生时，各方执行 git pull --rebase 把自己的本地提交变基到重放后的新历史之上，使本地旧提交被新提交取代；必要时配合 reset 丢弃基于旧提交的工作，再与新历史对齐。



### pull --rebase

#### 拉取时变基

**git pull --rebase**：在拉取远程更新时，**把本地尚未推送的提交变基到远程新提交之上**，而不是生成一个合并提交。

```bash
git pull --rebase           # 本次拉取采用变基
git config pull.rebase true # 设为默认行为，此后 git pull 一律变基
```

- 普通 git pull 的隐患：本地与远程各有新提交时，每次拉取都产生一个合并提交，历史被大量拉取合并的噪音填满。
- pull --rebase 的效果：本地提交移到远程新提交之上，历史保持直线，无意义的合并提交不再出现。
- 适用前提：本地待推送的提交尚未共享给他人，符合变基黄金法则。

> [!TIP]
> **建议内容**：个人开发或约定了线性历史的团队，可用 git config pull.rebase true 把变基设为拉取默认值，从机制上杜绝拉取产生的合并提交噪音。



### 选择建议

#### 公共分支用合并、私有分支用变基

**合并与变基的选择标准是分支的公开程度**：公共分支的历史是团队的共同资产，不可改写；私有分支只有自己使用，怎么整洁怎么来。

- **公共分支用合并**：主干这类多人共用的分支只接受合并，历史只增不改，任何人随时可以信任它。
- **私有分支用变基**：自己的功能分支在推送前随意变基、整理提交，合并进主干前先把分叉抚平。
- **团队须统一约定**：合并与变基的选择不是纯技术问题，而是团队契约；成员策略不一致时，历史照样混乱。

> 通说认为，小团队常约定**主干只进不改写历史**：进入主干的提交永不变基，分支上的私有提交推送前自由变基。两条规则合用，既保证主干可信，又保住历史的整洁。
