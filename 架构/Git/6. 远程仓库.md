## 远程仓库

### 远程仓库的定义与作用

#### 远程仓库与默认名 origin

**远程仓库**：托管在网络上的仓库版本，可以是 GitHub、Gitee 等平台上的仓库，也可以是团队内网服务器或同事电脑上的仓库，用于**协作与备份**。

- **协作**：多人各自克隆同一仓库，各自提交后通过推送与拉取交换工作成果。
- **备份**：本地仓库损坏或丢失时，远程保存着全部历史，可随时重新克隆恢复。
- **origin**：clone 时 Git 自动为来源远程起的**默认名**，习惯上团队固定用它指代主仓库；名字本身并无特殊含义，只是约定俗成。

> 远程仓库与本地仓库地位对等：Git 是分布式版本控制，远程并不比本地更权威，它只是团队成员交换提交的中转站。同一仓库可以同时配置多个远程，如一个 origin 加一个上游仓库。



#### 查看与增删远程

**git remote**：列出已配置的远程名；加 **-v** 同时显示抓取与推送的地址。增删改通过子命令 add、remove、rename 完成。

- **git remote**：只列远程名，如 origin。
- **git remote -v**：列出远程名与对应地址。
- **git remote show 远程名**：显示某远程的详细信息，如分支跟踪关系、抓取与推送地址。
- **git remote add 简称 地址**：添加一个新远程。
- **git remote remove 简称**：移除远程。
- **git remote rename 旧名 新名**：重命名远程。

```bash
git remote add upstream https://github.com/example/project.git
git remote -v
# origin    https://github.com/me/project.git (fetch)
# origin    https://github.com/me/project.git (push)
# upstream  https://github.com/example/project.git (fetch)
# upstream  https://github.com/example/project.git (push)
```

> remote 的增删只修改本地配置，不影响远程服务器上的任何数据；remove 之后重新 add 即可恢复。origin 只是默认名，rename 改名不触碰任何历史与提交。



### 拉取：fetch 与 pull

#### fetch 与 pull 的对比

**git fetch**：把远程的新提交下载到本地的**远程跟踪分支**，不合并、不改工作区；**git pull**：等于 fetch 加合并，下载后立即合并进当前分支，一步到位。

- **git fetch**：稳妥的先看后合——下载后可用 log、diff 检查远程改了什么，再决定是否合并。
- **git pull**：快捷的下载即合——省一步操作，但远程改动与本地改动冲突时，冲突处理在 pull 过程中被立刻推到面前。
- 对比记忆：**稳妥的 fetch 加自行合并** 对 **快捷但易冲突的 pull**；不确定远程状态时用 fetch，单人维护的日常分支用 pull 足够。



#### 远程跟踪分支的只读性质

**远程跟踪分支**：形如 **origin 分支名**（如 origin/main）的只读指针，记录"上次与远程同步时，远程分支停在哪里"。

- 它由 Git 在 fetch、pull 时自动更新，**本地不能直接向它提交**。
- 可以查看与预览：log origin/main 看它的历史，checkout origin/main 进入只读预览。
- 它是 fetch 与本地分支之间的中间层：fetch 只更新它，不碰本地分支；合并由 pull 或手动 merge 完成。

> origin/main 这类名字中，origin 是远程名、main 是远程上的分支名；它是本地的"远程快照"，只有 fetch 之后才与远程服务器的真实状态一致。区分"快照"与"实时"，是理解 fetch 行为的关键。



### 推送

#### push 的基本用法与被拒情形

**git push 远程名 分支名**：把本地分支的提交上传到远程的对应分支，如 push origin main。

- 推送被拒绝的典型情形：远程分支上有**本地没有的新提交**（如同事先推了代码），Git 拒绝覆盖，要求先整合远程改动。
- 处理方式：先 fetch 或 pull 把远程新提交拉下来合并，再重新推送。
- 默认配置下不允许直接覆盖远程历史，强推需显式加 --force，属于协作中的高危操作。

> [!IMPORTANT]
> **重要内容**：推送被拒的正确流程是"先拉取、再推送"：pull 整合远程改动并解决冲突后，push 自然成功。切勿在未理解后果时使用 --force 强推，它会抹掉远程上他人的提交。



#### 上游分支与 push -u

**上游分支（upstream）**：本地分支所跟踪的远程分支，建立跟踪关系后 push、pull 可以省略远程名与分支名参数；**push -u**（--set-upstream）在首次推送时建立这一关系。

- 首次推送新分支：git push -u origin 分支名，此后在该分支内 push、pull 不再带参数。
- 跟踪关系的价值：pull 默认拉取上游分支的更新，status 能显示本地分支相对上游领先、落后多少个提交。

```bash
git push -u origin feature-search
# 建立跟踪关系后，在同分支内：
git push
git pull
```



### 远程地址的两种协议

#### HTTPS 与 SSH 的对比

远程地址有两种常用协议：**HTTPS**（地址以 https:// 开头）与 **SSH**（地址以 git@ 开头），差别集中在**认证方式**。

- **HTTPS**：推送时用**用户名加密码**（或凭据管理器保存的令牌）认证，配置门槛低，克隆公开仓库无须任何准备。
- **SSH**：用**密钥对**认证——私钥留在本机、公钥登记在托管平台，推送拉取**免密**。
- 对比记忆：**HTTPS 的账号密码认证** 对 **SSH 的密钥对免密**；偶尔使用选 HTTPS，团队长期开发推荐 SSH。



#### 配置 SSH 密钥的步骤

配置 SSH 认证分三步：生成密钥对、复制公钥、登记到托管平台。

1. 执行 ssh-keygen -t ed25519 -C "邮箱"，一路回车，在 .ssh 目录下生成私钥与以 .pub 结尾的公钥。
2. 用文本编辑器或系统剪贴板命令查看并复制公钥文件的完整内容。
3. 在托管平台的 SSH 设置页（如 GitHub 的 SSH and GPG keys）粘贴公钥并保存。

```bash
ssh-keygen -t ed25519 -C "you@example.com"
ssh -T git@github.com   # 验证与平台的连接是否成功
```

> 私钥等同于身份，绝不外发、不提交进仓库，用于登记平台的只有公钥。验证配置用 ssh -T 而不是直接 push，避免误传提交。



### 克隆仓库

#### clone 做了什么

**git clone 地址 目录名可选**：把远程仓库完整复制到本地，省略目录名时按仓库名自动创建。clone 一条命令背后完成了四件事。

1. **初始化**本地仓库，等价于执行 init。
2. **添加远程**并自动命名为 origin。
3. **拉取全部历史**：所有分支的历史提交都下载到本地。
4. **检出默认分支**（如 main）到工作区。

> clone 下载的是**所有分支**的完整历史，而工作区只检出默认分支；其余分支在本地以远程跟踪分支（origin 分支名）的形式存在。要在某个分支上工作，直接 checkout 分支名，Git 会自动创建对应的本地跟踪分支并关联上游，无须手动设置。
