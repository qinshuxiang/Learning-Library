## 标签与版本发布

### 标签的定义与用途

#### 标签的定义

**标签（tag）**：是指向某一个提交的固定标记，用来给版本历史钉上里程碑，最常见的用途是标注发布点（如 v1.0.0）。

- 标签指向一个具体的提交，含义是"这个时刻的代码值得记住"。
- 典型场景：发布版本、标记重大重构的完成点、给演示当天的代码留坐标。
- 标签名在同一仓库内唯一，命名通常遵循语义化版本规范（见下文）。

> 标签解决的问题很明确：分支会一直向前走，而已发布的版本需要原地不动。有了标签，任何时候都能精确回到 v1.0.0 发布那一刻的代码状态。



#### 标签与分支的区别

**分支**与**标签**都指向提交，但**分支**会随新提交的写入不断向前移动，**标签**创建后固定不动，永远指向同一个提交。

- **分支**：可移动的指针，每次提交都会让它指向新的提交，用来承载正在进行的开发。
- **标签**：不可移动的指针，创建时钉在某个提交上，之后不再变化，用来记录历史坐标。
- **分工**：开发过程交给分支，发布节点交给标签，两者互不替代。

> 速记：**分支是会动的书签，标签是焊死的里程碑**。无论主线推进到多远，切到 v1.0.0 标签，看到的永远是发布那一刻的样子。



### 轻量标签与附注标签

#### 轻量标签

**轻量标签（lightweight tag）**：只是一个指向某提交的引用，不含任何附加信息，像一支永不移动的分支。

- 本质：一个只存提交哈希的引用文件，没有标签者、日期、说明等元数据。
- 创建方式：git tag 标签名，一行即可。
- 适用：个人临时标记，例如在实验性提交旁做个记号。

> 轻量标签与分支的唯一差别是动与不动：分支随提交前移，轻量标签固定。它没有可展示的附加内容，因此 git show 的输出与直接查看那个提交几乎一样。



#### 附注标签

**附注标签（annotated tag）**：是存储在对象库中的一个完整 Git 对象，包含标签者姓名、邮箱、打标签日期与标签说明，还支持 GPG 签名。

- **完整对象**：有自己的校验和，指向某个提交，可被校验与验证。
- **元数据齐全**：记录谁在何时打了这个标签、说明了什么，是可审计的发布记录。
- **可签名**：可为标签对象附加 GPG 签名，证明发布来源（详见 Pro Git 第二版"签署工作"一章）。
- 创建方式：git tag -a 标签名 -m 消息。

> 辨析两类标签的判断标准是"要不要元数据"：需要向使用者交代谁发布的、何时发布的、这次发布了什么，就打附注标签；只是自己留个坐标，轻量标签足够。通说认为正式发布一律使用附注标签。



### 标签的常用操作

#### 打标签与补打标签

git tag 命令负责创建标签：加 -a 打附注标签，在末尾附上提交哈希可给历史提交补打。

```bash
# 给当前提交打轻量标签
git tag v1.0.0

# 给当前提交打附注标签，-m 后接标签说明
git tag -a v1.1.0 -m "发布 1.1.0：新增导出功能"

# 给历史提交补打附注标签：先找到提交哈希，再对它打标签
git log --oneline
git tag -a v0.9.0 1a2b3c4 -m "补标 0.9.0：当时的稳定版本"
```

- git tag 标签名：打轻量标签，指向当前提交。
- git tag -a 标签名 -m 消息：打附注标签；省略 -m 会弹出编辑器要求填写说明。
- git tag -a 标签名 历史提交哈希：补打标签，适合"发完才想起要标"的场景。

> 补打标签不必先切到那个提交，把哈希跟在标签名后即可，标签会钉在指定提交上；漏写哈希则钉在当前提交，这是常见的误操作来源。



#### 查看、过滤与删除标签

git tag 的其余子命令负责检索、检视与删除，均为本地操作。

```bash
# 列出全部标签
git tag

# 按模式过滤，只看 1.x 系列
git tag -l "v1.*"

# 查看标签详情：附注标签显示标签者与说明，轻量标签只显示提交内容
git show v1.1.0

# 删除本地标签
git tag -d v0.9.0
```

- git tag -l 模式：过滤标签，-l 可写为 --list，支持通配符，标签多时按前缀检索。
- git show 标签名：查看标签指向的提交，附注标签还会列出标签者、日期与说明。
- git tag -d 标签名：删除本地标签，不影响远程，远程需单独删除（见下文）。

> git show 对两类标签的输出差异可以反过来当"体检手段"：输出里多出标签者、日期与说明段落的是附注标签，直接就是提交内容的是轻量标签。



### 标签的远程操作

#### 推送标签

git push 默认不传送标签，标签必须显式推送。

```bash
# 推送单个标签
git push origin v1.1.0

# 推送全部本地标签（含轻量与附注）
git push origin --tags

# 推送分支提交的同时，只附带附注标签
git push origin --follow-tags
```

- git push 远程名 标签名：推送指定标签。
- git push 远程名 --tags：一次性推送全部标签，临时轻量标签也会一并上去。
- git push 远程名 --follow-tags：只随分支推送附注标签；通说认为这是更稳妥的推送方式，个人实验性的轻量标签不会混进公共仓库。

> --tags 与 --follow-tags 的取舍是"全量同步"与"克制发布"之别：团队仓库建议约定只推附注标签，避免个人记号污染远程标签列表。



#### 删除远程标签

删除远程标签有两种等价写法，本地标签不受影响，需另行删除。

```bash
# 写法一：把空引用推到远程标签上，即删除
git push origin :refs/tags/v1.1.0

# 写法二（语义更明确）
git push origin --delete v1.1.0
```

- git push 远程名 :refs/tags/标签名：冒号前留空，表示"用空值覆盖远程引用"，效果是删除。
- git push 远程名 --delete 标签名：等价且更易读，两种写法选其一即可。

> [!CAUTION]
> **注意内容**：本地与远程标签的删除互不影响，要分别执行 git tag -d 与 git push --delete。此外，删除远程标签并不能撤回已发布的内容——依赖该版本的构建产物不会随之消失，误发版本的处理办法是发布新的修订版，而不是只删标签。



### 语义化版本

#### 版本号的构成

**语义化版本（Semantic Versioning，SemVer）**：是社区通行的版本号规范，格式为主版本号.次版本号.修订号，三个非负整数从左到右递增频率依次降低。

- **主版本号**：包含不兼容的改动时递增，使用者需要适配，如 1.x 升到 2.x。
- **次版本号**：包含向下兼容的新功能时递增，如 1.1 升到 1.2。
- **修订号**：包含向下兼容的缺陷修复时递增，如 1.1.0 升到 1.1.1。
- 起始值各团队约定不同，1.0.0 通常代表首个正式稳定版；0.x 阶段表示接口尚未稳定。



#### 与标签配合的发布惯例

发布流程把标签与语义化版本绑定，从打标签到写说明有固定做法。

- 每次发布在对应提交上打附注标签，标签名即版本号（如 v2.0.0），前缀 v 是社区惯例。
- 发布说明写进 -m 消息：主版本号变化时写清迁移要点，次版本号变化时列出新增功能。
- 版本号一旦发布即不可复用：撤销发布时发布新的修订版，而不是把同号标签改指向。

> 速记口诀：**破坏兼容动首位，新增功能动中间，修复缺陷动末位**。标签与语义化版本的关系是载体与内容：标签是钉在提交上的载体，版本号是写在载体上的内容。
