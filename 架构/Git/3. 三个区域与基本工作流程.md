## 三个区域与基本工作流程

### 三个工作区域

Git 管理的项目内部存在**三个工作区域**：**工作区**（working tree）、**暂存区**（staging area，也称 index）与**版本库**（repository）。

- **工作区（working tree）**：本地磁盘上能直接看到、直接编辑的项目目录，日常写代码、改文件都发生在这里。
- **暂存区（staging area 或 index）**：一份保存着下次提交内容清单的区域，物理上通常存放在 .git 目录下的 index 文件中；它像一个购物车，决定本次提交装哪些修改。
- **版本库（repository，又称仓库）**：项目根目录下名为 .git 的隐藏目录，保存项目的全部提交历史与元数据，是 Git 的核心数据所在。

数据流向固定为一条流水线：工作区的修改经 git add 进入暂存区，暂存区的内容经 git commit 固化进版本库。

> 暂存区是 Git 区别于很多版本控制系统的设计：提交内容先经过一层缓冲，可以精确挑选这次提交只包含哪些修改，把不相干的改动拆成多次提交。



### 文件的四种状态

Git 中的每个文件在任何时刻都处于**四种状态**之一，状态由 Git 自动判定，无需手动刷新。

- **未跟踪（untracked）**：新建的文件，Git 尚未纳入管理，不参与任何版本记录。
- **未修改（unmodified）**：已跟踪的文件与上一次提交时完全一致。
- **已修改（modified）**：已跟踪的文件被改动，但改动尚未进入暂存区。
- **已暂存（staged）**：已修改的文件被放入暂存区，其当前内容将进入下一次提交。

状态流转按以下顺序触发，每一步的触发命令一并标注：

1. 新建一个文件：进入未跟踪状态。
2. 对未跟踪文件执行 git add：转为已暂存状态，同时被纳入跟踪。
3. 编辑一个未修改的已跟踪文件：未修改转为已修改。
4. 对已修改文件执行 git add：已修改转为已暂存。
5. 对暂存内容执行 git commit：提交完成后所有文件回到未修改状态，开始新一轮循环。
6. 对已跟踪文件执行 git rm：文件被删除并退出跟踪，删除动作本身也会被提交记录。

> 判断依据记住一句话：Git 对比的是三份内容——上一次提交、暂存区、工作区文件，相邻两份不一致即产生状态变化。



### 初始化仓库

**git init** 的行为只有一个：在当前目录创建一个 .git 子目录，其中包含 Git 仓库必需的全部骨架；此时目录里已有的文件不会自动纳入版本管理，全部处于未跟踪状态。

两种常见场景：

- **对已有目录初始化**：进入项目根目录执行 git init，适合为进行中的项目接入 Git。
- **新建目录同时初始化**：先创建目录、进入后再执行 git init，适合从零开始的新项目。

**git clone 与 git init 的区别**：clone 从一个已有仓库出发，复制其全部历史，自动配置好指向原仓库的远程连接，并检出一份可直接编辑的工作区；init 只生成一个没有历史的空仓库，需要自己逐步积累提交。

> 一句话选择：本地从零开始用 git init，从既有仓库获取副本用 git clone。clone 得到的仓库无需再执行 init。



### 检查状态

**git status** 是查看工作区与暂存区状态的标准命令，输出未跟踪、已修改、已暂存三类文件的清单，并给出下一步操作提示。加上 -s 参数切换为短格式，每行以两个字符加空格描述状态，再加文件名；-sb 则额外显示当前分支名与领先落后情况。

短格式的状态字母拆解：

- **??**：未跟踪（untracked）。
- **A**：已暂存的新增文件（首次加入暂存区）。
- **M**（第一列）：已暂存的修改，即暂存后未再改动。
- **M**（第二列）：工作区中已修改、尚未暂存。
- **D**：已删除。
- **R**（第一列）：已重命名。
- 两列组合如 **MM**：先暂存了修改，之后又在工作区继续修改。

```bash
git status -s
# 输出示例：
#  M notes.md   工作区已修改，尚未暂存（第一列空格，第二列 M）
# M  todo.md    已暂存，暂存后未再改动（第一列 M，第二列空格）
# MM main.js    先暂存，之后又修改（两列都是 M）
# ?? temp.txt   未跟踪
```

> 记忆线索：第一列描述暂存区相对上一次提交的状态，第二列描述工作区相对暂存区的状态；第一列为空格表示暂存区与上次提交一致。



### 忽略文件 .gitignore

**.gitignore**：放在仓库根目录（或任意子目录）的纯文本文件，逐行列出**不希望 Git 跟踪的文件模式**，用于排除构建产物、依赖目录、本地配置等临时性内容。

书写规则要点：

- 每行一条模式；空行不生效，以井号开头的行是注释。
- 以斜杠结尾的模式表示**目录**，如 build/ 只匹配目录。
- 星号匹配零个或多个任意字符（不跨目录层级）；双星号匹配任意层级；问号匹配单个字符；方括号匹配其中任意一个字符。
- 以斜杠开头的模式从 .gitignore 所在目录开始匹配；不以斜杠开头则匹配任意层级。
- 以感叹号开头的行表示**例外**，把已被前面模式忽略的文件重新纳入跟踪。

典型示例：

```text
# 忽略所有 .log 文件
*.log

# 例外：保留 debug.log
!debug.log

# 只忽略根目录下的 temp 目录
/temp/

# 忽略 build 目录与 node_modules 依赖目录
build/
node_modules/
```

> [!IMPORTANT]
> **重要内容**：.gitignore 只对**未跟踪文件**生效。已被跟踪的文件即使写入 .gitignore，Git 仍会继续跟踪其改动；需要先用 git rm --cached 把文件移出跟踪（详见第 5 章）并提交，忽略规则才会生效。



### 基本工作流演示

把前面的概念串起来，Git 的日常就是一条最小工作循环：修改、暂存、提交。以下从零开始跑通一遍。

```bash
# 1. 初始化仓库，生成 .git 目录
git init

# 2. 新建一个文件，此刻处于未跟踪状态
echo "# 学习笔记" > notes.md

# 3. 查看状态，确认文件未跟踪
git status

# 4. 把文件放入暂存区，转为已暂存状态
git add notes.md

# 5. 再次查看状态，确认已暂存
git status

# 6. 提交暂存区内容到版本库，-m 后接提交说明
git commit -m "初始化学习笔记"

# 7. 提交完成后查看状态，工作区干净、回到未修改
git status
```

> 把暂存区当作本次提交的购物车：一次提交只装一个完整意图，说明写清做了什么。这个循环一旦熟练，后续的分支、合并、远程协作都建立在它之上。
