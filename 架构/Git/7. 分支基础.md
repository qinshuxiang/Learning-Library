## 分支基础

### 分支的本质

#### 分支的定义与提交链

**分支**：是**指向某个提交对象的可变指针**。Git 记录一个分支，只是记录一行"分支名 对应 某个提交哈希"的映射，分支本身不包含任何历史数据。

- **提交对象**：保存每一次提交的数据单元，内容包含一棵树对象（对应提交时刻的完整目录快照）、作者与提交信息，以及指向父提交的**父指针**。
- **提交链**：每个提交通过父指针指向前一个提交，多次提交依次串联成链；分支指针只是站在这条链的某个节点上。
- **默认分支**：仓库初始化后的第一个分支，常见名字为 master 或 main。
- **可变指针**：分支随着新提交的产生自动前移，始终指向该分支上最新的提交。

> 分支不是目录拷贝，也不是文件副本，它只是一个小文件。所谓在分支上开发，本质是把分支指到某个提交，再让 HEAD 指向这个分支，新提交顺着父指针接在链上。



#### 分支为什么快

创建一个分支的开销极小：**Git 只需要写一个 41 字节的文件**（40 个字符的提交哈希加一个换行符），不复制任何项目文件，因此分支的创建与切换几乎瞬时完成。

- **轻量级分支**：Git 的分支模型，分支只是指针，成百上千个分支也不增加仓库负担。
- **重量级分支**：SVN 等系统的分支模型，分支意味着对整个目录树的完整拷贝，创建慢、占空间，开发者因此不敢多用分支。

> 这正是 Git 与 SVN 等重量级分支系统的根本区别：**轻量的分支模型鼓励频繁分支**，把分支当作日常工作方式而非昂贵操作；第 14 章介绍的各类 Git 工作流，正是建立在这一前提之上。



### HEAD 的定义

#### HEAD 与分离 HEAD 状态

**HEAD**：是**指向当前所在分支的特殊指针**，并通过该分支指向当前的提交，它是 Git 判断下一个提交应接到哪里的依据。

- **常规状态**：HEAD 指向分支名，分支名再指向提交，例如 HEAD 指向 main，main 指向该分支的最新提交。
- **分离 HEAD（detached HEAD）状态**：当直接检出某个提交哈希或标签时，HEAD 不再指向分支而是直接指向提交，此时进入分离 HEAD 状态。
- **分离状态的风险**：在分离 HEAD 上产生的提交不属于任何分支，切到别的分支后它们失去引用，成为**孤立提交**（数据仍在对象库中、但没有任何分支指向它的提交）。
- **退出方式**：执行 checkout 分支名 回到既有分支；若想保住分离状态下的提交，执行 checkout -b 新分支名，把它们固定到一个新分支上。

> [!WARNING]
> **警告内容**：看到处于分离 HEAD 状态的提示时不要慌，但也不要在分离状态下持续开发：此时的新提交随时可能因切换分支而丢失，应立即用 checkout -b 把工作落到分支上。



### 分支操作

#### 分支的创建、切换与删除

分支的全部操作都围绕指针进行，常用命令如下：

```bash
git branch             # 列出本地分支，当前分支带星号
git branch -v          # 列出分支，附带最后一次提交的哈希与提交消息
git branch --merged    # 列出已合并到当前分支的分支
git branch --no-merged # 列出尚未合并到当前分支的分支
git branch dev         # 创建 dev 分支，但不切换
git checkout dev       # 切换到 dev（或 git switch dev）
git checkout -b dev    # 创建并切换到 dev（或 git switch -c dev）
git branch -d dev      # 删除分支，仅允许删除已合并的分支
git branch -D dev      # 强制删除，未合并的分支必须用大写 D
```

- **git branch 分支名**：在当前提交上创建一个新分支，HEAD 不动，仍停留在原分支。
- **git checkout 分支名** 与 **git switch 分支名**：把 HEAD 移到目标分支，工作区文件随之更新为该分支的内容；switch 是 2.23 版本引入的语义更清晰的专用切换命令。
- **checkout -b 分支名** 与 **switch -c 分支名**：创建并切换一步完成，是最常用的起手式。
- **branch -d 分支名**：删除分支，本质是删除那个指针文件；Git 会先检查该分支是否已合并，未合并则拒绝执行。
- **branch -D 分支名**：绕过合并检查强制删除，分支上未合并的提交随之成为孤立提交。

> 删除分支删掉的只是指针，不是提交：分支被删后，其上的提交仍完整保存在对象库中，只是失去了引用。因此 -d 的安全检查可以放心信任，而 -D 应在确认不再需要那条工作线后再用。



### 分支的用途与切分时机

#### 一个分支聚焦一件事

分支的核心价值是**隔离**：一个分支只承载一件事（一个新功能或一个缺陷修复），完成后合并回主干，主干始终保持可用。

- **主干可用**：任何时刻检出主干，得到的都是一个能正常构建、能交付的版本，不稳定的工作放在分支上做。
- **一件事一分支**：功能开发、缺陷修复、实验尝试互不掺杂，分支生命周期清晰，合并时冲突也更少。
- **随手可弃**：某条思路走不通，直接删除分支即可，不留痕迹。

常见的分支切分时机：

1. **开发新功能**：从主干切出功能分支，开发完成并自测通过后合并回去。
2. **修复缺陷**：为每个待修复的问题切出修复分支，避免修复与开发互相干扰。
3. **试验性改动**：尝试一种不确定可行的方案，失败即弃。
4. **并行处理紧急任务**：功能开发到一半时出现线上问题，先切回主干开修复分支处理，功能分支原地等待。

> [!TIP]
> **建议内容**：分支宜短命不宜长命：存活期越长的分支，与主干的分叉越大，合并时的冲突越多。功能分支应尽快完成、尽快合并。



### 快进合并预览

#### 快进合并的指针本质

**快进（fast-forward）**：当被合并分支是当前分支的**直接后代**（当前分支自分叉后没有新提交）时，合并不需要创建新提交，Git 只是把当前分支的指针向前移动到目标分支的最新提交。完整的合并机制详见第 8 章。

```text
合并前：dev 领先 main 两个提交

A ── B ── C ── D
      ↑         ↑
     main      dev

执行 git merge dev 后：main 指针直接前移

A ── B ── C ── D
                ↑
            main、dev
```

- 快进的条件：main 自分叉点 B 之后没有新提交，历史没有分叉。
- 快进的动作：没有新提交产生，只有 main 指针从 B 移到 D。
- 快进的历史：合并后历史仍是一条直线，看不出 dev 曾经单独存在。

> 快进这场合并名不副实：它什么都没有合，只是指针前移。这也决定了它只在无分叉时可用，一旦双方都有新提交，就必须走三方合并（详见第 8 章）。



### 分支数据流判断题

#### 提交的隔离性与孤立提交

**在分支上提交不影响其他分支**：提交只会让当前分支的指针前移，其他分支的指针纹丝不动，这一性质常以判断题形式考查。

- **判断一**：在 dev 上提交后，main 的指向是否变化？不变，main 仍指向原来的提交。
- **判断二**：删除未合并的 dev 后，dev 上的独有提交是否消失？不消失，提交仍完整保存在对象库中。
- **孤立提交**：失去任何分支引用的提交，从任何分支的历史上都看不到它，但数据仍在。

> [!NOTE]
> **提醒内容**：孤立提交并非永远找不回：Git 把 HEAD 的移动历史记录在引用日志中，在垃圾回收运行之前，可凭它找回孤立提交，具体机制详见第 11 章。
