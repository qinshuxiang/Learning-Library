## 面向服务架构与 Web 服务

> **全章主脉**：**面向服务架构把系统能力组织为可复用、可组合、位置透明的服务，并以标准化接口与契约完成跨系统集成**。本章先讲 SOA 的定义、核心特征与服务的分层分类，再讲企业服务总线的功能与争议、自顶向下与自底向上的实现路线，随后展开 Web 服务技术栈的 SOAP、WSDL、UDDI 与 WS-* 规范族，进而讲透 REST 与面向资源的架构及其成熟度模型，最后落到 SOAP 与 REST 的成对对比、Web 服务安全、服务质量契约化与 SOA 治理，并在篇末与微服务架构作辨析衔接。

### SOA 的概念与服务分层

#### SOA 的定义与核心特征

**面向服务架构**（Service-Oriented Architecture，SOA）是把应用功能抽象为**服务**、并通过良好定义的**接口与契约**把服务联系起来的企业级架构范式，其目标是让跨系统、跨组织的能力可被发现、调用与组合。

- **松耦合**（Loose Coupling）：消费方只依赖接口契约，不依赖服务内部的实现语言与数据存储，实现替换不影响调用方。
- **粗粒度**（Coarse-Grained）：服务暴露完整的业务能力而非零碎的数据访问，以减少远程调用次数与网络开销。
- **接口契约先行**（Contract-First）：先定义接口描述与消息格式，再分别实现提供方与消费方，契约是双方唯一的约定。
- **位置透明**（Location Transparency）：调用方按逻辑名称访问服务，真实地址由注册中心或总线解析，服务迁移对调用方无感。
- **可组合与可复用**（Composable and Reusable）：服务可作为构件被编排进新的业务流程，一次实现、多次使用。
- **自治**（Autonomous）：服务自行管理其内部逻辑与数据，对外只承担契约中承诺的职责。

> [!IMPORTANT]
> **重要内容**：SOA 的六项特征中，**接口契约先行是根，松耦合与位置透明是果**。没有契约就没有可替换性，没有可替换性就谈不上复用与组合。判断一段设计是否属于 SOA 只需看两点——**功能是否被封装为可独立部署的服务，服务之间是否只通过契约交互**。



#### 服务与构件、组件的区别

**服务**（Service）是**自描述、可发现、跨进程边界、以契约对外暴露的粗粒度功能单元**；**构件**（Component）是架构视角下承担计算或存储职责的单元；**组件**在软件复用语境下多指可独立替换的二进制实现单元，三者抽象层次不同。

- **边界不同**：构件与组件通常处于同一进程内，服务跨越进程、主机乃至组织边界，因此必然依赖网络调用与序列化。
- **契约不同**：构件靠编译期接口约定，服务靠运行期可读取的描述文档（如 WSDL、OpenAPI）约定。
- **粒度与复用时机不同**：构件可为任意小且在开发期被组装进程序，服务强调粗粒度且在运行期被远程发现与调用。

> **辨析**：软考常把**构件、组件、服务**三者并列设题。一句话区分——**构件是设计单元，组件是二进制复用单元，服务是可远程调用的业务单元**。服务在架构上仍属构件的一种，但其契约化、网络化与粗粒度的要求，使之成为 SOA 的基本组织单位。



#### 服务的分层与分类

通说认为企业级服务可按抽象层次自上而下分为**编排服务、业务服务、应用服务与基础服务**四类，层次越高越贴近业务流程，越低越贴近具体实现。

- **基础服务**（Infrastructure Service）：通用技术能力，如认证授权、日志审计、消息通知、字典转换，供其他服务复用。
- **应用服务**（Application Service）：面向单个应用系统的功能封装，如订单系统的查询接口，多由既有系统改造而来。
- **业务服务**（Business Service）：面向业务领域的完整能力，通常由若干应用服务与基础服务组合而成，如完整的下单流程。
- **编排服务**（Orchestration Service）：跨系统的流程级服务，按业务流程依次或并行调用业务服务，并处理异常与补偿。

> **速记**：**编排在最上，业务在中，应用在下，基础贯穿全局**。判断某服务属哪一层，只需问它描述的是**流程、业务能力、单个系统功能，还是通用技术能力**。



#### 服务编排与服务编制

**服务编排**（Orchestration）与**服务编制**（Choreography）都描述多个服务如何协同完成一个流程，区别在于**是否存在一个中心控制者**。

- **控制方式**：**服务编排**由**一个中心协调者**（流程引擎）持有完整流程定义并依次调用各服务，控制权集中；**服务编制**没有中心协调者，各参与方按事先约定的协作规则与事件交互，控制权分散。
- **逻辑位置**：编排的流程逻辑集中在一处，代表如 BPEL；编制的协作规则分布于各方，每个参与者只知道何时响应、响应后发出什么。
- **可观测性与变更影响**：编排的流程状态集中可查、改流程只改中心定义；编制的全局状态需由各方拼凑、改协作需多方共同约定并同步发布。

> [!TIP]
> **建议内容**：记忆抓手是**编排有指挥、编制像合唱**。答题时若题干出现「流程引擎统一调度」「由中心服务依次调用」，答**服务编排**；若出现「各方按约定自行响应事件、无中心调度」，答**服务编制**。



### 服务集成方式与实现路线

#### 企业服务总线的定位、功能与争议

**企业服务总线**（Enterprise Service Bus，ESB）是 SOA 中位于服务提供者与消费者之间的**服务中介基础设施**，承担协议转换、消息路由与格式转换等职责，使异构系统无需彼此直接适配即可互联。

- **协议转换**：在 HTTP、JMS、FTP、SOAP 等不同协议之间转换，使采用不同通信方式的系统互通。
- **消息路由**：按内容、规则或地址把请求转发到目标服务，支持静态路由与内容路由。
- **消息转换**：在 XML、JSON、定长报文等格式间做映射与翻译，屏蔽双方数据模型差异。
- **注册与发现**：维护服务目录与端点地址，供调用方按逻辑名查找目标服务。
- **安全、监控与服务质量**：集中完成认证授权与消息加解密，提供流量统计、日志审计、告警，以及负载均衡、失败重试与事务补偿。

> [!WARNING]
> **警告内容**：ESB 的代价与收益同样显著。**集中化的路由与转换逻辑会让总线演变为架构中枢，进而成为性能瓶颈与单点故障，并与 SOA 追求的松耦合、服务自治相矛盾**；重度的消息转换还会造成厂商锁定与高昂的运维成本。实务中因此出现**轻量级集成**趋势——用轻量协议与消息队列承担传输、用 API 网关承担接入与安全，把转换逻辑下沉到服务自身，这也正是微服务架构否定「重 ESB」的直接动因。



#### SOA 的实现路线与代价

SOA 的落地有两条典型路线——**自顶向下**由业务建模驱动，**自底向上**由遗留系统封装驱动，二者的出发点、周期与风险截然不同。

- **自顶向下**（Top-Down）：先从业务流程与业务能力建模出发，划分业务服务与编排流程，再逐层落到具体系统；业务对齐好、复用度高，但周期长、初期投入大，强依赖业务与信息部门的协同。
- **自底向上**（Bottom-Up）：先盘点既有系统，把可复用功能封装为服务对外暴露；见效快、投入小、对业务冲击小，但缺乏统一规划，易出现粒度不一、语义重复、接口风格各异的问题，长期治理成本高。
- **中间相遇**（Meet-in-the-Middle）：以自顶向下的服务蓝图作规划、以自底向上的封装作落地，是实务中最常见的折中路线。

> **速记**：**自顶向下治本但慢，自底向上见效但乱**。案例题若强调「遗留系统多、要求快速集成、预算有限」，倾向自底向上；若强调「业务统一、长期复用、跨部门协同」，倾向自顶向下。



### Web 服务技术栈

#### SOAP 的报文结构与通信绑定

**简单对象访问协议**（Simple Object Access Protocol，SOAP）是一种基于 XML 的**消息格式与处理模型规范**，现行标准为 W3C 的 **SOAP 1.2**，其 2003 年发布、2007 年修订第二版；早期 **SOAP 1.1** 于 2000 年发布，级别为 W3C Note。SOAP 消息由**信封、头、体**三部分构成。

```xml
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <m:authToken xmlns:m="http://example.com/auth" soap:mustUnderstand="true">ABC123</m:authToken>
  </soap:Header>
  <soap:Body>
    <m:GetOrder xmlns:m="http://example.com/order"><m:OrderId>20260912</m:OrderId></m:GetOrder>
  </soap:Body>
</soap:Envelope>
```

- **信封**（Envelope）：消息的根元素，声明 SOAP 命名空间并容纳头与体，是判定一个 XML 文档是否为 SOAP 消息的唯一标志。
- **头**（Header）：可选，承载**与业务无关的控制信息**，如安全令牌、事务上下文、路由信息；条目可带 mustUnderstand 与 role 属性，接收方对标记为必须理解的条目不得忽略。
- **体**（Body）：必需，承载实际的调用请求、响应或错误；错误以 **Fault** 元素返回，含错误码、原因与细节。
- **绑定**（Binding）：SOAP 规范只定义消息、不绑定传输，由绑定框架把消息映射到下层协议；最常用 **HTTP 绑定**，也支持 **SMTP 绑定**（异步、可推送）以及 JMS、TCP 等实现（后者多为非标准扩展）。

> [!IMPORTANT]
> **重要内容**：**SOAP 与 HTTP 是「消息」与「传输」的关系，不在同一层**。SOAP over HTTP 只是众多绑定中的一种。必须记住——HTTP 返回 200 只代表**传输成功**，业务失败仍可能以 SOAP Fault 的形式放在响应体中，因此「HTTP 200 加 SOAP Fault」是完全正常的组合。REST 的做法与此相反，它把业务语义直接映射到 HTTP 方法与状态码上。



#### WSDL 的抽象与具体部分

**Web 服务描述语言**（Web Services Description Language，WSDL）是描述 Web 服务**接口与访问方式**的 XML 语言，WSDL 1.1（2001 年）为 W3C Note，**WSDL 2.0** 于 2007 年成为 W3C Recommendation，其核心设计是**把抽象接口与具体绑定分离**。

```xml
<definitions xmlns="http://schemas.xmlsoap.org/wsdl/">
  <types>...</types>
  <message name="GetOrderRequest">...</message>
  <portType name="OrderPortType"><operation name="getOrder">...</operation></portType>
  <binding name="OrderBinding" type="OrderPortType">...</binding>
  <service name="OrderService">
    <port name="OrderPort" binding="OrderBinding"><address location="http://api.example.com/order"/></port>
  </service>
</definitions>
```

- **抽象部分**回答「服务做什么」：**types** 定义数据类型（通常用 XML Schema）；**message** 定义抽象消息；**portType** 定义抽象操作集合，是服务的接口视图。
- **具体部分**回答「服务怎么做、在哪做」：**binding** 把抽象接口绑定到具体协议与消息格式（如 SOAP over HTTP）；**service** 是一组端口的集合；**port** 由绑定加网络地址构成，标明实际调用端点。
- **分离的意义与 WSDL 2.0 术语变更**：同一抽象接口可对应多种绑定、同一服务可在多个地址发布，消费方据此生成客户端代码；WSDL 2.0 把 portType 改称 interface、把 port 改称 endpoint、移除 message 元素，并显式支持消息交换模式（MEP）。

> **辨析**：WSDL 的抽象与具体是高频考点，记忆线索是**「上面说做什么，下面说怎么做、在哪做」**。抽象部分只有 types、message、portType，具体部分只有 binding、service、port，两组名词不要交叉。



#### UDDI 的三类注册与 WS-* 规范族

**统一描述、发现与集成**（Universal Description, Discovery and Integration，UDDI）是**服务的注册与发现规范**，由 OASIS 标准化；**WS-*** 则是在 SOAP 之上扩展企业级能力的一组规范族，二者共同回答「服务在哪里、怎么安全可靠地调用」。

- **白页**（White Pages）：按**组织身份信息**查找服务提供者，如企业名称、联系人、联系方式，回答「谁提供了什么服务」。
- **黄页**（Yellow Pages）：按**分类标准**查找服务，如行业分类、产品分类、地理分类，回答「哪一类服务由谁提供」。
- **绿页**（Green Pages）：提供**技术调用信息**，如服务接口描述（WSDL 文件）与调用方式，回答「这个服务怎么调用」。
- **WS-Security**：在 SOAP 头中实现**消息级安全**，规范签名、加密与安全令牌，OASIS 标准版本为 WS-Security 1.1（2006 年）。
- **WS-Addressing**：在 SOAP 头中携带**端点引用与寻址信息**（To、From、ReplyTo、MessageID），把寻址从传输层解耦到消息层，2006 年成为 W3C Recommendation。
- **WS-ReliableMessaging**：在不可靠传输之上提供**可靠消息传递**，保证消息送达、去重与顺序，OASIS 标准版本为 WS-ReliableMessaging 1.1（2007 年）。

> **速记**：**白页认人、黄页分类、绿页给接口**。WS-* 三个最常考的规范各管一摊——**WS-Security 管安全、WS-Addressing 管寻址、WS-ReliableMessaging 管可靠传输**；另有 WS-Policy 管策略、WS-Trust 管信任与令牌交换、WS-AtomicTransaction 管分布式事务。



### REST 与面向资源的架构

#### REST 的约束与面向资源的架构

**表述性状态转移**（Representational State Transfer，REST）由罗伊·菲尔丁（Roy Fielding）在 2000 年的博士论文中提出，是一组**以资源为中心、约束服务形态的架构风格**，而非具体协议或标准；**面向资源的架构**（Resource-Oriented Architecture，ROA）则是其实践形态，把一切可命名的信息抽象为**资源**，用 URI 唯一标识，用统一的 HTTP 方法操作，用**表示**（如 JSON、XML）传输资源状态。

- **客户端-服务器**（Client-Server）：界面与数据存储分离，两端可独立演进。
- **无状态**（Stateless）：每个请求自带处理所需的全部信息，服务端不保存会话状态，会话状态由客户端持有。
- **可缓存**（Cacheable）：响应须标明是否可缓存，缓存可减少交互并提升性能。
- **统一接口**（Uniform Interface）：以统一方式操作资源，含资源标识、通过表示操作资源、自描述消息与超媒体驱动四项子约束。
- **分层系统**（Layered System）：允许在两端之间插入代理、网关等中间层，各层只感知相邻层。
- **按需代码**（Code-on-Demand，可选）：服务端可下发可执行代码扩展客户端，这是唯一可选的约束。

```json
{
  "id": "20260912",
  "status": "shipped",
  "links": [{ "rel": "cancel", "href": "/orders/20260912/cancel" }]
}
```

- **资源与表示分离**：资源是概念实体，表示是它在某一时刻的编码形态，同一资源可有多种表示并通过内容协商选择。
- **方法承载语义**：GET 取、POST 建、PUT 改（幂等全量替换）、PATCH 局部改、DELETE 删。
- **HATEOAS**（Hypermedia as the Engine of Application State）：响应中携带链接与可执行动作，客户端据服务端给出的链接发现下一步，而非硬编码 URL。

> [!NOTE]
> **提醒内容**：**无状态不等于不能有登录**。无状态指服务端不保存会话上下文，令牌与 Cookie 中的凭据属于客户端持有的状态，完全可以存在。此外要辨析 **PUT 的全量替换与 PATCH 的局部更新、GET 的幂等与安全**，软考常借「用 GET 执行删除」这类反例考查方法语义是否被正确使用。



#### REST 成熟度模型

**Richardson 成熟度模型**（Richardson Maturity Model，RMM）用四个层级衡量服务在多大程度上体现了 REST 思想，层级越高越接近完整意义上的 REST。

- **层级 0（单一端点）**：只用**一个 URI 与一个方法**（通常是 POST）交互，HTTP 仅作隧道，本质是远程过程调用（如 SOAP 风格、XML-RPC），与 REST 无关。
- **层级 1（资源）**：引入**资源概念**，每个资源拥有独立 URI，但方法仍单一，只是把 POST 的地址按资源拆开。
- **层级 2（HTTP 动词）**：引入**HTTP 方法与状态码**，用 GET、POST、PUT、DELETE 表达操作语义，用 200、201、404、409 等表达结果，这是实务中多数「RESTful API」所处的位置。
- **层级 3（超媒体控制）**：响应中携带**超媒体链接与表单**，客户端通过服务端返回的链接发现后续可用操作，达到 **HATEOAS**，是菲尔丁定义中 REST 的完整形态。

> **速记**：**零单一、一资源、二动词、三超媒体**。判断层级看三件事——**资源是否按 URI 拆分、方法语义是否被使用、下一步动作是否由响应中的链接驱动**。注意层级 3 在实务中并不普及，多数系统停在层级 2 即可满足需求，考试只需掌握各层级的判断标准，不必认为层级 3 是强制目标。



#### REST 与 SOAP 的系统对比

REST 与 SOAP 是软考选择题与案例题的固定对比点，二者在**协议与传输、消息格式、状态、性能、缓存、安全性、适用场景与工具生态**八个维度上两两相对，务必成对记忆。

- **协议与传输**：**REST** 是架构风格，实践上几乎只跑在 HTTP 上；**SOAP** 是消息协议，传输无关，可绑定 HTTP、SMTP、JMS 等。
- **消息格式**：**REST** 以 JSON 为主，按需选择 XML 或二进制；**SOAP** 强制使用 XML 信封，结构固定。
- **状态**：**REST** 要求无状态，会话状态留在客户端；**SOAP** 规范不禁止有状态交互，可借 WS-* 与传输层会话维持上下文。
- **性能**：**REST** 报文轻、解析快、开销小；**SOAP** 报文冗长、XML 解析开销大，附加头后更重。
- **缓存**：**REST** 可直接利用 HTTP 缓存语义，GET 可缓存并支持条件请求；**SOAP** 多用 POST，HTTP 缓存基本失效，需自行实现。
- **安全性**：**REST** 主要依赖传输层安全（HTTPS/TLS）与 OAuth 2.0 授权；**SOAP** 有 **WS-Security** 提供消息级端到端签名与加密。
- **适用场景**：**REST** 适合面向 Web、移动端、资源型、性能与易用性优先的公开接口；**SOAP** 适合企业内部集成，尤其是需要事务、可靠消息、消息级安全与严格契约的场景。
- **工具生态**：**REST** 生态轻量、语言支持广泛、调试方便；**SOAP** 有 WSDL 契约驱动的代码生成与成熟的 WS-* 企业级工具链。

> [!IMPORTANT]
> **重要内容**：答题时切忌把两者说成「新旧替代」。**SOAP 的优势是契约严格、传输无关与消息级安全，REST 的优势是轻量、可缓存与易用**，选择依据是**是否需要传输无关、事务与可靠消息、消息级安全**，而非哪个更时髦。



### 安全、质量与治理

#### Web 服务的安全机制与风险

Web 服务安全要解决三件事——**消息的保密性、完整性与访问的合法性**，其实现分为**传输层安全**与**消息层安全**两种层次，二者保护范围不同。

- **传输层安全**（Transport-Level Security）：用 TLS/HTTPS 加密整条通道，保护**相邻两个节点**之间的通信，实现简单、性能好；但消息在中间节点解密后即为明文，无法端到端保护。
- **消息层安全**（Message-Level Security）：用 **WS-Security** 在 SOAP 头中携带签名与加密信息，保护**端到端**，可对消息的指定部分做细粒度处理，即使经过 ESB 等中介仍能保持。
- **签名与加密手段**：**XML Signature** 提供完整性与不可否认性，**XML Encryption** 提供保密性，二者只作用于被指定的元素，粒度可精确到某个头块或体元素。
- **令牌与单点登录**：WS-Security 可携带用户名令牌、X.509 证书、SAML 断言与 Kerberos 票据；**SAML** 以断言承载认证与授权信息，是跨域单点登录的常用方案，而 **OAuth 2.0** 解决的是**授权**（委托第三方访问资源），不负责认证，二者不可混用。

> [!CAUTION]
> **注意内容**：Web 服务的典型风险必须能识别并对应到防护手段。**重放攻击**（消息被截获后重复提交）用时间戳与一次性随机数防护；**消息篡改**用数字签名防护；**越权调用**必须在服务端做鉴权，客户端隐藏按钮不构成任何保护；此外还要防范 **XML 外部实体注入（XXE）**、**XML 炸弹**（实体膨胀耗尽资源）与**接口信息泄露**（如 WSDL 暴露内部数据结构）。



#### 服务质量的契约化与版本演进

**服务级别协议**（Service Level Agreement，SLA）是服务提供方与消费方就服务质量达成的**书面契约**，把模糊的「服务要好用」转成可度量、可考核的指标；服务一旦发布，其接口演进必须遵守兼容性纪律。

- **SLA 的要素**：服务范围与责任边界、**可用性**（如 99.9%）、**性能**（响应时间、吞吐量）、**错误率**、**故障响应与恢复时间**、度量口径与采样周期、未达标的补偿或奖惩、有效期与变更条款。
- **向后兼容**（Backward Compatible）：**新版本服务能继续服务旧版本客户端**，是发布新版本时必须守住的红线。
- **向前兼容**（Forward Compatible）：**旧版本服务能容忍并处理按新版本约定发来的消息**，常用于灰度并存期，实现难度更高。
- **接口演进策略**：**只增不改**——只新增可选字段或新操作，不删除、不改名、不改既有字段的类型与语义；**并行版本**——用 URI 版本号或命名空间让多个版本并存，旧版本经公告期后退役；必要时辅以版本协商与兼容性测试。

> **速记**：**向后兼容保老客户端，向前兼容容新消息**。案例题常见问法是「新版本发布后老客户端报错，应如何调整」——标准答案是**坚持只增不改、字段一律可选、保留默认值，并以并行版本平滑退役**。



#### SOA 的治理与微服务辨析

**SOA 治理**是对服务的目录、生命周期与复用情况实施持续管理的一整套机制与组织安排；它与微服务架构的关系是**同源演进而非相互替代**，这也是本章与下一篇的衔接点。

- **服务目录**：登记全部服务的元数据，包括接口描述、版本、责任人、SLA、依赖关系与状态，是查找与复用服务的唯一入口。
- **服务生命周期**：通常划分为**识别、设计、实现、发布、运维、退役**六个阶段，每阶段设准入与准出条件，避免服务随意上下线。
- **复用度量**：用复用服务数、服务调用量、复用服务占比、重复建设数量与需求交付周期等指标衡量治理成效。
- **组织保障**：设立服务中心或卓越中心统一制定规范、组织**接口评审**、指定服务责任人，是治理能否落地的关键。
- **与微服务的相同点**：都主张**面向服务、松耦合、服务自治、接口契约化与可独立演进**，微服务可视为 SOA 的一种轻量化实现形态。
- **与微服务的不同点**：**服务粒度**上 SOA 粗、微服务细；**通信方式**上 SOA 常经 ESB 集中式中介、微服务多用轻量协议直连或服务网格；**数据管理**上 SOA 倾向共享数据或统一数据服务、微服务要求每个服务独享数据存储；**治理方式**上 SOA 强调集中式标准与管控、微服务强调去中心化与团队自治。

> [!TIP]
> **建议内容**：微服务的实现细节、服务拆分与治理机制留待第 3 篇展开。此处只需记住辨析结论——**微服务不是 SOA 的对立面，而是 SOA 去掉重 ESB、把粒度做细、把治理去中心化之后的演进形态**，答题时切忌写成二者互斥。

> **案例题答题线索**：判断该用 SOA 还是点对点集成，看三条线索——**集成点是否随系统数呈网状增长（点对点数量按平方增长，SOA 按线性增长）、是否存在多协议多厂商的适配需求、是否需要统一的安全与监控**，三者多为 SOA，三者皆无则点对点更简单经济。指出 Web 服务设计缺陷，重点查**服务端保存会话状态、用 GET 执行有副作用的操作、直接暴露数据库结构、缺失版本策略与 SLA、缺少服务端鉴权、粒度过细导致频繁往返调用**。说明 ESB 的收益与代价，收益写**协议转换、路由与转换、解耦与复用、统一安全监控**，代价写**集中式单点与瓶颈、额外延迟、运维复杂、厂商锁定**。
