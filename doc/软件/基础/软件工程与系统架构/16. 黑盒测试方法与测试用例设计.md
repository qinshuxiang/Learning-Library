## 黑盒测试方法与测试用例设计

> **全章主脉**：**黑盒测试把程序视为一个不透明的盒子，只依据需求规格设计输入并检验输出**，不需要了解内部实现。它回答的问题是「功能对不对、边界处理对不对」。本章按方法展开：**等价类划分、边界值分析、判定表、因果图、正交实验法、场景法、错误推测法**。全部方法围绕同一个目标——**用尽可能少的用例覆盖尽可能多的输入空间**。示例代码与用例结果均已在 Node 环境实测通过。

### 黑盒测试概述

#### 黑盒测试的基本思想

**黑盒测试**（又称功能测试或数据驱动测试）在**不关心程序内部结构**的前提下，依据需求规格说明书设计测试用例，验证程序的功能与接口是否符合规定。

- **测试依据**：需求规格说明、接口定义、业务流程、用户手册。
- **测试视角**：从使用者角度出发，把系统当作输入到输出的映射。
- **核心任务**：选择合适的输入数据，使各类处理路径与边界条件都被触发。
- **典型手段**：等价类划分、边界值分析、判定表、因果图、正交实验法、场景法、错误推测法。

> [!IMPORTANT]
> **重要内容**：**黑盒测试与白盒测试的目标互补，不是替代关系**。黑盒测试能发现**功能缺失、功能错误、接口错误、性能问题、初始化与终止错误**；但无法发现**代码中未被执行的路径、冗余逻辑与内部变量的错误**。因此完整测试必须两者结合，实践中常按「白盒管单元、黑盒管系统」分工。



#### 黑盒测试能发现与不能发现的问题

- **能发现的问题**：功能未实现或实现错误、界面与交互错误、数据结构或外部数据库访问错误、性能与容量问题、初始化与终止错误、输入组合导致的逻辑错误。
- **不能发现的问题**：程序内部特定路径从未被执行、内部逻辑冗余或死代码、内部变量未初始化、算法实现与设计不符、边界内部的细微处理错误。

> [!NOTE]
> **提醒内容**：**黑盒测试对内部未执行路径完全无能为力**。一个模块可能在功能上「看起来都对」，但其中某个异常分支从未被执行过，一旦真实环境触发即崩溃。这类缺陷只能通过白盒测试或代码审查发现，因此对安全攸关与高可靠性系统，白盒测试不可省略。



### 等价类划分法

#### 有效等价类与无效等价类

**等价类划分**把输入域划分为若干子集，**每个子集中的任一数据对揭露缺陷的作用等价**，因此每个等价类只需取一个代表值即可。

- **有效等价类**：对规格说明而言合理且有意义的输入集合，用于验证程序是否正确实现了功能。
- **无效等价类**：对规格说明而言不合理或无意义的输入集合，用于验证程序是否正确地拒绝非法输入。
- **划分原则**：若输入条件规定了取值范围，则划分出一个有效等价类（范围内）与两个无效等价类（低于下界、高于上界）；若规定了值的个数，则划分出一个有效等价类与两个无效等价类（过多、过少）；若规定了集合或布尔条件，则划分出一个有效等价类与一个无效等价类。

> [!TIP]
> **建议内容**：**设计用例时有效与无效等价类应分开处理**。通常做法是先用有效等价类的代表值设计尽量少的用例（一条用例可同时覆盖多个有效类），再为每个无效等价类单独设计一条用例。**一条用例只覆盖一个无效等价类**，因为多个非法输入同时出现时，程序可能只报出其中一个错误，无法判断另一个是否被正确处理。



#### 等价类划分的设计步骤

- **第一步**：依据需求确定输入条件与输出条件，逐条列出。
- **第二步**：为每个条件划分有效等价类与无效等价类，并编号。
- **第三步**：设计新用例，使其尽可能多地覆盖尚未覆盖的有效等价类，重复至全部有效类被覆盖。
- **第四步**：为每个尚未覆盖的无效等价类设计一条新用例，使其仅覆盖该无效类。
- **第五步**：为每条用例确定预期输出，形成完整用例表。



#### 等价类划分示例

以「用户注册时年龄必须是 18 至 60 之间的整数」为需求，等价类划分如下：

- **有效等价类**：18 至 60 之间的整数，如 18、30、45、60。
- **无效等价类**：小于 18 的整数，如 17、0、负数。
- **无效等价类**：大于 60 的整数，如 61、100。
- **无效等价类**：非整数，如 18.5、字符串、空值。

```js
// 被测函数：年龄校验
function checkAge(age) {
  if (!Number.isInteger(age)) return '类型非法';
  if (age < 18) return '未满 18 岁';
  if (age > 60) return '超过 60 岁';
  return '通过';
}

console.log(checkAge(30));
console.log(checkAge(17));
console.log(checkAge(61));
console.log(checkAge(18.5));
console.log(checkAge('20'));

// 输出：
// 通过
// 未满 18 岁
// 超过 60 岁
// 类型非法
// 类型非法
```

> [!NOTE]
> **提醒内容**：**等价类划分的关键在于「无效等价类的严格拆分」**。上例中若把「非整数」与「超出上界」合为一个无效类，用 61.5 作为代表值，就无法判断程序对「大于 60」与「非整数」两种情况是否分别做了正确拒绝。**每类非法情况都应有独立的代表值**。



### 边界值分析法

#### 边界值的选择

**边界值分析**是对等价类划分的补充，其依据是**大量缺陷发生在输入域的边界上而非中间区域**。因此对每个边界，应取**恰等于边界、略小于边界、略大于边界**三类值。

- **上点**：正好落在边界上的点，如区间 18 至 60 的上点为 18 与 60。
- **离点**：离上点最近、位于边界之外的点，对闭区间即比下界小一点与比上界大一点，如 17 与 61。
- **内点**：区间内部的任意点，用于确认正常情况下的处理，如 30。
- **取值个数**：若变量取值个数为 n，边界分析通常取 n 加 2 个用例，即四个边界点加中间点加略超出边界的点。

```js
const ageCases = [17, 18, 19, 59, 60, 61];
for (const value of ageCases) {
  console.log(`${value} -> ${checkAge(value)}`);
}

// 输出：
// 17 -> 未满 18 岁
// 18 -> 通过
// 19 -> 通过
// 59 -> 通过
// 60 -> 通过
// 61 -> 超过 60 岁
```

**对比边界值与等价类划分**：**选取依据**：等价类划分关注「取哪个子集的代表值」，边界值分析关注「取子集的边缘点」。**发现缺陷类型**：等价类划分擅长发现整体逻辑错误，边界值分析擅长发现边界条件处理错误（如把小于写成小于等于）。**共同点**：二者都以输入域划分为基础，实践中总是配合使用，边界值分析可视为等价类划分的精化。

> [!IMPORTANT]
> **重要内容**：**边界值分析是最经济也最有效的一种方法**。上例中若开发者把「未满 18 岁」的条件误写为小于等于 18，用中间的 30 测试永远发现不了，而用边界点 18 一次即可命中。因此凡涉及数值区间、长度限制、数量上限的需求，**边界用例必须优先设计**。



### 判定表与判定树

#### 判定表的组成

**判定表**用于表达**多个条件的组合与对应动作**，特别适合业务规则由若干条件共同决定的场景。它由四部分构成：

- **条件桩**：列出所有相关条件，如「是否会员」「订单金额是否超过 500」「是否在活动期内」。
- **动作桩**：列出所有可能的处理动作，如「打八折」「打九五折」「不打折」「提示活动已结束」。
- **条件项**：每一列给出该条件下各条件的取值组合。
- **动作项**：每一列给出该组合下应执行的动作。

一条完整的判定表要求**条件组合穷尽且互斥**，因此它能自动暴露出规则中的遗漏与矛盾——凡是有条件项组合找不到对应动作项，即规则存在缺口。

- **优点**：组合覆盖完整、规则显式、可直接转化为测试用例（每一列对应一条用例）。
- **缺点**：条件数量增加时组合数呈指数增长，需先化简。



#### 判定表的化简

**化简**的核心是合并**动作相同且条件项仅有部分无关的列**。例如某条规则中「是否会员」的取值不影响动作结果，则该条件可标为无关项，两列合并为一列。

- **化简依据**：两条规则的动作完全相同，且条件的取值差异不影响动作。
- **化简方式**：把不影响结果的条件标记为「无关」，用短横线表示。
- **化简的限度**：化简不能改变规则的语义，只减少列数。
- **化简后的验证**：化简后仍应能覆盖全部原始组合。

> [!TIP]
> **建议内容**：**判定表是「业务规则密集」场景中最值得使用的方法**。当需求中出现「同时满足条件 A、B、C 时执行 X」这类描述，且条件之间存在组合时，用自然语言书写的需求几乎必然遗漏部分组合。**画判定表的过程本身就是一次需求评审**，缺口会立刻显现。



### 因果图法

#### 因果图的基本思想

**因果图法**从需求中分析出**原因（输入条件）与结果（输出或状态变化）**，用图形表达它们之间的逻辑关系，再转换为判定表并据此生成用例。它弥补了等价类与边界值分析**无法处理输入条件之间组合关系**的不足。

因果图中的四种基本关系：

- **恒等**：原因成立则结果成立，一一对应。
- **非**：原因成立则结果不成立，取反关系。
- **或**：多个原因中任一成立即结果成立。
- **与**：多个原因全部成立时结果才成立。

因果图还包含五类约束条件：

- **互斥约束**：多个原因中至多一个成立。
- **包含约束**：多个原因中至少一个成立。
- **唯一约束**：多个原因中有且仅有一个成立。
- **要求约束**：一个原因成立则另一个必须成立。
- **屏蔽约束**：一个原因成立则另一个必须不成立。



#### 因果图到测试用例的转换

转换过程通常包含五步：

- **第一步**：从需求中识别原因与结果，并为其编号。
- **第二步**：分析原因与结果之间的逻辑关系，画出因果图。
- **第三步**：标注原因之间与结果之间的约束条件。
- **第四步**：把因果图转换为判定表，穷尽有效的条件组合。
- **第五步**：把判定表的每一列转换为一条测试用例。

**对比因果图与判定表**：**起点**：因果图从需求中分析因果并画图，判定表直接列举条件组合。**表达能力**：因果图能显式表达条件之间的约束关系（互斥、包含等），判定表以组合列的方式间接体现。**实际使用**：二者常结合使用，先用因果图梳理关系，再落为判定表生成用例。**共同点**：二者都以多条件组合为处理对象，都能保证组合覆盖的完备性。

> [!NOTE]
> **提醒内容**：**因果图在考试中通常只要求「读懂关系并转换为判定表」**，不要求手绘完整图形。掌握四种关系与五类约束的含义，并会判断「某场景应用了哪种约束」即可。若题干给出条件组合并要求指出缺失的规则，直接按判定表的思路列举全部组合再比对。



### 正交实验法与场景法

#### 正交实验法

**正交实验法**用于处理**多因素多水平**的组合爆炸问题，通过选择具有代表性的少量组合，在显著降低用例数量的同时保证对两两因素组合的覆盖。

- **因素**：参与实验的变量，如浏览器的种类、操作系统的种类、网络类型。
- **水平**：每个因素可能取值的个数，如浏览器有三种、操作系统有两种。
- **正交表**：一种特殊的表格，保证任意两个因素的各水平组合都恰好出现一次，即**两两组合覆盖**。
- **用例数量**：全组合数为各因素水平数之乘积，正交实验可将其压缩到接近「水平数较大的因素的水平数平方」量级。

上例中三个因素分别为三种、两种、两种水平，全组合为 12 种，正交实验通常可用 4 至 6 条用例覆盖全部两两组合。

> [!TIP]
> **建议内容**：**正交实验法最适合「配置组合类」测试**，如浏览器与操作系统的兼容性矩阵、不同参数配置的功能验证。它的前提假设是**缺陷多由两个因素的交互引起而非三因素以上**，因此适合交互影响较弱的场景；若因素之间存在强耦合，仍应退回到判定表做全组合分析。



#### 场景法

**场景法**从用户的真实使用流程出发设计用例，用**基本流**（最顺畅的成功路径）与**备选流**（各种异常与分支）组合出场景。

- **基本流**：从用例开始到成功结束的典型路径，无异常、无分支。
- **备选流**：基本流中的各种偏离，如输入错误、权限不足、外部系统超时、用户取消。
- **场景生成**：把基本流与不同的备选流组合，形成多个测试场景，每个场景对应一条用例。
- **覆盖策略**：先覆盖基本流，再让每条备选流至少被触发一次，最后组合出多异常叠加的场景。

**对比场景法与等价类划分**：**设计视角**：场景法以业务流程为主线，等价类划分以输入数据为主线。**处理对象**：场景法处理跨模块的完整流程，等价类划分处理单个输入的取值。**发现缺陷类型**：场景法擅长发现流程衔接与状态处理错误，等价类划分擅长发现输入校验错误。**共同点**：二者都需覆盖正常路径与异常路径，实践中常结合使用。

> [!WARNING]
> **警告内容**：**只测基本流是黑盒测试最常见的严重疏漏**。用户的实际使用中，异常路径的触发频率远高于开发者的预期——输入错误、网络中断、重复提交、并发操作、中途取消。若用例集只覆盖成功路径，系统会在真实环境中频繁失败。**合理的比例是备选流用例数量不低于基本流用例数量**。



### 错误推测法与测试方法的选用

#### 错误推测法

**错误推测法**依赖测试人员的经验与直觉，**推测程序中可能存在的缺陷并据此设计用例**。它没有固定的形式化步骤，但常用思路高度规律：

- **输入为空或缺失**：不填任何数据、只填部分必填项。
- **输入为非法值**：错误格式、超长字符串、特殊字符、负数、零。
- **重复提交**：连续点击提交按钮、并发发起同一请求。
- **顺序颠倒**：跳过前置步骤直接执行后续操作。
- **中断与恢复**：操作中途关闭页面、断网后重试。
- **极端数据量**：一次性导入超大数据、查询返回海量结果。
- **状态冲突**：对已删除的数据再次操作、对已支付的订单再次支付。

> [!NOTE]
> **提醒内容**：**错误推测法不能替代系统化方法，但能补足系统化方法的盲区**。等价类、边界值、判定表等方法保证「已知类型」的覆盖完备，错误推测法负责发现「意料之外」的缺陷。合理的做法是**先用形式化方法保证基线覆盖，再用错误推测法补充高风险的异常场景**。



#### 各方法的比较与选用

- **等价类划分**：适合输入域可明确划分的场景，是黑盒测试的基础方法。
- **边界值分析**：适合存在数值区间、长度限制、数量上下限的场景，优先级最高。
- **判定表与因果图**：适合业务规则由多条件组合决定的场景。
- **正交实验法**：适合多因素多水平的配置组合场景。
- **场景法**：适合跨模块的完整业务流程，尤其是状态流转复杂的系统。
- **错误推测法**：作为补充，用于高风险与历史缺陷密集区域。

> [!CAUTION]
> **注意内容**：**方法的选择取决于「缺陷可能藏在哪种结构里」，而不是方法的先进程度**。数值边界处的缺陷用边界值分析最有效，规则组合处的缺陷用判定表最有效，流程衔接处的缺陷用场景法最有效。实践中通常**组合使用多种方法**，先用等价类与边界值建立基线用例集，再用判定表或场景法补充组合与流程用例，最后用错误推测法补齐高风险异常场景。
