## 设计模式概述与创建型模式

> **全章主脉**：**设计模式是被反复验证过的、针对特定设计问题的可复用解法**，由 GoF（四人组）归纳为创建型 5 种、结构型 7 种、行为型 11 种，共 23 种。学模式的顺序应当是**先立原则、再记模式、最后看取舍**——原则解释「为什么这样设计」，模式记录「别人是怎么做的」。本章先讲模式的分类与六项设计原则，再逐一展开五种创建型模式，全部代码示例均已在 Node 环境实测通过。

### 设计模式的概念与分类

#### 设计模式的定义

**设计模式**（Design Pattern）是**在特定环境下、针对重复出现的设计问题所给出的经过验证的解决方案**。它描述的是**对象之间如何组织与协作**，而不是某段具体代码，因此与实现语言无关。

设计模式的实质是**对变化的封装**：识别出系统中会变化的部分，用接口与多态把它隔离出来，使变化不影响不变的部分。这一思想贯穿全部 23 种模式。

> [!IMPORTANT]
> **重要内容**：**设计模式不是语法技巧，也不是代码模板**。它的价值在于提供共同词汇（说「这里用策略模式」比画十分钟图更快）、沉淀设计经验、并显式标注出系统的变化点。若一段代码用了模式却说不清它隔离了什么变化，这个模式就是装饰性的，反而增加理解成本。



#### 设计模式的四要素

GoF 把每个模式的描述归纳为四个要素，四者齐备才算一个完整的模式：

- **模式名称**：一个能准确传达问题与解法的词汇，如「观察者」「装饰器」，是模式进入团队语言的入口。
- **问题**：描述模式适用的场景与条件，说明在什么情况下应当考虑它。
- **解决方案**：描述构成设计的元素、元素之间的关系、职责分配与协作方式，通常配以类图与序列图。
- **效果**：描述采用该模式后的权衡结果，包括收益、代价与需要留意的副作用。

> [!NOTE]
> **提醒内容**：**四要素中最容易被忽略的是「效果」**。每个模式都带来代价——增加间接层、增加类数量、增加运行时开销。只说收益不说代价，就会把模式当成万能药。判断是否需要某个模式，本质上是在比较它的收益与代价。



#### GoF 二十三种模式的分类

GoF 依据**模式的用途**（做什么）把 23 种模式划分为三大类：

- **创建型模式 5 种**：关注**对象的创建过程**，把创建与使用分离。含工厂方法、抽象工厂、建造者、原型、单例。
- **结构型模式 7 种**：关注**类与对象的组合方式**，通过组合获得更灵活的结构。含适配器、桥接、组合、装饰器、外观、享元、代理。
- **行为型模式 11 种**：关注**对象之间的职责分配与算法封装**，含责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者。

此外 GoF 还按**范围**给出第二种分类维度：**类模式**处理类与子类之间的关系，主要通过继承实现，编译期确定；**对象模式**处理对象之间的关系，主要通过组合实现，运行期可变。23 种模式中，绝大多数为对象模式。

> [!TIP]
> **建议内容**：**三大类的数量必须记准：创建型 5、结构型 7、行为型 11，合计 23**。这是高频记忆点。按用途分类与按范围分类是两个独立维度，不要混答——「创建型」说的是用途，「对象模式」说的是范围，同一个模式可以同时是「创建型模式」与「对象模式」。



#### 模式、原则、风格与框架的关系

四个概念层次不同，需明确区分：

- **设计原则**：最抽象，是判断设计好坏的一般准则，如单一职责、开闭原则，不提供具体结构。
- **设计模式**：中等抽象，是原则在特定问题上的具体化，提供可复用的结构，如策略模式。
- **架构风格**：宏观层面，规定系统的整体组织范式，如分层、事件驱动，影响全局质量属性。
- **框架**：可运行的半成品软件，规定扩展点由使用者填充，属于代码级的复用，如 Spring、Vue。

**对比设计模式与框架**：**层次**：模式是设计经验的描述，与语言和平台无关；框架是可运行的代码骨架，与语言和平台强绑定。**控制方向**：使用模式时由开发者调用库，控制流在开发者手中；使用框架时框架调用开发者填写的代码，即**控制反转**。**共同点**：二者都通过复用降低开发成本，都要求理解其设计意图才能正确使用。

> [!CAUTION]
> **注意内容**：**不要为了用模式而用模式**。模式是解决已知问题的工具，不是展示水平的装饰。当一段代码只有一种实现、且短期内不会扩展时，引入工厂、策略或抽象工厂只会增加阅读成本。判断标准很简单——**该变化点是否真实存在**，若不存在，模式带来的抽象就是纯负担。



### 面向对象设计的六项原则

#### 单一职责原则与开闭原则

**单一职责原则**（Single Responsibility Principle，SRP）指出：**一个类应当只有一个引起它变化的原因**。这里的「职责」指的是变化的来源，而非功能的数量。

- **判据**：如果一个类会因两种不同的业务需求而修改，说明它承担了多个职责。
- **表现**：职责过多导致类臃肿、修改互相牵连、难以复用与测试。
- **应用**：把不同变化来源的逻辑拆到不同类中，使每个类只对一个变化源负责。

**开闭原则**（Open-Closed Principle，OCP）指出：**软件实体应当对扩展开放、对修改关闭**。即新增功能时应通过增加新代码实现，而不是修改既有代码。

- **实现手段**：抽象化与多态、依赖注入、配置化、注册机制。
- **与 SRP 的关系**：SRP 通过拆分变化源为 OCP 提供前提；职责混杂的类无法做到只扩展不修改。
- **价值**：OCP 是设计模式的总目标，绝大多数模式都在以不同方式实现「不改老代码即可扩展」。

> [!IMPORTANT]
> **重要内容**：**开闭原则是整个设计模式体系的总纲**。判断某个模式为什么存在，几乎都可以问一句「它如何帮助实现不改老代码就能扩展」。策略模式让算法可扩展、观察者模式让订阅者可扩展、装饰器让功能可叠加、工厂方法让产品种类可扩展——凡此种种都是 OCP 的具体形态。



#### 里氏替换原则与依赖倒置原则

**里氏替换原则**（Liskov Substitution Principle，LSP）指出：**所有引用基类的地方必须能透明地使用其子类的对象**。子类可以扩展父类的行为，但不能改变父类已约定的语义。

- **违反的典型表现**：子类方法抛出父类方法不抛出的异常、子类加强了前置条件、子类削弱了后置条件、子类对父类已实现的方法直接覆盖为空实现。
- **经典反例**：正方形继承长方形，改变宽时会同时改变高，破坏了长方形的语义契约。
- **判断方法**：看客户端代码是否需要在调用处判断「这是哪个子类」——若需要，说明 LSP 已被破坏。

**依赖倒置原则**（Dependency Inversion Principle，DIP）指出：**高层模块不应该依赖低层模块，二者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象**。

- **依赖方向**：传统分层中高层直接依赖低层实现，DIP 要求把依赖方向倒置为「双方都依赖接口」。
- **实现手段**：定义接口、依赖注入、控制反转容器。
- **与开闭原则的关系**：DIP 是实现 OCP 的主要技术路径，抽象稳定、细节可变，把易变部分挡在接口之后。

> [!NOTE]
> **提醒内容**：**里氏替换与依赖倒置常被混记，区分方法看「谁替换谁、谁依赖谁」**——**LSP 讲子类与父类的替换关系**，关注继承是否正确；**DIP 讲高层与低层通过抽象解耦**，关注依赖方向是否正确。前者是继承的使用约束，后者是模块的解耦手段。



#### 接口隔离原则与迪米特法则

**接口隔离原则**（Interface Segregation Principle，ISP）指出：**客户端不应该被迫依赖它不使用的方法**。应当把臃肿的接口拆分为多个小而专的接口。

- **违反的典型表现**：一个接口定义了十几个方法，实现类被迫为空实现一部分方法。
- **后果**：实现类充满空方法或异常抛出，接口的语义被稀释，修改接口会波及所有实现类。
- **应用**：按客户端的使用需求拆分接口，一个接口只服务一类客户端。

**迪米特法则**（Law of Demeter，LoD）又称**最少知识原则**，指出**一个对象应当尽可能少地了解其他对象**，只与直接的朋友通信。

- **朋友的范围**：对象自身、作为参数传入的对象、自身创建的对象、自身的成员对象。
- **违反的典型表现**：出现「a.getB().getC().doSomething()」这类长链调用，客户端穿透了多层内部结构。
- **代价**：为满足迪米特法则需要增加大量转发方法，可能反而增加代码量，因此需要权衡。

> [!TIP]
> **建议内容**：**迪米特法则的记忆抓手是「不要和陌生人说话」**。判断一段代码是否违反它，看调用链上是否穿越了非直接持有的对象。链越长，说明内部结构暴露越彻底，上游一改就会连锁断裂。



#### 合成复用原则

**合成复用原则**（Composite Reuse Principle，CRP）指出：**优先使用对象组合或聚合来实现复用，而不是使用继承**。

- **继承的局限**：继承在编译期确定、破坏封装（子类可见父类实现细节）、父子类强耦合、单继承语言下灵活性受限。
- **组合的优势**：组合在运行期可变、封装性好、耦合低、可通过替换部件改变行为。
- **判断依据**：若两个类的关系是「是一个」用继承，是「有一个」用组合；若关系介于两者之间或会变化，优先用组合。

**对比继承与组合**：**绑定时机**：继承在编译期确定，组合可在运行期替换。**封装性**：继承会暴露父类实现细节，组合只暴露接口。**耦合度**：继承是白箱复用、耦合强，组合是黑箱复用、耦合弱。**复用单位**：继承复用整个父类行为，组合复用某个部件的能力。**共同点**：二者都是复用手段，可结合使用，例如子类内部持有其他对象以扩展能力。

> [!NOTE]
> **提醒内容**：**六项原则中，合成复用原则对设计实践的指导最直接**。实践中大量设计问题源于滥用继承——继承层次过深、子类被迫实现无意义的方法、父类一改全族崩溃。凡是能用组合表达的关系，都不要用继承；只有当子类确实是父类的特例时，继承才合适。装饰器、策略、桥接、代理等模式都是合成复用原则的直接产物。



### 创建型模式

#### 简单工厂

**简单工厂**（Simple Factory）不属于 GoF 的 23 种模式，但在实践中使用极为广泛。它由**一个工厂类集中负责所有产品的创建**，客户端只需传入参数即可获得对应产品，无需了解具体类名。

- **优点**：客户端与具体产品解耦，创建逻辑集中。
- **缺点**：工厂类集中了全部产品的创建逻辑，**新增产品必须修改工厂类**，违反开闭原则，因此被 GoF 排除在正式模式之外。
- **改进方向**：用工厂方法模式取而代之，把创建逻辑分散到各具体工厂。

> [!NOTE]
> **提醒内容**：**简单工厂常被考到「它为什么不是 GoF 模式」**，标准答案是**它违反开闭原则**——每增加一个产品就要修改工厂类中的分支判断。这一对比也解释了工厂方法模式存在的理由：把「选哪个产品」的决定权下移给子类或注册表，从而使新增产品无需修改既有代码。



#### 工厂方法模式

**工厂方法模式**定义**一个用于创建对象的接口，但让子类决定实例化哪一个类**，从而把类的实例化推迟到子类。每个具体产品都有对应的具体工厂。

```js
class WechatPay { pay(amount) { return `微信支付 ${amount} 元`; } }
class Alipay { pay(amount) { return `支付宝支付 ${amount} 元`; } }

class PayChannelFactory {
  create(channel) {
    const registry = { wechat: WechatPay, alipay: Alipay };
    const Channel = registry[channel];
    if (!Channel) throw new Error(`未知支付渠道：${channel}`);
    return new Channel();
  }
}

const channelFactory = new PayChannelFactory();
console.log(channelFactory.create('wechat').pay(100));
console.log(channelFactory.create('alipay').pay(200));

// 输出：
// 微信支付 100 元
// 支付宝支付 200 元
```

- **角色构成**：抽象产品、具体产品、抽象工厂、具体工厂。
- **优点**：新增产品只需新增具体产品与具体工厂，**无需修改既有代码**，符合开闭原则；客户端只依赖抽象产品。
- **缺点**：每增加一个产品就要增加一个工厂类，类的数量成对增长；结构比简单工厂复杂。

> [!TIP]
> **建议内容**：上例中的注册表写法是工厂方法在动态语言中的常见变形——**用「产品名到构造函数」的映射表代替分支判断**，从而达到新增产品只需注册、不必修改工厂逻辑的效果。这与简单工厂的关键区别在于：简单工厂的扩展点是「修改工厂代码」，注册表方案的扩展点是「新增注册项」。



#### 抽象工厂模式

**抽象工厂模式**提供**创建一系列相关或相互依赖对象的接口**，而无需指定它们的具体类。它面向的不是单个产品，而是**产品族**。

```js
class MysqlUser { save() { return 'MySQL 保存用户'; } }
class MysqlOrder { save() { return 'MySQL 保存订单'; } }
class PgUser { save() { return 'PostgreSQL 保存用户'; } }
class PgOrder { save() { return 'PostgreSQL 保存订单'; } }

class MysqlFactory {
  createUser() { return new MysqlUser(); }
  createOrder() { return new MysqlOrder(); }
}

class PgFactory {
  createUser() { return new PgUser(); }
  createOrder() { return new PgOrder(); }
}

const persist = (factory) => [factory.createUser().save(), factory.createOrder().save()].join('，');

console.log(persist(new MysqlFactory()));
console.log(persist(new PgFactory()));

// 输出：
// MySQL 保存用户，MySQL 保存订单
// PostgreSQL 保存用户，PostgreSQL 保存订单
```

- **产品族与产品等级**：**产品族**是同一工厂产出的成套产品（如 MySQL 系的用户与订单组件）；**产品等级**是同类产品在不同族中的对应物（如各数据库的用户组件）。
- **优点**：保证同一产品族内的产品被配套使用，避免混搭；切换产品族只需替换工厂。
- **缺点**：**新增产品等级困难**——要在抽象工厂中加入新方法，所有具体工厂都要跟着改，违反开闭原则。

**对比工厂方法与抽象工厂**：**创建对象数量**：工厂方法创建一个产品，抽象工厂创建一族产品。**关注点**：工厂方法关注「产品种类可扩展」，抽象工厂关注「产品族可切换」。**扩展方向**：工厂方法便于新增产品，抽象工厂便于新增产品族，但难以新增产品等级。**结构复杂度**：抽象工厂的接口方法更多，具体工厂数量等于产品族数量。

> [!IMPORTANT]
> **重要内容**：**两个工厂模式的取舍依据是「变化的维度」**。如果变化的是「增加一种新产品」（如新增一种支付渠道），用工厂方法；如果变化的是「整套技术方案切换」（如从 MySQL 整体换到 PostgreSQL），用抽象工厂。判断方法是数一数：变化发生在纵向（新增同类产品）还是横向（成套替换）。



#### 建造者模式

**建造者模式**把**一个复杂对象的构建过程与它的表示分离**，使同样的构建过程可以创建不同的表示。它适用于构建步骤固定、但步骤组合方式或各部件的具体内容可变的场景。

```js
class QueryBuilder {
  constructor() { this.parts = { select: '*', from: '', where: [], orderBy: '', limit: 0 }; }
  select(fields) { this.parts.select = fields; return this; }
  from(table) { this.parts.from = table; return this; }
  where(condition) { this.parts.where.push(condition); return this; }
  orderBy(clause) { this.parts.orderBy = clause; return this; }
  limit(count) { this.parts.limit = count; return this; }
  build() {
    const { select, from, where, orderBy, limit } = this.parts;
    let sql = `SELECT ${select} FROM ${from}`;
    if (where.length) sql += ` WHERE ${where.join(' AND ')}`;
    if (orderBy) sql += ` ORDER BY ${orderBy}`;
    if (limit) sql += ` LIMIT ${limit}`;
    return sql;
  }
}

console.log(new QueryBuilder().select('id, name').from('t_user')
  .where('age > 18').where("city = '太原'").orderBy('name').limit(10).build());

// 输出：
// SELECT id, name FROM t_user WHERE age > 18 AND city = '太原' ORDER BY name LIMIT 10
```

- **角色构成**：**产品**（被构建的复杂对象）、**抽象建造者**（规定构建各部件的方法）、**具体建造者**（实现各部件的构建）、**指挥者**（负责按固定顺序调用建造步骤）。
- **与工厂模式的差别**：工厂模式一次调用产出一个产品，**建造者模式分步构建、最后一步才产出产品**；工厂关注「创建哪个产品」，建造者关注「如何分步组装这个产品」。
- **优点**：构建过程与表示分离、可复用同一构建流程产出不同结果、客户端无需知道内部组装细节。
- **缺点**：需要为每种表示定义具体建造者，类的数量增加；产品差异过大时建造者接口难以统一。

> [!NOTE]
> **提醒内容**：**链式调用只是建造者的常见实现形式，不是它的本质**。建造者的本质是「分步构建加最后产出」，因此既可以用链式调用实现，也可以用指挥者加多参数实现。若一个对象只有两三个参数，用构造函数加默认值即可，不必引入建造者。



#### 原型模式

**原型模式**通过**复制已有实例来创建新对象**，而不是通过构造函数从头创建。它适用于创建成本高、或需要保留初始状态作为模板的场景。

```js
const template = { title: '月度报告', sections: ['概述'] };
const shallow = { ...template };
shallow.sections.push('明细');
console.log(template.sections.length);

const strictTemplate = { title: '月度报告', sections: ['概述'] };
const deep = structuredClone(strictTemplate);
deep.sections.push('明细');
console.log(strictTemplate.sections.length);

// 输出：
// 2   —— 浅拷贝只复制了引用，修改副本污染了原对象
// 1   —— 深拷贝连同嵌套结构一起复制，原对象不受影响
```

- **浅拷贝**：只复制对象本身与各属性的引用，嵌套对象仍与原对象共享，修改嵌套结构会互相影响。
- **深拷贝**：递归复制全部层级，副本与原对象完全独立。
- **优点**：跳过昂贵的初始化过程、可动态增减原型、以复制代替工厂层级。
- **缺点**：深拷贝实现复杂（需处理循环引用、不可复制成员），且对含有大量内部结构的对象开销不小。

> [!WARNING]
> **警告内容**：**原型模式最容易出错的地方是浅拷贝与深拷贝混用**。上例第一段输出为 2，正是浅拷贝共享嵌套数组导致的污染——这在配置模板、默认参数、缓存对象上非常常见，且往往在运行时才暴露、极难排查。凡是用原型模式，必须明确当前需要的是浅拷贝还是深拷贝，并在文档与命名上写清楚。



#### 单例模式

**单例模式**保证**一个类只有一个实例，并提供访问它的全局访问点**。它适用于配置中心、连接池、日志器、缓存管理等「全局唯一且有状态」的场景。

```js
class ConfigCenter {
  static #instance = null;
  constructor() {
    if (ConfigCenter.#instance) return ConfigCenter.#instance;
    this.items = new Map();
    ConfigCenter.#instance = this;
  }
  set(key, value) { this.items.set(key, value); return this; }
  get(key) { return this.items.get(key); }
}

const configA = new ConfigCenter();
const configB = new ConfigCenter();
configA.set('timeout', 3000);
console.log(configA === configB);
console.log(configB.get('timeout'));

// 输出：
// true
// 3000
```

- **实现要点**：私有化构造函数、持有静态实例、提供获取实例的方法。上例利用构造函数中返回值覆盖默认行为的特性，使多次调用返回同一实例。
- **优点**：控制实例数量、节省资源、提供统一的访问点。
- **缺点**：**引入全局状态**，使依赖关系隐藏在代码内部而不体现在接口上；难以替身与测试；在多线程与分布式环境下需要额外处理并发与进程边界问题。

> [!CAUTION]
> **注意内容**：**单例是设计模式中最容易被滥用的一种**。把单例当作全局变量的替代品，会使模块之间产生看不见的耦合，导致单元测试无法隔离、并发改动互相干扰。在多进程与分布式部署下，单例只在单个进程内唯一，**并不等于全系统唯一**——若业务需要全局唯一，应改用分布式锁或集中式存储，而不是单例。



### 创建型模式的横向比较

#### 五种模式的关注点差异

五种创建型模式回答的是不同层面的创建问题：

- **工厂方法**：解决「创建哪一个产品」的问题，把选择权交给子类或注册表，扩展方向是新增产品。
- **抽象工厂**：解决「创建哪一族产品」的问题，保证产品族内部的配套一致，扩展方向是新增产品族。
- **建造者**：解决「如何分步组装复杂对象」的问题，把构建过程与最终表示分离。
- **原型**：解决「如何低成本复制已有对象」的问题，用复制代替重新构造。
- **单例**：解决「如何保证只存在一个实例」的问题，控制实例数量与访问方式。



#### 选用要点

选择创建型模式的判断链如下：

- **需要保证全局唯一**：选**单例**。
- **需要按条件创建不同产品，且种类会增长**：选**工厂方法**。
- **需要成套切换技术方案，且族内产品必须配套**：选**抽象工厂**。
- **对象构建步骤多、组合复杂、需要同流程产出不同结果**：选**建造者**。
- **对象初始化代价高，或需要用模板批量产出近似对象**：选**原型**。
- **只是把创建逻辑从客户端挪走，且产品种类稳定**：用**简单工厂**即可，不必升格为正式模式。

> [!TIP]
> **建议内容**：**创建型模式的记忆线索是「唯一、选一、选一族、分步拼、复制」**——唯一对应单例，选一对应工厂方法，选一族对应抽象工厂，分步拼对应建造者，复制对应原型。这个顺序也大致对应从简单到复杂的引入成本，选用时应从成本最低者开始考虑。
