## 白盒测试与覆盖率

> **全章主脉**：**白盒测试依据程序的内部逻辑结构设计用例，目标是让各类逻辑路径得到执行**。它回答的问题是「代码内部有没有走不到的分支、有没有处理错误的逻辑」。核心内容是**六种逻辑覆盖准则**（语句、判定、条件、判定条件、条件组合、路径）与**基本路径测试**（流图、环路复杂度、基本路径集）。示例代码与判定结果均已在 Node 环境实测通过。

### 白盒测试概述

#### 白盒测试的基本思想

**白盒测试**（又称结构测试或逻辑驱动测试）**把程序视为透明的盒子，依据程序的内部逻辑结构设计测试用例**，检查程序中的每条路径、每个判定的真假分支、每个条件的取值是否都能按预期工作。

- **测试依据**：源代码、流程图、控制流图、数据流图、设计文档。
- **测试视角**：从实现者角度出发，关注逻辑分支与执行路径的覆盖情况。
- **核心指标**：覆盖率，即被测试执行到的逻辑元素占全部逻辑元素的比例。
- **典型手段**：逻辑覆盖法、基本路径测试、循环测试、数据流测试、程序插桩与静态分析。

> [!IMPORTANT]
> **重要内容**：**白盒测试的目标不是「覆盖率达到 100%」，而是「发现逻辑缺陷」**。覆盖率是手段与度量，不是目的。实践中存在大量「覆盖率很高但缺陷仍未被发现」的情形——例如条件内部的组合错误、缺失的分支、错误的边界判断。因此在追求覆盖率的同时，必须结合代码审查与静态分析。



#### 白盒测试能发现与不能发现的问题

- **能发现的问题**：逻辑判断错误、条件组合遗漏、循环边界与终止条件错误、内部变量未初始化或计算错误、异常分支未处理、不可达代码。
- **不能发现的问题**：需求本身错误（实现了错误的需求）、功能遗漏（代码中根本没有对应逻辑）、性能与可用性问题、接口不匹配造成的集成问题、用户体验问题。

> [!NOTE]
> **提醒内容**：**白盒测试无法发现「缺失的功能」**。若需求要求某功能而代码中完全没有实现，白盒测试无论如何设计路径都不会发现——因为它只能测试已存在的代码。**「缺失」类缺陷只能由黑盒测试、需求追踪矩阵或代码审查发现**，这是两类测试最根本的分工。



### 逻辑覆盖的层级

逻辑覆盖按严格程度由弱到强依次为**语句覆盖、判定覆盖、条件覆盖、判定条件覆盖、条件组合覆盖、路径覆盖**，覆盖强度逐级提升，用例数量也随之增加。

#### 语句覆盖

**语句覆盖**要求**程序中的每条可执行语句至少被执行一次**，是最弱的覆盖准则。

- **优点**：用例数量少、执行成本低，可快速验证代码基本可运行。
- **缺点**：**无法发现判定中的逻辑错误**。例如把条件中的「与」误写为「或」，只要语句被执行过，语句覆盖仍然满足。
- **结论**：语句覆盖强度过低，通常不作为独立目标使用，只作为最低门槛。



#### 判定覆盖

**判定覆盖**（又称分支覆盖）要求**每个判定的真分支与假分支至少各被执行一次**，即每个判定都要取到真和假两种结果。

- **优点**：能发现判定结果被整体取反的错误（如条件写反），强度高于语句覆盖。
- **缺点**：**不保证判定内部各条件的取值被覆盖**。一个由多个条件复合而成的判定，只要整体结果为真与假各出现一次即可满足判定覆盖，内部各条件的组合可能从未被触发。
- **结论**：判定覆盖是实践中常用的最低可接受标准。



#### 条件覆盖

**条件覆盖**要求**每个判定中的每个原子条件都至少取到一次真值与一次假值**，而不关心判定的整体结果。

- **优点**：细化了覆盖粒度，能发现单个条件的取值错误。
- **缺点**：**条件覆盖不一定满足判定覆盖**。可能出现所有条件的真值都在同一组用例中被取到，而判定的某个整体结果从未出现。
- **结论**：条件覆盖强度高于判定覆盖但存在盲区，需与判定覆盖结合。



#### 判定条件覆盖

**判定条件覆盖**要求**同时满足判定覆盖与条件覆盖**，即每个判定的真假分支各出现一次，且每个原子条件的真假值各出现一次。

- **优点**：弥补了条件覆盖不保证判定覆盖的缺陷，覆盖强度更高。
- **缺点**：**仍不保证条件组合被覆盖**。当判定中含多个条件时，某些条件组合可能从未出现，而组合处正是逻辑缺陷的高发区。
- **结论**：判定条件覆盖是实践中常见的折中标准。



#### 条件组合覆盖

**条件组合覆盖**要求**每个判定中所有原子条件的各种可能取值组合至少出现一次**。

- **优点**：能发现条件组合层面的逻辑错误，强度显著高于判定条件覆盖。
- **缺点**：**组合数随条件数量指数增长**。含三个条件的判定就有八种组合，含五个条件则有三十二种，用例数量可能急剧膨胀。
- **结论**：适合条件数量较少的关键逻辑；条件较多时需结合等价类思想裁剪。



#### 路径覆盖

**路径覆盖**要求**覆盖程序中所有可能的执行路径**，是强度最高的覆盖准则。

- **优点**：覆盖最彻底，能发现路径相关的逻辑错误。
- **缺点**：**路径数量随判定数量指数增长**，且含循环时路径数量可能无限，实际不可穷尽；同时并非所有路径都可达，存在不可达路径造成的无解。
- **结论**：路径覆盖通常只在小规模关键模块上执行，实践中多用**基本路径测试**作为可操作的近似。

**对比六种覆盖准则**：**强度顺序**：语句覆盖弱于判定覆盖，判定覆盖与条件覆盖各有盲区，判定条件覆盖强于二者，条件组合覆盖又强于判定条件覆盖，路径覆盖最强。**用例数量**：随强度递增，路径覆盖可能不可穷尽。**实践取舍**：工业界通常以**判定覆盖**为最低门槛，以**判定条件覆盖或条件组合覆盖**为关键模块的目标。

> [!IMPORTANT]
> **重要内容**：**六种覆盖的强度顺序与「谁包含谁」是高频考点**：**语句覆盖最弱**，**判定覆盖与条件覆盖互不包含**（条件覆盖不保证判定覆盖，判定覆盖不保证条件覆盖），**判定条件覆盖是二者的交集要求**，**条件组合覆盖强于判定条件覆盖**，**路径覆盖最强但通常不可穷尽**。记住「互不包含」这一点，就能正确回答大部分辨析题。



### 基本路径测试

#### 控制流图

**控制流图**（流图）是对程序控制结构的图形化抽象，用结点表示语句或语句序列，用带箭头的边表示控制转移。

- **结点**：表示一条或多条顺序执行的语句，连续的顺序语句可合并为一个结点。
- **边**：表示控制流的方向，条件判定处会分出多条边。
- **判定结点**：出度大于一的结点，对应程序中的条件判断。
- **区域**：边与结点围成的封闭或半封闭区域，含图外部的那一个区域。



#### 环路复杂度

**环路复杂度**（又称圈复杂度或 McCabe 复杂度）是衡量程序逻辑复杂度的指标，同时也**给出了独立路径数量的上界，即所需测试用例数量的下限**。其计算方法有三种，结果一致：

- **边与结点法**：环路复杂度等于边数减结点数加二。
- **判定结点法**：环路复杂度等于判定结点数加一。
- **区域法**：环路复杂度等于控制流图中的区域数（含图外区域）。

以下面这段代码为例，计算其环路复杂度：

```js
function judgeScore(score, isRetake) {
  let level;
  if (score >= 90) {
    level = '优';
  } else if (score >= 60) {
    level = isRetake ? '及格（补考）' : '及格';
  } else {
    level = '不及格';
  }
  return level;
}

console.log(judgeScore(95, false));
console.log(judgeScore(70, true));
console.log(judgeScore(59, false));

// 输出：
// 优
// 及格（补考）
// 不及格
```

代码中有三个判定结点——第一个条件判断、第二个条件判断与三元表达式，因此判定结点数为 3，环路复杂度为 3 加 1 等于 **4**。这一结果说明该函数至少需要 4 条独立路径用例才能覆盖。

> [!TIP]
> **建议内容**：**环路复杂度的三种算法要会互相验证**。考试中若给出流图，用「边减结点加二」最直接；若给出代码文本，用「判定结点数加一」最快。需要特别注意：**复合条件（含与、或的判定）在流图中只算一个判定结点**，因此环路复杂度不随条件内部项数增加，这也是它无法衡量条件内部复杂度的原因。



#### 基本路径集的构造

**基本路径测试**通过构造一组**相互独立的基本路径**来达到路径覆盖的近似，其步骤为：

- **第一步**：根据程序过程设计绘制控制流图。
- **第二步**：计算环路复杂度，确定所需独立路径数量的上界。
- **第三步**：确定一组基本路径，第一条通常取最典型的正常路径，后续每条路径依次引入新的边。
- **第四步**：为每条基本路径设计测试用例，给定输入并确定预期输出。
- **第五步**：执行用例并核对结果。

对上例，环路复杂度为 4，因此需要 4 条基本路径：

```text
路径 1（score >= 90 为真）：score = 95 → 优
路径 2（score >= 90 为假，score >= 60 为真，isRetake 为假）：score = 70 → 及格
路径 3（score >= 90 为假，score >= 60 为真，isRetake 为真）：score = 70 → 及格（补考）
路径 4（score >= 90 为假，score >= 60 为假）：score = 59 → 不及格
```

> [!NOTE]
> **提醒内容**：**基本路径集的数量等于环路复杂度**，这一对应关系是最常考的结论。构造时可采用「先画流图、再算复杂度、最后逐条引出新路径」的流程，不必追求一次性找全。**要确保每条新路径至少引入一条此前未覆盖的边**，否则它不属于基本路径集。



### 循环测试与数据流测试

#### 循环测试

循环结构是路径数量爆炸的主要原因，因此通常单独测试。对简单循环，测试重点在四类边界值：

- **零次循环**：完全不进入循环体，验证循环被正确跳过。
- **一次循环**：只执行一次，验证首次执行的处理。
- **典型次数循环**：执行中间次数，验证正常迭代行为。
- **最大次数与最大次数加一**：验证循环上限与越界处理。

对嵌套循环与串接循环，常用策略是从内向外逐层测试，或在固定外层循环次数的前提下测试内层循环。



#### 数据流测试

**数据流测试**关注**变量的定义与使用之间的关系**，而非控制结构：

- **定义**：变量被赋值的位置。
- **使用**：变量被读取的位置。
- **定义使用路径**：从变量定义点到其使用点的执行路径。
- **检测目标**：发现变量未初始化即被使用、定义后从未被使用（冗余赋值）、以及在某个路径上定义被覆盖导致使用了错误值等缺陷。

> [!TIP]
> **建议内容**：**数据流测试能发现控制流覆盖发现不了的缺陷**。一个变量在两条不同路径上被赋予不同的值，若只覆盖其中一条路径，控制流覆盖可以满足，但另一条路径上可能使用了错误的值。因此在处理复杂的条件赋值逻辑时，数据流测试的价值高于单纯的判定覆盖。



### 白盒与黑盒的结合

#### 灰盒测试

**灰盒测试**介于白盒与黑盒之间，测试人员**了解部分内部结构信息但不深入代码细节**，据此设计更有针对性的用例。

- **典型形式**：依据数据库表结构设计数据一致性测试、依据接口协议设计契约测试、依据状态机设计状态迁移测试。
- **优势**：兼具黑盒的端到端视角与白盒的针对性，是集成测试阶段最常用的形态。



#### 测试策略中的分工

实际项目中两类测试按层次与目标分工：

- **单元测试**：以白盒为主，由开发者执行，追求判定覆盖或分支覆盖。
- **集成测试**：灰盒为主，关注接口与数据传递，必要时补充白盒分析。
- **系统与验收测试**：以黑盒为主，由独立测试团队执行，依据需求设计场景。
- **缺陷定位与修复验证**：白盒为主，依据缺陷报告定位具体代码位置。

> [!WARNING]
> **警告内容**：**颠倒黑白盒的分工是常见的组织错误**。若要求独立测试团队做白盒覆盖，他们会因不了解实现而效率低下；若要求开发者只做黑盒测试，则内部的逻辑缺陷无人发现。**正确的分工是：开发者负责白盒与单元级质量，独立团队负责黑盒与系统级质量，灰盒用于两者的衔接面**。



### 覆盖率度量及其局限

#### 常用覆盖率指标

- **语句覆盖率**：被执行的语句数占语句总数的比例。
- **判定覆盖率**：被取到真与假两种结果的判定比例。
- **条件覆盖率**：被取到真假值的原子条件比例。
- **路径覆盖率**：被执行的路径占全部可达路径的比例。
- **函数与方法覆盖率**：被调用的函数或方法比例。
- **代码行与分支覆盖率**（工具常用）：以插桩方式统计的行与分支覆盖情况。



#### 覆盖率的局限

- **覆盖率不等于质量**：高覆盖率只能说明代码被执行过，不能说明结果被正确验证。
- **无法覆盖需求缺失**：代码中根本没实现的功能，覆盖率再高也发现不了。
- **无法覆盖组合错误**：判定覆盖满足时，条件内部的错误组合可能仍未被触发。
- **覆盖率可被人为操纵**：为追求覆盖率数字而编写无断言的用例，是一种自欺欺人的做法。
- **100% 覆盖未必可达**：存在不可达代码、防御性分支与平台相关分支时，100% 覆盖率往往不可实现。

> [!CAUTION]
> **注意内容**：**不要用覆盖率考核开发或测试人员的绩效**。一旦覆盖率成为考核指标，最经济的应对方式就是编写大量无断言的「走过场」用例，使覆盖数字上升而缺陷发现率下降。**覆盖率只应用作发现测试盲区的诊断工具**——查看哪些模块覆盖率异常低，据此前去补测，而不是把它当作达标的证明。
