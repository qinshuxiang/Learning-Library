## 参考资料与延伸阅读

### 在线工具

#### 调试与验证工具

- **regex101.com**：在线解释器，能逐 token 解释模式、展示匹配步骤与回溯次数，是最常用的学习工具；注意把页面右上角的测试器标志（g、i 等）调成与生产代码一致，否则行为对不上。
- **regex-vis.com**：把正则渲染成可视化铁路图，长模式的辅助理解工具。
- **console 实测**：不确定返回值时，直接在控制台跑一遍比记忆规则更可靠。
- **Node 与浏览器控制台**：涉及 u、v、d 这类较新标志时，用目标运行环境实测一次，比在线工具更接近真实行为。

```js
const reg = /\d{3}/g;
console.log(reg.toString()); // "/\d{3}/g"
console.log(`${reg.source} | ${reg.flags}`); // "\d{3} | g"
```

> [!TIP]
> **建议内容**：用在线测试器验证模式后，**把模式、标志、测试串三样原样搬进生产代码**，不要凭记忆重写。测试器为方便而自动附加的 g 或 i 标志，是“测试通过、上线失灵”的常见来源。



#### 控制台排查小工具

**把常用排查动作写成小函数**，遇到“匹配不上”“替换不对”时先跑一遍，比反复改模式猜原因快得多。

- **看码点**：把字符串拆成码点并打印十六进制，专治不可见字符。
- **看全量匹配**：用 matchAll 打印每次匹配的完整串、分组与下标。
- **看替换输出**：替换类问题必须打印最终字符串，而不是匹配列表。
- **看回溯规模**：把可疑模式放到 regex101 的调试面板，观察回溯步数随输入长度增长的速度。

```js
// 三件套：码点、匹配详情、替换输出
function showCodePoints(text) {
  return [...text].map(
    (char) => "U+" + char.codePointAt(0).toString(16).toUpperCase().padStart(4, "0")
  );
}

function showMatches(text, reg) {
  return [...text.matchAll(reg)].map((m) => ({ match: m[0], groups: m.slice(1), index: m.index }));
}

console.log(showCodePoints("a\u00A0b"));            // ["U+0061", "U+00A0", "U+0062"]
console.log(showMatches("a1 b2", /([a-z])(\d)/g));  // 两条含 groups 与 index 的记录
console.log("价格 128".replace(/(\d+)/, "[$&]"));   // "价格 [128]"
```



### 系统学习资源

#### 权威文档与教程

- **MDN 正则表达式指南**：最权威的中文参考，覆盖语法、方法与实例；RegExp 对象页列全了全部属性与方法签名。
- **javascript.info 正则章节**：从字符类到贪婪惰性再到捕获组，体系完整、例题丰富，适合系统刷一遍。
- **RegexOne**：交互式入门教程，逐课练习，适合零基础起步。
- **ECMA-262 规范**：行为有争议时以规范为准，重点看 RegExp Objects 与 Pattern Semantics 两节；Quantifier、RepeatMatcher、GetSubstitution 这些名词都出自这里。

> 系列各篇的引用规则：行为性结论以 MDN 与 ECMA-262 为准；教程性示例参考 javascript.info 的组织方式；安全结论以 NVD、GitHub Advisory Database、OWASP 等披露源为据。



#### 按主题查哪一节

**带着问题找文档**比从头刷一遍更快。下表按常见疑问列出对应的查阅位置（按主题列举，不作先后顺序）。

- **“某个标点是不是元字符”**：查 MDN 的 RegExp 语法速查页，或直接看规范里 Pattern Semantics 的语法产生式。
- **“\\p{...} 支持哪些属性”**：查 MDN 的 Unicode character class escape 页，属性名与别名以 Unicode 标准的 PropertyValueAliases 文件为准。
- **“这个方法返回什么”**：查 MDN 对应方法页的返回值与异常章节，比凭记忆可靠。
- **“两个引擎行为不一致”**：查规范条文加各引擎的兼容性表格，注意 V8、SpiderMonkey、JavaScriptCore 的落地版本差异。
- **“这个标志能不能用”**：查 MDN 浏览器兼容性表与 Node 各版本的 V8 版本对照，不要以开发机为唯一依据。

```js
// 一行代码确认当前运行环境的支持面
console.log({
  v8: process.versions.v8,
  hasEscape: typeof RegExp.escape,          // ES2025，Node 24 起
  hasVFlag: (() => { try { new RegExp("a", "v"); return true; } catch { return false; } })(),
  hasDupName: (() => { try { new RegExp("(?<a>x)|(?<a>y)"); return true; } catch { return false; } })(),
});
```



### 安全与漏洞资源

#### 漏洞库与披露平台

**ReDoS 属于 CWE 编号与 CVE 体系内的正式缺陷类型**，遇到可疑模式或依赖时，下面几个平台是权威入口。

- **GitHub Advisory Database**：npm 生态的漏洞通告入口，可按包名与 CVE 编号查询，条目含受影响版本区间与修复版本。
- **NVD（美国国家漏洞库）**：CVE 的权威登记处，含 CVSS 评分与 CWE 分类。
- **OSV**：聚合多个漏洞库的开放数据源，支持按包名批量查询。
- **Snyk 漏洞库**：面向开发者的漏洞说明，附带修复建议与代码示例。
- **CWE-1333**：规范里对“低效正则复杂度”这一缺陷类型的编号，查报告时用这个编号最准。

> [!NOTE]
> **提醒内容**：**漏洞编号要核对到具体条目再引用**。同一类 ReDoS 在不同包里有不同编号（例如归一化库 nth-check、版本区间库 semver、Markdown 解析器 marked 各有独立编号），把编号张冠李戴会让整篇报告的结论失去可信度。

```js
// 自查依赖的已知 ReDoS 通告：用 npm audit 输出 JSON 后过滤
// npm audit --json | node -e "..."（下例示意过滤逻辑）
// 命令行示例：npm audit --json > audit.json
// 随后用正则筛出 ReDoS 相关的 advisories 标题
const auditTitles = ["Regular Expression Denial of Service in lodash"];
console.log(auditTitles.filter((title) => /regular expression denial of service/i.test(title)).length);
// 1
```



#### 防御工具链

- **静态检测**：safe-regex、eslint-plugin-redos、eslint-plugin-security 的 detect-unsafe-regex 规则、GitHub CodeQL 的 ReDoS 查询，都能在合并前拦下可疑模式。
- **动态检测**：vuln-regex-detector 这类工具会为给定模式自动生成攻击串并实测耗时曲线。
- **非回溯引擎**：Google RE2 及其各语言绑定、Rust 的 regex crate，从设计上保证线性耗时。
- **运行时兜底**：输入长度上限、把高风险匹配放进独立进程或工作线程。

> [!IMPORTANT]
> **重要内容**：工具只是**筛子而不是判决书**——静态检测普遍存在误报，safe-regex 对“(a+)+”以外的复杂歧义识别率有限。工具报出的每一条都要人工复看一眼，工具漏报的模式也要靠本篇的识别清单兜底。



### 测试方法论

#### 正则的测试矩阵

**单个样本的通过证明不了模式正确**：正则的错误大多藏在“长得像但不该匹配”与“长得不像但该匹配”的样本里，成体系的测试矩阵才是可靠性的底线。

- **正样本**：至少一个应当匹配的典型输入。
- **负样本**：与正样本形似但不该匹配的输入（多一位、错一位、夹杂质）。
- **边界样本**：空串、单个字符、最大合法长度、最大长度加一。
- **回溯压力样本**：对含嵌套量词的模式，构造“够长且最终失败”的输入，确认不会卡死。

```js
// 一个最小测试矩阵的样子
const phoneReg = /^1[3-9]\d{9}$/;
const cases = [
  ["13812345678", true],   // 正样本
  ["12812345678", false],  // 负样本（第二位不合法）
  ["1381234567", false],   // 边界（少一位）
  ["138123456789", false], // 边界（多一位）
  ["", false],             // 边界（空串）
];

for (const [input, expected] of cases) {
  console.log(phoneReg.test(input) === expected); // 全部 true 才算通过
}
```

> [!IMPORTANT]
> **重要内容**：**替换类正则必须测最终输出**而不只是匹配列表——匹配完全正确、替换串里一个裸 $ 就能悄悄损坏数据。测试矩阵四类样本齐备、替换输出逐条核对，是从“能跑”到“可信”的分界线。



#### 测试矩阵的落地方式

**把测试矩阵写成表驱动函数**，才能在日常改动中真正被跑起来，而不是停留在一次性的手工验证。

- **表驱动**：把“输入 + 期望”写成数组，一次遍历断言全部通过。
- **双向验证**：校验类模式除了测“该通过的通过”，还要测“不该通过的确实被拦下”。
- **替换类单独验**：替换的期望值写最终字符串，不要写匹配片段。
- **回归留存**：每修一个线上问题，就把它对应的样本补进矩阵，防止再次退化。

```js
function assertAll(reg, cases) {
  const failures = [];
  for (const [input, expected] of cases) {
    const actual = reg.test(input);
    if (actual !== expected) failures.push({ input, expected, actual });
  }
  return failures.length === 0 ? "全部通过" : failures;
}

const idCases = [
  ["110101199003072316", true],
  ["110101199013072316", false], // 月份 13
  ["11010119900307231", false],  // 少一位
  ["", false],
];
console.log(assertAll(/^[1-9]\d{5}(?:18|19|20)\d{2}(?:0[1-9]|1[0-2])(?:0[1-9]|[12]\d|3[01])\d{3}[\dXx]$/, idCases));
// "全部通过"
```

```js
// 替换类：期望值写最终字符串
function assertReplace(text, reg, replacement, expected) {
  const actual = text.replace(reg, replacement);
  console.log(actual === expected, JSON.stringify(actual));
}

assertReplace("价格 128 元", /(\d+)/, "[$&]", "价格 [128] 元"); // true "价格 [128] 元"
assertReplace("a1b2", /\d/, "#", "a#b2");                       // true "a#b2"
```



### 本系列的阅读路线

#### 推荐学习顺序

- **入门**：第 1 篇《正则表达式简介》建立对象观与方法主体概念。
- **语法主体**：第 2 至 6 篇按 修饰符 → 字符类与转义 → 量词 → 分组 → 断言 的顺序推进，每篇末尾的排查清单随学随用。
- **应用层**：第 7 篇《正则方法与字符串方法》是日常写代码的高频参照。
- **专项**：第 8 篇《Unicode 与中文处理》按需查阅，处理姓名、地址、emoji 时必读。
- **进阶**：第 9 篇《性能与安全》与第 10 篇《实战案例集》构成“理论防御 + 实战范式”的收束，写生产代码前通读一遍。
- **工具**：第 11 篇（本篇）的测试矩阵方法论适用于全系列任何一篇的练习。

> 学习检验的标准：能独立写出手机号、身份证、日期三类校验并说明每一截的含义；能解释 lastIndex 陷阱与至少一条 ReDoS 事故的成因；能对一个陌生正则拆解出分组、量词与断言的作用范围。



#### 本系列的定位与边界

**本系列讲的是“正则本身”**，而不是“用正则解决一切”。明确边界能避免把工具用错地方。

- **覆盖范围**：JavaScript 引擎下的语法、方法、Unicode 处理、性能与安全，以及面向国内业务的实战模式。
- **不覆盖的内容**：其它语言的方言差异（PCRE、Python、Go 的具体细节只在与 JavaScript 对照时提及）；不用正则也能更好解决的问题，会明确建议改用内置 API 或专用解析器。
- **明确反对的用法**：用正则解析 HTML、JSON、代码这类嵌套结构；用正则做数值范围判断；把未转义的用户输入拼进模式。
- **换语言的注意点**：迁移到 Python 或 PCRE 时重点核对三处——后行断言是否允许变长、正则字面量语法差异（Python 用原始字符串）、以及替换串的引用记号不同（Python 用反斜杠序号而非美元符号）。
