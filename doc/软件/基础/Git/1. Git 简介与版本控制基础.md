## Git 简介与版本控制基础

### 什么是版本控制

#### 版本控制的定义

**版本控制**（Version Control）：是一种**记录一个或若干文件的内容变化，以便将来查阅特定版本修订情况**的系统。它为文件的每一次修改保存快照与历史，使项目既能随时回溯到过去任意状态，也能在多人之间安全地并行协作。

- **记录快照与历史**：每次提交都会保存项目在那一刻的完整快照，并附带作者、时间与说明信息。
- **支持回溯**：任何一次提交都可以随时恢复，误删、改错都能回到过去。
- **支持协作**：多人各自的修改可以被追踪、比较与合并，不再互相覆盖。
- **适用范围**：版本控制的对象是任意文件，实践中以源代码等纯文本文件效果最佳。

> 版本控制不限于代码：文档、配置文件、图书章节同样适用。Git 把源代码等文本文件当作一等公民，可以逐行比较差异；二进制文件也可纳入版本控制，只是无法逐行比对。



#### 为什么需要版本控制

没有版本控制时，最常见的做法是**手动备份**：复制整个目录、在文件名上加日期或最终版、最最终版等后缀。这种方式看似直观，问题却成倍增长。

- **命名混乱**：目录名与文件名被迫承担版本信息，时间一久无法分辨谁新谁旧、改了什么。
- **无法回溯细节**：想知道两个月前某段代码长什么样，只能靠碰运气找到对应副本。
- **无法协作**：多人同时修改同一目录，只能靠互相拷贝合并，覆盖与丢失几乎不可避免。
- **无法定位问题**：不能方便地比较两次修改之间的差异，引入缺陷的那一次改动难以锁定。

**版本控制系统**针对以上痛点提供系统化方案：历史自动编号、差异一目了然、修改可以合并、任何状态都能恢复。对照来看，手动备份的每一次复制都要人工完成，而版本控制系统把备份、对比、合并、恢复全部自动化并保证一致性。

> 需要区分**手动备份**与**版本控制**的本质差异：前者只保存结果副本，后者保存的是带因果关系的修订历史——不仅知道文件变成了什么，还知道谁在何时因为什么而改。



### 版本控制系统的三个发展阶段

版本控制系统的发展经历了**本地版本控制系统**、**集中式版本控制系统**与**分布式版本控制系统**三个阶段，每一代都在解决上一代的协作瓶颈。

#### 本地版本控制系统

**本地版本控制系统**（Local VCS）：把版本数据保存在**单台计算机的本地磁盘**上，靠一套脚本或工具记录文件的补丁与历史，代表工具是 **RCS**。它保存文件在不同时刻的差异，需要时把补丁按顺序叠加即可还原任意版本。

- 解决了手动备份的命名混乱，历史可查询、可恢复。
- 全部数据都在一台机器上，磁盘损坏即历史尽失。
- 天然无法支持多人协作，是它最大的短板。



#### 集中式版本控制系统

**集中式版本控制系统**（Centralized VCS）：用一个**单一的中央服务器**保存所有文件的修订版本，协作者通过客户端连接服务器，把文件检出到本地，代表工具是 **CVS** 与 **SVN**。

- 解决了多人协作问题：所有人都能看到他人的修改进度，管理员可以精细控制权限。
- 缺点一：中央服务器是**单点故障**——服务器宕机期间，谁都无法提交与协作。
- 缺点二：本地只有单个文件的检出副本，服务器磁盘损坏且无备份时，全部历史丢失。



#### 分布式版本控制系统

**分布式版本控制系统**（Distributed VCS）：客户端**不只提取最新版本的文件快照，而是把整个代码仓库完整地镜像下来**，代表工具是 **Git** 与 **Mercurial**。

- 每个开发者的本地仓库都是**完整副本**，包含全部历史，服务器故障后可用任意一份本地镜像恢复。
- 提交、查看历史、对比差异等绝大多数操作在本地完成，速度快且可离线工作。
- 天然支持多个远程仓库，同一项目可以按不同方式组织协作流程。

> **集中式**与**分布式**的核心差异一句话概括：前者只有服务器持有完整历史，客户端按需取用；后者每个客户端都持有完整历史，服务器退化为主同步节点。单点故障问题因此被釜底抽薪。



### Git 的诞生历史

Git 诞生于 2005 年，由 Linux 内核的创造者 **Linus Torvalds** 亲自设计开发，起因是 Linux 内核社区与 BitKeeper 的授权关系破裂。

- **背景**：1991 年至 2002 年间，Linux 内核的修改以补丁与压缩包方式流转；2002 年起社区开始使用专用的分布式版本控制系统 BitKeeper。
- **导火索**：2005 年，BitKeeper 的开发方与内核社区的合作破裂，免费使用授权被收回，社区失去了这款工具。
- **回应**：Linus Torvalds 以数周时间亲自编写出 Git，同年发布首个版本，随后迅速普及。

Pro Git 列举的 Git 设计目标，决定了它此后二十年的竞争力：

1. **速度**：本地操作为主，性能远超同类工具。
2. **简单的设计**：概念模型清晰一致。
3. **对非线性开发的强力支持**：允许上千个并行开发的分支。
4. **完全分布式**：每份克隆都是完整仓库。
5. **有能力高效管理类似 Linux 内核这样的超大规模项目**：速度与数据量都要扛得住。

> 一款为救急而生、数周写成的工具，最终成为事实上的行业标准。Git 的诞生再次说明：好设计来自对真实痛点的精准回应。



### Git 与其他版本控制系统的区别

Git 与 **SVN**、**CVS** 等集中式工具的区别不止于分布式架构，还有四项设计层面的根本差异。

#### 直接记录快照而非差异

主流集中式系统（如 **SVN**）采用**基于差异**（delta-based）的存储模型：记录基本文件，再记录每个版本相对前一版的增量。Git 采用**快照流**模型：把数据看作对小型文件系统的一组快照，每次提交时对当时的全部文件制作快照并保存索引；文件没有修改时不重新存储，只保留一个指向前一版快照的链接。

- **SVN 的差异模型**：按版本逐个累积增量，比较与回溯需要沿着差异链推算。
- **Git 的快照模型**：每次提交都是完整状态的存档，回看历史即直接取快照，分支与合并的实现也由此变得轻量。

> 快照模型是理解 Git 后续一切特性的基石：分支只是指向某个快照的可移动指针，创建分支因此几乎零成本。



#### 几乎所有操作都在本地执行

Git 的绝大多数操作只需要**访问本地文件与资源**，不需要联网，这是快照模型带来的直接红利。

- 浏览项目历史、对比两次提交，全部读取本地数据库，无需向服务器查询。
- 断网状态下可以正常提交、开分支、查历史，联网后再同步。
- 本地磁盘读取远快于网络往返，操作延迟几乎为零。

> 由此带来的体验差异很直观：集中式系统里查看历史要等网络响应，Git 里同样的操作是瞬间完成的。



#### Git 保证完整性

Git 中的一切数据在存储前都会先计算**校验和**，之后以校验和而非原始文件名来引用数据。校验算法以 **SHA-1** 为主，计算结果是一个 40 位十六进制字符串，相当于文件内容的指纹。

- 数据入库前先算校验和，任何传输或存储损坏都会被发现，Git 因此能感知文件是否被改动。
- 整个 Git 数据库实际由校验和索引构成，不存在数据被悄然篡改而不被察觉的可能。
- 较新版本的 Git 已逐步支持 SHA-256，机制相同、指纹更长。



#### 一般只添加数据

Git 的操作**大多只添加数据**：提交快照、追加历史，几乎不会执行让数据不可逆消失的操作。一旦提交快照，就很难彻底丢失，尤其是定期推送之后。

- 可以任意回到历史某个状态，再回到最新，数据始终都在。
- 三种工作状态（详见第 3 章）保证了内容真正提交前有多次检查的机会。



### Git 的三个区域概览

Git 的日常操作围绕**三个区域**展开：**工作区**（working tree，本地直接编辑的目录）、**暂存区**（staging area 或 index，存放下次提交内容的清单）与**版本库**（repository，即 .git 目录，保存全部历史）。

- 数据流向固定：工作区的修改经 git add 进入暂存区，暂存区的内容经 git commit 进入版本库。
- 这条流水线把修改、挑选、存档拆成两步，让每次提交可以只包含一个完整意图。

> 本节仅作预告，三个区域的完整定义、文件状态流转与逐条命令演示，见第 3 章 三个区域与基本工作流程。



### Git 的学习路线

学习 Git 应遵循由基础操作到内部原理的路径，各阶段环环相扣。

1. **基础操作**：安装与配置、三个区域、文件的暂存与提交、状态检查——这是地基，决定日常提交是否规范。
2. **分支与合并**：创建分支、合并、处理冲突——这是 Git 的灵魂，非线性开发的全部威力在此。
3. **远程协作**：克隆、推送、拉取、与他人的提交协同——这是团队开发的主战场。
4. **内部原理与高级技巧**：对象模型、引用重置、变基、拣选等——这是进阶，决定遇到疑难时能否从容自救。

> [!WARNING]
> **警告内容**：初学者最容易犯的错误是**把 Git 当作只会上传下载的黑盒使用**：不建立提交粒度与分支意识，任何改动都堆成一次巨大提交、所有开发都挤在一条分支上，一旦出错便束手无策。正确姿势是把每次提交当作一个可独立回溯的存档点，把分支当作并行的安全试验场。
