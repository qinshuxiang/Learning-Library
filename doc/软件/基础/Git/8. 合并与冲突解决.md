## 合并与冲突解决

### 合并的本质

#### 合并提交与三方合并

**合并**：是**把两个分支的历史汇合在一起的操作**；汇合的产物是一个同时拥有两个父提交的特殊提交，称为**合并提交**。

- **合并提交**：Git 中唯一拥有两个父提交的提交，两个父提交分别指向合并发起方的末端提交与被合并方的末端提交。
- **三方合并**：Git 在历史分叉时自动采用的合并算法，以两个分支的**最近共同祖先**作为基准，对比两侧各自的差异再行整合。
- **三方的构成**：一方是最近共同祖先提交，另外两方分别是当前分支与目标分支的末端提交。
- **自动整合的依据**：相对基准，哪一方改动了就采用哪一方的内容，双方都没动的保持原样。

> 之所以叫三方，是因为参与对比的提交有三个：共同祖先、本分支末端、对方分支末端。只对比两个末端是不够的——没有基准，就无法判断某处改动出自哪一方、该不该保留。



### 快进合并与三方合并的对比

#### 两种合并的发生条件

**快进** 对 **三方合并**：两者的分界线是历史有没有分叉，即两个分支自共同祖先之后是否各自产生了新提交。

- **发生快进的条件**：当前分支自分叉点之后没有新提交，被合并分支是当前分支的直接后代；合并只是指针前移，不产生提交（指针示意见第 7 章）。
- **产生合并提交的条件**：双方各有新提交，历史分叉，Git 走三方合并并创建合并提交。
- **--no-ff 选项**：强制在可以快进的场合也生成合并提交。

--no-ff 的意义在于**保留功能分支的存在痕迹**：快进后的直线历史看不出功能曾经单独开发过，而合并提交像一枚书签，明确记录某个功能分支在此汇入。

> [!TIP]
> **建议内容**：团队若希望从历史中看清每一次功能分支的汇入点，可约定合并时统一使用 merge --no-ff；若追求干净的直线历史，保持默认的快进即可。



### 冲突的成因

#### 冲突何时发生

**冲突**：是**两个分支修改了同一文件的同一区域、Git 无法自动决定取舍**的状态。自动合并只对改动位置互不相邻的情形有效。

- **能自动合并**：双方改了不同的文件；或改了同一文件中互不相邻的区域（改动之间隔着未改动的行）。
- **触发冲突**：双方改动了同一文件中相邻的行乃至同一行，Git 判断不出以谁的版本为准。
- **修改删除冲突**：一方修改而另一方删除了同一文件，保留还是删除无法自动决定，同样需要人工裁决。

> 冲突不是错误，而是 Git 的诚实：它把无法自动判断的决定交还给人，绝不擅自替开发者选择任何一方的改动。



### 冲突的解决流程

#### 冲突解决五步

冲突解决有一套固定流程，按顺序执行即可：

1. **定位冲突文件**：执行 git status，所有显示为 both modified 的文件即为冲突文件。
2. **认识冲突标记**：打开冲突文件，Git 已在冲突区域写入标记，把双方的版本并排呈现。
3. **手工取舍或融合**：在标记区内决定保留哪一方，或把两方内容融合改写。
4. **标记已解决**：对处理完的文件执行 git add 文件名，Git 据此认定冲突已解决。
5. **完成合并**：全部文件解决完毕后执行 git commit，生成合并提交。

冲突标记的原文形态：

```text
<<<<<<< HEAD
当前分支上的内容
=======
被合并分支上的内容
>>>>>>> dev
```

- **小于号区**：小于号一行到等号一行之间，是 HEAD 所在的当前分支的内容。
- **等号分隔**：连续的等号一行是双方内容的分界线。
- **大于号区**：等号一行到大于号一行之间，是被合并进来的分支的内容，末行的大于号之后标注来源分支。

> [!WARNING]
> **警告内容**：提交前必须确认文件中不再残留任何冲突标记：小于号、等号、大于号三行只是给合并流程看的记号，原样提交会直接破坏代码，生成合并提交前应逐个文件检查。

**放弃合并**：执行 git merge --abort 可在任何阶段放弃本次合并，工作区回到合并开始之前的状态，适合冲突过于棘手、需要另寻时机处理的场合。



### 合并工具与策略

#### mergetool 与合并策略选项

Git 允许借助外部工具与策略选项控制合并行为，日常使用频率不高，作了解即可。

- **git mergetool**：调用配置好的图形化合并工具（如 vimdiff、VS Code 内置合并界面），逐个文件引导解决冲突，本质仍是手工取舍，只是把对比与编辑集中到一个界面。
- **ours 策略**：整棵树完全采用当前分支的版本，忽略对方的全部改动，适合丢弃某条分支的实验性内容。
- **theirs 策略**：与 ours 相对，整棵树完全采用对方的版本；二者都用于整体站队，而非逐行取舍。
- **octopus 策略**：一次合并两个以上分支时使用的默认策略，多个分支的末端共同汇入一个合并提交；分支越多，冲突越难理清。

> [!NOTE]
> **提醒内容**：ours 有两种写法且语义不同：merge -s ours 是策略，完全无视对方分支的内容；merge -X ours 是普通三方合并加偏向，只在冲突行上偏向自己一方。按整树取舍用 s、逐行偏向用 X 记忆。



### 减少冲突的工程实践

#### 降低冲突频率的三个习惯

冲突无法根除，但可以靠协作习惯把频率压到很低，三条实践彼此配合：

- **小步快提交**：提交粒度小、频率高，每次合并携带的改动量就小，与他人改动重叠的概率随之降低。
- **分支存活期短**：功能分支尽快合并回主干，分叉越浅，冲突越少（切分时机见第 7 章）。
- **分工避免同文件并行改动**：任务划分时尽量让不同的人负责不同的文件或模块，从源头消除同区域竞争。

> 冲突的解决成本与分支的分叉程度成正比：分叉越久、越深，代价越高。三条习惯共同指向同一件事——让分叉尽可能小。
