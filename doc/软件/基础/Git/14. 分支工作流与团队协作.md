## 分支工作流与团队协作

### 工作流的定义

#### 什么是分支工作流

**分支工作流（workflow）**：团队围绕 Git 分支达成的一套约定，规定分支怎么开、怎么合、何时发布、由谁审核，目的是让多人协作时历史清晰、主干可用。

- Git 本身只提供分支与合并的能力，不强制任何工作流；**工作流是约定，不是命令**——同一套命令可以套用完全不同的协作模式。
- 工作流的选择取决于团队规模、发布节奏与产品形态：小团队与按版本发布的产品，适合的工作流并不相同。
- 评估一个工作流的三条底线：主干是否随时可用、合并冲突是否可控、发布与回滚是否方便。

> 辨析：工作流没有绝对的优劣，只有是否匹配团队之分。盲目照搬大型开源项目的流程，常会把小团队拖进无谓的流程成本。



### 集中式工作流

#### 集中式工作流的形态与适用

**集中式工作流**：全员只在一个主干分支上开发，人人向它推送，是最接近 Subversion 使用习惯的 Git 工作流。

- 每个人先克隆仓库，在本地提交，再直接向主干分支拉取与推送。
- 推送被拒绝时，先拉取并合并主干上的新提交，解决冲突后再推。
- 适合人数少、改动小的团队：上手成本最低，不需要管理任何辅助分支。

> 辨析：集中式工作流最简单，也最容易冲突——所有人的改动都挤在一条历史上，任何人推送前都可能与他人的新提交相撞；团队规模一旦扩大，主干的可用性难以保证。



### 功能分支工作流

#### 功能分支工作流的形态与适用

**功能分支工作流**：每个新功能或修复都从主干拉出一个独立分支，开发完成后再合并回主干，主干始终保持可用状态。

- 分支命名通常带功能语义，如 feature 登录页、fix 侧栏错位，让历史一眼可读。
- 功能未完成时绝不污染主干；主干上的每个提交理论上都可以直接发布。
- 功能分支是代码评审的天然载体：评审者面对的是一个分支相对主干的全部差异，而不是散落的多个提交。

> 辨析：与集中式相比，功能分支把未完成的实验隔离在主干之外，代价是多一步合并与分支管理。它是多数团队协作的默认起点，也是拉取请求评审模式的基础。



### GitFlow 工作流

#### GitFlow 的两条长期分支

**GitFlow 工作流**：用两条长期分支加三类辅助分支组织开发的严格分支模型，适合按版本发布、发布周期明确的软件。

- **main（或 master）**：存放对外发布的正式历史，上面的每个提交都对应一个可发布的版本，以标签标记版本号。
- **develop**：集成分支，承载最新的开发成果；功能完成后先并入 develop，攒齐一轮改动再向 main 发起发布。

> 辨析：两条长期分支永不删除。develop 上的代码属于可能在下个版本发布的内容，main 上的代码一定已经发布；日常开发不直接碰 main，一切发布都经由 develop 汇入。



#### GitFlow 的三类辅助分支

三类辅助分支各有固定的起点、用途与归宿。

- **feature（功能分支）**：从 develop 拉出，开发单个功能，完成后并回 develop，随即删除；功能彼此独立、互不阻塞。
- **release（发布分支）**：从 develop 拉出，只做发布前的收尾工作（修复小缺陷、更新版本号与文档），完成后一边并入 main 打标签发布，一边并回 develop 同步修正。
- **hotfix（热修分支）**：从 main 拉出，紧急修复线上缺陷，完成后一边并入 main 打标签发布，一边并回 develop 保证修复不丢失。

> [!TIP]
> **建议内容**：记忆抓手是生灭时机：feature 生于 develop、归于 develop；release 与 hotfix 生于各自的版本线、双线并回，main 与 develop 各合一次。三类辅助分支用完即删，长期存在的只有 main 与 develop。



### GitHub Flow 与 GitLab Flow

#### GitHub Flow 与 GitLab Flow 的对比

**GitHub Flow** 与 **GitLab Flow**：两个围绕拉取请求运转的现代轻量工作流，前者只保留一支主干，后者在主干之外补充了环境或发布维度的分支。

- **GitHub Flow**：只有一支主干，任何改动都从主干拉出短命分支，完成后发起拉取请求，评审通过并合并即视为可以部署——部署即主干。
- **GitLab Flow**：在 GitHub Flow 的基础上增加环境分支（如 production、pre-production）或发布分支；代码合并进主干后，还要再合入对应环境分支才真正上线。
- **GitHub Flow** 适合持续部署的 Web 服务；**GitLab Flow** 适合需要区分代码已完成与已发布到某环境、或按版本交付的软件。

> 辨析：两者与 GitFlow 的差别在分支数量与发布哲学——GitFlow 用分支表达开发阶段，GitHub Flow 用一支主干加短命分支表达一切，GitLab Flow 介于两者之间，用少量分支表达环境与版本。



### 拉取请求与 fork 模式

#### 拉取请求的本质

**拉取请求（Pull Request，GitLab 中称为合并请求 Merge Request）**：请求把某个分支合并进目标分支的正式提议，同时承载围绕这批改动的评审讨论。

- 它不是 Git 的命令，而是托管平台（GitHub、GitLab 等）提供的协作功能：基于分支差异生成一个可评论、可审查、可逐条回应的页面。
- 评审者可以逐行评论、要求修改；作者推送新提交后，请求自动更新，全部通过后由维护者执行合并。
- 合并方式通常可选：普通合并提交、压缩为单个提交（squash）或变基式合并。



#### fork 与 clone 的对比

**clone** 与 **fork**：获得仓库副本的两种途径，差别在于副本落在谁的名下、是否具备推送权限。

- **clone**：把仓库复制到自己权限所及的本地磁盘；clone 的是自己或自己有写权限的仓库，推送目标就是原仓库。
- **fork**：在平台侧把他人仓库复制一份到自己账号名下，得到一个自己拥有推送权限的服务端副本；对原仓库的写权限仍归原维护者。
- 典型组合：向没有推送权限的开源仓库贡献代码，先 fork 再 clone 自己的 fork；团队内部仓库直接 clone 即可。



#### 开源协作的完整流程

无推送权限的贡献者，按固定次序向开源项目提交改动。

1. fork 目标仓库到自己账号。
2. clone 自己名下的 fork 到本地。
3. 从主干拉出一个描述用途的新分支。
4. 在分支上完成提交。
5. 把分支推送到自己的 fork。
6. 在平台上从该分支向原仓库发起 PR。
7. 按评审意见继续修改并推送，直到通过。
8. 由原仓库维护者执行合并，随后删除分支并同步 fork。

> 速记：**fork 拿权限、clone 落本地、分支装改动、推送回 fork、PR 通评审、维护者合并**。



### 提交评审与协作礼节

#### 评审与协作的基本礼节

评审能否顺畅，取决于提交与沟通的习惯，与工具无关。

- **小提交**：一次提交只做一件事，评审者才能逐条判断；一个巨型 PR 往往只能得到整体看上去还行的结论。
- **清晰的提交消息**：说清做了什么、为什么做，让今天的评审者与半年后的回溯者都能看懂。
- **及时同步主干**：分支开得越久越难合并，定期把主干合进自己的分支，把冲突化整为零。
- **对事不对人**：评审意见针对代码与行为，措辞友好；被评审者把意见当作改进线索而非个人评价。

> [!TIP]
> **建议内容**：发起 PR 前先自查一遍差异，写清改动动机与验证方式；评审时先认可合理的部分再提异议，争执不下的分歧转入线下沟通，避免把评审区变成争论区。
