## 数据类型：Hash

### Hash 的定义与适用场景

#### Hash 是键到字段值映射的复合类型

**Hash（哈希）**：是 Redis 的复合数据类型，在**一个键之下保存字段（field）到值（value）的映射表**，整体结构形如 key 指向一组 field 与 value 的键值对集合，相当于键名空间下再嵌套了一层小型字典。

- 一个 Hash 键内部可以包含任意多个 field，每个 field 对应一个字符串 value，形如 user:1001 这个键下挂 name、age、city 等字段。
- field 与 value 都只能是**字符串**，不支持嵌套结构，不能在某个 field 里再放一个 Hash 或 List。
- value 虽只能是字符串，但客户端可以在 field 中存序列化后的 JSON 表达半嵌套结构，代价是失去该 field 内部的细粒度更新能力。
- 对同一个 field 重复写入会**覆盖旧值**，Hash 是可变映射而非追加日志。
- 一个 Hash 的 field 数量理论上限为 2 的 64 次方减 1，实际受内存与业务设计约束。
- 在数据类型体系中，Hash 由对象系统中的哈希对象承载，底层编码见内部编码一节与第 13 章。

从命令族的视角看，Hash 的命令围绕四件事展开：写入（HSET、HSETNX）、读取（HGET、HMGET、HGETALL）、维护（HDEL、HLEN、HEXISTS）与遍历（HSCAN、HRANDFIELD），本章后续各节即按这一顺序展开。

> Hash 与 String 的层级差别：String 是 key 到 value 的**单层映射**，Hash 是 key 到 field 再到 value 的**两层映射**。多出来的 field 层，正是 Hash 能把一组相关数据装进一个键、并支持按属性单独读写的根本原因。字典底层的实现与渐进式 rehash 详见第 11 章。

```bash
# 一个 Hash 键的内部视图（示意）
# user:1001
# ├─ name -> "Alice"
# ├─ age  -> "26"
# └─ city -> "Hangzhou"
```

**速记**：Hash 就是**键下的迷你字典**，field 找 value。



#### Hash 适合存储对象的属性集合

**Hash 的典型场景**：把一个业务对象的多个属性集中存进一个键，field 对应属性名、value 对应属性值，是 Hash 最经典也最常见的用法。

- 存用户对象：键为 user:1001，field 为 name、age、city，value 为对应属性值。
- 存商品信息：键为 product:9001，field 为 title、price、stock，价格与库存各自独立更新。
- 部分读写：只改 age 一个 field 时不必读出整个对象，一条 HSET 即可，避免读改写全量。
- 按需取值：需要哪个属性就 HGET 哪个 field，天然支持按属性粒度的访问。
- 集中计数：对象的多个计数器字段（如 pv、like_count）可同处一个 Hash，各自 HINCRBY。

```bash
HSET user:1001 name Alice age 25 city Hangzhou

HGET user:1001 age
# 只取一个属性，返回 "25"

HSET user:1001 age 26
# 只改一个属性，其余 field 不受影响
```

> 场景辨析：对象属性需要**单独读写、单独更新**时用 Hash；对象总是**整体序列化后存取**（如把整个对象转成 JSON 字符串缓存）时用 String 更简单直接。判断标准是**访问粒度**，而不是数据本身是不是对象，二者的完整对比见后文专节。

**速记**：对象属性要**各改各的**，交给 Hash。



### 基础读写命令

#### HSET 写入字段与 HGET 读取字段

**HSET**：向 Hash 写入一个或多个 field-value 对，是 Hash 最核心的写命令，语法为 HSET key field value [field value ...]，时间复杂度 O(N)，N 为一次写入的 field 个数。

- 单字段写入：HSET user:1001 name Alice，返回 1 表示新建了 field，返回 0 表示 field 已存在、本次为覆盖。
- 多字段写入：HSET user:1001 name Alice age 25 city Hangzhou，一条命令写入多个 field 对，4.0 起支持。
- HGET key field：读取单个 field 的 value，field 不存在时返回 nil，时间复杂度 O(1)。
- 对不存在的 key 执行 HSET 会**先自动创建空 Hash 再写入**，无需预先初始化。
- 写入空字符串是合法操作：HSET user:1001 memo "" 存入空 value 后，HEXISTS 对 memo 仍返回 1。
- HGET 一次只接受一个 field，要一次取回多个 field 用 HMGET。

```bash
HSET user:1001 name Alice age 25 city Hangzhou
# 返回 (integer) 3，表示新建了 3 个 field

HSET user:1001 age 26
# 返回 (integer) 0，age 已存在，本次覆盖为 26

HGET user:1001 name
# 返回 "Alice"

HGET user:1001 email
# field 不存在，返回 (nil)

HSET user:1001 memo ""
# 写入空字符串是合法操作

HEXISTS user:1001 memo
# (integer) 1，field 存在，即使值为空串
```

> [!IMPORTANT]
> **重要内容**：自 Redis 4.0 起 HSET 支持多 field 写入，官方以 HSET 取代了多字段写命令 HMSET，HMSET 已被标记为弃用（deprecated），功能与新命令完全一致但不再推荐使用；新代码一律写 HSET，只有在维护历史系统时才会遇到 HMSET。

**速记**：HSET **多 field 一条写**，HGET **单 field 单取**。



#### HMGET 批量读取与 HGETALL 全量读取

**HMGET 与 HGETALL**：前者按给定的 field 列表**点名批量取值**，后者**一次性取回整个 Hash 的全部 field 与 value**，二者覆盖了从部分到全量的读取需求。

- HMGET user:1001 name age：按传入顺序返回 value 列表，返回顺序与请求顺序一致。
- HMGET 的参数中不存在的 field 以 nil 占位返回，不报错、也不会挤掉其他结果的位置。
- HMGET 请求多少个 field，返回列表长度就是多少，缺失项以 nil 补位，客户端严格按位置对应。
- HGETALL user:1001：返回结果按 field1、value1、field2、value2 的顺序交替排列，客户端再按奇偶位解析。
- 结果体积：HGETALL 的返回大小等于整个 Hash 的数据量，与 field 总数成正比，时间复杂度 O(N)。
- 客户端库通常会把 HGETALL 的交替列表折叠成对象返回，Node 的 ioredis 即直接返回对象形式，调用方式详见第 30 章。

```bash
HMGET user:1001 name age email
# 按顺序返回，不存在的 field 以 nil 占位：
# 1) "Alice"
# 2) "26"
# 3) (nil)

HMGET cart:1001 p9001 p9002 p9003
# 1) "2"
# 2) "1"
# 3) (nil)，缺失项以 nil 补位

HGETALL user:1001
# field 与 value 交替返回：
# 1) "name"
# 2) "Alice"
# 3) "age"
# 4) "26"
# 5) "city"
# 6) "Hangzhou"
```

读取命令的选择顺序建议是：先点名、后全量——先想清楚业务需要哪些 field，能用 HMGET 点名解决就不要整键拉取。

> HGETALL 在小 Hash 上简洁高效，是存对象场景的首选读取方式；但在大 Hash 上会一次性构建完整响应并长时间占用主线程，属于典型阻塞源，生产环境对大小未知的 Hash 应改用 HSCAN 渐进遍历，风险分析与慢查询治理详见第 29 章。

**速记**：HMGET **点名取值**，HGETALL **连锅端**。



#### HEXISTS、HDEL 与 HLEN

**HEXISTS、HDEL 与 HLEN**：分别负责判断 field 存在性、删除 field、统计 field 数量，是维护 Hash 内容的三个基础命令。

- HEXISTS user:1001 name：field 存在返回 1，不存在返回 0，注意它判断的是 field 而不是 key。
- HDEL user:1001 age city：删除一个或多个 field，可一次传多个，时间复杂度 O(N)，N 为要删的 field 个数。
- HDEL 删除不存在的 field 不报错，返回值是实际删除成功的 field 个数。
- HLEN user:1001：返回 field 总数，时间复杂度 O(1)，直接读元数据计数，不遍历内容。
- HLEN 之所以 O(1)，是因为 hashtable 编码在元数据中维护了元素计数；listpack 虽要顺序清点，但规模小到可忽略。
- 一个 key 下的最后一个 field 被 HDEL 之后，整个 key 自动删除，Hash 不会留下空壳。

```bash
HEXISTS user:1001 name
# (integer) 1，field 存在

HEXISTS user:1001 email
# (integer) 0，field 不存在

HDEL user:1001 city
# (integer) 1，删除成功

HDEL user:1001 not_exist_field
# (integer) 0，删除了 0 个 field

HLEN user:1001
# (integer) 2，剩余 name 与 age 两个 field
```

> 一字之差辨析：EXISTS 判断的是**某个 key 是否存在**，HEXISTS 判断的是**某个 key 下某个 field 是否存在**。判断整个 Hash 还在不在用 EXISTS，判断某个属性有没有存值用 HEXISTS，混用会得到错误的业务判断。

**速记**：EXISTS 管 **key**，HEXISTS 管 **field**，HLEN **数 field 不遍历**。



#### HKEYS 与 HVALS

**HKEYS 与 HVALS**：分别返回 Hash 的**全部 field 名**与**全部 value**，可以看作 HGETALL 的两个单向变体，时间复杂度均为 O(N)。

- HKEYS user:1001：只返回 field 名列表，例如 name、age、city。
- HVALS user:1001：只返回 value 列表，例如 Alice、26、Hangzhou。
- 只需要某一侧数据时，HKEYS 或 HVALS 比 HGETALL 少传一半内容，节省网络带宽。
- key 不存在或 Hash 为空时返回空列表，不报错。
- 返回顺序不保证与写入顺序一致，客户端不应依赖 HKEYS、HVALS 的排列次序做业务判断。
- 三者（HGETALL、HKEYS、HVALS）在大 Hash 上具有相同的阻塞风险，属于同一族的“全量拉取”命令。

```bash
HKEYS user:1001
# 1) "name"
# 2) "age"
# 3) "city"

HVALS user:1001
# 1) "Alice"
# 2) "26"
# 3) "Hangzhou"
```

> HKEYS 与 HVALS 丢失了 field 与 value 的配对关系：只要名或只要值时才用它们；如果名值配对在业务上有意义（比如 id 到名称的映射），必须用 HGETALL 或 HSCAN，否则解析端无法再把名与值对回去。

**速记**：HKEYS 拿**名**，HVALS 拿**值**，要配对用 **HGETALL**。



#### HSETNX 不存在才写入

**HSETNX**：仅当 field 不存在时才写入 value，是 HSET 的条件写入版本，语义为 field 级别的 SET if Not eXists，语法为 HSETNX key field value。

- HSETNX user:1001 name Bob：name 已存在则什么都不做并返回 0；不存在则写入并返回 1。
- 只支持**单 field** 写入，没有多 field 的 HSETNX 版本。
- 典型用途：初始化默认值，例如首次创建记录时写入 created_at，后续访问不会覆盖原始值。
- 判断与写入在服务端**一条命令内原子完成**，并发调用不会出现先检查后写入的竞态窗口。
- 与 String 的 SETNX 对照：SETNX 的原子性作用在 key 级别，HSETNX 作用在 field 级别，作用域差一层。

```bash
HSET user:1001 name Alice

HSETNX user:1001 name Bob
# (integer) 0，name 已存在，写入失败，值仍是 Alice

HSETNX user:1001 created_at 1736000000
# (integer) 1，field 原先不存在，写入成功

HSETNX user:1001 created_at 1736000001
# (integer) 0，field 已存在，写入被拒绝
```

> HSETNX 的原子性来自 Redis 单线程命令执行模型，多个客户端同时抢写同一个 field 时只有一个成功，其余全部返回 0；但分布式锁的实现应使用 String 的 SET NX PX 方案（详见第 27 章），HSETNX 不提供过期时间与持有者标识，不适合直接拿来当锁。

**速记**：HSETNX **占坑不抢坑**，抢不到返回 0。



### 计数与随机族命令

#### HINCRBY 与 HINCRBYFLOAT 字段级原子自增

**HINCRBY**：对 Hash 中指定 field 的整数值做**原子加法**，语法为 HINCRBY key field increment，是 String 的 INCRBY 在 field 级别的对应命令，时间复杂度 O(1)。

- field 不存在时先按 0 处理再执行加法，即首次执行 HINCRBY key counter 1 的结果是 1。
- 增量 increment 可为**负数**，负增量即减法；没有 HDECRBY 命令，自减一律靠负数增量表达。
- field 现值或减完结果若不是 64 位有符号整数范围内的数字，命令报错；对内容为非数字的 field 自增同样报错。
- HINCRBYFLOAT key field increment：支持浮点增量，按双精度计算；返回计算后的字符串值。
- 返回值是自增后的**新值**，不是增量前的旧值，需要旧值时应先 HGET（接受竞态）或改用 Lua 脚本（详见第 23 章）。
- 加法在服务端单线程内完成，天然免除客户端“读出、加一、写回”三步的并发竞态。

```bash
HSET product:9001 like_count 10

HINCRBY product:9001 like_count 1
# (integer) 11

HINCRBY product:9001 like_count -3
# (integer) 8

HINCRBYFLOAT product:9001 rating 0.5
# "8.5"

HINCRBYFLOAT product:9001 rating -1.25
# "7.25"

HSET stats:1001 pv 0 uv 0 like_count 0

HINCRBY stats:1001 pv 1
# (integer) 1
```

HINCRBY 的错误处理值得单独记：若 field 现值不是整数（例如被 HSET 写成了文字），命令直接报错而非强制转换，计数 field 应只由 HINCRBY 与数字 HSET 写入，杜绝脏值混入。

> 场景对应：购物车中某商品数量加一、文章点赞数累加、用户登录次数统计，都是 field 级自增的典型场景——一个 Hash 键承载同一实体的多个计数器，比每个计数器单独建 String 键**省键数量**、便于一次 HGETALL 总览全部指标。

> [!TIP]
> **建议内容**：把同一实体的多个统计指标放进一个 Hash，如键为 stats:1001 下挂 pv、uv、like_count 三个 field，用 HINCRBY 分别累加，看板刷新时一条 HGETALL 即可取回全部指标；组织计数器时优先考虑这种“一实体一键”的聚合方式。

**速记**：HINCRBY **原子加**，减法用**负增量**，浮点找 **HINCRBYFLOAT**。



#### HRANDFIELD 随机获取字段

**HRANDFIELD**：Redis 6.2 新增命令，从 Hash 中**随机返回 field**，可通过 count 参数控制数量、WITHVALUES 选项附带值，是随机抽样场景的专用命令，语法为 HRANDFIELD key [count [WITHVALUES]]。

- HRANDFIELD user:1001：不带 count，随机返回 1 个 field 名。
- HRANDFIELD user:1001 3：count 为**正数**时做不重复抽样，最多返回 3 个不重复的 field。
- HRANDFIELD user:1001 -3：count 为**负数**时做可重复抽样，必定返回恰好 3 个结果，可能含重复项。
- HRANDFIELD user:1001 3 WITHVALUES：field 与 value 成对交替返回，抽奖公布中奖者名字时常用。
- 常见用途：从参与用户 Hash 中抽中奖者、从候选池 Hash 中随机推荐若干条目。
- HRANDFIELD 只随机读、不改动内容，与 Set 的 SPOP 弹出即移除语义不同，抽样后候选池保持不变（Set 详见第 6 章）。

```bash
HSET lottery:2026 u1001 Alice u1002 Bob u1003 Carol u1004 Dave

HRANDFIELD lottery:2026
# 随机一个 field，例如 "u1003"

HRANDFIELD lottery:2026 2 WITHVALUES
# 随机两个不重复的 field-value 对：
# 1) "u1002"
# 2) "Bob"
# 3) "u1004"
# 4) "Dave"

HRANDFIELD lottery:2026 -5 WITHVALUES
# 返回恰好 5 个结果，field 可能重复

HRANDFIELD lottery:2026 10
# count 为正且大于 field 总数，返回全部 4 个 field，不报错
```

> 细节辨析：count 为正且大于 field 总数时，返回全部 field 而不报错，结果数可能少于请求值；count 为负则永远返回绝对值个结果。key 不存在或 Hash 为空时，正数 count 返回空列表，负数 count 返回 nil。正负号决定“可否重复”，是本命令最常考的差异点。

**速记**：正数**去重**、负数**可重**，WITHVALUES **带值返回**。



### 渐进遍历与 field 级过期

#### HSCAN 渐进遍历大哈希

**HSCAN**：以**游标（cursor）方式分批遍历** Hash 的 field-value 对，语法为 HSCAN key cursor [MATCH pattern] [COUNT count] [NOVALUES]，是全量拉取命令在大 Hash 场景下的替代方案。

- 游标从 0 开始，每次调用返回一个新游标和一批元素；新游标再次为 0 表示整趟遍历结束。
- MATCH pattern：按通配符过滤 field，例如 MATCH user:* 只返回以 user 开头的 field。
- COUNT count：向服务端建议每批扫描的元素数量，只是提示而非保证，实际返回量可能多于或少于该值。
- NOVALUES：7.4 起支持，只返回 field 不返回 value，省一半传输量。
- 单次调用复杂度约为 O(COUNT)，整趟遍历分摊后为 O(N)，代价被**摊到多次调用**而非一次性支付。
- HSCAN 只遍历单个 Hash 内部的 field，游标语义与遍历数据库键空间的 SCAN 一致，渐进思想相同。
- 遍历期间对同一 Hash 的增删改可能反映、也可能不反映在结果中，HSCAN 不提供快照语义，业务需容忍这一弱保证。

```bash
HSCAN user:1001 0 COUNT 10
# 第一行是新游标，第二部分是本批元素：
# 1) "0"
# 2) 1) "name"
#    2) "Alice"
#    3) "age"
#    4) "26"

HSCAN user:1001 0 MATCH name* COUNT 5
# 只返回以 name 开头的 field 及其 value
```

> [!WARNING]
> **警告内容**：对 field 数量达十万级以上的大 Hash 执行 HGETALL、HKEYS、HVALS 会一次性构建完整响应并长时间阻塞单线程，期间所有其他请求排队等待，是线上慢查询的常见来源。生产代码对大小未知的 Hash 一律改用 HSCAN 分批遍历，客户端以“返回游标不为 0 就继续下一批”的循环封装，阻塞定位与慢查询治理详见第 29 章。

```text
# 客户端封装的遍历循环（伪代码）
cursor = 0
repeat
    cursor, batch = HSCAN key cursor COUNT 100
    handle batch
until cursor == 0
```

**速记**：大 Hash 用 **HSCAN**，游标**不为 0 就再来一批**。



#### HGETDEL、HGETEX 与 HEXPIRE 字段级过期

**field 级 TTL 命令族**：Redis 7.4 起为 Hash 引入对**单个 field** 取值即删、取值续期与单独设过期能力，把过期控制的粒度从 key 下沉到了 field。

- HGETDEL key field [field ...]：取回 value 的**同时删除**该 field，原子完成，7.4 新增。
- HGETEX key field EX 60：取值的同时为 field 设置或刷新过期时间，EX、PX、EXAT、PERSIST 等选项语义与 String 的 GETEX 一致。
- HEXPIRE key seconds FIELDS numfields field ...：为指定 field 设置相对秒数过期，到期后 field 被删除而 key 仍在；必须带 FIELDS 声明 field 个数。
- 配套家族：HPEXPIRE（毫秒）、HEXPIREAT（绝对时间戳）、HTTL（查询 field 剩余存活时间）、HPERSIST（移除 field 的过期时间）。
- 适用场景：会话内的单个令牌限时有效、验证码字段独立过期、订单 Hash 中某个待支付子项单独倒计时。
- field 过期同样走惰性检查加周期清理的思路，与 key 级过期的删除策略同源（详见第 14 章）。

```bash
HEXPIRE session:1001 3600 FIELDS 1 token
# 1) (integer) 1，表示过期时间设置成功

HTTL session:1001 FIELDS 1 token
# 1) (integer) 3599，剩余 3599 秒

HGETDEL session:1001 token
# 取出 token 的值，同时该 field 立即消失

HGETEX session:1001 token EX 60
# 取值的同时把 token 的过期时间重置为 60 秒
```

> 两个边界要点：field 过期后若 key 下已无任何 field，整个 key 才随之删除；field 级 TTL 与 key 级 EXPIRE（详见第 14 章）相互独立，key 先到期会连全部 field 一起删除。这些命令是 7.4 才引入的，旧版本服务端会直接报未知命令错误，上线前先确认版本。

**速记**：HGETDEL **取了就删**，HGETEX **取了续期**，HEXPIRE **给 field 单独定时**。



### 内部编码与内存布局

#### listpack 与 hashtable 的转换

**Hash 的内部编码**：只有 **listpack（紧凑列表）与 hashtable（哈希表）** 两种，小 Hash 用 listpack 极省内存，大 Hash 用 hashtable 保证定位性能，二者按数据规模自动转换。

- listpack 编码：全部 field-value 依序紧凑存放于**一块连续内存**，没有指针开销，CPU 缓存命中率高，小规模下查询反而更快。
- hashtable 编码：标准字典结构，任意 field 定位 O(1)，代价是大量指针与桶数组的元数据开销，字典实现与渐进式 rehash 详见第 11 章。
- 转换条件由两个配置共同决定：hash-max-listpack-entries（默认 128，field 个数超过则转）与 hash-max-listpack-value（默认 64，**任意一个** value 长度超过则转）。
- 转换是**单向**的：一旦转为 hashtable，即使此后元素不断减少，也不会退回 listpack。
- 版本演进：Redis 7.0 起 listpack 全面取代 ziplist 作为小 Hash 的底层编码，旧文档中的 ziplist 即对应这里的 listpack，阅读历史资料时需做映射。
- listpack 中查找 field 需要顺序比较，field 数量是它能否胜任的第一道门槛，这正是 entries 阈值存在的原因。
- 查看方式：判断编码用 OBJECT ENCODING，估算单键内存占用用 MEMORY USAGE，两者配合可给大 Hash 体检。
- 编码名是只读的诊断信息，不存在手动切换编码的命令，转换永远由 Redis 依据阈值自动完成。

```bash
HSET small:hash f1 v1

OBJECT ENCODING small:hash
# "listpack"

# 当 field 个数超过 128，
# 或任何一个 value 长度超过 64 字节后：
OBJECT ENCODING small:hash
# "hashtable"

MEMORY USAGE small:hash
# (integer) 104，示意值，实际随内容浮动
```

> [!NOTE]
> **提醒内容**：listpack 的单 field 查询复杂度是 O(N)，但连续内存带来的缓存友好使它在小规模下实际快于 hashtable，128 与 64 这两个默认阈值是内存与性能折中的经验值；一般无需修改，确有调优诉求时应先实测再改，参数调优方法详见第 29 章。

**速记**：**小用 listpack 省内存，大用 hashtable 保速度**，转换**只升不降**。



### Hash 与 String 存对象的对比

#### Hash 对比 String 存 JSON 的取舍

**Hash 与 String 存对象的核心差异**：前者支持**属性级读写与 field 级控制**，后者实现简单且过期以**整个对象**为单位，选型依据是业务的访问模式而非数据形态。

- 部分读写：Hash 可 HGET 或 HSET 单个属性；String 存 JSON 必须整体反序列化、修改后再整体写回，并发写时还有**互相覆盖**的风险。
- 内存占用：属性值小且个数不多的对象，listpack 编码的 Hash 更省内存；对象很大或只作整体缓存时，String 存一份序列化结果开销更小。
- TTL 粒度：String 的 EXPIRE 作用于整个对象，语义简单直接；Hash 的 key 级 TTL 同样覆盖全部 field，field 级 TTL 需要 7.4 及以上版本。
- 序列化成本：String 需要客户端每轮做序列化与反序列化；Hash 的 field 直接对应属性，省去序列化环节。
- 读取模式：String 一次 GET 整体到手；Hash 按需 HMGET，传输量随业务所需伸缩。
- 结构演进：对象属性经常增删时，Hash 的 field 可灵活增减；String 的 JSON 结构一旦变更，还要处理新旧格式兼容。
- field 数量失控：把 Hash 当数据库表无限加 field，数量达到数十万时编码转 hashtable，内存暴涨且全量读取命令全部不可用。
- 二级索引需求：要按某个属性值检索对象时，两种方案都不够，需另建 Set 或 ZSet 辅助索引（详见第 6 章与第 7 章）。
- 混用组合：真实系统常二者并存——热属性与计数器放 Hash 逐项更新，大块渲染结果放 String 整体缓存。

```bash
# String 存对象：整体读写
SET user:1001:json '{"name":"Alice","age":26}'
GET user:1001:json
# 改一个属性也必须整体替换

# Hash 存对象：按属性读写
HGET user:1001 age
HSET user:1001 age 26
```

> 经验法则：需要按属性**单独读写、单独计数、单独设定有效期**的对象用 Hash；总是**整体读取、整体替换、整体过期**的对象（如页面渲染结果、接口响应缓存）用 String。判断顺序是先看访问粒度，再看过期粒度，最后才看内存。
> 内存视角的补充：listpack 编码的小 Hash 是最省内存的对象形态之一，海量小对象优先 Hash；超大对象整体缓存优先 String，避免转 hashtable 后指针开销反超内存优势。

**速记**：**零改整用 String，按属性动用 Hash**，field 数量别失控。



### 实战：购物车

#### 购物车的数据结构设计

**购物车的建模**：以 Hash 为核心，**键为 cart:userId，field 为商品 id，value 为商品数量**，一个用户对应一辆购物车、一个键。

- key：cart:1001，用户 id 写进键名，天然按用户隔离，也便于集群下按用户维度分片。
- field：商品 id（如 p9001），加购即写 field，清购物车中某商品即删 field。
- value：商品数量（整数），配合 HINCRBY 完成加减，无需客户端维护计数。
- 辅助结构：商品名称、价格等详情放在商品自身的 Hash 或 String 缓存里，购物车**只存 id 与数量**，结算时批量关联查询。
- 容量预期：单个用户购物车的 field 数通常在两位数以内，长期停留在 listpack 编码区间，内存极省。

```bash
HSET cart:1001 p9001 2 p9002 1

HGETALL cart:1001
# 1) "p9001"
# 2) "2"
# 3) "p9002"
# 4) "1"
```

> [!TIP]
> **建议内容**：购物车 Hash 扮演的是**商品 id 到数量的索引**，而不是完整商品库；展示商品名称、价格时应批量查询商品详情而非读购物车。把详情冗余进购物车，改价后数据即刻陈旧，以详情为准才能保证价格等敏感信息实时正确。

**速记**：**cart 加用户 id 为键，商品 id 为 field，数量为 value**。



#### 购物车核心操作实现

**购物车四类核心操作**：加购、改数量、移除、结算列举，每类都能用**一条 Hash 命令原子完成**，不需要客户端读改写。

- 加购与累加：HINCRBY cart:1001 p9001 1，商品已在车中则数量加一，不在则从 0 加到 1，一条命令同时覆盖两种情况。
- 直接改数量：HSET cart:1001 p9001 3 把数量设为指定值；HINCRBY cart:1001 p9001 -1 实现减一件。
- 移除商品：HDEL cart:1001 p9001，field 与数量一并消失。
- 判断空车：HLEN cart:1001 返回 0 即购物车为空。
- 结算列举：HGETALL cart:1001 取回全部商品 id 与数量；购物车 field 数通常很小，可以放心全量读取。
- 批量加购：HSET cart:1001 p9001 2 p9002 1，从详情页一次入车多件商品。
- 清空购物车：DEL cart:1001 整键删除，比逐个 HDEL 干净。

```bash
# 加购一件
HINCRBY cart:1001 p9001 1

# 再买两件
HINCRBY cart:1001 p9001 2

# 修改购买数量为 3
HSET cart:1001 p9001 3

# 移除商品
HDEL cart:1001 p9001

# 结算前取出全部明细
HGETALL cart:1001
# 1) "p9001"
# 2) "3"

HLEN cart:1001
# (integer) 0，field 全部删除后即空车
```

> 加购必须用 HINCRBY 而不是“HGET 读出数量、加一后 HSET 写回”：前者在服务端原子完成，同一用户多端并发加购不会丢计数；后者是典型的读改写竞态，多端同时加购会互相覆盖。Node 客户端的 ioredis 调用方式详见第 30 章。

**速记**：加购**一条 HINCRBY**，移除用 **HDEL**，结算 **HGETALL**。



### 常见误用与最佳实践

#### HGETALL 拉全量与超大表误用

**Hash 的两大典型误用**：对大 Hash 无节制地 HGETALL，以及把 Hash 当**超大表**无限扩容，两者都会演变为内存与阻塞问题，且事后治理成本高。

- 误用一：field 无上限增长。把全站商品、用户行为流水都塞进一个 Hash，field 达数百万级，单键内存巨大且集群下无法再分片。
- 误用二：热 key 风险。单键大 Hash 的读写全部落在同一个节点，无法靠分片摊薄流量，热点键治理详见第 22 章。
- 误用三：遍历习惯固化。开发期数据小、图省事一律 HGETALL，数据量增长后成为线上阻塞源才发现要改 HSCAN。
- 正确姿势一：预估 field 数量上限并**拆键**，例如按时间、id 区间拆成多个小 Hash，把规模控制在 listpack 友好范围。
- 正确姿势二：读取只 HMGET 业务真正需要的 field，遍历一律 HSCAN 分批进行。
- 监控先行：对 Hash 键的 field 数与内存占用设告警，逼近阈值即拆键，运维配套见第 31 章。
- 大键检测：redis-cli 的 --bigkeys 选项与 MEMORY USAGE 命令可用于巡检，发现隐患要早于事故发生。
- 复盘清单：任何 Hash 上线前先回答三个问题——field 预计多少、单个 value 多大、读取是点名还是全量，三个答案决定拆键设计与命令选择。

```bash
# 清理大 Hash 的安全方式：HSCAN 分批 HDEL
HSCAN big:key 0 COUNT 100
# 拿到一批 field 后：
HDEL big:key f1 f2 f3 ...
# 游标不为 0 则继续，直到遍历删除完毕

# 或直接异步删除整个大键
UNLINK big:key
```

> [!CAUTION]
> **注意内容**：大 Hash 一旦失控，连删除动作本身都可能引发事故——直接对百万 field 的 Hash 执行 DEL 会阻塞主线程直到删除完成。清理大 Hash 应使用 HSCAN 分批 HDEL，或改用 UNLINK 异步删除；删除大键的原理与操作细节详见第 29 章。

**速记**：**拆键控规模，HSCAN 替全量，UNLINK 删大键**。
