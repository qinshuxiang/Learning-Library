## 性能优化与慢查询

### 性能问题的定位思路

#### 先看监控再定位命令

**性能问题的排查路径**：先用监控指标定位问题类别，再定位到具体命令，避免凭感觉盲目优化。

- 第一步看**整体监控**：观察 QPS、CPU、内存、连接数、慢查询条数的曲线，判断异常发生在何时、属于哪一类。
- **CPU 突刺**：优先查慢查询日志，常见元凶是 KEYS 全量遍历、大集合全量读取、复杂 Lua 脚本等长耗时命令。
- **内存上涨**：优先查大 key 与键数量增长，再结合内存碎片率判断是数据膨胀还是碎片堆积。
- **连接数上涨**：优先查连接泄漏，即客户端只建不还、短连接高频创建，配合各应用的连接池配置排查。
- **慢查询条数持续非零**：说明存在稳定的慢命令，用 SLOWLOG GET 直接查看命令内容。
- 第二步定位到**具体命令与来源**：用 SLOWLOG 拿到慢命令，用 CLIENT LIST 找到来源客户端地址，再回到业务代码修改。
- 指标采集：用 INFO 定期采集并落到时间序列监控，单次快照意义有限，曲线趋势才是判断依据。
- 复现与验证：优化后用 redis-benchmark 或业务压测对比前后指标，确认改动有效再上线。
- 环境策略：拿不准时先在测试环境用等量数据复现，确认根因后再动线上。

```bash
# 一分钟快速体检：吞吐、连接、内存与慢查询
INFO stats
INFO clients
INFO memory
SLOWLOG LEN

# 找出执行中的连接：关注 cmd、idle、addr 三个字段
CLIENT LIST
# id=12 addr=10.0.0.8:52130 idle=302 cmd=keys ...
```

> 排查顺序不能颠倒：监控给出问题类别与大致时间点，命令定位给出具体原因。跳过监控直接翻日志，容易把偶发慢命令当成主要矛盾，改了半天不见效。

> 三层归因法：任何慢请求都可归因到客户端、网络、服务端三层——客户端看埋点与连接池日志，网络看 RTT 与带宽，服务端看慢查询与 CPU，逐层排除。

**速记**：**CPU 突刺查慢查询，内存涨查大 key，连接涨查泄漏**。



### 慢查询日志

#### 慢查询日志的配置与 SLOWLOG 命令

**慢查询日志**：Redis 自带的命令耗时记录机制，把执行时间超过阈值的命令写入内存中的先进先出队列，供事后定位慢命令。

- **slowlog-log-slower-than**：记录阈值，单位为微秒，默认 10000，即 10 毫秒；设为 0 记录所有命令，设为 -1 关闭记录。
- **slowlog-max-len**：队列最大长度，默认 128；队列保存在内存中，写满后淘汰最早的记录。
- **SLOWLOG GET**：读取记录，可带参数 N 只取最近 N 条，每条包含序号、发生时间戳、执行耗时（微秒）、完整命令与客户端地址。
- **SLOWLOG LEN**：查看当前队列里的记录条数。
- **SLOWLOG RESET**：清空队列，排查前先清空可获得干净的观察窗口。
- 集群注意：集群模式下每个节点维护自己的慢查询队列，SLOWLOG 命令只作用于当前连接的节点，排查时需逐节点查看。
- 存储位置：慢查询队列只存内存、不落盘，实例重启后记录清空，需要留证时先取走。
- 开销说明：慢查询日志本身开销极小，生产环境长期开启没有问题，不必担心影响性能。
- 内存占用：每条记录只有几百字节，128 条与 1024 条的占用都可忽略，可放心调大。

```bash
# 查看当前阈值与队列长度配置
CONFIG GET slowlog-log-slower-than
CONFIG GET slowlog-max-len

# 临时调整：阈值 5 毫秒，队列扩到 1024 条
CONFIG SET slowlog-log-slower-than 5000
CONFIG SET slowlog-max-len 1024

# 取最近 10 条慢查询，并确认队列长度
SLOWLOG GET 10
SLOWLOG LEN

# 调整确认无误后写入配置文件持久化
CONFIG REWRITE
```

> 先进先出意味着旧记录会被新记录挤掉：线上突增大量慢命令时，最早的那条元凶可能已被淘汰。排查时应及时取走记录，或临时调大 slowlog-max-len 保住现场。

> 阈值设置建议：默认 10 毫秒可能漏掉高频执行的小慢命令，线上排查期常以 1000 微秒即 1 毫秒起步，按业务 QPS 与命令画像调整。

**速记**：阈值单位是**微秒**，默认 **10000 即 10 毫秒**；队列**默认 128 条，先进先出**。



#### 慢查询只记录执行阶段

**记录范围辨析**：慢查询日志只记录命令在服务端的执行阶段，不记录排队等待与网络传输阶段。

- 一条命令对客户端的完整耗时 = 排队时间 + 执行时间 + 网络往返时间，日志只覆盖其中的执行时间。
- 单线程模型下，命令在服务端要排队等前面的命令执行完，排队时间不会被记进任何一条慢查询。
- 大 value 的网络传输发生在响应返回阶段，同样不进日志，但客户端会真实感知到慢。
- 阈值调得再低也测不到排队：排队时间属于等待而非执行，客户端埋点才是排队问题的唯一观测点。
- 主从复制中慢命令同样会阻塞该实例，从节点回放大命令造成的主从延迟，也不体现在慢查询日志里。
- 因此客户端明显变慢而日志为空时，瓶颈多半在排队或网络，而不是单条命令的执行本身。
- 集群注意：命中 MOVED 与 ASK 重定向的请求多一次往返，这部分开销同样不进任何日志。

```bash
# 每条记录的构成示意：只有第 3 行的执行耗时属于慢查询日志的统计范围
> SLOWLOG GET 1
1) 1) (integer) 14          # 序号
   2) (integer) 1757200000  # 发生时间戳
   3) (integer) 24531       # 执行耗时，单位微秒
   4) 1) "KEYS"             # 完整命令
      2) "user:*"
   5) "10.0.0.8:52130"      # 客户端地址
```

> [!WARNING]
> **警告内容**：不能因为慢查询日志为空就断定没有性能问题——单线程排队、大 value 网络传输、带宽打满都会让客户端变慢却不出现在日志里，必须结合客户端埋点耗时与网络指标共同判断。

> 判断耗时归属的实用办法：客户端埋点记录请求总耗时，与 SLOWLOG 中同一命令的执行耗时对比，两者的差值即排队与网络的开销。

**速记**：客户端慢而日志空，查**排队与网络**，不是命令本身。



### 大 key 的发现与治理

#### 大 key 的定义与危害

**大 key**：指 value 体积过大或集合元素个数过多的 key，判断依据是数据体积与元素规模，与 key 名字长短无关。

- 常见形态一：一个 String 存了几 MB 的序列化对象或整页 HTML 内容。
- 常见形态二：一个 Hash 有数百万个 field，一个 ZSet 有千万级成员。
- 经验阈值：String 的 value 超过 10 KB 需关注，超过 1 MB 视为明显过大；集合元素超过一万需评估拆分（实务经验值，非官方规定）。
- 危害一：**阻塞主线程**——单线程执行命令，读写大 key 的长耗时会让所有请求排队。
- 危害二：**网络拥塞**——一次拉取数 MB 的大 value，容易占满网卡带宽，拖慢同实例的其他请求。
- 危害三：**内存不均**——集群模式下大 key 落在单一分片，该节点内存与压力远高于其他节点，详见第 22 章。
- 危害四：**删除卡顿**——DEL 百万元素的大集合需要同步释放内存，可造成长时间阻塞。
- 集群下的迁移代价：不拆分则单分片既是该 key 的内存上限也是性能上限，拆分后按 key 哈希自然摊开到各分片。

```js
// 反例：把用户全部数据堆进一个 Hash，field 数量无上限
await redis.hset("user:1001:data", "orders", JSON.stringify(allOrders));

// 正例：按业务与时间拆 key，单 key 规模可控
await redis.hset("user:1001:orders:2026:09", orderId, JSON.stringify(order));
```

> [!CAUTION]
> **注意内容**：对大 key 执行 DEL、HGETALL、SMEMBERS 等全量操作都可能造成秒级以上阻塞，操作前务必先用 MEMORY USAGE 确认体积，再选择分页或异步方案。

> 大 key 与慢查询的关系：读一个大 key 往往直接成为一条慢查询，两条排查线在 CPU 突刺处汇合，治大 key 就是治慢查询。

> 阈值说明：大 key 没有官方统一标准，本文数值是实务经验值；评估的核心是单 key 的体积乘以访问频次，即它对实例的总开销。

**速记**：value 大或**元素多**都算大 key；四宗罪是**阻塞、拥塞、不均、卡顿**。



#### 大 key 的发现手段

**大 key 的发现**：有线上抽样、精确测量与离线分析三条路径，按对线上影响从小到大选用。

- **redis-cli --bigkeys**：自带抽样扫描，基于 SCAN 渐进遍历键空间，对每种数据类型给出元素个数最大的 key 与平均值，对线上影响小；缺点是结果为近似值，且集合类型给出的是元素个数而非字节数，详见第 28 章。
- **MEMORY USAGE**：精确测量单个 key 的内存占用，单位为字节，可加 SAMPLES 参数控制集合类型的抽样元素个数，适合对 --bigkeys 圈出的可疑 key 逐个复核。

```bash
# 线上抽样扫描，i 控制每轮扫描的间隔秒数，降低对线上的影响
redis-cli --bigkeys -i 0.1

# 复核单个 key 的精确内存占用
MEMORY USAGE user:1001:profile

# 集合类型指定抽样 100 个元素来估算
MEMORY USAGE big:zset SAMPLES 100
```

```bash
# --bigkeys 输出示意：每种类型给出最大 key 与平均值
-------- summary -------
Sampled 500000 keys in the keyspace!

Biggest string found 'user:1001:html' has 2048576 bytes
Biggest   hash found 'big:user:1001' has 1200000 fields
```

- **RDB 离线分析**：把 RDB 文件拉到离线机器解析，统计每个 key 的大小与类型并生成内存报告，rdb-tools 即这一思路的代表工具；优点是对线上零影响，缺点是数据非实时。

```bash
# 离线解析 RDB，输出按内存排序的报告，bytes 参数过滤出 10 KB 以上的 key
rdb -c memory dump.rdb --bytes 10240 -f report.csv
```

- **业务侧埋点**：在写入前统计序列化后的 value 大小，从源头发现即将形成的大 key。
- 四种手段的分工：埋点防患于未然，--bigkeys 日常巡检，MEMORY USAGE 精确复核，RDB 分析出全量报告。
- 时间安排：抽样与精确测量安排在业务低峰期，避免扫描本身给线上带来压力。

> --bigkeys 给出的是每类中最大的 key 与近似规模，不是全量精确排名；要出结论，先用它圈定范围，再用 MEMORY USAGE 逐个复核，或用离线工具分析 RDB。

> 巡检节奏：--bigkeys 全量扫描一遍有成本，建议接入定期巡检脚本在低峰期执行，把结果与上次对比，新增大 key 能被及时发现。

**速记**：**抽样**用 --bigkeys，**精确**用 MEMORY USAGE，**离线**分析 RDB。



#### 大 key 的治理手段

**大 key 的治理**：核心思路是化整为零、按需取用、异步删除，且尽量在写入之前完成设计。

- **拆分**：把一个大 Hash 按业务或编号拆成多个小 key，把超长集合分段分页，单 key 元素规模控制在万级以内。
- 拆分粒度：太碎则 key 数量暴涨、管理成本上升，按业务边界拆到单 key 规模可控即可，不必追求越小越好。
- **压缩**：value 序列化后先压缩再写入，如用 gzip 压缩后存 String，用少量 CPU 换数倍的内存与带宽节省。
- **按需取用**：用 SCAN 渐进遍历代替 KEYS 与 HGETALL，用 HMGET、ZRANGE 等带范围的命令代替全量读取，详见第 2 章。
- **异步删除**：用 UNLINK 代替 DEL，内存释放交给后台线程；再配合 lazyfree 配置族，把过期删除与隐式删除也转为异步，详见第 16 章。

```bash
# 异步删除：命令立即返回，内存由后台线程释放
UNLINK big:hash

# 把过期删除与隐式删除转为异步的配置族
CONFIG SET lazyfree-lazy-expiry yes
CONFIG SET lazyfree-lazy-server-del yes
CONFIG SET lazyfree-lazy-user-del yes

# 小 key 直接 DEL 更省事，大 value 与大集合才必须 UNLINK
DEL small:key
UNLINK big:zset
```

```bash
# 渐进遍历代替 KEYS：每次只取一小批，游标继续往下翻
SCAN 0 MATCH user:* COUNT 100

# 只读取需要的 field，代替 HGETALL 全量拉取
HMGET big:user:1001 name email
```

> 治理大 key 最省事的位置在设计期：结构定型后再拆分需要迁移线上数据；新业务从第一天就把集合规模控制在阈值内，成本最低。

> 拆分后的读取注意分页：拆出的每个小 key 依然要避免全量读取，分页游标与 SCAN 配合使用，防止把一个大 key 换成多个中 key。

**速记**：大 key 治理四字诀——**拆、压、取、异步删**。



### 热 key 的发现与应对

#### 热 key 的定义与发现

**热 key**：指访问 QPS 远高于其他 key、请求集中打在单一键上的现象，本质是流量倾斜而非数据体积问题。

- 热 key 本身可能很小，但全部流量涌向它，导致承载它的分片或节点被打满。
- 典型场景：秒杀商品详情、热点新闻内容、排行榜第一名、高频读取的配置项。
- 发现手段一：**MONITOR 抽样**——实时打印命令流，短时抽样统计 key 频次；MONITOR 自身开销大，只能短时低频使用。
- 发现手段二：**客户端埋点**——在应用侧统计 key 访问频次，精确且无服务端开销，覆盖面限于本应用。
- 发现手段三：**代理层统计**——使用代理接入时在代理层聚合统计，可覆盖全部客户端流量。
- 频次视角：判断热 key 看的是相对占比，单 key 访问量占到实例总 QPS 的一成以上即需警惕。
- 统计窗口：客户端埋点的统计窗口要短，长窗口会把已经降温的历史热点误判为当前热点。
- 采样降耗：超高 QPS 下埋点可按比例抽样，抽样统计的相对排序已足够定位热 key。

```bash
# 短时抽样热 key：抓一段命令流离线统计频次，看几秒就关
redis-cli MONITOR | head -n 1000
```

```js
// 客户端埋点：进程内统计 key 访问频次，定时输出 TopN
const counter = new Map();
function trackKey(key) {
  counter.set(key, (counter.get(key) || 0) + 1);
}

function topHotKeys(limit) {
  return [...counter.entries()]
    .sort((a, b) => b[1] - a[1])
    .slice(0, limit);
}
```

> MONITOR 会把每条命令实时推送给订阅它的客户端，开一个 MONITOR 就可能让高 QPS 实例的吞吐明显下降，生产环境严禁长时间开启。

> 热 key 与缓存击穿的关联：热 key 集中过期的瞬间，大量请求会穿透到数据库，应对手段相互衔接，详见第 25 章。

**速记**：热 key 是**流量倾斜**，不是体积问题；发现靠**抽样与埋点**。



#### 热 key 的对策

**热 key 的对策**：核心思路是分流，把打在单 key 上的流量摊到多个副本或多个内存层级。

- **本地缓存 L1**：在应用进程内加一层短 TTL 的本地缓存，命中后不再请求 Redis，适合读多写少的热点数据。
- **key 加随机后缀打散**：写入时把同一份数据复制为多个带随机后缀的副本，读取时随机选一个，把流量均摊到多个 key 乃至多个分片。
- 副本数量：按热度从 10 到 100 个不等，副本太多浪费内存，太少摊不平流量。
- **读写分离**：开启主从复制，把读流量分摊到多个从节点，详见第 20 章。
- 三招可组合：先用 L1 挡掉大部分读，剩余请求用打散与读写分离消化。
- L1 的代价：本地缓存占应用内存且需处理失效，TTL 不宜过长，写多的数据慎用。
- 写多热点：打散与 L1 都偏读场景，写热点要用本地合并写或队列削峰，思路不同。

```js
// 进程内 L1 缓存：短 TTL 的本地缓存挡掉大部分读
const l1 = new Map();
function getWithL1(key, ttlMs) {
  const hit = l1.get(key);
  if (hit && hit.expire > Date.now()) {
    return Promise.resolve(hit.value);
  }
  return redis.get(key).then((value) => {
    l1.set(key, { value, expire: Date.now() + ttlMs });
    return value;
  });
}

// 随机后缀打散：读时随机选一个副本
function getHotKey(key, replicaCount) {
  const idx = Math.floor(Math.random() * replicaCount) + 1;
  return redis.get(key + ":" + idx);
}
```

> 打散方案要求副本间数据一致：写时同步更新全部副本，或给副本设很短的过期时间、容忍秒级不一致，按业务对一致性的容忍度选择。

> 多级缓存的整体视角：本地缓存是第一级，Redis 是第二级，数据库是第三级；层级越多，一致性维护越复杂，热 key 场景下通常值得付出这个代价。

**速记**：热 key 分流三招——**本地缓存、随机打散、读写分离**。



### SCAN 渐进式遍历

#### SCAN 的游标语义与遍历保证

**SCAN**：以游标为基础、分批返回 key 的渐进式遍历命令，自 Redis 2.8.0 引入，用于替代一次遍历全键空间并阻塞主线程的 KEYS。

- 游标语义：首次调用传游标 0 开始新一轮遍历，每次返回一批 key 与一个新游标，把新游标原样带入下一次调用，直到返回游标 0 表示整轮遍历结束。
- **COUNT**：对每轮扫描工作量的提示值，默认 10，含义是本轮尝试遍历的哈希桶数而非返回 key 的数量上限，返回多少个 key 由桶里装了什么决定。
- MATCH 与 TYPE 过滤：在服务端返回之前进行，模式过滤后本批可能一个 key 都没有，此时仍要以返回的游标继续调用，判断结束只看游标是否回到 0。
- 家族命令：HSCAN、SSCAN、ZSCAN 分别渐进遍历 hash、set、zset，游标语义与 SCAN 一致，用于替代 HGETALL、SMEMBERS、ZRANGE 的全量拉取。
- 复杂度：单次调用均摊 O(1) 到 O(COUNT)，完整遍历一轮 O(N)，N 为元素总数；KEYS 是一次性的 O(N) 阻塞，SCAN 把 N 摊到多次调用之间，每批之间主线程仍可服务其他命令。
- 客户端封装：ioredis 的 scanStream 会自动管理游标并按批推送数据，业务侧无需手工搬运游标。
- 遍历保证：SCAN 只保证遍历开始到结束期间一直存在的 key 一定会被返回，不提供任何时刻的快照语义。
- 可能重复：完整遍历期间同一个 key 可能被返回多次，客户端需容忍重复或自行去重。
- 动态而非快照：遍历期间新增的 key 不保证返回，删除的 key 若在被扫到之前删掉则不会出现。
- 与渐进式 rehash 的兼容：字典扩容或缩容期间新旧两张哈希表并存（详见第 11 章），SCAN 采用反向二进制迭代法按桶的倒序二进制位推进，保证已扫过的桶不会因 rehash 搬移而漏扫。
- rehash 期间的重复从何而来：同一个桶可能在新旧两表各被访问一次，重复返回正是用空间换不漏的直接代价。
- 工程含义：需要精确一致的全量数据时不要依赖 SCAN，应改用 RDB 离线分析；SCAN 的定位是低影响的在线巡检与分批处理。

```bash
# 从游标 0 开始，每轮约扫 100 个桶，只返回 user: 前缀的 key
SCAN 0 MATCH user:* COUNT 100
# 返回示意：第一行是新游标，第二行是本批 key
# 1) "17"
# 2) 1) "user:1001"
#    2) "user:1002"

# 对大 hash 分批读 field，替代 HGETALL
HSCAN big:hash 0 COUNT 100
```

> 辨析：COUNT 只是提示不是硬限——对 int 编码的小对象一次全量返回，对大哈希表则按桶扫描，每批条数可能多于也可能少于 COUNT，业务侧不应依赖每批数量固定。

> [!CAUTION]
> **注意内容**：**SCAN 的结果中可能混有重复 key**——下游若按条计数或逐条写入而不去重，统计会翻倍、数据会重复处理；用集合去重或按 key 幂等写入是标准做法。

**速记**：**游标 0 起且 0 止**，COUNT 是**桶数提示**，三条保证是**不漏、可重、非快照**。



### pipeline 与命令打包

#### pipeline 的原理与收益

**pipeline**：客户端把多条命令一次性打包发给服务端，服务端依次执行后把全部结果一次返回，是把多次网络往返合并为一次的传输层优化。

- 逐条发送时每条命令都要等待一个往返时间 RTT，N 条命令就是 N 次 RTT；打包后总耗时接近一次 RTT 加命令执行时间。
- 收益与 RTT 成正比：跨机房 RTT 达几十毫秒时收益巨大，同机房 RTT 在 1 毫秒以内时收益主要来自系统调用次数减少。
- 服务端对打包命令仍是**逐条执行**，pipeline 不提供原子性保证。
- 响应顺序与发送顺序一一对应，客户端按序对应结果，无需额外的匹配机制。
- pipeline 不改变命令语义，打包里的每条命令与单独发送完全等价。
- pipeline 与连接池配合使用：多条连接各自打包，吞吐进一步提升，但要留意服务端输入缓冲区的上限。
- Node 中 ioredis 提供专门的 pipeline 方法，链式添加命令后用 exec 一次性提交。

```js
const pipeline = redis.pipeline();
pipeline.set("user:1001:name", "alice");
pipeline.incr("stats:visit");
pipeline.hget("user:1001", "email");
const results = await pipeline.exec();
// results 是按添加顺序排列的结果数组
```

```js
// 批量写入 1000 条：分批打包，每批 200 条，兼顾往返次数与缓冲区大小
async function batchSet(items) {
  const batchSize = 200;
  for (let start = 0; start < items.length; start += batchSize) {
    const pipeline = redis.pipeline();
    for (const item of items.slice(start, start + batchSize)) {
      pipeline.set(item.key, item.value);
    }
    await pipeline.exec();
  }
}
```

> [!TIP]
> **建议内容**：单次打包的命令量控制在 100 到 500 条：过少省不掉多少 RTT，过多则一次发送的数据量会撑大客户端与服务端的输入缓冲区，反而带来内存压力。

> 算一笔账：跨机房 RTT 为 30 毫秒时，逐条执行 100 条命令至少 3 秒，打包后一次往返加执行时间通常不到 50 毫秒，收益接近两个数量级。

**速记**：pipeline 攒命令**一次往返**，收益来自省 RTT。



#### pipeline 与 mget、事务的区别

**三者辨析**：pipeline 是传输层的批量优化，mget 是命令层的批量读取，事务是执行层的原子打包，三者解决不同层面的问题。

- **pipeline 与 mget**：mget 是一条命令取多个 String，天然一次往返且原子执行；pipeline 可打包任意命令，但无原子性。
- **pipeline 与事务**：事务以 MULTI 与 EXEC 保证命令成组原子执行、不被其他客户端插队，详见第 23 章；pipeline 只保证一次发送，不保证执行不被插队。
- 事务可以装进 pipeline 一起发送，两者可组合使用，先省 RTT 再保原子。
- 选择原则：需要原子性用事务或 Lua 脚本，只需要减少往返用 pipeline，后者开销更小。
- Lua 脚本可视为服务端打包：兼具原子性与省往返，代价是脚本复杂度与超时风险，详见第 23 章。

```js
// 事务保证原子执行，底层同样借助批量发送减少往返
const result = await redis
  .multi()
  .incr("stock:1001")
  .lpush("orders:queue", "order:1")
  .exec();
```

> 常见误区是把 pipeline 当事务用：pipeline 打包的命令执行期间，其他客户端的命令仍可能插入执行，依赖打包即原子的代码存在并发安全隐患。

> 一句话区分：pipeline 管的是传输效率，事务管的是执行原子性，mget 管的是单命令批量读，三者可以按需叠加。

**速记**：pipeline **省 RTT 不保原子**；要原子用**事务或 Lua**。



### 连接与网络优化

#### 连接池的必要性

**连接池**：预先建立并复用一组到 Redis 的 TCP 连接、避免每次请求新建连接的客户端机制。

- 新建一次连接要经历 TCP 三次握手、AUTH 认证、SELECT 选库等多个往返，高频短连接下这些开销可能超过命令本身。
- 无池化时高并发会瞬间创建大量连接，冲击服务端 maxclients 上限，也可能耗尽客户端的文件描述符。
- 池大小经验值：从应用并发量与命令耗时估算，常见以 10 起步再压测调整，并非越大越好，过大徒增服务端连接管理负担。
- 池化参数：空闲连接回收、借出超时、最大等待数等按业务设定，避免请求排队在池本身上。
- 连接保活：池中的连接要定期校验，剔除被服务端 timeout 断开的死连接，避免拿到即失败。
- Node 生态中 ioredis 默认自带连接复用：单个实例内部维护连接并自动复用，多数场景无需手动建池；并发极高时可建多个实例分摊。

```js
const Redis = require("ioredis");
// 单实例默认即复用连接，业务代码无需关心建连细节
const redis = new Redis({ host: "127.0.0.1", port: 6379 });

// 并发极高时可建多个实例，按序取用，效果等同连接池
const instances = [
  new Redis({ host: "127.0.0.1", port: 6379 }),
  new Redis({ host: "127.0.0.1", port: 6379 }),
  new Redis({ host: "127.0.0.1", port: 6379 }),
];
let cursor = 0;
function nextRedis() {
  cursor = (cursor + 1) % instances.length;
  return instances[cursor];
}
```

> 判断连接泄漏：CLIENT LIST 显示的连接数持续上涨且大量连接的空闲时间 idle 很长，多半是只建不还或忘记释放；把连接统一交给连接池托管即可根治。

> 服务端的对应配置：maxclients 限定最大连接数，池化后连接数可预期，配合 rejected_connections 指标可以确认连接规划是否合理。

**速记**：短连接贵在**握手与认证**；ioredis **默认复用**，泄漏查 CLIENT LIST。



#### 网络层面的优化手段

**网络优化**：Redis 的对外性能上限很大程度由网络决定，优化目标是减少传输量、缩短传输距离。

- **同机房部署**：应用与 Redis 部署在同一机房乃至同一可用区，把 RTT 压到 1 毫秒以内；跨机房 RTT 会叠加到每个请求上。
- 调度注意：容器化部署时把 Redis 与应用调度到同一节点或同可用区，避免反亲和策略把距离拉开。
- **分页读集合**：RESP 协议下返回数据量与网络带宽成正比，集合读取一律带范围参数分页，如 ZRANGE 指定起止下标、HSCAN 控制每批数量，避免一次拉取整个大 value。
- **压缩后传输**：大 value 序列化后压缩再写入，读取后客户端解压，用少量 CPU 换数倍带宽节省；JSON 与文本类数据压缩率最高，已压缩数据不必二次压缩。
- 带宽打满的典型症状：命令在服务端排队、客户端超时增多，但服务端 CPU 并不高，可结合网卡流量监控确认。
- pipeline 同受带宽约束：打包命令的返回值总量过大时照样打满带宽，大批量读取要分批并压缩返回内容。
- 连接维持：频繁的短连接健康检查同样消耗握手开销，用长连接心跳代替高频重连。

> 网络问题与命令慢的区分要点：服务端 CPU 低、慢查询日志干净、客户端却普遍超时，优先怀疑带宽与 RTT，而不是命令本身。

> 读写分离的补充：分页与压缩减少的是每次传输的字节数，读写分离减少的是单节点上的连接与流量，两条路可以同时走。

**速记**：同机房压 RTT，**分页减传输**，**压缩换带宽**。



### 危险命令治理

#### 危险命令清单与 rename-command

**危险命令**：会在生产环境造成阻塞、数据丢失或安全风险的命令，需要规范与配置双重治理。

- **KEYS**：全量遍历键空间，键多时阻塞主线程数秒，一律用 SCAN 代替，详见第 2 章。
- **FLUSHALL 与 FLUSHDB**：清空全部或当前数据库的数据，误执行即灾难。
- **CONFIG**：运行时修改配置，存在被利用篡改持久化路径等安全风险，重点治理 CONFIG SET。
- **DEBUG**：调试用途，如 DEBUG SLEEP 会直接挂起主线程。
- 规范层面治理：代码评审拦截 KEYS 与 FLUSHALL，数据清理一律走渐进删除脚本。
- 替代手段：清库需求用脚本按 SCAN 渐进删除，或在新版本中用 FLUSHALL ASYNC 异步清空。
- 配置层面治理：用 rename-command 把危险命令改名或改名成空串禁用，详见第 31 章。
- 补充手段：部分网关与云托管支持命令禁用名单，与 rename-command 互为兜底。
- 效果验证：改名生效后尝试执行原命令应返回未知命令错误，用这一步确认治理到位。
- 流程兜底：静态扫描业务代码中的禁用命令关键字，发布前自动拦截。

```bash
# 配置文件中把危险命令改名或禁用
rename-command KEYS ""
rename-command FLUSHALL ""
rename-command DEBUG "d1e3b2f8debug"
```

> [!IMPORTANT]
> **重要内容**：rename-command 修改后需重启实例才生效，且改名后原命令名不再可用——依赖这些命令的运维脚本与监控工具需同步更新，详见第 31 章。

> 改名的取舍：把命令改名成空串是彻底禁用，改成一个难猜的字符串是保留应急入口；两者都比放任原命令名裸奔安全。

**速记**：KEYS、FLUSHALL、CONFIG、DEBUG 是生产四害，**改名治理**。



### 指标观察与检查清单

#### INFO 关键运行指标

**运行指标观察**：INFO 命令输出的分段统计是性能优化的日常观察面板，重点看 stats 与 memory 两段。

```bash
# stats 段：吞吐与命令统计
INFO stats
# memory 段：内存占用与碎片
INFO memory

# 开启主动碎片整理
CONFIG SET activedefrag yes

# 内存上限与淘汰策略配合检查
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
```

```bash
# 关键字段示意
total_commands_processed:1048576
instantaneous_ops_per_sec:2350
keyspace_hits:802130
keyspace_misses:200320
rejected_connections:0
expired_keys:45210
used_memory:536870912
used_memory_rss:601295416
mem_fragmentation_ratio:1.12
```

- **total_commands_processed**：实例累计处理的命令总数，反映历史总负载。
- **instantaneous_ops_per_sec**：当前每秒执行的命令数，是实时吞吐的核心指标。
- **keyspace_hits 与 keyspace_misses**：命中与未命中次数，两者之比即缓存命中率，命中率下滑要回到缓存设计排查，详见第 25 章。
- **rejected_connections**：因超过 maxclients 被拒绝的连接数，长期大于零说明连接数不足或存在泄漏。
- **expired_keys 与 evicted_keys**：过期删除与内存淘汰的数量，evicted 长期增长说明内存上限不够用。
- **mem_fragmentation_ratio**：内存碎片率，即操作系统实际分配内存与 Redis 申请内存之比，1.0 到 1.5 为合理区间；低于 1 说明发生了 swap，高于 1.5 说明碎片偏多。
- **activedefrag**：主动碎片整理开关，开启后 Redis 在运行中逐步回收碎片空间，需配合内存上限与淘汰策略使用，详见第 15 章。
- 采集注意：INFO 本身也是命令，高频全量 INFO 在大实例上有成本，按需只取 stats、memory 等所需段。

> [!NOTE]
> **提醒内容**：判读 mem_fragmentation_ratio 要看绝对值也要看趋势——长期缓慢上涨比一次性偏高更值得关注，其数值来自 used_memory_rss 与 used_memory 的比值。

> 采集方式：INFO 输出便宜，可按秒级周期采集进监控系统；重点字段单独设阈值告警，比人肉盯屏可靠。

**速记**：吞吐看 instantaneous_ops_per_sec，内存健康看 mem_fragmentation_ratio 的 **1.0 到 1.5** 区间。



#### 优化检查清单

**优化检查清单**：把本章手段收敛为可逐项核对的清单，作为上线评审与定期巡检的依据。

- 慢查询：阈值与队列长度是否合理，SLOWLOG LEN 是否长期非零，元凶命令是否已治理。
- 大 key：是否定期用 --bigkeys 抽样，删除是否用 UNLINK，集合读取是否分页。
- 热 key：是否有 L1 缓存与随机打散方案，代理层是否有频次统计。
- 客户端：是否使用连接池，pipeline 打包量是否在 100 到 500 区间。
- 网络：应用与 Redis 是否同机房，大 value 是否压缩后传输。
- 危险命令：rename-command 是否已配置，评审是否拦截 KEYS。
- 操作系统：THP 是否已关闭，vm.overcommit_memory 是否为 1，换页监控是否就位。
- 指标：OPS、碎片率、慢查询条数、缓存命中率是否在看板上长期跟踪并设置告警。
- 变更：每次发布前用压测对比核心指标，性能回退能被及时发现。
- 演练：大 key 清理与热 key 应急预案是否演练过，出事时照预案执行而不是临场发挥。
- 告警分级：慢查询条数、碎片率、命中率、连接数分别设阈值与升级策略，避免一条告警包打天下。
- 记录：优化结论与参数变更写入运维文档，方便回溯与交接。

> 🧭 性能优化口诀：**慢查询查命令，大 key 查结构，热 key 查拓扑**——先定位类别，再上手段，最后用清单兜底。

**速记**：先看监控定类别，再按**清单逐项核对**，口诀兜底。
