## 通用命令与键管理

### 键的本质与命名规范

#### 键的本质：二进制安全的字符串

**键（Key）**：是 Redis 中标识一份数据的唯一名字，本质是一个二进制安全的字符串，从空串到任意字节序列都可以作为键。

- 键的最大长度为 512MB，与 String 值的上限一致，普通业务永远用不到这个上限。
- 键本身没有类型，类型附着在值上；对键能执行哪些命令由值的类型决定。
- 每个逻辑库的键空间（keyspace）本质是一个大字典，保存键到值的映射，字典的底层实现详见第 11 章。
- 键名即数据的一部分：改名得到的是同一份数据的新视角，删除键名即删除数据本身。
- 键在 RDB、AOF 与主从复制中按原始字节传输，不存在编码转换，写进什么读出来就是什么。
- 二进制安全意味着键里可以放序列化后的任意内容，但也意味着不规范键名会造成难以排查的脏数据。
- 键名中的二进制字节会原样进入持久化文件，可打印性差会直接影响排障，因此键名应当使用可打印字符。
- 所有键级命令（GET、DEL、EXISTS、TTL 等）都要求完整精确的键名，模式匹配只在 KEYS、SCAN 这类专门的遍历命令中提供。
- 键级命令的返回都以键是否存在为前提，不存在时大多返回 nil、0、-1 或 -2，具体语义在本章各节展开。

```bash
SET 用户:1001 "Alice"     # 中文、任意字节都能当键，技术上合法
GET 用户:1001
DEL 用户:1001    # 键级命令按完整键名操作
```

```text
OK
"Alice"
(integer) 1
```

> 常见误解是「键名像变量名，必须符合某种语法」。实际上 Redis 对键没有任何语法约束，中文、空格、换行都能当键，但工程上必须自我约束，否则运维工具、监控与代码将难以统一处理。

> 工程细节：键名里避免空格与换行。redis-cli 中虽可用引号包裹这类键名，但多数监控与统计工具按空白或冒号切分键名，特殊字符会让它们失灵。
> 中文键名应在代码评审中被拦截，统一走英文前缀词典。

**速记**：键是二进制安全的字符串，512MB 封顶，键无类型、值有类型，按原样字节存储与传输。



#### 冒号分层的设计惯例

**冒号分层**：是用半角冒号把键拆成层级的命名惯例，形如 business:id:field，是社区约定俗成的目录式设计。

- 第一段放业务或系统名：mall、user、order，用于隔离不同业务的键。
- 中间段放对象类型：profile、cart、detail，说明这个键存的是什么。
- 末段放唯一标识：用户 ID、订单号、日期，定位到具体一条数据。
- 典型例子：user:profile:1001、order:detail:20260907、mall:cart:1001。
- 层级粒度按需决定：两到四段是常见范围，层级过深会让键名冗长且难维护。
- 需要更细分时可以继续加层级，例如 user:profile:1001:cache 表示用户资料的具体字段缓存。
- 冒号前后不留空格：user:1001 是惯例写法，user : 1001 中的空格会被当成键名的一部分带来困扰。
- 同一业务内的层级深度保持一致，便于监控按固定段数做前缀聚合。
- 分层的直接收益：SCAN 配合 MATCH user:* 可以按前缀增量扫描某一业务的键，排障时一眼识别键的归属，避免多业务键名互相冲突。
- 冒号本身没有语法含义，Redis 不解析层级，它只是给人类与工具看的分隔符。
- 前缀层级同时服务于监控与运维：按业务前缀统计键量、按前缀配置告警，都依赖规整的冒号结构。

```bash
# 典型的分层键设计
SET user:profile:1001 "Alice"
SET user:cart:1001 "item:3,item:7"
SET order:detail:202609070001 "paid"
SET mall:seckill:goods:88 "10"   # 秒杀业务的商品库存
```

> [!TIP]
> **建议内容**：团队应先定一份键名词典（前缀表），再开始写业务代码；前缀一旦散落进各处字符串，后期统一改名只能全库 SCAN 加迁移，代价极高。

> 反面例子是全平铺命名 user_profile_1001 与 shoppingcart_88：没有统一分隔符，SCAN 无法按业务段过滤，监控与告警也没法按前缀聚合统计。

**速记**：冒号是目录分隔符，业务:对象:ID，前缀即命名空间。



#### 键长度与可读性的权衡

**键长度权衡**：键本身常驻内存且被字典等结构反复引用，需要在省内存与可读性之间找平衡。

- 键越短越省内存：千万级键量下，每个键省 20 字节就是上百 MB 的差距。
- 过度缩写伤可读性：u:1:p 这类键在监控与排障时几乎无法辨认。
- 经验做法：业务前缀用约定缩写，唯一标识保持原样，整体控制在 50 字节以内。
- 超长业务名先在词典里定缩写，例如 mall、bbs，不要临时造词。
- 唯一标识不要二次加工：直接用订单号、用户 ID 原文，避免排障时还要反推规则。
- 键名统一小写：Redis 键区分大小写，User:1 与 user:1 是两个键，大小写混用是脏数据的高发源。
- 可读性的兜底手段是统一的命名规范与文档，而不是把所有信息塞进键名。
- 权衡没有唯一答案，但必须全团队一致：一半键用全称、一半键用缩写，比全部用缩写更糟。

```bash
# 三种写法的对比：前两种可接受，第三种过度压缩
SET order:detail:202609070001 "paid"
SET o:d:202609070001 "paid"
SET o:202609070001:d:u:1001:s:1 "paid"
```

> 值得区分的是：键的长度影响的是内存与网络传输，不影响查找性能——字典查找按哈希进行，时间复杂度与键长基本无关。因此优先保证可读、可控，其次才是压长度。

**速记**：键短省内存，键清可排障；查找速度看哈希，不看键长。



### 基础读写命令

#### SET 与 GET：写入与读取

**SET**：写入字符串键的核心命令，完整语法为 SET key value [EX seconds] [PX milliseconds] [NX|XX] [KEEPTTL] [GET]，成功返回 OK。**GET**：读取字符串值，键不存在返回 nil。

- SET name "Alice"：最基本形式，写入或覆盖已存在的键。
- EX seconds 与 PX milliseconds：写入的同时设置过期时间，单位分别为秒与毫秒。
- NX：键不存在时才写入；XX：键已存在时才写入；二者互斥，条件不满足返回 nil。
- KEEPTTL（6.0 起）：覆盖写入时保留原键的剩余 TTL。
- GET 选项（6.2 起）：写入新值的同时返回旧值，省去一次 GET 的往返。
- SET 成功返回 OK，条件不满足（NX、XX 不成立）返回 nil，客户端靠返回值区分结果。
- NX 与 XX 只控制是否执行写入，失败时返回 nil 且不做任何修改，不改变其他语义。
- GETSET 是历史命令，等价于 SET 的 GET 选项，新代码统一用 SET key value GET。
- 值与键一样是二进制安全的字符串，序列化后的 JSON、图片字节都能存。
- GET 对非字符串键报 WRONGTYPE 错误；字符串类型的完整命令集详见第 3 章。
- SET 覆盖旧值时旧值直接丢弃，需要旧值时用 GET 选项一次性带回，避免覆盖前先读造成的竞态。

```bash
SET user:name "Alice"          # 写入
GET user:name                  # 读出
SET user:name "Bob" NX         # 键已存在，不覆盖
SET user:name "Carol" XX       # 键已存在，覆盖
SET user:token "abc" EX 3600   # 写入并设置 3600 秒过期
SET user:name "Dave" GET       # 写新值的同时返回旧值
```

```text
OK
"Alice"
(nil)
OK
OK
"Carol"
```

> SET 带 EX 与「先 SET 再 EXPIRE」效果不同：前者一条命令原子完成，后者两条命令之间存在间隙，其他客户端可能读到一把没有过期时间的键。缓存场景务必优先用 SET 的自带选项。

> SET NX 是很多分布式锁实现的第一块积木：只有拿到 OK 的客户端才算抢到锁，锁的完整方案（过期、续期、释放）详见第 27 章。

**速记**：SET 管写、GET 管读；EX 定时、NX 防覆盖、KEEPTTL 保 TTL。



#### EXISTS 与 TYPE：存在性判断与类型查询

**EXISTS**：判断键是否存在，语法为 EXISTS key [key ...]，存在返回 1，不存在返回 0。**TYPE**：返回键对应值的类型，如 string、hash、list、set、zset、stream。

- EXISTS 支持一次传多个键，返回其中存在的个数，可做批量探测。
- TYPE 对不存在的键返回 none，而不是报错。
- 二者时间复杂度均为 O(1)，可放心在生产高频使用。
- 对错误类型的键执行命令会报 WRONGTYPE 错误，写入前用 TYPE 检查可提前发现键被污染。
- TYPE 的返回值决定了该键能用哪一族命令，是排查「命令用错键」的第一入口。
- EXISTS 判断的是键的存在性，与值是否为空无关：键存在但值为空串仍返回 1。
- pipeline 中批量 EXISTS 是批量探测的高效写法，减少往返次数，结果与逐条调用一致。
- 这两个命令也是巡检脚本的基础件：先 SCAN 拿键名，再 EXISTS 与 TYPE 逐个确认。

```bash
EXISTS user:name user:cart user:ghost   # 三个键中存在几个
TYPE user:name                          # 查类型
TYPE user:cart                          # list 键
TYPE user:ghost                         # 不存在的键
```

```text
(integer) 2
string
list
none
```

> TYPE 只能一次查一个键，批量场景需客户端循环调用；EXISTS 多键形态返回的是计数而非每个键的布尔值，需要逐键结果时应分开传或每个键各调一次。

**速记**：EXISTS 数存在个数，TYPE 报值类型，都是 O(1)，none 表示键不存在。



### 过期时间管理

#### EXPIRE 一族：相对与绝对过期时间

**EXPIRE**：给已存在的键设置以秒为单位的存活时长，语法为 EXPIRE key seconds [NX|XX|GT|LT]，成功返回 1，键不存在返回 0；这一族还包括 PEXPIRE、EXPIREAT、PEXPIREAT 与 7.0 新增的 EXPIRETIME。

- EXPIRE 与 PEXPIRE 是相对时间：从命令执行那一刻起，再经过 seconds 秒或 milliseconds 毫秒键被删除。
- EXPIREAT 与 PEXPIREAT 是绝对时间：以 Unix 时间戳（秒或毫秒）指定键活到哪一刻。
- EXPIRETIME（7.0 新增）与 PEXPIRETIME：反向查询键的绝对过期时间戳，键不存在或无 TTL 时返回 -1。
- EXPIRETIME 返回的是到期时刻而不是剩余时长，与 EXPIREAT 形成写入与读取的闭环。
- EXPIRE 的四个条件选项（7.0 新增）：NX 仅当当前无 TTL 时设置，XX 仅当已有 TTL 时设置，GT 仅当新 TTL 更大时设置，LT 仅当新 TTL 更小时设置。
- 返回值约定一致：设置成功返回 1，键不存在返回 0。
- 过期精度为毫秒级（底层统一存到期时间戳），但删除动作并非精确准时，详见第 14 章的惰性与定期删除。
- EXPIREAT 传入过去的时间戳会让键立即过期，相当于变相删除，个别脚本用这个特性做定时清理。

```bash
SET session:1001 "data"
EXPIRE session:1001 1800          # 30 分钟后过期
PEXPIRE session:1001 1500         # 1.5 秒后过期，覆盖上一次
EXPIREAT coupon:2026 1798761599   # 活到指定时刻
EXPIRETIME coupon:2026            # 查询过期时刻
```

```text
OK
(integer) 1
(integer) 1
(integer) 1
(integer) 1798761599
```

> 相对时间适合「会话再活 30 分钟」这类从现在起算的业务；绝对时间适合「当天 23:59:59 失效」「优惠券到月底」这类与日历对齐的业务。给键续期要警惕覆盖语义：EXPIRE 是重设 TTL 而不是叠加，剩余 10 分钟的键执行 EXPIRE key 600 后剩余时间正好回到 10 分钟。

**速记**：EXPIRE/PEXPIRE 定时长，EXPIREAT 定时刻，EXPIRETIME（7.0）查时刻；GT/LT/NX/XX 是 7.0 的精细控制。



#### TTL、PTTL 与 PERSIST：剩余存活时间的查询与移除

**TTL**：返回键的剩余存活秒数；**PTTL**：返回剩余毫秒数；**PERSIST**：移除键的过期时间，使其成为永不自动删除的持久键。

- 返回值三态：正数是剩余时间；-1 表示键存在但没有 TTL；-2（2.8 起）表示键不存在。
- PERSIST 成功返回 1；键不存在或本无 TTL 返回 0。
- 没有设置 TTL 的键是持久键，Redis 不会自动删除它，只能被淘汰策略或显式删除清走。
- PTTL 的毫秒精度常用于续期计算：先读剩余毫秒，再按业务逻辑决定新的 TTL。
- TTL 是秒级取整的显示，PTTL 才是底层精确值，对到期时机敏感的续期必须用 PTTL。
- TTL 与 PTTL 在键被 EXPIRE 重设后立即反映新值，读到的永远是最新剩余时间。
- 过期键的真正删除由惰性删除与定期删除完成，详见第 14 章。
- TTL 是本章使用频率最高的返回值辨析点，也是面试常考的 -1 与 -2 区别。

```bash
SET cache:page "html" EX 600
TTL cache:page          # 剩余秒数
PTTL cache:page         # 剩余毫秒数
PERSIST cache:page      # 取消过期
TTL cache:page          # 已是持久键
```

```text
(integer) 600
(integer) 599999
(integer) 1
(integer) -1
```

> [!NOTE]
> **提醒内容**：-1 与 -2 的含义完全不同——-1 是「键活着，但没有定时」，-2 是「键已经不存在」。依赖 TTL 判断缓存是否命中的代码，必须同时处理这两个返回值，否则极易把未设 TTL 的键误判为已过期。

**速记**：TTL 看秒、PTTL 看毫秒；-1 没定时，-2 已消失；PERSIST 一键保永久。



#### 过期时间的覆盖与继承规则

**过期时间的覆盖规则**：TTL 附着在键对象上而不是键名上，因此围绕同一个键的操作对 TTL 的影响有明确规则，覆盖写入与重命名是两大易错点。

- 覆盖写入清 TTL：不带 KEEPTTL 的 SET 会把旧 TTL 一起清掉，键回到持久状态。
- KEEPTTL 保 TTL：SET 带 KEEPTTL 选项时覆盖值并保留剩余 TTL。
- 重命名带 TTL：RENAME 改的是键名，TTL 原样随键迁移。
- EXPIRE 覆盖旧值：再次设置过期时间以最后一次为准，不做叠加。
- PERSIST 清除 TTL：显式移除后键变持久键，再想定时需重新 EXPIRE。
- 主从之间过期以到期时刻传播而不是剩余秒数，主从视角的剩余时间随同步略有差异，但到期时刻一致。
- 除此之外的其他值操作（如对字符串 APPEND）不改变 TTL：过期规则只在 SET 覆盖、PERSIST、重新 EXPIRE 这几个明确动作上变化。
- SETRANGE、APPEND 等局部写同样不清 TTL，只有整体覆盖（SET 不带 KEEPTTL）才清。

```bash
SET k "v1" EX 100
SET k "v2"            # 覆盖写入，TTL 被清除
TTL k                 # 返回 -1
SET k "v3" EX 100
RENAME k k2           # TTL 随键迁移
TTL k2                # 返回剩余秒数
```

```text
OK
OK
(integer) -1
OK
OK
(integer) 98
```

> 「缓存突然不过期了」的事故多数源于覆盖写入：先 SET key value EX 3600，后续刷新缓存时又执行了不带 EX 的 SET，TTL 被无意清除，键变成永不过期的脏数据。刷新缓存的代码应统一带上 EX 或 KEEPTTL。

**速记**：覆盖写入默认清 TTL，KEEPTTL 才保留；改名带 TTL，重设是覆盖不是叠加。



### 键空间操作命令

#### RENAME 与 RENAMENX：重命名及其连带效应

**RENAME**：把键改名为新键名，语法为 RENAME key newkey，O(1) 完成。**RENAMENX**：仅当新键名不存在时才改名，是防覆盖版本。

- 源键不存在时 RENAME 直接报错；新键已存在时 RENAME 无声覆盖，没有任何提示。
- RENAMENX 新键已存在返回 0 且不做任何修改，改名成功返回 1。
- 过期时间随键迁移：改名后剩余 TTL 原样保留，值与类型同样原样迁移。
- 重命名只改字典中的键名映射，不搬移值对象，因此大键改名也是瞬间完成。
- 主从之间重命名以命令形式原样传播，从库会执行同样的改名动作，保持两侧键名一致。
- RENAMENX 在集群与单机上的语义一致，仅集群多出同哈希槽的前置校验。
- 线上做键迁移时，SCAN 配合 RENAME 逐键改名是常见的灰度手段，注意改名会让旧键名立即失效。
- 重命名是排查「键名写错但数据还在」场景的直接手段，不必删了重写。

```bash
SET old:counter 100 EX 60
RENAME old:counter new:counter    # 改名
TTL new:counter                   # TTL 随键迁移
SET target "occupied"
RENAMENX source:1 target          # 目标已存在，拒绝改名
```

```text
OK
OK
(integer) 59
OK
(integer) 0
```

> RENAME 是覆盖语义，new 键会被无声抹掉，上线前必须确认目标键名未被占用，或改用 RENAMENX；集群模式下源键与目标键必须位于同一哈希槽，跨槽改名直接报错，集群的键分布规则详见第 22 章。

> 另一个细节：对同一个键执行 RENAME k k 是合法操作，等价于无动作，正常返回 OK。

**速记**：RENAME 改名兼覆盖，RENAMENX 加了保险；TTL 与值都跟着键走。



#### RANDOMKEY 与 DBSIZE：随机抽样与键量统计

**RANDOMKEY**：从当前库随机返回一个键名，键的内容不动，空库返回 nil。**DBSIZE**：返回当前库的键总数。

- RANDOMKEY 基于随机抽样实现，不保证均匀覆盖整个键空间，想有多样性需要多抽几次。
- DBSIZE 时间复杂度 O(1)，读取的是数据库内部维护的计数器，不是遍历统计。
- 与 SCAN 统计相比，DBSIZE 是即时的权威总数；SCAN 受重复与游标影响，只适合估算。
- 两者都不阻塞，可放心在生产执行，是巡检脚本与监控面板的常客。
- RANDOMKEY 返回的是键名而不是值，查看值需要再用 GET 等命令按类型读取。
- RANDOMKEY 常被用于抽样检查键的命名质量，配合 TYPE 能快速了解键空间里存了什么。
- DBSIZE 与 INFO keyspace 中的键数一致，后者还能分库查看，巡检脚本两边可交叉核对。

```bash
RANDOMKEY     # 随机看一个键名
DBSIZE        # 当前库键总数
```

```text
"user:profile:1001"
(integer) 1024
```

> 观察 DBSIZE 的走势是判断异常的最快手段：短时间陡增多半是未设 TTL 的循环写入，陡降则可能是误执行了删除或清库命令，配合监控告警可以在事故初期就发现问题。

**速记**：RANDOMKEY 抽一个看名，DBSIZE 一眼看总量，都是 O(1) 不阻塞。



#### SELECT：切换逻辑库

**SELECT**：切换当前连接使用的逻辑库，默认实例提供 16 个逻辑库，编号 0 到 15，默认使用 0 号。

- 每个逻辑库是独立的键空间，同名键在不同库中互不干扰。
- SELECT index 成功返回 OK，编号越界报错；配置项 databases 可调整库数量，默认 16。
- 切换是连接级别的状态：一个客户端连接切到 3 号库，不影响其他连接各自所在的库。
- 集群模式只允许使用 0 号库，SELECT 1 直接报错。
- 从库复制的是整个实例的数据，多库结构在主从间原样保留，但集群不存在多库。
- SELECT 的状态跟着连接走，连接池中的连接可能处于不同库，ioredis 等客户端默认总在 0 号库工作，详见第 30 章。
- 生产环境多数团队只用 0 号单库，用键前缀代替多库做业务隔离。
- 单库为主的原因：键管理命令（SCAN、FLUSHDB）与监控指标都围绕单键空间更简单，多库反而增加心智负担。
- 从库对 SELECT 没有额外限制，只读操作在任意库都能执行，限制只来自集群拓扑。

```bash
SELECT 3
SET user:1 "only-in-db3"
SELECT 0
EXISTS user:1    # 0 号库看不到 3 号库的键
```

```text
OK
OK
OK
(integer) 0
```

> 多库隔离的历史包袱要在选型阶段想清楚：依赖 SELECT 1 的老代码迁移到集群会直接失败；多业务共实例时，分实例比分库更清晰——独立内存、独立淘汰策略、独立故障域。集群的相关约束详见第 22 章。

**速记**：默认 16 库 SELECT 切，切换只影响当前连接；集群只认 0 号库，生产以单库加前缀为主。



### 键的元信息查询

#### OBJECT：查看编码与空闲时间

**OBJECT**：内省命令，用于查看键值对象底层的实现细节，语法为 OBJECT subcommand key，常用子命令是 ENCODING 与 IDLETIME。

- OBJECT ENCODING key：返回值底层的编码，如 int、embstr、raw、listpack、skiplist；同一键的编码会随值的变化自动转换，编码机制详见第 13 章。
- OBJECT IDLETIME key：返回键自最后一次被读写以来的空闲秒数，用于冷热数据分析。
- OBJECT FREQ key：LFU 淘汰模式下返回访问频率计数。
- OBJECT REFCOUNT key：返回引用计数，主要与共享整数对象池相关。
- OBJECT HELP：列出全部子命令说明，忘了语法时的现场速查入口。
- OBJECT IDLETIME 返回 0 表示键刚被访问过，热键的空闲时间通常很小，冷键可达数天。
- 查看键的内存占用不用 OBJECT，而是用 MEMORY USAGE key，二者互补。
- OBJECT 的子命令都是 O(1) 读操作，可在生产安全执行，不会触碰值内容。

```bash
SET num 100
OBJECT ENCODING num    # 整数编码
SET num "a long string value more than forty-four bytes in total length"
OBJECT ENCODING num    # 编码随值自动转换
OBJECT IDLETIME num    # 空闲秒数
```

```text
OK
"int"
OK
"raw"
(integer) 0
```

> OBJECT IDLETIME 是只读的，查询本身不会刷新空闲计数；但在 LFU 淘汰策略下该命令不可用，应改用 OBJECT FREQ。空闲数据可指导冷键清理的决策，与内存淘汰策略的联动详见第 15 章。

**速记**：ENCODING 看底层实现，IDLETIME 看冷热，LFU 模式换用 FREQ；查内存占用用 MEMORY USAGE。



### 键的遍历方式

#### KEYS：全量遍历的阻塞风险

**KEYS**：返回当前库中匹配模式的所有键，语法为 KEYS pattern，时间复杂度 O(N)，N 为全库键总数。

- 通配符支持：星号匹配任意长度，问号匹配单个字符，方括号匹配字符集。
- Redis 单线程执行命令，KEYS 遍历期间整个实例停止响应，千万级键可造成数秒级卡顿。
- 遍历过程无法中途取消，客户端断开也不会让服务端停止扫描。
- KEYS 的返回结果不排序，顺序由字典遍历决定，不能依赖其稳定性。
- 生产环境禁止在业务代码与人工排障中使用 KEYS，临时排查应改用 SCAN。
- KEYS 在测试库的小数据量下用起来顺手，但「习惯」会带到生产，工具层应直接封装 SCAN。
- 与 KEYS 同族的全量读取还有 SMEMBERS、HGETALL 等，它们阻塞的是单键内部的大集合，大 key 排查详见第 29 章。
- 慢查询日志会记录 KEYS 的执行耗时，是发现线上误用的重要线索，详见第 29 章。

```bash
KEYS user:*        # 匹配全部 user 前缀键，键量大时极度危险
KEYS user:?001     # 问号匹配单字符
```

```text
1) "user:profile:1001"
2) "user:cart:1001"
1) "user:1001"
```

> [!WARNING]
> **警告内容**：KEYS 在键量大的实例上执行一次就可能引发全站超时，且无法中途取消。任何环境都不应把 KEYS 写进业务代码，代码评审与上线检查应将其列入黑名单。

**速记**：KEYS 一次梭哈全库，O(N) 必阻塞，线上只认 SCAN。



#### SCAN：渐进式遍历

**SCAN**：基于游标的渐进式遍历命令，语法为 SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]，每次调用只扫描一小批，全程不阻塞。

- 游标机制：从游标 0 开始，每次返回新游标与一批键；新游标为 0 表示遍历完成。
- COUNT count：提示本次扫描的哈希桶数量，默认 10，返回的键数可能多于或少于该值。
- MATCH pattern：服务端模式过滤，等价于 KEYS 的通配符。
- TYPE type（6.0 起）：按值类型过滤。
- 完整性保证：整个遍历期间始终存在的键，一定会被返回到至少一次。
- 集合类内部的遍历用 SSCAN、HSCAN、ZSCAN，游标语义与 SCAN 一致。
- 单次调用耗时可控，键量越大可适当调大 COUNT 减少往返次数，但要压住单次延迟。
- 遍历中途的游标可以记录下来，任务中断后从上次游标继续，是断点续扫的基础。
- SCAN 在集群下只能遍历单节点，全集群遍历要逐节点扫描，节点的键分布规则详见第 22 章。
- Node 中 ioredis 的 scanStream 封装了游标循环，详见第 30 章。

```bash
SCAN 0 MATCH user:* COUNT 100
# 返回新游标与一批键，客户端拿新游标继续调用，直到游标回到 0
SCAN 3417 MATCH user:* COUNT 100
SCAN 0 TYPE hash COUNT 50    # 6.0 起可按类型过滤
```

```text
1) "0"
2) 1) "user:profile:1001"
   2) "user:cart:1001"
```

> [!IMPORTANT]
> **重要内容**：SCAN 不保证不重复——同一个键可能在多批中返回多次，客户端必须做幂等处理（例如用 Set 去重）；遍历期间被新增或删除的键也可能不被返回，这是用准确性换不阻塞的代价。

> redis-cli 提供 --scan 参数，在客户端侧封装游标循环并直接输出全部匹配键，比手写 SCAN 循环更省事，但仍要警惕结果集过大。
> MATCH 的过滤发生在返回前，扫描量仍与全库成比例，COUNT 不要盲目调大。

**速记**：游标 0 起终 0，COUNT 是提示不是配额，重复要幂等，不阻塞是最大价值。



### 删除与清库命令

#### DEL 与 UNLINK：同步删除与异步删除

**DEL**：同步删除一个或多个键，语法为 DEL key [key ...]，返回实际删除的个数。**UNLINK**（4.0 起）：异步删除，主线程只把键从键空间摘除，内存回收交给后台线程。

- DEL 的时间复杂度与被删键的大小相关：删除百万元素的 list 或 hash 时，释放内存的工作会阻塞主线程。
- UNLINK 的摘除动作 O(1)，真正的对象释放在后台线程完成，几乎瞬间返回。
- 这一设计源于 lazyfree 思想：把「不可中断的释放」改为「可延迟的回收」。
- 配置 lazyfree-lazy-user-del yes 后，DEL 命令本身也走异步路径；lazyfree-lazy-expire 则让过期删除异步化。
- UNLINK 的返回值语义与 DEL 完全一致，代码迁移几乎零成本。
- 返回值是被删除键的个数，传入的键不存在时不计入，也不报错，天然幂等。
- 主从之间删除同样以命令形式传播，从库同步执行删除，保持数据一致。
- UNLINK 摘除后键立即不可见，业务视角下与 DEL 的生效时机没有区别，区别只在内存回收的节奏。

```bash
DEL user:ghost     # 同步删除
UNLINK big:hash    # 异步删除大键
DEL user:ghost no:here    # 不存在的键不计入，不报错
```

```text
(integer) 1
(integer) 1
(integer) 0
```

> [!CAUTION]
> **注意内容**：删除大 key 前先评估规模，对百万元素级别的键直接执行 DEL 会造成明显卡顿；不确定大小时应先用 MEMORY USAGE 查看内存占用，再决定用 DEL 还是 UNLINK。

**速记**：DEL 同步、UNLINK 异步；大 key 删除一律先想 UNLINK，lazyfree 把回收移出主线程。



#### FLUSHDB 与 FLUSHALL：清库命令及其治理

**FLUSHDB**：清空当前连接所在的逻辑库；**FLUSHALL**：清空实例的全部逻辑库；两者都是不可恢复的毁灭性操作。

- 二者均支持 ASYNC 选项（4.0 起）：主线程立即返回，清空工作交给后台线程。
- 不带 ASYNC 时同步执行，大实例会长时间阻塞，等同于一次全实例停服。
- FLUSHDB 只清当前库，FLUSHALL 清全部库，多库实例上二者的破坏范围差异巨大。
- 误执行没有任何回收站可救，只能靠 RDB 或 AOF 备份恢复，持久化机制详见第 17、18 章。
- 生产治理手段：通过 rename-command 把命令改名或置空禁用，配合权限与审计，详见第 31 章。
- 集群模式下 FLUSHALL 只作用于当前节点，全集群清空需按节点逐一执行，详见第 22 章。
- 巡检脚本还应监控 DBSIZE 的骤降，它是清库误操作最早的可观测信号。
- 与 FLUSH 相比，逐键 UNLINK 的清理方式慢但可控，误删范围有限，是更稳妥的批量清理替代。

```bash
FLUSHDB ASYNC      # 异步清空当前库
FLUSHALL ASYNC     # 异步清空全部库，影响面更大
```

```text
OK
OK
```

> [!CAUTION]
> **注意内容**：FLUSHALL 影响整个实例的全部业务，执行前必须二次确认目标实例与环境影响；许多团队直接在配置里将其改名封印，只保留运维专用的执行通道。

**速记**：FLUSHDB 清本库、FLUSHALL 清全库，ASYNC 异步、生产改名封印。
