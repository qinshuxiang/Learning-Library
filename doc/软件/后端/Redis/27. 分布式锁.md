## 分布式锁

**分布式锁**：是把锁状态放在多个进程共同访问的共享存储（Redis、ZooKeeper、etcd）上、由共享存储做唯一裁判的跨进程互斥机制——谁能原子地写入锁键谁就持锁，Redis 中它就是一个带过期时间的字符串键。

- 本章先讲动机：单机锁为什么管不到多实例，分布式锁的三性要求是什么。
- 再讲正确姿势：SET NX EX 一条命令原子加锁、Lua 脚本校验后释放，两处姿势不对都会酿成事故。
- 然后是三个进阶问题：锁超时与看门狗续期、可重入锁、加锁失败后的等待与自旋策略。
- 接着展开 Redlock 算法与 Kleppmann 和 antirez 的论战，划清 Redis 锁的安全边界。
- 最后落到工程实践：Node 侧最小实现、与 ZooKeeper 和 etcd 的选型对比、使用建议与替代方案。
- 阅读前提：第 16 章的单线程模型解释了单条命令为何原子，第 23 章的 Lua 脚本是释放与续期姿势的基础，建议先行。

### 分布式锁的定义与存在理由

#### 什么是分布式锁

**分布式锁**：是运行在多进程、多机环境下，借助**共享存储**实现的跨进程互斥机制，保证同一时刻只有一个客户端能进入临界区操作共享资源。

- 单机环境里，进程内互斥锁（如 Java 的 synchronized、Node 单线程的天然串行）只对**本进程**有效。
- 服务一旦多实例部署，各实例内存彼此独立，进程内锁**互相不可见**，这就是单机锁失效的根源。
- 负载均衡会把同类请求分发到**不同实例**，每个实例都以为只有自己在改数据，锁各自成立，数据却被并发写坏。
- 典型事故是库存超卖：两个实例各自用进程内锁保护同一条库存记录，锁互不干扰、双双生效，库存却被**双重扣减**。
- 分布式锁把锁状态放到**所有实例都能访问的第三方存储**（Redis、ZooKeeper、etcd）上，以共享状态仲裁互斥。
- 第三方存储是**唯一的裁判**：谁能在它那里原子地写入锁键，谁就获得临界区的进入权。
- 在 Redis 中，锁就是**一个带过期时间的字符串键**：加锁即原子写入该键，释放即删除该键。
- Redis 锁因实现轻、性能高，成为工程中最常用的分布式锁方案，代价是主从切换时可能丢锁。
- 判断一个需求是否真需要分布式锁：问「多个实例同时做这件事会怎样」，若答案是数据被写坏或重复处理，就需要。
- 常见场景清单：定时任务防重复执行、库存防超卖、接口防并发重入、分布式环境下的互斥计算。

```bash
# 锁键命名惯例：业务前缀 + 资源类型 + 资源标识，粒度越小互斥越精准
SET lock:order:1001 tokenA NX EX 30
SET lock:stock:sku:889 tokenB NX EX 30
SET lock:task:report:20260907 tokenC NX EX 30
```

锁键命名是最容易被忽视的细节：粒度过粗会让不相干的请求互相等待，粒度过细则会产生大量零散键。惯例是把锁落在具体资源标识上，让互斥范围与业务临界区严格对齐。

> 分布式锁并不是一种新的数据结构，而是一套**约定出来的协议**：用共享存储的原子命令加锁、校验持有者、按期释放或续期。
> 谁遵守这套协议，谁就获得互斥保护；任何一环绕过协议，锁就形同虚设。
> 它解决的是**跨进程互斥**问题，而不是进程内的线程安全，两者不互相替代。

**速记**：分布式锁＝**公共存储上的互斥协议**，本质是一个会过期的键。



#### 分布式锁的三性要求

**分布式锁三性**：是评价一个分布式锁实现是否可靠的三条底线，即**互斥性、避免死锁、高可用**。

- **互斥性**：任意时刻，同一个锁最多只有一个客户端持有，这是锁的本体功能，也是一切讨论的前提。
- **避免死锁**：持有者崩溃、断网之后，锁最终一定能被释放，不能永久卡死其他客户端，通常靠过期时间保证。
- **高可用**（容错性）：锁服务本身不能是脆弱单点，节点宕机、主从切换后锁服务仍能继续工作。
- 三者按序排查：先看互斥是否成立，再看宕机能否自愈，最后看锁服务自身的可用性。

三性不是并列的口号，而是有依赖顺序的：互斥是目的，防死锁是安全底线，高可用是工程前提；讨论任何锁实现，都要三问齐备。

- 实现层面的对应物：互斥靠原子命令（SET NX），防死锁靠 EX 或 PX 过期时间，高可用靠哨兵或集群部署。
- 面试与设计评审常问「你的锁为什么不会死锁」，答案就落在过期时间与续期机制这两点上。
- 一把「永远不过期的锁」实现起来最简单，却把防死锁的责任完全丢给调用方，是最危险的设计。
- 三性也可当作 review 清单：互斥怎么保证、宕机谁来释放、锁服务挂了怎么办，三问都答得上才算过关。

> 三性之间存在内在张力：为了高可用把锁复制到多节点，主从异步复制就可能在切换瞬间丢失锁，破坏互斥；互斥与高可用**不可兼得**，只能按业务取舍。
> Redlock 争议的本质正是这对矛盾的放大，详见本章 Redlock 一节。

**速记**：三性＝**互斥、不死锁、锁服务自己活得住**。



### 正确的加锁姿势

#### 为什么不用 SETNX 单命令

**SETNX 的缺陷**：它只能在键不存在时写入，**无法在同一条命令里设置过期时间**，与过期配合就出现原子性缺口。

- 早期写法是两条命令：先 SETNX 加锁，再 EXPIRE 设过期。
- 两条命令之间**不是原子的**：若客户端在 SETNX 之后、EXPIRE 之前宕机，锁就没有过期时间，永远无法释放。
- 没有过期时间的锁，其他客户端只能无限死等，这就是**死锁**，且只能人工介入清理。
- 所谓人工介入，就是 SCAN 定位到无过期的锁键后手删，被动且有风险。
- 补救思路的历史演进：先是用 Lua 脚本把两条命令包成原子操作，后来 SET 命令直接扩展了参数。
- 现在的 SET 命令扩展参数（NX、EX、PX）从命令层面根治了该问题，无需再写脚本。

判断两个操作是否原子，标准是「在 Redis 看来它们之间能否插入其他命令」。两条独立命令之间，任何客户端的命令都可能插队，这正是宕机窗口的来源；一条命令内部则永远不会被打断。

```bash
# 错误示范：两条命令之间存在宕机窗口
SETNX lock:order:1001 clientToken
# 若进程恰在此处崩溃，EXPIRE 永远执行不到，锁变成永久死锁
EXPIRE lock:order:1001 30
```

```lua
-- 旧版补救：用 Lua 把加锁与过期包成原子操作
if redis.call("SETNX", KEYS[1], ARGV[1]) == 1 then
    redis.call("EXPIRE", KEYS[1], ARGV[2])
    return 1
end
return 0
```

> [!CAUTION]
> **注意内容**：加锁与设置过期时间必须原子完成。任何先加锁、后补过期的两步写法，都存在第一步成功、第二步失败的窗口，一旦该窗口内宕机，就会留下一把删不掉的死锁。

**速记**：两条命令**非原子**，宕机窗口即死锁，一条 SET 才是正解。



#### SET NX EX 一条命令原子加锁

**标准加锁命令**：SET 键 值 NX EX 秒数，在**一条命令内原子完成**「不存在才写入 + 设置过期时间」两个动作。

```bash
# 正确写法：原子加锁，30 秒后自动过期，返回 OK 表示抢锁成功
SET lock:order:1001 f3a9c2e8-7b1d-4c2a-9e5f-8d0a6b3c1e2f NX EX 30
# 锁已被他人持有时返回 nil，抢锁失败
SET lock:order:1001 anotherToken NX EX 30
# 毫秒版：PX 后接毫秒数，程序中更常用
SET lock:order:1001 someToken NX PX 30000
```

- **NX**：Not eXists，键不存在时才设置，即抢锁；键已存在则返回 nil，抢锁失败。
- **EX 30**：过期时间 30 秒，保证持有者宕机后锁最终自动释放，是避免死锁的关键。
- **PX**：以毫秒为单位设置过期，是 EX 的毫秒版，可避免秒级取整误差。
- 命令返回 OK 表示加锁成功，返回 nil 表示锁已被他人持有，客户端据此分支处理。
- NX 与 EX（或 PX）可交换顺序，但值必须写在键之后，过期时间必须紧跟 EX 或 PX。
- 命令超时后的重试是安全的：NX 保证只有第一次写入生效，后发的重试只会拿到 OK 或 nil，不会破坏互斥。
- 该命令是本章后续一切机制（释放、续期、Redlock）的基石，必须一步到位。

> NX、EX 是 SET 命令的扩展参数，不是独立命令；先 SETNX 再补 EXPIRE 是历史遗留写法，新代码一律使用带参数的 SET。
> 读老代码时见到 SETNX 加 Lua 补救的组合，应识别出它是在给旧版本 Redis 打补丁。
> 参数写法的记忆锚点：SET 命令把「设值、设过期、设条件」三件事收进一条命令，任何拆开写法都要警惕。

**速记**：**SET 键 值 NX EX 秒**，抢锁加保险一条命令搞定。



#### uniqueValue 与持有者标识

**uniqueValue**：加锁时写入锁键的**持有者唯一标识**，通常用 UUID 加机器与线程信息拼接生成，是后续安全释放与续期的凭证。

- 它的作用是回答「这把锁是谁的」：释放锁时只有 value 与自己的 uniqueValue 一致才允许删除。
- 每次加锁都要**重新生成**，绝不能所有请求共用一个固定字符串。
- 推荐格式为 UUID 加机器标识加线程 ID，保证跨进程、跨机器唯一。
- 若 value 写成固定值（如 1），就无法区分持有者，误删他人锁将不可避免。
- 续期逻辑同样依赖它：续期脚本先比对 uniqueValue，匹配才延长过期时间。
- 它相当于锁的「私钥」，只在本端内存中流转，不出现在锁键名里。

uniqueValue 的生命周期与锁严格绑定：加锁时生成、持锁期间不变、释放后即作废。复用旧值会让过期锁的幽灵持有者通过校验，比没有校验更隐蔽。

```bash
# Node 侧生成持有者标识：UUID 加进程号
# uniqueValue = randomUUID() + ":" + process.pid
SET lock:order:1001 5f8ac2e8-7b1d-4c2a-9e5f-8d0a6b3c1e2f:3215 NX PX 30000
```

> [!IMPORTANT]
> **重要内容**：value 必须是本次加锁独有的随机值。它是持有者身份的唯一凭证，释放与续期逻辑都依赖它做比对；把它写成常量，等于给全系统发了同一把钥匙。

**速记**：value 存 **UUID 指纹**，谁加的锁谁才删得掉。



### 释放锁的正确姿势

#### 为什么释放锁必须验证持有者

**释放锁必须先验证持有者**：删除锁之前先确认锁里存的 uniqueValue 是自己的，否则会**误删他人的锁**，互斥性随之被击穿。

```bash
# 第 0 秒：客户端 A 加锁，过期时间 30 秒
SET lock:order:1001 uuidA NX EX 30
# 第 31 秒：A 的业务还没跑完，锁已过期；客户端 B 抢到锁
SET lock:order:1001 uuidB NX EX 30
# 第 32 秒：A 终于跑完，不加验证直接 DEL，删掉的是 B 的锁
DEL lock:order:1001
# 第 33 秒：客户端 C 趁虚而入，此刻 B 与 C 同时认为自己持锁
SET lock:order:1001 uuidC NX EX 30
```

- 推演中 A 的 DEL 不做验证，删掉的是 B 的锁，B 名存实亡。
- 随后 C 加锁成功，B 与 C 同时持锁，互斥性被破坏。
- 整条事故链的根源：锁过期易主后，A 仍以为自己是持有者。
- 业务执行时间逼近或超过锁过期时间时，该场景出现的概率显著上升。
- 验证持有者本质上是在锁协议里补上「所有权」这一环，让删除操作有据可依。
- 该推演也解释了为什么「锁过期后业务还在跑」是事故高发区：易主后旧持有者的每一步操作都可能伤及新持有者。
- 判断标准很简单：释放动作若依赖「我记得我持有锁」而非「锁里记着我持有锁」，就不可靠。
- 排查这类事故的第一步，是比对被删锁键在删除时刻的实际 value 与各客户端日志里的 uniqueValue。

> 即便改成先 GET 比对、再 DEL 两步，仍存在**非原子窗口**：比对通过后锁恰好过期、他人接管，随后的 DEL 照样误删。
> 彻底解法是把比对与删除放进**同一段 Lua 脚本**，详见下节与第 23 章。
> 换个角度看：验证持有者把「释放」从一步操作变成两步判断，正是多出的这一步换来了安全。

**速记**：锁可能易主，**删前必须对暗号**。



#### 释放锁的 Lua 原子实现

**Lua 原子释放**：把「读取比对 uniqueValue」与「删除锁」写进同一段 Lua 脚本，由 Redis 单线程**一次性执行完毕**，中间不会插入其他命令。

- KEYS[1] 传锁键名（如 lock:order:1001），ARGV[1] 传本端 uniqueValue。
- 比对成功返回 1，锁被释放；不一致或键不存在返回 0，说明锁已易主或已过期，不做任何删除。
- Redis 执行 Lua 脚本期间**阻塞其他命令**，因此 GET 与 DEL 之间不存在并发窗口。
- 返回值应被调用方检查：返回 0 时不必重试删除，只记录日志即可，锁本来就不归自己管。
- 该脚本同样适用于续期场景的变体，只是把 DEL 换成 PEXPIRE。
- 脚本内容务必版本化入库：线上脚本的任何改动都要走评审，误改比对逻辑等于打开误删的大门。

为什么单线程能保证原子：Redis 命令执行是单线程排队模型，Lua 脚本作为一个整体排在队列里，执行期间不接受任何其他命令，等效于命令级互斥。

```lua
-- 释放锁：仅当持有者身份匹配时才删除
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```bash
# 首次加载并缓存脚本，返回脚本摘要
SCRIPT LOAD "释放锁脚本源码"
# 之后用摘要调用，网络传输量更小
EVALSHA 脚本摘要 1 lock:order:1001 uuidA
```

> [!IMPORTANT]
> **重要内容**：释放锁禁止裸用 DEL。任何不校验持有者的删除逻辑，在锁过期易主之后都会误删他人锁；Lua 比对加删除是这个问题的唯一正确解法。

**速记**：GET 比对再 DEL，**包进 Lua 才原子**。



### 锁超时与续期

#### 锁超时与业务超时的冲突

**超时两难**：锁的过期时间必须**人为预估**，而业务执行时长**无法精确预知**，两者不匹配就会出事故。

- 过期时间设得太短：业务还没跑完锁先过期，其他客户端趁虚而入，互斥被破坏。
- 过期时间设得太长：持有者宕机后，其他客户端要**白等很久**才能拿到锁，吞吐受损。
- 业务时长天然会波动：数据库慢查询、下游接口抖动、GC 停顿，都可能让平时 1 秒的操作变成 40 秒。
- 长尾延迟不可消除，因此「锁失效」不是小概率事件，而是设计时必须正视的常态。
- 该矛盾无法靠把时间设准来根治，因为预估永远可能失准，只能靠**续期机制**缓解。
- 出问题的时间点总是「业务执行到一半、锁恰好到期」，这个交界处是分布式锁最脆弱的地方。

下面用时间轴把两个方向的失败各演一遍，帮助把抽象的两难落到具体的秒数上。

```bash
# 同一把锁在时间轴上的两种危险
# t=0   SET lock ... NX EX 30，加锁成功
# t=29  业务仍在执行，一切正常
# t=30  锁过期，互斥保护悄然消失
# t=31  客户端 B 进入临界区，A 与 B 并发
# 若把过期改成 300 秒来规避：
# t=1   A 宕机，锁却还在
# t=299 其余客户端全部干等，吞吐归零
```

- 两难的本质是「锁的有效期」与「任务的执行期」互相不可见：锁不知道业务跑完没有，业务不知道锁还活着没有。
- 后续的进阶设计（续期、可重入、Redlock），本质上都是在给这个两难打补丁。
- 工程上建议过期时间取「业务正常耗时的数倍」作为起点，再交给续期机制兜底，而不是反过来。

> 场景：给锁设 30 秒过期，扣库存链路平时 3 秒跑完；某天数据库抖动拖到 32 秒，锁在第 30 秒失效，另一实例进入临界区，出现并发扣减。
> 两个错误方向（设短设长）都不安全，说明问题不在数值本身，而在「静态过期时间」这个机制。

**速记**：过期时间是**猜的**，业务时长是**跑的**，猜的兜不住跑的就要续期。



#### 看门狗续期机制

**看门狗（Watchdog）**：加锁成功后启动一个**后台定时任务**，周期性检查锁是否仍由自己持有，是则把过期时间**续满**，直到业务执行完毕才停手。

- 工作节奏：Redisson 默认锁超时 30 秒，看门狗每 10 秒（三分之一周期）检查并续期一次。
- 取三分之一周期是为了留足容错：单次续期失败还有两次补救机会。
- 续期动作本身也要**原子**：Lua 脚本先比对 uniqueValue，匹配才执行 PEXPIRE 续期，防止给别人的锁续命。
- 停止条件有两个：业务正常结束主动释放；进程宕机则无人续期，锁按最后期限自动过期。
- 续期失败要谨慎处理：连续多次续期失败说明锁已易主或连接异常，应中止临界区操作而不是硬撑。
- 注意启用条件：Redisson 仅在**未显式指定 leaseTime** 时才启动看门狗，手动指定了超时时间就退化为普通定长锁。
- Node 侧可用 setInterval 定时调续期 Lua 脚本实现简版看门狗，见本章工程实践一节。
- 看门狗的本质是用「持续的活性证明」替代「一次性的时间预估」，把静态过期变成动态租约。

```lua
-- 续期：身份匹配才延长过期时间
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
    return 0
end
```

```bash
# 加锁后持续观察 TTL，可看到看门狗在续命
TTL lock:order:1001
# (integer) 23
# 约 10 秒后再查，TTL 被拉回 30 附近
TTL lock:order:1001
# (integer) 29
```

> [!WARNING]
> **警告内容**：Redisson 主从切换丢锁场景——客户端 A 在主节点加锁成功，锁尚未通过异步复制到达从节点时主节点宕机，哨兵把从节点提升为新主，客户端 B 到新主上加锁成功，A 与 B 同时持锁。看门狗与 Lua 释放都防不住这一层丢失，因为问题出在**异步复制**本身。对互斥要求极高的场景，需改用 Redlock、ZooKeeper 等方案，或引入 fencing token 兜底（哨兵机制详见第 21 章）。

**速记**：看门狗**定时续命**，业务不停锁不过期，进程一死锁自然过期。



### 进阶锁特性

#### 可重入锁的 Hash 实现

**可重入锁**：同一个持有者对同一把锁**再次加锁不会被拦**，用重入计数记录加了几层，解锁同样次数后才真正释放。

- 用 Hash 结构承载：锁键为 key，**field 存持有者标识**（uniqueValue），**value 存重入计数**。
- 加锁逻辑（Lua）：field 不存在则 HSET 计数为 1 并设置过期；field 与自己相同则 HINCRBY 加 1；否则返回失败。
- 解锁逻辑（Lua）：field 匹配则 HINCRBY 减 1，计数减到 0 才 DEL 整个键。
- Hash 结构让锁键从单个字符串值扩展为「持有者加计数」两个维度，原子性仍靠 Lua 保证。
- 每次重入成功后都应重置过期时间，防止外层逻辑尚未跑完、内层刚进入就过期。
- 典型场景：持锁方法内部递归调用自身，或多个持锁方法层层嵌套调用同一把锁。
- 与字符串锁相比，Hash 锁还能顺便容纳更多元数据（如加锁时间、来源机器），为排查问题留下线索。

与字符串实现的取舍：Hash 方案的脚本更长、分支更多，出错的代价也更大；业务里若没有真实的重入需求，简单的字符串锁反而更可靠，不为功能完整而引入复杂度。

```lua
-- 可重入加锁：KEYS[1] 锁键，ARGV[1] 持有者标识，ARGV[2] 过期秒数
if redis.call("EXISTS", KEYS[1]) == 0 then
    redis.call("HSET", KEYS[1], ARGV[1], 1)
    redis.call("EXPIRE", KEYS[1], ARGV[2])
    return 1
end
if redis.call("HGET", KEYS[1], ARGV[1]) then
    redis.call("HINCRBY", KEYS[1], ARGV[1], 1)
    redis.call("EXPIRE", KEYS[1], ARGV[2])
    return 1
end
return 0
```

```lua
-- 可重入解锁：计数减到 0 才真正删除锁键
if redis.call("HGET", KEYS[1], ARGV[1]) then
    local count = redis.call("HINCRBY", KEYS[1], ARGV[1], -1)
    if count <= 0 then
        redis.call("DEL", KEYS[1])
    end
    return 1
end
return 0
```

> 辨析：不可重入锁在递归调用或同一持有者多次进入临界区时会**自己把自己锁死**——第二次加锁永远在等自己释放。
> 反过来，重入计数也要求**解锁次数与加锁次数严格配对**，多解一次就会提前释放锁，殃及后续持有者。
> Hash 锁的正确姿势是把加解锁脚本当成一个整体来测试：只测加锁不测解锁，等于只验收了半个锁。

**速记**：Hash 里**field 认人、value 计数**，同门可再进，出门要对账。



#### 等待与自旋策略

**自旋等待**：加锁失败后不立刻放弃，而是**间隔一段时间重试**，直到拿到锁或达到重试上限。

- 失败处理有三种取向：**直接失败**（快速返回并降级）、**自旋重试**（轮询抢锁）、**阻塞等待**（由锁框架基于发布订阅通知唤醒，Redisson 采用）。
- 轮询间隔不能为 0：无间隔的密集重试等于对 Redis 发起自我攻击，白白消耗连接与 CPU。
- 常用节奏：固定间隔（如 50 至 200 毫秒）起步，再配合**指数退避**逐步拉长间隔。
- 必须设置**重试上限或总等待超时**，避免业务线程无限滞留在抢锁循环里。
- 更优雅的等待方式是订阅锁键的过期或删除事件再发起尝试，但事件通知不可靠，工程上仍以轮询加退避为主。
- 抢锁循环里每次重试都用带 NX 的 SET 原子尝试，不要先 GET 判断再 SET（两步非原子）。
- 自旋应发生在异步环境里（如 Promise 循环），Node 单线程下绝不能写同步忙等，会卡死事件循环。
- 排队场景可偏向公平性：按请求先后错开初始间隔，减少惊群，但实现复杂度上升。

等待策略要与业务语义匹配：对时效敏感的请求宁可快速失败降级，对不能错过的任务则值得长等待，不要用统一的默认值套所有场景。

```js
// 自旋抢锁：指数退避 + 总等待上限
async function acquireWithRetry(lockKey, ttlMs, maxWaitMs) {
  let interval = 50;
  const deadline = Date.now() + maxWaitMs;
  while (Date.now() < deadline) {
    const lock = await acquireLock(lockKey, ttlMs);
    if (lock) {
      return lock;
    }
    await sleep(interval);
    interval = Math.min(interval * 2, 500);
  }
  return null;
}
```

> 热点键抢锁务必加退避与上限：数百个请求围着同一把锁自旋时，固定小间隔轮询会把 Redis 打出高负载，指数退避加最大等待时间是最省心的组合。
> 同时临界区代码要尽量短，拿到锁尽快做完，缩短他人等待。
> 阻塞等待（发布订阅唤醒）比轮询优雅，但代价是引入订阅连接与不可靠通知，工程上常作为轮询的补充而非替代。

**速记**：失败别硬怼，**退避、限次、超时**三件套。



### Redlock 与多节点锁

#### Redlock 算法流程

**Redlock（红锁）**：是 antirez 提出的**多节点分布式锁算法**，在 N 个完全独立的 Redis 实例上依次加锁，以**多数派**是否成功判定最终是否获得锁。

- 前提：部署 N 个（推荐 5 个）互相独立、没有主从关系的 Redis 实例。
- 步骤一：记录起始时间，用相同的 uniqueValue 依次向 N 个实例执行 SET NX PX 加锁。
- 步骤二：若成功拿到**多数派**（超过 N/2，5 节点即 3 个），且总耗时小于锁的有效期，判定加锁成功。
- 步骤三：加锁失败（不足多数派或耗时超限），则向**所有实例**发起释放，无论该实例上加锁是否成功。
- 有效期的实际可用部分要扣掉获取耗时与时钟漂移：漂移量按实例数估算，防止「刚拿到就过期」。
- 多数派设计的目的：即便个别实例宕机或网络分区，只要过半存活，锁服务整体仍可判定。
- 实例之间必须完全独立，任何主从或集群关系都会让算法退化为单点复制模型。
- uniqueValue 在全部实例间保持同一个，释放时才能在所有节点上准确清除自己的锁。

多数派判定让 Redlock 在个别实例故障时仍能工作，但它默认各实例时钟大体一致，且判定过程本身消耗时间，这些正是后续争议的入口。

```js
// Redlock 流程伪代码
async function redlock(key, uniqueValue, ttlMs) {
  const start = Date.now();
  let success = 0;
  for (const node of nodes) {
    if ((await node.set(key, uniqueValue, "PX", ttlMs, "NX")) === "OK") {
      success += 1;
    }
  }
  const drift = ttlMs * 0.01 * nodes.length;
  const elapsed = Date.now() - start;
  const valid = success > nodes.length / 2 && elapsed + drift < ttlMs;
  if (!valid) {
    await unlockAll(key, uniqueValue);
  }
  return valid;
}
```

> Redlock 的释放必须覆盖全部实例：哪怕某实例上从未加锁成功，也要发释放命令，防止只清理一半留下半把锁。
> 算法的代价是 N 倍的网络开销与明显更高的实现复杂度。

**速记**：**过半成功才算赢**，失败全体释放，时间要扣漂移。



#### 时钟漂移争议与论战结论

**Redlock 之争**：围绕 Redlock 是否安全，Martin Kleppmann 与 antirez 展开了一场著名论战，焦点是**互斥性与可用性的取舍**。

- Kleppmann 的质疑：长时间 GC 停顿或进程暂停会让持有者「人还在、锁已丢」，自己感知不到锁已过期易主。
- 他还指出 Redlock 依赖各节点本地时钟，**时钟跳变**可能同时放行两个持有者。
- 他给出的出路是 fencing token：锁服务每次发放**单调递增令牌**，存储层拒绝旧令牌的写入，用下游校验兜底锁失效。
- antirez 的回应：时钟问题可通过运维手段约束（不让时钟随意跳变），异步复制的丢锁窗口 Redlock 已用多数派缓解。
- antirez 还认为 fencing token 把一致性压力转嫁给存储层，并非所有存储都支持。
- 论战的实际产物：大家意识到锁的正确性有**安全性与活性**两个维度，两者在异步模型下无法同时完美。
- 社区主流结论：Redlock 复杂度高、正确性论证仍有争议；**单实例加高可用架构（哨兵或集群）已覆盖绝大多数业务场景**。
- 只有互斥性要求极端严格时，才考虑 Redlock、ZooKeeper 或 fencing token（哨兵与集群分别详见第 21 章、第 22 章）。
- 论战的另一共识：任何锁都只是「大概率互斥」，关键数据的一致性最终要靠下游的幂等与校验兜底。
- fencing token 依赖存储层支持条件写入（如 CAS），数据库与 etcd 支持良好，纯 Redis 原生则需要用 Lua 模拟。

fencing token 的适用前提是存储层支持按版本拒绝旧写入；若下游存储不具备该能力，令牌只能沦为日志线索，失去防护意义。对多数业务而言，论战带来的实用结论只有一条：锁负责缩小并发窗口，数据正确性靠幂等与校验收尾，两层防线缺一不可。

```js
// fencing token 思想：令牌单调递增，存储层校验
const token = await lockService.acquireWithToken(resource);
// 每次成功加锁发放的 token 递增，如 34、35、36
await storage.write(resource, data, token);
// 存储层拒绝 token 小于已见最大值的写入，旧持有者的迟到写入被挡下
```

> [!NOTE]
> **提醒内容**：论战没有绝对胜者，它澄清的是一个选型原则——先问业务能承受多小的锁失效概率，再决定为此付出的复杂度。绝大多数系统里，锁偶发失效的代价远小于引入 Redlock 的运维与理解成本。

**速记**：之争的本质是**安全与可用的权衡**，多数场景单实例加高可用即可。



### 工程实践与选型

#### Node 侧最小可用实现

**Node 最小实现**：用 ioredis 串起「原子加锁、Lua 释放、定时续期」三件事，即可得到一把生产可用的简版分布式锁。

```js
const Redis = require("ioredis");
const { randomUUID } = require("crypto");

const redis = new Redis();

const RELEASE_LUA = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end`;

const RENEW_LUA = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
  return 0
end`;

async function acquireLock(lockKey, ttlMs) {
  const uniqueValue = randomUUID();
  const res = await redis.set(lockKey, uniqueValue, "PX", ttlMs, "NX");
  if (res !== "OK") {
    return null;
  }
  const renewTimer = setInterval(async () => {
    await redis.eval(RENEW_LUA, 1, lockKey, uniqueValue, String(ttlMs));
  }, Math.floor(ttlMs / 3));
  return { lockKey, uniqueValue, renewTimer };
}

async function releaseLock(lock) {
  clearInterval(lock.renewTimer);
  const res = await redis.eval(RELEASE_LUA, 1, lock.lockKey, lock.uniqueValue);
  return res === 1;
}
```

```js
// 调用侧：务必用 try finally 保证释放
const lock = await acquireLock("lock:order:1001", 30000);
if (!lock) {
  return failFast();
}
try {
  await deductStock();
} finally {
  await releaseLock(lock);
}
```

- 加锁：SET 键 值 PX 毫秒 NX 一条命令原子完成，失败返回 null，调用方按退避策略重试或直接降级。
- 续期：拿锁成功即启动 setInterval，按三分之一周期用 Lua 比对后 PEXPIRE，是最简看门狗。
- 释放：先清掉续期定时器，再用 Lua 验证持有者身份后删除，杜绝误删他人锁。
- 锁键命名建议带业务前缀与资源标识，如 lock:order:1001，粒度到具体资源而不是整个业务。
- 生产化方向：换 redlock 类库支持多节点、复用连接并接入错误监控、用 try finally 保证临界区无论成败都会走释放。
- 代码评审时重点盯三处：加锁是否带 NX 与过期、释放是否走 Lua 校验、临界区是否被 try finally 包住。
- 联调阶段可用 redis-cli 的 MONITOR 观察锁命令流，确认加锁、续期、释放的时序符合预期。

三件事与三种机制的对应关系值得背下来：加锁靠 SET PX NX 的原子性，释放靠 Lua 的所有权校验，续期靠看门狗的三分之一周期；任何一件缺失，锁都不完整。

> 续期定时器与业务应放进 try finally 或等价的清理逻辑：业务抛异常时若忘记 clearInterval，定时器会持续给一把本该交还的锁续期，造成幽灵持锁。
> 该简版实现也未处理网络分区下的续期失败重试，严格场景应改用成熟的开源库。

**速记**：**PX NX 拿锁、Lua 验证释放、定时器续命**，三件齐了才算一把锁。



#### 与 ZooKeeper 和 etcd 锁的对比

**三种实现的分野**：Redis 锁靠**过期时间加原子命令**，ZooKeeper 锁靠**临时顺序节点加监听**，etcd 锁靠 **Raft 一致性加租约**，性能与一致性各占一端。

- **Redis**：性能最高、实现最轻，一把锁就是一条命令的事；但主从异步复制使切换瞬间可能丢锁，整体偏 AP。
- **ZooKeeper**：客户端创建临时顺序节点抢占，序号最小者持锁，watch 前驱节点实现公平等待。
- ZooKeeper 的会话断开后临时节点自动消失，天然防死锁；强一致偏 CP，但写入要过半确认，吞吐低、运维重。
- **etcd**：基于 Raft 协议的强一致存储，用 lease 租约绑定锁，租约到期自动释放；与 Kubernetes 生态天然亲和。
- 三者防死锁的机制不同：Redis 靠过期时间，ZooKeeper 靠会话存活，etcd 靠租约续期，本质都是「持有者失联即释放」。
- 等待唤醒机制也不同：Redis 原生靠轮询，ZooKeeper 的 watch 与 etcd 的 watch 都能推送变更，等待体验更好。
- 选型维度一：性能敏感、能容忍极小概率锁失效，选 Redis。
- 选型维度二：互斥性是硬要求、吞吐要求不高，选 ZooKeeper 或 etcd。
- 选型维度三：技术栈已在 Kubernetes 生态内，etcd 是顺路的选择。
- 迁移成本也要纳入考量：锁的接口是键名加唯一值，三套实现的加锁语义相近，切换主要落在客户端库与部署运维上，业务代码改动有限。
- 小团队首选 Redis 锁：团队已有 Redis 运维经验，为一把锁引入 ZooKeeper 集群往往得不偿失。

> 不要孤立地比较性能数字：Redis 的高性能部分来自它对一致性的妥协（异步复制），ZooKeeper 与 etcd 的低吞吐部分来自强一致的开销。
> 三者是同一根轴上的不同落点，没有免费的强一致，选型先问业务能接受哪头的短板。

**速记**：**Redis 快而偏 AP，ZK 与 etcd 强一致而慢**，按业务容忍度选。



#### 使用建议与替代方案

**使用分布式锁的首要原则**：**能不用则不用**，锁是并发控制里成本最高的手段，多数场景存在更轻的替代。

- 优先用数据库手段：唯一索引防重复插入，并发重复请求直接被数据库拒绝。
- 乐观锁版本号防并发更新：update 时带上版本条件，更新失败即说明有并发冲突。
- 状态机条件更新防状态跳变：如 update 订单 set status = 已支付 where status = 待支付，天然幂等。
- 必须用锁时，**锁粒度要小**：锁到业务键级别（如 lock:order:1001 而不是笼统的 lock:order），临界区代码尽量短。
- 过期时间、重试上限、等待超时都要显式设定，不依赖框架默认值。
- 释放逻辑必须放在 finally 中，续期与释放必须校验持有者身份。
- 评估互斥失效的业务代价：代价可承受就用 Redis 单实例加高可用；不可承受再上 Redlock、ZooKeeper 或 fencing token。
- 上线前做故障演练：杀掉持锁进程、断开主节点，验证锁能否按预期释放与接管。

判断技巧：如果锁只是为了防重复提交，唯一索引通常就够；如果是为了同一资源同一时刻只能被一个任务处理，才真正需要互斥锁。

> [!TIP]
> **建议内容**：把「为什么需要这把锁」写进设计文档。大量所谓的分布式锁需求，本质是唯一索引或乐观锁就能解决的并发去重；先压测数据层方案，确认不够用再引入锁，代码与运维复杂度都会显著下降。

**速记**：**先数据库后锁，锁要小、要限时、要 finally**。
