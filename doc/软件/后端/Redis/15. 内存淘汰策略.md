## 内存淘汰策略

### 内存淘汰的认识

Redis 自动删键有两条彼此独立的路径：过期删除清理到期键，内存淘汰为满内存腾路。二者都发生在服务端、对客户端透明，但服务的目标完全不同：一个管理键的生命周期，一个管理实例的容量水位。本章聚焦后者，先厘清定义、配置与触发时机，再逐一拆解八种策略，最后深入近似 LRU 与 LFU 两种核心算法的实现细节。学完本章应能回答三个问题：什么时候开始淘汰、在哪些键里挑、凭什么挑这个而不是那个。

#### 内存淘汰的定义与过期删除的区别

**内存淘汰（Eviction）**：当 Redis 已使用内存达到 maxmemory 上限时，按配置的策略挑选并删除部分键，为新写入让出空间的自保机制。

- 触发前提是 **used_memory 达到 maxmemory**：内存未触顶时，淘汰流程永远不会启动。
- 删除对象是**尚未过期的活键**：被淘汰的键不是因为到期，而是因为「占了地方」被选中牺牲。
- 淘汰的目的是让**写入类命令继续执行**：腾出空间后，SET、LPUSH 等命令才能正常返回。
- 具体删谁由 **maxmemory-policy** 配置决定，默认值 noeviction 表示谁也不删、直接拒绝写入。
- 被淘汰的键**一去不回**：客户端不会有任何通知，应用层只能靠写入成功这一事实确认空间已腾出。
- 淘汰是**服务端自治行为**：不需要任何客户端指令参与，Redis 在命令执行的间隙自行完成。
- 淘汰单位是**整个键**：不管该键是 String 还是 Hash，删除都连带其全部数据。
- 淘汰与删除效果等同：被淘汰的键空间立刻回收，与手动执行 DEL 没有区别。
- 淘汰不区分数据类型与价值：策略眼里只有元数据特征，没有业务语义。

**过期删除管到期，内存淘汰管满了**：两者都会自动删键，但动机、对象、时机完全不同，是两套独立机制（过期删除详见第 14 章）。

- **过期删除**：只针对设置了过期时间的键，在键**到期之后**执行，删的是已失效的键，属于生命周期管理。
- **内存淘汰**：在**内存满**之后执行，删的键**并没有过期**，属于容量管理。
- 触发条件不同：过期删除看**时间**（惰性检查与定期抽样），淘汰看**空间**（命令执行前的内存检查）。
- 候选范围不同：过期删除只看带 TTL 的键；淘汰按策略可能覆盖**全部键**。
- 执行频率不同：过期删除随访问与后台周期持续发生；淘汰只在触顶后的命令间隙发生。
- 二者不排斥：一个键可能先到期被删，也可能没等到期就被淘汰，还可能一直活到被手动删除。

```bash
# 对比演示：键未过期，但内存触顶后仍可能被淘汰
127.0.0.1:6379> SET hotkey somevalue
OK
127.0.0.1:6379> PERSIST hotkey
(integer) 1
# hotkey 没有 TTL，在 allkeys 系列策略下依然是淘汰候选
```

注意 PERSIST 移除 TTL 后，键就从 volatile 系列的候选中除名，但在 allkeys 系列中不受影响——TTL 状态只决定过期删除的资格，不影响 allkeys 策略下的候选资格。

> 常见误区是把「键消失了」都归因于过期：即使实例里所有键都未设置 TTL，内存触顶后淘汰照样会发生。反过来，过期键的清理也不依赖内存是否触顶。整体关系可概括为**先删过期的、再谈淘汰的**——过期机制持续清理死键，淘汰机制只在内存告急时对活键动刀，两套机制的详细行为可对照第 14 章复习。

**速记**：满了才动手，删的是**没过期的键**；过期看**时间**，淘汰看**空间**，两套机制互不替代。



#### maxmemory 配置、0 的语义与触发时机

**maxmemory**：设定实例可使用内存上限的配置项，是整个淘汰机制的总开关，达到上限后策略才开始工作。

- 配置方式两种：redis.conf 中写入 maxmemory 512mb，或运行期执行 CONFIG SET maxmemory 512mb。
- **默认值为 0**：64 位系统下表示不限制内存，Redis 用多少申请多少；32 位系统下隐含约 3GB 上限。
- 比较对象是 **used_memory**：它包含数据、缓冲区与分配器碎片等 Redis 层面的开销，实际可存数据量略低于 maxmemory。
- used_memory_rss 是操作系统视角的物理内存占用，与 used_memory 的差值反映碎片与分配器行为，调优时应两者同看。
- maxmemory 不宜设得过大：要给复制缓冲区、AOF 缓冲等留出余量，避免数据占比过高挤爆物理内存。
- 也不宜设得过小：频繁触顶意味着频繁淘汰，命中率下降、CPU 开销上升，缓存质量随之劣化。
- 单位支持 k、mb、gb 等写法，配置文件里不写单位则按字节解释。
- 触顶判定带少量容错：临近上限时 Redis 就可能提前启动淘汰，避免写入命令直接撞墙。

```bash
# 查看与设置内存上限
CONFIG GET maxmemory
CONFIG SET maxmemory 512mb
# 查看实际内存水位与两项核心指标
INFO memory
# used_memory: 536870912
# used_memory_rss: 610271232
# 差值反映碎片与分配器开销
```

触发时机是**执行每条命令之前**：Redis 处理任何客户端命令时先检查内存水位，若已触顶且该命令可能增大内存占用，就先执行一轮淘汰流程——5.x 及更早版本由 **freeMemoryIfNeeded** 函数承担，6.0 起重构为 **performEvictions**（源码位于 evict.c），语义不变。

- 淘汰流程结束后按结果分派：腾出了空间则命令照常执行，腾不出则按策略决定放行还是报错。
- 检查粒度是**命令级**而非定时级：不存在后台定时触发的淘汰，一切围绕命令执行展开。
- 因此淘汰耗时会计入该命令的延迟：采样与比较开销落在触发它的那条命令头上，这是 maxmemory-samples 调参的代价来源。
- 短时间大量写入触顶时，可能连续多轮淘汰，表现为写入延迟毛刺，监控上应关注淘汰量的突增。

命令级触发也意味着空闲实例不会自我瘦身：没有命令就没有淘汰，内存水位停在触顶状态，直到下一个命令到来才继续腾挪。

> [!IMPORTANT]
> **重要内容**：64 位环境下默认 maxmemory 为 0 意味着完全不设防——内存只增不减，写入量一旦超出物理内存，可能触发操作系统交换甚至 OOM 杀进程，且此时淘汰策略完全没有上场机会。生产环境必须显式设置 maxmemory，并同步配置 maxmemory-policy，让触顶后的行为可预期。

**速记**：maxmemory 是**天花板**，默认 0 等于**没装天花板**；每条命令**进门先称重**，超了先淘汰再干活。



### 八种淘汰策略

maxmemory-policy 共有八个取值，按候选范围分为 volatile 与 allkeys 两族，外加一个不淘汰的 noeviction。每个取值回答两个问题：在哪些键里挑（作用域），挑谁（淘汰标准）。逐一细讲之前，先给一张总览清单：

- **noeviction（不淘汰，作用于全部键）**：内存触顶后拒绝一切增内存的写入，读照常。
- **volatile-lru（限有过期时间的键，按空闲时长淘汰）**：挑最久没人访问的带 TTL 键删除。
- **volatile-lfu（限有过期时间的键，按访问频次淘汰，4.0 引入）**：挑访问频次最低的带 TTL 键删除。
- **volatile-random（限有过期时间的键，随机淘汰）**：随机挑一个带 TTL 的键删除。
- **volatile-ttl（限有过期时间的键，按剩余存活时间淘汰）**：挑最快到期的带 TTL 键删除。
- **allkeys-lru（作用于全部键，按空闲时长淘汰）**：从所有键里挑最久没人访问的删除。
- **allkeys-lfu（作用于全部键，按访问频次淘汰，4.0 引入）**：从所有键里挑频次最低的删除。
- **allkeys-random（作用于全部键，随机淘汰）**：从所有键里随机挑一个删除。

记清单时抓两条主线：候选范围看首词，volatile 认 TTL、allkeys 认全部；淘汰标准看后缀，lru 比空闲、lfu 比频次、random 抽签、ttl 看到期。清单会背不如主线会推。

#### noeviction：默认策略，写报错读正常

**noeviction（不淘汰，作用于全部键）**：内存触顶后不删除任何键，所有可能导致内存增长的写入命令直接报错，读命令与释放内存的命令照常执行。

- 是 Redis 的**默认策略**：不显式配置 maxmemory-policy 时的行为即为此。
- 写入报错：SET、LPUSH、HSET 等命令返回 OOM command not allowed when used memory > 'maxmemory'。
- **读命令正常**：GET、ZRANGE 等只读操作不受影响，实例仍可提供完整的查询服务。
- **释放内存的命令不受限**：DEL、UNLINK、EXPIRE、HDEL 等只会腾空间，触顶时依然可执行。
- 部分特殊命令也在放行之列：如 SCRIPT LOAD 这类不增数据内存的命令仍可执行。
- 报错信息固定为 OOM 开头，便于应用层统一识别与告警。
- 适用场景：把 Redis 当**不能丢数据的存储**而非缓存，宁可报错也不允许自动删数据。
- 选择它意味着**容量责任转移给应用层**：必须配套内存监控、告警与扩容预案。
- 与写入方的契约要提前约定：应用收到 OOM 报错后是降级、重试还是熔断，需在架构层设计好。
- 若配合过期删除使用，noeviction 下写入压力可通过主动清理过期键部分缓解，但不能根治。

```bash
127.0.0.1:6379> SET k1 v1
(error) OOM command not allowed when used memory > 'maxmemory'
127.0.0.1:6379> GET k1
(nil)
127.0.0.1:6379> DEL k1
(integer) 0
```

> 报错是**面向客户端的显式失败**，应用层必须捕获并处理；这与其余策略「悄悄删数据、写入成功」形成鲜明对比——一个是写入失败但数据完整，一个是写入成功但旧数据丢失。选 noeviction 就要靠监控内存水位提前扩容，不能等报错了才行动。

**速记**：noeviction **宁拒不删**，写入报 OOM、读取照常，数据完整性靠应用层兜底。



#### volatile-lru 与 volatile-lfu：在过期键中挑最久不用与最不常访问

**volatile-lru 与 volatile-lfu**：都只把设置了过期时间的键作为淘汰候选，区别在挑选标准——前者挑最近最少使用的，后者挑访问频次最低的。

- **volatile-lru（候选为有过期时间的键）**：挑空闲时间最长、最久没人访问的键淘汰，依据是对象记录的最近访问时钟。
- **volatile-lfu（候选为有过期时间的键，4.0 引入）**：挑一段时间内访问频次最低的键淘汰，依据是对象记录的对数计数器。
- 两者都复用 redisObject 中的 lru 元数据字段存储访问信息（详见第 13 章）。
- 挑选采用**近似算法**而非精确排序，原理见本章近似 LRU 与 LFU 两节。
- 两种策略的候选集**动态变化**：随键的过期与写入，带 TTL 的键集合时刻变动，候选范围随之伸缩。
- 共同前提：实例中必须存在带 TTL 的键，否则候选集为空、触发兜底行为。
- 若实例中绝大多数键都带 TTL，volatile 系列与 allkeys 系列的实际表现会非常接近。
- 两者在 4.0 之前不存在：老版本升级到 4.0 及以上才可用 lfu 系列策略。
- 会话类键的访问模式适合 LFU：热会话高频读写，冷会话低频维持，区分度自然拉开。
- 与 allkeys 系列的差异只在**圈地**：比较算法完全相同，圈的是全部键还是带 TTL 的键。
- 候选集小时采样质量下降：带 TTL 的键太少时，5 个样本的代表性明显弱于全库场景。
- 适合「多数键可丢、少数键保命」的实例：丢的是会话与临时数据，保的是无 TTL 的核心键。

```bash
# 典型的 volatile 场景：会话键设 TTL，配置键不设
127.0.0.1:6379> SET session:1001 "uid=1001" EX 3600
OK
127.0.0.1:6379> SET app:config "v2.3" 
OK
127.0.0.1:6379> OBJECT IDLETIME session:1001
(integer) 5
# 配置 volatile-lru 后，触顶时只会在 session:* 这类键里挑
```

> 辨析两种「不热门」：LRU 看的是**最近一次访问距今多久**，侧重时间局部性；LFU 看的是**一段时间内访问有多勤**，侧重频次稳定性。一次偶发访问就能让键在 LRU 眼里变「新鲜」，却几乎不会改变它在 LFU 眼里的低频次——这正是后面 LRU 与 LFU 对比一节的伏笔。

**速记**：volatile 只在**带 TTL 的键**里挑，lru 淘**最久没碰**，lfu 淘**最少光顾**。



#### volatile-random 与 volatile-ttl：在过期键中随机挑与挑最快到期

**volatile-random 与 volatile-ttl**：同样只把设置了过期时间的键作为候选，前者随机挑、后者挑剩余存活时间最短的，都不关心访问热度。

- **volatile-random（候选为有过期时间的键）**：从候选集中随机挑一个键淘汰，不参考任何访问历史，实现与决策成本最低。
- **volatile-ttl（候选为有过期时间的键）**：挑剩余存活时间（TTL）最短的键优先淘汰，即「快到期的先走」。
- volatile-ttl 的方向与过期删除一致，但动手时机更早：键还没到期就可能被淘汰。
- volatile-random 的淘汰质量全凭运气，可能刚写入的热键立即被删。
- 剩余存活时间可用 TTL 或 PTTL 命令观察，便于排查 volatile-ttl 的淘汰选择。
- 两种策略都不需要维护访问元数据的比较逻辑，实现上比 lru、lfu 系列简单。
- 若带 TTL 的键本来就都是短命键，volatile-ttl 的效果近似于「替过期删除提前收尾」。
- volatile-ttl 也不保证全局最优：它只在采样的候选里比 TTL，不是全库排序。
- 随机与 TTL 导向的策略同样受淘汰池影响：历史候选会留档参与下一轮比较。
- 键的剩余寿命分布越均匀，volatile-ttl 的「先到期先淘汰」优势越不明显。

```bash
127.0.0.1:6379> SET tmp:a "1" EX 30
OK
127.0.0.1:6379> SET tmp:b "2" EX 3600
OK
127.0.0.1:6379> TTL tmp:a
(integer) 28
127.0.0.1:6379> TTL tmp:b
(integer) 3598
127.0.0.1:6379> PTTL tmp:a
(integer) 27500
# volatile-ttl 触顶时会优先淘汰 tmp:a，因为它最快到期
```

> volatile-ttl 并不是过期删除的变体：它可能在剩余 1 秒与剩余 1 小时的键之间选择删掉前者，但**不会碰**无 TTL 的键。也不要指望 volatile-random 公平——随机就是随机，没有任何保护机制，被抽中的键无论多热都会被删。

**速记**：random 靠**抽签**，ttl 挑**最快到期**，两者都只在带 TTL 的键里动手。



#### allkeys-lru 与 allkeys-lfu：在全部键中按热度淘汰

**allkeys-lru 与 allkeys-lfu**：把实例中**全部键**一视同仁作为候选，按热度挑人——前者挑最近最少使用的，后者挑频次最低的，是最常用的缓存策略。

- **allkeys-lru（候选为全部键）**：无论是否设置 TTL，从所有键中挑最久未访问的淘汰。
- **allkeys-lfu（候选为全部键，4.0 引入）**：从所有键中挑访问频次最低的淘汰。
- 键是否设 TTL **不影响候选资格**，只影响它何时被过期删除（详见第 14 章）。
- 缓存语义最贴合：缓存数据本就允许丢失，用热度决定去留最符合访问规律。
- 生产环境绝大多数「纯缓存」实例建议在此二选一，算法细节见后文近似 LRU 与 LFU 两节。
- 与 volatile 系列相比，allkeys 系列**永远有键可选**：候选集是全部键，不会出现空集退化。
- 混合负载下要小心：少量长期不访问的重要键，在 allkeys-lru 眼里就是头号淘汰对象。
- 若实例同时承担缓存与持久数据两种角色，应优先考虑拆分成两个实例再分别选型。
- allkeys-lru 是社区使用率最高的策略，绝大多数缓存教程的默认推荐即为此。
- 若从 volatile-* 切到 allkeys-*，注意原先「受 TTL 保护」的键从此也进入候选。

```bash
# 纯缓存实例的典型配置组合
# 混合负载请先拆实例，再分别选型
# 命中率观察入口：INFO stats
CONFIG SET maxmemory 4gb
CONFIG SET maxmemory-policy allkeys-lfu
```

> 场景辨析：如果业务里有少量**不可丢弃**的键（如配置项、长期状态），它们也会进入 allkeys 系列的候选池，可能被淘汰。这类需求应拆实例或改用 noeviction，而不是指望热点数据永远占满淘汰名单之外的名额。

**速记**：allkeys **人人有份**，lru 淘最久、lfu 淘最懒，缓存首选，混合负载慎用。



#### allkeys-random：在全部键中随机淘汰

**allkeys-random（候选为全部键）**：从实例中的所有键里随机挑一个淘汰，不看访问历史、不看 TTL、不看剩余存活时间，是八种策略中决策成本最低的一个。

- 淘汰完全随机，**没有公平性保证**：刚写入的键与存在已久的键被选中概率相同。
- 适合键被访问的概率**高度均等**、不存在明显热点、且任何键丢了都不心痛的场景。
- 实践中很少使用：真实负载几乎总有冷热之分，随机淘汰的命中率代价高。
- 与 volatile-random 的唯一区别是候选范围从「带 TTL 的键」扩大到「全部键」。
- 好处是**零元数据依赖**：不需要比较空闲时长或频次，也不需要淘汰池参与。
- 若键集合近乎均匀访问且量大，随机淘汰省下的比较开销也有可观收益。
- 淘汰不产生任何元数据维护：它不需要访问时钟也不需要计数器，切换到它也不必重建什么。
- 若从 lru 系列切到它，访问元数据仍在但不再参与决策，切回时无需预热。
- 观察它的行为很简单：多触发几轮淘汰，被删键看不出任何规律，这正是随机的特征。
- 它也遵循「命令前检查、触顶才淘汰」的统一触发时机，与其余策略一致。
- 缓存命中率对它最敏感：一旦出现热点，命中率会随淘汰显著下滑，是最早的报警信号。
- 它与 noeviction 恰好构成两个极端：一个全删、一个全不删，其余策略都在两者之间找平衡。
- 若键都无 TTL 且改用 allkeys-random，效果与 volatile-random 的兜底形成对照：前者有得删，后者直接报错。

> 若业务负载经实测确实冷热均等（如纯均匀散列的临时映射表），allkeys-random 可以省去维护与比较访问元数据的开销；但这是罕见的特例，不是默认选择。选型拿不准时，先选 lru 系列再观察命中率，比赌随机更稳妥。

**速记**：allkeys-random **纯抽签**，谁中谁走，实践中基本不用。



#### volatile-* 系列无过期键时的兜底行为

**volatile-* 系列的兜底行为**：当实例中不存在任何设置过期时间的键时，volatile-lru、volatile-lfu、volatile-random、volatile-ttl 四种策略都退化为 noeviction，触顶后写入报错而不是乱删。

- 退化的原因是**候选集为空**：四种策略都不允许越权删除无 TTL 的键，无键可选时只能放弃淘汰。
- 兜底表现与 noeviction 完全一致：写入返回 OOM 错误，读命令正常。
- 退化是**静默发生的**：配置上写着 volatile-lru，实际行为却可能是拒绝写入，极易误判。
- 排查思路：先抽查键是否带 TTL，或确认业务是否遗漏了过期时间设置。
- 解决方式：给可丢弃的键补设 TTL，或直接改用 allkeys-* 系列。
- 反过来讲，若给全部键都设了 TTL，volatile-* 与 allkeys-* 的候选范围就完全重合。
- 判断覆盖程度可用 SCAN 抽样统计带 TTL 键的比例，比例过低就该警惕。
- 兜底行为不需要任何配置开关：它是 volatile-* 系列的内置语义，无法关闭。
- 监控上可用 evicted_keys 指标区分：volatile-* 下该值长期为零且写入报错，多半就是候选集为空。

```bash
# 抽查键是否带 TTL，-1 表示永不过期
127.0.0.1:6379> TTL app:config
(integer) -1
127.0.0.1:6379> TTL session:1001
(integer) 3542
127.0.0.1:6379> SCAN 0 COUNT 100
1) "0"
# 若实例里全是 -1，volatile-* 系列已静默退化为 noeviction
```

> [!NOTE]
> **提醒内容**：volatile-* 的「只在过期键里挑」是硬约束而非优先级提示——它永远不会把无 TTL 的键纳入候选。打算使用 volatile-* 系列时，必须确认带 TTL 的键覆盖了全部可淘汰数据，否则淘汰机制形同虚设、实例会以 OOM 报错的方式罢工。

**速记**：volatile **无米下锅**时，一律**装成 noeviction**，配置要与 TTL 覆盖情况配套检查。



### 近似 LRU 的实现

Redis 的 lru 系列策略并不维护精确的访问顺序，而是用「记录时间戳加随机采样比较」的近似算法，用可接受的精度损失换取内存与速度。理解这个取舍，才能正确解读 maxmemory-samples 的调参逻辑，也才能明白为什么淘汰结果偶尔「不像 LRU」。

#### 为什么 Redis 只做近似 LRU：随机采样与淘汰池

**近似 LRU（Approximated LRU）**：Redis 不维护全局访问链表，只在每个对象里记录最近访问时间，淘汰时随机采样若干键、取其中空闲时间最长的删除，用精度换内存与速度。

- 精确 LRU 需要**全局双向链表**：每次访问都要把对应节点移到表头，淘汰时从表尾取人。
- 链表为每个键增加**前后指针开销**，且每次读访问都要移动节点，高频读场景下耗时与内存双输。
- Redis 的取舍：对象只在 redisObject 的 lru 字段里记**一个时间戳**（详见第 13 章），访问时顺手刷新，几乎零额外成本。
- 淘汰时**随机采样、局部比较**：不追求全局最优，只保证删掉的不是最近活跃的键。
- 采样数量由 **maxmemory-samples** 控制，默认 5，值越大越接近精确 LRU，CPU 消耗也越大。
- **Redis 3.0 引入淘汰池（Eviction Pool）**：大小为 16 的候选池，每轮采样的键与池中历史候选合并排序，空闲时间最长的一批反复留档、逐轮积累。
- 淘汰池让**跨轮次的历史样本参与竞争**，用同样的采样数获得明显更优的淘汰效果。
- 淘汰池同样服务于 lfu 与 ttl 等策略的候选比较，并非 LRU 独有。
- 采样是**放回式**的：同一批键可能在不同轮次被反复采到，淘汰池的留档缓解了这一点。
- 淘汰一轮可能删多个键：单次腾不出足够空间时，Redis 会连续执行多轮采样淘汰。
- 空闲时长的度量来自 lru 时钟，时钟按秒或分钟级更新，秒级以下不精确。
- 采样发生在淘汰流程内部：平时不采样，只在触顶需要腾空间时才动。
- 淘汰池只保存有限历史：池满后新样本按空闲时长竞争入池，最旧的候选被挤出。

```bash
# 提高采样数以换取更接近精确 LRU 的效果
CONFIG SET maxmemory-samples 10
# 观察当前采样设置
CONFIG GET maxmemory-samples
```

理解淘汰池之后，maxmemory-samples 的含义更准确：它限制的是每轮新采样的数量，而实际参与比较的是新样本与池内历史候选的并集，因此默认 5 也能获得接近更大采样的效果。

> 权衡结论：官方测试表明默认采样 5 个键时，淘汰结果已能稳定保留最热的那批键，设为 10 已非常接近真实 LRU，设为 3 则更快但精度下降。淘汰池缓存的是**候选键的引用与其空闲度量**，池中键在被选中前仍正常提供服务，被真正选中时才执行删除。近似算法偶尔会淘汰掉本应保留的键，这是设计内的代价而非缺陷。

**速记**：不建链表，**每键一个时间戳**，淘汰时**抽样比谁最久没用**，samples 调精度，3.0 起候选入池逐轮再比。



#### OBJECT IDLETIME 观察键的空闲时长

**OBJECT IDLETIME**：返回键自最近一次被访问以来的空闲秒数，是直接观察 LRU 淘汰依据的诊断命令。

```bash
127.0.0.1:6379> SET k1 v1
OK
127.0.0.1:6379> OBJECT IDLETIME k1
(integer) 12
127.0.0.1:6379> GET k1
(nil)
127.0.0.1:6379> OBJECT IDLETIME k1
(integer) 0
```

- 输出以秒为单位：普通读、写访问都会刷新键的 lru 时钟，IDLETIME 随之归零重新累计。
- **只看不碰**：OBJECT IDLETIME 本身不会刷新 lru 字段，连续两次执行会看到读数持续增长。
- 用途：排查「哪些键总被淘汰」——采样淘汰的是空闲最久的键，逐一观察即可验证策略行为。
- 配合实验：构造访问序列后改小 maxmemory-samples，可直观看到近似算法的误淘汰现象。
- 大批量排查时可用 SCAN 遍历加 IDLETIME 组合，找出长期无人访问的冷键。
- 注意 IDLETIME 反映的是**空闲时长**而非累计访问次数，与 LFU 的度量维度完全不同。
- 时间精度有上限：lru 时钟按秒或分钟级更新，秒级读数仅供参考。
- 只读命令不会刷新时钟的例外情况需留意：OBJECT 系列命令本身就是设计为不触碰元数据。
- 用它验证近似 LRU 时，应挑多个键对比读数，单键读数说明不了采样整体行为。

该命令在 LFU 模式下仍可执行，但读数含义已变；同样地，LRU 模式下执行 OBJECT FREQ 会直接报错。两个诊断命令与两种淘汰模式一一对应，用错即失真。

> [!CAUTION]
> **注意内容**：在 LFU 模式下 OBJECT IDLETIME 的读数基于分钟级的 ldt 时间戳，粒度粗、语义已变，不能当作精确空闲时间使用；观察键的热度应改用 OBJECT FREQ，且后者要求 maxmemory-policy 已切到 lfu 系列，否则命令直接报错。

**速记**：IDLETIME 看**多久没人碰**，只看不碰不清零，GET 一碰就归零，LFU 模式下改看 FREQ。



### LFU 淘汰的实现

LFU 系列策略（4.0 引入）复用 redisObject 中原有的 24 位 lru 字段存储频次信息，不为 LFU 新增任何内存。它的两个核心问题——🔥 频次怎么涨、热度怎么凉——分别由对数计数器与衰减机制回答。

#### LFU 的存储结构：24 位 lru 字段的拆分

**LFU 的存储基础**：把 redisObject 中原用于 LRU 时钟的 24 位 lru 字段一拆为二——16 位分钟级时间戳 ldt 加 8 位对数计数器 logc。

- **ldt（16 位，Last Decrement Time）**：记录最后一次计数器调整的时间，以分钟为精度截取 unix 时间戳的低 16 位，约 45 天回绕一次。
- **logc（8 位，Logarithmic Counter）**：对数计数器，取值 0 到 255，是访问频次的对数近似。
- 键被访问时 logc **按概率递增**而非加一：计数器越大，再涨一格的概率越低，这是 Morris 计数器思想。
- 新键进入 LFU 模式时 logc 初值为 5（LFU_INIT_VAL），避免初生键立即成为头号淘汰对象。
- LRU 与 LFU 共用同一字段：切换策略时，同一块内存按新语义重新解释，历史数据需要重新积累。
- 拆分方案的好处是**零额外内存**：改动只发生在既有字段的解释方式上，每个键不增一字节。
- 回绕问题影响有限：ldt 只用于衰减的时间差结算，45 天内的差值足够支撑衰减判断。
- 位段拆分属于对象编码层面的设计，redisObject 的整体结构详见第 13 章。
- 16 位与 8 位的切分比例是刻意为之：频次只需对数近似，8 位足够；时间要支撑衰减结算，16 位保 45 天窗口。
- 与 LRU 模式的 lru 字段不同，LFU 模式下该字段不再表示「最近访问时间」。

```bash
# 切到 LFU 后观察键的计数值
CONFIG SET maxmemory-policy allkeys-lfu
CONFIG SET maxmemory 4gb
# 复用 lru 字段，切换后旧数据按新语义解读
127.0.0.1:6379> OBJECT FREQ hotkey
(integer) 87
```

> 用 8 位表达远超 255 的访问量级：计数器已到 100 时，再涨一格的概率只有约百分之一量级，持续访问一百万次也就把计数推到 255 附近。精度随数值增大而下降，但「谁更热」的相对排序依然成立，而相对排序正是淘汰决策需要的全部信息。

**速记**：24 位一拆二，**16 位记时间、8 位记频次**，越热越难更热，初值 5 护新键。



#### 对数计数器与 lfu-log-factor、lfu-decay-time

**logc 计数器的涨与落**由两个配置项共同调节：lfu-log-factor 决定增长多难，lfu-decay-time 决定消退多快，二者默认值分别为 10 与 1。

- **lfu-log-factor（增长难度）**：访问发生时，计数器递增的概率为 1 除以 ((logc − 5) × lfu-log-factor + 1)，计数越高、factor 越大，涨一格越难。
- 默认 factor 为 10 时，计数器推到 255 约需**一百万次访问**，足以区分日常热点与冷门键。
- factor 越大：增长越慢，可区分的访问量级越高，适合 QPS 极高的实例。
- factor 越小：增长越快，低访问量实例更易拉开区分度，但高计数段迅速饱和。
- **lfu-decay-time（衰减速度）**：单位为分钟，每经过该时长且键未被访问，logc 减 1；设为 0 表示永不衰减。
- 没有衰减的频次统计**只涨不跌**：键只要曾经很热就永远排在淘汰名单末尾，冷热变化无法体现。
- 衰减是**惰性结算**而非后台定时任务：按 ldt 与当前时间的时间差，在键被访问或参与淘汰比较时一次性补算，思路与过期删除的惰性检查一脉相承。
- 衰减让 LFU 能识别「曾经热、现在冷」的键，避免旧热点长期霸占内存。
- 两个参数都是**实例级配置**：作用于所有键，不能按键单独调节。
- 调整 factor 只影响之后的增长速度，已有的计数值不会被回溯重算。
- 冷启动阶段频次区分度不足属正常现象，需运行一段时间再评估 LFU 效果。

```bash
# 观察与调节 LFU 参数
CONFIG GET lfu-log-factor
CONFIG SET lfu-decay-time 1
```

两个参数组合出 LFU 的完整画像：factor 定标尺长短，decay-time 定遗忘速度，二者配合得当才能既区分冷热又跟上负载变化。

> 调参前提是先估算单键的典型访问频次：目标是让「最热键」与「普通键」的计数值拉开明显差距，而不是把计数值当精确访问次数用。计数值是对数刻度，从 100 涨到 110 所代表的访问增量远大于从 10 涨到 20；比较两键热度看计数值大小即可，反推精确访问次数没有意义。

**速记**：越访问越**难涨**（factor），不访问就**慢慢凉**（decay-time），结算都在访问与比较时补算。



#### OBJECT FREQ 与 LRU、LFU 的对比辨析

**OBJECT FREQ**：返回键当前 logc 计数值的诊断命令，仅在 maxmemory-policy 为 lfu 系列时可用，否则报错。

```bash
127.0.0.1:6379> OBJECT FREQ hotkey
(integer) 87
127.0.0.1:6379> OBJECT FREQ coldkey
(integer) 6
# 热键与冷键的计数值差距明显，LFU 据此决定删谁
```

- LRU 与 LFU 的核心差异：**LRU 回答最近一次访问距今多久**，**LFU 回答一段时间内访问有多频繁**。
- LRU 的典型弱点是**偶发扫描污染**：全表遍历、备份扫描会把大量冷键的空闲时间清零，热键反而排到淘汰前列。
- LFU 的典型弱点是**对新键不友好**：新键频次低，容易先被淘汰，初值 5 只能缓解不能根治。
- LFU 的优势是**频次稳态**：偶发的一次性访问几乎不影响计数，热点排序长期稳定。
- 选择口径：负载存在明显扫描类访问、或希望热点长期保留，选 LFU；热点随时间快速轮转、旧热点应让位，选 LRU。
- 两种算法共用候选池与采样框架，差别只在比较依据：一个比空闲时长，一个比频次计数。
- 观察工具对应关系：LRU 模式看 OBJECT IDLETIME，LFU 模式看 OBJECT FREQ，用错命令会报错或失真。
- 报错信息提示需要 LFU 策略：未切到 lfu 系列时执行 OBJECT FREQ 会直接返回错误。
- FREQ 读数就是 logc 原值，范围 0 到 255，与淘汰比较所用的是同一个数。
- 若想看「最近访问时间」与「频次」两路信息，LFU 模式下只有后者可用，前者已被复用。

> [!TIP]
> **建议内容**：不确定选哪个时，先用 allkeys-lru 起步，再通过 OBJECT IDLETIME 与命中率监控观察是否存在「热键被误淘汰」的迹象；确认存在扫描污染或冷热长期分明后，再切换 allkeys-lfu，并按实际访问量微调 lfu-log-factor 与 lfu-decay-time。

**速记**：LRU 论**新鲜度**，LFU 论**忠诚度**；扫描多选 LFU，热点轮转快选 LRU。



### 内存碎片与主动碎片整理

淘汰与过期删除回收的是键空间的逻辑内存，分配器层面还有一块看不见的损耗：碎片。本节讲碎片的成因与观测，以及 Redis 4.0 起提供的运行期主动整理机制。

#### activedefrag 主动碎片整理与参数调优

**activedefrag**：Redis 4.0 起提供的主动碎片整理机制，在运行期把分散的存活数据搬移到重新申请的连续内存中，再释放旧分配、把整块空洞归还操作系统，全程不影响对外服务。

- **内存碎片**的成因主要有三：值的长度频繁变化（反复覆盖写）、大量键被删除后留下不连续的空洞、大量不同长度的写入导致分配单元参差。
- 观测指标是 INFO memory 中的 **mem_fragmentation_ratio**：等于 used_memory_rss 除以 used_memory，前者是操作系统视角的物理占用，后者是 Redis 视角的逻辑申请量；明显大于 1 说明碎片偏高（工程上常以 1.5 为经验关注线），小于 1 说明部分内存被换出到 swap，比碎片更危险。
- 硬前提是 **jemalloc**：机制依赖 jemalloc 提供的分配器接口——通过 mallctl 读取分配器的页级统计识别碎片，用 malloc_usable_size 估算对象真实占用；以 libc malloc 编译的版本不支持，强行开启会直接报错。
- 开启方式：CONFIG SET activedefrag yes，或配置文件中的 active-defrag-enabled（默认 no）。
- **active-defrag-ignore-bytes**（默认 100mb）：碎片浪费的绝对量低于此值不动手，避免小实例为蝇头碎屑空耗 CPU。
- **active-defrag-threshold-lower**（默认 10）：碎片率超过此百分比才开始整理，是启动线；**active-defrag-threshold-upper**（默认 100）是满载线，达到后以最大力度整理，实际力度在两线之间随碎片程度线性增强。
- **active-defrag-cycle-min（默认 1）与 active-defrag-cycle-max（默认 25）**：整理占用的 CPU 百分比区间——服务器繁忙时把力度压到 cycle-min 附近、空闲时才向 cycle-max 逼近，即「繁忙让路、空闲抢工」的自适应静默节流；7.0 起另有 active-defrag-cycle-millis 限制每轮整理的时间片毫秒数。
- CPU 代价的本质：搬移是把存活数据复制到新内存，这些复制操作与命令处理共享主线程，力度参数因此存在——碎片率高又强行全速整理的实例，命令延迟会明显抖动。

```bash
# 观测碎片并开启主动整理
INFO memory
CONFIG SET activedefrag yes

# 常用参数（redis.conf 写法，注释为默认值）
active-defrag-enabled no
active-defrag-ignore-bytes 100mb   # 碎片绝对量门槛
active-defrag-threshold-lower 10   # 启动线：碎片率 10%
active-defrag-threshold-upper 100  # 满载线：碎片率 100%
active-defrag-cycle-min 1          # 繁忙时 CPU 占比下限
active-defrag-cycle-max 25         # 空闲时 CPU 占比上限
```

> [!WARNING]
> **警告内容**：主动碎片整理在 4.0 引入时标注为实验特性，且整理的 CPU 开销与碎片程度正相关——高负载大实例开启前，务必以生产同规模数据实测 cycle 参数下的延迟影响；碎片轻微时宁可不开，靠合理的写入设计控制碎片更稳妥。版本演进的脉络详见第 32 章。

**速记**：activedefrag 靠 **jemalloc 接口**在运行期搬家整理，门槛看 **ignore-bytes 与 threshold 双线**，力度在 **cycle-min 与 cycle-max** 之间自适应——繁忙让路、空闲抢工。



### 策略配置与选型

淘汰机制的全部行为由几个配置项共同决定，它们都支持运行期动态修改。本节给出动态切换的操作方法、按场景选型的建议口径，以及主从架构下的特殊规则。配置与选型决定淘汰机制的最终形态，务必与业务数据的可丢弃性、访问模式一起通盘考虑。

#### CONFIG SET 动态切换策略

**动态切换**：maxmemory 与 maxmemory-policy 都支持运行期通过 CONFIG SET 修改，无需重启实例，下一次触顶即按新配置执行。

- CONFIG GET maxmemory-policy 查看当前策略，CONFIG SET 直接覆盖，立即生效。
- CONFIG REWRITE 将当前配置写回 redis.conf，避免重启后修改丢失。
- 切换到 lfu 系列时，已有键的 lru 字段按新语义重新解释，频次数据需要时间重新积累，短期内 LFU 的区分度有限。
- 切换策略不影响数据本身，只影响触顶时**删谁的规则**。
- 调低 maxmemory 是更危险的变更：若当前水位已高于新上限，SET 完成的瞬间就可能触发一轮大规模淘汰。
- 修改也可以走 redis.conf 加重启的路径，但会中断服务，动态切换是更常用的手段。
- 常用组合：先 CONFIG GET 确认现状，再 SET 调整，最后 REWRITE 固化，三步走完闭环。
- CONFIG SET 的修改只作用于当前进程：不执行 REWRITE 的话，重启即回退到配置文件里的旧值。
- 切换到 noeviction 也要谨慎：一旦触顶，写入方将立刻收到报错，需提前通知上游。
- 配置管理平台化后可批量下发：多实例同步切换时更要控制节奏，避免同时触发大规模淘汰。

```bash
127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"
127.0.0.1:6379> CONFIG SET maxmemory 2gb
OK
127.0.0.1:6379> CONFIG SET maxmemory-policy allkeys-lru
OK
127.0.0.1:6379> CONFIG REWRITE
OK
```

> 配置变更属于高风险操作：调低 maxmemory 可能立刻触发大规模淘汰，切换策略会改变删键口径。变更安排在低峰期执行，变更前确认容量，变更后通过 used_memory 与命中率监控验证行为符合预期，并把变更记录进运维日志。

**速记**：先 GET 再 SET，改完 **REWRITE 落盘**，切换即时生效不重启，调低 maxmemory 前先看水位。



#### 策略选型建议

**选型原则**：按数据的可丢弃性选策略——可丢的缓存数据选 allkeys 热度系列，不可丢的数据选 noeviction 并自行做好容量规划。

- **纯缓存场景**：首选 allkeys-lru 或 allkeys-lfu，所有键可丢、按热度让路。
- **扫描类访问多或热点长期稳定**：allkeys-lfu；**热点随时间快速轮转**：allkeys-lru。
- **部分键不可丢**：可考虑 volatile-* 系列，给可丢的键设 TTL、不可丢的不设，但必须确认 TTL 覆盖完整，否则退化为 noeviction。
- **把 Redis 当存储用**：保持 noeviction，靠扩容内存、拆分实例或清理冷数据解决压力，绝不允许自动删键。
- **random 系列**：仅当键访问概率高度均等时偶有价值，一般不选。
- **选型不是一锤子买卖**：负载会演变，应定期结合命中率与淘汰量监控复核策略是否仍然合适。
- **命中率是最直接的验收指标**：切换策略后对比 INFO stats 中的 keyspace 命中率变化。
- **evicted_keys 反映淘汰压力**：该值持续快速增长，说明容量规划或选型出了问题。
- 多数生产实例的最终形态是「allkeys-lfu 起步，按监控数据微调」，而非一次性定型。
- 有持久化诉求的实例更应慎选 allkeys 系列：淘汰删除同样会体现在持久化数据中，重启后无法找回（详见第 17、18 章）。

```bash
# 观察命中率与淘汰量，作为选型调整依据
INFO stats
# keyspace_hits:123456
# keyspace_misses:23456
# evicted_keys:789
```

监控三件套——used_memory、evicted_keys、命中率——应组合解读：内存高但无淘汰说明余量充足，淘汰快且命中率降说明容量吃紧，命中率平稳则当前策略可继续沿用。

> [!WARNING]
> **警告内容**：淘汰删除不可恢复——被淘汰的键不会进入任何回收站，持久化文件也只是事后重建的手段，而非保护伞。若实例中存在一旦丢失就影响业务的键，唯一正确的选择是 noeviction 加足量容量规划，而不是指望淘汰策略「恰好不删它」。

**速记**：缓存用 **allkeys-lru 或 lfu**，存储用 **noeviction**，volatile 要确保 **TTL 全覆盖**，random 基本不用。



#### 主从架构下的淘汰行为差异

**主从下的淘汰规则**：内存淘汰只在主库执行，从库不自行淘汰，而是等待主库把被淘汰键的删除命令随复制流同步过来再删除（主从复制详见第 20 章）。

- 从库默认**无视自己的 maxmemory**：配置项 replica-ignore-maxmemory 默认为 yes，即使内存超限也不主动触发淘汰。
- 设计动机是**主从一致**：若从库按本机内存各自淘汰，可能删掉主库仍存在的键，造成复制偏差。
- 后果是从库内存占用可能**明显高于主库**：主库触顶即淘汰，从库要等删除命令同步后才释放。
- 主库为 noeviction 且触顶时，写入报错，从库不会出现主库没有的新数据。
- 复制流本身也占内存：主库需为每个从库维护复制缓冲区，这部分开销在 maxmemory 之外，容量规划要计入。
- 写入集中于主库、从库只读的架构下，淘汰引发的删除命令也会随复制流广播到所有从库。
- 从库的过期键处理另有规则，与淘汰机制并行，详见第 14 章。
- 从库内存超限的告警阈值应设得比主库更宽松，避免误报。
- 读写分离场景下，从库承担读流量，键被主库淘汰后从库随之删除，读请求会短暂 MISS。
- 应用层应把淘汰导致的 MISS 视为正常现象，配合旁路缓存模式自动回源（详见第 26 章）。
- 从库宕机重启后的数据重建同样来自主库同步，而不是本地留存，淘汰状态因此天然一致。
- 哨兵与集群架构下的淘汰归属同理：淘汰永远跟着「可写的主」走，详见第 21、22 章。

```bash
# 查看从库是否忽略自身的 maxmemory
CONFIG GET replica-ignore-maxmemory
# 1) "replica-ignore-maxmemory"
# 2) "yes"
# 主库触顶淘汰后，删除命令随复制流到达，从库内存随之回落
```

从库不淘汰还有一层含义：主库淘汰产生的删除是复制流的一部分，网络抖动时从库的释放会滞后，监控从库内存时应把这条传播延迟计入。

> [!IMPORTANT]
> **重要内容**：主从架构做容量规划时，不能只按主库的 maxmemory 估算从库内存——复制缓冲区、尚未同步完的删除命令、以及 replica-ignore-maxmemory 带来的「超限不淘汰」，都会让从库实际占用高于主库，从库内存不足可能引发交换甚至崩溃。

**速记**：**主库淘汰、从库照删**，从库内存要**留足余量**，replica-ignore-maxmemory 默认放行超限。
