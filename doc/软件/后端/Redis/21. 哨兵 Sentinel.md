## 哨兵 Sentinel

**哨兵 Sentinel**：是 Redis 官方提供的高可用（High Availability）解决方案，本质是**运行在哨兵模式下的 Redis 服务器进程**——它叠加在主从复制（详见第 20 章）之上，持续监控主从拓扑，在主库故障时自动完成换主，并充当客户端的配置发现中心。本章依次展开哨兵的认识与四大任务、下线判定与自动发现、领头选举与故障转移四步、部署配置与客户端接入、脑裂风险的缓解，最后以运维命令与 Cluster 的适用边界收束，各模块考点地图如下。

```text
本章考点地图：

认识：定义与定位 ─ 哨兵集群形态 ─ 四大任务 ─ 事件频道
判定与发现：主观下线 SDOWN ─ 客观下线 ODOWN ─ 自动发现
选举与转移：领头哨兵选举 ─ 故障转移四步 ─ 新主挑选三条件
部署与接入：最少三节点 ─ 核心配置 ─ 客户端接入 ─ 脑裂缓解
边界：SENTINEL 命令族 ─ 哨兵与 Cluster 的适用边界
```

### 哨兵的认识

#### 哨兵解决主库宕机后的自动换主问题

**哨兵（Sentinel）**：是 Redis 官方提供的**高可用（High Availability）解决方案**，由一组独立运行的监视进程组成，用于在主从复制架构中自动完成故障检测与主库切换。

- 问题的起点：主从复制（详见第 20 章）只解决了数据冗余与读扩展，主库宕机后**切换靠人工**——服务中断时间完全取决于运维的响应速度。
- 人工切换的真实负担：确认主库确实不可用、从多个从库中挑出数据最新的一个、对其执行晋升、把其余从库逐台改为复制新主、等旧主恢复后降级、再通知所有应用方改连新地址，一步都不能错、一步都不能慢。
- 哨兵出现前的临时做法：用外部脚本定时探测主库、检测到故障后自动改配置重启，这类脚本既无法处理误判，也无法协调多个从库的重配置顺序，故障处理质量完全依赖脚本作者的功力。
- 哨兵的定位：把**故障检测、自动换主、客户端通知**三件事交给机器，主库宕机后通常几十秒内完成切换，全程无人工介入。
- 时间起点：哨兵自 **Redis 2.8 正式版**起随 Redis 官方发布并走向成熟，此前的早期实现不建议在生产环境使用。
- 数据边界：哨兵**不存储任何业务数据**，只维护监控元数据，包括主从组、节点地址、下线状态与配置纪元，因此哨兵进程的内存占用极小。
- 架构位置：哨兵与数据节点平行部署，不改变主从复制本身的任何机制，只是在复制体系之上叠加一层**监视与调度**。
- 官方地位：哨兵是 Redis 官方文档中的标准组件，与 Cluster 并列为两条高可用路径，社区探活方案均属补充而非替代。
- 运维解耦：哨兵的升级、重启与数据节点互不影响，哨兵层可以独立于数据层单独维护。
- 与漂移 VIP 方案对比：keepalived 加 VIP 的老方案对客户端透明，但切换时无法感知从库数据新旧，容易把流量切到落后的副本；哨兵按数据新鲜度选主，丢数据更少。
- 与代理层方案对比：代理层的探活脚本只改代理指向，不重配置复制拓扑；哨兵直接改写主从关系，让复制链路跟随新主。
- 与应用自愈对比：应用内自动重连只能更换连接地址，不能**创造**新主库；新主库的产生必须由哨兵或人工完成。

一次人工切换在深夜值班场景下往往要十分钟以上，还可能因为误判从库数据新旧而丢失数据；哨兵把这一串动作**标准化并自动化**，把分钟级的人工响应压缩到秒级的机器响应，同时用多节点协商把误判概率压到极低。理解哨兵的正确视角是：它不是新的存储组件，而是**主从架构的运维自动化层**。引入哨兵后，业务侧唯一需要配合改造的环节是客户端——从写死地址改为向哨兵查询并订阅切换事件，其余全部透明。

> 辨析：哨兵解决的是**可用性**问题而非**容量**问题。数据量超出单机内存、写压力超出单机上限时，换多少个主库也无济于事，应转向 Cluster 分片方案（详见第 22 章）；反过来，Cluster 内部自带故障转移，部署了 Cluster 就不再需要哨兵。

**速记**：哨兵＝主从复制之上的**自动换主组件**，2.8 起官方标配，只管可用性不管容量。



#### 哨兵集群是一组互为兄弟的独立进程

**哨兵集群**：由多个哨兵进程组成，各哨兵**互为兄弟节点**，彼此独立地监控同一批主从节点，再通过消息协商达成一致结论。

- 进程形态：哨兵是**独立进程**，可以用 redis-sentinel 启动，也可以用 redis-server 加 --sentinel 参数启动；它不是主从节点上的附属线程，哨兵宕机不影响主从服务本身。
- 进程轻量：哨兵不承载数据、只做探测与协调，单实例内存占用可以忽略，通常与业务应用同机部署一个即可。
- 为什么不部署一个：单哨兵既可能误判——网络抖动、进程卡顿都会被当成主库故障；自身又是单点——它一挂，整个高可用体系失效；多哨兵协商才能把**误判与单点**同时消除。
- 协作方式：哨兵之间通过发布订阅频道交换存活信息，通过下线询问命令交换故障判定，构成一个**小型分布式共识系统**。
- 数据隔离：哨兵与哨兵、哨兵与数据节点之间**不共享业务数据**，只交换控制信息，任何一个哨兵重启都不会丢失业务。
- 视角独立：每个哨兵只在本地保存自己视角的拓扑与状态，不依赖中央存储；兄弟哨兵列表、从库列表都是自动发现并各自维护的。
- 多组监控：每个哨兵可以同时监控多组主从架构，每组用一个自取的组名标识，组与组之间互不干扰。
- 启动入口：哨兵端口独立于数据端口（默认 26379），配置文件、日志文件也与数据实例分开，进程管理上视同独立的守护服务。
- 可观测性：哨兵提供 INFO sentinel 子命令查看自身状态，日志独立输出，故障前后可回放完整时间线。
- 无状态恢复：哨兵重启后从配置文件与自动发现重新建立拓扑，无需人工修复，也不存在需要恢复的业务状态。
- 防误报扩散：哨兵之间相互确认的机制让单个哨兵的误报不会升级为集群动作，这正是多节点部署的第一价值。
- 命名管理：组名与哨兵端口的约定应在团队内统一记录，多套环境混用同名组名会干扰排障。

一个典型三哨兵部署的物理分布示意：

```text
机器一  哨兵A            机器四  主库 6379
机器二  哨兵B            机器五  从库 6380
机器三  哨兵C            机器六  从库 6381
（三台哨兵分散在不同机器，与主库物理隔离）
```

> 注意：哨兵集群自身也是分布式系统，部署奇数个（3 个或 5 个）是行业惯例，最少三个的数学原因与多数派计算见本章 部署与配置 模块。

**速记**：哨兵是一群**互为兄弟的独立进程**，单哨兵不可信，多数派才可信。



#### 哨兵的四大任务是监控、通知、自动故障转移与配置发现

**哨兵四大任务**：**监控（Monitoring）**、**通知（Notification）**、**自动故障转移（Automatic Failover）**、**配置发现（Configuration Provider）**——前三者构成一条完整的故障处理链路，第四项是日常态下持续对外提供的服务。

- **监控**：每个哨兵每秒一次向主库、从库与其他哨兵发送 PING，持续检查可达性；回复正常则维持在线判定，连续超时即进入主观下线判定，这是后续一切动作的触发源。
- **通知**：节点状态变化时，哨兵通过发布订阅向 +sdown、+odown、+switch-master 等事件频道推送消息；运维脚本或客户端订阅这些频道即可实时感知故障与切换，这是四大任务中唯一面向**外部观察者**的任务。
- **自动故障转移**：主库被确认客观下线后，哨兵内部先选举领头哨兵，再由领头哨兵挑选一个从库晋升为新主，并重配置其余从库与旧主，这是四大任务中唯一会**改动集群拓扑**的任务。
- **配置发现**：哨兵充当客户端服务发现的**权威来源**——客户端启动时连接哨兵查询当前主库地址，而不是把地址写死在业务配置里；故障转移完成后，同一查询返回的已是新主地址，业务代码零改动。这是四大任务中唯一在**日常态**持续工作的任务。
- 任务关系：监控是感知、通知是播报、转移是处置、发现是指路；前三者依次触发、边界清晰，第四者贯穿始终，理解了这四项就理解了哨兵的全部工作。
- 职责归属：监控由**每个哨兵**独立执行；通知由**每个哨兵**各自发布；转移由**领头哨兵**一人执行、其余哨兵监督；配置发现由**每个哨兵**共同应答，客户端向任一可用哨兵查询即可，权责分明。
- 关键配套：自动故障转移与配置发现必须**成对落地**——只做自动换主而客户端仍写死地址，切换完成后业务依旧连着旧主，等于白切；接入方式见本章 客户端接入哨兵的三步流程 考点。
- 相互依赖：没有监控就没有触发，没有通知就没人知道发生了什么，没有转移就没有恢复，没有发现客户端就找不到新主；四者缺一不可，没有主次之分。
- 全程可观测：四项任务的每一步推进都会反映到事件频道，运维无需登录数据节点逐台确认，盯住哨兵事件流即可掌握全局。
- 周期参数：PING 的频率、hello 消息的 2 秒间隔、INFO 的 10 秒间隔共同决定了哨兵感知变化的速度上限，这些周期属于内部约定，调优空间主要在配置参数而非内部周期。
- 影响面排序：监控失败只损失感知，通知失败只损失可见性，转移失败才会造成服务持续不可用；理解这个排序有助于在故障时判断紧急程度。

四大任务的整体流程示意：

```text
监控：PING 持续超时 → 单哨兵标记主观下线（+sdown）
        ↓
      quorum 个哨兵都同意 → 升级为客观下线（+odown）
        ↓
通知：向各事件频道发布状态变化，运维与客户端订阅感知
        （此时只是播报，尚未改动任何节点）
        ↓
自动故障转移：选举领头哨兵 → 挑选新主 → 晋升与重配置 → 旧主降级
        （拓扑在此阶段被实际改动，完成后再次通知）

配置发现：客户端随时向任一哨兵查询当前主库地址
        （日常态持续工作，返回的永远是最新主库）
```

> 提醒：通知任务只负责**播报**，不负责替客户端完成切换；客户端必须主动订阅事件或主动查询，才能拿到最新的主库地址，具体接入方式见本章 客户端接入哨兵的三步流程 考点。

**速记**：**监控**找病、**通知**喊话、**故障转移**动刀，三步一条链。



#### 事件频道是通知任务的落地形式

**事件频道**：哨兵把所有状态变化发布到以半角加号或减号开头的命名频道，运维与客户端通过订阅哨兵实例即可获得实时故障流。

- 命名规律：加号开头表示**发生**某事件（如 +sdown、+switch-master），减号开头表示**解除**某状态（如 -sdown 表示节点恢复正常）。
- 下线类事件：+sdown 与 +odown 分别标记主观与客观下线生效，对应的 -sdown 与 -odown 标记解除，是判断故障起止的基准信号。
- 转移类事件：+switch-master 宣告换主完成，事件体依次为组名、旧主 IP、旧主端口、新主 IP、新主端口；+failover-state 系列直播挑选从库、晋升、重配置等各阶段进展。
- 重配置类事件：+slave-reconf-done 表示一个从库已成功改为复制新主，+convert-to-slave 表示旧主被降级，可用于确认切换是否彻底完成。
- 中止类事件：-failover-aborted 与 +failover-abort 系列表示转移被放弃或中止，常与领头丢失、候选从库失联有关，排障时应重点回看。
- 选举类事件：+vote-for-leader、+elected-leader 完整记录一轮领头选举的起止，可用于分析选举为何反复失败。
- 订阅位置：事件频道存在于**哨兵实例**上而不是数据节点上，订阅时连接的是哨兵端口，不是 6379 之类的业务端口。
- 连接管理：订阅需要独占一条长连接，不能与普通的命令连接混用；客户端应单独维护一条到哨兵的订阅连接，断开后自动重建并重新订阅。
- 运维用途：把事件流接入告警系统，故障发生秒级触达值班人员；事件也可作为审计线索，回溯一次故障的完整时间线。
- 状态机视角：把订阅到的事件按时间排列，即可还原一次故障从发生到恢复的完整状态流转，是复盘故障的标准材料。

一次典型故障期间的事件序列示意：

```text
+sdown master mymaster 127.0.0.1 6379        # 单哨兵认定主库可疑
+odown master mymaster #5 0 ...              # quorum 确认客观下线
+vote-for-leader <runid> <epoch>             # 领头选举投票进行中
+elected-leader master mymaster ...          # 领头哨兵当选
+failover-state-select-slave ...             # 正在挑选新主
+selected-slave 127.0.0.1 6380 ...           # 选定 6380 为新主
+switch-master mymaster 127.0.0.1 6379 127.0.0.1 6380   # 换主完成
```

手工订阅事件流可用于联调与排障：

```bash
# 连接任一哨兵实例，订阅三类关键事件
redis-cli -p 26379 SUBSCRIBE +switch-master +sdown +odown
# 收到消息即表示对应状态发生变化，联调客户端切换逻辑时尤其有用
```

> 提醒：同一事件会由**每个哨兵各自发布一次**，订阅方会收到多条相似消息，去重逻辑要由消费方自己处理；切勿因为收到多条就误判为发生了多次切换。

**速记**：加号**发生**、减号**解除**，订阅哨兵端口拿故障流。



### 下线判定与自动发现

#### 主观下线 SDOWN 是单个哨兵的孤立判断

**主观下线（SDOWN，Subjectively Down）**：指单个哨兵在 down-after-milliseconds 毫秒内没有收到目标节点对 PING 的**有效回复**，从而单方面认定该节点已下线。

- 判定依据：PING 的回复为 +pong、-loading、-masterdown 三种之一算**有效**；超时无回复、拒绝连接、回复其他错误均视为**无效**，无效状态累计超过阈值即标记 SDOWN。
- 有效回复的含义：+pong 表示节点正常应答；-loading 表示节点正在加载数据暂时不能服务，但进程活着；-masterdown 表示对方以从库身份回应主库已失联——三种回复都证明**链路通、进程在**。
- 时间的含义：down-after-milliseconds 衡量的是**累计无效时长**，而不是单次命令超时；窗口内任何一次有效回复都会重置计时，偶发的单次超时不会直接触发下线。
- 参数来源：down-after-milliseconds 由 sentinel down-after-milliseconds 配置指定，同一主从组的从库与哨兵共用这一个值，不区分监控对象。
- 局部性：SDOWN 只是**本地结论**，该哨兵进入 +sdown 状态并发布事件，不触发任何切换动作；网络抖动、哨兵自身网卡故障都会造成误报。
- 覆盖对象：主库、从库、其他哨兵任一目标失联都会触发 SDOWN，但只有主库的 SDOWN 才会进入后续客观下线协商。
- 可逆性：目标节点在超时窗口内恢复有效回复，状态自动回退为在线并发布 -sdown 事件，无需人工干预。
- 排查视角：看到 +sdown 先区分是网络问题还是节点问题——同机其他服务若同时失联多半是网络抖动，若只有该节点失联才怀疑节点本身故障。
- 复制中断不是下线：主从之间断开复制不等于节点下线，节点存活仍能应答 PING，哨兵不会因为复制断开而判定主观下线。
- 慢回复等价无回复：回复超出等待时间同样按无效处理，在下线判定中慢节点与死节点没有区别。

```bash
# 哨兵配置中的判定阈值（同一主从组共用一个值）
sentinel down-after-milliseconds mymaster 30000
# 判定语义：30 秒窗口内任一次 PING 得到有效回复都会重置计时
# 只有连续 30 秒无有效回复，该哨兵才标记 +sdown
```

有效与无效回复的区分示意：

```text
有效回复：+pong（正常应答）
          -loading（节点加载中，进程存活）
          -masterdown（对方报告其主库失联）
无效情形：超时无回复、连接被拒绝、回复其他错误
判定结论：窗口内无任何有效回复 → 标记 +sdown
```

> 辨析：从库与哨兵节点只存在主观下线状态，永远不进入客观下线流程——从库挂了影响的是读能力，哨兵各自记录即可，不存在需要协商的集群级决策；主库挂了则牵动全局写服务，才需要多人确认。

**速记**：SDOWN＝**我一个人觉得它挂了**，判定阈值由 down-after-milliseconds 决定。



#### 客观下线 ODOWN 需要 quorum 个哨兵联合确认

**客观下线（ODOWN，Objectively Down）**：当至少 **quorum 个**哨兵在同一个配置纪元内都认为主库主观下线时，主库被判定为客观下线，此后才有资格启动故障转移。

- 参数含义：quorum 是 sentinel monitor 配置行的最后一个数字，例如设为 2 表示需要 2 个哨兵都报告主库 SDOWN，才升级为 ODOWN。
- 确认机制：哨兵判定主库 SDOWN 后，向其他哨兵发送 is-master-down-by-addr 询问，收集到的同意回复达到 quorum，即把本地状态升级为 ODOWN 并发布 +odown 事件。
- 询问内容：请求中携带主库地址与端口，收到询问的哨兵用**自己本地的探测结果**回答，而不是转抄询问者的结论，保证每一票都是独立观察。
- 两道门槛：quorum 只解决**确认下线**这第一道门槛；真正执行切换还需要领头哨兵获得**多数派授权**，见本章 领头哨兵的选举基于 Raft 思想 考点，两个数字彼此独立、可以配置得不同。
- 取值建议：quorum 通常取哨兵总数的一半向下取整再加一，与多数派一致，让确认下线与执行切换的门槛对齐；设得比多数派小只会让切换提前，不会降低执行门槛。
- 纪元约束：询问与同意都携带配置纪元（epoch，配置版本计数器），每个纪元的判定独立计数，防止旧纪元的过期结论污染新一轮判定。
- 语义意义：ODOWN 把**我觉得挂了**升级为**大家都觉得挂了**，这是哨兵避免单点误判导致误切换的核心设计。
- 资格与动作：达成 ODOWN 只意味着获得发起故障转移的**资格**，从 +odown 到 +switch-master 之间还有领头选举与四步切换，故障确认时间不等于服务恢复时间。
- 失联与判定：哨兵之间失联不影响各自独立判定，询问消息只能尽力送达；quorum 的计数以实际收到的同意回复为准，收不到就达不到门槛。

询问与确认的交互示意：

```text
哨兵A：主库 PING 超时 → 本地标记 +sdown
  ↓ 向哨兵B、哨兵C 发送 is-master-down-by-addr 询问
哨兵B：用自己的探测结果确认超时 → 回复同意
哨兵C：用自己的探测结果确认超时 → 回复同意
  ↓ A 收到 2 票同意，quorum = 2 已达成
哨兵A：将主库升级为 +odown，发起领头选举
```

> [!IMPORTANT]
> **重要内容**：SDOWN 与 ODOWN 只对**主库**生效。原因在于：主库下线意味着需要换主，这是一项影响全局写服务的集群级决策，必须多人确认以防误切；而从库与哨兵的下线只影响局部读能力或监控能力，单个哨兵记录即可，无需任何协商流程。

**速记**：SDOWN 是**个人观点**，ODOWN 是 **quorum 人联合签名**，仅主库适用。



#### 哨兵通过 hello 频道与 INFO 命令自动发现节点

**自动发现机制**：哨兵无需在配置文件里手工登记每个从库与每个兄弟哨兵，而是依靠 **__sentinel__:hello 频道**与 **INFO 命令**两条途径自动补全集群拓扑。

- 发现兄弟哨兵：每个哨兵每隔 2 秒向所监控主库与从库的 __sentinel__:hello 频道发布一条消息，内容包括自身 runid、监听地址端口、当前配置纪元；订阅同一频道的其他哨兵收到后，将发布者登记为兄弟哨兵。
- 发现从库：哨兵每隔 10 秒向已知主库发送 INFO 命令，从回复的 replication 段落解析出全部从库的地址与状态，据此建立并维护从库监控列表。
- 解析粒度：INFO 回复中每个从库一行，包含其 IP、端口、复制状态与复制偏移量，哨兵据此既知道有哪些从库，也知道各自的数据新鲜度。
- 发布即发现：借助于主从库本身就是消息中枢，新哨兵只要知道主库地址就能加入，其余哨兵通过频道自动感知它，不需要逐台登记。
- 持续更新：新哨兵加入、新从库上线、节点地址变更，都会通过 hello 消息与 INFO 回复周期性反映到所有哨兵的本地拓扑中，无需人工同步。
- 发现新主：故障转移完成后，新主库的 INFO 回复与 hello 消息会让各哨兵自动更新主库指向，不需要修改任何配置文件。
- 信息收敛：hello 消息还携带各哨兵所知的最新主库配置版本，版本落后者会被更新，保证集群拓扑最终一致。
- 角色感知：INFO 回复同时报告节点的角色字段（role 为 master 或 slave），哨兵据此发现角色漂移等异常状态，例如本应是从库的节点自己当了主。
- 载体复用：hello 消息发布在数据节点上，复用 Redis 自身的发布订阅机制，不引入哨兵与节点之外的额外通信通道。
- 新成员加入：新启动的哨兵只要配置了主库地址，就能通过 hello 频道被存量哨兵感知并纳入集群，扩容无需重启任何存量节点。

两条发现路径的示意：

```text
路径一：哨兵之间互相发现（靠频道）
哨兵A ──每 2 秒 PUBLISH __sentinel__:hello──→ 主库与从库
其余哨兵订阅同一频道 → 记录 A 的地址 → 兄弟列表自动补全

路径二：哨兵发现从库（靠命令）
哨兵B ──每 10 秒 INFO 命令──→ 主库
从 INFO 回复的 replication 段解析出从库地址列表
```

> 提醒：hello 频道属于哨兵内部协议，业务客户端一般不消费它；运维排查时可以手工订阅该频道观察哨兵心跳是否正常，作为诊断哨兵间失联的辅助手段。

**速记**：**hello 找兄弟（2 秒一发），INFO 找从库（10 秒一查）**，拓扑全自动发现。



### 领头哨兵与故障转移

#### 领头哨兵的选举基于 Raft 思想

**领头哨兵（Leader Sentinel）**：主库客观下线确认后，哨兵集群必须推举**唯一一个**哨兵来执行故障转移，推举过程借鉴 **Raft 算法**的选举思想。

- 先到先得：发现客观下线的哨兵立刻自荐为候选人，向其他哨兵发送携带自身 runid 的 is-master-down-by-addr 请求拉票，谁先发出谁占先机。
- 一人一票：每个哨兵在一个配置纪元（epoch，每次选举自增的版本计数器）内**只投一张赞成票**，通常投给第一个来拉票的候选者；投出后本纪元不可改票。
- 多数派当选：候选者拿到**超过半数**已部署哨兵的赞成票即当选；得票不足则本次选举作废，各哨兵随机等待一段时间后进入下一纪元重新选举。
- 冲突消解：等待时长包含随机偏移，降低多个哨兵同时自荐造成选票瓜分的概率；若连续选不出领头，故障转移整体受 failover-timeout 约束直至超时后重试。
- 投票前提：收到拉票请求的哨兵只有在自己也认为主库已失联时才会投出赞成票，判定不通过则拒绝投票，避免误判一路绿灯。
- 当选即执行：领头哨兵负责后续全部切换动作，其余哨兵只跟踪进度，切换完成后各自更新本地状态。
- 为何需要领头：若每个哨兵都独立执行切换，会同时选出不同从库、发出互相矛盾的命令；推举唯一执行者保证**切换动作全局一致**。
- 与标准 Raft 的差异：哨兵并未完整实现 Raft 的日志复制与任期机制，只借用了**先到先得、随机超时、多数派投票**这三个选举要素，因此只能说借鉴思想而非照搬算法。
- 协议复用：拉票与下线询问复用同一条 is-master-down-by-addr 命令，靠携带的参数区分语义，无需为选举单独设计命令，协议保持精简。
- 纪元作用：每次选举都会使配置纪元自增，纪元同时服务于下线判定与主库配置版本管理，是哨兵体系全局一致性的时间基准。
- 选举失败的表现：事件流中反复出现投票事件而无当选事件，通常意味着哨兵数量不足或多数派失联，此时应扩容哨兵而不是等待。

选举流程示意：

```text
主库确认 ODOWN
      ↓
哨兵A 自荐：发送 is-master-down-by-addr 拉票
      ↓
哨兵B、C：本纪元尚未投票 → 投给 A（先到先得）
      ↓
A 收集到超过半数赞成票 → 当选领头哨兵
      ↓
若无人过半：随机等待后纪元自增，重新选举
```

> 辨析：这里的多数派按**哨兵集群总数**计算，与 quorum 是两个独立参数——quorum 决定谁有权发起故障转移，多数派决定候选人能否当选执行。quorum 配置得再小，也替代不了执行切换所需的多数派授权；这正是哨兵把**判定权**与**执行权**分离的设计。

**速记**：**先到先得、一人一票、过半当选**，一轮不成，换纪元再来。



#### 故障转移按四个固定步骤执行

**故障转移（Failover）**：领头哨兵当选后，按**选新主、晋升、重配置、收尾**四个步骤完成换主，全程自动执行、无需人工介入。

- 第一步选新主：从该主从组的从库列表中按优先级规则挑选最优者（规则见下一考点），被选中的从库成为晋升候选者。
- 第二步晋升：向候选者发送 **REPLICAOF NO ONE**，撤销其从库身份，使其升级为新的主库并开始接受写入。
- 第三步重配置：向其余从库逐批发送 **REPLICAOF 新主地址端口**，让它们断开与旧主的复制、改为复制新主库；每批允许重配置几个由 parallel-syncs 控制。
- 第四步收尾：将旧主库登记为新主的从库，待旧主恢复上线后自动降级并完成数据同步；同时更新 hello 频道中的主库信息，向 +switch-master 频道发布事件宣告切换完成。
- 步骤性质：第一步是**决策**，第二、三步是**拓扑改动**，第四步是**状态收敛**；任何一步失败都会在 failover-timeout 约束下重试或放弃。
- 失败处理：晋升失败（候选者不可达）则重新挑选从库；重配置中断则对未完成的从库补发命令；整体超时后本轮作废、下一轮重新开始，不会留下半切换状态。
- 执行者唯一：四个步骤的全部命令都由领头哨兵发出，其余哨兵只旁观进度，避免了多哨兵并发改写拓扑的冲突。
- 耗时构成：一次完整切换的耗时由三段组成——down-after 的判定等待、选举的秒级开销、数据同步的数据量相关耗时；写服务恢复通常在几十秒量级，读服务完全恢复更久。
- 观察手段：切换的全过程都能从事件频道的 +failover-state 系列事件中看到，出现 -failover-aborted 表示本轮转移被中止。

完整流程示意：

```text
确认客观下线 → 选举领头哨兵（多数派授权）
        ↓
步骤一  按优先级规则挑选最优从库
        （过滤下线与 priority=0，逐轮决胜）
        ↓
步骤二  向其发送 REPLICAOF NO ONE，晋升为新主
        ↓
步骤三  其余从库逐批改为复制新主
        （每批数量由 parallel-syncs 控制）
        ↓
步骤四  旧主恢复后降级为新主的从库
        发布 +switch-master 事件，客户端据此换连
```

> [!CAUTION]
> **注意内容**：步骤二与步骤三之间存在一个**无从库窗口**——新主已开始接受写入、其余从库尚未跟上，此窗口内新主的写入没有任何副本保障。parallel-syncs 取值越大窗口越短，但对新主的瞬时同步压力也越大，配置时须在收敛速度与主库负载之间权衡。

**速记**：**选主、升主、改从、降旧**，四步一气呵成。



#### 挑选新主按三个条件依次决胜

**新主挑选规则**：领头哨兵在从库列表中按**优先级、复制偏移量、runid** 三个条件依次过滤与决胜，保证任何情况下都能得到唯一且全员一致的结果。

- 前置过滤：先剔除处于下线或断线状态的从库，再剔除 replica-priority 配置为 0 的从库——0 在 Redis 中的语义是**永不参与竞选**，专用于指定只读不竞选的副本。
- 第一轮比较：replica-priority 数值**小者优先**。注意方向是数值小者胜出，权重由运维显式指定，通常给硬件最好的机器配更小的数值，体现运维对新主人选的**人工表态**。
- 第二轮比较：权重相同的从库中，复制偏移量（offset）**最大者优先**。offset 越大代表从旧主同步到的数据越多，晋升后**丢失的数据越少**，这是技术层面的最优选择。
- 第三轮决胜：offset 仍然相同的极少数情况下比较 runid，**runid 字符序最小者**胜出。runid 是节点首次启动时随机生成的，此条件实质是随机拍板，但能保证所有哨兵独立计算得到同一个结果。
- 结果唯一性：三轮条件层层收窄，最终必然只剩一个从库，这一设计让即使多个哨兵分别计算，结论也完全一致，避免了候选者冲突。
- 默认权重：replica-priority 默认值为 100，多数场景无需调整；确有主次之分（如跨机房从库）时才显式配置区分。
- 权重配置建议：希望某台机器优先当主的给它配更小的数值；跨机房、弱配置或仅作冷备的从库配更大的数值；确定永远不该当主的直接配 0。
- 数据来源：offset 即复制偏移量（详见第 20 章），主从之间通过它对齐数据流；哨兵在挑选新主时直接读取 INFO 回复中的最新偏移量，无需额外探测。
- 规则根基：offset 单调递增的特性保证了数据新旧可以客观比较，挑选规则才能用数值大小度量丢数据的多少，而不依赖任何主观判断。
- 顺序固化：三个条件的先后顺序由 Redis 实现固定，不提供配置项调整，运维只能在权重维度施加影响。

一个直观的挑选示例：

```text
从库甲  replica-priority=100  offset=9000  runid=abc...
从库乙  replica-priority=100  offset=9500  runid=def...
从库丙  replica-priority=50   offset=8000  runid=xyz...

第一轮：丙权重 50 最小 → 丙胜出，offset 不再参与比较
若甲乙丙权重全为 100 → 第二轮乙 offset 9500 最大 → 乙胜出
```

> 提醒：三者的排列逻辑是**运维意图优先于技术最优**：先让运维用权重表态，权重分不出高下才让数据量说话，数据量也一致才用 runid 随机收尾——每一轮都只为一个目的服务：消除并列，得出唯一答案。

**速记**：**先比权重（小者胜），再比 offset（大者胜），最后比 runid（小者胜）**。



### 部署与配置

#### 哨兵集群至少部署三个节点

**最少三个哨兵**：生产环境的哨兵数量不应少于 3，且建议取**奇数**，这是多数派机制对部署数量的直接要求。

- 数学原因：当选领头哨兵需要超过半数的赞成票。2 个哨兵时必须 2 票全齐，任意一个宕机或网络隔离，剩余 1 票不过半，故障转移永远无法启动——等于把单点故障从主库转移到了哨兵层。
- 两节点推演：主库宕机后，若哨兵之一也恰好失联，剩下的 1 个哨兵既凑不齐客观下线（quorum 至少为 2），更凑不齐多数派，整个体系只能眼睁睁看着写服务中断。
- 容错能力：3 个哨兵可以容忍 1 个故障（剩 2 票仍过半），5 个哨兵容忍 2 个故障；每增加 2 个节点才多容忍 1 个故障。
- 奇数原因：4 个哨兵与 3 个一样只容忍 1 个故障，6 个与 5 个一样只容忍 2 个——偶数节点不提升容错能力，徒增成本。
- 物理分布：哨兵之间、哨兵与主库之间应部署在**不同机器甚至不同可用区**，避免同机断电导致哨兵与被监控对象同时失联。
- 分布建议：三哨兵分别放在三个机柜或三个可用区，任何单一物理单元的故障都不会同时带走两个哨兵，多数派始终可达成。
- 云上实践：公有云部署时把三个哨兵分别绑定到三个可用区的虚机，主从库再与哨兵机器错开，形成六台机器的最小高可用拓扑。
- 与应用混部：哨兵足够轻量，可以与业务应用同机部署一个实例，这样应用机器天然承担了哨兵职责，还能顺带保证哨兵分布在应用所在的全部机房。
- 弹性扩容：哨兵集群可以从 3 平滑扩到 5，新哨兵通过 hello 频道自动加入并参与后续投票，存量节点无需重启。
- 两节点困境的本质：两个成员的系统在任一成员故障时，无法区分对方宕机与自己被隔离，多数派机制天然要求三个起步。
- quorum 取值：quorum 应小于哨兵总数，常取哨兵数的一半向下取整再加一，既保证下线判定有代表性，又不至于一台哨兵故障就卡死判定。

> [!IMPORTANT]
> **重要内容**：哨兵与主库必须物理隔离部署。若 3 个哨兵中有 2 个与主库同机，该机器断电时只剩 1 个哨兵存活，凑不齐多数派，故障转移永久卡死，哨兵体系形同虚设；同理，quorum 也不应设为哨兵总数，否则任何一台哨兵故障都会让客观下线无法达成。

**速记**：**至少 3 个、取奇数、别和主库住同一台机器**。



#### 最小配置三行与常用参数详解

**sentinel 配置文件**：每个哨兵实例对应一份 sentinel.conf，最小可用配置仅 monitor 一行，生产实践通常配置三行核心参数即可工作。

```bash
# sentinel.conf 核心配置（同一主从组的所有哨兵保持一致）
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 30000
sentinel parallel-syncs mymaster 1
# 可选：主库设置密码时必须补充认证参数
# sentinel auth-pass mymaster <主库密码>
# 可选：故障转移整体超时，默认 3 分钟
# sentinel failover-timeout mymaster 180000
```

- **sentinel monitor**：声明监控的主从组，四个参数依次为**组名**（mymaster，运维自取，客户端凭它查询）、**主库 IP**、**主库端口**、**quorum 值**。此行是必填项，是哨兵全部工作的起点；主库地址只需写初始值，发生切换后哨兵会自动更新记忆。
- **sentinel down-after-milliseconds**：主观下线超时阈值，单位毫秒，默认 30000（30 秒）。值越小发现故障越快，但网络抖动误判率越高；值越大越稳健，代价是故障感知迟缓。
- **sentinel parallel-syncs**：故障转移完成后**每次允许几个从库同时**改为复制新主。设 1 表示逐个重配置，读服务有损失但新主压力平稳；设大则切换收敛快，但所有从库同时全量同步可能压垮新主。
- **sentinel failover-timeout**：故障转移整体超时上限，默认 180000 毫秒（3 分钟），同时约束同一主从组两次故障转移之间的最小间隔；超时后哨兵放弃本次尝试并在下一轮重新发起。
- 辅助参数：sentinel auth-pass 用于主库设置了访问密码的场景；该阈值对从库与哨兵的探测同样生效，无需单独配置。
- 配置一致性：同一主从组的所有哨兵必须使用**相同的组名与 quorum**，否则下线判定与选举会出现分裂；down-after-milliseconds 也应保持一致，避免各哨兵判定标准不一。
- 运行时改写：哨兵会在运行过程中把自动发现到的兄弟哨兵、从库列表以及切换后的新主地址**写回自己的配置文件**，因此配置文件会被哨兵动态修改，人工改动前应先确认哨兵已停止。
- 时长估算：按默认值推算一次故障的恢复节奏——30 秒判定加秒级选举再加逐台重同步，写服务恢复通常在 40 秒上下；对恢复速度敏感的场景应从 down-after 与 parallel-syncs 两个参数入手调优。
- 密码注意：sentinel auth-pass 必须在哨兵启动前就写入配置，运行中补加会导致这段时间内的探测以认证失败告终。

> [!TIP]
> **建议内容**：down-after-milliseconds 不建议低于 2000 毫秒。主库偶发一次长耗时的持久化操作或网络抖动超过该阈值就会触发 SDOWN，quorum 配置较小时容易连锁升级为 ODOWN，造成不必要的主从切换与写服务闪断。

**速记**：**monitor 定对象与 quorum，down-after 定敏感度，parallel-syncs 定恢复节奏**。



#### 客户端接入哨兵的三步流程

**客户端接入方式**：启用哨兵后，客户端不再把主库地址写死在配置里，而是遵循**先查哨兵、再连主库、订阅切换事件**的接入流程。

- 第一步查询：向哨兵发送 SENTINEL get-master-addr-by-name 命令（主从组名作参数），得到当前主库的 IP 与端口，向该地址建立连接；查询任意一个哨兵实例均可，客户端通常配置全部哨兵地址列表以实现查询冗余。
- 第二步订阅：同时订阅哨兵的 **+switch-master** 频道，收到事件说明发生换主，事件体中携带旧主与新主地址，客户端据此切换连接目标。
- 第三步重连：连接异常断开时，优先重新向哨兵查询最新主库地址，而不是盲目重连旧地址——旧主此时可能已经被降级为从库，发往它的写请求要么报错要么丢数据。
- 冗余设计：向**全部**哨兵地址列表发起查询，任何一个可达的哨兵都能应答，避免单一哨兵故障导致客户端无法发现主库。
- 密码场景：主库设置了访问密码时，客户端要用 sentinel auth-pass 对应的密码连接主库；哨兵本身的连接密码用 SENTINEL 命令的认证方式另行处理，两者是两套凭据。
- 工程实践：主流客户端库内置了哨兵支持，例如 Node 生态的 ioredis（详见第 30 章）传入哨兵地址列表、主从组名与密码即可自动完成发现与切换，业务代码无需手写上述逻辑。
- 读分摊：写连接之外，客户端还可以用 SENTINEL replicas 获取从库列表，把只读请求轮询到从库，充分利用主从架构的读扩展能力。
- 切换期间的表现：换主过程中旧连接会陆续报错，客户端应把**查询哨兵重连**纳入重试逻辑，而不是简单抛出异常给业务层。
- 组名约定：组名一旦确定就不应更改，它是哨兵与客户端之间的契约；换名等于换了一组监控对象。
- 只读从库的提示：从从库读取时业务要接受秒级的数据延迟，对强一致的读请求仍应回落到主库。
- 超时兜底：查询哨兵本身也要设置超时与重试，哨兵全部不可达时客户端应有明确的降级与告警策略。

三步流程示意：

```text
客户端启动
   ↓ ① 向哨兵列表查询主库地址
SENTINEL get-master-addr-by-name mymaster → 127.0.0.1 6379
   ↓ ② 与主库建立连接，正常读写
   ↓ ③ 订阅哨兵 +switch-master 频道，等待切换事件
收到 +switch-master（旧主 6379 → 新主 6380）
   ↓ 重新执行第一步，换连新主
```

> [!CAUTION]
> **注意内容**：切换发生的瞬间，不同哨兵对本组主库的记忆存在毫秒级差异，先后查询可能得到新旧两个答案；客户端不应以单次查询结果为准做最终切换，而应以订阅到的 +switch-master 事件为权威信号，否则可能把写请求连回即将降级的旧主。

**速记**：**问哨兵拿地址，连主库发请求，订 +switch-master 听切换**。



#### 脑裂风险与数据丢失的缓解

**脑裂（Split Brain）**：指网络分区期间**新旧两个主库同时接受写入**，分区恢复后旧主被降级，其上未同步给新主的数据随之丢失的现象。

- 形成场景：主库与多数哨兵之间网络中断，但仍与部分客户端连通。哨兵这边照常完成客观下线判定与换主，选出新主；客户端那边感知滞后，继续把写请求发往旧主——新旧两个主库各自接受写入，双主并存。
- 数据后果：分区恢复后，旧主被哨兵重新配置为新主的从库，并从新主全量同步数据；它在分区期间接受的所有写入**全部丢弃**，业务表现为订单、计数等数据凭空消失。
- 时间窗口：从哨兵完成切换到所有客户端都收到 +switch-master 并完成重连，中间的间隔无法消除，只能缩短——客户端心跳与重连逻辑越积极，窗口越小。
- 常态风险兜底：即使没有分区，异步复制本身也意味着主库宕机瞬间尚未传播到从库的已确认写入会随旧主降级而丢失（复制机制详见第 20 章）；脑裂只是把这一丢失窗口拉长到分区愈合为止的极端形态。
- 缓解手段：在**主库与从库**的配置中同时启用 min-replicas-to-write 与 min-replicas-max-lag，限制主库只有当足够多的从库保持连接且延迟可控时才接受写入。

```bash
# 写入主库与从库的 redis.conf（两处都要配置）
min-replicas-to-write 1
min-replicas-max-lag 10
```

- 参数含义：以上示例表示主库至少要有 1 个从库处于连接状态、且该从库的复制延迟不超过 10 秒，否则主库拒绝一切写命令并返回错误。
- 缓解原理：脑裂场景中旧主与自己的从库同处网络孤岛，从库无法上报心跳，旧主在隔离期间自动**拒绝写入**，丢失窗口从分钟级压缩到秒级。
- 参数代价：从库全部宕机或网络拥塞时，主库会拒绝写入，**用可用性换一致性**，是否启用需按业务对数据丢失的容忍度权衡。
- 客户端配合：应用在写命令收到只读错误或连接错误时，应立即重新向哨兵查询主库地址，而不是对旧连接做长时间退避重试——客户端反应越快，脑裂窗口越小。
- 识别征兆：启用了 min-replicas 参数的主库在进入孤岛时会持续拒绝写命令并在日志中记录，监控到这类日志即可确认脑裂防护已经生效。
- 告警联动：把主库日志中的拒绝写记录与哨兵事件同时接入告警系统，两条线索互相印证，可以第一时间确认孤岛与脑裂防护的状态。

一次脑裂的时间线示意：

```text
t0  网络分区：旧主与哨兵、与未来新主之间隔离，仍连着部分客户端
t1  哨兵多数派完成换主，从库 6380 晋升为新主
t2  双主窗口：客户端A 写旧主 6379，客户端B 写新主 6380
t3  分区恢复：旧主被降级为从库，向新主全量同步
t4  旧主在 t2 到 t3 期间接受的写入被全部丢弃
（配置 min-replicas 后，t0 起旧主即拒绝写入，t2 段几乎无数据）
```

> [!WARNING]
> **警告内容**：脑裂窗口内写入旧主的数据在分区恢复后无法找回，min-replicas-to-write 只能压缩窗口、不能杜绝丢失；要求强一致的业务（如金融账务）必须在应用层配合对账与补偿机制，Redis 层面的保障到此为止。

**速记**：脑裂＝**旧主诈尸双写，恢复后丢数据**；min-replicas 两参数让它**少写几秒**。



### 运维命令与适用边界

#### SENTINEL 子命令覆盖状态查看与手动干预

**SENTINEL 命令族**：运维人员向哨兵实例发送 SENTINEL 子命令，完成状态查看、地址查询、手动切换与票仓检查四类日常操作。

```bash
# 查看指定主从组的完整状态（含 flags、哨兵数、从库数）
SENTINEL master mymaster
SENTINEL replicas mymaster

# 查看该组的兄弟哨兵列表与各自状态
SENTINEL sentinels mymaster

# 查询当前主库地址（客户端接入口径）
SENTINEL get-master-addr-by-name mymaster

# 手动触发一次故障转移（跳过客观下线判定）
SENTINEL failover mymaster

# 重置该哨兵对指定主从组的全部记忆（重新自动发现）
SENTINEL RESET mymaster

# 检查当前哨兵数量是否满足多数派授权条件
SENTINEL CKQUORUM mymaster
```

- 状态查看：SENTINEL master 与 SENTINEL replicas 输出主库与从库的详细字段，重点看 flags（s_down、o_down、disconnected 等状态标记）、num-other-sentinels（已发现的兄弟哨兵数）与 info-refresh（最近一次 INFO 更新时间），是排查判定异常的第一入口。
- 地址查询：SENTINEL get-master-addr-by-name 返回主库 IP 与端口两行，供客户端与运维脚本使用，是接入流程的标准入口。
- 手动切换：SENTINEL failover 不等待下线判定直接换主，适用于计划性迁移，例如更换主库硬件、机房搬迁；切换期间写服务有秒级中断，应在业务低峰执行。
- 记忆重置：SENTINEL RESET 清空哨兵对指定组的从库与兄弟哨兵记录，随后通过 INFO 与 hello 频道重新自动发现，常用于拓扑纠错。
- 票仓检查：SENTINEL CKQUORUM 返回当前哨兵部署是否满足多数派，新环境上线验收与故障排查时应首先执行。
- 排查次序：怀疑哨兵失灵时先执行 CKQUORUM 确认票仓完好，再看主库与从库的 flags 与 info-refresh，最后检查各哨兵的配置一致性，由全局到局部逐步定位。
- 历史兼容：老版本中查看从库的子命令为 SENTINEL slaves，新版本已更名为 replicas，旧名仍被兼容保留。
- 热更新：SENTINEL SET 子命令可在运行时修改指定组的参数，例如临时调大 down-after-milliseconds；改动只作用于当前哨兵实例，需要逐台下发以保持一致。
- 排查示例：怀疑误判时先看 flags 中是否出现 s_down，再对照 info-refresh 是否停滞——停滞说明哨兵与主库之间链路有问题，而非节点本身故障。
- 输出体积：replicas 与 sentinels 的返回是长数组，脚本消费时应按字段提取所需键值，而不是整段打印到日志。
- 批量巡检：监控多组主从架构时可循环调用 SENTINEL master 汇总各组状态，形成定期巡检报表。

> 注意：SENTINEL failover 属于写操作级别的干预命令，执行前应确认没有正在进行中的自动故障转移，否则两者叠加可能造成集群状态混乱；CKQUORUM 输出若提示无法达到多数派，应优先扩容哨兵节点而不是反复重试切换。

**速记**：**master 看状态、get-master 拿地址、failover 手动切、CKQUORUM 验票仓**。



#### 哨兵与 Cluster 的适用边界

**适用边界**：哨兵与 Cluster 都提供高可用能力，但职责层次不同——**哨兵在单分片的主从架构上做故障转移，Cluster 在多分片架构上同时提供数据分布与故障转移**。

- 选哨兵：数据量单机内存可容纳、写压力单机可承受，痛点仅仅是**主库宕机需要自动换主**；此时哨兵方案改动最小、运维心智最简单。
- 选 Cluster：数据总量或写入吞吐超出单机上限，需要把 16384 个哈希槽分布到多个主节点分担容量与写入，同时要求每个分片自带高可用。
- 互斥关系：同一套数据节点要么由哨兵管理，要么纳入 Cluster，二者不能叠加；Cluster 内部的故障转移由集群节点自行协商完成，不依赖也不支持哨兵进程。
- 演进路径：业务增长过程中通常是**主从复制 → 哨兵 → Cluster** 三段演进：先加从库分摊读压力，再加哨兵解决可用性，容量顶到天花板再迁移 Cluster；每一步都在前一步的数据基础上平滑升级。
- 过度设计警惕：小规模场景硬上 Cluster 会白白引入分片复杂度，客户端从直连变为槽感知，运维从单组变成多节点协商，得不偿失。
- 判断标准：只问一个问题——**数据与写入是否超出单机上限**；没超出就用主从加哨兵，超出了才考虑 Cluster。
- 两者对照：数据分布上哨兵不分片、Cluster 按哈希槽分片；故障转移上哨兵由独立进程协商、Cluster 由数据节点自协商；客户端上哨兵先查地址再连节点、Cluster 直连后按槽重定向。
- 迁移次序：从哨兵架构迁往 Cluster 时，先搭建集群并搬迁数据、再切换客户端指向、最后下线哨兵进程；顺序颠倒会造成客户端无主可查。
- 成本意识：哨兵方案的全部成本是三个轻量进程加客户端改造；Cluster 的成本是分片规划、槽迁移与多节点运维，能力越强负担越重，按需选择即可。
- 监控分层：哨兵监控的是节点可用性，业务层还应监控缓存命中率与访问延迟，两层监控互为补充、缺一不可。
- 共同地基：无论选择哪条路径，主从复制都是底层机制，复制原理（详见第 20 章）必须先行掌握。

> 提醒：哨兵的全部机制——四大任务、两级下线判定、领头选举、故障转移四步——只服务于普通主从架构；进入 Cluster 世界后，故障转移由哈希槽与节点间的消息协议接管，机制完全不同。Cluster 的分片原理与节点协商详见第 22 章。

**速记**：哨兵管**可用性**，Cluster 管**容量加可用性**；分片需求就上 Cluster，别拿哨兵硬撑。
