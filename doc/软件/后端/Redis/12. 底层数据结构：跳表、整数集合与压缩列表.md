## 底层数据结构：跳表、整数集合与压缩列表

**跳表、整数集合与压缩列表**：是 Redis 在 SDS 与字典之外的三件紧凑武器——跳表用多层索引链表支撑有序集合的有序性与范围查询，整数集合用定宽整数数组承载元素全为整数的集合，压缩列表与它的继任者 listpack 则把少量小元素打包进一块连续内存。三者共同回答同一个问题：数据量小或访问模式特殊时，如何把内存占用与操作速度同时做到极致。

- 本章先讲跳表：节点与整体结构、层高的幂次定律生成、span 跨度的两个用途、查找插入的复杂度，以及为什么用跳表而不用平衡树。
- 再讲 ZSet 对跳表与字典的组合使用，说明双结构各自承担的职责，字典一侧的机制详见第 11 章。
- 接着讲整数集合：三种编码的选择、只升不降的升级机制与适用边界。
- 最后讲压缩列表：五部分构成、prevlen 的两档编码、连锁更新隐患，以及 Redis 7.0 的 listpack 如何从结构上根除这一隐患、quicklist 节点如何同步换代，版本脉络详见第 32 章。

### 跳表 zskiplist 的结构与原理

#### 跳表的定义与性能特征

**跳表（zskiplist）**：是一种多层有序链表，在有序链表之上为部分节点叠加索引层，把单向顺序查找优化为自上而下逐层缩小范围的查找，平均时间复杂度 O(logN)、最坏 O(N)，本质是空间换时间。

- 跳表底层是一条完整的有序链表，上层索引由底层节点**按比例抽取**构成，越往上层节点越稀疏。
- 查找从最高层出发，在每层沿前进指针尽量跨越，跨不过去就下降一层，先坐快车再换慢车。
- 平衡性由**随机层高**概率性维持，不依赖旋转或重平衡操作。
- 上层索引节点并不是数据副本，只是指向底层节点的指针引用，数据本体始终只存一份。
- 索引层数量随数据量对数增长，数千元素通常只需两三层即可覆盖。
- 最坏 O(N) 出现在层高分布极不均匀、结构退化接近单链表时，概率极低但理论存在。
- 与哈希表对比：哈希点查 O(1) 但无序，跳表略慢却换来了有序与范围能力。
- 跳表与树的本质差异在形态：树节点父子关系固定，跳表的层只是指针数量的差别，结构上仍是线性链。
- Redis 的跳表只服务于有序集合 ZSet 的底层实现，普通链表的兴衰见第 10 章。

> [!NOTE]
> **提醒内容**：跳表由 William Pugh 在 1990 年的论文 Skip Lists: A Probabilistic Alternative to Balanced Trees 中提出；Redis 在论文原始设计上额外增加了 span 跨度与 backward 后退指针，分别服务于排名计算与逆序遍历。

> 跳表常见误读：它不是树，没有根与叶的层级实体，所谓层只是同一批节点在竖直方向上的多条前进指针；图中把各层分开画是为了便于理解，内存里节点始终横向串成一体。

> 链表无法二分查找，因为二分依赖数组的随机访问能力；跳表用多级索引在链表上模拟出对数级定位，且是**概率性平衡**而非强制性平衡，这是它与平衡树的根本分野。

**速记**：多层索引链表，平均 **O(logN)**，**空间换时间**。



#### zskiplistNode 的结构详解

**zskiplistNode**：是跳表的节点结构，核心成员为 level 层数组、forward 前进指针、span 跨度、backward 后退指针，以及 score 分值与 ele 成员。

```c
typedef struct zskiplistNode {
    sds ele;                          // 成员对象，sds 字符串，元素唯一标识
    double score;                     // 分值，排序的依据
    struct zskiplistNode *backward;   // 后退指针，指向表头方向的前一个节点
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针，指向表尾方向的下一节点
        unsigned long span;            // 跨度，该前进指针跨越的节点数
    } level[];                        // 柔性数组，层高因节点而异
} zskiplistNode;
```

- **ele**：保存成员对象，是 sds 字符串，在同一跳表中不重复。
- **score**：double 类型分值，跳表按 score 升序组织全部节点；分值相同时按 ele 的字典序排列。
- **level**：柔性数组，每个元素代表一层，层内持有前进指针与跨度；层高在节点创建时随机生成，各节点不同。
- **forward**：前进指针，沿表尾方向前进；表尾节点的所有前进指针指向 NULL。
- **span**：跨度，当前层前进指针跨越的节点个数，指向 NULL 时记为 0。
- **backward**：后退指针，指向表头方向的前一个节点；每个节点只有一条，仅能沿第一层逐个后退。
- ele 与 score 在 ZSet 语义下对应成员与分值；跳表只按 score 排序，ele 仅在同分时决胜。
- level 数组按层号升序排列，level[0] 即第一层，一切查找的最终落点都在第一层。
- 节点不存储反向多层指针，backward 只有一条，从表头方向的回退能力因此受限，属有意取舍。
- 层内结构体与层高一起构成节点的可变部分，固定部分仅 ele、score、backward 三员。

单个双环节点的层结构示意：

```text
        +--------------------------------------+
        | ele: "member"    score: 2.0          |
        | backward ----------------------------|--> 前一节点
        | level[1] forward ---------------->   |   高层快车道
        | level[0] forward ---------------->   |   底层慢车道
        +--------------------------------------+
```

> [!NOTE]
> **提醒内容**：ele 的命名存在版本差异——Redis 5.0 之前该成员名为 obj、类型为 robj 指针，5.0 起更名为 ele、类型改为 sds，直接持有字符串本体，免去了对象包装；阅读不同版本的源码或旧版资料时须先确认版本，再对号入座，两版其余字段含义一致。

> forward 与 backward 的辨析：forward 每层各有一条，形成多车道快行线；backward 全节点仅一条，是第一层专用的慢行车道。二者方向相反、数量不同，并非对称设计，逆序遍历能力因此局限于第一层。

> level 用柔性数组实现，节点大小随层高在创建时一次性确定，之后不再扩容；层高不同则节点大小不同，这正是跳表节点内存布局异构、必须逐节点分配的原因。

> 节点结构里没有长度字段，跳表不在节点上存储元素计数；总数由上层 zskiplist 的 length 维护，节点自身保持轻量，这是整体结构与节点结构职责划分的体现。

**速记**：一节点**多层数组**，层载 forward 与 span，单条 backward。



#### 层的生成与幂次定律

**层的生成**：新节点的层高由幂次定律随机产生，初始为 1 层，之后每层以 25% 的概率再加一层，最高 64 层。

- 随机过程等价于反复抛一枚正面概率为 25% 的硬币：正面则层高加一，直到抛出反面或触及上限。
- 层高上限 ZSKIPLIST_MAXLEVEL 在 Redis 7.0 之前为 32，7.0 起提升为 64。
- 幂次定律使层高呈几何级数分布：第 1 层含全部节点，第 2 层约占四分之一，第 k 层约占 25% 的 k 减 1 次方。
- 表头节点例外：其层高固定为上限，永远不低于任何业务节点。
- 75% 的节点层高为 1，平均每节点前进指针数约为 1.33，空间开销远低于直觉。
- 随机比较用 16 位定点数完成，规避浮点运算，zslRandomLevel 即按此实现。
- 上限的存在防止极端随机把层高掷得过高，64 层已足以容纳天文数字级的节点数。
- 层高期望约为 1.33，与平均每节点前进指针数吻合，可作复杂度验算的口径。

各层节点占比示意：

```text
L4:                     ~1.5% 节点
L3:              ~6%    节点
L2:      ~25%    节点
L1:  100% 全部节点
```

```c
int zslRandomLevel(void) {
    static const int threshold = ZSKIPLIST_P*RAND_MAX; /* ZSKIPLIST_P = 0.25 */
    int level = 1;
    while (random() < threshold)
        level += 1;
    return (level<ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;
}
```

> 层高与节点内容无关，插入时一次掷定、终身不改；正因层高随机且不再调整，跳表才免去平衡树旋转重平衡的负担，插入删除只做指针摘接，这也是 Pugh 论文的核心思想。

> 上限调整的历史佐证了层高分布的稀薄：32 层足以覆盖天文数字量级的节点，Redis 7 提至 64 层更多是前瞻性冗余，实际负载几乎永远掷不满。

> 幂次定律的名字来自分布形态：层高每升一级，期望节点数就乘以同一个分数，概率质量集中在低层，少数节点偶然爬到高层充当快车道，整体呈指数衰减形态。

**速记**：层高**掷骰子**，25% 再升一层，封顶 64。



#### span 跨度的两个用途

**span 跨度**：记录前进指针跨越的节点数，承担计算排名与表示步数两大用途。

- **计算排名**：从表头出发沿查找路径把沿途各层的 span 累加，即得目标节点的位次，ZRANK 命令再减 1 转为 0 起算的排名，全程无需额外遍历计数。
- **表示步数**：相邻节点之间 span 为 1，一次前进跨越 k 个节点则 span 为 k，各段 span 相加就是从当前节点到目标节点的步数。
- **度量查找代价**：查找路径的长度可由 span 静态得出，便于评估跳表效率与调试定位。
- **插入时的修正依据**：新节点接链后，各层前驱节点的 span 按查找路径上累加的 rank 拆分重算，保证跨度账目始终自洽。
- ZREVRANK 的结果可由元素总数减正序排名直接换算，同样不增加跳表的额外负担。
- span 的修正只发生在插入删除所经路径上，其余节点的跨度永不变动，维护成本局部化。
- span 为 unsigned long 类型，足以记录任何现实规模下的跨度，不存在溢出之忧。

排名计算示意：

```text
ZADD board 30 carol 40 dave 50 eve
ZRANK board eve
查找 eve 的路径各段 span 相加得位次 3，ZRANK 对外返回 2（0 起算）
```

> span 与层的辨析：span 不是层号，也不描述节点在竖直方向的位置，它只记录水平方向跨越了多少节点；指向 NULL 的前进指针 span 恒为 0，不代表跨到了表尾。

> span 是 Redis 对经典跳表的增强：原版论文没有该字段，排名必须另行遍历计数；有了 span，ZRANK 与 ZREVRANK 都能在一次 O(logN) 查找内顺带完成。

> 排名语义以第一层为准：跳表按 score 升序、同分按 ele 字典序排列，ZRANK 衡量的正是节点在第一层序列中的位置，因此同分成员的排名稳定可复现。

**速记**：span 一箭双雕——**累加得排名，相加即步数**。



#### zskiplist 的整体结构与查找插入过程

**zskiplist**：是管理全部节点的跳表整体结构，包含 header、tail、level、length 四个成员。

```c
typedef struct zskiplist {
    struct zskiplistNode *header, *tail; // 表头节点与表尾节点
    unsigned long length;                // 节点数量，不含表头
    int level;                           // 当前所有节点中的最大层高
} zskiplist;
```

- **header**：特殊表头节点，不存储数据，层高固定为上限，是所有查找与插入的起点。
- **tail**：指向表尾节点，支持 O(1) 取最大元素，也是逆序遍历的起点。
- **length**：节点计数，不含表头，ZCARD 一类命令直接读取，无需遍历。
- **level**：当前最大层高；新节点层高超出时上调，删除最高层独苗节点后下调。

查找与插入过程示意：

```text
L3: header -------------------------------------> [50] ------> NULL
L2: header -------------> [20] ------------------> [50] ------> NULL
L1: header -> [10] -> [20] -> [30] -> [40] -> [50] -> [70] -> NULL

查找 40：L3 在 50 前退回，L2 经 20 停在 50 前，L1 顺序命中 40
插入 40：先复现查找路径并逐层记录前驱，再按随机层高创建节点逐层接链
删除 40：逐层摘链并修正沿途 span，若是最高层独苗则下调整体 level
```

- **查找**：自最高层开始，前进指针指向节点的分值不大于目标就前进，否则落到下一层，直到第一层命中或确认不存在。
- **插入**：先按查找路径逐层记录前驱节点并累加 rank，再生成随机层高、创建节点并逐层接链，同时按 rank 拆分修正沿途 span。
- **删除**：先定位目标节点，逐层摘链并修正前驱 span，最后释放节点。
- **更新**：修改已存在成员的分值时，Redis 不做原位调整，而是先删除旧节点再重新插入，因为分值变化会破坏有序性。
- 查找路径上的每一步都可由 span 复述，调试时可打印各层前驱逐层核对账目。
- ZINCRBY 引起的分值变化同样走删旧插新路径，跳表不提供原位改分接口。

```text
ZADD rank 10 tom 20 jerry 30 spike 40 max
ZRANGE rank 0 -1       # 定位起点后沿第一层顺序输出，范围扫描即线性走链
ZREVRANGE rank 0 0     # 借 tail 指针 O(1) 落到表尾，再沿 backward 回退
```

> 表头节点没有 ele、score 与 backward，自身不参与排名计算；查找的每一步都发生在某一层之内，跨层只发生在下降动作上——这两点在画图与推演时最易出错。

> span 在删除后同样要修正：被删节点跨越的层段由前驱接管，前驱 span 取被删节点自身 span 减一与原前驱 span 之和的对应组合，保证路径账目连续。

> 查找复杂度的直觉解释：每层期望只需常数次前进即可大幅收窄候选，层数为 O(logN)，故平均代价 O(logN)；层高全部退化时退回 O(N)。

> 插入时若新节点层高超过现有 level，整体 level 立即上调并把表头接到新层；表头永远保持最高层覆盖，否则高层查找会漏节点。

**速记**：header 起步、**逐层收窄**、span 记账、length 直供。



#### 为什么用跳表而不用平衡树

**选型结论**：Redis 有序集合采用跳表而非平衡树或红黑树，核心原因有三——实现简单、范围查询天然友好、并发改造容易。

- **实现简单**：无旋转、无变色、无强制重平衡，插入删除只做指针操作，代码量与出错面远小于 AVL 树与红黑树。
- **范围查询友好**：定位区间起点后沿第一层前进指针顺序扫描即可，ZRANGE、ZRANGEBYSCORE 一类命令天然契合；平衡树做范围需中序遍历，实现绕远。
- **并发改造容易**：跳表的插入删除只触及局部前驱后继，便于改造为无锁或细粒度锁结构，LevelDB 与 Memcached 内部的跳表均受益于此。
- **性能不差**：平均 O(logN) 与平衡树同阶，概率性平衡的期望深度在实践中足够稳定。
- **内存可控**：由于 75% 的节点只有一层，平均每节点前进指针数约 1.33，空间开销远低于直觉。
- **排名免费送**：借助 span，跳表还能顺带支持平衡树不易实现的 O(logN) 排名查询。
- 范围查询成本低：ZRANGE 只需一次定位加一次线性扫描，无须额外维护区间结构。
- 工业验证充分：LevelDB、RocksDB 与 Redis 的长期实践说明跳表足以承载生产负载。
- 内存数据库的选型常被读写放大绑架，跳表局部修改的特点天然规避了整树调整的写放大。

> 与红黑树的辨析：红黑树每个节点固定两个子指针，内存更省；跳表以少量额外指针换来简单与范围友好。在内存与实现复杂度之间，Redis 作者选择了简单，并辅以 span 增强了平衡树也不具备的排名能力。

> 与 B 树一族的辨析：B 树为磁盘页设计，节点大、树高低，适合块设备；Redis 面向内存，节点小、指针跳转即可，跳表更贴合内存场景，无须为磁盘页大小妥协。

> 选型的启示：在内存数据库里，结构的简单可靠往往比理论最优更重要；跳表用概率平衡替代强制平衡，把维护复杂度从运行期转移到了设计期。

**速记**：**简单、范围、并发**三赢，性能与平衡树同阶。



### ZSet 对跳表与字典的组合使用

#### ZSet 同时使用字典与跳表的原因

**双结构设计**：ZSet 的底层同时持有字典与跳表两个结构——字典负责 O(1) 查分值，跳表负责范围查询与排名，二者通过指针共享同一份数据。

- **字典（dict）**：以成员 ele 为键、分值 score 为值的哈希表，支撑 ZSCORE 一类点查 O(1) 完成，字典机制详见第 11 章。
- **跳表（zskiplist）**：同一批成员按 score 升序串成有序链，支撑 ZRANGE、ZRANK、ZRANGEBYSCORE、ZCOUNT 等范围与排名命令。
- **指针共享**：两个结构各自持有的是指向同一 sds 字符串与同一分值的指针，成员字符串本体只存一份，不构成内容冗余。
- **命令择路**：点查走字典，范围与排名走跳表，每类命令各取所长。
- WITHSCORES 与范围类命令全部落在跳表一侧，字典对这些命令毫无参与。
- ZCARD 直接读取跳表的 length 字段返回元素总数，无须遍历任何结构。
- 两结构的长度恒等：跳表的 length 与字典的键值对数量始终一致，二者皆可作为 ZCARD 的读数来源。
- ZSet 的类型编码与对象系统全貌，详见第 13 章。

双结构各自的用武之地：

```text
ZADD leaderboard 100 alice 90 bob 95 carol
ZSCORE leaderboard bob               # 走字典：O(1) 直接取分值
ZRANK  leaderboard bob               # 走跳表：O(logN) 沿 span 累加得排名
ZRANGE leaderboard 0 -1 WITHSCORES   # 走跳表：第一层顺序扫描整个区间
```

> [!IMPORTANT]
> **重要内容**：ZSet 双结构共享指针而非复制数据，这是理解其空间开销的关键——冗余的是每个成员多出一组结构与指针开销，而非成员与分值本身被存两份。

> 空间与时间的取舍：只为 ZSet 保留字典会失去有序能力，只保留跳表则点查退化为 O(logN)；双结构让每类命令都走最优路径，代价是可接受的指针冗余，属于主动的空间换时间。

> 写路径的一致性代价：ZADD、ZINCRBY、ZREM 等修改命令必须同步维护两个结构，先改字典再改跳表，任一不同步都会造成两边数据失配，这是双结构方案的主要实现负担。

> 同分排序由 ele 字典序兜底，这让分值相同的成员在 ZRANGE 输出中顺序稳定；字典一侧不感知任何排序，两边职责边界清晰。

> 双结构的存在也解释了 ZSet 命令复杂度标注的差异：同一集合点查 O(1)、排名 O(logN)、取全部成员 O(N)，三条曲线分别对应字典、跳表与线性扫描。

**速记**：**字典查分数、跳表管范围**，指针共享不复制。



### 整数集合 intset

#### 整数集合的定义与三种编码

**整数集合（intset）**：是集合全部元素均为整数且数量不多时 Set 的底层实现，本质是一段有序、去重的整数数组，采用 int16、int32、int64 三种编码之一。

```c
typedef struct intset {
    uint32_t encoding; // 编码方式：INTSET_ENC_INT16、INT32、INT64 三选一
    uint32_t length;   // 元素数量
    int8_t contents[]; // 柔性数组，真实类型随 encoding 切换
} intset;
```

- **int16 编码**：数组每项占 2 字节，可表示 -32768 至 32767 的整数。
- **int32 编码**：每项占 4 字节；**int64 编码**：每项占 8 字节，可表示 64 位有符号整数。
- contents 按数值**升序排列且不重复**，有序性是二分查找的前提，去重性由插入时的命中检测保证。
- 编码由集合中**宽度最大的那个数**决定：能被 int16 装下就绝不升级，按需取最小类型以省内存。
- contents 声明为 int8_t 只是便于按字节寻址的技巧，真实读法随 encoding 而定。
- 结构中没有容量字段，contents 是定长柔性数组，每次插删都按需重新分配整块内存。
- 三种编码均为有符号整数，没有无符号变体，编码选择按数值的绝对范围判断。
- 有序加去重让小集合的 SISMEMBER 可走二分，是 intset 场景下最快的点查形态。
- 重复插入在二分命中时即被拒绝，contents 因此天然不含重复值，无须事后清理。

int16 编码的存储示意：

```text
SADD nums 5 12 40 97 320
encoding = INT16，每项 2 字节，contents 升序排列：
| 5 | 12 | 40 | 97 | 320 |
```

> encoding 字段名中的 INT16 含义是数组项的最小宽度，而非内容只有 16 位整数的承诺；一个 int32 编码的集合里，数值较小的元素同样按 4 字节存放，不会按元素单独压窄。

> intset 的内存布局没有对齐填充：编码宽度即实际字节宽度，contents 挨个紧排，是 Redis 各结构里最贴近裸数组的实现。

**速记**：**有序去重整数数组**，三种编码按最大数取最小宽度。



#### 编码升级规则

**编码升级**：新插入整数超出当前编码的表示范围时，整数集合把整个数组按更宽的类型逐个迁移重编码，且**只升不降**。

- 升级三步：按新编码计算数组所需总空间并重新分配内存；从尾到头把旧元素逐个重编码搬移到新位置；更新 encoding 字段并把新元素写入腾出的位置。
- **从尾到头迁移**是为了避免向前搬移时覆盖尚未处理的元素，新元素恰好落在最后一个被腾出的槽位。
- 升级是全局动作：哪怕只插入一个 64 位整数，全部旧元素都要重写一遍，代价 O(N)。
- **只升不降**：编码一旦升级便不随元素删除而回退，int16 集合升为 int32 后不会再变回 int16。
- 升级判断在插入路径最前端完成，先定编码、再腾位写入，两步串行不可颠倒。
- 旧元素搬移到新槽位时按新宽度对齐放置，原 2 字节项在新 4 字节槽位中符号扩展存放。

升级过程示意：

```text
int16 数组：| 5 | 12 | 40 |          插入 70000 → 70000 超出 int16 → 触发升级
按 int32 重新分配，从尾到头重编码：| 40 | 12 | 5 | 空 |
写入新元素：| 5 | 12 | 40 | 70000 |   encoding 变为 INT32，每项 4 字节
```

> [!CAUTION]
> **注意内容**：删除大数值元素不会触发降级，一个曾混入过大数的集合将长期按宽编码占内存；确需回收空间时，只能整体重建集合。

> 升级与连锁更新的辨析：intset 升级是全集合一次性重编码，代价 O(N) 封顶；后文 ziplist 的连锁更新是逐节点连环扩展，最坏 O(N²)。二者都源于紧凑设计，严重程度不同。

> 升级不改变有序性与去重性：重编码按原顺序逐项搬移，升序依旧；新元素写在前次命中的空槽，位置仍由二分插入点决定。

> 升级路径没有回滚：即使随即删掉触发升级的那个数，编码与已分配空间也不回收，设计上以多占内存换取结构稳定，避免反复升降抖动。

> 升级仅由插入触发、删除只减数量，这一非对称是阅读 intset 源码的关键线索：编码判断只出现在插入路径，删除路径里找不到任何升级或降级逻辑。

**速记**：超范围**全体升级**、从尾到头重编码、**只升不降**。



#### intset 的查找与插入

**intset 的查找与插入**：查找基于 contents 的有序性使用二分查找，时间 O(logN)；插入先二分定位再腾位写入，必要时先升级，整体 O(N)。

- **查找**：二分比较，intsetSearch 返回命中与否及所在位置，查找、插入、删除三个操作共用它。
- **插入已存在元素**：直接返回失败，集合保持去重。
- **插入新元素**：二分确定插入点，memmove 腾出空间后写入，length 加一；数值超范围时先触发升级再插入。
- **删除**：二分定位后整体搬移覆盖被删位置，length 减一，编码不降级。
- 复杂度评估：查找 O(logN)，插入与删除因搬移为 O(N)，触发升级时再叠加重编码的 O(N)。
- 头尾特判：新元素小于最小值或大于最大值时无需二分，直接头插或尾插，这类场景在自增场景中占比很高。
- SADD 的返回值差异即来源于此：命中重复返回 0，真正新插入返回 1。
- 升级判断与插入合并为一次流程：确认无需升级后定位写入，最坏两段 O(N) 相加仍为 O(N)。

> intset 只适用于元素全为整数的小集合：一旦混入任意字符串元素，或元素数量超过配置阈值，Set 就切换为字典编码，切换门槛见第 6 章与第 13 章。

> intset 没有对外暴露专属命令，它的存在对使用者透明：SADD、SREM、SISMEMBER 等命令在底层自动按集合内容选择 intset 或字典编码，调用方无须感知切换。

> 二分比较按 encoding 解码后进行，与编码宽度解耦：无论 contents 是 int16 还是 int64，算法只有一份，读法由 encoding 决定。

> 升级与插入的先后也有讲究：先按新值确定目标编码再分配空间，可避免二分定位后二次扩容，一次重分配完成全部动作。

**速记**：**二分 O(logN)**，插删搬移 O(N)，命中重复即拒绝。



### 压缩列表 ziplist 的结构与缺陷

#### 压缩列表的结构回顾

**压缩列表（ziplist）**：是为极致省内存设计的顺序紧凑结构，整块连续内存依次存放若干特殊编码的节点，Redis 7.0 起已被 listpack 全面取代。

```text
| zlbytes | zltail | zllen | entry1 | entry2 | ...... | zlend |
   4字节     4字节    2字节                                     1字节

单个 entry：| prevlen | encoding | content |
```

- **zlbytes**（4 字节）：整个压缩列表占用的内存字节数，供内存重分配与 zlend 定位使用。
- **zltail**（4 字节）：表尾节点距离起始地址的偏移量，可不遍历直接定位尾节点。
- **zllen**（2 字节）：节点总数，超过 65534 时该字段装不下，须遍历才能得出真实数量。
- **entry**：节点本体，由前一节点长度 prevlen、自身编码 encoding、自身数据 content 三部分组成。
- **zlend**（1 字节）：固定值 255，标记列表末端。
- 头部三字段加尾部一字节，固定开销合计仅 11 字节，几乎可以忽略。
- entry 的 encoding 标识 content 是字符串还是整数及字节长度，小整数有专用紧凑编码。
- zltail 让尾部定位无须遍历，与 zllen 配合可在多数情况下常数步完成计数与定位。
- 存储密度是它的最大优点：没有指针、没有对齐填充，节点紧挨节点，一段内存从头用到尾。
- 曾服务于 List、Hash、ZSet 的小规模编码场景，7.0 起全部让位给 listpack。

> 阅读布局时须记住 entry 长度可变：各 entry 的 prevlen 与 encoding 宽度都可能不同，不能按固定步长跳跃访问，只能逐节点解码前进。

> prevlen 的长度规则是理解 ziplist 的命脉：前一节点长度小于 254 字节时 prevlen 占 1 字节，否则占 5 字节；这个 1 字节与 5 字节之间的跳变，正是连锁更新问题的祸根。

> zlbytes 与 zlend 的组合让整块内存可以整体重分配：扩容按 zlbytes 加新尺寸 realloc，收缩同理，这是连续内存结构共同的红利。

**速记**：头部 **zlbytes、zltail、zllen**，尾部 **zlend**，中间挤满 entry。



#### 连锁更新问题

**连锁更新（cascade update）**：插入或删除节点迫使后续节点的 prevlen 在 1 字节与 5 字节之间跳变，从而引发的连环内存重分配现象，最坏时间复杂度 O(N²)。

- 诱因：新插入节点达到一定长度后，紧随其后节点的 prevlen 由 1 字节扩展为 5 字节，该节点自身总长随之增长，又迫使再下一个节点的 prevlen 扩展，逐个向后传递。
- 触发条件苛刻：需要连续多个节点总长恰好落在 250 至 253 字节之间，扩展 4 字节后才跨过 254 的门槛，实际业务中概率很低。
- 最坏情形：一次插入引发 N 次逐节点重分配，每次重分配又伴随内存搬移，总代价 O(N²)。
- 删除同样可能连锁：删掉一个短节点后，其后节点的 prevlen 由 5 字节缩为 1 字节，反向引发连环收缩。
- 查找本身也是短板：ziplist 没有索引，按成员定位须顺序遍历，O(N) 起步。
- prevlen 扩展重写的是后继节点的头部字段，content 本体不动，但节点总长变化仍需整块内存腾挪。
- 连环传播沿表尾方向进行，删除引发的收缩则朝表头传播，两类情形由同一段循环代码处理。
- ziplist 时代的常见缓解手段是把节点长度控制在远离临界区间的范围，这本质上是与应用层耦合的规避技巧。

连锁更新逐级传播示意：

```text
entry2.prevlen 由 1 字节扩展为 5 字节 → entry2 总长跨过 254
→ entry3.prevlen 也要 1 变 5 → entry3 总长跨过 254
→ entry4.prevlen 同样扩展 …… 一路向后连环重分配
```

> [!WARNING]
> **警告内容**：连锁更新叠加 ziplist 本身 O(N) 的顺序查找，节点一多性能急剧恶化；根治手段是升级到 Redis 7.0 使用 listpack，低版本应避免把大量临界长度的元素塞进同一个 ziplist。

> 触发概率低的原因：节点总长要恰好连续落在 250 至 253 字节区间，本身概率不高还要连续出现，故真实业务中连锁更新鲜少成为瓶颈，但理论风险始终存在。

> 连锁更新与 intset 升级的辨析：intset 升级是一次性重编码、O(N) 封顶；连锁更新是逐节点连环扩展、最坏 O(N²)。前者可控，后者有尾部风险，这也是 ziplist 被 listpack 取代、intset 仍保留的原因。

> Redis 实现中对连锁更新做了防御式处理：插入删除后检查是否触发连锁并循环修复，但并没有从根本上避免重分配，治本要靠 listpack 的结构改造。

**速记**：prevlen **1 变 5 连环涨**，最坏 **O(N²)**，7.0 后被 listpack 取代。



### listpack 紧凑列表

#### listpack 的定义与结构

**listpack（紧凑列表）**：是 Redis 7.0 起全面取代 ziplist 的连续内存紧凑列表，每个节点自带 header 与 backlen，只记录与自身有关的信息。

```text
整体布局：| 头部 | entry1 | entry2 | ...... | 末端 |
单个 entry：| header | data | backlen |
```

- **header**：节点自身的编码信息，记录 data 是字符串还是整数及其长度，与前一节点无关。
- **data**：实际数据，按 header 的编码存放字符串或整数。
- **backlen**：节点自身总长的变长编码，占 1 至 5 字节，供从尾向头反向遍历时回跳使用。
- 整个 listpack 仍是一块连续内存，头部记录总字节数与节点数量，沿用 ziplist 的省内存思路。
- backlen 采用变长编码：长度小时只占 1 字节，长度大时逐字节扩展，与数据体量自适应。
- 变长编码让小节点付 1 字节即够 backlen，大节点也至多 5 字节，开销有明确上界。
- 头部记录总字节数与节点数，尾端保留末端标记，与 ziplist 的整体布局一脉相承。
- listpack 头部字段与 ziplist 同名同义，迁移改造时上层读取逻辑基本平移。

> 与 ziplist 相比，listpack 没有引入新的压缩技巧，它的价值在于布局契约的修正——把记别人改成记自己，以小改动消除大隐患。

- 适用场景：Hash、ZSet、List 在小规模元素下的紧凑编码，省内存的同时结构简单。

> backlen 与 prevlen 方向相对：backlen 记自己多长、在从尾向头遍历时按它回跳；prevlen 记前一个多长、在正向遍历与反向定位时使用。方向一换，连锁更新的土壤即被铲除。

> listpack 的名字强调列打包：所有节点装进一块连续内存，中间没有任何空洞与对齐垫片，序列化与传输时整块拷贝即可。

**速记**：entry 三件套 **header、data、backlen**，**只记自己、不记别人**。



#### listpack 如何消灭连锁更新

**连锁更新的消除**：listpack 的节点不记录前一节点的长度，任何节点的增删都不影响其他节点的字段，从结构上根除了 prevlen 跳变引发的连环重分配。

- 插入节点：写入新 entry 并更新头部计数即可，后续节点不发生任何字段变化，不触发连环重分配。
- 删除节点：摘除该 entry 并更新计数，后继节点原样保留。
- 反向遍历改由 backlen 支撑：从尾节点出发按 backlen 逐个向前回跳，替代 ziplist 依赖 prevlen 的反向定位。
- 增删代价稳定且局部化，性能可预期，不再有最坏 O(N²) 的尾部风险。
- 由于每节点多了 backlen，单节点开销略高于 ziplist 的最短情形，换来的是完全消除级联风险。
- 增删后的修正范围缩小到头部计数字段，重分配次数从可能 O(N) 降为常数次。
- 反向遍历与正向对称，每按一次 backlen 回跳都是常数代价，无须任何全局重算。

两代紧凑结构的对照：

```text
ziplist：entry 记录 prevlen（前一节点长度）→ 邻节增删会改写字段 → 可能连环重分配
listpack：entry 只记 header 与 backlen（自身信息）→ 邻节增删与我无关 → 无连环
```

> listpack 并未改变顺序结构的本质：按成员查找仍是顺序遍历 O(N)，因此它只适合元素不多的场景；元素增多后上层对象会切换为字典、跳表等编码，切换规则详见第 13 章。

> 结构改造的启示：连锁更新不是算法问题而是契约问题——prevlen 让相邻节点之间产生隐式依赖；listpack 砍掉依赖字段，问题在结构定义层面即被消灭。

> 复杂度对账：ziplist 时代最坏 O(N²) 的尾部风险被整体移除，listpack 的增删从最好常数、最坏平方变为稳定常数次重分配，性能上界重新变得可信。

**速记**：**不记前节长度**、backlen 反向回跳，连锁更新无处发生。



### quicklist 快速列表

#### quicklist 的定义与混合结构

**quicklist（快速列表）**：是用双向链表把多个 listpack 串联起来的混合结构，块与块之间灵活插删、块内连续内存省存储，兼顾内存与性能。

- 外层是**双向链表**：每个 quicklistNode 持有前驱与后继指针，节点之间插删 O(1)。
- 节点内是**listpack**：每个节点持有指针指向一块 listpack，少量元素挤在同一块连续内存，免去每元素一个链表节点的指针与元数据开销。
- quicklist 层集中维护头尾节点指针、节点计数与元素总数，支持 O(1) 取头尾与整体计数。
- 每个节点还记录自身 listpack 的字节数与元素数，便于按块判断是否需要拆分合并。
- 每个节点另有 recompress 标记，记录该节点是否因临时解压而待重新压缩。
- 头尾节点由 head、tail 直连，LPUSH、RPOP 一类命令常数步内即可定位。
- 元素总数与节点数分两级记账，LLEN 一类统计直接读全表计数，无须遍历。
- 节点的 sz 字段记录所在块的字节数，判断块是否超限时直接读取无须重算。
- List 类型的底层在元素较多时即为此结构，命令行为详见第 5 章。

```c
typedef struct quicklist {
    quicklistNode *head, *tail;   // 头节点与尾节点
    unsigned long count;          // 全部元素总数
    unsigned long len;            // quicklistNode 节点个数
    int fill;                     // 单节点 listpack 的长度上限，正数限个数
    unsigned int compress;        // 两端之外压缩的节点深度
} quicklist;
```

> 两个极端的辨析：纯双向链表插删快，但每元素都要背负两个指针加节点元数据，内存浪费严重；单个大 listpack 省内存，但中间插删要整块搬移。quicklist 取中间态——块内紧凑、块间灵活，是内存与性能的折中设计。

> 块的粒度由 fill 决定：块越多越接近纯链表、插删越快但内存越贵；块越少越接近单个 listpack、内存越省但搬移越重，quicklist 的性能特征落在两个极端之间且连续可调。

> quicklist 的演进轨迹本身就是一部取舍史：3.2 前的 List 在 ziplist 与 linkedlist 之间二选一，3.2 引入 quicklist 合二为一，7.0 起节点内部的 ziplist 又统一换成 listpack，方向始终是取两家之长、去两家之短。

> 判断理解是否到位可自问三个数字：一个元素最多经历几次指针跳转、一个块最多装多少字节、一块被压缩后读写要付多少额外成本，答案分别藏在节点链、fill 与 compress 里。

**速记**：**链表串 listpack**，块内省内存、块间好插删。



#### fill 与 compress 参数

**fill 与 compress**：quicklist 的两个核心调节参数，fill 限定每个节点内 listpack 的长度上限，compress 限定两端之外多少个节点用 LZF 算法压缩。

- **fill 为正数 n**：每个 listpack 最多容纳 n 个元素。
- **fill 为负数**：按字节限长，-1 至 -5 分别对应 4KB、8KB、16KB、32KB、64KB 的单节点上限，默认配置取 -2。
- **compress 为 0**：不做任何压缩；为正数 n 时，首尾各 n 个节点保持原样，中间节点用 LZF 压缩存储。
- **两端免压缩**的原因：List 的读写集中在头尾，热区不压缩保证常用操作零解压开销，冷区压缩换取内存节省。
- 节点的增删会引起 listpack 的拆分与合并：超限的块从中间分裂，过小的块向邻块合并，保证块大小始终贴近 fill 约束。
- LZF 是轻量级无损压缩，压缩解压都很快，属于以极小 CPU 换明显内存节省的选择。
- compress 深度按两端保留的节点数计，取值越大保留的原样块越少、压缩面越大。
- 两个参数都可经 CONFIG SET 运行时调整，存量节点按新参数逐步重排与重压缩。
- 参数改动只影响此后新建与重排的节点，旧块在写入时逐步向新配置收敛。

> 观测手段：OBJECT ENCODING 可确认当前 List 的编码，MEMORY USAGE 可量化压缩前后的内存差异，调参后用二者对照验证收益。

compress 取值的示意：

```text
compress = 1，节点序列 A - B - C - D - E：
A 与 E 原样保留（首尾各 1 个），B、C、D 以 LZF 压缩存放
读写命中压缩节点时先解压，操作后再视 recompress 标记压回
```

```text
list-max-listpack-size -2   # 单节点上限 8KB，旧名 list-max-ziplist-size
list-compress-depth 1       # 首尾各留 1 个节点不压缩
```

> [!TIP]
> **建议内容**：追求内存就调小 fill 并增大 compress，追求吞吐就调大 fill 或将 compress 设为 0；被压缩节点读写时须临时解压，频繁访问列表中段的场景不宜开深压缩。

> 配置名变迁的辨析：Redis 7.0 前参数名为 list-max-ziplist-size 与 list-compress-depth，7.0 起前者更名为 list-max-listpack-size，语义不变，只是底层由 ziplist 换成了 listpack。

> 经验默认值：fill 取 -2 即 8KB 上限、compress 取 0，多数负载下无须改动；确有超长列表且访问集中于头尾时，才值得开启压缩换内存。

**速记**：fill 定**节点多大**，compress 定**压多深**，两端常热不压缩。
