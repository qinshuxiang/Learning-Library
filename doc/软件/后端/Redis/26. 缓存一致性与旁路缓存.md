## 缓存一致性与旁路缓存

**缓存一致性**：是指同一份数据同时存在于缓存与数据库两个存储层时，二者取值保持一致的性质——本章以业界最主流的**旁路缓存（Cache Aside）**模式为主线，讲清它的读写流程、两个步骤顺序选择的并发依据、残余不一致窗口的概率分析，以及延迟双删、异步重试、binlog 订阅等补救手段，最后站在 CAP 视角说明为什么工程上只能追求最终一致，而 TTL 是一切手段的兜底。

- 本章先讲模式本身：旁路缓存的读写流程，以及两个最经典的追问——为什么删缓存而不是更新缓存、为什么先更新数据库再删缓存。
- 再讲模式的边界：读写并发下仍存在的不一致窗口，用时序图把它拆到毫秒级，并给出概率与业务容忍度的评估方法。
- 然后讲补救手段：延迟双删的原理与争议、删除失败的两种异步处理路径（消息队列重试与订阅 binlog），以及其他三种经典缓存模式的取舍。
- 最后收束到理论：CAP 视角下强一致不可得，工程目标是把不一致窗口压进业务容忍区间，TTL 是永远生效的最后防线。
- 前置衔接：本章的读路径与第 25 章三类缓存故障共用同一条未命中分支，读路径骨架不再重复展开；示例代码沿用 Node.js 风格，与第 30 章的 ioredis 实战相互印证。

### 旁路缓存模式的读写流程

旁路缓存是缓存一致性问题发生的舞台，先把模式的完整流程与两个顺序选择讲透，后面的补救手段才有落点。

#### 旁路缓存的定义与读写流程

**旁路缓存（Cache Aside）**：应用代码同时握着缓存与数据库两个存储层，读请求先走缓存、未命中再走数据库并回填，写请求先更新数据库、再删除缓存——缓存只是主存储（数据库）旁边的一条加速旁路，故得此名。

- **读路径**：先读缓存，命中直接返回；未命中则读数据库，把结果回填缓存并设置 TTL，再返回。
- **写路径**：先更新数据库，成功后再删除对应的缓存键，而不是去更新缓存内容。
- **职责归属**：缓存条目的建立与失效全部由应用代码显式维护，缓存层自身不感知数据库，这也是「旁路」的另一层含义——缓存在数据访问路径的旁边，由应用代码来缝合两条路。
- **读多写少适配**：该模式的收益建立在读远多于写的前提上，写路径的删除是每次写都要付出的固定成本。
- **与第 25 章的衔接**：读路径未命中分支的三类故障（穿透、击穿、雪崩）与对策已在前一章展开，本章聚焦写路径与一致性问题。

```js
// 旁路缓存完整读写骨架（Node.js 伪代码）
async function getItem(key) {
  const cached = await redis.get(key);            // ① 先读缓存
  if (cached !== null) return JSON.parse(cached); // 命中：直接返回

  const data = await loadFromDb(key);             // ② 未命中：读库
  if (data === null) return null;
  await redis.set(key, JSON.stringify(data), "EX", BASE_TTL_SECONDS); // ③ 回填
  return data;
}

async function putItem(key, value) {
  await saveToDb(key, value);   // ① 先更新数据库
  await redis.del(key);         // ② 再删除缓存（是删除，不是更新）
}
```

> 辨析：「旁路」不是「备胎」——缓存承载的是主要读流量，数据库反而是被旁路绕开的那一侧；模式的全部一致性风险都来自「同一份数据落在两个地方、两步写操作又不是原子的」这一根本事实，后续所有手段都是在为这条裂缝打补丁。

**速记**：**读走缓存未命中回源，写先更库再删缓存**，应用代码是缝合两条存储路径的人。



#### 为什么是删除缓存而不是更新缓存

**删除缓存**：写路径在更新数据库之后，对缓存执行的是删除动作而非写入新值——把缓存的最新值推迟到下一次读未命中时懒加载回填，这是模式中最经典的取舍之一。

- **并发写覆盖**：两个写请求并发更新缓存时，缓存写入顺序不可控——写 A 先把缓存更成值 A，写 B 随后更成值 B；但数据库落库顺序可能相反（B 先、A 后），最终缓存是 B、数据库是 A，**旧值覆盖新值**，且这一错误状态无人纠正，会一直活到下一次删除或过期。
- **懒加载避免写放大**：写一次就更一次缓存时，新值可能在被读之前又被覆盖，白写多次；删除把回填推迟到真正有人读的那一刻，冷数据的反复更新完全不触碰缓存。
- **计算成本**：更新缓存往往意味着先查出完整最新对象再序列化写入（缓存里存的常常不是单行而是聚合结果），删除只需要一个键名，成本天然更低。
- **幂等性优势**：删除是幂等操作，删两次无害；而「更新」一旦乱序，错的就是终态——失败重试时删除可以放心重试，更新必须先判断时序。

> [!IMPORTANT]
> **重要内容**：并发写覆盖是删除优于更新的决定性理由——**缓存值必须与数据库值在同一个时序基准上生成**，先更缓存后更库的做法让缓存值先于数据库值生效，两个写请求交错时必然出现缓存与数据库分属两个版本的撕裂；删除把缓存值的生成推迟并重新锚定到读路径的数据库查询上，撕裂自然愈合。

> 例外提示：若一个 key 读极多、写极少且每次读都要求缓存必有值（如全局配置项），也可以选择写路径直接更新缓存，避免删除后第一波读的回源抖动，但必须保证「先更库、后更缓存」且写并发极低，否则并发覆盖问题仍然存在。

**速记**：**删除等一次读，更新赌一把时序**——懒加载让缓存值永远锚定数据库最新态。



#### 为什么先更新数据库再删除缓存

**先更新数据库再删除缓存**：写路径两步的顺序铁律——反过来先删缓存再更新数据库，会在并发读写下制造长期脏数据，把两个顺序的并发时序摆在一起对比，结论是唯一站得住的选择。

- **先删后更的窗口**：写请求先删缓存，此刻另一个读请求到达——缓存未命中，去读数据库，读到的还是**旧值**（数据库尚未更新），随后把旧值回填进缓存；写请求这才完成数据库更新，而缓存里躺着的已是旧值，且没有人再删它，脏数据长期留存，直到 TTL 到期。
- **先更后删的窗口**：读请求先在缓存未命中、查到数据库旧值，写请求恰在其间完成「更库加删缓存」，读请求最后把旧值回填——同样存在不一致，但触发条件苛刻得多：要求**读先 miss、且写操作完整地插在「查库」与「回填」两步之间**，这两步的间隔通常是毫秒级，命中概率远低于先删后更的情形。
- **先删后更还有回源放大**：更新数据库期间的所有读请求全部未命中，回源压力集中打到数据库；若更新耗时较长，等于人为制造一次小规模击穿（详见第 25 章）。
- **结论**：两害相权，先更后删的不一致窗口更短、触发条件更苛刻、失败影响更可控，是通说与主流实践公认的顺序。

```text
先删缓存再更新数据库——脏数据长期留存的时序：

写请求：① DEL cache ──────── ②③④⑤  UPDATE db（耗时较长）──► 完成
读请求：        ② 缓存未命中
                ③ 读数据库 ──► 拿到旧值
                ④ 回填缓存（旧值）
                ⑤ 返回旧值
结果：数据库已是新值，缓存是旧值，且再无人删除 ──► 脏数据活到 TTL 到期

先更新数据库再删除缓存——偶发不一致的时序：

读请求：① 缓存未命中 ── ② 读数据库（旧值）── ③④ ── ⑤ 回填缓存（旧值）
写请求：                 ③ UPDATE db ── ④ DEL cache ──► 完成
结果：仅当写完整地插在读请求②与⑤之间才不一致，窗口为毫秒级，概率低
```

> 辨析：先更后删并非零风险——上图中若回填发生在删除之后，缓存依然是旧值；区别在于触发需要「读 miss 加写恰好插入」的双重巧合，而先删后更只需要「删后有一个读」这一个平凡条件。把概率压低与把概率归零是两回事，残余窗口的分析见下一节。

**速记**：**先删后更留长疤，先更后删缝小口**——顺序选择的依据是窗口长短与触发概率。



### 残余不一致窗口与概率分析

先更后删不是完美方案，把它残余的不一致窗口拆到毫秒级，是评估「要不要上更强手段」的前提。

#### 读写并发的不一致时序

**残余不一致窗口**：即使严格遵循先更库后删缓存，读写并发仍可能让旧值完成最后一次回填——这个窗口由读路径「查库」与「回填」两个动作之间的空隙构成。

- **时序拆解**：读请求 miss 后查库拿到旧值，正要回填时被调度暂停；写请求插进来完成更库加删缓存；读请求恢复执行，把旧值写进缓存——写请求的删除发生在回填之前，等于白删。
- **不一致时长**：旧值会在缓存里活到该 key 下一次被写（删除）或 TTL 到期；写频率高的 key 很快被下一次写纠正，写频率低的 key 则可能活满整个 TTL。
- **触发三条件**：一是读请求恰好 miss（命中率越高概率越低）；二是查库与回填之间恰好插入一次完整写；三是窗口期内没有后续写来纠正。三者同时成立概率很低。
- **量化视角**：概率约为「读 miss 率乘以查库到回填的间隔占单位时间的比例再乘以写频率」，在常见参数组合下量级可达百万分之一以下——但**低概率不等于不发生**，读多写少的系统里总会撞上。
- **概率分析的价值**：算出概率与脏数据存活时长，就能回答「业务能不能忍」——能忍就不必为小概率上复杂架构，不能忍再引入下一节的补救手段。

```text
残余不一致窗口的时序（读写并发）：

读请求：① miss ── ② 查库得旧值 ── ③（挂起）──────── ⑤ 回填旧值
写请求：                          ④ 更新库 ── ④' 删缓存 ──► 完成
关键：删除（④'）发生在回填（⑤）之前，删除被回填覆盖，旧值留存
```

> [!NOTE]
> **提醒内容**：这一窗口是旁路缓存模式的**固有属性**，靠调换步骤顺序无法消除，只能靠删除重试、延迟双删或异步订阅等手段进一步压缩——理解「窗口固有」这一点，才能避免陷入「再调一下顺序就完美了」的误区。

**速记**：**miss 加写恰好插队，旧值最后一次回填**——窗口固有，只能压缩不能归零。



#### 一致性等级与业务容忍度

**一致性等级选择**：把系统对不一致的容忍度显式化为指标——容忍多长的窗口、容忍读到多旧的值——再据此选手段，是比「追求最强一致」更工程化的做法。

- **强一致**：任何时刻读到的都是最新值，缓存加数据库的架构下需要分布式锁或分布式事务把读写串行化，性能代价通常不可接受，绝大多数业务并不需要。
- **最终一致**：允许中间时刻读到旧值，但保证停止写入后经过有限时间两边必然收敛一致——旁路缓存加删除重试加 TTL 的组合属于这一档。
- **容忍窗口三问**：不一致对业务是钱的事还是体验的事（库存超卖是钱，头像更新慢半拍是体验）；最长能容忍多旧（秒级、分钟级还是更久）；读到旧值的后果是否可逆。
- **典型取舍**：账户余额、库存等强一致语义字段不宜只靠旁路缓存兜底，要么不走缓存、要么叠加数据库层面的原子操作；资讯、详情、排行等展示类数据容忍秒级陈旧，先更后删足矣。
- **手段阶梯**：容忍度高——裸的旁路缓存；中——加删除重试与延迟双删；低——上 binlog 订阅的准实时失效，甚至放弃缓存直接读库。

> [!IMPORTANT]
> **重要内容**：不要问「缓存与数据库怎么才能强一致」，正确的问题是「**业务的容忍窗口有多长、现有手段能把窗口压到多短**」——缓存架构设计的本质是窗口管理，而不是消除窗口。

**速记**：先问业务**能忍多久**，再选**压窗手段**，别上来就追强一致。



### 延迟双删的原理与争议

延迟双删是针对并发回填旧值的一个流行补丁，理解它能解决什么、解决不了什么，比记住操作序列更重要。

#### 延迟双删的原理

**延迟双删**：在写路径中删除两次缓存、中间留一段延迟——常见序列为「删缓存、更新数据库、等待若干毫秒、再删一次」，第二次删除的目的是清掉窗口期内其他读请求回填的旧值。

- **针对场景一（先删后更）**：写请求先删缓存、正在更新数据库期间，读请求 miss 并回填了旧值；第一次删除已用掉，靠延迟后的第二次删除把这批旧值清掉。
- **针对场景二（先更后删的残余窗口）**：读请求在写请求删除之后完成了旧值回填；第二次删除若发生在回填之后，可以把这个残余也清掉——但前提是延迟时长恰好覆盖这个并发交错，这是概率而非保证。
- **延迟时长的选取**：经验值为读路径「查库加回填」的总耗时再留余量，通常几百毫秒到一秒；太短清不到并发回填，太长则扩大第二次删除之前的脏窗口。
- **执行方式**：延迟期间同步休眠会占用线程，工程实现一般把第二次删除丢进异步任务或延迟消息，不阻塞主流程。
- **两次删除都要考虑失败重试**：双删只是把删除次数翻倍，删除本身的可靠性问题依然要靠下一节的重试机制兜底。

```js
// 延迟双删骨架（第二次删除走异步定时器，不阻塞写请求）
const DOUBLE_DELETE_DELAY_MS = 800;

async function updateWithDoubleDelete(key, value) {
  await redis.del(key);          // 第一次删除
  await saveToDb(key, value);    // 更新数据库
  setTimeout(() => {
    redis.del(key).catch(logError); // 第二次删除：异步执行
  }, DOUBLE_DELETE_DELAY_MS);
}
```

> 辨析：延迟双删通常与**先删缓存再更库**的序列搭配使用——有些团队因回源压力或框架限制选择这个顺序，双删就是给这个顺序配的补偿；若本身已采用先更库后删缓存的顺序，第二次删除的边际收益取决于残余窗口的实际概率，未必值得引入。

**速记**：**删一次不够就删两次，中间歇一拍**——第二次删除清的是并发期回填的旧值。



#### 延迟双删的争议

**延迟双删的争议**：它被广泛传播的同时也被广泛质疑——核心争议在于延迟时长只能按经验估计、第二次删除只能压低概率而不能消除不一致，以及它对主流程与架构复杂度的真实代价。

- **争议一：延迟值无理论解**：并发交错的完成时刻不可预知，任何固定延迟都可能太短（没覆盖交错）或太长（扩大脏窗口），通说认为它本质是按经验参数化的启发式补偿，不是有保证的机制。
- **争议二：不解决删除失败**：若第一次或第二次删除本身失败，双删形同虚设；它没有内建重试语义，可靠性仍要外挂。
- **争议三：收益场景有限**：若已按先更库后删缓存实现，残余窗口概率本来就低，为它引入异步任务、延迟消息与监控的成本可能大于收益。
- **争议四：更库耗时不可控时失效**：数据库更新若因锁等待而耗时超过延迟值，第二次删除先于更库完成，等于白删，甚至早于脏数据产生。
- **公允评价**：延迟双删是**低成本的概率压缩器**，不是正确性保障——把它当作锦上添花的补偿可以，把它当作一致性方案的核心不可。

> [!CAUTION]
> **注意内容**：不要把延迟双删当作一致性问题的**终解**向团队推广——它掩盖问题的时间可能长于解决问题的时间；正确路径是先确认读写顺序正确，再用消息队列或 binlog 订阅保证删除可靠，双删仅在明确观察到「并发回填旧值」的实际案例时作为局部补丁使用。

**速记**：双删是**概率补丁不是保证**，用时先问残余窗口是否真的被观察到。



### 删除失败的处理

删除缓存可能因网络抖动、Redis 故障、进程崩溃而失败，两条异步化路径把「删可靠」从业务代码中剥离出去。

#### 消息队列重试删除

**消息队列重试删除**：写路径删除缓存失败后，把待删除的键投递进消息队列，由独立消费者重试删除直到成功，用异步补偿把最终一致性维持住。

- **基本流程**：更新数据库后尝试删缓存，失败则把键写入队列（也可无条件都走队列，把删除整体异步化）；消费者取出键、重试删除，仍失败则按队列的重试策略退避重试，消息队列的选型与原理详见第 24 章。
- **重试上限与兜底**：多次重试仍失败的消息进入死信队列，触发告警与人工介入；无论重试多少轮，TTL 都会兜底，见本章末节。
- **顺序与幂等**：同一键的多次删除天然幂等，无需担心重复消费；但同一键连续多次写时，队列要保证删除不乱序，按键哈希到同一分区是常见做法。
- **耦合度权衡**：业务代码要感知队列发送，属于轻度侵入；相比同步重试，异步队列把删除延迟从写路径中移走，写请求不再被 Redis 故障拖住。
- **轻量变体**：规模小的场景可用定时任务轮询重试表替代完整队列，键与重试计数落库，失败次数超限告警，本质相同。

```js
// 删除失败转投递重试（示意）
async function putItemWithRetry(key, value) {
  await saveToDb(key, value);
  try {
    await redis.del(key);          // 同步先删一次
  } catch (error) {
    await sendToQueue("cache-invalidate", key); // 失败：转异步补偿
  }
}
```

> 辨析：不要把「删除失败」与「删除前 Redis 已不可达」混为一谈——后者意味着消费者此刻大概率也删不动，异步补偿的意义在于把删除动作**延后到 Redis 恢复之后**自动补齐，这正是异步重试相对同步重试的核心价值。

**速记**：**删不掉就排队慢慢删**，失败动作交给消息队列，写路径绝不为 Redis 故障买单。



#### 订阅 binlog 异步删除

**binlog 订阅删除**：用中间件订阅数据库的变更日志（MySQL 的 binlog），解析出数据变更事件后驱动缓存删除，让「删缓存」彻底从业务代码中消失，由数据变更本身触发。

- **Canal 的工作原理**：Canal 把自己伪装成 MySQL 的一个从库，向主库拉取 binlog，解析出增删改对应的行级变更事件，再投递给下游——常见下游是消息队列，由缓存删除服务消费执行删除。
- **解耦收益**：业务代码只管写数据库，删除缓存对业务完全透明；新业务、老业务、脚本直改数据库，删除都能被统一触发，杜绝「改库忘删缓存」的人为遗漏。
- **链路形态**：数据库、Canal、消息队列、缓存删除服务、Redis 五级串联，全链路异步，删除滞后通常在毫秒到秒级。
- **适用前提**：数据变更必须以数据库为唯一入口且 binlog 为行格式，直接改缓存而不改库的路径不会被捕获。
- **代价**：引入 Canal 与队列两个组件，部署与排障复杂度上升；表结构与缓存键的对应关系需要额外维护。
- **同类中间件**：云厂商普遍提供数据订阅服务，PostgreSQL 生态有逻辑复制槽加逻辑解码插件等等价物，原理与 Canal 一致。

```text
binlog 订阅删除链路（示意）：

业务写 ──► MySQL（binlog，ROW 行格式）
              │
              ▼
        Canal（伪装为 MySQL 从库，拉取并解析 binlog）
              │  变更事件（表、主键、操作类型）
              ▼
        消息队列 ──► 缓存删除服务 ──► 删除 Redis 对应键
```

> [!TIP]
> **建议内容**：多团队共享数据、写入入口难以收敛的系统，binlog 订阅是**性价比最高的最终一致方案**——一次搭好链路，所有写路径自动获得缓存失效能力；写入入口单一、变更量小的系统，从简的消息队列重试即可，不必为架构美感引入中间件。

**速记**：**库变了缓存跟着变**，Canal 伪装从库听 binlog，删除与业务代码彻底解耦。



#### 最终一致的达成路径

**最终一致**：写操作完成后的有限时间内，缓存与数据库的取值必然收敛一致——达成路径是「正确顺序、可靠删除、TTL 兜底」三层叠加，每一层负责一类不一致来源。

- **第一层：正确顺序**：先更库后删缓存，把窗口压到最小，属于结构性预防。
- **第二层：可靠删除**：队列重试或 binlog 订阅保证删除动作最终成功，消除删除失败这一类残留。
- **第三层：TTL 兜底**：任何手段都失效时，过期时间给不一致一个确定的上界，属于最后防线。
- **监控配套**：对账任务抽样比对缓存与数据库取值、统计删除消息的积压与死信量、给不一致窗口打点——最终一致要有证据，不能靠信仰。
- **与强一致的边界**：最终一致不承诺「任意时刻读到新值」，读路径在窗口内仍可能拿到旧值，这一点要在方案评审时向业务方明示。

> [!IMPORTANT]
> **重要内容**：三层缺一不可——只有顺序没有可靠删除，删除失败即产生长窗口脏数据；只有可靠删除没有 TTL，任何一次链路故障都可能让不一致**无限期**存续；TTL 是唯一不依赖任何组件存活的保底机制。

**速记**：**顺序防、删除补、过期兜**，三层叠加成就最终一致。



### 其他缓存模式

旁路缓存之外还有三种经典读写模式，它们把缓存维护责任上移到缓存组件，或以一致性换写性能，理解取舍才能解释为什么旁路缓存是默认选择。

#### Read Through 与 Write Through

**Read Through 与 Write Through**：两种把缓存层升级为「唯一门面」的模式——应用只与缓存对话，数据库的读写由缓存组件代理，同步逻辑从应用代码转移到缓存组件。

- **Read Through（读穿透）**：应用只向缓存要数据；未命中时由**缓存组件自己**查库并回填，应用代码不接触数据库。与旁路缓存的差别只在「谁来查库」——旁路是应用查，Read Through 是缓存组件查。
- **Write Through（写穿透）**：应用向缓存写数据，缓存组件**同步地**先写数据库、再更新缓存，两步完成后才返回成功——读写都经过缓存这个门面，缓存与数据库同步推进。
- **一致性优势**：Write Through 把「写库」与「写缓存」收拢到一个组件内顺序执行，不存在旁路缓存模式的应用层并发交错，一致性更容易做对。
- **实现前提**：需要缓存组件内建存储抽象，进程内缓存库常提供此类能力；Redis 作为独立服务时，工程上常见做法是用统一的缓存中间层把这两种语义封装出来，调用方无感。
- **代价**：写路径同步等待两步完成，时延高于先更库再删缓存的旁路模式；冷数据也会随写被带入缓存，缺少懒加载的过滤效果。

> 辨析：Read Through 与旁路缓存读路径的分辨标准是**回填代码的位置**——写在应用里是旁路缓存，写在缓存组件内是 Read Through；行为相似，职责归属不同，面试中常以此设问。

**速记**：**Read Through 缓存代读，Write Through 缓存代写**，应用只认缓存一个门面。



#### Write Behind 异步写回

**Write Behind（Write Back，异步写回）**：写请求只更新缓存即返回，缓存积累的变更由后台线程**异步批量刷回**数据库——用一致性换写性能的激进模式。

- **原理**：写落在缓存里立即生效并返回，后台按固定周期或脏数据阈值把变更合并刷回数据库，与操作系统页缓存回写磁盘是同一个思想。
- **收益**：写时延降到缓存操作量级，批量合并能大幅减少对数据库的写次数，适合写入极其密集、单条写入价值密度低的场景，如计数、点赞、浏览量累加。
- **风险一：丢数据**：缓存宕机时，尚未刷回数据库的变更全部丢失——这是它与旁路缓存最本质的分野，旁路缓存里数据库永远是完整的，Write Behind 里数据库长期落后于缓存。
- **风险二：复杂度**：脏数据追踪、刷回排序、缓存与数据库冲突合并都要自己实现，缓存组件必须持久化或高可用才敢承载未刷回数据。
- **适用判断**：数据可容忍丢失、或可从其他源头重算（计数可由流水重放）时才敢用；订单、余额类数据绝不可用。

> [!CAUTION]
> **注意内容**：Write Behind 的丢数据风险是**结构性的**——崩溃瞬间未刷回的变更无法找回，启用前必须回答「这批数据丢了会怎样」；答案不能接受的业务，写性能再紧张也不应选用此模式，可改用消息队列削峰后顺序入库。

**速记**：**写缓存即返回，后台慢慢刷库**——买来极致写性能，卖掉的是不丢数据的保证。



### CAP 视角与 TTL 兜底

把前文所有工程手段收拢到理论坐标里，回答最后一个问题：缓存与数据库之间到底能做到多一致。

#### CAP 视角下的一致性边界

**CAP 视角的结论**：缓存与数据库是分布式系统中两个独立的存储节点，网络分区不可避免，二者之间做不到强一致——工程目标是在可用性与分区容忍的前提下，把最终一致的窗口压进业务容忍范围。

- **CAP 简述**：一致性、可用性、分区容忍三者不可兼得，网络分区必然发生时，实际选择只在 CP 与 AP 之间。
- **缓存加数据库的归属**：这是一对为读性能服务的 AP 组合——写路径数据库为主、缓存旁路失效，读路径优先可用（返回旧值也好过拒绝服务），属于典型的最终一致架构。
- **强一致的代价**：要强一致就得让读写请求在同一协调者上串行化，等于给每次读写叠加分布式共识的开销，缓存带来的读加速被大幅吃掉（借助分布式锁串行化的思路详见第 27 章）——这也是 CP 选型在缓存场景少见的根本原因。
- **工程翻译**：把 CAP 的抽象命题翻译成本章语言——窗口分析是量化不一致，删除重试与 binlog 订阅是收敛机制，业务容忍度是 AP 选择的自觉声明。

> [!NOTE]
> **提醒内容**：CAP 中的 C 指线性一致性这个最强等级，而缓存一致性语境下的「一致」大多是最终一致——两个「一致」同名不同义，讨论时先对齐定义，避免用 CAP 直接否定缓存方案的误读。

**速记**：**缓存与库天生两节点**，分区下强一致不可得，工程做的是窗口管理。



#### TTL 兜底的意义

**TTL 兜底**：给缓存条目统一设置过期时间，使任何一致性手段失效后留下的脏数据也有确定的存活上界——它是唯一不依赖任何其他组件正确性的保底机制。

- **意义一：不一致有上界**：删除重试会失败、binlog 链路会断裂，但 TTL 到期自动失效，脏数据最长存活时间被钳制在 TTL 之内，不一致从「可能无限期」变成「确定有限度」。
- **意义二：修复无需人知**：TTL 之后的第一次读会回源重建，数据自动回到与数据库一致的最新值，修复过程不依赖告警与人工。
- **意义三：与内存治理同源**：TTL 同时是过期删除（详见第 14 章）与内存淘汰（详见第 15 章）的输入，一套参数兼顾一致性与内存健康。
- **设置原则**：TTL 不得超过业务的容忍窗口；配合随机抖动防止集体过期（详见第 25 章）；对一致性敏感的 key 可以刻意调短 TTL，用回源成本换窗口收缩。
- **评审最后一问**：评审任何缓存方案时都要问一句「所有异步手段全挂了，脏数据最多活多久」——答案就是 TTL，答不出来说明方案有漏洞。

> [!TIP]
> **建议内容**：把 TTL 当作**兜底预算**来管理——按业务容忍窗口倒推出 TTL 上限，再在预算内尽量调大以提升命中率；监控里同时盯住各前缀 key 的 TTL 分布与实际脏数据对账结果，让兜底从口头承诺变成可观测的指标。

**速记**：**TTL 是最后的保险丝**，一切手段失效，过期时间替不一致画上句号。
