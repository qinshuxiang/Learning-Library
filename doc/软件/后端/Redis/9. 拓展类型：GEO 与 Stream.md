## 拓展类型：GEO 与 Stream

**GEO 与 Stream**：是 Redis 在统计工具之外的两个专项结构——GEO 把经纬度编码进有序集合，提供地理半径与区域查询能力；Stream 是只追加的消息日志，提供消息 ID、消费组与待确认机制，是 Redis 内置的轻量消息队列方案。

- 本章先讲 GEO：底层实现（geohash 编码为 52 位整数存入 zset）、六个核心命令、编码原理与误差来源，以及附近的人、门店查询两类典型应用。
- 再讲 Stream：消息 ID 格式、写入与裁剪、独立读取、消费组体系（XGROUP、XREADGROUP、XACK、XPENDING、XCLAIM）与 PEL 语义。
- 最后做三方对比：Stream 与 List 的阻塞弹出、与发布订阅、与 RabbitMQ、Kafka 等专业消息队列的能力边界与选型。
- GEO 的查询结果、Stream 的消息投递都发生在内存与单线程之内，理解第 16 章的事件循环是理解二者阻塞行为的前提。
- Stream 的工程化实践（可靠投递模式、与 Lua 结合）在第 24 章展开，本章只锚定数据结构本身的能力与语义。

### GEO：地理空间索引

#### GEO 的定义与底层实现

**GEO**：是 Redis 3.2.0 引入的地理空间索引用法——把位置成员的经纬度编码后存入一个 zset，以 zset 的有序性支撑按半径、按矩形区域查询附近成员。🌍

- GEO 不是新的底层结构，键的真实类型就是 **zset**（ZSet 详见第 7 章，跳表结构详见第 12 章）：成员是位置名，分值是坐标经 geohash 编码得到的 **52 位整数**。
- 编码思路：把经度、纬度各自的取值区间反复二分，将两串二分结果按位交织成一个二进制串，取其 52 位整数值作为 zset 的 score。
- 64 位 double 的尾数恰好有 52 位，足以无损容纳这个整数，因此编码后的分值不损失精度。
- 相近的地理位置会得到相近的编码值，zset 按 score 排序后，地理上邻近的点在集合中也是邻近的，这是半径查询得以高效进行的根基。
- 所有 GEO 命令都直接作用在这个 zset 上，因此 zset 的通用命令同样可用：**ZREM** 删除成员、**ZRANK** 查排名、**ZSCORE** 返回编码整数值而非坐标。
- GEO 没有独立的删除命令，删除位置一律通过 ZREM；整个键的过期与键管理规则与其他键一致（详见第 2 章）。

```bash
GEOADD stores:beijing 116.404 39.915 shop:1
TYPE stores:beijing
ZSCORE stores:beijing shop:1
```

```text
127.0.0.1:6379> GEOADD stores:beijing 116.404 39.915 shop:1
(integer) 1
127.0.0.1:6379> TYPE stores:beijing
zset
127.0.0.1:6379> ZSCORE stores:beijing shop:1
"4065884169420875"
```

> 用 ZSCORE 读出的是 52 位编码整数而不是坐标，这是 GEO 键本质是 zset 的直接证据；想拿回经纬度要用 GEOPOS 做反解。删除成员用 ZREM，因为 GEO 命令族没有提供删除能力。

**速记**：GEO 就是 **zset 的地理视角**，成员是位置名、score 是 **52 位 geohash 编码整数**，删除靠 **ZREM**。



#### GEOADD：写入地理坐标

**GEOADD**：向地理索引写入一个或多个成员的坐标，完整签名 GEOADD key [NX | XX] [CH] longitude latitude member [longitude latitude member ...]。

- 参数顺序固定为**经度在前、纬度在后**，与数学上习惯的横纵坐标顺序不同，是高频笔误点。
- 合法范围：经度 -180 到 180，纬度 -85.05112878 到 85.05112878（Web 墨卡托投影的上下边界），越界直接报错。
- NX 与 XX 互斥：**NX** 表示只新增、已存在成员不更新；**XX** 表示只更新、不存在成员不写入。
- **CH**（changed）：默认返回新增成员数，加 CH 后返回被改动的成员数（新增与更新都计入）。
- 每个成员的写入复杂度为 O(log(N))，N 是索引内成员数，代价来自 zset 的插入。
- 同一键可存多个成员，键不存在时自动创建；成员不可重复，重复写入同一名成员即更新其坐标。

> [!CAUTION]
> **注意内容**：经纬度顺序颠倒时未必报错——把纬度写进经度位不会越界，只有把大于 85.05 的经度写进纬度位才会触发范围错误。若两个数值恰好都落在合法区间，位置会被**悄悄存错**，所有距离与查询结果随之失真，写入端务必封装统一的存入函数。

```bash
GEOADD geo:demo 116.404 39.915 a 121.473 31.230 b
GEOADD geo:demo NX 116.500 39.900 a
GEOADD geo:demo XX CH 116.600 39.880 a
```

> NX 写已存在的 a 返回 0 且坐标未变；XX 加 CH 更新 a 返回 1，表示发生了 1 次改动。没有 CH 时 XX 更新返回 0，容易误判为失败。

**速记**：**经度在前**，范围经度 180、纬度 85.05 封顶，**NX 只增、XX 只改、CH 数改动**。



#### GEOPOS 与 GEOHASH：读回坐标与编码

**GEOPOS**：返回成员的经纬度，完整签名 GEOPOS key member [member ...]；**GEOHASH**：返回成员的标准 geohash 字符串，完整签名 GEOHASH key member [member ...]。

- 两者都是每成员 O(1)，都是纯读命令，键或成员不存在时对应位置返回 nil，不影响其他成员。
- GEOPOS 返回的坐标是**从编码反解出来的近似值**：末尾若干位可能与写入值不同，误差在编码网格尺度之内。
- GEOHASH 返回 **11 个字符**的标准 base32 geohash，与内部 52 位表示对应，读出时不损失精度。
- geohash 字符串可从右侧截断来降低精度：字符越少网格越大、定位越粗，但仍指向原来的大致区域。
- 前缀相近的 geohash 位置必然相近；**反之不成立**——前缀不同的两个 geohash 也可能相邻（恰在网格边界两侧）。
- geohash 字符串便于在应用层做粗粒度分桶、缓存与展示，例如只取前 5 个字符做同城聚合。

```bash
GEOPOS geo:demo a
GEOHASH geo:demo a b
```

> GEOPOS 返回的反解值通常是一串长小数，与写入值的末尾几位不同，这是编码网格反解的痕迹，属正常现象而非数据损坏；成员不存在时对应位置返回 nil，命令整体照常执行。

**速记**：GEOPOS 拿回的是**反解近似坐标**，GEOHASH 拿回的是 **11 字符标准编码**，可截断降精度，前缀相近必相近、反过来不成立。



#### GEODIST：测量两成员距离

**GEODIST**：返回地理索引内两个成员之间的距离，完整签名 GEODIST key member1 member2 [M | KM | FT | MI]。

- 单位四选一：**M** 米（默认）、**KM** 千米、**FT** 英尺、**MI** 英里，7.0 起单位大小写均可。
- 返回值为 double 字符串，表示按指定单位计算的球面距离；复杂度 O(1)。
- 任一成员缺失时返回 nil，而不是报错，调用方需区分 0 距离与成员不存在。
- 距离基于反解坐标计算，并把地球当作**理想球体**处理，与真实测地距离存在细小偏差，城市级 LBS 场景可忽略。
- 距离只与两个成员的编码有关，与查询方向无关：GEODIST key a b 与 GEODIST key b a 结果一致。

```bash
GEODIST geo:demo a b
GEODIST geo:demo a b km
GEODIST geo:demo a missing
```

> 以北京、上海两成员为例，GEODIST geo:demo a b km 返回约 1068 千米，与常识一致；任一成员缺失时返回 nil。球体近似带来的偏差通常在千分之一量级以内（通说数据，随两点位置变化），对门店距离、骑手调度这类业务完全够用，不应用于测绘级需求。

**速记**：**默认米、四单位可选**，缺成员给 **nil**，结果按**理想球体**计算、允许细小偏差。



#### GEOSEARCH：区域查询与 GEORADIUS 的废弃

**GEOSEARCH**：在地理索引内查询落在指定圆形或矩形区域中的成员，是 6.2.0 引入的统一查询命令，完整签名 GEOSEARCH key FROMMEMBER member | FROMLONLAT longitude latitude BYRADIUS radius unit | BYBOX width height unit [ASC | DESC] [COUNT count [ANY]] [WITHCOORD] [WITHDIST] [WITHHASH]。

- 中心点二选一：**FROMMEMBER** 以索引内已有成员为圆心，**FROMLONLAT** 以给定坐标为圆心，二者互斥。
- 形状二选一：**BYRADIUS** 按半径圆形查询，**BYBOX** 按宽、高查询轴对齐矩形，二者互斥。
- 排序：**ASC** 由近到远、**DESC** 由远到近；不加则结果顺序不作保证。
- **COUNT count** 限制返回条数；追加 **ANY** 时服务器凑够数量即返回，速度更快但结果可能未按距离排好序，且不保证是最近的那些。
- 三个可选回传项：**WITHDIST** 附带距离、**WITHCOORD** 附带坐标、**WITHHASH** 附带 52 位编码原始分值，可叠加，返回结构变为嵌套数组。
- 复杂度 O(N+log(M))，N 是区域包围盒内元素数、M 是区域内项目数；不带 ANY 的 COUNT 会对区域内全部结果排序，大区域取很小的 COUNT 也可能偏慢。
- **版本与废弃**：GEORADIUS、GEORADIUSBYMEMBER（3.2.0）及其只读变体 GEORADIUS_RO、GEORADIUSBYMEMBER_RO（3.2.10）自 6.2 起被官方标注废弃，官方明确建议改用 GEOSEARCH；需要落库结果时用同为 6.2 新增的 **GEOSEARCHSTORE**。旧版本实例上废弃命令仍可用，但新代码一律写 GEOSEARCH（版本演进详见第 32 章）。

```bash
GEOSEARCH geo:demo FROMLONLAT 116.40 39.90 BYRADIUS 300 km ASC COUNT 2 WITHDIST
```

> 以坐标为圆心、300 千米半径查询，WITHDIST 在每个成员名后附带距离；BYBOX 的写法为 BYBOX 宽 高 单位，返回结构与本例一致，叠加 WITHCOORD、WITHHASH 时每个成员会相应追加坐标数组或 52 位编码整数值。

> [!NOTE]
> **提醒内容**：官方对 GEORADIUS 系列的废弃是**替代建议**而非立即移除，存量脚本仍能运行；但 GEOSEARCH 补上了旧命令没有的 BYBOX 能力，迁移只会增加能力不会损失能力，新项目没有理由再写旧命令。

**速记**：中心 **FROMMEMBER 或 FROMLONLAT**、形状 **BYRADIUS 或 BYBOX**，ASC、DESC、COUNT、ANY 控制结果，**WITH 三件套**附带详情，6.2 起**全面取代 GEORADIUS 系列**。



#### geohash 编码原理与精度误差

**geohash 编码**：把二维坐标压进一维整数的过程——对经度、纬度区间交替二分，每轮二分得一个二进制位，把两串位按经纬交织的固定规则排列，截取 52 位即为编码值。

- 二分过程：以经度为例，区间 [-180, 180] 每次按目标值落在左半还是右半记 0 或 1，区间随之折半；纬度在 [-85.05, 85.05] 上同样处理。
- 交织规则使相邻位置的编码值在数轴上也大致相邻：zset 按编码排序后，查询半径内成员只需在有序集合上定位一段连续区间再逐个过滤。
- 精度由位数决定：52 位对应非常细的网格，GEOHASH 命令返回的 11 字符标准编码与 52 位内部表示等精度（通说资料给出其网格在数十厘米量级，仅作数量级参考）。
- 误差来源一：**量化误差**。坐标被吸入固定网格，GEOPOS 反解出的是网格内的值而非原值，误差恒定在网格尺度内。
- 误差来源二：**计算误差**。GEODIST 按理想球体计算，不是真实的椭球测地线。
- 误差来源三：**降精度误差**。应用层自行截断 geohash 字符串会成倍放大网格，分桶聚合时要清楚截断位数对应的尺度。
- 对业务的影响：附近的人、门店查询对百米级误差不敏感，这些误差通常可以接受；要求精确到米的定位类需求不应以 GEO 为唯一数据源。

> [!IMPORTANT]
> **重要内容**：理解**误差来源固定且可控**是放心使用 GEO 的前提——量化误差与球体近似都是结构自带的常数级偏差，不随数据量增长；真正会放大错误的是写入端经纬度颠倒与业务层盲目截断编码，这两类属于人为缺陷而非结构缺陷。

**速记**：**交替二分加位交织**得 52 位整数，误差来自**量化、球体近似、截断**三处，常数级、可控、够 LBS 用。



#### 实战：附近的人与门店查询

**附近查询**：GEO 的两类典型应用共享同一套命令组合——GEOADD 写入、GEOSEARCH 查询、GEODIST 算距离，差别只在键设计与过滤口径。

- 附近的人：键设计为 geo:user:城市 或按天拆分的 geo:user:日期，成员是用户 ID，动态位置由客户端定位后周期性 GEOADD 覆盖更新。
- 查询：GEOSEARCH geo:user:beijing FROMMEMBER 1001 BYRADIUS 5 km ASC COUNT 20 WITHDIST，取最近 20 人，应用层剔除自己并叠加性别、标签等业务过滤。
- 门店查询：键设计为 geo:store:城市，成员是门店 ID；用户发起请求时以用户坐标 FROMLONLAT 查 3 千米内门店，WITHDIST 让前端直接展示距离。
- 距离与营业状态等多维过滤：GEOSEARCH 只懂地理距离，门店营业、库存等条件由应用层对结果二次过滤，或先用业务条件圈定成员集合再入 GEO 键。
- 写入频率控制：骑手、行人这类高频移动对象按秒级上报时，单键写入 QPS 可能很高，可按城市拆键、降低单键规模与竞争。
- 排序与分页：GEOSEARCH 的 ASC 加 COUNT 组合等价于按距离取 TopN，没有原生的距离分页，翻页需在应用层基于 WITHDIST 结果排序截取。

> [!WARNING]
> **警告内容**：GEO **没有成员级过期机制**——用户流失后其位置成员永久留在 zset 里，键会只增不减，附近的人查到的可能是三年前的坐标。动态位置必须配合应用层心跳表定期 ZREM 失效成员，或按天拆键后对旧键设置 TTL 自动回收（过期删除详见第 14 章）。

```bash
GEOADD geo:user:beijing 116.397 39.909 1001
GEOADD geo:user:beijing 116.418 39.921 1002
GEOSEARCH geo:user:beijing FROMMEMBER 1001 BYRADIUS 5 km ASC COUNT 10 WITHDIST
GEODIST geo:user:beijing 1001 1002 m
```

```text
127.0.0.1:6379> GEOADD geo:user:beijing 116.397 39.909 1001
(integer) 1
127.0.0.1:6379> GEOADD geo:user:beijing 116.418 39.921 1002
(integer) 1
127.0.0.1:6379> GEOSEARCH geo:user:beijing FROMMEMBER 1001 BYRADIUS 5 km ASC COUNT 10 WITHDIST
1) 1) "1001"
   2) "0.0002"
2) 1) "1002"
   2) "2368.4600"
127.0.0.1:6379> GEODIST geo:user:beijing 1001 1002 m
"2368.4600"
```

> 用户 1001 查附近 5 千米，结果按距离升序且第一个是自己（距离 0），应用层跳过即可；用户 1002 距其约 2.37 千米。需要在前端地图打点时，命令上追加 WITHCOORD 即可一并取回坐标。

**速记**：**GEOADD 更新位置、GEOSEARCH 取附近、GEODIST 算距离**，业务过滤留在应用层，动态位置必须**自建失效清理**。



### Stream：只追加日志

#### Stream 的定义与消息 ID 格式

**Stream**：是 Redis 5.0.0 引入的只追加日志结构——消息按写入顺序排列、每条消息拥有全局唯一且严格递增的 ID，并在此之上提供随机访问、范围查询与消费组等复杂消费策略，是 Redis 内置的轻量消息队列方案（工程实践详见第 24 章）。📨

- 每条消息称为**条目**，由一个消息 ID 与若干**字段-值对**组成，字段-值对按写入顺序存储，读取顺序与写入顺序完全一致。
- 消息 ID 格式为 **毫秒时间戳-序号**，如 1526919030474-55：前半部分是写入时刻的 Unix 毫秒时间，后半部分是同一毫秒内的序号，两部分都是 64 位整数。
- 使用星号占位时服务器自动生成 ID：取当前毫秒时间，同一毫秒内序号从 0 起递增，保证 ID 严格递增。
- 严格递增带来**全序保证**：流内任何条目的 ID 都大于其前的所有条目，按 ID 范围读取即是按时间线回放。
- 显式指定 ID 时必须大于流中现有最大 ID，否则命令报错；最小合法 ID 为 0-1；7.0 起支持只写毫秒部分加星号（如 1526919030474-*），让服务器只补序号。
- 时钟回拨保护：若当前本地时间小于流顶条目的时间（时钟回跳或故障转移后新主时间滞后），服务器沿用顶条目的毫秒值并递增序号，ID 依然递增。
- 底层按**宏节点**组织条目（多个条目打包存储，编码细节详见第 13 章），这使得 XADD 近似 O(1)、XDEL 单条 O(1)。

```bash
XADD mq:order * order:1001 status:created
XADD mq:order * order:1002 status:created
```

> 服务器返回的新 ID 形如 1725686400000-0 与 1725686400001-0，两条消息分属相邻两个毫秒，序号各自从 0 起；若在同一毫秒内连发，第二条会是 1725686400000-1。返回的 ID 要由调用方保存，它是后续 XRANGE、XACK、XDEL 的定位凭据。

**速记**：Stream 是**只追加日志**，ID 为 **毫秒-序号** 且**严格递增**，自动生成可回拨保护，显式 ID 必须**大于现有最大值**。



#### XADD：追加消息与 MAXLEN 近似裁剪

**XADD**：向流追加一条消息，是唯一写入命令，完整签名 XADD key [NOMKSTREAM] [MAXLEN | MINID [= | ~] threshold [LIMIT count]] id | * field value [field value ...]。

- 键不存在时自动创建流；6.2 起可加 **NOMKSTREAM**，键不存在时不创建、直接返回 nil，用于只向已存在的流发消息。
- 消息至少一组字段-值对，多组依次排列；新增条目 O(1)，附带裁剪时为 O(N)，N 是被驱逐的条目数。
- **MAXLEN threshold**：写入后把流裁剪到最多 threshold 条，从最旧端驱逐。
- **MINID threshold**（6.2 起）：驱逐所有 ID 小于 threshold 的条目，按时间线清理而非按条数。
- **等号与波浪号**：默认等号为精确裁剪；**波浪号为近似裁剪**，利用宏节点整块驱逐，效率显著更高，实际保留量可能比阈值多出几十条。
- **LIMIT count**（6.2 起）：限制本次裁剪检查的节点数量，避免一次 XADD 因裁剪耗时过久阻塞（单线程阻塞机制详见第 16 章）；不写时默认按约 100 乘宏节点条目数计，写 0 表示完全放开。
- 生产环境推荐组合：XADD key MAXLEN ~ 1000000 * field value，一条命令同时完成追加与容量兜底。

```bash
XADD mq:order MAXLEN ~ 1000 * order:1003 status:paid
XADD mq:order NOMKSTREAM MAXLEN ~ 1000 * order:1004 status:paid
```

> 两条命令都返回新条目的 ID；NOMKSTREAM 只在键不存在时才改变行为（返回 nil 且不建流），本例键已存在，行为与普通 XADD 完全一致。同一毫秒内连续写入多条消息时，ID 的序号部分逐条递增，严格递增的保证依然成立。

**速记**：XADD 是**唯一写入口**，**MAXLEN ~ 阈值**边写边裁是生产标配，NOMKSTREAM 防手滑建流，MINID 与 LIMIT 均为 6.2 新增。



#### XLEN、XRANGE 与 XDEL：查看与删除消息

**XLEN**：返回流内条目数，复杂度 O(1)；**XRANGE**：按 ID 区间读取条目，完整签名 XRANGE key start end [COUNT count]；**XDEL**：按 ID 删除指定条目，完整签名 XDEL key id [id ...]。

- XRANGE 的 start 与 end 是闭区间，特记号 **减号** 表示最小 ID、**加号** 表示最大 ID；COUNT 限制返回条数，复杂度 O(N)，N 为返回条数。
- ID 可只写毫秒部分，表示该毫秒的 0 号序号起；6.2 起 ID 前可加左圆括号表示开区间，如 (1526919030474 表示不含该 ID。
- 按时间回放：XRANGE key 1725686400000 + 即取出该毫秒之后的全部消息，这是故障排查与数据补拉的常用形态。
- **XREVRANGE** 是反向版本，按 ID 从大到小取，end 在前 start 在后，取最新 N 条写作 XREVRANGE key + - COUNT 10。
- XDEL 逐条 O(1)，与流大小无关；删除只做逻辑标记，条目所在宏节点的内存在节点腾空后才整体回收，立即回收空间应配合 XTRIM。
- 被删除条目若已在某消费组的 PEL 中，PEL 记录并不会随之消失，需按下一节语义另行 XACK 清理，否则出现幽灵待确认条目。

```bash
XADD mq:order * order:1001 status:created
XADD mq:order * order:1002 status:created
XLEN mq:order
XRANGE mq:order - + COUNT 1
XREVRANGE mq:order + - COUNT 1
XDEL mq:order 1725686400004-0
XLEN mq:order
```

```text
127.0.0.1:6379> XLEN mq:order
(integer) 2
127.0.0.1:6379> XRANGE mq:order - + COUNT 1
1) 1) "1725686400004-0"
   2) 1) "order"
      2) "1001"
      3) "status"
      4) "created"
127.0.0.1:6379> XREVRANGE mq:order + - COUNT 1
1) 1) "1725686400005-0"
   2) 1) "order"
      2) "1002"
      3) "status"
      4) "created"
127.0.0.1:6379> XDEL mq:order 1725686400004-0
(integer) 1
127.0.0.1:6379> XLEN mq:order
(integer) 1
```

> 消息体返回为扁平的字段-值交替数组，客户端库会组装成对象。XDEL 之后 XLEN 立即减一，但底层内存是否回收取决于宏节点是否腾空，删除不等于立即释放内存。

**速记**：**XLEN O(1) 数条数**，XRANGE **减号到加号**顺读、XREVRANGE **加号到减号**倒读，XDEL **按 ID 逐条删**、内存随宏节点腾空才回收。



#### XREAD：独立读取与阻塞等待

**XREAD**：从一条或多条流读取 ID 大于给定值的条目，完整签名 XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]。

- STREAMS 关键字后按顺序配对流与 ID：从指定 ID 之后读，特记号 **美元符** 表示从流的末尾开始、只等新消息，**0-0** 表示从头读全部历史。
- **BLOCK milliseconds** 指定阻塞时长：无新数据时挂起等待，BLOCK 0 表示永久阻塞直到有数据；不写 BLOCK 则立即返回，无数据时返回 nil。
- 一次可同时监听多条流，任一流有新数据即返回，返回按流分组——这是单连接同时消费多个事件源的轻量做法。
- XREAD **没有任何消费状态**：不记录读到哪里，两个客户端用同一 ID 读会读到相同内容，适合只看不消费的场景，也意味着用它做队列时消费位移全靠应用层自己存。
- 阻塞等待由服务器端实现，客户端连接被挂起但不占用轮询资源；大量客户端同时阻塞在同一条流上时，每次 XADD 的唤醒成本随阻塞客户端数线性增长。
- 与第 5 章 List 的阻塞弹出对比：BRPOP 取走元素即消失，XREAD 只读不删，消息仍在流中可被反复读取。

```bash
XREAD COUNT 1 STREAMS mq:order 0-0
XREAD BLOCK 5000 STREAMS mq:order $
```

```text
127.0.0.1:6379> XREAD COUNT 1 STREAMS mq:order 0-0
1) 1) "mq:order"
   2) 1) 1) "1725686400006-0"
         2) 1) "order"
            2) "1001"
            3) "status"
            4) "created"
127.0.0.1:6379> XREAD BLOCK 5000 STREAMS mq:order $
(nil)
(5.00s)
```

> 从 0-0 读出全部历史；从美元符读则只等新消息，5 秒内无人写入即返回 nil。XREAD 是理解消费组的阶梯：给读位置加上组内共享与确认机制，就是 XREADGROUP。

**速记**：**美元符只等新、0-0 读全部**，BLOCK 挂起等待、0 为永久，多流一次监听，**无消费状态、纯读取**。



#### 消费组体系：XGROUP 与 last-delivered-id

**消费组**：是挂在流上的独立消费视图——每组维护一个 **last-delivered-id**（最后投递位置）与自己的 PEL，组间互不干扰地各自收全量消息，组内多个消费者共享一个投递位置分食消息。

- **XGROUP CREATE key group id | $ [MKSTREAM]**：创建组。起始 ID 写 **美元符** 表示只消费创建之后的新消息，写 **0-0** 表示从流头重放全部历史；流不存在时加 MKSTREAM 先创建空流再建组。
- **XGROUP SETID key group id**：把组的 last-delivered-id 拨到指定位置，用于跳过积压或重放历史，复杂度 O(1)。
- **XGROUP CREATECONSUMER**（6.2 起）：显式创建消费者；实际上 XREADGROUP 遇到不存在的消费者名会自动创建，显式命令主要用于预建与统计。
- **XGROUP DELCONSUMER key group consumer**：删除消费者；该消费者 PEL 中未确认的消息仍留在组 PEL 里但失去属主，只能被其他消费者 XCLAIM 接管，删除前应先确认其 PEL 已清空。
- **XGROUP DESTROY key group**：销毁整个组，复杂度 O(N)，N 为组 PEL 中的条目数；组内投递位置与待确认状态一并消失。
- 组的数量没有上限：同一流可挂订单组、风控组、审计组，各组从各自的 last-delivered-id 独立推进——**组间广播、组内独占**八个字是整个体系的纲。
- 消费者只是组内的一个名字，天然支持横向扩容：新实例起一个消费者名加入组即可参与分食，无需预注册。

```bash
XGROUP CREATE mq:order pay-group $ MKSTREAM
XGROUP CREATE mq:order audit-group 0
```

```text
127.0.0.1:6379> XGROUP CREATE mq:order pay-group $ MKSTREAM
OK
127.0.0.1:6379> XGROUP CREATE mq:order audit-group 0
OK
```

> pay-group 从流尾只收新消息，承担实时处理；audit-group 从 0-0 重放全量历史，承担对账补录。同一份消息两个组各得一份、互不影响投递进度，这正是多订阅场景选 Stream 而非 List 的关键理由。

> [!IMPORTANT]
> **重要内容**：创建组时的起始 ID 决定消费起点——**美元符放弃历史、0-0 重放历史**，选错会漏消息或重复处理；对已在大规模运行的流补建消费组时，用 0-0 意味着组要消化全部积压，务必评估处理能力后再决定。

**速记**：组内共享 **last-delivered-id**，**组间广播、组内独占**；建组起点 **美元符或 0-0**，DELCONSUMER 前先清 PEL，DESTROY 的代价随 PEL 增长。



#### XREADGROUP：组内独占消费

**XREADGROUP**：以消费组内某个消费者的身份读取消息，完整签名 XREADGROUP GROUP group consumer [COUNT count] [BLOCK milliseconds] [NOACK] STREAMS key [key ...] id [id ...]，是消费组体系的核心读命令。

- 目标 ID 写**大于号**：读取组内从未投递过的新消息（即 last-delivered-id 之后的），投递成功后组的 last-delivered-id 前移，消息同时登记进该消费者的 PEL。
- 目标 ID 写 **0** 或具体 ID：不再取新消息，而是从本消费者 PEL 中重读 ID 之后的**待确认消息**，用于崩溃恢复后的续做。
- **组内独占**：同一条消息经组投递只会给一个消费者，多个消费者各得不同消息，天然实现多实例并行分食；组间则各收全量。
- **NOACK**：投递时不写入 PEL，消息即取即弃，属于 at-most-once 语义；省去确认开销，但处理中途崩溃消息即丢，仅适用于可容忍丢失的场景。
- COUNT 限制单次条数，BLOCK 与 XREAD 语义一致（毫秒数、0 为永久阻塞）；阻塞期间大量消费者挂在同一条流上时，XADD 每次要付出唤醒全部阻塞客户端的代价。
- 消费者名任意取，惯例用实例标识加进程号；消费者集合随使用自动增长，长期不用的消费者应 DELCONSUMER 清理。

```bash
XREADGROUP GROUP pay-group worker-1 COUNT 2 STREAMS mq:order >
XREADGROUP GROUP pay-group worker-1 STREAMS mq:order 0
```

```text
127.0.0.1:6379> XREADGROUP GROUP pay-group worker-1 COUNT 2 STREAMS mq:order >
1) 1) "mq:order"
   2) 1) 1) "1725686400008-0"
         2) 1) "order"
            2) "1001"
            3) "status"
            4) "paid"
127.0.0.1:6379> XREADGROUP GROUP pay-group worker-1 STREAMS mq:order 0
1) 1) "mq:order"
   2) 1) 1) "1725686400008-0"
         2) 1) "order"
            2) "1001"
            3) "status"
            4) "paid"
```

> 第一条命令用大于号领到新消息并进入 PEL；第二条改用 0，读回的正是自己 PEL 中尚未确认的同一条消息。处理完成前消息始终留在 PEL，这就是 at-least-once 语义的载体。

> [!WARNING]
> **警告内容**：大于号与 0 混用是消费组最常见的事故源——**大于号只管新消息、0 只管自己的 PEL**，把续做逻辑写成大于号会导致跳过崩溃前未确认的消息；反之，日常循环里误用 0 则永远读不到新消息，消费停滞。两种读法对应恢复与推进两种职责，务必分开封装。

**速记**：**大于号领新消息并登记 PEL，0 重读自己的待确认消息**，组内独占、NOACK 即弃，消费者名随用随建。



#### XACK、XPENDING 与 PEL：确认与待处理

**PEL**（Pending Entries List，待确认条目列表）：消费组内部维护的登记簿——消息投递给消费者时记入，XACK 确认后移除，是 at-least-once 语义的核心机制。

- PEL 是**组级**的：每条记录包含消息 ID、所属消费者与投递次数；同一消息只属于一个消费者的 PEL，这与组内独占一致。
- **XACK key group id [id ...]**：确认处理完成，把条目从组 PEL 移除，每个 ID O(1)，返回实际确认的条数；确认不是消费流程的可选项，漏确认会让消息永远滞留 PEL。
- **XPENDING key group**：摘要形式，一行返回 PEL 总条数、最小与最大待确认 ID、各消费者及其持有条数，用于快速巡检积压。
- **XPENDING key group [IDLE milliseconds] start end count [consumer]**：扩展形式，逐条返回 ID、消费者、空闲毫秒数与投递次数；IDLE 过滤空闲超阈值的消息，投递次数偏大说明反复处理失败。
- 常规巡检节奏：先看摘要判断是否积压，再用扩展形式按空闲时长锁定可疑条目，决定重投、接管或告警。
- 消息被 XDEL 删除后，其 PEL 记录不自动消失，成为幽灵条目：扩展形式仍能查到，但 XRANGE 已读不到消息体，处理逻辑需判空并 XACK 清掉。
- 投递次数由服务器在每次 XREADGROUP 重读或 XCLAIM 认领时递增，是判断毒消息（反复失败的消息）的第一指标。

```bash
XPENDING mq:order pay-group
XPENDING mq:order pay-group - + 10
XACK mq:order pay-group 1725686400008-0
```

```text
127.0.0.1:6379> XPENDING mq:order pay-group
1) (integer) 1
2) "1725686400008-0"
3) "1725686400008-0"
4) 1) 1) "worker-1"
      2) "1"
127.0.0.1:6379> XPENDING mq:order pay-group - + 10
1) 1) "1725686400008-0"
   2) "worker-1"
   3) (integer) 130000
   4) (integer) 1
127.0.0.1:6379> XACK mq:order pay-group 1725686400008-0
(integer) 1
```

> 摘要显示 worker-1 持有 1 条待确认；扩展形式给出空闲 130 秒、投递 1 次；XACK 返回 1 表示该条已移出 PEL，再查摘要时总条数即归零。巡检脚本即可据此把空闲超时的条目转入下一节的路由接管流程。

**速记**：**投递即入 PEL、XACK 才出 PEL**，XPENDING **摘要看总量、扩展看明细**，投递次数异常即毒消息信号，XDEL 不清 PEL。



#### XCLAIM 与 XAUTOCLAIM：故障转移

**XCLAIM**：把组 PEL 中某条消息的所有权转移给指定消费者，完整签名 XCLAIM key group consumer min-idle-time id [id ...] [IDLE ms] [TIME ms] [RETRYCOUNT count] [FORCE] [JUSTID]，是消费者崩溃后消息重投的标准手段。

- **min-idle-time** 是认领门槛：只有空闲时间超过该值的消息才允许被认领，防止误抢仍在正常处理中的活跃消费者的消息。
- 认领即改写归属：消息 PEL 记录的消费者字段改为新消费者，其后续确认也由新消费者执行；RETRYCOUNT 可重置投递次数。
- **JUSTID** 只转移所有权不投递消息体，用于只做簿记的场景；FORCE 则允许消息已不在流中时强制认领。
- **XAUTOCLAIM**（6.2 起）：自动版认领，完整签名 XAUTOCLAIM key group consumer min-idle-time start [COUNT count] [JUSTID]——从 start 起扫描组 PEL，把所有空闲超时的条目批量转移给指定消费者，并返回游标与认领清单，把手工挑 ID 的流程自动化。
- 故障接管的标准流程：巡检发现消费者掉线且其 PEL 有积压 → XAUTOCLAIM 批量认领到存活消费者 → 重新处理 → XACK 确认。
- 转移只解决**谁来重做**，不改变消息本身；若消息体已被 XDEL，XAUTOCLAIM 会把该条目列入删除清单返回，调用方直接 XACK 清理即可。

```bash
XAUTOCLAIM mq:order pay-group worker-2 60000 0-0 COUNT 10
XACK mq:order pay-group 1725686400009-0
```

```text
127.0.0.1:6379> XAUTOCLAIM mq:order pay-group worker-2 60000 0-0 COUNT 10
1) "0-0"
2) 1) 1) "1725686400009-0"
      2) 1) "order"
         2) "1002"
         3) "status"
         4) "paid"
3) (empty array)
127.0.0.1:6379> XACK mq:order pay-group 1725686400009-0
(integer) 1
```

> 空闲超过 60 秒的条目被自动认领给 worker-2 并连消息体一并返回，游标归零表示扫描完毕；处理完成后 XACK。整个接管不需要知道原消费者是谁，这也是生产脚本的标准写法。

> [!TIP]
> **建议内容**：把 **巡检加认领固化成定时任务**：每隔固定周期以 min-idle-time 等于处理超时阈值执行 XAUTOCLAIM，认领即重处理；配合投递次数上限判断毒消息，超过上限的条目转入死信表人工介入，即可在 Redis 上手工搭出可靠消费的闭环。

**速记**：**XCLAIM 手工点名、XAUTOCLAIM 自动扫仓**，min-idle-time 防**误抢活跃者**，认领改归属、确认才算完。



#### XTRIM 与容量控制

**XTRIM**：显式裁剪流，完整签名 XTRIM key MAXLEN | MINID [= | ~] threshold [LIMIT count]，与 XADD 内联裁剪共用同一套策略。

- **MAXLEN threshold**：保留最新的 threshold 条，从最旧端驱逐；**MINID threshold**（6.2 起）：驱逐 ID 小于 threshold 的全部条目，适合按时间线清理。
- **等号精确裁剪**：裁到恰好等于阈值；**波浪号近似裁剪**：按宏节点整块驱逐，可能多留几十条，但省去逐条拆节点的开销，性能远好于精确模式。
- **LIMIT count**（6.2 起）：单次裁剪最多检查的节点数，超出的部分留给后续调用，把裁剪成本摊薄到多次命令中。
- 裁剪是**从头部截断**：只删最旧消息，绝不动新消息；已进入各组 PEL 的旧消息被裁掉后同样成为幽灵条目，需按前述方式清理。
- 日常运维三选一：XADD 内联 MAXLEN ~ 自动兜底；定时任务周期性 XTRIM；MINID 按保留窗口（如只留 7 天）清理。三者的共同目的是防流无限增长拖垮内存（内存淘汰详见第 15 章）。
- XTRIM 的返回值是被裁掉的条目数；对已由内联 MAXLEN 管理的流再手工 XTRIM 通常多余，二选一即可。

```bash
XADD mq:order MAXLEN 2 * order:2001 status:new
XADD mq:order MAXLEN 2 * order:2002 status:new
XADD mq:order MAXLEN 2 * order:2003 status:new
XLEN mq:order
XTRIM mq:order MAXLEN ~ 1
XLEN mq:order
```

```text
127.0.0.1:6379> XLEN mq:order
(integer) 2
127.0.0.1:6379> XTRIM mq:order MAXLEN ~ 1
(integer) 1
127.0.0.1:6379> XLEN mq:order
(integer) 1
```

> 每条 XADD 都带 MAXLEN 2，写入第三条时最旧的 order:2001 已被自动驱逐，XLEN 只剩 2；再执行 XTRIM 后仅存 order:2003。小流看不出近似与精确的差别，宏节点规模大时波浪号的优势才显现。

**速记**：**MAXLEN 按条数、MINID 按时间线**，**波浪号近似换性能**，LIMIT 摊薄成本，裁剪只动**最旧端**。



### Stream 与其他消息方案的对比

#### Stream 与 List 阻塞弹出对比

**对比结论**：List 的 BRPOP 是**取走即消失**的简单队列，Stream 是**消息留存、可确认、可回溯**的可靠队列——二者的差距本质是有无消息留存与消费状态。

- 消费语义：**BRPOP** 弹出后元素即不在队列中，没有 ID、没有 PEL、没有确认，消费者处理中途崩溃则消息永久丢失；**XREADGROUP** 投递只登记不删除，处理完 XACK，崩溃后可经 PEL 重投，天然 at-least-once。
- 回溯能力：List 只能对当前内容做范围读取，取走的元素无法找回；Stream 可按 ID 区间重放任意历史段，新加的消费组还能用 0-0 重放全量。
- 多消费者扩展：List 的多消费者靠竞争弹出实现分食，无组概念、无投递位置；Stream 的消费组提供 last-delivered-id 与消费者管理，扩缩容只需增减消费者名。
- 阻塞能力：BRPOP 可同时阻塞多个键，XREAD 与 XREADGROUP 可同时阻塞多条流，能力相当；但 XREAD 不删数据，读的代价与普通读一致。
- 轻量场景仍是 List 的天下：元素无需确认、允许丢失、任务量小的异步任务队列，BRPOP 加 LMOVE 的组合更简单直接（List 详见第 5 章）。
- 判断标准：问一句**消息丢得起吗、需要重做吗**——都答否则 List 足够，任一答是则上 Stream。

> 把 List 队列改造出可靠性（取出前备份、处理后删除）等价于用应用层重新发明 PEL，复杂度反而高于直接用 Stream；而用 Stream 承载毫秒级高频的轻任务，确认开销又属浪费。按可靠性需求选型，不要按习惯选型。

**速记**：**BRPOP 取走即丢、Stream 留存可重做**，回溯靠 ID、恢复靠 PEL，丢得起用 List、丢不起用 Stream。



#### Stream 与发布订阅对比

**对比结论**：发布订阅是**即时广播、不落盘**，Stream 是**持久日志、可回放**——消息可靠性是二者的分水岭。

- 投递模型：发布订阅（详见第 24 章）把消息实时推给所有在线订阅者，服务器不为任何人保存消息；Stream 把消息写入流，消费者按自己的进度拉取，进度落在 last-delivered-id。
- 离线容忍：订阅者离线期间的 Pub/Sub 消息**永久丢失**，重新上线收不到补发；Stream 的消费组离线再上线，从 last-delivered-id 继续消费，一条不落。
- 确认与重投：Pub/Sub 无确认机制，消费失败无从谈起；Stream 有 PEL、XACK 与 XCLAIM，完整覆盖失败重做。
- 持久化：Pub/Sub 纯内存转发，不进任何持久化文件；Stream 随 RDB 与 AOF 持久化（详见第 17、18 章），重启后消息仍在。
- 性能特征：Pub/Sub 是即时扇出、无存储压力，吞吐上限高、延迟极低；Stream 有写入与存储成本，容量靠 MAXLEN 管理。
- 适用边界：允许丢失的实时通知（配置变更广播、缓存失效通知，见第 26 章）用 Pub/Sub 足矣；订单、支付、审计等不容丢失的事件流必须用 Stream。

> 两者不是替代关系而是互补关系：对可靠性零要求的通知场景，Pub/Sub 更轻更快；一旦消息需要**离线可达、失败重做、事后审计**三者中的任何一个，Pub/Sub 就出局，Stream 是 Redis 域内的唯一选择。

**速记**：Pub/Sub **在线广播、离线即丢、无确认**，Stream **落盘、可回放、有确认**，按**丢得起丢不起**划界。



#### Stream 与专业消息队列的选型

**选型结论**：Stream 的定位是**零运维成本的轻量可靠队列**——它覆盖了消息队列的核心闭环（持久化、消费组、确认、重投），但在并行度、生态与高级特性上与 RabbitMQ、Kafka 存在代差。

- 与 **Kafka** 对比：Kafka 以分区实现水平并行、磁盘顺序写入支撑超高吞吐、按时间而非消费进度保留数据、生态与流处理体系完整；Stream 单键内部串行、存储在内存中受实例内存约束、并行只能靠集群按键分片（集群详见第 22 章）。日志聚合、大规模事件流属于 Kafka 的主场。
- 与 **RabbitMQ** 对比：RabbitMQ 提供复杂路由（exchange 交换机模型）、死信队列、优先级队列、消息 TTL 与完善的管理界面；Stream 无路由、无死信、无延迟队列，这些都要应用层自建。企业集成的多拓扑场景属于 RabbitMQ 的主场。
- Stream 的优势：**少一个中间件**——与业务数据同实例、同监控、同客户端，低延迟，部署与运维成本近乎为零；XADD 一条命令起步，学习成本远低于任何专业 MQ。
- Stream 的风险面：数据在内存，可靠性取决于持久化配置——AOF 关闭时宕机即丢已确认未落盘的消息，appendfsync everysec 也存在约 1 秒丢失窗口（详见第 18 章），对消息可靠性要求高于持久化能力时必须上专业 MQ。
- 决策路径：先评估吞吐量级与可靠性等级；中低吞吐、消息量可控、团队已在用 Redis，Stream 起步完全够用；日亿级消息、需多消费者镜像、需严格不丢，直接 Kafka 或 RabbitMQ。
- 混合形态常见于成长期业务：核心交易链路走专业 MQ，边缘通知与内部事件用 Stream，随规模演进再迁移，Stream 的 ID 语义与 Kafka 的 offset 概念相近，迁移心智成本不高。

> [!WARNING]
> **警告内容**：**不要默认 Stream 等于专业消息队列**——单键无分区并行、内存容量上限、无死信与延迟队列、持久化存在丢失窗口，这四条决定了它在高吞吐与强可靠场景的天花板；把 Stream 当作过渡与轻量方案，把专业 MQ 当作规模与合规方案，边界清楚才不会在故障复盘时才发现选型错误。

**速记**：Stream 胜在**零运维与低延迟**，输在**并行度、容量与高级特性**；轻量选 Stream、高吞吐选 Kafka、重路由选 RabbitMQ。⚡
