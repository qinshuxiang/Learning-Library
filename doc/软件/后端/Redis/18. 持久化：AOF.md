## 持久化：AOF

### AOF 的定位与开启

#### AOF 的定位：写后日志

**AOF（Append Only File）**：是 Redis 两大持久化方式之一，把**每一条写命令按执行顺序追加**为一个文本日志文件，重启时通过**重放全部命令**恢复出数据状态。

- AOF 与 RDB 分工互补：RDB 保存**某一时刻的内存快照**，AOF 保存**到达该状态的命令序列**；前者回答“现在是什么样”，后者回答“是怎么一步步变成这样的”（详见第 17 章）。
- 只有**写命令**会被追加，读命令不改变任何状态，不产生任何日志。
- 追加发生在**命令执行成功之后**，故称**写后日志**：先执行、后记录，执行失败的命令不会进入日志。
- 日志内容是命令的 **RESP 文本协议**，可以用文本编辑器直接打开阅读，甚至手工裁剪修复。
- 文件以**追加写**方式生长，从不随机改写已写入的内容，顺序 IO 对磁盘友好。
- 与 RDB 的全量序列化相比，AOF 的每次持久化动作都很小，日常写入的瞬时开销更平滑。

恢复的完整过程是：启动时新建一个空的数据库状态，逐条读出日志中的命令并执行，全部重放完毕后才开始对外服务。这个过程与主从复制中从库追平主库的方式同源，理解了重放就理解了 AOF 的一切。

> AOF 的“写后”特性与数据库的 WAL（预写日志，先写日志再执行）方向相反：WAL 能在执行前校验语法，AOF 则天然过滤掉执行失败的命令；同时先执行后记录**不阻塞当前写操作本身**，是 AOF 写入开销较低的原因之一。代价是宕机时可能丢失最近尚未刷盘的命令，丢失窗口的大小由刷盘策略决定。

```text
*2\r\n$6\r\nSELECT\r\n$1\r\n0\r\n
*3\r\n$3\r\nSET\r\n$5\r\ncount\r\n$3\r\n100\r\n
*3\r\n$4\r\nINCR\r\n$5\r\ncount\r\n
```

> 上例即 AOF 文件的真实内容：RESP 协议以 \r\n 作为分隔符，星号开头的一行是命令的参数个数，美元符号开头的一行是每个参数的长度。恢复时 Redis 把这些字节当作普通客户端请求逐条执行，效果与当初现场执行完全一致。

**速记**：AOF 是**先执行、后记账**的命令流水账，重启时**按序重放**还原状态。



#### 开启 AOF 与文件名配置

**开启 AOF**：由配置项 **appendonly** 控制，设为 yes 后 Redis 启动时载入 AOF 文件，此后每条写命令都被追加；**appendfilename** 决定文件名，**appenddirname**（Redis 7 新增）决定 AOF 系列文件所在的子目录。

- AOF 在所有版本中的默认配置均为关闭（appendonly no），生产环境建议显式开启，并与 RDB **同时开启**，二者互为补充而非二选一。
- AOF 与 RDB 同开时，重启**只载入 AOF**：其数据通常比 RDB 更完整，RDB 退居备份与重写素材的位置（详见第 19 章）。
- Redis 6 及以前，AOF 是**单个文件**（如 appendonly.aof）；Redis 7 起变为**目录加多文件**，appendfilename 退化为文件名前缀。
- 文件落在 dir 指定的数据目录下；Redis 7 中实际路径为 dir 之下的 appenddirname 子目录。
- 动态开启无需重启：执行 CONFIG SET appendonly yes 后，Redis 会立刻触发一次 AOF 重写生成首份文件并开始追加。
- 动态关闭用 CONFIG SET appendonly no 即可；要跨重启生效，仍需把改动写入 redis.conf。

```bash
# redis.conf 中开启 AOF
appendonly yes

# AOF 文件名（Redis 7 起为 base 与 incr 文件的共同前缀）
appendfilename "appendonly.aof"

# Redis 7 新增：AOF 文件存放目录，相对 dir
appenddirname "appendonlydir"

# 数据目录
dir /var/lib/redis
```

> 提醒一点：配置 appendonly yes 时务必确认 dir 目录对 Redis 进程可写——AOF 追加失败会导致写入命令报错甚至拒绝服务，这不是静默降级的故障，而是会直接暴露给业务的故障。动态开启与关闭都应随后用 CONFIG REWRITE 把改动落回配置文件，避免重启后配置回退。

**速记**：**appendonly yes 开启**，文件名看 **appendfilename**，位置看 **dir 与 appenddirname**。



#### 为什么记录命令而不记录内存页

**记录单位是命令而非内存数据**：AOF 以**文本协议的写命令**为最小记录单位，而不像 RDB 那样把内存数据整体序列化成二进制快照。

- **可读性**：日志即命令，人能直接读懂、能 diff 两次检查之间的差异、能在损坏时手工修复。
- **协议兼容**：重放恢复等于把日志当作 RESP 请求依次发给一个空实例，与主从复制传播命令复用同一套机制。
- **增量友好**：命令天然是增量语义，追加即持久化，不必像 RDB 那样等待全量快照时机。
- **实现简单**：在命令执行路径上顺手把协议文本追加进缓冲即可，不需要复杂的序列化器与版本兼容层。
- **粒度一致**：命令与主从复制、事务、Lua 脚本的传播单位统一，一条通路多种用途。
- **跨版本稳定**：命令语义变化慢于内存布局变化，旧日志在新版本上仍能重放。

> 辨析：记录内存页的方案（如某些存储引擎的物理日志）恢复最快、体积最紧凑，但要求日志与内存布局强绑定，版本升级后旧日志难以兼容；记录命令则与内存布局解耦，**恢复慢一点，换来的是可读、可修复、跨版本稳定**。

```text
# 同一次业务操作，两种视角
# AOF 的视角：三条命令
SET user:1:name "alice"
HSET user:1:info age 18
EXPIRE user:1:info 60

# RDB 的视角：某个时刻的全部键值对（二进制，无过程）
```

**速记**：AOF 记**命令**：可读、可重放、增量友好，代价是**会膨胀**。



### 命令追加与刷盘策略

#### 命令追加的传播路径：aof_buf

**命令追加的流程**：一条写命令**执行成功**后，先以 RESP 格式追加到主进程内存中的 **AOF 缓冲区 aof_buf**，再由刷盘策略决定何时真正写入磁盘，而不是每条命令直接落盘。

- **aof_buf** 是主进程持有的 SDS 字符串缓冲，**攒批后一次 write**，减少系统调用次数与小 IO。
- 缓冲攒批的副作用是单条命令的落盘时间点不确定，这正是丢失窗口存在的结构性原因。

##### 传播的起点：propagate 与双通路

**propagate 传播**：命令执行器在命令成功后调用的传播函数，是 AOF 追加与主从复制共同的分发入口。

- 同一条命令一次生成、两处使用：一份交给复制流发给从节点（详见第 20 章），一份以 RESP 格式进入 aof_buf。
- 事务与 Lua 脚本中的多条命令在执行完毕后**作为一个整体**追加，保证日志与实际执行顺序一致。
- 只有执行成功的写命令会被传播，失败命令不产生任何日志，这与写后日志的语义一致。



##### 落盘的终点：write 与 fsync 两步

**write 与 fsync 的分工**：把数据送入内核页缓存的是 write，真正等待磁盘落盘的是 fsync，刷盘策略管理的正是后者的频率。

- write 的时机在**事件循环每一轮的 beforeSleep 钩子**，按 appendfsync 策略决定随后的 fsync 动作（详见第 16 章）。
- everysec 档的 fsync 交给**后台线程 bio** 异步执行，磁盘再慢也不阻塞主进程处理命令。
- 磁盘写入出错时 Redis 会记录错误状态并停止接受写入，避免数据静默丢失。

```text
时间线示意（everysec 档）：
t0  命令 A 执行成功，进入 aof_buf
t1  命令 B 执行成功，进入 aof_buf
t2  后台线程 fsync，A、B 落盘
t3  命令 C 执行成功，进入 aof_buf
—— 此刻宕机：A、B 安全，C 丢失
```

> [!IMPORTANT]
> **重要内容**：先写缓冲、再按策略刷盘，是理解 AOF 丢失窗口的钥匙——命令进入 aof_buf 只代表进了**内存**，宕机时缓冲里尚未 fsync 的部分就是可能丢失的部分；丢多少，完全取决于 appendfsync 选了哪一档，这也是下一节三种策略比较的坐标系。

**速记**：执行成功 → 追加 aof_buf → beforeSleep 按策略刷盘。



#### 三种 fsync 策略详解

**appendfsync**：控制 aof_buf 刷盘频率的配置项，共 **always、everysec、no** 三档，在数据安全与性能之间呈梯度分布。

- 三档差异的本质是 **fsync 的发起者与频率**：主进程每条、后台线程每秒、操作系统自主决定。
- 从 always 到 no，性能递增、安全性递减，不存在既零丢失又零开销的选项。
- everysec 档的 fsync 在后台线程执行，若上一秒的 fsync 尚未完成会顺延，极端时推迟计数上升。
- no 档并非“不持久化”：数据仍会 write 进内核页缓存，只是进程崩溃时安全、主机断电时不安全。

##### always 档：每条命令都刷盘

**always 档**：每条写命令执行后都由主进程立即 fsync，是三档中数据安全性最高、写入吞吐最低的一档。

- 理论丢失上限为**一条命令**，适合把 Redis 当唯一存储且要求严格的场景。
- 代价是每条写入都要等一次磁盘往返，吞吐通常只有 everysec 档的几分之一。
- 在机械盘上吞吐塌陷尤其明显，若必须选 always，应配置 NVMe 等低延迟磁盘。

> always 档也并非绝对零丢失：fsync 成功返回前的最后一条命令仍可能随缓冲一起丢失，只是窗口被压缩到单条命令级别。



##### everysec 档：每秒刷盘的默认选择

**everysec 档**：由后台线程**每秒执行一次 fsync**，是 Redis 的默认配置，也是安全与性能的官方均衡点。

- 宕机时最多丢约 1 秒的写入，丢失上限与业务写速率无关，只与时间相关。
- fsync 的执行者是后台刷盘线程 **bio**（详见第 16 章）：事件循环每轮的 beforeSleep 检查距上次 fsync 是否已超过 1 秒，超过才把任务投递给后台线程，磁盘慢时也不阻塞主进程处理命令。
- **主线程的让路与等待**：若后台线程上一次 fsync 尚未完成、且距其发起不足 2 秒，主线程推迟本次落盘，命令继续留在 aof_buf，推迟次数计入 aof_delayed_fsync。
- 推迟一旦超过 2 秒，主线程不再等待，亲自执行 write 与 fsync 并阻塞到完成——宁可短暂阻塞也要止血，防止日志无限滞后；磁盘持续吃紧时 aof_delayed_fsync 持续增长，即是磁盘 IO 吃紧的直接信号。

> 多数生产环境的最优解就是默认档：先跑 everysec，再用监控数据决定是否升级为 always 或降级为 no，而不是凭感觉调整。



##### no 档：交给操作系统

**no 档**：Redis 从不主动 fsync，何时把页缓存刷入磁盘**完全交给操作系统决定**，是性能最好、安全性最差的一档。

- Linux 通常约 30 秒刷一次脏页，意味着宕机时可能丢失约 30 秒的写入。
- 丢失窗口不可控，只能用于数据可随时重建的缓存类场景。
- 性能上与 everysec 差距通常不大，因为瓶颈常在 write 而非 fsync，除非磁盘极慢。
- no 档常与“没有持久化”混淆：write 仍在发生，只是 fsync 的时机不受 Redis 控制。

> 注意 no 档的语义边界：Redis 进程崩溃（而非主机断电）时内核页缓存仍在，数据并不丢失；no 档真正防不住的是主机断电与内核崩溃。

```bash
# redis.conf 三选一
appendfsync always    # 每条命令都刷盘：最安全，性能最低
appendfsync everysec  # 每秒后台刷盘（默认）：最多丢 1 秒
appendfsync no        # 交给操作系统：最快，丢失窗口不可控
```

> [!WARNING]
> **警告内容**：everysec 的保证是**秒级而非零丢失**——宕机时最多丢约 1 秒的命令；把 Redis 当唯一存储时必须评估这 1 秒能否承受，承受不了就选 always 并接受吞吐下降，纯缓存场景则可放心使用默认值。

**速记**：always **条条刷**，everysec **秒秒刷**，no **全听操作系统**。



#### no-appendfsync-on-rewrite 与重写期间的刷盘权衡

**no-appendfsync-on-rewrite**：决定在 **BGSAVE 或 BGREWRITEAOF 进行期间**主进程是否照常 fsync，设为 yes 时暂停刷盘，刷盘策略临时退化为 no 档的行为。

- 重写与 fork 期间磁盘 IO 本就紧张，主进程若仍坚持每秒 fsync，容易与子进程争抢磁盘，造成**写入延迟抖动**。
- 设为 **yes**：重写期间 aof_buf 只写入内核页缓存而不 fsync，规避了争抢，代价是这期间宕机丢失的数据**可能远超 1 秒**。
- 设为 **no**（默认）：重写期间照常 fsync，安全不降级；但当 fsync 耗时变长时，**写命令会被阻塞**，表现为周期性延迟尖刺。
- 被推迟的 fsync 会累计在 INFO 的 **aof_delayed_fsync** 计数中，是判断磁盘是否吃紧的直接证据。
- 该项只影响重写与保存**进行期间**的行为，平时刷盘节奏不受影响。
- 大实例重写持续时间长，该项的取舍对这段时间的数据安全影响显著，不能只当普通开关看待。
- 判断现状的方法：观察重写窗口内写入延迟是否抬升、delayed_fsync 是否增长，用数据决定开关取向。

> [!CAUTION]
> **注意内容**：设为 yes 并非免费午餐——大实例重写动辄持续数十秒，这段时间的数据安全实际降级为 no 档；磁盘性能充裕时建议保持默认 no，用监控确认 fsync 延迟即可，而不是预先牺牲一致性。

**速记**：yes **换平稳丢更多**，no **保安全忍抖动**。



### AOF 重写

#### 重写的必要性：日志无限膨胀

**AOF 重写（Rewrite）**：根据**当前键空间的数据状态**重新生成一份**等价的最小命令集**替换旧日志，用以解决 AOF 只增不减带来的体积膨胀问题。

- 膨胀根源：命令日志记录的是**过程**而非**结果**——对同一计数器执行一百次 INCR，日志里有一百条，而最终状态只需要一条。
- 已删除、已过期的键在旧日志中占据的篇幅，重写后自动消失。
- 重复设置同一键的中间版本（如先 SET a 1 再 SET a 2 再 DEL a）在重写后归零或归一。
- 重写**不读取旧日志**：直接遍历当前内存数据生成新文件，与历史命令如何书写完全无关。
- 不控制膨胀的连带后果：磁盘占用持续增长，恢复时需要重放的命令变多，**启动时间变长**。
- 对计数器、队列、购物车这类高频修改的键，重写的压缩比尤其显著。
- 膨胀还会放大修复成本：文件越大，redis-check-aof 的检查时间与截断决策都越重。
- 膨胀速度与写速率正相关，读密集型业务的 AOF 几乎不增长。

##### 膨胀的三个来源

**膨胀来源**：日志体积超出数据本体规模的部分，主要来自三类重复与残留。

- **重复修改**：同一键被反复改写，每次都完整记录，如计数器与热点配置键。
- **残留键**：已删除、已过期的键留下的命令篇幅，重放时是纯粹的浪费。
- **冗余操作**：先 RPUSH 大批元素又 LTRIM 裁剪的组合，过程与结果偏离越大膨胀越快。



##### 重写不是日志压缩

**重写与压缩的区别**：重写是基于当前内存重新生成最小命令集，而不是对旧日志做无损压缩。

- 重写产物与当前数据量成正比，而非与历史操作次数成正比，这才是体积收敛的本质。
- 压缩只能缩小旧日志的字节数，无法清除过期与删除残留。
- 重写产物语义等价但内容全新，因此能顺手完成清理，这是单纯压缩做不到的。

> 场景辨析：秒杀场景下热点库存键每秒被改写成百上千次，一小时的原始日志可能上 GB；重写后这一小时对它的全部影响收敛为最后一条命令。**重写是 AOF 体积得以收敛的唯一手段**，也正因重写期间要处理增量，才衍生出后文的重写缓冲与 Multi-Part AOF 两段历史。

```text
# 重写前：过程记录，共 100 条
INCR count    （该命令在日志中出现 100 次）

# 重写后：结果记录，仅 1 条
SET count 100
```

**速记**：日志记**过程**，重写记**结果**。



#### BGREWRITEAOF 与自动触发条件

**触发重写**有两种途径：客户端手动执行 **BGREWRITEAOF** 命令，或满足**自动触发条件**由 Redis 主动发起，二者都由子进程异步完成，不阻塞主进程。

- **auto-aof-rewrite-min-size**：自动重写的体积门槛（默认 64mb），当前 AOF 小于该值时永不触发，避免小文件频繁重写。
- **auto-aof-rewrite-percentage**：增长比例（默认 100），当前体积相对**上次重写后体积**增长到两倍才触发。
- 判断依据是 INFO 中的 **aof_current_size**（当前体积）与 **aof_base_size**（上次重写完成时的体积）：同时满足 current 达到 base 的 1 加 percentage 百分比倍、且 current 达到 min-size。

##### 手动触发：BGREWRITEAOF 命令

**BGREWRITEAOF**：客户端随时可执行的手动重写命令，由 Redis fork 子进程异步完成，不阻塞主进程。

- 已有重写在跑时直接返回错误，不会排队等待。
- 适合在业务低峰期主动整理体积，把重写时机的主导权握在运维手里。
- 触发后用 INFO 的 aof_rewrite_in_progress 观察进度，完成后核对 current 与 base 是否重置。



##### 自动触发：比例与门槛的双条件

**自动触发条件**：current 体积达到 base 的 1 加 percentage 百分比倍，且 current 达到 min-size，两个条件缺一不可。

- 触发带节流：距上次重写过近时会顺延，避免重写风暴。
- INFO 中的 aof_pending_rewrite 表示自动触发已被安排但尚未开始执行。
- 长期低写入的实例不会满足比例条件，体积可以稳定很久不重写，这正是双条件设计的目的。

```bash
redis-cli BGREWRITEAOF

# redis.conf 自动触发条件
auto-aof-rewrite-percentage 100   # 相对上次重写后体积增长 100% 触发
auto-aof-rewrite-min-size 64mb    # 且当前体积至少 64mb
```

> [!TIP]
> **建议内容**：默认参数对写密集实例可能重写过于频繁、对小实例又过于迟钝；应按业务写入速率调整 percentage，并把 min-size 设为实例稳态体积的量级，避免频繁 fork 带来的内存与延迟毛刺。参数调整同样可用 CONFIG SET 动态生效后 CONFIG REWRITE 落盘。

**速记**：手动 **BGREWRITEAOF**，自动看**翻倍且过 64mb**。



#### 重写的实现原理：fork 子进程与重写缓冲

**重写的执行机制**：主进程 **fork 出子进程**遍历当前键空间，把每个键翻译成等价的写命令写入**临时 AOF 文件**；重写期间的新写命令则同时进入 aof_buf 与 **aof_rewrite_buf（重写缓冲）**，子进程完成后由主进程把重写缓冲追加到新文件并原子替换旧文件。

##### fork 与子进程生成全量

**fork 与子进程**：重写的全量部分由 fork 出的子进程完成，子进程基于 fork 时刻的**内存快照**工作，与主进程后续的修改互不可见。

- 写时复制（COW）保证子进程看到的是一份不再变化的一致状态，无需加锁同步。
- 子进程遍历键空间，按类型归并生成最小命令集：String 直接 SET，List 用一条长 RPUSH（过长时分批），Hash 与 Set 各用一批 HSET、SADD，ZSet 用一批 ZADD。
- 带过期时间的键在重写时会把过期时间一并写进新文件，过期语义不因重写丢失。
- 实例越大页表越大，fork 阻塞主进程的时间越长，写时复制的内存增量（INFO 中 aof_last_cow_size 可观测）也随之放大。



##### 双写缓冲与收尾替换

**双写与收尾**：重写期间的新写命令同时进入 aof_buf 与 aof_rewrite_buf 两份缓冲，子进程完成后由主进程一次性收尾，原子替换旧文件。

- 进 aof_buf 保证**旧 AOF 文件继续可用**，重写失败也不影响既有持久化。
- 进 aof_rewrite_buf 保证**新文件不缺尾部增量**，收尾时补齐 fork 之后发生的全部修改。
- 收尾动作：主进程把重写缓冲追加到临时文件末尾，再**原子改名**替换旧文件，全程只有收尾阶段占用主进程少量时间。
- 收尾期间新命令的写入会被短暂阻塞，缓冲越大阻塞越久，这是旧版重写尾延迟的来源之一。
- 旧版的主要隐患：重写持续越久、写入越多，aof_rewrite_buf 占用内存越大，主进程内存出现**数倍毛刺**，极端时引发 OOM。

```text
收尾时序示意（Redis 7 之前）：
1  子进程写完临时 AOF 文件，通知主进程
2  主进程把 aof_rewrite_buf 追加到临时文件
3  主进程把 aof_buf 余量追加进新文件
4  原子改名替换旧 AOF，重写结束
```

> 辨析：fork 本身有瞬时成本——实例越大页表越大，fork 阻塞主进程的时间越长，加上写时复制的内存增量，大实例重写期间内存与延迟都容易抖动；这一问题的根治方案见下文 Multi-Part AOF。

**速记**：**fork 快照写全量，双写缓冲保增量，收尾原子替换**。



### Redis 7 的 Multi-Part AOF

#### Multi-Part AOF 的文件构成

**Multi-Part AOF**：Redis 7.0 起的 AOF 新组织形式，把单个 AOF 文件拆成 **base 基础文件、incr 增量文件与 manifest 清单文件**三类，由清单统一描述与编排。

- base 与 incr 的划分让“全量”与“增量”各归其位，重写不再是替换一个巨型单文件。
- 每次重写生成新的 base 与新 incr，序号递增，旧文件组由 Redis 后台清理。
- manifest 是唯一权威：哪些文件算数、按什么顺序装载，一切以清单为准，孤儿文件会被忽略。

##### base 文件：重写产物的全量

**base 文件**：一次重写生成的**全量数据**文件，记录重写时刻的完整键空间状态。

- 格式可以是 RDB（混合持久化）或纯 AOF 文本，由 aof-use-rdb-preamble 决定。
- 同一时间只有一份 base 有效，旧 base 在新重写成功后被清理。



##### incr 文件：命令增量的流水

**incr 文件**：base 之后**按时间顺序追加的命令流水**，负责衔接全量快照与最新状态。

- 可以存在多个，序号递增，恢复时按序重放。
- 重写期间新命令直接写入新 incr 文件，是新版消灭重写缓冲的关键。
- 单个 incr 文件过大时，下次重写会以新 base 归并全部增量。



##### manifest 文件：多文件编排的清单

**manifest 清单**：描述当前有效的 base 与 incr 文件名、序号、格式类型的**元数据文件**。

- 启动时按清单依次装载，清单缺失或损坏时 AOF 整体不可用。
- 文件名如 appendonly.aof.manifest，与其描述的数据文件同目录存放。

> [!NOTE]
> **提醒内容**：Redis 7 起 appendfilename 变为**文件名前缀**而非单一文件名，看到 appendonly.aof.1.base.rdb 这类名字不要误以为配置失效；跨大版本升级时，旧版单文件 AOF 需通过重写或工具转换为新格式，直接把旧文件改名并不能被识别。

```text
appendonlydir/
├── appendonly.aof.1.base.rdb      # base：重写生成的全量（RDB 格式）
├── appendonly.aof.1.incr.aof      # incr：之后的命令增量
└── appendonly.aof.manifest        # manifest：文件清单
```

**速记**：**base 存全量，incr 存流水，manifest 管编排**。



#### Multi-Part AOF 消灭了重写缓冲

**Multi-Part AOF 取消了 aof_rewrite_buf**：重写期间的新写命令不再进入独立重写缓冲，而是**直接追加进新的 incr 文件**，旧版重写期间的内存暴涨问题随之消失。

- 重写完成时主进程只需更新 manifest 指向新文件集，**无需再搬移大块缓冲数据**，收尾更快、不可服务窗口更短。
- INFO 中的 aof_rewrite_buffer_length 字段在新机制下恒为 0，可作为是否运行于新版重写机制的旁证。
- 该变革与 Multi-Part 文件结构互为表里：正因为文件被拆小，增量才有了直接落盘的去处。
- 重写期间的写放大代价依然存在（一份进旧流水、一份进新 incr），但内存压力换成了磁盘压力。

##### 旧版之痛：重写缓冲的内存毛刺

**aof_rewrite_buf 之痛**：Redis 7 之前重写期间的新写命令要在主进程内存里再攒一份完整副本，是旧版 AOF 最受诟病的工程问题。

- 重写越久、写入越多，缓冲越大，极端时内存翻倍乃至 OOM。
- 缓冲在收尾前无法释放，写入洪峰与重写叠加时风险最高。
- 收尾要一次性追加整块缓冲，造成明显的尾延迟。



##### 新版之法：增量直写新 incr 文件

**直写 incr**：重写开始时即创建新 incr 文件，新命令越过内存缓冲直接落盘，内存占用与重写时长彻底解耦。

- 主进程只多维持一个文件描述符，内存增量近乎为零。
- 任何时候崩溃都按 manifest 装载，多余 incr 内容在下次重写时自然归并。
- 对外表现更平稳：旧流水照写、新流水照建，互不干扰。

> 辨析：aof_buf 依然存在且仍有必要——它服务于 everysec 的攒批刷盘；被消灭的只是**为重写准备的第二份内存缓冲**。两个缓冲名字相近、职责不同，是面试中的常见混淆点：前者常驻且受 appendfsync 管，后者只在旧版重写期间存在。

**速记**：7.0 重写**不攒内存缓冲**，增量**直接进新 incr 文件**。



#### aof-use-rdb-preamble 与混合持久化

**aof-use-rdb-preamble**：混合持久化开关（4.0 引入，5.0 起默认 yes），重写时把 **RDB 格式的全量快照作为前导（preamble）**写入 AOF 文件头部，其后继续追加文本命令，形成二进制快照加文本命令的混合文件。

- 重写时子进程先以 RDB 编码写出**当前全量数据**作为 base，之后的新增命令仍以 RESP 文本追加为 incr。
- 恢复时 Redis 识别文件开头的 RDB 魔数，先按 RDB 速度**快速载入全量**，再重放尾部增量命令。
- 收益：RDB 载入远快于重放海量命令，**恢复时间大幅缩短**，文件体积也更小。
- 代价：文件头部不再是纯文本，直接打开阅读的**可读性下降**（尾部命令仍可读）。
- Redis 7 中混合形态即 base 文件后缀为 .base.rdb，与其后的 incr 文件并存于 appendonlydir。
- 对超大实例，混合持久化常把分钟级的重放时间压缩到秒级，是大实例默认推荐的形态。
- 开关只影响**重写产物**的编码：关闭时 base 为纯文本 AOF 格式，开启时为 RDB 格式。

```bash
# redis.conf（5.0 起默认已为 yes）
aof-use-rdb-preamble yes
```

> 混合持久化的开关细节，以及 RDB、纯 AOF、混合 AOF 的三方选型对比属于持久化选型专题，**详见第 19 章**，本章只需掌握它与 AOF 重写的衔接关系：混合不是第三种持久化，而是 AOF 重写产物的另一种编码。

**速记**：重写产物为 **RDB 前导加 AOF 尾巴**，恢复快、体积小、可读性略降。



### AOF 的载入与修复

#### 启动时载入 AOF 的流程

**AOF 的恢复即重放**：开启 AOF 的实例启动时**只载入 AOF**（忽略 RDB），逐条读取命令模拟客户端执行，把数据状态重放到文件末尾为止。

- 载入过程**同步阻塞**，文件越大启动越慢；混合前导使大快照部分以 RDB 速度载入，明显缓解该问题。
- 遇到解析失败或残缺命令时，Redis 默认**报错拒绝启动**，把处理权交给运维。

##### Redis 7 的装载顺序

**装载顺序**：manifest 先读，base 先载，incr 依序重放，全部完成后才开始对外服务。

- base 以快照级速度载入（混合时为 RDB 解析），incr 逐条重放命令。
- 重放的执行者是**伪客户端**：Redis 在进程内构造的一个不带网络的假客户端，日志命令逐条经它执行，走与真实写入完全相同的命令执行路径；过期键在重放中按过期时间正常淘汰，恢复状态与宕机前逻辑一致。
- 装载期间实例不接受客户端连接，AOF 体积直接决定故障恢复的中断时长。



##### 容忍截断的开关：aof-load-truncated

**aof-load-truncated**：控制启动时是否容忍尾部不完整命令的开关，默认 no。

- 设为 yes 时跳过最后一条残缺命令继续启动，并记录日志提示。
- 适用于宕机后接受尾部丢失、优先恢复服务的场景。
- 文件中部损坏不在此开关的管辖范围，仍需 redis-check-aof 处理。

```text
装载顺序示意（Redis 7）：
manifest → base 文件（快照级载入）
         → incr 文件 1（重放命令）
         → incr 文件 2（重放命令）
         → ……直到清单末尾，开始对外服务
```

> 辨析：aof-load-truncated 只能处理**尾部不完整**这一种损坏，文件中部损坏时它无能为力；能自动截断的前提是损坏恰好发生在最后一次 fsync 边界附近，而这正是宕机损坏最常见的形态，所以多数生产环境都安全地开着这一选项。

**速记**：启动**只认 AOF**，base 先进、incr 后放，尾部坏了看 aof-load-truncated。



#### 文件损坏与 redis-check-aof 修复

**redis-check-aof**：官方自带的 AOF 检查与修复工具，加 **--fix** 选项可把尾部不完整的命令**截断**，使文件恢复到可载入状态。

- 直接运行 redis-check-aof 加文件路径，只检查并报告问题位置，不改动文件。
- 加 --fix 后工具会提示确认，然后**从最后一条完整命令处截断**，之后的残缺内容被丢弃。
- Redis 7 起 redis-check-aof 能识别 manifest，对 **Multi-Part AOF 的整组文件**进行检查与修复。
- 截断意味着尾部数据被**永久丢弃**，修复前务必先复制备份原文件。
- 文件中部损坏时工具同样只能截断到损坏点，损失更大，应优先考虑从从节点或 RDB 重建。
- 修复完成后建议先在测试端口空跑一次载入，确认无误再放回生产。
- 修复的前提是损坏在**尾部**：checksum 错误、磁盘坏块导致的中部损坏，截断只能弃掉损坏点之后的全部数据。

> [!CAUTION]
> **注意内容**：--fix 的截断**不可逆**——被丢弃的命令无法找回，务必先备份原文件再执行修复；若损坏发生在文件中部，应优先用从节点数据或 RDB 快照重建，而不是反复截断，截断只是让服务能起来的止血手段。

```bash
redis-check-aof appendonly.aof         # 只检查，不修改
redis-check-aof --fix appendonly.aof   # 检查并截断修复
```

**速记**：先查后修，**--fix 截尾巴，动手前先备份**。



### AOF 的观测与优缺点

#### INFO 命令中的 AOF 观测点

**INFO persistence 段**：AOF 的运行状态集中暴露在 INFO 命令的 persistence 部分，是排查 AOF 问题的第一观测入口。

- **aof_enabled**：AOF 是否开启，非 1 说明配置未生效或被动态关闭。
- **aof_rewrite_in_progress**：重写是否正在进行，配合 aof_last_rewrite_time_sec（上次重写耗时，秒）判断重写是否过慢。
- **aof_current_size 与 aof_base_size**：当前体积与上次重写后的基准体积，二者差值反映膨胀速度，也是自动触发条件的输入。
- **aof_buffer_length**：aof_buf 当前积压长度，写入洪峰时短暂变大属正常，长期不落说明刷盘异常。
- **aof_delayed_fsync**：因磁盘繁忙被推迟的 fsync 次数，持续增长说明磁盘 IO 吃紧。
- **aof_last_write_status 与 aof_last_bgrewrite_status**：最近一次写入与重写的结果，出现 ok 之外的状态必须立刻处理。
- **aof_last_cow_size**：上次重写写时复制消耗的内存增量，用于预估下次重写的内存水位。
- **aof_pending_rewrite**：自动重写已被安排但尚未开始的标志。
- **aof_rewrite_scheduled**：BGSAVE 期间发现需要重写时置位，保存完成后立即补上重写。

```text
redis-cli INFO persistence 的 AOF 相关输出示意：
aof_enabled:1
aof_rewrite_in_progress:0
aof_last_rewrite_time_sec:5
aof_current_size:134217728
aof_base_size:67108864
aof_buffer_length:0
aof_delayed_fsync:0
aof_last_write_status:ok
aof_last_bgrewrite_status:ok
aof_last_cow_size:0
```

> Redis 7 的 Multi-Part AOF 保留了上述绝大多数字段，aof_rewrite_buffer_length 在新机制下恒为 0；监控脚本建议同时兼容单文件与多文件两种形态的字段表现，重点告警项是 delayed_fsync 与两个 last 状态。上例中 current_size 是 base_size 的两倍，正好踩在默认自动触发的临界点上。

**速记**：盯 **size 差值看膨胀，delayed_fsync 看磁盘，last 状态看成败**。



#### AOF 的优点与缺点

**AOF 的优点与缺点**：一句话概括——**丢数据少、文件可读可修复**是优点，**体积更大、恢复更慢**是缺点，与 RDB 互为镜像。

- 优点一：丢失窗口可控，everysec 档最多约 1 秒，远小于 RDB 两次快照间隔内的全部改动。
- 优点二：日志为文本协议，**可读、可检查、可截断修复**，出了问题有挽救余地。
- 优点三：与主从复制的命令传播同源，配合混合持久化后恢复速度可接近 RDB。
- 优点四：追加写不依赖定时快照时机，不会出现 RDB 那样集中消耗 CPU 与内存的保存瞬间。
- 缺点一：同样数据量下文件**体积普遍大于 RDB**，必须依赖重写机制控制膨胀。
- 缺点二：恢复要**逐条重放命令**，纯文本大 AOF 的载入时间明显长于直接载入 RDB 快照。
- 缺点三：everysec 仍有**秒级丢失**，always 又牺牲吞吐，不存在零丢失且零开销的免费方案。
- 缺点四：重写与 fsync 都会触碰磁盘，磁盘抖动时写延迟更敏感，对磁盘质量要求高于 RDB。
- 缺点五：重写期间的 fork 与写时复制会带来内存毛刺，与 RDB 的 bgsave 共享同一类风险。

> 选型上 AOF 与 RDB 不是二选一，而是如何组合的问题：是否同开、是否启用混合前导、恢复优先级等属于选型专题，**详见第 19 章**；AOF 相关的性能调优手段另见第 29 章。记忆的主线是把两条缺点与 RDB 的两条优点镜像对置，成对背更牢。

**速记**：**AOF 丢得少但恢复慢，RDB 恢复快但丢得多**，镜像互补。
