## 数据类型：String

### String 的定义与基本特性

#### String 是二进制安全的字符串

**String（字符串）**：是 Redis 最基础的数据类型，本质是**二进制安全**的字节序列，单个值最大 **512MB**。

- **二进制安全**：值按字节原样存储与读取，内容可以包含任意字节，不做字符集解释，也不要求以空字符结尾。
- 既能存普通文本与数字，也能存 JSON、序列化对象、图片缩略图等二进制内容，写入什么字节就取回什么字节。
- 底层由 SDS（简单动态字符串）实现，支持 O(1) 取长度并杜绝缓冲区溢出，实现细节详见第 10 章。
- 键名本身也是 String：Redis 的键永远是字符串，本章讨论的是作为**值类型**的 String。
- 数字形态的值同样以字符串形式记录，只是内部会用整数编码优化，见本章内部编码一节。

> 不少教程把二进制安全误解为只支持 ASCII 文本：恰恰相反，Redis 对值的内容零假设，中文、Emoji、压缩数据、各类序列化协议都可以安全存放，这正是它能承载千行万种业务场景的基础。

**速记**：String 是**不设防的字节串**，二进制安全，上限 **512MB**。



#### String 的常见使用形态

**String 的使用形态**：按所存内容划分，常见有**文本值、数字值、序列化对象、二进制块**四类。

- **文本值**：token、验证码、配置项、开关标记等短文本，如验证码键 captcha:13800000000。
- **数字值**：计数器、点赞数、库存、积分等整数或浮点，配合 INCR 一族使用，是高性能场景的主力。
- **序列化对象**：把对象 JSON 序列化后整体存入、整体读出，适合读多写少的缓存，见本章实战一节。
- **二进制块**：小图片、序列化协议报文等，但大文件不属于 String 的适用范围。
- 四类形态共用同一套命令，差异只在于应用层如何解释这些字节。

```bash
SET cfg:debug "on"
INCR pv:home
SET user:1001 '{"id":1001,"name":"tom"}' EX 600
APPEND log:20260907 "user-1 login\n"
```

```text
OK
(integer) 1
OK
(integer) 14
```

> 数字值并不是独立类型：INCR 一族只接受能解析为整数的值，浮点数不能自增，只能用 INCRBYFLOAT；判断一个键能否参与计数，标准是内容能否被解析，而不是存入时的写法。

**速记**：文本、数字、序列化对象、二进制块，**四形态、一套命令**。



### SET 命令全家族

#### SET 的基本用法与覆盖语义

**SET**：设置键值对的核心写命令，完整语法为 SET key value [EX seconds] [PX milliseconds] [NX|XX] [KEEPTTL] [GET]，选项按需组合。

- 基本形态 SET key value 成功返回 OK，把 value 原样存入 key。
- SET 是**覆盖语义**：键已存在时无条件用新值替换旧值，无论旧值原来是什么类型、还剩多少 TTL。
- 各选项顺序不影响语义，可自由组合，例如 SET key value NX EX 10。
- 返回值：无条件 SET 成功返回 OK；带 NX 时键已存在返回 nil；带 XX 时键不存在返回 nil。

```bash
SET greeting "hello redis"
SET session:uid1001 "a1b2c3" EX 3600
SET lock:order:1001 "holder-1" NX EX 10
SET status:uid1001 "active" XX
```

> 覆盖语义最常被忽略的副作用是 TTL：不带 KEEPTTL 的 SET 成功后，旧键上剩余的过期时间会被一并清除，缓存键因此悄悄变成永久键。若需保留原有 TTL，必须显式加 KEEPTTL 选项（6.0 起支持）。

> [!CAUTION]
> **注意内容**：用 SET 频繁刷新同一个键会反复清掉它的剩余 TTL，本应过期的缓存键将永远存活，长期累积会放大内存占用；刷新缓存时应统一带上 EX，或明确使用 KEEPTTL 继承原有过期时间。

**速记**：SET 是**无条件覆盖**，小心顺手清掉了 TTL。



#### 过期与条件选项 EX、PX、NX、XX

**EX、PX、NX、XX**：SET 的四个经典选项，分别控制过期时间（秒、毫秒两种精度）与设置条件（存在、不存在两种前提）。

- **EX seconds**（单位秒）：设置过期时间，到点自动删除，如 SET token abc EX 3600。
- **PX milliseconds**（单位毫秒）：同 EX，但精度为毫秒，适合验证码、短锁等短生命周期数据。
- **NX**（Not eXists）：仅当键**不存在**时才设置，键已存在则放弃并返回 nil。
- **XX**（eXists）：仅当键**已存在**时才设置，键不存在则放弃并返回 nil。

```bash
SET captcha:13800000000 "8362" EX 300
SET lock:order:1001 "a" PX 5000
SET config:banner "first" NX
SET config:banner "updated" XX
```

> NX 与 XX 是一对互补开关：NX 用于首次初始化、抢占资源，XX 用于只更新既有数据、不凭空造键；两者二选一，同时给出 NX 与 XX 属于非法组合，命令会直接报语法错误。

> [!TIP]
> **建议内容**：凡是缓存值加过期时间的写入，都应在 SET 里直接带 EX 或 PX，不要先 SET 再补一条 EXPIRE——既省一次网络往返，也避免两条命令之间进程崩溃导致键永不过期。

**速记**：EX/PX 定**生死时刻**，NX 抢**空位**，XX 只**改旧账**。



#### 新版本扩展选项 KEEPTTL、GET、EXAT、PXAT

**KEEPTTL、GET、EXAT、PXAT**：SET 在 6.0、6.2、7.0 中陆续加入的扩展选项，补齐了保留 TTL、原子读改写、绝对时间过期三类能力。

- **KEEPTTL**（6.0 起）：覆盖值时**保留**原键剩余的 TTL，与默认清 TTL 的行为相反。
- **GET**（6.2 起）：设置新值的同时**返回旧值**；键不存在返回 nil，键存在但不是 String 类型则报错并放弃设置。
- **EXAT unix-time-seconds**（7.0 起）：以**秒级 Unix 时间戳**指定过期时刻。
- **PXAT unix-time-milliseconds**（7.0 起）：以**毫秒级 Unix 时间戳**指定过期时刻。

```bash
SET config:mode "fast" EX 60
SET config:mode "slow" KEEPTTL
TTL config:mode
SET config:mode "quick" GET
SET rank:day "top10" EXAT 1798761600
```

```text
OK
OK
(integer) 60
"slow"
OK
```

> GET 选项让读旧值、写新值从两次往返压缩为一次，典型场景是覆盖前留存旧数据做比对或审计；EXAT 与 PXAT 适合多节点需要对齐同一过期时刻的场合，例如统一在次日零点失效的榜单缓存。

> EXAT 与 PXAT 给出的时间戳早于当前时间时，键会被立即删除；GET 选项遇到键存在但类型不符时报错并放弃设置，不会破坏原值。

**速记**：KEEPTTL **留命**，GET **换货退旧**，EXAT/PXAT **约定死期**。



### 读取、删除与批量操作

#### GET 与 DEL

**GET 与 DEL**：分别是 String 最基础的读命令与删命令，GET 返回键的字符串值，DEL 按键删除并返回实际删除的键数。

- GET key：返回值；键不存在返回 nil；键存在但不是 String 类型返回 WRONGTYPE 错误。
- DEL key [key ...]：删除一个或多个键，返回**实际删除**的键个数，可跨类型删除。
- GET 只能读 String；读 Hash、List 等类型必须换用各自的读命令，类型体系详见第 13 章。

```bash
SET greeting "hello"
GET greeting
DEL greeting
GET greeting
```

```text
OK
"hello"
(integer) 1
(nil)
```

> DEL 是同步删除，value 很大时会造成瞬时阻塞；对大键更稳妥的做法是评估后改用 UNLINK 异步删除（4.0 起），过期键的回收机制详见第 14 章，大键治理详见第 29 章。

**速记**：GET 读值 **nil 即无**，DEL 删键**返回删了几个**。



#### GETDEL 与 GETEX（6.2 新命令）

**GETDEL 与 GETEX**：6.2 引入的两个组合命令，GETDEL 取值的同时删除键，GETEX 取值的同时调整过期时间。

- GETDEL key：返回值并把键删掉，键不存在返回 nil，适合一次性令牌、取走即焚的消息场景。
- GETEX key [EX seconds] [PX milliseconds] [EXAT ts] [PXAT ts] [PERSIST]：取值同时可顺带续期、改绝对过期或清除过期时间。
- GETEX 不带任何选项时只取值、不动 TTL，行为等同 GET。
- PERSIST 子命令移除键的过期时间，使其变为永久键。
- GETEX 常用于读取会话的同时顺带续期，模拟滑动过期效果。
- GETDEL 的删除动作无条件执行：取到什么就删什么，不存在读到旧值却删不掉的情况。

```bash
SET otp:13800000000 "664821" EX 300
GETDEL otp:13800000000
GETDEL otp:13800000000
SET session:uid1001 "token-a" EX 3600
GETEX session:uid1001 EX 7200
GETEX session:uid1001 PERSIST
TTL session:uid1001
```

```text
OK
"664821"
(nil)
OK
"token-a"
"token-a"
(integer) -1
```

> GETDEL 出现之前，取出即删除需要 GET 与 DEL 两次往返，中间窗口里值可能被其他客户端再次读取；GETDEL 在服务端一次完成，天然消除了这个重复消费窗口。

**速记**：GETDEL **取走即焚**，GETEX **边读边管 TTL**。



#### MSET 与 MGET 批量操作

**MSET 与 MGET**：批量设置与批量读取命令，一次网络往返处理多个键。

- MSET key value [key value ...]：同时设置多对键值，执行成功永远返回 OK。
- MGET key [key ...]：按请求顺序返回多个键的值，**不存在**的键在对应位置返回 nil。
- 一次往返的意义：N 条独立命令要 N 次网络 RTT，MGET 只需 1 次，键越多收益越大。
- 批量命令是降低网络开销的第一手段，进一步的网络层优化见第 29 章。

```bash
MSET user:1001:name "tom" user:1001:age "18" user:1001:city "hangzhou"
MGET user:1001:name user:1001:age user:1001:city user:9999:name
```

```text
OK
1) "tom"
2) "18"
3) "hangzhou"
4) (nil)
```

> [!NOTE]
> **提醒内容**：MSET 是原子命令，执行期间不会出现一部分键已设置、另一部分尚未设置的中间状态；但这不等于事务，它不保证与 MGET、其他写命令之间的时序，需要事务语义时见第 23 章。

> MGET 的 nil 占位是高频踩坑点：按位回填业务对象前必须逐位判断 nil，不能假定返回数组里每一项都有效，也不能用长度判断哪些键存在。

**速记**：MSET/MGET 把 **N 次往返压成 1 次**，nil **占位莫踩坑**。



### 计数器一族

#### INCR 与 DECR 原子自增自减

**INCR 与 DECR**：对键所存整数做原子加一与减一，是 Redis 最经典的计数命令。

- 键不存在时**从 0 开始**：对不存在的键执行 INCR 等价于先置 0 再加 1，返回 1。
- 值必须能解析为 **64 位有符号整数**，否则报错 value is not an integer or out of range。
- 自增动作在服务端**一次完成**，并发多客户端同时调用不会丢失任何一次计数。
- 返回操作后的**新值**，可直接当取号器使用，如订单号序列、每日序号。
- 时间窗计数、全局序号、活跃标记等都能由 INCR 衍生，无需引入额外数据结构。
- INCR 的上限是 64 位有符号整数的最大值，超限同样报 value is not an integer or out of range。

```bash
SET likes:1001 10
INCR likes:1001
DECR likes:1001
DEL seq:order
INCR seq:order
INCR seq:order
SET name "tom"
INCR name
```

```text
OK
(integer) 11
(integer) 10
(integer) 0
(integer) 1
(integer) 2
OK
(error) ERR value is not an integer or out of range
```

> 先 GET、再在业务代码里加一、最后 SET 的写法在并发下必然丢计数：两个客户端同时读到同一个旧值，各自加一后互相覆盖。计数必须在服务端原子完成，这正是 INCR 一族存在的意义。

> [!IMPORTANT]
> **重要内容**：INCR 一族的原子性由 Redis 单线程模型保证，计数、限流、库存扣减等并发敏感场景都应直接使用这些命令，绝不能把自增逻辑拆到客户端用 GET 与 SET 拼装。

**速记**：INCR/DECR **从 0 起跳**、**原子加减一**、返回**新值**。



#### INCRBY、DECRBY 与 INCRBYFLOAT

**INCRBY、DECRBY 与 INCRBYFLOAT**：INCR 的带步长版本，前两者加减指定整数，INCRBYFLOAT（2.6 起）加减指定浮点数。

- INCRBY key increment：加指定整数，increment 可为负数，返回新值。
- DECRBY key decrement：减指定整数，decrement 可为负数，返回新值。
- INCRBYFLOAT key increment：加指定浮点数，increment 可为负数；键不存在时从 0 开始计算。
- INCRBYFLOAT 的结果最多保留 **17 位有效数字**，输出时会去掉多余的尾零。

```bash
SET stock:1001 100
DECRBY stock:1001 30
INCRBY stock:1001 -20
SET price:1001 9.5
INCRBYFLOAT price:1001 0.1
INCRBYFLOAT price:1001 -1.5
SET name "tom"
INCRBYFLOAT name 0.1
```

```text
OK
(integer) 70
(integer) 50
"9.5"
"9.6"
"8.1"
OK
(error) ERR value is not a valid float
```

> 三个易错点：INCRBYFLOAT 要求现有值与增量都能解析为双精度浮点，纯文本一样报错；INCR 不能作用于浮点值，浮点计数只能交给 INCRBYFLOAT；二进制浮点存在表示误差，金额类计数建议以分为单位的整数配合 INCRBY 完成，不要用浮点存钱。

**速记**：整数加减带 **BY**，浮点只有 **INCRBYFLOAT**，金额记**分**不用浮点。



#### 计数器应用场景：点赞、库存、限流

**计数器三场景**：点赞、库存扣减、接口限流是 INCR 一族最典型的落地场景，共同点都是用原子命令替代客户端拼装。

- **点赞**：键设计为 likes:文章ID，点赞 INCR、取消 DECR、展示 GET，读多写少时可再叠一层缓存。
- 展示类计数可先写 Redis、定期落库，兼顾实时性与持久性，落库方案见第 26 章。
- **库存**：键设计为 stock:商品ID，下单 DECR 并判断返回值，小于 0 说明库存已被抢空，回滚后拒绝。
- **限流**：键设计为 rate:接口:IP:时间窗，窗口内首次 INCR 并补 EXPIRE，返回值超过阈值即拒绝。
- 三个场景都依赖返回值驱动业务判断，这正是 INCR 一族返回新值的设计意图。

```js
// Node 中基于 INCR + EXPIRE 的固定窗口限流（ioredis 用法详见第 30 章）
const key = `rate:order:1.2.3.4:${Math.floor(Date.now() / 60000)}`;
const count = await redis.incr(key);
if (count === 1) {
  await redis.expire(key, 60); // 窗口内首次访问时补一个窗口长度的过期时间
}
if (count > 100) {
  throw new Error("请求过于频繁，请稍后再试");
}
```

> 库存防超卖的标准写法是先 DECR 后判断：返回值小于 0 就执行 INCRBY 1 回滚本次扣减，全程无需业务锁也不会超卖；更复杂的扣减规则可交给 Lua 脚本原子化，详见第 23 章。

> 固定窗口在窗口切换的边界处可能放过接近两倍的流量，对精度有要求的限流可改用 ZSet 实现滑动窗口，详见第 6 章。

**速记**：点赞 **INCR/DECR**，库存 **DECR 判负回滚**，限流 **窗口内计数**。



### 字符串内容操作

#### APPEND 与 STRLEN

**APPEND 与 STRLEN**：APPEND 把值追加到键已有值的末尾，STRLEN 返回值的字节长度。

- APPEND key value：键不存在时等同 SET，存在时把 value 拼到末尾，返回**追加后的总长度**。
- STRLEN key：返回值的字节数，键不存在返回 0。
- 两者都按**字节**而非字符计数：UTF-8 中文每字 3 字节，常见 Emoji 4 字节。
- STRLEN 对不存在的键与空串都返回 0，凭返回值无法区分这两种情形。
- APPEND 是 O(1) 追加，SDS 的预分配机制让连续追加不会反复扩容，详见第 10 章。

```bash
SET greet "hello"
APPEND greet " redis"
SET greet2 "你好"
STRLEN greet
STRLEN greet2
APPEND log:20260907 "user-1 login\n"
APPEND log:20260907 "user-2 login\n"
STRLEN log:20260907
```

```text
OK
(integer) 11
OK
(integer) 11
(integer) 6
(integer) 13
(integer) 26
(integer) 26
```

> [!CAUTION]
> **注意内容**：STRLEN 与 GETRANGE 都按字节计数，对中文取前 10 个字符会截到第 3 个字的中间，切出乱码；含多字节字符的值应在应用层解码后再截取，或改用 Hash、JSON 等结构组织文本。

> APPEND 的轻量用法是按键拼接日志，如键 log:20260907 每次追加一行。但该键会随追加无限增长，需要定期轮转，或改用 List（详见第 5 章）与 Stream（详见第 9 章）承载顺序消息。

**速记**：APPEND **接尾巴**返回**总长**，STRLEN 数的是**字节**不是字。



#### GETRANGE 与 SETRANGE

**GETRANGE 与 SETRANGE**：对值的字节区间做读取与覆写，相当于字符串级的切片与原位替换。

- GETRANGE key start end：返回 start 到 end 的**闭区间**字节，下标支持负数从尾部计数，-1 是最后一个字节。
- GETRANGE 越界安全：start 或 end 超出实际范围时按边界截断，不报错也不补零。
- SETRANGE key offset value：从 offset 指定的字节位置开始用 value 覆写，返回**覆写后**的总长度。
- offset 超过原值长度时，中间空洞用**零字节**填充，值会被拉长到 offset 加 value 的长度。
- 两个命令的操作单位同样是字节，对多字节字符按字符直觉截取会出错。
- SETRANGE 在原值足够长时只覆写目标区间，区间外的字节保持原样。

```bash
SET greet "hello redis"
GETRANGE greet 0 4
GETRANGE greet -5 -1
SETRANGE greet 6 "Redis"
SET pad ""
SETRANGE pad 8 "x"
STRLEN pad
```

```text
OK
"hello"
"redis"
(integer) 11
OK
(integer) 9
(integer) 9
```

> SETRANGE 填零扩长是把双刃剑：可用于预分配定长数据块，但 offset 误写成极大值会瞬间制造一个巨大的稀疏字符串，占满内存并拖慢操作，offset 必须来自可信计算，不可透传用户输入。

**速记**：GETRANGE **闭区间切片**、支持负下标，SETRANGE **原位覆写**、越界**填零**。



### SETNX 与分布式锁雏形

#### SETNX、MSETNX 与原子批量设值

**SETNX 与 MSETNX**：SETNX 仅在键不存在时设置（是 SET NX 选项的前身），MSETNX 仅在**所有**给定键都不存在时才批量设置。

- SETNX key value：键不存在则设置并返回 1，已存在则放弃返回 0；官方建议改用 SET key value NX 代替。
- MSETNX key value [key value ...]：所有键都不存在时一次性设置全部并返回 1；**只要有一个键已存在**，则一个都不设置并返回 0。
- MSETNX 的全或无语义由服务端保证：先检查全部键，再统一写入。
- SETNX 与 SET NX 返回值语义一致，旧代码迁移成本几乎为零。
- MSETNX 常用于一次性初始化一组关联配置，避免留下半初始化的中间状态。
- 返回值只有 1 与 0 两态，业务侧据此判断抢占或初始化是否成功。

```bash
MSETNX cfg:a "1" cfg:b "2"
MSETNX cfg:a "9" cfg:c "3"
MGET cfg:a cfg:b cfg:c
```

```text
(integer) 1
(integer) 0
1) "1"
2) "2"
3) (nil)
```

> SETNX 无法同时设置过期时间是它的硬伤：加锁方一旦崩溃，锁可能永远不释放。正确姿势是用 SET key value NX EX seconds 一条命令同时完成抢占与限时，这也是分布式锁雏形的标准写法，见下一节。

**set nx ex 组合**：SET key uniqueValue NX EX seconds 一条命令同时完成不存在才设置与限时过期，是单机分布式锁的最小雏形。

- NX 保证**互斥**：锁被占用时其他客户端设置失败，返回 nil 即视为获取锁失败。
- EX 保证**自动释放**：持锁方崩溃后，锁随 TTL 到期自动消失，避免死锁。
- value 应写入**唯一标识**（如 UUID 或请求 ID），释放锁时先校验标识再删除，防止误删他人的锁。
- TTL 取值要覆盖业务最长执行时间，太短会在业务未完成时提前释放锁。

```bash
SET lock:order:1001 "uuid-550e" NX EX 10
SET lock:order:1001 "uuid-777f" NX EX 10
DEL lock:order:1001
```

```text
OK
(nil)
(integer) 1
```

> 校验 value 再 DEL 两步之间存在竞态，持锁到期换主后可能误删新锁，严格实现要用 Lua 脚本把校验与删除合成原子操作，详见第 23 章；锁的续期、可重入、红锁等进阶话题详见第 27 章。

> 抢锁失败时无需原地等待：不需要锁的业务应立即走降级路径，需要等待的业务应在客户端做有限次重试并加随机退避，避免大量请求同时唤醒造成惊群。

**速记**：**NX 抢锁、EX 保命、value 防误删**，释放校验要原子。



### 内部编码

#### 内部编码：int、embstr 与 raw

**String 的内部编码**：共 **int、embstr、raw** 三种，Redis 按值的内容与长度自动选择，可用 OBJECT ENCODING 实时查看。

- **int**：值能解析为 **64 位有符号整数**时使用，直接把整数存进对象指针位置，省去字符串开销。
- **embstr**：值是字符串且长度**不超过 44 字节**时使用，对象头与 SDS 数据**一次内存分配**完成，内存连续、缓存友好。
- **raw**：字符串长度**超过 44 字节**时使用，对象头与数据分两次分配，适合长文本。
- 浮点数没有独立编码：以字符串形式存放，通常落在 embstr 或 raw 中。

```bash
SET num 12345
OBJECT ENCODING num
SET short "hello"
OBJECT ENCODING short
SET long "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
OBJECT ENCODING long
```

```text
"int"
"embstr"
"raw"
```

```bash
INCR num
OBJECT ENCODING num
APPEND num "x"
OBJECT ENCODING num
```

```text
(integer) 12346
"int"
(integer) 6
"raw"
```

> embstr 是**只读编码**：任何写操作（APPEND、SETRANGE，或 INCR 引发的修改）都会把它转成 raw，且转换不会逆转；int 编码在值被 APPEND 一个字符后同样退化为 raw。编码流转的完整规则见第 13 章。

**速记**：整数 **int**，短串 **embstr 一次分配**，长串 **raw**，阈值 **44 字节**。



### 实战与误用

#### 对象缓存实战与常见误用

**对象缓存实战**：把对象 JSON 序列化后整体存入 String，读取时反序列化，配合过期时间构成最简单的旁路缓存。

- 写入：SET user:1001 加 JSON 字符串并带 EX 600，一步完成存值与过期。
- 读取：GET 命中后在应用层 JSON.parse 直接使用；未命中回源数据库并回写。
- 整存整取最适合读多写少；需要按字段读写对象时改用 Hash 更合适，详见第 4 章。
- 键名用冒号分层是社区通行的命名习惯，如 业务:对象:ID 形式的 user:1001。
- 大对象缓存建议叠加随机 TTL，避免大量键同时失效引发雪崩，详见第 25 章。
- 缓存与数据库的一致性维护属于旁路缓存模式问题，详见第 26 章。

```bash
SET user:1001 '{"id":1001,"name":"tom","age":18}' EX 600
GET user:1001
OBJECT ENCODING user:1001
```

```text
OK
"{\"id\":1001,\"name\":\"tom\",\"age\":18}"
"raw"
```

```js
// 旁路缓存读路径：先查缓存，未命中回源并回写（一致性策略详见第 26 章）
async function getUser(id) {
  const cacheKey = `user:${id}`;
  const cached = await redis.get(cacheKey);
  if (cached) {
    return JSON.parse(cached); // 命中：反序列化直接返回
  }
  const user = await db.query("SELECT * FROM users WHERE id = ?", [id]);
  if (user) {
    await redis.set(cacheKey, JSON.stringify(user), "EX", 600); // 回写并设置过期
  }
  return user;
}
```

**常见误用**：String 的典型问题集中在**大 value、TTL 丢失、拆散原子命令、整存整取高频改**四点。

- **大 value**：单值数 MB 会拖慢网络传输与序列化，读写大键还可能阻塞单线程；单值建议控制在几十 KB 内，超大内容外置存储、Redis 只存引用。
- **TTL 丢失**：SET 不带 KEEPTTL 会清掉剩余过期时间，缓存键悄悄变成永久键，内存只进不出。
- **拆散原子命令**：把 INCR、判重等逻辑拆成 GET 与 SET 两条命令，并发下必然出错，见本章计数器一节。
- **整存整取高频改字段**：改一个字段也要全量序列化与覆盖，热点对象的局部更新应改用 Hash。
- **键名滥用**：把 String 当存储桶无限拼接超大 JSON，字段一多整存整取的开销急剧上升。
- **忽视单线程边界**：大 JSON 的解析与再加工应放在客户端完成，Redis 只负责存取字节。

> [!WARNING]
> **警告内容**：单个 String 值接近或超过 1MB 就应视为危险信号：读写延迟显著上升，主从同步与持久化开销被放大，大键删除还可能阻塞主线程，务必在设计与代码评审阶段拦住大 value。

**速记**：小而短是 String 的美德，**大 value、丢 TTL、拆原子**是三大反模式。
