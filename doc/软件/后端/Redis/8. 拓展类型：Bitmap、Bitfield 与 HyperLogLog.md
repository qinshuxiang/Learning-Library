## 拓展类型：Bitmap、Bitfield 与 HyperLogLog

本章介绍 Redis 在五种基础类型之外的三个统计工具：**Bitmap**（位图）、**Bitfield**（位域）与 **HyperLogLog**（基数估计结构）。它们不面向业务对象的存取，而是以极小或可控的内存完成按位记录、位段运算与去重计数等统计任务。掌握三者的定位、命令与实战模式，是设计签到、日活、UV 统计等功能的前提。

### 三者的定位与总览

#### 三者是统计类用法而非通用容器

**统计类用法**：指 Bitmap、Bitfield 与 HyperLogLog 三者都不是新的通用容器，而是围绕计数与标记两类需求设计的工具。

- **Bitmap（位图）**：把一个 String 键的内容当作二进制位数组来用，本质是 String 的位视角（详见第 3 章）。
- **Bitfield（位域）**：同样基于 String，把键内容划分为任意宽度的位段，按无符号或有符号整数读写。
- **HyperLogLog**：独立的基础类型，是专门做基数估计的概率结构，不保存元素本身。
- 三者的共同点：只产出**统计结果**，不提供遍历成员与取出成员的能力。
- Bitmap 与 Bitfield 不引入新的底层编码，数据就是普通字符串（编码细节详见第 13 章）。
- 三个工具都把状态压缩到极限：一个对象只占 1 位或几个位，一个集合只占一个固定大小的估计器。
- 三者都可与过期策略配合：按天或按月拆键后，对历史键设置 TTL 即可自动回收（键管理详见第 2 章）。

> HyperLogLog 虽然是独立类型，但同样只为统计服务：它无法列出放入过哪些元素，也无法判断某个元素是否存在，这与 Set 形成本质差别（Set 详见第 6 章）。

**速记**：两把刀架在 **String** 上（Bitmap 按位、Bitfield 按段），一个独立结构（HyperLogLog）只数个数不存元素。



#### 与五种基础类型的边界

**边界标准**：需要取回数据本身用五种基础类型，只需要统计结果时才用本章工具。

- **String、Hash、List、Set、ZSet**：通用容器，能存取、遍历、修改业务对象。
- **Bitmap**：精确记录每个对象的某个是非状态，内存与对象规模成正比，常数是 1 位。
- **Bitfield**：精确记录每个对象的一个小整数（如等级、状态码、数值开关），内存与位段宽度成正比。
- **HyperLogLog**：只回答大约有多少个不重复元素，内存恒定约 12KB，结果带约 0.81% 的标准误差。
- 判断顺序：先问要不要成员明细，再问要不要精确值，最后才轮到近似方案。
- 三类工具可以组合：位图做标记、位域存小整数、HyperLogLog 出总数，各管一段统计口径。

```bash
SETBIT bm:demo 9999999 1
STRLEN bm:demo
SADD set:demo u9999999
SCARD set:demo
```

```text
127.0.0.1:6379> SETBIT bm:demo 9999999 1
(integer) 0
127.0.0.1:6379> STRLEN bm:demo
(integer) 1250000
127.0.0.1:6379> SADD set:demo u9999999
(integer) 1
127.0.0.1:6379> SCARD set:demo
(integer) 1
```

> 对象只有 1 个时，位图要为编号 9999999 分配 125 万字节，集合只要几十字节，Set 反而更省；当对象规模达到千万级，位图仍是这 1.25MB 上下，集合却要涨到数百 MB，优势彻底反转。位图的收益来自对象规模与编号紧凑度，不是无条件的。

> 三类工具出错的方向也不同：Bitmap 与 Bitfield 是精确的，出错通常源于 offset 设计或键拆分不当；HyperLogLog 的误差是结构固有的，只能以省内存为出发点去接受它。

**速记**：要明细用容器，要精确标记用 **Bitmap**，要小整数用 **Bitfield**，只要个数用 **HyperLogLog**。



### Bitmap：位图

#### Bitmap 的定义与本质

**Bitmap**：由二进制位组成的数组，Redis 把一个 String 键的内容按位解释，允许以位为单位读写。

- 位下标 offset 从 0 开始，最大值为 2 的 32 次方减 1，即 4294967295 位，整键最大约 512MB。
- 键的内容就是普通字符串，用 STRLEN 查看字节数，用 GET 可以看到原始字节串。
- 位图极稀疏时浪费明显：只置最高一位，中间未用到的位也要真实占内存。
- 适合表达海量对象各自的二元状态：签没签到、活没活跃、买没买过。
- 判断一个需求适不适合位图，看它能否归结为一串整齐编号的是非问题。
- 位图与字符串编码共享同一套内存管理，位图键同样会出现在键空间与淘汰策略的视野内。

> [!WARNING]
> **警告内容**：对同一键先写小 offset、再写接近 2 的 32 次方减 1 的大 offset，Redis 会一次性分配整段内存（最大 512MB），在单线程内可能造成明显卡顿。设计键时务必把 offset 范围控制在实际需要的规模内。

```bash
SETBIT bm:demo 0 1
STRLEN bm:demo
SETBIT bm:demo 15 1
STRLEN bm:demo
```

```text
127.0.0.1:6379> SETBIT bm:demo 0 1
(integer) 0
127.0.0.1:6379> STRLEN bm:demo
(integer) 1
127.0.0.1:6379> SETBIT bm:demo 15 1
(integer) 0
127.0.0.1:6379> STRLEN bm:demo
(integer) 2
```

> 位图按整字节向上扩展，第 15 位落在第 1 个字节，键长便从 1 字节变为 2 字节。容量规划时按最大 offset 除以 8 估算字节数，再留少量余量即可。

**速记**：Bitmap 就是 **String 的位视图**，offset 上限 **2 的 32 次方减 1**，整键不超 512MB。



#### SETBIT 与 GETBIT：按位写入与读取

**SETBIT**：把键的指定位置为 0 或 1，完整签名 SETBIT key offset value；**GETBIT**：读取指定位置的位值，完整签名 GETBIT key offset。

- offset 从 0 起，value 只能是 0 或 1，其他值直接报错。
- SETBIT 返回该位写入前的**旧值**，便于实现翻转类逻辑。
- 写入超过当前长度的 offset 时**自动扩展**，中间从未写过的位一律补 0。
- GETBIT 访问超过当前长度的 offset 不报错，直接返回 0。
- 两个命令的时间复杂度都是 O(1)，读写任意位代价相同。
- 位下标不支持负数，没有从尾部倒数第几位的语义，需要时用 BITCOUNT 一类的负下标区间命令变通。

```bash
SETBIT bit:demo 7 1
GETBIT bit:demo 7
SETBIT bit:demo 20 1
STRLEN bit:demo
GETBIT bit:demo 100
```

```text
127.0.0.1:6379> SETBIT bit:demo 7 1
(integer) 0
127.0.0.1:6379> GETBIT bit:demo 7
(integer) 1
127.0.0.1:6379> SETBIT bit:demo 20 1
(integer) 0
127.0.0.1:6379> STRLEN bit:demo
(integer) 3
127.0.0.1:6379> GETBIT bit:demo 100
(integer) 0
```

> 第 20 位落在第 2 个字节（每字节 8 位），故键长度从 1 字节扩展为 3 字节，第 8 到 19 位全是自动补上的 0；读第 100 位并未触发扩展，只返回 0。理解字节与位的换算关系，是看懂位图长度变化的关键。

**速记**：SETBIT 返回**旧值**，越界**自动扩展补 0**；GETBIT 越界**返回 0 不报错**，读不会扩展键。



#### BITCOUNT：统计置位数量

**BITCOUNT**：统计指定区间内值为 1 的位有多少个，完整签名 BITCOUNT key [start end [BYTE | BIT]]。

- 不带区间时统计整个键，是最常用的形态。
- start 与 end 默认按**字节**计，第 0 字节覆盖第 0 到 7 位。
- 负数下标从末尾倒数，-1 表示最后一个字节。
- Redis 7.0 起可选 BYTE 或 BIT 修饰：BYTE 按字节（与默认行为一致），BIT 按位。
- 时间复杂度 O(N)，N 是被统计区间的字节数。
- 只统计值为 1 的位；想知道 0 的个数，用区间总位数减去 BITCOUNT 结果即可。

> [!CAUTION]
> **注意内容**：start 与 end 默认是字节下标而不是位下标，BITCOUNT key 0 9 统计的是前 10 个字节即前 80 位，不是前 10 位。想按位划定区间，必须在 Redis 7.0 及以上显式追加 BIT 修饰。

```bash
SETBIT bit:demo 0 1
SETBIT bit:demo 5 1
SETBIT bit:demo 20 1
BITCOUNT bit:demo 0 0
BITCOUNT bit:demo
BITCOUNT bit:demo 0 20 BIT
BITCOUNT bit:demo 0 -1
```

```text
127.0.0.1:6379> BITCOUNT bit:demo 0 0
(integer) 2
127.0.0.1:6379> BITCOUNT bit:demo
(integer) 3
127.0.0.1:6379> BITCOUNT bit:demo 0 20 BIT
(integer) 3
127.0.0.1:6379> BITCOUNT bit:demo 0 -1
(integer) 3
```

> 区间语法是闭区间：BITCOUNT key 0 20 BIT 统计第 0 到第 20 位共 21 位，两端都包含。负下标与 7.0 的新修饰参数可以叠加使用，如 BITCOUNT key -1 -1 BIT 表示最后一个字节的 8 位。字节与位两套下标互不相通，跨版本迁移脚本前先确认目标实例的 Redis 版本，再决定是否携带 BIT 修饰。

**速记**：区间默认**按字节**，7.0 加 **BIT** 才按位，整键统计不传区间最常用。



#### BITPOS：查找第一个 0 或 1 位

**BITPOS**：在键内容中查找第一个值为 0 或 1 的位，完整签名 BITPOS key bit [start [end [BYTE | BIT]]]。

- bit 参数只能是 0 或 1，返回值是**位下标**。
- start 与 end 的规则与 BITCOUNT 相同，Redis 7.0 起同样支持 BYTE 或 BIT 修饰。
- 找不到目标位时返回 -1。
- 常与 BITCOUNT 配合，用于定位首个签到日、最早置位对象等场景。
- 给定区间时只在该区间内查找，配合负下标可以从尾部向前定位。

> 键不存在或内容全为 0 时找 1 返回 -1；找 0 时若键真实存在且只含零字节，会返回第一个位的位置，若键根本不存在则特判返回 -1，避免把不存在的键当成无限长的零串去解释。

```bash
SETBIT bit:demo 5 1
BITPOS bit:demo 1
BITPOS bit:demo 0
DEL bit:demo
BITPOS bit:demo 1
BITPOS bit:demo 0
```

```text
127.0.0.1:6379> BITPOS bit:demo 1
(integer) 5
127.0.0.1:6379> BITPOS bit:demo 0
(integer) 0
127.0.0.1:6379> DEL bit:demo
(integer) 1
127.0.0.1:6379> BITPOS bit:demo 1
(integer) -1
127.0.0.1:6379> BITPOS bit:demo 0
(integer) -1
```

> 返回的永远是位下标而非字节下标，即使区间参数按字节给出也要换算理解。业务上用它找第一个 1 的场景多于找 0，例如取出用户在本月的第一个签到日。

**速记**：BITPOS 找**第一个目标位**，返回位下标，找不到给 **-1**，键不存在时特判返回 -1。



#### BITOP：多键位运算

**BITOP**：对若干键做按位运算并把结果写入目标键，完整签名 BITOP operation destkey key [key ...]。

- operation 支持 AND（与）、OR（或）、XOR（异或）、NOT（非）四种运算。
- AND、OR、XOR 接受多个输入键，NOT 只接受一个输入键。
- 缺失的输入键按全 0 字节串参与运算。
- 结果键的长度等于最长输入键的长度，短键缺位一律按 0 处理。
- 时间复杂度 O(N)，N 是最长输入键的字节数。
- BITOP 会覆盖 destkey 原有内容；把某个源键同时作为 destkey 是安全的，运算在内部完成后才写回。

> [!NOTE]
> **提醒内容**：BITOP 在单线程模型内同步执行（详见第 16 章），对大键做位运算会短暂阻塞其他命令，亿位级别的运算应拆分执行或放到业务低峰期。

```bash
SETBIT dau:20260906 1001 1
SETBIT dau:20260907 1001 1
SETBIT dau:20260907 1002 1
BITOP AND dau:two-days dau:20260906 dau:20260907
BITOP OR dau:any-day dau:20260906 dau:20260907
BITCOUNT dau:two-days
BITCOUNT dau:any-day
```

```text
127.0.0.1:6379> BITOP AND dau:two-days dau:20260906 dau:20260907
(integer) 63
127.0.0.1:6379> BITOP OR dau:any-day dau:20260906 dau:20260907
(integer) 63
127.0.0.1:6379> BITCOUNT dau:two-days
(integer) 1
127.0.0.1:6379> BITCOUNT dau:any-day
(integer) 2
```

> BITOP 的返回值是结果键的字节长度，不是置位个数，数个数要再接一次 BITCOUNT。AND 出连续两天都活跃的用户，OR 出两天内活跃过的用户，一与一或正好覆盖留存与活跃两类口径。

**速记**：与、或、异或走**多键**，非运算走**单键**，结果落 destkey，长度随**最长输入键**。



#### BITFIELD：位段读写与溢出控制

**BITFIELD**：把键内容划分为多个任意宽度的位段，一次命令完成读、写与自增，完整签名 BITFIELD key [GET type offset] [SET type offset value] [INCRBY type offset increment] [OVERFLOW WRAP | SAT | FAIL]。

- 类型由前缀加宽度构成：u 表示无符号、i 表示有符号，如 u8、i32；无符号最宽 63 位，有符号最宽 64 位。
- offset 是位下标，也可写成 #n 形式，表示按类型宽度对齐的第 n 个位段。
- 子命令可以混用多次，返回值是与子命令顺序一一对应的数组。
- 溢出策略三种：WRAP 回绕（默认）、SAT 饱和到边界、FAIL 失败（返回 NULL 且不改动原值）。
- OVERFLOW 子命令只影响它之后出现的 INCRBY，不改写之前的子命令。
- 与 SETBIT 一次只写 1 位不同，BITFIELD 能一次写入或读取一个多位整数并正确处理符号。
- 位段操作不改变键的整体长度：写到已有的位上原地生效，写到超出当前长度的位上才会触发扩展。

```bash
BITFIELD bf:demo SET u8 #0 200 SET i8 #1 -5
BITFIELD bf:demo GET u8 #0 GET i8 #1
BITFIELD bf:demo OVERFLOW SAT INCRBY u8 #0 100
BITFIELD bf:demo OVERFLOW FAIL INCRBY u8 #0 100
```

```text
1) (integer) 0
2) (integer) 0
1) (integer) 200
2) (integer) -5
1) (integer) 255
1) (nil)
```

> 末次自增时 u8 位段已是 255，FAIL 策略拒绝溢出，返回 NULL 且原值不动；若换成 SAT 会停在 255，换成默认 WRAP 则回绕为 99。三种策略的差别只体现在 INCRBY 溢出的瞬间，GET 与 SET 不受 OVERFLOW 影响。

**速记**：类型 **u 或 i 加位宽**，偏移 **#n 对齐**，溢出 **WRAP、SAT、FAIL** 三选一，OVERFLOW 只管后面的 INCRBY。



#### 实战：用户签到场景

**签到场景**：以月为周期、以天为 offset，用一张位图记录一个用户整月的签到状态。

- 键设计：sign:用户ID:年月，例如 sign:1001:202609，按月拆键避免键无限增长。
- offset 设计：天数为 offset，9 月 1 日对应第 0 位，9 月 7 日对应第 6 位。
- 签到动作：SETBIT sign:1001:202609 6 1。
- 当月签到天数：BITCOUNT sign:1001:202609。
- 连续签到：用 BITFIELD 的 GET 一次取出当月前若干位，再在应用层从今天往前数连续的 1。
- 查询某天与补签：直接对对应 offset 执行 GETBIT 与 SETBIT 即可。
- 月初清理或归档：对上月键设置过期时间即可回收（键管理详见第 2 章）。

```bash
SETBIT sign:1001:202609 0 1
SETBIT sign:1001:202609 5 1
SETBIT sign:1001:202609 6 1
BITCOUNT sign:1001:202609
BITFIELD sign:1001:202609 GET u7 0
```

```text
127.0.0.1:6379> BITCOUNT sign:1001:202609
(integer) 3
127.0.0.1:6379> BITFIELD sign:1001:202609 GET u7 0
1) (integer) 97
```

> 连续签到的判定在应用层完成：97 的二进制是 1100001，从最低位（今天）向高位连续数 1 得到 2 天；跨月连续需要再拼上上个月的键继续往前数。一个整数一次取出整段位序列，比逐天 GETBIT 少一次网络往返。

**速记**：**月为键、天为位**，BITCOUNT 数总天数，连续天数靠 **GET 取位序列回应用层去数**。



#### 实战：亿级用户的日活统计

**日活统计**：以天为键、以用户 ID 为 offset，用一张位图记录当天哪些用户活跃。

- 键设计：dau:日期，例如 dau:20260907，一天一张位图。
- offset 设计：用户数字 ID 直接当 offset，ID 为 1001 的用户活跃则 SETBIT dau:20260907 1001 1。
- 当日 DAU：BITCOUNT dau:20260907，一次统计完成。
- 多日留存与活跃：BITOP AND 或 OR 合并多张日位图后再 BITCOUNT。
- 空间账：1 亿用户单日位图约 12.5MB；即使日活高达 3 亿多，单张位图也只占 40 多 MB。
- 对比方案：用 Set 存亿级用户 ID，每个 ID 至少几十字节，内存要以 GB 计，相差两个数量级（Set 详见第 6 章）。
- 历史位图按日期天然分区，过期回收只需对旧日期键设置 TTL。

> offset 必须是紧凑的小整数。若系统使用不连续的大 ID 或字符串型 UUID，需要先映射成自增序号再入位图，否则 4 字节范围的随机 ID 会把位图撑到数百 MB 而毫无收益。

```bash
SETBIT dau:20260907 1001 1
SETBIT dau:20260907 1002 1
BITCOUNT dau:20260907
BITOP AND dau:keep-2d dau:20260906 dau:20260907
BITCOUNT dau:keep-2d
```

```text
127.0.0.1:6379> BITCOUNT dau:20260907
(integer) 2
127.0.0.1:6379> BITOP AND dau:keep-2d dau:20260906 dau:20260907
(integer) 63
127.0.0.1:6379> BITCOUNT dau:keep-2d
(integer) 2
```

> 次日留存就是 AND 结果的置位数，7 日留存就是把 7 张日位图 AND 起来；若要统计 N 日内任意一天活跃过的用户，把 AND 换成 OR。一套 SETBIT 加 BITOP 加 BITCOUNT 的组合，覆盖绝大多数活跃口径。

**速记**：**日为键、用户为位**，BITCOUNT 出 DAU，BITOP 出留存，亿级用户也只要几十 MB。



### HyperLogLog：基数估计

#### HyperLogLog 的定义与原理

**HyperLogLog**：一种概率型基数估计结构，用固定约 12KB 的内存估计一批数据中不重复元素的个数，标准误差约 0.81%。

- 它只回答一个数字问题：不重复的元素大约有多少个。
- 不保存任何元素本身，因此无法遍历、无法查重、无法删除单个元素。
- 底层是 16384 个寄存器，每个 6 位，合计约 12KB。
- 原理：对元素哈希后按前缀分桶，用桶内哈希值前导 0 的最大位数推断基数，再用调和平均汇总各桶。
- 元素很少时采用稀疏（sparse）编码，占用更小；元素增多后转为稠密（dense）编码，上限约 12KB。
- 重复元素反复添加不影响结果，也不增加任何内存。
- 结构无法回退：不存在删除单个元素的能力，误写入的脏数据只能整键重建。

> [!NOTE]
> **提醒内容**：估计结果不是随机的：同一批输入无论执行多少次 PFCOUNT，得到的都是同一个确定数值。0.81% 的标准误差描述的是该数值与真实基数之间可能存在的偏离，而不是每次运行会变。

```bash
PFADD hll:demo a b c
PFADD hll:demo a c
PFCOUNT hll:demo
```

```text
127.0.0.1:6379> PFADD hll:demo a b c
(integer) 1
127.0.0.1:6379> PFADD hll:demo a c
(integer) 1
127.0.0.1:6379> PFCOUNT hll:demo
(integer) 3
```

> 重复添加 a 与 c 不会让基数变成 5，估计值始终围绕真实基数 3 波动；当真实基数极大时，估计值与真值的偏差被稳定控制在 0.81% 的标准误差量级。小基数下稀疏编码可以让键远小于 12KB，不必担心几个元素就占满。

**速记**：用**固定 12KB** 换一个**确定但近似**的去重计数，误差约 **0.81%**，只数个数不存元素。



#### PFADD 与 PFCOUNT：写入与计数

**PFADD**：向 HyperLogLog 添加元素，完整签名 PFADD key [element [element ...]]；**PFCOUNT**：返回基数估计值，完整签名 PFCOUNT key [key ...]。

- PFADD 不带 element 时只创建或清空结构，带任意多个 element 时逐一吸收。
- 重复元素重复添加不影响结果，命令本身总是 O(1)。
- PFCOUNT 传单个键时读取缓存值，接近 O(1)。
- PFCOUNT 传多个键时需要临时合并各结构再计算，代价与键的规模成正比，较慢。
- 返回值是估计的基数，不是精确值，理解这一点是使用前提。
- 添加的元素会先做哈希再进寄存器，元素可以是任意字符串，长度只影响哈希开销。

> [!IMPORTANT]
> **重要内容**：PFCOUNT 在稠密编码下会把算出的基数缓存回结构内，属于事实上的写命令。它不能当作纯读操作对待，在只读从库的访问设计、事务与脚本的读写判定中都要留意这一语义（事务与脚本详见第 23 章）。

```bash
PFADD uv:index:20260907 u1
PFADD uv:index:20260907 u2 u3 u1
PFCOUNT uv:index:20260907
PFCOUNT uv:index:20260907 uv:index:20260908
```

```text
127.0.0.1:6379> PFADD uv:index:20260907 u1
(integer) 1
127.0.0.1:6379> PFADD uv:index:20260907 u2 u3 u1
(integer) 1
127.0.0.1:6379> PFCOUNT uv:index:20260907
(integer) 3
127.0.0.1:6379> PFCOUNT uv:index:20260907 uv:index:20260908
(integer) 5
```

> 多键 PFCOUNT 给出的是各结构并集的估计值，结果不落键、每次都重算；高频读取多日合计 UV 时应改用 PFMERGE 固化结果，避免反复承担合并开销。

**速记**：PFADD **只进不重**，PFCOUNT **单键快、多键慢**，且它本质上是**写命令**。



#### PFMERGE：合并估计器

**PFMERGE**：把多个 HyperLogLog 合并写入目标键，完整签名 PFMERGE destkey sourcekey [sourcekey ...]。

- 合并按寄存器逐个取最大值，等价于对源集合求并集后的估计。
- 目标键可以同时出现在源键列表中，适合做滚动累加。
- 合并结果落键持久保存，可被 PFCOUNT 反复读取，适合周报、月报聚合。
- 时间复杂度 O(N)，N 是参与合并的寄存器总数。
- 源键缺失时按空结构参与合并，不会报错。
- 合并只增不减：先合入的元素无法从目标键中剔除，按天聚合的键不要复用作按周目标。
- 目标键不存在时自动创建，结果从零开始累积。

```bash
PFMERGE uv:index:2026w36 uv:index:20260901 uv:index:20260902 uv:index:20260903
PFCOUNT uv:index:2026w36
```

```text
127.0.0.1:6379> PFMERGE uv:index:2026w36 uv:index:20260901 uv:index:20260902 uv:index:20260903
OK
127.0.0.1:6379> PFCOUNT uv:index:2026w36
(integer) 1893
```

> PFMERGE 与多键 PFCOUNT 的区别：前者把并集结果固化成新键供反复使用，后者只做一次性临时计算不落键。需要反复读取聚合值时，先 PFMERGE 再单键 PFCOUNT 更划算。

**速记**：PFMERGE 逐寄存器**取最大值**，结果**落键**，专为**按周按月聚合 UV** 而生。



#### 实战：UV 统计与 Set 方案对比

**UV 统计**：以页面加日期为键记录访客，PFADD 记录、PFCOUNT 读数、PFMERGE 聚合。

- 键设计：uv:页面:日期，例如 uv:index:20260907。
- 访客到访执行 PFADD uv:index:20260907 用户ID，重复访客自然被吸收。
- 单日 UV 执行 PFCOUNT，周月 UV 先 PFMERGE 再 PFCOUNT。
- 内存：无论 UV 是一千还是一亿，稠密编码下每个键恒定约 12KB。
- Set 精确方案：亿级 UV 仅存元素就要 GB 级内存，而多数报表场景只求个数不求明细（Set 详见第 6 章）。
- 口径评估：误差 0.81% 意味着日 UV 100 万时偏差约在 8000 上下，对运营报表通常可接受。
- 多页面汇总：把各页面同一天的键 PFMERGE 成整站键，即可得到整站 UV。

> 选择的关键不在命令而在口径：允许近似的报表用 HyperLogLog；财务、风控等要求逐个可查、可对账的场景必须回到 Set 或 Bitmap。先定精度，再定结构。

```bash
PFADD uv:index:20260907 1001
PFADD uv:index:20260907 1002 1003
PFCOUNT uv:index:20260907
PFMERGE uv:index:202609w uv:index:20260901 uv:index:20260907
PFCOUNT uv:index:202609w
PFMERGE uv:site:20260907 uv:index:20260907 uv:pay:20260907
```

```text
127.0.0.1:6379> PFCOUNT uv:index:20260907
(integer) 3
127.0.0.1:6379> PFCOUNT uv:index:202609w
(integer) 3
127.0.0.1:6379> PFMERGE uv:site:20260907 uv:index:20260907 uv:pay:20260907
OK
127.0.0.1:6379> PFCOUNT uv:site:20260907
(integer) 4
```

**速记**：**页面加日期为键**，PFADD 记人、PFCOUNT 出数、PFMERGE 滚周月，内存**恒定 12KB**。



### 选型与适用边界

#### 选型辨析：精确 Set 与近似 HyperLogLog

**选型标准**：要精确结果或需要成员本身用 Set；只要近似个数且内存敏感用 HyperLogLog。

- **Set**：精确，可遍历成员、可判断存在、可求交并差，内存随元素数线性增长。
- **HyperLogLog**：近似，固定约 12KB，不能取成员、不能查单个元素、不能删减。
- **Bitmap**：介于二者之间，对每个对象精确记录一个布尔状态，内存与对象规模成正比但每对象只有 1 位。
- 决策链：需要成员明细选 Set；只需要每个对象的是非标记选 Bitmap；只需要个数且容忍误差选 HyperLogLog。
- 混合方案：日常报表用 HyperLogLog 出数，抽样明细另存 Set，兼顾成本与可解释性。
- 三者的键规模都要提前规划：Set 看元素量级，Bitmap 看 offset 上限，HyperLogLog 基本免规划。
- 迁移路径：从近似起步的项目，先留好精确口径的旁路统计，日后需要时可平滑切换。

> [!TIP]
> **建议内容**：先与需求方确认误差容忍度再选型。若报表误差 1% 以内可接受，HyperLogLog 省下的内存通常以 GB 计；若结论会被用于对账或追责，任何近似结构都不应进入统计链路。

> Bitmap 与 HyperLogLog 并非互斥：日活位图给出精确的去重人数，跨天聚合与超大分母场景用 HyperLogLog 兜底，两套口径互相校验，成本依然远低于全量 Set。

**速记**：对账用 **Set**，报表用 **HyperLogLog**，打标记用 **Bitmap**，先问精度再算内存。



#### 时间复杂度与适用边界

**复杂度结论**：Bitmap 系命令按区间线性计时，HyperLogLog 系命令以常数级为主，三者都不适合承载高频的大区间运算。

- **SETBIT、GETBIT**：O(1)。
- **BITCOUNT、BITPOS**：O(N)，N 是被统计区间的字节数。
- **BITOP**：O(N)，N 是最长输入键的字节数，且在单线程内同步执行。
- **BITFIELD**：O(S)，S 是子命令数量。
- **PFADD**：O(1)；**PFCOUNT** 单键 O(1)、多键 O(N)；**PFMERGE** O(N)。
- 适用边界：高频位运算的键控制在几百万位以内，更大的运算拆批或错峰执行。
- 监控口径：把 BITOP 的返回字节数与 BITCOUNT 的区间大小纳入观察，增长趋势提前预警。
- 三类工具的键都建议纳入统一的大键巡检，超出阈值的键优先拆分。

> 位图键达到几十 MB 量级后，任何一次全键 BITCOUNT 或 BITOP 都可能进入慢查询，应结合慢日志与监控评估（详见第 29 章性能优化与慢查询），必要时把大位图按时间或业务段拆成多个小键。

**速记**：读写 **O(1)**，统计运算 **O(N)**，HyperLogLog 近似常数，大键运算**拆批错峰**。
