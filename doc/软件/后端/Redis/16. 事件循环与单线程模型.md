## 事件循环与单线程模型

**事件循环与单线程模型**：是 Redis 网络服务的执行骨架——服务器用单个主线程运行事件循环，通过 IO 多路复用同时监听成千上万个套接字，把可读可写的文件事件与到期的时间事件在一条时间线上交替处理，从而以单线程支撑高并发。

### Reactor 模式与事件驱动架构

#### Reactor 模式的定义

**Reactor 模式**：是一种基于 IO 多路复用的**事件驱动架构模式**——用一个线程同时监视大量连接上的事件，事件就绪后由分派器交给对应的处理器处理，处理完继续回到等待，如此循环往复。

- 核心角色有四个：**资源句柄**（socket 等可监视的对象）、**同步事件多路分离器**（epoll 等系统调用，阻塞等待事件就绪）、**事件分派器**（把就绪事件按类型分派出去）、**事件处理器**（响应具体事件的回调函数）。
- 工作流程：处理器先向分派器注册关注的事件 → 多路分离器等待事件 → 事件就绪后分派器回调对应处理器 → 处理完毕回到等待。
- 优势：**一个线程服务海量连接**，避免了每连接一线程的内存与上下文切换开销；代价是单个处理器执行过久会拖慢全部事件。
- 采用者：Redis、Nginx、Netty、libevent 等高性能网络组件都基于 Reactor 模式，差别只在封装方式与线程数的取舍。
- 名字拆解：Reactor（反应器）强调**事件就绪才反应**，分离器强调**一次等待收集多路**，分派器强调**按事件类型路由**——三个关键词串起完整闭环。
- 生命周期视角：资源句柄注册进分派器后长期存在，事件反复发生、反复处理，处理器本身无状态，状态由业务对象持有——Redis 的 client 结构正是这样的业务对象。

```text
       ┌────────────── 事件循环 ──────────────┐
       │                                      │
资源句柄（socket 等文件描述符）                   │
       │                                      │
       ▼                                      │
同步事件多路分离器（epoll 等多路复用调用）          │
       │  就绪事件清单                         │
       ▼                                      │
  事件分派器（按事件类型查找处理器）               │
       │                                      │
       ▼                                      │
   事件处理器（执行处理逻辑，可再注册新事件）       │
       │                                      │
       └────────────► 回到等待 ◄───────────────┘
```

> Reactor 与**每请求一线程**的模型是两个极端：后者串行推进每个连接、并发靠堆线程，适合重计算业务；前者串行处理事件、并发靠事件数，适合以 IO 为主、单次处理极轻的场景——Redis 的命令执行恰是典型的轻量内存操作。

> 与 Reactor 相对的概念是 **Proactor 模式**：Reactor 通知“你可以读了”，实际读写仍由处理器自己做；Proactor 则连读写都由内核或线程池代劳、完成后只通知结果。Redis、Nginx、Node.js 均属前者，理解这一归属有助于区分“事件通知”与“异步完成通知”两类模型。

**速记**：**Reactor 等事件、派事件**，单 Reactor 单线程是 Redis 的最简形态。



#### Reactor 在 Redis 中的套用

**Redis 的事件框架**：是 Reactor 模式的单线程实现——ae 事件库充当多路分离器与分派器，主线程里的 aeMain 循环驱动全部事件的收集与处理。

- Redis 把每个客户端连接的 socket 当作资源句柄，启动时对监听端口的 socket 注册可读事件，对每个已建立的客户端 socket 按需注册可读、可写事件。
- ae 模块负责调用底层多路复用接口收集就绪事件，并把事件放入就绪队列等待分派。
- 主循环 aeMain 每一轮做三件事：等待事件、收集事件、分派执行；一轮只处理一批已就绪的事件，事件之间天然串行。
- 事件串行是 Redis **原子性的来源**：任何时刻只有一条命令在执行，不存在两个命令同时修改同一个键的可能。
- 从启动视角串一遍：服务器初始化时创建事件循环、注册监听 socket 的连接应答处理器、注册周期时间事件，随后进入 aeMain——此后一切行为都是这三类初始事件的展开。
- 就绪事件的消费是一轮内清空：本轮收到多少就处理多少，不在循环外堆积，客户端感知到的延迟与单轮事件总量挂钩，而非与总连接数挂钩。
- Redis 只有一个 Reactor、一个主线程，属于 Reactor 变体中最简单的**单 Reactor 单线程**形态；Netty 等框架的**主从 Reactor** 变体用多个线程分担事件处理，而 Redis 直到 6.0 才把多线程引入网络读写环节，且命令执行仍留在主线程。
- 承载这一切的核心数据结构是 aeEventLoop：它保存文件事件表、已就绪事件数组与时间事件链表，主循环的每一轮都在这三块数据上运转。
- 主循环每轮处理事件前还会执行 beforeSleep 钩子，把上一轮留在输出缓冲区里的回复尽量刷出、完成集群心跳等收尾工作，随后才进入等待与收集。
- 之所以不用现成的 libevent 或 libuv：一是 Redis 只需要文件事件与时间事件两类调度，第三方库功能冗余；二是自研才能把等待、分派的每个细节按 Redis 的负载特征定制。

```text
        ┌────────────── 单个主线程 ──────────────┐
        │                                        │
socket 事件（可读/可写）                          │
        │                                        │
        ▼                                        │
IO 多路复用程序（ae 封装 epoll/kqueue/evport/select）│
        │  就绪事件队列                           │
        ▼                                        │
   事件分派器（按事件类型查找对应处理器）            │
        │                                        │
        ▼                                        │
事件处理器：连接应答 / 命令请求 / 命令回复           │
        │                                        │
        └────────────► 回到等待，循环往复 ◄────────┘
```

```text
aeEventLoop 的关键字段（示意）：

events 数组      —— 每个文件描述符注册了什么事件、绑定哪个处理器
fired 数组       —— 本轮多路复用返回的就绪事件清单
timeEvent 链表   —— 全部时间事件（周期执行的 serverCron 在此）
```

> 与 Node.js 用 libuv 承载事件循环不同，Redis 事件库 ae 是**为 Redis 量身自研**的，不依赖 libevent、libev 等第三方库，代码极其精简，这也是它能对事件调度做极致控制的原因；二者更细的异同见本章末尾的对照节。

**速记**：ae 循环**等事件、收事件、派事件**，事件串行即原子。



#### 事件处理器的三种类型

**事件处理器**：是 Redis 预先注册的三类事件处理函数，分别应对客户端通信的三个环节——建立连接、读取请求、写回回复。

- **连接应答处理器**：应对监听 socket 的可读事件，调用 accept 接受新连接，创建客户端对象 client，并为其 socket 注册可读事件，此后该客户端的命令才能被读入。
- **命令请求处理器**：应对客户端 socket 的可读事件，把请求内容读入输入缓冲区，交给协议解析与命令执行逻辑，执行结果写入输出缓冲区并注册可写事件。
- **命令回复处理器**：应对客户端 socket 的可写事件，把输出缓冲区中的回复数据写回 socket，写完后注销可写事件，避免无数据可写时空转。
- 处理器与事件的绑定在注册时确定：同一个 socket 的可读事件与可写事件可以绑定不同处理器，事件就绪时 ae 按绑定关系回调。
- 一次典型交互中三类处理器会依次接力：连接应答创建连接，命令请求读入并执行命令，命令回复写回结果，随后连接保持可读注册等待下一条命令。
- 除 TCP 外，Redis 还支持 Unix 域套接字监听，走独立的 accept 处理函数，但事件框架与上述三类处理器完全一致。
- 与命令表的分工：三类处理器只负责网络收发这一层，具体命令逻辑由命令表在请求处理器内部接管——网络层与命令层解耦，新增命令只需登记命令表，不必触碰事件框架。
- 三类处理器都是可重入的纯逻辑：事件发生多少次就执行多少次，内部不排队；排队的是就绪事件本身，在本轮被逐个消费。

```text
事件类型与处理器的对应（示意）：

监听 socket 可读 ────────► 连接应答处理器
客户端 socket 可读 ──────► 命令请求处理器
客户端 socket 可写 ──────► 命令回复处理器
```

```text
客户端执行 GET foo 的一次完整事件序列：

① 服务器监听 socket 可读 ──► 连接应答处理器（若无连接则无此步）
② 客户端 socket 可读 ─────► 命令请求处理器：读入 *2$3GET$3foo
③ 主线程执行命令，读内存返回 bar
④ 客户端 socket 可写 ─────► 命令回复处理器：写出 $3bar
⑤ 回复写完，注销可写事件，保持可读注册，等待下一条命令
```

> 文件事件是**一次性触发**的：事件发生后，处理器是否继续保持对该事件的关注由逻辑自行决定——可读事件持续注册，可写事件则仅在输出缓冲区有待发送数据时才注册，写完即注销，这个细节是理解事件框架的关键。

**速记**：**应答建连、请求读命令、回复写数据**，三类处理器接力一轮。



### IO 多路复用与 ae 封装层

#### IO 多路复用与 ae 的统一封装

**IO 多路复用**：是指单个线程同时监视多个 socket、任一 socket 就绪即返回就绪事件清单的系统调用家族，Linux 的 epoll、BSD 与 macOS 的 kqueue、Solaris 的 evport、以及各平台通用的 select 都属于此类。

- Redis 自研的 ae 事件库把这四套接口抽象成**统一 API**：aeCreateFileEvent 注册事件、aeDeleteFileEvent 注销事件、aeApiPoll 等待并收集就绪事件，上层逻辑完全不感知底层差异。
- **编译期择优**：编译时按目标平台的宏定义决定把哪个实现编入二进制，优先级为 evport、epoll、kqueue，都没有则退回 select。
- select 作兜底的原因：它有描述符数量上限（通常 1024）且每次调用都要把全部 socket 从用户态拷到内核态再全量扫描，连接数一多性能急剧下降。
- epoll 的优势：事件注册一次、内核持续维护（事件表常驻内核），调用时只返回就绪的 socket，连接数增长时开销近乎平稳，这正是 Redis 单线程能扛十万级连接的系统基础。
- kqueue 与 evport 的能力与 epoll 同级：kqueue 服务 BSD 与 macOS，evport 服务 Solaris 系列，三者都是事件表常驻内核的高效实现，select 是唯一的低效兜底。
- 从演进脉络看：select 用固定大小的位图描述关注集且有数量上限；poll 去掉了上限但仍需全量扫描；epoll 用内核事件表加回调把开销降到只返回就绪集合，现代多路复用由此定型。
- 一个线程的处理能力被“复用”于多条连接之间，这正是多路复用名字的由来——复用的不是连接，是线程。
- ae 使用**水平触发**语义：只要条件满足（如接收缓冲区仍有数据），下次调用仍会报告该事件，处理器即使一次没处理完也不会丢事件。
- 对使用者的意义：同一份 Redis 代码在 Linux 用 epoll、在 macOS 用 kqueue，行为完全一致，跨平台高性能由此而来。

```text
select 与 epoll 的调用模式对比（示意）：

select：每轮把全部关注 fd 拷入内核 ──► 内核线性扫描 ──► 返回全量集合，用户再遍历
epoll ：fd 注册进内核事件表（仅一次）──► 内核只回报就绪清单 ──► 用户直接处理
```

```c
// config.h 中的编译期择优（示意）
#if defined(HAVE_EVPORT)
#include "ae_evport.c"
#elif defined(HAVE_EPOLL)
#include "ae_epoll.c"
#elif defined(HAVE_KQUEUE)
#include "ae_kqueue.c"
#else
#include "ae_select.c"
#endif
```

> [!NOTE]
> **提醒内容**：四种实现的择优发生在**编译期**而非运行期，同一份二进制不会动态切换多路复用后端；Linux 生产环境部署的 Redis 用的必然是 epoll，排查网络问题时可直接按 epoll 的语义理解事件行为。

**速记**：**ae 统一四后端、编译期择优**，evport、epoll、kqueue 优先，select 兜底。



### 文件事件与 RESP 协议

#### 文件事件的定义

**文件事件**：是 Redis 对 socket 就绪状态的抽象——一个 socket 变得可读或可写时，即产生一个文件事件，事件本身不携带数据，只负责唤醒对应处理器。

- **可读事件**：客户端发送了命令数据、监听端口有新连接到达、客户端关闭连接或发生异常。
- **可写事件**：客户端的输出缓冲区中还有待发送数据、且内核 socket 发送缓冲已腾出空间。
- 服务器对每个 socket 的关注集是动态的：读事件常驻，写事件按需挂载，事件与处理器的绑定关系由 aeCreateFileEvent 维护。
- 事件与数据是两层概念：事件只是通知信号，数据的实际读写由处理器从 socket 收发完成，协议解析又发生在数据读入之后。
- 与时间事件对照记忆：文件事件由外部 IO 驱动、数量不可预知，时间事件由时钟驱动、周期固定，两类事件合起来构成主线程的全部工作。
- 水平触发兜底：处理器漏处理一次也不会丢事件，只要就绪条件仍满足，下一轮仍会收到同一事件，连接不会因此永久卡死。

```text
同一个 socket 的关注集随处理进度动态变化（示意）：

空闲等待命令 ──► 关注集 = 可读
回复过大未写完 ─► 关注集 = 可读 + 可写
回复全部写完 ──► 关注集 = 可读（注销可写）
```

> 名字中的**文件**二字容易误解：这里的文件指操作系统把 socket 也视作文件描述符，与磁盘文件无关；Redis 中所有经由文件描述符产生的就绪通知统一归入文件事件。
> 辨析：可读事件不等于“一定有完整命令”——socket 可读只保证接收缓冲区里有字节，命令可能只到一半；完整性由 RESP 解析器判断，这正是输入缓冲区存在的意义。

**速记**：**socket 可读可写即文件事件**，读事件常驻、写事件按需。



#### 命令请求与回复的处理流程

**命令处理全流程**：从客户端发送命令到收到回复，每一步都由主线程在事件循环内完成，一次完整往返对应多个事件、多个处理器接力。

```text
① 连接应答处理器 accept 新连接，创建 client 结构并注册可读事件
② 命令请求处理器把请求文本读入客户端输入缓冲区
③ 解析 RESP 协议，取出命令名与全部参数
④ 查命令表、做权限与参数校验，执行命令（读写内存数据结构）
⑤ 回复写入客户端输出缓冲区，并注册可写事件
⑥ 命令回复处理器把输出缓冲区数据写回 socket，写完注销可写事件
```

- 流程中的①③发生在不同轮次的事件循环里，各事件之间穿插着其他客户端的事件，但每一步都在主线程内串行完成。
- 步骤④执行命令时直接读写内存数据结构，耗时通常在微秒级，这正是单线程模型能够成立的根本前提。
- 输入缓冲区承接不完整请求：客户端一次发送可能被网络拆成多段，读入后若协议尚不完整，数据留在输入缓冲区，等下次可读事件继续拼接，拼齐才执行。
- 输入缓冲区有大小上限，超过阈值会主动断开该客户端，防止畸形客户端无限占内存；协议解析器是逐字节状态机，对粘包、半包天然免疫。
- 步骤④的校验清单：命令是否存在、参数个数是否匹配、客户端是否通过鉴权、内存是否超限、当前是否处于事务或 Lua 上下文——任何一项不过，命令都不会真正执行。
- 若回复过大无法一次写完，输出缓冲区会保留剩余数据，写事件保持注册，下一轮循环继续发送；输出缓冲区同样设有硬性上限，超限即断开连接。
- 每个连接的全部状态都封装在 client 结构中：输入缓冲区、已解析的参数、目标命令、输出缓冲区、注册的事件，事件处理器只是围绕 client 结构的几段逻辑。

```text
client 结构的关键字段（示意）：

querybuf   —— 输入缓冲区，暂存客户端发来的原始字节
argc/argv  —— 解析出的参数个数与参数数组
cmd        —— 解析命中的命令实现
buf        —— 输出缓冲区，暂存待写回的回复
db         —— 该客户端当前选中的数据库
```

> 辨析：**一次命令往返 = 多个事件接力**——Redis 从不等待单个请求走完全程再服务下一个客户端，而是在事件粒度上交错服务所有客户端；也正因如此，任何一个事件的处理耗时都会顺延其他所有客户端的事件。

**速记**：**建连、读入、解析、执行、写回**，五步全在主线程。



#### RESP 协议与 RESP2、RESP3

**RESP 协议**：全称 REdis Serialization Protocol，是 Redis 客户端与服务器之间的通信协议，二进制安全、以回车换行定界，人类可读且解析极快。

- **RESP2** 定义五种类型：简单字符串以加号开头、错误以减号开头、整数以冒号开头、批量字符串以美元符开头、数组以星号开头；客户端发命令、服务器回结果都遵循这套编码。
- **RESP3** 自 Redis 6.0 起可选启用，新增映射、集合、布尔、双精度浮点、空值、推送等类型；推送类型是客户端缓存（client-side caching）失效通知的载体。
- 协议版本由客户端发送 HELLO 3 切换，RESP2 始终是默认版本，旧客户端不受任何影响。
- 解析与执行都在主线程完成，协议简单是 Redis 单线程能扛住高吞吐的重要配合条件——解析开销越小，留给命令执行的时间越多。
- 二进制安全的含义：批量字符串的长度由头部声明，正文中出现任何字节（包括换行）都不影响解析，因此 Redis 的值可以存任意二进制数据。

```text
# 客户端发送 SET foo bar 的 RESP2 编码（\r\n 为行结束符）
*3\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n

# 服务器回复
+OK\r\n

# 各类型示例：简单字符串、错误、整数、批量字符串、数组
+PONG\r\n
-ERR unknown command\r\n
:1000\r\n
$5\r\nvalue\r\n
*2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n
```

```text
# RESP3 新增类型示例（\r\n 为行结束符）
%2\r\n$1\r\na\r\n:1\r\n   —— 映射：键 a 对应整数 1
~3\r\n$1\r\nx\r\n$1\r\ny\r\n$1\r\nz\r\n   —— 集合
#t\r\n   —— 布尔真
,3.14\r\n   —— 双精度浮点
_\r\n   —— 空值
>1\r\n$10\r\ninvalidate\r\n   —— 推送（客户端缓存失效通知）
```

```bash
# 用 HELLO 命令切换到 RESP3，服务器以映射类型返回服务器信息
HELLO 3
```

> [!TIP]
> **建议内容**：调试协议问题时可用 nc 直连 Redis 端口，把上述 RESP 编码原样粘进去即可看到服务器回复；理解 RESP 的行定界与类型前缀，是排查客户端兼容性与抓包分析的第一步，协议细节可配合第 28 章的调试工具实践。

**速记**：**RESP2 五类型、RESP3 加推送**，HELLO 3 才切换，默认仍是 RESP2。



### 时间事件与事件调度

#### 时间事件与 serverCron 定时任务

**时间事件**：是 Redis 以指定周期触发的事件，与 socket 无关，载体是服务器内置的 serverCron 函数——它像心跳一样周期性驱动服务器的后台维护工作。

- 时间事件分两类：**定时事件**到点执行一次，**周期事件**按固定周期反复执行；Redis 只使用周期事件。
- 执行频率由配置项 hz 决定：默认值为 10，即每秒触发 10 次、约每 100 毫秒一次，可配置范围为 1 到 500；开启 dynamic-hz 后实际频率会在基准值附近自适应微调，以削平多个实例同频共振的毛刺。
- dynamic-hz 的用意：让实际执行频率在配置的基准值附近随机浮动，使多个周期任务错峰执行，避免集中触发造成周期性延迟毛刺。
- serverCron 承担的任务清单：过期键的主动删除（详见第 14 章）、字典渐进式 rehash 的主动推进（详见第 11 章）、统计信息与内存水位的更新、内存淘汰的触发（详见第 15 章）、RDB 保存条件与 AOF 重写条件的检查（详见第 17、18 章）、主从复制的心跳与超时判断（详见第 20 章）、客户端超时与缓冲区检查、集群 gossip 任务的驱动（详见第 22 章）。
- 时间事件同样在主线程执行，与文件事件共享同一条时间线，不存在专门的时间事件线程。
- serverCron 单次执行的工作量被刻意切碎：过期删除每次只扫描有限的键、rehash 每次只推进有限的桶，用次数换时长，保证单轮不超时。

```text
def serverCron:                        # 周期执行，约每 100 毫秒一次
    更新时间缓存与统计信息               # 内存水位、连接数、命中统计
    触发内存淘汰（必要时）               # 详见第 15 章
    推进各数据库的渐进式 rehash          # 详见第 11 章
    分批删除过期键                      # 详见第 14 章
    检查 RDB 保存条件与 AOF 重写条件     # 详见第 17、18 章
    清理超时客户端、驱动主从心跳         # 详见第 20 章
```

> hz 调大意味着过期键清理、统计刷新更及时，但每秒空耗的 CPU 也更多；一般业务默认 10 即可，键规模巨大且过期密集的场景才考虑调大，hz 与过期删除策略的配合详见第 14 章。

**速记**：**serverCron 是每 100 毫秒一次的心跳**，过期、rehash、统计、持久化检查全在其中。



#### 文件事件与时间事件的调度关系

**调度关系**：文件事件与时间事件在单线程的事件循环中**交替执行、互不并发**——每一轮先处理就绪的文件事件，随后执行到期的时间事件，时间事件绝不抢占文件事件。

- 主循环 aeMain 的结构：先计算距离最近一次到期时间事件还差多久，以此作为本次多路复用等待的超时上限；然后等待并收集就绪的文件事件并逐一分派；最后执行所有已到期的时间事件。
- 超时上限的设定保证了时间事件**不会因等待文件事件而无限顺延**：若最近的时间事件 50 毫秒后到期，本轮等待最多阻塞 50 毫秒。
- 时间事件**不抢占**：若某轮文件事件处理耗时过长，到点的时间事件只能排队，等这轮文件事件全部处理完才执行，因此时间事件的实际触发时刻是“约每 100 毫秒”而非精确的 100 毫秒。
- 事件之间只有先后、没有并发，这是 Redis 免锁、命令原子执行的结构性保证。

```text
def aeMain:                            # 主循环，单线程
    while not stop:
        timeout = 距离最近到期时间事件的时长   # 作为等待上限
        events = aeApiPoll(timeout)          # 等待并收集文件事件
        for e in events: 分派给事件处理器      # 先处理文件事件
        执行所有已到期的时间事件               # 后处理时间事件
```

- 补充两个工程事实：一是主进程内除主线程外还有少量后台线程，但它们只处理关闭文件、刷盘、释放内存等杂务，不参与事件循环；二是主线程在多路复用调用中阻塞等待时，若一直无事件且无时间事件临近，线程会休眠让出 CPU，有事件到达即被唤醒。
- 从时间片视角看，单线程主循环把 CPU 时间切成了无数个小片：每个小片处理一个事件或一批事件，客户端感知到的是并发，实际发生的是极快轮转的串行。

- 事件循环没有优先级：时间事件不比文件事件更高级，唯一的时间保障来自等待上限的动态计算，让到期时刻尽量不被拖延。

```text
一轮事件循环的时间线（示意）：

t0 ──► 计算最近时间事件的剩余时长（如 50 毫秒）
t1 ──► aeApiPoll 最多等这么久（或提前被文件事件唤醒）
t2 ──► 逐个处理就绪的文件事件
t3 ──► 执行到期的时间事件（serverCron）
t4 ──► 回到 t0，开始下一轮
```

> [!IMPORTANT]
> **重要内容**：牢记“**时间事件绝不抢占文件事件**”这一调度铁律——由此可推出两个结论：一是 serverCron 的执行时刻会随负载漂移，不能当作精确定时器；二是一轮事件若被慢命令拖长，过期删除、心跳等后台维护全部顺延，慢命令的危害因此是全局性的。

**速记**：**先文件事件、后时间事件、绝不抢占**，等待上限由最近的到期时间倒推。



### 单线程模型的快与慢

#### 单线程为什么快：四要素

**单线程高性能**：Redis 的快并非来自多线程，而是来自四要素的组合——纯内存操作、高效数据结构、单线程免锁免切换、IO 多路复用，四者缺一不可。⚡

- **纯内存操作**：数据全部存于内存，读写延迟比磁盘低若干个数量级，命令执行本身微秒级完成，这是高性能的第一来源（内存管理与淘汰详见第 15 章）。
- **高效数据结构**：SDS、字典、跳表、压缩列表等专为内存设计的结构，让每个命令的计算量尽可能小（分别详见第 10、11、12 章）。
- **单线程免锁免切换**：没有多线程竞争就没有锁开销，没有线程切换就没有上下文保存与缓存失效，CPU 时间全部花在正事上。
- **IO 多路复用**：单线程同时监视海量连接，等待事件时让出 CPU，就绪时集中处理，并发能力不依赖线程数。
- 四要素共同支撑起单实例十万级 QPS 的基准能力：内存决定单次操作的延迟下限，数据结构决定每次操作的计算量，免锁免切换决定 CPU 的有效利用率，多路复用决定并发连接的规模上限。
- 对照记忆：数据库多线程模型的 CPU 大量耗在锁等待与线程切换上，Redis 把这两项开销直接归零，把省下的时间全部投给内存读写。
- 数量级参照：内存随机访问在百纳秒级、同机房网络往返在零点几毫秒级、机械磁盘寻道在毫秒级——Redis 的一切设计都在保证命令执行不离开内存量级。
- 快是四要素的合力结果，不是单线程本身的功劳：单线程只是免锁免切换这一项的载体，没有内存与数据结构兜底，单线程反而会成为瓶颈。

> 四要素是**乘法关系而非加法关系**：任一要素坍塌，单线程模型的整体性能即坍塌——内存不够用会引发淘汰与换页，数据结构选错会让单条命令变慢，而任何一条慢命令则会同时废掉“免切换”与“高并发”两项优势，这也是下一考点展开的主题。

**速记**：**内存、数据结构、免锁、多路复用**四要素相乘，缺一即塌。



#### 单线程的代价：慢命令阻塞一切

**单线程的代价**：所有命令串行执行意味着一条慢命令会阻塞其后一切事件——其他客户端的命令、心跳、过期删除全部排队等待，慢命令是单线程模型唯一的软肋。

```text
正常时序：  命令A ─ 命令B ─ 命令C ─ 心跳/过期维护 ─ 命令D
出现慢命令：命令A ─ KEYS（阻塞 2 秒）────────────────► 命令B、C、心跳全部顺延
```

- 典型慢命令：KEYS 遍历全部键空间、对大 hash 的 HGETALL、对大集合的 SMEMBERS、一次返回百万级的 LRANGE。
- 阻塞型管理命令：不带 ASYNC 的 FLUSHALL 与 FLUSHDB 同步清空全部键空间，键多时足以卡死实例数秒。
- 误用型阻塞：运行 O(N) 的 Lua 脚本、对百万级成员执行 ZADD、无限制的 SORT，效果与慢命令等价。
- 危害是全局性的：阻塞期间所有客户端超时堆积，恢复瞬间还可能出现连接风暴与重试放大。
- 识别手段：SLOWLOG GET 看慢查询日志、INFO commandstats 看命令耗时分布、LATENCY 系列命令看延迟毛刺，三者配合即可定位阻塞源头（详见第 29 章）。
- 工程对策：生产环境禁用 KEYS 改用 SCAN 渐进遍历，大对象查询改用 HSCAN、SSCAN、ZSCAN 分批读取，清库一律带 ASYNC；排查手段与性能调优详见第 29 章，命令行工具详见第 28 章。

```bash
# 高危写法与替代写法对照
KEYS *                      # 高危：全键空间扫描
SCAN 0 COUNT 100            # 替代：游标分批遍历

HGETALL bigHash             # 高危：一次拉取大哈希全部字段
HSCAN bigHash 0 COUNT 100   # 替代：分批读取

DEL bigList                 # 高危：百万级元素的同步释放
UNLINK bigList              # 替代：摘引用加后台释放
```

```bash
# 用 SCAN 渐进遍历替代 KEYS，每次只扫一小批，光标为 0 表示新一轮
SCAN 0 COUNT 100
# 对大 hash 用 HSCAN 分批读取，避免 HGETALL 一次拉全量
HSCAN bigHash 0 COUNT 100
# 清库一律带 ASYNC，内存释放转交后台线程
FLUSHDB ASYNC
```

> [!CAUTION]
> **注意内容**：**KEYS、FLUSHALL、FLUSHDB（不带 ASYNC）属于生产环境高危命令**——单线程下它们阻塞的是整个实例而非单个连接，千万级键库执行 KEYS 可造成秒级到分钟级的服务停摆；应在配置层用 rename-command 重命名或在代理层禁用，配合 big key 治理（详见第 29 章）从源头规避。

**速记**：**一条慢命令阻塞一切**，KEYS 换 SCAN、DEL 换 UNLINK、清库带 ASYNC。



### Redis 6.0 的多线程 IO

#### 多线程 IO 的引入与原子性边界

**多线程 IO**：是 Redis 6.0 引入的网络读写并行化机制——命令的执行仍然全部在主线程串行完成，只有 socket 的读取与回复写入可以交给多个 IO 线程并行处理。

- 动机：对大流量实例，网络数据的读写与协议解析成为瓶颈，纯内存命令执行反而不是；多线程把这部分可并行的搬运工作摊给多个线程。
- 工作方式：主线程把待处理客户端分派给各 IO 线程并行执行读取（或写入），随后主线程等待全部 IO 线程完成，再串行执行命令、生成回复；下一轮再由 IO 线程并行写回。
- **原子性边界**：命令执行阶段永远单线程，因此多线程 IO 不改变任何命令语义，事务、Lua、单命令的原子性全部保持，客户端无感知。
- 边界归纳：并行只发生在“数据进网卡前、数据出网卡后”的搬运环节，键空间的修改永远发生在主线程这一条线上。

```text
一轮事件循环（开启多线程 IO 后）：

主线程：分派待读客户端给 IO 线程 ──► 等待全部完成 ──► 串行执行命令并生成回复
IO 线程：并行读取各自客户端的请求数据                          │
主线程：分派待写客户端给 IO 线程 ◄──────────────────────────┘
IO 线程：并行写出各自客户端的回复数据
```

- 这一设计回答了一个高频疑问：多线程 IO 会不会带来并发安全问题——不会，因为竞态只会发生在写内存的环节，而写内存的命令执行从未离开主线程。
- 协调方式上，主线程分派任务后原地等待所有 IO 线程干完再继续，属于屏障式同步；IO 线程之间各管各的客户端，互不共享待处理数据。
- 从演进看，这是对单线程模型的一次有限度扩展：只并行化与网卡打交道的搬运环节，内存数据结构的操作依旧独占，是性能与正确性之间的折中。
- 收益主要出现在**大回复、大流量**场景：大量小请求或命令本身很重的实例，瓶颈不在网络搬运，多线程收益有限。

**速记**：**搬运并行、执行串行**，原子性分毫未动。



#### io-threads 配置与默认关闭的原因

**io-threads 配置**：控制参与网络读写的 IO 线程数量，默认值为 1，即完全关闭多线程 IO，回到传统单线程模式。

- io-threads 设为 1 表示只有主线程自己处理网络 IO；设为 N 表示启用 N 个线程（含主线程）分担网络读写。
- io-threads-do-reads 默认为 no：即默认只有回复写出用多线程，请求读取仍由主线程完成；官方测试表明多数场景读多线程收益不明显，写出并行化收益更大。
- 官方建议：至少 4 核以上且实测网络读写确为瓶颈的实例才开启，值设 2 到 4 即可，盲目调大反而增加线程协调开销。
- 官方文档同时提醒：开启前应先用基准测试确认瓶颈确实在网络 IO，而不是命令执行或内存。
- 默认关闭的三条原因：其一，多数实例瓶颈在内存与命令而非网卡，开了没收益；其二，多线程带来线程协调与等待开销，流量小时得不偿失；其三，单线程模型历经多年验证，行为可预期、问题易排查，没必要为少数大流量实例让全部用户承担复杂度。

```bash
# redis.conf 中的多线程 IO 配置
io-threads 1                # 参与网络 IO 的线程数，默认 1 即关闭
io-threads-do-reads no      # 请求读取是否也用多线程，默认 no
```

> [!WARNING]
> **警告内容**：**不要盲目开启 io-threads**——默认关闭的原因在于多数实例的瓶颈根本不在网络读写，小流量或 CPU 核数不足的实例开启后，线程间协调与自旋等待反而拉低性能；开启前必须以生产同规模的流量做基准测试对比，并以实测吞吐为准，而非听信“多线程一定更快”。

**速记**：**io-threads 默认 1 即关闭**，四核以上且实测瓶颈在网络才开 2 到 4。



### 后台线程与异步删除

#### 后台线程承担的工作

**后台线程**：是 Redis 主线程之外专职处理阻塞式杂务的线程组，由 bio 模块管理，让耗时的系统调用不占用主循环。

- **关闭文件线程**：负责关闭文件描述符——close 系统调用在特定条件下可能阻塞，交由后台线程执行。
- **AOF 刷盘线程**：负责 AOF 文件的 fsync——把内核页缓存强制刷入磁盘是毫秒级甚至更久的阻塞操作，详见第 18 章。
- **惰性释放线程**：负责大对象内存的异步释放，即下一考点展开的 lazyfree 机制。
- bio 线程在服务器启动时创建、数量固定且极小，与客户端连接数无关——无论多少连接涌入，后台线程始终只有这几条。
- bio 的任务队列是单向的：主线程只投递、后台线程按序消费，通过锁与条件变量同步；后台任务异常不影响主循环，只留日志可查。
- 此外，RDB 持久化与 AOF 重写通过 fork 出**子进程**完成（子进程不是线程，与 bio 线程是两回事），主线程仅负责 fork 与结果检查，详见第 17、18 章。

```text
主线程 ──投递任务──► bio 任务队列 ──► 关闭文件线程   （close 文件描述符）
                        │
                        ├──► AOF 刷盘线程     （fsync AOF 文件）
                        │
                        └──► 惰性释放线程     （异步释放大对象内存）
```

> 三条 bio 线程与主线程通过任务队列协作：主线程只把任务投递进队列即返回，真正干活的是后台线程——这套“投递即返回”的模式，正是 Redis 能在单线程主循环里不碰任何可能阻塞的系统调用的关键。

```text
谁在干活（示意）：

主线程   ── 事件循环、命令执行、键空间修改（永远只有它）
bio 线程 ── close 文件、AOF fsync、大内存释放（阻塞性杂务）
子进程   ── RDB 生成、AOF 重写（fork 出来的重量级任务）
```

**速记**：**close、fsync、释放内存**三类杂务归 bio，主线程只投递。



#### 异步删除命令族与 lazyfree 配置

**异步删除命令族**：以 UNLINK 与 FLUSHDB、FLUSHALL 的 ASYNC 选项为代表，把键空间摘除与内存释放拆成两步——摘除引用在主线程瞬时完成，真正释放内存交给后台线程，从而消除大 key 删除的阻塞。

- **UNLINK**：DEL 的异步版。主线程先从键空间字典摘除该键（引用层面近似 O(1)），再评估释放代价——对元素数量超过 64 的集合类对象（list、set、hash、zset），把实际释放投递给惰性释放线程；对小对象则直接同步释放，因为异步调度的开销反而更大。
- **FLUSHDB ASYNC 与 FLUSHALL ASYNC**：主线程只清空键空间字典并把待释放的键登记到后台队列，海量内存的回收全部由后台线程逐步完成，主循环几乎瞬时返回。
- **lazyfree 配置项**：lazyfree-lazy-eviction 开启后内存淘汰时也异步释放；lazyfree-lazy-expire 开启后过期删除时异步释放；lazyfree-lazy-server-del 开启后命令内部隐式删键（如 RENAME 覆盖旧键）时异步释放。三者默认均为 no，即默认同步释放。
- 延伸配置：lazyfree-lazy-user-del 使客户端发 DEL 时自动按 UNLINK 语义执行；lazyfree-lazy-user-flush 使 FLUSHALL、FLUSHDB 默认走异步；副本清库配置 replica-lazy-flush 默认已为 yes。
- 判断口令：凡涉及**释放大量内存**的动作，主线程只动引用、后台线程动内存；凡是小对象，同步释放更快，系统会自动择优，无需人工干预。

```text
FLUSHDB ASYNC 的流程（示意）：

主线程：把键空间字典清空，将摘除的键值对象登记进惰性释放队列 ──► 命令立即返回 OK
后台线程：逐个取出登记的对象，慢慢完成内存释放
```

```text
UNLINK bigkey 的两步走（示意）：

第一步（主线程）：从键空间字典摘除 bigkey 的引用，命令立即返回 1
第二步（评估）：集合类对象且元素数大于 64 ──► 投递给惰性释放线程异步 free
                 其余小对象 ────────────────► 主线程顺手同步 free
```

```bash
# 异步删除与异步清库
UNLINK bigkey
FLUSHDB ASYNC
FLUSHALL ASYNC

# redis.conf 中的 lazyfree 配置（默认均为 no）
lazyfree-lazy-eviction no
lazyfree-lazy-expire no
lazyfree-lazy-server-del no
```

> 经典事故场景：业务高峰期用 DEL 删除一个含数百万成员的 hash，主线程同步释放内存耗时数秒，期间全部请求排队；改用 UNLINK 后，同样的删除在主线程只花微秒级时间，内存释放由后台线程慢慢完成。

> [!TIP]
> **建议内容**：**生产环境删除不确定大小的键时，一律用 UNLINK 替代 DEL**，清库一律带 ASYNC——二者语义与同步版完全一致、只是释放时机不同，却能在不改变业务行为的前提下规避大 key 阻塞；配合开启 lazyfree-lazy-expire 可进一步消除过期键集中删除时的抖动，big key 的发现与治理详见第 29 章。

**速记**：**UNLINK 摘引用、后台释内存**，三个 lazyfree-lazy 配置覆盖淘汰、过期、隐式删。



### 与 Node.js 事件循环的对照

#### 与 Node.js 事件循环的异同对照

**异同总览**：Redis 与 Node.js 的事件循环同源而不同路——都是单线程、事件驱动、以 IO 多路复用为底座的循环结构，但二者的调度对象与保证完全不同。

- 相同点：主线程运行事件循环；底层同为多路复用（Redis 用自研 ae 封装 epoll、kqueue、evport、select，Node 用 libuv 封装 epoll、kqueue 等）；都以回调或处理器响应就绪事件；都强调绝不能阻塞主线程。
- 不同点一：**原子性保证**。Redis 的事件处理器是内置的命令执行逻辑，事件之间无任何用户代码插队，单条命令天然原子；Node 的回调之间可以穿插任意 JS 逻辑，无原子性可言，需要原子操作时反而要借助 Redis（详见第 27 章分布式锁）。
- 不同点二：**微任务与阶段**。Node 有六阶段循环与微任务优先级（Promise、nextTick 在宏任务后清空），调度精细；Redis 只有文件事件与时间事件两类，无微任务概念，也没有阶段间优先级插队。
- 不同点三：**卸载策略**。Node 把文件 IO、DNS 等交给 libuv 线程池；Redis 把 close、fsync、大内存释放交给 bio 后台线程，二者殊途同归——把阻塞从主循环挪走。
- 不同点四：**扩展路径**。Redis 6.0 用多线程 IO 并行化网络收发；Node 靠 cluster 多进程横向扩展，主线程始终单线程。
- 对照记忆框架：问“谁在事件循环里跑”——Node 跑的是**用户回调**，Redis 跑的是**内置命令执行**；问“阻塞了怎么办”——Node 靠异步化业务代码，Redis 靠避开慢命令、启用 UNLINK 与 lazyfree。

```text
事件循环对照（示意）：

Redis：aeMain ──► 文件事件（命令收发）──► 命令执行（原子）──► 时间事件（serverCron）
Node ：libuv ──► 六阶段（timers/poll/check 等）──► 用户回调 ──► 微任务清空（Promise/nextTick）
```

> 常见误区是把二者混为一谈：Node 的事件循环在**应用代码**层面调度用户回调，业务代码自身的耗时直接决定循环快慢；Redis 的事件循环在**数据库内核**层面调度命令处理，用户能影响的只有发什么命令——所以 Node 的优化方向是异步化业务代码，Redis 的优化方向是避开慢命令与 big key，详见第 29 章。

**速记**：同为**单线程事件驱动加多路复用**，Redis 命令原子、Node 回调灵活；Redis 卸载给 bio 线程，Node 卸载给 libuv 线程池。
