## 常见问题与踩坑清单

### 反向代理类

#### proxy_pass 路径拼接错误

**现象**：反代后的接口返回 404，或后端收到的路径多了一段、少了一段；同一份业务配置换个 proxy_pass 写法就时好时坏，问题几乎全部出在路径拼接上。

**原因**：proxy_pass 是否携带 URI 决定了拼接规则，这是 Nginx 反代中最容易误读的一条。

- **不带 URI**（如 http://backend）：Nginx 把**原始请求 URI 原样转发**给后端。
- **带 URI**（末尾出现斜杠或路径，如 http://backend/）：Nginx 用 proxy_pass 的 URI **替换掉请求中匹配 location 的那一段**，再把剩余部分拼上去。

以 location /api/ 为例，请求 /api/user/list 的实际转发结果，四组对照如下：

- **proxy_pass http://backend**：转发 **/api/user/list**，原始路径完整保留。
- **proxy_pass http://backend/**：转发 **/user/list**，匹配段 /api/ 被去掉。
- **proxy_pass http://backend/v1**：转发 **/v1user/list**，替换段 /v1 与剩余的 user/list 直接相连，缺少斜杠，后端大概率 404。
- **proxy_pass http://backend/v1/**：转发 **/v1/user/list**，拼接正确。

```nginx
# 错误示例：proxy_pass 的替换路径少写了一个斜杠
location /api/ {
    proxy_pass http://backend/v1;    # /api/user/list 被拼成 /v1user/list，后端 404
}
```

```nginx
# 修复：替换路径以斜杠结尾，保证替换段与剩余段之间有分隔
location /api/ {
    proxy_pass http://backend/v1/;   # /api/user/list 被转发为 /v1/user/list
}
```

**解法**：先确定口径再选写法——整段透传就用不带 URI 的形式；要做前缀改写，就把替换路径写成带末尾斜杠的完整前缀，并用 curl 实测验证。

```bash
# 验证反代后的真实路径，结合后端访问日志即可确认拼接结果
curl -s http://127.0.0.1/api/user/list
```

> 记忆口诀：**proxy_pass 只看末尾带不带路径**。不带，原样透传；带了，做替换——把替换段与剩余段沿字符串肉眼拼一遍，就能预判最终路径。

> [!IMPORTANT]
> **重要内容**：是否携带 URI 的判定标准是末尾是否出现斜杠或路径，与域名写法无关；http://backend 与 http://backend/ 仅差一个斜杠，行为却完全不同，后者属于带 URI 的写法。



#### 反向代理后取不到真实客户端 IP

**现象**：后端日志里记录的客户端 IP 全是代理的地址（如 127.0.0.1 或内网网关），风控、限流、统计全部失真；偶尔还会取到陌生的公网 IP，疑似头被伪造。

**原因**：反向代理建立的是**新 TCP 连接**，后端看到的连接对端永远是 Nginx；真实 IP 只能靠应用层请求头传递。Nginx 不传、后端无条件相信、或多层代理未逐层追加，都会导致取错。

- **Nginx 未设置转发头**：后端无从得知真实 IP，只能记录代理 IP。
- **头被伪造**：任何客户端都能自带 X-Forwarded-For 头，后端若直接取链条第一个值，就会被恶意注入假 IP。
- **多层代理**：每一层只看得见上一跳，逐层追加才能保留完整链路。

```nginx
# 面向用户的入口层：把连接级变量写进应用层头再转发
location /api/ {
    proxy_set_header Host            $host;
    proxy_set_header X-Real-IP       $remote_addr;                # 当前连接的对端 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 在原有链路后追加
    proxy_pass http://backend;
}
```

**解法**：入口层负责写入，中间层与后端负责只信可信来源。

```nginx
# 中间层或后端侧的 Nginx：声明信任的上跳代理网段，再从头里还原真实 IP
set_real_ip_from 10.0.0.0/8;     # 只信任内网代理段
real_ip_header X-Forwarded-For;
real_ip_recursive on;            # 从右往左剔除可信地址，取第一个不可信的
```

> 关键结论：**真实 IP 以从右往左遇到的第一个不可信地址为准**，而不是链条的第一个值。链头由客户端任意书写，只有从右往左逐个剔除可信代理，剩下的才是用户的真实地址。

> [!WARNING]
> **警告内容**：后端应用绝不能无条件信任 X-Forwarded-For 的第一个值：直连场景下攻击者可伪造该头冒充任意 IP。正确做法是只在可信代理网段内传递，并在最后一跳用 realip 模块还原，或让应用仅信任入口层的 X-Real-IP。



#### 跨域响应头重复

**现象**：浏览器控制台报 Access-Control-Allow-Origin 存在多个值（如 *, *），或报 The Access-Control-Allow-Origin header contains multiple values，跨域请求全部失败；但单独访问后端、单独看 Nginx 配置，都好像各自没问题。

**原因**：**Nginx 与后端应用都添加了一遍 CORS 头**，响应经过反代后同名头出现两次。CORS 规范要求该头的值唯一，出现重复即判定失败。

```nginx
# 错误示例：后端已经输出 CORS 头，Nginx 又追加一遍
location /api/ {
    add_header Access-Control-Allow-Origin * always;   # 与后端重复
    proxy_pass http://backend;
}
```

**解法**：全链路只在一处添加，二选一并写进团队约定。

```nginx
# 方案一：统一由 Nginx 添加，后端不再输出 CORS 头
location /api/ {
    add_header Access-Control-Allow-Origin  https://www.example.com always;
    add_header Access-Control-Allow-Methods "GET, POST, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;
    proxy_pass http://backend;
}
```

```nginx
# 方案二：CORS 交给后端统一处理，Nginx 只做透传
location /api/ {
    proxy_pass http://backend;   # 不出现任何 add_header
}
```

> add_header 默认只对 200、201、204、206、301、302、303、304、307、308 这些成功与重定向状态码生效，404、500 等错误响应不会携带；跨域的错误响应同样需要这些头，因此必须写 always 参数。

> [!TIP]
> **建议内容**：前后端分属不同职能时，CORS 建议收敛到网关层由 Nginx 统一管理，OPTIONS 预检请求也在网关层一并处理；若后端框架已有成熟的 CORS 中间件，则保留后端方案，Nginx 侧彻底不碰。



### 静态资源类

#### root 与 alias 误用导致文件找不到

**现象**：文件明明放在磁盘上，访问却 404，或拼出诡异路径（如请求 /static/app.css 却找 /data/webapp.css）；把 root 换成 alias（或反过来）就碰巧修好，但不明白原理，下次接着犯。

**原因**：**root** 与 **alias** 的路径拼接规则不同，混用必然出错。

- **root**：把**完整 URI** 拼接在 root 值之后，磁盘路径 = root + 完整 URI。
- **alias**：用 alias 的值**替换** location 匹配的那一段，磁盘路径 = alias + location 之后的剩余 URI。

```nginx
# root：请求 /static/app.css 对应磁盘上的 /data/web/static/app.css
location /static/ {
    root /data/web;    # 拼接：/data/web + /static/app.css
}
```

```nginx
# alias：请求 /static/app.css 对应磁盘上的 /data/web/app.css
location /static/ {
    alias /data/web/;  # 替换：/data/web/ + app.css
}
```

```nginx
# 错误示例：alias 末尾漏了斜杠
location /static/ {
    alias /data/web;   # /static/app.css 被拼成 /data/web + app.css = /data/webapp.css
}
```

```nginx
# 修复：location 与 alias 的末尾斜杠成对出现
location /static/ {
    alias /data/web/;
}
```

**解法**：两步定位。第一步选对指令：URI 路径与磁盘目录**同名映射**用 root，**改名映射**（URL 前缀与磁盘目录名不同）必须用 alias；第二步核对斜杠：location 与 alias 的末尾斜杠同时带或同时不带，绝不能一有一无。

> 经验法则：用 root 时只关心父目录写对，不受斜杠影响；用 alias 时先在心里把替换演算走一遍——alias 值 + location 之后的剩余 URI，结果应与磁盘真实路径一致。

> [!NOTE]
> **提醒内容**：root 还可写在 server 块作为整站默认根目录，location 内再按需覆盖；alias 只能出现在 location 中。二者语义不同，不能因为都能让 404 消失就互换。



#### 静态文件访问报 403 权限问题

**现象**：访问静态资源返回 403 Forbidden，错误日志出现 Permission denied；文件确实存在，用 root 账户启动 Nginx 又好了，但这样做的风险极高。

**原因**：真正读文件的是 **worker 进程**，其运行用户由 user 指令决定（默认为编译时的 nobody 或 nginx），403 的本质是**这个用户对路径没有读取权限**。

- **文件无读权限**：worker 用户不属于文件属主或属组，其他用户位又不可读。
- **目录缺执行位**：进入任何目录都需要 x（执行）权限，路径上缺任何一级都会 403。
- **SELinux 拦截**：传统权限位正常，但 SELinux 处于 Enforcing，策略不允许 nginx 读非标准目录。

```nginx
# 声明 worker 运行用户（只能出现在 main 上下文，即主配置顶部）
user  www-data;
```

```bash
# 逐级检查路径权限：worker 用户需对每一级目录有 x，对目标文件有 r
namei -l /data/web/static/app.css

# 补齐属主与权限：目录 755、文件 644 是静态站点的常规配置
chown -R www-data:www-data /data/web
chmod -R u=rwX,g=rX,o=rX /data/web
```

**解法**：按现象分派。权限位问题用 namei -l 逐级修复属主与读写执行位；SELinux 问题为自定义目录登记正确的安全上下文后恢复 Enforcing，不要长期关闭 SELinux 护航。

```bash
# SELinux 环境的排查与修复：先确认状态，再登记安全上下文
getenforce
ausearch -m avc -ts recent
semanage fcontext -a -t httpd_sys_content_t "/data/web(/.*)?"
restorecon -Rv /data/web
```

> [!NOTE]
> **提醒内容**：排查 403 应紧盯错误日志（error_log）而非访问日志：Permission denied 与 Permission denied while reading upstream 等具体描述，远比 403 这个状态码更能直接指向原因。



### 配置生效类

#### if 指令误用（if is evil）

**现象**：在 location 里写了 if 之后，出现 500、空响应、rewrite or internal redirection cycle 循环重定向，或 if 内的指令时灵时不灵；同样的配置挪到别的 location 又恢复正常。

**原因**：if 属于 rewrite 模块指令，**执行阶段与其他模块交织**，每个 if 块还会生成一个隐藏的嵌套配置上下文。当 if 内同时出现**不同模块的指令**（尤其是 proxy_pass 这类内容处理指令）时，指令归属哪个上下文变得违反直觉，这正是社区所称 **if is evil** 问题的根源。

```nginx
# 错误示例：if 内混用内容处理指令，行为不可预期
location /download/ {
    if (!-f $request_filename) {
        proxy_pass http://backend;   # if 内的 proxy_pass 与外层配置的交互难以预料
    }
    root /data/web;
}
```

**解法**：把条件计算与请求处理分开——变量交给 map 预先算好，文件存在性交给 try_files，简单跳转直接用 return；if 内只保留 return 这类官方认可的安全用法。

```nginx
# 修复一：文件存在性判断改用 try_files，回退交给命名 location
location /download/ {
    root /data/web;
    try_files $uri @backend;
}

location @backend {
    proxy_pass http://backend;
}
```

```nginx
# 修复二：条件计算移到 map，if 内只写一条 return
map $http_user_agent $is_mobile {
    default  0;
    ~*mobile 1;
}

server {
    location / {
        if ($is_mobile) {
            return 302 https://m.example.com$request_uri;   # if 内只有 return，安全
        }
        root /data/web;
    }
}
```

> [!WARNING]
> **警告内容**：社区对 if 的共识是 if is evil：if 内只允许出现 return（以及 rewrite ... last 等少数场景），绝不在 if 内混用 proxy_pass、root、try_files 等内容处理指令。需要条件逻辑时，一律改用 map、try_files 或多个正则 location 实现。

> Nginx 官方 wiki 的 If is Evil 一文收录了各类翻车案例与安全边界，动手写 if 之前值得通读一遍。



#### 修改配置后不生效

**现象**：改了 nginx.conf 或 conf.d 下的文件，线上行为毫无变化；或新增了 server 块，请求仍被旧 server 接走；换台机器、换个浏览器又显示生效了。

**原因**：配置生效的链路上有四道常见的假生效关卡。

- **未 reload**：Nginx 只在启动或 reload 时读取配置，单纯修改文件不会触发任何行为变化。
- **include 顺序与默认 server 抢占**：conf.d 按文件名字典序 include；请求匹配不上任何 server_name 时，交给第一个监听该端口与地址的 server（或显式的 default_server），排在其后的 server 若没匹配上域名就永远选不中。
- **server_name 冲突**：两个 server 声明了相同的 server_name，先加载的优先，后写的形同虚设。
- **浏览器缓存干扰**：301 重定向与静态资源被浏览器本地缓存，呈现出配置未生效的假象。

```bash
# 标准生效流程：先测语法，通过后再平滑重载；任何一步报错都说明改动有问题
nginx -t && nginx -s reload
```

```bash
# 绕开浏览器与 DNS，带 Host 头直连本机，验证命中的 server 与返回头
curl -sI -H "Host: api.example.com" http://127.0.0.1/health
```

**解法**：按顺序过四道关卡。

- **第一关 reload**：先 nginx -t 后 nginx -s reload，确认命令无报错再观察行为。
- **第二关绕缓存**：用 curl 带 Host 头直连本机，排除浏览器缓存与 DNS 解析的干扰。
- **第三关 server 匹配**：核对 server_name 是否唯一、默认 server 是否被抢占，必要时显式声明 default_server。
- **第四关覆盖关系**：检查 conf.d 的 include 顺序与同名指令——普通指令在同一上下文重复出现时多数以先出现者为准，add_header 这类可重复指令则逐条全部生效。

> [!IMPORTANT]
> **重要内容**：reload 是平滑重载：master 进程重新读取配置并拉起新 worker，旧 worker 处理完存量请求后退出，服务不中断。每次改配置后都应固定执行 nginx -t 加 nginx -s reload，避免带病配置导致 reload 失败、旧配置继续生效而无人察觉。



### 上传与超时类

#### 上传文件报 413 请求实体过大

**现象**：上传几兆以上的文件直接收到 413 Request Entity Too Large，小文件正常；错误日志伴随 client intended to send too large body 的记录，请求根本到不了后端。

**原因**：**client_max_body_size** 限制请求体大小，**默认值约为 1m**，现代文件稍一超限就触发 413；Nginx 收满限额即断开连接，后端完全无感知。

- 该指令可出现在 **http、server、location** 三个层级，就近生效。
- 反代场景下后端框架的 multipart 限额是第二道闸，两处都要核对，取小者先拦。

```nginx
# 修复：http 层给一个全局兜底值，上传接口的 location 单独放大
http {
    client_max_body_size 20m;          # 全局兜底

    server {
        location /api/upload/ {
            client_max_body_size 500m; # 仅对上传接口生效
            proxy_pass http://backend;
        }
    }
}
```

**解法**：按业务给上传接口单独设置更大的限额，其余接口维持小限额以降低滥用风险；同时确认后端应用的 multipart 上限不低于 Nginx 侧的值，避免 Nginx 放行、后端拒绝的错位。

> [!NOTE]
> **提醒内容**：client_max_body_size 设为 0 表示不限制大小，但这等于放弃对恶意大包的第一道防线；生产环境不建议全局置 0，只在确实需要的接口上放开。



#### 大文件上传中断与超时

**现象**：几百兆的大文件上传到一半失败，表现为 504 Gateway Time-out 或连接被重置；调大 client_max_body_size 后，换到慢速网络再传，依然中途断开。

**原因**：上传链路上有三个相互联动的阈值，任何一个先到都会掐断请求。

- **client_max_body_size**：先卡大小，超过即 413，是第一道闸。
- **client_body_timeout**：两次**读取请求体**之间的空闲间隔上限（默认 60 秒），慢速客户端两次写入间隔过长即中断，注意它不是整个上传的总时长。
- **proxy_read_timeout**：Nginx 等待**后端响应**的两次读间隔（默认 60 秒），后端处理大文件耗时过长时先超时，表现为 504。

```nginx
# 修复：三个阈值按同一量级联动调整，避免按下葫芦浮起瓢
location /api/upload/ {
    client_max_body_size    2g;    # 大小上限按业务上限给足
    client_body_timeout     300s;  # 客户端两次发数据的最大间隔
    proxy_read_timeout      300s;  # 等待后端处理与响应的最大间隔
    proxy_send_timeout      300s;  # 向后端转发请求体的最大间隔
    proxy_request_buffering off;   # 大文件可选：边收边转，不在 Nginx 落盘
    proxy_pass http://backend;
}
```

**解法**：先定位断点在哪一段——一上来就 413 调大小上限；上传中途断开调 client_body_timeout；传完等结果超时调 proxy_read_timeout。三者按业务最慢场景统一量级，再视磁盘与内存压力考虑 proxy_request_buffering off。

> client_body_timeout 与 proxy_read_timeout 都是两次读写之间的**间隔**而非总时长：面对极慢的客户端，300 秒也未必够。真正的大文件场景应转向分片上传等应用层方案，而不是无限调大超时。



#### 301 永久重定向被浏览器长期缓存

**现象**：曾把某域名或路径 301 到旧地址，后来想改跳转目标，服务器配置明明已更新，老用户访问仍被带到旧地址，怎么清 Nginx 缓存都无济于事。

**原因**：**301 属于永久重定向**，浏览器会按 HTTP 缓存语义将其缓存（响应带 Cache-Control 或 Expires 时更甚），**后续同名请求不再访问服务器**，直接本地跳转；服务端此后的任何改动，对已缓存的浏览器都无效。

```nginx
# 错误示例：迁移初期就使用 301，方向一旦要改，老用户短期无法挽回
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;
}
```

```nginx
# 修复：过渡期一律用 302 临时重定向，跳转关系稳定后再切 301
server {
    listen 80;
    server_name old.example.com;
    return 302 https://new.example.com$request_uri;
}
```

**解法**：两条实务规则。第一，域名与路径迁移**先上 302 观察，稳定后再切 301**；第二，若已被 301 污染，服务端无法撤销，只能引导用户手动清理，或通过新路径、带查询参数的新 URL 绕开缓存。

```bash
# 检查重定向响应是否携带缓存头，评估被浏览器缓存的时长
curl -sI https://old.example.com/ | grep -iE "HTTP/|location|cache-control|expires"
```

> [!CAUTION]
> **注意内容**：301 的缓存效力掌握在每一个用户浏览器手里，服务端永远无法批量撤销；对跳转关系还有任何不确定性时，一律先用 302。这正是 HTTP 语义中永久与临时的分工所在。



### 连接与限流类

#### 连接暴涨与 worker_connections 耗尽

**现象**：流量高峰时 Nginx 开始拒绝新连接或响应极慢，错误日志出现 worker_connections are not enough；监控上并发连接数逼近某个整数上限后不再增长，错误率陡增。

**原因**：单个 worker 进程能打开的连接数由 **worker_connections** 限制（默认值随平台，常为 512 或 1024），每个客户端连接至少占一个连接位；反代场景下到后端的连接**同样占用 worker 的连接配额**，一条代理请求实际消耗两个连接位。

```nginx
# 错误示例：保持默认的小配额，高峰期直接耗尽
events {
    worker_connections 1024;   # 默认量级，未按流量评估
}
```

```nginx
# 修复：worker 进程数自动对齐 CPU，连接配额按压测结果放大
worker_processes auto;         # 与 CPU 核数一致是常规做法

events {
    worker_connections 10240;  # 单 worker 连接上限，按压测数据设定
}

# 主上下文抬高进程级文件描述符上限，保证配额拿得到系统资源
worker_rlimit_nofile 65535;
```

**解法**：三步走。第一步看错误日志，确认确实是 worker_connections 耗尽；第二步按 总连接上限 = worker_processes × worker_connections 评估目标流量并调大；第三步核对操作系统层 worker 用户的文件描述符上限（ulimit -n 与 worker_rlimit_nofile）是否跟上，避免应用配额调了、系统层卡死。

> 连接上限并非越大越好：每个连接都有内存与文件描述符开销，应结合压测与内存容量确定；连接数长期贴着上限运行，本身就是容量告警信号。



#### TIME_WAIT 堆积与 upstream 未开 keepalive

**现象**：Nginx 所在机器上 netstat 一刷满屏 TIME_WAIT（数以万计）；到后端的连接每条请求都新建，后端出现大量短连接；高并发下本地端口耗尽，报 Cannot assign requested address。

**原因**：Nginx 与 upstream 后端之间**默认每条请求新建一条 TCP 连接、用完即关**，主动关闭方（通常是 Nginx）的连接进入 TIME_WAIT 并停留约两分钟；QPS 一高，短连接开销与 TIME_WAIT 堆积同时爆发。

```nginx
# 错误示例：未配置 keepalive，每条请求都经历完整的握手与挥手
upstream backend {
    server 10.0.0.1:8080;
}
```

```nginx
# 修复：开启 upstream 连接池，并让反代使用长连接协议
upstream backend {
    server 10.0.0.1:8080;
    keepalive 32;                # 每个 worker 进程保留的空闲长连接数
}

server {
    location /api/ {
        proxy_http_version 1.1;          # keepalive 需要 HTTP/1.1
        proxy_set_header Connection "";  # 清空 Close 头，避免每请求断连
        proxy_pass http://backend;
    }
}
```

**解法**：给高频调用的 upstream 开启 keepalive 连接池，同时必须配合 proxy_http_version 1.1 与清空 Connection 头，三者缺一不可；已经堆积的 TIME_WAIT 属历史连接的自然消亡，等待其超时即可，重点是掐断新增短连接的源头。

> [!IMPORTANT]
> **重要内容**：keepalive 的数值指每个 worker 进程的空闲连接池大小，不是全机总量；设得过小起不到复用效果，设得过大占用后端资源，常规按单机 QPS 乘以平均响应时间的量级估算，再以压测校准。



### 压缩与传输类

#### gzip 不生效的排查清单

**现象**：配置里明确写了 gzip on，用浏览器或 curl 查看，响应却没有 Content-Encoding: gzip，正文原样传输，页面体积与加载时间居高不下。

**原因**：gzip on 只是总开关，**响应要被压缩需同时满足一串条件**，任何一条不满足都会静默跳过压缩，这正是它配了却没生效的根本原因。排查按清单逐项核对：

- **类型不在白名单**：gzip_types 默认只含 text/html，CSS、JS、JSON 都必须显式加入。
- **响应太小**：小于 gzip_min_length（默认 20 字节）的内容不压缩，收益为零甚至变大。
- **响应无 Content-Length**：长度未知（如流式响应）时 gzip_min_length 无从判断，需结合版本行为与实测确认。
- **代理层剥离了 Accept-Encoding**：上游代理或中间层未透传该请求头，Nginx 收到的是客户端不支持压缩的信号。
- **内容本身已压缩**：图片、视频、zip、woff2 字体等已是压缩格式，再压无益，不放进 gzip_types 属正常设计。

```nginx
# 一份生产可用的压缩配置，覆盖清单中的主要缺口
http {
    gzip on;
    gzip_min_length 1k;              # 小于 1k 不压缩
    gzip_comp_level 5;               # 压缩级别 1-9，5 是常见性价比点
    gzip_types text/plain text/css application/json application/javascript
               text/xml application/xml application/xml+rss image/svg+xml;
    gzip_vary on;                    # 追加 Vary: Accept-Encoding，供缓存层区分
    gzip_proxied any;                # 对代理请求也执行压缩判断
}
```

```bash
# 验证：显式带上 Accept-Encoding 头，观察响应是否出现 Content-Encoding: gzip
curl -sI -H "Accept-Encoding: gzip" https://www.example.com/app.js
```

**解法**：按清单逐项排查——先确认请求带 Accept-Encoding、响应类型在 gzip_types 里、体积超过 gzip_min_length；反代链路再核对 Accept-Encoding 的透传情况与后端是否已压缩；最后用 curl 直连 Nginx，排除浏览器与中间层干扰。

> [!TIP]
> **建议内容**：gzip_vary on 应与 gzip on 同时开启：经过 CDN 或代理缓存时，压缩与未压缩版本共用同一缓存键会互相串版本，Vary: Accept-Encoding 头正是告知缓存层按该请求头区分缓存副本。
