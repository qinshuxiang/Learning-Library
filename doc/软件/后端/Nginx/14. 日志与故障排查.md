## 日志与故障排查

### 两类日志的定义与作用域

Nginx 的可观测性建立在两类日志之上：**access_log** 访问日志记录每个请求的处理结果，**error_log** 错误日志记录 Nginx 自身运行过程中的事件与错误。排障工作几乎总是从这两类文件开始。

#### access_log 与 error_log

**access_log**：记录每个 HTTP 请求的访问信息（来源、时间、URI、状态码、耗时等）的日志，是流量分析、审计与问题定位的数据源。

**error_log**：记录 Nginx 运行中事件与错误（启动、配置问题、上游异常、限流事件等）的日志，是排障的第一入口。

- access_log 按请求逐条产生，量级与流量成正比；error_log 量级小得多，但信息密度高。
- 分析「某个请求为什么这样返回」看 access_log；分析「Nginx 本身或上游哪里坏了」看 error_log。
- 两类日志相互独立、分别配置，路径与格式互不影响。



#### 可定义的作用域与覆盖关系

两类日志都可在多个层级定义，**内层覆盖外层**：某一范围定义了自己的日志配置后，就不再继承外层的设置。

- **access_log** 可定义在 http、server、location 中。
- **error_log** 可定义在 main（主配置顶层全局段）、http、server、location 中。
- 覆盖关系是「整段替换」而非合并：location 里写了 access_log，就完全独立于 server 与 http 层的配置，包括格式与缓冲参数。
- 利用覆盖关系可对特定路径单独记日志（如管理后台单独落盘）、对噪声路径关闭访问日志（access_log off）。

> 排障时若发现某 location 的日志格式与预期不符，先检查该 location 及其上层是否有覆盖配置，这是「改了格式却不生效」的常见原因。



#### 日志写盘的缓冲

访问日志默认每条请求同步写盘，高并发下磁盘 IO 会成为瓶颈，可通过 buffer 参数与 open_log_file_cache 缓解。

- **buffer=size**：日志先写入指定大小的内存缓冲区，攒满或到达 flush 时间点再批量落盘，显著减少写盘次数。
- **open_log_file_cache**：缓存已打开日志文件的文件描述符，避免每写一条日志都执行一次打开与关闭文件的操作，适用于日志文件众多或频繁滚动的场景。
- 两者都是性能优化手段，配置在 access_log 指令的附加参数或独立指令中。

> [!CAUTION]
> **注意内容**：开启 buffer 后，Nginx 进程异常退出时缓冲区中未落盘的日志会丢失。普通业务日志可接受这一折中，涉及安全审计、计费对账的日志不建议开缓冲。



### log_format 自定义日志格式

log_format 指令定义访问日志的行格式，内置变量按需拼装；生产上普遍在默认格式之外自定义结构化格式。

#### 默认 combined 格式

**combined**：log_format 的默认预置格式，未自定义时访问日志按它输出，一行包含来源、时间、请求行、状态码与常见请求头。

```nginx
# 默认 combined 格式的构成（log_format 源自 Nginx 编译内置）
log_format combined '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent"';
```

- 字段依次为：客户端地址、认证用户、本地时间、请求行、状态码、响应体字节数、来源页、用户代理。
- combined 是业界事实标准，大量日志分析工具默认按它解析。
- 自定义格式时通常保留 combined 的主干，再追加耗时、上游等排障变量。



#### 常用内置变量

以下变量是自定义日志格式与排障的基础，逐个给出定义。

- **$remote_addr**：客户端地址，即与 Nginx 直接建立 TCP 连接的对端 IP；未用 realip 模块还原时，前置代理场景下它是代理的地址。
- **$time_local**：本地时间格式的请求时间（如 07/Sep/2026:10:00:00 +0800），日志按天切割的依据之一。
- **$request**：完整的原始请求行，包含方法、URI 与协议版本（如 GET /api/items HTTP/1.1）。
- **$status**：响应状态码。
- **$body_bytes_sent**：发送给客户端的响应体字节数，不含响应头；统计流量用它而非 $bytes_sent。
- **$http_referer**：请求头 Referer 的值，即来源页地址；无来源时为空。
- **$http_user_agent**：请求头 User-Agent 的值，用于识别浏览器、爬虫与客户端类型。
- **$http_x_forwarded_for**：请求头 X-Forwarded-For 的值，记录经过的代理链路追加的客户端 IP 列表。
- **$request_time**：请求处理总耗时，单位秒（毫秒精度），详见下一节辨析。
- **$upstream_response_time**：从上游服务器获得响应的耗时，单位秒（毫秒精度）。
- **$upstream_addr**：本次请求转发的上游地址，多台上游被依次尝试时以逗号、冒号分隔。
- **$upstream_cache_status**：缓存命中状态，取值如 MISS、HIT、EXPIRED、BYPASS、STALE、UPDATING、REVALIDATED，排查缓存问题必备。

> 每个以 http_ 开头的变量都对应同名请求头（横线换下划线、统一小写），如 $http_x_forwarded_for 对应 X-Forwarded-For。这类变量在请求未携带对应头时为空字符串，日志中表现为空位。



#### JSON 风格 log_format 示例

生产环境常用 JSON 格式记录访问日志，便于日志采集系统（如 ELK）直接解析。escape=json 对变量值做 JSON 转义，防止引号注入破坏结构。

```nginx
http {
    log_format json_log escape=json
        '{'
            '"time":"$time_local",'
            '"remote_addr":"$remote_addr",'
            '"request":"$request",'
            '"status":$status,'
            '"body_bytes_sent":$body_bytes_sent,'
            '"request_time":$request_time,'
            '"upstream_addr":"$upstream_addr",'
            '"upstream_response_time":"$upstream_response_time",'
            '"referer":"$http_referer",'
            '"user_agent":"$http_user_agent",'
            '"x_forwarded_for":"$http_x_forwarded_for"'
        '}';

    server {
        listen 80;
        access_log /var/log/nginx/access_json.log json_log;
    }
}
```

- $status、$body_bytes_sent、$request_time 恒为数字或可转为数字，不加引号；可能为空的字符串字段一律加引号并依赖 escape=json 转义。
- upstream_response_time 可能出现逗号、冒号（多次重试）或横线（无上游），故按字符串处理。



### 关键排查变量辨析

访问日志里有三组变量是高频考点，也是线上排障最常用的证据，必须分清各自度量的是什么。

#### request_time 与 upstream_response_time

**$request_time**：Nginx 从收到客户端请求的第一个字节起，到响应最后一个字节发出为止的总耗时；**$upstream_response_time**：仅统计从上游服务器取得响应所花的纯上游耗时。

- $request_time 包含 Nginx 自身的全部开销：读取请求体、查找配置、与上游建连、缓冲响应、向客户端传输数据等。
- $upstream_response_time 只覆盖上游侧：与上游建连、发送请求、等待上游处理并读取响应的时间。
- 二者的差值就是 Nginx 环节的开销：request_time 明显大于 upstream_response_time 时，瓶颈多在缓冲、网络传输或客户端接收慢。
- 两者都慢：上游慢；只有 request_time 慢：Nginx 或链路慢；两者都短但用户抱怨慢：慢在客户端到 Nginx 之间。

> [!IMPORTANT]
> **重要内容**：判断「慢在谁」的第一步就是对比这两个变量：upstream_response_time 高，去查上游；只有 request_time 高，去查 Nginx 的缓冲、带宽或客户端链路。颠倒方向会把排查引向完全错误的一层。



#### upstream_addr 判断命中哪台上游

**$upstream_addr**：记录本次请求实际转发的上游服务器地址（IP 加端口或 unix 套接字路径），是定位「问题出在哪台后端」的直接依据。

- 配置了多台上游时，正常请求只记录一台；发生重试时按尝试顺序以逗号分隔列出多台。
- 地址后可能附带冒号分隔的状态（如 502），表示该台上游返回的结果。
- 与 $upstream_response_time 配合，可精确到「哪台上游、慢了多少毫秒」。
- 排查负载不均、某台后端持续报错时，先按该变量聚合统计。



#### remote_addr 与 X-Forwarded-For 的呼应

**$remote_addr** 是 TCP 直连对端的物理地址，不可伪造；**X-Forwarded-For** 是 HTTP 头，链路上的每一跳代理都可以追加或篡改。

- 无代理时，$remote_addr 就是真实客户端 IP，X-Forwarded-For 通常为空。
- 经过了代理或 CDN 时，$remote_addr 是最后一跳代理的地址，真实客户端 IP 只能从 X-Forwarded-For 的链路中还原，Nginx 需用 realip 模块配合 set_real_ip_from 与 real_ip_header 完成还原（与第 6 章呼应）。
- 日志实践：同时记录 $remote_addr 与 $http_x_forwarded_for，前者作为可信判据，后者保留完整链路。
- 安全结论：**做白名单、限流、封禁等判据时只信 $remote_addr（realip 还原后的），绝不直接信任 X-Forwarded-For**，否则攻击者可伪造该头绕过限制。



### error_log 的级别

error_log 指令的第二个参数控制日志级别，级别决定了记录哪些事件以及日志量的多少。

#### 八个日志级别

error_log 支持从轻到重共八个级别：debug、info、notice、warn、error、crit、alert、emerg。

- **debug**：最详细的调试信息，量极大，仅排障时短期开启。
- **info**：一般性信息，如 upstream 响应异常等事件。
- **notice**：值得注意的正常事件，如配置变更后的提示。
- **warn**：警告，功能仍可用但存在隐患，如请求头过大被丢弃。
- **error**：错误，操作失败，是最常用的运行级别。
- **crit**：临界错误，如套接字资源分配失败。
- **alert**：需要立即警觉的严重问题。
- **emerg**：紧急错误，进程通常已无法继续工作，如配置解析彻底失败。

error_log 的级别参数表示「记录该级别及更严重的事件」，生产默认级别为 error；级别每调低一档，日志量都会明显增加。



#### 排障时临时调低级别

排障的标准做法是临时把级别调低、复现问题、取证后再调回。

1. 备份当前 error_log 配置行。
2. 把级别临时改为 notice 或 info（需要更细线索时改 debug），执行 nginx -t 后 reload。
3. 复现问题，用 tail -f 或 grep 过滤新增日志。
4. 取证完毕立即恢复原级别，再次 reload。

> [!WARNING]
> **警告内容**：级别调低后日志量会成倍增长，磁盘可能被快速写满，进而影响整个机器上的服务。临时调级须设定回收时间，并确认 error_log 所在分区的剩余空间足够。



#### debug 级别与 --with-debug

debug 级别的完整调试日志需要 Nginx 在编译时加入 **--with-debug** 选项支持，否则配置了 debug 也拿不到完整调试输出。

- 验证方式：nginx -V 查看编译参数中是否含 --with-debug。
- 主流发行版的软件源预编译包通常已启用该选项；自行编译而未加该参数时，debug 级别只能输出部分信息。
- debug 日志量巨大且包含敏感的内部细节，只在排障窗口开启，取完证据即关闭。



### 日志切割

访问日志持续增长，必须按周期切割归档，否则检索与运维都会陷入困境。切割的核心动作是改名加重新打开。

#### 为什么要切割

切割是把持续追加的单个日志文件按天（或按大小）拆分为一系列归档文件的例行运维。

- 单文件过大会导致检索缓慢、grep 耗时长，编辑器与部分工具直接打不开。
- 按天切割后归档、压缩、投递到日志平台的粒度清晰，保留期管理（如只留三十天）易于执行。
- 不切割的极端后果是写满磁盘分区，影响同机所有服务。



#### logrotate 的配置思路

**logrotate**：Linux 上通用的日志轮转工具，由 cron 或 systemd timer 周期触发，按配置文件对指定日志执行改名、压缩、删除旧档，并可在切割后执行自定义脚本。

```text
/var/log/nginx/*.log {
    daily
    rotate 30
    missingok
    notifempty
    compress
    dateext
    sharedscripts
    postrotate
        [ -f /var/run/nginx.pid ] && nginx -s reopen
    endscript
}
```

- daily 按天轮转，rotate 30 保留三十份，compress 压缩归档，dateext 用日期作归档后缀。
- missingok 与 notifempty 避免日志缺失或为空时报错。
- 关键在 postrotate 钩子：切割（改名）完成后必须通知 Nginx 重新打开日志文件，发 USR1 信号与执行 nginx -s reopen 两种写法等价，选其一即可。



#### nginx -s reopen 与切割的坑

**nginx -s reopen**：让 master 进程重新打开所有日志文件的命令，效果等同向 master 发送 USR1 信号，是日志切割后必做的收尾动作。

```bash
# 切割脚本完成改名后执行
nginx -s reopen

# 等价写法：向 master 进程发送 USR1 信号
kill -USR1 "$(cat /var/run/nginx.pid)"
```

Nginx 打开文件后持有的是文件描述符而非路径，改名文件并不影响已打开的描述符。**切割后若不执行 reopen，Nginx 会继续把日志写进已被改名的旧文件，新文件始终为空，产生「日志消失」的假象**。

> [!WARNING]
> **警告内容**：logrotate 配置里漏掉 postrotate 的 reopen 是经典事故：切割当天看新日志文件永远是 0 字节，而磁盘仍在被那个已改名的旧文件撑大。自建切割脚本同样必须在改名后执行 nginx -s reopen，并核对新文件确有增量。



### 常见错误码的排查链

对 4xx 与 5xx 错误，Nginx 侧的排查有相对固定的链路，逐个错误码给出演练步骤。

#### 404 排查链

404 表示服务器找不到请求的资源，绝大多数是静态路径配置问题。

1. 演算 root 与 alias 的路径拼接：root 是「根加完整 URI」拼接，alias 是「用别名替换 location 前缀」，二者混用是 404 的头号原因。
2. 核对拼接出的绝对路径下文件是否真实存在，注意文件名大小写（Linux 文件系统区分大小写）。
3. 检查文件与各级目录的读取权限，进程运行用户（user 指令）是否有权进入目录。
4. 检查 try_files 的兜底参数：配置了 try_files 时，前序候选都不存在会跳转到兜底项（如转给前端路由或返回 404），确认跳转是否符合预期。



#### 403 排查链

403 表示资源存在但被拒绝访问，是权限类问题。

1. 检查目录权限：Nginx 进程用户对请求路径上每一级目录都需要执行位（x），目录缺执行位是 403 的最常见原因。
2. 检查 index 配置：目录请求时若 index 指定的默认文件都不存在，且 autoindex 处于默认的 off，直接返回 403。
3. 检查 allow 与 deny 规则：请求来源 IP 是否命中了 deny 规则（首个命中生效）。
4. 排查 SELinux：开启了 SELinux 的系统上，文件安全上下文不对也会 403，可用相关命令核对与修复上下文。



#### 413 排查链

413 表示请求实体过大，由 Nginx 的请求体大小上限触发。

1. 确认 client_max_body_size 的值与作用域：默认上限很小（1m），上传接口必须在对应 server 或 location 中调大。
2. 注意该指令可定义在 http、server、location，内层覆盖外层，检查是否有内层配置覆盖了外层调大的值。
3. 前置了代理或 CDN 时，其自身也有体积上限，须整链路一并调整。
4. 客户端上传超时类问题与之相伴，必要时同步检查 client_body_timeout 等参数。



#### 499 排查链

499 是 Nginx 自定义状态码，表示**客户端在上游返回响应之前主动断开了连接**。

1. 它通常不是故障本身而是症状：客户端（或其前面的网关、浏览器）等不及超时离开，根因多在上游太慢。
2. 结合 access_log 的 $request_time 与 $upstream_response_time 确认：499 请求的 upstream_response_time 往往接近某处的超时阈值。
3. 检查上游该时段是否抖动：慢查询、连接池耗尽、下游依赖超时。
4. 评估客户端侧超时设置与 Nginx 的 proxy_read_timeout 是否匹配；大量 499 也可能来自客户端重试风暴，需结合业务确认。



#### 500 与 502、504 排查链

**500**：服务器内部错误，在 Nginx 场景多为配置错误（如 rewrite 死循环、内存问题）或反代的后端代码异常被透传；**502**：上游返回了无效响应或连接被拒；**504**：上游在超时时间内没有响应。

- 500 排查：先看 error_log 是否为 Nginx 自身配置问题（配合 nginx -t）；若 Nginx 无异常，则 500 来自上游应用的异常响应，转入应用日志排查。
- 502 排查：确认上游进程是否存活、端口是否正确、监听地址是否可达；查看 error_log 中 connect() failed 或 upstream prematurely closed 类记录。
- 504 排查：上游存活但响应过慢，检查 proxy_connect_timeout、proxy_read_timeout 与上游实际耗时，与第 6 章反向代理的超时体系呼应。
- 三者的分界：500 是「内部出错」，502 是「上游给的回应不可用」，504 是「上游一直没给回应」。



### 排查工具链

Nginx 排障依赖一组命令行工具，掌握各自的适用场景能把定位时间从小时级压到分钟级。

#### nginx -t 与 -T

**nginx -t**：校验配置文件语法与语义正确性，不实际生效；**nginx -T**：在校验之外把最终合并后的完整配置打印到标准输出。

- 任何配置修改后、reload 前都必须执行 nginx -t，这是最低限度的安全动作。
- -T 的价值在于查看「实际生效的配置」：多个 include 合并后的全貌、变量展开前后的上下文，排配置冲突时最直接。
- 两者都可指定 -c 加载非默认路径的配置文件。

```bash
nginx -t
nginx -T | grep -n "limit_req"   # 在合并后的完整配置中定位限流相关配置
```



#### tail -f 与 curl 的用法

**tail -f**：持续追踪日志文件新增内容的命令，是「边复现边看日志」的基本手段；**curl**：从命令行发起 HTTP 请求，绕开浏览器缓存直达真相。

```bash
# 同时追踪访问与错误日志的新增行
tail -f /var/log/nginx/access.log /var/log/nginx/error.log

# 只看响应头，快速确认状态码与响应头字段
curl -I http://127.0.0.1/api/status

# 指定 Host 头，验证 server_name 匹配是否正确
curl -I -H "Host: example.com" http://127.0.0.1/
```

- curl -H "Host: ..." 在本机模拟任意域名的请求，是排查 server_name 冲突、default_server 接流的利器。
- 浏览器看到的结果可能被缓存污染，curl 每次都是真实请求，两者结论冲突时以 curl 为准。



#### ss 与 lsof 查端口占用

启动 Nginx 报 Address already in use，或怀疑端口被抢占时，用 ss 或 lsof 定位占用者。

```bash
# 查看谁在监听 80 端口
ss -ltnp | grep ":80 "

# 同样目的的另一种写法
lsof -i :80 -sTCP:LISTEN
```

- ss -ltnp 列出监听中的 TCP 端口及进程信息；lsof -i 按端口反查进程。
- 常见占用来源：本机已有另一实例 Nginx、Apache、其他 Web 服务或开发服务器。
- 确认占用者后，改用其他端口或停掉冲突进程，而非盲目杀进程。



#### systemctl status nginx

**systemctl status nginx**：查看 Nginx 服务单元状态的命令，可看到运行状态、主进程号、最近日志行与退出原因。

```bash
systemctl status nginx        # 服务状态与最近日志
journalctl -u nginx --since "10 min ago"   # 服务单元最近的完整日志
```

- 服务起不来时，status 与 journalctl 输出通常直接给出配置错误的行号或权限问题。
- status 中的启动时间与 reload 记录可佐证「改动是否真的被加载过」。



### 配置变更不生效的通用排查顺序

改了配置却看不到效果，是运维最高频的问题，按固定顺序逐项排除，避免无头苍蝇式试错。

#### 通用排查顺序清单

按以下顺序逐项检查，绝大多数「不生效」都能在前五步内定位。

1. 确认修改已保存：编辑器缓冲未保存、改的是备份文件、改了另一套环境的配置，都是真实高发的事故。
2. 执行 nginx -t 确认语法通过：语法错误时 reload 不会执行，旧配置继续生效。
3. 确认已 reload：nginx -s reload 或 systemctl reload nginx；只改文件不重载，Nginx 永远跑旧配置。
4. 确认请求真的打到了这台、这个 server 块：用 curl -H "Host: ..." 复现，排除请求被其他 server 块（server_name 冲突或 default_server）接走的可能。
5. 排除浏览器缓存与代理缓存干扰：直接用 curl 请求，必要时加随机查询参数绕过缓存，对比浏览器与 curl 的响应差异。
6. 检查配置覆盖关系：location 内层覆盖 server、server 覆盖 http，用 nginx -T 查看合并后的最终配置确认改动仍在生效链上。
7. 复核监听与流量路径：请求是否被 CDN、前置代理、防火墙转发到了别处。



#### server_name 冲突与 default_server 接流

请求被「错误的 server 块」处理，是配置明明改对了却不见效的隐蔽原因。

- Nginx 按 Host 头匹配 server_name，多个 server 块都能匹配或都匹配不上时，取 listen 上标记 default_server 的块；未显式标记时取该端口下第一个定义的 server 块。
- 排查方法：curl -I -H "Host: 目标域名" http://127.0.0.1/ 看返回的是谁，再对照 nginx -T 里的 server 块定义顺序。
- 修复方式：规范每个 server 块的 server_name，显式指定 default_server，并为未知 Host 提供专门的兜底块（返回 444 或提示页）。

> [!TIP]
> **建议内容**：养成「改配置三连」的肌肉记忆：保存、nginx -t、reload，一步不少。再配合一条固定的 curl 验证命令，绝大多数「不生效」问题在三十秒内即可闭环。
