## location 匹配与请求处理

### location 的语法与五类修饰符

**location**：定义针对某一类 URI 的处理规则的指令，写在 server 块内；按是否带**修饰符**分为五类写法，修饰符直接决定匹配行为。

#### 无修饰符前缀匹配

**前缀匹配**：请求 URI 以模式开头即命中，是五类写法中最基础的一种。

```nginx
location /static/ {
    root /data;
}

location / {
    # 匹配所有以 / 开头的请求，常用作兜底
}
```

- 请求 /static/a.png 与 /static/b/c.js 都命中 location /static/。
- 多个前缀同时命中时取**最长**的那个。
- 无修饰符写法最常用，生产配置中大量充当兜底块。



#### = 精确匹配

**精确匹配**：请求 URI 与模式**完全相等**才命中，命中后立即结束整个搜索。

```nginx
location = / {
    # 只匹配站点首页这一个 URI
    index index.html;
}

location = /login {
    # 只匹配 /login，不匹配 /login/ 与 /login/xxx
}
```

- 请求 / 会命中 location = /，请求 /page 不会。
- 首页写精确匹配是性能最佳实践：命中即止，跳过所有后续搜索。



#### ^~ 前缀匹配

**^~ 前缀匹配**：按前缀规则选中后**跳过全部正则检查**，是前缀匹配的加强形态。

```nginx
location ^~ /static/ {
    # 选中后不再测试任何正则 location
    root /data;
}

location ~ \.png$ {
    # /static/ 下的 png 请求到不了这里
}
```

- 与无修饰符前缀的区别只有一个：被选中后不再走正则测试。
- 典型用途：保护静态目录不被按扩展名分流正则误伤。



#### ~ 与 ~* 正则匹配

**~ 正则匹配**：区分大小写的正则；**~* 正则匹配**：不区分大小写的正则；两者都按**配置书写顺序**测试。

```nginx
location ~ \.(gif|png|jpg)$ {
    root /data/images;      # 区分大小写：只匹配小写扩展名
}

location ~* \.(GIF|PNG|JPG)$ {
    root /data/images;      # 不区分大小写：Gif、GIF 均可
}
```

- 正则按书写顺序逐个测试，第一个命中的立即生效，后面的不再测试。
- 正则可使用捕获组，配合 rewrite 与 alias 引用捕获结果。
- 模式含空格或特殊字符时用引号包裹，一般场景直接书写。

> [!TIP]
> **建议内容**：五类修饰符的选择口径：固定页面（首页、登录页）用 =、静态目录用 ^~、按扩展名分流用 ~ 或 ~*、其余兜底用无修饰符前缀 /。



### 匹配算法与优先级

#### 匹配算法的完整流程

Nginx 对一次请求的 location 搜索按固定步骤执行，顺序由框架写死：

1. 先检查所有 **= 精确匹配**，命中即采用并立刻结束搜索。
2. 在所有前缀 location（含无修饰符与 ^~）中找出**最长匹配**，先记下暂不采用。
3. 若该最长前缀带 **^~**，直接采用它，跳过正则。
4. 否则按**配置书写顺序**逐个测试正则 location，第一个命中的立即采用。
5. 正则全部未命中时，回退采用第 2 步记下的最长前缀。

```nginx
server {
    location /doc/     { return 200 "prefix"; }
    location ~* \.php$ { return 200 "regex";  }

    # 请求 /doc/a.php：两者都能匹配。
    # /doc/ 是最长前缀但不带 ^~，继续测正则，\.php$ 命中 → 返回 regex。
    # 请求 /doc/a.txt：正则不中 → 回退最长前缀 → 返回 prefix。
}
```

> 精确匹配命中即止是唯一能提前结束搜索的情况；其余一切请求都要走完全部步骤才能确定归属，这保证了结果与配置文件中 location 的排列方式无关（正则除外）。



#### 书写顺序的影响

**书写顺序对前缀匹配没有影响，对正则匹配有决定性影响。**

- 前缀之间比的是长度，谁写在前面无关紧要：location / 与 location /api/ 无论先后，/api/x 永远进 /api/。
- 正则之间比的是书写顺序，第一个命中者赢：交换两条正则的前后位置，结果可能完全不同。
- 实战排序建议：精确匹配任意位置；静态目录 ^~ 尽量靠前书写以表意清晰；正则按从特殊到一般排列。

```nginx
server {
    location ^~ /static/ { root /data; }        # 带走静态目录，正则碰不到
    location ~* \.css$   { root /data/theme; }  # 书写顺序在此类之间敏感
    location /           { try_files $uri =404; }
}
```

**一句话记忆：前缀比长度，正则比顺序，精确抢先，最长前缀兜底。**



### location 匹配的 URI 形态

#### 匹配对象是规范化后不含参数的 URI

location 匹配的对象是**规范化后的、不含查询参数的 URI**，与内置变量 $uri 的语义完全一致。

- 查询参数（问号之后的部分）不参与匹配：/search 与 /search?q=nginx 命中同一个 location。
- 规范化包括两步：把相对路径归一为绝对路径（/a/../b 变为 /b）、把百分号编码解码为字符（/%E4%B8%AD 变为中）。
- 想按参数分流只能借助 $args、$request_uri 配合 if 与 map，location 本身做不到。

> [!IMPORTANT]
> **重要内容**：location 与 $uri 同源：判一个请求会进哪个 location 时，先把参数划掉、再把编码还原、再做路径归一化，最后看剩下的路径段。凡是带参数的请求匹配行为不符合直觉，都是忘了参数不参与匹配。



#### 与 $uri、$request_uri 的对照

location 跟着 $uri 走，与 $request_uri 无关；用一次带重写的请求可以同时看到三个概念的分工：

```nginx
location /old/ {
    rewrite ^/old/(.*)$ /new/$1 last;   # 改写后 $uri 变为 /new/page，重新匹配
}

location /new/ {
    return 200 "uri=$uri request_uri=$request_uri";
}

# 请求 /old/page?id=1 的响应：
# uri=/new/page request_uri=/old/page?id=1
```

- 匹配 location /old/ 时依据的是 $uri 的初值 /old/page。
- rewrite 只改 $uri，$request_uri 始终是客户端原始请求 /old/page?id=1。
- 访问日志记录 $request_uri 才能还原用户真实入口；文件查找用 $uri。



### 嵌套 location

#### 嵌套的写法与限制

**嵌套 location**：写在另一个 location 花括号内部的 location，用于在大类路径之下再细分小类处理。

```nginx
location /files/ {
    root /data;

    location ~ \.mp4$ {
        # 仅 /files/ 目录下的 mp4 请求走到这里
        mp4;
    }
}
```

- 嵌套只允许出现在**前缀 location** 内部；正则 location 与命名 location 内再嵌套会被 nginx -t 直接拒绝。
- 子 location 的匹配沿用同一套算法，但候选范围只有外层前缀内部的子块。
- 外层命中后请求会继续在内层子块中匹配，外层的指令在子块未覆盖时仍然生效。



#### 使用价值的边界

通说认为嵌套的实际使用价值有限，默认应当拍平：

- 绝大多数配置可以写成一维的 location 列表，配合最长前缀与 ^~ 达到同样效果。
- 嵌套会让某个请求究竟进了哪一层变得难以口算，排查成本高于收益。
- alias 与嵌套组合存在历史遗留的边界问题，通说建议避免同时使用。

> [!TIP]
> **建议内容**：默认不嵌套。只有当外层前缀内出现需要完全不同处理逻辑的少量子路径、且拍平后前缀关系变得啰嗦时，才考虑嵌套，并保证嵌套内只使用 root。



### root 与 alias

#### root 的拼接语义

**root**：指定静态文件的根目录，真实路径等于 **root 值加上当前 $uri**，即 location 路径被完整保留在最终路径中。

```nginx
location /i/ {
    root /data/w3;
}
# 请求 /i/top.gif → 实际文件 /data/w3/i/top.gif
```

- root 可写在 http、server、location 三个层级，内层未写时继承外层。
- location 前缀 /i/ 原样出现在最终路径里，这是 root 最重要的特征。



#### alias 的替换语义

**alias**：指定静态文件的真实目录，真实路径等于 **alias 值加上当前 $uri 中去掉 location 前缀后的剩余部分**，即匹配前缀被整体替换。

```nginx
location /i/ {
    alias /data/images/;
}
# 请求 /i/top.gif → URI 去掉前缀 /i/ 剩 top.gif
# 最终文件 /data/images/top.gif
```

- alias 只能写在 location 块内。
- URI 中与 location 匹配的那一段不再出现在最终路径里，这是 alias 与 root 的根本差别。



#### 两组对照与逐步演算

**root 是加法（root 加 URI），alias 是换法（alias 替换 location 前缀）。**

配置一（root）与请求 /static/css/main.css 的演算：

```nginx
location /static/css/ {
    root /srv/www;
}
# 第一步：命中前缀 location /static/css/
# 第二步：root 拼接 → /srv/www + /static/css/main.css
# 第三步：实际文件 /srv/www/static/css/main.css
```

配置二（alias）与同一请求的演算：

```nginx
location /static/css/ {
    alias /srv/assets/;
}
# 第一步：命中前缀 location /static/css/
# 第二步：URI 去掉 location 前缀 /static/css/ 剩 main.css
# 第三步：alias 替换 → /srv/assets/ + main.css = /srv/assets/main.css
```

> 同一份磁盘目录，用 root 时 location 前缀必须是目录真实结构的一部分；用 alias 时 URI 结构与磁盘结构可以完全脱钩——alias 的价值正在于此，风险也在于此。



#### alias 的末尾斜杠问题

**末尾斜杠问题**：location 前缀结尾带斜杠时，alias 值结尾也必须带斜杠，两边不一致会丢失分隔符导致路径拼接错误。

```nginx
location /i/ {
    alias /data/images;      # 错误示范：location 带斜杠，alias 不带
}
# 请求 /i/top.gif → 替换后成为 /data/imagestop.gif，分隔符丢失

location /i/ {
    alias /data/images/;     # 正确：两边斜杠对齐
}
```

- 判断标准是替换动作本身：alias 值直接顶替 location 前缀，斜杠不会自动补。
- 正则 location 中使用 alias 时必须以捕获组承接路径，如 location ~ ^/images/(.+)$ 配 alias /data/images/$1。
- alias 与 try_files、嵌套 location 组合时行为存在历史遗留的边界问题，通说建议此类场景改用 root 并保持目录结构与 URI 一致。



### try_files 指令

#### 按顺序检查与内部重定向兜底

**try_files**：按列出顺序逐个检查文件或目录是否存在，采用第一个存在的；全部不存在时，用**最后一个参数**发起一次内部重定向。

```nginx
location /images/ {
    try_files $uri /images/default.gif;
}
# /images/a.png 存在 → 直接返回该文件
# 不存在 → 内部重定向到 /images/default.gif，重新走一遍 location 匹配
```

- 除最后一个参数外，每个参数都是一次存在性检查：$uri 查文件、$uri/ 查目录。
- 最后一个参数不参与存在性检查，而是作为新 URI 触发内部重定向；它也可以写成错误码，如 =404。
- 兜底重定向会让请求重新经历 location 匹配，因此兜底 URI 必须落在能够正确处理它的块里。

> [!CAUTION]
> **注意内容**：最后一个参数是兜底出口而不是都不存在就 404。若兜底 URI 仍会命中当前 location 且依旧找不到文件，内部重定向会形成循环，Nginx 检测到循环后返回 500；排查 500 时先检查 try_files 的兜底目标。



#### 单页应用 history 路由配置

单页应用的 history 路由把所有路径都交给前端处理，服务端只保留真实存在的静态资源，经典配置如下：

```nginx
server {
    listen 80;
    root /srv/spa/dist;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

- 请求 /user/123：磁盘上无此文件也无此目录，兜底内部重定向到 /index.html，由前端路由接管渲染。
- $uri 在此承担找文件的职责；$request_uri 不参与文件查找，但完整保留在访问日志中，用于还原用户真实入口。
- 带参数的请求如 /user/123?from=ad 同样命中该块：匹配看 $uri，参数随请求保留给兜底页面。

SPA 与后端 API 同机共存时，用前缀 location 先行分流 API 请求：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}

location / {
    try_files $uri $uri/ /index.html;
}
```

> [!IMPORTANT]
> **重要内容**：API 前缀与 SPA 兜底共存时，务必保证 /api/ 不会被某条正则 location 按书写顺序抢走；静态目录同理，必要时写成 ^~ /api/ 以跳过正则检查。



### error_page 与命名 location

#### error_page 的内部重定向语义

**error_page**：为指定响应码定义跳转目标，该跳转是一次**内部重定向**：客户端地址栏不变，对外状态码默认也保持原值。

```nginx
error_page 404 /404.html;

location = /404.html {
    root /srv/www/errors;
    internal;          # 仅限内部跳转到达，禁止外部直接访问
}
```

- 404 发生后，Nginx 以 /404.html 为新 URI 重新走一遍 location 匹配，此处命中精确块。
- internal 指令把该 location 标记为仅限内部访问：外部直接请求 /404.html 反而得到 404。
- error_page 还支持改写对外状态码（如 error_page 404 =200 /index.html）与跳转命名位置（如 error_page 500 = @fallback）。



#### 命名 location

**命名 location**：以 @ 开头定义的、不参与常规 URI 匹配的 location，只能被 try_files、error_page 等指令通过名字显式跳入。

```nginx
location / {
    try_files $uri $uri/ @backend;
}

location @backend {
    proxy_pass http://127.0.0.1:8080;
}
```

- 外部请求永远无法直接命中命名 location：它不是地址，是跳转标签。
- 典型用途有二：静态文件找不到时统一转交上游；上游或错误发生时提供兜底处理。
- 命名 location 内部不能再嵌套子 location，其 URI 语义由跳转来源决定。

> 命名 location 与 try_files 是天生一对：try_files 的兜底参数写成 @名字，可以避免兜底 URI 恰好又被某个普通 location 捕获而产生的语义混乱。



### 请求处理阶段概述

#### 处理阶段的划分与顺序

Nginx 把一次 HTTP 请求从接收到响应的过程划分为**固定顺序的处理阶段**，通说按源码枚举归纳为十余个，逐项列出即为下列名称：

1. **POST_READ**：读取完请求头后最早介入，realip 模块在此改写 $remote_addr。
2. **SERVER_REWRITE**：执行 server 块级别的 rewrite 指令。
3. **FIND_CONFIG**：按当前 $uri 匹配 location。
4. **REWRITE**：执行 location 块级别的 rewrite 指令。
5. **POST_REWRITE**：检查 URI 是否被改写，决定是否回到 FIND_CONFIG 重新匹配。
6. **PREACCESS**：访问控制前的准备，如限流限连模块 limit_req、limit_conn 的工作。
7. **ACCESS**：访问控制判定，allow、deny、auth_basic 在此执行。
8. **PRECONTENT**：内容生成前的准备，try_files 在此执行。
9. **CONTENT**：生成响应，static、index、autoindex、proxy_pass 等内容模块在此竞争。
10. **LOG**：请求结束后记录日志，access_log 在此执行。

**阶段顺序由框架写死，与配置书写顺序无关；同一阶段内才按模块注册顺序执行。**



#### 以阶段解释指令的生效先后

不同模块挂载在不同阶段，这正是各指令生效先后确定不移的原因：

- rewrite 早于 allow、deny：改写后的 $uri 才进入 ACCESS 阶段，封禁判断针对的是改写后的地址。
- try_files 晚于 allow、deny：被拒绝的请求根本走不到 PRECONTENT 阶段的文件检查。
- proxy_pass、静态文件响应属于 CONTENT 阶段的兜底：前面所有阶段都放行后才生成响应。
- rewrite last 触发重新匹配 location，会再次经历 FIND_CONFIG 及之后的阶段。

```nginx
location /secret/ {
    rewrite ^/secret/(.*)$ /internal/$1 last;   # REWRITE 阶段改写 URI
}

location /internal/ {
    deny 192.168.1.0/24;    # ACCESS 阶段：按改写后的 URI 生效
    try_files $uri =404;    # PRECONTENT 阶段：晚于 deny，被拒请求到不了这里
}
```

> [!NOTE]
> **提醒内容**：记住三组相对顺序即可应对绝大多数问题：rewrite 最早、allow 与 deny 居中、try_files 与文件及代理响应最后；配置书写顺序影响不了这个框架顺序。
