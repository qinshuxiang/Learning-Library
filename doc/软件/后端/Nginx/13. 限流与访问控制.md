## 限流与访问控制

### 限流的定义与核心算法

限流是 Nginx 保护自身与上游服务的第一道闸门，本章围绕 limit_req 与 limit_conn 两大指令族，以及 allow、deny、geo、map 等访问控制指令展开。

#### 限流的定义与应用场景

**限流**：对单位时间内进入的请求数或同时保持的连接数设置上限，超出上限的请求被延迟处理或直接拒绝的流量控制手段。

- **防刷**：限制单个 IP 对登录、下单、短信验证码等敏感接口的请求频率，抬高脚本刷接口的成本。
- **防爬**：对高频抓取行为按 IP 降速，避免站点内容被批量拉取。
- **削弱攻击流量**：在遭受 CC 攻击等应用层攻击时，把超出容量的恶意流量挡在网关层，避免其全部打到后端。
- **保护上游**：应用服务的处理能力有上限，限流把请求规模约束在上游可承受的范围内，防止雪崩。

> 限流解决的是「量太多」的问题，访问控制（allow、deny、auth_basic）解决的是「谁被允许」的问题。前者面向频率，后者面向身份，两者常配合使用。



#### 漏桶算法

**漏桶算法**（Leaky Bucket）：把请求想象成注入水桶的水，桶以**恒定速率放行**（匀速流出），桶满时新到的请求溢出被拒，从而把不规则的外部流量整形为平滑的匀速流量。

- 请求到达后先进入队列（桶），按固定速率逐个处理。
- 桶满即队列长度达到上限时，新到的请求被直接拒绝。
- 输出速率只由算法本身决定，与请求到达的密集程度无关。

**Nginx 的 limit_req 指令基于漏桶算法实现**。



#### 令牌桶算法

**令牌桶算法**（Token Bucket）：系统以恒定速率向桶中投放令牌，请求只有拿到令牌才能被处理，桶中可预存一定数量的令牌，从而**允许突发配额**。

- 令牌匀速生成，未被消费的令牌持续累积，累积上限即桶容量。
- 空闲期积攒的令牌，允许后续瞬间到来的突发请求一次性消费。
- 没有令牌可用的请求被拒绝或等待。

> 令牌桶的典型实现多见于各类应用层限流组件；Nginx 原生的 limit_req 并不采用令牌桶，而是漏桶。



#### 漏桶与令牌桶的差异

两者的核心差异在于对**突发流量**的态度：**漏桶算法**恒定速率放行，把突发整平；**令牌桶算法**允许突发配额，把空闲额度攒起来集中放行。

- **输出曲线**：漏桶的输出速率恒定；令牌桶的输出速率取决于桶内令牌存量，空闲后可短时超出平均速率。
- **适用场景**：漏桶适合保护处理能力刚性的下游（如按调用量计费的第三方接口）；令牌桶适合既要平均限速、又要容忍正常用户突发操作的业务。
- **约束方向**：漏桶约束的是「流出的节奏」，令牌桶约束的是「进入的总量」。

> 速记：漏桶「匀速出门」，令牌桶「攒票进场」。面试问 Nginx 用哪种，答漏桶，并指出 burst 队列与 nodelay 参数是对漏桶行为的精细化手段。



### limit_req_zone 指令

limit_req_zone 用于定义限流的统计口径与共享内存区，它只负责「记账」，真正执行限流的是 limit_req 指令，两者必须配对使用。

#### 指令的语法与三要素

**limit_req_zone**：在 http 块中声明一个基于共享内存的请求速率统计区，完整语法为 limit_req_zone key zone=name:size rate=rate;，由 key、zone、rate 三要素构成。

```nginx
http {
    # 以客户端 IP 为 key，创建名为 addr_zone 的 10m 共享内存区，速率每秒 10 个请求
    limit_req_zone $binary_remote_addr zone=addr_zone:10m rate=10r/s;

    server {
        listen 80;

        location /api/ {
            limit_req zone=addr_zone;
            proxy_pass http://backend;
        }
    }
}
```

- **key**：限流的统计维度，决定「按什么维度分别计数」，如 $binary_remote_addr 按客户端 IP 分别限流。
- **zone=name:size**：共享内存区的名称与大小，所有 worker 进程共享该内存中保存的计数状态。
- **rate=rate**：平均速率，必须带 r/s 或 r/m 后缀，如 rate=10r/s、rate=30r/m。

> [!IMPORTANT]
> **重要内容**：zone 共享内存耗尽时，后续无法记账的请求会被 Nginx 以 503 拒绝。按官方文档口径，10m 大小的 zone 以 $binary_remote_addr 作 key 时可保存约 16 万个 IPv4 地址的状态，容量规划可据此估算。



#### 以 binary_remote_addr 作 key

限流 key 应优先使用 **$binary_remote_addr** 而非 **$remote_addr**，原因是内存占用：$remote_addr 是点分十进制的文本字符串，$binary_remote_addr 是二进制形式的地址。

- IPv4 地址的文本形式长度不固定，存储时须按较长的字符串预留空间；二进制形式固定为 4 字节（IPv6 为 16 字节）。
- 每一个正在被统计的 key 都要在 zone 中保存状态，key 越小，同样大小的 zone 能容纳的并发统计对象越多。
- 二者的取值含义相同（都是客户端地址），只影响内存效率，不影响限流逻辑。

> 若站点前置了 CDN 或反向代理，$binary_remote_addr 拿到的是直连 Nginx 的那一跳地址，全站用户会被当成同一个 key 限流。此场景须先用 realip 模块还原真实客户端 IP（与第 6 章呼应），再做限流。



#### rate 速率的写法

rate 只接受两种单位：**r/s**（每秒请求数）与 **r/m**（每分钟请求数），数值为整数。

```nginx
# 每秒平均放行 10 个请求
limit_req_zone $binary_remote_addr zone=s_zone:10m rate=10r/s;

# 每分钟平均放行 30 个请求
limit_req_zone $binary_remote_addr zone=m_zone:10m rate=30r/m;
```

- rate=30r/m 的语义是每 2 秒平均放行 1 个，而不是「攒够 30 个名额每分钟集中放行」。
- 漏桶按速率匀速放水，小颗粒度的 r/s 在突发场景下通常配合 burst 使用；r/m 适合验证码、短信发送等低频接口。



#### 作用域与配对使用

**limit_req_zone 只能出现在 http 块**，这是硬性约束：共享内存区是服务器级的全局资源，必须先在 http 层定义，才能被各 server、location 中的 limit_req 引用。

- 同一个 zone 可被多个 limit_req 指令引用，实现按路径差异化限流。
- limit_req_zone 本身不产生任何限流效果，只有在对应 location 写了 limit_req 后才生效。
- 一台 Nginx 可定义多个 zone，按不同 key、不同速率分别记账。

> 速记：zone 是「表」，limit_req 是「执法」。只建表不执法，限流等于没配。



### limit_req 指令与突发流量

limit_req 在 server 或 location 中引用一个 zone，对该范围内的请求执行漏桶限流；burst 与 nodelay 参数决定超出速率的请求如何处置。

#### zone 引用与基本用法

**limit_req**：对所在范围（server 或 location）内的每个请求，按指定 zone 的速率执行漏桶检查。

```nginx
location /login/ {
    limit_req zone=addr_zone;
    proxy_pass http://backend;
}
```

- 不带任何参数时，超过速率的请求立即被拒绝，返回 limit_req_status 指定的状态码（默认 503）。
- limit_req 可写在 http、server、location 中，内层配置覆盖外层；引用的 zone 须已在 http 块定义。



#### burst 的排队语义

**burst**：允许超出速率的请求**排队延迟处理**的容量，burst=5 表示在速率之外额外容忍 5 个请求进入队列，按漏桶节奏依次放行。

- 无 burst 时，超速请求立刻被拒；有 burst 时，超速请求先入队，等桶以恒定速率腾出名额再转发。
- burst 只增加「容忍的突发量」，不改变 rate 本身：平均速率仍被严格限制在 rate 以内。
- 排队有代价：请求的响应时间随排队时间变长，客户端侧超时的风险随之上升。

```nginx
# 平均每秒 10 个，最多容忍 5 个请求排队延迟处理
limit_req zone=addr_zone burst=5;
```

> [!WARNING]
> **警告内容**：单独使用 burst=5 而不加 nodelay，超速请求虽不被拒绝，但要按漏桶节奏排队等待后才被转发，对实时性接口等于变相不可用。纯 burst 方案只适合「结果稍后返回也无妨」的异步类路径。



#### nodelay 与 delay 参数

**nodelay**：与 burst 配合使用，让排队名额**立刻放行、不延迟**——突发请求马上转发，名额照样从 burst 池中扣除，池空后超速请求仍被拒绝。

- limit_req zone=addr_zone burst=5 nodelay 是生产中最常见的组合：既容忍瞬时突发，又不给请求增加延迟。
- **delay**：折中参数（Nginx 1.15.7 起支持），delay=2 表示突发请求中前 2 个立即放行，其余仍排队延迟。
- nodelay 等价于「delay 等于整个 burst」；不写 delay 也不写 nodelay，则全部排队延迟。

```nginx
# 三种形态的对照
limit_req zone=addr_zone burst=5;          # 5 个全部排队延迟
limit_req zone=addr_zone burst=5 delay=2;  # 前 2 个立即放行，其余排队
limit_req zone=addr_zone burst=5 nodelay;  # 5 个全部立即放行
```

> 速记：burst 决定「容忍多少」，nodelay 决定「等不等」。要吞吐加 burst，要低延迟加 nodelay。



#### limit_req_status 与 limit_req_log_level

被限流的请求默认返回 503，限流事件默认按 error 级别记日志，这两个指令分别定制拒绝状态码与日志级别。

- **limit_req_status**：设置被限流请求的响应状态码，可取 400 到 599，常改为 429。
- **limit_req_log_level**：设置限流事件写入 error_log 的级别，可选 info、notice、warn、error，默认 error；被延迟的请求按低一级记录。
- 两者均可写在 http、server、location 中。

```nginx
limit_req_status 429;
limit_req_log_level warn;
```



#### 多条 limit_req 的叠加行为

同一 location 配置多条 limit_req 时，请求会同时接受所有限制的检查，**实际生效的是其中限制最严格的一条**。

```nginx
location /download/ {
    # zone ip_zone：按 IP 每秒 5 个；zone global_zone：全站共享每秒 1000 个
    limit_req zone=ip_zone burst=10 nodelay;
    limit_req zone=global_zone;
}
```

- 每条 limit_req 引用不同的 zone，叠加的是不同维度的限制（按 IP 限、按全站限）。
- 请求只要触发其中最严一条的拒绝条件就会被拒绝；未被拒绝的部分按各自 zone 的速率延迟或放行。
- 典型用法是「单 IP 细粒度限制」叠加「全站总闸」，防止单 IP 限制被人用大量 IP 绕过。

> 官方文档的表述是：同一级别存在多条 limit_req 时，采用其中最严格的限制。排查「明明配了限流却没拦住」时，应逐条核对每条 limit_req 引用的 zone 与参数。



### limit_conn 并发连接数限制

limit_conn 族指令与 limit_req 平行，限制的是**同一时刻的并发连接数**而非请求频率，两者互为补充。

#### limit_conn_zone 与 limit_conn

**limit_conn_zone**：定义连接数统计区，语法与 limit_req_zone 同构；**limit_conn**：引用该区，限制每个 key 取值的并发连接数上限。

```nginx
http {
    limit_conn_zone $binary_remote_addr zone=conn_zone:10m;

    server {
        listen 80;

        location /download/ {
            # 每个 IP 同时最多 2 条连接
            limit_conn conn_zone 2;
        }

        location / {
            # 每个取到该 key 的范围同时最多 1000 条连接
            limit_conn conn_zone 1000;
        }
    }
}
```

- 超出上限的连接会被关闭并返回 limit_conn_status 指定的状态码（默认 503）。
- limit_conn 的第二个参数是数量上限，可叠加多条、按不同 key 限不同维度。
- 常与 limit_req 组合：下载站限连接数防多线程抢占，API 入口限请求数防高频调用。



#### 连接数不等于请求数

**连接数**：TCP 层面建立的链路数量；**请求数**：HTTP 层面一次请求加响应的往返次数。启用长连接或作为反向代理时，一条连接可承载多个请求。

- 反向代理场景中，客户端与 Nginx 之间一条 keepalive 长连接可能串行发送多个请求，limit_conn 统计的是连接，limit_req 统计的是请求。
- 走 HTTP/2 时，一条连接上可并行承载多个流，连接数与请求数的差距进一步拉大。
- 因此限连接挡不住「单连接高频请求」的客户端，限请求挡不住「开几百条连接慢慢下」的客户端，两者须按业务特征选用或并用。

> 速记：limit_conn 管「几条管道」，limit_req 管「管道里水流多快」。高频小请求以 limit_req 为主，大文件下载以 limit_conn 为主。



#### limit_conn_status

**limit_conn_status**：设置超出并发连接上限时返回的状态码，默认 503，可改为 429 或其他状态码，用法与 limit_req_status 一致。

```nginx
limit_conn_status 429;
```

> 被限连接与被限请求的状态码建议统一口径：全站要么都是 429，要么都是 503，便于监控按状态码聚合告警。



### 限流白名单的经典组合写法

生产上常需要「内网与合作伙伴不限流、其余全限」。经典做法是 geo 打标记、map 造空 key、limit_req_zone 以该 key 记账，三步组合实现白名单。

#### geo 与 map 的配合原理

限流 key 为**空字符串**的请求不会被 limit_req_zone 计入统计，这正是白名单的支点：先用 geo 把白名单 IP 标记为 0，再用 map 把 0 映射成空 key。

- **geo 指令**：按客户端 IP 生成一个标记变量，白名单网段赋值 0，其余默认 1。
- **map 指令**：把标记变量映射成最终限流 key——标记为 0 时映射为空串，否则取 $binary_remote_addr。
- key 为空则不记账，白名单请求完全绕过限流；key 非空则按 IP 正常限流。



#### 完整配置示例

以下为可直接运行的白名单限流完整配置：

```nginx
http {
    # 第一步：geo 给白名单 IP 打标记，命中记 0，其余记 1
    geo $limited {
        default           1;
        10.0.0.0/8        0;    # 内网网段
        192.168.0.0/16    0;    # 内网网段
        203.0.113.7       0;    # 合作方固定 IP
    }

    # 第二步：map 把标记映射为限流 key，白名单得到空 key
    map $limited $limit_key {
        0    "";
        1    $binary_remote_addr;
    }

    # 第三步：用映射后的 key 记账，空 key 的请求不计入限流
    limit_req_zone $limit_key zone=addr_zone:10m rate=10r/s;

    server {
        listen 80;

        location /api/ {
            limit_req zone=addr_zone burst=20 nodelay;
            proxy_pass http://backend;
        }
    }
}
```

- 验证方式：从白名单 IP 高频请求不触发拒绝，从普通 IP 超频后观察被拒绝的状态码，并在 error_log 中确认出现 limiting requests 字样的记录。
- 白名单条目的增减只改 geo 块，limit_req_zone 与 limit_req 无需变动。



#### 白名单方案的注意事项

该方案的有效性依赖「限流 key 确实是真实客户端 IP」这一前提。

- 站点前置 CDN 或代理时，须先用 realip 模块把 $remote_addr 还原为真实客户端地址，否则 geo 与限流都作用在错误的 IP 上。
- geo 与 map 都定义在 http 块中；map 生成的变量按需惰性求值，不使用该变量的请求几乎不付出额外开销。
- 同样的空 key 技巧也可配合登录态等变量实现「已登录用户不限流」，但作为 key 来源的变量须可靠可信。

> [!TIP]
> **建议内容**：白名单要定期收敛审计：长期累积的合作方 IP 常成为被滥用的入口。把 geo 块放在独立配置文件中由配置管理下发，配合 nginx -t 校验后 reload，比手改主配置更可控。



### allow 与 deny 访问控制

allow 与 deny 来自 **ngx_http_access_module** 模块，按客户端 IP 决定放行或拒绝，是 Nginx 最基础的访问控制手段。

#### 基本用法与首个命中生效

**allow**：放行匹配的地址；**deny**：拒绝匹配的地址。规则从上到下逐条匹配，**首个命中生效**，命中后不再检查后续规则。

```nginx
location /admin/ {
    allow 192.168.1.0/24;
    allow 10.0.0.0/8;
    deny  all;
}
```

- 地址可写单个 IP、CIDR 网段，或 all（匹配所有地址）。
- 规则顺序即优先级：上例中来自 192.168.1.0/24 与 10.0.0.0/8 的请求命中 allow 被放行，其余请求命中 deny all 被拒绝。
- 命中 deny 的请求返回 403 Forbidden。



#### deny all 兜底与典型布局

访问控制的惯用布局是「先列白名单，后用 deny all 兜底」，即允许的条目写在前面，最后一条 deny all 拒绝其余所有请求。

- 只写 allow 不写 deny all 兜底时，未匹配 allow 的请求默认放行，等于没做限制。
- 反向布局「先 deny all 后 allow」会让所有请求先命中 deny all，allow 永远轮不到生效。
- allow 与 deny 可作用于 http、server、location，各层级按自己范围内的规则组独立匹配。

> [!CAUTION]
> **注意内容**：规则顺序写反是最高频事故：deny all 写在 allow 之前，所有请求都会先命中 deny all，白名单完全失效。修改访问控制后，务必分别用白名单内与白名单外的出口 IP 各实测一次。



#### 与 auth_basic 的组合使用

**auth_basic**：HTTP 基本认证，基于用户名密码核验身份。它与 allow、deny 可叠加使用，形成「网络位置 + 账号密码」的双重防线。

```nginx
location /admin/ {
    allow 10.0.0.0/8;
    deny  all;

    auth_basic           "Admin Area";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
```

- allow、deny 在 access 阶段执行，auth_basic 在其后的认证阶段执行，两个阶段都通过，请求才能到达上游。
- 典型场景：只允许内网访问管理后台，内网用户还需输入账号密码。
- 认证文件可用 htpasswd 命令或 openssl passwd 生成，注意收紧文件权限。



### geo 与 map 指令的定位辨析

geo 与 map 都属于「按输入生成自定义变量」的指令，区分二者的关键在输入源：**geo** 按 IP 生成变量，**map** 按任意变量映射生成变量。

#### geo 按 IP 生成变量

**geo 指令**：以客户端 IP 地址为输入，按预定义的网段表输出一个变量值，专用于 IP 归类场景。

```nginx
geo $region {
    default         oversea;
    10.0.0.0/8      intranet;
    192.168.0.0/16  intranet;
}
```

- 输入只能是客户端 IP（可配合 realip 模块处理代理场景）。
- 网段表支持 CIDR 网段与单 IP，default 提供兜底值；命中即输出对应值。
- 常用于白名单标记、按网段分流、内外网区分。



#### map 按任意变量映射生成变量

**map 指令**：以任意已有变量为输入，按映射表生成新变量，输入不限于 IP。

```nginx
# 按请求头里的浏览器标识粗略判断是否移动端
map $http_user_agent $is_mobile {
    default     0;
    "~*Mobile"  1;
}
```

- 输入可以是请求头、URI、geo 的结果等任何 Nginx 变量。
- 支持正则映射（值以 ~ 开头表示区分大小写，~* 表示不区分大小写），default 提供兜底值。
- 典型用途：把请求特征映射成开关变量，供条件判断、日志、限流 key 复用。



#### 共同约束与选用原则

两者都必须写在 **http 块**中，生成的变量在被引用时才求值，二者都不能单独生效，须被其他指令消费。

- **选用原则**：输入是 IP 或网段表庞大时用 geo；输入是其他变量或需要正则映射时用 map。
- geo 可看作 map 在 IP 维度上的特化，内部按网段组织了高效索引，大规模网段表下性能优于逐条正则。
- 白名单限流场景中二者各司其职：geo 负责「识别」，map 负责「翻译成 key」。

> 速记：geo 回答「你从哪来」，map 回答「你像什么」。两者都只产变量，不产动作。



### 限流阈值的实务建议

阈值没有万能公式，本节给出从压测基线出发逐步收紧的方法论，以及全局限流与业务级限流的分工、拒绝状态码的取舍。

#### 阈值如何定：先压测后收紧

限流阈值的锚点是**系统实测容量**而非拍脑袋数字，通用流程是先压测出基线、上线宽阈值、观察指标、逐步收紧。

1. 对目标接口压测，得到单机可稳定承载的吞吐基线（响应时间与错误率同时达标时的 QPS）。
2. 初期把阈值设在基线之内并留有余量，先宽后紧，观察是否误伤正常业务。
3. 观察被限流状态码的比例与 error_log 中 limiting requests 的日志：误伤多则放宽，恶意流量占比高则收紧。
4. 阈值随上游扩缩容同步调整，避免上游扩容后网关仍按旧容量限流。

> [!IMPORTANT]
> **重要内容**：限流阈值必须写入配置管理并注明依据（压测报告、调整日期与责任人），无依据的阈值是最难维护的魔法数字。上游扩容或架构调整后不复核阈值，等于用旧地图走新路。



#### 全局限流与业务级限流的分工

Nginx 网关限流与业务应用限流应分层设防，各管一段，不要指望一层解决所有问题。

- **全局限流（Nginx 层）**：粗颗粒度、按 IP 维度，目标是挡住明显的刷子与攻击流量，保护网关与上游不被瞬时洪峰冲垮。
- **业务级限流（应用层）**：细颗粒度、按用户 ID、接口重要程度、订单价值等业务维度，目标是防止业务滥用（如单个用户超量下单）。
- Nginx 层阈值宜宽，宁可多放行、少误拦；业务层阈值可精，按用户画像差异化。
- 依赖登录态、用户等级等业务信息的限流，Nginx 变量难以表达，应交由应用层或专门的网关组件处理。



#### 返回 429 还是 503

被限流请求返回 **429**（Too Many Requests）还是 **503**（Service Unavailable）的取舍，本质是「语义准确」与「沿用默认」之间的选择。

- Nginx 的 limit_req 与 limit_conn 默认返回 503；503 的语义是服务暂不可用，调用方可能理解为「整体故障，稍后再试」。
- 429 的语义是「请求过多」，对调用方更准确，便于其执行退避重试策略，部分客户端库对 429 有内建处理。
- 通过 limit_req_status 429 与 limit_conn_status 429 即可改写，生产上改为 429 是通说推荐做法。
- 面向第三方开放的 API 建议统一返回 429，并在接口文档中写明限流策略；纯内部服务沿用 503 亦可，关键是全站口径一致。
