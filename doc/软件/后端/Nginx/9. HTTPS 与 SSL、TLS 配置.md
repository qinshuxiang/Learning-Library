## HTTPS 与 SSL、TLS 配置

### HTTPS 的基本原理

#### HTTPS 的定义与 TLS 的位置

**HTTPS**：即 HTTP over TLS，是在 **TLS**（Transport Layer Security，传输层安全协议）加密通道之上传输 HTTP 报文的协议。**TLS** 位于**传输层**与**应用层**之间：对下借用 TCP 的可靠传输能力，对上为 HTTP 提供加密与身份认证，应用层代码几乎无需改动。

- 明文的 **HTTP**：报文全程可读，链路上的任何中间人都能窃听内容、篡改页面或注入广告。
- 加密的 **HTTPS**：报文在传输前经 TLS 加密，中间人只能看到通信双方与流量大小，看不到具体内容。
- 封装顺序：应用层的 HTTP 报文先经 TLS 加密，再交给 TCP 传输，即 HTTP、TLS、TCP、IP 自上而下的分层。
- 默认端口：HTTPS 使用 443，HTTP 使用 80，Nginx 需分别监听。

> HTTPS 并不是一个新的应用层协议，而是“HTTP 套上 TLS 外壳”。因此 Nginx 配置 HTTPS 时，server 块内的 location、proxy_pass 等业务配置与 HTTP 完全相同，差异只在监听方式与证书相关指令上。

速记：**HTTPS 就是 HTTP 加 TLS**，TLS 夹在传输层与应用层之间，只管加密与认证，不改变 HTTP 语义。



#### 非对称加密与对称加密的分工

TLS 握手的核心设计是**非对称加密**与**对称加密**的分工协作：前者解决“密钥怎么安全交给对方”，后者解决“大量数据怎么快速加密”。

- **非对称加密**：公钥加密、私钥解密，安全性高但速度慢，只用于握手阶段交换密钥材料与验证签名。
- **对称加密**：通信双方使用同一把**会话密钥**加解密，速度快，用于握手完成后的全部应用数据传输。
- 握手阶段：客户端验证服务器证书并取得公钥，双方通过密钥交换算法协商出会话密钥，全程不直接传输密钥明文。
- 数据阶段：此后所有 HTTP 请求与响应都用会话密钥做对称加密，浏览器与服务器各自在内存中持有该密钥。

> 为什么不全用非对称加密？因为非对称算法的运算开销比对称算法高出一到三个数量级，一个页面动辄几十个请求，全部用非对称加密会让服务器不堪重负；而对称密钥若明文传输又会被窃听，所以必须先靠非对称加密安全地“送钥匙”，再换对称加密“干活”。**握手用非对称换钥匙，传输用对称送数据**。

速记：**握手非对称、传输对称**，先保安全、再讲效率，一段一责。



#### 证书的作用

**数字证书**：由**证书颁发机构**（CA，Certificate Authority）签发的、把**域名**与**公钥**绑定在一起的签名文件。它的作用有二：证明“这台服务器确实是该域名的主人”，以及把这个经过认证的公钥分发给客户端。

- **身份认证**：浏览器校验证书上的域名、有效期、签发链与吊销状态，防止中间人伪造服务器。
- **分发公钥**：证书内携带服务器的公钥，客户端用它完成握手阶段的密钥交换，无需线下传递。
- **防篡改**：证书内容由 CA 私钥签名，任何改动都会导致签名校验失败。
- 证书文件在 Nginx 侧是配置的输入，证书不合法时浏览器会直接拦截并告警。

> 证书解决的是“公钥属于谁”的信任问题，而不是加密本身：没有证书，攻击者可以在握手时把自己的公钥冒充给客户端（即中间人攻击），客户端毫无察觉。**证书是 HTTPS 身份认证的基石**。

速记：证书一本两职——**对内绑公钥，对外证身份**。



### 证书的类型与获取

#### 自签证书

**自签证书**：自己给自己签发的证书，签发者与使用者是同一主体，不经过任何 CA。它适合**内网服务、本地开发与测试环境**，用于公网则会被浏览器告警。

- 优点：零成本、即签即用，不依赖外部机构，适合封闭内网。
- 缺点：浏览器不信任，访问时出现“您的连接不是私密连接”之类的**安全告警**，需手动确认或导入信任。
- 生成方式：用 openssl 命令即可一行生成证书与私钥，见下方示例。
- 适用边界：通信双方是可控的机器或自己人、告警可接受时，自签证书就够用。

```bash
# 生成自签证书与私钥，CN 填服务域名或 IP，有效期 365 天
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout server.key -out server.crt \
  -subj "/CN=dev.example.local"
```

> [!WARNING]
> **警告内容**：自签证书绝不能用于对外的生产站点：访客看到的浏览器告警会直接劝退用户，长期训练用户“忽略证书告警”，还会麻痹其对真实钓鱼站点的警惕。

速记：自签证书就是**自己当 CA**，省钱包不省信任，只进内网、不上公网。



#### Let's Encrypt 与 certbot

**Let's Encrypt**：免费、自动化、开放的非营利 CA，通过 ACME 协议验证域名所有权后签发受主流浏览器信任的证书，是个人站点与中小业务获取证书的首选。

- 免费与自动化：签发、续期均免费，证书有效期为 90 天，官方的设计意图就是靠自动化工具持续续期。
- **certbot**：官方推荐的 ACME 客户端，certbot --nginx 插件能自动修改 Nginx 配置，完成证书安装与跳转改造。
- 续期：certbot 安装后自带定时任务，证书到期前自动续期，一般无需人工干预。
- 验证方式：常用 HTTP-01 验证，即 CA 访问域名下 .well-known/acme-challenge/ 目录中的文件，确认你控制该域名。

```bash
# 安装 certbot 及 nginx 插件（以 Ubuntu/Debian 为例）
sudo apt install certbot python3-certbot-nginx

# 自动申请证书并改写 nginx 配置（证书、跳转一并完成）
sudo certbot --nginx -d example.com -d www.example.com

# 演练续期流程，验证自动化链路是否健康
sudo certbot renew --dry-run
```

> certbot --nginx 会读取 nginx.conf 找到匹配 server_name 的 server 块，把证书指令写入其中，并顺手把 80 端口改为 301 跳转 HTTPS；若不想让它自动改配置，可改用 certonly 参数只取证书、手工配置。90 天有效期意味着续期任务一旦失效，三个月内证书必然过期，部署完成后务必用 renew --dry-run 演练一次。

速记：**Let's Encrypt 免费送证书，certbot 自动装到家**，90 天一轮全靠续期。



#### 证书验证等级与商业证书

按 CA 验证申请者身份的严格程度，证书分为 **DV**、**OV**、**EV** 三档：验证越严价格越高，但加密强度完全相同。

- **DV**（Domain Validation，域名验证）：只验证申请者控制该域名，几分钟即可签发，Let's Encrypt 即此类，适合个人站点与博客。
- **OV**（Organization Validation，组织验证）：额外验证企业真实性，证书中含公司信息，适合企业官网。
- **EV**（Extended Validation，扩展验证）：最严格的身份审查，适合金融类高信任场景。
- 商业证书由 DigiCert、GlobalSign 等商业 CA 收费签发，附带人工支持、通配符与多域名选项、保险赔付等增值服务。

> 无论 DV、OV 还是 EV，三种证书启用的加密算法与强度完全一致，HTTPS 的安全性不因价格而异；差异只在“证书里写入多少身份信息”与信任展示层面。**为加密强度买单没有意义，为业务信任背书买单才有意义**。

速记：**DV 验域名、OV 验组织、EV 验一切**，加密强度三者无差。



#### 证书链与中间证书完整性

**证书链**：从服务器证书出发、经一级或多级**中间证书**、最终到达浏览器内置信任的**根证书**的签名验证路径。部署时必须把中间证书一并配置，链不完整是 HTTPS 上线最常见的事故。

- 签发模型：根证书私钥离线保存，日常签发由中间证书代劳，服务器证书由中间证书签名。
- 验证过程：浏览器逐级向上验签，直到命中本地信任的根证书为止，任何一环缺失即告失败。
- 典型故障：只配服务器证书而漏配中间证书，部分手机与 curl、Java 等客户端提示证书不受信任，而开发者自己的桌面浏览器因缓存了中间证书而一切正常。
- 解决方式：向 CA 下载 fullchain（服务器证书与中间证书的合并文件）配置给 ssl_certificate。

> [!NOTE]
> **提醒内容**：Nginx 的 ssl_certificate 指令要求的正是 fullchain 文件——服务器证书在前、中间证书依次在后拼接而成；只贴证书本体不带中间证书，多数现代桌面浏览器看似正常，但移动端与命令行、Java 等客户端会报证书链错误，属于典型的“本机能访问、用户不能访问”。

速记：配置证书认准 **fullchain**，**少一环、链就断**。



### HTTPS 基础配置

#### 证书与监听的最小配置

启用 HTTPS 只需三件事：监听 443 端口并带 ssl 参数、指定证书文件、指定私钥文件。这是 Nginx HTTPS 配置的最小骨架。

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    # 其余 location、代理等业务配置与 HTTP 的 server 块完全相同
    location / {
        root /var/www/html;
    }
}
```

- **listen 443 ssl**：在 443 端口上启用 TLS，ssl 参数不可省，否则该端口按普通 HTTP 处理。
- **ssl_certificate**：指定 fullchain 证书文件路径，PEM 格式，含服务器证书与中间证书。
- **ssl_certificate_key**：指定私钥文件路径，权限应收敛到 master 进程用户可读。
- 私钥文件泄露即等于域名身份被盗，需纳入密钥管理，不可随代码仓库提交。

> [!IMPORTANT]
> **重要内容**：修改证书配置后先执行 nginx -t 校验语法，再 reload 生效；证书路径错误或私钥与证书不匹配时，reload 会失败或 443 端口无法握手。变更前备份旧证书、变更后实测一次 HTTPS 访问，应固化为标准流程。

速记：**443 加 ssl、证书加私钥**，三条指令撑起一个 HTTPS 站点。



#### 证书指令的继承与 http2

证书指令可放在 **http 块**级别，由块内多个 server 共同继承；各 server 再按需用自己的 ssl_certificate 覆盖。这是多站点共享同一张证书（如通配符证书）时的标准组织方式。

- http 块配置一次，块内未显式声明证书的 server 全部继承，消除重复。
- server 块内重新声明则就近覆盖，适合同一台机器上多个域名各持证书的情形。
- 监听指令上可追加 http2 参数（如 listen 443 ssl http2）启用 HTTP/2，其多路复用能摊薄 HTTPS 多一次握手的延迟。
- 通配符证书配合 http 块级证书，是“一台 Nginx 挂几十个子域”的常见架构。

```nginx
http {
    # http 块级默认证书，供未单独声明的 server 继承
    ssl_certificate     /etc/nginx/ssl/wildcard.example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/wildcard.example.com.key;

    server {
        listen 443 ssl http2;
        server_name a.example.com;
    }

    server {
        listen 443 ssl http2;
        server_name b.example.com;
    }
}
```

> http2 参数属于传输层升级，与证书本身无关，但实践中几乎总与 HTTPS 一起启用——主流浏览器对 HTTP/2 的支持基本限于 TLS 连接。较新版本的 Nginx 也可用独立的 http2 on; 指令表达同一含义，写法随版本而异，配置前应查阅所用版本的官方文档。

速记：**证书放 http 块共享，server 内覆盖特例**；http2 挂在 listen 上顺手开。



### 协议与算法安全

#### ssl_protocols 与旧协议禁用

**ssl_protocols**：控制 Nginx 允许使用的 TLS 协议版本。通说认为应只保留 TLSv1.2 与 TLSv1.3，明确禁用 SSLv3（受 POODLE 等攻击影响）以及 TLSv1.0 与 TLSv1.1（已过时并被主流标准废弃）。

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
```

- **SSLv3 及更早版本**：存在根本性缺陷，任何现代部署都不应启用。
- **TLSv1.0 与 TLSv1.1**：通说认为已不安全，主流合规体系早已要求禁用，主流浏览器也已停止支持。
- **TLSv1.2**：当前兼容性与安全性的主力版本，覆盖几乎所有现存客户端。
- **TLSv1.3**：握手更快、默认算法更安全，是新部署的推荐目标。

> [!WARNING]
> **警告内容**：若业务确有极老旧客户端（如某些嵌入式设备）必须依赖 TLSv1.0，也应把它隔离在独立的 server 块或独立实例中，与主站隔离风险；主站一律 TLSv1.2 起步。是否放宽的依据应来自自己的客户端访问统计，而非凭想象兼容。

速记：**协议只留 1.2 与 1.3**，SSLv3 与 1.0、1.1 是历史包袱，一律关门。



#### ssl_ciphers 与 ssl_prefer_server_ciphers

**ssl_ciphers**：限定 TLSv1.2 及以下版本可用的加密套件清单；**ssl_prefer_server_ciphers**：决定协商时以服务器还是客户端的套件偏好为准。两者共同决定“用哪套算法加密”，具体算法串时效性强，应以权威基线为准。

- ssl_ciphers 接受 OpenSSL 格式的套件列表，支持排除符号（如 !aNULL 排除不做认证的套件）。
- TLSv1.3 的套件由协议内置、单独管理，不受 ssl_ciphers 控制，无须也无法在该指令中配置。
- ssl_prefer_server_ciphers on 表示服务器清单优先；通说认为由服务端掌握选择权有利于执行统一的安全基线。
- 具体套件串更新频繁，旧推荐会随新攻击手法而失效，不宜死记硬背。

```nginx
# 示意写法：实际套件串应取自权威基线（如 Mozilla SSL Configuration Generator）
ssl_ciphers HIGH:!aNULL:!MD5;
ssl_prefer_server_ciphers on;
```

> [!TIP]
> **建议内容**：不要凭记忆手写套件串，推荐以 Mozilla SSL Configuration Generator 或 SSL Labs 的现行建议为准，生成后整体粘贴进配置，并在 SSL Labs 复测评分；启用 TLSv1.3 后该指令的影响范围仅剩 1.2 及以下。

速记：**ssl_ciphers 管菜单，ssl_prefer_server_ciphers 管谁点菜**；菜单常换，照抄权威基线。



### 会话复用

#### 会话缓存与超时

完整 TLS 握手需要一到两次网络往返并伴随大量非对称运算，**会话复用**（Session Resumption）让回访客户端跳过大部分握手、直接恢复此前的加密参数，显著降低 HTTPS 延迟与服务器 CPU 开销。

- **ssl_session_cache**：开辟存储会话参数的缓存。shared:SSL:10m 表示全体 worker 共享一块名为 SSL、大小 10m 的共享内存，回访者无论落到哪个 worker 都能命中。
- **ssl_session_timeout**：会话参数在缓存中的存活时间，超时后回访仍需完整握手，实务中常配 10m 左右。
- 效果：命中复用时握手往返减少、非对称运算省去，对移动端弱网用户的体感提升明显。

```nginx
ssl_session_cache   shared:SSL:10m;
ssl_session_timeout 10m;
```

> 使用缓存方式实现复用时，多 worker 架构务必选 shared：若用各 worker 私有的缓存，同一回访连接落在不同 worker 上就无法命中，复用率大打折扣。shared 模式的内存按需存放会话，10m 通常可容纳数万个会话，个人与中型业务足够。

速记：**shared 缓存全员共享，timeout 决定保多久**，复用一次就省一次完整握手。



#### 会话票据及其争议

**ssl_session_tickets**：以**会话票据**（Session Ticket）方式实现会话复用——服务器把加密后的会话状态发给客户端，客户端回访时原样带回，服务器解密即恢复会话，服务器侧无需保存任何状态。

- 优点：零存储、天然适配多机部署与负载均衡，任何一台持有相同票据密钥的机器都能恢复会话。
- 争议：票据密钥若长期不轮换，**前向安全性**被削弱——密钥一旦泄露，历史会话可被解密；多机共享密钥又带来分发与管理成本。
- 实务分歧：安全基线严格的团队选择关闭票据、只留缓存；追求多机无状态复用的团队保留票据并做定期轮换。
- Nginx 默认开启该选项，而其对票据密钥轮换的支持长期有限，这也是不少安全基线直接建议 off 的原因。

```nginx
ssl_session_tickets off;
```

> [!NOTE]
> **提醒内容**：票据与缓存是两条并行的复用路径，可并存：缓存要求服务器存有会话记录，票据则把状态挪到客户端。对单机个人站点，只留 shared 缓存、关掉票据，是省心又符合常见安全基线的取舍。

速记：**缓存存服务端，票据揣客户端**；票据省内存但密钥要轮换，不轮换就关掉。



### OCSP stapling

#### 证书吊销查询与 OCSP 概念

证书在有效期内也可能被吊销（如私钥泄露），**OCSP**（Online Certificate Status Protocol，在线证书状态协议）用于向 CA 实时查询“这张证书是否已被吊销”。传统方式由浏览器逐个查询，**OCSP stapling** 则改为服务器主动代劳。

- 传统 OCSP：浏览器握手时另发查询请求到 CA 的 OCSP 服务，增加延迟；CA 服务器由此得知哪些用户在何时访问了哪些站点，带来隐私问题。
- **OCSP stapling**：服务器定期从 CA 取回带签名的吊销状态响应，握手时随证书“钉”（staple）在一起发给浏览器，浏览器本地即可完成验证。
- 收益：省去浏览器到 CA 的额外往返；查询行为由服务器完成，用户访问隐私不外泄给 CA。
- 前提：CA 必须支持 OCSP 服务且证书在有效期内，stapling 才有意义。

> OCSP stapling 的本质是把“浏览器逐次问 CA”改成“服务器定期问一次、转手钉给所有人”，**查询一次、复用万人**。它不改变吊销判断的标准，只改变谁去问、何时问。

速记：**staple 就是钉**——服务器把吊销状态钉在证书旁，浏览器免跑 CA 一趟。



#### Nginx 的 OCSP stapling 配置

Nginx 通过 ssl_stapling 系列指令启用该特性，核心三项：开启 stapling、开启响应验证、配置 DNS 解析器。

```nginx
ssl_stapling        on;
ssl_stapling_verify on;

# OCSP 服务器地址记录在证书的 AIA 扩展中，是一个域名，解析依赖 resolver
resolver 8.8.8.8 8.8.4.4 valid=300s;
resolver_timeout 5s;
```

- **ssl_stapling on**：启用 stapling，Nginx 在握手时附带 OCSP 响应。
- **ssl_stapling_verify on**：对取回的 OCSP 响应做签名与证书链验证，防止附带的内容本身被伪造。
- **resolver**：OCSP 服务器地址写在证书扩展里，是一个域名，Nginx 必须能解析它才能查询，漏配 resolver 是 stapling 不生效的最常见原因。
- 验证效果：可用 openssl s_client 观察握手是否携带证书状态，或用 SSL Labs 报告确认。

> [!WARNING]
> **警告内容**：只写 ssl_stapling on 而不配 resolver，Nginx 拿不到 OCSP 服务器地址，stapling 静默失效——握手照常成功，只是不附带吊销状态，全程没有任何报错。另外，自签证书与部分 CA 签发的证书不支持 OCSP，启用前先确认证书具备该能力。

速记：**stapling 三件套：on、verify、resolver**，缺 resolver 等于白开。



### HTTP 跳转与 HSTS

#### 80 端口自动跳转的标准写法

HTTP 流量迁移到 HTTPS 的标准做法是：单独写一个只监听 80 端口的 server 块，把全部请求以 301 永久重定向指到 HTTPS，443 块专心处理加密业务。

```nginx
server {
    listen 80;
    server_name example.com;

    # 所有 HTTP 请求 301 永久跳转到同路径的 HTTPS 地址
    return 301 https://$host$request_uri;
}
```

- **return 301**：永久重定向，浏览器与搜索引擎会记住新地址，比 302 临时跳转更利于 SEO。
- **$host**：取自请求的 Host 头，保证跳转目标域名与用户访问的一致。
- **$request_uri**：原始请求的路径与查询串，保证路径与参数原样保留。
- 独立 server 块的写法让 80 与 443 职责分离，避免在业务块里堆判断逻辑。

> [!TIP]
> **建议内容**：跳转块里除了 return 不应再放 root、index 等业务配置；certbot --nginx 若已自动生成跳转，核对其写法等价即可。全站只保留一层 301，跳转套跳转会拖慢首访并干扰搜索引擎收录。

速记：**80 端口只做一件事：return 301 https://$host$request_uri**，host 保域名、uri 保路径。



#### HSTS 响应头

**HSTS**（HTTP Strict Transport Security，HTTP 严格传输安全）：通过响应头 Strict-Transport-Security 告诉浏览器——在指定时长内访问本域名一律强制 HTTPS，即使用户手输 http:// 也在本地直接改写为 https://，不给中间人劫持跳转的机会。

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
```

- **max-age**：策略生效秒数，上例为一年；期间浏览器对站点的一切访问强制 HTTPS。
- **includeSubDomains**：策略覆盖全部子域，a.example.com 与 b.example.com 一并强制。
- **preload**：表示申请加入浏览器内置的 HSTS 预载列表，让首次访问就受保护，需另行提交申请。
- 生效链路：浏览器收到该头后在本地记忆策略，之后的访问不再经过服务器跳转，直接发起 HTTPS。

> [!CAUTION]
> **注意内容**：HSTS 一旦下发便难以撤回：max-age 期间内，浏览器会拒绝该域名的任何合法 HTTP 访问与不受信任的证书。若证书过期未续、或某个子域仍需 HTTP，用户将看到无法跳过的拦截页。上线前先以较小的 max-age 试运行，确认全站与全部子域 HTTPS 就绪后，再逐步加大到一年并考虑 includeSubDomains 与 preload。

速记：HSTS 三参数——**max-age 管时长、includeSubDomains 管子域、preload 管首访**；下发容易，收回极难。



### 全站安全基线

#### 隐藏版本与证书到期监控

HTTPS 之外，还应配合几项基础加固指令，构成最低限度的安全基线，其中 server_tokens off 是第一步。

- **server_tokens off**：响应头与错误页中不再暴露 Nginx 版本号，收敛被针对性利用的信息面。
- 证书到期监控：证书过期是最常见也最尴尬的事故，应把到期时间纳入监控告警（各类拨测与 uptime 服务均可探测证书剩余有效期）。
- 最小化协议与套件：沿用前文的 ssl_protocols 与 ssl_ciphers 基线，不随意叠加。
- 变更流程：配置变更一律先 nginx -t 校验，再走灰度 reload，避免一次性全量变更。

```nginx
server_tokens off;
```

> [!IMPORTANT]
> **重要内容**：certbot 的自动续期依赖定时任务正常运行，部署完成后务必执行 certbot renew --dry-run 演练一次；并在监控中为证书到期时间设置提前告警（实务中常设提前两周至一个月），把“发现过期”变成“收到提醒”。

速记：**关版本号、盯到期日、锁协议基线**，三件事构成 HTTPS 站点的日常巡检项。



#### SSL Labs 评分自测

**SSL Labs**（ssllabs.com）提供的免费在线评测，会对站点的 HTTPS 配置打分（A 到 F），并逐项列出协议、套件、证书链、吊销机制的问题，是 HTTPS 配置上线后的标准自测手段。

- 测评维度：证书有效性、协议版本、套件强度、会话复用、OCSP stapling、HSTS 等十余项。
- 评分用法：以 A 为合格线逐项排查扣分点，每修一项复测一次；追求 A+ 通常还需 HSTS 与 preload。
- 补充工具：openssl s_client 可手工观察握手细节，curl -vI 可验证跳转与响应头。
- 适用范围：在线测评面向公网站点，内网地址无法直接测，可参考相同配置的公网环境结果。

> [!TIP]
> **建议内容**：把“SSL Labs 达到 A”写进 HTTPS 变更的验收标准：每次调整协议、套件或证书后复测一次，评分与扣分明细留档，形成配置变更与安全评分一一对应的可追溯记录。

速记：**改完 HTTPS 必测 SSL Labs**，A 是及格线，扣分项即整改清单。
