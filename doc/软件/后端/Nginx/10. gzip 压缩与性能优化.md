## gzip 压缩与性能优化

### HTTP 压缩的原理

#### 内容协商机制

**HTTP 压缩**：服务器对响应正文压缩后传输、浏览器解压后呈现的机制，双方通过请求头 **Accept-Encoding** 与响应头 **Content-Encoding** 完成协商。

- 客户端在请求头 Accept-Encoding 中声明自己支持的压缩格式，如 gzip、deflate、br。
- 服务器从中选择一种格式压缩正文，并在响应头 Content-Encoding 中标注实际所用格式。
- 浏览器读到 Content-Encoding 后按对应算法解压，再进入渲染流程，整个过程对页面代码透明。
- 若客户端不支持任何压缩格式，服务器应回退为不压缩的原文传输。

```http
# 请求：客户端声明可接受的压缩格式
GET /app.js HTTP/1.1
Host: example.com
Accept-Encoding: gzip, deflate, br

# 响应：服务器标注实际使用的压缩格式
HTTP/1.1 200 OK
Content-Type: application/javascript
Content-Encoding: gzip
```

> 协商是“客户端申报、服务器拍板”的单向选择过程：Accept-Encoding 只是意愿清单，最终用什么格式、甚至压不压缩，决定权都在服务器。**Content-Encoding 标了什么，浏览器就按什么解压**，两边不对齐就会出现乱码。

速记：**Accept-Encoding 是申报，Content-Encoding 是定案**。



#### 收益与成本

压缩的收益是传输体积大幅缩小，成本是压缩与解压消耗的 CPU，是否开启与怎么配，本质是拿服务端 CPU 换带宽与加载时间的权衡。

- 收益：文本类资源（HTML、CSS、JS、JSON、SVG）重复度高，压缩后体积通常下降六到九成，弱网与移动端受益最明显。
- 成本：每次响应都要实时压缩，压缩级别越高 CPU 消耗越大，高并发场景下压缩可能成为 CPU 瓶颈。
- 不宜压缩的内容：图片、视频等本身已压缩的格式再压几乎无收益，纯浪费 CPU。
- 折中手段：热点静态资源可用预压缩（见 gzip_static 一节）把压缩成本从运行期挪到构建期。

> [!TIP]
> **建议内容**：判断该不该压缩的最快方法是抓一次响应对比：对同一资源分别观察压缩前后的体积与 $request_time，若体积下降明显而 CPU 占用可忽略，就值得开；对已压缩的图片、视频类资源保持不压，避免双输。

速记：**文本大赚、媒体白赔**，压缩赚的是带宽，赔的是 CPU。



### gzip 指令组详解

#### gzip 开关与压缩级别

gzip 指令组的总开关是 **gzip**，压缩深度由 **gzip_comp_level** 控制，取值 1 到 9：数字越大压缩率越高、耗时越长。实务中 5 或 6 被普遍视为压缩率与 CPU 的性价比拐点。

```nginx
gzip on;
gzip_comp_level 6;
```

- **gzip on**：启用 gzip 压缩，可置于 http、server、location 任意层级。
- **gzip_comp_level 1**：压缩最快、压缩率最低，适合 CPU 紧张的高并发动态响应。
- **gzip_comp_level 9**：压缩率最高但耗时成倍增长，相比 6 的体积收益通常很小，性价比差。
- 实务结论：静态资源交给预压缩时可以放心用 9；运行期实时压缩选 5 或 6 即可。

> 从 1 到 9 压缩率的提升是边际递减的：级别 6 相比级别 1 体积往往显著缩小，而 9 相比 6 的额外收益常不足几个百分点，CPU 耗时却明显增加。**运行期压缩不值得为最后几个百分点买单**，把级别 9 留给构建期的预压缩脚本。

速记：**实时压缩 5 或 6，预压缩才配谈 9**。



#### gzip_min_length 最小压缩阈值

**gzip_min_length**：设置启用压缩的最小响应字节数，小于该值的响应原样返回。其判断依据是响应头 Content-Length，该头不存在的响应不受限制、按可压缩处理。

```nginx
gzip_min_length 1k;
```

- 太小的响应压缩后可能不降反升（压缩头开销占比高），设阈值可避免负收益。
- 常见取值：1k 是个人站点的常见起点，接口与动态内容较多的服务可放宽到 10k。
- 依据来源：阈值应基于自家最小资源实测调整，而非照抄模板。
- 边界：判断基于 Content-Length，分块传输（chunked）的响应绕过该判断。

> [!NOTE]
> **提醒内容**：gzip_min_length 只拦“小到不值得压”的响应，不是性能开关——阈值设得过大，会让本可压缩的中等体积文本裸奔传输；拿不准时从 1k 起步，观察日志再微调。

速记：**小于阈值不压，Content-Length 说了算**；1k 起步、按需调大。



#### gzip_types 类型白名单

**gzip_types**：指定除 HTML 之外额外压缩的 MIME 类型白名单。关键事实是 Nginx 默认只压缩 text/html，CSS、JS、JSON 等一概不压，必须手工补进白名单。

```nginx
gzip_types text/css application/javascript application/json
           image/svg+xml text/plain text/xml;
```

- 默认行为：仅 text/html 被压缩，且它无须写进 gzip_types（写了一般也无害）。
- 必补清单：text/css、application/javascript、application/json、image/svg+xml 是最常见的四类文本资源。
- 补充类型：XML 的 text/xml、RSS 的 application/rss+xml 等，按业务需要补充。
- 写法要求：类型名必须与响应的 Content-Type 完全一致，写错等于没配。

> [!WARNING]
> **警告内容**：图片（jpeg、png、webp）、视频（mp4 等）以及 zip、gz 等本身已压缩的文件不要再加进 gzip_types：它们的字节已高度随机，二次压缩几乎不减体积，却照样消耗 CPU，还可能让部分客户端处理变慢。判断标准只有一条——Content-Type 是文本才压，二进制与已压缩格式一律不压。

速记：**默认只压 HTML，文本类型靠白名单补**；媒体与压缩包碰都不要碰。



#### gzip_vary 与 gzip_buffers

**gzip_vary** 让压缩响应追加 Vary: Accept-Encoding 头，告知代理与缓存“同一 URL 会按客户端能力返回不同版本”；**gzip_buffers** 则指定压缩时使用的内存缓冲块数量与大小。

```nginx
gzip_vary on;
gzip_buffers 16 8k;
```

- **gzip_vary on**：等价于给每个压缩响应补 Vary: Accept-Encoding，是接入 CDN 与代理缓存的前置条件。
- 缺 Vary 的后果：中间缓存可能把压缩版发给不支持 gzip 的客户端（乱码），或把未压缩版缓存下来反复回源。
- **gzip_buffers**：压缩时的内存缓冲区，16 8k 表示 16 块 8k；不配置时 Nginx 按页面大小取默认值。
- 调整时机：仅当压超大响应且要控制内存占用时才需要动它，绝大多数场景保留默认。

> gzip_buffers 属于“不配也对、配错才坏”的指令：缓冲区小于实际需要时，Nginx 会回退磁盘临时文件反而更慢。保留默认、把精力花在 gzip_types 与压缩级别上，是更划算的投入。

速记：**gzip_vary 是给缓存看的说明书**；buffers 默认即可，少动为妙。



#### gzip_proxied 代理请求策略

**gzip_proxied**：决定对“带代理特征”的请求（响应来自上游而非 Nginx 本地文件）是否压缩，参数按响应的缓存特征逐项开关。

- off（默认）：来自代理的响应一律不压缩。
- any：代理响应一律压缩，最省心的取值。
- no-cache、no-store、private、no_last_modified、no_etag、auth：仅在响应具备对应缓存特征（如带 no-cache）或属于对应情形（如请求带 Authorization）时压缩。
- 背景逻辑：上游可能已压缩过响应（此时 Nginx 不再压），或响应是不该缓存的私有数据，压了缓存层也用不上。

```nginx
# 接口网关类站点常用：代理响应全部压缩
gzip_proxied any;
```

> [!NOTE]
> **提醒内容**：Nginx 只压缩上游未压缩的响应——若上游已返回带 Content-Encoding 的响应，gzip_proxied 无论配什么都不生效。反向代理 Java、Node 等应用时，先确认应用自身是否已开压缩，避免两头重复压或两头都不压。

速记：**proxied 管代理来的响应，默认不压**；要压就 any，上游已压则无效。



### 静态预压缩 gzip_static

#### gzip_static 的原理与配置

**gzip_static**：开启后 Nginx 对每个请求先查找同目录下的同名 .gz 文件（如请求 app.js 就找 app.js.gz），存在则直接以 Content-Encoding: gzip 返回，不存在再回退普通流程，实现“构建期压缩、运行期零压缩成本”。

```nginx
location /static/ {
    root /var/www/site;
    gzip_static on;
}
```

- 前置条件：.gz 文件由构建或发布流程生成，与源文件同目录、同名。
- 收益：运行期完全不做压缩运算，省下的 CPU 直接转化为并发能力；响应路径只剩磁盘读与网络发送。
- 参数差异：on 表示存在 .gz 就用、没有就回退；always 表示无论如何优先用 .gz（源文件可以不存在）。
- 典型组合：前端构建产物整体预压缩加 gzip_static on，是静态站点性价比最高的方案。

```bash
# 发布前为构建产物批量生成 .gz（-k 保留源文件，-9 最高压缩率）
find dist -type f \( -name "*.js" -o -name "*.css" -o -name "*.svg" \) \
  -exec gzip -9 -k {} \;
```

> [!TIP]
> **建议内容**：预压缩文件会多占一份磁盘空间，且必须在发布流水线里保证 .gz 与源文件同版本同步更新——漏了这一步，用户会拿到旧版本的 .gz。把生成 .gz 固化为构建脚本的一个步骤，不要靠人工执行。

速记：**构建期压好、运行期白拿**；gzip_static on 加构建脚本，静态站的最优解。



#### 与动态压缩的取舍

**动态压缩**（gzip on）与**预压缩**（gzip_static on）是互补而非互斥的两条路，选择取决于内容是静态可枚举还是每次请求都不同。

- 静态资源（构建产物、文档、下载包）：一律预压缩，级别可用 9，运行期零成本。
- 动态响应（API JSON、服务端渲染页面）：只能实时压缩，级别控制在 5 或 6 以内。
- 混合站点：两者同时开启互不冲突，gzip_static 先在文件类 location 生效，gzip 管其余响应。
- 收益排序：先开动态 gzip 拿大头收益，再对热点静态资源上预压缩抠运行期成本。

> 一条实务分界线：**能提前生成的内容就提前压，请求时才存在的内容才实时压**。把级别 9 的 CPU 开销从运行期挪到构建期，是压缩优化里收益最确定的一步。

速记：**静态预压、动态实时**，两条腿各走各的路。



### Brotli 压缩

#### Brotli 的概念与协商方式

**Brotli**：由 Google 设计的通用压缩格式（HTTP 内容编码标识为 br），对文本的压缩率普遍高于同级别 gzip，协商机制与 gzip 完全相同——客户端在 Accept-Encoding 中带上 br，服务器以 Content-Encoding: br 响应。

- 协商与 gzip 走同一套 Accept-Encoding、Content-Encoding 机制，只是格式标识换成 br，主流现代浏览器均已支持。
- Nginx 侧：官方核心不包含 Brotli，需安装第三方模块（如 ngx_brotli），指令组为 brotli、brotli_comp_level 等，风格与 gzip 指令组一致。
- 压缩表现：通说认为同等内容下 Brotli 比 gzip 再省一成到两成体积，压缩耗时也更高。
- 共存策略：二者可同时启用，按协商结果分别服务不同客户端，互不干扰。

```nginx
# 第三方 ngx_brotli 模块的典型配置（示意）
brotli on;
brotli_comp_level 5;
brotli_types text/css application/javascript application/json image/svg+xml;
```

> Brotli 不是官方发行版的组成部分，模块版本与主程序版本需自行维护：升级 Nginx 时要重新编译或同步升级模块，使用发行版包管理器的部署接入第三方模块也更繁琐。能否引入，先看团队是否愿意承担这部分维护成本。

速记：**br 比 gzip 更省流量**，但它是第三方模块，多一份能力也多一份维护。



#### 生产启用的权衡

是否在生产启用 Brotli，取决于流量结构、CPU 余量与运维成本的权衡：通说认为纯静态资源站点收益明确，动态为主的小站点收益有限。

- 明确受益：静态资源为主、带宽成本敏感、且走预压缩（brotli_static）的站点，构建期压缩可无视运行期 CPU。
- 谨慎评估：动态响应实时 Brotli 压缩的 CPU 开销高于 gzip，高并发下可能得不偿失。
- 运维成本：第三方模块的编译、升级、兼容性检查是长期负担。
- 渐进路线：先把 gzip 配置做对，其收益已覆盖绝大部分场景，Brotli 属于锦上添花。

> [!NOTE]
> **提醒内容**：压缩优化的优先级排序是：先把 gzip 开对（类型白名单补全），再做静态预压缩，最后才轮到 Brotli。多数站点的 gzip 配置缺口（如没补 JS 与 JSON 类型）带来的损失，远大于换用 Brotli 的收益。

速记：**gzip 没配对，别谈 Brotli**；先补课，再升级。



### 与 CDN 和上游的配合

#### 双重压缩问题

**双重压缩**：同一份响应在链路上被两个环节先后压缩，客户端解一层后拿到的仍是压缩数据。接入 CDN 或反向代理后，压缩可能发生在链路的多个环节，需要显式管理。

- 成因：上游应用已压缩，Nginx 或 CDN 未识别又压一次；客户端只解最后一层，中间各层白白消耗 CPU 与带宽。
- Nginx 的内建保护：上游响应已带 Content-Encoding 时，Nginx 的 gzip 不再处理；gzip_proxied 只对未压缩的代理响应生效。
- CDN 的行为差异：部分 CDN 默认对源站响应再做压缩或解压，需在控制台核对压缩与透传策略。
- 排查思路：从客户端逐层向上核对每一跳的 Content-Encoding 与压缩开关，最怕两层都“以为对方压了”。

```nginx
# 对照排查：对可疑路径临时关闭 gzip，确认压缩发生在哪一层
location /api/ {
    proxy_pass http://backend;
    gzip off;
}
```

> [!IMPORTANT]
> **重要内容**：排查“部分用户拿到乱码或拿到未压缩响应”时，第一步是核对全链路各层（客户端到 CDN、CDN 到源站、源站到上游）的压缩开关与 Content-Encoding：每一层要么压且标对，要么明确不压；最危险的状态是两层都默认对方已处理。

速记：**一条链路只压一层**；上游已带 Content-Encoding 时，Nginx 自动放手。



#### Vary 头的作用

**Vary**：HTTP 响应头，告诉缓存层“缓存键除 URL 外还要纳入指定请求头”。压缩场景下指 Vary: Accept-Encoding，声明同一 URL 会按客户端能力返回压缩或未压缩的不同版本。

- 作用机制：缓存层（代理、CDN）看到 Vary: Accept-Encoding 后，按每个客户端的 Accept-Encoding 值分别缓存与命中，版本不串发。
- 缺失后果：不支持 gzip 的客户端可能收到缓存里的压缩版（乱码），或压缩请求命中未压缩缓存导致反复回源。
- Nginx 配置：gzip_vary on 即自动追加该头，是接入 CDN 与代理缓存的前置条件。
- 透传要求：CDN 与代理自身也要把 Vary 正确透传给下游，任何一层丢头都会破坏协商。

> gzip_vary on 的成本是一个几十字节的响应头，收益却是全链路缓存版本的正确性，属于“必开”级别；个别老旧 CDN 对 Vary 的处理不完善，接入前应实测缓存行为。

速记：**Vary 是缓存的分版本说明书**，缺了它压缩版与原文会串门。



### 连接与传输层优化

#### keepalive 的超时与请求数

**keepalive**（长连接）让一条 TCP 连接在多个 HTTP 请求间复用，省去每个请求重复 TCP 握手与 TLS 握手的开销；Nginx 用 **keepalive_timeout** 与 **keepalive_requests** 两个指令控制其生命周期。

```nginx
keepalive_timeout  65s;
keepalive_requests 1000;
```

- **keepalive_timeout**：连接空闲多久后关闭，期间下一个请求可直接复用；过短则复用率低，过长则空闲连接堆积占用句柄。
- **keepalive_requests**：单条连接最多承载的请求数，达到上限即关闭，防止单条连接长期占用，也让客户端有机会重建连接。
- 与 HTTPS 的叠加收益：TLS 握手比 TCP 更昂贵，长连接对 HTTPS 的提速尤其明显，与上一章的会话复用配合效果更佳。
- 与第 5 章的呼应：反向代理到上游的 keepalive 连接池（upstream 块内配置）是另一套独立机制，别与此处混淆。

> [!TIP]
> **建议内容**：keepalive_timeout 的取值应低于负载均衡器与防火墙的空闲连接超时，否则连接被中间设备静默掐断，客户端会拿到连接重置错误；实务中 65s 或 75s 是 HTTP/1.1 下的常见取值。迁移 HTTP/2 后该参数的重要性下降，因为 HTTP/2 本身就是多路复用。

速记：**timeout 管闲多久断，requests 管最多传几个**；HTTPS 时代长连接更是刚需。



#### sendfile 三件套

**sendfile** 让文件数据在内核态直接从磁盘送到网卡，跳过用户态拷贝；与 **tcp_nopush**、**tcp_nodelay** 搭配构成静态文件传输的三件套，与第 5 章的静态服务配置形成呼应。

```nginx
sendfile     on;
tcp_nopush   on;
tcp_nodelay  on;
```

- **sendfile on**：启用零拷贝路径，文件响应不再经过用户空间缓冲，CPU 占用与延迟双降。
- **tcp_nopush on**：在 sendfile 开启时把响应头与文件首个数据块攒在一次发送，提升网络利用率。
- **tcp_nodelay on**：禁用 Nagle 算法，小包立即发送，降低交互类响应的延迟（keepalive 连接下默认开启）。
- 适用范围：三者主要惠及静态文件与大响应传输，纯代理场景的收益要看响应是否走文件路径。

> 三件套是“几乎总该全开”的基线配置；更细的调优（如大文件场景下的 sendfile_max_chunk）属于专项优化，普通站点保持全开即可，不必逐个实验。

速记：**sendfile 省拷贝、nopush 攒着发、nodelay 立刻发**，静态传输三连开。



#### client_max_body_size 与 413 错误

**client_max_body_size**：限制客户端请求体的最大字节数，超出即返回 **413**（Request Entity Too Large），是上传接口最常见的“莫名其妙 413”的根源。

```nginx
# 全局默认与上传接口的差异化配置
client_max_body_size 1m;

server {
    listen 80;
    server_name upload.example.com;

    location /api/upload/ {
        client_max_body_size 100m;
    }
}
```

- 默认值：未配置时为 1m，上传稍大的文件或携带大 JSON 的接口请求就会被拒。
- 生效层级：可配在 http、server、location 任意层级，就近覆盖，适合“全局收紧、上传口放开”的策略。
- 与代理的关系：作为反向代理时需与上游应用的限制（如框架的 multipart 上限）协调，取不冲突的组合。
- 排查入口：日志中 413 状态码集中出现的路径，就是该放宽的位置。

> [!NOTE]
> **提醒内容**：413 的频次是配置是否合理的直接信号：偶发 413 多为正常拒绝恶意大包，集中出现的 413 说明阈值低于真实业务需求。放宽阈值时同步评估连接占用与磁盘写入压力，不要无限放大。

速记：**413 就是 body 超了 client_max_body_size**；全局 1m 起步，上传口单独放大。



### worker 与系统层优化

#### worker_processes auto 的取值

worker 进程是 Nginx 干活的主体，其数量决定并发处理能力的上限；本章只做简要复述，详细的进程模型见第 2 章。

- **worker_processes auto**：worker 数自动等于 CPU 核数，是通说认可的最优默认值。
- 显式写死数字的弊端：机器迁移、容器扩缩容后配置与硬件脱节，auto 则始终跟随实际核数。
- 单核容器或虚拟机中 auto 同样正确，不必因核数少而改回写死写法。
- worker 数不是越大越好：超过核数的 worker 只会增加进程切换开销。

```nginx
worker_processes auto;
```

> worker 数量之外，每个 worker 内部靠事件驱动同时承载数千连接，因此“worker 等于核数、连接靠事件循环扛”才是 Nginx 并发模型的全貌；连接层的天花板则由文件描述符上限决定，见下一考点。

速记：**worker_processes 无脑 auto**，写死数字是历史包袱。



#### worker_rlimit_nofile 与系统 ulimit

**worker_rlimit_nofile**：设置 worker 进程可打开文件数的运行时上限，须与操作系统的 **ulimit** 限制协调一致，单改 nginx.conf 不一定生效。

```bash
# 查看当前 shell 的文件描述符上限
ulimit -n

# 查看某个正在运行的 nginx worker 实际生效的上限
cat /proc/$(pgrep -o nginx)/limits | grep "open files"
```

```nginx
worker_rlimit_nofile 65535;
```

- 每一条连接至少占用一个文件描述符，代理场景还要加上游连接；上限不足时报 too many open files，直接拒绝新连接。
- 配套检查：/etc/security/limits.conf 与 systemd 服务的 LimitNOFILE 都可能构成真正的天花板，实际生效的是其中最小的那个。
- 容量经验：让 nofile 上限明显大于预估峰值连接数，代理场景按两倍以上估算。
- 验证方式：压测中观察 worker 进程的 limits 与错误日志，确认无文件描述符耗尽。

> [!IMPORTANT]
> **重要内容**：worker_rlimit_nofile 设得再大，若系统 ulimit 或 systemd 的 LimitNOFILE 更小，实际生效的是更小的那个值。改完配置务必用 /proc 下对应进程的 limits 文件复核，并在压测中确认无 too many open files 报错，才算闭环。

速记：**nofile 取三方最小值**——nginx.conf、ulimit、systemd 谁小听谁的；要大就三处一起改。



### 优化方法论

#### 先测量再优化

性能优化的第一原则是**先测量、后动手**：没有定位到瓶颈的调参都是碰运气，Nginx 自带的日志字段就是最低成本的测量工具。

- **$request_time**：Nginx 从收到请求第一个字节到发完响应的全程耗时，包含客户端上传与网络传输。
- **$upstream_response_time**：上游应用返回响应的耗时，代理场景下与 $request_time 之差即 Nginx 自身与传输的耗时。
- 判读方法：两者都高——瓶颈在应用；仅 $request_time 高、差值大——瓶颈在 Nginx 或传输环节（大文件、缺压缩、缺 sendfile）。
- 采集方式：自定义 log_format 把两个时间字段落盘，再统计 P95、P99 分位数，均值会掩盖长尾。

```nginx
log_format timing '$remote_addr "$request" $status '
                  'rt=$request_time urt=$upstream_response_time';

access_log /var/log/nginx/access_timing.log timing;
```

> [!TIP]
> **建议内容**：任何性能改动（开压缩、调 keepalive、换 sendfile）都应走“改前采样、改后采样、对比分位数”的闭环；$request_time 与 $upstream_response_time 的差值变化，是判断 Nginx 层优化是否见效的最直接证据。

速记：**rt 看全程，urt 看上游，两者相减就是 Nginx 自己的账**。



#### 基准建议清单

以下清单是 Nginx 压缩与性能配置的一组基准起点，多数站点可直接采用，再按测量结果微调。

```nginx
# 压缩
gzip on;
gzip_comp_level 6;
gzip_min_length 1k;
gzip_types text/css application/javascript application/json image/svg+xml;
gzip_vary on;
gzip_proxied any;

# 静态预压缩（构建产物已含 .gz 时）
gzip_static on;

# 传输与连接
sendfile on;
tcp_nopush on;
tcp_nodelay on;
keepalive_timeout 65s;
keepalive_requests 1000;
client_max_body_size 1m;

# 进程与文件描述符
worker_processes auto;
worker_rlimit_nofile 65535;
```

- 起点配置以稳为目标：全部取通说认可的保守值，不追求极限。
- 每一项调整前先测量、调整后复测，让配置与数据一一对应。
- 与安全相关的协议、套件、证书配置见上一章，两者合并即一份完整的生产基线。

> [!IMPORTANT]
> **重要内容**：基准清单是起点不是终点——照抄模板后放任不管，与从不优化的区别只是起点不同；真正拉开差距的是持续测量、按业务特征迭代配置的闭环习惯。

速记：**先抄基准，再按测量改**；清单管起点，测量管终点。
