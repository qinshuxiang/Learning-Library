## Rewrite 与重定向

### 外部重定向与内部重写

#### 外部重定向与内部重写的定义

**外部重定向**：服务器返回 301、302 等状态码并附上新地址，由浏览器重新发起新请求访问新地址的处理方式。**内部重写**：服务器在内部把请求的 URI 改写成另一个路径后继续处理，全程只有一次请求、客户端无感知的处理方式。

- **外部重定向**：浏览器地址栏变化，产生两次请求，第一次响应返回 301 或 302 与新地址。
- **内部重写**：浏览器地址栏不变，自始至终只有一次请求，路径的变换完全发生在服务器内部。
- 两者都改变请求实际命中的资源，区别在于改变的环节发生在客户端还是服务端。

> 判定口诀：响应里出现 301 或 302、浏览器要再发一次请求，就是外部重定向；响应直接就是最终内容、地址栏纹丝不动，就是内部重写。



#### 两者的行为对比

外部重定向与内部重写在请求次数、地址栏表现、使用目的上逐项不同，选型前先明确目的。

- 请求次数：外部重定向两次（旧地址一次、新地址一次）；内部重写一次。
- 地址栏：外部重定向变为新地址、用户可见；内部重写保持原地址、用户无感。
- 典型目的：外部重定向用于域名迁移、HTTP 跳 HTTPS、旧链接维护；内部重写用于 URL 美化、把对外友好路径映射到内部真实路径。
- 性能影响：外部重定向多一次往返；内部重写无额外往返。

```nginx
# 外部重定向：浏览器会再请求一次新地址
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;
}

# 内部重写：服务器内部换成 /files/... 继续处理，客户端无感
location /download/ {
    rewrite ^/download/(.*)$ /files/$1 break;
}
```

> [!NOTE]
> **提醒内容**：内部重写后的新路径会重新参与 location 匹配（配合 last 标志时），但这一切都在服务器内部完成，客户端自始至终只发了一次请求——这是理解 last 与 break 行为的前提，后文展开。



### return 指令

#### return 的语法与常用写法

**return 指令**：立即停止处理并向客户端返回指定状态码、可选附带正文或重定向地址的指令，属于 ngx_http_rewrite_module 模块。

- return 301 URL;：返回 301 并跳转到指定地址，URL 通常拼接 $request_uri 以保留原路径。
- return 302 URL;：返回 302 临时跳转，语义见下一节。
- return 200 "文本";：直接以指定状态码返回一段文本，常用于健康检查端点或简单占位。
- return 也可只写状态码（如 return 403;），或状态码加正文，写法灵活。

```nginx
server {
    listen 80;
    server_name old.example.com;

    # 301 永久跳转，$request_uri 保留原路径与参数
    return 301 https://new.example.com$request_uri;
}

server {
    listen 8080;

    # 健康检查端点：直接返回文本
    location = /healthz {
        return 200 "ok";
    }

    location /admin/ {
        # 拒绝未授权访问，直接给状态码
        return 403;
    }
}
```

> return 写在 server 块内时对整个虚拟主机生效，写在 location 内时只对该 location 生效；范围取决于它的位置，这也是它能承担整站跳转的原因。



#### return 的中断语义

return 一旦执行，当前上下文中后续的所有处理立即终止，不再执行 rewrite 序列、不再做任何请求转发，这是它与 rewrite 最本质的行为差异之一。

- 执行即终止：同一 location 中写在 return 之后的 rewrite、proxy_pass 等指令都不会再执行。
- 不发起重匹配：return 不改写 URI，也不触发重新匹配 location，直接把响应交还给客户端。
- 因此 return 是终局型指令：要么给出最终响应，要么给出跳转地址，二者必居其一。

```nginx
location /demo/ {
    # return 命中后，下面的 rewrite 与 proxy_pass 都不会执行
    return 301 https://example.com/moved;

    rewrite ^/demo/(.*)$ /new/$1 last;
    proxy_pass http://backend;
}
```

> return 之后的指令属于死代码：Nginx 不报错，但永不执行。阅读他人配置时先扫 return，能迅速判断一段 location 的真实走向。



### 301 与 302 的语义差异

#### 301 永久重定向

**301**：永久移动（Moved Permanently），告知客户端该资源已永久迁移到新地址、此后应直接访问新地址的重定向状态码。

- 浏览器会缓存 301 结果：同一地址再次访问时，多数浏览器不再请求旧地址，直接按本地缓存跳往新地址。
- 搜索引擎会把旧地址的权重逐步转移到新地址，是域名迁移、URL 结构调整的标准选择。
- 副作用来自缓存本身：一旦设置错误，即使改好配置，用户浏览器仍可能按缓存跳往错误地址，必须清缓存或强刷才能恢复。

```nginx
# 域名永久迁移
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;
}
```

> [!CAUTION]
> **注意内容**：误用 301 是实务中最常见的重定向事故：跳转目标写错后，浏览器与搜索引擎都会长期记住错误结果，即使清了浏览器缓存，公共缓存与搜索引擎收录的恢复也可能以周计。对不确定是否永久的跳转，先用 302 过渡，确认无误后再改 301。



#### 302 临时重定向

**302**：临时移动（Found），告知客户端本次请求被临时引到新地址、原地址仍然有效、浏览器不应缓存该跳转关系的重定向状态码。

- 浏览器不缓存 302：每次访问旧地址都会重新向服务器确认，跳转关系随时可以收回。
- 适用于过渡期场景：活动页临时切换、维护期间引流、尚未确定的迁移先以 302 观察。
- SEO 影响与 301 相反：搜索引擎不转移权重，旧地址的收录与排名保持不变。

```nginx
# 活动期临时引流，活动结束后删掉这条配置即可
location = /promo {
    return 302 https://example.com/promo-2026;
}
```

> 通说的选型法则：**永久搬迁用 301，临时跳转用 302，拿不准时先 302**。302 用错损失的是一次跳转往返，301 用错损失的是长期缓存，风险完全不对称。



#### 307 与 308

**307** 与 **308**：后续 HTTP 规范补充的两个重定向状态码，核心特征是重定向时保持原请求方法不变。

- 307 是 302 的严格版：临时重定向且不得把 POST 改成 GET；308 是 301 的严格版：永久重定向且保持请求方法。
- 传统 301、302 在历史上被浏览器实现为跳转时把 POST 降级为 GET，307 与 308 修正了这一行为。
- Nginx 中可直接写 return 307 URL; 与 return 308 URL;；日常 Web 页面跳转仍以 301、302 为主，涉及表单提交或 API 转发时才需要 307、308。

```nginx
location = /api/legacy {
    # 保持 POST 方法原样跳转，避免方法被降级为 GET
    return 308 https://example.com/api/v2;
}
```

> 速记：301 永久、302 临时、307 临时且保持方法、308 永久且保持方法；四者按永久与临时、是否保持方法两个维度一组记忆即可。



### rewrite 指令

#### rewrite 的语法与匹配对象

**rewrite 指令**：用正则表达式匹配当前 URI 并替换为新 URI 的指令，语法为 rewrite 正则 替换串 flag;，同属 ngx_http_rewrite_module 模块。

- 正则作用于 $uri：即不含查询参数的路径部分，写正则时不要把问号后面的内容算进去。
- 替换串默认自动继承原查询参数：重写后原参数自动拼在新路径后面，无需手工处理。
- 替换串以问号结尾可丢弃原参数：写成 /new? 表示重写后不保留原有参数。
- 捕获组：正则中的圆括号捕获的内容，在替换串中以 $1、$2 引用。

```nginx
server {
    # 原参数自动继承：/a?x=1 重写后内部为 /b?x=1
    location = /a {
        rewrite ^/a$ /b last;
    }

    # 替换串以问号结尾：丢弃原参数，/a?x=1 重写后内部为 /b
    location = /old {
        rewrite ^/old$ /new? last;
    }

    # 捕获组引用：路径片段搬移
    location /download/ {
        rewrite ^/download/(.*)$ /files/$1 break;
    }
}
```

> rewrite 匹配的是不含参数的路径，这一事实最容易出错：想用正则匹配查询参数里的内容是不可能的，参数的处理要靠 $args、$arg_name 等变量在替换串中完成。



#### 四个 flag 的行为

rewrite 的行为由末尾的 flag 决定，四个标志分别是 **last**、**break**、**redirect**、**permanent**：前两者是内部行为，后两者产生外部重定向。

- **last**：停止当前这一轮 rewrite 指令序列，用改写后的新 URI 重新发起 location 匹配（仍在服务器内部）。
- **break**：停止当前 rewrite 序列，并且不重新匹配 location，停留在当前 location 内继续处理。
- **redirect**：返回 302 临时重定向，浏览器地址栏可见新地址。
- **permanent**：返回 301 永久重定向，效果等同 return 301。
- 不写 flag 时：继续执行当前 location 中后续的 rewrite 指令，序列走完后按新 URI 重新匹配 location；隐式行为不易预测，生产中建议总是显式写 flag。

```nginx
server {
    # last：重写后重新匹配 location（内部）
    location = /a {
        rewrite ^/a$ /b last;
    }
    location = /b {
        return 200 "hit /b";
    }

    # break：重写后停在原地继续处理（配合 root 取文件）
    location /pics/ {
        root /data;
        rewrite ^/pics/(.*)$ /store/$1 break;
    }

    # redirect 与 permanent：外部重定向
    location /old/ {
        rewrite ^/old/(.*)$ /new/$1 redirect;        # 302
    }
    location /legacy/ {
        rewrite ^/legacy/(.*)$ /classic/$1 permanent;  # 301
    }
}
```

> [!IMPORTANT]
> **重要内容**：redirect 与 permanent 是四个 flag 中仅有的两个外部重定向标志，last 与 break 都是内部行为。另有一条隐式规则：替换串以 http://、https:// 或 $scheme 开头时，处理停止并直接向客户端返回跳转，即使不写 redirect 或 permanent 也是如此。



### last 与 break 的区别

#### 行为差异与判定

last 与 break 都会停止当前 rewrite 序列，唯一区别是 **last 用新 URI 重新走一遍 location 匹配，break 不重新匹配、原地继续处理**。

- **last**：重写后的 URI 会重新参与 location 匹配，可能进入完全不同的 location 块。
- **break**：重写到此终止，请求留在当前 location 内，用改写后的 URI 完成后续处理（如读取静态文件）。
- 选择标准：看改写后的路径该由谁来处理——交给别的 location 处理用 last，由当前 location 处理完用 break。

```nginx
server {
    # last：/a 重写为 /b 后重新匹配，命中 location = /b
    location = /a {
        rewrite ^/a$ /b last;
    }
    location = /b {
        return 200 "由 /b 的 location 处理";
    }

    # break：/clean/1 重写为 /raw/1 后原地取文件，不重新匹配
    location /clean/ {
        root /data;
        rewrite ^/clean/(.*)$ /raw/$1 break;
    }
}
```

> 高频考点一句话：**last 重新匹配 location，break 停在当前 location**。静态文件场景误用 last，改写后的 URI 可能落进其他 location 造成 404；需要二次路由的场景误用 break，请求永远出不了当前块。



#### 与 root、proxy_pass 的搭配惯例

last 与 break 的选择与 location 内部最终由谁处理有关，实务中围绕 root 与 proxy_pass 形成了稳定惯例。

- root 静态文件场景：改写只是为了换一个磁盘路径，由当前 location 自己完成，惯例用 break。
- proxy_pass 反向代理场景：想让当前 location 直接把改写后的 URI 转给后端，用 break；想让改写后的 URI 重新匹配到其他 location 再处理，用 last。
- 多条 rewrite 链：链中间用 last 传递、最后一条落地用 break，是较常见的组织方式。

```nginx
# 静态文件：break 原地取文件
location /images/ {
    root /data;
    rewrite ^/images/(.*)$ /store/$1 break;
}

# 反向代理：break 后把改写好的 URI 交给后端
location /api/ {
    rewrite ^/api/(.*)$ /$1 break;
    proxy_pass http://app_pool;
}
```

> 惯例之外的判断方法：问自己改写后的 URI 还需不需要再挑一次处理者——需要就 last，不需要就 break；拿不准时先写 break，出问题再看是否需要重新匹配。



### rewrite 与 return 的选型

#### 能用 return 不用 rewrite

选型通说：**能用 return 表达的跳转就不要用 rewrite**——return 语义直白、行为可预测，rewrite 依赖正则与 flag，出意外的面更大。

- return 适合：固定地址的跳转、状态码直返、整站搬迁——路径无需计算时 return 全部覆盖。
- rewrite 适合：需要正则捕获、路径变换、参数重组的场景，这些计算 return 表达不了。
- 可读性差异：return 301 https://new.example.com$request_uri; 一眼可懂；等价的 rewrite 写法多一层正则与 flag 的认知负担。

```nginx
# 推荐：固定跳转用 return
server {
    listen 80;
    server_name old.example.com;
    return 301 https://new.example.com$request_uri;
}

# 不推荐的等价写法：能用 return 时绕道 rewrite，多一层正则
# rewrite ^/(.*)$ https://new.example.com/$1 permanent;
```

> 通说依据：rewrite 的隐式规则多——默认继承参数、不写 flag 时序列续跑、替换串以 http:// 开头时自动跳转，每条都可能造成意外；return 没有这些分支。**显式优于隐式，能 return 不 rewrite**。



#### rewrite 不可替代的场景

return 写不了带捕获组的路径变换，凡是要算出新路径的场景，仍是 rewrite 的领地。

- 路径美化：把 /article/1 这类对外路径映射到内部真实路径，必须靠正则捕获完成。
- 批量搬迁：旧 URL 结构到新 URL 结构有规律可循（如目录改名）时，一条 rewrite 覆盖全部，无需逐条 return。
- 参数重组：结合 $args、$arg_name 把查询参数拼进新路径或新参数串。

```nginx
# 对外 /article/1，内部交给动态脚本处理
location / {
    rewrite ^/article/(\d+)$ /index.php?id=$1 last;
}
```

> [!TIP]
> **建议内容**：审查配置时的实操法则：先找 return——所有固定跳转都应收敛为 return；剩下的 rewrite 才是需要逐条核对正则与 flag 的部分。这样能快速把跳转类配置与路径计算类配置分开审查。



### if 指令与 if is evil

#### if 指令的语法与风险

**if 指令**：按条件决定是否执行块内指令的控制结构，语法为 if (条件) { ... }，属于 rewrite 模块；社区通说以 if is evil 概括其风险——if 与多数指令组合时行为可能出乎意料。

- 风险由来：if 在 location 内并非按直觉顺序执行，它与该 location 其余内容（如 proxy_pass、静态文件处理）的交互，在不同场景下会产生意外结果，这是 nginx 官方开发者在社区反复强调的著名问题。
- 基本安全的组合：if 块内只写 rewrite 模块自己的指令——return、rewrite、set——通说认为这类用法安全可靠。
- 高危组合：if 块内写 proxy_pass、root 等内容处理器类指令，是意外行为的高发区。

```nginx
# 高危写法示意（仅示意，生产勿用）：if 内写内容处理器指令
# if ($http_user_agent ~ MSIE) {
#     proxy_pass http://ie_backend;
# }
```

> [!WARNING]
> **警告内容**：if is evil 的准确含义是 if 与块外其他指令的组合可能产生意外行为，而非 if 语法本身有缺陷；最危险的是在 location 的 if 块内写 proxy_pass、root 等内容处理类指令。把 if 块内的指令收敛为 return、rewrite、set 三类，风险即可控。



#### 生产环境的安全写法

生产中 if 的安全用法集中在两类：server 层判断 host 做整站跳转、用 set 改写变量后再交给 location 处理。

- server 层 if 判断 host：块内只有 return，是官方示例与实务公认的写法，用于多域名收敛。
- if 加 set：条件满足时改写变量，由后续 location 依据变量决定行为，规避在 if 内写内容处理器。
- 能用多个 server 块按 server_name 拆分表达的，优先拆 server 块，而不是在单个 server 内堆 if。

```nginx
server {
    listen 443 ssl;
    server_name example.com www.example.com;

    # server 层 if：块内只有 return，公认安全
    if ($host = www.example.com) {
        return 301 https://example.com$request_uri;
    }

    location / {
        root /data/www;
    }
}
```

> 判断一条 if 是否安全的最快标准：块内指令是否只有 return、rewrite、set。是则放行；否则重构——要么拆 server 块，要么改用 map 指令映射变量后再在 location 中使用。



### 经典场景集

#### HTTP 自动跳 HTTPS

HTTP 自动跳 HTTPS 的标准做法：单独一个 80 端口的 server 块，内部一句 return 301 把全部请求引到 HTTPS。

- 结构：80 端口的 server 只做跳转，443 端口的 server 承载真实业务，职责分离。
- 保留原路径与参数：跳转地址拼接 $request_uri，用户访问的页面在跳转后原样保持。

```nginx
# 80 端口：专职跳转
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

# 443 端口：真实业务
server {
    listen 443 ssl;
    server_name example.com;

    location / {
        root /data/www;
    }
}
```

> 用 if 判断 $scheme 再跳转的写法也能实现同样效果，但多一个 if 就多一分风险；独立 server 块加一句 return 是更简单也更安全的通说做法。



#### www 域名与裸域互跳

www 与裸域只能对外暴露一个规范域名，另一个统一 301 到规范域名，避免搜索引擎视为两个站点而分散权重。

- 先定规范域名：业务上二选一（本例定裸域 example.com 为规范域名）。
- 再做收敛：非规范域名的请求整站 301 到规范域名，路径与参数原样保留。
- 实现方式：独立 server 块写 server_name 加 return 301，通常不需要 if。

```nginx
# 非规范域名：整站跳到规范域名
server {
    listen 443 ssl;
    server_name www.example.com;
    return 301 https://example.com$request_uri;
}

# 规范域名：承载业务
server {
    listen 443 ssl;
    server_name example.com;

    location / {
        root /data/www;
    }
}
```

> [!NOTE]
> **提醒内容**：收敛方向（www 跳裸域，还是裸域跳 www）没有标准答案，选定后长期保持一致即可；SEO 层面重要的是全站只有一个规范域名，而不是选了哪一个。



#### URL 美化

URL 美化是把对外友好的路径在服务器内部改写为真实处理路径的内部重写应用，用户看到的永远是美化后的地址。

- 典型形态：/article/1 在内部改写为动态脚本的查询路径，浏览器地址栏保持 /article/1。
- 用内部重写而非外部重定向：美化属于路径映射，不应增加请求往返，也无需暴露内部实现。
- flag 通常用 last：改写后的内部路径需要重新匹配 location，交给对应的处理块。

```nginx
location / {
    # /article/1 在内部变为 /index.php?id=1，浏览器无感
    rewrite ^/article/(\d+)$ /index.php?id=$1 last;
}

location ~ \.php$ {
    # 动态脚本处理块（示意，需配合 FastCGI 参数等完整配置）
    fastcgi_pass 127.0.0.1:9000;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    include fastcgi_params;
}
```

> 美化的本质是内部重写：对外 URL 结构与内部实现解耦，内部脚本或框架换掉时，对外地址可以不变——这是 URL 设计中地址稳定原则在 Nginx 层的落地。



#### 查询参数的保留与丢弃

查询参数在 rewrite 与跳转中是否保留、如何拼接，由 $args、$is_args、$request_uri 等变量的配合决定。

- rewrite 默认继承原参数：替换串末尾不加问号时，原参数自动拼到新路径后面。
- 替换串末尾加问号丢弃原参数：写成 /new? 即表示重写后不带原参数。
- 手动拼接：$is_args 在有参数时展开为问号、无参数时为空，配合 $args 可精确控制拼接。
- 跳转保路径：return 的目标地址拼接 $request_uri，原路径与参数整体带过去。

```nginx
server {
    # rewrite 默认保留参数：/s?kw=nx 到 /search?kw=nx
    location = /s {
        rewrite ^/s$ /search last;
    }

    # 丢弃原参数：/logout?from=xx 到 /home，不带 from
    location = /logout {
        rewrite ^/logout$ /home? permanent;
    }

    # 跳转中整体保留：路径与参数都交给 $request_uri
    location = /legacy-entry {
        return 301 https://new.example.com$request_uri;
    }
}
```



#### uri 与 request_uri 的选用辨析

**$uri**：当前请求已解码、且会被 rewrite 不断改写的路径变量（不含参数）。**$request_uri**：客户端原始请求的完整 URI，含参数、未经解码、从不被 rewrite 改变。

- 内部改写逻辑用 $uri：rewrite 的正则匹配的就是它，捕获组也来自它。
- 跳转保留原地址用 $request_uri：无论之前发生过多少次内部改写，它始终是用户最初请求的完整地址。
- 关键差异：$uri 已做 URL 解码，$request_uri 保留编码原样——拼跳转地址时用错变量，会把解码后的内容再拼进 URL，产生畸形链接。

```nginx
server {
    listen 80;
    server_name old.example.com;

    # 跳转用 $request_uri：保留用户最初访问的完整地址
    return 301 https://new.example.com$request_uri;
}
```

> 速记：**跳转找 $request_uri（原始完整、含参数、不变），改写找 $uri（已解码、会被改写、不含参数）**。跳转场景错用 $uri 的典型症状：路径中的编码字符被提前解码，且拿到的是中间改写结果而非用户原始请求。
