## SQL 分类与书写规范

### SQL 语句的五大分类

**SQL 语句按功能分为五大类**：DDL、DML、DQL、DCL 与 TCL，每类对应数据库生命周期中的一类操作，认清归属有助于理解权限体系与日志行为。

- DDL 管结构：库、表、索引、视图的定义与删除
- DML 管数据：插入、更新、删除
- DQL 管查询：SELECT 及其配套子句
- DCL 管权限：用户的创建、授权与回收
- TCL 管事务：提交、回滚与保存点

> 五类划分是教学与工程上的习惯用法，并非 SQL 标准的强制约束；SHOW 一类辅助命令通常不归入五类。判断一条语句属于哪类，看它改变的是结构、数据还是权限。

**速记**：五类各管一摊，**结构 DDL、数据 DML、查询 DQL、权限 DCL、事务 TCL**。

#### DDL：数据定义语言

**DDL**：操作数据库对象结构的语言，改动的是“表长什么样”而不是“表里有什么”。

- 代表语句：CREATE、ALTER、DROP、TRUNCATE
- 作用对象：数据库、表、索引、视图、存储过程
- 多数 DDL 在 MySQL 中会引发**隐式提交**，无法用事务回滚
- 大表上执行 ALTER 可能长时间锁表，需谨慎评估

> TRUNCATE 虽然清空的是数据，但按 DDL 处理：重置自增值、触发隐式提交、不能回滚。把它当 DML 使用是常见误区。

**速记**：DDL 动结构，**改表即改库，多数不可回滚**。



#### DML：数据操作语言

**DML**：操作表内数据的语言，改变的是“表里有什么”。

- 代表语句：INSERT、UPDATE、DELETE
- 三者都会写入 binlog 与 redo log，可随事务回滚
- UPDATE 与 DELETE 不带 WHERE 会作用于全表，是高危操作
- 批量操作建议分批执行，避免长事务与锁扩散

> 开启 sql_safe_updates 后，不带索引条件的 UPDATE 与 DELETE 会被拒绝，是生产环境的常用保险。

**速记**：DML 动数据，**无 WHERE 不动手，分批防长事务**。



#### DQL：数据查询语言

**DQL**：从表中读取数据的语言，核心是 SELECT。

- 只读不写，是使用频率最高的一类
- 由 SELECT 与 FROM、WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 等子句组合而成
- 执行顺序与书写顺序不同：先 FROM、再 WHERE、再分组过滤、最后排序分页
- 查询优化的全部工作都围绕这一类展开

> 严格按 SQL 标准划分时 SELECT 属于 DML 的读取部分；本系列按国内教程惯例单列为 DQL，两种口径都对，知道即可。

**速记**：DQL 只读不写，**书写有顺序，执行另有其序**。



#### DCL：数据控制语言

**DCL**：管理用户与权限的语言，决定“谁能对什么做什么”。

- 代表语句：CREATE USER、GRANT、REVOKE
- 权限可细到全局、库、表、列四个层级
- 生产系统遵循最低权限原则，应用账号只授予必要权限
- root 账号只用于管理，不用于业务连接

> DCL 语句多数同样触发隐式提交；在事务中途授权，事务会被悄悄提交。

**速记**：DCL 管权限，**最小授权，root 不下放**。



#### TCL：事务控制语言

**TCL**：控制事务边界的语言，决定一组语句是“一起算”还是“不算”。

- 代表语句：BEGIN、COMMIT、ROLLBACK、SAVEPOINT
- 配合 SET autocommit 控制自动提交行为
- 保存点允许回滚到事务中的某个中间位置
- 事务相关原理在 31 与 33 篇专门展开

> 隔离级别设置（SET TRANSACTION ISOLATION LEVEL）通常也归入此类，它决定并发事务互相看见什么。

**速记**：TCL 圈边界，**要么全成，要么全不算**。



### 注释与语句结束

#### 三种注释写法

**MySQL 支持三种注释**：单行两种、多行一种，各有适用场景。

- 单行注释一：两个连字符加空格，即 -- 注释内容
- 单行注释二：井号开头，即 # 注释内容，MySQL 方言
- 多行注释：斜杠星号包裹，即 /* 注释内容 */，可嵌在语句中间
- -- 后必须有空格才被识别为注释，紧跟字符会被当运算符

> 可移植性优先用 -- 与 /* */，它们是 SQL 标准；# 是 MySQL 独有方言，迁移到其他数据库时会失效。

**速记**：注释三式，**双横扛加空格、井号方言、斜杠星跨行**。



#### 分号结束语句

**分号是语句的结束标志**：客户端据此切分并逐条发送语句。

- 交互式客户端中每条语句以分号收尾才会执行
- 存储过程与触发器体内含多条语句，定义时需先 DELIMITER 换结束符
- 脚本文件中一行一条分号结尾，便于逐行排错
- 漏写分号时客户端会显示续行提示符等待输入

> 在图形化工具中单条执行可以省略分号，但养成写分号的习惯能避免迁移到脚本与命令行时踩坑。

**速记**：分号即句读，**过程体里先换界**。



### 书写惯例

#### 关键字大写与标识符小写

**行业主流惯例是关键字大写、库表列名小写**：读语句时一眼分清“语法”与“对象”。

- SELECT、FROM、WHERE 等关键字全大写
- 库名、表名、列名统一小写加下划线，即蛇形命名
- Linux 下 MySQL 默认区分表名大小写（lower_case_table_names=0），混用大小写在跨平台迁移时会出错
- 列名与关键字同名时用反引号包裹，属例外而非常态

> 大小写本身不影响语法正确性，但影响可读性与可移植性；团队内统一比个人偏好更重要。

**速记**：**关键字大写、对象小写、蛇形命名**，跨平台不受大小写拖累。



#### 缩进与换行

**多子句语句竖向排版**：每个主要子句独占一行，长条件缩进续行。

- SELECT 列清单、FROM、WHERE、GROUP BY、ORDER BY、LIMIT 各占一行
- 列较多时一行一列，逗号放行尾或行首，团队内统一
- 长的 AND/OR 条件换行缩进，逻辑块对齐
- 嵌套子查询逐层缩进，让层次一目了然

> 排版不影响执行，只影响协作；评审他人 SQL 时，竖向排版的 diff 更容易看清改动点。

**速记**：**一子句一行，嵌套逐层缩**。



#### 命名规范

**命名规范解决的是可读与不冲突**：让后来者见名知义、不踩保留字。

- 表名用业务语义名词，如 orders、order_items，避免拼音与缩写堆砌
- 列名避免与关键字同名，如 order、desc、type 尽量绕开
- 布尔语义列用 is_ 前缀，如 is_deleted
- 时间列统一命名习惯，如 created_at、updated_at
- 索引名按 idx_列名、唯一索引 uk_列名的约定组织

> 表名用单数还是复数没有对错，国际上两大流派并存；关键是全库统一，不混用。

**速记**：**见名知义、绕开保留字、全库统一**。



#### 别名 AS

**AS 为列或表起临时名字**：让输出可读、让自连接可行。

- 列别名：SELECT price * count AS total，AS 可省略但建议保留
- 表别名：FROM orders AS o，多表连接与自连接必备
- 别名可用的位置有讲究：GROUP BY 与 ORDER BY 可用，WHERE 不可用
- 原因是执行顺序：WHERE 先于 SELECT 求值，别名那时还不存在

> 别名一经定义，同层语句中应统一使用别名而非原表名，混写会降低可读性。

**速记**：**列名表名皆可别，WHERE 里用不了**。



### 常用辅助命令

#### SHOW 系列查看元数据

**SHOW 命令族是元数据查询的快捷入口**：不写系统表也能看清库表现状。

- SHOW DATABASES：列出所有库
- SHOW TABLES：列出当前库的表，可加 LIKE 过滤
- SHOW CREATE TABLE 表名：看建表语句原文，含引擎与字符集
- SHOW VARIABLES LIKE 'xxx'：查系统变量
- SHOW WARNINGS：看最近一条语句的告警

> SHOW CREATE TABLE 输出的建表语句可直接复制执行，是核对结构与生成文档的利器；更系统的方式是查 information_schema，两者互补。

**速记**：SHOW 看元数据，**建表语句一把抓**。



#### DESC 查看表结构

**DESC 是查看表结构的缩写**：一秒看清列、类型、键与默认值。

- 完整写法为 DESCRIBE 表名，DESCRIBE 与 DESC 等价
- 输出五列：字段名、类型、是否允许 NULL、键、默认值与额外信息
- Extra 列会显示 auto_increment、DEFAULT_GENERATED 等信息
- 与 SHOW COLUMNS FROM 等价，本质是同一查询的简写

> DESC 只有结构没有索引详情；查索引用 SHOW INDEX FROM 表名，两者配合使用。

**速记**：DESC 看五列，**结构一屏尽收**。



#### USE 选择数据库

**USE 切换当前默认库**：之后的表名可以省略库前缀。

- USE 库名后，表名可不带库名直接访问
- 不切换则必须写 库名.表名 全限定形式
- 查看当前所在库用 SELECT DATABASE()
- 脚本开头显式 USE，可避免连错库写错数据

> 多库联合查询时，建议所有表都写全限定名，读语句的人不必回头猜当前库是哪个。

**速记**：USE 定当前库，**脚本开头先定位**。



### 一条 SQL 的执行路径

#### 服务端处理流程概览

**一条 SQL 从连接到返回要经过四站**：连接器、分析器、优化器、执行器，理解路径才能定位慢在哪一环。

- 连接器：校验用户名密码，管理连接与权限快照
- 分析器：词法与语法分析，识别语句结构与表列
- 优化器：选择索引、决定连接顺序，生成执行计划
- 执行器：按计划调用存储引擎接口取数
- 引擎层（如 InnoDB）负责真正读写数据页

> 以上是 Server 层与引擎层的分工概览；8.0 已移除查询缓存，命中缓存的老路径不复存在，讨论执行路径时不必再提缓存层。

**速记**：**连接、分析、优化、执行**四站，引擎收尾。



#### 词法与语法分析

**分析器把字符流变成语法树**：先切词、再验结构。

- 词法分析：把整串字符切成关键字、标识符、常量等记号
- 语法分析：按 SQL 语法规则检查记号序列，构建语法树
- 表或列不存在、关键字拼写错误都在此阶段报错
- 报错信息会指出大致出错位置，是排错第一现场

> 语法分析不验证业务语义：列存在但类型不匹配、权限不足等问题要到更晚的阶段才暴露。

**速记**：先切词再验法，**错在此处的多是拼写与名字**。



#### 优化器选择执行计划

**优化器决定“怎么执行最快”**：同一语句可有多种执行方式，它挑一种。

- 决定用哪个索引、多表连接的驱动顺序
- 依据是统计信息（索引区分度、行数估算）与代价模型
- 统计信息不准会导致选错索引，这是偶发慢查询的常见根源
- EXPLAIN 展示的就是优化器的最终决定（详见 30 篇）

> 优化器选错时可用 FORCE INDEX 人工干预，但那是止血手段；根本解法是修正统计信息或改写语句。

**速记**：优化器挑路，**估错行数走错路**。



#### 执行器调用引擎

**执行器按计划逐步取数**：循环调用引擎接口，校验权限后返回结果。

- 先判断用户对目标表是否有操作权限
- 按计划调用引擎的读取接口，逐行过滤条件
- 结果集边取边发给客户端，不一次性攒全
- 写操作同理，逐行调用引擎写入并记日志

> Server 层管流程与函数计算，引擎层管存取与事务；两层配合的细节在 5 篇体系结构中已展开，此处建立整体图景即可。

**速记**：执行器流水线，**权限先验、逐行取送**。
