## 排序与分页

### ORDER BY：排序

#### 单列与多列排序

**ORDER BY 决定结果集的输出顺序**：多列排序从左到右依次生效。

- 语法：ORDER BY 列1 [ASC|DESC], 列2 [ASC|DESC]
- ASC 升序是默认值，可省略；DESC 降序须显式写
- 多列排序时，前一列相同的行才按后一列排
- 列可写名字、别名、位置序号或表达式

> 位置序号（ORDER BY 2）写起来短，但列顺序一变语义就变，评审时还得多看一层；工程代码统一用列名或别名。

**速记**：**多列左优先，升序可省略，降序要写全**。

```sql
SELECT name, price, stock
FROM products
ORDER BY stock DESC, price ASC;
```



#### 按别名与表达式排序

**ORDER BY 在 SELECT 之后执行**：所以它能用别名，也能用表达式。

- SELECT price * 0.9 AS discounted ... ORDER BY discounted 合法
- 也可直接对表达式排序：ORDER BY price * 0.9
- WHERE 不能用别名的同一根因反过来说明了这里为什么可以
- 排序发生在结果集即将返回之前

> 与 WHERE 的时序差异值得记住一张执行顺序图：FROM、WHERE、GROUP BY、HAVING、SELECT、ORDER BY、LIMIT。别名诞生于 SELECT，因此只在它之后的子句可用。

**速记**：**别名生在 SELECT，身后才有 ORDER BY**。



#### NULL 的排序位置

**MySQL 把 NULL 当最小值**：升序排最前，降序排最后。

- 升序时 NULL 行排在所有非空值之前
- 想让 NULL 沉底：ORDER BY col IS NULL, col，空值标记列排后
- 想让 NULL 置顶：ORDER BY col IS NULL DESC, col
- 8.0 尚不支持标准 SQL 的 NULLS FIRST/LAST 语法

> IS NULL 返回 0 或 1，把它当第一排序键就是给空值分组；这一招简单可靠，是 NULLS 语法缺失时代的标准替代品。

**速记**：**NULL 最小，IS NULL 当开关挪位置**。



#### FIELD 自定义顺序

**FIELD 函数按给定清单排序**：让状态值按业务顺序输出。

- FIELD(col, 'v1', 'v2', ...) 返回 col 在清单中的位置，不在则 0
- ORDER BY FIELD(status, 'pending', 'paid', 'shipped') 按流程顺序排
- 不在清单中的值统一为 0，排最前（升序时）
- 本质是给每行算一个数字再排序，无法利用索引

> 自定义顺序状态少时用 FIELD 直观；状态多或顺序常变时，老老实实在字典表加排序列，别把业务顺序硬编码进每一条查询。

**速记**：FIELD **按清单发号，号小排前，索引无缘**。



#### ORDER BY 与索引

**排序键与索引序一致就免排序**：不一致就是 filesort。

- 索引列顺序与 ORDER BY 完全一致（含方向）时可跳过排序
- 混合 ASC 与 DESC 在 8.0 支持降序索引之前难走索引
- 排序列带函数、类型不一致同样失效
- EXPLAIN 的 Extra 出现 Using filesort 即内存或磁盘排序

> filesort 不一定慢：行数少时内存排序瞬间完成；大结果集上的 filesort 才是需要消灭的目标。结合 LIMIT 只取头部时，索引序的价值最大。

**速记**：**排序贴索引免排，Extra 见 filesort 再掂量**。



### LIMIT：分页

#### LIMIT 两种形态

**LIMIT 控制返回条数与起点**：单参取前 N，双参跳 N 取 M。

- LIMIT 10：返回前 10 行
- LIMIT 偏移, 条数：跳过偏移行，返回条数行
- 等价写法 LIMIT 条数 OFFSET 偏移，语义更显式
- 与 ORDER BY 配合才有稳定的“第 N 页”

> 无排序的 LIMIT 分页在并发写入下页与页会重叠或漏行：行集顺序没定义，两次查询的分界自然不稳。分页必须先定序，通常用唯一键兜底（如 ORDER BY id）。

**速记**：**双参先跳后取，分页先排序才稳定**。

```sql
-- 第 3 页，每页 20 条
SELECT * FROM orders
ORDER BY id
LIMIT 40, 20;
```



#### 分页公式与边界

**页码换算成偏移量是一个减法**：第 n 页每页 s 条，偏移 (n-1) 乘 s。

- 偏移量 = (页码 - 1) × 每页条数
- 应用层把页码、每页条数参数化，防止越界大数
- 每页条数设上限（如 100），防止恶意大页拖库
- 总页数需要额外 COUNT 查询，大表上同样要优化

> COUNT 加 LIMIT 的组合让一次分页变成两条查询；总数不必每次精确，缓存总数或只显示“下一页”按钮，都是大表分页的常见减负手段。

**速记**：**偏移等于页减一乘页大小，条数设上限**。



### 深分页：性能与解法

#### 深分页为什么慢

**LIMIT 1000000, 20 要先扫出一百万行再扔掉**：代价全在丢弃上。

- 偏移越大，扫描越多，延迟线性恶化
- 即使有索引，回表一百万次同样致命
- EXPLAIN 的 rows 显示扫描估算，偏移大时触目惊心
- 用户很少翻到深页，但爬虫与导出任务会

> 深分页慢的根源是“跳过也须读取”：索引知道从哪开始，但偏移语义逼它数完前 N 行。解法都是同一个思路——把“数到第 N 行”改成“直接定位到第 N 行”。

**速记**：**深页慢在白扫，偏移就是丢弃量**。



#### 子查询定位法

**先查起始主键，再从主键往后取**：扫描量从 N 行降到 20 行。

- 第一步：SELECT id FROM 表 ORDER BY id LIMIT 偏移, 1 取起始 id
- 第二步：SELECT ... WHERE id 大于等于 起始id ORDER BY id LIMIT 条数
- 两步都走主键，无回表浪费
- 延迟只与每页条数相关，与页码无关

> 该法要求排序列是唯一且有序的（主键最合适）；排序列非唯一时“跳过 N 行取 1 行”的位置不稳定，页间可能重叠。

**速记**：**先拿起点主键，再向后翻页，扫描与页码脱钩**。

```sql
SELECT * FROM orders
WHERE id >= (SELECT id FROM orders ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 20;
```



#### 游标式分页

**记住上一页末尾的位置，下一页从那里继续**：偏移量彻底消失。

- 上一页返回最大 id，下一页 WHERE id 大于该值 ORDER BY id LIMIT 20
- 只能顺序翻页，不能随机跳页
- 无重叠无遗漏，写入并发下也稳定
- 接口形态为游标 token，业内通用做法

> 游标分页是 Feed 流、导出任务的标准答案；需要跳页的产品交互则退回子查询定位法或限制最大页深。两种方案按交互形态选，不必二选一。

**速记**：**游标续翻页，WHERE 大于上页尾**。

```sql
-- 下一页：上一页末尾 id 为 1000000
SELECT * FROM orders
WHERE id > 1000000
ORDER BY id LIMIT 20;
```



### 综合运用

#### 排序分页的交付清单

**排序分页查错集中在稳定性与深页**：交付前逐项过一遍。

- 有 ORDER BY 且含唯一键兜底，页间不重叠不遗漏
- 每页条数有上限，页码或游标有合法性校验
- 大表接口不用裸偏移，已换游标或子查询定位
- 排序列尽量贴索引，EXPLAIN 无大范围 filesort
- COUNT 与明细查询的成本分开评估，总数可缓存

> 前四条是正确性，最后一条是性能。正确性坑在并发写下的页界漂移，性能坑在偏移语义；两类问题在测试环境数据少时全部隐形，上生产才爆。

**速记**：**唯一键定页界，游标防深页，EXPLAIN 验排序**。
