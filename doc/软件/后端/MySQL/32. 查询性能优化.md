## 查询性能优化

### 定位问题

#### 慢查询日志

**慢查询日志记录超阈值的语句**：优化的第一现场。

- 开启：slow_query_log = ON，long_query_time 设阈值（如 0.5 秒）
- log_queries_not_using_indexes 可额外记录未走索引的语句
- mysqldumpslow 汇总排序：按出现次数、总耗时、平均耗时
- 日志给出执行时间、锁定时间、扫描行数与语句原文

> 阈值定多少看业务：接口类 0.1 到 0.5 秒，报表类放宽。优化顺序按“出现次数乘总耗时”排，高频慢查询优先——修一次修掉一半耗时。

**速记**：**日志先开阈值定，频次乘耗时排优先级**。

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;
```



#### 标准优化流程

**优化是循环不是灵感**：定位、归因、改写、回归四步走。

- 第一步：EXPLAIN（27 篇）看 type、key、rows、Extra
- 第二步：归因——没走索引、走错索引、扫描量大、临时表、锁等待
- 第三步：改写语句或加改索引，一次只改一处
- 第四步：回归验证，EXPLAIN 加真实耗时对比

> 一次改一处的纪律来自归因需求：同时改三个东西，好了不知道为什么好，坏了不知道谁干的。性能优化是实验科学，单变量控制是底线。

**速记**：**EXPLAIN 归因，单变量改动，回归说话**。



### 索引与语句层面

#### 索引侧的优化要点

**索引优化三板斧**：覆盖、最左、对齐序。

- 覆盖索引：高频查询的关键列进索引，免回表
- 最左前缀：联合索引列序与查询条件匹配
- 排序分组对齐：ORDER BY 与 GROUP BY 贴索引序，消 filesort 与临时表
- 失效场景排查：函数、隐式转换、百分号开头（26 篇清单）

> 加索引是优化手段的第一直觉，但要有验收：加了之后 EXPLAIN 必须显示它被用上，且 rows 显著下降。没验收的索引可能只是白付写入税。

**速记**：**覆盖免回表，列序合查询，序对齐消罚单**。



#### JOIN 优化

**连接优化的核心是驱动顺序与索引就位**：让每次循环都是点查。

- 小表驱动大表：EXPLAIN 第一行即驱动表
- 被驱动表的连接列必须有索引，否则每次循环全表扫
- 连接列类型与字符集一致，防隐式转换废索引
- Block Nested Loop 出现（Extra 提示）说明没有可用索引，考虑改写或加索引

> join_buffer 与 BNL 是“索引缺失”的代偿机制：能跑，但代价是内存换 IO。见到 BNL 先补索引，而不是调大 buffer。

**速记**：**小表驱动，被驱动列有索引，见 BNL 先补索引**。



#### 子查询改写与深分页

**两处经典改写**：子查询 JOIN 化，深分页游标化。

- 相关标量子查询逐行执行，改 JOIN 加 GROUP BY（18 篇）
- NOT IN 有 NULL 陷阱，改 NOT EXISTS 或 LEFT JOIN 加判空
- 深分页 LIMIT 大偏移改游标式或子查询定位（16 篇）
- 改写前后行数必须核对，防一对多放大

> 改写是拿可读性换性能的交易，每次交易要留证：改前改后的 EXPLAIN 与耗时截图进评审记录，避免后人“优化回退”。

**速记**：**子查询逐行改连接，深页偏移改游标，行数留证**。



### 数据与架构层面

#### 字段与表设计

**慢查询的一半根子在表设计**：设计期省下的都是运行期利润。

- 类型够用最小：能 int 不 bigint，能 date 不 datetime 的场景要辨析
- 大字段拆表：TEXT、BLOB 拆出主表，防缓存稀释（25 篇）
- 尽量 NOT NULL：省 NULL 位图与三值逻辑分支
- 冗余字段换连接：读多写少的高频连接列可适度冗余

> 设计期的每个决定都在给未来的查询定价：行宽、NULL、大字段、连接深度。上线后再改设计的成本十倍于此，评审表结构时把查询模式一起过。

**速记**：**设计定性能上限，行窄字段实大字段拆**。



#### 架构层手段

**数据库优化到头，还有架构层出口**：按顺序考虑。

- 缓存层：读多改少的热点进 Redis，注意一致性与穿透
- 读写分离：报表与查询走从库，主库留给写
- 连接池：复用连接，控制并发上限
- 限流与熔断：max_execution_time 兜底慢查询，应用层限流保护库

> 架构手段都不能替代基础功：索引与语句不优，加缓存只是把慢查询缓存起来。顺序是先库内后库外，缓存是放大器不是救火队。

**速记**：**先库内后库外，缓存放大基础功**。



### 综合运用

#### COUNT 与统计的优化

**COUNT 的优化先想清楚要不要精确**：口径决定方案。

- COUNT(*) 由引擎层优化，是三者中最快的形态
- 大表实时精确计数代价高，评估能否接受估算或延迟
- 汇总数落汇总表或缓存，定时或事件驱动刷新
- 前端展示可退化为“约 N 条”或不显示总数

> “总数必须精确”往往是不假思索的默认，而非业务真实要求。把口径问题抛回产品， Frequently 能砍掉一条昂贵的实时聚合。

**速记**：**COUNT 先问要否精确，汇总表缓存接大数**。



#### 优化守则清单

**优化的纪律比技巧值钱**：十条守则收束本系列。

- 无 EXPLAIN 不谈优化，无基线不谈收益
- 一次一变量，改动留证可回滚
- 先索引与语句，后参数与架构
- 慢日志定期看，别等告警才看
- 大表任何操作先想锁面与主从延迟
- 设计期的一分力等于运行期十分力

> 这份清单来自本篇与 24、26、27 篇的汇总；性能优化没有银弹，只有纪律性的循环改进。每次优化留档，团队的性能知识就这样沉淀。

**速记**：**EXPLAIN 开路单变量行进，先内后外，留档沉淀**。
