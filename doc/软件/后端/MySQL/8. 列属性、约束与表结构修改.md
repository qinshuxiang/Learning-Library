## 列属性、约束与表结构修改

### 约束的认识

#### 什么是约束

**约束**：是附加在表或列上的规则，强制进入表的数据满足指定条件。

- 约束在**写入与更新时校验**，违反则语句失败报错。
- 约束是数据库层的数据质量保证，比应用层校验更可靠。
- 常见约束：NOT NULL、DEFAULT、PRIMARY KEY、AUTO_INCREMENT、UNIQUE、FOREIGN KEY、CHECK。



#### 为什么要约束

**为什么要约束**：是为了把"数据长什么样才合法"这一规则下沉到数据库，避免脏数据扩散。

- 防止不合法、不完整数据进入系统（如负年龄、空主键）。
- 减少应用层重复校验逻辑，统一由库保障。
- 为查询优化器提供索引与唯一性线索。

> 没有约束的表如同无门槛的入口，任何值都能写入；一旦脏数据进入，清理成本远高于事前约束。约束与索引常被混淆，但约束是"规则"、索引是"加速结构"，UNIQUE 与 PRIMARY KEY 同时兼具二者。



#### 约束的作用级别：列级约束与表级约束

**作用级别**：约束按定义位置分为列级约束与表级约束，二者生效范围不同。

```sql
CREATE TABLE t (
  a INT NOT NULL,
  b INT,
  PRIMARY KEY (a),
  CONSTRAINT uk_b UNIQUE (b)
);
```

- **列级约束**：写在列定义内，只约束该列（如 NOT NULL、DEFAULT、列内 UNIQUE）。
- **表级约束**：写在所有列定义之后，可跨多列（如复合主键、复合唯一、外键）。
- NOT NULL 没有表级写法，只能列级；PRIMARY KEY、UNIQUE、FOREIGN KEY、CHECK 均可表级。

> 列级与表级约束在生效上无优劣之分，仅语法位置不同；涉及多列的约束（如复合主键）只能用表级。写表级约束时建议显式给名字（CONSTRAINT 名），便于后续删除与排查。



#### 查看与删除约束

**查看与删除**：约束的元信息可从 information_schema 读取，删除需对应语句。

```sql
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM information_schema.TABLE_CONSTRAINTS
WHERE TABLE_SCHEMA = 'school_mgmt' AND TABLE_NAME = 'student';

ALTER TABLE student DROP PRIMARY KEY;
ALTER TABLE student DROP FOREIGN KEY fk_dept;
ALTER TABLE student DROP INDEX idx_unique;
```

- TABLE_CONSTRAINTS 表列出每张表的约束名与类型。
- 主键用 ALTER TABLE ... DROP PRIMARY KEY 删除（一个表仅一个，无需写名）。
- 外键、唯一约束删除时需指定名字；唯一约束本质是索引，DROP INDEX 同样可移除。

> 约束名若未显式指定，MySQL 会自动生成（主键默认 PRIMARY，唯一/外键按列名推导）。显式命名（CONSTRAINT 名）能让 DROP 语句可读，也方便跨环境一致。删除唯一约束既可用 DROP INDEX 也可 DROP KEY，二者等价。



### NOT NULL 非空约束

#### 作用

**NOT NULL**：是禁止列取空值的约束，保证该列必有内容。

- NOT NULL 列在插入或更新时**必须提供值**。
- 它**不**是索引，也**不**禁止重复，仅禁止空。
- 常与 DEFAULT 或业务必填语义搭配。



#### 列级写法

**列级写法**：NOT NULL 只能写在列定义中，无表级形式。

```sql
CREATE TABLE t (
  id INT NOT NULL,
  name VARCHAR(50) NOT NULL
);
```

- NOT NULL 紧跟类型之后书写。
- 可同时加 DEFAULT 提供缺省（见 DEFAULT 章节）。
- 用 ALTER TABLE ... MODIFY 可追加或移除 NOT NULL。



#### 空字符串与 NULL 的区别辨析

**空字符串与 NULL**：是两类不同的"无值"，语义与存储都不同，严禁混为一谈。

- **NULL** 表示"未知、不存在"，是缺失的标记，不参与普通比较。
- **空字符串** 是一个长度为 0 的合法字符串值，是确定的内容。
- 对 NULL 用等于号比较得不到真，必须用 IS NULL 与 IS NOT NULL。
- 对 VARCHAR 列，空字符串与 NULL 是两条不同的记录。

> [!IMPORTANT]
> **重要内容**：NULL 不等于空字符串，也不等于 0。WHERE col = NULL 永远不成立，必须写成 WHERE col IS NULL。COUNT(col) 忽略 NULL 行但会计入空字符串行，这是统计口径最常踩的坑。

> 口诀：**NULL 是未知不是空，比较要用 IS NULL；空串是值别混淆，COUNT 统计要当心**。



### DEFAULT 默认值约束

#### 字面量默认值

**DEFAULT**：是当插入未指定该列时使用的缺省值，字面量默认值为常量。

```sql
CREATE TABLE t (
  status TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

- DEFAULT 后接字面量（数值、字符串、NULL）或特定函数如 CURRENT_TIMESTAMP。
- 显式插入 NULL（且该列可空）会存 NULL，而非默认值。
- 仅当插入省略该列或写 DEFAULT 关键字时才套用默认值。



#### 表达式默认值（8.0.13 起支持）

**表达式默认值**：是 8.0.13 起支持的、以函数或表达式计算得到的默认值。

```sql
CREATE TABLE t (
  price DECIMAL(10,2) NOT NULL,
  tax DECIMAL(10,2) AS (price * 0.13),
  updated_at DATETIME DEFAULT (CURRENT_TIMESTAMP)
);
```

- 用括号包裹的表达式作默认值，如 DEFAULT (CURRENT_TIMESTAMP)。
- 与**生成列**（AS 表达式）不同：表达式默认值仍允许显式插入覆盖。
- 8.0.13 之前 DEFAULT 只接受字面量或 CURRENT_TIMESTAMP，写表达式会报语法错。

> 表达式默认值让"插入时自动算出来"成为可能，例如默认填入当前时间、默认按某列推导。注意它与生成列的区别：生成列是**始终由表达式决定、不可显式写入**，而表达式默认值**可**被显式值覆盖。



#### NOT NULL 与 DEFAULT 的配合

**NOT NULL 与 DEFAULT 配合**：二者互补，既能强制必填，又免去每次显式赋值。

- NOT NULL 保证列非空，DEFAULT 在省略赋值时兜底。
- 二者并存时，省略该列会落入默认值而非报错。
- 仅 NOT NULL 无 DEFAULT，且插入省略该列，则报错无默认值。

> 推荐对业务必填列同时声明 NOT NULL 与合理 DEFAULT，既防脏数据又提升写入便利。但要注意：DEFAULT 不适用 NULL 关键字当"想存空"的情形——若列可空，显式写 NULL 是直接存空，不走默认。



### PRIMARY KEY 主键约束

#### 主键唯一且非空

**PRIMARY KEY**：是标识每行唯一性的约束，兼具**唯一**且**非空**双重特性。

- 主键列**不允许重复**，也**不允许 NULL**。
- 一个表**只能有一个**主键（可含多列，即复合主键）。
- 主键在 InnoDB 中同时是聚簇索引，决定数据的物理排列。



#### 单列主键

**单列主键**：是最常见形式，用一列唯一标识行。

```sql
CREATE TABLE user (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  PRIMARY KEY (id)
) ENGINE=InnoDB;
```

- 主键定义在列定义后单独写 PRIMARY KEY (列)。
- 也可列内联写 id INT ... PRIMARY KEY。
- 配合 AUTO_INCREMENT 最典型，见 AUTO_INCREMENT 章节。



#### 复合主键

**复合主键**：是用多列共同作为主键，组合值唯一标识一行。

```sql
CREATE TABLE score (
  stu_id INT UNSIGNED NOT NULL,
  course_id INT UNSIGNED NOT NULL,
  score TINYINT UNSIGNED,
  PRIMARY KEY (stu_id, course_id)
) ENGINE=InnoDB;
```

- 多列写在 PRIMARY KEY (a, b) 中，顺序影响索引排列。
- 要求**组合**唯一，单看某一列可重复。
- 常用于多对多关系表（如选课、订单明细）。

> 复合主键下，索引先按第一列排序，再按后续列；查询若只按第二列过滤，往往用不上该主键索引的最左前缀。设计时应把区分度高的列放前面。复合主键还常用于天然存在业务联合唯一性的关联表。



#### 自增主键

**自增主键**：是把主键设为 AUTO_INCREMENT，插入时自动递增赋值。

```sql
CREATE TABLE user (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  PRIMARY KEY (id)
) ENGINE=InnoDB;
```

- 自增列插入时可省略，库自动生成下一个值。
- 必须建立索引（主键天然满足）。
- 详见 AUTO_INCREMENT 章节。



#### 主键的选择（自然主键与代理主键）

**主键选择**：是在业务自带唯一键（自然主键）与系统生成键（代理主键）之间取舍。

- **自然主键**：用业务字段作主键，如身份证号、学号，具有业务含义。
- **代理主键**：用与业务无关的自增或 UUID 作主键，如自增 id。
- 互联网实践多倾向**代理主键**：稳定、简短、不随业务变更。

> 自然主键好处是免额外列、查询直观，但业务字段一旦变更（如学号规则调整）会牵动所有外键与索引，代价高。代理主键与业务解耦，插入性能与索引宽度更优；缺点是多一列、且需额外唯一约束保证业务唯一性。



### AUTO_INCREMENT 自增列

#### 必须与索引键关联

**AUTO_INCREMENT**：是自动生成递增整数值的列属性，必须挂在索引键上。

- 自增列必须是**索引的一部分**（通常即主键或唯一索引）。
- 列类型须为整数或浮点族（常用 INT 与 BIGINT）。
- 既定义 AUTO_INCREMENT，又需 NOT NULL。

```sql
CREATE TABLE t (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  PRIMARY KEY (id)
) ENGINE=InnoDB;
```

> 若把 AUTO_INCREMENT 加在没有索引的普通列上，MySQL 会直接报错；因为自增机制依赖索引来快速定位当前最大值与分配下一个值。选用 BIGINT 而非 INT 可避免高并发写入下的溢出风险（INT 上限约 21 亿）。



#### 一个表只能有一个

**一个表只能有一个自增列**：这是硬性限制，防止自增语义冲突。

- 单表**至多一个** AUTO_INCREMENT 列。
- 该列必须被索引。
- 若需多列"自动编号"，应改用应用层或触发器实现。

> 这一限制源于自增计数器只有一个，无法同时维护多列的递增序列。设计上也不需要多个自增列——真正的多序列需求（如按部门分别编号）由应用层或生成列处理更合适。



#### 自增量的持久化行为

**自增量持久化**：指自增计数器在重启后的保留情况，8.0 起已可靠持久化。

- **8.0 之前**：自增值仅存在于内存，重启后从"当前最大 id 加 1"重新计算，若曾删除最大行，可能复用已用值（导致主键冲突风险）。
- **8.0 起**：自增计数器写入 redo 日志与数据字典，**持久化**，重启后不回退。
- 即使 8.0 持久化，显式插入一个较大值后再自增，仍会按"已用最大值加 1"推进。

> [!IMPORTANT]
> **重要内容**：MySQL 8.0 把自增计数器持久化进 redo 日志，重启不会丢失、不会回退到旧小值，这是相对 5.7 的重要可靠性改进。但自增本身不保证"连续"——事务回滚、显式插入、DELETE 都会留下空洞，主键连续不应作为业务假设。



#### LAST_INSERT_ID 函数

**LAST_INSERT_ID**：是返回当前连接上最近一次自增生成值的函数。

```sql
INSERT INTO user (name) VALUES ('张三');
SELECT LAST_INSERT_ID();
```

- 返回**当前连接**最近的自增 id，不受其他连接影响。
- 批量插入时返回**第一行的**自增值，后续行按步长推算。
- 常用于拿到新主键后写入关联子表。

> LAST_INSERT_ID 的"连接级"特性很关键：并发下各连接互不干扰，不会读到别人的自增 id。它是 ORM 框架获取插入主键的底层机制；注意它反映的是自增列，对非自增主键无效。



### UNIQUE 唯一约束

#### 允许多个 NULL

**UNIQUE**：是唯一约束，保证列或列组合的值互不重复，但**允许多个 NULL**。

- UNIQUE 列可重复出现 **NULL**（NULL 不参与唯一比较）。
- 与 PRIMARY KEY 不同：UNIQUE 允许空，主键不允许。
- 一个表可有**多个** UNIQUE 约束。

```sql
CREATE TABLE t (
  email VARCHAR(100) UNIQUE,
  phone VARCHAR(20) UNIQUE
);
```

> 这与"唯一"的字面直觉略有出入：因为 NULL 代表未知，两个未知无法判定相等，故标准 SQL 允许唯一列存在多个 NULL。若需"最多一个 NULL"，可改用过滤索引或 CHECK 约束在应用层模拟。



#### UNIQUE KEY 也是一个索引

**UNIQUE KEY**：是唯一约束在存储上的体现，它同时是一棵**索引**。

- 声明 UNIQUE 会隐式创建一棵唯一索引，加速等值查询。
- 可给唯一约束显式命名：CONSTRAINT uk_email UNIQUE (email)。
- 多列组合唯一用表级 CONSTRAINT uk_x UNIQUE (a, b)。

> 唯一约束与唯一索引本质同一事物，只是入口不同：写 UNIQUE 列定义得到约束，写 CREATE UNIQUE INDEX 得到索引，二者最终都落地为唯一索引。删除时 DROP INDEX 与 DROP KEY 等价。



#### 唯一约束的创建与删除

**创建与删除**：唯一约束可建表时声明，也可后期追加或移除。

```sql
ALTER TABLE student ADD CONSTRAINT uk_stu_name UNIQUE (stu_name);
ALTER TABLE student DROP INDEX uk_stu_name;
```

- 建表后用 ALTER TABLE ... ADD UNIQUE 追加。
- 删除时用 DROP INDEX 指定约束名。
- 若列已存在重复值，加唯一约束会失败，需先清理重复。

> 追加唯一约束时，MySQL 会扫描全表校验既有数据是否冲突，大表上加唯一锁表风险高，应在低峰或使用在线 DDL 工具。唯一约束名建议以 uk_ 前缀规范命名，便于识别与运维。



### FOREIGN KEY 外键约束

#### 父子表概念

**FOREIGN KEY**：是建立子表某列与父表主键或唯一键之间引用关系的约束。

- **父表**：被引用的表，提供被引用的键（通常是主键或唯一键）。
- **子表**：持有外键的表，外键值须存在于父表的被引用键中。
- 插入子表时，外键值必须在父表存在，否则报错（除非该外键列本身为 NULL）。

```sql
CREATE TABLE student (
  stu_id INT UNSIGNED NOT NULL,
  dept_id INT UNSIGNED NOT NULL,
  PRIMARY KEY (stu_id),
  CONSTRAINT fk_dept FOREIGN KEY (dept_id) REFERENCES department (dept_id)
) ENGINE=InnoDB;
```



#### 级联操作 CASCADE、SET NULL、NO ACTION、RESTRICT

**级联操作**：定义父表记录被更新或删除时，子表关联行的反应方式。

- **CASCADE**：父变子跟着变（删除父则级联删子，更新键则同步更新子）。
- **SET NULL**：父删除或更新后，子表外键列置为 NULL（要求子列可空）。
- **NO ACTION**：默认行为，父有子引用时拒绝删除或更新父。
- **RESTRICT**：与 NO ACTION 类似，拒绝操作，语义几乎一致。

```sql
CONSTRAINT fk_dept FOREIGN KEY (dept_id)
  REFERENCES department (dept_id)
  ON DELETE CASCADE
  ON UPDATE RESTRICT;
```

> CASCADE 与 SET NULL 是"自动传播"，NO ACTION 与 RESTRICT 是"拒绝传播"；两者取向相反。NO ACTION 与 RESTRICT 在标准上略有差异，但 InnoDB 实现里二者行为相同，均拒绝破坏引用完整性的操作。ON DELETE 与 ON UPDATE 可分别指定，互不影响。



#### 外键要求 InnoDB

**外键要求 InnoDB**：MySQL 的外键约束**只在 InnoDB 引擎下生效**。

- 仅 **InnoDB** 支持外键，MyISAM 等引擎会**忽略**外键定义。
- 父子表必须都是 InnoDB，且字符集与排序规则兼容。
- 被引用列须是父表的主键或唯一键。

> 若误用 MyISAM 建外键，语句虽能"执行"，但外键根本不建立、不校验，数据完整性实际无保障。因此凡涉及外键的表务必确认 ENGINE=InnoDB；这也进一步印证"生产表统一 InnoDB"的建议。



#### 外键的优缺点争议

**优缺点争议**：外键保证引用完整性，但互联网高并发场景常改由应用层保证。

- **优点**：由数据库强制完整性，杜绝脏引用，级联方便。
- **缺点**：写入需查父表、加锁，影响性能；分库分表后跨库外键失效。
- **实践**：很多互联网系统**去掉外键**，把校验放到应用层与审核流程。

> 外键取舍是"强一致与高性能"的权衡：金融、ERP 等强一致场景倾向保留外键；高并发、海量、分布式场景倾向弃用外键以换取写入自由与水平扩展。弃用后须在应用层补齐校验，否则引用完整性将无兜底。



### CHECK 检查约束

#### 8.0.16 之前被忽略、之后才真正生效

**CHECK**：是限制列值必须满足某布尔表达式的约束，但历史上长期被忽略。

- **8.0.16 之前**：CHECK 语法被解析但**直接忽略**，不报错也不校验。
- **8.0.16 起**：CHECK 真正生效，插入或更新违反表达式则失败。
- 更早版本若需值校验，只能靠触发器或应用层模拟。

> [!IMPORTANT]
> **重要内容**：MySQL 在 8.0.16 之前对 CHECK 约束"只认语法、不校验数据"，这是与标准 SQL 的重大偏差。升级到 8.0.16 及以上后，原本被忽略的 CHECK 会突然开始拦截数据，老数据若违反表达式将引发后续写入失败，升级时需预先清洗。



#### 用法示例

**用法示例**：CHECK 可限制取值区间、枚举、跨列关系等。

```sql
CREATE TABLE product (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  price DECIMAL(10,2) NOT NULL,
  discount DECIMAL(3,2) NOT NULL,
  PRIMARY KEY (id),
  CONSTRAINT ck_price CHECK (price >= 0),
  CONSTRAINT ck_disc CHECK (discount BETWEEN 0 AND 1),
  CONSTRAINT ck_pd CHECK (price * (1 - discount) >= 0)
);
```

- CHECK (表达式) 可引用本行多列，做跨列校验。
- 可显式命名 CONSTRAINT ck_xxx CHECK (...)。
- 违反时抛 CHECK constraint failed 错误。

> CHECK 比枚举 ENUM 更灵活：ENUM 取值固定且修改需改表结构，CHECK 可用任意表达式并随业务调整。对"年龄在 0 到 150""折扣在 0 到 1"这类范围约束，CHECK 是最直接的声明式方案。



### 列的属性速查

#### 注释与数值属性（COMMENT、UNSIGNED、ZEROFILL）

**列属性**：是附加在列定义上的修饰，影响语义、存储与显示。

- **COMMENT**：列注释，说明业务含义，可由 SHOW CREATE TABLE 或 information_schema 读取。
- **UNSIGNED**：无符号，仅存非负数，同类型上限翻倍（如 INT 上限约 42 亿）。
- **ZEROFILL**：显示时左侧补零至指定宽度，仅影响显示，底层仍为整数值。

```sql
CREATE TABLE t (
  age TINYINT UNSIGNED COMMENT '年龄',
  code INT ZEROFILL
);
```

> UNSIGNED 常用于 id、计数器等不会为负的数量；ZEROFILL 已较少使用，且其隐式要求列变为 UNSIGNED。COMMENT 虽不影响运行，却是团队协作中沉淀字段含义的最低成本手段，强烈建议必填。



#### 列级字符集与排序（CHARACTER SET、COLLATE）

**列级字符集**：允许单列为字符串列指定独立于表的字符集与排序规则。

- 列可单独声明 CHARACTER SET 与 COLLATE，覆盖表级默认。
- 同一表的不同字符串列可使用不同字符集。
- 列级字符集须为服务器支持的字符集。

```sql
CREATE TABLE t (
  name VARCHAR(50) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci,
  code VARCHAR(20) CHARACTER SET ascii
);
```

> 列级字符集常用于混排场景：主字段用 utf8mb4，固定编码字段（如邮编、ASCII 编码）用更紧凑的 ascii，节省空间并明确语义。混用字符集时，跨列比较会触发隐式转换，需谨慎。



#### 列的可见与不可见（INVISIBLE，8.0.23 起）

**INVISIBLE**：是 8.0.23 起支持的列可见性属性，控制列是否默认出现在 SELECT * 中。

```sql
CREATE TABLE t (
  id INT PRIMARY KEY,
  secret VARCHAR(50) INVISIBLE
);

SELECT * FROM t;
SELECT id, secret FROM t;
```

- **INVISIBLE** 列默认不参与 SELECT *，但显式指定仍可取。
- **VISIBLE** 为默认，即普通列。
- 适合在不破坏旧查询的前提下"隐藏"新增列。

> INVISIBLE 让"加列但不影响既有 SELECT *"成为可能，便于灰度发布与兼容老代码。它不改变存储，只改变默认投影；对该列显式点名查询完全正常。8.0.23 之前的版本不支持该属性，升级后才会生效。



### ALTER TABLE 修改表结构

#### ADD COLUMN（含 FIRST 与 AFTER）

**ADD COLUMN**：是向已有表追加新列的语句，可指定位置。

```sql
ALTER TABLE student ADD COLUMN email VARCHAR(100) NOT NULL DEFAULT '';
ALTER TABLE student ADD COLUMN age TINYINT UNSIGNED FIRST;
ALTER TABLE student ADD COLUMN phone VARCHAR(20) AFTER stu_name;
```

- 默认新列追加到**末尾**。
- FIRST 放到最前，AFTER 列 放到指定列之后。
- 带 NOT NULL 又无默认值的大表加列会触发表重建，需谨慎。

> 大表 ADD COLUMN 在 8.0 下多数情况可 Instant 完成，无需重建全表；但带 NOT NULL 且无默认值的加列在旧算法下会锁表并拷贝数据。加列位置（FIRST 与 AFTER）通常只影响可读性，InnoDB 物理存储对顺序不敏感。



#### MODIFY COLUMN

**MODIFY COLUMN**：是修改列的类型、属性（不改列名）的语句。

```sql
ALTER TABLE student MODIFY COLUMN stu_name VARCHAR(100) NOT NULL;
ALTER TABLE student MODIFY COLUMN age SMALLINT UNSIGNED;
```

- MODIFY 可改类型、长度、默认值、NOT NULL 等属性。
- 改类型若 widening（如 VARCHAR(50) 改 100）通常较快，narrowing 可能需重排数据。
- MODIFY **不能**改列名，改名用 CHANGE。

> 将 VARCHAR(50) 改为 VARCHAR(100) 在 8.0 多在原地完成；但若跨越字节阈值或改小长度，则可能触发表重建。MODIFY 会丢失列的原有注释（除非重写 COMMENT），改列时务必把注释一并带上。



#### CHANGE COLUMN

**CHANGE COLUMN**：是同时改名并改定义列的语句，比 MODIFY 多一个旧列名参数。

```sql
ALTER TABLE student CHANGE COLUMN stu_name full_name VARCHAR(50) NOT NULL;
```

- CHANGE 语法为 CHANGE 旧名 新名 新定义。
- 只改名不改类型时，新定义须重复写一遍原定义。
- 既能改名也能改属性，功能覆盖 MODIFY。

> CHANGE 与 MODIFY 的核心区别是"能否改名"：CHANGE 必需旧名与新名，可改名；MODIFY 只有单个列名，不可改名。仅调整类型用 MODIFY 更简洁，需要重命名则只能用 CHANGE。



#### ALTER COLUMN SET DEFAULT

**ALTER COLUMN SET DEFAULT**：是专门修改列默认值的轻量语句。

```sql
ALTER TABLE student ALTER COLUMN gender SET DEFAULT 'F';
ALTER TABLE student ALTER COLUMN gender DROP DEFAULT;
```

- SET DEFAULT 改默认值，DROP DEFAULT 移除默认值。
- 该操作**只改元数据**，不触碰已有数据，通常很快。
- 相比 MODIFY 改默认值，ALTER COLUMN 更轻量、更不易锁表。

> 改动默认值用 ALTER COLUMN 而非 MODIFY，是因为前者仅更新数据字典、不重写行，开销极小且几乎不锁表；MODIFY 改默认值则可能触发全表重建。日常调默认值应优先 ALTER COLUMN。



#### DROP COLUMN

**DROP COLUMN**：是从表中删除某列的语句，列数据与索引一并移除。

```sql
ALTER TABLE student DROP COLUMN phone;
ALTER TABLE student DROP COLUMN age, DROP COLUMN email;
```

- 单条 ALTER 可逗号分隔**批量** DROP 多列。
- 删除列会同时移除其上的索引与约束。
- 大表 DROP COLUMN 在 8.0 下多数可 Instant 完成。

> DROP COLUMN 不可逆，删除前确认无查询、视图、应用依赖该列。8.0 的 Instant DROP COLUMN 通过标记列废弃实现，物理回收在后续重整时发生，故当下很快；但表定义膨胀期间仍建议择机优化。



#### 修改表名与字符集

**修改表名与字符集**：ALTER TABLE 也支持改名与整表字符集转换。

```sql
ALTER TABLE student RENAME TO student_info;
ALTER TABLE student CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

- RENAME TO 等价于前文 RENAME TABLE，单表改名。
- CONVERT TO CHARACTER SET 会转换表及所有字符串列的字符集与数据。
- 修改字符集可能影响索引前缀长度与存储占用。

> CONVERT TO CHARACTER SET 是"连数据一起转"，不同于仅改默认；错误转换方向（如从 utf8mb4 转 ascii）会丢失无法映射的字符。转换前务必备份，并确认目标字符集能容纳现有数据。



#### 修改列顺序

**修改列顺序**：是通过 MODIFY 或 CHANGE 配合 FIRST 与 AFTER 重新排列列位置。

```sql
ALTER TABLE student MODIFY COLUMN stu_name VARCHAR(50) NOT NULL AFTER stu_id;
```

- 列顺序本质是逻辑定义顺序，InnoDB 物理存储对此不敏感。
- 调整顺序通常需表重建，大表代价高。
- 没有性能收益时，不应仅为"看着顺"而重排列。

> 列顺序对查询性能几乎无影响，因为行是以整行格式存储的；重排列多是为了与文档或约定对齐。若必须重排，应认识到大表会经历重建，应在低峰或借助在线 DDL 完成。



### 表结构变更的风险与在线 DDL 简述

#### 在线 DDL 与工具简述

**在线 DDL**：是指在变更表结构时尽量减少对读写阻塞的技术与工具集合。

- MySQL 5.6 起原生支持部分**在线 DDL**，8.0 大幅扩展（如 Instant ADD COLUMN）。
- **pt-online-schema-change**：Percona 工具，建影子表、触发器同步增量、最后原子换表。
- **gh-ost**：GitHub 工具，基于 binlog 异步同步，无触发器、对主库压力更小。
- 大表结构变更应避开高峰，优先选 Instant 算法或上述工具。

```bash
pt-online-schema-change --alter "ADD COLUMN email VARCHAR(100)" \
  D=school_mgmt,t=student --execute

gh-ost --alter "ADD COLUMN email VARCHAR(100)" \
  --database=school_mgmt --table=student --execute
```

> 即便 8.0 原生在线 DDL 已很强，超大表或需复杂变更时，pt-online-schema-change 与 gh-ost 仍更稳：前者用触发器、后者用 binlog，二者都能在变更期间保持读写可用。选型上 gh-ost 因无触发器、可暂停、可控性强，渐成主流；但二者都要求表有主键。

> 速记：**大表改结构，Instant 优先、工具兜底；pt 用触发器、gh-ost 用 binlog；表无主键皆不可行**。
