## 数据类型：日期时间与特殊类型

### 日期时间类型概览

日期时间类型用于保存时刻与时间段，MySQL 提供从年到微秒的多档精度，存储字节与取值范围各不相同。

- **YEAR**：只占 1 字节，表示年份，范围 1901 到 2155（以及 0000）。
- **DATE**：占 3 字节，表示日期，范围 1000-01-01 到 9999-12-31。
- **TIME**：占 3 字节（5.6.4 起带小数秒会变长），表示时间或时间间隔。
- **DATETIME**：MySQL 5.6.4 之后占 5 字节（不含小数秒部分），表示日期加时间，与时区无关。
- **TIMESTAMP**：占 4 字节，表示日期加时间，本质是 UTC 时间。

> 五种类型可归纳为"**是否含时区语义**"这一分水岭：**TIMESTAMP 绑定时区，其余四种与时区无关**。选型前先回答"这个时间要不要跟着时区走"，方向就清晰了。



> 记范围不必死背数字，抓住两个边界即可：**TIMESTAMP 受 2038 年限约束，DATETIME 上限到 9999 年**。其余类型按业务需要取精度档位。



### YEAR 类型

#### 1 字节存储

**YEAR**：是仅占用 1 字节的年份类型，用于只关心"哪一年"的场景，空间成本极低。

- **存储本质**：内部以 1 字节整数保存年份偏移，范围 1901 到 2155。
- **非法值处理**：超出范围或无法解析时存为 0000，不报错（取决于 SQL 模式）。
- **典型用途**：出生年、毕业年、会计年度等只需到年级别的字段。

```sql
CREATE TABLE year_demo (
  birth YEAR
);
INSERT INTO year_demo VALUES (1990), (2024);
SELECT birth FROM year_demo;
```

> YEAR 是五种日期时间类型里**最省空间**的，但只能到"年"。任何需要月日的需求都该改用 DATE，而非用整数硬凑。



#### 四位与两位格式及年份映射

**YEAR 输入格式**：支持四位与两位两种写法，两位格式按区间映射到四位年份，这是易错点。

- **四位格式**：直接写 1990、2024，原样保存。
- **两位格式 00 到 69**：映射到 2000 到 2069。
- **两位格式 70 到 99**：映射到 1970 到 1999。
- **字符串与数字**：'00' 与 0 在 YEAR 下含义不同，前者得 2000，后者得 0000。

```sql
CREATE TABLE year_format (
  y YEAR
);
INSERT INTO year_format VALUES (00), (68), (70), (99);
SELECT y FROM year_format; -- 2000、2068、1970、1999
```

> 两位写法务必小心：**00–69 归 2000 起、70–99 归 1970 起**。生产环境建议一律用四位格式，避免跨世纪歧义。



### DATE 类型

#### 3 字节存储

**DATE**：是占用 3 字节的纯日期类型，不含时分秒，适合记录"某天"而非"某时刻"。

- **存储本质**：以三个字节分别编码年、月、日，范围覆盖公元千年到万年。
- **零值表示**：非法日期存为 0000-00-00（取决于 SQL 模式，严格模式会报错）。
- **典型用途**：出生日期、下单日期、有效期起止日。

```sql
CREATE TABLE date_demo (
  born DATE
);
INSERT INTO date_demo VALUES ('1990-05-20');
SELECT born, YEAR(born), MONTH(born) FROM date_demo;
```

> DATE 比 DATETIME 省 2 字节，且语义清晰。凡是"只需日期"的字段，坚决用 DATE，不要拿 DATETIME 截断了事。



#### 格式与输入写法

**DATE 输入格式**：支持标准连字符写法与多种宽松写法，MySQL 会做容错解析。

- **标准写法**：'YYYY-MM-DD'，如 '2024-03-15'。
- **宽松写法**：'YYYYMMDD'、'YY-MM-DD' 也可被解析。
- **分隔符灵活**：除连字符外，斜杠等分隔也可，但不推荐用于正式写入。

```sql
CREATE TABLE date_input (
  d DATE
);
INSERT INTO date_input VALUES ('2024-03-15'), ('20240315');
SELECT d FROM date_input; -- 均为 2024-03-15
```

> 写入时始终用**标准 'YYYY-MM-DD'** 写法，宽松写法仅作读取兼容，不应出现在业务写入语句里。



#### 两位年份的转换规则

**DATE 两位年份**：与 YEAR 类似的映射规则，00 到 69 映射 2000 到 2069，70 到 99 映射 1970 到 1999。

- **00–69**：解析为 2000–2069。
- **70–99**：解析为 1970–1999。
- **四位优先**：写四位年份可彻底规避该映射，推荐始终四位。

```sql
CREATE TABLE date_two_digit (
  d DATE
);
INSERT INTO date_two_digit VALUES ('00-01-01'), ('70-01-01');
SELECT d FROM date_two_digit; -- 2000-01-01、1970-01-01
```

> 与 YEAR 同理，**DATE 的两位年份也踩同一映射坑**。凡涉及历史或未来跨世纪数据，必须用四位年份写入。



### TIME 类型

#### 3 字节存储（5.6.4 起带小数秒变长）

**TIME**：是占用 3 字节的时间类型，5.6.4 起带小数秒（fsp）时存储会变长，用于表示时刻或时间段。

- **无小数秒**：固定 3 字节，精度到秒。
- **带小数秒**：fsp 1–2 加 1 字节、3–4 加 2 字节、5–6 加 3 字节。
- **典型用途**：营业时间、耗时、定时任务时刻。

```sql
CREATE TABLE time_demo (
  open TIME,
  cost TIME(3)
);
INSERT INTO time_demo VALUES ('09:30:00', '00:01:23.456');
SELECT open, cost FROM time_demo;
```

> TIME 的"变长"只发生在**带小数秒**时；纯秒级 TIME 始终是 3 字节。需要亚秒精度才追加 fsp，否则徒增空间。



#### 可表示超过 24 小时的时间间隔

**TIME 超 24 小时**：与日常时钟不同，MySQL 的 TIME 可表示远超一天的时间长度，最大到 838:59:59。

- **取值范围**：-838:59:59 到 838:59:59，可正可负。
- **语义双重**：既表示一天内的时刻，也表示跨天的时间间隔（如影片时长、累计工时）。
- **写入负值**：用负号表示负向间隔，如 '-02:00:00'。

```sql
CREATE TABLE time_span (
  duration TIME
);
INSERT INTO time_span VALUES ('100:00:00'), ('-02:30:00');
SELECT duration FROM time_span;
```

> 记住 TIME **能超过 24 小时**，它不等于"钟表时间"。存放"说了多久、跑了多久"这类间隔，TIME 比 DATETIME 更贴切。



#### 输入格式

**TIME 输入格式**：支持标准时分秒写法与带天数的写法，MySQL 均能解析。

- **标准写法**：'HH:MM:SS' 或 'HH:MM'。
- **带天数写法**：'DD HH:MM:SS'，如 '2 03:04:05' 表示 51 小时多的间隔。
- **小数秒写法**：'HH:MM:SS.fraction'，fraction 长度由 fsp 决定。

```sql
CREATE TABLE time_fmt (
  t TIME
);
INSERT INTO time_fmt VALUES ('23:59:59'), ('2 03:04:05'), ('12:30:00.5');
SELECT t FROM time_fmt;
```

> 写入跨天间隔时用 **'D HH:MM:SS'** 天数写法最直观，避免自己先把天数折算成小时而出错。



### DATETIME 类型

#### 5.6.4 之后占 5 字节且与时区无关

**DATETIME**：是日期加时间的组合类型，MySQL 5.6.4 之后存储空间为 5 字节（不含小数秒部分），存储的是字面量，与时区无关。

- **与时区无关**：写入什么值就存什么值，读取原样返回，不参与时区换算。
- **字节数**：5.6.4 之前为 8 字节，之后压缩为 5 字节（不含小数秒）。
- **典型用途**：需要原样保存、不随时区漂移的业务时刻，如订单创建时刻的业务记录。

```sql
CREATE TABLE datetime_demo (
  created DATETIME
);
INSERT INTO datetime_demo VALUES ('2024-03-15 10:30:00');
SELECT created FROM datetime_demo;
```

> **DATETIME 存的是字面量**：同一份数据在任何时区会话下读出都一致。这与 TIMESTAMP 的本质区别，决定了跨时区业务的选型。



#### 范围 1000-01-01 到 9999-12-31

**DATETIME 范围**：从 1000-01-01 00:00:00 到 9999-12-31 23:59:59，覆盖人类日常所需的全部历史与未来。

- **下限**：1000-01-01 00:00:00，远早于 TIMESTAMP 下限。
- **上限**：9999-12-31 23:59:59，几乎不受"年份溢出"担忧。
- **零值**：'0000-00-00 00:00:00' 为允许的零值（取决于 SQL 模式）。

```sql
CREATE TABLE datetime_range (
  dt DATETIME
);
INSERT INTO datetime_range VALUES ('1000-01-01 00:00:00'), ('9999-12-31 23:59:59');
SELECT dt FROM datetime_range;
```

> DATETIME 的**长范围**是其相对 TIMESTAMP 的最大优势：不受 2038 年限约束，适合需留存久远日期的系统。



### TIMESTAMP 类型

#### 4 字节存储

**TIMESTAMP**：是占用 4 字节的日期时间类型，本质保存 UTC 秒值，是五种类型里最紧凑的"时刻"类型。

- **存储本质**：内部以 4 字节整数记录自 1970-01-01 00:00:00 UTC 起的秒数。
- **字节对比**：比 DATETIME 省 1 字节，但付出了时区依赖与范围受限的代价。
- **典型用途**：需要随会话时区展示、且集中在近代的记录时刻。

```sql
CREATE TABLE ts_demo (
  updated TIMESTAMP
);
INSERT INTO ts_demo VALUES ('2024-03-15 10:30:00');
SELECT updated FROM ts_demo;
```

> 4 字节的紧凑换来的是**2038 硬上限**：存 1970 至 2038 之间的时刻最合适，超出范围的远未来数据应选 DATETIME。



#### 本质是 UTC 时间，读写按会话时区自动转换

**TIMESTAMP 时区语义**：是它最关键的机制——写入时按当前会话时区转换为 UTC 存储，读取时再按会话时区转换回本地展示。

- **写入转换**：insert 时把会话时区的时间换算成 UTC 秒值落盘。
- **读取转换**：select 时把 UTC 秒值按当前会话时区还原成可读时间。
- **时区依赖**：同一份底层数据，在不同时区会话下显示不同，这是与 DATETIME 的根本差别。

```sql
-- 会话 A：东八区
SET time_zone = '+08:00';
INSERT INTO ts_demo VALUES ('2024-03-15 10:30:00');
-- 底层存的是 2024-03-15 02:30:00 UTC

-- 会话 B：UTC
SET time_zone = '+00:00';
SELECT updated FROM ts_demo; -- 显示 2024-03-15 02:30:00
```

> **TIMESTAMP 跟着时区走**：存的是 UTC，展示的是会话时区。跨时区系统用它，用户看到的总是自己本地时间；但底层值随时区解释变化，备份与比对要小心。



#### 范围 1970-01-01 到 2038-01-19（2038 年问题）

**TIMESTAMP 范围**：从 1970-01-01 00:00:01 UTC 到 2038-01-19 03:14:07 UTC，上限由 4 字节符号整数溢出决定，即为"2038 年问题"。

- **下限**：1970-01-01 00:00:01 UTC，早于该时刻无法表示。
- **上限**：2038-01-19 03:14:07 UTC，之后 4 字节有符号整数溢出。
- **2038 问题**：任何需要表示 2038 年之后时刻的字段，都不能用 TIMESTAMP。

```sql
CREATE TABLE ts_range (
  ts TIMESTAMP
);
-- 以下会报错，超出上限
INSERT INTO ts_range VALUES ('2039-01-01 00:00:00');
```

> **2038 是 TIMESTAMP 的天花板**：凡是会员到期、设备寿命、长期合同等可能跨 2038 的字段，一律改用 DATETIME，否则届时数据将溢出或报错。



#### 自动初始化与自动更新

**自动时间戳**：是 TIMESTAMP（以及 DATETIME）支持的便捷机制，可在插入或更新时自动填入当前时间，无需应用层赋值。

- **DEFAULT CURRENT_TIMESTAMP**：插入时自动写入当前时间。
- **ON UPDATE CURRENT_TIMESTAMP**：行被更新时自动刷新为当前时间。
- **组合使用**：二者可同时声明，实现"创建时间 + 最后修改时间"双自动。

```sql
CREATE TABLE ts_auto (
  id BIGINT PRIMARY KEY,
  created TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
INSERT INTO ts_auto (id) VALUES (1);
SELECT created, updated FROM ts_auto;
UPDATE ts_auto SET id = 1 WHERE id = 1; -- updated 自动刷新
```

> 自动时间戳是**审计字段的利器**：created 记初建、updated 记变动，把"谁改了、何时改"交给数据库而非应用。注意 DEFAULT CURRENT_TIMESTAMP 对 TIMESTAMP 是默认行为，对 DATETIME 需显式声明。



### DATETIME 与 TIMESTAMP 的对比

#### 时区相关性

**时区相关性**：是二者最根本的分歧，决定了数据在跨时区下的表现是否一致。

- **DATETIME**：与时区无关，存什么读什么，任何会话下原样返回。
- **TIMESTAMP**：与时区相关，底层 UTC、展示会话时区，跨时区显示不同。
- **影响**：跨国系统用 TIMESTAMP 用户看到本地时间；用 DATETIME 需应用自行换算。

```sql
CREATE TABLE cmp_tz (
  dt DATETIME,
  ts TIMESTAMP
);
SET time_zone = '+08:00';
INSERT INTO cmp_tz VALUES ('2024-03-15 10:00:00', '2024-03-15 10:00:00');
SET time_zone = '+00:00';
SELECT dt, ts FROM cmp_tz; -- dt 仍为 10:00，ts 变为 02:00
```

> **DATETIME 不变、TIMESTAMP 变时区**是核心结论。需要"用户各看各的本地时间"用 TIMESTAMP；需要"全球一致的唯一时刻"用 DATETIME。



#### 存储空间

**存储空间**：DATETIME 在 5.6.4 之后为 5 字节，TIMESTAMP 为 4 字节，二者相差 1 字节。

- **DATETIME**：5 字节（不含小数秒），5.6.4 之前为 8 字节。
- **TIMESTAMP**：4 字节，历史版本同样为 4 字节。
- **行级累积**：大宽表或海量行下，每列差 1 字节会放大成可观的空间与内存差异。

```sql
CREATE TABLE cmp_space (
  dt DATETIME,
  ts TIMESTAMP
);
```

> 单看空间 **TIMESTAMP 省 1 字节**，但别为省 1 字节牺牲时区正确性。空间优化应排在语义正确之后。



#### 时间范围

**时间范围**：DATETIME 上限到 9999 年，TIMESTAMP 上限到 2038 年，二者下限也不同。

- **DATETIME**：1000-01-01 至 9999-12-31，几乎无未来边界焦虑。
- **TIMESTAMP**：1970-01-01 至 2038-01-19，受 2038 年问题约束。
- **选型后果**：需要久远日期（如文物年代、长期合约）必须用 DATETIME。

```sql
-- TIMESTAMP 无法表达 2100 年
CREATE TABLE far_future (
  ts TIMESTAMP
);
INSERT INTO far_future VALUES ('2100-01-01 00:00:00'); -- 报错或截断
```

> **范围差距决定未来可用性**：只要数据可能活过 2038，TIMESTAMP 即出局，这是硬性边界而非偏好。



#### 默认值技巧

**默认值技巧**：二者都支持 CURRENT_TIMESTAMP，但 TIMESTAMP 在历史版本里对"多列自动"有约束，现代 8.0 已放开。

- **TIMESTAMP 默认**：若只声明一列，DEFAULT CURRENT_TIMESTAMP 是隐式默认；多列需显式声明。
- **DATETIME 默认**：必须显式写 DEFAULT CURRENT_TIMESTAMP，无隐式默认。
- **可读性建议**：无论哪种，都显式写出 DEFAULT 与 ON UPDATE，避免依赖隐式规则。

```sql
CREATE TABLE default_trick (
  a TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  b DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

> 默认技巧口诀：**TIMESTAMP 隐式、DATETIME 显式；写代码时一律显式声明**，让 schema 自解释、不依赖版本暗规则。



#### 速记

**速记口诀**：把 DATETIME 与 TIMESTAMP 的取舍压缩为可背诵的一句话。

> **DATETIME 稳、TIMESTAMP 灵**：要全球一致、要跨 2038、要原样留存 → DATETIME；要随用户时区、要省 1 字节、要自动时间戳 → TIMESTAMP。

> 进一步记：**时区无关选 DATETIME，时区相关选 TIMESTAMP；怕 2038 选 DATETIME**。考试选型先判时区、再判年份。



### 小数秒 DATETIME(fsp) 与 TIME(fsp)

#### fsp 取值范围与存储变化

**小数秒（fsp）**：是 DATETIME 与 TIME 的精度参数，取值 0 到 6，表示小数部分的位数，直接影响存储字节。

- **fsp 取值**：0 到 6，分别代表到秒、十分之一秒直至微秒。
- **字节增量**：fsp 1–2 加 1 字节、3–4 加 2 字节、5–6 加 3 字节。
- **对照**：DATETIME(0) 为 5 字节，DATETIME(6) 为 8 字节；TIME 同理。

```sql
CREATE TABLE fsp_demo (
  dt DATETIME(3),
  t  TIME(6)
);
INSERT INTO fsp_demo VALUES ('2024-03-15 10:30:00.123', '12:00:00.123456');
SELECT dt, t FROM fsp_demo;
```

> fsp 不是越大越好：**精度每升一档就多吃字节**。日志级到毫秒（fsp=3）足够，微秒（fsp=6）仅限确需高精度测量的场景。



### 用数值还是日期表示日期的建议

#### 用日期类型的理由

**日期类型优先**：是大多数场景的推荐做法，MySQL 内建了完整的日期函数与校验，数值无法替代。

- **内建函数**：YEAR、MONTH、DATE_ADD、DATEDIFF 等只接受日期类型，数值需先转换。
- **校验与排序**：日期类型自带合法性校验，按时间天然有序；数值易写出歧义格式。
- **时区友好**：TIMESTAMP 能自动处理时区，数值时间戳需应用自行换算。

```sql
SELECT DATE_ADD('2024-03-15', INTERVAL 7 DAY); -- 2024-03-22
SELECT DATEDIFF('2024-03-22', '2024-03-15');   -- 7
```

> **除非有明确性能或兼容理由，一律用日期类型**：函数丰富、校验严格、语义清晰，是数据库的原生能力。



### JSON 类型

#### JSON 文档的存储与规范校验

**JSON 类型**：是 MySQL 5.7 起提供的原生文档类型，以二进制格式（Document Object Notation 的优化存储）保存，并自动做格式与规范校验。

- **规范校验**：写入时即解析，非法 JSON 直接报错，杜绝脏数据入库。
- **二进制存储**：内部以解析后的二进制树存储，访问成员无需每次重新解析文本。
- **不可设默认值**：与 TEXT 类似，JSON 列不能有默认值。

```sql
CREATE TABLE article (
  id BIGINT PRIMARY KEY,
  doc JSON
);
INSERT INTO article VALUES (1, '{"title":"MySQL","tags":["db","sql"]}');
-- 写入非法 JSON 会报错
INSERT INTO article VALUES (2, 'not json'); -- ERROR: Invalid JSON text
```

> JSON 类型省去了**应用层校验与解析**的麻烦：数据库保证存进去的一定是合法 JSON，且后续读取是结构化访问而非全文正则。



#### 常用函数与箭头操作符

**JSON 函数族**：提供构造、提取、判断与修改的一整套工具，配合箭头操作符可极简访问成员。

- **JSON_OBJECT / JSON_ARRAY**：构造对象与数组。
- **JSON_EXTRACT**：按路径提取成员，箭头 -> 与 ->> 是其语法糖（->> 自动去引号）。
- **JSON_CONTAINS**：判断某路径是否包含给定值。
- **JSON_SET / JSON_REMOVE**：原地修改（设置、删除）成员。
- **JSON_TABLE**：把 JSON 数组展开成关系表，便于 JOIN 查询。

```sql
INSERT INTO article VALUES (
  1,
  JSON_OBJECT('title','MySQL', 'tags', JSON_ARRAY('db','sql'))
);
SELECT JSON_EXTRACT(doc, '$.title') FROM article;     -- "MySQL"
SELECT doc->>'$.title' FROM article;                  -- MySQL（去引号）
SELECT JSON_CONTAINS(doc, '"sql"', '$.tags') FROM article; -- 1
```

```sql
UPDATE article SET doc = JSON_SET(doc, '$.views', 10) WHERE id = 1;
UPDATE article SET doc = JSON_REMOVE(doc, '$.views') WHERE id = 1;

SELECT jt.tag
FROM article,
     JSON_TABLE(doc, '$.tags[*]' COLUMNS (tag VARCHAR(20) PATH '$')) AS jt;
```

> 箭头 -> 取的是带引号的 JSON 片段，->> 取的是去引号的标量值，二者差异在**是否保留外层引号**。需要字符串比较时用 ->>，需要嵌套 JSON 时用 ->。



#### 生成列与二级索引

**生成列 + 索引**：是让 JSON 字段可被高效查询的关键技巧——在 JSON 成员上建生成列，再对生成列建二级索引。

- **生成列**：用 GENERATED ALWAYS AS 从 JSON 路径派生出普通列。
- **二级索引**：对生成列建 B+Tree 索引，查询走索引而非全表扫描 JSON。
- **代价**：写入需额外维护生成列与索引，但读性能大幅提升。

```sql
ALTER TABLE article
  ADD COLUMN title VARCHAR(100)
  GENERATED ALWAYS AS (doc->>'$.title') VIRTUAL;
ALTER TABLE article ADD INDEX idx_title (title);

SELECT id FROM article WHERE title = 'MySQL'; -- 走 idx_title
```

> **JSON 本体不能直接建高效索引**，必须借生成列落地为普通列再建二级索引。这是"文档灵活"与"查询高效"之间的桥梁。



### 空间数据类型（SRID 地理坐标）与 MySQL 的 GIS 支持

#### 几何类型、SRID 与 GIS 支持

**空间数据类型**：是一组表示几何对象的类型，用于存储点、线、面等地理或几何信息，并通过 SRID 绑定坐标参考系。

- **几何类型**：POINT（点）、LINESTRING（线）、POLYGON（面）及其 MULTI 集合版本。
- **SRID**：空间参考标识符，指明坐标使用的坐标系，如 4326 表示 WGS 84 经纬度。
- **存储要求**：MySQL 8.0 要求带 SRID 的几何列，未声明 SRID 的空间计算可能被拒绝。
- **空间索引**：可对几何列建 SPATIAL 索引，加速空间范围与邻近查询。
- **空间函数**：ST_Distance、ST_Within、ST_Contains 等支持距离与包含判断。
- **能力边界**：相较专业 GIS（如 PostGIS），MySQL 的空间函数集与精度仍较基础，复杂地理分析建议评估专用方案。

```sql
CREATE TABLE places (
  id BIGINT PRIMARY KEY,
  geo POINT NOT NULL SRID 4326
);
INSERT INTO places VALUES (1, ST_PointFromText('POINT(116.4 39.9)', 4326));
ALTER TABLE places ADD SPATIAL INDEX idx_geo (geo);
SELECT id FROM places WHERE ST_Distance_Sphere(geo, ST_PointFromText('POINT(116.4 39.9)', 4326)) < 1000;
```

> **SRID 不是可选项而是语义锚点**：同样的 (116.4, 39.9) 在不同坐标系下代表不同地点，声明 SRID 才能保证空间运算正确。

> 速记：**MySQL 能存点线面、能建空间索引、能做基础邻近查询，但别把它当完整 GIS**。轻量地理需求够用，专业分析另寻方案。



### 日期时间与特殊类型的选型建议

日期时间与特殊类型的选型，主线是"**要不要时区、要几秒精度、是否需结构化文档或地理**"三个问题。

- **只需年份**：YEAR。
- **只需日期**：DATE。
- **需时刻且全球一致 / 跨 2038 / 原样留存**：DATETIME。
- **需时刻且随用户时区 / 自动时间戳**：TIMESTAMP。
- **需时间段或跨天间隔**：TIME。
- **需灵活结构、半结构化文档**：JSON（配合生成列索引）。
- **需点线面与地理查询**：空间类型（必须带 SRID）。

> 选型优先级：**先判是否需时区（DATETIME 还是 TIMESTAMP），再判精度（fsp 几档），最后判是否文档化或地理化（JSON 或空间类型）**。日期类型优先于数值时间戳，这是新业务的默认答案。

> 速记总纲：**年 YEAR、日 DATE、刻 DATETIME/TIMESTAMP、段 TIME；跨时区 TIMESTAMP、要长久 DATETIME；文档用 JSON、地理用空间**。把这张清单背下，选型不慌。
