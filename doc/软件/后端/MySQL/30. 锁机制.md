## 锁机制

### 锁的层级

#### 全局锁

**全局锁让整库只读**：备份是它唯一常见的舞台。

- 加锁：FLUSH TABLES WITH READ LOCK，简称 FTWRL
- 生效后全库只读：写、DDL、更新类操作全部阻塞
- 典型用途：逻辑备份前冻结状态
- InnoDB 下更优选择是 --single-transaction：一致性快照不锁全库

> FTWRL 对主库是业务停摆，对从库是复制延迟；有了 MVCC 快照，多数备份场景不再需要它。见到 FTWRL 先问一句“为什么不用一致性快照”。

**速记**：**FTWRL 全库只读，InnoDB 时代快照替代**。



#### 表级锁家族

**表级锁有四位成员**：显式表锁、元数据锁、意向锁、自增锁。

- 显式表锁：LOCK TABLES READ/WRITE，粗粒度，现代应用极少使用
- 元数据锁 MDL：访问表自动加，读读兼容、读写互斥，保护结构一致
- 意向锁 IS/IX：标明“行里加了锁”，让表级判断免于全表扫描
- AUTO-INC 锁：自增值分配的协调锁，批量插入时短暂持有

> MDL 是最容易被忽视的一员：长事务持着 MDL 读锁，一条 ALTER 请求 MDL 写锁，后续所有查询排队——整表“假死”的经典剧本。做 DDL 前先查长事务。

**速记**：**MDL 自动加读写互斥，长事务不退 ALTER 堵门**。



#### 行级锁家族

**行级锁是 InnoDB 的看家本领**：四种锁型按范围与意图组合。

- Record Lock：锁单条索引记录
- Gap Lock：锁索引记录之间的间隙，防插入，RR 级别专属
- Next-Key Lock：记录锁加间隙锁，左开右闭区间
- 插入意向锁：INSERT 前在目标间隙设置的意向标记，彼此不冲突
- 行锁加在索引记录上，不锁数据行本身

> “锁加在索引上”是理解一切行锁现象的钥匙：条件没走索引，行锁无处安放，退化成对所有记录加锁，效果接近锁全表。

**速记**：**记锁点、隙锁间、临键合体，行锁长在索引上**。



### 加锁的规则

#### 等值与范围加锁推演

**当前读的加锁范围可以推演**：原则是 RR 下默认临键，等值命中唯一键可退化。

- 唯一索引等值命中：退化为纯记录锁
- 唯一索引等值未命中：锁住所邻间隙
- 普通索引等值：临键锁加下一间隙（防幻影插入）
- 范围条件：覆盖触及区间的全部临键锁
- 无索引可用：全表所有记录与间隙，事实上的全表锁

> 推演三步：找命中的索引区间、按“临键默认、等值唯一退化”套规则、再查条件有没有走索引。八个字记主干——**唯一退化、临键默认**。

**速记**：**唯一等值锁一行，普通加隙防插入，无索引锁全表**。



#### 锁与索引的关系

**没走索引的 UPDATE 是行锁灾难**：这不是比喻，是加锁路径。

- UPDATE ... WHERE 无索引列：扫描到的每条记录都上锁
- 事务结束前这些锁全部持有，并发写全被卡死
- 限制扫描范围（加 LIMIT、收窄条件）可显著缩小锁面
- 上线前的 EXPLAIN 不只是性能问题，也是锁安全问题

> “慢 SQL 影响的不只是性能”——它同时放大锁面与死锁概率。锁视角是评估索引必要性的第二把尺子。

**速记**：**锁面随扫描走，索引既保速度也保并发**。



### 死锁与等待

#### 死锁的产生与处理

**死锁是两个事务互相持有对方要的锁**：InnoDB 自动检测并回滚代价小的一方。

- 经典剧本：事务 A 锁行 1 要行 2，事务 B 锁行 2 要行 1
- InnoDB 默认开启死锁检测，发现即回滚其中一个事务
- 另一个事务收到 Deadlock found 错误，需在应用层重试
- innodb_lock_wait_timeout 管锁等待超时（默认 50 秒），是兜底机制

> 死锁不是故障而是并发常态：应用层拿到死锁错误应重试而非报障。写代码时把“死锁重试”作为事务操作的标配分支。

**速记**：**互相等待即死锁，引擎回滚一家，应用负责重试**。



#### 死锁的排查与预防

**死锁日志能还原现场**：预防靠缩小锁面与统一加锁顺序。

- SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段
- innodb_print_all_deadlocks = 1 把每次死锁记进错误日志
- 预防一：多表多行操作按固定顺序访问
- 预防二：事务短小，锁尽快释放
- 预防三：给条件列建索引，缩小锁面

> 死锁分析的三件套是日志、顺序、索引：日志找到冲突资源，顺序审查找出不一致的加锁路径，索引确认锁面没失控。三者齐了，死锁从玄学变数学。

**速记**：**日志见现场，顺序定规范，索引缩锁面**。



### 锁策略

#### 悲观锁与乐观锁

**悲观与乐观是两种并发假设**：冲突概率决定选谁。

- 悲观锁：假设冲突常发，读前先锁——SELECT ... FOR UPDATE
- 乐观锁：假设冲突稀少，提交时校验版本号或时间戳
- 乐观锁实现：表加 version 列，UPDATE ... WHERE version = 旧值，影响行数为 0 即冲突
- 冲突少用乐观省锁开销，冲突多用悲观少做无用功

> 乐观锁的失败处理与死锁一样需要重试策略；悲观锁的代价是锁等待与吞吐下降。库存秒杀类高冲突场景两者常混合使用（乐观为主、热点行悲观）。

**速记**：**悲观先锁后动，乐观先动后验，冲突频率定取舍**。

```sql
-- 乐观锁扣减
UPDATE goods SET stock = stock - 1, version = version + 1
WHERE id = 42 AND version = 7;
-- affected rows = 0 表示有并发冲突，需重读重试
```



#### 间隙锁的双面性

**间隙锁防幻读也防并发插入**：RR 的安全是用吞吐换的。

- 间隙锁之间不互斥：两个事务可同时锁同一间隙
- 但任何插入都要拿插入意向锁，与间隙锁冲突
- 于是热点区间上“读读相安、插入互卡”
- 高并发写入场景切到 RC 可去掉间隙锁，代价是幻读回归

> 间隙锁是 RR 级别的专属配置：理解它就理解了“RR 更安全但并发写更涩”的原因。级别选择（29 篇）的第二个权衡点正在这里。

**速记**：**隙锁共读不共插，安全与吞吐在此交易**。



### 综合运用

#### 锁问题的排查路径

**锁问题排查按“谁在等谁”展开**：四步定位法。

- 第一步：SHOW PROCESSLIST 看当前连接与状态
- 第二步：performance_schema.data_lock_waits 看锁等待关系
- 第三步：SHOW ENGINE INNODB STATUS 看死锁与最近锁事件
- 第四步：回到业务 SQL，EXPLAIN 验证锁面与索引

> 锁等待的现场信息会在事务结束后消失，8.0 的 performance_schema 才能抓到更完整的历史。事故发生时第一动作是快照，第二动作才是分析。

**速记**：**先快照再分析，等待关系里找元凶**。
