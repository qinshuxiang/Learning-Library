## 字符集与比较规则

### 字符集与编码的基本概念

#### 什么是字符集

**字符集**：是若干个字符的集合，规定了哪些字符可以被计算机识别、存储与表示。

- **字符范围**：一个字符集涵盖的字符总数，如英文字母、汉字、符号等。
- **编号规则**：每个字符在集合内被赋予一个唯一的编号（码点）。
- **与存储无关**：字符集只定义有哪些字符、各自编号多少，不规定字节层面如何存放。

> 字符集解决的是文字符号如何被命名的问题。例如中文环境需要收录成千上万个汉字，而纯英文环境只需收录英文字母与符号即可。字符集本身只管编号，落盘成字节是编码阶段的事。

> 速记：字符集管有哪些字、各自的号，不管怎么存成字节。



#### 什么是字符编码

**字符集编码**（常简称编码）：是将字符集里的字符编号转换为字节序列的规则。

- **编码即映射**：把字符的编号按某种规则写成一个或多个字节。
- **同一字符集可有多种编码**：如 Unicode 可用 UTF-8、UTF-16、UTF-32 三种编码存放。
- **编码决定字节数**：不同编码对同一个字符可能占用 1 到 4 个字节不等。

> 编码解决的是编号如何变成字节的问题。同一个字符在不同编码下占用的字节数不同，这直接影响存储开销与网络传输量。

> 速记：编码管编号怎么变字节，同一种字可有多套编码。



#### 字符集与编码的区别与关系

**字符集与编码**：是集合与转换规则的关系，二者常被混用，但概念边界清晰。

- **字符集是前提**：先有字符集合与编号，才有编码可言。
- **编码是手段**：编码把字符集的编号落实为字节。
- **日常混称**：人们常说用 UTF-8 字符集，实际指的是 Unicode 字符集加 UTF-8 编码。

> 二者关系的常见误读是认为 UTF-8 是一种字符集。严格地说，UTF-8 是 Unicode 字符集的一种编码方式，而非独立的字符集。在 MySQL 语境里也常把字符集一词同时指代字符集与默认编码，需注意语境。

> 速记：字符集是表，编码是翻译；UTF-8 是 Unicode 的翻译方式。



### 常见字符集

#### ASCII

**ASCII**：是最早的字符集之一，仅收录英文字母、数字、标点与控制字符，共 128 个字符。

- **收录范围**：大小写英文字母、阿拉伯数字、常用标点、控制字符。
- **编码方式**：单字节编码，最高位固定为 0，只用低 7 位表示 128 个码点。
- **局限**：无法表示任何非英文字符，如汉字、日文等。

```sql
-- 查看一个 ASCII 字符的字节（结果应为 1）
SELECT LENGTH('A') AS byte_length;
```

> ASCII 是几乎所有现代字符集的兼容基底：英文字母在 UTF-8 下仍然只占 1 字节，与其在 ASCII 下完全一致，因此英文文本在多种编码间迁移通常不会乱码。



#### GB2312、GBK

**GB2312 与 GBK**：是中文环境早期的事实标准字符集，采用变长多字节编码收录汉字。

- **GB2312**：收录约 6763 个汉字，双字节编码，兼容 ASCII。
- **GBK**：GB2312 的扩展，收录汉字更多（含繁体与生僻字），仍为双字节变长。
- **兼容 ASCII**：英文字符仍占 1 字节，汉字占 2 字节。

```sql
-- 在 MySQL 中可指定使用 gbk 字符集（不推荐新项目使用）
CREATE TABLE legacy_demo (
  id INT,
  name VARCHAR(50) CHARACTER SET gbk
) DEFAULT CHARSET=gbk;
```

> GB 系列字符集的致命缺陷是不收录全部 Unicode 字符，且不同国家有各自的本地编码（如 Big5、Shift-JIS），多语言混排时极易出现乱码。现代项目应统一使用 Unicode 体系。



#### Unicode 与 UTF-8

**Unicode**：是一个覆盖全球绝大多数文字的超大字符集，为每个字符分配唯一码点；**UTF-8** 是其最通用的编码方式。

- **码点空间庞大**：Unicode 用码点（如 U+4E2D 表示中）统一编号全球字符。
- **UTF-8 变长编码**：按字符码点大小使用 1 到 4 字节；英文 1 字节、常用汉字 3 字节、生僻字符 4 字节。
- **自同步与兼容 ASCII**：字节首位的标志位让程序能判定字符边界，且英文与 ASCII 完全一致。

```sql
-- 一个汉字在 utf8mb4 下通常占 3 字节
SELECT LENGTH('中') AS bytes_in_utf8mb4;
```

> UTF-8 同时具备节省英文空间与完整覆盖 Unicode 的优点，因此成为 Web 与数据库的事实默认编码。UTF-16、UTF-32 也是 Unicode 的编码，但占用空间更固定、通用性不如 UTF-8。



#### MySQL 的 utf8 与 utf8mb4 的坑

**MySQL 的 utf8**：是 utf8mb3 的别名，最多只用 3 字节表示字符，并非真正的 UTF-8，已被官方弃用。

- **utf8 实为 utf8mb3**：最多 3 字节，无法存储 4 字节的字符（如 emoji、部分生僻汉字）。
- **utf8mb4 才是真 UTF-8**：支持 1 到 4 字节，覆盖完整 Unicode。
- **弃用状态**：MySQL 8.0 中 utf8 仍是 utf8mb3 的别名，官方建议新表一律使用 utf8mb4。

```sql
-- 在 utf8（3 字节）列中插入 4 字节字符会报错或截断
CREATE TABLE emoji_test (
  id INT,
  content VARCHAR(20) CHARACTER SET utf8
);

-- 下述插入在 utf8 列上会因 4 字节字符（如某些生僻汉字、emoji）而失败
INSERT INTO emoji_test (id, content) VALUES (1, '𠮷');
```

> [!CAUTION]
> **注意内容**：utf8 的最大陷阱是能建表、平时正常，一旦遇到 emoji 或辅助平面字符就报错或静默截断。因此凡涉及用户输入、评论、昵称等场景，必须使用 utf8mb4；utf8 仅作为历史兼容存在，新建对象一律避免。

> 速记：MySQL 的 utf8 是假 UTF-8（3 字节），utf8mb4 才是真 UTF-8（4 字节）。



### MySQL 中的字符集与比较规则

#### 查看支持的字符集 SHOW CHARSET

**SHOW CHARSET**：是 MySQL 用于列出服务器支持的全部字符集及其默认比较规则的命令。

- **输出内容**：字符集名称、描述、默认比较规则、每个字符最大字节数。
- **最大字节数**：字段 Maxlen 显示该字符集单字符最多占几字节（utf8mb4 为 4）。
- **过滤用法**：可配合 LIKE 查看特定字符集。

```sql
-- 列出全部支持的字符集
SHOW CHARSET;

-- 只看 utf8mb4 相关
SHOW CHARSET LIKE 'utf8mb4%';
```

> SHOW CHARSET 的结果中，Maxlen 是判断字符集能否存 4 字节字符的关键：Maxlen 为 4 才能完整存 emoji；为 3 则说明是 utf8mb3 体系。



#### 查看比较规则 SHOW COLLATION

**SHOW COLLATION**：用于列出服务器支持的全部比较规则，以及每条规则所属的字符集与排序属性。

- **比较规则含义**：决定字符在比较、排序、去重时如何判定相等与大小。
- **按字符集筛选**：用 WHERE 子句限定字符集，避免结果过长。
- **关键字段**：Collation 名称、Charset 归属、是否默认、是否编译进服务器。

```sql
-- 查看 utf8mb4 下的全部比较规则
SHOW COLLATION WHERE Charset = 'utf8mb4';

-- 查看默认比较规则（Default 为 Yes 的项）
SHOW COLLATION WHERE Charset = 'utf8mb4' AND `Default` = 'Yes';
```

> 比较规则与字符集一一归属：每条 Collation 都挂在某个 Charset 之下。同一个字符集可有数十条比较规则，分别控制是否区分大小写、是否区分重音等。



#### 命名规则 utf8mb4_0900_ai_ci 的构成

**比较规则命名**：以 utf8mb4_0900_ai_ci 为例，名称由字符集、版本、重音、大小写四段拼接而成。

- **utf8mb4**：所属字符集，表示真 UTF-8（4 字节）。
- **0900**：基于 Unicode 9.0.0 的排序权重版本（UCA 9.0.0）。
- **ai**（accent insensitive）：不区分重音，如 e 与 é 视为相等。
- **ci**（case insensitive）：不区分大小写，如 a 与 A 视为相等。

> 命名中各后缀含义对照：**_ci** 不区分大小写、**_cs** 区分大小写、**_bin** 按二进制编码比较（最严格、区分大小写与重音）；**ai** 不区分重音、**as** 区分重音。组合时顺序固定为字符集、版本、重音、大小写，如 utf8mb4_0900_as_cs 表示区分重音且区分大小写。

> 速记：ci 不辨大小写、cs 辨大小写、bin 二进制最严；ai 不辨重音、as 辨重音。



### 四个级别的字符集设置

#### 服务器级

**服务器级字符集**：是 MySQL 实例启动时的全局默认，通过系统变量 character_set_server 与 collation_server 设定。

- **配置文件方式**：在 my.cnf 或 my.ini 的 [mysqld] 段设置 character-set-server。
- **运行时查看**：通过系统变量读取当前生效值。
- **影响范围**：新建库未显式指定字符集时，继承服务器级默认值。

```sql
-- 查看服务器级字符集与比较规则
SHOW VARIABLES LIKE 'character_set_server';
SHOW VARIABLES LIKE 'collation_server';

-- 运行时修改（仅当前实例，重启后失效）
SET GLOBAL character_set_server = 'utf8mb4';
SET GLOBAL collation_server = 'utf8mb4_0900_ai_ci';
```

> 服务器级是兜底默认：它只参与新建对象时的继承，不会改变已存在库、表、列的字符集。修改后想永久生效必须写入配置文件，否则重启即还原。



#### 数据库级

**数据库级字符集**：是每个数据库自身的默认字符集，新建表未指定时由它继承。

- **建库时指定**：在 CREATE DATABASE 时显式声明 CHARACTER SET 与 COLLATE。
- **查看方式**：通过 information_schema 或 SHOW CREATE DATABASE 读取。
- **修改方式**：ALTER DATABASE 可改默认，但不回改已有表与列。

```sql
-- 创建数据库并指定字符集与比较规则
CREATE DATABASE shop
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

-- 查看数据库的建库语句（含字符集）
SHOW CREATE DATABASE shop;

-- 修改数据库默认字符集（仅影响之后新建的表）
ALTER DATABASE shop
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

> 数据库级字符集只是该库内新建表的默认值。ALTER DATABASE 改变它之后，已存在的表与列不会自动跟着变，需额外对表执行转换（见 ALTER TABLE CONVERT TO CHARACTER SET 一节）。



#### 表级

**表级字符集**：是单张表的默认字符集，建表时声明，新建列未指定时由它继承。

- **建表时指定**：在 CREATE TABLE 末尾加 DEFAULT CHARSET。
- **查看方式**：SHOW CREATE TABLE 可读出表级字符集与比较规则。
- **修改方式**：ALTER TABLE 改默认，但不回改已有列的数据编码。

```sql
-- 建表时指定表级字符集
CREATE TABLE user (
  id INT,
  nickname VARCHAR(50)
) DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;

-- 查看表的实际字符集
SHOW CREATE TABLE user;

-- 修改表默认字符集
ALTER TABLE user
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

> 表级字符集同样只影响之后新增的列。对已有列，ALTER TABLE 仅改默认而不转码；若要连数据一起转换，必须使用 CONVERT TO 语法（见对应四级标题）。



#### 列级

**列级字符集**：可为同一张表中的不同列分别指定字符集，优先级最高，覆盖表级与库级默认。

- **建列时指定**：在列定义后加 CHARACTER SET 与 COLLATE。
- **典型场景**：同一表里大多数列用 utf8mb4，个别定长编码列单独指定。
- **优先级**：列级高于表级高于库级高于服务器级。

```sql
-- 为不同列分别指定字符集
CREATE TABLE article (
  id INT,
  title VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci,
  code CHAR(8) CHARACTER SET ascii
);

-- 查看列的字符集
SHOW FULL COLUMNS FROM article;
```

> 列级是字符集解析的最终裁决者：当列、表、库、服务器四级设定不一致时，以列级为准。但混用多种字符集会增加连接层转码负担，除非确有需要，建议整库统一 utf8mb4。



### 字符集的设置与继承关系

#### 逐级继承规则

**字符集继承**：遵循服务器到数据库到表到列的自上而下继承链，未显式指定的层级沿用上一级默认。

- **新建库**：未指定则用服务器级 character_set_server。
- **新建表**：未指定则用所属库的字符集。
- **新建列**：未指定则用所属表的字符集。
- **显式优先**：任一层级显式声明后，不再向上继承，且该层之下默认沿用此值。

> 继承是缺省才继承：只有未显式写明的层级才会去取上一级的默认。一旦某层显式指定，它就成了其下所有未指定层级的源头。列级若显式指定，则完全不受表级、库级影响。

> 速记：服务器兜底，库承服务器，表承库，列承表；哪层写了哪层算。



#### 只改字符集不改数据的误区

**只改字符集的误区**：ALTER TABLE 仅修改默认字符集时，不会重新编码已存储的数据字节，导致声明与实际存储脱节。

- **现象**：表声明变成 utf8mb4，但旧数据仍以 utf8mb3 或 latin1 字节存放。
- **后果**：新写入的数据用新编码，旧数据用旧编码，排序与比较结果错乱。
- **根因**：DEFAULT CHARSET 只改元数据，不触动既有行的字节。

```sql
-- 这种写法只改默认，不转已有数据
ALTER TABLE user DEFAULT CHARSET = utf8mb4;

-- 旧数据的字节编码并未改变，需用 CONVERT TO 才真正转码
```

> [!WARNING]
> **警告内容**：这是最常见的乱码来源之一：表头写着 utf8mb4，底层却是 latin1 字节，客户端按 utf8mb4 解读自然得到乱码。确认是否真转码，应查看 SHOW CREATE TABLE 与列的 Collation，而不只看默认字符集变量。



#### ALTER TABLE CONVERT TO CHARACTER SET

**CONVERT TO CHARACTER SET**：是真正对既有数据执行重新编码的语句，会按目标字符集转换每行的字节。

- **作用**：把表中所有字符列的数据从原编码转换为目标编码。
- **同时改比较规则**：可附带 COLLATE 一并修改排序规则。
- **代价**：大表转换会锁表并重写数据，需在低峰期执行。

```sql
-- 真正把整张表（含数据）转为 utf8mb4
ALTER TABLE user
  CONVERT TO CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

> CONVERT TO 与单纯改 DEFAULT CHARSET 的根本区别是否动数据：前者重写字节、彻底消除编码错配；后者只改声明。若表里已混入错误编码的历史数据，先用备份验证转换结果，再在业务低峰执行，避免锁表影响线上。



### 客户端与服务器通信时的字符集

#### character_set_client、character_set_connection、character_set_results 三者的作用与转换过程

**通信三变量**：character_set_client、character_set_connection、character_set_results 控制客户端请求与服务器响应在三个环节的字符集。

- **character_set_client**：服务器把客户端发来的 SQL 当作何种字符集来解读。
- **character_set_connection**：服务器内部处理（如常量比较、转码）使用的字符集。
- **character_set_results**：服务器把返回结果编码成何种字符集发给客户端。

```sql
-- 分别查看三个通信字符集
SHOW VARIABLES LIKE 'character_set_client';
SHOW VARIABLES LIKE 'character_set_connection';
SHOW VARIABLES LIKE 'character_set_results';
```

> 转换过程为：客户端请求先按 character_set_client 解读，再转成 character_set_connection 参与运算；若列字符集与之不同，还会做一次列级转码；最终结果按 character_set_results 编码回传客户端。三者不一致时，请求或结果易出现乱码。



#### SET NAMES 的含义

**SET NAMES**：是一条一次性设置通信三变量的快捷命令，让客户端、连接、结果三者统一为同一字符集。

- **等价效果**：同时设置 character_set_client、character_set_connection、character_set_results。
- **典型用法**：连接建立后立即 SET NAMES utf8mb4，保证全程一致。
- **不含校对**：SET NAMES 只设字符集，校对规则需用 SET NAMES ... COLLATE 或单独设 collation_connection。

```sql
-- 连接后统一通信字符集（推荐每次建连执行）
SET NAMES utf8mb4;

-- 等价的三条语句
SET character_set_client = utf8mb4;
SET character_set_connection = utf8mb4;
SET character_set_results = utf8mb4;
```

> [!WARNING]
> **警告内容**：SET NAMES 仅影响当前连接会话，断开后失效，因此应在每次建立连接时执行。现代连接器（如 JDBC 的 characterEncoding、各种 ORM 的连接参数）会自动发送等价设置；切勿依赖服务器默认值，否则跨客户端极易乱码。

> 速记：SET NAMES 一令定三处：client 收、connection 算、results 发。



### 乱码的成因与排查

#### 转码流程图解（文字描述）

**乱码本质**：是写入时按 A 编码、读出时按 B 编码解读造成的字节与字符映射错位。

- **写入链路**：客户端字符集到 character_set_client 到 character_set_connection 到列字符集（可能转码）。
- **读出链路**：列字符集到 character_set_results 到客户端字符集。
- **错位点**：链路任一处字符集不一致，且又发生了按错误编码解读，即表现为乱码。

> 用文字描述完整链路：客户端（如终端 UTF-8）发出字节，服务器依 character_set_client 解读，依 connection 处理，存入列字符集；读时反向：列字符集到 results 到客户端依自身字符集显示。只要写入解读字符集与读出解读字符集不同且不可逆，字节被错读成别的字符，便是乱码。



#### 常见乱码场景

**常见乱码**：多发生于 latin1 存储加 utf8mb4 读取，或客户端与服务器字符集不一致的组合。

- **latin1 误存中文**：列是 latin1（单字节），中文按字节原样塞入，读出按 utf8mb4 解读即乱码。
- **未执行 SET NAMES**：客户端发 UTF-8 字节，服务器按默认 latin1 解读，全程错位。
- **表里混用编码**：旧数据 latin1 字节、新数据 utf8mb4 字节，排序比较错乱。

```sql
-- 一个典型误用：表是 utf8mb4，但连接未设 NAMES，且终端是 gbk
-- 插入的中文在链路中被反复错转，最终显示乱码
INSERT INTO user (nickname) VALUES ('张三');
SELECT nickname FROM user;
```

> 最隐蔽的乱码是能存能取但内容已错：latin1 列会把任意字节原样接收（因为它不校验），表面上插入成功，按 utf8mb4 读出就成了乱码方块。这类问题靠 SHOW FULL COLUMNS 看列 Collation 即可暴露。



#### 排查步骤

**乱码排查**：按客户端到连接变量到列字符集到结果变量的顺序逐环核对，定位错位环节。

- **第一步**：确认客户端（终端、程序、文件）实际使用的字符集。
- **第二步**：查看 character_set_client、connection、results 是否一致且匹配客户端。
- **第三步**：查看目标列 Collation，确认与 connection 是否兼容。
- **第四步**：用 HEX 函数查看字节，判断数据本身是否已被错误编码。

```sql
-- 用 HEX 看底层字节，判断中文是否以 utf8mb4（通常 E4 开头三字节）存放
SELECT HEX(nickname) FROM user WHERE id = 1;

-- 逐环查看当前会话字符集
SHOW VARIABLES LIKE 'character_set_%';
```

> 排查铁律：先看 HEX 字节、再看变量、最后看显示。若 HEX 显示的字节本就是错误的（如中文被存成 latin1 单字节），则问题出在写入环节；若字节正确但显示乱码，则问题在 character_set_results 或客户端显示设置。定位到环节后再对症修正，切忌盲目 ALTER TABLE。

> 速记：乱码三查：查客户端、查三变量、查列 Collation；HEX 验字节定真凶。
