## 事务基础与 ACID

### 事务的基本操作

#### 事务是什么

**事务把一组语句捆绑成原子工作单元**：要么全做，要么全不做。

- 经典样例：转账 = 扣款加入账，两步必须同生共死
- 事务中间状态对外不可见（由隔离级别决定可见程度）
- 没有事务的数据库等于没有“撤销”的能力
- InnoDB 支持事务，MyISAM 不支持，选引擎先问要不要事务

> 事务的价值在失败路径：顺利时感觉不到它，断电、崩溃、并发冲突时它是唯一防线。评估一个系统要不要事务，问“中途失败能否接受半成品数据”。

**速记**：**一组语句同生死，价值显现在失败时**。

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```



#### 显式事务与自动提交

**autocommit 默认开启**：每条语句自成事务，显式事务把它关掉。

- BEGIN 或 START TRANSACTION 开启事务
- COMMIT 提交，ROLLBACK 回滚到事务起点
- autocommit = 1 时单条语句执行完立即隐式提交
- 显式 BEGIN 期间自动提交被挂起，直到 COMMIT 或 ROLLBACK
- SET autocommit = 0 会话级关闭后，每条语句都要手动提交

> autocommit = 0 的连接忘记 COMMIT 是长事务与锁等待的常见源头：连接池里的连接带着未提交事务被复用，故障面扩大到整个池子。除非有明确理由，保持默认自动提交加显式 BEGIN。

**速记**：**默认单句即提交，BEGIN 圈出工作单元，用完必收口**。



#### SAVEPOINT 部分回滚

**SAVEPOINT 在事务内立书签**：可退回中途某一步而不全弃。

- SAVEPOINT 名称：设立保存点
- ROLLBACK TO 名称：回滚到保存点，保存点之前的操作保留
- RELEASE SAVEPOINT 名称：删除保存点
- 整个 ROLLBACK（不带 TO）仍然撤销全部

> 保存点适合“多步导入、某步失败跳过继续”的场景：循环内每批设一个保存点，失败回滚到上一点。注意保存点是事务内的临时标记，COMMIT 后全部消失。

**速记**：**书签立中途，回滚退到签，提交全清零**。



### 隐式提交与长事务

#### DDL 与隐式提交

**事务中途执行 DDL 会先自动提交**：这是隐式提交最常见的一处。

- CREATE、ALTER、DROP 等 DDL 触发隐式提交
- DCL（GRANT、REVOKE）同样隐式提交
- 隐式提交后，之前的 DML 已成定局，无法回滚
- “事务里加个建表语句”是真实存在过的事故

> 混合 DDL 与 DML 的事务是伪事务：DDL 一到，边界即断。事务体内只放 DML，结构变更单独走变更流程。

**速记**：**DDL 一到边界断，事务体内只放 DML**。



#### 长事务的危害

**长事务是数据库的头号慢性病**： undo、锁、主从延迟三处同时恶化。

- undo log 不能清理：MVCC 版本链越长，老事务挡住一切
- 锁持有时间拉长：锁等待、死锁概率同步上升
- 主从延迟放大：大事务在从库重放同样耗时
- 排查入口：information_schema.innodb_trx 看运行中的事务

> 长事务的成因多为“事务里夹了非数据库动作”：调外部接口、等用户输入、批量过大。解法是把事务切薄——外部调用移出事务，大批量分批提交。

**速记**：**长事务三宗罪，undo 锁延迟，切薄是解药**。

```sql
SELECT trx_id, trx_started, trx_rows_modified
FROM information_schema.innodb_trx
ORDER BY trx_started;
```



### ACID 四性

#### 四性逐项定义

**ACID 是事务的合同条款**：每一项都有明确的实现归属。

- 原子性 Atomicity：全做或全不做，由 undo log 保证
- 一致性 Consistency：事务前后完整性不被破坏
- 隔离性 Isolation：并发事务互不干扰，由锁与 MVCC 保证
- 持久性 Durability：提交即落定，由 redo log 保证

> 一致性是目的，其余三者是手段：原子性管“做没做”，隔离性管“看见什么”，持久性管“丢没丢”，三者合力守住一致性。这个归属关系是面试与架构设计的通用答案。

**速记**：**原子 undo 隔离锁，持久 redo，一致性是目的**。



#### 并发三问题

**并发事务的三个经典病灶**：脏读、不可重复读、幻读，症状逐级加深。

- 脏读：读到别人还没提交的数据，对方回滚你就错了
- 不可重复读：同一事务内两次读同一行，值不一样（别人提交了更新）
- 幻读：同一事务内两次范围查询，行数不一样（别人提交了插入）
- 三者层次递进：值不稳定到行集不稳定

> 三病灶是隔离级别设计的靶子（33 篇）：每种级别就是“愿意容忍哪些病灶”的选择。区分不可重复读与幻读的关键：前者针对单行的值，后者针对结果集的成员。

**速记**：**脏读见未提交，重复读值变，幻读行数飘**。



### 综合运用

#### 事务使用守则

**事务要小、要短、要干净**：三词守则覆盖大多数最佳实践。

- 小：一次事务只做一件事，语句数可控
- 短：外部调用、用户交互一律移出事务
- 干净：只包含 DML，DDL 与 DCL 另行处理
- 兜底：异常路径确保 ROLLBACK，连接归还前确认无遗留事务

> 事务的工程纪律与语法同等重要：绝大多数事务事故不是不会写 COMMIT，而是事务边界划得随手。评审事务代码时先看边界，再看语句。

**速记**：**事务要小要短要干净，边界先于语句**。



#### 失败路径的设计意识

**写事务先写失败分支**：回滚路径想清楚了才算设计完成。

- 每个事务问三个问题：哪一步可能失败、失败后数据什么样、如何恢复
- 部分成功的业务语义：用 SAVEPOINT 还是整单重试
- 死锁与锁等待超时的重试策略放应用层
- 提交后的补偿：业务层对账与补偿事务

> InnoDB 兜住单库原子性，但跨服务、跨库的一致性需要业务层设计（Saga、对账补偿）。数据库事务是基石，不是全部答案。

**速记**：**先想失败再写成功，库内原子库外补偿**。
