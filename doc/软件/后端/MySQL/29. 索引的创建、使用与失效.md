## 索引的创建、使用与失效

### 索引的类型与创建

#### 索引家族一览

**六类索引覆盖绝大多数需求**：按唯一性与列数选择。

- 主键索引：唯一加非空，一棵聚簇树
- 唯一索引：值不得重复，可含 NULL（NULL 不参与唯一判定）
- 普通索引：纯加速，无约束
- 联合索引：多列合成一个索引，列顺序是学问
- 前缀索引：对长字符串列取前 N 字符建索引
- 全文索引：倒排结构，服务文本搜索

> 唯一约束用唯一索引表达，这是数据库层的最后防线，应用层校验挡不住并发重复。业务上“理论唯一”的列都值得一条唯一索引。

**速记**：**主键唯一普通三基础，联合前缀全文三扩展**。



#### 创建与删除语法

**建索引三条路，删索引一句话**：语法不多，时机才贵。

- 建表时：CREATE TABLE ... INDEX idx_col (col)
- 事后加：CREATE INDEX idx_col ON 表 (col)
- ALTER TABLE 表 ADD INDEX idx_col (col)，唯一索引换 ADD UNIQUE
- 删除：DROP INDEX idx_col ON 表 或 ALTER TABLE ... DROP INDEX

> 大表在线加索引 8.0 默认 INSTANT 或 INPLACE，不长时间锁表；但仍是重操作，错峰执行并盯着磁盘与主从延迟。联合索引与列顺序的设计见下节。

**速记**：**三条路建一句话删，大表操作错峰跑**。

```sql
CREATE INDEX idx_status_created ON orders (status, created_at);
ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);
```



#### 联合索引与最左前缀

**联合索引按列顺序排序**：从最左列开始连续匹配才有效。

- 索引 (a, b, c) 的序：先按 a 排，a 同再按 b，b 同再按 c
- WHERE a = 1 AND b = 2 可用；只有 b = 2 用不上
- a = 1 AND c = 3 只有 a 部分生效，c 无法继续定位
- 遇到范围查询（a 大于 x）后，右侧列的等值定位失效
- 设计口诀：等值列在前，范围列在后，区分度高的在前

> 最左前缀不是“必须从第一列查”，而是“不能跳过中间列”。理解索引即排序，这些规则全部可从字典序推导，不必死背。

**速记**：**索引即字典序，等值连续走，范围断后路**。



#### 覆盖索引

**查询的列全在索引里就免回表**：性能提升立竿见影。

- 联合索引 (a, b) 上 SELECT a, b 且 WHERE a = x：无需回表
- EXPLAIN 的 Extra 出现 Using index 即覆盖命中
- 主键值也在所有二级索引里：按主键查可直接用任意二级索引覆盖
- 盲目把所有列塞进联合索引是反向优化：索引太宽，写放大陡增

> 覆盖索引是高频查询的专用武器：为最重要的几条查询定制列组合，而不是为所有查询造宽索引。收益要拿 EXPLAIN 验证。

**速记**：**要的列索引都有，Extra 见 Using index**。



#### 前缀索引与区分度

**前缀索引用列的前 N 字符建树**：省空间，也丢能力。

- 语法：CREATE INDEX idx_name ON users (name(10))
- N 的选择看区分度：COUNT(DISTINCT LEFT(col, n)) 除以总行数，接近 1 才值
- 前缀索引无法用于覆盖索引与 ORDER BY（索引里没有完整值）
- 适合长字符串列（如 URL、邮箱）的等值查询场景

> 计算区分度是数据驱动的选 N 法：从 5、10、20 试起，区分度曲线走平即停。哈希生成列加索引是另一种长列方案，等值场景可对比选用。

**速记**：**前缀省空间，区分度定长度，覆盖排序两头丢**。



### 索引失效

#### 失效场景清单

**索引失效多半是查询写法踩了雷**：八类场景按频率排序。

- 对索引列用函数或表达式：YEAR(create_time) = 2026
- 隐式类型转换：数字列传字符串（15 篇）
- 隐式字符集转换：两表连接列字符集不同
- LIKE 以百分号开头：%abc
- OR 两侧混有非索引列：任一侧无索引则全表扫
- 联合索引不满足最左前缀
- NOT IN、不等于、IS NOT NULL：视区分度，优化器可能弃用
- 统计信息失真导致优化器误判

> 前五类是“结构性失效”，改写即可恢复；后三类是“优化器弃用”，要靠改写引导或更新统计信息。失效不等于一定全表扫，EXPLAIN 是唯一裁判。

**速记**：**函数转换乱序三类结构性失效，弃用与否 EXPLAIN 说了算**。

```sql
-- 失效与改写对照
-- 失效：WHERE DATE(created_at) = '2026-09-07'
-- 改写：
SELECT * FROM orders
WHERE created_at >= '2026-09-07' AND created_at < '2026-09-08';
```



#### 隐式转换的典型现场

**数字列传字符串是最贵的参数类型 bug**：一行代码拖垮一张表。

- user_id 是 bigint，代码传 '123'：列被套上转换，索引报废
- 字符串列传数字则相反：常量转换，索引安然无恙
- 测试环境数据量小，全表扫毫秒级，上线即事故
- 防线在应用层：ORM 字段类型、DTO 校验、code review

> EXPLAIN 判定法：type 从 ref 掉到 ALL、key 变 NULL，参数类型对不上几乎是唯一解释。这类问题多数不是 DBA 修的，是写代码的人防的。

**速记**：**列变字符串索引死，常量变数字无所谓**。



#### 索引下推 ICP

**索引下推让过滤提前在索引层完成**：5.6 引入的免费午餐。

- 场景：联合索引 (name, age)，WHERE name LIKE '陈%' AND age = 25
- 无 ICP：索引按 name 定位后逐条回表，再过滤 age
- 有 ICP：age 条件在索引内先判，不满足的行根本不回表
- 标志：EXPLAIN 的 Extra 出现 Using index condition

> ICP 告诉你优化器在持续进化：旧的失效口诀要按版本重新校准。判断一个“失效”场景的真实代价，永远以当前版本的 EXPLAIN 输出为准。

**速记**：**ICP 把过滤搬到索引层，回表前先淘汰**。



### 索引治理

#### 区分度与索引价值

**区分度低的列索引收益差**：性别列是经典反例。

- 区分度 = 不重复值数除以总行数，越接近 1 越值
- 性别、状态这类低基数列单独建索引通常不划算
- 但低基数列放进联合索引前缀可以服务特定组合查询
- 优化器对低区分度索引会倾向全表扫，建了也可能不用

> “该不该建索引”的答案永远是数据相关：看查询模式、行数、区分度三者，没有脱离业务的通用规则。

**速记**：**区分度定价值，低基数列入组合才有用**。



#### 冗余索引与闲置索引

**索引是资产也是负担**：定期清理是治理的一部分。

- 冗余：已有 (a, b) 再建 (a)，前者已覆盖后者的能力
- 闲置：长期无人使用的索引白耗写入与空间
- sys 库的 schema_unused_indexes 报告闲置索引
- 删除前观察一个完整业务周期，避开周期性任务

> 写入越多的表，索引税越重：每个索引都要同步维护。索引清理与索引创建同样需要评审，别让“加个索引试试”成为团队的默认动作。

**速记**：**冗余看前缀包含，闲置看 sys 报告，删前观察一周期**。



#### 索引设计评审清单

**建索引前过五问**：问完再 CREATE。

- 这条索引服务哪条具体查询？说不出的不建
- 列顺序符合最左前缀与查询习惯吗？
- 覆盖得了高频查询的关键列吗？
- 区分度与行数撑得起收益吗？
- 写入侧付得起维护税吗？

> 索引设计是查询与写入的联合作战：每条索引都要有明确的受益查询，每条查询都应有明确的服务索引。双向对账，索引才不泛滥。

**速记**：**索引为查询而生，五问对账再落笔**。
