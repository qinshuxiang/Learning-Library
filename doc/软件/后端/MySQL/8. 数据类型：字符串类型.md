## 数据类型：字符串类型

### 字符串家族概览

字符串类型用于保存文本与二进制字节序列，按"是否区分字符集"与"是否按行内存储"可划分为若干家族。

- **CHAR / VARCHAR**：定长与变长文本，受字符集与排序规则影响。
- **TINYTEXT / TEXT / MEDIUMTEXT / LONGTEXT**：长文本，主体溢出到独立页存储。
- **BINARY / VARBINARY**：定长与变长二进制字节串，无字符集。
- **TINYBLOB / BLOB / MEDIUMBLOB / LONGBLOB**：二进制大对象，与 TEXT 一一对应。
- **ENUM**：枚举，取值限定在预定义列表中的单一成员。
- **SET**：集合，取值可为预定义列表中零到多个成员的组合。

> 字符串类型表面上琳琅满目，实则可归纳为**文本串**与**二进制串**两条主线：带字符集的是文本，按字节解释的是二进制。后续各节均沿这两条主线展开。

#### 家族划分的两大主线

**存储主线**：是区分字符串类型边界的根本依据，决定数据如何比较、排序与填充。

- **文本主线（CHAR、VARCHAR、TEXT、ENUM、SET）**：依赖字符集与排序规则（collation），比较按字符而非字节。
- **二进制主线（BINARY、VARBINARY、BLOB）**：按字节原样存储，比较按字节数值，无字符概念。

```sql
CREATE TABLE main_line (
  txt VARCHAR(10) CHARACTER SET utf8mb4,
  bin VARBINARY(10)
);
INSERT INTO main_line VALUES ('AB', 0xAB);
SELECT txt, bin FROM main_line;
```

> 同一条 SQL 里混用两条主线的字符串会触发隐式转换，往往导致**索引失效**或结果不符合预期。建表时应当明确每一列的归属主线。



### CHAR

#### 定长特性

**CHAR**：是定长字符串类型，无论实际存入多少字符，都会占用声明长度的固定空间，不足处以空格填充。

- **存储方式**：写入时右侧补空格至声明长度，读取时尾部空格被去除。
- **适用数据**：长度高度稳定、几乎不变的短字符串，如国家代码、哈希前缀。
- **性能特征**：由于长度固定，更新时不会造成行迁移，随机访问定位更快。

```sql
CREATE TABLE char_fixed (
  code CHAR(4) CHARACTER SET utf8mb4
);
INSERT INTO char_fixed VALUES ('ab');
SELECT code, CHAR_LENGTH(code), LENGTH(code) FROM char_fixed;
-- 'ab'、2、8（utf8mb4 下每个字符 4 字节）
```

> CHAR 的"定长"指的是**分配长度固定**，而非"存多少占多少"。存入 'ab' 到 CHAR(10)，磁盘上仍是 10 个字符宽，末尾空格仅作填充，读取时被剥离。



#### CHAR(M) 中 M 的含义与取值

**CHAR(M) 的 M**：表示声明的字符个数上限，取值范围在 0 到 255 之间，与字符集的字节宽度无直接关系。

- **M 是字符数**：一个字符可能占多个字节，但 M 按"字符"而非"字节"计数。
- **M 可取 0**：CHAR(0) 仅占用 1 位（bit）存储，用于仅表示"存在与否"的标记列。
- **超出报错**：写入超过 M 个字符的数据会被截断或报错，取决于 SQL 模式。

```sql
CREATE TABLE char_m (
  code CHAR(3) CHARACTER SET utf8mb4,
  flag CHAR(0)
);
INSERT INTO char_m (code, flag) VALUES ('ABC', '');
SELECT CHAR_LENGTH(code) FROM char_m; -- 3
```

> 声明 CHAR 时务必留意 **M 的单位是字符**而非字节：在 utf8mb4 下 CHAR(10) 最多可占 40 字节，规划行长时需按最坏情况估算。



#### 尾部空格被去除的行为

**尾部空格去除**：是 CHAR 读取时的固有行为，MySQL 会在返回结果前剥离填充空格与真实尾部空格。

- **写入填充空格被剥离**：'ab   ' 存入 CHAR(5) 后，读取得到 'ab' 而非 'ab   '。
- **字符串比较时也被剥离**：CHAR 列之间的比较会先去除尾部空格再比对。
- **BINARY 下不剥离**：二进制串保留尾部空格，这是与 CHAR 的关键差异。

```sql
CREATE TABLE char_space (
  c CHAR(10) CHARACTER SET utf8mb4
);
INSERT INTO char_space VALUES ('hello');
SELECT c, CHAR_LENGTH(c) FROM char_space; -- 'hello'，长度为 5
```

> 这一行为常引发"明明存了空格却读不到"的困惑。若业务需要**保留尾部空格**，应改用 VARCHAR 或 BINARY，而非 CHAR。



#### CHAR 与 BINARY 的空格差异

**CHAR 与 BINARY 空格差异**：同样声明定长，CHAR 按字符补空格并去尾，BINARY 按字节补 0x00 且保留，二者不可混为一谈。

- **CHAR 填充 0x20（空格）**：读取时右侧空格被去除，'ab' 与 'ab ' 视为相等。
- **BINARY 填充 0x00**：读取保留 0x00，'ab' 与 'ab\x00' 视为不等。
- **比较语义**：CHAR 受排序规则影响（可能不区分大小写），BINARY 纯按字节数值比较。

```sql
CREATE TABLE char_vs_bin (
  c CHAR(4) CHARACTER SET utf8mb4,
  b BINARY(4)
);
INSERT INTO char_vs_bin VALUES ('ab', 'ab');
SELECT c = 'ab  ', b = 'ab' FROM char_vs_bin; -- 1（真）、0（假）
```

> **CHAR 吞空格、BINARY 留 0x00** 是最易混淆的点。需要区分大小写或保留精确字节时，必须用 BINARY 系列而非 CHAR。



### VARCHAR

#### 变长特性

**VARCHAR**：是变长字符串类型，仅占用实际数据长度外加少量长度描述字节，不强制填充至声明长度。

- **按需分配**：存入 'ab' 到 VARCHAR(100) 只占 2 字符外加长度字节，而非 100 字符。
- **保留尾部空格**：与 CHAR 不同，VARCHAR 完整保留写入的尾部空格，不做去除。
- **适用数据**：长度波动明显的中长文本，如用户名、地址、备注。

```sql
CREATE TABLE varchar_var (
  name VARCHAR(100) CHARACTER SET utf8mb4
);
INSERT INTO varchar_var VALUES ('ab');
SELECT name, CHAR_LENGTH(name), LENGTH(name) FROM varchar_var; -- 'ab'、2、6
```

> 变长带来"省空间"的收益，也带来**更新膨胀**的代价：把短值改成更长值时，若行内空间不足，InnoDB 可能触发页分裂或行溢出，写入成本高于 CHAR。



#### 需要 1 到 2 字节记录长度

**长度前缀**：是 VARCHAR 在行内额外保存的、描述实际数据字节数的头部，占用 1 或 2 字节。

- **数据字节数不超过 255**：使用 1 字节记录长度。
- **数据字节数超过 255**：使用 2 字节记录长度。
- **记的是字节数**：长度前缀记录的是**字节数**而非字符数；多字节字符会让字节数大于字符数。

```sql
CREATE TABLE varchar_len (
  a VARCHAR(10) CHARACTER SET utf8mb4,   -- 可能数据短，1 字节前缀
  b VARCHAR(300) CHARACTER SET utf8mb4   -- 可能超 255 字节，2 字节前缀
);
INSERT INTO varchar_len VALUES ('中', '中文测试内容');
```

> 计算 VARCHAR 实际占用时，别忘把**长度前缀**计入：真实字节数 = 数据字节数 + 1 或 2（前缀）+ 是否为 NULL 的标记位。



#### VARCHAR(M) 中 M 是字符数

**VARCHAR(M) 的 M**：与 CHAR 一致，表示字符个数上限而非字节数，理论最大值受行大小与字符集共同约束。

- **M 的单位是字符**：utf8mb4 下一个字符最多 4 字节，但 M 仍按字符计数。
- **M 的理论上限**：在单行 65535 字节限制下，结合字符集字节宽度推算（详见下一节）。
- **超长报错**：写入字符数超过 M 会被截断或报错。

```sql
CREATE TABLE varchar_m (
  name VARCHAR(50) CHARACTER SET utf8mb4
);
INSERT INTO varchar_m VALUES ('张三李四王五');
SELECT CHAR_LENGTH(name) FROM varchar_m; -- 6（字符数，与字节无关）
```

> 常被误认 M 是字节数。记住 **CHAR 与 VARCHAR 的 M 都是字符数**，真正限制字节的是"单行 65535 字节"这条硬规则。



#### MySQL 一行 65535 字节的限制

**行大小限制**：是 MySQL 对一条记录（不含溢出页）总字节数的硬性约束，所有列字节之和不得超过 65535。

- **适用范围**：限制的是一行内联存储的字节总量，含变长前缀与 NULL 标记。
- **与字符集联动**：utf8mb4 下每个字符最多 4 字节，会更快触及上限。
- **TEXT/BLOB 例外**：这类大对象仅在内联保留极小指针，主体存到溢出页，不计入 65535。

```sql
-- 以下建表会失败：两个 varchar(32768) 在 utf8mb4 下远超 65535 字节
CREATE TABLE too_wide (
  a VARCHAR(32768),
  b VARCHAR(32768)
) CHARACTER SET utf8mb4;
-- ERROR 1118 (42000): Row size too large
```

> 65535 是**字节**不是字符，且是整行共享的预算。设计宽表时应优先把大文本拆到 TEXT 列或独立表，避免单行超限。



### CHAR 与 VARCHAR 的对比

#### 存储占用

**存储占用**：CHAR 按声明长度固定分配，VARCHAR 按实际长度加前缀分配，两者空间效率相反。

- **CHAR 占用**：声明字符数 × 单字符最大字节数（如 utf8mb4 下 ×4），外加 NULL 标记位，恒定不变。
- **VARCHAR 占用**：实际字符字节数 + 1 或 2 字节长度前缀 + NULL 标记位，随数据变化。
- **短数据场景**：VARCHAR 明显更省；接近满长时两者接近，CHAR 反而因无前缀略省。

```sql
CREATE TABLE compare_store (
  c CHAR(20) CHARACTER SET utf8mb4,
  v VARCHAR(20) CHARACTER SET utf8mb4
);
INSERT INTO compare_store VALUES ('hi', 'hi');
-- c 占 80 字节（20×4），v 占 2 字节数据 + 1 前缀 = 3 字节
```

> 对比要点：**CHAR 空间恒定、VARCHAR 空间随数据浮动**。选错类型要么浪费空间，要么因行过大影响性能。



#### 尾部空格处理

**尾部空格**：CHAR 在读取时剥离尾部空格，VARCHAR 完整保留，这是二者最易踩坑的差异。

- **CHAR**：写入与读取均去除尾部空格，比较时亦去除。
- **VARCHAR**：原样保留写入的尾部空格，比较时区分。
- **比较影响**：'ab' 与 'ab ' 在 CHAR 列上相等，在 VARCHAR 列上不等。

```sql
CREATE TABLE space_cmp (
  c CHAR(10) CHARACTER SET utf8mb4,
  v VARCHAR(10) CHARACTER SET utf8mb4
);
INSERT INTO space_cmp VALUES ('ab', 'ab');
INSERT INTO space_cmp VALUES ('ab ', 'ab ');
SELECT COUNT(*) FROM space_cmp WHERE c = 'ab';   -- 2，尾部空格被忽略
SELECT COUNT(*) FROM space_cmp WHERE v = 'ab';   -- 1，尾部空格被区分
```

> **CHAR 去空格、VARCHAR 留空格**是铁律。涉及精确匹配（如令牌、校验值）时，选错类型会导致"明明相等却查不到"或反之。



#### 适用场景

**适用场景**：由数据长度的稳定性决定，定长短码用 CHAR，波动文本用 VARCHAR。

- **CHAR 适合**：长度固定的编码，如国家代码（CHAR(2)）、性别标记、MD5（CHAR(32)）、UUID 去横杠（CHAR(32)）。
- **VARCHAR 适合**：长度差异大的名称、地址、描述、评论等。
- **边界情形**：长度高度一致且较短时，CHAR 的定长优势（无前缀、无行迁移）才显现。

```sql
CREATE TABLE user_profile (
  country_code CHAR(2) CHARACTER SET ascii,
  username    VARCHAR(64) CHARACTER SET utf8mb4,
  bio         VARCHAR(500) CHARACTER SET utf8mb4
);
```

> 选型关键：**长度稳定且短 → CHAR；长度飘忽 → VARCHAR**。不要因为"省事"全表 VARCHAR，也不该为定长场景硬套 VARCHAR。



#### 速记：定长用 CHAR，变长用 VARCHAR

**速记口诀**：把定长与变长的本质压缩为一句话，便于考场上快速判断。

> **定长用 CHAR，变长用 VARCHAR**：长度固定选 CHAR，长度不定选 VARCHAR；尾部空格是否保留是二者最直观的区分标志。

> 进一步记：**CHAR 恒定、VARCHAR 浮动；CHAR 吞空格、VARCHAR 留空格**。遇到"长度会不会变"之问，先答这句话再展开。



### VARCHAR 长度上限的计算

#### 受字符集影响的例子

**长度上限**：由单行 65535 字节减去其他列与开销，再除以单字符字节数推算，字符集直接决定 M 的最大取值。

- **utf8mb4 单字符最多 4 字节**：VARCHAR 还需 2 字节长度前缀。
- **单列极限推算**：(65535 − 2 前缀 − 1 NULL 位) / 4 ≈ 16383，故 VARCHAR(16383) 在 utf8mb4 下接近上限。
- **ascii 单字符 1 字节**：同样预算下 M 可接近 65532。

```sql
-- utf8mb4 下接近上限的可建表写法
CREATE TABLE max_varchar (
  a VARCHAR(16383) CHARACTER SET utf8mb4
);

-- 超过则报错
CREATE TABLE too_long (
  a VARCHAR(16384) CHARACTER SET utf8mb4
); -- ERROR: Column length too big for column 'a'
```

> **字符集越宽，能声明的字符数 M 越小**。utf8mb4 的 VARCHAR(16383) 不是巧合，正是 65535 字节预算除以 4 的结果。



#### NOT NULL 的影响

**NOT NULL 约束**：会减少行的 NULL 标记位开销，从而略微提升 VARCHAR 可用的字节预算。

- **可空列**：每行需 1 位（bit）NULL 标记，多个可空列共享字节。
- **NOT NULL 列**：免除此标记位，等于多腾出极少量空间给行总长。
- **影响幅度**：对单行 65535 限制而言，NOT NULL 带来的空间增益极小，但语义上应避免无意义的"可空"。

```sql
CREATE TABLE null_effect (
  a VARCHAR(16383) NOT NULL CHARACTER SET utf8mb4,
  b VARCHAR(16383) NOT NULL CHARACTER SET utf8mb4
);
-- 两列均接近上限，NOT NULL 省下的标记位让它们能并存
```

> NOT NULL 主要价值在**数据语义与索引效率**，而非腾空间。不要为了"多塞几个字符"而滥用 NOT NULL，应按业务是否需要缺省值决定。



### TEXT 系列

#### 四种 TEXT 的容量与所需长度字节

**TEXT 系列**：是变长长文本类型，按容量从大到小分四种，每种用不同长度的前缀字节记录数据大小。

- **TINYTEXT**：最大 255 字节，用 1 字节记录长度。
- **TEXT**：最大 65535 字节（64KB），用 2 字节记录长度。
- **MEDIUMTEXT**：最大 16777215 字节（16MB），用 3 字节记录长度。
- **LONGTEXT**：最大 4294967295 字节（4GB），用 4 字节记录长度。

```sql
CREATE TABLE text_sizes (
  t1 TINYTEXT CHARACTER SET utf8mb4,
  t2 TEXT CHARACTER SET utf8mb4,
  t3 MEDIUMTEXT CHARACTER SET utf8mb4,
  t4 LONGTEXT CHARACTER SET utf8mb4
);
```

> 四种 TEXT 的区别仅在**容量上限与长度前缀字节数**。选 TEXT 而非 VARCHAR 的临界点，是数据可能超过单行 65535 字节预算。



#### TEXT 不能有默认值

**TEXT 默认值**：在 MySQL 中不被允许，声明默认值时建表会报错，这是与 VARCHAR 的重要差异。

- **语法限制**：TEXT、BLOB 及其变种列不能指定 DEFAULT。
- **替代方案**：将列设为可空，插入时显式给值，或改用 VARCHAR 配合默认值。
- **版本说明**：MySQL 8.0 下明确禁止 TEXT 设默认值。

```sql
-- 以下会报错
CREATE TABLE bad_default (
  content TEXT DEFAULT 'hello'
); -- ERROR: BLOB, TEXT, GEOMETRY or JSON column 'content' can't have a default value
```

> **TEXT 无默认值**是常见踩坑点。需要"默认空文本"语义时，应让列可空并在应用层处理，或改用 VARCHAR(含默认)。



#### TEXT 单独存储（行溢出 Off Page）

**行溢出（Off Page）**：是 InnoDB 处理超长列的机制，TEXT 等大对象主体存到独立溢出页，行内仅留指针。

- **行内仅留指针**：InnoDB 在行内保留约 20 字节指针指向溢出页，主体在页外。
- **读取成本**：访问 TEXT 需额外寻址溢出页，随机读成本高于行内 VARCHAR。
- **与 65535 的关系**：正因溢出存储，TEXT 不计入单行 65535 字节限制。

```sql
CREATE TABLE off_page (
  id BIGINT PRIMARY KEY,
  article LONGTEXT CHARACTER SET utf8mb4
);
-- article 主体在溢出页，行内只占指针
```

> 溢出存储让 TEXT 能突破行大小限制，代价是**额外 I/O**。频繁读取的大文本仍建议评估是否该放对象存储而非数据库。



#### TEXT 与 VARCHAR 的取舍

**TEXT 与 VARCHAR 取舍**：取决于数据长度、默认值需求与查询模式，二者并非简单替代。

- **长度边界**：确定不超过 65535 字节且需默认值 → VARCHAR；可能更长或极稀疏 → TEXT。
- **索引差异**：VARCHAR 可对整个列建索引，TEXT 必须指定前缀长度建索引。
- **排序与临时表**：TEXT 在内存临时表中会被强制转成磁盘表，排序性能更差。

```sql
CREATE TABLE pick_type (
  summary VARCHAR(1000) CHARACTER SET utf8mb4,  -- 可建完整索引、可默认
  body    MEDIUMTEXT CHARACTER SET utf8mb4      -- 超长正文，需前缀索引
);
CREATE INDEX idx_body ON pick_type (body(200));
```

> 取舍原则：**中等且规整 → VARCHAR；超长或稀疏大块 → TEXT**。能用 VARCHAR 解决的，优先 VARCHAR，索引与默认值都更友好。



### BINARY 与 VARBINARY

#### 二进制字符串，按字节比较，没有字符集

**BINARY / VARBINARY**：是二进制字节串类型，按字节原样存储与比较，不绑定任何字符集与排序规则。

- **无字符集**：数据被视为原始字节，不参与字符解码，尾部空格（实际是 0x00）也保留。
- **按字节比较**：比较时逐字节比对数值，'A'（0x41）与 'a'（0x61）明确不等，不忽略大小写。
- **定长与变长**：BINARY 定长补 0x00，VARBINARY 变长加长度前缀，对应 CHAR 与 VARCHAR 的二进制版。

```sql
CREATE TABLE bin_demo (
  b BINARY(4),
  vb VARBINARY(16)
);
INSERT INTO bin_demo VALUES (0xDEADBEEF, 0xCAFEBABE);
SELECT HEX(b), HEX(vb) FROM bin_demo;
```

> **BINARY 系列是按字节说话的**。需要区分大小写、存散列值或二进制流时，应优于 CHAR/VARCHAR，避免字符集带来的隐式转换。



#### BINARY 的定长填充与尾部字节

**BINARY 填充**：是定长二进制串的特有行为，写入不足声明长度时右侧补 0x00，且这些 0x00 在读取时保留。

- **填充字节 0x00**：与 CHAR 补空格（0x20）不同，BINARY 补的是零值字节。
- **保留不剥离**：0x00 不参与"空格去除"逻辑，因此 'ab' 与 'ab\x00' 在 BINARY 上不等。
- **排序影响**：0x00 是最小字节值，带填充的短值在排序时靠前。

```sql
CREATE TABLE bin_pad (
  b BINARY(4) CHARACTER SET binary
);
INSERT INTO bin_pad VALUES ('ab');
SELECT HEX(b) FROM bin_pad; -- 61620000（ab 后跟两个 0x00）
```

> **BINARY 补 0x00 且保留**这一细节，常被人用 CHAR 的经验误判。凡是"区分大小写、保留精确字节"的需求，都该交给 BINARY 系列。



### BLOB 系列

#### 四种 BLOB

**BLOB 系列**：是二进制大对象类型，对应 TEXT 的四种容量档位，用于存储图片、文件等原始字节。

- **TINYBLOB**：最大 255 字节，1 字节长度前缀。
- **BLOB**：最大 65535 字节，2 字节长度前缀。
- **MEDIUMBLOB**：最大 16777215 字节，3 字节长度前缀。
- **LONGBLOB**：最大 4294967295 字节，4 字节长度前缀。

```sql
CREATE TABLE blob_sizes (
  b1 TINYBLOB,
  b2 BLOB,
  b3 MEDIUMBLOB,
  b4 LONGBLOB
);
INSERT INTO blob_sizes VALUES (0x01, 0x0203, 0x040506, 0x0708090A);
```

> 四种 BLOB 与四种 TEXT **容量一一对应**，差别只在存储内容是二进制字节还是文本字符。



#### BLOB 与 TEXT 的对应关系与差别

**BLOB 与 TEXT 差别**：二者容量档位平行，但 BLOB 无字符集、按字节排序，TEXT 受字符集与排序规则影响。

- **对应关系**：TINYBLOB↔TINYTEXT、BLOB↔TEXT、MEDIUMBLOB↔MEDIUMTEXT、LONGBLOB↔LONGTEXT。
- **排序比较**：BLOB 按字节数值排序；TEXT 按字符集排序规则排序。
- **默认值**：两者均**不能有默认值**，这是共同限制。

```sql
CREATE TABLE blob_vs_text (
  raw BLOB,
  txt TEXT CHARACTER SET utf8mb4
);
-- 同样的字节流，BLOB 按字节比，TEXT 按字符规则比
```

> 速记：**BLOB 是 TEXT 的二进制孪生兄弟**——容量相同、都不能有默认值，但一个按字节、一个按字符。



### ENUM 与 SET 类型

#### 语法

**ENUM / SET**：是受限于预定义取值集合的字符串类型，建表时在类型后括号中枚举成员。

- **ENUM 语法**：ENUM('值1','值2',...)，一列只能取其中之一。
- **SET 语法**：SET('成员1','成员2',...)，一列可取零到多个成员的组合。
- **存储为字符串**：读写以字符串形式，底层以整数下标实现（见下节）。

```sql
CREATE TABLE enum_set (
  status ENUM('active','inactive','banned') CHARACTER SET utf8mb4,
  roles  SET('read','write','admin') CHARACTER SET utf8mb4
);
INSERT INTO enum_set VALUES ('active', 'read,write');
SELECT status, roles FROM enum_set;
```

> ENUM 与 SET 的"取值白名单"由建表时写死，后续增删成员需 **ALTER TABLE 改表结构**，这是它们最大的运维负担。



#### 底层用整数下标存储

**整数下标**：是 ENUM/SET 的底层表示，每个成员对应一个从 1（或 2 的幂）开始的整数编号，字符串仅作映射。

- **ENUM 下标**：从 1 起递增，'active'=1、'inactive'=2、'banned'=3，存的是编号而非文本。
- **SET 下标**：每个成员是 2 的幂（1、2、4、8…），多个成员以位或组合成整数存储。
- **排序依据**：二者排序按**整数下标**而非字母序，这与直觉常相反。

```sql
INSERT INTO enum_set (status, roles) VALUES ('banned', 'read,admin');
-- status 存 3，roles 存 1|4=5
SELECT status + 0, roles + 0 FROM enum_set; -- 3 与 5
```

> **ENUM/SET 存的是数字不是字符串**，比较与排序都走整数，因此 'active' 未必排在 'banned' 前。索引与聚合也按整数，省空间但易误读。



#### 各自的适用场景与缺点

**适用场景与缺点**：ENUM 适合取值极固定、几乎不变的单一状态；SET 适合固定标签组合；但二者均建议慎用。

- **ENUM 适用**：性别、订单状态等高度稳定的枚举；缺点是改成员要改表结构、迁移麻烦。
- **SET 适用**：权限位、标签组合；缺点是成员扩展性差、查询需位运算。
- **通用缺点**：可移植性差（其他数据库支持不一）、默认值与空串语义易混淆，建议改用字典表。

```sql
-- 更推荐的字典表方案
CREATE TABLE status_dict (
  id TINYINT PRIMARY KEY,
  name VARCHAR(20) NOT NULL
);
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  status_id TINYINT,
  FOREIGN KEY (status_id) REFERENCES status_dict(id)
);
```

> 速记：**ENUM/SET 能省空间，却牺牲了扩展性**。现代实践多用**字典表 + 外键**替代，既能约束取值，又不锁死表结构。



### 字符串类型的选型建议与速记

字符串选型的核心，是在**空间、性能、可维护性**之间取得平衡，而非追求某一项极致。

- **短而定长**：国家码、哈希、UUID 去横杠 → CHAR。
- **长度波动**：用户名、地址、备注 → VARCHAR。
- **超长文本**：文章、日志 → TEXT 系列（按需选档位）。
- **二进制流**：散列、图片、序列化字节 → BINARY/VARBINARY/BLOB。
- **受限取值**：极稳定的状态 → ENUM/SET，否则字典表。

```sql
CREATE TABLE profile_demo (
  id BIGINT PRIMARY KEY,
  country CHAR(2) CHARACTER SET ascii,
  nickname VARCHAR(64) CHARACTER SET utf8mb4,
  avatar MEDIUMBLOB,
  bio TEXT CHARACTER SET utf8mb4
);
```

> 选型优先级：**先判文本还是二进制，再判定长还是变长，最后判是否超长**。能用 VARCHAR 解决的优先 VARCHAR，索引与默认值都更友好。

> 速记总纲：**定长 CHAR、变长 VARCHAR、超长 TEXT、二进制 BLOB；ENUM/SET 省空间但锁表，字典表更灵活**。考试遇到选型，按此顺序逐层排除即可。
