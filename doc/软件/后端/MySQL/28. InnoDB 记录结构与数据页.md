## InnoDB 记录结构与数据页

### 行格式

#### 四种行格式

**行格式决定一行数据在页内怎么摆**：COMPACT 是理解一切的基准。

- COMPACT：紧凑经典格式，5.7 前的默认
- REDUNDANT：远古格式，冗余字段列表占空间，只为兼容
- DYNAMIC：5.7 起默认，大字段完全外置溢出页
- COMPRESSED：在 DYNAMIC 基础上压缩页，CPU 换空间
- 指定方式：建表或改表时 ROW_FORMAT = DYNAMIC

> 现代版本下 COMPACT 与 DYNAMIC 的差别集中在溢出列处理：前者溢出页仍存前 768 字节前缀，后者只留 20 字节指针。行格式选择影响的是大字段表的存储效率。

**速记**：**COMPACT 打底 DYNAMIC 默认，压缩用 COMPRESSED，REDUNDANT 只怀旧**。



#### COMPACT 结构拆解

**一行 COMPACT 记录分五段**：从变长列表到真实数据，逐段紧凑排列。

- 变长字段长度列表：逆序记录各变长列的实际长度
- NULL 值列表：每个允许 NULL 的列占一位，1 表示 NULL
- 记录头信息：5 字节，含下一记录偏移、类型、删除标记等
- 事务 id 与回滚指针两个隐藏列
- 真实数据：各列的值，NULL 列在此处不占空间

> NULL 列在值区不占空间但要进 NULL 位图：值省了空间，位图花了空间。全 NULL 的稀疏表靠位图省出真金白银，密集非空的表反而是负担。

**速记**：**变长逆序 NULL 位图，头部五字节隐藏两列**。



#### 隐藏列三兄弟

**每行自带事务 id、回滚指针、行 id**：MVCC 与兜底主键全靠它们。

- DB_TRX_ID：最近修改该行的事务 id，6 字节，MVCC 的裁判依据
- DB_ROLL_PTR：回滚指针，指向 undo log 里的上一版本，7 字节
- DB_ROW_ID：无主键且无唯一非空索引时才生成的 6 字节行号
- 版本链就是隐藏列把各行历史串起来的结果（33 篇）

> 三列都不可查询、不可索引，却支撑着事务与回滚的半壁江山。DB_ROW_ID 的存在解释了“没主键 InnoDB 也能跑”，但生成的主键对你不可控，仍是设计缺陷。

**速记**：**事务 id 定可见，回滚指针串版本，行 id 兜底无主键**。



#### CHAR 的存储细节

**定长列也会进变长列表**：变与不变取决于字符集。

- ASCII 等单字节字符集下 CHAR 是真定长，不进变长列表
- utf8mb4 下 CHAR 实际字节数可变（1 到 4 乘字符数），照记变长列表
- 尾部空格的处理在 CHAR 与 VARCHAR 间也有差异
- 行格式差异会进一步影响 CHAR 的存放策略

> CHAR(n) 的 n 是字符不是字节这一课，在长度函数（16 篇）与索引 key_len 计算（30 篇）里都会再考一遍；存储细节是同一知识点的第三面。

**速记**：**CHAR 定长是假象，多字节字符集照进变长表**。



### 数据页

#### 页的 16KB 逻辑分区

**数据页是 InnoDB 管理的最小单位**：一块 16KB 划成七个功能区。

- File Header：页号、前后页指针、校验和、日志序列号
- Page Header：页内统计，如记录数、槽位数
- Infimum 与 Supremum：两条虚拟记录，界定最小与最大
- User Records：真实行记录，逐条紧凑排布
- Free Space：未使用区域，分配即减
- Page Directory：槽目录，二分查找的索引
- File Trailer：校验和与日志序列号副本，刷盘完整性校验

> 页是 IO、锁、缓存的公共单位：读一行读一页，改一行改一页。理解页结构，buffer pool、刷脏、崩溃恢复的讨论才有落点。

**速记**：**16KB 七分区，头尾校验中间住人，页目录管查找**。



#### 页内与页间的组织

**页内单链表、页间双向链表**：两种链各管一层秩序。

- 行记录按主键序通过记录头的下一记录偏移串成单向链表
- 物理存储顺序可以与逻辑顺序不同，逻辑序靠指针维护
- 页间通过 File Header 的前后页指针连成双向链表
- B+ 树的“叶子链表”正是这条页间链（27 篇）

> 单向链表省空间（只记下一跳），双向链表服务范围扫描的往返遍历。两层链表合起来就是“有序存储”的实现方式——不是物理连续，是指针有序。

**速记**：**页内单向排主键序，页间双向连范围扫**。



#### Page Directory 与二分查找

**槽目录让页内查找从线性变对数**：每 4 到 8 条记录一个槽。

- Page Directory 记录各组最后一条记录的页内偏移
- 查找先在槽上二分，锁定组后再组内顺序扫
- 组规模 4 到 8 条，二分加短扫，代价可控
- 虚拟记录 Infimum 与 Supremum 充当二分的边界

> 页内查找不是从头遍历：目录二分把代价压到对数级。这与 B+ 树上层导航是同一个思想在不同尺度的复用——大尺子树、小尺子槽。

**速记**：**槽上二分组内短扫，树与槽同出一辙**。



### 更大的尺度

#### 区与段

**页之上还有区与段两级组织**：管理大表的磁盘布局。

- 区（extent）：连续 64 个页，约 1MB，分配的基本单位
- 段（segment）：同类型区的集合，如叶子节点段与非叶子节点段
- B+ 树每层的数据各归各段，索引即两个段起步
- 小表初期碎片化分配，长到 32 页后整区分配

> 区保证范围扫描的物理连续性：一次顺序 IO 读整区，比跳页读快得多。段与区的存在，让“索引是两个段”这句话落到实处。

**速记**：**64 页一区 1MB，树分两段，区保连续**。



#### 溢出页与行溢出

**超长行会溢出到专门的溢出页**：行内只留指针或前缀。

- 单页放不下的行，大字段数据移入溢出页
- COMPACT 在行内留 768 字节前缀加 20 字节指针
- DYNAMIC 全外置，行内只留 20 字节指针
- 溢出列通常是 TEXT、BLOB 或超长 VARCHAR

> 溢出让“读一行”变成“读一页加读溢出页”：大字段与常用字段同表时，缓存效率被大字段稀释。把大字段拆出主表（垂直分表）或改存对象存储，本质都是在减少溢出。

**速记**：**大字段外住溢出页，行内留指针，拆表省缓存**。



### 综合运用

#### 记录结构对设计的启示

**行格式知识直接映射到表设计**：四条推论够用。

- 控制行宽：行越小，一页装的行越多，IO 效率越高
- 大字段拆表或外置，避免缓存被稀释
- 能 NOT NULL 就 NOT NULL：省位图，语义也更清晰
- 主键短而有序，行存与页分裂两头受益

> 记录结构是“为什么”的来源：为什么行要小、为什么 NULL 有代价、为什么主键影响一切。知道结构的 DBA 与只会背结论的 DBA，在疑难杂症前分高下。

**速记**：**行小页多缓存足，非空省位图主键定乾坤**。
