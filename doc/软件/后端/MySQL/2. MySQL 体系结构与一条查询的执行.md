## MySQL 体系结构与一条查询的执行

### MySQL 的客户端与服务器架构

#### C/S 模型

**C/S 模型**：是**MySQL 整体采用客户端—服务器架构**的模式，客户端负责发起请求与展示结果，服务器（mysqld）负责存储数据并处理请求。

模型要点：

- **职责分离**：客户端只发命令、收结果；数据与管理全在服务端。
- **网络交互**：二者通过约定的协议（TCP 或本地套接字）通信。
- **一对多**：一个服务器可同时服务大量客户端。
- **进程独立**：客户端崩溃不影响服务器，反之亦然。

```bash
# 客户端与服务器可位于同一台机器
mysql -u root -p -h 127.0.0.1 -P 3306
```

> 理解 C/S 的关键，是分清**谁在算**：你写的 SQL 不是在 mysql 客户端里执行的，而是被原样发给 mysqld，由服务器计算结果后再回传。客户端只是传声筒，这也是为什么服务器配置（CPU、内存）远比客户端重要的原因。

> 速记：**客户端发令、服务器算账、结果回传**。



#### 服务器进程 mysqld

**mysqld**：是**MySQL 的服务器主进程（守护进程）**，常驻内存、监听端口、管理数据文件与连接，是真正干活的核心程序。

其职责：

- **监听连接**：在配置端口（默认 3306）等待客户端接入。
- **处理 SQL**：解析、优化并执行每条语句。
- **管理存储**：调用存储引擎读写磁盘数据。
- **保障安全**：做身份认证与权限控制。

```bash
# 查看 mysqld 进程是否在运行
ps aux | grep mysqld

# 查看其监听的端口
lsof -i :3306
```

> mysqld 与 mysql 客户端是**两个不同进程**：前者是服务器、长期运行、占有数据；后者是临时工具、用完即退。误把 mysql 当服务器进程去停止，或把 mysqld 当客户端去查数据，是初学者常见混淆。

> 速记：**mysqld 后台常驻、mysql 前台临时**。



#### 连接建立方式

**连接建立方式**：是**客户端与 mysqld 之间建立通信信道的具体手段**，MySQL 支持 TCP、命名管道与 Unix 域套接字三类，按操作系统与场景选用。

三种方式：

- **TCP/IP**：跨网络通用，默认端口 3306，本地与远程都可用。
- **命名管道（Named Pipe）**：仅 Windows，进程间通信，性能优于 TCP。
- **Unix 域套接字（Socket）**：仅 Unix/Linux/macOS，本地最快，文件如 /tmp/mysql.sock。

```bash
# 本地走 Unix 套接字（默认，无需 -h）
mysql -u root -p

# 强制走 TCP（指定 IP）
mysql -u root -p -h 127.0.0.1
```

> -h localhost 在 Unix 系默认走 **Unix 域套接字**而非 TCP，因此即使 mysqld 没监听 TCP 也能连上；想强制 TCP 必须写 -h 127.0.0.1。命名管道仅在 Windows 可用，Linux/macOS 没有这一选项，不同版本/发行版下套接字文件路径略有差异。

> 速记：**远程用 TCP、Windows 用管道、本地 Unix 走套接字**。



#### 客户端与服务器通信方式

**通信方式**：是**客户端与服务器之间传递请求与结果的数据交互形式**，MySQL 采用半双工的请求—响应模式，并基于字节流协议分包。

交互特征：

- **半双工**：同一时刻要么客户端发、要么服务器回，不能双向同时。
- **请求—响应**：客户端发一条 SQL，服务器回一个结果集。
- **流式结果**：大结果集分块返回，而非一次性全装内存。
- **协议分层**：在 TCP 之上定义 MySQL 私有报文格式。

```sql
-- 一个请求对应一个响应：发出查询，等待结果
SELECT * FROM employee WHERE dept_id = 1;
```

> 半双工意味着**客户端发完请求后只能等待**，无法在服务器还在算的时候追加指令。这也解释了为何一条超长 SQL 会长时间占用连接——客户端发出后只能等服务器算完返回，期间这条连接被占住。

> 速记：**半双工、一问一答、结果流式回传**。



### MySQL 的分层

#### 连接层

**连接层**：是**MySQL 架构最外层，负责接待客户端连接、做身份认证与权限初判、维护连接线程**的一层。

主要职责：

- **建立连接**：按 TCP/套接字接纳客户端。
- **身份认证**：校验用户名、密码、来源主机。
- **权限初取**：连接建立时读取该用户权限。
- **连接管理**：维护线程池，处理长/短连接。

```sql
-- 查看当前所有连接
SHOW PROCESSLIST;
```

> 连接层做的权限读取是**连接建立那一刻的快照**：之后管理员即使修改了该用户权限，已建立的连接不会立即生效，需重连或执行 FLUSH PRIVILEGES 后新连接才体现。这也是改了权限还不生效的常见原因。

> 速记：**连接层管谁来、有没有资格进门**。



#### 服务层

**服务层**：是**MySQL 处理 SQL 逻辑的核心层**，涵盖查询缓存（8.0 已移除）、分析器、优化器、执行器，所有跨存储引擎的 SQL 行为都在此完成。

核心组件：

- **查询缓存**：8.0 前用于缓存 SQL 文本—结果，现已移除。
- **分析器**：做词法、语法与语义检查。
- **优化器**：选择索引、决定表连接顺序。
- **执行器**：调用存储引擎接口真正取数。

```sql
-- 服务层负责把这条 SQL 解析、优化、执行
SELECT name FROM employee WHERE dept_id = 1 ORDER BY name;
```

> 服务层是**与存储引擎无关**的一层：不论底层是 InnoDB 还是 MyISAM，SQL 的解析、优化逻辑都一致，差异只在最后取数时调用哪个引擎的接口。这也是 MySQL 能插拔多存储引擎的架构基础。

> 速记：**服务层是大脑，解析优化执行都在它**。



#### 存储引擎层

**存储引擎层**：是**真正负责数据如何存储与读取的可插拔组件层**，MySQL 通过统一接口（handler）调用不同引擎，默认引擎为 InnoDB。

要点：

- **可插拔**：一个实例内不同表可用不同引擎。
- **默认 InnoDB**：8.0 默认且推荐，支持事务与外键。
- **引擎差异**：MyISAM 不支持事务，Memory 存内存。
- **统一接口**：服务层只调接口，不关心引擎实现。

```sql
-- 建表时指定存储引擎
CREATE TABLE log_archive (
    id INT PRIMARY KEY,
    msg VARCHAR(200)
) ENGINE = MyISAM;

-- 查看表的引擎
SHOW TABLE STATUS LIKE 'log_archive';
```

> 选错引擎代价很大：**需要事务、外键、崩溃恢复的业务务必用 InnoDB**；MyISAM 虽读快但无事务、表级锁，异常断电易损。8.0 已把 InnoDB 作为唯一完整支持的引擎，系统表也迁至 InnoDB。

> 速记：**默认 InnoDB，要事务就选它，别用 MyISAM 扛业务**。

> [!TIP]
> **建议内容**：生产业务默认 InnoDB 即可，无需在建表时反复指定 ENGINE=InnoDB，除非有特定诉求（如纯只读日志表可考虑 MyISAM），减少不必要的心智负担。



#### 文件系统层

**文件系统层**：是**存储引擎最终把数据落盘到的操作系统文件**，包括表数据文件、索引文件、重做日志、二进制日志等。

常见文件：

- **表空间文件**：如 ibd（每表一文件）或 ibdata（共享表空间）。
- **重做日志**：ib_logfile0/1，用于崩溃恢复。
- **二进制日志**：binlog，用于复制与点时间恢复。
- **配置文件与错误日志**：记录运行与错误信息。

```bash
# macOS 上 brew 安装的 InnoDB 数据文件位置示例
ls /opt/homebrew/var/mysql/*.ibd
```

> 文件系统层是**引擎与磁盘之间的边界**：服务层、存储引擎层都不直接碰磁盘，而是由引擎调用操作系统写文件。理解这层，有助于排查数据到底存哪了、ibd 文件能不能直接拷走等运维问题（通常不能简单拷贝，需配合备份机制）。

> 速记：**真正落地在磁盘，是引擎之下的文件世界**。



### 一条查询语句的执行过程

#### 连接器

**连接器**：是**查询执行的第一站**，负责接收连接、校验身份并把用户权限载入，只有通过后客户端才能继续发 SQL。

在此阶段发生：

- **TCP/套接字握手**：建立底层连接。
- **身份校验**：核对用户名、密码、来源 IP。
- **权限载入**：把该用户权限读入连接上下文。
- **失败即止**：任一环节错则拒绝连接。

```bash
# 连接失败示例：密码错误会被连接器直接拒绝
mysql -u root -p -h 127.0.0.1
# ERROR 1045 (28000): Access denied for user 'root'@'localhost'
```

> 连接器拒绝连接与语句报错是两回事：**连不上**发生在发 SQL 之前（网络/账号问题），**语句错**发生在连上之后（SQL 写错）。排障时先分清是门都没进还是进来了说错话。

> 速记：**连接器先把门，身份不过进不来**。



#### 查询缓存（8.0 已移除）

**查询缓存**：是**8.0 之前存在于服务层的 SQL 文本—结果缓存**，若收到一条与历史完全相同的 SQL，可直接返回缓存结果，跳过后续解析执行。

其机制：

- **命中条件**：SQL 文本、协议、环境完全一致才命中。
- **失效机制**：表一有更新，该表相关缓存全失效。
- **8.0 状态**：已被**彻底移除**，不再提供。
- **历史评价**：写多读少场景下命中率极低。

```sql
-- 8.0 中执行此语句会忽略查询缓存（功能已不存在）
SELECT * FROM employee WHERE dept_id = 1;
```

> 查询缓存看似美好，实则在**有写入的表上几乎无缓存价值**：只要表被更新，所有涉及该表的缓存全部清空，命中率随写入量陡降。8.0 干脆移除，腾出复杂度，相关需求改由应用层缓存（如 Redis）承担。

> 速记：**缓存一写就废，8.0 直接砍掉**。



#### 分析器

**分析器**：是**对 SQL 做读懂的环节**，先把字符串拆成词法单元，再按语法规则校验结构是否合法，并做表/列的语义检查。

具体工作：

- **词法分析**：识别关键字、表名、列名等 token。
- **语法分析**：按 SQL 语法树校验结构是否正确。
- **语义检查**：确认表、列是否存在，权限是否满足。
- **报错时机**：语法错或表不存在在此阶段暴露。

```sql
-- 表名拼错会在此阶段报表不存在
SELECT * FROM emplyee WHERE id = 1;
-- ERROR 1146 (42S02): Table 'test.emplyee' doesn't exist
```

> 常见的表不存在、列不存在错误**来自分析器的语义检查**，而非执行器。这也意味着：只要 SQL 写错表名，根本到不了执行阶段，更不会动任何数据，属于说错话就被拦下。

> 速记：**分析器管说得对不对、表在不在**。



#### 优化器

**优化器**：是**决定怎么算最快的环节**，在多种等价执行方案中挑选成本最低的一个，如选哪个索引、谁先谁后连接。

它决定的事：

- **索引选择**：在多索引中挑效率最高的。
- **连接顺序**：多表 JOIN 时决定驱动表与被驱动表。
- **重写等价**：把子查询改写为更优形态。
- **成本估算**：基于统计信息估算每种方案代价。

```sql
-- 优化器会决定走 dept_id 索引还是全表扫描
EXPLAIN SELECT * FROM employee WHERE dept_id = 1;
```

> 优化器**只选它认为最快的**，基于统计信息而非绝对真理。当统计信息过期（如表很久没 ANALYZE），它可能选错索引，导致慢查询。此时用 ANALYZE TABLE 更新统计，或 FORCE INDEX 干预，是常见调优手段。

> 速记：**优化器挑路径，统计过期会选错**。



#### 执行器

**执行器**：是**真正动手取数的最后一环**，它再次校验权限，然后循环调用存储引擎接口，把满足条件的行取出来并加工返回。

执行动作：

- **权限复核**：打开表前再次确认有权。
- **调用引擎**：向存储引擎要满足条件的下一行。
- **逐行判断**：在引擎返回的行上应用 WHERE 等条件。
- **返回结果**：把最终行集发给客户端。

```sql
-- 执行器在此条语句上调用引擎接口逐行取 dept_id = 1 的行
SELECT name FROM employee WHERE dept_id = 1;
```

> 执行器与优化器的分工：**优化器定方案（走哪个索引、什么顺序），执行器照方案执行**。若优化器选了索引，执行器就走索引取行；若选了全表扫描，执行器就逐行扫。二者配合，SQL 才真正落地。

> 速记：**执行器按图索骥，调引擎取数返回**。



### 连接器的工作

#### 身份认证与权限获取

**身份认证与权限获取**：是**连接器在建立连接时核实你是谁、能干什么的过程**，通过后才允许后续 SQL。

流程：

- **核对账号**：用户名 + 来源主机（如 root@localhost）唯一确定身份。
- **校验密码**：与 mysql 系统库中的密码哈希比对。
- **读取权限**：把该用户被授予的全局、库、表、列权限载入。
- **拒绝连接**：任一不符返回 Access denied。

```sql
-- 查看某用户来源于哪些主机、拥有什么权限
SHOW GRANTS FOR 'root'@'localhost';
```

> 身份由 **用户名与来源主机共同决定**：root@localhost 与 root@127.0.0.1 是**两个不同账号**，权限可以完全不同。这常导致本地能连、指定 IP 连不上，根因是没给对应主机的账号授权。

> 速记：**用户=名字+主机，两账号权限可不同**。



#### 长连接与短连接

**长连接与短连接**：是**客户端与服务器保持连接时长的两种策略**，直接影响性能与资源占用。

对比：

- **长连接**：连接建立后持续复用，减少握手开销，**但占内存**。
- **短连接**：每次查询新建、用完即关，开销大但**资源释放快**。
- **适用**：交互式客户端多用长连接；简单脚本可用短连接。
- **风险**：长连接累积可能导致内存上涨。

```bash
# 交互客户端默认保持长连接
mysql -u root -p
```

> 长连接虽省握手，但 **MySQL 为每条连接分配的内存（如排序缓冲、临时表）只在连接关闭时释放**。大量长连接堆积会让服务器内存居高不下。对策：定期重连、用连接池复用、或调小各连接缓冲，而非无限制保持。

> 速记：**长连接省握手占内存，短连接开销大释放快**。



#### wait_timeout

**wait_timeout**：是**服务器关闭空闲非交互连接的等待秒数**，超过该时长的空闲连接会被自动断开，用于回收资源。

要点：

- **默认值**：通常 **28800 秒（8 小时）**。
- **作用对象**：针对非交互连接（如程序连接）。
- **交互版**：交互连接有对应 interactive_timeout。
- **超时后果**：连接被断开，再操作报已丢失。

```sql
-- 查看当前超时设置
SHOW VARIABLES LIKE 'wait_timeout';

-- 会话级临时调整为 600 秒
SET SESSION wait_timeout = 600;
```

> 应用偶发 MySQL server has gone away，常与 **wait_timeout 超时**有关：连接空闲太久被服务器踢掉，应用还以为连着。解决：连接池做心跳/保活，或业务层捕获重连，而非一味调大超时（调太大又占资源）。

> 速记：**空闲超 wait_timeout 就被踢，应用要做重连**。



#### 连接数上限 max_connections

**max_connections**：是**MySQL 允许的最大并发连接数**，到达上限后新的连接请求会被拒绝，是保护服务器不被连接打垮的阀门。

关键认知：

- **默认值**：通常为 **151**（含管理员保留连接）。
- **超限表现**：新连接报 Too many connections。
- **调优依据**：结合内存与业务峰值设置。
- **监控**：用 SHOW PROCESSLIST 看连接占用。

```sql
-- 查看最大连接数与当前用量
SHOW VARIABLES LIKE 'max_connections';
SHOW STATUS LIKE 'Threads_connected';
```

> 调大 max_connections 并非越多越好：每个连接都消耗内存与线程，盲目调高可能在高并发时**把服务器内存打满**反而雪崩。合适做法是按单连接内存 × 峰值连接数 < 可用内存估算，并用连接池限流。不同版本默认值略有差异。

> 速记：**连接上限防被打垮，调大要看内存**。



### 分析器

#### 词法分析与语法分析

**词法分析与语法分析**：是**分析器把 SQL 字符串转换为可执行结构的两步过程**，先拆词、再验结构。

两步拆解：

- **词法分析**：扫描字符流，切出关键字、标识符、常量等 token。
- **语法分析**：依据 SQL 文法把 token 组装成语法树。
- **失败即报错**：结构非法在此抛出语法错误。
- **产出**：一棵供优化器使用的语法树。

```sql
-- 语法错误（括号不匹配）会在词法/语法阶段被拦下
SELECT * FROM employee WHERE (dept_id = 1;
-- ERROR 1064 (42000): You have an error in your SQL syntax
```

> 词法分析像认字，语法分析像断句：认出 SELECT、FROM 是关键字，employee 是表名；再判断 SELECT 列 FROM 表 WHERE 条件 的结构是否合规。**结构错的 SQL 根本进不了优化器**，这也是 1064 语法错误来得最早的原因。

> 速记：**先分词后造句，结构错最早报**。



#### 表不存在的报错时机

**表不存在的报错时机**：是**分析器在完成语法检查后、进行语义校验时报出表/列不存在的具体阶段**，早于真正的执行。

何时报：

- **阶段位置**：语法通过后，语义检查环节。
- **触发条件**：引用的表或列在元数据中查不到。
- **早于执行**：此时还没碰任何数据行。
- **错误号**：典型为 1146（表不存在）。

```sql
-- 即便 WHERE 条件内容正确，表名错也会在分析器阶段报错
SELECT name FROM non_exist_table WHERE id = 1;
-- ERROR 1146 (42S02): Table 'test.non_exist_table' doesn't exist
```

> 把表不存在归到分析器而非执行器，有助于理解**报错轻重**：它属于你说的话系统听不懂/找不到对象，而不是执行时算不出。因此在执行前 SQL 就被拦下，绝不会误改数据——这对排障与安全意识都很重要。

> 速记：**表错在分析器，没执行就先拦下**。



### 优化器

#### 选择索引与决定表连接顺序

**选择索引与决定表连接顺序**：是**优化器在多种可行执行计划中，权衡成本后选定索引与 JOIN 顺序的核心决策**。

决策内容：

- **索引选择**：单列、联合、覆盖索引中挑一个。
- **访问方式**：走索引范围扫描还是全表扫描。
- **连接顺序**：多表 JOIN 决定谁做驱动表。
- **成本目标**：让估算总代价最小。

```sql
-- 优化器需决定：走 dept_id 索引，还是先扫 employee 再 JOIN
EXPLAIN
SELECT e.name, d.name
FROM employee e
JOIN department d ON e.dept_id = d.id
WHERE d.name = '研发';
```

> 驱动表的选择**极大影响性能**：小表作驱动表、大表被驱动并走索引，通常远快于反过来。优化器基于统计的行数、索引区分度估算，但它看不见业务上哪张更小，统计失真时就需要人工用 STRAIGHT_JOIN 或索引干预。

> 速记：**小表驱动大表、索引挑最省的走**。



#### 优化器的成本模型

**优化器的成本模型**：是**MySQL 用以量化哪种执行方案更划算的计算体系**，基于 IO 成本与 CPU 成本对候选计划打分，取最低分。

模型构成：

- **IO 成本**：读取页（磁盘/缓冲池）的代价。
- **CPU 成本**：行比较、排序、函数计算代价。
- **统计信息**：表行数、索引区分度来自持久化统计。
- **可调参数**：部分成本常量可配置微调。

```sql
-- 查看优化器对一张表的成本估算依据
SHOW TABLE STATUS LIKE 'employee';
-- 或查看索引区分度
SHOW INDEX FROM employee;
```

> 成本模型是**基于统计的估算，不是实测**：它假设数据均匀、页命中率稳定。当数据严重倾斜（如某值占 90%）而统计未更新，估算会失真、选错计划。定期 ANALYZE TABLE、保证统计新鲜，是让优化器算得准的前提。

> 速记：**成本=IO+CPU，靠统计估算，过期就会错**。



### 执行器

#### 权限校验时机

**权限校验时机**：是**执行器在真正打开表、取数之前，再次确认当前用户对该表有相应操作权限的时刻**，形成连接时与执行时的双重把关。

校验特点：

- **双重校验**：连接器连接时取权限，执行器执行前再核。
- **理由**：权限可能在中途被改，需以最新为准。
- **失败表现**：无权限则返回拒绝，不取任何行。
- **细粒度**：可精确到列级权限。

```sql
-- 当前用户无 test.employee 的 SELECT 权限时，查询在此被拦
SELECT * FROM employee;
-- ERROR 1142 (42000): SELECT command denied to user ...
```

> 为什么连接器取了权限、执行器还要再查？因为**权限可随时变更**：管理员在连接建立后收回了某表权限，若只信连接时的快照，就会让已连上的用户继续越权操作。执行器复查，保证了权限调整的即时生效。

> 速记：**连接取权限、执行再复核，双保险**。



#### 调用存储引擎接口取行

**调用存储引擎接口取行**：是**执行器拿到优化后的计划后，向 InnoDB 等引擎逐行请求数据、并在服务层完成过滤与加工的过程**。

调用过程：

- **打开表**：执行器向引擎要表的句柄。
- **取下一行**：循环调用引擎接口拿满足条件的行。
- **层内加工**：在服务层应用 WHERE、排序、分组。
- **返回客户端**：把结果流式发回。

```sql
-- 执行器向 InnoDB 逐行取 dept_id = 1 的行，再投影 name 列
SELECT name FROM employee WHERE dept_id = 1;
```

> 存储引擎对执行器**只暴露取行接口**，不关心 SQL 语义；WHERE 中的 dept_id = 1 是执行器在拿到行后自行判断的（除非引擎能在索引层直接定位）。理解这一点，就能明白为什么有时索引用上了还是慢——取行后的过滤与加工同样耗时。

> 速记：**执行器逐行问引擎要，条件自己判**。



### 一条更新语句的执行

#### 更新流程与缓冲池、redo log、binlog

**更新语句的执行**：是**一条 UPDATE 在服务层解析优化后，由 InnoDB 借助缓冲池、redo log 与服务器层 binlog 协同完成落盘的过程**，比查询多出两套日志的参与。

参与角色：

- **缓冲池（Buffer Pool）**：InnoDB 在内存中缓存页，更新先改内存。
- **redo log**：InnoDB 的重做日志，保证崩溃后可恢复已提交事务。
- **binlog**：服务器层二进制日志，用于复制与点时间恢复。
- **两阶段提交**：二者通过 prepare/commit 保持逻辑一致。

```sql
-- 一条典型更新（执行器调用 InnoDB 修改缓冲池中的页）
UPDATE employee SET salary = salary + 1000 WHERE id = 1;
```

> 更新并非直接写磁盘：InnoDB 先改**缓冲池里的页**，再写 redo log 保证持久，最后由后台线程刷脏页到磁盘；同时服务器写 binlog 供从库同步。这三者通过**两阶段提交**（redo prepare → 写 binlog → redo commit）保证主库崩了也从库一致，是 MySQL 数据安全的基石。

> 速记：**更新走缓冲池，redo 保崩溃、binlog 供复制，两阶段提交保一致**。

> [!WARNING]
> **警告内容**：redo log 与 binlog 的刷盘策略（如 innodb_flush_log_at_trx_commit 与 sync_binlog）直接决定崩溃时丢不丢数据；要求不丢数据的业务须设为双 1，性能与持久化需权衡，不同版本默认值略有差异。



### MySQL 8.0 移除查询缓存的原因

**MySQL 8.0 移除查询缓存**：是**官方因查询缓存弊大于利，在该版本彻底删除该功能**的决定，改由应用层缓存承接。

移除根因：

- **失效代价高**：任意表更新即清空其全部缓存，写多场景命中率极低。
- **全局锁竞争**：查询缓存用一把大锁保护，高并发下成为瓶颈。
- **收益有限**：多数业务命中率低，维护成本却不小。
- **更好替代**：应用层缓存（如 Redis）更灵活、可控。

```sql
-- 8.0 中已无 query_cache_type 等变量
SHOW VARIABLES LIKE 'query_cache%';
-- 结果为 Empty set（8.0 已移除）
```

> 移除查询缓存**不代表缓存没用**，而是 MySQL 内置的这个缓存机制性价比太低。官方把这块复杂度去掉后，性能与可维护性反而更好；需要缓存请放到应用层或专门的缓存中间件，按业务键精准控制失效，远比整表失效聪明。

> 速记：**内置缓存写即废、锁争用，8.0 砍掉交应用层**。
