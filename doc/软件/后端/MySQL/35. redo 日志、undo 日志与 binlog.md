## redo 日志、undo 日志与 binlog

### redo 日志

#### WAL 与 crash-safe

**redo log 是 InnoDB 的物理日志**：先写日志再刷数据，崩溃也不丢已提交。

- WAL（Write-Ahead Logging）：修改先记 redo，数据页随后慢慢刷盘
- 事务提交只需保证 redo 落盘，不必等数据页落盘
- 崩溃恢复时重放 redo，把未刷盘的修改补齐
- 这套机制就是 crash-safe：挂了重启，数据不丢不错

> WAL 把随机写变顺序写：数据页刷盘是随机 IO，redo 是顺序追加，性能差异巨大。redo 既是可靠性基石也是性能引擎，双重身份。

**速记**：**先日志后数据，顺序写扛随机，崩溃重放保提交**。



#### 循环写与刷盘策略

**redo 文件固定大小循环使用**：写满就得推进 checkpoint。

- redo 由一组固定大小文件组成，write pos 追着 checkpoint 跑
- checkpoint 前的修改已刷到数据页，空间可复用
- write pos 追上 checkpoint 时必须停下来刷数据页，写入卡顿
- innodb_flush_log_at_trx_commit 三档：0 每秒刷、1 每次提交刷、2 提交写系统缓存每秒刷

> 参数 1 是唯一保证不丢已提交事务的档位；0 与 2 在主机崩溃时各丢一秒内的提交。金融类业务双 1（此参数加 sync_binlog=1），一般业务可权衡到 2。

**速记**：**write pos 追 checkpoint，追上就卡，参数 1 才真落盘**。



### undo 日志

#### 回滚与版本链

**undo log 记录反向操作**：回滚靠它，MVCC 也靠它。

- INSERT 的 undo 记删除，UPDATE 的 undo 记旧值，逻辑日志
- 事务回滚：沿 undo 链逆向执行即可恢复原状
- 版本链：undo 保存的旧版本供快照读回溯（33 篇）
- 长事务持有旧 ReadView，undo 无法清理，链越拖越长

> undo 的双份职责决定了长事务的双重危害：回滚变慢加 MVCC 膨胀。undo 相关的表空间膨胀，第一嫌疑永远是长事务。

**速记**：**undo 记旧值，回滚与快照共用，长事务挡清理**。



#### purge 与清理

**已提交事务的 undo 不会立即删**：等没有读者需要它再清。

- purge 线程负责回收不再被任何 ReadView 引用的 undo
- 清理进度受最老活跃事务约束
- undo 表空间可在线收缩（8.0 支持独立 undo 表空间 truncate）
- 监控点：history list length

> history list length 持续增长就是长事务在挡路的标准信号；发现即排查 innodb_trx，先杀长事务再谈其他优化。

**速记**：**没人看了才回收，history list 飙升找长事务**。



### binlog

#### 三种格式

**binlog 是 Server 层的逻辑日志**：STATEMENT、ROW、MIXED 三格式各有立场。

- STATEMENT：记原始 SQL 语句，体积小，但不确定函数（NOW、RAND）主从结果可能不一致
- ROW：记录每行的实际变更，精确复现，体积大
- MIXED：默认 STATEMENT，遇到不确定场景自动切 ROW
- 8.0 默认 ROW；生态工具（CDC、闪回）普遍依赖 ROW

> ROW 的体积换来的是确定性与可解析性：数据订正、审计、同步系统都以 ROW 为基础。默认跟生态走，选 ROW。

**速记**：**语句省空间，行级保精确，生态选 ROW**。



#### 用途：复制与恢复

**binlog 的两大用途**：主从复制与时间点恢复。

- 主从复制：从库拉取主库 binlog 重放，保持一致
- 时间点恢复：全量备份加 binlog 回放，恢复到任意时刻
- binlog 追加写，写满一个文件换下一个，不循环
- sync_binlog 三档：0 交给系统、1 每次提交刷盘、N 攒 N 个事务

> 没有 binlog 的备份体系只剩“回到备份点”，之后的变更全靠人工重放。binlog 的保留时长决定你能恢复到多久之前，按业务的容灾要求定。

**速记**：**追加不循环，复制与恢复全靠它，sync_binlog 1 才稳**。



### 三者协作

#### redo 与 binlog 的区别

**同为日志，身份完全不同**：四组对照记牢。

- 层次：redo 属 InnoDB 引擎层，binlog 属 Server 层
- 内容：redo 物理页修改，binlog 逻辑变更
- 写法：redo 循环写固定大小，binlog 追加写
- 用途：redo 管崩溃恢复，binlog 管复制与备份恢复

> 只在 InnoDB 单机里活，redo 足矣；一旦涉及主从、备份、下游订阅，binlog 不可替代。两者不是二选一而是各司其职。

**速记**：**引擎物理循环，Server 逻辑追加，各救各的场**。



#### 两阶段提交

**redo 与 binlog 必须原子一致**：靠内部两阶段提交。

- 阶段一：redo 写入并标记为 prepare
- 阶段二：写 binlog，再把 redo 标记为 commit
- 崩溃恢复判定：redo 处于 prepare 时，查对应 binlog——完整则提交，不完整则回滚
- 没有两阶段提交的后果：主库与从库、库与恢复点出现分叉

> 两阶段提交是分布式一致性的最小样例，就藏在每次事务提交里。理解判定规则（binlog 完整即提交），崩溃恢复的行为就不再神秘。

**速记**：**先 prepare 再写 binlog 后 commit，恢复以 binlog 为准绳**。



#### 双 1 配置

**双 1 是最高可靠性档位**：两个参数都设 1。

- innodb_flush_log_at_trx_commit = 1：redo 每次提交落盘
- sync_binlog = 1：binlog 每次提交落盘
- 代价：每次提交两次 fsync，吞吐显著下降
- 权衡档位：金融类必须双 1；一般业务可降其一换性能，并接受秒级丢失窗口

> 双 1 不是默认教条而是业务决策：丢失一秒数据值多少钱，决定参数怎么设。决策要落在文档里，而不是留在某次调优的记忆里。

**速记**：**双 1 双保险双 fsync，丢数据窗口业务定**。
