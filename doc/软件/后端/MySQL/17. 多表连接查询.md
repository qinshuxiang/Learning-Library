## 多表连接查询

### 连接的本质

#### 笛卡尔积与连接

**连接的底层是笛卡尔积加条件过滤**：先组合再筛选，理解这一点一切好懂。

- 两表连接先产生所有行的两两组合，即笛卡尔积
- ON 条件从组合中筛出合法配对
- 内连接只留配对成功的行，外连接额外保留未配对的行并补 NULL
- 表越大组合越多，连接列上的索引是性能生命线

> 漏写 ON 条件（或逗号连接忘写 WHERE）会真的执行笛卡尔积：两万行乘两万行，瞬间打爆。见到结果行数是两表行数的乘积，第一反应就是条件丢了。

**速记**：**连接等于先组合再筛选，条件是刹车索引是赛道**。



#### 内连接

**INNER JOIN 只保留两边都配上的行**：最常用、语义最直观的连接。

- 写法：FROM a JOIN b ON a.id = b.aid，INNER 可省略
- 任一侧无匹配的行都不出现在结果里
- 多表连接继续用 JOIN 链式书写，逐表叠加条件
- 连接条件必须写 ON，与 WHERE 过滤分开

> 内连接下 ON 与 WHERE 写在一起效果相同，这让人误以为两者随便放；一旦换成外连接，位置就是语义（本篇后文详述）。习惯上连接关系永远写 ON。

**速记**：**INNER 留成对，ON 写关系 WHERE 写筛选**。

```sql
SELECT o.id, u.name, o.amount
FROM orders o
JOIN users u ON o.user_id = u.id;
```



#### 左外连接

**LEFT JOIN 保留左表全部行**：右表配不上就补 NULL。

- 写法：FROM a LEFT JOIN b ON 条件，a 的行全部保留
- b 无匹配时，b 的所有列输出 NULL
- 找“没有订单的用户”这类反连接是招牌用法：左连接后 WHERE b.id IS NULL
- 右外连接 RIGHT JOIN 与之对称，实际工程多用 LEFT JOIN 表达

> 反连接（NOT EXISTS 的等价形态）写成 LEFT JOIN 加 IS NULL 时要注意：判空的列必须是右表的非空列（如主键），拿右表可空列判空会把“匹配了但值为 NULL”的行误杀。

**速记**：**LEFT 全留左，右缺补 NULL，反连接判空选非空列**。

```sql
-- 没有任何订单的用户
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```



#### 全外连接的模拟

**MySQL 没有 FULL JOIN**：用左连接与右连接拼出来。

- 标准写法：LEFT JOIN 结果 UNION ALL 右连接去掉左表已匹配部分
- 简化写法：LEFT JOIN 与 RIGHT JOIN 用 UNION 合并，去重代价换正确性
- UNION 去重会产生临时表，UNION ALL 需要手工排除重复
- 需要全外连接往往意味着设计可再想：两端都要保留时考虑桥表或应用层合并

> 业务上真需要“两边都要保”的场景不多见；多数是数据修复、对账类任务，一次性查询用 UNION 拼接即可，不必为了语法完整去改造表设计。

**速记**：**FULL 缺席 UNION 凑，先想设计再拼查询**。



### 连接的进阶形态

#### 自连接

**自连接是表和自己连接**：一张表里的行存在层级或配对关系。

- 必须用两个不同别名区分“同一张表的两个角色”
- 经典场景：员工表里查每个员工的经理名
- 也用于配对：城市对城市、节点对父节点
- 层级不定深时，递归 CTE（19 篇）才是通用解

> 自连接查经理是单层关系；组织架构树是多层关系，单层自连接写不动，别硬套。

**速记**：**一表两名分角色，单层配对够用，深层请递归**。

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```



#### 三表与多表连接

**多表连接按逻辑链路逐表叠加**：每加一张表，补一对关系。

- FROM a JOIN b ON ... JOIN c ON ...，链式书写
- 每张新表的条件引用的是“当前已连接的中间结果”
- 中间结果可能极大，驱动顺序由优化器决定
- 列名重复时必须用表名（别名）限定，否则报歧义错误

> 四表以上的连接优先考虑拆解：先分别查出中间结果再在应用层合并，或落成临时表。SQL 能写出来不等于该一条写完。

**速记**：**逐表链 ON，歧义必限定，多表先想拆**。



#### USING 与自然连接

**USING 是同名列连接的简写**：NATURAL JOIN 则慎用。

- USING (id)：两表同名同义列的连接简写，输出合并该列
- USING 后 SELECT 星号不会重复输出该列
- NATURAL JOIN 自动用所有同名连接，列名一改语义静默变化
- 生产代码用显式 ON，USING 可接受，NATURAL 禁止

> NATURAL 的危险在于它依赖“同名即同义”这个脆弱假设：新加一个同名时间戳列，连接条件就悄悄变了。显式写出条件，永远是最安全的选择。

**速记**：**USING 简写可留，NATURAL 隐式莫碰**。



### ON 与 WHERE 的语义

#### 外连接下条件的位置

**外连接中条件放 ON 还是 WHERE，结果可以完全不同**：这是连接查询最大的坑。

- 左连接时，右表的过滤条件写在 ON 上：右表不匹配处补 NULL，左表行保留
- 同一条件写在 WHERE 上：NULL 行被过滤，左连接退化成内连接
- 左表的过滤条件写 WHERE 才有意义，写 ON 上对外连接无影响（仍全保留）
- 内连接下两者等价，这种等价性掩盖了差异直到换用外连接

> 记忆口诀：**ON 决定怎么配，WHERE 决定怎么留**。外连接的“保留”语义发生在配对阶段，WHERE 是配对完成后的最终筛选，此时补出来的 NULL 行也逃不掉。

**速记**：**ON 管配对 WHERE 管留存，外连接下位置即语义**。

```sql
-- 保留所有用户，只关联已支付订单
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 1;

-- 写成 WHERE o.status = 1 会丢掉无支付订单的用户
```



#### 驱动表与连接成本

**外层循环的表是驱动表**：小表驱动大表是直觉也是方向。

- 嵌套循环连接下，驱动表每行去被驱动表查一次
- 被驱动表的连接列有索引时，每次查找是索引点查
- 驱动表越小，外层循环次数越少
- 优化器基于统计信息自选驱动顺序，EXPLAIN 第一行即驱动表

> “小表驱动大表”的“小”指过滤后的行数而非表的物理大小；一个 WHERE 条件把千万行压到百行，它就是小表。具体执行形态在 32 篇优化中再展开。

**速记**：**小表驱动大表，被驱动列必有索引**。



### 综合运用

#### 连接查询的交付清单

**连接查错集中在条件位置与索引缺失**：逐项自查再交付。

- 每个连接都有显式 ON，关系列上有索引
- 外连接的右表条件写在 ON，不在 WHERE
- 歧义列名全部用别名限定
- 结果行数符合预期：内连接不多于任一侧，外连接不少于左侧
- 反连接优先 NOT EXISTS，LEFT JOIN 加 IS NULL 须判非空列

> 连接查询的 bug 多数不在语法而在语义：条件放错位置、判空判错列、别名串台。EXPLAIN 只能告诉你快不快，语义对不对要靠行数与抽样核对。

**速记**：**ON 带索引，条件归位，行数核语义**。
