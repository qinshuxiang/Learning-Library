## 聚合函数与分组查询

### 聚合函数

#### 聚合的本质

**聚合函数把一组行压缩成一个值**：输入是行集，输出是单值。

- 五大常客：COUNT 计数、SUM 求和、AVG 平均、MAX 最大、MIN 最小
- 无 GROUP BY 时聚合作用于全表（或 WHERE 过滤后的行集）
- 有 GROUP BY 时每个分组各产出一个聚合值
- 聚合函数不能直接嵌套聚合，SUM(COUNT(*)) 会报错

> 聚合改变了结果的“粒度”：从行级跳到组级。理解粒度是读懂一切分组查询的钥匙——SELECT 列表里的每个非聚合列，都必须与最终粒度对齐。

**速记**：**多行进一值出，粒度从行变组**。



#### COUNT 的三种形态

**COUNT(*) 数行数，COUNT(列) 数非空值**：三者的语义与代价都不同。

- COUNT(*)：统计行数，不关心任何列的值，InnoDB 有专门优化
- COUNT(列)：统计该列非 NULL 的行数，NULL 被跳过
- COUNT(DISTINCT 列)：先去重再计数，代价最高
- MyISAM 的免锁总行数优化不适用于 InnoDB 的并发事务

> 问“有多少订单”用 COUNT(*)，问“有多少订单填了收件人”用 COUNT(receiver)。语义差一行，结果差一截；顺手写 COUNT(*) 计非空数，是统计口径错误的常见源头。

**速记**：**星号数行，列名数非空，DISTINCT 先去重**。



#### SUM、AVG 与 NULL 的纠缠

**SUM 与 AVG 自动忽略 NULL**：这不是便利，是需要对齐的口径。

- SUM(列) 只累加非 NULL 值；全为 NULL 时结果为 NULL 而非 0
- AVG(列) 等于非 NULL 值的平均，分母不含 NULL 行
- AVG(col) 不等于 SUM(col) 除以 COUNT(*)，除非该列全非空
- IFNULL 与 COALESCE 可在聚合外做兜底

> 统计“平均客单价”时，未支付订单的金额若存 NULL，AVG 会把它们排除出分母；若存 0，则会拉低平均值。两种存储选择对应两种口径，先确认业务要哪种，再决定存法。

**速记**：**SUM 跳空 AVG 缩分母，全空 SUM 得 NULL**。

```sql
SELECT SUM(amount), AVG(amount), COUNT(*), COUNT(amount)
FROM orders;
-- AVG 用的是 COUNT(amount) 这个分母，不是 COUNT(*)
```



#### MAX 与 MIN 的扩展用法

**MAX 与 MIN 不挑类型**：日期、字符串同样适用。

- 对日期列求 MAX 即最新时间，常用于取最近活动
- 对字符串比较按排序规则进行，中文排序受字符集影响
- 配合 GROUP BY 取“每组最新一行”是经典需求
- 取整行而非单值需要变通：子查询按最大值回查，或用窗口函数

> “每组最新一条”的坑：SELECT user_id, MAX(created_at), other_cols 加 GROUP BY 时，other_cols 的值并不保证来自最大时间那一行（ONLY_FULL_GROUP_BY 下直接报错）。正确姿势是窗口函数或相关子查询。

**速记**：**MAX MIN 万物可比，配组取行要绕道**。



### GROUP BY：分组

#### GROUP BY 基本用法

**GROUP BY 按列值把行分成组**：每组产出一条聚合结果。

- 语法：SELECT 分组列, 聚合() FROM 表 GROUP BY 分组列
- 多列分组按列的组合值分，写法上逗号并列
- 分组列之间顺序不影响结果，影响的是可读性
- WHERE 先过滤行，分组只对过滤后的行集生效

> 分组查询先想清楚“一组是什么业务单位”：按用户分组是每人一行，按天分组是每天一行。粒度错了，后面的聚合再对也全错。

**速记**：**同值归组，组出一行，WHERE 在分组之前**。

```sql
SELECT user_id, COUNT(*) AS order_cnt, SUM(amount) AS total
FROM orders
WHERE status = 1
GROUP BY user_id;
```



#### ONLY_FULL_GROUP_BY 约束

**SELECT 中的非聚合列必须进 GROUP BY**：默认模式强制这一对齐。

- 该 SQL 模式 5.7 起默认开启，挡住粒度不对齐的查询
- 违规示例：SELECT user_id, city, COUNT(*) GROUP BY user_id，city 未分组
- 合规改法：city 加入分组列、包聚合函数、或用 ANY_VALUE 显式豁免
- 豁免函数只应在确定组内该列值唯一时使用

> ANY_VALUE 是逃生门不是常规操作：它声明的其实是“我知道这列在组里可能乱取”。关闭该模式让全库回到模糊语义，更是下下策。

**速记**：**非聚合列必须进组，ANY_VALUE 是逃生门**。



#### HAVING：分组后过滤

**HAVING 过滤的是组，WHERE 过滤的是行**：时机与能力都不同。

- WHERE 在分组前筛行，不能用聚合函数，不能用列别名
- HAVING 在分组后筛组，可用聚合结果
- HAVING COUNT(*) 大于 1 这类“找重复”是招牌用法
- 能下推到 WHERE 的条件就别放 HAVING，提前减行永远划算

> 两者可读性分工明确：WHERE 谈“哪些行有资格”，HAVING 谈“哪些组有资格”。看到 WHERE 里写聚合就知道必错，看到 HAVING 里写纯列条件就该提醒下推。

**速记**：**WHERE 筛行在前，HAVING 筛组在后，条件尽量前推**。

```sql
SELECT user_id, COUNT(*) AS cnt
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 10;
```



#### WITH ROLLUP 汇总行

**WITH ROLLUP 在分组结果后追加各级小计与总计**：报表的好帮手，局限也明确。

- 写法：GROUP BY a, b WITH ROLLUP，按分组列从右往左逐级汇总
- 每级汇总行的分组列显示 NULL，代表“全部”
- 不能与 ORDER BY 同用，排序语义冲突
- 汇总行的 NULL 与数据本身的 NULL 无法区分，需用 GROUPING 函数辅助判断

> ROLLUP 适合一次性的明细加合计报表；交互式报表的前端通常自己算合计，数据库层 ROLLUP 反而让结果集解析变复杂。知道它存在，用时再查语法即可。

**速记**：ROLLUP **从右往左层层汇总，别跟 ORDER BY 同框**。



### 综合运用

#### 分组统计的标准模板

**维度、口径、排序三要素齐了，分组查询才算完整**：模板可直接套用。

- 维度列进 GROUP BY，度量列进聚合函数
- 过滤条件尽量放 WHERE，组级条件放 HAVING
- 结果按度量降序或维度升序，LIMIT 保护结果集
- 交付前 EXPLAIN 检查是否走了索引、有无临时表

> 常见性能红旗：分组列无索引导致临时表加 filesort（EXPLAIN 的 Extra 会显形）；数据量增长后报表变慢，方向是预聚合（汇总表）或把实时统计挪到数仓。

**速记**：**维度进组、度量进聚，Extra 见临时表就要警惕**。



#### 聚合的常见错误清单

**聚合查询的错误集中在口径与粒度**：交付前逐项自查。

- COUNT 用错形态：该数非空的用了星号，或反之
- AVG 忽略 NULL 与业务口径不符，分母悄悄缩水
- 非聚合列没进 GROUP BY，被 ONLY_FULL_GROUP_BY 拦截
- 想取“每组最新整行”却直接配 MAX 加 GROUP BY
- 条件放错位置：该下推 WHERE 的写进了 HAVING

> 这五条覆盖了日常分组查询的绝大多数事故；拿不准时把语句按“行集到组集”的两阶段在纸上过一遍，粒度对不上的一眼就能看出来。

**速记**：**口径粒度双自查，纸上过两阶段**。
