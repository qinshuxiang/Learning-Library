## 数据类型：数值与位类型

### 数据类型的认识

#### 为什么要有数据类型

**数据类型**：是列在表中存放数据时，对值的种类、取值范围、存储方式的约束声明。

- **约束取值**：类型限定了列能存什么，如整数列不能存字母。
- **决定存储**：类型决定占用字节数，直接影响磁盘与内存开销。
- **支撑运算**：类型决定可用的运算符与比较规则，如日期可相减、字符串可拼接。

> 数据类型是数据库用好空间、保证正确的基础：没有类型，数据库无法判断 12 是数字还是字符串、无法预分配存储、也无法在执行比较与运算时给出确定语义。



#### 选择数据类型的原则

**选型三原则**：更小通常更好、简单就好、尽量避免 NULL，是 MySQL 官方推荐的字段类型选择次序。

- **更小的通常更好**：在能容纳值的范围内选最小类型，减少磁盘、内存、CPU 开销。
- **简单就好**：整数比字符串便宜，用内建日期类型而非字符串存日期，用整数存 IP。
- **尽量避免 NULL**：NULL 使索引、统计、比较更复杂，可为空的列需要额外存储标识位。

> 三者优先级递减但需权衡：极小类型若频繁溢出或需强制转换反而得不偿失；避免 NULL 在确属未知语义时应让位给正确性。通用做法是先满足取值范围与精度，再在余量内选更小、更简单、更非空的类型。

> 速记：先够用、再小、再简单、最后避 NULL。



### 整数类型

#### 五种整数类型的取值范围与字节数

**整数类型**：MySQL 提供 TINYINT、SMALLINT、MEDIUMINT、INT、BIGINT 五种，字节数依次倍增，范围随之扩大。

- **TINYINT**（1 字节，有符号 -128 到 127，无符号 0 到 255）：最小的整数类型，适合布尔与状态码。
- **SMALLINT**（2 字节，有符号 -32768 到 32767，无符号 0 到 65535）：适合小范围计数。
- **MEDIUMINT**（3 字节，有符号 -8388608 到 8388607，无符号 0 到 16777215）：MySQL 特有，介于 SMALLINT 与 INT 之间。
- **INT**（4 字节，有符号 -2147483648 到 2147483647，无符号 0 到 4294967295）：最常用的一般整数。
- **BIGINT**（8 字节，有符号 -9223372036854775808 到 9223372036854775807，无符号 0 到 18446744073709551615）：超大整数，适合主键与计数。

```sql
-- 直观建表观察五种整数类型
CREATE TABLE int_demo (
  c_tiny   TINYINT,
  c_small  SMALLINT,
  c_medium MEDIUMINT,
  c_int    INT,
  c_big    BIGINT
);

-- 用 COLUMNS 元数据确认各列的字节占用
SHOW COLUMNS FROM int_demo;
```

> 范围公式统一为：有符号区间是 -2^(n-1) 到 2^(n-1)-1，无符号区间是 0 到 2^n-1，其中 n 为总位数（字节数乘 8）。MEDIUMINT 是 MySQL 独有，其他数据库常无此类型；跨库迁移时需注意。

> 速记：字节 1、2、3、4、8 对应 TINY、SMALL、MEDIUM、INT、BIG；有符号半正半负，无符号从 0 起。



#### 有符号与无符号

**SIGNED 与 UNSIGNED**：决定整数是否允许存负数；无符号把正数范围翻倍，但失去负值能力。

- **SIGNED（默认）**：可存正负，范围跨越 0 两侧。
- **UNSIGNED**：只存非负，上限翻倍，适合年龄、计数等永不为负的量。
- **溢出行为**：超范围写入在严格模式下报错，非严格模式下截断为边界值。

```sql
-- 显式声明无符号
CREATE TABLE counters (
  age   TINYINT UNSIGNED,
  score SMALLINT UNSIGNED
);

-- 无符号主键常见写法
CREATE TABLE log_seq (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
);
```

> 无符号并非免费午餐：它把负值区间让给了正值，但不能存负数。一旦业务需要负数（如账户余额、温度），误用 UNSIGNED 会导致写入失败或溢出。此外无符号与有符号混算时，MySQL 会把有符号提升为无符号再比较，易引发意料外的相等判定。



### 显示宽度与 ZEROFILL

#### 显示宽度的作用与 8.0 的弃用

**显示宽度**：是 INT(11) 中括号里的数字，仅控制查询结果以多少列宽显示，与能存多大无关，且在 MySQL 8.0 已弃用。

- **不限制范围**：INT(1) 与 INT(20) 都能存同样的整数范围，宽度只是显示提示。
- **历史用途**：配合 ZEROFILL 做前导零填充显示。
- **8.0 弃用**：MySQL 8.0 起显示宽度被标记为过时，未来版本将移除，建表不再推荐写宽度。

```sql
-- 8.0 中仍可写，但会收到弃用警告，且宽度不参与存储
CREATE TABLE legacy_width (
  id INT(11)
);
```

> 最常见的误解是以为 INT(10) 比 INT 小、或 INT(5) 只能存 5 位。显示宽度完全不影响存储与取值范围，只影响客户端对齐显示的列宽。新项目应直接写 INT，不写宽度。



#### ZEROFILL 的效果与自动 UNSIGNED

**ZEROFILL**：让查询结果在显示时用前导零填满显示宽度，且会隐式把列设为 UNSIGNED。

- **前导零填充**：如宽度 5、值为 42，显示为 00042。
- **隐式 UNSIGNED**：带 ZEROFILL 的列自动变为无符号，无法存负数。
- **仅显示层**：存储的仍是普通整数，前导零只在输出时出现。

```sql
-- 宽度 5 且补零，插入 42 查询显示 00042
CREATE TABLE padded (
  code INT(5) ZEROFILL
);

INSERT INTO padded (code) VALUES (42);
SELECT code FROM padded;
```

> ZEROFILL 的零只存在于结果集显示，不写入磁盘，也不参与运算或比较。由于依赖已弃用的显示宽度，ZEROFILL 同样处于弃用轨道；需要定宽编号应改由应用层或 LPAD 函数处理。



### UNSIGNED 属性

#### 无符号的价值与相减溢出的问题

**UNSIGNED 的价值**：在于把正数上限翻倍，但其相减可能下溢为负，触发无符号下的绕回错误。

- **价值**：年龄、数量、主键等非负量用 UNSIGNED 可存更大的正数。
- **相减坑**：两个 UNSIGNED 相减若结果为负，不会得负数，而是绕回成一个极大的正数。
- **规避**：相减前用 CAST 转回 SIGNED，或保证被减数不小于减数。

```sql
-- 两个无符号数相减，结果为负时绕回成极大值
SELECT CAST(1 AS UNSIGNED) - CAST(2 AS UNSIGNED) AS wrapped;
-- 结果是一个接近 2^64 的极大值，而非 -1

-- 正确写法：先转有符号再减
SELECT CAST(1 AS SIGNED) - CAST(2 AS SIGNED) AS correct;
-- 结果为 -1
```

> [!CAUTION]
> **注意内容**：无符号相减的绕回极易在统计差值、计算余额时产生错误大数，且不会报错。凡是涉及减法或可能为负的中间结果，务必用 CAST(... AS SIGNED) 显式转换，或改用有符号类型存储。

> 速记：UNSIGNED 减去更小值会绕回成极大值，减法前先 CAST 成 SIGNED。



### AUTO_INCREMENT 与整数

#### 自增列的要点

**AUTO_INCREMENT**：是让整数列在每次插入时自动取上一个值加一的属性，常用于主键。

- **自动赋值**：插入不指定该列时，数据库自动填入当前最大加一。
- **唯一性**：通常配合主键或唯一索引，保证不重复。
- **可显式插入**：允许手动指定值，之后自增基准会跳到最大值加一。

```sql
-- 标准自增主键
CREATE TABLE orders (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  amount DECIMAL(10,2)
);

INSERT INTO orders (amount) VALUES (9.90);
-- id 自动为 1、2、3……
```

> AUTO_INCREMENT 的值只增不自动回收：删除中间行不会复用被删的 id，重启后 InnoDB 会以表中最大值为新基准（MySQL 8.0 起自增值持久化，重启不再回退到历史最大已用值加一的行为）。并发插入下自增不保证严格连续，只保证唯一与递增。



#### 自增整数类型的选择

**自增类型选择**：应预估表的行数上限，选能容纳且不过度的整数类型，通常 BIGINT UNSIGNED 最稳妥。

- **小表可用 INT**：行数远低于 21 亿时用 INT 足够。
- **大表用 BIGINT**：预期超 21 亿行或需留余量，直接用 BIGINT 避免后期改类型锁表。
- **UNSIGNED 更宽**：自增主键永不为负，用 UNSIGNED 把上限再翻倍。

```sql
-- 高频大表推荐写法
CREATE TABLE events (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  payload VARCHAR(255)
);
```

> 自增主键一旦选小了再改类型，需要 ALTER TABLE 重建表，大表 online DDL 也耗时。经验上：业务核心表、增长无上限的表直接上 BIGINT UNSIGNED；内部小配置表用 INT 即可。不要用字符或 UUID 做自增主键，会拖慢聚簇索引顺序写入。

> 速记：自增主键怕选小；核心表直上 BIGINT UNSIGNED，小表可用 INT。



### 浮点类型

#### FLOAT 与 DOUBLE 的存储与精度问题

**FLOAT 与 DOUBLE**：是用 IEEE 754 标准近似存储的浮点类型，FLOAT 占 4 字节、DOUBLE 占 8 字节，均不保证精确。

- **存储方式**：以符号位、指数、尾数近似表示实数，多数小数无法精确存下。
- **精度差异**：FLOAT 约 7 位有效数字，DOUBLE 约 15 位，DOUBLE 误差更小但仍不精确。
- **空间换精度**：DOUBLE 用双倍空间换来更高精度，但本质仍是近似值。

```sql
-- FLOAT 与 DOUBLE 的字节占用
CREATE TABLE fp (
  a FLOAT,
  b DOUBLE
);

-- 观察近似存储带来的微小差异
INSERT INTO fp (a, b) VALUES (0.1, 0.1);
SELECT a, b, (a + a + a) AS fa, (b + b + b) AS fb FROM fp;
```

> 浮点的不精确源于二进制无法有限表示多数十进制小数（如 0.1）。它们是近似值类型，适合科学测量、坐标等允许误差的场景，绝不适合金额、计数等要求分文不差的业务。



#### 浮点不可用于相等比较

**浮点相等比较**：因存储的是近似值，直接用等号比较几乎必然失败，应比较两者之差是否小于误差阈值。

- **直接判等会失效**：两个理应相等的浮点可能因舍入而略有差异。
- **阈值比较**：用 ABS(a - b) 小于 1e-6 之类的方式判定近似相等。
- **业务规避**：需要精确相等的金额类字段改用 DECIMAL。

```sql
-- 危险的写法：浮点直接判等
SELECT 0.1 + 0.2 = 0.3 AS is_equal;
-- 结果为 0（不相等）

-- 安全的写法：用误差阈值
SELECT ABS((0.1 + 0.2) - 0.3) < 1e-6 AS is_close;
-- 结果为 1（近似相等）
```

> 浮点比较的坑在看起来相等却判不等，且不同运算路径得到的字节可能不同。凡涉及相等、去重、范围边界的浮点，都应改用阈值比较或定点类型，绝不直接用等号。



#### 小数相加不精确的现象

**小数相加不精确**：是 IEEE 754 浮点用二进制近似十进制小数导致的典型现象，0.1 加 0.2 并不等于 0.3。

- **现象**：0.1 与 0.2 在二进制中均为无限循环小数，相加后被舍入。
- **结果**：存储的是极接近 0.30000000000000004 的值，而非 0.3。
- **验证**：用等号比较 0.1 加 0.2 与 0.3 返回假。

```sql
-- 直观验证浮点求和误差
SELECT 0.1 + 0.2 AS sum_result;
-- 显示 0.30000000000000004

SELECT (0.1 + 0.2) = 0.3 AS direct_equal;
-- 显示 0
```

> 该现象不是 MySQL 的 bug，而是所有遵循 IEEE 754 的语言（C、Java、JavaScript 等）的共性。结论：凡是金额、汇率、单价等需精确的小数，一律使用 DECIMAL，不要使用 FLOAT 或 DOUBLE。

> 速记：浮点求和会漂移，0.1 加 0.2 不等于 0.3；要精确就用 DECIMAL。



### 定点类型 DECIMAL

#### 语法 DECIMAL(M, D)

**DECIMAL(M, D)**：是精确存储小数的定点类型，M 为总位数（精度）、D 为小数位数（标度）。

- **M（精度）**：整数部分与小数部分的总位数，范围 1 到 65。
- **D（标度）**：小数点后的位数，范围 0 到 30，且 D 不大于 M。
- **省略写法**：只写 DECIMAL 时默认等价于 DECIMAL(10, 0)；DECIMAL(M) 等价于 DECIMAL(M, 0)。

```sql
-- 金额常用 DECIMAL(10,2)：共 10 位，其中 2 位小数
CREATE TABLE account (
  id INT,
  balance DECIMAL(10,2)
);

INSERT INTO account (id, balance) VALUES (1, 99.90);
```

> M 与 D 的选择要覆盖业务最大值与精度：余额到分用 DECIMAL(10,2) 可存到千万级；汇率到万分之一用 DECIMAL(12,4)。D 过大浪费空间，过小会截断小数，需按真实精度设定。



#### 精度保证的原理

**DECIMAL 精度**：以每 9 位十进制数打包进 4 字节的二进制编码整数形式存储，按十进制而非二进制舍入，从而保证精确。

- **整数存储**：DECIMAL 把数字当作整数序列存，不做二进制浮点近似。
- **打包规则**：每 9 位十进制数字占用 4 字节，剩余位数按表占用更少字节。
- **十进制舍入**：运算按 DECIMAL 规则舍入，不引入二进制误差。

```sql
-- DECIMAL 求和精确，不会漂移
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.2 AS DECIMAL(10,2)) = 0.3 AS exact_equal;
-- 当两操作数均为 DECIMAL 时为 1（相等）
```

> DECIMAL 的精确来自以十进制数字为单位存储与运算，绕开了二进制无法表示多数小数的根本问题。代价是计算比浮点慢、占用空间更大；但金额场景这点开销远小于出错代价。



#### 金额为什么必须用 DECIMAL

**金额必用 DECIMAL**：是避免分文误差的硬性要求，FLOAT 与 DOUBLE 在累加与比较中会逐步放大误差。

- **累加漂移**：大量浮点金额相加，误差累积可能差出几分甚至更多。
- **比较失真**：等号比较浮点金额可能判错，造成重复扣款或漏扣。
- **合规要求**：财务系统要求金额可精确对账，浮点无法满足审计。

```sql
-- 浮点累加误差示意
SELECT SUM(v) AS float_sum
FROM (SELECT 0.1 AS v UNION ALL SELECT 0.1 UNION ALL SELECT 0.1) t;
-- 浮点求和可能得到 0.30000000000000004

-- 改用 DECIMAL 累加精确
SELECT CAST(0.1 AS DECIMAL(10,2)) + CAST(0.1 AS DECIMAL(10,2)) + CAST(0.1 AS DECIMAL(10,2)) AS dec_sum;
-- 得到精确的 0.30
```

> [!IMPORTANT]
> **重要内容**：任何涉及钱的加减、对账、计税、利息的字段都不应使用浮点。即便单笔误差极小，海量累加后误差不可忽略，且浮点比较还会引发业务逻辑错误。这是数据库设计的基本铁律。

> 速记：钱用 DECIMAL，绝不用 FLOAT；浮点累加必漂移，对账必错。



#### DECIMAL 在 8.0 的存储改进

**DECIMAL 存储改进**：MySQL 8.0 对 DECIMAL 的存储格式做了优化，减少了空间浪费并提升了效率。

- **紧凑打包**：8.0 沿用并将每 9 位十进制数 4 字节的打包方式进一步做紧凑处理。
- **负零消除**：8.0 改进了对负零等边界值的处理，结果更稳定。
- **性能提升**：相比 5.7，DECIMAL 的运算与存储在某些场景更高效。

```sql
-- 对比不同 M、D 的实际字节占用（用 LENGTH 观察编码后大小）
CREATE TABLE dec_size (
  a DECIMAL(10,2),
  b DECIMAL(30,10)
);
```

> 具体字节节省依赖 M 与 D 的取值：例如 DECIMAL(10,2) 实际只需约 5 字节而非固定 9 字节。版本差异上，5.7 与 8.0 的 DECIMAL 二进制格式大体兼容，但 8.0 在边界值与效率上有改进；从旧版本升级通常无需改表结构，仅需留意极端标度场景的细微差异。



### 位类型 BIT

#### 语法 BIT(M)

**BIT(M)**：是按位存储的整数类型，M 为位数，范围 1 到 64，适合存标志位集合。

- **位数 M**：声明该列占多少二进制位，默认 M 为 1。
- **存储本质**：以二进制位串存放，而非十进制整数。
- **典型用途**：把多个布尔开关压缩进一个整数列，节省空间。

```sql
-- 用 BIT(8) 存 8 个标志位
CREATE TABLE flags (
  id INT,
  perms BIT(8)
);

INSERT INTO flags (id, perms) VALUES (1, b'00000101');
```

> BIT 与 TINYINT 不同：TINYINT 按数值存储与显示，BIT 按位串解释。取用时若不转换，MySQL 会把它当作二进制串返回，在客户端显示为不可打印字符，需用函数转换后才可读。



#### 取值与显示需要转换函数

**BIT 显示转换**：直接查询 BIT 列会得到二进制串，需用 BIN、HEX 或 CAST 转成可读形式。

- **BIN 函数**：把 BIT 值转成二进制字符串显示，如 00000101。
- **HEX 函数**：转成十六进制，便于核对字节。
- **CAST 转整数**：用 CAST(col AS UNSIGNED) 把位串当作整数取出，便于参与运算。

```sql
-- 直查会得到不可打印的二进制串
SELECT perms FROM flags WHERE id = 1;

-- 转为可读形式
SELECT BIN(perms) AS bin_form,
       HEX(perms) AS hex_form,
       CAST(perms AS UNSIGNED) AS int_form
FROM flags WHERE id = 1;
```

> BIT 列参与运算或条件比较时，也建议先 CAST 成整数，否则位串与整数的比较语义容易出错。需要第几位是否置位可用位运算：WHERE (perms >> 2) & 1 判定第 3 位。多数业务用 TINYINT 配合位运算更直观，BIT 仅在极端省空间诉求下使用。



### 数值类型的选型建议与速记

**数值选型**：按取值范围、精度需求、是否自增、是否需位运算四项决定类型，总原则是够用、小、简单。

- **整数主键**：统一 BIGINT UNSIGNED AUTO_INCREMENT，核心表免后期改类型。
- **普通整数**：在范围内选最小类型，非负量加 UNSIGNED。
- **精确小数**：金额一律 DECIMAL(M, D)，按真实精度设 M 与 D。
- **近似小数**：仅科学、坐标等允许误差场景用 DOUBLE，禁用相等比较。
- **位标志**：能用 TINYINT 位运算就别用 BIT，除非极省空间。

```sql
-- 一个综合建表示例
CREATE TABLE product (
  id        BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  stock     INT UNSIGNED,
  price     DECIMAL(10,2),
  rating    DOUBLE,
  flags     TINYINT UNSIGNED
);
```

> 选型口诀总结：整数从小到大挑、主键 BIGINT 稳；金额 DECIMAL 精、近似 DOUBLE 慎等；位运算多用 TINYINT，BIT 只备极省空间。结合更小通常更好、简单就好、避免 NULL 三原则，即可在大多数业务表中做出正确取舍。

> 速记：整小主 BIG、钱 DECIMAL、近 DOUBLE、位 TINYINT；浮点不判等，UNSIGNED 减法先 CAST。
