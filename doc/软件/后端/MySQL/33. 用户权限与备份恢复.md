## 用户权限与备份恢复

### 用户与权限

#### 最低权限原则

**账号只授予完成工作所需的最小权限**：安全的第一原则。

- root 只用于管理，业务连接一律专用账号
- 按职责分账号：应用读写账号、报表只读账号、运维管理账号
- 权限可授予的对象从大到小：全局、库、表、列
- 定期审计账号清单，离岗即回收

> 泄露是概率问题，权限是止损上限：一个只读账号泄露的损失与 root 泄露完全不同量级。最低权限是把“一定会发生的事故”控制在可承受范围。

**速记**：**root 不出机房，业务账号按需最小授**。



#### 创建用户与授权

**CREATE USER 与 GRANT 两步走**：账号与权限分离管理。

- CREATE USER 'app'@'%' IDENTIFIED BY '密码'：创建账号并限定来源主机
- 主机部分的含义：'%' 任意来源（不含 localhost 的辨析）、'10.0.%' 网段、'localhost' 本机
- GRANT SELECT, INSERT, UPDATE, DELETE ON 库.* TO 'app'@'%'
- REVOKE 回收；SHOW GRANTS FOR 查看
- 修改密码：ALTER USER ... IDENTIFIED BY '新密码'

> 'app'@'%' 与 'app'@'localhost' 是两个不同账号：localhost 的规则更具体，本机连接会匹配到它而不是百分号账号。授权排错时先核对“账号加主机”的完整标识。

**速记**：**账号带主机才算完整，GRANT 收窄到库**。

```sql
CREATE USER 'app'@'10.0.%' IDENTIFIED BY 'S3cure!pass';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app'@'10.0.%';
SHOW GRANTS FOR 'app'@'10.0.%';
```



#### 权限层级与常用权限

**权限金字塔四层**：全局、库、表、列，越往下越细。

- 常用数据权限：SELECT、INSERT、UPDATE、DELETE
- 结构权限：CREATE、ALTER、DROP、INDEX——谨慎授予应用账号
- ALL PRIVILEGES 包含管理权限，除 GRANT OPTION 外全占，克制使用
- 列级授权用括号列举：GRANT SELECT (name) ON 库.表 TO 账号

> 应用账号持有 DROP 与 ALTER 意味着代码里一个注入就能删表；结构变更走独立的迁移流程与账号。审计应用账号时，结构与数据权限分离是第一检查项。

**速记**：**数据权限给应用，结构权限归迁移，ALL 克制**。



#### 密码策略与角色

**validate_password 管强度，角色管批量授权**：8.0 的两个管理利器。

- validate_password 组件：控制密码长度、字符类别、与用户名重合
- CREATE ROLE 建角色，角色是一组权限的命名集合
- GRANT 角色 TO 用户：批量授权，职责变更只改角色
- SET DEFAULT ROLE 激活；密码过期策略防陈旧凭证

> 角色把“人变权限不变”的模式固定下来：新员工入职授角色，离职回收角色，权限矩阵不再跟着人走。团队规模过五人就该启用。

**速记**：**策略管强度，角色管批量，权限跟着角色不跟人**。



### 备份

#### 逻辑备份 mysqldump

**mysqldump 导出 SQL 文本**：最通用的备份工具。

- 单库：mysqldump -u 账号 -p 库名大于 备份文件.sql
- 全库：加 --all-databases；单表：库名后跟表名
- InnoDB 必加 --single-transaction：一致性快照备份，不锁业务
- --master-data 记录备份时的 binlog 位点，配合增量恢复

> --single-transaction 是 InnoDB 备份的关键参数：借 MVCC 拿到一致性快照，业务无感。不加它且没有锁表，导出的数据可能内部不一致。

**速记**：**dump 出文本，InnoDB 必带 single-transaction，位点记档**。

```bash
mysqldump -u backup -p --single-transaction --master-data=2 \
  shop > shop_20260907.sql
```



#### 物理备份与增量

**物理备份拷文件，增量备份靠 binlog**：两条线互补。

- 物理备份：直接备份数据文件，恢复快，代表工具 Percona XtraBackup
- 逻辑备份：可读可编辑可跨版本，恢复慢于物理
- 增量备份：定期全量加 binlog 连续归档，恢复时回放到任意时刻
- 备份保留策略：周期与副本数按容灾等级定，异地存放

> 全量加 binlog 是恢复能力的底座：全量定起点，binlog 补增量。binlog 保留期（expire_logs_days 或 binlog_expire_logs_seconds）必须长于备份周期，否则链会断。

**速记**：**物理快逻辑通用，全量定起点 binlog 补增量**。



### 恢复

#### 恢复的操作路径

**恢复分两段：先全量后增量**：演练过的流程才是流程。

- 全量恢复：mysql -u 账号 -p 库名小于 备份文件.sql，或 source 命令导入
- 时间点恢复：用 mysqlbinlog 解析 binlog，从备份位点回放到目标时刻
- 误操作止损：回放到误操作之前，跳过事故语句
- 恢复前先验证备份文件完整性，再在隔离环境演练

> 没演练过的备份等于没有备份：文件损坏、版本不兼容、字符集陷阱，都只在真恢复时暴露。定期把恢复演练做成例行任务，记录 RTO。

**速记**：**全量打底 binlog 续命，演练过才算有备份**。

```bash
mysql -u root -p shop < shop_20260907.sql
mysqlbinlog --start-position=157 --stop-position=88310 \
  binlog.000123 | mysql -u root -p shop
```



#### 误删防护

**误删的防线在事前**：四道闸门逐级拦截。

- 权限闸门：应用账号无 DROP 与 DELETE 全表权限
- 流程闸门：危险操作双人复核，先备份后执行
- 技术闸门：sql_safe_updates 拦截无 WHERE 的写（10 篇）
- 兜底闸门：binlog 与延迟从库，把恢复窗口拉到小时级

> 延迟从库（刻意落后主库一小时）是最朴素的“后悔药”：误删发生后一小时内，从库上还有完整数据。成本是加一台机器，价值是一次事故。

**速记**：**权限流程技术兜底四道闸，延迟从库留后悔药**。



### 综合运用

#### 备份策略清单

**一套能落地的备份策略**：五要素定齐。

- 周期：全量每周或每日，binlog 实时归档
- 保留：至少两个完整周期，重要库按合规要求延长
- 异地：副本离开主机房，防机房级故障
- 校验：备份后自动验文件与导入测试
- 演练：每季度恢复演练，记录 RTO 与问题

> 备份策略的每一条都在回答一个事故场景：盘坏了、库删了、机房没了、备份本身坏了。五要素齐备，四种场景都有解。

**速记**：**周期保留异地校验演练，五件套齐才叫策略**。
