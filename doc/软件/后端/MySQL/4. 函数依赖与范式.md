## 函数依赖与范式

范式回答一个很具体的问题：一张表里到底该放哪些列。它用函数依赖作为判据，用模式分解作为手段。本篇承接 E-R 转换得到的关系模式（3 篇），判断哪些模式该拆、能拆到什么程度，并给出无损与保持依赖这两条不可让步的底线。

### 函数依赖

#### 函数依赖的定义

**函数依赖**：是**关系模式中属性之间“一个值定下、另一个值就随之定下”的语义约束**，记作 X 决定 Y。

- 设 R(U) 是属性集 U 上的关系模式，X 与 Y 是 U 的子集
- 若对 R 的任意两个元组，只要它们在 X 上的取值相同，在 Y 上的取值也必然相同，则称 X 函数决定 Y，或 Y 函数依赖于 X
- X 称为**决定因素**，Y 称为**依赖因素**
- 函数依赖由业务规则决定，是语义约束，不能靠观察某一时刻的数据反推
- 与函数依赖并列的还有部分函数依赖、传递函数依赖、多值依赖（见后文）

> [!WARNING]
> **警告内容**：函数依赖必须对“任意两个合法元组”都成立，不是在当前数据里恰好成立。反例是当前表里恰好没有重名，于是看起来“姓名决定年龄”，一旦来了两位同名的同龄人，依赖立刻崩塌。凭数据样本推断函数依赖，是范式设计中最典型的错误来源，得出的一定是“恰好成立”而非“必然成立”。

**速记**：**X 同则 Y 必同，看语义不看样本**。



#### 平凡与非平凡、完全与部分、传递

**三类形态决定范式等级**：逐级收紧。

- **平凡函数依赖**：Y 是 X 的子集，如(学号, 姓名)决定学号，永远成立，无实际意义
- **非平凡函数依赖**：Y 不属于 X，如 学号决定姓名，才是真正有约束力的依赖
- **完全函数依赖**：X 决定 Y，且 X 的任何真子集都不能决定 Y
- **部分函数依赖**：X 决定 Y，但存在 X 的某个真子集也能决定 Y
- **传递函数依赖**：X 决定 Y、Y 决定 Z，且 Y 不决定 X、Z 不属于 Y，则称 X 传递决定 Z

例题：设 选课(学号, 课程号, 成绩, 课程名, 教师)，业务上课程号决定课程名与任课教师。

- 完全函数依赖：(学号, 课程号)决定成绩，因为单靠学号或单靠课程号都定不出成绩
- 部分函数依赖：(学号, 课程号)决定课程名，因为课程号单独就能决定课程名
- 传递函数依赖：(学号, 课程号)决定课程号，课程号决定教师，故(学号, 课程号)传递决定教师
- 三种形态指向三条不同的拆表理由，对应 2NF、3NF 与更细的分解

> 部分依赖与传递依赖都以“码”作为参照物。所以判断范式之前必须先定码，码定错了，范式判断必然跟着错——这是范式判断题失分最多的地方，不是依赖判断错，而是码求漏了。

**速记**：**部分依赖看真子集，传递依赖走中间站**。



#### 码的形式化定义

**候选码是能函数决定全部属性的最小属性组**。

- 设 K 是 R(U) 的属性子集，若 K 能决定 U，则 K 是 R 的**超键**
- 若 K 能决定 U，且 K 的任何真子集都不能决定 U，则 K 是**候选码**
- 包含在任一候选码中的属性叫**主属性**，其余属性叫**非主属性**
- 求候选码的方法：先找只在函数依赖左部出现过的属性，它们必然出现在每个候选码中；再求其闭包是否覆盖全部属性
- 主属性的判定标准是“是否出现在某个候选码中”，只要出现一次就算，不需要是码的全部

例题：设 R(A, B, C)，函数依赖集为(A, B)决定 C、C 决定 A。

- (A, B) 的闭包是全部三个属性，且 A、B 单独都推不出 C，故(A, B) 是候选码
- (B, C) 的闭包：C 决定 A，故得到 A、B、C，覆盖全部属性，且 B、C 单独都推不出全部属性，故(B, C) 也是候选码
- 结论：候选码有两个，主属性是 A、B、C 三个全部，非主属性为空
- 因为无非主属性，该模式天然满足 3NF；但它不一定满足 BCNF，见后文

> 主属性容易漏：它按“是否出现在任一候选码中”判断，而不是按“是否是某个候选码的核心”。这道例题里 C 是主属性，因为它出现在候选码(B, C) 中，尽管 C 单独不是码。

**速记**：**码是全决定者的最小组合，主属性看候选码全集**。



#### Armstrong 公理系统

**三条基本公理加三条常用推论，是推导函数依赖的全部工具**。

- **自反律**：若 Y 包含于 X，则 X 决定 Y。这条给出全部平凡依赖
- **增广律**：若 X 决定 Y，则(X, Z)决定(Y, Z)
- **传递律**：若 X 决定 Y、Y 决定 Z，则 X 决定 Z
- **完备性**：凡被函数依赖集逻辑蕴含的依赖，都能用这三条公理推出
- **可靠性**：用这三条公理推出的每个依赖，都确实被原依赖集蕴含
- **合并规则**：X 决定 Y 与 X 决定 Z，可得 X 决定(Y, Z)
- **分解规则**：X 决定(Y, Z)，可得 X 决定 Y 与 X 决定 Z
- **伪传递规则**：X 决定 Y 与(W, Y)决定 Z，可得(W, X)决定 Z

> 完备加可靠等于“不多不少”：推理系统推出来的恰好是所有被蕴含的依赖。正因如此，属性闭包算法才可以作为判定工具——把“某依赖是否被蕴含”转化为“其右部是否在左部的闭包里”。

**速记**：**自反增广传递三条够用，合并分解伪传递三条好用**。



#### 属性闭包与判定算法

**属性闭包是判断依赖蕴含的主力工具**。

- 属性集 X 关于依赖集 F 的闭包，记作 X 在 F 下的闭包，指所有能由 X 推出的属性组成的集合
- **算法**：结果集初始化为 X；反复扫描 F，若某依赖的左部包含于结果集，就把它的右部并入结果集；直到结果集不再变化
- 判定 X 决定 Y 是否被 F 蕴含，只需看 Y 是否包含于 X 的闭包
- 判定 K 是否为候选码，只需看 K 的闭包是否覆盖全部属性，且 K 的每个真子集的闭包都不覆盖全部属性

例题：设 R(A, B, C, D, E)，F 为 A 决定 B、C；C 决定 D；E 决定 A。求 E 的闭包。

推演步骤：

```text
第 1 遍扫描：
  结果集 = { E }
  E 决定 A，左部含于结果集 → 并入 A，结果集 = { A, E }
  A 决定 B、C，左部含于结果集 → 并入 B、C，结果集 = { A, B, C, E }
  C 决定 D，左部含于结果集 → 并入 D，结果集 = { A, B, C, D, E }
第 2 遍扫描：无新属性可并入，闭包确定
结论：E 的闭包覆盖全部属性，E 是候选码
```

> 手算的要点是“反复扫描到不动”：一遍扫描往往不够，因为新并入的属性可能成为别的依赖的左部。上面的例题正好演示了这一点——E 推出 A 之后，A 才推出 B 和 C，C 才推出 D，一条链要扫三遍才走完。

**速记**：**闭包反复扫到不动，判蕴含看包含，判码看全覆盖**。



#### 最小依赖集

**最小依赖集是函数依赖集的去冗余版本**：三个条件同时满足。

- **右部单一**：每个函数依赖的右部只含一个属性
- **左部无冗余**：去掉任一依赖左部中的任一属性后，都不再是被蕴含的依赖
- **无多余依赖**：去掉任一依赖后，剩余依赖的闭包与原依赖集的闭包相同
- 三条同时满足时，该依赖集称最小依赖集或最小覆盖
- 最小依赖集不唯一，与检查顺序有关，但所有最小依赖集的依赖个数相同

求法三步：

1. 用分解规则把每个依赖的右部拆成单属性
2. 逐个检查左部属性是否冗余：用去掉该属性后的左部求闭包，若能推出右部则该属性冗余，删去
3. 逐个检查依赖是否冗余：去掉该依赖后，其左部的闭包若能推出其右部，则该依赖多余，删去

例题：F 为 A 决定 B、B 决定 C、A 决定 C，求最小依赖集。

```text
第 1 步：右部已单一，无需拆分
第 2 步：各依赖左部均为单属性，无左部冗余可删
第 3 步：检查 A 决定 C。去掉它后，剩余依赖为 A 决定 B 与 B 决定 C
        A 的闭包 = { A, B, C }，包含 C，故 A 决定 C 可从其余依赖推出，判为多余
结论：最小依赖集为 { A 决定 B，B 决定 C }
```

> 最小依赖集的用处有两个：一是判断两个函数依赖集是否等价，二是作为 3NF 分解算法的输入（见后文）。判断等价时更稳妥的做法是“互相能推出对方的全部依赖”，而不是直接比较两个最小依赖集是否逐项相同。

**速记**：**右拆单、左删冗、依赖去多余，顺序不同结果不唯一**。



### 范式

#### 范式的意义

**范式**：是**衡量关系模式冗余程度、逐级加严的分级标准**。

- 不规范的表会带来三类异常：插入异常、删除异常、更新异常
- 造成异常的根源是属性之间的不良函数依赖
- 范式由低到高：第一范式、第二范式、第三范式、BCNF、第四范式、第五范式
- 满足高范式必然满足低范式，反之不然
- **规范化**：通过模式分解把低范式的关系模式提升到高范式

> 三类异常有统一的解释——一份事实被存在了多处。插入异常是想记录一件事，却因为缺少另一件事的数据而记不进去；删除异常是删掉一件事，顺带丢掉了另一件事的信息；更新异常是同一事实的多个副本没有同步。三者同源，源于冗余；冗余源于不良依赖；治法就是分解。

**速记**：**插入删除更新三异常，同源是冗余，治本是分解**。



#### 第一范式

**第一范式要求每个分量不可再分**。

- 定义：关系模式的每个属性都是原子的，不可再分
- 违反例子：把地址存成“山西省临县某街某号”，再想按县统计就得做字符串切分
- 违反例子：把联系电话存成“13800000000,13900000000”，无法对单个号码建索引或做等值查询
- 第一范式是关系模型对关系的基本要求，是“成为关系”的门槛，不是可选的优化
- 满足第一范式的关系模式记作属于 1NF

> 第一范式不是“要不要做”的问题，而是关系定义的一部分（2 篇）。实务中真正重要的不是判断“算不算 1NF”，而是识别哪些字段实际是多值或复合语义却被压成了一个字符串——JSON 字段就是典型的“用字符串绕过原子性”，它在约束与查询上都留有代价。

**速记**：**分量不可再分，1NF 是关系的入场券**。



#### 第二范式

**第二范式消灭非主属性对码的部分函数依赖**。

- 定义：R 属于第一范式，且每个非主属性都完全函数依赖于码
- 前提是码为组合码；若码是单属性，则不存在部分依赖，1NF 必然满足 2NF
- 违反例子：选课(学号, 课程号, 成绩, 课程名)，码是(学号, 课程号)，而课程号决定课程名，课程名部分依赖于码
- 分解方法：把造成部分依赖的那部分属性与其决定者一起拆出去，组成新的关系模式
- 分解结果：选课(学号, 课程号, 成绩) 与 课程(课程号, 课程名)

> “部分依赖只可能发生在组合码上”是判断题的常设陷阱：单属性码的关系模式不存在部分依赖，因此任何单属性码的 1NF 关系都自动属于 2NF。判断顺序永远是先求码、再看是否组合码，最后才看依赖形态。

**速记**：**码是组合才有部分依赖，拆出决定者即达标**。



#### 第三范式

**第三范式消灭非主属性对码的传递函数依赖**。

- 定义：R 属于第二范式，且每个非主属性都不传递依赖于码
- 等价表述：每个非主属性既不部分依赖码，也不传递依赖码
- 违反例子：学生(学号, 姓名, 班级号, 班主任)，码是学号，而学号决定班级号、班级号决定班主任，故班主任传递依赖于学号
- 分解方法：把传递链的中间站连同由它决定的下游属性拆成新关系
- 分解结果：学生(学号, 姓名, 班级号) 与 班级(班级号, 班主任)

> 3NF 与 BCNF 的区别是最容易混淆的一处：3NF 只约束非主属性对码的依赖，不约束主属性之间的依赖；BCNF 把约束扩展到所有属性。因此存在属于 3NF 却不属于 BCNF 的关系模式，反例见下一条。

**速记**：**部分依赖与传递依赖都不许，管的是非主属性**。



#### BCNF

**BCNF 要求每个决定因素都包含码**。

- 定义：R 属于第一范式，且对每个非平凡函数依赖 X 决定 Y，X 必为超键
- 通俗表述：每个非平凡函数依赖的左部都必须是超键
- BCNF 比 3NF 严格：3NF 允许主属性对码的部分与传递依赖，BCNF 不允许
- 属于 BCNF 的模式必然属于 3NF；反之不然
- 分解到 BCNF 一定可以做到无损连接，但不一定保持函数依赖（见后文）

例题：设 授课(学生, 课程, 教师)，业务规则为一名教师只教一门课、每门课有多名教师、一名学生选定某门课后就固定了该课的某位教师。

```text
函数依赖集：
  ( 学生, 课程 ) 决定 教师
  ( 学生, 教师 ) 决定 课程
  教师 决定 课程

求候选码：
  ( 学生, 课程 ) 的闭包覆盖全部属性 → 候选码
  ( 学生, 教师 ) 的闭包覆盖全部属性 → 候选码
  学生 单独、课程 单独、教师 单独均推不出全部属性

主属性：学生、课程、教师（三者都出现在某个候选码中，故全为主属性）
非主属性：空

范式判断：
  无非主属性 → 不存在非主属性对码的部分依赖与传递依赖 → 属于 3NF
  但 教师 决定 课程 中，教师不是超键 → 违反 BCNF → 不属于 BCNF
```

> 这个例题是范式理论里最经典的反例：全部属性都是主属性，3NF 的约束条件一条都碰不到，所以它属于 3NF；然而“一名教师只教一门课”这条规则带来的冗余依然存在。它证明了一件事——满足 3NF 不等于没有冗余，范式等级只是充分条件的阶梯，不是冗余的精确刻度。

**速记**：**左部必是超键，3NF 管非主属性，BCNF 管全部**。



#### 多值依赖与第四范式

**第四范式消灭非平凡且非函数的多值依赖**。

- **多值依赖**：X 多值决定 Y，表示对 X 的每个取值，Y 都有一组与之对应的值，且这组值与关系中其余属性 Z 的取值无关
- 由函数依赖导出的多值依赖称为平凡多值依赖，独立于函数依赖存在的才需要专门处理
- 定义：R 属于 BCNF，且每个非平凡多值依赖的左部都包含码
- 违反的信号：表的行数等于几组独立多值的笛卡尔积
- 分解方法：把互相独立的两组多值属性各自拆成一张表

例题：设 教师授课(教师, 课程, 班级)，一名教师可教多门课，也可带多个班，课程与班级之间没有关联。

```text
多值依赖：
  教师 多值决定 课程
  教师 多值决定 班级

候选码：( 教师, 课程, 班级 )，即全键

冗余表现：若某教师教 2 门课、带 3 个班，为穷举全部组合，表中必须有 6 行
范式判断：多值依赖的左部“教师”不是超键 → 违反 4NF

分解：
  教师课程( 教师, 课程 )
  教师班级( 教师, 班级 )
  两张表均属 4NF
```

> 多值依赖的产生根源是“把两个互不相关的多值事实放进了同一张表”，表里只好用交叉相乘的方式穷举组合。识别信号很直观：行数等于两组独立多值的乘积，且删掉一列会连带删掉另一列的信息。反过来说，若两组多值之间确有联系，就不构成多值依赖，也就无需拆分。

**速记**：**多值依赖两独立，交叉相乘是信号，拆成两表即 4NF**。



#### 第五范式与各级关系

**第五范式处理连接依赖**：理论完备性的补充。

- **连接依赖**：一个关系能被它的若干投影的自然连接无损还原，即存在连接依赖
- **第五范式**（投影连接范式）：R 属于 4NF，且每个非平凡连接依赖都由候选码蕴含
- 第五范式消除的是三元以上、由投影连接带来的冗余，实际业务中罕见
- **包含关系**：属于 5NF 必属于 4NF，属于 4NF 必属于 BCNF，属于 BCNF 必属于 3NF，依次向下直到 1NF
- 各级之间是严格包含，存在属于低一级而不属于高一级的模式，反例已在前面各条给出

> 实务中做到 3NF 或 BCNF 已经足够，4NF 与 5NF 属于理论完备性的补充。考试会考第五范式的定义与各级包含关系，但生产库里追求第五范式并没有收益。

**速记**：**5NF 管连接依赖，四级嵌套，实务止于 BCNF**。



### 模式分解

#### 无损连接

**无损连接是分解必须满足的底线**：分解后要能还原。

- **判定条件**（二元分解）：R 分解为 R1 与 R2，若 R1 与 R2 的交集能函数决定 R1 或能函数决定 R2，则该分解无损
- 多元分解可反复应用二元判定，逐步合并验证
- **直观含义**：分解后再做自然连接，结果与原关系完全相同，不多行也不丢行
- **有损分解**的后果是凭空造出原关系里根本不存在的元组

例题：R(学号, 姓名, 班级号) 分解为 R1(学号, 姓名) 与 R2(班级号, 姓名)。

```text
交集：{ 姓名 }
判定：姓名 能否决定 学号？不能
      姓名 能否决定 班级号？不能
结论：该分解是有损的

有损表现：若 R 中有两位同名但不同班的学生（张三，一班）与（张三，二班），
          自然连接时按姓名匹配，会凭空拼出一班张三与二班张三的组合行
```

> 无损的判定必须依赖函数依赖，不能靠“看起来相关”。上面的反例之所以有损，是因为交集属性既不是 R1 的码也不是 R2 的码，自然连接只能按姓名匹配，于是组合出了原关系里不存在的元组。

**速记**：**交集能定一侧才无损，凭直觉拆必出多行**。



#### 保持函数依赖

**保持函数依赖要求原有的依赖不被拆散**。

- **定义**：分解后各关系模式上的函数依赖集的并集，逻辑蕴含原依赖集的全部依赖
- **判定方法**：对原依赖集中的每个依赖，检查分解后其左部所在的关系模式中能否推出它的右部
- **经验观察**：若某个依赖的左右部属性落在不同的关系模式里，这条依赖通常就丢失了
- **能力差异**：3NF 分解可以同时做到无损与保持依赖；BCNF 分解只能保证无损，可能丢失依赖

例题：设 R(A, B, C)，F 为 A 决定 B、B 决定 C。

```text
分解一：R1( A, B ) 与 R2( B, C )
  无损：交集为 B，B 决定 C，即交集能决定 R2 相对 R1 多出的部分 → 无损
  保持依赖：A 决定 B 落在 R1 中，B 决定 C 落在 R2 中 → 两条都保持
  结论：无损且保持依赖

分解二：R1( A, B ) 与 R2( A, C )
  无损：交集为 A，A 决定 B，也能推出 C → 无损
  保持依赖：A 决定 B 落在 R1 中，但 B 与 C 分属两个模式，B 决定 C 丢失
  结论：无损但丢失依赖
```

> 丢失依赖意味着这条业务规则在数据库层面不再被约束，只能由应用代码或触发器去保证。这正是实务中更常见的选择停在 3NF 的原因——3NF 分解可以两者兼得，而 BCNF 不能。

**速记**：**依赖跨表就丢失，3NF 能两者兼得，BCNF 只保无损**。



#### 分解到第三范式的算法

**第三范式分解能同时满足无损与保持依赖**：合成法三步。

1. 求函数依赖集 F 的最小依赖集
2. 把最小依赖集中左部相同的依赖合并成一组，每一组构成一个关系模式
3. 若所得关系模式都不包含 R 的任一候选码，则把候选码单独作为一个关系模式加入

例题一：设 R(A, B, C, D)，F 为 A 决定 B、B 决定 C、C 决定 D，候选码为 A。

```text
第 1 步：最小依赖集就是 F 本身，右部已单一，左部无冗余，无多余依赖
第 2 步：左部互不相同，各自成组 → R1( A, B )、R2( B, C )、R3( C, D )
第 3 步：候选码 A 包含在 R1 中，无需补充
校验：属性并集覆盖 A、B、C、D；两两相邻模式的交集能决定其中一侧，逐个合并验证无损
结论：三个模式都满足 3NF，分解无损且保持依赖
```

例题二：设 R(学号, 姓名, 班级号, 班主任)，F 为 学号 决定 姓名、学号 决定 班级号、班级号 决定 班主任。

```text
第 1 步：最小依赖集同上，无冗余可删
第 2 步：左部为“学号”的两条依赖合并 → R1( 学号, 姓名, 班级号 )
        左部为“班级号”的一条独立 → R2( 班级号, 班主任 )
第 3 步：候选码“学号”包含在 R1 中，无需补充
校验：交集为班级号，班级号决定班主任 → 无损
结论：R1、R2 均满足 3NF，分解无损且保持依赖
```

> 第 3 步“补上候选码”是保证无损的关键，省略它可能得到一个既保持依赖又有损的分解。判断依据只有一句话：是否存在一个关系模式包含了 R 的某个候选码。

**速记**：**左部相同合并、补候选码保无损**。



#### 分解到 BCNF 的算法

**BCNF 分解保证无损但不保证保持依赖**：逐步分裂。

1. 令结果集只包含一个关系模式 R
2. 若结果集中所有模式都已属于 BCNF，结束
3. 取一个不属于 BCNF 的模式 S，找出其中违反 BCNF 的函数依赖 X 决定 Y，即 X 不是 S 的码
4. 把 S 分裂为(X, Y) 与(S 去掉 Y) 两个模式，用它们替换 S
5. 回到第 2 步

说明：分裂时第二个模式中保留 X，因为 X 是连接属性；分裂后的分解必然无损。

例题：授课(学生, 课程, 教师)，F 为(学生, 课程)决定教师、(学生, 教师)决定课程、教师决定课程。

```text
候选码：( 学生, 课程 ) 与 ( 学生, 教师 )

第 1 轮：授课 不属于 BCNF，违反者是 教师 决定 课程（教师不是码）
        分裂 → 授课1( 教师, 课程 ) 与 授课2( 学生, 教师 )
第 2 轮：两个模式均属于 BCNF，结束
        
无损校验：交集为“教师”，教师决定课程 → 无损
依赖校验：( 学生, 课程 ) 决定 教师 在任一模式中都推不出来 → 依赖丢失
```

> 这个例题是“BCNF 分解可能丢失依赖”的标准演示。依赖丢失意味着应用层必须自己保证这条规则，或者用触发器、应用事务补偿去实现。因此实务中的常见落点是停在 3NF：无损加保持依赖，代价只是接受一处已证明难以消除的冗余。

**速记**：**破坏者一拆为二，保无损丢依赖，实务常止于 3NF**。



### 规范化与反规范化

#### 规范化的收益与代价

**规范化减少冗余，代价是查询要多做连接**。

- **收益**：消除三类异常，同一事实只存一处，一致性由结构保证
- **代价**：查询要连接多张表，连接本身有开销
- 收益集中体现在写路径，代价集中体现在读路径
- 判断依据是读写比例、数据量级与连接列是否有索引
- 连接列都是主键上的等值匹配时，连接代价其实很小（27 篇）；连接很多张表或连接列无索引时才显著

> 把规范化的代价笼统说成“性能差”不准确：真正的代价是“连接次数”，而单次连接的成本取决于索引是否覆盖。所以“要不要反规范化”这个问题，必须先看连接能不能走索引，再谈取舍。

**速记**：**规范利写、连接损读，看读写比例定夺**。



#### 反规范化的手法与代价

**反规范化是有意识的冗余**：为读性能主动降低范式等级。

- **冗余列**：把被连接表的常查列复制过来，如订单表里存一份冗余的用户名
- **派生列**：直接存储可计算的值，如订单表存订单总金额，避免每次聚合
- **汇总表**：把聚合结果独立存储，如日销量汇总表，供看板直接读取
- **垂直拆分**：把大字段或低频列拆出主表，让主表更窄、单页装更多行
- **代价**：一致性维护责任从结构转移到应用与触发器，冗余列可能长期漂移

> 反规范化的核心不是“违反范式”，而是“把一致性维护的责任从结构转移到代码”。做这个决定前必须回答两个问题：这份冗余能否容忍短暂不一致；由谁负责同步。两个问题回答不了，就不要做。

**速记**：**冗余列、派生列、汇总表、垂直拆，代价是同步责任外移**。



#### 范式在工程中的落点

**范式给出判断标准，工程给出取值**。

- 交易、账务、主数据类表：做到 3NF 或 BCNF，宁多连接不冗余
- 高频读的报表与看板：可放宽到 2NF 甚至非范式，用汇总表换速度
- 日志与流水类表：只追加不更新，冗余风险小，可放宽
- **推进顺序**：先按 3NF 设计，实测有性能问题再定向反规范化
- 反规范化之后要在设计文档里写明冗余的字段、同步的责任方与对账手段

> 先规范再反规范，与一开始就随手冗余有本质差别：前者知道每一处冗余在哪里、为什么存在，也就知道什么时候该收回；后者不知道自己违反了哪条规则，出问题时无从下手。设计顺序本身就是一种可维护性。

**速记**：**先 3NF 打底，按实测定向反规范**。



### 综合运用

#### 范式判定四步法

**拿到一个关系模式，四步定出它属于第几范式**。

- 第一步：写出全部函数依赖，检查右部是否单一，必要时用分解规则拆开
- 第二步：求全部候选码，据此标出主属性与非主属性
- 第三步：检查是否存在非主属性对码的部分依赖；有则不属于 2NF，判定到此为止
- 第四步：检查是否存在非主属性对码的传递依赖；有则不属于 3NF；无则再逐个检查非平凡依赖的左部是否为超键，不是则不属于 BCNF

> [!IMPORTANT]
> **重要内容**：第二步不能省。所有范式判断都以码为参照，跳过求码直接看依赖，必然误判，尤其是主属性的判定必须先求全部候选码才能确定。一道题里漏掉一个候选码，3NF 与 BCNF 的结论就可能同时错。

**速记**：**先写依赖、再求码、查部分、查传递，最后看左部**。



#### 分解方案的检查清单

**得到分解结果后，三项检查缺一不可**。

- **无损连接**：用二元判定反复验证，确保自然连接能还原原关系
- **保持函数依赖**：逐条检查原依赖是否被某个分解后的模式蕴含
- **范式达标**：逐个模式检查属于第几范式，未达标则继续分解
- **三项并非总能同时满足**：3NF 可以三者兼得；若强求 BCNF，需接受依赖丢失
- **分解不是越细越好**：拆得过细会让连接数上升，也让保持依赖更难满足

> 判断在哪一级停下的依据是业务对“依赖丢失”的容忍度，而不是范式等级本身。丢失的若是一条由应用逻辑天然保证的弱约束，代价可以接受；丢失的若是一条账务规则，就必须停在 3NF 保留它。

**速记**：**无损、保依赖、达范式，三项并检，止于 3NF 最稳**。
