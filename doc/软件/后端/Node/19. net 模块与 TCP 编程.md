## net 模块与 TCP 编程

### TCP 与网络分层回顾

#### TCP 是面向连接的可靠字节流协议

**传输控制协议（TCP）**：是**面向连接、可靠、基于字节流**的传输层协议，它为上层应用提供有序、无差错、不重复的数据传输。

- **面向连接**：通信前需先三次握手建立连接，结束时四次挥手释放连接，通信双方始终维持连接状态。
- **可靠传输**：通过序列号、确认应答、超时重传、流量控制与拥塞控制，保证数据不丢失、不乱序、不重复。
- **字节流**：不保留消息边界，发送方多次写入可能被合并，接收方一次读取也可能跨越多次写入。
- **全双工**：连接建立后，双方可同时收发数据，互不干扰。

> TCP 的"可靠"指的是传输层尽力送达并保证顺序，并不保证应用层一定能正确处理；业务上的消息边界、超时、断线重连仍需应用自己设计。

**速记**：TCP **先握手、保顺序、无边界、可双工**。



#### TCP 与 UDP 的区别

**用户数据报协议（UDP）**：是**无连接、不可靠、基于数据报**的传输层协议，与 TCP 形成互补。

- **连接**：UDP 无连接，发送前不建立通道，每个数据报独立路由；TCP 必须建立连接。
- **可靠性**：UDP 不保证送达、不保证顺序、不重传；TCP 通过确认与重传保证可靠。
- **边界**：UDP 保留数据报边界，一次发送对应一次接收；TCP 是字节流，无边界。
- **开销与速度**：UDP 头部小、无控制逻辑，延迟低、吞吐高；TCP 控制复杂，开销更大。
- **适用场景**：UDP 适合实时音视频、游戏同步、广播；TCP 适合网页、文件传输、数据库等要求完整的场景。

> 两者都位于传输层、都依赖 IP 寻址，区别只在"是否做可靠性工程"。WebSocket 在握手阶段借 HTTP，之后跑在 TCP 之上，并非 UDP。

**速记**：TCP **求稳**，UDP **求快**；一个有边界一个没有。



#### HTTP 与 WebSocket 都建立在 TCP 之上

**应用层与传输层的关系**：HTTP 与 WebSocket 都属于应用层协议，它们的底层连接均由 TCP 承载。

- **HTTP**：每次请求响应通常依赖一条 TCP 连接（可复用），协议本身定义报文格式与语义，传输交给 TCP。
- **WebSocket**：握手用一次 HTTP 请求完成，升级成功后**复用同一条 TCP 连接**做全双工通信，绕开了 HTTP 的请求响应轮询。
- **net 模块**：直接暴露 TCP，是 http 模块的实现底座；理解 net 才能理解上层协议的连接本质。
- 本篇为第 29 篇 WebSocket 打基础：WebSocket 服务端本质上也是先拿到一个 TCP socket，再在其上做帧解析。

> 不要以为"HTTP 是短连接、WebSocket 是长连接"是协议决定的——二者底层都是 TCP；区别在应用层是否主动关闭、是否在同一连接上持续收发。

**速记**：HTTP、WebSocket **同根 TCP**，差别在应用层规则。



#### IP 加端口唯一确定一个连接

**五元组（Five-tuple）**：一条 TCP 连接由 **源 IP、源端口、目的 IP、目的端口、协议** 五者唯一标识，其中协议固定为 TCP。

- **IP**：在网络层定位主机，分清通信两端是哪两台机器。
- **端口**：在传输层区分同一主机上的不同进程，使一台机器能同时跑多个网络服务。
- **服务端端口**：通常由服务约定（如 80、443、自定义 3000 等），客户端据此找到目标进程。
- **客户端端口**：由操作系统临时分配（ ephemeral port），范围一般为 32768 至 60999，用完回收。
- 只要五元组任意一项不同，就是两条独立的连接；因此同一客户端可同时与服务器建立多条连接。

> 一个服务端端口能被大量客户端连接共享，正是因为每条连接还带上了各自的源 IP 与源端口。所谓"端口被占用"通常指**本端监听地址加端口**已被某进程绑定。

**速记**：连接靠 **IP 配端口** 这对组合唯一定位。



### net 模块与 Socket 抽象

#### net 提供两类对象

**net 模块**：是 Node 内置的传输层网络模块，核心对外暴露 **net.Server** 与 **net.Socket** 两类对象。

- **net.Server**：代表一个 TCP 服务器，负责监听端口、接受新连接，每当有客户端接入就产生一个 socket。
- **net.Socket**：代表一条**已建立的 TCP 连接端点**，既可用于服务器侧（连接进来的客户端），也可用于客户端侧（主动连出的连接）。
- 二者的关系：Server 是"守门人"，Socket 是"通话线路"；一条连接对应一对 socket（两端各一）。
- 引入方式：通过 require("net") 获取模块对象，再调用其方法创建 Server 或 Socket。

```js
const net = require("net");

// net 是模块对象，net.Server 与 net.Socket 是其提供的两个类
console.log(typeof net.createServer); // function
console.log(typeof net.createConnection); // function
```

> net.Server 与 http.Server 不是同一类：http.Server 内部持有一个 net.Server，并在其产生的 socket 上做 HTTP 解析。直接理解 net 能看清 http 的底座。

**速记**：net 给 **Server 管接入，Socket 管连线**。



#### Socket 是双工流

**net.Socket 的本质**：它同时继承可读流与可写流，是一个**双工流（Duplex Stream）**，因此既能读也能写。

- 因为是**可读流**，可以监听 **data 事件** 拿到对方发来的数据，也能用 pipe 把数据导给别的流。
- 因为是**可写流**，可以调用 **write 方法** 向对方发送数据，也能被别的流 pipe 进来。
- 由于继承 EventEmitter，socket 上可以注册 data、end、close、error 等事件，写法与流、事件模块一致。
- 这种"流"的抽象意味着第 13 篇 Stream 的全部概念（背压、编码、管道）在 socket 上同样适用。

```js
const net = require("net");

const server = net.createServer((socket) => {
  // socket 既是可读流也是可写流
  socket.on("data", (chunk) => {
    socket.write("echo: ");
    socket.write(chunk); // 把读到的数据写回
  });
});

server.listen(8124, () => console.log("server on 8124"));
```

> 把 socket 当作流来用，是 net 与上层流生态打通的关键：你可以用 pipe 把一个 socket 的输出直接接到文件，或把文件内容 pipe 进 socket 发给客户端。

**速记**：Socket **可读又可写**，是双工流故能 pipe。



### 创建 TCP 服务器

#### 用 createServer 创建服务器

**net.createServer 方法**：用于创建一个 TCP 服务器对象，其完整签名为 **net.createServer(connectionListener)**，亦可写作 **net.createServer(options, connectionListener)**。

- 参数 **connectionListener**：每次有新客户端连接时触发的回调，回调以 **socket** 为唯一参数，代表这条新连接。
- 参数 **options**：可选对象，常用字段有 allowHalfOpen（是否允许半关闭）、pauseOnConnect（连接建立时是否先暂停读取）等。
- 该方法返回一个 **net.Server** 实例，此时尚未开始监听，需再调用 server.listen 才会真正占用端口。
- 不传 connectionListener 也合法，之后可改用 server 的 **connection 事件** 来处理新连接。

```js
const net = require("net");

const server = net.createServer((socket) => {
  console.log("有新客户端接入");
});

// 仅创建尚未监听，端口还没被占用
console.log(server instanceof net.Server); // true
```

> createServer 只是"造好服务器"，端口要在 listen 之后才算占用；因此在 listen 之前再次修改配置是安全的，listen 之后改动通常无效。

**速记**：createServer **造服务器**，listen **才开门**。



#### 用 listen 启动监听

**server.listen 方法**：让服务器开始监听指定地址与端口，其常用形式为 **server.listen(port, host, listeningListener)**。

- 参数 **port**：要监听的端口号，传 0 表示由系统随机分配一个空闲端口。
- 参数 **host**：要绑定的 IP 地址，省略或传 "0.0.0.0" 表示接受来自所有网卡的连接；传 "127.0.0.1" 仅本机可连。
- 参数 **listeningListener**：监听成功后的回调，等价于 **listening 事件**，常用于打印启动日志。
- 省略 host 直接写 **server.listen(port, callback)** 也能工作；也可传一个对象 **server.listen({ port, host })**。

```js
const net = require("net");

const server = net.createServer((socket) => {
  socket.end("你好，已连接\n");
});

server.listen(8124, "127.0.0.1", () => {
  console.log("TCP 服务器已启动，监听 127.0.0.1:8124");
});
```

> 若端口已被占用，listen 会触发 **error 事件** 并报 EADDRINUSE；生产代码务必监听 error，否则进程会直接退出（见常见坑一节）。

**速记**：listen 三参数 **端口、地址、回调**，成功进 listening。



#### 完整可运行的回显服务器

**回显（Echo）服务器**：是最经典的最小 TCP 服务，把客户端发来的每一段数据原样发回，用于验证连接与收发链路。

- 在 connectionListener 中拿到 socket，监听其 **data 事件** 得到 Buffer 形式的数据块。
- 收到数据后调用 **socket.write** 写回；注意 data 给的是 Buffer，需要字符串时先 toString。
- 收到对方 **end**（半关闭）时，服务器也应结束自己的写入侧，避免挂起。
- 用命令行工具 telnet 或 nc 即可作为客户端手动测试这条服务器。

```js
const net = require("net");

const server = net.createServer((socket) => {
  const clientAddress = `${socket.remoteAddress}:${socket.remotePort}`;
  console.log(`客户端 ${clientAddress} 已接入`);

  socket.setEncoding("utf8");

  socket.on("data", (message) => {
    console.log(`收到：${message}`);
    socket.write(`服务器收到：${message}`);
  });
  socket.on("end", () => console.log(`客户端 ${clientAddress} 结束写入`));
  socket.on("close", () => console.log(`连接 ${clientAddress} 已关闭`));
  socket.on("error", (err) => console.error(`连接出错：${err.message}`));
});

server.listen(8124, "127.0.0.1", () => {
  console.log("回显服务器启动，端口 8124，可用 nc 127.0.0.1 8124 测试");
});
```

> 即便只是示例，也建议像上例一样挂上 error 事件：一条坏连接不应拖垮整个进程。setEncoding 让 data 直接是字符串，但会失去对原始字节的精确控制，按场景取舍。

**速记**：回显服务器 = **连上就收、收到就发**。



### 服务器的常用事件与方法

#### 服务器的关键事件

**net.Server 的关键事件**：服务器在生命周期中会触发若干事件，掌握它们才能写好启动、接入与关闭逻辑。

- **listening 事件**：调用 listen 且端口绑定成功后触发，适合打印"服务已启动"日志。
- **connection 事件**：每接受一个新连接触发，回调参数为该连接的 **socket**；与 createServer 的 connectionListener 等价。
- **close 事件**：服务器**不再接受新连接且所有现有连接都已结束**后触发，表示彻底关闭。
- **error 事件**：监听或运行过程中出错时触发（如端口占用），未监听会导致进程崩溃。

```js
const net = require("net");

const server = net.createServer();

server.on("listening", () => console.log("listening 事件：开始监听"));
server.on("connection", (socket) => console.log("connection 事件：新连接"));
server.on("close", () => console.log("close 事件：服务器已完全关闭"));
server.on("error", (err) => console.error("error 事件：", err.message));

server.listen(8124, () => console.log("已调用 listen"));
```

> listening、connection、close、error 是服务器的四根支柱：分别回答"开了吗、来了谁、关干净了吗、出啥错了"。其中 error 最容易被忽略却最致命。

**速记**：服务器四事件 **开、接、关、错** 对应 listening/connection/close/error。



#### 停止接收与查询连接

**server.close 方法**：启动服务器关闭流程，其签名为 **server.close(callback)**，调用后**不再接受新连接**但已建立的连接仍可继续。

- 调用 close 后，服务器立刻停止监听端口；已在通信的客户端连接不受影响，可正常收发直到自然结束。
- 当**所有现存连接都关闭**后，服务器触发 **close 事件**，此时 callback 也会被执行。
- 若想立刻掐断所有连接，需遍历并调用每个 socket 的 destroy，close 本身只拒绝"新"连接。
- **server.getConnections 方法**：签名为 **server.getConnections(callback)**，回调返回当前连接数 **count**，用于监控或限流判断。

```js
const net = require("net");

const server = net.createServer((socket) => socket.write("hi\n"));

server.listen(8124, () => {
  server.getConnections((err, count) => {
    if (err) throw err;
    console.log(`当前连接数：${count}`);
  });
});

// 某些时刻决定停止接新连接
function gracefulShutdown() {
  server.close(() => console.log("已不再接受新连接，旧连接结束后彻底关闭"));
}
```

> close 是"温和关闭"：它等人走完再关门，而非立刻轰人。需要"强制关门"应配合 socket.destroy；二者语义不同，别混用。

**速记**：close **拒新不放旧**，getConnections **查人数**。



#### 用 maxConnections 限流

**server.maxConnections 属性**：是一个可设置的数值，当当前连接数达到该上限时，服务器会**拒绝后续新连接**以保护自身。

- 设置方式直接赋值，例如 **server.maxConnections = 100**，超过 100 条时新连接会被服务器直接断开。
- 被拒的连接不会进入 connectionListener，也不会触发 connection 事件，连接方会感知到连接被关闭。
- 它是粗粒度保护，适合防止单进程被海量短连接拖垮；精细限流（如按 IP）仍需应用层逻辑。
- 配合 **server.getConnections** 可在监控面板展示实时并发，辅助容量规划。

```js
const net = require("net");

const server = net.createServer((socket) => socket.write("welcome\n"));

server.maxConnections = 50; // 超过 50 条并发连接即拒收新连接

server.listen(8124, () => {
  console.log("服务器启动，最大并发连接限制为 50");
});
```

> maxConnections 只限制"数量"不限制"来源"，也不能区分恶意连接；它更像保险丝而非防火墙。真正防刷还要结合超时、心跳与业务鉴权。

**速记**：maxConnections **设上限，超了就拒**。



### 客户端连接

#### 用 createConnection 连出

**net.createConnection 方法**：用于创建一个主动连向服务端的 socket，其别名是 **net.connect**，二者完全等价。

- 最简形式 **net.createConnection(port, host, connectListener)**，port 为数字、host 为字符串地址。
- 另一种形式 **net.createConnection(options, connectListener)**，options 是对象，可含 port、host、timeout、localAddress 等字段。
- 回调 **connectListener** 在连接成功建立后触发，等价于 **connect 事件**。
- 该方法返回一个 **net.Socket** 实例，可直接对其 write、监听 data，用法与服务端拿到的 socket 一致。

```js
const net = require("net");

// 形式一：port 加 host
const clientA = net.createConnection(8124, "127.0.0.1", () => {
  console.log("clientA 连接成功");
  clientA.write("来自 clientA 的问候\n");
});

// 形式二：options 对象
const clientB = net.createConnection(
  { port: 8124, host: "127.0.0.1" },
  () => {
    console.log("clientB 连接成功");
    clientB.write("来自 clientB 的问候\n");
  }
);
```

> createConnection 与 connect 是同一方法的两个名字，阅读他人代码时遇到 connect 不要以为是别的东西；options 形式还能指定本地出口 IP、超时等。

**速记**：客户端 **createConnection 两种写法**，连上触发 connect。



#### 连接事件与手动测试

**connect 事件**：客户端 socket 成功与服务端建立 TCP 连接后触发，是客户端开始收发的起点。

- 在 connect 回调或 connect 事件中调用 **socket.write** 发送首条数据，是客户端最常见的开场动作。
- 数据到达时同样监听 **data 事件**；连接被对端关闭时触发 **end**，本方想关闭时调用 **end** 或 **destroy**。
- 除写代码外，也可用系统自带命令行工具做手动联调：
  - **telnet 127.0.0.1 8124**：经典 telnet 客户端，连上后键盘输入即发往服务器。
  - **nc 127.0.0.1 8124**（netcat）：更现代，支持管道输入，适合脚本化测试。
- 手动测试能快速验证"端口通不通、收不收得到回显"，是排查网络问题第一步。

```bash
# 终端里连接本地回显服务器并发送一行
nc 127.0.0.1 8124
你好，服务器
# 会收到：服务器收到：你好，服务器
```

> 用 nc 或 telnet 测通，只能证明 TCP 链路与回显逻辑正常，并不证明应用层协议正确；复杂协议仍要靠真实客户端代码验证。

**速记**：连上先 **connect 再 write**，手动用 **nc/telnet** 探。



### Socket 的常用属性、方法与事件

#### Socket 的常用属性

**net.Socket 的只读属性**：每条 socket 都携带着连接两端的地址信息以及收发字节统计，便于日志记录与监控。

- **remoteAddress**：对端的 IP 地址字符串，如 127.0.0.1 或 ::1，用于识别"谁连的"。
- **remotePort**：对端使用的端口号，结合 remoteAddress 可唯一定位一条连接来源。
- **localAddress**：本端绑定的 IP 地址，多网卡机器上能看出数据从哪块网卡进出。
- **localPort**：本端用于这条连接的端口号，客户端通常由系统分配。
- **bytesRead**：截至目前从对端**读取**的字节总数，是累计值，常用于流量统计。
- **bytesWritten**：截至目前向对端**写入**的字节总数，含重传之前的尝试，常用于对账。
- **destroyed**：布尔值，表示 socket 是否已被销毁；销毁后任何读写都不再有效。

```js
const net = require("net");

const server = net.createServer((socket) => {
  console.log(`对端：${socket.remoteAddress}:${socket.remotePort}`);
  console.log(`本端：${socket.localAddress}:${socket.localPort}`);
  console.log(`已读 ${socket.bytesRead} 字节，已写 ${socket.bytesWritten} 字节`);
  console.log(`是否已销毁：${socket.destroyed}`);
});

server.listen(8124);
```

> 这些属性都是"快照式"的：bytesRead、bytesWritten 会在通信中持续增长，调试时应在合适时机读取，而非连接刚建立时就打印空值。

**速记**：Socket 属性记 **对端/本端地址端口 + 收发字节 + 是否销毁**。



#### Socket 的发送与关闭方法

**net.Socket 的写入与关闭方法**：掌握 write、end、destroy 的语义差异，是正确处理"发"与"断"的前提。

- **write 方法**：签名为 **socket.write(data, encoding, callback)**，把数据发往对端；data 可为字符串或 Buffer，返回 true 表示内核缓冲区尚有空间、false 表示已满（应等待 drain）。
- **end 方法**：签名为 **socket.end(data, encoding)**，发送完剩余数据后**半关闭**写入侧，告诉对端"我不再发"，但仍可继续读。
- **destroy 方法**：签名为 **socket.destroy(exception)**，立即**强制断开**连接、释放资源，不等数据发完，等价于异常断线。
- 半关闭（end）与全关闭（destroy）区别显著：end 是礼貌道别，destroy 是强行挂断。

```js
const net = require("net");

const client = net.createConnection(8124, "127.0.0.1", () => {
  const ok = client.write("第一条\n");
  console.log(`write 返回值（缓冲区是否已满）：${ok}`);

  client.end("最后一条，然后我关闭写入\n"); // 半关闭
});

// 需要立刻掐断时：
// client.destroy();
```

> 不要混用 end 与 destroy：end 之后 socket 仍可读对端数据，适合"我说完了但你还可以说"；destroy 之后连接立即消失，未发完的数据可能丢失。

**速记**：write **发数据**，end **半关写**，destroy **强断开**。



#### Socket 的超时与编码方法

**setTimeout 与 setEncoding 方法**：前者防御"死连接"占用资源，后者决定 data 事件拿到的是 Buffer 还是字符串。

- **setTimeout 方法**：签名为 **socket.setTimeout(milliseconds, callback)**，设置空闲超时；超过该时长无任何数据收发即触发 **timeout 事件**，但连接不会自动断开，需自行 destroy。
- **setEncoding 方法**：签名为 **socket.setEncoding(encoding)**，设置字符编码（如 utf8）；设置后 data 事件直接给出字符串，否则给 Buffer。
- 未调用 setTimeout 时连接可能永远死等；设了超时却不在 timeout 里处理，连接也只是"超时通知"而非"断开"。
- 用 Buffer 更精确（尤其处理二进制协议），用字符串更方便（文本协议）；粘包场景几乎都要先拿到 Buffer。

```js
const net = require("net");

const server = net.createServer((socket) => {
  socket.setEncoding("utf8"); // data 直接是字符串
  socket.setTimeout(30000, () => {
    console.log("30 秒无活动，判定为死连接，强制断开");
    socket.destroy();
  });

  socket.on("timeout", () => {
    console.log("触发 timeout 事件（需自行处理断开）");
  });
});

server.listen(8124);
```

> [!IMPORTANT]
> **重要内容**：timeout 事件本身不会关连接，这是常见误区：它只是"提醒你该处理了"，真正的断开要由你在回调或事件里调用 destroy 完成。

**速记**：setTimeout **设空闲超时**，setEncoding **定 data 形态**。



#### Socket 的关键事件

**net.Socket 的关键事件**：socket 在收发与生命周期中触发若干事件，正确监听它们才能处理消息、断线与异常。

- **data 事件**：每当内核收到一段数据触发，参数为 **Buffer**（或设了编码的字符串）；是接收消息的主入口。
- **end 事件**：对端调用 end 半关闭写入侧时触发，表示"对方不再发数据"，本方读侧到此结束。
- **close 事件**：连接完全关闭（无论正常还是因错误）后触发，参数 **hadError** 指示是否因错误关闭。
- **error 事件**：发生错误（如 ECONNRESET、EPIPE）时触发，不监听会导致进程崩溃。
- **timeout 事件**：空闲超时触发，需自行决定是否 destroy。

```js
const net = require("net");

const client = net.createConnection(8124, "127.0.0.1");

client.on("data", (chunk) => console.log(`收到：${chunk}`));
client.on("end", () => console.log("对端结束写入"));
client.on("close", (hadError) => console.log(`连接关闭，是否因错误：${hadError}`));
client.on("error", (err) => console.error(`出错：${err.message}`));
```

> data、end、close、error、timeout 构成一条 socket 的完整生命线。其中 **error 是红线**：任何 socket 都建议挂 error，否则一个异常连接就可能让整个 Node 进程退出。

**速记**：Socket 五事件 **收 data、知 end、晓 close、捕 error、警 timeout**。



### 与 HTTP 的关系

#### http 模块内部基于 net 实现

**http 与 net 的层级关系**：http 模块是 net 的上层封装，**每个 HTTP 连接的本质仍是一条 TCP 连接**，由 net.Server 接受后再做 HTTP 报文解析。

- 调用 http.createServer 时，Node 内部先创建一个 net.Server，并在其 connection 回调里对每条 socket 做 HTTP 协议解析。
- 解析完成后，才构造出大家熟悉的 **request 与 response 对象** 交给用户的请求处理函数。
- 因此 request 与 response 并非凭空出现，它们底层就是那个 socket 的"读写封装"：response.end 最终仍是通过 socket.write 把字节发出去。
- 理解了 net，就能明白"为什么 HTTP 服务器能同时处理多个请求"——本质是 net.Server 为每个 TCP 连接生成独立 socket，再各自解析。

```js
const http = require("http");

// http 服务器底层就是 net 服务器
const httpServer = http.createServer((req, res) => {
  res.end("hello");
});

httpServer.listen(3000, () => console.log("http 服务在 3000（底层为 TCP）"));
```

> 不要认为 http 与 net 是两套独立机制：http 只是在 net 之上加了"报文格式、头部、状态码"的规则。想看 HTTP 原始字节，只要在 net 层拦截 socket 的 data 即可。

**速记**：http **是 net 加了报文规则**，req/res **是 socket 的封装**。



#### 为什么 HTTP 服务器能复用端口

**端口复用的真相**：HTTP 服务器"一个端口服务千万请求"，不是端口被复用，而是**每条请求或连接各自占用一条 TCP 连接**，五元组保证它们互不冲突。

- 服务端监听的是"本端 IP 加端口"，这条监听通道固定；但每条进来的连接还带各自的源 IP 与源端口，于是五元组各不相同。
- HTTP/1.1 默认开启 keep-alive，一条 TCP 连接可串行承载多次请求，进一步减少握手；HTTP/2 更可在一条连接上多路复用。
- 无论是否复用连接，"端口被监听占用"指的是服务端监听地址，与并发连接数无关；连接数受文件描述符与系统限制约束。
- 此机制与 WebSocket 升级同源：升级后那条 TCP 连接不关闭，继续被 WebSocket 帧协议使用，所以 WebSocket 也能"复用"原端口。

> 所谓"端口复用"常被误解为多个进程抢同一端口；真正能多进程共绑一端口要用 SO_REUSEADDR/cluster，与"一个端口服务多连接"是两回事，别混淆。

**速记**：一端口 **接万连**，靠 **五元组区分各连接**。



### 粘包与拆包

#### TCP 没有消息边界

**粘包与拆包现象**：由于 TCP 是字节流协议，**一次 write 不对应一次 data**，发送方多次写入可能被合并接收，一次读取也可能横跨多次写入。

- **粘包**：发送方连续写 A、B 两条消息，接收方一次 data 事件里拿到 "AB" 合并体。
- **拆包**：发送方写一条较长消息，接收方分两次 data 事件才收全，每次只拿到半截。
- 根因在传输层：TCP 只保证字节顺序与完整，不保留应用层"消息"的界限。
- NET 模块暴露的 data 事件天然按"内核何时交付"触发，与应用写入节奏无关，因此不能假设一次 data 就是一条完整消息。

> 粘包/拆包是 TCP 的**正常行为**而非 bug；把它当成异常去"修"是误区。正确做法是在应用层定义消息边界，再按边界重新切分。

**速记**：TCP **只管字节流**，消息边界 **应用层自己划**。



#### 常见解决思路

**消息定界四类思路**：业界用四种主流方式在字节流中还原消息边界，按协议复杂度递增。

- **定长法**：每条消息固定长度，读满 N 字节即为一条；实现简单但浪费带宽、不灵活。
- **分隔符法**：用特殊字符（如换行符）分隔消息，读到分隔符即一条；适合文本协议，需注意转义。
- **长度前缀法**：消息头先写 body 长度，接收方先读长度再读对应字节；最通用，二进制协议首选。
- **结束标记法**：用特定字节序列标记结束（如 HTTP 的空行），本质也是分隔符的变体。

> 选型口诀：**文本协议用分隔符，二进制协议用长度前缀，极简场景用定长**。不要想着靠"sleep 等数据到齐"，那既不靠谱又拖性能。

**速记**：定界四法 **定长、分隔、长度前缀、结束标记**。



#### 按分隔符切分的简单实现

**分隔符解码器**：维护一个累积缓冲区，每次 data 把新数据拼上，再按分隔符切成若干完整消息，剩余的半截留到下次。

- 用一个 Buffer 或字符串变量 **buffer** 保存"尚未凑齐"的残留数据。
- 收到 data 后，把新片段追加到 buffer，然后按分隔符 **\n** 切分。
- 切出的若干段中，最后一段若为不完整残留（不含分隔符），留回 buffer 等待后续数据。
- 完整段即可作为一条消息交给业务处理函数，实现"流式拆包"。

```js
const net = require("net");

function createDelimiterDecoder(onMessage) {
  let buffer = "";
  function handle(chunk) {
    buffer += chunk.toString("utf8");
    const parts = buffer.split("\n");
    buffer = parts.pop(); // 最后一段是未完成的残留，留在 buffer
    for (const line of parts) {
      if (line.length > 0) onMessage(line);
    }
  }
  return { handle };
}

const decoder = createDelimiterDecoder((message) => {
  console.log(`收到一条完整消息：${message}`);
});

const server = net.createServer((socket) => {
  socket.setEncoding("utf8");
  socket.on("data", (chunk) => decoder.handle(chunk));
});

server.listen(8124, () => console.log("分隔符解码服务器启动"));
```

> 上例用字符串累积，适合文本；若协议含二进制或分隔符可能出现在正文中，应改用 Buffer 并在应用层转义。长度前缀法更严谨，是生产协议的主流选择。

**速记**：分隔符切分 = **累积缓冲 + 按界切开 + 残留留待下次**。



### 心跳与保活

#### 用 setKeepAlive 启用传输层保活

**socket.setKeepAlive 方法**：用于开启 TCP 层的 keep-alive 机制，其签名为 **socket.setKeepAlive(enable, initialDelay)**。

- 参数 **enable**：布尔值，true 表示开启 TCP keep-alive 探测。
- 参数 **initialDelay**：多久后开始首次探测（毫秒），用于避免连接一空闲就频繁探测。
- 开启后，操作系统在连接空闲足够久时会发送探测包，若对端无响应则判定连接已死并关闭。
- TCP keep-alive 的探测间隔与次数由**操作系统**决定，应用层只能开与设首探延迟，无法精细控制。

```js
const net = require("net");

const server = net.createServer((socket) => {
  socket.setKeepAlive(true, 10000); // 空闲 10 秒后开始探测
  socket.on("data", (chunk) => socket.write(chunk));
});

server.listen(8124);
```

> TCP keep-alive 间隔通常很长（Linux 默认两小时才首次探测），对"及时剔除死连接"往往不够快；它更偏"清理半死连接"而非"实时心跳"。

**速记**：setKeepAlive **开传输层保活**，但 **节奏由系统定**。



#### 应用层心跳与超时剔除

**应用层心跳**：在业务协议里周期性互发小型探测消息（ping/pong），用于及时发现并清理"逻辑上已断但 TCP 未感知"的连接。

- **必要性**：中间设备（NAT、代理、防火墙）常会静默丢弃长时间无数据的连接，TCP keep-alive 又太慢，于是需应用主动发心跳维持"存在感"。
- **实现**：服务端定时（如每 30 秒）向每个客户端发心跳，并维护"最后活跃时间"；超过阈值未收到任何数据（含心跳）即视为掉线。
- **超时剔除**：配合前面 socket.setTimeout 与 timeout 事件，空闲超时就 destroy，回收资源、从在线列表移除。
- 客户端也应回 pong，使双向都能确认对方存活，避免单边误判。

```js
const net = require("net");

const clients = new Map(); // socket -> 最后活跃时间戳

const server = net.createServer((socket) => {
  clients.set(socket, Date.now());

  socket.setTimeout(60000, () => {
    console.log("超时，剔除疑似掉线客户端");
    socket.destroy();
  });

  socket.on("data", (chunk) => {
    clients.set(socket, Date.now()); // 收到任何数据都刷新活跃时间
    if (chunk.toString().trim() === "ping") socket.write("pong\n");
  });

  socket.on("close", () => clients.delete(socket));
});

// 每 30 秒发一次心跳
setInterval(() => {
  for (const socket of clients.keys()) socket.write("ping\n");
}, 30000);

server.listen(8124);
```

> 心跳频率是权衡：太频繁浪费带宽、惊动中间设备，太稀疏又发现不了死连接。常见取值 15 至 60 秒，并与超时阈值保持数倍关系。

**速记**：心跳 **应用层 ping/pong**，超时 **剔除死连接**。



### 实战：多人聊天室服务端

#### 聊天室的整体设计

**聊天室服务端目标**：让多个客户端连接同一服务器，彼此收发消息，实现"上线通知、广播、下线清理"三大功能。

- **维护客户端列表**：用集合或 Map 保存当前所有存活的 socket，作为广播的目标池。
- **上线通知**：新连接接入时，向其他所有人广播"某某上线"，并可给新人发送在线名单。
- **广播消息**：某客户端发来消息，服务端加工后转发给除发送者外的所有人（或含发送者）。
- **下线清理**：连接 close 或 error 时，从列表中移除该 socket，并广播"某某下线"。
- 本协议用换行符作消息分隔（复用前节解码思路），消息体为纯文本，便于用 nc 直接测试。

> 设计上把"连接管理"与"消息分发"拆开：前者管生命周期，后者管广播。这样逻辑清晰，也方便之后加上鉴权、房间、持久化等扩展。

**速记**：聊天室 = **列表 + 上线通知 + 广播 + 下线清理**。



#### 完整可运行代码

**完整实现**：下面给出可直接运行的聊天室服务端，配合 nc 或 telnet 即可多人联机测试。

- 每个客户端首次发送的内容视作其昵称，后续内容作为聊天消息广播。
- 服务端在有人上线、发言、下线时分别广播系统提示。
- 所有 socket 统一用 Map 登记，close 与 error 都执行清理，避免内存泄漏。

```js
const net = require("net");

const PORT = 8124;
const clients = new Map(); // socket -> { name, buffer }

function broadcast(message, exceptSocket) {
  const payload = `${message}\n`;
  for (const socket of clients.keys()) {
    if (socket !== exceptSocket && !socket.destroyed) socket.write(payload);
  }
}

function handleData(socket, raw) {
  const state = clients.get(socket);
  state.buffer += raw;
  const lines = state.buffer.split("\n");
  state.buffer = lines.pop(); // 残留留待下次
  for (const line of lines) {
    const text = line.trim();
    if (!text) continue;
    if (!state.name) {
      state.name = text;
      broadcast(`系统：${state.name} 上线了`, socket);
      const online = [...clients.values()].map((c) => c.name).join("、");
      socket.write(`系统：当前在线 —— ${online}\n`);
      continue;
    }
    broadcast(`[${state.name}] ${text}`, null);
  }
}

function removeClient(socket) {
  if (!clients.has(socket)) return;
  const name = clients.get(socket).name || "匿名";
  clients.delete(socket);
  broadcast(`系统：${name} 下线了`, null);
}

const server = net.createServer((socket) => {
  clients.set(socket, { name: "", buffer: "" });
  socket.setEncoding("utf8");
  socket.write("请输入你的昵称：\n");
  socket.on("data", (chunk) => handleData(socket, chunk));
  socket.on("end", () => removeClient(socket));
  socket.on("close", () => removeClient(socket));
  socket.on("error", (err) => {
    console.error(`连接出错：${err.message}`);
    removeClient(socket);
  });
});

server.listen(PORT, "127.0.0.1", () => {
  console.log(`聊天室已启动，监听 127.0.0.1:${PORT}，用 nc 127.0.0.1 ${PORT} 加入`);
});
```

> 该实现刻意保持最小可用：昵称未做去重与鉴权，生产环境应增加唯一性校验、长度限制与敏感词过滤。广播前检查 socket.destroyed，防止向已销毁连接写入导致 EPIPE（见常见坑）。

**速记**：聊天室 **先登昵称再广播，close/error 都清理**。



### 常见坑

#### 未监听 error 事件导致进程退出

**未捕获的 socket 错误**：任何 socket、server 上的 error 事件若不监听，Node 会把它当作未处理异常**直接终止整个进程**。

- 典型触发：客户端强制拔网线产生 ECONNRESET，或对已关闭连接写入产生 EPIPE。
- server 上最常见的 error 是 EADDRINUSE（端口已被占用），listen 前未挂 error 监听就会崩溃。
- 防御方式：给每个 server 与 socket 都挂 **error 事件** 处理，至少打印日志并做清理，绝不让其冒泡到进程级。
- 也可用 **process.on("uncaughtException")** 兜底，但更应把错误在来源处就地处理，而非依赖全局兜底。

> [!WARNING]
> **警告内容**：这是 net 编程最高频的"线上事故"：本地测试连接正常，一上生产遇到脏连接就整服务挂掉。养成"建连接必挂 error"的肌肉记忆。

**速记**：**不挂 error，一崩到底**；每个 socket 都要接住异常。



#### 忘记清理断开的 socket 造成内存泄漏

**连接泄漏**：若把 socket 存进数组或 Map 却不在 close/error 时移除，已断开的连接对象会一直被引用，无法被垃圾回收。

- 长期运行的服务会随时间累积成千上万条"僵尸"引用，内存持续上涨直至 OOM。
- 根本原因：clients 列表只增不减，开发者只记得"连上就加入"，忘了"断开就删除"。
- 正确做法：在 **close 与 error 事件** 中都执行删除，且删除逻辑要做"是否已存在"的判断避免重复。
- 配合 **server.getConnections** 或定期统计 clients.size，可监控是否出现连接数只增不减的异常。

```js
// 反例：只加不删，必然泄漏
// clients.add(socket);

// 正例：close 与 error 都删除
socket.on("close", () => clients.delete(socket));
socket.on("error", () => clients.delete(socket));
```

> 连接泄漏常表现为"重启后就正常、跑几天就卡慢"，定位难。上线前务必核对每处"加入列表"是否都有对应的"移除"路径。

**速记**：存连接 **必配删除**，否则 **内存只增不减**。



#### 客户端异常断开未处理 EPIPE

**EPIPE 错误**：向**已关闭（或对端已断开）的连接写入**时，会触发 EPIPE（或 Windows 下的 ECONNRESET），若未处理即崩溃。

- 场景：服务端正要广播，目标客户端却突然断开，此时 socket.write 抛错或被 error 事件捕获为 EPIPE。
- 直接对可能失效的 socket 调用 write 有风险，应先判断 **socket.destroyed** 或 **socket.writable**。
- 广播循环中务必跳过已销毁的连接，并在 error 事件里执行清理，避免同一条死连接反复被写入。
- 半关闭情况下对端调了 end 但本方仍可写，此时写入仍安全；真正的 EPIPE 发生在对端已完全关闭之后。

```js
function safeBroadcast(message) {
  for (const socket of clients.keys()) {
    if (socket.destroyed) {
      clients.delete(socket); // 顺手清理
      continue;
    }
    socket.write(message);
  }
}
```

> [!CAUTION]
> **注意内容**：EPIPE 与"忘记清理"常常同时出现：未清理的死连接被反复写入，持续抛 EPIPE，既崩溃又泄漏。把"判断 destroyed + 写前清理"写成广播的标配即可同时规避两者。

**速记**：写前 **先查 destroyed**，遇 EPIPE **清连接防再写**。
