## Stream 流

### 为什么需要流

#### readFile 一次性读入内存的代价

**readFile 的内存问题**：fs.readFile 在回调前把**整个文件**读入内存，文件越大占用越高，超大文件或高并发下容易撑爆进程堆。

- 回调前内存峰值**等于文件大小**，整文件都在缓冲里。
- 首个字节要等**全文件读完**才可用，存在明显首字节延迟。
- 高并发多文件叠加，可能触发 **OOM 或交换颠簸**。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "big.iso");

// 一次性读完：文件多大，内存就占多大
fs.readFile(file, (err, data) => {
  if (err) throw err;
  console.log("已读入内存的字节数：", data.length);
});
```

> 第 11 篇指出 readFile 默认返回 Buffer；这里强调“一次性”的代价——回调前默默累积整文件，而非边读边处理。流式接口正是为消除这个积累而生。

**速记**：readFile **整文件进内存，大文件会爆**。



#### 流以分块实现恒定内存

**流（Stream）**：是 Node 中**按块（chunk）连续处理数据**的抽象接口，数据就绪一块就处理一块，不必等全部到齐，从而让内存占用与文件总大小脱钩。

- 处理单位是 **chunk**，通常是 Buffer，对象模式下可是普通对象。
- 内存峰值只与 **highWaterMark 量级**有关，无论文件 1 MB 还是 1 TB 都恒定。
- 首字节在**第一块到达时**即可处理，无需等待整文件。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "huge.bin");

const readable = fs.createReadStream(file, { highWaterMark: 64 * 1024 });
readable.on("data", (chunk) => {
  console.log("处理 64 KB 块，内存恒定");
});
```

> 流不是“更快的 readFile”，而是**不同的处理范式**：把“先聚齐再处理”变成“边到边处理”，语义差异比速度差异更关键。

**速记**：流是 **分块连续处理，内存恒定**。



### 流的四种类型

#### Readable 可读流

**Readable（可读流）**：是**数据源头**，向外产出数据块供消费，典型如 fs.createReadStream 与 HTTP 请求对象。

- 完整创建形如 **fs.createReadStream(path[, options])**。
- HTTP 服务里 **request 对象** 也是可读流，客户端上传数据以块形式到达。
- 它处于**暂停或流动**两模式之一，决定数据如何被取出（见本篇第四部分）。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "note.txt");
const readable = fs.createReadStream(file, { encoding: "utf8" });
readable.on("data", (chunk) => console.log("读到：", chunk));
```

> 可读流是“生产侧”：只负责把数据交出来，谁来接收、是否慢，由消费侧与背压机制协调。

**速记**：Readable **产数据，如 createReadStream、request**。



#### Writable 可写流

**Writable（可写流）**：是**数据汇聚处**，供外部写入数据块，典型如 fs.createWriteStream 与 HTTP 响应对象。

- 完整创建形如 **fs.createWriteStream(path[, options])**。
- HTTP 服务里 **response 对象** 也是可写流，向前端回传的数据逐块写入。
- 写入通过 **write 方法**，返回布尔值标识内部缓冲是否已满。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "out.txt");
const writable = fs.createWriteStream(file);
writable.write("第一行\n");
writable.write("第二行\n");
writable.end("结束\n");
```

> 可写流是“消费侧”：接收别人 push 进来的数据并落盘或转发，写入跟不上时通过背压反向反馈生产侧。

**速记**：Writable **收数据，如 createWriteStream、response**。



#### Duplex 双工流

**Duplex（双工流）**：是**同时具备可读与可写**的流，一端进一端出，典型如 net.Socket。

- 一个 Duplex 实例**既是 Readable 又是 Writable**，两端独立工作。
- **net.Socket** 既接收对端数据（可读），又向对端发送数据（可写）。
- TCP 连接天然双向，故 Socket 用 Duplex 建模最自然。

```js
const net = require("net");

const server = net.createServer((socket) => {
  socket.on("data", (chunk) => socket.write("收到：" + chunk)); // 读到的写回
});
server.listen(3000);
```

> Duplex 与“可读 + 可写”组合不同：它把双向通道封装成**单个对象**，读写各自独立、互不阻塞。

**速记**：Duplex **双向，如 net.Socket**。



#### Transform 变换流

**Transform（变换流）**：是**既消费又产出、且输出由输入变换而来**的 Duplex，典型如 zlib.createGzip 压缩流。

- 它继承 Duplex，但**写入的数据会被处理后再读出**，输入输出有因果。
- **zlib.createGzip** 把写入的明文压缩后从另一端流出。
- 常用于**压缩、加密、编码转换**等“流过即改”的场景。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");

const file = path.join(__dirname, "note.txt");
fs.createReadStream(file)
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream(file + ".gz"));
```

> Transform 与 Duplex 之别在语义：Duplex 读写可无关，Transform 的**读入必然驱动写出**（写入即触发变换输出）。

**速记**：Transform **写入即变换输出，如 createGzip**。



### 流与 EventEmitter 的关系

#### 流继承 EventEmitter 并以事件驱动

**流的事件本源**：所有具体流类都**继承自 EventEmitter**，每个流实例本身即事件发射器；流的整个生命周期都以**事件发射与监听**驱动，而非轮询或阻塞。

- 完整基类链为 **Stream → EventEmitter**，data、end、error 等事件本质就是给这个 EventEmitter 注册监听器。
- 产出数据触发 **data**，结束触发 **end**，出错触发 **error**，全程无需主动查状态。
- 这种“**发射—监听**”模型与事件循环（第 8 篇）天然契合，非阻塞且高效。

```js
const fs = require("fs");
const path = require("path");
const { EventEmitter } = require("events");

const file = path.join(__dirname, "note.txt");
const readable = fs.createReadStream(file);

console.log(readable instanceof EventEmitter); // true
readable.on("data", (c) => console.log("数据块"));
readable.on("end", () => console.log("读完了"));
readable.on("error", (err) => console.error("出错了", err));
```

> 正因为流是 EventEmitter，第 14 篇将展开的 event 机制是理解流的内部根基：流的“数据来了、结束了、出错了”全部以事件形式广播。

**速记**：流 **继承 EventEmitter，靠事件驱动**。



### 可读流的两种模式与常用事件

#### 暂停模式 paused 需主动读取

**暂停模式（paused）**：是可读流的默认初始模式，数据**不会自动推送**，必须主动调用 read 或监听 readable 事件来取块。

- 默认创建的可读流处于 **paused**，数据停在内部缓冲等待被取走。
- 通过 **read([size])** 取出下一块；不调用就不前进。
- 也可监听 **readable 事件**，在回调里调用 read 逐块抽取。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "note.txt");
const readable = fs.createReadStream(file); // 默认 paused

readable.on("readable", () => {
  let chunk;
  while ((chunk = readable.read()) !== null) {
    console.log("取出一块：", chunk.length);
  }
});
```

> 暂停模式适合“按需取用”：想自己控制节奏、按 size 精确抽块时，用 read 比自动推送更可控。

**速记**：paused **要手动 read 才出数据**。



#### 流动模式 flowing 与 pipe 切换

**流动模式（flowing）**：是可读流的工作状态，数据块会**自动持续推送**给 data 事件监听者；而调用 **readable.pipe(writable)** 会自动把流切到 flowing 并搬运。

- 一旦注册 **data 事件**监听，流从 paused 切到 **flowing**，开始自动推送。
- 想退暂停可调用 **pause 方法**，想恢复则调用 **resume 方法**。
- pipe 内部替你注册 data 监听，所以流立即进入流动、自动写盘，无需手动监听。

```js
const fs = require("fs");
const path = require("path");

const src = path.join(__dirname, "note.txt");
const dst = path.join(__dirname, "copy.txt");

const readable = fs.createReadStream(src);
// 绑定 data 即进入 flowing，自动推送
readable.on("data", (chunk) => console.log("自动收到：", chunk.length));

// 或改用 pipe：同样自动 flowing 并搬运
// readable.pipe(fs.createWriteStream(dst));
```

> flowing 与 paused 是同一流对象的两个状态，而非两类流；切换靠事件监听与 pause/resume 控制。pipe 背后正是一套写好的流动模式样板。

**速记**：flowing **绑 data 即推送，pipe 自动切换**。



#### 模式混用的陷阱

**混用陷阱**：在同一可读流上既用 pipe（流动模式）又手动监听 data（或同时调用 read），会导致**数据流被重复或错乱消费**，是初学者高频错误。

- pipe 已让流进入 flowing 并自动写盘，再监听 data 会得到**额外的重复副本**。
- 在 flowing 模式下调用 read 往往返回 null，因为数据已被自动推走，不会留在缓冲。
- 正确姿势是**二选一**：要么全程 pipe，要么全程手动 read/pause/resume。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "note.txt");
const readable = fs.createReadStream(file);
const writable = fs.createWriteStream(path.join(__dirname, "copy.txt"));

readable.pipe(writable); // 进入 flowing
readable.on("data", (chunk) => console.log("多余消费", chunk)); // 危险：重复
```

> [!WARNING]
> **警告内容**：同一可读流不要既 pipe 又监听 data。混用会让同一块数据既被写入又进入你的回调，造成重复处理、计数翻倍甚至逻辑错乱。选定一种消费方式并贯穿始终。

**速记**：模式 **二选一，勿 pipe 又监听 data**。



#### 可读流常用事件 data end error readable

**四大事件**：可读流对外暴露 data、end、error、readable 四个最常用事件，分别承担推送数据、宣告结束、上报异常、提示可读取。

- **data 事件**：每产出一块触发一次，参数是 chunk，绑定后即进入 flowing。
- **end 事件**：**所有数据已被消费完**时触发，表示流读到尽头。
- **error 事件**：读取出错（如文件缺失）时触发，**不监听会抛异常中断进程**。
- **readable 事件**：表示“内部缓冲有数据可读”，在 paused 模式下配合 read 使用。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "note.txt");
const readable = fs.createReadStream(file);

readable.on("readable", () => console.log("有数据可读了"));
readable.on("data", (chunk) => console.log("收到", chunk.length));
readable.on("end", () => console.log("全部读完"));
readable.on("error", (err) => console.error("错误", err.message));
```

> end 表示“数据读完”，不是“流已销毁”；error 不监听在旧版会抛未捕获异常致进程退出，新版虽改为销毁流但仍建议显式监听。

**速记**：data 推块、end 读完、error 报错、readable 可抽。



### 可写流的方法、事件与背压

#### write 返回布尔值与 highWaterMark

**write 与水位**：可写流的 **write(chunk[, encoding][, callback])** 把一块数据写入缓冲，其**返回值布尔值**告诉你内部缓冲是否已超过 highWaterMark 水位。

- 返回 **true** 表示缓冲未达水位，可继续放心写。
- 返回 **false** 表示已达或越过 **highWaterMark**，应暂停生产、等待 drain。
- **highWaterMark** 是可写流阈值参数，默认 16 KB，决定“缓冲多少算满”。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "out.txt");
const writable = fs.createWriteStream(file, { highWaterMark: 16 * 1024 });

const ok = writable.write("一些内容");
console.log("缓冲未满可继续？", ok); // true 表示还能写
```

> write 的返回值只反映“此刻缓冲是否超水位”，并不保证数据已落盘；落盘完成由 finish/drain 体现。把它当作“是否该踩刹车”而非“已写完”的信号。

**速记**：write 返回 **false 即该暂停等 drain**。



#### drain 事件与 end finish

**放行与落盘**：当可写流缓冲从“满”回落到可写时触发 **drain 事件**，提示可**恢复写入**；而 **finish 事件**要等**所有数据真正写入底层**后才触发，二者分工明确。

- **drain** 前提是此前 write 返回过 **false**，缓冲被底层排空后触发；经典用法是暂停数据源待 drain 再 resume。
- **end([chunk][, encoding][, callback])** 表示**不再写入新数据**并关闭流，之后 write 会报错。
- **finish** 在 end 之后、内部缓冲**全部排空落盘**时触发，是“真的写完了”的信号。

```js
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "out.txt");
const writable = fs.createWriteStream(file);

writable.on("finish", () => console.log("所有数据已落盘"));
writable.on("drain", () => console.log("缓冲排空，可继续写"));

writable.write("第一段\n");
writable.write("第二段\n");
writable.end("最后一段\n"); // 声明写完，finish 才确认落盘
```

> end 不等同“已写完”：它只声明意图，真正落盘要等 finish。需在写完后收尾（关句柄、回响应）应挂 finish 而非 end 之后。

**速记**：drain **放行续写，finish 确认落盘**。



#### backpressure 背压机制与经典写法

**背压（backpressure）**：当**写入速度跟不上读取速度**时，可写流用内部缓冲水位反向约束读取端，使“生产”与“消费”速率自动匹配。

- 可读读得快、可写写得慢，多余数据堆在可写流的**内部缓冲**。
- 缓冲超过 **highWaterMark**，write 返回 **false**，生产方应**暂停读取**。
- 缓冲回落触发 **drain**，生产方再**恢复读取**，形成负反馈闭环。

```js
const fs = require("fs");
const path = require("path");

const src = path.join(__dirname, "big.iso");
const dst = path.join(__dirname, "copy.iso");

const readable = fs.createReadStream(src);
const writable = fs.createWriteStream(dst);

readable.on("data", (chunk) => {
  if (!writable.write(chunk)) {          // 写不进则暂停
    readable.pause();
    writable.once("drain", () => readable.resume()); // 排空再恢复
  }
});
readable.on("end", () => writable.end());
```

> 这段“手动背压”正是 pipe 在背后替你做的事。自己写最易漏掉 drain 的恢复导致流永久暂停——要么用 pipe/pipeline，要么务必成对 pause 与 resume。

**速记**：背压 **write 假则 pause，drain 则 resume**。



### pipe、pipeline 与 finished

#### pipe 用法、返回值与自动背压

**pipe 方法**：**readable.pipe(writable)** 把可读流数据自动导入可写流，是最常见的“搬运”写法；其**返回值是目标可写流**，故支持链式调用，并**自动处理背压与结束**。

- 完整签名 **readable.pipe(destination[, options])**，destination 通常是可写流。
- 返回 destination 本身，可继续 **.pipe(下一个)** 串起多段（如 读→压缩→写）。
- 源 emit end 时 pipe 自动调用目标 end；传 { end: false } 可保留目标继续写。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");

const file = path.join(__dirname, "note.txt");

fs.createReadStream(file)
  .pipe(zlib.createGzip())              // 返回 gzip，可链式
  .pipe(fs.createWriteStream(file + ".gz")); // 自动背压 + 自动收尾
```

> pipe 把上节手写几十行的背压样板压缩成一行，且行为更可靠。凡是“源到目标的直线搬运”，优先 pipe 而非手动 data 拼接。

**速记**：pipe **返回目标流，自动背压与收尾**。



#### pipe 的局限与 pipeline 统一错误

**pipe 的薄弱点**：pipe **不会把上游错误自动传下游**，任一段出错都需各自监听 error；而 **stream.pipeline** 是 pipe 的增强替代，会**统一收集任意一段的错误**，错误处理远优。

- pipe 链中某流 emit error 只通知**自身**，不冒泡到整条链，漏挂的流可能静吞错误或崩进程。
- pipeline 现代用法走 **stream/promises**：**pipeline(source, transform, destination)**，用 await 等待，任一段出错都**传播到最终结果**。
- 完成后自动清理、销毁各流，避免句柄泄漏，是官方推荐的搬运方式。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");
const { pipeline } = require("stream/promises");

const src = path.join(__dirname, "note.txt");
const dst = src + ".gz";

async function compress() {
  try {
    await pipeline(
      fs.createReadStream(src),
      zlib.createGzip(),
      fs.createWriteStream(dst)
    );
    console.log("压缩完成");
  } catch (err) {
    console.error("任意一段出错都被这里捕获：", err);
  }
}
compress();
```

> [!CAUTION]
> **注意内容**：用 pipe 串联多段流时，必须给**每一段**单独挂 error 监听；漏挂的流一旦出错，错误既不会自动传到下游，也可能让未捕获异常终止进程。统一错误处理应改用 pipeline。

**速记**：pipe **错误不自动传，pipeline 统一收**。



#### finished 判断流结束

**finished 方法**：**stream.finished(stream, callback)**（或 Promise 版）用于**等待某个流彻底结束**（成功或出错），是监听 end/finish/error 的便捷封装。

- 它同时关注**成功与异常结束**，触发一次即视为完成，比手动监听多个事件省心。
- Promise 版来自 **stream/promises**，可 await 一个流的完整生命周期。
- 适合“等这条流真正跑完再继续”的场景，如测试、收尾统计。

```js
const fs = require("fs");
const path = require("path");
const { finished } = require("stream/promises");

const file = path.join(__dirname, "note.txt");

async function waitDone() {
  try {
    await finished(fs.createReadStream(file));
    console.log("流已彻底结束（含出错）");
  } catch (err) {
    console.error("流以错误结束：", err);
  }
}
waitDone();
```

> finished 与 finish 不同：finish 只代表“可写流落盘完成”，finished 可作用于任意流并能感知 error，语义更接近“整条生命周期画上句号”。

**速记**：finished **等流彻底终了，含出错**。



### 自定义 Transform、对象模式与实战

#### 自定义 Transform 实现 _transform 与 _flush

**自定义 Transform**：通过继承 **stream.Transform** 并实现 **_transform(chunk, encoding, callback)** 与可选 **_flush(callback)**，可写出“流过即变换”的流。

- **_transform** 每收到一块调用一次，用 **this.push(output)** 送出变换后的块，再调用 **callback()** 通知本块处理完。
- **_flush** 在所有输入结束后调用一次，用于**吐出剩余缓冲**（如压缩尾帧、换行收尾）。
- callback 首参数用于报错；无错传 null，等价于 callback(null)。

```js
const { Transform } = require("stream");

class PrefixTransform extends Transform {
  _transform(chunk, encoding, callback) {
    this.push(Buffer.from(">> " + chunk.toString()));
    callback();
  }
}
```

> _transform 里必须要么 push 要么 callback：只 push 不 callback 会卡住流，只 callback 不 push 则丢数据，两端配合才能正常流动。

**速记**：Transform **_transform 中 push + callback 配合**。



#### 大写转换的完整示例

**大写变换实例**：下面给出可运行的 Transform，把流经文本**逐块转为大写**，演示 push、callback 与流的串联。

- 创建名为 **createUppercaseTransform** 的函数返回 Transform 实例，便于复用。
- 在 _transform 中把 chunk 转字符串、toUpperCase，再 push 回去。
- 用 pipe 把它插在“读—写”之间，实现边读边转大写落盘。

```js
const fs = require("fs");
const path = require("path");
const { Transform } = require("stream");

function createUppercaseTransform() {
  return new Transform({
    transform(chunk, encoding, callback) {
      this.push(chunk.toString().toUpperCase());
      callback();
    }
  });
}

const src = path.join(__dirname, "note.txt");
const dst = path.join(__dirname, "upper.txt");

fs.createReadStream(src)
  .pipe(createUppercaseTransform())
  .pipe(fs.createWriteStream(dst))
  .on("finish", () => console.log("大写转换完成"));
```

> 这是 Transform 最典型骨架：读进 Buffer，toString 转文本处理，push 结果，callback 放行。把 toUpperCase 换成别的函数即可复用结构做加密、替换等。

**速记**：大写示例 **读→Transform→写，逐块 toUpperCase**。



#### 对象模式 objectMode

**对象模式**：给流传入 **objectMode 为 true** 后，流不再承载 Buffer 字节，而是**承载任意 JavaScript 对象**，此时 highWaterMark 表示**对象个数**而非字节数。

- 普通流以字节计数水位；**objectMode 下以对象个数计数**，默认 highWaterMark 为 16 个对象。
- 典型用途是**流式中转结构化数据**（逐条记录、逐行解析对象），而非原始字节。
- 读、写、变换流都支持 objectMode，但一条链上应**保持一致**，否则类型不匹配。

```js
const { Transform } = require("stream");

const toObject = new Transform({
  objectMode: true,
  transform(chunk, encoding, callback) {
    this.push({ raw: chunk.toString(), len: chunk.length });
    callback();
  }
});

toObject.write("hello"); // 流经的是对象，而非 Buffer
```

> objectMode 改变的是“流里流淌的是什么”：默认字节，开启后对象。水位阈值也随之从字节量变为对象数量，配置 highWaterMark 时务必按此理解。

**速记**：objectMode **流对象，highWaterMark 计个数**。



#### 实战：大文件复制

**流式复制**：用 **fs.createReadStream** 配 **highWaterMark** 控制分块大小，再 pipeline 到 **fs.createWriteStream**，即可在**恒定内存**下复制任意大文件。

- 通过 highWaterMark 设定每块字节数（如 64 KB），决定内存峰值与 IO 次数折中。
- 用 pipeline 串联读写，统一捕获错误，复制完成走 await 后的逻辑。
- 复制的是字节，无需关心编码，对文本、压缩包、镜像都通用。

```js
const fs = require("fs");
const path = require("path");
const { pipeline } = require("stream/promises");

function copyFileByStream(src, dst, chunkSize = 64 * 1024) {
  return pipeline(
    fs.createReadStream(src, { highWaterMark: chunkSize }),
    fs.createWriteStream(dst)
  );
}

const src = path.join(__dirname, "big.iso");
const dst = path.join(__dirname, "big-copy.iso");

copyFileByStream(src, dst)
  .then(() => console.log("复制完成"))
  .catch((err) => console.error("复制失败", err));
```

> 相比 readFile 一次性复制，流式复制内存只与 chunkSize 相关，是处理大文件的唯一稳妥方案。highWaterMark 越大单次 IO 越少但内存越高，按机器内存调参。

**速记**：大文件复制 **createReadStream 配 highWaterMark 后 pipeline**。



#### 实战：统计文件行数

**流式行数统计**：用可读流逐块读取，按换行符 **\n** 切分累加，可统计**超大文件行数**而无需整文件进内存。

- 难点在“一行可能被拆成两块”，需用一个 **remainder 变量**保存跨块未完成的半行。
- 每块按 \n 拆分，块内换行数即 **分裂段数减一**；末尾若非空算作半行待续。
- 流结束后若 remainder 仍有内容，再补计一行，避免漏掉末行。

```js
const fs = require("fs");
const path = require("path");
const { finished } = require("stream/promises");

const file = path.join(__dirname, "note.txt");

async function countLines(filePath) {
  let lineCount = 0;
  let remainder = "";

  const readable = fs.createReadStream(filePath, { encoding: "utf8" });
  for await (const chunk of readable) {
    const parts = (remainder + chunk).split("\n");
    lineCount += parts.length - 1;        // 换行数 = 段数 - 1
    remainder = parts[parts.length - 1];   // 保存半行
  }
  await finished(readable);
  if (remainder.length > 0) lineCount += 1; // 末行无换行也计一行
  return lineCount;
}

countLines(file).then((n) => console.log("行数：", n));
```

> 用 for await ... of 遍历可读流是 Node 12+ 的语法糖，内部等价监听 data/end，代码更线性。跨块半行用 remainder 续接是关键，直接对单块 split 会少算被切断的行。

**速记**：行数统计 **按 \n 拆分，remainder 续接半行**。
