## 文件上传与静态资源

### 表单上传的原理与 multipart 编码

#### 表单上传依赖 multipart/form-data 编码类型

**multipart/form-data**：是 HTTP 表单在需要提交**二进制文件**时使用的请求体编码类型，它把表单字段与文件内容以带边界分隔符的多个部分（part）组装进请求体，使文本与二进制能在同一次请求中并存。

- 浏览器在提交文件时**必须**使用此编码，否则文件内容无法正确传输。
- 每个部分自带独立的 **Content-Disposition、Content-Type 等子头**，声明字段名、文件名与数据类型。
- 各部分之间以报文首部声明的**唯一边界（boundary）字符串**隔开，后端按该边界切回各个字段。
- 与之配合的请求头为 **Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryxxxx**，boundary 由浏览器随机生成。

> 普通文本字段用 multipart 也能传，只是每个字段都被独立包裹、开销略大；只有涉及文件时它才是唯一正确选择。早期表单默认编码并不支持文件，multipart 是为解决"表单带附件"而专门设计的。

**速记**：文件上传 **必用 multipart，边界切多段**。



#### multipart 与 urlencoded 编码的区别

**application/x-www-form-urlencoded**：是表单的默认编码类型，它把字段按 **key=value** 形式拼接、特殊字符做百分号转义，只适合传输**纯文本键值对**，并不能承载二进制文件。

- **传输内容**：urlencoded 把所有字段压平成字符串，二进制无法无损表达；multipart 把文件作为原始字节块嵌入独立部分。
- **体积与效率**：urlencoded 对大文件会先百分号编码使体积膨胀约三倍，且需整段先编码再发送；multipart 直接流式写入字节，对文件更友好。
- **Content-Type 头**：urlencoded 的 Content-Type 固定为 application/x-www-form-urlencoded 且无 boundary；multipart 必须带 boundary 才能被解析。

```text
urlencoded 请求体示例：
name=%E5%BC%A0%E4%B8%89&avatar=...（二进制被转义，实际无法传文件）

multipart 请求体示例：
------WebKitFormBoundary
Content-Disposition: form-data; name="name"

张三
------WebKitFormBoundary
Content-Disposition: form-data; name="avatar"; filename="a.png"
Content-Type: image/png

<二进制字节>
------WebKitFormBoundary--
```

> [!NOTE]
> **提醒内容**：若表单同时含文本字段与文件字段，仍应统一用 multipart/form-data，不要为文本字段单独退回 urlencoded。后端解析库通常一次性处理 multipart 内的全部字段，混用两种编码反而需要两次解析。

**速记**：urlencoded **只传文本**，multipart **能载二进制**。



#### 浏览器端表单需设置 enctype 并可用 FormData 构造

**enctype 属性**：是 HTML 表单元素上用于声明请求体编码的属性；提交文件时必须把它设为 **multipart/form-data**，否则浏览器仍按默认 urlencoded 提交，导致服务端收不到文件。

- **表单写法**：在 form 元素上写 enctype="multipart/form-data"，并配合 method="post"，浏览器才会以多部分格式发送。
- **文件域写法**：用 input 元素、type 属性取 file、name 属性命名，多个文件可加 multiple 属性允许多选。
- **脚本构造**：用 **FormData 对象** 以代码方式组装，调用 append 方法加入字段名与值，其中文件可直接取文件输入框的 files 集合传入；FormData 会自动设置正确的 multipart 边界。
- **发送方式**：把 FormData 实例作为请求体传给 fetch 或 XMLHttpRequest，且**不能手动设置 Content-Type**，由运行时自动附带 boundary。

```html
<form action="/upload" method="post" enctype="multipart/form-data">
  <input type="text" name="name" />
  <input type="file" name="avatar" />
  <button type="submit">提交</button>
</form>
```

```js
const form = document.querySelector("form");
form.addEventListener("submit", async (e) => {
  e.preventDefault();
  const data = new FormData(form); // 自动按 multipart 编码
  await fetch("/upload", { method: "post", body: data });
});
```

> 用 fetch 发送 FormData 时若手动设置 Content-Type 头，boundary 会丢失而解析失败；务必让浏览器自行填充。这也是新手上传"后端收不到文件"的高频原因之一。

**速记**：表单 **enctype 设 multipart**，脚本用 **FormData 自动边界**。



### 原生解析的困难与 Multer 中间件

#### multipart 报文需按边界切分并解析各部分

**原生解析的难点**：multipart 请求体是一长串字节，其中穿插着**边界分隔符、各部分的子头与各自的体**，要从原始缓冲区中正确还原每个字段，必须完成"按边界切分、解析子头、抽取体"三步，手工实现极易出错。

- **切分边界**：边界字符串长度不固定、前后还带 -- 与换行前缀，需要精确扫描定位每一段的起止。
- **解析子头**：每个部分开头是若干行文本头（字段名、文件名、类型），需按行与冒号拆解，且编码与换行随客户端而变。
- **处理体**：文件体可能是二进制，不能当字符串处理，必须按字节截取并写入流，稍有不慎就截断或污染数据。
- **边界歧义**：文件内容里恰巧出现与边界相同的字节序列时，切分逻辑若不够严谨就会产生错段。

```text
原生解析需处理的报文骨架（简化）：
--boundary\r\n
Content-Disposition: form-data; name="avatar"; filename="a.png"\r\n
Content-Type: image/png\r\n
\r\n
<原始字节体>\r\n
--boundary--\r\n
```

> 手工解析不仅是繁琐，更藏着安全陷阱：边界处理不当会漏读、多读，甚至让攻击者构造畸形报文耗尽内存。生产环境不应自己重写解析器。

**速记**：原生解析 **切边界、析子头、抽体，步步易错**。



#### Multer 是处理 multipart 的 Node 中间件

**Multer**：是 Express 生态中专门用来**处理 multipart/form-data 请求**的 Node 中间件，它替开发者完成报文的边界切分、字段解析与文件落盘，只把解析结果挂在请求对象上供路由使用。

- **安装方式**：执行 npm install multer 把它加入项目依赖，随后通过 require 引入使用。
- **类型专一**：Multer **只对 multipart/form-data 类型的请求生效**，遇到其他编码（如 JSON、urlencoded）会直接**放行**给后续中间件，不做任何拦截。
- **结果落点**：解析出的文本字段进入 **req.body**，单文件进入 **req.file**，多文件进入 **req.files**。
- **与 body 解析互补**：JSON 与 urlencoded 由 express.json、express.urlencoded 负责，文件上传由 Multer 负责，二者不冲突、应按需同时挂载。

```bash
npm install multer
```

```js
const express = require("express");
const multer = require("multer");

const app = express();
const upload = multer(); // 暂不配置存储，仅解析

app.post("/upload", upload.single("avatar"), (req, res) => {
  res.json({ file: req.file, body: req.body });
});

app.listen(3000);
```

> [!IMPORTANT]
> **重要内容**：Multer 仅处理 multipart 类型，非 multipart 请求会被直接放过。因此不要把 Multer 当作"总解析器"，JSON 与表单文本仍需各自的解析中间件；三者按请求类型各司其职。

**速记**：Multer **只管 multipart，其他放行**。



### Multer 的存储引擎

#### diskStorage 配置 destination 与 filename

**diskStorage**：是 Multer 的**磁盘存储引擎**，通过两个回调函数 **destination 与 filename** 精确控制"文件存到哪个目录"与"落地后叫什么名字"，是生产环境最常用的存储方式。

- **完整创建**：调用 **multer.diskStorage(options)**，options 内提供 destination 与 filename 两个函数，二者都接收请求对象、文件对象与回调 cb。
- **destination(req, file, cb)**：通过 cb(null, 目录路径) 告诉 Multer 把文件写到何处；也可用字符串直接写死目录。
- **filename(req, file, cb)**：通过 cb(null, 文件名) 指定落盘文件名；若不提供，Multer 会生成无扩展名的随机名，导致后续难以按类型打开。
- **回调首参为错误**：两个函数第一个参数都用于传错误，无误时传 null，再传结果；传错误会中断上传并交给错误处理中间件。

```js
const fs = require("fs");
const path = require("path");
const multer = require("multer");

function ensureUploadDir(dir) {
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true });
}

const storage = multer.diskStorage({
  destination(req, file, cb) {
    const dir = path.join(__dirname, "uploads");
    ensureUploadDir(dir);
    cb(null, dir);
  },
  filename(req, file, cb) {
    const ext = path.extname(file.originalname);
    cb(null, Date.now() + "-" + Math.round(Math.random() * 1e9) + ext);
  }
});

const upload = multer({ storage });
```

> destination 与 filename 都用回调而非返回值，是为了兼容异步（如向数据库查目录）。即便逻辑同步，也必须调用 cb，忘记 cb 会让上传永久挂起。

**速记**：diskStorage **destination 定目录、filename 定名字，皆走回调**。



#### memoryStorage 存内存与自定义存储引擎

**memoryStorage**：是 Multer 的**内存存储引擎**，解析出的文件**不落盘**，而是以 **Buffer** 形式暂存在内存中，字段为 file.buffer，适合小文件或需要二次处理（如校验、转码、直传云存储）的场景。

- **完整创建**：调用 **multer.memoryStorage()** 得到引擎实例，再传给 multer 的 storage 选项。
- **适用边界**：只在内存里，文件越大占用的堆越高，超大文件会撑爆进程，故**仅适合小文件或需即时加工**的情形。
- **配合流式写出**：拿到 buffer 后可用 fs 写入、或用第 13 篇的流管道转发，避免一次性占满内存。
- **自定义存储引擎**：实现 **_handleFile(req, file, cb) 与 _removeFile(req, file, cb)** 两个方法即可接入任意后端（如直接写对象存储），把文件控制权完全交给开发者。

```js
const multer = require("multer");

const storage = multer.memoryStorage();
const upload = multer({ storage });

app.post("/upload", upload.single("avatar"), (req, res) => {
  const buffer = req.file.buffer; // 文件内容在内存中
  console.log("收到字节数：", buffer.length);
  res.json({ size: buffer.length });
});
```

> 内存引擎虽然省去目录管理，但文件常驻堆内存，高并发上传多份大图时风险陡增。能落盘优先落盘，需加工再取 buffer。

**速记**：memoryStorage **存 buffer，小文件或二次加工**。



### Multer 的基本用法与文件信息 req.file

#### multer(options) 创建实例与 single/array/fields/none

**multer(options)**：是 Multer 的工厂函数，传入**含 storage、limits、fileFilter 等选项的对象**（也可只写 dest 字符串快速落盘）后返回一个 **upload 实例**，该实例上挂载着若干中间件方法，用于声明"这条路由接收怎样的文件"。

- **single(fieldname)**：处理**单个文件**，fieldname 是表单中文件域的 name；结果在 req.file，多传的文件会被忽略或报错。
- **array(fieldname, maxCount)**：处理**同一字段名下的多个文件**，maxCount 限制最多数量；结果在 req.files 数组。
- **fields(fields)**：处理**多个不同字段名**的混合上传，参数形如 [{ name: "avatar", maxCount: 1 }, { name: "gallery", maxCount: 8 }]；结果在 req.files 对象，按键分组。
- **none()**：**只解析文本字段、拒绝任何文件**；若请求带了文件会触发错误，适合纯表单接口做一道闸门。

```js
const multer = require("multer");
const upload = multer({ dest: "uploads/" });

app.post("/one", upload.single("avatar"), handler);
app.post("/many", upload.array("photos", 12), handler);
app.post("/mix", upload.fields([
  { name: "avatar", maxCount: 1 },
  { name: "gallery", maxCount: 8 }
]), handler);
app.post("/text-only", upload.none(), handler);
```

> 这些方法本质是中间件，必须放在路由处理器之前注册；路由回调里才会拿到已解析的 req.file 或 req.files。字段名务必与前端 FormData 的 append 键、或 input 的 name 属性严格一致，否则收不到文件。

**速记**：single **单文件**、array **同字段多文件**、fields **混合字段**、none **拒文件**。



#### 文件信息 req.file 的字段含义

**req.file**：是 Multer 把**单个已上传文件**的元信息封装成的对象，挂载在请求对象上；当使用 array 或 fields 时，多文件以 **req.files** 呈现（数组或按键分组的对象），其每一项结构都与 req.file 相同。

- **fieldname（字符串）**：表单中文件域的 name 属性值，用于区分配对。
- **originalname（字符串）**：客户端上传时的原始文件名，**由客户端提供、不可信**，含路径或特殊字符皆有可能。
- **encoding（字符串）**：文件的传输编码，常见为 7bit 或 binary。
- **mimetype（字符串）**：客户端声明的 MIME 类型（如 image/png），同样**仅为声明、可被伪造**。
- **size（数值，字节）**：文件实际字节大小，是校验体积最可靠的字段。
- **destination（字符串）**：diskStorage 下文件被写入的目录路径。
- **filename（字符串）**：diskStorage 下落地后的文件名（不含目录）。
- **path（字符串）**：diskStorage 下文件的**完整磁盘路径**，可直接用于读取或返回。
- **buffer（Buffer）**：仅内存引擎存在，文件的完整字节内容。

```js
app.post("/upload", upload.single("avatar"), (req, res) => {
  const f = req.file;
  console.log(f.fieldname, f.originalname, f.mimetype, f.size);
  console.log("落盘路径：", f.path);
  res.json({ filename: f.filename, size: f.size });
});
```

> [!CAUTION]
> **注意内容**：originalname 与 mimetype 都来自客户端报文，**可被任意伪造**，绝不能仅凭二者就判定文件真实类型或当作安全文件名直接使用。可信的文件名应自行生成，真实类型应另作校验。

**速记**：req.file **八字段记全**，originalname 与 mimetype **皆不可信**。



### 上传限制与文件筛选

#### limits 选项与 MulterError

**limits 选项**：是传给 multer(options) 的**约束对象**，用于在上游就掐断超限请求，避免超大文件或过多字段拖垮服务；一旦触发上限，Multer 会抛出 **MulterError**，由错误处理中间件捕获并返回友好提示。

- **fileSize（数值，字节）**：单个文件最大字节数，超出即抛 LIMIT_FILE_SIZE。
- **files（数值）**：允许上传的文件总数上限，超出抛 LIMIT_FILE_COUNT。
- **fields（数值）**：允许的非文件文本字段总数上限。
- **fieldSize（数值，字节）**：单个文本字段值的最大字节数，默认约 100 KB 量级。
- **parts（数值）**：请求中字段与文件部分的总数上限，防畸形报文。

```js
const upload = multer({
  storage,
  limits: {
    fileSize: 2 * 1024 * 1024, // 单文件 2 MB
    files: 5,                  // 最多 5 个文件
    fields: 10,
    fieldSize: 1024 * 1024
  }
});

app.post("/upload", upload.single("avatar"), (req, res) => {
  res.json({ ok: true });
});

app.use((err, req, res, next) => {
  if (err instanceof multer.MulterError) {
    return res.status(400).json({ error: "上传受限：" + err.code });
  }
  res.status(500).json({ error: "服务器错误" });
});
```

> MulterError 的 code 字段（如 LIMIT_FILE_SIZE）可直接映射成中文提示；错误中间件必须带 **四个参数 (err, req, res, next)**，否则 Express 不会把它识别为错误处理中间件而漏掉捕获。

**速记**：limits **卡体积与数量**，超限抛 **MulterError**。



#### fileFilter 按白名单筛选

**fileFilter**：是传给 multer(options) 的**筛选函数**，在文件落盘前由 Multer 逐文件调用，开发者据此决定接受、静默拒绝还是报错拒绝，是实现"只允许特定类型上传"的关键闸门。

- **完整签名**：fileFilter 接收 **请求对象、文件对象、回调 cb** 三个参数，通过调用 cb 表达裁决。
- **接受**：cb(null, true) 表示放行该文件，继续后续存储流程。
- **静默拒绝**：cb(null, false) 表示拒绝但不报错，文件被丢弃、请求照常继续。
- **报错拒绝**：cb(new Error("类型不符")) 表示拒绝并把错误抛给错误处理中间件，适合想给前端明确提示时。

```js
const ALLOWED = ["image/png", "image/jpeg", "image/gif"];

function fileFilter(req, file, cb) {
  if (ALLOWED.includes(file.mimetype)) {
    cb(null, true);
  } else {
    cb(new Error("仅支持 PNG、JPEG、GIF 图片"));
  }
}

const upload = multer({ storage, fileFilter });
```

> [!TIP]
> **建议内容**：筛选优先用**白名单**（明确列出允许的少数类型）而非黑名单（排除已知危险类型）。黑名单永远追不上新出现的危险扩展名，白名单的"默认拒绝"语义天然更稳。

**速记**：fileFilter **白名单优先**，cb 首参报错即拒。



### 安全实践：可信文件名与真实类型校验

#### 不信任 originalname 与自行生成文件名

**路径穿越风险**：客户端上传的 originalname 完全可控，攻击者可在文件名里塞入 **../ 序列**或绝对路径，若直接拿它拼接待写路径，文件可能被写到 Web 根目录之外甚至覆盖系统文件，是上传功能最典型的安全事故。

- **危险做法**：用 path.join(uploadDir, file.originalname) 拼接，若 originalname 为 "../../etc/cron.d/evil" 就可能逃逸出上传目录。
- **安全做法**：**忽略 originalname 的路径部分**，只保留一个自行生成的名字（如时间戳加随机串），必要时才从原名的尾部提取纯扩展名并做白名单校验。
- **扩展名处理**：即使要保留扩展名，也应先用 path.extname 取出后检查是否在白名单，绝不允许 .php、.exe 之类可执行后缀混入。
- **目录隔离**：上传目录应与代码、配置目录物理分离，并**不赋予执行权限**，使即便上传了脚本也无法被当作程序运行。

> [!WARNING]
> **警告内容**：切勿把 originalname 直接当作落盘路径的一部分。攻击者只需构造一个含 ../ 的文件名即可实现**路径穿越**，把文件写到任意可写位置，配合可执行后缀可能进一步造成远程代码执行。文件名永远自己生成，原名的路径信息一律丢弃。

**速记**：originalname **路径不可信，文件名自己生成**。



#### 校验真实类型而非仅看扩展名或声明

**类型伪造风险**：攻击者可以把一个 PHP 木马的后缀改成 .png、再把 mimetype 伪造成 image/png，从而骗过只看扩展名或客户端的校验；仅靠这两处"声明"无法保证文件真实内容安全。

- **扩展名与 mimetype 皆声明**：二者都来自请求报文，客户端可任意填写，不能作为安全依据。
- **真实类型校验**：读取文件**头部魔术字节（magic number）**判断，例如 PNG 以 89 50 4E 47 开头、JPEG 以 FF D8 FF 开头、GIF 以 47 49 46 开头，与白名单比对。
- **结合大小限制**：在 limits 层先卡死体积，再在 fileFilter 或落盘后做真实类型校验，双重保险。
- **数量与频率限制**：除单文件大小外，还应限制总文件数与单位时间上传次数，防资源耗尽型攻击。

```js
function detectImageType(buffer) {
  if (buffer.length < 4) return null;
  if (buffer[0] === 0x89 && buffer[1] === 0x50) return "png";
  if (buffer[0] === 0xFF && buffer[1] === 0xD8) return "jpg";
  if (buffer[0] === 0x47 && buffer[1] === 0x49) return "gif";
  return null;
}

app.post("/upload", upload.single("avatar"), (req, res) => {
  const type = detectImageType(req.file.buffer);
  if (!type) return res.status(400).json({ error: "真实类型非图片" });
  res.json({ ok: true, type });
});
```

> [!CAUTION]
> **注意内容**：仅比对扩展名或 mimetype 属于**类型伪造**的高危薄弱点——恶意文件换个后缀即可蒙混过关。务必以文件头魔术字节核验真实类型，并在落盘后做病毒扫描、隔离存储，形成纵深防御。

**速记**：类型看 **魔术字节**，后缀与声明 **皆可伪造**。



### 大文件上传的进阶方案

#### 分片上传与断点续传

**分片上传**：是把一个大文件在**前端按固定大小切片**，逐片并发或串行传给后端，后端接收后按序号**合并还原**的方案；它把"一次传完整个大文件"拆成"多次传小片"，从而规避单请求超时、内存峰值过高与网络抖动导致的前功尽弃。

- **前端切片**：用 **Blob 的 slice 方法**把文件切成若干块，每块带上序号、总片数与文件标识（如 hash）逐个上传。
- **后端接收**：每片写入临时目录，文件名含序号；用 fileFilter 与 limits 依然适用，只是针对单片而非整文件。
- **合并还原**：待全部切片到齐，按序号顺序用流管道（参考第 13 篇）拼接成完整文件，再删除临时片。
- **断点续传**：前端先询问后端"已收到哪些片"，只补传缺失部分；后端以"已存分片集合"作为续传依据，网络中断后无需从头再来。

```js
const fs = require("fs");
const path = require("path");

function mergeChunks(fileId, total, dest) {
  const writeStream = fs.createWriteStream(dest);
  return new Promise((resolve, reject) => {
    let index = 0;
    function next() {
      if (index >= total) {
        writeStream.end(resolve);
        return;
      }
      const chunkPath = path.join("tmp", fileId + "-" + index);
      fs.createReadStream(chunkPath).on("end", () => {
        fs.unlinkSync(chunkPath);
        index += 1;
        next();
      }).pipe(writeStream, { end: false });
    }
    next();
  });
}
```

> 分片大小需权衡：太小则请求数过多、合并开销大；太大则单片失败重试成本高。常见取值为 1 MB 至 10 MB，并按网络与存储能力调参。

**速记**：大文件 **前端切片、后端合并、断点补传**。



#### 直传对象存储减少服务器压力

**直传对象存储**：是让前端**绕过自有应用服务器**，凭后端签发的临时凭证（如 Token、Policy）**直接把文件上传到对象存储（如 S3、OSS）** 的方案；服务器只负责鉴权与签发签名，不再承担文件字节的接收、落盘与转发，从而大幅降低带宽与计算压力。

- **流程拆分**：前端先请求后端换取上传凭证；再携凭证直连对象存储上传；上传完成后存储方回调或前端通知后端"已就绪"。
- **服务器收益**：应用服务器**不接触文件字节**，省去磁盘 IO 与内存占用，专注业务与权限。
- **安全要点**：签名需带**过期时间与路径前缀**约束，防止凭证被滥用去上传任意内容到任意位置。
- **与 Multer 的关系**：直传场景前端不走 multipart 到服务器，Multer 不再参与；但若保留"经服务器中转"的链路，Multer 仍可作为服务端接收入口。

> 直传并非取代 Multer，而是按规模分流：小文件、需服务器加工（如缩略图、病毒扫描）时走 Multer 中转；海量大文件、追求吞吐时走直传。两者可并存于同一产品的不同接口。

**速记**：直传 **服务器只签发、存储收字节**。



### 静态资源托管、优化与安全

#### express.static 托管静态目录

**express.static**：是 Express 内置的**静态文件中间件**，把一个磁盘目录映射为可通过 URL 直接访问的资源（如图片、样式、脚本），自动按请求路径查找文件，找不到时**交给下一个中间件**而非报错。

- **完整用法**：调用 **express.static(root, options)**，root 是静态目录的**绝对路径**，options 可配缓存、索引等；用 app.use 挂载。
- **路径映射**：访问路径等于 root 之后的相对路径，例如 root 为 ./public 时，public/style.css 通过 /style.css 取得。
- **未命中行为**：若请求路径在目录中无对应文件，express.static **不响应、也不结束**，而是调用 next 把请求交后续路由，因此不会干扰业务接口。
- **虚拟前缀**：用 app.use("/assets", express.static(root)) 给资源加统一前缀，避免与业务路由重名冲突。
- **常用 options**：maxAge 设浏览器缓存毫秒数，index 指定目录默认页（默认 index.html）。

```js
const express = require("express");
const path = require("path");
const app = express();

app.use(express.static(path.join(__dirname, "public")));

app.use("/assets", express.static(path.join(__dirname, "uploads"), {
  maxAge: 86400000,
  index: false
}));

app.listen(3000);
```

> 静态中间件的**注册顺序**决定优先级：放在路由之前则静态文件先匹配；若希望某业务路由覆盖同名静态资源，应把静态中间件注册在该路由之后。

**速记**：express.static **挂目录、可加前缀、未命中放行**。



#### 静态服务的优化：缓存、压缩与 CDN

**静态优化三板斧**：对静态资源的访问优化集中在**减少重复传输、压小体积、拉近用户距离**三条主线，典型手段即设置缓存头、启用压缩与引入 CDN。

- **Cache-Control 与 ETag**：用 maxAge 或手动 set 头返回 Cache-Control 让浏览器缓存；ETag 由服务端生成、供条件请求比对，内容未变时返回 304 省流量。
- **gzip 压缩**：安装并挂载 **compression 中间件**，对文本类资源（CSS、JS、HTML）做 gzip 压缩后再发，传输体积常降一半以上；它应注册在静态中间件之前以覆盖其响应。
- **CDN 加速**：把静态资源推到边缘节点，用户从就近节点取文件，显著降低延迟与源站压力。
- **独立域名**：为静态资源使用单独域名（或子域），可避开主域 Cookie 的额外开销，并便于独立配置缓存与跨域。

```js
const express = require("express");
const compression = require("compression");
const path = require("path");

const app = express();
app.use(compression()); // 压缩应在静态之前
app.use(express.static(path.join(__dirname, "public"), {
  maxAge: "1d",
  etag: true
}));

app.listen(3000);
```

> [!TIP]
> **建议内容**：compression 这类"改写响应"的中间件应**注册在 express.static 之前**，才能对静态文件产出的响应生效；顺序颠倒则压缩覆盖不到静态资源。缓存时长对带哈希文件名的资源可设很长，对易变资源应短些。

**速记**：静态优化 **缓存减传、压缩缩体、CDN 拉近**。



#### 静态服务的安全：路径穿越与目录列表

**静态安全底线**：express.static 默认已做**路径规范化（normalize）防护**，但部署时仍须注意不暴露敏感目录、谨慎开启目录列表，并理解默认首页行为，避免把本不该公开的路径变成可遍历资源。

- **敏感目录隔离**：静态根目录应只放可公开资源，切勿把含配置、密钥、源码的目录挂成静态根，防止被直接下载。
- **路径穿越防护**：express.static 内部会拒绝包含 **../ 的越界路径**请求；但一旦开发者在 options 里误开危险配置或自行拼接路径，仍可能漏防，须以"最小暴露面"为原则。
- **目录列表默认关闭**：默认不返回目录索引；若需列出目录，可引入 **serve-index** 中间件，但务必配合访问鉴权，否则等于把文件树公开给任何人浏览。
- **默认首页**：请求目录路径时若目录内有 index.html（或 options.index 指定页），express.static 会自动返回该页，行为类似传统 Web 服务器的默认文档。

> [!CAUTION]
> **注意内容**：需要"列出目录下文件"时若启用 serve-index，**等于把目录树对全网可见**。仅在受信任的内网或加了鉴权的场景下开放，且限定到具体子目录，切勿对上传目录、代码目录套用公开列表。

**速记**：静态安全 **最小暴露、列表慎用、穿越靠规范**。



### 实战：完整的头像上传接口

#### 目录创建、重命名与校验一体的 uploadAvatar

**头像上传实战**：把前述知识整合为一个可运行接口——**确保上传目录存在、自行生成安全文件名、按白名单校验真实类型与大小、返回可访问 URL**，同时用 express.static 让上传的图片能被直接访问。

- **目录保障**：用 ensureUploadDir 在每次上传前确认目录存在，不存在则递归创建，避免首次上传因目录缺失而失败。
- **安全命名**：文件名由时间戳加随机串加白名单扩展名组成，完全丢弃 originalname 的路径与可疑后缀。
- **类型与大小**：limits 卡单文件体积，落盘后用 magic number 校验真实图片类型，双重把关。
- **返回 URL**：用公开的静态前缀拼出可访问地址回给前端，前端即可直接展示。

```js
const express = require("express");
const fs = require("fs");
const path = require("path");
const multer = require("multer");

const app = express();
const UPLOAD_DIR = path.join(__dirname, "public", "avatars");

function ensureUploadDir(dir) {
  if (!fs.existsSync(dir)) fs.mkdirSync(dir, { recursive: true });
}

function detectImageType(buffer) {
  if (buffer[0] === 0x89 && buffer[1] === 0x50) return ".png";
  if (buffer[0] === 0xFF && buffer[1] === 0xD8) return ".jpg";
  if (buffer[0] === 0x47 && buffer[1] === 0x49) return ".gif";
  return null;
}

const storage = multer.diskStorage({
  destination(req, file, cb) {
    ensureUploadDir(UPLOAD_DIR);
    cb(null, UPLOAD_DIR);
  },
  filename(req, file, cb) {
    const ext = detectImageType(file.buffer) || ".bin";
    cb(null, Date.now() + "-" + Math.round(Math.random() * 1e9) + ext);
  }
});

const upload = multer({
  storage,
  limits: { fileSize: 2 * 1024 * 1024 }
});

app.use("/avatars", express.static(UPLOAD_DIR));

function uploadAvatar(req, res, next) {
  upload.single("avatar")(req, res, (err) => {
    if (err) return res.status(400).json({ error: "上传失败：" + err.message });
    if (!req.file) return res.status(400).json({ error: "未收到文件" });
    const type = detectImageType(req.file.buffer);
    if (!type) {
      fs.unlinkSync(req.file.path);
      return res.status(400).json({ error: "真实类型非图片" });
    }
    const url = "/avatars/" + req.file.filename;
    res.json({ ok: true, url, size: req.file.size });
  });
}

app.post("/upload-avatar", uploadAvatar);

app.use((err, req, res, next) => {
  if (err instanceof multer.MulterError) {
    return res.status(400).json({ error: "上传受限：" + err.code });
  }
  res.status(500).json({ error: "服务器错误" });
});

app.listen(3000);
```

> 实战中把 Multer 的 single 包进自定义处理函数 uploadAvatar，是为了在落盘后还能做"真实类型校验失败即删除文件"的清理，避免垃圾文件堆积。返回 URL 时只用前端可访问的静态前缀，不暴露服务器目录结构。

**速记**：头像上传 **建目录、自命名、验真型、返 URL**。



#### 路由注册与静态托管配合让图片可访问

**托管配合要点**：让上传成功的图片"立即可见"，关键在于把**存储目录与静态托管目录设为同一路径**，并用一致的虚拟前缀拼接返回 URL，使前端拿到的地址正好命中 express.static 暴露的路由。

- **路径一致**：diskStorage 的 destination 写 UPLOAD_DIR，express.static 也以 UPLOAD_DIR 为根并由 /avatars 前缀暴露，二者指向同一磁盘位置。
- **URL 拼接**：返回 /avatars/ 加 filename，浏览器请求该路径时由静态中间件直接回文件，无需额外路由。
- **缓存取舍**：头像类资源可给较长 maxAge；但若支持"换头像后立即可见"，应在文件名或查询串带版本号以绕过缓存。
- **错误兜底**：所有上传相关异常（含 MulterError）都汇入四参错误处理中间件，统一返回结构化错误，避免堆栈外泄。

```js
// 上传目录与静态暴露目录一致，是"上传即可访问"的核心
app.use("/avatars", express.static(UPLOAD_DIR, { maxAge: "7d" }));

// 前端拿到 { url: "/avatars/1699...-123.png" } 后直接 <img src={url} /> 即可显示
app.post("/upload-avatar", uploadAvatar);
```

> 若存储目录与静态根不一致，前端 URL 会 404；调试"上传成功却打不开"时，第一反应是核对二者是否指向同一目录、虚拟前缀是否与返回 URL 前缀匹配。

**速记**：可访问 **存托同目录、前缀对得上**。
