## fs 进阶：读写与目录操作

### 目录的读取与创建

#### fs.readdir 与 withFileTypes

**fs.readdir**：是读取**某个目录下一层**内容的异步方法，回调的第二个参数是该层条目的名字数组或 Dirent 对象数组，本身不会向下钻取子目录。

- 完整签名为 fs.readdir(path, options, callback)，省略 options 时返回纯名字字符串数组。
- 返回的名只是"本层条目名"，要得到可操作路径需自行配合 path.join 拼接父目录。
- 设 options 为 { withFileTypes: true } 后返回 **fs.Dirent 对象数组**，每个对象自带 name 与 isDirectory、isFile、isSymbolicLink 等判断方法。
- 读取失败（路径非目录、无权限）时 err.code 可能是 ENOTDIR 或 ENOENT。

```js
const fs = require("fs");
const path = require("path");

fs.readdir(__dirname, { withFileTypes: true }, (err, dirents) => {
  if (err) throw err;
  dirents.forEach((d) => {
    const type = d.isDirectory() ? "目录" : "文件";
    console.log(type, d.name);
  });
});
```

> withFileTypes 省去了"先 readdir 再逐个 stat 判类型"的额外 IO 往返，是遍历前筛选目录的高效入口。但它对符号链接不跟随：调用 isDirectory 会得到 false，需要"链接真实类型"时仍要 stat。

**速记**：readdir **一层名字，withFileTypes 给 Dirent 就地判型**。



#### fs.mkdir 与 recursive 多级创建

**fs.mkdir**：是创建**目录**的方法，配合 recursive 选项可一次性创建多级（尚不存在的）父目录，解决"目标深层、父级缺失"的场景。

- 完整签名为 fs.mkdir(path, options, callback)，options 可为权限数字或对象。
- 设 { recursive: true } 后，路径上所有缺失的中间目录都会被依次创建，无需逐层 mkdir。
- recursive 模式下已存在的目录不再报错、被当作"已就绪"跳过，使调用幂等。
- 不写 recursive 时，只要父目录不存在就报 ENOENT，只能创建最后一层。

```js
const fs = require("fs");
const path = require("path");

const target = path.join(__dirname, "a", "b", "c");

// 一次性创建 a/b/c 整条链；重复调用不会因已存在而失败
fs.mkdir(target, { recursive: true }, (err) => {
  if (err) throw err;
  console.log("多级目录已就绪（幂等）");
});
```

> recursive 的"幂等"让"确保目录就位"成为一句无副作用的调用。但权限位（mode）只在最终目录首次创建时整体套用，中间目录用系统默认权限。

**速记**：mkdir **recursive 一键建多级且幂等**。



#### ensureDirectory 的惯用封装

**ensureDirectory**：是社区中反复出现的**惯用封装函数名**，语义为"确保某目录存在（不存在就建，存在则无事发生）"，把 recursive 的 mkdir 包成可读性更强的意图表达。

- 函数接受目录路径，内部调用 fs.mkdir 配 recursive 并忽略已存在错误，暴露 Promise 或回调。
- 它把"建目录可能失败"收敛为单一职责，调用方无需每次重复写选项与判错。
- 在写入文件前调用一次，可消除 writeFile 报 ENOENT（父目录不存在）的隐患（第 11 篇已铺垫）。
- 命名言简意赅、直陈意图，是比裸 mkdir 更贴近业务语义的写法。

```js
const fs = require("fs");
const path = require("path");

function ensureDirectory(dir) {
  return new Promise((resolve, reject) => {
    fs.mkdir(dir, { recursive: true }, (err) => {
      if (err) reject(err);
      else resolve(dir);
    });
  });
}

ensureDirectory(path.join(__dirname, "logs", "2026"))
  .then(() => console.log("日志目录已就绪，可放心写入"))
  .catch((e) => console.error(e));
```

> 封装时不要把 ensureDirectory 写成"先 existsSync 判断再 mkdir"——这正是第 11 篇警示的 TOCTOU 写法。直接用 recursive 的 mkdir 并吞掉已存在错误，才是竞态安全的惯用法。

**速记**：ensureDirectory **包 recursive，意图即"确保存在"**。



### 目录的删除与存在性判断

#### fs.rmdir 与 fs.rm 删除目录

**删除目录**：fs 提供 **fs.rmdir（只删空目录）与 fs.rm（可递归删非空目录）** 两类入口，二者在"是否接受目录内有内容"上分野明确。

- **fs.rmdir**：完整签名 fs.rmdir(path, options, callback)，只能删空目录，目标非空时报 ENOTEMPTY。
- **fs.rm**：完整签名 fs.rm(path, options, callback)，配 { recursive: true } 可递归清空并删除非空目录。
- fs.rm 另支持 { force: true }：路径不存在也不报错，让删除调用幂等。
- 删单文件时 fs.rm 等效于 unlink；删非空目录时它等效于"递归清空 + rmdir"。

```js
const fs = require("fs");
const path = require("path");

// 只删空目录
fs.rmdir(path.join(__dirname, "empty"), (err) => {
  if (err) console.log(err.code); // 非空则 ENOTEMPTY
});

// 递归删非空目录；不存在也不报错
fs.rm(path.join(__dirname, "old-build"),
  { recursive: true, force: true }, (err) => {
    if (err) throw err;
    console.log("目录已彻底移除（或原本就不存在）");
  });
```

> fs.rm 是从 Node 14.14 起稳定的统一删除接口，更早版本常用 rimraf 等第三方库实现递归删除。选 rmdir 还是 rm 取决于"目录是否保证为空"。

**速记**：rmdir **只删空**，fs.rm **recursive+force 删非空且幂等**。



#### 递归删除的危险性与风险提示

**递归删除风险**：recursive 删除会**不可恢复地清空整棵目录树**，一旦路径变量出错指向了错误目录（如空字符串、根目录的某子树），损失远超删除单文件，必须谨慎对待。

- 递归删除没有"回收站"中转，删除即释放；误删真实数据同样无法撤回。
- 路径拼接错误、变量为空、或用户输入未校验，都可能让 rm 指向意料之外的层级。
- 在服务器脚本、部署钩子里执行递归删除前，应先断言目标确属"可丢弃"目录（如以缓存/临时前缀开头）。

> [!CAUTION]
> **注意内容**：对来自配置、用户输入或环境变量拼接出的路径执行 fs.rm 配 recursive 前，必须校验结果未越出允许范围，避免把项目根目录或系统目录整树删除。与第 10 篇路径穿越同理，凡"破坏性递归删除"都应在删除前打印并确认目标绝对路径。

```js
const fs = require("fs");
const path = require("path");

function safeRemoveCache(base, sub) {
  const target = path.resolve(base, sub);
  if (!target.startsWith(base)) throw new Error("拒绝删除越界路径");
  return fs.rm(target, { recursive: true, force: true }, (err) => {
    if (err) throw err;
    console.log("已安全清理：", target);
  });
}
```

> 防御式删除的核心是"先 resolve 再 startsWith 校验"：把目标解析成绝对路径后确认仍落在白名单基准目录内，再允许递归删除，可把误操作降到最低。

**速记**：递归删 **先校验落点，不可逆**。



#### 存在性判断的正确姿势

**存在性判断**：fs 提供 **fs.existsSync（同步存在探针）与 fs.access（异步权限探测）**，但二者都落在"先判断再操作"的时序里、存在竞态窗口；Node 推荐**直接操作并捕获 ENOENT**，把判断与操作合一。

- **fs.existsSync(path)**：同步返回布尔，会阻塞主线程，官方不推荐用于前置判断。
- **fs.access(path, mode, callback)**：异步检查存在/可读/可写，mode 用 fs.constants 的 F_OK、R_OK、W_OK，但两步间文件状态可能已变。
- 二者同源竞态（TOCTOU）：判断与使用之间文件可能被别的进程改动。
- 正确姿势是打开/读取/删除时，用错误对象的 code 为 ENOENT 分支处理"不存在"。

```js
const fs = require("fs");
const path = require("path");

// 不推荐：fs.existsSync 同步 + 竞态
if (fs.existsSync(path.join(__dirname, "x"))) { /* ... */ }

// 推荐：直接读，靠 ENOENT 分支
fs.readFile(path.join(__dirname, "maybe.txt"), "utf8", (err, data) => {
  if (err) {
    if (err.code === "ENOENT") { console.log("走初始化分支"); return; }
    throw err;
  }
  console.log("读到：", data);
});
```

> [!TIP]
> **建议内容**：把"先 existsSync 再读写"改写为"直接读写并在 err.code 为 ENOENT 时分支"。这样代码既无同步阻塞，也无竞态，还少一次系统调用，是 Node 文件系统操作的首选范式。

**速记**：正确姿势 **直接做，捕 ENOENT 分支**。



### 递归遍历目录

#### 手写递归遍历与异步生成器

**递归遍历**：指从根目录出发，**每遇子目录就深入、对每个文件执行处理**，把整棵目录树"走"一遍；传统写法用手写递归，现代写法用异步生成器配 for await。

- 典型封装命名为 **walkDirectory**，用 fs.readdir 配 withFileTypes，对 Dirent 用 isDirectory 判断是否下钻。
- 用 path.join 把当前条目名拼回"当前层路径"，得到下一层要下钻或处理的全路径。
- 异步生成器写为 async function 星号，内部用 yield 星号委派子目录，调用侧用 for await 线性消费。
- 生成器写法天然支持"边遍历边处理"，且每个 await 点可被事件循环让出，不阻塞主线程。

```js
const fs = require("fs");
const path = require("path");

async function* walkDirectoryAsync(dir) {
  const dirents = await fs.promises.readdir(dir, { withFileTypes: true });
  for (const d of dirents) {
    const full = path.join(dir, d.name);
    if (d.isDirectory()) yield* walkDirectoryAsync(full); // 委派子目录
    else yield full;
  }
}

(async () => {
  for await (const file of walkDirectoryAsync(__dirname)) {
    console.log("文件：", file);
  }
})();
```

> 异步生成器用 yield 星号实现"递归产出"，比手写回调更贴近同步阅读直觉。注意它依赖 fs.promises.readdir（Promise 风格），与回调风格互补。

**速记**：walkDirectory **readdir 下钻，for await 用 yield 星号**。



#### 深度优先与广度优先的取舍

**遍历策略**：目录遍历按"先深还是先宽"分为**深度优先（DFS）与广度优先（BFS）** 两类，二者在内存占用、结果顺序与适用场景上取舍不同。

- **深度优先**：沿一条分支走到叶再回退，递归即天然 DFS，实现简单但深目录撑高调用栈。
- **广度优先**：先处理完当前层所有条目再统一进入下一层，需用队列显式保存待访问目录，调用栈浅但占内存多。
- 结果顺序：DFS 输出"先到底再旁支"，BFS 输出"逐层铺开"，排序需求不同则选法不同。
- 超大或未知深度的目录树，递归 DFS 有栈溢出风险，应改用显式栈或 BFS。

```js
const fs = require("fs");
const path = require("path");

// 广度优先：用队列逐层下钻，避免递归过深
function walkBreadthFirst(root, onFile) {
  const queue = [root];
  while (queue.length) {
    const dir = queue.shift();
    fs.readdirSync(dir, { withFileTypes: true }).forEach((d) => {
      const full = path.join(dir, d.name);
      if (d.isDirectory()) queue.push(full);
      else onFile(full);
    });
  }
}
```

> 选型口诀：**要顺序铺开用 BFS，要代码最简用 DFS，目录可疑极深则避开递归**。默认手写递归即 DFS，BFS 用队列消解递归深度。

**速记**：DFS **递归先深**，BFS **队列先宽**。



### 文件复制与权限属性

#### fs.copyFile 与 COPYFILE_EXCL

**fs.copyFile**：是把**源文件内容复制到目标路径**的方法，默认覆盖已存在的目标，且不读入内存（由内核在文件间搬运），适合大文件拷贝。

- 完整签名为 fs.copyFile(src, dest, mode, callback)，src 与 dest 可为路径或已打开的 fd。
- 默认（省略 mode）情况下 dest 已存在则**整体覆盖**；目标所在目录必须已存在。
- mode 传 **fs.constants.COPYFILE_EXCL**：目标已存在时**拒绝覆盖并报 EEXIST**，用于防意外替换。
- 它比"readFile 再 writeFile"更高效，省去了把数据搬进用户态 Buffer 再写回的往返。

```js
const fs = require("fs");
const path = require("path");

const src = path.join(__dirname, "a.txt");
const dest = path.join(__dirname, "b.txt");

// 默认覆盖同名目标
fs.copyFile(src, dest, (err) => {
  if (err) throw err;
  console.log("已复制");
});

// 仅当 b.txt 不存在才复制，已存在则报 EEXIST
fs.copyFile(src, dest, fs.constants.COPYFILE_EXCL, (err) => {
  if (err) { console.log(err.code); return; }
  console.log("安全复制完成");
});
```

> copyFile 默认覆盖与 writeFile 一致；防误覆盖用 COPYFILE_EXCL（等价于 wx 写标志）。它只在"开始复制"那一刻判存在，并非强锁，适合防自己脚本重复跑覆盖。

**速记**：copyFile **默认覆盖，COPYFILE_EXCL 防误覆盖**。



#### 复制目录需自行递归

**目录复制**：fs.copyFile **只复制单个文件、不会自动处理目录**；要复制整棵目录树，必须配合 readdir 递归遍历，对遇到的每个文件调用 copyFile、对每个子目录先 mkdir 再继续。

- copyFile 的 src 与 dest 都必须是文件，传入目录会报 EISDIR。
- 惯用封装命名 **copyDirectory**，内部结合遍历逻辑与目标目录的 ensureDirectory。
- 复制时保持相对结构：把"源根到文件"的相对路径，拼到"目标根"之下得到对应落点。
- 软链接、权限位、时间戳等是否保留需另行处理，copyFile 只保证内容一致。

```js
const fs = require("fs");
const path = require("path");

function copyDirectory(srcRoot, destRoot, done) {
  fs.mkdir(destRoot, { recursive: true }, (err) => {
    if (err) return done(err);
    fs.readdir(srcRoot, { withFileTypes: true }, (e, ds) => {
      if (e) return done(e);
      let pending = ds.length;
      if (!pending) return done(null);
      ds.forEach((d) => {
        const s = path.join(srcRoot, d.name);
        const t = path.join(destRoot, d.name);
        if (d.isDirectory()) copyDirectory(s, t, next);
        else fs.copyFile(s, t, next);
      });
      function next(x) { if (x) return done(x); if (!--pending) done(null); }
    });
  });
}
```

> 目录复制本质是"遍历 + 逐文件 copyFile + 按需建目录"的组合，没有单一 API 能一步到位。上述回调写法用计数器等待并发子任务，也可改为 async/await 版本（见本篇末尾）。

**速记**：目录复制 **遍历配 copyFile，无单 API**。



#### fs.chmod 与权限的 Windows 差异

**fs.chmod**：是修改**文件或目录权限位**的方法，按 Unix 风格的三段（属主、属组、其他）设置读、写、执行，但对跨平台脚本而言在 Windows 上语义有限。

- 完整签名为 fs.chmod(path, mode, callback)，mode 为数字权限（如 0o755、0o644）或字符串。
- 常见约定：可执行脚本 0o755，普通数据 0o644；对应同步版 chmodSync。
- 八进制字面量推荐 0o755（ES2015 起），旧式 0755 会触发弃用警告；权限不足时 err.code 为 EPERM。
- **Windows 差异**：Windows 以 ACL 管理权限，chmod 主要仅能粗略影响"只读"等属性，无法做到三位八进制的精细控制，符号链接创建也常需提升权限。

```js
const fs = require("fs");
const path = require("path");

fs.chmod(path.join(__dirname, "run.sh"), 0o755, (err) => {
  if (err) throw err;
  console.log("权限已设为 755");
});
```

> [!NOTE]
> **提醒内容**：凡涉及 chmod、符号链接、权限位判断的脚本，务必在 Windows 与 POSIX 双平台验证。Node 虽屏蔽了大部分差异，但"权限"这一层天然依赖操作系统，跨平台代码里要对该类 API 做容错与平台判断。

**速记**：chmod **数字权限位，Windows 靠 ACL 语义弱**。



#### fs.utimes 与 fs.realpath

**时间戳与真实路径**：**fs.utimes 修改文件时间元数据**，**fs.realpath 解析符号链接到真实落点**，二者分别处理"时间对齐"与"链接展开"两类目录树相关需求。

- **fs.utimes(path, atime, mtime, callback)**：修改访问时间（atime）与修改时间（mtime），可传 Date 或毫秒数，不动文件内容；常用作备份/复制后还原原时间。
- **fs.realpath(path, options, callback)**：把可能含符号链接的路径解析为真实绝对路径，遇到链接一路跟随到底，返回链接终点而非链接本身。
- utimes 对应同步版 utimesSync；realpath 对应 realpathSync，可配合 stat 判断"链接指向的东西"。
- 仅 utimes 能改 atime/mtime，无法改 ctime（状态变更时间由系统记录）。

```js
const fs = require("fs");
const path = require("path");

fs.utimes(path.join(__dirname, "data.txt"), Date.now(), Date.now(), (e) => {
  if (e) throw e;
});

fs.realpath(path.join(__dirname, "latest"), (e, resolved) => {
  if (e) throw e;
  console.log("真实路径：", resolved); // 链接最终指向处
});
```

> [!IMPORTANT]
> **重要内容**：realpath 会**跟随并展开符号链接**，返回的是链接终点而非链接本身。在遍历目录、校验路径落点时若混入链接，用 realpath 可暴露真实位置，避免"逻辑以为在 A、实际在 B"的错位；但也要警惕它把路径带出预期目录边界。

**速记**：utimes **改时间不动内容**，realpath **跟随链接到真实落点**。



### 文件监听

#### fs.watch 与 fs.watchFile 的机制差异

**监听机制**：fs 提供 **fs.watch（基于操作系统事件）与 fs.watchFile（基于定时轮询）** 两种监听，前者快但跨平台不一致、后者稳但费资源，本质是"推"与"拉"的区别。

- **fs.watch(path, options, listener)**：由内核在变化发生时主动通知，响应快、开销小；底层依赖 inotify/kqueue/ReadDirectoryChangesW。
- **fs.watchFile(path, options, listener)**：按 interval（默认约 5007 毫秒）反复读 mtime 与大小判断变化，跨平台一致但持续占用 CPU。
- watch 返回 FSWatcher 对象（含 close 与 error），watchFile 用 fs.unwatchFile 停止轮询。
- 选型上优先 watch，遇到拿不到 filename 或平台不一致时退回 watchFile。

```js
const fs = require("fs");
const path = require("path");

const watcher = fs.watch(path.join(__dirname, "watch-me.txt"), (type, name) => {
  console.log("事件：", type, name);
});
setTimeout(() => watcher.close(), 5000); // 停止监听

fs.watchFile(path.join(__dirname, "poll-me.txt"), { interval: 1000 }, (curr, prev) => {
  if (curr.mtimeMs !== prev.mtimeMs) console.log("轮询发现修改");
});
setTimeout(() => fs.unwatchFile(path.join(__dirname, "poll-me.txt")), 5000);
```

> watch 与 watchFile 的本质区别是"推"与"拉"：前者系统推事件（快、平台不一），后者 Node 主动拉（稳、费资源）。生产关键逻辑需对 watch 做平台兜底与容错。

**速记**：watch **系统事件驱动快**，watchFile **轮询拉取稳**。



#### 事件类型 rename/change 与监听常见坑

**事件与陷阱**：fs.watch 的 listener 收到 **eventType（rename 或 change）与 filename**，但实战最易踩的是**编辑器保存触发多次、递归监听非全平台支持、filename 可能为空**三类坑。

- **change**：通常表示文件内容被修改；**rename**：通常表示被删除、移动或用新文件同名替换。
- 跨平台下 eventType 边界模糊，同一操作可能报不同类型，稳健做法是"无论哪种都重新读取最新状态并校验"。
- **多次触发**：很多编辑器保存是"先删后写"或"写临时文件再 rename"，一次保存连发多条事件，需防抖合并。
- **递归监听**：options 的 recursive 仅在 macOS 与 Windows 稳定支持，Linux 常被忽略，监听子目录需自行逐层 watch。
- **filename 为空**：部分平台不提供 filename，监听目录时需对空值做兜底。

```js
const fs = require("fs");
const path = require("path");

let timer = null;
fs.watch(path.join(__dirname, "config.json"), () => {
  clearTimeout(timer); // 防抖：合并短时间内的多次事件
  timer = setTimeout(() => console.log("配置已变更，重新加载"), 200);
});
```

> [!WARNING]
> **警告内容**：在 Linux 上依赖 options.recursive 做递归监听往往**不会生效**（事件只覆盖直接监听的那一层），若需监听整棵目录树，应自行对每层子目录调用 fs.watch。忽视这一点会导致"子目录里的改动无声无息未被捕获"。

**速记**：坑三连 **多次触发、递归不全、filename 空**。



### 大文件的随机读写

#### fs.open 获取文件描述符 fd

**fs.open**：是**打开文件并取得文件描述符 fd** 的底层方法，后续可基于 fd 做带位置偏移的多次读写，适合"在任意位置反复操作"而非一次性读入的场景。

- 完整签名为 fs.open(path, flags, mode, callback)，回调第二参数是 fd（非负整数句柄）；flags 用法与第 11 篇一致（r 只读、r+ 读写、w 截断写）。
- 拿到 fd 后，读写都由 fs.read/fs.write 凭 fd 定位，不再每次传路径，省去反复打开的代价。
- 使用完毕必须 fs.close(fd) 释放句柄，否则会造成文件描述符泄漏、最终触发 EMFILE。
- fd 是有限资源，最好用 try/finally 或 Promise 的 finally 保证释放。

```js
const fs = require("fs");
const path = require("path");

fs.open(path.join(__dirname, "big.bin"), "r", (err, fd) => {
  if (err) throw err;
  console.log("已打开，fd =", fd);
  fs.close(fd, (closeErr) => { if (closeErr) throw closeErr; });
});
```

> 凡 open 必配 close。长期不关闭会渐尽 fd 上限，表现为 EMFILE 错误。日常读写仍优先 readFile/writeFile，它们内部已帮你 open 与 close。

**速记**：open **拿 fd，用毕必 close**。



#### fs.read 与 fs.write 基于偏移

**随机读写**：**fs.read 与 fs.write 基于 fd 与位置偏移（position）**，可在文件任意字节位置读或写指定长度数据，实现"分块、随机"访问，与 readFile 一次性读入相对。

- 完整签名 fs.read(fd, buffer, offset, length, position, callback)，把从 position 起的 length 字节读入 buffer 的 offset 处。
- 完整签名 fs.write(fd, buffer, offset, length, position, callback)，把 buffer 片段写入 fd 的 position 处。
- position 传 null 表示"从当前文件游标"，传具体数字则定位到绝对偏移。
- 这适合大文件分块、断点续传、固定格式二进制解析——内存占用恒等于 buffer 大小。

```js
const fs = require("fs");
const path = require("path");

fs.open(path.join(__dirname, "big.bin"), "r", (err, fd) => {
  if (err) throw err;
  const buffer = Buffer.alloc(16);
  fs.read(fd, buffer, 0, 16, 100, (rErr, bytesRead) => { // 从第 100 字节读 16 字节
    if (rErr) throw rErr;
    console.log("本次读到字节数：", bytesRead);
    fs.close(fd, (cErr) => { if (cErr) throw cErr; });
  });
});
```

> position 是"随机"的关键：把它当作文件内绝对游标，就能跳过无关区域只读需要的块，内存与文件整体大小无关——这正是大文件处理的优势。

**速记**：read/write **凭 fd 与 position 任意偏移**。



#### 与 readFile 一次性读入的区别

**二者取舍**：**readFile 一次性把整文件读入内存、简单但吃内存**；**open 配 read 按偏移分块、内存恒定但代码更繁**，选哪类取决于文件大小与访问模式。

- **readFile**：内部自动 open、读全、close，回调直接给完整 Buffer 或字符串，适合小到中等文件。
- **分块读写**：需自己管理 fd、buffer、position 与 close，适合大文件或"只需其中一段"的场景。
- 内存上 readFile 峰值约等于文件体积；分块读仅占单个 buffer，处理 GB 级文件也不爆内存。
- 第 11 篇已说明 readFile 默认返回 Buffer；本节补的是"当它不够用时"的底层出路。

```js
const fs = require("fs");
const path = require("path");

// 分块遍历读取（替代一次性 readFile 处理大文件）
function readInChunks(fd, chunkSize, onChunk, done) {
  const buffer = Buffer.alloc(chunkSize);
  let position = 0;
  (function step() {
    fs.read(fd, buffer, 0, chunkSize, position, (err, n) => {
      if (err) return done(err);
      if (n === 0) return done(null);
      onChunk(buffer.subarray(0, n), position);
      position += n;
      step();
    });
  })();
}
```

> 大文件分块读取是流（Stream，第 13 篇）出现前的"手动版"；若访问模式是顺序消费，优先用流而非手写 fd 循环。只有当需要"随机跳读特定偏移"时，open/read 的精确 position 控制才不可替代。

**速记**：小文件 **readFile 省心**，大文件 **fd 分块稳**。



### Promise 与 async/await 实践

#### fs/promises 重写与 util.promisify

**Promise 风格**：fs 的回调方法在 **fs/promises（或独立 require 的 fs/promises）** 下都有同名 Promise 版本，可配 async/await 把读目录、建目录、删目录、复制写成线性代码；旧接口还可用 **util.promisify** 转换。

- 引入写法 const fsp = require("fs/promises")，之后 fsp.readdir、fsp.mkdir 等返回 Promise，签名去掉 callback。
- await 直接拿"原回调第二参"结果，错误用 try/catch 捕获，与第 11 篇一致。
- readdir、mkdir、rm、copyFile、stat、realpath、open、read、write、close 在 fsp 下均有对应。
- util.promisify 把"最后一个参数是错误优先回调"的函数包成返回 Promise 的版本，适配 fs 回调方法；现代代码更推荐直接用 fsp。

```js
const fsp = require("fs/promises");
const path = require("path");
const { promisify } = require("util");
const readdirAsync = promisify(require("fs").readdir);

async function demo() {
  await fsp.mkdir(path.join(__dirname, "demo"), { recursive: true });
  const dirents = await fsp.readdir(__dirname, { withFileTypes: true });
  console.log(dirents.length);
}

demo().catch((e) => console.error(e));
```

> 把回调版改写 await 版几乎是去掉 callback、用 await 接结果、把 if (err) 换成 try/catch。同一模块不要混用回调与 Promise 两种风格，错误处理路径会分裂。

**速记**：fsp **await 线性化**，promisify **旧回调包成 Promise**。



#### 并发控制与批量操作

**并发控制**：对大量文件做批量 fs 操作（遍历、复制、删除）时，若**一次性全部并发**会瞬间打满文件描述符或拖垮磁盘，需用**限流（固定窗口并发）** 把并发数压在可控范围。

- 朴素写法 Promise.all(tasks) 会同时发起全部任务，任务数巨大时触发 EMFILE 或系统抖动。
- 常用策略：固定窗口并发（同时跑 N 个，完成一个补一个）或按批 for 循环 await 小批。
- fs 操作属 IO 密集，适度并发提速，但无限并发反而因竞争变慢甚至失败。
- 可借助 p-limit 等社区库，但手写固定窗口并不复杂。

```js
const fsp = require("fs/promises");
const path = require("path");

async function runWithLimit(tasks, limit) {
  let index = 0;
  async function worker() {
    while (index < tasks.length) {
      const cur = index++;
      await tasks[cur]();
    }
  }
  await Promise.all(Array.from({ length: limit }, () => worker()));
}

const files = ["a.txt", "b.txt", "c.txt"].map((n) =>
  () => fsp.copyFile(path.join(__dirname, n), path.join(__dirname, "out", n))
);
runWithLimit(files, 3).then(() => console.log("分批复制完成"));
```

> [!TIP]
> **建议内容**：批量 fs 操作务必限流，避免 Promise.all 一次性铺开成百上千个打开/删除。固定窗口并发（limit 取 5 到 20 之间视磁盘而定）通常是吞吐与稳定的最佳平衡点；千万级文件还需结合分页与进度落盘。

**速记**：批量 **限流并发，勿全铺开**。
