## RESTful API 设计规范

### REST 与 RESTful 的基本概念

#### REST 是一种架构风格而非协议

**REST（Representational State Transfer）**：是一种**架构风格**而非通信协议，它约定系统应以何种方式组织交互，但不规定具体的报文格式或传输手段。

- 它描述的是**客户端与服务器之间的交互约束**，而不是像 HTTP 那样定义报文结构的协议。
- 它为分布式超媒体系统提供了一组**设计原则**，是否采纳、如何落地由实现方决定。
- 它最早由 **Roy Fielding** 在 2000 年的博士论文中系统提出，是 HTTP 协议设计思想的理论源头之一。

> 协议与风格的区别在于：协议规定"必须怎么做"才有互操作，风格只给出"建议怎么做"的设计取向。把 REST 误当成协议，会让人误以为只要用了 HTTP 就自动成为 RESTful。

**速记**：REST 是**设计风格**，非**协议**，源自 **Fielding 论文**。



#### 资源、表现层与状态转移的三要素

**REST 的核心三要素**：是**资源（Resource）、表现层（Representation）、状态转移（State Transfer）**，三者共同构成"表述性状态转移"的字面含义。

- **资源**：系统中可被标识的任何事物，如一名用户、一篇文章、一次订单，统一用 URI 定位。
- **表现层**：资源在某时刻的**具体形态**，同一资源可以有 JSON、XML、HTML 等多种表现形式，由请求协商决定。
- **状态转移**：客户端通过**带动作的请求**（主要是 HTTP 方法）改变资源的表现，从而推动服务端状态演进。

> 三个词里最易被忽略的是"表现层"：REST 操作的是资源的"表述"而非资源本身，服务端返回的是某一时刻的快照，而非数据库行原貌。

**速记**：资源**定位**、表现**呈现**、方法**转移状态**。



#### 符合约束的 API 才称为 RESTful

**RESTful**：是"符合 REST 架构约束的接口"的简称，只有满足约束集的 API 才配称 RESTful，而非只要基于 HTTP 就成立。

- 约束包括：客户端服务器分离、无状态、可缓存、统一接口、分层系统、按需代码（可选）。
- 实践中常把"**统一接口**"与"**无状态**"两条视为 RESTful API 的底线。
- 社区把"像 REST 但只做到一部分"的接口称作 **REST 风格** 或 **HTTP API**，以区别于严格 RESTful。

> [!NOTE]
> **提醒内容**：术语并不绝对。严格 RESTful 还要求 HATEOAS（超媒体驱动），但绝大多数业务 API 只做到资源化与无状态，业界仍笼统称其为 RESTful。称呼上不必过度较真，重点看约束是否落实。

**速记**：满足**约束**才叫 RESTful，否则只是 HTTP API。



### 资源导向的设计思想

#### URL 只放名词表示资源

**资源导向**：要求 URL 路径中只出现**名词**来指代资源集合或个体，把"做什么"交给 HTTP 方法，路径本身保持名词中性。

- 集合用复数名词，如 /users 表示用户集合，/articles 表示文章集合。
- 个体用集合加标识符，如 /users/123 表示编号 123 的那一名用户。
- 路径表达的是"**哪一个资源**"，语义稳定、可缓存、可书签化。

> 名词化路径的好处是面向"事物"而非"动作"，当业务增加新操作时无需新建 URL，只需复用已有资源路径配合不同方法。

**速记**：URL 放**名词**，路径指**资源**。



#### 用 HTTP 方法表达操作语义

**方法即操作**：用 HTTP 方法（GET、POST、PUT、PATCH、DELETE）承载"增删改查"等动作语义，使同一资源路径能映射多种操作而无需额外路径。

- GET /users 是"查询用户"，POST /users 是"创建用户"，二者路径相同、动作不同。
- 方法与路径分离后，接口数量大幅减少，**语义却更清晰**，便于权限控制与网关路由。
- 方法名是 HTTP 标准词汇，客户端、代理、缓存中间件都能据此理解意图。

> 方法语义是"约定俗成"而非强制：代理与框架默认按方法处理，若你用 GET 做删除，中间层缓存就会误判。遵循标准方法是让生态工具生效的前提。

**速记**：路径定**资源**，方法定**动作**。



#### 不在 URL 中写动词

**反名词化**：应避免在路径里塞入动词或动作短语，如 /getUsers、/createOrder、/deleteArticle，这类写法破坏资源抽象。

- 动词本应由 HTTP 方法承担，写进路径造成**方法与方法语义的重复与错配**。
- 带动词的路径难以形成统一层级，集合与个体关系被打散，不利路由规划。
- 例如"激活用户"不写 /activateUser，而写 POST /users/123/activation 或 PATCH /users/123 携带激活字段。

> [!TIP]
> **建议内容**：遇到"非标准动作"时，优先用子资源或字段表达，而非动词路径。如"给用户发消息"写作 POST /users/123/messages，把动作转译为对子资源的创建，既符合资源化又保留语义。

**速记**：动词**交给方法**，路径**保持名词**。



### HTTP 方法、幂等性与安全性

#### HTTP 方法与 CRUD 的对应

**方法映射**：HTTP 方法与资源的增删改查存在约定俗成的对应，社区惯例以此作为接口设计基线。

- **GET**：查询、读取资源，对应 **Retrieve**。
- **POST**：在集合下**创建**新资源，对应 **Create**。
- **PUT**：用完整表述**替换**指定资源，对应 **Update（整体）**。
- **PATCH**：用局部表述**修改**资源部分字段，对应 **Update（局部）**。
- **DELETE**：**删除**指定资源，对应 **Delete**。

> 这套对应是"惯例"而非 HTTP 标准强制；RFC 7231 只定义各方法的语义，未把 POST 绑定到创建。但偏离惯例会提高协作成本，除非有充分理由。

**速记**：增 POST、查 GET、整体 PUT、局部 PATCH、删 DELETE。



#### PUT 与 PATCH 的区别

**整体与局部**：PUT 以**客户端提供的完整表述替换**资源，PATCH 以**差量表述局部修改**资源，二者语义不同、对缺失字段处理相反。

- PUT 时若客户端漏传某字段，服务端应理解为"该字段置为空或被移除"，因为 PUT 是全覆盖。
- PATCH 只携带要改的字段，未提及字段**保持原值不变**。
- PUT 要求客户端先 GET 全量再回传；PATCH 只需知道要改的少量字段，带宽更省。

> [!CAUTION]
> **注意内容**：用 PUT 做"局部更新"是常见误用。若客户端只传了 nickname 而服务端把它当作完整表述，会导致其余字段被清空。需要局部修改时务必使用 PATCH。

**速记**：PUT **全覆盖**，PATCH **改局部**。



#### 安全方法不修改资源

**安全方法**：指**不修改服务端资源状态**的方法，RFC 7231 明确 GET、HEAD、OPTIONS 属安全方法，语义上只读。

- 安全是"语义保证"，不表示实现上绝不触发副作用（如记日志），而是**不Intent修改资源**。
- 客户端、爬虫、预取器可放心对安全方法发起请求，不用担心改坏数据。
- 若用 GET 做删除或更新，就违背了安全语义，缓存与中间件会据此误判。

> 安全是相对的"约定语义"，不是技术锁。HTTP 本身无法阻止你在 GET 处理器里写数据库；但若这么做，就破坏了整个生态对 GET 的信任假设。

**速记**：安全方法**只读不改**，GET/HEAD/OPTIONS。



#### 幂等方法多次调用结果一致

**幂等性**：指**同一请求执行一次与执行多次，对服务端造成的资源状态影响一致**，客户端可安全重试。

- **GET、PUT、DELETE** 属于幂等方法：重复 GET 不改变状态；重复 PUT 以相同表述覆盖，结果等同一次；重复 DELETE 第二次通常返回 404 但资源状态仍一致。
- **POST** 通常非幂等：每次都会新建资源（详见后续考点）。
- **PATCH** 是否幂等取决于语义：用"设为某值"的改法是幂等的，用"自增 1"的改法非幂等。

> [!IMPORTANT]
> **重要内容**：幂等是接口可重试性的基础。网络超时后客户端是否敢重发请求，完全取决于方法是否幂等。设计写接口时应尽量让 PUT、DELETE 幂等，把非幂等集中于 POST。

**速记**：幂等**可重试**，GET/PUT/DELETE 是；POST 不是。



#### POST 非幂等的含义

**非幂等**：POST 每次调用通常都会**产生新的资源或新的副作用**，重复提交会创建多份而非覆盖一份。

- 典型场景：连续 POST /users 三次会生成三名用户，而非只保留最后一个。
- 因此 POST 不适合被客户端自动重试，重试前需先判断上一次是否真的失败。
- 用幂等键（Idempotency-Key 请求头）是缓解 POST 重复提交的常见工程手段。

> 非幂等并非缺陷，而是 POST 创建语义的自然结果。需要"只创建一次"时，应结合唯一约束或幂等键，而非改用幂等方法伪装。

**速记**：POST 重复**建多份**，重试需谨慎。



#### GET、HEAD 与 OPTIONS 的用途

**辅助方法**：GET 取资源表述，HEAD 取与 GET 相同的响应头但无响应体，OPTIONS 用于探测通信选项，三者各有专司。

- **HEAD**：常用于检查资源是否存在、查看 Content-Length 与缓存头，省去下载正文。
- **OPTIONS**：用于 CORS 预检，或查询某资源支持哪些 HTTP 方法（返回 Allow 头）。
- 三者均安全，可做探测与元信息查询，不影响资源本体。

> HEAD 的响应头必须与对应 GET 一致（除正文外），否则缓存与检查逻辑会失真。OPTIONS 在跨域场景下常被浏览器自动发出，接口需正确返回 Allow 与 CORS 头。

**速记**：HEAD **看头不看体**，OPTIONS **探支持方法**。



### URL 命名与查询参数规范

#### 用复数名词与层级表达从属

**名词化路径**：资源路径统一使用**复数名词**表示集合，用斜杠表达资源间的**从属关系**，使层级在 URL 上一目了然。

- 集合用复数：/users、/articles、/orders，不用 /user、/article。
- 从属表达：/users/123/articles 表示"用户 123 名下的文章集合"。
- 个体在集合下加标识符：/users/123、/articles/456。

> 复数优于单数的原因：集合与个体的 URL 形态统一，从集合到个体只是"加 ID"，路由规则更易编写，也符合"资源即集合元素"的直觉。

**速记**：集合**复数**，从属**斜杠嵌套**。



#### 避免过深嵌套

**扁平优先**：资源层级**一般不宜超过两层**，过深嵌套会让 URL 冗长、脆弱且难以维护。

- 推荐 /users/123/articles/456 这种两层结构。
- 若关系再深，应考虑用查询参数或独立资源表达，如 /comments?articleId=456 而非 /users/123/articles/456/comments/789。
- 深层嵌套中若上级资源被删除，下级 URL 整体失效，耦合过高。

> [!TIP]
> **建议内容**：当 URL 出现三层以上嵌套，先问"被嵌套资源是否真的从属于路径上的每一级"。多数情况下它只从属于最近一级，拆成顶层集合加查询过滤更稳妥，如 /articles?authorId=123。

**速记**：嵌套**不超两层**，过深就**查询化**。



#### 连字符、小写与统一约定

**书写约定**：路径中的多词资源名应使用**连字符（kebab-case）而非下划线**，全小写，保持全局统一。

- 多词用连字符：/user-profiles、/order-items，不用 /user_profiles。
- 全小写：RFC 3986 规定 URL 路径大小写敏感，统一小写可避免 /Users 与 /users 歧义。
- 不在路径中使用大写驼峰或下划线，降低跨平台与跨语言解析差异。

> 下划线在部分排版与终端中不易辨识，连字符在 URL 中更通用。大小写敏感是客观事实，靠"约定全小写"消除人为出错空间，而非靠运行时兼容。

**速记**：小写、连字符、弃下划线。



#### 过滤、分页与排序查询参数

**查询参数**：对集合的检索条件应放在 **URL 查询参数** 中，而非塞进路径，常见用途为过滤、分页、排序与字段筛选。

- **过滤**：用字段等于值表达，如 status=active、authorId=123，多值可重复键或逗号分隔。
- **分页**：用 page 与 pageSize 或 limit 与 offset，如 page=2&pageSize=20。
- **排序**：用 sort 指定字段，约定负号表示降序，如 sort=-createdAt 表示按创建时间倒序。
- **字段筛选**：用 fields 限定返回字段，如 fields=id,name，减小响应体。

> 查询参数属于"检索视图"，不影响资源本体，故放在问号之后。路径定位"哪一个资源"，查询表达"如何呈现这一批"，二者职责不同，不可混用。

**速记**：过滤 status、分页 page、排序 -字段、筛选 fields。



#### 分页的页码式与游标式

**两种分页**：集合分页主要有**页码式（offset 分页）**与**游标式（游标分页）**两种风格，取舍取决于数据集特征。

- **页码式**：以 page 与 pageSize 计算偏移，SQL 中用 LIMIT 与 OFFSET；优点是跳页方便，缺点是数据变动时易重复或漏读。
- **游标式**：以上一次结果的最后一条游标（如时间戳或 ID）作为下一页起点，如 ?after=20240101&limit=20；优点是对新增数据稳定、性能更优。
- 游标式通常**不支持任意跳页**，更适合信息流、日志等按序追加的场景。

> [!NOTE]
> **提醒内容**：页码式在大结果集且高写入场景下，因 OFFSET 需扫描跳过前面所有行，性能随页码加深而劣化；游标式用索引定位，深度分页几乎零损耗，但实现稍复杂且不利于"第 N 页"的直接跳转。

**速记**：页码式**好跳页**，游标式**稳深翻**。



### 状态码的正确使用

#### 2xx 成功类

**2xx 语义**：2xx 表示请求已被服务端**成功接收、理解并处理**，不同子码区分成功的具体形态。

- **200 OK**：通用成功，常用于查询与更新返回。
- **201 Created**：资源创建成功，应在响应头 **Location** 给出新资源的 URI，响应体可带新建资源。
- **204 No Content**：成功但**无响应体**，常用于删除成功或只更新不返回内容的场景。

> 201 与 Location 配套是 RESTful 的惯用法：客户端创建后可直接从 Location 取到新资源地址。204 的"无内容"是刻意设计，不要为了统一而给它套一个空 data。

**速记**：200 通用、201 带 Location、204 无体。



#### 3xx 重定向类

**3xx 语义**：3xx 表示客户端需**进一步操作**才能完成请求，多用于资源迁移与缓存协商。

- **301 Moved Permanently**：资源永久迁移，客户端应更新书签，搜索引擎转移权重。
- **302 Found**：临时重定向，后续请求仍用原地址。
- **304 Not Modified**：协商缓存命中，客户端可直接用本地缓存，响应无正文。

> 301 与 302 的"永久/临时"差异会影响客户端与代理的缓存与书签行为，用错会导致长期缓存错误地址。304 是性能优化关键，配合 ETag 或 Last-Modified 使用。

**速记**：301 永久、302 临时、304 缓存命中。



#### 4xx 客户端错误类

**4xx 语义**：4xx 表示**请求本身有问题**，属客户端责任，常见子码构成错误处理的骨架。

- **400 Bad Request**：请求报文格式或参数非法，通用错误。
- **401 Unauthorized**：**未认证**，缺少或凭证无效，需先登录。
- **403 Forbidden**：**已认证但无权限**，身份足够却被拒绝。
- **404 Not Found**：资源不存在，或对外隐藏存在性时统一返回。
- **405 Method Not Allowed**：方法不被该资源支持，应返回 Allow 头告知可用方法。
- **409 Conflict**：请求与资源当前状态冲突，如重复创建唯一键。
- **422 Unprocessable Entity**：报文格式正确但**语义校验不通过**，如字段值非法。
- **429 Too Many Requests**：超出速率限制，应带 Retry-After 提示重试间隔。

> 401 与 403 是最易被混用的两个：401 是"你是谁还没证明"，403 是"我知道你是谁但不许动"。前置返回哪一个，直接决定前端跳转登录还是展示无权限。

**速记**：401 未认证、403 无权限、404 不存在、422 校验败。



#### 5xx 服务端错误类

**5xx 语义**：5xx 表示**服务端处理请求时发生内部错误**，责任在服务端，客户端无法直接修正。

- **500 Internal Server Error**：未预期的通用服务端错误，兜底使用。
- **502 Bad Gateway**：网关或代理收到上游无效响应，常见于反向代理后服务崩溃。
- **503 Service Unavailable**：服务暂时不可用，常因过载或维护，可带 Retry-After。

> 5xx 一旦出现，说明服务端自身有 bug 或依赖故障。它与 4xx 的分界在于"错误是否由客户端请求内容引起"，区分清楚才能正确告警与定位。

**速记**：5xx **服务端错**，500 兜底、502 上游、503 不可用。



#### 不要一律返回 200

**状态码即信息**：HTTP 状态码本身就是响应语义的一部分，**不要所有情况都返回 200 再把错误塞进响应体**，这会令缓存、网关与监控失效。

- 一律 200 会让负载均衡器、重试中间件无法区分成功与失败，错误被计入成功指标。
- 客户端需逐层解析响应体才能判断成败，丧失 HTTP 语义带来的便利。
- 正确做法是**状态码反映大类（2/4/5），响应体给出细节**，二者分工协作。

> [!WARNING]
> **警告内容**：恒返 200 是严重反模式。它使 CDN 与代理误把错误响应缓存下来、使监控误报成功率、使客户端重试逻辑失灵。状态码必须真实反映处理结果。

**速记**：状态码**讲真话**，莫恒 200。



### 错误响应与统一响应封装

#### 错误响应的统一结构

**统一错误体**：错误响应应有一致的字段结构，让客户端以同一种方式解析失败，常见结构包含业务码、可读信息与细节。

- **code**：业务错误码，如 USER_NOT_FOUND，用于程序分支，比纯状态码更细。
- **message**：给开发者或用户可读的提示，如"用户不存在"。
- **details**：可选的字段级错误明细，如校验失败的具体字段与原因。

> 统一结构的核心是"客户端永远知道去哪取错误信息"。若有的接口返回 {error: ...}，有的返回 {message: ...}，前端就要写多套解析逻辑，脆弱且易漏。

**速记**：错误体 **code + message + details** 三件套。



#### 错误码与 HTTP 状态码的分工

**两种错误标识**：**HTTP 状态码**表达"大类结果"（成功/客户端错/服务端错），**业务错误码**表达"具体哪一种错误"，二者互补而非替代。

- HTTP 状态码供**中间件、网关、监控**消费，决定重试、缓存、告警策略。
- 业务错误码供**应用层逻辑**消费，决定前端具体提示与分支处理。
- 例如 422 配 code=INVALID_EMAIL，既标识"校验失败大类"，又点明"哪类校验"。

> 不要把业务码硬编码进状态码，如为每种错误发明一个 4xx 子码；HTTP 子码有限且语义固定，细分应交由业务 code 字段承载。

**速记**：状态码**管大类**，业务码**管细分**。



#### 统一响应封装的取舍

**封装选择**：对响应是否包裹一层统一结构（如 {code, data, message}）是**设计取舍而非强制**，两种做法各有适用。

- **包裹式**：所有成功与失败都包成同一外壳，前端解析统一，适合内部前后端分离项目。
- **直接式**：成功时直接返回资源本体，仅错误时给错误体，更贴近 HTTP 语义与 HATEOAS，利于第三方与缓存。
- 取舍要点：内部系统重**一致性**可选包裹；对外开放 API 重**标准与缓存**宜直接式。

> [!NOTE]
> **提醒内容**：包裹式里若再把 HTTP 状态码恒置 200、用内部 code 表示成败，就与"状态码讲真话"原则冲突。若采用包裹，仍应让 HTTP 状态码真实反映结果，内部 code 仅作细分。

**速记**：包裹**重一致**，直接**重标准**，状态码**都要真**。



### 版本管理与文档可发现性

#### URL 前缀版本

**URL 版本**：把版本号放进路径前缀，是最直观、最易调试的版本管理方式，如 /api/v1/users。

- 优点：版本在 URL 上**肉眼可见**，便于调试、日志追踪与网关按前缀路由。
- 缺点：资源 URI 随版本变化，破坏"同一资源稳定地址"的纯净性。
- 适用于对外 API 与需要清晰隔离的大版本迭代。

> URL 版本因可见性强，是多数公开 API 的首选。但它让"资源地址"绑定了版本，迁移时需保留旧前缀做兼容，旧地址不能轻易下线。

**速记**：URL 版本 **/api/v1**，直观可调试。



#### 请求头版本

**请求头版本**：通过自定义请求头（如 Accept 或 API-Version）携带版本，路径保持纯净，如 Accept: application/vnd.myapi.v2+json。

- 优点：资源 URI **不随版本变化**，更符合 REST 资源地址稳定的理念。
- 缺点：版本**不可见于 URL**，调试、分享、缓存键管理都不直观。
- 适用于对 URI 纯净度要求高、且客户端能稳定控制请求头的场景。

> 请求头版本把"版本"当成表述协商的一部分，与内容协商（JSON/XML）同源。但浏览器直接访问、日志排查时不如 URL 版本方便，需权衡团队习惯。

**速记**：头版本 **URI 纯净**，调试略不便。



#### 版本演进与兼容策略

**兼容策略**：版本演进应遵循**向后兼容优先、破坏性变更才升版本**的原则，避免频繁让客户端被迫升级。

- 新增字段、新增可选参数属于**兼容变更**，可在同版本内平滑发布，旧客户端不受影响。
- 删除字段、改字段语义、改路径结构属于**破坏性变更**，必须升主版本（v1→v2）。
- 旧版本应设**弃用期（deprecation）**，通过响应头或文档告知下线时间，给客户端迁移窗口。

> [!IMPORTANT]
> **重要内容**：版本不是越多越好。每多一个在线版本，服务端就要多维护一套逻辑、多测一套兼容。能用兼容变更解决的，绝不新开版本；新版本上线即规划旧版本退役时间。

**速记**：兼容变更**同版本**，破坏性**升版本**，旧版**设弃用期**。



#### 接口文档的价值

**文档价值**：接口文档是前后端、服务间协作的**契约载体**，降低沟通成本、减少联调返工，也是 API 可发现性的基础。

- 文档应覆盖：路径、方法、参数、请求与响应示例、状态码、错误码、鉴权方式。
- 没有文档的 API 等于不可用的 API，调用方只能靠源码或猜测，错误率陡增。
- 文档应**随代码同步更新**，过期文档比没有文档更具误导性。

> 文档的价值在"契约"而非"说明"：它让调用方在不动服务端源码的前提下正确使用接口。文档一旦滞后于实现，契约即失效，信任崩塌。

**速记**：文档是**协作契约**，须**随码更新**。



#### OpenAPI 规范简介

**OpenAPI**：是一套**描述 RESTful API 的开放标准规范**（原 Swagger 规范），用结构化文档（如 YAML/JSON）声明路径、参数、响应与模型。

- 它使 API 可被**机器读取**，据此自动生成文档页、客户端 SDK、服务端桩代码与测试。
- 生态工具丰富：Swagger UI 出可视化文档，Swagger Codegen 出多语言客户端。
- 规范本身只是描述格式，是否用它生成文档取决于工程管线。

> OpenAPI 把"接口长什么样"从自然语言升级为结构化数据，从而解锁自动化。它不强制运行行为，只约定描述方式，团队可渐进采用。

**速记**：OpenAPI **机器可读**，可**自动生成文档与 SDK**。



#### 用注释生成文档

**注释生成**：通过**代码内注解**描述接口，再用工具抽取生成 OpenAPI 文档，使文档与实现同源、不易脱节。

- 在路由处理函数上方用框架插件（如 swagger-jsdoc）写字段注解，构建时扫描生成 openapi.json。
- 好处是**文档紧贴代码**，改接口时顺手改注解，天然同步。
- 风险是注解可能被忽略而失效，需把"文档生成"纳入构建或 CI 校验。

> [!TIP]
> **建议内容**：把文档生成接入 CI，若注解缺失或字段与代码不符则构建失败，可强制文档不落后。纯手工维护的文档几乎必然过期，自动化是性价比最高的保障。

**速记**：注解**贴代码**，CI **保同步**。



### Express 实现用户资源接口

#### 路由与中间件骨架

**骨架设计**：以 Express 搭建用户资源接口，用 Router 聚合路由、用中间件统一解析与错误处理，示例聚焦规范落地而非完整工程。

- 用 express.json 中间件解析 JSON 请求体，使 req.body 可用。
- 用 router 把 /users 相关路由集中，挂载到 /api/v1/users（URL 前缀版本）。
- 用一个内存数组代替数据库，便于示例直接运行，结构对齐真实分层。

```js
const express = require("express");
const app = express();
app.use(express.json());

let users = [
  { id: 1, name: "Ada", email: "ada@example.com", status: "active" },
];
let nextId = 2;

const router = express.Router();
app.use("/api/v1/users", router);

app.use((err, req, res, next) => {
  // 统一错误处理中间件，定义见后续考点
  res.status(err.status || 500).json({
    code: err.code || "INTERNAL_ERROR",
    message: err.message || "服务器内部错误",
  });
});

app.listen(3000, () => console.log("监听 3000"));
```

> 示例用内存数组仅为可运行演示；真实项目应把数据访问抽成独立模块，路由只负责协议转换，控制器不直接触碰存储细节。

**速记**：Router **聚路由**，json 中间件 **解请求体**。



#### GET 列表与详情

**查询实现**：GET 列表返回集合、GET 详情返回个体，二者均用 200，详情不存在时返回 404，体现状态码真实语义。

- 列表支持过滤与分页查询参数（status、page、pageSize），演示资源导向与查询分离。
- 详情路径 /users/:id，未找到时返回 404 而非空 200，避免恒 200 反模式。
- 用 find 与 filter 完成定位与过滤，逻辑集中在控制器。

```js
router.get("/", (req, res) => {
  const { status, page = 1, pageSize = 10 } = req.query;
  let list = users;
  if (status) list = list.filter((u) => u.status === status);
  const start = (page - 1) * pageSize;
  res.json(list.slice(start, start + Number(pageSize)));
});

router.get("/:id", (req, res) => {
  const user = users.find((u) => u.id === Number(req.params.id));
  if (!user) return res.status(404).json({
    code: "USER_NOT_FOUND",
    message: "用户不存在",
  });
  res.json(user);
});
```

> 列表与详情的 200/404 选择，直接示范"状态码讲真话"：存在即 200 带数据，不存在即 404 带错误体，前端无需解析 data 是否为空来判断成败。

**速记**：列表**支持分页过滤**，详情**缺失返 404**。



#### POST 创建

**创建实现**：POST 创建资源，校验通过后生成标识，返回 201 并在 Location 头给出新资源地址，契合 RESTful 约定。

- 用 201 Created 而非 200，明确表达"已创建"。
- 在响应头 Location 写入 /api/v1/users/{id}，便于客户端定位新资源。
- 校验失败时返回 422 并带字段级 details，区分于 400 的格式错误。

```js
function createUser(req, res) {
  const { name, email } = req.body;
  if (!name || !email) {
    return res.status(422).json({
      code: "INVALID_FIELD",
      message: "字段校验失败",
      details: { name: !name ? "必填" : null, email: !email ? "必填" : null },
    });
  }
  const user = { id: nextId++, name, email, status: "active" };
  users.push(user);
  res.set("Location", `/api/v1/users/${user.id}`);
  res.status(201).json(user);
}
router.post("/", createUser);
```

> POST 非幂等：连续调用会创建多个用户。示例未做唯一约束，真实场景应结合邮箱唯一索引与 409 Conflict 防止重复，而非依赖客户端去重。

**速记**：创建 **201 + Location**，校验败 **422**。



#### PATCH 更新与 DELETE 删除

**修改与删除**：PATCH 做局部更新、DELETE 做删除，二者均保持幂等语义，删除成功用 204 无响应体。

- PATCH 只改请求体提供的字段，未提及字段保留原值，对应"局部更新"考点。
- DELETE 成功后返回 204 No Content，不携带响应体，符合无内容约定。
- 二者操作不存在的资源时返回 404，维持"状态码真实"原则。

```js
function updateUser(req, res) {
  const user = users.find((u) => u.id === Number(req.params.id));
  if (!user) return res.status(404).json({ code: "USER_NOT_FOUND", message: "用户不存在" });
  Object.assign(user, req.body); // 只覆盖传入字段
  res.json(user);
}
router.patch("/:id", updateUser);

router.delete("/:id", (req, res) => {
  const idx = users.findIndex((u) => u.id === Number(req.params.id));
  if (idx === -1) return res.status(404).json({ code: "USER_NOT_FOUND", message: "用户不存在" });
  users.splice(idx, 1);
  res.status(204).end();
});
```

> PATCH 用 Object.assign 直接合并请求体，演示"局部覆盖"；真实项目应做字段白名单，避免客户端篡改 id、status 等受保护字段。DELETE 的 204 用 res.status(204).end() 显式无体结束。

**速记**：PATCH **局部改**，DELETE **204 无体**。



#### 统一错误处理中间件

**错误处理**：用 Express 错误处理中间件集中收敛异常，保证所有错误都经统一结构返回，且 HTTP 状态码真实。

- 中间件签名为 (err, req, res, next) 四参数，Express 据此识别为错误处理专用。
- 业务层用 next(error) 抛出带 status 与 code 的错误对象，由中间件统一成形。
- 不在中间件里泄露堆栈与内部路径，只返回给开发者可读的 message。

```js
function notFoundHandler(req, res, next) {
  next({ status: 404, code: "ROUTE_NOT_FOUND", message: "接口不存在" });
}

function errorHandler(err, req, res, next) {
  const status = err.status || 500;
  const payload = {
    code: err.code || "INTERNAL_ERROR",
    message: err.message || "服务器内部错误",
  };
  if (status >= 500) {
    // 生产环境不向客户端暴露堆栈
    console.error(err.stack);
  }
  res.status(status).json(payload);
}

app.use(notFoundHandler);
app.use(errorHandler);
```

> [!CAUTION]
> **注意内容**：错误响应**绝不可**把 err.stack、SQL 语句、内部路径回传给客户端，这些信息会暴露系统结构助长攻击。服务端可记录日志用于排查，对外只给抽象后的 message 与 code。

**速记**：错误**集中收敛**，对外**不泄堆栈**。



### 常见反模式

#### URL 中携带动词

**反模式一**：在路径写动词（/getUsers、/createOrder），违背资源导向，造成路径与方法语义重复。

- 正确改法：GET /users、POST /orders，动作交由 HTTP 方法。
- 危害：路由膨胀、缓存与网关无法按标准方法识别意图。
- 本质是把"操作"错误地编码进了"资源地址"。

> 看到 URL 里出现 get、create、delete 等动词，基本可断定资源导向没做对。先问"这个动作能否表示为对某个资源的创建或子资源创建"。

**速记**：动词**进方法**，莫留**在路径**。



#### 只用 GET 与 POST

**反模式二**：技术栈或历史原因只暴露 GET 与 POST，用 POST 伪装删除、更新，丢失方法语义。

- 正确改法：更新用 PUT/PATCH、删除用 DELETE，让方法与意图一致。
- 危害：中间件、缓存、防火墙按方法优化时全部失效，接口不可被标准工具理解。
- 常见于老表单或某些网关只放行两种方法的环境，应以反向代理补全方法支持。

> 仅用两种方法是"环境受限"的妥协，不是设计规范。在允许全方法的服务中仍如此，便是反模式，会让 RESTful 退化为"POST 万能隧道"。

**速记**：莫让 POST **包揽一切**，方法**各司其职**。



#### 状态码恒定 200

**反模式三**：无论成败一律返回 200，把错误塞进响应体，使 HTTP 语义形同虚设。

- 正确改法：成功用 2xx，客户端错用 4xx，服务端错用 5xx，响应体仅补细节。
- 危害：监控误报、缓存误存错误、重试逻辑失灵（已在前文详述）。
- 常见于"统一封装 + 状态码恒 200"的错误组合。

> 这条反模式危害最大且最隐蔽：系统表面"能跑"，但所有基于 HTTP 语义的工具都收到错误信号。它是验收 API 健康度的第一道红线。

**速记**：状态码**必须真**，恒 200 **最危险**。



#### 错误信息不统一

**反模式四**：错误响应结构随意变化，时而 {error}、时而 {message}，前端解析无从下手。

- 正确改法：固定错误体结构（code、message、details），全站一套。
- 危害：客户端需为不同接口写不同解析分支，易漏判错误。
- 本质是缺乏"错误契约"，把错误当异常个案处理。

> 不统一的错误信息比明确的错误更难排查：开发者看到 message 字段为空或结构突变时，无法判断是成功还是失败。统一结构是接口成熟度的标志。

**速记**：错误体**要统一**，结构**莫漂移**。



#### 把会话状态放在服务端破坏无状态性

**反模式五**：在服务端用内存或会话保存客户端状态（如"当前登录用户""当前翻页位置"），违背 REST 无状态约束。

- 正确改法：每个请求**自带全部上下文**（凭证在 Authorization 头、状态在查询/载荷），服务端不存会话。
- 危害：水平扩展时请求被路由到不同实例会丢失状态，破坏可伸缩性。
- 注意区分：无状态指"请求间不依赖服务端会话"，**鉴权令牌仍可被服务端校验**，只是不在服务端保存客户端会话。

> [!IMPORTANT]
> **重要内容**：无状态不排斥鉴权，而是指"服务端不保留跨请求的客户端会话"。用 JWT 等令牌让每个请求自证身份，正是为维持无状态。把购物车、登录态存进服务端内存，是扩展性杀手。

**速记**：请求**自带状态**，服务端**不存会话**。
