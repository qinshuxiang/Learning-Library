## cluster 集群与进程守护

### 单进程的局限与多核利用需求

#### 一个 Node 进程默认只占用一个 CPU 核

**单进程单核局限**：Node 默认以**单线程**执行 JavaScript 代码，一个进程在同一时刻只能被操作系统调度到**一个 CPU 核**上运行。

- 该进程内部的事件循环在同一时刻只处理一条主线程逻辑，其余核心处于闲置。
- 当业务出现 CPU 密集型计算时，唯一的主线程被占满，其余请求全部排队等待。

> 第 8 篇已说明 Node 是单线程事件驱动模型。单线程解决了竞态问题，却也意味着"算力上限被钉死在一个核上"，这是多核利用需求的根源。

**速记**：单进程单线程，**只吃一个核**。



#### 多核机器上资源被严重浪费

**资源浪费**：在拥有多核 CPU 的服务器上，仅运行单个 Node 进程会使**其余核心长期空闲**，硬件投资无法转化为吞吐。

> 不要误以为"加机器"就能解决单进程瓶颈：单台多核机器内部若不启用多进程，加核等于白加。多核利用必须靠进程或线程级并行。

**速记**：多核不用，**等于没买核**。



#### 单进程崩溃会导致整个服务不可用

**可用性单点**：由于所有请求都依赖同一个进程，该进程一旦**崩溃退出**，对外服务便**整体中断**，没有冗余兜底。

- 未捕获异常、内存溢出、依赖故障都可能让单进程直接退出。
- 进程退出后，端口释放，新连接全部失败，直到有人重启进程。

> 单进程模型把"可用性"与"单个进程健康度"绑死。要消除单点，必须让多个进程同时对外服务，并能在某个进程死亡时自动补位。

**速记**：单进程一死，**全站皆停**。



### cluster 模块原理与端口共享机制

#### cluster 模块用于把单进程扩展为多进程集群

**cluster 模块**：是 Node 内置的**多进程管理模块**，允许在一个主进程下派生多个**工作进程**，共同承担同一服务，从而利用多核。

- 完整语法为 cluster 模块通过 require("cluster") 引入，主进程调用 cluster.fork 方法派生工作进程。
- 它建立在 child_process 之上：每个工作进程本质上是一个独立的 Node 子进程，但由 cluster 统一协调。
- 工作进程与主进程共享同一份入口脚本，靠 cluster.isPrimary 与 cluster.isWorker 判断自己身处哪一侧。

> [!IMPORTANT]
> **重要内容**：cluster 的底层仍是 fork 出多个 Node 进程，并非线程；因此各工作进程拥有独立的内存与事件循环，进程间不共享堆。

**速记**：cluster **多进程协作的指挥官**。



#### 用 isPrimary 与 isWorker 区分主从角色

**主从判断**：cluster.isPrimary 表示当前代码运行在**主进程**，cluster.isWorker 表示运行在**工作进程**；两者互斥，用于在同一个入口文件里分叉执行不同逻辑。

- 完整写法为 cluster.isPrimary 返回布尔值，cluster.isWorker 同样返回布尔值，二者恰好相反。
- 旧版本使用 cluster.isMaster 表达"主进程"含义，该名称**已被官方取代**，新代码应改用 cluster.isPrimary。
- 判断后，主进程负责派生与管理，工作进程负责创建服务器、处理请求。

> 旧名 isMaster 在文档中标记为废弃（deprecated）。若维护老项目遇到 isMaster，须知它与 isPrimary 语义一致，但新代码应避免继续使用，以免未来版本移除。

**速记**：isPrimary **主**，isWorker **从**；isMaster 已**退役**。



#### fork 方法复制出多个工作进程

**cluster.fork**：是主进程用来**派生一个工作进程**的方法，每次调用复制出一份当前脚本的新进程，返回对应的 worker 对象。

- 完整写法为 cluster.fork(环境变量对象)，参数可选，传入的对象会以环境变量的形式注入新进程。
- 调用一次产生一个工作进程；要起多个就循环调用多次，常见做法是按 CPU 核数循环。
- 每个 fork 出的工作进程会**重新执行同一份入口文件**，但因 cluster.isWorker 为 true，走的是工作分支逻辑。

```js
const cluster = require("cluster");

if (cluster.isPrimary) {
  // 主进程：派生两个工作进程
  cluster.fork();
  cluster.fork();
  console.log("主进程派生完毕，PID：" + process.pid);
}
```

> [!CAUTION]
> **注意内容**：fork 出的进程是"完整独立的 Node 进程"，拥有自己的内存与事件循环，并非轻量线程。派生数量应与机器核数相匹配，过多反而引发调度开销。

**速记**：fork 一次，**多一个工人**。



#### 主进程只负责管理，不处理业务请求

**主进程职责**：在 cluster 架构中，主进程的核心任务是**派生、监控、重启工作进程**，本身**不直接处理客户端请求**。

- 主进程通常只监听 cluster 的 fork、exit、message 等事件，做调度与守护。

> 主进程若也去处理请求，一旦它崩溃，所有工作进程虽仍在，却失去了统一的端口持有与调度，等于守护链断裂。因此约定主进程只做管理。

**速记**：主进程**管人不管事**。



#### 多个工作进程能监听同一端口不冲突

**端口共享**：多个工作进程**同时监听同一个端口却不报错**，是因为**真正持有端口的是主进程**，工作进程只是被主进程把连接**转发**过去。

- 工作进程调用 server.listen(端口) 时，cluster 拦截该调用，让主进程在对应端口上实际建立监听。
- 因此工作进程之间并未真正各自绑定端口，自然不存在"端口已被占用"的冲突。

> [!CAUTION]
> **注意内容**：这一机制是 cluster 与"手动起多个独立进程各自 listen 同一端口"的关键区别。后者在不共享端口的普通操作系统下会报 EADDRINUSE，而 cluster 由主进程统一持有端口予以规避。

**速记**：端口**主进程独享，连接按需分发**。



#### 调度策略分为 round-robin 与操作系统调度

**调度策略**：主进程把新连接分发给工作进程时，有两种可选策略——**轮询（round-robin）**与**操作系统调度**，由 cluster.schedulingPolicy 决定。

- **轮询（默认，除 Windows 外）**：主进程按"依次轮流"的方式把连接分配给各工作进程，负载相对均衡。
- **操作系统调度**：由操作系统内核自行把连接分发给进程，行为依赖底层实现，Windows 上常走此路径。
- cluster.schedulingPolicy 可设为 cluster.SCHED_RR（轮询）或 cluster.SCHED_NONE（操作系统调度），须在 fork 之前设置才生效。

```js
const cluster = require("cluster");

// 在 fork 前设置调度策略为轮询
cluster.schedulingPolicy = cluster.SCHED_RR;

console.log("当前调度策略：" + cluster.schedulingPolicy);
```

> [!TIP]
> **建议内容**：轮询策略下主进程是连接分发的"中枢"，能更好控制均衡；操作系统调度把决定权交给内核，某些场景下短连接可能分布不均。跨平台时务必留意 Windows 默认值不同。

**速记**：RR **主进程轮着发**，NONE **交内核决定**。



### 完整可运行示例：按 CPU 核数 fork 工作进程

#### 按 os.cpus 的核数决定 fork 数量

**核数驱动**：使用 os 模块的 cpus 方法获取本机 CPU 核心数，用该数值作为 fork 工作进程的**目标数量**，做到"一核一进程"。

- 完整写法为 os.cpus() 返回核心信息数组，取其 length 即为逻辑核数。

```js
const os = require("os");

const cpuCount = os.cpus().length;
console.log("本机逻辑核数：" + cpuCount);
```

> [!NOTE]
> **提醒内容**：os.cpus 返回的是**逻辑核数**（含超线程），并非物理核数。对多数 Web 服务而言，按逻辑核数 fork 已能较好利用硬件，但极端性能调优时需区分二者。

**速记**：一核**配一个工人**最稳妥。



#### 主分支用循环调用 cluster.fork

**主分支逻辑**：当 cluster.isPrimary 为真时，进入主进程分支，用循环调用 cluster.fork 派生与核数相等的工作进程。

```js
const cluster = require("cluster");
const os = require("os");

if (cluster.isPrimary) {
  const cpuCount = os.cpus().length;
  console.log("主进程 " + process.pid + " 启动，核数：" + cpuCount);

  for (let i = 0; i < cpuCount; i++) {
    cluster.fork();
  }
}
```

> 主分支一旦 fork 完成就"无事可做"，靠事件监听维持生命。若主进程意外退出，所有工作进程会成为孤儿或被一并终止，因此主进程本身也需被外部守护（如 PM2、容器）。

**速记**：主分支**只管生工人**。



#### 工作分支创建 http 服务器并打印 pid

**工作分支逻辑**：当 cluster.isWorker 为真时，进入工作进程分支，创建 http 服务器并监听同一端口，同时打印自身 pid 以便观察。

```js
const cluster = require("cluster");
const http = require("http");

if (cluster.isWorker) {
  http
    .createServer((req, res) => {
      res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
      res.end("由工作进程 " + process.pid + " 处理\n");
    })
    .listen(3000);

  console.log("工作进程 " + process.pid + " 已监听 3000");
}
```

> 不同工作进程的 pid 互不相同，但都 listen(3000)。外部用 curl 多次访问时，响应中的 pid 会在多个值之间变化，这正是负载被分摊的证据。

**速记**：工人**各持 pid，共听一端口**。



#### 主进程监听 exit 事件感知工人退出

**exit 监听**：主进程通过 cluster.on 注册 exit 事件，每当任一工作进程退出都会触发，回调可拿到退出的 worker、退出码与信号。

- worker 是退出进程的句柄，code 是正常退出的退出码（异常时为 null），signal 是致其终止的信号名（正常退出为 null）。

```js
const cluster = require("cluster");

if (cluster.isPrimary) {
  // ...fork 循环之后
  cluster.on("exit", (worker, code, signal) => {
    console.log(
      "工作进程 " + worker.process.pid + " 退出，code=" + code + " signal=" + signal
    );
    cluster.fork(); // 立即补位
  });
}
```

> [!WARNING]
> **警告内容**：这里的"立即补位"只是雏形。频繁崩溃时无限立即重启会造成 CPU 风暴，生产环境还需加入延时与次数限制（详见崩溃检测章节）。

**速记**：exit 一响，**补位跟上**。



#### 完整示例整合与运行方式

**整合示例**：把主分支与工作分支、exit 自愈合并为一份可直接运行的脚本，对外提供多进程 http 服务。

```js
const cluster = require("cluster");
const http = require("http");
const os = require("os");

if (cluster.isPrimary) {
  const cpuCount = os.cpus().length;
  console.log("主进程 " + process.pid + " 启动，核数：" + cpuCount);

  for (let i = 0; i < cpuCount; i++) {
    cluster.fork();
  }

  cluster.on("exit", (worker, code, signal) => {
    console.log("工作进程 " + worker.process.pid + " 退出，code=" + code + " signal=" + signal);
    cluster.fork();
  });
} else {
  http
    .createServer((req, res) => {
      res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
      res.end("由工作进程 " + process.pid + " 处理\n");
    })
    .listen(3000);

  console.log("工作进程 " + process.pid + " 已监听 3000");
}
```

运行方式与验证：

- 将上述代码保存为 server.js，执行 node server.js 启动。
- 另开终端多次执行 curl http://localhost:3000，观察响应中的 pid 是否在多个值间轮换。
- 用 kill 命令终止某个工作进程 pid，应看到主进程打印退出日志并立刻 fork 出替代者。

```bash
node server.js
# 另开终端
curl http://localhost:3000
# 观察 pid；再用 kill <某个工作进程pid> 验证自愈
```

> 该示例已含"主分支 fork + 工作分支监听 + exit 补位"三要素，是可运行的最小集群骨架。生产化还需补充通信、优雅退出、重启限流等（后续章节逐一展开）。

**速记**：三要素**主派生、工监听、退补位**。



### 主进程与工作进程之间的通信

#### 用 worker.send 从主进程向工作进程发消息

**主发消息**：主进程持有 worker 对象，可调用其 send 方法向对应的工作进程发送消息，实现管理指令的下达。

- 完整写法为 worker.send(消息内容, 可选的发送句柄, 可选的回调)，消息内容通常为普通对象。

```js
const cluster = require("cluster");

if (cluster.isPrimary) {
  const worker = cluster.fork();
  worker.send({ type: "command", action: "reloadConfig" });
  console.log("已向工作进程 " + worker.process.pid + " 下发 reloadConfig");
}
```

> send 的消息会被序列化传递，因此只能发送可结构化克隆的数据（对象、数组、字符串等），不能直接传递函数或包含原生资源的复杂句柄（特定 sendHandle 除外）。

**速记**：主用 **worker.send 下令**。



#### 工作进程用 process.on("message") 接收消息

**工收消息**：工作进程通过 process.on 监听 message 事件，回调里拿到主进程经 worker.send 发来的消息对象。

- 完整写法为 process.on("message", 监听器函数)，监听器接收主进程发来的消息作为唯一参数。

```js
if (cluster.isWorker) {
  process.on("message", (msg) => {
    console.log("工作进程 " + process.pid + " 收到：" + JSON.stringify(msg));
    if (msg && msg.action === "reloadConfig") {
      // 执行配置热更新逻辑
    }
  });
}
```

> 工作进程内监听的是 process 的 message 事件，而非 cluster 的。务必区分：cluster.on 用于主进程监听集群级事件（fork、exit、message 等），process.on("message") 用于单个进程接收点对点消息。

**速记**：工用 **process.on("message") 收令**。



#### 主进程用 cluster.workers 遍历所有工作进程

**workers 集合**：cluster.workers 是一个以 worker id 为键、worker 对象为值的集合，主进程可用它**遍历全部在线工作进程**群发消息。

- 完整写法为 cluster.workers，它是对象而非数组，键为从 1 开始递增的 worker id。

```js
const cluster = require("cluster");

function broadcast(message) {
  for (const id in cluster.workers) {
    const worker = cluster.workers[id];
    if (worker) worker.send(message);
  }
}

// 例如：通知所有工人重新加载配置
broadcast({ type: "command", action: "reloadConfig" });
```

> cluster.workers 的键是 id 而非 pid，若需按 pid 定位要先在集合里比对 worker.process.pid。对不存在的 worker 调用 send 会得到 rejected promise 或异常，遍历里加判空更稳妥。

**速记**：cluster.workers **全体点名**。



#### 与 child_process 的 send 用法一致

**写法同源**：cluster 工作进程间、主从间的消息收发，其 API 形态与 child_process 子进程的 send、message 机制**高度一致**，可类比迁移。

- child_process 中父进程用 child.send 发、子进程用 process.on("message") 收，cluster 中主进程用 worker.send 发、工作进程同样用 process.on("message") 收。

> 不要把 cluster 通信与 child_process 通信混用在同一次传递里。它们是两套独立派生体系，但"send 发、message 收"的心智模型完全通用。

**速记**：cluster 通信 **照搬 child_process 套路**。



### 工作进程的崩溃检测与自动重启

#### 监听 cluster.on("exit") 获取退出码与信号

**崩溃感知**：主进程通过 cluster.on 监听 exit 事件，回调的 code 与 signal 参数揭示工作进程**为何退出**。

- 完整写法为 cluster.on("exit", 监听器函数)，参数依次为 worker、code、signal。
- code 非空而 signal 为空：进程**主动调用 process.exit(code)** 或以非零码结束。
- signal 非空：进程被**外部信号**（如 SIGKILL、SIGTERM）强制终止，此时 code 为 null。

```js
cluster.on("exit", (worker, code, signal) => {
  if (signal) {
    console.log("工作进程 " + worker.process.pid + " 被信号 " + signal + " 杀死");
  } else {
    console.log("工作进程 " + worker.process.pid + " 以退出码 " + code + " 结束");
  }
});
```

> 通过 code 与 signal 的组合，可区分"自然结束""主动退出""被信号杀"。这是决定"是否重启""如何重启"的依据，务必在回调里打印或上报，便于排错。

**速记**：code 说**自尽**，signal 说**他杀**。



#### 用 exitedAfterDisconnect 区分主动断开与异常崩溃

**断开标记**：worker.exitedAfterDisconnect 为 true 表示该进程是在**主进程调用 disconnect 之后**才退出的，属计划内；为 false 则多为**意外崩溃**。

- 完整写法为 worker.exitedAfterDisconnect，是 worker 对象上的布尔属性，在 exit 事件回调中读取。
- 主进程主动执行 worker.disconnect() 触发退出时，该标记被置为 true，不应视为故障。
- 标记为 false 且伴随非零 code 或信号，通常意味着工作进程**真的崩了**，应安排重启。

```js
cluster.on("exit", (worker, code, signal) => {
  if (worker.exitedAfterDisconnect) {
    console.log("工作进程 " + worker.process.pid + " 按计划断开，无需重启");
  } else {
    console.log("工作进程 " + worker.process.pid + " 异常退出，准备重启");
    restartWorker();
  }
});
```

> [!CAUTION]
> **注意内容**：误把"计划内断开"也当作崩溃去重启，会导致零停机发布时工人刚优雅退出又被立刻拉起。exitedAfterDisconnect 正是为区隔这两种意图而生。

**速记**：exitedAfterDisconnect **真=主动，假=真崩**。



#### 延时重启避免崩溃循环耗尽 CPU

**重启节流**：当工作进程因同一错误**反复立即崩溃**时，若每次 exit 都立刻 fork，会形成"崩溃—重启—再崩溃"的死循环并打满 CPU，应改为**延时重启**。

- 用 setTimeout 包裹 cluster.fork，给系统留出喘息与日志落盘的时间。
- 延时期间主进程仍可服务，已存活的其他工人继续承接连接。

```js
function restartWorkerWithDelay(worker) {
  console.log("工作进程 " + worker.process.pid + " 崩溃，1 秒后重启");
  setTimeout(() => {
    cluster.fork();
  }, 1000);
}

cluster.on("exit", (worker, code, signal) => {
  if (!worker.exitedAfterDisconnect) {
    restartWorkerWithDelay(worker);
  }
});
```

> [!WARNING]
> **警告内容**：立即重启在偶发崩溃时恢复快，但在"每次启动即崩"的场景下会变成 CPU 风暴。延时是成本极低的兜底，应在任何自动重启逻辑里默认加上。

**速记**：崩了**别立刻拉，先歇一秒**。



#### 限制重启次数防止无限崩溃

**重启上限**：仅做延时仍不能阻止"持续崩溃"，应给单个工人或整体设置**最大重启次数**，超过阈值则停止重启并告警，避免无意义消耗。

- 用一个计数器记录某工人的累计重启次数，每次重启前自增并判断是否越界。
- 超过上限后停止 fork，转为打印错误、上报监控，交由人工或外部编排介入。

```js
const maxRestarts = 5;
const restartCount = {};

function safeRestart(worker) {
  const id = worker.id;
  restartCount[id] = (restartCount[id] || 0) + 1;
  if (restartCount[id] > maxRestarts) {
    console.error("工人 " + id + " 重启超过 " + maxRestarts + " 次，停止自愈并告警");
    return;
  }
  setTimeout(() => cluster.fork(), 1000);
}

cluster.on("exit", (worker, code, signal) => {
  if (!worker.exitedAfterDisconnect) safeRestart(worker);
});
```

> [!CAUTION]
> **注意内容**：不设上限的自愈等于"让错误无限重试"。生产环境必须把"重启次数上限 + 告警"当作标配，否则一个必崩的 bug 会被反复拉起直到资源耗尽。

**速记**：重启**设上限，超限即报警**。



### 零停机重启与优雅退出

#### 用 disconnect 配合 exit 实现滚动重启

**零停机重启**：通过逐个对工作进程调用 disconnect，使其停止接收新连接、处理完存量后再退出，主进程在其 exit 时补 fork 新进程，实现**滚动替换不中断服务**。

- 完整写法为 worker.disconnect()，它让该工人不再被分配新连接，待既有请求处理完毕自然退出。
- 退出时触发 exit 事件，此时 exitedAfterDisconnect 为 true，主进程据此 fork 一个**新版本**工人顶上。
- 对整个集群轮流执行"断开一个、补一个"，旧代码逐步被新代码取代，全程端口始终有人监听。

```js
function rollingRestart() {
  for (const id in cluster.workers) {
    const worker = cluster.workers[id];
    if (worker) {
      // 逐个断开，exit 时由主进程补发新工人
      worker.disconnect();
    }
  }
}
```

> 滚动重启的关键在于"一次只动一个"，保证始终有存活工人承接流量。若同时 disconnect 全部工人，会出现短暂无人接客的空窗，违背零停机初衷。

**速记**：零停机=**逐个换岗不空窗**。



#### 收到 SIGTERM 时先关闭服务器停止接新连接

**优雅退出的信号入口**：进程管理器（如 Kubernetes、docker stop）停止服务时常发送 SIGTERM，工作进程应监听该信号，**先关闭服务器停止接收新连接**，再处理存量。

- 完整写法为 process.on("SIGTERM", 监听器函数)，在监听器中调用 server.close 关闭监听。
- server.close 会让服务器**不再接受新连接**，但已建立的连接仍可继续处理直到完成。
- 主进程收到 SIGTERM 时，应把信号**转发给所有工作进程**，由工人各自优雅退出，而非自己硬杀工人。

```js
let server;

if (cluster.isWorker) {
  server = http.createServer(handler).listen(3000);

  process.on("SIGTERM", () => {
    console.log("工作进程 " + process.pid + " 收到 SIGTERM，关闭监听");
    server.close(() => {
      console.log("工作进程 " + process.pid + " 已无连接，退出");
      process.exit(0);
    });
  });
}
```

> [!WARNING]
> **警告内容**：SIGTERM 可被捕获并拦截，这正是实现优雅退出的前提；而 SIGKILL 不可捕获，会瞬间杀死进程。编排平台一般用 SIGTERM 给应用留清理时间，超时后才发 SIGKILL。

**速记**：SIGTERM 到，**先关门再走**。



#### 等待存量请求处理完再退出并设超时兜底

**退出兜底**：server.close 的回调表示存量连接已清空，此时再 process.exit 最干净；但若有连接**迟迟不结束**，必须加**超时强制退出**，防止进程吊死无法回收。

- 在 server.close 之外另起一个 setTimeout，到时若仍未退出则强制 process.exit(1)。
- 超时时长应覆盖"最长合理请求耗时 + 缓冲"，常见为 5 到 30 秒。
- 超时强制退出意味着可能丢弃个别长连接，但换来"进程一定能被回收"，优于无限等待。

```js
if (cluster.isWorker) {
  let closed = false;

  process.on("SIGTERM", () => {
    server.close(() => {
      closed = true;
      process.exit(0);
    });

    // 超时兜底：10 秒后仍有连接未结束则强制退出
    setTimeout(() => {
      if (!closed) {
        console.error("优雅退出超时，强制退出");
        process.exit(1);
      }
    }, 10000);
  });
}
```

> 优雅退出若不设超时，遇到"僵尸长连接"或"客户端不关连接"时进程会一直挂着，编排平台只能靠 SIGKILL 强杀，反而失去优雅意义。超时是优雅与确定性的折中。

**速记**：优雅退出**有耐心，也有底线**。



### 多进程状态共享与进程管理部署

#### 多进程之间内存不共享

**内存隔离**：cluster 的各工作进程是**独立 Node 进程**，拥有各自独立的 V8 堆与内存，一个进程里写入的变量**不会**出现在另一个进程里。

- 在某工人中声明的全局缓存、会话对象，对其他工人**完全不可见**。
- 进程间通信只能靠 send 传递**可序列化消息**，无法直接共享一个大对象引用。
- 这与 worker_threads 的共享内存（SharedArrayBuffer）不同，cluster 走的是进程隔离路线。

> [!CAUTION]
> **注意内容**：把"内存共享"误当作理所当然，是 cluster 初学者最常见的认知错误。多进程下没有全局可变状态能被所有工人同时看到，任何状态都要显式传递或外置。

**速记**：工人**各活各的内存**。



#### 会话与缓存必须外置或使用粘性会话

**状态外置**：由于内存不共享，用户会话、热点缓存等**不能放在进程内存**里，应改用外部存储或粘性会话策略。

- **外部存储**：将会话与缓存写入数据库、Redis 等独立服务，所有工人连接同一份数据源，天然一致。
- **粘性会话（session affinity）**：在负载均衡层把同一客户端的请求**固定转发到同一工人**，使其本地内存可用，但工人重启会丢失该部分状态。
- 选型上，无状态 + 外部存储最稳健；粘性会话仅在缓存无法外置或追求极致性能时考虑。

> 粘性会话是一把双刃剑：它让"进程内存当缓存"变得可行，却使扩容、缩容、滚动发布时部分用户被"绑死"在即将下线的工人上。生产首选仍是把状态交给 Redis 等外部存储。

**速记**：状态**要么外置，要么绑人**。



#### PM2 是社区常用的进程管理器

**PM2 定位**：PM2 是 Node 社区广泛使用的**进程管理工具**，提供开机自启、日志聚合、监控面板与自动重启等能力，属于**社区方案而非 Node 内置**。

- 完整写法为 pm2 start 脚本名 --参数，常用 -i 参数指定按核数启动的实例数。
- pm2 list 查看进程列表，pm2 logs 查看聚合日志，pm2 restart 重启，pm2 stop 停止。
- PM2 内部**同样基于 cluster 模块**实现多进程，是对 cluster API 的封装与增强，并非另一套并行体系。

```bash
# 按 CPU 核数启动（max 表示自动取核数）
pm2 start server.js -i max

# 查看状态与日志
pm2 list
pm2 logs

# 重启与停止
pm2 restart server.js
pm2 stop server.js
```

> [!IMPORTANT]
> **重要内容**：PM2 的 -i max 等价于"按核数 fork 工作进程"，底层仍是 cluster。它替你处理了 exit 自愈、日志轮转、开机自启等样板代码，但代价是引入额外依赖与学习成本；理解 cluster 原理才能看懂 PM2 在做什么。

**速记**：PM2 **社区封装，底层还是 cluster**。



#### 容器与编排环境里的 CPU 核数感知

**容器核数**：在 Docker 等容器里，进程看到的 CPU 核数可能受**配额限制**而非物理核数，cluster 按 os.cpus 取核数 fork 时需留意"感知到的核数"是否符合预期。

- 容器通过 cpu quota/limit 限制可用算力，os.cpus 在某些配置下仍返回宿主机核数，导致 fork 过多。
- 此时应改用编排平台（如 Kubernetes）管理**副本数**，每个容器只跑**单进程或少量进程**，由平台做横向扩缩容。
- 容器内日志应**输出到标准输出/标准错误**，交由编排平台统一采集，而非写本地文件。

> 在 Kubernetes 中常让每个 Pod 只运行一个 Node 进程（或靠 PM2 在 Pod 内起少量进程），副本数由 Deployment 的 replicas 控制。这样"多进程利用多核"与"多副本利用多机"分层清晰，滚动发布也由平台原生支持。

**速记**：容器里**核数可能虚高，日志走标准输出**。



#### 常见坑：fork 过量、未捕获异常循环、日志交错

**典型陷阱**：使用 cluster 时有三类高频坑——fork 数量超过核数、未处理未捕获异常导致循环崩溃、多进程日志交错难排查。

- **fork 过量**：工作进程数远超逻辑核数，进程切换开销反超并行收益，吞吐**不升反降**，应控制在核数附近。
- **未捕获异常**：工作进程里未监听 uncaughtException，一次崩溃触发无限重启风暴，必须配套"重启限流 + 异常兜底"。
- **日志交错**：多个工人同时写同一文件或同一标准输出，打印行互相穿插、pid 混乱，应**在每条日志前带 pid** 或集中到日志服务。

```js
// 每个工人日志都带 pid，便于区分来源
console.log("[" + process.pid + "] 处理请求 " + req.url);
```

> fork 过量是"以为越多越快"的错觉；未捕获异常循环是"自愈变自爆"；日志交错则让排错如大海捞针。三者都可通过"按核数 fork + 异常兜底 + 带 pid 日志"一次性规避。

**速记**：三坑**过量、自爆、日志乱**。
