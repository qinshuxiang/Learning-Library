## ES Module 模块化

### ES Module 的认识

**ES Module（ESM）**：是 ECMAScript 官方标准化的**模块系统**，浏览器与 Node 通用，用于把程序拆成可复用文件。

模块化的收益：

- **作用域隔离**：每个模块独立作用域，变量不泄漏全局。
- **依赖管理**：显式声明依赖，便于维护替换。
- **可复用**：通过导入导出拼装功能。

> ESM 之前社区用过 CommonJS、AMD、CMD 等互不兼容方案。ESM 的价值在于它是**语言级标准**，浏览器与 Node 共用同一套语法。

#### ECMAScript 官方标准

**ECMAScript Module**：是由 ECMAScript 规范（ES2015 起）定义的**官方模块语法**，用 import 与 export 关键字。

对照：

- **ESM**：语言标准，浏览器与 Node 原生支持。
- **CommonJS**：Node 自定义的社区规范，仅 Node 生态通用。

```js
import { readFile } from "node:fs/promises";
export const version = "1.0.0";
```

> ESM 与 CommonJS 语法**不能混写同一文件**：要么 import/export，要么 require/module.exports，由扩展名或 type 字段决定。



#### 静态化依赖

**静态化**：是 ESM 在**编译阶段**就确定全部导入导出关系、而非运行时解析的特性。

表现：导入导出必须位于**模块顶层**，不能写在 if、函数内；导入绑定在解析期完成，运行前可构建完整依赖图。

```js
import { add } from "./math.js"; // 合法：顶层
if (debug) {
  import { log } from "./logger.js"; // 非法：不能出现在块内
}
```

> 静态化代价是"不够灵活"——无法运行时决定导入谁。该限制由**动态导入 import()** 弥补，它返回 Promise、不受顶层约束。



#### 为什么支持 tree shaking

**tree shaking**：是打包工具在构建时**删除未引用导出代码**的优化，依赖 ESM 静态结构。

原因：导入导出编译期已知，工具可判断哪些导出从未使用；绑定是只读引用，删除无副作用风险，安全。

```js
export const add = (a, b) => a + b;
export const sub = (a, b) => a - b;
import { add } from "./math.js"; // 仅用 add，sub 可被摇掉
```

> **CommonJS 难 tree shaking**：require 是运行时调用，工具无法静态判断是否用到某导出，只能保守保留。这是前端默认选 ESM 的核心原因之一。



### 在 Node 中启用 ESM

**Node 的模块模式**：由文件的**扩展名**或 **package.json 的 type 字段**共同决定，二者冲突时扩展名优先。

启用 ESM 的两条主路径：把整个包声明为 ESM（type: module），或单文件用 .mjs 扩展名。

#### 用 package.json 切换 type

**type 字段**：是 package.json 中控制**默认模块系统**的开关，取值 module 或 commonjs（默认）。

设为 module 后，该目录下所有 .js 都按 ESM 解析：

```json
{ "name": "my-app", "type": "module", "version": "1.0.0" }
```

```js
import { createServer } from "node:http"; // type:module 下 .js 即 ESM
```

> type 只影响 **.js 的默认类型**：显式 .mjs 永远是 ESM，.cjs 永远是 CommonJS，type 对它们无效，扩展名优先级更高。



#### 用 .mjs 扩展名

**.mjs**：是 Node 认定的**原生 ESM 文件扩展名**，无需配置即可用 import/export。

优势是"局部、明确"：单文件用 .mjs 即启用 ESM，不波及同目录其他文件；与 .cjs 对称，迁移时逐个切换最稳妥。

```bash
node server.mjs   # 直接运行，无需 package.json 配置
```

```js
import { readFile } from "node:fs/promises";
const text = await readFile("./data.txt", "utf8");
```

> 当 package.json 是默认 commonjs 又想用 ESM 时，最干净的做法是把文件命名为 .mjs，二者互不干扰。



#### 反向启用 CommonJS 与历史演进

**反向启用**：是在默认 ESM 环境把个别文件改回 CommonJS 的两种手段——设 type: commonjs 让 .js 走 CommonJS，或用 .cjs 扩展名强制 CommonJS。

ESM 在 Node 的落地时间线：

- **Node 8.5**：--experimental-modules 首次试验（需 .mjs）。
- **Node 12**：支持 type 切换，实验性减弱。
- **Node 13.2**：取消强制实验标志，进入稳定通道。
- **Node 14+**：ESM 基本稳定，动态 import() 全面可用。

```bash
node --experimental-modules app.mjs   # 仅旧版本需要，现代版本已不需
```

> 现代 LTS 版 Node **无需任何实验标志**即可用 ESM。遇"Cannot use import statement outside a module"，通常是忘了 type: module 或文件没用 .mjs。



### export 导出

**export**：是 ESM 中**向外部暴露接口**的关键字，分命名导出与默认导出两类。

基本认知：命名导出可多次，默认导出只能一次；导出的是**绑定（引用）**而非值快照。

#### 命名导出

**命名导出**：是用 export 关键字导出**具名成员**的方式，一个模块可有任意多个。

三种等价写法：

- 声明时直接导出：在 function / const 前加 export。
- 统一导出：先声明，再用 export { } 集中列出。
- 导出时重命名：用 as 关键字改对外名称。

```js
export const PI = 3.14;
const sub = (a, b) => a - b;
export { sub, add as sum }; // 统一导出 + 重命名
```

> 命名导出强调"**名字即契约**"：导入方须用相同名字（或重命名后）才能拿到，与默认导出的匿名出口形成对比。



#### 默认导出

**默认导出**：是用 export default 导出**模块主出口**的方式，对外无需指定名字。

要点：一个模块**只能有一个**默认导出；默认导出可以是函数、类、对象或任意表达式。

```js
export default function greet(name) {
  return `Hello, ${name}`;
}
```

> 默认导出适合"一个模块只做一件事"（如 React 组件）。**多个默认导出会语法报错**，这是与命名导出最直观的区别。



#### 重命名与转发

**转发（re-export）**：是用 export ... from 把另一模块的接口**直接转手导出**，常用于聚合入口文件。

常见形式：

- 转发命名成员：export { a, b } from "./other.js"。
- 转发并重命名：export { a as x } from "./other.js"。
- 转发默认：export { default } from "./other.js"。

```js
export { add, sub } from "./math.js";
export { default } from "./logger.js";
```

> 转发**不在本模块创建绑定**，只是"过路"。它适合做**桶文件（barrel file）**，把分散子模块统一从一处暴露，调用方只需 import 一次。



### import 导入

**import**：是 ESM 中**引入外部模块接口**的关键字，形式须与对应导出匹配。

导入形态：命名导入对应命名导出；默认导入对应默认导出；整体导入把全部命名导出收进一个命名空间对象。

#### 各类导入形式

**导入形态**：按"要什么"分为命名导入、整体导入、默认导入、混合导入与副作用导入。

逐一说明：

- **命名导入**：花括号内写具体名字，可用 as 重命名。
- **整体导入**：import * as ns 把命名空间整体收进对象。
- **默认导入**：直接写名字，对应 export default。
- **混合导入**：默认与命名写同一行。
- **副作用导入**：只执行模块、不取绑定（import "./x.js"）。

```js
import { add as sum } from "./math.js";
import * as math from "./math.js";
import greet from "./greet.js";
import greet2, { name } from "./user.js";
import "./polyfill.js";
```

> 命名导入名字须与导出一致（除非用 as）；整体导入得到**实时只读**命名空间对象，对其赋值会报错。副作用导入常用于加载**样式、polyfill、全局注册**。



#### 顶层静态限制

**顶层静态限制**：是 import 必须写在**模块顶层**、不能进块级作用域或条件语句的约束。

这意味着：import 不能包在 if、for、函数内部；导入在模块执行前就完成绑定。

```js
import { a } from "./a.js"; // 合法
function load() {
  import { b } from "./b.js"; // 非法：出现在函数内
}
```

> 需在运行时按条件加载，必须用**动态导入 import()**，它返回 Promise 并绕过顶层限制。静态 import 与动态 import() 互补，不可互相替代。



### ESM 的严格性

**ESM 的严格性**：指 ESM 模块**默认运行在严格模式**下，并缺少 CommonJS 的若干全局变量。

理解严格性，才能避免"在 ESM 里找不到 require"的困惑。

#### 默认严格模式

**严格模式**：是 ES5 引入的更严格语言子集，ESM 中**自动开启、无法关闭**。

典型约束：禁止未声明变量直接赋值（不再隐式创建全局变量）；禁止删除变量、函数、函数参数；函数内 this 不再默认指向全局对象。

```js
x = 10; // ReferenceError: x is not defined（ESM 默认严格）
```

> 因默认严格，ESM 文件**不需要也不允许**写 "use strict"；写了不报错但冗余。CommonJS 默认非严格，需手动开启。



#### 顶层 this 与缺失的全局变量

**缺失的 CommonJS 全局**：是 ESM 顶层**不存在**的 require、exports、module、__dirname、__filename 等变量。

差异：顶层 this 在 ESM 中是 undefined（CommonJS 中指向 module.exports）；require / exports / module 不存在，改用 import/export；__dirname / __filename 不存在，改用 import.meta.url 推导。

```js
console.log(this);        // undefined
console.log(typeof require);    // "undefined"
console.log(typeof __dirname);  // "undefined"
```

> 这是 ESM 与 CommonJS 互操作最常见的坑：把 CommonJS 代码改名 .mjs 会立即因 require 报错。正确取路径方式见"在 ESM 中获取文件路径"。



### 在 ESM 中获取文件路径

**ESM 的文件路径问题**：因缺 __dirname 与 __filename，需通过 **import.meta.url** 与 **fileURLToPath** 推导当前文件位置。

这是所有"基于自身位置读写文件"的 ESM 代码必备技巧。

#### import.meta.url 与 fileURLToPath

**import.meta.url**：是 ESM 提供的**当前模块文件 URL**（形如 file:///.../app.mjs），是路径推导源头。

配合 node:url 的 fileURLToPath 将 URL 转为系统路径：fileURLToPath 接收 file:// URL 返回**平台绝对路径**；path.dirname 进一步得目录，等价于旧 __dirname。

```js
import { fileURLToPath } from "node:url";
import path from "node:path";
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
```

> import.meta.url 是 **URL 而非路径**，不能直接拼字符串当路径用，必须过 fileURLToPath 转换。这是与 CommonJS 直接用 __dirname 最大的写法差异。



#### 封装 getDirname 工具函数

**getDirname**：是一个**可复用工具函数**，把"由 URL 求目录"的样板封装，避免多处重复书写。

实现要点：入参是 import.meta.url；内部用 fileURLToPath 与 path.dirname 推导；返回字符串目录路径，对齐 CommonJS 的 __dirname。

```js
import { fileURLToPath } from "node:url";
import path from "node:path";
export function getDirname(metaUrl) {
  return path.dirname(fileURLToPath(metaUrl));
}
const here = getDirname(import.meta.url); // 当前文件目录
```

> 封装成 getDirname 后，任何 ESM 文件只需 here = getDirname(import.meta.url) 即得"当前目录"，迁移 CommonJS 代码时尤其省心。



### 动态导入 import()

**动态导入 import()**：是 ESM 提供的**运行时按需加载**语法，返回 Promise，突破静态 import 的顶层限制。

与静态 import 关键不同：可出现在任何位置、可条件执行。

#### 返回 Promise 与按需加载

**import() 的返回值**：是解析为**模块命名空间对象**的 Promise，需用 await 或 then 取用。

典型用途：

- **按需加载**：用到时才加载，减小初始体积。
- **条件加载**：按运行时状态决定加载哪个模块。
- **错误兜底**：用 try/catch 处理模块缺失。

```js
async function loadLocale(lang) {
  const m = lang === "zh"
    ? await import("./zh.js")
    : await import("./en.js");
  return m.messages;
}
```

> 动态 import() 返回**命名空间对象**，取导出要写 (await import("./x.js")).default 拿默认导出。它让 ESM 也能"懒加载"，是代码分割基础。



#### 在 CommonJS 中使用动态 import

**CommonJS 中的动态 import**：指老代码用 require 的同时，也能通过 import() 加载 ESM 模块。

原因与注意：require 只能同步加载 CommonJS，**无法直接 require ESM**；import() 是语言统一异步入口，CommonJS 与 ESM 都可用。

```js
// legacy.cjs（CommonJS 文件）
async function main() {
  const esmModule = await import("./modern.mjs");
  console.log(esmModule.default);
}
main();
```

> 这是"CommonJS 调 ESM"的**唯一标准途径**：用 import()。反向 ESM 用 import 即可直接消费 CommonJS，双向打通关键在于"异步侧适配同步侧"。



### ESM 与 CommonJS 的差异对比

**ESM 与 CommonJS 的差异**：集中在加载时机、值语义、异步性与顶层能力四维度，是选型与排错核心。

对比须成对记忆，下面逐条展开。

#### 加载时机与异步性

**加载时机**：是两者最根本区别——ESM 在**编译期**解析依赖，CommonJS 在**运行期**执行到 require 才加载。

对比：

- **ESM**：静态、编译期确定依赖图，可异步加载。
- **CommonJS**：动态、运行期遇 require 才加载，同步阻塞。

```js
const lodash = require("lodash");        // CommonJS：运行到才读
import { cloneDeep } from "lodash-es";   // ESM：执行前已绑定
```

> ESM 异步特性来自**可并行预加载**依赖；CommonJS 的 require 是同步 I/O，会阻塞后续。这也是 Node 原生支持顶层 await 的前提之一。



#### 值的绑定与顶层能力

**值绑定**：描述导入方拿到的是"引用"还是"拷贝"——两者最易踩坑的差异。

对比：

- **ESM**：导入**实时只读绑定**，原模块改了值，导入方立刻看到新值。
- **CommonJS**：require 得**值拷贝（对象则是同引用）**，原模块后续赋值不影响已拿到导出。

```js
export let count = 0;
export function inc() { count++; }
// 导入方 inc() 后，count 实时变为 1
```

> ESM 的"活绑定"意味着**导入方不能给命名导入重新赋值**（只读）。在顶层能力上，**顶层 this** ESM 是 undefined、CommonJS 指向 module.exports；**顶层 await** ESM 支持、CommonJS 不支持。



### ESM 与 CommonJS 的互操作

**互操作**：是 ESM 与 CommonJS 在**同一项目互相引用**时的规则与陷阱，理解它才能平滑迁移。

核心结论：ESM 侧更宽容，CommonJS 侧受限。

#### ESM 导入 CommonJS

**ESM 消费 CommonJS**：是 Node 内**天然支持**的方向，import 一个 .cjs 或 commonjs 包即可。

行为规则：CommonJS 的 module.exports 整体被当作**默认导出**；命名导入（import { x }）仅在模块提供**静态分析提示**时可用，否则取不到。

```js
// legacy.cjs
module.exports = { greet: (n) => `Hi ${n}` };
// app.mjs
import legacy from "./legacy.cjs";   // 拿到整个 module.exports
console.log(legacy.greet("why"));   // "Hi why"
```

> ESM 导入 CommonJS 时，**默认导入最稳**：拿到就是 module.exports 对象。依赖命名导入可能失败，因 CommonJS 导出本质是运行时对象，静态分析未必识别。



#### CommonJS 导入 ESM 的坑

**CommonJS 消费 ESM**：是**受限方向**，不能用 require，必须改用动态 import()。

常见坑：

- **require 无法加载 ESM**：ESM 异步、require 同步，根本冲突。
- **必须用 import()**：返回 Promise，需 async 包装。
- **默认导出位置不同**：ESM 默认导出在导入结果 default 上。

```js
const m = require("./modern.mjs");        // 错误：ERR_REQUIRE_ESM
async function use() {
  const m = await import("./modern.mjs"); // 正确：动态 import
  console.log(m.default);
}
```

> 若包同时提供 CommonJS 与 ESM（双格式包），让 CommonJS 通过 require 拿它的 **CommonJS 构建产物**，避免跨格式加载，是最常见稳妥方案。



### ESM 的解析规则

**ESM 的解析规则**：指 Node 在 ESM 模式下**如何定位被导入文件**的硬性约定，比 CommonJS 更严格。

违反会直接报 ERR_MODULE_NOT_FOUND。

#### 必须写完整扩展名

**完整扩展名**：是 ESM 导入时**必须显式写出** .js / .mjs 等后缀，不能省略。

对照：

- **ESM**：import "./util" 报错，必须写 "./util.js"。
- **CommonJS**：require 可省扩展名，Node 自动补 .js / .json / .node。

```js
import { helper } from "./helper.js";   // 必须带扩展名
import { helper } from "./helper";      // 错误：ERR_MODULE_NOT_FOUND
```

> 规则源于 ESM 的**浏览器语义**：浏览器加载脚本 URL 必须有完整文件名。Node 为与浏览器一致刻意不省略，避免同一写法两环境表现不同。



#### 目录自动解析与相对路径前缀

**目录与路径解析**：ESM 不自动解析 **index.js**，相对路径也**必须带 ./ 或 ../** 前缀。

约束：

- **不支持目录入口**：import "./utils" 不会自动找 utils/index.js。
- **必须相对前缀**：import "utils.js" 被当作**裸模块说明符**（去 node_modules 找），非本地文件。

```js
import { x } from "./utils";        // 错误：不自动解析 index.js
import { y } from "helper.js";      // 错误：缺前缀被当包名
import { x } from "./utils/index.js"; // 正确：写全
```

> 与 CommonJS"目录自动找 index"不同，ESM 要求**路径写全**。这是刻意与浏览器一致：浏览器没有"目录默认文档"概念，必须给确切文件。



### package.json 的 exports 与 imports 字段

**exports 字段**：是 package.json 中**控制对外暴露哪些子路径**的入口映射，取代并优先于 main。

它解决"包内部文件被随意引用"的封装问题。

#### 条件导出与子路径封装

**条件导出**：是在 exports 里按**运行环境**（import、require、node、default）给不同入口的能力。

子路径封装：只暴露 exports 中声明的路径，未列出的子文件**外部不可直接 import**；可对不同模块系统返回不同文件（ESM 用 .mjs、CommonJS 用 .cjs）。

```json
{
  "name": "my-lib",
  "exports": {
    ".": { "import": "./dist/esm/index.js", "require": "./dist/cjs/index.cjs" },
    "./utils": "./dist/esm/utils.js"
  }
}
```

> exports 既是**入口开关**也是**封装边界**：没写进 exports 的文件对外部不可见，调用方 import 内部路径会报 ERR_PACKAGE_PATH_NOT_EXPORTED。这也是现代库同时支持 ESM 与 CommonJS 的惯用写法。



#### main 与 exports 的优先级

**优先级**：当 package.json 同时有 main 与 exports 时，**exports 优先**，main 仅作兜底。

规则要点：定义 exports 后，根入口 "." 由 exports 决定，main 被忽略（除非 exports 未覆盖）；老工具不支持 exports 时可能仍读 main，故常两者并存。

```json
{
  "main": "./dist/cjs/index.cjs",
  "exports": { ".": { "import": "./dist/esm/index.js", "require": "./dist/cjs/index.cjs" } }
}
```

> 现代 Node 与打包工具优先认 exports；main 存在主要**兼容旧生态**。新包推荐直接用 exports 描述全部入口，把 main 当历史兼容字段。
