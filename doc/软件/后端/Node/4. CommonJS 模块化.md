## CommonJS 模块化

### 模块化的演进

#### 无模块时期的问题

**无模块时期**：指浏览器早期仅靠多个 script 标签顺序加载、所有代码共享全局作用域的阶段，主要问题是命名冲突与依赖脆弱。

- **全局污染**：不同脚本同名顶层变量互相覆盖。
- **依赖混乱**：脚本必须按手写顺序加载，调整顺序易报错。
- **复用困难**：功能无法干净导出，只能挂到全局约定对象上。

> 全局污染的根源是缺少作用域隔离，项目变大、多人协作时极易出错，这正是模块化要解决的起点。

**速记**：无模块时代 **全局共享，命名冲突靠人防**。



#### 立即执行函数 IIFE

**IIFE**：即立即执行函数表达式，用一层函数作用域把私有变量包起来，只把需公开的部分通过返回值暴露，让"模块"在语言尚未支持时提前出现。

```js
const moduleA = (function () {
  const privateValue = 1; // 外部访问不到
  return { publicMethod() { return privateValue; } };
})();
```

> IIFE 解决了作用域隔离，却无法自动解析依赖与加载顺序，语法也笨重，不适合大规模工程。

**速记**：IIFE **包一层函数，只交返回值**。



#### CommonJS 的出现与 Node 的采纳

**CommonJS**：是一套服务端 JavaScript 模块规范，定义 require 导入与 module.exports 导出，目标是让 JS 具备类似 Python、Java 的模块能力。

- **规范提出**：2009 年由 Kevin Dangoor 等人发起，初名 ServerJS。
- **Node 采纳**：早期即以 CommonJS 为模块系统基础，因服务端可同步读本地文件。

```js
const fs = require("fs");
module.exports = { read: () => fs.readFileSync };
```

> Node 选择已有规范而非自创，同步加载契合本地文件系统，奠定了早期 npm 生态形态。

**速记**：CommonJS **require 进、module.exports 出**。



#### 与 AMD、CMD、ES Module 的关系

**模块规范家族**：CommonJS 之外，浏览器侧先后出现 AMD、CMD，语言层最终统一于 ES Module（ESM）。

- **CommonJS**：同步加载，适用服务端，Node 早期采用。
- **AMD**：异步加载、依赖前置，适合浏览器（如 RequireJS）。
- **CMD**：异步加载、依赖就近，国产代表 SeaJS。
- **ES Module**：语言标准，静态结构，浏览器与服务端通用。

> CommonJS 与 ESM 最大差异是加载时机：前者运行时同步求值，后者解析阶段静态分析，这是 ESM 能做 tree shaking 而 CommonJS 不能的根本原因。



### CommonJS 的核心规范

**速记**：规范三家 **服务端 CJS、浏览器 AMD/CMD、语言层 ESM**。

#### 每个文件是一个模块

**文件即模块**：CommonJS 约定下每个 .js 文件天然是一个独立模块，拥有自己的作用域与 exports。

- 文件顶层声明的变量**不会**泄漏到其他文件。
- 对外接口集中放在 module.exports 上。

```js
const name = "why"; // 仅本文件可见
module.exports = { name };
```

> "文件即模块"使工程可按文件拆职责又不必担心名字撞车，是导入导出语法的物理前提。

**速记**：**一个文件即一个作用域**。



#### 通过 module.exports 导出

**导出机制**：模块通过给 module.exports 赋值或挂载属性，决定外部 require 能拿到什么。

- **对象挂载**：module.exports.key = value，导出多个成员。
- **整体替换**：module.exports = value，导出单值、类或函数。

> module.exports 是唯一决定导出内容的对象；exports 只是它的引用别名，所有导出最终都作用于它。

**速记**：导出看 **module.exports 的最终指向**。



#### 通过 require 导入

**导入机制**：用 require 传入模块标识，同步取得其 module.exports。

- require 的返回值是目标模块的 module.exports。
- 可整体接收，也可解构出所需成员。

```js
const { greet } = require("./user");
console.log(greet("why"));
```

> require 是 CommonJS 的入口，理解它返回 module.exports 而非整个文件，是避免"拿到空对象"困惑的关键。

**速记**：require **同步取回目标 exports**。



#### 模块加载是同步的

**同步加载**：require 会**阻塞当前执行流**直到目标模块编译执行完成并返回 exports。

- 在可随机读的服务端，同步延迟极低、语义直观。
- 在需边下载边解析的浏览器，同步会卡住页面，因此不适用。

```js
const a = require("./a"); // 返回前 a 已完整可用
const b = require("./b");
```

> 同步是 CommonJS 与浏览器方案的分水岭，换来"导入即用"的简单模型，代价是失去按需异步能力。



### exports 导出的各种写法

**速记**：**同步阻塞**，服务端读盘可接受。

#### 导出多个值

**多值导出**：在 module.exports 上逐个挂载属性，或等价用 exports.xxx，适合工具集合模块。

```js
// utils.js
exports.add = (a, b) => a + b;
exports.sub = (a, b) => a - b;
exports.mul = (a, b) => a * b;
```

```js
const utils = require("./utils");
console.log(utils.add(1, 2)); // 3
```

> 多值导出得到命名空间对象，使用者按属性名取用，是库文件最常见形态。

**速记**：多值 **逐个挂属性**。



#### 导出单个值

**单值导出**：用 module.exports = 值，把单一函数、对象或原始值作为整个模块导出。

```js
// config.js
module.exports = { port: 3000, host: "localhost" };
```

```js
const config = require("./config");
console.log(config.port); // 3000
```

> 单值导出让使用者直接拿到"那个东西"，当模块语义就是"一个配置/一个连接"时比命名空间更自然。

**速记**：单值 **整体赋值替换**。



#### 导出类

**类导出**：用 module.exports = 类，使模块本身是可实例化的构造器。

```js
// Person.js
class Person {
  constructor(name) { this.name = name; }
  say() { return `我是 ${this.name}`; }
}
module.exports = Person;
```

```js
const Person = require("./Person");
console.log(new Person("why").say()); // "我是 why"
```

> 导出类务必用 module.exports = 类 而非 exports = 类，否则切断与返回值的联系（赋值失效详见上一篇）。

**速记**：导出类 **模块本身即构造器**。



#### 导出函数

**函数导出**：用 module.exports = 函数，让模块本身是可调用入口，常见于中间件或工厂。

```js
// createServer.js
module.exports = function createServer(options) {
  return { options, start() { return "started"; } };
};
```

```js
const createServer = require("./createServer");
console.log(createServer({ port: 8080 }).start()); // "started"
```

> 函数导出适合"模块即能力"的场景，与类导出的区别是使用者拿到函数而非类，调用语义不同。

**速记**：导出函数 **模块本身即可调用**。



#### 混合写法

**混合导出**：在 module.exports 上既整体挂载主行为，又补充辅助成员，适合"主能力加工具集"的模块。

```js
// stringUtil.js
function trim(text) { return text.trim(); }
module.exports = trim;                    // 主能力
module.exports.capitalize = (t) => t[0].toUpperCase() + t.slice(1);
```

```js
const trim = require("./stringUtil");
console.log(trim("  hi  ")); // "hi"
console.log(trim.capitalize("hello")); // "Hello"
```

> 混合写法必须先 module.exports = 主值再挂属性；若先挂载再整体替换，前面属性会被覆盖丢失。



### require 的导入用法

**速记**：混合 **主体加辅助，主次同出**。

#### 解构导入

**解构导入**：在 require 同时用对象解构取出所需成员，减少中间变量、调用更简洁。

```js
const { add, sub } = require("./utils");
console.log(add(2, 1)); // 3
```

> 解构导入前提是对方确导出这些命名属性；若用 module.exports = 函数 整体导出，则只能整体接收。

**速记**：解构 **require 同时取名**。



#### 省略扩展名

**省略扩展名**：require 允许不写 .js、.json、.node，由 Node 按既定顺序补全探测。

```js
const config = require("./config"); // 实际可能解析为 ./config.js
```

> 省略扩展名提升简洁度但增加文件探测次数，追求性能时显式写扩展名更稳妥。

**速记**：后缀 **可省，按序补全**。



#### 导入 JSON 文件

**JSON 导入**：CommonJS 原生支持 require 直接加载 .json，返回解析后的对象，常用于配置。

```js
const setting = require("./setting.json");
console.log(setting.theme); // 读取 JSON 字段
```

> 导入 JSON 时 Node 会读取并 JSON.parse，无需手动解析，是配置管理几乎都依赖的能力。

**速记**：JSON **原生支持，得解析后对象**。



#### 导入目录时的查找规则

**目录导入**：require 指向目录而非文件时，Node 在该目录内按规则确定入口。

- 读目录 package.json 的 **main 字段**作为入口。
- 无 main 或文件缺失则默认加载目录 **index.js**。
- 再缺失抛出找不到模块错误。

```js
const lib = require("./lib"); // 等价 require("./lib/index.js")
```

> 目录导入让"一个文件夹就是一个子模块"，对外只暴露文件夹名；main 失灵回退 index.js 是约定俗成的兜底。



### require 的查找规则

**速记**：目录 **先看 main，再看 index**。

#### 核心模块的查找

**核心模块**：Node 内置、编译进二进制的模块（如 fs、path、http），require 优先且最快命中，不读文件系统。

- 标识不带路径前缀（如 "fs"），直接匹配内置名。
- 同名时核心模块**优先级最高**，用户文件无法覆盖。

```js
const fs = require("fs"); // 命中内置，不会去磁盘找 fs.js
```

> 核心模块预编译使加载几乎零成本，require("fs") 永远不会意外加载项目里自写的 fs.js。

**速记**：核心模块 **内置优先，无需寻盘**。



#### 第三方模块与 node_modules 逐级向上

**第三方模块**：裸名且非内置的模块（如 "lodash"），Node 从当前目录起逐级向上在 node_modules 查找。

- 从当前文件目录的 node_modules 开始。
- 找不到则进上层目录的 node_modules，直至文件系统根。
- 命中后按目录导入规则确定入口。

```js
const lodash = require("lodash"); // 向上找到 /project/node_modules/lodash
```

> 逐级向上是 npm 扁平或嵌套安装都能工作的基础，换来得"任意深度文件都能引用根 node_modules"的便利。

**速记**：裸名 **逐级向上找 node_modules**。



#### require.cache 的结构

**模块缓存**：require.cache 是以模块绝对路径为键、module 对象为值的对象，记录已加载模块避免重复执行。

- 键是解析后的**绝对路径字符串**。
- 值是被编译执行的 **Module 实例**（含 exports、loaded 等）。
- 同一路径再次 require 直接返回缓存中的 exports。

```js
const path = require.resolve("./config");
console.log(typeof require.cache[path]); // "object"
```

> 缓存键用绝对路径而非相对标识，不同位置 require 同一文件得到完全相同缓存实例，是"同一模块只执行一次"的实现所在。

**速记**：缓存 **绝对路径为键，module 为值**。



#### 路径解析伪代码

**解析流程**：require 内部可抽象为"先判核心、再找文件、后查目录、并逐级向上"的算法。

```js
function resolve(request, parent) {
  if (isCoreModule(request)) return coreLoad(request);
  const lookup = nodeModulesPaths(parent.path);
  for (const base of [dirName(parent.filename), ...lookup]) {
    const file = tryFile(join(base, request)) ||
                 tryExtensions(join(base, request), [".js", ".json", ".node"]);
    const dir = file ? null : tryDirectory(join(base, request));
    if (file || dir) return file || dir;
  }
  throw new Error("Cannot find module " + request);
}
```

> 该伪代码概括查找主链路：核心模块短路，文件模块补扩展名，目录模块走 main/index，全程在 node_modules 链重复。



### 模块的加载过程

**速记**：解析顺序 **核心、文件、目录、向上**。

#### 路径解析

**路径解析**：加载第一步，把 require 标识换算成磁盘绝对路径，决定去哪读文件。

- 输入：模块标识（核心名、相对/绝对路径、目录名）。
- 输出：可被文件系统定位的**绝对路径**。

```js
console.log(require.resolve("./config")); // /project/config.js
```

> 解析失败直接抛 Cannot find module；require.resolve 可单独探测模块是否存在而不真正加载。

**速记**：第一步 **标识换绝对路径**。



#### 文件定位

**文件定位**：拿到路径后确定具体读哪个文件，包括补扩展名与目录入口判定。

- **精确文件**：路径直接指向存在文件则加载它。
- **补扩展名**：依次尝试 .js、.json、.node。
- **目录入口**：指向目录读 package.json 的 main，否则 index.js。

> 定位每多一次试探就多一次磁盘访问，显式写扩展名能让 Node 跳过补扩展名步骤，定位更快更确定。

**速记**：第二步 **补后缀、定入口**。



#### 编译执行

**编译执行**：Node 读取文件内容，用模块包装函数包裹后运行，结果写入 module.exports。

- .js 作为 JavaScript 编译执行。
- .json 读取后 JSON.parse 并直接作为 exports。
- .node 作为编译好的插件加载。

> 编译执行是"代码变成模块"的瞬间，包装函数注入五个参数从而产生模块作用域（详见上一篇相关章节）。

**速记**：第三步 **包装函数包裹后执行**。



#### 加入缓存

**加入缓存**：模块编译执行成功后，Node 以绝对路径为键存入 require.cache 供复用。

```js
require.cache[module.filename] = module; // 内部逻辑示意
```

> 缓存写入在执行成功之后；若中途抛错则不入缓存，下次 require 重新尝试，错误模块不会"半缓存"。

**速记**：第四步 **按绝对路径写入缓存**。



#### js、json、node 三类扩展名

**扩展名处理**：Node 对 .js、.json、.node 有专门编译分支。

- **.js**：当 JavaScript 源码包裹编译执行。
- **.json**：读文本并 JSON.parse，结果直接作 exports。
- **.node**：由 C++ 编译的插件，经 dlopen 加载为导出对象。

```js
require("./data.json");   // JSON 分支
require("./native.node"); // 插件分支
```

> 同文件名不同扩展名视为不同模块（缓存键不同），日常最常用 .js 与 .json，.node 多见于原生扩展。



### 模块缓存机制

**速记**：三类后缀 **各走各的编译分支**。

#### 同一模块只执行一次

**单次执行**：无论被 require 多少次，同一绝对路径模块只编译执行一次，后续返回已缓存的 exports。

```js
// counter.js
let n = 0;
module.exports = { tick() { return ++n; } };
// main.js
const a = require("./counter");
const b = require("./counter"); // 不重新执行
a.tick();
console.log(b.tick()); // 2，共享同一状态
```

> 单次执行保证性能与状态一致：初始化代价只付一次，副作用（打印、建连接）也只在首次发生。

**速记**：**只执行一次，其后皆取缓存**。



#### require.cache 的结构

**缓存结构**：require.cache 是对象，键为模块绝对路径，值为对应 Module 实例。

- **键**：解析后的绝对路径字符串。
- **值**：Module 实例，含 id、exports、loaded、children 等。
- **清空**：delete require.cache[path] 可移除某项。

```js
const id = require.resolve("./config");
console.log(require.cache[id].loaded); // true
```

> 缓存与 module 对象一一对应，通过它既能读导出又能查加载状态与依赖树，是调试循环依赖的常用入口。

**速记**：缓存项 **键是绝对路径，值是 Module 实例**。



#### 删除缓存实现热加载

**热加载**：删除 require.cache 对应项后再次 require，Node 重新编译执行该模块，常用于开发期不重启刷新配置。

```js
const path = require.resolve("./config");
delete require.cache[path];
const config = require("./config"); // 本次重新执行
```

> 热加载适合配置变更、插件开发；仅删目标缓存不够时还要递归删其 children 缓存，否则旧依赖仍复用造成"半热"状态。



### exports 与值的绑定

**速记**：热加载 **删缓存项再 require**。

#### 对象属性的引用语义

**对象引用**：导出对象、数组或类实例时，require 拿到的是**同一引用**，模块内部改属性对所有导入方可见。

```js
const state = { count: 0 };
module.exports = state;
require("./state").count += 1;
console.log(require("./state").count); // 1，已变化
```

> 引用语义意味着"导出容器非快照"，任一导入方改容器属性都会扩散，既是便利（共享状态）也是风险（意外耦合）。

**速记**：对象是 **同一引用，改属性互见**。



#### 基本类型值的拷贝

**基本类型拷贝**：module.exports 是基本类型（数字、字符串、布尔等）时，require 拿到的是该值的拷贝式绑定，模块后续再改不影响已导入方。

```js
// version.js 初始 module.exports = 1
const v = require("./version"); // 1
// 模块内部改为 2 后，v 仍为 1
```

> 基本类型"拷贝"本质是不可变性：旧引用绑原值，模块换绑新值不回溯影响，与对象引用共享形成对照。

**速记**：基本类型 **值拷贝，后变不可见**。



#### 想要获取变化的值必须导出 getter 或对象

**获取变化**：希望导入方总能读实时值，应导出**对象属性**或**getter 函数**，而非一次性基本类型。

```js
let count = 0;
module.exports = { getCount() { return count; }, inc() { count += 1; } };
const m = require("./m");
m.inc();
console.log(m.getCount()); // 1，总是最新
```

> 用函数/getter 把"读值"变成实时调用，规避基本类型拷贝带来的陈旧问题。口诀：**要实时导出对象或函数，要快照才导出基本类型**。



### require.main 与入口模块

**速记**：要实时值 **导出对象或 getter**。

#### 判断当前是否为入口文件

**入口判断**：用 require.main === module 可判断当前模块是不是被直接执行的入口，还是被别的模块引入。

```js
if (require.main === module) {
  console.log("被 node app.js 直接运行");
} else {
  console.log("被其他模块引入");
}
```

> 该写法常用于"既能当库引入又能当脚本跑"的模块：自测或启动逻辑放进 if 分支，被引入时不触发。

**速记**：入口判断 **require.main === module**。



#### 竞争条件与 module.id

**入口标识**：入口模块的 module.id 为 "."（圆点），被引入模块 id 为解析后的绝对路径，二者构成判断的竞争条件。

- **入口模块**：require.main 指向自身，module.id 为 "."。
- **被引入模块**：require.main 指向调用方，module.id 为绝对路径。

```js
console.log(module.id === "."); // 入口为 true
```

> require.main === module 是官方推荐；module.id === "." 是其等价表现，都依赖"入口 id 为点、被引 id 为路径"的约定。



### 循环依赖问题

**速记**：入口 id 是 **点号**。

#### CommonJS 循环加载处理机制

**循环依赖**：指 A 引入 B、B 又引入 A 的相互引用。CommonJS 处理机制是"**先返回已部分构建的 exports**"，而非报错或死等。

- 加载 A 执行到 require(B) 转去加载 B。
- B 中又 require(A)，此时 A 未完成，直接拿到 A **当前 exports 对象**（可能仅部分属性）。
- B 执行完回 A 继续，A 后续挂载属性之后才补全。

```js
// a.js
exports.done = false;
const b = require("./b");
exports.done = true;
// b.js
exports.done = false;
const a = require("./a"); // 拿到 a 的半成品 exports
console.log("在 b 中，a.done =", a.done); // false
exports.done = true;
```

> 循环加载不崩溃，因为 CommonJS 在 A 未完成时就返回其 exports 引用，B 拿到的"半填充"对象读到的是旧值。

**速记**：循环 **先占位、后补全**。



#### 未执行完时导出的是半成品

**半成品 exports**：循环加载瞬间，后加载方拿到的 exports 只含对方**已执行到当前行**前挂载的属性，缺失后续部分。

```text
在 b 中，a.done = false   // 此时 a 还没执行到 exports.done = true
b 结束
在 a 中，b.done = true
a 结束
```

> a.done 为 false 正是半成品的直观证据——属性缺失因执行尚未到达，而非未导出。

**速记**：循环瞬间拿到的是 **半成品 exports**。



#### 代码示例演示

**完整演示**：用入口文件串联 a 与 b，观察最终拿到的是完整对象。

```js
// main.js
const a = require("./a");
const b = require("./b"); // 已缓存直接返回
console.log("a.done =", a.done, "b.done =", b.done); // a.done = true b.done = true
```

> 加载途中出现过半成品，加载结束后两模块 exports 都已补全，main 中看到完整正确值；坑在于**加载途中**读取可能是旧值。

**速记**：演示 **入口串联 a、b，终得完整对象**。



#### 如何避免循环依赖

**避免手段**：从根本上消除相互引用，或把共享状态下沉，可规避半成品风险。

- **重构拆分**：把 A、B 共同依赖部分抽到独立第三模块 C，A、B 都引 C。
- **延迟引用**：把 require 放进函数体，待真正调用时再加载，避开初始化期循环。
- **使用对象引用**：导出对象并改其属性，而非依赖初始化期读对方基本类型值。

```js
function useB() {
  const b = require("./b"); // 调用时才加载
  return b.doSomething();
}
module.exports = { useB };
```

> 延迟引用利用"函数执行晚于模块初始化"把循环拆到运行时，往往能绕开半成品问题；治本仍靠拆分依赖、降低耦合。



### CommonJS 的局限

**速记**：避循环 **消除互引、状态下沉**。

#### 同步加载不适合浏览器

**同步局限**：require 是阻塞式同步加载，浏览器需从网络逐文件下载，同步会卡住解析与渲染。

- **服务端**：本地磁盘随机读极快，同步等待可忽略。
- **浏览器**：网络延迟高，同步冻结页面，须先下载完才能执行。

> 该局限直接催生 AMD 等异步方案，最终由语言层 ESM 以静态、可异步加载结构统一解决，CommonJS 始终是服务端友好设计。

**速记**：浏览器 **同步下载卡渲染**。



#### 无法静态分析与 tree shaking

**静态分析缺失**：CommonJS 导入导出发生在运行时，模块标识可为任意表达式，工具无法编译期确定依赖图。

- 打包器难判断哪些导出被使用，无法安全删未用代码。
- **tree shaking** 依赖静态结构，CommonJS 基本无法受益。

```js
const name = "u" + "tils"; // 运行期才确定的标识，静态分析无能为力
const utils = require(name);
```

> ESM 的 import/export 是静态语法，编译期即可建完整依赖图从而精准摇树；CommonJS 的灵活性（动态标识）正是不受静态优化的根源。

**速记**：运行时决定，故 **无法 tree shaking**。



#### 由此引出 ESM

**ESM 登场**：为兼顾浏览器与服务端并支持静态优化，ES2015 引入原生模块 ES Module（import/export）。

- **静态结构**：编译期可分析依赖、做 tree shaking。
- **异步友好**：语言层支持按需加载，天然适配浏览器。
- **统一生态**：前后端同一套模块语法。

```js
import { add } from "./utils.js";
export const sum = (a, b) => add(a, b);
```

> Node 现已同时支持 CommonJS 与 ESM（.mjs 或 type:module）。迁移 ESM 时 __dirname、require、module.exports 不再可用，需改用 import.meta.url 与 import/export（详见上一篇相关说明）。

**速记**：ESM 用 **静态结构换可优化**。
