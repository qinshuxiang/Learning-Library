## crypto 加密与安全

### crypto 模块定位

#### crypto 是封装 OpenSSL 的内置加密模块

**crypto 模块**：是 Node.js 的**内置模块**，无需安装第三方包即可直接引入，底层能力来自 **OpenSSL** 库。

- 它覆盖哈希、HMAC、对称加密、非对称加密、数字签名、随机数等密码学能力。
- 引入方式为 **const crypto = require("crypto")**，随 Node 一起发布，版本与 Node 的 OpenSSL 绑定。
- 它提供的是**底层原语**，高层封装（如 JWT、bcrypt 库）往往也建立在它或同类算法之上。

```js
const crypto = require("crypto");
console.log(crypto.getRandomValues ? "Web Crypto 可用" : "使用传统 crypto");
```

> crypto 与 Web Crypto API 并存：传统 crypto 模块 API 以回调与同步为主，浏览器同源的 Web Crypto 以 Promise 为主；两者算法底层一致，业务可按运行环境选择。

**速记**：crypto 是**内置模块**，能力来自 **OpenSSL**。



### 三类算法的区分

#### 哈希是不可逆的摘要算法

**哈希（Hash）**：是**单向不可逆**的摘要算法，把任意长度输入压缩成**定长输出**，无法从摘要反推原文。

- 输入相同则输出**恒定相同**；输入改动一位，输出**面目全非**（雪崩效应）。
- 典型算法有 **sha256、sha512**，不安全的 **md5、sha1** 已不应用于安全场景。
- 用途集中在**完整性校验、口令派生、去重**，它本身不保密，只保证"未被改动"。

> 哈希的"不可逆"指计算上无法反推，但**相同输入永远得到相同输出**，因此直接用哈希存密码仍会被彩虹表反查，需结合盐与慢哈希。

**速记**：哈希**单向定长**，只验**完整性不保密**。



#### 对称加密用同一把密钥加解密

**对称加密（Symmetric）**：是**加解密使用同一把密钥**的算法，速度快，适合加密大量数据。

- 加密方用密钥把明文变密文，解密方用**同一把密钥**还原明文。
- 典型算法有 **aes-128、aes-192、aes-256**，以分组方式工作，需配合模式与初始化向量。
- 核心难点是**密钥的安全分发**：通信双方如何在不安全的信道上共享同一把密钥。

> 对称加密的保密性完全依赖密钥保密；一旦密钥泄露，所有密文都能被还原，因此密钥绝不能硬编码进代码库。

**速记**：对称加密**一把密钥**，快但**难分发**。



#### 非对称加密用公钥私钥配对

**非对称加密（Asymmetric）**：是**公钥私钥成对**的算法，公钥加密的内容只能由私钥解密，反之亦然。

- 公钥可公开分发，私钥必须保密；用**公钥加密**只有对应**私钥**能解。
- 典型算法有 **rsa、ecdsa、ed25519**，其中 rsa 既可用于加密也可用于签名。
- 运算比对称加密**慢得多**，通常用于**小数据加密与密钥交换**，不直接加密大文件。

> 非对称加密解决的是"无需预先共享密钥"的信任问题；它常把对称密钥用公钥加密后传给对方，后续大数据仍走对称加密。

**速记**：非对称**公私钥配对**，慢而**易分发**。



#### 三类算法的典型用途对照

**用途对照**：三类算法并非互斥，实际系统常**组合使用**，各司其职。

- **哈希**：文件完整性校验、口令派生、内容去重、区块链记账。
- **对称加密**：磁盘加密、数据库字段加密、会话数据加密等大数据量场景。
- **非对称加密**：HTTPS 握手交换对称密钥、数字签名验明身份、加密短消息。

```text
场景          推荐算法          保密性     可逆性
完整性校验    sha256           不保密     不可逆
口令存储      scrypt / bcrypt  不保密     不可逆（加盐）
大数据加密    aes-256-gcm      保密       可逆（需密钥）
密钥交换      rsa              保密       可逆（公钥私钥）
数字签名      rsa + sha256     不保密     可验证
```

> 上表把"保密性"与"可逆性"拆开看：哈希与签名不保密只验真，加密才保密；选型时先问"要不要还原原文"。

**速记**：哈希验真、对称加密、非对称交换与签名。



### 哈希摘要与文件校验

#### createHash 的链式用法

**createHash(algorithm[, options])**：是创建哈希对象的入口，参数为算法名（如 **sha256**），返回可链式调用的 **Hash** 对象。

- 先以 **crypto.createHash("sha256")** 创建对象，再以 **update(data[, encoding])** 喂入数据，可多次调用 update 累积。
- 最后以 **digest([encoding])** 收尾并产出摘要；digest 只能调用一次，再次调用会报错。
- update 的 encoding 指输入数据的编码，digest 的 encoding 指输出格式（hex、base64、latin1）。

```js
const crypto = require("crypto");

const hash = crypto.createHash("sha256")
  .update("hello")
  .update(" world") // 可多次累积，等价于一次喂入 "hello world"
  .digest("hex");

console.log(hash); // 64 位十六进制字符串，定长输出
```

> digest 一旦调用，Hash 对象即报废；若需对另一段数据哈希，必须重新 createHash。update 不返回新对象，而是返回自身以支持链式写法。

**速记**：createHash 起手，update 喂料，digest 收尾。



#### digest 编码与哈希的核心性质

**digest([encoding])**：决定摘要以何种**可打印编码**输出，不传则返回 **Buffer**；哈希本身有三条不可动摇的性质。

- 输出编码常用 **hex（十六进制）与 base64**，前者每字节两位、后者更紧凑；缺省返回原始字节 Buffer。
- **同一输入恒定输出**：相同明文两次哈希结果完全一致，便于比对。
- **任意长度输入定长输出**：无论原文 1 字节还是 1 GB，sha256 永远输出 32 字节。
- **不可逆**：摘要丢掉原文信息，数学上无法还原。

```js
const crypto = require("crypto");

const a = crypto.createHash("sha256").update("x").digest(); // Buffer，32 字节
const b = crypto.createHash("sha256").update("x").digest("hex");
const c = crypto.createHash("sha256").update("x").digest("base64");
console.log(a.length, b.length, c.length);
```

> 定长输出意味着哈希会"压缩"信息，必然存在碰撞可能，但**强哈希算法的碰撞在计算上不可寻**；md5、sha1 已被找到实际碰撞，故禁止用于安全用途。

**速记**：恒定、定长、不可逆，三性定哈希。



#### 文件完整性校验

**完整性校验**：把下载或存储的文件哈希，与官方公布的摘要比对，一致则说明**文件未被篡改、传输无误**。

- 计算文件哈希需先**读取全部字节**再 update，大文件可流式分块 update 后 digest。
- 比对时比较**摘要字符串**而非逐字节，既快又抗干扰。
- 官方常提供 **sha256sum** 一类清单，下载后用其值核对发布物。

```js
const crypto = require("crypto");
const fs = require("fs");

function fileHash(path) {
  const hash = crypto.createHash("sha256");
  const stream = fs.createReadStream(path);
  return new Promise((resolve, reject) => {
    stream.on("data", (chunk) => hash.update(chunk));
    stream.on("end", () => resolve(hash.digest("hex")));
    stream.on("error", reject);
  });
}
```

> 完整性校验防的是"被动损坏与篡改"，不防"主动伪造官方摘要"——若攻击者同时替换了文件与公布的摘要，哈希无能为力，此时需数字签名背书。

**速记**：文件哈希对官方摘要，一致即未改。



### 密码存储与慢哈希

#### 用 sha256 存密码仍不安全

**哈希存密码的误区**：仅用 **sha256(密码)** 入库，看似不可逆，实则**仍可被高效反查**，绝不是安全做法。

- 相同密码产生**相同摘要**，攻击者可预计算"密码到摘要"的**彩虹表**批量反查。
- 现代 GPU 每秒可试**数十亿**次哈希，弱口令在极短时间内被爆破。
- 没有盐的哈希等于"把字典排序好供人查"，攻击者无需逐站破解。

> [!WARNING]
> **警告内容**：用 sha256、md5、sha1 等**快哈希直接存密码**属于高危做法，可被彩虹表与 GPU 集群轻易爆破。凡密码存储，必须加盐且使用慢哈希。

**速记**：快哈希存密码，**彩虹表可破**。



#### 慢哈希保护密码

**慢哈希（Slow Hash）**：是专门**故意放慢、并强制加盐**的口令派生算法，让爆破成本居高不下。

- 它通过**大量迭代或占内存**抬高单次计算成本，使批量爆破在经济上不可行。
- 主流选择有 **bcrypt、scrypt、argon2**，三者都内建盐机制，无需手工拼接。
- 慢哈希仍不可逆，但比快哈希多出"**每个密码独立盐 + 计算昂贵**"两道防线。

```js
// 概念示意：慢哈希相对快哈希多出了"盐"与"成本参数"
// bcrypt 摘要形如 $2b$12$<salt><hash>，前缀即成本与盐
```

> 密码学里"慢"是优点：登录只需算一次，攻击者却要算亿万次；把单次耗时从微秒级抬到百毫秒级，爆破难度指数上升。

**速记**：慢哈希**加盐加成本**，爆破不划算。



#### crypto.scrypt 是内置的慢哈希

**scrypt**：是 Node 内置的**口令派生函数**，属于慢哈希家族，无需额外依赖即可用于密码存储。

- 调用形式为 **crypto.scrypt(password, salt, keylen[, options], callback)**，同步版为 **crypto.scryptSync(password, salt, keylen[, options])**。
- 它**刻意消耗内存**以抵抗专用硬件爆破，比单纯多次 sha256 更抗衡。
- keylen 指定派生出的密钥字节数（如 64），salt 必须由随机源生成，不可固定。

```js
const crypto = require("crypto");

const salt = crypto.randomBytes(16);
crypto.scrypt("userPassword", salt, 64, (err, derivedKey) => {
  if (err) throw err;
  console.log(derivedKey.toString("hex")); // 派生出的定长密钥
});
```

> scrypt 虽内置，但**参数选择**影响安全：keylen 过小、salt 过短、成本过低都会削弱防护；生产建议参考 OWASP 当期推荐的工作因子。

**速记**：scrypt 是**内置慢哈希**，凭盐与成本抗爆破。



### HMAC 消息认证码

#### createHmac 需要密钥

**HMAC**：是带**密钥的哈希消息认证码**，在哈希之上引入密钥，用于同时验证**完整性与来源**。

- 创建方式为 **crypto.createHmac(algorithm, key[, options])**，algorithm 如 sha256，key 为密钥（字符串或 Buffer）。
- 之后同样链式 **update(data)** 再 **digest([encoding])** 得到带密钥的摘要。
- 没有密钥的人即使知道算法，也**无法伪造**合法的 HMAC 值。

```js
const crypto = require("crypto");

const hmac = crypto.createHmac("sha256", "shared-secret")
  .update("message-body", "utf8")
  .digest("hex");

console.log(hmac); // 只有持有密钥者才能算出相同值
```

> HMAC 的密钥应与通信双方**安全共享**，且不同于用于加密的密钥；密钥泄露等同于失去来源验证能力。

**速记**：HMAC = **哈希 + 密钥**，验真又验源。



#### 与单纯哈希的区别

**HMAC 与哈希的区别**：普通哈希只防篡改不防伪造，HMAC 额外防"无密钥者伪造"。

- 普通哈希任何人都能计算，攻击者可改内容后**重新算哈希**一并替换。
- HMAC 因含密钥，攻击者在**没有密钥**时无法生成匹配的认证码，篡改即被发现。
- 二者都不可逆、都定长，差别只在"**是否有密钥参与**"。

```js
const crypto = require("crypto");

const data = "transfer 100";
const plain = crypto.createHash("sha256").update(data).digest("hex"); // 任何人可算
const mac = crypto.createHmac("sha256", "k").update(data).digest("hex"); // 需密钥
```

> 把 HMAC 当"带密码的哈希"理解最直观：它回答两个问题——内容改了吗（完整性）、这真是对方发的吗（来源认证）。

**速记**：哈希只验改，HMAC 还验**谁发的**。



#### Webhook 签名验证场景

**Webhook 验证**：支付或平台回调常把 **HMAC 签名放在请求头**，服务端用同一密钥重算并比对，确认请求真实未被篡改。

- 平台用密钥对请求体算 HMAC，放入如 **X-Signature** 头；服务端收到后用同样密钥、同样算法重算。
- 比对必须用**恒定时间比较**（timingSafeEqual），避免时序侧信道泄露。
- 算法与密钥由平台文档规定，常见 **sha256 + 十六进制签名**。

```js
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const expected = crypto.createHmac("sha256", secret)
    .update(rawBody, "utf8")
    .digest("hex");
  const a = Buffer.from(signatureHeader, "hex");
  const b = Buffer.from(expected, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

> Webhook 验签的前提是**密钥仅服务端持有**且走 HTTPS；明文 HTTP 下签名可被中间人重算替换，传输层加密与签名验证须同时具备。

**速记**：Webhook 验签 = **重算 HMAC 比对头**。



### 密码学安全的随机数

#### randomBytes 生成随机字节

**randomBytes(size[, callback])**：生成**密码学安全**的随机字节，返回 Buffer，适合做令牌、盐、密钥材料。

- 同步版 **crypto.randomBytes(size)** 直接返回 Buffer；回调版第二个参数为 (err, buf) => {}。
- 它取自系统的**密码学安全随机数发生器（CSPRNG）**，不可预测、不可重现。
- 典型用途：生成会话令牌、盐、初始化向量、一次性验证码。

```js
const crypto = require("crypto");

const token = crypto.randomBytes(32).toString("hex"); // 64 位十六进制令牌
console.log(token);
```

> 把 randomBytes 的字节转 hex 或 base64 即成可读字符串；长度按安全需求取，令牌常用 16 到 32 字节。

**速记**：randomBytes 出**安全随机字节**。



#### randomUUID 与 randomInt

**randomUUID([options])** 与 **randomInt([min, ]max[, callback])**：分别生成标准 UUID 与指定区间的随机整数，底层同样安全。

- **randomUUID()** 返回标准 v4 的 UUID 字符串，常用于分布式主键、请求追踪号。
- **randomInt(min, max)** 返回 **[min, max)** 左闭右开的随机整数；只传一个参数时视为 max，min 默认为 0。
- 二者都基于 CSPRNG，可放心用于安全场景，无需自己用 Math.random 拼装。

```js
const crypto = require("crypto");

console.log(crypto.randomUUID());     // 标准 UUID v4
console.log(crypto.randomInt(0, 100)); // 0 到 99 的随机整数
```

> randomInt 的区间语义是"含下不含上"，与多数语言的左闭右开一致；需要含上界时把 max 加一传入。

**速记**：randomUUID 给标识，randomInt 给区间整数。



#### 与 Math.random 的本质区别

**Math.random 的局限**：它是**伪随机、可预测**的生成器，仅供展示与游戏，绝不能用于任何安全用途。

- Math.random 的算法与种子不保证不可预测，历史上曾多次被证明可被还原序列。
- 用它生成令牌、盐、密钥，等于把机密交给**可推算**的序列，攻击者可能复现。
- 凡涉安全，一律用 **crypto.randomBytes、randomUUID、randomInt** 这类 CSPRNG 来源。

> [!CAUTION]
> **注意内容**：切勿用 Math.random 生成密码、令牌、盐或密钥材料；它的输出可被预测，用作安全随机会直接酿成泄露。

**速记**：安全随机用 **crypto**，展示才用 **Math.random**。



### 对称加密 AES 与加密模式

#### createCipheriv 与 createDecipheriv 签名

**createCipheriv(algorithm, key, iv[, options])** 与 **createDecipheriv(algorithm, key, iv[, options])**：是对称加解密的入口，二者签名一致，算法、密钥、初始化向量三个参数必须对应。

- 加密方用 createCipheriv 得到 **Cipher**，解密方用 createDecipheriv 得到 **Decipher**。
- 数据经 **cipher.update(data, inputEncoding, outputEncoding)** 处理，再以 **cipher.final(outputEncoding)** 收尾。
- 解密必须提供**与加密完全相同的算法、密钥、IV**，否则 final 抛错或解出乱码。

```js
const crypto = require("crypto");

const algorithm = "aes-256-cbc";
const key = crypto.randomBytes(32);
const iv = crypto.randomBytes(16);

const cipher = crypto.createCipheriv(algorithm, key, iv);
let encrypted = cipher.update("敏感数据", "utf8", "hex");
encrypted += cipher.final("hex");
```

> update 的 inputEncoding 指明文编码，outputEncoding 指密文编码；不传编码则 update 返回 Buffer。final 之后 Cipher 即报废，不可再用。

**速记**：Cipheriv 加密，Decipheriv 解密，三参须一致。



#### 密钥长度与 IV 要求

**密钥与 IV 长度**：aes 的密钥长度由算法名末尾数字决定，IV 长度固定为**分组长度 16 字节**。

- aes-128 需 **16 字节**密钥，aes-192 需 24 字节，aes-256 需 **32 字节**；长度不符直接抛错。
- IV（初始化向量）固定 **16 字节**，决定同明文每次加密出不同密文，本身**无需保密但必须随机且唯一**。
- IV 不保密但**绝不可复用**：同一密钥下重复 IV 会泄露明文规律，故每次加密都要重新 randomBytes。

```js
const crypto = require("crypto");

const key = crypto.randomBytes(32);  // aes-256 要求 32 字节
const iv = crypto.randomBytes(16);   // IV 恒为 16 字节，每次随机
console.log(key.length, iv.length); // 32 16
```

> 解密时 IV 必须与加密时相同，因此实践中常把 IV **拼接在密文之前**一同传输；由于 IV 不保密，明文放在一起也无妨。

**速记**：aes-256 密钥 32 字节，IV 恒 16 且每次随机。



#### 加密模式与填充选择

**加密模式**：决定分组如何链接、是否带认证，选错模式会**直接破坏安全性**；填充处理分组不足一块的情况。

- **CBC 模式**：需 IV，是最常用的经典模式，但**只保证机密性、不防篡改**，需额外 HMAC 或换 GCM。
- **GCM 模式**：同时提供**机密性与完整性认证**，加密后调用 **cipher.getAuthTag()** 取认证标签，解密前用 **decipher.setAuthTag(tag)** 校验。
- **ECB 模式**：**不安全**，相同明文块产生相同密文块，会暴露结构，禁止使用。

> [!WARNING]
> **警告内容**：ECB 模式因相同明文块生成相同密文块而**泄露数据模式**，严禁用于任何真实加密。已废弃的 createCipher 与 createDecipher（无显式 IV、从密码推导密钥）同样不要使用，应一律改用带 iv 的 createCipheriv。

```js
const crypto = require("crypto");

const key = crypto.randomBytes(32);
const iv = crypto.randomBytes(16);

// GCM：加密后取认证标签
const cipher = crypto.createCipheriv("aes-256-gcm", key, iv);
let enc = cipher.update("敏感数据", "utf8", "hex");
enc += cipher.final("hex");
const tag = cipher.getAuthTag();

// GCM：解密前设回认证标签
const decipher = crypto.createDecipheriv("aes-256-gcm", key, iv);
decipher.setAuthTag(tag);
let dec = decipher.update(enc, "hex", "utf8");
dec += decipher.final("utf8");
```

> GCM 的认证标签在加密**完成之后**才可用（final 之后取），解密**之前**必须 setAuthTag，顺序错会抛错；标签被篡改时 final 会拒绝输出，天然防篡改。

**速记**：CBC 只保密、GCM 带认证、ECB 禁用。



### 密码加盐哈希实践

#### 用 randomBytes 生成盐

**盐（Salt）**：是每段密码**随机且唯一**的附加数据，使相同密码产生不同摘要，彻底瓦解彩虹表。

- 盐用 **crypto.randomBytes(16)** 生成 16 字节，转 hex 或 base64 后与派生密钥一同存储。
- 盐**不需要保密**，但必须每用户、每次注册都重新生成，绝不复用常量盐。
- 校验时从存储中读回盐，用同一盐重新派生再比对，因此盐必须随记录持久化。

```js
const crypto = require("crypto");

const salt = crypto.randomBytes(16).toString("hex"); // 每用户独立盐
console.log(salt);
```

> 盐的意义在于"让预计算失效"：攻击者不能再靠一张全局彩虹表通吃所有用户，而必须针对每个盐单独计算，成本陡增。

**速记**：盐**每用户随机**，破彩虹表的预计算。



#### scrypt 回调与同步用法

**scrypt 的两种形态**：同步版 **scryptSync** 阻塞事件循环、适合脚本；回调版 **scrypt** 不阻塞，适合服务。

- 同步：**crypto.scryptSync(password, salt, keylen)** 直接返回派生密钥 Buffer。
- 回调：**crypto.scrypt(password, salt, keylen, (err, derivedKey) => {})**，避免大成本计算卡住单线程。
- keylen 为输出字节数，常用 64；生产可加 options 调高成本参数进一步提升抗性。

```js
const crypto = require("crypto");

// 同步用法
const derived = crypto.scryptSync("password", "salt", 64);
console.log(derived.toString("hex"));

// 回调用法（服务推荐，不阻塞）
crypto.scrypt("password", "salt", 64, (err, key) => {
  if (err) throw err;
  console.log(key.toString("hex"));
});
```

> 在服务端处理登录时，scrypt 的昂贵计算若用同步版会**阻塞事件循环**影响并发；高吞吐场景应优先回调或 worker 线程执行。

**速记**：脚本用 Sync，服务用**回调不阻塞**。



#### timingSafeEqual 恒定时间比较

**timingSafeEqual(a, b)**：以**恒定时间**比较两个 Buffer 是否相同，防止比较耗时泄露密钥信息。

- 普通 **=== 或循环逐字节比较**会因"首个不同字节即返回"而暴露差异位置，形成时序侧信道。
- 它要求两参数**长度必须一致**，否则直接抛错；不等长本就说明不匹配。
- 用于比对派生密钥、HMAC、签名等敏感等值场景，避免被测量耗时反推。

```js
const crypto = require("crypto");

const a = Buffer.from("expect");
const b = Buffer.from("expect");
const c = Buffer.from("guess1");
console.log(crypto.timingSafeEqual(a, b)); // true
console.log(crypto.timingSafeEqual(a, c)); // false（长度须相等，否则抛错）
```

> timingSafeEqual 仅防时序攻击，不替代"先比长度"的判空；两 Buffer 长度不同会抛错，调用前应确保等长或用长度判断短路。

**速记**：敏感等值比较用 **timingSafeEqual** 防时序。



#### 完整注册与校验函数

**注册与校验流程**：注册时生成盐并用 scrypt 派生，存"盐:派生密钥"；校验时读盐重派生并用恒定时间比较。

- 注册函数返回形如 **saltHex:hashHex** 的字符串，盐与密钥一并落库。
- 校验函数拆分存储串、用同盐同参数重算、以 timingSafeEqual 比对，避免时序泄露。
- 全程不存明文密码，泄露库也只见到盐与慢哈希派生值。

```js
const crypto = require("crypto");

function hashPassword(password) {
  const salt = crypto.randomBytes(16);
  const derived = crypto.scryptSync(password, salt, 64);
  return salt.toString("hex") + ":" + derived.toString("hex");
}

function verifyPassword(password, stored) {
  const [saltHex, hashHex] = stored.split(":");
  const salt = Buffer.from(saltHex, "hex");
  const derived = crypto.scryptSync(password, salt, 64);
  const storedHash = Buffer.from(hashHex, "hex");
  return derived.length === storedHash.length &&
    crypto.timingSafeEqual(derived, storedHash);
}

const saved = hashPassword("mySecret");
console.log(verifyPassword("mySecret", saved)); // true
console.log(verifyPassword("wrong", saved));     // false
```

> 该函数是最小可运行骨架：生产中应把 scryptSync 换成回调版以不阻塞事件循环，并给 scrypt 配置更高的成本参数；存储串格式可换成更自描述的方案（如含算法与成本）。

**速记**：注册"盐:派生"入库，校验重算恒定比。



### 非对称加密与数字签名

#### generateKeyPairSync 生成密钥对

**generateKeyPairSync(type, options)**：同步生成**公钥私钥对**，type 常用 **rsa**，返回含 publicKey 与 privateKey 的对象。

- 调用如 **crypto.generateKeyPairSync("rsa", { modulusLength: 2048, publicKeyEncoding, privateKeyEncoding })**。
- modulusLength 为密钥位数，**2048 是当前最低安全线**，更高更安全也更慢。
- 编码常选 **pem 格式**的 spki（公钥）与 pkcs8（私钥），便于存储与传输。

```js
const crypto = require("crypto");

const { publicKey, privateKey } = crypto.generateKeyPairSync("rsa", {
  modulusLength: 2048,
  publicKeyEncoding: { type: "spki", format: "pem" },
  privateKeyEncoding: { type: "pkcs8", format: "pem" },
});
console.log(publicKey, privateKey);
```

> 私钥必须严格保密，通常加口令或使用密钥管理服务保护；公钥可自由分发，是"证明身份"的公开锚点。

**速记**：generateKeyPairSync 出 **rsa 公私钥对**。



#### publicEncrypt 与 privateDecrypt

**publicEncrypt(key, data)** 与 **privateDecrypt(key, data)**：用公钥加密、私钥解密，实现"只有私钥持有者能读"的保密通信。

- 发送方用**接收方公钥** publicEncrypt 加密短消息，接收方用**自己私钥** privateDecrypt 还原。
- 反向（私钥加密公钥解密）用于**数字签名**场景，见下一条。
- rsa 加密的数据长度受密钥位数限制，只适合**小数据**，大数据应先用对称加密再用公钥包密钥。

```js
const crypto = require("crypto");

const message = Buffer.from("短消息", "utf8");
const encrypted = crypto.publicEncrypt(publicKey, message);
const decrypted = crypto.privateDecrypt(privateKey, encrypted);
console.log(decrypted.toString("utf8")); // 短消息
```

> publicEncrypt 加密的数据上限约为密钥位数减去填充开销（2048 位约 245 字节），超出会报错；这正是非对称加密只适合小数据的原因。

**速记**：公钥加密、私钥解密，只保**小数据**。



#### sign 与 verify 数字签名

**sign 与 verify**：用**私钥签名、公钥验签**，证明数据来自私钥持有者且未被篡改，是数字签名的核心。

- 签名：**crypto.createSign("sha256")** 后 update 数据，再以 **sign(privateKey, "hex")** 产出签名串。
- 验签：**crypto.createVerify("sha256")** 后 update 同样数据，以 **verify(publicKey, signature, "hex")** 返回布尔。
- 算法参数（如 sha256）签名与验签必须一致，否则验证失败。

```js
const crypto = require("crypto");

const data = "待签名内容";
const signer = crypto.createSign("sha256");
signer.update(data);
const signature = signer.sign(privateKey, "hex");

const verifier = crypto.createVerify("sha256");
verifier.update(data);
const ok = verifier.verify(publicKey, signature, "hex");
console.log(ok); // true，内容未被篡改且确为私钥方所签
```

> 数字签名本质是"用私钥对哈希结果加密"——公钥能解开即证明来自私钥方，哈希一致即证明内容未改；它**不保密内容**，只认证来源与完整。

**速记**：私钥签名、公钥验签，证**来源与完整**。



#### 非对称加密的适用边界

**适用边界**：非对称加密擅长**小数据加密、密钥交换、身份认证**，不适合直接加密大文件。

- 加密大文件应先**随机生成对称密钥**，用对称算法加密数据，再用公钥加密该对称密钥传给对方（混合加密）。
- 签名用于**身份认证与防篡改**，而非保密；要保密内容需另行加密。
- 性能上非对称比对称慢**百倍到千倍**，批量数据走对称、非对称只管"密钥与签名"。

> HTTPS 正是混合典范：握手阶段用非对称算法交换对称会话密钥，之后所有应用数据用对称算法高速加密；既解决密钥分发，又兼顾性能。

**速记**：非对称管**密钥与签名**，大数据交对称。



### Base64、十六进制与安全实践清单

#### Base64 与十六进制只是编码

**Base64 与十六进制**：都是**可逆的编码方式**，仅把字节表示成文本，不是加密，不含任何保密性。

- 转换用 **Buffer 的 toString("base64") 或 toString("hex")**，反向用 **Buffer.from(str, "base64"/"hex")**。
- 它们解决的是"二进制如何在文本通道（JSON、URL、邮件）传输"的问题，任何人都能无损还原。
- 把 Base64 当作加密是**典型误解**，编码后的内容对任何人都是明文。

```js
const crypto = require("crypto");

const buf = Buffer.from("敏感原文", "utf8");
const b64 = buf.toString("base64"); // 编码，非加密
const back = Buffer.from(b64, "base64").toString("utf8"); // 原样还原
console.log(b64, back);
```

> [!CAUTION]
> **注意内容**：Base64、十六进制、URL 编码都只是**编解码**，不含密钥、可逆且无保密性。凡看到"我用 base64 加密了一下"的说法，需纠正其为编码而非加密。

**速记**：Base64 是**编码不是加密**，人人可还原。



#### 安全实践清单

**安全清单**：把前述原则落成可执行的纪律，避免最常见的加密误用。

- 密钥不放代码库：从**环境变量或密钥管理服务**读取，禁止硬编码密钥。
- 不用 md5 与 sha1 做安全用途：安全哈希用 **sha256 及以上**，口令用慢哈希。
- 密码绝不明文存储：入库必须**加盐慢哈希（scrypt/bcrypt/argon2）**。
- 敏感日志脱敏：打印前遮蔽令牌、密钥、身份证等，避免日志泄露。
- 依赖 HTTPS：传输层用 TLS 加密，签名验证与随机源才有意义。
- 随机源用 crypto：令牌、盐、IV 一律 **crypto.randomBytes / randomUUID / randomInt**。
- 对称加密用带 IV 的现代模式：优先 **aes-256-gcm**，禁用 ECB 与废弃的 createCipher。

> [!IMPORTANT]
> **重要内容**：加密安全是"短板即全局"的课题——一处硬编码密钥、一次明文存密码、一个被复用的 IV，都足以让整套防护归零。上线前务必逐条核对本清单。

```js
// 反例：硬编码密钥（禁止）
const key = "1234567890abcdef1234567890abcdef"; // 绝不能这样写
// 正例：从环境变量读取
const safeKey = Buffer.from(process.env.ENCRYPT_KEY, "hex");
```

**速记**：密钥不入库、密码要加盐、传输靠 HTTPS。
