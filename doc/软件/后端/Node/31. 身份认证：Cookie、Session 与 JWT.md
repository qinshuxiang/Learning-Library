## 身份认证：Cookie、Session 与 JWT

### 认证与授权、HTTP 无状态

#### 认证与授权是两件不同的事

**认证（Authentication）**：解决「你是谁」的问题，确认访问者声称的身份是否真实，典型动作是登录。

- **授权（Authorization）**：解决「你能做什么」的问题，在身份已确认后决定其可访问的资源和可执行的动作。
- **登录属于认证**：提交账号密码，系统确认这就是该用户本人。
- **权限校验属于授权**：登录后判断该用户能否访问某个接口、执行某个操作。
- 二者常连续出现：先认证取得身份，再据身份做授权判断，但概念不可混为一谈。

> 一句话区分：**认证回答身份，授权回答权限**。没有认证的授权是无据放行，没有授权的认证是只认人不问权。系统里二者通常由不同中间件承担。

**速记**：认证认人、授权放权，登录是认证、鉴权是授权。



#### HTTP 无状态使每次请求彼此独立

**HTTP 的无状态（Stateless）**：指协议本身不保存前后请求之间的关联，服务端默认不记得上一次是谁来访。

- 每个请求都是**独立的一次往返**，携带完整信息，服务端处理完即丢弃上下文。
- 服务端**不会自动维持登录态**，第二次请求不会"记得"你已登录。
- 维持登录态必须**借助额外机制**（Cookie、Session、令牌）在请求间传递身份凭证。

> 无状态本是 HTTP 的优点——请求互不耦合、易于水平扩展；但它也带来"每次都要重新证明身份"的问题，认证体系正是为弥补这点而生。

**速记**：HTTP 不记事，登录态靠外部机制续上。



### Cookie 机制与重要属性

#### Cookie 由服务器种下并由浏览器自动携带

**Cookie**：是服务器通过响应头种下、由浏览器按域名存储、并在后续同域请求中自动通过请求头回传的一小段键值数据。

- **种下**：服务器在响应里带上 **Set-Cookie** 头，浏览器据此创建或更新 Cookie。
- **携带**：之后浏览器对该域名发起请求时，自动在 **Cookie** 头里附上匹配的键值对，无需脚本干预。
- **隔离**：Cookie 按**域名**存储与隔离，一个站点的 Cookie 不会被另一个站点读取。
- **容量有限**：通常每域约 4 KB、约数十个，适合放小凭证而非大对象。

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; Secure
```

```http
GET /profile HTTP/1.1
Host: example.com
Cookie: sessionId=abc123
```

> 上述报文依据 RFC 6265：Set-Cookie 由服务器下发，Cookie 由浏览器回传。浏览器"自动"携带是 Cookie 机制的核心便利，也是它容易被 CSRF 利用的根源。

**速记**：服务器 Set-Cookie 种下，浏览器 Cookie 头自动回传。



#### Cookie 的重要属性控制有效期、作用域与安全

**Cookie 属性**：写在 Set-Cookie 值之后的键值开关，决定 Cookie 的存活时长、可见范围与安全防护，直接影响安全性。

- **Expires 与 Max-Age**：控制有效期。二者皆不设则为**会话级 Cookie**，浏览器关闭即失效；设了则成为**持久 Cookie**。
- **Domain 与 Path**：限定作用范围。Domain 指定可接收的主机，Path 进一步限定路径前缀，二者共同决定哪些请求会携带它。
- **Secure**：要求 Cookie **仅通过 HTTPS 传输**，明文 HTTP 下不发送，防中间人窃听。
- **HttpOnly**：禁止**脚本通过 document.cookie 读取**，从根本上防 XSS 窃取。
- **SameSite**：取值 **Strict、Lax、None**，约束跨站请求是否携带 Cookie，是防 CSRF 的关键开关。

> SameSite 三值含义：**Strict** 完全不跨站携带；**Lax** 仅顶级导航的 GET 携带（默认常见值）；**None** 任何跨站都携带，但必须配合 Secure。把本应 HttpOnly 的凭证设成可读、或把 SameSite 误设 None 又不配 Secure，都会放大攻击面。

```http
Set-Cookie: token=xyz; Max-Age=3600; Path=/; Secure; HttpOnly; SameSite=Lax
```

**速记**：Expires/Max-Age 管活多久，Domain/Path 管去哪，Secure/HttpOnly/SameSite 管安全。



### 在 Express 中读写 Cookie

#### 用原生 res.setHeader 设置 Set-Cookie

**原生设置法**：Express 的响应对象 res 本质是 Node 的 ServerResponse，可直接用 **res.setHeader(name, value)** 写入 Set-Cookie 头。

- 方法签名为 **res.setHeader(headerName, headerValue)**，headerName 传入字符串 "Set-Cookie"，值为形如 "key=value; 属性" 的字符串。
- 请求侧用 **req.headers.cookie** 拿到原始 Cookie 字符串，形如 "a=1; b=2"，需自行按分号拆分解析。
- 原生方式**无自动编码与属性封装**，多个 Cookie 要多次 setHeader 或拼成数组。

```js
const express = require("express");
const app = express();

app.get("/login", (req, res) => {
  res.setHeader(
    "Set-Cookie",
    "sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax"
  );
  res.send("已种下 Cookie");
});

app.get("/me", (req, res) => {
  const raw = req.headers.cookie || ""; // 形如 "sessionId=abc123"
  const cookies = Object.fromEntries(
    raw.split("; ").map((pair) => pair.split("="))
  );
  res.send("会话标识：" + (cookies.sessionId || "无"));
});

app.listen(3000);
```

> 原生解析要自己处理空格、缺失与编码，生产不易维护；它适合理解原理，真实项目多用中间件代劳。注意 req.headers.cookie 是**未经授信的字符串**，解析前需校验。

**速记**：res.setHeader 种、req.headers.cookie 取，解析自理。



#### 用 cookie-parser 与 res.cookie 简化读写

**cookie-parser 中间件**：把请求头里的 Cookie 自动解析成 **req.cookies** 对象，免去手工拆分。

- 安装后 app.use(require("cookie-parser")())，之后 **req.cookies.key** 即可取单个值。
- 写 Cookie 用 Express 自带的 **res.cookie(name, value, options)**，options 直接传 Max-Age、HttpOnly、Secure、SameSite 等，比拼字符串安全。
- 清除用 **res.clearCookie(name[, options])**，须与种下时的 Path、Domain 一致才能命中。

```js
const express = require("express");
const cookieParser = require("cookie-parser");
const app = express();

app.use(cookieParser());

app.get("/login", (req, res) => {
  res.cookie("sessionId", "abc123", {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
    maxAge: 3600 * 1000,
  });
  res.send("已登录");
});

app.get("/me", (req, res) => {
  res.send("会话标识：" + (req.cookies.sessionId || "无"));
});

app.get("/logout", (req, res) => {
  res.clearCookie("sessionId", { path: "/" });
  res.send("已退出");
});
```

> res.cookie 的 maxAge 单位是**毫秒**，与 Set-Cookie 里的 Max-Age（秒）不同，混用会造成有效期差一千倍。clearCookie 的选项必须与种下时匹配，否则浏览器不会删除该 Cookie。

**速记**：cookie-parser 解、res.cookie 写、res.clearCookie 删。



### Session 机制与 express-session 实现登录

#### Session 在服务端保存状态、仅把 sessionId 交给 Cookie

**Session（会话）**：是服务端为每次登录保存的一段状态数据，客户端只持有一个随机的 **sessionId**，二者靠这个 id 关联。

- **服务端存数据**：用户资料、登录标记等敏感状态放在服务端内存或外部存储，客户端看不到。
- **只发随机 id**：把一个无意义的随机串 sessionId 写入 Cookie，服务端据它查回对应会话。
- **默认存内存**：express-session 默认用内存存储，进程重启会丢失、多进程之间不共享。
- **生产需外部存储**：高可用场景应接入 **Redis 或数据库**，使会话跨重启、跨进程可用。

> Session 把"状态"留在服务端、把"指针"交给客户端，因此服务端能随时让某会话失效。代价是服务端要维护这份存储，且多实例部署必须共享它，否则用户在 A 进程登录、请求落到 B 进程就不认得。

**速记**：服务端存状态、客户端只拿随机 id。



#### 用 express-session 配置登录会话

**express-session 中间件**：为 Express 注入基于 Cookie 的会话能力，配置后可通过 **req.session** 读写登录状态。

- 安装后 app.use(session(options))，关键选项有 **secret** 用于签名防篡改、**resave** 是否每次都写回存储、**saveUninitialized** 是否保存未改动会话、**name** 改写 Cookie 名、**cookie** 传安全属性。
- 登录成功时给 **req.session.userId** 赋值，后续任意请求都能从 req.session 读回。
- secret 必须来自**环境变量**，绝不能硬编码；它用于给 sessionId 签名，泄露即能被伪造。

```js
const express = require("express");
const session = require("express-session");
const app = express();

app.use(express.json());
app.use(session({
  name: "sid",
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,
    secure: true,
    sameSite: "lax",
    maxAge: 1000 * 60 * 30,
  },
}));

app.post("/login", (req, res) => {
  // 假设已校验密码
  req.session.userId = 42;
  res.send("登录成功");
});

app.get("/profile", (req, res) => {
  if (!req.session.userId) return res.status(401).send("未登录");
  res.send("用户 " + req.session.userId + " 的资料");
});

app.listen(3000);
```

> resave 与 saveUninitialized 设为 false 是常见推荐：避免无谓的存储写入、减少会话存储压力。cookie 选项里的 secure 在开发若用 HTTP 本地自测会收不到 Cookie，上线务必开启。

**速记**：session 配 secret 与 cookie，req.session 存取登录态。



#### 退出登录与防范会话固定攻击

**会话固定（Session Fixation）**：攻击者先拿到一个合法会话 id 并诱使受害者用该 id 登录，登录后 id 不变，攻击者的 id 随即"升格"为已登录态。

- 退出用 **req.session.destroy(callback)** 销毁服务端会话数据，并配合 res.clearCookie 清掉客户端 Cookie。
- **登录时必须更换 sessionId**：先调用 **req.session.regenerate(callback)** 生成全新 id，再写入登录信息，使旧 id 失效。
- 仅清除 Cookie 而不销毁服务端数据，会话记录仍可被同 id 复用，退出不彻底。

```js
app.post("/login", (req, res) => {
  // 先换全新会话，破解会话固定
  req.session.regenerate((err) => {
    if (err) return res.status(500).send("会话错误");
    req.session.userId = 42;
    res.send("登录成功");
  });
});

app.post("/logout", (req, res) => {
  req.session.destroy((err) => {
    if (err) return res.status(500).send("退出失败");
    res.clearCookie("sid", { path: "/" });
    res.send("已退出");
  });
});
```

> [!WARNING]
> **警告内容**：登录时不调用 regenerate 而直接复用旧 sessionId，会留下会话固定漏洞——攻击者预先种下的 id 在受害者登录后直接变成已认证会话。凡是"身份权限发生提升"的节点，都必须重新生成会话标识。

**速记**：登录 regenerate 换 id，退出 destroy 清服务端。



### Session 的优缺点与适用边界

#### Session 服务端可控但存在存储与扩展成本

**Session 的权衡**：服务端持有会话使其可即时管控，但也带来存储开销与分布式扩展的复杂度。

- **优点**：服务端可**主动、即时让会话失效**（封禁、改密后踢下线）；敏感状态**不落客户端**，难以被用户篡改。
- **缺点**：服务端需**维护存储**，用户量大时内存或 Redis 成本上升；多进程、多节点必须共享存储，否则会话漂移。
- **场景局限**：在**跨域、移动端、多端共享**场景里，基于单域 Cookie 的 Session 不如无状态令牌灵活。

> Session 的"可控"来自"服务端记得你"，JWT 的"易扩"来自"服务端不必记得你"——二者是同一权衡的两极。选型看业务更看重即时失效能力，还是横向扩展与跨域便利。

**速记**：Session 可控但重存储，跨域移动端不划算。



### JWT 的结构、流程与 jsonwebtoken 实现

#### JWT 由 Header、Payload、Signature 三段组成

**JWT（JSON Web Token）**：是一种三段式的无状态令牌，形如 Header 点 Payload 点 Signature，各段为 **Base64URL 编码**，靠签名保证完整与可信。

- **Header（头部）**：声明令牌类型与签名算法，如 HMAC 或 RSA，经 Base64URL 编码为第一段。
- **Payload（载荷）**：存放业务与标准声明数据，同样仅编码，任何人都可解码查看，绝非加密。
- **Signature（签名）**：用 Header 与 Payload 的编码串加密钥算出的签名，验证时重算比对以确认未被篡改。
- **编码不是加密**：Base64URL 只做可逆转换，Payload 对持有者完全透明，敏感信息绝不能放入。

```text
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjQyLCJyb2xlIjoidXNlciJ9.SflKx...
└─ Header ─┘ └──── Payload ────┘ └─── Signature ───┘
```

> JWT 依据 RFC 7519。三段的"点"分隔只是编码拼接，剖开即见明文 JSON；因此"把密码放进 JWT"与"把密码放进 Base64"同样危险。需保密内容应放在服务端存储，令牌只带引用 id。

**速记**：JWT 三段点分隔，Header 与 Payload 只是编码。



#### JWT 的工作流程是签发、携带与验证

**JWT 流程**：登录后服务端签发令牌，客户端保存并在后续请求携带，服务端每次验证签名与过期时间后放行。

- **签发**：登录校验通过后，服务端用密钥生成令牌返回给客户端。
- **携带**：客户端后续请求通常在 **Authorization** 头使用 **Bearer** 前缀带上令牌，如 Authorization: Bearer <token>。
- **验证**：服务端收到后用同一密钥**验证签名有效且未过期**，通过即信任其中的身份声明。
- **无状态**：验证不依赖服务端存储，任意节点持密钥即可独立校验。

```http
POST /login
Content-Type: application/json

{"username":"alice","password":"***"}

HTTP/1.1 200 OK
{"token":"eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjQyfQ.SflKx..."}
```

```http
GET /profile HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjQyfQ.SflKx...
```

> 验证失败的情形包括签名不对（密钥不符或令牌被改）、已过期、格式非法。Bearer 前缀是约定写法，服务端取令牌时要先剥离 "Bearer " 再验证，少一个空格都会校验失败。

**速记**：登录签发、Bearer 携带、服务端验签与过期。



#### 用 jsonwebtoken 的 sign 与 verify 实现

**jsonwebtoken 库**：是 Node 实现 JWT 的主流包，核心为 **jwt.sign(payload, secretOrPrivateKey, options)** 签发与 **jwt.verify(token, secretOrPublicKey)** 验证。

- 签名方法 **jwt.sign(payload, secret, options)**：payload 为载荷对象，secret 为密钥（HMAC）或私钥（RSA），options 常用 **expiresIn** 设有效期、**algorithm** 设算法。
- 验证方法 **jwt.verify(token, secret)**：校验签名与过期，成功返回解码后的载荷对象，失败抛错。
- **jwt.decode(token)** 仅解码不校验，可用于只读声明，但**绝不能**据此信任身份。
- 错误处理：过期抛 **TokenExpiredError**，签名或格式问题抛 **JsonWebTokenError**。

```js
const jwt = require("jsonwebtoken");

const secret = process.env.JWT_SECRET;

// 签发
const token = jwt.sign(
  { userId: 42, role: "user" },
  secret,
  { algorithm: "HS256", expiresIn: "15m" }
);

// 验证
try {
  const payload = jwt.verify(token, secret);
  console.log("合法用户：", payload.userId);
} catch (err) {
  if (err.name === "TokenExpiredError") console.log("令牌已过期");
  else if (err.name === "JsonWebTokenError") console.log("令牌非法");
}

// 仅解码（不校验，不可信）
const peek = jwt.decode(token);
console.log(peek.userId);
```

> expiresIn 接受字符串 "15m"、"1h" 或数字秒；algorithm 默认 HS256（HMAC）。decode 跳过验证，若用它的结果做权限判断等于"不验票就放行"，是严重误用。

**速记**：sign 签发带 expiresIn，verify 验签捕 TokenExpired 与 JsonWebToken。



### JWT 的载荷设计、优缺点与刷新令牌

#### JWT 载荷只放必要非敏感信息

**载荷设计原则**：Payload 只放必要、非敏感的声明，标准字段与业务标识分离，敏感数据一律留服务端。

- **标准声明**：**iss** 签发者、**sub** 主体（常为用户 id）、**exp** 过期时间、**iat** 签发时间，均由 RFC 7519 约定。
- **只放必要项**：用户 id、角色等够鉴权即可，避免塞入大对象拖长令牌。
- **不放敏感数据**：密码、手机号、密钥等绝不进 Payload，因为它对人可读。
- **客户端可见**：前端拿到令牌可解码看到声明，因此不要把令牌当保密容器。

> exp 由 verify 自动检查，无需自己在载荷里写是否过期的判断；sub 习惯放用户主键，业务侧据此查库取最新资料，而不是直接信任 Payload 里的全部字段。

**速记**：载荷放 id 与角色，敏感数据留服务端。



#### JWT 无状态易扩展但无法主动失效

**JWT 的权衡**：无状态带来易扩展与跨域友好，却牺牲了服务端主动撤销的能力。

- **优点**：服务端**无需存储会话**，天然适合水平扩展、跨域与移动端；任意持密钥节点独立验证。
- **缺点**：令牌**发出后无法主动失效**，除非借助黑名单或短有效期；令牌体积大于一个 sessionId。
- **风险边界**：一旦**密钥泄露**，攻击者可自行签发任意合法令牌，全面失守，故密钥管理极关键。

> 解决"无法主动失效"常用两招：一是把有效期压得很短（如 15 分钟），过期自然作废；二是维护一个服务端黑名单（或版本号）在验证时额外查一次。前者简单，后者能即时封禁。

**速记**：JWT 易扩难撤销，密钥泄露即全局失守。



#### 刷新令牌降低长期令牌泄露风险

**刷新令牌（Refresh Token）**：用一枚短期访问令牌配一枚长期刷新令牌，访问令牌过期后用刷新令牌换新的，降低泄露面。

- **访问令牌短命**：如 15 分钟，即便被截获，可利用窗口极小。
- **刷新令牌长命且可撤销**：存于服务端（如数据库或 Redis），可随时作废；它不随每个请求频繁传输，泄露风险更低。
- **刷新流程**：访问令牌过期，客户端拿刷新令牌请求刷新接口，服务端校验刷新令牌有效且未撤销，签发新访问令牌。

```js
const jwt = require("jsonwebtoken");

function issueTokens(user) {
  const accessToken = jwt.sign(
    { userId: user.id },
    process.env.JWT_SECRET,
    { algorithm: "HS256", expiresIn: "15m" }
  );
  const refreshToken = jwt.sign(
    { userId: user.id },
    process.env.REFRESH_SECRET,
    { algorithm: "HS256", expiresIn: "7d" }
  );
  return { accessToken, refreshToken };
}

// 刷新接口
app.post("/refresh", (req, res) => {
  const { refreshToken } = req.body;
  try {
    const payload = jwt.verify(refreshToken, process.env.REFRESH_SECRET);
    // 此处可额外查库确认该刷新令牌未被撤销
    const newAccess = jwt.sign(
      { userId: payload.userId },
      process.env.JWT_SECRET,
      { algorithm: "HS256", expiresIn: "15m" }
    );
    res.json({ accessToken: newAccess });
  } catch (err) {
    res.status(401).send("刷新令牌无效");
  }
});
```

> 刷新令牌务必设独立密钥与更长的有效期，并最好绑定用户与设备、支持服务端撤销。若刷新令牌也随意塞进前端本地存储且长期不换，其泄露后果与长期访问令牌无异。

**速记**：短访问配长刷新，刷新令牌可撤销。



### 令牌存储取舍、安全实践与实战

#### 令牌存储位置的取舍：Cookie 与本地存储

**存储取舍**：访问令牌放 Cookie（配 HttpOnly 与 Secure）还是放浏览器本地存储，是安全与易用之间的权衡，没有一味最优解。

- **Cookie 存储**：配 **HttpOnly** 后脚本读不到，天然抗 XSS 窃取；配 **Secure** 仅走 HTTPS；但需认真对待 **CSRF**，可用 SameSite 与双重提交缓解。
- **本地存储**：前端用脚本读取后塞进 Authorization 头，天然无 CSRF 困扰、便于跨域；但 **XSS 一旦得手即可读走令牌**，风险更高。
- **取舍要点**：重防护选 HttpOnly Cookie，重灵活与跨域选本地存储并强化前端 XSS 防御，二者都需配合 HTTPS。

> [!CAUTION]
> **注意内容**：把访问令牌存进浏览器本地存储（localStorage）虽躲开了 CSRF，却把令牌暴露给任意能执行脚本的 XSS——一旦页面被注入，令牌即被读走。若选本地存储，必须把 XSS 防御（输入转义、CSP、依赖审计）做到位。

> [!WARNING]
> **警告内容**：关闭 Cookie 的 HttpOnly 或 Secure 属性，等同于把凭证直接交给脚本与明文信道。HttpOnly 是防 XSS 窃令牌的底线，Secure 是防中间人窃听的底线，二者在生产必须开启，不得为"方便调试"而长期关闭。

**速记**：Cookie 抗 XSS 但要防 CSRF，本地存储反之。



#### 身份认证安全实践清单

**安全清单**：把认证相关的最佳实践落成纪律，逐项核对可挡掉绝大多数常见漏洞。

- **全程 HTTPS**：所有凭证传输走 TLS，Cookie 配 Secure，令牌不在明文下暴露。
- **密码慢哈希存储**：用 scrypt、bcrypt 或 argon2 加盐派生，绝不存明文，也不直接用快哈希（见 23. crypto 加密与安全）。
- **登录失败不提示具体原因**：统一返回"用户名或密码错误"，避免攻击者借此枚举有效账号。
- **限制登录尝试频率**：对失败次数做限流与临时锁定，抵御暴力破解。
- **敏感操作二次验证**：改密码、转账等加一步多因素认证。
- **密钥放环境变量**：JWT 与 Session 的密钥从环境变量或密钥管理服务读取，禁止硬编码。

> [!IMPORTANT]
> **重要内容**：认证系统的强度等于它最弱的一环——一个明文存密码、一个硬编码密钥、一个被关掉的 Secure，都足以让整套防护归零。上线前务必逐条核对本清单与 23 篇的安全清单。

**速记**：HTTPS、慢哈希、限频、藏密钥、二次验证。



#### 实战：完整登录与鉴权流程

**完整流程**：把密码校验、令牌签发、鉴权中间件、受保护路由串成一条可运行链路，形成最小可用的登录系统。

- **登录接口**：用慢哈希比对密码（见 23 篇），成功则 sign 签发访问令牌与刷新令牌返回。
- **鉴权中间件**：从 Authorization 头取出 Bearer 令牌，verify 验证后把用户信息挂载到 **req.user**，失败则 401。
- **受保护路由**：依赖中间件注入的 req.user 返回业务数据，无需再次解析令牌。
- **退出**：前端丢弃令牌即可，若用刷新令牌机制则服务端将其撤销。

```js
const express = require("express");
const jwt = require("jsonwebtoken");
const crypto = require("crypto");
const app = express();

app.use(express.json());

// 演示用：真实应查库并以 scrypt 慢哈希比对
const users = [{ id: 42, username: "alice", passwordHash: "", salt: "" }];

function verifyPassword(password, stored, salt) {
  const derived = crypto.scryptSync(password, salt, 64);
  const a = Buffer.from(stored, "hex");
  return a.length === derived.length && crypto.timingSafeEqual(a, derived);
}

function loginHandler(req, res) {
  const { username, password } = req.body;
  const user = users.find((u) => u.username === username);
  if (!user || !verifyPassword(password, user.passwordHash, user.salt)) {
    return res.status(401).send("用户名或密码错误");
  }
  const accessToken = jwt.sign(
    { userId: user.id },
    process.env.JWT_SECRET,
    { algorithm: "HS256", expiresIn: "15m" }
  );
  res.json({ accessToken });
}

function requireAuth(req, res, next) {
  const header = req.headers.authorization || "";
  const token = header.startsWith("Bearer ") ? header.slice(7) : "";
  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.user = { userId: payload.userId };
    next();
  } catch (err) {
    res.status(401).send("未认证");
  }
}

function profileHandler(req, res) {
  res.json({ userId: req.user.userId, message: "受保护数据" });
}

app.post("/login", loginHandler);
app.get("/profile", requireAuth, profileHandler);

app.listen(3000);
```

> requireAuth 是典型的"认证中间件"：它只负责验票并把身份挂到 req.user，业务路由专心处理数据。把认证与业务分离，既复用又清晰；任何需要登录的路由都只要在链里加上 requireAuth 即可。

**速记**：loginHandler 验密签发，requireAuth 验签挂 user，路由取用。
