## npm 与包管理

### 包管理工具的认识

**包管理工具**：是**自动安装、更新、卸载、管理第三方依赖**的命令行工具，让复用他人代码变得可控。

没有包管理时，开发者需手动下载、放置、维护每个库，版本冲突难以解决。

#### 什么是包 Package

**包 Package**：是**一个可分发的功能单元**，通常含代码、package.json 描述文件与依赖声明。

基本构成：

- **代码文件**：实现功能的脚本。
- **package.json**：包的元数据与入口声明。
- **依赖声明**：它自己需要哪些包。

```bash
my-package/
├── package.json
├── index.js
└── node_modules/   # 安装后自动产生
```

> 包既能是**被安装的库**（如 lodash），也能是**可执行的命令行工具**（如 eslint）。二者都经 npm 分发，区别在后者通常带 bin 字段并全局安装。



#### npm 的安装与版本查看

**npm**：是 Node 的**默认包管理器**，随 Node 一起安装，无需单独下载。

验证安装：

- 查看 npm 版本：npm -v。
- 查看 Node 版本：node -v。

```bash
npm -v
node -v
```

> npm 版本**跟随 Node 发布**，升级 Node 通常也升级了 npm。生产环境一般保持与 Node 配套版本，避免意外行为差异。



#### 为什么需要包管理

**包管理的价值**：在于把"找库、装库、锁版本、更新、卸载"标准化、**可复现**。

核心收益：

- **依赖可复现**：借锁文件，团队每人装到完全一致版本。
- **版本可控**：语义化版本让升级有章可循。
- **卸载干净**：一条命令移除包及其记录。

> 没有包管理，项目依赖散落各处、版本混乱、协作崩溃。包管理是现代 JavaScript 工程**不可或缺的基础设施**。



### package.json 的生成

**package.json**：是**每个 Node 项目的身份证**，记录名称、版本、入口、脚本与依赖。

它是 npm 一切操作的依据文件。

#### npm init 与快速生成

**npm init**：是**交互式生成** package.json 的命令，按提示逐项填写。

两种用法：

- 交互式：直接 npm init，逐字段问答。
- 快速生成：npm init -y 用默认值一次性生成，跳过提问。

```bash
npm init      # 交互式
npm init -y   # 快速生成
```

> npm init -y 字段都是**占位默认值**（name 取目录名、license 为 ISC 等），生成后仍应手动补正 name、description、author 等真实信息。



#### 核心字段解释

**package.json 字段**：分基础信息、入口与脚本、依赖三大类。

基础与入口字段：

- **name**：包名，发布时必填且须唯一。
- **version**：版本号，遵循语义化版本。
- **description**：一句话描述，便于检索。
- **main**：包入口文件，被 require/import 时的默认加载点。
- **scripts**：自定义脚本命令集合。
- **author / license**：作者与开源协议。

```json
{
  "name": "demo-app",
  "version": "1.0.0",
  "description": "A demo project",
  "main": "index.js",
  "author": "siluhao",
  "license": "MIT"
}
```

> name 与 version 是**唯二强制字段**，缺一则无法发布。main 在 ESM 项目里常被 exports 取代，但仍是旧生态兜底入口。



#### 依赖相关字段

**依赖字段**：描述项目需要哪些包，分生产依赖与开发依赖，还可用 engines 约束环境。

关键字段：

- **dependencies**：生产环境运行所必需。
- **devDependencies**：仅开发、构建、测试阶段需要。
- **engines**：声明支持的 Node/npm 版本范围。

```json
{
  "dependencies": { "express": "^4.19.2" },
  "devDependencies": { "eslint": "^9.0.0" },
  "engines": { "node": ">=18.0.0" }
}
```

> 正确分类能**减小生产镜像体积**（部署用 --production 只装前者）。engines 是"建议性"约束，除非加 engine-strict，否则仅警告不阻断。



### 语义化版本 semver

**语义化版本（SemVer）**：是**用三段数字表达版本含义**的约定，让版本号本身传递兼容性信息。

理解 semver 是读懂 package.json 里 ^ 与 ~ 的前提。

#### 版本号格式

**版本号格式**：是 主版本号.次版本号.修订号 的三段结构，依次对应**不兼容变更、向后兼容新功能、向后兼容修复**。

三位含义：

- **主版本号（Major）**：做了不兼容 API 修改时递增。
- **次版本号（Minor）**：做了向后兼容功能新增时递增。
- **修订号（Patch）**：做了向后兼容问题修复时递增。

```json
{ "express": "4.19.2" } // 4 主版本，19 次版本，2 修订号
```

> 预发布版本可追加连字符，如 1.0.0-beta.1。语义化版本保证：**同主版本内，次版本与修订号升级不应破坏你的代码**，这是依赖自动升级的安全基础。



#### ^ 与 ~ 的区别

**版本范围符号**：^ 与 ~ 都允许"自动升级到兼容版本"，但**放开区间不同**。

对比：

- **^（caret）**：允许**次版本号与修订号**变化，主版本不变。^1.2.3 接受 1.x.x 中大于等 1.2.3、直到 2.0.0 之前。
- **~（tilde）**：只允许**修订号**变化，次版本锁定。~1.2.3 接受 1.2.x 中大于等 1.2.3、直到 1.3.0 之前。

```json
{ "a": "^1.2.3", "b": "~1.2.3" } // a 可到 1.9.0；b 只到 1.2.9
```

> 速记：**^ 放开次版本与修订，~ 只放开修订**。默认 npm install 写 ^，即"允许向后兼容功能更新"。稳定性要求极高者可用 ~ 或更严锁定。



#### 精确版本与升级风险

**精确版本**：是不带前缀、写死具体版本号（如 1.2.3）的写法，锁定不自动升级。

风险对照：

- **全写精确版本**：绝对稳定，但**错过安全补丁与修复**，需手动逐个更新。
- **过度放开（* 或 latest）**：自动拿最新，**可能引入不兼容主版本变更**，导致大版本跳跃式破坏。

```json
{ "safe": "1.2.3", "risky": "*", "wild": "latest" }
```

> 工程上推荐用 **^ 或锁文件**平衡稳定与更新，避免 * 或 latest。所谓"大版本跳跃的危险"正来自放开范围却未充分测试。



### npm install 的各类用法

**npm install**：是**安装依赖**的核心命令，借不同参数区分安装位置与版本。

掌握各类变体，才能精确控制依赖落点。

#### 安装各类依赖

**安装命令的参数**：决定依赖被装进 dependencies、devDependencies 还是全局。

常用形式：

- **生产依赖**：npm install 包名，写入 dependencies。
- **开发依赖**：npm install 包名 -D 或 --save-dev。
- **全局安装**：npm install 包名 -g，装到全局而非项目。
- **指定版本**：npm install 包名@1.2.3。
- **指定 tag**：npm install 包名@beta 装预发布标签。

```bash
npm install lodash            # 生产依赖
npm install eslint -D         # 开发依赖
npm install http-server -g    # 全局安装
npm install react@18.2.0      # 指定版本
npm install vite@beta         # 指定 tag
```

> -D 是 --save-dev 简写；全局安装的包通常是有 bin 的**命令行工具**（如 http-server）。项目依赖务必本地安装以保证可复现。



#### 卸载与更新

**卸载与更新**：是依赖生命周期收尾动作，对应 uninstall 与 update。

要点：

- **卸载**：npm uninstall 包名 同时移除包与 package.json 记录。
- **更新**：npm update 把依赖升到 package.json 允许的**最高兼容版本**（受 ^ / ~ 限制）。
- **更新全部**：npm update 不加包名即更新所有可升级依赖。

```bash
npm uninstall lodash   # 卸载
npm update eslint      # 更新单个
npm update             # 更新所有可兼容升级的包
```

> npm update **不会跨越主版本号**（遵守 ^ 范围），要大版本升级需手动改版本号重装，或借 npm install 包名@latest 显式指定。



### node_modules 的结构

**node_modules**：是 npm install 后**所有依赖实际落地的目录**，内部结构直接影响加载路径与体积。

现代 npm 已采用扁平化策略，与早期版本差异明显。

#### 扁平化与依赖提升

**依赖提升（hoisting）**：是 npm 把**嵌套依赖尽量提升到顶层 node_modules** 的机制，减少重复与层级。

表现：

- 多个包依赖同一库时，该库被**提升到顶层**共享一份。
- 原本嵌套在子包下的依赖，被"提"到 node_modules 根目录。

```bash
node_modules/
├── lodash/   # 被提升，a 与 b 共用
├── a/
└── b/
```

> 提升带来**磁盘与安装速度收益**，但也造成"幽灵依赖"——项目未声明却因被提升能直接 import 的包，上游一调就报错。这正是 pnpm 要解决的问题之一。



#### 嵌套安装的发生条件

**嵌套安装**：是当**同一包不同不兼容版本**被需要时，npm 不得不在子目录各放一份的现象。

触发条件：

- 包 A 依赖 lodash@4，包 B 依赖 lodash@3，主版本冲突。
- 顶层只能放一个版本，另一个被迫嵌套在依赖它的包之下。

```bash
node_modules/
├── lodash/          # 4.x 在顶层
└── a/
    └── node_modules/
        └── lodash/  # 3.x 嵌套在 a 内
```

> 嵌套是**版本冲突的无奈妥协**，增体积但保正确。现代 npm 扁平化能合的都合，只在真冲突时才嵌套。



#### .package-lock.json

**.package-lock.json**：是 npm 在 node_modules 内生成的**内部锁文件**，记录本次安装的真实结构。

与根目录 package-lock.json 区别：

- 位置在 node_modules/.package-lock.json，描述**已安装树**。
- 用于加速后续安装、判断是否需要重装。

```bash
node_modules/.package-lock.json   # 内部锁，非项目根锁
```

> 该文件由 npm **自动维护**，无需手动编辑。它与项目根锁互补：根锁管"应该装什么"，内部锁管"实际装了什么"。



### package-lock.json 的作用

**package-lock.json**：是项目根的**依赖锁文件**，把当前依赖树精确固化，保证处处一致。

它是可复现安装的关键，应提交到版本库。

#### 锁定依赖树

**锁文件的作用**：是记录**每个依赖的确切版本与下载地址**，使 npm install 在任何机器装出相同树。

它锁定了：

- **直接依赖的解析版本**：即便 ^ 允许升级，锁文件钉死实际版本。
- **完整传递依赖树**：所有间接依赖版本一并固定。
- **完整性校验值**：用于校验下载内容未被篡改。

```json
{
  "name": "demo",
  "lockfileVersion": 3,
  "packages": {
    "node_modules/lodash": {
      "version": "4.17.21",
      "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz"
    }
  }
}
```

> 无锁文件时，npm install 按 ^ / ~ **重新求解最新兼容版本**，不同时间可能得不同结果，造成"在我机器上能跑"。锁文件正是为消灭这种不确定性。



#### 提交与 npm ci

**提交锁文件**：是把 package-lock.json 纳入**版本控制**，让团队与 CI 共享同一份依赖快照。

为什么必须提交：保证**开发、测试、生产环境依赖完全一致**；新成员 clone 后 install 得与作者相同版本。

**npm ci 与 npm install 的差异**：

- **npm ci**：严格按锁文件安装，**先删 node_modules** 再装，更快更干净，适合 CI。
- **npm install**：可偏离锁文件（按 package.json 更新它），适合本地开发。

```bash
npm ci       # CI 推荐：严格、快速、可复现
npm install  # 本地开发：可能更新锁文件
```

> npm ci 在**锁文件与 package.json 不一致时会直接报错**，强制先解决冲突，正是 CI 需要的"确定性"。生产部署一律优先 npm ci。



### scripts 脚本

**npm scripts**：是 package.json 的 scripts 字段里定义的**可命名命令**，用 npm run 名 执行。

它把常用 shell 命令集中管理，避免记一长串参数。

#### 定义与运行及简写

**脚本定义**：是在 scripts 对象写 **"键名": "命令行"** 键值对，键名即命令别名。

运行规则：

- 普通脚本：npm run 名，如 npm run build。
- **两特例可省 run**：npm start 等价于 npm run start，npm test 等价于 npm run test。
- 未定义脚本运行会报错。

```json
{ "scripts": { "start": "node index.js", "build": "webpack --mode production", "test": "jest" } }
```

```bash
npm run build   # 运行 build
npm start       # 等价于 npm run start
npm test        # 等价于 npm run test
```

> start 与 test 是**约定俗成的简写命令**，托管平台常默认执行 npm start 启动服务。其余脚本都必须带 run，这是 npm 硬规定。



#### 钩子与传参与 npx

**生命周期钩子**：是 npm 在以 pre / post 为前缀时**自动串联执行**的脚本。

机制要点：

- 运行 npm run build 前，若有 prebuild 先执行；之后若有 postbuild 再执行。
- 常用于"构建前清理、构建后打包"。

**向脚本传参**：用双横杠 -- 把参数透传给脚本内命令。**npx**：随 npm 提供的**临时执行工具**，可直接运行 node_modules/.bin 或远程下载的包，免全局安装。

```bash
npm run dev -- --watch   # 把 --watch 透传给 vite
npx eslint .             # 直接运行本地或远程命令
```

> pre / post 钩子**隐式自动触发**，命名须严格匹配主脚本名。双横杠 -- 之后内容原样交脚本命令，是传参标准方式。npx 解决"用一次却要全局装"的痛点。



### npm 的镜像与配置

**npm 配置**：决定 npm 从**哪个 registry（仓库源）** 下载包，及各类默认行为。

国内访问官方源慢时，切换镜像源是常见优化。

#### 配置 registry 与 npmrc

**registry**：是 npm 拉取包的**远程仓库地址**，默认指向 https://registry.npmjs.org。

配置方式：

- 命令行：npm config set registry 地址。
- 配置文件 .npmrc：写 registry=地址 持久化。

```bash
npm config get registry                       # 查看当前源
npm config set registry https://registry.npmmirror.com  # 切换镜像
```

```bash
# 项目级 .npmrc
registry=https://registry.npmmirror.com
```

> npm config set 默认写**用户级** .npmrc（如 ~/.npmrc）；项目根放 .npmrc 只对该项目生效。registry 改动影响后续所有 install，改回用同命令。



#### nrm 与优先级

**nrm**：是**管理多个 registry 源**的第三方命令行工具，一键切换、测速，免去记地址。

npmrc 优先级（从高到低）：

- **项目级 .npmrc**：项目根文件，优先级最高。
- **用户级 .npmrc**：用户主目录配置。
- **全局级 .npmrc**：npm 安装目录配置。
- **内置默认**：npm 自带出厂设置。

```bash
npx nrm ls       # 列出所有源
npx nrm use taobao  # 切换
```

> 优先级遵循"**就近覆盖**"：项目级覆盖用户级，用户级覆盖全局级。把团队统一 registry 写进项目 .npmrc 并提交，能保证所有成员与 CI 用同一源。



### 依赖的安全与维护

**依赖维护**：是定期**检查漏洞、更新过期包**的持续动作，防止项目随依赖老化变脆弱。

依赖不是"装完就忘"，安全与时效都需关注。

#### 安全审计 audit

**npm audit**：是 npm 内置**依赖安全扫描**命令，对照已知漏洞库检查依赖树。

用法：

- npm audit 查看漏洞报告（按严重度分级）。
- npm audit fix 自动升到**修复了漏洞的兼容版本**。
- 加 --force 可跨主版本修复，但需谨慎（可能破坏兼容）。

```bash
npm audit           # 查看漏洞
npm audit fix       # 自动修复（兼容范围）
npm audit fix --force  # 强制修复（可能跨主版本）
```

> npm audit fix 默认**只做兼容升级**，安全且推荐；--force 跨主版本可能引入破坏性变更，生产环境应先在分支验证再合并。



#### 过时检查 outdated

**npm outdated**：是列出**当前安装版本、期望版本、最新版本**三者差距的命令，用于发现可升级包。

输出含义：

- **Current**：当前已装版本。
- **Wanted**：package.json 范围允许的最高兼容版本。
- **Latest**：仓库中最新版本（可能已跨主版本）。

```bash
npm outdated   # 查看所有可升级的包
```

> 定期跑 npm outdated 能发现"**有主版本大版本已发但你还停在旧版**"。结合 npm audit，形成"先修漏洞、再评估大版本升级"的维护节奏。



### 竞品方案

**竞品包管理器**：指除 npm 外的 yarn 与 pnpm，在**安装速度、磁盘占用、依赖隔离**上各有改进。

了解三者差异，才能在团队里做合适选型。

#### yarn 的特性

**Yarn**：是 npm 之后出现的包管理器，主打**并行安装与确定性锁文件**。

核心特性：

- **并行下载**：同时拉取多个包，安装更快。
- **yarn.lock**：固定依赖树，与 package-lock.json 思路一致。
- **离线缓存**：装过的包可离线复用。

```bash
yarn init -y     # 初始化
yarn add lodash  # 安装
yarn install     # 安装全部
```

> Yarn 在 npm 早期（无锁文件、串行慢）解决了痛点；如今 npm 也支持锁文件与较快安装，二者能力趋同，差异多在历史习惯与个别特性（如 workspaces）。



#### pnpm 的原理

**pnpm**：是采用**硬链接 + 符号链接 + 内容寻址存储**的包管理器，在省磁盘与解决幽灵依赖上突出。

原理要点：

- **全局 store**：所有包真实文件存于全局内容寻址仓库，靠内容哈希去重。
- **硬链接**：项目 node_modules 里的包通过**硬链接**指向全局 store，不复制多份，省磁盘。
- **符号链接**：node_modules 用**符号链接**组织依赖树，严格按 package.json 暴露，杜绝幽灵依赖。

```bash
pnpm add lodash
pnpm install
```

> pnpm 能**大幅省磁盘**：同版本包在全局 store 只存一份，各项目硬链接引用，不再每项目复制整份。严格链接还让"未声明却能用"的幽灵依赖无处遁形。



#### 三者对比

**三者对比**：npm、yarn、pnpm 在锁文件、磁盘、隔离性上各有侧重，按诉求选型。

逐维对比（成对加粗强调差异）：

- **锁文件**：npm 用 package-lock.json；yarn 用 yarn.lock；pnpm 用 pnpm-lock.yaml。
- **磁盘占用**：npm 每项目复制、较占空间；yarn 类似；pnpm 靠**硬链接到全局 store**、最省。
- **幽灵依赖**：npm 与 yarn 因提升而**可能存在**；pnpm 严格链接、**基本杜绝**。
- **安装速度**：npm 中等；yarn 并行较快；pnpm 复用 store、**通常最快**。
- **生态兼容**：npm 原生最广；yarn 兼容 npm；pnpm 命令近似但个别行为不同。

> 选型口诀：**求稳妥与原生 → npm；要并行与生态熟悉 → yarn；重磁盘与依赖纯净 → pnpm**。新项目若磁盘与隔离性是考量，pnpm 往往最优解。
