## http 模块与 Web 服务器

### 最简 HTTP 服务器

#### http 模块、createServer 与 listen

**http 模块**：是 Node.js 内置的 HTTP 服务核心模块，随运行时发布，无需 npm 安装，通过 require 直接引入即可搭建服务器或发起客户端请求。

- 引入写法为 const http = require("http")，得到承载 createServer、request、get 等方法的模块对象。
- **createServer 方法**完整签名为 http.createServer(requestListener)，requestListener 是请求到达时调用的回调，可省略而改由 server.on("request") 补充。
- 回调固定接收两个参数：一个**请求对象**（IncomingMessage）与一个**响应对象**（ServerResponse），分别承载客户端数据与回写能力。
- **listen 方法**完整签名为 server.listen(port, host, callback)，port 必填、host 可选、callback 在就绪后执行一次；host 写 127.0.0.1 仅本机可访问，写 0.0.0.0 则可被同网段其他机器访问。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("你好，世界");
});

server.listen(3000, "127.0.0.1", () => {
  console.log("访问 http://127.0.0.1:3000");
});
```

> 回调参数顺序固定为（请求对象，响应对象），不可颠倒；两者都由 Node 在请求到达时自动创建并传入，无需手动构造。host 省略时默认绑定 0.0.0.0，并非"仅本机"。

**速记**：http **内置直引**，createServer **拿 req 与 res**，listen **绑端口**。



### 请求处理回调的执行时机

#### 每来一个请求触发一次且运行在单线程

**回调触发与线程模型**：createServer 的回调**每收到一个请求就执行一次**，且其中代码运行在 Node 的**同一个主线程**上，与事件循环、其他回调共享这一线程。

- 同一实例在生命周期内反复触发该回调，触发次数等于到达的客户端请求数，每次都得到一对全新的 req 与 res。
- 多个并发请求在某一时刻**只有一个回调在真正运行**，其余在事件循环队列中排队等待。
- 单线程免去多线程竞态与锁，却也意味着任何阻塞都会同时影响所有请求。
- 续 8 篇结论：单线程靠非阻塞与事件循环实现高并发，受限的只是同步计算本身。

```js
const http = require("http");
let count = 0;

const server = http.createServer((req, res) => {
  count += 1;
  res.end("这是第 " + count + " 次请求");
});

server.listen(3000, "127.0.0.1");
```

> 把"只在启动时执行一次"的逻辑（读配置、建连接池）写在回调之外，别误放进每次请求都会跑的回调，否则会重复执行、浪费资源。

**速记**：回调**一请求一触发**，共享**主线程**。



#### 重计算会阻塞所有请求

**阻塞危害**：若在请求回调里执行**长时间同步计算**，主线程被独占，事件循环无法派发其他请求的回调，于是所有连接同时卡住。

- 典型表现：一个用户触发大循环，其余用户的接口全部变慢甚至超时。
- 这与第 8 篇"CPU 密集任务会卡住整个服务"、第 11 篇"同步磁盘 IO 阻塞事件循环"本质相同，都是占满了唯一的主线程。
- 解决思路是把重活移出主线程（子进程、worker_threads）或切片让出事件循环，详见相关篇章。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  let sum = 0;
  for (let i = 0; i < 1e10; i++) sum += i; // 危险：独占主线程
  res.end(String(sum));
});

server.listen(3000, "127.0.0.1");
```

> [!WARNING]
> **警告内容**：请求回调里严禁放长时间同步计算或同步 IO。一旦主线程被占满，所有并发请求都会被拖垮，服务表现为整体无响应。凡可能慢的操作，一律走异步或交给其他线程/进程。

**速记**：回调里 **不放重计算，慢活异步或下放**。



### HTTP 协议要点回顾

#### 请求报文与响应报文的结构

**HTTP 报文**：是客户端与服务器之间交换的文本，二者都由"行、头、空行、体"四部分构成，是理解 req、res 各字段的原始来源。

- **请求报文**：请求行（方法 空格 请求目标 空格 HTTP 版本）、请求头（多行键值对）、空行、可选的请求体。
- **响应报文**：状态行（HTTP 版本 空格 状态码 空格 原因短语）、响应头、空行、响应体。
- 请求行与请求头对应请求对象的 method、url、headers；状态行与响应头由响应对象的 writeHead/setHeader 写入。
- 头与体之间用单独一个空行分隔，这正是"只能写一次头"考点的结构根源。

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 27

{"username":"alice","pwd":"x"}
```

> 请求体并非所有方法都有：GET、HEAD 通常无请求体，POST、PUT、PATCH 才常带。读懂报文结构，才能理解为什么 req 要以流的方式读取 body。

**速记**：请求**行头空体**，响应**行头空体**。



#### HTTP 的无状态特性

**无状态（Stateless）**：指 HTTP 协议本身**不保存**前后请求间的任何关联，服务器把每个到达的请求都当作全新、独立的调用来处理。

- 服务器默认不记得"上一秒是谁、刚做了什么"，两次请求之间没有任何上下文被协议自动保留。
- 这带来水平扩展的便利：任意请求可由任意实例处理，便于做负载均衡。
- 需要"记住用户"时，须借助 Cookie、Session、Token 等机制在应用层自行维持状态。

> 无状态是 HTTP 的设计选择而非缺陷：它让协议简单、可伸缩。把状态放到客户端或独立存储（如 Redis），才能既保持无状态又实现登录等连续体验。

**速记**：HTTP **不记事**，状态靠应用层补。



#### 常见请求方法与状态码分类

**方法与状态码**：请求方法是客户端意图的动词，状态码是服务器处理结果的三位数字归类，二者共同决定一次交互的语义。

- **常见请求方法**：GET 取资源、POST 提交、PUT 整体替换、PATCH 局部更新、DELETE 删除、HEAD 只取头、OPTIONS 探测。
- **1xx 信息**：请求已收到、继续处理，如 100 Continue。
- **2xx 成功**：已被正常处理，如 200 OK、201 Created、204 No Content。
- **3xx 重定向**：需客户端进一步动作，如 301 永久移动、302 临时移动、304 未修改。
- **4xx 客户端错误**：请求本身有问题，如 400 参数错、401 未认证、403 禁止、404 未找到、405 方法不允许。
- **5xx 服务端错误**：服务器处理失败，如 500 内部错误、502 网关错、503 不可用。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.method === "GET") {
    res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("GET 成功");
  } else {
    res.writeHead(405, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("方法不被允许");
  }
});

server.listen(3000, "127.0.0.1");
```

> 状态码是"服务器给客户端的信号"而非"业务成功与否"的全部。404 与 500 含义截然不同，排错时先看区间（4xx 查请求、5xx 查服务）能快速缩小范围。

**速记**：方法表**意图**，状态码分**五段**。



### 服务器对象、端口与主机

#### server.listen、server.close 与事件

**服务器对象**：是 http.createServer 返回的 http.Server 实例，除回调外还通过一组成员方法控制监听、停止并暴露事件。

- **server.listen(port, host, callback)**：启动监听；可重复调用前须先 close，否则端口冲突。
- **server.close(callback)**：停止接收新连接，已建立的连接处理完才真正关闭，回调在完全关闭后执行。
- **server.listening**：布尔属性，true 表示正处于监听状态，可用于运行期判断。
- **listening 事件**：成功开始监听后触发，等价于 listen 的第三个回调，适合打印启动日志。
- **error 事件**：绑定或运行出错时触发，端口被占用表现为 code 为 EADDRINUSE，不监听它会直接抛出未捕获异常致进程退出。

```js
const http = require("http");

const server = http.createServer((req, res) => res.end("hi"));

server.on("listening", () => console.log("监听已就绪"));
server.on("error", (err) => {
  if (err.code === "EADDRINUSE") console.error("端口被占用");
  else throw err;
});

server.listen(3000, "127.0.0.1");
```

> [!IMPORTANT]
> **重要内容**：服务器务必监听 error 事件。只要发生 EADDRINUSE 这类绑定错误而你没有捕获，Node 会以未处理异常终止整个进程，正在服务的所有连接一并断开。

**速记**：listen **开监听**，close **拒新连**，error **防崩**。



#### server.on("request") 与 createServer 回调等价

**request 事件**：http.Server 每次收到请求时会触发名为 request 的事件，其监听器与 createServer 的回调**完全等价**，二者注册的是同一处理逻辑。

- 写法一：createServer((req, res) => { ... }) 在创建时直接挂上回调。
- 写法二：先 createServer() 拿到 server，再用 server.on("request", (req, res) => { ... }) 补充监听。
- 两者可叠加：一个请求会依次触发 createServer 回调与所有 request 监听器，因此不要重复注册相同逻辑以免执行两次。
- 除 request 外，服务器还触发 connection、listening、error、close 等事件。

```js
const http = require("http");

const server = http.createServer();
server.on("request", (req, res) => res.end("由 request 事件处理"));
server.listen(3000, "127.0.0.1");
```

> 等价不等于互斥：createServer 回调与 on("request") 都会在请求到达时执行。若两套都注册了写响应的逻辑，第二次 end 会因头已发送而报错，务必只选一种方式。

**速记**：createServer 回调 **即 request 事件**。



#### 端口范围与常见端口

**端口**：是 TCP 连接在同一机器上区分服务的 16 位编号，范围 **0 到 65535**，服务器 listen 时从中选取一个进行绑定。

- **0 到 1023（特权端口）**：系统或标准服务占用，绑定通常需管理员权限，如 80 用于 HTTP、443 用于 HTTPS。
- **1024 到 49151（注册端口）**：普通应用可用，开发常用 3000、8080 等。
- **49152 到 65535（动态端口）**：操作系统临时分配，listen 传 0 时由系统从中挑一个返回。
- **80**：HTTP 默认端口；**443**：HTTPS 默认端口；**3000 / 8080**：Node 开发测试常用非特权端口。

```js
const http = require("http");

const server = http.createServer((req, res) => res.end("port demo"));
server.listen(0, "127.0.0.1", () => {
  console.log("随机端口：", server.address().port); // 由系统分配
});
```

> 端口是"门牌号"而非"速度"：选 3000 还是 8080 不影响性能，只影响访问时是否要显式带端口，以及是否撞上本机其他服务。

**速记**：端口 **0 到 65535**，80/443 是标准。



#### 127.0.0.1、0.0.0.0 与 EADDRINUSE

**绑定地址与冲突**：listen 的 host 决定监听哪块网卡，端口被别的进程占用时则抛出 EADDRINUSE 错误，二者都是绑定时必须弄清的事。

- **127.0.0.1（回环地址）**：只接受本机发起的连接，外部机器无法访问，常用于本地调试。
- **0.0.0.0（通配地址）**：监听所有网络接口，同网段乃至公网（防火墙放行时）都能连入，容器与云服务器对外暴露服务时多用它。
- **localhost**：一般解析为 127.0.0.1（也可能含 IPv6 的 ::1），语义偏向"本机"，不等价于 0.0.0.0。
- **EADDRINUSE**：地址已被使用的错误码，成因多为旧进程未退出或另一服务占着同端口；应在 error 事件中判断 err.code 并写清日志，而非忽略。

```js
const http = require("http");

const PORT = 3000;
const server = http.createServer((req, res) => res.end("ok"));

server.on("error", (err) => {
  if (err.code === "EADDRINUSE") {
    console.error("端口 " + PORT + " 已被占用，请释放或更换");
    process.exit(1);
  } else throw err;
});

server.listen(PORT, "127.0.0.1");
```

> [!CAUTION]
> **注意内容**：容器内服务若绑定 127.0.0.1，即使端口已映射出去，外部仍连不通——映射面向的是容器网络接口而非回环，部署时应绑定 0.0.0.0。端口冲突不要吞掉错误，否则服务"看似启动实则没在监听"。

**速记**：127.0.0.1 **仅本机**，0.0.0.0 **全接口**，占用即 **EADDRINUSE**。



### 请求与响应对象的主干

#### 请求对象的主干字段

**请求对象主干**：本次交互的客户端信息集中在请求对象上，method、url、headers、httpVersion 是路由与判别最依赖的四个字段，本篇仅点出主干、细节留第 17 篇。

- **req.method**：字符串，表示请求方法（如 GET、POST），用于判断客户端意图，通常为大写。
- **req.url**：字符串，包含请求的**路径与查询串**，但不含协议与主机，例如 /users?page=1；后续拆路径、取参数需配合 URL 模块（见第 18 篇）。
- **req.headers**：对象，键为小写后的请求头名、值为对应内容，例如 req.headers["content-type"]、req.headers["user-agent"]。
- **req.httpVersion**：字符串，表示客户端使用的 HTTP 协议版本，常见为 "1.1" 或 "1.0"。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  console.log("方法：", req.method);
  console.log("路径与查询：", req.url);
  console.log("协议版本：", req.httpVersion);
  console.log("用户代理：", req.headers["user-agent"]);
  res.end("ok");
});

server.listen(3000, "127.0.0.1");
// 访问 /search?q=node 时 req.url 为 "/search?q=node"
```

> req.url 是"原始字符串"而非解析后的对象；想拿到路径名或单个查询参数需借助 URL 与 URLSearchParams。headers 的值是字符串（或字符串数组），直接当数字/布尔比较会出错。

**速记**：method **表意图**，url **含路径查询**，headers **小写键**，httpVersion **记版本**。



#### writeHead、setHeader 与状态码

**writeHead 与 setHeader**：是响应对象写出状态与响应头的两种途径，writeHead 完整签名为 res.writeHead(statusCode, statusMessage, headers) 或 res.writeHead(statusCode, headers)。

- **statusCode（状态码）**：必填的三位整数，如 200、404、500，决定客户端如何理解本次响应；statusMessage 可选，省略时由状态码自动推导。
- **setHeader(name, value)**：把头存入**隐式头队列**，并不立刻发送，会与其他头合并，直到第一次 write 或 end 时才随响应一起发出。
- **writeHead**：**显式写出**状态行与全部响应头，调用即意味着头部已发送（flush）；之后再 setHeader 会因头已发送而报错。
- 二者择一、避免同头双写：先 setHeader 同名头再用 writeHead 写同键，后者覆盖前者。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.setHeader("X-Powered-By", "Node.js");
  res.end("用隐式头返回"); // 头尚未发出，可继续 setHeader
});

server.listen(3000, "127.0.0.1");
```

> [!TIP]
> **建议内容**：需"先设头、后面再补充"或让 Node 自动计算 Content-Length 时，优先用 setHeader；需一次性明确状态与全部头、强控制发送时机时，用 writeHead。

**速记**：setHeader **攒着发**，writeHead **立刻发**。



#### res.end 必须调用且响应头只能写一次

**结束与写头限制**：响应对象的 end 方法（完整签名 res.end(data, encoding, callback)）必须调用以结束响应；且响应头一旦发出就**不能再设置或修改**。

- **不调用 end 的后果**：响应头与连接迟迟不收尾，客户端一直等待，请求**挂起**，浏览器持续转圈、curl 不返回；每个请求必须且只能结束一次。
- **头不可重复写**：响应头随第一次 write/end（或 writeHead）发出后，再 setHeader 或 writeHead 会抛出 ERR_HTTP_HEADERS_SENT（Cannot set headers after they are sent to the client）。
- 根因在于 HTTP 报文头在空行之后就是响应体，协议层不允许回头改写已发出的头部。
- 规避：在第一次发送数据前统一决定好所有头，把写头逻辑集中、避免分支里重复写。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.write("第一段");
  res.end("结束"); // 必须调用，否则请求挂起
  // res.setHeader("X-Extra", "1"); // 会抛 ERR_HTTP_HEADERS_SENT
});

server.listen(3000, "127.0.0.1");
```

> [!WARNING]
> **警告内容**：ERR_HTTP_HEADERS_SENT 不是偶发 bug，而是违反"头只发一次"的铁律。凡看到该错误，检查是否有多条写头/结束路径（如正常分支与错误分支都写了头），把响应收敛为"每个请求恰好一次"。

**速记**：响应**必调 end**，头**只能发一次**。



### 返回 HTML、JSON 与读取请求体

#### 设置 Content-Type 与字符集

**Content-Type**：是响应头里声明"返回内容类型与编码"的字段，设置是否正确直接决定浏览器能否正确解析、中文是否乱码。

- 返回纯文本写 text/plain，返回网页写 text/html，返回 JSON 写 application/json，三者都要带 charset=utf-8 避免中文乱码。
- **中文乱码根源**：未指定或错配字符集时，浏览器按默认编码解读 UTF-8 字节，于是出现乱码；显式写 charset=utf-8 即可根治。
- 不写 Content-Type 时，部分客户端会按扩展名或内容猜测，行为不可靠，生产环境应始终显式声明。
- 必须在第一次 write/end 之前完成设置。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
  res.end("<h1>标题</h1><p>中文内容</p>");
});

server.listen(3000, "127.0.0.1");
```

```html
<h1>标题</h1>
<p>中文内容</p>
```

> 字符集写错比不写更隐蔽：例如写 charset=gbk 而数据实际是 UTF-8，乱码只在某些字符上出现，难以一眼定位，务必让编码声明与数据真实编码一致。

**速记**：Content-Type **定类型**，charset **防乱码**。



#### 返回 JSON 与返回 HTML 的写法

**两种常见响应**：Web 服务最常返回 JSON（接口）与 HTML（页面），二者写法仅在 Content-Type 与响应体构造上有别，其余流程一致。

- **返回 JSON**：把数据对象用 JSON.stringify 转为字符串，Content-Type 设为 application/json; charset=utf-8，再 end 出去。
- **返回 HTML**：直接 end 一段 HTML 文本，Content-Type 设为 text/html; charset=utf-8；要返回完整页面可拼接或读文件。
- JSON 必须序列化：直接 end(对象) 会触发类型错误，因为响应体只能是字符串或 Buffer。
- HTML 的标签原文用普通文字描述即可，必须展示标签结构时放入 html 标注的代码块（如本篇上例）。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.url === "/api") {
    const data = { name: "张三", age: 20 };
    res.writeHead(200, { "Content-Type": "application/json; charset=utf-8" });
    res.end(JSON.stringify(data));
    return;
  }
  res.writeHead(200, { "Content-Type": "text/html; charset=utf-8" });
  res.end("<p>这是 HTML 页面</p>");
});

server.listen(3000, "127.0.0.1");
```

> JSON 接口务必设对 Content-Type：若写成 text/plain，前端 fetch 后需手动 JSON.parse，且某些框架不会自动解析，易引发"拿到字符串而非对象"的困惑。

**速记**：JSON **先 stringify**，HTML **给 charset**。



#### 读取请求体：req 是可读流

**请求体的本质**：请求对象**同时是一个可读流（Readable Stream）**，客户端提交的请求体数据以"流"的形式分批到达，需通过流的方式读取而非一次性取完。

- 与第 13 篇所述 Stream 一脉相承：大体积数据不必整块驻留内存，而是边到边处理。
- 读取入口是流的 data 事件（拿数据块）与 end 事件（数据读完）；也可用 for await 语法异步迭代消费。
- 只有带请求体（POST、PUT、PATCH 等）时才会有 data 输出，GET 通常无体、不会触发 data。
- 流读到的块默认是 Buffer，需按 Content-Type 指定的编码（如 utf-8）转为字符串，并且必须在读取阶段设体积上限。

```js
const http = require("http");
const MAX = 1 * 1024 * 1024; // 1MB 上限

const server = http.createServer((req, res) => {
  let size = 0;
  const chunks = [];
  req.on("data", (chunk) => {
    size += chunk.length;
    if (size > MAX) {            // 超限立即掐断，防内存被吃满
      res.writeHead(413, { "Content-Type": "text/plain; charset=utf-8" });
      res.end("请求体过大");
      req.destroy();
      return;
    }
    chunks.push(chunk);
  });
  req.on("end", () => {
    const body = Buffer.concat(chunks).toString("utf-8"); // 统一转码避免半字符
    res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("已接收 " + size + " 字节");
  });
});

server.listen(3000, "127.0.0.1");
```

> [!CAUTION]
> **注意内容**：请求体体积限制缺失是真实的安全风险。务必在流式读取阶段就拦截超限请求，等全部收完再判断就为时已晚——内存早已被占用。用 Buffer.concat 后再统一 toString，可避免分片切在多字节字符中间导致碎字。

**速记**：请求体是**可读流**，data **攒分片**、end **统一处理**、超限**即掐断**。



### 路由初探与客户端请求

#### 按 method 与 url 手写路由与 404 处理

**手写路由**：在请求回调里依据 req.method 与 req.url 的分支判断，把不同请求分发到不同处理函数，是框架路由的思想雏形；未命中则回 404。

- 判断顺序通常先比 method（GET 或 POST），再比 url 路径，命中即调用对应逻辑并结束响应。
- 处理函数建议抽成独立的有意义函数，例如 handleHome、handleLogin，而非把全部逻辑堆在回调里。
- url 含查询串（如 /search?q=1），比路径时应只取 ? 之前的部分，或用 URL 模块解析。
- 404 必须显式写状态码：所有分支都不匹配时，writeHead(404) 后 end 一段说明，这是后续框架"错误处理中间件"的雏形。

```js
const http = require("http");

function handleHome(req, res) {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("首页");
}

const server = http.createServer((req, res) => {
  if (req.method === "GET" && req.url === "/") return handleHome(req, res);
  res.writeHead(404, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("404 未找到该资源");
});

server.listen(3000, "127.0.0.1");
```

> 手写路由在路径变多后会迅速膨胀成难以维护的 if 长串，适合理解原理；静态资源（如 /static/style.css）可单独判断路径前缀再读文件返回。真实项目应交由 Express 等框架（见第 26 篇）。

**速记**：路由靠 **method 加 url**，未命中 **兜底 404**。



#### http.get、http.request 与 fetch 对比

**发起外部请求**：Node 的 http 模块既能做服务器，也能以 http.get 与 http.request 充当客户端；自 Node 18 起还内置了 fetch。

- **http.request(options, callback)**：通用客户端方法，完整签名为 http.request(options[, callback])，options 可传 URL 字符串或含 host、port、method、path、headers 的对象；需手动调用 req.end() 才会真正发出。
- **http.get(options, callback)**：专用于 GET 的便捷方法，自动把 method 设为 GET 并代为调用 end()，使用更省事。
- **fetch(url)**：返回 Promise<Response>，用 await 取结果、res.json() 解析，写法贴近浏览器、比回调式 http.get 更线性。
- 三者 callback 或响应对象都是可读流（response 为 IncomingMessage），用 data/end 读取；版本上 fetch 在 Node 18 为实验、Node 21 起稳定。

```js
const http = require("http");

// http.get 发起 GET（内部已 end）
http.get("http://127.0.0.1:3000/", (res) => {
  let body = "";
  res.on("data", (c) => (body += c));
  res.on("end", () => console.log("状态码：", res.statusCode, "内容：", body));
});

// 用 fetch（Node 18+），写法更线性
async function callApi() {
  const resp = await fetch("http://127.0.0.1:3000/");
  const json = await resp.json();
  console.log("fetch 拿到：", json);
}
```

> [!TIP]
> **建议内容**：新项目且运行在 Node 18 以上时，优先用 fetch 处理常规外部调用，代码更简洁；需要精细控制连接、流式转发或兼容老版本时，再回退到 http.request。两者是"易用"与"可控"的取舍。http.request 忘记 end 是最常见的客户端"无响应"原因。

**速记**：get **自动 end**，request **手动 end**，fetch **Promise 风**。



### 常见坑

#### 忘记调用 res.end 与重复设置响应头

**坑一与坑二**：请求回调执行完却未调用 res.end 会让请求挂起；在头部已发送后再次 setHeader 或 writeHead 会抛 ERR_HTTP_HEADERS_SENT。

- 挂起表现：浏览器持续转圈、curl 不返回、连接数随时间累积把服务器拖垮；成因多为异常或提前 return 的分支遗漏了 end。
- 重复写头表现：日志出现 Cannot set headers after they are sent to the client；成因多为正常与错误分支都写了头、或异步回调里又补了一次 writeHead。
- 规避：每个分支（含错误分支）都确保走到 end 或 destroy；把写头逻辑收敛到一处，确保每个请求"恰好一次"。
- 关联考点见本篇"res.end 必须调用且响应头只能写一次"，二者是同一铁律的两面。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.url === "/ok") {
    res.end("ok"); // 正常分支有 end
    return;
  }
  res.writeHead(404, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("not found"); // 兜底也必须 end，否则挂起
});

server.listen(3000, "127.0.0.1");
```

> 判断是否"每路径都 end"的最快办法：把所有 return 与分支画出来，确认没有一条路径能跳过 end 而结束回调。凡写头前先想"此刻头发出去了没"。

**速记**：任一支路 **都要 end**，头 **只写一次**。



#### 回调中抛异常与未监听 error 事件

**坑三与坑四**：请求回调里未捕获的同步异常会让整个进程退出；服务器或请求对象的 error 事件若无人监听，会升级为未处理异常。

- 异常崩溃表现：单个错误请求把整个服务带崩，日志出现未捕获异常后进程退出；成因多为访问 undefined 属性、JSON.parse 了非法串却没 try 包裹。
- 忽略 error 表现：端口冲突、客户端中断等本可恢复的错误变成进程崩溃；成因多为只写业务回调、忘了 server.on("error") 等。
- 规避异常：对不可信输入（请求体、外部响应）用 try/catch 防御；进程层用 process.on("uncaughtException") 仅作最后防线，根因仍要修。
- 规避 error：服务器绑定 error 处理 EADDRINUSE，客户端收发时为 req、res 都挂上 error 监听。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  try {
    const bad = JSON.parse("{ not valid json");
    res.end(bad);
  } catch (err) {
    res.writeHead(500, { "Content-Type": "text/plain; charset=utf-8" });
    res.end("服务器内部错误");
  }
});

server.on("error", (err) => console.error("服务器错误：", err.message));
server.listen(3000, "127.0.0.1");
```

> [!WARNING]
> **警告内容**：请求回调里的异常会拖垮整个进程——因为 Node 是单线程，一个未捕获异常让主线程退出，所有用户同时掉线。对不可信输入务必做防御性处理，并对所有长生命周期对象挂 error 监听（低成本高收益），否则错误会升级为进程退出。

**速记**：回调异常 **崩进程**，error **不监听** 易退场。
