## Node 的架构：V8 与 libuv

### Node 的整体架构

**Node 的整体架构**：是分层的——**JavaScript 层** 调用 **内置模块**，经 **C/C++ Binding** 桥接到 **底层 C/C++ 库**（V8、libuv、c-ares 等），最终由操作系统提供服务。

- **JavaScript 层**：开发者代码与部分 JS 实现模块。
- **内置模块**：fs、net、http 等，部分用 C/C++ 实现提性能。
- **C/C++ Binding**：把 JS 调用翻译成 C/C++ 调用的胶水层。
- **底层库**：libuv、V8、c-ares、llhttp、OpenSSL、zlib。

```js
const fs = require("fs");
fs.readFile("a.txt", (err, data) => { /* 穿过 binding 落到 libuv */ });
```

> 你写的 JavaScript 在最上层，越往下越接近系统；Node 用统一 JS 接口屏蔽了底层差异。

#### 分层职责与底层库清单

**各层职责**：每层只做好自己的事，通过明确边界向上供能力、向下委工作。

- **JavaScript 层**：表达业务逻辑，调内置模块 API。
- **内置模块层**：实现文件、网络等核心能力，决定异步与回调方式。
- **Binding 层**：类型转换与调用转发，是 JS 与 C++ 的桥。
- **底层库层**：V8 执行、libuv 做 IO、OpenSSL 加密、zlib 压缩等。

```bash
node -p "process.versions"

# { node, v8, uv, zlib, openssl, ... }

```

> **内置模块**既可纯 JS（工具模块），也可 C++（如 fs 核心）；Node 按性能与成本选择落地层。底层库大多独立于 Node 演进，Node 把它们整合成协调一致的运行时。



### V8 引擎

**V8 引擎**：是 Google 开发的 **高性能 JavaScript 引擎**，负责编译执行 JavaScript，是 Node 能跑 JS 的根本。

- **编译执行**：即时编译为机器码，而非逐行解释。
- **标准实现**：完整支持 ECMAScript 规范。
- **能力边界**：只执行 JS，**不提供任何 IO**。

```js
const double = (n) => n * 2;
console.log([1, 2, 3].map(double)); // [2, 4, 6]
```

> 一句话：**V8 负责"算"，libuv 负责"等"**；Node 高性能来自二者配合，而非 V8 单独提供 IO。

**速记**：分层**各司其职，边界清晰**。

#### 高性能引擎、JIT 与垃圾回收

**JIT（即时编译）**：是 V8 在运行时把 JS 编译为机器码并持续优化的技术，避免纯解释低效。

- **解释与编译结合**：先快解释，再把热点编译优化。
- **类型反馈**：据实参类型生成特化机器码，提速明显。
- **去优化**：类型假设失效时回退，保证正确优先性能。

```js
function add(a, b) { return a + b; }
for (let i = 0; i < 1000000; i++) add(i, 1);
```

> JIT 让"脚本语言"逼近编译型速度；代价是**冷启动稍慢**、内存占用略高。垃圾回收（GC）则自动回收无用内存，分新生代（Scavenge）与老生代（标记-清除/整理），长时间运行服务的 GC 停顿会直接影响延迟。

**速记**：V8 靠**JIT 编译与垃圾回收**提速。



#### Ignition 与 TurboFan

**Ignition 与 TurboFan**：是 V8 的**解释器**与**优化编译器**，构成现代 V8 编译管线。

- **Ignition（解释器）**：先把 JS 编译为字节码并立即执行，保证快启动。
- **TurboFan（优化编译器）**：把热点字节码编译为高度优化机器码。
- **协作**：Ignition 先跑，TurboFan 据类型反馈深度优化。

```bash
node -p "process.versions.v8"
```

> 现代 V8 不是"单纯解释器"。**Ignition 负责快，TurboFan 负责快且优**，二者协作是 Node 性能来源。

**速记**：**Ignition 解释，TurboFan 优化**。



#### V8 只负责执行 ECMAScript，不提供 IO

**V8 能力边界**：只管 JS 的计算与内存，**完全不涉及文件、网络等 IO**。

- **能做的**：变量、函数、对象、Promise、内存管理。
- **不能做的**：读写文件、发起网络请求、监听端口。
- **IO 谁做**：由 libuv 经 binding 承接，V8 只等回调。

```js
const result = Math.max(1, 2, 3); // V8 能算
// fs.readFile("a.txt", cb);      // 能力来自 libuv，非 V8
```

> 把"Node 能 IO"归功于 V8 是误解；准确说：**V8 让 JS 能算，Node 通过 libuv 让 JS 能 IO**。



### libuv

**libuv**：是 Node 依赖的**跨平台异步 IO 库**，提供事件循环与线程池，是 Node 异步能力的真正基石。

- **事件循环（Event Loop）**：调度各类回调执行顺序。
- **异步 IO**：把文件、网络等阻塞操作变非阻塞。
- **跨平台**：在 Linux、macOS、Windows 提供一致接口。

```bash
node -p "process.versions.uv"
```

> libuv 最初为 Node 而生，如今也被其他项目使用；它是**让单线程 JS 拥有高并发 IO 的秘密武器**。

**速记**：V8**只管计算，不管 IO**。

#### 事件循环 Event Loop

**事件循环**：是 libuv 中不断"取任务、执行回调"的循环，是 Node 异步调度核心。

- **循环本质**：反复检查是否有待处理任务，有则取出执行。
- **阶段划分**：定时器、待处理 IO、立即回调、轮询、检查、关闭等阶段。
- **单轮推进**：每轮处理完当前阶段再进下一阶段。

```js
setTimeout(() => console.log("定时器回调"), 0);
console.log("同步代码先执行");
// 同步代码先执行 → 定时器回调
```

> 这解释了为何**同步代码先于异步回调**：同步在"执行用户代码"阶段跑完，异步要等循环轮到对应阶段。

**速记**：事件循环**取任务、跑回调**。



#### 线程池与 UV_THREADPOOL_SIZE

**线程池（Thread Pool）**：是 libuv 内部维护的工作线程组，执行无法纯异步完成的阻塞型系统调用。

- **默认大小**：libuv 线程池默认 **4 个线程**。
- **可调上限**：环境变量 **UV_THREADPOOL_SIZE** 调整，最大值为 **1024**。
- **共享**：同进程内所有操作**共用**这一个线程池。

```bash
export UV_THREADPOOL_SIZE=8
node app.js
```

> **UV_THREADPOOL_SIZE** 必须**在 Node 启动前**设置；调得过大不能线性提升吞吐，反增线程切换成本。

**速记**：线程池**默认 4 个，可用环境变量调**。



#### 为什么 IO 操作由 libuv 完成

**IO 委托 libuv**：因底层很多 IO 在部分平台非真正异步，libuv 用"事件循环 + 线程池"抹平成统一接口。

- **平台差异**：不同系统异步 IO 接口不一（io_uring、kqueue）。
- **兜底异步**：对无法原生异步的操作，丢进线程池模拟异步，避免阻塞主线程。
- **统一抽象**：上层 JS 只看到"异步回调"，无需关心底层。

```js
const fs = require("fs");
fs.readFile("big.txt", (err, data) => {
  if (err) throw err;
  console.log(data.length);
});
```

> 正是 libuv 的抽象，让 Node 在各操作系统上**行为一致**：写一次异步代码，libuv 负责高效落地。



### 其他核心依赖

**其他核心依赖**：除 V8 与 libuv，Node 还依赖若干专攻单项能力的 C/C++ 库，覆盖网络、安全与压缩。

- **c-ares**：处理 DNS 解析。
- **llhttp**：解析 HTTP 报文。
- **OpenSSL**：提供加密与 TLS。
- **zlib**：提供数据压缩。

```bash
node -p "process.versions.openssl"
node -p "process.versions.zlib"
```

> 这些库让 Node **不必从零造轮子**：DNS、HTTP、加密、压缩由久经考验的成熟库承担。

**速记**：**平台异步不齐，libuv 来兜底**。

#### c-ares、llhttp 与网络解析

**c-ares 与 llhttp**：分别负责 Node 的异步 DNS 解析与 HTTP 报文解析。

- **c-ares**：异步 DNS，解析在底层完成经回调返回，不阻塞主线程。
- **llhttp**：高性能 C 库，把字节流拆成请求行、头部与正文。
- **可靠性**：llhttp 严格按规范解析，拦截畸形报文。

```js
const dns = require("dns");
dns.lookup("example.com", (err, address) => {
  if (err) throw err;
  console.log("解析结果：", address);
});
```

> DNS 解析耗时不可控，正因有 **异步 DNS 库**，Node 等待解析时仍能处理其他请求；你写的 req.url、req.headers 都建立在 llhttp 解析出的结构之上。

**速记**：**c-ares 管 DNS，llhttp 管 HTTP 解析**。



#### OpenSSL 与 zlib

**OpenSSL 与 zlib**：分别提供 Node 的加密安全和数据压缩能力。

- **OpenSSL**：为 https、tls 提供安全传输，crypto 算法多由其实现。
- **zlib**：支持 gzip、deflate，用于 HTTP 压缩与文件流式压缩。
- **CPU 密集**：压缩常进 libuv 线程池，避免阻塞主线程。

```js
const crypto = require("crypto");
const hash = crypto.createHash("sha256").update("hello").digest("hex");
console.log(hash); // 64 位十六进制串
```

> **crypto 与 https 模块**背后都是 OpenSSL；Node 升级常伴随 OpenSSL 版本更新，安全补丁主要来自这一层。



### Node Bindings

**Node Bindings**：是 JavaScript 与 C/C++ 之间的**胶水层**，把上层 JS 调用翻译成底层库函数调用。

- **桥接**：让 JS 够得到用 C/C++ 写的底层能力。
- **类型转换**：在 JS 值与 C++ 类型间编解码。
- **无感存在**：开发者只调 JS API，感知不到中间层。

```js
const fs = require("fs");
fs.readFile("a.txt", () => {}); // 内部经 binding 调 libuv 文件读取
```

> Binding 是 Node "**用 JS 写界面、用 C++ 干重活**"得以实现的关键；没有它，JS 碰不到 libuv、OpenSSL。

**速记**：**OpenSSL 管加密，zlib 管压缩**。

#### 一次 fs 调用如何落到系统调用

**fs 调用落地路径**：从 JS 一路穿透到操作系统内核的调用链，清晰展示分层协作。

- **第一步**：JS 调 fs.readFile，进入内置模块。
- **第二步**：内置模块经 C++ Binding 把参数转为 C++ 结构。
- **第三步**：Binding 调 libuv 对应函数（uv_fs_read）。
- **第四步**：libuv 在线程池或事件循环发起真正系统调用。
- **第五步**：内核完成读盘，结果沿原路回调 JS。

```js
const fs = require("fs");
fs.readFile("a.txt", "utf8", (err, content) => {
  console.log(content); // 数据已穿过 binding、libuv、系统调用回到回调
});
```

> 一次 fs.readFile 背后是"JS → 内置模块 → binding → libuv → 系统调用 → 原路返回"的旅程；理解这条链就理解了 Node 异步本质。



### Node 的执行过程

**Node 的执行过程**：从启动到退出，大致经历**启动 → 加载内置模块 → 创建 V8 实例 → 执行用户代码 → 事件循环 → 进程退出**。

- **启动**：Node 二进制初始化运行环境。
- **加载内置模块**：fs、http 等核心模块挂好。
- **创建 V8 实例与上下文**：分配堆、建执行上下文。
- **执行用户代码**：运行入口文件。
- **事件循环运行**：处理异步回调直至无任务。
- **进程退出**：队列清空或主动退出。

```bash
node -e "console.log('用户代码执行阶段')"
```

> 关键点：V8 实例在**用户代码之前**建好，事件循环在**用户代码之后**才持续运转，二者顺序不可颠倒。

**速记**：调用链**JS → libuv → 系统调用 → 内核**。

#### 启动加载与 V8 实例执行

**启动与加载**：是 Node 最前的准备阶段，确保运行所需先就位。

- **环境准备**：设置进程对象、全局变量等。
- **内置模块注册**：fs、path、http 等被注册，可被 require。
- **原生优先**：核心能力多以 C++ 实现并提前编译进二进制。

```js
const fs = require("fs");
const path = require("path");
console.log(typeof fs.readFile, typeof path.join);
```

> 内置模块启动期就加载好，**首行 require("fs") 几乎零成本**——只是拿已注册引用，非现场编译。V8 实例与用户代码阶段先建上下文、再逐行执行入口，同步部分一次性跑完，异步回调留待事件循环。

**速记**：启动阶段**先备料、再执行**。



#### 事件循环与进程退出

**事件循环与退出**：Node 收尾阶段，决定是否继续等待、何时结束。

- **持续轮询**：只要有待处理异步任务，循环就继续。
- **退出条件**：任务清空且无人保持循环活跃，进程自然退出。
- **主动退出**：process.exit() 可立即结束。

```js
setTimeout(() => console.log("还有任务，循环继续"), 1000);
// 约 1 秒后输出，随后进程退出
```

> 想让进程**常驻**（如 Web 服务器），必须保持事件循环有事做——server.listen 正用底层句柄让循环一直转。



### 单线程的含义

**单线程的含义**：Node 语境下特指 **JavaScript 主线程是单线程的**——同一时刻只有一段 JS 在跑，但不意味 Node 进程只有一个线程。

- **主线程单线程**：你写的 JS 在单一线程顺序执行。
- **进程多线程**：底层仍有 libuv 线程池、V8 辅助线程等。
- **误区澄清**："Node 是单线程"省略了"主线程"限定。

```js
console.log("A");
console.log("B"); // 永远先 A 后 B，严格顺序
```

> 准确说法是：**Node 的 JS 执行是单线程的，但 Node 的进程是多线程的**；混淆二者会导致性能模型误判。

**速记**：**循环空转且无任务，进程即退出**。

#### JavaScript 主线程单线程

**主线程单线程**：所有 JS 回调在同一条线程排队执行，互不并行。

- **无并行计算**：两段 JS 不能真正同时跑，只能事件循环调度交替。
- **共享状态简单**：无需为 JS 层数据加锁，避免竞态复杂度。
- **阻塞代价高**：一段长计算会卡住所有后续回调。

```js
const start = Date.now();
while (Date.now() - start < 2000) { /* 空转两秒 */ }
console.log("这两秒事件循环被按住，其他回调全排队");
```

> **单线程**最大约束：主线程重计算会**阻塞整个事件循环**，这是 Node 不擅长 CPU 密集任务的根本原因。

**速记**：**JS 回调排队走同一条线程**。



#### 不代表 Node 只有一个线程

**Node 并非只有一个线程**：除 JS 主线程，libuv 线程池、V8 后台线程等都在并行工作。

- **libuv 线程池**：默认 4 个，处理文件 IO、DNS、压缩等。
- **V8 辅助线程**：参与 GC、编译等底层任务。
- **主线程**：独占 JS 执行，与上述线程协作。

```bash
export UV_THREADPOOL_SIZE=8
node app.js
```

> "Node 单线程"是**针对 JS 执行**的缩略；真正干 IO 重活的线程，藏在 libuv 线程池里与主线程并行。

**速记**：**JS 是单线程，Node 不是**。



#### 哪些操作在线程池里完成

**线程池操作**：被 libuv 放进工作线程执行的阻塞型任务，避免拖垮主线程。

- **文件 IO**：fs 多数读写操作。
- **crypto**：加解密、哈希等计算。
- **zlib**：压缩与解压。
- **DNS lookup**：域名解析（部分实现路径）。

```js
const crypto = require("crypto");
crypto.pbkdf2("pwd", "salt", 100000, 64, "sha512", () => {
  console.log("计算完成，回到主线程");
});
```

> 注意区分：**网络 IO（socket）由事件循环用 OS 异步机制处理，不占线程池**；文件 IO、crypto、zlib、DNS lookup 才落线程池，这是性能调优关键认知。



### Node 的线程模型

**Node 的线程模型**：由 **JavaScript 主线程** 加 **libuv 线程池** 构成，主线程跑业务、线程池跑阻塞底层任务，二者经事件循环衔接。

- **主线程**：执行 JS，驱动事件循环。
- **libuv 线程池**：默认 4 线程，并行执行阻塞操作。
- **协作**：主线程派活给线程池，线程池干完回调主线程。

```js
fs.readFile("a.txt", () => console.log("主线程收到结果"));
```

> "**一个主线程调度、一组工作线程干活**"是 Node 兼顾"简单"与"高并发"的设计核心。

**速记**：**阻塞型任务下沉线程池**。

#### 主线程与 libuv 线程池

**主线程与线程池分工**：是 Node 并发能力来源——主线程不被重活拖住，重活交线程池并行。

- **主线程负责**：执行 JS、调度事件循环、处理已完成回调。
- **线程池负责**：文件读写、加密、压缩、DNS 等阻塞操作。
- **衔接点**：线程池完成后，结果以回调回主线程事件循环。

```js
const crypto = require("crypto");
for (let i = 0; i < 4; i++) {
  crypto.pbkdf2("pwd", "salt", 100000, 64, "sha512", () => console.log(`任务 ${i} 完成`));
}
```

> 默认 **4 个线程池线程**，上述 4 个加密任务近乎并行；任务数远超 4 会在线程池排队，等空闲线程。

**速记**：**主线程调度，线程池干重活**。



#### 为什么 libuv 默认线程池是 4 个线程

**默认 4 线程的取舍**：libuv 在"并行度"与"线程开销"间做的经验平衡，非硬性上限。

- **够用常见场景**：多数服务并发阻塞操作不会长期远超 4。
- **控制开销**：线程占内存、有切换成本，过多反拖慢。
- **可调非固定**：UV_THREADPOOL_SIZE 可改，最大到 1024。

```bash
export UV_THREADPOOL_SIZE=16
node app.js
```

> **4 是默认值不是最优解**：IO 密集且阻塞任务多时调大到 8 或 16 更顺；盲目拉满 1024 只浪费内存，需以压测为依据。



### 回调即异步的设计哲学

**回调即异步的设计哲学**：Node 早期以**回调函数**作为异步结果通知机制的核心范式——把"完成后做什么"作为参数传入，而非同步等待返回值。

- **函数即续体**：把后续逻辑写成回调传入异步 API。
- **非阻塞**：调用后立即返回，不空等结果。
- **通知到位**：操作完成时由运行环境调用你的回调。

```js
fs.readFile("a.txt", (err, data) => {
  if (err) throw err;
  console.log(data);
});
```

> 回调解决了"**不阻塞主线程**"：调异步 API 后主线程立刻去干别的，等底层完成再回来执行回调。

**速记**：4 是**经验平衡值，不是上限**。

#### 为什么 Node 大量使用回调

**为何依赖回调**：事件循环模型下，回调是把异步结果"送回主线程"最自然、最早可用的机制。

- **契合事件循环**：回调天然适合"完成后通知"调度。
- **历史最早**：早期 JS 无 Promise 与 async/await，回调是主力。
- **零额外抽象**：直接把函数交底层，开销最小。

```js
const http = require("http");
http.get("https://example.com", (res) => {
  let body = "";
  res.on("data", (chunk) => (body += chunk));
  res.on("end", () => console.log("长度：", body.length));
});
```

> 即便今天有 **Promise 与 async/await**，Node 大量底层 API 仍以回调为基石；新语法多是把它们"包裹"成易读形式。

**速记**：回调**把异步结果送回主线程**。



#### 回调地狱的出现

**回调地狱（Callback Hell）**：多层嵌套回调导致代码向右缩进、难读难维护的反模式。

- **顺序依赖**：下一步必须等上一步结果，只能层层嵌套。
- **错误处理分散**：每层都要判 err，样板代码膨胀。
- **结构扭曲**：代码呈"金字塔"状向右无限缩进。

```js
fs.readFile("a.txt", (err, a) => {
  if (err) return handle(err);
  fs.readFile(a, (err, b) => {
    if (err) return handle(err);
    fs.readFile(b, (err, c) => {
      if (err) return handle(err);
      console.log(c);
    });
  });
});
```

> 出路是**升级抽象**：用 Promise 的链式 then 或 async/await 扁平写法替代嵌套；Node 现已原生支持后者，新代码应优先采用。

```js
const fs = require("fs").promises;
async function readChain() {
  const a = await fs.readFile("a.txt", "utf8");
  const b = await fs.readFile(a, "utf8");
  const c = await fs.readFile(b, "utf8");
  console.log(c);
}
readChain();
```

**速记**：**层层嵌套向右爬**即回调地狱。
