## Express 框架基础

### Express 的定位与版本选择

#### Express 是极简的 Node Web 框架

**Express**：是基于 Node 内置 **http 模块** 封装的极简 Web 应用框架，只提供 **路由分发** 与 **中间件（middleware）管道** 这两样骨架，其余能力由开发者按需组合。

- 它在原生 http 的"请求回调"之上，抽象出声明式路由与层层中间件，省去手写 if 分支判断 method 与 url 的繁琐。
- 它 **不强制项目结构、不绑定数据库、不内置 ORM**，给了开发者最大自由度，这也是它被称为"非框架的框架"的原因。
- 生态极其丰富，社区沉淀了大量中间件（如日志、鉴权、压缩、CORS），几乎任何需求都能找到现成包。
- 它的设计哲学是 **最小、灵活、可组合**，适合从微型接口到中大型 REST 服务的广泛场景。

> Express 的"极简"不等于"功能弱"：它把通用能力做成可插拔中间件，需要时才挂载，从而保持核心精简。与第 16 篇原生 http 相比，同样是返回文本，Express 用几行声明即可替代一整段手写路由分发。

**速记**：Express **薄封装 http**，只给 **路由加中间件**。



#### 与其他框架的位置对比

**框架坐标**：Express 处于 Node Web 框架谱系中的"经典中庸"位置，比它更薄的有 Koa，比它更重的有 NestJS，比它更偏性能的有 Fastify，选型取决于项目对约定与性能的要求。

- **Koa**：同样由 Express 原班团队打造，更"裸"——核心只保留中间件机制与上下文对象，连路由都要额外引入；适合追求极致精简与可控的团队。
- **NestJS**：面向企业级的全功能框架，强约定、以 TypeScript 优先、依赖注入驱动，底层可跑在 Express 或 Fastify 之上；适合大型、强结构项目。
- **Fastify**：以性能与低开销为卖点，内置 schema 校验与日志，吞吐表现优于 Express；适合对延迟敏感的高并发服务。
- **Express**：介于之间，学习曲线平缓、资料最多、中间件最全，是多数业务系统的稳妥默认。

> 选型不是"谁更好"，而是"谁更贴合约束"：快速验证用 Express 或 Koa，强规范团队协作用 NestJS，极致性能场景评估 Fastify。Express 仍是社区认知度与招人成本的最低公约数。

**速记**：Koa **更裸**、NestJS **更重**、Fastify **更快**、Express **最稳**。



#### 版本选择：4.x 主流、5.x 已发布

**版本现状**：Express 目前 **4.x 是绝对主流版本**，长期处于稳定维护；**5.x 已正式发布**，在保留多数 API 兼容的同时修正了若干历史行为，本篇示例统一以 4.x 为准。

- 4.x 自发布以来十年未做大版本跃迁，API 稳定、教程与中间件兼容性最好，是生产项目的默认选择。
- 5.x 引入了 Promise 化的异步错误处理、对路由路径的更严格解析等改进，但部分旧中间件可能不兼容，升级需评估。
- 安装时可用 npm install express 取最新 4.x，或 npm install express@4 显式锁定大版本，避免意外升到 5.x。
- 生态里大量中间件（如 body-parser、cors）的示例都基于 4.x 书写，新手跟学时以 4.x 最不易踩版本坑。

> 5.x 最重要的体验改善是异步错误可被 Express 自动捕获并交给错误处理中间件（详见本篇"常见坑"一节）。在未升级前，回调或 async 函数里的异常仍需开发者自行 try/catch 或调用 next(error)。

**速记**：生产用 **4.x 稳**，尝鲜看 **5.x 新**。



### 安装与项目初始化

#### 用 npm init 初始化项目

**初始化项目**：在空目录执行 **npm init** 会引导生成 **package.json** 清单文件，它是 Node 项目的元数据与依赖入口，Express 安装后也会登记于此。

- 完整写法是 npm init，按提示填写名称、版本、入口等字段；想跳过问答可加 -y 参数一次性生成默认文件。
- 生成的 package.json 记录项目名称、版本、**入口文件（main）**、**脚本（scripts）** 与 **依赖（dependencies/devDependencies）**。
- 它让项目可复现：其他人拿到代码后只需 npm install 就能按其中的依赖清单装齐所有包。
- 初始化后再安装 Express，包名会自动写入 dependencies，无需手工编辑。

```bash
mkdir my-app
cd my-app
npm init -y
# 生成 package.json
```

> npm init 只生成清单、不安装任何包；真正的依赖安装要另跑 npm install。忘做初始化直接装包时，npm 也会自动补一个最简 package.json，但字段不全。

**速记**：npm init **生清单**，依赖随装随登记。



#### 用 npm install express 安装并登记依赖

**安装命令**：在已初始化项目内执行 **npm install express**，会把 Express 及其依赖下载到 **node_modules** 目录，并把版本范围写入 package.json 的 dependencies。

- 写法 npm install express 等价于 npm install express --save，4.x 起 save 是默认行为，无需额外参数。
- 仅开发期使用、运行时不依赖的包（如 nodemon）应加 --save-dev，落入 devDependencies。
- 安装完成后，项目里出现 **node_modules 目录**（存放真实代码，通常不提交 git）与写入依赖的 package.json。
- 他人克隆项目后执行 npm install（不带包名）即按 package.json 还原全部依赖，实现环境一致。

```bash
npm install express
# 或锁定 4.x 系列
npm install express@4
```

> node_modules 体积往往很大，应在 .gitignore 中忽略、不要提交到仓库。依赖的"真相"保存在 package.json 与 package-lock.json，靠它们还原即可。

**速记**：npm install express **装包入 node_modules、登记 dependencies**。



#### package.json 的 type 字段决定模块系统

**模块系统选择**：**package.json 里的 type 字段** 决定项目默认用 CommonJS 还是 ES Module，**不加该字段时默认 CommonJS**；设为 module 则默认启用 ES Module（import/export 语法）。

- 默认（无 type 或 type 为 commonjs）：用 require 与 module.exports 引入与导出，文件名可用 .js。
- type 为 module：用 import 与 export，同样可用 .js；若想在该模式下写 CommonJS，需把文件改成 .cjs。
- 反向地，在无 type 的 CommonJS 项目中想写 ES Module，可把文件命名为 .mjs。
- 两种写法本篇都给出示例，Express 本身对两者均支持，选哪一种取决于团队与构建链约定。

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "dependencies": {
    "express": "^4.19.2"
  }
}
```

> 混用两套模块系统最容易报 ERR_REQUIRE_ESM 之类的错。一个项目应固定一套；升级老项目到 ESM 时，连带第三方依赖是否支持也要一并确认。

**速记**：type 缺省 **CommonJS**，置 module **转 ESM**。



### 最小可运行应用

#### 引入 express 并调用 express 创建 app

**创建 app**：无论 CommonJS 还是 ESM，都要先 **引入 express 模块**，再 **调用 express() 这个函数** 得到一个 **app 应用对象**，后续路由与配置都挂在它上面。

- CommonJS 写法：const express = require("express"); 然后 const app = express();。
- ES Module 写法：import express from "express"; 同样以 const app = express(); 得到 app。
- express 是一个函数，调用它（不是 new）才返回应用实例，这是 Express 的约定。
- 返回的 app 既是配置容器，也是一个可被 http 服务器调用的请求处理函数。

```js
// CommonJS
const express = require("express");
const app = express();

// 或在 ES Module 中
// import express from "express";
// const app = express();
```

> 常见误写是把 express 当构造函数用 new express()，这是错的：express 自身是可调用工厂函数，直接调用即可。引入时若用解构 const { express } = require("express") 也会拿到 undefined，应整体引入默认导出。

**速记**：express **是函数，调用得 app**。



#### 用 app.listen 启动服务

**启动服务**：在得到 app 后调用 **app.listen(port, callback)** 即可让 Express 绑定端口、开始监听请求，callback 在就绪后执行一次，常用于打印访问地址。

- 完整签名为 app.listen(port, host, callback)，port 必填、host 可选、callback 可选；省略 host 时默认监听所有网卡。
- 它内部其实就是帮你用 http.createServer(app) 建好服务器再 listen，省去手工拼装的样板。
- 端口建议用 1024 以上的非特权端口（如 3000、8080），避开 80/443 所需的管理员权限。
- 生产环境端口应从环境变量读取而非硬编码，做法见本篇"环境变量与端口"一节。

```js
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  res.send("你好，Express");
});

app.listen(3000, () => {
  console.log("服务已启动：http://127.0.0.1:3000");
});
```

```bash
node app.js
curl http://127.0.0.1:3000
# 输出：你好，Express
```

> listen 的回调只跑一次，不要把"每请求要执行"的逻辑放进去。需要在启动时执行一次的初始化（读配置、建连接池）才适合放在回调或 listen 之前。

**速记**：app.listen **绑端口、起服务**。



### app 对象的本质

#### app 是可传给 http.createServer 的请求处理函数

**app 的本质**：Express 的 **app 对象本质上就是一个标准的请求处理函数**，签名与 http 模块的请求回调一致（接收请求对象与响应对象），因此可直接交给 http.createServer 使用。

- 因为 app 是 (req, res) => {} 形态的函数，所以 http.createServer(app) 完全合法，Express 在背后正是这么封装 listen 的。
- 这意味着你既能用 app.listen 简化启动，也能在需要精细控制服务器（如挂载 upgrade 事件、复用同一 server 跑 WebSocket）时，自行 new http.Server 并传入 app。
- 理解这一点，就能把 Express 看作"对原生 http 的一层增强回调"，而非另起炉灶的体系。

```js
const http = require("http");
const express = require("express");
const app = express();

app.get("/", (req, res) => res.send("经 http 模块托管"));

// app 本身就是请求处理函数，可直接交给 createServer
const server = http.createServer(app);
server.listen(3000, () => console.log("http + express 启动"));
```

> 当你需要同一个 TCP 服务器同时服务 HTTP 与 WebSocket 时，这种"把 app 交给 createServer"的写法几乎是必选项——Express 只处理普通请求，升级连接交给 ws 库。

**速记**：app **即请求处理函数**，可交 createServer。



#### 路由与配置都挂载在 app 上

**app 的角色**：app 既是 **请求处理器**，也是 **全局配置与路由的容器**——所有路由规则、中间件、模板引擎与错误处理都通过 app 上的方法注册。

- 路由注册：app.get、app.post 等把"路径 + 处理器"登记进内部的路由栈。
- 中间件注册：app.use 把中间件挂到指定或全局位置，决定请求处理链的先后顺序。
- 配置项：app.set 用于设置运行参数（如视图引擎、信任代理），app.locals 存放应用级共享变量。
- 这种"一切挂在 app"的设计，让应用像搭积木一样逐步装配，也是第 26 篇深入路由与中间件的基础。

```js
const express = require("express");
const app = express();

app.set("view engine", "ejs"); // 配置模板引擎
app.use(express.json());        // 挂载解析中间件
app.get("/health", (req, res) => res.send("ok")); // 注册路由

app.listen(3000);
```

> app 上的方法大致分两类：一类改变"处理链"（use、get、post），一类改变"运行参数"（set、locals）。分不清时会把配置写成路由，记住"动词式多为路由、set 式多为配置"即可。

**速记**：app **挂载路由、中间件与配置**。



### 路由方法、路径匹配与请求对象增强

#### app.get 等路由方法注册处理器

**路由方法**：Express 为常见 HTTP 方法各提供同名方法，形如 **app.get(path, callback)**、**app.post(path, callback)**，把"某方法 + 某路径"映射到对应的处理函数。

- 方法集合覆盖 get、post、put、patch、delete、head、options，命名与 HTTP 动词一一对应。
- 完整签名 app.get(path, callback) 中，path 是匹配规则，callback 是 (req, res) => {} 形式的处理器（可串联多个）。
- 同一个路径可同时注册不同方法的处理器；Express 只调用"方法 + 路径"双匹配的那一个。
- 所有方法之外还有 app.all，匹配任意 HTTP 方法，常用于统一预处理。

```js
const express = require("express");
const app = express();

app.get("/articles", (req, res) => res.send("文章列表"));
app.post("/articles", (req, res) => res.send("创建文章"));
app.put("/articles/:id", (req, res) => res.send("更新文章"));

app.listen(3000);
```

> 路由方法的第一个参数必须是路径（字符串或模式），把路径写错成 req.url 之类的判断是退回原生写法的反模式。多处理器时写成 app.get(path, a, b, c)，它们按顺序形成中间件链。

**速记**：app.get/post/put **方法加路径映射处理器**。



#### 路径支持字符串、模式与参数占位

**路径匹配**：Express 路由的 path 参数支持 **精确字符串**、**带通配符的模式** 与 **冒号参数占位**，比原生手写 url 比较更表达力更强。

- **精确字符串**：如 "/about" 只匹配该路径，不含查询串（查询串不参与匹配）。
- **冒号占位**：如 "/users/:id" 中 :id 是动态段，命中后可在 req.params.id 取到实际值，适合资源详情页。
- **正则与通配**：可用 * 匹配一段、或用正则 /user/.+/profile 做精细控制，复杂场景才需要。
- 多段动态可用 "/files/:dir/:name"，所有冒号段都会被解析进 req.params 对象。

```js
const express = require("express");
const app = express();

app.get("/users/:id", (req, res) => {
  res.send("用户 " + req.params.id);
});

app.get("/files/*", (req, res) => {
  res.send("匹配任意以 /files/ 开头的路径");
});

app.listen(3000);
```

> 路径里的 : 段只捕获"一段"（到下一个斜杠为止），不会跨斜杠；想匹配含斜杠的剩余部分要用 * 或 /:rest*。查询串（? 之后）永远不参与路由匹配，取参数要走 req.query。

**速记**：路径 **字符串精确、冒号取参、星号通配**。



#### 请求对象增强：req.params 与 req.query

**req.params**：是 Express 对原生请求对象的 **增强属性**，存放路由中冒号占位解析出的路径参数，键名与占位名一一对应，取值即字符串。

- 定义路由 "/users/:id" 且访问 "/users/42" 时，req.params.id 的值为字符串 "42"。
- **req.query**：存放已解析的 **查询字符串对象**，无需再像第 17 篇那样手工 new URL 拆分；访问 "/search?q=node&page=2" 时得到 { q: "node", page: "2" }。
- 二者都是纯对象，直接按属性读取即可；req.query 的值恒为字符串（或字符串数组，当键重复出现时）。
- 这是 Express 相对原生 http 的核心便利：路径参数与查询参数开箱即得，省去手动解析。

```js
const express = require("express");
const app = express();

app.get("/search", (req, res) => {
  const keyword = req.query.q;   // 来自 ?q=xxx
  const page = req.query.page;   // 来自 &page=2
  res.send("搜索 " + keyword + " 第 " + page + " 页");
});

app.get("/goods/:category", (req, res) => {
  res.send("分类 " + req.params.category);
});

app.listen(3000);
```

> req.query 的解析由 Express 内部基于 qs 完成，数组与嵌套写法都支持；若查询串为空，req.query 是空对象 {} 而非 null，判断"是否传参"应检查键是否存在而非整体是否为空。

**速记**：req.params **取路径段**，req.query **取查询串**。



#### 请求对象增强：req.body、req.headers、req.get 与 req.ip

**请求体相关增强**：Express 在原生 req 上补充了 **req.body（请求体对象）**、**req.headers（请求头）**、**req.get（取头方法）** 与 **req.ip（客户端 IP）**，让读取元信息更顺手。

- **req.body**：经解析中间件（express.json、express.urlencoded）后存放反序列化结果；未挂载解析中间件时它是 undefined，这是高频坑，详见本篇"请求体解析"与"常见坑"。
- **req.headers**：与原生一致的对象，键名已小写，访问如 req.headers["content-type"]。
- **req.get(field)**：取请求头的方法版写法，field 大小写不敏感，等价于 req.headers[field.toLowerCase()]，语义更清晰。
- **req.ip**：客户端 IP 字符串；当服务前置反向代理时，需配合 app.set("trust proxy", true) 才能拿到真实访客 IP 而非代理 IP。

```js
const express = require("express");
const app = express();

app.use(express.json());

app.post("/login", (req, res) => {
  const ua = req.get("user-agent");   // 取请求头
  const ip = req.ip;                  // 客户端 IP
  const body = req.body;              // 解析后的请求体
  res.json({ ua, ip, name: body.name });
});

app.listen(3000);
```

> req.ip 在直连场景下是真实客户端地址；一旦前面有 Nginx 等代理而未设 trust proxy，它只会显示代理机器的内网 IP，导致限流、审计、封禁全部失效。设信任代理后，Express 会按 X-Forwarded-For 还原真实 IP。

**速记**：req.body **靠中间件填充**，req.get **取头**、req.ip **记访客**。



### 响应对象增强

#### res.send 与 res.end 的区别

**res.send**：是 Express 对原生响应对象的 **增强方法**，会根据传入内容 **自动设置 Content-Type 与 Content-Length** 并结束响应，比原生的 res.end 更"智能"。

- 传入字符串：自动设 text/html; charset=utf-8（历史默认，Express 4 中纯字符串按 text/html 处理）；传入 Buffer：按二进制；传入对象或数组：自动 JSON 序列化并设置 application/json。
- **res.end**：是 Node 原生方法，只把给定数据写出并结束，**不自动推断类型、不补 Content-Type**，需自行 setHeader。
- 二者都结束响应，但 res.send 内部已替你算好头与长度；在 Express 应用里优先用 res.send / res.json。
- 同一响应不要混用：调用 res.send 后再 res.end 会触发"已结束"类错误。

```js
const express = require("express");
const app = express();

app.get("/text", (req, res) => {
  res.send("这是纯文本，Content-Type 由 Express 自动设置");
});

app.get("/obj", (req, res) => {
  res.send({ ok: true, n: 1 }); // 自动序列化为 JSON
});

app.listen(3000);
```

> res.send 对"纯字符串"默认按 HTML 处理 Content-Type，这常让浏览器把接口返回的普通文本当成网页解析。返回纯文本接口时若想声明 text/plain，应显式 res.type("text/plain").send(...) 或用 res.json。

**速记**：res.send **自动设头结束**，res.end **裸写原生**。



#### res.json 自动序列化与 res.status 链式调用

**res.json**：是 Express 专门返回 JSON 的增强方法，会对传入的对象 **自动 JSON 序列化**、设置 **application/json** 的 Content-Type 并结束响应，省去手写 JSON.stringify 与设头。

- 完整写法直接 res.json(data)，内部等价于"序列化 + 设头 + 结束"三步合一，比原生 res.end(JSON.stringify(data)) 简洁且不易漏设头。
- **res.status(code)**：设置状态码，且 **返回 res 自身（this）**，因此可与 res.json、res.send 链式拼接，如 res.status(201).json({ id: 1 })。
- 链式之所以可行，是因为 res.status 不改变响应、只标注状态，返回 this 供后续方法继续作用在同一响应上。
- 除 status 外，res.set、res.type 等也返回 this，链式是一种统一风格。

```js
const express = require("express");
const app = express();

app.get("/user/:id", (req, res) => {
  const user = { id: req.params.id, name: "张三" };
  res.status(200).json(user); // 链式：先设状态码再发 JSON
});

app.post("/user", (req, res) => {
  res.status(201).json({ created: true });
});

app.listen(3000);
```

> 链式调用要放在"真正发送"的方法（send/json）之前：先 res.status(404) 再 .json(...)。若先 res.json 结束后再 res.status 会无效，因为响应已经出口。状态码务必如实反映结果，错误返回 200 会破坏 HTTP 语义。

**速记**：res.json **自动序列化**，res.status **返 this 可链式**。



#### res.sendFile、res.download 与 res.redirect

**文件与跳转类方法**：Express 在 res 上提供 **res.sendFile（发送文件）**、**res.download（触发下载）** 与 **res.redirect（重定向）** 三个常用增强方法，覆盖静态交付与跳转场景。

- **res.sendFile(path, options, callback)**：把磁盘文件内容作为响应发回；path 必须是 **绝对路径**，相对路径需先用 path.resolve 或 __dirname 拼接，否则报路径错误。
- **res.download(path, filename, callback)**：功能近似 sendFile，但会附加 Content-Disposition: attachment 头，使浏览器 **弹出下载** 而非直接展示，filename 可指定下载时的文件名。
- **res.redirect(status, path)**：向客户端发出重定向；status 默认 302，可显式给 301 等，path 可为绝对地址或相对路径。
- 三者都会结束响应；sendFile 与 download 在文件不存在时会触发回调的 err 或抛到错误中间件。

```js
const express = require("express");
const path = require("path");
const app = express();

app.get("/show", (req, res) => {
  // 必须用绝对路径
  res.sendFile(path.join(__dirname, "public", "demo.png"));
});

app.get("/get", (req, res) => {
  res.download(path.join(__dirname, "public", "demo.png"), "图片.png");
});

app.get("/old", (req, res) => {
  res.redirect(301, "/new"); // 永久迁移
});

app.listen(3000);
```

> [!CAUTION]
> **注意内容**：res.sendFile 的 path 若传相对路径，Express 会以进程工作目录（process.cwd）为基准解析，部署环境变更即失效甚至读错文件。务必用 path.resolve/__dirname 拼成绝对路径再传入。

**速记**：sendFile **显文件**、download **促下载**、redirect **做跳转**。



### 静态文件托管与请求体解析

#### 用 express.static 托管静态目录

**express.static**：是 Express 内置的 **静态文件中间件**，把某个磁盘目录映射为可直接通过 URL 访问的静态资源（如图片、样式、脚本），无需为每文件写路由。

- 完整用法 app.use(express.static(root, options))，root 是静态目录的 **绝对路径**，options 可配置缓存、索引等。
- 访问路径默认等于"root 之后的相对路径"：若 root 为 ./public，则 public/style.css 通过 /style.css 取得。
- 可用虚拟前缀隔离：app.use("/assets", express.static(root)) 后，资源改由 /assets/style.css 访问，避免与业务路由冲突。
- options 常用 **maxAge** 设浏览器缓存时长（毫秒），以及 **index** 指定目录默认页（默认 index.html）。

```js
const express = require("express");
const path = require("path");
const app = express();

// 把 ./public 目录托管到根路径
app.use(express.static(path.join(__dirname, "public")));

// 带虚拟前缀与缓存
app.use("/assets", express.static(path.join(__dirname, "public"), {
  maxAge: 86400000, // 缓存一天
  index: "index.html"
}));

app.listen(3000);
```

> 静态中间件的 **注册位置** 有讲究：它排在路由之前意味着静态文件优先匹配，排在之后则业务路由可"覆盖"同名路径。把高频静态资源前置能少走一截路由逻辑；但若路由与静态同名且你希望路由胜出，应把静态中间件放在该路由之后。

**速记**：express.static **挂目录、可加前缀、可设缓存**。



#### 用 express.json 与 express.urlencoded 解析请求体

**请求体解析中间件**：Express 4.16 起把常用的 **express.json()** 与 **express.urlencoded()** 内置为顶层方法，分别用于解析 JSON 体与表单体，解析结果写入 **req.body**。

- **express.json(options)**：解析 Content-Type 为 application/json 的请求体，把 JSON 反序列化为对象赋给 req.body；options 可设 limit 限制体积，如 { limit: "1mb" }。
- **express.urlencoded(options)**：解析 application/x-www-form-urlencoded 表单体，默认把数据解析为对象；需传 { extended: true } 才支持嵌套对象（推荐开启）。
- **必须在路由之前注册**：中间件按顺序执行，若放在路由之后，请求已到达处理器时 body 尚未解析，req.body 为空。
- 两者皆返回中间件函数，用 app.use 挂载即可；旧版教程提到的独立 body-parser 包现已无需安装。

```js
const express = require("express");
const app = express();

app.use(express.json({ limit: "1mb" }));                 // 解析 JSON 体
app.use(express.urlencoded({ extended: true }));          // 解析表单体

app.post("/api/data", (req, res) => {
  res.json({ received: req.body }); // req.body 已有内容
});

app.listen(3000);
```

> [!IMPORTANT]
> **重要内容**：express.json 与 express.urlencoded 必须 **在路由注册之前** 用 app.use 挂好。顺序错位是 req.body 为 undefined 的头号原因；中间件像流水线，请求先经过解析阶段才能带着 body 抵达后续处理器。

**速记**：json 解 JSON 体、urlencoded 解表单体，**路由前注册**。



### 环境变量、项目结构、开发效率与常见坑

#### 用 process.env.PORT 读取端口并给默认值

**端口配置**：生产环境中监听端口不应硬编码，而应 **从 process.env.PORT 读取**，并提供一个 **本地默认值**，使同一份代码可在不同环境无缝切换端口。

- process.env 是 Node 暴露的 **环境变量对象**，部署平台（如容器、PaaS）通常通过它注入 PORT。
- 取端口的惯用写法 const PORT = process.env.PORT || 3000;，当环境变量未设置时回落到 3000。
- 这样本地直接 node app.js 用 3000，上云后平台设了 PORT 就自动改用平台值，代码无需改动。
- 除端口外，数据库地址、密钥等也应走环境变量，避免把敏感信息写死进仓库。

```js
const express = require("express");
const app = express();

app.get("/", (req, res) => res.send("读取环境变量端口"));

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log("监听端口：" + PORT);
});
```

> 用 || 兜底只适用于"假值即回落"；若平台可能把 PORT 设为空字符串，更稳妥的写法是用 process.env.PORT ?? 3000（空值合并）或显式判断。把密钥也塞进环境变量时，切忌连同 .env 真实文件一起提交仓库。

**速记**：PORT **取 env、缺省回 3000**。



#### 用 dotenv 加载点 env 文件（社区包）

**dotenv**：是 **社区维护的第三方包**（非 Node 内置、也非 Express 内置），用于在开发期把名为 .env 的文件里的键值对 **加载到 process.env**，免去手动 export 环境变量的麻烦。

- 安装写法 npm install dotenv，使用上在入口顶部调用 require("dotenv").config()，之后即可用 process.env.KEY 读取。
- .env 文件每行形如 KEY=VALUE，存放本地开发配置；它含有密钥，**必须加入 .gitignore 禁止提交**。
- 它只解决"开发期方便"，**生产环境通常由平台直接注入环境变量**，无需也不应依赖 .env 文件。
- 注意 dotenv 是社区方案，Express 官方文档不强制；是否使用取决于团队习惯，不要把它当成 Express 的一部分。

```bash
npm install dotenv
```

```js
require("dotenv").config(); // 在引入 express 之前调用最佳
const express = require("express");
const app = express();

const PORT = process.env.PORT || 3000;
app.listen(PORT);
```

> .env 的加载是"尽力而为"：若变量已存在于系统环境，.env 里的同名值通常 **不会覆盖** 既有环境值（取决于具体配置）。把 .env.example（不含真实密钥的模板）提交仓库、把 .env 忽略，是团队协做的标准做法。

**速记**：dotenv **社区包、开发期填 env**。



#### 入口与应用分离、路由与中间件分目录

**结构约定**：随着接口增多，把所有路由与逻辑堆在单文件会迅速失控；社区常见做法是 **入口与应用分离、路由与中间件各成目录**，形成可维护的分层结构。

- **入口文件（如 app.js / server.js）**：只负责创建 app、挂载中间件与路由、调用 listen，保持薄。
- **routes 目录**：按资源把路由拆分（如 routes/user.js、routes/article.js），每个文件用 express.Router 导出子路由，再在入口里 app.use 挂载。
- **controllers 目录**：存放真正的业务逻辑处理函数，与"路由定义"解耦，便于复用与测试。
- **middlewares 目录**：集中存放自定义中间件（鉴权、日志、错误处理），避免在入口里散落大段函数。

```js
// routes/user.js
const express = require("express");
const router = express.Router();
const { getUser } = require("../controllers/user");

router.get("/:id", getUser);
module.exports = router;
```

```js
// app.js
const express = require("express");
const userRouter = require("./routes/user");
const app = express();

app.use(express.json());
app.use("/users", userRouter);
app.listen(3000);
```

> 路由文件用 express.Router 而非再建一个完整 app，是 Express 推荐的"子路由"机制：每个模块导出自己的 router，入口负责把它们拼装成整体 URL 树，职责清晰、便于单元测试。

**速记**：入口薄、routes/controllers/middlewares **三分天下**。



#### 用 nodemon 与 npm scripts 提升开发效率

**开发提效**：手写 node 启动每次改代码都要手动重启，**nodemon** 能在文件变化时 **自动重启进程**；配合 **npm scripts** 把常用命令固化进 package.json，可显著提升迭代速度。

- 安装写法 npm install --save-dev nodemon，开发依赖即可，运行时无需它。
- 用法 nodemon app.js：监视项目文件，保存即重启；可用 --watch 指定目录、--ext 指定扩展名。
- **npm scripts**：在 package.json 的 scripts 里定义 dev 与 start，如 "dev": "nodemon app.js"、"start": "node app.js"，之后用 npm run dev 开发、npm start 生产。
- 平台执行 npm start 时默认不写 run 也能跑，是部署环境的约定入口；dev 需显式 npm run dev。

```bash
npm install --save-dev nodemon
```

```json
{
  "scripts": {
    "start": "node app.js",
    "dev": "nodemon app.js"
  }
}
```

```bash
npm run dev    # 开发：自动重启
npm start      # 生产：直接运行
```

> [!TIP]
> **建议内容**：把 start 指向不带 nodemon 的 node 命令，确保生产进程不被文件监视拖累；把 dev 指向 nodemon。这样同一套 scripts 既适配本地又适配部署，CI 与平台也认 start 这个约定名。

**速记**：nodemon **改即重启**，scripts **固化 dev 与 start**。



#### 常见坑：未注册解析中间件、res.send 后继续执行、异步错误未被捕获

**三大高频坑**：Express 新手最容易踩的三类问题是 **未注册解析中间件导致 req.body 为空**、**res.send 后代码继续执行** 与 **异步错误未被 Express 自动捕获**，三者都源于对"中间件顺序"与"响应生命周期"的误解。

- **坑一·未注册解析中间件**：忘记 app.use(express.json()) 就直接读 req.body，得到 undefined；务必在路由前注册，详见本篇"请求体解析"一节。
- **坑二·res.send 后仍执行**：调用 res.send/json 结束响应后，函数并不会自动 return，后续代码（尤其是写库、再发响应）照常运行，可能引发"已发送后再写"报错；应在发送后尽早 return。
- **坑三·异步错误未被捕获**：Express 4 中路由处理器的同步异常会被框架捕获并转错误中间件，但 **async 函数里 reject 的 Promise 不会被自动捕获**，需自行 try/catch 后调用 next(error)；Express 5 起对此做了改善，能自动把 rejected promise 交给错误处理中间件。

```js
const express = require("express");
const app = express();
app.use(express.json());

// 坑二示例：send 后忘了 return
app.get("/bad", (req, res) => {
  res.send("已响应");
  // 下面代码仍会执行，若再 res.send 会报错
  res.send("重复响应"); // 危险：响应已结束
});

// 正确写法
app.get("/good", (req, res) => {
  res.send("已响应");
  return; // 及时结束处理器
});

// 坑三示例：async 异常需手动 next
app.get("/async", async (req, res, next) => {
  try {
    throw new Error("出错了");
  } catch (err) {
    next(err); // 交给错误处理中间件
  }
});

app.listen(3000);
```

> [!WARNING]
> **警告内容**：在 async 路由里直接 throw 而不捕获，Express 4 会把这个 rejected promise 当作"未处理拒绝"，既不会进错误中间件、也可能让进程不稳定。凡用 async 处理函数，要么内部 try/catch 调 next(err)，要么升级 Express 5 借助其内置的异步错误捕获。

**速记**：中间件 **路由前挂**、send 后 **早 return**、async 错 **手动 next**。
