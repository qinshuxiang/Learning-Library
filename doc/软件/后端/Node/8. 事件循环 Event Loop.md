## 事件循环 Event Loop

### 事件循环的认识

#### Node 是单线程的事件驱动模型

**Node 的执行模型**：是**单线程、事件驱动**的，所有 JavaScript 代码默认跑在**同一个线程**上。

- 主线程执行脚本，遇到异步操作就**登记回调**后立刻返回，不阻塞。
- 真正的阻塞 IO 由 **libuv 的线程池与操作系统**在底层完成，结果通过事件通知。
- 单线程意味着**不存在多线程竞态**，但长时间同步任务会卡住全部请求。

> 单线程不等于"只能串行干活"：Node 把耗时操作**委托给底层**，自己只处理事件与回调，从而在单线程上也能服务大量并发连接。

**速记**：单线程**跑 JS**，重活**交给底层**。



#### 事件循环是处理非阻塞 IO 的核心机制

**事件循环（Event Loop）**：是 Node **调度异步回调**的核心机制，让异步结果能在合适时机执行。

- 它是一个**循环结构**，每轮从各阶段取出已就绪的回调来执行。
- 异步 API（定时器、IO、网络）的回调，最终都由事件循环**按阶段派发**。
- 没有事件循环，异步回调就**无人触发**，非阻塞 IO 也无从实现。

> 事件循环像一个**永不停歇的调度员**：不断询问"现在有哪些回调就绪"，再依次调用。开发者的回调之所以能在将来执行，正是它在背后驱动。

**速记**：事件循环是**异步回调的调度中心**。



#### 单线程也能高并发

**高并发原理**：单线程通过**非阻塞 + 事件循环**，在等待 IO 时转而服务其他请求，实现高并发。

- 传统多线程每连接一线程，切换与内存开销大；Node **单线程复用**，省去切换成本。
- 当某请求等待数据库或网络时，线程**不空等**，去处理别的请求。
- 高并发前提是**业务以 IO 为主**；若全是 CPU 密集计算，单线程反而成为瓶颈。

> Node 擅长 **IO 密集型**（网络、文件、数据库）并发，而非 **CPU 密集型**（大量计算）。后者会占满单线程拖慢所有请求，解决方式见本章末尾。

**速记**：IO 等待不空等，**转去服务他人**。



### Node 与浏览器事件循环的差异

#### 浏览器的宏任务与微任务

**浏览器的循环模型**：把任务分为**宏任务（Macrotask）与微任务（Microtask）** 两大类。

- **宏任务**：script 整体、setTimeout、setInterval、IO、UI 渲染等。
- **微任务**：Promise.then、MutationObserver、queueMicrotask 等。
- 每执行完**一个宏任务**，就**清空整个微任务队列**，再取下一个宏任务。

> 浏览器更强调"宏任务 → 微任务 → 渲染"的节奏，**没有细分的阶段队列**；这与 Node 的阶段式结构不同。

**速记**：浏览器**宏任务夹微任务**，无细分阶段。



#### Node 的事件循环分阶段且有六个阶段

**Node 的循环模型**：不像浏览器笼统，而是把回调按来源**严格划分成六个阶段**，依次执行。

- 六阶段顺序：timers、pending callbacks、idle/prepare、poll、check、close callbacks。
- 每个阶段维护**自己的回调队列（任务池）**，进入阶段时批量取出执行。
- 微任务（nextTick 与 Promise）穿插在**阶段之间或操作之后**清空。

> 这种"分阶段"设计让 Node 能**精确控制**不同类型回调的优先级与时机（如 check 专门服务 setImmediate）。理解六阶段是看懂异步顺序的前提。

**速记**：Node **六阶段**轮转，各管一类回调。



#### Node 中宏任务也有优先级

**宏任务优先级**：在 Node 里不同宏任务**并非平等**，而是按所处阶段有固定先后。

- **timers 阶段**先于 **check 阶段**，故 setTimeout 总体上早于 setImmediate（在各自就绪时）。
- **check 阶段**专门承接 setImmediate，使其在 IO 回调之后尽快执行。
- 即便都是宏任务，**落地的阶段不同，时机就不同**。

> 与浏览器"宏任务大致平级"的直觉不同，Node 的宏任务优先级由**阶段顺序**决定。比较 setTimeout 与 setImmediate 的先后，必须先判断它们分别落在哪个阶段。

**速记**：Node 宏任务**阶段定先后**。



### 事件循环的六个阶段及各阶段的任务池

#### timers 与 pending callbacks 阶段

**timers 阶段**：执行 **setTimeout 与 setInterval** 到期的回调，是循环的第一个阶段。

- 回调在**设定的延时到期后**才进入此阶段，实际时间受循环整体耗时影响，是下限而非准点。
- **pending callbacks 阶段**：执行**上一轮循环中延期**的一些系统 IO 回调，多由底层使用，业务代码几乎不注册。

```js
setTimeout(() => console.log("timer"), 0);
// 回调在 timers 阶段、延时到期后执行
```

> pending callbacks 对应用层透明；了解它有助于建立"六阶段完整闭环"的心智模型，但不必在此编写业务回调。

**速记**：timers 跑 **setTimeout/setInterval**，pending 收**上轮推迟的 IO**。



#### idle/prepare 与 poll 阶段

**idle/prepare 阶段**：是 Node **内部使用**的两个阶段，普通代码无法注册回调。

- **idle** 在循环空闲时运行，**prepare** 在进入 poll 前做准备，二者**不承接用户回调**。
- **poll 阶段**：是事件循环**最重要的场所**，处理绝大多数 **IO 回调**（文件、网络）。
- poll 若没有别的事要做，会**在此停留**等待新 IO 事件；停留时长由最近的定时器阈值决定。

```js
const fs = require("fs");
fs.readFile("demo.txt", (err, data) => {
  // 该回调大多在 poll 阶段被执行
});
```

> poll 被称为核心阶段，是因为真实服务里**绝大多数异步都来自 IO**，这些 IO 结果的消费发生在 poll。理解 poll 的"等待与唤醒"是掌握循环的关键。

**速记**：idle/prepare **内部专用**，poll 是 **IO 主战场**。



#### check 与 close callbacks 阶段

**check 阶段**：专门执行 **setImmediate 的回调**，位于 poll 阶段之后。

- 因为 poll 之后紧接 check，所以 **setImmediate 总在当轮 IO 之后、下一轮 timers 之前**执行。
- 它是 setImmediate 与 setTimeout 行为差异的**结构性根源**。
- **close callbacks 阶段**：处理**关闭类事件**（如 socket 的 close 回调），是六阶段最后一环。

```js
setImmediate(() => console.log("immediate"));
// 回调在 check 阶段执行
```

> 把关闭回调放在最后，能保证"连接相关的读写回调都已处理完"再统一清理，避免边读边关的竞态，是循环闭环的安全收尾。

**速记**：check 跑 **setImmediate**，close 做**收尾清理**。



### 六个阶段的完整执行流程

#### 阶段从上往下循环

**循环顺序**：每一轮事件循环按固定次序**自上而下走完六个阶段**，再回到起点。

- 固定次序：timers → pending callbacks → idle/prepare → poll → check → close callbacks。
- 每一轮称为一个 **tick**；只要还有未完成的任务，循环就**持续进行**。
- 阶段之间会**穿插清空微任务**（nextTick 队列与 Promise 微任务队列）。

> 记住"一轮 tick"：一次完整的六阶段遍历就是一 tick。定时器、IO 即使同时就绪，也按阶段次序被消费，这保证了行为可预测。

**速记**：一轮 tick **六阶段走完再回顶**。



#### poll 阶段的详细行为

**poll 的等待逻辑**：进入 poll 后，事件循环计算"应当阻塞多久"并据此行动。

- 先检查**是否有到期的定时器**：若有，poll 不阻塞，直接让出以尽快回到 timers。
- 再检查**是否有就绪的 IO 回调**：有则取出执行，执行完继续检查，直到清空。
- 若既无定时器到期也无 IO 就绪，则**阻塞等待**新 IO 事件，直到被唤醒或到达阈值。
- 一旦被唤醒且**没有 setImmediate**，处理 IO 回调；若有，则**跳到 check 阶段**。

> poll 的"阻塞时长"由**最近的定时器延时**决定：既不空转浪费 CPU，也保证定时器及时响应，是连接"等待 IO"与"及时唤醒"的枢纽。

**速记**：poll 看**定时器与 IO**，决定阻塞或跳转。



#### 完整的阶段流程图

**流程总览**：下面用文本流程图表示一轮 tick 的走向与微任务穿插位置。

```text
            ┌─────────────── 新一轮 tick ───────────────┐
            ▼                                           
   ┌─────────────────┐                                 
   │     timers      │  执行 setTimeout / setInterval    
   └────────┬────────┘                                 
            ▼                                           
   ┌─────────────────┐                                 
   │ pending callbacks│ 收上轮推迟的 IO 回调             
   └────────┬────────┘                                 
            ▼                                           
   ┌─────────────────┐                                 
   │  idle / prepare │ 内部专用                         
   └────────┬────────┘                                 
            ▼                                           
   ┌─────────────────┐                                 
   │      poll       │ 处理 IO 回调，可阻塞等待         
   └────────┬────────┘                                 
            ▼                                           
   ┌─────────────────┐                                 
   │      check      │ 执行 setImmediate                
   └────────┬────────┘                                 
            ▼                                           
   ┌─────────────────┐                                 
   │ close callbacks │ 处理关闭事件                     
   └────────┬────────┘

```

> 流程图里的"清空微任务"标注在阶段之后，提醒微任务不在阶段内部，而在**操作完成或阶段切换的间隙**被 draining，其中 **nextTick 队列优先于 Promise 微任务队列**清空。

**速记**：图记**六阶段 + 微任务穿插**。



### 微任务的执行位置

#### process.nextTick 队列优先于 Promise 微任务队列

**两类微任务**：Node 中有 **process.nextTick 队列** 与 **Promise 微任务队列**，前者优先级更高。

- 一次操作完成、准备继续之前，Node 先**清空 nextTick 队列**。
- nextTick 队列空了之后，才清空 **Promise 的微任务队列**。
- 同一时机注册的 nextTick 回调**总是早于** Promise.then 回调执行。

```js
Promise.resolve().then(() => console.log("promise"));
process.nextTick(() => console.log("nextTick"));
// 输出：nextTick 先于 promise
```

> 这种优先级是明确设计：nextTick 用于"**当前操作后立即、且赶在任何微任务前**"做事。滥用会压过 Promise，需理解其分层。

**速记**：nextTick 队列 **压在 Promise 之前**。



#### 每个宏任务执行完后清空所有微任务

**清空时机**：在每个宏任务（更准确说，每次操作/回调）执行完毕后，**清空全部微任务**再继续。

- 这保证了微任务的"**即时性**"：紧跟产生它的宏任务之后落地。
- 在阶段层面，微任务清空发生在**当前操作结束、进入下一阶段之前**的间隙。
- 所有排队的 nextTick 与 Promise 回调都会**一次性排空**，不留到下一轮。

> "每个宏任务后清空微任务"是把 Node 与浏览器对齐的关键：await 或 .then 的后续逻辑会在**同一轮 tick 内、该回调结束后立刻**继续。

**速记**：宏任务一完，**微任务全清空**。



#### Node 11 之后行为与浏览器趋同

**版本差异**：Node 11 之前与之后，微任务的清空粒度**不同**，11 起趋近浏览器。

- **Node 11 之前**：同一阶段内**连续执行完所有回调**，微任务队列要等到**整个阶段结束**才清空。
- **Node 11 起**：每执行**一个回调（宏任务）**，就立即清空微任务，行为**趋同浏览器**。
- 这一变化主要影响**同一阶段多个同类回调**时的输出顺序。

```js
setTimeout(() => {
  console.log("timer1");
  Promise.resolve().then(() => console.log("promise in timer1"));
}, 0);
setTimeout(() => console.log("timer2"), 0);
```

> 上例在 Node 11 之前输出 timer1、timer2、promise in timer1；Node 11 起输出 timer1、promise in timer1、timer2。判断顺序务必**先确认 Node 版本**。

**速记**：Node 11 起 **每回调清微任务**。



### process.nextTick

#### nextTick 不属于事件循环的任何阶段

**nextTick 的定位**：process.nextTick **不是六个阶段之一**，它插队于**当前操作之后、事件循环继续之前**。

- 它在一个回调**刚执行完的那一刻**就被触发，不进入 timers、poll 等任何阶段队列。
- 因此它的时机**比任何阶段回调都早**，甚至早于微任务队列中的 Promise。
- 文档称它"**not technically part of the event loop**"。

```js
setTimeout(() => console.log("timeout"), 0);
process.nextTick(() => console.log("nextTick"));
// 输出：nextTick 先于 timeout
```

> 因为不隶属阶段，nextTick 回调会在同步代码结束后立刻排尽，远在循环转到 timers 之前。这是它"最快"的原因，也带来饥饿风险。

**速记**：nextTick **游离于六阶段之外**。



#### 递归调用会导致饥饿

**饥饿风险**：若在 nextTick 回调里**递归注册 nextTick**，事件循环将**永远得不到继续的机会**。

- nextTick 队列总是被优先清空，递归注册会让队列**无限增长**。
- 结果：IO 回调、定时器、check 阶段**始终轮不到**，服务看似"卡死"。
- 需分批循环时，应改用 setImmediate 或 setInterval，让出控制权。

```js
function starveLoop() {
  process.nextTick(() => {
    console.log("nextTick 递归");
    starveLoop(); // 危险：会饿死事件循环
  });
}
// starveLoop(); // 切勿实际运行
```

> [!WARNING]
> **警告内容**：nextTick 递归会**饿死事件循环**，使定时器、IO、setImmediate 全部停滞。凡要等待其他 IO，应改用 setImmediate，把主动权交还循环。



#### nextTick 的应用场景

**典型用途**：nextTick 适合"**在当前逻辑结束后、但赶在下一次事件前**"做收尾或抛错。

- **错误尽早抛出**：异步启动发现错误时用 nextTick 抛出，避免打断当前调用栈。
- **确保构造后再回调**：先完成对象初始化，再于 nextTick 触发用户回调，防止访问半成品。
- **轻量收尾**，不适合让出事件循环的场合。

```js
function asyncTask(callback) {
  if (!callback) {
    process.nextTick(() => {
      throw new Error("callback 必须提供");
    });
    return;
  }
}
```

> 使用准则是"**只做轻量、必要的收尾**"。要让出事件循环、等待其他 IO，应改用 setImmediate。

**速记**：nextTick 用于 **轻量收尾与早抛错**。



### setImmediate 与 setTimeout 的对比

#### 在主线程与 IO 回调内环境不同

**环境差异**：setImmediate 与 setTimeout(fn, 0) 的先后，**取决于注册时所处的执行环境**。

- 在**主线程顶层**注册二者，顺序**不确定**（取决于定时器何时到期）。
- 在 **IO 回调内部**注册二者，setImmediate **一定先于** setTimeout 执行。
- 原因在于二者分别落在 **check 阶段** 与 **timers 阶段**，阶段到达时机随环境变化。

> 区分"主线程"与"IO 回调内"是判断二者顺序的**第一把钥匙**；环境不同，同一段代码可能得出相反输出。

**速记**：顺序先看 **注册环境**。



#### 主线程执行时二者顺序不确定

**顶层不确定性**：在主模块顶层同时写 setTimeout(fn,0) 与 setImmediate，输出顺序**不可预测**。

- setTimeout(0) 实际被**钳制为至少 1 毫秒**才到期。
- 循环从启动到走到 timers 往往**不足 1 毫秒**，定时器尚未到期而被跳过，于是 setImmediate 先跑。
- 但也存在**恰好超过 1 毫秒**的偶然，使 setTimeout 先跑，故顺序会漂移。

```js
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
// 顺序不确定，不能依赖
```

> 这种不确定性是**设计使然**而非 bug。主线程下不应依赖二者顺序，应使用 IO 回调内的确定规则。

**速记**：主线程下 **谁先谁后看运气**。



#### IO 回调内 setImmediate 一定先执行

**IO 内确定性**：在 fs、net 等 IO 回调内部注册时，**setImmediate 必定早于 setTimeout(fn,0)**。

- IO 回调运行于 **poll 阶段**，结束后事件循环紧接着进入 **check 阶段** 执行 setImmediate。
- 此时 setTimeout(0) 虽已注册，但其 1 毫秒延时**通常尚未到期**，要等到**下一轮 timers** 才触发。
- 因此 setImmediate 在当轮 check 落地，setTimeout 落到下一轮 timers，**顺序固定**。

```js
const fs = require("fs");
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
});
// 稳定输出：immediate 先于 timeout
```

> 这是面试高频题的确定答案：**IO 回调内，setImmediate 永远先于 setTimeout(0)**。记住"poll 之后立刻 check"即可稳定推演。

**速记**：IO 内 **setImmediate 必在前**。



#### 原理说明

**结构原理**：二者顺序的本质，是 **check 阶段与 timers 阶段在循环中的相对位置**。

- setImmediate 落点是 **check 阶段**，紧接在 poll 之后。
- setTimeout 落点是 **timers 阶段**，位于每一轮循环的**最开头**。
- 在 IO 回调（poll）之后，循环**先到 check 再到下一轮 timers**；在主线程开头，循环**先到 timers 再到 check**。

> 把六阶段顺序图记牢，就能解释所有表面矛盾：所谓"顺序不确定"是"到达 timers 时延时是否已过"的偶然；"IO 内确定"是"poll 之后先 check 后 timers"的结构必然。

**速记**：阶段位置 **check 在 timers 之前（下一轮）**。



### 常见异步 API 的分类练习

#### 顶层混合示例推演

**练习目标**：把 console.log、setTimeout、process.nextTick、Promise、setImmediate 混在一起，推演可靠输出。

```js
console.log("A: 同步开始");

setTimeout(() => console.log("A: setTimeout"), 0);
setImmediate(() => console.log("A: setImmediate"));
Promise.resolve().then(() => console.log("A: Promise"));
process.nextTick(() => console.log("A: nextTick"));

console.log("A: 同步结束");
```

> 顶层推演要点：同步代码优先；同步结束后先清空 nextTick 队列（A: nextTick），再清空 Promise 微任务（A: Promise）；进入循环后 A: setTimeout 与 A: setImmediate 顺序**不确定**，不能断言。确定前缀为：同步开始 → 同步结束 → nextTick → Promise，其后两者随环境漂移。



#### 嵌套 IO 回调的确定推演

**可靠示例**：把异步注册放进 fs.readFile 回调，顺序即可**完全确定**。

```js
const fs = require("fs");

console.log("0 同步开始");

fs.readFile(__filename, () => {
  console.log("1 readFile 回调开始");

  setTimeout(() => console.log("2 setTimeout"), 0);
  setImmediate(() => console.log("3 setImmediate"));
  Promise.resolve().then(() => console.log("4 Promise"));
  process.nextTick(() => console.log("5 nextTick"));

  console.log("6 readFile 回调结束");
});

console.log("7 同步结束");
```

逐步推演：

- 第一步（同步）：打印 **0 同步开始**，注册 readFile，打印 **7 同步结束**。顶层无 nextTick 与微任务，事件循环直接启动。
- 第二步（poll 阶段）：readFile 的 IO 完成后，其回调在 **poll 阶段**执行，打印 **1 readFile 回调开始**，就地注册四个异步，再打印 **6 readFile 回调结束**。
- 第三步（清微任务）：该回调这一"操作"完成，先清空 **nextTick 队列**打印 **5 nextTick**，再清空 **Promise 微任务**打印 **4 Promise**。
- 第四步（check 阶段）：poll 之后进入 check，执行 setImmediate 打印 **3 setImmediate**；此刻 setTimeout 的 1 毫秒通常未到，留待下一轮。
- 第五步（下一轮 timers）：循环回到 timers，延时已过期，打印 **2 setTimeout**。

最终确定输出：

```text
0 同步开始
7 同步结束
1 readFile 回调开始
6 readFile 回调结束
5 nextTick
4 Promise
3 setImmediate
2 setTimeout
```

> 全链串起：**同步最先 → 回调在 poll → 回调内 nextTick 压过 Promise → check 的 setImmediate 早于下一轮 timers 的 setTimeout**。逐阶段套用，任何混合代码都能可靠推演。

**速记**：嵌套推演 **poll→nextTick→Promise→check→timers**。



### 阻塞事件循环的危害与解决

#### CPU 密集任务会卡住整个服务

**危害本质**：单线程下，**长时间同步计算**会独占事件循环，使所有异步回调都无法执行。

- 主线程陷入大循环或重计算，定时器、IO 回调、请求响应**全部停顿**。
- 表现为接口**无响应、延迟飙升**，甚至被健康检查判定为掉线。
- 根本原因是**没有第二线程**去接管被阻塞期间涌入的任务。

```js
function handleRequest() {
  let sum = 0;
  for (let i = 0; i < 1e10; i++) sum += i; // 单线程被长时间占用
  return sum;
}
```

> 这种"算完才放手"的代码在 Node 里尤其致命，因为它阻塞的是**唯一的**主线程。判断是否阻塞，看任务是否**必须同步跑在主线程**。

**速记**：重计算**占满单线程**即卡死。



#### 改用子进程、worker_threads 与任务分片

**解决路径**：把 CPU 密集工作**移出主线程**，或**切成小片让出事件循环**。

- **child_process / cluster**：把重计算交给**独立进程**，主进程继续处理请求，结果经消息回传。
- **worker_threads**：同进程内开**工作线程**做计算，适合需共享内存或轻量并发。
- **setImmediate 分片**：把大循环**切成小块**，每块用 setImmediate 让出事件循环。

```js
function chunkedCompute(total, done) {
  let i = 0, sum = 0;
  function step() {
    const end = Math.min(i + 1000000, total);
    for (; i < end; i++) sum += i;
    if (i < total) setImmediate(step); // 让出控制权
    else done(sum);
  }
  step();
}
```

> 选型口诀：**能下放进程就下放进程**，需线程级并发用 **worker_threads**，逻辑简单则用 **setImmediate 分片**。核心都是"**别让重活在唯一的主线程上久留**"。

**速记**：重活**移出主线程或切片让出**。
