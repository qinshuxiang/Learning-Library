## TypeScript 与 Node 工程化

### 为什么在 Node 项目中引入 TypeScript

#### 静态类型带来的收益

**TypeScript**：是 JavaScript 的**超集**，在语法之上增加静态类型系统，最终编译为纯 JavaScript 运行。

- 编译期发现类型错误，把一部分运行时崩溃提前到**写代码时**暴露。
- 编辑器能基于类型做补全、跳转与重命名，重构更安全。
- 类型声明本身即**文档**，接口字段一目了然，减少口头约定。

> 类型只在编译期存在，运行时会被完全擦除。TypeScript 不做运行时校验，来自外部的输入仍需自行判断。

**速记**：TypeScript 管 **编译期**，运行时校验另做。



#### 引入的代价与取舍

**代价**：引入类型系统不是零成本，需要构建步骤、类型声明与团队共识。

- 新增**编译环节**，开发期需 ts-node 或监视编译。
- 第三方库缺类型时需安装对应的 types 包或自行声明。
- 类型写不好会变成"**到处 any**"，既没有收益又增加负担。

> 小型脚本或一次性工具未必值得引入。中大型、长期维护、多人协作的项目收益最明显。

**速记**：长期项目 **值得引入**，临时脚本可省。



### 环境搭建

#### 依赖安装与初始化

**安装方式**：TypeScript 相关依赖装到 **devDependencies**，因为生产运行的是编译后的 JavaScript。

- **typescript**：编译器本体，提供 tsc 命令。
- **ts-node**：直接运行 TypeScript 文件，免去手动编译，适合开发期。
- **@types/node**：Node 内置模块的类型声明，缺它则 require、process 等无类型提示。
- **tsx**：更快的 TypeScript 执行器，基于 esbuild，是社区常用替代方案。

```bash
npm init -y
npm install -D typescript ts-node @types/node
npx tsc --init
```

> 执行 tsc --init 会生成带注释的 tsconfig.json，注释中列出了绝大多数可选配置，值得通读一遍。

**速记**：typescript 加 ts-node 加 **@types/node** 三件套。



#### 编译与运行

**编译流程**：tsc 读取配置，把源码目录下的 TypeScript 编译为 JavaScript 输出到指定目录。

- **npx tsc**：按 tsconfig.json 全量编译。
- **npx tsc --watch**：监视文件变化增量编译，开发期常用。
- **ts-node src/index.ts**：不产出文件直接运行，启动略慢但省事。

```bash
npx tsc
node dist/index.js
```

> 生产部署应运行 **dist 中的编译产物**，不要在生产用 ts-node 启动，它会在每次启动时重新编译，拖慢启动速度且占用内存。

**速记**：开发用 ts-node，**生产跑 dist**。



### tsconfig 核心配置

#### 目标与模块

**target 与 module**：决定编译后的语法版本与模块系统，是最容易配错的两项。

- **target**：输出的 JavaScript 语法版本，如 ES2020、ES2022。版本越高越接近现代语法，需 Node 版本支持。
- **module**：输出的模块规范。Node 用 CommonJS 时写 commonjs，用 ES Module 时写 nodenext 或 esnext。
- **moduleResolution**：模块解析策略，与 module 配套，用 nodenext 时通常也写 nodenext。

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "commonjs",
    "moduleResolution": "node"
  }
}
```

> module 与 package.json 中的 type 字段必须一致。若项目声明了 type 为 module 却又编译成 CommonJS，运行时会报"require 未定义"之类错误。

**速记**：module 与 **package.json 的 type** 要对齐。



#### 目录与严格模式

**路径与检查项**：控制输入输出位置与检查强度。

- **rootDir**：源码根目录，通常为 src。
- **outDir**：产物目录，通常为 dist。
- **include 与 exclude**：限定参与编译的文件范围，exclude 默认已含 node_modules。
- **strict**：开启严格模式的**总开关**，包含严格空值检查、严格函数类型等，新建项目应默认开启。

```json
{
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "esModuleInterop": true,
    "sourceMap": true
  },
  "include": ["src"]
}
```

> [!IMPORTANT]
> **重要内容**：**strict 建议从项目一开始就开启**。中途再打开会出现大量报错，改造成本陡增；新项目开启几乎无额外负担。

**速记**：src 进 **dist** 出，strict **从一开始**开。



#### 互操作与调试支持

**esModuleInterop**：让 CommonJS 与 ES Module 的默认导入写法互相兼容。

- 开启后可用 **import express from "express"** 导入 CommonJS 包。
- 未开启时只能用 **import * as express** 的写法，容易在运行时拿到包装对象。
- **sourceMap**：生成映射文件，让调试与报错能定位到原始 TypeScript 行号。

```json
{
  "compilerOptions": {
    "esModuleInterop": true,
    "allowSyntheticDefaultImports": true,
    "sourceMap": true
  }
}
```

> 排查线上报错时，sourceMap 是定位原始代码的关键。生产可生成但不随包发布，或仅上传到错误监控平台。

**速记**：esModuleInterop **必开**，sourceMap **便于排错**。



### 类型声明文件

#### 类型的三种来源

**类型来源**：一个包的类型可能来自三处，决定了是否需要额外安装。

- **包自带**：包的 package.json 中声明了类型入口，安装即可用。
- **DefinitelyTyped**：由社区维护，安装同名 **@types/xxx** 包获得类型。
- **自行声明**：无类型的小众包，可在项目中写 d.ts 文件补充。

```bash
npm install -D @types/express @types/cors
```

> 安装后无需在代码中引入，TypeScript 会自动从 node_modules/@types 目录加载全局可用的声明。

**速记**：无类型就装 **@types** 前缀包。



#### 声明文件的写法

**声明文件**：以 **.d.ts** 结尾，只含类型不含实现，用于补充全局变量或模块的类型。

- **declare**：声明一个已存在但没有类型的全局变量或模块。
- **declare module**：为整个模块补类型，常用于无类型的第三方包。
- 声明文件不会生成运行时代码。

```ts
declare module "legacy-lib" {
  export function formatDate(input: string): string;
}

declare global {
  namespace NodeJS {
    interface ProcessEnv {
      PORT?: string;
      DB_PASSWORD?: string;
    }
  }
}
```

> 为 process.env 扩展类型是常见需求：默认类型是 string 或 undefined，扩展后可获得字段提示与拼写检查。

**速记**：d.ts **只声明不实现**。



### 常用类型语法

#### 基础与复合类型

**基础类型**：在 JavaScript 原始类型基础上增加了若干专用类型。

- 原始类型：string、number、boolean、null、undefined、symbol、bigint。
- **数组**：元素类型加方括号，或 Array 加尖括号。
- **元组**：固定长度与位置类型的数组。
- **any**：关闭类型检查，应尽量避免；**unknown**：未知类型，使用前必须先收窄，比 any 安全。

```ts
const names: string[] = ["张三", "李四"];
const point: [number, number] = [10, 20];
let input: unknown = JSON.parse("{}");
```

> unknown 与 any 的区别在于**能否直接使用**：any 可以任意操作，unknown 必须先判断类型。接收外部数据时用 unknown 更安全。

**速记**：外部数据用 **unknown**，别用 any。



#### 接口与类型别名

**interface 与 type**：都可描述对象结构，使用场景略有侧重。

- **interface**：描述对象形状，支持**声明合并**（同名自动合并），适合描述公共结构。
- **type**：可表达联合、交叉、元组等更丰富的类型，不支持合并。
- 可选属性用问号，只读属性用 readonly。

```ts
interface User {
  readonly id: number;
  name: string;
  email?: string;
}

type Role = "admin" | "user";
type UserWithRole = User & { role: Role };
```

> 团队约定其一即可，不必混用造成困惑。描述对象结构优先 interface，需要组合变换时用 type。

**速记**：结构用 **interface**，组合用 **type**。



#### 泛型与工具类型

**泛型**：把类型作为参数，让函数或结构在保持类型安全的同时可复用。

- 函数泛型：函数名后加尖括号声明类型参数，调用时可省略由推断得出。
- **常用工具类型**：Partial（全部可选）、Pick（挑选字段）、Omit（剔除字段）、Record（键值映射）。
- 泛型约束用 extends 限定取值范围。

```ts
interface ApiResponse<T> {
  code: number;
  data: T;
  message: string;
}

type UserBrief = Pick<User, "id" | "name">;
type UserDraft = Partial<User>;

function wrap<T>(data: T): ApiResponse<T> {
  return { code: 0, data, message: "ok" };
}
```

> 统一响应结构配合泛型，能让每个接口的返回值都有精确类型，前端调用时无需重复断言。

**速记**：泛型 **一处定义多处复用**。



### 为 Express 补充类型

#### 请求与响应的类型

**@types/express**：为 Express 提供请求、响应与中间件的类型定义。

- **Request 与 Response**：通常从 express 导入，作为处理函数的参数类型。
- 路径参数、查询参数默认是宽泛类型，可用泛型进一步约束。
- 中间件函数的 next 参数类型为 NextFunction。

```ts
import express, { Request, Response, NextFunction } from "express";

const app = express();

app.get("/users/:id", (req: Request, res: Response) => {
  const id = req.params.id;
  res.json({ id });
});

app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  res.status(500).json({ message: err.message });
});
```

> 路径参数的类型默认是字符串或字符串数组，取用时注意可能需要显式转换或类型断言。

**速记**：Request、Response、**NextFunction** 三件套。



#### 扩展请求对象

**声明合并**：利用 interface 的同名合并特性，为 Request 增加自定义字段。

- 常见需求：鉴权中间件解析出用户后挂到 req.user 上。
- 做法是在声明文件中扩展 express 的 Request 接口。
- 扩展后所有处理函数中均可获得该字段的类型提示。

```ts
declare global {
  namespace Express {
    interface Request {
      user?: { id: number; role: string };
    }
  }
}

app.get("/profile", (req, res) => {
  if (!req.user) return res.status(401).json({ message: "未登录" });
  res.json(req.user);
});
```

> 扩展字段建议设为**可选**，因为在鉴权中间件执行之前该字段并不存在，强制非空会导致误用。

**速记**：扩展 Request 走 **声明合并**。



### 编译与运行工作流

#### npm scripts 的典型配置

**脚本配置**：把常用命令写进 package.json 的 scripts，统一团队操作方式。

- **dev**：开发启动，用 ts-node 或 tsx 配合 nodemon 自动重启。
- **build**：清理并编译，输出到 dist。
- **start**：运行编译产物，供生产环境使用。

```json
{
  "scripts": {
    "dev": "nodemon --exec ts-node src/index.ts",
    "build": "tsc -p tsconfig.json",
    "start": "node dist/index.js"
  }
}
```

> 生产镜像中只需安装生产依赖并执行 build 与 start，开发依赖不进入最终镜像，可显著减小体积。

**速记**：dev 跑源码，**start 跑产物**。



#### 路径别名与运行时问题

**路径别名**：用简短前缀替代深层相对路径，改善导入可读性。

- 在 tsconfig 中用 **paths** 配置，配合 baseUrl 使用。
- 但 TypeScript 只做编译期解析，**运行时 Node 并不认识别名**，直接运行会报模块找不到。
- 解决方案：使用 tsc-alias 之类工具改写产物路径，或在运行时注册解析钩子。

```json
{
  "compilerOptions": {
    "baseUrl": "src",
    "paths": {
      "@services/*": ["services/*"]
    }
  }
}
```

> [!CAUTION]
> **注意内容**：路径别名是**编译期语法糖**。若不做运行时处理，用 ts-node 开发一切正常，一旦 node 直接跑 dist 就会启动失败，属于典型的"开发环境能跑线上崩"。

**速记**：别名需 **编译期与运行时双配**。



### 代码质量工具

#### ESLint 与 Prettier

**分工**：ESLint 负责**代码质量与潜在错误**，Prettier 负责**格式统一**，两者互补。

- **ESLint**：发现未使用变量、可能的类型错误、不推荐的写法。
- **Prettier**：统一缩进、引号、换行，终结格式争论。
- 二者可能冲突，通常用 eslint-config-prettier 关闭 ESLint 中与格式相关的规则。

```json
{
  "scripts": {
    "lint": "eslint src --ext .ts",
    "format": "prettier --write src"
  }
}
```

> 类型检查与静态检查各有侧重：tsc 管类型正确，ESLint 管写法规范，二者都要跑，不可互相替代。

**速记**：ESLint 查 **质量**，Prettier 管 **格式**。



#### 提交前校验

**Git 钩子**：在提交或推送前自动运行检查，防止问题代码入库。

- **Husky**：管理 Git 钩子的工具，把钩子配置纳入版本控制。
- **lint-staged**：只对**本次改动的文件**执行检查，速度快、不打扰。
- 典型组合：提交前跑 ESLint 与 Prettier，推送前跑类型检查与测试。

```json
{
  "lint-staged": {
    "*.ts": ["eslint --fix", "prettier --write"]
  }
}
```

> 校验规则应**从宽松起步再逐步收紧**。一开始就设过高门槛，团队会把钩子当障碍绕过，反而失去意义。

**速记**：Husky 管钩子，**lint-staged 只查改动**。



### 项目结构与渐进迁移

#### 分层目录约定

**目录结构**：按职责分层，让每个文件有明确的归属。

- **routes**：路由定义，只负责路径与方法的映射。
- **controllers**：处理请求与响应，做参数校验与结果组装。
- **services**：业务逻辑，与 HTTP 无关，便于复用与测试。
- **models 或 repositories**：数据访问层，封装数据库操作。

```text
src
├── index.ts
├── routes
├── controllers
├── services
├── middlewares
└── utils
```

> 分层的意义在于**依赖方向单一**：上层依赖下层，下层不反向依赖。业务逻辑不写在路由里，才能脱离 HTTP 单独测试。

**速记**：路由薄、**服务厚**、数据访问独立。



#### 从 JavaScript 渐进迁移

**渐进迁移**：不必一次性重写，可让两种文件共存，逐步替换。

- **allowJs**：允许 TypeScript 项目编译 JavaScript 文件。
- **checkJs**：对 JavaScript 文件也做类型检查，可配合注释逐文件开启。
- 迁移顺序建议：先工具类与数据模型，再服务层，最后路由与入口。

```json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false
  }
}
```

> 迁移时优先给**被最多地方调用的底层模块**加类型，收益最大。注释抑制手段应作为过渡手段，不要长期遗留。

**速记**：allowJs **共存**，自底向上替换。
