## 错误处理、日志与调试

### 错误对象的类型

#### Error 与常见内置错误

**Error**：是 JavaScript 表示错误的标准对象，Node 中所有异常最终都以它的实例或子类的形式抛出。

- **message**：错误描述文本，说明发生了什么。
- **name**：错误类型名，如 Error、TypeError、RangeError。
- **stack**：调用栈字符串，记录错误发生时经过的函数调用链，是定位问题的第一手资料。
- 常见子类：**TypeError**（类型不符）、**RangeError**（数值越界）、**SyntaxError**（语法错误）、**ReferenceError**（引用未声明变量）。

> 栈信息里最上方是抛出点，往下是调用来源。排查时应先找**属于自己代码的那一层**，中间的第三方包帧通常只是传递。

**速记**：Error 三要素 **message、name、stack**。



#### 系统错误与错误码

**系统错误**：Node 在调用操作系统能力失败时抛出的错误，特征是带 **code** 属性。

- **ENOENT**：文件或目录不存在。
- **EADDRINUSE**：端口已被占用，常见于重复启动服务。
- **ECONNREFUSED**：连接被拒绝，目标服务未启动。
- **EACCES 与 EPERM**：权限不足。
- **ETIMEDOUT**：连接或响应超时。

```js
const fs = require("fs");

fs.readFile("not-exist.txt", "utf8", (err, data) => {
  if (err) {
    console.log(err.code); // ENOENT
    console.log(err.message);
    return;
  }
  console.log(data);
});
```

> 判断错误类型应以 **code 属性** 为依据，而不是比对 message 文本。message 可能随版本与系统语言变化，code 则稳定。

**速记**：系统错误看 **code**，业务错误看自定义字段。



#### 自定义错误类

**自定义错误**：继承 Error 并扩展业务字段，让上层能区分错误的性质与状态码。

- 继承后应**设置 name**，否则 name 仍为 Error。
- 可挂载 **statusCode**（对客户端返回的状态码）、**code**（业务错误码）、**details**（补充信息）。
- 抛出用 throw，拒绝用 Promise.reject，两者都应传 Error 实例而非字符串。

```js
class AppError extends Error {
  constructor(message, statusCode = 500, code = "INTERNAL_ERROR") {
    super(message);
    this.name = "AppError";
    this.statusCode = statusCode;
    this.code = code;
  }
}

function findUser(id) {
  if (!id) throw new AppError("缺少用户 id", 400, "MISSING_ID");
  return { id, name: "张三" };
}
```

> [!TIP]
> **建议内容**：抛出的必须是 **Error 实例**。抛出字符串会丢失栈信息，导致无法定位抛出位置，是初学者最常见的隐性损失。

**速记**：自定义错误 **带 statusCode 与 code**。



### 同步代码的错误处理

#### try/catch/finally 的用法

**try/catch**：捕获同步代码块中抛出的异常，让程序在出错后仍可继续执行。

- **try**：包裹可能出错的代码。
- **catch**：参数为捕获到的错误对象，可做补救或记录。
- **finally**：无论是否出错都会执行，适合释放资源、关闭句柄。
- 三者中 **finally 的 return 会覆盖** try 或 catch 中的 return，应避免在 finally 里返回值。

```js
function parseConfig(text) {
  try {
    return JSON.parse(text);
  } catch (err) {
    console.error("配置解析失败", err.message);
    return null;
  } finally {
    console.log("解析流程结束");
  }
}
```

> catch 只捕获 **try 块内的同步异常**。try 块里启动的异步回调若抛错，早已脱离 try 的作用范围，catch 捕获不到。

**速记**：try 管 **同步**，异步另有其道。



#### throw 的时机与代价

**throw 的语义**：表示当前流程**无法继续**，把问题交给上层决定。

- 适合用于**参数非法、前置条件不满足、外部依赖不可用**等真正异常的情形。
- 不适合用作普通的控制流（如用异常跳出循环），会降低可读性并消耗性能。
- 抛出后当前函数**立即终止**，后续语句不再执行。

```js
function divide(a, b) {
  if (b === 0) throw new RangeError("除数不能为零");
  return a / b;
}
```

> 抛出错误会生成栈快照，成本不低。**高频路径上应以返回值表达失败**，仅在真正异常时抛出。

**速记**：异常用于 **不可继续**，不是流程跳转。



### 异步代码的错误处理

#### 错误优先回调约定

**错误优先回调（error-first callback）**：Node 异步 API 的统一约定，回调的**第一个参数是错误对象**。

- 成功时第一个参数为 null 或 undefined，后续参数为结果。
- 失败时第一个参数为 Error，后续参数无意义。
- 每个回调都应**先判 err 再使用结果**，跳过判断会让程序带着错误数据继续跑。

```js
const fs = require("fs");

fs.readFile("config.json", "utf8", (err, data) => {
  if (err) {
    console.error("读取失败", err.code);
    return;
  }
  console.log("读取成功", data.length);
});
```

> 回调风格无法用 try/catch 捕获异步错误，因为回调执行时外层的 try 早已结束。这是回调风格最容易被误解的一点。

**速记**：回调 **先判 err** 再用结果。



#### Promise 的 catch 与 finally

**Promise 的错误传递**：链上任意一环出错，都会跳过后续 then，直接进入最近的 catch。

- **catch**：捕获链上此前产生的异常或 reject。
- **finally**：无论成功失败都执行，常用于关闭加载状态、释放资源。
- catch 之后**仍可继续 then**，表示错误已在此处处理完毕。

```js
const fs = require("fs/promises");

fs.readFile("config.json", "utf8")
  .then((data) => JSON.parse(data))
  .then((config) => console.log("端口", config.port))
  .catch((err) => console.error("失败", err.message))
  .finally(() => console.log("流程结束"));
```

> 若 catch 中再次抛出，错误会继续向后续传递；若 catch 中返回正常值，链条则视为已恢复。

**速记**：Promise 错误 **沿链下传到最近 catch**。



#### async/await 的 try/catch

**await 的错误捕获**：await 会把 Promise 的拒绝变成同步抛出，因此可以用 try/catch 捕获。

- 用 try 包裹 await 表达式，catch 接收错误对象。
- 多个 await 顺序执行时，一个 try 可统一捕获，但**难以区分是哪一步出错**；需要区分时应分别包裹或检查错误类型。
- 忘记 await 会让 Promise 逃逸，错误变成未处理的拒绝。

```js
const fs = require("fs/promises");

async function loadConfig() {
  try {
    const text = await fs.readFile("config.json", "utf8");
    return JSON.parse(text);
  } catch (err) {
    if (err.code === "ENOENT") return {};
    throw err;
  }
}
```

> [!CAUTION]
> **注意内容**：在 forEach、map 的回调里写 async 函数，await 的异常**不会被外层捕获**，且循环不会等待完成。批量异步应使用 for 循环配合 await，或 Promise.all 配 try/catch。

**速记**：await 让 **异步错误可同步捕获**。



### 未被捕获的异常

#### uncaughtException 的兜底与风险

**uncaughtException**：当异常冒泡到事件循环仍无人捕获时触发的进程级事件。

- 注册后进程**不会立即退出**，可在此做最后的日志记录。
- 官方立场明确：捕获后**程序状态已不可信**，应记录并重启进程，而非继续提供服务。
- 未注册该事件时，Node 的默认行为是打印栈并退出。

```js
process.on("uncaughtException", (err) => {
  console.error("未捕获异常", err);
  process.exit(1); // 交由守护进程重启
});
```

> [!WARNING]
> **警告内容**：不要依赖 uncaughtException 让服务"带病运行"。异常发生时的内存与连接状态可能已不一致，继续处理请求会产生难以复现的脏数据。

**速记**：兜底为 **记录后重启**，不是续命。



#### unhandledRejection 的兜底

**unhandledRejection**：Promise 被拒绝却没有任何 catch 处理器时触发。

- 常见于**忘记 await、忘记 return Promise、忘记写 catch**。
- Node 15 起默认行为是**直接终止进程**，此前版本仅打印警告。
- 可用 process.on 捕获并转为告警或退出。

```js
process.on("unhandledRejection", (reason) => {
  console.error("未处理的拒绝", reason);
  process.exit(1);
});
```

> 出现该事件说明代码里存在**确定性的疏漏**，正确做法是补上 catch 或 await，而不是靠兜底掩盖。

**速记**：unhandledRejection 是 **漏写 catch 的信号**。



### Express 中的错误处理

#### 错误处理中间件的写法

**错误处理中间件**：签名比普通中间件**多一个 err 参数**，共四个参数，Express 据此识别其用途。

- 必须写在所有路由之后，才能兜住前面产生的错误。
- 调用 **next(err)** 会跳过后续普通中间件，直达错误处理中间件。
- 不写第四个参数会被当成普通中间件，错误将落入默认处理器。

```js
app.use((err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  res.status(statusCode).json({
    message: err.message || "服务器内部错误",
    code: err.code || "INTERNAL_ERROR"
  });
});
```

> 默认错误处理器会把堆栈返回给客户端（开发环境）。生产环境必须自定义，避免泄露路径与实现细节。

**速记**：错误处理 **四参数、放最后**。



#### 异步错误的传递

**异步错误**：Express 4 及更早版本**不会自动捕获**异步处理器中抛出的异常。

- 路由处理函数里 await 抛错，异常不会进入错误中间件，而是变成未处理的拒绝。
- 解决办法一：在处理器内 try/catch 并调用 next(err)。
- 解决办法二：用包装函数统一捕获，或升级到 Express 5（已支持自动传递）。

```js
function asyncHandler(fn) {
  return (req, res, next) => {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
}

app.get("/users/:id", asyncHandler(async (req, res) => {
  const user = await findUser(req.params.id);
  if (!user) throw new AppError("用户不存在", 404, "USER_NOT_FOUND");
  res.json(user);
}));
```

> 包装函数的价值在于**把每个异步路由的重复 try/catch 收敛为一处**，减少遗漏。

**速记**：异步错误 **手动 next 或统一包装**。



#### 404 与统一响应

**404 处理**：在所有路由之后注册一个普通中间件，表示前面的路径全部未命中。

- 位置必须在**所有业务路由之后、错误处理中间件之前**。
- 响应体应与全局错误格式一致，便于前端统一解析。
- 请求方法不匹配时可用 405，实践中常以 404 统一返回。

```js
app.use((req, res) => {
  res.status(404).json({ message: "接口不存在", code: "NOT_FOUND" });
});
```

> 统一响应结构是前后端协作的前提：约定好 message 与 code 后，前端可用拦截器集中处理提示，不必在每个请求里重复判断。

**速记**：404 中间件 **夹在路由与错误之间**。



### 日志的价值与分级

#### 为什么需要日志

**日志**：是系统运行过程的**事实记录**，用于事后追溯、问题定位与行为审计。

- 线上环境无法打断点，日志是唯一的"现场证据"。
- 错误日志回答"哪里错了"，访问日志回答"谁在什么时候做了什么"。
- 日志要能**还原时间线**：请求标识、用户标识、关键参数、耗时缺一不可。

> console.log 适合开发期临时观察。它缺少分级、无法落盘、不便检索，不应作为生产环境的日志方案。

**速记**：日志是 **线上唯一的现场**。



#### 常见日志级别

**日志级别**：用级别区分重要程度，按环境控制输出量，避免日志淹没关键信息。

- **error**：错误，功能受影响，需立即关注。
- **warn**：警告，异常但可继续，需观察趋势。
- **info**：常规信息，记录关键业务动作。
- **debug**：调试细节，仅开发或排障时开启。
- 生产环境通常输出 **warn 及以上**，开发环境输出 debug。

```js
const level = process.env.NODE_ENV === "production" ? "warn" : "debug";
console.log("当前日志级别", level);
```

> 级别应按**是否需要人来处理**划分。预期内的分支（如用户未登录）记 info 即可，不必打成 error 造成告警疲劳。

**速记**：级别**分级**输出，生产只留 warn 以上。



### console 与日志库

#### console 的常用方法

**console**：Node 内置的控制台输出对象，开箱即用，适合开发与排查。

- **log、info、warn、error**：分别输出到标准输出或标准错误。
- **time 与 timeEnd**：成对使用，测量一段代码耗时。
- **dir**：以对象形式展开查看，depth 控制深度。
- **table**：以表格形式展示数组（仅控制台可视化，非日志结构）。

```js
console.time("query");
// 模拟一次查询
setTimeout(() => {
  console.timeEnd("query");
}, 120);
```

> console 的输出是**同步写**的还是异步写取决于目标类型：写文件时同步，写管道时异步。高并发下大量 console 输出仍会拖慢性能。

**速记**：console 用于 **开发期**，生产换专业库。



#### winston 与 pino

**日志库**：提供分级、格式化、多目标输出与轮转，是生产环境的标配。

- **winston**：功能全面，支持自定义 format、多 transport（控制台、文件、HTTP），配置灵活。
- **pino**：以**高性能**著称，输出 JSON，适合高吞吐服务。
- 二者都支持按级别输出、子日志器、序列化错误处理。

```js
const winston = require("winston");

const logger = winston.createLogger({
  level: process.env.NODE_ENV === "production" ? "warn" : "debug",
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.json()
  ),
  transports: [
    new winston.transports.Console(),
    new winston.transports.File({ filename: "logs/error.log", level: "error" })
  ]
});

logger.info("服务启动", { port: 3000 });
logger.error("数据库连接失败", { code: "ECONNREFUSED" });
```

> 选型口诀：**需要复杂输出目标选 winston，追求吞吐选 pino**。小项目也可用 pino 配少量配置，学习成本不高。

**速记**：winston **灵活**，pino **快**。



#### 结构化日志与敏感信息

**结构化日志**：以 JSON 等机器可读格式记录，便于检索、聚合与告警。

- 每条日志包含**时间、级别、消息、上下文字段**。
- 上下文字段用对象传入，而不是把变量拼进字符串。
- 请求维度应带 **requestId**，把同一次请求的多条日志串起来。

```js
logger.info("用户登录", {
  requestId: "a1b2c3",
  userId: 1001,
  ip: "203.0.113.10",
  durationMs: 42
});
```

> [!WARNING]
> **警告内容**：日志中**禁止记录密码、令牌、身份证号、手机号**等敏感信息。日志常被长期留存并多方可见，一旦落盘，泄露范围难以控制，必要时应做脱敏（如只保留手机号后四位）。

**速记**：日志 **带 requestId、脱敏、JSON 化**。



### 调试手段

#### 内置调试器与 inspect

**内置调试器**：Node 自带基于 Chrome DevTools 协议的调试能力，无需安装额外工具。

- **node --inspect app.js**：启动并开放调试端口，程序正常运行。
- **node --inspect-brk app.js**：启动时**在第一行暂停**，适合调试启动阶段代码。
- 浏览器访问 chrome://inspect 即可连接，进行断点、单步、查看变量。

```bash
node --inspect app.js
node --inspect-brk app.js
```

> 调试端口默认监听 127.0.0.1:9229。切勿在生产环境开放该端口到公网，否则可被远程接管调试会话。

**速记**：inspect 连 **DevTools**，brk **首行暂停**。



#### 编辑器调试配置

**编辑器调试**：在 VS Code 中通过配置文件启动调试，获得与代码同屏的断点体验。

- 配置文件为项目根目录下 **.vscode/launch.json**。
- 常用类型有两种：**launch**（编辑器启动程序）与 **attach**（连接到已启动的进程）。
- program 字段指定入口文件，env 字段注入环境变量。

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "launch",
      "name": "启动服务",
      "program": "${workspaceFolder}/src/app.js",
      "env": { "NODE_ENV": "development" }
    }
  ]
}
```

> 调试子进程或 ts-node 时需额外配置 runtimeArgs。断点调试适合**逻辑复杂、状态难猜**的场景；简单的取值问题用日志更快。

**速记**：launch **由编辑器启动**，attach **连已有进程**。



#### 排查问题的思路

**排查方法**：先复现、再定位、后修复，避免凭猜测改代码。

- 第一步：确认**能否稳定复现**，记录触发条件与输入。
- 第二步：看错误栈中**属于自己代码的最上层帧**。
- 第三步：用日志或断点缩小范围，**二分法**定位到具体语句。
- 第四步：修复后补一条**回归验证**，确认问题不再出现。

> 不要急于修改没看懂的代码。先读懂逻辑再动手，否则容易把问题从一个地方挪到另一个地方，掩盖真正的根因。

**速记**：复现 → 定位 → 修复 → 回归。
