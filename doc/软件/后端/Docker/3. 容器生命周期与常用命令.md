## 容器生命周期与常用命令

### 容器与镜像的概念底座

#### 镜像、容器、仓库与守护进程

**镜像（Image）**：是只读的、分层组织的应用与运行环境模板，自身不能运行。**容器（Container）**：是镜像之上叠加一层可写层后启动的进程实例，是镜像的运行态。**仓库（Registry）**：是集中存放与分发镜像的服务，Docker Hub 是默认的公共仓库。

- 三者是模板、实例、分发点三种角色：镜像不动，容器是运行中的实例，仓库负责搬运。
- 同一个镜像可以启动任意多个容器，容器之间互相隔离，写入只落在各自的容器可写层。
- 容器被删除时可写层一并丢弃，镜像层不受影响；可写层采用写时复制，因此新容器启动极快。
- **Docker 守护进程（dockerd）**：常驻后台、真正创建容器与管理镜像的服务进程。**Docker 客户端（docker CLI）**：把命令行意图翻译成 API 请求发给守护进程的前端。
- 客户端通过 /var/run/docker.sock 上的 Unix 套接字通信，能否操作 Docker 取决于当前用户对该文件的权限。

```bash
docker version                # 同时显示 Client 与 Server 两段
docker info                   # 查看存储驱动、容器与镜像总数
docker context ls             # 查看当前连接的上下文
```

```text
Server: Docker Engine - Community
 Engine:
  Version:          29.8.0
  Storage Driver:   overlayfs
```

> [!NOTE]
> **提醒内容**：docker version 只输出 Client 段，通常说明守护进程没跑起来或当前用户连不上套接字，此时 docker ps 会报 Cannot connect to the Docker daemon。先确认 dockerd 是否运行，再查用户是否在 docker 组里。

**速记**：镜像是只读模板，容器是可写实例，仓库是分发服务；dockerd 干活、docker CLI 传话。



### 生命周期状态机

#### 六个状态的进入与退出条件

**容器状态机**：容器的生命周期由守护进程维护为一个状态字段，常考状态有 created、running、paused、restarting、exited、dead 六个，状态迁移由命令与进程自身行为共同触发。

- created：已用 docker create 建好但从未启动，只占存储不占 CPU。
- running：容器内 PID 1 进程正在执行；paused 由 docker pause 冻结，进程留在内存但不消耗 CPU。
- restarting：进程已退出，因 --restart 策略命中而处于重启间隙。
- exited：进程已终止，元数据与可写层保留，日志仍可查；dead 是清理失败的半残容器，无法启动只能删除。
- 另有瞬时的 removing 状态，出现在 docker rm 执行过程中，一般一闪而过。

```bash
docker ps -a --filter status=paused        # 状态可作过滤器取值
docker pause web && docker unpause web
```

> restarting 是排障的关注点：反复出现该状态说明容器处在崩溃与重启的循环里，应先取一份 docker logs 再决定如何处置，而不是急着删容器。

**速记**：created 未启动、running 在跑、paused 被冻、restarting 在重启间隙、exited 已停、dead 只能删。



#### docker ps -a 的 STATUS 列与退出码

**STATUS 列**：运行中显示 Up 加已运行时长，已退出显示 Exited 加退出码与发生时间，两种格式承载的判断信息完全不同；默认只列运行中的容器，全量要加 -a。**退出码（Exit Code）**：容器内 PID 1 终止时返回的状态码，0 表示正常结束，非 0 表示异常结束，它是 --restart on-failure 判断是否重启的唯一依据。

- Up 3 minutes (healthy)：运行中且健康检查通过；Restarting (1) 5 seconds ago：处于重启间隙，括号内是上一次的退出码。
- Exited (0) 2 weeks ago：正常结束；Exited (137)：被 SIGKILL 杀死。
- 126 表示命令没有执行权限，127 表示命令不存在，143 表示收到 SIGTERM，通用规律是 128 加信号编号。
- 137 的两个来源需分辨：docker stop 超时后补发的 SIGKILL，与内核因内存超限发起的 OOM Kill。
- 反复重启的容器应先用 container inspect 读 RestartCount 与退出码定位原因。

```bash
docker ps -a --filter status=exited
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' web
```

```text
Exited (137) 30 seconds ago
137 true
```

> [!WARNING]
> **警告内容**：STATUS 括号里的数字是退出码，不是已重启次数。Exited (1) 表示进程以失败码 1 退出且不会再自己起来；要看重启次数得读 inspect 的 RestartCount 字段。

**速记**：Up 看时长、Exited (码) 看结果、Restarting (码) 看崩溃循环；0 正常，126 无权限，127 没命令，137 被强杀，143 收到 SIGTERM。



### 创建与运行容器

#### docker run 与 create 加 start

**docker run**：等价于 docker create 加 docker start 两步的合成命令，是创建并启动容器的最常用入口。**docker create**：只创建容器并准备可写层，不启动进程，创建后状态为 created。

- docker create 会打印容器 ID，据此可 docker start 启动、docker inspect 检查配置。
- 两步分离的价值在于先建好容器、确认配置符合预期，再决定何时启动。
- 两者共享同一套参数，docker run 的选项几乎都能原样用在 docker create 上。
- 容器一旦创建，端口、挂载、网络等大部分配置不可再改，只能删除重建。
- 删除容器后同名容器才能重新创建，名字与端口的占用随之释放。

```bash
docker create --name web -p 8080:80 nginx   # 只创建，不启动
docker start web                            # 稍后再启动
docker rm web                               # 重建前先删旧容器
```

> 一次 docker run 出错时，往往已经留下一个 exited 或 created 的容器占着名字与端口，重建前必须先 rm 清理，否则会报容器名已被占用。

**速记**：run 等于 create 加 start，先建后启只用于需要检查配置的场合，配置改不了只能删了重建。



#### 运行模式与命名：-d、-i、-t、--name、--rm

**-d（detach）**：让容器在后台运行并立刻打印容器 ID 返回。**-i（interactive）**：保持标准输入打开。**-t（tty）**：分配一个伪终端。**--name**：给容器指定唯一名字。**--rm**：容器退出时自动删除容器本体与关联的匿名卷。

- 不带 -d 时容器在前台运行并占住终端，Ctrl+C 会把信号直接发给容器主进程。
- -i 单独用很少见，-t 单独用只有终端没有输入流，二者通常连写成 -it；-dit 则兼得后台与可附加终端。
- -it 能进交互式 shell 的前提是镜像里有 shell 且入口允许，服务型容器加了只会得到一个不退出的前台进程。
- 名字在同一守护进程内全局唯一，不给 --name 时随机生成两个单词拼接的名字，如 eager_einstein。
- --rm 与 --restart 是互斥选项，同用直接报冲突错误；它删除的是容器与匿名卷，绑定挂载与命名卷不受影响。

```bash
docker run -d --name web -p 8080:80 nginx    # 后台跑服务
docker run -it --rm alpine sh                # 前台交互式，退出即清理
docker run -dit --name box alpine sh         # 后台运行且保留 stdin 与 tty
```

> [!CAUTION]
> **注意内容**：--rm 是退出即删除，可写层里的数据无法找回，缺少挂载时日志与现场一并消失。排查故障期间不要加 --rm，等问题定位完再手动 rm。

**速记**：-d 后台、-i 保输入、-t 给终端，-it 是交互式标准组合；--name 定唯一名，--rm 退出即删且与 --restart 互斥。



#### 环境与主机信息：-e、--env、--hostname

**-e、--env**：在容器启动时把环境变量注入进程环境，语法为 -e KEY=VALUE。**--hostname**：设置容器内的主机名，默认是容器 ID 的前 12 位。

- 不写等号时（如 -e DEBUG）会把宿主机当前 shell 中同名变量的值传进去，该变量不存在则跳过。
- 可重复多次传递，变量多时用 --env-file 从文件批量读取。
- 变量在容器启动时固化，运行中修改只能重建容器；它对容器内所有进程可见，也会出现在 inspect 输出里。
- --hostname 只改容器内的主机名，与容器之间能否互相访问无关，互访靠自定义网络的 DNS。
- 应用应优先读环境变量而不是读配置文件，一个镜像即可通过变量适配多套环境。

```bash
docker run -d --name api --hostname api-01 \
  -e NODE_ENV=production \
  -e TZ=Asia/Shanghai \
  -e DB_HOST=mysql \
  node:24-alpine
```

> [!IMPORTANT]
> **重要内容**：环境变量对容器内所有进程可见，也会出现在 docker inspect 与宿主上的进程环境里。密码、令牌之类高敏感值不应通过 -e 明文传入，应改用密钥挂载或专用密钥机制，详见第 12 章。

**速记**：-e 注入进程环境，只写键名则继承宿主机；--hostname 只管容器内称呼，明文变量不等于安全。



#### 端口、数据与网络：-p、-v、--network

**-p、--publish**：把容器端口映射到宿主机端口，格式为宿主端口:容器端口。**-v、--volume**：把宿主目录或命名卷挂载到容器内路径。**--network**：指定容器接入哪个网络，不指定时接入默认的 bridge 网络。

- -p 的完整格式可带绑定地址与协议，如 -p 127.0.0.1:8080:80/tcp；只给容器端口时由守护进程随机分配宿主端口，用 docker port 查询。
- 与 -p 相对的是 --expose，它只声明端口不发布；同一宿主端口不能被两个容器同时占用，冲突报 Bind failed。
- -v 的格式为源:目标:权限，源是路径即绑定挂载、是名字即命名卷、省略则生成匿名卷；ro 后缀表示只读。
- 默认 bridge 网络下容器只能靠 IP 互访且没有自动 DNS，自定义网络才支持按容器名解析。
- --network host 共享宿主网络命名空间，--network none 切断网络，--network container:名字 共享目标容器的网络命名空间。

```bash
docker run -d --name web -p 127.0.0.1:8080:80 nginx
docker run -d --name mysql -v mysql-data:/var/lib/mysql --network app-net mysql:8
docker run -d --name api --network app-net node:24-alpine
docker exec api getent hosts mysql
```

```text
172.18.0.2      mysql
```

> [!CAUTION]
> **注意内容**：不带源路径的 -v 会创建匿名卷，容器删除后数据难以找回，还会留下大量难以辨认的悬空卷。端口方向固定为左宿主右容器，写反会造成服务不通却难以一眼看出。

**速记**：-p 左宿主右容器，-v 源:目标:权限，按名字互访必须自定义网络；host 共享宿主网络，none 切断网络。



#### 重启策略：--restart 四值对照

**--restart**：规定容器退出后守护进程是否以及如何自动拉起，取值有 no、on-failure、always、unless-stopped 四种，默认 no。

- no：不自动重启，默认值，用于手工调试与一次性任务。
- on-failure[:max-retries]：仅在退出码非 0 时重启，可限制重试次数；守护进程自身重启后不会恢复该策略的重启行为。
- always：无论退出码如何都重启；手工 stop 后不再自行重启，但守护进程或机器重启后会拉起。
- unless-stopped：与 always 类似，区别在容器被手工停止后，即使守护进程重启也不会再拉起。
- 四值的差异集中在两件事：非 0 退出才重启还是都重启，手工停止后是否仍然复活。

```bash
docker run -d --name web --restart unless-stopped -p 80:80 nginx
docker update --restart always web                      # 运行中改策略，无需重建
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' web
```

```text
always
```

> 常被忽略的差别：always 在被手工 docker stop 后，守护进程一重启它就会复活；unless-stopped 则尊重手工停止这一意图。生产上用 unless-stopped 更贴合人的预期。

**速记**：no 不重启，on-failure 非 0 才重启，always 一律重启，unless-stopped 手工停后不再复活。



#### 入口与身份：--entrypoint、-w、-u

**--entrypoint**：覆盖镜像里定义的 ENTRYPOINT，用于临时改掉默认启动程序。**-w、--workdir**：指定容器内的工作目录。**-u、--user**：指定以哪个用户或 UID 运行容器内进程。

- --entrypoint 只接受一个可执行文件路径，其参数要放到镜像名之后的命令位置。
- -w 默认取自镜像的 WORKDIR，覆盖后进程当前目录随之改变，脚本里的相对路径都以此为基准。
- -u 可写用户名、UID 或 UID:GID 组合，如 -u 1000:1000；不指定时以镜像的 USER 为准，镜像未定义 USER 则以 root 运行。
- -u 常用于解决挂载目录的权限不匹配，让容器进程的用户与宿主目录属主一致。
- Engine 29.8.0 起新增 --umask，用于设定容器主进程、exec 进程与健康检查的 umask，不指定则继承守护进程（通常为 0022）。

```bash
docker run --rm --entrypoint /bin/sh alpine -c "id"
docker run --rm -w /tmp -u 1000:1000 alpine pwd
docker run --rm --umask 0027 alpine sh -c "umask"
```

```text
uid=1000 gid=1000 groups=1000
/tmp
0027
```

> [!WARNING]
> **警告内容**：不写 -u 时容器默认以 root 运行，容器内的 root 与宿主 root 只隔一层命名空间，一旦逃逸后果严重。生产容器应显式指定非 root 用户，安全细节见第 16 章。

**速记**：--entrypoint 换启动程序，-w 换工作目录，-u 换运行身份，--umask 换文件掩码；默认 root 是安全红线。



#### 命令行参数如何覆盖 CMD

**启动命令的来源**：容器最终执行什么，由镜像的 ENTRYPOINT 与 CMD 以及 docker run 命令行追加的参数三者按规则拼合而成。

- 镜像无 ENTRYPOINT 时，docker run 镜像名之后的参数整体覆盖 CMD，如 docker run alpine echo hi 就是覆盖。
- 镜像有 ENTRYPOINT 时，命令行参数追加在 ENTRYPOINT 之后成为其实参，而不是整体替换。
- CMD 在两种情况下都只是默认值，命令行一旦给出参数就被取代。
- 想改掉 ENTRYPOINT 本身必须显式使用 --entrypoint，仅在命令行追加参数是改不动的。
- 这解释了一个常见现象：给带 ENTRYPOINT 的镜像直接追加命令，命令会变成入口程序的参数而被误解。

```bash
docker run --rm alpine echo hello
docker inspect -f '{{.Config.Entrypoint}}' nginx:1.27
docker inspect -f '{{.Config.Cmd}}' nginx:1.27
```

```text
hello
[nginx -g daemon off;]
```

> 判断某镜像属于哪种情形的快捷方法：用 docker inspect 查看 Config.Entrypoint 是否为空。非空即命令行参数为追加，为空即覆盖，这一条能省掉大量试错。

**速记**：无 ENTRYPOINT 时命令行覆盖 CMD，有 ENTRYPOINT 时命令行追加为参数；换入口要显式 --entrypoint，拼合细节见第 5 章。



### 启停与移除

#### start、stop、restart 与停止宽限期

**docker start**：启动一个已创建或已停止的容器，复用其原有配置。**docker stop**：向容器内 PID 1 发送 SIGTERM，宽限期后仍不退则补发 SIGKILL。**docker restart**：等价于 stop 加 start。

- start 对 created 与 exited 都有效，对 running 的容器是空操作。
- stop 默认宽限期 10 秒，可用 --time 或 -t 指定秒数；restart 同样接受 --time。
- 停止后容器不会消失，可写层与配置保留，再次 start 即可恢复运行。
- 容器启动时可设置 --stop-timeout 改变默认停止宽限期，运行中调整则在 stop 命令上显式传 -t。
- stop 发的是信号而不是拔电源，程序应捕获 SIGTERM 做收尾，这依赖 PID 1 的信号处理。

```bash
docker start web
docker stop web
docker stop -t 30 web                        # 给 30 秒宽限期
docker run -d --stop-timeout 30 --name slow-api myapp:1.0
```

> [!NOTE]
> **提醒内容**：docker stop 默认只等 10 秒，处理慢的应用（如正在写盘的数据库）常被强杀，表现为退出码 137。这类容器应在启动时加 --stop-timeout，或在停止时显式传 -t 更长的秒数。

**速记**：start 复用旧配置启动，stop 先 SIGTERM 后 SIGKILL 且默认等 10 秒，restart 等于 stop 加 start。



#### kill、pause 与 unpause

**docker kill**：直接发送信号终止容器，默认 SIGKILL，不给程序收尾机会。**docker pause**：冻结容器内所有进程。**docker unpause**：解冻恢复。

- kill 可指定信号，如 docker kill -s SIGTERM web 等价于一次不等待的快速停止。
- kill 不等待，容器立即进入 exited，退出码通常为 137。
- pause 不终止进程只冻结，进程仍在内存中，状态显示 Paused，CPU 占用归零。
- 容器处于 paused 状态时 exec 会报错，须先 unpause 才能进入。
- 冻结的容器内存并不释放，缓解不了内存压力；pause 适合临时让容器让出 CPU 或保留现场做静态排查。

```bash
docker pause web && docker unpause web
docker kill -s SIGTERM web    # 温和终止，不等待
docker kill web               # 立即强杀
```

> 停止语义分三档：kill 立即、stop 礼貌等待、pause 只冻不杀。它们对数据的风险依次是高风险、低风险、无风险，恢复手段则依次是没有、重新 start、直接 unpause。

**速记**：kill 立即发信号不等待，pause 冻结不杀进程，unpause 解冻；被冻结的容器仍占内存。



#### rm、rm -f、rm -v 与批量清理

**docker rm**：删除已停止的容器，连同可写层与元数据一起清除，不可恢复。**-f**：强制删除运行中的容器，相当于先 kill 再删除。**-v**：同时删除该容器创建的匿名卷。

- 删除运行中的容器会报 You cannot remove a running container，须先 stop 或加 -f。
- -f 直接杀进程，未落盘的数据可能丢失；稳妥顺序是先 docker stop 再 docker rm。
- -v 删除的是匿名卷，命名卷与绑定挂载不受影响；不加 -v 时匿名卷会成为悬空卷残留。
- 批量清理的标准写法是 docker ps -aq 加过滤器再喂给 docker rm，先不带删除地跑一遍确认范围。
- 不要使用 docker rm $(docker ps -aq) 这类无条件写法，除非确实要清空一切。

```bash
docker rm -v temp-db
docker ps -aq --filter status=exited                  # 先看要删哪些
docker rm $(docker ps -aq --filter status=exited)     # 确认后再删
```

> [!CAUTION]
> **注意内容**：rm 是不可逆操作，可写层里未挂载到卷的数据彻底丢失，也没有回收站。想留证据先 docker cp 出日志，或 docker commit 存一份快照，再执行删除。

**速记**：rm 删已停容器，-f 强删运行中，-v 捎带删匿名卷；批量清理用 ps -aq 加过滤并先看后删。



### 进入与调试

#### exec 与 attach 的差别

**docker exec**：在运行中的容器里新起一个进程执行命令，是进去排障的标准方式。**docker attach**：把当前终端接到容器 PID 1 的标准输入输出上，不新起进程。

- exec 每执行一次就多一个进程，退出的是这个新进程，不改变容器状态。
- attach 接的是主进程，按下 Ctrl+C 会把信号直接送给主进程，容器可能因此退出。
- 脱离方式不同：attach 默认用 Ctrl+P Ctrl+Q 脱离，exec 直接 exit 即可。
- attach 要求主进程有可交互的终端，服务型容器 attach 上去通常只见日志刷屏。
- exec 起的进程不随容器重启而保留，容器一重启它就消失了。

```bash
docker exec -it web sh                 # 新起一个 shell
docker attach web                      # 接到主进程，脱离需 Ctrl+P Ctrl+Q
```

> [!WARNING]
> **警告内容**：attach 后直接按 Ctrl+C 会把中断信号发给容器主进程，很可能把服务按停。脱离应当用 Ctrl+P Ctrl+Q，或用 --detach-keys 自定义脱离键。

**速记**：exec 新起进程不动主进程，attach 接主进程且 Ctrl+C 会传给它；脱离用 Ctrl+P Ctrl+Q。



#### exec 的 shell 选择与常用选项

**exec 的常见用法**：docker exec -it 容器名 命令，最常用的是进一个 shell；选 sh 还是 bash 取决于镜像里装了哪个。

- alpine、busybox 等精简镜像通常只有 sh，没有 bash，敲 bash 会报 not found；Debian、Ubuntu 基底镜像一般两者都有。
- 命令必须是可执行文件，带引号的整条命令不生效，需要 shell 解析时用 sh -c 包起来。
- -u 指定 exec 进程的运行用户，-w 指定工作目录，-e 传入只对本次 exec 生效的环境变量。
- -d 让 exec 的命令在后台执行；容器处于 paused 状态时 exec 直接报错，先 unpause 再进。
- 写进脚本的自动化流程不走交互式 shell，直接用 docker exec 容器 命令 的形式，避免依赖镜像里存在某个 shell。

```bash
docker exec -it web bash
docker exec web sh -c "echo a && echo b"
docker exec -u root -w /app web id
```

```text
a
b
uid=0(root) gid=0(root) groups=0(root)
```

**速记**：有 bash 用 bash、精简镜像用 sh；整条命令交给 sh -c，-u、-w、-e 只影响本次 exec。



#### docker logs 的过滤组合

**docker logs**：读取容器主进程写到标准输出与标准错误的日志，是容器化后查日志的第一入口。

- 默认输出全部已有日志，-f 或 --follow 持续跟踪新日志，等价于 tail -f。
- -n 或 --tail 限制末尾行数，如 --tail 100 只看最后一百行，避免被历史日志淹没。
- --since 与 --until 按时间范围过滤，支持相对写法（42m、3h）与时间戳；-t 或 --timestamps 为每行加时间戳。
- --details 额外显示日志驱动附带的属性；日志能否读到取决于日志驱动，默认的 json-file 驱动才支持 logs。
- 日志总量与轮转由日志驱动参数控制，属第 14 章内容。

```bash
docker logs -f --tail 100 web
docker logs --since 42m web
docker logs -t --since 2026-09-12T00:00:00 web
```

```text
2026-09-12T08:01:02.345678901Z 172.18.0.1 - - "GET / HTTP/1.1" 200
```

> [!IMPORTANT]
> **重要内容**：docker logs 只拿得到主进程写到 stdout 与 stderr 的内容；应用把日志写进容器内文件时 logs 里什么也看不到，只能用 exec 进去读文件，或改配置让它输出到标准输出。

**速记**：-f 跟踪、--tail 限行、--since 与 --until 限时段、-t 加时间戳；只认标准输出与错误流。



#### docker inspect 与 --format

**docker inspect**：以 JSON 形式输出容器、镜像、网络或卷的完整底层配置，是查证实际生效的是什么 的权威手段。**--format**：用 Go 模板从这份 JSON 里抽取字段。

- -f 或 --format 支持 Go 模板语法，路径按 JSON 层级点分，如 {{.State.Status}}。
- 常用字段：.State.Status 看状态、.State.ExitCode 看退出码、.State.OOMKilled 看是否被内存杀、.RestartCount 看重启次数、.NetworkSettings.IPAddress 看 IP。
- 模板中还能用 range 遍历数组，例如列出所有挂载点。
- inspect 同样适用于镜像与网络，镜像的 Config 段可查 ENTRYPOINT、CMD、Env 等构建期配置。
- 不加筛选时输出长 JSON，适合交给 jq 二次处理。

```bash
docker inspect web
docker inspect -f '{{.State.Status}}' web
docker inspect -f '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' web
docker inspect -f '{{.Config.Cmd}}' nginx:1.27
```

```json
{
  "State": {
    "Status": "running",
    "ExitCode": 0,
    "OOMKilled": false
  },
  "RestartCount": 0
}
```

> [!TIP]
> **建议内容**：遇到"我明明加了参数却不生效"的疑问，一律先 docker inspect 看运行时实际值，而不是回看自己敲过的命令——inspect 反映的是守护进程真正采纳的配置。

**速记**：inspect 出全量 JSON，--format 抽字段；查退出码看 .State.ExitCode，查内存杀看 .State.OOMKilled。



#### stats、top、diff 与 cp

**docker stats**：实时显示容器的 CPU、内存、网络与磁盘读写用量，类似 top。**docker top**：查看容器内运行的进程列表。**docker diff**：列出容器可写层相对镜像层的文件改动。**docker cp**：在宿主机与容器之间双向拷贝文件。

- stats 默认对所有运行中容器流式刷新，加 --no-stream 只取一次快照，便于脚本采集。
- stats 的 MEM USAGE 包含页缓存，与容器内 free 的读数口径不同，判断上限要看向 LIMIT 逼近的程度。
- top 显示容器内进程及其在宿主上看到的 PID；diff 的三种标记是 A 新增、C 修改、D 删除，且只覆盖可写层。
- cp 的方向由哪一侧带容器名冒号决定，已停止的容器同样可以拷入拷出，同名文件会被覆盖。
- 大量文件或需要持续同步时应改用 -v 挂载，cp 只是应急搬运手段。

```bash
docker stats --no-stream web
docker top web
docker diff web
docker cp web:/etc/nginx/nginx.conf ./nginx.conf
```

```text
CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   PIDS
a1b2c3d4e5f6   web    0.02%   12.3MiB / 7.6GiB    0.16%   5

C /var/log/nginx
A /var/cache/nginx/client_temp
```

**速记**：stats 看用量、top 看进程、diff 看可写层改动、cp 双向拷贝；diff 的 A 是新增、C 是修改、D 是删除。



#### docker debug 简介

**docker debug**：是 Docker Desktop 内置的容器调试工具，用一条命令给目标容器或镜像套上一个可交互的调试环境，预装常用排障工具。

- 前提明确：它是 Desktop 提供的子命令，纯 Docker Engine 环境（服务器上独立安装的 docker-ce）没有这个命令，执行会报未知子命令。
- 用法是对容器名或镜像名执行 docker debug，进入后自带 curl、vim、netstat 等常用工具。
- 它的价值在于解决精简镜像里没有 shell、也没有 curl 之类工具的窘境，无需重建镜像。
- 与 exec 的关系是互补：能 exec 进去且工具够用就不必用它，镜像太精简时它更省事。
- 无 Desktop 时退回 docker exec 加手工安装工具，或用 docker cp 拷入静态二进制。

```bash
docker debug web            # 进入 web 容器的调试环境
docker debug nginx:1.27     # 对镜像调试，不必先启动容器
```

**速记**：docker debug 是 Desktop 专属，给精简镜像套调试环境；纯 Engine 环境不可用，退用 exec 与 cp。



### 镜像侧常用命令

#### images、pull、tag 与 push

**docker images**：列出本地镜像的仓库名、标签、镜像 ID、创建时间与大小。**docker pull**：从仓库把镜像拉到本地。**docker tag**：给已有镜像再贴一个名字加标签，指向同一镜像 ID。**docker push**：把本地镜像推送到仓库。

- 不写标签时默认拉 latest，latest 只是默认标签，并不是最新版 的保证。
- SIZE 一列是压缩层与解压后的合计，同一底层镜像的多个标签会重复计数；--filter dangling=true 只看悬空镜像。
- pull 与 push 都逐层比对，已有层直接复用或跳过，只传缺失层。
- tag 不复制镜像数据，只是新增一个引用；推送前必须先 docker login 登录。
- 标签格式为 仓库地址/命名空间/名字:标签，不写仓库地址时默认目标是 Docker Hub 的官方命名空间。
- 从 Engine 29.0 起全新安装默认使用 containerd 镜像存储，与旧的 overlay2 有细微差异，命令用法不变，详见第 4 章。

```bash
docker pull nginx:1.27
docker tag myapp:1.0 registry.example.com/team/myapp:1.0
docker login registry.example.com
docker push registry.example.com/team/myapp:1.0
```

```text
The push refers to repository [registry.example.com/team/myapp]
1.0: digest: sha256:1f2e3d4c5b6a... size: 1234
```

> 镜像名与仓库地址必须成对：本地叫 myapp 的镜像直接 push 会被当成要推到 Docker Hub 的官方库，多半因无权限失败；先 tag 成完整名字再推。

**速记**：images 列本地、pull 拉远端、tag 贴新名、push 推仓库；latest 只是标签名，推送前要写全地址并先 login。



#### rmi、history 与 image prune

**docker rmi**：删除本地镜像及其标签。**docker history**：展示镜像的构建历史，逐层列出创建命令与大小。**docker image prune**：清理无用镜像。

- 镜像被容器引用时不能删，须先删除容器或用 -f 强制；-f 只解除标签，底层层仍被占用时不释放空间。
- 一个镜像有多个标签时，rmi 删掉其中一个标签不等于删除镜像本体。
- history 是理解镜像分层与定位哪一层把体积撑大 的入口，属第 4、5 章的引子。
- image prune 默认只删悬空镜像，加 -a 才删除所有未被容器使用的镜像。
- -a 的删除不可逆，更稳妥的写法是加 --filter 限定时间，如 --filter until=24h。

```bash
docker rmi myapp:1.0
docker history nginx:1.27
docker image prune                                   # 只清悬空镜像
docker image prune -a --filter "until=24h"           # 只清一天前创建且未被使用的
```

```text
Untagged: myapp:1.0
Deleted: sha256:7a8b9c0d1e2f...

IMAGE          CREATED        CREATED BY                       SIZE
a1b2c3d4e5f6   2 weeks ago    /bin/sh -c #(nop) CMD ["nginx"]   0B
```

> [!CAUTION]
> **注意内容**：docker image prune -a 会删除所有当前没有容器使用的镜像，包括手工拉下来准备用的基础镜像，之后必须重新拉取。执行前先用 docker images 确认范围。

**速记**：rmi 删镜像、history 看分层、prune 默认只清悬空、加 -a 清全部未使用镜像。



#### save/load 与 export/import 的差别

**save 与 load**：在镜像层面搬运，保留完整的分层与元数据。**export 与 import**：在容器文件系统层面搬运，压成一层的扁平 tar，丢失历史与配置。

- docker save 镜像名 -o 文件.tar 把镜像连同全部层导出为一个 tar，docker load -i 文件.tar 导入。
- docker export 容器名 -o 文件.tar 导出容器当前文件系统的快照，docker import 文件.tar 名字 生成只有一层的镜像。
- save 与 load 保留分层、环境变量、入口等元数据，适合离线迁移镜像。
- export 与 import 丢失 CMD、ENTRYPOINT、环境变量与层历史，导入后必须重新指定运行参数。
- export 导出的是此刻的文件系统，包含运行中产生的改动，更适合做一次性快照。
- 采用 containerd 镜像存储的新版守护进程，save 的产物可能是 OCI 布局，load 仍可正确读取，详见第 4 章。

```bash
docker save nginx:1.27 -o nginx.tar
docker load -i nginx.tar
docker export web -o web-fs.tar
docker import web-fs.tar myapp:snapshot
```

> 判断该用哪一对只需一问：要搬的是镜像 还是容器的当前文件系统。要保完整的镜像语义用 save 与 load，只要一个扁平快照用 export 与 import。

**速记**：save 与 load 搬镜像保留分层与元数据，export 与 import 搬文件系统只剩一层且丢配置。



#### build 与镜像清理入口

**docker build**：读取 Dockerfile 构建镜像，是镜像来源的主入口，语法细节属第 5 章，此处只交代它在命令体系中的位置。

- 基本形式为 docker build -t 名字:标签 构建上下文路径；-t 打标签、-f 指定 Dockerfile 路径、--no-cache 禁用缓存。
- 构建产物进入本地镜像库，随后可用 images 查看、run 启动、push 推送。
- 构建过程中产生的中间层与缓存由 docker builder prune 清理。
- 构建上下文是发给守护进程的目录内容，不是 Dockerfile 所在位置，在巨大目录里执行会把无关文件一起上传。
- 从 Engine 29 起的 containerd 镜像存储对构建缓存的存放位置有调整，清理命令不变。

```bash
docker build -t myapp:1.0 .
docker build -t myapp:dev -f Dockerfile.dev .
docker builder prune
```

**速记**：build 出镜像、-t 打标签、-f 指定文件；缓存用 builder prune 清，上下文与 .dockerignore 见第 6 章。



### 容器与宿主机的边界

#### PID 1、信号与 --init

**PID 1 的特殊性**：容器内第一个进程的 PID 是 1，它同时承担被容器视为 init 的角色，对信号的处理方式与普通进程不同。**单进程模型**：容器的设计前提是一个容器一个主进程，主进程退出即容器结束，容器内没有 systemd 或任何服务管理器。

- 作为 PID 1 的进程若没有为某信号注册处理函数，内核会忽略该信号，包括 SIGTERM。
- 结果就是 docker stop 发出的 SIGTERM 可能被无视，只能等宽限期结束被 SIGKILL 强杀。
- 应用直接作为入口时若被一层 shell 包装，信号也传不到真正的主进程，需用 exec 形式启动。
- docker run 的 --init 可以注入一个极简 init 进程，负责收信号与回收僵尸进程。
- 需要多个进程时应拆成多个容器并用网络或 Compose 组合，把 systemd 塞进容器会带来权限与 cgroup 的连锁问题。

```bash
docker run -d --init --name api node:24-alpine node server.js
docker stop -t 30 api
docker inspect -f '{{.State.Pid}}' api       # 主进程在宿主上的 PID
```

> [!IMPORTANT]
> **重要内容**：进程作为 PID 1 运行时，未注册处理函数的信号会被内核丢弃，这不是 Docker 的行为，而是 Linux 对 PID 1 的既有规定。服务卡在 stop 上十秒才被强杀，多半就是这个原因。

**速记**：一容器一主进程、没有 systemd；PID 1 收不到的信号会被内核忽略，要优雅退出就自注册 SIGTERM 或加 --init。



#### 时区、locale 与 hosts/DNS 注入

**时区（TZ）**：容器默认沿用镜像里固化的时区，多数基础镜像为 UTC。**locale**：字符集与语言环境，精简镜像常只装了最小字符集。**DNS 注入**：守护进程启动容器时会生成 /etc/hosts 与 /etc/resolv.conf，使容器能解析其他容器名与外部域名。

- 最直接的改时区办法是注入 -e TZ=Asia/Shanghai，前提是镜像里有对应时区数据，alpine 等需先安装 tzdata。
- 另一种办法是把宿主的 /etc/localtime 与 /etc/timezone 只读挂载进去。
- locale 决定中文显示、排序与日期格式，缺字符集时程序可能报编码错误。
- /etc/hosts 里写入容器自身 hostname 与 --add-host 追加的映射，/etc/resolv.conf 指向守护进程内置的 DNS 服务器。
- 默认 bridge 网络不提供按容器名解析，只有自定义网络才有，这是互访成败的关键。
- 这些文件由守护进程生成，容器内手工修改在重启后会丢失，要持久化应借助挂载。

```bash
docker run -d --name web -e TZ=Asia/Shanghai --add-host db.internal:10.0.0.5 nginx
docker exec web date
docker exec web cat /etc/hosts
```

```text
Sat Sep 12 08:30:00 CST 2026
172.18.0.3      web
10.0.0.5        db.internal
```

> [!TIP]
> **建议内容**：时区与 locale 都应在镜像构建阶段定好，而不是每条 run 命令临时注入；容器数量一多，临时注入迟早会漏。要在容器内用 ENV TZ 加安装 tzdata 的方式固化。

**速记**：容器默认多为 UTC，用 -e TZ 或挂载 localtime 改时区；hosts 与 resolv.conf 由守护进程生成，自定义网络才有名字解析。



### 系统级命令与磁盘回收

#### system df 与 system prune 的边界

**docker system df**：汇总镜像、容器、卷与构建缓存各自占用的磁盘空间，是清理前的第一步侦察。**docker system prune**：一键清理已停止的容器、未被使用的网络、悬空镜像与构建缓存。

- system df 只做统计不删除，加 -v 展开到每一个镜像、容器、卷的明细，RECLAIMABLE 一列提示能省多少。
- system prune 默认范围不含未使用的镜像（只清悬空）与任何卷，是相对温和的一档。
- -a 或 --all 会删除所有未被任何容器使用的镜像，包括手工拉取待用的。
- --volumes 会删除未被容器使用的匿名卷；三者叠加时破坏面最大，等价于把不用的东西全清掉。
- --filter 可按 until 或 label 限定范围，是比裸跑更安全的用法。

```bash
docker system df -v
docker system prune --filter "until=168h"        # 只清一周前的
docker system prune -a --volumes                 # 最激进，含匿名卷
```

```text
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all dangling images
  - unused build cache
Are you sure you want to continue? [y/N]
```

> [!WARNING]
> **警告内容**：docker system prune -a --volumes 会连未被容器引用的匿名卷一并删除，卷里可能是数据库的残留数据。清除前确认没有停掉容器但数据仍在卷里 的对象，误删无法找回。

**速记**：df 看总量、活跃与可回收，只统计不删除；prune 默认温和，-a 加未用镜像，--volumes 加匿名卷，叠加最危险。



#### 分类清理：builder、network、volume 与 image

**分类清理命令**：把清理粒度拆到单类对象上的四条命令，比 system prune 更可控，适合按需回收。

- docker builder prune 只清构建缓存，可用 --filter until= 限定时间范围。
- docker network prune 清未被任何容器使用的网络，自定义网络闲置后会被回收。
- docker volume prune 默认只清未被引用的匿名卷，加 -a 才连命名卷一起清（需 API 1.42 以上）。
- docker image prune 默认清悬空镜像，加 -a 清所有未被容器使用的镜像。
- 逐类清理的好处是每次只看一类对象，副作用范围明确，误删概率低于一键全清。

```bash
docker builder prune --filter "until=168h"
docker network prune
docker volume prune -a       # 连命名卷一起清
```

> [!CAUTION]
> **注意内容**：docker volume prune -a 会删除未被容器引用的命名卷，命名卷往往承载数据库数据，只要容器停了而卷留着就会被判定为未引用。删卷前用 docker volume ls 与 docker volume inspect 逐个确认。

**速记**：builder、network、image、volume 四类分开清更可控；volume prune 加 -a 会删命名卷，最需谨慎。



### 命令速查与组合模式

#### 一次性任务容器与临时调试容器

**一次性任务容器**：以 --rm 起一个临时容器执行完即退出并自删，适合跑脚本、做数据处理、验证环境。**临时调试容器**：起一个带网络与工具的精简容器，去访问同网络内的其他服务，用于排查连通性与配置问题。

- 一次性任务用 docker run --rm 镜像 命令 的形式，任务结束容器自动消失，不留垃圾。
- 需要把产物写到宿主时配套 -v 挂载，只需读宿主目录内容时把挂载加 ro 更安全。
- 调试容器不必往生产容器里装工具，起一个 alpine 接同一网络即可，常见动作是 getent 验 DNS、wget 验 HTTP、nc 验端口。
- --network container:目标容器 可让调试容器共享目标网络命名空间，直接查端口监听。
- 一次性容器天然幂等，反复执行不留残留，是验证镜像最省心的形态。

```bash
docker run --rm alpine sh -c "echo done"
docker run --rm -v mysql-data:/from:ro -v "$PWD":/to alpine sh -c "cd /from && tar czf /to/mysql.tgz ."
docker run --rm -it --network app-net alpine sh
docker run --rm --network container:web nicolaka/netshoot ss -lntp
```

```text
done
172.18.0.4      api
```

> [!TIP]
> **建议内容**：把起一个同网络的一次性容器去探测目标 作为网络排障的第一步，它的结论比在应用容器里猜更直接——能解析说明 DNS 通，能连上端口说明网络与发布都通，剩下的才是应用本身的问题。

**速记**：--rm 即用即走、产物靠挂载落宿主；同网络起临时容器测 DNS 与端口，随用随弃。



#### 按名字批量操作与管道组合

**管道组合**：把 docker 的查询命令用 -q 只输出 ID，再喂给删除、停止等命令，是批量操作的标准套路。

- docker ps -q 输出容器 ID，docker images -q 与 docker volume ls -q 同理。
- 命令替换写成 docker stop $(docker ps -q --filter name=api-)，过滤在前、动作在后。
- 结果过多时改用 xargs，如 docker ps -q | xargs -r docker stop，-r 让输入为空时不执行命令。
- 日志侧的常见组合是 docker logs -f 加 grep 做实时过滤。
- 组合命令前先单独跑一遍查询部分，确认对象范围再拼上动作。

```bash
docker stop $(docker ps -q --filter name=api-)          # 按名字前缀停止
docker ps -q --filter status=exited | xargs -r docker rm
docker logs -f web | grep --line-buffered ERROR         # 日志实时过滤
```

> [!WARNING]
> **警告内容**：docker stop $(docker ps -q) 与 docker rm $(docker ps -aq) 会作用于当前守护进程上的全部对象。多项目共用一台机器时，这类无条件写法极易误伤，务必先加 --filter 限定范围。

**速记**：-q 出 ID、过滤限范围、xargs -r 防空参；日志用 logs -f 加 grep；无条件批量命令要先加过滤。
