## 镜像分层与存储驱动

### 分层模型的原理

#### 每一层是一次文件系统差异

**层（Layer）**：是镜像中一组文件系统改动的集合，记录的是相对其父层的**差异（diff）**，而不是一份完整文件系统的快照。镜像就是这些差异按父子顺序叠起来的结果。

- 构建镜像时，每条会改动文件系统的指令（RUN、COPY、ADD）产出一个新层。
- 差异以增量方式记录：新增的文件、被修改的文件、被删除的文件各以不同方式体现。
- 每层都有内容摘要，摘要由层内容算出，内容相同则摘要相同。
- 层与层按父子顺序串成一条链，链的最底端是基础镜像（如 alpine、debian）自带的根文件系统层。
- 层的总数等于基础镜像自带的层数，加上构建过程中产生文件系统改动的步骤数。

> 需要区分“指令数”与“层数”。ENV、CMD、LABEL 这类只写元数据的指令不改变文件系统，也就不会产出一个有内容的新层，历史上仍会生成一条层记录，在 docker history 里显示为 0B，其成因见本篇后文。

**速记**：层是相对父层的**文件系统差异**，按内容算摘要、按父子串成一条链。



#### 层是只读的

**只读性**：镜像的所有层一经生成即不可修改，任何运行期写入都不落在镜像层上。

- 只读使多个容器可以安全共享同一批层，彼此不会互相污染。
- 只读也使镜像可被并发拉取与分发：层内容不变，摘要即可作为完整性校验的依据。
- 层内容一旦改变，其摘要随之改变，等同于换成了一个新层。
- 只读层配合写时复制，使新容器启动时无需复制整个文件系统。

> 只读的是**镜像层**，不是容器里的整个文件系统。容器运行时所看到的是一个可写的统一视图，只是这个视图里的改动全部落在最上面的可写层，与下面的只读镜像层无关。

**速记**：镜像层**生成即只读**，共享安全、分发可校验。



#### 容器启动时叠加可写层

**可写层（Writable Layer，又称容器层）**：是容器启动时在镜像层栈顶新增的一层，是这个容器独有的可写空间。

- 每个容器各自拥有一个可写层，容器 A 的写入对容器 B 不可见。
- 可写层的生命周期等于容器本体：容器被删除，可写层随之一并丢弃。
- 可写层保存容器运行期对文件系统做出的全部改动：新建的文件、改过的配置、写下的日志等。
- 容器停止（exited）后可写层仍然保留，下次 start 继续沿用；只有 rm 才会真正丢掉它。
- 同一镜像启动的多个容器，只有可写层各自独立，下面所有镜像层完全共用。

> [!IMPORTANT]
> **重要内容**：可写层不是持久化存储。数据只写在可写层里，容器一删就没了。需要跨容器生命周期保留的数据必须放进卷或绑定挂载，用法见第 7 章。

**速记**：**可写层一容器一层，随容器生、随容器灭**。



#### 联合挂载与自顶向下的查找

**联合挂载（Union Mount）**：把多个目录即多个层叠加成一个统一目录视图的机制，容器看到的根文件系统就是这个联合挂载的结果。

- 查找文件时自上而下逐层搜索：先看最上面的可写层，未命中再看下层镜像层，命中第一处即返回。
- 因此可写层里的同名文件会遮蔽（obscure）下层镜像层中的同名文件。
- 上层无法表达“下层没有的东西”，删除必须靠可写层里显式写入的记录来体现。
- 联合挂载对进程透明，容器内的程序只看到一个普通的根目录，感知不到分层。

> 自顶向下意味着“最近一次改动优先”。这解释了一个常见现象：容器里改了某个配置文件，行为立刻变化，但下面镜像层里的原文件其实一个字节都没动。

**速记**：联合挂载把多层叠成一个视图，查找**自上而下、命中即止**。



### 写时复制在运行期的具体行为

#### 读命中下层直接读

**读的行为**：读文件时先查可写层，未命中则沿镜像层自上而下查找，命中后直接读取，全程不产生任何复制。

- 镜像层在容器运行期始终以只读方式参与联合挂载，读操作不需要副本。
- 多个容器读同一镜像层的同一文件时，内核共享同一份页缓存，不会各存一份。
- 只读依赖使高密度场景的内存占用保持较低，这是 overlayfs 被广泛采用的原因之一。
- 读性能的代价主要在层数：层数越多，未命中可写层时的逐层查找路径越长。

> 页缓存共享只针对只读的镜像层内容。一旦某个容器把文件复制到自己的可写层并改写，那份副本就是该容器私有的，不再与其他容器共享。

**速记**：读走**自上而下的查找**，命中即读，镜像层的页缓存跨容器共享。



#### 写触发把文件复制到可写层

**写时复制（Copy-on-Write，CoW）**：第一次写入一个位于下层的文件时，内核先把整个文件复制到可写层，再在副本上执行修改。

- 复制发生在**文件级别**而非块级别，因此改动一个很大的文件里的一个字节，也要复制整个文件。
- copy-up 只在首次写入某个文件时发生，之后对该文件的写入都直接落在副本上，不会重复复制。
- 新建文件直接写进可写层，不涉及复制。
- 修改目录元数据同样可能触发复制，代价与文件大小和目录规模相关。
- 写密集的负载应改用卷，卷绕过存储驱动，不承担写时复制的开销。

> [!TIP]
> **建议内容**：容器内对镜像层既有文件的第一次写入会有一次复制延迟，对大文件尤其明显。写密集场景（数据库文件、频繁改写的日志）把目录挂到卷上，能把这份开销整体消掉。

**速记**：首次写触发 **copy-up**，整文件复制到可写层再改；新建文件不复制，写密集走卷。



#### 删除只打白障标记

**白障（Whiteout）**：删除只读镜像层中的文件时，下层文件本身无法删除（因为它只读），于是在可写层写一个白障标记，使其在联合视图中表现为已不存在。

- 删除文件：在可写层创建一个白障文件，下层原文件仍在磁盘上，只是被遮蔽。
- 删除目录：在可写层创建一个不透明目录（opaque directory），效果等同白障，阻止访问下层同名目录。
- 白障只影响该容器的联合视图，其他容器与镜像本身都不受影响。
- “改名”在联合文件系统里通常表现为一次删除加一次新建，因此同样会留下白障。
- 白障本身也占可写层空间，大量增删会让可写层比预期更大。

> [!NOTE]
> **提醒内容**：在容器里删掉镜像层中的大文件，并不会让镜像变小，也不会立刻释放宿主机磁盘。层是只读且内容寻址的，删除只在可写层留一个标记；真正释放空间要等相应层不再被任何镜像或容器引用。

**速记**：删除只写 **whiteout**，下层原文件不删；目录用不透明目录遮蔽，改名等于删加建。



#### 两个实务后果

**可写层的两条实务结论**：其一，可写层只在容器存活期有意义，容器删除即丢弃；其二，容器内的写入量决定可写层膨胀程度，进而决定磁盘占用。

- 后果一：任何写在可写层里的数据都不具备跨容器生命周期的价值，重建容器即归零。
- 后果二：日志、缓存、临时文件、数据库文件若都落在可写层，容器运行越久，可写层越大。
- 两个后果共同指向同一条处置：需要持久或大量写入的数据，一律挂载卷或绑定挂载。
- 排查磁盘异常时，docker diff 可看出可写层相对镜像层改动了哪些文件，docker ps -s 可看可写层大小。

```bash
docker ps -s                                    # SIZE 列含可写层大小
docker diff web                                 # 只列可写层的 A/C/D 改动
docker inspect -f '{{.GraphDriver.Data.UpperDir}}' web   # 经典驱动的可写层路径
```

> 反直觉之处在于：删容器不是“清理磁盘”的同义词，可写层被删只是不再占用它自己那部分空间，下面的镜像层仍可能被其他镜像与容器引用而继续保留。

**速记**：可写层**只活在容器生命周期内**，写入越多膨胀越大；持久与大量写一律走卷。



### 联合文件系统与 OverlayFS

#### lowerdir、upperdir、merged 与 workdir

**OverlayFS**：是 Linux 内核提供的一种联合文件系统驱动，通过叠加若干目录生成一个统一视图；Docker 把它用作容器根文件系统的实现基础。

- **lowerdir**：下层目录，对应只读的镜像层，可以指定多个，多个路径以冒号分隔。
- **upperdir**：上层目录，对应容器的可写层，所有运行期改动落在这一层。
- **merged**：统一视图目录，即容器实际使用的挂载点，读它看到的是上下层合并后的结果。
- **workdir**：OverlayFS 内部使用的目录，不出现在合并视图中，必须与 upperdir 位于同一文件系统且为空目录。
- overlay2 驱动原生支持最多 128 个 lowerdir 层，层数上限与 inode 消耗都因此受控。

```bash
sudo mount -t overlay overlay \
  -o lowerdir=/lower1:/lower2,upperdir=/upper,workdir=/work \
  /merged
```

> 四个概念里只有 merged 是给进程看的视图，lowerdir、upperdir、workdir 都是实现细节。内核文档对 workdir 的内部用途未作具体规定，只要求它与 upperdir 同处一个文件系统。

**速记**：**lowerdir 只读镜像层、upperdir 可写容器层、merged 是视图、workdir 是内核内部目录**。



#### mount 命令与 /proc/mounts 里怎么看出用了 overlay

**观察方式**：容器的联合挂载在宿主机上以一处 overlay 类型的挂载出现，用 mount 或读 /proc/mounts 即可看出某个容器是否使用 overlay，以及它的四个目录分别指向哪里。

```bash
mount | grep overlay
cat /proc/mounts | grep overlay
```

```text
overlay on /var/lib/docker/rootfs/overlayfs/9f2c... type overlay (rw,relatime,
lowerdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/5/fs:
/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/4/fs,
upperdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/6/fs,
workdir=/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/6/work)
```

- 首行的挂载点是容器的合并根目录，能据此把挂载与某个容器对应起来。
- lowerdir 一段以冒号分隔，条数即该容器底下的只读层数，越靠前越靠近顶层。
- upperdir 一段指向该容器的可写层在磁盘上的位置。
- rw 表示该挂载可读写；若显示 ro，说明该视图被以只读方式挂载。

> [!NOTE]
> **提醒内容**：29.0 之后全新安装的引擎中，lowerdir 与 upperdir 都指向 /var/lib/containerd 下的快照目录，而挂载点位于 /var/lib/docker 下。同一台机器上镜像存储与运行时挂载已经分属两个存储路径，排查时不要只在 /var/lib/docker 里找层。

**速记**：**mount 加 grep overlay** 看四处路径，挂载点是容器根，lowerdir 数出现只读层数。



#### upperdir 在磁盘上的实际位置

**落盘位置**：upperdir 即容器可写层的物理位置，随存储后端不同而不同，29.0 是一个分界线。

- 29.0 之后（containerd 镜像存储）：可写层位于 /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/ 下的编号目录中。
- 29.0 之后：容器合并根位于 /var/lib/docker/rootfs/overlayfs/ 下的容器 ID 目录。
- 29.0 之前（overlay2 经典驱动）：可写层位于 /var/lib/docker/overlay2/ 下的层目录中，具体是其中的 diff 子目录。
- 29.0 之前：合并根位于同一层目录下的 merged 子目录，workdir 对应 work 子目录。

> [!WARNING]
> **警告内容**：不要手工改动 /var/lib/docker 或 /var/lib/containerd 下的任何文件与目录。这些内容由 Docker 与 containerd 管理，直接增删会造成元数据与磁盘数据不一致，轻则镜像损坏，重则引擎无法启动。

**速记**：29.0 后 upperdir 在 **/var/lib/containerd 的快照目录**、合并根在 **/var/lib/docker/rootfs/overlayfs**；29.0 前都在 **/var/lib/docker/overlay2** 下。



### 存储驱动的演进脉络

#### 早期候选：aufs 与 devicemapper

**aufs**：是早期 Docker 默认使用的联合文件系统实现，长期未进入 Linux 主线内核，依赖发行版自行打补丁，在 Docker Engine v19.03 被弃用、v24.0 被移除。**devicemapper**：是基于设备映射与精简置备的块级驱动，在 v18.09 弃用、v23.0 默认关闭、v25.0 移除。

- aufs 的价值在于让不支持 OverlayFS 的老发行版也能跑 Docker，代价是内核支持不稳、inode 消耗大。
- devicemapper 面向更老的内核，配置繁琐，默认的 loop-lvm 模式性能与稳定性都欠佳。
- 两者被移除的共同原因是：受支持的发行版都已能运行 overlay2，继续维护的收益不足。
- 早期还有 legacy overlay 驱动，因 inode 消耗过多被 overlay2 取代，同样在 v24.0 移除。

> 这些驱动现在都无法在 29.x 上启用，遇到旧资料里“换 aufs 或 devicemapper 试试”的建议可直接忽略。现行可选集只剩 containerd snapshotter、overlay2、fuse-overlayfs、btrfs、zfs 与 vfs。

**速记**：**aufs 与 legacy overlay 止于 v24.0，devicemapper 止于 v25.0**，均为 overlay2 让路。



#### 块级驱动：btrfs 与 zfs

**btrfs 与 zfs**：是兼具文件系统与卷管理能力的块级存储方案，Docker 为其提供了对应驱动，前提是宿主机的数据目录本身就跑在该文件系统上。

- 块级驱动工作在块级别，对写密集负载的性能通常优于文件级的 overlay2。
- 两者都支持快照等高级能力，便于做层与卷的快速复制。
- 代价是运维复杂度与内存开销都明显更高，官方文档明确提到它们需要大量内存。
- 选用前提苛刻：btrfs 驱动只在宿主机以 btrfs 为存储时可用，zfs 驱动同理依赖 zfs。
- 需要精细化的卷特性时它们仍有价值，但通用场景并不划算。

> [!NOTE]
> **提醒内容**：块级驱动对写密集负载更友好，但官方文档同时指出，对写密集负载更好的做法仍是使用卷，而不是把数据写进容器可写层。驱动选型改变的是层的实现，改变不了可写层不宜承载数据这一结论。

**速记**：**btrfs 与 zfs 属块级驱动**，写密集性能好、支持快照，但吃内存、运维重、依赖对应文件系统。



#### overlay2 为何成为长期默认

**overlay2 的胜出理由**：它在受支持的所有 Linux 发行版上开箱可用，无需额外的文件系统配置，性能与稳定性在经典驱动中最好，因此长期作为默认并被写进多数发行版。

- 兼容面最广：主流发行版的默认经典驱动都是 overlay2。
- 无需改造磁盘：不像 btrfs、zfs 那样要求宿主机改用特定文件系统。
- 内存效率好：只读层页缓存可跨容器共享，适合高密度场景。
- 实现简单：文件级写时复制，逻辑直观，出问题时易于定位。
- 稳定性最高：官方文档称 overlay2 在经典驱动中提供最高的稳定性。

> [!IMPORTANT]
> **重要内容**：按 docs.docker.com 的存储驱动文档，overlay2 自 Docker Engine 29.0 起已被定位为遗留存储驱动，由 containerd 的 overlayfs snapshotter 取代。这里的“默认”指的是全新安装之前的长期默认，29.x 全新安装的默认后端已是 containerd 镜像存储。

**速记**：overlay2 靠**广泛兼容、无需改盘、内存高效、稳定**成为长期默认，29.0 起转为遗留。



#### 各驱动对内核与文件系统的前提要求

**前提差异**：不同存储驱动对内核版本与后备文件系统的要求不同，选型前必须先确认宿主环境是否满足。

- overlay2：Linux 内核 4.0 及以上；RHEL 或 CentOS 需内核 3.10.0-514 及以上。
- overlay2 的后备文件系统：xfs 必须启用 d_type，即 ftype=1；ext4、btrfs 等亦可。
- fuse-overlayfs：任意文件系统都可，官方仅推荐用于 rootless 且宿主机不支持 rootless overlay2 的场景。
- btrfs 驱动：要求后备文件系统是 btrfs；zfs 驱动：要求后备文件系统是 zfs。
- vfs：对文件系统无特殊要求，但不支持写时复制，每层都完整复制，性能差，仅用于测试。
- Windows 主机上唯一受支持的驱动是 windowsfilter，上述 Linux 驱动均不适用。

```bash
docker info
# 关注三行：Storage Driver、Backing Filesystem、Supports d_type
xfs_info /var/lib/docker | grep ftype      # xfs 后备文件系统须为 ftype=1
```

> “后备文件系统”指的是数据目录 /var/lib/docker 所在的那个文件系统，不是镜像里的文件系统。选驱动时先看这个文件系统是什么、内核版本够不够，再看负载特性。

**速记**：**overlay2 要内核 4.0 以上、xfs 须 ftype=1**；btrfs 与 zfs 各自依赖同名文件系统，vfs 仅测试用。



### containerd 镜像存储（snapshotter）

#### 29.0 起的默认后端与切换方式

**containerd 镜像存储**：是以 containerd 的 snapshotter 为后端、取代 Docker 自研 graph driver 的镜像与容器存储机制，从 Docker Engine 29.0 起成为全新安装的默认存储后端。

- 只有全新安装才默认启用；从旧版升级的机器继续沿用原 graph driver，需手动切换。
- 启用方式是向 /etc/docker/daemon.json 加入 features.containerd-snapshotter 为 true，然后重启守护进程。
- 验证方式是 docker info -f '{{ .DriverStatus }}'，输出 [[driver-type io.containerd.snapshotter.v1]] 即表示已启用。
- Docker Engine 默认使用的 snapshotter 是 overlayfs，对应 docker info 里 Storage Driver 显示为 overlayfs。
- 切换存储后端会临时隐藏另一个后端创建的镜像与容器：数据仍在磁盘上，切回原配置即可重新看到。

```json
{
  "features": {
    "containerd-snapshotter": true
  }
}
```

```bash
sudo systemctl restart docker
docker info -f '{{ .DriverStatus }}'
docker info | grep "Storage Driver"
```

> [!CAUTION]
> **注意内容**：切换存储后端不是无损迁移。旧后端已拉取的镜像与新后端互不可见，若要让新后端用上既有镜像，须先推送到镜像仓库，或用 docker save 导出后再导入。动手前先备份，不要在有生产容器时直接切换。

**速记**：**29.0 全新安装默认 containerd 镜像存储**，升级机须手动开 features.containerd-snapshotter，切换会互相隐藏数据。



#### snapshotter 与 graph driver 的关系

**snapshotter**：是 containerd 中负责把镜像层与容器可写层落实为文件系统快照的组件，作用与 Docker 经典架构里的 graph driver 相对应，但不是同一套实现。

- 职责对齐：两者都回答“层在磁盘上如何存储与访问”，都向运行时提供可用的根文件系统。
- 实现归属不同：graph driver 是 Docker 自研并长期维护的一套驱动，snapshotter 属于 containerd 生态。
- 演进结果是 Docker 不再维护自己的一套驱动，改用 containerd 的 snapshotter，Docker 与 Kubernetes 因此可共用同一套镜像存储。
- containerd 支持可插拔 snapshotter，overlayfs 是默认实现，另有 btrfs、zfs 等可选实现。
- 对普通用户而言切换是透明的：存储后端变了，命令与工作流不变。

> 区分两个词：**OverlayFS 是 Linux 内核驱动**，**overlayfs 是 containerd 的 snapshotter 名称**，**overlay2 是 Docker 的经典 graph driver**。三者名字相近，讲义与报错里常混用，读到时要先确认指的是哪一层。

**速记**：snapshotter **对应 graph driver 的职责但归属 containerd**；Docker 不再自研驱动，overlayfs 是默认 snapshotter。



#### 带来的能力差异

**能力增量**：containerd 镜像存储不只是换了一条落盘路径，它还解锁了经典驱动在架构上无法支持的四类能力。

- **本地多平台镜像**：可直接在本地构建并保存多平台（如 amd64 与 arm64）镜像；经典驱动需要外部构建器。
- **带 attestation 的镜像**：可处理包含来源证明与 SBOM 等证明材料的镜像，这类镜像使用镜像索引（image index），经典存储不支持。
- **Wasm 容器**：支持 WebAssembly 工作负载。
- **高级 snapshotter**：可插拔的 snapshotter 带来镜像懒加载（lazy pulling，如 stargz）与点对点镜像分发（如 nydus、dragonfly）等能力。

> [!TIP]
> **建议内容**：需要构建多平台镜像、或在镜像里附带 SBOM 与来源证明时，先确认存储后端是不是 containerd 镜像存储。经典驱动下这些能力不是配错了参数，而是架构上就不成立。多平台构建的用法见第 6 章。

**速记**：四类增量——**本地多平台、attestation、Wasm、可插拔 snapshotter**。



#### 已知限制与磁盘代价

**两项已知代价**：containerd 镜像存储与 userns-remap 不能同时启用，且相同镜像会占用比经典驱动更多的磁盘。

- 限制一：使用用户命名空间重映射（userns-remap）时该存储不可用，官方以 moby 仓库 issue 47377 记录该限制。
- 代价二：containerd 同时保留压缩层与解压层。拉取镜像时保留从仓库收到的压缩层，又把它们解压到磁盘，同一层占两份空间。
- 双份存储换来的是更快的 push 与 pull；经典驱动只存解压后的层，因此磁盘占用更小。
- 存储路径与 Docker 数据目录分离：为 Docker 配置的自定义 data-root 不会自动搬移 containerd 的存储，必要时须单独配置 containerd 的数据目录。
- 缓解手段是定期 docker image prune 清理无用镜像，并用 docker system df 监控占用。

> [!WARNING]
> **警告内容**：把 data-root 改到大分区后，containerd 镜像存储仍可能写在根分区的 /var/lib/containerd 下，根分区被写满却找不到是哪来的大文件。启用 containerd 镜像存储时，要同时确认 containerd 的数据目录也在容量足够的分区上。

**速记**：**与 userns-remap 互斥**；**压缩层加解压层双份存盘**，磁盘更费，data-root 不搬 containerd。



### 两种后端的磁盘路径对照

#### 29.0 之后的镜像层与内容存储

**29.0 之后的镜像层路径**：全新安装默认使用 containerd 镜像存储，层的快照数据落在 /var/lib/containerd 下，与 Docker 的数据目录分家。

- 快照目录：/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/，其 snapshots 子目录下按编号存放，快照内容在编号目录的 fs 子目录里。
- 内容目录：/var/lib/containerd/io.containerd.content.v1.content/，存放按内容寻址的层数据，含从仓库收到的压缩层。
- 镜像层在这里不再以“每层一个可读目录”的形式直接铺开，而是表现为编号快照加上一份内容存储。
- 因此 29.0 之后在 /var/lib/docker 下找层目录会一无所获，这是路径分家带来的最常见困惑。

```bash
sudo ls /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/
sudo du -sh /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/
sudo du -sh /var/lib/containerd/io.containerd.content.v1.content/
```

> 快照编号与镜像层摘要不是一回事。快照目录的数字是 containerd 分配的序号，要把它对应回具体镜像与层，得用 ctr 或 nerdctl 查询，而不能靠肉眼比对目录名。

**速记**：29.0 后层在 **/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/**，内容在 **io.containerd.content.v1.content/**。



#### 29.0 之后的容器合并根

**合并根路径**：29.0 之后，容器运行时的合并文件系统仍挂在 Docker 的数据目录下，位于 /var/lib/docker/rootfs/overlayfs/。

- 每个运行中的容器在 /var/lib/docker/rootfs/overlayfs/ 下有一个以容器 ID 命名的目录，即该容器的挂载点。
- 镜像存储与运行时挂载因此分属两处：层在 /var/lib/containerd，视图在 /var/lib/docker/rootfs/overlayfs。
- 这一点与经典驱动不同：经典驱动下层的 diff、可写的可写层与合并视图都在 /var/lib/docker/overlay2 的同一个层目录里。
- 容器停止后该挂载点消失，再次启动会重新挂载。

```bash
docker inspect -f '{{.GraphDriver.Data.MergedDir}}' web   # 部分环境可能为空
mount | grep rootfs/overlayfs
df -Th | grep overlay | grep rootfs
```

> 在 29.0 之后的引擎里，GraphDriver 字段的可用性会随存储后端而变。判断挂载点更可靠的办法是看 inspect 的 Mounts 与宿主机上的 overlay 挂载，而不是只依赖 GraphDriver.Data。

**速记**：29.0 后容器合并根在 **/var/lib/docker/rootfs/overlayfs/容器ID**，与 /var/lib/containerd 里的层分离。



#### 29.0 之前的 overlay2 与 image 元数据

**经典布局**：29.0 之前，镜像层与其元数据都集中在 Docker 数据目录下，overlay2 驱动以每层一个目录的形式铺开。

- 层与容器目录：/var/lib/docker/overlay2/ 下每个层或容器一个目录，内含 diff、merged、work 等子目录。
- diff 子目录即该层的内容，merged 是合并视图，work 供 OverlayFS 内部使用。
- l 子目录存放缩短后的层标识符符号链接，用于规避 mount 参数的长度限制。
- 镜像元数据：/var/lib/docker/image/ 下按驱动存放镜像与层的元信息，含 layerdb。
- 最底层目录只有 link 文件与 diff 目录，更高层则同时含 lower、diff、merged、work。

```bash
sudo ls /var/lib/docker/overlay2/ | head
sudo ls /var/lib/docker/overlay2/l/ | head
sudo du -sh /var/lib/docker/overlay2/
sudo ls /var/lib/docker/image/overlay2/
```

> 镜像层 ID 与 overlay2 的目录 ID 并不对应，官方文档明确指出这一点。想按层摘要找到目录，要靠 docker image inspect 的 GraphDriver 字段，而不是把摘要当目录名去拼。

**速记**：29.0 前层在 **/var/lib/docker/overlay2/**（每层一个目录、含 diff 与 merged），元数据在 **/var/lib/docker/image/**。



#### 可执行的查看命令

**查看命令**：判断当前用的是哪种后端、层落在哪、各占多少空间，有一组固定命令可以照抄。

```bash
# 当前存储驱动与后备文件系统
docker info | grep -E "Storage Driver|Backing Filesystem|Cgroup"

# 是否启用了 containerd 镜像存储
docker info -f '{{ .DriverStatus }}'

# 容器的 overlay 挂载与四个目录
mount | grep overlay
cat /proc/mounts | grep overlay

# 两处存储目录的体积
sudo du -sh /var/lib/docker/overlay2 2>/dev/null
sudo du -sh /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs 2>/dev/null

# containerd 侧直查快照与镜像
sudo ctr -n moby snapshots ls | head
sudo ctr -n moby images ls | head

# 单个容器的存储相关字段
docker inspect -f '{{json .GraphDriver}}' web
docker ps -s
```

- docker info 的 Storage Driver 在经典驱动下显示 overlay2，在 containerd 镜像存储下显示 overlayfs。
- du 的两条命令按环境二选一，不存在的路径可忽略。
- ctr 需要在 containerd 的 moby 命名空间下操作，见本篇末节的工具说明。

> [!TIP]
> **建议内容**：把 docker info 里 Storage Driver、Backing Filesystem、Cgroup Version 三行与 du 的两条命令记成一套巡检动作。磁盘异常时先确认用的是哪种后端，再看层目录体积，能省去大量猜测。

**速记**：**docker info 看后端、mount 看四处目录、du 看体积、ctr 看快照**。



### 层共享与磁盘账本

#### 相同基础层不重复占用

**层共享**：多个镜像若基于同一基础镜像，其底部的公共层在磁盘上只存一份，镜像之间通过引用同一批层来复用。

- 两个基于 alpine 的镜像各自只有自己新增的层是独立的，alpine 的基础层共用一份。
- 同一镜像启动的多个容器共用全部镜像层，只有各自的可写层不同。
- overlay2 还会在层目录之间使用硬链接共享数据，进一步减少物理占用。
- 共享带来的直接推论：镜像的“大小”不能简单相加，多个镜像的合计占用通常小于各自大小之和。

```bash
docker system df -v            # 关注 SHARED SIZE 与 UNIQUE SIZE 两列
```

> docker system df -v 对镜像给出的 SIZE 等于 SHARED SIZE 加 UNIQUE SIZE：前者是与他镜像共享的层，后者是本镜像独有的层。看“删掉它能省多少”要看 UNIQUE SIZE，而不是 SIZE。

**速记**：**公共基础层只存一份**，容器共用镜像层、只各自拥有可写层；镜像合计占用小于大小之和。



#### 引用计数与删镜像不删层

**引用计数**：层是否占着磁盘，取决于还有没有被镜像或容器引用；删掉一个镜像只是减少引用，未必释放空间。

- docker rmi 删除的是镜像与它的标签；若该镜像的层仍被其他镜像或容器引用，磁盘空间不释放。
- 一个镜像有多个标签时，删掉其中一个标签只是减少一个引用，镜像本体可能仍在。
- 镜像正被容器引用时不能直接删除，须先删容器或用 -f 强制。
- 用 -f 强制删除也只是解除引用，底层仍有其他引用时不释放空间。
- 释放空间的真正时机是最后一个引用消失，此时对应层才会被回收。

> [!NOTE]
> **提醒内容**：删了镜像但磁盘没变小，多半是层还被其他镜像或容器引用着，不是删除失败。用 docker system df 观察 RECLAIMABLE 是否下降，比反复执行 rmi 更能看清实际效果。

**速记**：**层按引用计存**，删镜像只是减引用；最后一个引用消失才真正释放空间。



#### docker system df 的输出怎么读

**docker system df**：汇总镜像、容器、本地卷与构建缓存各自占用的磁盘空间，是清理前的第一步侦察，只统计不删除。

- 第一列 **TYPE**：资源类型，取值为 Images、Containers、Local Volumes、Build Cache。
- 第二列 **TOTAL**：该类型的对象总数。
- 第三列 **ACTIVE**：其中正在被使用的对象数，如被容器引用的镜像数。
- 第四列 **SIZE**：该类型占用的磁盘总大小。
- 第五列 **RECLAIMABLE**：其中可以回收的空间，并给出可回收比例。

```bash
docker system df
docker system df -v            # 展开到每个镜像、容器、卷的明细
```

```text
TYPE            TOTAL   ACTIVE   SIZE        RECLAIMABLE
Images          5       2        16.43MB     11.63MB (70%)
Containers      2       0        212B        212B (100%)
Local Volumes   2       1        36B         0B (0%)
```

- TYPE 之外共四列数值：TOTAL、ACTIVE、SIZE、RECLAIMABLE。
- -v 或 --verbose 展开明细，镜像部分多出 SHARED SIZE 与 UNIQUE SIZE 两列。
- RECLAIMABLE 只表示“理论可回收”，实际能回收多少取决于清理后是否还有引用。

> [!CAUTION]
> **注意内容**：启用 containerd 镜像存储时，同一批镜像的 SIZE 与 RECLAIMABLE 会比经典驱动读起来大，因为压缩层与解压层都计入占用。看到数字变大先确认后端，不要误判为镜像被重复拉取。

**速记**：**TYPE 之外四列——TOTAL 总数、ACTIVE 在用、SIZE 占用、RECLAIMABLE 可回收**；-v 展开看共享与独占。



#### 悬空镜像的产生与清理

**悬空镜像（dangling image）**：指没有标签、也没有被任何容器引用的镜像，在 docker images 里显示为 none 加 none。

- 典型成因是用同一标签反复构建或重新拉取：新镜像占用了标签，旧镜像失去标签，成为无标签的悬空镜像。
- 判定条件是“无标签且无容器引用”，只有无标签但被容器使用的镜像不算悬空。
- 清理命令是 docker image prune，默认只删悬空镜像，是相对温和的一档。
- docker image prune -a 会删除所有未被容器使用的镜像，包括手工拉下来待用的基础镜像。
- 清理前可加 --filter until= 限定时间，避免误删刚拉取的镜像。

```bash
docker images --filter dangling=true            # 先看有哪些悬空镜像
docker image prune                              # 只清悬空
docker image prune -a --filter "until=168h"     # 只清一周前且未被使用的
```

> [!CAUTION]
> **注意内容**：docker image prune -a 的删除范围包含手工拉取但尚未使用的镜像，删掉之后必须重新拉取。执行前用 docker images 与 docker system df 确认范围，或用 --filter 限定时间。

**速记**：悬空镜像即 **none 加 none、无标签无引用**，由重复构建或重拉产生；prune 默认只清悬空，加 -a 清全部未用镜像。



### 观察层的工具与方法

#### docker history 的 CREATED BY 与 SIZE

**docker history**：按层列出镜像的构建历史，是定位“哪一层把体积撑大”的第一入口。

- 每行对应一层，输出含 IMAGE、CREATED、CREATED BY、SIZE 四列。
- **CREATED BY** 列显示产出该层的指令，默认会被截断，加 --no-trunc 显示完整命令。
- **SIZE** 列显示该层自身贡献的大小，注意是增量而非累计。
- 用 --format 可只取关心的列，便于脚本处理或排序。
- 一个镜像最上面的几行常是 CMD、ENTRYPOINT 等，它们不改文件系统，SIZE 显示为 0B。

```bash
docker history nginx:1.27
docker history --no-trunc nginx:1.27
docker history --format "{{.Size}}\t{{.CreatedBy}}" nginx:1.27 | head
```

```text
IMAGE          CREATED       CREATED BY                                      SIZE
a1b2c3d4e5f6   2 weeks ago   /bin/sh -c #(nop) CMD ["nginx" "-g" "daemon...   0B
b2c3d4e5f6a1   2 weeks ago   /bin/sh -c apt-get update && apt-get install...  42.1MB
```

> CREATED BY 里带 #(nop) 前缀的行是“空操作”指令，即只写元数据、不改文件系统的指令。看到它配合 0B 的 SIZE，就能判断该层不占空间，排查体积时应跳过这类行。

**速记**：history 一行一层，**CREATED BY 是指令、SIZE 是该层增量**；加 --no-trunc 看完整命令。



#### 为什么有些层显示 0B

**0B 的成因**：SIZE 为 0B 的层是只写元数据、不改变文件系统的指令所产生的层记录，不携带任何文件内容。

- 常见来源：ENV、CMD、ENTRYPOINT、LABEL、WORKDIR、EXPOSE、USER、VOLUME 等指令。
- 这些指令改变的是镜像配置，而非根文件系统，因此没有文件差异可继承。
- 它们仍会出现在构建历史里，因为历史记录的是指令序列，不等于磁盘上的内容层。
- 排查体积时忽略 0B 行，把注意力放在有非零 SIZE 的 RUN、COPY、ADD 上。
- 一次在 RUN 里装完并清缓存，比拆成多条 RUN 更省层数，也更容易看出体积来源。

> [!NOTE]
> **提醒内容**：SIZE 显示 0B 不代表这行指令“没生效”。它可能恰恰设定了容器最终的启动命令或环境变量，只是这些内容不占文件系统空间。判断是否生效要看 docker image inspect 的 Config 字段。

**速记**：**0B 层来自只写元数据的指令**（ENV、CMD、LABEL、WORKDIR 等），看体积时跳过，判断是否生效看 Config。



#### docker image inspect 的 RootFS 与 GraphDriver

**两个关键字段**：docker image inspect 的 RootFS.Layers 列出镜像全部层的摘要，GraphDriver 描述该镜像在存储驱动侧的目录信息。

- RootFS.Layers 是一个摘要数组，按自底向上的顺序列出每个层的内容摘要。
- 数组长度即该镜像的层数，可据此与 docker history 的行数对照。
- GraphDriver.Name 是实际使用的驱动名，经典驱动下为 overlay2，containerd 镜像存储下可能表现为 overlayfs 或字段内容不同。
- GraphDriver.Data 含 LowerDir、MergedDir、UpperDir、WorkDir 等路径，是经典驱动下定位层的直接依据。
- GraphDriver.Data 的具体字段随后端而变，29.0 之后不应假定它一定给出与经典驱动相同的键。

```bash
docker image inspect nginx:1.27
docker image inspect -f '{{json .RootFS.Layers}}' nginx:1.27
docker image inspect -f '{{.GraphDriver.Name}}' nginx:1.27
docker image inspect -f '{{json .GraphDriver.Data}}' nginx:1.27
```

```json
{
  "RootFS": {
    "Type": "layers",
    "Layers": [
      "sha256:8a3b...",
      "sha256:4c5d..."
    ]
  }
}
```

> RootFS.Layers 里的是层的**内容摘要**，不是镜像 ID，也不是磁盘上的目录名。它只保证同一份内容得到同一个摘要，因此可用来判断两个镜像是否共用了某些层。

**速记**：**RootFS.Layers 列层摘要、GraphDriver 给驱动与目录**；摘要不等于镜像 ID，也不是目录名。



#### 第三方与 containerd 侧工具

**补充工具**：docker 自带命令之外，可用第三方工具逐层查看体积构成，也可用 containerd 侧命令在快照层面直接查询。

- **dive**：常用的镜像逐层分析工具，能交互式查看每层新增、修改、删除的文件与浪费空间，需自行安装。
- dive 的安装方式与版本以项目官方说明为准，本篇不写死安装命令。
- **ctr**：containerd 自带的命令行工具，须指定 moby 命名空间才能看到 Docker 的镜像与快照。
- ctr -n moby snapshots ls 列出快照，ctr -n moby images ls 列出镜像。
- **nerdctl**：面向 containerd 的 Docker 兼容 CLI，可在 containerd 命名空间下以更熟悉的方式查询。
- 这些工具都属只读观察，不要在引擎运行时用它们删除快照或镜像。

```bash
# dive 需自行安装，安装方式以项目官方说明为准
dive nginx:1.27

# containerd 侧只读查询
sudo ctr -n moby images ls
sudo ctr -n moby snapshots ls | head
```

> [!WARNING]
> **警告内容**：不要在 Docker 运行期间用 ctr 或类似工具删除镜像、快照或内容数据。Docker 与 containerd 的元数据需要保持一致，绕过 Docker 直接删 containerd 侧对象会造成状态错乱。清理一律走 docker image prune 等 Docker 命令。

**速记**：**dive 逐层看体积（自行安装）**，**ctr -n moby 与 nerdctl 在 containerd 侧只读查询**。



### 层与构建缓存的关系

#### 层一旦生成即按内容寻址

**内容寻址**：层以内容摘要为标识，摘要由层内容计算得到，相同内容必定产生相同摘要，这是层能够跨镜像复用的前提。

- 层的摘要与实际内容一一对应，内容不变摘要不变，内容一变摘要随之改变。
- 按内容寻址意味着存储系统不需要知道层来自哪个镜像，只按摘要比对与存取。
- 这也解释了为什么同一批层能在多个镜像、多个仓库之间被复用而不冲突。
- docker image inspect 的 RootFS.Layers 列出的就是这些内容摘要。

> 区分两个标识：**镜像摘要**标识整个镜像（含配置与层清单），**层摘要**只标识一层的内容。同一个基础层可以出现在很多镜像里，它们的镜像摘要各不相同，但该层的摘要相同。

**速记**：层按**内容摘要寻址**，内容相同摘要相同，这是跨镜像复用的根基。



#### 内容相同可跨镜像复用

**复用机制**：构建或拉取时，若某一层的内容摘要已存在于本地，直接复用已落盘的层，不重复下载也不重复占用空间。

- 拉取镜像时逐层比对摘要，已有层跳过或直接复用，只传缺失层。
- 两个镜像若共享一段构建过程，中间层可被两者共同引用，磁盘上只存一份。
- 复用是自动的，不需要显式声明，判定完全依据内容摘要。
- 这也是多阶段构建能省体积的底层原因之一：中间产物若不进入最终镜像，就不会成为被引用的层。

```bash
docker pull nginx:1.27
docker pull nginx:1.27-alpine      # 与上一镜像共享的层会显示 Already exists
```

```text
a1b2c3d4e5f6: Already exists
b2c3d4e5f6a1: Pull complete
```

> 输出里的 Already exists 就是层复用的直接证据：本地已有同摘要的层，不必重新下载。它同时也说明该层此刻只存一份，两个镜像共享它。

**速记**：摘要命中即**复用已有层**，拉取时显示 Already exists，磁盘只存一份。



#### 换顺序为何全量重建

**缓存失效的血缘关系**：构建缓存按“父层摘要加指令”匹配，父层一变，其后所有层都成了新层，于是从改动点往后全量重建。

- 每条产生层的指令都以上一层为父，缓存命中要求父层摘要与指令内容都一致。
- 把 Dockerfile 里靠前的指令改动一点，其后所有层的父链都变了，缓存全部失效。
- 这正是“先装依赖、后拷源码”这一排序的原因：源码经常变，依赖较少变，把易变的部分放后面能保住前面的缓存。
- 换顺序后即使命令文本完全没变，只要父层摘要变了，也一律重新执行。

> [!TIP]
> **建议内容**：把不常变、耗时长的步骤（装系统依赖、拉依赖包）排在 Dockerfile 靠前位置，把频繁变动的源码拷贝排在后面。这不是风格偏好，而是让缓存血缘断点尽量靠后的直接手段。排序细则见第 5、6 章。

**速记**：缓存按**父层摘要加指令**匹配，父层一变其后全废；**易变的往后放**以保住缓存。



#### 缓存规则的分工边界

**本篇只讲存储视角**：层一旦生成即按内容寻址、内容相同即可跨镜像复用，这是缓存能够成立的基础；缓存的具体命中规则、失效条件与调优手段留给后续章节。

- 本篇负责的结论：层是内容寻址的、可复用的，缓存复用的对象正是这些层。
- 第 5 章负责 Dockerfile 各指令如何生成层、缓存如何逐条命中。
- 第 6 章负责构建缓存的最佳实践，包括多阶段构建与缓存挂载。
- 构建缓存本身也占磁盘，由 docker builder prune 清理，其体积计入 docker system df。

> 一条容易混淆的地方：构建缓存中的层与最终镜像的层是同一类对象，都可被引用；缓存被清掉不等于镜像受损，只是下次构建要重新生成这些层。

**速记**：本篇给**存储底账**（层内容寻址可复用），**命中规则与调优看第 5、6 章**。



### 存储驱动与内核能力的联动

#### overlay2 的内核与文件系统前提

**内核前提**：overlay2 依赖内核的多下层 OverlayFS 支持，官方要求 Linux 内核 4.0 及以上，或 RHEL、CentOS 使用 3.10.0-514 及以上内核。

- 内核需支持多个 lowerdir，这是 overlay2 相对早期 legacy overlay 驱动的关键增量。
- 后备文件系统为 xfs 时，必须启用 d_type，即 ftype=1，否则 overlay2 不可用。
- 后备文件系统为 ext4、btrfs 等时通常无需额外设置，但仍以 docker info 的 Supports d_type 为准。
- rootless 模式下，内核 5.11 起 overlay2 可直接工作，不再需要 fuse-overlayfs 兜底。
- 检查方式：docker info 看 Storage Driver、Backing Filesystem、Supports d_type 三行。

```bash
docker info | grep -E "Storage Driver|Backing Filesystem|Supports d_type|Kernel Version"
xfs_info /var/lib/docker | grep ftype       # 应输出 ftype=1
uname -r                                    # 确认内核版本
```

> [!IMPORTANT]
> **重要内容**：xfs 未启用 ftype=1 时，overlay2 无法正常使用。这种 xfs 通常来自创建文件系统时漏掉 -n ftype=1，属于装机阶段就埋下的问题，升级 Docker 也解决不了，只能备份数据后重做文件系统。

**速记**：overlay2 要**内核 4.0 以上**（RHEL 系 3.10.0-514 以上），**xfs 必须 ftype=1**，rootless 要内核 5.11 起。



#### backing filesystem 的选择禁忌

**后备文件系统**：指数据目录 /var/lib/docker 所在的那个文件系统，它的类型与特性直接决定哪些存储驱动可用，错误选择会让引擎启动失败或行为异常。

- 首要禁忌是不要把数据目录放在 overlayfs 挂载之上，即“overlay 叠 overlay”。按内核文档，OverlayFS 作为上层所在的后备文件系统不受支持。
- 这类场景常见于“容器里再跑 Docker”的做法，若不额外配置数据目录，层会叠在容器的 overlay 根上，出现难以定位的报错。
- 官方文档指出，SAN、NAS、硬件 RAID 等共享存储可承载 Docker，但并未做紧密集成，需遵循对应文件系统的既有实践。
- 选驱动的顺序是：先看内核与后备文件系统支持哪些驱动，再按写密集程度与稳定性要求缩小范围。
- 写密集负载的通用建议不是换驱动，而是用卷，卷绕过存储驱动，不承担写时复制与层膨胀的开销。

> [!WARNING]
> **警告内容**：在容器内运行 Docker（Docker in Docker）时，若把 /var/lib/docker 落在容器的 overlay 根上，等于用 overlayfs 承载 overlayfs。必须为内层 Docker 单独准备一个非 overlay 的后备文件系统或数据目录，否则可能出现层损坏与随机失败。

**速记**：后备文件系统**不能是 overlayfs 本身**；共享存储按既有实践用；写密集改**用卷**而不是换驱动。



#### cgroup v1 与 v2 的辨析

**两者的关系**：cgroup 版本与存储驱动同属 docker info 呈现的环境画像，但二者互不决定：cgroup 管资源限制，存储驱动管层如何落盘。

- cgroup v1 与 v2 的差异影响 CPU、内存等资源限制的语义与层级组织，属资源约束话题，见第 13 章。
- 存储驱动的可用性由内核版本与后备文件系统决定，与 cgroup 版本无关。
- docker info 中 Cgroup Version 显示 1 或 2，Cgroup Driver 显示 cgroupfs 或 systemd，可与 Storage Driver 并列查看。
- 现代发行版多已默认 cgroup v2，这是内核与发行版演进的趋势，不是 Docker 的存储策略。
- 排障时不要把资源限制异常与层膨胀混为一谈：前者看 cgroup，后者看可写层与卷。

```bash
docker info | grep -E "Storage Driver|Cgroup Version|Cgroup Driver"
stat -fc %T /sys/fs/cgroup        # 输出 cgroup2fs 即 cgroup v2
```

> 常见误判是把“容器内存被限制”归因到存储驱动。这两件事走的完全是两套内核机制：资源限制看 cgroup，文件落盘看存储驱动与写时复制。

**速记**：**cgroup 管资源、存储驱动管落盘，二者互不决定**；docker info 里并列查看，别把两类问题混在一起。



#### 改 storage-driver 的风险

**变更风险**：修改 storage-driver 会让既有镜像与容器在新驱动下无法访问，因为它们的层是按旧驱动的格式与元数据落盘的，新驱动读不懂。

- 官方文档明确提示：更改存储驱动后，现有容器与镜像在本地系统上不可访问。
- 数据仍在磁盘上，把配置改回原驱动即可重新访问，不会立即丢失。
- 同样地，启用 containerd 镜像存储会隐藏 overlay2 的镜像与容器，切回后重新出现。
- 迁移的正确做法是先 docker save 导出镜像，或推送到镜像仓库，再在新驱动下导入。
- 这类变更应安排在维护窗口，并在变更前确认宿主机上所有数据目录都有备份。

```bash
# 变更前先导出需要保留的镜像
docker save nginx:1.27 -o nginx.tar
docker save -o all-images.tar $(docker images -q | sort -u)

# 变更后如需回滚，把 daemon.json 改回并重启
sudo systemctl restart docker
```

> [!CAUTION]
> **注意内容**：storage-driver 与 containerd-snapshotter 的切换都属于存储后端变更，不是无损迁移。备份镜像、确认可回滚、再动手；在有生产容器运行时直接改配置并重启，风险最高。

**速记**：改驱动后**旧镜像与容器不可访问**（数据仍在，改回可见）；迁移靠 **save 导出或推送仓库**，并在维护窗口操作。
