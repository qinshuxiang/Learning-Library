## 数据卷与数据持久化

### 三种挂载类型总览

#### 三种挂载类型的定位

**数据持久化**：指让数据存放到容器可写层之外的存储上，使容器被删除、重建、迁移后数据仍在。Docker 提供三种基本挂载类型：**volume（卷）**、**bind mount（绑定挂载）**、**tmpfs（内存文件系统）**，三者的差异集中在数据的存放位置与生命周期上。

- **volume（卷）**：由 Docker 守护进程管理、以名字寻址的存储，数据放在守护进程的数据目录里（Linux 默认安装下为 /var/lib/docker/volumes/），容器删除后卷与卷内数据继续存在。
- **bind mount（绑定挂载）**：把宿主机上一个已存在的路径直接映射到容器内路径，数据始终是宿主文件系统上的那一份，Docker 不复制也不托管。
- **tmpfs（内存文件系统）**：把一段挂在宿主机内存里的文件系统映射进容器，不写入任何磁盘，容器一停即消失。
- 三者共用同一套 --mount 语法，类型由 type 字段区分，取值分别是 volume、bind、tmpfs。
- 选型只需问三件事：数据要不要活过容器、宿主是否要直接读写同一份数据、数据能不能落在容器以外的存储上。

```bash
docker run -d --name db1 --mount type=volume,src=db-data,dst=/var/lib/mysql mysql:8
docker run -d --name db2 --mount type=bind,src=/srv/html,dst=/usr/share/nginx/html nginx:1.27
docker run -d --name cache --mount type=tmpfs,dst=/tmp/cache,tmpfs-size=67108864 redis:7-alpine
```

> 三种类型可用一句话分工：**volume** 管长住的数据，**bind mount** 管宿主与容器要看同一份的数据，**tmpfs** 管用完就忘的数据。篇 2 讲过容器应当无状态，篇 4 讲过可写层随容器消亡，本节正是承接这两点回答数据该放哪儿。

**速记**：volume 由 Docker 托管，bind mount 指向宿主路径，tmpfs 只活在内存。



#### 生命周期、可移植性与性能的成对差别

**生命周期**：volume 独立于容器，删容器不删卷；bind mount 的数据寿命取决于宿主路径本身，与容器无关；tmpfs 的数据寿命等于容器本次运行，停止即清空。三者在可移植性、性能与可见性上同样成对分化。

- **生命周期**：volume 比容器长；bind mount 由宿主路径决定，可长于也可短于容器；tmpfs 比容器短或等长，容器一停就没了。
- **可移植性**：volume 在命令里只出现卷名，换机器后需另行搬数据；bind mount 写死宿主机绝对路径，换一台机器路径往往不存在；tmpfs 无数据可搬。
- **性能**：Linux 上三者开销接近，都是本地文件系统；macOS 与 Windows 上 bind mount 要跨虚拟机边界，明显慢于 volume。
- **可见性**：bind mount 宿主机可直接打开查看；volume 内容在 Docker 的数据目录里，需借助 Docker 或提权访问；tmpfs 宿主看不到文件。
- **备份手段**：volume 官方指定用一次性容器打包成 tar；bind mount 直接拷贝宿主目录即可；tmpfs 无需备份。

```bash
docker volume inspect db-data          # volume：看 Mountpoint 找宿主路径
ls -l /srv/html                        # bind mount：宿主路径直接可见
docker exec cache ls /tmp/cache        # tmpfs：只能在容器内看到
```

> 可移植性与可控性是一对取舍：**volume** 换来跨平台一致的抽象，代价是数据藏在 Docker 目录里；**bind mount** 换来宿主直接可控，代价是绑死具体路径。开发机上这个取舍偏 bind mount，生产机上偏 volume。

**速记**：volume 活得比容器长、bind mount 绑死宿主路径、tmpfs 最短命；macOS 上 bind mount 最慢。



#### image 与 npipe 两种少见类型

**--mount 的 type 全集**：除 volume、bind、tmpfs 三种基本类型外，Docker 还支持 **image** 与 **npipe** 两种少见类型，它们不属于本篇的持久化主题，此处只作边界说明，避免把 type 的取值记成只有三种。

- **image**：把另一个镜像的文件系统只读地挂进容器，用于临时借用工具镜像或共享只读数据集，需 containerd 镜像存储支持，且没有对应的 -v 写法。
- **npipe**：Windows 上的命名管道挂载，把宿主的命名管道暴露给容器，属 Windows 容器场景。
- image 类型的源必须是本地已有镜像，Docker 不会为它自动拉取；挂载始终只读。
- npipe 仅 Windows 平台可用，Linux 上写出来直接报错。
- 记全 type 取值的意义在于排查报错时能分辨「类型名写错」与「类型不被当前平台支持」。

```bash
docker pull busybox:musl
docker run --rm --mount type=image,src=busybox:musl,dst=/dbg alpine:latest /dbg/bin/echo ok
```

> [!NOTE]
> **提醒内容**：image 挂载需守护进程使用 containerd 镜像存储，经典存储驱动下不可用；从 Engine 29.0 起全新安装默认即为 containerd 存储，从旧版升级的机器则可能仍是旧驱动。该类型只能写 --mount，不存在 -v 等价写法。

**速记**：type 全集是 volume、bind、tmpfs、image、npipe；本篇只展开前三种。



### 命名卷

#### 创建命名卷与匿名卷的区别

**命名卷（named volume）**：有明确名字、可被命令与配置按名字引用的卷。**匿名卷（anonymous volume）**：创建容器时未指定卷名，由守护进程随机生成一串唯一标识的卷，写命令时无法预先知道它的名字。

- 显式创建用 docker volume create 卷名，卷名在同一个守护进程内唯一。
- 命名卷的 -v 写法为 卷名:容器路径；匿名卷的 -v 写法只给容器路径，省略源。
- 命名卷可被多个容器按名字复用；匿名卷设计上不在容器间自动复用，要共享只能按随机 ID 挂载。
- 二者一旦创建都持久化，删容器不会自动删除，除非容器创建时带了 --rm，那时关联的匿名卷会被销毁。
- 因此匿名卷是隐式生成、难以寻址的一次性卷，命名卷是可寻址、可复用的正式资源。

```bash
docker volume create mysql-data                  # 显式创建命名卷
docker run -d --name db -v mysql-data:/var/lib/mysql mysql:8     # 命名卷
docker run -d --name cache -v /var/lib/redis redis:7-alpine       # 匿名卷
docker volume ls
```

```text
DRIVER    VOLUME NAME
local     mysql-data
local     3f8a1c2d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2
```

> [!CAUTION]
> **注意内容**：不带源路径的 -v 会生成匿名卷，容器删除后很难从名字上认出它属于谁，长期运行会积累大量悬空卷。需要长期保留的数据务必用命名卷，或至少在创建容器时记下匿名卷的随机名。

**速记**：给了名字是命名卷、省略源是匿名卷；--rm 会删匿名卷，命名卷两边都不碰。



#### 卷的默认存储位置

**卷的宿主存储位置**：在 Linux 以默认数据目录安装的 Engine 上，每个卷对应 /var/lib/docker/volumes/卷名/_data 这样一个目录，卷内文件实际就写在这里。该路径由卷子系统单独管理，与 Engine 29.0 起镜像层迁往 containerd 存储的改动无关。

- docker volume inspect 的输出里 Mountpoint 字段就是该卷的宿主目录，形如 /var/lib/docker/volumes/my-vol/_data。
- 目录属主通常是 root，非 root 用户要直接读需提权；这正是卷内容不便在宿主上直接翻看的原因。
- 卷名中的下划线与点等字符会原样出现在路径里；卷名不能含斜杠。
- Docker Desktop 下容器跑在虚拟机里，这个路径位于虚拟机内部的文件系统，宿主 macOS 或 Windows 上看不到。
- 想定期在宿主上直接备份或编辑卷内文件时，应改考虑 bind mount，而不是去动这个目录。

```bash
docker volume inspect mysql-data
```

```json
[
    {
        "Driver": "local",
        "Labels": {},
        "Mountpoint": "/var/lib/docker/volumes/mysql-data/_data",
        "Name": "mysql-data",
        "Options": {},
        "Scope": "local"
    }
]
```

> [!CAUTION]
> **注意内容**：直接改 /var/lib/docker/volumes 下的内容属于绕过 Docker 的带外操作，可能让卷的元数据与实际内容不一致。除紧急抢修外，读写卷数据一律通过挂载卷的容器进行，正规备份走临时容器加 tar。

**速记**：Linux 默认路径是 /var/lib/docker/volumes/卷名/_data，用 volume inspect 的 Mountpoint 确认。



#### 卷的生命周期独立于容器

**卷的生命周期**：卷是独立于容器的顶层对象，删容器只删除容器可写层与元数据，卷与卷内数据原样保留，直到显式删除卷本身。

- docker rm 只清掉容器；卷的删除是另一个独立步骤。
- 卷只有在执行 docker volume rm 或 docker volume prune 时才会消失。
- 容器重建后按同一个卷名挂回，数据仍在，这是「升级镜像、换配置但保留数据」的标准做法。
- 一个卷可以同时挂载到多个容器上，用于多进程共享同一份数据。
- 卷为空且挂到镜像里本来有内容的目录时，镜像中的内容会在首次挂载时被复制进卷；不想复制可在挂载时加 volume-nocopy。

```bash
docker run -d --name db -v mysql-data:/var/lib/mysql mysql:8
docker rm -f db                                    # 删容器，卷保留
docker volume ls                                   # mysql-data 仍在
docker run -d --name db2 -v mysql-data:/var/lib/mysql mysql:8   # 新容器沿用旧数据
```

```text
DRIVER    VOLUME NAME
local     mysql-data
```

> [!WARNING]
> **警告内容**：删容器不等于删数据，删卷才等于删数据。很多「数据消失」的故障并非容器被删，而是有人执行了 docker volume prune 或带 -v 的 down。删卷前的第一问应是：这份数据有没有备份、还有没有容器引用它。

**速记**：删容器不删卷、删卷才丢数据；一个卷可同时挂到多个容器。



#### 卷的查看、删除与批量清理

**卷的日常管理命令**：docker volume ls 列出卷，inspect 查看详情，rm 删除指定卷，prune 批量清理未被容器引用的卷。四者的破坏力依次递增，prune 尤其要看清楚默认范围。

- docker volume ls 列出全部卷；加 -q 只输出卷名，便于喂给管道；加 --filter dangling=true 只看悬空卷。
- docker volume inspect 卷名 给出 Mountpoint、Driver、Labels，排查「数据到底在哪」时必用。
- docker volume rm 卷名 删除指定卷，被容器引用时会报错；加 -f 可强制删除，但被运行中容器引用时删不掉。
- docker volume prune 默认只删未被容器引用的匿名卷；加 -a 才连未被引用的命名卷一起删，该标志需 API 1.42 及以上。
- docker system df 加 -v 可看到卷占用的空间与可回收量，是清理前的侦察手段。

```bash
docker volume ls
docker volume ls -q --filter dangling=true
docker volume inspect mysql-data
docker volume rm old-data
docker volume prune                    # 默认只清匿名卷
docker volume prune -a                 # 连未引用的命名卷一起清
```

```text
WARNING! This will remove anonymous local volumes not used by at least one container.
Are you sure you want to continue? [y/N]
```

> [!CAUTION]
> **注意内容**：docker volume prune -a 会删除未被容器引用的命名卷，而命名卷往往承载数据库数据。只要容器停了而卷留着，它就会被判定为未引用。执行前先用 docker volume ls 与 inspect 逐个确认对象，必要时加 --filter 限定范围。

**速记**：ls 查、inspect 看路径、rm 删指定、prune 默认只清匿名、加 -a 连命名卷一起清。



#### -v 短语法与 --mount 长语法

**-v（--volume）**：用冒号分隔源、目标与选项的三段式短语法，书写紧凑但把类型判断藏在写法里。**--mount**：用逗号分隔键值对的长语法，类型与每个选项都显式写出，官方推荐用于生产。

- -v 的格式为 源:目标:选项，三段顺序固定；省略源即为匿名卷，源以点或斜杠开头视为宿主路径即 bind mount，源是单纯名字视为命名卷。
- --mount 的格式为 type=类型,source=源,target=目标,选项，键值对顺序无关，可读性与自解释性更好。
- 长语法支持短语法表达不出的能力：volume-subpath 挂卷内子目录、volume-opt 传驱动选项、bind-propagation 设传播、bind-create-src 让源目录自动创建。
- 两种语法的挂载结果与数据行为完全一致，差别只在表达能力与书写可读性。
- 短语法的第三个字段可写 ro、volume-nocopy、z 等，但选项集比长语法小。

```bash
# 短语法：三段冒号，顺序固定
docker run -d --name web -v ./html:/usr/share/nginx/html:ro nginx:1.27

# 长语法：键值对，顺序随意，可读性更好
docker run -d --name web --mount type=bind,source=./html,target=/usr/share/nginx/html,readonly nginx:1.27

# 长语法独有能力：挂卷内子目录
docker run --rm --mount type=volume,src=mysql-data,dst=/sub,volume-subpath=backup alpine ls /sub
```

> 短语法没有 type 字段，靠「源是不是以点或斜杠开头」来猜类型，这在源写成相对路径或变量展开时最容易猜错；长语法把 type 写死，不存在猜的环节。凡是脚本与生产声明，优先长语法。

**速记**：-v 三段冒号顺序固定、--mount 键值对顺序随意且表达力更强，生产推荐长语法。



### 绑定挂载

#### 绑定挂载的写法与绝对路径要求

**绑定挂载的源路径**：bind mount 的源是宿主机上的一个绝对路径，写相对路径会被当成命名卷名而不是宿主目录，这是与卷最容易混淆的一处。

- 短语法写作 宿主绝对路径:容器路径:选项，如 -v /srv/app/conf:/etc/nginx/conf.d:ro。
- 长语法写作 type=bind,source=宿主绝对路径,target=容器路径。
- 想在命令里用当前目录，须显式展开为绝对路径，如 ${PWD} 或 $(pwd)，不能直接写点斜杠让 Docker 去解析。
- 容器内的目标路径也建议写绝对路径，省略绝对路径的容器侧写法在部分场景下含义不同。
- 挂载会把容器内目标路径原有的内容遮蔽，目标目录里镜像自带的东西在挂载期间不可见。

```bash
docker run -d --name web \
  -v /srv/app/html:/usr/share/nginx/html:ro \
  -v /srv/app/conf/default.conf:/etc/nginx/conf.d/default.conf:ro \
  nginx:1.27

docker run --rm --mount type=bind,source=/srv/app/html,target=/usr/share/nginx/html,readonly nginx:1.27
```

> [!WARNING]
> **警告内容**：把 bind mount 挂到容器内已有内容的关键目录上会遮蔽镜像原文。官方文档以 -v /tmp:/usr 为例，挂载后镜像的 /usr 被宿主 /tmp 覆盖，容器随即无法正常工作。挂载点应选在应用自己管理的目录，而不是系统目录。

**速记**：源必须是宿主绝对路径、相对路径会被当成卷名；挂载会遮蔽容器内目标目录的原内容。



#### 宿主机路径不存在时的行为差异

**源路径不存在时的行为**：-v 与 --mount 在这一情形下行为相反——**-v** 会自动在宿主机上创建缺失的目录，**--mount** 默认直接报错，这是两种语法在实战中最容易踩到的差异。

- -v 遇到源路径不存在时由守护进程自动创建，且无论意图如何都建成目录。
- --mount 遇到源路径不存在时报 bind source path does not exist 并终止启动。
- --mount 可加 bind-create-src 让它像 -v 一样自动创建源目录。
- 若守护进程没有创建该目录的权限，-v 也会失败，官方建议先手工把目录建好。
- 想绑定的是一个文件却写成 -v，而宿主上只有同名目录时，会得到「挂目录而非文件」的结果，往往引发后续报错。

```bash
docker run --mount type=bind,src=/dev/noexist,dst=/mnt/foo alpine
```

```text
docker: Error response from daemon: invalid mount config for type "bind":
bind source path does not exist: /dev/noexist.
```

```bash
# 显式让 --mount 自动创建源目录
docker run --rm --mount type=bind,src=/home/user/mydir,dst=/mnt/foo,bind-create-src alpine ls /mnt/foo
```

> [!IMPORTANT]
> **重要内容**：-v 自动建目录看似省事，实则容易掩盖路径拼写错误——本该存在的目录被静默建成空目录，容器照常启动却读不到数据。生产脚本里推荐用 --mount 让不存在的路径直接失败，把错误暴露在启动阶段。

**速记**：-v 自动建目录、--mount 默认报错、加 bind-create-src 才自动建。



#### 文件与目录都能绑定

**绑定粒度**：bind mount 的源既可以是目录，也可以是单个文件，这一点比命名卷更灵活——卷的挂载点是目录，bind mount 则能把宿主上的一个文件精确映射到容器内的一个文件。

- 绑文件用于替换单个配置：nginx.conf、应用配置文件、证书文件、时区文件。
- 绑目录用于整体替换：开发时的源码目录、静态资源目录、证书目录。
- 绑文件时源必须是已存在的文件；宿主上若只有同名目录，挂载会失败或得到非预期结果。
- bind mount 默认可写，容器对挂载内容的改动直接落到宿主文件上；加只读标记后容器不可写。
- 该特性适合开发期热更新：改宿主源码不需要重建镜像，进程重载或重启容器即可看到变化。

```bash
# 绑单个文件：只替换这一份配置
docker run -d --name web \
  -v /srv/app/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx:1.27

# 绑目录：整体替换静态资源，开发时改宿主即刻生效
docker run -d --name dev -v "$(pwd)/src":/app/src:ro node:24-alpine
```

> 绑文件与绑目录的差别不只是粒度：绑文件时容器内路径必须指向一个文件，宿主上删掉该文件后再重启容器会失败；绑目录则对目录内文件的增删不敏感。要整体切换多份配置，绑目录比逐个绑文件更省事。

**速记**：文件和目录都能绑；绑文件前先确认宿主上是文件而非目录，绑目录更适合批量替换。



### 权限与属主

#### 容器内 uid/gid 与宿主机文件的对应关系

**uid/gid 对齐**：容器与宿主机共用同一个内核，文件的属主以数字 uid 与 gid 记录，权限判定只看这串数字，不看用户名。容器内看到的用户名只是镜像里 /etc/passwd 的映射结果。

- 镜像里的 /etc/passwd 与宿主上的 /etc/passwd 是两份文件，同一个数字在两边的名字可能完全不同。
- 未启用 userns-remap 时，容器内 root 就是 uid 0，映射到宿主的 uid 0，对宿主文件拥有 root 权限。
- 容器内以 uid 1000 运行，写宿主目录时内核检查的是宿主该目录对 uid 1000 是否可写。
- 名字不同、数字相同即视为同一属主；因此容器内叫 app 的用户，可能正对应宿主上另一个名字的用户。
- 这正是「镜像里属主看着对、挂到宿主目录却写不进去」的根因：数字没对上。

```bash
docker run --rm -u 1000:1000 alpine id
```

```text
uid=1000 gid=1000 groups=1000
```

> 排查权限问题的第一步永远是 docker exec 容器 id 看到那串数字，再 ls -ln 宿主目录 看宿主目录属主的数字，两边一比即可定位错配点。名字对不上不要紧，数字对不上才是问题。

**速记**：权限认数字不认名字；容器内 uid 1000 就是宿主 uid 1000，userns-remap 例外。



#### root 与普通用户运行的写入失败现象

**写入失败的两类现象**：以 root 运行时，容器几乎能写任何宿主目录，反过来说明容器权限过大；以非 root 运行且宿主目录属主不匹配时，写入会直接报 Permission denied。

- 镜像未定义 USER 时容器以 root 运行，能写宿主目录，但这是安全隐患而非便利。
- 非 root 运行、宿主目录属其他 uid 时，写操作报 Permission denied 或 EACCES。
- 数据库镜像尤为典型：官方镜像内部以固定用户运行，把宿主空目录以 bind mount 挂到数据目录后，常因属主不匹配而启动失败。
- SELinux 系统上还有一类标签拒绝，表现为 Permission denied 但属主看起来是对的。
- 使用命名卷时由 Docker 处理卷目录属主，通常不会碰到这类问题。

```bash
docker run --rm -u 1000:1000 -v /srv/data:/data alpine sh -c "touch /data/x"
```

```text
touch: /data/x: Permission denied
```

```bash
# 数据库容器常见的启动失败
docker run -d --name db -v /srv/mysql:/var/lib/mysql mysql:8
docker logs db
```

```text
mysqld: Can't create/write to file '/var/lib/mysql/...' (Errcode: 13 - Permission denied)
```

> [!CAUTION]
> **注意内容**：以 root 运行能写通，不代表配置正确。生产容器应显式指定非 root 用户运行，但非 root 与 bind mount 的属主匹配必须同时安排，否则就会出现「为了安全改成非 root，结果容器起不来」的局面。

**速记**：root 写谁都行但危险，非 root 写宿主目录常报 Permission denied。



#### 权限问题的解决办法

**权限错配的五种解法**：按侵入性从低到高依次为指定运行身份、预先调整宿主属主、改用命名卷、调整目录权限或 gid、处理 SELinux 标签。优先选不削弱安全边界的那一种。

- **--user 指定身份**：用 -u UID:GID 让容器进程以与宿主目录属主相同的数字运行，最简单，前提是容器内进程能以该 uid 正常工作。
- **预先 chown**：挂载前把宿主目录属主改成容器进程的 uid:gid，适合目录内容由容器独占的场景。
- **改用命名卷**：把数据目录从 bind mount 换成命名卷，属主由 Docker 初始化，绕开宿主目录差异，是数据库类容器最省心的选择。
- **调整 gid 或 umask**：把容器进程加入目标 gid 组，或用 Engine 29.8.0 起新增的 --umask 控制新建文件的权限掩码。
- **SELinux 标签**：在挂载选项末尾加 z（多容器共享）或 Z（私有），让宿主文件带上容器可读的安全标签。

```bash
docker run -d --name db -u 1000:1000 -v /srv/mysql:/var/lib/mysql mysql:8

sudo chown -R 1000:1000 /srv/mysql

docker run -d --name db -v mysql-data:/var/lib/mysql mysql:8

docker run --rm --umask 0027 alpine sh -c "umask"

docker run -d --name web -v /srv/html:/usr/share/nginx/html:ro,z nginx:1.27
```

> [!WARNING]
> **警告内容**：权限报错时把宿主目录改成 777 是最常见的错误解法，它等于把这份数据暴露给机器上的任意用户，也把问题从「属主错配」变成「谁都能改」。正确顺序是先看容器进程的 uid，再定向调整宿主属主或改用命名卷。

**速记**：-u 对齐身份、chown 对齐属主、命名卷最省心、SELinux 用 z 与 Z。



### macOS 与 Windows 的文件 I/O 差异

#### 跨虚拟机边界的架构原因

**跨 VM 文件共享**：在 macOS 与 Windows 上，Linux 容器跑在一台由 Docker Desktop 启动的轻量虚拟机里，宿主机文件系统在虚拟机之外；bind mount 的每一次读写都要经文件共享层在宿主与虚拟机之间往返，因此明显慢于 Linux。

- Linux 上容器与宿主共用内核，bind mount 是同一内核内的路径映射，几乎没有额外开销。
- macOS 与 Windows 上容器在虚拟机内，宿主目录要先被共享进虚拟机，容器再挂载，链路多出「共享层」这一段。
- 大量小文件的读写会把这层往返开销逐次累积，延迟与 CPU 占用都明显上升；大文件顺序读写受影响较小。
- 命名卷落在虚拟机内部的文件系统上，不经过共享层，所以同一台机器上卷明显快于 bind mount。
- 官方文件共享说明指出，共享文件过多会导致高 CPU 负载与文件系统性能下降。

```bash
docker run --rm -v "$(pwd)":/app node:24-alpine sh -c "cd /app && time npm ci"
```

> 这不是 Docker 的缺陷，而是「Linux 容器必须跑在 Linux 内核上」这一前提在非 Linux 宿主上的必然结果。理解这点就不会把 bind mount 的慢当成 bug 去追，而会转而调整挂载策略。

> 还有一项跨平台差异值得一并记住：macOS 默认文件系统大小写不敏感，Linux 大小写敏感。同一份源码在 macOS 上能通过编译、进容器（Linux）后报找不到文件，多半是文件名大小写不一致，与文件共享性能无关。

**速记**：macOS 与 Windows 上容器在虚拟机里，bind mount 要跨边界，volume 在虚拟机内所以快。



#### 缓解手段

**缓解思路**：把不需要宿主直接读写的目录从 bind mount 挪到命名卷，只在必要的源码目录上保留 bind mount，再选对文件共享实现。官方对缓存目录与数据库给出的建议正是放进虚拟机内的卷。

- **依赖与缓存放卷**：node_modules、vendor、包缓存、数据库数据目录挂命名卷，只把源码目录用 bind mount 挂进来。
- **官方建议**：缓存目录、数据库这类非代码内容存放在虚拟机内的数据卷或数据容器里，性能会好得多。
- **选对文件共享实现**：Docker Desktop 现行默认使用 VirtioFS，官方称其把文件系统操作耗时最多降低约 98%，且是 Docker VMM 唯一支持的文件共享实现；旧的 gRPC FUSE 作为可选实现保留。
- **同步式共享**：Docker Desktop 的 Synchronized file shares 通过同步文件系统缓存增强 bind mount 性能，属需要订阅的能力。
- **开发期同步工具**：用 watch 类工具把源码同步进容器，容器内读到的是虚拟机内的副本，绕开共享层，代价是文件变更存在短暂延迟。
- **缩小共享范围**：只把必要目录加入文件共享列表，未列入的目录会报 Mounts denied 或服务启动失败。

```bash
# 依赖放卷、源码绑宿主，是 Node 项目在 macOS 上的常见组合
docker run -d --name api \
  -v node-modules:/app/node_modules \
  -v "$(pwd)/src":/app/src:ro \
  node:24-alpine
```

> [!TIP]
> **建议内容**：判断某个目录该用卷还是 bind mount，只问一句「宿主上的工具需要直接读它吗」。源码需要编辑器直接改，用 bind mount；依赖与缓存容器自己管，用命名卷。把这条落到每个目录上，macOS 上的性能问题基本可以被规避。

**速记**：依赖放卷、只绑源码、默认用 VirtioFS，必要时改用同步工具。



### tmpfs 与内存盘

#### 适用场景

**tmpfs 挂载**：把一段建立在宿主机内存里的文件系统挂进容器，数据不写入任何磁盘，容器停止时挂载被移除、文件不保留。它适合临时数据与敏感中间数据两类场景。

- 临时缓存：应用运行期生成的、丢了也无所谓的缓存与临时文件。
- 敏感中间数据：解密后的临时文件、一次性密钥、会话数据，避免明文落到磁盘上。
- 高写入低价值的非持久状态：频繁写、但不需留存的状态数据，放内存既快又省磁盘。
- 不适合需要持久化的数据，也不适合需要跨容器共享的数据，tmpfs 挂载不能在容器之间共享。
- 仅在 Linux 上运行 Docker 时可用，macOS 与 Windows 上的 Linux 容器虽在虚拟机里，该能力仍以 Linux 容器为准。

```bash
docker run -d --name cache --tmpfs /tmp/cache redis:7-alpine
docker exec cache sh -c "echo hi > /tmp/cache/a && ls /tmp/cache"
```

```text
a
```

> tmpfs 与卷、bind mount 的根本分野在于「落不落盘」：卷与 bind mount 都把数据写进文件系统，重启宿主仍在；tmpfs 只在内存里，宿主机断电或容器停止即消失。

**速记**：tmpfs 放内存、不落盘、容器停即清空，只 Linux 可用且不能容器间共享。



#### 大小限制与参数写法

**tmpfs 的两种写法与容量**：短写法 --tmpfs 用冒号接挂载选项，长写法 --mount 用 tmpfs-size 与 tmpfs-mode 两个键。不指定大小时，tmpfs 的默认最大容量是宿主机总内存的 50%。

- 短写法格式为 --tmpfs 容器路径:选项，如 --tmpfs /data:noexec,size=1024,mode=1777，选项用逗号分隔。
- 长写法格式为 --mount type=tmpfs,destination=路径,tmpfs-size=字节数,tmpfs-mode=八进制权限。
- tmpfs-size 以字节计，省略时默认为宿主总内存的一半；tmpfs-mode 默认 1777，即全局可写。
- tmpfs 没有 source，不能指定来源，这是它与卷和 bind mount 的语法差别之一。
- tmpfs 用量计入容器的内存 cgroup 限制，size 设得再大也不会突破 --memory 的上限，写满挂载可能导致容器 OOM。

```bash
docker run -d --name app \
  --tmpfs /data:noexec,size=1024,mode=1777 \
  redis:7-alpine

docker run -d --name app2 \
  --mount type=tmpfs,destination=/app,tmpfs-size=67108864,tmpfs-mode=1770 \
  redis:7-alpine
```

> [!WARNING]
> **警告内容**：tmpfs 占用的内存会计入容器内存限制。给容器设了 --memory 512m 又从 tmpfs 写入大量数据，可能触发 OOM Kill 而非「写满 tmpfs 报错」。限制内存敏感的容器时，tmpfs-size 之和必须放进内存预算里一起算。

**速记**：--tmpfs 用冒号、--mount 用 tmpfs-size 与 tmpfs-mode；默认上限是宿主内存的一半，用量算进容器内存。



### 只读挂载与其他挂载选项

#### :ro 只读挂载与配置只读惯例

**:ro 只读挂载**：在挂载选项里加 ro（长语法写作 readonly），使容器内无法写入该挂载点。把配置文件、证书、时区文件以只读方式挂进容器，是容器安全加固的固定惯例。

- 短语法写成 源:目标:ro；长语法写成 type=...,readonly，二者等价。
- 只读对 bind mount 与命名卷都适用：bind mount 默认可写，加 ro 后容器不能改宿主文件；卷同样可挂成只读。
- 容器内对被只读挂载的路径执行写操作会报 Read-only file system。
- 配置类挂载应一律只读：容器不需要改配置，只读能防止应用或攻击者篡改宿主上的配置与证书。
- 只读挂载同时也是「证明容器不写该目录」的手段，便于权限审计。

```bash
docker run -d --name web \
  -v /srv/conf/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /srv/conf/certs:/etc/nginx/certs:ro \
  nginx:1.27

docker run --rm --mount type=bind,src=/srv/conf,target=/conf,readonly alpine sh -c "echo x > /conf/a"
```

```text
sh: can't create /conf/a: Read-only file system
```

> [!TIP]
> **建议内容**：凡是不需要容器写入的挂载都加 ro，尤其是配置与证书目录。加与不加对容器功能通常没有影响，却能在应用被攻破时把可篡改的范围缩小一截，属于成本极低的加固动作。

**速记**：配置与证书类挂载一律加 ro；容器内写只读挂载报 Read-only file system。



#### 一致性选项 cached 与 delegated

**一致性标记**：consistent、cached、delegated 是 Docker Desktop 早期为宿主与虚拟机之间的文件共享引入的一致性档位，写在挂载选项第三个字段，用于在性能与一致性之间取舍。它们与 :ro 同处一个位置，但语义完全不同。

- **consistent**：宿主与容器看到的文件始终一致，最强也最慢，是历史默认档。
- **cached**：允许容器读到宿主改动时略有延迟，以宿主视图为准，读多写少的场景更快。
- **delegated**：以容器视图为准，宿主看到容器写入可延迟，容器大量写文件时更流畅。
- 三者都属于「放松一致性换性能」：cached 与 delegated 各自偏袒一端，只保证最终一致。
- 现行 Docker Desktop 默认使用 VirtioFS，官方设置页已不再列出这三个标记，写了通常被忽略；它们主要对应更早的 osxfs 与 gRPC FUSE 实现，具体是否生效以所装 Desktop 版本的官方说明为准。
- 不要把它们与 SELinux 的 z、Z 或只读的 ro 混写在同一位置，含义互不相干。

```bash
# 历史写法：在 gRPC FUSE 时代用于放宽一致性
docker run -d --name dev -v "$(pwd)/src":/app/src:cached node:24-alpine
```

> [!NOTE]
> **提醒内容**：一致性标记是否生效取决于 Desktop 的文件共享实现。在 VirtioFS 下不必依赖它们调性能，改用「依赖放卷、只绑源码」的策略更可靠；在旧实现上写 cached 或 delegated 才可能有实际效果。

**速记**：consistent 最严、cached 偏宿主观、delegated 偏容器观；VirtioFS 下已不再是官方列出的选项。



#### --mount 的 propagation 选项

**bind-propagation（挂载传播）**：控制一个挂载点上的子挂载是否向外传播到其他挂载点，仅对 bind mount 且仅在 Linux 宿主机上可配置，取值为 private、shared、slave、rprivate、rshared、rslave，默认 rprivate。

- private：挂载点的子挂载不向外传播，也不接收外部传播。
- shared：子挂载双向传播，原挂载点与其副本互相看到对方新增的子挂载。
- slave：类似 shared 但只单向传播，副本接收原挂载点的子挂载，反向不成立。
- 前缀 r 表示递归，作用于嵌套的挂载点，如 rshared 是 shared 的递归版本，rslave 同理。
- rprivate 是默认值，即两个方向都不传播；命名卷的传播固定为 rprivate 且不可配置。

```bash
docker run -d --name dev \
  --mount type=bind,source="$(pwd)"/target,target=/app \
  --mount type=bind,source="$(pwd)"/target,target=/app2,readonly,bind-propagation=rslave \
  nginx:1.27

# 短语法的传播选项写在第三个字段
docker run -d --name dev2 -v "$(pwd)"/target:/app2:ro,rslave nginx:1.27
```

> 大多数场景用默认的 rprivate 就够，只有在宿主上动态挂载新磁盘、又希望容器内自动看到时，才需要 shared 或 rshared。传播配置复杂且平台相关，不确定时保持默认，不要凭直觉设成 shared。

**速记**：propagation 只在 bind mount 与 Linux 上可调，默认 rprivate，r 前缀表示递归。



### volumes-from 与共享数据

#### --volumes-from 的作用与被弱化的原因

**--volumes-from**：让新容器复制另一个容器已声明的全部挂载（卷与 bind mount）的选项。它早期配合「数据容器」模式使用——起一个只声明卷、不跑业务的容器，其余容器用 --volumes-from 引用它，从而少写挂载参数。

- 用法是 docker run --volumes-from 源容器名 镜像，新容器获得源容器的整套挂载定义。
- 卷定义是被复制而非引用：源容器删除后，被复制过去的定义仍在引用它的容器上。
- 弱化的第一个原因是依赖隐式：读一个容器的命令看不出它挂了哪些目录，得回头看源容器。
- 弱化的第二个原因是不够精确：无法只共享其中某一个挂载，只能整组接收。
- 弱化的第三个原因是编排不友好：Compose 不直接支持这种写法，导到声明式配置时需要改写。
- 现行做法是直接按卷名挂载，显式、精确、无隐式依赖。

```bash
# 旧的数据容器模式
docker run -v /dbdata --name dbstore ubuntu /bin/bash
docker run --rm --volumes-from dbstore -v "$(pwd)":/backup ubuntu tar cvf /backup/backup.tar /dbdata

# 现行写法：直接按卷名挂
docker run --rm -v dbdata:/from:ro -v "$(pwd)":/to alpine sh -c "cd /from && tar czf /to/db.tgz ."
```

> --volumes-from 至今仍出现在官方文档的备份示例里，看到旧脚本不必惊慌；但新写的配置应改用按卷名直接挂载，尤其在 Compose 环境里，--volumes-from 没有对应字段，最终仍要落到命名卷上。

**速记**：--volumes-from 复制整组挂载、依赖隐式且无法精确选取，新配置改用按卷名直接挂。



#### 共享数据的推荐替代做法

**共享数据的三种正道**：同一命名卷挂到多个容器、在 Compose 中声明顶层卷供多服务引用、跨主机时改用外部存储服务。三者按数据是否需要跨主机依次升级。

- **同卷多挂**：同一个命名卷用 -v 卷名:路径 挂到多个容器，各自书写、语义清晰，是谁挂了什么一目了然。
- **Compose 顶层卷**：把卷写在顶层 volumes 段，多个 service 按同一卷名引用，写法集中且可复用。
- **只读共享**：只消费不生产的一方用 :ro 挂载，避免多写者互相覆盖。
- **跨主机共享**：本地卷不跨主机，多机共享数据必须改用对象存储、网络文件系统或数据库等外部服务。
- **生产数据库**：数据目录优先放宿主机卷或独立存储，再配合定期备份与恢复演练。

```bash
docker run -d --name writer -v shared:/data app:1.0
docker run -d --name reader -v shared:/data:ro app:1.0
```

```yaml
services:
  writer:
    image: app:1.0
    volumes:
      - shared:/data
  reader:
    image: app:1.0
    volumes:
      - shared:/data:ro

volumes:
  shared:
```

> [!WARNING]
> **警告内容**：让多个容器同时以可写方式挂载同一个宿主目录或同一个卷，会造成并发写冲突：两个进程各自以为文件归自己管，写坏的数据难以定位责任方。要共享就读写分离，写方独占，其余一律 :ro。

**速记**：同卷多挂或 Compose 顶层卷，跨主机必须用外部存储，共享时写方独占、他方只读。



### 数据备份与恢复

#### 用一次性容器把卷打包为 tar

**卷备份套路**：起一个一次性容器，同时挂上待备份的卷与一个宿主目录，在容器内用 tar 把卷内容打包到宿主目录。全程不必知道卷在宿主机上的真实路径，也不依赖宿主机装了 tar。

- 关键是把两个挂载放进同一个容器：卷挂在容器内某路径，宿主目录挂在另一个路径，tar 在容器内完成搬运。
- 官方示例：docker run --rm --volumes-from dbstore -v $(pwd):/backup ubuntu tar cvf /backup/backup.tar /dbdata。
- 现行写法可直接按卷名挂载，不必借助数据容器：docker run --rm -v dbdata:/from:ro -v "$PWD":/to alpine sh -c "cd /from && tar czf /to/db.tgz ."。
- 源卷加 :ro 只读挂载，避免备份过程意外改动源数据。
- 产物落在宿主目录，可再复制到异地或对象存储，实现离线保管。

```bash
docker run --rm \
  -v mysql-data:/from:ro \
  -v "$PWD":/to \
  alpine sh -c "cd /from && tar czf /to/mysql-data-20260912.tgz ."

ls -lh mysql-data-20260912.tgz
```

```text
-rw-r--r--  1 user  staff   18M Sep 12 10:20 mysql-data-20260912.tgz
```

> [!TIP]
> **建议内容**：把备份命令固定成脚本，卷名与日期做参数，产物带上时间戳并落到持久位置。手工备份的问题不在于命令难写，而在于事后无人知道上次备份是哪一天、备份的是哪个卷。

**速记**：一次性容器同时挂卷与宿主目录，容器内 tar 打包；源卷加 :ro，产物带时间戳。



#### 从 tar 恢复到新卷

**卷恢复套路**：先准备一个空的卷，再起一次性容器同时挂该卷与备份文件所在目录，在容器内解包。恢复到全新空卷最干净，因为卷里不会残留旧数据。

- 官方示例：docker run --rm --volumes-from dbstore2 -v $(pwd):/backup ubuntu bash -c "cd /dbdata && tar xvf /backup/backup.tar --strip 1"。
- --strip 1 用于剥掉归档里最外层目录，避免解出来多套一层路径；层数按实际打包方式决定。
- 现行写法：docker run --rm -v new-data:/to -v "$PWD":/from alpine sh -c "cd /to && tar xzf /from/db.tgz"。
- 恢复到非空卷会把备份内容与旧数据混在一起，形成难以理清的状态，应用务重建新卷再恢复。
- 恢复后检查文件属主与权限，必要时用容器内 chown 调整到目标 uid:gid。

```bash
docker volume create mysql-data-restored

docker run --rm \
  -v mysql-data-restored:/to \
  -v "$PWD":/from \
  alpine sh -c "cd /to && tar xzf /from/mysql-data-20260912.tgz"

docker run --rm -v mysql-data-restored:/to alpine ls -la /to
```

> [!CAUTION]
> **注意内容**：恢复到已有数据的卷上属于破坏性操作，且往往不可回退。正确顺序是先创建一个新卷、恢复到新卷、验证无误后再切换容器挂载；确认新卷可用之前不要删除旧卷或旧备份。

**速记**：新卷加临时容器解包，--strip 1 去掉外层目录；恢复前先建空卷。



#### 停机与一致性前提

**备份的一致性前提**：直接 tar 一个正在被写入的卷，可能得到内部状态不一致的副本——数据库事务写到一半、日志与数据文件不同步，恢复出来无法使用。备份前必须先让写入停下，或改用应用自带的逻辑导出。

- 最稳妥的做法是先停止写入方容器，再执行 tar，备份完成后重新启动。
- 数据库类应用优先用自带的一致性导出工具，如 mysqldump、pg_dump，导出的是逻辑一致的数据，而非直接拷贝数据目录。
- 若业务不允许停机，则让应用进入静默或只读状态，或依赖其自带的在线备份能力，而不是赌文件系统此刻是静止的。
- 备份不等于安全：未验证过能否恢复的备份不能算数，应定期在独立环境演练恢复。
- 卷的备份只覆盖卷内数据；bind mount 的数据在宿主目录里，直接备份宿主目录即可，两者要分别安排。

```bash
# 一致性优先：数据库自带逻辑导出
docker exec db mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" shop > shop-20260912.sql

# 直接打包数据目录前先停写
docker stop db && docker run --rm -v mysql-data:/from:ro -v "$PWD":/to alpine sh -c "cd /from && tar czf /to/db.tgz ." && docker start db
```

> [!WARNING]
> **警告内容**：对运行中的数据库数据目录做热备，得到的 tar 可能包含损坏的副本，且在恢复失败前毫无征兆。凡涉及数据库，一律用它的逻辑导出工具，或先停写再打包，绝不把「拷得快」当成「备份对」。

**速记**：备份先停写、数据库用自带导出、定期演练恢复；卷与 bind 数据要分别备份。



### 卷与 Compose / 编排的衔接

#### 顶层 volumes 声明与 service 引用

**Compose 中的卷**：命名卷在 Compose 文件顶层的 volumes 段声明，各 service 在自身 volumes 列表里按名字引用，形成「顶层定义、下层引用」的两层结构。这是 Compose 与裸 docker run 在卷组织上的主要差别。

- 顶层 volumes 段声明卷名，service 内写 卷名:容器路径 的短语法或 type 为 volume 的长语法。
- 只有被 service 引用的顶层卷才会在运行时被创建，未引用的声明不会产生卷。
- 顶层声明可带 driver、driver_opts、name 等字段，用于换驱动或固定实际卷名。
- external 为 true 表示引用一个已存在的外部卷，Compose 不负责创建，也不能删除它。
- service 内直接写一个未在顶层声明的卷名时，Compose 也会隐式创建，但显式声明更清楚也更可控。

```yaml
services:
  db:
    image: mysql:8
    volumes:
      - db-data:/var/lib/mysql
  api:
    image: app:1.0
    volumes:
      - db-data:/data:ro
      - type: bind
        source: ./conf
        target: /app/conf
        read_only: true

volumes:
  db-data:
  external-cache:
    external: true
```

> 语法层写法与短长语法的完整对照参见第 10 章 Docker Compose 入门；本节只讲与卷生命周期相关的部分——顶层声明决定了卷由谁创建、down 时会不会被删。external 卷的生命周期完全握在 Compose 之外。

**速记**：顶层声明卷、service 按名引用；external 表示卷已存在，Compose 不建不删。



#### 命名卷前缀（项目名_卷名）

**Compose 卷命名规则**：Compose 创建的卷，实际名字是 项目名_卷名，例如项目 demo-shop 中声明的 db-data 会生成 demo-shop_db-data。前缀用于把不同项目的同名卷隔离开。

- 项目名依次取自命令行 -p、环境变量 COMPOSE_PROJECT_NAME、文件顶层的 name 字段，最后回退到目录名。
- 同一份 Compose 文件用不同项目名运行两遍，会得到两套互不干扰的卷、容器与网络，这是环境隔离的实现方式。
- 想在卷列表里认领卷，必须按带前缀的实际名去找，直接找 db-data 往往找不到。
- 需要固定卷名时，用顶层 name 字段指定，或把卷声明为 external 并指向一个已有卷。
- 卷名前缀与容器名前缀同源，排查时两者可互相印证归属哪个项目。

```bash
docker compose -p shop-dev up -d
docker volume ls
```

```text
DRIVER    VOLUME NAME
local     shop-dev_db-data
```

> [!NOTE]
> **提醒内容**：docker compose down 不会影响 external 卷，但会保留由它自己创建的命名卷；卷的实际名字带项目名前缀，所以换个项目名再 up 会挂到一个全新的空卷上，看起来就像「数据没了」。这是环境隔离的预期行为，而非故障。

**速记**：实际卷名是 项目名_卷名，靠前缀做环境隔离；排查时用带前缀的名字。



#### down -v 的数据丢失风险

**down 与 -v**：docker compose down 默认停止并移除容器与网络，命名卷保留；加上 -v 会额外移除顶层声明的命名卷与容器附着的匿名卷，也就是连数据一起删。

- 不带 -v 的 down 只删容器与网络，命名卷与其中的数据保留，下次 up 沿用旧数据。
- 带 -v 的 down 删除顶层 volumes 声明的命名卷以及容器附着的匿名卷，属不可逆操作。
- external 方式声明的卷不受 down -v 影响，因为它的生命周期在 Compose 之外。
- 这个命令的破坏力在于它出现在日常命令里，容易被当成「重启环境」顺手敲出。
- 日常重启应使用 down 或 stop；只有在确认数据可弃或已有可用备份时，才加 -v。

```bash
docker compose down            # 保留命名卷
docker compose down -v         # 连命名卷一起删，数据丢失
docker compose stop            # 只停容器，最温和
```

> [!WARNING]
> **警告内容**：docker compose down -v 会删除命名卷，数据库数据与用户上传文件随之消失且无法恢复。执行前先确认三件事：卷里是不是重要数据、有没有最近验证过的备份、是否真的需要删卷，任何一项存疑就不要加 -v。

**速记**：down 留卷、down -v 删卷删数据；external 卷例外，日常重启用 down 或 stop。



### 选型决策

#### 什么数据该放卷、什么该放 bind

**选型的两个判据**：一问数据是否需要活过容器，二问宿主机上的其他工具是否需要直接读写同一份数据。前者决定要不要挂载，后者决定用卷还是 bind mount。

- **放命名卷**：数据库数据目录、应用上传文件、队列持久化目录等需要长期存活、且不需要宿主直接编辑的状态。
- **放 bind mount**：开发时挂源码、挂要频繁修改的配置文件、挂证书目录，以及宿主上已有且需被其他程序共同读写的目录。
- **放 tmpfs**：临时缓存、会话数据、解密后的敏感中间文件等不需要留存的内容。
- 判据的操作化：宿主上的编辑器、脚本或运维工具要直接打开它，选 bind mount；只有容器自己管，选命名卷。
- 生产数据库的数据目录优先放宿主机卷或独立存储，并明确安排备份，而不是默认容器可写层。

```bash
# 数据库数据：命名卷，容器自己管，宿主不直接编辑
docker run -d --name db -v mysql-data:/var/lib/mysql mysql:8

# 开发源码：bind mount，宿主编辑器直接改，容器即时看到
docker run -d --name api -v "$(pwd)/src":/app/src:ro node:24-alpine
```

> 卷与 bind mount 的分界不在「哪个更高级」，而在「谁是这份数据的责任人」。由 Docker 托管的数据用卷，由人或宿主工具托管的数据用 bind mount，混用会让归属在两处之间漂移。

**速记**：宿主要看要改用 bind、容器自己的状态用卷、临时敏感数据用 tmpfs。



#### 不该放进容器本地盘的与决策清单

**不该只放容器可写层**：容器可写层随容器一起消亡，写进这里的数据既保不住也无法单独备份，任何有留存价值的数据都不该只躺在容器可写层。跨主机共享本地卷同样不可行，本地卷的作用域限于单台机器。

- 有留存价值的数据必须挂到卷或 bind mount 上，不能依赖容器可写层。
- 生产数据库不能只依赖本机容器可写层，应落到卷或独立存储，并配异地备份。
- 本地卷不跨主机，多机共享数据必须改用外部存储服务。
- 一次性任务容器用 --rm 时，要保留的产物必须显式挂载到卷或宿主目录，否则随容器消失。
- 决策按顺序问五个问题：要不要活过容器、宿主要不要直接读写、要不要跨主机、要不要落盘、是不是生产数据库。

```text
选型决策清单（按顺序问）
1. 这份数据需要活过容器重启与重建吗？
   不需要 → 可放容器可写层或 tmpfs
   需要   → 进入第 2 问
2. 宿主机上的工具需要直接读写同一份数据吗？
   需要 → 用 bind mount（注意绝对路径与属主匹配）
   不需要 → 进入第 3 问
3. 数据需要跨主机共享吗？
   需要 → 用外部存储服务（对象存储、网络文件系统、数据库）
   不需要 → 用命名卷
4. 数据是否需要落盘？
   不需要且属临时或敏感数据 → 用 tmpfs
5. 是生产数据库的数据目录吗？
   是 → 命名卷或宿主机卷加独立存储，并做定期备份与恢复演练
```

> [!IMPORTANT]
> **重要内容**：选型的核心不是记住三种类型的名字，而是先问清楚数据要不要活过容器、宿主要不要直接读写、要不要跨主机这三件事。三问的答案会直接把你导向卷、bind mount、tmpfs 或外部存储，不需要凭经验猜。

**速记**：先问「要不要活过容器、宿主要不要看、要不要跨主机」，再定 volume、bind mount、tmpfs 或外部存储。
