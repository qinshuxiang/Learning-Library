## Docker 部署 MySQL 与 Redis 实战

### 在容器里跑数据库的取舍

#### 容器化数据库买到了什么

**容器化数据库**：指把 MySQL、Redis 这类有状态服务的进程与其运行环境一起固化进镜像，由容器运行时启动，数据通过卷落到容器之外。它买到的是可复现的环境与可版本化的部署方式，而不是「数据库本身变简单了」。

- **环境一致**：镜像把数据库版本与基础系统一并固化，开发机、测试机与 CI 跑出同一套行为，不再出现本机 8.0、测试机 5.7 的错配。
- **版本易切换**：换一个镜像标签就能并行拉起两个大版本，用同一份业务数据做兼容性验证，验完删容器即可。
- **测试库随手起**：一条命令得到空实例，跑完即删，测试之间互不污染，CI 流水线里的收益最明显。
- **配置即代码**：初始化 SQL、配置片段、环境变量都能提交进版本库，可评审、可回滚。
- **与缓存一起编排**：应用所依赖的数据库与缓存可由一份 Compose 文件描述，启动顺序与网络隔离一并声明，见篇 11 Docker Compose 进阶与实战。

```bash
docker run -d --name tmp-mysql \
  -e MYSQL_ROOT_PASSWORD=dev-only-pass \
  -e MYSQL_DATABASE=demo \
  mysql:8.4
```

> 一致性也意味着「数据库不再是能随手进去改的东西」：改配置要改文件、重建容器，而不是登录后敲一句 SET GLOBAL。作为基础设施，这恰是应有的约束。

**速记**：容器化数据库买到**环境一致、版本可切换、测试库随手起**。



#### 必须接受的四项代价

**四项代价**：I/O 性能折扣、持久化必须外置、网络暴露面变化、运维与备份责任不变。它们不是容器引入的缺陷，而是「数据库跑在容器里」这一事实的必然代价。

- **I/O 性能有折扣**：容器与宿主共用内核，Linux 上直连磁盘的开销与裸机接近，但叠加镜像存储驱动、卷子系统的路径后，尤其在小 fsync 密集的写场景下，吞吐与延迟通常差于同硬件裸机。
- **持久化必须靠卷**：数据目录若不挂出来，容器可写层随容器消亡，删容器即删库；这条在篇 2 与篇 7 已反复强调，本篇负责落到数据目录上。
- **网络与暴露面**：容器有独立网络命名空间，默认不与宿主同栈；端口不发布外部就连不上，一旦发布又可能直接暴露到公网。
- **运维责任不变**：备份、恢复演练、监控、容量规划、版本升级，一件都不会因为换了容器而省掉，只是换了操作入口。

> 辨析：容器解决的是「怎么部署和交付」，不解决「怎么把数据库运维好」。把 MySQL 塞进容器不会自动获得高可用，也不会自动获得备份策略，这两件事仍要单独设计。

**速记**：代价是**掉一点 I/O、数据必须落卷、网络要自己规划、运维责任不转移**。



#### 一句结论：生产可用，但前提是数据出容器

**结论**：把 MySQL 与 Redis 放进容器用于生产是完全可行的，唯一不可退让的前提是——数据目录必须落在容器之外（命名卷或宿主目录），且备份与恢复演练照旧执行。满足这两条，容器化是收益；不满足，它就是一场迟早发生的删库事故。

- **数据出容器**：数据目录挂到命名卷或宿主目录，容器可随时重建而数据不动，这是篇 7 的核心结论在本篇的落地。
- **备份也要出宿主机**：卷只在单机，卷不跨主机；异地副本仍要另行安排，见本篇备份一节。
- **能重建的才是无状态**：数据库是有状态服务，容器只是它的运行外壳；把外壳当主体，就会在重建容器时丢掉全部。
- **不适用的例外**：对 I/O 极度敏感、明确要求裸机性能的核心库，或合规要求数据不落可迁移存储的场景，应留在裸机或用托管数据库。

> 官方 MySQL Docker 镜像文档明确只支持 Linux 平台，其他平台属「自担风险」；在 macOS 与 Windows 上跑的是 Linux 虚拟机内的容器，性能与路径行为都要按虚拟机理解。

> [!IMPORTANT]
> **重要内容**：判断一个数据库容器是否「生产可用」，先问三句：数据目录挂卷了吗、有没有验证过能恢复的备份、端口有没有暴露到公网。三问里有任何一句答不上来，就不该把它当生产库使用。

**速记**：**生产可用，前提只有一个——数据出容器；备份、演练、责任都不因此减少**。



### MySQL 官方镜像的初始化机制

#### 四个初始化环境变量与相互关系

**四个初始化环境变量**：MYSQL_ROOT_PASSWORD、MYSQL_DATABASE、MYSQL_USER、MYSQL_PASSWORD，它们由镜像的入口脚本读取，在**数据目录为空**的首次启动时创建账号与库。四者的关系是「一个必填、三个可选、两两成对」。

- **MYSQL_ROOT_PASSWORD**：为 root 账号设置密码，是必填项；除非改用 MYSQL_ALLOW_EMPTY_PASSWORD 或 MYSQL_RANDOM_ROOT_PASSWORD，否则不写它容器会直接启动失败。
- **MYSQL_DATABASE**：可选，指定一个在启动时创建的数据库名。
- **MYSQL_USER 与 MYSQL_PASSWORD**：可选，**必须成对出现**，共同创建一个普通用户并设其密码；只写其中一个不会创建用户。
- **授权关系**：当同时给了 MYSQL_DATABASE 时，MYSQL_USER 会被授予该库的全部权限（官方表述对应 GRANT ALL），未给库名时该用户不被授权到具体库。
- **与 root 的关系**：MYSQL_USER 不能写成 root，入口脚本会拒绝；root 账号由 MYSQL_ROOT_PASSWORD 单独创建。
- **密码从文件读**：给上述变量名追加 _FILE 后缀（如 MYSQL_ROOT_PASSWORD_FILE），可从文件读取取值，官方文档说明当前仅对 ROOT_PASSWORD、ROOT_HOST、DATABASE、USER、PASSWORD 支持。

```yaml
services:
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: root-pass-change-me
      MYSQL_DATABASE: shop
      MYSQL_USER: app
      MYSQL_PASSWORD: app-pass-change-me
```

> 四个变量只管「创建一个用户和一个库」这件最小的事，不负责建表、不负责灌数据、也不负责授权到多库。更复杂的初始化属于下一考点的初始化脚本。

**速记**：**root 密码必填，库名可选，USER 与 PASSWORD 必须成对，USER 不能叫 root**。



#### 只在数据目录为空时生效

**关键规则**：上述变量只在**数据目录为空**的首次启动阶段生效；只要数据目录里已经有数据库（官方文档表述为已经存在一个 mysql 子目录），后续启动时它们会被整体忽略，既有数据一动不改。

- **判定依据是数据目录**：入口脚本检查 /var/lib/mysql 是否为空，空则执行初始化，非空则直接以现有数据启动。
- **忽略是静默的**：改了 MYSQL_PASSWORD 再重建容器，旧密码仍然有效、新密码不生效，且不会有任何报错。
- **数据目录来自卷**：只要卷里还留着上一轮的初始化结果，环境变量就被跳过；这正是「改了变量却没反应」的唯一根因。
- **重建与重初始化的区别**：docker rm 再 run 只换容器壳，卷还在；要让变量重新生效，必须先清掉数据目录。
- **官方谨慎建议**：当数据目录里已有数据库时，运行命令应省略 MYSQL_ROOT_PASSWORD，它无论如何都会被忽略。

> [!WARNING]
> **警告内容**：想让初始化变量重新生效，唯一办法是删除数据目录（删卷或清空宿主目录），而这会连同库里的全部数据一起删除。正确顺序永远是「先备份、再决定是否重建」，绝不要为了改一个密码直接删卷。

**速记**：变量**只在数据目录为空时按一次**；非空即被静默忽略，要重来只能连数据一起清。



#### /docker-entrypoint-initdb.d 的挂载与执行顺序

**初始化脚本目录**：把脚本放进容器的 /docker-entrypoint-initdb.d 目录（通常用挂载），首次初始化时入口脚本会按**文件名字母序**依次执行它们，用于建表、灌种子数据、设置额外的库与用户。

- **执行时机**：只在首次初始化、即数据目录为空时执行一次，之后无论容器重启多少次都不再执行。
- **支持的文件类型**：官方文档列出 .sh、.sql、.sql.gz、.sql.bz2、.sql.xz、.sql.zst；压缩文件会先解压再送入对应客户端。
- **.sql 的落库**：SQL 文件默认导入到 MYSQL_DATABASE 指定的数据库，因此灌数据前要先设好库名。
- **.sh 的处理**：有可执行位的 shell 脚本直接执行，没有可执行位的会被 source 执行，所以不必特意 chmod。
- **顺序可控**：文件按字母序执行，需要严格先后时用 01-、02- 这样的前缀命名。
- **挂载方式**：把宿主目录以只读方式挂到该目录，或写进自定义镜像，两种方式官方都支持。

```yaml
services:
  db:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: root-pass-change-me
      MYSQL_DATABASE: shop
    volumes:
      - db-data:/var/lib/mysql
      - ./initdb:/docker-entrypoint-initdb.d:ro
```

```text
initdb/
├── 01-schema.sql       # 建表结构，按字母序先执行
├── 02-seed.sql         # 灌种子数据
└── 03-grant.sh         # 需要额外授权时用 shell 脚本
```

> 初始化脚本只在首次启动跑一次，写 CREATE TABLE IF NOT EXISTS 之类的幂等语句意义有限，因为它根本不重跑；真正要改结构时，应走版本化的迁移工具，而不是指望再往 initdb 里丢一个文件。

**速记**：**进 initdb、按字母序、只在首次跑一次，.sql 落 MYSQL_DATABASE，.sh 可执行不到位就 source**。



#### 初始化失败时容器长什么样

**失败表现**：初始化过程中任一步失败，入口脚本会带着非零退出码终止，容器状态变为 Exited 而不是 Up，端口连不上，业务侧表现为「数据库一直没起来」。定位入口在日志，不在客户端。

- **看状态**：docker compose ps -a 或 docker ps -a 看到容器已退出而非运行中。
- **看日志**：docker compose logs db 会打印入口脚本执行到哪一步失败，常见的是初始化 SQL 语法错误、权限不足、字符集不匹配。
- **看退出码**：非零退出码配合日志可判断是脚本失败还是 mysqld 起不来。
- **初始化未完成即中断的后果**：若中途失败，数据目录可能已写入部分内容，下次启动会被判定为「非空」而跳过初始化，导致卡在半初始化状态。
- **处置方向**：先读日志定位失败的脚本或语句，修正后清掉半成品数据目录再重来；确认是数据目录非空导致跳过时，同样按上一考点的顺序处理。

```bash
docker compose ps -a
docker compose logs --tail=100 db
docker inspect -f '{{.State.ExitCode}} {{.State.Status}}' db
```

> 半初始化是比初始化失败更难缠的状态：容器能起来，库却缺表或缺账号。排查这类问题先执行 SHOW DATABASES 与 SELECT user, host FROM mysql.user，确认初始化到底跑到了哪一步。

**速记**：失败即**退出码非零、状态 Exited，日志里找入口脚本的报错，半初始化要去库里核对**。



### MySQL 的数据、配置与连接

#### /var/lib/mysql 必须挂命名卷

**数据目录**：MySQL 官方镜像把数据文件写在容器的 /var/lib/mysql 下，这个目录必须挂到命名卷，否则数据随容器可写层一起消亡。挂命名卷而非绑定宿主目录，是数据库容器最省心的默认选择。

- **镜像声明了卷**：镜像把 /var/lib/mysql 声明为卷，不显式挂载时会生成匿名卷；匿名卷难以寻址，长期运行后会积累一堆认不出归属的悬空卷。
- **命名卷的优势**：由 Docker 托管属主与初始化，避开宿主目录的权限差异；卷名可寻址，重建容器时按名挂回即可。
- **绑定宿主目录的代价**：容器内进程的 uid 与宿主目录属主不匹配时启动即报 Permission denied，数据库镜像尤其典型，见篇 7 数据卷与数据持久化。
- **卷的生命周期**：删容器不删卷、删卷才丢数据；docker compose down 保留命名卷，加 -v 才连卷删除。
- **迁移与备份**：卷不跨主机，跨机迁移要靠逻辑导出或一次性容器打包，不能靠搬卷目录。

```bash
docker volume create mysql-data
docker run -d --name db \
  -e MYSQL_ROOT_PASSWORD=root-pass-change-me \
  -v mysql-data:/var/lib/mysql \
  mysql:8.4
```

> [!WARNING]
> **警告内容**：docker compose down -v 与 docker volume prune -a 都会删除命名卷，也就是删除数据库本体。日常重启一律用 down 或 stop；只有在确认数据可弃、或已验证过备份可恢复时，才允许带 -v 或 -a。

**速记**：**数据目录挂命名卷，属主交给 Docker 管；删容器不丢，删卷才丢**。



#### 配置文件走 /etc/mysql/conf.d 目录

**配置挂载方式**：推荐把 .cnf 片段挂进 /etc/mysql/conf.d 这一**目录**，而不是把单个 .cnf 文件挂到某个固定路径。原因是绑定单个文件时，宿主机上的编辑器替换文件（写临时文件再改名）会让容器里指向旧 inode 的挂载失联，表现为配置改了不生效；挂目录没有这个问题。

- **默认文件位置**：按官方镜像文档，Oracle 系基础镜像（现行默认）的默认配置在 /etc/my.cnf，Debian 系的 MySQL 8 镜像在 /etc/mysql/my.cnf，二者都可能用 !includedir 引入 /etc/mysql/conf.d。
- **优先级**：官方自定义配置示例说明，结果由默认配置与 /etc/mysql/conf.d 下的片段合并而成，片段中的同名项优先。
- **挂目录的写法**：把宿主上的 conf.d 目录整体挂到 /etc/mysql/conf.d，容器只读该目录即可。
- **只读挂载**：配置目录加 :ro，既防止容器写，也证明容器不依赖改配置运行。
- **改配置即重启**：绝大多数 MySQL 配置项需要重启 mysqld 生效，改完要重建或重启容器。

```yaml
services:
  db:
    image: mysql:8.4
    volumes:
      - db-data:/var/lib/mysql
      - ./mysql-conf:/etc/mysql/conf.d:ro
```

> 挂单文件与挂目录的差别不只是粒度：绑目录时容器里看到的是宿主目录的实时内容，容器内进程按目录读取即可；绑文件时宿主侧一替换文件，容器里的挂载点就指向了已被替换掉的旧文件。

**速记**：**配置走 conf.d 目录，别绑单文件；默认文件在 /etc/my.cnf 或 /etc/mysql/my.cnf，片段优先**。



#### 常用配置项：字符集与内存

**三个高频配置项**：字符集与排序规则决定能否存下表情与四字节字符，max_connections 决定并发上限，innodb_buffer_pool_size 决定 InnoDB 的内存胃口。三者都要与容器内存限制一起算。

- **字符集与排序规则**：写 character-set-server 等于 utf8mb4、collation-server 等于 utf8mb4_0900_ai_ci；MySQL 8.0 起这两项默认即为该值，显式写出来是为了防止历史配置或客户端串掉链子。
- **连接侧的字符集**：除 server 段，客户端段也要写 default-character-set 等于 utf8mb4，否则连接字符集与表字符集不一致时仍可能报错。
- **max_connections**：最大并发连接数，默认 151；每个连接都占线程与缓冲，不能只按业务并发数往上堆，要结合内存预算。
- **innodb_buffer_pool_size**：InnoDB 的缓冲池，是 MySQL 最吃内存的一项，经验上给容器内存上限的 50% 至 70%，余量留给连接、排序与系统。
- **与容器限制的配合**：给容器设 -m 512m 却把 buffer pool 设成 800M，等于把容器推给 OOM Killer，见篇 13 容器资源限制与运行时约束。

```conf
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_0900_ai_ci
max_connections = 200
innodb_buffer_pool_size = 512M

[client]
default-character-set = utf8mb4
```

> [!IMPORTANT]
> **重要内容**：容器内的 MySQL 不会自动读取容器的内存上限来调整自身参数。innodb_buffer_pool_size 必须由人显式设好，并且要小于容器内存限制，否则配置越激进，容器被杀得越快。

**速记**：**utf8mb4 加 utf8mb4_0900_ai_ci、连接数看内存、缓冲池取容器上限的五六成**。



#### 两种进入客户端的方式

**两种连接方式**：一是用 docker exec 在容器内起 mysql 客户端，走容器本地；二是从宿主机用 mysql 客户端连容器**发布的端口**，走网络。前者不依赖端口发布，后者需要把 3306 暴露出来。

- **容器内方式**：docker compose exec db mysql -uroot -p 进入交互客户端，或带 -e 执行单条语句；密码不进命令行，由交互提示输入最安全。
- **宿主机方式**：先用 -p 127.0.0.1:3306:3306 把端口绑到本机回环，再用 mysql -h 127.0.0.1 -P 3306 -u app -p 连接。
- **主机名陷阱**：客户端写 -h localhost 时在 Unix 系默认走 Unix 域套接字而非 TCP，要强制走 TCP 必须写 -h 127.0.0.1。
- **端口发布的范围**：只写 -p 3306:3306 会把端口绑到 0.0.0.0，即所有网络接口；只供本机访问要写成 127.0.0.1:3306:3306。
- **非交互脚本**：脚本里用 exec 加 -T 关闭伪终端分配，避免报错。

```bash
docker compose exec db mysql -uroot -p
docker compose exec -T db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW DATABASES;"
mysql -h 127.0.0.1 -P 3306 -u app -p -D shop
```

> 生产环境不必向宿主机发布数据库端口：应用容器与数据库容器在同一张自建网络里，用服务名直连即可，端口发布属于开发和调试手段。

**速记**：**容器内 exec 进客户端，宿主机连要发布端口；-h localhost 走套接字，走 TCP 写 127.0.0.1**。



### MySQL 的备份与恢复

#### 容器内 mysqldump 导出到宿主机

**逻辑导出**：在运行中的容器里执行 mysqldump，把输出重定向到宿主机的文件，是容器化 MySQL 最通用的备份方式。官方镜像文档给出的正是这种「exec 加 sh -c 加 exec」的模式。

- **官方模式**：docker exec 某容器 sh -c 后接一条命令，命令里用 exec 让 mysqldump 成为容器主进程，减少一层 shell。
- **密码取自容器环境**：脚本里用 MYSQL_ROOT_PASSWORD 这个容器内已有的环境变量，避免在命令行明文写字面量。
- **一致性参数**：InnoDB 表加 --single-transaction 走一致性快照，不锁业务；需要时再加 --routines 与 --triggers 带上存储程序与触发器。
- **输出方向**：重定向发生在宿主机侧，容器只负责把 SQL 打到标准输出，落在宿主机的文件天然就在容器之外。
- **单库与全库**：库名写在命令末尾导单库，加 --all-databases 导全库。

```bash
docker exec db sh -c 'exec mysqldump --single-transaction --routines --triggers \
  -uroot -p"$MYSQL_ROOT_PASSWORD" shop' > shop-20260912.sql

docker exec db sh -c 'exec mysqldump --single-transaction --all-databases \
  -uroot -p"$MYSQL_ROOT_PASSWORD"' > all-20260912.sql
```

> [!CAUTION]
> **注意内容**：不要把密码直接写在 -p 后面（例如 -p123456），它会进入进程列表与 shell 历史。正确做法是像上面这样引用容器内的环境变量，或用 -p 让客户端交互提示输入。

**速记**：**exec 进容器跑 mysqldump，标准输出重定向到宿主机；InnoDB 带 --single-transaction，密码取自环境变量**。



#### 一次性容器做导出与导入

**一次性容器套路**：如果本机没有 mysql 客户端，或不想在宿主上装任何东西，就起一个一次性容器完成任务，做完自动删除。导出与导入各一次，互不干扰。

- **复用服务配置**：docker compose run --rm 后接服务名，会按该服务的镜像、环境变量与网络新建一个临时容器，最省事。
- **独立一次性容器**：docker run --rm 挂上网络与输出目录，在容器里连数据库服务名；镜像与数据库保持同一大版本，避免客户端不兼容。
- **导出的落点**：把宿主目录挂进临时容器的 /backup，容器内写文件即落到宿主，避免结果留在容器里随容器删除。
- **导入的方式**：用 exec -i 或 run 的 -i 把 SQL 从标准输入喂给 mysql 客户端，官方示例同样是 sh -c 加 exec 的模式。
- **恢复前先建空库**：导入到已存在的库会把数据与旧数据混在一起；恢复到干净目标最可控。

```bash
docker compose run --rm -T db sh -c 'exec mysqldump --single-transaction \
  -uroot -p"$MYSQL_ROOT_PASSWORD" shop' > shop-20260912.sql

docker compose exec -T db sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" shop' < shop-20260912.sql

docker run --rm --network shop_backend -v "$PWD":/backup mysql:8.4 \
  sh -c 'exec mysqldump --single-transaction -h db -uroot -p"$MYSQL_ROOT_PASSWORD" shop > /backup/shop.sql'
```

> 一次性容器连数据库时，网络名要写 Compose 生成的实际名（通常是 项目名_网络名）或用 docker compose run 代劳；直接写 Compose 文件里声明的逻辑名是连不上的。

**速记**：**临时容器连网络、挂输出目录，导出写入 /backup、导入从标准输入喂**。



#### 逻辑备份与物理备份的分工

**两类备份**：**逻辑备份**导出 SQL 文本，可读、可跨版本、单表可恢复；**物理备份**直接拷贝数据文件，恢复快、体积小，但绑死版本与平台。容器化场景优先逻辑备份，物理备份交给专业工具做。

- **逻辑备份适用**：跨版本迁移、单库单表恢复、审计与脱敏、数据量中小；代表工具 mysqldump。
- **物理备份适用**：数据量大、要求快速恢复、能接受绑版本；代表工具 Percona XtraBackup，需额外容器或工具链。
- **卷打包不等于物理备份**：直接 tar 运行中的数据目录可能拿到内部不一致的副本，数据库必须走逻辑导出或先停写，见篇 7。
- **binlog 补增量**：逻辑全量定起点，binlog 连续归档补增量，可恢复到任意时间点；这属于 MySQL 主题的备份恢复范围。
- **容器化的选择**：多数团队的容器化 MySQL 以「每日逻辑全量加 binlog 归档」为主，物理备份只在明确需要快速恢复时引入。

> 逻辑与物理不是二选一：全量用逻辑保通用性，热点大库用物理保恢复时间，两者并存时以逻辑备份作为兜底的跨版本手段。

**速记**：**逻辑dump通用可跨版本、物理拷贝快但绑版本；卷 tar 不是数据库备份**。



#### 恢复演练：没验证过的备份等于没有

**恢复演练**：备份的价值只在成功恢复的那一刻兑现。未在独立环境实际导入过一次的备份文件，不能算作可用备份——它可能损坏、版本不兼容、字符集错乱，这些问题只在恢复时暴露。

- **演练的频率**：至少按季度做一次，或每次变更备份策略后立刻做一次。
- **演练的最小动作**：在独立实例或临时容器里导入最新备份，跑几条业务查询确认数据完整。
- **记录 RTO**：记录从开始恢复到可用的耗时，这是灾难时的真实预期，不是估计值。
- **验证落点**：确认库表数量、关键表行数、字符集与排序规则是否与源库一致。
- **备份要异地**：卷在单机、备份文件也应离开这台机器，否则磁盘或主机损坏时备份与数据一起没。

```bash
docker run --rm -d --name drill-mysql \
  -e MYSQL_ROOT_PASSWORD=drill-pass \
  -e MYSQL_DATABASE=shop \
  mysql:8.4

docker exec -i drill-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" shop' < shop-20260912.sql
docker exec drill-mysql mysql -uroot -pdrill-pass -e "SELECT COUNT(*) FROM shop.orders;"
docker rm -f drill-mysql
```

> [!WARNING]
> **警告内容**：备份没恢复过，等于没有备份。磁盘损坏、误删库、版本升级失败这三类事故里，唯一的退路就是一份被实际导入验证过的备份；只把 mysqldump 跑成功不算验证。

**速记**：**备份要演练、恢复要计时、结果要核对；异地一份，才算真备份**。



### MySQL 的版本升级与数据迁移

#### 为什么不能随便挂旧数据目录

**不可随意升级的根因**：MySQL 的数据目录里存着**数据字典**与系统表，它们的结构随大版本变化。直接用新版本容器挂上旧数据目录，服务器在启动时会尝试把数据字典升级到新结构；这是一次单向、不可逆的改写，中途失败或版本路径不支持就会留下无法启动的数据目录。

- **数据字典随版本变**：新增的权限、系统表与元数据需要由新版本服务器补齐，旧目录不能直接当新目录用。
- **服务器负责升级**：自 MySQL 8.0.16 起，升级任务由服务器在启动时自动完成，官方文档明确说明 mysql_upgrade 变得不再需要、并已标记为弃用。
- **升级动作发生在启动时**：新版本容器第一次挂上旧数据目录并启动，就是升级发生的那一刻；此时看到的「容器起来慢」很可能正是在做升级。
- **所以先备份**：升级前必须备份，这是官方升级章节反复强调的第一条。
- **升级中不要并发写**：升级期间不要有业务连进来写入，让它安静跑完。

```text
升级的时间线（容器化）
1  旧版本容器继续服务
2  对旧库做一次逻辑全量备份
3  停止旧容器（保留数据卷）
4  用新版本镜像、挂同一个数据卷起新容器
5  新服务器启动时自动升级数据字典
6  看日志确认升级成功，再做功能验证
```

> [!IMPORTANT]
> **重要内容**：升级的第一步永远是备份，第二步永远是在测试环境先走一遍。生产库上直接换镜像标签，是把「能不能升级」交给运气，而升级是单向的，失败往往意味着回滚到备份。

**速记**：**旧数据目录带着旧数据字典，新服务器启动时做一次性、单向的升级；先备份、先测试**。



#### 官方推荐路径与工具现状

**官方路径**：停旧容器、拉新镜像、用新镜像挂同一份数据与配置起新容器、等服务器完成升级、看日志确认。官方 Docker 升级章节给的正是这条流程，并强调数据与配置必须先持久化在宿主上。

```bash
docker stop mysql84
docker pull mysql:9.7
docker run --name mysql97 \
  --mount type=volume,src=mysql-data,dst=/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=root-pass-change-me \
  -d mysql:9.7
docker logs -f mysql97
```

- **数据与配置都在容器外**：官方要求升级前数据与配置已持久化在宿主侧，这样才能换容器不换数据。
- **同系列小版本升级同理**：同一 LTS 系列内（例如 8.4.x 到 8.4.y）也是「停旧容器、用新镜像挂旧数据起新容器」，流程一致。
- **mysql_upgrade 已退场**：官方 8.0 文档说明该工具自 8.0.16 起不再执行升级任务、并已弃用；8.4 及以后不必再找它，具体以官方升级文档为准。
- **升级后看日志**：数据目录升级的进展与结果写在服务器错误日志里，容器场景就是 docker logs。
- **升级兼容性检查**：官方建议升级前用 MySQL Shell 的升级检查工具核对兼容性，具体以官方升级文档为准。

> 官方升级方式不止一种：除原地升级（in-place），还支持逻辑导出再导入、复制升级与 MySQL Clone。数据量小、跨版本跨度大时，逻辑导出再导入往往比原地升级更可控。

**速记**：**停旧、拉新、挂同一份数据与配置起新容器、看日志确认；mysql_upgrade 已不需要**。



#### 大版本不能跳级与降级不可行

**路径约束**：官方升级路径表明确，bugfix 或 LTS 系列**不可跳过**。跨系列升级必须逐级走，例如从 5.7 到 8.4 不能一步到位，要先升到 8.0，再从 8.0 升到 8.4。

- **不可跳系列**：从一个 LTS 或 bugfix 系列跳到更远的系列属不支持路径，必须先升到中间的 LTS。
- **Innovation 到更远的 Innovation**：官方路径表也标注此类跳跃不被允许，需要先经过中间的 LTS 再继续。
- **同系列内可自由升**：同一系列内的小版本升级（如 8.4.0 到 8.4.4）属常规路径。
- **降级基本不可行**：数据字典升级是单向改写，降级回旧版本通常不被支持；官方把「降级」限定在很窄的场景，具体以官方升级文档为准。
- **容器化不改变这些约束**：换镜像标签很容易，但约束是 MySQL 的，不是 Docker 的；标签越容易换，越容易踩到不合法的路径。

> [!CAUTION]
> **注意内容**：看到 mysql:8.4 与 mysql:9.7 两个标签就随手把生产的 8.4 换成 9.7，跳过的可能是官方不支持的升级路径。换标签前先对照官方升级路径，确认这次跨度是否被允许。

**速记**：**系列不能跳，要逐级升；降级基本不可行，标签好换、约束没变**。



#### 容器化后回滚为什么更难

**回滚更难的原因**：裸机上回滚可以「换回旧二进制、指向旧数据目录」，但在数据字典已被新版本单向升级之后，旧版本根本读不懂这份数据。容器化把「换版本」变得更容易，却没有让「回退版本」变容易，反而更容易在慌乱中重复试错。

- **升级即改写**：升级一旦发生，旧版本对这份数据目录已不再兼容，回滚的前提是回到升级前的备份。
- **容器重建很快，但数据只有一份**：镜像换回去只需几秒，被改写的数据不会自己变回去。
- **卷是唯一现场**：所有容器都挂同一个卷，反复用不同镜像去挂，会让数据目录在多次半升级之间变得更乱。
- **正确回滚姿势**：停掉新容器、从升级前备份恢复到新卷、用旧版本镜像挂恢复出的卷。
- **测试环境先练**：在生产升级前，用同一份备份在测试环境完整走一遍升级与回滚，把步骤固化成脚本。

```bash
# 回滚思路：不动被升级过的卷，改从备份恢复到一个新卷
docker volume create mysql-data-old
docker run --rm -v mysql-data-old:/var/lib/mysql -v "$PWD":/backup mysql:8.4 \
  sh -c 'exec tar xzf /backup/mysql-data-20260911.tgz -C /var/lib/mysql'
docker run -d --name db-old -v mysql-data-old:/var/lib/mysql mysql:8.4
```

> [!WARNING]
> **警告内容**：不要指望把镜像标签换回旧版本就能回滚——数据字典已经被新版本改写，旧版本会拒绝或误读这份数据。真正的回滚是「恢复升级前的备份」，所以升级前的备份不是可选项，是回滚的唯一依据。

**速记**：**升级单向、回滚靠备份；卷反复被不同版本挂只会更乱，测试环境先练一遍**。



### Redis 官方镜像的使用

#### 启动参数怎么传给 redis-server

**参数位置**：Redis 官方镜像的启动命令是 redis-server，启动参数写在镜像名之后。入口脚本会识别两种写法：直接以 redis-server 开头，或只给以短横线开头的参数（此时入口脚本自动补上 redis-server）。

- **显式写法**：docker run 镜像名后接 redis-server 再跟参数，语义最清楚。
- **简写**：只写以 -- 开头的参数时，入口脚本会把 redis-server 补在前面，效果等同。
- **指定配置文件**：把配置文件名作为位置参数传给 redis-server，即 redis-server /path/redis.conf。
- **文件加参数叠加**：先给配置文件、再跟命令行参数，命令行参数覆盖文件中的同名项。
- **仅容器内生效**：docker exec 进 redis-cli 用 CONFIG SET 改的项是运行期行为，要跨重启生效必须写回配置文件。

```bash
docker run -d --name cache -v redis-data:/data redis:8.4 \
  redis-server --appendonly yes --requirepass change-me

docker run -d --name cache2 -v redis-data:/data redis:8.4 \
  redis-server /usr/local/etc/redis/redis.conf --appendonly yes
```

> 由于入口脚本能自动补 redis-server，docker run redis:8.4 --requirepass change-me 也是合法的；但显式写出 redis-server 更利于阅读与排错，脚本里建议保持完整写法。

**速记**：**命令位置在镜像名后，写 redis-server 加参数；只给 -- 参数入口脚本会自动补**。



#### 配置文件挂载与 command 覆盖

**配置文件挂载**：把宿主的配置目录挂到 /usr/local/etc/redis，再用 redis-server 指定其中的 redis.conf，是官方文档给出的做法。需要注意该目录**必须可写**，因为 Redis 视配置与运行模式可能需要新建或重写配置文件。

- **官方路径**：镜像内的配置目录是 /usr/local/etc/redis，官方示例把 redis.conf 放在这里。
- **可写要求**：官方文档明确提示映射目录应可写，否则在需要改写配置时启动或运行会失败。
- **Compose 的 command 覆盖**：在 Compose 里用 command 覆盖镜像默认命令，内容按列表形式写完整，例如 redis-server 加配置路径再跟参数。
- **不要只给参数丢掉配置**：若 command 只写一个参数列表而没带配置文件路径，等于用默认配置加少量覆盖，原有 redis.conf 不会生效。
- **改配置后重建**：改配置文件后要重启容器；在 Compose 里对 command 的改动只需重建容器，不必重建镜像。

```yaml
services:
  cache:
    image: redis:8.4
    command: ["redis-server", "/usr/local/etc/redis/redis.conf"]
    volumes:
      - redis-data:/data
      - ./redis-conf:/usr/local/etc/redis
```

> 挂目录而非挂单文件，与 MySQL 的配置挂载是同一个理由：宿主编辑器替换单文件时，容器里指向旧文件的挂载会失联。把整个目录挂进去，再用目录内的文件名指定，稳定性更好。

**速记**：**配置挂 /usr/local/etc/redis 且要可写，command 里要给 redis-server 加配置路径**。



#### 四个常用启动参数

**四个常用启动参数**：--appendonly 决定是否开 AOF，--requirepass 设置密码，--maxmemory 设定内存上限，--maxmemory-policy 指定淘汰策略。它们都能写在命令行，也能写进 redis.conf。

- **--appendonly yes**：开启 AOF，把每条写命令追加落盘，丢失窗口比 RDB 更小；Redis 7 起 AOF 是目录加多文件结构。
- **--requirepass**：为实例设置全局密码，客户端连接后需先认证；官方镜像文档特别指出该镜像默认关闭保护模式，暴露端口时务必设密码。
- **--maxmemory**：Redis 可用的最大内存，默认 0 表示不限制；容器里必须显式设成小于容器内存上限的值。
- **--maxmemory-policy**：内存打满时的淘汰策略，默认 noeviction（拒绝写），纯缓存场景常用 allkeys-lru。
- **持久化二选一不是必须**：RDB 与 AOF 可以同时开启，重启时优先用 AOF 恢复，见 Redis 主题的持久化章节。

```bash
docker run -d --name cache \
  -v redis-data:/data \
  -m 768m \
  redis:8.4 redis-server \
    --appendonly yes \
    --requirepass "$REDIS_PASSWORD" \
    --maxmemory 512mb \
    --maxmemory-policy allkeys-lru
```

> 命令行参数与配置文件是同一组配置项的两种写法：临时验证用命令行，生产用配置文件并纳入版本管理；二者同时出现时，命令行覆盖文件。

**速记**：**appendonly 管落盘、requirepass 管密码、maxmemory 管上限、maxmemory-policy 管淘汰**。



#### /data 目录必须挂卷

**/data 目录**：官方镜像把 /data 声明为卷，RDB 快照与 AOF 文件都写在这里。不挂卷，数据只活在容器可写层，删容器即全部丢失；挂了卷，重建容器按名挂回即可。

- **镜像声明了 VOLUME /data**：不显式挂载时会生成匿名卷，命名卷才是可寻址的正解。
- **RDB 落点**：dump.rdb 写在 dir 指向的目录，镜像默认就是 /data。
- **AOF 落点**：Redis 7 起 AOF 在 dir 下的子目录（默认 appendonlydir）里，也是 /data 之内，挂 /data 即可一并覆盖。
- **备份靠卷或命令**：备份可以在容器内触发 BGSAVE 后打包 /data，也可以用 redis-cli 触发保存再从卷导出。
- **本地卷不跨主机**：跨机迁移要另想办法，不能指望搬卷。

```bash
docker volume create redis-data
docker run -d --name cache -v redis-data:/data redis:8.4 redis-server --appendonly yes
docker exec cache redis-cli CONFIG GET dir
docker exec cache ls -l /data
```

> [!CAUTION]
> **注意内容**：用 docker run 起 Redis 而不挂 /data，是「Redis 重启后数据没了」最常见的原因。容器重建、镜像升级、甚至 docker compose down 都会让可写层里的数据消失，先确认卷挂上了再查其他原因。

**速记**：**/data 声明为卷，RDB 与 AOF 都在其下；不挂卷等于把数据放在随时会消失的可写层**。



### Redis 持久化在容器里的配置

#### RDB 与 AOF 落盘到 /data 的关键参数

**关键参数**：RDB 侧是 save 与 dbfilename，AOF 侧是 appendonly、appendfilename、appenddirname 与 appendfsync。它们都作用于 dir 指向的目录，镜像里默认就是挂卷的 /data。

- **save**：形如 save 60 1，表示 60 秒内至少 1 次写入就触发一次快照；可写多组条件，官方镜像示例用的就是这个参数。
- **dbfilename**：RDB 文件名，默认 dump.rdb，落在 dir 之下。
- **appendonly**：是否开启 AOF，默认关闭；开启后写命令追加到 AOF。
- **appenddirname**：Redis 7 起 AOF 系列文件所在的子目录，默认 appendonlydir，仍在 dir 之下。
- **appendfsync**：刷盘策略，默认 everysec，最多丢约 1 秒；always 最稳最慢，no 交给操作系统。
- **dir**：数据目录，镜像默认 /data；容器场景不要改成容器内不挂卷的路径。

```conf
dir /data
save 900 1
save 300 10
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"
appendfsync everysec
```

> 同时开启 RDB 与 AOF 时，重启只载入 AOF：它通常比 RDB 更完整，RDB 退居备份与重写素材的位置。若两者都不开，Redis 就退化成纯内存缓存，重启即空。

**速记**：**RDB 看 save 与 dbfilename，AOF 看 appendonly、appenddirname 与 appendfsync，全都落在 dir 之下**。



#### 卷的权限与属主

**属主问题**：官方 Redis 镜像默认切换到 redis 用户运行，去掉不必要的能力；若绑定的宿主目录属主是 root，redis 用户写不进去，持久化就会失败。官方镜像自 8.0.2 起会在基本场景下自动纠正数据与配置目录的属主权限，但复杂挂载仍可能出问题。

- **默认运行身份**：镜像默认降权到 redis 用户执行；用 --user 指定用户或设 SKIP_DROP_PRIVS=1 会跳过这一步，但官方不推荐。
- **自动纠偏**：自 8.0.2 起镜像会尝试修正 /data 与配置目录的属主与权限，官方说明它只在基本默认场景下生效。
- **跳过纠偏**：设 SKIP_FIX_PERMS=1 可跳过自动纠偏，适合自己管理权限的场景。
- **手动对齐属主**：官方给出的方法是起一次性容器，对宿主目录执行 chown，把它交给 redis 用户。
- **命名卷更省心**：数据目录优先用命名卷，属主由 Docker 初始化，绕开宿主目录差异。

```bash
docker run --rm -v /your/host/path:/data redis:8.4 chown -R redis:redis /data
docker run -d --name cache -v redis-data:/data redis:8.4 redis-server --appendonly yes
```

> 排查思路仍是老一套：docker exec 进容器执行 id 看运行身份，再到宿主上看目录属主的数字；名字对不上不要紧，数字对不上才是问题。详见篇 7 数据卷与数据持久化。

> [!WARNING]
> **警告内容**：碰上权限报错就把宿主目录改成 777，等于把数据暴露给机器上任意用户。正确顺序是先确认容器进程的 uid，再针对性 chown 或改用命名卷，绝不靠放宽权限绕过。

**速记**：**镜像降权到 redis 用户，宿主目录属主不对就写不进去；优先命名卷，必要时按官方方式 chown**。



#### docker stats 的内存与 maxmemory 的关系

**两个内存概念**：docker stats 显示的 MEM USAGE 是 cgroup 层面的容器内存占用，包含进程 RSS、页缓存与内核记账；Redis 的 maxmemory 是 Redis 自己维护的逻辑上限，只约束它管理的数据与开销。两者相关但不相等，容器限制也不会自动变成 maxmemory。

- **docker stats 的三列**：MEM USAGE 是当前占用，LIMIT 是容器内存上限（对应 -m），MEM% 是二者之比。
- **maxmemory 的来源**：由配置或启动参数显式设定，Redis 不会自动读 cgroup 上限来填这个值。
- **两者的差值**：容器内存里包含 Redis 之外的部分，如客户端缓冲、fork 时的写时复制、页缓存；maxmemory 拿到容器上限的满额就会把这些挤出预算。
- **推荐比例**：maxmemory 留出余量，经验上取容器上限的六到七成，余量留给 fork 与碎片。
- **观测入口**：redis-cli INFO memory 看 used_memory 与 maxmemory，配合 docker stats 看容器侧实际占用。

```bash
docker stats --no-stream cache
docker exec cache redis-cli INFO memory | grep -E 'used_memory:|maxmemory:'
docker exec cache redis-cli CONFIG GET maxmemory-policy
```

> used_memory 与 docker stats 的 MEM USAGE 对不上是常态：前者是 Redis 记账口径，后者是内核 cgroup 口径，差值主要是页缓存、内存碎片与分配器开销。

**速记**：**stats 的 MEM USAGE 是 cgroup 口径、maxmemory 是 Redis 口径；maxmemory 不自动跟随容器上限，要自己设且留余量**。



#### 不设上限的后果：OOM Kill 与退出码 137

**不设 maxmemory 的后果**：Redis 默认 maxmemory 为 0，即不限制自身内存；若同时给容器设了 -m，Redis 会一路涨到容器上限，然后被内核在 cgroup 内 OOM Kill，容器以退出码 137 结束。若连 -m 也不设，风险会从单个容器扩散到整台宿主。

- **被杀的过程**：接近上限时先回收页缓存，回收不足则由 OOM Killer 杀掉容器内的进程，主进程被杀即容器退出。
- **退出码 137**：等于 128 加 9，表示收到 SIGKILL；判断是不是 OOM 要看 docker inspect 的 State.OOMKilled 字段是否为 true，见篇 13 容器资源限制与运行时约束。
- **数据风险**：被强杀时，尚未 fsync 的 AOF 尾部与两次 RDB 之间的增量都会丢失，是否可接受取决于持久化配置。
- **重启策略放大问题**：把内存不足的容器设成 always，会形成「OOM、重启、再 OOM」的循环，既掩盖根因又持续制造负载。
- **正确配置**：maxmemory 设成小于容器上限，并把容器上限设成小于宿主可承受值，三层预算逐级收紧。

```bash
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' cache
docker exec cache redis-cli INFO stats | grep evicted_keys
docker exec cache redis-cli INFO memory | grep maxmemory
```

> [!WARNING]
> **警告内容**：Redis 不会因为跑在容器里就自动遵守容器的内存限制，必须显式设 maxmemory。不设的典型结局是容器被 OOM Kill、退出码 137，且可能丢掉最近一段未落盘的写入。

**速记**：**maxmemory 默认 0、容器有 -m 就会被 OOM Kill；137 要配 OOMKilled 字段定因，三层内存预算逐级收紧**。



### 连接与网络

#### 应用怎么连到数据库：服务名与内部网络

**连接方式**：在 Compose 里，应用应通过**服务名**连接同网络内的数据库，而不是宿主 IP 或 localhost。服务名由 Docker 内嵌 DNS 解析成容器地址，不经过端口发布，也不需要知道对方 IP。

- **服务名即主机名**：数据库服务名 db、缓存服务名 cache，在同一张自建网络内可直接当主机名使用，见篇 9 自定义网络与容器互联。
- **内部网络优于端口发布**：容器之间互通走容器端口，不经过宿主端口映射；少发布一个端口就少一个对外暴露面。
- **连接串写法**：把主机写成服务名，例如 mysql://app:密码@db:3306/shop 与 redis://cache:6379。
- **不写 IP**：容器重建后 IP 会变，写死 IP 的应用会在下次重建后连不上。
- **依赖与就绪**：服务名能解析不代表对方已就绪，启动顺序与等待策略见篇 11 Docker Compose 进阶与实战。

```yaml
services:
  app:
    image: node:24-alpine
    environment:
      DATABASE_URL: mysql://app:app-pass-change-me@db:3306/shop
      REDIS_URL: redis://:cache-pass-change-me@cache:6379/0
    networks:
      - backend
  db:
    image: mysql:8.4
    networks:
      - backend
  cache:
    image: redis:8.4
    networks:
      - backend

networks:
  backend:
```

> 连接串里的主机名是服务名，这一点与裸机部署里填主机域名同构；区别只在于这个名字由 Docker 内嵌 DNS 提供，作用范围仅限同一张网络。

**速记**：**同网络内用服务名当主机名，走容器端口不经过端口发布，永远别写死 IP**。



#### 绝不要把数据库端口发布到公网

**暴露风险**：把 3306 或 6379 发布到 0.0.0.0，等于把数据库直接放到所有网络接口上；Redis 官方镜像还默认关闭保护模式，一旦暴露且无密码，任何人都能连上并读写全部数据。

- **不要写裸端口**：-p 3306:3306 或 -p 6379:6379 会把端口绑到全部接口，可能绕过主机防火墙直达公网。
- **只在开发机绑回环**：需要本机客户端连容器时，写成 127.0.0.1:3306:3306 与 127.0.0.1:6379:6379，只对本机开放。
- **生产不发布**：生产环境让应用与数据库在同一张内部网络上直连，数据库服务根本不写 ports。
- **Redis 的两重防线**：官方镜像文档明确保护模式默认关闭，务必设 requirepass；同时绝不对外发布端口。
- **云主机另查安全组**：发布到宿主后，云安全组与主机防火墙是最后一道闸门，但不应把安全寄托在这一层。

```yaml
services:
  db:
    image: mysql:8.4
    # 生产不写 ports：只在内部网络暴露
    networks:
      - backend
  cache:
    image: redis:8.4
    command: ["redis-server", "--requirepass", "cache-pass-change-me"]
    networks:
      - backend
```

> [!WARNING]
> **警告内容**：把未设密码的数据库端口发布到公网，是历史上大量数据被清空、被勒索的直接原因。数据库端口一律不发布；确有调试需要，只绑 127.0.0.1，并在调试结束后移除。

**速记**：**裸端口等于绑全部接口，开发只绑 127.0.0.1，生产不发布；Redis 保护模式默认关闭，必须设密码**。



#### 用 internal 网络隔离数据面

**internal 网络**：在 Compose 顶层把某张网络声明为 internal，接在该网络上的服务就与外部网络隔离——既不能被外界直接访问，也不能主动出网。把数据面放进 internal 网络，可达范围被压到最小。

- **声明方式**：在网络的 internal 字段写 true，接在该网络的服务即受隔离。
- **隔离效果**：该网络上的容器不能直连外网，也不能被从宿主或外部网络直接访问。
- **典型拓扑**：应用节点同时接入前端网络与 internal 数据网络，只有应用能触达数据库，前端网络中的其他服务不能。
- **与端口发布的关系**：internal 网络上的服务无法发布端口，这与「数据面不暴露」的目标一致。
- **注意副作用**：被隔离的服务若自身需要出网（如下载依赖、连外部认证），要么放到非 internal 网络，要么另接一张网络。

```yaml
services:
  app:
    image: node:24-alpine
    networks:
      - frontend
      - backend
  db:
    image: mysql:8.4
    networks:
      - backend
  cache:
    image: redis:8.4
    networks:
      - backend

networks:
  frontend:
  backend:
    internal: true
```

> internal 网络提供的是网络层的可达性收敛，不是认证：能进入该网络的应用依然能连数据库。应用侧的账号权限与密码仍是必需的第二道防线。

**速记**：**数据面进 internal 网络，进出双向隔离、也不发布端口；可达性收敛不能替代账号密码**。



#### 容器内 localhost 的误区

**localhost 的含义**：localhost 在容器里指的是**容器自身**，不是宿主机。容器内的应用连 127.0.0.1 或 localhost，找的是同一个容器里的进程；要连另一个容器，必须用服务名或容器名。

- **容器有自己的网络栈**：每个容器有独立的网络命名空间与回环接口，localhost 的作用范围仅限该容器。
- **典型的连不上**：宿主上跑 MySQL、容器里应用写 localhost:3306，连的是容器自己，必然连不上。
- **正确写法**：容器间用服务名；容器连宿主上的服务要用宿主在容器网络里的地址，而不是 localhost。
- **MySQL 客户端的另一层坑**：-h localhost 在 Unix 系走 Unix 域套接字，要强制走 TCP 得写 -h 127.0.0.1，见本篇连接一节。
- **排查手段**：容器内用 getent hosts 服务名 验证解析，用 redis-cli -h cache ping 验证连通。

```bash
docker compose exec app sh -c 'getent hosts db && getent hosts cache'
docker compose exec cache redis-cli -h cache ping
```

> [!NOTE]
> **提醒内容**：在容器里 ping 宿主上的 127.0.0.1 没有意义，那是容器自己的回环接口。判断「谁能连到谁」只看网络归属与解析结果，不要凭宿主上的直觉推断。

**速记**：**容器里的 localhost 是它自己；连别的容器用服务名，连宿主不用 localhost，-h localhost 走套接字**。



### 编排两个有状态服务的完整 Compose 文件

#### compose.yaml 全文

**完整示例**：一份文件同时声明应用、MySQL 与 Redis 三个服务：MySQL 与 Redis 各带命名卷、初始化脚本挂载与健康检查，数据面放进 internal 网络，应用通过环境变量接入。健康检查字段的语义见篇 11 Docker Compose 进阶与实战，此处只给可直接运行的完整形态。

```yaml
name: shop

services:
  app:
    image: node:24-alpine
    restart: unless-stopped
    environment:
      DATABASE_URL: mysql://app:app-pass-change-me@db:3306/shop
      REDIS_URL: redis://:cache-pass-change-me@cache:6379/0
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    networks:
      - frontend
      - backend

  db:
    image: mysql:8.4
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root-pass-change-me
      MYSQL_DATABASE: shop
      MYSQL_USER: app
      MYSQL_PASSWORD: app-pass-change-me
      TZ: Asia/Shanghai
    volumes:
      - db-data:/var/lib/mysql
      - ./mysql-conf:/etc/mysql/conf.d:ro
      - ./initdb:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p$$MYSQL_ROOT_PASSWORD"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s
    networks:
      - backend

  cache:
    image: redis:8.4
    restart: unless-stopped
    command: ["redis-server", "/usr/local/etc/redis/redis.conf"]
    environment:
      REDIS_PASSWORD: cache-pass-change-me
    volumes:
      - redis-data:/data
      - ./redis-conf:/usr/local/etc/redis
    deploy:
      resources:
        limits:
          memory: 768M
    healthcheck:
      test: ["CMD-SHELL", "REDISCLI_AUTH=$$REDIS_PASSWORD redis-cli ping | grep -q PONG"]
      interval: 10s
      timeout: 3s
      retries: 10
      start_period: 10s
    networks:
      - backend

volumes:
  db-data:
  redis-data:

networks:
  frontend:
  backend:
    internal: true
```

```conf
# mysql-conf/charset.cnf
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_0900_ai_ci
max_connections = 200
innodb_buffer_pool_size = 256M
default-time-zone = '+08:00'

[client]
default-character-set = utf8mb4
```

```conf
# redis-conf/redis.conf
dir /data
save 900 1
save 300 10
appendonly yes
appendfilename "appendonly.aof"
appenddirname "appendonlydir"
appendfsync everysec
requirepass cache-pass-change-me
maxmemory 512mb
maxmemory-policy allkeys-lru
```

> [!IMPORTANT]
> **重要内容**：示例里的密码是明文占位值，仅用于演示字段写法。真实项目应把口令抽到环境变量文件或 secrets 中，并确保它不被提交进版本库，具体做法见篇 12 环境变量、配置注入与密钥管理。

**速记**：**两服务各带命名卷与健康检查，数据面 internal，应用用环境变量接服务名**。



#### 逐段讲解

**逐段说明**：整份文件可以按「应用段、MySQL 段、Redis 段、顶层声明」四块读，每块都在回答一个具体问题。

- **name**：固定项目名为 shop，容器名前缀与实际卷名（shop_db-data、shop_redis-data）都由它派生。
- **app 的 environment**：主机名写服务名 db 与 cache，端口写容器端口；依赖写成 condition 加 service_healthy，等健康检查通过再启动应用。
- **db 的 environment**：四个初始化变量一次给全，首次初始化时创建 shop 库与 app 用户；TZ 用于让系统时区落到东八区。
- **db 的 volumes**：db-data 保数据，mysql-conf 提供配置片段，initdb 提供初始化脚本；后两者都只读。
- **db 的 healthcheck**：用 mysqladmin ping 探活，地址写 127.0.0.1 强制走 TCP；命令里的双美元符号是 Compose 的转义写法，运行时还原成容器内变量名。
- **cache 的 command 与 volumes**：用配置文件启动，配置目录与数据目录分别挂载；数据目录必须挂在卷上。
- **cache 的 deploy.resources**：单机下 Compose 会采纳的正是 limits 部分，给 Redis 设容器内存上限，与 redis.conf 里的 maxmemory 形成两层预算。
- **顶层 volumes 与 networks**：声明两个命名卷与两张网络，backend 声明 internal 实现数据面隔离。

> mysqladmin ping 的语义要看清：官方文档说明只要服务器在运行它就返回 0，**即使因为拒绝连接（如 Access denied）而报错也一样**。所以探针要带上凭据，才能把「服务器活着」和「账号可用」分开确认。

**速记**：**应用段接服务名、MySQL 段四个变量加三类挂载、Redis 段配置加数据卷、顶层声明卷与 internal 网络**。



#### 首次启动与初始化日志

**首次启动流程**：先校验文件，再后台启动，然后用 ps 与 logs 观察初始化是否走完，最后进入客户端核对。首次启动比后续慢，因为要初始化数据目录、执行初始化脚本。

- **第一步校验**：docker compose config --quiet 只校验语法与插值，不启动容器。
- **第二步启动**：docker compose up -d 在后台创建并启动全部服务。
- **第三步观察状态**：docker compose ps 看到 db 与 cache 从 starting 变为 healthy，应用才可能正常起来。
- **第四步看初始化日志**：docker compose logs db 里能看到入口脚本执行初始化 SQL 的输出；Redis 的日志则能看到加载 AOF 或 RDB 的记录。
- **第五步进客户端核对**：在 MySQL 里 SHOW DATABASES 确认 shop 存在，在 Redis 里 INFO persistence 确认持久化状态。

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs -f --tail=100 db
docker compose exec db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW DATABASES; USE shop; SHOW TABLES;"
docker compose exec cache redis-cli -a "$REDIS_PASSWORD" INFO persistence | head -20
```

> 首次启动时若 db 长时间停在 starting 或反复重启，先看 logs 里入口脚本的报错，再按本篇初始化失败一节处理；不要一上来就怀疑网络或应用。

**速记**：**config 校验、up 启动、ps 看健康、logs 看初始化、exec 进客户端核对**。



#### 优雅停止、保留数据与彻底清除

**三种停止方式**：stop 最温和，只停容器；down 额外删容器与网络但保留命名卷；down -v 连命名卷一起删，即删除数据。三者的破坏力依次递增，日常重启前两者足矣。

- **docker compose stop**：停止容器，容器与网络、卷全部保留，详见篇 10 的 stop 与 start 成对使用。
- **docker compose down**：停止并移除容器与网络，命名卷默认保留，下次 up 沿用旧数据。
- **docker compose down -v**：额外移除顶层声明的命名卷与容器附着的匿名卷，属不可逆的数据丢失。
- **docker volume prune**：默认只清匿名卷，加 -a 才连未被引用的命名卷一起清。
- **保留数据的验证**：down 之后再 up，MySQL 里既有数据仍在，就说明卷与数据都被正确保留。

```bash
docker compose stop
docker compose down
docker compose up -d
docker compose exec db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT COUNT(*) FROM shop.orders;"

docker compose down -v
docker volume ls
```

> [!WARNING]
> **警告内容**：docker compose down -v 会删除命名卷，数据库数据与缓存内容随之消失且不可恢复。执行前先确认三件事：卷里是不是重要数据、有没有最近验证过的备份、是否真的需要删卷，任何一项存疑就不要加 -v。

**速记**：**stop 留容器、down 留卷、down -v 连数据一起删；日常重启只用前两个**。



### 备份与恢复的完整流程

#### 定时导出加异地保存的步骤清单

**可执行清单**：把备份拆成「导出、校验、归档、异地、演练」五个动作，固定成脚本并纳入定时任务，才算一套能落地的流程。每一步都要有明确的成功判据，而不是「命令没报错就算成功」。

- **导出**：定时对每个库执行一致性逻辑导出，产物带日期与库名。
- **校验**：检查文件非空、末尾完整，必要时在临时实例里试导入，验证备份本身可用。
- **归档**：保留至少两个完整周期，按合规要求延长；过期清理要有明确规则，不能靠手工。
- **异地**：把副本传到另一台机器或对象存储，卷与备份同机等于没备份。
- **演练**：按季度在隔离环境恢复一次，记录耗时与问题，把恢复步骤固化成脚本。

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%Y%m%d-%H%M)
OUT=/srv/backup/mysql

docker exec db sh -c 'exec mysqldump --single-transaction --routines --triggers \
  -uroot -p"$MYSQL_ROOT_PASSWORD" shop' > "${OUT}/shop-${STAMP}.sql"

test -s "${OUT}/shop-${STAMP}.sql"
gzip -f "${OUT}/shop-${STAMP}.sql"
ls -lh "${OUT}/shop-${STAMP}.sql.gz"
```

> 时钟与文件名约定很重要：脚本用同一套时间戳格式，校验与清理脚本才能按名字识别产物；否则一段时间后没人知道哪个文件是最新的。

**速记**：**导出、校验、归档、异地、演练五步走，产物带时间戳，清理有规则**。



#### 两种定时备份做法

**两种做法**：其一是在**宿主机**上用 cron 调 docker exec，简单直接；其二是用**一次性容器**在 Compose 网络里执行，宿主上不需要装数据库客户端。两者都需要宿主侧保留产物。

- **宿主机 cron**：脚本里用 docker exec 进运行中的数据库容器执行导出，重定向到宿主目录；前提是容器在跑。
- **一次性容器**：用 docker run --rm 挂输出目录并接入数据库网络，适合宿主没有 mysqldump 客户端、或想把备份逻辑与宿主解耦的场景。
- **Compose 场景**：用 docker compose run --rm 复用服务配置，省去手写网络名与环境变量的麻烦。
- **失败要告警**：定时任务失败必须能被发现，否则「连续几个月没备份成功」是常见事故。
- **与保留策略配合**：备份脚本要同时处理过期清理，不然磁盘会被备份撑满。

```bash
# crontab：每天 02:30 执行备份脚本
30 2 * * * /srv/backup/mysql-backup.sh >> /var/log/mysql-backup.log 2>&1
```

```bash
# 一次性容器做法：接入数据网络并把结果写到宿主目录
docker run --rm --network shop_backend -v /srv/backup/mysql:/backup mysql:8.4 \
  sh -c 'exec mysqldump --single-transaction -h db -uroot -p"$MYSQL_ROOT_PASSWORD" shop \
  | gzip > /backup/shop-$(date +%Y%m%d-%H%M).sql.gz'
```

> 定时备份的敌人不是命令难写，而是「没人确认它还在跑」。把失败告警接进监控，把最后一次成功时间作为告警指标，比每周人工检查可靠得多。

**速记**：**宿主 cron 用 exec、解耦用一次性容器、Compose 用 run --rm；失败必须告警**。



#### 验证备份可用性的最小操作

**最小验证**：把最新备份导入一个干净实例，再核对关键表行数与字符集。这是「备份可用」的最低证据链，十分钟内可完成，应在每次备份策略变更后与每季度演练时执行。

- **起干净实例**：用同大版本镜像起一个临时容器，配一个空的命名卷。
- **导入**：把备份喂给 mysql 客户端，观察是否有报错。
- **核对**：确认库表清单、关键表行数、字符集与排序规则与源库一致。
- **记录**：记下恢复耗时，作为 RTO 的实测值。
- **清理**：验证完成后删除临时容器与临时卷，避免长期占用资源。

```bash
docker run -d --name drill-mysql -e MYSQL_ROOT_PASSWORD=drill-pass \
  -e MYSQL_DATABASE=shop mysql:8.4

gunzip -c /srv/backup/mysql/shop-20260912-0230.sql.gz \
  | docker exec -i drill-mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" shop'

docker exec drill-mysql mysql -uroot -pdrill-pass \
  -e "SELECT COUNT(*) AS orders FROM shop.orders; SHOW VARIABLES LIKE 'character_set_server';"
docker rm -f drill-mysql
```

> [!TIP]
> **建议内容**：把恢复演练写成脚本并纳入定期任务，演练失败要能自动告警。演练的产出不是「数据能恢复」这句话，而是一份记录的耗时与核对的数字，它们才是灾难当天可以依赖的东西。

**速记**：**起干净实例、导入、核对行数与字符集、记耗时、清临时资源**。



### 常见坑清单

#### 初始化变量失效：数据目录非空

**成因**：初始化变量只在数据目录为空时生效。卷里已有数据时改了 MYSQL_PASSWORD 或 MYSQL_DATABASE，入口脚本会整体忽略这些变量，新旧密码都不会报错。

- **现象**：改了密码后旧密码仍能登录，新密码无效；或新建的库名没有出现。
- **定位**：确认数据目录是否非空，是不是复用了旧卷。
- **正解**：确需重建时，先备份、清空数据目录再启动；日常改密码应进库执行 ALTER USER，而不是改环境变量。
- **不要删卷了事**：删卷等于删数据，顺序永远是先备份。

> [!CAUTION]
> **注意内容**：环境变量不是运行期开关，改它不会改动已有库里的账号。把「改 MYSQL_PASSWORD 重建容器」当成改密码的手段，会导致既没改成密码、又差点误删数据。

**速记**：**变量只在空目录生效，非空即静默忽略；改密码进库 ALTER，不要改环境变量**。



#### 卷权限导致启动失败

**成因**：容器内进程以固定用户运行，宿主目录属主与之不匹配时写入被拒，表现为启动报 Permission denied；MySQL 与 Redis 的属主差异是典型来源。

- **MySQL**：镜像内部以固定用户运行，绑定宿主空目录时属主不匹配会启动失败，报 Can't create/write to file。
- **Redis**：镜像默认降权到 redis 用户，宿主目录属主不是 redis 时持久化失败；自 8.0.2 起镜像会尝试自动纠偏基本场景。
- **定位**：docker exec 进容器执行 id 看运行身份，再到宿主 ls -ln 看目录属主的数字。
- **正解**：优先用命名卷；必须绑定时按官方方式 chown 到容器进程身份。
- **禁止**：不要把目录改成 777。

**速记**：**先看进程 uid、再看目录属主数字；优先命名卷，必要时 chown，绝不放宽到 777**。



#### 容器时区导致时间字段错乱

**成因**：容器系统时区默认通常是 UTC，MySQL 若保持 time_zone 为 SYSTEM，就会跟随容器时区；应用按本地时间写入而数据库用 UTC 解释，时间字段随之整体错位。

- **现象**：NOW() 与业务时间差八小时，时间戳字段比预期早或晚。
- **两层来源**：操作系统时区（容器环境）与 MySQL 的 time_zone（会话或全局变量）分别影响结果。
- **统一办法**：给容器注入 TZ 环境变量，并在 MySQL 配置里显式设 default-time-zone 为一个固定偏移或时区名，双管齐下最稳。
- **客户端也要对齐**：JDBC 等驱动的时区参数应与服务端一致，否则连接层又会换算一次。
- **验证**：进库执行 SELECT NOW(), @@global.time_zone, @@system_time_zone; 分别看会话时间与两级时区变量。

```bash
docker exec db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "SELECT NOW(), @@global.time_zone, @@system_time_zone;"
```

> 只设 TZ 或只设 default-time-zone 都可能被另一层抵消：TZ 影响系统时区，default-time-zone 影响会话与全局变量，两者都固定下来才不会有空隙。

**速记**：**容器默认 UTC，MySQL 的 SYSTEM 跟随它；TZ 与 default-time-zone 一起设，客户端时区也要对齐**。



#### 字符集不是 utf8mb4 引发报错

**成因**：表或连接字符集不是 utf8mb4 时，四字节字符（如表情符号）写入会报 Incorrect string value。库的字符集来自服务端默认值或建库时的显式指定，连接字符集则来自客户端设置，两处都要对。

- **报错特征**：Incorrect string value: 后跟一串十六进制转义，指向具体列。
- **服务端对齐**：设 character-set-server 与 collation-server 为 utf8mb4 与 utf8mb4_0900_ai_ci；MySQL 8.0 起这两项默认即为该值。
- **连接侧对齐**：客户端段设 default-character-set 为 utf8mb4，应用连接串也带上字符集参数。
- **存量库转换**：已有表若为 utf8mb3 或 latin1，需要显式转换表与列的字符集，转换前先备份。
- **验证**：SHOW VARIABLES LIKE 'character_set%'; 与 SHOW CREATE TABLE 某表 逐项核对。

```bash
docker exec db mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "SHOW VARIABLES LIKE 'character_set%'; SHOW VARIABLES LIKE 'collation%';"
```

> utf8 在 MySQL 里是 utf8mb3 的别名，最多三字节，存不了表情；要四字节必须写 utf8mb4。这是命名造成的长期误解，排查字符集问题先确认看到的是哪一个。

**速记**：**服务端与连接端都要 utf8mb4；utf8 是 utf8mb3 的别名，存不了表情**。



#### 数据目录挂到宿主目录：非空即跳过初始化

**成因**：初始化判定只看数据目录是否为空。绑定宿主目录时，若目录里混入任何文件（例如 macOS 上生成的 .DS_Store、某些卷根部的 lost+found），入口脚本会判定为「已有数据」，跳过初始化，容器随后因缺少系统表启动失败。

- **现象**：初始化脚本一条都没跑，容器却起来了或起不来，库是空的或报系统表缺失。
- **判定口径**：入口脚本按目录是否为空决定是否初始化，不识别文件是不是「真正的数据」。
- **规避**：优先用命名卷；必须绑定宿主目录时，确保目录干净且为空，或仅在必要时清空后重建。
- **排查**：docker exec 进容器 ls -la /var/lib/mysql 看目录里到底有什么。
- **与上一坑的区别**：这一坑是「不该有的文件让初始化被跳过」，初始化变量失效那一坑是「初始化跑过了但变量被忽略」，两者现象不同。

```bash
docker exec db ls -la /var/lib/mysql | head
```

> [!NOTE]
> **提醒内容**：宿主目录里被系统或工具悄悄塞进一个隐藏文件，就足以让 MySQL 的初始化判定翻转。数据库数据目录优先用命名卷，正是为了避开这类宿主侧的不确定性。

**速记**：**初始化只认「目录是否为空」，混入任何文件就跳过；数据目录优先命名卷**。



#### 用 latest 标签被动升级

**成因**：用 latest 或宽泛标签时，某次 docker pull 之后再重建容器，会静默换上新的数据库大版本，触发一次未经计划、未经备份的数据目录升级。

- **现象**：一次例行重建后数据库版本变了，数据目录被升级，回滚无路。
- **根因**：latest 随上游漂移，重建时才生效，问题在事后才暴露。
- **正解**：mysql 与 redis 都固定到具体版本或 LTS 标签，例如 mysql:8.4、redis:8.4；升级时显式改标签，并按升级一节走流程。
- **配套**：把镜像版本写进版本库，让变更可评审、可追溯；配合篇 15 的标签规范。
- **核对**：进库执行 SELECT VERSION(); 确认实际运行版本与预期一致。

**速记**：**latest 会随上游漂移、重建即被动升级；数据库镜像一律固定版本标签**。



#### Redis 重启后数据没了的排查顺序

**排查顺序**：先确认卷挂没挂，再确认持久化开没开，再确认 dir 指向，最后看数据是否真丢。绝大多数「数据没了」其实是三件事之一：没挂卷、没开持久化、或容器被连卷一起删。

- **第一看挂载**：docker inspect 看 Mounts，确认 /data 挂在命名卷上而不是匿名卷或根本没挂。
- **第二看持久化开关**：CONFIG GET appendonly 与 CONFIG GET save，确认落盘方式真的开着。
- **第三看目录**：CONFIG GET dir 确认是 /data；再看 /data 下有没有 dump.rdb 或 appendonlydir。
- **第四查删除动作**：是否执行过 docker compose down -v、docker volume prune -a，或是否用了 --rm 带走了匿名卷。
- **第五区分丢失与窗口**：只开 RDB 时崩溃会丢最近写入，这不是数据全没，而是丢失窗口；用 INFO persistence 与持久化章节的指标判断。
- **第六看是否被 OOM 杀**：137 退出且 OOMKilled 为 true 时，尾部未 fsync 的数据会丢。

```bash
docker inspect -f '{{json .Mounts}}' cache
docker exec cache redis-cli CONFIG GET dir
docker exec cache redis-cli CONFIG GET appendonly
docker exec cache redis-cli INFO persistence | head -20
docker exec cache ls -l /data
```

> [!WARNING]
> **警告内容**：把「数据没了」直接归因为 Redis 故障，往往会漏掉真正原因——卷被 down -v 或 prune 删掉了。先按顺序确认挂载、开关、目录与删除动作，再谈数据能不能找回。

**速记**：**先看挂载、再看开关、再看 dir、再查删卷动作，最后区分丢失与丢失窗口**。
