## 核心概念：镜像、容器与仓库

### 镜像

#### 镜像的定义与两条不可动摇的性质

**镜像（Image）**：是只读的、分层组织的应用与运行环境模板，把运行一个程序所需的文件、二进制、库与配置打包成一个可按内容寻址的制品。

- **不可变**：镜像一经构建即不可修改，任何改动只能叠加为新层并派生出新镜像。
- **分层**：镜像由若干层组成，每一层代表一组文件系统变更，即对文件的添加、删除与修改。
- **不可运行**：镜像只是模板，自身没有进程，必须由容器把它变成运行态。
- **可分发**：镜像可被打标签、推送到仓库，并在任意装了 Docker 的机器上拉取运行。

> 官方文档 docs.docker.com 的 get-started 章节「What is an image?」把镜像定义为「包含运行容器所需全部文件、二进制、库与配置的标准化打包产物」，并列出两条首要性质：镜像是不可变的、镜像由层组成。本系列后续所有讨论都建立在这两条性质之上。

**速记**：**镜像是只读模板，性质两条——不可变、分层**。



#### 镜像的三段构成：层文件、镜像配置与清单

**镜像的三段构成**：一个镜像在存储中并非单个文件，而是由**层文件**、**镜像配置**、**清单与索引**三类对象通过摘要互相引用组成的一张有向图。

- **层文件（layer blob）**：每层是一组文件系统变更，通常以压缩的 tar 形式存放，靠自身摘要寻址；多层按顺序叠加成最终根文件系统。
- **镜像配置（image config）**：一份 JSON，记录环境变量、入口命令、工作目录、暴露端口、构建历史以及各层的 diff_id，它描述「这堆层该怎么运行」。
- **清单（manifest）**：一份小 JSON，列出该平台镜像配置的摘要与全部层的摘要和大小，把配置与层串成一个整体。
- **索引（index，Docker 旧称 manifest list）**：列出同一标签下各平台（如 linux/amd64 与 linux/arm64）各自的清单摘要，供客户端按架构挑选。

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "size": 7023,
    "digest": "sha256:b5b2b2c507a0944348e0303114d8d93aaaa081732b86451d9bce1f432a537bc7"
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "size": 32654,
      "digest": "sha256:9834876dcfb05cb167a5c24953eba58c4ac89b1adf57f28f2f9d09af107ee8f0"
    }
  ]
}
```

- **观察点**：清单里只写摘要与大小，不写文件内容，因此一份清单就能代表整个镜像的全部内容。
- **实践线索**：docker image history 展示的是层与层的构建历史，docker inspect 的 RootFS 段展示的是各层 diff_id，两者分别对应上面的第二段与第一段。

> 三层对象的媒体类型前缀不同：OCI 用 application/vnd.oci.image.*，Docker 旧格式用 application/vnd.docker.*。二者内容等价，客户端可互通，差别只在类型字符串，不要因为看到两套类型名而怀疑镜像损坏。

**速记**：**层放内容、配置定运行、清单串全部、索引挑平台**。



#### 镜像 ID 与 digest 的分工

**镜像 ID（Image ID）**：是镜像配置 JSON 的散列，也是本地 docker image ls 中 IMAGE ID 一列的值，它标识「内容相同的一份镜像」。**摘要（digest）**：是清单内容的散列，写为 sha256: 加 64 位十六进制，它是镜像的内容寻址标识，可在 NAME@sha256:... 形式的引用里精确定位一份镜像。

- 两者是不同文档的散列，因此同一镜像的镜像 ID 与 digest 通常不相等，这是常见困惑的来源。
- **镜像 ID 认内容**：只要层与配置不变，重新导出与推送都应得到相同的镜像 ID。
- **digest 认清单**：清单里记录了配置摘要与层摘要，任何一处变化都会向上传播，最终改变清单本身的散列。
- **可用性差异**：digest 可以直接写进 docker pull 的引用中，镜像 ID 不能，因为仓库按清单索引内容而非按配置。

```bash
docker image ls --no-trunc            # IMAGE ID 列即镜像配置的散列
docker image ls --digests             # DIGEST 列即清单摘要
docker inspect --format '{{.Id}}' nginx
docker inspect --format '{{.RepoDigests}}' nginx
```

> 多平台镜像还有第三个散列：索引摘要。docker pull 输出里的 Digest 可能取自索引，而 docker image ls 的 IMAGE ID 始终取自配置，两者来源于不同层级的 JSON，比较它们是否相等没有意义。

> [!NOTE]
> **提醒内容**：判断「两次构建是不是同一份镜像」时看镜像 ID；判断「拉到的字节是否与上一次完全相同」时看 digest。前者验证解压后的内容，后者验证传输中的清单与压缩层，两个问题不能混用一个标识回答。

**速记**：**镜像 ID 是配置的散列，digest 是清单的散列；前者认内容，后者认字节**。



#### tag 与 digest：可变指针与不可变标识

**标签（tag）**：是仓库内指向某个 digest 的可变名字，形如 nginx:1.29 中的 1.29，它是一层间接引用，可以被重新指向别的清单。**摘要（digest）**：是内容自身的散列，指向哪份字节由算法决定，无法被重新指向。

- **tag 可移动**：重复推送同一标签会改写映射，旧清单仍可按自己的 digest 取回，直到被回收。
- **digest 不可移动**：客户端拉到字节后会重新计算散列，与请求不符即校验失败，因此同一 digest 永远对应同一份字节。
- **latest 无特殊语义**：它只是引用中省略标签时的默认值，不代表最新，也不代表稳定。
- **工程含义**：生产部署与基础镜像应锁 digest，日常手工操作看标签足够。

```dockerfile
# 可读但可移动：同一次构建在不同时间可能拉到不同内容
FROM node:24-alpine

# 精确且不可移动：适合生产与需要可复现的构建
FROM node:24-alpine@sha256:2e863c44b718727c860746568e1d54afd13b2fa71b160f5cd9058fc436217b30
```

> [!WARNING]
> **警告内容**：把 latest 当作版本约束是典型的踩坑来源。配置发布流水线用 latest，等于让每次部署拉到什么内容取决于推送时间与缓存，回滚时也无法复现上一版；需要可复现就必须固定标签或直接固定 digest。

**速记**：**tag 是可变指针，digest 是内容地址；latest 只是默认值，生产要锁 digest**。



### 命名规则

#### 完整形态的五个字段

**镜像引用（image reference）**：定位一份镜像的完整写法由**仓库主机**、**命名空间**、**仓库名**、**标签**、**摘要**五段构成，除仓库名外每段都可省略，省略即取默认值。

- **仓库主机（registry host）**：存放该镜像的仓库服务地址，可带端口，如 docker.io、ghcr.io、myregistry.local:5000。
- **命名空间（namespace）**：仓库主机下的一级分组，通常是用户名或组织名，如 library、bitnami、yourteam。
- **仓库名（repository）**：命名空间下的一组相关镜像的名字，如 nginx、node、my-app。
- **标签（tag）**：仓库名内指向某个清单的可变名字，前接半角冒号。
- **摘要（digest）**：清单的散列，前接半角 at 符号，可与标签同时出现，实际解析以摘要为准。

```text
[仓库主机[:端口]/]命名空间/仓库名[:标签][@摘要]

docker.io         /  library  /  nginx  :  1.29  @  sha256:...
  主机                命名空间     仓库名    标签        摘要
```

> 五段并非随意拼接：仓库主机与命名空间之间、命名空间与仓库名之间用斜杠连接，标签与摘要紧贴仓库名，二者都没有斜杠。斜杠数量由命名空间是否嵌套决定，Docker Hub 与多数公有仓库只允许一级命名空间。

**速记**：**主机、命名空间、仓库名、标签、摘要——五段各司其职，只有仓库名不可省**。



#### 省略时的默认值

**默认规则**：省略仓库主机补 **docker.io**，省略官方镜像的命名空间补 **library**，省略标签补 **latest**；摘要永不自动补，提供了摘要即以摘要解析。

- **默认仓库主机**：Docker 官方公共仓库 Docker Hub，其服务端 API 端点实际为 registry-1.docker.io，引用中写 docker.io 即可。
- **默认命名空间**：仅当仓库名属于官方镜像时自动补 library，用户仓库不会补，必须显式写自己的命名空间。
- **默认标签**：省略时不报错，静默使用 latest 并打印 Using default tag: latest。
- **端口**：仓库主机为 5000 等非标准端口时必须写出，标准端口 443 与 80 可省略。
- **摘要优先**：同时写标签与摘要时，解析以摘要为准，标签只作展示。

> [!IMPORTANT]
> **重要内容**：官方镜像自动补 library 是「省略命名空间」这一条规则的唯一适用场景。写 nginx 会被补成 library/nginx，写 yourname/app 不会被补，若此时也自动补 library 就会指向一个并不存在的官方仓库，因此用户镜像必须自带命名空间。

**速记**：**省略主机补 docker.io，省略命名空间只对官方镜像补 library，省略标签补 latest**。



#### 常用写法展开对照

**展开方法**：把日常缩写逐段补齐，即可得到仓库中真实存在的完整引用；下面每一行左边是常用写法，右边是它实际指的镜像。

```text
nginx
  -> docker.io/library/nginx:latest

nginx:1.29
  -> docker.io/library/nginx:1.29

ubuntu@sha256:2e863c44b718727c860746568e1d54afd13b2fa71b160f5cd9058fc436217b30
  -> docker.io/library/ubuntu@sha256:2e863c44b718727c860746568e1d54afd13b2fa71b160f5cd9058fc436217b30

bitnami/nginx:latest
  -> docker.io/bitnami/nginx:latest

ghcr.io/owner/app:v1.2.0
  -> ghcr.io/owner/app:v1.2.0    （主机已显式写出，无省略）

myregistry.local:5000/team/api:dev
  -> myregistry.local:5000/team/api:dev
```

- **能省则省**：日常操作写 nginx、node:24-alpine 即可，守护进程会自动补全并打印完整名。
- **显式写出**：切换仓库主机、使用非官方命名空间或固定 digest 时，必须把对应段写全。
- **保留半角**：引用中的斜杠、冒号、at 符号一律半角，因为它们处在标识符内部而非中文行文之间。
- **验证手段**：docker pull 的输出末尾会回显归一化后的完整名，用它核对是否拉错了目标。

> 易混点：docker.io 是仓库主机名，registry-1.docker.io 是其后端 API 域名；引用里写 docker.io/library/nginx 是正确的，写 registry-1.docker.io/library/nginx 也能连通但属于绕过别名的非标准写法，日常不建议使用。

**速记**：**缩写靠规则补全，切主机与用摘要时写全；拉取输出回显的完整名就是标准答案**。



### 容器

#### 容器的定义：镜像加一层可写层

**容器（Container）**：是在镜像的只读层之上叠加一层**容器可写层**后启动的进程实例，是可写层、进程与一组运行时配置的合称。

- **运行态**：容器等于「镜像 + 可写层 + 一个正在运行的进程」，镜像提供底座，进程提供行为。
- **可写层**：容器创建时在镜像顶层之上追加的一个空层，容器内所有写入都落在这一层。
- **元数据**：守护进程为容器保存一份配置与状态记录，包含网络、挂载、日志驱动、重启策略等。
- **可并存**：同一个镜像可以启动任意多个容器，它们共享同一份只读层，各自拥有独立的可写层。

```bash
docker run -d --name web nginx      # 同一镜像
docker run -d --name web2 nginx     # 可再起一个互不干扰的容器
docker ps --format '{{.Names}} {{.Image}} {{.Status}}'
```

> 容器与镜像的关系是实例与模板的关系：模板只读且只有一份，实例可写且可无限复制。删除容器时被丢弃的只是它的可写层与元数据，镜像层始终不动。

**速记**：**容器等于镜像加一层可写层再加一个进程；模板一份，实例任意多**。



#### 容器不是虚拟机，而是被隔离的一组进程

**本质判断**：容器不是一台机器，而是被内核的**命名空间**与**控制组**约束后运行在宿主机上的一组普通进程，在宿主机上 ps 就能看见它们。

- **共享内核**：容器与宿主机、容器与容器共用同一个内核，容器内没有独立内核。
- **宿主可见**：宿主机上的进程表里能看到容器进程，只是它们处在不同的命名空间中。
- **无硬件模拟**：没有 Hypervisor，没有虚拟设备，容器本质上是带视图隔离与资源配额的进程。
- **启动开销**：创建一个容器接近于 fork 一个进程并切换命名空间，因此是毫秒到秒级。

```bash
# 在宿主机上直接观察容器进程
docker run -d --name web nginx
ps -ef | grep nginx
docker top web
```

> [!NOTE]
> **提醒内容**：把容器当虚拟机用会出现两类误判：一是试图在容器里换内核或装内核模块，注定失败；二是以为容器提供了硬件级安全边界，从而放开了本应有的多租户防护。容器边界是内核级的，强度弱于虚拟机，相关风险见第 16 章。

**速记**：**容器是被隔离与限制的一组进程，共享宿主内核，宿主 ps 可见**。



#### 容器内 PID 1 的特殊地位

**PID 1**：是容器内第一个被启动的进程，镜像的入口命令通常就成为它，它承担信号接收与孤儿进程回收两项特殊职责，其生死直接决定容器的生死。

- **生命周期绑定**：PID 1 退出，容器即进入 exited 状态，可写层与元数据保留但进程不再运行。
- **信号语义**：docker stop 先向 PID 1 发送 SIGTERM，若它在默认超时内未退出，再补发 SIGKILL，退出码为 137。
- **僵尸回收**：命名空间内 PID 1 还须回收被它收养的孤儿进程，否则会累积僵尸进程。
- **不转发信号**：若入口是 shell 脚本且未用 exec 启动真正的主程序，SIGTERM 会发给 shell 而主程序收不到，表现为停止要等满超时才被杀。

```dockerfile
# 用 exec 形式让主程序直接成为 PID 1
CMD ["node", "server.js"]

# 反例：主程序被 shell 包住，信号到不了它手上
CMD node server.js
```

> [!CAUTION]
> **注意内容**：Dockerfile 的 CMD 与 ENTRYPOINT 一律用 exec 数组形式，让应用自身成为 PID 1 并处理 SIGTERM；用 shell 形式会把应用藏在 sh 之下，停止时只能靠 SIGKILL 强杀，正在处理的请求与未落盘的数据都会丢失。

**速记**：**PID 1 死则容器死，它要收信号、收孤儿；入口用 exec 形式，别让 shell 挡在中间**。



#### 可写层的归宿：容器删除即消失

**可写层的生命周期**：容器可写层与容器同生共死，docker rm 删除容器时它一并被清除，其中的数据不可恢复。

- **默认不持久**：不挂载卷时，容器内新增或修改的文件只存在于可写层，删除容器即丢失。
- **镜像不受影响**：可写层的写入不回流到只读的镜像层，因此删除容器不会破坏镜像。
- **其他容器不受影响**：每个容器各有可写层，一个容器内的改动对同镜像的其他容器不可见。
- **外置才有持久性**：需要留存的数据必须放在卷或绑定挂载上，那部分由宿主机或卷驱动管理，不随容器删除。

```bash
docker run --name c1 -d nginx
docker exec c1 sh -c 'echo hello > /tmp/marker'
docker rm -f c1
docker run --name c2 -d nginx
docker exec c2 cat /tmp/marker        # 报文件不存在，可写层已随 c1 消失
```

> [!WARNING]
> **警告内容**：把数据库、上传文件或任何有价值的数据只放在容器可写层，删除或重建容器就是一次不可逆的数据丢失。容器编排器会因扩缩容、更新、故障随时替换容器，可写层从来不是可靠存储，持久化方案见第 7 章。

**速记**：**可写层随容器生灭，删容器即删数据；要留存就挂卷**。



### 隔离与限制机制概览

#### namespaces：视野隔离

**命名空间（namespace）**：是 Linux 内核提供的一组隔离机制，让一组进程看到独立的进程、网络、挂载、主机名等视图，彼此看不到对方。按 Linux 内核文档（namespaces(7) 手册页），共 8 种。

- **PID**：进程编号视图，容器内 PID 从 1 开始，看不到宿主与其他容器的进程。
- **Network**：网络设备、协议栈、路由表与端口，容器因此拥有独立 IP 与端口空间。
- **Mount**：挂载点视图，容器看到自己的根文件系统与挂载表。
- **UTS**：主机名与域名，让容器拥有自己的 hostname。
- **IPC**：System V IPC 与 POSIX 消息队列，隔离进程间通信对象。
- **User**：用户与组 ID 映射，可在容器内是 root 而宿主上是普通用户。
- **Cgroup**：控制组根目录视图，隐藏宿主上的 cgroup 层级。
- **Time**：启动时钟与单调时钟，可让容器看到不同的时钟偏移。

```bash
# 查看某容器进程的各类命名空间编号
docker inspect --format '{{.State.Pid}}' web
ls -l /proc/<PID>/ns/
```

> 命名空间只提供「视野隔离」，不提供资源上限。容器能看到独立视图，但仍可能与邻居争抢 CPU 与内存，这类限制由下一项机制负责。8 种命名空间的启用细节与实现见第 4 章。

**速记**：**namespace 管视野：PID、NET、MNT、UTS、IPC、USER、CGROUP、TIME 八种**。



#### cgroups：资源限制

**控制组（cgroup）**：是 Linux 内核提供的资源计量与限制机制，按组统计并限制 CPU、内存、块设备 IO 与进程数等资源，容器是其典型使用场景。

- **限制**：为组设定内存上限、CPU 配额等硬性边界，超限被限流或杀死。
- **计量**：统计组内资源用量，docker stats 展示的数据即来源于此。
- **优先级**：在多组争抢时按权重分配，属于相对份额而非绝对值。
- **版本**：cgroup v1 与 v2 两代并存，多数现代发行版已默认 v2，Docker 由 systemd 驱动管理。

> 内存超限时内核会触发 OOM Kill，进程以退出码 137 结束；这与 docker stop 超时后补发 SIGKILL 得到的 137 是同一个数字、不同来源。区分方法是看 docker inspect 的 State.OOMKilled 字段。

> [!NOTE]
> **提醒内容**：命名空间与 cgroup 常被并称，职责却相反：前者决定「看得见什么」，后者决定「能用多少」。容器「快而轻」来自命名空间的低开销，容器「可控」来自 cgroup 的硬边界，两者缺一不可。

**速记**：**cgroup 管用量：限制、计量、优先级，超内存会被 OOM Kill**。



#### capabilities：拆分的 root 权限

**能力（capability）**：是 Linux 把 root 的单一特权拆成的一组细粒度权限项，如 CAP_NET_BIND_SERVICE、CAP_CHOWN、CAP_SYS_ADMIN、CAP_NET_RAW，容器通过只保留所需能力来削弱特权。

- **默认丢白名单**：Docker 默认丢弃绝大多数能力，仅保留运行常见程序所需的一组，采用允许列表而非拒绝列表。
- **典型可禁行为**：挂载文件系统、访问原始套接字、创建设备节点、修改文件属主、加载内核模块。
- **按需追加**：需要额外能力时用 --cap-add 显式追加，用 --cap-drop 进一步收紧。
- **比 root 更细**：容器内可以是 root，但只持有被保留的能力，危害面小于宿主上的完整 root。

```bash
docker run -d --name web --cap-drop ALL --cap-add NET_BIND_SERVICE nginx
docker inspect --format '{{.HostConfig.CapDrop}} {{.HostConfig.CapAdd}}' web
```

> 实践口径：非必要不追加能力；确实需要某项时，先确认能否用更小的能力替代，而不是直接 --privileged。--privileged 会放开几乎所有限制，等同于把宿主交给容器，属高风险开关，详见第 16 章。

**速记**：**capability 把 root 拆成细项，默认丢白名单；要权就按项加，别开 privileged**。



#### seccomp 与 LSM：系统调用与访问控制的过滤

**seccomp**：是内核的系统调用过滤机制，通过加载过滤策略决定进程可调用哪些系统调用，Docker 默认启用一份允许列表策略。**LSM（Linux Security Modules）**：是内核的强制访问控制框架，常见实现为 AppArmor 与 SELinux，按路径与标签约束程序可访问的资源。

- **seccomp 管调用**：在系统调用入口处裁决，禁用如部分提权或已废弃的危险调用。
- **LSM 管访问**：在文件、进程、网络等对象上做强制策略，即使程序有权限也未必能访问。
- **叠加生效**：seccomp、LSM 与 capabilities 三者可同时生效，各自过滤不同层面，凡是任一机制不允许就被拒绝。
- **可定制**：可用自定义 seccomp profile 收紧或放宽，用 --security-opt 指定。

```bash
docker run -d --name web \
  --security-opt seccomp=/etc/docker/seccomp.json \
  --security-opt apparmor=docker-default \
  nginx
```

> [!TIP]
> **建议内容**：学习与开发阶段用默认 profile 即可；生产环境应基于工作负载生成最小化的 seccomp 与 AppArmor 策略，并以只读根文件系统、非 root 用户配合。安全加固的具体做法见第 16 章。

**速记**：**seccomp 过滤系统调用，LSM 做强制访问控制；与 capability 叠加生效**。



### 写时复制

#### 写时复制的基本含义

**写时复制（Copy-on-Write，CoW）**：是一种「读共享、写才复制」的存储策略，多个使用者共享同一份只读数据，任何一方要修改时，内核只把被改动的部分复制到自己的可写层，其余数据继续共享。

- **读路径共享**：读取未修改的文件时直接命中下面共享的只读层，不产生额外副本。
- **写路径复制**：首次修改某文件时，该文件被复制到可写层，之后读写都落在副本上。
- **按文件粒度**：复制以文件为单位，修改一个小文件也可能复制整份文件，大文件反复改写会显著增加可写层体积。
- **启动即得**：新容器只需建一个空可写层，不必复制镜像内容，因此启动极快。

```text
容器 A 可写层  ← 只读共享 →  容器 B 可写层
       ↑                            ↑
   ┌───┴────────────────────────────┴───┐
   │        同一份镜像的只读层            │
   └────────────────────────────────────┘
```

> CoW 是「容器轻」的结构性原因：镜像层只有一份，无论启动多少容器都不复制，只有真正被写入的文件才产生新数据。存储驱动的实现细节，如 overlay2 与 snapshotter 的差异，见第 4 章。

**速记**：**读共享、写复制，改动才占空间；按文件粒度，所以新容器启动快**。



#### 共享只读层：多个容器的公共底座

**共享后果之一**：同一镜像启动的所有容器共用同一份只读层，镜像层在磁盘上只有一份，容器数量增加不会按比例增加磁盘占用。

- **底座唯一**：第一个容器创建时镜像层已就位，后续容器直接复用，不再复制。
- **节省磁盘**：十个基于同一镜像的容器，镜像层仍只有一份，额外占用只来自各自的可写层。
- **节省内存**：相同的文件页可被多个容器共享缓存，减少内存压力。
- **隔离仍完整**：共享的是只读内容，容器之间的写入互不可见，隔离性不受影响。

> 共享带来一个运维推论：删除镜像前必须先确认没有容器再引用它。有容器在用镜像层，docker rmi 会因引用计数不为零而拒绝删除，这正是共享关系的直接体现。

**速记**：**镜像层全机一份，多容器共用；省磁盘省内存，但删镜像要先删引用它的容器**。



#### 改文件为什么既不影响镜像也不影响别的容器

**影响范围**：容器内修改文件时，被改文件先复制到本容器的可写层再修改，因此**镜像层保持只读不变**，**其他容器的可写层也不受影响**。

- **不影响镜像**：修改只发生在可写层，镜像的只读层从未被写入，所以镜像内容与摘要都不变。
- **不影响别的容器**：每个容器有独立可写层，改动只在本层可见，邻居读到的是共享的原始文件。
- **删除同理**：在容器内删除文件表现为可写层里的一条「标记删除」记录，底层文件仍在，邻居照常看到它。
- **重建即还原**：删除容器再新建一个，可写层从零开始，镜像内容原样呈现。

```bash
docker run --name a -d nginx
docker run --name b -d nginx
docker exec a sh -c 'echo changed > /usr/share/nginx/html/index.html'
docker exec b cat /usr/share/nginx/html/index.html   # 仍是镜像里的原始内容
docker exec a cat /usr/share/nginx/html/index.html   # 读到改后的内容
```

> [!IMPORTANT]
> **重要内容**：这条性质决定了容器的两条使用纪律：一是「容器内手工改配置」不可持续，重建即丢，配置应通过环境变量或挂载注入；二是调试时进容器改文件只能验证想法，正式改动必须回到镜像构建或挂载数据。

**速记**：**改动落在自己的可写层，镜像不变、邻居不变；重建即还原**。



### 仓库

#### registry、repository、tag 的层级关系

**三者的层级**：一个**registry**上有多个**repository**，一个 repository 下有多个**tag**，tag 指向某个 digest，digest 对应一份确定的清单。

- **registry**：集中存放与分发镜像的服务，有主机名与端口，如 docker.io、ghcr.io、自建 Harbor。
- **repository**：registry 内一组相关镜像的集合，形如命名空间/仓库名，如 library/nginx、yourteam/api，可理解为按项目分的文件夹。
- **tag**：repository 内指向某个 digest 的可变名字，如 1.29、latest、dev。
- **digest**：tag 最终解析到的内容地址，一个 repository 可以有多份不同 digest 的清单。

```text
registry（docker.io）
  └── repository（library/nginx）
        ├── tag latest  -> digest sha256:aaaa...
        ├── tag 1.29    -> digest sha256:bbbb...
        └── tag 1.28    -> digest sha256:cccc...
```

> 常见误用是把 repository 与 registry 混称。docker pull 的第二段 library/nginx 是 repository，它所在的 docker.io 才是 registry；镜像名里出现的斜杠一半用于分隔主机与 repo，一半用于分隔命名空间与仓库名，读名字时要数清斜杠的归属。

**速记**：**registry 装 repository，repository 装 tag，tag 指向 digest**。



#### 官方仓库与命名空间仓库

**官方镜像（Official Image）**：位于 Docker Hub 的 library 命名空间，由 Docker 官方维护与审核，引用时可省略 library，如 nginx 即 library/nginx。**命名空间仓库**：位于用户名或组织名下，由发布者自行维护，引用时必须写出命名空间，如 bitnami/nginx。

- **官方镜像**：覆盖常见基础系统与中间件，更新频繁、文档完整，适合作为基础镜像或直接使用。
- **命名空间仓库**：可能是企业官方发布（如 bitnami），也可能是个人项目，质量与更新频率取决于发布者。
- **识别方法**：看引用里斜杠的个数，无命名空间且能直接拉通的是官方镜像，带命名空间的是普通仓库。
- **信任判断**：带 Docker 验证发布者或赞助开源标记的属受信内容，普通个人仓库使用前应审查来源。

> [!CAUTION]
> **注意内容**：不要凭名字像不像官方来判断可信度。任何人都能注册命名空间并发布名字相近的镜像，拉取企业基础镜像前应确认发布者身份与镜像来源，避免引入被植入后门的镜像。

**速记**：**官方镜像在 library 下、可省命名空间；命名空间仓库必须写清发布者**。



#### 公共 registry 与私有 registry

**公共 registry**：向所有人开放拉取的镜像服务，如 Docker Hub、ghcr.io、quay.io。**私有 registry**：需要认证才能访问的镜像服务，如自建 Harbor 或云厂商的 ACR、TCR，用于内部镜像与合规场景。

- **公共 registry**：上手快、镜像全，适合开源项目与个人学习，但有拉取限流与跨境网络问题。
- **私有 registry**：可控制访问、审计与网络路径，适合企业内部交付，需自行运维或付费使用云服务。
- **混用常态**：基础镜像来自公共 registry，业务镜像推送到私有 registry，两者可在同一条流水线中共存。
- **加速机制**：为公共 registry 配置 registry-mirrors 只解决拉取速度，不改变其公开属性；私有 registry 走认证与证书配置，两者互不替代。

> [!NOTE]
> **提醒内容**：官方文档与社区讨论里的「registry」通常泛指私有的镜像存储服务，而 Docker Hub 是其中一个特例。自建 registry 的最小实现是官方提供的 registry 镜像，生产级方案通常改用 Harbor 等带权限与扫描能力的实现，详见第 15 章。

**速记**：**公共 registry 谁都可拉，私有 registry 要认证；基础镜像拉公共，业务镜像推私有**。



### 镜像与容器的生命周期对照

#### 镜像的生命周期

**镜像生命周期**：镜像只有**拉取**、**构建**、**打标签**、**推送**、**删除**五类操作，全程围绕「产生或搬运只读制品」，没有启动、暂停、停止这类运行态动作。

- **拉取**：docker pull 从 registry 取回层与清单，写入本地镜像存储。
- **构建**：docker build 由 Dockerfile 产出一个新镜像，每一条指令通常生成一层。
- **打标签**：docker tag 在不同仓库名或标签间新增一个指向同一 digest 的引用，不复制数据。
- **推送**：docker push 把本地镜像的层与清单上传到 registry，供他人拉取。
- **删除**：docker rmi 删除本地引用与不再被引用的层，有容器在用时会拒绝删除。
- **不可运行**：镜像不能 start、stop、pause，这些动作的宾语只能是容器。

```bash
docker build -t yourteam/api:1.0 .     # 构建
docker tag yourteam/api:1.0 yourteam/api:latest
docker push yourteam/api:1.0           # 推送
docker rmi yourteam/api:1.0            # 删除本地引用
```

> 打标签刻意被单列：它不产生新镜像，只是给同一 digest 再起一个名字。因此给镜像改标签几乎瞬时完成，也不占额外磁盘。

**速记**：**镜像只能拉、建、标、推、删，没有启停暂停**。



#### 容器的生命周期

**容器生命周期**：容器有**创建**、**启动**、**暂停与恢复**、**停止**、**重启**、**删除**六个动作，另有不改变状态的**执行命令**，全程围绕「进程的生灭与可写层的存留」。

- **创建**：docker create 建立可写层与元数据，状态为 created，进程未运行。
- **启动**：docker start 拉起容器内 PID 1，状态为 running；docker run 是创建加启动的合成。
- **暂停与恢复**：docker pause 冻结进程留在内存，docker unpause 恢复，状态在 paused 与 running 间切换。
- **停止**：docker stop 先发 SIGTERM 再在超时后发 SIGKILL，状态转 exited，可写层与元数据保留。
- **重启**：docker restart 等价于停止再启动；docker start 可让已退出的容器再次运行。
- **删除**：docker rm 移除容器、可写层与元数据，不可恢复。
- **执行命令**：docker exec 在运行中的容器内另起进程，不改变容器状态。

```bash
docker create --name web nginx    # created
docker start web                  # running
docker pause web && docker unpause web
docker exec web nginx -v          # 不改变状态
docker stop web && docker start web
docker rm web                     # 删除，可写层一并消失
```

> 两条生命周期在对象上完全分离：能对镜像做的事（推、拉）容器不能做，能对容器做的事（启、停、暂停）镜像不能做。唯一交叠处是删除，且需先删引用镜像的容器，才能删镜像。

**速记**：**容器能创建、启停、暂停、重启、删除；exec 不改状态**。



#### 两条生命周期的交接点

**交接关系**：容器从镜像派生，因此删除顺序固定为**先删容器、后删镜像**，其他动作互不约束。

- **派生方向单向**：容器依赖镜像，镜像不依赖容器；改镜像不会改动已运行的容器，容器的写入也不会回流镜像。
- **删除受引用约束**：镜像层被至少一个容器引用时，docker rmi 拒绝删除；先 docker rm 释放引用，才能删镜像。
- **同名资源释放**：删除容器才释放容器名与端口占用，重建同名容器前必须先删旧容器。
- **镜像更新不等于容器更新**：重新拉取同名标签得到新镜像后，已运行的容器仍跑在旧镜像上，需重建容器才会用上新镜像。

```bash
docker pull nginx:latest      # 镜像更新
docker ps                     # 运行中的旧容器不受影响
docker rm -f web && docker run -d --name web nginx:latest   # 重建才换镜像
```

> [!WARNING]
> **警告内容**：docker pull 拉取新版镜像不会自动更新正在运行的容器，容器与镜像是两份对象。误以为「拉了新版就等于升级了服务」会导致线上长期运行旧版本；滚动更新需要编排工具或显式重建容器来完成。

**速记**：**容器依赖镜像，先删容器后删镜像；拉新镜像不等于换新容器**。



### 无状态假设

#### 为什么容器被设计成可随时销毁重建

**设计前提**：容器被设计为**一次性、可替换**的单元，任何时刻都可能因扩缩容、更新、故障或调度被销毁并原样重建，这一前提称为无状态假设。

- **编排驱动**：编排器按期望副本数随时创建与销毁容器，容器的身份与寿命不再由人工控制。
- **更新驱动**：滚动更新逐个替换容器以发布新版本，旧容器被删除是发布流程的正常环节。
- **故障驱动**：节点宕机或进程崩溃后，容器会在别处重建，重建次数与落点都不可预期。
- **可替换性**：只要镜像与配置不变，重建出的容器应与原容器在功能上等价，这是可替换性的判据。

> 推导结论：不能依赖容器可写层或容器内部状态来保存任何跨生命周期的信息。凡是重建后应当仍然存在的数据，都必须外置；凡是可以从镜像与配置重建出来的东西，才允许留在容器里。

**速记**：**容器随时会被销毁重建，所以它是可替换单元，不是长期居所**。



#### 有状态数据必须外置

**外置原则**：凡是跨容器生命周期需要保留的数据，都必须放到**卷**或**外部服务**上，容器可写层只放可丢弃的临时内容。

- **卷（volume）与绑定挂载（bind mount）**：把宿主或卷驱动管理的目录挂进容器，数据随容器删除而保留，细节见第 7 章。
- **外部数据库与对象存储**：把状态完全移出容器，应用容器无状态化，数据库由独立实例或托管服务承担。
- **消息队列与缓存**：队列与缓存作为外部服务，使应用容器可以任意增减而不丢任务。
- **外置的代价**：挂载与外部依赖会引入额外的配置与网络依赖，需要在部署时一并管理。

```bash
docker run -d --name mysql \
  -v mysql-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=changeme \
  mysql:8
```

> [!IMPORTANT]
> **重要内容**：外置的粒度应按数据性质决定：数据库数据文件、上传文件、证书等必须外置；临时缓存、编译产物、会话快照等可留在可写层。把所有目录都挂出来会破坏镜像的可移植性，把该外置的留在可写层则会丢数据，两者都要避免。

**速记**：**持久数据放卷或外部服务，可写层只放可丢内容**。



#### 由此推出的三条实务原则

**三条原则**：为了让容器真正可随时重建，实践中须做到**配置外置**、**日志走标准输出**、**进程前台运行**。

- **配置外置**：环境变量、挂载的配置文件、密钥注入，把易变的环境差异从镜像中剥离，一个镜像适配多套环境。
- **日志走标准输出**：应用把日志写到 stdout 与 stderr，由 Docker 日志驱动统一收集与轮转，不写容器内文件。
- **进程前台运行**：入口进程在前台持续运行，不自行 daemonize，因为容器生命周期跟随 PID 1，后台化的进程会让容器误判为已结束。
- **三者同源**：都服务于「镜像不变、环境可变、实例可替换」，是同一假设在配置、可观测性与进程模型上的三个投影。

```dockerfile
# 反例：把日志写进容器内文件、把进程放到后台
RUN service nginx start

# 正例：前台运行，日志交给标准输出
CMD ["nginx", "-g", "daemon off;"]
```

> [!TIP]
> **建议内容**：把这三条写进团队的镜像规范并纳入构建检查：日志目录是否指向标准输出、入口是否前台、配置是否全部可注入。满足了这三条，容器才具备被编排器安全替换的前提。

**速记**：**配置外置、日志上屏、进程前台；三件事落实，容器才真能随时重建**。



### 一次完整的对象关系串讲

#### pull 阶段生成的对象

**pull 阶段**：docker pull 只产生与镜像相关的对象，不产生任何容器、网络端点或卷挂载点，动作范围完全限定在镜像存储内。

1. **镜像层 blob**：逐层下载压缩层文件，按摘要写入镜像存储，已存在的层直接跳过。
2. **镜像配置对象**：下载配置 JSON 并落盘，其散列即本地镜像 ID。
3. **清单与索引记录**：记录标签解析出的 digest 与各平台清单，供后续按摘要引用。
4. **本地标签指针**：在本地登记仓库名与标签到 digest 的映射，使 docker run nginx 能直接命中。
5. **无容器对象**：此时 docker ps -a 仍为空，容器要等到 run 或 create 才出现。

```bash
docker pull nginx:1.29
docker image ls
docker ps -a          # 此时无容器
```

> 拉取是按层增量进行的：只有本地缺失的层才下载，因此升级同一镜像通常只拉少数变更层。这也是分层镜像分发效率的来源。

**速记**：**pull 只造镜像侧对象——层、配置、清单、标签指针，不造容器**。



#### run 阶段生成的对象

**run 阶段**：docker run 在镜像之上派生出一整套运行态对象，包括容器可写层、容器元数据、网络端点、端口映射与卷挂载点。

1. **容器可写层**：在镜像只读层之上创建一个空可写层，作为容器内所有写入的落点。
2. **容器元数据对象**：写入配置与状态记录，生成容器 ID，此后可用名字或 ID 引用。
3. **网络端点**：把容器接入默认 bridge 或指定网络，创建 veth 对并分配容器 IP。
4. **端口映射规则**：按 -p 建立宿主端口到容器端口的转发规则，涉及宿主网络配置。
5. **卷挂载点**：-v 指定的命名卷不存在时先创建卷，再把卷或绑定目录挂载到容器内路径。
6. **进程与限制配置**：应用命名空间、cgroup 配额、capabilities 与 seccomp 策略，拉起 PID 1。

```bash
docker run -d --name web \
  -p 8080:80 \
  -v site-data:/usr/share/nginx/html \
  --network bridge \
  nginx:1.29

docker inspect --format '{{.NetworkSettings.IPAddress}}' web
docker volume ls
```

> run 是对象生成最密集的一步：它同时触碰镜像、容器、网络与卷四个子系统。排障时按这条顺序逐项核对，就能定位失败发生在哪一类对象上，而不必盲目重试整条命令。

**速记**：**run 一次生成——可写层、容器元数据、网络端点、端口规则、卷挂载、受限进程**。



#### rm 阶段回收的对象

**rm 阶段**：docker rm 回收容器侧的全部对象，但保留镜像层与命名卷，动作范围与 run 阶段大致对称。

1. **停止并回收进程**：若容器仍在运行，先停止 PID 1，再回收命名空间与 cgroup。
2. **删除容器可写层**：其中的数据被永久清除，这是 rm 不可逆的部分。
3. **删除容器元数据与 ID**：容器名与 ID 被释放，可再次用于新建同名容器。
4. **回收网络端点**：断开网络、删除 veth 对并释放容器 IP，临时端口映射规则随之移除。
5. **卸载卷挂载点**：命名卷与绑定挂载从容器视图卸载，但卷本身与其数据保留。
6. **镜像侧不变**：镜像层、镜像 ID 与本地标签指针均不受影响，仍可用于启动新容器。

```bash
docker stop web
docker rm web
docker ps -a            # 容器消失
docker volume ls        # site-data 仍在
docker image ls         # nginx:1.29 仍在
```

> [!CAUTION]
> **注意内容**：rm 只保证命名卷与绑定挂载的数据留存，匿名卷在 rm 时不必然一起删除，长期累积会变成难以辨认的悬空卷。删除容器时若确要一并清理匿名卷，用 docker rm -v；命名卷与绑定目录始终不受该选项影响。

> [!NOTE]
> **提醒内容**：对象之间是引用关系而非包含关系。删容器不必然删卷，删镜像不必然删层（被其他镜像共享的层会保留），删网络前必须先断开接在上面的容器。理解引用计数，就能预判每一步会连带回收什么。

**速记**：**rm 回收进程、可写层、元数据、网络端点；卷与镜像层保留**。



### 常见概念混淆清单

#### 镜像与容器

**镜像与容器**：镜像是只读模板，容器是含可写层的运行实例，两者的核心区别在于是否可写、是否有进程。

- **可写性**：镜像只读不可改，容器含独立可写层且写入互不影响。
- **运行态**：镜像没有进程无法运行，容器有 PID 1 并可启停暂停。
- **数量关系**：一个镜像可派生任意多个容器，一个容器只基于一个镜像。
- **删除关系**：删容器不影响镜像，删镜像前须先删引用它的容器。

> 判断口诀：能 docker run 起来的是容器，docker image ls 里列的是镜像。命令动词也分家，run、start、stop 作用于容器，pull、push、build 作用于镜像。

**速记**：**镜像是模板只读，容器是实例可写；一镜像多容器**。



#### 镜像 ID 与容器 ID

**镜像 ID 与容器 ID**：两者分别是不同对象的标识符，成分也不同——镜像 ID 是镜像配置的散列，容器 ID 是守护进程为容器生成的随机十六进制串。

- **来源不同**：镜像 ID 由内容决定，容器 ID 由创建时随机生成。
- **长度相同**：默认都显示前 12 位，完整值都是 64 位，因此外形相似易混。
- **稳定性不同**：相同内容的镜像 ID 稳定可复现，容器 ID 每次创建都不同。
- **使用场景**：docker rmi 接收镜像 ID，docker rm、exec、logs 接收容器 ID 或名字。

> [!WARNING]
> **警告内容**：在两套 ID 外形相似时，把镜像 ID 传给 docker rm 或把容器 ID 传给 docker rmi 会得到 no such container 或 no such image 的报错；更危险的是凭前缀猜 ID 时命中错误对象，从而删掉不该删的东西。用 docker image ls 与 docker ps -a 分别确认后再操作。

**速记**：**镜像 ID 是内容散列，容器 ID 是随机串；外形像，含义与用途都不同**。



#### repository 与 registry

**repository 与 registry**：registry 是存放镜像的服务与主机，repository 是它内部按项目划分的一组镜像，前者是容器，后者是其中的文件夹。

- **层级不同**：registry 在上，repository 在下，一个 registry 含多个 repository。
- **命名表现**：docker.io 是 registry，library/nginx 是 repository。
- **权限粒度**：认证与权限通常按 repository 授予，推送也要先有目标 repository。
- **删除影响**：删 repository 影响其下所有标签，删 registry 则是整个服务层面的事。

> 中文语境里两者常都被译成「仓库」，这是混淆的根源。读文档时遇到「镜像仓库」，先看它说的是服务（registry）还是项目分组（repository），再决定理解成哪个概念。

**速记**：**registry 是服务，repository 是项目分组；一个 registry 装多个 repository**。



#### tag 与 digest

**tag 与 digest**：tag 是指向 digest 的可变名字，digest 是内容自身的散列，前者可被重新指向，后者由内容决定、无法重指。

- **可变与不可变**：重复推送同一 tag 会改写映射，同一 digest 永远对应同一份字节。
- **引用写法**：tag 前接冒号，digest 前接 at 符号，二者可同时出现且摘要优先。
- **人机分工**：tag 便于人读与记忆，digest 用于机器校验与精确复现。
- **默认值**：省略 tag 时补 latest，latest 本身不保证是最新或最稳定。

> 一个 repository 可以有多个 tag 指向同一个 digest，也可以有多个 digest 被不同 tag 指向。标签与内容是多对多的指针关系，不是一一绑定。

**速记**：**tag 可变、digest 不可变；tag 给人看，digest 给机器锁**。



#### 删除镜像与删除容器

**两条删除命令**：**docker rm** 删除容器，回收可写层与元数据；**docker rmi** 删除镜像，移除本地引用与不再被引用的层。二者宾语不同，顺序也有约束。

- **宾语不同**：rm 后接容器名或容器 ID，rmi 后接镜像名、标签、镜像 ID 或 digest。
- **顺序约束**：镜像被容器引用时不能删，须先 rm 掉引用它的所有容器再 rmi。
- **数据后果**：rm 丢失可写层数据（卷除外），rmi 丢失本地镜像，需要时得重新拉取或构建。
- **批量清理**：docker system prune 会按规则清理已停止容器、悬空镜像与未使用网络，属批量删除，执行前须确认范围。

```bash
docker rm web                  # 删容器
docker rmi nginx:1.29          # 删镜像
docker rm -v old-container     # 删容器并清理其匿名卷
docker system df               # 先看占用，再决定清理什么
```

> [!CAUTION]
> **注意内容**：docker system prune -a 会删除所有未被使用的镜像与已停止容器，且不加确认提示。它可能与后续离线部署、回滚所需的本地镜像冲突，执行前先 docker system df 看清占用，并确认没有尚需保留的对象。

**速记**：**rm 删容器、rmi 删镜像；先删容器再删镜像**。
