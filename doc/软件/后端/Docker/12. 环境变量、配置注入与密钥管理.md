## 环境变量、配置注入与密钥管理

### 配置注入的四条通道

#### 环境变量、env_file、命令行参数与挂载配置文件

**配置注入**：把容器启动时才该确定的取值（连接串、监听端口、外部服务地址、口令）从镜像里剥离出来，在创建容器时送入进程环境或文件系统，使同一镜像可在开发、测试、生产多套环境复用。四条通道如下。

- **环境变量**：以 -e 或 compose 的 environment 把键值写进容器进程环境，最常见、跨语言支持最好。
- **env_file**：把一批环境变量写进文本文件，用 --env-file 或 env_file 字段整批注入，适合变量数量多的场景。
- **命令行参数**：把取值直接拼进启动命令或覆盖后的 command，覆盖力最强，但只适合少量、非敏感、少变的开关。
- **挂载配置文件**：用绑定挂载把宿主上的配置文件或配置目录挂进容器，适合结构化配置（nginx.conf、application.yaml），能保留注释与嵌套结构。

```bash
docker run -d --name api \
  -e NODE_ENV=production \
  --env-file ./api.env \
  -v ./conf/app.yaml:/app/config/app.yaml:ro \
  node:22-alpine node server.js
```

> 四条通道并非互斥：实践中常同时使用——端口与运行模式走环境变量，结构化配置走挂载文件，成批变量走 env_file。

**速记**：环境变量、env_file、命令行参数、挂载配置文件，四条通道各管一类取值。



#### 四条通道的适用边界与代价

**适用边界**：判断走哪条通道，看四个维度——取值是简单键值还是结构化文档、是否敏感、是否需要热更新、是否要跨平台一致。

- **可读性**：环境变量适合扁平键值；深层嵌套配置写成变量会迅速失控，此时挂载文件更清晰。
- **可审计性**：env_file 与挂载文件是版本可控、可比对的文本；散落在脚本里的命令行参数最难审计。
- **热更新能力**：挂载文件可在不重建容器的前提下改宿主文件再让进程重载；环境变量一旦注入便固定在进程环境里，改动必须重建容器。
- **平台差异**：环境变量在所有语言与平台上语义一致；env_file 的解析规则在 docker run 与 Compose 下略有差别，挂载文件在 Windows 容器下受限更多。
- **敏感程度**：越敏感的取值越应远离环境变量与命令行参数，转向 secrets 或外部密钥服务。

> 环境变量的代价是「值一旦进入运行态就不可改」：宿主改了 .env、改了 compose 文件，都必须重新创建容器才能生效，restart 不够。

**速记**：扁平键值用变量、结构化配置用挂载、成批用 env_file、少量开关用命令行。



#### 十二要素应用为何推崇环境变量

**十二要素应用（Twelve-Factor App）**：一套面向可移植服务的工程约定，其第三条「配置」主张把配置存在环境变量里、与代码严格分离。这一主张看重的是可移植性与一致性，与「环境变量是否安全」是两个不同问题。

- **与代码分离**：配置不写进仓库，同一份构建产物可在任意环境运行，避免「为每个环境各打一个镜像」。
- **与语言无关**：环境变量是操作系统级接口，任何语言、任何框架都能读取，无需额外解析库。
- **最小公分母**：它不依赖某一种配置文件格式与文件位置，容器编排平台普遍原生支持。
- **不解决安全**：环境变量对同主机的其他进程、对 docker inspect、对被 fork 的子进程都可见，因此密钥不应只依赖这一层。
- **配套取舍**：现实中常是「非敏感配置进环境变量、敏感配置进 secrets」，把十二要素的第三条与安全分层合起来用。

> [!IMPORTANT]
> **重要内容**：十二要素推崇环境变量解决的是「配置与代码分离」，而不是「密钥安全」。把数据库口令塞进环境变量属于对该主张的常见误用，密钥应优先走 secrets 或外部密钥服务，环境变量只承载非敏感配置。

**速记**：十二要素要的是分离与可移植，不是安全；密钥另走 secrets。



### 单个环境变量的注入写法

#### -e 与 --env 的显式赋值

**-e 与 --env**：是同一个选项的长短两种写法，用于在 docker run 时把键值写进容器环境；可重复出现，同名变量按出现顺序后者覆盖前者。

- 显式赋值写法为 -e KEY=VALUE，一次一组，可写多组。
- 值里含等号时，按第一个等号切分为变量名与值，值中后续的等号原样保留，例如 -e URL=a=b 得到 URL 的值为 a=b。
- 该选项只设置简单（非数组型）变量，不支持数组。
- 它同时用于覆盖镜像 Dockerfile 中同名的 ENV。
- 命令行与 compose 的 environment 一一对应，写法见 Docker Compose 入门。

```bash
docker run --rm -e APP_ENV=staging --env LOG_LEVEL=debug node:22-alpine \
  node -e "console.log(process.env.APP_ENV, process.env.LOG_LEVEL)"
```

> 同名变量多次出现时以最后一次为准，因此把「环境默认值」写在前面、把「本次覆盖值」写在后面，是脚本里常见的排布方式。

**速记**：-e 与 --env 等价，KEY=VALUE 显式赋值，后者覆盖前者。



#### --env VAR 形式的宿主机继承

**宿主机继承**：只写变量名、不写等号时，docker CLI 会读取当前 shell 中的同名变量并传给容器，适合把已在部署环境里导出的变量原样透传。

- 写法为 --env VAR，不带等号。
- CLI 取的是执行 docker 命令的那个 shell 环境，不是宿主的全局配置文件。
- 若该变量在当前 shell 中未导出，容器内该变量为未设置，不会报错。
- compose 的 environment 列表里只写名字，行为相同：优先从宿主机取，取不到再从项目 .env 取。
- 用等号赋值与只写名字可以混用，脚本里通常对非敏感项用继承、对关键项显式赋值。

```bash
export DB_HOST=db.internal
docker run --rm --env DB_HOST alpine:3.21 sh -c 'echo "$DB_HOST"'
```

> [!WARNING]
> **警告内容**：--env VAR 的取值完全取决于执行命令时的 shell 环境，同一份命令在不同机器、不同终端会注入不同结果，且失败是静默的——变量未导出时容器内直接为空。生产启动脚本应显式赋值或改用 env_file，避免这种不可复现的隐式继承。

**速记**：只写名字就继承 shell 同名变量，未导出则容器内为空且不报错。



#### 空格、换行与特殊字符的转义

**转义规则**：值的边界由 shell 决定，含空格或 shell 元字符的值必须加引号；--env-file 不支持多行值，需要换行的值只能靠运行期手法或改走挂载文件。

- 含空格：用双引号包住整组，例如 -e "GREETING=hello world"。
- 含 $、! 等 shell 特殊字符：用单引号阻止 shell 展开，或对特殊字符逐个转义。
- 含换行：在 bash 中可写成 ANSI-C 引用 $'line1\nline2'，但写入 env_file 后换行即行结束，无法表达多行值。
- 含引号本身：在双引号值里转义双引号，或整体改用单引号包裹。
- Compose 的 env 文件：未加引号的值会做插值，想保留字面 $ 需用单引号或转义。

```bash
docker run --rm -e 'MOTD=hello world' -e 'TOKEN=a$b!c' alpine:3.21 \
  sh -c 'printf "%s\n%s\n" "$MOTD" "$TOKEN"'
```

> [!NOTE]
> **提醒内容**：Compose 的 .env 与 env_file 支持加引号、支持 \n 这类转义序列；而 docker run --env-file 只按每行原样解析，不处理转义序列。同一份变量文件在两种命令下表现可能不同，跨命令复用时需留意。

**速记**：值含空格或元字符一律加引号，env_file 表达不了多行值，两种命令的转义规则不同。



#### 变量名与值的合法字符

**合法字符**：环境变量的键在 POSIX 惯例下只能由字母、数字、下划线组成且不以数字开头；值可包含任意字符，但书写与读取要处理转义。

- 键的惯例字符集为下划线、大小写字母与数字，首字符不能是数字。
- 连字符与点虽可能被 shell 接受，但在多数语言里无法直接读取，应避免。
- Compose 插值把美元符号后符合字母或下划线开头、后续为字母数字下划线的串视为变量，其余情况原样保留。
- 键区分大小写，APP_ENV 与 app_env 是两个不同变量。
- 全大写加下划线是社区惯例而非强制，但能提高可读性。
- 值的长度与内容原则上无限制，但单条变量过大（数十 KB 级）会挤占进程环境区，属反模式。

> 环境变量不是承载结构化数据的好容器：把一段 JSON 塞进一个变量虽可行，但引号与转义会迅速失控，超过数百字符就应改走挂载配置文件。

**速记**：键只用字母、数字、下划线且不以数字开头，值可任意但不宜塞长结构化数据。



### 文件式注入：env_file 与 --env-file

#### docker run --env-file 的格式规则

**--env-file（docker run）**：从文本文件成批读取环境变量并注入容器，文件每行一个键值对或一个变量名。

- 行格式为 VARIABLE=VALUE，或只写 VARIABLE 表示从宿主同名变量取值。
- 以 # 开头的整行是注释，被忽略；出现在行中间或取值里的 # 属于值的一部分。
- 空行被忽略。
- 取值不加引号也原样使用，不做转义序列处理，也不做插值。
- 不支持多行值，也无法表达数组。
- 该选项只作用于运行期注入，不参与任何插值。

```text
# api.env
NODE_ENV=production
LOG_LEVEL=info
API_PORT=3000
```

```bash
docker run --rm --env-file ./api.env alpine:3.21 sh -c 'echo "$NODE_ENV $API_PORT"'
```

> [!CAUTION]
> **注意内容**：这类文件常被直接提交进仓库或打进镜像，一旦含密钥就等于公开。务必把具体的环境变量文件加入 .gitignore 与 .dockerignore，只提交一份 .env.example 作为字段清单。

**速记**：每行 KEY=VALUE 或仅 KEY，# 整行注释，行内 # 属值，不支持多行与转义。



#### Compose 的 env_file 字段与多文件合并

**env_file（Compose）**：服务级字段，指向一个或多个环境变量文件，把其中变量注入该服务容器；与 environment 同时出现时，environment 优先。

- 相对路径以 Compose 文件所在目录为基准，绝对路径会导致文件不可移植并触发警告。
- 写成列表时自上而下处理，同名变量以列表中最后一个文件为准，常用于「基础配置加环境覆盖」。
- 列表元素可写成映射，用 required: false 让文件缺失时静默跳过，避免因可选文件不存在而启动失败。
- 可对某个文件指定 format: raw 关闭插值，让值按原样（含引号与美元符号）传给容器。
- environment 声明的同名变量覆盖 env_file 的值，即使该值为空也成立。
- 文件行格式比 docker run 更宽：分隔符可用等号或冒号，取值可加单双引号，双引号内支持 \n、\t 等转义序列。

```yaml
services:
  api:
    image: node:22-alpine
    env_file:
      - ./env/base.env
      - path: ./env/prod.env
        required: false
    environment:
      NODE_ENV: production
```

> env_file 里的键不会盖掉 environment 里写死的同名键，覆盖方向始终是「environment 压 env_file，后者压镜像 ENV」。

**速记**：env_file 可列多个、后者覆盖前者，environment 再压一层且最高。



#### 宿主机 .env 与 --env-file 是两回事

**两回事**：项目根目录的 .env 与 docker compose --env-file 指向的文件，都是给 Compose 做变量插值用的，不直接进入容器；只有写在服务 environment 或 env_file 里的变量才会被注入容器。

- .env：Compose 默认从项目目录加载，供 Compose 文件中占位符的取值。
- docker compose --env-file：指定一个替代 .env 的文件作为插值来源。
- 这两个文件里的变量若未在 environment 或 env_file 中被引用，容器内根本看不到。
- 与之对照，docker run --env-file 是把变量直接注入容器的，语义完全不同。
- 宿主机 shell 中导出的变量同样只是插值来源，不会自动进入容器。

```bash
docker compose --env-file ./env/interp.env config
docker compose --env-file ./env/interp.env up -d
```

> 名字都叫 env file，作用却分属两个阶段：一个在解析期喂给 Compose 自己，一个在运行期喂给容器进程，混淆这两者会得到「明明设了变量容器里却没有」的困惑。

**速记**：.env 与 compose --env-file 管插值、不进容器；docker run --env-file 管注入、进容器。



#### 验证两者差别的实验

**验证思路**：用一个只存在于 .env、未被 environment 引用的变量做对照，再检查插值结果与容器内实际变量，即可确认「插值来源」与「容器变量」不是一回事。

- 在 .env 中写 ONLY_FOR_INTERP=alpha，但不在任何服务的 environment 或 env_file 中引用它。
- 执行 docker compose config，输出里看不到它，因为它未被任何字段使用。
- 执行 docker compose exec 查看容器环境，同样看不到该变量。
- 再把同一变量写进服务的 env_file，容器内即可读到，说明进入容器的是 env_file 而非 .env。
- 把 .env 中的变量用占位符写进 image 或 ports 等字段，可见 config 输出已被替换为实际值，证明插值确在本地完成。

```bash
docker compose config                        # 看插值后的最终配置
docker compose exec api env | grep ONLY_     # 看容器内实际变量
```

> config 输出的是「Compose 解析并插值后的结果」，容器里跑的是「environment 与 env_file 注入后的结果」，两张清单不是同一份，排错时要分别看。

**速记**：.env 里的变量不引用不生效，config 看插值、exec env 看注入。



### Compose 的变量插值

#### 插值语法与默认值、必需值

**变量插值**：Compose 在解析文件时把形如美元符号加变量名的占位符替换为实际取值，语法与 Bash 的参数展开相近，但只支持其中一部分形式。

- ${VAR} 或 $VAR：直接替换为取值。
- ${VAR:-default}：VAR 未设置或为空时用 default；${VAR-default}：仅当 VAR 未设置时用 default，为空则保留空。
- ${VAR:?err}：VAR 未设置或为空时直接报错退出；${VAR?err}：仅当未设置时报错。
- ${VAR:+replacement} 与 ${VAR+replacement}：已设置时用 replacement 替换，否则为空。
- 支持嵌套，如 ${A:-${B:-fallback}}；不支持 ${VAR/foo/bar} 这类扩展 shell 语法。
- 无法解析且无默认值时，Compose 打印警告并把该处替换为空字符串。

```yaml
services:
  web:
    image: nginx:${NGINX_TAG:-1.27}
    environment:
      - "PUBLIC_URL=${PUBLIC_URL:?PUBLIC_URL is required}"
```

> [!TIP]
> **建议内容**：对启动后无法自愈的关键配置用 ${VAR:?err}，让缺失在解析阶段就暴露，而不是等容器跑起来才报连接失败；对可选配置用 ${VAR:-default} 给出安全兜底。

**速记**：默认值用 :- 与 -，必需值用 :? 与 ?，冒号的有无区分「空」与「未设置」。



#### 插值发生的时机与作用范围

**时机**：插值发生在 Compose 本地解析文件的阶段，且在每个文件合并之前逐文件进行；容器内进程看到的永远是替换后的字面值，不会看到占位符。

- 发生在客户端：由 docker compose 命令在本地完成，不依赖容器内 shell 或环境。
- 逐文件先插值再合并：多份 Compose 文件各自插值后再合并，覆盖关系作用在插值后的结果上。
- 只作用于 YAML 的值，不作用于键；映射写法的变量名一侧不参与插值，列表等号写法可让整串参与。
- 用两个美元符号表示字面量美元符号，同时阻止插值。
- environment 中直接写死的值也会参与插值，因此可写成从 .env 取值的占位符形式。
- 镜像 ENV 不参与插值，插值发生在镜像被拉取与容器创建之前。

```yaml
services:
  web:
    command: "echo $$HOME"                 # 两个美元符号转义，容器内看到 $HOME
    environment:
      - "BUILD_TAG=${BUILD_TAG:-dev}"      # 值参与插值，取自 shell 或 .env
```

**速记**：插值在本地解析、合并之前完成，只替换值不替换键，两个美元符号表示字面量。



#### 插值的取值来源与优先级

**插值来源**：Compose 解析插值时按固定顺序取值——执行命令的 shell 环境中已导出的变量优先，其次是环境文件（--env-file 指定的文件，未指定时回落到项目目录下的 .env）。

- 第一来源：执行 docker compose 命令的 shell 环境。
- 第二来源：--env-file 指定的文件；未指定时使用项目目录的 .env。
- 服务 environment 里定义的变量不作为插值来源，同文件其他字段取不到它。
- 容器镜像里的 ENV 也不参与插值。
- 用两个美元符号可让某个字段完全绕过插值，原样传给容器。

```bash
NGINX_TAG=1.29 docker compose config | grep -n 'image:'
```

> [!IMPORTANT]
> **重要内容**：服务 environment 中写 KEY=value 只是「给容器的注入」，不能反向供同文件其他字段插值；想在多处复用同一个取值，应把它放进 shell 环境或 .env，再在需要处用占位符引用。

**速记**：插值来源是 shell 环境优先、环境文件次之，服务 environment 与镜像 ENV 都不参与。



#### 用 docker compose config 查看最终配置

**docker compose config**：在不启动容器的前提下解析、插值并合并文件，输出最终生效的配置，是核对插值结果的权威手段。

- 默认输出合并插值后的完整 YAML，可据此确认每个占位符被替换成了什么。
- 加 --quiet 只做校验、不打印，适合放进 CI 做语法与缺失变量的门禁。
- 输出中所有相对路径会按项目目录解析，便于确认挂载源指向何处。
- 变量的值以明文出现在输出里，若用于排查需注意该输出不要落进共享日志。
- 输出中出现空串时，说明对应占位符既无取值也无默认值。

```bash
docker compose config --quiet
docker compose config | sed -n '1,40p'
```

> [!WARNING]
> **警告内容**：config 会把插值后的值原样打印，若 .env 或 shell 中带有口令，这些明文会出现在终端、CI 日志与重定向文件里。排查配置时不要把 config 的完整输出粘进工单或聊天工具。

**速记**：config 输出插值合并后的最终配置，--quiet 只校验，输出含明文需当心。



### 配置优先级全景

#### 谁覆盖谁：五层级联

**优先级级联**：同一个变量被多处设置时，按官方文档给出的优先级从高到低依次是命令行、插值来源、Compose 文件直写值、env_file，最后才是镜像 ENV。

- 最高：docker compose run 的 -e 或 --env 命令行取值。
- 次高：environment 或 env_file 中通过插值从 shell 或环境文件取到的值。
- 再次：Compose 文件中 environment 直接写死的值。
- 再次：Compose 文件 env_file 中的值。
- 最低：镜像 Dockerfile 中的 ENV，仅当上面各层都未提供该变量时才生效。
- 层外说明：宿主机 shell 变量和 .env 本身不直接进容器，只在被 environment 或 env_file 引用时才产生作用。

```bash
docker compose run --rm -e APP_MODE=from_cli api printenv APP_MODE
```

> 这张级联表是排查「取值不对」的索引：先问命令行有没有传，再问插值来源是什么，最后才怀疑镜像，按这个顺序找几乎不会走弯路。

**速记**：命令行最高，其次是插值来源，再次是 environment 与 env_file，镜像 ENV 垫底。



#### 同一变量五处都设的对照推演

**对照推演**：设镜像 ENV、env_file、environment、宿主机同名变量、命令行 -e 五处都设置了变量 APP_MODE，最终容器内取到的是命令行 -e 的值。

- 第一处镜像 ENV：Dockerfile 写 ENV APP_MODE=image，是垫底值，任何上层设置都会盖掉它。
- 第二处 env_file：文件中写 APP_MODE=from_env_file，覆盖镜像 ENV。
- 第三处 environment 直写：APP_MODE=from_compose，覆盖 env_file。
- 第四处宿主机同名变量：本身不进容器，只在被以继承形式引用或作为插值来源时才有影响。
- 第五处命令行 -e：docker compose run -e APP_MODE=from_cli 覆盖以上全部，取值最高。
- 结论：五处并存时容器读到 from_cli；去掉命令行后依次回落到 from_compose、from_env_file、image。

```bash
docker compose run --rm -e APP_MODE=from_cli api printenv APP_MODE
# 输出：from_cli
```

> 若把 environment 中的直写值改成从 shell 取值的插值写法，且 shell 中已导出该变量，则这一档升到「插值来源」层级，会盖住 environment 直写，但仍旧低于命令行。

**速记**：五处并存取命令行，命令行缺席则 environment 压 env_file 压镜像 ENV，宿主变量只作来源。



#### ENTRYPOINT 里写死变量导致覆盖失效

**覆盖失效**：如果入口脚本用 export、赋值语句把变量写死，或启动命令里直接传参，运行期 -e 就覆盖不了它；只有当脚本以「有值则用、无值才取默认」的写法读取时，外部覆盖才生效。

- 写死形式：entrypoint 脚本里 export APP_MODE=hardcoded，或 CMD 里写 sh -c "APP_MODE=x exec ..."。
- 后写覆盖前写：脚本内的赋值发生在进程环境建立之后，会盖掉 -e 注入的值。
- 正确写法：脚本里用默认值展开的方式，仅在外部未提供时套用默认值。
- 排查手段：容器内执行 printenv 或读 /proc/1/environ，确认到底是注入值还是脚本默认值。
- 同类坑：镜像 ENV 覆盖不了、模板渲染又用写死值覆盖，都会让「改了变量没反应」。

```dockerfile
# 反例：写死，外部 -e 无法覆盖
ENTRYPOINT ["sh", "-c", "export APP_MODE=hardcoded; exec /app/server"]

# 正例：尊重外部注入
ENTRYPOINT ["sh", "-c", "export APP_MODE=\"${APP_MODE:-production}\"; exec /app/server"]
```

> [!CAUTION]
> **注意内容**：排查「环境变量改了不生效」时，第一步不是怀疑 Docker，而是打开入口脚本看它有没有在内部重新赋值。写死的赋值是这类现象最常见的根因，且现象表现得像 Docker 失灵。

**速记**：entrypoint 内部赋值会盖掉 -e，脚本要用默认值展开才允许外部覆盖。



### 环境变量的风险面

#### docker inspect 与 proc 文件系统的可见性

**可见性**：环境变量的值对任何能访问 Docker 守护进程的人都是明文，也能被容器内进程自身从 proc 文件系统读出，因此它不是保密机制。

- docker inspect 的 Config.Env 字段完整列出容器环境，明文可读，无需进入容器。
- 容器内每个进程可从 /proc/1/environ 或对应进程号下的 environ 文件读到自身环境，文件以空字符分隔各项。
- 这些 proc 文件属于容器内进程，而容器进程就是宿主内核上的进程，拥有宿主机 root 权限者可通过宿主上的 proc 文件系统读到同一份数据。
- 能执行 docker exec 的人通常也能执行 printenv，从另一条路拿到同样的值。
- 结论：把环境变量当密钥存储，等价于把密钥向「可访问守护进程或持有宿主 root」的范围公开。

```bash
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' api
docker exec api cat /proc/1/environ | tr '\0' '\n'
```

> [!WARNING]
> **警告内容**：只要密钥以环境变量形式存在，任何拿到守护进程访问权、docker exec 权限或宿主机 root 的人都能直接读到明文。对真正敏感的口令与私钥，应改用 secrets 或外部密钥服务，而不是依赖「很少有人进容器」这种侥幸。

**速记**：inspect 看 Config.Env，进程看 proc 下的 environ，宿主 root 同样可见，环境变量不保密。



#### 子进程继承与日志外泄

**继承与外泄**：环境变量会被容器内所有子进程继承，容易被日志框架、崩溃报告与诊断脚本整体打印，泄露常发生在无人察觉时。

- 继承是默认行为：父进程的环境会传给 fork 出的所有子进程，包括 shell、作业脚本与第三方命令行工具。
- 日志打印：应用启动时打印整份配置、框架 debug 模式、异常堆栈带出上下文，都会把变量写进日志。
- 崩溃报告：错误采集客户端常把环境快照一并上报，采集范围往往超出预期。
- 排查转储：诊断时执行的 env、printenv 与进程树工具会把环境打进工单或聊天记录。
- 缓解：应用侧过滤敏感键、日志脱敏、关闭生产 debug，且不把密钥放进会被整体打印的对象。

```bash
docker logs api | grep -iE 'password|token|secret'   # 排查日志是否带出敏感值
```

> 官方在 Compose secrets 的说明里点明了三条环境变量风险：通常对所有进程可见、访问难以追踪、调试报错时可能在不知情的情况下被打进日志，这正是 secrets 想解决的问题。

**速记**：子进程全继承，日志与崩溃报告最易带出，敏感项要过滤且别用变量存。



#### 构建期 ARG 传密钥永久残留

**构建期残留**：用 ARG 或 --build-arg 把密钥传进构建阶段，会让取值留在镜像历史与构建记录里，之后无论怎么删都抹不掉。

- ARG 取值会出现在镜像历史的创建命令中，docker history 明文可查。
- 即便在后续 RUN 中删除文件，底层层里已写下的内容依然存在，删除只发生在新的层。
- BuildKit 构建还会把构建参数写进来源证明记录，随镜像一起分发。
- 任何拿到镜像的人都能还原这些值，私有仓库同样不能豁免。
- 正确做法是构建期用密钥挂载，读取即销毁、不进层也不进缓存。
- 该做法与 Dockerfile 语法详解、镜像构建最佳实践与多阶段构建两篇的结论一致，此处只强调运行期与构建期的分界。

```dockerfile
# 反例：密钥进历史
ARG NPM_TOKEN
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > /root/.npmrc && npm ci

# 正例：密钥挂载，不进层
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```

> [!WARNING]
> **警告内容**：用 ARG 传过口令或令牌，之后删文件、重建镜像，都不能消除历史里的明文；只要该镜像曾被推送过，就必须把对应密钥视为已泄露并作废轮换。构建期凭据一律改用密钥挂载，这属于不可省略的红线。

**速记**：ARG 传密钥进 history 与证明记录，删不掉，只能挂载读取或事后轮换。



### Docker secrets 在 Swarm 与 Compose 下的差别

#### secrets 的两种实现：tmpfs 与只读文件挂载

**实现差别**：Swarm 的 secret 以内存文件系统（tmpfs）挂载进容器，不落盘；Compose 本地运行时没有这种内存挂载语义，改用把单个文件绑定挂载到容器内。

- Swarm：secret 存于加密的 Raft 日志，通过双向 TLS 分发，解密后以 tmpfs 挂进容器，容器停止即从内存清除。
- Swarm：仅 swarm service 可用，独立容器不支持；创建后不可更新，只能删除重建，因此惯例在名字里带版本号。
- Compose 本地：按官方说明，Compose 通过把单个文件绑定挂载进容器来交付 secret，且仅适用于 Linux 容器，Windows 容器只能挂载目录。
- Compose 本地：挂载点为 /run/secrets 下与 secret 同名的文件，通过标准文件系统权限做访问控制。
- 二者共同点：密钥都不以环境变量形式出现，也不在 docker inspect 的 Env 中暴露。

```yaml
services:
  db:
    image: postgres:17-alpine
    secrets:
      - db_password
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
secrets:
  db_password:
    file: ./db_password.txt
```

> 因此「用了 secrets 就自动安全」并不成立：Compose 单机下的 secret 本质是「由 Compose 管理的只读文件挂载」，安全边界与 Swarm 的内存挂载不同，宿主上的源文件权限仍要自己管。

**速记**：Swarm 走 tmpfs 内存挂载，Compose 本地走单文件绑定挂载，二者都不进 inspect 的 Env。



#### secret 的默认挂载路径与 target

**默认路径**：secret 挂载到容器内的 /run/secrets 目录，文件名默认等于 secret 名称；可通过 target 改成其他路径或文件名。

- Linux 容器默认路径为 /run/secrets 下与 secret 同名的文件。
- 长语法可指定 source、target、uid、gid、mode 等字段做细粒度控制。
- 默认权限为所有用户可读（八进制 0444），需要收紧时用 mode 指定为 0440 之类。
- 注意：Compose 下当 secret 来源是文件时，底层用绑定挂载，不允许 uid 与 gid 重映射，这些字段会被静默忽略；只有来源为 environment 时才生效。
- 服务必须显式声明 secrets 才获得访问权，顶层定义 secret 不等于授权。
- 官方镜像常见约定：用 POSTGRES_PASSWORD_FILE、MYSQL_ROOT_PASSWORD_FILE 这类带 FILE 后缀的变量告诉入口脚本从文件读密钥。

```yaml
services:
  frontend:
    image: example/webapp
    secrets:
      - source: server-certificate
        target: /etc/ssl/certs/server.crt
        mode: 0440
secrets:
  server-certificate:
    file: ./server.cert
```

> [!NOTE]
> **提醒内容**：默认 0444 意味着容器内任何用户都能读到该文件；若同一容器内既有受信主进程又有不受信工具，应显式设置 mode 并以最小权限的属主运行进程。

**速记**：默认落 /run/secrets 下同名文件、权限 0444，target 可改路径，mode 可收紧。



#### Compose 下 secrets 的降级行为

**降级行为**：在不启用 Swarm 的普通 docker compose 下，secrets 不再享有加密存储与内存挂载，退化为「Compose 读取本地文件后以只读形式挂进容器」，安全性取决于宿主文件与权限设置。

- 来源为 file 时，secret 内容取自宿主上的文件，该文件的权限与归属直接决定安全下限。
- 来源为 environment 的 secret 仅 Docker Compose 支持，docker stack deploy 不支持，属于另一条实现分支。
- uid、gid、mode 对 file 来源不生效会被静默忽略，故单机下收紧权限要靠宿主侧文件权限。
- 部署时 Compose 会在 /run/secrets 下创建对应文件，容器内不出现变量形式的密钥。
- 优点：密钥不再出现在 inspect 的 Env、不再被全部子进程继承；缺点：宿主侧仍是明文文件，隔离弱于 Swarm。

```bash
docker compose config | grep -A3 secrets   # 确认 secret 的最终定义
docker compose exec db ls -l /run/secrets  # 查看容器内挂载与权限
```

> [!CAUTION]
> **注意内容**：单机 Compose 下若把 secret 源文件放在项目目录里并提交进版本库，secret 机制就形同虚设——它保护的是「运行期不以变量暴露」，并不阻止你把源文件本身泄露。源文件必须加入 .gitignore 与 .dockerignore。

**速记**：Compose 单机 secrets 退化为只读文件挂载，file 来源的 mode 不生效，宿主文件权限就是底线。



### 挂载配置文件的做法

#### 只读挂载与单文件、目录挂载的差异

**只读与粒度**：配置类挂载一律加只读标记，避免容器内进程误改；挂载目录比挂载单个文件更稳，因为单文件挂载绑定的是宿主文件的 inode。

- 只读挂载：短语法在末尾加冒号加 ro，长语法写 read_only: true。
- 单文件挂载：绑定到具体 inode，宿主上用编辑器保存时常常是「新建临时文件再改名」，inode 变了，容器内仍指向旧 inode，改动看不到。
- 目录挂载：把整个目录挂进去，宿主上的任何文件替换都会在容器内体现，更适合频繁修改的配置。
- 权限与属主：容器内进程的 uid 要与宿主文件权限匹配，否则读不到配置。
- 路径建议：需要多份配置时，挂目录并让进程按约定文件名读取，新增文件无需改 Compose 声明。

```yaml
services:
  web:
    image: nginx:1.27-alpine
    volumes:
      - ./conf.d:/etc/nginx/conf.d:ro     # 目录挂载：替换文件也能看到
```

> [!TIP]
> **建议内容**：配置目录用目录挂载而不是逐个挂单文件，既避免 inode 替换带来的「改了没反应」，也让新增配置文件时不必改动 Compose 声明。

**速记**：配置挂载加只读，优先挂目录而非单文件，单文件会因 inode 替换而看不到改动。



#### 配置热加载与重启信号

**热加载**：挂载只是把新文件放进容器，进程是否读取新配置取决于它自身——多数服务需显式 reload 命令或收到信号后才会重载。

- nginx：执行 nginx -s reload 或发送 SIGHUP，平滑加载新配置，不断开既有连接。
- 许多应用：启动时读一次配置，之后不再读，只能重启进程或重建容器。
- docker kill 加信号：可用 docker kill --signal 向主进程发指定信号触发重载。
- 重启与重建之别：docker restart 会重置容器内环境变量，只适合不依赖新变量的场景。
- 校验先行：重载前先用配置校验命令（如 nginx -t）确认新文件语法正确，避免把服务改崩。

```bash
docker kill --signal=HUP web
docker exec web nginx -t && docker exec web nginx -s reload
```

> 热加载只解决「配置文件内容」的更新；若变更的是环境变量，则必须重建容器，因为进程环境无法就地替换。

**速记**：挂载只放文件，重载靠信号或 reload 命令，改环境变量只能重建容器。



#### 启动时渲染模板的常见模式与风险

**模板渲染模式**：在入口脚本里用 envsubst 之类工具，把环境变量填进配置模板，渲染出进程实际读取的配置文件，是「变量易注入」与「配置要嵌套」之间的折中。

- 做法：镜像内放一份 conf.tmpl，entrypoint 执行 envsubst 读取环境变量，输出到进程要求的路径，再启动服务。
- 优点：结构化配置由模板承载，取值仍从环境变量来，避免把整份配置写死进变量。
- 风险一：若渲染结果落到容器可写层且含密钥，等于把密钥写进容器文件系统，一旦被 commit 就进了镜像。
- 风险二：envsubst 默认替换所有美元符号变量，会误伤配置里本就想要的美元符号，应用白名单限定只替换已知变量。
- 风险三：渲染发生在启动期，模板语法错误会导致容器起不来，需在脚本中加校验并给出明确报错。

```bash
# entrypoint 片段：只替换列出的变量，避免误伤
envsubst '$UPSTREAM_HOST $UPSTREAM_PORT' < /app/nginx.conf.tmpl > /etc/nginx/conf.d/app.conf
```

> [!WARNING]
> **警告内容**：把渲染结果写进容器可写层，等于把密钥落到容器文件系统里；若有人对该容器执行 docker commit，密钥就会进入新镜像。含密钥的渲染产物应输出到内存文件系统或仅在内存中传递，并明确禁止对运行中容器做 commit。

**速记**：模板加 envsubst 兼顾结构与注入，渲染含密钥产物勿落可写层，envsubst 要用白名单。



### 密钥落地做法排序

#### 从最差到最好的六档路径

**排序总览**：从最差到最好依次是——写进 Dockerfile、写进镜像内文件、作为运行期环境变量、作为构建期 secret、用编排层 secret 机制、用外部密钥管理服务启动时拉取。

- 最差：写进 Dockerfile 的 ENV、ARG 或 RUN 内联，永久留在镜像与历史里。
- 次差：把含密钥的 .env 或配置文件复制进镜像，同样进层、删不掉。
- 一般：作为运行期环境变量注入，不进镜像，但 inspect、proc 与子进程都可读。
- 较好：构建期用密钥挂载，只解决构建凭据，不进层不进缓存。
- 更好：用编排层 secret（Swarm 的 tmpfs 或 Compose 的只读文件挂载），不以变量形式暴露。
- 最佳：用外部密钥管理服务（如 Vault、云厂商 KMS 或密钥管理服务），启动时凭身份拉取，可集中轮换与审计。

**速记**：Dockerfile 最差、镜像内文件次差、环境变量一般、build secret 较好、编排 secret 更好、外部密钥服务最佳。



#### 每一档挡得住什么、挡不住什么

**逐档边界**：每一档都比前一档多挡一类风险，但没有任何一档能同时挡住所有路径，选择取决于威胁模型与运维成本。

- 写进 Dockerfile：挡不住任何拿到镜像的人，取值明文在历史里；只适合完全公开的默认值。
- 镜像内文件：挡不住镜像分发范围内的任何人，层内容可被提取。
- 环境变量：挡得住「不进镜像」，挡不住 inspect、proc、子进程与日志外泄。
- 构建期 secret：挡得住「不进镜像与历史」，但只管构建阶段，运行期仍需另想办法。
- 编排 secret：挡得住「不以变量暴露、可控制文件权限」，Swarm 下还挡得住落盘；Compose 单机下挡不住宿主源文件泄露。
- 外部密钥服务：挡得住长期保存与静态泄露，并可轮换与审计；挡不住运行期内存中短暂存在的明文，也挡不住应用把密钥打进日志。

> [!IMPORTANT]
> **重要内容**：安全是分层的，选档要匹配威胁模型。单机开发用 Compose secrets 的只读文件挂载通常够用；生产环境、多团队共享密钥或需合规审计时，应上外部密钥管理服务，而不是把口令塞进环境变量后自我安慰。

**速记**：每档都只挡住一部分路径，编排 secret 挡变量暴露，外部服务挡长期保存，运行期明文是共同软肋。



### 常见事故与检查清单

#### 五类高频事故

**高频事故**：密钥泄露在容器场景下高度集中在五类情形——镜像历史残留、变量文件进仓库、多环境共用密钥、日志打印配置、容器内密钥文件权限过宽。

- 镜像历史残留：曾用 ARG 或内联命令传入密钥，docker history 与分层扫描工具可看到痕迹。
- 变量文件进版本库：.env 或 app.env 被 git add，或未进 .dockerignore 被打进镜像。
- 多环境共用密钥：开发、测试、生产用同一份口令，任一处泄露即波及全部环境。
- 日志打印配置：应用启动打印整份配置、框架 debug 模式把敏感值写进容器日志。
- 权限过宽：secret 文件或挂载配置为世界可读，同一容器内任意用户都能取到。

```bash
docker history --no-trunc myapp:latest          # 看构建命令里有没有密钥
git log --all --full-history -- .env            # 查 .env 是否被提交过
docker logs api | grep -iE 'password|token|secret'
docker exec api ls -l /run/secrets
```

> [!WARNING]
> **警告内容**：一旦密钥已进入镜像历史或提交进 git，仅删除当前文件并不能撤销泄露——历史同样可被还原。正确处置是立即作废并轮换该密钥，再去清理历史与镜像，顺序不可颠倒。

**速记**：历史残留、文件入库、多环境共用、日志打印、权限过宽，五类占绝大多数。



#### 自查命令与整改顺序

**自查与整改**：按「先止漏、再轮换、后清理」的顺序处理，先确认泄露面，再让已泄露的密钥失效，最后才清理仓库与镜像。

- 第一步止漏：确认密钥出现在哪些位置——镜像历史、git 历史、日志、容器内文件。
- 第二步轮换：第一时间作废旧密钥并下发新密钥，这一步与清理并行，不可拖延。
- 第三步清仓库：把具体变量文件加入 .gitignore，补一份 .env.example，必要时用工具重写历史。
- 第四步清镜像：重建不含密钥的镜像并重新推送，旧镜像从仓库下架。
- 第五步改机制：把密钥迁到 secrets 或外部密钥服务，并把一次性检查脚本纳入 CI。
- 第六步加固：收紧容器内文件权限、日志脱敏、分环境分密钥。

```bash
# 常用自查锚点
docker history --no-trunc myapp:latest | grep -iE 'token|password|key'
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' api | grep -iE 'PASS|TOKEN|SECRET'
docker exec api ls -l /run/secrets
```

> [!NOTE]
> **提醒内容**：清理与整改都可以慢慢做，轮换必须最先做。判断标准很简单——只要密钥曾在镜像或仓库里出现过，就默认它已泄露，先作废再讨论其他。

**速记**：先止漏、再轮换、清仓库镜像、改机制、加加固，轮换永远排第一。
