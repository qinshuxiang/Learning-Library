## Docker Compose 入门

### Compose 解决什么问题

#### 长命令的困境与声明式思路

**命令行参数的可维护性**：当启动一个容器需要十几个选项时，难以复现的不是命令本身，而是这串参数——它们散落在终端历史与脚本里，记错一处就与环境不符。**Compose** 正是把这串参数固化成一份可提交、可审阅文件的工具：它让用户在一份 YAML 里声明若干服务，再由一条命令按声明创建、启动与拆除这组容器。

- **记不住也传不下去**：端口、环境变量、挂载、重启策略、网络名合计常超十个选项，手敲必错，新同事也无从得知该用哪条命令启动。
- **声明式**：文件只描述期望状态（用哪个镜像、开哪些端口、挂哪些卷），创建与启动交由 Compose 完成。
- **一组容器即一个应用**：同一条命令同时操作这组容器，并自动为它们建立同一张网络。
- **服务即容器模板**：文件里的一项服务叫 service，运行时对应一个或按需多个容器，服务名同时是容器之间互相访问的主机名。

```yaml
services:
  cache:
    image: redis:7-alpine
```

> 服务名不是随意取的字符串：Compose 会把它注册进自动创建的网络，让 api 这样的服务名可直接当作主机名互相解析，这正是篇 9 讲的自定义网络能力在 Compose 中的默认体现。

> [!NOTE]
> **提醒内容**：本篇只覆盖 Compose 在单机上的用法。它负责「一台机器上的一组容器」，不具备跨主机调度、故障转移与集群自愈能力，这些语义属于 Swarm 与 Kubernetes。

**速记**：一份文件、一组服务、一条命令——多容器应用的单机声明式入口。



#### 与 Swarm、Kubernetes 的分界

**定位分界**：Compose 面向单机（或单 Docker 守护进程）的多容器编排，Swarm 与 Kubernetes 面向多主机的集群编排；三者解决问题的层次不同，而非新旧替代关系。

- **Compose 管什么**：一台机器上的容器如何组合、按什么配置启动、通过哪张网络互访、数据挂在哪个卷上。
- **Compose 不管什么**：多机调度、节点宕机后容器迁到哪、副本数如何跨节点维持、滚动升级如何分批。
- **Swarm**：Docker 原生的集群编排模式，可部署 Compose 风格的声明，如今在新项目中已较少作为首选。
- **Kubernetes**：当前集群编排的事实标准，概念模型不同（Pod、Deployment、Service 等），迁移需重新组织声明。
- **衔接关系**：service、network、volume 三组概念在集群编排里都有对应物，先掌握 Compose 是理解编排概念的平滑起点。

> 实务中常见的是「本地开发与单机部署用 Compose、集群环境用 Kubernetes」的双轨结构，两者声明难以直接互转，但由服务、网络、卷构成的心智模型是通用的。

**速记**：单机编排归 Compose，集群编排归 Swarm 与 Kubernetes。



### Compose V2 与历史版本

#### docker-compose 与 docker compose 之差

**命令形态**：现行 Compose 是以 docker compose 子命令形式提供的 V2 架构，用空格分隔两段命令；历史上的 V1 是一个独立可执行文件 docker-compose，用短横线连成一段。

- **V1**：以 Python 编写的独立程序 docker-compose，通过短横线连接，属于已停止支持的旧架构。
- **V2**：以 Go 编写的 Docker 插件，作为 docker 的子命令调用，随 Docker CLI 一同安装。
- **功能差异**：V2 与 Docker 引擎共享同一套 API 与上下文，能直接沿用当前的登录凭据与上下文配置，无需另行设置。
- **写法纠正**：网上大量旧教程仍写 docker-compose，照抄会在只装了 V2 的机器上得到 command not found。

```bash
docker-compose version   # V1 写法：独立程序，旧教程常见
docker compose version   # V2 写法：docker 的子命令，现行标准
```

> [!IMPORTANT]
> **重要内容**：判定标准只有一条——现行环境一律使用 docker compose 这段带空格的写法。看到短横线版本时，应意识到那是在引用早已停止维护的 V1 语法与命令集。

**速记**：短横线是旧版独立程序，空格是现行 Docker 子命令。



#### 确认版本与现行发布状态

**版本查验**：执行 docker compose version，输出中带 Docker Compose version 字样即说明 V2 已作为 Docker 插件就位；若提示不认识 compose 子命令，则当前 Docker 环境尚未提供 V2。

- **看命令是否被识别**：docker compose 无报错即说明插件存在，版本号中的主版本可确认发布批次。
- **看主版本号**：现行 Compose 已进入 5.x 系列，与历史文档中常见的 2.x 不再是同一计数。
- **现行发布批次**：截至 2026 年 9 月，最新版为 5.5.1，于 2026 年 9 月 3 日发布；上一版 5.5.0 于 2026 年 8 月 17 日发布。
- **5.5.0 的改动**：官方 release notes 表述为重构了镜像摘要的协调机制，以避免不必要的容器重建；同一份说明指出，升级后首次执行 compose up 时既有容器可能因摘要按新逻辑重新评估而被重建一次。

```bash
docker compose version
# 输出形如：Docker Compose version v5.5.1
```

> [!NOTE]
> **提醒内容**：发布号会持续变化，发布日期与改动条目应以 GitHub 上 docker/compose 的 releases 页面为准；此处引用的是该页面在 2026 年 9 月记录到的状态。此外，watch 命令需 Compose 2.22 及以上。

**速记**：5.5.1 于 2026-09-03 发布，5.5.0 重构镜像摘要、升级后首启可能重建容器。



### Compose 文件的命名与查找

#### 推荐文件名与查找顺序

**推荐名**：Compose 官方推荐的文件名是 compose.yaml，未用 -f 指定时按固定顺序在工作目录及其父目录中查找。

- **首选**：compose.yaml，官方示例与文档统一使用的名字。
- **次选**：compose.yml，仅扩展名不同，语义完全相同。
- **兼容旧名**：docker-compose.yaml 与 docker-compose.yml，为兼容 V1 时代的习惯而保留。
- **自动叠加的覆盖文件**：与主文件同目录时可自动读取 compose.override.yaml，用于放置本地或开发环境的覆盖项。
- **向上查找**：未在当前目录找到时逐级向上级目录查找，因此在子目录中执行命令也可能命中项目根的文件。

> 同名不同扩展名的多个文件同时存在时，按上述顺序取第一个命中的；把 compose.yaml 与 compose.yml 并存是常见误配，会让实际读取的文件与预期不符。

**速记**：compose.yaml 为首选，其后依次是 compose.yml、docker-compose.yaml、docker-compose.yml。



#### -f 指定与项目目录

**-f 参数**：用于显式指定 Compose 文件，可重复出现，多个文件按命令行顺序合并为一份配置；**项目目录**：默认取首个 Compose 文件所在目录，Compose 在该目录下读取 .env 文件用于变量插值。

- **多文件合并方向**：后出现的文件覆盖或追加到前面的文件上，惯用写法是先写基础文件、再写覆盖文件。
- **字段合并粒度**：单值选项（如 image、command）后写者替换前者；多值选项（如 ports）两组合并；键值映射（如 environment）按键合并、后写者优先。
- **路径基准**：所有相对路径都相对第一个 -f 文件所在目录解析，而不是相对各覆盖文件自身。
- **环境变量替代**：不写在命令行时，可用环境变量 COMPOSE_FILE 指定文件列表；命令行显式给出的 -f 会覆盖它的取值。
- **.env 与 env_file 的分工**：.env 服务于 Compose 解析文件时的插值（如在文件中把镜像写成 nginx:${TAG}，TAG 取自项目目录下的 .env），env_file 则是把变量注入容器运行环境，两者作用对象不同。

> 多文件覆盖的完整规则与 include 元素留给篇 11，环境变量与配置注入的体系留给篇 12；此处只需记住「.env 供插值、env_file 供注入」。

**速记**：-f 可重复、后写覆盖前写、路径基准取第一个文件，.env 管插值、env_file 管注入。



### 顶层结构与缩进层级

#### 六大顶层字段的分工

**顶层字段**：Compose 文件的最外层只允许若干固定名称的键，其中 name、services、networks、volumes、configs、secrets 六项构成主体，services 为必需项。

- **name**：项目名称，未设置时由目录名等机制推导，决定容器名前缀与资源归属。
- **services**：服务定义，文件的核心，键为服务名、值为该服务的配置映射。
- **networks**：顶层声明的网络，供服务引用；不必声明时 Compose 也会自动创建一张默认网络。
- **volumes**：顶层声明的命名卷，供服务引用并在容器之外持久保存数据。
- **configs 与 secrets**：以文件形式向服务挂载的配置内容，前者放不敏感配置，后者语义上更严格。

> configs 与 secrets 属选读项，日常应用多数只用 services、networks、volumes 三项；而 networks 与 volumes 的深层原理分别属于篇 8、9 与篇 7 的范围。

**速记**：name 定项目，services 是核心，networks 与 volumes 供引用，configs 与 secrets 管文件注入。



#### 顶层字段与 service 字段的缩进

**缩进层级**：YAML 用缩进表达从属关系，服务名缩进在 services 之下，服务内的字段再缩进一层，同级键必须左对齐。

- **第一层**：name、services、networks、volumes 等顶层键，全部顶格书写。
- **第二层**：服务名（如 web、db），缩进在 services 之下。
- **第三层**：具体字段（如 image、ports、environment），缩进在服务名之下。
- **第四层**：映射型字段的子项（如 environment 下的键值、build 下的 context），再向里缩进一层。
- **硬性要求**：YAML 不允许用制表符缩进，同一层级内必须用相同数量的空格，通常取两个空格。

> 顶层字段的缩进决定了它是否生效：把 services 误缩进一层，解析结果会变成某个未知顶层键，或直接报字段无法识别；这类错误几乎都源于缩进，而非字段名拼写。

**速记**：顶层顶格、服务名进一层、字段再进一层、映射子项再进一层，空格替代制表符。



#### 字段复用的两种手段

**复用手段**：Compose 提供两套在文件内复用片段的方式——以 x- 开头的扩展字段，与 YAML 自身的锚点与别名机制。

- **扩展字段**：任何以 x- 开头的顶层键都会被 Compose 忽略，可用于存放自定义片段，再借 YAML 锚点引入到服务中。
- **YAML 锚点与别名**：用 & 定义锚点、用 * 引用别名，可把同一段配置映射到多个服务，避免逐处复制。
- **合并键**：配合 YAML 的合并键可把锚点内容并入当前映射，并允许本地字段覆盖锚点中的同名字段。
- **适用场景**：多个服务共享同一套 environment、logging 或 deploy 片段时收益最明显。

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"

services:
  web:
    image: nginx:1.27
    logging: *default-logging
```

> [!NOTE]
> **提醒内容**：两种复用手段的完整写法、可复用字段范围与团队约定，本篇只到「知道它们存在」为止，具体展开见篇 11。

**速记**：x- 扩展字段承载片段，YAML 锚点与别名完成引用，二者可组合使用。



### services 字段逐项讲解

#### image 与 build 的取舍

**image 与 build**：image 表示直接使用现成镜像，build 表示从本地源码构建镜像；二者写在同一个服务里时，构建产物会被标记为 image 指定的镜像名。

- **只用 image**：使用仓库中已有的镜像，如 nginx、postgres，常见于第三方中间件与已发布应用。
- **只用 build**：由本地 Dockerfile 构建，适合自己维护的服务，构建上下文由 context 指定。
- **两者同时写**：Compose 先按 build 构建镜像，并把构建结果命名为 image 的值，便于后续引用与推送。
- **取舍依据**：镜像是否已由他人发布并按版本管理；能直接拉取就不在本地重复构建。
- **最小要求**：一个服务至少要给出 image 或 build 中的一项，否则无法确定运行什么。

```yaml
services:
  db:
    image: postgres:17-alpine
  api:
    build:
      context: ./api
      dockerfile: Dockerfile
```

> [!TIP]
> **建议内容**：自定义服务优先用 build 并固定基础镜像标签，第三方组件优先用 image 并固定版本标签；无论哪种，都应避免使用 latest 这类随上游漂移的标签。

**速记**：现成镜像用 image，本地源码用 build，二者并存时构建结果按 image 命名。



#### container_name 与自动命名

**container_name**：用于指定容器名称以替代 Compose 自动生成的名称；不指定时由项目名、服务名与序号拼成。

- **自动命名规则**：形如 项目名-服务名-序号，例如 demo-shop-web-1，序号从 1 开始。
- **显式命名**：写 container_name 后容器名即该固定值，便于脚本与人工引用。
- **代价**：一旦固定名称，该服务就无法横向扩展出第二个容器，尝试扩展会直接报错。
- **命名约束**：容器名需符合字母、数字、下划线、点、短横线的组合，且以字母或数字开头。

> [!WARNING]
> **警告内容**：固定 container_name 后，同一台机器上两个不同项目若使用相同名字会直接冲突，第二个项目启动失败。除非确有必要，应让 Compose 按项目名自动命名，把重名风险交给项目隔离。

**速记**：默认名是项目名加服务名加序号，固定名换来可引用、失去可扩展。



#### command 与 entrypoint 的覆盖

**command 与 entrypoint**：两者都用于覆盖镜像中由 Dockerfile 写入的默认值，command 覆盖默认命令，entrypoint 覆盖入口点。

- **覆盖范围**：command 对应 Dockerfile 的 CMD，entrypoint 对应 ENTRYPOINT，写法与语义一一对应。
- **书写形式**：既可写成单行字符串，也可写成列表形式；列表形式不经过 shell，能避免 shell 展开带来的意外。
- **shell 特性**：需要在命令里用变量展开或管道时，须显式调用 shell，例如写成 /bin/sh -c 后接整条命令。
- **清空与连带效果**：值写成空列表或空字符串表示忽略镜像默认值；新写的 entrypoint 非空时，镜像中的默认命令也会被忽略。

> 覆盖只改运行参数，不改变镜像内容；因此 command 与 entrypoint 上的改动无需重新构建镜像，只需重新创建容器即可生效，这是调试阶段最省事的一类改动。

**速记**：command 盖默认命令，entrypoint 盖入口点，改它不用重建镜像。



#### ports 的短语法与长语法

**ports**：声明主机与容器之间的端口映射，短语法适合常见情形，长语法在需要指定绑定地址或协议等细节时使用。

- **短语法格式**：主机端口冒号容器端口，可再加斜杠协议，如 8080:80 或 6060:6060/udp。
- **只写容器端口**：如只写容器端口 3000，表示由 Docker 随机分配一个主机端口，适合避免端口冲突的调试场景。
- **长语法字段**：target 为容器端口、published 为对外端口、host_ip 为绑定地址、protocol 为协议、mode 为发布模式。
- **范围写法**：主机与容器端口都支持区间，如 9090-9091:8080-8081，需两端数量一致。
- **约束**：端口映射不能与 host 网络模式同时使用，否则运行时报错。

```yaml
services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"
      - target: 443
        published: "8443"
        host_ip: 127.0.0.1
        protocol: tcp
```

> [!IMPORTANT]
> **重要内容**：不写主机地址时，Docker 会把端口绑定到 0.0.0.0，即所有网络接口，可能绕过主机防火墙把服务直接暴露到公网。只供本机访问时应写成 127.0.0.1:主机端口:容器端口。

**速记**：短语法共端口，长语法点名道姓，不写绑定地址等于绑全部接口。



#### environment 与 env_file

**environment 与 env_file**：两者都用于向容器注入环境变量，environment 直接写在文件里，env_file 从外部文件读取。

- **environment 的映射写法**：变量名冒号取值，逐行书写，简洁直观。
- **environment 的列表写法**：等号连接变量名与取值，与 docker run 的 -e 形式一致。
- **只写变量名**：列表中只写名字不带等号时，表示从宿主的同名变量取值为容器注入。
- **env_file**：指向一个或多个环境变量文件，文件中每行形如键等于值。
- **优先级与引号**：environment 中的值覆盖 env_file 中的同名变量；true、false、yes、no 这类取值应加引号，避免被 YAML 解析成布尔值。

> [!CAUTION]
> **注意内容**：把密码、密钥直接写进 environment 会连同文件一起进入版本库，属常见泄密途径。敏感取值应改用 secrets 或环境变量文件并加入忽略清单，具体做法见篇 12。

**速记**：environment 写文件里、env_file 读文件外，同名时 environment 赢。



#### volumes 的短语法与长语法

**volumes**：声明宿主侧存储到容器内路径的挂载关系；短语法一行搞定，长语法显式写明挂载类型与选项。

- **短语法格式**：宿主侧冒号容器内路径，可再加只读标记，如 ./html:/usr/share/nginx/html:ro。
- **源是路径还是名字**：源以点或斜杠开头时是绑定挂载（挂载宿主上的某个目录），源是单纯的名字时是命名卷。
- **命名卷**：由 Docker 管理、存放于引擎的数据目录中，适合数据库数据这类不应散落在项目目录里的内容。
- **绑定挂载**：直接把宿主目录挂进容器，适合开发时挂载源码或配置文件，目录内容随宿主实时变化。
- **长语法字段**：type 为卷或绑定类型、source 为源、target 为容器内路径、read_only 表示只读。
- **顶层声明**：命名卷若被多个服务共享，应在顶层 volumes 中声明名字，服务内再引用。

```yaml
services:
  db:
    image: postgres:17-alpine
    volumes:
      - db-data:/var/lib/postgresql/data     # 裸名字：命名卷
  web:
    image: nginx:1.27
    volumes:
      - ./html:/usr/share/nginx/html:ro      # 点斜杠开头：绑定挂载
      - type: bind                           # 长语法：显式声明类型与选项
        source: ./conf
        target: /etc/nginx/conf.d
        read_only: true

volumes:
  db-data:
```

> 此处只讲语法层的区分：短语法靠源是否以路径符号开头来判断是绑定还是命名卷，长语法则把 type 显式写出来。两者的挂载原理、读写层行为与数据迁移方法属于篇 7。

**速记**：源以点斜杠开头是绑定、以裸名字出现是命名卷，长语法用 type 说明白。



#### networks 字段

**networks**：声明服务连接到哪些网络，值是顶层 networks 中定义的名字的列表；不写时服务会连入项目自动创建的 default 网络。

- **默认网络**：未声明 networks 的服务全部连入名为 default 的网络，同项目内可直接以服务名互访。
- **自定义网络**：把服务分配到不同网络可隔离流量，例如前端服务与数据库各在一张网络上。
- **服务名即主机名**：同一网络内的容器可用服务名互相解析，是 Compose 里最常见的互联方式。
- **别名与静态地址**：服务在某张网络上可设别名、静态 IP 等属性，属进阶用法。
- **不连任何网络**：需要完全隔离时可把网络模式设为 none。

```yaml
services:
  api:
    image: node:22-alpine
    networks:
      - frontend
      - backend
  db:
    image: postgres:17-alpine
    networks:
      - backend

networks:
  frontend:
  backend:
```

> 网络隔离的动机在于缩小可达范围：把数据库只放进后端网络，前端网络中的服务便无法直接连接它。网络的创建、驱动与 DNS 行为详见篇 8 与篇 9。

**速记**：不写 networks 进默认网络，同网络内以服务名互访，分网络即分可达范围。



#### restart 与 deploy 的适用边界

**restart**：声明容器退出后的重启策略；**deploy**：声明部署与生命周期相关配置，但其中相当一部分字段只对 Swarm 生效。

- **no**：默认策略，任何情况下都不重启。
- **always**：只要容器退出就重启，直到容器被移除。
- **on-failure**：仅当退出码表示失败时重启，可附加冒号加最大重试次数。
- **unless-stopped**：无论退出码都重启，但在被手动停止后不再拉起，是常驻服务最常用的取值。
- **deploy.resources**：其中的 limits 与 reservations 可在单机下约束 CPU 与内存，是 deploy 段里 docker compose 真正会用的部分。
- **deploy 的其余字段**：replicas、placement、update_config、rollback_config 等编排语义属于 Swarm，普通 docker compose 下不生效或被忽略。

```yaml
services:
  api:
    image: node:22-alpine
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 512M
```

> [!NOTE]
> **提醒内容**：deploy 段按规范属于可选部分，未被实现的字段会被忽略而文件仍视为有效，因此写了 replicas 却不生效时并不报错。单机下扩容应改用 docker compose up 的 scale 参数，完整差异见篇 11。

**速记**：重启策略用 restart，单机资源限制看 deploy.resources，其余 deploy 字段留给 Swarm。



### 常用命令全景

#### up、build、pull 与 restart

**up**：按 Compose 文件创建并启动全部服务，是日常使用频率最高的命令；**build**：按 build 段构建或重建镜像；**pull**：拉取服务所用镜像；**restart**：重启服务容器。

- **up 的前台与后台**：不加 -d 时占据终端并聚合打印各服务日志；加 -d 后立即返回，容器在后台运行。
- **up 的两个附加项**：加 build 可在启动前先构建带 build 段的服务，加 force-recreate 可忽略配置未变这一条件强制重建。
- **重复执行 up**：只重建发生变化的服务，其余保持运行，属正常行为。
- **restart 不会重建**：它只是停止再启动既有容器，不重新构建镜像、不重新读取配置。
- **只处理指定服务**：四条命令都可只写服务名，把操作限定在单个服务上。

```bash
docker compose up -d
docker compose up -d --build
docker compose build api
docker compose pull db
docker compose restart api
```

> 改了 Dockerfile 却没看到效果，通常是只执行了 restart 或 up 而未触发重新构建；restart 不会重建镜像，正确做法是先 build 再 up。

**速记**：up 建并起、-d 转后台，build 重造镜像、pull 更新镜像、restart 只重启不重建。



#### ps 与 logs

**ps**：列出当前项目下的容器及其状态；**logs**：汇总打印各服务的日志输出。

- **ps 默认**：只显示运行中的容器，包含名称、镜像、命令、状态与端口。
- **ps 全量**：加 -a 一并列出已停止的容器，排查「起过又退出」的服务必用。
- **logs 跟随**：加 -f 持续跟随新输出，相当于同时 tail 各容器日志。
- **logs 截断与筛选**：加 tail 限定只显示末尾若干行；在命令末尾写服务名可只看指定服务。

```bash
docker compose ps
docker compose ps -a
docker compose logs -f --tail=100 api
```

> [!TIP]
> **建议内容**：排查容器「启动后立刻退出」时，先用 ps -a 确认退出状态，再用 logs 加服务名查看退出前的最后输出；两者组合几乎能定位绝大多数启动失败。

**速记**：ps 看状态、-a 看含停止，logs 加 -f 跟随、加服务名过滤。



#### exec 与 run

**exec**：在一个正在运行的容器里执行命令；**run**：以某个服务的配置新建一个一次性容器来执行命令。

- **exec 的前提**：目标容器必须已在运行，命令在既有容器内执行，不新建容器。
- **exec 的典型用途**：进入容器交互式排查、执行数据库客户端、查看进程与文件。
- **run 的行为**：按指定服务的镜像、环境变量与卷新建一个容器，执行完即退出；加 rm 让容器退出后被自动删除。
- **run 与端口的差异**：run 默认不为一次性容器映射服务声明的端口，需要时加 service-ports 才会映射。
- **非交互场景**：脚本中使用 exec 或 run 时加 -T 关闭伪终端分配，避免报错。

```bash
docker compose exec db psql -U app -d shop
docker compose exec -T api node -e "console.log(process.env.NODE_ENV)"
docker compose run --rm api npm run migrate
```

> exec 处理的是「已经在跑的容器」，run 处理的是「另起一个临时容器」；改动数据库结构这类一次性任务用 run，观察线上状态用 exec。

**速记**：exec 进既有容器、run 起临时容器，临时任务加 --rm 自清理。



#### stop、start 与 down

**stop**：停止运行中的容器但保留容器本身；**start**：启动已存在但停止的容器；**down**：停止并移除容器与网络，是拆除整个应用环境的命令。

- **stop 与 start 成对**：两者都不重新创建容器，状态与数据保留，适合临时暂停环境。
- **down 的默认行为**：停止并移除服务对应的容器，以及 Compose 创建的网络；命名卷与匿名卷默认保留。
- **down 加 -v**：额外移除顶层 volumes 中声明的命名卷与容器附着的匿名卷，即删除数据。
- **down 加 rmi**：额外移除服务使用的镜像，取值可为 local（仅无自定义标签的）或 all。
- **清除孤儿容器**：加 remove-orphans 一并移除已从文件中删除的旧服务所遗留的容器。
- **永不移除的资源**：以外部方式声明的网络与卷，down 不会触及。

```bash
docker compose stop
docker compose start
docker compose down
docker compose down -v
```

> [!WARNING]
> **警告内容**：docker compose down -v 会删除命名卷，数据库与上传文件等持久化数据将一并丢失且不可恢复。日常重启环境应使用 down 或 stop，只有在确认数据可弃或已有备份时才加 -v。

**速记**：stop 留容器、down 删容器与网络，加 -v 连卷带数据一起删。



#### config、top、events 与 watch

**config**：在不启动容器的前提下解析并渲染最终配置，是校验与排错的权威工具；**top**：显示容器内进程；**events**：订阅实时事件；**watch**：监视构建上下文并在文件变化时同步或重建。

- **config 的用途**：验证文件语法、查看变量插值后的结果、确认多文件合并的最终形态；加 quiet 则只校验不输出。
- **top**：列出各容器内正在运行的进程，用于确认容器里究竟跑着什么。
- **events**：以流式方式接收容器的启动、停止、健康状态变化等事件。
- **watch 的前提**：需要 Compose 2.22 及以上版本，属于开发期的文件同步能力，不是生产运行手段。
- **watch 的行为**：按文件类型对应不同动作，可同步进容器、重建容器或重启容器。

```bash
docker compose config --quiet
docker compose top
docker compose events
docker compose watch
```

> [!NOTE]
> **提醒内容**：watch 是面向开发环境的同步工具，依赖 2.22 及以上的 Compose；在旧版本上执行会提示命令不存在，升级前请确认当前版本号。

**速记**：config 只看不跑、top 看进程、events 看事件，watch 需 2.22 起用于开发同步。



### 项目名与容器命名规则

#### 项目名与容器名的确定

**项目名**：Compose 用来隔离同一台机器上不同应用集合的名称，按固定优先级从多个来源取值；**容器名**：未指定 container_name 时由项目名、服务名与序号自动拼成。

- **项目名第一优先**：命令行 -p 参数，直接指定项目名，优先级最高。
- **项目名第二、三优先**：环境变量 COMPOSE_PROJECT_NAME，其次是 Compose 文件顶层的 name 字段。
- **项目名兜底**：包含 Compose 文件的目录名；未指定任何文件时取当前目录名。
- **项目名命名约束**：只能由小写字母、数字、短横线与下划线组成，且以字母或数字开头。
- **容器名构成**：项目名、服务名、序号三段拼接，序号从 1 起递增；由 run 创建的一次性容器名带 run 与一段随机后缀。
- **固定名的影响**：一旦写了 container_name，名字不再包含项目名，跨项目隔离随之失效。

```bash
docker compose -p shop-dev up -d
COMPOSE_PROJECT_NAME=shop-dev docker compose up -d
```

> 同一份 compose.yaml 用不同的项目名运行两遍，会得到两套互不干扰的容器、网络与卷，这正是靠项目名做环境隔离的方式，常见于同一功能分支并行验证。容器名的序号段只在同一服务存在多个副本时才会递增，单副本服务的名字里同样是 1。

**速记**：-p 最高、环境变量次之、name 再次、目录名兜底；容器名是项目名加服务名加序号。



#### 重名与冲突的排查

**冲突来源**：Compose 的资源冲突主要有两类——同项目重复执行带来的重建，与跨项目重名带来的创建失败。

- **同项目重复 up**：属正常行为，Compose 比对配置后只重建发生变化的部分，无需手动干预。
- **跨项目容器重名**：两个项目写了相同的 container_name 时，后者启动会报名字已被占用。
- **跨项目网络重名**：手动指定了同名网络时同理，网络名冲突会让第二个项目启动失败。
- **排查手段**：用 docker ps -a 查看同名容器归属，用 docker compose ls 列出当前机器上已知的 Compose 项目与状态。
- **规避办法**：去掉固定 container_name，让项目名参与命名；或为两套环境分别指定不同的项目名。

> [!CAUTION]
> **注意内容**：发现重名时，直接删除「看起来碍事」的容器可能误删另一套环境的运行实例。删除前先用 docker compose ls 与容器标签确认归属，再决定清理哪一套。

**速记**：同项目重复 up 是重建，跨项目重名才是故障，先查归属再决定删谁。



### 单容器命令与 Compose 的对应

#### 一条 docker run 的字段翻译

**翻译思路**：把一条 docker run 拆成「镜像、名称、端口、环境变量、挂载、重启策略、网络」几组参数，再逐组落到 services 下同名的字段上，即可完成从命令到文件的转换。

- **镜像位置**：docker run 末尾的镜像名对应 image 字段，它是唯一位置固定的参数。
- **名称与端口**：--name 对应 container_name；-p 对应 ports 列表，一条 -p 对应列表中的一项。
- **环境变量与挂载**：-e 或 --env 对应 environment；-v 或 --mount 对应 volumes，短挂载一行对应列表一项。
- **重启与网络**：--restart 对应 restart；--network 对应 networks 列表中的网络名，并在顶层 networks 中声明。

```bash
docker run -d \
  --name web \
  -p 8080:80 \
  -e NODE_ENV=production \
  -v ./html:/usr/share/nginx/html:ro \
  --restart unless-stopped \
  nginx:1.27
```

```yaml
services:
  web:
    image: nginx:1.27
    container_name: web
    ports:
      - "8080:80"
    environment:
      NODE_ENV: production
    volumes:
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped
```

> 命令与字段并非总是一一对应：docker run 的 --network 需要在顶层 networks 中成对声明才完整，而 --add-host、--ulimit 之类较少见的参数则在服务内有各自的字段名，不能按字面直译。

**速记**：镜像落 image、--name 落 container_name，-p、-e、-v、--restart 各归其位。



#### 双向翻译的实践要点

**双向翻译**：既能把既有命令改写成 Compose 文件，也能把 Compose 文件还原成等效的 docker run，用来核对 Compose 到底生成了什么。

- **由命令到文件**：适合把散落的启动脚本收拢成可提交的声明，迁移时逐条对照参数即可。
- **由文件到命令**：遇疑难时用 docker compose config 渲染出最终字段，再据其手工转写 docker run，可验证 Compose 的行为预期。
- **默认值差异**：docker run 不写某项时使用引擎默认，Compose 不写某项时还会叠加上自动网络、自动命名与项目标签，因此二者并非完全等价。
- **不要混用**：同一个容器不要既由 docker run 创建又由 Compose 管理，标签与命名体系不同会让两边互相看不见。
- **渐进迁移**：多容器场景可从逐条 docker run 起步，先翻译成单服务文件跑通，再补齐其余服务与网络。

> [!TIP]
> **建议内容**：拿不准 Compose 会生成什么时，一律先跑 docker compose config 看渲染结果，再决定要不要调整字段；它比反复 up 与 down 试错快得多。

**速记**：命令可翻文件、文件可还原命令，但 Compose 会额外补上网络与命名，两边不等价。



### 完整实战：web 加 api 加 db

#### compose.yaml 全文与逐段讲解

**实战场景**：用一份文件同时声明一个对外提供页面的 web 服务、一个提供接口的 api 服务与一个提供数据的 db 服务，三者分属前端与后端两张网络，数据落在命名卷上。

```yaml
name: demo-shop

services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
    environment:
      API_BASE_URL: http://api:3000
    networks:
      - frontend

  api:
    build:
      context: ./api
      dockerfile: Dockerfile
    env_file:
      - ./api/api.env
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/shop
      NODE_ENV: production
    volumes:
      - type: bind
        source: ./api/src
        target: /app/src
        read_only: true
    networks:
      - frontend
      - backend

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend

volumes:
  db-data:

networks:
  frontend:
  backend:
```

- **name**：固定项目名为 demo-shop，容器名前缀与资源归属都以此为准。
- **web 的 ports 与 environment**：把容器 80 端口映射到宿主 8080；API_BASE_URL 指向 http://api:3000，其中 api 是服务名，靠同网络内的服务名解析生效。
- **api 的 build 与 env_file**：上下文与 Dockerfile 都取同级 api 目录；变量从该目录下的 api.env 注入，environment 中的同名项会覆盖它。
- **api 的 volumes**：把宿主源码目录以只读方式挂进容器，改动源码无需重建镜像即生效，属开发期便利配置。
- **db 的 environment 与 volumes**：设置初始用户、密码与库名，首次初始化数据目录时生效；数据目录挂到命名卷，容器重建后数据不丢。
- **顶层 volumes 与 networks**：声明 db-data 命名卷与 frontend、backend 两张网络，供上面的服务引用。

> [!IMPORTANT]
> **重要内容**：示例中的密码是明文占位值，仅用于演示字段写法，不可直接用于任何真实环境。真实项目应把口令抽到环境变量文件或 secrets 中，并确保其不被提交进版本库。

**速记**：一份文件三层结构，三服务两张网络，ports 通端口、environment 传变量、volumes 保数据。



#### 启动、观察与拆除

**完整流程**：按「校验、启动、观察、进入、拆除」五步走一遍，即可把这份文件从静态声明变成可用的三容器环境。

- **第一步校验**：先执行 config 确认文件语法与插值结果无误，再执行启动。
- **第二步启动**：加 -d 让三个服务在后台创建并启动。
- **第三步观察**：用 ps 看容器状态，用 logs 跟服务日志确认 api 已连上数据库。
- **第四步进入**：用 exec 进入数据库容器执行客户端命令，验证库已就绪。
- **第五步拆除**：用 down 停止并移除容器与网络，命名卷默认保留；确认数据可弃时才加 -v。

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
docker compose logs -f --tail=50 api
docker compose exec db psql -U app -d shop -c "\dt"
docker compose down
```

> [!NOTE]
> **提醒内容**：这一次 down 之后命名卷 db-data 仍然存在，下一次 up 时数据库会沿用旧数据；只有加上 -v 才会把卷一并删除，重建出空库。

**速记**：config 校验、up 启动、ps 与 logs 观察、exec 验证、down 拆除。



### 常见报错与处置

#### YAML 语法与缩进错误

**报错特征**：文件无法解析时，命令会在读取阶段直接失败，提示行号与 expected、mapping values 之类的字样，容器一个也不会创建。

- **缩进不一致**：同一层级的键用了不同数量的空格，解析器无法确定从属关系。
- **制表符**：YAML 禁止用制表符缩进，从编辑器复制的文件常把空格替换成制表符。
- **冒号后缺空格**：键值对的冒号之后必须有一个空格，写成键冒号值会解析失败。
- **中文冒号**：文件内是技术写法，键值之间的冒号必须用半角，全角冒号会被当成普通字符。
- **列表符号与内容未隔空格**：短横线后要紧跟一个空格再写内容。
- **定位手段**：按报错行号往上看一到两行，问题通常出现在紧邻的上一层缩进。

```bash
docker compose config
# 解析失败时会在输出中给出文件名与出错行号
```

> [!TIP]
> **建议内容**：把 compose.yaml 交给带 YAML 语法高亮的编辑器，缩进错位会以色块与波浪线即时显现，比运行后看报错快得多。

**速记**：缩进靠空格、冒号后留空格、短横线后留空格，出错先看报错行的上一行。



#### port is already allocated

**报错特征**：创建容器时提示端口已被分配，说明宿主机上该端口已被别的进程或容器占用。

- **常见来源**：上一次未清理干净的容器仍占用端口，或宿主上另有一个本地服务监听同一端口。
- **排查手段**：用 docker ps 查看是否有容器映射了该端口，用系统命令查看宿主机上监听该端口的进程。
- **处置一**：停掉并移除占用端口的旧容器，再重新启动。
- **处置二**：改映射到宿主机的另一个空闲端口，容器内端口保持不变。
- **注意绑定地址**：把同一容器端口先后映射到 0.0.0.0 与 127.0.0.1 的同一端口，也会互相冲突。

```bash
docker ps --filter publish=8080
docker compose down
docker compose up -d
```

> 报错里的 allocated 指的是宿主机端口，不是容器端口；容器内端口由镜像决定，通常不需要改，改的是冒号左边那一项。

**速记**：端口冲突改冒号左边，先清旧容器、再换主机端口。



#### 服务名无法解析

**报错特征**：容器日志里出现无法解析主机名或连接被拒绝，说明服务之间的名称解析或连通性没建立起来。

- **不同网络**：两个服务不在同一张网络上，服务名只在同一网络内可解析。
- **服务名写错**：名字必须与 Compose 文件里服务键完全一致，大小写与拼写都要相符。
- **服务未启动**：被依赖的服务没跑起来，名字自然解析不到对应的容器。
- **启动太快**：被依赖的服务容器虽已创建，但内部进程尚未就绪，此时连接会失败。
- **处置**：确认两个服务连入同一网络、核对服务名拼写、确认目标服务处于运行状态。

> 这类问题的本质多半是网络归属与启动时机，而非 Compose 本身的缺陷。启动次序的等待机制属于篇 11，本篇只需先确认网络与名字这两项。

**速记**：同网络才解析、名字要一致、服务要在跑，次序等待见篇 11。



#### 卷的权限问题

**报错特征**：容器内进程读写挂载目录时报权限不足或被拒绝，常见于绑定挂载与数据库数据目录。

- **属主不匹配**：容器内进程以某个用户身份运行，而宿主目录的属主是另一个用户，写权限对不上。
- **绑定挂载的覆盖**：把宿主目录挂到容器内的数据目录上，会用宿主目录的内容覆盖镜像里已初始化的目录。
- **SELinux 场景**：在启用 SELinux 的系统上，绑定挂载可能需要追加共享或私有标记。
- **命名卷更省心**：数据目录优先用命名卷，由 Docker 管理属主与初始化，避开宿主目录的权限差异。
- **处置方向**：先确认容器内进程的运行身份，再核对宿主目录属主；不要用放宽到人人可写作为默认解法。

```bash
docker compose exec db ls -ld /var/lib/postgresql/data
```

> [!CAUTION]
> **注意内容**：为绕过权限报错而把宿主目录权限改成人人可写，等于把数据暴露给机器上的任意用户。应先定位运行身份与目录属主的不匹配点，再针对性调整。

**速记**：先看进程身份、再看目录属主，数据目录优先用命名卷。



#### version 字段废弃告警

**报错特征**：文件里写了顶层的 version 字段时，命令会输出一条告警，提示该字段已废弃，但解析仍照常进行。

- **字段现状**：按官方说明，顶层 version 是规范为向后兼容保留的信息性字段，使用时会收到已废弃的告警。
- **校验行为**：无论 version 写什么，Compose 始终以最新规范校验文件，该字段不参与任何校验分支。
- **历史写法**：version: '3' 是旧教程里最常见的写法，直接照抄会触发告警。
- **正确做法**：删掉该字段即可，文件其余部分无需改动。
- **顺带提醒**：若文件里出现 Compose 无法识别的字段，同样会收到告警，通常说明写法对应的是更新的规范或另有拼写错误。

```yaml
# 废弃写法，会告警；现行写法直接删除 version 一行
version: "3"
services:
  web:
    image: nginx:1.27
```

> [!WARNING]
> **警告内容**：发现废弃告警就应删掉 version，不要为了「消除告警」而改成别的高版本号。版本号写法早已被规范合并，继续写它既无意义，也掩盖了文件真实的校验依据。

**速记**：version 已废弃、写了会告警、删掉即可，校验一律按最新规范。
