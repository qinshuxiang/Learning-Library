## Docker 简介与安装配置

### 容器与虚拟机的分野

#### 虚拟化的两条路线

**虚拟化**：指在单一物理机上抽象出多个相互隔离运行环境的技术的总称，按抽象层次分为**宿主级虚拟化**与**操作系统级虚拟化**两条路线，前者对应虚拟机，后者对应容器。

- **宿主级虚拟化**：在硬件之上加一层 **Hypervisor（虚拟机监视器）**，由它切分 CPU、内存、磁盘与网卡，为每台虚拟机模拟出一套完整硬件。
- **操作系统级虚拟化**：不模拟硬件，直接复用宿主机的**同一个内核**，靠内核提供的命名空间与资源限制把进程彼此隔开。
- 代表实现：宿主级有 KVM、VMware ESXi、Hyper-V、VirtualBox；操作系统级有 Docker、containerd、Podman、LXC。
- **关注点差异**：前者关心"多台独立机器"，后者关心"多个隔离进程"，这个差别决定了后续所有性能与隔离特性的走向。

> 常见误解是把容器当成轻量虚拟机。容器省掉的正是硬件模拟与客户机内核这两层开销，它并不试图造出一台机器，只是给一组进程裁剪出一个受控的视图。

**速记**：两条路线——**虚拟机模拟整套硬件，容器共享宿主机内核**。



#### 共享内核与各自内核

**共享内核**：容器与宿主机、以及同机上其他容器共用同一个内核，容器内看到的进程、网络、挂载与文件系统视图，都是内核按命名空间裁剪出来的结果。

- **命名空间（namespace）** 负责隔离视图，覆盖 PID、网络、挂载、IPC、UTS、用户、cgroup 等类别。
- **控制组（cgroup）** 负责限制资源，管控 CPU、内存、块设备 IO 等配额与优先级。
- 虚拟机各自拥有独立内核，容器镜像内**不含内核**，因此镜像体积常以几十到几百兆计。
- **内核版本由宿主机决定**，容器内无法更换内核，Linux 容器只能运行 Linux 程序，Windows 容器同理。

> 例外情况是容器仍可自带完整的用户态发行版：镜像里装着 Ubuntu 的 libc、包管理器与工具链，只是内核那部分借用宿主。所以"镜像里是 Ubuntu"指的是用户态而非内核。

**速记**：共享内核两件套——**namespace 隔离视图，cgroup 限制资源**。



#### 启动速度与隔离强度的取舍

**取舍关系**：容器以**快、小、密**见长，虚拟机以**隔离强**见长；二者是同一组设计目标在不同抽象层次上的不同取舍，不存在全面压倒的一方。

- **启动**：容器启动等价于拉起一个进程，毫秒到秒级；虚拟机需引导客户机内核与 init，数秒到分钟级。
- **体积**：镜像以 MB 计，虚拟机镜像以 GB 计。
- **密度**：单机可跑成百上千个容器；虚拟机受内存与虚拟化开销限制，通常几十台。
- **隔离**：虚拟机边界是硬件级的，强；容器边界是内核级的，弱，内核漏洞可能被利用来逃逸。
- **资源开销**：容器几乎无固定开销，虚拟机为每台保留独立内核与虚拟设备。

> 实务中两者常叠加使用：云上容器跑在虚拟机里，既有虚拟机的安全边界，又有容器的交付效率。选型看的是安全边界要求与资源预算，而非新旧之分。

**速记**：容器赢**快、小、密**，虚拟机赢**隔离强**。



#### 适用场景对照

**判定口径**：问题落在"应用交付与依赖一致"就选容器；问题落在"机器与内核边界"就选虚拟机。

- **容器适用**：微服务部署、CI/CD 流水线、前后端一致的开发环境、批处理任务与弹性伸缩。
- **虚拟机适用**：需要不同内核或不同操作系统、强隔离的多租户环境、遗留单体应用整体搬迁、需要完整硬件特性（如嵌套虚拟化）。
- **两者并用**：Kubernetes 节点本身是虚拟机，Pod 内跑容器；开发机用 Docker Desktop 起一台 Linux 虚拟机再在其中跑容器。
- **迁移路径**：把应用容器化通常需要改造启动方式与配置注入，而整机迁到虚拟机则几乎不改代码。

> 需要留意：macOS 与 Windows 上运行 Linux 容器，底层仍要一台 Linux 虚拟机，容器只是这台虚拟机内的进程。因此这两个平台上的容器性能与文件挂载体验会受虚拟机层影响。

**速记**：**交付一致性用容器，机器与内核边界用虚拟机**。



### Docker 是什么

#### Docker 的定义与定位

**Docker**：是一个用于构建、分发与运行容器的开源平台，2013 年由 Docker 公司（原 dotCloud）发布，它把原本偏底层的 Linux 容器能力包装成人人可用的开发与运维工具链。

- **构建**：以 Dockerfile 描述镜像，由构建引擎产出可分发镜像。
- **分发**：通过镜像仓库（默认 Docker Hub）推送与拉取镜像。
- **运行**：以容器为单位启动应用，隔离依赖并限制资源。
- **定位**：Docker 既不是内核也不是虚拟机，它是内核能力的封装者与工作流的定义者。

> 常见说法"Docker 就是容器"并不准确。准确表述是 Docker 为**容器平台**或称**容器引擎**，容器本身是内核提供的隔离机制，Docker 只是让它变得易用。

**速记**：Docker 三件事——**构建镜像、分发镜像、运行容器**。



#### OCI 与 Docker 的关系

**OCI（Open Container Initiative，开放容器计划）**：2015 年由 Docker 与业界共同发起、现由 Linux 基金会托管的标准化组织，负责制定容器**镜像格式规范**与**运行时规范**。

- **镜像格式规范（image-spec）**：定义镜像的层、清单、配置与索引格式，保证镜像在各实现间通用。
- **运行时规范（runtime-spec）**：定义如何从镜像创建一个运行中的容器，即文件系统与进程配置的约定。
- Docker 是 OCI 规范的**主要贡献者与实现者之一**，但不再独占标准，镜像已可跨 Docker、containerd、Podman 使用。
- **观察点**：docker save 导出的镜像与 OCI 镜像格式高度一致，这是生态互通的直接证据。

> 关系可概括为：**OCI 定标准，Docker 做实现**。Docker 镜像仍然遵循 OCI，"Docker 镜像格式"如今是一种 OCI 兼容镜像的表达。

**速记**：OCI 两份规范——**image-spec 管镜像格式，runtime-spec 管运行时**。



#### 客户端-守护进程架构

**Docker 的架构**：是**客户端-守护进程**架构，docker 命令只是客户端，真正干活的是后台守护进程 dockerd，两者通过 REST API 通信，本地默认走 Unix 套接字。

- **客户端**：docker 命令，负责解析用户输入、向守护进程发请求、展示返回结果。
- **守护进程**：dockerd，常驻后台，管理镜像、容器、网络与卷，监听 /var/run/docker.sock。
- **通信**：默认走本地 Unix 套接字，也可配置 TCP 监听供远程客户端连接。
- **推论**：删除 docker 客户端不影响正在运行的容器；守护进程停了，所有管理操作都会失败。

> [!IMPORTANT]
> **重要内容**：本地能跑 docker 命令的前提是守护进程在运行。报错 Cannot connect to the Docker daemon 指向的正是客户端连不上守护进程，而不是命令拼写有误，排查方向应先落在进程与套接字上。

**速记**：**客户端发指令，dockerd 干活，套接字搭桥**。



#### Docker 解决了什么问题

**核心价值**：Docker 把"环境"从口头约定变成可分发、可复现的制品，一次解决环境一致性、交付效率、资源密度与可复现四项问题。

- **环境一致性**：应用与依赖一起打包成镜像，"在我机器上能跑"变成"在哪都能跑"。
- **交付效率**：构建、分发、运行三段统一为镜像这一种制品，流程标准化。
- **资源密度**：容器共享内核，比虚拟机省资源，单机可承载更多实例。
- **可复现**：Dockerfile 即环境文档，镜像摘要即内容指纹，构建结果可追溯。
- **生态标准化**：OCI 规范与 Compose、Kubernetes 形成完整工具链，镜像可跨平台迁移。

> 需要区分"解决环境一致"与"解决所有部署问题"：编排、扩缩容、服务发现、存储与网络治理都不是 Docker 单机能覆盖的，这些由 Compose 与 Kubernetes 等上层工具接手。

**速记**：四大价值——**一致环境、统一交付、高密度、可复现**。



### 组件栈

#### docker CLI 与 dockerd

**docker CLI**：是面向用户的命令行客户端，也是唯一的人机入口，它把子命令翻译为对守护进程 API 的调用。**dockerd**：是 Docker 守护进程，负责镜像与容器的高层管理、API 服务、网络与卷管理。

- **CLI 职责**：参数解析、请求构造、结果格式化与展示，不直接操作容器。
- **dockerd 职责**：维护镜像与容器状态、编排网络与卷、对外提供 REST API。
- **关系**：dockerd 对外提供 API，docker CLI 只是它众多客户端之一，SDK 与第三方工具走同一套 API。
- **配置**：dockerd 读取 /etc/docker/daemon.json，并由 systemd 单元 docker.service 托管。

> docker context 允许客户端指向不同守护进程，本地虚拟机、远程服务器可并存切换；这也是"命令一样、环境不同"的常见困惑来源，排查时先确认当前 context。

**速记**：**CLI 管交互，dockerd 管全局**。



#### containerd 与 runc

**containerd**：是 dockerd 下方的高层容器运行时，负责镜像拉取与存储、容器生命周期管理、任务执行，是 CNCF 毕业项目，也被 Kubernetes 直接使用。**runc**：是符合 OCI 运行时规范的低层运行时，负责真正调用内核的命名空间与控制组，创建并启动容器进程。

- **containerd 管"容器抽象"**：镜像、快照、任务、事件与命名空间。
- **runc 管"进程创建"**：按配置文件克隆进程、设置隔离、执行入口程序。
- **runc 是一次性的**：容器进程启动后 runc 即退出，由 containerd-shim 接管进程与 IO。
- **containerd-shim**：每个容器一个，负责回收退出状态、保持标准输入输出通道，使容器不依赖守护进程存活。

> [!NOTE]
> **提醒内容**：从 Docker Engine 29.0 起，全新安装默认使用 containerd 的镜像存储（snapshotter）取代传统 overlay2 graph driver；从旧版升级的机器仍沿用旧存储，需要手动切换。这也让 Docker 与 Kubernetes 共用同一份镜像，减少重复拉取。

**速记**：**containerd 管生命周期，runc 管建进程，shim 管收尾**。



#### 一次 docker run 的完整调用链

**调用链**：docker run 自外向内依次经过 **docker CLI、dockerd、containerd、containerd-shim、runc**，最终由 runc 创建出容器进程。

1. docker CLI 解析参数，向 /var/run/docker.sock 发送创建容器请求。
2. dockerd 检查本地是否有该镜像，没有则从仓库拉取并存入镜像存储。
3. dockerd 调用 containerd 创建容器与任务。
4. containerd 准备快照即根文件系统，随后调用 runc。
5. runc 依据 OCI 配置设置命名空间、控制组与根文件系统，启动入口进程后退出。
6. containerd-shim 接管容器进程，dockerd 通过它获取日志与退出码。
7. 返回容器 ID 给客户端；加 -d 则后台运行，不加则客户端附着到输出。

> 记住这条链的意义在于排障定位：拉取失败在 dockerd 层，容器起不来在 runc 层，日志丢失往往在 shim 或日志驱动层。知道问题落在哪一环，就不必盲试命令。

**速记**：调用链——**CLI 到 dockerd 到 containerd 到 runc**。



#### BuildKit 在构建中的位置

**BuildKit**：是 Docker 的下一代镜像构建引擎，自 18.09 引入、23.0 起成为默认构建器，负责解析 Dockerfile 或更通用的构建前端，并按依赖图并行执行构建步骤。

- **位置**：默认位于 dockerd 内部，也可独立运行 buildkitd。
- **能力**：并发执行、缓存挂载、构建密钥、多平台构建与更细的增量复用。
- **buildx**：CLI 插件，把 BuildKit 的构建能力暴露为用户命令，支持多平台与多 builder 实例。
- **与传统构建器差异**：旧 builder 基本按 Dockerfile 顺序逐步执行，BuildKit 按低级中间语言的依赖图调度。

> [!TIP]
> **建议内容**：Dockerfile 的语法与构建最佳实践见本主题第 5、6 章；本篇只需记住构建由 BuildKit 承担，构建期错误与运行期错误的输出格式不同，排障时先分清阶段。

**速记**：**构建交给 BuildKit，buildx 是它的命令行门面**。



### 版本线与产品形态

#### Docker Engine

**Docker Engine**：是 Docker 的核心运行引擎，即 dockerd 加 docker CLI、containerd、runc 与相关插件的组合，是服务器上真正跑容器的组件。

- **组成部分**：dockerd、docker CLI（docker-ce-cli 包）、containerd.io、runc、docker-buildx-plugin、docker-compose-plugin。
- **版本线**：现行 Docker Engine 为 **29.x 系列**，29.8.0 于 2026-09-03 发布，同期组件为 BuildKit v0.33.0、containerd v2.3.4、runc v1.5.1。
- **版本节奏**：按月发布特性版本，跟随官方发布说明升级，具体小版本以官方 release notes 为准。
- **适用**：Linux 服务器、CI 环境以及一切无需图形界面的场景。

> [!NOTE]
> **提醒内容**：Docker Engine 29.8.0 引入了 --umask 标志等改动。版本号与组件版本随时间变动，本文不写死小版本号；确认当前版本请查 docs.docker.com/engine/release-notes。

**速记**：**Engine 是引擎本体，服务器上装的就是它**。



#### Docker Desktop

**Docker Desktop**：是面向个人开发机的桌面应用，把 Docker Engine 与图形界面、Kubernetes、Compose、buildx 等打包在一起，在 macOS 与 Windows 上以一台托管虚拟机运行 Linux 引擎。

- **组成**：桌面图形界面、命令行工具、托管虚拟机、可选的单节点 Kubernetes、扩展机制。
- **版本**：现行最新 GA 为 4.83.0，发布于 2026-07-20。
- **平台包型**：macOS 提供 Apple Silicon 与 Intel 两种安装包；Windows 提供 WSL2 与 Hyper-V 两种后端。
- **便利性**：安装即用，免去手工配置虚拟机、网络与文件共享。

> [!WARNING]
> **警告内容**：Docker Desktop 的许可对大型企业有偿——员工规模或年收入超过官方阈值的商业实体使用需购买订阅，小规模企业与个人免费。面向服务器的商业部署应改用 Docker Engine 以规避授权风险。

**速记**：**Desktop 是开发机上的全家桶，大企业商用要授权**。



#### Compose、buildx 与 BuildKit 的产物形态

**三者定位**：Docker Compose 解决"一次编排多个容器"，buildx 解决"构建"，BuildKit 是其底层的构建引擎，三者均以插件或独立组件形式围绕 Engine 提供能力。

- **Docker Compose**：用一份 YAML 定义多个服务、网络与卷，一条 docker compose up 拉起整套环境，v2 起以 docker 子命令形式发布。
- **Docker buildx**：负责多平台构建与构建缓存管理，底层调用 BuildKit。
- **BuildKit**：构建引擎本体，可被打包在 dockerd 内，也可独立部署。
- **版本归属**：三者版本各自演进，不随 Engine 同号，升级时需分别确认。

> 区分要点：Compose 先有独立的 Python 版（命令为 docker-compose），后统一为 Go 版插件（命令为 docker compose）。旧命令带连字符，新命令带空格，脚本迁移时容易踩这个坑。

**速记**：**Compose 管编排，buildx 管构建，BuildKit 是构建引擎**。



#### Docker Hub 与授权边界

**Docker Hub**：是 Docker 官方运营的公共镜像仓库与分发服务，是 pull 时的默认来源，也是整个 Docker 生态的中心节点。

- **作用**：托管官方镜像（如 ubuntu、nginx、mysql）、提供自动构建、组织与团队协作能力。
- **限流**：匿名与免费账号有拉取速率限制，付费计划可提升配额。
- **替代**：可自建私有 Registry（见本主题第 15 章），或使用云厂商提供的镜像服务。
- **授权边界**：Docker Engine 开源免费，Docker Desktop 对大型企业收费，Docker Hub 免费额度有限，三者是不同产品。

> [!CAUTION]
> **注意内容**：Docker Desktop 的收费不等于 Docker 全面收费，也不等于容器技术收费。服务器上使用 Docker Engine 不受 Desktop 许可约束，这是企业规避授权争议的常规做法，切勿混为一谈。

**速记**：**Engine 免费、Desktop 商用收费、Hub 免费额度有限**。



### 在 macOS 上安装

#### Docker Desktop for Mac

**安装途径**：macOS 上最标准的方式是安装 Docker Desktop，它自带一台 Linux 虚拟机并提供完整工具链，Apple Silicon 与 Intel 机型各选对应包型。

```bash
# 方式一：用 Homebrew 安装 cask
brew install --cask docker

# 方式二：从官网下载 dmg 安装包
# 安装页：docs.docker.com/desktop/setup/install/mac-install/
```

- **包型选择**：Apple Silicon 机型选 Apple chip 包，Intel 机型选 Intel chip 包。
- **首次启动**：需在图形界面完成授权与初始化，等待鲸鱼图标变为运行态。
- **资源设置**：可在设置里调整 CPU、内存、磁盘与文件共享范围。
- **命令行工具**：安装后 docker、docker compose、kubectl 等一并可用。

> [!IMPORTANT]
> **重要内容**：Docker Desktop 必须至少用图形界面启动一次以完成初始化。仅用 brew 命令装完而不启动应用，docker 命令会报 Cannot connect to the Docker daemon，这是新手最常见的误判。

**速记**：macOS 首选 Desktop——**选对包型、启动一次、命令行即用**。



#### Colima 与 OrbStack 替代方案

**替代方案**：不满足于 Desktop 时，macOS 上可用 **Colima** 与 **OrbStack** 提供 Linux 虚拟机加 Docker 运行时，命令行体验与官方一致。

- **Colima**：基于 Lima 的开源命令行方案，完全免费，用 brew 安装后以 colima start 拉起一台轻量虚拟机。
- **OrbStack**：商业产品（个人免费），以启动快、资源占用低著称，同时提供图形界面与命令行。
- **优点**：无 Desktop 许可顾虑，资源占用可按需配置。
- **代价**：功能面窄于 Desktop，Kubernetes、扩展生态等需自行拼装。

```bash
# Colima 基本用法
brew install colima docker
colima start
colima status

# 查看与停止虚拟机
colima list
colima stop
```

> 选择口径：追求稳定与图形化选 Desktop；追求轻量、免费、可脚本化选 Colima；追求极致启动速度与省电选 OrbStack。三者可共存，但同一时刻只应有一个默认上下文指向的引擎。

**速记**：macOS 替代三选——**Desktop 全家桶、Colima 免费、OrbStack 轻快**。



#### macOS 安装后的验证

**验证顺序**：装完先看 docker version 的 Client 与 Server 两段是否都出现，再运行 hello-world 验证整条链路。

```bash
docker version          # Client 与 Server 两段都应输出
docker info             # 查看引擎、存储驱动与镜像源等运行状态
docker run hello-world  # 拉取并运行测试镜像
```

- **只有 Client 段**：说明守护进程或托管虚拟机没有起来，客户端本身正常。
- **docker info 的 Server 段**：Operating System 显示 Docker Desktop，说明引擎运行在托管虚拟机内。
- **首次运行 hello-world**：会自动拉取镜像，网络不畅时可能失败，重试前先确认镜像源配置。

> [!TIP]
> **建议内容**：macOS 上把学习用的镜像与容器视为可随时重建的临时资产。出现难以定位的怪异问题时，用设置里的 Reset 或重建 Colima 虚拟机，往往比逐项排查更快恢复可用状态。

**速记**：macOS 自检三步——**version 两段齐、info 看引擎、hello-world 通**。



### 在 Windows 上安装

#### WSL2 后端与 Hyper-V 后端

**两个后端**：Windows 上运行 Linux 容器必须先有一台 Linux 虚拟机，Docker Desktop 提供 **WSL2 后端**与 **Hyper-V 后端**两种选择，当前官方默认推荐 WSL2。

- **WSL2 后端**：复用 Windows 的 WSL2 轻量虚拟机，启动快、内存按需分配、与 Linux 文件系统互操作好。
- **Hyper-V 后端**：用 Hyper-V 起一台传统 Linux 虚拟机，仅 Windows 专业版与企业版可用。
- **启用前提**：需要管理员执行 wsl --install 并重启，同时打开虚拟机平台相关功能。
- **互斥性**：同一引擎不能同时使用两种后端，切换需在 Desktop 设置中更改并重启。

```powershell
# 启用 WSL 并安装默认发行版（管理员 PowerShell）
wsl --install
wsl --set-default-version 2
wsl --status
```

> [!IMPORTANT]
> **重要内容**：Windows 家庭版没有 Hyper-V，只能走 WSL2 后端，这也是官方默认推荐 WSL2 的原因之一。启用后务必确认 wsl --status 显示默认版本为 2，版本 1 会导致容器与文件性能明显下降。

**速记**：Windows 两个后端——**WSL2 通用推荐，Hyper-V 限专业版以上**。



#### Docker Desktop 的安装

**安装流程**：从官网或包管理器安装 Docker Desktop for Windows，安装时选择 WSL2 后端，首次启动完成初始化后即可使用。

```powershell
# 用 winget 安装
winget install --id Docker.DockerDesktop

# 安装后确认版本与运行状态
docker version
docker info
```

- **前置条件**：Windows 10 或 11 的 64 位版本，开启硬件虚拟化与 WSL2，必要时安装内核更新包。
- **后端选择**：安装过程中会提示选择 WSL2 或 Hyper-V，无特殊需求选 WSL2。
- **首次启动**：接受条款并等待引擎就绪，登录账号可选。
- **安装位置**：程序默认在 Program Files 下，引擎参数在设置界面调整。

> [!TIP]
> **建议内容**：WSL2 后端下可在 Desktop 设置里为常用 WSL 发行版打开集成，这样在 WSL 终端中可直接调用 docker 命令，文件读写性能与 Linux 原生接近。

**速记**：Windows 装法——**winget 安装、选 WSL2、启动初始化、version 验证**。



#### 在 WSL 发行版内直接装 Engine

**另一种做法**：也可以不用 Docker Desktop，直接在某个 WSL 发行版里按 Linux 的方式安装 Docker Engine，此时容器完全运行在该发行版内部。

- **做法**：进入 WSL 发行版，按 Ubuntu 的官方 apt 流程安装 docker-ce 等包，启用 systemd 或手动启动 dockerd。
- **差别**：没有 Desktop 的图形界面与自动集成，需自行配置 daemon.json 与开机启动。
- **好处**：不依赖 Desktop，无授权顾虑，资源占用更可控。
- **限制**：跨发行版与 Windows 侧的互操作需手工处理，且要求 WSL 支持 systemd。

```bash
# 进入 WSL 发行版后（以 Ubuntu 为例）
sudo apt update && sudo apt install -y docker.io
sudo service docker start
docker run hello-world
```

> 与 Desktop 的 WSL2 集成相比，这种方式是把引擎装进发行版内部，而 Desktop 是反过来把发行版接入它托管的引擎。两者的套接字路径与镜像存储位置都不同，排障时不要混用思路。

**速记**：**要图形与集成用 Desktop，要干净自管就在 WSL 里装 Engine**。



### 在 Linux 上安装

#### Ubuntu/Debian 用官方 apt 源

**推荐方式**：生产环境的 Ubuntu 与 Debian 建议使用 Docker 官方 apt 源安装 docker-ce，而非发行版自带的 docker.io 包。

1. 更新索引并安装 curl 等依赖工具。
2. 创建 keyrings 目录并下载官方 GPG 公钥。
3. 写入软件源，新格式为 deb822 的 sources 文件，旧格式为 sources.list 单行。
4. 执行 apt update 后安装 Engine 相关包。

```bash
# 1. 准备工具
sudo apt update
sudo apt install -y ca-certificates curl

# 2. 导入官方 GPG 公钥
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# 3. 写入软件源（deb822 格式，当前官方写法）
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

# 旧写法等价于下面这一行（二选一，不要同时写）
# deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable

# 4. 安装并启动
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

- **包分工**：docker-ce 是守护进程，docker-ce-cli 是客户端，containerd.io 是运行时，后两个是 Compose 与 buildx 插件。
- **前置清理**：安装前移除 docker.io、docker-compose、podman-docker 等冲突包，避免命令与套接字互相干扰。
- **验证**：sudo docker run hello-world。
- **早期文档差异**：旧版指引还需 gpg --dearmor 解码头；当前官方源直接提供 asc 格式公钥，无需该步骤。

> [!CAUTION]
> **注意内容**：把用户加入 docker 组等同于赋予其 root 权限，组内成员可把宿主机根目录挂载进容器从而提权。多人共用的机器应优先使用 rootless 模式，而非简单地把所有人加进 docker 组。

**速记**：apt 装法四步——**导密钥、写源、装包、启服务**。



#### RHEL 系用 dnf

**RHEL 系安装**：RHEL、CentOS Stream、Rocky、AlmaLinux、Fedora 上用 dnf 安装，官方提供稳定的仓库文件 docker-ce.repo。

```bash
# 添加官方仓库
sudo dnf -y install dnf-plugins-core
sudo dnf config-manager --add-repo \
  https://download.docker.com/linux/centos/docker-ce.repo

# 安装并启动
sudo dnf install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

- **仓库文件**：/etc/yum.repos.d/docker-ce.repo，内含 stable 与 test 等段落，默认启用 stable。
- **与 Podman 的关系**：RHEL 系默认自带 Podman，二者可共存，但要注意 docker 命令别名与套接字冲突。
- **卸载**：先用 dnf remove 移除包，再手动清理数据目录。
- **验证**：sudo docker run hello-world。

> [!NOTE]
> **提醒内容**：Fedora 与新版 RHEL 上，官方仓库的地址与添加命令随 dnf 版本演进有所调整，docker-ce.repo 的写法也在变化。动手前以 docs.docker.com/engine/install 对应发行版页面的当前指引为准。

**速记**：RHEL 系——**加 docker-ce.repo、dnf 装包、systemctl 起服务**。



#### 便捷脚本与 rootless 模式

**便捷脚本**：官方提供 get.docker.com 一键安装脚本，但官方明确建议仅用于开发测试；**rootless 模式**则让普通用户无需 root 即可运行守护进程，适合共享机器与安全敏感环境。

- **便捷脚本**：curl 下载脚本后管道给 shell，自动识别发行版并安装最新版。
- **风险**：脚本不便于审计、难以固定版本，升级与卸载路径与包管理器不一致。
- **rootless 原理**：把 dockerd 与 containerd 以普通用户身份运行，借助用户命名空间映射权限。
- **数据位置**：rootless 下数据存于用户家目录（如 ~/.local/share/docker），与系统级互不影响。
- **安装方式**：执行 dockerd-rootless-setuptool.sh install，配套依赖为 rootlesskit 与 slirp4netns。

```bash
# 便捷脚本（仅供开发测试，生产禁用）
curl -fsSL https://get.docker.com | sudo sh

# 安装 rootless 依赖并初始化（以 Ubuntu 为例）
sudo apt install -y uidmap dbus-user-session
dockerd-rootless-setuptool.sh install
systemctl --user start docker
```

> [!WARNING]
> **警告内容**：把 get.docker.com 脚本直接管道给 shell 执行，等于信任一段无法逐行审计的远程代码，生产服务器上禁止这样做。要固定版本请用包管理器，要避免 root 权限请用 rootless 模式。

**速记**：**便捷脚本只用于尝鲜，生产用包管理器，免 root 用 rootless**。



### daemon 配置

#### 配置文件位置与生效方式

**配置文件**：Linux 上守护进程的默认配置文件是 /etc/docker/daemon.json，Windows 上为 %programdata%\docker\config\daemon.json，修改后需重载或重启守护进程才生效。

- **格式**：JSON 对象，文件不存在时需自行创建。
- **冲突规则**：同一选项不能既写在文件里又写在 dockerd 启动参数里，重复出现会导致守护进程启动失败。
- **reload 语义**：systemctl reload docker 发送 SIGHUP，仅少数选项可热生效，如 registry-mirrors、insecure-registries、max-concurrent-downloads。
- **restart 语义**：systemctl restart docker 重启进程，所有选项生效，但会短暂中断容器管理面。

```bash
# 校验配置语法（不启动守护进程）
sudo dockerd --validate --config-file=/etc/docker/daemon.json

# 热重载与完整重启
sudo systemctl reload docker
sudo systemctl restart docker
```

> 关键区别：**reload 只让可热改的字段生效，restart 才让全部字段生效**。改完配置若行为没有变化，多半是改动落在了需要重启的字段上，而不是配置没写对。

**速记**：**reload 热改少数字段，restart 全量生效**。



#### 存储与数据目录字段

**存储字段**：daemon.json 中与存储相关的字段决定镜像与容器的落盘位置和实现，其中 **data-root** 与 **storage-driver** 最常用。

- **data-root**：镜像、容器、卷等状态的根目录，默认值为 /var/lib/docker。
- **storage-driver**：存储驱动，Linux 常用 overlay2；29.0 起默认改用 containerd 镜像存储即 snapshotter。
- **迁移注意**：改 data-root 前应先迁移旧数据，否则原有镜像与容器在界面上看似"消失"。
- **路径变化**：29.0 起镜像层位于 /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/ 下，容器合并文件系统位于 /var/lib/docker/rootfs/overlayfs/ 下；29.0 之前的镜像层路径是 /var/lib/docker/overlay2/。

```json
{
  "data-root": "/var/lib/docker",
  "storage-driver": "overlay2"
}
```

> [!NOTE]
> **提醒内容**：从 29.0 起，只有全新安装默认启用 containerd 镜像存储，从旧版升级的机器仍沿用 overlay2 graph driver，需要手动切换才能获得 snapshotter 的收益，例如与 Kubernetes 共享同一份镜像存储。

**速记**：存储两个字段——**data-root 定位置，storage-driver 定实现**。



#### 日志字段

**日志字段**：log-driver 与 log-opts 控制容器标准输出的落盘方式与轮转策略，不做设置会导致宿主机磁盘被日志写满。

- **log-driver**：日志驱动，默认 json-file，常见还有 local、syslog、journald、fluentd。
- **log-opts**：驱动选项，json-file 下常用 max-size 与 max-file 做轮转。
- **local 驱动**：官方推荐的本地默认驱动，压缩存储、轮转更省磁盘。
- **覆盖层级**：日志驱动可在容器级单独指定，但在守护进程级设默认值更省事。

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

> [!TIP]
> **建议内容**：学习环境与生产环境都建议显式设置 max-size 与 max-file。默认 json-file 不限制文件大小，长时间运行的服务会把日志文件写到占满磁盘，进而引发难以定位的故障。

**速记**：日志两字段——**log-driver 选方式，log-opts 设轮转**。



#### 网络与仓库字段

**网络与仓库字段**：registry-mirrors、insecure-registries 与 default-address-pools 分别控制镜像源、不安全仓库与容器网段分配，三者同属网络与仓库类配置。

- **registry-mirrors**：镜像加速地址列表，拉取时优先走镜像，未命中再回源。
- **insecure-registries**：允许以 HTTP 或不校验证书方式访问的仓库，典型场景是内网自建 Registry。
- **default-address-pools**：为容器网络分配子网时使用的地址池，用于避开与内网已有网段的冲突。
- **生效性**：镜像源类字段可热重载，地址池类改动通常需重启并对新建网络生效。

```json
{
  "registry-mirrors": ["https://your-mirror.example.com"],
  "insecure-registries": ["registry.internal:5000"],
  "default-address-pools": [
    { "base": "172.30.0.0/16", "size": 24 }
  ]
}
```

> 易混点：insecure-registries 是"对某个仓库降低安全校验"，属安全例外；registry-mirrors 是"给官方仓库找缓存代理"，属速度优化。两者目的相反，不要混用，更不要以为加速源能顺带解决自建仓库的证书问题。

**速记**：网络三字段——**mirrors 提速、insecure 放行、address-pools 划网段**。



### 国内镜像加速

#### registry-mirrors 的作用机制

**registry-mirrors**：让守护进程在拉取 Docker Hub 镜像时先请求配置的镜像加速站点，命中则由镜像站回源并缓存，从而绕开跨境网络瓶颈。

- **机制**：客户端请求被改写指向镜像站，镜像站作为上游缓存代理，首次拉取后在本地留存。
- **作用范围**：只影响 Docker Hub 官方仓库，对自建 Registry 与其他公有仓库无效。
- **生效方式**：写入 daemon.json 的 registry-mirrors 后需重载守护进程。
- **现状**：公共镜像源的可用性随时间变动，各厂商地址经常调整或下线。

> [!IMPORTANT]
> **重要内容**：本文不写死任何镜像站地址。公共加速源与账号策略随时可能变更或限流，落笔时可用不代表次日仍可用；正确做法是查当前云厂商或官方文档给出的地址再填入。

**速记**：**mirrors 只加速 Docker Hub，地址随时会变，用时再查**。



#### 配置与验证

**配置方法**：把镜像地址写入 daemon.json 的 registry-mirrors 数组，重载后由 docker info 的 Registry Mirrors 段验证是否生效。

```bash
# 编辑配置
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": ["https://your-mirror.example.com"]
}
EOF

# 重载并验证
sudo systemctl reload docker
docker info | grep -A5 "Registry Mirrors"
```

- **验证点**：docker info 输出中出现 Registry Mirrors 段并列出所配置的地址。
- **未出现时**：依次检查 JSON 语法、文件路径与守护进程是否重载成功。
- **拉取测试**：docker pull 一个小镜像，观察拉取速度与提示来源。
- **多地址**：数组按顺序尝试，前一个不可用时会自动尝试下一个。

> 用通用 CDN 直接加速镜像层是历史流传的做法，稳定性与合规性都不可靠，不建议作为长期方案；有条件的团队应自建缓存代理，可控且可审计。

**速记**：配置三步——**写 mirrors、reload、docker info 查看**。



#### 拉取失败的排查顺序

**排查顺序**：拉取失败时按"配置是否生效、网络是否可达、镜像名与标签、认证与限流"的顺序逐项确认，而不是反复重试。

1. 执行 docker info 确认 Registry Mirrors 是否已生效。
2. 直接 curl 镜像站地址，判断本机到镜像站是否可达、证书是否可信。
3. 确认镜像名与标签拼写正确，并可先试官方域名能否拉通。
4. 检查是否触发 Docker Hub 速率限制，或该镜像是否需要 docker login。
5. 换用可用地址或自建代理，并权衡 HTTPS 证书与 insecure 配置的取舍。

```bash
# 观察拉取时的实时输出
docker pull nginx:latest

# 直接测试镜像站连通性
curl -I https://your-mirror.example.com/v2/

# 查看守护进程日志
sudo journalctl -u docker --no-pager -n 50
```

> [!CAUTION]
> **注意内容**：为让 HTTP 镜像站可用而把它加进 insecure-registries，等于允许明文传输与不校验证书的镜像拉取，中间人可替换镜像内容。仅在完全可控的内网中这样做，公网环境绝不接受。

**速记**：排查顺序——**先看 mirrors 生效否，再测网络与镜像名，最后查认证与限流**。



### 验证与自检

#### hello-world 首次运行

**hello-world**：是官方提供的最小验证镜像，能成功运行即说明客户端、守护进程、镜像拉取与容器运行时四个环节全部打通。

```bash
docker run hello-world
```

- **输出内容**：一段说明文字，提示安装成功并给出后续学习入口。
- **隐式动作**：本地无镜像时先 pull，再 create、start、输出、退出。
- **退出状态**：容器进程终止后处于 Exited 状态，可用 docker ps -a 查看。
- **耗时**：首次拉取较慢属正常，网络不畅时可能超时并报错。

> 若这一步就失败，不要急着往下看。连 hello-world 都跑不通说明引擎或网络存在基础问题，应按报错信息逐类处置，而不是先怀疑某条业务命令写错。

**速记**：**hello-world 跑通，等于安装成功**。



#### docker version 与 docker info 解读

**两条命令**：docker version 报告客户端与服务端各自的版本与 API 版本，docker info 报告引擎运行时的整体状态，二者是安装后必看的两条命令。

- **docker version 的 Client 段**：客户端版本、API 版本、Go 版本与构建信息。
- **docker version 的 Server 段**：守护进程版本、API 版本、最小 API 版本与容器运行时，缺失即说明连不上守护进程。
- **docker info 的 Server 段**：容器与镜像数量、存储驱动、日志驱动、cgroup 版本、内核版本与运行中引擎类型。
- **docker info 的 Registry Mirrors 段**：镜像加速是否生效的直接依据。
- **关注点**：两条命令的版本号应一致，Server 段内容才反映真实运行环境。

```bash
docker version
docker info

# 只看版本号
docker --version
docker version --format '{{.Server.Version}}'
```

> 报错 Cannot connect to the Docker daemon 时，docker version 会出现 Client 段但没有 Server 段。这是判断"客户端正常、守护进程异常"的最快依据，比逐条读日志高效得多。

**速记**：**version 看两端版本，info 看引擎全貌**。



#### 常见安装报错与处置

**四类报错**：安装后的报错集中在连不上守护进程、权限不足、端口占用与 WSL 集成未开四类，每一类都有对应的处置路径。

- **Cannot connect to the Docker daemon at unix:///var/run/docker.sock**：守护进程未运行或套接字路径不对，用 systemctl status docker 确认并启动。
- **permission denied while trying to connect to the Docker daemon socket**：当前用户不在 docker 组，加入组并重新登录，或改用 rootless 模式。
- **端口占用**：映射的宿主机端口已被占用，改用其他端口，或用 ss -lntp 查出占用进程再处理。
- **WSL 集成未开**：Windows 下当前发行版未在 Desktop 设置中启用集成，开启后重启终端即可。

```bash
# 守护进程状态与日志
sudo systemctl status docker
sudo journalctl -u docker --no-pager -n 50

# 当前用户所在组
groups

# 查看端口占用
sudo ss -lntp | grep 8080
```

> [!WARNING]
> **警告内容**：用 sudo 临时绕过权限报错只是掩盖问题，且 docker 组等价 root 权限这一点必须知悉。多人环境请改用 rootless 或受控的远程 API，而不是让所有人都进 docker 组。

**速记**：四类报错——**守护进程没起、权限不在组、端口被占、WSL 集成没开**。



### 卸载与清理

#### 各平台卸载路径

**卸载原则**：卸载分两步，先移除程序包，再清理数据目录；只删程序不删数据会留下大量磁盘占用与旧配置。

- **Ubuntu/Debian**：sudo apt purge docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin docker-ce-rootless-extras。
- **RHEL 系**：sudo dnf remove docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin。
- **macOS**：退出 Docker Desktop 后删除应用，必要时按其官方卸载说明清理；Colima 用 colima delete，OrbStack 直接删除应用。
- **Windows**：在设置的应用列表中卸载 Docker Desktop，或执行 winget uninstall Docker.DockerDesktop。
- **通用原则**：程序与数据分离卸载，卸载前先确认数据是否需要备份。

```bash
# Debian/Ubuntu 卸载并清理仓库与密钥
sudo apt purge -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo rm -f /etc/apt/sources.list.d/docker.sources
sudo rm -f /etc/apt/keyrings/docker.asc

# RHEL 系
sudo dnf remove -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
```

> [!TIP]
> **建议内容**：重装前先卸载干净，尤其是残留的 daemon.json 与镜像存储。否则新装的引擎可能读到旧配置或旧数据，把环境问题伪装成安装失败，白白浪费排查时间。

**速记**：卸载两步——**卸包，再删仓库与密钥**。



#### 残留目录与数据清理

**残留目录**：容器相关数据集中在少数目录，卸载程序不会自动删除，需要手工清理，且删除后不可恢复。

- **/var/lib/docker**：镜像、容器、卷、网络与守护进程状态的默认根目录。
- **/var/lib/containerd**：containerd 的镜像存储与快照数据；29.0 起镜像层位于 /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/。
- **29.0 之前的路径**：镜像层在 /var/lib/docker/overlay2/ 下，容器合并文件系统在 /var/lib/docker/rootfs/overlayfs/ 下。
- **/etc/docker**：配置目录，含 daemon.json。
- **桌面平台**：macOS 与 Windows 的数据在 Desktop 托管的虚拟机磁盘映像内，用 Reset 或在卸载时选择删除数据。
- **rootless 模式**：数据位于用户家目录的 ~/.local/share/docker。

```bash
# 彻底清理（确认无需保留数据后再执行）
sudo rm -rf /var/lib/docker
sudo rm -rf /var/lib/containerd
sudo rm -rf /etc/docker

# rootless 用户
rm -rf ~/.local/share/docker
```

> [!CAUTION]
> **注意内容**：删除上述目录会永久清除全部本地镜像、容器与卷数据，其中可能包含未备份的数据卷。执行前先用 docker volume ls 与 docker ps -a 确认没有需要保留的内容。

**速记**：三处残留——**/var/lib/docker、/var/lib/containerd、/etc/docker**。
