## 容器资源限制与运行时约束

### 资源限制的落地机制

#### cgroup 的两代：v1 与 v2

**cgroup（control group，控制组）**：是 Linux 内核用来对一组进程做资源计量与限制的机制，Docker 的每一个资源旋钮最终都落成一个 cgroup 参数。它有两代实现，**cgroup v1** 是各控制器分挂的多个独立层级，**cgroup v2** 是收敛到一棵树上的单一层级。

- **v1 的组织方式**：CPU、内存、块设备 IO、pids 等控制器各自挂载在 /sys/fs/cgroup 下的独立目录中，如 cpu、memory、blkio、pids，各管一摊。
- **v2 的组织方式**：所有控制器统一挂在 /sys/fs/cgroup 这一棵树上，用 cgroup.controllers 声明可用控制器，用 cgroup.subtree_control 逐层启用。
- **文件命名不同**：v1 用 cpu.cfs_quota_us、memory.limit_in_bytes、blkio.weight 这类名字；v2 收敛为 cpu.max、memory.max、io.weight 等。
- **量纲差异**：v2 的 cpu.weight 与 v1 的 cpu.shares 刻度不同（v2 默认 100，v1 默认 1024），Docker 在写入时做换算，用户仍按 --cpu-shares 的 1024 口径书写即可。
- **能力差异**：v2 下部分较老的实时调度旋钮不再可用，官方 daemon 选项说明中标注 not supported with cgroups v2 的即为这一类。

> [!NOTE]
> **提醒内容**：Docker 对两代 cgroup 都支持，命令行参数在两代下的语义一致，差别落在内核里的落点文件与个别能力。因此本篇只讲参数语义，具体文件名按代区分。

**速记**：v1 分目录各管一摊，v2 统一一棵树；参数语义一致，落点文件不同。



#### 判断当前主机用哪一代

**判断口径**：主机跑的是哪一代，看 docker info 的 Cgroup 相关字段，或直接看 /sys/fs/cgroup 的文件系统类型，两条路可互相印证。

```bash
# 路径一：看守护进程自报
docker info | grep -i cgroup        # 关注 Cgroup Driver 与 Cgroup Version 两行

# 路径二：看内核实际挂载
stat -fc %T /sys/fs/cgroup          # v2 输出 cgroup2fs，v1 输出 tmpfs
ls /sys/fs/cgroup/cgroup.controllers  # 文件存在即为 v2 的统一层级
```

- **Cgroup Version 字段**：显示 1 或 2，是最直接的依据。
- **Cgroup Driver 字段**：显示 cgroupfs 或 systemd；按官方 daemon 文档，未显式指定时，v1 主机默认 cgroupfs，v2 主机在 systemd 可用时默认 systemd。
- **文件系统类型**：v2 的 /sys/fs/cgroup 是 cgroup2 类型，v1 是 tmpfs，此判据不依赖 Docker。
- **cgroup.controllers 的存在性**：这是 v2 独有的顶层文件，只看它也能区分。

> 容器内判断要更谨慎：cgroupns 取 private 时容器看到的是以自身为根的裁剪视图，此时 stat 的结果反映的是挂载方式而非宿主上真正的层级划分，需要看宿主侧。另外 docker inspect 里没有直接给代际的字段，别去那里找。

**速记**：docker info 看 Cgroup Version，stat 看 cgroup2fs 还是 tmpfs，两法互验。



#### 容器在 cgroup 树中的位置

**定位方式**：容器的 cgroup 目录名由驱动与容器 ID 决定，v2 下 systemd 驱动的典型路径是 /sys/fs/cgroup/system.slice/docker-完整 ID.scope，v1 下则按控制器分散在各自的目录里。

```bash
# v2 + systemd 驱动：按容器 ID 定位
CID=$(docker inspect -f '{{.Id}}' web)
ls /sys/fs/cgroup/system.slice/docker-$CID.scope/

# v1：按控制器分别定位
ls /sys/fs/cgroup/memory/docker/$CID/
ls /sys/fs/cgroup/cpu/docker/$CID/

# 容器内（cgroupns=private）直接看自己的视图
docker exec web sh -c 'cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes'
```

- **可直接读取的关键文件（v2）**：cpu.stat 记统计、cpu.max 记配额、memory.current 与 memory.max 记当前与上限、memory.stat 记细分、pids.current 与 pids.max 记进程数。
- **v1 的对应文件**：cpu.stat、cpu.cfs_quota_us 与 cpu.cfs_period_us、memory.usage_in_bytes 与 memory.limit_in_bytes、memory.stat、pids.current 与 pids.max。
- **路径随驱动变化**：cgroup 驱动为 cgroupfs 时容器目录形如 /sys/fs/cgroup/docker/ID，不再是 system.slice 下的 scope。
- **只在运行中的容器有值**：容器停止后对应 cgroup 目录随之消失，历史数据要提前采集。

> [!TIP]
> **建议内容**：把容器内 /sys/fs/cgroup 视为最可信的现场证据。docker stats 是加工后的展示值，而这里读到的是内核原始计数，两者对不上时以内核文件为准。

**速记**：v2 在 system.slice 下找 docker-ID.scope，v1 按控制器分目录；容器内 private 视图可直接读。



#### --cgroup-parent 与 --cgroupns

**--cgroup-parent**：指定容器 cgroup 的父节点，用于把一批容器收拢到同一棵子树下统一管理或施加外层配额。**--cgroupns**：指定容器使用哪个 cgroup 命名空间，取值 host 或 private。

- **--cgroup-parent 的作用**：既可由守护进程级设默认，也可在 docker run 上逐容器指定，后者优先。
- **默认父节点**：按官方 daemon 文档，cgroupfs 驱动下默认是 /docker，systemd 驱动下默认是 system.slice。
- **两种驱动的写法差别**：cgroupfs 下写 /foobar 是从根 cgroup 起建、写 foobar 是在守护进程 cgroup 之下建；systemd 下要写切片名，如 user-a-b.slice。
- **--cgroupns=private**：容器看到以自身 cgroup 为根的视图，读到的 memory.max 就是自己的上限，这是现行默认。
- **--cgroupns=host**：容器与宿主共享 cgroup 命名空间，看到的整棵树与宿主一致，排障时有用，但可读范围扩大。

> 守护进程级的默认命名空间模式由 daemon 选项 default-cgroupns-mode 决定，官方文档标注其默认值为 private（该容器级选项自 API 1.41 起提供）。私有视图让容器内的 cgroup 文件读起来更直观，也让进程无法轻易向上修改宿主的层级配置。

**速记**：--cgroup-parent 定父节点（默认 /docker 或 system.slice），--cgroupns 定视图（现行默认 private）。



### CPU 限制

#### --cpus：绝对配额

**--cpus**：按核数给容器设定 CPU 使用上限，取值是小数，1.5 表示该容器至多可用到 1.5 个核的算力，与宿主机总核数无关。

```bash
docker run -d --name api --cpus="1.5" node:24-alpine
docker inspect -f '{{.HostConfig.NanoCpus}}' api   # 单位是纳核，1.5 显示为 1500000000
```

- **语义是上限而非保障**：它保证容器不会用到超过 1.5 个核的算力，但不保证一定拿得到 1.5 个核，忙时仍可能被别的容器挤占。
- **计量基于时间片**：内核按周期统计容器内所有进程累计消耗的 CPU 时间，超过配额后把该容器限流，直到下一个周期。
- **是全容器口径**：容器内所有进程、线程加总计入，不是每个进程各有一份 1.5 核。
- **底层是周期与配额的组合**：按官方文档，--cpus="1.5" 等价于 --cpu-period="100000" 与 --cpu-quota="150000"。

> --cpus 是最常用的 CPU 限制旋钮，可读性好、跨 v1 与 v2 语义一致。需要精确控制短时突发时才去动底层的 --cpu-period 与 --cpu-quota。

**速记**：--cpus 是核数口径的硬上限，1.5 等于至多 1.5 个核，底层是周期与配额。



#### --cpu-shares：相对权重

**--cpu-shares**：设定容器在 CPU 资源竞争时的相对权重，默认值为 1024；多个容器争抢同一批 CPU 时间时按权重比例分配，空闲时不限制。

- **只在有竞争时生效**：这是官方文档明说的软限制，CPU 充裕时所有容器都能用满所需，权重不起作用。
- **按比例而非按额度**：两个容器分别设 1024 与 512，争抢时前者大致拿后者的两倍时间，而不是固定拿多少核。
- **不预留也不封顶**：它既不保证任何具体份额，也不限制绝对用量，与 --cpus 是两种正交的语义。
- **默认值可下调**：不设时权重为 1024，想压低某容器优先级就把它设成小于 1024 的值，如 256。

> [!IMPORTANT]
> **重要内容**：--cpu-shares 与 --cpus 常被混为一谈。前者是相对权重，只有在资源紧张时才体现差别；后者是绝对上限，任何时刻都生效。想限制某个容器不得抢太多用 --cpus，想调整容器之间的相对优先级用 --cpu-shares。

**速记**：--cpu-shares 是竞争时的相对权重，默认 1024，空闲不限、紧张按比例。



#### --cpuset-cpus：绑核

**--cpuset-cpus**：把容器可用的物理 CPU 限定在指定的核上，取值为逗号分隔的列表或连字符范围，核号从 0 开始。

```bash
docker run -d --name db --cpuset-cpus="0-3" mysql:8.4
docker run -d --name worker --cpuset-cpus="1,3" node:24-alpine
```

- **作用是绑定而非限额**：它规定容器只能在哪几个核上被调度，不规定能用多少算力，容器在这几个核上仍可跑满。
- **用途一：隔离关键负载**：把数据库绑到固定的几个核，避免被同机上其他容器反复抢占。
- **用途二：缓存局部性**：进程固定在核上运行，L1、L2 缓存与 NUMA 亲和更稳定，与操作系统中处理器亲和性的道理一致。
- **代价**：可用核数变少，容器内的并行度上限被压低，负载不均时这几个核忙不过来而其他核闲置。
- **与 --cpus 的叠加**：两者可同时使用，绑核决定在哪跑，配额决定能跑多少。

> 绑核适合核数较多、负载特征明确的服务，不适合核数本来就紧张或负载波动很大的场景。它也是排查 CPU 抖动时的常用手段，把干扰源隔开后再看指标是否恢复平稳。

**速记**：--cpuset-cpus 管在哪几个核上跑，--cpus 管能跑多少，绑核要付并行度上限的代价。



#### --cpu-quota 与 --cpu-period：底层换算

**--cpu-period**：CPU 完全公平调度器（CFS）的调度周期，单位微秒，默认 100000 微秒即 100 毫秒。**--cpu-quota**：在一个周期内允许容器消耗的微秒数，超出即被限流，它才是生效的上限。

- **换算关系**：可用核数等于配额除以周期，如 150000/100000 等于 1.5 个核，50000/100000 等于 0.5 个核。
- **--cpus 是封装**：命令行的 --cpus 会被换算成这两个值写入 cgroup，官方文档把 --cpus 表述为二者组合的等价写法。
- **一般不改周期**：官方文档明确多数用户不必调整 --cpu-period，需要时优先用 --cpus。
- **写入落点不同**：v1 落到 cpu.cfs_quota_us 与 cpu.cfs_period_us，v2 落到统一表示配额与周期的 cpu.max。

```bash
# 下面两条命令对 CPU 限制而言等价
docker run -d --cpus="0.5" nginx
docker run -d --cpu-period=100000 --cpu-quota=50000 nginx

# 查看限流统计
docker exec nginx cat /sys/fs/cgroup/cpu.stat
```

```text
nr_periods 1234
nr_throttled 37
throttled_usec 1850000
```

- **限流统计怎么读**：nr_throttled 是被限流的周期数，throttled_usec 是累计被限流的微秒数，二者持续增长说明配额偏紧。

> [!NOTE]
> **提醒内容**：配额设得过低会把容器压成周期性卡顿，表现为响应时间出现规律性尖峰。看到 cpu.stat 中 throttled_usec 快速增长而 CPU 利用率并不高，就该考虑放宽配额或改用 --cpu-shares。

**速记**：可用核数等于 quota 除以 period，默认周期 100000，--cpus 是二者的封装。



#### 三种 CPU 旋钮的适用判断

**判断依据**：按要解决的问题选旋钮——要封顶用 --cpus，要排优先级用 --cpu-shares，要指定运行位置用 --cpuset-cpus。

- **--cpus 适用**：单容器不得吃满整机 CPU，如共享宿主机上的 Web 服务、CI 构建任务。
- **--cpu-shares 适用**：多个同类容器并存、希望忙时让重要服务先拿到时间片，如网关与后台任务同机。
- **--cpuset-cpus 适用**：负载特征稳定、需要缓存亲和或隔离干扰源，如数据库、实时音视频处理。
- **组合使用**：先按位置绑核，再用 --cpus 封顶，最后用 --cpu-shares 在绑定的核内排优先级，三层各司其职。
- **不要叠义词**：同时写 --cpus 与 --cpu-quota 容易产生困惑，二者表达同一件事，保留可读性更好的那个即可。

> 判断顺序可概括为：位置、上限、权重。先确定在哪跑，再确定最多跑多少，最后确定和邻居比谁优先。顺序颠倒时会出现「限了算力却没限制它占哪些核」之类的漏洞。

**速记**：封顶用 --cpus，排优先级用 --cpu-shares，定位置用 --cpuset-cpus；顺序是先位置、后上限、再权重。



### 内存限制

#### -m 与 --memory：硬上限

**-m 或 --memory**：给容器设定可用的内存硬上限，容器内所有进程的物理内存用量合计不得越过该值，越过即触发内核的内存回收乃至 OOM 处理。

```bash
docker run -d --name api -m 512m --memory-swap 512m node:24-alpine
docker inspect -f '{{.HostConfig.Memory}}' api     # 单位字节，512m 显示为 536870912
```

- **语法与单位**：接受 b、k、m、g 后缀，如 512m、1g，不写后缀按字节计。
- **最小值**：按官方文档，设置该选项时允许的最小值是 6m，低于此值容器无法启动。
- **写进去的位置**：v1 落到 memory.limit_in_bytes，v2 落到 memory.max，容器内可直接读。
- **是全容器口径**：容器内所有进程、页缓存与内核记账之和计入，不是主进程单独一份。

> [!IMPORTANT]
> **重要内容**：设置内存硬上限是共享宿主机上最重要的一个旋钮。不设上限时，一个内存泄漏的容器可以吃光整机内存，进而让内核去杀宿主上的其他进程，故障范围从单个服务扩大到整台机器。

**速记**：-m 是整容器内存硬上限，最小 6m，越界即触发回收与 OOM。



#### --memory-swap 与 --memory 的联动

**--memory-swap**：内存加交换空间的总量上限，是 --memory 的修饰项，只有同时设置了 --memory 才有意义；它不单独存在。

- **正整数**：与 --memory 同时设置，表示内存加交换的总量，交换额度等于两者之差，如 --memory="300m" 配 --memory-swap="1g" 可再用 700m 交换。
- **不设置 swap 项**：只要设了 --memory，容器可用的交换额度默认与内存相等，即 300m 内存可再配 300m 交换，总计 600m。
- **等于 --memory**：表示容器完全不能使用交换，这是禁用交换的标准写法。
- **设为 0**：该设置被忽略，按未设置处理，不是「零交换」的意思。
- **设为 -1**：允许使用不限量的交换，上限只受宿主可用交换空间约束。

```bash
# 下限内存、禁用交换：推荐给延迟敏感的服务
docker run -d --name api -m 512m --memory-swap 512m app:1.0

# 允许交换：适合内存峰值大但可容忍换页延迟的批处理
docker run -d --name batch -m 512m app:1.0
```

> [!WARNING]
> **警告内容**：禁用交换的容器一旦触到内存上限就没有缓冲，直接进入 OOM 处理；允许交换的容器虽不容易被杀，却可能因频繁换页而变得极慢，出现「没死但卡住」的现象。两者都不是万全，关键是为应用留出足够的内存余量。

**速记**：不设 swap 额度等于内存数，相等即禁交换，0 按未设处理，-1 为不限。



#### --memory-reservation：软限制

**--memory-reservation**：内存软限制，设定一个比 --memory 更小的目标值，在宿主机出现内存竞争或低内存时，内核会尽量把该容器的用量压回这个值，但它不构成硬性保证。

- **必须小于硬上限**：官方文档要求它低于 --memory 才能生效，等于或大于硬上限时不起作用。
- **只在压力下激活**：内存充裕时不限制容器使用，只有宿主紧张时才压回。
- **不保证不越界**：它是软限制，容器在硬上限之内仍可能超过软限制，故不能当作安全边界。
- **与硬上限的分工**：软限制用于让不重要的容器在紧张时先让出内存，硬上限才是真正兜底的那道线。

> [!NOTE]
> **提醒内容**：软限制容易给人「已限制」的错觉。真正决定容器会不会被杀的是 --memory，排查内存问题时先看硬上限与 memory.max，再考虑软限制是否合理。

**速记**：--memory-reservation 是压力下才压回的软限制，必须小于硬上限，不保证不越界。



#### --oom-kill-disable 与 --oom-score-adj

**--oom-kill-disable**：关闭容器的 OOM Killer，使内核内存耗尽时不杀该容器内的进程。**--oom-score-adj**：调整容器进程的 OOM 评分，影响内存紧张时谁先被杀，取值范围 -1000 到 1000。

- **--oom-kill-disable 的前提**：官方文档强调只能在同时设置了 -m 的容器上使用；不设内存上限就关闭 OOM Killer，宿主内存耗尽时内核可能转而杀宿主上的关键进程。
- **关闭后的表现**：容器不会被杀，但内存分配会失败，应用可能卡死或报内存不足错误，故障从「崩溃」变成「假死」。
- **--oom-score-adj 的方向**：值越低越不容易被杀，值越高越容易被杀；把它设成极端负值等于人为干预内核的保护机制。
- **宿主的差别对待**：按官方文档，Docker 会调低守护进程自身的 OOM 优先级使其不易被杀，但不会调整容器的 OOM 优先级。

```bash
# 只在确有必要且已设内存上限时使用
docker run -d --name db -m 1g --oom-kill-disable mysql:8.4

# 调整被杀倾向（谨慎）
docker run -d --name batch -m 512m --oom-score-adj 500 app:1.0
```

> [!CAUTION]
> **注意内容**：官方文档明确不建议把 --oom-score-adj 设成极端负值，或用 --oom-kill-disable 绕过内核的自我保护，这会让内存耗尽的后果从单容器崩溃扩散到宿主不稳定。以设好内存上限、留足余量为正解。

**速记**：--oom-kill-disable 需先设 -m 且会把崩溃变假死；--oom-score-adj 越低越不易被杀，官方不建议走极端。



#### 内存溢出在容器内的表现

**溢出过程**：容器内存接近上限时，内核先在 cgroup 内回收可回收的页缓存与可换出的匿名页；回收不足以满足分配请求时，才由 OOM Killer 在容器内选一个进程发送 SIGKILL。

- **第一步是回收**：clean page cache 与可换出的页优先被释放，此时应用只觉得变慢，尚未报错。
- **第二步是失败或被杀**：无法回收时，分配方可能拿到内存不足错误，也可能被 OOM Killer 直接杀死，取决于内核当下的选择。
- **被杀后的容器状态**：主进程若被杀，容器随即退出，退出码为 137，inspect 的 State.OOMKilled 为 true。
- **典型日志**：容器日志里常能看到分配失败或进程被杀的线索，配合宿主的 dmesg 可确认是 cgroup OOM 而非宿主整体 OOM。
- **观察指标**：memory.events 中的 oom 与 oom_kill 计数可反映发生次数，memory.stat 的 pgmajfault 升高则提示换页压力。

```bash
# 观察是否发生过 cgroup 内 OOM
docker exec web cat /sys/fs/cgroup/memory.events
```

```text
low 0
high 12
max 3
oom 1
oom_kill 1
```

- **计数怎么读**：max 是触到硬上限的次数，oom 是进入 OOM 处理的次数，oom_kill 是真正杀掉进程的次数。

> 内存溢出在容器里不是一次性事件，而是先限流、后回收、再杀进程的连续过程。看到应用先变慢再被杀，往往是内存上限设得过紧而非应用突然崩溃。

**速记**：先回收页缓存、再分配失败或杀进程；被杀即退出码 137 且 OOMKilled 为 true，看 memory.events 计数。



### OOM 与退出码

#### 退出码 137 的含义

**退出码 137**：等于 128 加 9，表示进程是被 SIGKILL 强杀的，是容器最常见的一种异常退出。

- **来源一：内核 OOM Killer**：容器内存越限被内核杀死，属资源问题。
- **来源二：docker stop 超时强杀**：docker stop 先发 SIGTERM，宽限期（默认 10 秒）内不退则补发 SIGKILL，属停止方式问题。
- **来源三：docker kill**：直接发送 SIGKILL，立即终止，属人为操作。
- **同码不同因**：三种来源在 docker ps 里都显示 Exited (137)，单看退出码无法区分。

> [!IMPORTANT]
> **重要内容**：137 只说明「被 SIGKILL 杀了」，不说明「为什么被杀」。把 137 直接等同于内存不足是排障中最常见的误判，正确做法是再查一个字段来定因。

**速记**：137 等于 128 加 9，是被 SIGKILL 强杀；OOM、stop 超时、kill 三种来源都可能是它。



#### 区分 OOM Kill 与 stop 超时强杀

**区分手段**：用 docker inspect 读 State.OOMKilled 字段，为 true 即内核 OOM Kill，为 false 则 137 多半来自 stop 超时或手动 kill。

```bash
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' web
```

```text
137 true
```

- **OOMKilled=true**：内核判定容器内存越限并杀了进程，方向转向内存上限与用量。
- **OOMKilled=false**：不是内存问题，检查是否执行过 docker stop 或 docker kill，以及停止宽限期是否够长。
- **辅助线索一**：docker ps 的 STATUS 列给出退出码与时间，配合操作记录判断当时是否有人停止容器。
- **辅助线索二**：宿主 dmesg 中出现 cgroup 相关的 OOM 记录可佐证。

> [!NOTE]
> **提醒内容**：处理慢的服务被 stop 强杀是常见误伤，尤其是正在刷盘或写事务的数据库。给这类容器加 --stop-timeout 或在停止时传 -t 更长的秒数，比事后排查「为什么又被杀了」更省事。

**速记**：先看 OOMKilled，true 是内存杀、false 查 stop 与 kill；停止宽限期不足是常见误伤源。



#### 139、143 与 0 的对照

**退出码规则**：通用规律是 128 加信号编号，0 表示正常结束，据此可快速判断容器的终止方式。

- **0**：进程正常结束，属预期退出，多用于一次性任务容器。
- **137**：128 加 9，收到 SIGKILL，被强杀。
- **139**：128 加 11，收到 SIGSEGV，进程发生段错误，指向程序自身的 bug 或非法内存访问。
- **143**：128 加 15，收到 SIGTERM，通常是收到停止请求后正常响应退出，属礼貌退出留下的码。
- **126 与 127**：126 表示命令无执行权限，127 表示命令不存在，属启动阶段问题，与运行期信号无关。

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}'
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' web
```

> 143 与 137 的对照最能说明问题：同一次 docker stop，若应用正确响应了 SIGTERM，退出码就是 143；若响应不了被补发 SIGKILL，退出码就是 137。这也解释了为什么同一个容器在不同停止时机下会给出不同退出码。

**速记**：0 正常、137 被 SIGKILL、139 段错误、143 收到 SIGTERM；规律是 128 加信号编号。



### 磁盘与块设备 IO

#### --blkio-weight：相对权重

**--blkio-weight**：块设备 IO 的相对权重，竞争同一设备时按权重比例分配 IO 带宽，取值 10 到 1000，默认 0 表示不启用。

- **语义同 --cpu-shares**：只在有竞争时生效，设备空闲时不限制，属相对优先级而非绝对限速。
- **默认不启用**：官方命令行参考标注默认值为 0，即不设权重；需要区分优先级时才显式指定。
- **按容器整体计**：权重作用于该容器的全部块设备读写，不区分读与写。
- **落点变化**：v1 落到 blkio.weight，v2 归入统一的 io 控制器下。

> 权重的作用是让重要服务在同盘竞争时先拿到 IO 带宽，它不能防止某个容器把磁盘打满的瞬时冲击，要拦住冲击得用后面的绝对限速。

**速记**：--blkio-weight 是竞争时的相对权重，10 到 1000，默认 0 不启用。



#### 绝对限速：bps 与 iops

**绝对限速四件套**：按字节速率限用 --device-read-bps 与 --device-write-bps，按每秒 IO 次数限用 --device-read-iops 与 --device-write-iops，四者都针对具体设备。

- **写法**：设备路径冒号限值，bps 支持 b、k、m、g 后缀，iops 写整数。
- **读写分开限**：读与写各自一个旋钮，可按负载特征只限其中一侧。
- **与权重的关系**：权重管相对分配，bps 与 iops 管绝对上限，二者可同时使用。
- **需要指定设备**：均须给出宿主机上的设备路径，写错路径参数不生效。

```bash
# 限制对 /dev/sda 的读速率与写次数
docker run -d --name backup \
  --device-read-bps /dev/sda:10mb \
  --device-write-bps /dev/sda:5mb \
  --device-write-iops /dev/sda:500 \
  backup:1.0
```

> 块设备限速对写入路径的实际约束力取决于是直接 IO 还是经过页缓存的缓冲写。经过缓存时，限速可能只作用于最终落盘的那一段，应用侧看到的写速度未必立即受限。压测验证限速是否生效，而不是假定它一定生效。

**速记**：bps 限字节速率、iops 限每秒次数，读写各一个旋钮，均须指名设备路径。



#### 需要限制 IO 的场景

**适用判断**：当同一块盘上存在多个互相争抢的写入方，且某一方的突发 IO 会拖慢其他方时，就值得给这一方加 IO 限制。

- **多租户同宿主机**：多套业务共盘运行，防止某个容器的批量写入把盘占满。
- **备份与归档任务**：备份容器顺序读大量数据，不限速会挤占在线服务的磁盘带宽。
- **日志密集写入方**：某服务日志量突增时，用写限速把它挡在关键服务的 IO 之外。
- **与容量限制的分工**：IO 限制管的是一段时间内的速率，磁盘容量与配额管的是总量，两者解决的不是同一问题。

> 限制 IO 会带来直接的性能代价，设得过紧会让被限方自身超时。判断要点是：这台盘上的 IO 是否真的彼此影响，以及被限方的业务能否承受更慢的读写。

**速记**：多租户共盘、备份抢带宽、日志突增这三类场景值得设 IO 限制，设前先确认 IO 确实互相干扰。



#### 对 overlay 存储的效果边界

**现实提醒**：容器读写落在 overlay 之类的联合文件系统上时，块设备限速与权重对容器内文件操作的实际约束往往弱于预期。

- **原因一：多层合并**：写操作先落在容器可写层，再经文件系统合并到块设备，限速在块设备这一层生效，容器内看到的速度与它不一定同步。
- **原因二：页缓存介入**：缓冲写先入页缓存，宿主的回写时机由内核决定，短时高峰可能不被限速拦住。
- **原因三：v2 下控制器改名**：块设备控制器在 v2 中并入 io 控制器，旧文档里的 blkio 写法需对照 v2 的 io.weight 与 io.max 理解。
- **应对方针**：把 IO 限制当作削峰而非精确控速的手段，必要时用带独立盘或独立卷的部署方式从物理上隔开。

> 需要精确控制磁盘速率时，更稳的做法是先把数据盘或卷拆开，再在拆开的设备上施加限速。仅靠容器参数去约束共享块设备，得到的往往是方向正确、精度不足的效果。

**速记**：overlay 上 IO 限制易被多层合并与页缓存稀释，把它当削峰手段，精确控速靠拆盘。



### 进程数与文件描述符

#### --pids-limit：限定进程总数

**--pids-limit**：限制容器内可创建的进程与线程总数，取值是整数，显式写 -1 表示不限。

- **防护目标**：防止容器内程序失控或恶意行为反复 fork 出大量进程把宿主拖垮，即典型的 fork 炸弹。
- **计数口径**：统计的是进程与线程合计，与 docker stats 的 PIDS 列口径一致。
- **默认值**：不设置时由守护进程按默认放行，未显式配置即为不设上限；要紧的是知道不写就没有这层保护。
- **触顶表现**：达到上限后新的 fork 或线程创建失败，应用报资源不可用错误，容器本身不一定会退出。

```bash
docker run -d --name worker --pids-limit 200 node:24-alpine
docker exec worker cat /sys/fs/cgroup/pids.max
docker exec worker cat /sys/fs/cgroup/pids.current
```

- **取值建议**：按应用正常峰值的进程与线程数留出数倍余量，既拦住失控增长，又不误伤正常的线程池扩张。

> [!IMPORTANT]
> **重要内容**：容器里一个进程崩溃前可能先疯狂创建子进程，这类故障在没有 pids 上限时会迅速耗光宿主的进程表，波及同机所有服务。给每个容器设一个合理的 --pids-limit，是成本最低的一道保险。

**速记**：--pids-limit 限进程与线程总数，防 fork 炸弹，-1 为不限，不设即无此保护。



#### --ulimit：常用项与写法

**--ulimit**：设置容器内进程的资源限制，写法为类型等号软限制冒号硬限制，未给硬限制时软限制同时用作两者。

- **常用项一 nofile**：单进程可打开的文件描述符数，长连接与高并发服务最常调大。
- **常用项二 nproc**：按官方文档，nproc 在 Linux 上限制的是单个用户可用的进程数，而不是整个容器，语义要看清。
- **常用项三 core**：核心转储文件大小，容器内一般设为 0 避免生成大文件。
- **常用项四 memlock**：可锁定在内存中的字节数，数据库与需要 mlock 的程序会用到。
- **其余可选项**：官方参考列出 core、cpu、data、fsize、locks、memlock、msgqueue、nice、nofile、nproc、rss、rtprio、rttime、sigpending、stack 等。
- **继承规则**：不指定取值时继承守护进程上的默认 ulimits；守护进程级可用 default-ulimits 统一设定，容器级 --ulimit 会覆盖它。

```bash
docker run -d --name api \
  --ulimit nofile=65536:65536 \
  --ulimit core=0 \
  node:24-alpine
docker exec api sh -c 'ulimit -n; ulimit -c'
```

```text
65536
0
```

- **两段写法的含义**：nofile=65536:65536 中冒号前是软限制、冒号后是硬限制，只写一个值时两者相同。

> [!NOTE]
> **提醒内容**：容器内 ulimit 的默认值来自守护进程，不是宿主 shell 的当前设置。高并发服务上线前应显式声明 nofile，而不是依赖环境的隐式默认，否则换一台宿主机就可能重现连接打不开的老问题。

**速记**：--ulimit 写类型等号软限制冒号硬限制，nofile 与 nproc 最常用，nproc 限的是用户，不写则继承守护进程默认。



### 设备与 GPU

#### --device：映射设备节点

**--device**：把宿主机上的设备节点映射进容器，使容器内的进程可以直接读写该设备。

- **基本写法**：宿主路径冒号容器路径，可再加冒号权限集，如 --device /dev/ttyUSB0:/dev/ttyUSB0。
- **权限集**：官方文档说明默认允许读、写与创建设备节点（r、w、m），可用第三个冒号段覆盖；容器以特权模式运行时，指定的权限会被忽略。
- **适用场景**：需要直接访问串口、USB 设备、特定块设备的容器化程序。
- **不适用场景**：官方文档指出该选项不能安全地用于临时出现的设备，因为宿主的设备插拔时机与容器启动时机难以对齐。

```bash
docker run -d --name serial-agent \
  --device /dev/ttyUSB0:/dev/ttyUSB0 \
  agent:1.0
```

> [!WARNING]
> **警告内容**：把设备节点映射进容器等于把宿主硬件的一段控制权交出去，映射错设备或权限过大都可能造成数据损坏。生产环境应遵循最小必要原则，只映射业务确实需要的设备。

**速记**：--device 按宿主路径冒号容器路径映射，默认读写加创建设备节点，特权模式下权限集被忽略。



#### --gpus 的语法与前提

**--gpus**：把 NVIDIA GPU 分配给容器使用，语法支持 all、count 与 device 三种指定方式，前提是宿主已装好 NVIDIA 的容器工具链。

- **前提条件**：官方文档要求先安装 nvidia-container-runtime（现通常以 nvidia-container-toolkit 提供），否则 --gpus 无法生效。
- **常见取值**：--gpus all 使用全部 GPU，--gpus '"device=0,2"' 指定设备，--gpus count=2 指定数量。
- **版本要求**：该选项自 API 1.40 起提供，较老的引擎需要升级。
- **与 CDI 的关系**：官方文档说明也可用 --device 以 CDI 语法指定设备，如 --device=vendor.com/class=device-name，当前仅支持 Linux 容器。

```bash
docker run --rm --gpus all nvidia/cuda:12.6-base-ubuntu24.04 nvidia-smi
docker run --rm --gpus '"device=0,1"' nvidia/cuda:12.6-base-ubuntu24.04 nvidia-smi
```

> 设备映射与 GPU 分配的安全含义——容器由此获得直接操作硬件的能力——属安全加固范畴，细节参见 容器安全实践。本篇只讲清语法与前提。

**速记**：--gpus 需 nvidia-container-toolkit，支持 all、count、device 三种写法，也可走 CDI 语法。



### 资源限制与重启策略的联动

#### --restart 四值在 OOM 场景下的差异

**联动关系**：容器因 OOM 被杀后会不会自动起来，由 --restart 的取值决定，取值有 no、on-failure、always、unless-stopped 四种，默认 no。OOM 导致的退出码是 137，属非零退出。

- **no**：不重启，容器停在 Exited (137)，适合调试或一次性任务。
- **on-failure**：因 137 属非零退出而触发重启，可用冒号加次数限制重试，如 on-failure:3。
- **always**：无论退出码都重启，内存问题未解决时会形成「OOM、重启、再 OOM」的循环。
- **unless-stopped**：与 always 类似，区别在容器被手工停止后即使守护进程重启也不再拉起。
- **重启延迟递增**：官方文档说明重启延迟从 100 毫秒起逐次翻倍，用于避免冲击宿主；容器若能稳定运行至少 10 秒，延迟重置回 100 毫秒。

```bash
docker run -d --name api --restart on-failure:3 -m 512m app:1.0
docker inspect -f '{{.RestartCount}} {{.State.OOMKilled}}' api
```

> [!CAUTION]
> **注意内容**：把内存不足的容器设成 always，等于让它进入无限重启循环，既掩盖了根因，又持续制造负载。看到 RestartCount 快速增长且 OOMKilled 为 true，应先解决内存上限与用量的矛盾，而不是继续让它自愈。

**速记**：no 不重启、on-failure 会因 137 重启且可限次、always 会无限重启成循环、unless-stopped 手工停后不复活。



#### 用 on-failure 与重启次数观察故障

**观察方法**：把重启策略当作观测工具而非修复手段——用 on-failure 加次数上限让故障容器重试有限次，再通过 RestartCount 与事件流判断故障性质。

- **第一步设上限**：用 on-failure:3 之类的写法限定重试次数，避免无限循环淹没日志。
- **第二步读计数**：docker inspect 的 RestartCount 给出已重启次数，配合 State.OOMKilled 判断是否内存问题。
- **第三步看事件**：docker events 实时给出 start、die、restart 等事件，可还原重启的时间序列。
- **第四步定归属**：分清是应用自身崩溃、内存越限，还是外部编排在重复拉起，三者处置完全不同。
- **区分守护进程重启**：官方文档说明 on-failure 在守护进程重启后不会恢复重启行为，这与 always 不同，判断谁在重启它时要把这一条考虑进去。

```bash
docker inspect -f '{{.RestartCount}}' api
docker events --filter container=api --filter event=restart
```

> [!IMPORTANT]
> **重要内容**：容器反复起来又退出，第一反应常是怀疑编排出了问题，但更常见的原因是应用崩溃或内存越限被内核杀死。先读退出码与 OOMKilled，再谈是不是编排行为，可以省下大量走错方向的排查。

**速记**：on-failure 加次数上限做重试、RestartCount 看次数、events 看时序，再判断是应用崩溃还是编排拉起。



### 观察与度量

#### docker stats 各列含义与 --no-stream

**docker stats**：实时显示容器的 CPU、内存、网络与块设备 IO 用量的命令，默认流式刷新，加 --no-stream 只取一次快照。

- **CPU % 与 MEM %**：容器占用的宿主 CPU 与内存百分比，后者相对的是 LIMIT 而非宿主总量。
- **MEM USAGE / LIMIT**：左侧是当前内存用量，右侧是允许使用的上限，未设限时显示宿主可用内存。
- **NET I/O 与 BLOCK I/O**：网络与块设备上的收发、读写累计量。
- **PIDs**：容器创建的进程与线程数，与 --pids-limit 的口径一致。
- **内存用量的口径**：按官方文档，Linux 上 CLI 报告的内存用量是从总用量中扣除了缓存部分后的值，缓存按 cgroup 版本取 memory.stat 中的 inactive_file（v2）或 total_inactive_file（v1）。

```bash
docker stats --no-stream web
docker stats --no-stream --format '{{.Name}} {{.CPUPerc}} {{.MemUsage}} {{.MemPerc}} {{.PIDs}}'
```

```text
web 0.03% 12.3MiB / 512MiB 2.40% 5
```

- **脚本友好写法**：--format 支持 table、json 与自定义模板，采集时优先用 --no-stream 加 --format，避免流式输出阻塞脚本。
- **注意口径差异**：MEM USAGE 扣缓存后的值与容器内 free 报告的读数口径不同，判断逼近上限的程度要看向 LIMIT 逼近的幅度。

> docker stats 是加工后的展示值，适合快速判断趋势，不适合当作精确证据。需要核实某一刻的真实用量时，读容器内 /sys/fs/cgroup 下的 memory.current 与 memory.max。

**速记**：stats 看 CPU%、MEM USAGE/LIMIT、NET、BLOCK、PIDS，--no-stream 取快照，Linux 上内存用量已扣缓存。



#### 没有 docker stats 时直接读 cgroup 文件

**替代手段**：无法使用 docker stats 时，直接读 cgroup 文件即可获得原始度量，这也是核实展示值是否准确的办法。

- **CPU 统计**：cpu.stat 给出被限流的周期数与时长，v2 记 throttled_usec，v1 记 throttled_time。
- **CPU 配额**：v2 读 cpu.max 得到配额与周期，v1 读 cpu.cfs_quota_us 与 cpu.cfs_period_us。
- **内存现状与上限**：v2 读 memory.current 与 memory.max，v1 读 memory.usage_in_bytes 与 memory.limit_in_bytes。
- **内存事件**：v2 的 memory.events 给出 high、max、oom、oom_kill 计数，是判断是否发生过内存越限的直接证据。
- **进程数**：读 pids.current 与 pids.max。

```bash
# 容器内（cgroupns=private）
docker exec web sh -c 'for f in memory.current memory.max pids.current cpu.stat; do echo "== $f"; cat /sys/fs/cgroup/$f; done'

# 宿主上按容器 ID 定位
CID=$(docker inspect -f '{{.Id}}' web)
cat /sys/fs/cgroup/system.slice/docker-$CID.scope/memory.max
```

```text
== memory.current
132120576
== memory.max
536870912
== pids.current
7
== cpu.stat
nr_periods 902
nr_throttled 0
throttled_usec 0
```

- **读法提示**：内存类数值单位是字节，上限显示 max 字样表示未设限。

> 在容器内读这些文件的前提是 cgroupns 为 private，此时 /sys/fs/cgroup 即为容器自身的根；若为 host 模式，看到的路径与宿主一致，需按容器 ID 定位。

**速记**：cpu.stat 看限流、memory.current 与 memory.max 看内存、pids.current 看进程，宿主上按 docker-ID.scope 定位。



#### 容器内看 /proc 会看到宿主机信息

**反直觉现象**：容器内执行 cat /proc/meminfo 或 cat /proc/cpuinfo，看到的是宿主机的内存总量与 CPU 数量，而不是该容器的限制值，即使已经设了 -m 与 --cpus。

- **原因**：procfs 中的 meminfo 与 cpuinfo 反映的是内核的全局视图，并不随 cgroup 而裁剪，命名空间隔离的是进程、网络、挂载等，不含这两份统计。
- **后果一：运行时误判**：JVM、Node 及各类自动探测资源的库会据此按宿主规模设置线程池与堆大小，从而远超容器的实际额度。
- **后果二：并发度虚高**：按 /proc/cpuinfo 的核数决定工作线程数，在只给 1.5 核的容器里会开出一堆线程争抢，反而拖慢。
- **正确做法**：显式给运行时传参，或用支持 cgroup 感知的版本；Java 在较新版本中已能读取 cgroup 限额，Node 仍常需手工指定 --max-old-space-size。
- **另一种做法**：用 lxcfs 之类的工具把 /proc 的相应文件虚拟成容器视图，这是实践中常见的弥补手段。

```bash
# 容器内看到的是宿主信息
docker exec web sh -c 'grep -E "MemTotal|MemAvailable" /proc/meminfo; nproc'
```

```text
MemTotal:       16384000 kB
MemAvailable:    9820000 kB
8
```

- **对照**：容器实际限制可能只是 512m 内存与 1.5 核，而上面读到的是宿主的 16g 与 8 核。

> [!WARNING]
> **警告内容**：把 /proc/meminfo 当作容器的内存上限来配置应用，是内存超限被杀的常见根因——应用以为有很多内存可用，持续增长直到触到 cgroup 上限被内核杀掉。配置堆大小时一律以 -m 的值为准，必要时留出堆外内存余量。

**速记**：/proc/meminfo 与 /proc/cpuinfo 是全局视图不随 cgroup 裁剪，运行时会误判规模；以 -m 为准手工传参或用 lxcfs。



### 在 Compose 与编排层怎么设

#### 服务级字段与 deploy.resources 的关系

**两套写法**：Compose 里限制资源有两条路——服务级直接写 cpus、mem_limit 等字段，或用 deploy.resources 下的 limits 与 reservations；两者表达同一组约束，官方规范要求同写时取值一致。

- **服务级字段**：cpus、mem_limit、mem_reservation、memswap_limit、pids_limit、cpu_shares、cpu_quota、cpu_period、cpuset、oom_kill_disable、oom_score_adj、ulimits、devices、gpus。
- **deploy.resources.limits**：cpus、memory、pids，语义是平台必须阻止容器分配超过该量的资源。
- **deploy.resources.reservations**：cpus、memory、devices，语义是平台必须保证容器至少能分配到该量。
- **一致性约束**：官方 Compose 规范逐条写明，cpus 须与 deploy 的 cpus 一致，mem_limit 须与 limits.memory 一致，pids_limit 须与 deploy 的 pids 一致。
- **同一项目选一套**：两种写法混用会让文件难以阅读，也无法一眼看出哪个值生效。

```yaml
services:
  api:
    image: app:1.0
    cpus: "1.5"
    mem_limit: 512m
    pids_limit: 200
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 512M
          pids: 200
```

> [!NOTE]
> **提醒内容**：规范要求部署级与服务级取值一致，并非说必须同时写。日常单机项目选服务级字段更直观；已经按编排规范组织文件的项目统一走 deploy.resources，二者择一即可。

**速记**：服务级 cpus、mem_limit、pids_limit 与 deploy.resources 的 limits、reservations 表达同一组约束，同写须一致。



#### deploy 在非 Swarm 环境下的生效范围

**生效边界**：按 Compose 规范，deploy 是可选部分，平台未实现时整段被忽略而文件仍视为有效；实践中 docker compose（V2）会应用 deploy.resources 中与资源相关的部分，其余编排字段对单机无意义。

- **规范原文口径**：resources 描述为对平台施加的资源约束，limits 由平台阻止超配、reservations 由平台保证下限，义务落在平台而非特指 Swarm。
- **单机实际生效的部分**：limits 中的 cpus、memory、pids 与 reservations 中的 memory，会落到容器的 HostConfig 上。
- **单机无意义的部分**：mode、placement、update_config、rollback_config、endpoint_mode、replicas 属于集群编排字段，docker compose 下不产生调度行为。
- **历史差异**：旧版独立程序 docker-compose（V1）不实现 deploy，会输出忽略告警；现行 V2 是插件形态，行为不同。
- **验证办法**：部署后读 docker inspect 的 HostConfig.Memory 与 NanoCpus，为 0 说明该限制没有真正落到容器上。

```bash
docker compose up -d
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}} {{.HostConfig.PidsLimit}}' demo-api-1
```

```text
536870912 1500000000 200
```

> [!WARNING]
> **警告内容**：不要因为「deploy 属于 Swarm」这句过时说法就把资源限制整段删掉，也不要写完就假定它一定生效。唯一稳妥的做法是部署后用 docker inspect 核对，看到 HostConfig 里的数值确实是所设的值才算落地。

**速记**：deploy 未实现即被忽略而文件仍有效；V2 单机会应用 resources 的 CPU、内存、pids，其余字段留给集群；是否生效用 inspect 核对。



#### 有 limits 无 requests 的调度后果

**调度后果**：在具备调度器的编排环境里，只写上限不写下限会让调度的资源账本缺失依据，后果从节点可能被超配到请求值被自动补齐不等。

- **单机 Compose 无调度**：docker compose 只在一台机器上创建容器，没有节点选择环节，limits 与 reservations 的差别只体现在运行时约束与内存软限制上。
- **Kubernetes 的行为**：按官方文档，为某资源设置了 limits 而未设 requests 时，Kubernetes 会把该 limits 的值复制为 requests，调度据此预留资源。
- **被复制的后果**：requests 被抬到 limits 的高度后，调度器按上限预留，节点可容纳的副本数减少，容易出现资源明明空闲却调度不上的情形。
- **只给 requests 不给 limits**：容器可用量不封顶，突发时可能挤占同节点其他 Pod，两种偏向各有利弊。
- **实践取向**：为关键服务显式给出 requests 与 limits 两个值，前者按稳定负载、后者按峰值留余量，才能兼顾调度与稳定性。

> 这一条是对 多容器编排概览与向 Kubernetes 过渡 的呼应：单机 Compose 不必关心请求值，一旦进集群，limits 与 requests 的配对就成了调度正确性的前提。

**速记**：单机 Compose 无调度概念；K8s 里只写 limits 会把 limits 复制为 requests，导致按上限预留、可调度副本变少。



### 容量规划与排障套路

#### 给容器设限的三条原则

**三条原则**：先测量再设限、为运行时留出堆外余量、所有容器的限制之和低于宿主可用资源。

- **原则一先测后限**：先让容器在接近生产的负载下跑一段，观察 docker stats 的峰值与 cpu.stat 的限流计数，再据此设定，而不是凭猜测填一个整数。
- **原则二留堆外余量**：JVM 除堆之外还要用元空间、线程栈、直接内存与 JIT 代码缓存，Node 除老生代之外还要用堆外缓冲，因此 -m 必须明显大于 -Xmx 或 --max-old-space-size 的值。
- **原则三总量有账**：同一宿主上所有容器的内存限制之和，加上宿主自身与内核的开销，应小于物理内存，否则一旦同时逼近上限，宿主仍会承压。
- **为峰值而非均值为准**：按业务峰值加上安全系数设定，避免每次流量高峰都触发限流或 OOM。
- **保留调整通道**：先用宽松值上线，观察一段再收紧，比一开始就设很紧、事后不断放宽要安全。

> [!TIP]
> **建议内容**：把限制值当作需要复核的参数而不是一次性写死的常量。每次发布新版本、调整并发、更换运行时版本后，都应重新核对一次内存与 CPU 的余量。

**速记**：先测后限、堆外留余量、限制总和低于宿主可用；按峰值设、上线后复核。



#### 限制过紧与过松的典型症状

**症状对照**：限制过紧表现为容器侧频繁触碰上限，限制过松表现为宿主整体被少数容器拖累，两类症状的观察点不同。

- **过紧之内存**：容器频繁以 137 退出且 OOMKilled 为 true，memory.events 的 oom_kill 计数增长。
- **过紧之 CPU**：响应时间出现规律性尖峰，cpu.stat 的 nr_throttled 与 throttled_usec 快速增长，而整体 CPU 利用率并不高。
- **过紧之进程数**：容器内 fork 或创建线程失败，报资源不可用，pids.current 贴着 pids.max。
- **过松之内存**：某个容器用量持续增长无人制止，宿主 free 内存不断下降，最终可能触发宿主级 OOM，波及同机其他服务。
- **过松之 CPU**：某容器长时间占满多核，其他容器被明显拖慢，docker stats 中该容器 CPU% 长期高企。
- **过松之 IO**：备份或日志容器把磁盘带宽占满，在线服务的读写延迟抬升。

> 两类症状常同时出现在同一台机器上：给 A 不设限导致它抢资源，给 B 设得过紧导致 B 频繁被杀。排查时先看谁在抢、谁在触顶，再分别调整，不要只盯一个容器。

**速记**：过紧看 137、限流计数与 pids 触顶；过松看单容器吃满内存或 CPU 拖慢邻居；两类常并存，分别处置。



#### 一次完整的排查路径示例

**排查路径**：以一个接口间歇性不可用、容器偶发重启的服务为例，走一条从现象到根因的完整链路。

- **第一步看状态与退出码**：docker ps -a 发现容器状态在 Up 与 Exited (137) 之间反复，说明处于崩溃重启循环。
- **第二步定因**：docker inspect 读 State.OOMKilled 为 true、RestartCount 已积累多次，指向内存越限被杀。
- **第三步看用量与上限**：docker stats --no-stream 看到内存用量贴近 LIMIT，读容器内 memory.current 与 memory.max 确认已触顶。
- **第四步查事件计数**：读 memory.events 中 oom_kill 计数增长，佐证确实发生过内核 OOM Kill。
- **第五步查运行时配置**：进入容器核对 JVM 堆参数或 Node 的 --max-old-space-size，常发现它按 /proc/meminfo 的宿主总量设置，远高于 -m 的值。
- **第六步修正**：把堆上限下调到硬上限之下并留出堆外余量，必要时适度放宽 -m，再观察 RestartCount 是否停止增长。

```bash
docker ps -a --filter name=api
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' api
docker stats --no-stream api
docker exec api sh -c 'cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.max; cat /sys/fs/cgroup/memory.events'
docker exec api sh -c 'java -XX:+PrintFlagsFinal -version | grep -i maxheapsize'
```

> [!TIP]
> **建议内容**：把这条路径固化成检查清单——先退出码与 OOMKilled，再用量与上限，后事件与技术栈的运行时配置。顺序固定后，同类故障的定位时间会大幅缩短，也不容易在是不是编排重启的这类问题上绕圈。

**速记**：看状态码定 137、inspect 定 OOM、stats 与 cgroup 看用量上限、events 佐证、复核运行时堆参数、下调堆并复测。
