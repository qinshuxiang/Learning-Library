## 自定义网络与容器互联

### 用户自定义 bridge 网络

#### 创建网络与常用选项

**用户自定义 bridge 网络**：是由 docker network create 显式创建、名字与网段可由使用者指定的容器网络，它不随守护进程的默认配置生成，也不依赖端口映射就能让同一张网内的容器按名字互访。

- 基本创建：docker network create 网络名，不指定驱动时默认使用 bridge 驱动。
- 指定子网与网关：--subnet 接受 CIDR 形式的网段，--gateway 指定该网段上的网关地址。
- 指定分配范围：--ip-range 让容器地址只从子网内的某一段分配，便于把网关、预留地址与容器地址分开。
- 指定驱动：-d 或 --driver 选用驱动，绝大多数单机场景保持默认的 bridge。
- 打标签：--label 为网络附加元数据，docker network inspect 与按标签筛选时都能读到。
- 其它常用项：--internal 关闭出网、--attachable 允许独立容器接入 swarm 作用域网络、--scope 控制网络作用域。
- 查看结果：docker network ls 列出全部网络，docker network inspect 网络名 查看子网、网关与已接入容器。

```bash
docker network create my-net

docker network create \
  --driver bridge \
  --subnet 172.28.0.0/16 \
  --ip-range 172.28.5.0/24 \
  --gateway 172.28.5.254 \
  --label project=shop \
  shop-net

docker network ls
docker network inspect shop-net
```

> 官方 docker network create 参考页给出的示例与上面一致，--subnet、--ip-range、--gateway 三者必须落在同一网段内，写错会直接报错。未指定子网时由守护进程按 default-address-pools 自动分配，因此自定义网络的网段有时会随机器而变。

> [!IMPORTANT]
> **重要内容**：自建网络的网段不要与本机所在内网重叠。一旦重叠，容器访问内网地址或走网关出网时可能走错路由，表现为部分地址可达、部分地址超时，排查代价很高。规划时先看一眼宿主机的路由表与既有网段。

**速记**：create 三个常用选项——**--subnet 划网段、--ip-range 缩范围、--gateway 定出口**。



#### 同一网络内为何能用容器名互访

**名字互访的前提**：容器接入一张用户自定义网络后，该网络会为它登记名字，同网络的其它容器通过内嵌 DNS 把名字解析成地址，因此不必知道对方的 IP，也不必做端口映射。

- 注册来源：docker run --name 指定的容器名会被自动登记进该网络的解析表。
- 解析范围：名字解析只在同一张网络内生效，跨网络的成员看不到这个名字。
- 必须显式命名：Docker 的自动服务发现只解析自定义容器名，不解析自动生成的默认名，因此要按名字互访就必须写 --name。
- 验证方式：在同一网络的另一容器里执行 nslookup 或 getent hosts，能返回目标地址即解析已生效。
- 与端口的关系：同网容器互通走的是容器端口，不需要 -p 映射；-p 只服务于宿主机与外部访问。

```bash
docker network create app-net
docker run -d --name db --network app-net postgres:17-alpine
docker run -d --name api --network app-net my-api:1.0
docker exec api nslookup db
```

> 官方 bridge 驱动页有一处容易忽略的说明：自动服务发现只解析自定义容器名，不解析 Docker 自动生成的默认名。因此 docker run 不带 --name 起的容器，即使接入同一张网，也不能按名字找到。

> [!NOTE]
> **提醒内容**：按名字互访与端口映射是两件事。前者解决容器找容器，后者解决宿主机或外部找容器。只做内部互联的服务不必暴露任何端口，少映射一个端口就少一个对外暴露面。

**速记**：**自定义名字加同一张网等于按名互访；自动生成的默认名不参与解析**。



#### 同一容器接入多个网络

**多网络接入**：一个容器可以同时连接多张网络，每张网络各给它一个地址与一套名字，因此它既能与 A 网成员互通，也能与 B 网成员互通，充当两网之间的通道。

- 创建时接入：docker run 的 --network 可以重复书写，重复几次就接入几张网络。
- 运行中接入：docker network connect 网络名 容器名，把已在运行的容器接进新网络。
- 运行中断开：docker network disconnect 网络名 容器名，把它从某张网络摘出。
- 典型用途：反向代理或网关容器同时接入前端网络与后端网络，前端只能到网关，后端只接受网关访问。
- 名字可分网设置：同一容器在不同网络里的别名可以不同，用 docker network connect --alias 为某张网络单独取名。

```bash
docker run -d --name gateway \
  --network frontend \
  --network backend \
  nginx:1.27-alpine

docker network connect --alias proxy frontend gateway
docker network disconnect backend gateway
```

> 官方网络总览用了一个类比：把容器接入网络，等同于给一台物理主机插一根网线；主机可以同时插多张网卡，容器也可以同时接入多张网络。但要记住，不在同一张网内的两个容器仍不能按名字解析，跨网通信必须借一个同时接入两网的容器中转。

**速记**：**--network 可重复、connect 补接入、disconnect 摘出；一个容器一张网一条腿**。



#### 删除网络的前提

**删除前提**：docker network rm 只能删除没有任何容器接入的网络，仍有容器连接时命令会报错，需先断开连接或删除这些容器。

- 报错特征：提示网络仍有活动端点，即 active endpoints，删除失败。
- 逐容器断开：docker network disconnect 网络名 容器名，断开后再删除。
- 连带解除：删除容器，即 docker rm，也会解除它对该网络的占用。
- 批量清理：docker network prune 删除所有未被任何容器使用的自定义网络，执行前会提示确认。
- 不能删的：默认网络 bridge、host、none 属内置网络，删除会失败。

```bash
docker network rm shop-net
docker network disconnect shop-net gateway
docker network prune
```

> [!CAUTION]
> **注意内容**：docker network prune 会删除所有没有容器接入的自定义网络，包括你手工建好、准备下次使用的网络。执行前先用 docker network ls 与 docker network inspect 确认没有需要保留的网段、网关与标签配置。

**速记**：**网络无容器才能删，先 disconnect 再 rm，prune 清掉所有空闲网**。



### Docker 内嵌 DNS

#### 127.0.0.11 的角色

**127.0.0.11**：是 Docker 为接入自定义网络的容器提供的内嵌 DNS 服务器地址，容器里的域名解析请求都先发给它，由它决定返回容器名对应的地址还是转给上游 DNS。

- 出现位置：容器内 /etc/resolv.conf 的 nameserver 一行写着 127.0.0.11，容器内不需要也不应手工配置它。
- 两类查询：查容器名或别名时由内嵌 DNS 直接回答；查外部域名时转给宿主机配置的 DNS 服务器。
- 无 IPv6 等价物：官方明确说明没有 IPv6 版本的这个地址，纯 IPv6 容器里同样使用这个 IPv4 地址。
- 生效前提：只有接入自定义网络的容器才使用它，默认 bridge 上的容器拿到的是宿主机 resolv.conf 的一份副本。
- 可显式指定：应用若要求写明 DNS 服务器地址，填 127.0.0.11 即可。

```bash
docker exec api cat /etc/resolv.conf
# nameserver 127.0.0.11
# options ndots:0

docker exec api nslookup db
```

> 本机解析链路是"应用到 127.0.0.11 再到上游 DNS"。因此排查连不上外部域名时，先确认 127.0.0.11 是否在 resolv.conf 中，再确认宿主机本身能否解析该域名，不要一上来就怀疑容器网络。

> [!NOTE]
> **提醒内容**：127.0.0.11 只在容器的网络命名空间内有效，不是宿主机的地址。在宿主机上 ping 或 nslookup 这个地址没有任何意义，判断它是否工作只能进入容器测。

**速记**：**自定义网络内的 resolv.conf 指向 127.0.0.11，容器名它回答、外部名它转发**。



#### 容器名与别名的解析规则

**解析表**：内嵌 DNS 把名字到地址的映射按网络分别维护，一个容器在每张它接入的网络里都有一组名字，查询只在该网络范围内生效。

- 容器名：docker run --name 给出的名字，自动登记为该容器在该网络上的名字。
- 网络别名：--network-alias 或 docker network connect --alias 追加的名字，与容器名并列，一个容器可以有多个。
- 名字作用域：名字是网络作用域的，两个容器即使同名，只要不在同一张网就不会冲突。
- 别名可共享：同一张网里多个容器可以使用同一个别名，此时该名字会解析出多个地址。
- 自动生成名不登记：未显式命名时，Docker 自动生成的名称不参与服务发现。

```bash
docker run -d --name redis-primary \
  --network app-net \
  --network-alias cache \
  redis:7-alpine

docker exec api getent hosts cache
docker exec api getent hosts redis-primary
```

> 官方 Compose 参考页对共享别名的表述是：网络作用域的别名可被多个容器甚至多个服务共用，若如此，该名字解析到哪个容器并不保证。因此别名适合表达一组等价实例，不适合表达唯一目标。

**速记**：**名字等于容器名加别名，均按网络登记；同名可共享、解析不保证**。



#### 同名多副本的解析行为

**多副本解析**：当同一张网络中有多个容器共享同一个名字或别名时，该名字会对应多个地址，客户端最终取用哪一个由记录顺序与客户端实现共同决定。

- 返回形态：一次查询返回多条 A 记录，即多个 IPv4 地址，而不是单条。
- 轮询倾向：客户端多次解析或多次建立连接时，通常会轮流用上这些地址，形成最朴素的客户端分摊。
- 官方口径：按官方 Compose 参考页，共享别名时解析到哪一个容器不保证，这把轮询定位为可观察到的行为而非契约。
- 客户端差异：是否缓存与缓存多久由应用的解析器决定，长连接场景下客户端选定一个地址后会一直用下去。
- 适用与不适用：适合无状态副本的初级分摊；需要粘性会话、健康检查与故障摘除时，应交给反向代理或集群编排。

> 这套机制常被称为 Docker 层的服务发现雏形。它与 Kubernetes 的 Service 有共同理念，即按稳定名字访问一组后端；但 Kubernetes 的 ClusterIP 由 kube-proxy 承担转发与健康检查，能力更强，两者不可直接等同。

> [!WARNING]
> **警告内容**：依赖共享别名做负载均衡时，客户端一旦建好长连接就不会切换后端，某个副本挂掉会持续报错直到连接超时重建。生产环境应在副本之前放一层反向代理，由它负责健康检查与摘除，而不是把负载均衡责任交给 DNS。

**速记**：**同名多副本等于多条 A 记录，轮询是行为不是保证，长连接不会自动切换**。



#### 默认 bridge 为何不启用这套解析

**机制原因**：内嵌 DNS 是自定义网络的属性，默认 bridge 网络按历史设计只提供地址连通与 -p 映射，不提供名字解析，容器之间只能按地址访问，或在历史上用 --link 写 /etc/hosts。

- 维护维度不同：自定义网络按网络维度维护名字表，默认 bridge 没有这套登记，容器名进不了解析表。
- 注入内容不同：默认 bridge 上的容器拿到的是宿主机 /etc/resolv.conf 的副本，而不是指向 127.0.0.11。
- 历史补丁：早期靠 --link 往被连接容器的 /etc/hosts 里写死名字与地址，把解析问题就地解决。
- 波及范围：默认 bridge 是全体未指定 --network 的容器共用的，若默认开启名字解析，互不相干的应用会互相看见，与隔离目标冲突。
- 现行结论：需要按名字互访，就新建一张自定义网络并让相关容器接入，不做其它变通。

> 官方 bridge 驱动页给出的对照实验中，默认 bridge 上 ping 容器名直接返回 bad address，而用户自定义网络上同一操作成功，差别只在于是否接入自定义网络。容器网络的底层机制见第 8 篇 容器网络基础与端口映射。

> [!IMPORTANT]
> **重要内容**：默认 bridge 上按名字 ping 不通不是配置错误，而是设计如此。看到这类报错时不要反复重建容器，直接新建自定义网络并把发起方与目标方都接进去即可。

**速记**：**默认 bridge 只通地址不通名字，名字解析是自定义网络的专属能力**。



#### resolv.conf 与 hosts 的注入内容

**注入分工**：Docker 在容器启动时写入两份与名字有关的基础文件，/etc/resolv.conf 管找谁问域名，/etc/hosts 管哪几个固定名字自己答，内容随网络类型不同。

- resolv.conf 的 nameserver：接入自定义网络时写 127.0.0.11；接入默认 bridge 时写宿主机 DNS 配置的副本。
- resolv.conf 的 options：常见一行 options ndots:0，表示优先按原样名字查询，而不是先拼接搜索域。
- resolv.conf 的 search：容器默认继承宿主机的搜索域设置，可用 docker run --dns-search 覆盖。
- hosts 的内容：官方网络总览页说明，容器内 /etc/hosts 有本容器主机名、localhost 等固定几行；宿主机自己的 /etc/hosts 自定义条目不会被容器继承。
- 补充外部主机：需要额外的主机名映射时，用 docker run --add-host 名称:地址 追加，而不是改镜像里的 hosts。

```bash
docker exec api cat /etc/resolv.conf
docker exec api cat /etc/hosts

docker run --rm \
  --add-host host.docker.internal:host-gateway \
  alpine ping -c1 host.docker.internal
```

> [!NOTE]
> **提醒内容**：容器里的 /etc/hosts 与 /etc/resolv.conf 都是运行期由 Docker 生成的文件，在容器内手工改动只在本次运行有效，容器重建即消失。需要长期生效的条目应写进启动参数，即 --add-host 与 --dns 系列，或写进编排文件。

**速记**：**resolv.conf 定问谁、hosts 定自己答谁，两者都是运行期生成、重建即重置**。



### 网络别名与多名字

#### network-alias 的用法

**network-alias**：是 docker run 的一个选项，为容器在某张网络上追加一个名字，使同一网络内的其它容器既能用容器名、也能用这个别名找到它。

- 创建时指定：docker run --network-alias 名字，可重复书写以追加多个别名。
- 运行中追加：docker network connect --alias 名字 网络名 容器名，为已运行容器在某张网络上加别名。
- 声明式等价写法：docker run 的 --network 扩展语法里，别名写作 alias=名字，与 --network-alias 等价。
- 作用范围：别名只在其被添加的那张网络内生效，同一容器在不同网络里可以有不同别名。
- 常见用途：把实现细节名，如 redis-primary，与稳定服务名，如 cache，分开，应用只依赖后者。

```bash
docker run -d --name redis-primary \
  --network app-net \
  --network-alias cache \
  --network-alias session-store \
  redis:7-alpine

docker exec api getent hosts cache
docker exec api getent hosts session-store
```

> 别名与容器名在解析上地位并列，两个名字指向同一个地址。差别在于容器名随实例绑定，别名可以脱离实例名单独约定，这正是把别名用作稳定接口的原因。

**速记**：**一个容器多张网、每张网可多名字；应用依赖别名，别名比容器名更稳**。



#### Compose 中的服务别名

**Compose 别名**：在服务级 networks 字段的长语法里，aliases 声明该服务在某张网络上的备用主机名，与容器名并列登记进内嵌 DNS。

- 长语法结构：networks 下列出网络名，网络名下的 aliases 是一个名字列表。
- 与容器名的关系：服务名默认就是该服务容器在项目网络里的名字，aliases 是在此之外追加的名字。
- 网络作用域：别名写在某张网络下，只在该网络生效，同一服务在不同网络可给不同别名。
- 共享提示：官方说明该别名可被多个容器甚至多个服务共用，解析到哪个不保证。
- 短语法对比：服务级 networks 写成名字列表时不带别名，只有长语法才能声明 aliases。

```yaml
services:
  backend:
    image: example/backend
    networks:
      back-tier:
        aliases:
          - database
          - db

networks:
  back-tier: {}
```

> 服务名与网络别名不是一回事：服务名由 Compose 依据服务键自动登记，别名要手工声明。把数据库的调用方从具体服务名改为稳定别名后，替换数据库实现时不必逐处改应用配置。

**速记**：**服务名自动登记、aliases 手工追加；别名写在哪张网下就只在那张网生效**。



#### 别名在滚动更新与蓝绿部署中的价值

**稳定接口**：别名把应用依赖的名字与当前提供服务的容器解耦，因此可以在不惊动应用的前提下替换后端实例，是滚动更新与蓝绿切换能够成立的前提之一。

- 滚动更新：新版本容器先接入网络并挂上别名，应用仍用稳定别名访问，切换完成后再下线旧实例。
- 蓝绿部署：蓝组与绿组各自是独立实例，把稳定别名依次指向当前活跃的一组，回滚时把别名指回旧组。
- 失败切换：别名切换是瞬时的，客户端下一次解析即可拿到新地址，无需改配置或重启。
- 与容器名的对比：容器名绑定具体实例，实例重建即换名；别名可跨越实例的生命周期。
- 局限：客户端若有 DNS 缓存或长连接，别名切换不会立即对已在链路上的请求生效。

> 别名的这一用法本质是用名字做指针。真正承担平滑切换的仍应是反向代理与健康检查，别名只是把后端的地址入口稳定下来；只靠别名而没有任何健康判断的切换，会把失败实例继续暴露给客户端。实务中宜把应用配置里出现的名字一律固定为别名或服务名，把实例名只留给运维排查使用。

**速记**：**别名是稳定指针，更新期换指向、回滚时指回旧组，缓存与长连接是它的天花板**。



### 容器互联方式的演进

#### --link 的历史地位

**--link**：是 Docker 网络功能出现之前的容器互联手段，用法是 docker run --link 源容器:别名，让接收方能在 /etc/hosts 里按别名找到源容器的地址。

- 解决的问题：在还没有自定义网络与内嵌 DNS 的年代，给容器之间提供按名寻址与少量元数据传递。
- 写入 hosts：Docker 会把源容器的主机名与别名写进接收方的 /etc/hosts，地址可随源容器重启自动更新。
- 传递环境变量：Docker 会自动生成一批与源容器相关的环境变量注入接收方。
- 方向性：链接有方向，接收方能看到源方，反之不成立，双向互通要建两条链接。
- 现状：官方已把默认 bridge 上的 --link 标记为弃用并给出移除时间表。

```bash
docker run -d --name db postgres:17-alpine
docker run -d --name api --link db:database my-api:1.0
```

> [!WARNING]
> **警告内容**：官方 links 文档明确，默认 bridge 上的链接已弃用并计划在 Docker Engine 30.0 中移除，自 Engine 29.6 起创建这类容器会打印弃用警告；链接附带的环境变量自 Engine 29.0 起默认禁用、计划在 30.0 移除。新写的部署不应再使用 --link，迁移方式是用自定义网络加服务名解析。

**速记**：**--link 是网络功能之前的互联补丁，单向、写 hosts、传变量，如今已弃用**。



#### --link 被弃用的原因

**弃用原因**：--link 的互联能力依赖写死 /etc/hosts 与注入环境变量两套旁路机制，既不能动态按需发现，也把容器的启动顺序与地址耦合在一起，随自定义网络能力成熟而被替代。

- 单向且成对维护：链接只在一个方向生效，容器越多需要两两建立的链接越多，维护量平方增长。
- 静态写入：名字与地址被写进 /etc/hosts，成员变化时靠 Docker 更新，语义上仍是一张静态表。
- 环境变量泄漏：官方 links 文档警告，链接会把源容器中所有源自 Docker 的环境变量一并暴露给接收方，若其中含敏感值即构成安全问题。
- 无法表达网络作用域：链接不区分网络，同一套链接关系可能把本不该互相看见的容器连起来。
- 缺少服务发现语义：没有别名共享、没有多副本解析，扩容后无法按名字分摊到多个副本。

> 官方给出的迁移替代很直接：用用户自定义网络替代 legacy 的 --link。前者把解析交给内嵌 DNS，成员变化即时生效，且有明确的网络作用域。

**速记**：**弃用根因是单向难维护、hosts 静态、变量泄漏，自定义网络全面取代**。



#### 现行推荐做法与旧资料识别

**现行做法**：需要容器互联时，创建一张自定义网络，让相关容器接入，再用容器名或网络别名互相访问；不写 --link，也不手工改 /etc/hosts。

- 单机做法：docker network create 加 docker run --network，再用 --name 或 --network-alias 定名。
- 编排做法：在 Compose 里声明顶层 networks，服务级 networks 引用，服务名与 aliases 即解析名。
- 出网与对外：同网容器互相访问不需要 -p；对外提供服务才用 -p 映射。
- 旧资料识别点一：出现 docker run --link 或服务级 links 字段。
- 旧资料识别点二：出现用 --link 传环境变量、改 /etc/hosts 让容器互通之类步骤，均属网络功能之前或绕过 DNS 的写法。
- 旧资料识别点三：出现带短横线的 docker-compose 命令或顶层 version 字段，说明文档年代更早。

```yaml
services:
  api:
    image: my-api:1.0
    networks:
      - app-net
  db:
    image: postgres:17-alpine
    networks:
      - app-net

networks:
  app-net: {}
```

> [!NOTE]
> **提醒内容**：读到 --link 相关内容时不必全盘丢弃，其中关于 /etc/hosts 写入与自动更新地址的说明有助于理解历史行为；但要意识到这是被弃用路径，实际部署应换成自定义网络。Compose 语法层面的新旧识别见第 10 篇 Docker Compose 入门与第 11 篇 Docker Compose 进阶与实战。

**速记**：**现行做法等于自定义网络加容器名或别名；见到 --link 与手改 hosts 即判为旧法**。



### 网络隔离

#### 分段：前端网络与后端网络

**网络分段**：把承担不同职责的容器放进不同网络，只让必要的成员跨网接入，可以把可达范围缩小到设计所需的最小集合。

- 典型分层：前端网络放页面与网关，后端网络放接口与缓存，数据网络放数据库与缓存。
- 网关角色：反向代理或网关容器同时接入前端与后端网络，成为外部流量进入后端的唯一入口。
- 数据层位置：数据库只接入后端或更内层的独立网络，前端网络里的容器看不到它。
- 可达方向：同一张网内双向可达；不共网则既不能按名字解析，也不能直接建连。
- 验证方式：从前端网络中的容器尝试解析并连接数据库名应失败，从网关容器尝试则成功。

```yaml
services:
  gateway:
    image: nginx:1.27-alpine
    networks:
      - frontend
      - backend
  web:
    image: example/webapp
    networks:
      - frontend
  db:
    image: postgres:17-alpine
    networks:
      - backend

networks:
  frontend: {}
  backend: {}
```

> 官方网络总览给出的正是这一模式：前端容器接入一张可出网的 bridge 网络，再接入一张 internal 网络与不需要外部访问的后端服务通信。分段的目的不是多建网，而是让谁能连到谁成为一条可审阅的显式配置。

**速记**：**按职责分网、网关跨两网、数据只在内层；不可达就是安全边界**。



#### internal 网络禁止出网

**internal 网络**：是以 docker network create --internal 创建的、没有默认路由且被防火墙丢弃外部流量的网络，接入它的容器之间可以互通，但不能访问网络外部，也不能经它出网。

- 创建方式：docker network create --internal 网络名，或在 Compose 顶层网络写 internal: true。
- 连通范围：容器之间可通、可与网关通信，出网方向被阻断。
- 需配套出网网卡：只接入 internal 网络的容器无法访问外部，需要出网时要另接一张可出网的网络。
- 典型场景：数据库、缓存、内部消息队列这类只被内部服务访问、不需要访问外网的组件。
- 与防火墙的关系：它是 Docker 层面的路由与过滤控制，不替代宿主机防火墙与集群网络策略。

```bash
docker network create --internal data-net

docker run -d --name db --network data-net postgres:17-alpine
docker run -d --name api \
  --network app-net \
  --network data-net \
  my-api:1.0
```

> 官方 ipvlan 驱动页给出一条等价关系：省略 -o parent 与使用 --internal 创建出的都是隔离网络，都会建一个 dummy 父接口从而阻断外部连通，可见 internal 的语义就是没有外部出口。

> [!CAUTION]
> **注意内容**：把本就需要访问外网的服务放进 internal 网络，会表现为拉取依赖、访问第三方接口全部超时，且报错往往是连接超时而非网络不可达，排查成本高。接入 internal 前先确认该服务不需要任何出网访问。

**速记**：**--internal 关掉默认路由与外部流量，只留内部互通；要出网就再插一张网卡**。



#### 隔离对安全边界的意义

**安全价值**：网络隔离把能否建立 TCP 连接这件事实本身变成一道门槛，即使某个服务存在漏洞，攻击者也必须先跨过网络边界才能触达下一步目标。

- 缩小横向移动：数据库不接入前端网络，前端容器被攻破也无法直接连数据库。
- 减少暴露面：内部服务不映射端口，宿主机与外网都无法直连。
- 明确依赖：网络连接关系写在声明文件里，可审阅、可评审，比谁都连得上更易审计。
- 配合最小权限：与只读挂载、非 root 运行、能力裁剪等措施叠加使用，单独一层不足以防住内核级逃逸。
- 常见误区：以为容器天然隔离而不分段，实际同一张网内所有容器默认可互相访问任意端口。

> [!IMPORTANT]
> **重要内容**：同一张网络内的容器默认可互相访问全部容器端口，这是官方网络总览的明确表述。因此把服务都放进一张网等于取消服务间的访问控制，隔离要落在一张张网络的分段上，而不是指望容器名解析本身带来限制。

**速记**：**隔离等于缩小可达范围加隐藏端口加显式声明依赖；它防横向移动，不防内核逃逸**。



### 静态 IP 与固定地址

#### --ip 的前提

**--ip**：是在创建容器时为其在指定网络上指定 IPv4 地址的选项，它的使用有两条硬前提，即网络必须是自定义网络，且该网络必须显式指定过子网。

- 网络要求：只能在用户自定义网络上使用，默认 bridge 不支持。
- 子网要求：官方文档的表述是，要给容器分配静态地址，必须为网络指定子网，否则地址不在受管范围内无从分配。
- 运行中指定：用 docker network connect --ip 地址 网络名 容器名，为已运行容器在某张网络上定址。
- 地址约束：地址必须落在该网络的子网内，不与已分配地址冲突，也不应落在 --ip-range 之外。
- IPv6 对应项：--ip6 用于指定 IPv6 地址，前提相同。

```bash
docker network create --subnet 192.0.2.0/24 my-net

docker run -d --name db \
  --network my-net \
  --ip 192.0.2.69 \
  postgres:17-alpine

docker network connect --ip 192.0.2.70 my-net api
```

> 指定静态地址与规划网关、预留地址属于同一件事：网关、辅助地址与容器地址应当互不重叠。Compose 侧对应服务级网络的 ipv4_address 字段，顶层网络的 ipam.config 里须写明 subnet，否则静态地址无从校验。

**速记**：**--ip 两前提，自定义网络加显式子网；地址须落在网段内且不冲突**。



#### 何时需要固定地址

**需要固定地址的场景**：当外部系统按来源或目标 IP 做访问控制时，容器地址必须可预期，此时固定地址才成为必要手段。

- 对外白名单：上游数据库、第三方接口或被访问方只放行特定 IP，容器地址漂移会导致放行失效。
- 设备与监控：监控、日志或安全设备按地址识别实例。
- 网络设备联动：交换机、路由或防火墙上有针对该地址的规则或路由条目。
- 配置外置：目标系统的地址不能通过 DNS 或配置下发，只能写死一个 IP。
- 排查便利：少数情形下固定地址便于把日志与流量对上具体实例。

> 更稳的替代是把地址依赖换成名字依赖：让外部系统识别一个稳定别名或域名，而不是识别一个 IP。只有在对方确实不支持任何形式的名字寻址时，固定地址才是唯一选择。

**速记**：**只有当外部按 IP 放行或识别时才固定地址，能换成名字就换名字**。



#### 为何不推荐日常固定 IP

**不推荐的理由**：固定地址把容器重新绑回网络位置，与容器可随时销毁重建的运行模型相冲突，会引入地址冲突与难以扩展两类问题。

- 地址冲突：同一网段内若两处声明了同一地址，后启动者直接失败，跨项目共享网络时冲突概率更高。
- 阻碍扩展：副本要按同一配置起多个容器，固定地址下无法简单扩容。
- 编排不兼容：集群编排按名字与虚拟地址做调度，固定 IP 与其模型不符，迁移到集群时需重做。
- 掩盖依赖：应用里写死地址后，环境迁移与故障切换都要逐处改配置。
- 官方倾向：官方示例把 --ip 定位为实现地址规划的工具，默认路径是用名字解析。

> [!WARNING]
> **警告内容**：在共享网络或多项目环境里固定地址，最容易出现的故障是第二个项目启动失败、报地址已被占用，而根因是两处声明撞在同一网段。日常使用应让 Docker 从子网自动分配，把固定地址留给确实需要的少数实例。

**速记**：**固定 IP 换来地址依赖，冲突、难扩容、迁移要重做，默认交给自动分配**。



### 其他网络驱动

#### overlay：跨主机的基础

**overlay 驱动**：在多台 Docker 守护进程主机之间创建一张分布式网络，它在各主机自有网络之上再叠一层，让接入的容器跨主机直接通信。

- 前提：所有主机必须属于同一个 swarm，即便只连接独立容器也一样，这是官方明确的硬条件。
- 创建方式：docker network create -d overlay 网络名，与创建 bridge 网络的命令形式一致。
- 加密选项：--opt encrypted 开启 VXLAN 层面的 IPsec 加密，官方提示有不可忽略的性能开销。
- 独立容器接入：创建时加 --attachable，独立容器才能接入，否则只有 swarm 服务能连。
- 端口要求：参与主机之间需放通 swarm 控制平面 2377/tcp、overlay 流量 4789/udp 与节点通信 7946 的 tcp 与 udp。
- 何时才需要：容器分布到多台主机且需要互相通信时；单机多容器用 bridge 网络即可。

```bash
docker network create -d overlay --attachable my-overlay
docker run -d --name api --network my-overlay my-api:1.0
```

> [!NOTE]
> **提醒内容**：overlay 加密官方特别指出不要在 Windows 容器上使用，且在 Windows 上不受支持。即便 swarm 不报错，Windows 容器也无法与加密网络中的 Linux 容器通信，且 Windows 容器之间的流量不会被加密。跨平台集群规划时须先确认这一点。

**速记**：**overlay 跨主机、须在 swarm 内、--opt encrypted 加密有性能代价、独立容器要 --attachable**。



#### macvlan：容器直接出现在物理网络

**macvlan 驱动**：为每个容器分配一个虚拟网卡与独立 MAC 地址，使容器看起来像物理网络中一台独立主机，从而能被同网段的其它设备直接访问。

- 适用场景：遗留应用、需要监控或抓取链路上流量的应用，这类应用要求自己直接连在物理网络上。
- 必要参数：创建时要给出父接口，即 -o parent，以及子网 --subnet 与网关 --gateway。
- 地址分配：默认由 Docker 内置 IPAM 从指定子网中分配；若要求由既有 DHCP 服务器派址，需借助额外的 IPAM 驱动，属进阶配置。
- 平台限制：仅 Linux 可用，Docker Desktop for Mac 与 Windows 以及 Windows 上的 Engine 不支持，rootless 模式也不支持。
- 内核与网络要求：内核至少 3.9，官方推荐 4.0 以上；物理网络设备需能处理混杂模式。
- 已知制约：容器无法与宿主机直接通信，这是内核限制；多数云厂商阻断 macvlan，可能需要物理网络访问权限。

```bash
docker network create -d macvlan \
  --subnet=172.16.86.0/24 \
  --gateway=172.16.86.1 \
  -o parent=eth0 \
  pub_net

docker run -d --name legacy-app --network pub_net legacy-app:1.0
```

> 官方给出的取舍很清楚：若应用用 bridge 或 overlay 就能满足，长期看这两种方案更合适。macvlan 的成本在于要让物理网络承担更多 MAC 与地址，且带来 VLAN 蔓延与地址耗尽的风险。

**速记**：**macvlan 把容器装成物理机，要父接口与子网，仅 Linux、不连宿主机、云上多被阻断**。



#### ipvlan：共享 MAC 的变体

**ipvlan 驱动**：与 macvlan 目标相近，让容器直接落在物理网络上；但它不给每个容器分配独立 MAC，而是让多个容器与父接口共用同一个 MAC，用 IP 区分彼此。

- 与 macvlan 的差别：macvlan 每容器一个 MAC，ipvlan 共享父接口 MAC，因此网络侧看到的 MAC 更少。
- 常用模式：默认 l2 模式，容器与父接口在同一广播域；l3 模式丢弃全部广播与组播，官方称其适合大规模与可预测的网络集成。
- 必要参数：-o parent 指定父接口；l2 模式需给出子网与网关，l3 模式下网关参数被忽略。
- 平台与内核：同样仅 Linux，需 Linux 内核 4.2 以上，更低版本虽可运行但有缺陷。
- 已知制约：l2 模式下不同子网不能互相 ping，容器也不能 ping 底层主机接口。
- 何时才需要：需要完全掌控 IPv4 与 IPv6 编址、需要二层 VLAN 标签控制，或需要 l3 路由做底层网络集成时。

```bash
docker network create -d ipvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o ipvlan_mode=l2 \
  -o parent=eth0 \
  db_net

docker run -d --name db --network db_net postgres:17-alpine
```

> 选择 macvlan 还是 ipvlan 取决于环境：交换机对 MAC 数量敏感、或需要彻底掌控编址时偏向 ipvlan；需要容器在网络上表现为完全独立设备时偏向 macvlan。两者都不适合在 Docker Desktop 或默认云环境下尝试。

**速记**：**ipvlan 与 macvlan 同目标，差别在共享 MAC；l2 同广播域、l3 丢广播**。



#### none 与其它驱动选择的边界

**none 驱动**：创建的容器只有回环接口，没有外部网络，是对外完全隔离的一种网络模式；它与 bridge、host、overlay、macvlan、ipvlan 同列，均为官方内置驱动。

- none 的语义：容器不接入任何网络，只保留 loopback，需要完全离网运行或自建网络栈时使用。
- host 的语义：容器直接使用宿主机网络命名空间，取消网络隔离，端口映射随之失去意义。
- 选择口径：单机多容器互联用 bridge；跨主机用 overlay；容器要成为物理网络成员用 macvlan 或 ipvlan；完全离网用 none；要取消隔离用 host。
- 平台差异：原生 Windows 容器有另一套驱动，不在上述之列。
- 判断顺序：先问要不要出网，再问要不要跨主机，最后才在物理网络成员方案里选 macvlan 或 ipvlan。

```bash
docker run -d --name offline-tool --network none alpine sleep 3600
docker network ls
docker network inspect bridge
```

> [!TIP]
> **建议内容**：多数项目只需 bridge 一种驱动就能满足，遇到瓶颈再考虑其它驱动。按官方说法，应用能在 bridge 或 overlay 上跑通时，长期看这两种方案更合适，物理网络成员类驱动留给确有需求的场景。

**速记**：**先判出网、再判跨主机、最后才判物理网络成员；bridge 是默认答案**。



### 跨 Compose 项目共用网络

#### external 网络的声明与创建

**external 网络**：是在 Compose 文件之外创建、由 Compose 直接引用而非创建管理的网络，写法是顶层 networks 下单列 external: true。

- 声明方式：顶层 networks 里写网络名，其下写 external: true。
- 生命周期：网络的生命周期在应用之外维护，Compose 不会尝试创建它，若不存在则报错。
- 字段限制：按官方 Compose 参考页，external 网络除 name 之外的其它属性都无关紧要，一旦检测到其它属性会判定文件无效。
- name 的作用：用于指定要检索的平台网络名，该名称按原样使用、不加项目名前缀。
- 常配参数：用变量注入网络名，如 name 写 ${NETWORK_ID}，避免在文件里硬编码运行期取值。
- 拆除行为：docker compose down 不会删除外部声明的网络。

```yaml
services:
  proxy:
    image: nginx:1.27-alpine
    networks:
      - shared-net
      - default

networks:
  shared-net:
    external: true
```

> 官方示例中，proxy 被定位为通往外部世界的网关：它同时接入外部网络与项目默认网络，从而成为项目与外部资源之间的唯一通道。这与本篇网络隔离一节讲的网关跨两网是同一手法，只是网络由项目外部创建。

**速记**：**external 为真表示网在外建、我只引用；除 name 外写其它属性会被判无效，down 也不会删它**。



#### 项目名前缀与默认网络名

**命名规则**：Compose 为项目自动创建的网络名由项目名加下划线加网络名拼成，因此同一份文件在不同项目名下运行会得到不同的网络；一旦显式写了 name，名称按原样使用、不加前缀。

- 默认形态：项目名与文件里的网络名拼接，如项目 demo-shop 下声明的 backend 实际名为 demo-shop_backend。
- 隐式 default：服务未声明 networks 时会连入名为 default 的网络，实际名称同样带项目前缀。
- 项目名来源：命令行 -p 最优先，其次是环境变量 COMPOSE_PROJECT_NAME，再次是顶层 name 字段，最后是目录名。
- 显式 name 的效果：一旦写 name，网络名按原样使用，跨项目引用同一张网时靠它对齐。
- 外部网络的引用：external 声明中给出确切名字，Compose 便不再做前缀拼接。

```bash
docker network ls | grep demo-shop
docker network inspect demo-shop_backend
```

> [!IMPORTANT]
> **重要内容**：项目名前缀意味着默认自带隔离，而不是名字可以随便写。两个项目若各自声明了同名的普通网络，实际网络名因前缀不同而互不干涉；要让两项目共用一张网，正确做法是把网络声明为 external 并给出确切名字，而不是指望两边的网络名碰巧相同。

**速记**：**默认网络名等于项目名加下划线加网络名；写了 name 或 external 则按原样取，前缀随之消失**。



#### 共享网络的运维注意

**责任划分**：共享网络把谁创建、谁清理的问题从单个项目提升为跨项目事务，必须先约定归属，否则会出现一方 down 掉共享网络、另一方随即断连的故障。

- 创建方：由平台或第一个项目负责 docker network create，并记录子网、网关与用途。
- 清理方：只有创建方可以删网，且要先确认没有其它项目的容器仍在接入。
- 引用方：其它项目只写 external: true 与确切网络名，不写驱动与子网等属性。
- 自动清理的风险：docker network prune 会删除所有无容器接入的网络，共享网络在没有容器的空窗期可能被误删。
- 记录与命名：共享网络建议用带环境与用途的名字，如 shared-edge-prod，并在运维文档里登记创建命令与负责方。

```bash
docker network create --subnet 172.30.0.0/24 shared-net
docker network inspect shared-net
docker network rm shared-net
```

> [!CAUTION]
> **注意内容**：共享网络一旦被误删，所有引用它的项目都会在下次解析时失败并中断跨项目通信，且重建后子网可能与旧值不同，使按 IP 写死的配置失效。删除前先 docker network inspect 查看接入容器列表，确认无人在用再动手。

**速记**：**共享网络先定归属，谁建谁删、引用方只写 external 与名字，prune 与空窗期是最大风险**。



### 网络排查套路

#### 进入容器测试解析

**第一步排查**：先确认名字解析这一环是否通，方法是进入容器或起一个同网络的临时容器，用解析类命令查询目标名字。

- 看配置：docker exec 容器 cat /etc/resolv.conf，确认 nameserver 是否指向 127.0.0.11。
- 用 getent：docker exec 容器 getent hosts 名字，能返回值即解析通；getent 在 glibc 环境，即 Debian 与 Ubuntu，自带。
- 用 nslookup：Alpine 等基于 busybox 的镜像自带 nslookup；Debian slim 一类精简镜像默认没有，需要另行安装。
- 起临时容器验证：docker run --rm --network 网络名 busybox nslookup 名字，避免在被排查容器的镜像里缺工具。
- 区分两类失败：解析不到属名字问题，解析到但连不上属端口或进程问题，处置方向完全不同。

```bash
docker exec api cat /etc/resolv.conf
docker exec api getent hosts db
docker run --rm --network app-net busybox nslookup db
```

> [!TIP]
> **建议内容**：排查前先备一个带常用网络与调试工具的临时容器，比在被排查的业务镜像里反复装包更快。测试时务必把它接入问题网络，即用 --network 指定同一张网，否则测到的是一张无关网络的解析行为。

**速记**：**先看 resolv.conf、再用 getent 或 nslookup，缺工具就起同网临时容器**。



#### 用另一个容器同网络测试

**第二步排查**：把问题拆成目标服务本身是否可用与调用方到目标的链路是否通两问，用第三个同网络的容器做对照，能快速定位故障落点。

- 对照的价值：同样的名字与端口，从另一容器能通、从原容器不通，问题就在原容器；两者都不通，问题在目标服务或网络本身。
- 测名字与地址层：docker run --rm --network 网络名 busybox ping -c1 目标名。
- 测端口层：用对应服务的客户端更可靠，例如 docker run --rm --network 网络名 postgres:17-alpine pg_isready -h 目标名 -p 5432。
- 确认同网：先 docker network inspect 网络名 看两个容器的接入情况，避免压根不在同一张网。
- 排除启动次序：目标进程是否已就绪，用 docker logs 目标容器 确认。

```bash
docker network inspect app-net
docker run --rm --network app-net busybox ping -c1 db
docker run --rm --network app-net postgres:17-alpine pg_isready -h db -p 5432
```

> 用第三方容器做对照的关键是只改一个变量：保持网络、名字、端口不变，只换成另一个发起方。这样才能判断差异来自调用方还是服务端，而不是同时动了多个条件导致结论不可用。

**速记**：**换一个同网容器做对照，都通是调用方的问题，都不通是服务或网络的问题**。



#### inspect 查看接入与别名

**inspect 的两个方向**：docker network inspect 从网络看成员，docker container inspect 从容器看接入，两者配合可核实容器到底在哪张网、挂的什么名字。

- 看网络成员：docker network inspect 网络名 列出该网络下已接入容器的名称与地址。
- 看容器接入：docker container inspect 容器名，查看 Networks 段下每张网络的名字、地址与 Aliases。
- 核对别名：Aliases 段会同时列出容器名与别名，别名不生效时先在这里确认它是否真的登记上了。
- 看网络配置：同一命令可确认 Driver、Internal 与 IPAM.Config 下的子网与网关，用于核对网段规划。
- 格式化输出：加 --format 只取需要的字段，便于脚本化核对。

```bash
docker network inspect app-net \
  --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'

docker container inspect api \
  --format '{{json .NetworkSettings.Networks}}'
```

> 排查别名不生效时，最常见的根因是别名加在了另一张网络上：容器接入两张网时，别名只在其被添加的那张网里登记，从另一张网的成员看去，这个名字并不存在。

**速记**：**network inspect 看成员、container inspect 看接入与别名；别名不生效先查加没加在对的网上**。



#### 常见故障：现象、原因与处置

**五类常见故障**：服务名解析失败、同网端口连不上、别名不生效、地址陈旧、跨网互访失败，各自的现象、原因与处置如下。

- 现象一：容器日志报无法解析主机名。原因是两个容器不在同一张网、名字拼错，或用了自动生成的默认名。处置是用 docker network inspect 核对是否共网，改用显式 --name 或服务名，必要时 docker network connect 补接入。
- 现象二：同网能 ping 通但连不上端口。原因是目标进程未就绪、监听在回环地址上，或端口写错。处置是用 docker logs 确认就绪，确认服务监听在 0.0.0.0 而非仅 127.0.0.1，并核对端口。
- 现象三：别名解析不到，容器名却能解析。原因是别名加在了另一张网络，或写成短语法未带 aliases。处置是用 docker container inspect 看 Aliases 落在哪张网，改用长语法或对正确的网络加别名。
- 现象四：目标容器重建后调用方仍连旧地址。原因是调用方应用或解析器缓存了旧结果，或长连接仍指向旧实例。处置是重启调用方进程或连接池，缩短应用的 DNS 缓存时间，长期靠别名或反向代理承接切换。
- 现象五：跨网络解析失败但确实需要互通。原因是跨网不共享解析表。处置是让其中一个容器接入对方网络，或新增一个同时接入两网的网关容器中转。

> [!WARNING]
> **警告内容**：见到连不通就直接重启容器，往往只是暂时掩盖了启动次序或缓存问题，根因还在。应先按解析是否通、地址是否可达、端口是否可连、进程是否就绪逐层定位，确认断点后再动手。

**速记**：**五类现象对应五处断点，不在同网、进程未就绪、别名加错网、缓存陈旧、跨网无解析表**。



### 网络设计的实务建议

#### 按职责划分网络数量

**划分口径**：网络数量按可达范围的需求确定，而不是按容器数量；凡是需要互相直接访问的容器归入同一张网，凡是不需要的不放进同一张网。

- 按层分网：接入层、应用层、数据层各一张网，跨层由网关或应用容器桥接。
- 不按微服务拆网：每个服务一张网会让网络数量失控且无实际收益，隔离价值来自层而非个体。
- 复用同一张网：同类且互信的服务，如一组无状态 api 副本，共用一张网。
- 兼顾排查成本：网络越多，接入关系越难一眼看清，应以能画出一张清晰的连接图为准。
- 与 Compose 对应：顶层 networks 声明若干张，服务级 networks 显式列出所属。

```yaml
networks:
  frontend: {}
  backend: {}
  data:
    internal: true
```

> 一个实用的自检问题是：去掉这张网，谁和谁就不该能通信？若答不上来，说明这张网没有承担隔离职责，可以并入相邻网络。

**速记**：**按可达范围分网，不按容器数分网；一张网一批互信成员**。



#### 给数据库单独一个 internal 网络

**数据层做法**：数据库只接入一张 internal 网络，仅由需要访问它的应用容器同时接入该网，其余容器一概不接触，从而把数据的可达面压到最小。

- 网络属性：该网络以 --internal 或 internal: true 创建，没有出网能力。
- 成员控制：只让数据库与直接调用它的应用接入，反向代理等中间层不接入。
- 地址与端口：数据库不需要 -p 映射，宿主机与外网都无法直连。
- 凭据配合：数据库口令仍应从密钥或环境变量文件注入，网络隔离不能替代凭据管理。
- 备份与运维：需要从宿主机运维数据库时，用 docker exec 进入，或用一次性容器接入该网执行任务。

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    networks:
      - data

  api:
    image: my-api:1.0
    networks:
      - backend
      - data

networks:
  backend: {}
  data:
    internal: true
```

> [!NOTE]
> **提醒内容**：internal 网络只阻断出网，不阻断同网成员之间的访问。数据库与所有调用它的应用仍在同一张网内互相可达，因此同网内任意容器可访问任意端口这一默认行为依然成立，进一步收紧需依赖数据库自身的账户与权限控制。

**速记**：**数据库进 internal 网、只留应用接入、不映射端口，凭据与网络两道防线并行**。



#### 命名规范与 Compose 中的显式声明

**落地做法**：为网络起可读且带环境信息的名字，并在 Compose 文件里显式声明与引用，让连接关系成为可提交、可评审的声明，而不是散落在启动命令里。

- 命名要素：环境与职责或项目，如 shop-prod-backend，避免出现 net1、mynet 这类无信息名。
- 显式声明：不用隐式 default，服务级 networks 逐条写出所属网络，便于阅读与审查。
- 慎用 container_name：固定容器名会失去项目名前缀带来的隔离，跨项目更易冲突。
- 打标签：用顶层 networks 或 docker network create --label 给网络打标签，便于按标签筛选与清理。
- 文档同步：共享网络与固定子网都要在运维文档里登记创建命令与负责方。

```yaml
name: shop-prod

services:
  api:
    image: my-api:1.0
    networks:
      - backend
      - data
  db:
    image: postgres:17-alpine
    networks:
      - data

networks:
  backend: {}
  data:
    internal: true
    labels:
      com.example.tier: data
```

> [!TIP]
> **建议内容**：把网络名、职责、子网与负责方整理成一页清单随项目维护。当出现某个服务连不上数据库时，先按清单核对它应属哪张网、实际是否接入，排查时间会大幅缩短。

**速记**：**网络命名带环境与职责、Compose 里显式声明、共享网络登记在册**。
