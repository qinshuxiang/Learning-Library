## Docker 与 Nginx 反向代理实战

### 为什么把 Nginx 放进容器

#### 与裸机部署相比的收益

**配置即代码**：把 Nginx 的配置文件从宿主机的 /etc/nginx 挪进项目仓库，配置与后端代码同源、同审阅、同版本化；**与后端同网**：Nginx 容器与后端容器接入同一张自定义网络，靠服务名互访，后端不必对外发布端口；**随栈上下线**：Nginx 作为栈里的一个服务，与后端一起被拉起与拆除，环境可以整体重建。

- **配置随仓库走**：conf.d 目录随仓库提交，开发与生产的差异体现在挂载哪份配置上，而不是谁登过哪台机器改过什么。
- **与后端同网**：Nginx 到后端走容器网络，不必经过宿主机端口，少一层地址与防火墙配置，后端也就无需发布任何宿主端口。
- **随栈上下线**：一条启动命令同时拉起入口与后端，一条拆除命令同时清理，环境生命周期一致。
- **版本可锁定**：镜像标签固定版本，配合同一份配置，在新机器上重建出的入口与旧机器行为一致。
- **资源可约束**：入口容器同样受 CPU 与内存限制约束，不会在宿主上无人管辖地抢占资源。

> 这一节的收益都可归结为「入口成为栈里的一员」，而不是宿主机上一个独立于应用的常驻服务。库内 Nginx 系列讲的是入口本身怎么配，本篇讲的是入口变成容器之后的差异，配置语法不再重复。

**速记**：配置随仓库走、与后端同网、随栈起落、版本可锁、资源可限。



#### 与裸机部署相比的代价

**四类代价**：上游地址的解析时机从「每次连接」变成「加载配置那一刻」，证书与配置只能靠挂载注入，日志的采集点从文件移到容器的标准流，容器网络还带来一次额外的转发。

- **解析时机变化**：Nginx 处理静态域名上游时，只在启动或重载时解析一次并缓存，容器重建换了地址后 Nginx 仍指向旧地址，现象是 502，详见 upstream 指向服务名一节。
- **注入路径变化**：容器里的 Nginx 看不到宿主机上的配置目录，配置与证书都必须通过挂载或镜像进入，且通常要求只读。
- **日志位置变化**：日志不再落在宿主机的固定文件里，而是进入容器的标准输出与标准错误，采集方式随之改变，详见日志与可观测一节。
- **多一跳网络**：请求从宿主进入容器要经过一次地址转换与一次虚拟网卡转发，相比 Nginx 直接跑在宿主机多出一小段路径开销。

> 除网络路径外，其余三类代价都不是性能损失，而是运维动作变了——原来改文件加重载的两步操作，现在要先确认容器内看到的是不是新文件。

**速记**：解析一次、靠挂载注入、日志进标准流、多一跳网络。



#### 仍然建议 Nginx 留在宿主机的情形

**判断口径**：当入口需要的东西超出了容器能自然提供的能力，比如宿主级网络位置、极高的转发性能、独立于应用的升级窗口，或宿主机上已有的文件与套接字，把 Nginx 留在宿主机或做成独立网关更省事。

- **需要绑定特权端口且运行在非特权环境**：非特权用户无法绑定 1024 以下的端口，容器化后常需额外配置，而宿主机上的 Nginx 由系统包管理本就具备。
- **追求极低转发延迟**：入口与后端同处宿主机时，Nginx 直接跑在宿主可省掉容器这一跳；对延迟极度敏感且规模较大的场景，独立网关或四层负载均衡更合适。
- **已有宿主级入口体系**：机器上已经有一套宿主 Nginx、云负载均衡或硬件负载均衡在分发流量，再在容器里加一层入口只会让调用链更长。
- **需要访问宿主本地资源**：入口要读宿主机上的证书目录、本地 unix 套接字或宿主机挂载的共享存储时，留在宿主更直接。
- **需要与应用分开升级**：入口的发布节奏与业务应用不同，混在同一份文件里反而互相牵制。

> 这不是二选一。常见做法是宿主机或云上放一层四层入口，容器栈里再放一层七层 Nginx 做路由与静态资源；层次越多，越要写清各层各自负责什么。

**速记**：要特权端口、要极限低延迟、已有宿主入口、要读本地资源、要独立升级，就留在宿主机。



### 配置文件如何进入容器

#### 挂载单个文件与挂载配置目录

**结论先行**：挂载配置目录（通常是 /etc/nginx/conf.d/）比挂载单个 nginx.conf 更稳，因为单文件绑定挂载在宿主机上被替换时，容器内看到的仍是旧文件。

- **挂载单个文件**：写成宿主文件冒号容器文件，如把宿主 nginx.conf 挂到 /etc/nginx/nginx.conf，语义直观，但有被替换的风险。
- **挂载整个目录**：把宿主上的一个配置目录挂到 /etc/nginx/conf.d/，主配置里的 include 指令会把目录内每个 conf 文件汇入，新增站点只需加文件。
- **单文件的陷阱**：许多编辑器保存时先写临时文件再改名替换，宿主机上的文件被换成了新的 inode，而容器绑定的仍是旧 inode，于是文件明明改了、容器里没变。
- **目录为何更稳**：绑定的是目录这一层，目录内的文件增删改都通过目录项反映，不涉及目录本身被整体替换。
- **通配符约束**：只挂一个文件时，文件名与扩展名必须落在主配置 include 通配符的覆盖范围内，否则等于没配。

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
```

> 沿用库内配置管理的一贯结论：把可变的、按站点拆分的配置放进目录，把公共骨架留在主配置里。目录挂载让新增一个站点退化为在宿主目录里加一个 conf 文件，改动面最小。

**速记**：挂目录不挂单文件，避免编辑器替换 inode 导致改动看不见。



#### 只读挂载的必要性

**只读挂载**：在挂载项结尾加 :ro，使容器对挂载内容没有任何写权限；配置与证书这类容器只应读取、不应改写的文件，默认都应只读。

- **挡住误写**：Nginx 进程本身不写配置文件，但只读挂载让容器在异常情况下也无法篡改宿主上的配置，更不可能把恶意内容写回宿主。
- **让宿主成为唯一真源**：配置的实际内容只由宿主仓库决定，容器内再改也只是内存里的假象，重启即还原。
- **证书同样只读**：证书与私钥是另一种只读资产，详见 HTTPS 与证书一节。
- **写法**：短语法写冒号加 ro；长语法把 read_only 写成 true，项目里统一一种写法即可。

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    volumes:
      - type: bind
        source: ./nginx/conf.d
        target: /etc/nginx/conf.d
        read_only: true
```

> [!IMPORTANT]
> **重要内容**：容器里改配置是无效操作。容器内的配置文件是挂载进来的视图，在容器内编辑它要么被只读挂载挡住，要么改动只存在于当前容器；正确做法是改宿主仓库里的文件，再让 Nginx 重新加载。

**速记**：配置与证书一律只读，改内容只改宿主仓库。



#### 用官方镜像还是自建镜像

**取舍口径**：默认用 nginx 官方镜像，只在需要自定义编译模块或希望把配置与静态产物固化进镜像时才自建；自建时沿用多阶段与最小镜像的思路。

- **官方镜像带来的东西**：与上游同步的安全更新、正确的编译选项与自带模块、处理模板与环境变量的入口脚本、把日志引到标准流的软链接，以及统一的 nginx 用户身份。
- **官方镜像不含的东西**：第三方模块（如 Lua 一类），以及把静态产物烤进镜像的定制。
- **何时自建**：需要第三方模块、需要非默认编译选项，或希望镜像本身就包含配置与前端产物，让发布单元直接等于镜像。
- **自建要保留的约定**：若覆盖了镜像的启动命令，必须保留让 Nginx 前台运行的参数，否则容器启动后立即退出；官方镜像的默认命令已写成前台方式。
- **最小化思路**：前端产物的构建用多阶段，构建阶段用 Node 镜像产出静态文件，运行阶段只把产物拷进 nginx 镜像，最终镜像不含构建工具链。

```dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
```

> [!WARNING]
> **警告内容**：自建镜像里若把启动命令改成后台模式或漏掉前台参数，容器会立刻退出并不断重启。前台运行是容器里主进程的基本要求，覆盖启动命令时必须保留官方镜像默认命令里的前台参数。

**速记**：默认用官方镜像，要模块或要固化产物才自建，自建走多阶段且别丢前台运行。



### upstream 指向服务名

#### 容器网络里用服务名当上游地址

**基本写法**：Nginx 容器与后端容器同处一张自定义网络时，upstream 里可以直接写后端服务名加端口，解析由 Docker 内嵌 DNS 完成。

- **服务名即主机名**：同一网络内，Compose 的服务名会被登记进内嵌 DNS，容器按名字即可解析到地址，不必知道 IP。
- **写法**：upstream 块内用 server 指令写服务名加端口，proxy_pass 指向该 upstream 名。
- **只服务内部**：后端服务不必发布宿主机端口，同网容器直接访问它的容器端口即可。
- **与宿主机解析的区别**：这里的名字只有接入同一网络的容器才能解析，宿主机本身解析不到这个服务名。

```nginx
upstream api_backend {
    server api:3000;
}

server {
    listen 80;
    location /api/ {
        proxy_pass http://api_backend;
        proxy_set_header Host $host;
    }
}
```

> 这与库内 Nginx 系列里 upstream 写地址加端口是同一件事，只是地址换成了一个只在容器网络里存在的名字，解析机制改由内嵌 DNS 承担，详见第 9 篇 自定义网络与容器互联。

**速记**：同网服务名当主机名，upstream 写服务名加端口，后端不必发布宿主端口。



#### 加载期解析一次带来的核心问题

**核心行为**：Nginx 对 upstream 中的静态域名只在配置加载那一刻解析一次，把结果地址收进内存，此后不再查询 DNS；后端容器重建换了地址，Nginx 仍会连旧地址。

- **解析时机**：发生在启动与每次重载，不在每个请求上；一个域名解析出多个地址时，全部收进 upstream 组按轮询使用。
- **缓存后果**：容器重建得到新地址后，已在运行的 Nginx 组里还是旧地址，直到下一次重载才会更新。
- **旧地址的两种走向**：旧地址上已无进程监听时表现为连接被拒；旧地址若被别的容器复用，则请求可能被发到错误的实例上，问题更隐蔽。
- **触发条件**：只在重建后端但不重建 Nginx 时出现；整栈拆除再重建时 Nginx 也重建，会重新解析，因此通常不暴露问题。
- **与配置是否改动无关**：Nginx 的配置文件没动，只是它背后的地址变了，编排工具也不会因此重建 Nginx。

> [!WARNING]
> **警告内容**：这是容器化反向代理最典型的故障。后端容器被重建换地址后，Nginx 仍指向旧地址，表现是接口 502，而重启 Nginx 容器后立刻恢复。看到重启入口就好、过一阵又坏的循环，优先怀疑上游地址过期，而不是后端代码。

**速记**：静态域名只在启动或重载时解析一次并缓存，后端换地址后不重载就连旧地址。



#### 现象与因果链

**完整因果链**：后端容器重建，内嵌 DNS 中的地址变了，Nginx 内存里的 upstream 地址没变，Nginx 仍按旧地址建连，连接被拒或连错实例，最终返回 502 Bad Gateway。

- **第一步现象**：浏览器或调用方收到 502，而在容器网络内直接访问后端本身是正常的。
- **第二步证据**：看 Nginx 的错误日志，出现连接失败或没有可用上游的记录，记录里的上游地址与后端当前地址不一致。
- **第三步验证**：进入 Nginx 容器解析服务名，得到的是新地址；错误日志里的地址是旧的，两者对不上即坐实。
- **第四步处置**：让 Nginx 重新加载配置以重新解析，可用重载命令，或直接重建 Nginx 容器，处置后立刻恢复。

```bash
docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload

# 对照两条证据：容器内解析到的新地址，与日志里尝试的旧地址
docker compose exec nginx getent hosts api
docker compose logs --tail=50 nginx | grep -i upstream
```

> 把这条链记住，它同时是「为什么日志与 DNS 要一起看」的范例：光看 502 只能定位到代理与上游之间，要看旧地址才能定位到解析缓存过期。

**速记**：重建后端换地址、Nginx 内存没更新、连旧地址、502、重载即好，一条链背下来。



### 让上游解析跟随容器变化

#### resolver 加变量强制运行时解析

**方案一**：把上游地址写进变量，并用 resolver 指令指定 Docker 内嵌 DNS，让 Nginx 在每个请求上重新解析域名，从而跟随容器地址变化。

- **resolver 指令**：声明用哪个 DNS 服务器解析变量形式的域名，容器内应填内嵌 DNS 地址 127.0.0.11，并可用 valid 参数覆盖解析结果的缓存时长。
- **配合变量的写法**：把目标地址放进一个变量，proxy_pass 里引用该变量；只有出现变量，Nginx 才放弃加载期解析、改走 resolver。
- **valid 的意义**：控制解析结果在 Nginx 侧缓存多久，取小一点能让地址变化更快被感知，代价是解析与查询次数增加。
- **作用范围**：resolver 可写在 http、server 或 location 层，写在 http 层对全站生效。
- **变量下的路径行为**：proxy_pass 里出现变量后，URI 的处理方式与静态写法不同，需要按实际期望显式拼接，改完务必用请求验证上游收到的路径。

```nginx
server {
    listen 80;
    resolver 127.0.0.11 valid=10s ipv6=off;

    location /api/ {
        set $api_upstream http://api:3000;
        proxy_pass $api_upstream;
        proxy_set_header Host $host;
    }
}
```

> [!WARNING]
> **警告内容**：resolver 必须指向容器内可用的 DNS，也就是内嵌 DNS 地址 127.0.0.11；填宿主机上的 DNS 地址在容器里往往不可达。同时，走变量解析意味着放弃 upstream 块的高级特性，取舍见本节最后一条。

**速记**：变量加 resolver 127.0.0.11 加 valid，让每次请求重新解析，代价是放弃 upstream 高级特性。



#### 基于容器事件的自动重载

**方案二**：保留常规的 upstream 块写法，另起一个监听容器事件的进程；当上游相关容器启动或停止时，对 Nginx 执行一次重载，让配置被重新加载并重新解析。

- **实现思路**：订阅 Docker 的事件流，关注容器的启动、停止与网络变更，判断变化是否涉及上游服务，命中后向 Nginx 主进程发送重载信号。
- **两种载体**：在 Nginx 容器内运行一个侧进程，或单独起一个只负责触发重载的侧车容器。
- **成熟实现**：社区有以这套思路做成的自动代理工具，按事件生成上游配置并触发重载，避免手写这个循环。
- **代价一**：读取事件通常要挂载宿主机的 Docker 套接字，等于把宿主机的控制权交给这个容器，安全风险高。
- **代价二**：容器抖动频繁时会触发密集重载，每次重载都要重新拉起 worker，需要做去抖与限频。
- **收益**：upstream 块的全部特性都还在，长连接池、权重、被动健康检查照常可用。

```text
订阅 docker events（容器 start、die、network connect 等）
  -> 过滤出属于上游服务的容器事件
  -> 去抖后执行 nginx -s reload
```

> [!WARNING]
> **警告内容**：把宿主机的 Docker 套接字挂进任何容器，都等于把相当于最高权限的控制能力交出去——持有它的进程可以创建特权容器、挂载宿主目录。生产环境若采用这条路线，必须限制该容器的能力、网络与挂载面，或改用只暴露受限接口的代理。

**速记**：监听容器事件触发重载，保留 upstream 全部特性，代价是套接字带来的高权限。



#### 两种解法比较与定时 reload 为何是下策

**选择口径**：只关心地址跟随、且愿意放弃 upstream 高级特性时用 resolver 加变量；需要长连接池、权重与被动健康检查时用事件驱动的重载。

- **resolver 加变量**：改动只在 Nginx 配置内，不引入新组件与新权限，适合上游名字固定、副本集合不常变、对连接复用要求不高的场景。
- **事件驱动重载**：保留 upstream 块，适合上游集合会随扩容变化、且需要连接池与健康检查的生产场景，代价是需要一个能看容器事件的进程。
- **可接受的半自动**：扩容或发布后由发布脚本顺手执行一次重载，是介于两者之间的做法，前提是把重建后端就要重载入口写进发布流程。
- **定时重载的下策之处**：它不依据任何事件，只是周期性重载，故障窗口等于定时周期；周期内地址已过期但没人处理，周期一到又做一次与变化无关的重载，白白切换 worker。
- **更合理的方向**：与其定时重载，不如把重载挂到后端重建这个明确的动作上，或直接采用前两条方案之一。

> 判断标准很简单：重载应该由配置或上游发生了变化来触发，而不是由时间到了来触发。定时是拿确定性换简单，代价是把故障窗口固定成了一个可预测的长度。

**速记**：地址跟随用变量加 resolver，特性优先用事件驱动重载，定时重载按时间而非按变化，属下策。



### 代理头、缓冲与超时的容器语境

#### 代理四件套与后端生成绝对地址

**代理四件套**：Host、X-Real-IP、X-Forwarded-For、X-Forwarded-Proto 四个请求头，是把客户端信息与访问意图完整传给后端的最小集合，容器语境下缺一不可。

- **Host**：不设置时 Nginx 会把 Host 改成 proxy_host，也就是 upstream 里那个只在内网存在的服务名；后端据此生成的重定向与绝对地址会变成内网名，外部打不开。
- **X-Real-IP**：放入与 Nginx 直连的对端地址，供后端记录与风控读取。
- **X-Forwarded-For**：用 $proxy_add_x_forwarded_for 在已有链尾追加当前对端地址，保留完整代理链。
- **X-Forwarded-Proto**：用 $scheme 告知后端客户端用的是 http 还是 https，后端据此决定生成的绝对链接协议与是否给 Cookie 加安全标记。
- **后端侧配合**：应用需要显式声明自己信任代理，例如 Node 应用设置信任代理后，请求对象上的 IP 与协议才取自这些头，否则仍按直连地址判断，详见第 17 篇 Docker 部署 Node 应用实战。

```nginx
location /api/ {
    proxy_pass http://api_backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

> [!IMPORTANT]
> **重要内容**：容器化后 Host 被改写的后果比裸机更明显，因为默认值是一个外部根本解析不了的容器服务名。做代理时把四件套作为默认动作写进每个反代的 location，后端才会生成正确的跳转、回调与绝对地址。

**速记**：Host 给域名、X-Real-IP 给直连对端、X-Forwarded-For 给完整链、X-Forwarded-Proto 给协议，后端还要打开信任代理。



#### 缓冲与超时的默认值调整方向

**默认取向与调整方向**：Nginx 默认开启响应缓冲并给出偏保守的超时；容器网络内建连通常在毫秒级，连接超时可以收紧，读取超时按业务真实耗时放宽。

- **proxy_buffering**：默认开启，Nginx 尽快把上游响应收进自己的缓冲再慢慢发给客户端，保护上游不被慢客户端拖住；流式接口要单独关闭。
- **proxy_connect_timeout**：与上游建连的等待上限，默认偏长；容器网络内建连快，实践中收紧到几秒即可，避免上游不可达时长时间挂住。
- **proxy_read_timeout**：等待上游两次可读之间的间隔上限，是最常调整的一个；长任务接口按实际耗时放宽，或改造成异步任务。
- **容器语境的新增变量**：除上游本身慢，解析变慢或失败也会体现为超时类错误，排查超时要一并看名字解析是否正常。
- **流式的处理**：事件推送与流式对话接口要关闭缓冲并放宽读取超时，否则表现为后端在推、前端迟迟不出数据。

```nginx
location /api/ {
    proxy_pass http://api_backend;
    proxy_connect_timeout 5s;
    proxy_read_timeout    120s;
    proxy_buffering       on;
}
```

> 三个超时都是两次进展之间的间隔，而不是整次请求的总时限，只要上游持续有字节往来就不会触发。这也是流式接口能长时间不断、而完全无响应的接口会在超时点被切断的原因。

**速记**：连接超时收紧、读取超时按业务放宽、普通接口开缓冲、流式接口关缓冲。



#### 大文件上传与请求体上限

**请求体上限**：Nginx 用一条指令限制客户端请求体的最大体积，官方默认值很小（1m），超过即返回 413，上传接口必须在对应层级调大。

- **指令位置**：可写在 http、server、location 三层，内层覆盖外层；只改一处时要确认没有被更内层的配置盖回。
- **默认值触发**：默认上限很小，图片、附件、视频类上传几乎必然触发 413。
- **多道上限**：Nginx 只是第一道；后端应用框架、对象存储以及入口前面的云负载均衡各有自己的体积上限，需整链路一致。
- **容器语境**：上限写在挂载进容器的配置里，改完同样要重载或重建入口，容器内配置没更新则改了也不生效。
- **相关超时**：大文件上传常与上传超时相伴出现，必要时同步检查请求体读取相关超时参数。

```nginx
location /api/upload {
    proxy_pass http://api_backend;
    client_max_body_size 100m;
}
```

> [!CAUTION]
> **注意内容**：把请求体上限调得很大等于放宽了入口的资源占用口子，攻击者可以用超大请求体耗尽连接与磁盘。调整时应结合业务需要的上限设置，并配合限流与超时参数，而不是一味放大。

**速记**：默认 1m 超了 413，Nginx 只是第一道，整链路各层都要放宽。



### 多副本后端的负载均衡

#### upstream 写服务名还是容器名

**结论**：upstream 一律写服务名，不写容器名；容器名绑定具体实例，实例重建即换名，不能当作稳定上游。

- **服务名**：由编排工具依据服务键自动登记进内嵌 DNS，扩出多个副本时该名字会对应多个地址。
- **容器名**：形如项目名加服务名加序号，指向某一个具体容器，重建即失效，也不承担代表整个服务的语义。
- **多副本解析**：同一名字对应多个容器时，解析会返回多条地址记录，Nginx 加载配置时把这些地址都收进上游组按轮询使用。
- **加载期限制**：扩容发生在 Nginx 启动之后时，新增副本不会自动进入已在运行的上游组，这与上游解析一次的核心问题同源。
- **正确期望**：服务名负责让 Nginx 知道这个服务现在有哪些地址，是否分发、怎么分发由 Nginx 侧决定。

> 内嵌 DNS 返回多条地址只是把副本地址交出来，不代表它会替你做健康检查或会话保持。真正的分发策略、失败摘除与连接复用都由 Nginx 负责，两者是分工而非替代。

**速记**：上游写服务名不写容器名；服务名给地址集合，Nginx 给分发策略。



#### Docker DNS 服务发现与 Nginx 负载均衡的分工

**分工口径**：Docker 内嵌 DNS 负责名字到地址集合的映射，Nginx 的上游组负责在集合内选择、复用连接并在失败时摘除；前者是发现，后者是调度。

- **DNS 侧只做映射**：它不感知后端是否健康，不保证轮询，客户端若持有长连接则不会因地址变化自动切换。
- **Nginx 侧做调度**：轮询、权重、最少连接、哈希等策略，以及失败次数与超时窗口构成的被动摘除，都在上游组里配置。
- **配合方式**：启动或重载时，Nginx 通过内嵌 DNS 拿到地址集合填进上游组，此后在本组内按策略分发。
- **扩容的缺口**：DNS 能返回新地址，但 Nginx 已经解析过，缺口就出现在新副本进入了 DNS、却没进入 Nginx 的组，需要重载或改用运行时解析方案。
- **反向代理才有的健康判断**：这套组合让故障副本在被真实请求撞到后被摘除，是纯 DNS 轮询做不到的。

> 一句话分工：DNS 回答这个服务现在有哪些地址，Nginx 回答这个请求该交给哪一个、它坏了怎么办。把负载均衡的责任交给 DNS，等于放弃了后半个问题。

**速记**：DNS 管发现、Nginx 管调度；扩容缺口在 DNS 已知而 Nginx 未解析。



#### 会话保持的取舍

**取舍结论**：容器化下多副本应用的会话应外置到共享存储，不要把会话保持寄托在入口的粘性策略上，尤其不能用按客户端 IP 取哈希的策略当作完备方案。

- **有状态会话的问题**：会话存在单个副本的内存里时，负载均衡把后续请求分给另一副本，用户就被当作未登录。
- **按 IP 粘性的缺陷**：它只按客户端 IP 维持粘性，公司或校园网这类共享出口会让大量用户压到同一副本；该副本故障时这些用户的会话仍然丢失。
- **集中存储的正解**：把会话写进 Redis 一类共享存储，所有副本读写同一份数据，节点可随意增减、宕机不丢会话，呼应 Docker 部署 MySQL 与 Redis 实战。
- **无状态更优**：能用无状态令牌承载身份时，连共享存储都不必，副本可任意扩缩。
- **容器语境的额外理由**：副本会因重建、扩容、滚动发布而换地址与换实例，靠粘性维持会话的成功率比裸机时代更低。

> [!WARNING]
> **警告内容**：把会话保持交给按 IP 粘性，等于把应用的架构债转嫁给入口。共享出口导致的负载倾斜无法根治，副本故障时的会话丢失也无法避免；正确方向是无状态化，退一步也要把会话外置到 Redis。

**速记**：会话外置到 Redis 或做成无状态，按 IP 粘性只算过渡手段，靠不住。



### 静态资源与前端单页应用

#### 静态产物进镜像还是挂载

**两种做法**：把构建好的静态产物打进 Nginx 镜像适合发布，绑定挂载宿主构建目录适合开发；两者对应发布单元是镜像与改动即时可见两种需求。

- **打进镜像**：用多阶段构建，构建阶段产出静态文件，运行阶段只把产物拷进 nginx 镜像；镜像即发布单元，可版本化、可回滚、可推到私有仓库。
- **挂载宿主目录**：把宿主上的构建产物目录只读挂进容器的站点根目录，改完刷新即可见，适合本地开发与调试。
- **混合做法**：平时挂载开发，发布时构建一个把产物烤进去的镜像，两套流程不冲突。
- **容器语境的注意点**：挂载目录的属主与权限要与容器内进程可读相匹配；只在宿主改文件而容器看不到，先怀疑挂到了别处或没挂上。
- **与入口的关系**：静态资源由 Nginx 直接返回，不经过后端应用，少一次上游转发，这也是把静态资源放在入口的标准理由。

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    volumes:
      - ./dist:/usr/share/nginx/html:ro
```

> 生产优先把产物打进镜像，是为了让这次上线的是哪个版本有唯一定论；开发期挂载，是为了让改一行看一眼不用等构建。两种诉求不同，做法也应不同。

**速记**：生产把产物烤进镜像可回滚，开发挂载宿主目录即时可见。



#### 单页应用的路由回退

**路由回退**：单页应用的可见路径都由前端路由管理，直接刷新某个子路径时服务端并没有对应文件，需要用 try_files 把找不到的路径回退到入口页面。

- **try_files 的语义**：按顺序检查文件是否存在，用第一个存在的文件处理请求；全部不存在时，对最后一个参数做内部重定向。
- **常见写法**：先找同名文件，再找同名目录，最后回退到入口页；入口页由 index 指定。
- **顺序的坑**：反代接口的 location 必须优先于静态兜底，否则接口路径会被回退到入口页，前端拿到的是页面而不是接口数据。
- **index 的作用**：指定目录请求时的默认页，与回退目标配合，保证访问根路径与访问子路径都落到同一个入口页。
- **容器语境不变**：这部分行为与 Nginx 是否在容器里无关，只是配置同样要靠挂载或镜像进入容器并重载生效。

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location /api/ {
        proxy_pass http://api_backend;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

> [!IMPORTANT]
> **重要内容**：回退规则写得太宽会把接口请求也回退成页面。先匹配到的 location 才算数，因此把接口与长连接一类路径的 location 放在静态兜底之前，或用更精确的匹配修饰符限定，是单页应用上线的必查项。

**速记**：try_files 依次找文件、找不到回退入口页，接口的 location 必须排在兜底之前。



#### 同域分路径与缓存头

**同域分路径**：前端页面与后端接口放在同一域名下、用路径区分（页面走根路径，接口走 /api/），可以免去跨域配置，是容器栈里最省事的分法。

- **路径分法**：静态资源与页面由 Nginx 直接服务，接口路径反代到后端应用，客户端只需访问一个域名。
- **受益**：同源之下没有跨域请求，Cookie 天然同域，鉴权与回调都更简单。
- **缓存头分两类**：入口页面不能长缓存，带内容指纹的静态资源要长缓存。
- **入口页不缓存**：入口页每次都要回源确认，用 no-cache 一类响应头，保证发布后用户能拿到引用新资源的新页面。
- **指纹资源长缓存**：文件名里带内容哈希的脚本与样式可以放心配置一年期强缓存，因为内容变了文件名就变了。
- **配对原则**：两类头必须成对配置；只配了长缓存的静态资源而没有不缓存的入口页，用户会长期被旧页面指向旧资源。

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location ~* \.(?:js|css|woff2|png|jpg|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

> [!CAUTION]
> **注意内容**：给入口页面配长缓存，会让用户在新版本发布后仍打开旧页面，而旧页面引用的旧资源可能已被清理，表现是白屏或样式错乱，且刷新也未必恢复。发布类站点务必让入口页每次回源确认，只对带指纹的资源长缓存。

**速记**：同域分路径免跨域，入口页不缓存、带指纹资源长缓存，两者必须成对。



### HTTPS 与证书

#### 证书文件挂载进容器

**做法**：把证书与私钥文件只读挂载进容器内的一个目录，在 server 块里用容器内的绝对路径引用；证书是宿主侧资产，不写进镜像。

- **挂载方式**：把宿主的证书目录只读挂到容器内如 /etc/nginx/certs，配置里按该路径引用。
- **完整链**：证书指令指向服务器证书与中间证书拼接的完整链文件，缺中间证书会让部分客户端报不受信任。
- **私钥**：指向私钥的指令对应的文件权限应收敛到只有需要读取它的身份可读；挂载时保持只读。
- **不在镜像里放私钥**：把私钥烤进镜像会被推到仓库并被任何能拉取镜像的人读取，等同于泄露；一律靠挂载注入。
- **路径基准**：配置里用容器内的绝对路径，而不是宿主上的路径，这是容器化后最常见的写错点。

```nginx
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/certs/example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/example.com.key;
}
```

```yaml
services:
  nginx:
    volumes:
      - ./nginx/certs:/etc/nginx/certs:ro
```

> [!WARNING]
> **警告内容**：私钥绝不能进入镜像层。镜像层可被任何能拉取镜像的人解开读取，即便后续删除也仍留在历史层里；证书与私钥只通过只读挂载注入容器，是容器化下不可退让的一条。

**速记**：证书与私钥只读挂载、用容器内路径引用、认准完整链、私钥不进镜像。



#### Let's Encrypt 的两条路线

**两条路线**：独立证书客户端容器与 acme.sh，都是在容器栈里自动申请与续期的常见做法；差别在载体与自动化方式，思路一致。

- **独立容器路线**：把证书申请与续期做成栈里的一个服务，与 Nginx 解耦；常用网页目录方式，让验证文件通过 Nginx 可直接访问的目录完成校验，也可用临时占用端口的方式。
- **acme.sh 路线**：一个轻量的证书客户端脚本，支持网页目录验证与 DNS 验证，续期靠其自带的定时任务触发。
- **共同的落点**：两者都把签出的证书写到某个目录，再由 Nginx 从该目录读取，因此证书目录通常是容器之间共享的一个卷或宿主目录。
- **验证方式的选择**：网页目录验证要求域名已能对外访问且 Nginx 已在服务；DNS 验证不依赖 80 端口，适合只开内网或用通配符证书的场景。
- **只记思路与官方入口**：具体命令与参数随版本变化，以 Let's Encrypt 官方文档与各客户端的官方站点为准，不在笔记里写死。

> 证书客户端都只是取证书的工具，取到之后证书放在哪里、谁去读、读完要不要重载，这才是容器栈里真正需要设计的三步。

**速记**：独立客户端容器与 acme.sh 都是取证书的工具，证书目录共享、续期自动化、细节以官方站点为准。



#### 续期后的重载联动与自签名证书

**必须联动**：Nginx 把证书读进内存后不会自动重读磁盘上的新文件，因此证书续期成功只是把新文件写到磁盘，必须再让 Nginx 重新加载配置，新证书才真正生效。

- **联动方式**：在续期工具的续期后钩子里执行一次重载，让申请与生效成为一步。
- **从容器外触发重载**：由宿主上的定时任务在续期后对 Nginx 容器执行一次重载，是最简单也最可控的做法。
- **共享套接字的代价**：让证书容器通过 Docker 套接字去操作 Nginx 容器，实现上更顺，但同样带来高权限风险，需权衡。
- **自签名证书**：本地开发用自签证书启用 HTTPS，浏览器必然报警告；它只适合本地调试与内部服务间的加密，不能替代面向公网的可信证书。
- **内部服务间加密**：自签证书用于内部双向加密时，需要把签发它的根写入对端信任列表，否则同样报不受信任。

> [!CAUTION]
> **注意内容**：续期脚本报成功、证书文件也换新了，但浏览器仍提示过期，九成是没有重载 Nginx，它还在用内存里的旧证书。判断方法是对外实际取一次证书看它下发的到期时间，而不是只看磁盘文件的时间。

**速记**：续期只是写文件，必须再重载才生效；自签证书只用于本地与内部，不能上公网。



#### HSTS 的启用前提

**前提**：HSTS 是通过响应头让浏览器在指定时长内强制用 HTTPS 访问本域名的机制，启用前必须先确认全站与相关子域都已在 HTTPS 上稳定运行。

- **作用**：浏览器收到该头后记住策略，之后对本站的访问一律改用 HTTPS，不再走明文的跳转，堵住中间人把 HTTPS 降级为 HTTP 的空间。
- **启用前提**：全站已经能用 HTTPS 正常访问，且证书有效、续期链路可靠，否则策略期内用户会被浏览器拦在门外。
- **子域的影响**：让策略覆盖子域时，所有子域都必须 HTTPS 就绪，任何一个还在用 HTTP 的子域都会立刻不可访问。
- **撤回困难**：策略一旦下发，在有效期内极难撤回，证书过期或配置回退都会造成用户侧无法绕过的拦截。
- **推荐路径**：先用很短的有效期试运行，确认全站与子域都就绪后，再逐步延长有效期并考虑覆盖子域。

```nginx
add_header Strict-Transport-Security "max-age=300" always;
```

> [!WARNING]
> **警告内容**：HSTS 在有效期内的约束对浏览器是强制的，用户与服务方都很难绕过。证书一旦过期未续，用户看到的是无法跳过的拦截页；上线前务必先小步试运行，确认证书自动续期与全站 HTTPS 都没问题，再延长有效期。

**速记**：HSTS 的前提是全站及子域 HTTPS 就绪，先小有效期试跑，下发容易收回难。



### 日志与可观测

#### 访问日志与错误日志的去向

**去向**：nginx 官方镜像把访问日志与错误日志分别软链接到标准输出与标准错误，因此日志默认进入容器的标准流，由 Docker 日志驱动采集，用 docker logs 一类命令查看。

- **默认行为**：镜像构建时就建立了这两条软链接，日志内容直接出现在容器的标准输出与标准错误里。
- **查看方式**：用聚合日志命令或容器日志命令查看，配合跟随与截断选项定位问题。
- **轮转责任转移**：容器内不再需要日志轮转工具；轮转由日志驱动的大小与数量选项，或外部的日志采集器负责。
- **写文件则失联**：若配置把日志指向容器内的普通文件，日志就离开了标准流，容器日志命令看不到，采集器也可能收不到。
- **采集位置变化**：裸机时代是采集器去读宿主上的日志文件，容器化后是采集器读容器标准流或日志驱动的落盘文件，采集配置要跟着改。

```nginx
# 保留默认软链接即日志进标准流；若确要显式指定
access_log /dev/stdout;
error_log  /dev/stderr;
```

> [!IMPORTANT]
> **重要内容**：把日志写进容器内文件是容器日志里最差的做法——文件随容器销毁而消失，宿主上也看不到，采集器还常常无从接入。日志一律走标准输出与标准错误，与 Docker 容器日志与监控一篇的结论一致。

**速记**：日志默认进标准流、由日志驱动采集，别再往容器内文件里写。



#### 记录真实客户端 IP 的格式

**目标**：在代理链的不同位置，$remote_addr 的含义不同；要在日志里稳定拿到真实客户端地址，要么信任代理链并还原，要么直接记录转发头。

- **Nginx 直接对外**：客户端经宿主端口访问时，$remote_addr 通常就是真实客户端地址。
- **前面还有一层代理**：Nginx 前面若还有云负载均衡或内容分发网络，$remote_addr 会是那一层的地址，真实地址只在转发头里。
- **记录转发头**：在日志格式里补上转发头字段，保留完整代理链，便于事后还原。
- **还原为 $remote_addr**：用 realip 模块声明可信代理网段并指定从哪个头还原，把 $remote_addr 本身改写成真实地址，后端与日志都无需再改。
- **安全前提**：可信代理网段只能写自己可控的节点，绝不能无条件信任来自任意来源的转发头。

```nginx
log_format proxy_log '$remote_addr - $remote_user [$time_local] "$request" '
                     '$status $body_bytes_sent "$http_referer" '
                     '"$http_user_agent" "$http_x_forwarded_for"';

server {
    listen 80;
    access_log /dev/stdout proxy_log;
}
```

> 容器语境的额外情况：从宿主机自身访问、或从同一张容器网络内的其他容器访问时，$remote_addr 会落在容器网段里，这是正常的直连对端地址，不代表配置有错。

**速记**：直连对端看 $remote_addr，有前置代理就记转发头或用 realip 还原，可信网段只写自己人。



#### 健康检查端点

**做法**：给 Nginx 配一个专用的探针路径，只返回一个固定的成功响应，并用它做容器健康检查；不要把首页或依赖上游的路径当探针。

- **专用端点**：用精确匹配的 location 直接返回成功状态，不读磁盘、不转上游，开销最小、结论最确定。
- **探针的价值**：容器编排用健康检查判断入口是否就绪，决定是否把流量交给它，也决定依赖它的服务能否启动。
- **不要用首页**：首页可能依赖上游或磁盘，返回成功也可能是上游挂了而错误页正常，让探针给出假阳性。
- **不要用依赖上游的路径**：那是在探入口和后端两个东西，任一抖动都会让入口被判定不健康，反而放大故障。
- **工具选择**：探针命令要用镜像里现成的工具，Alpine 系变体可用 busybox 的 wget，Debian 系变体装有 curl，不必额外装包。

```yaml
services:
  nginx:
    image: nginx:1.27-alpine
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "-", "http://localhost/healthz"]
      interval: 30s
      timeout: 3s
      retries: 3
```

```nginx
location = /healthz {
    access_log off;
    return 200 "ok";
}
```

> [!CAUTION]
> **注意内容**：探针路径若依赖上游或磁盘，会把后端抖动放大成入口不健康，进而触发入口重启或被摘除，故障范围从一层扩散到两层。入口的探针只回答入口自己在不在，后端是否健康交给后端自己的探针。

**速记**：探针用专用端点直接返回成功，不依赖上游与磁盘，命令用镜像自带工具。



### 完整实战：四服务栈

#### compose.yaml 全文

**栈的构成**：一个入口、一个可多副本的应用、一个数据库、一个缓存，四者分属外部、后端与数据三层网络，静态资源由入口直接服务，接口反代到应用。

```yaml
name: demo-stack

services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
      - ./nginx/certs:/etc/nginx/certs:ro
      - ./dist:/usr/share/nginx/html:ro
    depends_on:
      api:
        condition: service_healthy
    networks:
      - edge
      - backend
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "-", "http://localhost/healthz"]
      interval: 30s
      timeout: 3s
      retries: 3
    restart: unless-stopped

  api:
    build:
      context: ./api
    expose:
      - "3000"
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/shop
      REDIS_URL: redis://cache:6379
      NODE_ENV: production
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    networks:
      - backend
      - data
    healthcheck:
      test:
        - "CMD"
        - "node"
        - "-e"
        - "fetch('http://localhost:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"
      interval: 30s
      timeout: 3s
      retries: 3
    restart: unless-stopped

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: shop
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    volumes:
      - cache-data:/data
    networks:
      - data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    restart: unless-stopped

volumes:
  db-data:
  cache-data:

networks:
  edge: {}
  backend: {}
  data:
    internal: true
```

配套的入口配置放在宿主的 nginx/conf.d/default.conf，静态产物放在宿主的 dist 目录。

```nginx
upstream api_backend {
    server api:3000;
    keepalive 16;
}

server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/certs/example.com.fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    root /usr/share/nginx/html;
    index index.html;

    location = /healthz {
        access_log off;
        return 200 "ok";
    }

    location /api/ {
        proxy_pass http://api_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection          "";
        proxy_set_header Host                $host;
        proxy_set_header X-Real-IP           $remote_addr;
        proxy_set_header X-Forwarded-For     $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto   $scheme;
        client_max_body_size 20m;
    }

    location ~* \.(?:js|css|woff2|png|jpg|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

> [!NOTE]
> **提醒内容**：示例中的口令是占位值，仅用于演示字段写法，不可用于任何真实环境。真实项目应把口令抽到环境变量文件或密钥中，并确保其不进入版本库，做法见环境变量、配置注入与密钥管理一篇。

**速记**：四服务、三层网络、入口只发 80 与 443、静态入口直出、接口反代、多副本只暴露容器端口。



#### 逐段讲解

**关键取舍**：入口只发布 80 与 443，应用只暴露容器端口不发布宿主端口，数据层放进内部网络；这样副本可自由增减，数据层也不对外可达。

- **name 与项目隔离**：固定项目名，容器名前缀、网络名与卷名都据此生成，便于识别这套栈的资源。
- **nginx 的 ports**：只把 80 与 443 发布到宿主，整个栈对外仅这两个入口；其余服务不暴露宿主端口。
- **nginx 的 volumes**：配置目录、证书目录、静态产物目录都只读挂载；配置改动重载即生效，产物改动刷新即见。
- **nginx 的 depends_on**：用长语法把依赖条件写成应用健康，保证入口启动时后端至少已经就绪，写法见第 11 篇 Docker Compose 进阶与实战。
- **api 的 expose**：只声明容器端口供同网服务访问，不发布宿主端口，因此可以扩出多个副本而不冲突。
- **api 的环境变量**：数据库与缓存的地址都用服务名，靠内嵌 DNS 解析，与入口用服务名当上游是同一套机制。
- **api 的 depends_on**：等数据库与缓存都健康再启动，减少必然失败的启动尝试。
- **db 与 cache**：都只接入内部数据网络，数据落在命名卷上，容器重建不丢；命名卷不随普通拆除命令删除。
- **networks 三层**：edge 承载入口与外界，backend 承载入口到应用，data 是内部网络承载应用与数据层；内嵌 DNS 的名字只在同网可见。
- **upstream 与长连接**：应用服务名写进 upstream，保留连接池；要让连接池真正生效，代理的 location 里必须同时有协议版本与清空连接头两行。

> api 用 build 从本地源码构建，适合演示；若换成已发布镜像，把 build 换成 image 并固定标签即可，其余不变。

**速记**：入口只发 80 与 443，应用只 expose，数据层进内部网，命名卷存数据，配置与证书只读挂载。



#### 启动与扩容验证

**操作链路**：先校验文件，再启动，确认健康后访问；扩容后要重建或重载入口，新副本才会被纳入。

- **校验**：启动前先用 config 子命令确认文件语法与插值无误。
- **启动**：后台启动全栈，静态资源由入口直接返回，接口反代到应用。
- **观察**：用进程状态命令看健康，用日志命令看入口与应用输出，确认入口能连上游。
- **扩容**：把应用扩成多副本，再重建或重载入口，让其通过内嵌 DNS 拿到全部副本地址。
- **验证负载**：多次请求接口，从入口日志的上游地址字段观察分发是否落在不同副本上。
- **拆除**：普通拆除保留命名卷；确认数据可弃时才加删除卷的选项，那会连数据一起删除。

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose up -d --scale api=3
docker compose up -d --force-recreate nginx
docker compose logs -f --tail=50 nginx
docker compose down
```

> [!WARNING]
> **警告内容**：拆除命令加上删除卷选项会删除命名卷，数据库与缓存的持久化数据一并丢失且不可恢复。日常重建环境用不带该选项的拆除命令，只有确认数据可弃或已有备份时才加。

**速记**：先校验、再启动、看状态与日志、扩容后重建或重载入口、拆除时慎用删除卷选项。



### 常见故障排查

#### 502 Bad Gateway 的三层排查

**排查顺序**：502 表示代理连不上上游或上游给了非法响应；容器化下按网络是否通、上游是否健康、解析到的地址是否过期三层依次查，能覆盖绝大多数情况。

- **第一层，Nginx 到上游的网络**：从 Nginx 容器内向服务名与端口发一个请求，通则说明网络与解析都没问题。
- **第二层，上游是否健康**：用进程状态命令看应用容器状态与健康，用日志命令看应用是否在报错或反复重启。
- **第三层，解析到的地址是否过期**：在 Nginx 容器内解析服务名得到当前地址，再与错误日志里记录的地址对照，不一致即坐实解析缓存过期，重载或重建入口即可。
- **日志证据**：错误日志里连接被拒或没有可用上游的记录会带出实际尝试的上游地址，这是最直接的证据。
- **处置动作**：属于第三层的，对入口执行一次重载；属于第二层的，先把应用拉起来；属于第一层的，核对两个服务是否在同一张网络上。

```bash
docker compose exec nginx wget -q -O - http://api:3000/health
docker compose ps
docker compose exec nginx getent hosts api
docker compose logs --tail=100 nginx | grep -i upstream
```

> [!WARNING]
> **警告内容**：看到 502 就直接重启容器，往往只是暂时掩盖了地址缓存或启动顺序问题，根因还在。先按三层确认断点在哪一层，再动手，避免重启就好、过一阵又坏的循环。

**速记**：先测网络通不通，再看上游活没活，最后比对解析地址与日志地址是否一致。



#### 504 超时定位

**定位方法**：504 表示上游连得上但没在时限内给出进展，要区分是建连阶段、发送阶段还是读取阶段超时，再对应调整或优化上游。

- **三类阶段**：连接超时指建连就没成功，发送超时指请求写不出去，读取超时指等响应等不到，三者各对应自己的超时指令。
- **日志关键字**：错误日志里出现上游超时的字样，并会指出是哪个阶段、哪台上游。
- **容器侧新增因素**：除上游本身慢，容器网络抖动、解析变慢、宿主资源紧张也会表现为超时，排查时一并看容器与宿主状态。
- **调参方向**：调大超时只是把等待拉长，治标；反复超时的接口应先分析上游为什么慢，或改造为异步任务。
- **与客户端断开的对照**：若日志里同时出现大量客户端提前断开的记录，说明调用方等不及先走了，根因仍多在上游太慢。

```bash
docker compose logs --tail=100 nginx | grep -i 'timed out'
docker compose exec nginx wget -q -O - http://api:3000/health
```

> 区分 502 与 504 只需一句：502 是连不上或答非所问，504 是连上了却等不到回应。方向不同，先看日志里是拒绝连接还是超时。

**速记**：502 查死活、504 查快慢；建连、发送、读取三段各查一次。



#### 413 上传被拒

**成因**：413 表示请求体超过入口允许的上限，多半是上传路径没有把请求体大小上限调大，官方默认值很小。

- **先确认指令与层级**：请求体大小上限可写在 http、server、location，内层覆盖外层；确认上传路径命中的那一层到底是多少。
- **确认改动已生效**：容器里生效的是挂载进去的配置，改完要重载或重建入口，否则改的是宿主文件而容器没读。
- **整链路核对**：入口之外，后端应用的请求体限制、前面的云负载均衡都可能拦下大请求，需一并调整。
- **相关参数**：大文件上传常伴随超时问题，必要时同步放宽请求体读取相关超时。
- **两难取舍**：上限放大提高了资源被占用的风险，应结合业务设置合理值并配合限流。

```bash
docker compose exec nginx nginx -T | grep -n client_max_body_size
```

> 这一条与裸机上的排查完全一致，容器化只多了一问：容器里实际生效的配置，是不是刚改的那份。

**速记**：默认上限很小、内层会覆盖外层、容器内配置要重载才生效、整链路都要放宽。



#### 真实 IP 变成容器网段地址

**成因**：Nginx 日志里的客户端地址落在容器网段，通常是访问来自宿主机自身或同一容器网络内的其他容器，也可能是前面还有一层代理而没做还原。

- **同网访问**：从容器网络内的其他容器访问入口时，对端地址本来就是容器地址，属正常现象。
- **宿主机访问**：在宿主上用本机地址直接请求时，也可能落到容器网段，这与真实用户的访问路径不同。
- **前置代理未还原**：入口前还有一层代理或内容分发网络时，$remote_addr 是那一层的地址，真实地址在转发头里，需要还原。
- **还原做法**：用 realip 模块声明可信代理网段与从哪个头还原，把 $remote_addr 改成真实地址，日志与后端都据此取值。
- **安全底线**：可信来源只能是自己可控的节点，绝不能无条件信任任意转发头，否则限流与封禁会被伪造绕过。

```nginx
set_real_ip_from 172.16.0.0/12;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

> [!CAUTION]
> **注意内容**：把转发头里的地址不加甄别地当作真实客户端 IP，用于风控与限流，等于把伪造入口递给攻击者。只信任自己链路上的代理节点，把可信网段写死在配置里。

**速记**：容器网段地址多为同网或宿主访问，有前置代理就用 realip 还原，可信网段只写自己人。



#### 配置改了不生效

**三类原因**：容器里看到的不是新文件、改了文件没重载，或者文件根本没落在被加载的路径上，逐项排除即可。

- **原因一，单文件挂载被替换**：编辑器保存时替换了宿主文件，容器绑定的还是旧文件，改动看不见；改用目录挂载可避免。
- **原因二，改了没重载**：Nginx 在加载期读取配置，改完文件必须重载或重建入口容器才生效。
- **原因三，没落在加载范围**：新增的文件名或扩展名不符合主配置 include 的通配符，等于没被读入。
- **定位手段**：用输出最终配置的选项查看容器内合并后的结果，直接确认改动有没有被加载；同时把容器内文件内容打印出来与宿主对照。
- **固定流程**：改宿主文件、核对容器内内容、校验配置、重载，四步走完再验证。

```bash
docker compose exec nginx nginx -T
docker compose exec nginx cat /etc/nginx/conf.d/default.conf
docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload
```

> 先分清是文件没进去还是进去了没加载，两者处置完全不同：前者查挂载，后者查重载与 include 范围。

**速记**：查文件进没进容器、查有没有重载、查文件名在不在 include 范围，三步定位。



#### 证书续期后仍报过期与端口被占用

**两类问题**：证书续期后浏览器仍报过期，多是 Nginx 没重读到新证书；容器重启后端口占用，多是旧容器没清理或有别的进程占着宿主端口。

- **证书仍过期**：磁盘上的证书已换新，但 Nginx 内存里还是旧证书，必须重载才换成新的；也可能是续期根本没成功，或前面还有一层代理在用旧证书。
- **验证实际下发**：在宿主上对外实际取一次证书，看它下发的到期时间；这个时间比磁盘文件的时间更有说服力。
- **端口被占用**：看到端口已被分配，先用容器与宿主两侧的命令查是谁占着该端口。
- **旧容器残留**：上一次没清理干净的容器仍在占用宿主端口，移除旧容器再启动即可。
- **绑定地址冲突**：同一容器端口先后绑到全部接口与仅本机地址的同一端口，也会互相冲突，注意映射写法是否一致。

```bash
docker ps --filter publish=80
docker compose exec nginx nginx -s reload
docker compose up -d --force-recreate nginx
```

> 证书与端口这两件事在这一步合看，是因为它们都指向同一个动作——让入口重新读取环境。证书要重载，端口冲突往往要重建。

**速记**：续期后必须重载才换证书、用对外实际取到的到期时间判断；端口占用先查旧容器再查宿主进程。
