## Docker 部署 Node 应用实战

### 示例项目与目录约定

#### 最小但完整的应用结构

**示例项目**：一个刻意做小的 Node HTTP 服务，它同时带有源码、测试、静态资源、迁移脚本与依赖清单，足以覆盖镜像构建需要处理的每一类文件。

```text
node-app/
├── src/
│   ├── index.js           # 入口：创建并启动 HTTP 服务
│   ├── app.js             # 组装中间件与路由
│   ├── db.js              # 数据库与缓存客户端
│   └── routes/
│       └── health.js      # 存活与就绪端点
├── test/
│   └── app.test.js
├── public/                # 静态资源，由应用直接托管
│   └── index.html
├── scripts/
│   └── migrate.js         # 一次性迁移任务
├── package.json
├── package-lock.json
├── .env.example           # 变量清单，只列键名与示例值
├── .dockerignore
├── Dockerfile
└── compose.yaml
```

- src：应用源码，运行镜像真正需要的只有这一部分，编译型项目对应编译后的 dist。
- test：测试用例，只在构建阶段运行，永不进入运行镜像。
- public：静态资源，由应用进程直接托管时属于运行产物。
- scripts：迁移与初始化脚本，供一次性任务服务复用应用镜像。
- package.json 与 package-lock.json：前者声明依赖范围，后者锁定确切版本与下载地址。
- .env.example：只写键名与示例值，真实的 .env 既不提交也不打包。

> 约定俗成的入口是 src/index.js 加 package.json 的 start 脚本。镜像里的启动命令应当直接指向入口文件，而不是绕道 npm start，原因见后文进程与信号一节。

**速记**：src 与产物进镜像，test 与脚本不进运行镜像，清单与锁文件一起带。



#### 文件的三层归属

**三层归属**：把项目文件按「构建上下文」「构建阶段」「运行镜像」三层划分，先确定每个文件的归属，再动手写 Dockerfile。

- 进构建上下文但不进任何镜像：.git 目录、.env、日志、编辑器配置、本地数据目录、宿主上装好的 node_modules。
- 进构建阶段但不进运行镜像：test 目录、TypeScript 编译器与打包器、devDependencies 全量、构建脚本、原生模块的编译工具链。
- 进运行镜像：编译产物或源码目录、生产依赖、package.json、必要的静态资源与配置模板。

> 判断标准只有一条：这个文件在容器启动之后还会被读到或用到处吗。答不上来的，一律不进运行镜像。

> 三层归属是整篇的主线：单阶段镜像的问题、多阶段镜像的价值、.dockerignore 的写法，最终都归结为「把文件放对层」。先列出清单再写 Dockerfile，比事后靠 history 反查哪里多带了文件省事得多。

**速记**：上下文、构建阶段、运行镜像三层，运行镜像只留启动后还用得到的。



#### .dockerignore 排除什么与为什么

**.dockerignore**：放在上下文根目录的排除清单，在上下文打包上传之前剔除指定文件，既缩小传输量，又挡住不该进镜像的内容。

```text
# 版本库与本地环境
.git
.gitignore
.env
.env.*

# 依赖与构建产物
node_modules
dist
build
coverage

# 日志与临时文件
*.log
npm-debug.log*
.DS_Store

# 编辑器与文档
.vscode
.idea
README.md
```

- node_modules：宿主依赖绝不能进上下文，否则 COPY 会把宿主装好的依赖覆盖进镜像，甚至把另一个平台的二进制带进去。
- .env 与 .env.*：真实变量文件含口令，一旦被 COPY 就打进镜像层，删不掉。
- dist 与 build：产物由构建阶段现算，复制宿主产物会把本机平台差异带进镜像。
- .git：体积大且会暴露提交历史与作者信息。
- 语法与 .gitignore 相近，一行一条，支持星号通配与叹号取反。

```bash
docker build -t node-app:1.0 .
docker build --no-cache -t node-app:1.0 .
```

> [!CAUTION]
> **注意内容**：构建上下文是整体上传给构建器的。漏排 node_modules 会让每次构建都多传成千上万个文件，构建明显变慢；漏排 .env 则等于把密钥随镜像分发出去。先写 .dockerignore，再写 Dockerfile。

**速记**：版本库、依赖目录、产物、日志、凭证一律排除，先写 .dockerignore 再写 Dockerfile。



### 单阶段镜像：先把应用跑起来

#### 朴素 Dockerfile 的写法

**单阶段镜像**：整份 Dockerfile 只有一个 FROM，从基础镜像出发依次复制与安装，最后直接启动应用，是所有优化之前必须能跑通的那一版。

```dockerfile
FROM node:24
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["node", "src/index.js"]
```

- FROM 用带主版本的官方镜像，不写 latest。
- WORKDIR 建工作目录并成为其后相对路径的基准。
- COPY 整个上下文，简单但把一切都绑进同一层。
- RUN npm install 装齐 dependencies 与 devDependencies。
- CMD 用数组形式启动，保证信号直达 Node 进程。

> 这一版的价值是「先证明应用能在容器里跑起来」。构建失败、端口不通、依赖缺失这类基础问题应当在这一步解决，不要去优化一个跑不起来的镜像。

**速记**：一个 FROM、COPY 全部、装全部依赖、直接启动，先跑通再谈优化。



#### 构建、启动与验证

**验证顺序**：构建镜像、前台运行看日志、另开终端验证响应，三步确认应用真的可用。

```bash
docker build -t node-app:1.0 .
docker run --rm -p 3000:3000 --name node-app node-app:1.0
```

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/healthz
docker exec node-app node -v
docker image ls node-app
```

- 前台运行便于直接看到启动日志与报错，确认无误后再加 -d 转后台。
- 端口映射写成宿主端口在前、容器端口在后，写反会表现为启动成功却访问不到。
- 应用必须监听 0.0.0.0 而不是 127.0.0.1，后者只接受容器内部连接。
- 用 node -v 确认镜像内的运行时版本，用 image ls 记下体积作为后续对比的基线。

> [!WARNING]
> **警告内容**：容器内监听 127.0.0.1 是最常见的「容器跑着却访问不了」。它在开发机正常，进容器即失效，排查时容易被误判为端口映射配错。容器里的监听地址一律写 0.0.0.0。

**速记**：build 看报错、run 看日志、curl 看响应、image ls 记基线。



#### 朴素写法的四个问题

**四个问题**：能跑通不等于能上线，单阶段朴素写法在体积、依赖、权限与可观测性四处同时失分。

- 体积大：完整基础镜像加上全量依赖与源码，镜像动辄数百兆，推送与拉取都慢。
- 含构建依赖：test 目录、打包器、编译器与原生模块工具链全部随镜像发行，攻击面被放大。
- 以 root 运行：不写 USER 时主进程默认是 root，一旦应用被突破即获得容器内 root 权限。
- 无健康检查：编排器与运维只能靠「进程还在不在」判断，进程活着但依赖断开时仍会继续收流量。

```bash
docker run --rm node-app:1.0 ls -la /app
docker history node-app:1.0
docker inspect -f '{{.Config.User}}' node-app:1.0
docker inspect -f '{{.Config.Healthcheck}}' node-app:1.0
```

```text
Config.User 为空，表示以默认的 root 运行
Config.Healthcheck 为空，表示未定义健康检查
```

- ls 看运行镜像里有没有 test、源码与编译工具。
- history 看每一层做了什么，找出体积贡献最大的层。
- Config.User 为空说明没降权，Config.Healthcheck 为空说明没探活。

> 四个问题对应后文的四组解法：多阶段构建、依赖裁剪、USER 降权、HEALTHCHECK。它们彼此独立，可以逐个补齐。

**速记**：体积大、带构建依赖、跑 root、缺探活，四处都要单独补。



### 多阶段镜像：deps、build 与 runtime

#### 三阶段的分工

**多阶段构建**：在同一个 Dockerfile 内用多个 FROM 把「装依赖」「编译」「运行」拆开，最终镜像只保留运行阶段，工具链与源码留在被丢弃的中间阶段。

- deps 阶段：只复制依赖清单，装齐全部依赖，作为编译阶段的底座，同时保住依赖层缓存。
- build 阶段：从 deps 继承已装好的依赖，复制源码并执行构建，产出 dist 或直接产出可运行的源码目录。
- runtime 阶段：只带生产依赖与产物，以非 root 身份运行，是真正发布出去的那个镜像。

```dockerfile
# syntax=docker/dockerfile:1

ARG NODE_VERSION=24

FROM node:${NODE_VERSION}-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM node:${NODE_VERSION}-alpine AS prod-deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM deps AS build
WORKDIR /app
COPY . .
RUN npm run build

FROM node:${NODE_VERSION}-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=prod-deps /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY --from=build /app/package.json ./
USER node
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "require('http').get('http://127.0.0.1:'+(process.env.PORT||3000)+'/healthz',r=>process.exit(r.statusCode===200?0:1)).on('error',()=>process.exit(1))"
CMD ["node", "dist/index.js"]
```

- ARG 写在 FROM 之前用于参数化基础镜像版本，进入阶段后若要读取需再声明一次同名 ARG。
- deps 与 prod-deps 各自独立，前者服务编译，后者服务运行，互不影响。
- build 用 FROM deps 直接继承依赖，避免重复安装。
- runtime 的三条 COPY --from 是镜像的全部内容来源，没有一条复制源码。

> [!TIP]
> **建议内容**：把 prod-deps 单独拆成一个阶段，比在 build 阶段装完全量依赖再 npm prune --omit=dev 更清晰，也更利于缓存：改源码不会让生产依赖层失效。两种写法都可用，选一种并在项目内统一。

**速记**：deps 装全量给编译用，prod-deps 装生产依赖给运行用，build 产产物，runtime 只带产物与生产依赖。



#### 逐阶段讲解与可复制文件

**逐阶段意图**：按出现顺序说明每个阶段为什么这样写，以及每一行留下的坑。

- syntax 指令：必须位于文件第一行，启用 heredoc 与 RUN --mount 等 BuildKit 前端语法。
- ARG NODE_VERSION=24：把基础镜像版本提成参数，便于 CI 里按版本矩阵切换，默认值固定在主版本。
- deps 阶段先 COPY 清单再 npm ci：清单不变则依赖层命中缓存，源码改动不会触发重装。
- RUN --mount=type=cache：把 npm 的下载缓存目录挂成跨构建复用的缓存，不写进镜像层。
- prod-deps 阶段 npm ci --omit=dev：只把生产依赖装进这一份 node_modules，供 runtime 使用。
- build 阶段从 deps 继承：拿到 node_modules 后再 COPY 源码并 npm run build。COPY 整个目录依赖 .dockerignore 兜底，否则会把宿主 node_modules 覆盖进来。
- runtime 阶段 ENV NODE_ENV=production：只在这一阶段设置，避免被 deps 与 build 继承后影响构建行为。
- COPY --from=prod-deps 与 COPY --from=build：分别取生产依赖与编译产物，是运行镜像的全部内容。
- USER node：复用官方镜像内置的非特权用户，切换身份后运行。
- HEALTHCHECK：周期探活，启动宽限期内失败不计入重试。
- CMD exec 形式：Node 直接作为主进程接收信号。

> [!CAUTION]
> **注意内容**：切勿在 base 或 deps 阶段写 ENV NODE_ENV=production。该变量一旦进入这些阶段，npm 的 omit 默认值会变成 dev，构建阶段所需的打包器、编译器都装不上，构建会以「找不到命令」失败；同时部分库在构建期也会走生产分支产生错误产物。

**速记**：清单先行、缓存挂载加速、生产依赖与产物分开取、只在运行阶段设 NODE_ENV。



#### 纯 JavaScript 与 TypeScript 两种形态

**两种形态**：没有构建步骤的纯 JavaScript 项目可以省掉 build 阶段，直接把源码目录复制进 runtime；TypeScript 或需要打包的项目必须保留 build 阶段。

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM node:24-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY --chown=node:node src ./src
COPY --chown=node:node public ./public
COPY --chown=node:node package.json ./
USER node
EXPOSE 3000
CMD ["node", "src/index.js"]
```

- 纯 JavaScript 项目：deps 直接装生产依赖，runtime 复制 src 与 public，入口指向源码文件。
- TypeScript 项目：保留 build 阶段，runtime 只复制 dist，不复制 src，也不带 tsc 与 ts-node。
- --chown=node:node 让复制进来的文件属主就是运行用户，省去后续 chown 多出一层。
- 编译产物若含 sourcemap，需要评估是否随镜像发布，它可能暴露源码路径与实现细节。

> TypeScript 项目里 typescript、ts-node、@types/node 都属 devDependencies，只在 build 阶段存在，运行镜像里既无编译器也无 .ts 文件，这正是多阶段在编译型项目上收益最大的原因。

**速记**：纯 JS 省掉 build，TS 必留 build；runtime 只复制产物，编译器留在构建阶段。



#### 镜像体积的对比思路

**对比方法**：不看绝对数字，只看「同一项目、同一提交、两种写法的镜像体积差」，并定位差在哪一层。

```bash
docker image ls --format '{{.Repository}}:{{.Tag}} {{.Size}}' node-app
docker history --no-trunc node-app:1.0
docker run --rm --entrypoint sh node-app:1.0 -c 'du -sh /app/* 2>/dev/null'
```

- 先构建朴素版并记下体积，再构建多阶段版并记下体积，两者相减即为这次拆分的收益。
- 差异的主要来源通常是基础镜像变体、devDependencies 与源码、编译工具链三项。
- 用 du 在运行镜像里量化各目录占用，能确认「少带的到底是什么」而不是只看总数。
- 实测差异以各自项目为准，依赖越多、构建链越重，收益越明显。

> 不要照搬他人文章里的体积数字。同一份 Dockerfile 在不同基础镜像、不同依赖规模下的结果差异极大；把「体积对比」当成一次自带基线的测量，而不是一个可以抄的结论。

**速记**：同项目两版对比，先记朴素版基线，再用 history 与 du 定位差在基础镜像、开发依赖还是工具链。



### 依赖安装的正确姿势

#### npm ci 与 npm install 的分工

**npm ci**：严格按 package-lock.json 还原依赖树的安装命令，会先删除现有 node_modules、不读取也不改写清单，适合确定性要求高的场合。

- npm ci 要求锁文件必须存在，锁文件与 package.json 不一致时直接报错退出，不会自行改锁。
- npm ci 每次先清空 node_modules 再装，结果只由锁文件决定，同一锁文件在任何机器上装出同一棵树。
- npm install 会按 package.json 的范围重新求解，可能更新锁文件，适合本地开发与增删依赖。
- 镜像构建、CI 与部署一律用 npm ci；本地开发用 npm install 更顺手。

```bash
npm ci
npm ci --omit=dev
npm install
```

> 锁文件必须提交进版本库，否则 npm ci 直接失败。参见 npm 与包管理中对锁文件与 ci 的完整说明。

**速记**：构建与 CI 用 npm ci 求确定性，本地开发用 npm install，锁文件不入库则 ci 无法运行。



#### 锁文件必须一起复制并提交

**一起复制**：package.json 与 package-lock.json 必须在同一条 COPY 中复制，二者是 npm ci 的完整输入，缺一不可。

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
```

- 只复制 package.json 会让 npm ci 因缺少锁文件而失败，退化成 npm install 又会丢掉确定性。
- 用 package*.json 通配符同样可行，但通配符必须能命中文件，否则 COPY 直接报错。
- 锁文件是文本且应提交进版本库，它是「应该装什么」的权威快照。
- node_modules/.package-lock.json 是 npm 自动维护的内部锁，无需提交也不该被复制。

> [!WARNING]
> **警告内容**：锁文件被 .gitignore 排除是极常见的团队事故。此时 CI 与镜像构建要么失败，要么静默回落到 npm install 装出与本地不同的版本，问题往往拖到线上才暴露。提交前确认锁文件确实在版本库里。

**速记**：清单与锁在同一条 COPY，锁文件必须提交，内部锁不复制。



#### 清单先复制以保住依赖层缓存

**缓存顺序**：先复制依赖清单并安装依赖，再复制源码，让源码改动不击穿依赖安装层的缓存。

```dockerfile
# 正例：清单与源码分两步
COPY package.json package-lock.json ./
RUN npm ci
COPY . .

# 反例：任何源码改动都让依赖重装
COPY . .
RUN npm ci
```

- 缓存按指令逐条比对，前一条指令的输入变了，其后所有层都要重算。
- 依赖清单变化频率低，单独 COPY 能让依赖层在多数提交上命中缓存。
- 源码 COPY 排在安装之后，改动源码只影响它及其后的少数层。
- 依赖越多、安装越慢，这条习惯省下的时间越多。

> COPY 的缓存判定基于匹配到的文件内容与元数据摘要，增删文件同样会让该层失效。一次 COPY 整个目录等于把全部源码绑在一层，任何改动都击穿依赖缓存。

**速记**：清单先、依赖中、源码后，一条 COPY 整个目录等于放弃依赖缓存。



#### 生产依赖裁剪与已废弃的 --production

**依赖裁剪**：用带类型的 omit 参数只装生产依赖，是运行镜像瘦身的直接手段；旧的 --production 写法已被官方标注为废弃。

- npm ci --omit=dev：跳过 devDependencies，同时保留 optional 与 peer 类依赖的默认处理。
- 官方 npm 配置文档把 --production 标注为 DEPRECATED，并写明它是 --omit=dev 的别名。
- omit 的默认值本身随环境变化：当 NODE_ENV 为 production 时默认为 dev，否则为空。
- 若 omit 后的列表包含 dev，npm 会把所有生命周期脚本的 NODE_ENV 设为 production。
- --include 与 --omit 是反向操作，同名同时出现时以 include 为准。

```bash
npm ci --omit=dev
npm ci --omit=dev --omit=optional
```

> 仍在用 npm ci --production 或 npm install --production 的项目应当改为 --omit=dev。当前写法会打印废弃告警，且官方已明示会在后续版本移除；omit 的默认值受 NODE_ENV 影响，显式写 --omit=dev 才不依赖环境。

**速记**：生产依赖用 npm ci --omit=dev，--production 是废弃别名，omit 默认值受 NODE_ENV 影响。



#### 用缓存挂载保留 npm 的下载缓存

**缓存挂载**：RUN --mount=type=cache 把 npm 的缓存目录挂成可跨构建复用的缓存，缓存内容不写进镜像层，只加速下载。

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev
```

- target 指向 npm 的缓存目录，默认用户为 root 时是 /root/.npm。
- 该目录只在执行这条 RUN 期间可读写，构建结束后不进镜像、不进层。
- 与层缓存不同，它缓存的是下载内容本身；指令缓存失效时下载仍可复用。
- 属 BuildKit 前端能力，需要顶部 syntax 指令或足够新的内置前端。

> 缓存挂载解决的是「下载慢」，不解决「清单变了要重装」。清单变化后依赖仍会重新解析安装，只是免去了重复联网下载。

> 私有 registry 需要凭据时，把 .npmrc 用密钥挂载临时提供，而不是复制进镜像：RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci。密钥只在这一次 RUN 期间存在，既不入层也不入缓存。

**速记**：缓存挂载挂 /root/.npm 加速下载，不落层；私有源凭据走密钥挂载。



### 以非 root 运行

#### node 镜像自带的 node 用户

**node 用户**：官方 Node 镜像内置一个名为 node、UID 为 1000 的非特权用户，可直接用 USER 指令复用，无需自己创建。

- 官方 docker-node 最佳实践文档明确说明，镜像中的 node 用户就是为以非特权身份运行而提供的。
- 该用户带同名用户组与主目录 /home/node，属主关系已配置好。
- 直接用 USER node 即可，跨项目写法一致，比自建用户更省心。
- 需要固定 UID 与宿主卷对齐权限时，可在构建期调整 UID 或自建用户。

```dockerfile
USER node
```

> 这个用户既不是构建期依赖也不是运行期依赖，可以被删除或改名；但如果应用不依赖它，直接复用是最省的方案。

**速记**：官方镜像自带 node 用户（UID 1000），优先直接 USER node。



#### USER node 与自建用户的取舍

**取舍标准**：能用镜像自带用户就复用，只有在需要特定 UID、特定用户名或特定主目录时才自建。

- 复用 node 用户：一行指令、跨项目一致、无需处理创建命令在 alpine 与 debian 上的差异。
- 自建用户：需要固定 UID 与宿主文件属主对齐，或需要专属主目录、专属 shell 时使用。
- alpine 用 addgroup 与 adduser，debian 用 groupadd 与 useradd，命令与参数差异明显。
- 自建后必须用 COPY --chown 或 RUN chown 授权，否则非 root 身份读不到应用目录。
- 固定 UID 能让挂载卷上的文件在宿主与容器两侧权限一致，是多环境协作的常见要求。

```dockerfile
# alpine 自建用户
RUN addgroup -S app && adduser -S -G app -u 1001 app
COPY --chown=app:app . /app
USER app
```

> 自建用户时，复制之后再逐目录 chown 会各产生一层。用 COPY --chown=用户:组 一步到位，既少一层也让属主关系在镜像里一眼可见。

**速记**：能复用就 USER node；要固定 UID 或专属主目录才自建，并配 COPY --chown 授权。



#### 文件属主与全局目录权限

**权限问题**：非 root 运行时，应用能写哪些目录由文件属主决定；镜像里复制进来的文件默认属主是 root，可能让运行用户无法写入。

- COPY 未指定 --chown 时，文件属主是 root，运行用户通常仍可读取，但不能写入。
- 应用需要写的目录应显式授权，例如日志目录、上传目录、缓存目录或 SQLite 数据文件目录。
- 需要全局安装 npm 包时，默认全局目录属主是 root，非 root 用户无法写入。
- 官方建议把全局安装前缀改到用户主目录下，用环境变量覆盖。

```dockerfile
ENV NPM_CONFIG_PREFIX=/home/node/.npm-global
ENV PATH=$PATH:/home/node/.npm-global/bin
```

```bash
docker run --rm node:24-alpine sh -c 'id node; ls -ld /home/node'
docker run --rm --user node node:24-alpine sh -c 'touch /app/x 2>&1 || true'
```

- NPM_CONFIG_PREFIX 把全局安装位置改到用户主目录，避免对 /usr/local 的写入需求。
- 用 --user node 临时验证：能在哪些目录写、哪些目录报权限不足，一次看清。
- 需要写入挂载卷时，宿主目录的属主 UID 要与容器运行用户一致，否则同样写不进去。

> [!CAUTION]
> **注意内容**：不要为了让应用能写而简单地把运行用户改回 root。更好的做法是把需要写的目录单独列出并授权给非特权用户，或改为挂载卷，让可写范围最小化。

**速记**：COPY 默认属主是 root，运行用户只读能行、写要授权；npm 全局目录改到用户主目录下。



#### 非 root 监听 1024 以下端口为何失败

**端口限制**：Linux 上绑定 1024 以下的特权端口需要 CAP_NET_BIND_SERVICE 能力，非 root 用户默认没有该能力，因此监听 80、443 会以权限错误失败。

- 现象是应用启动即报权限不足一类错误，容器退出，与端口映射是否写对无关。
- 常见触发场景是把应用端口直接设成 80，再以 USER node 运行。
- 最直接的解法是让应用监听 1024 以上的端口，如 3000、8080，再由宿主机端口映射对外暴露。
- 需要对外提供 80 时，把宿主 80 映射到容器 3000 即可，或交给反向代理统一监听。
- 另一种思路是给容器补授 CAP_NET_BIND_SERVICE 能力，牺牲一部分最小权限原则。

```bash
# 宿主 80 映射到容器 3000，应用只需监听非特权端口
docker run -d --name node-app -p 80:3000 node-app:1.0
```

> [!TIP]
> **建议内容**：让应用只监听非特权端口，把「监听 80 与 443」交给唯一的反向代理，是本系列一贯的分层做法。这样应用容器可以稳定以非 root 运行，端口对外的工作交给代理，扩容与证书管理也更集中。参见 Docker 与 Nginx 反向代理实战。

**速记**：非 root 不能绑 1024 以下端口，应用监听 3000 一类端口，由映射或代理对外提供 80。



### 进程与信号

#### 容器内 Node 作为 PID 1 的行为

**PID 1 特殊性**：容器的主进程就是 PID 1，它既承担常规进程职责，也承担 init 的收尾职责，而 Node 并非为这一角色设计。

- 官方 docker-node 最佳实践文档的原话是：Node.js 未按 PID 1 设计，作为 PID 1 运行时会出现不符合预期的行为，例如不响应 SIGINT 一类信号。
- PID 1 还负责回收孤儿进程，普通应用进程不会做这件事，长期运行可能积累僵尸进程。
- 信号语义也与常规进程不同：内核会把没有处理函数的信号对 PID 1 特殊对待。
- Node 在非 Windows 平台为 SIGTERM 与 SIGINT 装了默认处理器，以退出码 128 加信号编号退出；一旦应用自己注册了监听器，这个默认行为即被移除。

```bash
docker run --rm --entrypoint sh node:24-alpine -c 'echo pid=$$; node -e "console.log(process.pid)"'
```

> Node 官方进程文档还指出：信号事件是异步发出的，当事件循环已经为空时，Node 可能在监听器被调用之前就退出。因此优雅退出的监听必须在进程仍在正常服务时就已经注册好。

**速记**：Node 不是为 PID 1 设计，官方明确其行为不符预期；PID 1 还要负责回收孤儿进程。



#### 为什么必须显式监听 SIGTERM

**显式监听**：只有在应用里注册了 SIGTERM 处理函数，才能保证收到停止信号时执行优雅退出，否则进程会直接消失或拖到被强杀。

- docker stop 默认发送 STOPSIGNAL 指定的信号，通常是 SIGTERM，等待宽限期后若进程仍未退出，补发 SIGKILL。
- 宽限期默认值由守护进程决定，Linux 容器为 10 秒，可用 docker stop 的 -t 参数或容器的 --stop-timeout 调整。
- 应用收到 SIGTERM 后应停止接收新连接、处理完存量请求、关闭数据库与缓存连接，再以 0 退出。
- 若注册了监听器却忘记调用 process.exit，Node 不会退出，因为默认退出行为已被移除，只能等 SIGKILL 强杀。
- SIGKILL 不能安装监听器，任何平台都会无条件终止进程。
- 退出码可反推终止方式：143 表示已被 SIGTERM 正常处理，137 表示被 SIGKILL 强杀。

```bash
docker stop node-app
docker stop -t 30 node-app
docker kill --signal=SIGTERM node-app
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' node-app
```

> [!IMPORTANT]
> **重要内容**：业务侧必须自己实现优雅退出，Docker 只负责发信号与兜底强杀。把「停止时不丢请求、不丢数据」建立在应用主动处理 SIGTERM 上，而不是建立在宽限期足够长这一侥幸上。

**速记**：docker stop 先发 SIGTERM、宽限 10 秒后补 SIGKILL；应用必须显式监听并主动退出，143 是正常、137 是强杀。



#### 解法一：应用内注册信号处理函数

**应用内处理**：在启动服务的同一处注册 SIGTERM 与 SIGINT 处理函数，关闭服务器与外部连接后退出，并设置超时兜底。

```js
import http from "node:http";

const port = Number(process.env.PORT) || 3000;
const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ status: "ok" }));
});

server.listen(port, "0.0.0.0", () => {
  console.log(`listening on ${port}`);
});

let shuttingDown = false;
function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`received ${signal}, shutting down`);

  server.close(() => {
    console.log("server closed");
    process.exit(0);
  });

  setTimeout(() => {
    console.error("graceful shutdown timed out, forcing exit");
    process.exit(1);
  }, 10000).unref();
}

process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));
```

- server.close 只停止接收新连接，不会断开已建立的连接，因此需要超时兜底避免长连接拖住退出。
- 支持 closeAllConnections 的 Node 版本可主动断开存量连接，配合 close 使用更彻底。
- 超时定时器上用 unref，避免它本身把事件循环留住。
- 用 shuttingDown 标志防止多个信号重复触发同一套收尾逻辑。

> [!WARNING]
> **警告内容**：只监听不退出是不完整的优雅退出。注册了 SIGTERM 监听器后，Node 的默认退出行为被移除，若处理函数里没有走到 process.exit，进程会一直挂着，最终被 SIGKILL 强杀，退出码变成 137，优雅退出彻底落空。

**速记**：收信号后停收新连接、关外部连接、超时兜底，最终显式 process.exit。



#### 解法二：用 --init 引入轻量 init 进程

**init 进程**：在容器里额外起一个极小的 init 作为 PID 1，由它转发信号并回收僵尸进程，应用进程退居其后。

- docker run --init 让守护进程注入 docker-init（由 tini 提供）作为 PID 1，是最省事的开启方式。
- Compose 里用服务级 init 为 true 达到同样效果。
- 也可以把 tini、catatonit、dumb-init 直接装进镜像，用 ENTRYPOINT 或 CMD 包住应用命令。
- init 只解决信号转发与僵尸回收，不代替应用实现优雅退出，应用仍要处理 SIGTERM。

```dockerfile
# 在镜像内自带 init：以 dumb-init 包住 node
CMD ["dumb-init", "node", "dist/index.js"]
```

```yaml
services:
  app:
    build: .
    init: true
    ports:
      - "3000:3000"
```

```bash
docker run -d --init --name node-app -p 3000:3000 node-app:1.0
```

> 官方 docker-node 最佳实践文档给出的多阶段示例就是：构建阶段用 node 镜像，运行阶段换成精简基础镜像并在 CMD 里用 dumb-init 启动 node，理由正是「Node.js 未按 PID 1 设计」。精简基础镜像的取舍参见镜像构建最佳实践与多阶段构建。

**速记**：--init 或 compose 的 init 为 true 引入 tini 作 PID 1，转发信号并回收僵尸；优雅退出仍靠应用自己。



### 健康检查与就绪

#### 不依赖 curl 的探针写法

**无 curl 探针**：精简镜像往往没有 curl，探针应改用镜像内一定存在的运行时自带能力，Node 用 node -e 发起一次 HTTP 请求即可。

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD node -e "require('http').get('http://127.0.0.1:'+(process.env.PORT||3000)+'/healthz',r=>process.exit(r.statusCode===200?0:1)).on('error',()=>process.exit(1))"
```

- node -e 用内置的 http 模块发一次请求，只依赖 Node 运行时本身，alpine 与 slim 变体都能用。
- 退出码 0 表示健康、非 0 表示不健康，这是 HEALTHCHECK 的约定。
- 探针请求 127.0.0.1 是容器自己，不是宿主；探测的是应用在当前容器内是否可应答。
- 用 Node 内置的 fetch 也可以，写法更短，但要求运行时具备该全局对象。
- Compose 里用 CMD 或 CMD-SHELL 形式写等价命令，语义与镜像 HEALTHCHECK 一致。

```yaml
healthcheck:
  test: ["CMD", "node", "-e", "require('http').get('http://127.0.0.1:3000/healthz',r=>process.exit(r.statusCode===200?0:1)).on('error',()=>process.exit(1))"]
  interval: 30s
  timeout: 3s
  retries: 3
  start_period: 10s
```

> 探针命令的引号层级容易写错。CMD 列表形式下每个参数原样传递，node -e 的脚本整体作为一个参数，内部引号按 JavaScript 规则书写即可，不要再套一层 shell 转义。

**速记**：用 node -e 加内置 http 做探针，不依赖 curl，退出码 0 为健康。



#### 存活探针与就绪探针的分工

**两类探针**：存活探针回答「要不要重启这个实例」，就绪探针回答「要不要把流量给它」，二者用途不同，不能用同一个端点草率代替。

- 存活探针：只检查进程本身是否还能工作，通常是极轻量的固定响应，失败意味着需要重启。
- 就绪探针：检查应用能否真正服务请求，必要时包含对数据库、缓存的连通性判断，失败意味着暂时摘掉流量。
- 就绪检查若把下游依赖算进去，会在数据库抖动时让所有副本一起被判为不就绪，放大故障面。
- 容器层面的 HEALTHCHECK 只有一档状态，实践中常把就绪逻辑放在应用端点内部，用状态码区分自身可用与依赖降级。
- 区分两者的意义在于：不该因为下游短暂不可用就重启一个本身健康的实例。

```js
// 存活：只证明进程可应答
app.get("/healthz", (req, res) => {
  res.status(200).json({ status: "ok", uptime: process.uptime() });
});

// 就绪：真实检查下游依赖
app.get("/readyz", async (req, res) => {
  try {
    await db.query("SELECT 1");
    await cache.ping();
    res.status(200).json({ status: "ready" });
  } catch (err) {
    res.status(503).json({ status: "degraded" });
  }
});
```

> [!IMPORTANT]
> **重要内容**：探针要轻、要快、不写数据、不做昂贵查询，否则健康检查本身会成为负载来源。就绪检查的粒度按业务容忍度决定，把「自身可用」与「依赖降级」分清，是避免雪崩式重启的前提。

**速记**：存活管重启、就绪管流量；就绪可含依赖检查但别过重，存活保持极轻。



#### 由健康检查驱动的依赖等待

**依赖等待**：Compose 的启动顺序由依赖条件决定，配合被依赖服务的健康检查，才能保证应用启动时数据库与缓存真的可用。

- depends_on 短语法只保证被依赖容器已启动，不等待其进入健康状态。
- 长语法用 condition 指定门槛：service_healthy 看健康检查，service_completed_successfully 看退出码为 0。
- 被依赖服务必须定义 healthcheck，否则 service_healthy 没有判定依据，启动会卡住并报错。
- 编排层的等待只覆盖启动这一次，运行期的依赖抖动仍要靠应用内的连接重试兜底。
- 应用启动阶段也应做有限次重试与退避，把「必然失败的启动」降为「可自愈的等待」。

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
```

> 编排管的是启动顺序，应用管的是运行期韧性，二者叠加而非互相替代。依赖条件的完整语义参见 Docker Compose 进阶与实战。

**速记**：started 看进程、healthy 看检查、completed_successfully 看退出码；启动靠编排、运行靠重试。



### 生产模式与运行时配置

#### NODE_ENV 设置在哪里

**NODE_ENV**：社区约定的运行环境标识，取值通常是 production、development、test，Node 本身不强制，但大量框架与库据此切换行为。

- Express 一类框架在 production 下启用视图缓存、精简错误响应与内部优化。
- npm 的 omit 默认值受它影响：为 production 时默认跳过 devDependencies。
- 设置在 Dockerfile 的 ENV 会写进镜像，同一镜像无法再当开发镜像用；设置在运行时的 environment 更灵活。
- 只把它当作「运行模式开关」，不要用它承载密钥或环境专属参数。
- 部署时确需固定为生产镜像时可在运行阶段写 ENV，但仍建议用运行时注入以便同一镜像复用于预发。

```dockerfile
# 只在运行阶段设置，避免影响构建阶段的依赖安装
FROM node:24-alpine AS runtime
ENV NODE_ENV=production
```

> [!CAUTION]
> **注意内容**：NODE_ENV 写进基础阶段会连锁影响构建：它会让 npm 的 omit 默认变成 dev，构建工具装不上，构建失败或产物异常。只在真正的运行阶段设置它，并且显式写 --omit=dev 让意图不依赖默认值。

**速记**：NODE_ENV 切换框架行为也影响 omit 默认值；只在运行阶段设置，别写进基础阶段。



#### 运行时配置全部走环境变量

**配置外置**：端口、数据库地址、缓存地址、外部服务 URL、日志级别等一切随环境变化的取值，都从环境变量读入，镜像本身不写死。

```js
const config = {
  port: Number(process.env.PORT) || 3000,
  databaseUrl: process.env.DATABASE_URL,
  redisUrl: process.env.REDIS_URL,
  logLevel: process.env.LOG_LEVEL || "info",
};

if (!config.databaseUrl) {
  console.error("missing required config: DATABASE_URL");
  process.exit(1);
}
```

- 读取时给安全默认值或对缺失项快速失败，让配置错误在启动时就暴露。
- 环境变量的值一律是字符串，端口与数量要自行做类型转换。
- 敏感取值走环境变量只是权宜，它可被 docker inspect 与容器内进程读到，应改用密钥机制。
- 同一镜像配不同变量即可在开发、预发、生产复用，无需为每个环境各打一版镜像。

> [!WARNING]
> **警告内容**：把数据库口令写进环境变量等于向「能访问守护进程或能进入容器」的人公开明文，docker inspect 的 Config.Env 一把就能看到。密钥应走 secrets 或外部密钥服务，环境变量只承载非敏感配置。机制详见环境变量、配置注入与密钥管理。

**速记**：配置全部走环境变量、缺失即快速失败；镜像跨环境复用，密钥另走 secrets。



#### 时区与 locale 的显式设置

**显式固定**：镜像内的时区与字符环境不能依赖宿主默认，应显式声明，否则日志时间错乱、字符处理随构建机变化。

```dockerfile
ENV TZ=UTC
ENV LANG=C.UTF-8
```

- TZ 固定为 UTC，日志时间戳在开发机、CI 与线上保持一致，排查时不必做时区换算。
- 需要展示本地时间时在应用层转换，而不是改容器时区。
- LANG 与 LC_ALL 影响排序、大小写转换与字符编码，显式写 C.UTF-8 可避免随宿主漂移。
- alpine 变体默认不含完整时区库，若必须使用某个具名时区，需要额外安装 tzdata，否则时区设置不生效。
- 时区与 locale 也影响构建产物，多阶段构建下应在运行阶段显式声明。

> 日志统一用 UTC 并不意味着只能看到 UTC。约定「存储与传输用 UTC、展示层按用户时区转换」，既保证可比性，又不牺牲可读性。

**速记**：TZ=UTC、LANG=C.UTF-8 显式声明；alpine 用非 UTC 时区需装 tzdata，展示层再转本地时间。



#### 内存上限与 Node 堆大小的配合

**堆与容器内存**：Node 的老生代堆上限默认按宿主机内存推算，不感知容器限制，因此必须用 --max-old-space-size 显式压到容器内存之下并留出堆外余量。

- 容器内读 /proc/meminfo 得到的是宿主总量，Node 据此推算的堆上限会远超容器配额。
- 用 NODE_OPTIONS 设置，通用于任何启动方式：ENV NODE_OPTIONS=--max-old-space-size=384。
- 或直接写进启动命令：node --max-old-space-size=384 dist/index.js。
- 上限要明显小于容器内存限制，因为堆外还有 Buffer、代码段、线程栈与运行时结构。
- 触到容器内存上限时进程会被内核杀死，退出码 137 且 OOMKilled 为 true。

```dockerfile
# 容器内存限制 512M 时，给堆留 384M，其余留给堆外内存
ENV NODE_OPTIONS=--max-old-space-size=384
```

```bash
docker inspect -f '{{.HostConfig.Memory}}' node-app
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' node-app
docker exec node-app node -e "console.log(process.memoryUsage())"
```

> [!WARNING]
> **警告内容**：把堆上限设得比容器内存还大，是内存被杀的高频根因。应用以为还能继续增长，直到触到 cgroup 上限被内核直接杀掉，容器反复重启却看不到明显的应用报错。堆上限与容器内存要按「堆加堆外小于限制」留出余量，参数取值方法参见容器资源限制与运行时约束。

**速记**：Node 堆默认不感知容器，用 NODE_OPTIONS 设 --max-old-space-size；堆加堆外要小于容器内存，137 与 OOMKilled 是越限信号。



### 开发态与生产态两套运行方式

#### 用 override 文件承载环境差异

**环境差异**：把与环境无关的服务、网络、卷声明放进基础文件，把开发与生产各自的差异放进覆盖文件，用 -f 按序叠加。

- compose.yaml 只写共有部分：服务定义、依赖链、网络与卷。
- compose.dev.yaml 打开源码绑定挂载、调试端口与热重载命令，启用调试 profile。
- compose.prod.yaml 固定镜像标签或 digest、去掉源码挂载、收紧资源与重启策略。
- 未用 -f 指定时，Compose 会自动加载同目录的 compose.override.yaml 并在基础文件之上叠加。
- 改完文件先跑 docker compose config 看最终结果，避免覆盖关系与预期不符。

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml config
```

> compose.override.yaml 的「隐身生效」是配置错乱的常见源头——基础文件写的是生产端口，实际却连到开发端口。怀疑合并结果不符预期时，第一动作是看 config 的输出，而不是逐个容器猜。

**速记**：基础文件管共有，dev 与 prod 覆盖管差异，命令用 -f 叠加，改完先看 config。



#### 开发态挂源码与热重载

**开发态挂载**：把源码目录绑定挂载进容器，配合 nodemon 一类监视工具，改文件即重启，无需重建镜像。

- 开发用镜像要比生产镜像多装 devDependencies，提供一个保留了开发依赖的 dev 阶段。
- 挂载粒度以源码目录为准，例如把 ./src 挂到 /app/src，不挂整个项目目录。
- 用 nodemon 或 node --watch 监视文件变化并重启，前者需装在 devDependencies 里。
- 某些宿主文件系统下文件事件不可靠，nodemon 可用 --legacy-watch 改用轮询。
- 依赖清单或 Dockerfile 改动仍需重建镜像，挂载只解决源码改动。

```dockerfile
# 供开发态使用的阶段，保留 devDependencies
FROM node:24-alpine AS dev
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ENV NODE_ENV=development
CMD ["npx", "nodemon", "--legacy-watch", "src/index.js"]
```

```yaml
services:
  app:
    build:
      context: .
      target: dev
    command: ["npx", "nodemon", "--legacy-watch", "src/index.js"]
    volumes:
      - ./src:/app/src
      - /app/node_modules
    environment:
      NODE_ENV: development
      LOG_LEVEL: debug
    ports:
      - "3000:3000"
```

> 热重载改变的是「源码如何进入容器」；生产态则相反，源码在构建时就固化进不可变镜像，运行期不挂任何源码。

**速记**：开发镜像保留 devDependencies，挂源码目录加 nodemon 热重载，改依赖仍要重建。



#### 为什么不能把 node_modules 挂进去

**不挂依赖目录**：宿主上的 node_modules 与容器内的依赖在平台、libc 与二进制格式上都可能不同，把它挂进容器会让应用因模块加载失败而崩溃。

- 原生模块（node-gyp 编译出的 .node 文件）绑定具体平台与 libc，macOS 上装的二进制在 Linux 容器里无法加载。
- 即使同为 Linux，glibc 与 musl（alpine）编译出的原生模块也不能互换。
- 宿主依赖目录可能为空或版本与容器不一致，挂进去会覆盖容器内正确的依赖。
- 经典做法是用匿名卷把容器内的依赖目录屏蔽掉，让宿主目录不被挂载覆盖。
- 匿名卷只声明挂载点而不指定宿主路径，容器内该目录保持镜像里的内容。

```yaml
services:
  app:
    volumes:
      - ./src:/app/src      # 挂源码
      - /app/node_modules   # 匿名卷：屏蔽宿主的同路径目录
```

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
docker compose exec app sh -c 'ls /app/node_modules | head'
```

> [!WARNING]
> **警告内容**：把宿主 node_modules 挂进容器（或从宿主拷进镜像）是跨平台部署的高频事故。它常在「本地是 macOS、镜像是 alpine」的组合下以「找不到模块」「invalid ELF header」的形式爆发，却把你引向排查代码而非排查依赖来源。依赖一律在构建阶段于容器内安装。

**速记**：宿主 node_modules 与容器不兼容；挂源码后必须用匿名卷屏蔽 /app/node_modules，依赖只在容器内装。



#### 生产态用构建好的不可变镜像

**不可变镜像**：生产态不挂源码、不依赖宿主文件，运行的就是构建阶段产出的那一份镜像，同一标签或 digest 对应的内容不再变化。

- 生产覆盖文件里去掉所有源码绑定挂载，只保留必要的配置或数据卷。
- 镜像标签用具体版本或 digest，不用 latest，保证可回滚、可追溯。
- 运行阶段以非 root 启动，带健康检查与日志轮转策略。
- 配置通过环境变量或挂载配置文件注入，绝不写进镜像。
- 需要初始化或迁移时用一次性任务服务复用同一镜像，而不是在启动脚本里做。

```yaml
services:
  app:
    image: registry.example.com/node-app:1.4.2
    init: true
    environment:
      NODE_ENV: production
      PORT: "3000"
    ports:
      - "3000:3000"
    restart: unless-stopped
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

> 开发态追求「改完立刻看到」，生产态追求「看到的即已发布」。两套方式共用同一个 Dockerfile 的不同阶段，共用同一份业务代码，差异只体现在挂载、命令与资源约束上。

**速记**：生产不挂源码、只跑不可变镜像，固定版本标签、非 root、带探活与日志轮转。



### 编排一个完整应用

#### 拓扑、依赖链与端口

**拓扑**：一个对外端口，三个常驻服务与一个一次性任务，网络、卷与依赖链各就各位。

- app：Node 应用，唯一的对外入口，发布宿主端口 3000 到容器 3000。
- db：PostgreSQL，数据落命名卷，暴露 healthcheck 供依赖条件消费。
- cache：Redis，数据落命名卷，同样暴露 healthcheck。
- migrate：与应用同镜像，command 覆盖为迁移脚本，跑完即退，restart 为 no。
- 依赖链：migrate 等 db 健康，app 等 db 与 cache 健康并且 migrate 成功完成。
- 网络：四个服务接同一自定义网络，服务之间用服务名互通，只有 app 发布端口。
- 环境变量：非敏感项经 env_file 注入，连接串在 environment 中给出，敏感口令真实环境应改走密钥。

> 只暴露一个端口的价值在于：应用不必处理 TLS 与多入口，端口对外的工作可以收拢到唯一入口或反向代理，应用自身只在内部网络提供明文 HTTP。数据库与缓存的独立部署细节参见 Docker 部署 MySQL 与 Redis 实战。

**速记**：一个对外端口、两个命名卷、三段依赖链，migrate 跑完即退、app 等三方就绪。



#### compose.yaml 全文

```yaml
name: node-app

services:
  app:
    build:
      context: .
      target: runtime
    init: true
    env_file:
      - ./.env
    environment:
      NODE_ENV: production
      PORT: "3000"
      DATABASE_URL: postgres://app:secret@db:5432/appdb
      REDIS_URL: redis://cache:6379
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    healthcheck:
      test: ["CMD", "node", "-e", "require('http').get('http://127.0.0.1:3000/healthz',r=>process.exit(r.statusCode===200?0:1)).on('error',()=>process.exit(1))"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 15s
    networks:
      - backend
    restart: unless-stopped

  migrate:
    build:
      context: .
      target: runtime
    command: ["node", "dist/scripts/migrate.js"]
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/appdb
    restart: "no"
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    networks:
      - backend
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - cache-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    networks:
      - backend
    restart: unless-stopped

volumes:
  db-data:
  cache-data:

networks:
  backend:
```

> 示例中的数据库口令是明文占位值。真实项目应把口令抽到环境变量文件或密钥机制，并确保其不进入版本库；数据库与缓存也不应接入对外网络。

**速记**：app 唯一对外并带 init 与探活，migrate 跑完即退，db 与 cache 各挂命名卷，共用一个后端网络。



#### 逐段讲解

**逐段要点**：从项目名到顶层卷与网络，每一段都对应启动链条上的一个环节。

- name：固定项目名，容器名前缀、网络与卷的归属都以此为准，便于多处引用同一份环境。
- app 的 build：用 context 指定项目目录，target 指定只构建到 runtime 阶段，不产出带工具链的中间镜像。
- app 的 init 为 true：注入轻量 init 作为 PID 1，转发信号并回收僵尸，应用内的优雅退出仍然保留。
- app 的 healthcheck：用 node -e 探测 /healthz，不依赖 curl，与镜像内的 HEALTHCHECK 同语义。
- app 的 depends_on：三种条件各司其职，db 与 cache 看健康，migrate 看退出码。
- migrate：与应用同镜像，command 覆盖为迁移脚本，restart 为 no，跑完即退；必须写成幂等脚本。
- db 与 cache：各挂命名卷保存数据，健康检查分别用 pg_isready 与 redis-cli ping。
- 顶层 volumes 与 networks：显式声明命名卷与自定义网络，避免依赖隐式默认。
- 日志与重启：restart 用 unless-stopped，单容器日志轮转在守护进程或容器级统一设置，避免无上限增长写满磁盘。

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=50 app
docker compose run --rm migrate
```

- config --quiet 先校验语法、插值、合并与路径，再动手启动。
- up -d --build 在启动前构建带 build 段的服务，后台运行。
- ps 看各服务状态，app 应显示 healthy，migrate 应显示 Exited (0)。
- run --rm migrate 用于迁移失败或需要重跑时单独执行，不牵动其余服务。

> 首次启动用 docker compose up -d --wait 让命令等到服务进入健康状态再返回，脚本据此判断「环境真的可用了」而不是「容器已创建」。CI 与自动化脚本里，等健康比等创建更可靠。

**速记**：命名与依赖条件串起链条、init 与探针齐备；启动后看 ps 与 logs，迁移用 run 重跑。



#### 从零跑起来与验证

**验证闭环**：从配置校验、构建启动，到接口验证、日志确认与优雅停止，走完一遍才算部署成功。

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
```

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:3000/healthz
curl -sS http://127.0.0.1:3000/readyz
docker compose exec app node -e "console.log(process.env.NODE_ENV)"
docker compose exec app sh -c 'cat /sys/fs/cgroup/memory.max 2>/dev/null || true'
```

- healthz 返回 200 说明进程可应答；readyz 返回 200 说明数据库与缓存都连通。
- exec 进容器读 NODE_ENV，确认运行模式确实生效。
- 读容器内的内存上限文件，核对资源限制是否真的落到容器上。
- 停止时观察日志，应看到优雅退出的收尾输出，而不是被直接强杀。

```bash
docker compose stop
docker compose down
docker compose down -v
docker inspect -f '{{.State.ExitCode}}' node-app-app-1
```

> [!CAUTION]
> **注意内容**：down -v 会连同命名卷一起删除，数据库与缓存中的持久化数据不可恢复。日常重启只用 stop 或 down；只有在确认数据可弃或已有备份时才加 -v，误加的代价是不可逆的数据丢失。

**速记**：config 校验、up 构建启动、curl 验接口、exec 验配置；停止看优雅退出，down -v 是删数据。



### 上线前的检查清单与常见坑

#### 镜像内容自查命令

**自查命令**：上线前用几条命令把镜像摊开看一遍，确认没有多带源码、开发依赖与密钥。

```bash
docker image ls --format '{{.Repository}}:{{.Tag}} {{.Size}}' node-app
docker history --no-trunc node-app:1.0
docker run --rm --entrypoint sh node-app:1.0 -c 'ls -la /app; du -sh /app/*'
docker inspect -f '{{.Config.User}} {{.Config.WorkingDir}}' node-app:1.0
docker inspect -f '{{.Config.Healthcheck}}' node-app:1.0
docker run --rm --entrypoint sh node-app:1.0 -c 'ls /app/test 2>/dev/null || echo "no test dir"'
```

- image ls 与 history 看体积与每层的构成，找出体积贡献最大的指令。
- ls 与 du 直接确认运行镜像里有没有 src、test、dist 之外的多余内容。
- Config.User 非空才说明降了权，为 root 或空即未降权。
- Config.Healthcheck 为空说明没有探活，只能靠进程存活判断。
- 用 history 与分层扫描核对是否残留密钥，参见环境变量、配置注入与密钥管理中的自查命令。

> [!WARNING]
> **警告内容**：镜像里一旦残留过密钥，删除文件并不能消除它——底层历史仍可还原。若自查发现密钥曾进过层，必须立即作废并轮换该密钥，再重建镜像，顺序不可颠倒。

**速记**：看体积、看 history、看 /app 内容、看 User 与 Healthcheck，五条命令过一遍再上线。



#### 非 root、健康检查、日志三条硬线

**三条硬线**：以非 root 运行、有健康检查、日志只写标准输出，是任何 Node 容器上线前不必讨论的底线。

- 非 root：Dockerfile 里写 USER node 或自建用户，用 inspect 确认 Config.User 非空。
- 健康检查：在镜像或 Compose 里定义探针，探针要真实反映可用性，不要只检查进程存在。
- 日志标准输出：应用只写 stdout 与 stderr，交给日志驱动与平台收集，不自己写文件、不做应用内轮转。
- 三条缺一都会在生产排障时付出代价：无降权是安全债，无探活是可用性债，日志进文件是排障债。
- 日志轮转参数在守护进程或容器级配置，避免单个容器日志无上限增长把磁盘写满。

```bash
docker inspect -f '{{.Config.User}}' node-app:1.0
docker inspect -f '{{.State.Health.Status}}' node-app-app-1
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}' node-app-app-1
docker logs --tail=20 node-app-app-1
```

> 日志写在容器可写层会读不到、留不住、搬不走、聚不齐，容器删除即随可写层消失。日志链路的完整机制与轮转写法参见容器日志与监控。

**速记**：非 root、有探活、日志走标准输出，三条硬线任一缺失都不算可上线。



#### 环境变量与构建缓存的坑

**两类坑**：环境变量的可见性坑与构建缓存的跨平台坑，二者都不报错，只在特定时机暴露。

- 环境变量可被 docker inspect 的 Config.Env 与容器内 /proc/1/environ 读到，不是保密机制。
- 用 --env VAR 只写变量名时会从执行命令的 shell 继承，同一命令在不同机器注入不同结果且失败是静默的。
- 构建缓存与构建平台绑定：在 arm64 开发机与 amd64 服务器上构建同一项目，缓存不通用，且原生模块产物架构不同。
- 基础镜像标签漂移会让缓存命中却底层已换，需要时用 --pull 重新拉基础镜像。
- 缓存挂载与层缓存是两套机制，前者只加速下载，后者决定是否重跑指令。

```bash
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' node-app-app-1
docker exec node-app-app-1 cat /proc/1/environ | tr '\0' '\n'
docker build --pull -t node-app:1.0 .
docker buildx build --platform linux/amd64,linux/arm64 -t repo/node-app:1.0 --push .
```

> 跨平台团队应约定构建发生的位置与架构，或统一用 buildx 产出多平台镜像，避免「开发机构建的镜像在服务器上能跑、CI 构建的却崩」这类因缓存与架构不一致引发的问题。

**速记**：环境变量对 inspect 与 proc 可见不算保密；构建缓存绑定平台与基础镜像，跨架构要统一用 buildx。



#### 原生模块与跨平台共享的禁忌

**原生模块**：含 node-gyp 编译步骤的依赖会产出平台相关的二进制，必须在与运行镜像相同的基础镜像内编译，并且绝不跨平台共享 node_modules。

- node-gyp 需要 python、make 与 C++ 编译器，精简基础镜像默认不含，需在构建阶段补齐。
- alpine 用 apk 装 python3、make、g++；debian 用 apt 装 python3、make 与 build-essential。
- 构建工具只应存在于构建阶段，多阶段构建让它们不进运行镜像。
- 编译阶段与运行阶段必须用同一类基础镜像：alpine 编译的产物不能拿到 debian 上跑，反之亦然。
- 绝不要把宿主或另一平台的 node_modules 复制进镜像或挂进容器，见上文「为什么不能把 node_modules 挂进去」。

```dockerfile
# 构建阶段补齐原生模块工具链并编译，运行阶段不带这些工具
FROM node:24-alpine AS build
WORKDIR /app
RUN apk add --no-cache --virtual .gyp python3 make g++
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build
```

```bash
docker buildx build --platform linux/amd64 -t repo/node-app:1.0 --push .
docker run --rm repo/node-app:1.0 node -e "require('bcrypt'); console.log('native ok')"
```

> [!CAUTION]
> **注意内容**：在 macOS 上 npm install 后把 node_modules 拷进 Linux 镜像，或把 arm64 开发机上装好的依赖推到 amd64 服务器运行，都会以「找不到模块」「invalid ELF header」一类错误失败。依赖只在目标平台的基础镜像内安装，这是跨平台部署不可越过的红线。

**速记**：原生模块要在同一基础镜像内编译，构建工具留在构建阶段；node_modules 永不跨平台共享。
