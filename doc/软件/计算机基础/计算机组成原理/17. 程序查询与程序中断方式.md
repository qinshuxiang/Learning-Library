## 程序查询与程序中断方式

> **全章主脉**：程序查询和程序中断都是"CPU 介入数据传送"的控制方式，但介入方式截然不同——查询靠 CPU 主动轮询设备、设备就绪才传一个数据，简单却让 CPU 空等；中断让 CPU 发完命令就干别的、设备就绪主动来"敲门"，CPU 响应后短暂处理再回来。本章先讲查询方式，再重点讲**中断**的概念、请求判优、响应与服务流程、多重中断与屏蔽。
>
> **一句话记中断流程**：设备请求 → 判优排队 → CPU 在当前指令执行完响应（关中断、保存断点、转中断服务程序）→ 保护现场、服务、恢复现场 → 开中断返回断点继续。

### 程序查询方式

#### 查询流程

**程序查询方式**由 CPU 用程序反复查询设备是否就绪，就绪后才进行一个数据的输入或输出，直到数据传完。

**查询式输入/输出流程**：

- CPU 向设备发出启动/读命令。
- CPU 循环读取接口状态寄存器，查询设备是否"就绪"。
- 若未就绪则继续查询等待（CPU 空转）。
- 若就绪，则从接口数据寄存器取一个数据（输入）或向接口送一个数据（输出）。
- 处理完当前数据后，继续下一个数据的查询，直至整批数据传完。

**查询方式的特点**：

- 优点：控制逻辑简单，无需中断硬件，易实现。
- 缺点：CPU 要不断查询等待，查询期间不能做别的事，CPU 利用率低；且要等设备就绪，速度受设备拖累。

> [!NOTE]
> 提醒内容：程序查询的本质是"CPU 忙等设备"，串行地处理一个个数据，中间还伴随地址译码与状态判断开销，故整机效率低。它只适合少量、低速、实时要求不高的场合。CPU 利用率、能否处理突发与设备数量是判断用何种控制方式的关键。



#### 接口电路

**查询方式的接口电路**为 CPU 提供"查询状态、读/写数据"的端口，是查询得以进行的基础。

查询式接口中的主要组成：

- **状态寄存器（状态端口）**：保存设备是否"就绪/忙"等状态，供 CPU 读取判断。
- **数据寄存器（数据端口）**：暂存待输入或待输出的数据。
- **命令寄存器（命令端口）**：接收 CPU 的启动、读、写等命令。
- **地址译码与选中逻辑**：识别本接口地址，使 CPU 能对相应端口操作。

**查询的工作依托**：CPU 先读状态端口判断就绪，就绪后经数据端口传数——这正是查询流程在电路层面的落点。

> [!TIP]
> 建议内容：接口通常暴露"命令、状态、数据"三类寄存器（端口）。查询方式里 CPU 反复读状态端口、就绪后经数据端口搬运；理解"状态端口决定何时传、数据端口承担传送"即可，查询方式本身不涉及中断硬件的判优与响应。



### 程序中断方式

#### 中断的概念与分类

**程序中断**指 CPU 正在执行程序时，因内部或外部原因暂停当前程序，转去执行处理相应事件的中断服务程序，处理完再返回原程序继续执行。

**中断的分类**（按引起原因与来源）：

- **内中断（异常/例外）**：由 CPU 内部执行指令引起，与当前指令相关，如整除错、溢出、非法指令、缺页、系统调用（访管指令）。又分故障、陷阱与终止。
- **外中断（中断）**：由 CPU 外部事件引起，与当前指令无关，如 IO 设备完成请求、定时器到时、硬件故障等，是狭义"中断"。
- **按可屏蔽性**：可屏蔽中断（可被屏蔽字屏蔽）与不可屏蔽中断（须立即响应，如电源故障、内存校验错）。

> [!IMPORTANT]
> 重要内容：区分**内中断（异常，由指令引起）与外中断（由外部事件引起）**是常考点。内中断与当前执行指令相关、同步发生；外中断异步、与当前指令无关。系统调用/缺页/除零属内中断，IO 设备请求、时钟中断属外中断。有的教材把"访管指令/软中断"归入异常一类，注意用语差异。

**中断的作用**：实现 CPU 与 IO 并行、处理随机事件、实现多道程序并发与系统调用接口，是现代操作系统的基础机制之一。



#### 中断请求与判优

**中断请求**由中断源（设备或异常）发出，经中断请求寄存器登记后提交 CPU；CPU 在指令执行的适当时刻检查是否有未屏蔽的中断请求。

**中断判优**解决多个中断源同时请求时"先响应谁"的问题，决定响应次序。

**判优原则**：

- 先响应高优先级、紧急或实时要求高的中断。
- 硬件故障、不可屏蔽中断等紧急事件优先级最高。
- 不同中断源可通过优先级编码器排队，同一时刻只允许一个中断获得响应。

**中断响应次序（判优硬件）**与**中断处理次序（可由屏蔽字改变）**不同：硬件判优决定谁先被响应，屏蔽字可在处理时临时屏蔽某些中断，从而改变嵌套处理的先后。

**中断屏蔽字**：用若干位对应各中断源，置 1 表示屏蔽（不响应）。通过动态修改屏蔽字，可控制哪些中断能打断当前处理、实现多级嵌套。

> [!NOTE]
> 提醒内容：判优要回答"同时来了先服务谁"；屏蔽字要回答"我正处理这个时，允许谁来打断我"。判优由硬件排队决定，屏蔽字可由程序设定——所以"响应次序"由硬件定，而"实际嵌套处理次序"可被屏蔽字调整。



#### 中断响应与中断服务程序流程

**中断响应**指 CPU 决定接受某中断请求的时刻及所作的动作，它是"从被打断程序转向中断服务程序"的切换动作。

**中断响应的条件与时机**：

- 条件：有未屏蔽的中断请求，且 CPU 处于允许中断（开中断）状态。
- 时机：通常在**当前指令执行完**时响应（一条指令不可被打断），这样现场完整、便于恢复。

**中断响应完成的动作**（隐操作，由硬件完成）：

- 关中断：防止响应过程中再来新中断干扰（保护现场完整性）。
- 保存断点：把返回地址（PC）压栈保存，以便处理完返回。
- 引出中断服务程序：据中断源找到中断服务程序入口，把 PC 设为入口地址（向量中断用中断向量表直接查得）。

**中断服务程序的流程**（由程序完成）：

- **保护现场**：把被打断程序的寄存器、状态字等压栈保存。
- **执行中断处理**：针对该中断源完成实际处理。
- **恢复现场**：弹栈恢复各寄存器与状态。
- **开中断并返回**：开中断（允许新中断），用返回指令把断点地址送回 PC，回到原程序继续。

**中断响应（硬件）与服务程序（软件）的分工**：响应阶段做"关中断、存断点、转入口"，服务阶段做"保护现场、处理、恢复现场、返回"。

> [!WARNING]
> 警告内容：分清"响应"与"服务"的边界——**中断响应由硬件自动完成，只做关中断、存断点、找入口三件事**；**中断服务程序处理实际业务并负责保护/恢复现场、最后开中断返回**。现场保护通常放在服务程序开头，由软件压栈；不要误以为现场全由硬件保存。单重中断下服务前关中断、返回前开中断。



#### 多重中断与中断屏蔽

**多重中断（中断嵌套）**指在处理一个中断的过程中又响应了更高级别的新中断，从而嵌套处理，处理完新中断再返回原中断服务。

**多重中断的处理原则**：

- 仅当新中断**优先级更高**时才允许打断当前中断服务（低级或同级中断排队等待）。
- 响应新中断前先保护当前现场，处理完再恢复。
- 高优先级中断可嵌套打断低优先级中断，形成"优先级高的先处理完、逐层返回"。

**实现多重中断的关键——开中断的时机**：在服务程序中，完成"保护现场"之后、进入实际处理之前开放中断（开中断），使高优先级中断得以打断当前服务；返回前再关中断以完成恢复现场与返回的完整性。

**中断屏蔽的运用**：在多重中断中，通过设置屏蔽字可把某些低优先级中断屏蔽掉，使当前服务不被它们打断，或实现"暂时禁止除最高优先级外一切中断"的临界区保护。

> [!NOTE]
> 提醒内容：单重中断"响应一次服务到底，服务前关、返回前开"；多重中断则在"保护现场后开中断"以便嵌套。是否支持嵌套、何时开中断，取决于是否允许多重中断。屏蔽字既用于硬件判优时选定响应，也用于处理中封锁无关中断，二者要分清。
