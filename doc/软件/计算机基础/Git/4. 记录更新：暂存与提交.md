## 记录更新：暂存与提交

### git add 的多重含义

#### add 的准确语义：加入暂存区

**git add**：是把内容加入**暂存区**的命令，含义远不止"添加新文件"——跟踪新文件、暂存已修改文件、标记冲突已解决，都用同一条命令完成。

- **跟踪新文件**：对从未被 Git 管理的文件执行 add，Git 开始跟踪它，内容同时进入暂存区。
- **暂存已修改文件**：对已跟踪文件执行 add，把当前修改的快照存入暂存区，等待下一次提交。
- **标记冲突已解决**：合并冲突处理完毕后执行 add，告诉 Git 该文件的冲突状态已消除。

> add 的精确语义是"添加内容到下一次提交中"，而不是"添加文件"。把一次修改 add 进暂存区后又继续改这个文件，新改动不会自动进入暂存区——必须再次执行 add，提交的才是最新版本。

> 速记线索：add 的对象是**内容**（一次快照），不是**文件**；暂存区存的是"准备提交的版本"，工作区存的是"正在编辑的版本"，两者可以不一致。



#### add 的常用形式

add 有三种最常用的书写形式，区别在于**暂存范围**不同。

- **add 文件名**：只暂存指定的这一个文件，范围最小、最可控，适合精细提交。
- **add .**：暂存当前目录（含子目录）下的全部改动，包括新文件、修改与删除。
- **add -A**：暂存整个仓库的所有改动，无论当前位于哪个子目录，范围最大。

```bash
git add index.html   # 只暂存单个文件
git add .            # 暂存当前目录下的全部改动
git add -A           # 暂存全仓库的所有改动
```

> 三种形式的辨析：在仓库根目录执行时，add . 与 add -A 效果几乎相同；在子目录中执行时，add . 只作用于当前目录树，add -A 始终覆盖全仓库。实务中建议先执行 status 查看改动清单，再选择暂存范围。



#### 交互式暂存 add -p

**交互式暂存**：通过 add -p（patch）命令，把一个文件内的修改按**块（hunk）**拆分，逐块询问是否暂存，从而实现"同一个文件里只提交一部分修改"。

- 适用场景：一次改了多处，其中一部分属于功能 A、另一部分属于功能 B，希望拆成两个提交。
- 执行 add -p 后，Git 逐块展示差异，常用回答有：y 暂存该块、n 跳过该块、s 把大块再拆成小块、q 退出。
- 未被暂存的块仍留在工作区，本次提交后可继续编辑处理。

> add -p 的价值在于**提交粒度**：让每次提交只包含逻辑上完整的一组修改，提交历史因此更清晰，回滚定位也更精确。代价是操作变慢，适合重要提交，不适合高频琐碎提交。



### 查看差异

#### git diff 与 git diff --staged

**git diff**：查看**工作区与暂存区**之间的差异，回答"改了但还没暂存的内容有哪些"。**git diff --staged**：查看**暂存区与最近一次提交**之间的差异，回答"已暂存、即将被提交的内容有哪些"。

- **git diff（工作区 对 暂存区）**：不加参数时比较的是"还没 add 的修改"；一旦执行 add，这些修改就从 diff 中消失。
- **git diff --staged（暂存区 对 最近提交）**：比较的是"已 add、还没 commit"的修改，即下一次提交将要写入的内容。

> 常见误区是以为 git diff 能看到所有改动。实际上改动一旦 add 进暂存区，git diff 就不再显示它，须改用 git diff --staged。两条命令各管一段，合起来才覆盖"上次提交之后"的全部变化。



#### diff 输出的读法

diff 输出由减号行、加号行与上下文行构成，读懂三种行的符号即可还原变化。

- **减号行（以 - 开头）**：旧版本中被删除或被改动的行，显示变化前的内容。
- **加号行（以 + 开头）**：新版本中新增或改后插入的行，显示变化后的内容。
- **上下文行（以空格开头）**：没有发生变化的周围行，用于定位修改所在的位置。

```bash
git diff
# @@ -1,2 +1,2 @@
#  const name = "Git";
# -const version = 1;
# +const version = 2;
```

> 一对减号行与加号行描述同一处修改：先删旧行、再加新行。看到 -1 与 +2 相邻，含义是"把 1 改成 2"，而不是"删掉一行又空出一行"。



### 提交

#### commit 的行为与 -m

**git commit**：把**暂存区的快照**写入版本库，形成一条提交记录；**-m** 参数直接在命令行书写提交消息，省去打开编辑器的步骤。

- 提交的对象是暂存区当前的快照，不是工作区此刻的状态——未 add 的修改不会进入提交。
- 每次提交都会记录作者、日期、提交消息与指向父提交的指针，构成版本历史的节点。
- commit -m 后的消息用引号包裹，消息含空格时引号不可省略。

```bash
git add index.html
git commit -m "修复导航栏在窄屏下错位的问题"
```

> 不用 -m 书写消息时，Git 会打开默认编辑器（如 vim），首行即主题行；退出编辑器且消息为空时，提交会被中止，改动仍安全地留在暂存区。



#### commit -a 跳过暂存

**commit -a**：自动把所有**已跟踪文件**的修改暂存并一并提交，省去单独执行 add 的一步。

- 适用对象只有已跟踪文件的修改；新建的、尚未跟踪的文件不会被纳入。
- 对已跟踪文件而言，commit -a 的效果约等于 add -A 加 commit 两步合成一步。
- 风险在于粒度：不加区分地打包所有修改，容易把不相干的改动混进同一次提交。

```bash
# 以下两条命令对已跟踪文件效果等价
git add -A
git commit -m "更新配置项"

git commit -a -m "更新配置项"
```

> [!CAUTION]
> **注意内容**：commit -a 对**未跟踪文件无效**：新建的文件不会因为 -a 而被提交，仍然要先 add 让 Git 开始跟踪。依赖 -a 容易漏掉新文件，协作场景中建议保持"先 add、后 commit"的显式流程。



### 提交消息的写法

#### 消息结构：主题加正文

通行的提交消息结构是**一行主题加一个空行加正文**，主题是摘要，正文补充细节。

- **主题行**：一行以内，概括这次提交做了什么；log --oneline、托管平台的提交列表等场景默认只展示主题行。
- **空行**：主题与正文之间用一个空行分隔，这是多数工具解析消息的依据。
- **正文**：可写多行，说明改动的原因、背景与副作用，回答"为什么这么改"；简单的提交可以省略正文。

```text
修复导航栏在窄屏下错位的问题

媒体查询断点原为 768px，iPhone SE 的横屏宽度低于该值，
导致导航栏未切换为折叠形态。现将断点调整为 640px。
```

> 主题与正文的分工是"主题说结果、正文说原因"。主题行会被单行展示场景单独提取，一旦把细节堆进主题，提交列表就失去了信息密度。



#### 主题句的写法

主题句的通行惯例是**祈使句、50 字以内、说明为什么而非怎么做**。

- **祈使句**：写成"修复某问题"而非"修复了某问题"，与 Git 自动生成的提交消息（如 Merge branch 开头的合并提交）保持同一语态。
- **50 字以内**：通说认为主题行约以 50 个字符为上限，保证在各类界面中单行显示完整。
- **为什么而非怎么做**：改动的"怎么做"已由 diff 完整呈现，消息的价值在于补充 diff 读不出来的动机与约束。

> 实务中，团队常在主题行前加任务编号（如 #123 修复登录超时），便于提交与需求系统双向追溯；是否加编号依团队规范而定，祈使句与长度上限则是跨团队通用的惯例。



#### 约定式提交 Conventional Commits

**约定式提交（Conventional Commits）**：一种提交消息的书写约定，格式为**类型加半角冒号加空格加描述**，让提交历史可被程序解析，常用于自动生成变更日志与决定版本号。

- **feat**：新增功能。
- **fix**：修复缺陷。
- **docs**：仅改动文档。
- **refactor**：既非新增功能也非修复缺陷的代码重构。
- **test**：增加或修改测试。
- **chore**：构建流程、依赖管理等杂务改动。

```bash
git commit -m "feat: 支持深色模式切换"
git commit -m "fix: 修复上传大文件时进度条越界"
```

> 约定式提交属于社区约定而非 Git 内建功能，不带类型前缀的提交完全合法；它的收益来自团队的共同遵守，实务中常配合工具（如 commitlint）在提交前自动校验格式。



### 删除文件

#### git rm 的作用

**git rm**：把文件从**暂存区与工作区同时移除**，删除动作会随下一次提交写入版本历史。

- 只执行 git rm 而未提交时，删除先进入暂存区，工作区的文件同时被删除。
- 文件已有未暂存的修改时，Git 会拒绝删除以保护数据，需加 -f 强制确认。
- 删除目录时加 -r，如 git rm -r 目录名。

> 用文件管理器直接删除文件时，工作区少了文件而暂存区仍有记录，status 会把该文件同时标为已删除与未暂存；执行 git rm（或对它执行 add）后，状态才收敛为待提交的删除。git rm 的意义在于把删除也当作一次受版本控制的修改。



#### rm --cached 仅取消跟踪

**git rm --cached**：只把文件从暂存区移除（取消跟踪），**保留工作区中的文件本身**，常用于补写 .gitignore 之后。

- 典型场景：文件此前已被提交，后来才发现不该纳入版本控制（如本地配置、日志），先把它写进 .gitignore，再用 rm --cached 取消跟踪。
- 取消跟踪并提交后，Git 不再记录该文件的变化，本地文件原样保留。
- 不加 --cached 的 git rm 会连工作区文件一起删除，二者只差这一个参数。

```bash
# 补写 .gitignore 后，让已跟踪的本地配置脱离版本控制
echo "config.local.js" >> .gitignore
git rm --cached config.local.js
git commit -m "chore: 停止跟踪本地配置文件"
```

> [!IMPORTANT]
> **重要内容**：.gitignore 只对**未被跟踪**的文件生效；已被跟踪的文件即使写进 .gitignore，Git 仍会继续记录其修改。想让 ignore 规则生效，必须先用 git rm --cached 取消跟踪，再提交这一次状态变化。



### 移动与改名

#### git mv 与改名的识别

**git mv 旧名 新名**：完成文件的移动或重命名，并自动把变化暂存。它等价于 mv 改名后，再执行 git rm 移除旧路径、git add 登记新路径的三步组合。

- git mv 一步完成三步操作：改名（mv）、从暂存区移除旧路径（rm）、把新路径加入暂存区（add）。
- 移动到子目录同样适用，如 git mv index.html src/index.html。
- Git 并不显式记录"改名"这一事件，而是提交后依据**内容相似度**自动识别新旧路径的对应关系。

> 改名识别是启发式的：改名的同时大幅改写文件内容，Git 可能识别不出对应关系，历史会显示"一删一增"而非"重命名"。用 log --follow 追踪文件历史，可沿改名前的路径继续回溯。
