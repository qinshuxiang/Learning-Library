## 储藏与引用日志

### 储藏 stash

#### 储藏的定义与使用场景

**储藏（stash）**：是把工作区与暂存区中尚未提交的修改暂时收起、存入一个栈式列表的功能；存入后工作区恢复干净，之后随时可以恢复。

- 典型场景：开发到一半被要求紧急修复问题，当前改动不宜提交，又要先切到别的分支处理急事。
- 存入储藏后，工作区回到最近一次提交的状态，可以自由切分支、拉更新。
- 储藏完全属于本地，不会被推送，也不会被克隆带走。

> 储藏的定位是"临时停车场"而非备份手段：适合小时级的暂存；要跨天保留的工作，更稳妥的做法是提交到一个专门的工作分支。



#### 储藏的基本操作

stash 的全部操作围绕"存入、列出、恢复、删除"四个动作展开。

```bash
# 存入储藏并清理工作区：stash push 可省略为 stash
git stash push -m "购物车功能开发到一半"

# 查看储藏列表
git stash list

# 恢复指定储藏，但条目保留在列表中
git stash apply stash@{0}

# 恢复最近一次储藏，并删除该条目
git stash pop

# 删除指定储藏条目
git stash drop stash@{0}

# 连未跟踪的新文件一起存入
git stash -u

# 以储藏时的提交为起点新建分支，并恢复储藏
git stash branch fix-hotkey
```

- git stash push -m 消息：存入并清理工作区，-m 写说明便于日后辨认；直接写 git stash 效果相同。
- git stash list：列出全部储藏；条目按栈编号，新存入的编号更小，stash@{0} 永远是最近一次储藏。
- git stash apply 编号：恢复指定条目但不删除它，同一份改动可反复恢复到多个分支。
- git stash pop：恢复并删除条目，等价于 apply 之后紧跟 drop；不带编号时作用于 stash@{0}。
- git stash drop 编号：只删除条目，不恢复内容。
- git stash -u：把未跟踪文件也一并存入；默认只收已跟踪文件的修改，新建且从未 add 过的文件会留在工作区。
- git stash branch 分支名：从储藏新建分支并恢复内容——储藏与当前分支冲突时，这是最省事的出路。

> apply 与 pop 的选择看是否要留后手：同一份改动要恢复到多个分支时用 apply 反复取用，用完再 drop；一次性的暂存用 pop 一步到位。



#### 恢复时的冲突处理

pop 或 apply 时，若储藏内容与当前分支的代码冲突，Git 转入合并冲突流程，此时储藏条目不会被自动删除。

- 冲突表现：工作区出现冲突标记，命令输出提示储藏未能干净地应用。
- 处理方式：与合并冲突一致——编辑文件解决冲突标记，再用 git add 标记已解决。
- 关键差别：apply 遇冲突后条目本就保留；pop 遇冲突后条目同样保留，需要手动 git stash drop 清理。

> [!WARNING]
> **警告内容**：pop 冲突后条目仍留在栈里，解决冲突后若忘记 drop，之后再次 pop 会把同一份改动重复应用一次。冲突高发的场景建议直接改用 apply 加手动 drop，每一步都由自己确认。



### 引用日志 reflog

#### 引用日志的定义

**引用日志（reflog）**：是 Git 在后台记录的 HEAD 移动轨迹——每一次提交、切换、重置、变基都会留下一条记录，是本机的操作流水账。

- 记录对象是引用的移动：HEAD 与分支的每次变化都被记下，普通提交、checkout、reset、rebase 全在内。
- 本地专属：reflog 只存在于本机的 .git/logs 目录，不随 push 同步，别人看不到你的轨迹。
- 查看方式：git reflog，每条记录形如 哈希 HEAD@{编号}: 操作说明，按时间倒序，HEAD@{0} 是当前位置。

```bash
git reflog
```

```text
1a2b3c4 (HEAD -> main) HEAD@{0}: commit: 完成导出功能
e4f5a6b HEAD@{1}: checkout: moving from dev to main
9f8e7d6 HEAD@{2}: reset: moving to HEAD~1
```

- 编号越大越久远：HEAD@{1} 是上一次移动之前 HEAD 所指的位置。
- 引用语法 stash@{0} 与 HEAD@{2} 同源：引用加 @{编号}，表示"该引用在若干次移动之前的位置"。

> reflog 常被称为后悔药的安全网：分支与 reset 之下看似消失的提交，只要 reflog 里还有记录，就能凭哈希找回。但它是会过期的流水账而非永久档案，过期规则见下节。



#### 引用语法与历史位置

**引用语法（HEAD@{2}、stash@{0} 这类写法）**：在引用后接 @{数字}，表示"该引用在 N 次移动之前指向的位置"。

- HEAD@{2}：HEAD 在两次移动之前的位置，回答"我之前在哪"。
- 与 HEAD~2 的区别：HEAD~2 沿提交图谱向上数两代父提交，回答"代码的祖先是谁"；两者指向的常常不是同一个提交。
- 该语法可用于一切接受提交参数的命令，如 checkout、reset、diff、show。

> 易混辨析：**HEAD~2 是提交历史里的祖先，HEAD@{2} 是操作足迹里的旧位置**。reset 到 HEAD@{2} 是"回到我两步操作之前"，reset 到 HEAD~2 是"回到当前提交的祖父提交"。



### 找回丢失的提交

#### 找回的原理与流程

被 reset --hard 抛弃或随分支删除而失联的提交并不会立刻消失：只要仍被 reflog 或任何引用记着，就能凭哈希找回。

- 原理：Git 不删除提交对象，只移动引用；对象本体仍留在 objects 目录中，等待过期回收。
- 第一步：git reflog 找到目标提交的哈希。
- 第二步：git branch 恢复名 哈希 新建分支把它挂回分支图，或 git checkout 哈希 先检视再决定。

```bash
# 第一步：在操作轨迹里找到被抛弃提交的哈希
git reflog

# 第二步：凭哈希新建分支，把提交重新挂回分支图
git branch rescue 9f8e7d6

# 或先切过去确认内容，再建分支
git checkout 9f8e7d6
```

- 用 branch 恢复：适合整个分支被误删的场景，一步回到正轨。
- 用 checkout 哈希：进入**游离 HEAD（detached HEAD）**状态——HEAD 直接指向提交而不在任何分支上；确认内容后建分支即可固化。

> 判断一个提交是否真的丢失，标准是可达性：从任何引用（分支、标签、stash、reflog）出发都走不到它，才算不可达。只要有一条路通着，找回就只是几条命令的事。



#### 对象的过期与垃圾回收

reflog 的条目有保质期，过期之后不再可达的对象可能被垃圾回收，那时提交才真正无法找回。

- 默认保质期：可达提交的引用日志条目保留 90 天，不可达提交的条目保留 30 天。
- 清理由 git gc 触发：垃圾回收运行时清理过期条目、回收不可达对象。
- 失效时刻：对象被回收后 reflog 无从查起，只能退而求其次用 fsck 碰运气（见下节）。

> [!TIP]
> **建议内容**：重要节点先打个分支或标签是最省心的保险——引用是永久的，reflog 是会过期的。执行 reset --hard 这类大动作之前，先 git branch backup 落一个引用，远比事后翻日志稳当。



#### 底层检查工具 fsck

**fsck --lost-found**：底层检查工具，列出所有**悬空提交（dangling commit）**——不再被任何引用指向、但仍留在对象库中的提交。

- 适用场景：reflog 已过期或被清空，而对象尚未被垃圾回收的窗口期。
- 用法：git fsck --lost-found 输出悬空提交的哈希，逐个用 git show 哈希 确认内容，再建分支恢复。

```bash
# 列出悬空提交
git fsck --lost-found

# 逐个确认内容后恢复
git show 9f8e7d6
git branch rescue 9f8e7d6
```

> fsck 是 reflog 之外的第二道找回手段，代价是输出只有哈希、没有操作说明，需要逐个 show 确认。两者的使用次序固定：先翻 reflog，再查 fsck。
