## Git 内部原理：对象与引用

### 底层命令与上层命令

**底层命令（plumbing）**：直接操作对象库、暂存区与引用的命令，接口朴素、输出面向机器，供脚本与内省使用；**上层命令（porcelain）**：把底层命令组合封装后的日常命令，输出友好、面向人。

- **上层命令**：git add、git commit、git log、git branch 等，日常开发只与它们打交道也够用。
- **底层命令**：git cat-file、git hash-object、git ls-tree 等，是观察 Git 内部的窗口。
- 分工关系：一次 git commit 背后，依次是把文件内容写成 blob、把目录结构写成 tree、把元数据写成 commit、把分支引用改指向——上层命令是这些底层动作的编排。

> 理解底层是读懂 .git 目录的钥匙：.git 里存放的一切都以底层命令的数据模型为准。本章的验证全部借助底层命令完成，建一个试验仓库即可随手复现。



### .git 目录导览

仓库的全部状态都在 .git 目录中，认识它的关键成员等于认识 Git 的工作台。

```bash
# 在仓库根目录查看 .git 的顶层内容
ls -A .git
```

```text
COMMIT_EDITMSG
HEAD
ORIG_HEAD
config
hooks/
index
info/
logs/
objects/
packed-refs
refs/
```

- **HEAD**：文本文件，内容形如 ref: refs/heads/main，指示当前所在分支；处于游离状态时直接存一个提交哈希。
- **config**：仓库级配置文件，记录远程仓库地址、分支跟踪关系等设置。
- **objects 目录**：对象库，blob、tree、commit、tag 四类对象全部存放于此。
- **refs 目录**：引用目录，分支、标签、远程引用各占一个子目录，每个引用是一个存着哈希的小文本文件。
- **index**：暂存区文件（不是目录），记录下一次提交将包含的内容。
- **hooks 目录**：钩子脚本目录，可在提交、推送等动作前后插入自动执行的脚本。
- **packed-refs**：打包引用文件，把数量庞大的引用合并为逐行清单存放，是 refs 目录的补充。

> [!NOTE]
> **提醒内容**：index 是文件，objects 与 refs 是目录，三者分别对应暂存区、对象库、引用三大核心；logs 目录存放的正是上一章的引用日志。



### Git 的四类对象

#### 对象模型的总体结构

Git 把仓库里的一切内容抽象为四类对象，全部存放在 objects 目录中，靠"指向"组织成完整的版本历史。

```text
tag（附注标签对象）
 └─ 指向 ─> commit（提交对象）
              ├─ 指向父提交 ─> 更早的 commit
              └─ 指向 ─> tree（根目录树对象）
                           ├─ 指向 ─> blob（文件内容）
                           └─ 指向 ─> tree（子目录树对象）
                                        └─ 指向 ─> blob（文件内容）
```

- 每次提交记录一个根 tree，根 tree 层层展开，覆盖仓库当时的完整快照。
- commit 通过父提交串联出历史，tag 再给某个 commit 钉上可读的名字。
- 四类对象各司其职：blob 管内容、tree 管结构、commit 管历史、tag 管发布。



#### 四类对象详解

##### blob：数据对象

**blob**：存储文件的内容，不存储文件名与目录位置——文件名由 tree 记录。

- 两个文件只要内容相同，就共享同一个 blob，无需重复存储。
- 文件改名后 blob 不变，变的只是 tree 里的记录。
- blob 不含任何元数据，连文件权限都由 tree 记录。

> blob 只认内容不认名字，这解释了 Git 的一个现象：把一个文件复制改名再提交，仓库体积几乎不变——底层始终只有一份 blob。



##### tree：树对象

**tree**：存储一个目录的快照，记录该目录下每个条目的名字、类型与指向。

- 每个条目要么指向一个 blob（文件），要么指向一个子 tree（子目录）。
- 条目同时记录文件的权限模式，如 100644 表示普通文件。
- 一个 commit 对应一个根 tree，根 tree 逐层展开就是提交时点的完整目录结构。

> tree 与 blob 的分工：blob 管"内容是什么"，tree 管"内容叫什么、放在哪、权限是什么"。目录改名会生成新 tree，但其中的 blob 原样复用。



##### commit：提交对象

**commit**：存储一次提交的元数据，并指向一个根 tree 与一个或多个父提交。

- 元数据包括作者与提交者（各含姓名、邮箱）、提交时间与完整的提交说明。
- 指向一个根 tree，代表这次提交的完整快照。
- 指向父提交：普通提交有一个父，合并提交有两个父，首个提交没有父。
- 提交哈希就是 commit 对象内容的 SHA-1 值，元数据或快照任一变化都会产生新提交。

> commit 记录的是快照而不是差异：每个 commit 都完整指向一棵树。后续的增量压缩是存储层的优化（见下文），概念模型上每次提交就是一张全量快照。



##### tag：标签对象

**tag**：附注标签的载体，指向一个 commit，附带标签者、日期与说明，可签名。

- 轻量标签没有自己的对象，引用文件里直接存 commit 的哈希。
- 附注标签是一个真正的 tag 对象：refs/tags 下的引用指向 tag 对象，tag 对象再指向 commit。
- 比引用多一层，换来的是可审计的元数据与签名能力。

> 附注标签比轻量标签多的正是"一层对象"：引用指向的不再是提交而是标签对象。想分辨手里是哪一种，用 git cat-file -t 看类型即可，输出 tag 就是附注标签。



#### 内容寻址

**内容寻址（content-addressable storage）**：对象的文件名就是对象内容本身的 SHA-1 哈希，内容相同则哈希相同，内容一字之差哈希就完全不同。

- 对象写入 objects 目录时，按哈希前两位建子目录、其余哈希作文件名。
- 哈希同时充当校验和、去重键与被引用的地址，一个值三种用途。
- 推论：仓库中不会出现两份相同内容的对象，历史再长也自动去重。

> 内容寻址解释了多个日常现象：空文件在所有仓库中的哈希一致；改一个字符必然产生新对象；提交哈希能唯一代表一次提交。反过来说，同一个提交哈希在任何机器上指向的内容必然相同——这是 Git 可信的根基。



### 亲手验证对象

#### 写入与读取对象

用底层命令把"内容变成对象"的过程亲手走一遍，以下命令在任意试验仓库中可运行。

```bash
# 把一段文本按 blob 写入对象库，输出它的哈希
echo "test content" | git hash-object -w --stdin
# 输出：d670460b4b4aece5915caf5c68d12f560a9fe3e4

# -p 以可读形式打印对象内容，-t 只显示对象类型
git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
# 输出：test content

git cat-file -t d670460b4b4aece5915caf5c68d12f560a9fe3e4
# 输出：blob
```

- git hash-object -w --stdin：从标准输入读取内容、按 blob 写入对象库并返回哈希；去掉 -w 则只计算哈希、不落盘。
- git cat-file -p 哈希：打印对象的可读内容，对 blob、tree、commit、tag 四类都适用。
- git cat-file -t 哈希：只回答这个哈希是什么类型的对象。

> 同一段内容无论写多少次，hash-object 返回的哈希都不变——这正是内容寻址的直接体验：内容决定名字，而不是名字决定内容。



#### 查看提交的目录树

一次提交在对象库中的真实形态，可以用 ls-tree 与 cat-file 拆开看。

```bash
# 查看当前提交的根 tree：每行一个条目，含权限、类型、哈希、名字
git ls-tree HEAD

# 查看当前提交对象本身
git cat-file -p HEAD
```

```text
100644 blob a906cb2a4a904a152e80877d4088654daad0c859  README.md
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0  src

tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0
parent 0c5a2b1d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8b
author 示例作者 example@example.com 1796000000 +0800
committer 示例作者 example@example.com 1796000000 +0800

完成导出功能
```

- 第一行 tree 指向根 tree，是这次提交的快照入口。
- parent 指向父提交，串出历史；首个提交没有这一行。
- author 与 committer 分开记录：作者与最终提交者可以是两个人，例如改动经补丁由他人合入时。

> 这条链条演示了一次提交在对象库中的真实形态：commit 记元数据、tree 记结构、blob 记内容。git log 与 git show 展示的一切，最终都由这三类对象拼装而成。



### 引用的本质

**引用（ref）**：是 refs 目录下的一个文本文件，内容只有一个 40 位的对象哈希；分支、标签、远程引用本质上都是引用。

- **分支引用**：refs/heads/main 文件的内容就是 main 当前指向的提交哈希，每次提交 Git 只是改写这一个文件。
- **HEAD**：.git 根下的文本文件，内容形如 ref: refs/heads/main，表示"当前在 main 分支"；游离 HEAD 状态下内容直接是一个哈希。
- **远程引用**：refs/remotes/origin/main 记录上次与远程同步时 origin/main 的位置，是只读的坐标，不由本地提交改写。
- **附注标签引用**：refs/tags/v1.0.0 存的是 tag 对象的哈希，tag 对象再指向提交，比轻量标签多一层。

```bash
# 分支引用的内容：一个 40 位提交哈希
cat .git/refs/heads/main
# 输出示例：1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b

# HEAD 的内容：指向当前分支
cat .git/HEAD
```

```text
ref: refs/heads/main
```

- 验证方式很直接：任何引用都能用 cat 打开看内容。
- 引用文件小到可以忽略成本：新建分支只是新建一个 41 字节的文本文件（40 位哈希加一个换行）。

> 引用的"轻"解释了分支的"廉价"：创建、删除、切换分支都不复制任何文件内容，只是增删改一个小文本文件。Git 工作流的灵活，根基全在这里。



### 包文件与松散对象

**松散对象（loose object）**：每个对象独立存成一个文件的存放形式；**包文件（packfile）**：把大量对象合并压缩进单个文件的存放形式。

- 新提交产生的对象先以松散形式写入 objects 目录，随取随写。
- 对象数量累积后，git gc 或一次推送会触发打包：松散对象被合并进 pack 文件，并生成配套的索引文件加速查找。
- 打包采用增量压缩：相似的对象之间只存差异，历史越长、内容越相似，省下的空间越多（思路至此即可，细节不在本章范围）。

> objects 目录下同时存在两位哈希子目录与 pack 文件是正常现象：新对象松散、旧对象已打包。打包只是存储层的优化，对象的内容与哈希不变，上层命令对此完全无感。



### refspec

**refspec**：是"源引用加半角冒号加目标引用"的映射规则，规定远程操作时两侧引用如何对应，如 refs/heads/*:refs/remotes/origin/*。

- fetch 按 refspec 决定"远程的分支映射到本地的哪个位置"，默认规则即上例。
- push 按 refspec 决定"本地的引用推到远程的哪个位置"，上一章删除远程标签的 :refs/tags/标签名 就是一条 refspec。

> 记住一个坐标就够：冒号左边是"从哪里来"，右边是"到哪里去"。fetch 时源在远程、目标在本地；push 时源在本地、目标在远程。其完整行为在讲远程仓库与 push、fetch 时展开。
