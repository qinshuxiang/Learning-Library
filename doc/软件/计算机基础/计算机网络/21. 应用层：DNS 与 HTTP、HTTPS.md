## 应用层：DNS 与 HTTP、HTTPS

### 网络应用模型

#### 应用层与网络应用模型概述

**应用层（application layer）**：是 TCP/IP 体系结构中的最高层，直接为用户的应用进程提供服务，规定应用进程之间通信的规则（协议），如域名解析、网页浏览、电子邮件、文件传输等。

- 网络应用通常按通信双方的角色关系划分成几种**应用模型**，主流的三种是：客户/服务器（C/S）、对等（P2P）以及两者的混合模型。
- 理解应用模型有助于判断系统的扩展性、管理与安全特性，是后续各协议（HTTP、FTP、邮件、BitTorrent）共同的组织框架。

> 分层回顾：**物理到传输层解决"数据怎么通"，应用层解决"应用之间说什么话"**。学本章时带着"谁提供服务、谁消费服务"的视角去读每个协议。



#### 客户/服务器模型（C/S）

**客户/服务器模型（Client/Server，C/S）**：把通信双方划分为**服务器**（提供服务的一方）与**客户**（请求服务的一方）两种角色，客户向服务器发起请求，服务器响应并返回结果。

- **服务器**：**常驻运行**、拥有**固定的 IP 与端口**（well-known），可扩展为**服务器集群**分担负载；管理集中、内容可控。
- **客户**：**主动发起**通信，通常是间歇性接入的终端（浏览器、邮件客户端），IP 可不固定。
- 典型例子：HTTP 网站、FTP、电子邮件（SMTP/POP3/IMAP）、DNS 查询。
- 优缺点：内容与服务**集中管理**方便（易维护、易安全管控），但服务器易成**性能瓶颈**与**攻击目标**，服务能力受限于服务器规模。

> 记忆：C/S 是"**中心化服务、客户主动上门**"。做题时抓住特征词：常驻服务器、固定地址、集群扩展、瓶颈在服务器。



#### P2P 对等模型

**P2P 对等模型（Peer-to-Peer）**：网络中的每个节点地位**对等**，既是服务的消费者（客户）又是服务的提供者（服务器），这样的节点称为**对等方（peer）**，对等方之间直接通信、互相共享资源。

- **自扩展性强**：每加入一个新对等方，既消耗资源也**贡献带宽与存储**，整体服务能力随用户规模增长而增强，不存在"瓶颈服务器"。
- **成本低、去中心化**：无需部署昂贵的大型服务器集群，也无需固定 IP 的中心节点。
- 典型例子：BitTorrent、电驴（eMule）等文件共享软件。
- 缺点：**管理困难**（无集中控制点，难以审计与监管），存在**版权与安全**问题（易传播恶意软件与盗版内容），节点的动态上下线使服务不稳定。

> 对比一句话：**C/S 能力受限于服务器，用户越多越拥塞；P2P 能力来自全体用户，人越多分发越快**。两者互为镜像，考试常考"谁承担服务、瓶颈在哪里"。



#### 混合模型与典型应用

**混合模型**：在一个系统中同时存在 C/S 与 P2P 两种交互方式——通常用中心服务器负责**索引、认证、在线状态**等"控制面"职责，实际数据传输由对等方之间以 P2P 方式完成。

- **即时通信（IM）**：中心服务器维护用户的**在线状态**与好友列表，登录、查找走 C/S；用户之间互发消息、传文件则尽量走 P2P 直连。
- **Napster（典型考题）**：中央索引服务器保存"文件名到对等方地址"的目录，**检索走 C/S**，文件下载在对等方之间**点对点直传**——它是 P2P 思想的开端，但中心目录仍是单点。
- 混合模型兼顾了"P2P 的扩展性"与"中心化的可管理性"，是大型商业系统（QQ、微信等）的常见折中。

> 记忆：**"登录找中心，传输找对等"**是混合模型的判别特征。考到"Napster 属于什么模型"时，答"集中式目录 + 分布式内容传输的混合/P2P 雏形"。



### DNS 域名系统

#### DNS 的定位与工作方式

**DNS（Domain Name System，域名系统）**：是完成**域名与 IP 地址相互映射**的**分布式、层次化**的数据库系统，也是运行在 UDP/TCP 53 端口上的查询协议，被称为互联网的"目录服务"。

- 人的记忆用域名（www.example.com），网络寻址用 IP，DNS 负责把两者互转（正向：域名到 IP；反向：IP 到域名）。
- **分布式**：不存在一台服务器存下全网域名，而是把域名空间切成许多区（zone），由各级域名服务器分层管理，避免单点故障与性能瓶颈。
- 默认使用 **UDP 53** 端口发送短小的查询报文（快、省开销）；仅当响应超过 512 字节或进行**区域传送**（主从服务器同步整区数据）时改用 **TCP 53**。

> 定位口诀：**"用户记名字，路由要号码，DNS 当翻译"**。DNS 是应用层协议，但全网的 Web、邮件都依赖它，一旦 DNS 故障，表现为"能上 IP 不能上域名"。



#### 层次域名空间

**域名空间（domain name space）**：是一种树状命名的层次结构，根在最上层（用空标号表示），往下依次是顶级域、二级域……，叶子通常是主机名。域名从右向左读，越靠右层级越高。

以 www.cs.tsinghua.edu.cn 为例的层次划分：

- **根（root）**：域名树的根，通常写作点 .。
- **顶级域 cn**：表示中国；同时存在通用顶级域 com、org、net、edu、gov 等与国家顶级域 cn、uk、jp 等。
- **二级域 edu.cn**：在 cn 之下再划分，表示"中国的教育机构"。
- **三级域 tsinghua.edu.cn**：清华大学的域。
- **四级域 cs.tsinghua.edu.cn**：计算机系子域；最左的 **www** 是主机名。

命名的基本规则：

- 各级域名之间用**点**分隔，一个标号长度不超过 63 个字符，整个域名不超过 255 个字符，不区分大小写。
- 域名是**逻辑概念**，不直接对应物理位置；同一个域下的主机可以在不同地点。

> 解析方向记忆：**域名是"从右往左越来越具体"**——先找到大区域（国家/类型），再逐级缩小到具体主机。这个顺序正是迭代查询沿树下降的顺序。



#### 域名服务器的层次结构

**域名服务器按职责划分成四类**，自顶向下形成查找链路：根域名服务器、顶级域名服务器、权威域名服务器，外加用户身边的本地域名服务器。

- **根域名服务器**：知道所有**顶级域名服务器**的地址，是解析的"总入口"。全球有 **13 个逻辑根服务器编号**（a.root-servers.net 等），每个逻辑编号背后有大量镜像，通过 **Anycast** 部署在世界各地。
- **顶级域名（TLD）服务器**：管理某个顶级域（如 .com、.cn）下所有二级域的权威服务器地址。
- **权威域名服务器（authoritative name server）**：保存某个区内域名的**最终解析记录**，负责给出"终极答案"；通常由域名注册商或托管服务商提供。
- **本地域名服务器（local name server / 递归解析器）**：不是域名树的一层，而是主机的"代理"，通常由 ISP 或公共 DNS 提供（如 114.114.114.114、223.5.5.5、8.8.8.8、1.1.1.1）。

> 一个域名往往配置**主权威服务器与辅权威服务器**，并通过 NS 记录声明，保证高可用。主机只需配置本地域名服务器的地址，不必知道任何根服务器地址——递归代理会替它跑完整个查找过程。



#### 域名解析过程：递归与迭代

**域名解析**是应用进程把域名换成 IP 的过程，依据查询方与被查询方的关系分为**递归查询**与**迭代查询**两种方式。

- **递归查询（recursive query）**：查询方要求被查询的服务器**替自己跑完整个解析**，无论它知不知道答案，最终都要返回"最终答案"或"查不到"。主机对本地域名服务器的查询通常是递归的。
- **迭代查询（iterative query）**：被查询的服务器只回复"**下一步该问谁**"（下一级服务器的地址），由查询方自己继续逐级询问，直到拿到最终答案。本地域名服务器对根、TLD、权威服务器的查询通常是迭代的。

以解析 www.example.com 为例的完整流程：

1. 客户端先查**浏览器缓存**，再到**操作系统 hosts 文件与本地 DNS 缓存**，命中则直接返回。
2. 未命中则向**本地域名服务器**发起**递归查询**。
3. 本地域名服务器若也无缓存，则代表客户端开始**迭代查询**：先问根服务器，根返回 .com TLD 服务器地址；再问 TLD 服务器，返回 example.com 权威服务器地址；再问权威服务器，得到 www.example.com 的 IP。
4. 本地域名服务器把答案**缓存**起来（受 TTL 控制），并沿原路**递归返回**给客户端。

> 考试判别：**"主机→本地服务器"必答递归；"本地服务器→根/顶级/权威"必答迭代**。如果题目说某台服务器替客户端一路问到最终答案并返回，那就是递归；若它只告诉"下家是谁"，就是迭代。



#### DNS 缓存与 TTL

**DNS 缓存**：各级域名服务器与主机都会把近期查询结果暂存，下次遇到相同域名直接命中，减少对外查询、降低解析时延与根/TLD 服务器压力。

- 缓存条目带**TTL（生存时间）**，过期后自动失效，需重新向上级查询刷新。
- TTL 由域名管理员在资源记录中设定：太短则缓存命中率低，太长则域名切换 IP 后全网收敛慢。
- 缓存使"改域名解析"不是立即全局生效——旧记录可能还要存活最长一个 TTL 的时间。

> 排障提示：本地改了 hosts 或刚换了 DNS 仍解析旧 IP，先考虑**缓存未过期**；可执行 ipconfig /flushdns（Windows）或 dscacheutil -flushcache（macOS）清缓存验证。



#### 资源记录 RR

**资源记录（Resource Record，RR）**：是域名服务器中存储的一条条"域名到值"的映射条目，格式为四元组 **（Name，Value，Type，TTL）**，含义由 Type 决定。

- **A（Address）**：域名 → IPv4 地址，如 www.example.com → 93.184.216.34。
- **AAAA**：域名 → IPv6 地址（A 的 IPv6 版本）。
- **CNAME（Canonical Name）**：别名 → 规范名，如 www.example.com → example.com，用于域名别名与 CDN 接入。
- **NS（Name Server）**：域 → 该域的权威域名服务器主机名。
- **MX（Mail eXchanger）**：域 → 接收该域邮件的邮件服务器，带优先级数值（越小越优先）。
- **PTR（Pointer）**：IP → 域名，用于**反向解析**（如反查邮件服务器身份）。
- **SOA（Start of Authority）**：区的开始记录，声明该区的权威信息与主服务器（可选补充）。
- **TXT**：任意文本，常用于发布 SPF、DKIM 等域名验证信息（见第 22 章邮件治理）。

> 用法速记：**"上网查 A/AAAA，起别名用 CNAME，找权威用 NS，收邮件靠 MX，反查用 PTR"**。做题常给一个域名问应配置哪类记录，按上句对号入座即可。



#### DNS 安全与隐私：劫持、污染与 DoH/DoT

**DNS 的安全威胁**主要有劫持与污染两类：**DNS 劫持**指篡改域名解析结果（攻击路由器、运营商或注册商层面），把用户导向钓鱼站点；**DNS 污染（缓存投毒）**指攻击者向解析器**伪造响应报文**，使错误记录被缓存。

- 传统 DNS 查询用 **UDP 明文**传输，中间人可窥探查询内容（隐私泄露）、伪造响应（污染），这也是审查与封堵常发生在 DNS 环节的原因。
- 主要防御手段：
  - **DoH（DNS over HTTPS）**：把 DNS 查询封装进 HTTPS（443 端口），借助 TLS 加密与服务器认证，防止窃听与篡改；现代浏览器与公共 DNS 普遍支持。
  - **DoT（DNS over TLS）**：用独立 TLS 连接承载 DNS（853 端口），与 DoH 思路相同、通道不同。
  - **DNSSEC**：用数字签名对 DNS 记录做**来源认证与完整性校验**，防止伪造响应（防止"污染"，但不能防窃听）。
  - 客户端侧：及时更新系统、使用受信 DNS、定期检查 hosts 文件与路由器设置。

> 对比记忆：**DoH/DoT 加密解决"被偷看、被篡改"，DNSSEC 签名解决"答案是不是权威发的"**。考试答"如何防 DNS 劫持/污染"时，先写 DoH/DoT，再补 DNSSEC 与客户端自查。



### 万维网 WWW 与 HTTP

#### WWW 的组成三要素

**WWW（World Wide Web，万维网）**：是一个大规模的、分布式的**超媒体**信息系统，用户通过浏览器以统一的方式访问分散在全球的网页资源。万维网的三要素是 **URL、HTML、HTTP**。

- **URL（Uniform Resource Locator，统一资源定位符）**：标识资源的位置与访问方式，格式为"协议://主机[:端口]/路径[?查询][#片段]"，如 https://www.example.com:443/index.html。
- **HTML（HyperText Markup Language，超文本标记语言）**：描述网页内容的标记语言，借助**超链接**把不同页面互连成网。
- **HTTP（HyperText Transfer Protocol，超文本传输协议）**：浏览器与服务器之间传输超文本（HTML、图片等）的应用层协议。

> 三者关系：**URL 告诉"去哪儿拿"，HTTP 规定"怎么拿"，HTML 描述"拿回来看什么"**。万维网依赖这三者才把分散的资源组织成可点击的"网"。



#### HTTP 的定位与报文结构总览

**HTTP（HyperText Transfer Protocol，超文本传输协议）**：是万维网使用的应用层协议，采用**客户/服务器**模式与**请求-响应**模型，默认基于 **TCP**（HTTP/3 改用 QUIC），默认端口 **80**，是无状态协议。

- 浏览器（客户）发起请求，服务器处理后返回响应；每个 HTTP 报文都由四部分组成：**起始行、首部字段、空行、报文主体**。
- HTTP 报文的交换靠 TCP 可靠传输，因此不必担心数据在传输层丢失或乱序。
- "无状态"指服务器**不记忆**上一次请求的任何信息，每个请求独立处理。

> 报文结构四段式：**"起始行打头，首部表属性，空行做分隔，主体放数据"**。请求报文与响应报文的差异只在起始行的写法与首部内容。



#### HTTP 请求报文

**HTTP 请求报文**：由客户端发往服务器，格式为**请求行 + 请求首部 + 空行 + 请求体**。

- **请求行**：方法 SP URL SP 版本 CRLF，如 GET /index.html HTTP/1.1。
- **请求首部（header）**：一行一个"首部名: 值"，常见有：
  - **Host**：目标主机域名与端口（HTTP/1.1 起必须携带，服务器靠它区分同一 IP 上的多个站点）。
  - **User-Agent**：客户端（浏览器）标识。
  - **Cookie**：携带此前服务器下发的会话状态。
  - **Content-Type / Content-Length**：请求体的类型与长度。
  - **Accept / Accept-Language**：客户端可接受的内容类型与语言。
- **空行**：标志首部结束。
- **请求体（body）**：携带用户提交的数据，如表单内容；GET 通常无请求体。

> 排障常看首部：**Host 缺失报 400，Content-Length 与实体不符会挂起或截断**。用浏览器开发者工具网络面板可查看完整请求报文。



#### HTTP 响应报文

**HTTP 响应报文**：由服务器返回客户端，格式为**状态行 + 响应首部 + 空行 + 响应体**。

- **状态行**：HTTP/1.1 200 OK 形式的"版本 + 状态码 + 原因短语"。
- **响应首部**：常见有 **Set-Cookie**（下发 Cookie）、**Content-Type**（如 text/html; charset=utf-8）、**Content-Length**、**Location**（重定向目标地址）、**Cache-Control/Expires**（缓存控制）、**Date**（响应时间）。
- **空行**：分隔首部与主体。
- **响应体**：服务器返回的资源内容，如 HTML 页面、图片二进制流、JSON 数据。

> 状态行的三个要素（版本、状态码、短语）缺一不可；**Location 首部通常与 3xx 重定向状态码配合**，告诉浏览器"去新的地址请求"。



#### HTTP 请求方法

**HTTP 方法**：在请求行中指明客户端希望服务器执行的操作，常用的有 GET、POST、PUT、DELETE、HEAD、OPTIONS 等，每种方法都有语义上的"幂等性"。

- **GET**：请求获取指定资源。只读、**幂等**（多次请求结果相同），参数通常放 URL 查询串。
- **POST**：向服务器**提交数据**（如表单、JSON），**非幂等**，数据放请求体，可能创建或修改多个资源。
- **PUT**：用请求体**整体替换**指定资源，幂等。
- **DELETE**：删除指定资源，幂等。
- **HEAD**：只请求**响应首部**、不返回主体，用于探测资源是否存在、检查链接有效性。
- **OPTIONS**：询问服务器**支持哪些方法**，常用于 CORS 预检。

> 高频考点：**GET 幂等（只读）、POST 不幂等（提交）**；浏览器对 GET 与 POST 的缓存、重试行为也不同——POST 重复提交可能造成重复下单，页面刷新时常有"重新提交表单"的确认。



#### 状态码分类

**HTTP 状态码**由三位数字组成，按首位数字归为五类，表明服务器对请求的处理结果。

- **1xx 信息性**：请求已收到、继续处理，如 100 Continue（实际使用较少）。
- **2xx 成功**：200 OK（成功）、204 No Content（成功但无返回内容）。
- **3xx 重定向**：301 Moved Permanently（永久重定向）、302 Found（临时重定向）、304 Not Modified（缓存有效，未修改）。
- **4xx 客户端错误**：400 Bad Request（语法错误）、401 Unauthorized（未认证）、403 Forbidden（已认证但无权限）、404 Not Found（资源不存在）。
- **5xx 服务器错误**：500 Internal Server Error（服务器内部错误）、502 Bad Gateway（网关/代理收到上游无效响应）、503 Service Unavailable（服务暂不可用）。

> 记忆锚点：**"4 开头怪你，5 开头怪我"**；考试要求精确记住的典型码为 200、301/302、304、400/401/403/404、500/502/503。304 在浏览器缓存命中场景极常见。



#### HTTP 的无状态与 Cookie

**HTTP 无状态**：指协议本身不保存"你是谁、你之前干过什么"——每次请求彼此独立，服务器无法仅凭请求认出同一个用户。

- 无状态简化了服务器设计（无需维护会话，易水平扩展），但无法支撑登录态、购物车等需要"记住用户"的业务。
- **Cookie**：是服务器通过响应首部 **Set-Cookie** 下发给浏览器的一段小数据（如会话标识、偏好设置），浏览器之后每次请求都通过 **Cookie 首部**自动带回，从而让服务器"认出"用户。
- Cookie 可能携带隐私信息，**第三方 Cookie**（由非当前站点域名设置的追踪 Cookie）可跨站追踪用户行为，现代浏览器已逐步默认禁用并收紧 SameSite 策略。

> 一句话：**无状态是 HTTP 的出厂设定，Cookie 是给无状态协议"外挂记忆"的标准做法**。有 Cookie 之后服务器仍不保存状态，状态在浏览器手里，这是与 Session 的关键差异。



#### Session 与会话保持

**Session（会话）**：把用户状态**保存在服务器端**，服务器为每个登录用户分配唯一的 **SessionID**，通常通过 Cookie 下发给浏览器，浏览器后续请求带上该 ID，服务器据此找到对应的会话数据。

- 典型流程：登录成功后服务器创建 Session 并回 Set-Cookie（内容是 SessionID）→ 浏览器保存 → 之后每次请求带 Cookie → 服务器按 SessionID 查出会话。
- 若浏览器禁用 Cookie，可把 SessionID 放到 URL 参数或隐藏表单字段中（安全性下降，易泄露）。
- 分布式场景需把 Session 放入共享存储（Redis 等）或用 JWT 等无状态令牌，否则服务器扩容后用户会被"登出"。

Cookie 与 Session 的对比：

- **存放位置**：Cookie 在**客户端**；Session 在**服务器端**。
- **安全性**：Cookie 明文可见、可被篡改（重要数据应加密或只放 ID）；Session 数据在服务端更安全，但 SessionID 被窃取（会话劫持）同样危险。
- **容量与性能**：Cookie 大小受限（典型 4 KB）且每次请求都传，增大带宽；Session 只传一个 ID，但占用服务器内存。
- **典型分工**：Cookie 放"非敏感的小偏好"，Session 放"登录态等敏感状态"，二者配合：SessionID 存 Cookie，会话数据存服务端。

> 记忆：**Cookie 是"身份证放在你自己口袋"，Session 是"档案存在柜台，口袋只放凭证号"**。题目问"为什么还要 Session"——因为 Cookie 明文易改、容量小，敏感状态放服务端更可靠。



#### HTTP 版本演进总览

**HTTP 的版本演进**主线是围绕"连接复用、并发、压缩、队头阻塞"不断优化，当前互联网处于 HTTP/1.1 为主、HTTP/2 普及、HTTP/3 快速上线的并存阶段。

- **HTTP/1.0**：非持续连接，每次请求都新建 TCP 连接，开销大。
- **HTTP/1.1**：默认**持久连接**（流水线仅为可选且实际极少启用），解决了连接重建开销，但仍有**队头阻塞**。
- **HTTP/2**：**二进制分帧 + 多路复用**，一条连接并发多个请求，引入 HPACK 首部压缩与服务器推送。
- **HTTP/3**：底层从 TCP 换成 **QUIC**（基于 UDP），彻底摆脱 TCP 层队头阻塞，并内置 TLS 1.3。

> 演进主线一句话：**"连接从每次新建到长期复用，并发从排队到多路，加密与传输从分离到内建"**。面试常要求对比各版本如何解决前一个版本的问题。



#### HTTP/1.1 与队头阻塞

**HTTP/1.1** 的改进集中在连接复用：默认开启**持久连接（keep-alive）**，一次 TCP 连接上可连续传输多个请求/响应，避免了 HTTP/1.0"每资源新建连接"的三次握手开销。

- **流水线（pipelining）**：允许客户端不等前一个响应就连续发出多个请求，理论上提高利用率。
- **队头阻塞（head-of-line blocking）**：由于响应必须**按请求顺序**返回（要求按序，否则客户端无法把响应和请求对应），若第一个请求处理很慢，后面所有响应都要排队等待——队头阻塞是 HTTP/1.1 最突出的性能问题。
- 流水线因实现复杂、易被代理中断，实际普及度低，多数浏览器默认关用。
- 缓解手段：域名分片（一个页面开多个域名并行建多条连接）、合并请求与雪碧图等，都是"绕开"而非"解决"队头阻塞。

> 理解队头阻塞：HTTP/1.1 的响应"**必须按序返回**"，慢请求挡道，后面全堵——这是**应用层**的队头阻塞，到 HTTP/2 用多路复用解决。



#### HTTP/2：多路复用与 HPACK

**HTTP/2** 通过把报文拆成**二进制帧**并在**一条 TCP 连接上多路复用多个流（stream）**，实现了并发请求/响应的交错传输，解决了 HTTP/1.1 的应用层队头阻塞。

- **二进制分帧层**：每个报文被拆成 HEADERS、DATA 等帧，帧上带流 ID，可在同一连接上交错发送，接收端按流 ID 重组——响应不再必须按序返回。
- **多路复用**：一条连接并发传输多个请求与响应，大幅减少连接数量与握手开销。
- **HPACK 首部压缩**：用静态表、动态表与哈夫曼编码压缩重复的首部（如 Cookie、User-Agent），显著降低首部传输字节。
- **服务器推送（server push）**：服务器可主动推送客户端可能需要的资源（如 HTML 引用的 CSS/JS），减少往返。
- **遗留问题**：HTTP/2 仍在 **TCP** 之上，TCP 层只要丢一个包，其重传机制仍会阻塞该连接上**所有流**——传输层队头阻塞依旧存在。

> 关键区分：**HTTP/2 解决了"应用层队头阻塞"（响应不用排队），却治不了"TCP 层队头阻塞"（一个丢包卡住整条连接的所有流）**，这正是 HTTP/3 改用 QUIC 的动机。



#### HTTP/3 与 QUIC

**HTTP/3** 把传输层从 TCP 换成 **QUIC**（基于 UDP 实现可靠传输与加密的传输协议），从根上消除了传输层队头阻塞，成为新一代 Web 传输方案。

- **基于 UDP 但自带可靠与拥塞控制**：QUIC 在 UDP 之上重新实现了序号、确认、重传与拥塞控制，并把 **TLS 1.3 加密内建**进握手，省去"TCP+TLS 分两次握手"的开销。
- **彻底解决传输层队头阻塞**：QUIC 的可靠传输**按流独立**进行，某条流丢包只重传该流的数据，不阻塞其他流。
- **0-RTT 快速建连**：对曾经连接过的服务器，可携带缓存凭证直接发送首个请求数据，首包时延更低。
- **连接迁移**：QUIC 连接用**连接 ID** 而非 IP+端口标识，手机从 Wi-Fi 切到 5G 时连接不中断（TCP 遇到 IP 变化只能重建连接）。
- 部署现状：Google、Meta（Facebook）等大型服务已大规模上线 HTTP/3，HTTP/3 与 QUIC 的规范分别由 RFC 9114 与 RFC 9000 定义。

> 演进收束：**1.0 每次新建连接，1.1 持久连接但响应排队，2 多路复用但被 TCP 拖累，3 连 TCP 都换掉（QUIC）**——每一版都在消灭上一版留下的"头"（阻塞点）。



### HTTPS 与 TLS

#### HTTPS 的定位与组成

**HTTPS（HyperText Transfer Protocol Secure）**：是 HTTP 与 **TLS**（Transport Layer Security，安全传输层协议）结合的安全版本，在 HTTP 之下、传输层之上增加一层安全协议，默认使用 **443** 端口，需要由 CA 颁发的数字证书。

- HTTPS 解决了 HTTP 明文传输的三大风险：**窃听**（内容被截获可读）、**篡改**（内容被中间人改动）、**冒充**（无法确认服务器身份）。
- TLS 的前身是网景公司提出的 SSL（Secure Sockets Layer），TLS 是它的标准化继承者，日常混称 SSL/TLS。
- 结构位置：TLS 位于传输层与应用层之间——对应用层而言它是"可靠的安全管道"，对 TCP 而言它只是普通数据。

> 记忆：**HTTPS = HTTP + TLS，端口从 80 换 443，明文换密文，无证换有证**。浏览器地址栏的锁形图标即表示该站点启用了 HTTPS。



#### 加密通信的安全目标

**安全目标**是 HTTPS/TLS 要解决的四个问题：机密性、完整性、身份认证与防重放，各自由不同的密码技术承担。

- **机密性（保密）**：数据加密传输，防止被窃听者读取明文——用**对称加密**（如 AES）加密数据。
- **完整性**：防止数据在传输中被篡改——用**消息认证码（MAC）/哈希**校验，TLS 记录层对每条消息计算并校验。
- **身份认证**：确认服务器（及可选的双向认证中的客户端）确实是声称的那一方——用**证书 + 数字签名**。
- **密钥协商安全与防重放**：握手阶段通过**非对称加密/密钥交换**安全协商对称密钥，并用随机数、序号防止历史报文被重放。

> 分工一句话：**"对称算法加密数据（快），非对称算法与签名完成身份认证和密钥协商，哈希/MAC 保证完整性"**——四种技术各司其职，缺一不可。



#### TLS 握手过程

**TLS 握手**：是客户端与服务器在传输应用数据之前，完成"协商加密套件、验证服务器身份、安全地产生共享密钥"的过程。以最常见的 RSA/ECDHE 密钥交换流程简化描述：

1. **ClientHello**：客户端发送支持的 TLS 版本、**密码套件**列表（如 TLS_AES_128_GCM_SHA256）与客户端**随机数**。
2. **ServerHello**：服务器选定版本与套件，返回服务器随机数；随后发送**证书**（含服务器公钥，及证书链）与 ServerHelloDone。
3. **证书验证与密钥交换**：客户端**验证证书链**（确认由受信 CA 签发、域名匹配、未过期）；随后用服务器公钥加密**预主密钥**（RSA 方式），或参与 **ECDHE** 密钥交换生成预主密钥。
4. **派生会话密钥**：双方用"客户端随机数 + 服务器随机数 + 预主密钥"经伪随机函数**派生会话密钥**。
5. **握手完成**：双方互发 Finished 校验握手消息的完整性，此后**所有应用数据用会话密钥对称加密**传输。

TLS 1.3 的改进：握手压缩到 **1-RTT**（正常情况一个往返即可完成并发送首个应用数据），支持 **0-RTT** 会话恢复；删除 RSA 密钥交换与旧的不安全套件，默认使用支持**前向保密**的 ECDHE。

> 理解要点：**"非对称/密钥交换只用于握手期换钥匙，真正的数据全走对称加密"**——因为对称加密快几个数量级，这是 HTTPS 兼顾安全与性能的经典设计。



#### HTTP 与 HTTPS 的对比

HTTP 与 HTTPS 的对比如下：

- **传输安全**：**HTTP** 明文传输；**HTTPS** 加密传输，对数据加密并建立信息安全通道。
- **默认端口**：**HTTP** 80；**HTTPS** 443。
- **体系位置**：**HTTP** 直接运行在传输层之上（纯应用层）；**HTTPS** 在应用层与传输层之间多了一层 TLS/SSL 安全机制。
- **证书与认证**：**HTTP** 无需证书；**HTTPS** 需要 CA 颁发的 SSL/TLS 证书，并对服务器做**真实身份认证**，防止仿冒站点。
- **安全性**：**HTTPS** 可防窃听、防篡改、防冒充，明显更安全。
- **性能开销**：**HTTPS** 握手增加 RTT、加解密消耗 CPU；通过会话复用、TLS 1.3、硬件加速可大幅缓解。
- **搜索引擎与信任标识**：**HTTPS** 对搜索引擎更友好（利于 SEO），浏览器对合规站点显示绿色锁形安全标识；HTTP 明文站点常被标记"不安全"。

> 结论：**"能用 HTTPS 就不用 HTTP"** 已是业界共识——搜索引擎降权、浏览器告警、中间人风险三方面都倒逼全站 HTTPS，证书签发（Let's Encrypt）也已免费自动化，成本不再是理由。
