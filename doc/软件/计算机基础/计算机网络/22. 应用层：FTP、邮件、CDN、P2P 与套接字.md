## 应用层：FTP、邮件、CDN、P2P 与套接字

### FTP 文件传输协议

#### FTP 的定位与工作特点

**FTP（File Transfer Protocol，文件传输协议）**：是用于在互联网上**传输文件**的应用层协议，基于 TCP 提供可靠传输，负责把文件在客户与服务器之间复制，而不关心文件的格式与内容。

- 与 HTTP 的区别：HTTP 主要取回网页资源，FTP 专门做文件的上传与下载，支持断点续传、目录浏览等文件操作。
- FTP 最大的结构特点是**控制连接与数据连接分离**：控制信息用一条长期连接带外传送，文件数据另用按需建立的连接传送。
- FTP 服务器默认监听 **21 端口**（控制连接），数据连接视工作方式使用 20 端口或临时端口。

> 记忆：**FTP 是"一个会话、两条连接"**——控制连接负责说"我要什么文件"，数据连接负责真传数据，两者分离是 FTP 与多数单连接协议最大的不同。



#### 控制连接与数据连接的分离

**控制连接（control connection）**：客户端主动与服务器 21 端口建立、**在整个会话期间保持**的 TCP 连接，用于传送命令（如 USER、PASS、RETR、STOR）与应答，不传文件内容。

**数据连接（data connection）**：仅在**每次传输文件或列目录时按需建立**、传完即关闭的 TCP 连接，用于实际搬运文件数据。

- 控制连接先建立、全程存活，但数据量小；数据连接按需建立、传完就断，可频繁创建。
- 因为命令在"带外"通道传送，FTP 也被称为**带外控制**协议（对比 SMTP 等命令与数据同通道的带内控制）。
- 数据连接由谁发起，取决于 FTP 的工作方式：**主动方式（PORT）**或**被动方式（PASV）**。

> 理解：**控制连接像"对讲机"，数据连接像"货梯"**——对讲机全程开机下达指令，货梯只在搬货时开、搬完即停。



#### PORT 主动方式

**主动方式（PORT / active mode）**：数据连接由**服务器主动发起**连接客户端。流程如下：

1. 客户端先与服务器的 21 端口建立控制连接。
2. 需要传数据时，客户端在控制连接上用 PORT 命令告知服务器："我这边打开了 XXXX 端口，请你来连我。"
3. 服务器用**自己的 20 端口**主动向客户端的 XXXX 端口发起数据连接。

- 此方式下服务器必须能"主动外连"客户端的临时端口。
- 局限：客户端若处于 **NAT 或防火墙之后**（内网私有地址、防火墙拦截外部主动连接），服务器将无法连回客户端的监听端口，导致数据连接失败。

> 记忆要点：**主动模式名字虽叫"主动"，其实动作上是"服务器主动连客户端"**。考场景判断题——客户端在内网（NAT 后）时，主动模式往往失败，应改用被动模式。



#### PASV 被动方式

**被动方式（PASV / passive mode）**：数据连接由**客户端主动发起**连接服务器。流程如下：

1. 客户端先与服务器的 21 端口建立控制连接。
2. 需要传数据时，客户端在控制连接上发送 PASV 命令。
3. 服务器开启一个临时端口（通常大于 1024），在控制连接上回复："我打开了 XXXX 端口，请来连我。"
4. 客户端主动向服务器的 XXXX 端口发起数据连接。

- 此方式下服务器的**21 端口仍由客户端主动连接**、数据端口也由客户端主动连接，服务器无需"反向"连回客户端，因此能穿透客户端一侧的 NAT/防火墙。
- 这是浏览器与下载工具**默认使用被动模式**的原因。
- 服务器侧需要放行其临时端口范围（防火墙配置），否则被动模式也会失败。

> 对比记忆：**主动（PORT）是"服务器连客户端"，被动（PASV）是"客户端连服务器"**；内网/防火墙后的客户端一律选被动，这也是现代默认。匿名 FTP 使用用户名 anonymous、密码任意（惯例为邮箱）。



### 电子邮件系统

#### 电子邮件的组成与工作流程

**电子邮件系统**由三部分组成：**用户代理（User Agent，UA）、邮件服务器、邮件协议**；整体采用"存储转发"的工作方式，而不是实时直连投递。

- **用户代理**：用户撰写、阅读、管理邮件的客户端程序，如 Outlook、Foxmail、网页邮箱。
- **邮件服务器**：既管接收又管发送，为每个用户维护**邮箱（mailbox）**存放来信，并维护**报文队列（message queue）**暂存待发的邮件。
- **协议分工**：发送与服务器间中继用 **SMTP**（"推"），用户从自己邮箱取信用 **POP3 或 IMAP**（"拉"），Webmail 则通过浏览器走 HTTP/HTTPS。
- 工作流程：发件人 UA 用 SMTP 把邮件推到自己的发送服务器 → 发送服务器经 SMTP 中继转发到收件人的接收服务器 → 收件人 UA 用 POP3/IMAP 从接收服务器取信。

> 记忆链条：**"推上自己的服务器、中继到对方服务器、拉回自己的电脑"**——SMTP 管"送"（前两跳），POP3/IMAP 管"取"（最后一跳）。邮件地址形如 用户名@域名，@ 后是收件人所在域。



#### SMTP：发送与中继的"推"协议

**SMTP（Simple Mail Transfer Protocol，简单邮件传输协议）**：负责把邮件从用户代理"推"到发送方邮件服务器、并从一个邮件服务器"推"到另一个邮件服务器，默认端口 **25**，基于 TCP 建立可靠连接。

- 通信模型：发送方作为客户端，向接收方服务器发起 TCP 连接，用 ASCII 命令交互（如 HELO/EHLO、MAIL FROM、RCPT TO、DATA、QUIT），服务器回三位的状态码。
- 限制：SMTP 最初**只能传输 ASCII 文本**，二进制与多媒体内容需要靠 **MIME** 扩展编码后传输。
- 端口细化：
  - **25**：服务器之间的**中继转发**（现代运营商常封锁普通用户的 25 端口防垃圾邮件）。
  - **587（Submission）**：用户代理向邮件服务器"提交"邮件的标准端口，通常要求认证。
  - **465（SMTPS）**：SMTP over SSL，从一开始就加密。

> 考点：SMTP 是**"推"协议**——发送方主动推送，双方都必须在线；邮件传输依赖 TCP，属于可靠连接。它只关心"把信送到对方的邮件服务器"，不管收件人是否正在阅读。



#### MIME 的作用

**MIME（Multipurpose Internet Mail Extensions，多用途互联网邮件扩展）**：是为弥补 SMTP"只能传 ASCII 文本"而设计的扩展标准，允许邮件携带非 ASCII 文本、图片、音频、视频等附件。

- 扩展手段：新增 MIME 首部（Content-Type、Content-Transfer-Encoding、Content-Disposition 等）说明正文结构与编码方式。
- 编码方式：**Base64** 把二进制数据编码为 ASCII 字符（用于附件），**quoted-printable** 处理以 ASCII 为主、少量非 ASCII 的文本（用于国际字符正文）。
- **多部分（multipart）**结构：一封邮件可包含纯文本、HTML、多个附件，用边界字符串分隔。

> 一句话：**MIME 是 SMTP 的"包装术"**——SMTP 只会搬 ASCII，MIME 把任何内容都打扮成 ASCII 让它搬得动，接收端再按 Content-Type 还原。



#### POP3：脱机拉取协议

**POP3（Post Office Protocol version 3，邮局协议第 3 版）**：是用户代理从邮件服务器**取信**的协议，默认端口 **110**（加密版 POP3S 为 995），支持 C/S 结构的**脱机（offline）工作模型**。

- 工作方式：用户把服务器上的邮件**下载到本地主机**，之后**可选择删除服务器上的副本**，再离线阅读、管理——因特网电子邮件最早的离线标准。
- 简单性：服务器端的邮箱管理功能很少（基本是"取走即清"），适合单设备用户。
- 常用命令：USER、PASS、STAT、LIST、RETR（取某封）、DELE（删某封）、QUIT。
- 局限：邮件一旦被取走/删除，其他设备（手机、另一台电脑）就看不到；多设备同步体验差。

> 对比记忆：**POP3 是"把信从邮局搬回家再慢慢看"（脱机），IMAP 是"信一直留在邮局、想查哪封取哪封"（联机）**。现代多设备场景基本用 IMAP。



#### IMAP：联机同步协议

**IMAP（Internet Message Access Protocol，互联网报文访问协议）**：也是取信协议，但把邮件**保留在服务器上**，客户端只是"查看服务器上的邮件"，默认端口 **143**（加密版 IMAPS 为 993）。

- **多设备同步**：手机、电脑、网页邮箱看到的是服务器上的同一份邮件，删除/已读状态跨设备一致。
- **文件夹管理**：可在服务器端建文件夹（收件箱、已发送、归档等）并移动邮件。
- **部分收取**：可只取邮件的首部或部分内容（大附件可暂不下载），按需取信、节省流量。
- 协议状态机复杂于 POP3，服务器需要保存与同步更多状态。
- Webmail（163、Gmail 网页版）实质由邮件服务商后端经 HTTP/HTTPS 提供服务，用户代理是浏览器。

> 选型建议：**"只在一台电脑收信、想要离线归档"用 POP3；"手机电脑多端同步、邮件量大"用 IMAP**。安全上两者都建议走加密端口（995/993）防窃听。



#### 邮件寻址与 MX 记录

**邮件寻址**依赖 DNS 的 **MX 记录**：发件方服务器要投递到 收件人@example.com 时，先查询 example.com 的 **MX 记录**，得到负责收信的**邮件服务器主机名**，再查询该主机名的 A/AAAA 记录获得 IP，最后用 SMTP 投递。

- MX 记录带**优先级**数字：数字越小优先级越高，主服务器故障时按优先级轮换备用服务器。
- MX 记录是"域 → 邮件服务器"的映射，与网页的 A/CNAME 记录相互独立——收信服务器可以跟网站服务器完全不同。

> 链路记忆：**发邮件 = 先 DNS 找 MX → 再 A 找 IP → 然后 SMTP 推送**。考题若问"对方邮箱收不到信、但域名能打开网站"，常与 MX 记录缺失或配置错误有关。



#### 垃圾邮件治理：SPF、DKIM、DMARC

**垃圾邮件治理**围绕"验证发件人身份、防止伪造发件地址"展开，主流技术是三道建立在 DNS TXT 记录之上的防线：**SPF、DKIM、DMARC**。

- **SPF（Sender Policy Framework）**：域管理员在 DNS TXT 记录中声明"哪些服务器 IP 有权以本域名义发信"；收件方校验发件 IP 是否在名单内，防止伪造发件域。
- **DKIM（DomainKeys Identified Mail）**：发件服务器用**域私钥**对邮件做数字签名，签名随邮件送达；收件方用 DNS 公布的**公钥**验签，证明"邮件确实来自该域且未被篡改"。
- **DMARC（Domain-based Message Authentication, Reporting & Conformance）**：在 SPF/DKIM 之上发布策略，告诉收件方"验证失败的信怎么处理"（放行/隔离/拒收），并把结果汇报给域管理员。
- 其它辅助手段：黑白名单、贝叶斯内容过滤、发送频率限制、验证码与人机识别等。

> 记忆层级：**SPF 认"发件 IP 对不对"，DKIM 认"签名真不真"，DMARC 定"不合格怎么办"**。三道记录都发布在 DNS TXT 里，是域名反垃圾与反钓鱼的基础配置。



### 流媒体与 CDN

#### 流媒体的存储播放与边下边播

**流媒体（streaming media）**：指音视频内容经**压缩编码**后分块存储、边下载边播放的传输方式。典型编码有视频的 H.264/H.265 与音频的 AAC 等。

- **边下边播**：客户端播放器在本地**缓冲（buffer）数秒**内容，用缓冲平滑网络抖动，避免因瞬间延迟卡顿。
- 音视频文件通常切分为**小分块（chunk/segment）**存放（每个分块数秒时长），便于按需请求与码率切换。
- 与"先下载后播放"对比：流媒体可即时开始播放、节省本地存储，但要求稳定的带宽与延迟。

> 理解：流媒体不是"等整个文件下完再放"，而是**"边下边放 + 缓冲兜底"**——缓冲是播放流畅度与启动延迟之间的折中。



#### DASH：客户端自适应的分块流

**DASH（Dynamic Adaptive Streaming over HTTP，基于 HTTP 的动态自适应流）**：把同一视频编码为**多档码率**（如 480p/720p/1080p），并提供清单文件（manifest，如 DASH 的 MPD），让客户端**实时测量带宽并动态请求合适码率**的分块。

- 清单文件描述各码率分块的 URL 与时长，客户端"点菜式"地按需请求。
- **客户端自适应（client-driven）**：选什么码率由**客户端**根据实时网络状况决定——网好要高清分块，网差降级要低码率分块，实现播放不中断的"无级变速"。
- 同类技术：Apple 的 **HLS**（用 m3u8 清单）与 DASH 思路一致，是当前视频网站主流的自适应流方案。

> 记忆：**DASH 的关键词是"多档码率 + 清单 + 客户端测速选档"**。它与老式"服务器端转码推单一码率"最大的不同在于：决定权在客户端，天然适配网络波动。



#### RTP、RTCP 与 RTSP 辅助协议

围绕实时媒体传输还有三个常见协议家族，与流媒体/实时通信配套使用：

- **RTP（Real-time Transport Protocol，实时传输协议）**：承载**实际媒体数据**（音视频净荷），常运行在 **UDP** 之上，为每个分组提供**序号与时间戳**，供接收端排序与定时播放。RTP 本身不保证可靠交付。
- **RTCP（RTP Control Protocol，RTP 控制协议）**：与 RTP 配套的**质量反馈**通道，周期性地在会话成员间交换收发统计（丢包率、抖动、往返时延），供应用调整编码或诊断，本身不传媒体数据。
- **RTSP（Real Time Streaming Protocol，实时流协议）**：相当于流媒体的"**遥控器**"，用类似 HTTP 的文本命令控制媒体会话，支持 PLAY、PAUSE、TEARDOWN 等操作；媒体数据本身仍由 RTP 传送。

> 分工口诀：**"RTP 扛货（媒体数据），RTCP 报路况（质量反馈），RTSP 当遥控器（播放控制）"**。媒体走 UDP 求实时，控制走可靠通道求稳定。



#### CDN 的工作原理与定位

**CDN（Content Delivery Network，内容分发网络）**：把内容**复制并缓存到部署在网络边缘的大量服务器**上，让用户从"离自己最近的边缘节点"获取内容，从而缓解源站压力、降低时延、提升可用性。

- **边缘部署**：CDN 服务商在各地（尤其各 ISP 接入网内）部署缓存节点，把热点内容推向用户身边。
- 作用收益：源站只需被少量回源请求访问；用户侧响应更快、更稳定；遭遇突发流量时由海量节点分摊，具备抗拥塞能力。
- 适用对象：静态资源（图片、CSS/JS、视频）、下载、网页加速、动态加速等各类内容。

> 一句话定位：**CDN = "把内容搬到离用户最近的地方，再把用户调度到那里去拿"**。它让"数据中心在千里之外"的用户也能获得"内容就在隔壁"的体验。



#### 内容分发与注入方式

CDN 在"往哪放、怎么放"上有两类技术选择：

- **分发部署（放哪里）**：
  - **enter-deep（深入部署）**：把节点放到 ISP 接入网深处，离用户最近、体验最好，但节点数量多、维护成本高。
  - **bring-home（集中部署）**：只在少数关键位置（大型 IXP/数据中心）部署集群，成本低、好维护，但离部分用户较远。
- **内容注入（何时有内容）**：
  - **pull（拉取/回源）**：用户首次访问未命中时，边缘节点**回源站取内容并缓存**，之后命中缓存直接返回。实现简单、自动适应访问热点。
  - **push（推送/预热）**：源站提前把热点内容**主动推送到各边缘节点**，用户访问时直接命中；适合可预见的大热点（如新剧上线）。

> 记忆：**enter-deep 求"近"、bring-home 求"省"；pull 是"用到才取"，push 是"提前铺货"**。现实中两者常混用：大热点用 push 预热，长尾内容靠 pull 按需缓存。



#### CDN 的调度机制：DNS、Anycast 与 302

**CDN 调度（重定向）**指把用户请求导向最合适的边缘节点，常见三种实现机制：

- **DNS 调度**：CDN 改造权威 DNS——用户解析某个 CDN 域名时，权威 DNS 根据发起查询的**本地 DNS 位置**（配合 EDNS Client Subnet 可获得更精确的用户网络）返回**距离最近的边缘节点 IP**。这是最主流、对用户最透明的方式。
- **Anycast 调度**：多个边缘节点广播**同一个 IP**，互联网路由器按 BGP 路由自动把用户流量送到**拓扑上最近**的节点；无需逐用户计算，天然容灾。
- **302 重定向调度**：用户的请求先到某个调度服务器，由它根据用户 IP 等信息返回 **HTTP 302**（Location 指向最优边缘节点 URL），浏览器再去请求边缘节点。
- 附加角色：边缘节点可**终结 TLS**、承载 HTTP/2 与 HTTP/3（QUIC），是新一代 Web 协议大规模落地的重要推动者。

> 记忆：**DNS 调度"算好了告诉你地址"，Anycast 调度"全网同一地址、路由自己选近道"，302 调度"先登录、再指路"**。三者都服务于"把用户领到最近的节点"这一目的。



### P2P 文件分发

#### P2P 文件分发与 BitTorrent

**BitTorrent**：是最具代表性的 P2P 文件分发系统，把大文件切分成固定大小的**块（chunk/piece）**，众多参与下载的节点（对等方）**彼此互相上传已获得的块**，使整体下载能力随参与者增加而增长。

- 文件发布方生成一个**洪流（torrent）元数据**（含文件分块信息与 Tracker 地址）；参与者据此加入"洪流"。
- **Tracker 服务器**维护当前正在下载该文件的节点列表；无 Tracker 的环境由 **DHT**（分布式哈希表）承担"找对等方"的职责。
- 下载过程：一个节点同时从**多个对等方并行下载不同块**，同时把自己已拥有的块上传给其他对等方——"边下边传"，下载速度越快、贡献也越大。
- 与 C/S 分发对比：C/S 分发总量受服务器带宽上限约束、用户越多每个用户分到的越慢；P2P 分发中每个新节点都贡献上传带宽，用户越多分发越快。

> 一句话：**BitTorrent 让"下载者"同时也是"上传者"，把单点瓶颈打散成全网互助**。这也是版权与安全争议的根源——P2P 天然难以监管。



#### 最稀有优先与 tit-for-tat

BitTorrent 靠两个核心策略保证整体高效与节点公平：

- **最稀有优先（rarest first）**：优先请求当前**持有副本最少**的块。作用是防止某些块只在极少数节点手里、这些节点一旦离线全 torrent 都无法完成——"先把最稀缺的补齐"，提升整体健壮性。
- **tit-for-tat（以牙还牙/对等激励）**：优先向"给自己上传最多"的邻居上传，即"你帮我传、我就帮你传"。作用是**激励上传、惩罚白嫖（free-rider）**——只下不上的节点会被其他节点"choke"（拒绝上传），很难下完。
- 为防止"只跟老邻居互传、错过新节点"，节点会周期性**乐观解除阻塞（optimistic unchoke）**，随机给某个陌生节点上传，以探测更好的交易对象。

> 记忆：**最稀有优先解决"块可用性"（防死锁），tit-for-tat 解决"人积极性"（防白嫖）**。两个策略一个管数据、一个管人心，是 P2P 系统的灵魂。



#### DHT 与结构化/非结构化 P2P

**DHT（Distributed Hash Table，分布式哈希表）**：是一种结构化的 P2P 查找技术，把"键 → 值"的映射（如"信息哈希 → 拥有该文件的节点地址"）**分散存储在全体节点上**，任何节点都可在 O(log N) 级跳数内找到持有该键的节点。

- **结构化 P2P**：节点与键都被映射到同一个标识空间，按规则组织成拓扑（如 **Chord** 的环、**Kademlia** 的异或距离），查找有确定的路由路径，可扩展性好。Kademlia 是 BitTorrent DHT、以太坊等广泛采用的实现。
- **非结构化 P2P**：节点随意相连，没有固定组织，查找靠**泛洪（flooding）**把查询广播给所有邻居（Gnutella）或**随机漫步**（random walk），简单但查询开销随规模增长大。
- 应用延伸：区块链（各节点同步账本）、去中心化存储（IPFS、Sia）等都建立在 DHT/结构化 P2P 思想上。

> 对比记忆：**结构化 P2P 是"有组织、查得快"，非结构化 P2P 是"靠广播、简单但费流量"**。做题判断——要大规模确定性查找选 DHT（Kademlia/Chord），小规模网络才考虑泛洪式非结构化方案。



### 套接字编程简介

#### 套接字 API 与编程模型

**套接字（socket）编程**：是应用进程使用操作系统提供的网络 API 收发数据的标准方式。本处"套接字"指编程接口（socket() 函数族）而非 IP 加端口的通信端点，两者语境不同。

- 一次网络通信的双方仍是"客户/服务器"：**服务器先启动、被动等待**，**客户端主动发起连接或发送**。
- 核心流程都由一组系统调用完成，TCP 与 UDP 的调用序列不同——TCP 需要建立连接，UDP 直接发数据报。
- 下面以类 Unix 系统调用名描述通用顺序，各种语言（C、Java、Python 等）都提供对应的封装。

> 术语提醒：**"socket"既是"端点标识"又是"API"**。看书时看到"套接字 = IP 加端口"是前者，看到"调用 socket() 函数"是后者，务必区分。



#### TCP 套接字通信流程

**TCP 套接字**是面向连接的编程模型，服务器与客户端各自遵循固定的调用顺序，API 调用与三次握手一一对应。

- **服务器端顺序**：socket() 创建套接字 → bind() 绑定 IP 与端口 → listen() 转为监听、等待连接 → accept() 接受连接（阻塞直到有客户端连入）→ 用 recv()/send() 收发数据 → close() 关闭。
- **客户端顺序**：socket() → connect() 发起连接（触发三次握手）→ send()/recv() → close()。

```text
TCP 服务器                           TCP 客户端
socket()                             socket()
bind()
listen()
accept()  ←— 阻塞等待 —————— connect()（三次握手）
  |           建立连接成功              |
recv()  ←———————— send()
send()  ————————→  recv()
close()                            close()
```

- accept() 每次返回一个**新的连接套接字**，服务器常用多线程/事件循环处理多个并发连接。
- 数据传输是字节流，应用需自行处理消息边界。

> 对应关系：**connect() 触发第一次握手，内核在握手完成后才让 connect 返回；accept() 取出已完成握手（ESTABLISHED）的连接**。客户端三次握手由内核自动完成，编程者只需调用 API。



#### UDP 套接字通信流程

**UDP 套接字**无需建立连接，收发数据报只靠两个函数，流程比 TCP 简单得多。

- **服务器端**：socket() → bind()（绑定端口，固定接收地址）→ 循环用 recvfrom()/sendto() 收发数据报。
- **客户端**：socket() → 直接 sendto()/recvfrom()，通常无须 bind（由内核自动分配源端口），也无须 connect。

```text
UDP 服务器                           UDP 客户端
socket()                             socket()
bind()
recvfrom() ←— 阻塞等待 ————— sendto()
sendto()   ————————→  recvfrom()
close()                            close()
```

- sendto()/recvfrom() 每次调用都要携带**对端地址**（因为无连接，内核不知道该"发给谁/来自谁"）。
- UDP 套接字可选调用 connect()，作用不是建立连接，而是**固定通信对端**，此后可用 send()/recv()，并只接收该对端的报文（用于过滤）。

> 核心区别：**TCP 要先"接线"（connect/accept）再传，UDP "拿起话筒就喊"（sendto 带地址）**。UDP 编程虽简单，但丢包、乱序、消息边界都由应用自行处理。



#### 套接字编程常见问题

套接字编程的典型坑与对策：

- **端口被占用**：bind() 报"Address already in use"——前一个进程未释放端口，或大量 TIME_WAIT 残留；可设置地址复用选项，或等待/缩短 TIME_WAIT。
- **accept 队列溢出**：并发连接超过 listen() 的 backlog 时新连接被拒，表现为握手成功但应用无响应；应加大 backlog 或优化处理速度。
- **TCP 粘包/拆包**：应用写入与内核发送不对齐，接收方需按长度前缀或分隔符切分消息。
- **UDP 报文过大触发 IP 分片**：应控制单报文小于路径 MTU（典型 1400 字节左右），避免分片丢失导致整报作废。
- **阻塞与非阻塞/超时**：默认套接字是阻塞的，服务端不设置超时可能被慢客户端拖死；用非阻塞模式或设置收发超时。

> 调试建议：先用两个本机脚本做最小收发，再用 netstat/lsof 看端口监听，最后用 Wireshark 抓包核对握手与报文——套接字程序的 bug 大多能在报文层面一眼定位。
