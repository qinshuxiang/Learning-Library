## UDP

### 传输层概述

#### 传输层的地位与作用

**传输层（transport layer）**：是体系结构中位于网络层之上、应用层之下的层次，提供**进程到进程（端口到端口）**的端到端逻辑通信，负责把应用进程产生的数据可靠或尽力地交付给**主机上正确的应用程序**。

- 网络层只负责**主机到主机**：IP 协议按目的 IP 把分组送到目标主机，但主机上有多个进程（如浏览器、邮件客户端同时运行），网络层不区分数据属于谁。
- 传输层补上"最后一步"：用**端口号**区分主机内的不同进程，把收到的数据按目的端口交付给对应的应用进程。
- 传输层面向**端到端（end-to-end）**：传输连接只在通信的两个端系统之间有意义，中间路由器只按网络层转发，不感知传输层连接。
- 传输层还提供差错检测（校验和）、流量控制、拥塞控制等服务，弥补网络层"尽力而为"的不足。

> 分层视角的速记：**网络层负责"把分组送到哪台主机"，传输层负责"把数据交给主机上哪个进程"**。前者是"找门牌号"，后者是"找房间号"。



#### 传输层使用的两种协议

**TCP（Transmission Control Protocol，传输控制协议）**：是面向连接的、可靠的传输协议，提供按序、不丢、不重的字节流交付；**UDP（User Datagram Protocol，用户数据报协议）**：是无连接的、尽最大努力交付的传输协议，不保证可靠与按序。

- **TCP**：适合网页浏览、文件传输、电子邮件等对可靠性要求高的应用，付出的代价是首部开销大（20~60 字节）、需维护连接状态。
- **UDP**：适合实时音视频、域名查询等对时延敏感、能容忍个别丢失的应用，开销极小（首部仅 8 字节）。
- 两种协议都运行在 IP 之上，IP 首部中的**协议号**字段用于分用：值为 6 表示上层是 TCP，值为 17 表示上层是 UDP。

> 面向连接的比喻：**TCP 像"打电话"（先拨号接通再说话，说错可重说），UDP 像"寄明信片"（写好就投递，丢了不补）**。



#### 复用与分用

**复用（multiplexing）**：发送方多个应用进程共享同一个传输层协议，各自的应用数据被加上端口等信息封装后共同交给下面的网络层；**分用（demultiplexing）**：接收方传输层根据报文中的端口号，把收到的数据正确地交付给对应的应用进程。

- **发送方向看复用**：一台主机上同时开着浏览器、邮件客户端、即时通信软件，多个进程产生的数据都要走传输层，传输层为每个进程的数据分别加上"源端口、目的端口"后交给 IP 层发送。
- **接收方向看分用**：主机收到一个报文段后，检查**目的端口号**，例如目的端口为 80 的数据交给 HTTP 服务器进程，为 25 的交给邮件服务器进程。
- 分用得以成立的依据正是端口号——**端口号是传输层服务访问点（TSAP）**，是传输层与上层应用之间的接口。

> 记忆要点：**"复用"是把多股流合成一股往网络里送，"分用"是把收到的一股流拆开送给不同进程**。发送端复用、接收端分用，两端配合完成进程间通信。



#### 端口号与三类端口

**端口号（port number）**：是一个 16 位的二进制数（范围 0~65535），用于在一台主机上标识不同的应用进程，是传输层实现复用与分用的依据。

- **熟知端口（well-known port）0~1023**：分配给全球公认的重要应用，由 IANA 统一分配，用户进程一般不使用：
  - FTP 数据 20／控制 21、SSH 22、Telnet 23、SMTP 25、DNS 53、HTTP 80、POP3 110、HTTPS 443。
- **登记端口（registered port）1024~49151**：供普通应用向 IANA 登记后使用，避免端口冲突。
- **短暂端口（ephemeral port）49152~65535**：客户端进程发起通信时，由操作系统**临时分配**，通信结束即释放，用作本次通信的**源端口**。

> 端口速记口诀：**"21 传文件、22 管远端、25 发邮件、53 查域名、80 看网页、443 上加密网站"**。记忆时注意：服务器进程使用熟知端口并长期监听，客户端进程使用短暂端口随用随分。



#### 套接字与连接的四元组

**套接字（socket）**：是 IP 地址与端口号的组合，写作"IP 地址:端口号"的形式，在网络中唯一标识一个**端点上**的应用进程。

- 一个套接字唯一确定"一台主机上的一个进程"，例如 203.0.113.5:80 表示某服务器上的 HTTP 服务。
- 一条 **TCP 连接**由**四元组（源 IP、源端口、目的 IP、目的端口）**唯一标识，两端各有一个套接字，通信双方都知道对方的 IP 与端口才能建立连接。
- 不同主机可以使用相同的端口号，因为套接字中的 IP 地址已经把它们区分开，这就是"端口号只需在主机内唯一"的原因。

> 术语辨析：**套接字**在不同语境有两个含义——网络层语义上是"IP 加端口"的通信端点标识；编程语境上还指操作系统提供的一组网络编程接口（socket() 函数族，见第 22 章）。考试中通常取前者，编程题中取后者。



### UDP 协议

#### UDP 的定位与主要特点

**UDP（User Datagram Protocol，用户数据报协议）**：是一种**无连接的、不可靠的、尽最大努力交付**的传输协议，应用进程把数据报交给 UDP 后，UDP 只负责"尽快把报文送上网络"，不保证对方能收到、收到后按序。

UDP 的主要特点：

- **无连接**：发送数据前不需要建立连接（无握手），减少了时延。
- **尽最大努力交付**：不保证可靠交付，不维护复杂的连接状态表。
- **面向报文**：对应用层报文既不合并也不拆分，保留报文边界。
- **无拥塞控制**：网络拥塞时 UDP 不会主动降低发送速率。
- **支持多种通信方式**：一对一、一对多、多对一、多对多均可。
- **首部开销小**：首部仅 8 字节（TCP 最少 20 字节），且没有拥塞控制意味着吞吐不受调节，只受应用产生数据的速率、传输带宽与主机性能限制。

> 一句话定位：**UDP 是"想发就发、丢了不管"的极简传输协议**——它把控制开销降到最低，把实时性与灵活性留给应用自己把握。凡是"等不起重传、丢一两包无妨"的场景，正是 UDP 的主场。



#### 无连接与尽最大努力交付

**UDP 的无连接**：指通信双方在传输数据前不交换任何建立连接的握手报文，发送进程随时可以把数据报交给 UDP，UDP 封装后立即交给 IP 层发送，通信结束也无须释放连接。

- 发送方不需要记住"对面是谁、当前连接处于什么状态"，每个数据报独立封装、独立路由，可能走不同路径到达。
- 接收方也不必为每条会话维护状态，收到报文后按目的端口分用即可，因此一台 UDP 服务器可以轻松同时服务大量客户端。
- **尽最大努力交付**的体现：若报文在传输中出错或被丢弃，UDP 既不检测也不重传，是否要处理丢包完全由应用程序自行决定（例如音视频应用选择"丢掉重来一帧"，而不是等待重传）。

> 辨析：无连接不等于"不能收发数据"，而是"收发前无开销、出错后无兜底"。正因为省掉了握手与状态维护，UDP 的时延与资源占用远小于 TCP。



#### 面向报文的特性

**UDP 面向报文**：指 UDP 对应用层交付下来的报文**既不合并也不拆分**，只加上 8 字节首部就向下交给 IP 层，一次交付的报文以"报文"为整体在网络上传输。

- 发送方：应用程序给多少数据，UDP 就封装成一个用户数据报发出去，多个小报文不会被攒成一个再发。
- 接收方：UDP 一次向应用程序交付一个完整的报文，**报文边界被保留**，接收方读一次就是一个完整报文，不存在 TCP 那种"粘包"问题。
- 对应用程序的约束：应用必须选择**大小合适**的报文——报文过长时 IP 层会分片，增大丢失概率与开销；报文过短时首部占比高、浪费带宽。
- 一般认为用户数据报应小于 IP 数据报的长度，避免 IP 分片。

> 对比记忆：**TCP 面向字节流，报文之间"没有边界"，应用需自行划分消息；UDP 面向报文，"一条是一条"，天然有界**。若应用本身有明确的消息边界（如 DNS 查询、DHCP 交互），用 UDP 最省事。



#### UDP 首部格式

**UDP 用户数据报首部固定 8 字节**，由四个 16 位字段组成，位于 IP 数据报的数据部分之前。

- **源端口**（16 位）：发送方进程的端口号。在不需要对方回信时（如单向探测）可置为 0。
- **目的端口**（16 位）：接收方进程的端口号，是接收端做**分用**的依据。
- **长度**（16 位）：UDP 用户数据报的总长度（首部 8 字节 + 数据部分），以字节为单位。最小值为 8（表示数据部分为 0），最大值为 65535。
- **校验和**（16 位）：检测整个 UDP 用户数据报（首部 + 数据）在传输中是否出错，计算时还要加上伪首部。在 IPv4 下该校验和是可选的（置 0 表示不校验），但实际实现普遍启用；在 IPv6 下为**强制**字段。

> 字段识记：**"源目的、长度、校验"共 8 字节、每项 16 位**。长度字段是必需的——IP 层交付的数据末尾可能带填充字节，仅靠 IP 首部长度字段无法精确切出 UDP 数据的边界，必须由 UDP 长度字段指明。



#### 伪首部与校验和

**伪首部（pseudo header）**：是在计算 UDP 校验和时临时添加在用户数据报之前的 12 字节虚拟首部，**只参与校验和计算、不随报文传输**，也不计入 UDP 长度字段。

伪首部的组成（12 字节）：

- **源 IP 地址**（4 字节）：来自 IP 数据报首部。
- **目的 IP 地址**（4 字节）：来自 IP 数据报首部。
- **保留字节**（1 字节）：置 0。
- **协议号**（1 字节）：UDP 为 17，TCP 为 6。
- **UDP 长度**（2 字节）：即 UDP 首部加数据的总长度。

校验与出错处理要点：

- 校验方法：把伪首部与 UDP 用户数据报一起按**二进制反码求和**，结果填入校验和字段；接收方做同样的反码求和，结果为全 1 则判定无误。
- **添加伪首部的目的**：把"IP 地址"与"协议号"也纳入检错范围，防止报文因路由错误被送到错误的主机或错误的协议栈，接收端却仍然接受。
- UDP 校验覆盖首部与数据（比只查首部的 IP 校验更彻底）；发现差错时 UDP 通常**静默丢弃**，不通知发送方。
- 对比：TCP 校验和也使用伪首部（其中协议号为 6），且是**强制**校验；IPv4 下的 UDP 校验和可选但建议开启，IPv6 下强制开启。

> 常见问法：**伪首部"假"在哪里？答：它不参与传输，只在收发双方的校验计算中出现一次**，作用是让传输层也能校验 IP 层地址与协议号有没有被搞错。



#### 无拥塞控制与适用场景

**UDP 无拥塞控制**：指 UDP 发送端不会因为网络出现拥塞而主动降低发送速率，拥塞时仍按应用产生的速率"照发不误"。

- 从全网角度看，UDP 流量在拥塞时不退让，会挤占带宽、加剧拥塞；与有拥塞控制的 TCP 流量竞争时，可能"欺负" TCP。
- 从应用角度看，这种"自私"恰恰是实时应用需要的：实时音视频的旧帧重传毫无意义，等不及拥塞窗口慢慢恢复，宁可丢帧也不能卡顿。
- 现代解决思路：让基于 UDP 的新协议（如 QUIC，见第 21 章 HTTP/3）在 **UDP 之上自行实现**速率控制、拥塞控制与可靠传输，把"控制权"交回应用层。

UDP 的典型适用场景：

- **实时性优先、可容忍丢包**：IP 电话（VoIP）、视频会议、直播、在线游戏。
- **一次一问一答、报文短小**：域名解析 DNS、动态配置 DHCP、时间同步 NTP。
- **开销敏感的内网管理协议**：简单网络管理 SNMP、路由协议 RIP、简单文件传输 TFTP。
- **不适用场景**：需要可靠有序交付的网页浏览、文件传输、电子邮件，一律选择 TCP。

> 选型口诀：**"实时、简单、查询类"上 UDP；"可靠、文件、会话类"上 TCP**。做题时先看应用能否容忍丢包，能忍则 UDP，不能忍则 TCP。



#### UDP 的典型应用

UDP 承载了大量"小而短"或"实时"的著名应用，理解每个应用"为什么用 UDP"能帮助记忆端口与协议归属。

- **DNS（53）**：域名解析查询短小，一次一问一答，用 UDP 快且省；仅区域传送等大数据量交互才用 TCP 53。
- **DHCP（服务器 67、客户端 68）**：客户机还不知道自己的 IP 时就要广播请求，用 UDP 广播收发最合适。
- **TFTP（69）**：简单文件传送协议，实现极简，建立在 UDP 之上的"停等 + 超时重传"保证基本可靠。
- **RIP（520）**：路由信息协议，周期性广播整张路由表，数据量小，直接跑在 UDP 上。
- **SNMP（161 轮询、162 陷阱）**：简单网络管理协议，管理站与代理之间传送短报文。
- **NTP（123）**：网络时间协议，用 UDP 传递时间戳，需要低时延。
- **RTP**：实时传输协议，承载音视频媒体流，端口为偶数（典型为 1024~65535 中动态选取），见第 22 章流媒体部分。
- **新一代传输协议 QUIC**：虽以 UDP 为地基，却实现了可靠传输、加密与拥塞控制，是 HTTP/3 的载体。

> [!NOTE]
> **注意区分**：**ping 用 ICMP，不是 UDP 也不是 TCP**——它封装在 IP 之上，属于网络层辅助协议。考试与面试中“ping 基于什么协议”是高频陷阱题。



### TCP 与 UDP 的初步区分

#### 两者的核心差异（初步）

**TCP 与 UDP 的本质差异**：在于"是否面向连接、是否保证可靠"，其余区别都由这一根本差异派生而来。

- **连接**：**TCP** 面向连接，传输前须三次握手；**UDP** 无连接，想传就传。
- **可靠性**：**TCP** 可靠交付，按序、不丢、不重；**UDP** 尽最大努力交付，可能丢包、乱序。
- **传输单位**：**TCP** 面向字节流（无边界）；**UDP** 面向报文（保留边界）。
- **拥塞与流量控制**：**TCP** 均有；**UDP** 均无。
- **首部开销**：**TCP** 20~60 字节；**UDP** 仅 8 字节。
- **通信方式**：**TCP** 只能一对一（点对点）；**UDP** 支持一对一、一对多、多对一、多对多（可广播多播）。
- **系统资源占用**：**TCP** 需维护连接状态表，占用较多；**UDP** 状态简单，占用较少，程序结构也较简单。
- **典型应用**：**TCP** 为 HTTP/HTTPS、FTP、SMTP、SSH；**UDP** 为 DNS、DHCP、RTP、在线游戏、QUIC。

> 完整逐项对比（含报文格式、连接管理、拥塞控制机制）在第 20 章 TCP 章末的"全面对比"模块，本处先建立总体印象。



#### 常见误区与选型原则

围绕 TCP 与 UDP 有几个反复出现的认知误区，需要刻意纠正。

- **误区一**：ping 是 UDP 或 TCP。纠正：ping 基于 **ICMP**，属网络层。
- **误区二**：UDP 一定比 TCP 快。纠正：UDP 省去握手与重传开销，首包时延确实更低；但大量丢包且应用需自行重传时，整体效率未必高于 TCP。
- **误区三**：面向连接 = 必须可靠。纠正：TCP 面向连接是"手段"，可靠性是"承诺"，二者相关但不同层面。
- **误区四**：所有视频都该用 UDP。纠正：点播类视频（如视频网站）多用 HTTP/TCP 配合缓冲播放；只有直播、会议等实时互动才依赖 UDP。

**选型原则**：先问"丢一包能不能忍、需不需要按序到达"，需要可靠按序选 TCP；再问"时延是否比可靠性更敏感"，对时延敏感、可容忍丢包选 UDP；最后一问"能否接受连接建立的开销"，低频大流量可靠传输（文件、网页）选 TCP，高频小报文（查询、状态上报）选 UDP。

> 综合判断一句话：**"可靠、大块、会话式"归 TCP，"实时、短小、无连接"归 UDP**。特殊情况下（如 QUIC），应用可以在 UDP 之上自己"补造"出可靠性——说明传输协议的边界正在被上层技术打破。
