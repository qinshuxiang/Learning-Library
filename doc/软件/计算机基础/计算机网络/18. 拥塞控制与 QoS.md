## 拥塞控制与 QoS

### 拥塞控制

#### 拥塞的定义与表现

**网络拥塞（congestion）**：当网络中注入的分组过多，超过链路带宽、路由器缓存与处理能力等资源可承受的水平时，网络出现**时延增大、丢包增多、吞吐量不升反降**的现象。

拥塞的典型过程：

- 载荷轻时，吞吐量随注入流量近似线性上升，时延很小。
- 载荷超过“拐点（膝点）”后，排队时延开始急剧上升。
- 载荷继续增大超过“悬崖点”后，大量分组因缓存溢出被丢弃，**吞吐量反而下降**——网络进入了“越塞越慢、越慢越塞”的恶性循环。

- 拥塞的直接表现：端到端时延上升（排队是主因）、分组丢弃率上升（缓存溢出）、吞吐量下降、重传增多又加重拥塞。
- 拥塞控制的本质目标：**把网络工作点维持在膝点附近**——吞吐量接近最大且时延尚可接受，避免滑向悬崖点。

> 形象类比：公路车流超过容量后，所有车都堵在路上，单位时间通过的车辆数反而减少——拥塞不是“慢一点”，而是“效率塌陷”。网络层与传输层协作的目标就是避免这种塌陷。

#### 拥塞控制与流量控制的区别

**拥塞控制（congestion control）**：是**全局性**问题，涉及网络中的所有主机、路由器与链路，防止过多数据同时注入网络导致整体瘫痪。

**流量控制（flow control）**：是**端到端局部性**问题，只涉及收发双方，防止发送方发送太快而淹没接收方（接收缓存溢出）。

- 拥塞控制的观察对象是“网络的资源（链路、缓存）够不够”，流量控制的观察对象是“接收方吃不吃得下”。
- 拥塞控制需要全网配合、收集网络状态；流量控制只需收发两端协商窗口即可完成。
- 处理拥塞不只需要端系统调整，路由器侧的队列管理（RED）、调度与整形也参与其中。

> 两者的辨析是高频概念题：**流量控制管“发快了对方收不下”，拥塞控制管“全网都发多了网络受不了”**。一对一的窗口机制解决不了全网性拥塞——拥塞需要“全网一起踩刹车”。

#### 开环控制与闭环控制

**拥塞控制按“是否依据当前网络状态动态调整”分为开环与闭环两类**：

- **开环控制（预防式）**：事先把参数协商好、设计好，运行期间不再根据网络现状改变。典型手段包括重传策略（决定丢了怎么办）、丢弃策略（缓存满时丢谁）、流量整形（限制注入速率）。它不探测拥塞，只求“按规矩来”。
- **闭环控制（反馈式）**：先**监测**网络状态（丢包率、排队时延），把拥塞信息**反馈**给发送方，发送方据此**调整**发送速率，形成“检测—反馈—调整”的循环。按反馈来源又分两种：
  - **显式反馈**：网络节点明确告诉源“我拥塞了”，如 ICMP 源抑制、ECN 标记。
  - **隐式反馈**：端系统自己从丢包、超时等现象推断拥塞，最典型的是 TCP 的拥塞控制（详见《TCP》章）。

> 一句话区分：**开环是“事前立规矩”，闭环是“事中看脸色”**。TCP 的慢启动与拥塞避免属于闭环（且是隐式反馈），漏桶整形属于开环；两者常配合使用。

#### 闭环控制的手段：抑制包与逐跳抑制包

**抑制包（choke packet）**：路由器检测到自身拥塞（如输出队列超过阈值）时，向产生拥塞分组的源主机回送一个告警，源主机收到后降低发送速率，一段时间后试探性恢复。

- 简单直接，但存在缺陷：抑制包本身也是流量，会进一步加重拥塞；且从源到路由器的路径可能正堵，告警未必及时到达。
- 经典的 ICMP 源点抑制（Source Quench）报文就是这种思想的实现，因效果有限已废弃。

**逐跳抑制包（hop-by-hop choke packet）**：抑制包不是直接送回源，而是**在每个途经路由器逐跳往回传递**，让沿途每一级路由器都降低对该流的转发速率，使拥塞“就地缓解”。

- 优点：越靠近拥塞点的路由器越早收到抑制，**见效快**，缓解局部拥塞明显。
- 代价：需要上游路由器准备**更大的缓冲区**，拥塞可能被“背压”推向网络边缘，实现也更复杂。

> 理解视角：**抑制包是“源头刹车”，逐跳抑制是“每站刹车”**。前者简单但告警绕远，后者把刹车一级级传回拥塞点附近，响应更快——代价是沿途节点都要有“缓冲余量”配合。

#### 显式拥塞通告 ECN

**ECN（Explicit Congestion Notification，显式拥塞通告）**：利用 IP 首部区分服务字段中的 2 位，让路由器在拥塞时**不打标记（不丢包）也能明确告知发送方“我拥塞了”**，是一种显式反馈机制。

ECN 的 2 位取值与流程：

- 组合含义：00 表示端点不支持 ECN；01 或 10 表示支持 ECN（ECT，可发送拥塞标记）；11 表示经历拥塞（CE）。
- 发送方：在自己发出的 IP 首部把 ECN 置为“支持”（01 或 10）。
- 路由器：检测到拥塞时，若分组的 ECN 位表明发送方支持，就把该位改为 CE（11），**不丢弃分组**。
- 接收方：收到带 CE 标记的分组后，在回送的 TCP 确认中置位“ECN 回显”标志，告诉发送方网络发生了拥塞。
- 发送方：收到 ECN 回显后像“收到丢包信号”一样降低发送速率，从而**在真正丢包前就做出反应**。

> 与“以丢包为信号”的对比：传统 TCP 只能等超时或重复确认（丢包）才推断拥塞，代价是已经丢了数据；**ECN 让路由器提前“举手示意”，省去一次不必要的重传**。ECN 常与 RED 结合：路由器在轻度拥塞时用“标记 CE”代替“丢弃分组”。

#### 随机早期检测 RED

**RED（Random Early Detection，随机早期检测）**：是一种主动式队列管理算法，路由器持续监测**平均队列长度**，与最小门限、最大门限比较，**在队列真正装满之前就开始有选择地丢弃分组**，从而避免“尾部丢弃”引发的全局同步。

RED 的判别规则：

- 平均队列长度小于最小门限：拥塞尚轻，分组正常入队。
- 平均队列长度大于最大门限：拥塞严重，分组一律丢弃（或标记）。
- 介于两门限之间：按某个**概率**丢弃（概率随平均队列长度上升而增大），被“抽中”的流先降速。

RED 为什么要“提前随机丢”：

- 传统的**尾部丢弃（tail drop）**是队列满时把新来的分组全部丢弃，导致多条 TCP 流**几乎同时**超时、同时重传、同时撞车，全网流量出现“一起冲、一起停”的**全局同步**锯齿振荡。
- RED 的提前丢弃只涉及少量流，多数 TCP 流尚未察觉，网络吞吐更平稳；且丢弃概率与占用成比例，近似实现公平。
- 现代路由器多采用**加权 RED（WRED）**，对不同优先级的流量用不同门限，高优先级业务更晚被丢。

> 考试一句话：**RED 用“平均队列长度 + 两个门限 + 概率丢弃”代替“满了才丢”**。它把拥塞控制的“信号”从队尾的强制丢弃提前到队列接近满的时刻，配合 ECN 时还能把“丢弃”换成“打标”。

### 服务质量 QoS

#### QoS 的概念与指标

**QoS（Quality of Service，服务质量）**：是网络为特定业务提供有保障的传输性能的能力。互联网默认提供**尽力而为（best-effort）**服务——所有分组同等对待，不承诺时延与带宽；而实时业务需要差异化的保障。

- 尽力而为的局限：语音、视频会议、直播等对时延与抖动敏感，拥塞时若不区分流量，实时业务会与普通下载抢资源、体验断断续续。
- QoS 的核心思路：**识别不同业务、分配不同资源**（分类、标记、整形、调度、丢弃策略）。
- 可量化的 QoS 指标有四个：

- **带宽（带宽/速率）**：业务可获得的传输速率，如视频会议要求下行不低于某个速率。
- **时延（时延）**：分组从源到目的的时间，实时语音通常要求端到端时延很低。
- **抖动（jitter）**：分组时延的**变化幅度**，播放缓冲只能吸收有限抖动，过大则卡顿。
- **丢包率（丢包率）**：被丢弃分组占发送分组比例，直接影响音视频质量与重传开销。

> 带宽与时延易混：**带宽是“多宽的路”，时延是“跑一趟多久”**。QoS 保障通常围绕这四个指标做承诺，不同业务取舍不同——文件传输在乎丢包率与吞吐，实时通话在乎时延与抖动。

#### 流量整形：漏桶算法

**流量整形（traffic shaping）**：在业务流进入网络前，主动调节其发送速率与突发形态，使流量符合网络约定的参数。**漏桶（leaky bucket）**是最经典的整形算法。

漏桶的原理：把网络比作一个底部开孔的桶——水（分组）任意速率倒入桶顶，桶底以**恒定速率 r** 漏出；桶容量 b 有限，水满则溢出（分组被丢弃）。

- 输出速率被强制为恒定值 r，**不允许突发**：无论上游怎么猛灌，下游始终匀速出水。
- 突发流量被桶的容量吸收成“排队”，超出的部分只能丢弃或延迟。
- 效果：完全平滑流量，为下游提供可预期的恒定速率。

```text
       随机到达的分组（速率可变）
              ↓
        ┌───────────┐
        │ 桶（容量 b）│ ← 溢出即丢弃
        └───────────┘
              ↓
       恒定速率 r 输出（严格均匀）
```

> 特性定位：**漏桶是“强制匀速器”**——它保证输出不越过速率 r，特别适合对速率稳定性要求高、不允许突发的场景；代价是突发业务若超出桶容量只能丢弃，不会“先攒后冲”。

#### 流量整形：令牌桶算法

**令牌桶（token bucket）**：与漏桶相反，它**允许短时突发**，只限制“平均速率 + 最大突发量”，是更贴近真实业务的整形算法。

令牌桶的原理：以速率 r 不断生成令牌放入桶中（桶容量 b，满了则令牌作废）；发送分组时必须消耗与分组大小相当的令牌数，**桶里有多少令牌就能立刻发多少数据**。

- 长期平均速率被令牌生成速率 r 限制。
- 桶中最多可**积攒 b 个令牌**，攒下的令牌可支撑“一段时间内的突发发送”——突发长度受桶容量 b 约束。
- 业务流空闲时令牌越攒越多，忙时可用积攒的令牌一次性冲出去，这正是多媒体等“平时低调、突发时猛发”的业务所期望的。

> 漏桶与令牌桶的对照记忆：

- **漏桶**输出恒定速率、**不允许突发**、超出桶容量即丢；**令牌桶**允许积累令牌、**允许最大为 b 的突发**、只约束平均速率。
- **漏桶强制匀速、令牌桶限平均**；对突发敏感、必须稳速的业务选漏桶，允许短时冲刺、需要宽容突发的业务选令牌桶。
- 一个形象说法：**漏桶存不住“冲动”，令牌桶可以把“冲动”攒起来一次性释放**——考试问“哪个算法允许突发”，答案永远是令牌桶。

#### 分组调度算法

**分组调度（scheduling）**：发生在路由器输出端口，决定“队列里有多个分组时先发哪一个”，是 QoS 落到每个分组上的执行环节。常见算法如下：

- **FIFO（先进先出，First In First Out）**：按到达顺序发送，实现最简单。问题是无差别服务——长分组会拖住后面的短分组，也不做流量区分，适用于尽力而为网络。
- **公平队列（FQ，Fair Queuing）**：为每条活跃流维护一个独立队列，按轮转（round robin）方式轮流发送各队列的分组，使各条流大致均分带宽，避免“霸道的流饿死别人”。
- **加权公平队列（WFQ，Weighted Fair Queuing）**：在公平队列基础上为每条流分配**权重**，按权重比例分配带宽（如 3:1、5:1）。权重可以来自业务优先级或带宽预约，是实际网络中兼顾公平与差异的主流调度。
- **优先级调度（priority scheduling）**：严格按优先级队列服务，**高优先级队列清空后才服务低优先级**，保证实时业务优先通过，但极端情况下低优先级业务可能被**饿死**（长时间得不到服务）。

> 调度算法的选型规律：**FIFO 简单无差别、FQ 公平、WFQ 公平加权、优先级保实时但可能饿死低优先级**。它们与整形（入口处限制速率）、丢弃（RED/WRED）一起构成 QoS 的完整工具箱——整形管“进门”，调度管“出门”，RED 管“丢谁”。
