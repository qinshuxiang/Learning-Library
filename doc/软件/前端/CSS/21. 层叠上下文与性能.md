## 层叠上下文与性能

### 层叠上下文

#### 什么是层叠上下文

**层叠上下文（Stacking Context）**：把一组元素视作一个**独立的"图层组"**，其内部的层叠顺序**相对组内排序**；整组作为一个整体再与外部其它组比较。它是决定"谁盖住谁"的底层规则。

- **z-index 只在同一层叠上下文内比较**——不同上下文之间，比的是"上下文整体"的层叠值。
- 多个因素会**创建新的层叠上下文**（见下）。
- 层叠顺序从底到顶大致为：背景/边框 → 负 z-index → 块级 → 浮动 → 行内 → z-index:0/auto → 正 z-index。

```css
.a { position: absolute; z-index: 1; }   /* 上下文1 */
.a .inner { position: relative; z-index: 999; }
.b { position: absolute; z-index: 2; }   /* 上下文2（更高）盖过 inner */
/* 即使 inner 的 999 很大，也压不过上下文更低的 b */
```

> 理解层叠上下文才能解释"为什么 z-index 设了很大还是不生效"：z-index 只能和**同一层叠上下文**里的兄弟比。一旦某祖先创建了上下文，子孙的 z-index 就被"关"在里面，只能改变组内顺序，比不过外层更高的整体。很多"z-index 失灵"都源于此。



#### 创建层叠上下文的因素

很多属性都会**隐式创建层叠上下文**，设了它们之后元素就自带一个"图层组"。

- **定位 + z-index**：relative/absolute 需 z-index 不为 auto；而 **fixed/sticky 无论 z-index 取值为何总是创建**层叠上下文。
- **opacity < 1**（如 opacity: 0.9）。
- **transform / perspective / filter / backdrop-filter / clip-path / mask / will-change** 非初值。
- **mix-blend-mode 非 normal**、**isolation: isolate**。
- **flex/grid 子项**且 z-index 非 auto。
- **contain、content-visibility** 等。

```css
.ghost { opacity: 0.8; }   /* 已创建层叠上下文 */
.el { will-change: transform; }  /* 预建合成层，也建上下文 */
```

> 这些属性是"帮你自动分层"的双刃剑：一方面隔离了内部顺序（是好事），另一方面**任何 opacity/transform 都会把元素变成新的层叠上下文**——若祖先用了 opacity，则其子元素无法"跳出"去压过祖先的平级对手。排查堆叠异常时先查祖先是否有这些属性。



#### z-index 与堆叠规则

z-index 决定**定位元素（或 flex/grid 项、以及已建上下文的元素）**在其上下文内的堆叠位置。

- **数值越大越靠上**，可为负（沉到底层，但仍在本上下文内）。
- **auto**：对 relative/absolute 而言 z-index: auto 不创建新上下文，元素按 DOM 顺序堆叠（后写在上）；fixed/sticky 仍会创建。
- **负 z-index**：放到普通内容的下面、但仍在所在上下文的背景之上。
- 同为 auto 时后出现的元素在上。

```css
.back { position: absolute; z-index: -1; }  /* 垫在文字下层 */
.modal { position: fixed; z-index: 1000; }  /* 盖全屏 */
```

> z-index 实践口诀：**相同层级才比 z-index**；要"全局最上"（弹窗、toast）尽量把它们放在**不参与任何带上下文祖先**的顶层，并给足够大的 z-index。把整站 z-index 规划成几档（如 基础 / 浮层 / 弹窗 / 提示）比随手写 9999 更可维护。



### CSS 渲染性能

#### 重排、重绘与合成

浏览器渲染一条流水线大致为 **样式计算 → 布局(重排) → 绘制(重绘) → 合成**。改不同属性触发到不同阶段，性能差异巨大。

- **重排（Layout/Reflow）**：改动影响**几何**（宽高、边距、top/left、字体）时，浏览器要重新计算布局，代价最大。
- **重绘（Paint）**：改动只影响**外观**（颜色、背景、阴影）但不影响几何时，只需重绘，代价中等。
- **合成（Composite）**：只动 **transform / opacity** 时，元素走独立合成层，只做合成，代价最小、可 GPU 加速。

```css
/* 坏：改 left/top 触发重排 */
.box { left: 0; }
/* 好：改 transform 只合成 */
.box { transform: translateX(0); }
```

> [!IMPORTANT]
> **重要内容**：性能金律：**动画/高频变化用 transform + opacity，别碰 top/left/width/height**。想移动元素就 translate，想淡入就 opacity，二者都不触发重排与大面积重绘。能用合成的绝不重排，是 CSS 性能优化的第一原则。



#### 触发重排/重绘的属性分类

清楚哪些属性"贵"、哪些"便宜"，才能有的放矢。

- **触发重排（贵）**：width/height、margin/padding、border-width、top/right/bottom/left、font-size、display、position、flex 相关等几何属性。
- **触发重绘（中）**：color、background-color、box-shadow、text-shadow、border-radius、outline 等外观属性。
- **只触发合成（便宜）**：transform、opacity（在合成层上）。

```css
/* 变更 background-color 只重绘；动画 color/shadow 逐帧成本也可观 */
```

> 把"要频繁变的值"尽量落到 transform/opacity 上。若必须改几何（如展开高度），尽量把变化限定在**一个独立合成层**内，或减少触发频率。理解属性→阶段映射，就能从"为什么卡"倒推出"改哪个属性惹的祸"。



#### 合成层与性能优化实践

- **will-change**：提前告诉浏览器某属性将变化，让它**预先建好合成层**减少动画期间的抖动。勿滥用——过多合成层会占用内存。
- **translate: ...（独立属性）** 与 **contain** 等也能帮助浏览器分组。
- **减少合成层数量**、避免给大量元素同时加 opacity/filter 动画。
- **content-visibility**：跳过屏外内容的渲染以加速（长列表/长文）。
- **图片性能**：尺寸合适、懒加载、用现代格式。

```css
.slide { will-change: transform; }   /* 该元素将做位移动画时提示 */
article { content-visibility: auto; contain-intrinsic-size: 1px 600px; }
```

> 合成层的性价比：**明确要做 transform/opacity 动画时再 will-change: transform**，动画结束可移除；will-change: all 或对几十个元素滥用反而更卡。日常更该重视"少用重排属性、减少层数、控制大阴影/大 blur"，这些往往比微调 will-change 更见效。
