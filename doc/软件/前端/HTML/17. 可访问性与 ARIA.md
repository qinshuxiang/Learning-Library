## 可访问性与 ARIA

### 可访问性基础

#### Web 可访问性的意义

**Web 可访问性（Accessibility，缩写 a11y）**：让网站能被尽可能多的人使用，包括残障人士，是衡量 Web 质量的基本维度。

- 面向视力障碍者：依赖屏幕阅读器朗读、放大、高对比度。
- 面向肢体障碍者：依赖键盘、语音、辅助开关操作。
- 面向认知与听力障碍者：需要清晰结构、字幕与文本替代。
- 可访问性的改进惠及所有人（如嘈杂环境开字幕、色弱环境高对比）。

> [!IMPORTANT]
> 重要内容：可访问性不是"给少数人加的特例"，而是让内容"对机器可解析、对人都可用"的基础工程。语义化 HTML 本身就是可访问性最大的免费红利——正确的语义开箱即用。

#### 无障碍准则与工具

可访问性有成熟准则与审计工具可供遵循。

- **WCAG（Web Content Accessibility Guidelines）**：国际通行的无障碍指南，分 A、AA、AAA 三个等级，多数组织以 AA 为目标。
- **POUR 原则**：WCAG 的四大支柱——可感知（Perceivable）、可操作（Operable）、可理解（Understandable）、健壮（Robust）。
- 审计工具：Lighthouse、axe、WAVE，能在开发期发现大量可访问性问题。

> [!TIP]
> 建议内容：用 Lighthouse 与 axe 对页面跑一次可访问性审计，能快速发现对比度不足、缺少 label、缺少语义等高频问题。把 axe 集成进 CI 可长期守住基线。



### 原生语义与键盘可达

#### 语义化即内置可访问性

正确的语义元素自带可访问角色与行为，是无障碍的第一层保障。

- button、input、a 等原生控件可被键盘聚焦，自带按键行为（Enter、Space、Tab）。
- 语义结构（nav、main、h1-h6、label 关联）被辅助技术识别为导航点与名称。
- 尽量使用原生控件而非用 div 模拟，能免费获得键盘与无障碍支持。

> [!NOTE]
> 提醒内容：能用原生 button 就绝不用可点击的 div 加脚本模拟——原生控件天然支持键盘、焦点样式、屏幕阅读器识别。模拟控件需自行补齐大量细节，极易遗漏。

#### 键盘操作与焦点可见

让所有交互都能通过键盘完成，并让焦点清晰可见，是操作层面的核心要求。

- Tab 键在可聚焦元素间移动，Enter/Space 触发按钮，方向键操作部分控件。
- 焦点可见：:focus 样式应清晰（如明显的 outline），不可完全隐藏焦点指示。
- 不要用 tabindex 打乱自然 Tab 顺序；用 tabindex="-1" 支持程序化聚焦。

> [!WARNING]
> 警告内容：去掉 outline（outline: none）却不提供替代焦点样式，会让键盘用户完全迷失当前焦点位置，是常见的可访问性破坏。保留或重写焦点可见样式，勿一味清除。

#### 语义跳转与地标

辅助技术与浏览器能依据语义元素提供"跳转"能力，需正确组织。

- main、nav、aside、header、footer 等被视为 landmark（地标），可被快速跳转。
- 标题大纲 h1-h6 供屏幕阅读器生成章节导航。
- 长页面应在开头提供"跳到主内容"链接，让键盘用户绕过重复导航。

> 善用"跳转"：给键盘与屏幕阅读器用户提供跳过导航直达 main 的链接，是低成本的显著体验提升。地标元素布局正确时这类跳转即告可用。



### ARIA 概览

#### ARIA 的定位：语义不足时的补充

**ARIA（Accessible Rich Internet Applications）**：一组用于给 HTML 补充无障碍语义的属性，用于弥补原生语义无法表达的自定义组件。

- ARIA 只改进"无障碍树"的语义，不改变视觉与行为。
- 首要原则：能用原生语义就不用 ARIA——原生没有对应元素时才引入。
- ARIA 分角色（role）与状态/属性（aria-*）两类。

> [!IMPORTANT]
> 重要内容：ARIA 的第一条规则是"不要使用 ARIA，除非别无选择"。滥用 ARIA（给原生按钮再贴 role="button"、给已有语义的元素贴多余 role）反而会制造混乱。先语义化，再谈 ARIA。

#### role 与 aria-* 的两大类

**role 属性**：声明元素在无障碍树中的角色（如 dialog、tab、alert、switch）。

**aria-* 属性**：描述元素的状态、属性与关系，常见如下。

- 状态：aria-hidden（从辅助技术隐藏）、aria-disabled（禁用但保留于树中）、aria-expanded（展开/收起）、aria-pressed（按下态）。
- 属性：aria-label（可访问名称）、aria-labelledby（用另一元素文本作名称）、aria-describedby（引用描述文本）。
- 关系：aria-controls（所控制元素的 id）、aria-live（动态区域的播报方式）。

```html
<button aria-expanded="false" aria-controls="menu">菜单</button>
<div id="menu" hidden>…菜单项…</div>
```

> ARIA 是"给机器读的补充语义"。aria-label、aria-labelledby 用于为无可读文本的元素提供可访问名称，是无障碍中的高频属性。

#### aria-label 与 aria-labelledby

为控件提供可访问名称，是比补角色更常用也更重要的 ARIA 用法。

- **aria-label**：直接给出名称字符串。
- **aria-labelledby**：引用页面中另一元素的 id 作为名称，名称会随被引用文本变化。

```html
<!-- 图标按钮无可读文本，用 aria-label 命名 -->
<button aria-label="关闭对话框">✕</button>

<!-- 用可见文本作名称 -->
<div id="title">设置</div>
<button aria-labelledby="title">…</button>
```

> [!TIP]
> 建议内容：优先用真实的可见文本 + label（for）、再考虑 aria-labelledby，最后才用 aria-label。当屏幕阅读器读到的名称应与看到的一致时，用可见文本关联最佳；纯图标/符号按钮用 aria-label 补名。



### 常见可访问模式

#### 动态内容与 aria-live

**aria-live 区域**：当其中内容动态变化时，屏幕阅读器会自动向用户播报，用于无需打断用户焦点即可提示更新的场景。

- aria-live="polite"：空闲时播报（推荐，避免打断）。
- aria-live="assertive"：立即打断播报（慎用，用于紧急警报）。
- 常见场景：表单错误提示、消息通知、搜索结果数量更新。

```html
<p aria-live="polite" id="status"></p>
<script>
  document.getElementById("status").textContent = "已保存更改";
</script>
```

> [!WARNING]
> 警告内容：aria-live 只应包裹真正需要实时播报的少量文本。把整个正在频繁更新的列表设为 assertive 会狂刷屏阅读器用户。错误提示用 polite 即可，别滥用 assertive。

#### 表单错误与 aria-describedby

表单错误提示要能"被读出来"，用 aria-describedby 把提示文本关联到控件。

```html
<label for="mail">邮箱</label>
<input id="mail" type="email" required aria-describedby="mail-hint mail-err">
<span id="mail-hint">将用于登录通知</span>
<span id="mail-err" role="alert"></span>
```

- aria-describedby 让辅助技术读出控件的补充说明（帮助文本、错误信息）。
- role="alert" 可让错误在出现时被及时播报。
- 错误提示应既给视觉反馈（颜色、图标）又有文本可供朗读，不只靠颜色传达。

> 表单可访问的关键：每个控件有 label（名称）、必要时有 describedby（说明/错误）、校验反馈不单依赖颜色。可参考表单章结合理解。

#### 自定义组件的基本模式

常见的自定义组件（标签页、手风琴、模态框）各有约定的 ARIA 角色与键盘交互。

- 模态对话框：用 dialog 元素（原生最佳）或 role="dialog" 加 aria-modal="true"，聚焦需移入并锁定。
- 标签页：role="tablist"、"tab"、"tabpanel"，配方向键切换。
- 手风琴：用原生 details/summary 最佳（见交互元素章），自定义时用 aria-expanded。

> [!IMPORTANT]
> 重要内容：现代浏览器逐步提供原生交互组件（dialog、details、popover），它们内置了正确的无障碍与键盘行为——优先用原生，远胜手工拼 ARIA。复杂自定义组件应查权威无障碍模式（WAI-ARIA Authoring Practices）实现。

#### 颜色对比与不只靠颜色

视觉信息传达要兼顾色觉障碍与低对比度环境。

- 文本与背景需满足 WCAG 对比度要求（正文约 4.5:1，大字约 3:1）。
- 不要只用颜色区分状态——配合图标、文字、下划线等非颜色线索。
- 用色盲安全配色并借助对比度检查工具（Lighthouse 会测）。

> 设计原则：错误不只标红、必填不只加红点，应同时用文字或符号说明。颜色是辅助线索而非唯一通道。

### 全站可访问实践

#### 一份可访问页面的检查清单

综合运用上述要点，可用一张清单快速自查。

- 每个表单控件都有 label（或用 aria 名称）。
- 所有交互均可键盘操作、焦点可见。
- 图片有恰当 alt，图标按钮有 aria-label。
- 使用语义元素与合理标题层级。
- 动态更新区域配 aria-live，错误可被朗读。
- 颜色对比达标，信息不单靠颜色传达。
- 用工具跑一次可访问性审计并清零严重项。

> 可访问性不是一次做完，而是贯穿开发始终的持续要求。把这些检查内化为发布前的固定步骤，页面即可稳步达标 AA。
