## 性能与加载策略

### 性能对 HTML 的意义

#### 为什么要在 HTML 层关注性能

前端性能受资源大小、网络与渲染链路影响，而 HTML 的编写方式直接影响浏览器如何加载与渲染。

- HTML 先被解析，才触发样式、脚本、图片的加载。
- 阻塞解析的资源（同步脚本、未正确加载的样式）会拖慢首屏。
- 关键渲染路径上的每一个决定，都可能放大为加载与体验的差异。

> [!IMPORTANT]
> 重要内容：首屏性能（尤其 LCP 最大内容绘制）直接影响用户体验与 SEO。HTML 是"引导浏览器优先做什么"的清单——通过合理的脚本时机、资源提示与懒加载，可显著改善首屏。

#### 关键渲染路径概览

从收到 HTML 到绘制首屏，浏览器经历固定链路，HTML 在其中扮演入口角色。

- 解析 HTML 构建 DOM 树。
- 解析 CSS 构建 CSSOM。
- 二者合成渲染树，进入布局、绘制。
- 阻塞 DOM 解析的脚本会延迟整条链路。

> 理解"HTML 解析会被同步脚本与某些样式阻断"，就抓住了性能优化的纲。脚本加载策略见下。



### 脚本的加载策略

#### 同步脚本为何阻塞

默认的 script 元素（不带属性）会阻塞 HTML 解析。

- 浏览器遇到同步脚本，会暂停解析 HTML，先下载并执行脚本。
- 脚本在文档中部或 body 内会拖慢后续内容的解析与显示。
- 缓解之道：defer、async 或把脚本放合适位置。

> 结论：能用 defer 或 async 就不要让脚本同步阻塞解析。放 body 末尾只是缓解，defer 是更现代的主动优化。

#### defer 与 async 的差别

**defer**：延迟执行，脚本并行下载、文档解析完后再按文档顺序执行。

**async**：异步执行，脚本并行下载、下载完即执行（此时会暂停解析），执行顺序不定。

```html
<script defer src="./app.js"></script>   <!-- 依赖 DOM，按序执行 -->
<script async src="./analytics.js"></script> <!-- 独立，下完即跑 -->
```

- defer 适合相互依赖、需访问 DOM 的脚本。
- async 适合独立无依赖的脚本（统计、广告）。
- 内联脚本不支持 defer/async；动态插入的脚本默认按 async 处理。

> [!TIP]
> 建议内容：业务主脚本多用 defer（保序且不阻塞），第三方独立脚本用 async。避免"无属性同步大脚本"阻塞首屏。defer 脚本在 DOMContentLoaded 前、按文档顺序执行。

#### type="module" 与 nomodule

**type="module"**：把脚本声明为 ES 模块，天然延迟执行（类 defer）。

**nomodule**：旧浏览器兜底（模块不支持时加载经典脚本）。

```html
<script type="module" src="./main.js"></script>
<script nomodule src="./legacy.js"></script>
```

- 模块脚本默认延迟、独立作用域、支持 import。
- 模块受 CORS 约束，file:// 直接打开会失败，需走 HTTP 服务。
- 更多模块语义见 JavaScript 目录相关章节。

> 现代应用常用 type="module" 承载打包产物（构建工具输出带 import 的模块脚本），天然获得延迟执行与依赖管理。



### 资源加载提示与懒加载

#### preload 关键资源预加载

**preload**：让浏览器提前下载当前页面即将用到的关键资源，减少等待。

```html
<link rel="preload" href="./font.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preload" href="./hero.png" as="image">
```

- as 指明资源类型（font、image、style、script 等）。
- 预加载是"提示"，仅用于确认会立刻用到的关键资源；滥用会浪费带宽。

> [!WARNING]
> 警告内容：preload 是双刃剑——它抢在浏览器原计划前下载，若被预加载的资源其实不急着用，反而可能挤占首屏关键请求的带宽。只对 LCP 图、关键字体、首屏所需等真正优先的资源使用，别滥用。

#### preconnect 与 dns-prefetch

**preconnect**：提前与第三方源建立连接（DNS、TCP、TLS），减少跨域请求延迟。

**dns-prefetch**：提前解析域名。

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="dns-prefetch" href="https://api.example.com">
```

- 适合已知必会访问的第三方源（字体 CDN、API 域名）。
- dns-prefetch 更轻，preconnect 更彻底但也更"重"。

> 对首屏必请求的跨域第三方，preconnect 能省下连接建立时间；无法确认时用 dns-prefetch 成本更低。同样以"确实需要"为前提，不宜乱堆。

#### loading=lazy 与 fetchpriority

图像的懒加载与优先级提示用于精细控制加载顺序。

- loading="lazy"：图片进入视口附近才加载。
- fetchpriority="high" / "low"：提示浏览器提高/降低某资源优先级。
- 首屏关键图（LCP 图）适合 fetchpriority="high"，不宜 lazy。

```html
<img src="hero.png" alt="首图" fetchpriority="high">
<img src="below.png" alt="下方图" loading="lazy" decoding="async">
```

> [!IMPORTANT]
> 重要内容：LCP 首屏关键图绝不要加 loading="lazy"（会推迟加载），反而应给 fetchpriority="high"；视口之下的长页图片用 loading="lazy" 可显著省流量。合理组合 lazy 与 priority 是图像性能的关键。



### 关键资源与字体

#### 字体加载对文字闪烁的影响

网页字体的加载若处理不当，会引起文字不可见或闪烁。

- 字体默认按需加载，加载期间文本可能用后备字体或隐藏。
- font-display 属性控制加载期间的显示策略（swap、block 等）。
- 用 preload 提前关键字体可减少 FOIT（文字不可见）。

> 字体是许多页面的性能与体验暗坑。给关键字体 preload、合理设置 font-display 与字重子集，可避免文字延迟出现或排版跳动。细节在 CSS 目录字体章有述。

#### 避免阻塞的样式与脚本位置总结

把加载策略收拢为一套可行准则。

- 样式一般放 head（尽早、利于无闪渲染），脚本多用 defer/module。
- 关键 CSS 可内联或用 preload，避免 render-blocking 过长。
- 关键图 preload + 高优先级，非关键图 lazy。
- 第三方连接 preconnect。

> 现代实践常由构建工具产出优化后的资源与 link 标签。理解这些属性，既能在手工页面直接优化，也能读懂构建产物的优化逻辑。



### 测量与持续优化

#### 用性能指标与工具度量

优化要建立在测量之上，用浏览器工具量化首屏。

- Lighthouse：综合评分并给出优化建议。
- 核心 Web 指标：LCP、INP（替代 FID）、CLS 等。
- Performance 面板观察资源加载瀑布图，找出瓶颈。

> 建议：改前先测基线，优化后再测对比，用数据验证每项改动。避免凭感觉优化而忽略真正的瓶颈。

#### HTML 层的性能自查清单

从 HTML 层面做一次性能自查：

- 业务脚本用 defer 或 module，关键脚本不阻塞解析。
- 首屏关键图 preload 或高优先级，不 lazy。
- 视口下图片 loading="lazy"。
- 关键字体 preload 且 font-display 合理。
- 必连第三方 preconnect。
- 跑 Lighthouse 确认核心指标达标。

> HTML 层的优化多为"给浏览器的引导"，成本低、见效快。配合服务端缓存、压缩与 CDN，即可获得健康的首屏性能。
