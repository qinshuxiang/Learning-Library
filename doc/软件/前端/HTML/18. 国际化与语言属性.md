## 国际化与语言属性

### 国际化基础

#### 国际化、本地化与多语言

**国际化（i18n）**：把产品设计成不依赖特定语言与地区、能适应多种文化的工程实践。

**本地化（l10n）**：在国际化基础上为特定语言与地区提供翻译与适配。

- i18n 让"加一种语言"不需重写代码。
- l10n 产出具体语言版本的文案、日期格式、货币等。
- 与二者相对的是仅针对单一语言地区设计、难以扩展的"硬编码"。

> 网页国际化起步：不在代码与 HTML 里硬编码单一语言文案，把可翻译文本抽出统一管理，并正确标注语言，便于后续多语种扩展。

#### lang 属性的作用

**lang 属性**：声明内容所用的语言，可写在 html 根元素或任一元素上，是国际化的基础标记。

```html
<html lang="zh-CN">
```

- 影响屏幕阅读器的发音选择（中文/英文等朗读规则不同）。
- 影响浏览器的拼写检查语言。
- 影响排版与断行、部分字体选择。
- 供搜索引擎判断内容语言、翻译工具识别。

> [!IMPORTANT]
> 重要内容：lang 声明不当会让屏幕阅读器用错误语言发音整页内容（如用英文规则读中文），严重影响可读性。中文页面在 html 上写 lang="zh-CN"，个别外文片段再局部覆盖。

#### 语言标签写法

语言标签（language tag）由主语言加可选地区等构成，格式遵循规范。

- 基本形式：语言代码（如 zh、en），可加地区子标签（zh-CN、zh-TW、en-US）。
- zh-CN 简体中文（中国大陆）、zh-TW 繁体中文（中国台湾）、zh-Hans/zh-Hant 也可标识简体/繁体。
- 常见写法应统一：简体中文用 zh-CN 或 zh-Hans。

> 选择策略：区域差异明显时用带地区的标签（zh-CN 与 zh-TW 用词、用字不同），一般也可用 zh-Hans/zh-Hant 强调简繁。取一种并在全站一致即可。



### 局部语言与多语言页面

#### 在外文片段上局部标注

一页以中文为主但含英文术语时，可在英文片段上用 lang="en" 局部标注。

```html
<p>这个字段需要用 <span lang="en">email address</span> 填写。</p>
```

- 局部 lang 让屏幕阅读器按英文读那一段，避免用中文规则念英文。
- 只对确会按语言朗读的整词整句标注，单个缩写可不必逐一标注。

> 局部标注的收益是发音准确。多语言混排时，给明显属于另一语言的完整词句加 lang，可读性会显著提升。

#### 多语言页面与语言切换

面向多语言用户的站点需处理内容切换与语言声明。

- 同一 URL 提供多语言时，用链接、下拉或自动检测切换。
- 文档级 lang 跟随当前显示语言动态更新。
- 可用 link rel="alternate" hreflang 声明同一页面的各语言版本，利于搜索引擎。

```html
<link rel="alternate" hreflang="zh-Hans" href="/">
<link rel="alternate" hreflang="en" href="/en/">
```

> 多语言站点要保证：内容语言切换后，html 的 lang 同步更新，且每处链接正确对应目标语言版本。hreflang 帮助搜索引擎把用户导向合适语言页。



### 文本方向与双向文本

#### dir 属性与 RTL

**dir 属性**：声明文本方向。默认语言大多从左到右（LTR），部分语言从右到左（RTL，如阿拉伯语、希伯来语）。

- dir="ltr"：从左到右。
- dir="rtl"：从右到左。
- dir="auto"：按首字符自动判断。

```html
<p dir="rtl">هذا نص عربي</p>
```

> 含 RTL 语言片段时用 dir="rtl" 包裹，可让该语言正确排版。整页为 RTL 语言时，在 html 上设 dir="rtl"。

#### 双向文本与 bdi

**双向文本（Bidi）**：同一行内混排 LTR 与 RTL 文本，方向算法需正确处理，否则标点与顺序错乱。

- 大多数情况下浏览器自动处理方向，只需正确声明 dir。
- 用户输入内容（如用户名）可能含 RTL，混入 LTR 句子时易出错。
- **bdi 元素**：隔离一段不确定方向的文本，防止其影响周边排版。

```html
<p>用户 <bdi>محمد</bdi> 刚刚登录</p>
```

> [!NOTE]
> 提醒内容：展示用户生成内容或可能含异向语言的名字、评论时，用 bdi 或正确 dir 隔离，能避免方向符号干扰整句排版。这是多语言产品常见的细节坑。



### 本地化相关的 HTML 实践

#### datetime 与本地化格式

时间日期的显示应按用户地区格式化，而机器可读值保持规范。

- time 元素用 datetime 提供机器可读的 ISO 格式（如 2026-09-04T14:00）。
- 显示文本由本地化决定（如 9/4/2026 与 2026年9月4日 因地区而异）。
- 通过 JS Intl 或 CSS 按用户 locale 格式化显示。

> 实践：底层存/传统一用 ISO 时间（time 的 datetime），展示层按 locale 格式化，避免把本地化格式硬编码进内容。

#### 货币、数字与文字方向

本地化不仅涉及语言，也涉及数字、货币、度量衡的呈现。

- 数字与货币符号格式因地区而异，应交由格式化库/API 处理。
- 文案中的数字建议使用合适的数字体系（中文多用阿拉伯数字或汉字视语境）。
- 一律避免在 HTML 里写死特定地区格式。

> HTML 层能做的，是提供语义正确、无地区假设的结构与可机器读的值；真正的本地化格式化在应用逻辑层完成。

#### translate 属性与机器翻译

**translate 属性**：提示浏览器与机器翻译工具某元素内容是否可翻译。

- translate="yes"：可翻译。
- translate="no"：不可翻译（如品牌名、代码、姓名）。

```html
<p translate="no">WorkBuddy</p>
```

> 需要保持原文不被翻译的品牌词、专有名词、示例代码可用 translate="no" 提示。它作为对翻译工具与浏览器的建议，非强制。



### 国际化最佳实践小结

#### 常见国际化坑

多语言产品有若干反复出现的问题，值得预先规避。

- 忘记给 html 设 lang 或设错。
- 把可翻译文案硬编码在 HTML 中难以统一管理。
- 混排多语言时不标注局部 lang，发音错乱。
- 时间、货币格式写死单一地区。
- 用户输入含异向语言时不做 bdi 隔离。

> 提醒核心：语言（lang）、方向（dir）、时间格式、文案抽取是国际化的四个基本抓手，从第一版就做对，可避免日后大规模返工。

#### 规范的国际化文档骨架

一个规范的国际化为本页面骨架如下。

```html
<!DOCTYPE html>
<html lang="zh-CN" dir="ltr">
<head>
  <meta charset="UTF-8">
  <title>多语言支持示例</title>
</head>
<body>
  <p>中文正文，含 <span lang="en">English term</span> 与外文术语。</p>
</body>
</html>
```

> 骨架要点：html 声明 lang 与 dir、head 声明字符集、异语言片段局部标 lang、动态异向内容用 bdi。在此基础上扩展即可稳妥支撑多语言。
