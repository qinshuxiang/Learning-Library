## 执行上下文与内存管理

### 浏览器的渲染流程

#### 浏览器从下载到渲染的流程

浏览器从输入 URL 到显示页面的完整流程，是理解前端性能与 JS 执行时机的基础。

主要步骤：

1. **DNS 解析**：把域名解析为 IP 地址。
2. **建立连接**：与服务器建立 TCP 连接（HTTPS 还需 TLS 握手）。
3. **发送请求**：请求 HTML 文档。
4. **解析 HTML**：构建 **DOM 树**。
5. **解析 CSS**：构建 **CSSOM 树**。
6. **合成渲染树**：DOM + CSSOM 合成 Render Tree。
7. **布局（Layout）**：计算每个节点的位置大小。
8. **绘制（Paint）**：把节点画到屏幕上。

```js
// 关键事件
document.addEventListener("DOMContentLoaded", () => {
  console.log("DOM 树构建完成");
});
window.addEventListener("load", () => {
  console.log("所有资源加载完成");
});
```

> 这个流程揭示了几个重要结论：JS 会**阻塞 HTML 解析**（<script> 默认同步）、CSS 会**阻塞渲染**、DOM 与 CSSOM 都就绪才能渲染。这也是"脚本放底部""CSS 放 head""使用 defer/async"等最佳实践的根源。



#### JavaScript 引擎与浏览器内核的关系

**浏览器内核（渲染引擎）** 与 **JavaScript 引擎** 是浏览器中**协作的两大核心**。

- **渲染引擎**（如 Blink、WebKit）：负责**解析 HTML/CSS、布局、绘制**。
- **JavaScript 引擎**（如 V8）：负责**解析执行 JavaScript**。

```js
// JS 引擎执行代码时，可通过 DOM API 操作渲染引擎产出的 DOM
document.body.style.backgroundColor = "red";
// 渲染引擎感知 DOM 变化后，重新布局与绘制
```

> 二者通过 **DOM** 这座"桥梁"协作：JS 引擎执行脚本修改 DOM，渲染引擎监听变化后重新渲染。理解这一分工，就能理解"JS 操作 DOM 为何昂贵"（每次修改都可能触发渲染引擎的重排重绘）。



### V8 引擎的执行过程

#### V8 引擎执行代码的过程

V8 执行 JavaScript 经历了**从源码到机器码**的完整流程。

主要阶段：

1. **词法分析（Parse）**：源码拆成 token。
2. **语法分析**：token 构建 AST（抽象语法树）。
3. **生成字节码**：由 Ignition 解释器生成字节码。
4. **执行与优化**：热点代码由 TurboFan 编译成机器码（JIT）。

```js
// 源码 → token → AST → 字节码 → 机器码
const sum = 1 + 2;
// 1. 分词：const、sum、=、1、+、2、;
// 2. 语法分析：构建变量声明语句的 AST
// 3. 生成字节码
// 4. 执行
```

> V8 的核心是 **JIT（即时编译）**：先用解释器快速执行，发现"热点代码"（频繁执行的部分）再编译成机器码优化。这种"解释 + 编译"混合策略，兼顾了启动速度与运行性能。



#### V8 引擎的简单总结

对 V8 的执行过程做一个凝练总结。

- **解释 + 编译混合**：Ignition 解释执行 + TurboFan 优化编译。
- **热点优化**：频繁执行的代码被编译成机器码。
- **垃圾回收**：自动管理内存（见后续小节）。

> 一句话总结 V8：**"先把 JS 快速解释起来，再对热点代码进行机器码优化，同时自动回收内存"**。这种设计让 JS 从"纯解释型慢语言"蜕变为性能接近静态语言的现代引擎。



#### V8 解析过程的预解析

**预解析（Pre-parse）**：是 V8 的一项优化，对**暂时不会执行的函数**只做轻量解析，节省时间。

- 函数定义时，V8 先**预解析**（只检查语法，不生成完整 AST）。
- 函数**首次被调用**时，才进行**完整解析**。

```js
function rarelyUsed() {
  // 这个函数被预解析，首次调用时才完整解析
  const x = 1;
  return x;
}

// 大量代码...

rarelyUsed(); // 此时才完整解析
```

> 预解析的意义在于**性能**：页面里有大量函数，若全部完整解析会拖慢启动。V8 只完整解析"马上要用的"，其余先预解析。这也提示我们：**顶层立即执行的代码少而精**，有助于加快脚本启动。



### 执行上下文

#### 词法作用域与动态作用域

作用域有两种模型，JavaScript 采用**词法作用域**。

- **词法作用域（静态作用域）**：作用域在**代码书写时**就确定，由函数定义的位置决定。
- **动态作用域**：作用域在**运行时**确定，由函数调用的位置决定。

```js
const name = "全局";

function showName() {
  console.log(name);
}

function callIt() {
  const name = "局部";
  showName(); // 词法作用域：输出"全局"
}

callIt();
```

> JavaScript 是**词法作用域**：showName 里访问的 name，由它**定义位置**（全局）决定，而非调用位置。这也解释了"闭包"——函数记住了它**诞生时**的作用域，无论在哪里调用。



#### 全局代码的执行过程

JavaScript 代码在**执行上下文（Execution Context）** 中运行，全局代码在**全局执行上下文**中执行。

全局代码执行前，引擎会做**预处理**：

1. **变量提升（Hoisting）**：var 变量与函数声明被提升。
2. **创建全局对象**：浏览器中是 window。
3. **建立作用域链**。

```js
console.log(a); // undefined（var 提升，未赋值）
console.log(fn); // 函数（函数声明整体提升）

var a = 10;
function fn() {}
```

> "提升"是理解执行上下文的第一块拼图：**var 变量提升声明（值为 undefined），函数声明整体提升**。而 let/const 虽也"提升"但存在**暂时性死区（TDZ）**，声明前访问会报错，这是它与 var 的关键区别。



#### 作用域提升

**作用域提升（Hoisting）**：是指在代码执行前，引擎**把声明"提升"到作用域顶部**的行为。

提升的规则：

- **函数声明**：整体提升（可提前调用）。
- **var 变量**：只提升**声明**，赋值留在原地（提前访问为 undefined）。
- **let/const**：提升但进入**暂时性死区**，提前访问报错。

```js
console.log(foo()); // "hello"（函数声明整体提升）

function foo() {
  return "hello";
}

console.log(x); // undefined（var 提升声明）
var x = 5;

// console.log(y); // 报错（let 的暂时性死区）
let y = 10;
```

> 提升的本质：**执行上下文创建阶段**先扫描并登记所有声明，**执行阶段**才真正赋值。理解"声明先于执行"，才能解释 console.log(a) 为何是 undefined 而非报错。



#### 执行上下文栈

**执行上下文栈（Call Stack）**：是引擎维护的一个**栈结构**，管理执行上下文的创建与销毁。

- 全局上下文**始终在栈底**。
- 每次**函数调用**压入新的函数上下文，**函数返回**则弹出。

```js
function a() {
  b();
}
function b() {
  c();
}
function c() {
  console.log("栈顶");
}

a();
// 调用栈：全局 → a → b → c，c 执行完依次弹出
```

> 调用栈遵循**后进先出（LIFO）**：最后调用的函数最先执行完。**栈溢出（Stack Overflow）** 就是调用栈过深（如无限递归）超出上限导致。理解调用栈，是理解函数执行顺序、调试、递归的基础。



#### 变量对象与活动对象

**变量对象（VO，Variable Object）** 与 **活动对象（AO，Activation Object）** 是执行上下文存储变量的**内部结构**。

- **变量对象 VO**：存储当前上下文中所有变量、函数、参数。
- **活动对象 AO**：函数上下文中，VO 的"激活"形式，即**函数被调用时**的 VO。

```js
function foo(a) {
  const b = 2;
  function bar() {}
  // 这里的 AO 包含：a（参数）、b（变量）、bar（函数）
}
foo(1);
```

> VO/AO 是 ECMAScript 早期规范的概念（新规范用"词法环境"表述），但理解它们有助于理解"变量到底存在哪"。核心认知：**每个执行上下文都有自己的变量存储空间**，函数每次调用都会创建新的 AO。



#### 全局函数的执行过程

函数执行时，会经历"**创建上下文 → 执行 → 销毁**"的完整生命周期。

1. **创建阶段**：创建 AO、建立作用域链、绑定 this、提升声明。
2. **执行阶段**：逐行执行代码、赋值。
3. **回收阶段**：函数返回后，上下文出栈、变量等待回收。

```js
function greet(name) {
  const msg = "你好，" + name;
  console.log(msg);
}

greet("why"); // 创建 greet 的执行上下文 → 执行 → 销毁
```

> 函数每次调用都是**独立的上下文**：即使是同一个函数，两次调用也各自有独立的变量环境。这解释了为什么函数的局部变量在多次调用间**互不影响**。



#### 函数调用函数的作用域查找

当函数嵌套调用时，内层函数访问变量需要**沿作用域链查找**。

```js
const global = "全局";

function outer() {
  const outerVar = "外层";
  function inner() {
    console.log(outerVar); // 查找：inner → outer → 全局
    console.log(global);
  }
  inner();
}
outer();
```

> 查找规则：内层函数访问变量时，先找**自己的作用域**，找不到就**沿作用域链向上**（外层函数 → 全局）逐级查找，找到即止。这一"由内向外"的查找机制，正是作用域链的核心。



#### 作用域链的查找规则

**作用域链（Scope Chain）**：是执行上下文维护的一个**变量查找链路**，决定了变量解析的顺序。

- 每个函数创建时，都会保存其**定义位置**的外部环境引用。
- 访问变量时，沿这条链**从内到外**查找。

```js
const value = "global";

function foo() {
  const value = "foo";
  function bar() {
    const value = "bar";
    console.log(value); // "bar"（最近优先）
  }
  bar();
}
foo();
```

> 作用域链是**静态的**（由定义位置决定），配合"就近原则"查找。它是**闭包**的底层机制：函数即使离开了定义位置，仍能沿这条链访问外部变量。



#### 作用域常见面试题

作用域与提升是面试高频题，看一个经典例子。

```js
var n = 100;

function foo() {
  n = 200; // 没有 var，修改的是全局的 n
}
foo();
console.log(n); // 200

function bar() {
  var n = 300; // 有 var，是局部变量
}
bar();
console.log(n); // 200（全局 n 未被修改）
```

> 题眼在于"**有没有 var/let**"：n = 200 没有声明，**修改的是全局 n**；var n = 300 声明了局部变量，**不影响全局**。理解"赋值到底改的是谁"，是作用域题目的核心。



#### 变量环境与环境记录

新规范用**词法环境（Lexical Environment）** 与 **环境记录（Environment Record）** 替代了旧的 VO/AO 概念。

- **词法环境**：由**环境记录**和**外部环境引用**组成。
- **环境记录**：存储变量与函数绑定的实际结构。
- **外部引用**：指向外层环境，形成作用域链。

```js
function foo() {
  const a = 1;
  // 环境记录：{ a: 1 }
  // 外部引用：指向全局环境
}
```

> 现代规范用"词法环境"统一描述：每个环境有**自己的记录**（存变量）+ **对外层环境的引用**（形成链）。这比 VO/AO 更通用（能描述块级作用域、let/const），是理解规范级行为的基础。



#### 变量环境与词法环境的分工

执行上下文同时持有**变量环境（VariableEnvironment）** 与**词法环境（LexicalEnvironment）** 两个组件，分别存放不同关键字声明的变量。

- **变量环境**：存放 var 声明与函数声明，创建阶段即初始化为 undefined——这正是"提升"的来源。
- **词法环境**：存放 let、const、class 声明，创建阶段**只登记绑定、不初始化**。
- **暂时性死区（TDZ）**：从作用域开头到声明语句执行之间的区域，访问未初始化的绑定抛出 ReferenceError。

```js
function foo() {
  console.log(a); // undefined（var 在变量环境中已初始化为 undefined）
  console.log(b); // ReferenceError（b 在词法环境中，尚处于暂时性死区）

  var a = 1;
  let b = 2;
}
```

> TDZ 的本质：let/const 并非"不提升"，而是"**提升但未初始化**"——引擎在创建阶段就登记了绑定的存在，只是值要到声明语句执行时才写入。这解释了为何声明前访问 let 变量报的是 ReferenceError（绑定已存在但不可用），而非返回 undefined（压根没找到绑定）。



#### 块级作用域的环境创建

代码块 {} **不会创建新的执行上下文**，但会为 let/const 创建**新的词法环境**。

- **函数调用**：创建新**执行上下文** + 新词法环境。
- **进入块**：只创建新**词法环境**（沿用当前执行上下文）。
- **离开块**：块级词法环境随之失效（除非其中创建的函数被外部引用，形成闭包）。

```js
{
  let blockScoped = "块内可见";
  var functionScoped = "函数或全局可见";
}
// console.log(blockScoped); // ReferenceError（块环境已失效）
console.log(functionScoped); // 正常输出（var 不受块环境影响）
```

> 区分两者的创建时机：只有**全局代码、函数调用、eval** 会创建执行上下文；块、for 循环体、catch 子句只创建词法环境。这也是 for (let i ...) 每轮迭代都产生新 i 绑定的底层机制（详见第 18 章闭包的经典循环问题）。



### 内存管理与垃圾回收

#### 内存管理

**内存管理**：是程序**分配、使用、释放内存**的过程。JavaScript 与 C/C++ 不同，采用**自动内存管理**。

内存生命周期：

1. **分配**：声明变量时分配内存。
2. **使用**：读写内存。
3. **释放**：不再使用时由**垃圾回收器（GC）** 自动释放。

```js
// 分配
let obj = { name: "why" };
// 使用
console.log(obj.name);
// 释放：obj 不再被引用时，GC 自动回收
obj = null;
```

> JS 不需要手动 free 内存，但**理解 GC** 仍有必要：它能帮你写出**不易内存泄漏**的代码（及时解除引用、清理定时器/监听器）。"自动"不等于"无需关心"。



#### GC 垃圾回收算法

**垃圾回收（Garbage Collection，GC）**：是自动**找出并回收不再使用的内存**的机制。JavaScript 引擎内置 GC，主要算法有几种。

##### 引用计数

**引用计数（Reference Counting）**：记录每个对象**被引用的次数**，次数归零即回收。

```js
let obj = { a: 1 };  // obj 引用 +1
let ref = obj;       // 引用 +1（共 2）
obj = null;          // 引用 -1（剩 1）
ref = null;          // 引用 -1（归零，可回收）
```

> [!CAUTION]
> **注意内容**：引用计数实现简单，但有个致命缺陷：**无法处理循环引用**——两个对象互相引用，计数永不归零，造成内存泄漏。这正是现代引擎弃用它、改用标记清除的原因。



##### 标记清除

**标记清除（Mark-and-Sweep）**：是现代引擎（如 V8）采用的**主流算法**。

两步过程：

1. **标记（Mark）**：从**根对象**（全局对象）出发，标记所有**可达**的对象。
2. **清除（Sweep）**：回收**未标记**（不可达）的对象。

```js
let a = { x: 1 };
let b = { y: 2 };
a.ref = b; // a、b 都可达，被标记
a = null;  // a 不可达，但 b 仍被 a.ref 引用？不，a 没了则 b 也不可达
```

> 标记清除从根出发**判断可达性**：只要从根（全局对象、调用栈）能到达，就保留；否则回收。它**能正确处理循环引用**（循环引用但不可达，照样回收），是更优的方案。



##### 标记整理

**标记整理（Mark-Compact）**：是标记清除的**改进版**，多了一步**整理**，解决内存碎片。

- 标记清除后，存活对象可能**分散**在内存中，产生**碎片**。
- 标记整理把存活对象**移动到一起**，消除碎片。

```js
// 内存碎片示意：回收后留下零散空洞
// 标记整理：把存活对象集中，腾出连续空间
```

> 内存碎片会降低**大对象分配**的成功率（没有足够大的连续空间）。标记整理通过**移动存活对象**紧凑内存，代价是移动有开销，因此它常与标记清除配合、按需触发。



##### 分代收集与增量标记

**分代收集（Generational Collection）** 与 **增量标记（Incremental Marking）** 是 V8 的进一步优化。

- **分代收集**：按对象"存活时间"分代——**新生代**（短命对象，频繁回收）与**老生代**（长寿对象，低频回收）。
- **增量标记**：把标记过程**拆成多次**，穿插在程序执行间，减少卡顿。

```js
// 新生代：刚创建的对象，多数很快失效，用 Scavenge 算法快速回收
// 老生代：存活久的对象，晋升到老生代，用标记清除/整理
```

> 分代基于"**多数对象朝生夕死**"的观察：新生代用**复制算法**（快但占空间）回收，存活久才晋升老生代。增量标记让 GC 不再"一次性暂停"，而是**碎片化**进行，显著减少页面卡顿。
