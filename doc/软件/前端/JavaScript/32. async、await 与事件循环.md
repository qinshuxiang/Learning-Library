## async、await 与事件循环

### 异步代码的处理方案

#### 演化过程

异步代码的写法经历了三步演化，层层递进。

- **回调函数**：getData(callback)，易产生回调地狱。
- **Promise**：.then().then()，链式扁平化。
- **async/await**：await 语法糖，同步写法写异步。

```js
// 回调
getData((data) => {
  process(data, (result) => {
    console.log(result);
  });
});

// Promise
getData().then((data) => process(data)).then((result) => console.log(result));

// async/await
async function main() {
  const data = await getData();
  const result = await process(data);
  console.log(result);
}
```

> 三者的关系是**层层封装**：Promise 封装了回调，async/await 又是 Promise 的语法糖。理解这条演化链，才能理解"为什么 async/await 是最优雅的异步写法"。



### async 函数

#### 写法与执行流程

**async 函数**：用 async 声明的函数，**始终返回 Promise**，内部可用 await。

```js
async function foo() {
  return "结果"; // 返回值会被包装成 Promise
}

foo().then((v) => console.log(v)); // "结果"
```

> async 函数的关键特性：**返回值永远是 Promise**。即使 return 的是普通值，也会被自动 Promise.resolve 包装；若 return 的是 Promise，则直接返回该 Promise。



#### 与普通函数的区别

async 函数与普通函数的区别。

- **返回值**：async 返回 Promise，普通函数返回原值。
- **错误处理**：async 内抛错会被**转为 reject**（可被 .catch 捕获）。
- **可 await**：async 内可用 await 等待异步结果。

```js
async function foo() {
  throw new Error("出错了"); // 会被转成 reject
}

foo().catch((err) => console.log(err.message)); // "出错了"
```

> async 函数把**同步抛错也转成 Promise reject**，让错误处理统一走 .catch，这是它与普通函数的重要区别，也是异步错误不易"丢失"的原因。



#### await 关键字

**await**：只能用在 async 函数内，**等待一个 Promise 完成**，返回其结果。

```js
async function main() {
  const result = await new Promise((resolve) => {
    setTimeout(() => resolve("异步结果"), 1000);
  });
  console.log(result); // "异步结果"（等待后拿到）
}
```

> await 的核心是"**暂停 async 函数的执行，直到 Promise 完成**"。它让异步代码**看起来像同步**：await 后的代码，要等 Promise resolve 才继续。await 也可以跟普通值（直接返回）。



### 进程与线程

#### 操作系统、进程、线程与 JS 线程

理解 JavaScript 的单线程，需先理清进程与线程。

- **进程（Process）**：程序的一次运行实例，拥有独立的内存空间。
- **线程（Thread）**：进程内的执行单元，共享进程内存。
- **JS 是单线程**：一个 JS 引擎只有一个主线程执行代码。

```js
// JS 单线程：一次只能做一件事
console.log("A");
console.log("B"); // 必须等 A 执行完
```

> JS **单线程**的设计源于它的**运行场景**（操作 DOM）：若多线程同时改 DOM，会陷入复杂的同步问题。单线程"一次做一件事"看似低效，但配合**事件循环**，也能高效处理并发（I/O 等异步操作交给底层线程）。



#### Web Worker 与多线程

**Web Worker**：让 JavaScript 在**独立线程**中运行脚本，实现"多线程"，弥补主线程单线程的局限。

```js
// 主线程
const worker = new Worker("worker.js");
worker.postMessage("开始");
worker.onmessage = (e) => {
  console.log("收到结果：", e.data);
};

// worker.js（独立线程）
self.onmessage = (e) => {
  const result = heavyComputation();
  self.postMessage(result);
};
```

> Web Worker 把**耗时计算**放到独立线程，避免阻塞主线程（页面卡顿）。但 Worker **不能操作 DOM**、与主线程通过**消息**通信，适合 CPU 密集任务（图像处理、大量计算）。



### 浏览器的事件循环

#### 事件循环与队列

**事件循环（Event Loop）**：是 JavaScript 处理**异步任务**的机制，让单线程能"并发"执行任务。

- **调用栈（Call Stack）**：执行同步代码。
- **任务队列（Task Queue）**：存放待执行的**宏任务**。
- **微任务队列（Microtask Queue）**：存放待执行的**微任务**。

```js
console.log("同步");        // 1. 先执行同步代码
setTimeout(() => console.log("宏任务"), 0); // 3. 最后执行宏任务
Promise.resolve().then(() => console.log("微任务")); // 2. 再执行微任务
// 输出顺序：同步 → 微任务 → 宏任务
```

> 事件循环的流程：**同步代码 → 清空微任务队列 → 执行一个宏任务 → 再清空微任务**，如此循环。核心结论是"**微任务优先于宏任务**"，这是理解一切执行顺序题的关键。



#### 宏任务与微任务

异步任务分为**宏任务**与**微任务**两类，优先级不同。

##### 常见的宏任务

宏任务（MacroTask）是"**较大粒度**"的异步任务。

- **setTimeout / setInterval**。
- **I/O 操作**、**事件回调**（点击、滚动、postMessage 等）。

```js
setTimeout(() => console.log("宏任务"), 0);
```

> [!CAUTION]
> **注意**：**requestAnimationFrame 并不属于宏任务队列**。它在浏览器事件循环中是一个**独立的渲染阶段**——在一次循环里，宏任务执行完、微任务清空后，浏览器若决定渲染，才在**绘制之前**统一执行所有 requestAnimationFrame 回调（见下方引用块）。因此它的时机是"**微任务之后、绘制之前、下一批宏任务之前**"，常被粗略地说成"比宏任务早"，但规范层面它与宏/微任务不同轨。MacroTask/MicroTask 之外单列它，能更准确预测动画回调的时序。



##### 常见的微任务

微任务（MicroTask）是"**更细粒度、优先级更高**"的异步任务。

- **Promise.then / catch / finally**。
- **queueMicrotask()**。
- **MutationObserver** 回调。

```js
Promise.resolve().then(() => console.log("微任务"));
queueMicrotask(() => console.log("也是微任务"));
```

> 记忆口诀：**"微任务优先于宏任务"**。每次事件循环，先执行完**所有微任务**，才执行**下一个宏任务**。Promise.then、queueMicrotask 是微任务，setTimeout 是宏任务。

> 一张更完整的单次事件循环时序表（浏览器）：**① 执行一个宏任务 → ② 清空所有微任务 → ③ 若该轮到渲染，执行所有 requestAnimationFrame 回调 → ④ 样式计算、布局、绘制 → ⑤ 回到 ①**。因此 requestAnimationFrame 排在"微任务之后、屏幕绘制之前"，它与 setTimeout 这类宏任务不在同一个队列。执行顺序的常见题中 同步 → 微任务 → 宏任务 的简化结论依然成立，但若要精确到动画回调，需在"宏任务"与"绘制"之间给它单独一档（依据：HTML Living Standard 的事件循环渲染步骤）。



### 执行顺序面试题

#### Promise 的执行顺序

经典执行顺序题，考察微任务与宏任务。

```js
console.log(1);

setTimeout(() => {
  console.log(2);
}, 0);

Promise.resolve().then(() => {
  console.log(3);
});

console.log(4);
// 输出：1 4 3 2
```

> 解析：同步代码 1、4 先执行；Promise.then 是**微任务**（先于宏任务），输出 3；setTimeout 是**宏任务**，最后输出 2。核心是"**同步 → 微任务 → 宏任务**"的顺序。



#### async-await 的执行顺序

async/await 在事件循环中的表现，本质是 Promise 的语法糖。

```js
async function async1() {
  console.log("async1 start");
  await async2();
  console.log("async1 end");
}
async function async2() {
  console.log("async2");
}

console.log("script start");
async1();
console.log("script end");
// 输出：script start → async1 start → async2 → script end → async1 end
```

> 解析：await 前的代码**同步执行**（async2 立即打印）；await 之后的代码相当于 **.then 回调**（微任务），要等同步代码（script end）执行完才执行。所以 async1 end 最后输出。



#### Promise 返回结果的执行顺序

then 返回 Promise 时的执行顺序，涉及多层微任务。

```js
Promise.resolve()
  .then(() => {
    console.log("第一个 then");
    return new Promise((resolve) => resolve());
  })
  .then(() => {
    console.log("第二个 then");
  });
// 输出：第一个 then → 第二个 then
```

> then 返回**新 Promise** 时，下一个 then 要等它 resolve，这会产生**额外的微任务**（多一层等待）。理解"返回 Promise 会多一层微任务"，能精确判断复杂链式的执行顺序。



### Node 的事件循环

#### 各个阶段

Node.js 的事件循环比浏览器更复杂，分为**多个阶段**。

主要阶段：

- **timers**：执行 setTimeout、setInterval 回调。
- **poll**：检索新的 I/O 事件。
- **check**：执行 setImmediate 回调。
- **close callbacks**：执行关闭回调。
- **微任务**：process.nextTick 与 Promise 在**每个阶段之间**执行。

```js
// process.nextTick 优先级最高，先于 Promise
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("Promise"));
// 输出：nextTick → Promise
```

> Node 的事件循环是**阶段驱动**的：每个阶段执行特定类型的回调。微任务中 **process.nextTick 优先级最高**（先于 Promise），这是 Node 与浏览器的一个重要差异。



#### Node 代码执行顺序

理解 Node 中 setTimeout 与 setImmediate 的执行顺序。

```js
setTimeout(() => console.log("setTimeout"), 0);
setImmediate(() => console.log("setImmediate"));
// 输出顺序不固定（取决于循环进入时机）
// 但 I/O 回调内，setImmediate 先于 setTimeout
```

> Node 中 setTimeout(0) 与 setImmediate 的顺序**不固定**（取决于事件循环状态），但在 **I/O 回调内** setImmediate 一定先于 setTimeout。这是 Node 面试的经典考点，理解需结合事件循环的阶段划分。
