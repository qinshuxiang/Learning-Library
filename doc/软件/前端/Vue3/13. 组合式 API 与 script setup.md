## 组合式 API 与 script setup

### 组合式 API 的定位

#### 组合式 API 按逻辑关注点组织代码

**组合式 API（Composition API）**：是一组允许**按逻辑关注点**组织组件代码的函数式 API，核心是 ref、computed、watch、onMounted 等从 Vue 导出的响应式函数与生命周期函数。

- 组织单位是**功能**：同一功能的状态、计算、监听、方法连续写在一起，形成完整的逻辑块。
- 载体是**函数调用**：通过调用 Vue 导出的函数声明响应式能力，而不是把代码填进预置的选项槽位。
- 解决的问题：组件变大后，一个功能的代码被**拆散在多个选项里**，阅读与修改需要来回跳转。
- 额外收益：逻辑可封装成组合式函数在组件间复用，配合 TypeScript 的类型推导也更自然。

> [!NOTE]
> **提醒内容**：组合式 API 不是另一套组件系统，而是与选项式共用同一套响应式内核的**另一种代码组织方式**。掌握它的关键是转变归类习惯：先想功能，再写代码。

**速记**：组合式 API **按功能聚拢代码**，逻辑不拆散。



#### 选项式 API 按选项类型组织代码

**选项式 API（Options API）**：以 data、methods、computed、watch 与生命周期钩子等**选项**为组织单位的写法，同一类型的代码集中放进同一个选项。

- 组织单位是**类型**：data 放状态、computed 放计算、methods 放方法，归类标准是代码的**种类**而非功能。
- this 贯穿始终：各选项之间通过 **this** 相互访问，例如 this.count、this.getFullName()。
- 优点：结构固定、位置可预期，初学者按选项找代码即可快速上手。
- 局限：同一功能的代码被**强行分散**到多个选项中，组件达到数百行后维护成本明显上升。

> 辨析：选项式的分散是**结构性**的——即使某功能只有一个状态加一个方法，状态也必须进 data、方法也必须进 methods，代码位置由框架规则决定，而非由功能逻辑决定。

**速记**：选项式**按类型归堆**，同一功能各奔东西。



#### 同一功能两种风格的代码对照

**对照要点**：同一个计数器功能，两种风格的状态声明、方法书写与视图绑定方式完全不同。

```js
// 选项式：状态进 data，方法进 methods，逻辑分散在两处
export default {
  data() {
    return { count: 0 };
  },
  methods: {
    increment() {
      this.count++;
    },
  },
};

// 组合式：状态与方法聚在一起，是一个完整逻辑块
import { ref } from "vue";

export default {
  setup() {
    const count = ref(0);
    function increment() {
      count.value++;
    }
    return { count, increment };
  },
};
```

> 对比阅读的落点是**代码距离**：选项式中 increment 与 count 相距一个选项层级；组合式中二者紧邻，且新增第三个功能时只需另起一块，不再与已有代码交叉穿插。

**速记**：同一功能，**选项式拆两处，组合式一块写完**。

### setup() 函数

#### setup 是组合式 API 的组件内入口

**setup() 函数**：是组合式 API 在组件中的**入口函数**，在组件实例创建之前、props 解析之后执行，且每个组件实例只执行一次。

- 执行时机：早于 beforeCreate 钩子，此时组件实例尚未完全建立。
- 无 this：setup 内部 **this 是 undefined**，一切依赖显式传入的参数与导入的 API。
- 职责：声明响应式状态、计算属性、侦听器与生命周期逻辑，并把模板需要的内容返回出去。
- 混用限制：setup 可与 data、methods 等选项共存，但同一组件内**不推荐混用两种风格**。

```js
import { ref } from "vue";

export default {
  setup() {
    const message = ref("你好");
    function shout() {
      message.value += "！";
    }
    return { message, shout };
  },
};
```

> setup 早于实例建立解释了它为什么没有 this：此时连实例都还不完整，自然无法经 this 访问 data 或 methods，所有能力只能来自导入的函数。

**速记**：setup **先于实例执行**，无 this、只跑一次。



#### setup 的参数 props 与 context

**setup 的签名**：setup(props, context) 接收两个参数——props 是响应式的 props 对象，context 是包含 attrs、slots、emit、expose 的上下文对象。

- props：组件声明的**响应式 props**，可直接读取，但**不可手动解构**，解构会丢失响应性。
- context.attrs：未被声明为 props 的**透传属性**，是非响应式对象。
- context.slots：父组件传入的插槽内容对象，同样是非响应式对象。
- context.emit：触发自定义事件的函数，等价于选项式里的 this.$emit。
- context.expose：显式声明允许外部通过模板 ref 访问的成员。

```js
export default {
  props: ["title"],
  setup(props, { attrs, emit }) {
    console.log(props.title); // 读取 props
    console.log(attrs.class); // 读取透传属性
    function submit() {
      emit("confirm", "已提交"); // 触发自定义事件
    }
    return { submit };
  },
};
```

> [!CAUTION]
> **注意内容**：在 setup 中对 props 做解构（如 const { title } = props）会把值**从响应式上下文中撕下来**，后续 props 更新不再触发更新。需要保持响应时要么整体持有 props 对象逐属性访问，要么用 toRefs(props) 转成引用再解构。

**速记**：setup 收 **props 与 context**，attrs、slots、emit、expose 四件套。



#### setup 必须返回对象或渲染函数

**返回值要求**：setup 必须返回一个**对象**或一个**渲染函数**——返回对象时其成员暴露给模板，返回函数时直接接管渲染。

- 返回对象：对象里的每个属性与方法都**暴露给模板**使用，这是绝大多数场景的用法。
- 返回渲染函数：返回 h 函数的调用结果，完全绕过模板，以函数方式描述视图结构。
- 痛点所在：模板用到的每一个名字都必须**手动写进 return**，漏写一个，模板里就是 undefined。

```js
import { ref, h } from "vue";

export default {
  setup() {
    const count = ref(0);
    function increment() {
      count.value++;
    }
    // 方式一：返回对象，模板继续用 button 元素写视图
    // return { count, increment };
    // 方式二：返回渲染函数，模板被整体替代
    return () => h("button", { onClick: increment }, count.value);
  },
};
```

> [!IMPORTANT]
> **重要内容**：手动 return 正是 script setup 要消灭的样板——编译器扫描顶层绑定后**自动生成 return**，遗漏问题从根源上消除。理解 setup 的返回值约定，才能理解 script setup 便利的来历。

**速记**：setup 必返**对象或渲染函数**，手写 return 易漏。

### script setup 语法糖

#### script setup 是编译期的组件写法糖

**script setup**：是在 script 标签上添加 setup 属性的单文件组件写法，编译器在**编译期**把它转换成等价的 setup() 函数代码。

- 本质：编译器把顶层代码**原样搬进自动生成的 setup 函数**，并自动完成 return。
- 版本：3.0 引入实验支持，**3.2 起正式稳定**，是官方当前推荐的默认写法。
- 收益：免去 setup 函数壳与 return 清单，顶层即组件逻辑，代码量显著减少。
- 前提：需要单文件组件与支持 Vue 编译的构建工具，纯运行时引入的写法无法使用。

```html
<script setup>
import { ref } from "vue";

const count = ref(0);
function increment() {
  count.value++;
}
</script>

<template>
  <button @click="increment">计数 {{ count }}</button>
</template>
```

> [!TIP]
> **建议内容**：新项目直接把 script setup 作为默认组件写法，不必先写 setup 再迁移。两种写法产物等价，糖的转换由编译器完成，不引入额外运行时开销。

**速记**：script setup = **编译器代写的 setup**，顶层即逻辑。



#### 顶层绑定自动暴露给模板

**自动暴露**：script setup 中**任何顶层绑定**——变量、函数、import 进来的内容——都无需 return，即可直接在模板中使用。

- 变量与常量：ref、reactive、computed 的结果直接当变量书写，模板中 ref 自动解包。
- 函数：顶层声明的函数可直接绑定事件，如 @click="increment"。
- 导入即注册：import 进来的组件**无需 components 选项注册**，导入后直接当标签使用。

```html
<script setup>
import { ref } from "vue";
import UserCard from "./UserCard.vue";
import { formatPrice } from "./formatPrice.js";

const price = ref(1990);
function raise() {
  price.value += 100;
}
</script>

<template>
  <UserCard :price-text="formatPrice(price)" />
  <button @click="raise">涨价</button>
</template>
```

> 自动暴露只作用于**模板**：顶层绑定对父组件实例并不可见，父组件通过模板 ref 也拿不到它们，对外可见的成员由 defineExpose 白名单决定，这一点见后文。

**速记**：顶层绑定**免 return 直达模板**，导入的组件免注册。



#### 更少样板与更好的类型推导

**双重收益**：script setup 相比手写 setup，同时收获**更少样板代码**与**更好的类型推导**。

- 无需 return：省去维护返回对象的工作，也杜绝漏 return 导致的模板报错。
- 无需 name：组件名默认**取自文件名**，递归自引用等少数场景才需要显式命名。
- 类型友好：全程不经过 this，纯变量作用域让 TypeScript 能直接推导模板中的类型。
- 宏配合：defineProps 与 defineEmits 的类型声明都依赖编译器，script setup 是它们的主场。

> 辨析：选项式并非无法配 TypeScript，而是需要额外的泛型参数与辅助声明来还原 this 的类型；组合式把 this 从代码中移除，类型系统只需追踪普通变量，推导成本大幅下降。

**速记**：script setup **少样板、强类型**，无 this 是关键。

### 编译宏全家福

#### 编译宏是编译期处理的特殊关键字

**编译宏（Compiler Macros）**：defineProps、defineEmits、defineExpose、defineModel、withDefaults 这组**无需导入、由编译器直接处理**的特殊 API。

- 无需导入：不写 import 也能用，它们**不是运行时函数**，而是编译器识别的关键字。
- 编译期消失：编译器把宏调用**改写为真实运行时代码**，宏本身不出现在构建产物中。
- 位置限制：只能在 script setup 的**顶层**调用，不能放进函数体、条件分支或普通 js 文件。
- 成员分工：defineProps 管输入、defineEmits 管事件、defineExpose 管对外暴露、defineModel 管双向绑定、withDefaults 管默认值。

```text
defineProps    → 声明输入    → 编译为运行时 props 选项
defineEmits    → 声明事件    → 编译为 emits 选项与 emit 函数
defineExpose   → 对外白名单  → 编译为 expose 调用
defineModel    → 双向绑定    → 编译为 props + update 事件组合
withDefaults   → props 默认值 → 编译为合并后的 props
```

> [!WARNING]
> **警告内容**：把编译宏写进函数体或条件分支（例如在事件处理器内部调用 defineProps）会让编译器**直接报错**，因为宏的改写依赖确定的位置。同样，给宏补 import 语句没有意义，编译器根本不会执行它。

**速记**：宏**免导入、限顶层、编译期消失**。



#### defineProps 声明组件的输入

**defineProps**：编译宏，用于**声明组件接收的 props**，返回一个响应式的 props 对象。

- 运行时声明：传入对象字面量，键为 prop 名，值为类型构造器或选项对象（type、default、required、validator）。
- 类型声明：传入 TypeScript 类型字面量，编译器据此**反向生成运行时校验**，声明与使用合一。
- 响应性：返回的 props 对象是**浅层响应式**的，直接读取属性即可获得最新值。
- 禁止改写：props 是只读契约，组件内部**不得修改** props，需要变更应 emit 给父组件。

```html
<script setup>
// 写法一：运行时声明
const props = defineProps({
  title: String,
  count: { type: Number, default: 0 },
});

// 写法二：类型声明（推荐，与 TypeScript 配合最好）
interface BookProps {
  title: string;
  count?: number;
}
const bookProps = defineProps<BookProps>();
</script>
```

> [!NOTE]
> **提醒内容**：两种声明方式**二选一**，同一处 defineProps 不能同时给类型参数与运行时对象。类型声明的短板是无法表达 validator 等强校验语义，需要时退回运行时声明。

**速记**：defineProps **两套声明二选一**，返回只读响应式对象。



#### defineEmits 声明组件的事件

**defineEmits**：编译宏，用于声明组件**可以触发的自定义事件**，返回一个 emit 函数供调用。

- 返回值：emit 函数，签名等价于选项式里的 this.$emit(事件名, 附加参数)。
- 声明方式：数组简单列举事件名；类型声明式可连参数类型一起精确约束。
- 收益：emits 选项成为组件契约的一部分，未声明的事件会被归入透传属性而非可监听事件。

```html
<script setup>
// 数组式：只列举名称
const emit = defineEmits(["confirm", "cancel"]);

function save() {
  emit("confirm", "保存成功");
}
</script>

<template>
  <button @click="save">保存</button>
</template>
```

> [!IMPORTANT]
> **重要内容**：声明 emits 不只是文档约定——未声明的事件会被 Vue 当作**透传属性**落到组件根元素上，可能意外触发原生行为。子组件声明的自定义事件一律应写入 defineEmits。

**速记**：defineEmits **先声明后触发**，返回 emit 函数。



#### withDefaults 为类型声明的 props 提供默认值

**withDefaults**：编译宏，与**类型声明式 defineProps** 搭配使用，通过第二个参数为 props 提供默认值。

- 存在原因：运行时声明把 default 写进选项即可，**类型声明**的接口里没有位置承载默认值，因此由 withDefaults 补位。
- 返回值：返回合并默认值后的 props 对象，类型上各字段变为非可选。
- 默认值要求：对象与数组类型的默认值须用**工厂函数**返回，与运行时声明的规则一致。

```html
<script setup>
interface ListProps {
  items: string[];
  loading?: boolean;
}
const props = withDefaults(defineProps<ListProps>(), {
  items: () => [],
  loading: false,
});
</script>
```

> [!NOTE]
> **提醒内容**：withDefaults 只服务于类型声明式 defineProps。3.5 起响应式 props 解构把默认值直接写进解构模式，写法更短，官方文档已以解构默认值为推荐路径，withDefaults 更多保留在存量代码中。

**速记**：withDefaults = **类型声明的默认值补丁**。



#### defineModel 声明双向绑定

**defineModel**：编译宏，3.4 引入、3.5 起稳定，用于一行声明**双向绑定**所需的 props 与更新事件。

- 返回值：一个**自定义 ref**，读取它得到父组件传入的绑定值，写入它自动向父组件发出 update:modelValue 事件。
- 默认与命名：不传参数时绑定 modelValue；传字符串参数如 defineModel("title") 则绑定 title。
- 可带选项：第二个参数传入对象，支持 required、default 等 props 选项。

```html
<script setup>
const model = defineModel({ required: true });

function clear() {
  model.value = ""; // 写入即向父组件同步
}
</script>

<template>
  <input v-model="model" />
  <button @click="clear">清空</button>
</template>
```

> defineModel 的本质是**语法糖组合**：modelValue 的 prop、update:modelValue 的 emit 声明、内部读写转发，三件事被压成一个 ref。理解它等价于理解 Vue 双向绑定的全部分工。

**速记**：defineModel **一个 ref 管双向**，读写即同步。



#### 响应式 props 解构在 3.5 稳定

**响应式 props 解构（Reactive Props Destructure）**：在 defineProps 的返回值上**直接解构**仍保持响应性，该行为 3.5 起正式稳定。

- 写法：解构模式中**直接写默认值**，如 const { count = 0, title = "无标题" } = defineProps。
- 响应原理：编译器把解构出的变量**改写回对 props 对象的属性访问**，模板与侦听器仍追踪原始 props。
- 覆盖场景：默认值写法取代了 3.4 时代 withDefaults 的主要用途，代码从两层嵌套缩成一行。
- 限制：解构出的变量**不能整体重新赋值**，也不能当作独立对象传递后期待整体响应。

```html
<script setup>
interface GreetProps {
  greeting?: string;
  count?: number;
}

// 解构 + 默认值，一步到位且保持响应性
const { greeting = "你好", count = 0 } = defineProps<GreetProps>();
</script>

<template>
  <p>{{ greeting }}，第 {{ count }} 次</p>
</template>
```

> [!IMPORTANT]
> **重要内容**：3.5 之前解构 defineProps 的结果会**丢失响应性**——解构发生在 setup 执行时，拿到的只是当时的快照值。3.5 之后响应性由编译器恢复，同一写法在不同版本结论相反，判断时务必先确认版本。

**速记**：3.5 起解构 props **不失响应性**，默认值写在解构里。

### defineExpose 与组件的对外封闭

#### script setup 组件默认对外封闭

**封闭原则**：使用 script setup 的组件**默认对外封闭**，父组件通过模板 ref 拿到的实例上**看不到任何顶层绑定**。

- 设计原因：script setup 的顶层绑定属于组件**内部作用域**，框架有意不把它们挂到公开实例上，避免内外耦合。
- 与选项式差异：选项式组件的 this 自然携带 data 与 methods，模板 ref 一取一大把；组合式改为**白名单制**。
- 实际影响：父组件要调用子组件的 open、reset 之类方法，必须由子组件**显式放行**，否则访问结果一律是 undefined。

> [!IMPORTANT]
> **重要内容**：封闭是**默认行为而非疏漏**。它把子组件对外提供什么接口，从隐式的全量暴露变成显式的契约声明，接口面越小，重构越安全。

**速记**：script setup 组件**默认封闭**，对外看不见顶层绑定。



#### defineExpose 指定模板 ref 的访问白名单

**defineExpose**：编译宏，通过一个对象字面量显式列出**允许外部访问的成员**，父组件经模板 ref 只能拿到白名单内的内容。

- 写法：defineExpose({ open, reset, count })，值可以是 ref、函数或任意数据。
- 白名单语义：未列入的成员**完全不可见**，父组件访问得到 undefined，不报错但拿不到。
- 自动解包：白名单中的 ref 到了父组件一侧**自动解包**，直接读到值本身。
- 衔接：模板 ref 的获取方式、生命周期时机与 DOM 交互详见 15. 模板引用与 DOM 交互.md。

```html
<script setup>
import { ref } from "vue";

const isOpen = ref(false);
const draft = ref("");

function open() {
  isOpen.value = true;
}
function close() {
  isOpen.value = false;
}

defineExpose({ open, close });
// draft 与 isOpen 未列入白名单，父组件无法访问
</script>
```

> 白名单里的 ref 到父组件侧自动解包：父组件拿到的 childRef.value.open 是函数本身，计数类 ref 也无需再补一层 .value，与模板内的解包规则一致。

**速记**：defineExpose **画白名单**，名单外一律 undefined。

### 顶层 await 与异步组件

#### script setup 支持顶层 await

**顶层 await**：script setup 中可以直接书写 await 表达式，编译器会把组件转换成**异步 setup**，await 之后的初始化代码在结果就绪后才继续执行。

- 行为变化：顶层 await 使组件初始化**可以被挂起**，组件随之成为父组件的异步依赖。
- 典型场景：进入组件即请求接口拿初始数据、动态 import 资源模块、等待本地存储就绪。
- 作用域约束：await 之后的顶层代码仍属 setup，变量与函数照常对模板可见。

```html
<script setup>
import { ref } from "vue";

// 顶层 await：初始数据就绪前组件保持挂起
const response = await fetch("/api/config");
const config = ref(await response.json());
</script>

<template>
  <p>站点名称：{{ config.siteName }}</p>
</template>
```

> [!CAUTION]
> **注意内容**：顶层 await 会**阻塞整个组件树的初次渲染**——接口慢时用户看到的是一段空白或占位。只对首屏必需的数据使用它，非必需数据应改为挂载后再请求。

**速记**：顶层 await **挂起组件初始化**，数据就绪再渲染。



#### 含顶层 await 的组件必须由 Suspense 包裹

**Suspense 要求**：使用了顶层 await 的组件成为异步组件，其父级**必须提供 Suspense 边界**，否则没有优雅的加载态处理。

- Suspense 结构：提供 default 与 fallback 两个插槽，default 渲染就绪内容，fallback 渲染加载占位。
- 挂起过程：异步依赖未就绪时显示 fallback，就绪后整体切换到 default 内容。
- 衔接：Suspense 的插槽细节、嵌套边界与过渡配合详见 18. 内置组件与过渡动画.md。

```html
<template>
  <Suspense>
    <ConfigPanel />
    <template #fallback>
      <p>配置加载中……</p>
    </template>
  </Suspense>
</template>
```

> Suspense 与顶层 await 是**成对特性**：await 提供挂起点，Suspense 提供挂起期间的展示策略。二者单独使用都会造成不可控的空白或告警，写其一必想其二。

**速记**：顶层 await **必配 Suspense**，fallback 管加载态。

### 两种 API 风格的关系与选型

#### 选项式是组合式的底层封装

**关系定位**：**选项式 API 是组合式 API 的底层封装**——框架内部把 data、methods 等选项的代码最终归拢到同一个组件实例上，与组合式共用同一套响应式系统。

- 同一内核：两种风格操作的是**同一个组件实例**与同一套响应式机制，不存在两套引擎。
- 封装方向：选项式把能力**按类型预先归类**成槽位，组合式把能力**原样交给开发者**自由编排。
- 产物等价：二者最终都落到组件实例的 setup 与渲染函数上，运行性能没有差异。
- 学习顺序含义：先理解组合式这层**裸能力**，选项式各选项的行为即可据此推导。

> [!NOTE]
> **提醒内容**：官方文档明确把组合式 API 定位为**更底层、更灵活**的表达，而非对选项式的取代。把两种风格理解为同一能力的两种封装粒度，是选型讨论的前提。

**速记**：选项式是**组合式的类型化封装**，内核同一。



#### 两种风格可以共存

**共存规则**：同一组件内 setup 与 data、methods 等选项**可以同时书写**，两边的状态与方法互相可见。

- 访问方向：选项中（如 methods）可以读到 setup 返回的绑定；反向则不便，因为 setup 内**没有 this**。
- 执行顺序：setup 先于所有选项初始化执行，选项里的 this 上能看到 setup 放出的内容。
- 实务定位：共存主要用于**渐进迁移**存量组件——新逻辑进 setup，旧逻辑留在选项里逐步搬离。

```js
export default {
  data() {
    return { legacyCount: 0 };
  },
  setup() {
    const freshMessage = ref("组合式新增");
    return { freshMessage };
  },
  methods: {
    showBoth() {
      console.log(this.legacyCount, this.freshMessage); // 两边都可见
    },
  },
};
```

> [!CAUTION]
> **注意内容**：共存是**迁移手段而非长期形态**。同一组件长期混用两种风格会让代码位置失去规律，迁移完成后应收敛到单一风格。

**速记**：两风格**可共存**，宜作迁移过渡。



#### 官方的选型建议

**选型结论**：官方建议**新代码默认使用组合式 API**，同时明确选项式不会废弃、仍是受支持的正式风格。

- 选组合式的情形：逻辑复杂、需要组合式函数跨组件复用、重度使用 TypeScript、大型单页应用与长期演进的项目。
- 选选项式的情形：低复杂度组件、无构建步骤的渐进增强页面、由 Vue 2 迁移的存量代码、熟悉按类型归类心智的团队。
- 不变的底线：两者能力等价、可随时互转，选型的差别在**维护体验**而非功能上限。

> [!TIP]
> **建议内容**：团队层面的选型标准是**统一高于偏好**——一个仓库内混用两种风格的组织方式，比选哪种风格本身代价更大。新项目直接统一 script setup，存量项目按模块逐步迁移。

**速记**：新代码用**组合式**，团队内部**风格统一**。

### 逻辑组织的实践

#### 状态、计算、监听与方法按功能聚合

**聚合原则**：组合式的正确组织方式是把**同一功能的全部代码连续写在一起**，而不是照搬选项式按类型分堆的摆放习惯。

- 反例形态：所有 ref 挤在文件顶部、所有函数挤在底部，等于用新语法延续旧的分散结构，组织优势完全落空。
- 正例形态：一个功能块内连续书写它的 ref、computed、watch、方法与卸载清理，块与块之间用空行或注释分组。
- 检验标准：修改某个功能时，**只在一个连续区域**内完成全部改动，不需要在文件里上下跳跃。

```js
// 正例：两个功能各自成块，块内自包含
// ---------- 功能一：搜索 ----------
const keyword = ref("");
const results = computed(() => filterList(rawList.value, keyword.value));
watch(keyword, () => submitSearch(keyword.value));

// ---------- 功能二：分页 ----------
const pageIndex = ref(1);
const pageSize = ref(20);
const pageData = computed(() => sliceByPage(results.value, pageIndex.value, pageSize.value));
function turnPage(next) {
  pageIndex.value = next;
}
```

> [!TIP]
> **建议内容**：把功能块内聚当作 script setup 的默认排版纪律。一个块长大到压迫主线阅读时，就是抽取组合式函数的信号，而不是退回按类型分堆的理由。

**速记**：按**功能分块**书写，一块读完整功能。



#### 逻辑块变大就抽成组合式函数

**抽取时机**：当某个功能块需要**跨组件复用**，或体积大到干扰组件主线时，把它抽成 use 开头的**组合式函数（Composable）**。

- 形态：一个**返回响应式状态与方法**的普通函数，内部自由使用 ref、computed、watch 等组合式 API。
- 命名：以 use 为前缀并写明领域，如 useCounter、useSearchList，遵循驼峰命名要求。
- 调用约束：组合式函数**必须在 setup 上下文中调用**（含其他组合式函数内部），因为它依赖组件的响应式作用域。
- 收益：状态与方法成组流转，组件里只剩调用一行，逻辑复用不再依赖 mixins 的隐式合并。

```js
// useCounter.js：把计数逻辑整块抽离
import { ref } from "vue";

export function useCounter(initialValue = 0) {
  const count = ref(initialValue);
  function increment() {
    count.value++;
  }
  function reset() {
    count.value = initialValue;
  }
  return { count, increment, reset };
}
```

> 组合式函数是组合式 API 的**复用终点**：同一功能块从组件内的小块，升级为可跨组件流转的独立单元。抽离的边界判断与嵌套细节在组合式函数专篇展开，此处只须建立块大即抽、抽必成组的意识。

**速记**：功能块**大了就抽 use 函数**，状态方法成组复用。
