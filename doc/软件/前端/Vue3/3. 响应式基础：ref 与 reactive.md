## 响应式基础：ref 与 reactive

### 响应式的认识

#### 响应式是状态变化自动同步视图的机制

**响应式（Reactivity）**：是状态发生变化时，依赖该状态的视图与副作用**自动同步更新**的机制。

- 开发者只修改**数据（状态）**，不直接触碰 DOM；框架在状态变化后自动重新渲染受影响的视图。
- 自动更新的前提是框架**知道谁依赖了该状态**：渲染函数读取状态时被登记为依赖，状态一变就重新执行。
- 响应式是声明式渲染的地基：模板里写双花括号插值，count 一变，插值处自动变化，无需任何手动干预。
- 依赖状态的不止视图：**计算属性与侦听器同样是副作用**，它们随状态变化自动重算，与视图更新共用同一套响应式机制。

> 响应式的本质是**数据与视图的自动同步**：只管改数据，框架负责更新界面。Vue3 通过 ref 与 reactive 两个入口，把普通数据变成可被追踪的响应式数据。

**速记**：改数据即**自动更新视图**，不手写 DOM。



#### 对比手动 DOM 操作

**手动 DOM 操作**：先拿到元素再逐条修改，与响应式的**声明式**路线形成对照。

- 手动方案里，状态与视图的对应关系靠**人脑维护**：哪里用了这个数据、改完要更新哪段 DOM，全部自己记。
- 漏改一处就出现**视图与数据不一致**的缺陷，且这类问题随规模增长急剧恶化。
- 响应式把这份对应关系**交给框架统一管理**，开发者只描述状态与视图的映射。
- 术语对照：手动方案属于**命令式**（一步步指挥怎么做），响应式属于**声明式**（只声明结果长什么样），后者是现代框架的共同选择。

```js
// 手动操作 DOM：每处更新都要自己写
const countEl = document.getElementById("count");
let count = 0;
countEl.textContent = count; // 初始渲染要手动
count += 1;
countEl.textContent = count; // 每次变化都要手动同步
```

```html
<!-- Vue 响应式：只改状态，视图自动跟上 -->
<span id="count">{{ count }}</span>
```

> 手动方案的痛点是**同步逻辑分散**：状态一多，更新点散落在各处，极易漏改；响应式收敛为一条规则，改状态就够了。

**速记**：手动**改完还要推 DOM**，响应式**只改状态**。



### ref：值类型的响应式包装

#### ref 包装任意值为响应式引用

**ref**：接收任意类型的值，返回一个带有 value 属性的**响应式引用对象**。

```js
import { ref } from "vue";

const count = ref(0);
const user = ref({ name: "why" });

console.log(count.value); // 0
count.value++;            // 修改必须经过 value
console.log(count.value); // 1
user.value.name = "tom";  // 对象内部属性通过 value 进入
```

- **读取与修改**都要经过 value：count.value 是唯一入口，直接写 count = 1 只是替换普通变量，不会触发任何更新。
- ref(0) 返回的是一个 **RefImpl 类的实例**，其 value 属性的读取与写入被 getter 与 setter 拦截，从而接入响应式系统。
- ref 可以包装**原始值、对象、数组、函数**等任意值，一个 API 覆盖所有类型。

> [!CAUTION]
> **注意内容**：在脚本代码里忘记写 value 是最高频的错误。count++ 既不报错也不生效，页面毫无反应，因为顶层的 count 只是普通变量，与响应式系统毫无关联。

**速记**：ref 出手必带 **value**。



#### ref 为什么存在：统一值类型的响应式包装

**ref 的设计意图**：用一层**包装对象**弥补 JavaScript 原始值无法被代理的短板，让值类型与对象类型共享同一套响应式机制。

- Proxy 只能代理**对象**，无法拦截 number、string、boolean 等原始值的读写。
- 把值装进对象的 value 属性，Proxy 与 getter/setter 就有了**拦截点**。
- 于是 ref(0) 与 ref({}) 走通同一条路：**先包一层、再拦截**，调用方式完全一致，心智负担降到最低。
- 包装层同时是**类型统一的载体**：组合式函数返回 ref、props 传 ref、依赖注入传 ref，到处都是同一种响应式单位。

```js
const count = ref(0);
// ref 内部相当于把值挂在一个对象的 value 属性上
// 对 value 的读写被拦截，从而实现响应式
```

> 若没有 ref，值类型只能塞进对象再用 reactive 包装，写法分裂成两套；有了 ref，**一个入口覆盖所有类型**。名字里的 ref 即引用（reference），含义是持有一个指向值的稳定引用。

**速记**：原始值拦不住，**包一层 value 再拦**。



#### ref 的深层响应式：嵌套对象自动转为代理

**深层响应式**：ref 包装对象类型的值时，内部会借助 reactive 把嵌套对象转换成 **Proxy 代理**，深层属性的修改同样可追踪。

```js
const state = ref({ profile: { age: 18 } });

state.value.profile.age = 20; // 深层修改同样是响应式的
console.log(state.value.profile.age); // 20
```

- 深层转换是**惰性且递归**的：访问到哪一层，哪一层才被代理，开销按需产生。
- 深层对象已被代理，因此 state.value.profile 的行为与 reactive 对象完全一致。
- 想关掉深层转换、只追踪 value 本身，需要 shallowRef，属于响应式进阶 API 的内容。

> [!NOTE]
> **提醒内容**：ref 的深层响应式与 reactive 同源，都建立在 Proxy 之上；ref(obj) 的 value 拿到的其实就是 obj 的响应式代理。

**速记**：ref 深层**自动转代理**，改到哪层都能更新。



#### 模板中的自动解包

**自动解包**：在模板中访问**顶层** ref 时，无需写 value，Vue 自动取其内部值。

```html
<script setup>
import { ref } from "vue";

const count = ref(0);
</script>

<template>
  <!-- 模板里直接写 count，无需 count.value -->
  <button @click="count++">{{ count }}</button>
</template>
```

- 解包只发生在**模板渲染**环节，且只对**顶层属性**生效。
- 脚本逻辑里仍必须写 value，两条规则互不干涉。
- 事件处理器里同样自动解包，模板中的 count++ 实际等价于 count.value++。

> 自动解包的判定条件是 ref 成为渲染上下文的**顶层属性**：由 script setup 声明或 setup 顶层返回的名字都满足；一旦 ref 嵌在别的对象里再取出来，就要按下方的边界规则判断。

**速记**：模板顶层**免 value**，脚本里**必带**。



#### 解包规则的三个边界

**解包边界**：ref 是否自动解包取决于**它所处的位置**，共三种典型情形。

- **模板顶层属性**：解包，直接写名字。
- **reactive 对象的属性**：解包，读写 state.count 自动落到 count.value 上。
- **数组与集合的元素**：不解包，元素就是 ref 本身，必须手动加 value。

```js
import { ref, reactive } from "vue";

const count = ref(0);
const state = reactive({ count }); // ref 作为属性被收编

state.count++;            // 自动解包，等价于 count.value++
console.log(count.value); // 1，两者指向同一个 ref

const arr = reactive([count]);
console.log(arr[0].value); // 1，元素位置不解包，arr[0] 是 ref 本身

const map = reactive(new Map([["c", count]]));
console.log(map.get("c").value); // 集合同样不解包
```

> [!WARNING]
> **警告内容**：数组与集合元素位置的 ref 不解包是硬规则，遍历时拿到的是 ref 对象本身，必须补 value 才能得到值；Vue 3.5 起 v-for 已支持直接遍历响应式的 Set 与 Map，元素位置的解包规则不变。

**速记**：顶层与 reactive 属性**解包**，数组集合**原样保留**。



### reactive：对象的深层响应式代理

#### reactive 的基本使用

**reactive**：接收一个对象类型的值，返回原对象的**深层响应式代理**，读写属性无需任何包装。

```js
import { reactive } from "vue";

const state = reactive({
  user: { name: "why" },
  list: [1, 2, 3]
});

state.user.name = "tom";  // 直接改属性
state.list.push(4);       // 数组方法同样被拦截
```

- **返回的是代理**：reactive(obj) 与 obj 不是同一个对象，只有通过返回的 state 读写才会被追踪。
- 深层生效：嵌套对象、数组、Map、Set 都会被转换成响应式代理。
- 新增属性、删除属性、数组索引赋值都能被监听，这正是 Proxy 相对 Vue2 的 Object.defineProperty 的进步之处。

> [!IMPORTANT]
> **重要内容**：必须使用返回的代理对象，保存原对象引用毫无响应式能力；对 state 调用 isReactive 返回 true，对原对象 obj 调用则返回 false。

**速记**：reactive 返回**代理**，直读直写即响应。



#### 局限一：整体替换对象会与代理断开

**不能整体替换**：对承载代理的变量重新赋一个新对象，原有的响应式连接随之中断。

- 响应式绑定的是**最初那个代理对象**：模板、计算属性、侦听器都依赖它的引用。
- 重新赋值后，旧引用仍指向旧数据，新对象与已建立的依赖**互不相识**。
- 替代思路是**修改属性而非换对象**：多加一个字段、把某个键置空，都好过整体替换。

```js
let state = reactive({ count: 0 });

state.count++; // 响应式生效

state = reactive({ count: 100 }); // 换成新代理
// 模板持有的仍是第一个代理，界面不再跟随新对象变化
```

> [!WARNING]
> **警告内容**：整体替换是 reactive 最常见的翻车点。需要频繁整包换数据（如接口返回后整包覆盖）的场景，改用 ref 承载，把新对象整体赋给 value 即可，引用始终不变。

**速记**：reactive **换对象即断线**，整包更新交给 ref。



#### 局限二：解构与传参后失去响应

**解构失响应**：从 reactive 对象解构出来的值类型是**普通值**，一旦复制出来就脱离了代理的追踪。

- 原始值赋给新变量后与代理**再无关联**，后续各自修改、互不可见。
- 传参同理：把 state.count 传给函数，函数拿到的是调用那一刻的**快照值**。
- 传对象类型的属性（如 state.user）则不受影响，因为拿到的仍是**代理对象**。
- **toRefs** 把 reactive 的每个属性逐一转成 ref，解构后仍与原对象保持连接。

```js
import { reactive, toRefs } from "vue";

const state = reactive({ count: 0, name: "why" });

let { count, name } = state; // count 是普通数字，name 是普通字符串
count++; // 不会触发任何更新

const refs = toRefs(state); // 逐个属性转成 ref
refs.count.value++;         // 响应式保留，且与 state.count 双向同步
```

> 失响应主要发生在**值类型属性**上：对象类型的属性解构后依然是代理，依旧响应。判断标准是解构出来的是原始值还是代理对象。

**速记**：值类型**解构即断**，先 toRefs 再解构。



#### 局限三：只对对象类型有效

**类型限制**：reactive 只接受对象、数组、Map、Set 等对象类型，原始值直接传入**没有响应式效果**。

- 原始值没有属性可拦截，Proxy 的能力无从施展。
- 想让单个值具备响应式，唯一正解是 **ref**。
- 对原始值调用 reactive 会**原样返回**该值，不报错但也不响应。

```js
const num = reactive(0);       // 无效，开发模式下控制台给出警告
const str = reactive("hello"); // 同样无效，返回原字符串
```

> [!CAUTION]
> **注意内容**：对原始值调用 reactive 不抛异常、只在开发模式告警，问题容易潜伏到运行时才暴露；凡是要包装值类型，直接条件反射地选 ref。

**速记**：reactive **只收对象**，原始值找 ref。



### ref 与 reactive 的选型

#### 组合式 API 主推 ref

**选型结论**：组合式 API 下**默认用 ref**，仅当需要就地聚合一批强关联状态时才用 reactive。

- ref 支持**整体赋值**：把新对象赋给 value，一行完成整包更新，引用不变。
- ref 作为函数返回值、作为组合式函数的产物都**不会丢失响应**，行为可预期。
- reactive 的三大局限（换对象断线、解构断线、只收对象）在 ref 身上都不存在。

```js
import { ref } from "vue";

function useCounter() {
  const count = ref(0);
  function increment() {
    count.value++;
  }
  return { count, increment }; // ref 返回后响应式依旧
}
```

> [!IMPORTANT]
> **重要内容**：官方文档明确建议默认使用 ref，理由正是它对整体赋值与函数返回更友好；reactive 适合就地组织一批不再整体替换、也不解构的状态结构。

**速记**：默认 **ref**，局部成组才 **reactive**。



#### 官方建议与混用守则

**混用守则**：两者可共存于同一组件，守住几条边界即可安心并用。

- 状态主体用 **ref**；一个业务域内多个强关联字段可用 **reactive** 就地聚合。
- reactive 的属性值可以是 ref，属性访问时自动解包；ref 的 value 里也可以放 reactive 代理，深层响应式照常生效。
- 团队内**统一一种默认**比纠结单点差异更重要：以 ref 为主，能显著减少心智负担。

```js
import { ref, reactive } from "vue";

const form = reactive({
  keyword: ref("") // ref 入 reactive，属性访问自动解包
});

form.keyword = "vue"; // 无需写 value，已解包
```

> 两者并非对立：ref 负责对外、负责整体，reactive 负责内部组织；记住**状态入口用的是谁**，就守住谁的规则，解包差异便不会踩坑。

**速记**：**ref 对外、reactive 对内**，入口统一。



### DOM 更新时机与 nextTick

#### 更新是批量且异步的

**异步批量更新**：修改响应式状态后，DOM **不会立刻**更新；Vue 把同一轮的多次修改收集起来，等下一个时机统一渲染。

- 连续多次赋值只触发**一次**渲染，中间状态被合并，这是性能层面的关键设计。
- 同步代码读到的 DOM 永远是**上一次渲染**的结果，与刚修改的状态有一拍之差。
- 批量刷新借助**微任务队列**调度，与事件循环机制同源。
- 合并渲染还顺带避免了**同一帧内的多次重排与重绘**：浏览器只需按最终状态画一次。

```js
import { ref, nextTick } from "vue";

const count = ref(0);

async function addTwice() {
  count.value++;
  count.value++;
  console.log(document.getElementById("count").textContent); // 旧值 0
  await nextTick();
  console.log(document.getElementById("count").textContent); // 2，已合并渲染
}
```

> [!NOTE]
> **提醒内容**：修改状态后立刻读 DOM 拿到的是旧内容，这不是缺陷而是批量更新的正常表现；需要读到更新后的 DOM 时，请使用 nextTick。

**速记**：改完不立刻渲染，**攒一波统一刷**。



#### nextTick 在 DOM 更新后执行回调

**nextTick**：返回一个 Promise，在 **DOM 更新完成后**兑现，用于在视图刷新之后再执行依赖新 DOM 的逻辑。

- 支持**回调版** nextTick(callback) 与 **await 版** await nextTick()，二者等价，按团队习惯选择。
- 其实现基于**微任务**：调度时机与 JavaScript 系列的《32. async、await 与事件循环.md》中 Promise.then 的微任务机制一致，微任务先于下一次渲染周期收尾。
- 典型场景：更新列表后滚动到底部、渲染后聚焦输入框、读取新尺寸做测量。

```js
import { ref, nextTick } from "vue";

const list = ref([]);
const inputEl = ref(null);

async function addItem(text) {
  list.value.push(text);
  await nextTick();     // 等新节点真正插入 DOM
  inputEl.value.focus(); // 此刻聚焦才不会丢失
}
```

> [!TIP]
> **建议内容**：能用 nextTick 解决的 DOM 时序问题，不要用 setTimeout 凑合；setTimeout 依赖宏任务排队，时机不如微任务精确，还平白引入延迟。

**速记**：等 DOM 刷新完再动手，**await nextTick()**。



### 响应式原理引子

#### 响应式基于 Proxy 拦截读写

**原理引子**：Vue3 响应式的底座是 **Proxy**：get 捕获器里**收集依赖**，set 捕获器里**触发更新**。

- **track 与 trigger**：读取属性时把当前副作用函数记入依赖表，修改属性时找出依赖并重新执行，渲染函数因此自动重跑。
- ref 的 value 读写与 reactive 的属性读写，最终都汇入同一套依赖收集体系。
- 相比 Vue2 的 Object.defineProperty，Proxy 能拦截**新增属性、删除操作与数组索引**，且无需遍历预处理。

```js
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key); // 读取时登记依赖
      return Reflect.get(target, key, receiver);
    },
    set(target, key, value, receiver) {
      const result = Reflect.set(target, key, value, receiver);
      trigger(target, key); // 写入时通知更新
      return result;
    }
  });
}
```

> 依赖收集的存储结构（WeakMap 套 Map 套 Set）与完整手写实现，见本系列《17. 响应式原理：Proxy 与依赖收集.md》与 JavaScript 系列的《29. Proxy、Reflect 与响应式.md》。

**速记**：get **收依赖**，set **发通知**，全靠 Proxy。
