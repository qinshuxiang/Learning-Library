## 渲染机制与 render 函数

### 模板编译流水线

#### parse 阶段把模板解析为 AST

**parse 阶段**：是模板编译的第一步，把模板字符串解析成 AST（抽象语法树），即用 JavaScript 对象树描述模板的结构。

- 输入是单文件组件的 template 块或 DOM 内模板，本质是一段符合 HTML 语法的字符串。
- 输出是一棵 AST，每个节点是一个普通 JS 对象，记录标签名、属性、子节点、位置信息等。
- 解析过程借助 HTML 的结构规则逐段切分：遇到开标签、闭标签、文本、注释分别生成对应节点并入树。
- AST 是后续所有处理的中介形态，模板不再以字符串身份参与，而是以对象树身份被加工。

```text
<div id="app">
  <p>{{ count }}</p>
</div>
```

> 上述模板经 parse 后会得到一棵三层对象树：div 节点带 id 属性，其下挂一个 p 节点，p 的文本是一个插值表达式节点。parse 只负责结构化，不做任何优化，优化由下一阶段接管。

**速记**：parse 是**模板字符串进、AST 对象树出**的结构化一步。



#### transform 阶段转换 AST 并标记优化信息

**transform 阶段**：是编译的第二步，对 AST 做一系列插件式转换，并在此打上编译优化的关键标记。

- 遍历整棵 AST，依次应用一组转换器，例如处理 v-model 与 v-on 的糖语法、转换插槽表达式。
- 给纯静态节点打上静态标记，为静态提升做准备。
- 给动态节点打上 patchFlags，标注它到底哪一部分会变，是文本、类名还是属性。
- 确定 block 节点边界，让运行时更新时可以只遍历动态节点。

> [!IMPORTANT]
> **重要内容**：transform 是 Vue 编译优化的主战场，静态提升、patchFlags、block tree 这三大优化全部在这一阶段生成。没有 transform 的加工，运行时只能做传统虚拟 DOM 的全量比较。

**速记**：transform **既改写又打标**，是编译时优化的发生地。



#### generate 阶段生成 render 函数代码

**generate 阶段**：是编译的最后一步，把加工后的 AST 序列化为 render 函数的 JavaScript 代码字符串。

- 输出的代码里，节点创建统一表现为 createVNode 一类调用，静态内容表现为提前声明的变量。
- 动态节点以带 patchFlags 参数的调用出现，供运行时按标记做靶向更新。
- 单文件组件由 vue-loader 与 vite-plugin-vue 在构建期执行这三个阶段；运行时版本的编译器则可在浏览器里现场编译。

```js
// 模板：<p>计数：{{ count }}</p> 经编译后大致生成的代码
import { createVNode as _createVNode, openBlock as _openBlock, createBlock as _createBlock } from "vue";

function render(_ctx, _cache) {
  return (_openBlock(), _createBlock("p", null, "计数：" + _ctx.count, 1 /* TEXT */));
}
```

> [!NOTE]
> **提醒内容**：浏览器内完整版包含编译器，运行时版只含运行时。脚手架项目一律预编译模板，打包产物里并不存在模板字符串，也不需要编译器。

**速记**：generate **把 AST 翻译成 render 函数源码**，模板到此退役。



### 虚拟 DOM 的定义与动机

#### 虚拟 DOM 是用 JS 对象描述节点树的结构

**虚拟 DOM**：是用普通 JavaScript 对象来描述真实 DOM 树的中间表示，每个对象对应一个真实或逻辑的节点。

- 一棵组件树对应一棵虚拟 DOM 树，树上的每个对象称为 VNode（虚拟节点）。
- VNode 是纯数据结构，不含真实 DOM 引用，创建与比较都是普通 JS 运算。
- 渲染时由运行时依据虚拟树一次性生成真实 DOM，更新时先比虚拟树再改真实 DOM。
- 真实 DOM 是平台对象，操作成本高；虚拟 DOM 把渲染决策转移到便宜的一侧。

> 虚拟 DOM 不是渲染结果的缓存，而是渲染的蓝图。它让框架先在数据层面算清楚要改什么，再动手触碰真实页面。

**速记**：虚拟 DOM 是**页面的 JS 蓝图**，先算后改。



#### 虚拟 DOM 以 JS 计算换取 DOM 操作成本

**核心动机**：虚拟 DOM 用便宜的 JS 计算替代昂贵的 DOM 操作，把每次更新的改动量压到最小。

- 真实 DOM 操作会触发重排与重绘，代价远高于纯 JS 运算。
- 直接操作 DOM 的手写代码难以保证最小改动，容易整块重建。
- 更新时先对新旧两棵虚拟树做 diff 比较，得到最小补丁集合，再按补丁更新真实 DOM。
- 虚拟树与平台解耦，同一套描述可映射到浏览器 DOM 之外的目标，如自定义渲染器。

> [!TIP]
> **建议内容**：理解动机时记住一笔账：多花一次 JS 层的树比较，换来真实 DOM 只做必要改动。数据驱动的声明式框架正是依赖这笔交换才成立。

**速记**：虚拟 DOM **拿 diff 的计算，换 DOM 的操作**。



### VNode 的结构要点

#### VNode 的核心字段描述一个节点

**VNode 结构**：一个 VNode 对象由若干关键字段组成，合起来足以描述一个节点该如何渲染。

- **type**：节点类型，可以是 HTML 标签名字符串、组件对象、异步组件或特殊类型占位。
- **props**：属性与元信息，包括普通 attribute、组件 prop、事件监听器、指令附加信息等。
- **children**：子节点，可以是文本字符串、VNode 数组或描述插槽的对象三种形态。
- **key**：同层节点的身份标识，列表更新时用于判定复用关系。
- **shapeFlag 与 patchFlag**：形状标记与补丁标记，供运行时快速判断节点形态与动态部位，由编译时或运行时生成。
- **el**：节点渲染后指向对应真实 DOM 的引用，卸载与更新时依赖它定位。

> type 与 children 的组合决定了节点的形态分支：type 是标签则 children 走元素逻辑，type 是组件则 children 走插槽逻辑，这也是 children 存在三种形态的原因。

**速记**：VNode 看四样——**type 定身份、props 定属性、children 定内容、key 定复用**。



#### key 是同层节点的身份标识

**key 字段**：是给 VNode 标注身份的属性，运行时依据它判断同层节点之间能否复用。

- 同层比较时，key 相同视为同一节点，走就地更新；key 不同则视为不同节点。
- 不写 key 时，框架退化为按索引原位对应，称为就地复用策略。
- key 必须在同级之间唯一且稳定，通常取业务数据的主键。

> [!CAUTION]
> **注意内容**：用数组索引当 key，在插入、删除、排序场景下会让身份错位，导致状态串位与多余更新。数据有稳定主键时务必用主键作 key，细则见《5. 条件渲染与列表渲染.md》。

**速记**：key 是**同层的身份证**，要稳定唯一，莫用索引凑数。



### h 函数

#### h 函数的签名与参数

**h 函数**：是手写虚拟 DOM 的入口，签名完整写出为 h(type, props, children)，三个参数分别对应 VNode 的三大字段。

- 第一个参数 type：标签名字符串、组件对象或特殊占位类型。
- 第二个参数 props：可选，对象形式，装 attribute、prop 与事件监听器。
- 第三个参数 children：可选，子内容，接受字符串、数组或对象三种形态。
- h 返回的就是一个 VNode，它本身不执行渲染，只负责创建虚拟节点描述。

```js
import { h } from "vue";

const vnode = h("button", { class: "btn", onClick: submitForm }, "提交");
```

> h 一词源自 hyperscript，意为创建 HTML 的辅助函数。Vue 内部编译产物里的 createVNode 与 h 同源，二者只是调用习惯不同。

**速记**：h(type, props, children) **三参造 VNode**，只描述不渲染。



#### children 的三种形态

**children 形态**：第三个参数按内容性质分为字符串文本、VNode 数组与对象插槽三种形态。

- **字符串**：表示纯文本子节点，例如 h("p", null, "你好")。
- **数组**：表示一组子节点，元素仍是 h 的返回值，用于表达嵌套结构。
- **对象**：表示插槽，键是插槽名，值是返回 VNode 的函数，用于给组件传内容。

```js
import { h } from "vue";

// 字符串：纯文本
h("p", null, "纯文本子节点");

// 数组：多个子节点
h("ul", null, [
  h("li", null, "第一项"),
  h("li", null, "第二项"),
]);

// 对象：具名插槽
h(CardPanel, null, {
  header: () => h("h3", null, "标题"),
  default: () => h("p", null, "正文"),
});
```

> 无 props 可传时可以省略第二个参数，把 children 直接提到第二位，写成 h("p", "文本")，这是 h 的参数重载约定。

**速记**：children **字符串成文本、数组成子树、对象成插槽**。



#### h 函数的基础示例与事件绑定

**事件绑定**：在 h 的 props 里以 on 开头加事件名的驼峰形式注册监听器，点击事件即 onClick。

- 事件监听器命名遵循 onXxx 规则，DOM 原生事件与自定义事件统一走这一形态。
- 普通属性如 class、style、id、disabled 直接写在 props 对象中。
- props 为空时可传 null 占位，让第三个参数对齐 children 的位置。

```js
import { h, defineComponent, ref } from "vue";

const ClickCounter = defineComponent({
  setup() {
    const count = ref(0);
    const increaseCount = () => count.value++;

    return () =>
      h("div", null, [
        h("p", null, `当前计数：${count.value}`),
        h("button", { onClick: increaseCount }, "加一"),
      ]);
  },
});
```

> setup 返回一个渲染函数，就等价于组件的 render。count 是 ref，在渲染函数中被读取，于是它成为该渲染 effect 的依赖，count 变化会触发组件重新渲染。

**速记**：事件写在 props 里，**on 加事件名**，onClick 即点击。



### 更新机制

#### 渲染 effect 驱动组件重新渲染

**渲染 effect**：每个组件实例在挂载时创建一个渲染副作用，render 执行期间读到的响应式数据都会被收集为依赖，数据变化时该副作用重新执行。

- setup 返回渲染函数后，运行时把渲染函数包进一个 effect 并立即执行一次，完成首次渲染。
- render 中读取的 ref 与 reactive 属性，成为这个 effect 的依赖集合。
- 依赖变化时，运行时重新调用 render 得到一棵新虚拟树，交给 patch 与旧树比较。
- 渲染粒度是组件级的：一个组件数据变化只重跑该组件的 render，不牵连其他组件。

> [!IMPORTANT]
> **重要内容**：Vue 的更新单位是组件而非整棵应用树。这也是为什么跨层级共享状态要靠 props 传递或状态管理，而不是指望父组件数据直接触发深层组件刷新。

**速记**：**谁在 render 里读了数据，数据变就重渲染谁**。



#### patch 比较新旧 VNode 树并复用或替换

**patch 过程**：是把新虚拟树与旧虚拟树逐节点比较，据比较结果对真实 DOM 做最小更新的核心算法。

- 新旧节点同类型时复用真实 DOM，只更新变化的 props 与 children，这一过程称为就地更新。
- 新旧节点不同类型时卸载旧节点、挂载新节点，其整棵子树随之一并替换。
- 节点类型为组件时，patch 走组件更新分支，触发子组件实例自身的渲染 effect。
- patchFlags 在这里发挥作用：运行时按标记只检查动态部位，静态部分直接跳过。

> [!WARNING]
> **警告内容**：不同类型节点替换时，旧节点内部的状态随之销毁。两个结构相近的分支若被框架判为不同类型，切换即意味着整棵子树重建，表现为输入框内容丢失、动画重播，此时应排查两个分支的根元素或根组件是否同类型。

**速记**：patch 口诀——**同型复用改差异，异型卸旧挂新的**。



#### key 决定列表 diff 的复用关系

**key 的复用作用**：列表更新时，patch 借助 key 把新旧子节点配对，决定哪些节点原位更新、哪些移动、哪些增删。

- 有稳定 key 的列表，框架按身份匹配，数据顺序变化对应 DOM 节点的移动而非内容重写。
- 依赖 key 匹配后，节点内部的组件状态、焦点、选区都能在位置变化时保持。
- 无 key 时按索引配对，索引变了身份就变，表现为整列内容重写。

> 《5. 条件渲染与列表渲染.md》中的 v-for 与 key 规则，正是本节更新机制在列表场景的直接应用；理解 patch 后，那一章的诸多建议不再需要死记。

**速记**：key 让 diff **按身份配对**，移动节点而非重写内容。



### 编译时优化

#### 静态提升 hoistStatic 避免重复创建节点

**静态提升**：是编译器把模板中不会变化的节点或属性对象提取到 render 函数外声明的优化，整棵应用生命周期内只创建一次。

- 提升后的静态 VNode 在 render 外声明，每次渲染直接复用引用，省去重复创建对象的开销。
- 纯静态的属性对象同样被提升，避免每次渲染都新建对象触发垃圾回收。
- 连续静态节点构成的超大子树，编译器会进一步压缩处理，减少虚拟树体积。

```js
// 模板：<div><span>固定文案</span><span>{{ msg }}</span></div> 编译后大致如下
import { createVNode as _createVNode, openBlock as _openBlock, createBlock as _createBlock } from "vue";

const _hoisted_1 = _createVNode("span", null, "固定文案", -1 /* HOISTED */);

function render(_ctx, _cache) {
  return (_openBlock(), _createBlock("div", null, [
    _hoisted_1, // 静态节点，引用复用
    _createVNode("span", null, _ctx.msg, 1 /* TEXT */),
  ]));
}
```

> 提升的前提是编译期能确定内容永不变更。手写 render 时无法被静态分析，因此享受不到这一优化，这是两种写法成本差异的典型例子。

**速记**：静态提升 = **render 外建一次，render 内用 N 次**。



#### patchFlags 标注节点的动态部位

**patchFlags**：是编译器给动态 VNode 打上的数字位掩码标记，向运行时指明该节点究竟哪一部分会变。

- 标记按二进制位区分内容：文本动态、类名动态、样式动态、属性动态等各有独立位。
- 一个节点可以叠加多个标记，运行时按位判断走哪条更新分支。
- 更新 props 时，运行时只比对被标记涵盖的字段，不再全量遍历属性对象。
- 特殊值 -1 表示静态节点，永不参与更新比较。

```text
TEXT        = 1    // 动态文本内容
CLASS       = 2    // 动态 class
STYLE       = 4    // 动态 style
PROPS       = 8    // 动态属性（不含 class 与 style）
FULL_PROPS  = 16   // 属性名本身动态，需全量比对
HOISTED     = -1   // 静态节点，跳过更新
```

> [!TIP]
> **建议内容**：记不全具体数值无妨，记住设计意图即可：patchFlags 是编译器写给运行时的便签，告诉它别看无关部位。手写 render 需要自行给 createVNode 或 createBlock 的第四个参数传入标记才能享受同等优化。

**速记**：patchFlags 是**动态部位的位掩码便签**，更新按位查。



#### block tree 让更新只遍历动态节点

**block tree**：是编译器与运行时协作生成的优化结构，把组件虚拟树中的动态后代节点收集成一个扁平数组，更新时只遍历这个数组，跳过一切静态内容。

- 组件渲染时以 openBlock 开启收集，以 createBlock 创建 block 节点，动态后代在创建过程中被登记进数组。
- 传统虚拟 DOM diff 需要递归遍历整棵树，树越大静态内容越多，无效比较越多。
- block tree 下更新只走扁平数组，遍历量与动态节点数成正比，与静态内容多少无关。
- v-if、v-for 等结构会产生嵌套 block，保证结构性变化时动态节点收集仍然正确。

> [!IMPORTANT]
> **重要内容**：block tree 与 patchFlags、静态提升合称 Vue 模板编译优化的三板斧，共同把模板的更新成本从全树 diff 压缩到靶向更新。手写 render 放弃的正是这三样，选型时必须计入这笔账。

**速记**：block tree **只数动态节点**，静态内容直接跳过。



### 何时需要 render 函数

#### 模板语法表达不了的场景才动用 render

**render 的定位**：模板是默认首选，render 函数只在模板语法表达不了或表达成本过高的场景启用。

- **动态标签名**：标签本身由变量决定时，模板里写不了，render 里把变量直接传给 h 即可。
- **高度动态结构**：节点层级与数量完全由数据递归生成，写模板会退化成大量套壳组件。
- **程序化生成内容**：需要按条件拼装复杂的节点序列，用 JS 逻辑组织比堆指令更清晰。
- 绝大多数常规页面结构、条件与循环，模板都完全胜任，不必为炫技换 render。

```js
import { h } from "vue";

// 动态标签名：标题层级由数据决定
function renderHeading(level, text) {
  return h(`h${level}`, null, text);
}
```

> 判断标准是表达力而非熟悉度：模板写得出来就用模板，写不出来再上 render。先模板后 render 的次序能让编译优化为你所用。

**速记**：**模板能写就模板，表达不了才 render**。



#### defineComponent 与函数式组件提供轻量封装

**函数式组件**：是一个只接受 props 与上下文、直接返回 VNode 的普通函数，没有组件实例，也不含响应式状态与生命周期。

- 定义形式就是一段函数：function GreetingTag(props) 返回 h 调用的结果。
- 注册与使用方式与普通组件相同，模板里照常书写标签。
- 无实例意味着无 this、无状态缓存，开销最小，适合纯展示的包装节点。
- defineComponent 本身不改变行为，它只是给组件定义对象提供类型提示，让 render 与 props 获得完整推导。

```js
import { h, defineComponent } from "vue";

// 函数式组件：无实例，纯映射
function GreetingTag(props) {
  return h("span", { class: "greeting" }, `你好，${props.name}`);
}
GreetingTag.props = ["name"];

// defineComponent 提供类型推导的正常组件
const FarewellTag = defineComponent({
  props: { name: String },
  setup(props) {
    return () => h("span", null, `再见，${props.name}`);
  },
});
```

> [!NOTE]
> **提醒内容**：函数式组件适合无状态包装；一旦需要内部状态或生命周期钩子，就应回到 defineComponent 定义的常规组件，二者不是互相替代关系。

**速记**：函数式组件**是函数、无实例、纯映射**；defineComponent 管**类型推导**。



### JSX 支持

#### JSX 经插件编译后与 h 完全等价

**JSX 支持**：通过 @vue/babel-plugin-jsx 插件，可以在 Vue 组件中书写 JSX 语法，构建时被编译为对应的 createVNode 调用。

- 插件负责把 JSX 语法转换为等价的虚拟节点创建代码，运行时行为与手写 h 一致。
- 事件绑定写 onClick，属性写法贴近 HTML，插槽用花括号表达式直接书写。
- class、style 支持对象写法，插件会做对应转换。
- 需要在构建配置中安装并注册该插件，Vite 项目对应 @vitejs/plugin-vue-jsx。

```js
// 以下两种写法编译结果等价
import { h } from "vue";

function renderH(props) {
  return h("button", { class: "btn", onClick: props.onSubmit }, "确认");
}

function renderJsx(props) {
  return <button class="btn" onClick={props.onSubmit}>确认</button>;
}
```

> [!TIP]
> **建议内容**：JSX 的适用场景与 render 相同且书写更顺手：熟悉 JSX 的团队迁移成本低、复杂渲染逻辑表达更自然。但它在编译优化上与手写 render 同等受限，模板能覆盖的场景仍优先模板。

**速记**：JSX = **h 的语法糖**，表达友好但优化待遇与 render 相同。



### 模板与 render 的选型辨析

#### 模板用约束换优化，render 用灵活失提升

**选型核心**：模板与 render 的取舍，本质是编译时优化与表达自由度之间的交换。

- **模板**：语法受指令集约束，表达力有限；但静态可分析，编译器得以实施静态提升、patchFlags 与 block tree，运行时更新更快。
- **render 与 JSX**：可使用任意 JS 表达式，动态结构表达自由；但编译器无法静态分析其输出，优化三板斧基本失效，退回相对通用的虚拟 DOM 更新路径。
- 团队协作与可维护性上，模板结构直观、上手门槛低；render 逻辑集中、利于复杂抽象。
- 常见工程实践是模板为绝对主流，render 与 JSX 作为局部逃生舱。

> [!CAUTION]
> **注意内容**：把全项目改写为 render 或 JSX 不会带来性能收益，反而失去编译优化的红利。性能敏感的常规界面应坚持模板，只有动态性超出模板表达力的部分才局部降级到 render。

**速记**：模板**受约束换优化**，render **得灵活失提升**，默认模板。



### Vapor 模式展望

#### Vue 3.6 Vapor 模式探索免虚拟 DOM 的编译方向

**Vapor 模式**：是 Vue 3.6 正在研发的编译策略，方向是编译期直接生成响应式绑定到 DOM 的更新代码，绕开虚拟 DOM 与运行时 diff。

- 传统模式先产出虚拟树再 diff，Vapor 模式在编译时就确定每个动态部位与数据的绑定关系。
- 更新时直接改写对应 DOM 属性，不再创建 VNode、不再比较树，运行时体积与更新开销都有望下降。
- 计划与传统虚拟 DOM 组件互操作，存量组件可逐步迁移，而非整体推翻。
- 截至目前的口径均为在研特性，具体 API、兼容范围与发布节奏以官方文档为准。

> [!NOTE]
> **提醒内容**：Vapor 模式说明的是演进方向而非既成事实，学习时把握编译时直接绑定这一思路即可，不要据此提前改造现有代码，特性落地细节以 Vue 官方发布的稳定版说明为准。

**速记**：Vapor 方向是**编译时直连 DOM，省去虚拟 DOM 中间层**。
