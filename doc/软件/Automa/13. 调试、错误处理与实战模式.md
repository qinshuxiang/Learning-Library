## 调试、错误处理与实战模式

### 调试手段

#### 日志与单块运行

**调试工作流的三板斧**：日志、单块运行、逐步执行。

- 运行日志：每次执行的块级记录，成功失败与耗时一目了然
- 单块运行：编辑器里直接运行某个块，快速验证参数
- 从指定块开始执行：跳过已验证的前段，直奔问题现场
- 表达式的求值结果可在配置面板预览

> 调试纪律与写代码一致：缩小范围、单变量验证。全流程跑一遍看日志只能知道“哪里坏了”，单块运行才能知道“为什么坏”。

**速记**：**日志找位置，单块找原因**。



#### 常见失败与排查

**高频失败集中在四类**：选择器、等待、超时与数据形状。

- 选择器失效：页面改版导致元素找不到，去 DevTools 重新验证
- 等待不足：元素没加载就操作，改事件驱动等待（3 篇）
- 超时中断：代码块默认 20 秒预算耗尽，拆块或重置（8 篇）
- 数据形状错位：表格列名与写入键不匹配、表达式路径写错（5、6 篇）

> 排查顺序从便宜到贵：先看日志确认失败块，再单块复现，再检查选择器与数据形状，最后才怀疑执行环境（浏览器版本、扩展权限）。环境类问题一天一现，别一上来就怀疑玄学。

**速记**：**选择器、等待、超时、形状，四坑按序排**。



### 错误处理

#### 块级与流程级容错

**容错分两层设计**：块的重试与流的分支。

- 块级：失败重试次数与间隔，对付瞬时抖动
- 流程级：条件块判断错误标记，决定重跑、跳过或告警
- 代码块内部 try 处理 JS 异常，失败写标记变量后正常续流（11 篇）
- 工作流全局的失败出口：统一接通知或 Webhook 告警

> 容错设计的目标是“失败也是数据”：错误有标记、有记录、有出口，而不是流程无声中断。无人值守任务的第一要求就是坏也坏得明白。

**速记**：**块管抖动流管分支，失败也要留名**。



#### 幂等与重跑

**可靠的定时任务必须是幂等的**：重跑不产生重复数据。

- 幂等设计：同样的输入跑两次，结果一致且不重复入库
- 手段：写入前查重（表格或目标系统）、按日期命名导出文件覆盖旧版
- 子工作流拆分时，每段保持独立可重跑
- 记录执行水位（处理到哪一页、哪一条），重跑从断点继续

> 幂等是无人值守的入场券：不能幂等的流程，一次失败就要人工清场。设计工作流时先问“跑到一半挂了怎么办”，答不上来就还不够格上定时。

**速记**：**重跑无害叫幂等，水位记录续断点**。



### 实战模式

#### 模式一：列表抓取流水线

**抓取类的标准工作流模板**：五个部件拼装。

- 触发器（定时或手动）加 Global Data 传入关键词
- 循环翻页（While 加下一页存在判断）
- 页内循环元素或 JS 代码块抽取列表数据
- 数据表累积，循环结束导出 CSV
- Webhook 推送结果摘要

> 本系列各篇的骨架在这里合体：触发与执行（2 篇）、选择与操作（3 篇）、循环（4 篇）、数据表（5 篇）、表达式（6 篇）、代码块抽取（10 篇）、导出与通知（12 篇）。先照模板搭一遍，再按目标站点微调。

**速记**：**传参、翻页、抽取、导出、推送，五件套成流**。



#### 模式二：表单批量提交

**表单自动化模板**：数据源驱动加校验等待。

- 数据源：Sheets 或 API 提供每行的表单数据
- 循环数据块逐行驱动：导航到表单页、逐字段填写（3 篇表单交互）
- 提交前等待校验完成，提交后等成功提示元素出现
- 结果（成功或错误信息）写回数据表，失败行单独标记

> 表单流的难点在校验时机：填完不等于能交，提交后不等于成功。每个“点提交”动作后必须跟一个“等结果元素”的判断，这是成功率与数据可信度的分水岭。

**速记**：**数据源驱动，填后等校验，交后等回执**。



#### 模式三：定时巡检与告警

**巡检类工作流的模板**：轻量、稳定、必告警。

- 定时触发（如每小时）：打开目标页，检查关键元素或数据
- 异常判断：内容缺失、数值越界、页面报错
- 正常时静默结束，异常时通知块或 Webhook 告警
- 巡检结果（正常也记一条）写入日志表，留运行痕迹

> 巡检流的价值在“安静”：大多数执行无事发生，通知只在该响时响。告警疲劳比没有告警更危险——正常也推送的巡检，一周后就会被无视。

**速记**：**安静巡检，异常才响，留痕可查**。
