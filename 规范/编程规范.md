# 编程规范

## 通用规则

### 编码前思考

**不要假设。不要隐藏困惑。把权衡摆出来。**

动手实现之前：

- 明确声明你的假设。不确定就问。
- 存在多种理解时，全都摆出来，不要默默选定一种。
- 有更简单的做法就说出来，该反驳时反驳。
- 有不清楚的地方就停下来。指出困惑点。发问。



### 简洁优先

**用最少的代码解决问题。不做任何推测性的设计。**

- 不加要求之外的功能。
- 不为一次性代码创建抽象。
- 不加没人要求的「灵活性」或「可配置性」。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而其实 50 行就够，就重写。

问自己一句：「资深工程师会不会觉得这太复杂？」会，就简化。



### 精准修改

**只碰必须碰的。只清理自己制造的混乱。**

编辑现有代码时：

- 不要「改进」相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 沿用现有风格，哪怕你自己更习惯另一种写法。
- 发现无关的死代码，提一句即可，不要删。

当你的改动制造出孤儿代码时：

- 删除**因你的改动**而变得无用的导入、变量、函数。
- 不要删除本就存在的死代码，除非明确要求。

检验标准：每一行改动都应能直接追溯到用户的请求。



### 目标驱动执行

**定义成功标准。循环验证直到达成。**

把任务转成可验证的目标：

- 「加校验」→「为非法输入写测试，然后让测试通过」
- 「修这个 bug」→「写一个能复现它的测试，然后让测试通过」
- 「重构 X」→「确保重构前后测试都通过」

多步任务要先给出简短计划：

```text
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强的成功标准让你能自行循环推进；弱的标准（「让它能跑」）会迫使你反复澄清。



## 技术栈

### 前端

- **启动**：Vue3（组合式 API）＋ Vite，默认不使用 TypeScript；Node 26。
- **组件**：shadcn-vue ＋ Tailwind；组件源码直接复制进仓库（`src/components/ui/`）。
- **样式**：SCSS；全局变量与 mixin 收敛在 `src/styles/`，不散落组件内。
- **请求**：axios；统一封装实例。
- **存储**：pinia；按业务模块拆分 store，命名 `useXxxStore`。



### 后端

- **启动**：Express，默认装 5.x。
- **限流**：敏感操作（登录、refresh）必须限流。



### 数据库

- MongoDB 8、MySQL 26、PostgreSQL 18、Redis 8，按项目需要选用，默认不引入清单之外的数据库。



### 工具与环境

- **环境**：macOS，包管理 pnpm 12。
- **工具**：Git 2.55、gh 2.101、nginx 1.31、ffmpeg 9。
- **代码评审**：OpenCodeReview 1.12（命令 `ocr`），提交前对 Git diff 做行级 AI 评审；模型端点用 `ocr config provider` 配置，要求 Git ≥ 2.41。
- **Git 提交与协作规则**：见协作偏好.md「Git 操作」节（提交流程、ocr review 嵌入、自动提交与仓库检查）。
