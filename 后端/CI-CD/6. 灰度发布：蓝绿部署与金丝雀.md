## 灰度发布：蓝绿部署与金丝雀

### 为什么需要灰度

#### 全量发布的风险

**全量发布**：新版本一瞬间替换全部实例，任何未发现的问题都会同时影响所有用户。

- 测试覆盖再全也有盲区：真实流量、真实数据规模、真实客户端行为只有线上才有。
- 全量发布一旦出问题，**爆炸半径是 100%**，且回滚窗口内持续有用户受影响。
- 灰度的思路是**控制爆炸半径**：先让小部分流量接触新版本，验证后再逐步放量。

> 灰度发布的本质不是技术炫技，而是**把「发布」和「出问题」解耦**：发布照常进行，问题被限制在小流量内，回滚只影响灰度用户。用户量大、迭代频繁的系统，灰度是必选项而不是可选项。

**速记**：灰度＝**先小流量验证，再逐步放量**，控制爆炸半径。



### 蓝绿部署

#### 两套环境切换流量

**蓝绿部署（Blue-Green Deployment）**：同时准备两套完整环境，蓝跑旧版、绿部署新版，验证后把流量从蓝整体切到绿。

```nginx
# Nginx upstream 切换：把 default 从 blue 改为 green 后 reload
upstream default {
    server 127.0.0.1:3001;   # blue：当前生产
}

upstream green {
    server 127.0.0.1:3002;   # green：新版本
}
```

```nginx
# 切换前：default upstream 指向 blue（3001）
upstream default {
    server 127.0.0.1:3001;
}

# 切换后：只改 server 行为 3002，再平滑重载
upstream default {
    server 127.0.0.1:3002;
}
```

```bash
# 切换动作：改配置指向 + 平滑重载（不断开现有连接）
nginx -t && nginx -s reload
```

- **切换是秒级原子操作**：改 upstream 指向＋reload，不存在「部署了一半」的中间态。
- 回滚同样秒级：把指回切回去即可。
- 代价是**双倍资源**：蓝绿两套环境同时在线，资源成本翻倍。
- 切换后蓝环境保留一段时间，用于快速切回与问题排查，确认稳定后再下线或复用。

> 蓝绿适合**资源充裕、要求切换原子性**的场景。数据库是蓝绿之外的独立变量：新旧版本共库时，蓝绿只解决了代码切换，**结构兼容问题仍然存在**（见第 5 章的两段式迁移）。

**速记**：蓝绿＝**两套环境、一次切换**，秒级回滚、双倍资源。



### 金丝雀发布

#### 小比例流量逐步放量

**金丝雀发布（Canary Release）**：新版先承接一小部分流量（如 5%），观察指标正常后逐步放大比例，直至全量。

```nginx
# Nginx 加权 upstream：canary 承接 5% 流量
upstream app {
    server 127.0.0.1:3001 weight=95;   # stable
    server 127.0.0.1:3002 weight=5;    # canary
}
```

- **放量节奏**：5% → 25% → 50% → 100%，每一档停留观察一段时间再进下一档。
- 每档观察的判据是**可观测指标**：错误率、P95 延迟、关键业务量对比新旧两组数据。
- 任何一档指标异常，权重改回 0 即完成回切，灰度用户以外的用户全程无感。
- 无会话粘性的前提下，要求新旧版本**共用数据库且结构互相兼容**，否则按用户分流（同一用户固定进同一版本）。

> 金丝雀的可靠性来自**指标说话**：没有监控指标对比，5% 流量放出去也看不出问题。先有第 5 章的健康检查与基础监控，灰度才有决策依据——**没有可观测性的灰度只是盲测**。

**速记**：金丝雀＝**加权分流、分档放量、指标决策、权重归零即回切**。



### 策略对比与选型

#### 三种发布策略对比

**选型逻辑**：以回滚速度、资源成本、实现复杂度三个维度衡量，小项目从滚动或蓝绿起步，迭代快、流量大再上金丝雀。

| 策略 | 回滚速度 | 资源成本 | 实现复杂度 | 适用场景 |
|---|---|---|---|---|
| 滚动发布 | 中（逐实例回退） | 低（复用实例） | 低 | 实例多、无硬性切换要求的常规更新 |
| 蓝绿部署 | 秒级（切回 upstream） | 高（双倍环境） | 中 | 要求原子切换、资源充裕 |
| 金丝雀 | 秒级（权重归零） | 中（多一组灰度实例） | 高（需指标监控与分流） | 流量大、迭代频繁的核心服务 |

- **滚动发布**：逐个或分批替换实例，最朴素的默认策略，Docker Compose 多实例与 Kubernetes 默认滚动更新都是它。
- 三种策略不互斥：先用蓝绿保证切换原子性，蓝绿内部再按金丝雀放量，是大型系统的常见组合。
- 个人项目与低流量服务：滚动发布＋快速回滚脚本（第 5 章）已经足够，灰度体系可后置。

> 策略没有先进落后，只有**与故障容忍度匹配与否**。判断标准是一句话：这个服务出 10 分钟故障的代价，值不值得为它维持双倍资源或一套监控分流体系。

**速记**：**小项目滚动＋秒回滚，核心服务蓝绿＋金丝雀**，按故障代价选型。

**警告内容**：灰度期间新旧版本并行，**数据库结构必须同时兼容两个版本**——这正是第 5 章两段式迁移存在的原因。灰度未结束就执行破坏性迁移，等于让旧版本代码跑在不认识的结构上，故障范围会超出所有灰度设计。
