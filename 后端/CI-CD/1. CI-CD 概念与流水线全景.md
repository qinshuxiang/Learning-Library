## CI-CD 概念与流水线全景

### 什么是 CI 与 CD

#### CI：持续集成

**持续集成（Continuous Integration，CI）**：开发者频繁地把代码合入主干，每次合入都自动触发构建与测试，用机器反馈代替人工验证。

- **小步提交**：每次提交只包含一个完整的改动，出问题容易定位与回退。
- **自动化验证**：提交后流水线自动执行 lint、类型检查、单元测试，几分钟内给出结果。
- **快速失败**：谁提交谁负责，红灯必须立即修，不允许在红灯主干上继续堆功能。

> CI 的核心价值不是「自动化」本身，而是**把集成问题提前暴露**。拖到上线前才合并，冲突与回归的排查成本按天计；每次提交就集成，成本按分钟计。

**速记**：CI＝**频繁合入＋自动验证＋快速反馈**。



#### CD：持续交付与持续部署

**CD** 有两种含义，区别在于「自动化的终点停在哪」。

- **持续交付（Continuous Delivery）**：流水线把代码自动验证、打包成随时可发布的产物，但**上线需要人工批准**。
- **持续部署（Continuous Deployment）**：通过全部验证后**自动上线**，无需人工介入，上线动作本身也是流水线的一步。
- 个人与小型项目常直接做到持续部署；有审批合规要求的团队多停在持续交付。

> 判断自己处于哪一档，只看一个问题：**从代码合并到用户可用，中间还有没有人工步骤**。有审批就是交付，没有就是部署。

**速记**：交付 **停在发布前**，部署 **一路到线上**。



### 流水线的标准阶段

#### 典型阶段划分

**流水线（Pipeline）**：一次提交触发的自动化步骤序列，从代码进入仓库到产物可部署为止。

- **lint 与静态检查**：代码风格、类型检查，秒级到分钟级，放在最前面。
- **测试**：单元测试优先跑，集成测试、E2E 按需分层。
- **构建**：产出可部署的产物，如打包后的应用或 Docker 镜像。
- **部署**：把产物送到目标环境，测试环境自动部署，生产环境按策略发布（见第 5、6 章）。

```text
push → lint → unit test → build → deploy(测试环境) → [人工批准] → deploy(生产环境)
```

> 排序原则：**越快、越便宜、越容易定位问题的检查越靠前**。lint 三十秒跑完就没理由放到测试后面；E2E 昂贵又脆，放最后兜底。

**速记**：**快查在前，贵查在后**，构建产物一次到处复用。



#### 门禁与分支保护

**门禁（Gate）**：合入主干前必须满足的自动化条件，靠分支保护规则强制执行。

- 主干分支设置保护规则：PR 必须通过指定 workflow 的 check 才允许合并。
- 必须至少一人 review 后才可合并（个人项目可关闭，但机制保留）。
- 禁止直接 push 主干，所有改动走 PR，让每次改动都有流水线记录。

> 门禁的意义在于**让红灯有牙齿**：没有分支保护的 CI 只是提醒，有保护的 CI 才是规则。GitHub 上的配置路径是仓库 Settings → Branches → Branch protection rules，勾选 Require status checks。

**速记**：**check 不过，merge 不进**。



### 主流工具全景

#### CI-CD 工具对比

**选型逻辑**：代码托管在哪，优先用哪家的内置 CI，省去对接成本；只有自建机房或复杂编排需求才考虑 Jenkins。

| 工具 | 形态 | 优势 | 适用 |
|---|---|---|---|
| GitHub Actions | 托管 | 与 GitHub 深度集成，生态市场庞大 | GitHub 托管项目的默认选择 |
| GitLab CI | 托管/自建 | `.gitlab-ci.yml` 单文件配置，自建方便 | GitLab 项目、需私有部署 |
| Jenkins | 自建 | 插件极多，完全可控 | 自建机房、遗留系统 |
| 阿里云效／腾讯 CODING | 托管 | 国内访问快，与云厂商部署链路打通 | 国内云上的项目 |

- GitHub Actions 免费额度：公开仓库完全免费，私有仓库按分钟计费有免费额度。
- 本系列后续章节以 **GitHub Actions** 为例展开，概念可平移到其他工具。

> 工具之间迁移的只是配置写法，**流水线阶段划分、门禁、发布策略这些设计不变**。先把第 1 篇的概念吃透，换工具只是换语法。

**速记**：**代码在哪托管，CI 就用哪家**，概念通用、语法各异。
