## GitHub Actions 核心语法

### 基本概念

#### Workflow、Event、Job 与 Step

**Workflow（工作流）**：一个可自动执行的流程，定义在仓库 `.github/workflows/` 目录下的 YAML 文件中，是 Actions 的最大组织单位。

- **Event（事件）**：触发工作流的活动，如 push、PR、定时、手动触发。
- **Job（任务）**：一组步骤的集合，多个 Job **默认并行**执行，每个 Job 运行在独立的虚拟环境里。
- **Step（步骤）**：Job 内的最小执行单位，可以是 shell 命令，也可以是一个 **Action（可复用动作）**。

```yaml
name: CI

on: push

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run lint
```

> 记住两层隔离：**Job 之间默认不共享文件**，上一个 Job 构建的产物要传给下一个，必须用 artifact 显式传递（见第 3 章）；Job 内的 Step 共享同一个工作目录。

**速记**：workflow 触发 **job**，job 并行跑，step 串行做。



#### Runner：托管与自托管

**Runner**：真正执行 Job 的服务器。GitHub 提供托管 Runner，也允许注册自己的机器。

- **GitHub 托管**（`ubuntu-latest`、`windows-latest`、`macos-latest`）：每次 Job 用全新虚拟机，干净无残留，公开仓库免费。
- **自托管**（`self-hosted`）：自己的机器注册为 Runner，适合需要访问内网资源、构建环境特殊或私有仓库分钟数超标的场景。
- `ubuntu-latest` 是滚动别名，生产流水线建议钉住具体版本（如 `ubuntu-24.04`），避免 GitHub 更新别名后流水线行为突变。

> 托管 Runner 每次都是新机器，所以**每个 Job 都要从 checkout 开始**，不存在「上一步留下的文件」；自托管 Runner 则恰恰相反，残留状态是常见的翻车来源，需要自己保证环境干净。

**速记**：托管 **即用即抛**，自托管 **省额度但管环境**。



### 工作流文件详解

#### 触发器 on

**on 字段**：声明工作流由哪些事件触发，是流水线的入口开关。

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: "0 18 * * *"
  workflow_dispatch:
```

- `push.branches`：限定只有推到 `main` 才触发，避免功能分支重复跑。
- `pull_request`：PR 更新时触发，配合分支保护做门禁。
- `schedule`：定时触发，cron 使用 **UTC 时间**，北京时间 18 点要写 `0 18 * * *` 对应的 UTC 表达式（`0 10 * * *`）。
- `workflow_dispatch`：允许在 Actions 页面手动点击运行，调试流水线必备。

> schedule 的 cron **不是常用 crontab 的时区**。GitHub 官方明确 schedule 使用 UTC，忘记换算会导致定时任务整晚不跑或白天突袭，这是新手最高频的踩坑点之一。

**速记**：on 定 **何时跑**，push 与 PR 是门禁主力，dispatch 用来调试。



#### Job 并行、依赖与矩阵

**needs 与 strategy.matrix**：控制多个 Job 的执行关系——`needs` 声明依赖形成串行链，`matrix` 用一组参数批量生成同构 Job。

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [20, 22]
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploy after build"
```

- 上例中 `build` 会展开为 Node 20、Node 22 两个并行 Job；`deploy` 等**全部** `build` 成功后才运行。
- 任何一个矩阵分支失败，默认整个 Job 标记失败，`deploy` 不会执行。
- `${{ }}` 是表达式语法，用于引用上下文变量（矩阵值、密钥、环境变量等）。

> 矩阵最适合「多版本兼容验证」这类重复劳动。日常只需要跑一个版本时不要硬上矩阵——**结构越简单，排错越快**。

**速记**：needs 定 **先后**，matrix 定 **重复**，默认并行、依赖串行。



### 变量与密钥

#### env、secrets 与上下文

**env 与 secrets**：`env` 存普通配置，`secrets` 存敏感凭据，两者都可在 workflow、job、step 三级分别声明，就近覆盖。

```yaml
env:
  NODE_ENV: production

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      APP_URL: https://example.com
    steps:
      - name: Deploy
        run: ./deploy.sh
        env:
          SSH_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
```

- **secrets 先在仓库设置**：Settings → Secrets and variables → Actions 中添加，日志中自动脱敏为 `***`。
- secrets 只能在 step 内注入环境变量或用 mask 处理，**不能像普通变量那样直接展开到 run 命令里再 echo**。
- `${{ github.sha }}`、`${{ github.ref_name }}` 等是常用上下文，取当次提交的哈希与分支名。

**警告内容**：任何 secrets 一旦被 `echo` 进日志就会永久留在运行历史里，即使后续删除 secret 也无法撤销已泄露的值。密钥泄露的唯一正确处置是**立即在服务商处吊销并更换**，而不是删除 workflow 日志。另外不要把密钥写进 `env` 明文、fork 的 PR 默认拿不到 secrets，这是安全设计而非 bug，勿绕过。

**速记**：配置用 **env**，凭据用 **secrets**，密钥只进环境变量、绝不进日志。



### 提速与复用

#### 缓存依赖

**actions/cache**：把 `node_modules` 这类可再生的重型目录缓存起来，跳过重复安装。

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 22
    cache: npm
```

- `setup-node` 的 `cache: npm` 一行即可缓存 npm 全局缓存目录，按 lockfile 哈希作 key，依赖不变则命中缓存。
- lockfile 变更时缓存自动失效，重新完整安装。
- 自定义目录用 `actions/cache@v4` 并显式声明 `path` 与 `key`。

> 缓存的粒度是 **key 完全匹配才命中**，所以 key 里一定要带上 lockfile 的哈希（`hashFiles('**/package-lock.json')`）。缓存装的是 npm 下载缓存而非 node_modules，安装步骤仍要执行 `npm ci`，只是从缓存取包、不再走网络。

**速记**：**key 绑 lockfile 哈希**，命中跳下载、不跳安装。



#### Artifact 传递产物

**Artifact**：Job 产出的文件包，用于跨 Job 传递（如 build 产物交给 deploy）或留存排查。

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: dist
    path: dist/

- uses: actions/download-artifact@v4
  with:
    name: dist
```

- `upload-artifact` 打包上传，另一个 Job 用 `download-artifact` 取回。
- Artifact 默认保留 90 天，可在仓库设置调整；仅用于 Job 间传递的临时产物用完即弃，不占心思。
- 与 cache 的区别：**cache 给构建提速、可被丢弃重建，artifact 是正式产物、要被下游消费**。

> build 和 deploy 拆成两个 Job 时，产物必须走 artifact，因为 Job 之间文件系统隔离。想省事也可以合成一个 Job 内完成构建与部署，代价是无法在两者之间插入人工审批环节——生产部署建议保留两个 Job。

**速记**：cache **提速可弃**，artifact **产物必达**。
