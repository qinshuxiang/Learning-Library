## Docker 镜像的 CI 构建与发布

### 为什么用镜像做交付物

#### 从文件产物到镜像产物

**镜像作为唯一交付物**：CI 不再传递 dist 目录，而是构建出包含运行时全部依赖的镜像，测试环境与生产环境跑的是同一个镜像。

- 第 3 章的 artifact 方案要求服务器预装 Node、版本一致；镜像方案把这些一并打包，服务器只要有 Docker。
- 镜像带 tag 不可变，**回滚就是换回旧 tag**，比重新部署文件可靠得多。
- Dockerfile 与多阶段构建的写法见 Docker 主题第 5、6 章，本篇聚焦 CI 侧的构建与发布。

> 「构建一次、到处运行」是镜像交付的核心纪律：**同一 commit 产出的镜像从测试推到生产，绝不重新构建**。重新构建就可能因为基础镜像更新而行为漂移，交付物的确定性被破坏。

**速记**：交付物换成 **镜像 tag**，一次构建、tag 不可变。



### 登录镜像仓库

#### 推送到 GHCR

**GHCR（ghcr.io）**：GitHub 官方镜像仓库，用 `GITHUB_TOKEN` 免密认证，是 GitHub 项目最顺手的私有镜像仓库。

```yaml
permissions:
  contents: read
  packages: write

jobs:
  image:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

- `permissions` 块显式声明最小权限，只读代码、写 packages。
- `GITHUB_TOKEN` 由 Actions 自动注入，**不需要配置任何 secret**，生命周期仅限本次运行。
- 推送第三方仓库（Docker Hub、阿里云 ACR）时改用 `docker/login-action` 对应 registry 并配置用户名密码 secret。

> `GITHUB_TOKEN` 的权限由 workflow 顶部的 `permissions` 决定，不声明时默认权限可能过宽。**每个 workflow 都显式写 permissions**，是官方推荐的安全基线。

**速记**：GHCR 用 **GITHUB_TOKEN**，permissions 显式最小化，零 secret 配置。



### 标签与构建提速

#### 镜像标签策略

**tag 设计**：镜像打什么 tag，决定部署与回滚的精度。

- `${{ github.sha }}`：提交哈希做 tag，**每个镜像全球唯一**，生产部署与回滚都锚定它。
- 语义化版本（`v1.2.3`）：面向外部发布的正式版本，配合 git tag 触发。
- `latest`：仅作本地开发便利，**严禁用于生产部署**——它是个会漂移的指针，两台机器各拉一次 latest 可能拿到不同镜像。

```yaml
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha
            type=ref,event=tag

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
```

> 部署清单里写 `image: ghcr.io/org/app:8f3e2a1` 这种哈希 tag，配合第 5 章的回滚，才能做到「回滚＝把 tag 改回上一个哈希」这种秒级确定性操作。**latest 出现的每一处生产配置都是隐患**。

**速记**：生产锚定 **sha tag**，latest 只配本地开发。



#### BuildKit 层缓存

**registry 缓存**：把 Docker 层缓存放到镜像仓库，跨 Runner 复用，构建从全量降到增量。

```yaml
      - uses: docker/setup-buildx-action@v3

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

- `type=gha` 用 GitHub Actions 的缓存服务存层缓存，无需额外服务；跨仓库共享则用 `type=registry`。
- `mode=max` 连中间层一起缓存，配合 Dockerfile「稳定在前、易变在后」的指令排序，依赖不变时重建只跑最后几层。
- 托管 Runner 每次全新虚拟机，本地那种「天然有缓存」不存在，**不配缓存就每次全量构建**。

> 缓存效果取决于 Dockerfile 的分层顺序，CI 配得再好也救不了「先 COPY 源码再 npm install」的写法。缓存命中率突然归零时，先看是不是基础镜像或前置层变了，再怀疑 CI。

**速记**：buildx＋`type=gha` 缓存，**分层顺序决定命中**。

**警告内容**：构建日志会完整输出各层执行过程，Dockerfile 里的 `ARG` 与构建参数会原样出现在日志中。**密钥严禁通过构建参数传入镜像**——它们会留在镜像层与 CI 日志里被永久记录，正确做法是用 BuildKit 的 `--secret` 挂载或运行时环境变量注入。
