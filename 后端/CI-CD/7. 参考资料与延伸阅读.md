## 参考资料与延伸阅读

### 官方文档与规范

#### GitHub Actions 官方文档

**GitHub Actions 官方文档**（docs.github.com/actions）：是 workflow 语法、事件、上下文与表达式的**权威参考**，也是本主题判定语法行为的最终依据。

- 覆盖 workflow 语法、events 触发器、contexts 与 expressions、secrets 管理全部主题。
- Understanding GitHub Actions 一文是概念全景的最佳入门，对应本主题第 1、2 章。

> 语法细节（如 `permissions` 的可用取值、environment 的配置项）以官方文档当前版本为准。Actions 迭代较快，第三方 action 的输入参数一律以该 action 仓库的 README 为准。

**速记**：语法争议查官方文档，action 用法查其仓库 README。



#### docker build-push-action 与 buildx 文档

**docker/build-push-action**（github.com/docker/build-push-action）与 **Docker Buildx 文档**（docs.docker.com/build）：是镜像 CI 构建的第一手资料，对应本主题第 4 章。

- build-push-action 的 README 覆盖 tags、cache-from/cache-to、多平台构建等全部常用配置。
- Buildx 文档讲解 BuildKit 构建器的缓存机制，`type=gha` 与 `type=registry` 两种缓存后端的差别以此为准。

> 缓存不生效时的排查顺序：先看 Dockerfile 分层顺序，再对 buildx 文档核对缓存类型参数。镜像层缓存的行为细节，官方文档比任何二手教程都准确。

**速记**：镜像构建两份文档：action 的 README 管配置，buildx 文档管缓存。



### 书籍与长文教程

#### 《持续交付》

**《持续交付：发布可靠软件的系统方法》**（Jez Humble、David Farley 著，人民邮电出版社）：是 CI-CD 领域的**奠基之作**，讲的是方法论而非某个工具。

- 提出部署流水线的完整概念，覆盖配置管理、自动化测试、发布策略与环境管理。
- 本主题第 1 章的阶段划分、第 5 章的环境分离，思想源头都在这本书。

> 工具十年一换，这本书讲的原则二十年未变。读它的正确姿势是对照自家流水线找差距：每个阶段是否自动化、产物是否唯一、回滚是否演练过。

**速记**：工具会过时，**流水线原则**在这本书里。



#### 阮一峰《GitHub Actions 入门教程》

**《GitHub Actions 入门教程》**（阮一峰，ruanyifeng.com/blog）：是中文世界流传最广的 Actions **短平快入门**。

- 以概念＋最小实例讲解 workflow、job、step、action 四层结构。
- 篇幅短，适合第一次接触 Actions 时快速通读，再回到本系列补实战细节。

> 入门读它建立地图，实战回本系列第 3、4 章对照完整配置，是效率较高的组合。

**速记**：先读它建地图，回本系列补实战。



### 深入方向

#### Google SRE 书籍中的发布工程章节

**《SRE：Google 运维解密》与《SRE 工作坊》**（Google Team 著，sre.google/books，中文版电子工业出版社出版）：从**可靠性工程**视角讲发布与回滚。

- 「Release Engineering」与「Emergency Response」章节回答：发布节奏怎么定、回滚为什么必须是第一选项、变更怎么逐步放量。
- 本主题第 5、6 章的回滚纪律与灰度思想，可在书中找到工程化展开。

> SRE 的核心立场是「变更即风险」：发布系统的所有设计——自动化、灰度、可回滚——都是为降低变更风险服务。做发布体系遇到取舍时，用这个立场校准方向不会错。

**速记**：发布体系的一切设计，都是为了**让变更风险可控**。



#### act 与 actionlint

**act**（github.com/nektos/act）与 **actionlint**（github.com/rhysd/actionlint）：是本地验证 workflow 的两款工具。

- **act**：用 Docker 在本地模拟 Runner 执行 workflow，改配置不必反复 push 试错。
- **actionlint**：workflow 的静态检查工具，语法错误、表达式拼写、矩阵引用问题提交前就能抓出来。

> 两件套的使用时机：actionlint 每次改 workflow 后必跑，秒级反馈；act 在调试复杂 job 时用，注意它对 `secrets` 与部分官方 action 的模拟有限，**本地通过不等于云端通过，最终仍以 CI 结果为准**。

**速记**：**actionlint 常跑，act 调试用**，云端结果才是准绳。
