## 自动化部署与回滚

### 部署方式与目标

#### 三种常见部署路径

**部署路径**：镜像就绪后把它变成线上运行的服务，自管服务器场景下有三条常用路径。

- **SSH 执行脚本**：Runner 登录服务器拉取新镜像、重启容器（见第 3 章），实现最简单。
- **服务器端拉取**：服务器上常驻 Watchtower 类工具或定时 `docker compose pull && up -d`，CI 只负责推镜像。
- **触发 Webhook**：CI 通知部署服务（如自建 webhook 接收器）执行预置脚本，解耦 CI 与服务器网络。

```bash
# 服务器上的标准部署序列（SSH 脚本的核心内容）
docker compose pull
docker compose up -d
docker image prune -f
```

- 三条路径的差别只在「谁登谁、谁来执行」，核心序列一致：**拉新镜像、替换容器、清旧镜像**。
- 项目规模小、服务器少时选 SSH 直连；服务器多或网络不通时选 Webhook 或专用部署工具。

> 部署脚本本身也要进版本库。**服务器上手写的任何改动都是负债**：下次流水线部署会把不一致冲掉，而排查的人很难想起服务器上曾经手改过。一切以仓库里的脚本为准。

**速记**：部署＝**pull 新镜像、up 替换、prune 收尾**，脚本进版本库。



### 环境分离与审批

#### Environments 与环境保护规则

**Environment**：GitHub Actions 内置的环境概念，给不同部署目标（测试／生产）配置独立的保护规则与密钥。

- 仓库 Settings → Environments 中创建 `production`，开启 **Required reviewers**：部署 Job 运行到该环境时暂停，等待指定人在页面上点击批准。
- 每个环境可配独立 secrets：测试库与生产库的连接串隔离，workflow 代码不用改。
- `environment: production` 写在 Job 上，其余环境（如 `staging`）不配审批即自动通过。

```yaml
  deploy-staging:
    environment: staging
    steps:
      - run: ./deploy.sh staging

  deploy-production:
    needs: deploy-staging
    environment: production   # 此处暂停等待人工批准
    steps:
      - run: ./deploy.sh production
```

> 环境分离的本质是把「进生产的决定权」做成**显式的、有记录的动作**。审批记录自动留在 Deployment 历史里，谁批准的、何时批准的，事后可查——这比口头确认可靠得多。

**速记**：environment 定 **目标＋审批＋独立密钥**，生产必配 reviewer。



### 回滚

#### 镜像回滚：改 tag 重启

**回滚**：把线上服务恢复到上一个正常版本，镜像交付下回滚是确定性的轻量操作。

```bash
# 当前版本有问题，回滚到上一个 commit 的镜像
docker compose down
# .env 中 IMAGE_TAG=8f3e2a1 改为上一个已知正常 tag
docker compose up -d
curl -fsS http://localhost:3000/health
```

- 部署配置中镜像 tag 用变量（`.env` 里的 `IMAGE_TAG`）而非写死，回滚只改一个变量。
- 保留最近 N 个版本的镜像不清理（`prune` 别配 `until` 过紧），保证旧 tag 随时可拉。
- 回滚后同样要过健康检查，确认服务真实恢复。

> 回滚的速度取决于**改 tag 到服务恢复的距离**。把 tag 做成变量、健康检查写进脚本，回滚就是一分钟内的事；每次回滚都要手工找产物、改配置、重启，就会拖延到不敢回滚。**回滚方案的可用性，要在第一次正常部署时就准备好**。

**速记**：回滚＝**tag 换回上一个**，旧镜像要留够、脚本要提前备好。



#### 数据库变更的回滚边界

**迁移与回滚的鸿沟**：镜像可以随意回滚，**数据库结构变更不行**——回滚代码后，新代码写入的数据与结构仍在数据库里。

- 扩展性变更（加列、加索引、加表）向后兼容，回滚代码后旧代码照常运行。
- 破坏性变更（删列、改类型、收紧约束）**不可直接回滚**，旧代码读到缺失列会报错。
- 正确流程是**两段式**：先上线兼容新旧结构的代码，再单独变更库结构，确认无误后才清理兼容代码。

```text
破坏性变更的安全序列：
1. 发布兼容版代码（同时读写新旧结构）
2. 执行数据库迁移（加新列、迁数据）
3. 发布只依赖新结构的新版代码
4. 回滚点在 2 与 3 之间：代码可回、结构不回，兼容版代码仍能跑
```

**警告内容**：任何包含数据库迁移的部署，**不要开启全自动回滚**——脚本自动回滚代码很容易，自动回滚数据库几乎必然造成数据损坏。迁移类变更的回滚必须人工评估数据现状后决策，宁可停机排查，不可脚本硬滚。

**速记**：**代码可回滚，结构慎回滚**，破坏性变更走两段式。



### 部署后验证

#### 冒烟测试与自动回滚

**部署后验证**：上线后立即用最小用例确认核心链路可用，是回滚决策的依据。

- **冒烟测试**：登录、下单、核心接口返回 200 等一两条关键路径，部署后自动执行。
- 验证失败触发自动回滚：脚本改回上一 tag、重启、再验证，全程无人值守。
- 自动回滚只适用于**无数据库迁移**的发布（见上节边界）。

```bash
./deploy.sh && ./smoke_test.sh || ./rollback.sh
```

> 自动回滚是把双刃剑：它能把故障恢复时间从「人醒来」缩短到「脚本跑完」，也会在误报时反复重启服务。**误报率必须先用冒烟测试的准确性驯服**，再交给自动执行；验证脚本本身不稳定时，先做成告警＋人工确认。

**速记**：**先冒烟、后回滚**，迁移发布只告警不自动滚。
