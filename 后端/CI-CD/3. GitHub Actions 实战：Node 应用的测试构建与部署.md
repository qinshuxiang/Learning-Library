## GitHub Actions 实战：Node 应用的测试构建与部署

### 项目准备

#### 统一脚本与锁文件

**可流水线化的前提**：所有验证与构建动作都收敛为 `package.json` 中的 npm script，流水线只调用脚本，不写具体命令。

```json
{
  "scripts": {
    "lint": "eslint .",
    "test": "vitest run",
    "build": "vite build"
  }
}
```

- **lockfile 必须提交**（`package-lock.json`），CI 用 `npm ci` 严格按锁文件安装，保证与本地一致。
- 脚本名保持惯例化（lint／test／build），流水线配置就能在项目间直接复用。
- 本地先跑通全部脚本再提交，不要把 CI 当调试工具。

> CI 里每一步都应该是本地可复现的。**流水线只是把这些命令搬到干净机器上按序执行**，本地跑不过的测试在 CI 里也一定过不了。

**速记**：命令进 **script**，CI 只认脚本；lockfile 必进仓库。



### CI：测试工作流

#### 单元测试与多版本矩阵

**测试工作流**：PR 与主干 push 都触发，多 Node 版本矩阵验证，全部通过作为合并门禁。

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-24.04
    strategy:
      matrix:
        node-version: [20, 22]
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: npm

      - run: npm ci

      - run: npm run lint

      - run: npm test
```

- `npm ci` 而非 `npm install`：前者删掉 node_modules 重装并严格校验锁文件，CI 场景的正确选择。
- `cache: npm` 按 lockfile 哈希缓存依赖，依赖不变时安装从分钟级降到秒级。
- lint 与 test 顺序执行，lint 更快，先失败先止损。

> `npm ci` 在 lockfile 与 package.json 不同步时**直接报错退出**，而不是悄悄更新。这个「严格」正是它的价值：依赖被意外改动会在 CI 第一时间暴露。

**速记**：CI 三板斧 `checkout → setup-node(cache) → npm ci`，先 lint 后 test。



### 构建与产物传递

#### build 与 upload-artifact

**构建 Job**：测试通过后构建产物，打包成 artifact 交给部署 Job。

```yaml
  build:
    needs: test
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run build

      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/
          retention-days: 7
```

- `needs: test` 保证只发布通过全部测试的代码。
- 产物只上传运行所需目录（`dist/`），不把 node_modules、源码打包进去。
- Docker 项目可跳过此步，改为直接构建镜像（见第 4 章）。

> 产物的自检清单：**本地删掉 node_modules 后还能跑吗**。能，说明产物自包含；不能，说明漏了依赖或配置，部署到服务器同样会挂。

**速记**：build 只认 `needs: test` 的代码，产物走 artifact 不走工作目录。



### 部署：SSH 到服务器

#### 密钥配置与部署 Job

**SSH 部署**：用私钥从 Runner 免密登录服务器执行部署脚本，是自管服务器最直接的方案。

```yaml
  deploy:
    needs: build
    runs-on: ubuntu-24.04
    environment: production
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist

      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SSH_HOST }}
          username: deploy
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd /srv/myapp
            rsync -a --delete /tmp/upload/ ./
            pm2 reload myapp
```

- 仓库需配置四个 secret：`SSH_HOST`、`SSH_PRIVATE_KEY`（对应服务器 `~/.ssh/authorized_keys` 中的公钥）。
- 专用 `deploy` 系统用户＋目录级权限，**禁止用 root 跑部署**，缩小密钥泄露的爆炸半径。
- `environment: production` 配合环境保护规则，可要求人工审批后才开始部署（见第 5 章）。

> 密钥要遵循**最小权限**：单独建部署用户、只授权目标目录、在服务器 `sshd_config` 里限制该用户仅可用密钥登录。一把能 sudo 的万能私钥放进 secrets，等于把服务器 root 送进了日志系统旁边。

**速记**：SSH 部署＝**专用用户＋专用密钥＋最小权限**，root 密钥一律不给。



#### 部署后健康检查

**上线验证**：部署脚本最后一步探测健康接口，失败即非零退出，让 Job 标红。

```bash
for i in $(seq 1 10); do
  if curl -fsS http://localhost:3000/health; then
    exit 0
  fi
  sleep 3
done
echo "health check failed" >&2
exit 1
```

- 健康检查接口应无副作用、不依赖外部服务，只回答「进程活着且能响应」。
- 重试若干次覆盖进程启动耗时，超时后显式 `exit 1` 让流水线失败。
- 失败后的处置（回滚）在第 5 章展开，本篇先保证「失败可见」。

> 没有健康检查的部署等于**闭眼上线**：pm2 reload 成功只说明进程重启了，不说明服务可用。一行 curl 的成本，换「部署结果有结论」的确定性。

**速记**：部署最后一行 **curl 健康接口**，不通就 exit 1。
