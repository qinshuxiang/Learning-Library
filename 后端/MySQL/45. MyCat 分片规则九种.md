## MyCat 分片规则九种

### 规则的取舍框架

#### 先看三条判据

**选规则只看三件事**：均匀度、扩容成本、查询命中率。

- **均匀度**：数据能否大致均分，倾斜会让某片先撑爆
- **扩容成本**：加片时是否需要全量搬迁，取模与固定 hash 都要搬
- **命中率**：分片键条件能否定位到单片，范围与枚举天然受限于取值分布
- 时间类规则（按天、按月）均匀但热点集中，最新片承担几乎全部写入

> 九种规则里没有最优解，只有匹配业务的那一个。订单按月分片、用户按取模分片、地区按枚举分片，判断依据都是「查询带什么条件」。

**速记**：**均匀、扩容、命中率，三判据定规则**。

#### 规则在 rule.xml 里的结构

**所有规则同一套骨架**：tableRule 挂列，function 挂实现类与参数。

- `tableRule` 的 `columns` 可写多列，构成复合分片
- `function` 的 `class` 是算法实现，`property` 是参数
- 规则名可复用，同一算法用不同参数实例化多次
- `algorithm` 里可用 `mapFile` 指向外部映射文件

```xml
<tableRule name="sharding-by-murmur">
    <rule>
        <columns>user_id</columns>
        <algorithm>murmur</algorithm>
    </rule>
</tableRule>
<function name="murmur" class="io.mycat.route.function.PartitionByMurmurHash">
    <property name="seed">0</property>
    <property name="count">2</property>
</function>
```

> 参数名大小写敏感，写错不报错只是不生效——这是最容易踩的坑。改完配置必须 `reload @@config` 并用真实数据验证落点。

**速记**：**规则挂列，函数挂参数，改完必须 reload 验落点**。

### 数值类规则

#### 范围分片

**范围分片按分片列的区间落点**：区间边界来自映射文件。

- 实现类 `AutoPartitionByLong`，映射文件 `autopartition-long.txt`
- 文件格式 `起始值-结束值=节点号`，支持 K、M、G 单位
- 优点是可以按区间扩容，旧数据不动
- 缺点是热点集中在最后一段，且区间外数据无处安放

```xml
<function name="rang-long" class="io.mycat.route.function.AutoPartitionByLong">
    <property name="mapFile">autopartition-long.txt</property>
    <property name="defaultNode">0</property>
</function>
```

```text
# autopartition-long.txt
0-500M=0
500M-1000M=1
1000M-1500M=2
```

> `defaultNode` 是兜底：落在所有区间之外的数据被塞进 0 号节点，不报错但会静默倾斜。上线前把映射文件的上界设得比预估峰值高一档。

**速记**：**区间连节点，扩容只加段，越界进默认**。

#### 取模分片

**取模是最直白的均匀方案**：`分片列 % count` 决定节点。

- 实现类 `PartitionByMod`，只认一个参数 `count`
- 数据与请求都均匀，实现简单，排查直观
- 扩容时绝大多数数据要重新分布，是它最大的代价
- `count` 一旦改动，历史数据必须全量搬迁

```xml
<function name="mod-long" class="io.mycat.route.function.PartitionByMod">
    <property name="count">2</property>
</function>
```

> 取模的扩容之痛可以用「成倍扩容」缓解：2 片扩到 4 片时，原 0 号的数据一半留在 0、一半去 2，迁移量只有一半。非成倍扩容则接近全量搬迁。

**速记**：**取模最均匀，扩容最伤，成倍扩才省一半**。

#### 固定 hash 分片

**固定 hash 把取模范围从 2 的幂扩到任意组合**：本质是分段取模。

- 实现类 `PartitionByLong`，参数 `partitionCount` 与 `partitionLength`
- `partitionCount` 是各段的分片数，`partitionLength` 是各段长度
- 两个数组逐项相乘后求和，结果必须等于 **1024**
- 相比纯取模，能表达「前 256 落 0、1 号，后 512 落 2 号」这类不均匀需求

```xml
<function name="hash-int" class="io.mycat.route.function.PartitionByLong">
    <property name="partitionCount">2,1</property>
    <property name="partitionLength">256,512</property>
</function>
```

> 固定 hash 的现实用途是「给大客户单独留片」：把某个取模段整体指向大规格节点，兼顾均匀与隔离。参数算错会直接启动失败，改前先用纸算一遍总和。

**速记**：**分段取模，长度总和 1024，能给大客户留位**。

### 字符串类规则

#### 字符串 hash

**字符串 hash 对字符串做哈希再取模**：适合用户 ID、订单号这类字符串键。

- 实现类 `PartitionByHash`，参数同样是 `partitionCount` 与 `partitionLength` 的分段形式
- 哈希值与固定 hash 一样按 1024 分段，`prefixLength` 可只取前 N 个字符
- 同一字符串永远落同一片，扩容同样要搬数据
- 哈希值分布均匀，但不可读、不可预测

```xml
<function name="hash-str" class="io.mycat.route.function.PartitionByHash">
    <property name="partitionCount">2</property>
    <property name="partitionLength">512</property>
</function>
```

> 字符串 hash 与取模是一体两面：一个对字符串、一个对数字。选择只看分片列的类型，扩容代价完全一样。

**速记**：**字符串先哈希再取模，同值同片，扩容同痛**。

#### 字符串 hash 解析

**按前缀模式取子串再哈希**：适用于单号带业务前缀的场景。

- 实现类 `PartitionByPrefixPattern`，参数 `patternValue` 与 `prefixLength`
- 取前 `prefixLength` 位，转成数值后对 `patternValue` 取模
- 适合 `NO20261020001` 这类定长编码，业务含义保留在单号里
- 前缀若无变化，等于全部落同一片——务必先看真实数据的前缀分布

```xml
<function name="prefix-hash" class="io.mycat.route.function.PartitionByPrefixPattern">
    <property name="patternValue">256</property>
    <property name="prefixLength">6</property>
</function>
```

> 前缀解析的隐性风险是数据格式演进：单号从 12 位变 14 位后，前缀截取的含义变了，落点跟着漂移。这类规则必须与单号生成规则一起版本管理。

**速记**：**截前缀转数值再取模，格式一变落点漂**。

#### 枚举分片

**枚举把分片列的有限取值映射到节点**：地区、租户、渠道的常用解法。

- 实现类 `PartitionByFileMap`，`type` 为 0 表示数字、1 表示字符串
- 映射文件 `partition-hash-int.txt`，格式 `取值=节点号`
- `defaultNode` 兜底未知取值，`-1` 表示未配置时报错
- 取值集合天然有限时最稳，新增取值只改文件不必搬数据

```xml
<function name="hash-enum" class="io.mycat.route.function.PartitionByFileMap">
    <property name="mapFile">partition-hash-int.txt</property>
    <property name="type">0</property>
    <property name="defaultNode">0</property>
</function>
```

```text
# partition-hash-int.txt
10000=0
10010=1
```

> 枚举的均匀度取决于业务分布：一线城市与边缘省份的用户量差几十倍。按枚举分片前先统计真实取值分布，别用「地区」这种天然倾斜的列硬扛。

**速记**：**有限取值查表落点，加值只改文件，倾斜看真实分布**。

#### 应用指定分片

**由应用在 SQL 里指定落点**：MyCat 只做转发不做计算。

- 实现类 `PartitionDirectBySubString`，按子串位置决定节点
- 参数 `startIndex`、`size`、`partitionCount`、`defaultPartition`
- 也支持 `PartitionDirectByDate` 按日期前缀直接定位
- 路由完全可控，但把分片逻辑暴露给了应用，一致性靠约定

```xml
<function name="direct-sub" class="io.mycat.route.function.PartitionDirectBySubString">
    <property name="startIndex">0</property>
    <property name="size">2</property>
    <property name="partitionCount">4</property>
    <property name="defaultPartition">0</property>
</function>
```

> 应用指定适合「分片键不固定、但业务能算出来」的场景，代价是逻辑双写：MyCat 与应用的算法必须同步演进。一处改了另一处没改，就是静默写错片。

**速记**：**应用算好片号，中间件只转发，双份逻辑必须同版**。

### 时间类规则

#### 按天分片

**按天分片是日志、流水类表的标准方案**：一片一天，历史片只读。

- 实现类 `PartitionByDate`，`dateFormat` 为 `yyyy-MM-dd`
- `sBeginDate` 起始日，`sPartionDay` 每片天数，`sEndDate` 可省
- 起始日之前的数据落 `defaultNode`，之后每 N 天一片
- 片数随时间无限增长，必须配套归档与清理策略

```xml
<function name="sharding-by-date" class="io.mycat.route.function.PartitionByDate">
    <property name="dateFormat">yyyy-MM-dd</property>
    <property name="sBeginDate">2026-01-01</property>
    <property name="sPartionDay">10</property>
</function>
```

> 时间分片的真正成本不在查询而在运维：一天一片，一年 365 个物理表，备份、DDL、监控全部乘以 365。没有归档策略就不要上按天分片。

**速记**：**一天一片，历史只读，片数随时涨，归档要先行**。

#### 按自然月分片

**按月分片是按天分片的克制版**：片数可控，热点仍在新片。

- `dateFormat` 用 `m` 表示按月，`sBeginDate` 写 `2026-01`
- `sEndDate` 限定终止月份，超出则循环（需谨慎，容易覆盖旧数据）
- 每月一片，一年 12 片，物理表数量可控
- 按月分区后跨月查询会命中多片，报表类要按片聚合

```xml
<function name="sharding-by-month" class="io.mycat.route.function.PartitionByDate">
    <property name="dateFormat">m</property>
    <property name="sBeginDate">2026-01</property>
</function>
```

> 循环分片的语义是「写满从头覆盖」：适合只保留固定窗口的日志表，用在订单这类不可丢数据上就是灾难。设 `sEndDate` 之前先想清楚数据保留期。

**速记**：**一月一片，季度报表跨三片，循环只在可丢场景用**。

### 综合运用

#### 九种规则速查

**按分片列类型对号入座**：这张表是选规则的起点。

| 规则 | 实现类 | 关键参数 | 扩容 | 适用 |
|---|---|---|---|---|
| 范围 | AutoPartitionByLong | mapFile | 加段即可 | 自增 ID、按量分段 |
| 取模 | PartitionByMod | count | 全量搬 | 数值键，均匀优先 |
| 固定 hash | PartitionByLong | partitionCount/Length | 全量搬 | 需要不均匀留片 |
| 字符串 hash | PartitionByHash | partitionCount/Length | 全量搬 | 字符串键 |
| 前缀解析 | PartitionByPrefixPattern | patternValue/prefixLength | 全量搬 | 定长业务单号 |
| 枚举 | PartitionByFileMap | mapFile/type | 只改文件 | 地区、租户 |
| 应用指定 | PartitionDirectBySubString | startIndex/size | 看应用 | 键不固定 |
| 按天 | PartitionByDate | sPartionDay | 自然增长 | 日志、流水 |
| 按月 | PartitionByDate | dateFormat=m | 自然增长 | 账单、订单归档 |

> 表里没有「最好」的一行，只有与分片键类型、扩容预期、查询模式三者同时匹配的一行。先定分片键，规则自然浮出来。

**速记**：**键定类型，扩容定代价，查询定命中**。
