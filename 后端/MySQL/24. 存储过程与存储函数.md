## 存储过程与存储函数

### 存储过程

#### 什么是存储过程

**存储过程是存在数据库服务端的 SQL 程序**：一次定义，多次调用。

- CREATE PROCEDURE 定义，CALL 调用
- 定义时用 DELIMITER 临时更换语句结束符，避免体内的分号提前截断
- 体内可包含完整 SQL 与流程控制（26 篇）
- 定义存于数据字典，SHOW CREATE PROCEDURE 查看

> 存储过程的价值主张是“逻辑贴近数据”：多次数据库交互合并为一次调用，省网络往返。逻辑进入数据库的工程代价，见后文「优缺点与工程取舍」一节。

**速记**：**过程存服务端，CALL 即执行，先换结束符再写体**。

```sql
DELIMITER //

CREATE PROCEDURE sp_user_order_count(IN p_user_id BIGINT)
BEGIN
    SELECT COUNT(*) FROM orders WHERE user_id = p_user_id;
END //

DELIMITER ;

CALL sp_user_order_count(42);
```



#### 三种参数模式

**IN、OUT、INOUT 决定参数的数据流向**：默认是 IN。

- IN：入参，过程内可读，改动不影响外部
- OUT：出参，过程内赋值，调用方接收结果
- INOUT：进出皆可，先带入再带回
- 调用处 OUT 与 INOUT 参数须传用户变量（@v）接收

> OUT 参数是过程返回多值的通道。多 OUT 参数的过程调试不便，结果集加 OUT 组合时要写清文档。

**速记**：**IN 进 OUT 出 INOUT 双向，出参靠 @ 变量接**。

```sql
CREATE PROCEDURE sp_stats(IN p_user_id BIGINT, OUT p_cnt BIGINT, OUT p_total DECIMAL(12,2))
BEGIN
    SELECT COUNT(*), IFNULL(SUM(amount), 0)
      INTO p_cnt, p_total
      FROM orders WHERE user_id = p_user_id;
END;
```



#### 存储函数

**存储函数必须有返回值**：像内置函数一样用在表达式里。

- CREATE FUNCTION 定义，RETURNS 声明返回类型，体内 RETURN 返回
- 调用方式是 SELECT 函数名(参数)，可嵌进任何表达式
- 体内同样可用 SQL 与流程控制，但不得返回结果集
- 声明 DETERMINISTIC 或 NOT DETERMINISTIC 标记确定性

> 开启 binlog 的服务器对函数有安全审查：不确定的函数在语句级复制下主从结果可能不一致，需声明特性或调 log_bin_trust_function_creators。这不是可无视的警告，是复制一致性的根。

**速记**：**函数必 RETURNS，SELECT 里调，确定性声明关复制安危**。

```sql
CREATE FUNCTION fn_circle_area(p_r DOUBLE)
RETURNS DOUBLE
DETERMINISTIC
BEGIN
    RETURN 3.14159265 * p_r * p_r;
END;

SELECT fn_circle_area(2);
```



### 过程与函数的对比

#### 两者的区别

**过程管动作，函数管计算**：定位决定形态。

- 返回：函数必有单值返回，过程靠 OUT 参数与结果集
- 调用：函数在表达式内，过程用 CALL 独立执行
- 位置：函数能进 SELECT、WHERE，过程不能
- 复制：函数有确定性审查，过程没有此限制

> 选型口诀：要一个值用函数，要做一串事用过程。判断不出就想想它像 Math.max 还是像一段事务脚本。

**速记**：**函数求值进表达式，过程干事用 CALL**。



#### 优缺点与工程取舍

**存储过程是双刃剑**：省交互但绑死数据库。

- 优点：批量操作少网络往返、权限可只授予过程而不授予底层表、逻辑集中
- 缺点：难以调试与单测、版本管理脱节、数据库耦合、水平扩展受限于单机
- 互联网高并发团队多在应用层实现逻辑，库内逻辑退守报表与数据订正
- 中小系统与数据密集型批处理场景仍是利器

> 判断标准是变化频率与团队栈：逻辑稳定、计算密集、离数据越近越快的，过程合适；频繁迭代、需要完整测试链路的，放应用层。

**速记**：**省往返换耦合，高频迭代莫入过程**。



### 过程体的编写

#### 变量与流程骨架

**过程体内先 DECLARE 后使用**：变量、游标、句柄按序声明。

- DECLARE 变量名 类型 DEFAULT 默认值，必须在 BEGIN 块最前
- 声明顺序强制：普通变量、游标、异常句柄依次排
- SET 与 SELECT INTO 赋值
- IF、CASE、LOOP、WHILE、REPEAT 控制流程（26 篇详述）

> DECLARE 顺序错了是语法错误不是警告，写成游标在变量前直接报错；记住“变量、游标、句柄”三段式即可。

**速记**：**先声明后使用，变量游标句柄排序固定**。

```sql
CREATE PROCEDURE sp_scan_users()
BEGIN
    DECLARE v_done INT DEFAULT 0;
    DECLARE v_id BIGINT;
    DECLARE cur CURSOR FOR SELECT id FROM users;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = 1;
    -- 后续逻辑
END;
```



#### 错误处理与事务

**过程体是事务的好容器**：HANDLER 捕获异常决定回滚。

- DECLARE EXIT HANDLER FOR SQLEXCEPTION 捕获任意 SQL 异常
- 处理块内可 ROLLBACK 后重新抛出信号（SIGNAL）
- EXIT HANDLER 触发即退出当前 BEGIN 块，CONTINUE 则继续
- 事务边界由你控制：BEGIN 内 START TRANSACTION 到 COMMIT

> 用 SIGNAL 抛出自定义错误信息，让调用方拿到可读的失败原因，而不是静默吞掉异常假装成功。错误处理不写的过程，是最危险的一类过程。

**速记**：**EXIT HANDLER 捕获即撤，SIGNAL 把错说明白**。

```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    ROLLBACK;
    RESIGNAL;
END;
```



### 管理与维护

#### 查看与删除

**过程的元数据走 SHOW 与 information_schema**：改动走 ALTER 或重建。

- SHOW CREATE PROCEDURE 名称：看定义原文
- SHOW PROCEDURE STATUS WHERE Db = 库名：列清单与特征
- information_schema.routines：程序化查询入口
- DROP PROCEDURE 删除；修改定义通常 DROP 后重建

> 过程没有 ALTER 支持改体，改逻辑就是 DROP 加 CREATE 的组合；把定义放进版本库（迁移脚本），否则库里的过程就是无版本管理的黑盒。

**速记**：**定义进版本库，改体即重建**。



#### 存储例程的安全边界

**把过程当 API 设计**：参数校验与权限收口都要做。

- 权限可只授 EXECUTE 过程，不授底层表，收缩暴露面
- 过程内部仍以定义者的权限执行（SQL SECURITY 语义）
- 参数在体内校验类型与范围，别信任调用方
- 命名规范：sp_、fn_ 前缀区分例程类型

> 权限收口用得克制是利器，用滥了就是绕过应用层审计的暗门；例程清单必须纳入治理。

**速记**：**过程当 API，校验在体内，权限收在 EXECUTE**。
