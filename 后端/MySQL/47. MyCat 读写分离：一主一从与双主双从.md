## MyCat 读写分离：一主一从与双主双从

### 分工与开关

#### 谁在读，谁在写

**读写分离的前提是复制已经跑通**：MyCat 只做分发，不做同步。

- 复制链路由 MySQL 自己完成（38 篇原理、39 篇搭建）
- MyCat 在 `dataHost` 里区分 `writeHost` 与 `readHost`，按开关决定读去哪
- 主库故障时由 `switchType` 决定是否切换到备用 writeHost
- 读写分离解决的是读压力，不解决写压力与数据量

> 先确认复制延迟再谈分离：从库落后 10 秒，读请求分过去就是读到旧数据。分离是流量工程，复制是数据工程，后者不稳前者必翻车。

**速记**：**复制先跑通，MyCat 只管分发，延迟不解决就是脏读**。

#### 三个开关

**balance 管读、writeType 管写、switchType 管切**：三者独立配置。

- `balance=0`：不分离，所有读走 writeHost
- `balance=1`：所有 readHost 与备用 writeHost 参与读
- `balance=2`：所有读随机分摊到 writeHost 与 readHost
- `balance=3`：只在 readHost 间分摊，writeHost 不参与读
- `writeType=0`：第一个 writeHost 承担写；`1` 随机写；`2` 不写
- `switchType=-1` 不自动切；`1` 自动切；`2` 依主从状态切；`3` 依 Galera 状态切

```xml
<dataHost name="host1" maxCon="1000" minCon="10" balance="1"
          writeType="0" dbType="mysql" dbDriver="native" switchType="1">
    <heartbeat>select user()</heartbeat>
    <writeHost host="hostM1" url="192.168.200.210:3306" user="root" password="123456">
        <readHost host="hostS1" url="192.168.200.211:3306" user="root" password="123456"/>
    </writeHost>
</dataHost>
```

> `balance=2` 是最容易被误用的档位：它把读也分给主库，看着「均匀」，实际把主库仅剩的余量也吃掉，写性能跟着下降。生产上默认 `1`，主库只留写。

**速记**：**读走从、写走主、切看 switch，balance 别贪 2**。

### 一主一从

#### 配置与验证

**一主一从是最小可用形态**：一个写节点带一个读节点。

- 主库开 `log_bin`，从库配 `server_id` 与 `read_only`
- 从库 `CHANGE REPLICATION SOURCE TO` 指向主库，`START REPLICA`
- MyCat 侧把 readHost 挂在 writeHost 内部，形成父子关系
- 验证方式：在主库写入，从库能查到；MyCat 读请求落到 3307 的从库

```sql
-- 主库写入
INSERT INTO tb_user(id, name) VALUES (9, 'test');

-- 从库确认
SELECT * FROM tb_user WHERE id = 9;

-- MyCat 侧确认分发
SHOW VARIABLES LIKE 'server_id';   -- 或看从库 general_log 是否有该查询
```

> 验证分离是否真的生效，最笨也最可靠的办法是给从库开 general_log，看 MyCat 发来的查询有没有落进去。只看结果对，主库也能返回同样的数据。

**速记**：**主写从读，父子挂载，验分离看从库日志**。

#### 延迟与降级

**从库延迟是读写分离的固有病**：MyCat 不知道你的业务能不能等。

- 秒杀、下单后立刻回查这类场景必须走主库
- 延迟超阈值时的策略：降级到主库、返回旧值、直接报错
- MyCat 本身没有延迟感知，需要外部监控加应用侧路由
- `balance=1` 下主库故障，写会切到备用 writeHost，读仍尝试 readHost

> 「刚写完查不到」是读写分离上线后最常见的一类工单。解法不是调大复制线程数，而是把强一致读显式指向主库——这需要应用层配合，不是中间件能代劳的。

**速记**：**写完即读走主库，延迟阈值要外部盯**。

### 双主双从

#### 拓扑与数据流向

**双主双从是两套主从叠起来**：主备互相同步，各带一个从。

- master1 与 master2 互为主从，任一方可写
- slave1 挂 master1，slave2 挂 master2
- 写入 master1 后，经 master2 级联到 slave2，要求 **master2 开启 `log_slave_updates`**
- MyCat 里两个 writeHost 并列，各自内嵌一个 readHost

```text
        ┌──────────┐  复制  ┌──────────┐
写入 ──>│ master1  │<──────>│ master2  │
        └────┬─────┘        └────┬─────┘
             │                   │
        ┌────▼─────┐        ┌────▼─────┐
        │  slave1  │        │  slave2  │
        └──────────┘        └──────────┘
```

> `log_slave_updates` 是级联复制的开关，默认关闭。不开，master2 收到的变更不会写进自己的 binlog，slave2 永远同步不到——这是双主双从最常见的「配了但不生效」。

**速记**：**双主互备，从挂两边，级联必开 log_slave_updates**。

#### 双主的关键参数

**双主最容易死在主键冲突上**：两个主都能写，自增会撞。

- `auto_increment_increment=2`、`auto_increment_offset` 分别设 1 与 2
- 两库 `server_id` 必须不同，否则复制直接拒绝
- 两库都开 `log_bin` 与 `log_slave_updates`
- 建议加 `read_only=1` 在备用主上，只允许复制线程写

```ini
# master1
[mysqld]
server-id = 1
log-bin = mysql-bin
auto_increment_increment = 2
auto_increment_offset = 1

# master2
[mysqld]
server-id = 2
log-bin = mysql-bin
log_slave_updates = 1
auto_increment_increment = 2
auto_increment_offset = 2
```

> 自增步长只是缓解不是根治：两个主同时插入仍可能产生相同 ID（不同表、不同时刻的边界情况）。真正的唯一性靠业务主键或分布式 ID，别把自增当成跨主唯一。

**速记**：**步长 2 偏移分 1/2，server_id 必须不同**。

#### MyCat 侧配置与切换

**双主双从在 MyCat 里就是两个并列 writeHost**：主备关系由 switchType 表达。

- `writeType=0` 时只往第一个 writeHost 写，第二个待命
- `switchType=1` 时第一个挂掉自动切到第二个
- 配合 `balance=1`，两个 readHost 与备用主共同分担读
- 切换后需人工把旧主修好并重新挂回，自动切回默认关闭

```xml
<dataHost name="host1" maxCon="1000" minCon="10" balance="1"
          writeType="0" dbType="mysql" dbDriver="native" switchType="1">
    <heartbeat>select user()</heartbeat>
    <writeHost host="hostM1" url="192.168.200.210:3306" user="root" password="123456">
        <readHost host="hostS1" url="192.168.200.211:3306" user="root" password="123456"/>
    </writeHost>
    <writeHost host="hostM2" url="192.168.200.212:3306" user="root" password="123456">
        <readHost host="hostS2" url="192.168.200.213:3306" user="root" password="123456"/>
    </writeHost>
</dataHost>
```

> 自动切换只解决「能继续写」，不解决「数据有没有丢」：切换瞬间未同步的事务会永久缺失。切换后必须核对 GTID 或位点差异，补齐数据再对外恢复读。

**速记**：**两主并列，首主先写，切换要补数据**。

### 综合运用

#### 读写分离落地清单

**上线前六项确认**：少一项就是一个故障预案的缺口。

- 复制延迟监控与阈值告警已就绪
- 强一致读的接口清单已梳理，全部显式走主库
- 主库故障的切换演练做过，包含切换后的数据核对
- MyCat 连接池总和不超过后端 `max_connections`
- 从库 `read_only=1`，防止误写污染复制链路
- 双主场景的自增步长与业务 ID 方案已对齐

> 读写分离的收益是线性的，风险是非线性的：读越多，延迟暴露面越大。上线顺序应该是先监控、再灰度、最后全量，而不是一次性把读全部切走。

**速记**：**延迟先监控，强读走主库，切换要演练**。
