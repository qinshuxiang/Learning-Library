## 联合查询与派生表

### UNION 联合

#### UNION 与 UNION ALL

**UNION 合并多个结果集**：去重与否是两者的全部区别。

- UNION：合并后去重，重复行只留一份
- UNION ALL：直接拼接，不去重不排序
- 各个 SELECT 的列数必须一致，对应列类型需兼容
- 结果列名以第一个 SELECT 为准

> 去重不是免费的：UNION 需要临时表去重，大结果集上代价可观。确定无重复（如按分区查询同表）或允许重复时，一律 UNION ALL，把去重决策留给需要它的地方。

**速记**：**UNION 去重花代价，UNION ALL 直拼零开销**。

```sql
SELECT id, name FROM users_2025
UNION ALL
SELECT id, name FROM users_2026;
```



#### 联合结果的排序

**ORDER BY 只能放在联合的最后**：作用于合并后的整体。

- 末尾的 ORDER BY 可引用第一个 SELECT 的列名或别名
- 各子查询内写 ORDER BY 无意义，除非配合 LIMIT
- 子查询内 ORDER BY 加 LIMIT 的组合有“取每组前 N”的过渡用法（8.0 推荐窗口函数）
- LIMIT 同样只放最后，限制合并后的总行数

> 想给每个分支单独排序再合并，把每个 SELECT 包成派生表，各自排序加 LIMIT 后再 UNION ALL；直接在子查询里裸写 ORDER BY 会被优化器忽略。

**速记**：**排序只认最后，子句内单独排须包一层**。

```sql
SELECT * FROM (
    SELECT id, name FROM users_2025 ORDER BY id DESC LIMIT 5
) t1
UNION ALL
SELECT * FROM (
    SELECT id, name FROM users_2026 ORDER BY id DESC LIMIT 5
) t2;
```



### 派生表

#### 派生表与别名

**FROM 里的子查询叫派生表**：必须起别名，这是语法强制。

- 写法：FROM (SELECT ...) AS t，别名不可省
- 派生表在语句内像普通表一样被引用与连接
- 优化器可能把它合并进外层（merge），也可能物化成临时表
- 合并与物化的选择由优化器决定，EXPLAIN 可见（DERIVED）

> 派生表是“先算中间结果再继续”的标准手段，但物化意味着临时表落内存或磁盘；中间结果过大时的退出策略见后文综合运用一节。

**速记**：**FROM 里子查询，别名必须有，物化合并看优化器**。

```sql
SELECT t.city, AVG(t.total) AS avg_order
FROM (
    SELECT u.city, o.user_id, SUM(o.amount) AS total
    FROM orders o JOIN users u ON o.user_id = u.id
    GROUP BY u.city, o.user_id
) AS t
GROUP BY t.city;
```



### CTE 公用表表达式

#### WITH 子句基本用法

**CTE 用 WITH 给子查询命名**：一次定义，语句内多处引用。

- 写法：WITH 名称 AS (SELECT ...) 后接主查询
- 可定义多个 CTE，逗号分隔，后面的可引用前面的
- 按步骤命名，逻辑自上而下
- 同一 CTE 可被主查询引用多次，不必重复粘贴

> CTE 与派生表能力是否等价、如何取舍，详见下一节专述；本节记住写法即可。

**速记**：**WITH 命名可复用，多个逗号连，先定义后引用**。

```sql
WITH user_totals AS (
    SELECT user_id, SUM(amount) AS total
    FROM orders
    GROUP BY user_id
)
SELECT u.name, t.total
FROM user_totals t JOIN users u ON t.user_id = u.id
WHERE t.total > 10000;
```



#### CTE 与派生表的取舍

**两者能力等价，可读性分高下**：选择主要看复杂度。

- 单次使用的简单子查询：派生表紧凑
- 多次引用、多步推导：CTE 命名清晰
- CTE 链式分解复杂逻辑：每步一个名字，逐层验收
- 物化行为一致，性能无天然差异

> 团队内统一风格比个人偏好重要：一半 CTE 一半嵌套派生表的代码库，读起来最痛苦。

**速记**：**能力相同看可读，多步用 CTE 单步派生表**。



#### 递归 CTE

**WITH RECURSIVE 让查询自己调用自己**：SQL 里遍历树与序列的标准解法。

- 结构三件套：锚成员（起点查询）、UNION ALL、递归成员（引用自身）
- 递归成员每次处理上一轮产出的行，直到返回空集
- 经典场景一：组织架构树，从某节点向下展开全部下属
- 经典场景二：生成日期序列或数字序列，补齐报表空档
- 递归深度上限 cte_max_recursion_depth 默认 1000，防失控

> 递归 CTE 必须有收敛条件，否则撞深度上限报错；写完先想清楚终止条件是什么、最坏多少层，别指望上限替你兜底。

**速记**：**锚点加自引用，收敛条件必须写，深度上限是保险丝**。

```sql
WITH RECURSIVE sub_tree AS (
    SELECT id, name, manager_id FROM employees WHERE id = 1
    UNION ALL
    SELECT e.id, e.name, e.manager_id
    FROM employees e
    JOIN sub_tree s ON e.manager_id = s.id
)
SELECT * FROM sub_tree;
```



### 综合运用

#### 联合与派生的选型路径

**合并用 UNION，中间结果用 CTE，树用递归**：三招覆盖绝大多数复杂查询。

- 同构数据合并展示：UNION ALL 打底，按需去重
- 多步聚合、先算后筛：CTE 分步表达
- 层级遍历、序列生成：WITH RECURSIVE
- 中间结果超大：退出单条语句，落临时表或应用层接管

> 复杂查询的维护成本随嵌套深度指数上升；能用 CTE 拉平的层次尽量拉平，每一步的中间结果都可独立验证，出问题时二分定位。

**速记**：**合并 UNION、分步 WITH、遍历递归，复杂拆临时**。



#### 复杂查询的验收方法

**复杂 SQL 的验收靠拆解验证，不靠一眼看懂**：给每一层单独跑一遍。

- 每个 CTE、每个派生表独立执行，核对行数与粒度
- UNION 前后各分支行数相加核对，去重差异要解释得清
- 递归 CTE 先限制小范围试跑，确认终止与层级正确
- 最终语句 EXPLAIN 看物化与扫描量，防临时表爆炸

> 逐层验证是复杂 SQL 唯一可靠的调试法；把几百行的查询当成一个整体“目测正确”，等于没有验收。

**速记**：**逐层单独跑，行数对得上，递归小样先试**。
