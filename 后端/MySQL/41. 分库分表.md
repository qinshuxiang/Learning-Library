## 分库分表

### 什么时候需要分库分表

#### 单库单表的瓶颈判断

**分库分表是最后手段**：它用数据分布的复杂性换取容量与性能上限，动手前必须确认瓶颈真的在存储层。

- **单表数据量**：B+ 树层高随行数缓慢增长，经验上单表到 **千万级行、几十 GB** 后，即使索引正确，DDL 变更耗时与缓存命中率也会明显恶化。
- **单机资源**：CPU、磁盘 IO、连接数打满，而第 40 章的读写分离只能分摊读，写与数据量仍压在一台主库上。
- **标准替代路线先走完**：索引优化（第 36 章）、读写分离、冷数据归档、升级更大规格的实例——全部无效再考虑拆分。

> 分库分表解决不了的伪瓶颈最常见：慢查询先查执行计划，连接打满先查连接泄漏，先证明「已无单机解法」再谈拆分。**拆分的运维成本是永久性的，性能收益却常常可以用一个索引拿到**。

**速记**：先索引、再读写分离、后归档，**全部无效才拆**。



### 拆分策略

#### 垂直拆分

**垂直拆分**：按业务边界或字段访问模式切，把「一锅端」的库表按职责分家。

- **垂直分库**：订单、用户、商品各自成库、独立部署，服务边界随之清晰，是微服务化时数据库层的同步动作。
- **垂直分表**：把一张宽表按访问频率切分——高频小字段留主表，低频大字段（详情 TEXT、扩展 JSON）放扩展表，主表页密度提高、缓存效率上升。
- 垂直拆分的边界来自业务语义，拆完各库表职责单一，**跨库 join 从此消失**，必须改为接口聚合。

> 垂直拆分通常一次到位、之后稳定，代价可控；真正长期的复杂性都在水平拆分。两步常常连续进行：先按业务垂直分库，再对最大的单表水平分片。

**速记**：垂直拆分＝**按业务分库、按冷热分字段**，边界来自业务语义。



#### 水平拆分

**水平拆分**：同一张表的数据按分片键拆到多个库表，每个分片结构相同、数据不同。

- **哈希取模**：`shard = hash(user_id) % N`，数据均匀、请求分布均匀；缺点是扩容要大规模搬迁数据。
- **范围切分**：按时间或 ID 区间分片，扩容只需新增区间、旧数据不动；缺点是热点集中——最新分片承担几乎全部读写。
- 范围＋哈希组合（先按时间分段、段内取模）是折中方案，兼顾扩容平滑与段内均匀。

```text
orders 表按 user_id 哈希拆 4 片：
  shard_0: user_id % 4 == 0
  shard_1: user_id % 4 == 1
  shard_2: user_id % 4 == 2
  shard_3: user_id % 4 == 3
同一用户的全部订单永远落在同一分片 → 用户维度查询单片命中
```

> 水平拆分后**每一片的容量上限就是架构上限**，规划片数要按 3—5 年的数据量预估，宁多勿少——因为哈希方案的扩容搬迁成本极高。

**速记**：哈希 **均匀难扩容**，范围 **易扩容有热点**，按取值预估、宁多勿少。



### 分片键与代价

#### 分片键的选择

**分片键（Sharding Key）**：决定每行数据落在哪个分片的字段，是水平拆分所有后续复杂性的根源。

- **选查询最常用的维度**：绝大多数 SQL 的 WHERE 都带它，才能保证单片命中。订单表选 `user_id`（买家查自己的订单）而不是 `order_id`，是典型取舍——商家按订单号查变成跨片，需另建按订单号的路由索引表。
- **选数据天然聚合的维度**：同一用户的数据落在同一分片，分片内的 join、事务、聚合都还是普通单机操作。
- **分片键一旦选定极难更换**：换分片键等于全量数据重分布，选型阶段的谨慎花多少都值得。

> 分片键决策的本质是回答「**这个系统上最主要的查询维度是什么**」。C 端业务几乎都是用户维度，`user_id` 是安全答案；数据所有维度查询都重要的系统，说明它不适合水平拆分，先考虑垂直拆分或异构索引。

**速记**：分片键＝**最高频查询维度**，选错即全量搬家，选定难改。



#### 跨片操作与分布式 ID

**拆分的代价清单**：单片命中之外的一切操作都变贵，动手前逐项确认业务能否接受。

- **跨片查询**：不带分片键的 WHERE 扫全部片，聚合（COUNT、SUM）要在各片执行后汇总；用中间件时表现为 SQL 能力受限。
- **跨片事务**：本地事务失效，需要分布式事务（复杂度高）或业务侧最终一致设计（顺序消息、对账补偿）。
- **全局唯一 ID**：自增主键在各分片必然重复，改用分布式 ID 方案——雪花算法（Snowflake）、号段模式或专门的发号服务，保证全局唯一且趋势递增（利于 B+ 树写入）。
- **跨片 join**：基本不可用，改为接口聚合、字段冗余或异构一份按另一维度组织的数据。

> 全局 ID 的取舍口诀：**雪花算法够用就别上发号服务**——它只依赖本机时钟与预分配的机器号，无外部依赖；代价是要管理 workerId 分配与处理时钟回拨。这组主题的完整展开见「分布式」主题的分布式 ID 篇。

**速记**：跨片 **查询扫全片、事务要分布式、join 基本没了**，ID 必须换全局方案。

**警告内容**：分库分表方案落地后，**数据库结构变更（DDL）的成本随之翻倍**——每片都要变更，还要处理变更期间的复制延迟与业务兼容。没有配套的在线 DDL 流程（如 gh-ost、pt-online-schema-change）就上分片，会把每一次加字段都变成一次线上事故的风险窗口。
