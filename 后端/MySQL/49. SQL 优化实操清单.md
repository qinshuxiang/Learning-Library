## SQL 优化实操清单

### 与第 36 篇的分工

#### 方法论之外的七项动作

**36 篇讲怎么想，本篇讲怎么做**：七个高频场景的逐项改法。

- 写入侧：批量插入、主键顺序、`LOAD DATA` 大批量导入
- 排序分组：`ORDER BY` 与 `GROUP BY` 消 filesort 与临时表
- 分页：深分页的两种改写
- 计数：`COUNT` 三种写法的真实差异
- 更新：`UPDATE` 的行锁升级为表锁

> 这七项的共同点是「改法固定、收益可测」：不需要重新设计架构，改语句或加索引就能拿到结果。它们是优化的第一梯队。

**速记**：**七项固定动作，改完即可测收益**。

### 插入优化

#### 批量与事务

**插入慢的两大原因**：每条一次事务、每条一次网络往返。

- 一条 INSERT 写多行，500 到 1000 行一批，减少解析与事务开销
- 多批之间手动开事务，避免每批一次提交
- 批太大触发 `max_allowed_packet` 限制，也会拉长锁持有时间
- 主键顺序插入，避免随机 IO 与页分裂

```sql
START TRANSACTION;
INSERT INTO tb_order(id, order_no, user_id) VALUES
 (1,'NO001',1001),(2,'NO002',1002),(3,'NO003',1003);
INSERT INTO tb_order(id, order_no, user_id) VALUES
 (4,'NO004',1004),(5,'NO005',1005),(6,'NO006',1006);
COMMIT;
```

> 批量大小的经验值是 500 到 1000 行：再大，回滚成本与锁持有时间都会变成新问题。导入百万级数据不要用 INSERT 硬怼，用下面的文件导入。

**速记**：**一条多行、多批一事务、主键顺序写**。

#### LOAD DATA 大批量导入

**文件导入比 INSERT 快一个量级**：跳过 SQL 解析，直接走批量装载。

- `LOAD DATA LOCAL INFILE` 由客户端读文件发送，不受 `secure_file_priv` 限制
- 去掉 LOCAL 则由服务器读文件，路径必须在 `secure_file_priv` 目录内
- 需要服务端与客户端都开启 `local_infile`
- 导入前建议 `SET UNIQUE_CHECKS=0`、`SET FOREIGN_KEY_CHECKS=0`，导入后恢复

```sql
SET GLOBAL local_infile = 1;

LOAD DATA LOCAL INFILE '/tmp/orders.csv'
INTO TABLE tb_order
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES
(id, order_no, user_id, amount);
```

```bash
mysql --local-infile=1 -uroot -p test < load.sql
```

> 关掉唯一性检查与 `AUTOCOMMIT` 能把导入时间再压一半，代价是失败后无法回滚到中途状态。导入是幂等可重跑的任务时才这么干。

**速记**：**文件导入快十倍，LOCAL 绕开文件目录限制，导入前关检查**。

### 主键优化

#### 页分裂与页合并

**主键顺序决定页的填充率**：乱序插入就是随机写。

- 顺序插入：新行总在最后一页追加，页填满再开新页，几乎无分裂
- 乱序插入：目标页已满则分裂成两页，各占一半，空间与 IO 双输
- 删除大量行后页利用率下降，InnoDB 会做页合并
- UUID 作主键是乱序插入的极端案例

```text
顺序插入： [1..100][101..200][201..300]  → 追加即可
乱序插入： [1,57,203..] 插入 150 → 页分裂为 [..149][150..] 各半满
```

> 分裂不是错误而是代价：每次分裂都要搬一半数据到新页，还要更新上层索引。批量导入时把数据按主键排序再灌，是最便宜的一次优化。

**速记**：**顺序追加不分裂，乱序插入半页空**。

#### 主键设计约束

**主键要短、要稳定、要递增**：三条约束互相支撑。

- 短：二级索引的叶子都存主键值，主键多长，每条二级索引就多长
- 稳定：主键被更新等于删一行加一行，代价极高
- 递增：保证顺序插入，避免分裂
- 自增 `BIGINT` 是默认最优解，业务编号另建唯一索引

```sql
CREATE TABLE tb_order (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  order_no VARCHAR(32) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no)
) ENGINE=InnoDB;
```

> 「用业务单号做主键」是最常见的反模式：单号 32 字节，每条二级索引都背着它，索引体积翻几倍；单号还可能被修正，一改就是全表重建。

**速记**：**短稳定递增，自增做主键，业务号建唯一索引**。

### 排序与分组

#### ORDER BY 优化

**目标只有一个**：让 Extra 从 `Using filesort` 变成 `Using index`。

- 排序列与 WHERE 的等值列组成联合索引，且顺序为「等值列 + 排序列」
- 排序方向必须与索引一致，`ORDER BY a ASC, b DESC` 在 8.0 可用降序索引支持
- 覆盖索引可免回表，但排序列不在索引里仍会 filesort
- `sort_buffer_size` 调大可让排序在内存完成，但会放大并发内存占用

```sql
-- 索引：(status, created_at)
SELECT id, status, created_at FROM tb_order
 WHERE status = 1
 ORDER BY created_at DESC
 LIMIT 20;
-- Extra: Using index（覆盖 + 有序读取，无 filesort）
```

> filesort 不等于慢：小结果集在内存排很快，只有行数大、`sort_merge_passes` 增长时才值得动手。判断依据是 Extra 加实际耗时，不是见到 filesort 就改。

**速记**：**等值列在前排序列在后，方向要一致，覆盖才免回表**。

#### GROUP BY 优化

**分组的代价是临时表**：能借索引就不建临时表。

- `GROUP BY` 的列有索引时，可沿索引顺序扫描直接分组
- 无索引则建内部临时表，`Using temporary` 出现在 Extra 里
- 8.0 起 `GROUP BY` 不再隐式排序，不需要再写 `ORDER BY NULL`
- 分组前的 `WHERE` 过滤尽量走索引，减少进入临时表的行数

```sql
-- 索引：(status, user_id)
SELECT user_id, COUNT(*) FROM tb_order
 WHERE status = 1
 GROUP BY user_id;
```

> 「分组慢就加索引」有时无效：如果分组列基数极高（接近行数），走索引分组的收益不如全表扫加哈希聚合。看 `Using temporary` 是否伴随大 `rows` 再决定。

**速记**：**有索引沿序分组，无索引建临时表，8.0 不再隐式排序**。

### 分页与计数

#### LIMIT 深分页

**深分页慢在「读了又丢」**：`LIMIT 1000000, 10` 要扫一百万行。

- 覆盖索引子查询先取主键，再回表取整行（延迟关联）
- 游标式分页用上一页的末位值做条件，彻底避开偏移
- 业务上限制最大页数，比技术优化更有效
- `LIMIT` 的偏移越大，扫描行数线性增长

```sql
-- 延迟关联：先在索引上定位主键
SELECT o.* FROM tb_order o
  JOIN (SELECT id FROM tb_order
         WHERE status = 1 ORDER BY id LIMIT 1000000, 10) t
    ON o.id = t.id;

-- 游标式：记住上一页最后一个 id
SELECT * FROM tb_order WHERE id > 1000010 ORDER BY id LIMIT 10;
```

> 游标式分页的前提是排序键唯一且稳定。按 `created_at` 排序时同秒多行会漏数据，必须带上主键做次级排序。

**速记**：**深页先取主键再回表，能游标就别偏移**。

#### COUNT 的三种写法

**三种写法在 InnoDB 上都慢**：引擎不存总行数。

- `COUNT(*)` 与 `COUNT(1)` 等价，优化器选最小的二级索引扫描
- `COUNT(列)` 要判断非空，多一次判断，且不能选最窄索引
- `COUNT(*)` 不会展开成所有列，不要被 `*` 误导
- 大表精确计数靠汇总表或缓存，实时 `COUNT` 只用于小结果集

```sql
SELECT COUNT(*) FROM tb_order WHERE status = 1;
SELECT COUNT(1) FROM tb_order WHERE status = 1;
SELECT COUNT(user_id) FROM tb_order WHERE status = 1;  -- 排除 NULL
```

> 三种写法差距在 10% 量级，纠结写法不如解决「要不要精确」的问题（36 篇）。把 `COUNT(*)` 换成 `COUNT(1)` 拿不到数量级收益。

**速记**：**星号即 1，列计数多判空，要快靠汇总表**。

### 更新优化

#### UPDATE 与行锁升级

**WHERE 没走索引，行锁变全表锁**：这是 UPDATE 优化的核心。

- 条件列无索引时，扫描到的每一行都加锁，效果等同锁表
- 并发更新同一批数据时，锁等待迅速堆高，直至超时
- 改法：条件列建索引，或把更新拆成按主键的小批
- 大事务拆小批，每批提交，缩短锁持有时间

```sql
-- 反例：status 无索引，扫描全表并锁住所有行
UPDATE tb_order SET remark = 'x' WHERE status = 1;

-- 正例：按主键分批
UPDATE tb_order SET remark = 'x' WHERE id BETWEEN 1 AND 1000;
```

> 锁面与扫描面是同一个面（34 篇）：UPDATE 优化的收益一半在速度、一半在并发。只盯执行时间的优化，会把锁问题留给下一个故障。

**速记**：**条件有索引才锁行，大更新拆小批**。

### 综合运用

#### 七项优化对照表

**按症状找动作**：这张表是排查清单。

| 症状 | Extra 或现象 | 动作 |
|---|---|---|
| 批量导入慢 | 逐条提交 | 多行 INSERT + 单事务，或 LOAD DATA |
| 写入抖动 | 页分裂频繁 | 主键改自增、按序导入 |
| 排序慢 | Using filesort | 联合索引「等值列 + 排序列」 |
| 分组慢 | Using temporary | 分组列建索引，先过滤再分组 |
| 深分页慢 | rows 极大、返回极小 | 延迟关联或游标分页 |
| 计数慢 | 全表或全索引扫 | 汇总表、缓存、降级口径 |
| 更新卡顿 | 锁等待堆积 | 条件列建索引、拆小批 |

> 七行对应七个可独立验证的改动。一次只改一行，改完记录前后的 EXPLAIN 与耗时，这张表才会变成团队资产而不是个人记忆。

**速记**：**症状对动作，一行一改，前后留证**。
