## InnoDB 引擎内部结构

### 与第 28 篇的分工

#### 从记录到引擎

**28 篇看的是行与页，本篇看的是整个引擎**：三层结构加四块内存。

- 逻辑层：表空间 → 段 → 区 → 页 → 行，数据的组织规则
- 内存层：Buffer Pool、Change Buffer、自适应哈希、Log Buffer
- 磁盘层：各类表空间、双写缓冲、redo 文件
- 线程层：谁在把内存与磁盘对齐

> 理解引擎的目的不是背结构，而是解释现象：为什么脏页多会卡、为什么批量导入后磁盘 IO 飙升、为什么 `ibdata1` 一直变大。每个现象都能在结构里找到对应部件。

**速记**：**逻辑看层级，内存看四块，磁盘看表空间，线程看刷盘**。

### 逻辑存储结构

#### 五层嵌套

**InnoDB 的空间管理是分层的**：表空间里是段，段里是区，区里是页。

- **表空间**：逻辑上的存储容器，对应一个或多个文件
- **段**：一组区，按用途分数据段（B+ 树叶子）、索引段（非叶子）、回滚段
- **区**：连续的 64 个页，固定 1MB，是空间分配的最小单位
- **页**：16KB，读写的最小单位
- **行**：记录，按行格式存放（28 篇）

```text
表空间 (tablespace)
 └─ 段 (segment)      数据段 / 索引段 / 回滚段
     └─ 区 (extent)   64 页 = 1MB，分配单位
         └─ 页 (page) 16KB，读写单位
             └─ 行 (row)
```

> 「区固定 1MB」这个约束解释了小表为何浪费空间：一张只有几行的表也至少要占一个区（1MB）。表数量极多时，碎片空间会显著放大实际占用。

**速记**：**空间到段，分配到区，读写到页，存储到行**。

#### 为什么分段

**段的作用是让「顺序增长」与「随机插入」都高效**：

- B+ 树叶子节点顺序增长，申请新区时尽量连续，减少随机 IO
- 非叶子节点数量少，单独成段便于管理
- 回滚段承载 undo，与数据段隔离，清理互不影响
- 段是「按需扩展」的：数据涨一段就申请一个区，不预分配整表空间

> 段的设计直接服务 B+ 树的访问模式：叶子层要顺序、要大块；索引层要常驻内存、要小。分开管理，缓存与 IO 都能各按各的规律优化。

**速记**：**叶子顺序扩，索引常驻存，回滚单独管**。

### 内存结构

#### Buffer Pool

**Buffer Pool 是 InnoDB 的性能核心**：数据页与索引页都在这里被读写。

- 以页为单位缓存，默认大小 `innodb_buffer_pool_size`，生产建议物理内存的 50% 到 70%
- 内部分 chunk 管理，支持在线调整大小
- 三条链：free（空闲页）、LRU（缓存页）、flush（脏页）
- LRU 分 young 与 old 两区，`innodb_old_blocks_pct` 默认 37，防全表扫冲掉热数据
- 脏页由 Page Cleaner 后台刷盘，刷不及会阻塞写入

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_%';
SHOW STATUS LIKE 'Innodb_buffer_pool_wait_free';
```

> `Innodb_buffer_pool_wait_free` 大于 0 就是「没有空闲页可用」的信号：要么池子太小，要么脏页刷得太慢。这时写入会明显抖动，先调刷盘参数再加内存。

**速记**：**三链管页，LRU 防污染，脏页刷不及就卡写**。

#### Change Buffer

**Change Buffer 把二级索引的随机写攒起来**：减少离散读。

- 只对**非唯一二级索引**生效：唯一索引要判重，必须读页
- 更新时若目标页不在内存，先记入 Change Buffer，等页被读入时合并
- 持久化在系统表空间，崩溃不丢
- `innodb_change_buffer_max_size` 默认 25，占总池比例
- 读多写少的库收益明显，写极多的库可能反成负担

```sql
SHOW VARIABLES LIKE 'innodb_change_buffer_max_size';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_%';
```

> 唯一索引用不上 Change Buffer，这是「唯一索引比普通索引写更慢」的结构性原因。业务需要唯一性时别无选择，但别给不需要唯一的列加唯一索引。

**速记**：**只服务非唯一二级索引，攒随机写，读入时合并**。

#### 自适应哈希与 Log Buffer

**两块小结构，各管一件事**：

- 自适应哈希索引（AHI）：为热点页自动建 hash，等值查直接命中，`innodb_adaptive_hash_index` 默认开
- AHI 分区的锁在高并发下可能成为争用点，可按需关闭
- Log Buffer：redo 的内存缓冲，`innodb_log_buffer_size` 默认 16MB
- 大事务会撑爆 Log Buffer，触发提前刷盘，写入变慢

```sql
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';
SHOW VARIABLES LIKE 'innodb_log_buffer_size';
SHOW STATUS LIKE 'Innodb_buffer_pool_pages_free';
```

> AHI 是「引擎自己猜出来的索引」，命中率无法直接观测，只能通过 `SHOW ENGINE INNODB STATUS` 的 hash searches 与 non-hash searches 比值判断。比值低就可以关掉它省锁开销。

**速记**：**AHI 加速等值，Log Buffer 缓冲 redo，大事务撑爆提前刷**。

### 磁盘结构

#### 表空间家族

**InnoDB 有多种表空间，各有各的职责**：

- 系统表空间 `ibdata1`：数据字典、双写缓冲、Change Buffer 持久化，8.0 不可收缩
- 独立表空间 `.ibd`：`innodb_file_per_table=ON` 时每表一个，可单独收缩
- 通用表空间：多表共享一个文件，适合统一管理
- undo 表空间：存 undo（35 篇），8.0 支持在线 truncate
- 临时表空间：会话与全局临时表，重启重建

```sql
SHOW VARIABLES LIKE 'innodb_file_per_table';
SELECT NAME, FILE_SIZE, ALLOCATED_SIZE FROM information_schema.INNODB_TABLESPACES
 ORDER BY FILE_SIZE DESC LIMIT 10;
```

> `ibdata1` 只涨不缩是经典问题：早期用共享表空间时，删除数据也不释放。8.0 默认独立表空间后问题缓解，但系统表空间里的 undo 与 change buffer 仍会增长。

**速记**：**系统库只涨不缩，独立表可收缩，undo 可 truncate**。

#### 双写缓冲与 redo 文件

**双写缓冲防页断裂，redo 保崩溃恢复**：

- Doublewrite Buffer：刷数据页前先写一份到双写区（2MB，128 页），再写正式位置
- 断电导致页只写了一半时，从双写区恢复完整页
- redo 文件循环写，8.0.30 起用 `innodb_redo_log_capacity` 统一控制容量
- 8.0 的 redo 文件在 `#innodb_redo` 目录，最多 32 个

```sql
SHOW VARIABLES LIKE 'innodb_doublewrite';
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
```

> 双写带来一次额外写，对写性能有可观影响，但关掉它等于放弃页完整性保护。SSD 上可以用 `innodb_doublewrite=OFF` 换取写性能，前提是文件系统与设备保证原子写。

**速记**：**先双写再落位，断电不裂页；redo 循环写，容量按需调**。

### 后台线程

#### 四类线程

**线程的分工决定了「谁在拖慢你」**：

- **Master Thread**：调度核心，负责刷脏、合并 Change Buffer、回收 undo
- **IO Thread**：读写线程各若干，`innodb_read_io_threads`、`innodb_write_io_threads` 默认 4
- **Purge Thread**：清理不再需要的 undo（35 篇），`innodb_purge_threads` 默认 4
- **Page Cleaner Thread**：专门刷脏页，`innodb_page_cleaners` 默认 4，避免刷脏阻塞用户线程

```sql
SHOW VARIABLES LIKE 'innodb_%io_threads';
SHOW VARIABLES LIKE 'innodb_page_cleaners';
```

> 高并发写入下的「间歇性卡顿」常常是 Page Cleaner 跟不上脏页产生速度。调大 `innodb_page_cleaners` 与 `innodb_io_capacity` 是第一步，加内存是第二步。

**速记**：**主线程调度，IO 线程搬页，purge 清旧，cleaner 刷脏**。

### 综合运用

#### 结构到现象

**六个现象对应六个部件**：排障时的对照表。

| 现象 | 部件 | 先看 |
|---|---|---|
| 写入间歇卡顿 | Buffer Pool 脏页 | `Innodb_buffer_pool_wait_free`、cleaner 线程数 |
| 二级索引写入慢 | Change Buffer | 是否唯一索引、`change_buffer_max_size` |
| 磁盘只涨不降 | 表空间 | 独立表空间 / undo / `ibdata1` |
| 崩溃后数据完好 | redo + 双写 | 双 1 配置（35 篇） |
| 小表占用异常大 | 区分配 | 表数量与 1MB 区的关系 |
| 等值查偶发变慢 | AHI 争用 | hash searches 比值 |

> 这张表的价值是把「玄学卡顿」变成「查某个计数器」。结构知识的用处就在于此：知道东西在哪，才知道去哪看。

**速记**：**现象对部件，部件对计数器**。
