## 主从搭建与读写分离

### 搭建一主一从

#### 配置主库并初始化数据

**主库配置**：开启 binlog、分配唯一 server_id，然后做一次全量备份作为从库的起点。

```ini
# 主库 my.cnf
[mysqld]
server_id = 1
log_bin   = mysql-bin
```

```sql
-- 创建专用复制账号：只授予复制权限，不授予业务权限
CREATE USER 'repl'@'192.168.1.%' IDENTIFIED BY '强密码';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'192.168.1.%';

-- 记录当前 binlog 位点（备份时刻的坐标）
SHOW MASTER STATUS;
```

- **全量备份**：用 `mysqldump --single-transaction --source-data=2` 对业务库做一致性备份，输出文件里自带备份时刻的 binlog 坐标。
- **server_id 全局唯一**：主库与每台从库不得重复，重复会导致复制关系异常。
- 复制账号限定来源网段并使用强密码，它是能读取全部 binlog 的高价值账号（第 37 章的权限最小化原则）。

> 从库起点的正确性来自「**全量备份＋备份时刻的 binlog 坐标**」这对组合：从库先恢复全量数据，再从坐标处继续重放，才能与主库对齐。手工跳过备份直接 START 复制，是新手最常见的事故来源。

**速记**：主库三件事 **开 binlog、建复制账号、全量备份记坐标**。



#### 配置从库并启动复制

**从库配置与拉起**：导入全量备份，配置 server_id 与主库连接信息，启动复制线程。

```ini
# 从库 my.cnf
[mysqld]
server_id = 2
relay_log = relay-bin
read_only = ON
```

```bash
mysql -u root -p < full_backup.sql
```

```sql
-- MySQL 8.0.22+ 推荐语法（旧语法为 CHANGE MASTER TO）
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '192.168.1.10',
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = '强密码',
  SOURCE_LOG_FILE = 'mysql-bin.000003',   -- 备份文件中记录的坐标
  SOURCE_LOG_POS = 157;
  -- GTID 模式下改用 SOURCE_AUTO_POSITION = 1，免手工对坐标

START REPLICA;
```

- `read_only` 挡住普通用户的写操作，防止从库被误写造成主从分叉；SUPER 权限仍可写，MySQL 8.0 的 `super_read_only` 连管理员写入也一并挡住，生产建议两个都开。
- GTID 模式（`gtid_mode=ON`）下从库自动定位无需手工坐标，是第 42 章自动切换的前提，新集群直接上 GTID。

> 启动后第一件事是**验证复制状态**，不是验证业务查询：`SHOW REPLICA STATUS\G` 中 `Replica_IO_Running` 与 `Replica_SQL_Running` 必须同为 `Yes`，任何一环 No 都说明链路没通。

**速记**：从库四步 **导备份、改 server_id、CHANGE SOURCE、START REPLICA**，双 Yes 才算通。



#### 验证与日常巡检

**复制状态巡检**：搭建完成只是起点，日常以三项指标确认链路健康。

- `Replica_IO_Running` / `Replica_SQL_Running`：两个线程都为 `Yes` 是底线。
- `Seconds_Behavior_Source`：延迟秒数，持续大于 0 要回查第 39 章的成因清单。
- `Last_Error`：回放报错会停在原地等人工决策，**严禁无脑跳过**——跳过等于在从库静默丢数据。

```sql
-- 简单的一致性抽查：主从各执行一次
SELECT COUNT(*), MAX(id) FROM orders;
-- 严谨方案用官方校验工具 pt-table-checksum（Percona Toolkit）
```

**警告内容**：从库回放报错时，`SET GLOBAL sql_replica_skip_counter = 1` 跳过事务只能用于**已确认无业务影响**的冲突（如两边都建的同一张表），并且必须先定位原因。直接跳过主键冲突、数据冲突类错误，会在无人察觉的情况下让从库与主库永久分叉，之后的所有读流量都建立在错误数据上。

**速记**：巡检看 **双线程、延迟秒数、报错原因**，跳错等于造脏从库。



### 读写分离

#### 应用侧路由与中间件

**读写分离**：写请求固定走主库，读请求按策略分发到从库，读能力随从库数量扩展。

- **应用层路由**：项目里维护两个数据源（主／从），代码里显式选择。实现直白、无额外组件，适合中小项目，Node 侧见下节。
- **中间件代理**：ProxySQL、ShardingSphere-JDBC 等按 SQL 类型自动路由，业务代码无感知，代价是多一层组件要运维。
- **路由策略的关键限制**：写后立即读的场景（下单后查订单）必须强制回主库，否则撞上第 39 章的复制延迟。常用做法是写操作后的短时间窗口内该会话粘住主库。

> 选型判断只看一条：**团队愿不愿意为「代码无感知」养一个代理组件**。中小项目应用层路由两三个文件就做完，代理的运维成本反而高于收益；数据源多、流量大后迁移到中间件也不迟。

**速记**：**应用层路由小项目够用，中间件自动换透明**，写后读必须粘主库。



#### Node 侧接入读写分离

**mysql2 连接池分工**：用两个连接池分别指向主库与从库，业务代码按读写语义选池。

```js
const mysql = require('mysql2/promise');

const master = mysql.createPool({ host: '10.0.0.1', user: 'app', database: 'shop', connectionLimit: 20 });
const slave  = mysql.createPool({ host: '10.0.0.2', user: 'app', database: 'shop', connectionLimit: 40 });

// 写：走主库
await master.query('INSERT INTO orders(user_id, amount) VALUES (?, ?)', [uid, amount]);

// 读：走从库；关键路径读（支付结果、库存扣减校验）改用 master
const [rows] = await slave.query('SELECT * FROM products WHERE status = ?', ['on']);
```

- 从库池的 `connectionLimit` 可大于主库——读流量是分流的主要目标。
- 封装一个 `select(slave|master)` 的数据访问层入口，把「选池」收敛到一处，避免业务代码散落判断。
- 从库故障的处理策略要明确：降级读主库还是直接报错，两选一写进数据访问层，不做隐式兜底。

> 读写分离的收益前提是**读流量占比足够高**。写密集型业务从库再多也分不掉多少压力，此时的下一步是第 41 章的分库分表，而不是继续加从库。

**速记**：两个池 **写主读从**，选池收敛进数据访问层，关键读走主。
