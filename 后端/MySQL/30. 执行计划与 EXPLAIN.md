## 执行计划与 EXPLAIN

### EXPLAIN 基础

#### EXPLAIN 是什么

**EXPLAIN 展示优化器的执行计划**：语句怎么跑，它说了算。

- 用法：在 SELECT 前加 EXPLAIN，不真执行语句
- 8.0 起也支持 DML：EXPLAIN UPDATE、EXPLAIN DELETE
- 统计信息变化时，计划随之变化
- 输出 12 列，核心是 id、type、key、rows、Extra 五列

> EXPLAIN 是 SQL 优化的第一工具：任何“这条 SQL 慢”的讨论，没有 EXPLAIN 输出就没有开始。养成习惯——写完即看，交付前再看。

**速记**：**EXPLAIN 看戏不演戏，五列定生死**。

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```



#### id 与 select_type

**id 编号标识查询块，select_type 标注查询的角色**：合读即知结构。

- id 相同：自上而下顺序执行；id 越大越先执行（子查询与派生表）
- select_type = SIMPLE：无子查询无联合的朴素查询
- PRIMARY：最外层查询；SUBQUERY：子查询第一个 SELECT
- DERIVED：派生表；UNION 与 UNION RESULT：联合的各支与合并
- MATERIALIZED：物化的子查询

> id 与 select_type 合起来还原了优化器眼中的语句结构：哪个是主体、哪个是嵌套、哪里物化了。复杂语句的 EXPLAIN 从这里开始读。

**速记**：**大 id 先跑，SIMPLE 朴素 DERIVED 派生 MATERIALIZED 物化**。



### type：访问类型

#### type 七档梯度

**type 表示“怎么访问表”**：从秒查到全扫的七档阶梯。

- system 与 const：主键或唯一索引等值，最多一行
- eq_ref：连接时被驱动表走主键或唯一索引，一对一
- ref：非唯一索引等值匹配，可能多行
- range：索引范围扫描，BETWEEN、大于小于、IN
- index：扫全索引树，比全表好的有限
- ALL：全表扫描，性能底线

> type 是 EXPLAIN 的第一警报器：线上高频查询出现 ALL 或 index，先问为什么没走索引；const 与 eq_ref 是理想形态，ref 与 range 是常态可接受区。

**速记**：**const 顶级 ref 常态 range 可收，index ALL 亮红灯**。



#### key 与 key_len

**key 显示实际用的索引，key_len 显示用到几列**：联合索引的显微镜。

- possible_keys 是候选，key 才是决定；key 为 NULL 即没用索引
- key_len 按使用到的索引列累加：类型字节数加 NULL 标志 1 字节加变长 2 字节
- bigint 非 NULL 为 8；varchar(50) utf8mb4 非 NULL 为 200 加 2
- 由 key_len 反推联合索引用到了第几列

> key_len 是验证最左前缀的工具：计划 (a, b, c) 索引只用了 a 列时，key_len 只等于 a 的宽度。会算 key_len，联合索引的利用情况一目了然。

**速记**：**key 定索引，key_len 数列长，反推用几列**。



#### rows 与 filtered

**rows 是预估扫描行数，filtered 是再过滤比例**：两数相乘估结果。

- rows 来自统计信息，是估算不是精确值
- filtered 百分比表示存储层返回后在 Server 层再过滤的行占比
- rows 乘 filtered 约等于最终参与后续操作的行数
- 统计信息失真时 rows 严重偏离，ANALYZE TABLE 可刷新

> rows 是性能量级的秒表：乘以 IO 代价即可预估查询成本。rows 估算离谱（实际 10 行估 100 万）时先怀疑统计信息，别急着改 SQL。

**速记**：**rows 估扫描，filtered 算折扣，估算离谱刷统计**。



### Extra：执行细节

#### Extra 高频值

**Extra 补充计划的备注栏**：几个高频值对应几类典型行为。

- Using index：覆盖索引，免回表，最优备注
- Using index condition：索引下推 ICP 生效
- Using where：Server 层再过滤
- Using filesort：需要额外排序，没吃上索引序
- Using temporary：建临时表，常见于 GROUP BY、DISTINCT

> Using index 是奖状，Using filesort 与 Using temporary 是罚单。罚单不一定致命——小数据量的排序无所谓——但大表上的罚单必查。

**速记**：**index 是奖状，filesort temporary 是罚单，大表罚单必查**。



#### filesort 与 temporary 的成因

**两种罚单各有配方**：对症才能下药。

- filesort：ORDER BY 列没被当前索引序覆盖，或排序带函数表达式
- temporary：GROUP BY 列与索引序不符、DISTINCT 大集、UNION 去重
- 解法方向：调整联合索引让序对齐，或减小参与排序的数据量
- sort_buffer 与临时表都有内存上限，超限落磁盘更慢

> 消罚单的次序：先看能否用索引序替代（改索引或改写语句），再看能否减小数据集（提前过滤、只取必要列），最后才考虑调大缓冲参数——那是止血不是治病。

**速记**：**序不对齐开罚，先对索引再减量，调参最末**。



### 进阶工具

#### EXPLAIN FORMAT 与 ANALYZE

**计划不止一种看法**：JSON、树形与真执行三个层级。

- EXPLAIN FORMAT = JSON：完整代价细节，含成本估算
- EXPLAIN FORMAT = TREE：树形执行顺序，8.0 可读性最好
- EXPLAIN ANALYZE：真执行并统计每步实际行数与耗时
- EXPLAIN ANALYZE 会真的跑语句，写操作慎用

> 三层工具对应三个深度：日常看表格，调优看 JSON 或树形，疑难杂症上 ANALYZE 对比预估与实际的偏差——偏差大的地方就是优化器误判的地方。

**速记**：**表格日常，树形读序，ANALYZE 见真章**。

```sql
EXPLAIN ANALYZE
SELECT o.id, u.name FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.created_at >= '2026-09-01';
```



#### EXPLAIN 的使用纪律

**EXPLAIN 结论有时效性**：环境与数据一变，计划重估。

- 测试环境的计划不等于生产：数据量、统计信息、参数全不同
- 索引变更、版本升级后要重新 EXPLAIN 关键查询
- 统计信息驱动计划，刷新方式见前文 rows 与 filtered 一节
- 计划是依据不是教条：配合真实耗时监控验证

> “我 EXPLAIN 过了”不能作为上线依据，生产数据量下的验证才算数。把关键 SQL 的计划基线记录在案，回归时有对照。

**速记**：**计划跟着数据变，基线在案，上线前生产验**。
