## 触发器与事件

### 触发器

#### 触发器是什么

**触发器是绑定在表 DML 上的自动程序**：语句一到，程序即动。

- CREATE TRIGGER 定义，绑定某张表
- 时机二选一：BEFORE（动作前）或 AFTER（动作后）
- 事件三选一：INSERT、UPDATE、DELETE
- FOR EACH ROW 表示行级语义：每受影响行触发一次
- 一张表对同一事件同一时机只能有一个触发器

> 触发器把逻辑藏进数据库：应用层看不见它，出问题时最容易成为“幽灵改动”的来源；治理要求见篇末清单一节。

**速记**：**表绑程序 DML 触发，行级执行，一表一事一时机各一个**。

```sql
CREATE TRIGGER trg_order_after_insert
AFTER INSERT ON orders
FOR EACH ROW
BEGIN
    INSERT INTO order_audit(order_id, action, created_at)
    VALUES (NEW.id, 'create', NOW());
END;
```



#### NEW 与 OLD 引用

**NEW 是改动后的行，OLD 是改动前的行**：可用性随事件类型变化。

- INSERT：只有 NEW，OLD 不存在
- DELETE：只有 OLD，NEW 不存在
- UPDATE：两者都有，OLD 是旧值 NEW 是新值
- BEFORE INSERT 与 BEFORE UPDATE 里可给 NEW 赋值，实现默认值与清洗
- AFTER 系列只能读，行已落定

> BEFORE 赋值是触发器最实用的能力：入库前统一 trim、补默认时间、派生字段计算。想改行必须用 BEFORE，AFTER 里赋 NEW 直接报错。

**速记**：**插看 NEW 删看 OLD，改前改后全都有，改值只有 BEFORE 能干**。

```sql
CREATE TRIGGER trg_user_before_insert
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
    SET NEW.name = TRIM(NEW.name);
    SET NEW.created_at = NOW();
END;
```



#### 触发器的限制与风险

**触发器的能力边界与隐性代价都要清楚**：用前先看红线。

- 触发器内不能使用事务控制语句（COMMIT、ROLLBACK）
- 外键级联动作不会触发触发器，两者不叠加
- 触发器对应用层不可见，排障难度高
- 每行触发一次，大批量 DML 时成倍放大耗时

> 大批量导入时触发器是性能刺客：百万行的 INSERT 就是百万次触发器执行。批量任务前先评估是否临时禁用（删触发器重建，MySQL 不支持 DISABLE），或者把审计逻辑挪到 binlog 消费端。

**速记**：**管不了事务碰不到外键级联，批量场景先掂量**。



#### 触发器的典型用途

**审计、联动、清洗是三大正经用途**：业务逻辑不宜搬进来。

- 审计：AFTER 系列把变更写入审计表，记录谁改了什么
- 联动：AFTER DELETE 清理关联缓存表、同步冗余字段
- 清洗与默认值：BEFORE 系列修数据、补字段
- 复杂业务规则（扣库存、算佣金）不该放触发器，应放应用层或过程

> 判断一条逻辑该不该进触发器：它是否属于“数据完整性”而非“业务流程”。完整性（审计、一致性兜底）适合，业务流程（下单、扣款）绝不。

**速记**：**审计联动清洗可入，业务流程莫沾**。



### 事件调度器

#### 事件是什么

**事件是数据库内置的定时任务**：到点自动执行一段 SQL。

- CREATE EVENT 定义，前提是 event_scheduler 已开启
- AT 时间戳：一次性事件，到点执行一次
- EVERY 间隔单位：周期事件，如 EVERY 1 DAY
- ON SCHEDULE 子句定义计划，DO 子句是执行体

> 事件让数据库自己干定时活，不依赖外部调度器；哪些任务该交给它、哪些该留给外部调度，见后文取舍一节。

**速记**：**事件即库内 cron，AT 一次 EVERY 周期**。

```sql
SET GLOBAL event_scheduler = ON;

CREATE EVENT ev_daily_archive
ON SCHEDULE EVERY 1 DAY
STARTS '2026-09-08 02:00:00'
DO
    INSERT INTO orders_archive
    SELECT * FROM orders
    WHERE created_at < CURDATE() - INTERVAL 90 DAY;
```



#### 事件的生命周期管理

**事件有启用、过期与保留三个状态维度**：不管理就会悄悄堆积。

- ENABLE 与 DISABLE 控制事件的启停，ALTER EVENT 切换
- ON COMPLETION NOT PRESERVE（默认）：一次性事件执行后自动删除
- ON COMPLETION PRESERVE：执行后保留定义，便于审计与复用
- 周期事件持续存在，须在 DO 体内自行做幂等与清理

> 生产上推荐 PRESERVE 加 DISABLE 的组合管理变更：改动定义时先停再改再启，避免执行到一半的定义。information_schema.events 是巡检入口。

**速记**：**默认用完即删，PRESERVE 留档 DISABLE 检修**。



#### 事件与外部调度的取舍

**库内事件与外部调度器各管一段**：边界按任务性质划。

- 事件：单库内的数据维护，如归档、统计、清理临时数据
- 外部调度：跨库编排、依赖外部系统、需要重试告警的任务
- 事件没有原生的失败告警，需自己写错误表
- 多实例部署下事件每个实例都跑，注意主从与多写冲突

> 用事件前先回答：任务失败谁知道？数据重复执行会怎样？答不上来就别把关键任务交给它——事件适合可重跑的幂等维护，不适合一次性关键动作。

**速记**：**事件干幂等家务，关键任务靠外部调度**。



### 综合运用

#### 触发器与事件的治理清单

**自动执行的逻辑必须有台账**：看不见的代码最容易出事。

- 维护触发器与事件的完整清单：名称、作用、负责人
- 任何批量任务执行前检查目标表的触发器
- 事件全部幂等化：重复执行不产生脏数据
- 审计类触发器写入的表要设归档策略
- information_schema.triggers 与 events 定期巡检

> 这两类对象的共同风险是“静默”：不报错、不告警、悄悄改变数据。治理的本质是把它们从隐形变成显形，纳入与代码同级的评审流程。

**速记**：**清单化、幂等化、巡检化，隐形逻辑显形管**。
