## 日志体系与运维

### 四类日志

#### 分工与开关

**Server 层有四类日志**：错误、通用查询、慢查询、二进制。

- 错误日志：默认开，记录启动、崩溃、复制中断等非正常事件
- 通用查询日志：默认关，记录所有收到的语句，排障时临时开
- 慢查询日志：默认关，记录超阈值语句（48 篇）
- 二进制日志：8.0 默认开，记录数据变更，供复制与恢复（35 篇）
- redo/undo 属引擎层，不在这个清单里

```sql
SHOW VARIABLES LIKE '%log%';
SHOW VARIABLES LIKE 'log_error';
SHOW VARIABLES LIKE 'log_bin';
```

> 四类日志的默认状态差异很大：错误日志与 binlog 默认开，查询日志与慢日志默认关。上线前确认的应该是「开着的两个往哪写、留多久」，而不是两个关着的怎么开。

**速记**：**错误与 binlog 默认开，查询与慢日志默认关**。

#### 落盘位置

**日志位置由 datadir 与变量共同决定**：写错位置就是磁盘告警。

- 错误日志默认 `datadir/hostname.err`，8.0 由 `log_error` 指定
- 通用查询与慢查询日志默认在 `datadir`，文件名由各自 `_file` 变量控制
- binlog 默认 `datadir/mysql-bin.000001` 递增
- 全部日志建议独立挂盘，避免与数据文件争 IO 与空间

```sql
SELECT @@datadir, @@log_error, @@slow_query_log_file,
       @@general_log_file, @@log_bin_basename;
```

> 日志与数据同盘是容量事故的常见起点：慢日志一天涨几十 GB，把数据盘写满后 MySQL 直接不可写。独立分区加监控是基本配置。

**速记**：**默认都在 datadir，独立挂盘才安全**。

### 错误日志

#### 记录范围

**错误日志只记「不正常」与「生命周期」**：不是全量流水。

- 启动与关闭、版本与参数加载
- 崩溃与断言失败、InnoDB 表空间损坏
- 复制线程中断、连接数打满、权限拒绝
- 死锁详情（`innodb_print_all_deadlocks=1` 时，34 篇）
- 8.0 支持 `log_error_services` 输出 JSON 格式，便于采集

```ini
[mysqld]
log_error = /var/log/mysql/error.log
log_error_verbosity = 2
innodb_print_all_deadlocks = 1
```

> 错误日志是最被忽视的一份日志：平时没人看，出事时是唯一能还原「那一刻发生了什么」的材料。巡检项里应该有「错误日志新增 ERROR 数」，而不是只看进程活着。

**速记**：**错误日志记生死，死锁详情靠开关**。

#### 读法与常见条目

**读错误日志先看时间线，再看重复**：同一错误刷屏说明根因未除。

- `[ERROR]` 是要处理的，`[Warning]` 多数可忽略但要统计趋势
- `Aborted connection` 频繁出现，多半是应用连接池或超时配置不当
- `Too many connections` 对应 `max_connections` 与连接泄漏
- `Disk full` 与 `Cannot create/write` 是容量问题，先救火再分析

```bash
grep -c "\[ERROR\]" /var/log/mysql/error.log
grep "Aborted connection" /var/log/mysql/error.log | tail -20
```

> `Aborted connection` 有两个成因：客户端异常断开、或语句执行中连接被杀。前者是应用问题，后者可能是 `wait_timeout` 太短或大查询被中断——看紧邻的上下文再判。

**速记**：**先时间线后重复，ERROR 处理 Warning 看趋势**。

### 通用查询日志

#### 何时开

**通用查询日志是全量流水**：只在定位「到底发了什么 SQL」时开。

- `general_log=ON` 开当前实例，`general_log_file` 指定文件
- 记录每一条收到的语句，含连接与断开
- 开销明显：高 QPS 下每秒写 MB 级文本，磁盘与 IO 双杀
- 定位完立即关闭，别留在生产上

```sql
SET GLOBAL general_log_file = '/var/log/mysql/general.log';
SET GLOBAL general_log = ON;
-- 复现问题后立刻关闭
SET GLOBAL general_log = OFF;
```

```text
2026-10-20T10:12:31.452  12 Query  SELECT * FROM tb_order WHERE id = 9
2026-10-20T10:12:31.453  12 Query  SELECT * FROM tb_order WHERE id = 9
```

> 通用查询日志最有价值的场景是「怀疑应用发了重复 SQL」：ORM 的 N+1 问题在这里一目了然。开五分钟胜过读一天代码。

**速记**：**临时开、立刻关，用它抓应用发的原话**。

#### 与审计的区别

**通用查询日志不是审计日志**：它能被关、能被改、不防篡改。

- 无账号维度的完整审计字段，只有连接 ID
- 可被 DBA 关闭，不满足合规要求的不可抵赖性
- 审计需求应上审计插件（如 audit log 类插件）或外部代理
- 通用查询日志的定位是「排障工具」

> 把排障日志当审计证据，是合规审查里常见的错误。两者目的不同：一个为了查问题，一个为了追责任，后者要求独立、只追加、不可关闭。

**速记**：**排障可以关，审计必须不可关**。

### 二进制日志运维

#### 保留与清理

**binlog 会一直涨**：保留策略必须显式设置。

- `binlog_expire_logs_seconds` 控制自动清理，8.0 默认 2592000 秒（30 天）
- `PURGE BINARY LOGS TO 'mysql-bin.000010'` 删到指定位点之前
- `PURGE BINARY LOGS BEFORE '2026-10-01 00:00:00'` 按时间删
- `SHOW BINARY LOGS` 看现有文件与大小
- 从库正在读的 binlog 不能被删，否则复制中断

```sql
SHOW BINARY LOGS;
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';

PURGE BINARY LOGS BEFORE '2026-10-01 00:00:00';
```

> 保留时长由「最慢的从库能落后多久」与「恢复到多久之前」两个需求共同决定。只按磁盘空间删是危险动作：删掉的正是灾备要用的那一段。

**速记**：**过期按秒设，PURGE 按位点或时间，从库在读不能删**。

#### 切换与重置

**binlog 切换是运维常规动作**：备份前切一个，恢复边界才清晰。

- `FLUSH BINARY LOGS` 关闭当前文件并开新文件，等同一次切分
- `max_binlog_size` 默认 1GB，事务大会突破上限
- `RESET MASTER` 清空全部 binlog 并重置编号，仅用于初始化或重建复制
- 主从环境中执行 `RESET MASTER` 会让从库彻底失去同步依据

```sql
FLUSH BINARY LOGS;
SHOW MASTER STATUS;   -- 8.0.22 起可用 SHOW REPLICA STATUS 看从库
```

> 备份脚本里先 `FLUSH BINARY LOGS` 再记位点，恢复时的「从哪个文件哪个位点开始回放」才没有歧义。省这一步，恢复边界就落在文件中间。

**速记**：**备份先切分，位点才干净，RESET 只在重建时用**。

### 综合运用

#### 日志治理清单

**六项确认，日志才不会变成负担**：

- 四类日志的位置、保留期、磁盘配额已明确
- 慢日志阈值与业务 SLA 对齐，不用默认 10 秒
- 通用查询日志默认关闭，开启有审批与自动关闭机制
- binlog 保留期覆盖最坏恢复场景与最慢从库
- 错误日志纳入告警，ERROR 数量突增要通知
- 日志轮转与压缩策略就位，避免单文件无限增长

> 日志治理的目标不是「都开着」，而是「需要时拿得到、平时不占资源」。四类日志的开关与保留期，应该写进运维手册而不是留在某个人的习惯里。

**速记**：**位置保留告警轮转，四项定完再谈采集**。
