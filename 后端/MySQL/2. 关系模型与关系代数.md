## 关系模型与关系代数

关系模型是全部 SQL 的理论底座：表就是关系，查询就是关系代数表达式的求值。理解这一层，写 SQL 从记语法变成推导表达式，也能解释优化器为什么敢改写你的语句。本篇是本系列的理论起点，随后两篇分别讨论结构设计（E-R 模型）与冗余控制（范式）。

### 关系模型的三要素

#### 关系模型是什么

**关系模型**：是**用二维表描述数据、以集合运算与关系运算操纵数据、并施加完整性约束的数据库模型**，由数据结构、数据操作、完整性约束三要素构成。

- 数据结构：单一结构，即关系（二维表），不像层次模型与网状模型那样需要指针结构
- 数据操作：集合式的选择、投影、连接，一次操作作用于整个集合而非单条记录
- 完整性约束：实体完整性、参照完整性、用户定义完整性三类
- 提出者：E. F. Codd 于 1970 年提出，是当今绝大多数数据库的理论基础

> 关系模型能一统天下，靠的是**单一数据结构加非过程化的集合操作**：用户只说“要什么”，不说“怎么取”，怎么取交给优化器。三要素里“结构”只占一样东西，这是它比层次与网状模型简单得多的根本原因。

**速记**：**结构一张表，操作一批算，约束三类立**。



#### 关系模型的术语体系

**关系、元组、属性、域、分量**：五个术语各有精确定义，不可混用。

- **关系**（Relation）：一张二维表，如 学生(学号, 姓名, 年龄)
- **元组**（Tuple）：表中的一行，代表一个实体实例
- **属性**（Attribute）：表中的一列，列名即属性名
- **域**（Domain）：属性的取值范围，如“姓名”的域是全部合法姓名字符串
- **分量**（Component）：元组在某一个属性上的取值，即某行某列的那一个格子
- **关系模式**（表头）：关系的型，记作 关系名(属性1, 属性2, ...)，说明“有哪些列”
- **关系实例**（表体）：某一时刻关系里的全部元组，是关系的值

> 关系模式是型，关系实例是值，如同变量声明与变量的当前取值。要注意“关系模式”一词在本系列有两个层级：指单张表头时是本条定义，指全库表结构时应称数据库模式；正式表述中不要混用。

**速记**：**关系是表、元组是行、属性是列、域是取值界、分量是格**。



#### 键体系

**键是能唯一标识元组的属性集**：四个概念层层收窄。

- **超键**（Superkey）：能唯一标识元组的属性集，可能含多余属性
- **候选键**（Candidate Key）：不含多余属性的超键，任何真子集都不能唯一标识元组
- **主键**（Primary Key）：从多个候选键中选定一个用于日常标识
- **外键**（Foreign Key）：本关系中取值必须来自另一个关系（或本关系）主键或候选键的属性集
- **全键**（All-key）：候选键包含了关系的全部属性，此时称全码
- 主属性是包含在任一候选键中的属性；候选键可以有多个，主键只能有一个

例题：设 学生(学号, 姓名, 身份证号)，业务上一名学生只有一个学号、一个身份证号，且二者都可唯一确定学生。

- 候选键有两个：学号 与 身份证号
- 若选 学号 作主键，则 身份证号 是候选键但非主键，对它应加唯一约束
- 超键除上述两者外，还包括 (学号, 姓名)、(学号, 身份证号) 等含冗余属性的组合

> 候选键“不含多余属性”这个限定是全部推理的起点：含多余属性的超键无法用来讨论部分依赖，因此范式判断一律以候选键为参照（4 篇）。同一张表有多个候选键时，主属性集合要把它们全部并起来算。

**速记**：**超键能定行，候选键无冗员，主键选其一，外键指别人**。



### 关系的性质与完整性约束

#### 关系的五条性质

**关系必须同时满足五条性质**：任意一条被破坏，它就不再是关系。

- **属性同质**：同一列的所有分量取自同一个域，不允许一列里既是字符串又是数字
- **属性无序**：列可以任意交换次序，所以关系模式才需要显式写明列的顺序
- **元组无序**：行没有先后之分，除非用 ORDER BY 显式指定顺序
- **元组不重复**：关系中不允许出现完全相同的两行，这是集合互异性的要求
- **分量原子**：每个分量都是不可再分的最小数据单位，即满足第一范式（4 篇）

> 五条性质直接对应工程后果：因为行无序，分页必须自己写 ORDER BY 给结果定序，否则 InnoDB 返回的行序不保证（19 篇）；因为分量原子，往一个字段里塞“张三,李四”这种集合值就违反了关系定义，正确做法是拆出独立的表（3 篇）。

**速记**：**同质、列无序、行无序、不重复、不拆分**。



#### 三类完整性约束

**完整性约束保证库里的数据始终讲得通**：分三类。

- **实体完整性**：主键既不能为空也不能重复，保证每个元组可被唯一标识
- **参照完整性**：外键的取值要么为空，要么等于被参照关系中某个元组的主键值，保证引用不断链
- **用户定义完整性**：针对具体业务的语义约束，如成绩在 0 到 100 之间、性别只取男或女
- 前两类是关系模型固有的，任何关系数据库都必须支持；第三类由数据库或应用各自实现
- 外键“或为空”这一分支意味着允许“暂时不知道指向谁”，是否允许由业务决定

> 删除被引用行时的行为（级联删除、置空、拒绝）属于参照完整性的实现选项，在建表时用 ON DELETE 系列子句声明（11 篇）。把它当成约束的一部分来设计，比事后在应用层补救可靠得多。

**速记**：**主键非空不重、外键要么空要么对上、业务约束各自定**。



### 关系代数的运算体系

#### 两类运算与五个基本运算

**关系代数**：是**以关系为运算对象、结果仍是关系的抽象查询语言**，分传统集合运算与专门的关系运算两大类。

- **传统集合运算**：并、交、差、笛卡尔积，把关系当元组集合处理，要求参与运算的关系同元
- **专门的关系运算**：选择、投影、连接、除，针对表的结构设计
- **五个基本运算**：并、差、笛卡尔积、选择、投影，其余运算都可由这五个导出
- **封闭性**：任何运算的结果仍是一个关系，因此表达式可以层层嵌套

> 封闭性是关系代数能表达复杂查询的根本：先选择、再连接、再投影，像搭积木一样嵌套；SQL 的嵌套子查询就是这种嵌套结构在语法上的投影（21 篇）。反过来说，若运算结果不再是关系，嵌套就无从谈起。

**速记**：**并差积选投是基本，交连除靠它们导出**。



#### 并、差、交与相容性

**并、差、交都要求两个关系同元同域**：否则运算没有意义。

- **相容条件**：两个关系的属性个数相同，且对应属性的域相同
- **并**：属于 R 或属于 S 的元组构成的集合，结果自动去重
- **差**：属于 R 但不属于 S 的元组构成的集合
- **交**：同时属于两者的元组，可由 R 减 (R 减 S) 导出，所以不是基本运算
- **差不可交换**：R 减 S 与 S 减 R 的结果一般不同

> 相容性在 SQL 里对应 UNION 两侧列数与类型必须匹配（22 篇）。并运算的语义是去重的，而 SQL 的 UNION ALL 保留重复，UNION 才去重——把运算定义与实现选项混为一谈，是判断结果行数时出错的主要原因。

**速记**：**同元同域才可并差交，差不可交换**。



#### 笛卡尔积

**笛卡尔积把两个关系横向拼接**：元组数相乘、属性数相加。

- 设 R 有 m 个元组、n 个属性，S 有 p 个元组、q 个属性
- 结果有 m 乘 p 个元组、n 加 q 个属性
- 结果中每一行是把 S 的一行接在 R 的一行之后
- 单纯的笛卡尔积几乎总是无意义的大表，要靠后续选择挑出有意义的组合

> 笛卡尔积是连接的原料：θ 连接等于笛卡尔积加选择，写作对积做条件选择。这也是“忘记写连接条件会产生灾难性膨胀”的理论解释——优化器不得不先生成 m 乘 p 行的中间结果，再指望条件把它筛回去。

> [!WARNING]
> **警告内容**：多表查询漏写连接条件时，数据库会老老实实生成整张笛卡尔积再筛选，行数按乘法增长，千万行级的两张表一次就足以打满磁盘与内存。排查“结果行数莫名暴增”时，第一件事就是确认每个连接都有条件。

**速记**：**行相乘列相加，连条件才成连接**。



#### 选择与投影

**选择按行筛选，投影按列裁剪**：一个横切，一个纵切。

- **选择**：挑出满足条件的元组，对应 SQL 的 WHERE 子句
- **投影**：挑出指定的列，对应 SQL 的 SELECT 子句
- 选择不改变属性的个数，结果元组数不增
- 投影减少属性个数，并且结果要去掉重复元组
- 一元运算：两者都只作用于一个关系

> 投影天然去重这一点最容易被忽略：对“姓名”列做投影，若表中有两人同名，结果只保留一行。SQL 里必须写 DISTINCT 才有同样效果，因为 SQL 的表允许重复行——这是关系代数比 SQL 更“纯粹”的典型例子，也是对比两者语义时最该记住的差异。

**速记**：**选择挑行，投影裁列，投影天生去重**。



#### 连接

**连接是“笛卡尔积加选择”的复合运算**：按条件把两张表拼成一张。

- **θ 连接**：在 R 与 S 的笛卡尔积中挑出满足比较条件的元组，条件形如 R.A θ S.B，θ 可取任一种比较运算符
- **等值连接**：θ 连接中条件取等号的特例
- **自然连接**：在两张表的同名属性上做等值连接，并在结果中去掉重复的那一列
- **悬浮元组**：自然连接中因找不到配对而被舍弃的元组
- **外连接**：把悬浮元组也保留下来，缺失的一侧填空值，分左外、右外与全外连接

例题：两张表分别为 学生(学号, 姓名, 班级号) 与 班级(班级号, 班级名)。

- 等值连接的结果含 4 列：学号、姓名、班级号（学生表）、班级号（班级表）、班级名
- 自然连接只在同名属性 班级号 上配对，并去掉重复列，结果含 4 列：学号、姓名、班级号、班级名
- 若某学生尚未分配班级，班级号为空，则该学生在自然连接中成为悬浮元组被丢弃；用左外连接可把它保留下来

> [!IMPORTANT]
> **重要内容**：自然连接有两条隐含前提，同名属性且语义相同。若两张表都有一列 id，而一个是图书编号、另一个是作者编号，自然连接会照常按等值配对，产出看起来合理、实际完全错误的结果。因此高风险系统中常明令禁止 SQL 的 NATURAL JOIN，宁可手写 ON 条件把语义写在明处。

**速记**：**连接即积加选，等值是特例，自然连接去同名列并藏风险**。



#### 除运算

**除运算是“求满足全部对应者”的运算**：结果属性集比被除数窄。

- 设 R 的属性集为 X 并 Y，S 的属性集为 Y，则 R 除以 S 的结果属性集为 X
- 结果中的每个元组 x，与 S 中每个元组 y 组合成的 (x, y) 都出现在 R 中
- **可导出式**：R 除以 S 等于 对 R 在 X 上投影 减去 对 ( ( X 上投影 乘 S ) 减 R ) 在 X 上投影
- SQL 里没有对应的运算符，需用双重 NOT EXISTS 或分组计数表达（21 篇）
- 识别关键词是“全部”“所有”“每一门”“每一个”

例题：设 选课(学号, 课程号)，课程(课程号, 课程名)，查询“选修了全部课程的学生学号”。

- 被除数为 选课，除数为 对 课程 在 课程号 上投影（即全部课程号）
- 结果属性集为 学号
- 语义核对：某学号出现在结果中，当且仅当它与每一个课程号组成的元组都在选课里

> 除运算一步到位的表达能力是它的价值所在：同一问题改用其他运算，至少要绕两个“不存在”的嵌套。反过来说，读到一个多层嵌套的 NOT EXISTS 查询，第一反应就应该是“它其实是在做除法”。

**速记**：**除求“与 S 全配”，SQL 靠双重非存在**。



### 关系代数与 SQL 的对照

#### 一个查询的两种写法

**同一条查询可以写成关系代数表达式，也可以写成 SQL**：两者互为翻译。

例题：设 学生(学号, 姓名)、课程(课程号, 课程名)、选课(学号, 课程号, 成绩)，查询“选修了数据库课、且成绩大于 90 的学生的姓名”。

关系代数表达式：

```text
π 姓名 ( σ 成绩 > 90 ( σ 课程名 = '数据库' ( 课程 ) ⋈ 选课 ) ⋈ 学生 )
```

对应的 SQL：

```sql
SELECT s.姓名
FROM 学生 AS s
JOIN 选课 AS sc ON sc.学号 = s.学号
JOIN 课程 AS c  ON c.课程号 = sc.课程号
WHERE c.课程名 = '数据库' AND sc.成绩 > 90;
```

对应关系逐项拆开：

- FROM 与 JOIN 的部分对应笛卡尔积加连接条件
- WHERE 的部分对应整体的选择运算
- SELECT 的列表对应投影，注意关系代数的投影会去重，SQL 默认不去重
- 连接的先后顺序与选择的先后顺序不影响集合语义，但影响执行代价

> 对照的意义在于理解优化器：SQL 先被翻译成一棵关系代数表达式树，再用等价变换（选择下推、投影下推、连接重排）改写成更便宜的一棵树。所谓查询优化，本质上就是关系代数表达式的等价变换（30 篇、36 篇）。

**速记**：**SQL 是关系代数的方言，优化就是表达式树的改写**。



#### 常见查询的表达套路

**三类查询各有固定的表达套路**：先认型，再套式。

- **筛选加取列**：先选择后投影，写作对关系先做条件选择再投影目标属性
- **多表关联**：先把相关表自然连接成一张大表，再对其做选择与投影
- **带“全部”的查询**：用除法，或“存在—不存在”的嵌套表达
- **带“没有 / 不存在”的查询**：用差运算表达“全集减掉符合条件的部分”

例题（差运算）：查询“没有选修任何课程的学生学号”。

```text
π 学号 ( 学生 ) − π 学号 ( 选课 )
```

例题（除法）：查询“选修了全部课程的学生学号”。

```text
π 学号, 课程号 ( 选课 ) ÷ π 课程号 ( 课程 )
```

> 关系代数的价值在于把“要什么”一次说清：表达式写出来，SQL 只是语法糖。反过来，读到一段绕的 SQL，先把它还原成关系代数表达式，往往立刻看清它在算哪个集合，bug 也会自己浮出来。

**速记**：**先选后投是基本款，全部用除，没有用差**。



### 关系演算与表达能力

#### 元组演算与域演算

**关系演算是用谓词描述结果的语言**：只写要什么，不写怎么做。

- **元组关系演算**：以元组变量为主体，写作使谓词成立的全部元组构成的集合，谓词中可含比较、与或非以及存在量词与全称量词
- **域关系演算**：以属性取值为变量，用一组域变量描述结果，形式更接近以一行为单位的填表
- **QBE**（Query By Example）：域演算的典型实现，用户在表格中填写示例条件即可查询
- 存在量词表达“至少有一个满足”，全称量词表达“所有都满足”，因而可表达“全部”类查询

> 元组演算与域演算的差别在“声明什么变量”：前者声明代表整行的元组变量，后者声明代表单个取值的域变量。表达能力上两者等价，且都与关系代数等价，三者统称关系数据语言，这是关系模型的重要理论结论。

**速记**：**演算写谓词，代数写步骤，QBE 是演算的填表实现**。



#### 过程性与非过程性

**关系代数偏过程性，关系演算偏非过程性，SQL 两者兼取**。

- **过程性**指表达式规定了运算的先后次序；**非过程性**指只描述结果应满足的条件
- 关系代数是嵌套结构的，嵌套即规定了次序，因此偏过程性
- 关系演算只有谓词没有次序，因此偏非过程性
- SQL 的 SELECT 部分像演算（描述结果集），FROM 与 JOIN 部分像代数（描述步骤）
- 无论写法如何，实际执行路径既不取决于代数写法，也不取决于 SQL 写法，而由优化器决定

> 常见误记是把关系代数说成非过程化语言。判断标准只有一条：表达式里有没有规定运算的先后。关系代数规定了（嵌套结构即次序），所以偏过程性；关系演算只有谓词，所以非过程化。二者表达能力等价，差别在描述方式而不在能力。

**速记**：**代数管次序，演算写条件，能力等价**。



### 综合运用

#### 关系代数推 SQL 的自查路径

**把 SQL 还原成关系代数表达式是检验理解的最快方法**：四步走。

- 第一步：把 SQL 的每一层子查询各自还原成一个关系代数表达式
- 第二步：把 FROM 与 JOIN 还原成笛卡尔积加选择条件
- 第三步：把 WHERE 还原成选择，把 SELECT 的列表还原成投影，并补齐投影的隐式去重
- 第四步：把还原结果与业务意图对照，检查是否有多余的笛卡尔积或缺失的去重
- 若 ON 条件写在了 WHERE 里，左外连接会退化成内连接，这一退化在表达式上表现为“选择与连接的次序颠倒”

> 这条路径尤其适合排查“结果行数莫名变多”：多数情况下，还原出的表达式里会多出一个没有条件约束的笛卡尔积，或者一个被写进 WHERE 的外连接条件。

**速记**：**SQL 还原成表达式，多出来的积就是 bug**。

**关系模型的三条线索贯穿全系列**：结构、运算、约束。
