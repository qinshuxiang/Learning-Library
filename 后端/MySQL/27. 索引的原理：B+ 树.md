## 索引的原理：B+ 树

### 为什么是 B+ 树

#### 索引的本质

**索引是排好序的数据结构**：用额外的空间与写放大，换取查询少扫数据。

- 没有索引：查询只能全表扫描，逐行判断条件
- 有索引：按结构定位，直接跳到目标数据附近
- 代价：索引本身占空间，写入时要同步维护，不是越多越好

> 索引解决的是“找得快”，不是“存得省”。理解任何一个索引问题，先问三句：结构是什么、查询怎么走、写入付多少。

**速记**：**有序换快查，空间与写入是账单**。



#### 逐一排除候选结构

**哈希、二叉树、红黑树、B 树都各有硬伤**：排除法走到 B+ 树。

- 哈希表：等值快，但范围查询与排序无能为力，且哈希冲突需处理
- 二叉查找树：有序输入退化成链表，全靠运气
- 红黑树：自平衡但树太高，每层一次磁盘 IO，几百万行要二十多层
- B 树：矮胖且有序，但非叶子节点也存数据，单页容纳的键变少，且范围查询要中序回溯
- B+ 树：非叶子只存键、数据全在叶子且叶子链表相连

> 磁盘 IO 按页计费是整个推导的前提：树每深一层就多一次页读取。矮胖不是美学，是 IO 次数的算术。

**速记**：**哈希怕范围，二叉怕退化，红黑太高 B 树太胖，B+ 双优胜出**。



#### B+ 树的两大特性

**非叶子只导航、叶子存数据且相连**：两条特性分别成就了快查与范围扫。

- 非叶子节点只存键与子指针，单页能放更多键，树更矮
- 全部数据在叶子节点，任何查询都走固定深度，性能稳定
- 叶子节点间双向链表相连，范围查询顺链遍历即可
- 三层 B+ 树配合 16KB 页可承载千万级行

> “查询深度恒定”是 B+ 树被选中的隐藏优势：不会因数据分布不同而忽快忽慢，容量估算可预期。叶子链表则让 BETWEEN 与 ORDER BY 天然高效。

**速记**：**上层导航下层存数，叶子牵手范围白送**。



### 聚簇与二级索引

#### 聚簇索引

**InnoDB 的表本身就是一棵聚簇索引树**：叶子节点存整行数据。

- 主键即聚簇键，数据按主键顺序物理存放
- 没有主键时取唯一非空索引，再没有则生成隐藏的行 id
- 按主键查询直接定位，无需回表
- 主键顺序即物理顺序，这就是自增主键友好的根源

> “表即索引”是 InnoDB 与 MyISAM 的根本分歧：MyISAM 索引与数据分离，InnoDB 数据就长在主键树上。选主键就是在选数据的物理布局。

**速记**：**主键树即数据本身，无主键也能活但别懒**。



#### 二级索引与回表

**二级索引的叶子存主键值，不是整行**：查别的列要回表。

- 在 name 列建索引，叶子存 name 与主键 id
- 查询要的列不在索引里时，拿 id 回聚簇树再取整行，即回表
- 回表次数等于命中行数，行数多时代价线性放大
- 覆盖索引（要的列都在索引里）可完全免回表（29 篇）

> 为什么叶子放主键而不是行地址：行会挪（页分裂），主键不变，二级索引无需跟着改。设计索引时先想查询要哪些列，够得着就造覆盖，够不着就少查几行。

**速记**：**二级叶子挂主键，缺列回表来补齐**。



### 页与树的维护

#### 页分裂与页合并

**按主键顺序插入是 B+ 树的润滑剂**：乱序插入会撕开页。

- 页按主键有序存放，写满 16KB 就新开一页
- 自增主键总是追加到最后一页，顺序写，几乎不分裂
- 随机主键（如 UUID）落到树的中部，页满则分裂、挪半页数据
- 大量删除后页变稀疏，相邻页合并回收空间

> 页分裂不仅慢，还放大缓存抖动与写放大：同一份数据被搬来搬去。UUID 当 InnoDB 主键的代价在生产上通常被严重低估。

**速记**：**自增顺写免分裂，随机主键页页撕**。



#### 三层树能存多少行

**约两千万行是三层 B+ 树的经典量级**：可推导，不是玄学。

- 一页 16KB，假设主键 bigint 8 字节、页指针约 6 字节
- 非叶子一页可放约 16KB 除以 14 字节，约 1170 个键
- 叶子一页假设放 15 行（行宽较大时），根下两列即 1170 乘 1170 个叶子页
- 合计约 2000 万行；行更小则更多，行更宽则更少

> 推导的意义不在精确数字，而在建立直觉：树高决定查询 IO 次数，三层即三次 IO（根常驻内存后更少）。这也是大表分区的体感依据——控制单树规模。

**速记**：**1170 平方乘 15，三层两千万，树高即 IO**。



### 主键设计

#### 自增主键与业务主键

**主键要短、有序、稳定**：三个词对应三类代价。

- 短：所有二级索引都存主键副本，主键长则全库膨胀
- 有序：顺序写入免页分裂（前述）
- 稳定：主键更新意味着数据搬家，业务字段做主键易变则灾难
- 自增 bigint 是默认答案；UUID 主键需用有序变体（如雪花 id）替代，分裂代价见前文页分裂节

> 业务键（身份证号、手机号）做主键的问题在“变与长”：换手机号就得动整行与全部二级索引。业务唯一性用唯一索引表达，代理主键自增扛物理布局，两者各司其职。

**速记**：**短稳有序定主键，业务唯一交给唯一索引**。



#### 哈希索引的补充角色

**InnoDB 有自适应哈希但不归你管**：显式哈希索引另有局限。

- 自适应哈希（AHI）：引擎对热点页自动建哈希加速等值查，不可人工指定
- MEMORY 引擎支持显式 HASH 索引，仅等值，重启即失
- 全文检索用 FULLTEXT 索引，倒排结构，另成体系
- 人工想在 InnoDB 上造哈希：生成列存哈希值加普通索引，等值查再回原列核验

> 知道这些扩展角色即可，日常 95% 的索引决策都在 B+ 树体系内完成；真到了需要哈希索引的场景，问题本身通常已经不适合单机 MySQL。

**速记**：**热点哈希引擎自理，人工哈希等值专用**。



### 综合运用

#### 从原理到实践的推论

**B+ 树原理直接推出四条工程铁律**：不是经验，是结构必然。

- 主键自增有序，避免随机写分裂
- 主键短小，二级索引全部连带受益
- 查询列尽量进索引，免回表
- 控制单表规模，树太高则 IO 与缓存都恶化

> 面试与实战通用：讲索引先讲结构，讲结构先讲页与 IO。一切“最佳实践”都能从 16KB 页与叶子链表推导出来，背结论不如会推导。

**速记**：**结构决定实践，页与链表推出四铁律**。
