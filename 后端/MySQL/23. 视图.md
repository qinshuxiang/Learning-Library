## 视图

### 视图基础

#### 视图是什么

**视图是存储下来的查询语句**：一个虚拟表，本身不存数据。

- CREATE VIEW 视图名 AS SELECT 语句，把查询固化成可复用的名字
- 每次查询视图时，按定义实时执行底层查询
- 视图不占数据空间，只存定义文本
- 可以像表一样 SELECT，部分场景可以 UPDATE

> 视图是“命名的查询”而非“复制的表”：底表变了，视图结果跟着变。想要快照语义得用真实表加定时刷新，别指望视图存档。

**速记**：**视图存定义不存数，查询时现算**。

```sql
CREATE VIEW v_active_users AS
SELECT id, name, email
FROM users
WHERE status = 1 AND deleted_at IS NULL;
```



#### 视图的两大价值

**封装与隔离是视图的立身之本**：简化消费端，保护底表。

- 封装：把多表连接、复杂过滤固化为一个名字，业务方只写简单查询
- 隔离：只暴露部分列或部分行，配合权限实现数据收缩
- 语义统一：状态过滤、口径计算写一次，处处一致
- 平滑变更：底表重构时，视图保持旧接口不破消费方

> 视图带来一致性的同时也会藏住复杂度：一个看似轻量的视图底下可能连着五张表的全连接。用之前 SHOW CREATE VIEW 看看它到底是谁。

**速记**：**封装复杂、收缩暴露，接口稳定视图来扛**。



### 视图的进阶特性

#### 可更新视图

**简单视图可以直接 UPDATE、INSERT、DELETE**：复杂视图只能读。

- 可更新的条件：无聚合、无 DISTINCT、无 GROUP BY、无 UNION、无特定子查询
- 更新实质作用于底表，视图只是通道
- 多表连接视图在 8.0 部分场景可更新，限制多、实用性一般
- 不满足条件的视图可读不可写

> 把更新入口开在视图上是双刃剑：消费方少写一条 UPDATE，但你失去了在应用层统一校验的机会。敏感表的更新入口收在视图里反而更安全，按团队习惯取舍。

**速记**：**无聚合无去重才可写，写了也是改底表**。



#### WITH CHECK OPTION

**CHECK OPTION 让经视图写入的数据仍满足视图条件**：防止写进去就消失。

- WITH CHECK OPTION：插入或更新的行必须符合视图 WHERE 条件
- CASCADED（默认）：级联检查所有下层视图
- LOCAL：只检查本视图的条件
- 不加该选项时，经视图可写入视图本身查不到的行

> “写入即失踪”是可更新视图最迷惑的行为：WHERE status = 1 的视图能插入 status = 0 的行，随后再查无此行。加 CHECK OPTION 把视图条件变成约束，闭环才完整。

**速记**：**CHECK OPTION 封口，写进去的必须查得到**。

```sql
CREATE VIEW v_active_users AS
SELECT id, name, status FROM users WHERE status = 1
WITH CHECK OPTION;
-- 之后的 INSERT status = 0 会被拒绝
```



#### ALGORITHM：合并与物化

**视图有两种执行算法**：MERGE 展开语句，TEMPTABLE 物化临时表。

- MERGE：把视图定义文本替换进外层查询，能借用外层的索引与条件
- TEMPTABLE：先执行视图存临时表，外层再查临时表
- 含聚合、DISTINCT、UNION、子查询的视图只能 TEMPTABLE
- 可用 ALGORITHM 子句指定，默认由优化器自动选

> TEMPTABLE 视图丢掉了谓词下推的机会：外层的 WHERE 不能提前进视图内部。性能敏感路径上的复杂视图，用 EXPLAIN 确认它没有悄悄物化成大临时表。

**速记**：**MERGE 展开 TEMPTABLE 落表，复杂视图多物化**。



### 视图的管理

#### 定义查看与修改

**视图的定义与状态都有标准查看方式**：改与删同样简单。

- SHOW CREATE VIEW 视图名：看定义原文
- information_schema.views：系统级清单，含算法与检查选项
- ALTER VIEW 或 CREATE OR REPLACE VIEW：改定义
- DROP VIEW：删除，不影响底表数据

> CREATE OR REPLACE 在不中断依赖的情况下更新定义，是视图热更新的惯用写法；直接 DROP 再 CREATE 会留一个空窗，权限依赖还可能丢失。

**速记**：**定义可查可替换，删除只动壳不动数**。



#### 视图与派生表的区别

**视图是持久的命名查询，派生表是语句内的临时产物**：生命周期是分水岭。

- 视图跨语句、跨会话存在，可授权、可复用
- 派生表只在单条语句内有效
- 两者执行层面可能同样物化，性能未必有差
- 高频复用的查询固化成视图，一次性逻辑留在语句内

> 反过来，把一次性逻辑建成视图会造成视图沼泽：几十个没人再用又不敢单的视图；要不要建，见后文决策树一节。

**速记**：**视图持久可授权，派生表用完即散**。



#### 视图的维护成本

**视图的价值取决于被治理的程度**：没人管的视图群是负债。

- 视图嵌套视图，层层物化后性能不可预测
- 定义漂移：底表改列名，视图用旧别名撑着，语义渐行渐远
- 权限视图需要与角色体系同步维护
- 定期审计：列出所有视图，标注用途与负责人

> 视图适合薄薄一层：单一职责的封装与收缩，不是抽象层框架。

**速记**：**视图宜薄不宜深，定期审计防沼泽**。



### 综合运用

#### 视图使用决策树

**要不要建视图，四问定夺**：问完再动手。

- 这段查询逻辑是否被多处复用？不是则不建
- 是否需要收缩列或行做权限隔离？是则值得建
- 底层查询是否稳定不常变？常变则维护成本高
- 是否能保持简单（少嵌套、少聚合）？复杂则考虑落表

> 权限收缩是视图最无可替代的场景；单纯为了“少写 JOIN”而堆的视图，多数在半年后变成查询黑洞。

**速记**：**复用与隔离才建，简单稳定才留**。
