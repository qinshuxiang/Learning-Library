## MyCat 分片：垂直分库与水平分表

### 拆分的两种落法

#### 垂直分库在配置里的样子

**垂直分库就是不同表指向不同 dataHost**：一个 MyCat 前面，后面是多个独立实例。

- 按业务把表分组，每组一个 dataNode 甚至一个 dataHost
- schema.xml 里同一个 schema 下挂多张表，各自 `dataNode` 不同
- 跨库的关联查询 MyCat 无法下推，会拆成多条查询再内存关联
- 好处是故障与扩容都按业务隔离，坏处是跨业务事务失去单库保障

```xml
<schema name="SHOP" checkSQLschema="false" sqlMaxLimit="100">
    <table name="tb_user"  dataNode="dn_user"/>
    <table name="tb_order" dataNode="dn_order"/>
    <table name="tb_goods" dataNode="dn_goods"/>
</schema>

<dataNode name="dn_user"  dataHost="host_user"  database="shop_user"/>
<dataNode name="dn_order" dataHost="host_order" database="shop_order"/>
<dataNode name="dn_goods" dataHost="host_goods" database="shop_goods"/>
```

> 垂直分库后「用户下单」这条链路横跨两个实例，本地事务失效。要么上分布式事务，要么改造成最终一致——这个决定应该在拆分前做完，而不是拆分后被动应对。

**速记**：**一业务一主机，表按域分家，事务边界重新画**。

#### 水平分表在配置里的样子

**水平分表是同一张逻辑表映射到多个物理表**：结构与数据同构，按规则分家。

- 逻辑表一个名字，`dataNode="dn1,dn2,dn3"` 列出全部落点
- `rule` 指向 rule.xml 里的分片规则，按分片列决定归属
- 物理库里的表名可以不同，用 `dataNode` 的 database 属性区分
- 表数量与节点数量不必相等，一个节点可承载多个分片

```xml
<table name="tb_order" dataNode="dn1,dn2" rule="mod-long" primaryKey="order_id"/>
```

```sql
-- 应用侧看到的是完整一张表
SELECT * FROM tb_order WHERE user_id = 10086;   -- 单片命中
SELECT COUNT(*) FROM tb_order;                  -- 两片各算一次再求和
```

> 水平分片后「按主键查」与「按分片键查」是两种命运：分片键带条件才是单片点查，其余情形一律广播到所有片。这就是第 40 篇说的分片键即查询契约。

**速记**：**一表多节点，规则定归属，分片键决定单片还是广播**。

### 垂直分库实战

#### 建库建表与数据迁移

**先建物理结构与数据，再切流量**：中间件不代劳建表和搬数。

- 三个实例各建库 `shop_user`、`shop_order`、`shop_goods`
- 从原单库按表导出导入，`mysqldump` 按表过滤
- 表结构与索引保持原样，字符集与排序规则保持一致
- 校验行数与关键字段校验和，确认无遗漏

```bash
# 按表导出，再各导入对应实例
mysqldump -uroot -p shop tb_user  > /tmp/tb_user.sql
mysqldump -uroot -p shop tb_order > /tmp/tb_order.sql
mysql -h192.168.1.11 -uroot -p shop_user < /tmp/tb_user.sql
mysql -h192.168.1.12 -uroot -p shop_order < /tmp/tb_order.sql
```

> 迁移期最容易被忽略的是外键与触发器：跨实例后外键无法建立，触发器也要在各库重建。先在目标结构里删掉外键约束，用应用层保证一致性。

**速记**：**分表导出分库导入，外键先拆触发重建**。

#### 跨库关联的处理

**MyCat 能跑跨库 join，但代价藏在执行计划里**：能下推的下推，不能的拉回内存。

- 同一 dataHost 内的关联可能被下推到 MySQL 执行
- 跨 dataHost 的关联由 MyCat 各自查询后在内存拼装
- 内存拼装的数据量受 `sqlMaxLimit` 与堆内存约束，大表关联会 OOM
- 工程上的正解是拆成两次查询在应用层组装，或用宽表冗余

```sql
-- 跨实例关联：MyCat 拆成两条查询后内存 join
SELECT o.order_no, u.name
  FROM tb_order o JOIN tb_user u ON o.user_id = u.id
 WHERE o.user_id = 10086;
```

> 「中间件支持跨库 join」是营销话术：它支持，但支持的方式是把你最不该做的操作变得能跑。数据量一大，内存关联先拖垮 MyCat 进程，再拖垮整条链路。

**速记**：**同源可下推，跨源内存拼，大表关联必炸**。

### 水平分表实战

#### 分片表设计与落点验证

**分片前先算清三件事**：分片键、片数、每片容量。

- 分片键选区分度高且查询必带的列，订单表通常用 `user_id` 而非 `order_id`
- 片数按三到五年数据量预估，取模方案宁多勿少
- 每片表结构与索引完全一致，包括主键与唯一索引
- 插入后直连物理库验证落点，别只看 MyCat 的汇总结果

```sql
-- 在物理库 db1 上确认落点
SELECT COUNT(*) FROM db1.tb_order WHERE user_id % 2 = 0;
-- 在 db2 上验证另一片
SELECT COUNT(*) FROM db2.tb_order WHERE user_id % 2 = 1;
```

> 唯一索引在分片下只在片内唯一：`order_no` 建了唯一索引，两个片仍可能各存一条相同单号。全局唯一必须靠分布式 ID 或独立的去重表保证。

**速记**：**键要必带，片要留余量，唯一只在片内成立**。

#### 全局序列

**分片后自增主键必然冲突**：每个片各自从 1 开始。

- MyCat 提供 `sequnceHandlerType` 四种方式：本地文件、数据库、时间戳、ZK
- 数据库方式最常用：建 `MYCAT_SEQUENCE` 表用 `MyCatSeq_` 前缀取值
- 应用层方案是雪花算法，与中间件解耦，扩容不受影响
- 序列必须是趋势递增的，否则聚簇索引页分裂严重（28 篇）

```sql
-- server.xml 中把 sequnceHandlerType 设为 1（数据库方式）后
INSERT INTO tb_order(id, order_no, user_id)
VALUES (NEXT VALUE FOR MYCATSEQ_GLOBAL, 'NO20261020001', 10086);
```

> 自增主键在单库是白送的，在分片下变成一道设计题。时间戳与 ZK 方案在高并发下都可能成为瓶颈，数据库段号方案（一次取 1000 个号）是折中。

**速记**：**自增必冲突，序列四选一，趋势递增保页序**。

### 综合运用

#### 拆分验收清单

**验收不看功能通不通，看边界守不守**：六项逐条过。

- 每条高频 SQL 是否带分片键，不带的有多少条（用慢日志统计）
- 跨片查询的比例，超过一成就要重新设计分片键
- 有无跨实例 join，能否改成应用层组装
- 全局唯一约束是否都有替代方案
- 统计类查询的汇总耗时是否可接受，是否需要汇总表
- 扩容演练：加一个片，数据迁移脚本是否可用

> 拆分质量的分水岭是「分片键覆盖率」：九成查询带分片键，拆分就是成功；三成不带，等于把单库问题变成 N 倍的单库问题再加一层网络开销。

**速记**：**键覆盖率定成败，跨片比例看设计，扩容必须能演练**。
