## E-R 模型与概念结构设计

概念结构设计是把需求变成一张图，逻辑结构设计是把这张图变成一组表。这一步做对了，范式与索引才有讨论的意义；这一步做漏了，后面所有优化都只是给错误的骨架打补丁。本篇承接关系模型（2 篇），输出的是关系模式的骨架，交给范式理论（4 篇）去检验。

### 数据库设计的整体流程

#### 三级模式与两级映射

**三级模式**：是**数据库在架构上分成的外模式、模式、内模式三层**，两级映射负责在层与层之间转换。

- **外模式**（用户模式、子模式）：某一类用户看到的局部数据视图，对应 SQL 的视图（23 篇）
- **模式**（逻辑模式、概念模式）：全库数据的整体逻辑结构，对应全部表结构的定义
- **内模式**（存储模式）：数据在磁盘上如何组织与存储，对应索引、页与文件
- **外模式与模式的映射**：保证**逻辑独立性**，改表结构时可让视图不受影响
- **模式与内模式的映射**：保证**物理独立性**，改存储方式时不必改表定义

> 三级模式是“数据独立性”的实现手段：应用只依赖外模式，于是模式变了应用不必跟着改；模式只描述逻辑结构，于是换存储引擎、加索引都不算改数据模型。理解这个分层，才知道为什么“加索引不算改数据结构”，也才知道视图该挂在哪一层。

**速记**：**外模式给用户看，模式管逻辑，内模式管磁盘，两级映射换独立**。



#### 设计四阶段

**数据库设计分四个阶段**：需求分析、概念结构设计、逻辑结构设计、物理结构设计。

- **需求分析**：收集业务规则与数据需求，产出数据字典与数据流图
- **概念结构设计**：把需求抽象成与数据库产品无关的 E-R 图
- **逻辑结构设计**：把 E-R 图转换成关系模式，并做规范化处理（4 篇）
- **物理结构设计**：为关系模式选索引、存储参数与分区策略
- 概念结构设计是承上启下的关键，它既要忠实反映需求，又不能过早绑上实现细节

> 逻辑结构设计的产物是关系模式的集合，不是建表语句；建表语句属于物理实现的落地。实务中这两个阶段常被合并成“设计表结构”，但把“有哪些表和什么关系”与“用什么类型和索引”分开思考，能避免把物理细节过早固化进逻辑设计。

**速记**：**需求、概念、逻辑、物理，四步逐级落地**。



#### 概念模型为什么用 E-R 模型

**概念模型必须独立于任何数据库产品**：E-R 模型是它的通用表示。

- 概念模型面向用户与业务，用实体与联系的图形语言沟通，非技术人员也能参与评审
- 概念模型不涉及数据类型、索引、存储引擎等实现细节
- **E-R 模型**：由 P. Chen 于 1976 年提出的实体—联系模型，是概念模型事实上的标准
- 同一张 E-R 图可转换成关系模式、层次模式或网状模式，因此结果可复用
- E-R 模型的三要素：实体、属性、联系

> 必要性来自需求变更的代价：如果一开始就按 MySQL 的类型与索引思考，需求一变就要推倒重来；先画出与产品无关的 E-R 图，换数据库只是换一套转换规则。这就是逻辑设计必须晚于概念设计的理由。

**速记**：**概念模型不带实现味，E-R 图一处画多处用**。



### E-R 模型的三要素

#### 实体与属性

**实体**：是**客观存在且可相互区分的事物**；**属性**是刻画实体特征的数据项。

- **实体**：如一名学生、一门课程、一个班级
- **实体型**：对同类实体共同特征的刻画，用属性名表表示，如 学生(学号, 姓名, 年龄)
- **实体集**：同型实体的集合，如全校学生
- **属性**：实体具有的某一特征，如学号、姓名
- **码**（键）：能唯一标识实体型中每个实体的属性或属性组，如学号

> 实体与实体型、实体集的区别是概念设计的常考点：画在 E-R 图上的是实体型，图中的一个方框代表一个实体集，而不是某一个具体的学生。日常口语里的“实体”通常指实体型，写文档时要注意语境。

**速记**：**实体是类、元组是个，属性是特征，码是身份证**。



#### 属性的分类

**属性分复合、单值、多值、派生四类**：分类决定它在转换时怎么处理。

- **简单属性**：不可再分，如姓名、性别
- **复合属性**：可再分，如地址可分为省、市、街道；转换时通常拆成多个简单属性
- **单值属性**：对同一实体只取一个值，如出生日期
- **多值属性**：对同一实体可取多个值，如一个人的多个联系电话；转换时必须独立成表
- **派生属性**：可由其他属性计算得到，如由出生日期推出的年龄；通常不存储
- **空值**：可表示“不知道”“不适用”“尚未录入”三种语义，设计时要区分，不能一概而论

> [!IMPORTANT]
> **重要内容**：多值属性的唯一正确归宿是拆成一张独立的表，属性为该实体的码加多值属性本身。若把多个电话写成“13800000000,13900000000”塞进一个字段，既违反分量原子性，又让查询、去重与索引全部失效——前缀匹配改成后缀匹配，等值查询退化成全表扫描（14 篇、29 篇）。识别信号是“这个字段里出现过逗号、顿号或竖线分隔的列表”。

**速记**：**复合拆开、多值独立成表、派生不存**。



#### 联系与联系的类型

**联系**：是**实体集之间的关联**，用菱形表示并标注基数。

- **联系型**：两个或多个实体集之间的关联，如“学生—选修—课程”
- **联系的度**：涉及几个实体集就叫几元联系，常见二元联系，也有三元联系
- **基数**：一对一（1:1）、一对多（1:n）、多对多（m:n）
- **联系的属性**：联系本身也可以有属性，如“选修”联系有成绩属性
- **参与约束**：全体参与还是部分参与，前者要求每个元组都必须参与该联系
- 基数由业务规则决定，不能凭直觉：一名学生只能属于一个班、一个班有多名学生，故班级与学生是 1:n

> 联系的属性是设计时最容易漏的一项：成绩不属于学生，也不属于课程，它属于“学生选修课程”这件事本身。判据是问一句“这个值由哪一方决定”——由两方共同决定的值，就挂在联系上；只由一方决定的，就该挂在那一方或独立成表。

**速记**：**属性归谁看决定者，两方共同决定就挂联系上**。



### E-R 图的设计要点

#### 图形记号

**E-R 图用三类图形加边上的标注表达三要素**。

- **矩形**：实体集，框内写实体名
- **椭圆**：属性，用无向边连到所属的实体或联系
- **菱形**：联系，框内写联系名，连到参与的各实体
- **边上的标注**：1、n、m 等基数，以及角色名（用于一元联系）
- 双线矩形表示弱实体，双线菱形表示标识联系，双线椭圆表示多值属性
- 虚线椭圆表示派生属性，三角形表示 ISA 继承层次

> 画图的纪律是“一图一语义”：如果一条边既表示“属于”又表示“管理”，就该拆成两个联系。含混的图在转换成表时会分不清该在哪一侧放外键，也会让基数无法判断。

**速记**：**框是实体、椭圆是属性、菱形是联系、边上是基数**。



#### 弱实体与标识联系

**弱实体**：是**没有自己的完整码、必须借助属主实体才能唯一标识的实体**。

- **属主实体**（强实体）：弱实体所依赖的实体
- **标识联系**：弱实体与属主实体之间决定弱实体标识的联系，用双线菱形表示
- 弱实体的区分依赖“属主实体的码 + 自己的部分码”，如订单明细的码是订单号加行号
- 转换成表时，弱实体的主键由属主主键加部分码组成，并对属主主键加外键
- 弱实体对属主主键的外键必须带级联删除，否则会留下孤儿行

> 判断弱实体的标准是“离开属主它还有没有意义”：订单明细离开订单就不该存在，员工的家属信息离开员工也不该独立存在。这类实体在设计时要显式声明级联删除，不能指望应用层记得清理。

**速记**：**弱实体靠属主定身份，主键是属主码加部分码，必须级联删**。



#### 一元联系、三元联系与 ISA 层次

**联系可以发生在同一实体集内部，也可以涉及多个实体集**。

- **一元联系**（自反联系）：实体集与自身联系，如“员工—管理—员工”，必须在边上标角色名区分两端的角色
- **三元联系**：三个实体集同时参与，如“供应商—项目—零件”表示某供应商为某项目供应某零件
- **ISA 层次**（继承）：把实体集按共性抽象出父实体，子实体继承父实体的全部属性，如“学生”分为“本科生”与“研究生”
- ISA 层次有两组约束：**不相交与重叠**（一个实体能否同时属于多个子类）、**全包含与部分包含**（父类实体是否必须属于某个子类）

> 三元联系不要随手拆成三个二元联系：拆开后语义会变强或变弱，而“供应商为项目供零件”这件事本身没有办法挂到任何一对实体上。ISA 层次则要注意转换策略的选择，转换后可能出现空值增多或连接增多，见后文转换规则。

**速记**：**自反要标角色，三元别乱拆，ISA 管继承**。



#### 常见设计错误

**概念设计阶段的两类错误代价最大**：实体与联系的错分、基数的错判。

- **把联系当实体**：把“选修”直接画成一个实体，忽略了它本质上是学生与课程之间的联系
- **把实体当属性**：把“班级”当成学生的一个属性，导致班级信息大量重复且无法独立维护
- **基数写反**：把 1:n 画成 n:1，转换后外键落在错误的一侧
- **漏掉联系的属性**：成绩、数量、时间等由双方共同决定的属性没有标注
- **多值属性未识别**：地址、电话、别名等可多值的属性被当成单值字段
- **参与约束缺失**：没有写明某方是全体参与，导致转换后无法判定外键是否该加非空约束

> 判断“是实体还是属性”有一个经验法则：如果这个东西自己还有若干要描述的属性、还要被别的实体引用、还可能独立变化，它就是实体而不是属性。班级有班主任、有教室、人数会变，因此它必然是实体；而“性别”没有自己的属性、不会被引用，因此它是属性。

**速记**：**能独立描述、能被引用、会独立变化者，皆实体**。



### E-R 图到关系模式的转换

#### 转换的基本规则

**转换的产物是一组关系模式**：每条规则对应一类元素。

- 每个**实体型**转换为一个关系模式，实体属性成为关系属性，实体的码成为关系的码
- 每个**联系**按基数类型决定是否单独建表（见后三条）
- **多值属性**、**弱实体**、**ISA 层次**各有专门规则
- 关系模式的标准写法：关系名(属性1, 属性2, ..., 属性k)，主键加下划线，外键用文字说明
- 转换结果要用冗余、插入删除异常、完整性三条判据复核（见本篇末与 4 篇）

> 转换不是唯一解：同一张 E-R 图可以有多种等价的关系模式集合，差异在冗余度与外键位置。范式理论正是用来在多个解之间做判断的工具，所以转换先做到“对”，规范化再做到“好”。

**速记**：**实体各建一表，联系看基数决定取舍**。



#### 1:1 与 1:n 联系的转换

**一对一与一对多联系通常不另建表**：把外键放到“多”的一方。

- **1:1 联系**：把任意一方的主键作为外键放进另一方；若联系有属性，与该外键放在一起
- **1:n 联系**：把“1”方的主键放进“n”方作为外键，联系的属性一并放进“n”方
- 若“n”方对联系是全体参与，外键可再加非空约束
- 若 1:1 联系双方都部分参与，也可选择单独建表，但通常没有必要
- 把外键放到“1”方会使外键列数随“多”方数据增长，结构上不可行

例题：班级(班级号, 班级名) 与 学生(学号, 姓名)，一名学生属于一个班级，一个班级有多名学生。

转换结果：

```text
班级( 班级号, 班级名 )        主键：班级号
学生( 学号, 姓名, 班级号 )    主键：学号，班级号 为指向班级的外键
```

> [!WARNING]
> **警告内容**：外键放到“1”方在结构上就不可行，因为一个班级对应多名学生，班级表里得为每个学生预留一列，而列数不能随数据增长。基数写反的后果不是“性能稍差”，而是模型无法落地——这也是转换前必须复核基数的原因。

**速记**：**1:1 任一方放外键，1:n 外键落在 n 方**。



#### m:n 联系的转换

**多对多联系必须单独建表**：新表的码是双方码的组合。

- 新建一个关系模式，属性为双方的主键加上联系自身的属性
- 新关系的主键是双方主键的并集，即组合键
- 两个主键分别作为指向两张原表的外键
- 新表在实务中常被称为明细表、关联表或中间表
- 若“多对多”之间允许重复配对，需引入代理键，此时组合键降为唯一约束或普通索引

例题：学生(学号, 姓名) 与 课程(课程号, 课程名)，一名学生可选多门课，一门课可被多名学生选，“选修”有成绩属性。

转换结果：

```text
学生( 学号, 姓名 )                    主键：学号
课程( 课程号, 课程名 )                主键：课程号
选课( 学号, 课程号, 成绩 )            主键：( 学号, 课程号 )
                                      学号、课程号 均为外键
```

> 多对多联系的属性不能划归任何一方，这就是“成绩必须挂在选课上”的转换表现。若把成绩放进学生表，一个学生多门课的成绩无法表达；若放进课程表，一门课多个学生的成绩同样无法表达。新表的主键用组合键还是加自增代理键，属于物理设计的权衡（27 篇）。

**速记**：**多对多单表立，组合码是双方码，联系属性进新表**。



#### 多值属性、弱实体与 ISA 的转换

**三类特殊元素各有专门的转换规则**。

- **多值属性**：单独建立一个关系模式，属性为“原实体的码 + 该多值属性”，主键由两者共同组成
- **弱实体**：转换为一个关系模式，主键为“属主实体的主键 + 弱实体的部分码”，属主主键作外键并级联删除
- **ISA 层次的第一种策略**：父实体建表，每个子实体各建一表，子表用父表主键作外键与主键
- **ISA 层次的第二种策略**：只建子实体的表，把父实体的属性复制进每个子表
- **ISA 层次的第三种策略**：只建父实体的表，把所有子类属性都放进父表，用类型字段区分

例题（多值属性）：学生(学号, 姓名) 有“联系电话”这一多值属性。

转换结果：

```text
学生( 学号, 姓名 )                主键：学号
学生电话( 学号, 电话 )            主键：( 学号, 电话 )，学号 为外键
```

例题（弱实体）：订单(订单号, 下单时间) 与 订单明细(行号, 商品, 数量)，订单明细依赖订单存在。

转换结果：

```text
订单( 订单号, 下单时间 )                            主键：订单号
订单明细( 订单号, 行号, 商品, 数量 )                主键：( 订单号, 行号 )
                                                    订单号 为外键，级联删除
```

> ISA 的三种策略没有绝对优劣：父表加子表最规范，但查一个子类要多一次连接；只建子表无冗余，但公共属性在多个子表里重复；只建父表查询最简单，但子类特有属性会出现大量空值。选择依据是“父实体是否会被单独查询”与“各子类属性差异有多大”，属于逻辑设计阶段的判断。

**速记**：**多值独立成表、弱实体主键拼接、ISA 三择其一**。



#### 完整转换例题

**一张 E-R 图转换成一组建表定义**：逐步推演。

例题：图书借阅系统。

- 实体：读者(读者号, 姓名, 单位)、图书(书号, 书名, 出版社)
- 联系：借阅，发生在读者与图书之间，基数 m:n，带属性 借出日期、应还日期
- 特殊元素：读者的“联系电话”为多值属性

推演步骤：

1. 读者 → 读者(读者号, 姓名, 单位)，主键是读者号
2. 图书 → 图书(书号, 书名, 出版社)，主键是书号
3. 借阅是 m:n → 借阅(读者号, 书号, 借出日期, 应还日期)，主键是(读者号, 书号)，两个属性均为外键
4. 联系电话是多值属性 → 读者电话(读者号, 电话)，主键是(读者号, 电话)
5. 共得四个关系模式，其中借阅与读者电话各含一个外键

```sql
CREATE TABLE 读者 (
  读者号   CHAR(8)      PRIMARY KEY,
  姓名     VARCHAR(30)  NOT NULL,
  单位     VARCHAR(60)
);

CREATE TABLE 图书 (
  书号     CHAR(13)     PRIMARY KEY,
  书名     VARCHAR(80)  NOT NULL,
  出版社   VARCHAR(60)
);

CREATE TABLE 借阅 (
  读者号   CHAR(8)      NOT NULL,
  书号     CHAR(13)     NOT NULL,
  借出日期 DATE         NOT NULL,
  应还日期 DATE,
  PRIMARY KEY (读者号, 书号),
  CONSTRAINT fk_借阅_读者 FOREIGN KEY (读者号) REFERENCES 读者 (读者号),
  CONSTRAINT fk_借阅_图书 FOREIGN KEY (书号)   REFERENCES 图书 (书号)
);

CREATE TABLE 读者电话 (
  读者号   CHAR(8)      NOT NULL,
  电话     VARCHAR(20)  NOT NULL,
  PRIMARY KEY (读者号, 电话),
  CONSTRAINT fk_读者电话_读者 FOREIGN KEY (读者号) REFERENCES 读者 (读者号)
);
```

> 借阅表的主键选择要回到业务确认：(读者号, 书号) 意味着同一读者对同一本书只能有一条借阅记录。若业务允许同一本书被同一读者借还多次，就必须引入借阅流水号作主键，把(读者号, 书号)降为普通索引。这是“联系能不能重复发生”这一业务问题在结构上的直接体现——画图时就要问清楚。

**速记**：**实体先各表，联系看基数，特殊元素单独处理**。



### 逻辑结构设计与后续衔接

#### 关系模式的质量判据

**转换出的关系模式要用三条标准检验**：否则后面要还债。

- **冗余度**：同一事实是否在多个元组里重复存储
- **插入与删除异常**：能否只插入部分事实；删除一条是否会连带丢失其他信息
- **语义完整性**：外键是否齐备，参与约束是否落成了非空约束
- **语义完整性补充**：候选键是否都加了唯一约束，是否漏掉了由业务决定的唯一性

> 这三条判据正是范式理论要解决的问题（4 篇）。转换阶段先画对图、定对码，规范化阶段再判断该拆到第几范式，两个阶段的关注点不同，不能互相替代。

**速记**：**冗余、异常、完整性，三条判据过一遍**。



#### 用户子模式与视图

**外模式在关系数据库里的实现是视图**：规划逻辑结构时要一并考虑。

- 为不同角色的用户定义不同视图，隐藏无关列与敏感列
- 视图是逻辑设计的组成部分，不是建表阶段的补充动作
- 简化查询：把常用的多表连接固定成视图，应用层只写单表查询
- 权限可以挂在视图上，比挂在基表上更贴合业务角色（37 篇）
- 视图能否更新、是否物化，属于实现层面的选择（23 篇）

> 从三级模式看，视图就是外模式；把权限控制挂在外模式上，比把权限一点一点堆在基表上更容易审计。设计阶段就把视图规划进去，可以让查询接口与权限口径一次到位。

**速记**：**视图即外模式，按角色分口子**。



### 综合运用

#### 从需求到表的推演顺序

**一套可复用的设计动作顺序**：六步。

- 第一步：列出需求文档里的全部名词，逐个判断是实体、属性还是角色
- 第二步：列出全部动词，逐个判断是否为联系，并确定基数与参与约束
- 第三步：补充由双方共同决定的属性，挂到对应的联系上
- 第四步：识别多值属性、弱实体与继承层次
- 第五步：按转换规则生成关系模式，标出主键与外键
- 第六步：用冗余、异常、完整性三条判据复核，必要时进入规范化

> 名词动词法是实践中最有效的起点：每一个名词都问一句“它需要被独立描述吗”，每一个动词都问一句“它连接了哪两方、每一方到底能连几个”。走完这两遍，E-R 图基本完整，剩下的漏项多半是联系属性与参与约束。

**速记**：**名词定实体，动词定联系，双方决定的属性挂联系**。



#### 理论层与本系列的接口

**本篇产出的是关系模式的骨架，后续篇章都在骨架上填肉**。

- 建表与类型选择：把关系模式的属性落到具体数据类型（7 至 10 篇）
- 键与约束：把主键、外键、唯一约束写成 DDL（11 篇）
- 规范化：判断关系模式该拆到第几范式（4 篇）
- 索引设计：依据外键与查询模式选索引（27 篇、29 篇）
- 事务与锁：主键与外键的选择会直接影响行锁的争用范围（34 篇）

> 概念设计与逻辑设计是“画图定骨架”，其后每一篇都在这副骨架上作业。骨架错了，索引与优化只能打补丁——这也是把理论三篇放在实操之前的原因。

**速记**：**先定骨架，后填血肉，骨架错了补丁无用**。
