## Express 接入 MySQL 的工程实践

### 定位

#### 这一篇解决什么

**前 54 篇讲数据库本身，本篇讲怎么在 Express 里用它**：连接、时区、查询、事务、错误、分层。

- 读者是写业务接口的人，不是 DBA：只保留落代码时真正会碰到的部分
- 主线是 `mysql2` 原生驱动，ORM 只做对照（选型未定时不绑死）
- 代码用 JavaScript，Express 5 与 4 的差异单独标注
- 与 43 至 47 篇的关系：中间件方案在 Node 侧只体现为连接串不同

> 这一篇的取舍标准是「上线后会不会疼」：连接池配错、事务漏释放、注入漏防、时区错位，这四类问题占了生产事故的大头，其余可以查文档。

**速记**：**连接时区查询事务错误分层，六处写对就够用**。

### 连接层

#### 连接池

**一个进程一个池，绝不要每次请求建连接**：建连接是 TCP 加认证，比查询本身还贵。

- `mysql.createPool` 在进程启动时创建，全局复用
- `connectionLimit` 是单进程上限，要与 MySQL 的 `max_connections` 对齐
- 多进程部署要乘：`pm2 instances × connectionLimit` 才是总连接数
- `queueLimit` 控制排队上限，默认 0 表示不限制，容易把内存排爆
- `enableKeepAlive` 防中间设备掐掉空闲连接

```js
// db/pool.js
import mysql from 'mysql2/promise';

export const pool = mysql.createPool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT ?? 3306),
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,

  connectionLimit: 10,
  maxIdle: 10,
  idleTimeout: 60_000,
  queueLimit: 0,
  enableKeepAlive: true,
  keepAliveInitialDelay: 0,

  supportBigNumbers: true,
  bigNumberStrings: true,
  dateStrings: true,
  multipleStatements: false,
});
```

> 连接数算法要倒着推：MySQL `max_connections=500`，留 50 给运维与复制，剩 450 分给所有进程。4 个 Node 实例就是每实例 100，再留余量取 80。拍脑袋写 `connectionLimit: 100` 是最常见的打满库的方式。

**速记**：**进程一个池，上限乘实例数，倒着从 max_connections 算**。

#### 优雅关闭

**进程退出前要还连接**：否则库侧留一堆 Sleep 连接，重启几次就打满。

- 监听 `SIGTERM` 与 `SIGINT`，先停止接新请求，再 `pool.end()`
- `pool.end()` 会等待借出的连接归还，要给超时兜底
- 不要在请求处理中调用 `pool.end()`
- 容器环境注意 `preStop` 与 `terminationGracePeriodSeconds` 要大于关闭耗时

```js
// server.js
const server = app.listen(3000);

async function shutdown(signal) {
  console.log(`${signal} received, closing...`);
  server.close(async () => {
    await pool.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref();
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
```

> 没有优雅关闭的典型症状是「发布后库里多出几十个 Sleep 连接，几分钟后才消失」。短连接场景看不出问题，长连接加频繁发布就会撞上 `max_connections`。

**速记**：**先停服务再关池，超时兜底防挂死**。

### 时区：东八区

#### 三层时区

**时间错 8 小时，永远是这三层里有两层不一致**：

- **操作系统时区**：决定 `@@system_time_zone`，容器默认 UTC
- **MySQL 全局时区**：`time_zone` 默认 `SYSTEM`，跟随 OS；会话继承全局
- **Node 进程时区**：由 `TZ` 环境变量决定，未设置则跟随 OS
- 三者都设成东八区，时间才不会有暗坑；只设其中之一等于没设

```sql
SELECT NOW(), UTC_TIMESTAMP(),
       @@global.time_zone, @@session.time_zone, @@system_time_zone;
```

```text
NOW()              2026-10-20 14:30:00
UTC_TIMESTAMP()    2026-10-20 06:30:00
@@global.time_zone +08:00
@@session.time_zone +08:00
@@system_time_zone  UTC          -- 危险信号：OS 是 UTC
```

> `@@global.time_zone` 显示 `SYSTEM` 时，实际值等于 OS 时区，而 OS 在容器里通常是 UTC。这时 `NOW()` 返回的是 UTC，业务写入的时间直接差 8 小时，且没有任何报错。

**速记**：**OS、全局、进程，三层同频才不出错**。

#### 两种策略

**全链路东八区，还是全链路 UTC**：先定这一个，其余配置都是它的推论。

| 策略 | 库内存什么 | 适合 | 代价 |
|---|---|---|---|
| 全链路 +08:00 | 北京时间字面值 | 国内单区域业务、报表要直读 | 出海或多时区要改造 |
| 全链路 UTC | UTC 绝对时刻 | 跨时区、多租户、对接海外系统 | 每次展示都要转换 |

- 国内单体应用、用户全在东八区：选第一种，简单且报表 SQL 直接可读
- 有海外用户、跨时区调度、要与第三方系统对时间：选第二种，别事后改
- 两种都不能混：一半表存本地时间、一半存 UTC，是最坏的组合
- 中间件与从库必须同策略，否则复制出来的时间会错位

> 策略要写进建表规范，而不是留在某个人的记忆里。判断标准是「这条时间将来会不会被另一个时区的人看」，会就走 UTC。

**速记**：**国内存本地，出海存 UTC，绝不允许混用**。

#### 推荐配置：全链路东八区

**四处一起改，缺一处就差 8 小时**：

- MySQL：`default-time-zone='+08:00'` 写进 `[mysqld]`，重启生效
- 连接：mysql2 传 `timezone: '+08:00'`，告诉驱动「服务器在东八区」
- 进程：`TZ=Asia/Shanghai`，Docker 里也要设，别依赖宿主机
- 读取：`dateStrings: true`，让 DATETIME 以字符串原样出来，绕开 JS `Date` 的转换

```ini
# my.cnf
[mysqld]
default-time-zone = '+08:00'
```

```js
// db/pool.js
export const pool = mysql.createPool({
  // ...连接信息
  timezone: '+08:00',   // 服务器时区，写偏移不要写 Asia/Shanghai
  dateStrings: true,    // DATETIME 直接返回字符串
  supportBigNumbers: true,
  bigNumberStrings: true,
});
```

```bash
# 容器与进程
TZ=Asia/Shanghai
```

> `timezone` 的语义是「我认为服务器在哪个时区」，不是「我要转成哪个时区」。写错方向，8 小时会翻倍成 16 小时。用 `'+08:00'` 而不是 `'Asia/Shanghai'`，因为驱动只保证 `local`、`Z`、`±HH:MM` 三种写法。

**速记**：**库、驱动、进程、读取，四处同设 +08:00**。

#### 为什么不用命名时区

**`Asia/Shanghai` 看着规范，实际多两个失败点**：

- MySQL 的命名时区依赖 `mysql.time_zone*` 表，安装时不导入就是空的
- 未导入时执行 `SET time_zone='Asia/Shanghai'` 直接报 `ERROR 1298`
- 导入要跑 `mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -uroot -p mysql`
- Alpine 等精简镜像没有 `/usr/share/zoneinfo`，还得先装 `tzdata`

```bash
# 需要命名时区时才做，一次性的
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -uroot -p mysql
```

```sql
SELECT COUNT(*) FROM mysql.time_zone_name WHERE Name = 'Asia/Shanghai';
```

> 东八区没有夏令时，`+08:00` 与 `Asia/Shanghai` 在 1986 年之后完全等价。用偏移可以省掉时区表、省掉镜像里的 tzdata，也不会因为时区数据版本不同而出现诡异差异。

**速记**：**命名时区要导表，东八区用偏移就够**。

#### DATETIME 与 TIMESTAMP

**两者对时区的敏感度完全不同**，选错会在会话时区变化时跳变：

- `DATETIME`：存字面值，读写都不做转换，范围到 9999 年
- `TIMESTAMP`：存 UTC，读时按会话时区转回，范围止于 2038-01-19
- 会话时区被改成 `+00:00`，同一行 `TIMESTAMP` 读出会少 8 小时，`DATETIME` 不变
- 全链路东八区方案里统一用 `DATETIME`，行为可预测
- 需要绝对时刻（跨时区事件）时用 `TIMESTAMP`，或 `DATETIME` 存 UTC

```sql
CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  paid_at     DATETIME(3) NULL,          -- 毫秒精度
  PRIMARY KEY (id),
  KEY idx_created (created_at)
) ENGINE=InnoDB;
```

> `TIMESTAMP` 的 2038 上限不是理论问题：保单、合同、设备寿命都可能跨过。国内业务默认 `DATETIME`，除了「必须记录绝对时刻」的场景，没有理由选 `TIMESTAMP`。

**速记**：**DATETIME 存字面，TIMESTAMP 存 UTC，2038 是硬上限**。

#### 写入、读取与输出

**三个环节各自要做什么，写清楚就不会错**：

- 写入：让库生成时间（`DEFAULT CURRENT_TIMESTAMP` 或 `NOW()`），别用 Node 的 `new Date()` 拼字符串
- 读取：`dateStrings: true` 拿到的就是 `'2026-10-20 14:30:00'`，不再经过 `Date`
- 输出：转成带偏移的 ISO（`2026-10-20T14:30:00+08:00`），前端解析不会歧义
- 需要计算时间差时，在 SQL 里用 `TIMESTAMPDIFF`，避免两端时区不一致

```js
// 写入交给库
await conn.query(
  'INSERT INTO orders (user_id, amount) VALUES (?, ?)', [userId, amount],
);

// 读取后转 ISO 输出
function toISO(s) {
  return s ? `${s.replace(' ', 'T')}+08:00` : null;
}

// GET /orders/:id
const [[row]] = await pool.query(
  'SELECT id, amount, created_at FROM orders WHERE id = ?', [id],
);
res.json({ ...row, created_at: toISO(row.created_at) });
```

```js
// 时间差在库里算，别在 JS 里减
const [[{ hours }]] = await pool.query(
  `SELECT TIMESTAMPDIFF(HOUR, created_at, paid_at) AS hours
     FROM orders WHERE id = ?`, [id],
);
```

> 前端直接 `new Date('2026-10-20 14:30:00')` 在 Safari 上会得到 `Invalid Date`，因为它只认 ISO 格式。接口一律输出带 `T` 与偏移的字符串，能同时喂给 `new Date()`、`dayjs` 和数据库。

**速记**：**库生成时间，字符串读出，ISO 带偏移输出**。

#### 排查与验收

**时区问题要么一次配好，要么反复复发**。用四条命令验完：

- `SELECT NOW()` 与系统 `date` 对比，差 8 小时就是库在 UTC
- `@@global.time_zone` 与 `@@session.time_zone` 都要是 `+08:00`
- 从 Node 里查一次 `SELECT NOW()`，与库客户端查的结果一致
- 写入一条记录再读回，`created_at` 与当前北京时间一致

```js
// 一次跑完三层校验
const [[t]] = await pool.query(
  `SELECT NOW() AS db_now, @@session.time_zone AS tz,
          @@system_time_zone AS os_tz`, [],
);
console.log(t, new Date().toString(), process.env.TZ);
```

> 验收要覆盖跨天边界：23:59:59 写入、00:00:01 读回，日期不能跳。只在白天测，永远发现不了 `DATE` 列被截断或时区偏移导致跨日的问题。

**速记**：**库、会话、Node、写入回读，四验加跨天**。

### 查询层

#### query 与 execute

**两者都能参数化，区别在协议**：`execute` 走服务端预处理，`query` 走文本协议。

- `pool.query(sql, params)`：客户端转义后整条发送，兼容性最好
- `pool.execute(sql, params)`：先 `COM_STMT_PREPARE` 再执行，同 SQL 复用执行计划
- 连 MyCat 或部分代理时必须用 `query`（43 篇），它们对预处理支持不全
- 高频同构查询用 `execute` 有收益，低频动态 SQL 用 `query` 更稳

```js
// 推荐默认写法
const [rows] = await pool.query(
  'SELECT id, nickname FROM users WHERE status = ? LIMIT ?',
  [1, 20],
);

// 高频固定查询，可换 execute
const [user] = await pool.execute(
  'SELECT id, nickname FROM users WHERE id = ?',
  [userId],
);
```

> 参数化不等于安全：列名、排序方向、表名不能占位，只能白名单校验。`ORDER BY ?` 会被当成常量排序，是最常见的「写了占位符却没用」的坑。

**速记**：**默认 query，高频 execute，标识符只能白名单**。

#### 结果类型的三个开关

**驱动会替你转换类型，转错就是线上事故**：

- `supportBigNumbers + bigNumberStrings`：BIGINT 返回字符串，防 `Number` 精度丢失
- `decimalNumbers: false`（默认）：DECIMAL 返回字符串，金额不要过 JS 浮点
- `dateStrings: true`：DATE/DATETIME 原样返回字符串，避免时区与 `Date` 对象互转
- 三个开关都在池配置里，全局生效，不要按查询临时改

```js
const [[row]] = await pool.query(
  'SELECT id, balance, created_at FROM accounts WHERE id = ?', [1],
);
// row.id       -> '9007199254740993'（字符串）
// row.balance  -> '1234.56'（字符串）
// row.created_at -> '2026-10-20 14:00:00'（字符串）
```

> 金额用字符串再交给 `decimal.js` 或数据库侧算，是唯一不出错的做法。`0.1 + 0.2` 在 JS 里的结果，在账目上就是一分钱的差。

**速记**：**大整数转字符串，金额不过浮点，时间原样传**。

#### 常用写法

**四个高频模式，抄了就能用**：

- `IN` 查询：`query` 支持数组自动展开，不要手拼逗号
- 批量插入：二维数组一次插入多行
- 分页：`LIMIT ? OFFSET ?` 要传数字，传字符串会被当标识符
- 计数：与列表查询共用 WHERE，避免两处条件写不一致

```js
// IN
const [rows] = await pool.query(
  'SELECT id, nickname FROM users WHERE id IN (?)', [[1, 2, 3]],
);

// 批量插入
await pool.query(
  'INSERT INTO tags (name) VALUES ?', [[['a'], ['b'], ['c']]],
);

// 分页
const limit = 20, offset = (page - 1) * limit;
const [list] = await pool.query(
  'SELECT id, title FROM posts ORDER BY id DESC LIMIT ? OFFSET ?',
  [limit, offset],
);
```

> 批量插入要按 500 到 1000 行分批（49 篇），一次塞十万行会撞 `max_allowed_packet`，报错信息还很难懂。

**速记**：**IN 传数组，批量传二维，分页传数字**。

### 事务

#### 标准写法

**事务必须从池里借一条连接**：`pool.query` 每次可能拿不同连接，事务会散架。

- `pool.getConnection()` 借用，`conn.beginTransaction()` 开启
- 所有语句走这条 `conn`，不能用 `pool`
- `try/catch/finally` 三段：提交、回滚、释放
- `release()` 必须在 `finally`，漏一次就是连接泄漏

```js
async function transfer(fromId, toId, amount) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();

    const [[from]] = await conn.query(
      'SELECT balance FROM accounts WHERE id = ? FOR UPDATE', [fromId],
    );
    if (!from || Number(from.balance) < amount) {
      throw new Error('INSUFFICIENT_BALANCE');
    }

    await conn.query(
      'UPDATE accounts SET balance = balance - ? WHERE id = ?', [amount, fromId],
    );
    await conn.query(
      'UPDATE accounts SET balance = balance + ? WHERE id = ?', [amount, toId],
    );

    await conn.commit();
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}
```

> `SELECT ... FOR UPDATE` 是转账类场景的必需项：不加行锁，两个并发请求会同时读到旧余额，双双扣款成功。锁的粒度取决于索引（34 篇），`id` 是主键，锁的就是这一行。

**速记**：**借连接开事务，全程用同一条，finally 必释放**。

#### 三个禁忌

**事务写错多半不是语法问题，是用法问题**：

- 事务里不要发 HTTP 请求或调外部服务：网络抖动会让事务挂几十秒，锁全表
- 不要把一个事务跨多个 `await` 长时间持有：连接被占住，池很快耗尽
- 不要在事务里 `pool.query()`：那是另一条连接，不在事务内

```js
// 反例：事务里调外部接口
await conn.beginTransaction();
await conn.query('UPDATE orders SET status = ? WHERE id = ?', ['paid', id]);
await fetch('https://pay.example.com/notify');   // 网络不可控
await conn.commit();                              // 锁可能已持有数十秒
```

> 正确的顺序是「先本地提交，再发通知，失败进重试队列」。跨系统的强一致要用补偿，不是把外部调用塞进本地事务。

**速记**：**事务不跨网，不跨池，不长持**。

### 错误处理

#### 错误码对照

**按 `err.code` 分支，不要匹配错误文案**：

- `ER_DUP_ENTRY`（1062）：唯一键冲突，转 409
- `ER_LOCK_DEADLOCK`（1213）：死锁被回滚，可重试
- `ER_LOCK_WAIT_TIMEOUT`（1205）：锁等待超时，可重试或降级
- `ER_CON_COUNT_ERROR`：连接数打满，检查池配置
- `ECONNREFUSED` / `PROTOCOL_CONNECTION_LOST`：网络或库重启
- `ER_ACCESS_DENIED_ERROR`：账号密码或来源 IP 不对

```js
function toHttpError(err) {
  switch (err.code) {
    case 'ER_DUP_ENTRY':        return { status: 409, msg: '记录已存在' };
    case 'ER_LOCK_DEADLOCK':
    case 'ER_LOCK_WAIT_TIMEOUT': return { status: 503, msg: '请重试', retry: true };
    case 'ER_CON_COUNT_ERROR':  return { status: 503, msg: '服务繁忙' };
    default:                    return { status: 500, msg: '服务器错误' };
  }
}
```

> 死锁不是 bug，是并发常态（34 篇）：拿到 1213 应该重试，而不是给用户报错。重试要有次数上限与退避，否则高并发下会形成重试风暴。

**速记**：**按 code 分支，死锁重试，连接错误报警**。

#### 死锁重试封装

**重试逻辑写一次，全项目复用**：

- 只对 1213 与 1205 重试，其他错误直接抛
- 指数退避加随机抖动，防同时重试
- 重试次数 3 次足够，再多说明设计有问题
- 重试要整段事务重来，不能从中间继续

```js
export async function withRetry(fn, { retries = 3, base = 50 } = {}) {
  for (let i = 0; ; i += 1) {
    try {
      return await fn();
    } catch (err) {
      const retryable = err.code === 'ER_LOCK_DEADLOCK'
                     || err.code === 'ER_LOCK_WAIT_TIMEOUT';
      if (!retryable || i >= retries) throw err;
      const wait = base * 2 ** i * (0.5 + Math.random());
      await new Promise((r) => setTimeout(r, wait));
    }
  }
}
```

> 重试的前提是幂等：事务里如果已经发过短信、扣过库存的外部副作用，重试会重复执行。把副作用移出事务，或加幂等键。

**速记**：**只重试两类错，退避带抖动，整段重来**。

### 分层与迁移

#### 目录与职责

**SQL 只出现在 repository 层**：controller 不拼 SQL，service 不管连接。

- `routes` 定义路径与中间件，`controller` 做参数校验与响应
- `service` 编排业务与事务边界，`repository` 只做单表或多表读写
- 事务在 service 层开启，用「传连接」的方式让 repository 参与
- 一个 repository 函数只做一件事，便于单独测与复用

```js
// repositories/userRepo.js
export async function findById(conn, id) {
  const [rows] = await conn.query(
    'SELECT id, nickname, status FROM users WHERE id = ?', [id],
  );
  return rows[0] ?? null;
}

// services/userService.js
import { pool } from '../db/pool.js';
import * as userRepo from '../repositories/userRepo.js';

export async function disableUser(id) {
  const conn = await pool.getConnection();
  try {
    await conn.beginTransaction();
    const user = await userRepo.findById(conn, id);
    if (!user) throw Object.assign(new Error('NOT_FOUND'), { status: 404 });
    await conn.query('UPDATE users SET status = 0 WHERE id = ?', [id]);
    await conn.commit();
    return { ...user, status: 0 };
  } catch (err) {
    await conn.rollback();
    throw err;
  } finally {
    conn.release();
  }
}
```

> repository 接收 `conn` 而不是自己取池，是让事务能跨多个仓储的关键。如果每个仓储自己 `pool.query`，service 的事务就成了摆设。

**速记**：**路由校验控制器编排，事务在服务层，仓储只收连接**。

#### 结构变更

**表结构要能重放**：手工改库是团队协作的头号事故源。

- 用迁移工具管理 DDL：`knex`、`umzug`、`dbmate`、`Prisma Migrate` 都行
- 每个迁移文件只做一件事，且有对应的回滚
- 大表加索引与改字段要评估锁（34 篇），必要时走在线变更工具
- 初始化数据用 seed 脚本，不要写进迁移

```js
// migrations/20261020_create_users.js（knex 风格）
export async function up(knex) {
  await knex.schema.createTable('users', (t) => {
    t.bigIncrements('id').primary();
    t.string('nickname', 64).notNullable();
    t.string('phone', 20).notNullable().unique();
    t.tinyint('status').notNullable().defaultTo(1);
    t.timestamp('created_at').notNullable().defaultTo(knex.fn.now());
    t.index(['status', 'created_at']);
  });
}

export async function down(knex) {
  await knex.schema.dropTable('users');
}
```

> 迁移文件一旦合并进主干就不要再改：改了的人本地跑过，别人拉到的是另一个版本，两边都认为自己是对的。要修就加新迁移。

**速记**：**DDL 全部进迁移，一个文件一件事，合并后不改**。

### ORM 对照

#### 五种写法的取舍

**按团队规模与 SQL 复杂度选，不按流行度选**：

| 方案 | 类型 | 上手成本 | 适合 |
|---|---|---|---|
| mysql2 原生 | 驱动 | 低 | SQL 熟练、查询复杂、要精细控制 |
| Knex | 查询构建器 | 中 | 要拼动态条件，又不想被 ORM 抽象掉 SQL |
| Sequelize | ORM | 中 | 模型关系多，需要内置读写分离与迁移 |
| Prisma | ORM | 中 | 要类型安全与迁移一体化，schema 为中心 |
| Drizzle | ORM | 中 | 想要接近 SQL 的写法加类型推导 |

- 读写分离：Sequelize、TypeORM、Prisma 都有内置方案（上一轮对话的配置），原生驱动要自己写路由
- 分片：五者都没有透明分片，要么上代理（43 至 47 篇），要么应用层路由
- 迁移：Knex、Prisma、Drizzle 自带，Sequelize 用 umzug

> 选型的实际分水岭是「团队里谁改 SQL」：只有后端改，ORM 的抽象收益大；数据分析与 DBA 也要改，原生 SQL 加 Knex 更好协作。

**速记**：**原生控 SQL，Knex 拼条件，ORM 管关系，分片都得自己来**。

#### 与中间件的关系

**用了 MyCat 或 ShardingSphere-Proxy，Express 侧几乎无感**：

- 只改连接串的 host 与 port，代码不动
- 避开 `execute`，用 `query`（MyCat 1.6 的预处理支持不全）
- 事务仍然写 `beginTransaction`，跨片事务由中间件决定是否支持
- 唯一索引与自增要按分片规则重新设计（44 篇）

```js
// 从直连切到 MyCat，只改这三行
const pool = mysql.createPool({
  host: '127.0.0.1',
  port: 8066,        // 原来是 3306
  database: 'TESTDB', // 原来是物理库名，现在是逻辑库名
  // 其余配置不变
});
```

> 中间件方案的迁移成本低，是因为它把复杂度放在了运维侧。代价是排障时多一层：慢查询要同时看 MyCat 日志与真实库慢日志（46 篇）。

**速记**：**换端口换库名，避开 execute，排障看两层日志**。

### 上线检查清单

#### 十条

**发布前逐条过，每条对应一类事故**：

- 连接池上限 × 实例数 < `max_connections` 的八成
- 三个类型开关（`supportBigNumbers`、`decimalNumbers`、`dateStrings`）已确认

- 表结构全部来自迁移，无手工改库
- 慢查询日志与 `performance_schema` 已开（48 篇）
