## 主从复制原理

### 复制的价值与角色

#### 主从架构与职责分工

**主从复制（Replication）**：主库（源）把数据变更写入日志，从库拉取并重放，使两者保持一致。一台主库可挂多台从库。

- **读写分离的底座**：写走主库，读分流到从库，读能力随从库数量近似线性扩展（见第 40 章）。
- **备份与容灾**：从库承担备份任务与慢查询分析，避免备份和重查询拖垮主库。
- **高可用前提**：主库故障时把从库提升为新主库，是第 42 章所有高可用方案的基础。

> 复制解决的是「数据多副本」问题，**不等于高可用**：异步复制下主库宕机可能丢失最新数据，切换需要额外组件保障（第 42 章展开）。

**速记**：主从复制＝**一主多从、日志重放**，读写分离与高可用的共同底座。



### 复制的实现原理

#### binlog 与复制三线程

**复制链路**：主库把变更写入 binlog（第 35 章），从库拉取日志并在本地重放，由三个线程协作完成。

- 主库 **dump 线程**：为每个从库连接维护一份 binlog 推送，从库有请求就把日志事件发过去。
- 从库 **接收线程**（Receiver，旧名 IO thread）：连接主库拉取 binlog，写入本地**中继日志（relay log）**。
- 从库 **回放线程**（Applier，旧名 SQL thread）：读取 relay log，重放其中的数据变更。

```text
主库:  写事务 → binlog ──(dump 线程推送)──→ 从库接收线程
                                              │ 写入
                                              ▼
                                     relay log（中继日志）
                                              │ 读取
                                              ▼
                                        回放线程重放 → 数据一致
```

> relay log 是复制的「缓冲带」：接收与回放解耦，主库日志洪峰先落到 relay log 再慢慢重放，代价是这段积压时间表现为**主从延迟**。

**速记**：**主库 dump 推、从库收进 relay log、回放线程重放**，三线程一条链。



#### 异步、半同步与全同步

**复制模式**：按主库提交事务时对从库的等待程度划分，三档是安全与性能的取舍。

- **异步复制（ASYNC）**：主库写完 binlog 即返回客户端，不等待任何从库。默认模式，性能最好，主库宕机可能丢最新事务。
- **半同步复制（SEMI-SYNC）**：主库等**至少一个**从库确认收到 binlog（写入 relay log 即可，不必回放完成）才返回。损耗一次网络往返，换「不丢已确认事务」的保证。
- **全同步（组复制内部逻辑）**：主库等所有或多数节点确认后才提交，MySQL Group Replication（第 42 章）基于 Paxos 实现多数派确认，强一致但吞吐明显下降。

```sql
-- 主库安装并开启半同步（MySQL 8.0）
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = 1;
```

> 半同步的隐藏坑：**退化机制**。等待超时（默认 10 秒）后自动降级为异步复制，等从库恢复再升回来。降级期间主库不告警的话，「以为有半同步保护、实际在裸奔」是最常见的误判，生产必须监控降级状态。

**速记**：异步 **不等**、半同步 **等一个确认**、组复制 **多数派确认**，安全与延迟逐档上升。



### 复制的数据格式

#### 基于语句、基于行与混合

**binlog 格式**决定变更以什么形态传给从库，由 `binlog_format` 控制。

- **STATEMENT（SBR）**：记录原始 SQL 语句。日志量小，但 `NOW()`、`UUID()`、`LIMIT` 无排序等语句在主从可能产生不同结果。
- **ROW（RBR）**：记录每行数据的变更前后镜像。数据一致性最有保障，日志量大，是 **MySQL 5.7 起的默认值**。
- **MIXED**：默认用 STATEMENT，遇到不确定语句自动切换 ROW，兼顾两者但行为不够直观。

```sql
SHOW VARIABLES LIKE 'binlog_format';
-- 生产推荐显式 ROW，配合 binlog_row_image 控制镜像范围
```

> ROW 格式下一条 `UPDATE ... WHERE` 改一万行，binlog 就有一万行记录，批量作业的日志洪峰要纳入容量规划。判断格式不要背结论，用 `SHOW BINLOG EVENTS` 看一眼实际记录的形态最快。

**速记**：STATEMENT 记 **语句**、ROW 记 **行变化**，生产默认 **ROW**。



### 延迟与一致性

#### 主从延迟的成因与对策

**复制延迟（Replication Lag）**：从库回放进度落后主库的程度，用 `Seconds_Behind_Source`（旧名 `Seconds_Behind_Master`）观测。

- **单线程回放瓶颈**：主库多线程并发写入，旧版从库单线程串行回放，写高峰必然积压。MySQL 8.0 默认开启**基于写入集的并行回放**（`replica_parallel_workers`），先确认它已启用。
- **大事务**：一个几百万行的批量 UPDATE，主库执行多久、从库就回放多久，期间延迟持续累积。批量作业拆小是第一对策。
- **从库机器与负载弱于主库**：从库同时承担回放与读查询，资源被挤占。

```sql
SHOW REPLICA STATUS\G
-- 关注 Seconds_Behind_Source 与 Replica_SQL_Running_State
```

> 业务侧要接受一个事实：**异步复制下从库读到的是「几秒前的数据」**。「下单后立刻去从库查订单查不到」不是 bug，是架构语义。强制读主（关键路径读走主库）或半同步复制，是两条标准缓解路线，代价分别是一致性风险转移和写入延迟上升。

**速记**：延迟三因 **单线程回放、大事务、从库弱**，业务必须假设从库有滞后。

**警告内容**：主从复制**不是备份**。误删表的 DELETE 会原样重放到每一台从库，所有副本同时被删。防误删只能靠第 37 章的备份体系（全量＋binlog 恢复到误操作前一刻），复制副本救不了逻辑错误。
