## 索引性能分析：执行频次与 SHOW PROFILE

### 三层观测

#### 从宏观到微观

**性能分析有三层**：全局频次、单条耗时、单条执行计划。

- 第一层：`SHOW STATUS` 看各类语句执行了多少次，判断负载结构
- 第二层：慢查询日志与 `SHOW PROFILE` 看单条语句耗时分布
- 第三层：`EXPLAIN` 看优化器选了哪条路（30 篇）
- 顺序不能反：先知道「哪类语句多」，再谈「哪条语句慢」

> 直接上 EXPLAIN 是最常见的低效做法：一条不常执行的慢 SQL 优化了也没收益。先看频次分布，把优化力气花在高频语句上。

**速记**：**先频次后单条，先宏观后计划**。

#### 全局状态计数

**Com_ 系列计数器告诉你负载长什么样**：增删改查各多少次。

- `SHOW GLOBAL STATUS LIKE 'Com_______'`：七个下划线匹配 Com_select、Com_insert、Com_update、Com_delete 等
- `Com_select` 远高于写，说明是读密集，优先索引与缓存
- `Innodb_rows_read` 远高于返回行数，说明扫得太多
- 计数器是累计值，看增量要两次采样做差

```sql
SHOW GLOBAL STATUS LIKE 'Com_______';

SHOW GLOBAL STATUS LIKE 'Innodb_rows_%';
```

```text
Com_select      1842301
Com_insert         9821
Com_update        23110
Com_delete         1002
Innodb_rows_read  98213442   -- 读放大近百倍
```

> `Innodb_rows_read` 与业务返回行数的比值是最直接的「索引健康度」指标：比值几十上百，说明大量行被读出来又丢掉，索引或语句一定有得改。

**速记**：**Com_ 看结构，rows_read 看放大，累计值要采样做差**。

### 单条语句耗时

#### 慢查询日志

**慢查询日志是第二层的入口**：超过阈值的语句自动落盘。

- `slow_query_log=ON`、`long_query_time=0.5` 两个开关决定记录范围
- `log_queries_not_using_indexes=ON` 额外记未走索引的语句，小表也会刷屏
- `mysqldumpslow -s t -t 10` 按总耗时取前十条
- 日志字段含执行时间、锁定时间、扫描行数、返回行数

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;
SET GLOBAL log_queries_not_using_indexes = ON;
```

```bash
mysqldumpslow -s t -t 10 /var/lib/mysql/slow.log
```

> 阈值不是越低越好：0.1 秒阈值在 OLTP 库上一天能写出几个 GB。「频次乘总耗时」才是排序依据，单条慢但一天一次的不值得先动。

**速记**：**阈值定范围，dump 排序看总量，未走索引另开开关**。

#### SHOW PROFILES

**SHOW PROFILES 给的是耗时分解**：同一条语句各阶段花了多少。

- 会话级开关 `SET profiling = 1`，只影响当前连接
- `SHOW PROFILES` 列出近期语句的编号与总耗时
- `SHOW PROFILE FOR QUERY n` 看该语句各阶段耗时
- `SHOW PROFILE CPU, BLOCK IO FOR QUERY n` 加上 CPU 与磁盘 IO 维度
- **8.0 已标记弃用**，官方推荐改用 `performance_schema`

```sql
SET profiling = 1;

SELECT COUNT(*) FROM tb_order WHERE user_id = 10086;
SHOW PROFILES;

SHOW PROFILE CPU, BLOCK IO FOR QUERY 1;
```

```text
+----------+------------+
| Query_ID | Duration   |
+----------+------------+
|        1 | 0.00342100 |
+----------+------------+

+----------------------+----------+
| Status               | Duration |
+----------------------+----------+
| starting             | 0.000082 |
| checking permissions | 0.000012 |
| Opening tables       | 0.000031 |
| optimizing           | 0.000018 |
| executing            | 0.000094 |
| Sending data         | 0.002981 |   -- 大头在这里
| end                  | 0.000014 |
+----------------------+----------+
```

> `Sending data` 占比高不等于网络慢：这个阶段包含扫描行与组装结果集，绝大多数情况是扫描量太大。真正的网络耗时看客户端侧计时，不在服务端 profile 里。

**速记**：**会话级开关，看 Sending data 判扫描，8.0 已弃用改 P_S**。

#### performance_schema 替代方案

**8.0 的正解是按摘要聚合**：同结构 SQL 归并统计，比逐条 profile 更适合生产。

- `events_statements_summary_by_digest` 按 SQL 模板聚合，含次数、总延迟、扫描行
- 表默认有行数上限，历史会被淘汰，适合做短周期画像
- `sys.statement_analysis` 是它的可读视图，直接给排序结果
- 需要 `performance_schema=ON`，8.0 默认开启

```sql
SELECT DIGEST_TEXT, COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1e9, 2) AS total_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
  FROM performance_schema.events_statements_summary_by_digest
 ORDER BY SUM_TIMER_WAIT DESC
 LIMIT 10;

SELECT * FROM sys.statement_analysis LIMIT 10;
```

> 摘要表的 `SUM_ROWS_EXAMINED / SUM_ROWS_SENT` 就是读放大倍数，与慢日志互补：慢日志给单次现场，摘要给整体画像。两者一起看，优化目标才落得准。

**速记**：**摘要表按模板聚合，examined/sent 就是读放大**。

### SQL 提示

#### 三种索引提示

**优化器选错索引时，提示是应急手段**：不是常规优化。

- `USE INDEX (idx)`：建议用某索引，优化器可无视
- `FORCE INDEX (idx)`：强制用某索引，几乎不给优化器选择
- `IGNORE INDEX (idx)`：排除某索引，常用于避开选择度差的索引
- 语法位置在表名之后、WHERE 之前

```sql
SELECT * FROM tb_order USE INDEX (idx_user_created)
 WHERE user_id = 10086 ORDER BY created_at DESC;

SELECT * FROM tb_order FORCE INDEX (idx_user)
 WHERE user_id = 10086;

SELECT * FROM tb_order IGNORE INDEX (idx_status)
 WHERE status = 1 AND created_at > '2026-01-01';
```

> 提示是「优化器统计信息不准」的创可贴：根因往往是统计信息过期或数据分布突变。先 `ANALYZE TABLE` 更新统计，再考虑加提示，否则提示会随数据变化变成新的坑。

**速记**：**USE 建议、FORCE 强制、IGNORE 排除，先分析表再上提示**。

#### 优化器提示

**8.0 的 /*+ */ 写法比 INDEX 提示更细**：能指定表、索引、连接顺序。

- `/*+ INDEX(t idx) */` 指定表 t 用索引 idx
- `/*+ NO_INDEX(t idx) */` 排除索引
- `/*+ JOIN_ORDER(a, b) */` 指定连接顺序
- 提示必须紧跟在 SELECT、UPDATE、DELETE 关键字之后

```sql
SELECT /*+ INDEX(o idx_user_created) */
       o.order_no, o.amount
  FROM tb_order o
 WHERE o.user_id = 10086;
```

> 优化器提示的代价是可移植性：换数据库、换版本都可能失效且不报错。团队里要有约定——提示必须注释说明原因与失效条件，否则半年后没人敢删。

**速记**：**/*+ */ 更细，但绑定版本，必须写清原因**。

### 综合运用

#### 一条慢 SQL 的诊断路径

**六步走完，结论自然出来**：不要跳步。

- 第一步：慢日志或摘要表确认它值得优化（频次乘耗时）
- 第二步：`EXPLAIN` 看 type、key、rows、Extra
- 第三步：对比 `rows` 与实际返回行数，判断读放大
- 第四步：`SHOW PROFILE` 或 P_S 看耗时落在哪个阶段
- 第五步：判断是缺索引、索引失效、还是语句写法问题
- 第六步：改一处，重跑 EXPLAIN 与真实耗时，留档

```sql
EXPLAIN SELECT * FROM tb_order WHERE user_id = 10086 ORDER BY created_at DESC;
SHOW PROFILE CPU, BLOCK IO FOR QUERY 3;
```

> 六步里最容易跳过的是第六步的「留档」。没有改前改后的数据，优化就不可复现，下一次同类问题还要从头再来。

**速记**：**频次定性，EXPLAIN 定位，profile 定量，单变量验证**。
