## 子查询

### 子查询的形态

#### 什么是子查询

**子查询是嵌在另一条语句里的 SELECT**：外层用它的结果继续工作。

- 按返回结果分四类：标量（单值）、列（一列多行）、行（一行多列）、表（多行多列）
- 可出现的位置：SELECT、FROM、WHERE、HAVING
- 外层语句可以是 SELECT、INSERT、UPDATE、DELETE
- 相关子查询引用外层列，非相关子查询独立求值

> 子查询是“先算内层再用结果”的自然表达，但不是所有内层都能高效执行；复杂的子查询常常是 JOIN 改写的候选（本篇末节）。

**速记**：**内层先算外层用，标量列表行表四形态**。



#### 标量子查询

**标量子查询只返回一个值**：可以当普通值用在任何单值可用的地方。

- WHERE price 大于 (SELECT AVG(price) FROM products)
- SELECT 列表中逐行计算：相关标量子查询
- 返回多行时直接报错，类型约束是隐式保护
- 相关标量子查询逐行执行，外层行数多时性能急剧恶化

> 判断“高于平均”这类跨行比较，标量子查询是最自然的写法；但要警惕它出现在 SELECT 列表且外层是大表——每行一次查询等于亲手写了个循环。

**速记**：**一值入列，多行即炸，逐行相关是循环**。

```sql
SELECT name, price
FROM products
WHERE price > (SELECT AVG(price) FROM products);
```



#### 列、行与表子查询

**返回多列或多行的子查询各有所配**：形态决定可用的操作符。

- 列子查询配 IN、ANY、ALL 等集合操作符
- 行子查询：(a, b) = (SELECT x, y FROM ...) 一次比较多列
- 表子查询只能出现在 FROM 里，即派生表（22 篇）
- IN 加列子查询是“查属于某集合的行”的惯用式

> 行子查询的写法（元组比较）在 MySQL 支持良好但知晓率低，可以少写一条 OR 链；注意 NULL 参与元组比较时同样落进三值逻辑。

**速记**：**列配集合符，行做元组比，表进 FROM 当派生**。

```sql
SELECT * FROM orders
WHERE (user_id, amount) = (
    SELECT user_id, MAX(amount) FROM orders WHERE user_id = 42
);
```



### ANY、ALL 与 EXISTS

#### ANY 与 ALL

**ANY 与 ALL 把比较扩展到集合**：一个看“有没有”，一个看“是不是全都”。

- x 大于 ANY(子查询)：大于其中任意一个即可
- x 大于 ALL(子查询)：必须大于全部
- 等价改写：大于 ANY 即大于最小值，大于 ALL 即大于最大值
- = ANY 等价于 IN，不等于 ALL 等价于 NOT IN（同样有 NULL 陷阱）

> 集合为空时，ANY 条件恒假、ALL 条件恒真——这个反直觉行为常被忽略。写完 ANY/ALL 先想一下空集的语义是否符合预期。

**速记**：**ANY 够一个就行，ALL 得全胜，空集 ANY 假 ALL 真**。



#### EXISTS 与 NOT EXISTS

**EXISTS 问“有没有至少一行”**：找到一行即真，不再继续扫。

- 写法：WHERE EXISTS (SELECT 1 FROM b WHERE b.aid = a.id)
- 内层 SELECT 的列不重要，惯例写 1
- 相关子查询形态：外层驱动，内层走索引点查
- NOT EXISTS 是“反连接”的语义清晰版：找没有订单的用户

> NOT EXISTS 没有 NOT IN 的 NULL 灾难（子查询含 NULL 时 NOT IN 整体空结果），语义也更直白。工程上“不存在某关联”的需求默认选 NOT EXISTS。

**速记**：**EXISTS 找一行即停，NOT EXISTS 无 NULL 坑**。

```sql
SELECT u.id, u.name
FROM users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```



#### IN 与 EXISTS 的选择

**小表驱动大表的方向决定用 IN 还是 EXISTS**：两者可以互相改写。

- IN：内层结果先算出集合，外层逐行查集合，适合内层小
- EXISTS：外层驱动逐行探内层，适合外层小内层大
- 优化器会对 IN 做半连接（semijoin）改写，8.0 下很多场景差距已缩小
- 拿不准时两条都写，EXPLAIN 对比再定

> 经验法则在半连接优化后不再绝对；真正不过时的法则是：两边都给索引，让优化器有得选。

**速记**：**IN 备集合 EXISTS 逐行探，半连接时代先 EXPLAIN**。



### 相关子查询与物化

#### 相关子查询的执行模型

**相关子查询随外层每行执行一次**：本质是隐藏的嵌套循环。

- 内层引用外层列，无法独立求值
- 外层 N 行就是 N 次内层查询
- 内层条件必须走索引，否则是 N 次全表扫描
- 外层行数可控时可用；行数上万就该改写

> SELECT 列表里的相关标量子查询是逐行执行问题的重灾区（前文标量子查询小节已述），界面显示尚可，导出任务必炸。改写方向是 JOIN 或窗口函数，把 N 次查询合成一次集合操作。

**速记**：**相关子查询是循环，索引必配，行多必改**。

```sql
-- 每个用户最近一笔订单金额（相关标量子查询版，慢）
SELECT u.name,
       (SELECT MAX(o.amount) FROM orders o
        WHERE o.user_id = u.id) AS last_amount
FROM users u;
```



#### 物化与优化器改写

**优化器会把部分子查询物化或改写**：你写的是子查询，它跑的未必是。

- 物化：子查询结果存临时表，再与外层连接
- 半连接：IN 子查询被改写成半连接策略（多种实现）
- 派生表可被合并（merge）进外层，也可能保持物化
- EXPLAIN 的 select_type 显示 SUBQUERY、DERIVED、MATERIALIZED 等形态

> 判断“我写的子查询实际怎么执行”唯一可靠的方式是 EXPLAIN；优化器的改写策略随版本演进，十年前的口诀可能已经失效。

**速记**：**写了什么不算数，EXPLAIN 看它怎么跑**。



### 子查询与改写

#### 子查询改 JOIN

**能改写成 JOIN 的子查询通常更快**：集合运算变成一次连接。

- IN 加列子查询 改写为 JOIN 加 DISTINCT 或半连接语义
- 相关标量子查询改写为 JOIN 加 GROUP BY
- NOT IN 加子查询改写为 LEFT JOIN 加 IS NULL 或 NOT EXISTS
- 改写后必须核对行数：连接可能因一对多而放大行数

> 改写的动机是消除逐行执行与重复求值；但一对多连接会把外层行翻倍，通常需要再包一层 GROUP BY 或改用窗口函数，改写不是免费的。

**速记**：**改 JOIN 先看基数，防一对多翻行**。

```sql
-- 相关标量子查询改写为 JOIN + GROUP BY
SELECT u.name, MAX(o.amount) AS last_amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
```



#### 何时该用子查询

**子查询不是原罪，逐行执行才是**：按执行形态取舍。

- 标量、一次性集合、语义清晰的 NOT EXISTS：放心用
- SELECT 列表里的相关标量子查询：警惕，常需改写
- 大表上的 IN 大集合：确认走了半连接或改 JOIN
- 层级递归：直接用递归 CTE（22 篇），别堆子查询

> 写法服务于可读，性能由执行计划说话；先用最清晰的形态表达语义，再用 EXPLAIN 验证与改写，顺序不能反。

**速记**：**先写清楚，再 EXPLAIN，慢了才改**。
