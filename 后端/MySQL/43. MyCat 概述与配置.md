## MyCat 概述与配置

### 中间件定位

#### 分库分表之后的新问题

**拆完库表，应用要面对 N 个数据源**：MyCat 就是这层遮蔽物。

- 应用原本连一个 MySQL，拆完要连 N 个，路由、聚合、事务边界全落到业务代码里
- 中间件在应用与真实库之间伪装成「一个 MySQL」，由它解析 SQL 再转发到分片
- 好处是应用零改造，坏处是多一跳网络与一层不可控的 SQL 改写
- 这是**客户端分片**（ShardingSphere-JDBC）与**代理分片**（MyCat、ShardingSphere-Proxy）的分野

> 中间件不是免费的：它把「多数据源」的复杂度从应用搬到了运维。SQL 兼容性、跨片 join、分布式事务都成了新的坑，第 40 篇讲的跨片代价在中间件层并没有消失，只是换了个地方出现。

**速记**：**应用只见一个库，路由藏在中间件，复杂度从代码搬到运维**。

```text
应用 ──> MyCat(8066) ──┬──> db1 (dn1)
                       ├──> db2 (dn2)
                       └──> db3 (dn3)
```

#### MyCat 的核心概念

**五个概念撑起整套配置**：逻辑库、逻辑表、分片节点、分片规则、数据源。

- **逻辑库（schema）**：MyCat 对外暴露的库名，应用连的就是它
- **逻辑表（table）**：对外暴露的表名，与真实分片表可以同名也可以不同名
- **数据节点（dataNode）**：逻辑表与物理库的绑定关系，格式 `dn$hostname$database`
- **分片规则（rule）**：数据落到哪个节点的算法，含分片字段与算法实现
- **数据源（dataHost）**：真实的 MySQL 实例，读写分离配置也在这里

> 配置的阅读顺序是 schema → dataNode → dataHost，rule 挂在 table 上。看懂这四层嵌套，MyCat 的报错基本能自己定位——启动失败九成是 dataHost 连不上或 rule 找不到。

**速记**：**库表对应用，节点连物理，规则定归属，主机管连接**。

### 安装与启动

#### 安装前置条件

**MyCat 是 Java 程序**：跑起来只需要 JDK 与解压后的目录。

- 依赖 JDK 8 及以上，`java -version` 先确认
- 下载 `MyCat-server-1.6.7.4-release-*.tar.gz`，解压到 `/usr/local/mycat`
- 目录结构：`bin/` 启停脚本，`conf/` 全部配置，`lib/` 依赖包，`logs/` 日志
- 对外两个端口：**8066 数据端口**（应用连这个），**9066 管理端口**（运维连这个）

```bash
tar -zxvf MyCat-server-1.6.7.4-release-*.tar.gz -C /usr/local/
ls /usr/local/mycat/conf    # server.xml schema.xml rule.xml 及算法映射文件

/usr/local/mycat/bin/mycat start
/usr/local/mycat/bin/mycat status
tail -f /usr/local/mycat/logs/wrapper.log
```

> 启动失败先看 wrapper.log 而不是 mycat.log：JVM 起不来、端口被占、配置文件 XML 语法错误都记在这里。端口冲突是最常见的——上一个 mycat 没停干净，status 显示 not running 但 8066 仍被占。

**速记**：**JDK 加解压即装，8066 走数据，9066 走管理，起不来先看 wrapper**。

#### 三个配置文件的职责

**server.xml 管身份，schema.xml 管路由，rule.xml 管算法**：分工不重叠。

- `server.xml`：MyCat 自身的用户名密码、逻辑库名、防火墙与字符集
- `schema.xml`：逻辑表、数据节点、数据源的对应关系，读写分离也在这里
- `rule.xml`：分片函数的实现类与参数，被 schema.xml 的 table 标签引用

```xml
<!-- server.xml：定义一个逻辑库 TESTDB 与登录账号 -->
<user name="root" defaultAccount="true">
    <property name="password">123456</property>
    <property name="schemas">TESTDB</property>
</user>
```

> 三个文件里只有 server.xml 改错会直接起不来，另两个错了往往表现为「能连上但查不到数据」。排查顺序是：先确认 8066 能登、再 `show databases` 看逻辑库、最后查具体表的节点。

**速记**：**身份在 server，路由在 schema，算法在 rule**。

### 配置文件详解

#### server.xml

**server.xml 扮演 MySQL 的账号系统**：应用用它连 MyCat，不是连真实库。

- `system` 标签：全局参数，如 `charset`、`sequnceHandlerType`（全局序列方式，官方属性名就少一个 e，照写勿改）
- `user` 标签：MyCat 侧账号，`schemas` 决定该账号可见的逻辑库
- 一个 user 可挂多个 schema，用逗号分隔；只读账号用 `readOnly="true"`
- 真实库的账号密码不在这里，在 schema.xml 的 dataHost 里

```xml
<server>
    <system>
        <property name="charset">utf8mb4</property>
        <!-- 0=本地文件 1=数据库 2=时间戳 3=ZK -->
        <property name="sequnceHandlerType">2</property>
    </system>
    <user name="root" defaultAccount="true">
        <property name="password">123456</property>
        <property name="schemas">TESTDB</property>
    </user>
</server>
```

> MyCat 的账号是「接入层账号」，与 MySQL 的 `mysql.user` 毫无关系。应用迁移时改的只是连接串，库里的授权体系原封不动——这也是中间件方案迁移成本低的来源。

**速记**：**MyCat 自己有账号，schemas 划可见范围**。

#### schema.xml

**schema.xml 是全套配置的核心**：逻辑表到物理库的整条链路都在这里。

- `schema`：逻辑库，`checkSQLschema` 控制是否去掉 SQL 里的库名前缀
- `table`：逻辑表，`dataNode` 指定落点，`rule` 指定分片算法
- `dataNode`：`dn1` 这类名字加 `dataHost` 与真实库名，`database` 属性写物理库
- `dataHost`：真实实例的地址、账号、读写分离策略、连接池参数
- 不分片的表用 `dataNode="dn1"` 直连单节点，不必配 rule

```xml
<schema name="TESTDB" checkSQLschema="false" sqlMaxLimit="100">
    <table name="tb_user" dataNode="dn1,dn2" rule="mod-long"/>
    <table name="tb_dict" dataNode="dn1"/>
</schema>

<dataNode name="dn1" dataHost="host1" database="db1"/>
<dataNode name="dn2" dataHost="host1" database="db2"/>

<dataHost name="host1" maxCon="1000" minCon="10" balance="0"
          writeType="0" dbType="mysql" dbDriver="native" switchType="1">
    <heartbeat>select user()</heartbeat>
    <writeHost host="hostM1" url="192.168.1.10:3306" user="root" password="123456"/>
</dataHost>
```

> `sqlMaxLimit="100"` 是 MyCat 的隐性保护：不带 limit 的查询会被自动加 100 条上限。做数据核对或报表时忘了这一点，会得到「数据莫名变少」的假象，排查半天。

**速记**：**schema 挂表，表挂节点，节点挂主机，主机连真库**。

#### rule.xml

**rule.xml 把算法与参数解耦**：同一算法可以用不同参数实例化多次。

- `tableRule`：规则名 + 分片列 `columns` + 算法名 `algorithm`
- `function`：算法实现类 `class` 与参数 `property`
- 同一张表可引用多条规则，`columns` 写多列即复合分片
- 算法类名写全限定名，参数名大小写敏感

```xml
<tableRule name="mod-long">
    <rule>
        <columns>user_id</columns>
        <algorithm>mod-long</algorithm>
    </rule>
</tableRule>

<function name="mod-long" class="io.mycat.route.function.PartitionByMod">
    <property name="count">2</property>
</function>
```

> 分片列一旦定下就极难改：改列等于全量重分布。上线前用真实数据量压一遍，确认分布均匀，比事后迁移便宜两个数量级。

**速记**：**规则名挂列，算法挂参数，同算法可实例化多份**。

### 入门验证

#### 建库建表与插入

**先在真实库建表，再让 MyCat 指过去**：MyCat 不负责建物理表。

- 在两个真实库各建同名表 `tb_user`，结构完全一致
- 启动 MyCat 后用 8066 连接，`show databases` 应看到 `TESTDB`
- 插入数据后到两个真实库分别查，验证路由是否按预期落点
- 跨片查询由 MyCat 汇总，`explain` 可看它下发的实际 SQL

```sql
-- 连 MyCat，不是连真实库
mysql -h127.0.0.1 -P8066 -uroot -p123456

SHOW DATABASES;
USE TESTDB;
INSERT INTO tb_user(id, name) VALUES (1, 'a'), (2, 'b'), (3, 'c');
SELECT * FROM tb_user;   -- 跨两片汇总
```

> 验证分片最直接的手段是绕过 MyCat 直连物理库看数据落在哪。只看 MyCat 的查询结果永远是对的——它会把所有片的结果合起来，错了也看不出来。

**速记**：**物理表先建好，8066 验逻辑库，直连物理库验落点**。

#### 常见启动与连接故障

**MyCat 的故障分层很清楚**：进程、配置、连接、SQL 四层依次排查。

- 进程层：`mycat status`、`ps -ef | grep mycat`、wrapper.log
- 配置层：XML 语法、dataHost 地址账号、rule 名称拼写
- 连接层：真实库是否允许该 IP 连接、`heartbeat` 语句能否执行
- SQL 层：`show @@datanode` 看节点状态，`show @@heartbeat` 看后端存活

```sql
-- 9066 管理端
mysql -h127.0.0.1 -P9066 -uroot -p123456
show @@datanode;
show @@heartbeat;
```

> 「能连上但查不出数据」八成是 dataHost 的 database 名写错或物理库没建表；「连不上 8066」八成是进程没起或防火墙。两类故障的排查入口完全不同，先分层再动手。

**速记**：**进程配置连接 SQL，四层依次过，管理端口看后端**。

### 综合运用

#### 配置落地检查清单

**上线前把十项过一遍**：MyCat 的坑集中在配置细节。

- 三份配置文件改完先 `xmllint --noout` 验语法
- 真实库的库名、表名、结构三者一致，字符集一致
- 分片列在每张表都存在，且是查询的常用条件
- `sqlMaxLimit` 是否符合业务预期，报表类查询要显式带 limit
- dataHost 的连接数上限与真实库的 `max_connections` 匹配
- 全局序列方式确认（自增在分片下会冲突，必须换序列）
- 管理端 9066 只对内网开放，不暴露到公网

> 自增主键在分片下必然冲突，这是分库分表的第一课：要么用 MyCat 的全局序列，要么用雪花算法在应用层生成。第 40 篇讲的分布式 ID 在这里变成必须落地的配置项。

**速记**：**语法先验，三库同名，自增换序列，管理端口进内网**。
