## 存储引擎

### 可插拔架构

#### 引擎是什么

**存储引擎是数据的存取实现**：SQL 层不管数据怎么落地，引擎管。

- 第 5 篇的服务层负责解析、优化、执行，最后调引擎接口取数
- 引擎通过统一的 handler 接口接入，一个实例内不同表可用不同引擎
- 引擎决定：事务、锁粒度、索引结构、崩溃恢复、外键、压缩
- 5.5 起默认 InnoDB，8.0 的系统表也已改为 InnoDB

```sql
SHOW ENGINES\G
SHOW VARIABLES LIKE 'default_storage_engine';
```

> 「MySQL 支持事务」这句话不严谨：是「InnoDB 支持事务」。换成 MyISAM 的表，`BEGIN` 照样能执行，但没有任何回滚效果——这类静默失效比报错更危险。

**速记**：**服务层管 SQL，引擎管落地，能力随引擎变**。

#### 查看与切换

**引擎是表级属性**：建表指定，之后可改。

- 建表 `ENGINE=InnoDB`，不写则用 `default_storage_engine`
- `ALTER TABLE t ENGINE=MyISAM` 会重建表并搬数据，大表极慢且锁写
- `SHOW CREATE TABLE` 看当前引擎
- `information_schema.TABLES.ENGINE` 批量盘点

```sql
CREATE TABLE tb_log (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  msg VARCHAR(255),
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

ALTER TABLE tb_log ENGINE=MyISAM;   -- 重建表，慎用

SELECT TABLE_NAME, ENGINE FROM information_schema.TABLES
 WHERE TABLE_SCHEMA = 'shop';
```

> 换引擎不是改配置而是重建表：全表数据复制、索引重建、期间锁写。线上大表换引擎要走 gh-ost 或 pt-online-schema-change 这类工具。

**速记**：**建表定引擎，换引擎即重建，大表走在线工具**。

### InnoDB

#### 核心能力

**InnoDB 是默认且几乎唯一的选择**：事务、行锁、崩溃恢复齐备。

- 事务与 MVCC：支持四种隔离级别（31、33 篇）
- 行级锁：锁粒度细，并发写入能力远高于表锁（34 篇）
- 聚簇索引：数据按主键组织，主键查最快（27 篇）
- 崩溃恢复：redo log 保证已提交不丢（35 篇）
- 外键约束：唯一支持外键的常用引擎
- 独立表空间 `.ibd`：每表一个文件，支持在线收缩

```sql
SHOW VARIABLES LIKE 'innodb_file_per_table';   -- 默认 ON
```

> InnoDB 的代价是复杂度与空间：undo、redo、双写缓冲、聚簇索引的页分裂都要理解。但这些复杂度换来的是「出事能恢复」，对业务库没有替代品。

**速记**：**事务行锁聚簇树，崩溃能恢复，业务库唯一选**。

#### 适用与不适用

**InnoDB 不适合的场景其实很少**：

- 适合：一切需要事务、并发写、外键、崩溃安全的业务表
- 不适合：纯只读的超大历史表（可用列式或归档库）
- 不适合：全表扫描型统计（引擎层无列存优化）
- 仍需 InnoDB 的理由：即使只读，崩溃恢复与一致性依然重要

> 「读多写少所以用 MyISAM」是过时判断：MyISAM 的表锁会让并发的读与写互相阻塞，而 InnoDB 的 MVCC 读根本不加锁。只在极窄的只读归档场景才有讨论空间。

**速记**：**只读也别急着换，MVCC 读不加锁**。

### MyISAM

#### 结构与特征

**MyISAM 是前事务时代的引擎**：简单、快、但不安全。

- 三个文件：`.frm` 表结构（8.0 已并入数据字典）、`.MYD` 数据、`.MYI` 索引
- 表级锁：读锁共享、写锁独占，读写互斥
- 不支持事务、不支持外键、不支持崩溃安全恢复
- 索引与数据分离，非聚簇，二级索引直接存行地址
- 支持全文索引（5.6 之前是唯一选择）

```sql
CREATE TABLE tb_archive (
  id BIGINT UNSIGNED NOT NULL,
  content TEXT,
  PRIMARY KEY (id)
) ENGINE=MyISAM;
```

> 崩溃后的 MyISAM 表可能处于「可读但索引损坏」状态，必须 `CHECK TABLE` 与 `REPAIR TABLE`。没有 redo 的保护，异常断电就是数据风险。

**速记**：**三文件、表锁、无事务，崩溃要 repair**。

#### 剩余价值

**MyISAM 今天的合理用途只有两类**：

- 只读归档：历史数据写入一次、之后只查，且能接受表锁
- 计数型小表：`COUNT(*)` 在 MyISAM 上直接读元数据，O(1)
- 临时中间表：批处理时的落地表，用完即弃
- 除此之外一律 InnoDB

```sql
-- MyISAM 的 COUNT(*) 是常数时间，这是它唯一明显的性能优势
SELECT COUNT(*) FROM tb_archive;
```

> 为了 `COUNT(*)` 快而选 MyISAM，是把一张表的性能换成整库的风险：备份、复制、崩溃恢复都要单独考虑它。收益与代价完全不成比例。

**速记**：**只读归档与计数，其余不用**。

### Memory

#### 特征与限制

**Memory 引擎的表全在内存里**：快，但一重启就没了。

- 数据存内存，结构存磁盘，重启后表在数据空
- 默认 HASH 索引，等值查极快，范围查不走索引
- 表级锁，并发写能力有限
- 受 `max_heap_table_size` 限制，超限报错而非换页
- 不支持 BLOB、TEXT 列（可变长类型受限）

```sql
CREATE TABLE tb_session (
  sid VARCHAR(64) NOT NULL,
  uid BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (sid) USING HASH
) ENGINE=MEMORY;
```

> Memory 表在复制环境里是坑：主库重启丢数据，从库不会跟着丢，主从直接不一致。要用内存缓存，Redis 比 Memory 引擎合适得多。

**速记**：**全内存、HASH 默认、重启即空、复制会不一致**。

#### 内部临时表

**Memory 还有个隐形身份**：内部临时表的默认载体。

- `GROUP BY`、`DISTINCT`、派生表可能产生内部临时表（49 篇）
- 8.0 默认用 TempTable 引擎，超过阈值转磁盘
- `internal_tmp_mem_storage_engine` 可切回 MEMORY
- `Created_tmp_disk_tables` 增长说明内存临时表不够用

```sql
SHOW STATUS LIKE 'Created_tmp%';
SHOW VARIABLES LIKE 'internal_tmp_mem_storage_engine';
```

> 临时表落盘是分组查询变慢的常见原因，但调大 `tmp_table_size` 只是延后问题。根因通常是分组前没过滤，把百万行灌进了临时表。

**速记**：**临时表默认 TempTable，超限落盘，先减行再加内存**。

### 综合运用

#### 选型判据

**四问定引擎**：答完不用犹豫。

| 判据 | 是 | 否 |
|---|---|---|
| 需要事务与回滚 | InnoDB | 可考虑 MyISAM |
| 有并发写 | InnoDB | MyISAM 可接受 |
| 需要崩溃安全 | InnoDB | — |
| 数据可丢、要极快 | Memory（或 Redis） | InnoDB |

- 需要外键：只有 InnoDB
- 需要全文索引：InnoDB 5.6 起已支持，不必换引擎
- 需要列存分析：换引擎解决不了，换产品
- 犹豫时选 InnoDB：默认值的正确率在九成以上

> 引擎选型是少数「默认值就是最佳实践」的决策。真正需要讨论的是表设计与索引，而不是引擎——把精力放在后者，收益高一个数量级。

**速记**：**事务并发崩溃安全，三问全是要 InnoDB**。
