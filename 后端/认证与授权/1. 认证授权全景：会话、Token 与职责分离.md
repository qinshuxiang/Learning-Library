## 认证授权全景：会话、Token 与职责分离

### 认证与授权的边界

#### 两个词，两件事

**认证（Authentication）回答「你是谁」，授权（Authorization）回答「你能做什么」**——两者经常被缩写搞混（都是 Auth），职责必须分开设计。

- **认证**：验证身份，凭证是密码、验证码、证书、生物特征。输出是一个可信的身份标识。
- **授权**：基于已认证的身份判断权限，凭证是角色、策略、令牌中的权限声明。模型见第 4 章（RBAC/ABAC）。
- 顺序固定：**先认证、后授权**，没有身份谈不上权限；反过来，有身份不等于有权限。

> 把两件事揉在一起的系统（登录接口顺便返回「全部菜单权限」、改个角色要重新登录）迟早出问题。清晰的设计是：认证模块只管颁发与验证身份，授权模块只消费身份做判断，两者通过「身份标识」这一个接口对接。

**速记**：认证管 **身份**、授权管 **权限**，先认证后授权、接口只传身份。



### 会话与 Token

#### Session-Cookie 方案

**Session**：服务端存储登录状态，客户端只持有无意义的会话 ID（通常放 Cookie），每次请求带上 ID 服务端查状态。

- **流程**：登录成功 → 服务端生成 `sessionId` 存入存储（内存/Redis）→ `Set-Cookie` 下发 → 后续请求 Cookie 携带 → 服务端查 Session 得到身份。
- **Cookie 三属性是安全底线**：`HttpOnly`（JS 不可读，防 XSS 偷取）、`Secure`（仅 HTTPS 传输）、`SameSite=Lax`（缓解 CSRF，见浏览器主题的安全章节）。
- **优点**：服务端完全可控——随时注销、强制下线、查看在线列表。
- **代价**：状态在服务端，多实例部署需要共享存储（Redis 集中存 Session）；移动端与第三方接入不方便。

> Session 方案的「缺点」常被夸大。Redis 集中存储在多数项目里本来就有，「多一层依赖」的说法不成立；真正要权衡的是**可注销性（Session 强）与无状态扩展（Token 强）哪个对你的业务更重要**。

**速记**：Session＝**服务端存状态、Cookie 传 ID**，可控可注销，Cookie 三属性必配。



#### Token 方案与 JWT

**Token**：登录后服务端签发一个自包含的凭证（常见为 JWT，第 3 章深入），客户端存起来（内存/localStorage/Cookie），每次请求放入 `Authorization` 头，服务端**验签即可信任，无需查存储**。

- **无状态**：验证只需签名密钥，多实例、跨服务天然共享，这是它与 Session 的本质区别。
- **代价同样是状态问题**：签出去的 Token 在过期前**无法单方面作废**——「退出登录」「封号」只删客户端副本的话，Token 依然有效。解决方案（黑名单、短有效期＋Refresh Token 轮换）见第 3 章。
- **存放位置的取舍**：localStorage 读写方便但 XSS 可偷；放 `HttpOnly` Cookie 则 CSRF 回归、需要防重（SameSite＋CSRF Token）。

| 维度 | Session-Cookie | JWT Token |
|---|---|---|
| 状态存储 | 服务端（Redis） | 客户端自包含 |
| 注销/封号 | 即时生效 | 需黑名单或短有效期 |
| 多服务共享 | 需共享 Session 存储 | 验签即可，天然跨服务 |
| 移动端/开放 API | 不便 | 友好 |

> 选型口诀：**纯 Web 应用、需要强管控（后台管理），Session 够用且更安全；多端接入、微服务间调用，JWT 无状态的优势才真正兑现**。混合形态（Web 用 Session、移动端用 Token）在成熟系统里很常见，不必强求统一。

**速记**：JWT＝**验签即信、无需查库**，代价是作废难，短有效期＋轮换来补。



#### Refresh Token 与双凭证

**双 Token 结构**：短期 Access Token（分钟级）负责业务请求，长期 Refresh Token（天级）只负责换新 Access Token。

- Access Token 泄露的危害窗口被压到分钟级；Refresh Token 只在刷新接口出现、传输面更窄。
- **轮换（Rotation）**：每次刷新同时作废旧 Refresh Token、签发新的一对；检测到旧 Token 被第二次使用即判定泄露，吊销整个令牌族。
- 存储建议：Web 端 Refresh Token 优先 `HttpOnly` Cookie 限定刷新接口路径，Access Token 存内存。

> 双 Token 的本质是**把「长期有效」与「高频暴露」拆开**：暴露频繁的凭证活得很短，活得长的凭证很少露面。加上轮换，令牌体系才算有完整的泄露处置能力——只有一对永不过期的 Token 不是 Token 方案，是事故预案。

**速记**：Access **短命高频**、Refresh **长寿低频**，轮换＋复用检测是泄露兜底。

**警告内容**：任何 Token 方案上线前先回答「**这个 Token 怎么作废**」。答不出黑名单、轮换或超短有效期的具体参数，等于把封号、改密、踢下线这些基本管控全部放弃——这些功能的失效不会报错，只会在安全事件发生时才暴露。
