## OAuth 2.0

### OAuth 2.0 是什么

#### 授权框架的定位

**OAuth 2.0（RFC 6749）**：一个**授权**框架——让用户在不交出密码的前提下，授权第三方应用访问自己在某服务上的部分资源。

- 经典场景：「用微信登录某 App」，App 从未拿到你的微信密码，只拿到一份限定范围的授权。
- **四个角色**：资源所有者（用户）、客户端（第三方应用）、授权服务器（发令牌）、资源服务器（存数据、验令牌）。
- **关键认知**：OAuth 2.0 解决的是**授权委托**，不负责「证明你是谁」——「登录」场景实际是 OAuth 2.0＋OIDC 的组合（第 3 章），单用 OAuth 2.0 做登录是常见误用。

> OAuth 2.0 的价值在于**权限的最小化传递**：第三方只拿到指定范围（scope）、指定时效的访问能力，用户随时可撤销，密码全程不出门。理解了「委托」二字，四个角色与各种流程都是围绕它展开的细节。

**速记**：OAuth 2.0＝**授权委托框架**，管「同意」不管「证明」，登录场景需叠加 OIDC。



### 授权流程

#### 授权码模式（含 PKCE）

**授权码模式（Authorization Code）**：最完整、最安全的流程，第三方应用先换「授权码」，再在服务端用授权码＋密钥换令牌。

```text
1. 客户端把用户重定向到授权服务器，携带 client_id、redirect_uri、scope、state
2. 用户登录并同意授权
3. 授权服务器重定向回 redirect_uri，附带一次性 code
4. 客户端服务端用 code + client_secret 换取 access_token（用户无感知）
5. 客户端用 access_token 访问资源服务器
```

- **授权码中转的意义**：令牌交换发生在客户端**服务端**（HTTPS 直连授权服务器），令牌不经过浏览器前端，泄露面最小。
- **state 参数防 CSRF**：请求前生成随机值存会话，回调时校验一致，防止伪造的授权回调。
- **PKCE（RFC 7636）**：客户端无法保管 `client_secret` 时（SPA、移动端、CLI）的必配项——发起时携带 code 挑战的哈希，换令牌时验证原值，替代密钥防止授权码被截获冒用。

> 记住一条分界线：**有服务端的客户端用授权码＋密钥，没有服务端的用授权码＋PKCE**。两者都不用、把令牌直接经浏览器带回（隐式流程）的方案已被 OAuth 2.1 废弃，新项目一律不碰。

**速记**：授权码 **先换码、服务端再换令牌**，无后端加 **PKCE**，state 防 CSRF。



#### 客户端凭证模式与废弃流程

**Client Credentials**：无用户参与的机器对机器授权——服务自己用 `client_id`＋`client_secret` 直接向授权服务器要令牌，用于服务间调用。

- 没有用户、没有重定向，一次 POST 换令牌，是最简单的流程。
- 定时任务调内部 API、微服务间通信常用；令牌范围（scope）限定能访问的接口集合。

| 流程 | 用户参与 | 现状 | 用途 |
|---|---|---|---|
| 授权码（＋PKCE） | 有 | **推荐** | Web 应用、SPA、移动端 |
| 客户端凭证 | 无 | 推荐 | 服务间调用、后台任务 |
| 隐式（Implicit） | 有 | **废弃** | 历史 SPA，被授权码＋PKCE 取代 |
| 密码（Resource Owner Password） | 有 | **废弃** | 历史遗留，令牌经过客户端不可控 |

> 密码模式曾是「自研 App 快速接入」的偷懒选择，它的前提（客户端高度可信）在开放生态里不成立，OAuth 2.1 已明确移除。见到新项目还在用密码模式，直接按安全隐患处理。

**速记**：机器对机器用 **客户端凭证**，隐式与密码模式 **已废弃勿用**。

**警告内容**：OAuth 2.0 的 redirect_uri 校验不严是真实攻击面——**回调地址必须精确匹配**（协议、域名、路径全等，不允许通配子路径），否则授权码可被诱导重定向到攻击者站点。自建授权服务器时把 redirect_uri 白名单做成全等比较，是最廉价也最关键的一道防线。
