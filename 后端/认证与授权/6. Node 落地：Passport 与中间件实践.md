## Node 落地：Passport 与中间件实践

### 两套技术栈的选择

#### Session 栈与 JWT 栈的依赖清单

**技术栈选型先定存储与传递方式**，框架只是实现载体。Node 生态两套栈的依赖都很薄。

- **Session 栈**：`express-session`＋`connect-redis`（Session 存 Redis），登录态即一个 `req.session`。
- **JWT 栈**：`jsonwebtoken`（签发与验证）＋ 自写一个 `requireAuth` 中间件；OIDC 对接用 `openid-client`。
- **Passport**（`passport`＋策略包）：统一「认证方式」的插件框架——本地密码、微信、GitHub OIDC 各是一个 strategy，换登录方式不动业务代码。它与两套栈都兼容，多登录方式的项目建议引入。

> 判断依据回到第 1 章：**纯 Web 后台选 Session 栈，多端或跨服务选 JWT 栈**。选定后中间件结构完全一致——`authenticate`（认证）与 `authorize`（授权）两个中间件串在路由上，职责分明。

**速记**：Session 栈 `express-session`＋Redis，JWT 栈 `jsonwebtoken`，多登录方式加 **Passport**。



### 核心代码结构

#### 认证与授权中间件

**两个中间件各司其职**：`authenticate` 确认「请求来自已登录用户」并挂上身份，`authorize` 确认「该身份有此权限」。

```js
const jwt = require("jsonwebtoken");

// 认证中间件：验签 + 声明校验，通过后挂载 req.user
function authenticate(req, res, next) {
  const token = (req.headers.authorization || "").replace("Bearer ", "");
  if (!token) return res.status(401).json({ error: "未登录" });
  try {
    req.user = jwt.verify(token, process.env.JWT_PUBLIC_KEY, {
      algorithms: ["RS256"],          // 算法白名单：防 alg=none 攻击（第 3 章）
      issuer: "auth.example.com",
    });
    next();
  } catch {
    res.status(401).json({ error: "凭证无效或已过期" });
  }
}

// 授权中间件工厂：按所需权限生成检查器（角色 → 权限的展开见第 4 章）
function authorize(permission) {
  return (req, res, next) => {
    const perms = rolesToPermissions(req.user.roles);  // 查缓存的角色-权限映射
    if (!perms.has(permission)) return res.status(403).json({ error: "无权限" });
    next();
  };
}

// 路由上的组合
router.delete("/orders/:id", authenticate, authorize("order:delete"), handler);
```

- 401 与 403 语义分开：**401 是「没认证」（去登录），403 是「认证了但没权限」（别试了）**，前端按此分流。
- 角色到权限的映射是高频读、低频写，放内存缓存（启动加载＋变更时刷新），不要每个请求查库。
- JWT 栈的 `algorithms` 白名单与 `issuer` 校验是硬性要求（第 3 章的教训落到代码就是这两行）。

> 中间件的价值在**强制路径**：所有敏感路由必须穿过 `authenticate`，漏挂一条路由就是一个未授权访问。收敛手段是用路由分组（`router.use(authenticate)`）统一挂载，而不是逐条手写——逐条写法漏挂只是时间问题。

**速记**：`authenticate` 管 **401**、`authorize` 管 **403**，路由分组统一挂载防漏配。



#### 登录接口的安全清单

**登录接口是全系统被攻击最多的入口**，以下清单每项都是实战教训的结晶。

- **密码存储**：`bcrypt`（或 `argon2`），成本因子 10 以上；**绝无明文与 MD5/SHA-1**（Node 主题第 20 章 crypto 的正确用法）。
- **登录限速**：按 IP＋账号双维度限速（如 5 次失败锁 15 分钟），防撞库；失败提示统一为「用户名或密码错误」，不泄露账号是否存在。
- **登录成功后**：轮换会话 ID（Session 栈重生成 `sessionId`，防会话固定）；JWT 栈正常签发（Refresh 轮换见第 1 章）。
- **多因素预留**：关键系统至少把短信/邮箱验证码的字段与流程位留出——事后补 MFA 的改造成本远高于预留。

> 撞库攻击的流量特征很朴素：同一 IP 或同一账号的高频失败。第 4 条限速规则加上统一的失败响应，就能挡掉绝大多数自动化攻击——**认证安全的一半在密码学，另一半在限速与监控**。

**速记**：bcrypt 存密、双维限速、统一报错、轮换会话 ID，四件套缺一不可。

**警告内容**：本篇所有代码示例的密钥（JWT 私钥、数据库口令）一律走环境变量或密钥管理服务，**严禁提交进仓库**——私钥入库的历史会永久保留，即使后续删除，任何拿到仓库历史的人仍可伪造全部用户令牌。泄露处置只有一条：立即更换密钥（第 3 章版本号机制保证全量旧令牌作废）。
