## Dockerfile 语法详解

### Dockerfile 的定位与构建上下文

#### Dockerfile 是什么

**Dockerfile**：一个由**按顺序排列的指令**组成的纯文本文件，声明如何从基础镜像出发、逐层叠加生成一个新镜像，是构建过程的唯一输入脚本。

- 它描述**最终镜像的状态**而非操作环境的差异：写一条 COPY 就得到文件，写一条 RUN 就得到命令执行后的文件系统变更。
- 每条指令在构建时产生一个**新镜像层**，层与层按书写顺序依次叠加，最终合成完整镜像。
- 默认文件名即 Dockerfile，位于构建上下文根目录，可用 -f 指定其他路径。
- 构建命令 docker build 把 Dockerfile 与上下文一同交给构建器，由构建器逐条解释执行。

> Dockerfile 是**声明式**的：只读文件即可推断出镜像内容，不必依赖某台机器的当前状态，这是它与一段安装脚本最本质的区别。指令名大小写不敏感，但约定全大写以便与参数区分。

**速记**：Dockerfile 是**描述镜像最终状态的有序指令清单**，每条指令叠一层。



#### 构建上下文与 docker build

**构建上下文（build context）**：执行 docker build 时**整体发送给构建器的那一个目录**，是 COPY 与 ADD 唯一能取到文件的地方。

- 命令末尾的点号即上下文路径，docker build -t app:1.0 . 表示以当前目录为上下文。
- 上下文在构建开始时整体打包上传，文件越多越大，传输与解析越慢。
- COPY 的源路径只能取自上下文内部，不能写上下文之外的绝对路径。
- 构建器默认在上下文根目录查找名为 Dockerfile 的文件，-f 可指向别处但上下文本身不变。

> 上下文是 COPY 的取材范围，与 Dockerfile 存放位置无关：即使 Dockerfile 在别处，能用到的文件仍只有上下文里的那些。

**速记**：**上下文就是 COPY 的取材范围**，点号圈定，整体上传。



#### 文件变更为何让后续层缓存失效

**因果链**：构建器逐层复用缓存，一旦某条指令的输入变了，该层及其**之后所有层**都必须重算，这就是源码改动会拖慢构建的原因。

- COPY 的文件内容或元数据变化，会让该 COPY 层失效，其后的 RUN 依赖安装等全部重做。
- 因此固定顺序是先 COPY 依赖清单、装依赖、再 COPY 源码，让改动源码不影响依赖层。
- 一次 COPY 整个目录，等于把全部源码绑在一层，任何文件变动都击穿后续缓存。
- 缓存判定规则详见后文构建缓存一节，层与存储驱动的原理见第 4 章。

> 缓存链是严格的顺序依赖：改动靠前的指令代价最大，改动靠后的指令只影响其后。把易变内容放到最后，是控制构建速度的核心手法。

**速记**：**输入变则本层及其后全废**，易变内容放最后。



#### .dockerignore 的作用与写法

**.dockerignore**：置于上下文根目录的排除清单，在打包上传前剔除指定文件与目录，既缩小上下文又避免无关文件进入镜像。

- 语法与 .gitignore 类似，一行一条匹配模式，支持星号通配与叹号取反。
- 排除在上传阶段就生效，被排除的文件对 COPY 与 ADD 不可见。
- 典型排除项为版本库目录、依赖目录、构建产物、日志与本地凭证文件。
- 不存在该文件时，上下文原样上传，容易把大文件与密钥一并送进构建器。

```text
# .dockerignore 示例
.git
node_modules
dist
*.log
.env
```

> 排除规则同样会影响 COPY 的匹配：若目标文件被命中，COPY 会直接失败或复制不到内容，排查时先核对排除清单。

**速记**：**.dockerignore 在上传前过滤上下文**，缩小体积、挡住敏感文件。



### 指令逐条详解

#### 指令的通用书写规则

**通用书写规则**：一条指令由**指令名**与若干**参数**组成，两者以空白分隔，指令名约定全大写；井号起始的行为注释，构建前被整体移除。

- 每条指令独占一行，过长时用反斜杠续接下一行，反斜杠是唯一续行符。
- 注释不支持反斜杠续行，且注释不进入任何层、不影响缓存。
- 环境变量替换写 $变量名 或 ${变量名}，并支持 ${VAR:-默认值} 一类的默认值修饰符。
- 指令集合是固定的，拼错指令名会导致构建直接报错。

> 官方签名用方括号表示可选参数、尖括号表示占位符，本系列为可读性把占位符写成不带尖括号的普通文字，只保留参数格式本身。

**速记**：一行一指令，**全大写、空白分隔、反斜杠续行、井号注释**。



#### FROM

**FROM**：指定**基础镜像**并开启一个新的构建阶段，是除 ARG 外唯一允许出现在文件首部的指令。

```dockerfile
FROM [--platform=<platform>] <image>[:<tag>] [AS <name>]
FROM [--platform=<platform>] <image>[@<digest>] [AS <name>]
```

- 省略标签时默认 latest，属浮动版本，不推荐。
- AS name 给阶段命名，供后续 FROM name 与 COPY --from=name 引用。
- --platform 指定基础镜像的目标平台，如 linux/amd64、linux/arm64。
- 用 name@sha256 形式的 digest 可把基础镜像固定到不可变的精确版本。

> 一个 Dockerfile 里可以有多个 FROM，每个开启一个独立阶段，阶段之间默认互不相通，需要显式引用才能取到彼此的文件。

**速记**：FROM 打底、可命名 AS、可 --platform、可 @digest 锁死。



#### RUN

**RUN**：在**构建期**执行命令并把结果写进镜像层，是安装依赖、编译代码、修改配置的主要手段。

```dockerfile
RUN <command>                      # shell 形式
RUN ["executable", "param1"]       # exec 形式
RUN --mount=type=cache,target=/root/.npm npm ci
```

- shell 形式经过默认 shell 执行，支持变量展开、管道与逻辑与。
- exec 形式不经过 shell，按 JSON 数组直接启动进程，变量不展开。
- 可用选项含 --mount、--network、--security、--device，均属 BuildKit 前端能力。
- 每条 RUN 生成一层，命令中产生的临时文件若不在同一层清理会永久留在镜像里。

> RUN 的缓存不会因远端内容更新而自动失效：软件源换了版本，只要指令文本没变仍会命中旧结果，必要时用 --no-cache 强制重建。

**速记**：RUN 管**构建期执行并落层**，shell 与 exec 两种形式。



#### CMD

**CMD**：声明容器**启动时的默认命令**，构建期不执行任何内容，且很容易被 docker run 后跟的参数整体覆盖。

```dockerfile
CMD ["executable","param1","param2"]   # exec 形式，推荐
CMD ["param1","param2"]                # 仅作 ENTRYPOINT 的默认参数
CMD command param1 param2              # shell 形式
```

- 一个 Dockerfile 中写多条 CMD 时只有最后一条生效。
- exec 形式让进程直接作为 PID 1 接收信号，shell 形式会额外套一层 shell。
- 只写参数的形式必须与 ENTRYPOINT 搭配才有意义，单独写会被当成可执行文件。

> CMD 是默认值而非保证：只要 docker run 镜像后面带了命令，CMD 就被完全替换，需要不可覆盖的入口应改用 ENTRYPOINT。

**速记**：CMD 是**可被覆盖的默认命令**，构建期不执行。



#### ENTRYPOINT

**ENTRYPOINT**：声明容器**固定的入口可执行文件**，docker run 后跟的内容默认作为它的参数追加，而不是替换它。

```dockerfile
ENTRYPOINT ["executable", "param1", "param2"]   # exec 形式，推荐
ENTRYPOINT command param1 param2                 # shell 形式
```

- 要覆盖必须显式写 docker run --entrypoint，代价较高，故适合放不轻易变的入口。
- exec 形式保证信号直达主进程，shell 形式会另外起一个 shell。
- 与 CMD 同时存在时，CMD 的值作为 ENTRYPOINT 的默认参数。

> shell 形式的 ENTRYPOINT 会忽略 CMD 参数，因为 CMD 被当作命令后缀拼接，行为不直观，通常应避免。

**速记**：ENTRYPOINT 是**不可轻易覆盖的入口**，CMD 用来补参数。



#### LABEL

**LABEL**：给镜像附加**键值对形式的元数据**，不改变文件系统内容，可用 docker inspect 查询。

```dockerfile
LABEL org.opencontainers.image.authors="team@example.com"
LABEL version="1.0" description="demo api"
```

- 键推荐用反向域名前缀，避免与他人定义的键冲突。
- 一条 LABEL 可写多组键值对，也可分行书写，重复键以最后一次为准。
- 现代标准是 OCI 规定的 org.opencontainers.image 系列注解。
- MAINTAINER 已弃用，作者信息应改用 LABEL 表达。

> LABEL 只影响镜像元数据，不产生任何可执行行为，也不会改变运行中的容器，纯粹用于标识与检索。

**速记**：LABEL 是**镜像的元数据标签**，反向域名做键。



#### ENV

**ENV**：在镜像里**持久设置环境变量**，构建期的后续指令与容器运行时的进程都能读到。

```dockerfile
ENV NODE_ENV=production
ENV APP_HOME=/app PORT=3000
```

- 推荐 ENV 键=值 写法，可一次写多组；旧写法 ENV 键 值 已不推荐。
- 赋值后对后续 RUN、CMD、ENTRYPOINT 以及容器启动的进程全部可见。
- 值会固化进镜像配置，docker inspect 与容器内的 env 都能看到。

> ENV 会写进镜像并延续到运行期，因此不能承载密钥；只需构建期临时值时应改用 ARG。

**速记**：ENV **构建期赋值、运行期可见**，永久写进镜像。



#### ARG

**ARG**：定义**仅构建期有效**的变量，可由 docker build --build-arg 传值，默认不进入容器运行环境。

```dockerfile
ARG NODE_VERSION=24
ARG GIT_SHA
RUN echo "building ${GIT_SHA}"
```

- 默认值可写在 ARG 里，命令行 --build-arg 只覆盖本次构建取值，不改动文件内容。
- 作用域从声明处到当前阶段结束，并自动被其子阶段继承。
- 未声明默认值又未传值时，变量为空字符串。
- 存在一批约定俗成的预定义 ARG，如代理参数与平台参数。

> ARG 可以写在 FROM 之前用于参数化基础镜像标签，但进入阶段后要再次写一条同名 ARG 才能真正读到值。

**速记**：ARG 是**构建期变量**，--build-arg 传值，运行期不可见。



#### WORKDIR

**WORKDIR**：设置后续指令与容器启动时的**工作目录**，目录不存在会自动创建。

```dockerfile
WORKDIR /app
COPY package*.json ./
RUN npm ci
```

- 相对路径基于上一条 WORKDIR 叠加，WORKDIR /a 后再写 WORKDIR b 得到 /a/b。
- 影响 RUN 的执行目录、COPY 的相对目标以及 CMD 与 ENTRYPOINT 进程的起始目录。
- 可多次设置，每一步都改变其后指令的基准目录。

> 不要用 RUN cd /app 代替 WORKDIR：cd 只在那一条 RUN 内有效，下一条指令又回到原目录。

**速记**：WORKDIR 定**工作目录并自动建目录**，相对路径逐次叠加。



#### COPY

**COPY**：把**构建上下文或指定阶段中的文件**复制进镜像，是往镜像里放源码与配置的标准手段。

```dockerfile
COPY <src> ... <dest>
COPY --from=build /app/dist /usr/share/nginx/html
COPY --chown=node:node package*.json ./
```

- 源路径相对上下文根，可用通配符匹配多个源，目标以斜杠结尾表示目录。
- --from 从其他构建阶段或镜像取文件，是多阶段协作的关键。
- --chown 直接设置属主属组，省去复制后再 RUN chown 多出一层。
- --link 以独立层方式复制以提升缓存复用，属 BuildKit 前端能力。
- COPY 只复制内容与权限，不会展开压缩包。

> 源文件必须在上下文或指定阶段内；源内容变化会让该层及其后所有层缓存失效，这也是先复制清单后复制源码的原因。

**速记**：COPY 从**上下文或指定阶段**复制，默认不展开压缩包。



#### ADD

**ADD**：功能上是 COPY 的超集，额外支持**自动解压本地 tar 归档**与**从 URL 下载**，多数场景应优先用 COPY。

```dockerfile
ADD app.tar.gz /opt/
ADD https://example.com/file.txt /tmp/file.txt
```

- 源是本地归档（tar、tar.gz、tgz、bz2、xz）时自动解压到目标目录。
- 源是 URL 时直接下载，但不解压，且落地权限固定为 600。
- 不支持 --from，无法从其他构建阶段取文件。

> 隐式解压与隐式下载让行为不透明，官方建议只在确实需要解压本地 tar 时用 ADD，其余一律 COPY。

**速记**：ADD 等于 **COPY 加自动解压与 URL 下载**，能不用就不用。



#### EXPOSE

**EXPOSE**：声明容器**打算监听的端口与协议**，属文档性约定，本身不发布端口也不改动防火墙。

```dockerfile
EXPOSE 3000
EXPOSE 80/tcp 53/udp
```

- 协议省略时默认 tcp，可显式写 /tcp 或 /udp。
- 要真正对外可访问，仍需 docker run -p 或 Compose 的 ports 映射。
- 在同一自定义网络内，其他容器可直接按容器名加端口互访，无需发布。

> EXPOSE 不产生任何访问能力，只把端口写进镜像元数据，不要把它当成端口映射使用。

**速记**：EXPOSE **只声明不发布**，真正映射靠 -p。



#### VOLUME

**VOLUME**：声明一个**匿名数据卷挂载点**，使该路径的数据不写进镜像层，并在容器删除时按卷策略保留。

```dockerfile
VOLUME ["/var/lib/mysql"]
VOLUME /data
```

- exec 形式与 shell 形式都可用，exec 形式更明确。
- 声明后该路径在运行时自动挂载匿名卷，数据落到卷而非容器可写层。
- 在 Dockerfile 中声明 VOLUME 后，后续 RUN 对该目录的修改在运行时不保留，属易踩的坑。

> 数据库类镜像常用 VOLUME 保护数据目录；应用镜像更常见的是运行时用 -v 挂载，而非在 Dockerfile 里写 VOLUME。

**速记**：VOLUME 声明**匿名卷挂载点**，数据不落镜像层。



#### USER

**USER**：指定后续 RUN、CMD、ENTRYPOINT **以哪个用户身份执行**，是降低容器权限的常用手段。

```dockerfile
USER node
USER 1000:1000
```

- 可写用户名或 UID，也可带冒号加属组指定属组。
- 只影响其后的指令，理论上可再切回 root，但不应这么做。
- 以非 root 身份运行时，需要写入的目录要提前用 COPY --chown 或 RUN chown 授权。

> 默认身份是 root；不少基础镜像已内置可用的非特权用户，优先复用比自己创建更稳妥，也符合编排平台的强制要求。

**速记**：USER 定**执行身份**，默认 root，生产应降权。



#### HEALTHCHECK

**HEALTHCHECK**：定义**容器健康检查命令**，让 Docker 按固定间隔执行并记录状态，供编排器判断容器是否可用。

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1
HEALTHCHECK NONE
```

- --interval 检查间隔，默认 30s；--timeout 单次执行超时，默认 30s。
- --start-period 启动宽限期，期内失败不计入重试，默认 0s；--start-interval 宽限期内的检查间隔，默认 5s。
- --retries 连续失败多少次判为不健康，默认 3。
- NONE 用于关闭从基础镜像继承来的健康检查。

> 检查命令退出码 0 表示健康、1 表示不健康，状态显示在 docker ps 的 STATUS 列。基础镜像若不含探活工具，需自行准备。

**速记**：HEALTHCHECK **周期执行判健康**，参数为 interval、timeout、start-period、retries。



#### SHELL

**SHELL**：覆盖后续 shell 形式指令（RUN、CMD、ENTRYPOINT）**默认使用的 shell**。

```dockerfile
SHELL ["/bin/bash", "-c"]
RUN echo hello && echo world
```

- Linux 默认是 /bin/sh -c，Windows 默认为 cmd。
- 仅影响 shell 形式的 RUN、CMD、ENTRYPOINT，对 exec 形式无效。
- 常见用途是启用 bash 专有特性（如 pipefail）或换用 PowerShell。

> SHELL 是镜像级设置，中途再写一次会改变其后所有 shell 形式指令的解释方式，切换后应保持前后一致。

**速记**：SHELL **换默认 shell**，只作用于 shell 形式指令。



#### STOPSIGNAL

**STOPSIGNAL**：设置向容器主进程发送的**停止信号**，docker stop 与编排器据此优雅终止进程。

```dockerfile
STOPSIGNAL SIGTERM
STOPSIGNAL SIGQUIT
```

- 默认信号为 SIGTERM，写信号名或数字均可。
- 应用若需在退出前收尾（关连接、落盘），应监听该信号做优雅关闭。
- 它只改镜像配置，不改变应用本身如何处理信号。

> 若主进程不是 PID 1 或不监听该信号，会等到超时后被 SIGKILL 强杀，因此让应用主进程直接做 PID 1 是常见做法。

**速记**：STOPSIGNAL **定停止信号**，默认 SIGTERM，配合优雅退出。



#### ONBUILD

**ONBUILD**：注册一条**延迟触发器**，在当前镜像被当作其他 Dockerfile 的基础镜像时自动执行所登记的指令。

```dockerfile
ONBUILD COPY . /app/src
ONBUILD RUN npm install
```

- 触发器只在下游构建时执行，不影响当前镜像自身的构建。
- 登记内容会记入镜像元数据，可用 docker inspect 查看。
- 可登记多数指令，但不能登记 FROM 与 MAINTAINER，也不能嵌套 ONBUILD。

> ONBUILD 会把隐式行为带给下游、增加排查难度，现代实践中已较少使用，多数场景应由下游显式书写指令。

**速记**：ONBUILD **给下游埋触发器**，下游构建时自动执行。



### RUN、CMD、ENTRYPOINT 的分工

#### 执行时机与覆盖规则

**三者分工**：RUN 在**构建期**执行并写进镜像层；CMD 与 ENTRYPOINT 只在**容器启动时**决定运行什么进程，构建期不执行。

- RUN：构建时运行，结果固化为层，运行容器时不会再次执行。
- CMD：只提供默认命令，docker run 镜像 后跟的内容会整体覆盖它。
- ENTRYPOINT：提供固定入口，docker run 后跟的内容作为附加参数，覆盖需 --entrypoint。
- 三者可同时存在：RUN 造镜像，ENTRYPOINT 定入口，CMD 供默认参数。

> 一句话概括：**RUN 是构建动作，CMD 是可改的默认，ENTRYPOINT 是不轻易改的入口**。

**速记**：RUN **构建期执行落层**；CMD 可被覆盖；ENTRYPOINT 不可轻易覆盖。



#### shell 形式与 exec 形式的差别

**两种形式**：exec 形式用 JSON 数组直接启动进程，**不经过 shell**；shell 形式是一整条字符串，交给 **/bin/sh -c** 执行。

- 变量展开：shell 形式会展开 $VAR；exec 形式不展开，需自行把值传给可执行文件。
- 信号传递：exec 形式的主进程即 PID 1，信号直达；shell 形式外面多一层 shell，信号可能被吞掉。
- shell 特性：管道、逻辑与、通配符只有 shell 形式可用。
- JSON 数组必须用双引号，单引号不合法。

```dockerfile
RUN ["node", "server.js"]        # exec：信号直达，变量不展开
RUN node server.js               # shell：经 /bin/sh -c，可写管道与变量
```

> 需要 shell 特性时用 shell 形式，需要正确收发信号与退出码时用 exec 形式；CMD 与 ENTRYPOINT 强烈推荐 exec 形式。

**速记**：exec **不过 shell、信号直达**；shell **过 /bin/sh -c、可管道可变量**。



#### CMD 与 ENTRYPOINT 的拼接规则

**拼接规则**：当 ENTRYPOINT 用 exec 形式时，CMD 的内容作为参数**追加**到 ENTRYPOINT 之后；当 ENTRYPOINT 用 shell 形式时，CMD 被**忽略**。

- 无 ENTRYPOINT、只有 CMD：CMD 即最终命令。
- ENTRYPOINT exec 形式 + CMD exec 形式：最终命令为 ENTRYPOINT 参数加 CMD 参数。
- ENTRYPOINT exec 形式 + CMD shell 形式：CMD 整串被当作参数追加。
- ENTRYPOINT shell 形式：CMD 完全不生效。
- 只有 ENTRYPOINT 没有 CMD：只运行 ENTRYPOINT 本身。

```text
无 CMD                + ENTRYPOINT exec  → 只跑 ENTRYPOINT
CMD ["c","p"]         + ENTRYPOINT exec  → ENTRYPOINT c p
CMD exec 形式         + 无 ENTRYPOINT    → 只跑 CMD
CMD shell 形式        + ENTRYPOINT shell → 只跑 ENTRYPOINT（CMD 丢弃）
```

> 若只用 CMD 而不写 ENTRYPOINT，镜像使用者一条 docker run 参数就能把它整个换掉，不适合需要固定入口的发布镜像。

**速记**：ENTRYPOINT exec **拼 CMD 作参数**；ENTRYPOINT shell **吞掉 CMD**。



#### 用 ENTRYPOINT 加 CMD 传默认参数

**惯用法**：把**固定入口**写进 ENTRYPOINT，把**常用默认参数**写进 CMD，使用者只需替换参数即可改变行为。

```dockerfile
ENTRYPOINT ["/usr/bin/myapp"]
CMD ["--port", "3000", "--verbose"]

# docker run myapp                       → myapp --port 3000 --verbose
# docker run myapp --port 8080           → myapp --port 8080
# docker run --entrypoint /bin/sh myapp  → 直接进 shell 调试
```

- ENTRYPOINT 用 exec 形式，保证信号交给应用主进程。
- CMD 只列参数、不含可执行文件，语义清晰。
- 需要进入容器排查时，用 --entrypoint 临时覆盖为 shell。

> 入口脚本若要做初始化（等数据库、跑迁移），应在收尾时用 exec "$@" 把参数原样交给真正的进程，才能保持信号与退出码正确。

**速记**：**ENTRYPOINT 定入口、CMD 给默认参数**，exec 形式加 exec "$@" 保信号。



### 构建缓存与失效判定

#### 缓存如何形成与命中

**构建缓存**：构建器对每条指令的结果做缓存，重新构建时若**指令文本与输入都没变**，就直接复用上次结果、跳过执行。

- 缓存按指令逐个匹配：从基础镜像开始，逐层比对直到第一条不匹配的指令。
- 命中层被跳过执行，但仍参与后续指令的比对。
- 命中判断基于指令字符串、相关文件内容以及父层缓存标识。
- 缓存链是顺序依赖，前一条不命中，其后全部重算。

> 缓存的单位是指令层而非整个镜像，因此把易变的内容尽量放在文件末尾，能最大化复用前面已命中的层。

**速记**：缓存**逐条顺序比对，前变则后全废**。



#### 总是导致失效的指令

**总会失效的指令**：大多数指令按自身输入判定，而 RUN 只要指令文本不变就命中，**不感知外部变化**，需手动干预才能失效。

- RUN：指令文本不变即命中，即使它下载的内容已更新也不重新执行。
- COPY 与 ADD：文件内容或元数据（属主、权限）变化即失效。
- ARG：构建参数取值变化会让引用了它的指令及其后失效。
- ENV、WORKDIR、USER、EXPOSE 等：取值或书写位置变化即视为不同指令。
- ADD 从 URL 拉取时不校验远端内容，缓存命中就复用旧文件。

> 最典型的坑是包管理器：缓存命中时不会重新拉取索引，可能拿到过期或已下架的版本，必要时用 --no-cache 全量重建。

**速记**：**RUN 文本不变即命中、COPY 随文件变、ARG 随参数变**。



#### COPY 与 ADD 的校验和判定

**校验和判定**：构建器对 COPY 与 ADD 的**每个源文件的内容与元数据做摘要**，摘要变化即缓存失效。

- 内容变化、修改时间变化、权限位变化都可能改变摘要。
- 旧构建器只看修改时间，BuildKit 改看内容与元数据，判定更准确。
- 增删文件同样改变摘要，哪怕目标内容看起来没变。
- 因此先复制依赖清单、再装依赖、最后复制源码，是保住依赖缓存的固定顺序。

> 一次性 COPY 整个目录，会让任何源码改动都击穿依赖安装那一层；拆分 COPY 是让缓存生效的关键动作。

**速记**：COPY 与 ADD 按**文件内容与元数据摘要**判缓存，源变则失效。



#### --no-cache、--pull 与 --cache-from

**三个构建开关**：--no-cache **禁用本地缓存**强制全部重算；--pull **强制重新拉取基础镜像**；--cache-from **指定可作为缓存来源的镜像**。

```bash
docker build --no-cache -t app:1.0 .
docker build --pull -t app:1.0 .
docker build --cache-from=app:1.0 -t app:1.0 .
```

- --no-cache 用于确认缓存是否掩盖了问题，代价是每次全量构建。
- --pull 保证基础镜像不为旧的本地副本，适合在 CI 中定期刷新。
- --cache-from 让 CI 复用远程镜像里已有的层缓存。

> 跨机器复用缓存通常配合 Buildx 与 registry 缓存后端使用，--cache-from 只是取缓存的方式之一。

**速记**：**--no-cache 弃缓存、--pull 重拉底、--cache-from 借外部缓存**。



#### RUN 的缓存挂载

**缓存挂载**：RUN --mount=type=cache 把包管理器的缓存目录**挂载为可跨构建复用的缓存**，避免每次重建都重新下载依赖。

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=cache,target=/root/.npm npm ci
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
RUN --mount=type=cache,target=/var/cache/apt apt-get update && apt-get install -y curl
```

- target 指向包管理器的缓存目录，缓存内容不写进镜像层。
- 需要顶部语法指令或足够新的内置前端，属 BuildKit 前端能力。
- 与层缓存不同，这里缓存的是下载内容本身，命中与否不改层结果。
- 可用 sharing 参数控制并发访问，默认 shared，串行时可用 locked。

> 它解决的是依赖下载慢，不解决指令缓存失效；依赖清单变了仍要重新安装，只是下载过程可被加速。

**速记**：**RUN --mount=type=cache** 挂缓存目录加速 npm、pip、apt，不落层。



### 变量与作用域

#### ENV 与 ARG 的差别

**ENV 与 ARG**：ENV 是**运行期环境变量**，写进镜像并延续到容器；ARG 是**构建期变量**，只在该次构建内有效，默认不进运行环境。

- 可见范围：ENV 在构建期与运行期都可见；ARG 仅构建期可见。
- 持久性：ENV 固化进镜像配置；ARG 不进入容器环境。
- 覆盖方式：ENV 在运行期用 docker run -e 覆盖；ARG 在构建期用 --build-arg 传值。
- 命名冲突：同名时运行期以 ENV 为准。

> 需要运行期能读到就用 ENV，只在构建时拼路径选版本就用 ARG；两者可配合，用 ARG 传值、再用 ENV 落成运行期变量。

**速记**：**ENV 运行期可见且持久，ARG 构建期可见且临时**。



#### ARG 的作用域与 --build-arg

**ARG 作用域**：从声明处开始、到**当前构建阶段结束**为止，并自动被其子阶段继承；全局（FROM 之前）声明的 ARG 不自动进入任何阶段。

- 在阶段内声明一次，即可在整个阶段与其子阶段使用。
- FROM 之前声明的 ARG 只能用于 FROM 行本身，要在阶段内用得再写一次 ARG 名。
- --build-arg 名=值 可覆盖默认值；传了未声明的参数只会告警，不会报错。
- 未给默认值又未传值时，变量为空字符串。

> 一个高频易错点：写在 FROM 之前的 ARG 在 FROM 之后的阶段里默认取不到值，必须在该阶段内再写一条同名 ARG 才能消费。

**速记**：ARG **声明即生效至阶段末、子阶段继承**；全局 ARG 需在阶段内二次声明。



#### ARG 在 FROM 之前与之后的用法

**位置差异**：写在 FROM 之前用于**参数化基础镜像本身**（标签、平台），写在 FROM 之后用于**阶段内部的构建逻辑**。

```dockerfile
# syntax=docker/dockerfile:1
ARG NODE_VERSION=24
FROM node:${NODE_VERSION}-alpine AS base
ARG NODE_VERSION
RUN echo "node ${NODE_VERSION}"
```

- FROM 行里可直接引用全局 ARG，实现基础镜像版本可切换。
- 阶段内要再写一次 ARG 同名声明，才能读到同一个值。
- 预定义平台参数属全局作用域，进入阶段同样需要声明。

> 只想固定基础镜像时，直接写死标签或 digest 更简单；用 ARG 参数化的价值在于同一次构建可在多版本间切换，多用于 CI 矩阵。

**速记**：**FROM 前 ARG 参数化基础镜像，FROM 后 ARG 参数化构建逻辑**。



#### 密钥不得写进 ARG 或 ENV

**密钥禁令**：**ARG 与 ENV 都不适合承载密钥**，ARG 会残留在镜像历史与构建记录中，ENV 会持久存在于容器内，二者都可能泄露。

- ARG 取值会出现在 docker history 与构建记录中，明文可查。
- ENV 取值直接写进镜像配置，能 docker inspect 的人都能看到。
- 把密钥复制进层再用 RUN 删除同样不可取，底层内容删不掉。
- 正确做法是构建期用密钥挂载，运行期用外部密钥服务或编排平台注入。

> [!WARNING]
> **警告内容**：用 ARG 传入密码、随后在 Dockerfile 里把它删除，并不能抹去镜像历史里的痕迹，任何拿到镜像的人都能还原；构建期凭据一律改用密钥挂载，且对应镜像若已推送必须作废该密钥。

**速记**：**密钥不入 ARG 与 ENV**，构建用 secret 挂载、运行用外部密钥。



### 语法前端与高级特性

#### 语法前端指令 syntax

**语法前端**：文件顶部的井号加 syntax 等于 docker/dockerfile 加版本的一行，指定**由哪个前端解析这份 Dockerfile**，从而启用对应的新语法。

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-alpine
```

- 必须写在文件最顶部、位于任何注释与指令之前，且只能出现一次。
- 视为解析器指令而非普通注释，构建器在读取文件开头时解析。
- 不写时使用内置的捆绑版本，可能缺少数条较新的语法。
- 需要时可钉到精确版本，如前端的 1.7 之类。

> 位置放错会让它失效，表现为用了新语法却报语法错误；排查此类问题先确认该行确实位于文件第一行。

**速记**：**顶部 syntax 选前端**，决定可用哪些新语法。



#### heredoc 写法

**heredoc**：用一段**以自定义结束标记包围的多行文本**替代反斜杠续行，让 RUN 或 COPY 一次处理多行内容。

```dockerfile
# syntax=docker/dockerfile:1
RUN <<EOF
apt-get update
apt-get install -y curl git
rm -rf /var/lib/apt/lists/*
EOF

COPY <<EOF /app/config.yaml
server:
  port: 3000
EOF
```

- RUN 后跟 heredoc 可像脚本一样多行书写，免去满屏反斜杠。
- COPY 后跟 heredoc 可直接把文本内容写成文件，适合生成配置。
- 结束标记需顶格书写，标记名可自定义。
- 属 BuildKit 前端能力，需顶部语法指令或足够新的内置前端。

> heredoc 只改变书写形式，RUN 仍是一条指令一层；要控制层数仍应把命令合并进同一条 RUN。

**速记**：**heredoc 用结束标记包多行**，RUN 当脚本、COPY 当文件内容。



#### 平台构建参数

**平台构建参数**：构建器预定义的一组反映**目标平台**与**构建平台**的 ARG，用于多平台构建与交叉编译。

- TARGETPLATFORM：目标平台，形如 linux/arm64。
- TARGETOS、TARGETARCH、TARGETVARIANT：目标系统的操作系统、架构与变体。
- BUILDPLATFORM、BUILDOS、BUILDARCH、BUILDVARIANT：构建机自身的平台。
- 它们在全局作用域可用，进入阶段需用 ARG 显式声明。

```dockerfile
# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM golang AS build
ARG TARGETOS TARGETARCH
RUN GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /out/app .
```

> 只有一次构建同时面向多个平台时才需关心它们；多平台镜像用 buildx 的 --platform 指定目标列表，编译阶段则跑在本机架构上。

**速记**：**TARGET 系列指目标、BUILD 系列指本机**，进阶段先 ARG 声明。



#### 绑定挂载 --mount=type=bind

**绑定挂载**：RUN --mount=type=bind 把**构建上下文或某阶段的目录**临时挂进容器供该条 RUN 读取，读完即消失、不落层。

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=bind,from=build,source=/out,target=/out cp /out/app /usr/local/bin/app
RUN --mount=type=bind,source=.,target=/src ls /src
```

- 默认绑定上下文，from 可指定其他阶段。
- 内容只在执行该条 RUN 期间可见，不会成为镜像层的一部分。
- 常用于从构建阶段取产物，或让命令读取上下文而不把它们复制进镜像。

> 与 COPY 不同，bind 挂载不产生新层，适合那些只想被读取、不想留在镜像里的中间文件。

**速记**：**--mount=type=bind 临时挂目录**，用完即弃、不落层。



#### 密钥挂载 --mount=type=secret

**密钥挂载**：RUN --mount=type=secret 把**私下提供的敏感文件**临时挂给该条 RUN，读完即消失，既不进层也不进缓存。

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc .
```

- 密钥来源由构建命令的 --secret 指定，不在 Dockerfile 里出现明文。
- 挂载内容只在该条 RUN 期间存在，不写入镜像也不写入构建缓存。
- id 在 Dockerfile 与 --secret 之间对应，target 可指定挂载路径。

> 这是处理构建期私有依赖凭据的标准手段，替代过去把私钥复制进镜像再删除的危险做法，密钥管理的完整方案见第 12 章。

**速记**：**--mount=type=secret 临时挂密钥**，构建期可读、层与缓存皆不留。



### 完整实战：一份 Node 应用的 Dockerfile

#### 完整 Dockerfile 示例

**示例定位**：下面是一份**可直接构建运行**的 Node 应用 Dockerfile，把前文讲解的指令放进真实语境串起来。

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-alpine AS base
WORKDIR /app
ENV NODE_ENV=production

FROM base AS deps
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm npm ci --omit=dev

FROM base AS runtime
ARG GIT_SHA=unknown
LABEL org.opencontainers.image.revision=$GIT_SHA
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN addgroup -S app && adduser -S app -G app && chown -R app:app /app
USER app
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "fetch('http://localhost:3000/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "server.js"]
```

- FROM 用具体主版本标签而非 latest，base 阶段只放工作目录与运行期环境变量。
- deps 阶段单独装依赖，先复制清单再执行安装，源码改动不会触发重装。

> 这里演示的是语法能力本身的组合方式，多阶段拆分策略、镜像瘦身与层缓存的系统做法见第 6 章。

**速记**：**base 打底、deps 装依赖、runtime 拼产物**，先清单后源码。



#### 逐行意图与坑点解读

**逐行解读**：按出现顺序说明每一组指令为何这样写，以及对应的常见坑。

- syntax 指令：启用 heredoc、缓存挂载等前端语法，必须置于文件首行。
- FROM AS base：用 24 明确主版本，AS 命名供后续 FROM 与 COPY --from 引用。
- WORKDIR /app：定基准目录并自动创建，后续相对路径都基于它。
- ENV NODE_ENV=production：运行期可见，让 Node 以生产模式运行。
- COPY 依赖清单到当前目录：只复制依赖清单，让依赖层缓存稳定；通配符须能命中文件，否则构建报错。
- RUN 配合缓存挂载安装：缓存下载内容，--omit=dev 不装开发依赖。
- COPY --from=deps：从 deps 阶段取依赖目录，避免把源码一并带进来。
- COPY 当前目录到当前目录：复制应用源码，务必用 .dockerignore 排除依赖目录与版本库目录，否则会覆盖刚装好的依赖。
- addgroup 与 adduser 与 chown：创建非特权用户并授权，为下一步切换身份铺路。
- USER app：以非 root 运行，降低被突破后的影响面。
- HEALTHCHECK：周期探活，启动宽限期内失败不计入重试。
- CMD：exec 形式启动，信号直达 node 进程。

> 最容易翻车的是 COPY 整个目录覆盖依赖与通配符未命中两点：前者靠 .dockerignore 兜底，后者要先确认文件名与通配符一致。

**速记**：**清单在前源码在后、非 root 运行、exec 启动、dockerignore 兜底**。



#### 构建与验证

**构建与验证**：用固定命令把镜像构建、运行并核对前面各指令留下的元数据。

```bash
docker build -t node-demo:1.0 .
docker run --rm -p 3000:3000 node-demo:1.0
docker inspect node-demo:1.0 --format '{{.Config.User}} {{.Config.Env}}'
docker history node-demo:1.0
```

- build 失败时先看报错行号定位指令，再核对上下文与 .dockerignore。
- run 加 --rm 便于一次性验证，-p 才真正发布 EXPOSE 声明的端口。
- inspect 核验 USER 与 ENV 是否按预期写入镜像配置。
- history 查看层数与体积，确认没有把大文件或密钥带进层。

> 想验证缓存是否按预期复用，连续两次构建观察第二步是否秒完成；想验证信号处理，用 docker stop 看容器能否在宽限期内优雅退出。

**速记**：**build 看报错、run 看端口、inspect 看配置、history 看层**。



### 常见反模式清单

#### apt 更新与安装分成两条 RUN

**错误写法**：把 apt-get update 与 apt-get install 分成两条 RUN，会让镜像缓存停在两者之间、命中过期索引，导致安装失败或装上旧版本。

- 两条 RUN 各成一层，update 层若命中旧缓存，install 层就可能找不到目标包。
- 正确做法是写进同一条 RUN，用逻辑与串联，装完清理包索引目录。
- 同类问题也见于 apk 与 yum 的元数据刷新。

```dockerfile
# 反例
RUN apt-get update
RUN apt-get install -y curl

# 正例
RUN apt-get update && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*
```

> 拆开写看似清晰，实则把两个必须原子完成的动作拆散，是缓存相关的经典陷阱。

**速记**：**update 与 install 同一条 RUN**，逻辑与串联并清理索引。



#### 一次 COPY 整个目录

**错误写法**：用一条 COPY 把整个上下文塞进镜像，会让任何文件改动都击穿其后所有层缓存，还可能把依赖目录与版本库元数据一并带入。

- 应在复制源码之前先复制依赖清单并安装依赖。
- 用 .dockerignore 排除版本库目录、依赖目录、构建产物与凭证文件。
- 复制范围越精确，缓存复用率越高、镜像越小。

```dockerfile
# 反例：任何源码改动都让依赖重装
COPY . .
RUN npm ci

# 正例：清单与源码分两步
COPY package*.json ./
RUN npm ci
COPY . .
```

> 拆分的收益随依赖安装耗时放大，依赖越多这条习惯越值钱。

**速记**：**清单先源码后、范围越窄越好、dockerignore 兜底**。



#### 依赖 ADD 的隐式解压

**反模式**：用 ADD 复制普通文件并期待它与 COPY 行为一致，容易被自动解压与 URL 下载的隐式语义误导。

- 本地归档会被自动解开，目标目录结构与预期不符。
- URL 源不会解压，且落地权限固定为 600，容易埋下权限问题。
- 除确需解压本地归档外，一律用 COPY 表达意图。

> 隐式行为降低可读性也增加排错成本，官方明确建议优先 COPY；需要下载归档时，更稳妥的做法是在 RUN 里用 curl 配合明确的解压命令。

**速记**：**ADD 隐式解压、隐式下载**，能 COPY 就 COPY。



#### 用 latest 作基础镜像

**反模式**：FROM 写 latest 或不写标签，会让不同时间、不同机器构建出不同底层，构建结果不可复现。

- latest 是浮动标签，指向会随时间变化。
- 同一份 Dockerfile 今天与下月构建可能得到不同的基础镜像。
- 固定到主版本可平衡稳定性与安全更新，追求完全可复现可再固定到 digest。

> 完全写死 digest 会失去安全补丁，需配合定期更新流程；常规做法是固定主版本标签并定期重建。

**速记**：**别用 latest，固定主版本或 digest**。



#### 以 root 运行

**反模式**：不写 USER，容器主进程默认以 root 运行，一旦被突破影响面更大。

- 默认身份即 root，在缺少额外隔离时其权限接近宿主 root。
- 应建立非特权用户并用 COPY --chown 授权，再以 USER 切换。
- 许多基础镜像已内置可用的非特权用户，优先复用。

> 非 root 运行是容器安全基线的一部分，需与只读文件系统、能力裁剪等措施配合，安全实践详见第 16 章。

**速记**：**默认 root 要改，建用户、改属主、切 USER**。



#### 把敏感文件复制进镜像

**反模式**：把环境文件、私钥、凭据复制进镜像，即便后续用 RUN 删除，文件仍留在底层，可被提取。

- 层是不可变的，删除只在上层记一条遮蔽，底层内容依旧存在。
- 构建期凭据应改用密钥挂载。
- 运行期配置应通过环境变量、挂载卷或外部密钥服务注入。

> [!CAUTION]
> **注意内容**：一旦含密钥的层被推送到仓库，密钥即视为已泄露，删除新层也无法回收旧层；此时必须作废该密钥并重建镜像，而不是只发布一个删过文件的新版本。

**速记**：**密钥不复制，删也删不掉**，构建用 secret、运行用挂载。
