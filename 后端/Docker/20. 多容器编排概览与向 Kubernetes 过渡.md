## 多容器编排概览与向 Kubernetes 过渡

### 单机编排的天花板

#### 单主机故障即全栈不可用

**单点故障**：Compose 编排的全部容器都跑在同一台主机、同一个 Docker 守护进程上，宿主机宕机、守护进程异常退出或磁盘写满，都会让整套应用同时不可用。

- **故障域等于主机**：进程隔离解决的是容器之间的隔离，不解决主机之间的隔离，一台机器上的所有容器共享同一内核、同一磁盘与同一网络栈。
- **没有故障转移**：Compose 只会在本机按 restart 策略重启容器，宿主机关机后没有任何机制把容器迁到另一台机器。
- **恢复靠人**：备份、重建与流量切换都要人工执行，恢复时间取决于值守者是否在线。
- **与集群的差别**：集群编排器把容器分散到多个节点，单节点失效只损失其上的一部分副本，其余节点继续服务。

> 容器本身不等于高可用。把无状态服务做成多副本只是前提，真正的高可用还需要副本分散到不同故障域并由编排器持续维持数量。

**速记**：Compose 的故障域就是一台主机，主机没了全栈就没了。



#### 单机无法横向扩容

**横向扩容**：指通过增加服务实例数量来提升吞吐；Compose 的 scale 只能在单台主机上增加容器，受限于该主机的 CPU、内存、磁盘与端口。

- **上限是主机资源**：副本再多也要挤在同一台机器的资源预算内，扩容到某个点后副本之间开始争抢 CPU 与内存。
- **端口成为瓶颈**：入口服务若发布了固定宿主端口，第二个副本会因端口占用而无法创建。
- **数据卷不能共享**：同一命名卷同时挂给多个副本会引发写冲突，有状态服务无法这样扩容。
- **量级变化要跨主机**：只有需要超过单机容量时才需要集群，这一点应按实际负载判断，而不是先上集群再说。

> [!NOTE]
> **提醒内容**：单机 Compose 并非不能扩容，加 scale 参数即可在同一主机上起多个副本。本篇说的「不够用」指的是主机资源与端口已到上限，而非 Compose 不支持多副本。

**速记**：单机扩容的天花板就是这台机器的 CPU、内存与端口。



#### 资源用满后无处调度

**调度缺失**：Compose 没有调度器，它只在本机把服务拉起；当多个服务都需要大量资源时，没有任何组件去衡量哪台机器更适合承载它们。

- **没有资源画像**：Compose 不知道每台机器还剩多少 CPU 与内存，也就无法把新容器放到余量最大的节点。
- **没有装箱决策**：多个服务争抢同一台机器时只能人工拆分到不同主机，再分别维护各自的 Compose 文件。
- **没有抢占与迁移**：节点过载时没有机制把低优先级负载挤走或迁到别处。
- **集群的做法**：调度器读取每个节点的可分配资源与容器声明的 requests、limits，再决定落点，这部分与篇 13 的资源约束模型直接对应。

> 资源限制解决的是「一个容器最多能用多少」，调度解决的是「这个容器应该放在哪台机器上」，是两道不同的问题。

**速记**：没有调度器就只能人工分机器，requests 与 limits 是调度器决策的输入。



#### 发布与回滚只能靠手工

**发布手段**：单机 Compose 的发布是拉新镜像、重建容器，期间服务会短暂中断；回滚同样靠改回旧标签再重建，全过程没有编排器的分批与校验。

- **停旧起新有中断**：替换容器时旧容器先停、新容器再起，这段窗口内请求会失败。
- **没有分批策略**：无法先起一个新副本、验证健康后再逐步替换其余副本。
- **回滚靠人判断**：新版本出问题时要人工发现、人工改回旧标签、人工重建，恢复速度取决于响应速度。
- **发布状态不可观测**：没有「已更新几个副本、还剩几个」的进度视图，只能逐个容器查状态。

> [!IMPORTANT]
> **重要内容**：集群编排器把发布建模成受控的期望状态变更，先创建新副本、通过健康检查后摘除旧副本，失败自动暂停或回滚。这套语义单机 Compose 不提供，只能靠外部脚本近似模拟。

**速记**：单机发布是停旧起新，没有分批与自动回滚。



#### 多主机多环境靠人管

**管理成本**：当应用需要跑在多台主机，或同时跑在开发、预发、生产多套环境时，Compose 的每套环境都要各自维护文件与操作流程，一致性全靠人工保证。

- **文件按环境复制**：多套 Compose 文件随时间漂移，配置差异容易失控。
- **操作按主机重复**：每台主机都要登录、拉代码、执行命令，无法一处声明、处处生效。
- **状态分散**：哪台机器上跑了什么，往往要靠巡检或台账得知，而不是查询一个统一的状态源。
- **集群的收敛**：集群维护一份期望状态，由控制器持续把每个节点的实际状态向它对齐，人的职责从逐台操作变成声明一次。

> [!CAUTION]
> **注意内容**：用脚本加 SSH 批量跑 Compose 命令能缓解多主机问题，但脚本本身没有状态收敛能力，失败重试、节点漂移与部分成功都难以处理。规模一大，这类自研胶水会先于业务出问题。

**速记**：多主机多环境要靠集群收敛状态，靠人逐台维护终会漂移。



### 编排系统要解决的通用问题

#### 调度：把容器放到合适的节点

**调度（Scheduling）**：指按资源需求、亲和与反亲和、污点与容忍等规则，为每个待运行的容器选择一台合适的节点。

- **资源匹配**：节点剩余的可分配资源必须能容纳容器声明的 requests。
- **约束规则**：按标签选择节点、要求同类副本分散到不同节点、避免与特定工作负载同机。
- **优先级与抢占**：资源紧张时决定谁先被调度、谁可被挤走。
- **无解处理**：找不到合适节点时容器保持等待，并暴露原因供排查。

> 调度器只负责「放哪」，不负责「起没起来」；容器起来之后的健康维持由自愈机制承担，两者职责不同。

**速记**：调度按资源与规则选节点，放不下就排队。



#### 期望状态收敛：声明式与自我修复

**期望状态收敛（Reconciliation）**：用户只声明要几个副本、用什么镜像，控制器持续对比实际状态与期望状态，并修正差异。

- **声明式**：写目标是三个副本，而不是写脚本去启动三个进程。
- **持续循环**：控制器周期性巡检，副本挂了就补、多了就删。
- **幂等**：同一声明反复执行结果一致，可安全重放。
- **与命令式的差别**：命令式描述怎么做，声明式只描述要什么结果。

> Compose 的 up 已具备声明式的雏形，但它只在执行那一刻对齐一次，不具备常驻控制器持续收敛的能力。

**速记**：声明目标、控制器持续对齐，掉了就补。



#### 服务发现与负载均衡

**服务发现（Service Discovery）**：让调用方通过稳定的服务名找到后端实例，而不必硬编码某一台的地址。

- **名称稳定**：副本的地址随创建销毁而变化，服务名保持不变。
- **内部负载均衡**：把请求分发到该服务的多个健康副本。
- **两种访问要分开**：集群内访问靠内部 DNS，集群外访问靠入口组件。
- **与 Compose 的对照**：同网络内用服务名互访是单机范围的服务发现，跨主机时需要集群级 DNS 与负载均衡。

> 服务发现解决「找到谁」，负载均衡解决「分给谁」；二者通常一起提供，但概念上要分开。

**速记**：服务名稳定、后端可变，发现加均衡才可跨主机调用。



#### 滚动发布与回滚

**滚动发布（Rolling Update）**：分批替换旧副本，先起新的、健康后再停旧的，使发布过程中始终有可用副本。

- **分批控制**：一次替换几个副本、批次之间是否等待。
- **健康门禁**：新副本未通过健康检查则暂停发布。
- **自动回滚**：连续失败超过阈值时退回上一个版本。
- **版本记录**：需要保留可追溯的版本，才能执行回滚。

> 滚动发布的前提是无状态与服务发现：副本可以随时替换、地址随时变化，调用方仍能通过服务名访问。

**速记**：先起新、健康后停旧，失败暂停可回滚。



#### 配置与密钥分发

**配置分发**：把配置与密钥从镜像中剥离，作为独立对象注入容器，避免为改一个配置重建镜像。

- **配置外置**：非敏感配置以键值或文件形式注入容器。
- **密钥隔离**：敏感取值单独存放，只下发给需要的服务。
- **集群级分发**：配置对象在集群内共享，可一次更新、多处引用。
- **与 Compose 的对照**：Compose 用 environment、env_file、configs、secrets 注入，集群把这套能力对象化，做法见 12. 环境变量、配置注入与密钥管理。

> 把配置写死在镜像里，会让同一个镜像无法跨环境复用。配置外置是容器化的基本要求，也是迁移到集群的前置条件。

**速记**：配置与密钥从镜像剥离，作为对象按需注入。



#### 存储编排

**存储编排**：为需要持久化的容器提供与生命周期解耦的存储，容器在哪个节点重建，都能挂回同一份数据。

- **存储与容器解耦**：数据存在外部存储上，容器的创建销毁不影响数据。
- **动态供给**：按声明自动创建所需的存储卷。
- **访问模式**：区分单节点读写、多节点只读等不同挂载要求。
- **与 Compose 的对照**：Compose 的命名卷绑定在本机，跨主机时无法直接使用，做法见 7. 数据卷与数据持久化。

> 有状态服务是集群里最难的部分：数据落在哪、谁能挂、挂载模式如何，都比无状态服务复杂得多，这也是多数团队把数据库留在集群外的原因。

**速记**：数据与容器生命周期解耦，容器搬走数据不丢。



#### 健康检查与自愈

**健康与自愈**：编排器周期性探测容器状态，不健康的实例被替换或摘除，使故障不扩散到调用方。

- **存活探测**：判断容器是否需要重启。
- **就绪探测**：判断实例是否可以接收流量。
- **自动替换**：实例反复失败时被销毁并重建。
- **与 Compose 的对照**：Compose 的 healthcheck 只标记状态、由依赖条件消费；集群把探测结果直接接入流量与重建决策。

> 存活与就绪要分开。依赖暂时不可用时应先摘流量而不是重启，盲目重启会把一次下游抖动放大成整组实例的反复重启，相关讨论见 11. Docker Compose 进阶与实战。

**速记**：探测定状态，不健康就摘流量或重建。



#### 多租户与配额

**多租户**：把一套集群的资源按团队或环境划分给不同使用者，并限制各自能占用的上限。

- **逻辑隔离**：用命名空间一类的边界把对象分组。
- **资源配额**：限制单组可申请的 CPU、内存与对象数量。
- **权限控制**：限定谁能操作哪些资源。
- **与单机的对照**：单机 Compose 只有项目名做命名隔离，没有配额与权限模型。

> 多租户回答的是共用一套集群时如何互不干扰，这是团队规模上去后才显现的需求，小型团队往往用独立集群替代。

**速记**：命名空间分边界、配额限上限、权限定范围。



### Docker Swarm 的现状与定位

#### Swarm 是什么

**Docker Swarm 模式（Swarm mode）**：Docker Engine 内置的集群管理与编排能力，把多台运行 Docker 的机器组成一个 swarm，用 Docker CLI 直接创建集群、部署服务并管理其行为。

- **内置形态**：不需要额外安装编排组件，随 Engine 一同提供。
- **声明式服务**：用声明描述服务的期望状态，由 manager 节点维持。
- **官方定位**：官方文档把它定位为「把 Swarm 用作生产运行时环境时使用的模式」，并明确与 Compose 区分。
- **与 Compose 的分工**：不打算用 Swarm 部署时应改用 Compose；面向 Kubernetes 部署时应考虑 Docker Desktop 中集成的 Kubernetes 特性。

> 需要区分 Swarm 模式与已不再积极开发的 Docker Classic Swarm。前者是 Engine 内置特性，后者是历史项目，两者不可混为一谈。

**速记**：Swarm 是 Engine 内置的集群编排，Docker CLI 直接管。



#### 基本概念：node、service、task 与 stack

**四个概念**：node 是参与 swarm 的 Docker 引擎实例，service 是要在节点上执行的任务的定义，task 是携带一个容器及命令的原子调度单元，stack 是一组由同一份 Compose 文件部署的服务集合。

- **node（节点）**：分 manager 与 worker 两类，manager 负责编排与集群管理，worker 接收并执行被分派的任务，manager 默认也承担 worker 角色。
- **service（服务）**：swarm 的核心结构，是用户与 swarm 交互的主要入口；分复制服务与全局服务两种模型，前者按声明的副本数分发任务，后者在每个可用节点各跑一个。
- **task（任务）**：调度的最小单位，一旦分配到某个节点就不能迁移，只能在该节点上运行。
- **stack（服务栈）**：以 Compose 文件描述一组服务，一次部署形成一个 stack，stack 名会成为其下服务与网络名的前缀。

> 这套模型是「声明服务、由调度器生成任务、任务落在节点上」的三层结构，理解它可以与后文 Kubernetes 的 Pod 与 Deployment 做类比。

**速记**：node 是机器、service 是期望、task 是原子调度单位、stack 是一组服务。



#### docker stack deploy 与 Compose 文件

**stack 部署**：用 docker stack deploy 按一份 Compose 文件在 swarm 上创建或更新一个 stack，它必须在 manager 节点执行，stack 名由命令的位置参数给出。

- **命令形态**：docker stack deploy 后接文件参数与 stack 名，别名是 docker stack up。
- **文件形态**：接受 Compose 文件，可多次指定文件做叠加，也可从标准输入读取。
- **生效范围**：原属 Compose deploy 段的 replicas、placement、update_config 等字段在 Swarm 下才真正生效，这与 11. Docker Compose 进阶与实战 中「未被平台实现的 deploy 字段被忽略」的说明正好互补。
- **不负责构建**：stack deploy 不构建镜像，带 build 的服务需要先构建并推送，再由集群拉取。

> docker stack deploy 是把 Compose 文件当部署清单用的入口，因此为单机写的内容可以较大程度复用，但镜像必须先存在于集群可达的仓库中。

**速记**：stack deploy 在 manager 上按 Compose 文件建 stack，replicas 等 deploy 字段这时才生效。



#### 优劣势与选型建议

**选型结论**：新项目应选 Kubernetes；存量的小规模 Swarm 部署可以继续运行，但不宜再追加投入。

- **优势**：与 Engine 同源、上手快，概念少，Compose 文件几乎可以直接部署，适合快速搭起小集群。
- **劣势**：生态与人才市场已被 Kubernetes 占据，周边工具、托管服务与招聘供给都集中在 Kubernetes 一侧，长期维护与招人成本更高。
- **官方投入**：当前官方文档仍把 Swarm 作为受支持特性记载，但对新方向（面向 Kubernetes 的开发体验）的投入更明确，Swarm 的演进节奏相对缓慢。
- **迁移现实**：一旦周边系统（监控、CI、托管平台）都围绕 Kubernetes 建设，继续留在 Swarm 的集成成本会持续上升。

> [!NOTE]
> **提醒内容**：客观表述是 Swarm 仍可用但已不再是新项目的默认选择，不宜说成已被官方宣布废弃。判断依据是官方投入方向与社区事实，而非某一篇文档的措辞。

**速记**：新项目选 Kubernetes，存量小 Swarm 可续用但不加投入。



### Compose 与 Swarm 的概念映射

#### 服务定义到 service 对象

**映射关系**：Compose 文件 services 下的每一项，部署到 Swarm 后对应一个 service 对象，服务名即 service 名，在 stack 内以 stack 名为前缀。

- **镜像与命令**：image、command、entrypoint 直接映射到 service 的对应字段。
- **端口**：ports 映射为服务的发布端口，Swarm 默认在 30000-32767 范围内分配宿主端口，也可显式指定。
- **环境与配置**：environment、env_file、configs、secrets 对应 service 的环境与配置挂载。
- **资源**：deploy.resources 的 limits 与 reservations 在 Swarm 下真正生效。

> Compose 的服务是「一台机器上的一组容器」，Swarm 的 service 是「集群范围内维持若干任务的期望状态」，同一个名字背后的语义不同。

**速记**：Compose 的一个服务对应 Swarm 的一个 service 对象。



#### 副本数到 replicas

**副本语义**：Compose 单机用 scale 或命令行参数控制容器数，Swarm 用 deploy.replicas 声明期望任务数，由 manager 自动增删任务来维持。

- **声明位置**：副本数写在 deploy.replicas，属部署规范字段。
- **维持方式**：任务失败或节点失联时，manager 在其他节点重建任务以补齐数量。
- **全局服务**：另一种模型是每个可用节点各跑一个任务，适合日志采集、监控代理这类每节点都要有的组件。
- **单机对照**：单机的 scale 只在本机增加容器，Swarm 的 replicas 是跨节点的期望状态。

> 同一个 deploy.replicas 字段，在单机 Compose 下被忽略、在 Swarm 下生效，这正是 11. Docker Compose 进阶与实战 中「deploy 段未实现即忽略」的具体体现。

**速记**：单机看 scale，Swarm 看 deploy.replicas，后者跨节点维持数量。



#### 网络到 overlay 网络

**网络映射**：Compose 的 networks 在 Swarm 下对应 overlay 网络，它是跨主机的虚拟网络，让分布在多个节点上的任务像在同一台机器上一样互通。

- **overlay 特性**：覆盖在宿主网络之上，跨节点分配地址并转发流量。
- **内置服务发现**：Swarm 为每个服务分配 DNS 名称，集群内按服务名互访，机制与 Compose 的单网络服务名解析同源，范围扩到整个集群。
- **ingress 负载均衡**：对外发布端口时，任意节点都能接收并转发到正在运行任务的节点。
- **默认网络**：未显式声明时同样有默认网络，作用范围从单机扩到整个 swarm。

> 把 Compose 的 bridge 网络与 Swarm 的 overlay 网络当成同一个东西，会误判可达范围：前者只覆盖单机，后者跨主机。

**速记**：networks 变 overlay，跨主机互通、服务名照旧可解析。



#### 卷到集群卷

**存储映射**：Compose 的命名卷绑定在单台主机上，Swarm 下若要让任务在任何节点都能挂到同一份数据，需要改用支持多机的存储方案。

- **单机卷的局限**：命名卷的数据只存在于创建它的那台主机，任务被调度到别的节点就看不到数据。
- **集群卷**：需要外接网络存储，或以插件方式提供跨节点可挂载的卷。
- **绑定挂载的局限**：绑定挂载依赖宿主目录，同样只在单机有意义。
- **有状态服务的处理**：实践中常把数据库移出 swarm，或固定到带特定标签的节点上再配合本地卷。

> 存储是 Compose 到 Swarm 迁移中唯一无法靠改名完成的映射：数据在哪块盘上是物理问题，不是声明问题。

**速记**：单机命名卷不跨主机，集群存储要外接或用插件。



#### 命令到 stack 命令与 Compose 文件生效边界

**命令映射**：docker compose 的子命令在 Swarm 下换成 docker stack 与 docker service 两组命令，前者管部署单元，后者管单个服务。

- **部署**：docker compose up 对应 docker stack deploy，docker compose down 对应 docker stack rm。
- **观察**：docker compose ps 与 logs 对应 docker stack services、docker service ps 与 docker service logs。
- **扩缩容**：docker compose up 的 scale 参数对应 docker service scale。
- **生效边界**：Compose 文件里的 build 在 Swarm 下不生效（stack deploy 不构建镜像），deploy 段的编排字段反而开始生效，与单机下「deploy 被忽略、build 生效」正好相反。

> 同一份 Compose 文件在两种平台上生效的字段集合不同，迁移前应先区分哪些字段是给单机用的、哪些是给 Swarm 用的。

**速记**：up 变 stack deploy、ps 变 service ps，build 在 Swarm 下失效而 deploy 生效。



### Kubernetes 的核心对象入门

#### 集群与节点的构成

**集群构成**：一个 Kubernetes 集群由控制面与工作节点两部分组成，控制面负责决策与状态存储，工作节点负责运行容器。

- **控制面组件**：API Server 是集群的唯一入口，etcd 保存全部集群状态，调度器负责为 Pod 选节点，控制器管理器运行各类控制器做期望状态收敛。
- **工作节点组件**：kubelet 管理本节点上 Pod 的生命周期，容器运行时负责真正拉起容器，网络插件提供 Pod 网络，视部署形态还可能运行服务转发组件。
- **声明入口**：用户只向 API Server 提交声明，其余组件围绕它协作。
- **与单机的对照**：Compose 里「Docker 守护进程既决策又执行」的角色，在集群里被拆成控制面与节点两层。

> 控制面是集群的大脑，工作节点是手脚；etcd 是唯一的状态源，它的健康直接决定集群能否正常工作。

**速记**：控制面决策与存状态，节点跑容器，API Server 是唯一入口。



#### Pod：最小调度单元

**Pod（容器组）**：Kubernetes 中最小的可调度单元，一个 Pod 里可以放一个或多个共享网络与存储的容器，通常一个 Pod 只放一个业务容器。

- **共享命名空间**：同一 Pod 内的容器共享网络命名空间与 IP，可用 localhost 互相访问，也可共享挂载卷。
- **为何不直接管容器**：若以单个容器为调度单位，就无法表达「必须同机部署、共享网络」的组合；Pod 把这类容器打包成一个整体来调度。
- **生命周期**：Pod 是短暂的，重建后名称与 IP 都会变化，因此不应把 Pod 当成长期稳定的实体。
- **与 Compose 的对照**：Compose 的一个服务容器大致对应一个 Pod，但 Compose 的容器没有「同机共网」这一层抽象。

> Pod 不是容器，而是容器的外壳。把它的生命周期想得和容器一样短暂，是理解后续 Deployment 与 Service 的起点。

**速记**：Pod 是最小调度单元，同 Pod 共网共享卷，Pod 本身是短命的。



#### Deployment：副本与滚动发布

**Deployment（部署）**：声明某个 Pod 模板的副本数与更新策略，由它创建并管理 ReplicaSet，再由 ReplicaSet 维持 Pod 数量。

- **副本维持**：声明要几个副本，控制器持续补齐或删减。
- **滚动更新**：改镜像或模板后按策略分批替换 Pod，先起新的、健康后停旧的。
- **回滚**：保留历史版本，可退回上一版本。
- **与 Compose 的对照**：它同时承担了 Compose 里服务定义与 deploy.replicas、update_config 的角色。

> 日常不应直接创建裸 Pod，因为裸 Pod 没有控制器帮它维持数量。有状态的长期应用用 StatefulSet，需要定时任务用 Job 与 CronJob。

**速记**：Deployment 管副本与滚动更新，裸 Pod 没人补。



#### Service：稳定访问入口

**Service（服务）**：为一组 Pod 提供稳定的虚拟 IP 与 DNS 名称，把请求分发到匹配选择器的后端 Pod。

- **ClusterIP**：默认类型，只在集群内部可达，供集群内其他工作负载访问。
- **NodePort**：在每个节点的固定端口上暴露服务，集群外可经任意节点加该端口访问。
- **LoadBalancer**：借助云或基础设施的负载均衡器对外暴露，通常是最外层的入口类型。
- **ExternalName**：不代理流量，只把服务名映射为一个外部 DNS 名称。
- **与 Compose 的对照**：Service 同时承担了 Compose 里「服务名 DNS」与「负载均衡到多副本」两件事，且跨节点。

> Service 靠选择器匹配 Pod，副本如何变化都不影响调用方；这与 Compose 用服务名解析容器地址是同一思路，区别是后端会动态变化。

**速记**：ClusterIP 管内、NodePort 开端口、LoadBalancer 借外部均衡器、ExternalName 指外部域名。



#### Ingress：七层入口

**Ingress（入口）**：把集群外的 HTTP 与 HTTPS 流量按域名与路径规则转发到集群内的 Service，承担七层路由职责。

- **规则形态**：按主机名与路径匹配，再指向某个 Service 的某个端口。
- **需要控制器**：Ingress 只是规则声明，真正生效要部署一个 Ingress 控制器来执行。
- **与 Service 的分工**：Service 做四层转发与内部寻址，Ingress 做七层路由与 TLS 终止。
- **与 Compose 的对照**：它对应的正是容器栈里 Nginx 反向代理的角色，相关内容见 19. Docker 与 Nginx 反向代理实战。

> 集群里不再需要自己写一份 Nginx 配置来区分站点：站点规则变成 Ingress 对象，容器化的反向代理由 Ingress 控制器提供。

**速记**：Ingress 管七层路由与 TLS，替代了手写的 Nginx 站点配置。



#### ConfigMap 与 Secret：配置注入

**配置对象**：ConfigMap 存放非敏感的配置数据，Secret 存放口令、令牌一类的敏感数据，两者都以环境变量或文件的形式注入 Pod。

- **注入方式**：可作为环境变量注入，也可作为文件挂载进容器。
- **更新行为**：修改对象后，以文件方式挂载的内容会随更新而变，以环境变量注入的不会自动更新，需要重建 Pod。
- **与镜像解耦**：同一个镜像可跨环境复用，配置差异由对象承担。
- **与 Compose 的对照**：分别对应 Compose 的 configs 与 secrets，注入与优先级规则的完整讨论见 12. 环境变量、配置注入与密钥管理。

> [!CAUTION]
> **注意内容**：Secret 默认只是做了编码而非加密，能否真正保密取决于集群的加密配置与访问控制。把密钥写进 ConfigMap 或提交进版本库都是常见泄密途径。

**速记**：ConfigMap 放配置、Secret 放敏感值，两者都以环境变量或文件注入。



#### StatefulSet 与 PersistentVolumeClaim：有状态服务

**有状态对象**：StatefulSet 为 Pod 提供稳定的名称与存储绑定，PersistentVolumeClaim 声明所需的存储并由 PersistentVolume 提供，两者配合承载数据库这类有状态服务。

- **StatefulSet 的特性**：Pod 有固定序号与稳定网络标识，扩缩容按顺序进行。
- **PVC 与 PV**：PVC 是使用者的存储申请，PV 是实际提供的存储资源，二者通过声明绑定。
- **与 Deployment 的差别**：Deployment 的 Pod 可随意替换且共享存储语义弱，StatefulSet 的每个 Pod 有独立且稳定的存储。
- **与 Compose 的对照**：Compose 的命名卷大致对应一个 PVC，但单机命名卷没有动态供给与跨节点挂载的能力。

> 有状态服务在集群里最难运维，多数团队的做法是把数据库托管到集群之外的托管服务，集群内只跑无状态应用。

**速记**：StatefulSet 给稳定名称与存储，PVC 声明存储、PV 提供存储。



### 概念映射对照

#### services 与工作负载对象的对应

**对应总览**：一个无状态服务通常对应一个 Deployment 加一个 Service，有状态服务对应 StatefulSet 加 Service，跑完即退的任务对应 Job。

- **服务定义**：镜像、命令、环境变量落在 Pod 模板的容器字段里。
- **副本数**：Compose 的 scale 或 deploy.replicas 对应 Deployment 的 replicas。
- **端口**：容器端口对应 Pod 模板里的容器端口，服务端口对应 Service 的 ports。
- **一次性任务**：Compose 的迁移服务对应一个 Job，跑完即退的语义由 Job 承担。

> 这不是一对一改名，而是把「一个服务」拆成「控制器加访问入口」两个对象，职责分得更细。

**速记**：无状态用 Deployment 加 Service，有状态用 StatefulSet，一次性任务用 Job。



#### networks 与 ports 的对应

**网络对应**：Compose 的 networks 在 Kubernetes 里由集群级的 Pod 网络与网络策略承担，ports 则由 Service 与 Ingress 分担。

- **基础连通**：Pod 之间默认可互通，不需要像 Compose 那样先声明一张网络。
- **隔离**：需要限制可达范围时用网络策略声明允许的流量，相当于 Compose 分网络隔离的加强版。
- **端口分层**：容器内端口由容器声明，集群内访问入口由 Service 提供，集群外入口由 Service 的 NodePort、LoadBalancer 或 Ingress 提供。
- **与 Compose 的差别**：Compose 里服务连到哪张网络是显式的，Kubernetes 里默认全通、隔离要靠策略显式声明。

> 默认全通是 Kubernetes 与 Compose 最反直觉的差异之一。迁移后原本靠分网络实现的隔离不会自动保留，必须补上网络策略。

**速记**：Pod 网络默认全通，隔离靠网络策略，入口靠 Service 与 Ingress。



#### volumes 与存储对象的对应

**存储对应**：Compose 的命名卷对应 PersistentVolumeClaim，绑定挂载对应 hostPath 或 EmptyDir 一类的卷，前者用于持久数据，后者用于临时数据。

- **持久卷**：PVC 声明容量与访问模式，由 PV 或动态供给提供实际存储。
- **临时卷**：EmptyDir 随 Pod 生命周期存在，Pod 删除即清空。
- **配置卷**：配置文件以 ConfigMap 或 Secret 挂载，不占用持久存储。
- **与 Compose 的差别**：单机命名卷由 Docker 在本机管理，集群的 PV 可能来自网络存储，挂载与回收行为都更复杂。

> 迁移时最容易出错的是把数据目录写成临时卷：Pod 一重建数据就没了，这类问题往往在上线后才暴露。

**速记**：持久数据用 PVC，临时数据用 EmptyDir，配置用 ConfigMap 与 Secret 挂载。



#### environment 与配置对象的对应

**配置对应**：Compose 的 environment 与 env_file 对应 Pod 模板里的环境变量与批量注入字段，configs 与 secrets 则对应 ConfigMap 与 Secret。

- **直写变量**：environment 里的键值对应容器的环境变量列表。
- **批量注入**：env_file 的批量语义对应从 ConfigMap 或 Secret 整体注入。
- **文件注入**：以配置文件形式挂载的内容对应把 ConfigMap 或 Secret 挂成卷。
- **与 Compose 的差别**：集群里配置是有名字、可被多个工作负载共享的对象，改动影响面比单机 Compose 文件更大。

> 把配置抽成独立对象后，「改了配置会影响哪些服务」需要主动梳理，否则共享对象的改动可能波及意料之外的工作负载。

**速记**：environment 对环境变量、env_file 对整体注入、configs 与 secrets 对 ConfigMap 与 Secret。



#### depends_on 的换思路

**换思路**：Kubernetes 没有与 depends_on 直接对应的字段，启动顺序问题改用就绪探针加应用侧重试解决。

- **没有直接对应**：Pod 由控制器独立调度，无法保证 A 先于 B 启动。
- **就绪探针**：让依赖方只在对方就绪后才接收流量，间接实现先后的效果。
- **应用侧重试**：连接失败时由应用按退避策略重试，覆盖启动竞态与运行期抖动。
- **一次性任务**：初始化与迁移改用 Job，由 Job 完成后再启动应用。

> [!IMPORTANT]
> **重要内容**：把 depends_on 的心理模型直接搬到集群会处处碰壁。集群的设计假设是依赖随时可能不可用，正确做法是让应用能容忍依赖暂时缺席，而不是依赖启动顺序。这与 11. Docker Compose 进阶与实战 中「编排管顺序、应用管韧性」的结论一致。

**速记**：depends_on 没有对应，用就绪探针加应用重试替代。



#### healthcheck 与 restart 的换思路

**换思路**：Compose 的 healthcheck 与 restart 在 Kubernetes 里拆成探针与重启策略两套机制，且探针直接接入流量与重建决策。

- **存活探针**：容器存活探测失败时重启容器，对应「进程假死需要重启」的场景。
- **就绪探针**：就绪探测失败时把实例从 Service 的可用后端中摘除，不再接收流量。
- **启动探针**：为慢启动应用提供宽限期，成功前暂停其他探测。
- **重启策略**：重启行为由 Pod 的重启策略与控制器共同决定，常驻服务由 Deployment 维持副本。
- **与 Compose 的差别**：Compose 的 healthcheck 只影响依赖条件，不直接改变流量走向。

> 探针配置不当的后果与 Compose 不同：在集群里，一个过严的存活探针会引发整个 Deployment 的 Pod 循环重启，故障面比单机更大。

**速记**：存活探针管重启、就绪探针管流量、启动探针管宽限，对应 healthcheck 与 restart 两支。



### 迁移路径与工具

#### kompose 能转什么、转不了什么

**kompose（Compose 转换工具）**：把 Docker Compose 文件转换成 Kubernetes 或 OpenShift 清单的命令行工具，用法是 kompose convert 后接文件。

- **能转的基础项**：image、ports、environment、volumes、networks、command、entrypoint 等。
- **能转的部署项**：deploy.replicas 对应 Deployment 的副本数，deploy.resources 对应容器的资源声明，deploy.update_config 对应更新策略。
- **转不了或不适用**：depends_on 在官方转换矩阵里标注为不适用，links、external_links、logging、dns、network_mode、ulimits、devices 等同样没有对应。
- **需人工接管**：健康检查的转换结果、存储的实际提供方式，以及需要额外字段的场景，都要人工调整。
- **定位**：官方说明转换并非总是逐一对应，结果只能作为起点，需要人工审阅与补全。

```bash
kompose convert -f compose.yaml
kubectl apply -f .
```

> [!WARNING]
> **警告内容**：转换工具负责生成骨架，不负责保证语义等价。把 kompose 的输出直接应用到生产集群，等于让一个不理解业务拓扑的脚本替你做架构决策。转换后必须逐个核对副本数、探针、存储与网络策略。

**速记**：kompose 转骨架，depends_on 无对应，结果只能当起点。



#### 手工迁移的正确顺序

**迁移顺序**：先让应用可被容器化与去状态化，再把配置外置，然后补上探针与资源声明，最后接入入口与存储。

- **第一步容器化与去状态化**：确保应用不在本地磁盘写业务数据，会话状态外置到缓存或数据库。
- **第二步配置外置**：把配置与密钥抽成 ConfigMap 与 Secret，镜像不带环境差异。
- **第三步探针与资源**：补上就绪与存活探针，声明 requests 与 limits 供调度器决策。
- **第四步入口与存储**：按需接 Ingress 与 PVC，把集群外访问与持久数据补齐。
- **顺序理由**：前一步不成立时后一步无法验证，例如配置仍写死在镜像里就无法多环境复用。

> 迁移不是把文件翻译一遍，而是逐项消除对单机环境的隐式依赖。顺序本身就说明了哪些是前置条件。

**速记**：先去状态化、再配置外置、然后探针与资源、最后入口与存储。



#### 迁移前必须先解决的三件事

**三件前置**：数据出容器、日志走标准输出、配置全走环境变量或配置对象，是迁移到任何编排平台都必须先满足的条件。

- **数据出容器**：业务数据不写在容器可写层或本地路径上，改为外部数据库、对象存储或持久卷。
- **日志走标准输出**：日志写到标准输出与标准错误，由平台采集，而不是写在容器内的文件里。
- **配置全外置**：所有环境差异来自环境变量或配置对象，镜像本身不含任何环境相关取值。
- **检验方式**：把容器删掉重建，应用能否用新的配置重新拉起且不丢数据，是这三件事是否达标的直接检验。

> [!NOTE]
> **提醒内容**：这三件事在单机 Compose 下不做也能跑，所以常被长期忽略。迁移到集群时它们会同时变成硬性门槛，日志采集、存储挂载与多环境复用都依赖它们。

**速记**：数据出容器、日志进标准输出、配置全外置，三件事不达标就别谈迁移。



### 镜像与仓库在集群里的角色

#### 每个节点都要能拉到镜像

**拉取前提**：集群里 Pod 可能被调度到任意节点，因此每个工作节点都必须能访问到镜像仓库，或者能通过分发机制拿到镜像。

- **仓库可达性**：内网集群要能访问自建 registry，否则 Pod 会卡在拉取镜像阶段。
- **分发策略**：常见做法是每个节点都能直连同一个 registry，或预先在节点上加载镜像。
- **加速与缓存**：镜像较大或多副本同时启动时，仓库带宽与拉取耗时会成为发布速度的瓶颈，可考虑镜像缓存或就近仓库。
- **与篇 15 的关系**：仓库本身的能力与选型见 15. 镜像仓库与私有 Registry。

> [!WARNING]
> **警告内容**：一个节点拉不到镜像，Pod 就永远起不来，而现象只是调度后长时间停在拉取镜像状态。集群规模越大，任何一个节点的网络或凭证问题都会被放大成随机故障。

**速记**：Pod 可能落在任意节点，镜像必须每个节点都拉得到。



#### 标签不可变与固定 digest

**镜像标识**：集群场景应使用不可变标签或直接固定 digest，保证同一个版本在任何节点、任何时间拉到的都是同一份内容。

- **可变标签的风险**：latest 或可被覆盖的标签会让不同节点拉到不同内容，造成同一版本表现不一致。
- **digest 的意义**：digest 由内容计算得出，固定它即可精确锁定镜像，不随标签漂移。
- **发布纪律**：禁止覆盖已发布标签，新版本必须用新标签。
- **与篇 15 的对应**：命名规范与不可变标签是仓库治理的一部分，完整清单见 15. 镜像仓库与私有 Registry。

> 在单机上标签漂移往往被本地镜像缓存掩盖，一旦换成多节点，不同节点的缓存不同，问题才会显形。

**速记**：集群里标签必须不可变，关键发布固定 digest。



#### 镜像拉取凭证如何下发

**凭证下发**：私有仓库的拉取凭证以 Secret 形式存在集群里，再通过 Pod 的镜像拉取凭证字段引用，或绑定给某个服务账号由工作负载继承。

- **凭证对象**：凭证本身是一个 Secret，内容是仓库地址与认证信息。
- **引用方式**：在 Pod 模板里声明镜像拉取凭证，或配置到服务账号上批量生效。
- **命名空间**：凭证按命名空间隔离，每个需要拉取的工作负载所在命名空间都要有对应凭证。
- **与 Compose 的差别**：单机时拉取凭证存在执行命令的机器上，集群里则要显式下发到每个会用到的命名空间。

> 凭证下发的常见故障是「镜像在本地能拉、在集群里拉不到」，多半是该命名空间没有对应凭证，或凭证里的仓库地址与镜像地址前缀不一致。

**速记**：凭证存 Secret、经 Pod 声明或服务账号下发，按命名空间隔离。



### 本地与开发环境

#### 本地集群工具 kind、k3d 与 minikube

**三类工具**：kind 与 k3d 都以容器方式在本地跑起集群，minikube 以虚拟机或容器方式提供一个单节点集群，三者的取舍在启动速度、资源占用与贴近真实集群的程度。

- **kind**：把集群节点跑在容器里，适合在本地验证清单与做持续集成，集群形态贴近上游。
- **k3d**：在 Docker 里运行轻量发行版 k3s，启动快、占用小，适合资源有限的开发机。
- **minikube**：提供较完整的单节点集群与常用附加组件，适合学习与功能验证。
- **共同点**：都是本地的学习与验证手段，不等价于生产集群的网络、存储与高可用形态。

> 选择标准是用途：快速验证清单用 kind 或 k3d，需要更多附加能力做学习用 minikube。本节只给定位与取舍，安装命令以各自官方文档为准。

**速记**：kind 贴近上游、k3d 轻量快速、minikube 功能较全，都只是本地验证。



#### Docker Desktop 自带 Kubernetes

**集成的集群**：Docker Desktop 可在本机启用一个单节点 Kubernetes 集群，与 Compose 共用同一个运行环境，切换方便。

- **定位**：面向本地开发与学习，属于 Docker Desktop 的专有能力，纯 Engine 环境不含该特性。
- **与命令行工具的关系**：它把集群嵌在 Desktop 的运行环境里，省去单独安装 kind 或 minikube 的步骤。
- **使用前提**：需要机器上有可用的 Desktop 环境，且开启该特性后占用额外资源。
- **与 kind、k3d 的差别**：一键启用、开箱即用是它的优势，能否模拟多节点集群则是它的局限。

> [!NOTE]
> **提醒内容**：Docker Desktop 自带 Kubernetes 属 Desktop 独有能力，纯 Docker Engine 环境无法使用。写到本地集群时，应明确区分命令行工具与 Desktop 集成这两条路径。

**速记**：Desktop 自带 Kubernetes 是一键启用，但属 Desktop 专有、只到单节点。



#### 本地 Compose 与集群验证的分工

**分工原则**：日常快速迭代用本地 Compose，接近生产的结构与行为验证用本地集群，两者承担不同阶段的验证目标。

- **快速迭代**：改代码、调容器组合、验证依赖关系，Compose 的启动与反馈速度最快。
- **集群验证**：验证清单正确性、探针行为、滚动更新与存储挂载，必须用真实编排环境。
- **差异要提前暴露**：Kubernetes 的 Pod 网络默认全通、探针改变流量、存储语义不同，这些在 Compose 里验证不到。
- **避免双写漂移**：两套声明要明确谁是权威，常见做法是 Compose 服务于开发、集群清单服务于部署，并保持配置来源同源。

> [!TIP]
> **建议内容**：把「本地怎么跑」与「线上怎么跑」的差异列成清单，写在项目说明里。差异清单越明确，迁移时越不容易在最后一刻发现意外行为。

**速记**：迭代用 Compose、验证编排行为用本地集群，差异要显式记录。



### 什么时候不该上 Kubernetes

#### 不适合上集群的情形

**判断标准**：团队规模小、服务数量少、单机资源足够、没有专职运维、业务迭代优先于基础设施，这五条中占多数时，上 Kubernetes 的代价会高于收益。

- **团队规模小**：集群的学习、维护与升级本身要占掉一个人的精力，人手不足时会拖慢业务。
- **服务数量少**：几个服务用 Compose 加反向代理即可覆盖，集群带来的概念与组件成本换不来对应收益。
- **单机资源足够**：负载没到单机上限时，扩容并非当前问题。
- **没有专职运维**：集群不是装完就完，版本升级、证书轮换与故障排查都需要持续投入。
- **迭代优先**：把精力放在业务验证上的阶段，基础设施应尽量简单。

> 上集群的理由应当是具体的规模或可用性需求，而不是别人都在用。用需求驱动选型，而不是用潮流驱动。

**速记**：人少、服务少、单机够用、无专职运维、迭代优先，占多数就别上集群。



#### 三档务实路径

**三档路径**：按规模与需求递增，依次是单机 Compose、单机加反向代理与自动化部署、多机集群，读者按自身处境选择档位。

- **第一档单机 Compose**：一组容器声明在一份文件里，一条命令拉起，适合开发与小型部署。
- **第二档单机加增强**：在 Compose 之上加反向代理统一入口、加自动化部署脚本、加日志与监控采集，把单机的可靠性做到够用。
- **第三档多机集群**：当出现硬性的扩容需求、可用性要求，或服务数量增长到人工难以维护时，再迁移到 Kubernetes。
- **升级触发条件**：明确写出什么条件出现就升级，例如单机资源长期吃满、需要滚动发布且不可中断、需要多团队共用资源。

> [!IMPORTANT]
> **重要内容**：三档路径的价值在于把「要不要上集群」从立场问题变成条件问题。这三档不是必须逐级走完的流程，而是按需求跳档的选项，多数项目会长期停在前两档，先写下触发条件再迁移，比提前上集群并长期维护一套用不满的设施更务实。

**速记**：单机 Compose、单机加增强、多机集群三档，按触发条件跳档。

**知识块**：从容器基础走到编排，需要补齐声明式配置、网络与存储抽象、调度与资源模型、可观测性四块，它们在本篇都只做了导览。

- **网络与存储抽象**：理解服务发现、入口、持久卷与访问模式，是处理跨节点通信与数据的基础。
- **调度与资源模型**：理解 requests 与 limits 如何影响调度与稳定性，与篇 13 的资源约束一脉相承。
- **可观测性**：理解日志、指标与追踪在集群里如何采集，与篇 14 的日志监控衔接。

> 这四块各自都是一门独立的主题，本篇只负责让读者知道下一步该学什么，不展开细节。

**速记**：声明式、网络存储、调度资源、可观测性四块，本篇只做导览。



#### 对象练手顺序

**练手顺序**：按先能跑、再能扩、然后能更新、最后能有状态的顺序，逐一在本地集群里实践本篇提到的对象。

- **第一步跑起来**：部署一个单副本 Deployment 加 Service，理解 Pod 与 Service 的关系。
- **第二步能扩缩**：调整副本数，观察控制器如何补齐或删减 Pod。
- **第三步能更新**：改镜像触发滚动更新，再回滚，理解版本与发布策略。
- **第四步有配置**：用 ConfigMap 与 Secret 注入配置，理解配置外置。
- **第五步有状态**：用 StatefulSet 与 PVC 跑一个有状态服务，理解存储绑定。
- **第六步有入口**：接一个 Ingress，把集群外访问打通，对应容器栈里的 Nginx。

> 练手时优先用本地集群而不是生产集群，对象删错了重建成本很低；这一顺序也与手工迁移的顺序互为印证。

**速记**：跑起来、扩缩、更新、配置、有状态、接入口，六步练完核心对象。
