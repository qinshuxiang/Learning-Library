## 常见问题与踩坑清单

本篇是全系列的排障手册，前 20 篇讲怎么做对，本篇讲做错了怎么查。

组织原则有三条。**按故障现象分类**，不按知识点分类，读者从眼前的报错出发而不是从原理出发。每个考点统一按**现象、根因、处置步骤**展开，处置步骤给出可直接执行的命令。**以交叉引用代替重复讲解**，凡涉及机制展开之处只给结论并指向对应篇章，不在本篇重述。

- 排障的总链条是客户端、守护进程、containerd、runc 四层，先定位故障落在哪一层，再动手改配置，链条见《1. Docker 简介与安装配置》。
- 退出码语义的完整展开见《13. 容器资源限制与运行时约束》，日志与事件的细节见《14. 容器日志与监控》。
- 本篇是索引式速查篇，命令与字段名以官方文档为准，报错文本只给关键词而不逐字引用，避免因版本差异误导。

> [!NOTE]
> **提醒内容**：读到一个现象时，先按本节给出的最短动作把它定位到层，再跳转到对应篇章看原理。跳过定位直接改配置，是排障中最常见的返工来源。

### 安装与守护进程类

安装类故障集中在客户端连不上守护进程、权限不足与守护进程自身起不来三种，多数能在三条命令内定位。

#### 连不上守护进程的四种成因

**连不上守护进程**：指 docker 客户端无法与 dockerd 建立连接，表现为任何子命令都失败，且 docker version 只输出 Client 段而没有 Server 段。

- **成因一，守护进程没起**：最常见。用 systemctl status docker 看服务状态，未运行则 systemctl start docker 拉起，服务器重启后未设开机自启也会如此。
- **成因二，当前用户无权访问套接字**：报错关键词是 permission denied，处理见本节下一个考点。
- **成因三，DOCKER_HOST 或 context 指向错误**：环境变量或 docker context 指向了一台不存在或已下线的引擎，用 docker context ls 与 echo 环境变量核对。
- **成因四，Docker Desktop 或托管虚拟机未启动**：macOS 与 Windows 上引擎跑在托管虚拟机里，图形应用没启动时命令行必然连不上。

```bash
sudo systemctl status docker          # 成因一
docker context ls                     # 成因三
echo "$DOCKER_HOST"                   # 成因三
docker version                        # 只有 Client 段即连不上
```

> 关键判别点：能打印出 Client 段说明客户端本身完好，问题在进程、权限或端点，不必重装客户端。反之命令本身不存在才是安装问题。

**速记**：连不上先查四件事——**服务起没起、人在不在组、端点指哪、Desktop 开没开**。



#### permission denied 与为何不推荐放宽套接字权限

**permission denied**：指当前用户通过 /var/run/docker.sock 访问守护进程时被拒绝，根因是用户不在 docker 组，而该套接字默认属主为 root、权限为 660。

- **正确处置**：把用户加入 docker 组（sudo usermod -aG docker 用户名），再新开一个会话或用 newgrp docker 让组身份生效，仅执行 usermod 而不重登不生效。
- **备选处置**：使用 rootless 模式，或用 docker context 把客户端指向本机以外的引擎，避免在本机提权。
- **临时手段**：sudo docker 可以立刻绕过，但每次都要提权，不适合长期使用，也掩盖了权限模型本身的问题。
- **为何不放宽为 666**：套接字权限一旦对所有人可写，本机任何用户都能挂载宿主根目录进容器，等价于直接获得 root；而且守护进程重启会按自身策略重建套接字、覆盖手工改动的权限，改动并不持久。

> [!WARNING]
> **警告内容**：docker 组成员与 root 等价这一点必须知悉，这不是权限配置疏忽而是设计使然。多人共用的机器应优先用 rootless 或受控的远程 API，而不是把所有人都加进 docker 组，安全细节见《16. 容器安全实践》。

**速记**：加组、重登、组身份才生效；**放宽套接字权限等于给全机发 root，绝不推荐**。



#### 守护进程启动失败先看哪里

**守护进程启动失败**：指 systemctl start docker 返回失败、容器管理面整体不可用，此时客户端报的是连不上而非应用报错，必须先读守护进程自己的日志。

- **第一现场**：systemctl status docker 会截取最后几行失败原因，journalctl -u docker 给出完整日志。
- **常见根因一**：daemon.json 语法错误，或同一选项既写在文件里又写在启动参数里，冲突导致拒绝启动。
- **常见根因二**：配置的监听端口已被占用，详见下一个考点。
- **常见根因三**：存储驱动或数据目录不可用，如 data-root 指向的分区只读、权限错误或磁盘已满。
- **验证配置不改动服务**：dockerd --validate 可在不启动守护进程的前提下校验配置文件语法。

```bash
sudo systemctl status docker
sudo journalctl -u docker --no-pager -n 100
sudo dockerd --validate --config-file=/etc/docker/daemon.json
sudo dockerd --debug                  # 前台运行，启动输出直接打在终端
```

> 检查顺序：先看 status 的失败摘要，再翻 journalctl 找第一个致命错误，最后用 validate 或前台运行复现。跳过日志直接反复 restart 只会重复同一个失败。

**速记**：起不来先读 status 与 journalctl，再用 --validate 验配置，**守护进程的日志才是第一现场**。



#### 重装后旧数据目录不兼容

**数据目录不兼容**：指重装引擎或切换镜像存储后，原有镜像与容器在界面上凭空消失，或守护进程启动时报存储层不兼容，根因是新旧版本使用了不同的镜像存储实现。

- **存储分水岭**：从 Engine 29.0 起全新安装默认使用 containerd 镜像存储，即以 snapshotter 取代传统 overlay2 graph driver；从旧版升级的机器仍沿用旧存储，需手动切换。
- **路径差异**：29.0 起镜像层位于 /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/，容器合并文件系统位于 /var/lib/docker/rootfs/overlayfs/；29.0 之前镜像层在 /var/lib/docker/overlay2/、元数据在 /var/lib/docker/image/。
- **两处根目录**：data-root 管 /var/lib/docker，containerd 的存储另有根路径，只迁移其中一处会造成一半数据可见、一半丢失的假象。
- **已知限制**：containerd 镜像存储不支持与 userns-remap 同时使用，属于官方已知限制。
- **处置**：先 docker info 看清当前 Storage Driver 与 Docker Root Dir，再决定是迁移数据还是导出后重建，确认无误前不要删除任何数据目录。

> [!CAUTION]
> **注意内容**：删除 /var/lib/docker 或 /var/lib/containerd 会永久清除本地镜像、容器与卷，其中可能含未备份的数据。切换存储前先用 docker save 导出镜像、用一次性容器把卷打包成 tar，存储与卷的细节见《4. 镜像分层与存储驱动》与《7. 数据卷与数据持久化》。

**速记**：**29.0 前用 overlay2、29.0 起全新安装用 containerd 存储**；迁移先备份，data-root 与 containerd 根目录要一起考虑。



### 镜像拉取与推送类

拉取类故障先分清是网络、认证、命名还是磁盘，四类的报错关键词完全不同，混在一起排查会绕远路。

#### 拉取超时或连接被重置

**拉取超时**：指 docker pull 长时间卡住或提示超时、连接被重置，根因通常在本机到仓库的链路，而不在镜像本身。

- **第一步看加速是否生效**：docker info 的 Registry Mirrors 段应列出已配置的地址，未出现说明配置未生效或守护进程未重载。
- **第二步测可达性**：直接对镜像站发一个探测请求，判断是网络不通、DNS 失败还是 TLS 证书不被信任。
- **第三步缩小到域名**：若镜像站可达而官方域名不可达，问题在跨境链路，属网络环境问题而非 Docker 配置问题。
- **加速机制**：registry-mirrors 只对 Docker Hub 生效，命中则镜像站回源并缓存，配置写在 daemon.json 里，改完需重载守护进程；本文不推荐任何具体站点，公共源地址随时变动，用时按当前云厂商文档填写。

```bash
docker info | grep -A5 "Registry Mirrors"
curl -I https://your-mirror.example.com/v2/
sudo journalctl -u docker --no-pager -n 50
```

> 需要区分的两种情况：拉取慢但仍成功属链路问题，拉取在某一层反复重试后报错多属镜像站回源失败。两者都以换源或换网络收尾，而不是反复重试同一条命令。

**速记**：超时排查三步——**info 看 mirrors 是否生效、curl 测可达、再判断是链路还是域名**；只讲机制不推荐站点。



#### unauthorized 与 denied 的差别

**unauthorized**：表示未认证或凭据已失效，服务端不知道来者是谁。**denied**：表示身份已确认但权限不足，服务端知道来者是谁而拒绝其访问目标仓库。

- unauthorized 的处置：docker login 到目标仓库，确认凭据助手与 ~/.docker/config.json 是否写入了新凭据，凭据过期或多因素认证改动后需重新登录。
- denied 的处置：登录状态本身有效，问题在组织与仓库的授权，需由仓库管理员授予 push 或 pull 权限，改本机配置无用。
- 私有仓库对未登录用户有时返回 not found 而非 unauthorized，这是出于不泄露仓库是否存在的考虑，不要误判成镜像不存在。
- 判别顺序：先看是否已 login 且凭据未过期，再看该账号是否被授权访问该命名空间。

```bash
docker login registry.example.com
docker logout registry.example.com    # 排除旧凭据干扰
cat ~/.docker/config.json
```

> 一句话分辨：unauthorized 是**没登录或凭据错**，denied 是**登录了但没被授权**。前者自己能修，后者要找仓库管理员。

**速记**：**unauthorized 补登录，denied 找授权**；私有仓库的 not found 可能是未登录的伪装。



#### 标签不存在

**标签不存在**：指拉取时提示找不到清单，关键词是 manifest unknown 或 not found，根因是请求的镜像名、标签或平台三者之一对不上。

- 标签拼写：核对仓库页面上的标签，latest 只是默认标签名，并不保证存在，也不等于最新版。
- 命名空间与仓库地址：确认镜像路径完整，缺主机名与命名空间时默认落在 Docker Hub 的官方命名空间。
- 平台不匹配：多架构镜像索引里没有目标平台时，也会以找不到清单的形式报错，用 imagetools inspect 确认索引包含哪些平台。
- 私有仓库未登录：如前述，可能以 not found 呈现，先排除认证。

```bash
docker manifest inspect nginx:1.27              # 看清单与平台
docker buildx imagetools inspect nginx:1.27     # 看多架构索引
docker pull nginx:1.27-alpine
```

> 排查心法：把报错里的完整镜像引用原样复制出来核对，多数问题出在少写了主机名、多写了斜杠或标签大小写不符，标签是区分大小写的。

**速记**：找不到标签查三处——**标签拼写、完整命名、平台索引**；latest 不保证存在。



#### 推送到自建仓库必须带主机名

**推送目标**：由本地镜像名决定，镜像名不带主机名时默认目标是 Docker Hub 的官方命名空间，这是推送到自建仓库时最常见的失败原因。

- 现象：push 到自建仓库后仓库里没有镜像，或提示对 Docker Hub 无权限。
- 根因：本地镜像只叫 myapp:1.0，push 被理解为推到 Docker Hub，而不是推到自建仓库。
- 处置：先 docker tag 成 完整主机名/命名空间/名字:标签 的完整形式，再 login 到该主机，最后 push 完整名。
- 证书情形：自建仓库使用自签证书或 HTTP 时，需把证书放到守护进程信任的位置，或在 daemon.json 的 insecure-registries 中放行该主机，配置细节见《15. 镜像仓库与私有 Registry》。

```bash
docker tag myapp:1.0 registry.example.com/team/myapp:1.0
docker login registry.example.com
docker push registry.example.com/team/myapp:1.0
```

> [!CAUTION]
> **注意内容**：为了让 HTTP 仓库可用而把它加入 insecure-registries，等于允许明文传输与不校验证书的镜像拉取，中间人可替换镜像内容。仅在完全可控的内网中这样做，公网环境应改用受信任证书。

**速记**：**镜像名不带主机名就默认推 Docker Hub**；先 tag 全名、再 login、最后 push。



#### 磁盘空间不足与拉取限流

**磁盘空间不足**：指拉取到中途失败并提示设备无剩余空间，镜像层解压需要额外空间，可用空间不足一层也会中断。**拉取限流**：指公共仓库对拉取频率设限，超限时请求被拒绝而非网络中断。

- 磁盘处置：先 docker system df 看四类占用的总量与可回收量，再按无害到有害的顺序清理，顺序见本篇清理与磁盘回收类。
- 判定落盘位置：df 看 /var/lib/docker 所在分区，containerd 存储情形下还要看 /var/lib/containerd 所在分区。
- 限流表现：提示请求过多，通常伴随重试建议，属服务端策略而非本机故障。
- 限流缓解：登录账号后拉取、使用镜像加速的缓存、在 CI 中复用已拉取的层、避免在流水线里重复拉同一镜像；具体配额以官方文档为准，本文不写具体数值。

```bash
docker system df
docker system df -v
df -h /var/lib/docker
```

> 两者的判别很简单：磁盘不足在拉取某一层时报错且本地已有层完好，限流在请求发起阶段就被拒绝。前者清磁盘，后者换策略。

**速记**：**拉不动先 df 看账再清理；被限流靠登录、缓存与减少重复拉取**，额度以官方为准。



### 构建类

构建期问题与运行期问题的报错格式不同，先分清阶段再排查。构建由上层的 BuildKit 承担，缓存与多平台能力都来自它，详见《1. Docker 简介与安装配置》。

#### 构建上下文过大

**构建上下文**：指 docker build 命令末尾那个目录的全部内容，它会被打包发送给构建引擎，而不是只发送 Dockerfile。

- **现象**：构建第一行输出会提示 transferring context 并附带一个体积，这个数字动辄数百兆时说明上下文过大。
- **根因**：在包含 node_modules、.git、构建产物或数据集的大目录里直接构建。
- **处置一**：把构建上下文缩小到实际需要的最小目录，Dockerfile 用 -f 单独指定，而不是把上下文指向项目根以外的层。
- **处置二**：在上下文根写 .dockerignore 排除无关内容，排除发生在传输之前，比事后清理有效。

```bash
docker build -t myapp:1.0 .
cat .dockerignore
```

```text
 => [internal] load build context
 => => transferring context: 812.44MB
```

> 体积提示是判断上下文健康度的最快指标。同一个项目把它从数百兆压到几兆，构建时间往往立刻下降一个量级，这一点比换机器更有效。

**速记**：**上下文是整目录、先传输后构建**；看第一行 transferring context 的大小，用 .dockerignore 和缩小上下文两级处理。



#### .dockerignore 写错把密钥或大目录带进镜像

**.dockerignore**：是构建上下文的排除清单，语法类似 .gitignore，按行写模式，路径相对上下文根，支持通配符与叹号反向例外。

- **现象**：镜像体积异常大，或容器里出现了 .env、.pem、node_modules、.git 等本不该发布的内容。
- **常见写法错误**：模式写成相对 Dockerfile 而非上下文根，或用错了通配层级导致未能匹配；行首叹号表示重新纳入，误加会把已排除的目录又放回来。
- **高危组合**：Dockerfile 里用 COPY . . 复制全部内容，而排除清单没覆盖密钥文件时，密钥会直接进入镜像层。
- **验证手段**：docker history 看各层体积，或起一个容器后用 ls 检查可疑路径是否真的存在。

```text
.git
node_modules
.env
*.pem
dist
```

> [!WARNING]
> **警告内容**：密钥一旦写进镜像层，即使后续指令里删掉文件，它在更早的层里依然存在，可被完整提取。发现后应把该密钥视为已泄露并立即轮换，镜像也必须重新构建，密钥管理的正确做法见《12. 环境变量、配置注入与密钥管理》。

**速记**：**.dockerignore 相对上下文根、叹号是反向例外**；COPY . . 配遗漏的排除清单等于把密钥打进镜像，泄露后必须轮换。



#### COPY 失败

**COPY 失败**：指构建时提示源文件找不到，根因是 COPY 的源路径相对构建上下文，而不是相对 Dockerfile 所在位置。

- **源路径规则**：源必须位于上下文之内，且不能用宿主机的绝对路径，写 /home/user/app 这类路径在构建容器里不存在。
- **被排除的源**：目标文件若被 .dockerignore 匹配，等于在上下文里不存在，同样报找不到。
- **大小写与拼写**：Linux 文件系统区分大小写，src 与 Src 不是一回事。
- **处置**：调整构建命令末尾的上下文路径，或把 Dockerfile 与需要复制的文件放进同一上下文树，再用 ./ 开头的相对路径书写。

```dockerfile
COPY package.json package-lock.json ./
COPY ./src /app/src
```

> 常见误判是把 Dockerfile 所在目录当成上下文。若用 -f 指定了另一个位置的 Dockerfile，上下文仍是命令末尾那个点，两者可以不在同一目录，这正是 COPY 找不到文件的典型场景。

**速记**：**COPY 源相对上下文、绝对路径无效、被 ignore 的等于不存在**；先确认上下文根在哪，再核对大小写。



#### 缓存不命中

**缓存不命中**：指每次构建都从头重跑，尤其是依赖安装步骤，根因是缓存按层比对，被改动层之后的所有层都会失效。

- **顺序问题**：先 COPY 全部源码再装依赖，源码一改依赖层即失效，正确顺序是先复制依赖清单、安装依赖、最后复制源码。
- **命令问题**：构建命令带了禁用缓存的开关，或基础镜像标签指向 latest 导致基础层频繁变化。
- **环境问题**：缓存被清理过，或多平台构建时未共享缓存，不同平台各自一套。
- **处置**：调整 Dockerfile 指令顺序，用挂载型缓存保存包管理器目录，用 buildx 的缓存导出导入在 CI 间复用，然后用构建输出的 CACHED 标记确认命中情况。

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
```

> 判据是构建输出里每一步是否标注为命中缓存。若安装依赖那一步显示重新执行，问题几乎总在它之前有一条会变的指令，最典型的就是过早的 COPY 源码。

**速记**：**缓存按层比对，改动点之后全失效**；依赖清单先复制、依赖先安装、源码最后复制，构建输出看 CACHED。



#### 构建期间连不上网络

**构建期网络**：指 RUN 指令执行时的网络环境，它默认走构建器的网络，与宿主 shell 的代理变量无关。

- **现象**：apt、npm、pip 之类的安装步骤超时，或域名解析失败。
- **代理处置**：把代理地址用构建参数传入，并在 Dockerfile 里设为环境变量，代理变量需对构建期与运行期分别设置。
- **网络处置**：Linux 上可用构建器的宿主网络选项让本次构建直接复用宿主网络，该能力属 BuildKit，传统构建器不支持。
- **DNS 处置**：解析失败时检查守护进程的 DNS 配置与运行参数，而不是只改宿主。
- **源处置**：基础镜像自带的软件源不可达时，替换为可达的源或预先在基础镜像里装好依赖。

```bash
docker build --build-arg http_proxy=http://host:port \
  --build-arg https_proxy=http://host:port -t myapp:1.0 .
docker build --network=host -t myapp:1.0 .
```

> 判别点在于失败发生在解析域名还是连接地址。解析失败属 DNS，连接超时属链路或代理，报错关键词不同，处置路径也不同。

**速记**：**构建期网络独立于宿主 shell**；代理走构建参数、网络可临时用宿主、DNS 查守护进程配置。



#### 多平台构建与架构不匹配

**架构不匹配**：指镜像构建的 CPU 架构与运行机器不一致，表现为在另一台机器上启动即失败并提示可执行文件格式错误。

- **现象一**：本地用多平台构建指定了非本机架构，构建机拉不到对应架构的基础镜像。
- **现象二**：在 x86 机器上构建的镜像拿到 arm 机器上运行，容器启动即退出。
- **判定**：docker inspect 镜像看 Architecture 与 Os 两个字段，与运行机器的实际架构比对。
- **处置**：用 buildx 指定目标平台构建多架构镜像并推送索引；本地跨架构运行依赖模拟层，需先注册模拟器，其性能明显低于原生，只适合验证不适合压测。

```bash
docker inspect -f '{{.Architecture}} {{.Os}}' myapp:1.0
docker buildx build --platform linux/amd64,linux/arm64 -t myapp:1.0 .
docker version --format '{{.Server.Arch}}'
```

> 常见的隐藏来源是基础镜像本身：在同一份 Dockerfile 下，不同架构的基础镜像标签可能指向不同内容，构建成功不代表目标架构下能跑通，跨平台交付必须显式指定平台并实测。

**速记**：**inspect 看 Architecture 与 Os**；跨平台用 buildx 按平台构建，模拟运行只用于验证。



### 容器启动即退出类

容器退出码由主进程的终止状态决定，先读退出码能立刻把问题分成几类。退出码语义、信号编号换算与内存限制的完整展开见《13. 容器资源限制与运行时约束》。

#### 退出码 0

**退出码 0**：表示容器内主进程正常结束，本身不是错误。当服务本应常驻却立刻显示已退出且退出码为 0 时，问题在命令写错或进程转后台，而不是程序崩溃。

- **情形一**：把一次性命令当作常驻服务启动，如用镜像跑了一条 echo 或 --help，执行完自然退出。
- **情形二**：入口命令被写成了可执行文件的错误子命令，程序认为已正常完成任务。
- **处置**：先用 docker logs 看主进程输出了什么，再用 docker inspect 看实际生效的入口与命令字段，确认服务型进程是否前台运行。

```bash
docker logs --tail 100 web
docker inspect -f '{{.Config.Entrypoint}} {{.Config.Cmd}}' web
```

> 记住一条判据：**退出码为 0 说明程序自己认为任务完成了**，排查方向是命令与启动方式，而不是程序内部报错，后者会给出非 0 退出码。

**速记**：退出码 0 是**正常结束**；服务常驻却秒退，查启动命令是否前台、入口是否写错。



#### 退出码 1

**退出码 1**：表示应用自身以失败状态退出，是最常见的一般性错误码，原因必须从日志里找。

- **第一步**：docker logs --tail 100 看最后一段输出，配置错误、端口占用、连接数据库失败多在此暴露。
- **第二步**：docker inspect 读 State.ExitCode 与 State.Error 确认退出码与守护进程记录的错误。
- **第三步**：若日志为空，说明应用把错误写进了容器内文件或缓冲未刷新，处置见本篇日志与诊断类。
- **处置**：按日志给出的具体原因修正配置或依赖，不要凭退出码猜原因。

```bash
docker logs --tail 100 web
docker inspect -f '{{.State.ExitCode}} {{.State.Error}}' web
```

> 易混点：退出码 1 也可能是应用未捕获的异常导致进程终止，与退出码 0 的区别正是「程序是否认为自己失败」。看到 1 就先找日志，看到 0 才去查命令。

**速记**：**退出码 1 看日志**；多数是配置或依赖问题，日志为空时转去排查日志驱动与缓冲。



#### 退出码 137

**退出码 137**：等于 128 加 9，表示主进程被 SIGKILL 强制杀死，其来源只有两类，必须用字段区分而不是凭猜测。

- **来源一，内存超限**：容器内存用量触及硬上限后由内核的 OOM 机制杀死进程，inspect 的 State.OOMKilled 为真。
- **来源二，停止超时**：docker stop 发出 SIGTERM 后应用未在宽限期内退出，守护进程补发 SIGKILL，此时 OOMKilled 为假。
- **处置内存超限**：调高内存上限或修正应用的内存泄漏与缓存膨胀，内存限制与页面缓存口径见《13. 容器资源限制与运行时约束》。
- **处置停止超时**：确认应用是否处理 SIGTERM，或启动时加大停止宽限期；容器内 PID 1 未注册处理函数的信号会被内核忽略，这是 Linux 既有规定。

```bash
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' web
docker stats --no-stream web
docker run -d --stop-timeout 30 --name slow-api myapp:1.0
```

> [!WARNING]
> **警告内容**：用 docker kill 或 docker rm -f 结束容器同样会得到 137，但这是人为强杀而非故障。排查前先回忆是否手工停过该容器，否则会把正常操作误读成内存问题。

**速记**：**137 是 SIGKILL，看 OOMKilled 分两类**；为真是内存超限，为假是停止超时；手工强杀也会得 137。



#### 退出码 139 与 143

**退出码 139**：等于 128 加 11，表示进程收到 SIGSEGV 段错误而崩溃。**退出码 143**：等于 128 加 15，表示进程收到 SIGTERM 后退出。

- 139 的根因：原生程序访问了非法内存，常见于架构不匹配、底层库版本不兼容、栈溢出或内存被外部改写。
- 139 的处置：确认镜像架构与运行机器一致，核对基础镜像与依赖库版本，必要时用调试符号或核心转储定位到具体调用。
- 143 的根因：容器被要求优雅停止，若应用自行处理了 SIGTERM 并正常收尾，退出码通常是 0；出现 143 说明进程是被信号直接终止的，或它把信号透传成了退出状态。
- 143 的处置：属正常停止路径，不必当作故障；若进程本不该被停，则去查是谁发了终止信号，常见来源是编排层与手动 stop。

```bash
docker inspect -f '{{.State.ExitCode}}' web
docker inspect -f '{{.Architecture}} {{.Os}}' web
docker events --since 10m
```

> 判别要点：139 是程序自己出错，属于必须修的真故障；143 多数是被动终止，属于预期行为。把 143 当成崩溃去改代码是常见误判。

**速记**：**139 是段错误，查架构与库版本；143 是收到 SIGTERM 的被动终止，通常不必修**。



#### 退出码 126 与 127

**退出码 126**：表示命令存在但没有执行权限。**退出码 127**：表示找不到要执行的命令。

- 126 的根因：入口脚本或二进制缺少可执行位，多由宿主与容器的权限位不同步、复制时丢了执行位导致。
- 126 的处置：给入口文件补上可执行位，或在 Dockerfile 里显式赋予权限后重新构建。
- 127 的根因：入口或命令拼写错误、镜像里根本没装该程序、脚本首行解释器路径不存在，或脚本使用了 Windows 换行导致解释器解析失败。
- 127 的处置：用 docker run 加一个临时入口列出镜像内容，核对目标程序是否真实存在及其绝对路径。
- 两者的共同先手：docker inspect 看实际生效的 Entrypoint 与 Cmd，再用 exec 或临时入口确认文件系统里的可执行文件。

```bash
docker inspect -f '{{.Config.Entrypoint}} {{.Config.Cmd}}' web
docker run --rm --entrypoint /bin/sh myapp:1.0 -c "ls -l /app"
```

> 区分方法：**126 是找到了但跑不起来，127 是压根没找到**。两者都先确认入口字段，再看文件是否真的在镜像里，不要先怀疑 Docker 本身。

**速记**：**126 无执行权限、127 找不到命令**；先看 Entrypoint 与 Cmd，再核对文件是否在镜像里。



#### 进程转后台造成的成功退出

**进程转后台**：指入口进程启动后 fork 出后台进程、自己立即返回，此时容器的主进程已结束，容器随之退出，退出码为 0，而真正的服务进程可能仍在或被一并回收。

- **现象**：容器启动即显示已退出，退出码为 0，日志里似乎一切正常，但端口无人监听。
- **根因**：容器模型要求主进程前台运行，把守护进程式的服务直接塞进容器，主进程一返回容器就结束。
- **处置一**：给启动命令加前台运行的开关，例如让 Web 服务器禁用守护模式、让进程管理工具以非守护方式运行。
- **处置二**：检查入口脚本是否用 exec 形式启动真正的主进程，用 shell 包装而不 exec 会让信号与生命周期脱节，信号处理细节见《3. 容器生命周期与常用命令》。
- **处置三**：需要多个进程时拆成多个容器并用网络或 Compose 组合，不要在容器里塞进程管理器。

```bash
docker logs web
docker exec web ps -ef
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' web
```

> [!IMPORTANT]
> **重要内容**：退出码 0 配上「服务不可用」是这一类问题的固定签名。看到这个组合，第一反应应是前台进程转后台，而不是应用崩溃，这与退出码 1 的排查路径完全相反。

**速记**：**主进程返回即容器结束**；退出码 0 却服务不通，查是否守护式转后台，命令要前台运行且入口用 exec。



### 网络类

网络类故障的定位顺序是容器内先在容器内确认监听，再在宿主确认发布，最后在外部确认可达，逐层缩小。网络机制见《8. 容器网络基础与端口映射》，容器互访见《9. 自定义网络与容器互联》。

#### 容器内能出网但外部访问不到

**外部访问不到**：指容器内进程可以访问外网，但从宿主机或其他机器访问容器提供的服务失败，根因在发布与监听两个环节。

- **检查一，服务监听地址**：进程若只绑定 127.0.0.1，则只有容器内部的回环可访问，容器外一律不通，应改为监听全部地址。
- **检查二，端口是否发布**：创建时未加发布参数或发布的宿主端口与预期不一致，用 docker ps 的端口列与 docker port 核对。
- **检查三，发布绑定的宿主地址**：发布时写成只绑 127.0.0.1 时，仅宿主本机可访问而其他机器不可访问，公网访问需要绑定全部地址。
- **检查四，宿主与云侧防火墙**：宿主防火墙规则、云服务器安全组任一拦截都会造成外网不可达，而容器内部一切正常。

```bash
docker exec web ss -lntp
docker port web
docker ps --format 'table {{.Names}}\t{{.Ports}}'
```

> 判别顺序建议固定为容器内、宿主、外部三级。容器内 ss 能听到端口而外部不通，问题必在发布或防火墙；连容器内都听不到，问题在应用自身。

**速记**：**先看应用绑没绑全部地址，再看端口发没发布、绑的是哪个宿主地址，最后查防火墙与安全组**。



#### 容器间用服务名解析失败

**服务名解析**：指容器之间按名字互相访问依赖 DNS，只有接入同一自定义网络的容器才有内置的名称解析，默认 bridge 网络不提供该能力。

- **根因一**：两个容器不在同一自定义网络，各自接入不同网络时彼此看不到。
- **根因二**：名字写错，应按服务名或容器名访问，而不是宿主名或镜像名。
- **根因三**：使用默认 bridge 网络，该网络下只能靠 IP 互访且没有自动名称解析。
- **处置**：用 network inspect 看目标容器接了哪些网络与别名，用 exec 加 getent 或 ping 在源容器内实测解析，必要时起一个同网络的一次性容器做交叉验证。

```bash
docker network inspect app-net
docker exec api getent hosts db
docker run --rm -it --network app-net nicolaka/netshoot sh
```

> 一个高效起手式是起一个接入同网络的临时工具容器去解析与连接目标。它排除了源容器自身配置的干扰，能直接判定是网络拓扑问题还是应用问题。

**速记**：**同自定义网络才有名字解析，默认 bridge 没有**；用 network inspect 看归属、getent 在源容器实测。



#### 改了端口映射不生效

**端口映射不可变**：端口、挂载、网络等配置在容器创建时固化，重启容器不会重建这些配置，改端口必须删除并重建容器。

- **现象**：改了发布参数后行为不变，仍按旧端口工作。
- **根因**：docker restart 只是重新启动同一个容器，沿用创建时的配置；docker update 也不能修改端口映射。
- **处置**：删除旧容器后按新参数重新创建；用 Compose 时改动会触发重建，必要时显式要求强制重建。
- **确认手段**：docker inspect 的 NetworkSettings.Ports 与实际生效的发布规则比对，而不是回看自己敲过的命令。

```bash
docker rm -f web
docker run -d --name web -p 8080:80 nginx
docker compose up -d --force-recreate web
```

> 这条与「改了配置总要先重启」的直觉相反：**端口映射改不了只能重建**。先重启再排查会浪费一轮时间，直接 inspect 看实际值最快。

**速记**：**端口映射创建时固化，restart 改不了**；改端口或绑定地址要删容器重建，Compose 用 up 触发重建。



#### 容器访问宿主机失败

**访问宿主机**：指容器内需要连接宿主上运行的服务，路径因平台与网络模式而异，混用会直接连不通。

- **Linux 常见做法**：给容器追加一条指向宿主网关的映射，让容器内可用一个固定名字访问宿主服务。
- **Docker Desktop 情形**：托管虚拟机场景下已内置可访问宿主的名字，Linux 容器直接使用即可；Desktop 下的宿主网络能力自 4.34 起可选择性开启，且只覆盖传输层，详情见《8. 容器网络基础与端口映射》。
- **宿主网络模式**：容器与宿主共享网络命名空间时可直接用回环地址访问宿主服务，该模式牺牲网络隔离，且非 Linux 平台的行为不同。
- **常见遗漏**：宿主服务只监听了回环地址，则无论用哪种方式从容器侧访问都不通应先让宿主服务监听可被容器触达的地址。

```bash
docker run --rm --add-host host.docker.internal:host-gateway \
  alpine ping -c1 host.docker.internal
docker run --rm --network host alpine wget -qO- http://127.0.0.1:8000
```

> 平台差异是易错点：同样一条 host.docker.internal 写法在 Desktop 上开箱可用，在纯 Linux 引擎上需要显式追加网关映射才可用，脚本跨平台时要按平台分支处理。

**速记**：**Linux 用网关映射，Desktop 用内置宿主名，共享网络时用回环**；宿主服务还得监听可被触达的地址。



#### DNS 解析异常

**解析异常**：指容器内域名解析失败或解析到过期地址，根因是容器内的解析配置在创建时生成，之后宿主的变化不会同步到已运行的容器。

- **生成机制**：守护进程启动容器时生成 hosts 与 resolv.conf，指向内置的解析服务；宿主解析配置后续变化不会改写已运行容器内的文件。
- **处置一**：在容器内直接查看解析配置，确认上游服务器是否是预期值。
- **处置二**：新容器可用运行参数指定解析服务器，或在守护进程配置里设全局值，但都只对之后创建的容器生效。
- **处置三**：内网域名需要在容器内可解析时，优先在守护进程层面配置内部解析服务器，而不是逐个容器传参。
- **使用自定义网络时**：内置解析服务在自定义网络中同时承担服务名解析与外部转发，接入错误网络会造成外部域名也解析不到。

```bash
docker exec web cat /etc/resolv.conf
docker run --dns 10.0.0.53 --rm alpine nslookup example.com
docker network inspect app-net -f '{{range .Containers}}{{.Name}} {{end}}'
```

> 反直觉之处在于已经跑着的容器不会感知宿主解析配置的变化。遇到解析突然异常，先看容器内文件是不是旧值，再决定是否重建容器，改宿主文件往往无效。

**速记**：**解析配置创建时生成、之后不同步**；查容器内 resolv.conf，改配置只对新容器生效，必要时重建。



#### 端口已分配冲突

**端口冲突**：指容器启动时提示端口已被分配，根因是目标宿主端口已被其他进程或其他容器占用。

- **第一步**：用 socket 工具查宿主端口的占用者，区分是普通进程还是 Docker 的端口代理。
- **第二步**：用 docker ps 与 docker port 检查是否已有容器发布了同一端口，同名旧容器未清理是最常见来源。
- **第三步**：确认占用者用途后再处理，属于闲置容器的停掉或删除，属于系统服务的换端口或换发布端口。
- **处置**：换一个宿主端口发布，或停止并清理占用方；不要直接杀未知进程，先确认它是不是宿主关键服务。

```bash
sudo ss -lntp | grep 8080
docker ps --format 'table {{.Names}}\t{{.Ports}}'
docker port web
```

> [!CAUTION]
> **注意内容**：直接对占用端口的进程执行强杀有风险，它可能是宿主上另一个业务服务。先按进程名与启动命令确认身份，属于容器的走 Docker 命令清理，属于宿主服务的应改端口而不是杀进程。

**速记**：**冲突先 ss 找占用，再用 ps 与 port 找同端口容器**；确认身份后再释放，不要盲杀进程。



### 存储与权限类

存储类故障的两个高频来源是绑定挂载的路径与属主，以及删卷操作的不可逆后果。挂载类型与权限细节见《7. 数据卷与数据持久化》。

#### 绑定挂载路径不存在

**路径不存在**：指指定的宿主源路径在宿主上不存在，两种语法的行为相反，这是实战中最容易踩到的差异。

- **短语法行为**：用冒号分隔的短语法在源路径缺失时自动创建一个空目录，容器照常启动，路径拼写错误被静默掩盖。
- **长语法行为**：显式写法默认直接失败并提示绑定源路径不存在，把错误暴露在启动阶段。
- **处置**：核对源路径是否为绝对路径且真实存在；希望缺失即失败时用长语法，需要自动创建时给长语法加自动建源选项。
- **权限连带问题**：自动建出的空目录属主是 root，若容器以非 root 运行仍会写入失败，见本节权限部分。

```bash
docker run --rm --mount type=bind,src=/srv/app/html,dst=/usr/share/nginx/html nginx:1.27
docker run --rm --mount type=bind,src=/srv/app/html,dst=/srv,readonly alpine ls /srv
```

> [!WARNING]
> **警告内容**：短语法自动建目录看似省事，实则会把「路径写错」伪装成「目录为空」，容器正常启动却读不到配置，这类故障排查成本远高于启动即失败。生产脚本推荐用长语法让缺失路径直接报错。

**速记**：**短语法自动建目录、长语法默认报错**；生产用长语法暴露拼写错误，自动建出的目录属主是 root。



#### 容器内写入被拒绝

**写入被拒**：指容器内进程对挂载目录的写操作返回权限不足，根因是容器内进程的用户标识与宿主文件的属主不匹配。

- **判定**：用 exec 在容器内执行 id 看进程的用户与组，再在宿主用 ls -ln 看目标目录的属主数字标识，两者不一致即为此类。
- **处置一**：启动容器时指定运行用户，使其与宿主目录属主对齐，这是最干净的做法。
- **处置二**：在宿主侧把目录属主改为容器内使用的用户标识，适合容器用户固定的场景。
- **处置三**：启用强制访问控制（如 SELinux）的系统上还需为挂载加标签，否则文件权限正确仍会被策略拦截。
- **不要做**：把宿主目录改成所有人可写来绕过，这等于放弃权限边界，且会在共享机器上引入风险。

```bash
docker exec web id
ls -ln /srv/app/data
docker run -d -u 1000:1000 -v /srv/app/data:/data myapp:1.0
```

> 判别关键是把「属主不匹配」与「只读挂载」分开：只读挂载下任何用户都写不了，报错也是权限不足，先用 inspect 看挂载是否带了只读选项，再查属主。

**速记**：**exec 看 id、宿主看 ls -ln，两边对不齐就写不进去**；用运行用户或宿主属主对齐，别改成所有人可写。



#### 宿主机改了配置文件不进容器

**配置不生效**：指在宿主编辑了被挂载进容器的配置文件，容器内读到的仍是旧内容，根因通常是单文件挂载与编辑器的保存方式共同作祟。

- **根因一，inode 被替换**：多数编辑器保存时先写临时文件再改名替换，宿主上文件已是新 inode，而容器的挂载仍指向旧 inode，内容自然不变。
- **根因二，应用未重载**：文件确实更新了，但进程只在启动时读一次配置，需要显式重载或重启。
- **处置一**：改为挂载整个配置目录而不是挂载单个文件，目录挂载不受改名影响。
- **处置二**：编辑后重启容器，或对应用发送重载信号，具体方式取决于应用本身。
- **确认手段**：exec 进容器读该文件内容，别只看宿主文件的时间戳。

```bash
docker exec web cat /etc/nginx/nginx.conf | head
docker inspect -f '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}' web
docker restart web
```

> 这条之所以经典，是因为宿主侧一切正常：文件确实改了、时间戳也新，唯独容器里是旧的。判定只看容器内内容，不看宿主文件。

**速记**：**单文件挂载碰上编辑器替换 inode 会读旧内容**；改成挂目录，或改完重启容器，判定以容器内文件为准。



#### 卷删了数据没了

**卷删除**：指清理命令删除了数据卷，卷中的数据不进入回收站也无法恢复，四种操作风险相同。

- **不可逆操作一**：Compose 的 down 加数据卷选项，会删除项目中定义的命名卷，属不可逆的数据丢失风险。
- **不可逆操作二**：卷清理命令默认只清匿名卷，加全部选项后连未被容器引用的命名卷一并删除。
- **不可逆操作三**：删除容器时附带删除卷的选项，删掉的是该容器的匿名卷，命名卷与绑定挂载不受影响。
- **不可逆操作四**：单独的卷删除命令按名删除指定卷，常用于脚本里的重建流程，写错卷名即删错数据。
- **处置**：删除前先卷列表与卷详情逐个确认，把要保留的卷先用一次性容器打包成 tar。

```bash
docker volume ls
docker volume inspect mysql-data
docker run --rm -v mysql-data:/from:ro -v "$PWD":/to \
  alpine sh -c "cd /from && tar czf /to/mysql.tgz ."
```

> [!WARNING]
> **警告内容**：卷的生命周期独立于容器，容器停了而卷还在时，卷会被判定为未被引用，此时清理命令会连它一起删。数据库类数据务必先备份再清理，备份与恢复手法见《7. 数据卷与数据持久化》。

**速记**：**down 带卷选项、卷清理加全部、删容器带卷、按名删卷，四个都不可逆**；删前备份成 tar。



#### 磁盘满先定位

**磁盘满**：指宿主提示设备无剩余空间，Docker 侧的可能来源有日志、镜像层、卷与构建缓存四类，先定位再清理。

- **总账**：docker system df 给出四类占用的总量与可回收量，是第一眼要看的东西。
- **明细**：加展开选项后逐项列出每个镜像、容器、卷的占用，能直接看出谁是大头。
- **日志类嫌疑**：单容器日志异常大时，多半是默认日志驱动未配轮转，处置见本篇日志与诊断类。
- **卷类嫌疑**：卷占用大但业务数据量不大时，检查是否有容器往卷里写了临时文件或缓存。
- **确认分区**：用 df 看 Docker 数据所在分区，注意新存储下镜像层与容器数据可能落在不同分区。

```bash
docker system df
docker system df -v
df -h /var/lib/docker
```

> 清磁盘的正确姿势是先看账再动手：不看 df 直接跑一键清理，既可能清不掉真正的大头，又可能误删要保留的对象。清理顺序见本篇清理与磁盘回收类。

**速记**：**磁盘满先 system df 看四类账，再定位是日志、镜像层、卷还是构建缓存**，最后才动手清。



### Compose 类

Compose 类故障的关键工具是一个命令：配置展开子命令，它把多文件合并、变量插值后的最终配置原样打印，排障时先用它对齐预期。Compose 基础见《10. Docker Compose 入门》，进阶见《11. Docker Compose 进阶与实战》。

#### yaml 缩进与语法报错

**语法报错**：指 Compose 文件解析失败，绝大多数来自缩进与标点，而不是字段名写错。

- **缩进规则**：YAML 用空格缩进且不允许制表符，混用会直接解析失败；同级键必须对齐。
- **冒号规则**：键值对中冒号后必须有一个空格，值里含冒号时要用引号包起来。
- **定位手段**：用配置展开子命令校验并打印最终结构，报错会给出出错行号，比肉眼找缩进快得多。
- **常见来源**：从网页或聊天工具复制配置时带了不可见字符，或全角空格混入缩进。

```bash
docker compose config
docker compose -f compose.yaml config --quiet
```

> 一个稳妥习惯：改完 Compose 文件先跑一次配置展开，它既校验语法又展示合并结果，成功后再执行启动命令，能把语法问题与运行问题彻底分开。

**速记**：**YAML 只用空格、冒号后带空格、含冒号的值加引号**；用配置展开子命令定位出错行。



#### version 字段废弃告警

**version 字段**：是 Compose 文件旧版规范里声明文件格式版本的顶层字段，当前规范已废弃该字段，写上会打印告警但解析照常进行。

- **现象**：启动时提示该顶层属性已过时。
- **根因**：新版 Compose 按文件本身推断格式，不再需要显式声明版本。
- **处置**：直接删除顶层 version 字段，配置文件与行为都不受影响。
- **连带影响**：删除后若仍出现告警，检查是否引用了外部文件或旧模板，那些文件里可能还留着该字段。

```yaml
services:
  web:
    image: nginx:1.27
    ports:
      - "8080:80"
```

> 别把告警当成错误：它不影响启动。但也不要留着，规范的 Compose 文件不应包含废弃字段，长期保留会在工具链升级后变成真错误。

**速记**：**顶层 version 已废弃，写了只告警、删掉即可**，新版按文件自动推断格式。



#### 服务起不来但没报错

**静默不起**：指启动命令返回成功、也没有明显报错，但目标服务没有运行，根因多藏在依赖条件、健康检查与配置档三处。

- **排查一，状态与日志**：先用状态子命令看每个服务是运行、退出还是等待中，再对异常服务单独看日志。
- **排查二，健康检查过严**：依赖条件要求被依赖服务健康时才启动，健康检查阈值太紧或未给启动预留时间，会让主服务一直等不到条件满足。
- **排查三，配置档未启用**：标记了配置档的服务默认不启动，需要显式启用对应档位。
- **排查四，重启循环**：服务不断重启时状态会显示重启中，定位手法见本篇日志与诊断类。
- **处置**：给健康检查加上启动宽限期，或临时放宽阈值确认是否卡在这里；确认配置档后按档位启动。

```bash
docker compose ps -a
docker compose logs --tail 100 web
docker compose --profile debug up -d
```

> [!TIP]
> **建议内容**：健康检查是双刃剑，过松则形同虚设，过紧则把正常服务挡在启动之外。给初始化耗时较长的服务设置启动宽限期，等它稳定后再转为常规探测，能避免一大类「没报错但起不来」。

**速记**：**没报错不起就查三样：状态与日志、健康检查是否过严、配置档是否启用**。



#### 多文件合并后配置与预期不符

**多文件合并**：指同时指定多个 Compose 文件时后者覆盖前者，不同字段的合并方式并不统一，最终结果必须以展开后的为准。

- **合并规则**：单值字段通常后写覆盖先写，列表类字段可能追加也可能替换，具体依字段而定，以官方规范为准。
- **定位手段**：用配置展开子命令按同样的文件顺序展开，打印的就是守护进程最终采纳的配置。
- **易错点**：命令行指定的文件顺序决定覆盖方向，顺序颠倒会得到完全不同的结果。
- **变量插值**：插值在合并过程中发生，值来自环境变量或环境文件，插值的优先级规则以官方文档为准，详见《12. 环境变量、配置注入与密钥管理》。

```bash
docker compose -f compose.yaml -f compose.override.yaml config
docker compose -f compose.yaml config --services
```

> 判据是「不信推断信展开」：无论怎么理解覆盖规则，先跑配置展开看最终值。这与容器排障里先看 inspect 再看命令是同一个道理。

**速记**：**多文件后者覆盖前者，列表字段合并方式依字段而定**；用配置展开按同序查看最终结果。



#### 容器名冲突与网络残留

**名称与资源残留**：指容器名被占用导致启动失败，或项目下线后网络仍在，根因是显式命名与外部资源声明这两类配置。

- **容器名冲突**：显式指定固定容器名会与多副本扩缩容冲突，同一项目内名字必须唯一；同名旧容器未清理时也会占用名字。
- **容器名处置**：去掉固定名让编排工具自动命名，服务间用服务名互访而不依赖容器名；清理旧容器后再启动。
- **网络残留现象**：执行下线命令后网络没有消失。
- **网络残留根因**：声明为外部引用的网络由用户自行创建，编排工具只使用不创建也不删除。
- **处置**：外部网络需手动删除；自建网络若被其他容器占用也会保留，先用网络列表与详情确认引用者。

```bash
docker ps -a --filter name=myproject
docker compose down
docker network ls
docker network rm app-net
```

> [!NOTE]
> **提醒内容**：固定容器名看似便于脚本引用，代价是失去横向扩展能力。用服务名做 DNS 名称是更稳的做法，名称解析依赖自定义网络，见《9. 自定义网络与容器互联》。

**速记**：**固定容器名与多副本互斥、同名旧容器会占用名字**；外部网络不会被 down 删除，需手动清理。



### 性能类

性能问题的第一难点是判断慢在哪里，容器内看到的资源信息并不等同于容器自身用量。资源限制与运行时约束见《13. 容器资源限制与运行时约束》。

#### 宿主机负载高但容器指标不高

**指标口径差异**：指宿主机整体负载很高，但逐个容器的指标看起来都不高，根因是容器内读到的部分系统信息来自宿主机视图，不能直接当作容器用量。

- **为什么**：默认情况下容器内读取的内存、CPU 与部分内核信息反映宿主状态，除非使用专门的视图隔离方案。
- **正确取数**：容器用量以运行时提供的统计为准，取一次快照的统计命令适合脚本采集。
- **排查动作**：在宿主用系统工具找出真正的负载来源，再对照容器的统计命令逐一对号。
- **可能的真凶**：宿主上非容器的进程、多个容器叠加的总和、以及容器的磁盘读写与页面缓存。

```bash
docker stats --no-stream
docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}'
top -o %CPU
```

> 反直觉点在于容器里的 free 与 top 会让人误判容器很闲。判容器是否吃资源，用运行时统计而不是容器内的系统工具，这一点与退出码 137 的 OOM 判定用 inspect 字段同源。

**速记**：**容器内系统信息是宿主视图，不等于容器用量**；用 stats 取容器口径，用宿主工具找真正负载源。



#### macOS 上文件读写慢

**跨虚拟机文件共享**：macOS 与 Windows 上 Linux 容器运行在一台托管的 Linux 虚拟机内，绑定挂载的宿主目录要跨虚拟机边界同步，性能天然低于 Linux 原生。

- **架构性原因**：文件共享层要在宿主与虚拟机之间传递文件事件与内容，海量小文件与频繁读写时开销放大最明显。
- **现行默认**：macOS 上文件共享的现行默认实现是 VirtioFS，旧的共享实现与其一致性档位通常不再生效。
- **缓解一**：把依赖目录、构建缓存、数据库数据放在命名卷里，让读写发生在虚拟机内部的文件系统上。
- **缓解二**：源码用绑定挂载以便编辑，但把安装依赖与构建产物放在卷或镜像内，避免 node_modules 之类海量小文件跨边界。
- **缓解三**：用忽略清单缩小构建上下文，减少跨边界传输量。

```bash
docker volume create app-node-modules
docker run -d -v "$PWD":/app -v app-node-modules:/app/node_modules myapp:1.0
```

> 这是平台架构决定的固有代价，不是配置能完全消除的。优化方向是减少跨边界文件数量，而不是反复调共享实现的参数，机制细节见《7. 数据卷与数据持久化》。

**速记**：**macOS 容器在托管虚拟机里，绑定挂载要跨边界**；把依赖与产物放进卷、只把源码留在绑定挂载。



#### 容器启动慢与构建慢

**启动慢**：指容器从创建到就绪的时间偏长。**构建慢**：指镜像构建耗时偏长。两者成因不重叠，处置也不同。

- 启动慢的原因一，镜像层多且本地未命中，需要先拉取或解压。
- 启动慢的原因二，入口脚本里做了重活，如装包、跑迁移、预热缓存。
- 启动慢的原因三，健康检查等待与依赖条件串行，服务实际已就绪但编排层仍在等。
- 构建慢的原因一，缓存未命中导致依赖被反复安装，优化见本节构建类。
- 构建慢的原因二，构建上下文过大，传输本身就耗时，看构建第一行的上下文体积提示。
- 处置：把重活前移到构建阶段写进镜像，精简入口；构建侧调整指令顺序、缩小上下文、挂依赖缓存。

```bash
docker events --since 10m
docker image history myapp:1.0 --no-trunc
docker build --progress=plain -t myapp:1.0 .
```

> 判别方法：用事件流看从创建到启动的时间点，能直接把「拉取解压慢」与「入口执行慢」分开。前者要靠预热镜像，后者要靠精简启动流程。

**速记**：**启动慢查层与入口脚本，构建慢查缓存与上下文**；重活前移到构建阶段，用事件流分隔两段时间。



### 日志与诊断类

诊断的通用顺序是先看状态与退出码，再看日志，最后进容器复现。日志驱动、轮转与事件流的完整展开见《14. 容器日志与监控》。

#### docker logs 看不到输出

**读不到日志**：指执行 logs 命令没有输出或只输出一部分，根因有三类：驱动不支持读取、应用写到了文件、输出被缓冲。

- **根因一，日志驱动**：并非所有驱动都支持本地读取，日志被转发到外部系统后，本地读取命令通常拿不到内容，按官方文档只有把日志保留在本地的驱动才支持读取。
- **根因二，写到了文件**：应用把日志写进容器内文件而非标准输出，本地读取命令什么也看不到，这是容器化日志最常见的设计错误。
- **根因三，缓冲未刷新**：语言运行时把标准输出做了块缓冲，进程没退出前日志不出现在流里。
- **处置**：用 inspect 看日志驱动与日志路径字段；exec 进容器读应用自己的日志文件；改应用为输出到标准输出；启动时关闭缓冲或显式刷新。

```bash
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.LogPath}}' web
docker exec web ls -l /var/log/app
docker logs --tail 100 web
```

> [!IMPORTANT]
> **重要内容**：容器日志的正确形态是应用把日志写到标准输出与标准错误，由运行时统一收集。往容器内写日志文件既读不到、又随容器删除而丢失，还白白占用可写层空间，应尽早改掉。

**速记**：**看不懂日志先查三样：驱动支不支持读、应用写没写到文件、缓冲刷没刷**；正解是输出到标准输出。



#### 日志占满磁盘

**日志写满**：指容器日志把宿主磁盘占满，根因是默认日志驱动在未配置轮转时不限制单个日志的大小与个数。

- **默认事实**：默认的日志驱动按官方文档不自动轮转，长期运行的服务会把日志文件写到占满磁盘。
- **确认**：看容器日志路径与文件大小，或用系统级磁盘统计看整体占用。
- **处置一**：在守护进程配置里设置日志驱动与轮转参数，单文件大小与保留个数一起给，改完对新容器生效。
- **处置二**：也可在单容器级别覆盖日志配置，适合个别日志量大的服务。
- **应急清理**：清空当前大文件用截断而不是删除，直接删除文件而进程仍持有文件描述符时空间不会立即释放，要重启容器才回收。

```bash
docker inspect -f '{{.LogPath}}' web
sudo truncate -s 0 "$(docker inspect -f '{{.LogPath}}' web)"
docker system df
```

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

> [!WARNING]
> **警告内容**：不要在容器运行时直接删除日志文件来腾空间。文件描述符仍指向被删的 inode，磁盘空间不会释放，且日志路径会消失造成后续排查断档，应改为截断或先停容器。

**速记**：**默认日志不轮转、会写满磁盘**；配单文件大小与保留个数，应急用截断而不是删除。



#### 容器反复重启形成循环

**重启循环**：指容器退出后被重启策略反复拉起，状态显示重启中，根因必须先定位再谈处置，贸然改配置会丢失现场。

- **第一步看事件流**：按容器过滤事件，能看到退出与启动交替出现的时间线，判断循环的周期与规律。
- **第二步看字段**：inspect 看重启次数、退出码与是否被内存杀，退出码能直接指向应用错误、配置错误或内存超限。
- **第三步看日志**：取最后一次退出的日志尾部，多数原因在此暴露。
- **止血手段**：确需先停住循环时把重启策略临时改为不重启，把容器按当前配置稳定下来，再从容排查。
- **处置**：按退出码分类处置，退出码 1 查日志，退出码 137 区分内存与停止超时，判定方法见《13. 容器资源限制与运行时约束》。

```bash
docker events --filter container=web --since 10m
docker inspect -f '{{.RestartCount}} {{.State.ExitCode}} {{.State.OOMKilled}}' web
docker update --restart=no web
```

> [!WARNING]
> **警告内容**：不要用 docker rm 直接删掉正在重启循环的容器来图清净，那会连同可写层里的现场一起清掉。先读事件与日志取证，再决定删除与重建。

**速记**：**重启循环先看事件流、再看字段、再看日志**；需要止血时临时关闭重启策略，别急着删容器。



#### 进不去容器

**进不去**：指 exec 无法获得交互式 shell，最常见原因是精简镜像里根本没有 shell，其次是容器状态不允许。

- **先排除状态问题**：容器处于暂停状态时 exec 会报错，需先恢复；容器已退出则任何 exec 都无效，应改用删除前取证或临时容器。
- **精简镜像的情形**：镜像里只有二进制没有 shell，可临时用该镜像加一个存在的入口程序做检查，或起一个带工具的同网络容器打辅助。
- **数据侧取证**：用拷贝命令在宿主与容器之间搬运文件，已停止的容器同样可用。
- **Desktop 专属手段**：Docker Desktop 提供一条调试命令，可为容器或镜像套上预装工具的调试环境，纯引擎环境没有该能力，不可作为通用方案。
- **兜底做法**：用同镜像加卷挂载起一次性容器查看文件系统，或用静态工具二进制拷入后执行。

```bash
docker exec -it web sh
docker run --rm --entrypoint /bin/ls myapp:1.0 -l /app
docker cp web:/var/log/app.log ./app.log
```

> 判据是先确认镜像里有没有 shell：用镜像的构建历史与入口字段推断，或用存在的二进制做临时入口。没有 shell 时不要反复试 bash，那只会浪费时间。

**速记**：**先排除暂停与已退出，再确认镜像有没有 shell**；精简镜像用临时入口、同网络工具容器或 Desktop 专属调试命令。



#### 通用诊断动作序列

**诊断序列**：是一套与具体故障无关的固定动作，按状态、原因、趋势、复现四步推进，能把大多数问题在几分钟内定位到层。

1. 看状态与配置：用状态命令与 inspect 读当前状态、退出码、重启次数与实际生效的挂载、端口、网络。
2. 看原因：用日志命令取尾部日志，判断是应用错误还是启动前就失败。
3. 看趋势与事件：用统计命令看资源占用，用事件流看退出与重启的时间线。
4. 进容器复现：用交互式进入容器或起同网络临时容器，手工重放失败动作。
5. 缩小范围：把问题收敛为一段最小可复现的命令或配置，再决定修复方案。

```bash
docker ps -a
docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}} {{.RestartCount}}' web
docker logs --tail 100 web
docker stats --no-stream web
docker events --filter container=web --since 10m
docker exec -it web sh
```

> 这套序列的价值在于顺序固定、不依赖具体故障：先状态后原因再趋势最后复现，任何一步拿到决定性证据就可以停下来处理，不必跑完全程。

**速记**：**状态与 inspect 到日志到 stats 与 events 到进容器复现**；拿到决定性证据即可止步，不必机械跑完五步。



### 清理与磁盘回收类

清理的核心是分清哪些对象可以安全删除，以及哪些操作删掉的是数据而不是缓存。清理命令的边界见《3. 容器生命周期与常用命令》。

#### 辨识四类占用

**四类占用**：磁盘被镜像、容器、卷与构建缓存四类对象瓜分，任何清理动作之前都应先看清四者各占多少。

- **镜像**：所有本地镜像的总大小，含未被任何容器使用的部分，是常见的最大头。
- **容器**：已停止容器的可写层占用，容器数量多时累积可观。
- **卷**：命名卷与匿名卷的占用，往往包含数据库数据，删除风险最高。
- **构建缓存**：构建中间层与缓存挂载的占用，长期构建的机器上容易堆积。
- **可回收量**：统计命令会单独列出可回收一列，提示当前能安全释放多少。

```bash
docker system df
docker system df -v
```

> 判读要点是把「总量」与「可回收量」分开看。总量大但可回收量小，说明占用对象仍在被引用，强行删除要么删不掉要么会误伤业务数据。

**速记**：**四类占用是镜像、容器、卷、构建缓存**；先 df 看总量与可回收量，再决定清哪一类。



#### 安全清理顺序

**安全顺序**：指从影响面最小的对象清到影响面最大的对象，每一步之前重看一次账、之后核对释放量，避免一步到位误删数据。

1. 清构建缓存，只影响构建速度，不影响任何运行中的业务。
2. 清悬空镜像，即没有任何标签与引用的中间层残留。
3. 清未被使用的网络，自定义网络闲置后即属此类。
4. 清已停止的容器，删除的是可写层，运行中的容器不受影响。
5. 清所有未被容器使用的镜像，之后需要重新拉取，属可选加码。
6. 清未被引用的卷，进入不可逆的数据删除范畴，必须单独确认。
7. 一键全清并带卷，影响面最大，仅在确认整机可重建时使用。

```bash
docker builder prune
docker image prune
docker network prune
docker container prune
docker image prune -a
docker volume prune
docker system prune -a --volumes
```

> [!TIP]
> **建议内容**：每一步都可用时间过滤缩小范围，只清若干小时或若干天之前创建的对象。相比裸跑一条全清命令，加时间与标签过滤能在保留近期工作成果的同时释放大部分空间。

**速记**：**缓存到悬空镜像到网络到停止容器到未用镜像到卷，逐级加码**；每步先看账再清、再核对释放量。



#### 不可逆的删数据操作

**不可逆操作**：指删除后数据无法找回、也没有回收站的动作，共同点是删除了卷或卷中数据，执行前必须单独确认并做好备份。

- 编排工具下线并带卷：删除项目定义的命名卷。
- 卷清理加全部选项：删除未被容器引用的命名卷，包括刚停掉容器的数据库卷。
- 删除容器带卷选项：删除该容器的匿名卷。
- 一键全清带卷选项：连未被引用的匿名卷一并删除。
- 按名删除卷：脚本里最危险的一条，写错卷名即删错数据。
- 共同处置：先用卷列表与卷详情确认对象，再用一次性容器把要保留的卷打包成 tar。

```bash
docker volume ls
docker volume inspect mysql-data
docker run --rm -v mysql-data:/from:ro -v "$PWD":/to \
  alpine sh -c "cd /from && tar czf /to/mysql.tgz ."
```

> [!CAUTION]
> **注意内容**：这五类操作会真的删除数据，不是清理缓存。判断标准只有一个：命令里是否出现了卷或带卷的选项。出现即按数据删除流程走，先备份、再核对、最后执行。

**速记**：**带卷的操作都不可逆**：down 带卷、卷清理加全部、删容器带卷、全清带卷、按名删卷；先备份成 tar。



#### 被引用的镜像删不掉与批量清容器

**删不掉**：指删除镜像时提示该镜像正被容器使用，根因是镜像被某个容器引用，删除的前提是先清理引用它的容器。

- **处置一**：用容器列表按镜像过滤，找出所有引用该镜像的容器，含已停止的。
- **处置二**：先删除容器再删镜像；强制删除只解除标签，底层仍被引用的层不会释放空间，空间要等引用消失后才回收。
- **悬空层的归宿**：容器全部删除后，不再被引用的层变为悬空镜像，用悬空镜像清理命令统一回收。
- **批量清容器**：用查询命令输出容器标识再喂给删除命令，先把过滤器限定到已退出状态，跑一遍查询确认范围后再执行删除。
- **更稳的写法**：用容器清理命令并按时间过滤，或用管道逐条删除并对空输入做保护。

```bash
docker ps -a --filter ancestor=myapp:1.0
docker ps -aq --filter status=exited
docker ps -aq --filter status=exited | xargs -r docker rm
docker container prune --filter "until=24h"
```

> [!WARNING]
> **警告内容**：不要使用不带过滤器的无条件删除写法，例如把全部容器标识一次性喂给删除命令。多项目共用一台机器时，这类写法会波及运行中的容器，务必先用过滤器把范围限定到已退出的对象。

**速记**：**镜像删不掉先找引用它的容器，强制删只解标签不释放层**；批量清容器先过滤已退出、先看后删、空输入要保护。



### 通用排错心法

前面各节按现象分类，这一节收束成几条与具体故障无关的判断习惯，照做能显著减少无效尝试。

#### 先缩小范围

**缩小范围**：指在动手修之前，先确定问题只出现在 Compose 编排下，还是在单容器命令下也能复现，这一步决定排查方向。

- 单容器命令能复现：问题在镜像、运行参数或应用本身，与编排无关。
- 只有编排下出错：优先怀疑网络归属、环境变量注入、启动顺序、卷与配置挂载这些编排层引入的差异。
- 缩小手法：用同镜像同参数起一个一次性容器复现，或用最小编排文件只保留相关服务。
- 记录方法：把能复现的最小命令与不能复现的对照命令并排写下，差异处往往就是根因。

```bash
docker run --rm -it --network app-net myapp:1.0 sh
docker compose -f compose.min.yaml up -d
```

> 判据很直接：**能脱离编排复现就不是编排的问题**。反过来，只有编排下才出问题，就不要在镜像里找原因。

**速记**：**先分清是单容器还是只有编排下出错**；单容器能复现查镜像与应用，只有编排出错查网络、变量、顺序与挂载。



#### 先看状态再看日志再进容器

**诊断顺序**：指按状态与配置、日志、进入容器复现三级推进，前一级能给出结论就不进入下一级。

- 第一级看状态与配置：状态、退出码、重启次数、实际生效的挂载与端口，回答「现在是什么情况」。
- 第二级看日志：应用与运行时的输出，回答「为什么变成这样」。
- 第三级进容器：手工重放失败动作，回答「怎样稳定复现」。
- 顺序的意义：状态是客观事实、日志是程序陈述、手工复现才验证假设，跳过前两级直接猜原因容易南辕北辙。

```bash
docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.RestartCount}}' web
docker logs --tail 100 web
docker exec -it web sh
```

> 反例是把「进容器乱敲」当作第一步。容器内能改的东西随时会被重建冲掉，先固定状态与日志这两类证据，再进容器验证假设。

**速记**：**先 inspect 看状态与配置，再看 logs 找原因，最后进容器复现**；前一级有结论就不走下一条。



#### 一次只改一个变量

**单变量原则**：指每次只改动一个因素并观察结果，否则即使问题消失也无法归因，后续会再次踩坑。

- 反例：同时改镜像版本、网络模式、环境变量与挂载路径，问题消失后不知道是哪一项起了作用。
- 正确做法：从最小可复现案例出发，每次只改一处，改动前后各记录一次观察结果。
- 配置改动的适用范围：部分配置需重启容器才生效，部分需删除重建，确认生效方式后再判断改动是否真的生效。
- 判断标准：改动生效的标志是 inspect 里的实际值发生变化，而不是命令执行成功。

```bash
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' web
docker update --restart=on-failure:3 web
```

> 与「先看状态再看日志」配套使用：改之前先记录 inspect 的实际值，改之后再看同一个字段，两次取值一致说明改动没生效，而不是问题不存在。

**速记**：**一次只改一个变量、改前后各记录一次真实生效值**；命令成功不等于配置生效。



#### 把重启一下就好了当线索并写最小案例

**重启即恢复**：指问题在重启容器后消失，这只是症状缓解而不是修复，背后通常有确定性的原因，应把它当作定位线索而不是解决方案。

- **常见背后原因一**：解析结果被缓存，重启后重新解析才拿到新地址，对应 DNS 类问题。
- **常见背后原因二**：连接池或客户端与已变更的对端失联，重启后重建连接。
- **常见背后原因三**：依赖启动顺序颠倒，重启时依赖先就绪而侥幸成功，应改为显式依赖与健康检查。
- **常见背后原因四**：启动时读取的挂载内容在运行期间被替换，重启后才重新读取。
- **最小可复现案例**：把问题收敛为一段最小命令、一份最小配置或一个最小镜像，写清现象、复现步骤与预期，再带着它去查或求助。
- **处置**：找到并消除上面某一条的具体成因，用健康检查与启动顺序把偶发变成确定。

> [!TIP]
