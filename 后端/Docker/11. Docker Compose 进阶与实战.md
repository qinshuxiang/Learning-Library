## Docker Compose 进阶与实战

### 依赖与启动顺序

#### depends_on 的短语法与长语法

**depends_on（依赖声明）**：声明服务之间的启动与停止先后关系；短语法只列服务名，长语法写成映射，可为每项追加 condition、restart、required 三个附加字段。

- **短语法**：在 depends_on 下直接列出被依赖的服务名，一项一行，只表达「先启动谁」。
- **启动方向**：Compose 按依赖顺序创建并启动，被依赖服务先于依赖方创建。
- **停止方向**：执行 down 或 stop 时按相反顺序移除，依赖方先于被依赖方停止。
- **短语法的边界**：官方规范原文写明，短语法下 Compose 保证被依赖服务「已启动」，但「不等待其进入健康状态」。
- **长语法的三个附加字段**：condition 指定依赖满足的条件，restart 指定被依赖服务更新后是否连带重启本服务，required 指定依赖缺失时是报错还是只告警。
- **版本要求**：restart 自 Compose 2.17.0 起提供，required 自 2.20.0 起提供。

```yaml
services:
  api:
    image: node:22-alpine
    depends_on:
      - db
      - cache

  web:
    image: nginx:1.27-alpine
    depends_on:
      db:
        condition: service_healthy
        restart: true
      cache:
        condition: service_started

  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      retries: 5

  cache:
    image: redis:7-alpine
```

> 依赖声明回答的是「谁先谁后」，不是「谁能不能用了」。把「已启动」与「已就绪」当成同一件事，是短语法最常见的误用。

**速记**：短语法只排先后，长语法补 condition、restart、required 三项。



#### 短语法为何会「数据库还没起来应用就崩」

**根因判断**：短语法只保证被依赖服务的容器进程已经启动，数据库类服务在进程起来之后还要完成数据目录初始化、监听套接字、加载系统表，这段时间里应用发起连接会被拒绝或超时。

- **现象**：api 容器日志出现连接被拒、名称解析正常但端口未监听、驱动报无法建立连接。
- **时间差来源**：postgres 首次启动要初始化数据目录并重启一次内部进程，MySQL 首次启动要初始化系统表，这些动作在「容器已启动」之后仍在进行。
- **偶然自愈的假象**：把 api 的 restart 设为 unless-stopped 时，api 崩溃后会被反复拉起，等到数据库就绪时恰好连上，问题被掩盖。
- **真正的代价**：这种自愈依赖重启次数与初始化耗时，换机器或换数据量就可能失败，首次冷启动与迁移后重启表现不一致。
- **判定手段**：用 compose ps 看数据库是否显示 healthy，再对照 api 日志里首次连接的时间点。

```bash
docker compose ps
docker compose logs --tail=50 api
docker compose logs --tail=50 db
```

> [!WARNING]
> **警告内容**：靠重启策略「碰运气」等到数据库就绪，在数据量大或冷启动慢的环境里会变成随机失败。启动顺序问题应在声明层用依赖条件解决，而不是交给重启次数兜底。

**速记**：容器已启动不等于服务已就绪，短语法只等到前者。



#### 用 condition 修正启动顺序

**condition（依赖条件）**：长语法下为每个依赖指定必须满足的状态，取值有 service_started、service_healthy、service_completed_successfully 三种，分别对应「已启动」「健康」「成功跑完」三个门槛。

- **service_started**：等价于短语法，只要求被依赖服务的容器已经启动。
- **service_healthy**：要求被依赖服务通过自身健康检查，即其 healthcheck 判定为 healthy；未定义健康检查时该条件失去判定依据。
- **service_completed_successfully**：要求被依赖服务运行到成功退出，即退出码为 0，用于迁移、初始化一类的跑完即退任务。
- **required**：默认 true；写 false 时依赖缺失只告警不报错，适合可选组件。
- **失败表现**：被依赖服务始终无法满足条件时，启动会停在等待处并最终报错，而不是静默跳过。

```yaml
services:
  api:
    image: node:22-alpine
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
```

> 启动顺序在 Compose 里是整组容器的创建与启动次序，condition 只是把它从「进程起来了」细化为「达到某个可用状态」。真正的可用性仍由业务侧的连接重试兜底，两者是叠加而非二选一。

**速记**：started 看进程、healthy 看检查、completed_successfully 看退出码。



### 健康检查

#### healthcheck 的字段与默认值

**healthcheck（健康检查）**：由 Compose 在容器内周期执行的探测，其行为与默认值同镜像的 HEALTHCHECK 指令一致，Compose 文件中的取值会覆盖镜像里的设置。

- **test**：探测命令，字符串或列表两种形式，决定「怎么判断健康」。
- **interval**：两次探测之间的间隔，默认 30s，从容器启动后开始计时。
- **timeout**：单次探测的最长等待时间，默认 30s，超时即记为一次失败。
- **retries**：连续失败多少次后判定为 unhealthy，默认 3 次。
- **start_period**：启动宽限期，默认 0s；期间探测失败不计入 retries，一旦成功即进入正式计数。
- **start_interval**：宽限期内的探测间隔；不写时沿用 interval。
- **disable**：写成 true 时关闭健康检查，用于覆盖镜像自带的 HEALTHCHECK。
- **状态取值**：容器健康状态为 starting、healthy、unhealthy 三态，可经 compose ps 与容器 inspect 查看。

> 官方规范把 interval、timeout、start_period、start_interval 一律按 duration 解析，故 30s、1m30s 均为合法写法；写纯数字会被当作纳秒级时间，属常见误配。

**速记**：interval 隔多久查一次、timeout 单次等多久、retries 错几次算病、start_period 给多久宽限。



#### test 的三种写法

**三种 test 写法**：列表形式的首项必须是 NONE、CMD、CMD-SHELL 之一；字符串形式等价于 CMD-SHELL 后接该字符串。

- **CMD 形式**：列表首项为 CMD，后续每项作为独立参数直接执行，不经过 shell，最不易被转义问题影响。
- **CMD-SHELL 形式**：列表首项为 CMD-SHELL，其后是一整条字符串命令，由容器默认 shell 执行，便于使用管道、变量与逻辑运算。
- **字符串形式**：直接写一条命令字符串，Compose 自动按 CMD-SHELL 处理，官方视两种写法等价。
- **NONE 形式**：列表首项写 NONE 表示关闭健康检查，其价值主要在关闭镜像自带的检查；等价写法是 healthcheck 下写 disable 为 true。
- **退出码约定**：命令退出码 0 表示健康，非 0 表示失败；用 curl 类工具时通常配合 -f，让非 2xx 响应也返回非 0。

```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost/health"]
```

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -f http://localhost/health || exit 1"]
```

```yaml
healthcheck:
  disable: true
```

```yaml
healthcheck:
  test: ["NONE"]
```

> CMD 形式不走 shell，因此不能在命令里直接用变量展开与管道；需要这些 shell 特性时必须显式选择 CMD-SHELL。反过来，CMD-SHELL 里若命令本身写错，失败会被 shell 吞成退出码，排查时不容易看出是哪一环。

**速记**：CMD 直执行、CMD-SHELL 过 shell、字符串等于 CMD-SHELL、NONE 与 disable 都是关。



#### 镜像自带 HEALTHCHECK 与 compose 覆盖

**覆盖关系**：Compose 的 healthcheck 与镜像 HEALTHCHECK 同语义、同默认值，Compose 文件中写出的字段覆盖镜像里对应的值；镜像没有 HEALTHCHECK 时，Compose 写什么就以什么为准。

- **只在 compose 里加**：基础镜像未定义 HEALTHCHECK 时，健康检查完全由 Compose 文件提供。
- **覆盖镜像定义**：镜像已带 HEALTHCHECK 时，Compose 里的 test 与各时长字段按项覆盖，最终生效值以 compose config 渲染结果为准。
- **关闭镜像定义**：镜像的健康检查不适合容器化场景时，用 disable 为 true 或 test 写 NONE 关掉。
- **合并时的限制**：官方规范指出，使用 extends 合并时，主映射不能单独指定 disable 为 true，除非被引用映射也指定了同样的值，否则 Compose 报错。
- **可见性**：健康检查定义会写进容器元数据，docker inspect 与 docker compose config 均可查。

> [!NOTE]
> **提醒内容**：镜像自带的健康检查常常只是「进程还在」，例如检查某个二进制能否响应 ping。这类检查通过不代表服务能对外提供请求，生产场景应按实际可用性重写 test。

**速记**：镜像有就覆盖、没有就新增，不要时用 disable 或 NONE 关掉。



#### Web 与数据库的健康检查实例

**实例原则**：健康检查要探测服务「能否对外服务」，而非「进程是否存活」；Web 用 HTTP 探针，数据库用各自客户端自带的可连性探测。

- **PostgreSQL**：用 pg_isready 检查实例是否可接受连接，指定用户与库名更贴近应用实际路径。
- **Redis**：用 redis-cli ping，返回 PONG 即视为可用。
- **HTTP 服务**：用 curl -f 或 wget 探测一个真实就绪端点，端点应包含对下游依赖的检查。
- **精简镜像的坑**：alpine 或 distroless 镜像常常没有 curl，需改用 wget、镜像内已有运行时自带的工具，或直接调用语言运行时的 HTTP 客户端。
- **时间参数配合**：数据库首次初始化慢，给足 start_period；探测间隔与超时要小于业务可接受的启动等待。

```yaml
services:
  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

  api:
    image: node:22-alpine
    healthcheck:
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 20s
```

> 上面 api 的探针调用 Node 自带的 fetch，既不依赖 curl，也检查了应用真实的 HTTP 就绪端点。若就绪端点内部会查询数据库，这一条探针同时覆盖了「应用在跑」与「依赖可达」两件事，比单纯的进程检查更接近可用性。

**速记**：Web 查 HTTP、Postgres 用 pg_isready、Redis 用 redis-cli ping，精简镜像先确认探针工具存在。



### 一次性任务与初始化

#### service_completed_successfully 的编排语义

**service_completed_successfully（成功完成）**：要求被依赖服务运行到退出码为 0，Compose 才继续启动依赖它的服务，专用于数据库迁移、初始化脚本、种子数据这类跑完即退的一次性任务。

- **判定依据**：只看退出码，不看运行时长；退出码非 0 视为失败，依赖方不会启动。
- **典型摆放**：迁移服务依赖数据库的 service_healthy，应用服务依赖迁移服务的 service_completed_successfully，形成三段链条。
- **与 service_started 的差别**：后者在迁移容器刚启动时即放行，应用可能在表还没建好时就接到请求。
- **重复执行**：每次 up 都会重新创建并运行一次性任务容器，因此迁移脚本必须写成可重复执行，即幂等。
- **手动重跑**：用 compose run 加 rm 单独重跑迁移服务，不牵动其余服务。

```yaml
services:
  migrate:
    image: node:22-alpine
    command: ["node", "scripts/migrate.js"]
    depends_on:
      db:
        condition: service_healthy

  api:
    image: node:22-alpine
    depends_on:
      migrate:
        condition: service_completed_successfully

  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      retries: 5
```

> [!IMPORTANT]
> **重要内容**：迁移任务必须可重复执行。Compose 不记录某条迁移是否已跑过，它只按声明重新创建容器并执行命令；脚本内部应依赖迁移版本表或幂等 SQL 来避免重复建表报错。

**速记**：退出码为 0 才算过，迁移任务依赖数据库健康、应用依赖迁移完成。



#### restart 设为 no 的必要性

**restart 策略**：一次性任务的退出是预期结果，因此 restart 必须保持 no（也是默认值）；写成 always 或 unless-stopped 时容器退出后会被反复拉起，service_completed_successfully 永远等不到稳定的「已完成」。

- **no**：不重启，退出即停，是一次性任务的正确取值。
- **on-failure**：迁移失败时会反复重试，可能把「配置写错」拖成无限循环。
- **always 与 unless-stopped**：常驻服务的取值，用在一次性任务上会造成退出即拉起的死循环。
- **显式写出的意义**：默认虽是 no，但团队成员可能复制常驻服务的片段，在迁移服务上显式写 restart 为 no 可防止被误改。
- **与依赖条件的配合**：只有任务稳定退出，依赖它的应用才有确定的启动时点。

```yaml
services:
  migrate:
    image: node:22-alpine
    command: ["node", "scripts/migrate.js"]
    restart: "no"
    depends_on:
      db:
        condition: service_healthy
```

> [!CAUTION]
> **注意内容**：把迁移服务写成 restart 为 always 后，容器会陷入「执行、退出、再执行」的循环，日志被刷屏，应用则卡在等待迁移完成的依赖条件上。发现迁移容器反复出现 Up 与 Exited 交替，先检查 restart 取值。

**速记**：跑完即退的任务一律 restart 为 no，避免退出即拉起。



#### 迁移、初始化与种子数据的完整写法

**任务分工**：把建库建用户（初始化）、建表结构（迁移）、灌入演示数据（种子）拆成三个一次性服务，各自依赖上一步成功完成，链条清晰且可单独重跑。

- **初始化服务**：适合幂等 SQL，例如建扩展、建库、建只读用户；依赖数据库 healthy。
- **迁移服务**：执行版本化迁移脚本，成功后退出；依赖初始化服务 completed_successfully。
- **种子服务**：灌入开发或演示数据，通常只在开发环境运行，可放进 profiles。
- **共享镜像**：初始化与迁移用应用同一镜像，靠 command 覆盖入口，避免维护多份构建。
- **幂等要求**：三个服务都可能被重复执行，脚本需能安全重复运行。

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      retries: 5
      start_period: 30s

  init-db:
    image: postgres:17-alpine
    command: ["psql", "-v", "ON_ERROR_STOP=1", "-f", "/scripts/init.sql", "-U", "app", "-d", "shop", "-h", "db"]
    volumes:
      - ./db/init.sql:/scripts/init.sql:ro
    restart: "no"
    depends_on:
      db:
        condition: service_healthy

  migrate:
    image: node:22-alpine
    command: ["node", "scripts/migrate.js"]
    env_file:
      - ./api/api.env
    restart: "no"
    depends_on:
      init-db:
        condition: service_completed_successfully

  seed:
    image: node:22-alpine
    command: ["node", "scripts/seed.js"]
    env_file:
      - ./api/api.env
    profiles: ["debug"]
    restart: "no"
    depends_on:
      migrate:
        condition: service_completed_successfully
```

> 种子数据放进 debug profile，是因为它只在需要演示数据时才运行；把它挂在 migrate 之后，保证表结构就绪。日常 up 不会触发它，显式加 debug profile 才会执行。

**速记**：初始化、迁移、种子各成一段，逐级依赖成功完成，脚本必须幂等。



### profiles 分组

#### profiles 的默认隐藏与启用方式

**profiles（配置档案）**：给服务打上的命名标签，未分配 profile 的服务始终启用，分配了的服务只在对应 profile 被激活时才启动。

- **默认行为**：不带任何 profile 时，只有未分配 profile 的服务参与，带 profile 的服务被忽略。
- **命令行启用**：加 profile 参数后接名字，可重复出现多个。
- **环境变量启用**：设置 COMPOSE_PROFILES，多个 profile 用逗号分隔。
- **全部启用**：profile 参数取值为星号时，一次性激活所有 profile，适合本地全量演练。
- **显式点名**：命令行直接点名某个带 profile 的服务时，其 profile 会被自动加入激活集合，无需手动启用。
- **命名规则**：profile 名需符合首字符为字母或数字、其后为字母数字与点、下划线、短横线组合的格式。

```bash
docker compose up -d
docker compose --profile debug up -d
docker compose --profile frontend --profile debug up -d
COMPOSE_PROFILES=frontend,debug docker compose up -d
docker compose --profile "*" up -d
```

> down 同样受 profile 影响：不带 profile 的 down 只处理默认服务，带 profile 的 down 会连同该 profile 下的服务一起停止与移除。

**速记**：未分配的始终启动，分配的默认隐藏，profile 参数、COMPOSE_PROFILES、星号三种启用方式。



#### 把调试工具与可选组件分离出去

**分离动机**：把管理界面、抓包工具、监控采集器等非核心容器打上 profile，让日常启动只拉起业务必需的几个服务，既省资源也缩小暴露面。

- **调试工具**：数据库管理界面、邮件拦截器等，放进 debug，仅在需要时启用。
- **可选依赖**：本地开发用的对象存储、消息队列模拟器，放进 tools。
- **监控组件**：指标采集与可视化属于观测需求，与业务运行解耦，放进 monitor。
- **多 profile 归属**：一个服务可以同时属于多个 profile，只要命中其中之一即被启用。
- **端口收敛**：调试类服务通常把端口绑到 127.0.0.1，避免误暴露到局域网。

```yaml
services:
  adminer:
    image: adminer:4
    profiles: ["debug"]
    ports:
      - "127.0.0.1:8081:8080"
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 10s
      retries: 5
```

> [!TIP]
> **建议内容**：给团队约定一套固定的 profile 名称，例如 debug、tools、monitor，并在 README 或注释里写清各自的用途。名字随意化会让「该加哪个 profile」变成口口相传的隐知识。

**速记**：调试进 debug、可选依赖进 tools、监控进 monitor，按需启用而非默认全开。



#### profile 与 depends_on 的相互约束

**约束关系**：depends_on 不会自动启用「因 profile 未激活而被忽略」的服务；被依赖服务若处于某个 profile 下，依赖它的服务必须能通过同一 profile、显式点名或未被分配 profile 三条路径之一拿到它，否则模型不成立。

- **同属一个 profile**：被依赖服务与依赖方写在同一个 profile 下，启用该 profile 时两者一起进来。
- **依赖方无 profile**：被依赖服务也不该被 profile 门控，否则默认启动时依赖缺失。
- **显式启动依赖**：依赖方与被依赖服务分属不同 profile 时，需把两个 profile 都启用。
- **官方对引用行为的说明**：Compose 参考文档指出，对其它服务的引用，无论是经由 links、extends 还是 service:xxx 这类共享资源语法，都不会自动启用本会被忽略的组件，而是返回错误。
- **被依赖服务可单独点名**：命令行直接点名该服务时，其 profile 自动激活，依赖随之满足。

```yaml
services:
  web:
    image: nginx:1.27-alpine
    profiles: ["frontend"]
    depends_on:
      api:
        condition: service_healthy

  api:
    image: node:22-alpine
    profiles: ["frontend"]
    healthcheck:
      test: ["CMD", "node", "-e", "process.exit(0)"]
```

> [!WARNING]
> **警告内容**：调试组件依赖一个默认服务是安全的，默认服务依赖某个 profile 下的组件则会把依赖链反向锁死。设计 profile 时先确认依赖方向，别让默认启动的服务挂在可选组件之下。

**速记**：依赖链不能跨 profile 断裂，要么同 profile，要么一起启用，要么都不分配。



### 多文件与环境覆盖

#### 多文件叠加的合并规则

**合并规则**：多个 -f 文件按命令行顺序合并，后续文件覆盖、追加或补充前面的文件；不同类型的字段遵循不同策略，路径一律相对第一个文件解析。

- **标量覆盖**：单值字段如 image、command、mem_limit，后写者直接替换前写者。
- **列表拼接**：ports、expose、external_links、dns、dns_search、tmpfs 这几类多值字段把两组值拼接起来，而不是替换。
- **映射按键合并**：environment 与 labels 以变量名或标签名为键合并，同名取后写者，异名追加。
- **挂载按路径合并**：volumes 与 devices 以容器内挂载路径为键合并，同路径取后写者。
- **路径基准**：所有相对路径相对第一个 -f 文件所在目录解析，覆盖文件自身的目录不参与。
- **合并顺序**：基础文件在前、覆盖文件在后，是惯用写法；把顺序写反会让基础值盖掉覆盖值。

```bash
docker compose -f compose.yaml -f compose.prod.yaml config
```

> 官方文档同时指出，若希望每个文件里的相对路径相对各自所在目录解析，应改用顶层的 include 元素，而不是用 -f 叠加。两种机制的路径基准不同，混用会造成找不到文件。

**速记**：标量替换、列表拼接、映射按键合并、挂载按路径合并，路径永远相对第一个文件。



#### override 文件的自动加载

**自动加载**：未用 -f 指定文件时，Compose 在工作目录及父目录中查找 compose.yaml 与可选的 compose.override.yaml，同目录下两者同时存在即自动合并，override 在后、优先生效。

- **配对规则**：compose.yaml 配 compose.override.yaml，compose.yml 配 compose.override.yml，扩展名按同一套取名规则匹配。
- **官方默认**：官方 merge 文档明确写道，默认读取 compose.yaml 与可选的 compose.override.yaml，至少必须存在基础文件。
- **典型用途**：把只适用本机开发的覆盖项，例如绑定挂载源码、调低资源、打开调试端口，放进 override 文件。
- **生效不可见**：它不写在命令里，容易忘记自己存在，从而误判字段来源。
- **禁用办法**：用 -f 显式列出文件时，自动叠加不再发生，也可在列表中显式包含或不包含它。

```yaml
# compose.override.yaml：仅在存在时自动叠加，用于本地开发覆盖
services:
  api:
    volumes:
      - ./api/src:/app/src
    environment:
      LOG_LEVEL: debug
```

> [!CAUTION]
> **注意内容**：override 文件的「隐身生效」是排查配置错乱的常见源头——基础文件写的是生产端口，实际却连到开发端口。怀疑合并结果与预期不符时，第一动作是查看 compose config 的最终输出。

**速记**：compose.override.yaml 与基础文件同目录即自动叠加，-f 显式指定时不再自动生效。



#### dev 与 prod 的文件组织与调用

**文件组织**：把与环境无关的公共声明放在基础文件，把环境差异放进各自的覆盖文件，再用一条命令把基础文件与对应覆盖文件叠起来。

- **基础文件**：compose.yaml 只写所有环境共有的服务、网络、卷与依赖关系。
- **开发覆盖**：compose.dev.yaml 打开源码绑定挂载、调试端口与低资源上限，启用 debug profile。
- **生产覆盖**：compose.prod.yaml 固定镜像标签、去掉源码挂载、收紧资源与重启策略。
- **调用命令**：开发与生产各自用一组 -f 叠加，命令写进脚本或 Makefile，避免手敲顺序出错。
- **环境变量文件**：不同环境用不同的 --env-file，把镜像标签、域名一类的插值来源分开。

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml up -d
docker compose -f compose.yaml -f compose.prod.yaml --env-file .env.prod up -d
```

> 环境差异也可以交给 profiles 表达，但 profiles 只能决定「哪些服务参与」，不能替换同一服务的字段取值。需要改镜像、改命令、改挂载时，仍要用文件叠加。

**速记**：基础文件管共有，dev 与 prod 覆盖管差异，命令用 -f 按序叠加。



#### 用 config 验证合并结果

**config（配置渲染）**：在不启动容器的前提下解析所有输入文件、完成变量插值与多文件合并，输出最终生效的配置，是排查配置错乱的第一手段。

- **验证范围**：文件语法、字段取值、变量插值结果、多文件合并后的最终形态、路径解析是否落在预期位置。
- **静默校验**：加 quiet 只校验不打印，适合放进脚本或钩子。
- **定位合并问题**：把 config 输出与预期逐段对照，能立刻看出某个字段被哪个文件覆盖或追加。
- **辅助枚举**：加 profiles、services、volumes 可分别只打印档案名、服务名、卷名，便于核对参与集合。
- **不产生副作用**：config 只读，不创建任何容器或网络。

```bash
docker compose config
docker compose config --quiet
docker compose config --services
docker compose config --profiles
docker compose -f compose.yaml -f compose.prod.yaml config
```

> 配置合并的结果是一个整体，任何一处改动都可能影响别的字段。改完文件先跑 config，比启动后再逐个容器排查快得多。

**速记**：改文件后先跑 config，语法、插值、合并、路径一次看全。



### 扩展与复用

#### x- 扩展字段

**扩展字段**：任何以 x- 开头的顶层键都会被 Compose 忽略，可用来存放自定义配置片段，再借 YAML 锚点引入到具体服务中。

- **顶层位置**：扩展字段与 services、volumes 平级，写在文件顶层。
- **内容自由**：其下可放任意映射或列表，Compose 不校验、不报错、不参与运行。
- **引用方式**：它本身不含引用能力，需配合 YAML 锚点与别名把自己交给服务。
- **服务内也可写**：服务级别同样允许 x- 开头的键，用于标注自定义元数据。
- **常见载体**：公共日志配置、公共环境变量块、公共资源限制、公共部署片段。

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  api:
    image: node:22-alpine
    logging: *default-logging
```

> 扩展字段不是 Compose 的功能，而是 YAML 能力在 Compose 文件里留下的合法缺口。它之所以能用，是因为 Compose 对未知顶层键采取忽略而非报错的策略。

**速记**：x- 开头即被忽略，本身是容器，靠锚点把内容送进服务。



#### YAML 锚点与合并键的能力边界

**锚点与合并键**：用 & 定义锚点、用 * 引用别名可整段复用同一份映射；用合并键可把锚点内容并入当前映射，并允许本地字段覆盖锚点中的同名字段。

- **锚点的作用域**：锚点是 YAML 的文件级特性，只在定义它的那一份文件内有效。
- **跨文件失效**：用 -f 叠加多份文件时，Compose 逐份解析各文件，另一份文件里的别名无法引用本文件的锚点，会直接解析失败。
- **合并键写法**：以两个小于号加一个冒号表示，把锚点映射并入当前映射，同名键以本地写出的为准。
- **列表的局限**：合并键对映射有效，对列表是整段替换而非逐项合并，需要叠加列表时得另想办法。
- **嵌套合并**：锚点内容里若还有映射，合并后仍是完整结构，不会只并一层。

```yaml
x-healthcheck: &default-healthcheck
  interval: 10s
  timeout: 3s
  retries: 5

services:
  api:
    image: node:22-alpine
    healthcheck:
      <<: *default-healthcheck
      test: ["CMD", "node", "-e", "process.exit(0)"]
```

> 锚点解决的是同一文件内的重复，跨文件复用要靠 x- 扩展字段配合文件叠加，或改用 include 元素。把两件事混为一谈，会在拆文件时遇到别名找不到定义的报错。

**速记**：锚点只在单文件内有效，合并键管映射合并、不管列表叠加。



#### 公共片段的实战写法

**实战目标**：把多个服务共享的日志、健康检查默认参数与环境变量抽成顶层片段，服务内按需引入并按服务覆盖差异项。

- **日志片段**：统一 max-size 与 max-file，避免单容器日志撑满磁盘。
- **健康检查片段**：抽出 interval、timeout、retries 的公共取值，各服务只写自己的 test。
- **环境变量块**：抽出公共非敏感变量，服务内以 environment 叠加差异项。
- **保留覆盖能力**：锚点引入后用同名键写本地值即可覆盖，不必整段重写。
- **命名约定**：锚点名统一带 default 前缀，便于一眼看出这是公共片段。

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

x-healthcheck-defaults: &healthcheck-defaults
  interval: 10s
  timeout: 3s
  retries: 5
  start_period: 15s

services:
  api:
    image: node:22-alpine
    logging: *default-logging
    healthcheck:
      <<: *healthcheck-defaults
      test: ["CMD", "node", "-e", "process.exit(0)"]

  proxy:
    image: nginx:1.27-alpine
    logging: *default-logging
    healthcheck:
      <<: *healthcheck-defaults
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1/health"]
```

> 公共片段的价值在于「改一处、全局生效」，但也会让单服务的最终取值变得不直观。判断某服务究竟用了什么，仍要看 compose config 渲染后的结果。

**速记**：公共片段放顶层，服务内锚点引入，差异字段就地覆盖。



### 扩缩容与无状态前提

#### scale、--scale 与 deploy.replicas 的适用差异

**三个入口**：服务级的 scale 字段声明该服务默认的容器数量；up 的 scale 参数在运行时覆盖它；deploy.replicas 属部署规范，是集群编排语义下的副本数。

- **scale 字段**：官方服务参考定义为「为该服务部署的默认容器数量」，写进文件、可版本化。
- **scale 参数**：官方 CLI 描述为把某服务扩展到指定实例数，并覆盖文件里的 scale 设置。
- **一致性要求**：官方规定 scale 与 deploy.replicas 同时出现时必须保持一致。
- **deploy.replicas**：出自部署规范，语义是调度平台在任意时刻维持的容器数，普通单机 Compose 不具备调度平台。
- **单机推荐**：需要多副本时用 scale 字段或命令行参数，把副本数交给文件与命令，而不是交给未被实现的部署字段。

```bash
docker compose up -d --scale api=3
docker compose up -d --scale api=3 --scale worker=2
```

> [!IMPORTANT]
> **重要内容**：给同一服务既写 scale 又写 deploy.replicas 且取值不一致，会让配置自相矛盾。单机场景只保留一种表达，通常是服务级的 scale 或运行时的 scale 参数。

**速记**：scale 写文件、命令行参数覆盖它，deploy.replicas 属集群规范。



#### deploy 段在非 Swarm 环境的生效范围

**生效范围**：官方规范把 deploy 明确定位为可选部分，未被平台实现时整段被忽略而文件仍视为有效；普通 docker compose 只实现其中与容器运行时直接相关的一小部分。

- **规范措辞**：部署规范开篇写明 Deploy 是 Compose 规范的可选部分；services 参考进一步写明，未被实现时 deploy 段被忽略，文件仍视为有效。
- **单机可用部分**：deploy.resources 下的 limits 与 reservations 对应容器运行时的资源约束；官方要求其取值与服务级 cpus、mem_limit、mem_reservation、pids_limit 保持一致。
- **无调度意义的字段**：mode、replicas、placement、update_config、rollback_config、endpoint_mode 描述的是集群调度与更新行为，单机没有调度器来执行。
- **服务标签**：部署规范指出 deploy.labels 只设在服务上，不设在该服务的任何容器上。
- **重启策略**：单机重启行为由服务级 restart 字段承担，deploy.restart_policy 属部署规范。
- **兼容模式**：CLI 提供 compatibility 选项，官方描述为以后向兼容模式运行 Compose。

```yaml
services:
  api:
    image: node:22-alpine
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 512M
        reservations:
          memory: 128M
```

> [!WARNING]
> **警告内容**：写了 deploy.replicas 却不生效时不报错、不告警，文件依然合法，这是最容易被误认为「配置已生效」的一类静默失效。需要副本数就明确用 scale 或命令行参数，不要依赖未实现的部署字段。

**速记**：deploy 整段可选、未实现即忽略；单机真正落地的多为 resources 的资源约束。



#### 扩容时的端口冲突与反向代理的分工

**冲突根源**：端口映射把容器端口绑定到宿主端口，同一宿主端口不能被两个容器同时占用，因此发布了固定宿主端口的服务无法扩出第二个副本。

- **冲突对象**：写了形如主机端口冒号容器端口的 ports 项时，每个副本都试图绑定同一宿主端口，第二个副本创建失败。
- **可扩容的服务**：只用 expose 声明端口、或完全不发布端口的服务，副本之间端口互不冲突。
- **不可扩容的服务**：发布固定宿主端口的入口服务，以及数据库这类有状态服务，通常保持单副本。
- **有状态前提**：多个副本共享同一数据卷会引发写冲突，扩缩容的前提是服务本身无状态。
- **正确分层**：把「谁负责监听宿主端口」交给唯一的反向代理，应用服务只在内部网络上暴露端口，副本数便可自由调整。

```yaml
services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"

  api:
    image: node:22-alpine
    expose:
      - "3000"
```

> [!CAUTION]
> **注意内容**：用服务名做 Nginx 的上游时，Nginx 只在启动或重载配置时解析一次地址，扩容后新增的副本不会被已在运行的 Nginx 自动纳入。要么按反向代理一章的做法配置解析器与变量转发，要么在扩容后重建代理容器。

**速记**：发布固定宿主端口的服务不可多副本，监听端口交给唯一的反向代理，应用只 expose。



### 服务间的等待与重试模式

#### 依赖编排与重试的分工

**分工原则**：依赖编排负责「启动顺序」，应用侧重试负责「依赖短暂不可用时的自愈」；前者是静态声明，后者是运行时韧性，二者叠加而非互相替代。

- **依赖编排的职责**：保证迁移先于应用、数据库先于应用启动，减少必然失败的启动。
- **重试的职责**：覆盖运行期依赖抖动、数据库故障切换、连接池断连等编排无法预知的场景。
- **只靠编排的不足**：依赖条件只作用于启动那一次，运行中依赖重启不会触发重排。
- **只靠重试的不足**：没有启动顺序时，应用在表结构尚未创建阶段反复重试，日志噪音大且掩盖真实错误。
- **组合做法**：声明层用 condition 保障顺序，应用层用连接重试与退避保障韧性。

> 判定故障属于哪一类：日志在启动后立即出现且只出现一次，多指向启动顺序；日志在运行中周期性出现，多指向运行时抖动，应对手段不同。

**速记**：编排管启动顺序，重试管运行期抖动，两者叠加。



#### wait-for 脚本与重试库的取舍

**两类手段**：wait-for 类脚本把等待放在容器启动命令里，阻塞到依赖可连才启动主进程；重试库把等待放进应用代码，主进程先起来、连接失败按策略重试。

- **wait-for 脚本**：入口脚本先轮询依赖端口或健康端点，就绪后再执行主进程，改动小、依赖少。
- **重试库**：在数据库客户端调用处包一层重试与指数退避，天然覆盖运行期断连。
- **wait-for 的优点**：应用代码零改动，适合快速给老项目补上等待。
- **wait-for 的缺点**：只判断端口可连，不代表依赖真正可用，且它把启动阻塞在单个依赖上，任一依赖慢都会拖住启动。
- **重试库的优点**：覆盖运行期，能区分可重试与不可重试错误，退避策略可控。
- **取舍结论**：一次性启动顺序交给依赖条件与健康检查，应用内的连接建立与恢复交给重试库，wait-for 只作为两者都不便改动时的补充。

```javascript
async function connectWithRetry(makeClient, retries = 10, delayMs = 2000) {
  for (let attempt = 1; attempt <= retries; attempt += 1) {
    try {
      return await makeClient();
    } catch (err) {
      if (attempt === retries) throw err;
      await new Promise((resolve) => setTimeout(resolve, delayMs * attempt));
    }
  }
}
```

> [!TIP]
> **建议内容**：重试必须配退避与上限。固定间隔的无限重试会在依赖长时间不可用时把日志与连接数打满；线性或指数退避加上最大次数，既能自愈也能让真正的故障快速暴露。

**速记**：wait-for 阻塞启动、重试库覆盖运行期，顺序靠编排，韧性靠重试。



#### 把健康检查写成真正可用

**可用性定义**：健康检查应回答「这个服务现在能否正确处理请求」，而不是「容器里还有没有进程」；进程存活但依赖断开、连接池耗尽时，服务实际上不可用。

- **反例：进程检查**：判断主进程存在或某个二进制可响应，只能说明容器没崩，不能说明请求能成功。
- **正例：就绪端点**：暴露一个就绪接口，内部真实检查数据库与缓存可达性，探针请求该接口。
- **区分存活与就绪**：存活探针回答「要不要重启」，就绪探针回答「要不要接流量」，容器场景下 depends_on 消费的是后者。
- **避免过重**：探针应轻量、快速、不写数据、不触发昂贵查询，否则健康检查本身成为负载来源。
- **超时与间隔匹配**：探测超时要小于业务可接受的中断时长，避免依赖已恢复但探针长时间未更新状态。

```javascript
// 就绪端点：真实检查下游依赖是否可用
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');
    await cache.ping();
    res.status(200).json({ status: 'ok' });
  } catch (err) {
    res.status(503).json({ status: 'degraded' });
  }
});
```

> [!IMPORTANT]
> **重要内容**：把依赖检查塞进健康检查会放大故障面——数据库短暂不可用会让所有应用副本同时被判为不健康，进而被重启或从依赖链上摘除。就绪端点宜区分「自身可用」与「依赖降级」，按业务容忍度决定哪一类计入不健康。

**速记**：健康检查查请求可用性，不查进程存活，区分存活探针与就绪探针。



### 完整实战栈一：反向代理加应用加数据库加缓存

#### 栈的组成与拓扑

**栈构成**：五个服务分别是反向代理 proxy、应用 api、数据库 db、缓存 cache，以及跑完即退的迁移任务 migrate，另有一个放进 debug profile 的管理界面 adminer。

- **唯一入口**：proxy 发布唯一的宿主端口对外暴露，api 只用 expose 在内部网络提供端口。
- **网络分层**：proxy 与 api 连 frontend 网络，api、db、cache、migrate 连 backend 网络，数据库与缓存不接入 frontend。
- **数据持久化**：db 与 cache 各用一个命名卷保存数据，容器重建不丢。
- **启动链条**：migrate 等 db 健康，api 等 db 健康、cache 健康且 migrate 成功完成，proxy 等 api 健康。
- **配置注入**：非敏感变量经 env_file 注入，敏感取值演示用环境变量，真实环境应改用密钥机制。
- **复用片段**：日志与健康检查默认参数以 x- 扩展字段抽出，多个服务引用。

> 拓扑的核心是把「监听宿主端口」与「提供业务端口」两件事拆给不同服务，前者唯一、后者可多副本，这是无状态扩容的前提。

**速记**：一个入口、两张网络、两个命名卷、三段依赖链。



#### compose.yaml 全文

把前文分散讲的依赖编排、健康检查与多文件合并规则收拢成一份可直接启动的完整编排文件。

```yaml
name: demo-stack

x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

x-healthcheck-defaults: &healthcheck-defaults
  interval: 10s
  timeout: 3s
  retries: 5
  start_period: 15s

services:
  proxy:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    healthcheck:
      <<: *healthcheck-defaults
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1/health"]
    depends_on:
      api:
        condition: service_healthy
    networks:
      - frontend
    logging: *default-logging
    restart: unless-stopped

  api:
    build:
      context: ./api
      dockerfile: Dockerfile
    env_file:
      - ./api/api.env
    environment:
      NODE_ENV: production
      PORT: "3000"
      DATABASE_URL: postgres://app:secret@db:5432/shop
      REDIS_URL: redis://cache:6379
    expose:
      - "3000"
    healthcheck:
      <<: *healthcheck-defaults
      test: ["CMD", "node", "-e", "fetch('http://127.0.0.1:3000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"]
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    networks:
      - frontend
      - backend
    logging: *default-logging
    restart: unless-stopped

  migrate:
    build:
      context: ./api
      dockerfile: Dockerfile
    command: ["node", "scripts/migrate.js"]
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/shop
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend
    restart: "no"

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: shop
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      <<: *healthcheck-defaults
      start_period: 30s
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
    networks:
      - backend
    logging: *default-logging
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - cache-data:/data
    healthcheck:
      <<: *healthcheck-defaults
      test: ["CMD", "redis-cli", "ping"]
    networks:
      - backend
    logging: *default-logging
    restart: unless-stopped

  adminer:
    image: adminer:4
    profiles: ["debug"]
    ports:
      - "127.0.0.1:8081:8080"
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend

volumes:
  db-data:
  cache-data:

networks:
  frontend:
  backend:
```

配套的 Nginx 站点配置只需把请求转给 api，并透传真实客户端信息。

```conf
upstream api_upstream {
    server api:3000;
    keepalive 16;
}

server {
    listen 80;

    location = /health {
        return 200 "ok\n";
    }

    location / {
        proxy_pass http://api_upstream;
        proxy_http_version 1.1;
        proxy_set_header Connection        "";
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> [!NOTE]
> **提醒内容**：proxy 自身的健康检查探测的是 Nginx 本地的 health 路径，不转发到 api，这样代理层的健康状态只反映自身进程，不会因后端抖动而被判为不健康。后端可用性由 api 自己的健康检查与依赖链把关。

**速记**：proxy 唯一对外、api 只 expose，迁移等数据库健康，api 等三方就绪，日志与探针走公共片段。



#### 逐段讲解

**逐段要点**：从项目名到各服务的依赖条件，每一段都对应启动链条上的一个环节。

- **name**：固定项目名为 demo-stack，容器名前缀、网络与卷的归属都以此为准。
- **x-logging 与 x-healthcheck-defaults**：顶层扩展字段承载公共片段，服务内以锚点引入并就地覆盖。
- **proxy**：映射宿主 8080 到容器 80，只读挂载站点配置；依赖 api 健康后才启动，保证入口一开就能转发。
- **api**：build 出应用镜像，env_file 注入非敏感变量、environment 覆盖并补充敏感取值；只 expose 不发布端口，故可多副本。
- **migrate**：与 api 同镜像，command 覆盖为迁移脚本；依赖 db 健康，跑完即退，restart 为 no。
- **db 与 cache**：数据库与缓存各挂命名卷；健康检查分别用 pg_isready 与 redis-cli ping；start_period 为首次初始化留出时间。
- **adminer**：放进 debug profile，端口绑到 127.0.0.1，默认不启动、不进默认启动集。
- **顶层 volumes 与 networks**：声明 db-data、cache-data 两个命名卷与 frontend、backend 两张网络。

> [!CAUTION]
> **注意内容**：示例中的数据库口令是明文占位值。真实项目应把口令抽到环境变量文件或密钥机制，并确保其不进入版本库；数据库与缓存也不应接入对外网络。

**速记**：扩展字段搭骨架，依赖条件串链条，命名卷存数据，两张网络分内外。



### 完整实战栈二：从零跑起来

#### 构建与首次启动

**首次启动序列**：先在不动容器的情况下校验配置，再构建应用镜像，然后后台启动并等待服务达到运行或健康状态。

- **校验**：config 加 quiet 确认语法、插值、合并与路径均无问题。
- **构建**：up 加 build 在启动前构建带 build 段的服务，也可先单独 build 再 up。
- **后台启动**：加 -d 让服务在后台创建并启动，命令立即返回。
- **等待就绪**：加 wait 让命令等到服务进入运行或健康状态再返回，隐含 detached 模式。
- **等待上限**：配合 wait-timeout 指定最长等待秒数，避免卡死。

```bash
docker compose config --quiet
docker compose build
docker compose up -d --build
docker compose up -d --wait --wait-timeout 120
```

> [!TIP]
> **建议内容**：首次启动用 up 加 wait，脚本据此判断「环境真的可用了」而不是「容器已创建」。CI 或自动化脚本里，等健康状态比等容器创建更能反映真实就绪。

**速记**：先 config、再 build、后 up，脚本场景加 wait 等健康。



#### 确认就绪与执行迁移

**确认动作**：用 ps 看各容器状态，用 logs 跟关键服务日志确认连接建立，用 exec 进数据库核对迁移后的表结构。

- **状态查看**：compose ps 显示各服务的状态与端口，健康服务显示 healthy。
- **日志确认**：跟随 api 日志，确认已连接数据库与缓存、迁移版本已应用。
- **进入排查**：exec 进数据库容器执行客户端命令，列出表与版本表。
- **重跑迁移**：迁移失败时用 run 加 rm 以一次性容器重跑，不影响其余服务。
- **全量查看**：ps 加 -a 可看到已退出的迁移容器及其退出码。

```bash
docker compose ps
docker compose logs --tail=100 api
docker compose exec db psql -U app -d shop -c "\dt"
docker compose run --rm migrate
docker compose ps -a
```

> 迁移服务在常态下应显示 Exited (0)。若显示非 0 退出码，说明建表或脚本本身出错，此时应用会停在等待迁移完成的依赖条件上，日志中的报错就是第一现场。

**速记**：ps 看状态、logs 看连接、exec 看表结构、run 重跑迁移。



#### 访问验证与优雅停止

**验证与停止**：通过宿主端口验证入口可达，然后按需选择停止方式，并在清理时明确是否保留数据。

- **访问验证**：请求宿主 8080，应经 proxy 转发到 api 并得到正常响应。
- **容器内验证**：在 proxy 或 api 容器内直接请求服务名，验证网络内解析与连通。
- **临时暂停**：stop 停止运行中的容器但保留容器本身，start 再启动，适合短暂离开。
- **拆除环境**：down 停止并移除容器与网络，命名卷默认保留。
- **删除数据**：down 加 -v 会连同命名卷一起删除，数据库与缓存数据不可恢复。
- **清理孤儿**：down 加 remove-orphans 一并移除已从文件中删除的旧服务残留的容器。

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/health
docker compose exec proxy wget -qO- http://api:3000/health
docker compose stop
docker compose down
docker compose down -v
```

> [!WARNING]
> **警告内容**：down 加 -v 会删除命名卷，数据库与缓存中的持久化数据一并丢失且不可恢复。日常重启只应使用 stop 或 down，只有在确认数据可弃或已有备份时才加 -v。

**速记**：curl 验证入口、exec 验证内网；stop 留容器、down 删容器与网络、加 -v 连数据一起删。



#### 日常开发循环

**开发循环**：改代码、重建目标服务、只看该服务日志、必要时进容器排查，形成短回路，避免每次都重建整组容器。

- **改动源码**：开发覆盖文件把源码目录绑定挂载进容器，改动无需重建镜像即生效。
- **改动构建依赖**：改了 Dockerfile 或依赖清单才需要 build 对应服务，再 up 该服务。
- **重建单服务**：up 后接服务名，只重建配置或镜像发生变化的那个服务。
- **只看单服务日志**：logs 加服务名与 tail 限定输出范围。
- **进容器排查**：exec 加服务名进入运行中的容器，查进程、文件与环境变量。
- **进未启动的服务**：run 加 rm 以一次性容器执行命令，适合迁移与脚本类操作。

```bash
docker compose -f compose.yaml -f compose.dev.yaml up -d
docker compose build api
docker compose up -d api
docker compose logs -f --tail=50 api
docker compose exec api sh
docker compose run --rm migrate
```

> watch 可在文件变化时自动同步或重建，但它需要 Compose 2.22 及以上，且面向开发期。团队里用不用它应统一约定，避免同一份配置在不同机器上行为不一致。

**速记**：改代码靠挂载、改依赖才 build、单服务 up 单服务看日志、进容器用 exec、临时任务用 run。



### 常见进阶报错与处置

#### 依赖条件写错导致永不启动

**报错特征**：启动停在等待阶段，依赖方一直不启动，最终报依赖未能满足的错误，容器可能连创建都没发生。

- **被依赖服务没有健康检查**：写了 condition 为 service_healthy，但被依赖服务未定义 healthcheck，条件没有判定依据。
- **服务名拼错**：condition 下的键写错，Compose 会指向不存在的服务或改名后的服务。
- **条件与被依赖服务的退出行为不匹配**：常驻服务用了 service_completed_successfully，该服务永不成功退出，依赖方永不启动。
- **一次性任务用了 service_started**：任务刚启动依赖方就放行，实际可能在建表途中，表现为间歇性失败。
- **排查手段**：用 compose config 看渲染后的依赖关系，用 ps 看被依赖服务是否达到所需状态。

```bash
docker compose config
docker compose ps
docker compose logs db
```

> [!CAUTION]
> **注意内容**：把常驻服务的依赖条件写成 service_completed_successfully 是最典型的「永不启动」，数据库不会以退出码 0 结束，条件永远不满足。条件类型必须与被依赖服务的生命周期形态对应。

**速记**：常驻服务配 healthy、一次性任务配 completed_successfully，先看依赖有没有健康检查。



#### 健康检查过严导致不断重启

**报错特征**：容器反复进入 unhealthy 并被重启，日志本身没有业务错误，但状态始终无法稳定为 healthy。

- **超时过短**：探针命令本身耗时超过 timeout，每次都以超时收场。
- **start_period 不足**：数据库或应用首次启动慢，宽限期内未成功，随后被记为失败并累积到 retries。
- **探针过重**：探针触发全表扫描或复杂查询，自身拖慢服务，形成越查越慢的循环。
- **工具缺失**：精简镜像里没有 curl，CMD 形式的探针直接以命令不存在失败。
- **排查手段**：用 exec 在容器里手工执行探针命令，看真实耗时与输出，再对照健康状态的判定。

```bash
docker compose ps
docker compose exec api node -e "fetch('http://127.0.0.1:3000/health').then(r => console.log(r.status))"
docker inspect --format '{{.State.Health}}' demo-stack-api-1
```

> 健康检查的失败是一种「判定」，不是「修复」。探针配置不当导致的 unhealthy 会误导后续所有依赖它的服务，先把探针本身调到能稳定反映真实状态，再去看业务。

**速记**：超时看单次耗时、宽限看首次启动、探针要轻、工具要存在。



#### profiles 未启用导致服务缺失

**报错特征**：文件里明明写了管理界面或监控组件，up 之后却找不到对应容器，ps 里也不显示。

- **默认隐藏**：服务带 profiles 且未启用对应 profile，属预期行为，不是故障。
- **依赖断裂**：默认服务依赖了带 profile 的服务，若依赖方自身也需要在默认集里运行，则会报依赖缺失。
- **网络与卷不受影响**：profiles 只影响服务，其它顶层元素始终生效。
- **排查手段**：看该服务的 profiles 取值，再用 profile 参数重新执行；config 不带参数时不会渲染被忽略的服务，可加 profiles 选项只列出档案名。
- **清理注意**：down 同样受 profile 影响，未启用的 profile 下服务不会被 down 处理。

```bash
docker compose config --profiles
docker compose --profile debug up -d
docker compose --profile debug down
```

> 显式点名某个带 profile 的服务时会自动激活其 profile，因此跑过一次以 adminer 为目标的命令后，不要误以为该服务已进入默认启动集。

**速记**：查 profiles 取值、按需加 profile 参数，config 不带参数看不到被隐藏的服务。



#### 多文件合并后端口重复与 override 意外生效

**报错特征**：端口绑定报已被占用，或实际生效的端口、环境变量与基础文件不符，指向合并结果与预期不一致。

- **端口拼接导致重复**：ports 属拼接字段，基础文件与覆盖文件都写了同一宿主端口，合并后同端口出现两次，创建时报冲突。
- **override 静默生效**：compose.override.yaml 未在命令中提及却自动叠加，把覆盖值当成了基础值。
- **顺序写反**：-f 列表里覆盖文件写在基础文件之前，基础值反而盖住了覆盖值。
- **路径基准误判**：覆盖文件里的相对路径相对第一个文件解析，写错时会挂到非预期目录。
- **排查手段**：用 config 查看最终配置，逐个核对端口、环境变量与挂载路径。

```bash
docker compose config
```

#### replicas 与 container_name 冲突

**报错特征**：尝试扩展写了 container_name 的服务时报错，提示无法扩展或名称冲突。

- **根本原因**：固定容器名意味着同一服务只能有一个容器；官方 container_name 条目写明，指定后 Compose 不会把该服务扩展到多于一个容器，尝试扩展会报错。
- **与 scale 的关系**：scale 或命令行参数大于 1 时，若服务写了 container_name，两者要求相互矛盾。
- **与 deploy.replicas 的关系**：同理，副本数与固定名不可共存。
- **处置一**：删掉 container_name，让 Compose 按项目名与服务名自动命名。
- **处置二**：确实需要固定引用名时保持单副本，用项目名与服务名定位容器，而不是死记固定名。

```yaml
services:
  api:
    image: node:22-alpine
    # container_name: demo-api   # 写了它就无法多副本
    expose:
      - "3000"
```

```bash
docker compose up -d --scale api=3
```

> [!IMPORTANT]
> **重要内容**：container_name 换来的稳定性是「名字可预期」，代价是「不可扩展」且跨项目可能重名。需要多副本的服务一律让 Compose 自动命名，脚本定位容器应改用服务名加项目名，而不是死记容器名。

**速记**：固定名只能单副本，要扩展就去掉 container_name。
