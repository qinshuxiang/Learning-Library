## 镜像仓库与私有 Registry

### 仓库的两种形态与选型

#### 公共托管仓库与自建私有仓库的分工

**公共托管仓库**：由第三方运营、面向任何用户开放或按账号授权分发的镜像服务，Docker Hub 是默认目标。**自建私有仓库**：由使用方自行部署与运维的镜像服务，数据与账号体系完全掌握在自己手里。

- 公共托管仓库的特点是零运维、上手即用，代价是受服务方的配额、速率、隐私与可用性政策约束。
- 自建私有仓库的特点是数据不出内网、可深度定制认证与治理，代价是要自行承担部署、证书、备份、升级与磁盘运维。
- 两者不是二选一：常见结构是基础镜像走公共仓库，业务镜像走自建仓库，再以 pull-through cache 把两条路径衔接起来。
- 判据是镜像里有没有不该外流的内容，以及拉取量会不会被配额卡住。

> 篇 2 已给出 registry、repository、tag 三者的概念层级，篇 3 已列出 pull、push、tag 的命令形态，本篇只从仓库侧讲分发、认证与治理，不再重复命名规则与 tag 与 digest 的定义。

**速记**：公共托管省运维受配额，自建私有保数据担运维；基础镜像与业务镜像可各走一条路。



#### 自建私有仓库的三条路线

**三条自建路线**：官方 distribution 镜像、Harbor、云厂商托管仓库，分别对应最简、最全、最省运维三种诉求。

- **官方 registry 镜像**：CNCF Distribution 项目发布的轻量服务，一条 docker run 即可跑起来，只有一个二进制与一份 config.yml，没有界面、没有用户体系、没有扫描。
- **Harbor**：CNCF 毕业项目，在 registry 之上补齐项目、角色、复制、扫描、签名、配额与保留策略，以安装器与 Compose 或 Helm 部署，组件多、资源占用高。
- **云厂商托管**：把仓库交给云上的容器镜像服务，按量或按套餐计费，免去证书、存储与高可用，代价是绑定厂商、数据出网与可能的跨区流量费。
- 三条路线能力由低到高大致是官方镜像、Harbor、云托管，运维负担的顺序则相反。

> 选型的第一个问题不是功能而是边界：仓库是否只在内网可达、是否必须自持数据、是否要对接单位的统一认证，这三项先定下来，路线往往只剩一条。

**速记**：官方镜像最简、Harbor 最全、云托管最省心；能力越高，运维与成本越高。



#### 小团队与企业的选择建议

**选择主线**：以内网可达性与治理需求为轴做决定，而不是以装机量或预算单点判断。

- 小团队与单机部署：先用官方 registry 镜像加 TLS 与 Basic 认证，够稳定够省资源，后续有治理需求再换 Harbor。
- 需要多项目隔离、跨机房复制、漏洞扫描与审计的中型企业：直接上 Harbor，避免在裸 registry 上自行拼装这些能力。
- 已经有云账号、且合规允许镜像出网的组织：优先用云厂商托管，把证书、高可用与磁盘扩容交给服务方。
- 无论走哪条路线，都应先把命名规范、标签规范与保留策略定下来，仓库只是执行这些约定的载体。
- 自建路线的共同前置是给仓库一个稳定的域名与受信任的证书，否则客户端每次都要改 daemon.json 才能用。

> [!NOTE]
> **提醒内容**：本篇的选型建议只讲判断维度，不涉及具体采购与硬件配置。部署规模、磁盘容量与高可用形态应由实际的镜像拉取量、并发数与保留周期推算，而非照搬固定配置。

**速记**：小团队用官方镜像，中型企业上 Harbor，有云账号且允许出网用云托管；先定规范再选仓库。



### Docker Hub 的实务

#### 账号、命名空间与仓库可见性

**命名空间（Namespace）**：Docker Hub 上归属于某个账号或组织的顶层名字段，决定镜像的完整路径与推送权限。**仓库可见性**：单个 repository 可设为公共或私有，公共仓库任何人可拉取，私有仓库仅授权账号可拉取。

- 完整名称形如 命名空间/仓库名:标签；官方维护的镜像不带命名空间前缀，如 nginx、redis 属 Docker 官方库。
- 个人账号默认有一个与用户名同名的命名空间；组织（Organization）可再分出多个命名空间并分配团队权限。
- 公共仓库免费但内容公开，私有仓库的数量与成员数受套餐约束，Team 及以上套餐另有服务账号。
- 仓库一旦被大量用户依赖，删除或改写已发布的同名标签会造成下游构建莫名失败，公共仓库尤其要克制。
- 命名空间不能重命名，账号改名不会迁移旧镜像路径，选名前要留出长期空间。

```bash
docker pull nginx:1.27-alpine                        # 官方库镜像，无命名空间前缀
docker pull alice/web-api:1.0.0                       # 个人命名空间
docker tag web-api:1.0.0 alice/web-api:1.0.0
docker push alice/web-api:1.0.0
```

> 私有仓库的私有只作用于拉取权限；把它当成存放密钥的地方并不合适，镜像层里的任何文件对有权拉取的人都可见。

**速记**：命名空间定路径与归属，公共人人可拉、私有按账号授权；官方镜像不带前缀。



#### 拉取速率限制的机制与额度

**拉取速率限制（Pull Rate Limit）**：按统计窗口对镜像拉取请求计数并在超限时拒绝的限制，按用户类型给不同额度。Docker 官方文档 Docker Hub usage 页给出的口径如下。

- **匿名未认证**：按每个 IPv4 地址或每个 IPv6 的 /64 子网统计，每 6 小时 100 次拉取。
- **免费账号已认证**：每 6 小时 200 次拉取。
- **付费套餐已认证**：Pro、Team、Business 等付费层级在认证状态下不受拉取速率限制。
- 计数按拉取动作而非按层计，一次 docker pull 计一次；同一网段内多台机器匿名拉取会共享同一个额度。
- 超限时返回 429 与一条带文档链接的错误消息，据此可与另一种限制区分。

> [!IMPORTANT]
> **重要内容**：以上额度是官方文档在 2026 年 9 月记录的数值，Docker 明确保留调整权利，且所有使用都受合理使用条款约束。另有一类滥用速率限制，面向所有层级的账号，按 IPv4 地址或 IPv6 子网统计全部 Hub 请求，阈值随负载浮动，命中后返回不带文档链接的 429。实际以官方文档为准，不要把这些数字当成长期承诺。

**速记**：匿名 100 次 6 小时、免费认证 200 次 6 小时、付费认证不限额；按拉取次数计、按 IP 或子网聚合，额度随时可变。



#### 避免被限流的四种手段

**避限流思路**：把拉取从每个客户端各自向 Hub 请求，改成集中认证、集中缓存、集中代理，减少对 Hub 的直接命中。

- **登录认证**：对匿名受限最直接，登录后额度翻倍，CI 中应配置专用只读账号或服务账号。
- **自建缓存**：用 pull-through cache 把常用基础镜像缓存在内网，第二次拉取不再打到 Hub。
- **镜像代理**：在内网部署代理镜像服务，客户端把 Hub 请求交给它，由它统一向上游取。
- **基础镜像本地化**：把 nginx、node、postgres 这类反复使用的基础镜像拉到自建仓库并固定标签，业务构建从自建仓库取基础镜像。
- 四者叠加效果最好：登录解决额度，缓存解决重复，代理解决并发，本地化解决长期稳定性。

```bash
docker login                       # 认证后匿名 100 次提升为免费账号的 200 次
docker pull registry.example.com/library/nginx:1.27   # 改从自建仓库取基础镜像
```

> 把限流当成容量问题而非偶发故障来治理——在 CI 里固定使用服务账号并缓存构建层，在开发机上统一指向内网缓存，比限流发生后逐台机器登录更省事。

**速记**：登录提额、缓存复用、代理集中、基础镜像本地化。



### 使用远程仓库的完整流程

#### docker login 与凭证落点

**docker login**：向指定仓库提交用户名与口令以换取访问凭据，成功后把凭据写入本地配置，后续 pull、push 自动携带。不指定服务器地址时默认登录 Docker Hub。

- 命令形式为 docker login 仓库地址，地址含端口时端口要写全，如 registry.example.com:5000。
- 口令可以用 --password-stdin 从标准输入读入，避免出现在命令历史与进程列表里，CI 中应一律用这种方式。
- 成功输出 Login Succeeded；认证失败返回 401，需区分是账号错、口令错还是该仓库未启用该认证方式。
- 登录成功只代表当前客户端拿到凭据，不代表对该仓库的每个路径都有推送权限，权限按仓库侧的角色判定。
- docker logout 只删除本地保存的凭据，不影响仓库侧的账号。

```bash
docker login registry.example.com
echo "$REGISTRY_TOKEN" | docker login registry.example.com -u ci-bot --password-stdin
docker logout registry.example.com
```

> [!WARNING]
> **警告内容**：在命令行直接写 --password 会把口令留在 shell 历史与进程列表里，同机的其他用户可读。任何自动化场景都应改用 --password-stdin，并用只读或最小权限的令牌而非主账号口令。

**速记**：docker login 地址换凭据，口令走标准输入，logout 只删本地。



#### 打标签的命名要求

**推送目标由标签决定**：docker push 依据镜像名第一段是否含点号或冒号来判断有没有带仓库主机名；不带主机名就按 Docker Hub 处理。

- 完整标签形如 主机:端口/命名空间/仓库名:标签，其中主机段是识别自建仓库的唯一依据。
- 要推到自建仓库，必须先 docker tag 出一个带该主机前缀的新名字，原镜像数据不复制，只是多一个引用。
- 只写 localhost:5000 这类主机名而不写端口时，客户端会按默认 443 连接，导致连不上，端口必须显式写全。
- 标签部分省略时补 latest，仅作占位，不代表最新，推送前应显式写版本标签。
- 同一镜像可同时拥有本地名与仓库全名两个标签，二者指向同一镜像 ID。

```bash
docker tag myapp:1.0 registry.example.com:5000/team/myapp:1.0
docker images --filter reference='registry.example.com:5000/*'
```

```text
REPOSITORY                                    TAG     IMAGE ID
registry.example.com:5000/team/myapp          1.0     a1b2c3d4e5f6
```

> 判断该不该带前缀只需看名字里有没有主机：myapp:1.0 会被当作 Docker Hub 官方库的仓库名，registry.example.com/team/myapp:1.0 才指向自建仓库。

**速记**：名字带主机前缀才推自建仓库，主机带端口要写全，tag 只加引用不复制数据。



#### push 与 pull 的完整命令序列

**完整流程**：登录、构建或准备镜像、打全名标签、推送、在目标机拉取，五步构成一次跨仓库分发。

- 第一步登录目标仓库，拿到推送权限。
- 第二步在本地构建或用 docker pull 取得镜像，并保证有版本明确的标签。
- 第三步用 docker tag 打上带主机前缀与目标命名空间的完整名。
- 第四步 docker push 完整名，客户端逐层比对，只上传本地有而仓库缺的层。
- 第五步在另一台机器 docker login 后 docker pull 完整名，随后即可 run 或写进 Compose 的 image 字段。

```bash
docker build -t myapp:1.0 .
docker tag myapp:1.0 registry.example.com:5000/team/myapp:1.0
docker push registry.example.com:5000/team/myapp:1.0
# 目标机器
docker login registry.example.com:5000
docker pull registry.example.com:5000/team/myapp:1.0
```

```text
The push refers to repository [registry.example.com:5000/team/myapp]
1.0: digest: sha256:9f2a... size: 1987
```

> push 的输出以 digest 结尾，这是内容的摘要，等同于不可变的镜像标识；发布记录里应同时记下标签与 digest，标签可变而 digest 不变。

**速记**：登录、构建、打全名、push、他机 pull；标签与 digest 并记。



#### 推不上去的三种常见原因

**典型失败**：标签没带主机名、主机名或端口写错、账号对该路径没有推送权限，三者合计解释绝大多数推送失败。

- **标签没带主机名**：直接 push myapp:1.0 被当作推 Docker Hub，多半报 requested access to the resource is denied 或要求登录。
- **主机名与端口写错**：漏写端口、把容器内端口当对外端口、写了内网不可达的地址，表现为 connection refused 或 i/o timeout。
- **权限不足**：账号口令正确但对目标命名空间没有写权限，返回 401 unauthorized 或 403 denied。
- **证书不被信任**：自建仓库用了自签证书而未让客户端信任，报 x509 证书错误，需配置受信任证书而不是关掉校验。
- **认证方式不匹配**：仓库启用了 Basic 认证但客户端未登录，或仓库只允许令牌认证，都会在握手阶段被拒。

```bash
docker push myapp:1.0                                    # 反例：被当作 Docker Hub
docker push registry.example.com:5000/team/myapp:1.0     # 正例：带全主机与端口
curl -u ci-bot https://registry.example.com:5000/v2/     # 验证认证与可达性
```

> [!CAUTION]
> **注意内容**：为了绕过证书错误而给守护进程加不校验 TLS 的选项，等于把镜像分发暴露给中间人。正确做法是把自建仓库的 CA 证书放进客户端的受信任目录，而不是降低校验强度。

**速记**：先看标签带没带主机、再看主机端口对不对、最后看权限与证书。



### 凭证管理

#### config.json 的结构与 base64 的性质

**Docker 配置文件**：Linux 默认位于 ~/.docker/config.json，Windows 位于 %USERPROFILE%/.docker/config.json，记录认证、上下文与客户端行为。未配置凭据助手时，登录信息写在其中的 auths 段。

- auths 的键是仓库地址，值是含 auth 字段的对象，auth 是用户名与口令以冒号连接后经 base64 编码的字符串。
- 键为 https://index.docker.io/v1/ 的条目对应 Docker Hub 登录。
- base64 只是把字节转成可打印字符的编码，任何人可一条命令还原，不具备保密性。
- 该文件权限默认为仅属主可读写，但一旦被同步、备份或提交进版本库，编码就不再提供任何保护。
- 出现 credsStore 或 credHelpers 时，对应仓库的凭据不再落在此文件中，auths 段可能为空或只剩非敏感占位。

```json
{
  "auths": {
    "registry.example.com:5000": {
      "auth": "Y2ktYm90OnMzY3JldA=="
    }
  }
}
```

```bash
echo Y2ktYm90OnMzY3JldA== | base64 -d    # 还原为 ci-bot 加口令
```

> [!WARNING]
> **警告内容**：base64 不是加密。config.json 里的 auth 字段可被任何拿到该文件的人直接解码还原出账号与口令，切勿把它提交进版本库、贴进工单或放进共享目录。生产与 CI 环境应改用凭据助手，或以 Secret 形式注入临时凭据。

**速记**：config.json 的 auths 段存登录，auth 是账号口令的 base64，编码不等于加密。



#### credential helper 机制与配置写法

**凭据助手（Credential Helper）**：实现固定协议的独立程序，把凭据交给操作系统的安全存储保管，Docker 通过它存取而不再写明文到 config.json。

- 助手名字形如 docker-credential-后缀，config.json 里只记后缀。
- credsStore 指定全局默认助手，所有仓库的凭据都交给它。
- credHelpers 按键为仓库地址指定助手，优先级高于 credsStore，用于个别仓库走不同存储。
- 助手须在客户端主机的 PATH 中可执行，缺失时 Docker 会回退到把凭据写入 config.json。
- 各平台默认助手：macOS 为 osxkeychain，Windows 为 wincred，Linux 为 pass，Linux 找不到 pass 时回退 secretservice；Docker Desktop 已预装并自动配置。

```json
{
  "credsStore": "osxkeychain",
  "credHelpers": {
    "registry.example.com:5000": "pass"
  }
}
```

```bash
docker-credential-osxkeychain list       # 列出该助手已保存的仓库
docker logout registry.example.com:5000
docker login registry.example.com:5000   # 切换助手后需重新登录
```

> 从明文存储改为凭据助手后，旧凭据不会自动迁移，必须先 docker logout 再 docker login，否则助手查不到凭据仍会走旧路径。

**速记**：credsStore 设全局助手、credHelpers 按仓库设；macOS 用 osxkeychain、Linux 用 pass 或 secretservice，改后要重新登录。



#### 多账号与多仓库的切换

**多账号并存**：Docker 客户端按仓库地址分别保存凭据，同一仓库同一时刻只有一个有效身份，切换靠重新登录。

- 不同仓库的账号互不干扰，可同时保存，拉取时按镜像名中的主机段自动选用对应凭据。
- 同一仓库要切换账号，只能再次 docker login 覆盖，或用 docker logout 清除后重新登录。
- Docker Hub 的账号与自建仓库账号各存一条，分别以 index.docker.io 与自建主机名为键。
- 借助 credHelpers 可让同一主机下的不同用途走不同助手，但同一主机仍只有一个当前凭据。
- 命令行选项 --config 可让某次命令使用另一份配置目录，用于在同一台机器上隔离多套身份。

```bash
DOCKER_CONFIG=~/.docker-ci docker login registry.example.com:5000   # 临时换一份配置
docker context ls                                                   # 确认当前上下文与目标主机
```

> [!TIP]
> **建议内容**：人工操作账号与自动化账号应分开，各自使用独立的配置目录或独立的凭据助手，避免一条登录命令把 CI 的身份覆盖掉，也便于在事故时只吊销其中一个。

**速记**：按仓库分别存凭据、同仓库只能有一个当前身份，切账号靠重新登录或换配置目录。



#### CI 环境下的注入与令牌最小化

**CI 注入原则**：凭据在流水线运行时以环境变量或 Secret 形式临时注入，用 --password-stdin 交给 docker login，任务结束即失效，绝不写进镜像与日志。

- 优先使用仓库或云平台提供的临时凭据，减少长期口令的暴露面。
- 令牌只授予推送目标项目所需的最小权限，构建镜像的账号不应同时具备删除其他项目或管理用户的权限。
- 把口令放在受保护的变量里，确保它不会被回显；docker login 的输出不含口令，但自定义脚本打印环境变量会泄漏。
- 避免把凭据写进 Dockerfile、构建参数或镜像层，构建参数会被记录在镜像历史里。
- 日常构建推送到带提交摘要的临时标签，生产标签由受控的发布流水线推送，二者权限分级。

```bash
echo "$CI_REGISTRY_TOKEN" | docker login "$CI_REGISTRY" -u "$CI_REGISTRY_USER" --password-stdin
docker build -t "$CI_REGISTRY/team/myapp:$CI_COMMIT_SHA" .
docker push "$CI_REGISTRY/team/myapp:$CI_COMMIT_SHA"
docker logout "$CI_REGISTRY"
```

> [!IMPORTANT]
> **重要内容**：构建参数与镜像层都会长期保留在仓库里，任何写进 ARG、ENV 或文件的口令都等同于永久泄漏，即使之后删掉标签，中间层仍可能被人拉到。凭据只应存在于流水线的运行时环境中。

**速记**：临时注入、标准输入、最小权限、用完登出；凭据不进镜像与日志。



### 官方 registry 镜像自建

#### 起一个官方 registry 容器

**官方 registry 镜像**：CNCF Distribution 项目发布的无状态镜像仓库服务，是自建私有仓库最轻的形态。当前官方文档推荐的标签为 registry:3，实现 OCI Distribution 规范；registry:2 是长期沿用的上一代标签，配置方式基本一致。

- 默认通过 5000 端口提供服务，数据默认落在容器内 /var/lib/registry。
- 必须把数据目录挂到卷或宿主目录，否则容器重建即丢镜像。
- 配置文件在 registry:3 镜像中的默认路径为 /etc/distribution/config.yml，早期 registry:2 镜像为 /etc/docker/registry/config.yml。
- 单一配置项可用环境变量覆盖，命名规则是 REGISTRY 加下划线分层的路径，如 REGISTRY_STORAGE_FILESYSTEM_ROOTDIRECTORY。
- 镜像本身无认证、无界面，启动即对网络开放，公网可达前必须先加 TLS 与认证。

```bash
docker run -d --name registry --restart=always \
  -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  registry:3
curl http://localhost:5000/v2/          # 未加固时返回 200 与空对象
```

```text
{}
```

> [!CAUTION]
> **注意内容**：默认配置下任何人只要能访问 5000 端口就能推送与拉取任意镜像，相当于给内网开了一个可写入任意内容的文件服务。仅在本机实验时可临时如此，一旦要让其他机器使用，必须先配置 TLS 与认证。

**速记**：registry:3 一条 run 起服务，端口 5000、数据 /var/lib/registry，配置挂卷，裸跑只限本机实验。



#### 存储后端：filesystem 与对象存储

**存储后端**：registry 把镜像层与清单落在哪里的选择，配置中 storage 段必须且只能指定一个后端，默认使用本地文件系统。

- **filesystem**：把内容写到本地目录，rootdirectory 指定根目录，默认 /var/lib/registry，适合单机与中小规模。
- **对象存储（如 S3 兼容）**：把内容写到对象存储桶，多实例可共享同一后端，适合需要高可用或多节点读取的场景。
- 切换后端只改配置，不改客户端，客户端仍按同一仓库地址访问。
- filesystem 后端的数据目录必须持久化并纳入备份，镜像层一旦损坏通常无法从其他副本恢复。
- 对象存储后端需提供访问密钥与桶名等参数，凭据本身也是需要保护的敏感信息。

```yaml
storage:
  filesystem:
    rootdirectory: /var/lib/registry
```

```yaml
storage:
  s3:
    bucket: my-registry-bucket
    region: us-east-1
    accesskey: REPLACE_ME
    secretkey: REPLACE_ME
    rootdirectory: /registry
```

> 单机自建从 filesystem 起步即可；只有当同一后端要同时服务多个 registry 实例，或本地磁盘的扩容与快照不便时，才有必要换成对象存储。

**速记**：storage 段只能选一个后端，filesystem 落本地、s3 落对象存储；数据目录必须持久化与备份。



#### config.yml 的常用项

**config.yml**：registry 的唯一配置文件，用 YAML 描述存储、监听、认证与日志。常用项集中在 storage、http、log 三段与删除开关。

- storage.delete.enabled：是否允许通过 API 删除清单与层，默认 false，不开就无法真正删除。
- http.addr：监听地址与端口，形如 0.0.0.0:5000；http.secret：用于签名状态数据，生产须用随机值且集群内一致。
- http.tls.certificate 与 http.tls.key：TLS 证书与私钥的绝对路径，启用 HTTPS 时必填。
- log.level 控制日志级别（error、warn、info、debug），log.formatter 可选 text、json、logstash。
- maintenance.readonly.enabled 置为 true 时拒绝写入，用于垃圾回收前暂停写入。

```yaml
version: 0.1
storage:
  filesystem:
    rootdirectory: /var/lib/registry
  delete:
    enabled: true
http:
  addr: 0.0.0.0:5000
  secret: REPLACE_WITH_RANDOM_VALUE
  tls:
    certificate: /certs/registry.crt
    key: /certs/registry.key
log:
  level: info
  formatter: json
```

> 配置项按层级用下划线拼成环境变量即可覆盖，适合在 Compose 或 CI 里注入少量差异；但整段配置仍应落在文件里，环境变量只做微调。

**速记**：delete.enabled 开删除，http 段定监听地址与 secret，tls 段定证书，log 定级别与格式，readonly 供回收前使用。



#### 把数据目录挂到卷上

**数据持久化**：registry 是无状态服务，镜像全部存在 storage 后端，容器只是进程，因此数据目录必须落在容器之外。

- 用命名卷挂载：registry-data:/var/lib/registry，卷由 Docker 管理，容器重建后数据仍在。
- 用宿主目录挂载：/srv/registry:/var/lib/registry，便于直接备份与查看，但要注意目录属主与权限。
- 换存储后端时数据不会自动迁移，需借助 registry 自身的分发能力逐仓库推送，或按后端提供的工具搬迁。
- 备份对象是数据目录整体，只备份部分子目录会得到不可用的一致性残缺。
- 卷的删除命令会连带删除镜像数据，属不可逆操作，执行前要确认卷的用途。

```bash
docker run -d --name registry --restart=always \
  -p 5000:5000 \
  -v /srv/registry:/var/lib/registry \
  -v /srv/registry-config/config.yml:/etc/distribution/config.yml \
  registry:3
docker volume ls --filter name=registry
```

> [!WARNING]
> **警告内容**：docker volume rm 或 docker volume prune 会删除卷及其中的全部镜像层，且没有回收站，删掉后所有依赖该仓库的机器都需要重新推送或拉取。备份与清理策略要一并规划，不要等磁盘告警时才临时处理。

**速记**：数据必须在容器外，卷或宿主目录均可；备份整体目录，删卷即删镜像。



### 让自建 registry 可用于生产

#### 启用 TLS：证书从哪来与如何配置

**TLS 前提**：registry 默认以 HTTP 提供明文服务，生产必须启用 TLS，否则认证凭据会明文暴露在网络上，现代客户端也会拒绝推送。

- 证书来源有三：公有 CA 签发的证书、单位内部 CA 签发的证书、自签证书，三者对客户端的信任要求不同。
- 证书必须包含客户端访问时使用的域名，客户端用哪个名字连，证书里就要有哪个名字，否则报名称不匹配。
- 配置方式是把 certificate 与 key 的绝对路径写进 config.yml 的 http.tls 段，并把这两个文件挂进容器。
- 内网场景用单位 CA 签发最省事，客户端只需安装该 CA 的根证书即可信任所有同类服务。
- 自签证书可行，但每台客户端都要单独安装该证书为受信任根，机器一多维护成本陡增。

```bash
docker run -d --name registry --restart=always \
  -p 443:5000 \
  -v registry-data:/var/lib/registry \
  -v /etc/registry/certs:/certs:ro \
  -v /etc/registry/config.yml:/etc/distribution/config.yml \
  registry:3
```

> 把为仓库准备一个带域名的受信任证书当成自建路线的第一件事，而不是最后一步。证书不被信任会直接表现为所有 push 失败，且报错信息容易被误读为认证问题。

**速记**：生产必须 TLS，证书里的名字要与访问域名一致，优先用单位内部 CA 签发。



#### 配置 Basic 认证：htpasswd 的生成与挂载

**Basic 认证**：registry 内置的账号口令认证方式，凭据文件用 htpasswd 工具生成，服务启动时读取。启用后未经登录的请求在 /v2/ 端点即被拒绝。

- registry 只接受 bcrypt 格式的 htpasswd 内容，生成时务必带 -B，否则所有登录都会失败。
- 生成命令用 httpd 官方镜像里的 htpasswd 工具，-B 用 bcrypt、-b 从参数读口令、-n 输出到标准输出。
- 认证相关配置可用 config.yml 的 auth 段，也可用 REGISTRY_AUTH、REGISTRY_AUTH_HTPASSWD_REALM、REGISTRY_AUTH_HTPASSWD_PATH 三个环境变量。
- htpasswd 文件与 TLS 是配套的：Basic 认证的凭据在网络上是可还原的，必须先有 TLS 才能安全传输。
- 账号应一人一个或一用途一个，便于单独吊销；不要所有人共用同一个账号。

```bash
mkdir -p /etc/registry/auth
docker run --rm --entrypoint htpasswd httpd:2 \
  -Bbn ci-bot 'REPLACE_WITH_STRONG_PASSWORD' > /etc/registry/auth/htpasswd
```

```yaml
auth:
  htpasswd:
    realm: Registry Realm
    path: /auth/htpasswd
```

> 启用认证后，未经登录访问 /v2/ 会得到 401，这是一条可用于监控与健康检查的信号：401 说明服务在跑且认证生效，意外返回 200 反而说明认证没配上。

**速记**：htpasswd 必须 bcrypt（-B），配 TLS 后再启用 Basic，一人一账号便于吊销。



#### daemon.json 的 insecure-registries 写法与风险

**insecure-registries**：守护进程配置项，列出允许以明文 HTTP 或不校验证书方式访问的仓库地址，是客户端侧的降级开关，写在 /etc/docker/daemon.json 中，改后需重启或重载守护进程。

- 启用 HTTPS 且证书受信任的仓库不需要这一项，只有走 HTTP 或使用客户端不信任的证书时才需要。
- 写法是主机加端口，如 registry.example.com:5000；写了不代表服务端一定允许，服务端仍按自身配置处理。
- 该配置作用于客户端与守护进程之间的镜像分发通道，即 pull 与 push 的流量。
- 生效范围随守护进程，凡连到这台守护进程的客户端都受影响。
- 更好的替代方案是把仓库证书加入客户端信任，从而完全不使用这一降级项。

```json
{
  "insecure-registries": ["registry.example.com:5000"]
}
```

```bash
docker info | grep -A2 'Insecure Registries'
```

```text
 Insecure Registries:
  registry.example.com:5000
  127.0.0.0/8
```

> [!WARNING]
> **警告内容**：insecure-registries 意味着这台机器与仓库之间的镜像流量可能以明文传输或不做证书校验，账号口令与镜像内容都可能被中途窃取或篡改，攻击者还能替换镜像层使拉取方运行被植入的代码。这条路只应用于完全可控的隔离内网与临时调试，任何跨网段或公网可达的仓库都必须改用受信任的 TLS。

**速记**：insecure-registries 是客户端降级开关，明文与不校验证书都有中间人风险，能上受信任证书就别用它。



### 仓库的日常运维

#### 用 v2 API 查看目录与标签

**Registry HTTP API v2**：registry 提供的标准接口，除供客户端 pull 与 push 使用外，也可用普通 HTTP 客户端查询仓库内容，基础路径是 /v2/。

- GET /v2/：探测服务是否就绪，未加固时返回 200，启用认证且未登录时返回 401。
- GET /v2/_catalog：列出仓库名，可用 n 限制返回条数、last 做分页。
- GET /v2/仓库名/tags/list：列出某仓库下的标签。
- GET /v2/仓库名/manifests/标签或摘要：取清单，响应头带 Docker-Content-Digest，即该清单的 digest。
- 启用认证后访问这些接口需先登录或带凭据，命令行可用 curl 加 -u 携带账号。

```bash
curl -s http://localhost:5000/v2/_catalog
curl -s http://localhost:5000/v2/team/myapp/tags/list
curl -sI -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  http://localhost:5000/v2/team/myapp/manifests/1.0 | grep -i docker-content-digest
```

```text
{"repositories":["team/myapp","library/nginx"]}
{"name":"team/myapp","tags":["1.0","1.1"]}
Docker-Content-Digest: sha256:9f2a...
```

> 目录接口只列出仓库名，不区分标签与摘要；要判断哪些内容占空间，需要再逐仓库取标签与清单，并结合 digest 与层大小分析。

**速记**：/v2/ 探活、_catalog 列仓库、tags/list 列标签、manifests 取 digest。



#### 删除镜像的前提与 digest 删法

**删除的两个前提**：一是配置中开启删除，二是按 digest 而非标签删除清单。缺前者接口直接拒绝，缺后者删不掉内容。

- storage.delete.enabled 默认为 false，必须显式置 true 并让服务重新加载配置，删除接口才会被接受。
- 删除请求打到清单路径并以 digest 作为标识：DELETE /v2/仓库名/manifests/sha256:...
- 只删标签不会释放任何空间，层仍被其他引用或残留清单占用。
- 删除清单只是去掉引用，磁盘上的层要等垃圾回收才真正释放。
- 删除操作不可逆，误删后已发布的镜像需要重新推送。

```bash
curl -s http://localhost:5000/v2/team/myapp/tags/list
curl -sI -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  http://localhost:5000/v2/team/myapp/manifests/1.0 | grep -i docker-content-digest
curl -s -X DELETE http://localhost:5000/v2/team/myapp/manifests/sha256:9f2a...
```

> [!IMPORTANT]
> **重要内容**：删除清单不等于释放磁盘。registry 采用内容寻址存储，层可能被多个清单共享，因此空间是否回收取决于垃圾回收时的引用扫描。以为删了标签就省了空间是最常见的误解，实际磁盘往往纹丝不动。

**速记**：先开 delete.enabled，再按 digest 删清单；只删标签不省空间，空间等 gc 回收。



#### 垃圾回收的时机与它会删什么

**垃圾回收（Garbage Collection）**：扫描仓库中所有清单，删除不再被任何清单引用的层与清单。它是一次性的离线操作，不做增量。

- 命令形式为 registry garbage-collect 配置文件路径，可选 --dry-run 只打印不删除、--delete-untagged 一并删除无标签清单、--quiet 静默。
- 它分两步：先标记所有被引用的内容，再清扫未被标记的 blob，属停止世界式操作。
- 必须在仓库只读或停止运行时执行；若回收期间有人推送，其层可能被误删，导致镜像损坏。
- 只删未引用内容，不会碰仍被清单引用的层；因此单靠删除标签通常回收不出空间。
- 先跑 --dry-run 看清将被删除的对象，确认无误再实际执行。

```bash
docker stop registry
docker run --rm \
  -v registry-data:/var/lib/registry \
  -v /etc/registry/config.yml:/etc/distribution/config.yml \
  registry:3 garbage-collect --dry-run --delete-untagged /etc/distribution/config.yml
docker start registry
```

> [!CAUTION]
> **注意内容**：在仓库处于可写状态时执行垃圾回收，可能把并发上传中的层当作未引用内容删掉，留下损坏的镜像。执行前必须停止服务或把 maintenance.readonly.enabled 置为 true，回收完成后恢复。--delete-untagged 会删掉所有无标签清单，之后无法再按 digest 拉取它们。

**速记**：gc 前先停写或只读、先 dry-run 后执行；只删未引用内容，配 --delete-untagged 会删无标签清单。



#### 磁盘增长过快的排查顺序

**排查主线**：先定位是哪一类内容在增长，再决定删除、回收还是调整保留策略，避免盲目清库。

- 第一步看总量：用 du 或卷的占用确认是仓库数据增长，还是日志、构建缓存等旁支。
- 第二步看分布：用 /v2/_catalog 与各仓库的 tags 列表，找出标签数量最多的仓库。
- 第三步找原因：是否每次构建都推新标签、latest 与版本标签是否长期堆积、是否把大体积基础镜像推了多份。
- 第四步做回收：按 digest 删除无用清单，再在停写状态下执行垃圾回收。
- 第五步改策略：为仓库或 Harbor 配置标签保留规则，自动清理超期标签，从源头控制增长。

```bash
du -sh /srv/registry
curl -s http://localhost:5000/v2/_catalog
```

> 只删标签往往看不到磁盘下降，是排查中最容易卡住的一步；确认清单已删后，还要走完垃圾回收，空间才会真正释放。

**速记**：先看是不是仓库在长，再找标签最多的仓库，删清单、做回收、定保留策略。



### 用 registry 做缓存与代理

#### pull-through cache 的用途与配置

**pull-through cache（拉取穿透缓存）**：让本地 registry 充当上游仓库的缓存代理，首次拉取时从上游取回并留存，后续相同内容直接从本地提供。

- 用途有三：减少对上游的直接请求以规避限流、加速内网拉取、在上游不可达时以缓存兜底。
- 配置方式是在 registry 的 config.yml 中加 proxy 段，remoteurl 指向上游，如 https://registry-1.docker.io。
- 可选 username 与 password 用于访问上游的私有镜像，但一旦填写，该账号可访问的私有内容会经此缓存对外提供，必须给缓存本身加认证。
- ttl 控制缓存条目的有效期，超过有效期后重新校验上游。
- 一次只能缓存一个上游仓库；要让缓存正常清理旧条目，还需在配置中开启 delete。

```yaml
version: 0.1
storage:
  filesystem:
    rootdirectory: /var/lib/registry
  delete:
    enabled: true
proxy:
  remoteurl: https://registry-1.docker.io
  ttl: 168h
```

```bash
docker run -d --name mirror --restart=always \
  -p 5001:5000 \
  -v mirror-data:/var/lib/registry \
  -v /etc/registry/mirror.yml:/etc/distribution/config.yml \
  registry:3
```

> 官方文档指出，为获得正确且稳定的行为，pull-through cache 应使用 filesystem 存储后端；同时持续拉取镜像的缓存仍要遵守上游的合理使用与速率政策，缓存不是绕过上游限制的护身符。

**速记**：proxy.remoteurl 指上游、ttl 定有效期，一次只缓存一个上游，须开 delete 并给缓存加认证。



#### registry mirror 与 pull-through cache 的差别

**两者位置不同**：registry mirror 是客户端侧的配置，写在 daemon.json 的 registry-mirrors；pull-through cache 是服务端的能力，写在 registry 的 config.yml。前者让客户端改道，后者让仓库代为缓存。

- registry-mirrors 的取值必须是域名根，不能带路径；配置后客户端优先向它请求镜像。
- 客户端侧的 mirror 目前只支持 Docker Hub 这一上游，无法用它去镜像别的自建仓库。
- mirror 本身通常就是一个开启了 pull-through cache 的 registry，二者是客户端指向与服务端缓存的配合关系。
- mirror 侧重加速分发与统一出口，pull-through cache 侧重本地留存与离线兜底，功能上有重叠但配置位置与责任方不同。
- 验证 mirror 是否生效可看 docker info 的 Registry Mirrors 段。

```json
{
  "registry-mirrors": ["https://mirror.example.internal"]
}
```

```bash
docker info | grep -A2 'Registry Mirrors'
```

> 只配了 registry-mirrors 而没在后端部署真正的缓存服务，等于把一个不可用的地址写进客户端，拉取会直接失败；两端要成对配置。

**速记**：mirror 在客户端 daemon.json、只支持 Hub 且必须是域名根；pull-through cache 在服务端 config.yml；一改道一留存。



#### 国内访问 Docker Hub 的现实与机制

**现实约束**：跨境访问 Docker Hub 常出现速度慢、连接中断与超时，这是网络链路与上游可用性的问题。应对思路是减少直连、集中出口，而不是依赖某个固定地址。

- 机制上有三条路：在 daemon.json 配置 registry-mirrors 指向内网或可信的镜像缓存、自建 pull-through cache、把基础镜像拉到自建仓库后从内网取。
- 公共镜像源的可用性与地址持续变动，本篇不列举具体站点为推荐，配置方法以官方文档与本单位实际运维为准。
- 配置后可用 docker info 的 Registry Mirrors 段确认是否生效。
- 企业场景应考虑自建 Harbor 或使用云厂商提供的容器镜像服务，把可用性与带宽掌握在可控范围内。
- 无论用哪种方式，都应把关键基础镜像在自建仓库中留一份，避免上游波动直接阻断构建。

```bash
# Docker Desktop 在 Settings 的 Docker Engine 里编辑同一份 daemon.json
docker info | grep -A3 'Registry Mirrors'
```

> [!IMPORTANT]
> **重要内容**：本篇只讲镜像加速与缓存的作用机制、配置位置与验证方式，不推荐也不背书任何具体的公共镜像站点。第三方镜像源的内容完整性与安全性无法由使用方保证，关键镜像应以官方来源或自建仓库为准。

**速记**：少直连、集中出口，mirror 加自建缓存加本地留底；不依赖具体公共站点。



### Harbor 简介

#### Harbor 的定位与核心能力

**Harbor**：CNCF 毕业的开源镜像仓库平台，在 distribution registry 之上补齐企业级治理能力，官方文档当前版本为 2.15。它不是另一个存储引擎，而是把仓库、认证、扫描与策略打包成一套可运维的服务。

- **基于角色的访问控制**：以项目为边界分配角色（如项目管理员、维护者、开发者、访客），权限按项目而非全局。
- **镜像复制**：在多个 Harbor 实例或与其他仓库之间按规则复制镜像，支持跨机房分发与灾备。
- **漏洞扫描**：集成扫描器对镜像做漏洞检测，可作为推送后的闸门，常见的默认扫描器为 Trivy。
- **镜像签名**：支持 Cosign 与 Notary 等内容信任机制，保证镜像来源与完整性可验证。
- **配额与保留策略**：对项目设存储配额，按规则自动保留或清理标签，控制磁盘增长。
- 此外还有标签不可变、代理缓存、审计日志与远程复制等能力。

```bash
docker login harbor.example.com
docker tag myapp:1.0 harbor.example.com/team/myapp:1.0
docker push harbor.example.com/team/myapp:1.0
```

> Harbor 内置的 Distribution 组件承担实际的镜像读写，Harbor 在其上加入控制面；因此推送与拉取的命令与裸 registry 完全一致，差别在登录后的权限与策略。

**速记**：Harbor 是带治理的仓库平台，核心是项目级 RBAC、复制、扫描、签名、配额与保留。



#### 与裸 registry 的能力差与自建时机

**能力差**：裸 registry 只解决存与取，Harbor 解决谁可以存取、内容是否可信、空间如何回收、跨机房如何同步。差距集中在控制面而非数据面。

- 裸 registry 没有界面、没有用户体系、没有扫描，认证只有 Basic 或令牌，治理几乎全靠外部脚本。
- Harbor 把这些做成配置项与界面，代价是组件多、依赖数据库与缓存、升级与备份流程更重。
- 判据是需要项目隔离、审计、扫描、复制、保留策略中的两项以上，需要就上 Harbor。
- 只在单机、少量镜像、少量人员的场景，裸 registry 加 TLS 与 Basic 认证已足够，引入 Harbor 是过度设计。
- 若已在用云厂商托管仓库，其治理能力通常覆盖上述需求，也不必再自建 Harbor。

> 两者不是新旧的替代关系：Harbor 内部仍跑着 distribution，理解裸 registry 的数据布局与运维命令，是排查 Harbor 存储与回收问题的基础。

**速记**：裸 registry 管存取、Harbor 管治理；需要项目隔离、审计、扫描、复制、保留中的多项才值得上 Harbor。



#### 部署前的资源与依赖预估

**部署前提**：Harbor 依赖一个容器运行时与编排工具，官方提供基于 Docker Compose 的安装器与基于 Helm 的高可用部署。资源需求由镜像规模与并发决定，不照搬固定配置。

- 软件依赖：Docker Engine、Docker Compose（安装器方式）或 Kubernetes 加 Helm（高可用方式）。
- 组件依赖：包含 PostgreSQL 数据库、Redis 缓存、Distribution 以及若干 Harbor 自身的服务进程，它们共同占用内存与磁盘。
- 资源维度一：CPU 与内存，要按并发拉取与扫描任务量估算，漏洞扫描会显著抬高瞬时开销。
- 资源维度二：磁盘，分数据盘与数据库盘，数据盘容量按镜像层总量乘保留周期估算，并留出垃圾回收前的冗余。
- 资源维度三：网络与证书，对外提供 HTTPS 需要证书，跨机房复制需要足够的带宽与可达性。
- 容量与高可用形态应结合实际指标推算，不要按固定清单采购。

```bash
# 安装器方式的大致流程（以官方文档为准）
tar xzvf harbor-offline-installer-*.tgz
cd harbor && ./install.sh
```

> [!NOTE]
> **提醒内容**：本篇只列出部署 Harbor 需要考虑的资源与依赖维度，不给出具体的硬件采购建议与固定配置数值。实际规模应依据镜像层总量、并发拉取数、扫描频率与保留周期测算。

**速记**：Docker Compose 或 Kubernetes 加 Helm 部署，依赖数据库与缓存；容量按镜像总量、并发与保留周期估算。



### 离线与内网分发

#### save 与 load 对 export 与 import

**两对命令的分工**：本篇从仓库侧只做一句承接——save 与 load 在镜像层面搬运，保留分层与元数据，适合离线迁移；export 与 import 在容器文件系统层面搬运，只剩一层且丢失配置。

- 离线分发镜像应使用 save 与 load：镜像名、标签、环境变量与入口都得以保留。
- export 与 import 得到的是扁平文件系统快照，导入后需重新指定运行参数，不适合做镜像分发。
- save 的产物是 tar，可压缩后传输，体积取决于镜像层总量。
- load 会按 tar 中的引用恢复标签，因此制作离线包时要确认标签写清楚。
- 命令的完整形态与更多细节见《3. 容器生命周期与常用命令》，本篇关注的是如何把它编排进离线分发链路。

```bash
docker save registry.example.com/team/myapp:1.0 -o myapp-1.0.tar
gzip myapp-1.0.tar
docker load -i myapp-1.0.tar
```

> 判断依据是要搬的是镜像还是容器的当前文件系统：要保留完整镜像语义用 save 与 load，只要一个扁平快照才用 export 与 import。

**速记**：离线分发用 save 与 load 保分层与标签，export 与 import 只剩一层且丢配置。



#### 离线包的制作与体积优化

**离线包**：把一组镜像导出为可携带的文件，用于无外网或低带宽环境的分发。制作要点是控制体积与保证可还原。

- 用 docker save 一次导出多个镜像到同一个 tar，减少文件数量与重复层。
- 先 docker pull 时把平台代对，多架构镜像应分别导出对应平台，避免目标机架构不匹配。
- 体积优化的第一手段是缩小镜像本身，删掉构建缓存与无关文件属篇 6 的内容。
- 第二手段是选择更小的基础镜像与精简运行时，减少层总量。
- 第三手段是压缩与分卷，超大包分片传输后再合并校验。
- 制作完成后在干净环境里 docker load 验证一次，确保标签与内容完整。

```bash
docker save -o bundle-1.0.tar \
  nginx:1.27-alpine \
  registry.example.com/team/myapp:1.0
sha256sum bundle-1.0.tar > bundle-1.0.tar.sha256
split -b 2G bundle-1.0.tar bundle-1.0.part-
```

> 离线包一定要附带校验值，并在目标端先校验再 load。传输中断或介质损坏的 tar 往往仍能被部分解出，造成看起来导入成功、运行却报层缺失的隐蔽问题。

**速记**：一次 save 多镜像、对齐平台、压缩分卷、附校验值、干净环境验证。



#### 内网 registry 中转的分发链路

**中转链路**：以外网机器拉取镜像、推送进内网 registry、再由内网机器从 registry 拉取，是常规的离线与半离线分发方式，比拷贝 tar 更易管理与增量更新。

- 第一步在外网可达的机器上拉取或构建镜像。
- 第二步打上内网 registry 的全名标签并推送。
- 第三步内网机器从内网 registry 拉取，标签与内容与上游一致。
- 相比 tar 包，registry 中转能复用已有层、支持按标签增量更新、可统一加认证与扫描。
- 内网 registry 需是可写且已配置认证与 TLS 的实例，避免成为无门槛的写入点。

```bash
# 外网侧
docker pull nginx:1.27-alpine
docker tag nginx:1.27-alpine registry.intranet.example/library/nginx:1.27-alpine
docker push registry.intranet.example/library/nginx:1.27-alpine
# 内网侧
docker pull registry.intranet.example/library/nginx:1.27-alpine
```

> 用 registry 中转时，标签要与上游保持一致或用统一的内部命名规范，否则上游是哪个版本很快就会说不清，给后续升级带来困难。

**速记**：外网拉取、打内网全名、推入 registry、内网拉取；可复用层、可增量、可加治理。



#### air-gapped 环境的基础镜像维护

**air-gapped 环境**：与外部网络物理或逻辑隔离、无法直接访问公网仓库的网络。其分发全靠离线包或内网中转，镜像来源必须提前规划。

- 基础镜像应预先导入内网 registry 并长期保存，业务构建一律从内网 registry 取基础镜像。
- 维护一份基础镜像清单，登记镜像名、标签、digest 与引入时间，便于追溯与批量更新。
- 更新时按清单逐项导入新版本并保留旧版本一段时间，避免一次性替换导致构建中断。
- 用 digest 而非可变的标签锁定基础镜像，保证重建结果可复现。
- 定期核对清单与实际仓库内容，清理长期无人使用的基础镜像，控制体积。

```bash
# 内网构建时固定 digest，避免标签漂移
docker build --build-arg BASE=registry.intranet.example/library/nginx@sha256:9f2a... .
```

> [!IMPORTANT]
> **重要内容**：air-gapped 环境下无法临时拉取，任何先跳过、回头再补的依赖都会在断网时成为永久缺口。基础镜像清单与离线包应在环境成型前就备齐，并明确谁负责更新与校验。

**速记**：基础镜像预先导入并建清单、按 digest 锁定、新旧并存、定期清理与核对。



### 仓库治理清单

#### 命名规范与标签规范

**命名规范**：用固定段数表达镜像归属，让路径本身携带信息。仓库名建议两段式，标签再承载版本与环境。

- 仓库名建议形如 项目/服务，如 shop/web、shop/api，第一段是项目、第二段是服务，便于按项目批量授权与清理。
- 标签承载版本与环境两类信息，版本用语义化版本或提交摘要，环境可用后缀如 -dev、-staging、-prod。
- 同一镜像不要用同一标签同时表达版本与环境，二者维度不同，混用会让回滚失去依据。
- 坚决避免 latest 进入生产流程：它可被反复覆盖，无法定位具体内容。
- 发布记录应同时保存标签与 digest，标签供人读、digest 供机器锁定。

```bash
docker tag myapp:1.0 registry.example.com:5000/shop/api:1.0.0-prod
docker push registry.example.com:5000/shop/api:1.0.0-prod
```

> 命名与标签规范只有落到仓库权限与保留策略上才有约束力。仅靠文档约定，迟早在紧急发布时被绕过，应把规则做成可校验、可拒绝写入的配置。

**速记**：仓库名两段式项目加服务，标签分离版本与环境，生产不用 latest，标签与 digest 并记。



#### 推送权限与不可变标签

**权限分级**：让生产标签只能由受控的流水线或少数角色推送，普通开发者与构建账号只能推临时标签，从源头保证发布可追溯。

- 按项目分配角色，开发账号对开发项目可写、对生产项目只读。
- 生产标签由发布流水线用专用凭据推送，人工不得直接推。
- 启用标签不可变（tag immutability）后，同名标签一旦推送即不能被覆盖，避免有人悄悄替换线上镜像。
- 结合镜像签名，只允许已签名的镜像被拉取或部署，进一步收窄可发布内容。
- 定期审计谁推送了生产标签、用了哪些凭据，异常推送应是可告警的事件。

```bash
# 仓库侧开启标签不可变后，重复推送同名标签会被拒绝
docker push registry.example.com:5000/shop/api:1.0.0-prod
```

> 不可变标签的价值在于把覆盖这一动作从可能变成不可能：镜像内容与标签的对应关系一旦固定，回滚、对账与事故追踪才有可靠依据。

**速记**：开发可写开发项目、生产标签归受控流水线，开标签不可变并配合签名。



#### 镜像保留与清理策略

**保留策略**：按标签数量或时间自动清理旧镜像，控制磁盘增长，同时保证可回滚的版本不被误删。

- 按数量保留：每个仓库保留最近 N 个版本标签，超出即清理。
- 按时间保留：只保留最近一段时间内推送的标签，适合更新频繁的服务。
- 保护规则：以标签匹配保护正式版本与正在使用的版本，避免被自动清理命中。
- 无标签清单设置独立规则，定期删除并在停写状态下垃圾回收。
- 清理策略应先在小范围试运行，确认不会误删回滚所需版本后再全面启用。

> [!CAUTION]
> **注意内容**：保留策略误删的往往是正要用于回滚的旧版本，而回滚通常发生在故障时，此时已无法从别处找回。配置规则时应对正式版本与最近一次稳定版本单独保护，且先观察再放开。

**速记**：按数量或时间保留、给正式版本设保护、无标签清单单独清、小范围试运行。



#### 公开仓库的敏感信息自查

**自查目的**：镜像层里的一切都会随分发扩散，推送到公共仓库等于公开发布。推送前必须确认镜像中不含口令、令牌、私钥与内部配置。

- 检查构建过程有没有把 .env、密钥文件、凭据或内部配置复制进镜像。
- 检查历史层：即使后续层删除了文件，早期层中仍可能残留，需从干净基底重建。
- 检查环境变量与构建参数，它们会写进镜像元数据，等同公开。
- 检查镜像标签与描述有没有暴露内部主机名、地址或账号。
- 建立推送前的自动扫描闸门，对疑似含密钥的内容直接阻断。

```bash
docker history --no-trunc myapp:1.0            # 逐层查看构建命令，排查误拷入
docker run --rm myapp:1.0 sh -c 'ls -la /app'  # 核对镜像内是否残留敏感文件
```

> [!WARNING]
> **警告内容**：把含密钥的镜像推到公共仓库，等于把凭据永久公开，即使随后删除标签与仓库，已被他人拉取的副本与中间层也无法收回。密钥一旦进入公共镜像，应立即在源头吊销并轮换，而不是仅删除镜像。切记在镜像里删除文件不能清除早先层中的内容。

**速记**：镜像层会扩散、历史层会残留，凭据不进镜像；推公共仓库前先自动扫描，泄了先吊销再轮换。



#### 推送前的漏洞扫描闸门

**扫描闸门**：在镜像推送进正式仓库前自动做漏洞扫描，按严重级别决定放行或阻断，把有已知高危漏洞的镜像挡在发布之前。

- 扫描对象是最终镜像的软件包与依赖，输出按严重级别分组，如严重、高、中、低。
- 闸门规则应先宽后严：初期只告警不阻断，摸清基线后再对高危级别启用阻断。
- 基础镜像的漏洞占比通常很高，应优先通过更新基础镜像消减，而非手工逐项处理。
- 扫描结果要留档并与发布记录关联，出现安全事件时可回溯当时镜像的漏洞状态。
- 无法立即修复的高危漏洞应有显式的豁免与期限，避免长期以已知问题为由带病发布。

```bash
# Harbor 等项目内置扫描，也可在 CI 中调用扫描器后再决定是否推送
docker push registry.example.com:5000/shop/api:1.0.0-prod
```

> 把扫描放在构建之后、推送正式标签之前这个位置最有效，因为它能在镜像进入正式仓库前阻断；放在部署前扫描虽也能拦，但脏镜像已经占用了仓库空间。

**速记**：推正式标签前扫、按级别设定阻断、优先更新基础镜像、结果留档、豁免设期限。
