## 容器网络基础与端口映射

### 容器的网络命名空间

#### 每个容器独享一套网络栈

**网络命名空间（network namespace）**：Linux 内核提供的网络隔离单元，每个命名空间拥有独立的网卡、路由表、ARP 表、防火墙规则、端口空间与套接字，容器之间以及容器与宿主机之间正是靠它彼此隔开。

- 一套网络栈包含网卡与回环、路由表、ARP 表、iptables 规则、端口空间、套接字六类资源，全部随命名空间独立。
- 容器里看到的 eth0、lo、默认路由与解析配置，都是这套命名空间的一部分。
- 命名空间只隔离视图，不限制资源；限制 CPU、内存由控制组（cgroup）负责，两者分工不同。
- 两个容器可以各自绑定宿主上的同一个端口号（如都用 80），因为端口空间相互独立，互不冲突。

> 易混点：网络命名空间与 UTS 命名空间都给容器一个"身份"，但 UTS 命名空间只管主机名（由 --hostname 设置），网络命名空间管整张网卡与协议栈，二者互不替代。改主机名不会改变容器能否被访问。

**速记**：一套网络栈六件套——网卡、路由表、ARP 表、防火墙规则、端口空间、套接字；命名空间管隔离视图，cgroup 管资源限制。



#### 观察容器网络栈：nsenter 与 ip netns

**nsenter**：进入指定进程已有命名空间的工具，用 -t 指定容器主进程在宿主机上的 PID、用 -n 指定网络命名空间，即可在宿主终端里观察容器的网络栈；**ip netns**：按 /var/run/netns 目录下的登记项操作命名空间，而 Docker 并不把容器网络命名空间登记到该目录，所以直接执行 ip netns list 看不到任何容器。

- 先取容器主进程在宿主机上的 PID，再用 nsenter 进去看地址与路由。
- 想用 ip netns，需要先把容器的命名空间文件绑定到 /var/run/netns 下的名字，再以 ip netns exec 加名字的方式操作。
- 守护进程自己维护的网络命名空间文件通常位于 /var/run/docker/netns/ 下，只读观察即可，不要手工改动。
- nsenter 只是借看容器视角，不改变容器本身；容器停止后 PID 失效，观察前提消失。

```bash
pid=$(docker inspect -f '{{.State.Pid}}' web)
sudo nsenter -t "$pid" -n ip addr show
sudo nsenter -t "$pid" -n ip route
```

```bash
# 把容器命名空间登记到 ip netns 后再操作
sudo mkdir -p /var/run/netns
sudo touch /var/run/netns/web
sudo mount --bind /proc/"$pid"/ns/net /var/run/netns/web
sudo ip netns exec web ip addr show
```

> [!CAUTION]
> **注意内容**：在容器的网络命名空间里直接改地址、加路由或改防火墙规则会立即影响该容器，且容器一重建就全部丢失。观察用 nsenter，真实改动应通过 docker network 系列命令完成。

**速记**：nsenter 按 PID 进栈观察，ip netns 要先登记命名空间；能看就够，不要在命名空间里手工改网络。



#### 容器内看到的 127.0.0.1 是容器自己

**回环地址（127.0.0.1，对应 lo 接口）**：属于容器自身的网络命名空间，容器内访问 127.0.0.1 访问的是容器自己，与宿主机或其他容器无关；跨命名空间的 localhost 永远不通。

- 应用若只监听 127.0.0.1，宿主机与其他容器都访问不到它，即使端口已经发布也无济于事。
- 发布端口时，目标地址被改写成容器网卡地址（如 172.17.0.2），而不是 127.0.0.1，因此只绑回环的服务发布后依然连不上。
- 这是"端口映射成功却访问不了"最常见的原因，先查应用监听地址再怀疑网络。
- 容器想访问宿主上的服务，不能用 localhost，要用 host.docker.internal 或默认网关地址。

```bash
docker exec web ss -lntp
```

```text
LISTEN 0 511 127.0.0.1:80 0.0.0.0:* users:(("nginx",pid=1,fd=6))
```

> [!WARNING]
> **警告内容**：只监听 127.0.0.1 是发布端口失效的头号原因，且它在容器内自测时一切正常，具有很强的迷惑性。容器里对外提供服务的进程必须监听 0.0.0.0，否则无论怎样写 -p 都访问不到。

**速记**：容器里的 127.0.0.1 就是容器自己；服务要对外必须监听 0.0.0.0，发布端口时改写的目标是容器网卡地址。



### veth pair 与网桥

#### veth pair 如何把容器接进宿主机

**veth pair（虚拟以太网卡对）**：成对出现的两块虚拟网卡，如同同一根网线的两端，一端放进容器的网络命名空间（通常名为 eth0），另一端留在宿主机的命名空间（通常名为 veth 开头的一串随机名），任何一端发出的帧都会从另一端收到。

- 容器 eth0 与宿主侧 veth 接口构成一条点对点链路，容器借此接上宿主机的网桥。
- 宿主上执行 ip link 能看到大量 veth 接口，每一个接入网络的容器对应一对。
- 一对 veth 只连接两个命名空间，本身不做转发；同一网段内的转发由网桥承担。
- veth 随容器网络命名空间一同创建与销毁，容器停止后宿主侧那一端也随之消失。

```bash
docker run -d --name web nginx
ip -br link show | grep -E 'docker0|veth'
```

> 类比记忆：veth pair 是网线的两端，容器端是 eth0，宿主端是 vethXXXX，而把许多根网线插在一起的交换机就是网桥 docker0。容器看不到宿主侧的 veth，宿主也看不到容器里的 eth0。

**速记**：veth pair 一对两卡，容器端 eth0、宿主端 veth；线的两头，桥在中间，转发靠网桥不靠网线。



#### docker0 网桥与默认网段

**docker0**：Linux 上 Docker 默认创建的虚拟网桥，相当于一台软件交换机，把宿主机上所有接入默认 bridge 网络的容器连成同一广播域；它自身的地址默认是 172.17.0.1，默认网段为 172.17.0.0/16。

- 网桥工作在二层，负责在同一网段内按 MAC 地址转发；跨网段的流量才交给宿主机路由与地址转换。
- 每个用户自定义 bridge 也会得到一块 br 开头的网桥设备，网段从 default-address-pools 地址池中分配，常见如 172.18.0.0/16。
- docker0 的地址就是容器路由表里的默认网关，容器出网时第一跳是它。
- 默认网桥的地址与网段可用 daemon.json 的 bip 与 fixed-cidr 调整，改动需重启守护进程。

```bash
ip addr show docker0
docker network inspect bridge -f '{{range .IPAM.Config}}{{.Subnet}} {{.Gateway}}{{end}}'
```

```text
172.17.0.0/16 172.17.0.1
```

> [!NOTE]
> **提醒内容**：默认 bridge 被官方标记为 legacy（遗留）网络，不推荐用于生产。但 docker0 与 172.17.0.0/16 这套默认值仍是理解所有 bridge 网络的起点，且默认 bridge 的 IPv4 配置无法像自定义网络那样用 --ipv4=false 关闭。

**速记**：docker0 是默认网桥，自身 172.17.0.1/16，网段 172.17.0.0/16，同时充当容器的默认网关。



#### 从宿主机观察容器网卡与 IP 分配

**容器 IP 分配**：由守护进程按网络的 IPAM 配置从子网中动态分配，通常从子网内第二个可用地址起（如 172.17.0.2）；容器每次启动都可能拿到不同地址，停止后即释放。

- 看容器 IP：读取容器 inspect 的 NetworkSettings.Networks 段中的 IPAddress。
- 看网络全貌：docker network inspect 的 Containers 段列出每个接入容器的名称、IPv4Address 与 MAC。
- 看宿主侧链路：ip -d link show type veth，或直接在 ip link 输出里找 veth 前缀的接口。
- 地址会变意味着不要把它写死进配置，互访应走自定义网络的容器名，或用发布端口。

```bash
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
docker network inspect app-net
```

> 静态 IP 需要在用户自定义网络上用 --ip 指定，并且该网络创建时必须先有 --subnet；默认 bridge 不支持给容器指定地址。这也是默认 bridge 适合练手、不适合编排的原因之一。

**速记**：IP 由 IPAM 动态分配、随容器生灭变化；查地址看容器 inspect，查全局看 network inspect，查链路看 ip link 的 veth。



### 四种内置网络驱动

#### bridge：默认的隔离网络

**bridge 驱动**：Docker 的默认网络驱动，为每个容器创建独立的网络命名空间，再用网桥把容器接入宿主网络，是单机场景下最通用的选择。

- 启动容器不指定 --network 时，自动接入名为 bridge 的默认网络。
- 同一 bridge 网络内的容器可自由互通，不同网络的容器默认不可达，需发布端口或让容器同时接入多个网络。
- 支持端口发布，也支持容器借宿主地址访问外部网络。
- 用户自定义 bridge 额外提供名字解析与更清晰的隔离，是官方推荐用法。

```bash
docker network ls
docker run -d --name web nginx
docker network inspect bridge -f '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
```

> bridge 是"有隔离但有代价"的一档：隔离靠独立命名空间，出网要靠一次地址转换，因此吞吐略低于 host 模式。绝大多数单机部署都落在这一档。

**速记**：bridge 是默认驱动，独立命名空间加网桥，网络内可互通、可发布端口、可出网，单机首选。



#### host：共享宿主机网络栈

**host 驱动（--network host）**：容器直接使用宿主机的网络命名空间，不分配独立 IP，容器内看到的网卡、路由表与端口空间就是宿主机的网络栈。

- 容器绑定 80 端口即等于宿主机 80 端口在监听，性能最好，省去了地址转换与用户态代理。
- -p、--publish、-P 在 host 模式下被忽略，并打印警告：Published ports are discarded when using host network mode。
- 副作用是端口直接占用宿主端口空间，容易与宿主进程冲突，且容器与宿主之间的网络隔离消失。
- 适合高吞吐场景，或需要绑定大范围、动态端口的服务。

```bash
docker run --rm -d --network host --name my_nginx nginx
sudo ss -lntp | grep :80
```

> [!IMPORTANT]
> **重要内容**：host 模式在平台上并不对等。Linux 原生支持；Docker Desktop 从 4.34 起才以选择性开启的方式支持（在设置中开启 host networking），且只作用于 TCP 与 UDP，不支持更底层协议，容器内进程也无法直接绑定宿主机 IP。Desktop 下容器共享的是那台托管 Linux 虚拟机的网络栈，Docker Desktop 通过额外转发让 TCP、UDP 双向可达，并不等于直接落在 mac 或 Windows 宿主上。

**速记**：host 共享宿主网络栈、不分配 IP、-p 失效并告警；Linux 原生，Desktop 需开启且仅支持 TCP、UDP。



#### none：只有回环

**none 驱动（--network none）**：给容器一个只有 lo 回环接口的网络命名空间，容器与外界（包括其他容器与宿主机）完全隔离。

- 容器内执行 ip addr 只能看到 lo，没有 eth0，也没有默认路由。
- 适合完全离线、只需本地计算的批处理任务，或需要自行接管网络配置的特殊场景。
- 与 host 正好相反，none 是最强隔离的一档，代价是完全无法通信。
- 该模式的容器无法访问任何外部服务，也无法被访问。

```bash
docker run --rm --network none alpine ip addr
```

> none 不等于"没有网络命名空间"。它仍然拥有一套完整的网络命名空间，只是其中除回环外没有任何对外接口，因此也没有地址与外网能力。

**速记**：none 只有 lo、没有 eth0、没有默认路由，与外界完全断开，是最强隔离档。



#### container：共享另一容器的网络栈

**container 驱动（--network container:目标容器）**：新容器直接加入目标容器的网络命名空间，两者共享 IP、端口空间与网卡，如同运行在同一台机器上。

- 典型用途是边车容器：调试容器共享业务容器的网络栈，可直接查看其端口监听；也可让处理代理流量的容器与主容器共用地址。
- 因为共享端口空间，两个容器不能绑定同一个端口。
- 该模式下 --publish、--expose、--dns、--hostname、--add-host、--mac-address 等网络相关选项不可用。
- 目标容器停止后，共享其网络栈的容器也随之失去网络能力。

```bash
docker run --rm --network container:web nicolaka/netshoot ss -lntp
```

> 共享网络栈不等于共享文件系统与进程，网络之外两者仍然隔离；--network container: 与 --volumes-from 是两回事，前者共网络，后者共卷。应用侧常把"日志边车共享网络"与"数据边车共享卷"配合使用。

**速记**：container 模式共享目标容器的网络命名空间，IP 与端口全共用，网络类选项多不可用，目标停了它也断网。



### 默认 bridge 与用户自定义 bridge 的关键差别

#### 默认 bridge 只能用 IP 互访

**默认 bridge 的互访规则**：接入默认 bridge 的容器之间可以通信，但只能依靠 IP 地址，没有按容器名自动解析的能力；该网络也不提供项目级隔离，任何未指定网络启动的容器都落在同一个广播域里。

- 容器名不会自动成为可解析的主机名，用容器名去 ping 会得到类似 bad address 的解析失败。
- 同网段容器默认全部互通且不设防，无关项目的容器也会互相可见、端口彼此可达。
- 容器停止后释放 IP，因此依赖 IP 的互访配置天然不稳定。
- 官方把默认 bridge 标为遗留用法，推荐改用用户自定义网络。

> 遗留的 --link 选项能在默认 bridge 上补充一层名字映射，但它已被废弃，不应作为新方案的依据。需要名字互访时应当使用用户自定义网络，而不是继续堆 --link。

**速记**：默认 bridge 只能凭 IP 互访、无隔离、IP 还会变，属被官方标记为遗留的用法。



#### 自定义 bridge 支持容器名解析

**用户自定义 bridge 的关键增益**：Docker 为每个自定义网络内嵌一个 DNS 服务器，容器之间可以用容器名或网络别名互相解析，从而摆脱对 IP 的依赖，这是它与默认 bridge 最重要的一条差别。

- 同一自定义网络内，容器名即主机名，可直接作为访问目标。
- 接入网络时还可为容器追加网络别名，便于用稳定名字指向同一容器。
- 名字解析只在同一自定义网络内有效，跨网络仍需 IP 或发布端口。
- 创建方式：docker network create 网络名，随后以 --network 网络名 接入容器。

```bash
docker network create app-net
docker run -d --name api --network app-net nginx
docker run --rm --network app-net alpine ping -c1 api
```

> [!NOTE]
> **提醒内容**：本篇只点出这一条差别。内嵌 DNS 的地址（127.0.0.11）、别名机制、多网络下的解析优先级与容器互联的完整做法，留给 9. 自定义网络与容器互联 展开，此处不重复。

**速记**：自定义 bridge 有内嵌 DNS，容器名即可互访；解析范围限于本网络，跨网络仍要靠 IP 或发布端口。



### 端口映射的写法

#### -p 的四种写法

**-p、--publish**：把容器端口发布到宿主机，基本语法是 宿主端口:容器端口，在其前面可加宿主地址、在后面可加协议，由此演化出四种常用写法。

- 宿主端口:容器端口：docker run -p 8080:80 nginx，把宿主 8080 映射到容器 80。
- 只给容器端口：docker run -p 80 nginx，宿主端口由守护进程随机分配，用 docker port 查询。
- 指定协议：-p 8080:80/udp 发布 UDP；TCP 与 UDP 需分别发布，可写 -p 8080:80/tcp -p 8080:80/udp。
- 绑定特定宿主地址：-p 192.168.1.100:8080:80 只在该地址监听，-p 127.0.0.1:8080:80 则只允许本机访问。
- 一个容器端口可同时绑定多个宿主地址，重复写多个 -p 即可。

```bash
docker run -d --name web -p 8080:80 nginx
docker run -d --name web2 -p 80 nginx
docker port web2
docker run -d --name dns -p 53:53/udp coredns/coredns
docker run -d --name local -p 127.0.0.1:8080:80 nginx
```

```text
80/tcp -> 0.0.0.0:32768
```

> 方向永远是左宿主、右容器，写反不会报错却导致服务不通，是新手最常见的失误。另外 -p 127.0.0.1:8080:80 里的 127.0.0.1 是宿主机地址，不是容器地址，容器内部始终监听它自己的地址。

**速记**：宿主:容器、只给容器端口则随机、斜杠后跟协议、前缀定宿主地址；左宿主右容器不能写反。



#### -P 与镜像 EXPOSE 的配合

**-P、--publish-all**：把镜像中 EXPOSE 声明过的所有端口一次性发布到宿主机随机端口，无需逐个写 -p，适合本地快速验证。

- EXPOSE 只声明"应用会监听这个端口"，既不发布也不改变运行时行为；是否对外由 -p 或 -P 决定。
- -P 把所有已 EXPOSE 的端口映射到随机宿主端口，用 docker port 查看结果。
- -P 无法指定宿主端口，因此不适合需要固定端口的场景，线上基本只用 -p。
- 发布结果可在 docker inspect 的 NetworkSettings.Ports 段看到每个端口的宿主绑定。

```bash
docker run -d --name static -P nginx
docker port static
```

```text
80/tcp -> 0.0.0.0:32770
```

> [!TIP]
> **建议内容**：EXPOSE 是文档性质的声明，不是安全边界。不写 EXPOSE，容器端口在宿主与同网络容器间仍可达；写了 EXPOSE 但不加 -p 或 -P，外部网络也访问不到。把 EXPOSE 当说明书而不是防火墙来理解。

**速记**：EXPOSE 只声明，-p 定点发布，-P 全量随机发布；端口暴露取决于发布动作，而非 EXPOSE 指令。



#### IPv6 与多地址绑定

**IPv6 发布**：把 IPv6 地址用方括号括起来写在宿主地址位置即可发布到 IPv6，形如 -p '[::1]:8080:80'；不写宿主地址时，端口默认同时发布到 0.0.0.0 与 [::]。

- -p '[::1]:8080:80' 只允许本机 IPv6 回环访问。
- -p '[::]:8080:80' 监听所有 IPv6 地址。
- 同一容器端口可同时用 IPv4 与 IPv6 地址分别发布：-p 127.0.0.1:8080:80 -p '[::1]:8080:80'。
- 宿主 IPv6 端口能否映射到容器 IPv4 地址，取决于网络是否为 IPv4-only 以及 userland-proxy 是否开启。

```bash
docker run -d --name web6 -p 127.0.0.1:8080:80 -p '[::1]:8080:80' nginx
```

> [!WARNING]
> **警告内容**：不写宿主地址时，守护进程把端口发布到所有宿主地址，即 0.0.0.0 与 [::]。这意味着不仅本机可达，局域网内任意主机乃至公网都能访问，等同于把服务摊开到网络上。凡是不需要被其他机器直接访问的端口，都应显式绑定到 127.0.0.1。

**速记**：IPv6 宿主地址要加方括号，默认同时铺到 0.0.0.0 与 [::]；多地址绑定就重复写多个 -p。



#### 端口冲突的报错与排查

**端口冲突**：当要绑定的宿主端口已被其他进程或旧容器占用时，容器创建会失败并提示端口已分配，属于典型的可恢复错误。

- 典型报错：Error response from daemon: ... Bind for 0.0.0.0:8080 failed: port is already allocated。
- 宿主进程占用时表现为：listen tcp 0.0.0.0:8080: bind: address already in use。
- 排查顺序：先用 ss -lntp 找出占用该端口的进程，再用 docker ps 看是否是旧容器在占。
- 处置：换一个宿主端口，或停掉、删除占用者；端口要等容器删除后才释放。
- 把同一容器端口发布到同一宿主端口两次，也会触发冲突。

```bash
sudo ss -lntp | grep :8080
docker ps --filter publish=8080
```

```text
LISTEN 0 4096 0.0.0.0:8080 0.0.0.0:* users:(("docker-proxy",pid=1234,fd=4))
```

> 端口在容器删除后才释放。用 --rm 的容器退出即释放，长期运行的旧容器则会一直占着端口；重建前先 docker rm 旧容器是避免冲突的常规动作。

**速记**：端口冲突先用 ss 找占用进程，再用 docker ps 找旧容器；换端口或删容器，端口随容器删除而释放。



### 端口映射的实现

#### DNAT 规则如何把流量送进容器

**DNAT（目标地址转换）**：Docker 在 nat 表的 DOCKER 链写入规则，把发往 宿主地址:宿主端口 的入站连接改写成 容器地址:容器端口，从而实现端口映射，这一改写发生在路由决策阶段。

- 内核先对到达的包做 DNAT，再把改写目标地址后的包转发给容器。
- 出网方向在同一条链上写入 MASQUERADE 规则，把源地址改写为宿主地址。
- 由于改写发生在 nat 表，流量绕过了 INPUT 与 OUTPUT 链，这是 ufw 这类基于 INPUT 链的防火墙拦不住 Docker 发布端口的原因。
- 宿主机上默认还有一个用户态代理进程 docker-proxy，可用 --userland-proxy=false 关闭，此后完全依赖防火墙规则。

```bash
sudo iptables -t nat -L DOCKER -n -v
sudo iptables -t nat -S DOCKER | grep -i dnat
```

> [!IMPORTANT]
> **重要内容**：这些规则由守护进程自动生成，容器增删或守护进程重启时都会被重写。不要手工修改 Docker 自己建立的链，否则改动随时会被覆盖；需要加限制规则时，应写进 DOCKER-USER 链（见下一条考点）。

**速记**：入站 DNAT 改目标地址把流量送进容器，出站 MASQUERADE 改源地址把流量送出宿主，两者都在 nat 表、绕过 INPUT 链。



#### DOCKER 与 DOCKER-USER 链

**DOCKER-USER 链**：位于 filter 表，是 Docker 专门留给用户的规则入口，其处理顺序先于 Docker 自己后续的链，适合写只允许某来源访问容器这类过滤规则；**DOCKER 链**：在 nat 表承载端口映射与地址伪装，在 filter 表承载是否放行转发流量。

- Docker 在 FORWARD 链上无条件跳转到 DOCKER-USER，之后才轮到它自己的链，因此在 DOCKER-USER 里插入的规则先命中。
- 直接往 FORWARD 链追加的规则会被排到 Docker 规则之后，很多包已被 Docker 处理，看不到预期效果。
- 数据包到达 DOCKER-USER 时已完成 DNAT，规则里只能匹配容器内部地址与端口；要按原始目的地址、端口匹配，需用 conntrack 扩展的 --ctorigdst 与 --ctorigdstport。
- 常用写法是用 -I 把规则插到链首，例如按来源地址放行或丢弃。

```bash
sudo iptables -I DOCKER-USER -i eth0 ! -s 192.0.2.0/24 -j DROP
sudo iptables -t filter -L DOCKER-USER -n -v
```

> conntrack 匹配会带来一定性能开销，规则应尽量精简。另外，默认情况下外部机器不能直接路由到容器自身 IP，这类包在 raw 表 PREROUTING 就被丢弃，DOCKER-USER 里的放行规则对它们无效；要放行需改用网络选项 trusted_host_interfaces 或守护进程选项 allow-direct-routing。

**速记**：用户规则写 DOCKER-USER，先于 Docker 的链执行，且看到的是 DNAT 后的地址；往 FORWARD 链追加会被排在 Docker 规则之后而失效。



#### nftables 后端的进展

**nftables 后端**：Docker Engine 29.0.0 起提供用 nftables 取代 iptables 的防火墙后端，但目前属实验特性，配置项、行为与实现都可能变化；默认仍使用 iptables。

- 启用方式：dockerd 的 --firewall-backend=nftables，或 daemon.json 里把 firewall-backend 设为 nftables。
- 与 iptables 的关键差异：nftables 下没有 DOCKER-USER 链，自定义规则要建在独立的表里，用相同 type 与 hook 的基础链并通过链优先级控制先后。
- nftables 下 Docker 不再自行开启 IP 转发，需要宿主机已开启 net.ipv4.ip_forward，否则创建需要转发的网络时会报错。
- Swarm 模式下不能启用 nftables，因为 overlay 网络的规则尚未从 iptables 迁移；从 iptables 迁移时还需处理 DOCKER-USER 里的既有规则与 FORWARD 链的 DROP 策略。

```bash
sudo dockerd --firewall-backend=nftables
sudo sysctl net.ipv4.ip_forward
```

```json
{
  "firewall-backend": "nftables"
}
```

> [!NOTE]
> **提醒内容**：现阶段生产环境仍应以 iptables 为默认，nftables 后端适合在测试环境验证。其确切的实验状态、限制与启用参数以官方页面 docs.docker.com/engine/network/firewall-nftables 当前内容为准，升级前先核对该页说明。

**速记**：nftables 自 Engine 29.0 起可选用但仍实验、默认仍是 iptables；没有 DOCKER-USER 链，不自动开转发，Swarm 模式下不可用。



### 出网与地址转换

#### 容器出网走 MASQUERADE

**MASQUERADE（地址伪装）**：容器访问外部网络时，其私网源地址在离开宿主机前被改写为宿主机对应出口接口的地址，回包再由连接跟踪还原，这就是容器无需额外配置即可上网的原因。

- 前提是宿主机开启了 IP 转发（net.ipv4.ip_forward=1），Docker 通常会代为开启。
- 外部网络看到的源地址是宿主地址，看不到容器的私网地址。
- 默认 bridge 与自定义 bridge 都默认启用伪装，可用驱动选项 enable_ip_masquerade 关闭。
- 容器之间在同一网段内的互通不经伪装，直接走二层网桥转发。

```bash
sudo iptables -t nat -L POSTROUTING -n -v
sudo sysctl net.ipv4.ip_forward
```

```text
MASQUERADE  all  --  172.17.0.0/16  0.0.0.0/0
net.ipv4.ip_forward = 1
```

> 关闭伪装后，容器就不能再借宿主地址访问外部网络了。若同时没有替代规则，容器的端口反而会对本地网络敞开，连通性与安全性必须一并权衡，不能只图多一层控制。

**速记**：出网靠 MASQUERADE 把源地址换成宿主地址，前提是 IP 转发已开启；它隐藏了容器私网地址，同网段互通则不经过它。



#### 容器的 DNS 从哪来

**容器 DNS 来源**：守护进程在创建容器时注入解析配置。接入默认 bridge 的容器得到一份宿主 /etc/resolv.conf 的副本；接入用户自定义网络的容器则把解析指向 Docker 内嵌 DNS 服务器 127.0.0.11。

- 默认 bridge：/etc/resolv.conf 是宿主配置的复制，容器直接使用宿主的上游 DNS，但没有内嵌服务发现。
- 自定义网络：/etc/resolv.conf 指向 127.0.0.11，由内嵌服务器转发外部查询，并解析同一网络内的容器名。
- --dns、--dns-search、--dns-opt 可在启动时覆盖，每个 --dns 只能写一个地址，多个需重复传递。
- 宿主机 /etc/hosts 里的自定义条目不会自动进入容器，需用 --add-host 追加。

```bash
docker exec web cat /etc/resolv.conf
docker run -d --dns 8.8.8.8 --dns 1.1.1.1 --name app nginx
```

> 内嵌 DNS 的地址 127.0.0.11 没有 IPv6 对等地址，即使在仅使用 IPv6 的容器里也用这个 IPv4 地址。若应用需要显式配置 DNS 服务器，写 127.0.0.11 即可，它由守护进程在容器命名空间内接管并转发。

**速记**：默认 bridge 抄宿主的 resolv.conf，自定义网络指向 127.0.0.11；--dns 逐个覆盖，宿主 hosts 不会自动带进容器。



#### 改宿主 DNS 后容器为何不生效

**生效时机**：容器的解析配置在启动那一刻写入，之后不再跟随宿主机改变。因此改了宿主 DNS 之后，已在运行的容器仍按旧配置解析，需要重建容器才会生效。

- 默认 bridge 容器持有的是启动时的 resolv.conf 副本，宿主后来的改动不会回灌。
- 自定义网络下解析虽走 127.0.0.11，但其上游同样取自启动时宿主的解析配置，改动宿主 DNS 也要重建容器。
- 验证方法：进容器看 /etc/resolv.conf 与解析结果，再与宿主的 /etc/resolv.conf 对比。
- 处置：删除容器后重新运行（或重建 Compose 服务）；需要稳定时用 --dns 显式固定，避免受宿主变动牵连。

```bash
docker exec web cat /etc/resolv.conf
docker exec web getent hosts example.com
cat /etc/resolv.conf
```

> 若宿主机使用 systemd-resolved，/etc/resolv.conf 常指向本机桩地址，守护进程会做相应处理，以便容器拿到可用上游。这一细节随发行版与版本而异，遇到解析异常先核对容器内实际生效的配置，而不是只改宿主文件。

**速记**：DNS 配置随容器启动固化，宿主改了不影响已启动容器；要改就重建容器，或用 --dns 固定以免受宿主变动影响。



### 容器访问宿主机

#### host.docker.internal 与 gateway.docker.internal

**host.docker.internal**：容器内指向宿主机的一个约定主机名；**gateway.docker.internal**：指向 Docker 虚拟机网关的一个特殊主机名。两者都是为容器访问宿主上的服务准备的便利入口。

- host.docker.internal 在 Docker Desktop（mac、Windows）上由内置 DNS 自动解析，无需任何配置。
- gateway.docker.internal 在 Docker Desktop 上解析为那台托管 Docker 虚拟机的网关地址。
- 二者在纯 Linux Engine 上默认不存在，需要自行用 --add-host 建立映射。
- 宿主服务必须绑定到 0.0.0.0；只绑 127.0.0.1 时，容器通过它们也访问不到。

```bash
docker exec web getent hosts host.docker.internal
docker run --rm -it alpine sh -c "wget -qO- http://host.docker.internal:8000/"
```

> [!TIP]
> **建议内容**：访问失败时把问题拆成三段逐一确认：名字是否解析（getent）、宿主服务是否监听 0.0.0.0、宿主防火墙是否放行该来源。名字解析成功并不代表端口通，多数连不上其实卡在后两段。

**速记**：host.docker.internal 指宿主、gateway.docker.internal 指 Docker 虚拟机网关；Desktop 自带解析，Linux 要自建。



#### Linux 上的默认网关地址

**默认网关地址**：在默认 bridge 上就是 docker0 的地址 172.17.0.1，也是容器路由表里 default 一行的下一跳；通过它，容器可以直达宿主机上监听 0.0.0.0 的服务。

- 容器内执行 ip route 会看到 default via 172.17.0.1 这一行。
- 自定义 bridge 的网关是各自网桥的地址（如 172.18.0.1），随网络不同而变。
- 直接写 172.17.0.1 只适用于默认 bridge，一旦网络换成自定义 bridge 即失效，可移植性差。
- 更稳妥的做法是用下面要讲的 host-gateway 让 Docker 解析出当前网关。

```bash
docker exec web ip route
```

```text
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 scope link src 172.17.0.2
```

> 网关地址会随网络配置变化，把 172.17.0.1 硬编码进应用配置是脆弱的：在自定义网络里它可能根本不存在。这正是引入 host-gateway 这个符号值、让守护进程在容器启动时动态解析网关的原因。

**速记**：默认 bridge 的网关是 172.17.0.1，自定义网络各不相同；能用 host-gateway 符号值，就不要写死具体数字。



#### --add-host 与 host-gateway

**host-gateway**：--add-host 的一个特殊取值，由守护进程在容器启动时解析成宿主机网关地址；Linux 上正是靠它让 host.docker.internal 可用。

- 用法：docker run --add-host=host.docker.internal:host-gateway 镜像，Docker 会把解析结果写进容器 /etc/hosts。
- host-gateway 默认解析为默认 bridge 的 IPv4 地址（通常 172.17.0.1），若宿主有 IPv6 地址则一并解析。
- 需要改解析目标时，用 dockerd 的 --host-gateway-ip，或 daemon.json 的 host-gateway-ips（多个地址用数组；单个地址为兼容旧版也可写在 host-gateway-ip 字符串里）。
- Compose 中的对应写法是服务下的 extra_hosts 列表项。

```bash
docker run --rm --add-host=host.docker.internal:host-gateway alpine \
  sh -c "wget -qO- http://host.docker.internal:8000/"
```

```yaml
services:
  app:
    image: myapp:latest
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

> [!IMPORTANT]
> **重要内容**：在 Linux 上不写这一行，host.docker.internal 会直接解析失败；在 Docker Desktop 上写了也无害，只是多余。要在镜像构建期访问宿主，应使用 docker buildx build 的 --add-host，而不是仅依赖 Compose 的 extra_hosts。

**速记**：Linux 用 --add-host=host.docker.internal:host-gateway，host-gateway 解析为默认 bridge 网关；Compose 对应 extra_hosts。



### MTU 与跨主机通信

#### MTU 不匹配的典型现象

**MTU（最大传输单元）**：单个数据帧能承载的最大字节数，以太网默认为 1500。当链路实际可承载的 MTU 小于容器与网桥的配置值时，大包被丢弃、小包照常通过，表现为能 ping 通却连不上服务。

- 典型现象：小包 ping 正常，TLS 握手或大响应卡死，HTTP 请求超时但 TCP 连接可以建立。
- 原因：TCP 依赖路径 MTU 发现，若中间设备丢弃大包且不回相应 ICMP，发送端会一直重传而无法完成。
- 高发场景：宿主机接入 VPN 或隧道、跨主机 overlay 网络，链路可承载的 MTU 往往小于 1500。
- 定位方法：在容器内用不分片标记的 ping 逐级试探，找出能通过的最大数据长度。

```bash
docker exec web ping -M do -s 1472 8.8.8.8   # 1472 加 28 字节头正好 1500
docker exec web ping -M do -s 1400 8.8.8.8   # 调小能通，说明链路 MTU 较小
```

> 1472 是 1500 减去 20 字节 IP 头与 8 字节 ICMP 头的结果。若 1472 不通而 1400 通，就把 MTU 往这两者之间收；若两者都不通，问题多半不在 MTU。

**速记**：大包丢、小包通是 MTU 不匹配的招牌现象；用不分片 ping 从小往大试探，找出链路真正能过的大小。



#### 调整 MTU 的两种位置

**调 MTU 的两个位置**：一是给具体网络设驱动选项，二是给守护进程设默认值。前者精确作用于某一个网络，后者统一作用于默认 bridge 网络。

- 网络级：docker network create -o com.docker.network.driver.mtu=1450 网络名。
- 守护进程级：daemon.json 的 mtu 键，或 dockerd 的 --mtu，官方描述为设置默认 bridge 网络的 MTU，默认 1500。
- 取值口径：取链路实测 MTU 减去封装开销（如隧道头）后的值，宁可略小，不要偏大。
- 改动后需重建网络或重启守护进程，已存在的容器不会自动改变，需重建才能继承新值。

```bash
docker network create -o com.docker.network.driver.mtu=1450 app-net
```

```json
{
  "mtu": 1450
}
```

> [!TIP]
> **建议内容**：overlay 等跨主机网络的 MTU 需要在创建时显式设定，且集群各节点必须保持一致。不一致时会出现抓包看不到明显异常、只在跨主机访问时复现的疑难问题，排查成本很高，不如建网时一次定好。

**速记**：网络级用驱动选项 com.docker.network.driver.mtu，守护进程级用 mtu 或 --mtu（默认 1500）；取链路实测值减封装开销，改完要重建。



### 网络观察与排查

#### docker network ls 与 inspect 的读法

**docker network ls**：列出所有网络，默认可见 bridge、host、none 三个内置网络；**docker network inspect**：输出某个网络的完整定义，是核验网段、网关、驱动选项与接入容器的权威入口。

- ls 的 DRIVER 列显示驱动类型，SCOPE 列为 local 表示仅本机有效。
- inspect 的 IPAM.Config 段给出 Subnet 与 Gateway；Containers 段列出每个接入容器的名称、IPv4Address 与 MAC。
- inspect 的 Options 段显示该网络被改动过的驱动选项，如 MTU、绑定地址等。
- 结合 -f 只取关键字段，便于脚本采集与快速核对。

```bash
docker network ls
docker network inspect bridge -f '{{json .IPAM.Config}}'
docker network inspect app-net -f '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
```

> 若在某个网络里看不到预期容器，多半是它接在别的网络上。用 docker inspect 该容器查看它的 NetworkSettings.Networks 段，才能确认它究竟在哪张网、拿的什么地址。

**速记**：ls 看有哪些网络与驱动，inspect 看网段、网关、选项与接入容器；想知道某容器在哪张网，看容器自己的 inspect。



#### 从容器内做连通性测试

**容器内测试工具的选择**：精简镜像常常没有 ping，且 ping 依赖 ICMP 与相应权限，连通性验证应优先用 curl、wget 或 nc 测端口，用 getent 测名字解析。

- 测名字解析：getent hosts 目标 或 nslookup 目标。
- 测端口连通：nc -zv 目标 端口，或 curl -sv 加目标地址。
- ping 不可用的三个原因：镜像未装 iputils、容器缺 NET_RAW 能力、中间网络禁 ICMP，任一都会让它失败，却不能说明端口不通。
- 诊断镜像：起一个自带全套网络工具的临时容器接入同一网络使用，不必污染业务容器。

```bash
docker run --rm --network app-net alpine nc -zv api 8080
docker run --rm --network app-net curlimages/curl -sv http://api:8080/health
docker exec api getent hosts mysql
```

> [!TIP]
> **建议内容**：端口测试通过，说明网络路径与发布都通，剩下的才是应用自身问题；解析成功但端口不通，则要查目标是否监听、发布是否正确、防火墙是否放行。把解析、端口、应用三层分开验证，比在应用日志里猜更快。

**速记**：先 getent 验解析，再 nc 或 curl 验端口；ping 常因缺包或权限不可用，不能作为唯一判断依据。



#### 从宿主机看规则与监听

**宿主侧观察三件套**：用 ss 看端口监听，用 iptables 看地址转换与过滤规则，用 ip link 与 network inspect 看网桥与网卡。三者交叉，即可还原一次访问的完整路径。

- ss -lntp 列出 TCP 监听及其进程，可判断发布端口上是否真有监听。
- iptables -t nat -L DOCKER -n -v 查看端口映射与伪装的地址转换规则；加 -S 可看更紧凑的规则原文。
- iptables -t filter -L DOCKER-USER -n -v 查看用户过滤规则及其命中计数。
- ip -br link show 找 docker0 与 br 开头的网桥以及 veth 接口，确认容器是否真的接上。

```bash
sudo ss -lntp | grep 8080
sudo iptables -t nat -S DOCKER | grep -E 'DNAT|MASQUERADE'
sudo iptables -t filter -L DOCKER-USER -n -v
ip -br link show
```

> 规则很多时，先看 -v 输出的命中计数，定位到底是哪一条在起作用；改动规则前先用 iptables-save 备份，避免把 Docker 自己建立的链改坏而影响整机容器网络。

**速记**：ss 看监听、iptables 看地址转换与过滤、ip link 看网桥与 veth；三处交叉，先看命中计数定位规则。



#### 典型故障的现象、原因与处置

**典型网络故障**：端口映射与容器网络的高频故障可归纳为几组稳定的现象、原因与处置对应，按这套对应逐条排查即可收束。

- 现象：容器内能出网，但外部访问不到它。原因：没有发布端口，或只发布到 127.0.0.1。处置：用 -p 发布并绑定到对外地址。
- 现象：宿主机能访问容器，局域网其他机器不能。原因：端口发布绑定在 127.0.0.1，或宿主防火墙只放行本机。处置：改绑到 0.0.0.0 对应地址，并在防火墙按需放行。
- 现象：改了端口映射却不生效。原因：容器已创建，网络配置不可热改；或只改了 Compose 文件而未重建。处置：删除容器后按新参数重建，或用 docker compose up 触发重建。
- 现象：端口已发布但仍连不上。原因：应用只监听容器内 127.0.0.1。处置：让应用监听 0.0.0.0。
- 共同顺序：先确认发布（docker port），再看监听（容器内 ss、宿主 ss），再验解析与连通（getent、curl），最后查防火墙规则。

> [!IMPORTANT]
> **重要内容**：改了没生效几乎都指向同一个事实——容器的网络配置在创建时固化，端口、网络、IP 都不能热改，只能删除重建。排障遇到这类现象，先确认改动是否真的落到了新建的容器上。

**速记**：出网通但外部不通查发布，本机通外部不通查绑定与防火墙，改了不生效一律重建容器。



### 网络与安全边界

#### 同网段容器不隔离

**默认 bridge 的隔离缺口**：接入同一 bridge 网络（尤其是默认 bridge）的容器之间默认无限制互访，端口无需发布即可彼此访问，任何落入该网络的容器都能旁路其他容器。

- 同一网络上的容器对彼此暴露全部端口，与是否写 -p 无关。
- 默认 bridge 是所有未指定网络的容器共用的，缺乏项目级边界，不同项目会互相可见。
- 可用网络驱动选项 com.docker.network.bridge.enable_icc 关闭同网络容器间的连通性，但它默认为开启。
- 正确做法是用用户自定义网络按项目隔离，而不是把所有容器都堆在默认 bridge 上。

> [!WARNING]
> **警告内容**：隔离的边界是网络而不是宿主机。同一网络内几乎不设防，不同网络默认互不可达。把本不该互通的容器放进同一张网，等于亲手拆掉了它们之间的边界，事后很难察觉。

**速记**：同一网络容器默认全互通、端口无需发布即可达；隔离靠分网络，不靠是否在同一台机器。



#### 发布端口等于对局域网开放

**发布端口的安全含义**：-p 默认把端口发布到宿主所有地址（0.0.0.0 与 [::]），只要宿主机可达，容器端口就暴露给整个局域网乃至公网；官方明确说明端口发布默认是不安全的。

- 不带宿主地址的 -p 8080:80 使局域网内任意主机都能访问该端口。
- 数据库、缓存、调试端口、管理接口若被这样发布，等于把内网服务直接摊开到网络上。
- 地址转换在 nat 表完成，基于 INPUT 链的 ufw 规则拦不住这类流量，需要改用 DOCKER-USER 链。
- 只有确需跨主机访问时才发布端口，且只发布必要的那几个端口。

```bash
docker run -d --name db -p 3306:3306 mysql:8            # 危险：数据库直接暴露
docker run -d --name db -p 127.0.0.1:3306:3306 mysql:8  # 稳妥：只在本机可达
```

> [!CAUTION]
> **注意内容**：把数据库、Redis 或管理后台的端口发布到宿主机 0.0.0.0，等于把整个局域网都当成了可信内网。这类端口被扫描、被暴力尝试是常态，生产环境绝不要这样发布。

**速记**：-p 默认铺到 0.0.0.0，宿主可达即全网可达；数据库与管理端口尤其不能这样发布。



#### 绑定 127.0.0.1 的实务惯例

**绑定回环的惯例**：本机自用或经反向代理转发的服务，发布时应显式绑定 127.0.0.1，使端口只在宿主机本地可达，再由 Nginx 等反向代理统一对外提供服务，从而缩小暴露面。

- 写法：docker run -d -p 127.0.0.1:8080:80 nginx，只在宿主回环上监听，局域网无法直连。
- 配合反向代理：Nginx 监听对外端口并转发到 http://127.0.0.1:8080，由代理统一处理 TLS、鉴权与限流，接口口径参见 6. 反向代理。
- 也可在守护进程层用 default-network-opts，把不带宿主地址的发布默认绑定改成 127.0.0.1。
- 判断标准只有一条：需要被别的机器直接访问才绑 0.0.0.0，否则一律绑回环。

> [!TIP]
> **建议内容**：经反向代理转发时，记得补齐 X-Real-IP 与 X-Forwarded-For 等请求头，让上游拿到真实客户端地址；否则日志与鉴权看到的都是代理的地址。具体写法见 6. 反向代理 的请求头一节。

**速记**：默认绑 127.0.0.1 加反向代理对外，是本机服务的稳妥惯例；确需外部直连才绑 0.0.0.0，并同步考虑防火墙与请求头。
