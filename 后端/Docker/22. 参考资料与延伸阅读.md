## 参考资料与延伸阅读

### 官方文档地图

#### 官方文档的全站分区

**docs.docker.com**：是 Docker 全部官方文档的唯一站点，也是本系列所有事实的最终仲裁者；它的分区按「概念与操作」「逐条参考」「产品形态」三类组织，查资料前先判断自己要的是哪一种。

- **概念与操作类**：engine 与 build 目录，讲「怎么做」，带步骤与示例，适合照着操作。
- **逐条参考类**：reference 目录，讲某个字段、参数或命令的准确定义，适合核对写法。
- **产品形态类**：docker-hub、desktop、scout 等目录，讲某个产品的功能边界与前置条件。
- **判断口诀**：要步骤去 engine 与 build，要准确定义去 reference，要产品前提去产品目录。

> 同一概念在两处解释不一致时以 reference 为准。概念页为了可读会省略边界条件，参考页是逐字段的权威定义。

**速记**：**操作查 engine 与 build，定义查 reference，产品前提查产品目录**。



#### 引擎文档：该在什么时候查

**引擎文档**（docs.docker.com/engine/）：是服务器上安装与运维 Docker Engine 的权威入口，覆盖安装、存储、网络、日志与安全五个高频子区。

- **安装**（docs.docker.com/engine/install/）：按发行版给出安装步骤，装不上、版本冲突先查这里。
- **存储**（docs.docker.com/engine/storage/）：总览容器数据持久化；镜像层与可写层的后端另见 docs.docker.com/engine/storage/drivers 与 docs.docker.com/engine/storage/containerd。
- **网络与日志**（docs.docker.com/engine/network/、docs.docker.com/engine/logging/）：前者给各网络驱动的行为定义，后者给日志驱动列表与配置字段。
- **安全**（docs.docker.com/engine/security/）：rootless、userns-remap、seccomp 等机制的前提与限制。

> [!TIP]
> **建议内容**：这几页的共同特点是先讲前提再讲步骤。某个能力在本机不生效时，先回对应页确认前提是否满足（内核版本、cgroup 版本、Desktop 还是纯 Engine），再怀疑配置写错。

**速记**：**Engine 五查——安装、存储、网络、日志、安全**。



#### 命令行、Dockerfile 与 Compose 参考

**命令行参考**（docs.docker.com/reference/cli/docker/）：是每一条 docker 子命令与每一个标志的权威出处。**Dockerfile 参考**（docs.docker.com/reference/dockerfile/）：是每一条指令语法与语义的权威出处。**Compose 文件参考**（docs.docker.com/reference/compose-file/）：是 Compose 字段的权威定义，命令行对应 docs.docker.com/reference/cli/docker/compose/。

- 命令行参考按子命令逐页组织，页内按用途归组标志，并标注适用版本。
- Dockerfile 参考逐条指令给出语法、可用变量、示例与注意事项。
- 构建层面另见 docs.docker.com/build/，其下 buildkit、building/multi-platform、cache、metadata/attestations 分别讲构建器、多平台、缓存与构建证明。
- Compose 字段语义一律以 compose-file 参考为准，顶层 version 字段已废弃，不要照旧教程填。

> [!IMPORTANT]
> **重要内容**：网上大量教程停留在旧引擎或 Compose V1 时代，参数名与默认值可能已变。凡是抄来的命令，动手前用这些页面核一遍标志名与默认值，是成本最低的避错动作。

**速记**：**命令核 CLI 参考，指令核 Dockerfile 参考，字段核 compose-file 参考**。



#### 按问题类型定位页面

**定位方法**：查资料的第一步不是打开搜索引擎，而是判断问题属于哪一类，再直接落到对应官方页面；这一步能过滤掉绝大多数版本错位的二手答案。

- **装不上、起不来、命令报错**：engine 的 install 与 reference/cli。
- **数据不见了、磁盘被占满**：engine/storage 及其 drivers、containerd 子页。
- **容器之间或对外连不通**：engine/network，再回本系列第 8、9 篇。
- **日志收不到、格式不对**：engine/logging。
- **权限被拒、担心逃逸**：engine/security，再回本系列第 16 篇。
- **字段不认、校验失败**：reference/compose-file。
- **构建慢、缓存不命中、跨架构失败**：build 目录。
- **想确认某功能是否已废弃**：engine/deprecated。

> [!NOTE]
> **提醒内容**：官方页面顶部有版本选择器与适用产品形态的标记。同一页针对 Desktop 与纯 Engine 的说明不同，读之前先确认当前环境，尤其是 Desktop 专有能力。

**速记**：**先分类再查页，别让搜索替你做分类**。



### 版本与变更

#### 发布说明与废弃页的分工

**发布说明**（docs.docker.com/engine/release-notes/）：记录每个版本的新增、修复与已知问题，回答「我想用的能力从哪个版本开始有」。**废弃页**（docs.docker.com/engine/deprecated/）：记录已废弃与已移除的特性及预定移除版本，回答「我正在用的能力还能撑多久」。

- 发布说明按版本倒序排列，用于确认能力的起始版本与修复范围。
- 废弃页同时标注废弃版本与预定移除版本，并区分**已废弃（Deprecated）**与**已移除（Removed）**两种状态。
- 已废弃指不应再使用，可能在后续版本被移除、禁用或改变行为；已移除指当前已不可用。
- 已核实案例：默认 bridge 上的链接标记为 Engine 30.0 移除；cgroup v1 支持自 Engine 29.0 起废弃。

> [!WARNING]
> **警告内容**：升级前先查废弃页是成本最低的一道防线。示例是本系列第 9 篇提到的 --link：默认 bridge 上的链接计划于 Engine 30.0 移除，legacy link 环境变量自 29.0 起默认禁用。若等到升级后才发现依赖它，回退成本远高于升级前改配置。

**速记**：**发布说明看新增，废弃页看退场，升级前两页都过一遍**。



#### 三条版本线与升级前的检查

**三条独立版本线**：Engine、Compose、BuildKit 各自发版，只看 Engine 的发布说明不足以保证行为一致；升级前先确认用到能力是否被废弃，是比升级后排查更省事的一道防线。

- **Compose 与 BuildKit**：Compose 以 docker compose 子命令提供、发布号已进入 5.x，版本变化看官方发布说明页与 docker/compose 仓库的 Releases 页；BuildKit 独立发版，Engine 的发布说明会标注同期捆绑的版本。
- **核对版本**：下列命令分别查看三条线的实际版本，再回各自发布页核对行为。

```bash
docker version
docker buildx version
docker compose version
```

- **升级前检查**：逐版本看发布说明，记录当前版本，备份关键配置与命名卷清单；例如 Compose 5.5.0 重构了镜像 digest 协调机制，官方提示升级后首次 compose up 可能触发既有容器重建。

> [!CAUTION]
> **注意内容**：把「能跑」当成「没被废弃」是常见误判。移除是破坏性的，配置里仍写着已移除的字段，轻则告警被忽略，重则容器直接起不来；软废弃的特性为兼容仍可用，但官方不保证后续可用。

**速记**：**三条版本线各查各的发布页；先查废弃、再备份、后升级**。



### 规范与标准

#### OCI 三份规范的分工

**OCI（Open Container Initiative，开放容器计划）**：由 Linux 基金会托管的标准化组织，其下三份规范分别管镜像格式、运行时行为与仓库分发，共同构成容器跨实现互通的基础。

- **image-spec**：定义镜像的**格式**，即层、配置、清单与多架构索引的结构，管镜像长什么样。
- **runtime-spec**：定义**运行时**如何从镜像创建容器，即文件系统布局与进程配置的约定，管容器怎么被创建出来。
- **distribution-spec**：定义**仓库分发 API**，即推送、拉取与发现清单的接口，管镜像怎么在仓库间流转。
- 三者的共同锚点是**内容寻址**：镜像以摘要标识内容，遵循规范的实现就能互相读懂。

> 三份规范常被混为一谈。镜像能跨工具跑靠 image-spec，容器行为一致靠 runtime-spec，私有仓库能互换靠 distribution-spec；缺哪一份，对应的互通就会断。

**速记**：**image-spec 管格式，runtime-spec 管运行，distribution-spec 管分发**。



#### OCI 与 Docker 的关系

**Docker 与 OCI 的关系**：Docker 是 OCI 的发起者与主要实现者之一，但标准已跨生态，镜像格式与运行时不再由 Docker 独占解释。

- **贡献侧**：Docker 把自身的镜像格式与运行时实现贡献为规范起点。
- **实现侧与边界**：Docker、containerd、Podman、CRI-O 等都实现 OCI 规范，镜像可在其间迁移；但符合 OCI 不等于行为完全一致，各家在规范未覆盖处仍有差异。
- **观察点**：docker save 导出的镜像结构与 OCI 镜像格式高度一致，是互通的直接证据。

> 关系可概括为 **OCI 定标准，Docker 做实现**。看到「Docker 镜像格式」这一说法时，理解为一种符合 OCI image-spec 的镜像更准确。

**速记**：**OCI 定标准，Docker 是主要实现者而非独占者**。



#### Compose Specification 的独立地位

**Compose Specification**：是描述多容器应用的**开放规范**，已从 Docker 私有格式中独立出来，字段语义由规范文档定义，而非某个产品单方面决定。

- **独立意义**：其他编排工具与实现也可按规范解析同一份文件，Compose 文件不再是某个产品的私有配置。
- **与实现的关系**：docker compose CLI 是规范的主要实现之一，实现可以早于或落后于规范。
- **对照依据**：字段是否合法一律以官方 Compose 文件参考为准，而不是以某个工具的报错为准。
- **已核实变更**：顶层 version 字段已废弃，写了会告警但解析照常；文件查找顺序为 compose.yaml、compose.yml、docker-compose.yaml、docker-compose.yml。

> [!NOTE]
> **提醒内容**：理解 Compose 文件是规范文件，就能解释两件事——为什么它可以被其他工具解析，以及为什么升级 CLI 可能让原本合法的字段开始告警。

**速记**：**Compose 是开放规范，CLI 只是它的一个实现**。



### 上游源码仓库

#### 引擎、命令行与运行时仓库

**四个核心仓库**：moby/moby（引擎）、docker/cli（命令行）、containerd/containerd（容器运行时）、opencontainers/runc（低层运行时），对应本系列第 1 篇讲过的组件栈。

- **moby/moby**：引擎主体，含守护进程、网络、卷与 API 的实现，是「为什么要这样设计」的第一手材料。
- **docker/cli**：命令行实现，含各子命令与标志的定义，可用于确认某个标志的准确行为。
- **containerd/containerd**：镜像存储、快照与容器任务的生命周期；Engine 29.0 起的镜像存储即由它承担。
- **opencontainers/runc**：按 OCI 配置创建容器进程的低层实现，隔离相关行为最终落在这里。

> 读源码不必通读。带着本系列某一篇的具体疑问去定位对应目录，比从头读到尾有效；仓库默认分支是开发中的代码，读稳定实现要切到对应版本标签。

**速记**：**引擎 moby/moby，命令 docker/cli，运行时 containerd 与 runc**。



#### 构建与编排仓库

**构建与编排的两个仓库**：moby/buildkit（构建引擎）与 docker/compose（Compose 实现），分别对应本系列第 5、6 篇与第 10、11 篇。

- **moby/buildkit**：BuildKit 的实现，含构建图调度、缓存与多平台构建，构建行为反直觉时查它。
- **docker/compose**：docker compose 子命令的实现，含文件解析与容器协调逻辑；Compose 5.5.0 的 digest 协调变更即出自这里。
- **Releases 页**：两个仓库的 Releases 页是发布说明最及时、最完整的来源；Issue 区则适合搜报错，但要先核对版本。

> [!TIP]
> **建议内容**：构建或编排行为与文档描述不一致时，先查这两个仓库的 Releases 与 Issue，再回官方文档。文档更新通常滞后于实现。

**速记**：**构建查 buildkit，编排查 compose**。



#### 读仓库的方法

**读仓库的正确顺序**：先看 Releases 了解变更，再搜 Issue 匹配报错，最后才读源码；跳过前两步直接读源码，多数时候是浪费时间。

- **Releases**：确认某行为在哪个版本引入或修改，判断自己的版本是否受影响。
- **Issue 搜索**：优先看**已关闭**且**版本匹配**的条目，已关闭通常意味着已有结论或修复。
- **源码**：只在前两步无法解释时进入，从入口文件顺着调用链读，不逐行通读。

> [!WARNING]
> **警告内容**：搜 Issue 时最容易踩的坑，是把一个未标明版本、且已关闭的旧条目当作当前问题的答案。同一条报错在不同大版本间成因可能完全不同，先核对报错文本、组件版本与运行形态（Desktop 还是纯 Engine），再决定是否采信。

**速记**：**先 Releases，再 Issue，后源码；Issue 要看已关闭且版本匹配**。



### 底层基础

#### 命名空间与 cgroup 的查阅入口

**命名空间与 cgroup**：容器隔离与限制所依赖的两项内核机制；前者隔离进程看到的视图，后者限制进程可用的资源，二者的权威说明在内核手册页，而非 Docker 文档。

- **命名空间手册**：man7.org 的 namespaces 手册页，给出各命名空间的语义与系统调用入口。
- **cgroup 手册**：man7.org 的 cgroups 手册页，以及 kernel.org 文档站的 cgroup v2 章节。
- **与 Docker 的接线**：docker run 的隔离相关标志最终都翻译为这两项机制，本系列第 13 篇的资源限制即作用于 cgroup。
- **已核实变更**：cgroup v1 支持自 Engine 29.0 起废弃，选型与排障时先确认宿主机的 cgroup 版本。

> 读内核手册页的价值在于分清哪些是 Docker 的约定、哪些是内核的能力。Docker 只是调用方，行为边界由内核决定。

**速记**：**隔离看 namespaces 手册，限制看 cgroups 手册**。



#### 联合文件系统、capabilities 与安全模块

**三类底层机制**：OverlayFS 决定镜像分层如何在磁盘上合并，capabilities 决定容器内进程持有哪些特权，seccomp 与 AppArmor、SELinux 决定系统调用与访问能否通过。

- **OverlayFS**：kernel.org 文档站的文件系统章节有其说明；它把多个只读层与一个可写层合并为统一视图，对应本系列第 4 篇的镜像分层。
- **capabilities**：man7.org 的 capabilities 手册页逐项列出能力名称与语义；容器默认只保留有限能力，本系列第 16 篇的安全收缩即围绕它展开。
- **seccomp**：Linux 手册页有系统调用说明，Docker 侧见引擎安全文档的 seccomp 章节，默认配置会拦截部分系统调用。
- **AppArmor 与 SELinux**：前者项目托管于 GitLab 的 apparmor 仓库，后者有 SELinux 项目站文档；两者启用情况随发行版不同，同一镜像在两种发行版上可能一个能跑一个被拒。

> [!NOTE]
> **提醒内容**：Engine 29.0 起全新安装默认使用 containerd 镜像存储，镜像层与容器合并文件系统的存放位置与旧版 overlay2 不同。排查磁盘占用时先确认存储后端，再查对应路径，不要照旧教程去找。

> [!IMPORTANT]
> **重要内容**：遇到权限被拒且与文件或挂载有关时，先确认宿主机启用了哪一类安全模块，再看是不是策略拦截。把安全模块整体关闭只是排障手段，不应作为长期配置。

**速记**：**分层看 OverlayFS，特权看 capabilities，系统调用看 seccomp，访问策略看 AppArmor 与 SELinux**。



#### 与操作系统、计算机网络系列的衔接点

**衔接点判定**：本系列的底层行为都能在库内两个基础系列里找到对应的原理章节，回头读原理是理解「为什么」的捷径。

- **隔离与调度**：对应 架构/操作系统 的 2. 进程的描述与控制 与 4. 处理机调度，前者讲进程的宿主概念，后者讲资源分配与优先级，正是 cgroup 限制的上位原理。
- **文件系统与存储**：对应 架构/操作系统 的 13. 文件目录与文件存储管理，讲目录与文件的存储组织，是理解 OverlayFS 合并视图的前置。
- **二层网络**：对应 架构/计算机网络 的 8. 局域网与以太网 与 9. 以太网交换与 VLAN，Docker bridge 网络正是虚拟交换与二层转发在单机上的实现。
- **三层与地址**：对应 架构/计算机网络 的 11. IP 协议与 IP 地址、12. 子网划分与 CIDR、13. ARP、DHCP、ICMP 与 NAT，容器网段划分与端口映射都建立在这些概念上。

> 判断该不该回头读的原则是：当某个 Docker 行为让你觉得没道理时，它通常有内核或网络协议层面的原因。原理系列给出原因，本系列给出用法。

**速记**：**隔离调度回操作系统第 2、4 篇，文件系统回第 13 篇，二层网络回网络第 8、9 篇，地址网段回第 11 至 13 篇**。

### 工具清单

#### 构建、镜像分析与调试工具

**构建与镜像分析工具**：用于把构建做对、把镜像看透、把漏洞查出来。**运行与调试工具**：用于进入容器内部或绕过镜像自带工具缺失，按是否依赖 Desktop 分为两类。

- **构建与分析**：buildx 是 docker CLI 的构建插件，暴露 BuildKit 能力并支持多平台与多构建器实例，随 Engine 安装；dive（github.com/wagoodman/dive）逐层展示内容与体积，用于定位镜像变大来自哪一层，需额外安装。
- **镜像扫描**：Docker Scout（docs.docker.com/scout/）可从 CLI 或 Docker Hub 触发，输出 SBOM 与漏洞匹配结果；也可用 Trivy 一类开源扫描器，均需接入漏洞库。
- **调试与运行时**：docker debug 属 **Docker Desktop 专有**能力（现行最新 GA 为 4.83.0），可在不修改镜像的前提下进入容器并获得调试工具；ctr 随 containerd 安装、nerdctl 需额外安装，两者直连 containerd；在镜像里预置 curl、dig 是最通用的替代方案，代价是增大体积。

> [!IMPORTANT]
> **重要内容**：docker debug 属 Desktop 能力，服务器上不可用。以其为唯一调试手段会出现本地能查、线上不能查的落差，生产镜像应预先规划排查手段。

**速记**：**构建用 buildx，看层用 dive，查漏洞用 Scout 或 Trivy；调试用 docker debug（Desktop 专属）或 ctr 与 nerdctl**。



#### 编排、本地集群与可观测性工具

**编排与本地集群工具**：用于把单机多容器组织起来，并按需在本地起一个 Kubernetes 环境验证编排。**监控与日志工具**：用于把资源指标与日志汇出到统一平台，两者是两条独立链路。

- **编排与集群**：Compose 是单机多容器编排主力，以 docker compose 子命令提供，属 V2 架构；kind 用容器作为节点运行 Kubernetes，k3d 在容器中运行轻量发行版 k3s，minikube 是官方本地单节点工具且驱动选项最完整，三者均需额外安装。
- **指标链路**：cAdvisor（github.com/google/cadvisor）采集容器级 CPU、内存、文件系统与网络指标，Prometheus 按拉取模型采集存储并支持告警，Grafana 做可视化看板，均需额外部署。
- **日志链路**：Fluent Bit 是轻量日志采集与转发器，适合以边车或节点代理方式收集；Loki 是日志聚合系统，与 Grafana 同生态，按标签索引日志。

> [!TIP]
> **建议内容**：先确定要回答的问题再选工具——问资源有没有打满走 cAdvisor 与 Prometheus，问某次请求发生了什么走 Fluent Bit 与 Loki。本系列第 14 篇给出的是容器侧的日志与监控基础。

**速记**：**单机编排用 Compose，本地集群在 kind、k3d、minikube 中按需选一；指标走 cAdvisor 到 Prometheus 到 Grafana，日志 Fluent Bit 汇入 Loki**。



### 学习路径建议

#### 前两级：能跑起来与能装起来

**前两级的目标**：能跑起来指会用镜像与容器完成日常操作，能装起来指能产出可复现、可共享的镜像；两级的分界是用别人的制品还是产出自己的制品。

- **能跑起来（第 1 至 3 篇）**：自测标准是能独立完成镜像拉取、容器起停、进入容器排查、查看日志与端口映射，并能解释容器与虚拟机的差别。
- **能装起来（第 4 至 6 篇）**：自测标准是能从零写出一份多阶段构建的 Dockerfile，说明每一层的作用，并用 .dockerignore 控制构建上下文。
- **顺序与自测**：不理解对象模型就直接写 Dockerfile，会把镜像写成能跑就行的一团，后续体积与安全问题都要返工；自测方法是给别人讲一遍从 Dockerfile 到容器启动的全过程，讲不清的环节就是该回读的篇章。

> 这一阶段最常见的失衡是跳过第 4 篇直接进第 5、6 篇。分层是后面所有优化的基础，跳过它会让缓存与体积问题变成玄学。

**速记**：**先会跑（第 1 至 3 篇），再会装（第 4 至 6 篇）**。



#### 第三、四级：能查起来与能管起来

**能查起来**：指容器出问题时能按层定位，而不是盲目重启或重装，对应本系列第 7 至 9 与第 14 篇。**能管起来**：指能对资源、配置、密钥与安全边界做出有依据的设置，对应第 12、13、15、16 篇。

- **数据、网络与定位（第 7 至 9、14 篇）**：自测标准是能说清命名卷与绑定挂载的区别，能解释默认 bridge 与自定义网络在名称解析上的差异，能定位容器日志写到了哪里、由哪个驱动接管，并独立排查一次容器之间连不通。
- **配置与密钥（第 12 篇）**：自测标准是能分清构建期与运行期的配置注入方式，并知道本地与集群下密钥机制的差别。
- **资源与安全（第 13、16 篇）**：自测标准是能设定合理的 CPU 与内存限制、解释相对权重与绝对上限之别，并说出至少三项默认安全机制与对应的收紧手段。
- **仓库（第 15 篇）**：自测标准是能搭起私有仓库并完成推送与拉取，理解镜像地址各段含义。

> [!CAUTION]
> **注意内容**：这一级的能力直接关联生产事故面。资源限制设置过紧会导致容器被杀，密钥挂载方式选错会把明文留在镜像层里，动手前先把对应篇章读完整，不要只抄一段配置。

**速记**：**能查起来即数据、网络、日志三处可定位；能管起来即配置、资源、仓库、安全四件事都有着落**。



#### 第五级与可跳过的进阶内容

**第五级能编排**：指能把多服务组织成一份可维护的编排文件，并知道何时该向集群过渡，对应本系列第 10、11、20 篇。

- **入门（第 10 篇）**：自测标准是能写出服务、网络、卷三者齐备的 Compose 文件并一键起停。
- **进阶（第 11 篇）**：自测标准是能用多份文件与覆盖机制管理开发与生产两套配置。
- **过渡（第 20 篇）**：自测标准是能说清 Compose 的能力边界，以及集群接手了哪些它不擅长的事；单机足够且无需自愈与弹性时留在 Compose。
- **可以跳过的内容**：第 20 篇的集群部分、第 4 篇的存储后端细节、第 16 篇的深度加固、第 13 篇的精细配额，四者可延后不可长期忽略。

> [!NOTE]
> **提醒内容**：Compose 与 Kubernetes 不是替代关系而是分层关系，二者描述的是不同抽象层级。先在 Compose 里把服务依赖与配置理顺，再迁移会顺利得多。

**速记**：**编排三级——入门 Compose、进阶多文件、过渡到集群；集群、存储后端细节、深度加固、精细配额四者可延后不可忽略**。



### 常见学习误区与查资料的方法

#### 两类通病与报错时的查询顺序

**两类通病**：把命令背下来而不理解容器对象模型，以及照抄网上配置而不核对版本，是入门阶段代价最高的两个习惯。**查询顺序**：常规报错先读官方文档，只有文档无法解释或明显与实现不符时才转向仓库 issue。

- **两类代价**：命令只是对象模型的表层，不理解镜像、容器、网络、卷的关系，遇到组合场景就无法推导该用什么命令；而大量教程停留在旧引擎或 Compose V1 时代，写了已废弃的顶层 version 字段或正在退场的连接方式。
- **纠正办法**：每学一条命令就写出它操作的是哪一类对象、改变了什么状态；每抄一段配置就回官方参考核对字段与版本。
- **先搜 issue 的情形**：行为与文档描述矛盾，或报错信息指向内部组件；此时看状态是否为已关闭、版本是否匹配、运行形态是否一致。
- **最小复现与一句话教程**：最小复现三要素是一份能直接运行的 Dockerfile 或 Compose 文件、一条触发问题的命令、一段完整报错；不写版本与前提的一句话教程，往往只在作者的环境下成立。

> [!WARNING]
> **警告内容**：照抄不核对版本的直接后果不是不生效，而是看起来生效却埋着坑。例如把默认 bridge 上的旧式连接写法当作推荐做法，一旦升级到禁用该能力的版本，服务会整体失联。

**速记**：**背命令不如懂模型，抄配置必须先核版本；常规报错先读文档，内部错误再搜 issue 且看关闭状态与版本**。

**全系列的一句话判断**：Docker 系列讲的不是一套命令，而是以镜像为制品、以容器为运行单元、以编排为组织方式的一整条交付链路；命令会随版本变化，对象关系与分层原理相对稳定。判断是否学会的标准很直接——遇到陌生的容器问题，能否不搜索就说出去查哪一页官方文档。
