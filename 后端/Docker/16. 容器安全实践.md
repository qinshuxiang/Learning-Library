## 容器安全实践

### 与虚拟机的安全边界差异

#### 共享内核的隔离边界

**结论**：容器与宿主机共用同一个内核，隔离由内核的命名空间、控制组、能力与安全模块拼成，而非硬件虚拟化，因此容器的安全边界比虚拟机薄。

- **边界的组成**：命名空间隔离视图，控制组限制资源，Linux 能力把 root 权限拆细，seccomp 过滤系统调用，LSM 做强制访问控制。这几件是并列的，缺一项就少一层。
- **虚拟机的边界**：由 Hypervisor 提供，客户机拥有独立内核；容器镜像里不含内核，这个差别是两者安全强度分野的根。
- **逃逸的定义**：容器内进程突破上述任一约束、进入宿主机命名空间或以宿主机身份执行操作，即构成逃逸。
- **共用的代价**：同机所有容器共享同一份内核攻击面，一个容器触发内核缺陷可能波及同机其他容器。

> 常见误解是把容器当成轻量虚拟机，于是默认它"出不去"。准确说法是：容器是内核裁剪出的一组受限进程，边界由内核实现，也因此随内核缺陷而失效。

**速记**：**隔离靠内核特性，不靠硬件虚拟化；边界薄在共用内核。**



#### 内核漏洞即逃逸路径

**结论**：凡是能触发宿主机内核缺陷的系统调用路径都可能成为逃逸路径，因此宿主机内核与容器运行时的版本更新属于安全前提，而非可选项。

- **逃逸的技术本质**：借内核缺陷取得宿主机命名空间中的权限，或绕过 runc 等运行时为容器设置的约束。
- **受影响面**：内核自身的缺陷、runc 与 containerd 的运行时缺陷、文件系统与驱动模块的缺陷，三者任一出问题都可能翻越边界。
- **更新属于安全策略**：内核、Docker Engine、containerd、runc 都要保持在受支持且可追溯的版本上，补丁窗口要有明确流程。
- **2026 年的状态**：BuildKit 与 containerd 年内均有安全更新，保持引擎版本更新是前提；具体公告与受影响版本以官方 release notes 与安全公告为准。
- **减少攻击面**：seccomp 默认配置挡掉一批高风险系统调用，使容器内根本调不到挂载、加载内核模块等接口，详见本篇能力与内核调用过滤一节。

> [!WARNING]
> **警告内容**：共享内核意味着宿主机内核的一个缺陷可能同时压穿同机上所有容器。容器主机必须像对待裸机一样及时跟进安全更新，不能因为"跑在容器里"而降低补丁优先级。

**速记**：**内核缺陷即逃逸入口，运行时与内核版本更新是前提。**



#### 从沙箱到权限约束的认知模型

**结论**：容器安全的正确心理模型不是"沙箱"，而是"带权限约束的资源隔离"；工作的落点是持续缩小容器能做的事，而不是指望边界自动兜底。

- **沙箱心智的错误**：以为容器内进程天然"出不去"，于是把不可信负载直接放进普通容器，省掉所有额外约束。
- **正确心智**：默认给出一组约束（非 root、能力裁剪、seccomp、只读根文件系统），再按实际需要逐项放宽，放宽的每一项都要能说出理由。
- **纵深防御**：镜像、构建、运行时参数、守护进程、网络、审计各层都要有措施，任一层失守不至于满盘皆输。
- **责任划分**：内核与运行时的缺陷靠上游更新解决，配置层的风险只能由使用者自己收口，而后者是绝大多数实际事故的来源。
- **操作原则**：默认拒绝、显式放行，这条原则贯穿本篇全部内容。

> [!IMPORTANT]
> **重要内容**：把容器当沙箱会系统性低估风险；把它看作"默认受限、可按需放权"的进程环境，才会去检查 USER、能力、挂载与网络暴露这些真正决定后果的配置。

**速记**：**不是沙箱，是带权限约束的隔离；默认拒绝、显式放行。**



#### 多租户与更强隔离方案

**结论**：当同一宿主机上运行互不信任的多方负载时，普通容器的内核级边界往往不够，需要考虑虚拟机级或专用沙箱运行时。

- **触发多租户的场景**：面向外部用户的函数计算、在 CI 中运行不受信代码、共享集群中承载不同客户的容器。
- **加固思路一：虚拟机承载**：把容器跑在各自虚拟机中，用硬件虚拟化边界兜住内核风险。云上容器节点普遍是这个模式。
- **加固思路二：沙箱运行时**：用额外的用户态内核或轻量虚拟机包裹容器进程，保持 OCI 兼容的同时加强边界。
- **代表性方案（仅作名词介绍）**：gVisor 以用户态内核拦截容器的系统调用；Kata Containers 以轻量虚拟机承载容器，兼顾 OCI 兼容与更强隔离。
- **代价**：兼容性下降、性能开销上升、运维复杂度提高，只在边界要求确实高时才引入。

> 辨析：这些方案改变的是隔离实现，不改变镜像格式与工作流。是否需要它们，取决于威胁模型里"是否运行不受信负载"，而不是取决于集群规模大小。

**速记**：**互不信任才上强隔离：虚拟机沙箱、gVisor、Kata。**



### 威胁模型与攻击面清单

#### 攻击面总览

**结论**：威胁模型的作用是先把"攻击者能从哪里进来、进来后想要什么"列清楚，再针对每一面配置防御，而不是零散地堆加固项。

- **建模方法**：按数据流与信任边界划分面——镜像从哪来、构建在哪跑、运行时以什么身份跑、守护进程谁能碰、宿主机与内核谁维护、网络向谁开放。
- **信任边界**：容器内进程默认不受信；镜像内容默认按不可信处理；来自宿主机之外的网络流量默认不可信。
- **攻击者目标**：取得容器内代码执行、提权为容器内 root、逃逸到宿主机、窃取凭证、横向移动到其他容器或数据库。
- **防御落点**：每一面都要有"默认拒绝"的配置，再加上能发现异常的审计手段。
- **面的优先级**：配置错误类问题出现频率最高、后果最直接，应优先收口。

> 建模的目的不是穷举，而是保证每一面都有人负责。下面三个考点把常见面分组列出，每一面附一句"攻击者想做什么"，便于对照自查。

**速记**：**先列面、再看攻击者想干什么，最后一面面配默认拒绝。**



#### 镜像与构建过程

**结论**：镜像与构建阶段是供应链攻击的主战场，攻击者的目标是在容器启动前就把代码或凭证放进产物里。

- **镜像来自不可信来源**：攻击者想借被投毒的基础镜像或第三方镜像，在容器启动时直接获得代码执行。
- **镜像内含已知漏洞**：攻击者想利用镜像里过期的库，在容器内先立足，再寻找提权与逃逸机会。
- **构建期注入**：攻击者想在构建步骤里插入后门命令，或读取构建环境中可用的密钥与令牌。
- **缓存与依赖投毒**：攻击者想污染构建缓存或依赖下载源，使最终产物在用户无感知的情况下被替换。
- **构建环境本身**：构建容器常被授予额外权限，攻击者一旦在构建期立足，收益往往高于在运行期。

> 这一面的收口手段属于镜像构建最佳实践与密钥管理两篇的范围，本篇只做定位与清单化，具体做法参见镜像构建最佳实践与多阶段构建、环境变量、配置注入与密钥管理。

**速记**：**供应链先攻镜像与构建：投毒、过期依赖、注入、缓存污染。**



#### 运行时与守护进程

**结论**：运行时攻击面关注容器进程本身的权限，以及守护进程对外暴露的接口，攻击者在这一面的目标是提权、逃逸与横向移动。

- **容器内提权**：攻击者想从普通用户变成容器内 root，或利用 setuid 程序与文件能力获得新权限。
- **逃逸**：攻击者想跳出命名空间进入宿主机，常借特权模式、宿主目录挂载或内核缺陷实现。
- **横向移动**：攻击者想从一台被攻陷的容器连到同网段的其他容器与数据库，放大影响范围。
- **守护进程接口**：攻击者想通过暴露的 docker.sock 或管理端口，以宿主机 root 身份创建容器、挂载宿主目录。
- **资源滥用**：攻击者想用无限制的容器发起资源耗尽或对外攻击，这一面由资源限制约束，参数见容器资源限制与运行时约束。

> [!CAUTION]
> **注意内容**：--privileged 让容器获得全部能力、关闭默认 seccomp 与 AppArmor 并可直接访问宿主设备，等于把宿主机控制权交出去。它只应存在于确知风险且经过评估的场景，不能作为"跑不起来就加它"的常规手段。

**速记**：**运行时四目标：提权、逃逸、横移、控制守护进程。**



#### 宿主机、内核与配置错误

**结论**：宿主机与内核层决定边界是否失效，配置错误层则决定边界是否被绕过；后者出现频率最高，也最容易在自查中纠正。

- **内核与运行时未修补**：攻击者想用已公开的缺陷完成逃逸，补丁滞后即等于留下通道。
- **挂载宿主机目录**：攻击者想借容器写入宿主的 /etc、计划任务、二进制或配置，把容器内的代码执行升级为宿主持久化。
- **特权与宿主命名空间**：--privileged、--pid=host、--net=host 让容器直接进入宿主视角，攻击者借此看到并影响宿主进程与网络。
- **管理端口暴露**：把守护进程端口或数据库端口发布到公网，攻击者无需容器逃逸即可直接接管。
- **安全模块被关闭**：seccomp=unconfined、apparmor=unconfined、label=disable 让内核层过滤与强制访问控制失效。

> 这一层的特征是"默认配置安全、人工改动导致不安全"。因此最有效的检查方式是定期跑一遍配置自查，而不是依赖一次性加固。

**速记**：**宿主内核决定边界是否失效，配置错误决定边界是否被绕过。**



### 最小权限运行

#### 默认 root 的由来与风险

**结论**：除非 Dockerfile 写了 USER，容器主进程默认以 root（uid 0）运行；这是历史默认值，不是运行应用的必要条件，把它改掉是第一优先级的加固项。

- **由来**：早期容器承担系统级任务（装包、改配置、绑定低端口），以 root 运行最省事，于是成为默认。
- **容器内 root 的实际权限**：受命名空间与能力约束，并非宿主 root，但仍可改容器内文件属主、安装软件、绑定低端口、读取容器内所有文件。
- **升级路径**：一旦叠加宿主目录挂载、额外能力或内核缺陷，容器内 root 就可能变成宿主机上的实际控制权。
- **默认能力的残留**：Docker 默认丢弃了很多危险能力，但仍保留 CAP_NET_RAW、CAP_CHOWN、CAP_SETUID 等，攻击者可借它们做不少事。
- **结论**：以非 root 运行能一次性消掉这一整类风险，收益远大于改造成本。

> [!IMPORTANT]
> **重要内容**：以非 root 运行是本篇列出的加固项里性价比最高的一条。应用不需要 root 时，务必在 Dockerfile 写 USER，并在运行时用 --user 兜底。

**速记**：**默认 root 是历史默认，不是必要；非 root 运行排第一。**



#### 用 USER 与 --user 切换

**结论**：镜像内用 USER 指令声明运行身份，运行时用 --user 覆盖；两处配合即可让容器主进程以非 root 身份启动。

- **Dockerfile 声明**：写 USER 1001 或 USER app，作用于其后的所有指令与最终容器进程。
- **运行时覆盖**：docker run --user 1001:1001 或 --user app 指定 UID、GID 或用户名。
- **优先用数字**：镜像里未必存在该用户名的 passwd 条目，写数字 UID 更稳，避免因查找失败而报错。
- **文件属主对齐**：应用需要读写的目录，其属主必须与运行身份匹配；构建时可用 COPY --chown 指定属主。
- **只读挂载的坑**：把宿主目录挂进容器时，容器内身份与宿主目录属主不一致会直接报权限错误，处理原则是调整属主而非放开人人可写。

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY --chown=1001:1001 . .
USER 1001:1001
CMD ["node", "server.js"]
```

> USER 只改变进程身份，不改变文件属主。镜像里由 root 创建的目录，切换 USER 后可能不可写；要么用 COPY --chown 预先改好，要么在构建期建目录并 chown。

**速记**：**USER 定镜像身份、--user 覆盖运行时身份，目录属主要提前对齐。**



#### 需要写临时目录时的处置

**结论**：非 root 运行后，容器内没有可写目录是最常见的落地障碍；用 tmpfs 或预先改属主解决，而不是把权限放宽到人人可写。

- **tmpfs 挂载**：docker run --tmpfs /tmp 在容器内挂一个内存文件系统，写入不落盘、容器停止即消失，适合临时文件与会话数据。
- **预先建目录并改属主**：在 Dockerfile 里以 root 建好目录并 chown 给运行身份，再切 USER，适合需要持久化的可写路径。
- **命名卷**：挂一个空命名卷到可写路径时，Docker 会把镜像中该目录的内容与属主一并复制进卷，属主因此能与运行身份对齐。
- **不要人人可写**：把宿主目录权限改成 777 是绕过报错的坏解法，等于把数据暴露给机器上任意用户。
- **排查顺序**：先确认容器内运行身份，再核对目标目录属主，最后才考虑调整挂载方式。

```bash
docker run --rm --user 1001:1001 --tmpfs /tmp:rw,noexec,nosuid,size=64m my-app
```

> tmpfs 的选项与 Linux 的 mount 选项一致，可用 noexec、nosuid、size 等参数进一步收紧；对只写临时数据的进程，加 noexec 能顺带降低恶意文件被执行的风险。

**速记**：**可写路径靠 tmpfs、预建目录或命名卷，不靠 777。**



#### 只读根文件系统

**结论**：--read-only 把容器根文件系统挂成只读，配合 --tmpfs 与卷白名单指定少数可写路径，是限制运行时篡改与落地持久化的有效手段。

- **基本写法**：docker run --read-only 使根文件系统只读，进程只能写显式挂载的卷或 tmpfs。
- **可写白名单**：用 --tmpfs /tmp、--tmpfs /run 与 -v 挂载为确有需要的路径开写权限，白名单越短越好。
- **典型冲突**：应用会写缓存、日志、PID 文件、Socket 文件，这些路径要么改到 tmpfs，要么挂卷，否则容器启动即失败。
- **代价明确**：--read-only 不是免费加固，需要逐个确认应用的写入点，遗留应用改造成本可能很高。
- **掩码路径**：Docker 默认把 /proc、/sys 下部分路径设为只读或掩码，可用 --security-opt systempaths=unconfined 关闭，但会削弱防护，不应作为常规手段。

```bash
docker run --rm --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --tmpfs /run:rw,noexec,nosuid,size=16m \
  --user 1001:1001 my-app
```

> [!CAUTION]
> **注意内容**：--read-only 会让写入根文件系统的容器直接启动失败，排障时容易误判成镜像问题。上线前应在预发环境确认应用的全部写入路径，把缓存、日志与 Socket 目录逐一改到 tmpfs 或卷上。

**速记**：**根只读、白名单开写；先找齐写入点，再上 --read-only。**



### 能力与内核调用过滤

#### Linux 能力的基本原则

**结论**：Linux 能力把 root 的权限拆成一组细粒度权限，容器默认只保留其中一小部分，剩余部分丢弃；理解默认保留了什么，才能判断还需不需要加。

- **拆分逻辑**：CAP_NET_ADMIN 管网络配置，CAP_SYS_ADMIN 管挂载与大量系统管理操作，CAP_NET_BIND_SERVICE 管绑定低端口，CAP_SYS_MODULE 管加载内核模块等。
- **默认保留的典型能力**：CAP_CHOWN、CAP_SETUID、CAP_SETGID、CAP_FOWNER、CAP_KILL、CAP_NET_BIND_SERVICE、CAP_NET_RAW、CAP_SYS_CHROOT 等。
- **默认丢弃的危险能力**：CAP_SYS_ADMIN、CAP_NET_ADMIN、CAP_SYS_MODULE、CAP_SYS_PTRACE、CAP_SYS_BOOT 等，因此容器内默认无法挂载文件系统或改网络配置。
- **NET_RAW 的注意点**：它在默认保留集里，允许构造原始报文，容器内 ping 就依赖它，属于默认权限中较敏感的一项。
- **查看方式**：可用 docker inspect 或进入容器后查看进程状态确认当前能力集，核对与预期是否一致。

> 能力是内核级开关，比容器内用户身份更底层：即使容器内是 root，没有对应能力也做不了对应操作。这也是"容器内 root 不等于宿主 root"的关键原因之一。

**速记**：**root 权限拆成能力，默认只留一小撮，CAP_SYS_ADMIN 等危险项不在其中。**



#### cap-drop ALL 起手与按需 cap-add

**结论**：加固的正确起手式是 --cap-drop ALL 先清空，再针对具体需求用 --cap-add 逐项加回；而不是在默认集上做减法。

- **起手清空**：docker run --cap-drop ALL 丢弃全部能力，得到一个能力集为空的容器。
- **按需加回**：需要什么加什么，加回的能力越少越好，且要为每一项写明用途。
- **典型场景一**：容器内要运行 ping 或需要构造原始报文，加 NET_RAW。
- **典型场景二**：容器内要改路由、配网卡或运行需要改网络配置的工具，加 NET_ADMIN。
- **典型场景三**：非 root 进程要绑定 80 或 443 之类低端口，加 NET_BIND_SERVICE，而不是退回以 root 运行。
- **对照反例**：--privileged 一次性给出全部能力并关闭多道防护，应作为最后手段而非起点。

```bash
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE --user 1001:1001 my-app
```

> 把 --cap-drop ALL 写进团队统一的运行模板或编排配置，需要额外能力的服务单独声明并附注释说明用途。这样能力集在评审时是显式的，不会随时间被无声放大。

**速记**：**先 drop ALL 清空，再按需求逐项 cap-add，一项一理由。**



#### no-new-privileges 阻断提权

**结论**：--security-opt no-new-privileges=true 设置内核的 no_new_privs 标志，禁止进程通过 setuid、setgid 或文件能力获得新权限，是几乎零成本的加固项。

- **阻断的对象**：带 setuid 位的程序、带文件能力的二进制，以及 su、sudo 这类依赖提权机制的命令。
- **效果**：即使容器内存在可提权的二进制，进程也无法借它获得更高权限，常见提权链被直接掐断。
- **附带效果**：按官方说明，它会让 seccomp 过滤器在降权之后应用，可能带来更严格的过滤效果。
- **兼容性**：对绝大多数应用无感知，不改变正常运行逻辑，适合作为所有非特权容器的默认项。
- **写法**：--security-opt no-new-privileges=true，也可用不带取值的简写形式。

```bash
docker run --rm --security-opt no-new-privileges=true --user 1001:1001 my-app
```

> 开启后容器内 sudo 与 su 将不再工作，若镜像把启动脚本写成先 su 到业务用户，需要改成直接以目标用户启动，否则容器会启动失败。

**速记**：**no-new-privileges 掐断 setuid 提权，兼容好、代价低，默认开。**



#### seccomp 过滤系统调用

**结论**：seccomp 在能力之上再加一层系统调用过滤，Docker 的默认配置文件是一份允许列表，默认拒绝、逐个放行，在 300 多个系统调用中挡掉约 44 个。

- **工作方式**：默认动作设为拒绝并返回权限错误，只对白名单内的系统调用放行，因此新增的高危系统调用默认够不着。
- **被挡的典型调用**：mount、umount、reboot、kexec_load、init_module、delete_module、ptrace、bpf、perf_event_open、setns、keyctl、add_key、swapon、settimeofday 等。
- **unshare 的例外**：unshare 通常被挡，但与用户命名空间相关的用法例外，因此容器内仍可做部分命名空间操作。
- **ptrace 的历史差异**：在 4.8 之前的内核上被默认挡掉，以避免绕过 seccomp。
- **自定义与关闭**：--security-opt seccomp=profile.json 指定自定义允许列表；seccomp=builtin 启用内置默认；seccomp=unconfined 关闭过滤。
- **前提**：需要内核开启 CONFIG_SECCOMP，且 Docker 构建时启用了 seccomp 支持。

```bash
docker run --rm --security-opt seccomp=./tight-profile.json my-app
```

> [!NOTE]
> **提醒内容**：自定义 seccomp 配置文件的相对路径由 docker 客户端解析，内容由客户端读好后发给守护进程；客户端与守护进程分处不同主机时，配置文件必须放在客户端一侧。

> 官方明确不建议修改默认的 seccomp 配置。实践中若确需自定义，做法应是保留默认允许列表、在其上再收紧，而不是从空白开始重建白名单。

**速记**：**seccomp 默认白名单，挡掉约 44 个高危调用；unconfined 等于关掉这层。**



#### AppArmor 与 SELinux 的定位

**结论**：AppArmor 与 SELinux 都是 Linux 安全模块提供的强制访问控制，前者按可执行文件路径写规则，后者按进程与文件的安全标签写规则，二者都与 seccomp、能力叠加生效。

- **AppArmor 的默认行为**：Docker 会自动为容器生成并加载名为 docker-default 的配置，它在 tmpfs 中生成后载入内核，保护程度适中，兼顾兼容性。
- **AppArmor 的指定与加载**：--security-opt apparmor=my-profile 指定自定义配置，配置加载用 apparmor_parser -r -W 路径完成，卸载用对应的反向参数。
- **AppArmor 的模式**：enforce 模式主动阻止并记录越界行为，complain 模式只记录不阻止，可用 aa-status 查看各配置处于哪种模式。
- **AppArmor 的例外**：特权容器若未显式指定配置，或以 unconfined 指定，则等于不使用该防护。
- **SELinux 的用法**：--security-opt label=type:xxx 指定类型标签，label=disable 关闭标签约束，label=level:xxx 设置多级安全级别；绑定挂载常需加 :z 或 :Z 重新打标签，否则容器无权限读取。
- **适用发行版**：AppArmor 多见于 Debian 与 Ubuntu 系，SELinux 多见于 RHEL、CentOS、Fedora 系，前提是宿主已启用对应模块。

> [!NOTE]
> **提醒内容**：按官方文档，Docker Engine 29.8 起支持用自定义模板生成 docker-default 配置，模板放在 /etc/docker/apparmor/docker-default，再通过 daemon.json 的 apparmor-profile 键或守护进程的同名标志启用；该配置不能同时写在标志与 daemon.json 里。是否使用以官方文档与 29.8 及以上版本为准。

**速记**：**AppArmor 管路径、SELinux 管标签，都用 --security-opt 指定，关掉即失去这层。**



### 用户命名空间与 rootless

#### userns-remap 的原理

**结论**：用户命名空间重映射把容器内的 root 映射到宿主机上一个高段、无特权的 UID 范围，使容器内 root 在宿主上不拥有任何特权。

- **映射来源**：/etc/subuid 与 /etc/subgid 记录每个用户可以使用的从属 UID 与 GID 范围。
- **映射规则**：范围起点在容器命名空间内表现为 UID 0，其后逐个递增；例如 testuser:231072:65536 表示 231072 在容器内映射为 0。
- **默认用户**：配置里写 default 时，Docker 会创建并使用名为 dockremap 的用户与组。
- **效果**：容器内进程即使以 root 身份运行，在宿主上也只是一个甚至不对应真实账户的高位 UID，无法读写宿主上属于其他用户的资源。
- **配置位置**：在 daemon.json 中设置 userns-remap，或在启动守护进程时用同名的 --userns-remap 标志。
- **关键区别**：它只重映射容器，守护进程本身仍以 root 运行，因此不等同于 rootless。

```json
{
  "userns-remap": "default"
}
```

> [!IMPORTANT]
> **重要内容**：userns-remap 与 rootless 都借助用户命名空间，但保护的对象不同：userns-remap 保护容器、守护进程仍为 root；rootless 把守护进程与容器一并降权。选择哪种取决于是否需要连守护进程一起降低风险。

**速记**：**容器 root 映射到宿主高位 UID，守护进程仍是 root。**



#### 开启方式与代价

**结论**：userns-remap 能显著提升容器内 root 的可控性，但会遮蔽既有数据、限制部分功能，且与现行的 containerd 镜像存储存在已知冲突，启用前必须评估。

- **验证是否生效**：docker info 的 Security Options 段会出现 userns 相关标识；/var/lib/docker 下会出现以 UID.GID 命名的目录，属主为映射后的用户。
- **遮蔽既有资源**：启用后会遮蔽原有的镜像与容器层，Docker 把它们放到按映射用户命名的子目录下，因此最好在新装机器上启用。
- **不可逆的代价**：关闭 userns-remap 后，启用期间创建的镜像与容器不再可直接访问，需要重新构建或迁移。
- **不兼容的功能**：与宿主共享 PID 或 NET 命名空间（--pid=host、--network=host）不兼容；--privileged 除非同时指定 --userns=host 也不兼容；不了解该映射的外部卷或存储驱动同样不可用。
- **官方已知限制**：Docker Engine 29.0 起默认使用的 containerd 镜像存储不支持与 userns-remap 同时使用。
- **单容器豁免**：可对个别容器用 --userns=host 关闭重映射，但只读镜像层在容器间共享，其文件属主仍被重映射，可能影响 sudo 与带 setuid 位的程序。
- **挂载属主**：绑定挂载要读写时，宿主目录的文件属主需要提前按映射后的 UID 安排。

> [!CAUTION]
> **注意内容**：userns-remap 不是可以随手开关的选项。在已有数据的机器上启用会让既有镜像与容器不可直接访问，在启用了 containerd 镜像存储的 29.x 新装机器上又无法同时启用。落地方案应在建机阶段就确定，而不是上线后临时加。

**速记**：**遮蔽旧数据、功能受限、与 containerd 镜像存储冲突；新装机阶段就定。**



#### rootless 模式的定位与落地

**结论**：rootless 模式以普通用户运行 dockerd 与容器，两者都在用户命名空间内，从根本上降低守护进程缺陷被利用后的影响。

- **前提条件**：必须安装 newuidmap 与 newgidmap（多数发行版由 uidmap 包提供），且 /etc/subuid 与 /etc/subgid 中至少有 65536 个从属 UID 与 GID。
- **安装方式**：以普通用户执行 dockerd-rootless-setuptool.sh install，脚本会创建用户级 systemd 单元并注册 rootless 上下文。
- **启动与自启**：用 systemctl --user start docker 管理生命周期，用 loginctl enable-linger 用户名 让服务在未登录时也能启动。
- **连接方式**：套接字默认位于 $XDG_RUNTIME_DIR/docker.sock，通常为 /run/user/用户 ID/docker.sock，通过设置 DOCKER_HOST 或 docker context use rootless 让客户端连上它。
- **数据位置**：镜像与容器数据默认放在用户家目录下的 .local/share/docker，而非 /var/lib/docker。
- **网络方案**：网络由 RootlessKit 的网络驱动提供，默认使用 slirp4netns 做用户态网络，也可切换到 pasta 等驱动。

```bash
dockerd-rootless-setuptool.sh install
systemctl --user start docker
export DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock
docker info
```

> [!NOTE]
> **提醒内容**：rootless 守护进程在独立的网络命名空间内运行，容器 IP 宿主侧默认不可直接访问，需要进入对应命名空间才能看到。排查连通性时要先意识到这层额外命名空间，而不是先怀疑防火墙。

**速记**：**普通用户跑 dockerd 与容器，网络走 RootlessKit（默认 slirp4netns）。**



#### rootless 的能力边界

**结论**：rootless 用功能性换取安全性，存储驱动、资源限制、安全模块与低端口访问都有明确限制，采用前要逐条对照业务需求。

- **存储驱动受限**：只支持 overlay2（需内核 5.11 及以上）、fuse-overlayfs（需内核 4.18 及以上且已安装）、btrfs 与 vfs。
- **资源限制受限**：cgroup 仅在 cgroup v2 加 systemd 的环境下可用；在 cgroup v1 上，--cpus、--memory、--pids-limit 会被忽略。
- **不支持的功能**：AppArmor、检查点与恢复、Overlay 网络、暴露 SCTP 端口均不支持。
- **低端口访问**：要暴露 1024 以下的端口，需要给 rootlesskit 二进制加 CAP_NET_BIND_SERVICE 能力，或把 net.ipv4.ip_unprivileged_port_start 调低。
- **数据目录限制**：数据目录不能放在 NFS 上。
- **适用定位**：适合开发机、共享构建机、低权限边缘场景；需要完整内核能力或依赖上述受限功能的场景不适合。

> 辨析：rootless 解决的是"守护进程以 root 运行"这一风险，不替代容器内的最小权限配置。即使跑在 rootless 下，容器仍应非 root、裁剪能力并保留 seccomp。

**速记**：**rootless 换安全舍功能：存储驱动、cgroup、AppArmor、低端口都要让路。**



### 守护进程的保护

#### docker.sock 的权限等价性

**结论**：能访问 /var/run/docker.sock 就等于能在宿主机上以 root 执行任意操作，这条等价关系是守护进程防护的出发点。

- **原因**：守护进程对外提供的 API 能创建容器、挂载宿主目录、以特权启动进程，而守护进程本身以 root 运行。
- **推论一，不要随手加 docker 组**：把普通用户加入 docker 组，等价于给该用户接近免密 sudo 的宿主权限。
- **推论二，不要把 socket 挂进容器**：挂载后容器内进程可通过 API 控制宿主机，哪怕容器本身是非 root。
- **推论三，CI 场景尤其危险**：为构建镜像而挂载 socket，等于把构建环境提升为宿主控制面。
- **推论四，只读挂载挡不住**：套接字是双向通信通道，只读挂载不能阻止通过它发起调用。
- **远程同理**：通过 TCP 暴露守护进程时，客户端证书与私钥的敏感度等同于宿主 root 口令。

> [!WARNING]
> **警告内容**：把 docker.sock 交给容器或普通用户，等价于把宿主机 root 权限交出去。攻击者只需一次容器创建请求，就能把宿主机根目录挂进新容器并改写系统文件，完成持久化。

**速记**：**碰得到 docker.sock，就等于摸到了宿主 root。**



#### 交出 socket 之外的替代方案

**结论**：需要程序化控制 Docker 时，应选择受限接口、rootless 或专用服务，而不是把完整 socket 交出去。

- **受限 socket 代理**：在 socket 前放一个只放行必要 API 的代理，例如只允许查看状态或只允许操作特定标签的容器，其余请求一律拒绝。
- **rootless 守护进程**：让本来就不需要 root 的工作负载跑在用户态守护进程上，被利用的上限随之降低。
- **专用构建服务**：把镜像构建放到一次性、隔离的构建集群或托管构建服务，避免在共享宿主上挂载 socket。
- **通过声明式配置下发**：用编排文件与流水线部署，减少人工执行 docker run 的窗口，权限收敛到流水线身份。
- **审计与告警**：无论采用哪种方案，都应对通过接口发起的容器创建与挂载操作留痕并监控。

> 辨析：受限代理降低但不消除风险，代理放行的接口仍需逐条评估；rootless 改变的是权限上限而非接口能力。落地时通常组合使用，而不是只挑一种。

**速记**：**别交 socket：受限代理、rootless、专用构建、声明式下发。**



#### 远程访问必须走 TLS

**结论**：默认只监听本地 Unix 套接字；需要远程访问时必须显式监听 TCP 并启用双向 TLS 校验，绝不以明文暴露。

- **默认状态**：守护进程默认只监听本地 Unix 套接字，远程连接需要显式用 -H 指定监听地址。
- **启用 TLS**：启动守护进程时用 --tlsverify 打开双向校验，用 --tlscacert、--tlscert、--tlskey 指定 CA、服务端证书与私钥，监听端口惯例为 2376。
- **客户端配置**：设置 DOCKER_HOST 指向 tcp://主机:2376、DOCKER_TLS_VERIFY 开启校验、DOCKER_CERT_PATH 指定证书目录，或把证书放进 ~/.docker 后用 docker context 管理。
- **密钥权限**：私钥文件权限设为 0400，证书文件设为 0444；默认 umask 为 022 时私钥可能全局可读，需要显式收紧。
- **证书要求**：证书的 subjectAltName 需包含客户端实际使用的 IP 或域名，否则校验失败。
- **更稳的替代**：用 SSH 隧道或基于 SSH 的 docker context 访问远程守护进程，不直接暴露 TCP 端口。

```bash
dockerd --tlsverify \
  --tlscacert=ca.pem \
  --tlscert=server-cert.pem \
  --tlskey=server-key.pem \
  -H=0.0.0.0:2376
```

> [!WARNING]
> **警告内容**：以 -H 0.0.0.0:2375 暴露守护进程、且不启用 TLS 校验，等于把一个无认证的 root 级 API 挂在公网上，任何人都能借此创建特权容器并接管宿主机。2375 是历史上最常见的管理端口事故来源，暴露前必须确认 TLS 已启用。

**速记**：**远程访问一律 TLS：2376 加双向校验，2375 明文等于交出 root。**



### 镜像供应链

#### 镜像来源与内容可控

**结论**：供应链治理的起点是让可拉取的镜像来源收敛且可知，公共镜像不等于可信镜像。

- **只从可信仓库拉取**：生产环境优先只允许从内部私有仓库拉取，公共仓库仅作为基础镜像的受控输入。
- **公共镜像的处理**：官方镜像相对规范，但仍需固定版本、扫描漏洞，并按内部标准重新构建后再入库。
- **统一维护基础镜像**：由专人维护少量内部基础镜像，业务镜像从它派生，避免每个项目各自从公共仓库起步。
- **禁止不可校验的下载**：Dockerfile 中从任意 URL 下载二进制或脚本会引入不可控内容，应改用包仓库或校验哈希与签名。
- **入口唯一**：私有仓库作为唯一入口，配合命名规范与权限控制，具体建设见镜像仓库与私有 Registry。

> 辨析：镜像来源可控解决的是"内容从哪来"，不等于"内容安全"；来源可信的镜像仍可能有已知漏洞，因此来源收敛与漏洞扫描要同时做。

**速记**：**来源收敛到内部仓库，基础镜像统一维护，禁不可校验下载。**



#### digest 固定与签名验证

**结论**：标签可以随上游漂移，摘要不可变；用摘要固定镜像、用签名验证来源，是供应链可控的两种互补手段。

- **标签与摘要的差别**：标签是可变引用，同一标签在不同时间可能指向不同内容；摘要由内容计算得出，内容变了摘要就变。
- **固定写法**：在镜像引用中写 镜像名@sha256:摘要，拉取与部署都按这份内容进行。
- **查看摘要**：可用 docker buildx imagetools inspect 查看远程镜像的摘要，或用 docker inspect 查看本地镜像的摘要。
- **Docker 原生签名**：Docker Content Trust 通过设置 DOCKER_CONTENT_TRUST=1 开启签名与验证，属于 Docker 自身的信任机制。
- **cosign**：Sigstore 生态的签名与验证工具，需要自行安装与部署，适合已有密钥与策略基础设施的团队。
- **策略化落地**：在 CI 中构建后签名，在部署入口校验签名，策略层拒绝未签名或摘要不符的镜像。

```bash
docker buildx imagetools inspect nginx:1.27-alpine
docker pull nginx@sha256:替换为实际摘要
```

> [!NOTE]
> **提醒内容**：固定摘要保证"这次部署用哪一份内容"，但不等于自动获得更新。摘要是手段而非目的，仍需要配套的重建节奏，见本节最后一个考点。

**速记**：**标签会漂移、摘要不会；摘要管内容，签名管来源。**



#### SBOM、attestation 与扫描闸门

**结论**：软件物料清单记录镜像里有什么，构建证明记录它是怎么构建出来的，漏洞扫描负责发现已知问题；三者在 CI 中组合成供应链闸门。

- **SBOM 的作用**：以标准格式列出镜像内的组件与版本，用于漏洞响应时快速判断哪些镜像受影响。
- **attestation 的作用**：记录构建来源、输入与过程，用于验证产物确实是这条流水线按这份源码构建的。
- **生成方式**：BuildKit 与 buildx 支持在构建时用 --sbom 与 --provenance 生成并随镜像推送，具体用法与构建期加固一起见镜像构建最佳实践与多阶段构建。
- **扫描工具**：trivy、grype 等开源扫描器可扫描镜像并输出按严重度分级的漏洞列表，Docker Scout 提供集成度更高的能力。
- **闸门位置**：在构建产出镜像后立即扫描，按严重度与可利用性设置阈值决定是否放行；基础镜像单独建立扫描任务。
- **范围之外**：运行时配置错误、业务逻辑漏洞与未知缺陷都不在扫描范围内。

> [!IMPORTANT]
> **重要内容**：扫描只覆盖已知问题，扫描结果为零不等于镜像安全。它的价值在于把已知漏洞的响应变成可追踪的流程，而不是给出一份安全证明。

**速记**：**SBOM 记内容、attestation 记来源、扫描找已知漏洞，闸门设在 CI。**



#### 基础镜像的更新与响应节奏

**结论**：有漏洞不等于要立刻替换基础镜像，关键是有分级标准与响应流程，把更新变成可持续的节奏。

- **分级依据**：漏洞是否在容器的实际代码路径上可被利用、服务是否对外暴露、修复是否向后兼容，三者共同决定处置优先级。
- **两种重建触发**：定期重建（如按周或按月）保证不长期落后；触发式重建（基础镜像更新或严重漏洞披露时）保证及时响应。
- **重建后复审**：重建产物的摘要、SBOM 与扫描结果都要更新并留档，否则无法回答线上跑的是哪一份、修没修。
- **摘要与重建不冲突**：固定摘要管本次部署用哪份内容，重建管何时产出新的一份内容，两者配合使用。
- **可追溯**：把镜像标签、摘要、SBOM、扫描结果与部署记录关联，事故时才能快速定位影响面。

> 辨析：长期不更新与盲目追新都是问题。前者积累已知漏洞，后者引入未经评估的破坏性变更。可控的做法是固定节奏加明确的例外流程，而不是被动等出事。

**速记**：**分级定优先级，定期加触发式重建，摘要与 SBOM 留档可追溯。**



### 运行时防护与审计

#### 审计与事件来源

**结论**：审计要能回答谁、对什么、做了什么，容器场景下需要把 Docker 层事件与宿主侧系统审计日志结合起来看。

- **Docker 层事件**：docker events 覆盖容器的创建、启动、停止、健康状态变化以及网络与卷事件，是运行状态变化的直接记录。
- **宿主侧审计**：用 auditd 一类系统审计工具记录对守护进程二进制、数据目录、配置目录与套接字的访问，弥补 Docker 事件看不到的层面。
- **官方规则样例**：官方文档给出针对 dockerd、/var/lib/docker、/etc/docker 与 docker.sock 的审计规则写法，可按需裁剪后落地。
- **容器内日志**：应用日志与容器内文件写入需要单独采集与留存，日志体系的搭建见容器日志与监控。
- **关联要求**：审计记录要能关联到具体容器与镜像，否则只能看到宿主机上发生了某件事，无法归因。

```bash
docker events --filter event=start --filter event=die
docker events --since 1h --until 10m
```

> 辨析：docker events 只覆盖 Docker 这一层，看不到宿主上直接执行的命令、内核模块加载与文件变更。安全审计以宿主侧审计日志为主、Docker 事件为辅。

**速记**：**Docker 事件看容器层，auditd 看宿主层，两端要能关联到同一容器。**



#### 行为基线与异常检测

**结论**：先建立"正常长什么样"的基线，才有资格判断异常；容器场景下基线的内容是进程、端口、外联与文件访问四类。

- **基线的四类内容**：哪些容器该起哪些进程、该监听哪些端口、该连接哪些地址、该读取哪些文件。
- **高价值异常信号一**：容器内出现交互式 shell。正常业务容器不应有人登录，出现即值得调查。
- **高价值异常信号二**：异常外联。被入侵的容器常被用于下载工具、挖矿或回传数据，出现基线之外的连接是强信号。
- **高价值异常信号三**：突然大量读取敏感文件或进程数异常增长，后者也可能是资源型攻击的前兆。
- **处置原则**：发现可疑容器时先断网隔离而不是直接删除，保留现场供后续分析。
- **检测落点**：宿主侧审计日志、网络流量记录、进程与文件完整性监控，三者组合覆盖度最好。

> 异常外联之所以价值最高，是因为容器的对外通信通常只涉及少数已知依赖。把基线之外的连接全部告警，误报可控而收益明显。

**速记**：**基线四类：进程、端口、外联、文件；异常外联信号最值钱。**



#### 容器里不放 shell 的价值

**结论**：最终镜像里不装 shell、包管理器与调试工具，能显著增加攻击者在容器内立足与横向移动的成本，属于最小化攻击面的手段。

- **distroless 类镜像**：只包含应用与运行时依赖，不含 shell 与包管理器，攻击者拿到代码执行后难以执行交互命令。
- **收益**：无法方便地下载工具、反弹 shell、探测内网或安装提权工具，攻击链被拉长。
- **代价**：排障不便，无法直接进入容器敲命令；应以临时调试容器替代，而不是把 shell 留在生产镜像里。
- **关联做法**：多阶段构建让最终镜像只含运行时产物，构建工具链留在构建阶段，具体见镜像构建最佳实践与多阶段构建。
- **边界**：不含 shell 只提高成本、不构成安全边界，仍要配合非 root、能力裁剪与 seccomp。

> [!TIP]
> **建议内容**：把"生产镜像不含 shell 与包管理器"写进镜像评审清单，同时明确排障时的替代路径，例如临时调试容器或带调试标签的镜像，避免因排障不便而回退到往镜像里塞工具。

**速记**：**不放 shell 拉长攻击链；是成本不是边界，排障用临时容器。**



### 网络与暴露面

#### 默认互通与网络隔离

**结论**：同一网络内的容器默认可以互相通信，这既是服务发现的基础，也是横向移动的通道；隔离手段是按职责划分网络。

- **互通的范围**：用户自定义网络内，容器可用容器名或服务名互相解析并通信；默认桥接网络上容器之间按 IP 可达。
- **横向移动的风险**：一台容器被攻陷后，可扫描并尝试连接同网络内其他容器，数据库与缓存往往是首要目标。
- **隔离手段一**：按职责划分网络，只让需要互访的服务处于同一网络，前端与数据库不共享同一张网络。
- **隔离手段二**：数据面用内部网络。docker network create --internal 创建的网络不给容器外网路由，适合数据库与内部服务。
- **隔离手段三**：不默认让所有容器连入同一张自定义网络，避免把整个应用栈放进一个互通域。
- **原理回顾**：网络的创建、驱动与 DNS 行为见容器网络基础与端口映射、自定义网络与容器互联。

```bash
docker network create --internal backend
docker run -d --network backend --name db postgres:17-alpine
```

> 辨析：网络隔离缩小的是可达范围，不改变容器本身的权限。被攻陷的容器若同时具备凭据，仍可在允许的网络路径上活动，因此隔离要与凭证收口一起做。

**速记**：**同网络默认互通；按职责分网络，数据面用 --internal。**



#### 端口发布的绑定地址纪律

**结论**：发布端口时不写绑定地址，Docker 会绑到 0.0.0.0，即所有网络接口，可能绕过主机防火墙直接暴露到公网。

- **默认行为**：不指定主机地址时绑定到全部接口，等价于对外可访问，这是最常见的意外暴露来源。
- **只供本机访问**：写 127.0.0.1:主机端口:容器端口，把监听限制在本机回环地址。
- **数据类端口**：数据库、缓存、消息队列与管理接口绝不发布到公网，改用内部网络供应用访问。
- **对外入口**：对外服务统一经反向代理进入，代理是唯一的公网入口，配置方法见 Docker 与 Nginx 反向代理实战。
- **核对真实暴露面**：定期用 docker ps 查看端口映射，并结合宿主机防火墙规则确认真实可达范围，而不是只看启动命令。
- **IPv6 注意**：绑定地址与防火墙规则要同时覆盖 IPv4 与 IPv6，避免只挡了一侧。

```bash
docker run -d -p 127.0.0.1:8080:80 nginx:1.27-alpine
```

> [!WARNING]
> **警告内容**：把数据库端口用 -p 5432:5432 这类写法发布出去，等于把它暴露在全部接口上，且可能绕过仅配置给特定网卡的主机防火墙规则。数据库必须只在内网可达，并配合强口令与访问控制。

**速记**：**不写地址就是绑 0.0.0.0；本机访问写 127.0.0.1，数据端口绝不发布。**



#### 出网与 DNS 出口控制

**结论**：容器默认可以主动访问外网，被入侵后常被用来下载工具或外传数据；出口控制与入口收口同样重要。

- **默认状态**：除内部网络外，容器可以通过宿主机网络访问外网，方向为容器发起的出站连接。
- **风险场景**：攻击者在容器内下载恶意载荷、连接命令与控制服务器、外传窃取的数据。
- **控制手段一**：非必要出网的容器放入 internal 网络，或经代理出口再放行。
- **控制手段二**：在宿主机或边界防火墙按目的地放行，只允许已知依赖的地址与端口。
- **控制手段三**：对 DNS 做白名单。DNS 是常见的隐蔽外传通道，出口控制要同时覆盖标准 53 端口与非标准端口的 DNS 流量。
- **与基线结合**：已知依赖之外的出站连接都应告警，与行为基线的外联检测互相印证。

```bash
docker network create --internal service-mesh
docker run -d --network service-mesh my-internal-service
```

> 辨析：入口收口解决别人进不来的问题，出口收口解决被攻陷后出不去的问题，只做其中一个仍会留下明显的攻击路径。

**速记**：**入口收口管别人进不来，出口收口管被抓后出不去；DNS 也要白名单。**



### 合规基线与自查

#### CIS Docker Benchmark 的定位

**结论**：CIS Docker Benchmark 是 Center for Internet Security 发布的 Docker 安全配置基线，按宿主机与守护进程配置逐条给出检查项与建议值。

- **性质**：它是配置基线而非认证标准，按它收口能显著降低配置型风险，但不能替代威胁建模与运行时防护。
- **覆盖维度**：宿主操作系统加固、守护进程配置、守护进程配置文件与套接字权限、容器运行时参数、镜像与构建、网络、日志与审计等。
- **条目形态**：每条给出检查项、理由、审计方法与修复建议，便于逐条对照执行。
- **版本关系**：基线条目随 Docker 与内核能力演进更新，使用前应确认所依据的版本与自身环境匹配。
- **与本篇的关系**：本篇的清单可以看作该基准在本主题语境下的落地摘要，覆盖面更窄但更贴近日常使用。

> 辨析：基准里的部分条目面向特定场景，未必适用于所有环境，例如是否允许容器内安装包管理器、是否启用用户命名空间，都要结合业务判断，不能机械照搬。

**速记**：**CIS Docker Benchmark 是配置基线，逐条对照能收掉配置型风险。**



#### 自动化检查工具的作用与局限

**结论**：Docker Bench for Security 等自动化工具把基准检查脚本化，适合做周期性体检，但其结论需要人工甄别。

- **Docker Bench for Security**：Docker 官方提供的开源脚本，按 CIS 基线逐项检查并输出通过、警告与不适用三类结果。
- **同类工具**：镜像与运行时扫描器、配置审计工具可与它配合，分别覆盖镜像内容与宿主配置。
- **作用一**：快速给出配置现状，把是否按基线配置从人工核对变成可重复执行的动作。
- **作用二**：作为回归检查，在变更守护进程配置或容器模板后及时发现问题。
- **局限一**：只反映检查时点的静态配置，不覆盖业务逻辑与运行时行为。
- **局限二**：不少条目需要人工判断适用性，误报与不适用项要甄别，不能把脚本输出当作绝对结论。

> [!TIP]
> **建议内容**：把自动化检查接入例行运维流程，例如随发布流水线定期执行并把结果留档；出现新的警告项时当天确认是配置漂移还是工具更新，不要让结果长期无人查看。

**速记**：**自动化检查管配置现状与回归，不覆盖运行时行为，结论要甄别。**



#### 可照做的安全检查清单

**结论**：下列清单按守护进程、镜像、运行参数、网络、凭证、日志、更新七个维度组织，每一项都写明检查方法，可直接照做。

- **守护进程配置**：确认 daemon.json 只配置了必需项，没有开启明文 TCP 监听，套接字仅 root 与必要管理身份可访问。检查方法是查看 /etc/docker/daemon.json 内容与套接字的属主与权限，确认不存在 -H 0.0.0.0 且未启用 TLS 的监听。
- **镜像来源与扫描**：确认生产镜像只来自内部仓库，基础镜像有统一维护方，镜像以摘要或固定版本引用，近期扫描结果已复核。检查方法是抽查部署清单中的镜像引用形式，核对仓库权限与扫描报告时间。
- **运行参数**：确认容器默认非 root、按需裁剪能力、保留 seccomp 与 AppArmor 默认配置、开启 no-new-privileges，且除确有必要外没有使用特权模式与宿主命名空间。检查方法是用 docker inspect 查看单个容器的用户、能力、安全选项与命名空间配置，与团队模板比对。
- **网络暴露**：确认对外端口只经反向代理开放，数据库与管理端口不在公网可达，数据面使用内部网络。检查方法是用 docker ps 列出端口映射，结合防火墙规则与外部端口扫描核对真实暴露面。
- **凭证与密钥**：确认密钥未写入环境变量、镜像层或版本库，运行时通过 secrets 或外部注入提供。检查方法是检查镜像历史与部署文件，检索是否出现明文口令，具体做法见环境变量、配置注入与密钥管理。
- **日志与审计**：确认容器日志有采集与留存，宿主侧审计规则覆盖守护进程与配置目录，审计记录能关联到容器。检查方法是确认日志驱动与留存策略已配置，抽查审计日志中是否记录到容器创建事件。
- **更新机制**：确认内核、Docker Engine、containerd、runc 与基础镜像都有明确的更新与重建节奏，异常情况有响应流程。检查方法是核对版本清单与最近一次重建记录，确认存在定期重建的流水线或计划任务。

> [!CAUTION]
> **注意内容**：清单的价值在于定期执行并留下记录，一次性跑完就归档等于没有。检查项与结果应随环境变更同步更新，否则清单会逐渐与真实配置脱节。

**速记**：**七维自查：守护进程、镜像、运行参数、网络、凭证、日志、更新，每项都要有检查方法。**



### 常见不安全配置清单

#### 权限与命名空间过度放权

**结论**：权限类反模式的共同特征是用一次性放权换掉麻烦，替代做法是按需逐项授权。

- **--privileged**：给全部能力、关闭默认 seccomp 与 AppArmor、开放全部宿主设备。替代做法是用 --cap-add 逐项加能力，确实需要特权时先评估是否该换隔离方案。
- **--pid=host**：让容器看到并影响宿主的全部进程，攻击者可借此观察宿主行为甚至发送信号。替代做法是保留独立 PID 命名空间，需要共享时用 --pid=container:目标容器。
- **--net=host**：跳过网络隔离，容器直接使用宿主网络栈，端口暴露量与横向可达范围都放大。替代做法是使用桥接或自定义网络并按需发布端口。
- **--ipc=host**：与宿主共享 IPC 命名空间，可能读到其他进程的共享内存。替代做法是使用私有 IPC 命名空间，仅确需共享时用 container: 形式。
- **不加 --user**：容器以 root 运行。替代做法是镜像内写 USER，运行时用 --user 兜底。
- **把用户加入 docker 组**：等价于给出接近宿主 root 的权限。替代做法是使用 rootless 或受限代理。

> [!WARNING]
> **警告内容**：--privileged 与宿主命名空间类选项会让容器丧失边界意义，但它们常因容器起不来而被顺手加上。遇到启动失败应先定位缺失的具体能力或挂载，再决定授权范围，不能把放权当作通用解法。

**速记**：**privileged 与 host 命名空间是放权前三名，替代方案是按需授权。**



#### 挂载与安全模块的危险项

**结论**：挂载类反模式把宿主资源直接暴露给容器，安全模块关闭类反模式则让内核过滤失效，两者常同时出现。

- **挂载 docker.sock**：容器内可借 API 控制宿主机。替代做法是使用受限代理或 rootless，确实需要编排能力时改用专用管理组件。
- **挂载宿主根目录或 /etc**：容器内可直接改写宿主系统文件与配置。替代做法是只挂载具体的数据目录，且尽量以只读方式挂载。
- **挂载宿主 /proc 或 /sys**：暴露宿主内核与进程信息。替代做法是保留容器自己的对应挂载，由内核按命名空间裁剪视图。
- **--security-opt seccomp=unconfined**：关闭系统调用过滤。替代做法是保留默认配置，必要时在默认白名单上收紧。
- **--security-opt apparmor=unconfined**：关闭 AppArmor 约束。替代做法是使用 docker-default 或自定义配置。
- **--security-opt label=disable**：关闭 SELinux 标签约束。替代做法是保留标签并为绑定挂载正确设置 z 或 Z 选项。
- **--device 与宿主设备**：把宿主设备直接交给容器会扩大攻击面。替代做法是只添加确需的设备，避免把可能热插拔的块设备交给不受信容器。

```bash
docker run --rm -v /data/app:/data:ro --user 1001:1001 my-app
```

> 辨析：只读挂载比可写挂载安全，但不等于无风险：只读仍可读取内容，若挂载的是包含凭证的目录，信息泄露照样发生。挂载范围本身要尽量小。

**速记**：**别挂 socket 与宿主系统目录，别关 seccomp、AppArmor、SELinux。**



#### 凭证、镜像与运行时反模式

**结论**：这一类反模式的共同点是把方便留在了生产环境里，替代做法是把一次性便利与生产配置分开。

- **密钥写进环境变量或镜像**：明文会进入镜像层历史与部署文件，属常见泄密途径。替代做法是使用 secrets 或运行时注入，做法见环境变量、配置注入与密钥管理。
- **依赖 latest 且长期不更新**：latest 会随上游漂移，长期不重建则积累已知漏洞。替代做法是固定版本或摘要，并建立定期重建节奏。
- **从任意 URL 下载未校验的二进制**：构建期即引入不可控内容。替代做法是从包仓库安装，或校验哈希与签名后再使用。
- **容器内运行 sshd**：把远程接入面搬进容器，容器内多一个长期监听的服务与一套凭证。替代做法是用 docker exec 或编排平台的调试机制接入，远程管理由宿主或平台承担。
- **把宿主机包管理目录挂进容器**：容器内的写入会污染宿主系统。替代做法是构建期装好依赖，运行期只挂业务数据目录。
- **以 root 运行且不加任何限制**：这是默认状态，也是所有其他反模式的基础。替代做法是把本篇前几节的最小权限配置作为团队默认模板。

```bash
docker run --rm --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges=true \
  --user 1001:1001 my-app
```

> [!CAUTION]
> **注意内容**：容器内运行 sshd、把调试工具留在生产镜像里、为排障保留特权开关，这些做法在单次排障时省事，但会长期留在生产环境。上线前应确认关闭了所有临时放权项。

**速记**：**密钥不入镜像与环境变量，版本不漂移，sshd 不进容器，临时放权不上线。**
