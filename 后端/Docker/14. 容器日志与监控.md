## 容器日志与监控

### 容器日志的默认模型

#### 日志从进程到落盘的完整链路

**容器日志的默认模型**：应用进程把输出写到标准输出与标准错误，容器运行时捕获这两条流，再交给守护进程配置的日志驱动，由驱动决定落盘位置或转发目标。

- 应用进程的 stdout 与 stderr 在启动时被接到运行时创建的管道写端，进程本身并不知道输出去了哪里。
- containerd-shim 持有管道的读端并维持 IO 通道，这正是 容器生命周期与常用命令 一章所述调用链里 shim 保持标准输入输出通道的原因。
- 守护进程的日志子系统从这条流里读取每一行，按时间戳与来源流（stdout 或 stderr）组装成日志记录。
- **日志驱动（logging driver）**：守护进程内负责把日志记录写到目标位置的组件，决定日志的存放形态、是否落盘以及能否被 docker logs 读取。
- 落盘型驱动把记录写进数据目录下的文件，转发型驱动把记录发往远端服务，none 驱动直接丢弃。

```bash
# 观察应用输出如何进入日志：起一个每秒打印的容器
docker run -d --name ticker busybox sh -c 'while true; do date; sleep 1; done'
docker logs --tail 3 ticker
```

```text
Sat Sep 12 08:30:01 UTC 2026
Sat Sep 12 08:30:02 UTC 2026
Sat Sep 12 08:30:03 UTC 2026
```

> 这条链路解释了容器排障的第一原则：日志先看 docker logs，看不到再去找日志驱动与应用的输出配置。日志在下游丢失，多半是应用没有写标准输出，或驱动把内容转去了别处。

**速记**：**应用写标准流，运行时捕获，日志驱动定去向**。



#### 十二要素给出的日志结论

**十二要素应用的日志结论**：应用只把事件流写到标准输出与标准错误，不关心日志的存储、轮转与路由，收集与投递交给运行环境承担。

- **不自己写日志文件**：进程不打开按日期切分的文件，也不维护多份日志路径。
- **不做应用内轮转**：切分、压缩、删除旧文件由运行时或日志平台负责，应用不去实现 logrotate。
- **不做分类路由**：不判断该写本地还是远端，不按级别分流到不同目的地。
- **运行时接管收集**：标准流由运行时统一捕获，容器编排平台再决定汇聚到何处。
- 这套约定与容器单进程模型天然契合：一个容器一个主进程，进程退出容器即结束，没有常驻的日志守护进程可用。

> 十二要素并非强制标准，而是一套降低运维耦合的经验总结。它要解决的问题是：应用一旦把日志写进自己的文件，就把存储布局、轮转策略与投递方式一起固化进了镜像，换环境就得改代码。

**速记**：**只写标准流，不落自家文件、不做轮转、不做路由**。



#### 为什么往容器内写日志文件是最差的做法

**往容器内写日志文件**：指应用把日志写进容器可写层的某个路径，而不是写到标准输出，这种做法的代价远大于收益。

- **读不到**：docker logs 只读标准流，写进文件的日志在 docker logs 里完全不可见，只能 exec 进去看。
- **会消失**：文件在容器可写层里，容器被删除时随可写层一起丢弃，重建即丢历史。
- **撑大可写层**：持续写入会让容器体积不断增大，docker diff 与提交镜像都会把这个增长带进去。
- **无法集中**：多副本、多主机场景下每台机器各写各的，检索与告警没有统一入口。
- **与轮转冲突**：应用内自建轮转与运行时的日志机制重叠，策略一旦不一致就会互相覆盖。
- 补救手段是把日志目录挂载到卷或宿主目录，但这只是把文件挪出可写层，读不到与无法集中两项问题依旧存在。

```bash
# 反例：日志写进容器内文件，docker logs 为空
docker run -d --name badlog busybox sh -c 'while true; do date >> /tmp/app.log; sleep 1; done'
docker logs badlog
docker exec badlog tail -3 /tmp/app.log
```

> [!WARNING]
> **警告内容**：日志写在容器可写层，容器一旦被删除或重建，日志与现场一并消失，事故复盘将无据可查。排查故障期间尤其不要对这类容器执行 docker rm，应先 docker cp 把日志导出。

**速记**：**写容器内文件等于读不到、留不住、搬不走、聚不齐**。



### 日志驱动总览

#### 日志驱动清单与各自去向

**日志驱动**：守护进程内决定日志记录去向的组件，按去向分为本地存储型、系统日志型与远端转发型三类。

- **json-file**：默认驱动，把记录格式化为 JSON 逐行写进数据目录下的文件。
- **local**：本地存储型，用为性能与磁盘占用优化的自定义格式存放，官方推荐的本地默认替代。
- **syslog**：把记录写进宿主机的 syslog 设施，宿主机必须有 syslog 守护进程在监听。
- **journald**：把记录写进 systemd 的日志系统，宿主机需运行 journald，可由 journalctl 统一检索。
- **fluentd**：按 forward 协议发往 Fluentd，fluent-bit 是同一协议的轻量采集器，二者常互为上下游。
- **gelf**：按 Graylog Extended Log Format 发往 Graylog 或 Logstash 一类可接收该格式的端点。
- **awslogs**：发往 Amazon CloudWatch Logs，需配置区域、日志组与凭证。
- **splunk**：通过 HTTP Event Collector 发往 Splunk。
- **gcplogs**：发往 Google Cloud Platform 的 Logging 服务。
- **etwlogs**：把日志作为 Windows 事件跟踪事件写出，仅在 Windows 平台可用。
- **none**：丢弃全部日志，容器不产生任何可读日志。

> 归类不必死记：json-file 与 local 是本地落盘，syslog 与 journald 是交给宿主机的系统日志，fluentd、gelf、awslogs、splunk、gcplogs 是发往远端平台，none 是彻底关闭。驱动一旦选定，容器创建后不能再改，只能删除重建。

**速记**：**本地两种、系统两种、远程五种，再加一个 none**。



#### 哪些驱动支持 docker logs

**支持读取的驱动**：官方文档明确，docker logs 可以读取 local、json-file 与 journald 三个驱动的日志；其余远程驱动与 none 不支持本地读取。

- **支持读取**：local、json-file、journald，docker logs 直接返回内容。
- **不支持读取**：syslog、gelf、fluentd、awslogs、splunk、gcplogs、etwlogs 等远程或平台驱动，日志已被转发出去，本地没有可读副本。
- **none**：容器根本不产生日志，docker logs 没有任何输出。
- **dual logging 缓存**：守护进程检测到所选驱动不支持读取时，会自动额外保留一份本地缓存，使 docker logs 仍能读到；可用 cache-disabled 选项按容器或全局关闭。
- 关闭缓存后对不支持读取的驱动执行 docker logs，会得到明确的报错，而非空输出。

```bash
# 查看某容器实际使用的日志驱动
docker inspect -f '{{.HostConfig.LogConfig.Type}}' web

# 使用 none 驱动的容器，docker logs 无输出
docker run -d --name silent --log-driver none nginx
docker logs silent
```

```text
Error response from daemon: configured logging driver does not support reading
```

> [!IMPORTANT]
> **重要内容**：把日志驱动换成远程转发后，"docker logs 查不到"是预期行为而非故障。要么接受改用远端平台检索，要么保留 dual logging 缓存，要么同时配一个本地落盘驱动的旁路采集器。

**速记**：能读的只有 **local、json-file、journald**，其余靠缓存或去远端查。



#### 全局默认与单容器覆盖

**配置层级**：daemon.json 的 log-driver 与 log-opts 设定守护进程级默认，docker run 的 --log-driver 与 --log-opt 按容器覆盖这层默认，形成全局加例外的两层结构。

- **全局默认**：写在 /etc/docker/daemon.json，对所有新建容器生效，适合统一策略。
- **单容器覆盖**：--log-driver 指定驱动，--log-opt 键=值 重复添加选项，只影响该容器。
- **值的形式**：log-opts 内的数值与布尔值都必须写成字符串，如 "max-file": "3"，写成数字会被拒绝。
- **生效范围**：改动只影响之后新建的容器，已存在的容器保留创建时的驱动与选项。
- **查看生效值**：docker info 的 LoggingDriver 是守护进程默认，docker inspect 的 HostConfig.LogConfig 是容器实际值。
- **Desktop 差异**：Docker Desktop 上改守护进程配置的入口在 Settings 的 Docker Engine 页，本质仍是编辑同一份 JSON。

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

```bash
# 单容器覆盖为 local 驱动
docker run -d --name web \
  --log-driver local --log-opt max-size=10m \
  nginx

# 查看生效值
docker info --format '{{.LoggingDriver}}'
docker inspect -f '{{.HostConfig.LogConfig}}' web
```

> 判断优先级只需记一句：容器上的 --log-driver 压过守护进程默认，守护进程默认压过内置的 json-file。改完 daemon.json 记得重启或重载守护进程，且改的是"新容器"的行为。

**速记**：**daemon.json 定默认，--log-driver 按容器覆盖，改动只对新容器生效**。



#### 本地存储与远程转发怎么选

**选型口径**：单机排障为主选本地落盘型，需要统一检索与长期留存选远程转发型；生产常见的是本地落盘加采集器转发的折中方案。

- **本地落盘（json-file、local）**：实现简单、docker logs 可直接读、不依赖外部服务；代价是占用宿主磁盘，日志散落在各机器上。
- **远程转发（fluentd、gelf、awslogs、splunk）**：日志集中到平台，检索、留存与告警由平台承担；代价是依赖网络与目标服务，docker logs 读不到本体。
- **系统日志（journald、syslog）**：复用宿主机既有的日志基础设施，适合已有统一日志规范的机器。
- **折中方案**：驱动仍用 local 或 json-file 落盘，另起 Fluent Bit 一类采集器读日志文件转发到平台，本地可读与集中检索兼得。
- **写阻塞风险**：转发型驱动默认采用阻塞模式，目标不可达时会拖住写日志的进程，高吞吐场景需改为非阻塞并设置缓冲区。

```bash
# 非阻塞模式加缓冲，避免远端故障拖住应用
docker run -d --name api \
  --log-driver fluentd \
  --log-opt fluentd-address=127.0.0.1:24224 \
  --log-opt mode=non-blocking \
  --log-opt max-buffer-size=4m \
  myapp:1.0
```

> [!CAUTION]
> **注意内容**：转发型驱动默认阻塞，远端日志服务不可达时写入会卡住，极端情况下应用因写日志而停顿。生产使用远程驱动务必评估非阻塞模式与缓冲区大小，并接受缓冲区满时丢日志的取舍。

**速记**：**要 docker logs 就本地落盘，要集中检索就转发，生产多用落盘加采集**。



### 日志轮转与磁盘炸盘

#### json-file 默认不轮转

**json-file 的默认值**：max-size 默认为 -1 表示不限制，max-file 默认为 1，因此默认配置下每个容器的日志文件会无限增长，这是容器磁盘写满的头号原因。

- **默认不切分**：不设 max-size 时不会发生轮转，单个日志文件可以涨到任意大小。
- **磁盘占满**：日志增长会把所在分区吃尽，dockerd 自身也可能因无法写盘而异常。
- **inode 耗尽**：即使空间尚有裕量，海量小文件也可能先耗尽 inode，表现为"有空间却写不进去"。
- **高发场景**：长时间运行的服务、循环报错的进程、把访问日志打到标准输出的应用。
- **核实方法**：docker system df 看整体占用，du 看日志目录明细，du -sh /var/lib/docker/containers 是最快的一眼定位。

```bash
# 确认日志驱动与占用
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}' web
docker system df
sudo du -sh /var/lib/docker/containers
```

> [!WARNING]
> **警告内容**：生产环境必须为每个容器设置日志轮转。默认 json-file 不限制文件大小，一个跑三个月且不断输出错误日志的容器足以把宿主机磁盘写满，进而引发宿主机上所有服务连锁故障。

**速记**：**json-file 默认 max-size 无限制、max-file 为 1，不设轮转必炸盘**。



#### max-size 与 max-file 的写法与取值

**max-size**：单个日志文件允许增长到的最大字节数，达到阈值即触发轮转。**max-file**：轮转后可保留的日志文件个数上限，超出时删除最旧的文件；它仅在同时设置了 max-size 时才生效。

- 单位支持 k、m、g，大小写不敏感，如 10m、100m、1g。
- 单容器日志总量上限约为 max-size 乘以 max-file，10m 加 3 个文件即约 30MB 封顶。
- 取值看输出量：低频服务 10m 与 3 个文件已足够，高频访问日志可用到 100m 与 5 个文件。
- 配置入口只有两处：daemon.json 的 log-opts 设全局默认，或在 docker run 上用 --log-opt 逐个指定。
- 已存在的容器不会自动套用新值，必须删除重建才会带上轮转参数。
- 另可加 compress 选项，让轮转后的旧文件压缩存放，牺牲少量 CPU 换磁盘。

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5",
    "compress": "true"
  }
}
```

```bash
# 单容器设置轮转
docker run -d --name web \
  --log-opt max-size=10m --log-opt max-file=3 \
  nginx
```

> 数量关系容易记反：max-size 管"单个文件多大"，max-file 管"留几个文件"。只设 max-file 而不设 max-size 不会轮转，等于白设。

**速记**：**max-size 管单文件上限，max-file 管保留个数，总量约为两者乘积**。



#### local 驱动的自带轮转

**local 驱动的默认轮转**：官方文档给出的默认值是单文件 20m、保留 5 个文件、默认启用压缩，合计每容器约 100MB；这是官方推荐用它替代 json-file 作为本地默认驱动的主要原因。

- **开箱即有上限**：不配置任何选项时，每容器日志已被限制在约 100MB，不存在 json-file 那种默认无限增长的问题。
- **存储格式**：使用为性能与磁盘占用优化的自定义格式，比纯文本 JSON 更省空间，代价是不能直接用 cat 当作文本阅读。
- **仍支持 docker logs**：local 属于支持读取的驱动，日常查看命令与 json-file 完全一致。
- **可调参数**：max-size、max-file、compress 三个选项含义与 json-file 一致，默认值不同。
- **切换代价**：驱动在容器创建时固化，把既有容器从 json-file 切到 local 需要删除重建。

```json
{
  "log-driver": "local",
  "log-opts": {
    "max-size": "20m",
    "max-file": "5"
  }
}
```

> 名字含 local 不代表它只写本地：它描述的是存储实现是本地文件，而不是与远程驱动对应的分类。要真正发往远端，仍需选用 fluentd、gelf 一类转发驱动。

**速记**：**local 默认 20m 乘 5 约 100MB、默认压缩，且照样支持 docker logs**。



#### 磁盘已被日志写满的处置顺序

**处置顺序**：先确认是不是日志占的，再定位到具体容器，再决定清理方式，最后补上轮转防止复发，顺序颠倒容易误删数据。

1. 用 df -h 确认哪个分区被占满，以及剩余空间是多少。
2. 用 du -sh /var/lib/docker/containers 确认日志目录总量，再逐目录排序找出最大的容器目录。
3. 用 docker ps 与目录名里的容器 ID 对应出容器，必要时 docker inspect 确认。
4. 用 docker logs --tail 200 看该容器是否在异常刷屏，先判断这是不是一个有问题的服务。
5. 处置分档：应急可清空单个日志文件释放空间，稳妥则修复应用的刷屏问题并重建带轮转参数的容器。
6. 补上 daemon.json 的 max-size 与 max-file 并重启守护进程，新建容器从此带上轮转。

```bash
# 定位占用最大的容器日志目录
sudo du -sh /var/lib/docker/containers/* | sort -h | tail -5

# 应急清空单个日志文件（外部工具操作日志文件可能干扰日志系统，属应急手段）
sudo truncate -s 0 /var/lib/docker/containers/<容器ID>/<容器ID>-json.log
```

> [!CAUTION]
> **注意内容**：不要在守护进程运行时直接 rm 容器的日志文件。守护进程持有该文件的句柄，删除目录项后空间往往不会立即释放，还会让后续写入落在已删除的 inode 上；应急清空应使用 truncate 清零内容，最彻底的做法是重建容器。

**速记**：**df 定分区、du 定容器、logs 定原因、truncate 应急、配轮转防复发**。



### 日志文件在哪

#### Linux 上的日志路径与命名

**json-file 的日志路径**：Linux 上位于 /var/lib/docker/containers/容器全量 ID/容器全量 ID-json.log，容器 ID 目录下还存放该容器的配置与元数据。

- 目录名与文件名都是容器全量 ID，文件后缀固定为 -json.log，这是识别 json-file 落盘结果最直接的特征。
- 同目录下还有 config.v2.json、hostconfig.json、hostname、hosts、resolv.conf 等由守护进程生成的文件。
- 该路径以 data-root 为基准，若在 daemon.json 中改过 data-root，日志位置随之迁移。
- local 驱动的文件不叫 -json.log，文件名与内部结构都不同，不能按同一命名去猜。
- 直接读该文件只适合应急确认，官方明确提示这些文件专供守护进程访问，外部工具操作可能干扰日志系统。

```bash
# 进入数据目录观察结构
sudo ls /var/lib/docker/containers | head
sudo ls /var/lib/docker/containers/<容器ID>/
```

```text
<容器ID>-json.log
config.v2.json
hostconfig.json
hostname
hosts
resolv.conf
```

> 路径里的容器 ID 是全量 64 位，与 docker ps 显示的短 ID 不同。找不到目录时，先确认 data-root，再确认驱动是不是 json-file，这两个前提不成立就换另一条路径去找。

**速记**：**/var/lib/docker/containers/容器ID/容器ID-json.log，路径随 data-root 走**。



#### 容器 ID 全量与短 ID

**容器 ID**：守护进程生成的 64 位十六进制字符串，全局唯一；**短 ID**：取前 12 位，用于日常命令与界面显示，二者指向同一容器。

- docker ps 的 CONTAINER ID 列显示的是短 ID，日志目录名用的是全量 ID。
- 命令行里传短 ID 只要在当前守护进程内唯一即可，冲突时需给更长的前缀或全量 ID。
- 取全量 ID 的标准写法是 docker inspect -f 的 Id 字段，也可以从 --no-trunc 的 ps 输出里拿。
- 按目录名反查容器时，用短 ID 前缀匹配即可，不必逐字符比对。
- 容器被删除重建后 ID 会变，旧的日志目录也随之消失，不要把 ID 当作长期标识来引用。

```bash
# 取全量 ID 与短 ID
docker inspect -f '{{.Id}}' web
docker ps --no-trunc --format '{{.ID}} {{.Names}}'
```

> 记规律比记命令重要：64 位是全量、12 位是短 ID、目录名用全量、命令行可简写。排障时对不上号，通常是拿短 ID 去 grep 全量目录名，用前缀匹配即可解决。

**速记**：**全量 64 位、短 12 位，目录用全量、命令可简写**。



#### Docker Desktop 的路径差异

**Docker Desktop 的日志位置**：引擎跑在一台托管 Linux 虚拟机内，/var/lib/docker/containers 这条路径存在于虚拟机里，macOS 与 Windows 宿主机的文件系统上并不存在。

- **宿主机看不到**：在 macOS 终端直接 ls 该路径不会得到有意义的结果，因为它不在宿主文件系统里。
- **替代入口**：常规做法是走 docker logs 与 docker exec 读日志，或把应用的日志目录挂载到宿主目录后再用宿主工具处理。
- **虚拟机内查看**：需要时可通过 Desktop 提供的虚拟机访问方式进入，或用特权调试容器共享宿主命名空间后查看，属非常规手段。
- **磁盘视角**：Desktop 的磁盘占用看设置里的磁盘镜像大小，日志增长会体现在这个镜像文件里，而不是宿主某个目录。
- **与 Engine 的差别**：服务器上用 Docker Engine 时该路径真实存在，排查磁盘写满必须按 Linux 路径处理。

```bash
# Desktop 上正确的做法是走 Docker 接口，而不是找宿主机路径
docker logs --tail 100 web
docker exec web ls -l /var/log
docker system df
```

> Desktop 与 Engine 的这一差异来自架构本身：Desktop 是一台虚拟机加图形界面，Engine 是直接在宿主上运行的守护进程。凡是依赖"宿主机文件系统路径"的排查思路，在 Desktop 上都要先翻译成 Docker 接口。

**速记**：**Desktop 的日志在虚拟机里，宿主机没有该路径，走 docker logs 与挂载**。



#### 用 inspect 查日志路径

**LogPath 字段**：docker inspect 输出的 LogPath 给出该容器日志文件在守护进程侧的绝对路径，是程序化定位日志文件的可靠来源。

- 取路径用 docker inspect -f 的 LogPath 字段，返回值为基于 data-root 与驱动的完整路径。
- 同时可用 HostConfig.LogConfig.Type 确认驱动，用其 Config 段确认 max-size 与 max-file 是否真的生效。
- 对远程转发型驱动，LogPath 可能为空或指向缓存文件，不能假定路径一定存在。
- 由于路径由守护进程给出，它比手工拼接更可靠，改过 data-root 的机器尤其明显。
- 批量场景可对多个容器循环取该字段，生成"容器到日志文件"的映射表供采集器使用。

```bash
docker inspect -f '{{.LogPath}}' web
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}' web
```

```text
/var/lib/docker/containers/3f9c2a.../3f9c2a...-json.log
json-file map[max-file:3 max-size:10m]
```

> 优先信 inspect 而不信记忆：路径、驱动、轮转参数三者都在同一次 inspect 输出里，写排查脚本时按字段取值即可，不必假设默认布局。

**速记**：**LogPath 给绝对路径，LogConfig 给驱动与轮转参数**。



### 阅读与过滤日志

#### docker logs 的选项组合

**docker logs**：读取容器主进程写到标准输出与标准错误的日志，选项在 容器生命周期与常用命令 一章已列出，此处只回顾组合形态与语义边界。

- --follow 或 -f：持续跟踪新日志，等价于 tail -f，配合 Ctrl+C 退出。
- --tail 或 -n：限制末尾行数，默认 all，负值与非整数会被视为 all。
- --since 与 --until：按时间范围过滤，支持相对时长（42m、3h）、Unix 时间戳与多种日期格式。
- --timestamps 或 -t：为每行加上 RFC3339Nano 时间戳，用于与事件流对齐。
- --details：额外显示日志驱动附带的属性，如创建时通过标签与环境变量注入的信息。
- 组合顺序不敏感，但 --since 与 --tail 同时存在时先按时间过滤再截取末尾行。

```bash
docker logs -f --tail 100 web
docker logs --since 42m --until 10m web
docker logs -t --since 2026-09-12T00:00:00 web
```

```text
2026-09-12T08:01:02.345678901Z 172.18.0.1 - - "GET / HTTP/1.1" 200
```

> --until 需要 API 1.35 及以上，配合 --follow 时表示"跟到该时刻为止"，适合截取某个时间窗内的日志再交由工具分析。

**速记**：**-f 跟、--tail 截、--since 与 --until 限窗、-t 加时间戳、--details 加属性**。



#### docker logs 的局限

**docker logs 的边界**：它只能读单个容器、只能读驱动支持的内容、时间与多容器对齐困难，也无法在服务端做内容过滤，因此不适合作为多服务排查的主力。

- **单容器视角**：一次只作用于一个容器，多服务联调要逐个执行，无法自动拼接。
- **驱动依赖**：远程驱动在未开缓存时读不到，容器内自写文件的日志也读不到。
- **无内容过滤**：没有按关键字、级别过滤的选项，只能取出后用 grep 一类的工具二次处理。
- **时间对齐难**：不加 -t 时行上不带时间戳，多个容器的时间线难以精确拼接。
- **不持久**：日志随容器与日志文件的生命周期存在，轮转过的旧内容受 max-file 限制可能已被删除。
- **无检索**：没有全文索引，历史日志的模糊查询只能靠本地 grep。

```bash
# 借助外部工具补救：先加时间戳再过滤
docker logs -t --since 1h web | grep --line-buffered ERROR | tail -50
```

> 局限的根因是 docker logs 读的是"这一个容器的这一份本地文件"。跨容器、跨主机、需要检索的场景属于日志平台的职责，不应指望命令行工具承担。

**速记**：**只一个容器、只认可读驱动、不能过滤、难对齐、不持久**。



#### compose logs 聚合多服务

**docker compose logs**：按 Compose 项目聚合各服务的日志输出，默认给每行加上服务名前缀，是多服务联调时查看日志的主入口。

- 默认只打印当前已有的日志，加 --follow 持续跟踪，行为与 docker logs 一致。
- 在服务名之后追加位置参数即可只看指定服务，如 docker compose logs web，也可一次列多个服务。
- --tail 限制每个服务末尾行数，--since 限定起始时间，二者可与 --follow 组合。
- --no-log-prefix 去掉行首的服务名前缀，输出更干净，便于直接喂给 grep 或 jq 一类工具。
- --no-color 关闭着色，--timestamps 为每行加时间戳，二者在写入文件或做时间对齐时常用。
- --index 指定服务副本的下标，多副本场景可只看某一个实例。

```bash
docker compose logs --follow --tail 100
docker compose logs --since 30m web api
docker compose logs --no-log-prefix --tail 200 web | grep ERROR
```

```text
web-1  | 172.18.0.1 - - "GET /health HTTP/1.1" 200
api-1  | level=info msg="request handled" path=/health
```

> 两个命令的分工要分清：临时看某一个容器用 docker logs，跟整套服务的启动顺序与互相调用用 docker compose logs。前者看细节，后者看全局，混用会浪费大量时间在逐容器切换上。

**速记**：**compose logs 按项目聚合、带服务名前缀、可点服务名过滤，联调用它**。



### 容器事件流

#### docker events 的用途与过滤

**docker events**：从守护进程订阅事件流，实时报告容器、镜像、网络与卷等对象发生的状态变化；命令全称 docker system events，docker events 是其别名。

- **过滤维度**：--filter type=container 限定对象类型，--filter event=die 限定事件名，--filter container=web 限定对象，三类可叠加。
- **容器事件名**：create、start、die、stop、kill、restart、pause、unpause、oom、health_status、destroy 等。
- **组合逻辑**：同一过滤器键写多次是逻辑或，不同过滤器键之间是逻辑与。
- **时间范围**：--since 与 --until 接受相对时长、Unix 时间戳与多种日期格式；不给 --since 时只显示新的或实时事件。
- **输出定制**：--format 支持 Go 模板与 json，便于接入脚本或流式写入文件。
- **历史限制**：事件不做持久化，命令只返回最近 256 条，更早的历史需要自行采集留存。

```bash
docker events --filter type=container --filter event=die
docker events --filter container=web --since 30m
docker events --format '{{.Time}} {{.Action}} {{.Actor.Attributes.name}}'
```

```text
2026-09-12T08:31:02.123456789+08:00 die web (exitCode=137)
```

> 事件是瞬时的广播，不订阅就错过。需要事后回溯时，应让一个长期运行的进程把 docker events 的输出按行落盘，形成可查询的事件日志。

**速记**：**docker events 订阅状态变化，type、event、container 三类过滤，同键或、异键且**。



#### 事件与日志的互补

**互补关系**：事件回答"何时发生了什么"，日志回答"为什么发生"，两者按时间戳对齐才能构成完整的时间线。

- **事件带元数据**：die 事件直接携带退出码，oom 事件标出内存超限，health_status 事件带健康值，这些是日志里未必有的结构化信息。
- **日志带上下文**：应用抛出的异常栈、请求路径、依赖地址只在日志里，事件不会记录。
- **时间对齐**：给日志加上时间戳（docker logs -t）再与事件的 Time 字段比对，即可把"发生了什么"与"为什么"对上。
- **历史能力相反**：日志可回溯——受轮转策略限制但通常保留数小时到数天；事件只要没订阅就永久丢失。
- **组合排查**：先用事件建立时间线，再针对每个时间点去取对应容器的日志，效率远高于通读日志。

```bash
# 建立时间线
docker events --filter container=api --since 1h --until 5m \
  --format '{{.Time}} {{.Action}} {{.Actor.Attributes.exitCode}}'

# 按时间点取日志
docker logs -t --since 2026-09-12T08:30:00 --until 2026-09-12T08:31:00 api
```

> 一个常见误区是只看日志。日志里满是堆栈却没有"容器在四十分钟内重启了十二次"这一事实，而事件流一句话就能给出结论，两者缺一不可。

**速记**：**事件给时间线与元数据，日志给原因与上下文，用时间戳对齐**。



#### 用事件定位重启循环

**重启循环的排查路径**：用事件流确认重启的节奏与退出码，用 inspect 确认累计次数与死因，用日志确认最后一次失败的原因，三步即可定位绝大多数崩溃循环。

1. 用 docker events 过滤该容器的 die、oom、restart 事件，观察重启的时间间隔是否有规律。
2. 用 docker inspect 取 RestartCount 与 State 段的 ExitCode、OOMKilled，判断是正常退出、被信号终止还是被内存杀手击杀。
3. 用 docker logs --tail 200 看最后一次失败前的输出，多数情况下原因就在最后几行。
4. 若退出码为 137 且 OOMKilled 为真，转向内存限制排查，参见 容器资源限制与运行时约束 一章。
5. 若退出码固定且间隔规律，检查启动依赖是否可达、健康检查是否过严、启动脚本是否因缺少配置而立即退出。

```bash
docker events --filter container=api --filter event=die --filter event=oom
docker inspect -f '{{.RestartCount}} {{.State.ExitCode}} {{.State.OOMKilled}}' api
docker logs --tail 200 api
```

```text
12 137 true
```

> 有规律的重启（如固定每 30 秒一次）通常指向探针连续失败或启动超时；无规律且伴随内存上升的重启指向内存超限；启动即退且退出码为 127 则多为入口命令或可执行文件路径不对。

**速记**：**事件看节奏与退出码、inspect 看次数与死因、logs 看最后遗言**。



### 健康检查作为可用性信号

#### 健康检查的观测面

**健康检查的观测面**：HEALTHCHECK 与 Compose 的 healthcheck 让守护进程按周期在容器内执行一条命令，用退出码判定容器是否健康；语法已在 Dockerfile 语法详解 与 Docker Compose 进阶与实战 两章讲过，这里关注它产生的可观测信号。

- **三个状态**：starting 表示宽限期内尚未得出结论，healthy 表示最近一次检查成功，unhealthy 表示连续失败达到阈值。
- **状态来源**：检查命令退出码为 0 视为成功，非 0 视为失败，连续失败次数由 retries 决定。
- **观测出口**：docker ps 的 STATUS 列、docker inspect 的 State.Health 段、docker events 的 health_status 事件，三处反映同一状态。
- **与存活判定的差别**：健康检查反映服务可用性，容器存活反映进程存在，两者不是一回事。
- **不带来的动作**：纯 Docker 不会因 unhealthy 自动重启容器，自动替换需要配合编排平台或外部监控。

```bash
docker inspect -f '{{.State.Health.Status}}' web
docker ps --filter health=unhealthy
```

> 默认宽限期与间隔均可调，排障时若看到长时间处于 starting，应先确认 start-period 是否设得过短，而不是立刻判定服务有问题。

**速记**：**starting 待定、healthy 正常、unhealthy 连续失败；语法的账记在第 5、11 章**。



#### docker ps 的 STATUS 列如何显示健康状态

**STATUS 列的健康后缀**：容器定义了健康检查时，docker ps 的 STATUS 在 Up 时长之后追加 (healthy)、(unhealthy) 或 (health: starting)，一眼即可判断服务可用性。

- 未定义健康检查的容器只显示 Up 加时长，没有后缀，此时"Up"只代表进程在。
- 处于宽限期的容器显示 health: starting，尚未得出健康结论。
- 检查失败的容器显示 unhealthy，但进程通常仍在运行，这正是健康检查的价值所在。
- --filter health=unhealthy 可批量筛出不健康的容器，适合接入巡检脚本。
- 已退出的容器显示 Exited 加退出码，健康信息不再有意义。

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}'
docker ps --filter health=unhealthy --format '{{.Names}} {{.Status}}'
```

```text
NAMES   STATUS
web     Up 3 minutes (healthy)
api     Up 12 minutes (unhealthy)
```

> 对照第三章的 STATUS 解析：Up 看时长、Exited (码) 看结果、Restarting (码) 看崩溃循环，加上本篇的健康后缀，才构成完整的可读状态。

**速记**：**有健康检查时 Up 之后带 healthy、unhealthy、health: starting 三选一**。



#### 健康状态变化进入事件流

**health_status 事件**：容器健康状态每次发生变化，守护进程都会在事件流里产生一条 health_status 事件，事件携带当前健康值，可作为告警的触发源。

- 从 starting 变为 healthy 的首次通过也会产生事件，可用于确认服务真正就绪。
- 从 healthy 变为 unhealthy 同样产生事件，是"服务已不可用"最直接的信号。
- 用 --filter event=health_status 与 --filter container=名字 精确订阅。
- --format 可提取事件时间与健康值，写入监控系统或告警通道。
- 事件与 docker ps 的显示互为印证：ps 看当前，事件看变化过程。

```bash
docker events --filter event=health_status --format '{{.Time}} {{.Action}} {{.Actor.Attributes.name}}'
```

```text
2026-09-12T08:35:10.000000000+08:00 health_status: unhealthy web
```

> 把告警规则挂在 health_status 事件上，比轮询 docker ps 更及时；但事件不持久，接入告警前需要一个常驻订阅进程保证不丢。

**速记**：**状态一变就出 health_status 事件，starting 到 healthy 也算一次**。



#### 进程活着但服务已死

**进程活着但服务已死**：指容器内主进程没有退出、容器状态仍是 Up，但服务已经无法正常处理请求的一类故障，只有健康检查能把它暴露出来。

- **典型成因**：线程死锁、连接池耗尽、依赖的数据库或缓存不可达、GC 长时间停顿、事件循环被同步操作阻塞。
- **失效信号**：接口超时或返回错误率上升，而 docker ps 显示 Up、RestartCount 保持为零。
- **暴露手段**：健康检查连续失败转为 unhealthy，并产生 health_status 事件；没有健康检查则只能等外部监控发现。
- **处置顺序**：先 exec 进容器做一次本机自测，再查日志中的依赖报错，最后确认依赖服务本身是否正常。
- **自动恢复**：纯 Docker 不会因 unhealthy 重启容器，需要编排平台依据健康状态替换实例，或由外部脚本调用 restart。

```bash
# 健康检查失败时的自测
docker exec web wget -qO- http://localhost:8080/health
docker exec web sh -c 'wget -T 3 -qO- http://db:3306 || echo "dep unreachable"'
docker logs --tail 100 web
```

> [!IMPORTANT]
> **重要内容**：健康检查命令必须真正代表服务可用性，探一个业务端点或依赖连通性，而不是只探 TCP 端口。只探端口时，进程在、端口开、健康检查就会一直是 healthy，而应用层早已不可用，等于白设。

**速记**：**Up 不等于可用，进程在而服务死只有健康检查能发现；探针要探业务而非端口**。



### 运行时指标观察

#### docker stats 与 --format

**docker stats 的定位**：流式显示运行中容器的 CPU、内存、网络与块设备 IO 用量，是运行时资源观察的第一入口；各项列含义与统计口径已在 容器资源限制与运行时约束 一章展开，此处只作为监控链路的采集点。

- 默认对所有运行中容器持续刷新，加 --no-stream 只取一次快照，适合脚本按周期采集。
- --format 用 Go 模板抽取字段，可直接生成 CSV 或 JSON 供监控系统消费。
- --all 把已停止的容器一并列出，用于观察退出前的资源轨迹。
- 观察重点是趋势而非瞬时值：内存随时间单调上升、CPU 周期性触顶，这些才是有意义的信号。
- 命令行观察只适合单机与临时排查，长期指标应交给采集器与时间序列数据库。

```bash
docker stats --no-stream
docker stats --no-stream --format '{{.Name}} {{.CPUPerc}} {{.MemUsage}}'
docker stats --no-stream --format json
```

```text
web 0.02% 12.3MiB / 7.6GiB
api 45.10% 320.5MiB / 1GiB
```

> 与第十三章的衔接：那里讲节流与上限的机制，这里讲怎么把数字采出来。stats 给出的是瞬时采样，判断是否受限要看 CPU 节流与内存超限这些衍生指标，而不是单看使用率。

**速记**：**stats 采瞬时用量，--no-stream 取快照，--format 供脚本消费；细节见第 13 章**。



#### inspect 的 State 与 RestartCount

**inspect 的运行时字段**：docker inspect 输出的 State 段描述容器当前运行状态，RestartCount 记录累计重启次数，二者是判断容器是否稳定运行的主要依据。

- State.Status：当前状态，取值 created、running、paused、restarting、exited、dead。
- State.ExitCode：主进程退出码，容器在运行时通常为零，容器已退出时代表真实死因。
- State.OOMKilled：布尔值，为真表示曾被内核因内存超限杀死。
- State.Health.Status：健康检查结论，未定义健康检查时该字段不存在。
- State.StartedAt 与 FinishedAt：最近一次启动与结束的时刻，用于计算存活时长与重启间隔。
- RestartCount：该容器自创建以来被重启策略拉起的累计次数，是判断稳定性最直观的数字。

```bash
docker inspect -f '{{.State.Status}} {{.State.ExitCode}} {{.State.OOMKilled}}' api
docker inspect -f '{{.RestartCount}} {{.State.StartedAt}} {{.State.FinishedAt}}' api
```

```json
{
  "State": {
    "Status": "running",
    "ExitCode": 0,
    "OOMKilled": false,
    "Health": { "Status": "healthy" }
  },
  "RestartCount": 0
}
```

> RestartCount 只在同一容器对象上累加，容器被删除重建后从零开始。看到 RestartCount 为零就断定服务稳定前，先确认容器确实老到足以积累出重启次数。

**速记**：**State 看当下与死因，RestartCount 看累计重启，二者共同判断稳定性**。



#### 已退出容器的取证三件套

**取证三件套**：容器退出后按 inspect 看死因、logs 看遗言、diff 看现场改动 的顺序收集证据，是事后复盘的标准动作。

- **inspect 看死因**：取 State.ExitCode 与 OOMKilled，先分清是被信号杀死、被内存杀死还是应用主动退出。
- **logs 看遗言**：取末尾若干行输出，异常栈、依赖连接失败等信息通常出现在最后几行。
- **diff 看现场**：列出可写层相对镜像层的文件改动，判断进程是否写出了预期外的文件或写了日志文件。
- **补充手段**：需要保留文件现场时用 docker cp 把关键文件导出到宿主机，再慢慢分析。
- **重建前提**：证据收集完再决定是重建还是删除，顺序颠倒会丢掉唯一现场。

```bash
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.FinishedAt}}' old-api
docker logs --tail 200 old-api
docker diff old-api
docker cp old-api:/app/crash.dump ./crash.dump
```

```text
C /app/cache
A /app/crash.dump
```

> [!CAUTION]
> **注意内容**：若容器创建时带了 --rm，退出即自动删除，inspect、logs、diff 三件套一起失效。排查期间不要加 --rm，等故障定位完成后再手动清理。

**速记**：**先 inspect 看死因、再 logs 看遗言、后 diff 看现场，证据收完再重建**。



### 监控体系接入

#### cAdvisor 加 Prometheus 加 Grafana 的分工

**三件套分工**：cAdvisor 负责采集容器与宿主机的资源指标，Prometheus 负责按周期拉取并存储时间序列，Grafana 负责查询与可视化，是单机自建容器监控的经典组合。

- **cAdvisor**：以容器为单位暴露 CPU、内存、文件系统与网络指标，直接读取内核 cgroup 数据，自身也以容器方式部署。
- **Prometheus**：按 scrape 配置周期拉取各 exporter 暴露的指标，存为带标签的时间序列，并提供查询语言与告警规则。
- **Grafana**：对接 Prometheus 作为数据源，用面板与看板把指标画成趋势图，并配置阈值告警。
- **关系**：cAdvisor 产出、Prometheus 存储、Grafana 呈现，缺一环链路即断；日志与指标是两条独立通道，指标看趋势，日志看原因。
- **取舍**：自建可控且免费，代价是要自行维护存储、保留期与高可用，规模变大后运维成本显著上升。

```yaml
# prometheus.yml 片段：抓取 cAdvisor
scrape_configs:
  - job_name: cadvisor
    static_configs:
      - targets: ['cadvisor:8080']
```

> 指标是采样值，只能告诉你"哪里不对"，不能告诉你"为什么不对"。内存曲线陡升是采样结论，真正的原因要看那一刻的日志与事件，二者必须配套使用。

**速记**：**cAdvisor 采集、Prometheus 存储、Grafana 展示；指标看趋势、日志看原因**。



#### dockerd 自身的指标端点

**metrics-addr**：dockerd 的 metrics-addr 选项指定指标 API 的监听地址，开启后在 /metrics 路径以 Prometheus 格式暴露守护进程自身的指标；该选项默认不启用。

- 配置方式是在 daemon.json 里写 metrics-addr，或用命令行 --metrics-addr 传给 dockerd，两者只能选其一。
- 官方示例使用 127.0.0.1:9323，9323 是 Docker metrics 约定的默认端口，选它是为了避开其他 exporter 常用端口。
- 端点返回 Prometheus 文本格式，把该地址加入 Prometheus 的 scrape 配置即可采集。
- 暴露的是守护进程与引擎层面的指标，如容器数量、镜像操作、API 请求等，与 cAdvisor 的每容器资源指标互补。
- 监听地址建议绑定到回环或内网，避免把内部指标暴露到公网。

```json
{
  "metrics-addr": "127.0.0.1:9323"
}
```

```bash
# 开启后确认端点可访问
curl -s http://127.0.0.1:9323/metrics | head
```

> metrics-addr 默认不开，这是它最容易被忽略的一点。没有显式配置时访问 /metrics 会直接连接失败，而不是返回空结果。

**速记**：**metrics-addr 默认关，开了在 /metrics 出 Prometheus 格式，官方惯例端口 9323**。



#### Docker Desktop 的资源视图

**Docker Desktop 的资源视图**：Desktop 的图形界面内置容器与引擎的资源曲线、日志查看器与一键进入容器的能力，是 Desktop 专有的观测手段。

- **容器视图**：展示每个容器的 CPU、内存、网络与磁盘曲线，以及运行的进程列表。
- **日志视图**：直接在界面上看容器输出并支持搜索，等价于 docker logs 的图形化版本。
- **进入容器**：提供终端入口，等价于 docker exec，用于手工排查。
- **资源设置**：在设置里调整虚拟机可用的 CPU、内存与磁盘，日志增长占用的是虚拟机磁盘镜像。
- **可用范围**：这些能力只在 Docker Desktop 上存在，服务器上用 Docker Engine 时没有该界面，观测要靠命令行、自建监控或按需开启的 metrics 端点。

```bash
# 纯 Engine 环境下的等价观测手段
docker stats --no-stream
docker logs -f --tail 100 web
docker exec -it web sh
```

> 本系列第 1 章已说明 Desktop 与 Engine 的产品差异，监控这一面同样适用：图形化便利属于 Desktop，服务器上要的是可脚本化、可集中化的观测链路。

**速记**：**Desktop 有图形资源视图与日志查看器，纯 Engine 环境只能命令行加自建监控**。



#### 日志集中化的取舍

**日志集中化**：把分散在各容器与各主机上的日志采集后送入统一后端，由后端提供检索、留存与告警；常见组合是用 Fluent Bit 采集，后端二选一为 Loki 或 Elasticsearch。

- **Fluent Bit 的角色**：轻量采集器，从日志驱动或日志文件读取记录，按标签与字段处理后转发到后端。
- **Loki 的特点**：以标签索引为主，只对标签建索引、正文压缩存储，资源开销小、成本低，适合以按服务与时间查为主的场景。
- **Elasticsearch 的特点**：提供全文索引，支持复杂的字段检索与聚合分析，查询能力强但存储与内存开销显著更大。
- **托管服务**：云厂商的日志服务省去运维，按写入量与留存期计费，规模大时费用需要提前估算。
- **取舍维度**：检索需求有多复杂、留存期多长、合规是否要求本地存放、团队能承担多少运维，四项定完再选组件。

```conf
# Fluent Bit 输出到 Loki 的示意片段
[OUTPUT]
    Name        loki
    Match       *
    Host        loki
    Port        3100
    Labels      job=container
```

> 顺序别搞反：先确认检索需求与留存期，再选后端，最后才配采集器。反过来先选定组件再倒推需求，往往得到一套能力过剩或不足的日志系统。

**速记**：**Fluent Bit 采集，Loki 省成本按标签查，Elasticsearch 强全文但重，托管省运维按量付费**。



### 从日志与指标到定位

#### 容器反复重启

**反复重启的排查路径**：按"先看计数、再看死因、后看遗言"的顺序推进，三步之内通常能给出结论。

1. docker ps 看是否处于 Restarting，或 docker ps -a 看 STATUS 中的重启迹象。
2. docker inspect 取 RestartCount、State.ExitCode、State.OOMKilled，判断重启的频率与性质。
3. docker events 过滤 die 与 oom，观察两次重启之间的时间间隔是否规律。
4. docker logs --tail 200 看最后一次退出前的输出，异常栈与依赖错误多在此处。
5. 依据结论分流：内存超限见第 13 章的资源限制；依赖不可达查网络与依赖服务；启动即退查入口命令与配置注入。

```bash
docker ps -a --filter name=api
docker inspect -f '{{.RestartCount}} {{.State.ExitCode}} {{.State.OOMKilled}}' api
docker events --filter container=api --filter event=die --since 30m
docker logs --tail 200 api
```

> 退出码 137 要分两种：OOMKilled 为真说明内存超限被内核杀死，为假则多是 docker stop 超时后补发的 SIGKILL。同样是 137，处置方向完全不同。

**速记**：**ps 看状态、inspect 看计数与死因、events 看节奏、logs 看遗言**。



#### 服务无响应但进程在

**无响应但进程在的排查路径**：这类故障容器状态正常、重启次数为零，排查要从健康状态与应用层的自测入手，而不是继续盯着容器状态看。

1. docker ps 看 STATUS 是否带 unhealthy 或 health: starting，用 --filter health=unhealthy 批量筛查。
2. docker inspect 取 State.Health 的最近一次输出，健康检查命令本身会打印失败原因。
3. docker exec 进容器做本机自测，直接请求健康端点，区分是应用挂了还是网络不通。
4. 起一个同网络的一次性调试容器，测 DNS 解析与依赖端口连通性，参见 自定义网络与容器互联 一章。
5. docker logs 找最近的错误与超时，结合依赖服务的状态确定瓶颈在哪一层。

```bash
docker ps --filter health=unhealthy
docker inspect -f '{{json .State.Health}}' api
docker exec api wget -qO- --timeout=3 http://localhost:8080/health
docker run --rm --network app-net nicolaka/netshoot nc -vz db 3306
```

> 若容器没有定义健康检查，这一整条路径的第一步就无从下手。为长驻服务补上健康检查，是把这类故障从"靠用户投诉发现"提前到"靠系统自己发现"的最低成本手段。

**速记**：**先看健康状态、再看检查输出、exec 自测、同网络测依赖、最后翻日志**。



#### 磁盘被日志写满

**磁盘写满的排查路径**：先确认是日志而非数据把盘占满，再定位到具体容器，最后补轮转与修应用，避免误删数据卷。

1. df -h 看哪个分区满、还剩多少，确认受影响的范围。
2. du -sh 逐层下钻到 /var/lib/docker，再进 containers 目录排序，找出最大的几个容器目录。
3. 由目录名里的容器 ID 反查容器，确认它是谁、在写什么。
4. docker logs --tail 200 看是否有异常刷屏，判断是应用缺陷还是输出本就如此。
5. 应急清空该日志文件释放空间，注意不要动容器目录里的配置文件，也不要动数据卷。
6. 补上 max-size 与 max-file 后重建容器，并检查应用是否在错误路径下无限重试。

```bash
df -h
sudo du -sh /var/lib/docker
sudo du -sh /var/lib/docker/containers/* | sort -h | tail -5
docker logs --tail 200 <容器名>
```

> [!WARNING]
> **警告内容**：容器化运维里，磁盘写满最常见的原因不是业务数据增长，而是未设轮转的日志无限增长。上线任何长驻容器前先把 max-size 与 max-file 写进 daemon.json，比事后清理省事得多。

**速记**：**df 定分区、du 定容器、logs 定原因、清空应急、轮转防复发**。



#### 性能劣化但资源未打满

**资源未打满的性能劣化**：CPU 与内存使用率看起来都不高，但服务响应变慢，这类问题要从限制、等待与下游三个方向找原因，而不是继续盯使用率。

1. docker stats 看趋势，区分是缓慢恶化还是某个时刻的突变。
2. docker inspect 与运行时约束结合，确认是否配置了 CPU 配额与内存上限，配额触顶表现为节流而非使用率打满。
3. 用 docker events 与 docker ps 确认有无重启、OOM 或健康状态变化同时发生。
4. 检查块设备 IO：磁盘 IO 饱和时进程会长时间处于等待，CPU 使用率反而偏低。
5. 排查下游依赖与网络，数据库慢查询、连接池耗尽、DNS 解析超时都会表现为本容器"没干什么但很慢"。
6. 回到应用日志看延迟分布与超时记录，把指标异常与日志中的具体请求对应起来。

```bash
docker stats --no-stream
docker inspect -f '{{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}' api
docker inspect -f '{{.State.Health.Status}}' api
docker logs -t --since 30m api | grep -i -E 'timeout|slow|retry'
```

> 使用率未打满不等于没有瓶颈：CPU 配额会让进程被节流、IO 等待会让进程让出 CPU、下游变慢会让本进程阻塞在网络上。这三类原因都不会推高本容器的 CPU 使用率，只看 stats 会得出"资源充足"的错误结论。

**速记**：**未打满也要查配额节流、IO 等待、下游依赖，使用率不是唯一指标**。



### 生产日志清单

#### 应用侧清单

**应用侧清单**：应用只负责把结构良好的事件流写到标准输出与标准错误，其余交给运行环境，这是所有后续观测能力的前提。

- **写标准流**：日志一律走 stdout 与 stderr，不写容器内文件，也不在应用内做轮转。
- **结构化输出**：以 JSON 等机器可解析的格式逐行输出，字段稳定，便于平台按字段检索与聚合。
- **统一时间**：时间戳用 UTC 并符合标准格式，由运行时或应用统一补齐，避免多主机时区混乱。
- **请求关联**：为每个请求生成请求 ID 或追踪 ID，并在该请求产生的所有日志里带上，串起跨服务调用链。
- **级别规范**：明确 debug、info、warn、error 的使用边界，生产默认不输出 debug 级别。
- **错误附上下文**：错误日志包含出错环节、关键参数与依赖地址，但不包含密码、令牌等敏感内容。
- 启动与退出也应留下日志，容器启动顺序与退出原因往往比运行中日志更能解释问题。

```json
{"time":"2026-09-12T08:30:01Z","level":"error","requestId":"a1b2c3","msg":"db query failed","host":"mysql:3306","err":"connection refused"}
```

> [!IMPORTANT]
> **重要内容**：日志里不要打印密码、令牌、身份证号与完整银行卡号等敏感信息。日志会被集中采集、长期留存并被多人检索，一旦写入就等于扩散，事后清理成本极高。

**速记**：**写标准流、结构化、UTC 时间、带请求 ID、级别规范、不打印敏感信息**。



#### 运行时侧清单

**运行时侧清单**：由 Docker 守护进程与容器配置承担的日志治理项，决定日志写到哪里、能留多久、会不会撑爆磁盘。

- **驱动选择**：本地排障用 json-file 或 local，需要集中检索则本地落盘加采集器，慎用默认阻塞的远程驱动。
- **轮转参数**：明确设置 max-size 与 max-file，并在 daemon.json 中设为全局默认，避免个别容器漏配。
- **保留期限**：依据排障与合规要求设定保留时长，落在磁盘容量可承受的范围内。
- **容量规划**：为 data-root 所在分区留出余量，把日志总量上限乘以容器数量纳入容量估算。
- **写入安全**：远程驱动评估非阻塞模式与缓冲区，避免日志后端故障拖垮业务。
- **配置生效**：轮转参数改动只对新容器生效，需重建既有容器才能真正落地。
- **健康检查**：为所有长驻服务配置能反映业务可用性的健康检查，让不可用状态进入事件流。

```bash
# 核对实际生效的驱动与轮转参数
docker info --format '{{.LoggingDriver}}'
docker inspect -f '{{.HostConfig.LogConfig}}' web
sudo du -sh /var/lib/docker/containers
```

> 运行时侧的绝大多数问题都可以归结为一句话：日志的去向与上限没有被显式配置。默认值不是为生产准备的，把驱动与轮转写进 daemon.json 是最小必要的动作。

**速记**：**驱动、轮转、留存、容量、写入安全、健康检查，六项都要显式配**。



#### 平台侧清单

**平台侧清单**：由监控与日志平台承担的治理项，回答"从哪里看、看什么、什么时候报警"。

- **集中收集**：把各主机各容器的日志采集到统一后端，保证多副本多主机场景下有单一检索入口。
- **检索与看板**：按服务、级别、请求 ID、时间范围检索，并为关键服务准备固定看板。
- **告警挂点**：容器重启次数在一段时间内超过阈值、出现 health_status 转为 unhealthy、发生 oom 事件、主机磁盘使用率接近上限、错误日志速率突增。
- **留存策略**：按日志级别与业务重要性分层留存，热数据短期可查，冷数据归档保存。
- **合规要求**：涉及敏感数据的日志需在采集环节脱敏，并遵守留存地域与期限的合规约束。
- **值班闭环**：告警要有明确的处置入口与责任人，否则看板再全也只是一面墙。

```text
建议挂在告警上的信号：
- 容器 5 分钟内重启次数大于 3
- health_status 变为 unhealthy 持续超过 2 分钟
- 出现 oom 事件
- 主机根分区或 data-root 分区使用率超过 85%
- error 级别日志速率显著高于基线
```

> 告警规则要少而准。把每一条 warn 日志都做成告警，结果只会是告警疲劳，真正重要的信号被淹没在噪声里。

**速记**：**集中收集、可检索、告警挂在重启与健康与磁盘与错误率上、留存分层**。



#### 一份可照抄的配置

**可直接采用的配置**：守护进程侧用 daemon.json 设全局驱动与轮转，应用侧用 Compose 的 logging 段按服务覆盖，两层配合即可覆盖绝大多数生产场景。

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "5",
    "compress": "true"
  },
  "metrics-addr": "127.0.0.1:9323"
}
```

```yaml
# compose.yaml 片段：按服务覆盖日志驱动与轮转
services:
  api:
    image: myapp:1.0
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 20s
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "3"

  worker:
    image: myworker:1.0
    logging:
      driver: local
      options:
        max-size: "20m"
        max-file: "5"
```

- daemon.json 的 log-opts 决定所有新建容器的默认行为，是兜底的第一层。
- Compose 的 logging 段按服务覆盖，options 的键名与 --log-opt 一致，max-size 与 max-file 在此处按普通字符串书写即可。
- 健康检查与日志配置放在同一个服务定义里，便于一起演进。
- 改动后需重建容器才会生效，用 docker compose up -d 会对配置变化的服务自动重建。
- 验证方式仍是 docker inspect 看 HostConfig.LogConfig 的实际值，以及 du 看日志目录是否受控。

```bash
# 重建并核对
docker compose up -d
docker inspect -f '{{.HostConfig.LogConfig}}' $(docker compose ps -q api)
sudo du -sh /var/lib/docker/containers
```

> [!TIP]
> **建议内容**：把上面的 daemon.json 与 logging 段作为新环境的初始化模板，在团队内固定下来。日志治理的成本主要来自某台机器某几个容器漏配，统一的默认值加上少量例外覆盖，比逐容器检查可靠得多。

**速记**：**daemon.json 兜全局轮转与指标端点，Compose 的 logging 段按服务覆盖，改完必须重建**。
