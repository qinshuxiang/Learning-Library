## 集群 Cluster

**集群 Cluster**：是 Redis 官方自 3.0 起提供的**去中心化分片集群**方案——数据分片与高可用一体：16384 个哈希槽分布到多个主节点以突破单机容量与写入上限，每个主节点可挂从节点，主节点故障后由数据节点自行协商完成故障转移，全程不依赖哨兵或代理层等任何外部组件。

- 本章先讲分片的骨架：哈希槽与键到槽的映射、16384 这个数字的由来、hash tag 强制多键同槽。
- 再讲节点如何互通：CLUSTER MEET 握手、gossip 协议与集群总线上的五类消息。
- 接着讲客户端如何找到数据：MOVED 与 ASK 重定向、smart client 与 CLUSTER SLOTS、CLUSTER SHARDS。
- 然后讲故障自治：PFAIL 到 FAIL 的两级检测、从节点基于纪元的选举、部分槽不可用时的行为。
- 最后讲使用边界与动手实践：集群模式的限制、常用集群命令、三主三从的最小集群搭建。
- 与前两章的关系：主从复制（详见第 20 章）解决冗余与读扩展，哨兵（详见第 21 章）解决自动换主，本章的 Cluster 把**容量分片与故障转移**一并解决，是横向扩展的终极形态。

```text
本章考点地图：

分片骨架：16384 哈希槽 ─ CRC16 取模 ─ 16384 的由来 ─ hash tag
节点通信：CLUSTER MEET ─ gossip 五类消息 ─ 集群总线
数据路由：MOVED ─ ASK ─ smart client ─ CLUSTER SLOTS / SHARDS
故障自治：PFAIL → FAIL ─ 从节点选举与投票 ─ full-coverage
边界与实践：使用限制 ─ CLUSTER 命令族 ─ 最小集群搭建
```

### 集群的认识

#### 集群是数据分片与高可用的一体化方案

**集群 Cluster**：是 Redis 3.0 正式引入的去中心化分片集群——把全部键空间切成 16384 个哈希槽分给多个主节点，容量与写入压力按槽分摊；每个主节点可配置从节点，主节点故障后由集群节点自行选举晋升，高可用内建而非外挂。

- 问题的起点：主从复制（详见第 20 章）只解决数据冗余与读扩展，哨兵（详见第 21 章）只解决自动换主，二者都不解决**容量**——数据量超出单机内存、写吞吐超出单机上限时，单分片架构无论加多少从库都无济于事。
- 去中心化的含义：没有中央代理、没有独立的管理进程，每个节点都维护一份集群状态，节点之间通过专用的集群总线直接通信；客户端直连任一节点，靠重定向协议找到数据所在节点。
- 高可用的含义：每个主节点配一个或多个从节点，主节点被判定下线后，其从节点通过集群内部的选举机制晋升为新主，过程与哨兵类似但完全内建在数据节点里，不再需要部署哨兵进程。
- 时间起点：Redis 3.0（2015 年正式发布）起进入生产可用状态，此前的测试阶段不建议使用；版本演进的全貌见第 32 章。
- 规模下限：官方规格要求至少三个主节点，推荐三主三从共六个节点起步；主节点数决定故障转移所需的多数派，下限的数学原因见本章故障检测部分。
- 节点标识：每个节点启动时生成 40 位十六进制的 Node ID 终身不变，集群内一切互认都以 Node ID 为准，IP 与端口只是随时可变的联系方式。
- 架构位置：Cluster 与哨兵互斥——同一批数据节点要么纳入 Cluster，要么由哨兵管理；Cluster 内部的故障转移由节点自身协商完成，不依赖也不支持哨兵进程。
- 集群总线：每个节点在客户端端口之外额外监听一个总线端口（传统上为客户端端口加 10000），节点间的握手、探活、状态交换全部走总线；容器与防火墙环境漏放行总线端口是组建失败的常见原因。

一次三主三从集群的槽分布示意：

```text
节点 A（主）  槽 0     – 5460     从节点 A'
节点 B（主）  槽 5461  – 10922    从节点 B'
节点 C（主）  槽 10923 – 16383    从节点 C'
（16384 个槽在三个主节点间均分，每个主节点各挂一个从节点）
```

> 辨析：哨兵与 Cluster 都提供高可用，但职责层次不同——**哨兵在单分片上做故障转移，Cluster 在多分片上同时做数据分布与故障转移**；部署了 Cluster 就不需要哨兵，因为换主这件事已由数据节点自身完成。数据量单机放得下、写压力不大时，哨兵方案结构更简单、功能限制更少，选型对比见本章末尾的使用限制部分。

**速记**：Cluster ＝ **分片加高可用一体**，去中心化、无哨兵、无代理。



#### 哈希槽与键到槽的映射

**哈希槽（hash slot）**：Redis Cluster 把键空间划分为固定的 **16384 个槽**，每个键按 CRC16 算法映射到唯一槽，每个主节点负责其中一段槽——键不直接绑定节点，而是通过槽间接归属。

- 映射公式：槽号 = CRC16(key) mod 16384；CRC16 采用 CCITT 变体，对 16384 取模后分布均匀，16384 是 2 的 14 次方，取模计算成本低。
- 两级映射：键到槽由算法决定、永不改变；槽到节点由集群分配、可随扩缩容调整——把不可变的哈希与可变的分配解耦，是增删节点不停机的根本原因。
- 不是一致性哈希：官方文档明确 Redis Cluster 不使用一致性哈希；一致性哈希用环形哈希空间加虚拟节点，key 的归属随节点集合变化而隐式漂移，Redis 用固定槽数做中间层，归属精确可控。
- 间接层的收益：扩缩容只需把槽在节点之间搬移，键到槽的映射永不变，迁移粒度可控、可分批、可暂停，每条数据归谁一目了然。
- 槽是最小迁移单位：数据迁移以槽为单位进行，把槽连同其上的键从源节点搬往目标节点，全程不停机；迁移中间态的处理见本章 ASK 重定向部分。
- 集群健康定义：16384 个槽全部有主节点负责时 cluster_state 才为 ok，任何一个槽无人负责集群即进入残缺状态，具体行为由 cluster-require-full-coverage 控制。
- 查询入口：CLUSTER KEYSLOT key 返回任意键所在的槽号，排查键落在哪个节点时首先执行。
- 键的定位路径：算槽号 → 查哪个节点负责该槽 → 请求直达该节点；这一步可以由客户端自己做（smart client），也可以由服务端重定向代劳。

键到节点的完整定位路径示意：

```text
键 {user1000}.follow
  → CRC16(user1000) mod 16384 = 槽号
  → 查槽表：槽号落在节点 A 负责的区间 → 节点 A
  → 请求发往节点 A（或被 MOVED 重定向到 A）
```

> 辨析：固定 16384 槽的设计让谁的槽成为集群状态中最核心的信息——心跳里广播槽位图、重定向里携带槽号、选举里槽随新主整体转移，全部围绕这份槽表展开；这也是为什么槽数必须固定，而不是像一致性哈希那样动态扩环。一层间接换来**可控迁移与精确归属**，这是工程取舍而非算法优劣。

**速记**：**键 → CRC16 → mod 16384 → 槽 → 节点**，键跟槽走、槽跟节点走，槽是分片与迁移的最小单位。



#### 为什么是 16384 个槽而不是 65536

**16384 的由来**：槽数是作者 antirez 权衡心跳包体积与集群规模上限后拍定的值，核心理由是**够用且省带宽**，而非 65536 有任何技术障碍。

- 理由一 心跳包体积：gossip 心跳消息必须携带本节点负责哪些槽的位图；16384 个槽的位图占 16384 除以 8 等于 2048 字节（2KB），65536 个槽则要 8KB——心跳是去中心化集群每秒都在发的常态流量，包体翻四倍意味着白白消耗四倍的带宽。
- 理由二 集群规模上限：antirez 的判断是 Redis Cluster 实际难以扩展到约 1000 个主节点以上——共识协商与心跳成本会先行触顶；16384 个槽平摊给 1000 个主节点，每个节点约 16 个槽，粒度足够。
- 规模再大得不偿失：节点数超过千级后，gossip 消息的收敛成本与状态表体积显著上升，槽再多只加重心跳负担，更细的粒度却没有消费方。
- 数学事实：CRC16 输出 16 位，理论取值 65536 个，对 16384 取模在分布上没有问题；16384 是在分布均匀、迁移粒度与消息体积之间选的平衡点。
- 结论：**65536 没有收益，16384 没有瓶颈**；槽数写死在协议实现中，不可配置。

```text
16384 个槽 → 位图 16384 bit → 16384 ÷ 8 = 2048 字节 = 2KB（每条心跳头部）
65536 个槽 → 位图 65536 bit → 65536 ÷ 8 = 8192 字节 = 8KB（四倍带宽开销）
1000 个主节点 → 16384 ÷ 1000 ≈ 16 槽/节点（粒度足够，无需更多槽）
```

> [!NOTE]
> **提醒内容**：antirez 对 16384 的解释出自 GitHub issue 的著名答复，属于设计权衡而非硬性数学约束；理解时抓两条主线——心跳里要放槽位图、集群规模设计上限约一千主——即可完整还原这个数字的来历，答题时能复述位图字节数的推导过程即可。

**速记**：**槽位图 2KB 随心跳满天飞，千主之内够用**，65536 纯交带宽税，16384 够用就好。



#### hash tag 强制多键同槽

**hash tag**：是键名中大括号的特殊约定——当键名包含大括号时，Redis 只对**大括号内的子串**计算 CRC16，从而让一组键强制落入同一个槽。

- 计算规则：键名含大括号时只取括号内子串参与哈希；不含时对全键计算，两种情况结果可能完全不同。例如 {user1000}.follow 与 {user1000}.fans 都按 user1000 计算，必然同槽。
- 空标签边界：若花括号内是空字符串，Redis 会退回对整个键计算槽，这是官方文档明确的边界行为。
- 存在的原因：多键命令、事务、Lua 脚本要求**所有涉及的键在同一槽**（详见本章使用限制部分），hash tag 是业务侧满足同槽前提的主要手段。
- 命名惯例：tag 取逻辑实体的唯一标识（用户、订单、会话），同一实体的关联键共用一个 tag，如 {user1000}.follow、{user1000}.fans、{user1000}.profile。
- 典型场景：需要 MGET 批量取一个用户的多个属性、需要对同一用户的多个集合做 SUNION、需要在 Lua 里原子更新同一实体的多把键。
- 生效范围：hash tag 只影响槽计算，不改变键本身的存储内容，取数据时仍要用完整键访问。
- 与单机写法的兼容：单机模式下大括号只是键名的普通字符，上集群后大括号才开始参与哈希，因此含大括号的键名可以平滑迁移。

hash tag 的映射效果示意：

```text
{user1000}.follow   →  只哈希 user1000 → 槽 4713
{user1000}.fans     →  只哈希 user1000 → 槽 4713   （同槽，可多键操作）
user1000.follow     →  哈希全键        → 槽 11101
user1000.fans       →  哈希全键        → 槽 15780   （不同槽，不可多键操作）
{}.follow           →  括号内为空，退回对整个键算槽
（槽号为示意值，实际以 CRC16 计算结果为准）
```

> [!CAUTION]
> **注意内容**：hash tag 有把数据压回单节点的副作用——同一 tag 的所有键永远落在同一槽，若全库只用一个 tag 或热门 tag 名下聚集海量键，其所在主节点的内存与流量都会过载而其他节点闲置，分片能力直接归零；tag 的粒度应控制在业务上确需同槽操作的键组层面，按需最小化使用。

**速记**：**大括号里才是键**，同 tag 必同槽，同槽才能多键操作；tag 一热节点倾斜，按需最小化使用。



### 节点通信与 gossip 协议

#### CLUSTER MEET 与节点握手

**CLUSTER MEET**：是让节点加入集群的握手命令——向目标节点发送 CLUSTER MEET ip port 后，两节点通过握手互相确认，新节点从此成为集群成员。

- 握手流程：节点 A 对 B 执行 MEET → B 回 PONG 并把 A 记入自己的节点表、将 A 视为普通成员 → B 定期向 A 发 PING → A 回 PONG 并确认 B 已认识自己，双向信任建立。
- 全网知晓：MEET 只是点对点的初次认识，其余节点通过 gossip 的 PING、PONG 携带的节点信息逐渐得知新节点的存在，拓扑信息最终收敛到全网一致。
- 加入不等于干活：新节点握手成功后不负责任何槽，是空节点；要让它分担数据，还须指派槽（redis-cli --cluster reshard 或 CLUSTER ADDSLOTS），否则它只是集群的旁观者。
- 建立主从关系：新节点作为从节点加入时，执行 CLUSTER REPLICATE 主节点 Node ID，即成为该主的从节点并开始全量同步（复制机制详见第 20 章）。
- 自动化封装：redis-cli --cluster add-node 命令的底层就是 CLUSTER MEET，日常运维不必手工握手。
- Node ID 优先：互认与指派都用 Node ID 而非 IP 端口，节点重启、换机后只要数据文件在，身份不变，主从关系自动延续。

握手与融入的时间线示意：

```text
t0  A 执行 CLUSTER MEET B_ip B_port        —— A 认识 B
t1  B 回 PONG，B 的节点表里出现 A           —— B 认识 A
t2  B 定期 PING，A 回 PONG                  —— 双向确认
t3  gossip 携带新节点信息扩散               —— 全网知晓 B
t4  指派槽（reshard）或 REPLICATE           —— B 开始承担角色
```

> 辨析：CLUSTER MEET 与哨兵的监控建立方式不同——哨兵靠订阅 hello 频道与 INFO 命令自动发现节点（详见第 21 章），Cluster 则必须显式 MEET 一次；但 MEET 只需执行一次，之后的拓扑变化全靠 gossip 自动同步。

**速记**：**MEET 认识一次，gossip 传遍全网，指派槽才开始干活**。



#### gossip 五类消息与集群总线

**gossip 协议**：集群节点之间通过 gossip 消息交换彼此掌握的集群状态——每个节点周期性地把部分已知信息传给部分节点，信息像流言一样扩散，最终全网收敛，这是去中心化架构唯一的信息同步通道。

- 集群总线：节点在客户端端口之外的专用端口上互相通信，传统上为客户端端口加 10000（如 7000 节点的总线端口为 17000，7.0 起可独立配置）；故障检测、配置更新、故障转移授权全部走总线，业务流量与控制流量分离。
- **MEET**：邀请新节点加入集群，语义与 PING 相同但只发给尚不认识的新节点，是握手的起点。
- **PING**：常规心跳，每个节点平均每 100 毫秒向随机一个节点发送，消息体携带自身状态以及随机挑选的部分已知节点状态。
- **PONG**：对 MEET 与 PING 的应答，同样携带自身状态；节点也会主动广播 PONG 来刷新全网对自己的认知，例如刚晋升为主节点、刚接管新槽时。
- **FAIL**：某节点被判定 FAIL 后发出的广播消息——不走常规 gossip 而是点对点直发所有可达节点，让全网尽快知道某主节点已死、可以换主。
- **UPDATE**：携带更高配置纪元（epoch）的节点配置，用于纠正还持有过期信息的节点，保证各家节点表向最新配置看齐。
- 信息量控制：每条 PING、PONG 只随机携带约十分之一节点的状态，单条消息体积可控，全量信息靠多次心跳逐步扩散收敛；消息头还携带发送者负责的槽位图，接收方借此更新本地的集群视图。
- 驱动者：gossip 任务由主线程事件循环内的周期任务驱动（详见第 16 章 serverCron 的集群心跳部分），因此节点阻塞同样会拖慢心跳，可能诱发误判下线。

五类消息的分工示意：

```text
MEET   —— 请客入门：认识新节点（一次）
PING   —— 打招呼：常规心跳，捎带槽位图与部分节点状态（常态）
PONG   —— 应答：回 MEET/PING，也可主动广播刷新认知
FAIL   —— 讣告：主节点确定死亡，点对点尽快通知全网
UPDATE —— 改口：以更高纪元的配置纠正过期认知
```

> 辨析：gossip 是**最终一致**而非实时一致，一条状态要传遍全网需要多个往返，节点视图存在短暂分歧是常态；FAIL 消息为什么单独存在而不靠 gossip 慢慢传——gossip 是指数级扩散、收敛有延迟，而主节点死亡后要尽快启动故障转移以减少写服务中断，于是采用点对点直发的**紧急广播**，宁可占用更多总线带宽也要压缩传播时间。

**速记**：**MEET 请客、PING 打招呼、PONG 应答、FAIL 讣告、UPDATE 改口**，捎带槽位图、最终一致。



### 数据路由与重定向

#### MOVED 重定向指向槽的永久归属

**MOVED 重定向**：客户端把命令发到不负责该键所在槽的节点时，节点回复 MOVED 槽号 ip:port，告知该槽现在归属哪个节点——这是**槽归属的永久性指引**，客户端应当更新本地槽表并按新地址重试。

- 触发条件：请求键的槽不归当前节点负责，且槽的归属已稳定转移（reshard 完成、故障转移后槽随新主），属于集群的长期状态。
- 回复格式：MOVED 3999 127.0.0.1:6381，槽号与目标节点地址一并给出，客户端照单全收即可。
- 两类客户端的应对：普通客户端收到 MOVED 后转向新地址重发这一条命令；smart client 则把槽号到节点的映射更新进本地槽表，后续同类请求直达，不再触发重定向。
- redis-cli 的表现：加 -c 参数进入集群模式后自动跟随重定向，不加则只打印 MOVED 信息；这也是演示重定向行为的最直观方式。
- 常见出现时机：集群刚 reshard 完而客户端槽表未刷新、故障转移后槽已随新主、直连了错误节点。

```text
127.0.0.1:7000> SET foo bar
(error) MOVED 12182 127.0.0.1:7002
```

> 辨析：MOVED 与 ASK 的完整对照见下一考点；单记 MOVED 的抓手是**以后都找他**——回复中的地址是槽的长期归属，值得写进槽表。

**速记**：MOVED ＝ **这槽以后归他，请记下并重发**。



#### ASK 重定向指向迁移中的临时去向

**ASK 重定向**：槽正从源节点迁往目标节点的中间态里，源节点发现请求的键已搬走，回复 ASK 槽号 ip:port——它只指路**这一次请求**，不改变槽的归属记录。

- 中间态的由来：reshard 以槽为单位、以键为步长分批搬运，搬运期间槽内键一部分在源、一部分在目标，但槽的正式归属仍记在源节点，直到迁移完成才整体易主。
- ASKING 前置：客户端收到 ASK 后，向目标节点**先发一条 ASKING 命令、再发原命令**；ASKING 是一次性通行证，只对紧接着的下一条命令生效，让目标节点按正在导入的槽处理，不带 ASKING 直接发命令会被再次以 MOVED 指回源节点。
- 与 MOVED 的三大区别：语义上 MOVED 表示槽已永久易主、ASK 表示槽正在迁移（临时）；有效期上 MOVED 值得更新槽表、ASK 只对本次请求生效；客户端动作上 MOVED 直接重发即可、ASK 必须先发 ASKING。
- 源节点的行为：迁移期间键还在本地则照常服务；键已搬走则回 ASK；一条命令涉及多键而部分键已搬走时返回 TRYAGAIN。
- 目标节点的行为：槽处于 IMPORTING 状态时，对带 ASKING 的命令正常执行，对不带 ASKING 的命令回 MOVED 指回源节点。

MOVED 与 ASK 的逐项对照：

```text
语义     MOVED：槽已永久归属目标节点
         ASK  ：槽迁移中，键本次在目标节点
槽表     MOVED：客户端应更新本地槽映射
         ASK  ：不更新槽表，只本次生效
动作     MOVED：直接向目标节点重发命令
         ASK  ：先向目标节点发 ASKING，再发原命令
时机     MOVED：reshard 完成后 / 故障转移后
         ASK  ：reshard 进行中，键已搬走
```

> [!IMPORTANT]
> **重要内容**：区分二者的价值在于**槽表是否更新**——smart client 若把 ASK 误当 MOVED 写进槽表，迁移结束后仍会把流量发往已卸下槽的源节点，造成持续的重定向往返；反之把 MOVED 当 ASK 处理则每次都多绕一层。一个是过户完成换地址，一个是搬家途中临时串门，记住口诀：**MOVED 改表，ASK 只改这一次的路**。

**速记**：MOVED 说**以后都找他**，ASK 说**这次先问他（先发 ASKING 再重发）**，一字之差语义两别。



#### smart client 与 CLUSTER SLOTS、CLUSTER SHARDS

**smart client（智能客户端）**：在客户端进程内缓存槽到节点的映射表，让绝大多数请求直达正确节点，只在映射失效时借助重定向纠偏——官方对 Serious client 的标准要求。

- 工作流程：启动时连接任一节点执行 CLUSTER SLOTS 拉取槽表 → 本地缓存槽区间到主节点（及其从节点）的映射 → 请求按键算槽、查表直达 → 收到 MOVED 时更新槽表、收到 ASK 时单次转向 → 拓扑剧变时全量刷新。
- CLUSTER SLOTS：自集群诞生（3.0）起可用的槽表查询命令，返回槽区间与主从节点地址的映射，是 smart client 初始化的标准入口。
- CLUSTER SHARDS：Redis 7.0 新增，以分片（shard）为单位返回拓扑，一个分片内的主节点与全部从节点组织在一起，信息结构比 SLOTS 更完整，官方建议新客户端逐步采用。
- 连接管理：客户端通常对每个主节点维护独立连接池，故障节点的连接会被隔离并在拓扑刷新后重建。
- 从节点读：默认所有读写都发往主节点；客户端可对从节点先发 READONLY 命令，把部分读请求分流到从节点，牺牲一点实时性换取读扩展。
- 现成实现：主流客户端库均内置集群支持，例如 Node 生态的 ioredis 用 Cluster 模式传入部分节点地址即可自动发现全网并维护槽表（详见第 30 章）。
- 无代理直连：集群没有中心代理层，路由职责全部落在客户端，这是它延迟低的原因，也是它要求客户端必须懂集群协议的原因。
- 刷新时机：收到 MOVED 且与本地槽表冲突、检测到节点增删、故障转移完成后，客户端应重新拉取槽表；不存在一次拉取终身有效的假设。

smart client 的请求路径示意：

```text
启动：CLUSTER SLOTS → 本地槽表（槽区间 → 节点）
请求：key → CRC16 mod 16384 → 查槽表 → 直达目标节点
纠偏：MOVED → 更新槽表并重试；ASK → 发 ASKING 后重发
兜底：槽表失效（如转移后）→ 重新拉取 CLUSTER SLOTS
```

> [!TIP]
> **建议内容**：接入集群时优先选用内置集群支持的客户端库，而不是自己实现槽表管理——槽表刷新、MOVED 与 ASK 处理、失败熔断等细节自研极易踩坑；业务代码只需按第 30 章的方式配置部分节点地址即可。

**速记**：**一次拉表、直达优先、重定向纠偏、失效重拉**，从节点读先 READONLY。



### 故障检测与从节点选举

#### PFAIL 到 FAIL 的两级故障检测

**PFAIL 与 FAIL**：集群对不可达节点先标记 PFAIL（Possible Failure，疑似下线，个别节点的局部观察），当集群的多数主节点都报告同一节点 PFAIL 时升级为 FAIL（确定下线，集群级结论）——两级检测与哨兵的主观下线、客观下线完全同构（详见第 21 章）。

- PFAIL 的判定：节点在超过 cluster-node-timeout（默认 15000 毫秒）的时长内没有收到目标节点对 PING 的 PONG，即把目标标记为 PFAIL；这是本地结论，可随目标恢复而撤销，与哨兵的 SDOWN 同理。
- 怀疑扩散：PFAIL 的判定随 gossip 消息捎带给其他节点，各节点据此更新各自的怀疑名单，为多数派表决积累证据。
- FAIL 的升级：任一主节点在 gossip 交换中收集到**多数主节点**对同一节点的 PFAIL 报告，就将其升级为 FAIL，并立即广播 FAIL 消息让全网生效，随后触发故障转移。
- 投票权归属：只有主节点能参与 FAIL 的确认，从节点的 PFAIL 报告只作参考、没有确认权——这与哨兵中只有哨兵参与协商、数据节点无话语权的分工一致。
- 失效对象与后果：主节点被判定 FAIL 触发故障转移，从节点晋升接槽；从节点被判定 FAIL 只影响其主节点的冗余度，不触发任何转移，等它恢复即可。
- 超时参数：cluster-node-timeout 是判定怀疑的门槛，设置过小会频繁误判，过大则故障发现变慢，生产常见取值在秒级到十几秒之间。
- 与哨兵的对照：PFAIL 约等于 SDOWN，FAIL 约等于 ODOWN；差别在于哨兵由独立进程协商，Cluster 由数据节点自身协商，少部署一层组件，机制思想一脉相承。

PFAIL 到 FAIL 的传播链示意：

```text
t0  节点 X 超过 cluster-node-timeout 未回 PONG
t1  与 X 通信过的各节点各自标记 X 为 PFAIL（局部观察，随 gossip 扩散）
t2  主节点 A 收集到多数主节点对 X 的 PFAIL 报告
t3  A 将 X 标记为 FAIL 并点对点广播 FAIL 消息
t4  全网节点知晓 X 已死；若 X 是主节点，其从节点启动选举
```

> [!IMPORTANT]
> **重要内容**：FAIL 的确认权握在**多数派主节点**手里，这直接决定集群的可用性下限——三主集群挂掉两个主（或与它们隔离）时，剩余一个主凑不齐多数派，FAIL 判定与故障转移都无法启动；同理，与多数主失联的节点会主动停止接受查询。主节点数量太少或集中部署，都会让这套机制形同虚设。

**速记**：PFAIL ＝ **一个人觉得它可疑**（超时收不到 PONG），FAIL ＝ **多数主签名确认**（广播全网触发转移），只有主节点有确认权。



#### 从节点基于纪元的选举与投票

**从节点选举**：主节点被判定 FAIL 后，其从节点发起基于纪元（epoch）的选举——向全集群主节点拉票，赢得多数派授权后晋升为新主并接管槽，全程自动完成，无需任何外部进程。

- 发起时机与延迟：主节点 FAIL 后，其从节点各自等待一段随机延迟再发起选举；延迟与数据新鲜度挂钩——复制偏移量越新等待越短，让数据最完整的从节点**最先**发起、最可能当选，机制上内建了选最新的偏好，数据较旧者主动让路。
- 拉票方式：从节点向所有可达的主节点广播投票请求，携带当前纪元与自身信息；主节点收到后先校验资格再决定是否授权。
- 投票规则：每个主节点**在一个纪元内只投一票**，通常投给第一个来拉票且通过校验的从节点，先到先得；投出后本纪元不可改投，防止多个从节点同时当选。
- 资格校验：主节点拒绝为数据落后过多的从节点投票——与已失效主节点断链时长超过 node-timeout 乘以 validity 因子的从节点不予授权，防止把流量交给数据陈旧者。
- 当选条件：收集到**多数主节点**的授权票即当选；得票不足则等待后进入更高纪元重试，与哨兵选举的落选重试完全同型。
- 晋升动作：当选从节点执行 REPLICAOF NO ONE 撤销从属身份，升级为新主，以更高纪元广播 PONG 宣告新身份，接管原主负责的槽区间。
- 纪元的作用：配置纪元与当前纪元单调递增，旧纪元的投票与配置一律不被接受，防止过期结论污染新决策；故障转移完成后新主以更高纪元广播，全网随之更新槽的归属。
- 与哨兵选举的异同：相同点是先到先得、一人一票、多数派授权、纪元计数、随机延迟防选票瓜分；不同点是哨兵先选出领头哨兵、再由它挑从库晋升，而 Cluster 的从节点自己直接当选晋升，且多数派按主节点数计（哨兵按哨兵总数计）。

选举流程示意：

```text
主节点 M 被广播 FAIL
      ↓
M 的从节点们按数据新鲜度错峰发起选举（offset 最完整者最先）
      ↓
从节点广播投票请求（携带纪元）
      ↓
各主节点：本纪元未投票且资格校验通过 → 授权（一人一票）
      ↓
收集到多数主节点授权 → REPLICAOF NO ONE 晋升，接管槽，广播新纪元
      ↓
smart client 刷新槽表，流量切到新主
      ↓
落选 → 等待后进入下一纪元重试
```

> 辨析：与哨兵挑选新主的三条件（优先级、偏移量、runid 依次决胜，详见第 21 章）相比，Cluster 把选最新的内建到了**选举时序**里——数据越新发起越早、越先拿票；二者殊途同归，都是在可用性与数据新鲜度之间尽量偏向后者。代价是职责耦合：数据节点既要扛业务流量，又要参与心跳、选举与故障判定，需要为集群通信留出余量。

**速记**：**offset 新者先出手、旧者让路，一人一票，多数主授权即登基**；哨兵逻辑**内置化**，少一套进程。



#### cluster-require-full-coverage 与部分槽不可用

**cluster-require-full-coverage**：控制部分槽无人负责时集群是否继续服务——默认 yes，只要有任何槽未被覆盖，整个集群停止接受查询；设为 no 则只对落在缺失槽上的键报错，其余键照常服务。

- 默认 yes 的行为：数据完整性优先。任何槽缺失即 cluster_state 变为 fail，整库返回 CLUSTERDOWN 错误，读与写全部拒绝，宁可全停也不留下数据黑洞。
- 设为 no 的行为：可用性优先。缺失槽上的键不可用（同样报错），但其他槽的读写完全正常，等于把全局故障降级为局部故障，适合把 Redis 当纯缓存、能接受部分键暂时失效的场景。
- 缺槽的典型来源：某主节点与其全部从节点同时故障、从节点数据过旧或数量不足导致选举无法完成、reshard 中途失败遗留半迁移状态、新节点尚未完成槽指派。
- 相关配置：cluster-allow-reads-when-down（7.0 起可用，默认 no）允许集群判定异常时继续提供读服务，适合更看重读可用性的部署。
- 另一条红线：即使槽全覆盖，任何节点若与多数主节点失联，也会主动停止接受查询——这是防止网络分区期间双写的自保机制，与 full-coverage 两条独立生效。

行为对照示意：

```text
槽 12182 所在分片整体故障，其余 16000 余槽正常：

require-full-coverage=yes → cluster_state=fail → 整个集群拒绝服务（CLUSTERDOWN）
require-full-coverage=no  → 仅槽 12182 上的键报错，其余键照常读写
```

> [!TIP]
> **建议内容**：缓存类业务可把 cluster-require-full-coverage 设为 no，用部分数据的临时不可用换取整体服务的持续；存储关键数据的业务保持默认 yes，让缺失尽早暴露、尽快人工介入——缺主的槽不会自行恢复，要等人工补节点或故障转移完成，带着数据黑洞继续服务反而更危险。

**速记**：默认 **yes 全有或全无**，设 no 则**缺哪块停哪块**，缺槽不会自愈、需人工介入。



### 集群模式的使用限制

#### 单数据库与多键同槽两条硬约束

**使用限制**：集群模式下仅有 db0 一个数据库可用，且多键命令、事务、Lua 脚本涉及的**所有键必须落在同一槽**——为单机假设设计的功能在分布式下必须收窄。

- 仅 db0：SELECT 只能选 0 号库，选其他库报错；单机的多库隔离惯例（一库一业务）上集群后必须改为键前缀区分或拆成多套集群。
- 多键命令跨槽即错：MGET、MSET、带多个键的 DEL、SUNION、RENAME 等，所有键跨槽时返回 CROSSSLOT 错误；解决手段是 hash tag（见本章前文）。
- 事务与 Lua 同受约束：事务中的全部键、Lua 脚本触碰的全部键必须同槽，跨槽脚本要么按实体拆分、要么借助 hash tag 归拢（事务与 Lua 详见第 23 章）。
- pipeline 限同节点：同一管道内的命令须发往同一节点，客户端应按槽分组、分批发送，不能把跨节点命令混进一条管道。
- 扫描的范围变化：SCAN 只遍历当前节点的槽内键，全库扫描要逐节点执行，不能沿用单机一次 SCAN 扫全库的习惯。
- 清库的作用域：FLUSHDB、FLUSHALL 只清空接收命令的节点，全集群清库需逐节点执行。
- 从节点默认只读：写命令只能发给主节点，误发从节点会收到 MOVED 指回主节点；先发 READONLY 才允许在从节点上读。
- 迁移场景的限制：多键命令撞上正在迁移的槽可能触发 TRYAGAIN 瞬态错误，客户端需具备重试能力。
- 发布订阅的范围：集群下普通发布订阅会广播到全集群，功能可用，但与 Stream 消息队列（详见第 24 章）的语义差异需要辨析。

从单机迁移到集群的改造检查清单示意：

```text
① SELECT n（n 大于 0）    → 改键前缀或拆集群
② MGET/MSET 跨槽键       → hash tag 归拢或按节点分组
③ MULTI/EXEC 跨槽键      → 同上（详见第 23 章）
④ EVAL 脚本触多槽键      → 同上
⑤ pipeline 混跨节点命令  → 按节点分组分批
⑥ SCAN 扫全库            → 逐节点 SCAN
⑦ FLUSHALL 清全库        → 逐节点执行
```

> [!WARNING]
> **警告内容**：从单机迁往集群的业务务必先审计三类用法——多 db、跨槽多键命令、跨槽事务与 Lua；它们在单机上畅通无阻，上集群后从静默可用变为显式报错（CROSSSLOT），若在上线后才暴露往往伴随业务中断，改造路径是用 hash tag 归拢、客户端按槽拆分或调整数据模型，应在迁移前完成。

**速记**：**只有 db0，多键、事务、Lua、pipeline 必同槽同节点**，hash tag 是唯一的解药，跨槽必撞 CROSSSLOT。



### 运维命令与搭建实践

#### CLUSTER 命令族覆盖查看、组网与手动转移

**CLUSTER 命令族**：面向运维与客户端的集群管理命令集合，覆盖状态查看、槽管理、主从指派与手动故障转移四类操作。

```bash
# 状态查看
CLUSTER INFO                          # 集群整体状态：state、槽覆盖数、纪元
CLUSTER NODES                         # 本节点视角的全部节点与槽段
CLUSTER MYID                          # 本节点的 Node ID
CLUSTER KEYSLOT user:1000             # 查询键所在槽号
CLUSTER SLOTS                         # 槽区间到节点的映射（客户端拉表用）
CLUSTER SHARDS                        # 7.0 起可用，按分片返回拓扑

# 组网与槽管理
CLUSTER MEET 127.0.0.1 7001           # 邀请节点加入
CLUSTER ADDSLOTS 0 1 2                # 把槽指派给本节点
CLUSTER REPLICATE <主节点 Node ID>     # 本节点降为指定主的从节点

# 故障转移与重置
CLUSTER FAILOVER                      # 在从节点上执行，手动晋升为主
CLUSTER RESET HARD                    # 重置节点集群状态（脱离集群用）
```

- CLUSTER INFO：重点看 cluster_state（ok 或 fail）、cluster_slots_assigned、cluster_slots_ok 与 cluster_known_nodes，是判断集群健康的第一入口。
- CLUSTER NODES：输出本节点视角的全网拓扑，每行一个节点，含 Node ID、地址加总线端口、flags（master、slave、fail、pfail、myself 等标记）、主从关系与负责的槽区间；排查拓扑异常以此为准。
- CLUSTER ADDSLOTS：新集群手工初始化或补指派槽时使用；成段的槽指派用 ADDSLOTSRANGE，7.0 起提供。
- CLUSTER REPLICATE：把本节点设置为指定主节点的从节点，节点清空自身数据后开始全量同步，是手工组网建立主从的入口。
- CLUSTER FAILOVER：在目标从节点上执行，默认先与主节点同步到一致再晋升，尽量不丢数据；适用于计划性迁移，如硬件更换、机房搬迁。
- 辅助命令：CLUSTER COUNTKEYSINSLOT 统计某槽的键数量，CLUSTER GETKEYSINSLOT 取出槽内一批键，迁移前评估数据量靠前者，逐批搬运靠后者。
- redis-cli --cluster 系列子命令：create、add-node、reshard、rebalance、check、fix 等把上述原语封装成一键操作（详见第 28 章），日常运维优先用它而非手工敲 CLUSTER 命令。

> [!NOTE]
> **提醒内容**：CLUSTER FAILOVER 与自动故障转移走同一条选举链路，区别只是由人工发起且默认更平稳（先同步后切换）；执行前确认该节点确为目标主节点的从节点，否则命令会被拒绝。

**速记**：**INFO 看健康、NODES 看拓扑、ADDSLOTS 派槽、REPLICATE 认主、FAILOVER 手动换主**，flags 里 fail、pfail 是病灶。



#### 搭建三主三从最小集群示例

**搭建流程**：每个节点开启 cluster-enabled 并指定集群状态文件，启动后用 redis-cli --cluster create 一条命令完成组网、分槽与主从指派。

```bash
# redis.conf（每个节点一份，仅端口不同）
port 7000
cluster-enabled yes
cluster-config-file nodes-7000.conf
cluster-node-timeout 5000
appendonly yes
```

- cluster-enabled yes：打开集群模式开关，缺省时该实例以普通单机模式启动，即使执行集群命令也不会生效。
- cluster-config-file：节点自动生成并持续改写的集群状态文件，记录节点表、槽段与纪元；它与 redis.conf 性质完全不同，**严禁人工编辑**，重启后集群状态从它恢复。
- cluster-node-timeout：判定节点失联的毫秒阈值（示例 5000，默认 15000），是 PFAIL 判定与从节点选举时钟的基准。
- appendonly yes：集群场景同样建议开启 AOF 持久化（详见第 18 章），避免全集群重启后数据全失。
- 前置条件：节点内若已有数据，create 会拒绝执行，组建前需确认实例为空；节点间网络互通含总线端口；容器与 NAT 环境需配置 cluster-announce-ip 把对外可达地址广播给集群。

```bash
# 启动 6 个实例后创建集群，--cluster-replicas 1 表示每个主节点配 1 个从节点
redis-cli --cluster create 127.0.0.1:7000 127.0.0.1:7001 \
  127.0.0.1:7002 127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005 \
  --cluster-replicas 1
```

- create 的工作内容：自动完成 MEET 组网、把 16384 个槽均分给前三个节点、按 replicas 参数把后三个节点设为从节点；执行中会打印计划并请求确认。
- 成功标志：输出 [OK] All 16384 slots covered，即每个槽都至少有一个主节点负责。
- 最小规模：能正常工作的集群至少三个主节点；官方强烈推荐三主三从共六节点，让每个分片都有故障转移能力。
- 验证与体验：用 redis-cli -c -p 7000 连入，SET 一个键会看到 MOVED 重定向提示并自动跟随，CLUSTER INFO 显示 cluster_state 为 ok，CLUSTER NODES 确认三主三从与槽区间分布。
- 本地实验捷径：源码 utils 目录下的 create-cluster 脚本可一键起停六个本地节点，免去手工写六份配置。

```bash
# 验证集群
redis-cli -c -p 7000 set foo bar        # 自动跟随 MOVED 重定向
redis-cli -p 7000 cluster info          # cluster_state:ok，槽全覆盖
redis-cli -p 7000 cluster nodes         # 三主三从与槽区间分布
```

> [!CAUTION]
> **注意内容**：cluster-config-file 由节点独占维护，人工编辑的内容会在下一次状态刷新时被覆盖，极端情况下还会造成节点表错乱；调整集群结构一律走 CLUSTER 命令或 redis-cli --cluster 子命令，不要碰这个文件。

**速记**：**两行配置开集群，一条 create 分好槽，All slots covered 才算成**。
