## 安全配置与运维实践

**安全配置与运维实践**：是让 Redis 在不可信环境中长期安全稳定运行的一整套工程方法——对外用网络隔离与认证授权把不可信访问挡在门外，对内用危险命令治理、传输加密、备份演练把误操作与入侵的影响面压到最小。

- 网络层是第一道防线：bind 限定监听地址、protected-mode 兜底拦截、防火墙与安全组保证禁止公网直连。
- 认证与授权是第二道防线：requirepass 与 AUTH 是传统手段，Redis 6.0 起 ACL 提供用户级的细粒度命令与键权限，主从之间用 masterauth 完成认证。
- 命令面与传输面分别治理：rename-command 与代理层禁用收窄危险命令，TLS 加密客户端连接、复制链路与集群总线。
- 用典型入侵路径的复盘理解每项配置的必要性，再落到日常运维：容量与内存水位、备份与恢复演练、配置固化与优雅重启、监控告警与应急处理。
- 本章偏工程实务，多数考点以配置示例呈现；性能侧的慢查询与延迟监控不在本章展开，统一指向第 29 章。

```text
本章考点地图：

安全模型：内网可信定位 ─ 纵深防御 ─ 未授权访问的入侵路径
网络与认证：bind 与 protected-mode ─ 防火墙 ─ requirepass ─ ACL
命令与传输：rename-command 与代理层对比 ─ TLS
架构与运维：备份恢复 ─ 容量规划 ─ 监控告警 ─ 优雅重启 ─ 上线检查
```

### 安全模型与威胁认知

#### Redis 官方安全模型的定位

**安全模型**：Redis 官方将自身定位为**内网可信环境中的高性能数据组件**，安全不依赖软件自身的深度加固，而是依靠**网络隔离、访问认证、权限最小化**三道外部防线。

- 官方安全指引（Redis 官网 Security 版块）明确：Redis 在设计上假定所在网络是**可信的**，软件层攻击面控制不是核心设计目标。
- DEBUG、CONFIG 等调试与运维命令在历史上被有意保留以便排障，也因此会成为入侵者手里的工具。
- 由此得到生产部署的安全等式：**不可达优先于可防御**——让攻击者根本连不上，胜过连上之后再防。
- 三道防线逐层收紧：网络层只允许内网访问，访问层强制认证，权限层用 ACL 限制命令与 key。
- 默认配置逐年收紧：新版本默认只绑定回环地址并开启保护模式，安全基线由默认值兜底，而不是依赖使用者逐项加固。
- 官方安全指引给出的最小加固集合非常朴素：用防火墙限制来源、设置强密码、按需启用 TLS，其余措施都围绕这三点展开。
- 评估任何第三方增强方案（代理、旁路审计、安全插件）时，先确认它不破坏这三道防线的语义，再谈收益。

安全建设要按**纵深防御**的思路组织，让任何一层失守时，下一层仍然能够顶住：

- 网络层失守（端口被扫描到）时，认证层让外部连接拿不到任何数据。
- 认证层失守（密码泄露）时，ACL 让泄露的账号只能触达有限的命令与 key。
- 权限层失守（应用账号被盗）时，异机备份保证数据最终可以重建。

每一层防线的强度都要定期验证：改密码后确认旧密码失效、封网段后从被封来源试连、降权后用受限账号实测越权访问是否被拒，防线配置了不等于生效了。

> 与数据库类软件不同，Redis 没有表级、行级那样细的内置权限体系，安全边界大量让渡给运维手段。理解这一官方立场，就能明白本章的行文顺序为何是先网络、再认证、后权限。

**速记**：内网可信组件，靠**网络隔离 + 认证 + 权限最小化**保平安。



#### 未授权访问漏洞的入侵路径

**未授权访问漏洞**：指实例在**无密码且端口可达公网**的配置下暴露 6379 端口，攻击者无需认证即可执行任意 Redis 命令的漏洞，是历史上发生最频繁、危害最直接的 Redis 安全事件。

- 清库勒索路径：连接后直接执行 FLUSHALL 删光数据，或篡改数据后留下勒索信息。
- 计划任务写入路径：用 CONFIG SET dir 把工作目录指向 /var/spool/cron，再用 CONFIG SET dbfilename 改名，写入一条带反弹 shell 的计划任务，随 crond 执行即拿到机器权限。
- ssh 密钥写入路径：把 dir 指向 /root/.ssh、dbfilename 指向 authorized_keys，写入攻击者公钥后即可 ssh 免密登录，常见后续动作是植入挖矿程序长期驻留。
- 模块加载路径：Redis 4.0 起支持 module 动态加载，配合主从复制同步恶意 so 文件再 MODULE LOAD，可直接获得代码执行环境。
- 传播放大路径：攻陷一台实例后扫描内网其他 6379 端口继续植入，形成横向移动，这也是内网弱密码实例连环沦陷的常见形态。
- 常见诱因回看：事故复盘中的高频原因是临时调试改了 bind 或安全组、忘了回收，临时改动必须带过期时间或工单闭环。

上述路径的共同前提是攻击者能执行 CONFIG 这类**带运行时写文件能力**的命令，因此防御抓手非常明确：

- 封命令：用 ACL 禁掉 CONFIG、MODULE、DEBUG 等高危命令分类。
- 封写文件：生产实例的运行用户不应对 cron 目录、ssh 目录有写权限。
- 封入口：网络层收口后，这些路径根本无从开始。

事后排查实例是否已被入侵，可按以下痕迹逐项核对：

- 检查 INFO clients 中是否长期存在来源不明的连接。
- 检查 keyspace 中是否出现特征明显的可疑 key，以及宿主机 crontab、authorized_keys 是否被改动。
- 检查 slowlog 与 ACL LOG 中是否存在陌生的命令记录。
- 核对宿主机流量与进程，挖矿程序的典型特征是异常高的 CPU 占用与对外连接。

```bash
# 排查可疑连接与遍历 key 名单
CLIENT LIST
SCAN 0 COUNT 100
```

> 描述上述路径的唯一目的是**防御**：运维人员必须知道攻击者会用到 CONFIG、dir、dbfilename 这些入口，才能逐项封死。后文的危险命令治理与 ACL 正是针对这些入口的解法。

> [!WARNING]
> **警告内容**：公网裸奔的 Redis 通常在数小时到数天内就会被自动化扫描脚本发现并植入挖矿程序，清库与数据泄露随之而来。凡是发生过未授权访问的实例都应视为已被完全攻陷，不能仅删除可疑 key 了事，必须清数据、换密码、排查宿主机后才能重新上线。

**速记**：无密码上公网，等于**把服务器直接交出去**。



### 网络层防护

#### bind 与 protected-mode 的双重防线

**bind 与 protected-mode**：是 Redis 自带的两个网络收口开关，bind 决定**监听哪些网卡地址**，protected-mode 决定**无人看管时是否自我封锁**，二者配合构成实例的第一道防线。

- bind 后跟地址列表，只写内网 IP 与回环地址，例如 bind 192.168.1.10 127.0.0.1；官方默认配置绑定回环地址并保持保护模式开启。
- bind 支持 IPv6：前缀减号表示忽略该地址解析失败（如 -::1），保证 IPv4 环境下配置不因 IPv6 缺失而启动报错。
- protected-mode 默认 yes：当实例**既没有设置密码、也没有显式 bind** 时，只接受本机回环连接，其余连接一律拒绝并返回提示。
- protected-mode 的保护是**有条件的兜底**：一旦配置了密码或 bind，它就不再额外限制，因此不能把安全完全寄托在它身上。
- 显式 bind 到内网地址后，公网网卡上根本没有监听，扫描流量在 TCP 层就被丢弃。

```bash
# redis.conf 中的推荐写法
bind 10.0.0.5 127.0.0.1
protected-mode yes
port 6379

# 与应用同机部署时只暴露给本机
bind 127.0.0.1
```

验证监听结果的两个常用手段：

```bash
# 确认实例只监听在预期的内网地址上
ss -lntp | grep 6379
# 从外部机器确认端口不可达或仅内网可达
redis-cli -h 10.0.0.5 -p 6379 PING
```

两个容易遗漏的配套收口：

- 集群与哨兵的附加端口（集群总线 16379、哨兵 26379）与数据端口同级重要，网络收口时要一并纳入。
- 实例启动日志中若出现安全相关的 WARNING 提示（未设密码且未限定监听），必须处理后再上线，启动日志的警告往往是最后的免费提醒。

监听与可达性验证应写进上线检查单：改 bind 之后在预期内网来源实测 PING 通过、在预期外来源实测超时，两头都验证过才算收口完成。

> 辨析 bind 0.0.0.0 与清空 bind：自行清空 bind 后实例会监听所有网卡，配合无密码即是最危险的组合；而 bind 127.0.0.1 只暴露给本机，适合与应用或代理同机部署的形态。禁止写成监听全部地址之后依赖防火墙兜底，收口应从监听层就开始。

**速记**：bind 定**听谁的门牌**，protected-mode 是**忘配密码时的保险栓**。



#### 防火墙与禁公网直连

**网络隔离**：是 Redis 安全中收益最高、成本最低的一层，核心原则是**实例只对内网应用网段可达**，公网任何来源都不得直连 6379。

- 云上部署用安全组放行来源为应用所在子网或安全组的 6379 端口，其余来源全部拒绝。
- 自建机房用 iptables 或 firewalld 限制来源网段，只信任应用服务器的地址。
- 内网规则也建议**精确到源 IP**，而不是放行整个网段，以缩小被横向利用的空间。
- 运维管理通道收敛到堡垒机，禁止任何人从办公网直连生产 Redis 排障。
- 确需跨公网访问时（如异地机房同步），走专线、VPN 或加密隧道，而不是暴露明文端口。
- 端口可以顺带更换：非默认端口挡不住定向攻击，但能过滤掉大量无脑扫描流量，属于低成本的附加收益。
- 安全组与防火墙规则同样要纳入版本化或文档管理，与实例清单对应，避免出现来历不明的历史规则。

```bash
# iptables 只放行应用网段访问 6379，其余拒绝
iptables -A INPUT -p tcp --dport 6379 -s 10.0.1.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 6379 -j DROP
```

firewalld 的等价写法，按机房现状二选一：

```bash
# firewalld 限定来源网段放行
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.0.1.0/24" port port="6379" protocol="tcp" accept'
firewall-cmd --reload
```

使用代理或隧道时的两点补充：

- stunnel、SSH 隧道等方案可把明文链路包进加密通道，适合少量跨网段管理访问，不适合全量业务流量。
- 引入代理层后，实例侧看到的是代理地址，ACL 的连接审计与日志排查都要按代理的真实转发规则来理解。

规则的生命周期管理与实例生命周期对齐：创建实例时建规则，下线实例时删规则，每次变更留下工单记录，避免规则越积越乱后无人敢清理。

> [!WARNING]
> **警告内容**：严禁把 6379 端口通过公网 IP、端口映射或 frp 类内网穿透工具暴露到互联网。安全组里顺手放行 0.0.0.0/0 是未授权访问事故最常见的原因，上线前务必复查一次入方向规则，下线与迁移机器时同步回收规则。

**速记**：安全组**只对内网开门**，公网直连一律封死。



### 认证与访问控制

#### requirepass 基础认证

**requirepass**：最基础的认证手段，为实例设置一个全局密码，客户端连接后必须先执行 AUTH 命令通过认证，才能继续操作。

- 配置方式：redis.conf 中写 requirepass YourStr0ngPass；运行时可用 CONFIG SET requirepass 立即生效，随后用 CONFIG REWRITE 写回配置文件。
- 客户端认证：命令行用 redis-cli -a 密码 连接，或在交互后执行 AUTH 密码；ioredis 等客户端在连接配置中传入 password 项。
- 密码必须是**足够长的随机串**：Redis 每秒可执行上万条命令，短密码会被爆破脚本瞬间试出。
- 主从架构中所有节点都应设置相同密码，从库通过 masterauth 配置项向主库认证，漏配会导致同步失败。
- 命令行带 -a 参数会把密码留在 shell 历史与进程列表里，脚本中改用 REDISCLI_AUTH 环境变量传入更稳妥。
- 在 6.0 之后，requirepass 实质等价于给 default 用户设置密码，底层统一由 ACL 系统管理。

```bash
# 未认证时的行为与认证流程
redis-cli
127.0.0.1:6379> GET order:1001
(error) NOAUTH Authentication required.
127.0.0.1:6379> AUTH YourStr0ngPass
OK
```

运行时更换密码并落盘，以及脚本中的安全传参：

```bash
# 运行时修改密码并写回配置文件
127.0.0.1:6379> CONFIG SET requirepass NewStr0ngPass
127.0.0.1:6379> CONFIG REWRITE
# 脚本中用环境变量传密码，避免明文进 shell 历史
REDISCLI_AUTH='YourStr0ngPass' redis-cli INFO memory
```

主从同步最常见的认证类故障是从库漏配 masterauth，日志中反复出现同步失败与认证错误字样，客户端侧则表现为从库数据长期落后或一直处于连接状态而非同步状态。

> requirepass 是**明文存储**在 redis.conf 中的，任何能读取该文件或执行 CONFIG GET requirepass 的人都能拿到密码；密码不应复用其他系统的口令，配置文件权限应收紧为仅运维账号可读。单密码模式防得住扫描与陌生人，防不住需要分权的内部场景，分权方案见下一考点的 ACL。

**速记**：requirepass 是**全局一把锁**，明文配置，防扫描不防内鬼。



#### ACL 访问控制与只读账号

**ACL（Access Control List）**：Redis 6.0 引入的访问控制列表，为每个用户独立定义**用户名、密码、可执行命令白名单与可访问 key 模式**，把授权粒度从实例级细化到用户级。

- 用户要素四元组：用户名、启停状态（on 或 off）、密码、命令权限（+cmd 放行、-cmd 拒绝，或 +@category 按命令分类放行）。
- key 模式权限：用 波浪号加通配 限定该用户只能触碰匹配的 key，例如 ~order:* 只允许操作 order 前缀的键。
- 常用命令：ACL LIST 查看全部用户、ACL GETUSER 查看指定用户、ACL SETUSER 创建或修改、ACL DELUSER 删除用户、ACL CAT 列出命令分类、ACL SAVE 持久化到 aclfile。
- 默认只有 default 一个用户，传统单密码模式即以该用户工作。
- 客户端认证方式随 ACL 扩展为 AUTH 用户名 密码 两参数形式，老客户端的单参数 AUTH 走 default 用户。
- ACL LOG 记录因权限不足被拒绝的命令，业务突然大面积报错时先查这里，ACL LOG RESET 可清空。
- ACL GETUSER 的输出分 flags、passwords、commands、keys 几段，逐段确认后再交付账号。

创建账号的完整示例：

```bash
# 创建只能读 order 前缀 key 的报表账号
ACL SETUSER report on >R3port#2026 ~order:* +@read
# 创建读写 cache 前缀的应用账号，并禁用危险命令分类
ACL SETUSER app on >App#2026 ~cache:* +@read +@write -@dangerous
# 创建只供监控采集用的账号
ACL SETUSER monitor on >Mon#2026 +info +ping +client
# 查看与持久化，并检查被拒命令记录
ACL GETUSER report
ACL LOG
ACL SAVE
```

用户定义也可独立成文件管理：

```bash
# /etc/redis/users.acl 的内容示例，redis.conf 中配置 aclfile 指向它
user default off
user report on >R3port#2026 ~order:* +@read
user app on >App#2026 ~cache:* +@read +@write -@dangerous
user monitor on >Mon#2026 +info +ping +client
```

- aclfile 独立文件：启用 aclfile 之后，redis.conf 中的 user 配置行不可再用，ACL SAVE 即把内存中的用户定义写回该文件。
- 密码写法：SETUSER 里用 大于号 前缀设明文密码，回显时会转为哈希；用 哈希号 前缀可直接写入哈希值，避免明文留在命令历史里。
- 即时生效：ACL SETUSER 的变更立刻作用于新建立的连接，不需要重启实例，这让收权操作可以随发现随执行。

> 辨析 requirepass 与 ACL 的关系：给 default 用户设密码就是 requirepass 的等价形式；一旦开始用 ACL，建议把全部用户（含 default）收进 aclfile 统一管理，避免 redis.conf 与 aclfile 两处定义互相覆盖造成困惑。注意给业务账号按需补上 +@connection 分类的连接类权限，缺失时客户端连基本连接建立都会受阻。

**速记**：ACL 四件套——**用户名、密码、命令白名单、key 模式**。



### 危险命令治理与传输加密

#### rename-command 置空与改名

**rename-command**：把指定命令重命名为自定义字符串或直接置空的配置指令，是 ACL 出现之前治理危险命令的主要手段，老版本实例至今仍依赖它。

- 置空写法：rename-command FLUSHALL 后接空串，表示该命令被彻底禁用，任何人调用都返回未知命令错误。
- 改名写法：rename-command CONFIG 后接一段随机串，只有知道新名字的运维能调用，扫描脚本猜不到。
- 常见治理对象：KEYS（慢查询大户，详见第 29 章）、FLUSHALL、FLUSHDB、CONFIG、DEBUG、SHUTDOWN。
- 治理粒度辨析：rename-command 是**全局生效**的，对所有人统一关掉或改名；ACL 则能**按用户**区分，运维账号保留 CONFIG、业务账号禁掉，6.0 之后优先选 ACL。
- 与代理层禁用的对比：Codis、Twemproxy 或云托管网关的命令黑白名单在接入层过滤、无需重启实例且可按客户端分组，但绕过代理的直连通道不受约束；rename-command 在服务端生效、覆盖一切入口，两者可叠加使用，叠加时以更严的一层为准。
- 治理能力辨析：它只改变命令名，不改变鉴权；配合 requirepass 使用时，拿到密码的攻击者仍可调用改名后的命令，因此它防误用、防扫描，不替代认证。

```bash
# redis.conf 中的危险命令治理示例
rename-command FLUSHALL ""
rename-command FLUSHDB ""
rename-command CONFIG "c0nfig-9x2k-random"
rename-command DEBUG ""
```

改名后的使用方式，也正是调用方同步成本所在：

```bash
# 改名后运维需用新名字调用
redis-cli c0nfig-9x2k-random GET maxmemory
```

治理思路的演进方向是从黑名单走向白名单：rename-command 是逐个关掉危险命令的黑名单思路，ACL 的 +@read、+@write 则是只放行需要的白名单思路，后者的默认安全性明显更高。存量老版本实例无法升级时，先按黑名单把高危命令置空，升级窗口打开后再迁移到 ACL。

> [!CAUTION]
> **注意内容**：rename-command 的误用成本很高——把 CONFIG 改名后，监控 exporter、哨兵与运维脚本若仍调用原命令会全部失败；把 KEYS 置空前必须确认没有业务依赖它。改名串一旦遗忘，只能重启换配置恢复。置空或改名后务必同步更新所有客户端与监控配置；6.0 之后的实例更推荐改用 ACL 的 -@dangerous 达成同样效果。

**速记**：置空是**焊死**，改名是**藏钥匙**，改完必须通知所有调用方。



#### TLS 配置与内网取舍

**TLS 加密传输**：Redis 自 6.0 起原生支持 TLS，可对客户端连接、主从复制与集群总线通信启用证书加密，防止链路被窃听或中间人劫持。

- 核心配置四件套：tls-port 指定加密端口、tls-cert-file 指定服务器证书、tls-key-file 指定私钥、tls-ca-cert-file 指定签发 CA。
- 明文端口与 TLS 端口可并存：port 6379 对内、tls-port 6380 对外，不同来源分别接入。
- 客户端证书校验：默认要求客户端出示证书，调低为不需要时用 tls-auth-clients no，按信任模型决定。
- 复制链路同样可加密：主从同步受 tls-replication yes 控制，集群总线由 tls-cluster 控制。
- 证书管理：建议用内部 CA 签发，服务端与客户端证书分开；私钥文件权限收敛为运行用户可读，并安排到期轮换计划。
- 性能取舍：TLS 握手与对称加密有可感知的 CPU 开销，高 QPS 实例需压测后再决定全量启用还是仅对跨信任域链路启用。

```bash
# redis.conf 的最小 TLS 配置
port 6379
tls-port 6380
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file /etc/redis/tls/redis.key
tls-ca-cert-file /etc/redis/tls/ca.crt
tls-replication yes
```

启用后用带证书的客户端验证：

```bash
# 用 TLS 端口连接验证握手与认证链
redis-cli --tls --cacert /etc/redis/tls/ca.crt --cert /etc/redis/tls/client.crt --key /etc/redis/tls/client.key -p 6380 PING
```

> 取舍结论：同机房纯内网、安全组边界清晰时，明文传输可接受；跨机房同步、混合云或链路经过不可控网络时，应启用 TLS。判断标准是**链路是否穿越不被信任的区域**，而不是一律开或一律关。加密引入后证书与私钥本身成为新的运维对象，到期未换、私钥泄露都会把加密链路变成故障源。

**速记**：TLS 四配置——**端口、证书、私钥、CA**，链路出内网就加密。



### 备份策略

#### RDB 与 AOF 的备份组合

**备份策略**：生产环境应同时利用 RDB 的紧凑快照与 AOF 的实时追加（两者机制详见第 17、18 章），并做到**异机保存**——备份只存在本机磁盘上，机器故障时等于没有备份。

- RDB 定时备份：用 cron 定期触发 BGSAVE，完成后把 dump.rdb 拷贝到异机或对象存储；拷贝前必须先 BGSAVE，避免拷到半写状态。
- AOF 实时保护：AOF 每秒 fsync 至多丢一秒数据，是恢复点最新的那份；定期 BGREWRITEAOF 压缩体积。
- 组合建议：核心数据两份都要——RDB 提供每日恢复点与快速全量恢复，AOF 提供秒级丢失上限；两者加载优先级与文件组织详见第 19 章。
- 备份窗口：BGSAVE 会触发 fork，安排在业务低峰执行，并把与同机其他定时任务的错峰纳入排期。
- 保留策略：常见做法是保留最近若干天的每日备份加数周的每周备份，RDB 文件经过压缩，存储成本低。
- 敏感数据治理：备份文件包含全部业务数据，落对象存储或异机时同步收紧访问权限，必要时加密后再传输。
- 恢复方式：停实例后用备份文件替换数据文件再启动，加载机制详见第 17、18 章。

```bash
# 每日凌晨两点触发 BGSAVE 并异机拷贝的 cron 示例
0 2 * * * redis-cli -a 'YourPass' BGSAVE && sleep 5 && rsync -a /var/lib/redis/dump.rdb backup-host:/backup/redis/
```

备份任务自身的监控同样要覆盖：cron 失败、rsync 失败、磁盘写满都会让备份静默停摆，备份任务的失败告警与实例告警同等重要。

> 辨析只备从库与全链备份：不要只依赖某台从库落盘——从库宕机时主库仍在写入，任何单点的备份文件都可能过时；多实例环境下应确保**每个主实例**都有独立的备份链，而不是备份了集群中某一台就认为完成。密码明文出现在 cron 中时，注意收紧 crontab 文件权限，或改用配置文件方式的认证。

**速记**：RDB 管**快照归档**，AOF 管**少丢数据**，异机存放才叫备份。



#### 备份验证与恢复演练

**备份验证**：未经恢复验证的备份不能称为可用备份——磁盘损坏、半写文件、版本不兼容，都会让看似存在的备份在关键时刻恢复失败。

- 文件校验：用 redis-check-rdb 与 redis-check-aof 工具检查备份文件完整性。
- 定期演练：每月在测试环境用备份文件启动一个临时实例，核对 key 数量与抽样数据，并记录恢复耗时。
- 演练覆盖完整流程：拷回文件、修改属主与权限、启动加载、应用重连，缺一环演练就不完整。
- 数据抽样核对：对比备份生成时的 dbsize 与恢复后的 dbsize，再抽查若干业务 key 的类型与内容。
- 演练记录要素：日期、使用的备份文件、恢复结果、实测耗时与执行人，逐次留档形成可追溯的记录。
- 版本匹配：恢复用的实例版本与备份来源版本保持兼容，跨大版本恢复先在演练中确认行为一致。
- 产出沉淀：演练过程写成操作手册，真实故障发生时按手册执行，没有时间试错。

```bash
# 校验备份文件完整性
redis-check-rdb /backup/redis/dump.rdb
redis-check-aof /backup/redis/appendonly.aof
# 在临时端口用备份起实例验证可加载
redis-server --port 6399 --dir /tmp/restore --dbfilename dump.rdb
```

校验与演练都可以脚本化，进入每月的定时任务，成功与否落到通知渠道，避免依赖人工记忆。

> [!TIP]
> **建议内容**：把恢复演练做成季度例行任务并记录 RTO——从决定恢复到服务可用的实测耗时。许多团队备份做了多年，第一次真正恢复时才发现文件损坏或路径变更；演练的意义就是把这种发现提前到没有损失的时候。

**速记**：**没验证过的备份等于没备份**，演练要跑全流程。



### 生产架构与容量规划

#### 最小生产架构的演进路线

**架构演进路线**：按数据价值与规模从**单机、主从加哨兵、Cluster 集群**三档推进，不提前过度设计，也不在数据变贵之后仍停留在单机。

- 单机：适合缓存类、丢了可重建的数据；前提是完成本章网络隔离、认证与备份三件基础工作。
- 主从加哨兵：核心数据的起步档，最小规模为 1 主 2 从 3 哨兵（详见第 20、21 章）；可精简为 3 台机器，每台跑 1 个数据节点加 1 个哨兵进程。
- 哨兵数量取奇数下限 3 的原因：故障判定靠多数派投票，2 个哨兵任一失联即无法形成多数，起不到自动切换的作用。
- Cluster：数据量超过单机内存或写入需要分片时启用，最小 3 主 3 从（详见第 22 章），规划时预留空节点便于后续迁移。
- 客户端改造成本：Cluster 需要客户端支持 MOVED 重定向与集群拓扑感知（详见第 22 章），升级前先确认所用客户端库的支持程度。
- 资源建议：单个数据节点的内存不宜超过 10 至 16 GB 一档，实例过大时主从同步、故障恢复与 fork 都会变慢。
- 每一档都要定期做故障演练：拔主库验证切换、拔从库验证冗余，架构的可用性是演练出来的，不是配置出来的。

集群与哨兵两种模式互斥：Cluster 依靠集群自身的故障转移机制，不依赖也不兼容哨兵进程；规划时在两条路线中选一条走到底，不要叠加两套高可用组件。

> 辨析需要哪一档：不是所有业务都需要哨兵或集群——纯缓存场景下，多花三台机器的运维成本可能不如把数据做成可重建；判断标准是**宕机丢数据能不能接受、服务中断几分钟能不能接受**。升级决策的输入就是容量规划与监控趋势，而不是照搬别人的架构。

**速记**：缓存单机起步，重要数据**主从加哨兵**，超大再上 **Cluster**。



#### 容量规划与内存预留

**容量规划**：核心是给 maxmemory 留足余量，避免把机器内存吃满之后触发系统 OOM 或 fork 失败。

- maxmemory 建议设为机器物理内存的 50% 至 70%，剩余部分留给 fork 时的写时复制、页缓存与其他进程。
- 大 value 用 MEMORY USAGE 命令按 key 估算实际占用，帮助发现设计失误（键管理详见第 2 章）。
- 淘汰策略必须与容量配套：缓存场景常用 allkeys-lru（详见第 15 章），不能容量靠淘汰兜底、策略却停在 noeviction。
- 碎片观察：mem_fragmentation_ratio 明显大于 1 时说明碎片偏高，必要时用 activedefrag 主动整理。
- 过期时间打散：大批 key 设置同一过期时刻会造成写入峰值与内存骤变，相关放大效应详见第 25 章的雪崩话题。
- 增长预估：按月观察 used_memory 增速，提前扩容，而不是等告警之后再救火。

粗略估算方法：总容量约等于 key 数量乘以单 key 平均占用，再加 10% 至 20% 的结构与碎片开销；单 key 平均占用用抽样 key 的 MEMORY USAGE 均值近似，估算结果再对照 INFO memory 实测校准。

```bash
# 估算单个 key 的实际内存占用
MEMORY USAGE order:1001
# 查看当前内存、峰值与碎片率
INFO memory
# 容量调整直接落到配置文件
CONFIG SET maxmemory 8gb
CONFIG REWRITE
```

大 key 的批量排查工具：

```bash
# 抽样扫描并统计各类别最大的 key
redis-cli --bigkeys
```

> 辨析两个内存指标：used_memory 与 used_memory_rss 的差值反映碎片与分配器开销；内存告警应基于 used_memory 相对 maxmemory 的比例，而不是看机器剩余内存，否则两者背离时会误判。fork 耗时与实例大小的关系，见下一考点的 latest_fork_usec 指标。

**速记**：maxmemory 留**三成余量**，大 value 用 **MEMORY USAGE** 估算。



#### 监控告警的基线指标

**监控告警基线**：判断实例健康状态的一组阈值约定，全部可从 INFO 命令输出或监控 exporter 获得，覆盖内存、性能、复制与系统四个维度，逐项一条线。

- 内存使用率：used_memory 达到 maxmemory 的 70% 告警、85% 严重告警，留出处置窗口。
- 缓存命中率：keyspace_hits 除以命中加未命中之和，长期低于 90% 需排查键设计与过期时间。
- 连接数：connected_clients 接近 maxclients 的 80% 告警，突增往往意味着连接泄漏。
- 键空间：dbsize 异常增长或 evicted_keys 出现非零增长都要告警，前者是泄漏征兆，后者说明容量已不够用。
- 慢查询数：slowlog 长度持续增长告警，逐条定位（详见第 29 章）。
- 主从延迟：主库 master_repl_offset 与从库 slave_repl_offset 的差值持续增大告警。
- fork 耗时：latest_fork_usec 超过数百毫秒告警，说明实例过大或宿主机内存紧张。
- 系统资源：实例所在机器的 CPU、网络吞吐与磁盘 IO 同步采集，用于排除宿主机层瓶颈的干扰。

采集侧的常见组合是 redis_exporter 加 Prometheus 加 Grafana，无监控体系时用脚本定时抓取 INFO 也够用：

```bash
# 巡检时一次性抓取核心三段
redis-cli INFO memory
redis-cli INFO replication
redis-cli INFO stats
```

告警要分级管理：内存 70%、延迟抖动归为当日处理的提醒级；内存 85%、主从断开、写报错归为立刻响应的严重级；每一级都要有明确的值班响应约定，告警没人响应等于没配。

阈值核查的两个常用入口：

```bash
CONFIG GET maxmemory-policy
SLOWLOG LEN
```

> 补充：以上指标按实例维度建看板，并以天为单位回顾趋势而不是只看瞬时值；趋势化的内存曲线是容量规划最直接的输入，突刺型的延迟曲线则多与 fork、慢查询相关。阈值上线后要经历一轮误报调优，避免狼来了效应。

**速记**：内存 **70 告警 85 严重**，命中、连接、慢查、延迟、fork 各设一条线。



### 日常运维与故障应急

#### 日常运维清单

**日常运维**：以定期巡检加受控变更为内容，目标是让问题在演变为故障之前被看见，让每次配置变化可追溯、可回滚。

- 每日巡检：抽查 INFO memory、INFO replication、INFO stats 三段输出，确认与监控基线一致。
- 每周巡检：确认备份任务成功落盘、slowlog 无异常新增、磁盘剩余空间充足。
- 月度任务：备份恢复演练、ACL 权限审计、容量与成本回顾，安排固定窗口执行。
- 配置变更：运行时用 CONFIG SET 调整后，必须执行 CONFIG REWRITE 写回配置文件，否则重启即失效。
- 变更管控：高危操作（改淘汰策略、重启、扩容）走审批并在低峰期执行，先在从库或测试实例验证。
- 版本升级：升级前阅读官方 Release Notes 中的不兼容项（例如 6.0 引入 ACL、7.0 调整了部分命令行为），先在测试环境完成业务回归再上生产。
- 权限收敛：定期执行 ACL LIST 审计账号，清理离职人员账号与权限过宽的账号。
- 文档同步：实例清单、密码交付方式、备份位置与负责人信息保持最新，故障时能立刻找到入口。
- 季度任务：故障应急演练、安全规则复查（安全组、ACL、rename 残留配置），与月度任务错峰安排。

变更留痕的最小记录要素：时间、变更人、变更内容、影响范围与回滚方式；有条件时配置文件直接进版本库管理，diff 即变更记录。

```bash
# 配置文件变更前先备份，改完 diff 留档
cp /etc/redis/redis.conf /etc/redis/redis.conf.bak
diff /etc/redis/redis.conf.bak /etc/redis/redis.conf
```

> [!CAUTION]
> **注意内容**：CONFIG SET 只改运行时状态，不改配置文件——改完不执行 CONFIG REWRITE，实例重启后旧配置原样回来，会出现改动凭空消失的事故。同理，CONFIG REWRITE 会以当前运行值覆盖文件，多人同时改配置时应约定单人操作并复核变更。

**速记**：巡检看 **INFO 三段**，改配置**SET 之后必 REWRITE**。



#### 优雅重启与持久化

**优雅重启与持久化**：是平滑更换 Redis 进程的标准操作——重启不丢数据的前提是 RDB 或 AOF 已把数据落盘，关闭前确认持久化状态、重启后核对数据，是两个必做动作。

- 关闭前确认：INFO persistence 中 rdb_last_bgsave_status 为 ok，开启 AOF 的实例确认 aof_last_write_status 为 ok；必要时显式 BGSAVE 并等待完成再关闭。
- SHUTDOWN 的默认行为：配置了保存点时阻塞执行保存后关闭，开启 AOF 时刷盘后关闭；未配置保存点且未开启 AOF 的实例不会主动保存，数据型实例必须先落盘（RDB 与 AOF 机制详见第 17、18 章）。
- 重启后验证：核对 dbsize 与关键业务键、确认应用重连与命中率回归基线，再宣布处置完成。
- 计划内重启主库先评估：哨兵环境会触发故障转移（详见第 21 章），集群环境该分片负责的槽位在重启期间不可用（详见第 22 章），均需按预案执行。
- 与 CONFIG REWRITE 的配合：运行期改过的配置先 REWRITE 落盘再重启，否则重启即回退旧值。

```bash
# 优雅重启的顺序（示意）
redis-cli INFO persistence        # 确认 rdb_last_bgsave_status:ok
redis-cli BGSAVE                  # 必要时显式触发并等待完成
redis-cli SHUTDOWN                # 按持久化配置落盘后关闭
redis-server /etc/redis/redis.conf
```

> [!CAUTION]
> **注意内容**：未配置保存点且未开启 AOF 的实例，SHUTDOWN 不会主动保存数据——纯缓存实例无所谓，数据型实例重启前必须确认持久化文件是最新状态，防止重启即丢数据。

**速记**：**重启之前必落盘**，SHUTDOWN 前看持久化状态，重启后核 dbsize。



#### 内存写满 noeviction 的处置

**noeviction 报错处置**：当 maxmemory 打满且淘汰策略为 noeviction（默认值，详见第 15 章）时，所有写命令返回 OOM 错误而读不受影响；处置顺序是先止血、再根因、后治本。

```bash
# 内存打满时的典型现象
127.0.0.1:6379> SET cache:1001 v
(error) OOM command not allowed when used memory > 'maxmemory'.
```

- 确认现状：执行 INFO memory 看 used_memory 与 maxmemory 的差距，执行 CONFIG GET maxmemory-policy 看当前策略。
- 紧急止血：数据可淘汰（纯缓存）时，临时 CONFIG SET maxmemory-policy allkeys-lru 放开淘汰；数据不可丢时，先清理过期与无用 key，或临时调大 maxmemory。
- 调大上限的边界：临时调大 maxmemory 不能超过机器物理内存的承载能力，否则可能把问题升级为整机 OOM。
- 键分布排查：用 SCAN 配合 MEMORY USAGE 抽样，找出占用最大的前缀，针对性清理或改设计。
- 根因排查：区分业务量自然增长、大 value 突增与泄漏型增长（只写不删、无过期时间）三类原因。
- 治本：按容量规划调整 maxmemory 与机器规格，为写入方补上过期时间，并把扩容流程沉淀为演练过的手册。

止血与排查的常用命令序列：

```bash
CONFIG GET maxmemory-policy
CONFIG SET maxmemory-policy allkeys-lru
SCAN 0 COUNT 100
```

> 辨析报错与静默淘汰：noeviction 下写报错本身是一种**保护**——它阻止数据被静默丢掉；改成 allkeys-lru 止血之前必须确认所有 key 都可以丢，否则缓存策略会悄悄淘汰本应保留的数据。持久化数据的实例不应依赖任何淘汰策略，容量必须按数据总量规划。

**速记**：写报 OOM 先**看策略**，能丢就开 **LRU**，不能丢就**清与扩**。



#### 主库宕机与误清库的应急处理

**应急处理**：对应两类典型事故——主库宕机需要尽快恢复服务，误执行 FLUSHALL 需要用备份找回数据；两者的第一动作都是**停止进一步破坏**。

**主库宕机的手动切换**：

- 确认主库真实故障且短期无法恢复；有哨兵的环境优先让哨兵自动切换（详见第 21 章），手动介入需避免与哨兵互相干扰。
- 对比各从库的 slave_repl_offset，选择最贴近原主库的一台，减少数据丢失。
- 在选中的从库上执行 REPLICAOF NO ONE 将其提升为主库。
- 应用侧把连接指向新主库；故障主库修复后降级为新主库的从库，恢复冗余。
- 切换完成后观察主从同步追平、命中率与错误率回归基线，再宣布处置结束。

**误执行 FLUSHALL 的恢复**：

- 第一时间停止所有写入并禁写实例，防止 AOF 把清库之后的空状态继续追加固化。
- 若 AOF 尚未 rewrite，用工具截掉 AOF 尾部的 FLUSHALL 命令后重启加载，可完整找回数据（AOF 机制详见第 18 章）。
- 若 AOF 已不可用，改用最近一次 RDB 备份按备份考点的流程恢复，接受两次备份之间的数据丢失。
- 恢复完成后核对 dbsize 与抽样数据，确认与备份生成时的规模一致，再放开写入。
- 事后复盘：用 ACL 禁用 FLUSHALL，给高危操作加双人复核。

两类事故都要求平时备好预案：切换命令序列、应用连接串改法、恢复操作手册形成文档并定期演练，应急的速度取决于演练的次数，而不是现场的反应。

```bash
# 查看各从库复制偏移量，选择最新的提升
redis-cli INFO replication
# 将选中的从库提升为主库
redis-cli REPLICAOF NO ONE
# 提升后确认角色已变为主库
redis-cli ROLE
```

> [!WARNING]
> **警告内容**：发现误执行 FLUSHALL 之后，任何情况下都不要先重启实例了事——重启会触发 AOF rewrite，把清库后的空数据固化下来，备份窗口之外的数据将永久丢失。正确动作是立即对实例禁写，先处理 AOF 或备份，再恢复服务。

**速记**：主库挂了**提从库**，误清库先**禁写救 AOF**，再谈恢复。
