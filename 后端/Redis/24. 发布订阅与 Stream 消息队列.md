## 发布订阅与 Stream 消息队列

**发布订阅与 Stream 消息队列**：是 Redis 在「即时通知」与「可靠投递」两端给出的消息方案——**发布订阅（Pub/Sub）** 以频道为单位做实时广播，消息在内存中转瞬即逝；**Stream** 是可持久化、可确认、可重投的追加日志型消息队列。本章以发布订阅的模型、底层实现与可靠性局限为主体，Stream 的命令细节详见第 9 章，这里聚焦定位与方案对比。

- 先讲发布订阅的模型与命令：SUBSCRIBE 订阅、PUBLISH 发布、PSUBSCRIBE 模式订阅，以及 pubsub_channels 字典与 pubsub_patterns 结构撑起的底层实现。
- 再讲 PUBSUB 自省命令族与 7.0 的分片发布订阅 Sharded Pub/Sub，理解它为什么能缓解集群里的广播风暴。
- 然后直面发布订阅的四大可靠性局限，从推送型与拉取型的分野解释为什么推送不可靠、拉取可弥补。
- 最后把 List 简单队列、Stream 消费者组、专业消息队列三种方案放在可靠性、有序性、堆积能力、重复消费四个维度上对比，给出选型结论。
- 阅读方法上，始终带着一条主线：这条消息丢了怎么办？答案决定了方案的选择。

```text
本章考点地图：

发布订阅：模型与命令 ─ 底层实现 ─ PUBSUB 自省 ─ 7.0 分片版

```

### 发布订阅的模型与命令

#### 发布订阅模型的定义与核心命令

**发布订阅（Pub/Sub）**：是一种消息传递范式——发布者把消息发往**频道（Channel）**而不是直接发给特定接收者，所有订阅该频道的客户端都各自收到一份推送，发布者与订阅者互不知晓对方存在，完全通过频道名解耦。

- **SUBSCRIBE channel [channel ...]**：订阅一个或多个频道，2.0 起可用，命令复杂度 O(N)，N 为订阅的频道数。
- **PUBLISH channel message**：向指定频道发布消息，2.0 起可用，返回接收到这条消息的客户端数量。
- **PSUBSCRIBE pattern [pattern ...]**：按通配符模式订阅，是与精确订阅并列的第二种订阅方式；通配符沿用 glob 风格，问号匹配单个字符、星号匹配任意长度字符、方括号匹配括号内任一字符。
- **UNSUBSCRIBE 与 PUNSUBSCRIBE**：分别退订普通频道与模式，不带参数时退订当前客户端持有的全部订阅。
- **RESET**：退出订阅态、清空全部订阅并恢复普通连接，6.2.0 起提供，是交互式客户端脱离订阅状态的正规出口。
- 消息模型是发后即忘（fire-and-forget）：PUBLISH 把消息推送给当下的订阅者即告完成，服务端不留副本、不等回执、不提供任何回查手段。

```text
订阅确认与消息推送的格式（示意）：

# 订阅确认：subscribe 频道名 当前订阅总数（频道与模式合并计数）
1) "subscribe"
2) "order:paid"
3) (integer) 1

# 普通消息：message 频道名 正文，共三个元素
1) "message"
2) "order:paid"
3) "orderId:1001"

# 模式命中的消息：pmessage 命中的模式 实际频道名 正文，共四个元素
1) "pmessage"
2) "order:*"
3) "order:paid"
4) "orderId:1001"
```

> 订阅态的命令限制：RESP2 下进入订阅态的客户端只能执行 SUBSCRIBE、SSUBSCRIBE、PSUBSCRIBE、UNSUBSCRIBE、SUNSUBSCRIBE、PUNSUBSCRIBE、PING、RESET、QUIT 这几个订阅类命令，不能再发普通读写命令；改用 RESP3（HELLO 3 切换）后推送是独立的带外消息类型，订阅态下可执行任意命令。redis-cli 进入订阅模式后不再接受命令，只能 Ctrl-C 退出。

> 与键空间无关是官方明文设计：Pub/Sub 不与任何数据库编号绑定，在 db 10 发布的消息，db 1 上的订阅者同样收得到；需要隔离时按环境给频道名加前缀（如 prod:order:paid），频道名即命名空间。

**速记**：**PUBLISH 广播、SUBSCRIBE 收听、PSUBSCRIBE 模糊收听**，发完即忘不保存。



#### 发布订阅的底层实现

**发布订阅的底层实现**：服务器用 **pubsub_channels 字典** 管理精确订阅、用 **pubsub_patterns 结构** 管理模式订阅，PUBLISH 沿着这两套结构遍历推送——它是一个纯内存的转发器，不与键空间发生任何关系。

- **pubsub_channels 字典**：键是频道名，值是订阅了该频道的客户端链表；SUBSCRIBE 时频道不存在就新建键再追加客户端，UNSUBSCRIBE 后链表空了就删除整个键。
- **pubsub_patterns 结构**：逐条记录「模式与订阅客户端」的对应关系；PSUBSCRIBE 追加一条对应记录，PUNSUBSCRIBE 移除对应记录。
- **PUBLISH 的执行流程**：第一步按频道名在 pubsub_channels 中定位客户端链表，逐一把 message 推给每个订阅者；第二步遍历 pubsub_patterns，对每条记录用 glob 语义匹配频道名，命中的向对应客户端推送 pmessage。
- 复杂度正是这套流程的注脚：官方标注 PUBLISH 为 O(N+M)，N 是该频道的订阅者数量，M 是全体客户端的模式订阅总条数——「遍历匹配」四个字直接写在复杂度里。
- 重复投递是官方明文行为：客户端同时订阅了命中同一条消息的多个模式，或同时持有精确订阅与命中模式，会按命中次数重复收到多份；PUBLISH 的返回计数也按推送次数计。
- 版本限定：以上按经典实现描述；7.0 起随分片发布订阅的引入，内部存储有所重构（模式与分片频道改用字典组织），但「按名查找频道、遍历匹配模式」的模型没有变化。

```text
一次 PUBLISH order:paid "orderId:1001" 的内部路径（示意）：

pubsub_channels 字典
  "order:paid" ──► [客户端A, 客户端B]   ──► 逐一推送 message
  "chat:1"     ──► [客户端C]             （未命中，不动）

pubsub_patterns 结构
  客户端D × "order:*"    ──► glob 匹配 order:paid 成功 ──► 推送 pmessage
  客户端E × "news.*"     ──► 不匹配，跳过
```

> 辨析：频道的「存在」只取决于 pubsub_channels 里有没有它的键——没有任何订阅者时，频道在服务端不占用任何结构，PUBLISH 一个无人订阅的频道就是一次空遍历，返回 0。

> 补充：PSUBSCRIBE 与 PUNSUBSCRIBE 的确认消息类型为 psubscribe 与 punsubscribe，格式与 subscribe、unsubscribe 完全一致，同样是三个元素——确认消息与正式消息在同一股推送流里排队，客户端按首元素类型分发处理。

**速记**：**字典管精确、模式表管模糊，PUBLISH 先查表再遍历**。



#### PUBSUB 自省命令族

**PUBSUB**：是发布订阅的**自省命令族**，无需订阅任何频道即可查看频道与订阅者的现状，是监控与排障的入口。

- PUBSUB CHANNELS [pattern]：列出当前**至少有一个订阅者**的活跃频道，支持按模式过滤。
- PUBSUB NUMSUB [channel ...]：逐一列出给定频道的精确订阅者数量，未列出的频道一律视为 0。
- PUBSUB NUMPAT：返回去重后的模式总数，同一模式被多个客户端重复订阅也只计一次（官方明文排除重复）。
- PUBSUB SHARDCHANNELS [pattern] 与 PUBSUB SHARDNUMSUB [channel ...]：7.0 起可用，查看分片频道的清单与订阅者数量。
- SHARDNUMSUB 的计数只统计分片订阅（SSUBSCRIBE），与 NUMSUB 的普通订阅口径互不包含，对账时勿混淆。

```bash
PUBSUB CHANNELS
PUBSUB NUMSUB order:paid
PUBSUB NUMPAT
PUBSUB SHARDCHANNELS
PUBSUB SHARDNUMSUB chat:{room1}
```

```text
1) "order:paid"
2) "order:refund"

# NUMSUB 返回 频道名 与 数量 交替出现的清单
1) "order:paid"
2) (integer) 2

# NUMPAT 返回单个整数
(integer) 3
```

> NUMSUB 只统计精确订阅，不包含按模式命中该频道的订阅者——想评估一条消息的真实受众，要把 NUMSUB 的数字与模式命中情况合起来看，这也是模式订阅排障困难的根源。

**速记**：CHANNELS **看清单**、NUMSUB **数人头**、NUMPAT **数模式**、SHARD 系列 **管分片**。



### Sharded Pub/Sub：7.0 的分片发布订阅

#### 分片发布订阅的机制

**Sharded Pub/Sub（分片发布订阅）**：Redis 7.0 引入的集群增强——**SSUBSCRIBE** 订阅、**SUNSUBSCRIBE** 退订、**SPUBLISH** 发布，分片频道按与普通键相同的槽算法归入集群槽位，消息只发往持有该槽的节点并在分片内转发。

- **路由规则**：频道名按键槽算法映射到槽位，哈希标签照常生效，如 chat:{room1} 与 chat:{room2} 会因大括号内的 room 不同而落进不同槽、不同分片。
- **转发范围**：集群保证分片消息被转发到该分片的全部节点，订阅端连槽所在的主节点或它的任意副本都能收到消息。
- **设计动机**：普通 Pub/Sub 在集群里每条消息都要经集群总线转发到每个节点，节点越多广播开销越大；分片版把传播范围收敛到单个分片，通过增加分片就能横向扩展发布订阅的吞吐。
- 适用场景：订阅者天然集中在某个槽附近的事件（如按房间、按用户分片组织的聊天与通知），分片版收益最大。

```bash
# 频道名含哈希标签，room1 整体参与槽计算
SSUBSCRIBE chat:{room1}
SPUBLISH chat:{room1} "hello"
SUNSUBSCRIBE chat:{room1}
```

```text
集群内两种传播范围的对照（示意）：

普通 PUBLISH： 消息 ── 集群总线 ──► 节点1、节点2、…、节点N（全网广播，节点越多开销越大）
分片 SPUBLISH：消息 ── 只发槽所在分片 ──► 槽的主节点 + 其全部副本（分片内转发）
```

> 注意分片版的能力边界：它**不支持模式订阅**，没有与 PSUBSCRIBE 对应的分片模式命令；需要模糊匹配时只能退回普通 Pub/Sub，或在客户端自行过滤。

**速记**：**SSUBSCRIBE 按槽归分片，SPUBLISH 分片内转发**，7.0 起可用。



#### 分片版与普通版的差异

**分片版与普通版的核心差异在传播范围**：普通 PUBLISH 把消息经集群总线转发到**每一个节点**，分片 SPUBLISH 只在**持有该槽的分片内**转发——一个是全网广播，一个是就近投递。

- **传播范围**：**普通版**在集群内每条消息转发到所有节点，任何节点上都能订阅任何频道；**分片版**只传到槽所在分片的主从节点。
- **订阅方式**：**普通版**支持精确订阅与模式订阅；**分片版**只有精确订阅，无模式订阅。
- **返回值口径**：PUBLISH 的返回值是消息送达的客户端数量，且集群下只统计与发布客户端同节点的订阅者（官方明文）；SPUBLISH 的计数同样限于收到消息的分片节点，两种口径都是抽样视图而非全局统计。
- **版本与兼容**：分片版要求服务端与客户端都支持 7.0 以上，老版本集群只能用普通版并接受全网广播的开销（版本演进详见第 32 章）。
- **选型依据**：订阅者集中在少数槽位选分片版，省总线带宽；跨业务的大范围广播、需要模式匹配选普通版（集群背景详见第 22 章）。

> PUBLISH 返回值的集群口径容易误读：返回 1 不代表全网只有一个订阅者，只代表发布所在节点上有一个——集群排障时不要拿这个数字当全局活跃度。

**速记**：普通版**全网广播带模式**，分片版**槽内转发无模式**。



### 发布订阅的可靠性局限

#### 四大可靠性局限

**Pub/Sub 的投递语义是 at-most-once（至多一次）**：消息从服务端发出后绝无第二次机会——这是官方文档的明文表述，订阅者因错误或断线没能收到，消息就永久丢失。

- **消息不落盘**：消息只沿订阅连接的推送路径流转，不写入键空间、不参与 RDB 与 AOF 持久化（详见第 17、18 章），服务重启后任何历史消息都无法恢复。
- **断线即丢**：订阅者离线期间发布的全部广播，重连后无法找回；发布时刻若一个订阅者都不在线，这条消息无声消失。
- **无 ACK 无消费确认**：服务端不知道订阅者是否收到、是否处理成功，投递质量完全不可度量，也无从重投。
- **堆积无背压**：服务端不为订阅者保存任何待消费列表，消费速度跟不上发布速度时，慢的代价不是延迟而是直接丢失，系统没有任何反压机制提醒生产方减速。
- **服务端零状态**：频道不落盘、无配额、无历史，PUBLISH 返回 0 就意味着这条消息此刻已经蒸发——生产代码应把返回 0 当作告警信号记录。

```text
断线丢消息的时序（示意）：

10:00:00 订阅者断线
10:00:01 PUBLISH order:paid "msg-101"   ──► 订阅者收不到（离线）
10:00:02 PUBLISH order:paid "msg-102"   ──► 订阅者收不到（离线）
10:00:03 订阅者重连并重新 SUBSCRIBE
结果：msg-101 与 msg-102 永久丢失，客户端与服务端都不报任何错误
```

> [!WARNING]
> **警告内容**：把订单状态变更、支付结果通知等不可丢失的消息放进 Pub/Sub 是高危误用——服务重启、网络抖动、消费方短暂离线都会造成静默丢失，且事后完全无法追溯；此类业务必须改用 Stream 消费者组或专业消息队列。

**速记**：**不落盘、断线即丢、无确认、无背压**，四缺注定只做广播。



#### 推送型为什么不可靠、拉取型可弥补

**推送型（push）与拉取型（pull）的分野**：推送型由服务端主动把消息塞给消费者，节奏由生产方决定；拉取型由消费者按自己的能力来取，节奏由消费方决定——Pub/Sub 属于前者，List 阻塞弹出与 Stream 读取属于后者，这一分野直接决定了可靠性上限。

- **推送型的三重困境**：一是速率错配——生产快于消费时只能丢弃（Pub/Sub 的选择），因为服务端没有地方替消费者暂存；二是消费者离线——消息无处安放，错过即错过；三是无确认——推出去就完了，是否送达无从知晓、无从重投。
- **困境的共同根因**：消息不在服务端留存，推送是它抵达消费者的唯一一次机会，任何环节失手都没有第二次。
- **拉取型的弥补**：消费者按能力拉取，忙不过来就少拉，天然形成**背压（backpressure）**；消息留在服务端（Stream 还落盘），配合待确认列表与 ACK，就能把投递语义从至多一次升级为**至少一次（at-least-once）**；消费进度是消费者自己的游标，断线后凭游标续读。
- **官方的对照结论**：Pub/Sub 是至多一次，需要更强投递保证就转向 Stream——Stream 的消息持久化，并同时支持至多一次与至少一次两种语义（命令细节详见第 9 章）。

> [!IMPORTANT]
> **重要内容**：消息模型的可靠性排序由此可推——**推送不留存、弹出即删、留存加确认，一级比一级可靠**。判断一个消息方案能不能托付必达业务，先问消息在服务端留多久、有没有确认机制，再看吞吐与延迟。

```text
推送型与拉取型的信息流对照（示意）：

推送型（Pub/Sub）：
  生产者 ──推送──► 消费者1（被动接收，快慢由生产方定）
  生产者 ──推送──► 消费者2（离线则直接丢，无第二次）

拉取型（Stream）：
  生产者 ──写入──► 流（服务端留存，可落盘）──拉取──► 消费者1（按节奏取）
                                            ──拉取──► 消费者2（忙就少拉，天然背压）
```

> 补充：拉取型并不牺牲实时性——BRPOP 的阻塞弹出与 Stream 的 BLOCK 阻塞读都是「挂着等新消息」，客户端以长轮询获得准实时体验，但消费节奏仍握在消费者手里，这正是推拉结合的常见形态。

> 客户端实现提示：推送消息自带来源（message 带频道名、pmessage 带命中的模式），官方据此建议客户端库用哈希表把订阅绑定到回调函数，收到消息做一次 O(1) 查找即完成分发——这也是各语言客户端订阅 API 的通用实现方式。

**速记**：**推送一次定生死，拉取留存可重来**。



#### 发布订阅的真实定位

**Pub/Sub 的价值在实时通知**：只要业务能接受错过就错过，它就是成本最低的广播通道——Redis 自身的基础设施也大量构建在它之上。

- **Redis 内部通信**：哨兵订阅 +switch-master、+sdown 等频道感知故障判定与主从切换结果（详见第 21 章）；集群的节点事件也在 Pub/Sub 之上传播（详见第 22 章）。
- **实时推送场景**：弹幕、行情报价、聊天室在线名单、配置变更提醒，共同特征是只关心最新状态、允许丢帧。
- **内部取舍**：这类通知是瞬时状态广播——订阅者常驻在线、旧通知过期即无用、无需回放与确认；改用 Stream 反而要引入堆积裁剪与 ACK 管理，复杂度白付。
- **运维侧注意**：订阅关系不持久化，Redis 重启后所有客户端必须自行重连重订阅，客户端库的重订阅逻辑是标配能力；订阅连接须独占专用（RESP2 订阅态命令限制），ioredis 等客户端为此提供订阅专用连接（详见第 30 章）。

> [!IMPORTANT]
> **重要内容**：判断能否使用 Pub/Sub 的唯一标准是**错过一条消息是否可容忍**。可容忍就放心用它换取零存储成本；不可容忍时立即转向 Stream 消费者组或专业消息队列，没有中间地带。

**速记**：内部通知与实时弹幕用它，**错过即放弃**是前提。



### 用 Redis 做消息队列的三种方案

#### 方案一：List 的 LPUSH 加 BRPOP 简单队列

**List 简单队列**：生产者用 LPUSH 入队、消费者用 BRPOP 阻塞出队（List 命令详见第 5 章），两三条命令拼出一个 FIFO 队列，是 Redis 上最古老也最轻量的消息队列方案。

- **基本用法**：LPUSH task-queue job 从左入队，BRPOP task-queue 5 从右阻塞出队、最多等 5 秒，方向相反保证先进先出。
- **天然优点**：阻塞弹出免去轮询空转；多个消费者同时 BRPOP 自动竞争，一条消息只被一人取走，即是负载均衡；出队操作原子，无需加锁。
- **可靠性短板**：弹出即删除，消费者拿到消息后崩溃，任务永久丢失；没有确认、没有重投、没有回放，与 Pub/Sub 同属至多一次语义。
- **笨办法补救**：BRPOPLPUSH 可把弹出的消息同时放进「处理中」备份队列，处理完再删除，崩溃后由巡检进程从备份队列回收——但这套补偿全要业务自建，且 BRPOPLPUSH 自 6.2 起已被 BLMOVE 取代。
- **无广播能力**：一条消息只能被一个消费者取走，需要多端各得一份时 List 无能为力。

```bash
# 生产者：入队
LPUSH task-queue "job:1001"
# 消费者：阻塞出队，最多等 5 秒；弹出即完成，无确认环节
BRPOP task-queue 5
# 可靠化的笨办法：弹出同时写入备份队列，处理完再清理
BRPOPLPUSH task-queue task-queue:processing 5
# 6.2 起的等价新写法：BLMOVE 源队列 目标队列 LEFT RIGHT 超时秒数
BLMOVE task-queue task-queue:processing LEFT RIGHT 5
```

> 辨析：List 队列与 Pub/Sub 的消费范式不同——**BRPOP 是拉取竞争**，一条消息一人得；**PUBLISH 是推送广播**，一条消息人人得。前者适合任务分发，后者适合事件通知，二者都不可靠。

**速记**：**LPUSH 加 BRPOP 两命令成队列**，弹出即删、丢失自负。



#### 方案二：Stream 消费者组的可靠队列

**Stream 消费者组**：Redis 5.0 起内置的可靠消息队列——XADD 追加消息、XREADGROUP 组内竞争消费、XACK 确认销账，消息落盘留存、投递留痕、超时可补偿，官方明确以它提供比 Pub/Sub 更强的投递保证。

- **消息生命周期**：XADD 入流 → XREADGROUP 以大于号投递并写入待确认列表 PEL → 业务处理 → XACK 确认出列；未确认的消息凭 PEL 随时可重取，构成**至少一次**投递。
- **组内竞争、组间广播**：同组内一条消息只分发给一个消费者，天然负载均衡；每个消费者组独立持游标与 PEL，多组各得全量。
- **故障补偿**：消费者宕机后，其名下未确认消息空闲超时，由 XAUTOCLAIM 改判给其他消费者重做，投递次数全程可追溯。
- **堆积管理**：XADD 携带 MAXLEN 近似裁剪，边写边把流控制在阈值内，内存与可靠性的权衡始终可控。
- 以上每一步的命令语法、参数与底层结构（radix tree 加 listpack）**详见第 9 章**，本篇不再展开。

```text
Stream 可靠队列的消息生命周期（示意）：

XADD ──► 流（落盘留存，可回溯）
           │ XREADGROUP 以大于号投递
           ▼
     消费者的 PEL（未确认留痕）
           ├─ 业务处理成功 ──► XACK 确认出列（闭环完成）
           └─ 处理失败或宕机 ──► XAUTOCLAIM 超时改判给其他消费者重做
```

```bash
# 可靠队列的最小骨架（细节详见第 9 章）
XGROUP CREATE orders:pay pay-group 0
XREADGROUP GROUP pay-group consumer-1 COUNT 10 STREAMS orders:pay >
XACK orders:pay pay-group 1727000000000-0
```

> 辨析：Stream 相对 Pub/Sub 补齐的是落盘、确认、堆积三件事，代价是每条消息占用内存、要规划裁剪阈值；只在「必须送达」时付这份代价，能丢的通知仍交给 Pub/Sub。

**速记**：**XADD 入流、XREADGROUP 投递、XACK 销账**，细节全在第 9 章。



#### 方案三：专业消息队列 RabbitMQ 与 Kafka

**专业消息队列**：RabbitMQ、Kafka、RocketMQ 等独立中间件，把消息场景需要的持久化、分区、路由、管理做成了完整产品，是 Redis 方案触顶之后的去处。

- **持久化与堆积**：Kafka 依托磁盘顺序写与零拷贝，消息可保留数天乃至更久，堆积近乎不设限；RabbitMQ 的队列同样可落盘。Redis 方案的数据常驻内存，堆积上限被内存封顶。
- **分区并行**：Kafka 主题可水平划分为多分区、多消费者并行，吞吐随分区扩展，消费者组成员增减自动重平衡；Redis 的 List 与 Stream 都没有分区，单键吞吐受单节点约束（单线程的原理详见第 16 章）。
- **路由与高级语义**：RabbitMQ 的交换机模型支持灵活路由、优先级、死信队列与延迟投递；Kafka 提供事务与幂等生产，逼近精确一次。Redis 方案的路由就是频道名或键名，语义贫瘠。
- **运维与生态**：独立的部署、监控、管理界面与庞大的客户端生态是资产也是负担——多养一个中间件，就多一个故障域与一份学习成本。
- **定位**：海量日志管道、大数据流、需要分区并行与长期保留的场景，直接上专业 MQ，不要用 Redis 硬扛。

> 适用边界：每秒几万条以内、想与缓存同栈部署、消息量可控的业务，Stream 已足够，引入 Kafka 是杀鸡用牛刀；反之日志聚合、用户行为流、跨系统解耦总线这类量级，Redis 的一切队列方案都不合格。

**速记**：**专业 MQ 赢在磁盘堆积与分区并行**，代价是独立运维与一份新故障域。



### 四维对比与选型

#### 四维对比：可靠性、有序性、堆积、重复消费

**四维对比**：把 Pub/Sub、List 队列、Stream 消费组、专业消息队列放在可靠性、有序性、堆积能力、重复消费处理四把尺子上量，结论各归其位。

- **可靠性**：**Pub/Sub** 至多一次，断线即丢；**List** 至多一次，弹出即删；**Stream** 至少一次，PEL 加 XACK 兜底；**专业 MQ** 至少一次起步，可配事务与幂等逼近精确一次。
- **有序性**：**Pub/Sub** 按发布顺序推送但无回溯；**List** 单队列严格 FIFO；**Stream** 单流按 ID 严格有序、跨流无保证；**Kafka** 分区内有序、分区间乱序。
- **堆积能力**：**Pub/Sub** 零堆积；**List** 与 **Stream** 都堆在内存、受内存封顶（Stream 靠裁剪换空间）；**专业 MQ** 堆在磁盘、近乎无限。
- **重复消费处理**：**Pub/Sub** 无投递记录，谈不上重投与去重；**List** 弹出即完成，失败无重试也无重复；**Stream** 与 **专业 MQ** 都因重投必现重复，要求消费端按消息 ID 或业务键做**幂等**。

```text
四维结论速览（示意）：

           可靠性          有序性           堆积            重复消费
Pub/Sub    至多一次        推送有序无回溯    零堆积          无从谈起
List       至多一次        FIFO             内存封顶        无重试
Stream     至少一次        单流严格有序      内存加裁剪      需幂等
专业 MQ    至少一次起步    分区内有序        磁盘近无限      需幂等/去重
```

> 至少一次与重复消费是一体两面：只要服务端留存消息并支持重投，消费者崩溃重启后就必然收到重复消息——幂等不是某个方案的补丁，而是所有可靠队列的共同前提，Redis 的 Stream 与 Kafka 皆然。

**速记**：**可靠性看留存与确认，堆积看内存还是磁盘，重复消费一律靠幂等**。



#### 选型建议与决策链

**选型的分水岭是可靠性与吞吐**：先用三问定方案——能不能丢、量有多大、愿不愿意为吞吐引入独立组件，三问答完方案自然浮现。

- **通知广播**：弹幕、行情、事件提醒，错过一条可容忍——选 **Pub/Sub**，零存储成本、接上就用；集群内订阅者集中在少数槽位时选 7.0 的**分片版**。
- **可靠任务**：订单、支付等必达任务，需要确认与重试，量级中低——选 **Stream 消费者组**，与缓存同栈部署，运维负担最小（命令细节详见第 9 章）。
- **海量吞吐**：日志管道、大数据流、长期保留、分区并行——选 **Kafka、RocketMQ 等专业消息队列**，不要用 Redis 硬扛。
- **轻量可丢**：允许丢失、追求最简的任务分发（缓存刷新、临时标记）——**List 的 LPUSH 加 BRPOP** 依然够用。
- **组合使用也常见**：同一业务里用 Pub/Sub 推实时行情、用 Stream 派发交易任务，二者分工互补而非互斥。
- **迁移路径**：从 Pub/Sub 迁往 Stream 时，发布端把 PUBLISH 换成 XADD，订阅端改造成消费者组循环（先收旧账再取新消息），改动面很小。
- **衍生需求**：延迟任务可用 ZSet 以 score 存到期时间、由轮询方到期再投递实现（ZSet 详见第 7 章）；优先级、死信、事务消息等高级语义 Redis 方案普遍缺位，这类需求成规模出现就是转向专业 MQ 的信号。

> [!TIP]
> **建议内容**：给决策加一道反向检查——发现必达业务跑在 Pub/Sub 上、或海量日志压在 Stream 里，都属于误配，前者迟早丢消息、后者迟早爆内存；按三问重新对号入座即可。

**速记**：**广播用 Pub/Sub，可靠用 Stream，海量上专业 MQ，轻量随手 List**。
