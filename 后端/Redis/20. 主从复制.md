## 主从复制

**主从复制**：是 Redis 把主节点（master）的数据实时同步到一个或多个从节点（replica）的机制，是 Redis 实现高可用与横向扩展的基石。

- 本章先讲基本形态：复制的定义与价值、读写分离与级联拓扑、从库只读约束。
- 再讲建立方式：replicaof 配置与 REPLICAOF 命令、masterauth 鉴权、slaveof 到 replicaof 的名称演进。
- 然后讲同步的两条路径：全量复制的完整流程与开销，部分复制的三要素与积压缓冲区调优。
- 接着讲常态与保障：命令传播、每秒一次的 REPLCONF ACK 心跳与 min-replicas 写安全。
- 最后讲工程细节与边界：无盘复制、主从延迟与不一致窗口、复制风暴、过期键的 DEL 传播。
- 主从复制是哨兵（详见第 21 章）与集群（详见第 22 章）共同依赖的底层能力，理解本章是理解后续两章的前提。

### 主从复制的认识

#### 主从复制的定义与价值

**主从复制**：是 Redis 把主节点（master）的数据实时同步到一个或多个从节点（replica）的机制，是 Redis 实现高可用与横向扩展的基石。

- 复制方向为**单向**：数据只从主节点流向从节点，写入入口收敛在主节点一处。
- 主节点承担**全部写操作**，从节点通过回放主节点的写命令获得相同的数据集。
- 复制是**异步**进行的：主节点执行写命令后立即返回，不等待从节点确认。
- 从节点首次接入时走全量同步，之后进入命令传播阶段持续增量同步。
- 从节点可随时增减：扩容读能力只需加一台机器挂到主库，下线读能力只需摘除一个从库。
- 从库的挂载与摘除都是在线操作，读写能力的扩缩容不需要停止主库服务。
- 主从复制是哨兵（详见第 21 章）与集群（详见第 22 章）共同依赖的底层能力。
- 主库也可以有多台：按业务拆分主库，每台主库再各自带从库，这是复制与分片结合的常见形态。

单机 Redis 面临三重瓶颈：内存容量有上限、读请求集中、进程或机器故障即服务中断。主从复制从架构上同时回应了这三个问题——数据有副本、读可分流、故障可切换；后两者正是读写分离与故障转移的前提。

主从复制解决的是可用性与读扩展，不解决写扩展：所有写仍然集中在主库，写入瓶颈要靠集群分片（详见第 22 章）把数据拆到多台主库上。同一份数据在主从之间是完整副本，在集群分片之间是互不重叠的子集，这是两种扩展方式的本质区别。

复制的单位是命令流而不是数据文件：主从之间传递的是写命令序列，从库通过回放命令重建数据集。这一设计决定了复制的所有行为特征——增量小、可断点续传、但依赖命令的可重放性。

> 主从复制与持久化互相独立：即使主节点关闭了 RDB 与 AOF（详见第 17、18 章），复制仍然可以正常工作；但从节点在全量同步时会清空并重建数据，持久化关闭的实例一旦重启，只能依赖主节点重新同步数据。

> 复制链路本身也走网络：主从跨机房部署时，命令传播延迟与带宽成本都会显著上升，主从应尽量部署在同机房或同城低延迟链路之内。

**速记**：主写从读、异步单向；复制是高可用与读写分离的**共同地基**。



#### 读写分离、数据冗余与从库只读

**架构价值**：主从复制同时带来**读写分离、数据冗余、故障恢复基础**三重收益，从库只读则是读写分离得以成立的约束条件。

- **读写分离**：读多写少的业务把读流量分摊到多个从库，主库专注写入，整体吞吐随从库数量横向提升。
- **数据冗余**：每个从库都持有全量数据副本，单机故障不再意味着数据全失。
- **故障恢复的基础**：主库宕机后，可把数据最新的从库提升为新主库继续对外服务。
- **从库只读**：配置项 replica-read-only 默认为 yes，从库拒绝一切写命令，保证复制拓扑中数据入口唯一。
- 从库还可以承接耗时的键扫描、触发持久化等重负载操作，把它们从主库剥离出去。
- 读路由通常在应用层或代理层按命令类型实现：写命令发主库，读命令按权重散到从库。
- 数据冗余的副本数等于从库数量，生产环境至少一主一从，重要数据一主两从。
- 从库也可按业务拆分：不同从库服务不同读业务，实现故障隔离与流量隔离的双重收益。

读写分离的落地要点是把读流量按数据新旧敏感度分层：能容忍滞后的统计、列表、详情页走从库；余额、库存等强一致读必须回主库。承接扫描与持久化的从库应选择硬件对等的机器，避免中间层成为级联复制的瓶颈。

从库数量并非越多越好：每个从库都消耗主库的输出缓冲与带宽，从库过多时主库反而成为复制瓶颈；读能力的横向扩展与复制成本必须放在一起核算。

判定一个从库是否可安全下线，看它的读流量是否已有承接方：有代理层的可直接摘除，应用直连的则要先改路由再摘库，顺序颠倒会造成读错误。

> [!NOTE]
> **提醒内容**：replica-read-only 的默认值就是 yes，从库天生只读；若显式改为 no 允许从库写入，本地改动不会反向同步给主库，且会在下一次全量同步时被整体清空，属于高危配置。

> 读写分离的流量比例要与业务真实读写比匹配：读占九成的业务从从库分流收益最大，读写各半的业务收益有限，此时应优先优化写入本身而不是加从库。

**速记**：**读分流、存副本、可晋升**；replica-read-only 守住写入口唯一。



#### 一主多从与级联复制结构

**拓扑结构**：主从复制支持**一主多从**与**级联复制**两种基本拓扑，后者也称主从从结构。

- 一主多从：所有从库直接从主库复制，路径短、延迟一致，是最常见的部署形态。
- 级联复制：从库 A 再挂载从库 A1 与 A2，A 同时扮演上游的从库与下游的主库。
- 级联结构中，中间节点先接收并回放上游数据，再以自己的复制流向下游转发。
- 两种拓扑可混用：主库带几个直接从库，直接从库再各带一批叶子从库。
- 拓扑深度越大，末端数据越滞后，故障的影响面也随节点位置而变化。
- 叶子从库故障只影响自己所在分支，直接从库故障则会中断其全部下游节点。
- 级联结构中更换中间层节点，需要其全部下游改挂，影响面大于叶子节点故障。
- 哨兵与集群在内部同样大量使用级联思想来分摊复制带宽（详见第 21、22 章）。

```text
一主多从：                        级联复制（主-从-从）：

        ┌── replica A                  master
        │                                │
master ─┼── replica B       ┌───────────┼───────────┐
        │                 replica A    replica B   replica C
        └── replica C        │
                             ├── replica A1
                             └── replica A2
```

拓扑选型没有绝对优劣：从库数量少、一致性要求高时用一主多从；从库数量多、读压力分散在多地时用级联，用中间层挡住主库的复制带宽。无论哪种拓扑，主库都只有数据入口一个身份，下游节点只读不写。

级联深度一般控制在两到三层：一层中间节点已能挡住大部分叶子接入，再深下去延迟叠加与运维复杂度都不划算。混用拓扑时，哨兵对中间层节点同样按从库监控，故障转移的链条会更长（详见第 21 章）。

中间层节点自身的硬件应当更强：它既回放上游命令，又向下游转发复制流，还承接读请求，负载是普通从库的数倍；中间层一旦成为瓶颈，其下游所有节点的延迟同时恶化。

复制拓扑的可见性靠 ROLE 与 INFO 维护：每个节点都能说清自己是哪台的主库、哪台的从库，巡检脚本应定期比对全网拓扑与预期拓扑，发现私自挂载或失联节点。

> 级联结构的代价是一致性延迟逐层叠加：数据先到中间层再到叶子层，最深处从库的滞后等于各层滞后之和；对数据新旧敏感的读请求应尽量落在直接从库上，叶子节点只承接可容忍延迟的只读业务。

**速记**：一主多从**路径短、延迟齐**；级联层层分担带宽，**延迟逐层叠加**。



### 建立复制的方式

#### 配置文件与启动参数建立复制

**静态建立**：在实例启动阶段通过**配置文件**或**启动参数**指定主库地址，是最稳定的建立复制方式。

- 配置文件方式：在 redis.conf 中写入 replicaof 主库地址 端口，从库每次重启都会自动连接主库。
- 启动参数方式：redis-server 启动时携带 --replicaof 主库地址 端口，效果与配置文件完全等价。
- 主库若开启 requirepass，从库必须配置 masterauth 指向主库密码，否则复制握手持续失败。
- 从库可继续保留自己的 requirepass 供客户端连接，两个密码互不相干。
- 常用配套配置还有 repl-timeout（复制超时）与 replica-serve-stale-data（同步期间是否继续应答旧数据）。
- 一台实例既可作从库也可作别库的主库，身份由配置与命令动态决定，级联结构正由此而来。
- 主库侧也有复制相关配置，如 min-replicas-to-write 与 repl-disable-tcp-nodelay，按需启用。
- 哨兵托管的部署里，配置文件中的 replicaof 只是初始拓扑，故障转移后由哨兵改写（详见第 21 章）。

静态方式的优点是拓扑随配置固化，重启不丢；缺点是调整主库必须改配置并重启实例，灵活性不如运行期命令。初次搭建只需关注 replicaof 与 masterauth 两项，其余参数遇到超时、状态异常等具体问题时再按需调整，避免一次性堆满配置却不知各项含义。

配置生效的时机也需要留意：replicaof 等拓扑项在重启或执行命令时生效，部分行为项需要重启才生效，改配置前应查对应版本文档确认生效方式，避免误以为已生效。

```bash
# 方式一：redis.conf
replicaof 192.168.1.10 6379
masterauth yourMasterPassword   # 主库开启 requirepass 时必配
replica-read-only yes           # 从库只读（默认值）
replica-serve-stale-data yes    # 首次同步期间继续用旧数据应答（默认值）
replica-lazy-flush yes          # 全量同步清库时异步删除旧数据，减少阻塞
repl-timeout 60                 # 复制超时（秒）
repl-ping-replica-period 10     # 主库向从库发 PING 的间隔（秒）

# 方式二：启动参数
redis-server --port 6380 --replicaof 192.168.1.10 6379
```

> masterauth 配置的是主库的密码而非从库自身的密码；从库连主库同样要走完整认证流程，密码不对时会反复重连并在日志中刷出权限错误，这是主从搭建失败最常见的原因。

**速记**：**replicaof 指主库**，主库有密码就配 **masterauth**。



#### REPLICAOF 命令动态建立与解除复制

**REPLICAOF 命令**：是运行期动态建立或解除复制关系的客户端命令，无需重启实例即可改写复制拓扑。

- 建立复制：执行 REPLICAOF 192.168.1.10 6379，实例立刻转为从库并开始同步。
- 解除复制：执行 REPLICAOF NO ONE，实例就地脱离主库成为独立主库，本地数据保留。
- 更换主库：直接执行指向新主库的 REPLICAOF，旧数据被清空后按新主库重新同步。
- 切换主库会清空本地数据，执行前应确认目标主库的数据是权威数据。
- 权限控制：该命令直接改写拓扑，生产上应通过 ACL 或 rename-command 限制普通用户执行。
- REPLICAOF 也可用于把实例临时挂到测试主库取数，用完立即 REPLICAOF NO ONE 脱离。

动态方式的典型用法是手工故障转移与演练：平时用它调整拓扑做迁移或压测，故障时把数据最新的从库提升为主库。由于其效果立竿见影，也常被误用——在错误节点上执行 REPLICAOF 指向错误的主库，等于人为制造一次数据清空。

演练价值同样突出：借 REPLICAOF 可以在测试环境反复模拟主从切换、级联挂载、断线重连，把本章其余考点的行为逐项验证一遍，是理解复制机制最快的实验入口。

```bash
# 建立复制
127.0.0.1:6380> REPLICAOF 192.168.1.10 6379
OK

# 解除复制，就地晋升为独立主库（数据保留）
127.0.0.1:6380> REPLICAOF NO ONE
OK

# 生产上可用 rename-command 置空高危命令，防止误操作改写拓扑
rename-command REPLICAOF ""
```

> [!CAUTION]
> **注意内容**：主从切换后复制身份必然改变——新主库拥有新的 replid，其余从库改挂过来时 replid 不匹配，只能走全量复制。因此无论手工执行 REPLICAOF NO ONE，还是哨兵自动切换（详见第 21 章），切换后所有从库都要与新主库重新同步，数据量大时这是一次可感知的抖动。

**速记**：挂主用 **REPLICAOF 地址 端口**，升主用 **REPLICAOF NO ONE**；一换主库就是一次全量。



#### 从 slaveof 到 replicaof 的命令名演进

**命令名演进**：Redis 5.0 起，**replicaof** 正式替代 **slaveof** 成为复制相关命令与配置的标准名称。

- slaveof 是 2.8 至 4.x 时代的旧命令名，5.0 起标记为废弃，仅为兼容保留，行为与 replicaof 完全一致。
- 配置项同步改名：slaveof 改为 replicaof，slave-read-only 改为 replica-read-only。
- 术语层面：官方文档把 slave 统一改为 replica，INFO 输出中复制相关字段也在版本演进中逐步向 replica 靠拢。
- 阅读旧版教程与运维脚本时，slaveof 可直接按 replicaof 理解；新写的配置与脚本应统一使用新名称。
- 跨版本工具应同时兼容两套命令名：先探测实例版本，再决定下发哪个命令。
- INFO 输出中的角色字段与从库列表字段的命名随版本调整，解析脚本不应写死字段名。
- ROLE 命令返回的字段含义跨版本稳定，是脚本判断复制角色的可靠入口。

改名背后的动机是术语去歧视化：slave 一词在社区长期被质疑不当，5.0 完成命令与配置层面的更名，后续版本再逐步清理 INFO 字段与日志用语。运维脚本从旧版本迁移到新版本时，命令名替换是必查项。

旧名称的残留不会在短期内消失：老版本实例、第三方教程、监控脚本里仍会大量出现 slaveof 与 slave 字样。团队应统一内部术语表，注明新旧对应关系，避免沟通与排障时的歧义。

对正在编写监控或部署工具的场景，建议把名称兼容做成独立适配层：输入统一用 replica 术语，输出前按实例版本转换，业务逻辑只写一份。

版本升级检查还应覆盖第三方依赖：旧版客户端库、连接池、管理面板可能仍按旧字段解析 INFO，升级主从相关版本前应逐一验证这些组件的兼容性。

> 在 5.0 之前的实例上执行 replicaof 会报未知命令错误，此时只能使用 slaveof；反之新版本实例两者都能执行。排查老环境问题时，先确认版本再对号入座。

**速记**：5.0 起 **slaveof 让位 replicaof**，只换名字、不换行为。



### 全量复制

#### 全量复制的完整流程

**全量复制**：是从节点首次接入或无法增量续传时，主库把**全部数据以 RDB 形式整体同步**的复制方式，是所有复制路径中最重的一条。

- 第一步：从节点发送 PSYNC ? -1，问号表示自己没有复制历史、给不出复制 ID，-1 表示偏移量未知。
- 第二步：主节点回复 FULLRESYNC replid offset，把本次复制要用的复制 ID 与当前偏移量交给从节点。
- 第三步：主节点执行 BGSAVE 在后台生成 RDB 快照（详见第 17 章），此期间到达的新写命令暂存进该从节点专属的复制缓冲区。
- 第四步：主节点把 RDB 文件传输给从节点，传输期间新写命令持续进入缓冲区。
- 第五步：从节点清空自身旧数据，载入收到的 RDB。
- 第六步：主节点把缓冲区内积压的写命令补发给从节点，完成后进入命令传播阶段。
- 补发完成后主从偏移量对齐，双方各自继续按传播与回放推进，无缝衔接。

六步里最容易被忽略的是缓冲区的角色：BGSAVE 与传输 RDB 期间主库的写入并没有停，它们全部暂存在为该从库分配的输出缓冲区里，等 RDB 载入完成后一次性补发；缓冲区受 client-output-buffer-limit replica 配置约束，积压超过硬限制或持续超出软限制，主库都会强制断开从库，复制从头再来。

全量总耗时由三段组成：BGSAVE 生成快照的时间、网络传输 RDB 的时间、从库清库与载入的时间。数据集越大，三段同比拉长，估算复制窗口时应把三段相加，而不是只算传输一段。

主库为每个从库维护独立的复制状态：处于哪个阶段、缓冲区积压多少、RDB 发送进度如何，都按从库逐一记录、互不干扰，因此多从库并发的全量与增量可以在同一主库上交错进行。

主从双方的握手远早于同步本身：从库先与主库建立 TCP 连接，发送 PING 确认可达，再 REPLCONF 上报端口与能力，最后才发出 PSYNC；握手序列中任何一步失败，都会回到重连状态重新开始。

```text
从节点                                主节点
   │  ① PSYNC ? -1                     │
   │ ────────────────────────────────► │
   │  ② FULLRESYNC <replid> <offset>   │
   │ ◄──────────────────────────────── │
   │                  ③ BGSAVE 生成 RDB
   │                     期间新写命令进入复制缓冲区
   │  ④ 传输 RDB 文件                   │
   │ ◄──────────────────────────────── │
   │  ⑤ 清空旧数据，载入 RDB             │
   │  ⑥ 补发缓冲区内积压的写命令          │
   │ ◄──────────────────────────────── │
   │  之后进入命令传播阶段，持续接收写命令  │
```

> 从节点载入 RDB 前会清空自身全部旧数据，把一个存有业务数据的实例改挂到新主库，等于主动放弃本地数据；BGSAVE 依靠写时复制在不停服的情况下完成快照，其内存峰值问题详见第 17 章。

**速记**：全量六步——**握手、回执、BGSAVE、传 RDB、清库载入、补发缓冲**。



#### 全量复制的开销与触发场景

**触发场景**：全量复制本是兜底手段，但多个常见场景都会触发它，是主从架构最大的性能负担来源。

- 首次接入：新从库没有复制历史，必然走一次全量。
- 断线重连失效：从库断线过久，偏移量已不在积压缓冲区内，无法续传，退化为全量。
- 主库重启：主库重启后 replid 更新，所有从库检测到身份不一致，全部触发全量。
- 主从切换：新主库拥有新 replid，其余从库改挂后同样只能全量。
- 从库载入 RDB 期间不对外服务，全量窗口内该从库的读能力整体暂缺。
- 数据集中存在大键时，RDB 生成与载入都会变慢，大键治理同样惠及复制（详见第 29 章）。
- 主从切换引发的全量是计划外成本最高的场景：切换本身已在故障期，全量会进一步延长整体恢复时间。
- 开销四笔账：BGSAVE 的 CPU 与写时复制的内存峰值、RDB 传输占用的网络带宽、从库清库载入期间的服务阻塞、复制缓冲区积压命令推高的主库内存。

定量感受一次全量的代价：一个 10 GB 的数据集，BGSAVE 可能占用数十秒 CPU 与额外数 GB 内存，RDB 在千兆内网上传输也要一两分钟，期间从库不可用、主库缓冲区持续增长。数据集越大、从库越多，这套账单翻的倍数越多。

判断一笔全量是否可承受，关键看三个比值：数据集大小与主库内存的比、快照与传输时间内写入增量与缓冲区大小的比、RDB 传输带宽与业务带宽的比。三个比值都在安全范围内，全量只是慢；任何一个失控，全量就会演变成事故。

压缩全量成本的方向有三个：缩小数据集（拆分实例、清理冷数据，详见第 14 章）、提高传输带宽（万兆网卡、就近部署）、缩短载入时间（更快的从库磁盘与内存），三者都比事后救火便宜。

> 从库越多、数据集越大，一次全量的时间窗越长；窗口越长，主库缓冲区积压越多。高写入速率下，一次全量可能演变为内存压力与再次断线的连锁反应，主库内存吃紧时还会触发内存淘汰（详见第 15 章）。

> 触发场景与开销要连起来记：四种触发场景里只有首次接入是计划内的，其余三种都发生在故障或变更期——这正是全量复制最需要被预案覆盖的原因。

**速记**：**首次、断线超窗、主重启、切主**四种场景必全量；开销算 **CPU、内存、带宽、阻塞** 四笔账。



### 部分复制

#### 部分复制的三要素

**部分复制**：从库断线重连后，若条件满足，只补传**断线期间缺失的写命令**而非全量数据的复制方式，由 Redis 2.8 引入。

- **复制偏移量（offset）**：主库每传播一个字节的写命令就递增一次；从库上报自己的偏移量即暴露复制进度，两个偏移量之差就是待补传的字节数。
- **复制积压缓冲区（repl_backlog）**：主库在内存中维护的固定大小环形缓冲区，保存最近一段时间传播过的写命令流，是断线期间缺失命令的唯一来源。
- **复制 ID（replid）**：主库的身份标识。2.8 引入 PSYNC 时称 runid（运行 ID），4.0 的 PSYNC2 改进后演化为 replid，并新增 replid2 记录上一个主库的身份，以支持故障切换后的部分重同步。
- replid 长度固定为 40 个十六进制字符，与 2.8 时代的 runid 同构，只是语义与用法在 PSYNC2 中得到增强。
- 三者缺一不可：replid 匹配证明主库身份没变，offset 落在缓冲区内证明缺口可补，缓冲区提供补传的内容本身。
- 从库通过 REPLCONF 命令族与主库交换能力信息，端口、密钥、监听 IP 都在握手期上报。

偏移量是理解三要素的钥匙：主库与所有从库共享同一条命令流，主库偏移量代表已传播到哪，从库偏移量代表已复制到哪，积压缓冲区按偏移量区间保存最近的命令流。断线重连时，从库只需说清我是谁（replid）、我到哪了（offset），主库就能判断缺口是否还补得上。

举例说明续传判定：积压缓冲区 1 GB，主库偏移量已走到 3 GB，从库断线前复制到 2.2 GB，缺口 0.8 GB 未被覆盖，重连可续传；若从库断线前只复制到 1.9 GB，缺口 1.1 GB 已超出缓冲区保存范围，只能退回全量。

从节点视角同样存在三份状态：它记住主库的 replid 与自己已复制到的 offset，断线期间这两份状态原样保留，重连时用于发起 PSYNC；状态什么时候被覆盖、什么时候清空，直接决定下一次同步的形态。

> 主库每次重启都会生成新的 replid，即便数据完全相同，从库也会因身份对不上而全量复制；这是复制机制以简单换可靠的设计取舍，4.0 之前的版本尤其如此。

**速记**：三要素——**offset 记进度、backlog 存缺口、replid 验身份**。



#### PSYNC 命令的判断逻辑

**PSYNC 命令**：从库发起同步的入口命令，完整形式为 PSYNC replid offset，主库据此在**部分重同步与全量复制**之间做裁决。

- 首次同步：从库没有复制历史，发送 PSYNC ? -1。
- 断线重连：从库发送 PSYNC 自己记住的 replid 与已复制到的 offset。
- 判定部分重同步：主库校验 replid 与自身一致，且 offset 之后的数据仍在积压缓冲区内，回复 +CONTINUE，仅补发缺口。
- 判定全量复制：replid 不匹配，或 offset 对应的数据已被环形覆盖，主库回复 +FULLRESYNC，转入全量流程。
- 从库会把 replid 与 offset 持续记在内存中，断线期间不丢失，重连时原样上送。
- 判定顺序不可颠倒：先验身份再验缺口，身份都对不上时检查偏移量毫无意义。

一个边界情况：从库上报的偏移量恰好等于主库当前偏移量，说明断线期间没有新写入，主库回复 +CONTINUE 但不补发任何命令，双方直接恢复命令传播；这仍是部分重同步，只是缺口为零。

PSYNC 的判定由主库单方面完成，从库只能接受结果：收到 +CONTINUE 就进入补传等待，收到 +FULLRESYNC 就清空本地数据准备接收 RDB，从库没有讨价还价的余地，这保证了主库作为裁决者的唯一权威。

性能上部分复制的补传开销与缺口大小成正比：缺口几 MB，重连在毫秒级完成；缺口几百 MB，补传也要占用数秒带宽，但仍远优于同量级的全量复制。

```text
从库发送 PSYNC <replid> <offset>
        │
        ├── replid 匹配，且 offset 之后的数据仍在积压缓冲区内
        │        └──► 回复 +CONTINUE，补发缺口命令（部分复制）
        │
        └── replid 不匹配，或 offset 已被环形覆盖
                 └──► 回复 +FULLRESYNC，转入全量复制流程
```

```bash
# 首次同步：无历史，用问号与 -1 占位
PSYNC ? -1
# 主库回复全量同步，并给出 replid 与当前偏移量
+FULLRESYNC 516d3b48c1e5a8ef5b0d0b0b 13724551

# 断线重连：带上记住的身份与进度
PSYNC 516d3b48c1e5a8ef5b0d0b0b 13724500
# 身份匹配且缺口仍在缓冲区内，只补差量
+CONTINUE
```

> 2.8 之前只有 SYNC 命令：无论断线多久，重连一律全量复制，这是老版本主从架构最大的痛点；PSYNC 把重连成本从全量降为增量。4.0 的 PSYNC2 进一步放宽条件，让故障切换后从库与新主库之间也有机会部分重同步。

> 从库侧也有一套复制状态机，从连接主库、握手、认证到发送 PSYNC 逐级推进，日志会记录每次状态推进与失败原因；排查从库连不上主库时，按日志逐段核对即可。

**速记**：**对得上、没被覆盖就 CONTINUE；对不上或被覆盖就 FULLRESYNC**。



#### 复制积压缓冲区的容量调优

**容量调优**：配置项 repl-backlog-size 决定部分复制的容错窗口，其默认值 1 MiB 在生产环境几乎必然偏小。

- 估算公式：缓冲区大小 ≥ 平均写入速率（MB/s） 乘以 预期容忍的断线时长（s），再留一倍余量。
- 写入速率越高，环形覆盖越快，同样容量下可容忍的断线窗口按比例缩短，估算必须按峰值速率。
- 修改该值后主库会重建缓冲区并断开所有从库，触发一轮全量复制，应在业务低峰执行。
- 积压缓冲区只存在于主库内存中，重启后重建，不需要也不应该持久化。
- 多主多从的大集群里，每个主库各有一份积压缓冲区，容量规划要按主库逐个计算而不是按集群总量。
- 内存预算紧张时，宁可缩短容忍时长，也不要让缓冲区挤占数据集的工作内存。
- repl-backlog-ttl 过短会在从库短暂全部断开时立刻释放缓冲区，重连反而退化为全量。
- Redis 7.0 起积压缓冲区在同一主库的多个从库间共享，且在无从库时可释放内存，调整的内存代价明显降低。

估算示例：业务峰值写入 20 MB/s，运维要求容忍 2 分钟的网络抖动，缓冲区至少 2400 MB，取整配置 3 GB；若主库内存吃紧，就应反过来压缩容忍时长或降低写入批量，而不是硬扛一个超出内存规划的缓冲区。

估算结果要落到监控上验证：对比主库偏移量的增长速率与配置的缓冲区大小，可以算出真实的可容忍断线时长；该值应大于历史上出现过的最长抖动，并保留余量应对未来的写入增长。

缓冲区本质是一份用内存换容错的开销：容量给足，断线是小事；容量不足，断线是全量。它的价值不在平时，而在网络故障的那一刻一次性兑现，这正是它容易被低估的原因。

```bash
# redis.conf
repl-backlog-size 1gb          # 默认 1mb，生产环境必调
repl-backlog-ttl 3600          # 主库失去所有从库后，缓冲区保留的秒数
# 估算：平均写入速率（MB/s） × 预期容忍断线时长（s），再留余量
```

> [!WARNING]
> **警告内容**：缓冲区过小的典型症状是每次网络抖动都演变为全量复制——从库明明只断线几十秒，重连却触发 BGSAVE 与 RDB 传输，主库 CPU、带宽、内存同时抖动，业务读写全面变慢。线上主库应按峰值写入速率估算容量，一般不低于数百 MB。

**速记**：容量 = **写入速率 × 断线容忍时长**；默认 1 MiB 只够测试环境。



### 命令传播与心跳维持

#### 命令传播阶段的持续同步

**命令传播**：初次同步完成后，主库通过**长连接把每一条写命令实时转发**给从库，使双方数据持续趋同，这是复制关系的常态阶段。

- 主库执行完一条写命令，将其按协议追加发送给所有从库，同时写入积压缓冲区。
- 传播是**异步、尽力而为**的：主库不等从库确认即继续处理后续命令。
- 从库收到命令后回放本地数据集，并推进自己的复制偏移量。
- 连接断开期间主库照常写入，缺口由积压缓冲区兜底，重连后按 PSYNC 逻辑续传或全量。
- 命令传播与心跳共用同一条长连接，这条链路既是数据通道，也是状态通道。
- 传播是逐从库独立进行的：某个从库接收慢不影响其他从库，也不阻塞主库执行命令。
- 从库回放命令同样消耗 CPU 与内存，大量从库把主库的写入压力分摊到各自机器。
- 主库重启或拓扑变更后，命令传播要从新的全量同步重新开始，不存在跨越身份的续传。
- 传播与回放的耗时差即主从延迟的最小构成：网络往返与从库性能各占一部分。

传播协议就是 RESP 协议的命令流：主库把写命令原样序列化后追加到复制连接上，从库按同样的协议解析回放，与客户端和服务端之间的通信协议完全一致，因此抓包分析复制流量不需要额外的知识储备。

从库回放命令与主库执行命令共用同一套引擎，主库上所有会改变数据集的行为——写、删、主动过期删除、内存淘汰删除——最终都以命令形式传播到从库，从库侧的过期与淘汰行为详见第 14、15 章。

主库在传播阶段并不合并命令：同一键的连续修改仍逐条发送，因此写放大模式下复制流量与写入量成正比，批量写入命令对降低复制流量有直接收益。

```text
主库执行 SET a 1
   ├──► 复制连接 A：命令流发给从库 A（offset 推进）
   ├──► 复制连接 B：命令流发给从库 B（offset 推进）
   └──► 积压缓冲区：环形追加（供断线重连补传）
```

> 只有写命令会被传播，读命令不会；从库默认只读，应用向从库写会直接报错。传播的异步性决定了从库永远略落后于主库，落后的程度即主从延迟问题。

**速记**：同步只是起点，**常态靠命令传播**：异步推、不断流，缺口由积压缓冲兜底。



#### 心跳检测 REPLCONF ACK 与丢包补偿

**心跳机制**：从库每秒向主库发送一次 REPLCONF ACK offset 命令上报偏移量，同时承担探测与补偿职能。

- 上报进度：从库把复制偏移量告知主库，主库据此掌握每个从库的落后程度。
- 补偿丢包：主库对比从库上报的偏移量与自己已传播的偏移量，发现区间缺失立即补发，即使连接未断也能修复丢包。
- 探活：主库在 repl-timeout 内收不到某从库的心跳即判定连接异常；从库同样以超时判断主库失联。
- 辅助选主：哨兵依据各从库上报的偏移量判断数据新旧，优先晋升落后最少的从库（详见第 21 章）。
- 心跳也是开销：每从库每秒一条 ACK，数量不大但不可忽略，repl-timeout 应远大于心跳间隔。
- repl-timeout 应同时覆盖全量传输场景，否则大 RDB 传输超时会反复打断复制。
- 心跳与命令传播共用连接：心跳恢复的那一刻，缺口补发与命令传播立即在同一连接上继续。
- 写安全：主库可配置 min-replicas-to-write 与 min-replicas-max-lag（Redis 2.8 起支持），当在线从库数少于 N 或从库落后超过 M 秒时，主库拒绝写入并返回错误，防止网络分区中主库在无备份的情况下继续接收写入。
- 写安全默认关闭（min-replicas-to-write 默认 0），官方定位是尽力而为的安全机制：只把可能丢失的写入窗口从无界压到有界，不构成强一致。

```bash
# 从库每秒自动上报（示意）
REPLCONF ACK 13724551
# 主库比对偏移量，发现落后即补发缺失区间的写命令
```

输出中的 lag 字段是心跳间隔的直接体现：主库记录最近一次收到某从库心跳过去了多少秒，lag 持续增大说明链路质量恶化。字段命名随版本演进有所调整，以对应版本的官方文档为准。

从库侧的 INFO replication 则能看到 master_link_status 与 master_last_io_seconds_ago 等字段，分别表示复制链路状态与最近一次收到主库消息的秒数，是排查从库侧断连问题的第一入口。

心跳频率与超时的组合应经过演练验证：人为断开从库网络，观察主库多久剔除该从库记录、恢复后多久补齐缺口，把理论窗口校准成实测值。

> [!CAUTION]
> **注意内容**：开启 min-replicas 写安全后，主从之间网络抖动或从库维护窗口会直接导致主库拒绝写入，读命令不受影响；对可用性优先的缓存场景，这可能比丢数据更难接受，开启前应确认业务能容忍写失败。

> 心跳机制在哨兵时代还有一层延伸：哨兵通过向从库发送 INFO 命令获取其复制状态，本质上是复用同一份状态数据的另一条观察路径（详见第 21 章）。

**速记**：**REPLCONF ACK 一秒一报**：报进度、补丢包、探存活，哨兵选主也看它。



### 进阶场景与运维实践

#### 无盘复制 repl-diskless-sync

**无盘复制**：主库生成 RDB 后**不落盘，直接经网络套接字边生成边发送**给从库的复制模式，由 repl-diskless-sync 配置开启。

- 常规模式：BGSAVE 先把 RDB 完整写入磁盘，再从磁盘读出发送，快照落盘可复用，也可兼作备份。
- 无盘模式：复用 BGSAVE 的写时复制机制，把快照数据直接写进从库的网络连接，省去一次磁盘写入与读取。
- 参数 repl-diskless-sync-delay 让主库在开始传输前等待数秒，使同时接入的多个从库共享同一次无盘快照。
- repl-diskless-sync-delay 等待窗口内新接入的从库会并入同一次快照，超窗接入的从库另起一轮。
- 适用场景：云盘或虚拟机等磁盘较慢、内存充裕、而全量复制又频繁发生的实例。
- 代价：快照期间对内存峰值的要求更高，且不再顺带产出可归档的 RDB 文件。
- 从库侧行为不变：仍把收到的字节流写成本地临时文件再载入，从库磁盘不能省。
- 无盘传输对主库网络出口压力更集中，万兆内网是开启前的基线条件。

无盘模式下主库侧只剩网络发送，主库磁盘慢不再是全量复制的瓶颈；但主库内存要同时承受写时复制与网络发送缓冲的压力，容量规划需按全量期间的最坏情况估计。

无盘与落盘的选择还要考虑备份策略：开启无盘后主库不再顺带产出 RDB，若同时关闭了自动持久化，全量复制期间就完全没有任何快照落盘；依赖 RDB 做备份的部署应保持落盘模式，或另设定时 BGSAVE（详见第 17 章）。

无盘模式对从库数量的敏感度更高：一次快照服务多个从库时网络是共享瓶颈，接入的从库越多，每个从库分到的传输速率越低，全量窗口被共同拉长，批量上线规划时必须计入。

从库侧也能受益于流式接收：字节流边收边写临时文件，收满即载入，无需等待完整文件先落主库磁盘，这是无盘模式缩短窗口的另一半原因。

```bash
# redis.conf
repl-diskless-sync yes        # 开启无盘复制
repl-diskless-sync-delay 5    # 延迟数秒，等待更多从库共享本次快照
```

> 磁盘快而网络慢的机器保持默认落盘模式即可；内存大、磁盘慢、全量复制频繁的实例开启无盘复制通常收益明显。repl-diskless-sync-delay 应在等待更多从库共享快照与尽快开始传输之间权衡，从库同时接入越集中，延迟窗口的价值越大。

**速记**：无盘复制 = **BGSAVE 直接进网络**，省磁盘、快全量、吃内存峰值。



#### 主从延迟与不一致窗口

**不一致窗口**：由于复制是**异步**的，主库写入成功与从库可见之间存在时间差，这段时间内主从数据不一致，称不一致窗口。

- 主库执行写命令即向客户端返回成功，命令传播、网络传输、从库回放都发生在返回之后。
- 窗口大小取决于从库回放速度与网络状况，可通过 INFO replication 中主库偏移量与从库偏移量之差观测。
- 这是 CAP 取舍下的选择：主从复制优先保可用与低延迟，放弃强一致。
- 业务应区分数据敏感度：能容忍旧读的走从库分担流量，不能容忍旧读的必须另有对策。
- 读取自己写入的典型场景（写后立即读）若读请求落到滞后的从库，会读到旧值；对策是关键路径强制读主库，或用 WAIT 命令等待指定数量的从库确认后再读。
- WAIT 的返回值是完成确认的从库数量，未达到预期数量时应视为写入未达副本，业务层据此降级或重试。
- 客户端库通常自带粘性读实现：记录写入命令的偏移量，等从库偏移量追上该值再执行读，是读写自己写入的通用方案。
- 监控从库延迟应纳入日常面板：突变与缓增都要告警，缓增往往预示从库回放能力不足。
- 从库回放大事务（如大集合删除）时会短暂卡住回放线程，是延迟突刺的常见来源。

观测之外还应给延迟设定预算：例如要求从库滞后不超过某个偏移量差值或时间阈值，超标的从库从读路由中临时摘除，这是多数客户端与代理实现读故障转移的基础逻辑。

应用层的兜底策略是给读操作声明容忍度：路由组件按业务标签决定可否读从库，超预算时自动回落主库。这样即使复制链路抖动，用户体验到的也只是延迟略升，而不是读到明显过期的数据。

WAIT 并不常见于普通读路径，多用于金融余额、库存扣减等关键写后的确认点；把 WAIT 当成每写必用的习惯会让吞吐急剧下降，它是精确制导的工具而非常规配置。

```bash
# 主库执行，观测主从延迟
127.0.0.1:6379> INFO replication
# master_repl_offset 为主库已传播到的偏移量
# slave0 行中的 offset 为该从库已复制到的偏移量，两者之差即滞后字节数

# 关键写入等待至少 1 个从库确认，最长等 100 毫秒
127.0.0.1:6379> WAIT 1 100
(integer) 1
```

> [!IMPORTANT]
> **重要内容**：异步复制意味着主库宕机瞬间尚未传播出去的写入会永久丢失，主从复制提供的是高可用与读扩展能力，不是数据零丢失的保证。对丢失敏感的关键写入应使用 WAIT 设置从库确认阈值，或依赖业务层补偿机制，不能默认复制等于不丢数据。

> 不一致窗口不是配置出来的，是异步系统固有的物理规律：Redis 能做的只是把窗口观测出来，把业务容忍度与窗口对齐。

**速记**：复制**异步即可能旧、可能丢**；写后必读走主库，敏感写入加 WAIT。



#### 复制风暴的成因与规避

**复制风暴**：多从库同时触发全量复制、主库连续或并发进行 BGSAVE 与 RDB 传输的现象，是主从架构最典型的事故模式。

- 成因一：多台新从库同时上线，各自发起首次全量。
- 成因二：主库重启或网络故障恢复，全体从库同时重连，积压缓冲区不足时集体退化为全量。
- 成因三：主从切换后所有从库改挂新主库，replid 失配带来一轮全量。
- 后果：主库 CPU 被快照占用、带宽被 RDB 传输挤占、内存被复制缓冲区推高，常常引发二次故障。
- 规避手段：错峰上线从库、按峰值写入速率调大积压缓冲区、必要时开启无盘复制缩短全量窗口。
- 监控上应为主库的复制类指标设阈值：输出缓冲区水位、BGSAVE 时长、RDB 传输速率同时告警，风暴苗头能被提前捕捉。
- 预案演练同样适用于风暴：每年至少一次模拟主库重启后全体从库重连的最坏情况。
- 云环境下还应关注虚拟机的突发带宽上限，RDB 传输挤占业务带宽在云主机上更明显。

风暴最危险的形态是循环风暴：全量导致主库抖动，抖动导致更多从库断线，断线重连又触发新的全量，形成正反馈。打断循环的手段包括临时摘除部分从库、对主库写入限流，以及在低峰期集中处理复制重建。

容量规划时应把最坏情况写进预案：假设主库凌晨重启、全部从库同时重连，按当前数据集大小与从库数量估算一轮全量的总耗时与总带宽；预案中还应写明谁有权执行摘除从库、写入限流等止血动作。

预案还要区分两类断点：可以等的新从库接入直接排队到低峰期，不能等的故障重连才走全量应急流程；把计划内与计划外的全量分开处理，是避免风暴演变为事故的最后一道闸门。

> [!TIP]
> **建议内容**：从库众多时改用级联拓扑分摊压力——主库只带两三个直接从库，其余挂在从库之下，把全量复制的快照与传输成本分散到多层节点。也可以预留一台高配从库专做中间层，让叶子从库的接入不再直接冲击主库。

> 从库数量与主库内存共同决定风暴的上限：数据集越大、从库越多，一轮风暴的总成本越高；这也是大实例场景更倾向级联拓扑、更少直接从库的原因。

**速记**：风暴 = **多从库 × 同时全量**；错峰、调大缓冲、级联分担三板斧。



#### 复制中的过期键处理

**复制中的过期键处理**：从库**不独立删除过期键**，而是等主库过期或淘汰键时合成 DEL 命令、随命令流传播下来，从库重放删除，保证主从数据始终一致。

- 主库按惰性与定期策略删除过期键（详见第 14 章）、或按淘汰策略驱逐键（详见第 15 章）时，会合成一条 DEL 命令进入复制流，所有从库收到后执行同样的删除。
- 从库自身的过期删除逻辑被禁用：即使本地键逻辑上已过期，从库也不主动删除。
- 读请求兜底：从库用自己的逻辑时钟判断，对已过期的键在只读操作中按不存在处理，且这种处理以不违反数据集一致性为界。
- Lua 脚本执行期间时间冻结：脚本运行过程中主库不执行键过期，脚本内的过期判断使用脚本开始时刻的时间。
- 从库提升为主库后立刻获得独立的过期删除能力，不再依赖旧主库。
- 可写从库的例外：Redis 4.0 起，可写从库对自己写入的带 TTL 键能像主库一样过期删除，是对只读规则的有限放行。

```text
过期键的传播路径（示意）：

键 foo 过期 ──► 主库删除（惰性或定期，详见第 14 章）
            ──► 合成 DEL foo 写入复制流
            ──► 所有从库重放 DEL，本地同步删除
从库本地已过期的键 ──► 不主动删，读请求按不存在兜底
```

> [!IMPORTANT]
> **重要内容**：不要把「从库读请求查不到过期键」误解为「从库会自己删键」——删除动作永远由主库发起并经 DEL 传播，从库只是用逻辑时钟在读取层把过期键当不存在返回；主从之间因此不会出现「从库先删、主库还没删」的分裂状态。

**速记**：**主删从等、DEL 传播**，从库只用逻辑时钟在**读层兜底**，提升为主后才独立过期。
