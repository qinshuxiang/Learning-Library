## Redis 版本演进与 Redis 7 新特性

### 版本号规则与发布节奏

#### 版本号规则：从奇偶号惯例到小步发布

**奇偶号规则**：是 Redis 早期借鉴 Linux 内核的版本惯例，即奇数次版本号代表开发分支、偶数次版本号代表稳定分支。

- 早期示例：2.5 系列是开发线，最终演进为稳定版 2.6。
- 该惯例始终没有硬性流程保障，社区实际执行并不严格。
- 后来 Redis 放弃了奇偶号惯例，改为直接以递增的版本号小步滚动发布，奇偶号不再代表稳定与否。
- 现行规则采用 x.y.z 三段式：y 位变化代表功能大版本，通常伴随新命令、新机制甚至内部结构重构。
- z 位变化代表补丁修订，原则上只做 bug 修复与安全加固，不引入新功能。
- 因此判断两个版本能否安全替换，先看 y 位是否一致：y 位相同的补丁版本之间升级风险最小。
- 查看历史演进的权威入口：官方仓库的 CHANGELOG 文件与官网 release notes 页面。

> 辨析：不要再用“奇数不稳定、偶数稳定”来判断现在的 Redis 版本——例如 3.0 与 3.2 都是稳定版本。判断一个版本是否为稳定版、是否适合生产，唯一可靠的依据是官方 release notes 的标注与发布说明；本文涉及的日期与特性表述，同样均以官方发布信息为准。

> [!NOTE]
> **提醒内容**：快速确认线上实例版本的两个途径：启动命令 redis-server --version，或连接后执行 INFO server 查看 redis_version 字段。排查版本相关行为差异时，先确认版本号再查资料，能避免大量“同一个命令行为不同”的无效争论。

```bash
# 查看服务器编译版本
redis-server --version

# 查看运行中实例的版本信息
redis-cli INFO server | grep redis_version
```

**全景对照**：先建立一张版本与年份的总览图，后续各节再逐段展开。

- 1.0（2009）：初版，确立内存键值模型。
- 2.6（2012）：Lua 脚本（EVAL、EVALSHA）。
- 2.8（2013）：PSYNC 部分重同步，哨兵趋于可用。
- 3.0（2015）：Cluster 集群正式版。
- 3.2（2016）：GEO 命令、quicklist 快速列表。
- 4.0（2017）：混合持久化、LFU、异步删除、模块系统。
- 5.0（2018）：Stream、ZPOPMIN 与 ZPOPMAX。
- 6.0（2020）：多线程 IO、ACL、RESP3、客户端缓存、TLS。
- 6.2（2021 年 2 月）：GETEX、SMISMEMBER、COPY、LPOS、GEOSEARCH 等大量命令补全。
- 7.0（2022）：Functions、Multi-Part AOF、listpack 全面铺开、sharded pubsub、ACL v2。
- 7.2（2023）：压测与工程体验改进、函数持久化默认生效。
- 7.4（2024）：hash field TTL；许可自此版本起变更。
- 8.0（2025）：回归开源（AGPLv3），模块能力与查询引擎一体化。

> 时间线记忆法：按三个阶段粗记——2009 到 2018 是从单机缓存到分布式与消息流（1.0 至 5.0），2020 年前后补齐并发、安全与协议（6.0、6.2），2022 年以后进入 7.x 工程化与许可变革期（7.0 至 8.0）。

**版本信息的三个层次**：读版本资料时按三层递进——先看大版本定位（解决了什么时代问题），再看特性清单（新增与弃用了什么），最后看补丁节奏（修复了哪些缺陷），三层看完再决定是否跟进。

**版本与生产节奏**：大版本刚发布时特性新但稳定性未经大规模验证，生产环境通常等待其补丁版本迭代数轮后再升级，这是社区通行的保守策略。

- 新大版本（x.y 中 y 变化）：先在测试环境验证，观察官方补丁修复情况。
- 补丁版本（z 位递增）：主要承载 bug 修复，生产升级的主要来源。
- 安全修复：随补丁版本发布，涉及漏洞时应尽快跟进对应补丁版本。

> 选用哪个版本线与许可、生态分叉密切相关，详见本章 License 变迁一节；日常性能与运维问题与版本号的关系，详见第 29 章。

**速记**：奇偶号是**历史习惯**，早已**废除**；现行为 **x.y.z 小步发布**，稳不稳看 **release notes**。



### 大版本时间线：从 1.0 到 5.0

#### 1.0 与 2.6：初版与早期奠基

**1.0（2009 年）**：是 Redis 的首个正式版本，由 antirez 发布，确立了内存键值模型与核心命令体系。

- 1.0（2009）：初版，提供 String 等基础类型与核心读写命令，奠定“内存数据库 + 单线程”的基本形态。
- 2.6（2012）：引入 Lua 脚本支持（EVAL、EVALSHA），服务器可在服务端原子地执行一段脚本。
- 初版时期就已确立的单线程内存模型沿用至今，此后十多年的演进都是在此根基上的扩展。
- 这一阶段 Redis 的定位从单纯的缓存工具，逐步走向带脚本能力的通用内存数据库。

**2.6 的脚本意义**：EVAL 让客户端把一段 Lua 源码发给服务器执行，多次网络往返压缩为一次，原子性由单线程执行天然保证；它标志着 Redis 从命令集合走向可编程平台的第一次跃迁。脚本与事务的完整用法详见第 23 章。

```bash
# 2.6 起：服务端原子执行一段 Lua 脚本
EVAL "return redis.call('GET', KEYS[1])" 1 stock:1001
```

> 2.6 引入的 Lua 脚本影响深远，它让“读改写”这类多步操作得以在服务端原子完成，也是后来 7.0 Functions 的基础。

**速记**：**1.0 打地基**（2009），**2.6 加脚本**（2012）。



#### 2.8 与 3.0：哨兵正式版与 Cluster 集群

**2.8（2013 年）**：补齐了主从复制的关键短板，并让哨兵体系走向可用；**3.0（2015 年）** 则发布了 Cluster 集群的正式版。

- 2.8（2013）：引入部分重同步 PSYNC，主从断线重连后无需整体重新同步，大幅降低复制开销。
- 2.8（2013）：哨兵 Sentinel 在这一阶段趋于成熟可用（具体以官方 release notes 为准），高可用方案有了正式落地。
- 3.0（2015）：Redis Cluster 正式发布，提供数据分片与去中心化的集群方案，官方补齐了水平扩展能力。
- 3.0（2015）：Cluster 引入槽位分片与节点间通信协议，多节点去中心化组网（机制详见第 22 章）。

> 影响最大的特性是 3.0 的 Cluster：它把数据按槽位分散到多个节点，使 Redis 突破单机内存与写入瓶颈，是 Redis 从单机缓存走向分布式基础设施的分水岭。此前的 2.8 则解决了复制层面的实际痛点——大实例断线后全量重同步既慢又耗资源，PSYNC 让主从只需传输缺失的命令段。复制原理详见第 20 章，哨兵详见第 21 章，Cluster 详见第 22 章。

> 集群时代之前，扩容只能靠垂直升级与客户端分片，Cluster 的槽位方案把路由职责分摊到节点本身，这是它与客户端分片方案的本质区别。

**哨兵在此阶段的定位**：哨兵负责监视主从、执行故障判定与自动切换，2.8 时期其核心流程趋于稳定，生产部署才真正放心。哨兵的部署拓扑与仲裁机制详见第 21 章。

**PSYNC 的原理要点**：主从各自维护复制偏移量与复制积压缓冲区，从库断线重连时携带偏移量发起请求，主库判断缓冲区能否覆盖缺失区间——能覆盖则部分重同步，否则退化为全量同步。机制细节详见第 20 章。

```bash
# 观察主从复制状态（含偏移量与积压缓冲区信息）
redis-cli INFO replication
```

**速记**：2.8 补**复制与哨兵**，3.0 上**集群分片**。



#### 3.2 至 5.0：GEO、异步删除与 Stream

**3.2 至 5.0**：是特性密集期，地理位置、内存效率、异步化与消息流能力先后落地。

- 3.2（2016）：新增 GEO 地理位置命令（GEOADD、GEOPOS 等）；List 底层引入 quicklist（快速列表），以 ziplist 节点串联成链表，兼顾内存与操作效率。
- 4.0（2017）：引入混合持久化（aof-use-rdb-preamble 配置）、LFU 内存淘汰策略、UNLINK 与 FLUSHALL ASYNC 异步删除，以及模块系统 Modules。
- 5.0（2018）：新增 Stream 数据类型，Redis 第一次拥有了可持久化、可消费者组的日志型消息结构；同期补充 ZPOPMIN、ZPOPMAX 等命令。
- 5.0（2018）：Stream 支持消费者组与消息确认，语义上接近一个简化版消息队列。

> 影响最大的两个特性值得单独强调。其一是 4.0 的**模块系统**：第三方可以像插件一样为 Redis 扩展新数据类型与命令，后来的 JSON、时序等能力都以此机制为载体，它决定了 Redis 此后的扩展路径。其二是 5.0 的 **Stream**：它同时兼具日志结构与消费者组语义，是官方对消息队列场景的正面回应。

> 4.0 的异步删除同样改变了日常运维习惯：删除大键从同步的 DEL 改为异步的 UNLINK，把内存回收交给后台线程，避免删除瞬间阻塞主线程。混合持久化详见第 19 章，淘汰策略详见第 15 章，Stream 详见第 9 章与第 24 章，UNLINK 与大键删除详见第 2 章与第 29 章。

```bash
# 4.0 起推荐的异步删除：先摘引用，内存后台回收
UNLINK big:key

# 3.2 起的地理位置写入
GEOADD city 116.40 39.90 beijing 121.47 31.23 shanghai
```

**LFU 的意义**：4.0 在经典 LRU 之外引入 LFU 淘汰策略，按访问频率而非最近时间淘汰，对“偶尔被扫一遍的长尾热键”更友好；策略机制详见第 15 章。

**混合持久化的影响**：4.0 的 aof-use-rdb-preamble 让 AOF 重写产物采用 RDB 格式作前缀——重写更快、文件更小、恢复更稳，是 7.0 之前持久化层面最重要的一次改进，选型分析详见第 19 章。

**quicklist 的定位**：3.2 引入的 quicklist 并非全新结构，而是把小段 ziplist 串成双向链表的混合体——段内连续内存省空间，段间链表化解单一大 ziplist 的更新开销；这一混合思路在 7.0 中延续，节点内容由 ziplist 换成更安全的 listpack。

```bash
# 5.0 起的 Stream 写入与读取
XADD mq:orders * order_id 1001 amount 59.9
XREAD COUNT 10 STREAMS mq:orders 0
```

**速记**：3.2 加**位置**，4.0 走**异步与模块**，5.0 开**消息流**。



### Redis 6：多线程 IO 与安全体系

#### 多线程 IO 与线程模型演进

**多线程 IO（6.0，2020 年）**：指 Redis 在保持命令执行单线程的前提下，把网络数据的读取、发送与协议解析交给多个 IO 线程并行处理。

- 命令执行仍然由主线程单线程完成，因此单个命令的原子性语义不变。
- 通过 io-threads 与 io-threads-do-reads 配置开启，默认关闭（以官方文档为准）。
- 收益主要出现在大吞吐、大 value 的网络密集场景；小 value、低负载场景收益有限。
- 它不是“命令执行多线程化”，数据结构的竞态问题并未引入。
- 开启后需观察 CPU 与延迟指标，线程数并非越多越好，通常不超过核数的一小部分。
- 6.0 之前并非完全无并发：4.0 起的异步删除等操作已使用后台线程，6.0 是把网络 IO 也并行化。

> 辨析：很多人误以为 6.0 之后 Redis 变成了多线程数据库，准确的说法是：**IO 多线程、执行单线程**。单线程模型与事件循环的原理详见第 16 章，理解这一点才能判断多线程 IO 是否值得开启。

```bash
# 查看当前 IO 线程配置
CONFIG GET io-threads

# 动态调整（部分线程参数修改后需重启才完全生效，以官方文档为准）
CONFIG SET io-threads 4
```

**开启前的判断**：先确认瓶颈在网络收发而非命令执行——若 OPS 很高但 CPU 未打满，瓶颈往往在别处；若网络处理线程饱和且 value 偏大，多线程 IO 才有明显收益。性能定位方法详见第 29 章。

> 另一个常见误读：io-threads 不是越大越好，线程过多反而增加调度与同步成本，推荐取值以官方文档为准。

**与后台线程的关系**：Redis 的线程分工是逐步演进的——4.0 起有负责异步删除与 fsync 的后台线程，6.0 又加入 IO 线程；所谓“单线程”始终指命令执行那条主路径，理解这条主线才能分清各版本并发能力的边界。

**速记**：6.0 是 **IO 多线程、执行仍单线程**，默认关闭、按需开启。



#### ACL、RESP3 与客户端缓存

**6.0 的安全与协议升级**：除多线程 IO 外，6.0 还一次性引入了 ACL 权限体系、RESP3 协议、客户端缓存与 TLS 支持。

- ACL：引入用户与权限管理，可按用户限制可执行命令与可访问的键，此前 Redis 只有单密码模型。
- RESP3：新一代通信协议，支持 push 类消息等能力，为服务端主动通知客户端铺路。
- client-side caching（客户端缓存）：允许客户端在本地缓存热点数据，服务端数据变更时通过失效通知告知客户端丢弃本地缓存。
- TLS：官方支持加密传输，满足更严格的安全合规要求。
- 使用 ACL 的前提是所有接入方都走支持新协议的客户端库，老客户端的兼容行为以官方文档为准。
- 这四项能力共同把 Redis 的适用面从内网可信环境，扩展到了对权限、审计与加密有要求的生产场景。

> 辨析：客户端缓存依赖 RESP3 的失效推送（或旧协议下的广播模式），本质是用网络换内存的权衡——服务端省了重复读，客户端多了本地状态管理。ACL 的实操配置与安全加固的整体思路详见第 31 章。

```bash
# 创建一个只能访问 app:* 键、只允许读写命令的用户
ACL SETUSER app_user on >strongPassword ~app:* +get +set +del

# 查看已有用户列表
ACL LIST
```

**最小权限实践**：为每个应用分配独立用户，按需授予命令与键模式，避免所有服务共用超级用户——这是 6.0 之前多数误操作事故的根源，也是 ACL 的设计初衷。

```bash
# 查看指定用户的权限细节
ACL GETUSER app_user

# 只读用户示例：仅授予 get 与 mget
ACL SETUSER report_user on >strongPassword ~report:* +get +mget
```

**RESP3 与旧协议的关系**：RESP3 是服务端与客户端之间的协议升级，服务端通常同时兼容旧协议，客户端按需协商；对应用代码而言，多数连接库在升级后无需改动，仅使用 push 类新能力时才需要 RESP3。

**引入 ACL 的背景**：此前 Redis 只有 requirepass 单密码模型，拿到密码即拥有全部权限，多应用共用实例时只能靠约定约束行为；ACL 把“谁能执行什么命令、访问什么键”变成服务端可配置的规则，是 Redis 走向多租户与合规场景的前提。

**速记**：6.0 一并带来 **ACL、RESP3、客户端缓存、TLS**。



### Redis 7 的核心新特性

#### Functions 与服务端函数机制

**Functions**：是 7.0（2022 年）引入的常驻服务端函数机制，允许把一段段命名函数注册到服务器长期保存，随时按名调用。

- 与 EVAL 的区别：Lua 脚本（EVAL）每次都要随请求发送完整源码，Functions 则**加载一次、常驻服务端**。
- 函数通过 Lua 编写，使用 redis.register_function 注册，客户端调用时按函数名触发，不再传输源码。
- 管理命令：FUNCTION LIST 查看已加载函数，FUNCTION DELETE 删除指定函数，FUNCTION FLUSH 清空全部函数。
- 函数随持久化与复制传播，主从和重启后仍可用（默认持久化行为以官方 release notes 为准）。
- 7.0 同时改进了 Lua 脚本能力，暴露了 Function API 供脚本注册与调用。

```bash
# 查看已加载的函数
FUNCTION LIST

# 删除指定名字的函数
FUNCTION DELETE mylib
```

**按库组织**：函数以库（library）为单位加载，一个库内可注册多个函数，重新加载时以库名为单位整体替换，这使服务端逻辑能像代码包一样管理版本。

- 函数名即调用入口，客户端像调用普通命令一样按名触发。
- 函数随持久化与复制在主从间保持一致，从库无需单独加载（细节以官方文档为准）。

**升级视角**：7.0 对既有 EVAL 脚本保持兼容，存量脚本无需改造即可继续运行；Functions 是新增的并行动线，而非对旧机制的替换，升级时可以分步引入。

**EVAL 与 Functions 对照**：加载方式——EVAL 随请求发源码，Functions 预先加载按名调用；复用粒度——EVAL 适合一次性逻辑，Functions 适合跨连接的常驻逻辑；版本收敛——EVAL 的“版本”散落在各调用方，Functions 的版本集中在服务端的库上。

> 影响最大的场景是“多客户端共享服务端逻辑”：过去每个连接都要携带同一段脚本源码，脚本一改各端同步成本高；Functions 把逻辑版本收敛到服务端，升级只需重新加载一次。

> 辨析：Functions 不取代 EVAL——临时的一次性脚本用 EVAL 依然最直接；需要跨连接复用、随库分发的服务端逻辑，Functions 才是正解。二者共享“服务端原子执行”的本质，事务与脚本的细节详见第 23 章。

**速记**：Functions 是**加载一次、常驻调用**的服务端函数，EVAL 是**随请求发源码**的一次性脚本。



#### Multi-Part AOF

**Multi-Part AOF**：是 7.0 对 AOF 持久化结构的重构，把单一的 AOF 文件拆成基础文件、增量文件与一份清单（manifest）。

- 组成：基础文件（base，通常由重写生成）+ 一个或多个增量文件（incr）+ manifest 清单文件记录三者关系。
- 收益：AOF 重写期间不再需要把新写入缓冲到旧文件里等待切换，重写过程更平滑，重写失败的风险面更小。
- 目录化：AOF 相关文件集中放在一个专用目录（默认 appendonlydir，目录名可配置）下管理。
- 兼容：7.0 可以读取旧版单一 AOF 文件并自动转换；从 7.0 降级回旧版则需谨慎处理数据文件。
- manifest 是整个结构的入口，服务器启动时先读清单、再按清单加载基础与增量文件。
- 多个增量文件按序号排列，清单中记录各自的起始与结束序号，保证重放顺序正确。
- 旧版 AOF 文件在首次以 7.0 启动时被转换进新目录结构，原文件的处理方式以官方文档为准。

```bash
# 7.0 起 AOF 目录的典型内容
ls appendonlydir
# appendonly.aof.1.base.rdb
# appendonly.aof.1.incr.aof
# appendonly.aof.manifest
```

**恢复视角**：新结构下恢复数据时按清单依次加载基础与增量文件，加载逻辑集中且可校验，出现损坏时也更容易定位是哪一段文件出了问题。

**与重写触发的关系**：Multi-Part AOF 改变的是文件组织方式，原有的重写触发条件与语义保持不变——重写产物成为新的基础文件，之后的写入进入增量文件，manifest 随之更新。

> 影响最大的是重写环节的健壮性：旧结构下重写要与正在追加的文件做繁琐的衔接，新结构把“历史快照”与“持续追加”彻底解耦，各自独立成文件。

> 辨析：升级到 7.0 后，看到数据目录里多出一个 AOF 目录与 manifest 文件不是异常，而是新结构。做备份与迁移时必须把整个 AOF 目录一起拷贝，只拷单个文件会丢数据。AOF 机制本身详见第 18 章，混合持久化详见第 19 章。

**速记**：7.0 的 AOF 变成 **base + incr + manifest 三件套**，备份要**连目录一起拷**。



#### listpack 全面取代 ziplist

**listpack**：是一种紧凑的连续内存编码结构，7.0 起全面取代 ziplist，成为小对象编码的统一底座。

- 解决的问题：ziplist 的每个节点记录前驱长度，修改中间节点可能引发后续节点逐级改写的**连锁更新**；listpack 的节点只记录自身信息，不再有这一隐患。
- 覆盖范围：Hash、ZSet、List、Stream 等原本使用 ziplist 的场景，7.0 起统一改用 listpack（List 的整体结构仍是 quicklist，节点内部换成 listpack）。
- 对用户透明：编码变化不影响命令语义，只影响内存占用与部分操作的效率。
- 判断手段：用 OBJECT ENCODING 查看某键的当前编码，7.0 起小对象普遍返回 listpack。
- 演进脉络：listpack 在更早的版本已开始部分引入，7.0 才实现全面替换（细节以官方 release notes 为准）。
- 连锁更新问题在极端构造下才会触发，但它正是历史上若干“偶发延迟毛刺”的元凶之一。

```bash
# 查看键的底层编码（7.0 起小 Hash 返回 listpack）
OBJECT ENCODING small:hash
```

**观察方法**：同一份数据分别写入 6.2 与 7.0 实例，用 OBJECT ENCODING 确认编码差异、用 MEMORY USAGE 对比内存占用，是验证升级收益最直接的手段。

```bash
# 对比编码与内存占用
MEMORY USAGE small:hash
```

> 影响最大的是极端场景的稳定性：连锁更新在最坏情况下会把一次小修改放大成一串节点的重写，造成难以解释的延迟尖刺；listpack 从结构上根除了这一类问题。

> 辨析：listpack 与 ziplist 同属紧凑编码，目标是小数据量省内存，元素变多变大后仍会转为基础编码（如 Hash 转哈希表、ZSet 转跳表）。ziplist、listpack 与跳表的底层结构详见第 12 章，对象系统与编码切换详见第 13 章。

**速记**：7.0 用 **listpack 换掉 ziplist**，根除**连锁更新**，小对象编码大一统。



#### shard pubsub 与其他 7.0 特性

**7.0 的其余重点特性**：除上述三项外，7.0 还集中落地了分片订阅、ACL v2、GEOSEARCH 推广与 AOF 时间戳注解。

- sharded pubsub（分片订阅）：新增 SSUBSCRIBE 等命令，发布订阅消息只在数据所在的分片内传播，不再广播到全集群，显著降低 Cluster 下的订阅开销。
- ACL v2：ACL 升级，新增对 Pub/Sub 频道的权限控制（细节以官方 release notes 为准）。
- GEOSEARCH：6.2 已引入的新地理位置查询命令，自 7.0 起正式接棒——GEORADIUS、GEORADIUSBYMEMBER 被标记弃用，官方推荐改用 GEOSEARCH。
- AOF 时间戳注解：可在 AOF 中记录时间戳，便于按时间点做数据回溯分析（由配置开关控制）。
- 这些特性共同指向两个方向：集群环境下的成本优化（分片订阅），与数据可追溯性（时间戳注解）。

> 影响最大的是 sharded pubsub：在大型 Cluster 中，普通 Pub/Sub 的全量广播会随分片数线性放大网络开销，分片订阅把消息面收窄到单个分片，是大规模聊天、推送类场景的关键优化。

> 辨析：普通 Pub/Sub 在 Cluster 下会把消息广播到所有节点，分片越大浪费越大；sharded pubsub 只在 key 所属分片内投递，适合集群大规模订阅场景。普通 SUBSCRIBE 命令族在集群中的行为不变，分片订阅是额外的新选择，二者并存。普通 Pub/Sub 与 Stream 两种消息方案的取舍详见第 24 章。

```bash
# 分片订阅：只接收所在分片内的消息
SSUBSCRIBE orders:events
```

**接入成本**：分片订阅复用既有的发布订阅心智模型，命令族与普通订阅对称（SSUBSCRIBE、SUNSUBSCRIBE 等），从普通订阅迁移的主要工作量在客户端连接与路由逻辑的调整。

**速记**：7.0 还带来**分片订阅、ACL v2、GEOSEARCH 接棒、AOF 时间戳**。



#### CONFIG 命令演进与配置项变化

**CONFIG 演进**：7.0 对配置体系的一次集中升级——CONFIG 命令本身支持一次调用处理多个配置项，配置项命名随数据结构演进而系统性改名，并新增了客户端内存、集群端口等一批配置选项。

- CONFIG SET 与 CONFIG GET 自 7.0 起支持在一次调用中传入多个参数，一次设置或查询多个配置项，且这一处理是原子的；例如一条 CONFIG SET 可同时修改 maxmemory 与 maxmemory-policy。
- 配置项改名一：与 listpack 全面替代 ziplist 同步，ziplist 系列配置项更名——hash-max-ziplist-entries 改为 hash-max-listpack-entries、list-max-ziplist-size 改为 list-max-listpack-size 等，旧名在 7.0 中不再存在。
- 配置项改名二：lua-time-limit 改名为 busy-reply-threshold，语义不变，即脚本或命令超过该时长后向其他客户端回复 BUSY。
- 新增配置项举例：maxmemory-clients 限制所有客户端输入输出缓冲区占用的总内存（支持绝对值或百分比两种写法）；cluster-port 允许自定义集群总线端口；shutdown-timeout 控制关机时等待从库追平复制的宽限时长。
- 安全侧收紧：enable-debug-command 与 enable-protected-configs 默认禁用，DEBUG 命令与受保护的配置项默认不可被客户端触碰，缩小了误操作与攻击面。
- 自省能力同步增强：COMMAND DOCS、COMMAND LIST、LATENCY HISTOGRAM 等新命令补齐了命令文档与延迟直方图的自省入口，与 CONFIG 一起构成更完整的可观测配置面。

```bash
# 7.0 起：一条命令原子地设置多个配置项
CONFIG SET maxmemory 2gb maxmemory-policy allkeys-lru

# 配置项改名对照（旧名 → 新名）
# hash-max-ziplist-entries  → hash-max-listpack-entries
# list-max-ziplist-size     → list-max-listpack-size
# lua-time-limit            → busy-reply-threshold

# 新增：限制全部客户端缓冲区的总内存
CONFIG SET maxmemory-clients 10%
```

> 辨析：配置项改名后旧名不会静默兼容——用旧配置文件启动 7.0 会因未知配置项而报错，升级时必须逐项改名再启动；这也是升级检查清单里“核对配置文件改名项”的具体落点，见本章末尾的升级实践一节。

> [!TIP]
> **建议内容**：升级到 7.0 前先用 CONFIG GET * 导出旧实例的全部运行时配置，对照官方 redis.conf 样例逐项确认新名与新默认值，再改写配置文件——改名项的报错会在启动时暴露，但默认值变化的项不会报错，只能靠主动比对发现。

**速记**：CONFIG 7.0 三件事——**多参数原子设置、配置项改名、新配置补齐**；旧名启动报错，改名后才能上。



### 7.2、7.4 与 Redis 8 的方向

#### 7.2 与 7.4 的演进概览

**7.2（2023 年）与 7.4（2024 年）**：延续 7.x 主线的两代稳定版，前者以工程体验改进为主，后者带来了 Hash 字段级过期。

- 7.2（2023）：redis-benchmark 与延迟观测能力改进，Functions 持久化默认生效；另含部分实验性能力，细节以官方 release notes 为准。
- 7.4（2024）：新增 hash field TTL，可对 Hash 的单个字段独立设置过期时间（详见下一考点）。
- 许可变更同样始于 7.4：自该版本起 Redis 不再采用纯 BSD 类许可，影响深远（详见 License 一节）。
- 7.2 的改进偏“打磨”：压测工具更准确、可观测性更强，反映官方重心从大开大合的新功能转向工程质量。
- 7.x 系列的默认配置与默认行为在版本间偶有调整，升级时逐项确认默认值变化。
- 两版的补丁更新都持续较长时间，选择时优先参考官方对长期维护版本的说明。

> 阅读建议：7.x 系列的补丁版本（z 位）更新频繁，生产环境选择时应锁定某个具体的补丁版本并跟进其修复记录，不要笼统地说“我们在用 7.2”。

> 阅读这两版更新的正确姿势：把它们当作 7.0 大改之后的“消化期”产物——大重构落地后，官方需要两到三个版本修复边界问题、补齐工具链，这一规律也适用于评估未来任何大版本后的跟进时机。

**两版的生态位置**：7.2 是 7.x 体系内长期使用的稳定线，也是 Valkey 分叉的代码起点；7.4 承载字段级过期与许可转向——生产可见差异不大，生态意义截然不同。

**速记**：7.2 磨**工具与工程体验**，7.4 加**字段级过期**、改**许可证**。



#### hash field TTL 与 HEXPIRE

**hash field TTL（7.4）**：允许对 Hash 中单个字段设置独立的过期时间，到期后仅该字段被删除，整个键仍可存活。

- 新命令族：HEXPIRE、HPEXPIRE、HEXPIREAT、HPEXPIREAT 负责设置，HTTL、HPTTL 负责查询剩余时间，另有 HPERSIST 取消过期等配套命令。
- 语义：设置时以 FIELDS 指定字段列表，字段到期后自动从 Hash 中移除，效果类似“字段级惰性删除”。
- 适用场景：购物车里不同商品的有效期不同、会话中不同凭据的生命周期不同等，过去只能靠应用层拆键或定时清理。
- 使用前提：客户端与服务端都需 7.4 及以上版本，旧客户端无法直接使用这些命令。
- 字段级 TTL 与键级 EXPIRE 可以同时使用，互不干扰。
- 过期精度与键级过期一致，均为近似秒级或毫秒级，业务不要假设精确到期。
- 过期字段在删除前后对 HGETALL 等读取命令的可见性细节，以官方命令文档的行为描述为准。

```bash
# 对 Hash 中单个字段设置 60 秒过期
HSET cart:1001 item_a 2 item_b 1
HEXPIRE cart:1001 60 FIELDS 1 item_a

# 查询字段剩余存活秒数
HTTL cart:1001 FIELDS 1 item_a
```

```bash
# 取消字段过期并查看整体内容
HPERSIST cart:1001 FIELDS 1 item_a
HGETALL cart:1001
```

**边界注意**：字段过期后的清理时机，以及 HTTL 对不存在字段、未设 TTL 字段的返回值语义，均以官方命令文档为准，业务代码不要硬编码魔数做判断。

> 影响最大的是会话与购物车一类“对象内字段生命周期不一”的场景：过去要么把过期粒度从对象级拆到字段级（键数量成倍增长），要么在应用层维护定时清理任务；HEXPIRE 让过期语义回到数据本身。

> 辨析：注意与键级过期区分——EXPIRE 作用于整个键，HEXPIRE 只作用于字段；键被删除时其字段自然一并消失。键级过期与删除策略详见第 14 章。

> [!TIP]
> **建议内容**：在字段级 TTL 出现前，很多团队用“一个业务对象拆成多个带 TTL 的小键”来模拟字段过期；升级到 7.4 后可评估回收这类拆键方案，但重构前先确认所有客户端库已支持新命令。

**速记**：7.4 的 HEXPIRE 是**字段级的 EXPIRE**，键整存、字段各死各的。



#### Redis 8 的方向概述

**Redis 8（2025 年）**：是又一次重大版本，主要方向是回归开源许可，并把此前以 Redis Stack 形态提供的模块能力整合进核心。

- 许可：Redis 8 新增 AGPLv3 作为许可选项之一，社区普遍视其为“回归开源”（许可细节与三许可并行的关系见下一节）。
- 能力整合：JSON、时序、概率结构等原先依赖 Redis Stack 安装的模块能力，以及带向量检索的查询引擎，被整合进 Redis 核心一起发布。
- 架构意义：应用不再需要分别部署 Redis 与 Stack 模块两套服务，一套实例即可覆盖文档、时序与检索场景。
- 性能与内存层面亦有相应优化（具体内容以官方 release notes 为准）。
- 兼容与细节：具体包含的命令、配置与性能表现变化较多，本文不做逐项展开，表述以官方 release notes 为准。

**定位方式**：把 Redis 8 理解为“平台化”——从单一的缓存键值服务，转向自带文档、时序、向量检索能力的多模型数据平台；理解这一定位，才能判断哪些新能力与自己的业务相关。

**对学习路线的意义**：数据结构、持久化、复制与集群等基础内容不因 8.0 而失效，前面各章仍是理解 8.x 的根基；新整合的检索与 JSON 能力，适合在基础牢固后按需扩展。

> 辨析：本节刻意只做方向性概述——Redis 8 的细节以官方发布说明为准。若生产选型直接上 8.x，务必先通读官方的升级与兼容性说明，并确认所用客户端库的适配版本。

**速记**：Redis 8 是**回归开源 + 模块一体化**的大版本，细节看官方发布说明。



### License 变迁与 Valkey 分叉

#### License 变迁史

**License 变迁史**：Redis 的开源许可经历了 BSD 独占、双许可收紧、回归开源三个阶段，直接影响了整个生态的走向。

- 长期 BSD：从诞生到 7.2，Redis 一直采用 BSD 类开源许可，任何人可自由使用、修改与商用托管。
- 2024 年 3 月，Redis Ltd 宣布自 7.4 起改为 RSALv2 与 SSPLv1 双许可：二者均对“直接对外提供 Redis 服务”的云厂商施加限制，不再被广泛认可为符合 OSI 开源定义。
- 2025 年 Redis 8：在原双许可基础上新增 AGPLv3 选项，即 RSALv2、SSPLv1、AGPLv3 三许可并行，Redis 重新被视为开源软件。
- 三阶段的主线是商业模式与开源社区的张力：Redis Ltd 希望限制云厂商“白嫖托管”，社区则坚持开源定义。
- 使用层面的影响：自建、容器化部署与客户端集成基本不受许可变更影响，受约束的主要是对外托管转售场景。

> 影响最大的是第二阶段的转向：它打破了十几年的使用预期，直接引发了 Valkey 分叉（见下一考点），也让“Redis 还算不算开源软件”成为 2024 年基础软件领域的标志性讨论。

**三阶段的读法**：把许可史当产品史读——BSD 时代对应社区扩张期，双许可对应商业化与云厂商的博弈期，AGPLv3 回归对应竞争压力下的再开放；许可选择始终服务于商业模式。

> 辨析：RSALv2 与 SSPLv1 对自用、开发、分发场景基本不受影响，受冲击最大的是“把 Redis 作为托管服务出售”的商业模式。许可条款的具体边界以官方许可文本为准，本节只描述演进脉络，不构成法律意见。

**与版本选型的联动**：许可变更后的版本选择多了一层判断——停留在 7.2 可保 BSD 类许可但失去官方新特性，升 7.4 需接受新许可条款，上 8.0 则有三许可可选；三条路径对应三类团队，没有对错只有取舍。

**速记**：BSD 长跑 → **7.4 起 RSALv2 与 SSPLv1**（2024 年 3 月宣布）→ **8.0 回归 AGPLv3**（2025）。



#### Valkey 分叉与生态反应

**Valkey**：是 2024 年许可变更后，由 Linux 基金会托管的 Redis 分叉项目，起自与 Redis 7.2 兼容的代码基线。

- 起因：RSALv2 与 SSPLv1 挡住了主要云厂商按原模式提供托管服务，AWS、Google 等公司随即支持 Valkey 作为开放替代。
- 演进：Valkey 在 7.2 兼容基线上独立演进，此后与 Redis 的版本号、特性逐步分化，二者不再是同一软件。
- 生态反应：各云厂商的托管产品线出现分化——有的转向 Valkey，有的按新许可继续提供 Redis，企业选型需逐一确认。
- 对开发者：Valkey 延续 BSD 类许可与既有协议，多数客户端可无感连接，但新特性层面与 Redis 渐行渐远。
- 分叉的底气在于 BSD 时代积累的社区与贡献者：代码、测试与文档体系完整，起点不是从零开始。
- Valkey 的名字取自 value 与 key 两个词的组合，项目由 Linux 基金会中立托管。

**兼容性现状**：起步于 7.2 基线意味着此前的命令与行为双方一致，此后各自新增的特性互不覆盖；协议层面保持兼容，存量应用的改造量主要来自后续新特性的使用差异。

**跟进成本**：分叉初期两边高度一致，团队可以低成本试水；随时间推移，两边的特性、性能优化与修复各自演进，长期使用必须指定明确的跟进线并定期评估差异，不能默认“都一样”。

> 影响最大的是托管市场格局：云厂商从“被动接受新许可”转为“主动投入分叉项目”，Valkey 迅速获得多家巨头背书，开源基础软件的许可策略从此被反复审视。

> 辨析：选择 Valkey 还是 Redis 没有统一答案——追求官方最新特性与向量检索等一体化能力看 Redis 8 之后的路线，追求明确的开源许可与社区共治看 Valkey；两者都已不是同一个软件，升级与迁移需各自评估。

> [!IMPORTANT]
> **重要内容**：许可与分叉直接影响生产选型，不能只看版本号——同样是“7.2”，Redis 官方版、Valkey 与各云厂商托管的分支在许可、支持与后续特性上并不相同。选型时应明确三件事：用哪条代码线，许可是否满足自身用途，未来升级跟谁走。

**速记**：许可收紧催生 **Valkey**（Linux 基金会、兼容 7.2），生态**分两条线**，选型先看清代码线。



### 升级实践与版本跟进

#### 升级注意事项与版本跟进习惯

**升级总原则**：Redis 各版本对旧数据文件总体向前兼容——高版本能读低版本的 RDB 与 AOF，反向则不成立，因此升级基本不可逆，必须先备份。

- 数据文件兼容：升级前确认 RDB、AOF 能被新版本正常加载；跨大版本（尤其 6 到 7 的 AOF 结构变化）要留意 Multi-Part AOF 的目录变化。
- 滚动次序：集群与主从环境先升从库、验证通过后再切换主库，逐实例推进，避免一次性全量升级。
- 弃用命令核对：升级前扫描业务代码中的弃用命令并替换，重点是 HMSET（4.0 起弃用，改用 HSET）与 GEORADIUS、GEORADIUSBYMEMBER（6.2 起被 GEOSEARCH 取代）；其余以官方命令文档的弃用标注为准。
- 脚本与配置：检查 Lua 脚本与 Functions 的兼容性，核对配置项的改名与新增，必要时对照官方的升级指南逐项确认。
- 客户端版本：大版本升级通常伴随协议与命令变化，确认所用客户端库已适配目标版本。
- 升级窗口安排在低峰期，预留数据加载与主从切换的时间。

```bash
# HMSET 已弃用，改用 HSET 一次写入多个字段
HSET user:1001 name alice age 30

# 旧命令（已弃用）
GEORADIUS city 116.40 39.90 100 km

# 新写法（6.2 起）
GEOSEARCH city FROMLONLAT 116.40 39.90 BYRADIUS 100 km
```

**升级流程**：一次规范的大版本升级通常按“备份、测试环境验证、灰度实例、全量推进”四步走，每一步都有明确的回退点。

- 第一步备份：触发 BGSAVE 并完整拷贝 RDB 与 AOF 目录，作为最终回退依据。
- 第二步验证：在测试环境用真实数据文件启动新版本，执行核心业务路径回归。
- 第三步灰度：先升级从库与低风险实例，观察复制、内存与延迟指标。
- 第四步推进：主从切换逐步替换全部实例，保留旧版本二进制以便应急回退。

**回退预案**：旧版本二进制、完整备份、恢复后的加载验证三要素齐备才算有回退能力——只留备份文件而从未演练加载，不算。

```bash
# 升级前备份示例
redis-cli BGSAVE
cp dump.rdb /backup/dump.rdb.bak
cp -r appendonlydir /backup/
```

> [!CAUTION]
> **注意内容**：升级前务必完整备份数据——触发 BGSAVE 后连同 RDB 与整个 AOF 目录（7.0 起为 appendonlydir）一起拷贝保存，并确认备份能在测试环境被新版本正常加载。只备份单个 AOF 文件或跳过加载验证，都可能在升级失败时造成数据损失。

> [!WARNING]
> **警告内容**：弃用不等于立即移除——弃用命令在当前版本通常仍能执行，但官方随时可能在后续大版本中移除。新代码一律不写弃用命令，存量代码在每次大版本升级前完成替换，避免升级当天踩雷。

**升级检查清单**：照单执行能覆盖绝大多数风险点。

- 备份 RDB 与完整 AOF 目录，并在测试环境验证加载。
- 扫描代码中的弃用命令并替换。
- 核对配置文件的改名项与新增项。
- 确认客户端库适配目标版本。
- 演练主从切换与回退路径。
- 升级后观察慢查询、内存与命中率等核心指标。

**版本跟进习惯**：把阅读官方 CHANGELOG 与 release notes 变成例行动作。

- 每个大版本发布后通读官方 release notes，重点看破坏性变更、配置改名与弃用清单，而不是只看新特性列表。
- 生产环境锁定具体补丁版本，定期跟进该版本线的安全修复，不要盲目追新。
- 关注官方博客与文档的升级指南；分叉之后，还需同时留意 Valkey 项目的独立发布节奏，确认自己跟进的是哪条线。
- 排查问题时先确认版本号（redis-server --version 或 INFO server），再对照对应版本的文档，避免张冠李戴。
- 订阅官方安全公告，漏洞修复版本的跟进优先级高于一切新特性。
- 把每次升级的变更记录沉淀进团队文档，逐步积累自己的版本演进知识库。

> 跟进节奏参考：大版本发布后先观察一到两个补丁版本，安全公告单独建立跟进通道，其余功能类更新按季度集中评估——把“追版本”从被动响应变成周期性决策。

**信息源优先级**：官方 release notes 与 CHANGELOG 优先于二手文章，官方命令文档的弃用标注优先于社区记忆；分叉后注意区分 Redis 与 Valkey 各自的发布页，不要混用两者的变更说明。

> [!TIP]
> **建议内容**：为团队维护一份内部升级清单，记录当前使用版本、目标版本、业务代码中的弃用命令扫描结果与回滚预案；每次升级前照单执行，可将版本演进带来的风险降到最低。

**速记**：升级三件事——**先备份、先从库、扫弃用**；跟进两件事——**读 release notes、锁定补丁版本**。
