## 底层数据结构：字典与渐进式 rehash

### 字典在 Redis 中的地位

#### 字典是 Redis 最通用的底层构件

**字典（dict）**：是 Redis 内部使用最广泛的底层结构，数据库键空间与多数集合类型的底层编码都以它为骨架。

- **数据库键空间**：每个数据库就是一个大字典，键为 SDS 字符串，值为指向 redisObject 的指针，一切键命令的入口都是这个字典的查改（详见第 13 章）。
- **Hash 类型**：哈希对象在元素较多或值较长时编码为 hashtable，底层正是本篇的字典（详见第 4 章）。
- **Set 类型**：普通字符串集合在元素较多时编码为 hashtable，元素充当字典的键、值置空（详见第 6 章）。
- **ZSet 类型**：有序集合由跳表与字典共同实现，字典负责成员到分值的 O(1) 定位（详见第 12 章）。
- **过期键与淘汰**：过期字典记录键的过期时间，内存淘汰在键空间字典上挑选牺牲者（详见第 14 章、第 15 章）。
- **集群元数据**：集群的节点表与槽位映射同样以字典组织（详见第 22 章）。
- **Pub/Sub 与内部状态**：模式订阅表、命令表等服务器内部映射也以字典实现，可见其通用性贯穿整个服务器。

学到这里应建立一个视角：Redis 是一个“字典上的系统”——类型系统给它披上多种数据类型的外衣，剥离之后内核反复做的都是同一件事：往哈希表里查、插、删一个键值对。

这一视角还有实用价值：排查大 key 与热 key 时，最终都要落回字典的桶分布与节点数量上思考；掌握了字典，性能问题的定位就有了结构层面的抓手（详见第 29 章）。

本篇按《Redis 设计与实现》与早期源码的**经典结构**讲解。Redis 7.0 对字典实现做过紧凑化改造，节点存储与经典结构有差异，涉及变化处单独点出；读旧源码与应对面试均以经典结构为准。

**速记**：**键空间是字典，Hash、Set、ZSet 的底层也是字典**。



#### 为什么不用平衡树或开放寻址

**选型结论**：字典底层选择**哈希表加链地址法**，不使用平衡树，也不使用开放寻址，这是读写模式与单线程模型共同决定的。

- **等值查询为主**：键空间与集合类的典型操作是按键取值，哈希表平均 O(1) 的定位能力正中下怀。
- **无须维护有序性**：需要范围查询的场景已由跳表承担，字典不必像平衡树那样维持全序、付出旋转成本。
- **链地址法便于删除**：开放寻址删除节点需墓碑标记，高负载下探测路径急剧变长；链地址法删除只需摘链，冲突密集也能正常运作。
- **扩容语义友好**：链地址法配合渐进式 rehash 可以边服务边搬迁，开放寻址的整表重排更难做增量。
- **扩容倍数自由**：链地址法扩容倍数可按需选择，Redis 取 2 倍；开放寻址对装载率更敏感，倍数选择余地小。
- **实现清晰**：每桶一条单向链表，代码短、易维护，符合 Redis 极简内核的风格。

平衡树的优势在有序遍历与稳定的对数最坏性能，但按值查找仍是 O(log N)，插入删除还要维护旋转；Redis 把有序查询交给跳表、等值查询交给哈希表，两种结构各司其职。

跳表与字典的分工还体现在成本互补上：跳表支持范围扫描但单点定位要 O(log N)，字典定位 O(1) 但不支持有序遍历，ZSet 同时持有两者，正好各取所长。

```text
三种候选方案的定位成本对比（n 为元素数）：
平衡树（红黑树）：O(log n)，且支持有序遍历，但旋转维护开销大
开放寻址哈希表：均摊 O(1)，但删除需墓碑，高负载探测链变长
链地址哈希表：  均摊 O(1)，删除摘链即可，负载因子可大于 1

再加一条现实约束：
Redis 要在单线程上保证每次操作的延迟上限
任何“某一次操作突然变慢”的方案都要被改造或放弃
```

> 概念辨析：开放寻址与链地址法都是解决冲突的手段，前者把冲突项探测放入其他桶，后者把冲突项串在同一个桶的链表上。选链地址法的直接推论是负载因子可以超过 1——节点数不再受桶数限制，由链表长度承接拥挤。

**速记**：等值找**哈希表**，有序找**跳表**，冲突用**链地址**。



### 字典的三层结构

#### dictEntry：键值对节点

**dictEntry**：是哈希表节点，代表字典中的一个键值对，位于三层结构的最内层。

- **key 成员**：保存键，通常指向一个 SDS 字符串。
- **v 联合体**：保存值，四个成员共用一段内存，可存 void 指针、uint64_t、int64_t 或 double。
- **next 指针**：指向同桶的下一个节点，把冲突键值对串成单向链表。

```c
typedef struct dictEntry {
    void *key;              /* 键，通常是 SDS */
    union {
        void   *val;        /* 指针对象值 */
        uint64_t u64;       /* 无符号整数值 */
        int64_t  s64;       /* 有符号整数值 */
        double   d;         /* 浮点数值 */
    } v;
    struct dictEntry *next; /* 同桶下一个节点 */
} dictEntry;
```

值设计成联合体是省内存的技巧：当值本身就是整数或浮点数时直接内联存储，不必再分配对象包装；只有存放复杂对象时才用 val 指针。这减少了小对象的堆分配次数，也提高了访问的缓存命中率。

节点的生命周期与字典操作严格同步：插入时分配、删除时按 type 中的析构函数释放键与值，再归还节点本身；析构逻辑由多态方法提供，使同一套节点结构能服务不同类型。

7.0 紧凑化的动机也在这里：经典结构下每个节点都要为 next 指针付出 8 字节并分散在堆各处，紧凑化把同桶条目排进连续内存，既省内存又让缓存一次加载整条冲突链。

> [!NOTE]
> **提醒内容**：Redis 7.0 起节点不再各带 next 指针，同桶条目改为连续存放、以相对偏移串联，节省了指针内存并改善局部性；经典结构（含 next 指针）仍是理解冲突与 rehash 的基础模型，两者只是物理布局不同，逻辑上都是同桶成链。

**速记**：dictEntry 三件套——**键、值联合体、next 指针**。



#### dictht：哈希表

**dictht**：是哈希表本体，由桶数组与三个控制字段组成，负责键值对的实际存放与定位。

- **table 成员**：指向 dictEntry 数组，每个数组位是一个桶，桶内挂着冲突链的表头。
- **size 成员**：桶数组长度，恒为 2 的幂，保证位运算取模可行。
- **sizemask 成员**：恒等于 size 减 1 的二进制全 1 掩码，与哈希值按位与即得桶下标。
- **used 成员**：已存键值对总数，是负载因子的分子，也是判断 rehash 完成的依据。

```c
typedef struct dictht {
    dictEntry **table;      /* 桶数组 */
    unsigned long size;     /* 桶数，恒为 2 的幂 */
    unsigned long sizemask; /* size - 1 的掩码 */
    unsigned long used;     /* 已存键值对数 */
} dictht;
```

空表的形态是 table 为空、size 与 used 均为 0：新建字典时 ht[1] 就处于这种未分配状态，直到 rehash 开始才为它分配空间。size 恒为 2 的幂换来一个直接收益——对 size 取模可以写成与 sizemask 按位与，一条位运算指令完成，这是桶下标计算高效的前提。

四个字段里只有 table 会随 rehash 整体更换，size 与 sizemask 同步更新，used 则随增删实时增减——理解每个字段在 rehash 各阶段的读法，是手推流程题的基础。

```text
一张已填充的哈希表（size = 4）：
table ─┬─ 桶0 ──► A ──► NULL
       ├─ 桶1 ──► B ──► C ──► NULL
       ├─ 桶2 ──► NULL
       └─ 桶3 ──► D ──► NULL
size = 4，sizemask = 3，used = 4，负载因子 = 1.0
桶1 上 B、C 冲突成链，但 used 仍逐节点计数为 4

掩码的二进制视角：
size = 4      → 0b100
sizemask = 3  → 0b011（全 1）
hash & sizemask 即取哈希值的低 2 位作下标
```

> 概念辨析：table 是桶的数组而非节点的数组，数组位上放的常常只是链表头指针；used 计的是节点数而非桶数，冲突链再长也逐个计数。

**速记**：dictht 四字段——**table、size、sizemask、used**，size 恒为**二的幂**。



#### dict：字典与双表设计

**dict**：是字典类型的最外层结构，持有一对哈希表与一个 rehash 游标，是所有字典操作的入口。

- **type 成员**：指向 dictType，内含针对不同键值类型的哈希函数、键比较、析构等多态方法，使一套字典代码服务多种用途。
- **privdata 成员**：携带调用多态方法时所需的私有参数。
- **ht 数组**：长度恒为 2，ht[0] 平时存放全部数据，ht[1] 仅在 rehash 期间启用。
- **rehashidx 成员**：rehash 进度游标，-1 表示未在 rehash，0 及以上表示正在搬运，其值是下一个待搬桶的下标。

```c
typedef struct dict {
    dictType *type;     /* 类型特定函数（多态） */
    void *privdata;     /* 私有数据 */
    dictht ht[2];       /* 两张哈希表 */
    long rehashidx;     /* rehash 进度，-1 未进行 */
} dict;
```

双表是渐进式 rehash 的物质基础：平时只用 ht[0]；rehash 期间两表并存，数据从 ht[0] 流向 ht[1]；搬完后 ht[1] 整体顶替 ht[0]。单表实现做不到“边服务请求边搬家”，这一字段布局就是 Redis 与普通哈希表实现的分水岭。

多态设计同样值得注意：键空间字典、过期字典、Hash 编码字典各有自己的哈希与比较需求，type 指针让它们复用同一套 dict 框架，这正是 dictType 中每个函数指针存在的意义。

> 概念辨析：ht[1] 顶替 ht[0] 之后，ht[1] 被重置为空表，“ht[0] 是主表”的说法始终成立——编号不变而实体已换，后续再扩容时 ht[1] 又从空表重新出发。

**速记**：dict 持**双表**，rehashidx 记**进度**，**负一未搬、非负在搬**。



#### 三层结构的整体示意

**三层嵌套关系**：dict 包着 dictht 数组，dictht 的桶数组挂着 dictEntry 链表，自外向内逐层展开。

```text
dict
├─ dictType *type ── 哈希函数 / 键比较 / 析构（多态）
├─ void *privdata ── 传给多态函数的参数
├─ dictht ht[2]
│   ├─ ht[0]（主表）
│   │    ├─ table ─┬─ 桶0 ──► dictEntry ──► dictEntry
│   │    │         ├─ 桶1 ──► dictEntry
│   │    │         ├─ 桶2 ──► NULL
│   │    │         └─ 桶3 ──► dictEntry
│   │    ├─ size = 4，sizemask = 3
│   │    └─ used = 4
│   ├─ ht[1]（备用表，未分配：table 为空、size 为 0）
│   └─ rehashidx = -1（未在 rehash）
└─ rehash 方向：ht[0] ──► ht[1]

rehash 进行中的同一结构（rehashidx = 2）：
├─ ht[0]：桶 0、1 已搬空，数据只剩桶 2、3
├─ ht[1]：已分配，承接搬迁节点与新写入节点
└─ rehashidx = 2，指向下一个待搬桶

dictEntry 内部（链上任一节点）：
┌─────────────────────────────┐
│ key ──► "name"（SDS 字符串） │
│ v   ──► 值对象 / 整数内联    │
│ next ──► 同桶下一节点或 NULL │
└─────────────────────────────┘
```

画图与口述都按“字典、哈希表、节点”的顺序自外向内：先说 dict 的双表与游标，再说 dictht 的四字段，最后说 dictEntry 的三件套。面试白板画图时先画三层框再填字段，层次不会乱。

若画出 rehash 进行中的状态，区别只有三处：ht[1] 已分配且有数据、rehashidx 大于等于 0、部分桶在 ht[0] 中已空——其余结构与平时完全一致，两张图对照着画最能加深理解。

> 概念辨析：图中桶2 为 NULL 表示空桶，空桶不影响负载因子的语义——used 只数节点、size 只数桶位，二者之比天然涵盖了空桶带来的浪费。

**速记**：**dict → dictht → dictEntry**，口述与画图都由外到内。



### 哈希算法与键冲突

#### 哈希函数与桶下标计算

**哈希定位**：键先经哈希函数算出整型哈希值，再与 sizemask 按位与得到桶下标，两步完成定位。

- **算法演进**：Redis 5.0 之前使用 MurmurHash2，5.0 起对字符串键改用 SipHash，整数键另有专门的整数哈希。
- **换用 SipHash 的动机**：SipHash 带密钥，攻击者无法离线构造大量同桶键，缓解了哈希碰撞拒绝服务攻击——这类攻击对单线程服务器尤其致命。
- **均匀性**：两种算法都追求输出位均匀分布，让键尽量散落到不同桶，控制冲突链长度。
- **下标公式**：index = hash & sizemask，等价于 hash 对 size 取模，但只需一条位运算指令。

```text
设 size = 4，则 sizemask = 3（二进制 11）

key1: hash = 0b1010 (10) → 10 & 3 = 0b10 → 桶 2
key2: hash = 0b0111 ( 7) →  7 & 3 = 0b11 → 桶 3
key3: hash = 0b1001 ( 9) →  9 & 3 = 0b01 → 桶 1
key4: hash = 0b1011 (11) → 11 & 3 = 0b11 → 桶 3（与 key2 冲突）

规律：掩码只保留哈希值的低 log2(size) 位
     size 翻倍后掩码多看一位，同一键的下标随之改变
```

哈希函数对使用者完全透明：对外只保证同一键恒得同一哈希值。rehash 时 sizemask 变大，同一键在 ht[1] 的下标通常不同于 ht[0]，这正是搬迁必须逐键重算下标的原因——不是把节点平移，而是重新定位。

SipHash 的密钥在服务器启动时随机生成，因此同一组键在不同实例、不同重启之间算出的哈希值也不同，碰撞模式无法被预知，这是防御的根基。

MurmurHash2 并非不能用：它只是不带密钥，算法公开意味着攻击者可离线批量构造同桶键；SipHash 在性能接近的前提下补上密钥这一环，属于低成本高收益的升级。两个算法都不必深究轮函数，考点停留在版本演进加动机的层面。

> 概念辨析：掩码法成立的唯一前提是 size 恒为 2 的幂；若 size 是任意整数，掩码不再是全 1，按位与的结果分布就会倾斜。这也是扩缩后的新表大小仍取 2 的幂的原因。

**速记**：先 **SipHash** 算哈希，再 **与掩码**得下标，掩码即 **size 减一**。



#### 键冲突与链地址法

**链地址法**：是 Redis 解决哈希冲突的方式，把哈希值映射到同一桶的节点用 next 指针串成单向链表。

- **头插法**：新节点总是插到链表头部，插入 O(1)，无须遍历既有链。
- **头插的直觉**：刚写入的键大概率很快被再次访问，放头部能缩短热键的命中路径。
- **计数联动**：每次插入对应表的 used 加一，删除则减一，负载因子随之实时变化。
- **与扩缩的配合**：冲突链越长查找越慢，链地址法本身不控制链长，控制链长的职责交给负载因子阈值与扩容。
- **7.0 的紧凑化**：节点不再各带 next 指针，同桶条目连续存放、以相对偏移串联，省指针内存也减少缓存未命中。

```text
桶 3 的链表随写入与删除变化（头插）：
写入 key2 后：桶3 ──► key2
写入 key4 后：桶3 ──► key4 ──► key2
写入 key6 后：桶3 ──► key6 ──► key4 ──► key2
删除 key4：  桶3 ──► key6 ──► key2（摘链，used 减一）
查找 key2：  定位桶 3，沿链 head → key6 → key2 命中
```

头插法在 Redis 中是安全的：单线程下不存在并发遍历与并发插入的竞态。Java 7 的 HashMap 曾因并发头插把链表插成环，Java 8 改为尾插，那是多线程语境的教训，不能拿来否定 Redis 的头插设计。

插入时的完整动作值得默背：先算哈希定桶，再分配节点、键值指针就位，接着头插接链，最后 used 加一——四步里没有遍历，这正是插入恒定 O(1) 的原因。

链表遍历只发生在冲突发生之后：命中路径先比哈希值或键值再前进，链越长查找越慢，这正是负载因子阈值要控制链长、而哈希函数要保证散布均匀的动机。

删除某个节点时还要沿链找到它的前驱才能摘除，最坏要遍历整条冲突链；不过单线程与短链两个前提让这一点在实践中不构成瓶颈。

> 概念辨析：链地址法的负载因子可以大于 1——每个桶只放一个链表头，节点数不受桶数限制；开放寻址的负载因子必须小于 1，表满即无处可放。这是两种方法最外显的差异。

**速记**：冲突**串链表**，新节点**插表头**，单线程**无成环风险**。



### 负载因子与自动扩容收缩

#### 负载因子的定义与计算

**负载因子（load factor）**：是哈希表已用节点数与桶数之比，即 ht[0].used 除以 ht[0].size，是扩容与收缩决策的唯一标尺。

- **公式**：负载因子 = ht[0].used / ht[0].size。
- **used 的口径**：键值对节点总数，不是桶数，也不区分节点是否挂在冲突链上。
- **经验解读**：约等于 1 表示平均每桶一个节点，链短查得快；远小于 1 表示大量空桶在浪费内存；远大于 1 表示冲突链普遍变长，查找退化。
- **作用域**：决策只看 ht[0]，ht[1] 在 rehash 期间不参与因子判断。

```text
size = 8, used = 8  → 负载因子 1.0（扩容线附近）
size = 8, used = 16 → 负载因子 2.0（冲突链平均长 2）
size = 8, used = 1  → 负载因子 0.125（接近收缩线 0.1）
size = 4, used = 9  → 负载因子 2.25（链长不均，最坏桶更长）
```

负载因子描述的是平均拥挤程度，不反映分布均匀性：即使因子不高，个别桶也可能堆出长链。哈希函数的均匀性把这种偏斜压到很低，工程上只盯因子即可，无须逐桶监控。

它还是理解字典一切行为的入口：扩容、收缩、rehash 的推进速度、查找路径的长短，追根溯源都是这个比值在驱动，读源码时盯住 used 与 size 的变化即可推演全局。

rehash 进行中负载因子会阶段性失真：数据分居两表，ht[0].used 持续下降而 ht[1].used 持续上升，此时不再依据 ht[0] 的因子做新的扩缩决策，直到搬迁完成。

计算时还有一个细节：used 与 size 都是无符号整型，实际代码用乘法比较（used × 10 与 size 比较）来避免除法与浮点，手算时按除法理解即可，结论完全一致。

另外注意口径问题：因子按节点数而非键数计算。过期字典里一个键占一个节点，键空间里一个键也占一个节点，两本账分开算、各自触发各自的扩缩。

> 概念辨析：Java HashMap 的默认扩容阈值是 0.75，Redis 无持久化时是 1——别把两者记混。Redis 敢把因子放到 1，靠的是 SipHash 的均匀性与单线程下可控的链长。

**速记**：负载因子 = **used ÷ size**，约 **1 拥挤、约 0 稀疏**。



#### 扩容与收缩的触发条件

**扩缩规则**：负载因子越过阈值即触发 rehash，扩容让表变大以降冲突，收缩让表变小以省内存，二者走同一条渐进式流程。

- **平时扩容**：负载因子大于等于 1 时扩容，新表大小为第一个大于等于 used 乘 2 的 2 的幂。
- **持久化期间扩容**：服务器执行 BGSAVE 或 BGREWRITEAOF 期间，负载因子大于等于 5 才扩容，阈值放宽五倍。
- **收缩**：负载因子小于 0.1 时收缩，新表大小为第一个大于等于 used 的 2 的幂。
- **方向无关**：扩或缩只决定 ht[1] 的大小，搬迁流程与游标推进完全一致。
- **目标取幂**：新表大小向上取 2 的幂，保证 sizemask 掩码法继续成立。

```text
例一：used = 4，size = 4，无子进程，因子 1.0 ≥ 1 → 扩容
      used × 2 = 8，新表 size = 8
例二：used = 20，size = 8，正在 BGSAVE，因子 2.5 < 5 → 暂不扩容
例三：used = 30，size = 8，正在 BGREWRITEAOF，因子 3.75 < 5 → 暂不扩容
例四：used = 1，size = 64，因子 0.016 < 0.1 → 收缩
      新表 size = 1（第一个 ≥ used 的 2 的幂）
例五：used = 48，size = 64，无子进程，因子 0.75 < 1 → 不动
例六：used = 1000，size = 512，无子进程，因子 1.95 ≥ 1 → 扩容
      used × 2 = 2000，新表 size = 2048（向上取 2 的幂）
```

扩容取两倍下取幂是空间与延迟的平衡：翻倍保证下次触发前有充分余量，取 2 的幂保住掩码法；收缩按 used 取幂则尽量归还内存，批量删除大量键后表会自动缩小。

> [!WARNING]
> **警告内容**：阈值数字是高频考点也是高频记错点——平时 **1 扩、0.1 缩**，持久化期间 **5 才扩**；且收缩阈值没有“有子进程就放宽”的例外，任何时刻小于 0.1 都照常收缩。三个数字与一个例外必须整组记忆。

**速记**：**≥1 扩、<0.1 缩**，有持久化子进程**≥5 才扩**。



#### 持久化期间提高扩容阈值的原因

**放宽阈值的原因**：持久化子进程依赖写时复制与父进程共享内存页，父进程此时扩容会大规模写页，抵消共享收益甚至引发内存翻倍。

- **写时复制机制**：BGSAVE 或 BGREWRITEAOF fork 子进程后，父子共享同一批物理内存页，只有被写的页才复制副本，未写的页继续共享（详见第 17 章）。
- **扩容是整表写入**：搬迁要为几乎每个节点重新分配并写入，等于把哈希表重写一遍，相关内存页几乎全部复制。
- **风险叠加**：页复制使内存占用陡增，最坏情形接近翻倍，在内存紧张的实例上可能触发 OOM。
- **权衡结果**：宁可让冲突链暂时变长、查找稍慢，也要在持久化窗口内保住页共享，故阈值从 1 放宽到 5。

```text
持久化窗口内的两难：
扩容 → 写遍全表 → 写时复制大爆发 → 内存可能翻倍
不扩 → 冲突链变长 → 查找稍慢但内存平稳
Redis 的选择：把扩容推迟到持久化结束（阈值 1 → 5）

时间线：
t0 发起 BGSAVE，fork 子进程，页共享开始
t1 负载因子升至 2.5，低于 5，不扩容，页共享不受破坏
t2 子进程落盘完成退出，共享结束
t3 负载因子仍 ≥ 1，扩容照常触发

极端对照：若无此放宽，一个 10GB 实例在 BGSAVE 期间扩容
最坏要为搬迁再复制近 10GB 的页，内存瞬时逼近翻倍
```

这里的“提高”是推迟而非取消：持久化结束、子进程退出后，负载因子若仍超线，扩容照常进行。它本质是延迟敏感的单线程服务器在内存与延迟之间做的让步。

BGREWRITEAOF 与 BGSAVE 对扩容阈值的影响完全相同，因为二者都走 fork 加写时复制的路径；区别只在子进程落盘的目标是 RDB 文件还是 AOF 重写文件。

同理，主从复制中主库向从库全量同步时也要 fork 出子进程落盘 RDB，那一窗口内的扩容阈值同样放宽到 5——凡 fork 之处，皆有此让步（详见第 20 章）。

> [!CAUTION]
> **注意内容**：不要把“持久化期间不扩容”绝对化——阈值放宽到 5 之后负载因子仍可能到达 5 并触发扩容；也不要认为收缩在持久化期间被豁免，收缩条件没有类似放宽。极端堆积下冲突链变长属于可接受的临时代价。

**速记**：fork 后**写页才复制**，扩容**写遍全表**会引爆复制，故**放宽阈值延后扩容**。



### 渐进式 rehash

#### rehash 的完整流程

**rehash 流程**：是数据从 ht[0] 整体迁往 ht[1] 的过程，分建表、搬运、收尾三个阶段，由 rehashidx 全程标记进度。

- **建表**：按扩容或收缩规则算出目标大小，为 ht[1] 分配空间，rehashidx 置 0，标志 rehash 开始。
- **事件搬运**：此后每次键空间的增删改查，都顺带把 ht[0] 中 rehashidx 指向的桶（跳过空桶）整桶搬进 ht[1]，然后 rehashidx 加一。
- **定时搬运**：服务器定时任务按毫秒预算批量搬桶，保证无人访问的字典也能推进。
- **收尾**：ht[0].used 归零后释放旧 ht[0]，把 ht[1] 设为新的 ht[0]，ht[1] 重置为空表，rehashidx 置回 -1。
- **触发来源**：扩容与收缩共用此流程，差别只在 ht[1] 的大小与方向。

```text
阶段一（建表）：ht[0] 全量数据，ht[1] 分配完成，rehashidx = 0
阶段二（搬运）：
  搬桶 0 → rehashidx = 1
  搬桶 1 → rehashidx = 2
  ……每桶：取出链上每个节点，重算下标，头插进 ht[1]

桶级细节（搬桶 1，链上有 B、C）：
  取 B：hash & ht[1].sizemask → 落 ht[1] 桶 5，头插
  取 C：hash & ht[1].sizemask → 落 ht[1] 桶 3，头插
  ht[0].used 减 2，rehashidx 前进到 2

阶段三（收尾）：ht[0].used = 0
  释放旧 ht[0]，ht[1] 接任为 ht[0]，ht[1] 复位为空
  rehashidx = -1
```

桶内的搬迁是逐节点重插而非整体平移：取出链上每个节点，用 ht[1] 的 sizemask 重算下标，再头插到 ht[1] 的对应桶中；同一桶的节点搬迁后可能散落到新表的多个桶，这正是重算下标的意义。

rehashidx 的语义是进度线：下标小于 rehashidx 的桶已全部搬空。据此单步函数可以精确知道该搬哪一桶，访问者也能 O(1) 判断某个桶的归属，避免重复搬迁。

面试手推流程题时按此三阶段作答最稳：先写两表状态与游标初值，再写一次搬迁涉及的表与计数变化，最后写收尾的换表动作——三段各自独立给分，不会因一处卡壳全盘皆输。

顺带一提，收尾阶段的“表互换”是三步指针赋值而非数据搬运：ht[0] 与 ht[1] 的内容整体交换、旧表内存释放，数据本身一个字节都不用再动，这正是双表设计的收尾红利。

> [!TIP]
> **建议内容**：把流程压缩成四拍口诀——**建新表、搬桶走、表互换、游标清**。答题时按这四拍展开，再补一句“新表大小取 2 的幂、游标指向下一个待搬桶”，流程分即可拿满。

**速记**：**建新表、置游标、逐桶搬、归零换表**。



#### 渐进式的核心思想

**渐进式 rehash**：把一次性 O(N) 的整表搬迁拆成无数个 O(1) 的小步，摊到后续每一次命令与定时任务里完成。

- **动机**：单线程执行命令，一次性搬几百万节点意味着数百毫秒到数秒的阻塞，期间所有请求排队，这对面向网络的服务不可接受。
- **摊销方式**：每条命令搭车搬一个桶，定时任务按毫秒预算批量搬，搬迁总工作量不变，但被切成细粒度片段。
- **代价**：rehash 期间双表并存，内存高于平时；查找可能要查两张表，删除与更新可能跨表。
- **思想归属**：这就是摊还分析——总成本不变，把峰值成本削平成均匀的小成本，换取每次操作的延迟上限可控。

```text
一次性扩容（普通哈希表）：
  命令 X：阻塞 500ms 搬完全部节点，其余请求全部排队

渐进式扩容（Redis）：
  命令 1：搬 1 桶，微秒级
  命令 2：搬 1 桶，微秒级
  定时任务：每毫秒搬一批
  ……总时长略增，但无任何一次长阻塞

等价视角：搬迁成本被“贴现”为每次操作的一点点额外开销
```

渐进式的总成本略高于一次性方案：多付双表内存、两表查找，以及游标维护的开销。但延迟的方差被大幅压低，对以响应时间为生命线的在线服务，这笔交易稳赚。

换一个角度看，这也是 Redis 对“慢操作”的系统性态度：所有可能 O(N) 的命令（KEYS、SMEMBERS 等）都有阻塞单线程的风险，渐进式 rehash 则是从数据结构内部就把这种风险拆掉了（详见第 29 章）。

答题时的表述层次也值得演练：先一句话下定义，再说动机（单线程怕阻塞）、做法（摊销到命令与定时任务）、代价（双表与两表查找），最后落在思想（摊还分析）收束，层次即完整。

> [!IMPORTANT]
> **重要内容**：渐进式的成立依赖两条配套规则——新增只写 ht[1]（保证 ht[0] 只减不增、搬迁必然收敛），以及 rehashidx 逐桶推进（保证每一步的边界清晰）。记忆思想时必须连这两条规则一起记，否则流程细节无从推导。

**速记**：**大事化小、摊进每次操作**，用**短期双表内存**换**延迟无尖刺**。



#### rehash 期间的查找与新增规则

**rehash 期间的读写规则**：查找先 ht[0] 后 ht[1]，更新在命中表上原位进行，删除可能命中任一表，而新增一律只进 ht[1]。

- **查找**：先用 ht[0] 的 sizemask 定位，未命中再用 ht[1] 的 sizemask 定位，两表皆无才返回不存在。
- **更新**：找到节点所在表后原表改值，不迁移、不换表。
- **删除**：在命中的表上摘链，并令该表 used 减一。
- **新增**：只写 ht[1]，ht[0] 的节点数只减不增，rehash 因此必然收敛。
- **恢复常态**：ht[0].used 归零即收尾换表，读写规则随之恢复单表常态。

```text
rehash 进行中（rehashidx = 2，桶 0、1 已搬空）：
查 key（原桶 0）：ht[0] 桶 0 已空 → 转查 ht[1] → 命中
查 key（仍在桶 3）：ht[0] 桶 3 → 直接命中
改 key（已在 ht[1]）：在 ht[1] 原表改值，不搬家
删 key（仍在 ht[0] 桶 3）：从 ht[0] 摘链，ht[0].used 减一
新写 key：只进 ht[1]，无论 ht[0] 的对应桶是否空
```

新增只进 ht[1] 是收敛的保证：若两表都允许写入，ht[0] 的存量可能被新写入抵消，used 永远减不到零，rehash 就没有终点。同理，判“键不存在”必须两表都查过，只查 ht[0] 会误报。

这套规则在特殊键值接口上同样成立：字典的原子递增、随机取键等操作都封装了同样的双表语义，调用方拿到的结果与单表时代完全一致，这正是封装的价值。

> 概念辨析：这套规则对外完全透明——命令语义不变，只是实现上多查一次、多写一处。应用层无须感知 rehash 是否正在进行，体现了结构与策略对接口透明的设计原则。

**速记**：查找**先零后一**，新增**只进一号**，删除**命中即摘**。



#### rehash 的两个驱动时机

**rehash 的驱动时机**：搬迁由事件驱动与时间驱动双轮推进，前者搭命令的便车，后者由定时任务主动补搬。

- **事件驱动**：每次执行键空间的增删改查命令时，调用单步搬迁函数顺带搬一个桶，单步开销微秒级，命令几乎无感。
- **时间驱动**：serverCron 定时任务周期性调用以毫秒为预算的批量搬迁函数，每批搬一批桶，预算用尽即停（详见第 16 章）。
- **双轮互补**：热点库靠命令本身即可快速搬完；冷库长期无人访问，靠定时任务兜底推进。
- **预算控制**：定时搬迁以时间为界而非桶数为界，保证补搬本身不会反过来阻塞事件循环。

```text
事件驱动：客户端命令 → 处理该命令 → 顺手搬 1 桶 → 返回响应
时间驱动：serverCron 触发 → 以 1ms 为预算 → 批量搬桶 → 到时即止
两轮独立运转、互不等待，任意一轮都能独立完成搬迁

冷热互补：
热点库：命令密集 → 事件驱动为主，搬迁迅速完成
冷库：  几乎无命令 → 时间驱动兜底，缓慢但确定地推进
```

面试常追问两个极端：“字典再也没人访问，rehash 能完成吗”——能，时间驱动兜底；“rehash 会不会拖慢命令”——事件驱动每步只搬一桶，摊销后可忽略。

毫秒预算的取值也值得留意：批量搬迁函数以 1 毫秒为单次预算，预算内能搬多少桶搬多少；这个数字再叠加事件循环的调度周期，就决定了 rehash 对正常请求延迟的最坏干扰上限（详见第 16 章）。

两轮驱动在源码中的落点也常被问到：事件驱动藏在字典的增删改查函数内部的单步搬迁调用里，时间驱动则由定时任务里的数据库维护函数统一发起——名字可以不背，但“一在命令路径、一在定时路径”的归属要清楚。

> 概念辨析：单步搬迁跳过空桶也要付出探测成本，极端稀疏的表上单步可能连续探测多个空桶；因此批量函数在时间预算之外还限制单轮探测的空桶数，防止空表扫描拖长单轮耗时。

**速记**：**命令搭车搬一桶，定时任务按毫秒批搬**，双轮任一都保收敛。



### 与 Java HashMap 的思想对照

#### 扩容思想的一次性与渐进式对照

**核心差异**：Java HashMap 的扩容在当前调用内一次性完成，Redis 把扩容摊到后续操作中渐进完成，取舍根源是线程模型与服务形态不同。

- **HashMap 的节奏**：负载因子越过默认 0.75 触发 resize，在当前 put 调用内一次搬完全部节点，单次耗时随表规模线性增长。
- **Redis 的节奏**：越过阈值只建新表、置游标，搬迁摊进后续命令与定时任务，单次命令耗时恒定。
- **线程模型根源**：HashMap 的延迟尖刺由单次调用者承担；Redis 单线程面向网络服务，一次尖刺即全局停摆，必须削峰。
- **思想同源**：两者都按 2 的幂扩表、位运算取模、按负载因子触发——底座相同，节奏不同。
- **过渡成本**：HashMap 搬完即恢复单表干净利落；Redis 在 rehash 期间要付双表内存与两表查找的过渡成本，是典型的空间换平滑。
- **冲突策略**：两者同为链地址法，HashMap 在链长超过阈值后还会树化为红黑树，Redis 不树化而靠扩容控制链长。

```text
对照总览：
触发：HashMap 因子 ≥ 0.75 ｜ Redis 因子 ≥ 1（平时）
搬迁：HashMap 一次搬完    ｜ Redis 渐进摊销
代价：HashMap 单次延迟尖刺 ｜ Redis 双表内存 + 两表查找
冲突：HashMap 长链树化    ｜ Redis 靠扩容控制链长
前提：HashMap 多线程需外部同步 ｜ Redis 单线程无竞态
阈值：HashMap 收缩不自动  ｜ Redis 因子 < 0.1 自动收缩
```

HashMap 树化的存在恰好反衬 Redis 的取舍：单线程下若放任长链再树化，插入与搬迁都更复杂；Redis 选择更勤地扩容，让链长始终短暂，结构保持极简。

对照的延伸价值在于面试迁移：被问“Java 里能不能也做渐进式 rehash”时，答案是能但收益有限——多线程下搬迁要处理并发可见性，收益不如直接用 ConcurrentHashMap 的分桶思路；渐进式的土壤是单线程加共享全表。

最后给一个记忆策略：先用一句话锚定差异（“一个搬一次，一个慢慢搬”），再依次展开触发阈值、搬迁节奏、代价与根源四层，对照题的答法就完整了。

> 概念辨析：渐进式并非 Redis 独有，本地缓存等实现也有分批搬迁的思路；但把它用在单线程网络服务器的核心键空间并贯穿始终，Redis 是教科书案例。对照记忆抓一个词——**削峰填谷**。

**速记**：HashMap **一次搬完有尖刺**，Redis **摊销搬完延迟平**，根源是**单线程**。
