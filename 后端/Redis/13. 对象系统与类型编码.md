## 对象系统与类型编码

**对象系统与类型编码**：是 Redis 在数据类型与底层数据结构之间架起的统一抽象层——每个键值对的值都被包装成 redisObject 对象，对象以 type 字段对外承诺逻辑类型，以 encoding 字段对内选择底层结构，再辅以引用计数、对象共享与 LRU 元数据，支撑内存回收、内存节省与淘汰决策。

- 本章先建立对象层的整体认识：为什么要有 redisObject，它的五个字段各自承担什么。
- 再给出类型与编码的总对应表，并逐类展开 string、list、set、hash、zset 的编码选择与阈值配置。
- 然后讲编码转换机制：何时触发升级、为何只升不降。
- 最后讲两个横切机制与实战：引用计数与对象共享、lru 字段的双重职责、OBJECT 命令族的观察实验。
- 底层数据结构本身（SDS、字典、跳表、intset、listpack、quicklist）分别在第 10、11、12 章详解，本章只回答一个问题：对象层如何在这些结构之间做选择。

### 对象系统的认识

#### 对象系统是键值之上的统一抽象

**对象系统**：Redis 在数据类型与底层数据结构之间引入的一层封装，任何键与值入库后都以 **redisObject**（常简称 robj）的形式存在。

- 面向用户的视角：TYPE 命令看到的是 string、list、set、zset、hash 五种**逻辑类型**，这是 API 层面的抽象承诺。
- 面向内部的视角：OBJECT ENCODING 看到的是 int、embstr、quicklist、listpack、hashtable、skiplist 等多种**编码**，对应真正承载数据的结构。
- redisObject 同时承载逻辑类型、底层编码、引用计数与 LRU/LFU 元数据，是引用计数回收与内存淘汰策略的共同作用载体。
- 引入对象层的收益：同一逻辑类型可以按数据规模自动切换底层实现，命令接口保持不变，内存与性能随数据形态自适应。
- 没有对象层的代价：若命令直接绑定某种结构，String 存整数与存字符串就得拆成两套命令，编码升级也会直接破坏兼容。
- 对象层同时是内省与运维的抓手：OBJECT 系列命令、引用计数、空转时间都挂在 robj 上，为诊断与淘汰提供依据。
- 版本演进：7.0 将 ziplist 全面替换为 listpack，部分编码名随之变化，但逻辑类型与命令完全不变，这正是对象层隔离变化的价值。
- 命令族由类型分派：同名命令对不同类型各有实现入口，类型检查失败即报 WRONGTYPE，分派依据正是 robj 的 type 字段。
- robj 上还可通过 DEBUG OBJECT 查看更多调试信息，该命令属开发诊断用途，生产观察以 OBJECT 系列为准。

```bash
redis-cli SET greeting hello
redis-cli TYPE greeting            # string，逻辑类型不变
redis-cli OBJECT ENCODING greeting # embstr，底层编码可变
redis-cli APPEND greeting "!"
redis-cli OBJECT ENCODING greeting # raw，类型仍是 string
```

> 辨析：五大数据类型是用户视角的抽象，不是数据结构；SDS、listpack、skiplist 是数据结构，不是类型。两者之间隔着的正是对象系统这一层，底层结构逐一详见第 10 章、第 11 章、第 12 章。

**速记**：外看**五种类型**，内看**多种编码**，中间隔一层 redisObject。



#### redisObject 的五个字段与 embstr 布局

**redisObject 的结构**：由 type、encoding、lru、refcount 与 ptr 五个成员组成，定义于源码 server.h，在 64 位平台结构体本身仅占 16 字节。

```text
typedef struct redisObject {
    unsigned type:4;      // 逻辑类型，如字符串、列表、集合
    unsigned encoding:4;  // 底层编码，如 int、embstr、listpack
    unsigned lru:24;      // LRU 时钟或 LFU 元数据，一槽两用
    int refcount;         // 引用计数，4 字节
    void *ptr;            // 指向底层数据结构，8 字节
} robj;
```

- **type**（4 位位域）：逻辑类型，取值如 OBJ_STRING、OBJ_LIST、OBJ_SET、OBJ_ZSET、OBJ_HASH，TYPE 命令读出的正是它。
- **encoding**（4 位位域）：底层编码，取值如 OBJ_ENCODING_INT、OBJ_ENCODING_EMBSTR、OBJ_ENCODING_RAW、OBJ_ENCODING_LISTPACK、OBJ_ENCODING_SKIPLIST。
- **lru**（24 位位域）：一专多能的元数据槽位。淘汰策略为 LRU 系列时存最近访问时钟；4.0 起为 LFU 系列时拆成 16 位分钟级时间戳加 8 位对数计数器，属于借位复用，字段本身并未加宽。
- **refcount**（4 字节整型）：引用计数，支撑对象共享与内存回收，减到 0 立即释放。
- **ptr**（8 字节指针）：指向真正的底层数据，如 SDS、dict、quicklist、zskiplist；int 编码时甚至直接把整数值塞进指针槽位，指针即数据。

> 网络上流传 redisObject 占 25 字节的说法：那是把 16 字节的 robj、旧版本 8 字节的 SDS 头部与 1 字节结尾符合并后得到的粗略口径，描述的是短字符串对象整块的常驻大小；现代源码中结构体本身只有 16 字节。位域压缩让 type、encoding、lru 三者合占 4 字节，这是 16 字节结论的由来。

ptr 与 SDS 还有一种更紧密的复用，即 **embstr 布局**：短字符串把 robj 与 SDS 头部连续放进同一块内存，ptr 指向紧随其后的 buf 数组，一次分配即可建成整个对象。

```text
raw 编码：  [robj 16B] --ptr--> [sdshdr 3B | buf | \\0]   两次分配
embstr：    [robj 16B | sdshdr8 3B | buf | \\0]  ptr 指向块内   一次分配
```

- raw 的常规布局：robj 一块、SDS 一块，共两次内存分配，ptr 跨块指向 SDS。
- embstr 的紧凑布局：robj、sdshdr8 与字符串数据三者连续，仅一次分配，省去分配与释放的调用开销，短字符串的创建销毁非常频繁。
- 局部性收益：robj 与数据大概率落在同一缓存行附近，读取更快。
- 固有代价：连续布局无法扩容，SDS 的 alloc 预算被固定，所以 embstr 是**只读**的。
- 修改路径：APPEND、SETRANGE 等任何写命令都会先把 embstr 解包成 raw 再写，源码中对应 embstr2raw 的转换函数。

**速记**：四位类型、四位编码、二十四位**淘汰元数据**，加引用计数与数据指针；embstr 把 robj 与 SDS **焊成一块**、只读。



#### TYPE 命令返回五种逻辑类型

**TYPE 命令**：返回键对应值的逻辑类型，基本取值只有 string、list、set、zset、hash 五种，对不存在的键返回 none。

```bash
redis-cli TYPE counter        # string
redis-cli TYPE queue          # list
redis-cli TYPE tags           # set
redis-cli TYPE ranking        # zset
redis-cli TYPE profile        # hash
redis-cli TYPE missing_key    # none
```

- TYPE 的答案来自 robj 的 type 字段，与 encoding 无关：同一个键底层编码怎么换，TYPE 的返回值不变。
- 返回 none 常用于写入前的防御判断，比 EXISTS 加读取两步更省一次往返。
- Bitmap 与 Bitfield 的键本质是字符串，TYPE 返回 string，位操作发生在字节内部，详见第 8 章。
- HyperLogLog 的键同样返回 string，其稠密或稀疏编码都封装在值字节内，对命令层不可见。
- GEO 键返回 zset，因为地理位置底层就存放在有序集合中，坐标被编码为 member 的地理哈希，详见第 9 章。
- 实战习惯：排障时先 TYPE 再选命令族，对 string 键执行 HSET 会直接报 WRONGTYPE 错误。

```bash
redis-cli LPUSH counter 1
# (error) WRONGTYPE Operation against a key holding the wrong kind of value
redis-cli TYPE counter        # 先看类型再选命令，避免此类错误
```

> 例外：Stream 是 5.0 起唯一新增的逻辑类型，TYPE 返回 stream；除此之外所有拓展类型都借用五种基本类型名作答，Stream 命令体系详见第 24 章。

**速记**：TYPE 答**逻辑类型**，五种加一个 stream，拓展类型各归其宗。



### 类型与编码的对应

#### OBJECT ENCODING 查看键的底层编码

**OBJECT ENCODING**：返回键值当前使用的底层编码，是观察对象系统最直接的命令，自 2.2.3 起可用。

- 命令形式为 OBJECT ENCODING key，编码名以小写字符串返回，如 int、embstr、quicklist、listpack。
- 编码名是字符串而非数字枚举，便于人工阅读，也便于脚本比对。
- 对不存在的键执行 OBJECT ENCODING 会报 no such key 错误而非返回 none，稳妥做法是先 TYPE 或 EXISTS 再查。
- 各逻辑类型的编码全集如下，这也是本章的主线框架。
- **string**（三种）：int、embstr、raw。
- **list**（一种）：quicklist；7.0 中节点内部为 listpack，6.2 及以前为 ziplist。
- **set**（三种）：intset、listpack（7.0 起，6.2 及以前为 ziplist）、hashtable。
- **hash**（两种）：listpack（7.0 起，6.2 及以前为 ziplist）、hashtable。
- **zset**（两种）：listpack（7.0 起，6.2 及以前为 ziplist）、skiplist。

```text
string : int / embstr / raw
list   : quicklist（节点内 listpack，7.0 起）
set    : intset / listpack / hashtable
hash   : listpack / hashtable
zset   : listpack / skiplist
```

```bash
redis-cli SET greeting hello
redis-cli OBJECT ENCODING greeting
# "embstr"
redis-cli RPUSH queue a b c
redis-cli OBJECT ENCODING queue
# "quicklist"
```

> 同一逻辑类型的编码名会随版本演进变化：从 6.2 升到 7.0 后，小体积的 hash、zset 编码由 ziplist 变为 listpack，7.2 起小集合也新增了 listpack 编码；这是内部结构换代，不是数据异常。编码与结构的对应关系详见第 12 章。

**速记**：string 三编码，list 一种，set 三、hash 二、zset 二，一条命令 OBJECT ENCODING 验收。



#### String 类型的三种编码与 44 字节分界

**String 的编码选择**：值为 long 范围内的整数时用 **int**，长度不超过 44 字节的短字符串用 **embstr**，其余情况用 **raw**。

- int：值可安全放进 long（64 位平台为 8 字节有符号整数），此时连 SDS 都不创建，整数值直接塞进 ptr 槽位，最省内存也最快。
- embstr：一次分配的连续布局，见上一考点的内存复用技巧，创建后只读。
- raw：常规 SDS 结构，robj 与 SDS 各占一块，可原地修改并利用空间预分配扩容。
- 升级路径：int 遇到 APPEND、SETRANGE 等修改类字符串命令转 raw；embstr 一旦被修改转 raw；长度超过 44 字节的字符串创建时直接建 raw。
- int 并非终点：INCR 的结果只要仍在 long 范围内就保持 int，但 INCR 溢出时命令直接报错、对象不变，而任何按字符串语义的改写都会让它离开 int 编码。
- SETRANGE 的行为值得注意：它会把目标键强制展开为 raw 并用零字节补齐空洞，即使只写一个字符。

44 字节分界的推导过程（以 7.x 与 jemalloc 为基准）：

```text
robj 结构体           16 字节
sdshdr8 头部          3 字节（len、alloc、flags 各 1 字节）
结尾空字符            1 字节
合计                  20 字节
jemalloc 64 字节档位  64 - 20 = 44 字节留给 buf
```

- 源码常量 OBJ_ENCODING_EMBSTR_SIZE_LIMIT 即 44，SET 写入时按长度直接决定走 embstr 还是 raw。
- 分界的本质：让整个对象恰好塞进一个 64 字节的分配档位，一次分配、零碎片。

```bash
redis-cli SET k1 12345
redis-cli OBJECT ENCODING k1                  # "int"
redis-cli SET k2 $(printf 'a%.0s' $(seq 44))
redis-cli OBJECT ENCODING k2                  # "embstr"
redis-cli SET k3 $(printf 'a%.0s' $(seq 45))
redis-cli OBJECT ENCODING k3                  # "raw"
redis-cli APPEND k1 x
redis-cli OBJECT ENCODING k1                  # "raw"，int 被改写
```

> 版本差异：3.0 及以前 SDS 头部为 8 字节，分界曾为 39 字节；3.2 起改用 sdshdr8 后固定为 44，4.0、6.0、7.0 均未再变。若把分配器从 jemalloc 换成其他实现，档位理论上不同，但 Redis 仍按 44 硬编码。

**速记**：整数走 int，44 字节以内走 embstr，改过或超长走 raw。



#### List 类型统一由 quicklist 承载

**List 的编码**：3.2 起统一为 quicklist，即用双向链表把多个紧凑节点串起来，节点内部在 7.0 用 listpack、6.2 及以前用 ziplist。

```text
quicklist 示意：
head <-> [node1: listpack] <-> [node2: listpack(压缩)] <-> [node3: listpack] <-> tail
```

- quicklist 兼得两端长处：链表层解决节点数多时的插入删除效率，紧凑节点层解决小数据时的内存碎片与冗余指针。
- 节点大小由 list-max-listpack-size 控制，默认 -2 表示单个节点不超过 8KB；取正数时表示单个节点最多容纳的元素个数。
- 压缩参数 list-compress-depth 控制两端各保留几个节点不压缩，中间节点以 LZF 算法压缩，适合头部尾部活跃、中部沉睡的超长列表。
- 7.0 中无论多少元素，OBJECT ENCODING 对 list 恒返回 quicklist，旧版曾出现的 linkedlist 与 ziplist 字样不再单独出现。
- 节点内结构换代：7.0 把 ziplist 换成 listpack，从根上消除了连锁更新问题，两种结构的差异详见第 12 章。
- 读写两端：LPUSH、RPUSH、LPOP、RPOP 都落在链表层做指针级操作，配合 BLPOP 等阻塞命令构成消息队列基础，详见第 24 章。
- 大列表的内存画像：链表层的指针开销按节点数线性增长，节点内的紧凑存储才是内存大头，调整 list-max-listpack-size 即在碎片与重建成本之间取舍。

```bash
redis-cli RPUSH queue a b c
redis-cli OBJECT ENCODING queue
# "quicklist"
redis-cli LRANGE queue 0 -1
# 1) "a"
# 2) "b"
# 3) "c"
redis-cli CONFIG GET list-max-listpack-size
# 1) "list-max-listpack-size"
# 2) "-2"
```

> 配置名演进：7.0 将 list-max-ziplist-size 更名为 list-max-listpack-size，旧名作为别名仍可读取；4.0 之前的更老版本里 list 曾有 ziplist 与 linkedlist 两种独立编码，3.2 的 quicklist 把二者合而为一。

**速记**：List 外层**链表**、内层**listpack**，编码名恒为 quicklist。



#### Set 类型按元素特征三选一

**Set 的编码选择**：全部元素为整数且数量不超过 set-max-intset-entries（默认 512）时用 **intset**；元素少而短时用 **listpack**；其余情况用 **hashtable**。

- intset：有序整数数组，按元素位数统一编码，查找走二分，是三种编码中最省内存的，详见第 12 章。
- listpack：7.0 起承接小规模字符串集合，阈值为 set-max-listpack-entries 128 与 set-max-listpack-value 64；6.2 及以前这一层用 ziplist。
- hashtable：元素多、单个元素长或整数与字符串混用时的兜底，即标准字典，成员查询 O(1)。
- 常见升级路径：少量短字符串先入 listpack；某元素超过 64 字节或条目超过 128，整体升级 hashtable。
- 纯整数集合的路径独立：只要元素全为整数且不超过 512，无论后续加多少都留在 intset，与 listpack 路径互不干扰。
- SREM 不会触发降级：即使把 hashtable 删回两三个元素，编码仍保持 hashtable，详见后文只升不降。

```bash
redis-cli SADD tags a b c
redis-cli OBJECT ENCODING tags
# "listpack"
redis-cli SADD tags $(printf 'x%.0s' $(seq 65))
redis-cli OBJECT ENCODING tags
# "hashtable"，出现超过 64 字节的元素
redis-cli DEL nums
redis-cli SADD nums $(seq 1 512)
redis-cli OBJECT ENCODING nums
# "intset"，纯整数且未破 512
```

> intset 只认整数：向 intset 集合加入第一个字符串时，若新元素短小且总数未超阈值则转 listpack，否则直接 hashtable；单纯追加整数不会离开 intset，直到数量突破 512。

**速记**：纯整数走 intset，小而短走 listpack，其余走 hashtable，三级逐层兜底。



#### Hash 与 ZSet 在 listpack 与重量级结构间选择

**Hash 与 ZSet 的编码形态**：两者规律一致——数据少而短时用 **listpack**，越过阈值后分别升级为 **hashtable** 与 **skiplist**。

- hash 的紧凑阈值：hash-max-listpack-entries 128、hash-max-listpack-value 64，field 与 value 任一超长即升级。
- zset 的紧凑阈值：zset-max-listpack-entries 128、zset-max-listpack-value 64，member 与 score 均短小时用 listpack。
- listpack 内部按插入顺序成对存放 field 与 value（zset 为 member 与 score），查找需顺序扫描，O(N) 的代价靠小规模摊薄。
- skiplist 编码实际同时持有 dict 与 zskiplist 两个结构：前者按 member 查 score 走 O(1)，后者按分数做范围查询走 O(logN)，双结构互为补位，详见第 12 章。
- hashtable 编码的 hash 即标准字典，field 到 value 的映射、扩容与渐进式 rehash 行为详见第 11 章。
- 6.2 及以前这两对配置名为 hash-max-ziplist-entries、hash-max-ziplist-value 与 zset-max-ziplist-entries、zset-max-ziplist-value，7.0 更名后旧名作为别名仍兼容。

```bash
redis-cli HSET p name tom age 18
redis-cli OBJECT ENCODING p
# "listpack"
redis-cli ZADD board 90 alice 85 bob
redis-cli OBJECT ENCODING board
# "listpack"
redis-cli ZRANGE board 0 -1 WITHSCORES
# 1) "bob"
# 2) "85"
redis-cli CONFIG GET zset-max-listpack-entries
# 1) "zset-max-listpack-entries"
# 2) "128"
```

> hash 与 zset 的阈值语义与 set 一致：不超过才留在 listpack，128 是条目数上限而非目标值；把 value 上限调大到数千字节会让 listpack 退化为顺序扫描大块头，读放大明显，生产上不建议轻易调大。

**速记**：小数据 listpack 一把抓，hash 升字典、zset 升**跳表加字典**双结构。



### 编码转换机制

#### 编码转换由阈值与元素类型触发

**转换时机**：每次可能改变数据形态的写命令执行后，实现层按当前数据重新判断编码，满足升级条件即整体转换。

- 触发命令：HSET、SADD、ZADD、LPUSH、APPEND 等一切增写操作，转换发生在写入路径内，对客户端完全透明。
- 两类条件：条目数量阈值与单个元素长度阈值，任一超出即触发升级。
- 元素类型条件：set 中出现第一个非整数字符串即告别 intset；hash 的 field 或 value 超长同样触发。
- 判断只看当前数据形态：阈值语义是不超过，恰好等于阈值仍算满足，多写一条即触发。
- 阈值可在 redis.conf 中静态调整，也可运行时用 CONFIG SET 动态修改，立即对后续写入生效。
- 转换是全量重建：旧编码结构整体释放，新编码结构逐项搬入，代价与当前元素数成正比。

```text
触发判定（以 hash 为例，每次写命令后执行）：
entries 超过 hash-max-listpack-entries   ->  升级 hashtable
任一 field 或 value 长度超过 64          ->  升级 hashtable
两项均未越线                             ->  保持 listpack
```

```bash
redis-cli CONFIG GET hash-max-listpack-entries
# 1) "hash-max-listpack-entries"
# 2) "512"
redis-cli CONFIG GET hash-max-listpack-value
# 1) "hash-max-listpack-value"
# 2) "64"
redis-cli CONFIG SET hash-max-listpack-entries 4
redis-cli CONFIG REWRITE
```

> 阈值并非越大越好：listpack 的查找是顺序扫描 O(N)，条目过多时读性能恶化；hashtable 内存开销更大但查找 O(1)。默认的 128 与 64 是官方在内存与速度之间的折中，调整前应先在预发环境压测。

**速记**：写后即查，数量或长度越线就升级，类型不合也升级。



#### 编码只升不降

**编码的单向性**：紧凑编码一旦升级为 hashtable、skiplist 或 raw，即使随后删除元素使数据重新满足紧凑条件，也不会降回。

```text
转换方向示意：
intset -----> listpack -----> hashtable   （set）
listpack --------------------> hashtable   （hash）
listpack --------------------> skiplist    （zset）
int / embstr -----------------> raw         （string）
箭头单向，删除元素不逆向回退
```

- 升级是一次 O(N) 的全量重建，来回转换会造成性能抖动，这是单向设计的第一层动机。
- 抖动场景推演：若允许降级，在阈值附近反复增删元素将触发反复重建，最坏情况每条写命令都是 O(N)，延迟完全失控。
- 唯一的重算机会：数据整体重载时按落盘数据重新选择编码——RDB 或 AOF 恢复、主从全量同步重建后，编码按当时的数据形态重新决定。
- 对象替换不是降级：DEL 后重建、SET 整体覆盖会生成新对象并按新数据挑编码，与原地降级是两回事。
- raw 到 int 的回流同理：APPEND 过的字符串即使内容恰为短整数也不会回 int，除非整体 SET 覆盖。
- RENAME、COPY 等键级操作搬的是 robj 指针，编码原样随行，同样不触发重算。

```bash
redis-cli CONFIG SET hash-max-listpack-entries 2
redis-cli HSET big a 1 b 2 c 3
redis-cli OBJECT ENCODING big        # "hashtable"
redis-cli HDEL big c
redis-cli OBJECT ENCODING big        # 仍为 "hashtable"，不降级
redis-cli DEL big && redis-cli HSET big a 1 b 2
redis-cli OBJECT ENCODING big        # "listpack"，新对象按新数据重选
```

> [!IMPORTANT]
> **重要内容**：依赖编码自动降级的优化思路会落空——把大 hash 删瘦并不能换回 listpack 编码；确需紧凑编码时应整体重建键，例如换名写入新键再原子 RENAME，或等待数据重载时自然重算。

**速记**：**只升不降**防抖动，重载与重建是仅有的两条重算路径。



### 引用计数与对象共享

#### 引用计数管理对象生命周期

**引用计数**：redisObject 的 refcount 字段记录当前引用该对象的键或内部结构的数量，是 Redis 唯一的对象回收依据。

- 对象创建时 refcount 为 1；被新键引用时加一；键被删除或值被替换时减一；减到 0 立即释放内存。
- Redis 没有垃圾收集器，释放发生在计数归零的当刻，属于确定性回收，不存在 STW 与标记周期。
- 共享是引用计数的主要应用：多个键的 ptr 指向同一个 robj，由 refcount 统一记账。
- 释放路径按编码区分：raw 需释放 robj 与 SDS 两块，embstr 整块连续只需一次释放，共享对象则永不释放。
- incrRefCount 与 decrRefCount 成对出现，贯穿读写、复制、淘汰与持久化各路径，任何一处漏配对都会造成泄漏或二次释放。
- 值替换语义：SET 一个已存在的键时，旧值对象计数减一、新值对象计数加一，两步都由写命令内部完成。
- RENAME 与 COPY 搬运的是引用而非数据：改键名不触碰值对象，计数不变，这正是对象层带来的轻量键操作。

```text
SET a 100     ->  键 a 的 ptr 指向共享整数对象 100
SET a hello   ->  a 改指新对象，旧引用解除（共享对象计数不动）
DEL a         ->  新对象 refcount 归 0，内存立即释放
```

> embstr 虽然整块分配，但同样拥有独立 refcount；decrRefCount 对 raw 与 embstr 分两条释放路径，后者一次 free 完成，这正是连续布局在回收侧的额外收益。

**速记**：引用计数归零即释放，无 GC、不拖延、路径按编码分流。



#### 整数值对象的共享机制

**对象共享**：Redis 启动时预创建 0 到 9999 共一万个整数值字符串对象，凡整数值落在此区间的键直接共享，源码常量为 OBJ_SHARED_INTEGERS。

```text
共享示意（值 100 落在共享区间）：
键 a --ptr--> [ 共享整数对象 100 ] <--ptr-- 键 b
                  refcount 恒为 2147483647
```

- 共享发生在创建值对象时：SET a 100 与 SET b 100 让两个键的 ptr 指向同一个预建对象，不再各建一份。
- 共享对象不参与普通计数：其 refcount 被设为 OBJ_SHARED_REFCOUNT，即 INT_MAX，引用增减不再改写，也就永远不会被释放。
- OBJECT REFCOUNT 对共享整数返回 2147483647，看到这个值即说明对象被共享。
- 服务器还预建了一批通用回复对象（如 +OK 这类高频应答），命令回复直接复用，减少小对象分配。
- 内存收益：robj 16 字节是独享对象的成本下限，共享让一万个以下的小整数无论被多少键使用都只占一份。
- 共享同样惠及 INCR 场景：计数器值在 0 到 9999 之间反复横跳时，对象无需反复分配。
- INCR 的细节：对共享整数执行 INCR 时按值计算新结果；新值若仍落在共享区间则重新指向共享对象，否则新建普通对象。

```bash
redis-cli SET a 100
redis-cli SET b 100
redis-cli OBJECT REFCOUNT a        # "2147483647"
redis-cli OBJECT REFCOUNT b        # "2147483647"
redis-cli SET c 100000
redis-cli OBJECT REFCOUNT c        # "1"，超出共享区间
redis-cli INCR b
redis-cli OBJECT REFCOUNT b        # 101 仍在共享区间，仍为 2147483647
```

> 超出 0 到 9999 的整数不共享：值 100000 即使被大量键重复出现，也各自创建对象。共享区间的设定是启动成本与命中率的折中，一万档基本覆盖计数器初值、状态码、分页号等高频小整数。

**速记**：**0 到 9999** 天生共享，REFCOUNT 见 2147483647 即共享对象。



#### 字符串对象为何不共享

**字符串不共享**：即使两个键的字符串内容完全相同，Redis 也为各自创建独立对象，共享名单里只有整数值对象。

- 验证成本：共享前必须确认值相等，整数比较 O(1)，字符串比较 O(N)，越长的串越不可接受，而共享恰恰发生在写路径最热的时刻。
- 统计隔离：每个 robj 自带 lru 字段，若共享字符串，一个键被访问会同时刷新所有引用方的空转时间，淘汰决策被整体污染。
- 可写语义：APPEND、SETRANGE 等命令要求对象可原地修改，共享对象被一方修改会波及其他键，破坏隔离性。
- 整数对象天然不可变，值即身份，共享无副作用；字符串没有这个保证。
- embstr 情形更复杂：其 robj 与 SDS 内嵌在一起，还各自携带 LRU 信息，共享意味着更多字段失去独立语义。
- IO 多线程（6.0 起）不改变这一结论：共享判定始终发生在主线程的值创建路径上，与线程模型无关。

```text
SET a "hello"    ->  对象 A（refcount=1，lru=t1）
SET b "hello"    ->  对象 B（refcount=1，lru=t2），内容相同也不共享
GET a            ->  只刷新对象 A 的 lru，对象 B 不受影响
```

> 社区曾讨论过引入字符串池，未获采纳：验证代价与 lru 语义是两大障碍。业务上确有大量重复长字符串时，正确做法是在客户端做去重，或改存短 id 引用再行还原，相关键设计详见第 26 章的旁路缓存模式。

**速记**：字符串共享**三连否**：验证贵、统计脏、可写乱，故只共享整数。



#### lru 字段与 IDLETIME、FREQ

**lru 字段的一专多能**：24 位空间在 LRU 策略下存最近访问时钟（秒级，约 194 天回绕一次），4.0 起在 LFU 策略下拆为 16 位分钟级时间戳加 8 位对数计数器。

```text
lru 字段的两种用法（同一 24 位空间）：
LRU 模式：| 最近访问时钟 24 位，秒级 |
LFU 模式：| 时间戳 ldt 16 位，分钟 | 对数计数器 logc 8 位 |
```

- OBJECT IDLETIME：返回对象空转秒数，仅 LRU 系列策略下可用；读取它本身不重置空转时间，但 GET 等访问键的命令会。
- OBJECT FREQ：返回 LFU 的对数访问计数，仅 LFU 系列策略下可用，4.0 起提供。
- 两个子命令互斥：策略为 LFU 时 IDLETIME 直接报错，策略为 LRU 时 FREQ 报错，错误信息会提示当前模式。
- LFU 计数器对新建对象初始为 5（源码 LFU_INIT_VAL），避免新对象因计数过低而立即被淘汰。
- 计数器按对数规律增长与衰减：访问越频繁计数越高，但高段位每再进一步需要更多访问，8 位空间因此足以表达长尾热度。
- 空转时间的用途：估算冷数据规模、验证淘汰策略是否按预期工作，是内存治理的常用观察口，详见第 15 章。

> [!NOTE]
> **提醒内容**：共享对象的 IDLETIME 恒为 0——访问共享对象不会更新其 lru，否则一次访问会刷新所有引用方的空转时间、污染淘汰统计；因此共享整数的空转数据不可作为分析依据。

```bash
redis-cli CONFIG SET maxmemory-policy allkeys-lru
redis-cli OBJECT IDLETIME a        # 正常返回秒数
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
redis-cli OBJECT IDLETIME a        # 报错，LFU 模式下不可用
redis-cli OBJECT FREQ a            # 正常返回对数计数
```

**速记**：LRU 看时钟问 IDLETIME，LFU 看计数问 FREQ，一槽两用看策略。



### OBJECT 命令与编码观察实战

#### OBJECT 子命令一览

**OBJECT 命令**：面向对象系统的内省命令集，自 2.2.3 起提供，全部子命令可用 OBJECT HELP 随时打印。

- **ENCODING key**：返回底层编码，本章使用频率最高的子命令。
- **REFCOUNT key**：返回引用计数，共享整数恒返回 2147483647。
- **IDLETIME key**：返回空转秒数，仅 LRU 系列策略下可用。
- **FREQ key**：返回 LFU 访问频率计数，仅 LFU 系列策略下可用，4.0 起。
- **HELP**：打印全部子命令与一句话说明，是离线速查入口。
- 组合用法一：REFCOUNT 加 ENCODING 可确认一个键是否命中共享整数。
- 组合用法二：IDLETIME 按 TTL 排序扫描，可找出长期无人访问的冷键清单。
- 组合用法三：ENCODING 配合 SCAN 抽样，可估算整库中 listpack 与 hashtable 编码键的比例，评估阈值配置是否合理。

```bash
redis-cli OBJECT HELP
# ENCODING <key> -- Return the kind of internal representation used...
# FREQ <key> -- Return the access frequency index of the key...
# HELP -- Print this help.
# IDLETIME <key> -- Return the idle time of the key...
# REFCOUNT <key> -- Return the number of references of the value...
```

```bash
# 组合诊断：确认键是否为共享小整数
redis-cli SET hit 42
redis-cli OBJECT ENCODING hit      # "int"
redis-cli OBJECT REFCOUNT hit      # "2147483647"，即共享对象
```

> OBJECT 命令是只读的诊断工具，不修改任何数据，生产环境可放心执行；但输出内容随版本与配置变化，只应作为人工观察窗口。

> [!CAUTION]
> **注意内容**：业务逻辑不应依赖 OBJECT ENCODING 的具体返回值——编码名随版本演进变化（如 ziplist 变 listpack），随数据形态变化（同一键生命周期内多次切换），把编码名写进业务判断会在升级 Redis 时悄然失效。

**速记**：四查一帮助：查编码、查引用、查空转、查频率。



#### 用 OBJECT ENCODING 观察编码变化的实验

**观察实验**：一组 bash 脚本可以完整复现本章全部编码切换路径，建议逐段执行并对照输出验证结论。

```bash
# 实验一：String 的 int、embstr、raw
redis-cli SET n 10086
redis-cli OBJECT ENCODING n          # int
redis-cli SET s hello
redis-cli OBJECT ENCODING s          # embstr
redis-cli APPEND s -world
redis-cli OBJECT ENCODING s          # raw，修改触发升级

# 实验二：Hash 从 listpack 到 hashtable
redis-cli DEL h
for i in $(seq 1 513); do redis-cli HSET h k$i v$i > /dev/null; done
redis-cli OBJECT ENCODING h          # hashtable，条目破 512

# 实验三：Set 的三级跳
redis-cli DEL s1
redis-cli SADD s1 1 2 3
redis-cli OBJECT ENCODING s1         # intset，纯整数
redis-cli SADD s1 str
redis-cli OBJECT ENCODING s1         # listpack，混入短字符串
redis-cli SADD s1 $(printf 'y%.0s' $(seq 65))
redis-cli OBJECT ENCODING s1         # hashtable，出现超长元素

# 实验四：ZSet 的编码切换
redis-cli DEL z
redis-cli ZADD z 1 a 2 b
redis-cli OBJECT ENCODING z          # listpack
for i in $(seq 1 129); do redis-cli ZADD z $i m$i > /dev/null; done
redis-cli OBJECT ENCODING z          # skiplist

# 实验五：44 字节边界复核
redis-cli SET b44 $(printf 'b%.0s' $(seq 44))
redis-cli OBJECT ENCODING b44        # embstr
redis-cli SET b45 $(printf 'b%.0s' $(seq 45))
redis-cli OBJECT ENCODING b45        # raw

# 实验六：hash 的 value 超长触发
redis-cli DEL h2
redis-cli HSET h2 k $(printf 'v%.0s' $(seq 65))
redis-cli OBJECT ENCODING h2         # hashtable，value 破 64
```

> [!TIP]
> **建议内容**：想快速观察阈值效应，可先用 CONFIG SET 把 hash-max-listpack-entries 调小到 2 再写三个字段；实验结束记得 CONFIG SET 调回 512 并 DEL 清理实验键，避免残留数据与非常规配置影响后续观察。

> 复盘要点：实验二故意写 513 条而非 512 条，因为阈值的语义是不超过；实验三依次演示了元素类型与元素长度两类触发条件；实验五直接验证 44 字节分界；每一步的输出变化都对应本章某个结论，输出不符时优先确认服务器版本——set 的 listpack 编码需 7.2 及以上，hash 与 zset 的 listpack 需 7.0 及以上。

**速记**：五个实验对应五条编码路径，跑一遍胜过背十遍。
