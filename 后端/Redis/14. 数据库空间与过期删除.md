## 数据库空间与过期删除

### 数据库的定义与结构

Redis 把「数据放在哪、何时失效」拆成两个正交的问题：前者由数据库的键空间回答，后者由过期字典与删除机制回答。本模块先看清服务器与数据库的组织方式，以及 redisDb 内部的两本核心账目。

#### redisServer 的 db 数组与默认 16 个数据库

**Redis 数据库**：服务器内部由 redisDb 结构承载的一个独立键值空间，服务器启动时默认创建并维护 **16 个数据库**。

- redisServer 结构中的 **db 属性**是一个 redisDb 数组，集中保存服务器内的全部数据库。
- 数据库总数由服务器状态中的 **dbnum 属性**记录，其值来自配置文件的 databases 选项，默认为 16。
- 客户端通过 **select 命令**切换目标数据库，库编号从 0 起计，切换结果记录在客户端状态所指向的库指针上（详见第 2 章）。
- 各数据库之间**完全隔离**：键空间、过期字典与统计信息互不相通，不存在跨库查询。
- flushdb 只清空当前库，flushall 清空全部库，两者作用范围不同，操作前须确认目标。
- 键在哪个库，它的 TTL、内存计算与持久化表达就都发生在那个库内，生命周期不跨库。
- 数据库个数为固定配置，运行期修改 databases 需要重启，客户端选库范围以服务端 dbnum 为准。
- select 切换后客户端长期停留在目标库，连接池复用时需警惕「上一个请求切了库」的残留影响。
- 多库的典型用途是按环境或用途做软隔离，但集群模式（详见第 22 章）只使用 0 号库。
- CONFIG GET databases 返回的是服务端配置的库数，与客户端当前实际连接的库号是两回事。

```text
服务器与数据库的组织关系
redisServer
├── db[0]   redisDb   ← 客户端默认落在 0 号库
├── db[1]   redisDb
├── ……
└── db[15]  redisDb   ← databases 默认 16，编号 0 至 15
```

```bash
# 切换到 2 号库
SELECT 2
# 查看服务器配置的数据库总数
CONFIG GET databases
# 查看当前库的键数量
DBSIZE
```

> 辨析：Redis 的「库」与关系型数据库的 database 名同实异——库之间没有关联查询能力，键的过期判断与内存计算都只在所在库内完成。
>
> 另外注意客户端与服务端的默认不一致：ioredis 等客户端默认连接 0 号库，跨库使用需在连接配置中显式指定 db 编号，否则所有读写都落在 0 号库。

**速记**：服务器一把 **db 数组**，默认 **16 库**，select 切换、库间隔离、flush 分库分全。



#### redisDb 结构与两个核心字典

**redisDb 的核心组成**：一个数据库主要依靠 **dict 与 expires 两个字典**分别管理键值对与过期时间。

- **dict（键空间字典）**：保存该库全部键值对，键是字符串对象，值是 String、Hash、List、Set、ZSet 等各类对象（详见第 13 章）。
- **expires（过期字典）**：只登记设置了过期时间的键，其键指向键空间中的同一个键对象，值是 long long 类型的**毫秒精度 UNIX 时间戳**。
- 两本账同步维护：设置 TTL 即向 expires 写入映射，键被删除或 TTL 被移除时，expires 中的登记同步清除。
- 判断键是否过期只需两步：先在 expires 中查找该键，查到后取出时间戳与**当前系统时间**比较，早于当前即为逻辑过期。
- 读写键空间时的附加动作：键被添加、覆盖或删除时，全局修改计数器 server.dirty 加一，作为 RDB 自动保存条件的判断依据（详见第 17 章）；读写访问都会刷新 redisObject 的 lru 字段，供内存淘汰策略使用（详见第 13、15 章）。
- 逻辑过期是判定而非动作：判定为过期只说明「该键应被删除」，真正回收内存由后文的惰性删除与定期删除完成。
- 除两个字典外，redisDb 还持有库编号、平均 TTL 统计等辅助字段，供运维观察与删除节奏参考。
- 键空间 dict 的规模决定全库遍历命令的成本，KEYS 这类命令（详见第 2 章）遍历的正是它。
- TTL 命令家族（EXPIRE、TTL 等）操作的则是 expires，expires 中的时间戳统一为毫秒精度，秒级命令写入时会被换算成毫秒存储；毫秒精度是 2.6 起的存储形态（官方文档注明），2.6 之前为秒级。
- 两个字典的底层均建立在第 11 章所述的字典结构之上，扩容缩容同样走渐进式 rehash。

```text
redisDb 的两本账
├── dict     键空间字典（保存全部键值对）
│   ├── "msg"     → stringObject "hello"
│   ├── "user:1"  → hashObject {name, age}
│   └── "session" → stringObject "abc"
└── expires  过期字典（只登记带 TTL 的键）
    ├── "session" → 1725003600000
    └── "msg"     → 1725000000000
```

```bash
# 两本账的联动观察
SET s:9 "v" EX 60
TTL s:9       # 正数：expires 已登记
PERSIST s:9
TTL s:9       # -1：expires 登记被移除，键回归永久
```

> 辨析：过期字典不是键空间的完整副本——它的键与键空间**共享同一个键对象**，额外内存开销主要来自每个带 TTL 键的一条时间戳记录，而不是键值对的全量复制。

> 辨析：「有没有 TTL」与「有没有过期」是两个独立状态——有 TTL 且已到期为逻辑过期，有 TTL 未到期为存活，无 TTL 为永久键；三者共存于一库，expires 只登记第一种候选。

**速记**：一库两本账，**dict 管键值、expires 管 TTL**，共享键对象、比对时间戳，两步定生死。



### 过期时间的设置与维护

TTL 从哪里来、到哪里去，是理解过期删除的前置知识。本模块覆盖设置、查看、清除、覆盖写入的影响，以及过期粒度的历史边界。

#### 设置与查看过期时间的命令族

**过期时间命令族**：Redis 以 **EXPIRE、PEXPIRE、EXPIREAT、PEXPIREAT** 四个命令显式设置过期时间，以 **TTL、PTTL** 查看剩余时间，以 **PERSIST** 移除过期时间，并允许 **SET 带 EX、PX 选项**在写入的同时附带 TTL。

- EXPIRE key seconds：以**相对秒数**设置，自执行时刻起算。
- PEXPIRE key milliseconds：以**相对毫秒数**设置，精度更高。
- EXPIREAT key timestamp 与 PEXPIREAT key timestamp：以**绝对时间戳**设置；PEXPIREAT 是其余三条换算后的统一底层入口，最终都落为对 expires 字典的一次写入。
- TTL key 与 PTTL key：分别以秒、毫秒返回剩余时间；键存在且有 TTL 返回正数，键存在但无 TTL 返回 **-1**，键不存在返回 **-2**（Redis 2.8 起区分）。
- PERSIST key：把键从过期字典中移除使其变为永久键，成功返回 1，键不存在或本无 TTL 返回 0。
- SET key value EX seconds 或 SET key value PX milliseconds：**写值与设 TTL 原子完成**，是缓存写入的首选形态（详见第 26 章）。
- SETEX、PSETEX 是先于 SET 选项出现的旧命令，效果分别等价于 SET 带 EX 与 PX，新代码统一用 SET 选项写法。
- GETEX（Redis 6.2 引入）在读取的同时可改 TTL：带 EX、PX 重设过期，带 PERSIST 清除过期，带 PEXPIREAT 指定绝对时刻。
- 查看类命令不改变任何状态，是排查「键何时过期」的第一工具。

```bash
SET otp:8830 "654321" EX 120   # 写入并设 120 秒过期
TTL otp:8830                   # 约 119，单位秒
PTTL otp:8830                  # 约 119500，单位毫秒
PERSIST otp:8830               # 移除 TTL，键变永久
TTL otp:8830                   # -1：键在但无 TTL
DEL otp:8830
TTL otp:8830                   # -2：键不存在
GETEX otp:8830 EX 60           # 6.2 起：读取的同时重设过期
TTL otp:8830                   # 约 59
```

> 辨析：-1 与 -2 的区分是高频考点——**-1 表示键存在但没有过期时间**，**-2 表示键本身不存在**；排障时先看返回值，可立刻判断问题是「忘设 TTL」还是「键已丢失」。

> 辨析：先 SET 再 EXPIRE 的两段式写法并非原子，中间失败或进程中断会留下**永不过期的脏键**；带 TTL 的写入应优先使用 SET 带 EX 或 PX，一步原子完成。

**速记**：四设置 **EXPIRE、PEXPIRE、EXPIREAT、PEXPIREAT** 归一 **PEXPIREAT**，二查看 **TTL、PTTL**，一清除 **PERSIST**；返回值 **-1 无 TTL、-2 无键**。



#### SET 重写 value 对 TTL 的影响与 KEEPTTL

**TTL 的依附性**：过期时间依附于**整个键**而非值，**SET 命令对键的覆盖写入默认会清空原有 TTL**。

- 不带任何选项的 SET key value：覆盖 value 的同时**移除过期字典中的登记**，键回到永久状态。
- SET 带 EX 或 PX：覆盖 value 并**写入新的 TTL**，旧 TTL 被替换而非叠加。
- SET 带 **KEEPTTL 选项**（Redis 6.0 引入）：覆盖 value 且**保留原剩余时间**，适合只改值、不动生命周期的更新。
- 对已过期的键执行覆盖写入等价于新建键：旧的登记已随删除清掉，新 TTL 从零起算。
- GETSET 这类整体覆盖 value 的命令同样会清掉 TTL；而 INCR、APPEND、HSET、LPUSH 等只改动值内容或结构的命令**不影响 TTL**。
- RENAME 会把 TTL 随键名一起迁移，新键名获得原键的剩余时间。
- 经验法则：改值是否清 TTL，取决于命令是否**整体替换 value**——替换则清，局部修改则保。
- 批量脚本中尤其小心：循环里的裸 SET 会把预热阶段设置的 TTL 逐个清掉，且不易察觉。
- KEEPTTL 在键本无 TTL 时执行不报错，只是维持无 TTL 状态。

```bash
SET cache:prod "v1" EX 100
SET cache:prod "v2"            # 覆盖写入，TTL 被清空
TTL cache:prod                 # -1
SET cache:prod "v3" EX 100
SET cache:prod "v4" KEEPTTL    # 改值但保留剩余时间
TTL cache:prod                 # 剩余时间延续，未重新计时
```

> [!WARNING]
> **警告内容**：忘带 EX 的 SET 覆盖，以及先 SET 后 EXPIRE 的两段式写入，都会让缓存键变成**不过期的永久键**；大批量发生时内存只能靠淘汰策略兜底（详见第 15 章）。带 TTL 的写入务必使用 SET EX/PX，更新已有 TTL 键的值时使用 KEEPTTL。

> 辨析：KEEPTTL 与重新执行 EXPIRE 语义不同——KEEPTTL 保留的是**剩余存活时间**，适合顺路改值；重新 EXPIRE 则以当前时刻**重算 TTL**，适合续期场景。
>
> 改值续命用 KEEPTTL，延期重算用 EXPIRE，两者不可混用。

**速记**：TTL 挂在**键**上，**SET 一覆盖就清零**，保命加 **KEEPTTL**，续期重新 EXPIRE。



#### EXPIRE 的 NX、XX、GT、LT 条件选项

**EXPIRE 条件选项**：Redis 7.0 起，EXPIRE、PEXPIRE、EXPIREAT、PEXPIREAT 均支持以 **NX、XX、GT、LT** 四个互斥的可选参数限定 TTL 的设置条件。

- **NX**：仅当键**当前没有** TTL 时才设置。
- **XX**：仅当键**当前已有** TTL 时才设置。
- **GT**：仅当新 TTL **大于**当前 TTL 时才设置，即只许延长。
- **LT**：仅当新 TTL **小于**当前 TTL 时才设置，即只许缩短。
- 条件不满足时命令返回 0 且**不做任何修改**，原 TTL 保持不变。
- 返回值约定：设置成功返回 1，未设置（含条件不满足）返回 0。
- 选项与时间参数同时给出，命令形如 EXPIRE key seconds NX，一次只能携带四个选项之一。
- 这组选项同样适用于 PEXPIRE 等其余三条命令，语义随时间单位对应换算。

```bash
SET ticket:9 "ok" EX 30
EXPIRE ticket:9 60 NX   # 已有 TTL，条件不满足，返回 0
EXPIRE ticket:9 60 GT   # 60 大于剩余 30，设置成功，返回 1
EXPIRE ticket:9 10 LT   # 10 小于剩余 60，设置成功，返回 1
```

```text
四个选项的典型场景
NX：只在首次设置时生效，如给新建缓存定生命周期
XX：只刷新已有 TTL，避免给永久键意外挂上过期
GT：只许延长，如活跃会话的续期保护
LT：只许缩短，如提前回收临时凭证
```

> 辨析：GT 与 LT 比较的是**剩余存活时长**而非设置的绝对时刻；这组选项主要用于分布式锁续期等并发场景，防止后来者把他人更长的持有时间**误改短**，或把续期变成重新计数（详见第 27 章）。

**速记**：**NX 无才设、XX 有才设、GT 只延长、LT 只缩短**，四选一互斥，不满足即原地不动。



#### TTL 只对整个键生效与 7.4 的 HEXPIRE

**过期粒度**：Redis 的过期时间以**整个键**为最小单位，键内成员（Hash 的 field、List 的元素、Set 的成员）长期无法单独设置 TTL。

- 历史限制：Hash 的 field 不能单独过期，业务只能**拆键模拟**——把每个 field 升级为独立小键分别设 TTL。
- 另一种模拟手段是**按时间分桶命名**：把不同批次的数据放进 data:20260907 这类日期键，整键过期即批量失效。
- Redis 7.4 引入 **HEXPIRE、HPEXPIRE、HEXPIREAT、HPEXPIREAT**，首次支持对 **Hash 的单个 field 设置过期时间**，并配套 HTTL、HPTTL 查看剩余时间、HPERSIST 移除。
- field 级过期同样遵循「到时逻辑过期、由删除机制回收」的语义，与键级 TTL 一致。
- HEXPIRE 的语法要点：以 FIELDS 关键字声明后续 field 的数量，一次可对多条 field 设置同一过期时间。
- field 级 TTL 的返回值体系与键级一致：不存在返回 -2，存在但无 TTL 返回 -1。
- 整键 TTL 与 field TTL 可以同时存在，互不影响、各自判定。
- List、Set、ZSet、Stream 的成员在 7.4 中仍**不支持**成员级 TTL。

```bash
HSET cart:u1 sku:100 2 sku:200 1
HEXPIRE cart:u1 60 FIELDS 1 sku:100   # 仅 sku:100 这个 field 60 秒后过期（7.4 起）
HTTL cart:u1 FIELDS 1 sku:100
HPERSIST cart:u1 FIELDS 1 sku:100     # 移除该 field 的过期时间
```

> [!NOTE]
> **提醒内容**：HEXPIRE 是 Redis 7.4 的新命令，低版本会直接报 unknown command 类错误；在不支持它的版本上，通行做法仍是**一个 field 一个键**，以键级 TTL 代替 field 级过期。

> 辨析：field 级过期要为每条 field 维护过期记录，内存与实现开销高于整键 TTL；除非确有逐条过期的业务需求，多数缓存场景给整个键设 TTL 更简单、更省内存。

**速记**：TTL 只认**键**；Hash 的 field 直到 **7.4 才有 HEXPIRE**，其余类型的成员级过期仍不支持。



### 过期删除的三种策略

有了过期时间，还要回答「谁来删、什么时候删」。教科书把可行方案归纳为三种策略，各自在 CPU 与内存之间做出不同的取舍，Redis 对它们做出了明确的选择。

#### 定时删除策略及其优缺点

**定时删除**：在设置键过期时间的同时**创建一个定时器**，由定时器在过期时刻到达时**立即删除该键**的策略。

- 优点：过期键在到期瞬间即被清除，内存释放最及时，对**内存最友好**。
- 缺点一：每个带 TTL 的键都要占用一个定时器，键量巨大时定时器的创建、维护与回调**大量消耗 CPU**，对 **CPU 最不友好**。
- 缺点二：大量键集中到期时，删除动作在时间上集中爆发，容易造成**响应延迟抖动**。
- 结构背景：Redis 的事件循环并不为业务键提供逐键定时器槽位，海量定时本身也与单线程模型冲突（详见第 16 章）。
- 适用判断：只有在键数量少、过期时刻分散、且业务对内存回收时效极度敏感时，定时删除才划算。
- 教科书意义大于工程意义：理解它为何被弃用，比记住它本身更重要。

```text
定时删除时间线
t0   SET k v EX 60 → 同时创建一个 60 秒后触发的定时器
t60  定时器触发 → 立即删除 k，内存即时回收
```

> 辨析：Redis **不采用**定时删除——单线程模型承受不起海量定时器的调度开销，把 CPU 花在「盯着每个键到点」上，会直接挤压正常命令的执行窗口。
>
> 这违背 Redis 用有限 CPU 服务高并发的总体设计，因此尽管它内存表现最好，仍被整体弃用。

**速记**：定时删除**内存友好、CPU 不友好**，代价是海量定时器，Redis 弃用。



#### 惰性删除策略及其优缺点

**惰性删除**：键到期后**暂不删除**，直到下一次有命令**访问该键**时才检查并删除的策略。

- 优点：删除由访问触发，只在真正用到时付出一次判断成本，**CPU 最友好**，实现也最简单。
- 缺点：过期键若长期无人访问，会**长期滞留内存**，形成逻辑已死、物理还在的占用，对**内存最不友好**。
- 典型恶化场景：批量写入日志类短 TTL 键之后只写不读，内存随写入持续攀升，且无法靠访问触发回收。
- 读语义不受影响：虽然键物理上还在，但检查先于命令执行，访问者得到的永远是不存在语义。
- 与定期删除配合才完整：惰性删除管「被访问的」，没人访问的部分必须由定期删除补位。
- 惰性删除不依赖任何后台任务，是三种策略中实现成本最低的一种。
- EXISTS、TTL 这类检查型命令同样触发惰性删除：探查键是否存在的过程也会顺手清账。

```text
惰性删除时间线
t0   SET k v EX 60 → 只写 expires，不创建任何定时器
t60  TTL 到期 → 键逻辑过期，物理上仍在内存
t100 客户端 GET k → 执行前检查发现过期，删除并返回 nil
```

```bash
SET otp:1 "code" EX 10
# 十秒之后：
GET otp:1     # 命令执行前先做过期检查：删除键并返回 nil
EXISTS otp:1  # 0，键已被惰性删除
```

> 辨析：惰性删除的检查发生在**命令执行前**，因此读到过期键时得到的一定是不存在的语义，**永远不会读到旧值**；被读到的那一刻，正是它被删除的时刻。

**速记**：惰性删除**CPU 友好、内存不友好**，没人访问就不清账。



#### 定期删除策略及其优缺点

**定期删除**：服务器**每隔一段时间主动抽检**一批键的过期状态、发现过期即删除，并以**限制单次时长**约束总开销的策略。

- 优点：在 CPU 与内存之间取**折中**——不像定时删除那样逐键精确，也不像惰性删除那样放任滞留，过期键被**分批渐进清理**。
- 缺点：清理力度受抽样数量与单次时长的双重限制，**难以一次性清干净**，残余过期键仍需惰性删除兜底。
- 设计要点：每次抽多少、执行多久都有硬性限额，保证单次清理**不会长时间阻塞**主线程上的正常命令。
- 定位：它是三种策略里唯一「主动但克制」的方案，主动在不用等访问，克制在每次投入的 CPU 有限。
- 清理节奏自适应：过期键密度越高，单次巡逻内触发重复抽检的轮次越多，投入的 CPU 随之增加。
- 每轮巡逻的轮数并无硬上限，上限约束的是**时间**而非轮数，轮数由过期密度决定。

```text
巡逻节奏示意
第 1 轮  随机抽 20 个 → 过期 3 个（15%）→ 低于阈值，收手
第 2 轮  随机抽 20 个 → 过期 7 个（35%）→ 超过阈值，再来一轮
第 3 轮  随机抽 20 个 → 过期 2 个（10%）→ 低于阈值，本轮结束
```

> 辨析：定期删除不是给键设定时器，而是周期性地**随机巡逻**；巡逻的频率与限额决定它只能是折中方案，不能保证过期键在到期后立刻消失。
>
> 它能保证的只有一件事：过期键「迟早被扫到」，内存不会因无人访问而无限滞留。

**速记**：定期删除是**周期巡逻、限量抽检**，内存与 CPU 的折中艺术。



#### Redis 的实际选择：惰性删除加定期删除

**Redis 的实际策略**：服务器**组合使用惰性删除与定期删除**两种策略，**不使用定时删除**，两条路径互补覆盖。

- 惰性删除覆盖**被访问**的过期键：读写命令触达时顺手删除，保证读语义正确。
- 定期删除覆盖**不被访问**的过期键：周期抽检主动清理，抑制内存滞留。
- 两条路径合起来保证过期键**最终一定被回收**：要么死于被访问，要么死于巡逻。
- 若清理速度仍追不上写入速度、内存压力持续上升，则交由第 15 章的内存淘汰策略兜底。
- 设计哲学：不做精确但昂贵的承诺，改做廉价且覆盖面完整的概率保证，这正是 Redis 在资源约束下的工程取舍。
- 观察命令：INFO 中的 expired_keys 与 evicted_keys 分别累计两条通道的删除量，可用于验证删除是否健康。

```text
三种策略对照
定时删除：设键即设定时器，到点立即删 —— 内存最好，CPU 最差（Redis 不用）
惰性删除：访问时检查再删 —— CPU 最好，内存最差（Redis 采用）
定期删除：周期抽检批量删 —— 两者折中（Redis 采用）
```

> [!IMPORTANT]
> **重要内容**：区分删除与淘汰两条通道——**惰性删除与定期删除只处理过期键**，**内存淘汰策略只在内存达到 maxmemory 上限时启动**。
>
> 过期键即便无人访问也会被定期删除清掉，而未过期的键只有内存吃紧时才可能被淘汰，二者触发条件完全不同。

**速记**：Redis 用**惰性加定期**双管齐下，**定时删除出局**；过期靠删、紧张靠淘汰。



### 过期删除的实现细节

策略落进源码只有两个入口：命令执行前的惰性检查，与周期执行的抽检循环。理解这两个函数的行为与边界，才能解释线上「过期键何时消失」的全部现象。

#### 惰性删除的实现：expireIfNeeded

**expireIfNeeded**：Redis 在**每个读写命令执行前**对目标键调用的过期检查函数，是惰性删除的具体实现。

- 读写命令真正操作键空间之前，都会先对涉及的键执行 expireIfNeeded 检查。
- 键未过期：函数直接返回，命令按原逻辑继续执行。
- 键已过期：函数**从 dict 与 expires 中同时移除该键**，并向 AOF 与从库传播删除事实，命令如同作用于一个不存在的键。
- 触发面覆盖所有读写命令：GET、EXISTS、TTL 这类只读命令，与 SET、DEL、HGETALL 这类写命令都在检查范围内。
- 开启懒释放相关配置时，大对象的实际内存释放可交由后台线程异步完成，避免同步释放阻塞主线程。
- 对写命令而言，作用于过期键等价于作用于不存在的键：SET 直接新建键，INCR 这类依赖旧值的命令会因键不存在而报错。
- 检查按命令涉及的具体键进行，MGET 这类批量命令对每个键各做一次判断。
- 该检查对客户端完全透明，不存在需要业务侧配合的开关或参数。
- 只有检查通过后命令才进入真正执行阶段，不存在「删了一半」的中间状态。

```text
读写命令的统一前检查
命令到达 → 解析出目标键
        → 对目标键执行 expireIfNeeded
        → 未过期：按原逻辑执行命令
        → 已过期：先删除键并传播删除，再执行命令
```

```bash
SET k "v" EX 5
# 五秒之后：
GET k        # 内部先执行 expireIfNeeded：键过期即删，返回 nil
SET k "new"  # 对已删除的键直接新建，无需先手动 DEL
```

> 辨析：正因为检查在命令前完成，业务命令**没有机会读到过期键的旧值**；过期检查的代价被均摊到每次命令里，只对带 TTL 且已过期的键产生真实的删除成本，这正是惰性删除「CPU 友好」的实现基础。

**速记**：每条读写命令先过 **expireIfNeeded** 这一关，过期即删、删完再干活。



#### 定期删除的实现：activeExpireCycle

**activeExpireCycle**：Redis 周期性执行的过期键抽检函数，是定期删除的具体实现，核心是**随机抽样、比例驱动、限时收工**。

- 函数由周期任务 **serverCron 以 hz 的频率驱动**（默认 10，即约每 100 毫秒一轮，详见第 16 章），每次调用最多检查 16 个数据库，借助静态游标跨调用增量推进。
- 每轮从当前库的 expires 过期字典中**随机抽取 20 个键**（源码常量 ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP 为 20，旧版本名为 LOOKUPS_PER_LOOP）检查。
- 删除抽检样本中所有已过期的键。
- 若本轮过期键占样本的**比例超过阈值**，立刻再抽一轮，直到比例降到阈值以下或时间上限到达；阈值有明确的版本演进——**2.6 至 5.0 为 25%**（源码注释写明超过四分之一继续），**6.0 起由常量 ACTIVE_EXPIRE_CYCLE_ACCEPTABLE_STALE 定为 10%**，且 6.0 起可用配置 active-expire-effort（1 到 10，默认 1）调节力度。
- 阈值的含义：抽样里过期占比过高，说明全库过期键密度已相当高，值得继续投入 CPU；密度低则及时收手。
- 每次执行都有**时间上限**：慢模式单次总耗时不超过该轮 CPU 周期的 25%（常量 ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC），hz 为默认值 10 时约 25 毫秒，执行中每 16 次迭代检查一次是否超时，超时立即让出——这是单线程模型的自我保护。
- hz 的配合：hz 越高慢模式巡逻越频繁、清理越及时，但每秒空耗的 CPU 也越多；键规模巨大且过期密集的实例才考虑调大（CONFIG GET hz 查看，hz 的通用讨论详见第 16 章）。
- 执行分两种模式：**慢模式**挂在周期任务 serverCron 中，单次时长上限相对宽松；**快模式**挂在事件循环的 beforeSleep 中，单次上限约 1 毫秒，执行更频繁但每次更轻量。
- 两种模式互补：慢模式保证每个周期至少巡逻一次，快模式在事件间隙见缝插针，共同压低过期键的滞留时长。
- 时间上限随 serverCron 频率折算，保证每秒内巡逻总耗时占 CPU 的比例受控。
- 参数观察：CONFIG GET hz 可查看周期任务频率，hz 越高慢模式巡逻越频繁，CPU 代价也越高。

```text
activeExpireCycle 单轮流程
1. 取当前库的 expires 过期字典
2. 随机抽取 20 个键
3. 逐个检查并删除其中已过期的键
4. 过期比例超过阈值？→ 是则回到步骤 2（2.6 至 5.0 为 25%，6.0 起为 10%）
5. 达到时间上限 → 本轮结束
```

> [!IMPORTANT]
> **重要内容**：activeExpireCycle 必须受时间上限约束——Redis 是单线程服务，一旦大批缓存同时到期，不限时的清理就会演变成整库卡顿；上限保证清理让路于服务，这是定期删除作为折中方案的技术底线。

> 辨析：采用**随机抽样**而非遍历整个 expires，是因为全量扫描的代价随库大小线性增长，会退化成定时删除式的重负。
>
> 抽样让清理力度随过期键密度**自适应伸缩**：密度高时多扫几轮，密度低时一轮即止。另需注意版本核对：不少流传资料描述「超过 25% 继续循环」，那对应 2.6 至 5.0 的源码，6.0 起阈值为 10%，讨论调优前先确认版本。

**速记**：**抽 20、删过期、超阈值再来（旧版 25%、6.0 起 10%）、限时收工** ⏱️；慢模式驻 serverCron，快模式驻 beforeSleep。



#### lazyfree-lazy-expire 与异步过期删除

**lazyfree-lazy-expire**：4.0 起提供的配置项，开启后过期删除的**内存释放交给后台惰性释放线程**，主线程只完成两本字典的摘除。

- 默认值为 no：过期删除默认同步释放内存，删除开销全额计入触发它的命令或抽检循环。
- 开启动机：惰性或定期删除撞上大对象时，同步释放可能耗时数毫秒甚至更久，阻塞主循环；开启后主线程摘引用、后台线程放内存——与第 16 章 UNLINK 命令族及 bio 惰性释放线程的机制同源。
- 传播联动：开启后过期删除向 AOF 与复制流传播的命令由 **DEL 改为 UNLINK**，源码按该配置在两者之间选择，主从与 AOF 的删除语义保持一致。
- 判断口令与第 16 章一致：凡涉及大内存释放，主线程只动引用、后台线程动内存；小对象同步释放更快，系统自动择优。
- 关联配置：lazyfree-lazy-eviction 管内存淘汰路径的异步释放（详见第 15 章）、lazyfree-lazy-server-del 管命令内部隐式删键的异步释放，三者默认均为 no。

```bash
# redis.conf 中的过期异步释放配置
lazyfree-lazy-expire no     # 默认关闭

# 运行期动态开启并固化
CONFIG SET lazyfree-lazy-expire yes
CONFIG REWRITE
```

> [!TIP]
> **建议内容**：键规模大、过期密集或存在大 value 的实例建议开启 lazyfree-lazy-expire，可消除过期集中删除时的延迟毛刺；开启后观察 INFO 中 expired_time_cap_reached_count 与内存释放节奏，确认清理未因异步化而积压。

**速记**：lazyfree-lazy-expire **摘引用在主线程、放内存去后台**，4.0 起可用，传播同步改 UNLINK。



### 过期键与持久化、复制与通知

过期键不仅要被删掉，还要在持久化文件、主从复制与通知订阅者面前保持状态一致。本模块逐一看 RDB、AOF、从库与键空间通知如何对待过期键。

#### 过期键对 RDB 生成与载入的影响

**RDB 与过期键**：RDB 持久化在**生成与载入**两个方向上对过期键的处理原则不同——生成时跳过，载入时按服务器角色区分（详见第 17 章）。

- 生成方向：执行 SAVE 或 BGSAVE 生成 RDB 文件时，数据库中**已过期的键不会被写入**文件，落盘的都是存活键。
- 载入方向（主服务器模式）：载入 RDB 时对每个键做过期检查，**已过期的键直接丢弃**，不入库。
- 载入方向（从服务器模式）：载入时**保留全部键**，包括逻辑上已过期的键，待复制流建立后由主库的删除操作对齐状态。
- 载入方向的主从区分只影响过期键，未过期的键一律正常入库。
- RDB 文件中过期时间以**毫秒级绝对 UNIX 时间戳**存储而非剩余时长。
- 绝对时间戳的原因：保存到载入之间存在时间差，剩余时长会失真；存绝对值，载入端即可直接与当前时间比较、即刻判断键是否已过期。
- 这也是 EXPIREAT 与 PEXPIREAT 存在的理由——绝对时刻便于序列化，相对时长便于直觉表达，两者在 expires 字典中统一收敛为绝对毫秒时间戳。
- RDB 的过滤发生在写入文件的枚举阶段，文件中因此不存在「过期但未删」的中间状态。

```text
RDB 两个方向的处理
生成（SAVE/BGSAVE）：过期键 → 不写入文件
载入（主服务器）：  过期键 → 丢弃不入库
载入（从服务器）：  过期键 → 保留，等主库 DEL 对齐
```

```bash
SET r:1 "v" EX 60
BGSAVE    # 若此刻 r:1 已过期则不写入 RDB，未过期则完整落盘
```

> 辨析：从库载入时保留过期键并非疏漏——此时从库尚未建立正常复制流，主库对过期键的删除命令尚未到来。
>
> 若自行丢弃，反而可能与主库的裁决不一致；复制流建立后，主库的 DEL 会完成最终对齐（详见第 20 章）。

**速记**：RDB **生成跳过过期、载入主跳从留**，文件里的 TTL 存**绝对时间戳**。



#### 过期键对 AOF 与重写的影响

**AOF 与过期键**：过期键被删除时，服务器向 AOF **追加一条 DEL 命令**；AOF **重写时跳过已过期的键**（详见第 18 章）。

- 惰性删除或定期删除真正删掉过期键时，服务器同步向 AOF 缓冲区追加该键的 DEL 命令，保证重放 AOF 与真实删除序列一致。
- AOF 重写（BGREWRITEAOF）扫描键空间时**不写入已过期的键**，重写产物只含存活键。
- 两条规则合起来保证：无论完整 AOF 还是重写后的 AOF，重放过程中过期键都不会「复活」。
- DEL 的追加发生在删除动作的同一时刻，与删除来源无关——惰性删除与定期删除产生的 DEL 都会落盘。
- 追加的 DEL 会同时进入 AOF 重写缓冲，重写期间发生的删除不会因此丢失。
- 重写文件与增量缓冲共同保证：无论重放完整 AOF 还是重写后的 AOF 加增量，删除序列都完整。
- 从库收到主库传播的 DEL 后，若自身开启 AOF，同样会留下该 DEL 记录，主从的重放序列保持一致。
- AOF 记录的是删除命令本身而非 EXPIRE 命令，剩余时间信息因此无需进入 AOF。

```text
AOF 的两条保障
删除时：追加 DEL，重放序列与真实删除一致
重写时：跳过过期键，重写产物只含存活键
```

```bash
SET m:1 "v" EX 60
# 六十秒后键被惰性或定期删除，AOF 中追加：
# DEL m:1
# 若此时执行 BGREWRITEAOF，m:1 已不存在，重写文件中不会有它
```

> 辨析：AOF 中出现 DEL 的时机是**键被真正删除时**，而不是 TTL 到期的瞬间——到期但尚未被惰性或定期机制处理之前，AOF 不会有任何记录。
>
> 这与过期事件的发送时机是同一个道理，见本章末节。

**速记**：删一个、追加一条 **DEL**，重写时**跳过过期键**，AOF 重放不复活。



#### 从库的过期键处理

**从库的过期键处理**：主从复制下，**过期键的删除由主库统一执行**，从库**不主动删除**过期键（详见第 20 章）。

- 主库通过惰性或定期删除处理过期键后，**显式向从库传播 DEL 命令**，从库执行后才真正删除。
- 从库即使发现键已逻辑过期，也**不自行删除**，而是等待主库的 DEL 到达，保证主从删除序列一致。
- 读路径的逻辑过期判断：源码自 2.6 起在从库读路径上返回「当前时间是否大于过期时间」的判断结果——已逻辑过期的键在读命令面前表现为**键不存在**，但物理删除仍等主库 DEL，键可能仍占内存。
- 官方文档同时明确：从库保存**完整的过期状态**，被提升为主库后即可独立执行全部过期逻辑（哨兵故障转移场景，详见第 21 章）。
- 版本与资料限定：部分早期资料（如《Redis 设计与实现》）描述从库读到过期键**仍像处理正常键一样返回旧值**，与 2.6 以来源码注释及官方文档不符；实际行为以所用版本的源码与官方文档为准核对。
- 理解要点：从库的自我定位是「重放主库命令的镜像」，凡是主库有权决定的数据变更，从库一律等待指令而非自行判断。
- 复制延迟期间，从库可能短暂保留逻辑过期键，读路径的逻辑判定已挡住旧值外泄。
- 该机制下从库不宜作为 TTL 的权威观测点，判断键是否过期应以主库为准。
- 从库执行 DEL 走的同样是键空间删除路径，dict 与 expires 两本账同步清除。

```bash
# 主库执行：
SET s:1 "v" EX 10
# 十秒后主库删除该键，并向从库传播：
# DEL s:1
# 从库在此之前读 s:1：已逻辑过期的键表现为键不存在，物理删除等主库 DEL 到达
```

> [!CAUTION]
> **注意内容**：从库读路径上已过期的键表现为键不存在，但物理内存可能尚未释放（主库 DEL 未到）；复制延迟越大，这种「读不到却还占着」的窗口越明显。业务要求严格的过期读语义时，应以读主库为准，或先确认所用版本的从库行为再设计读策略。

> 辨析：从库不自删的根因是**时钟与顺序**——主从时钟若有偏差，各自为政的删除会引入不一致。
>
> 由主库统一裁决删除时机并传播 DEL，从库的重放序列才能与主库完全一致。

**速记**：**主库删、从库等 DEL**；从库读过期键表现为键不存在，删除权在主库，升主后立即接管全部过期权。



#### 过期键删除与键空间通知

**键空间通知与过期事件**：过期键被真正删除时，Redis 会向订阅者发布 **expired 事件**，发布时机是**删除发生时**而非 TTL 到期的瞬间（详见第 24 章）。

- 过期事件需先开启通知：CONFIG SET notify-keyspace-events 参数组合为 **Ex**（E 表示 keyevent 事件通道，x 表示 expired 事件）。
- 订阅形态：订阅 __keyevent@0__:expired 频道后，收到的消息负载是**被删除的键名**。
- 事件发布跟随删除动作：惰性删除对应一次访问触达，定期删除对应一次抽检命中，因此 **expired 事件可能比 TTL 时刻晚数秒甚至更久**。
- 事件产生于**执行删除的实例**：主从架构下过期删除发生在主库，订阅过期事件应订阅主库。
- 键被 EXPIRE 显式删除或被淘汰策略驱逐时，发送的分别是 del 事件与 evicted 事件，与 expired 相互独立。
- 依赖过期事件实现业务回调（如订单超时关闭）时，必须容忍延迟并辅以轮询兜底。
- 通知与删除同源：能触发 DEL 传播的路径，同样是 expired 事件的产生路径。
- expired 事件的负载只有键名，业务若需更多上下文，须在键名或关联键中自行携带。
- 订阅端消费不及时时事件会积压在客户端缓冲区，服务端不做重试投递，必要时改用轮询补偿。

```text
事件时序对比
TTL 时刻   键逻辑过期，无任何对外动作
删除时刻   惰性（被访问）或定期（被抽检）删除真正发生
事件时刻   与删除同时，发布 expired，负载为键名
```

```bash
CONFIG SET notify-keyspace-events Ex
# 另开一个连接：
SUBSCRIBE __keyevent@0__:expired
# 键过期被删除后，该频道收到消息，负载为键名
```

> [!NOTE]
> **提醒内容**：expired 事件是「删除时才发」而非「到期即发」，把它当精确定时器是常见误用；对时效敏感的流程应以自身调度为主，Redis 过期事件只作轻量辅助。

> 辨析：被内存淘汰策略驱逐的键发出的是 **evicted 事件**而非 expired——两者都意味着键消失，但成因不同：前者源于内存压力，后者源于 TTL 到期。
>
> 监控与告警应分开统计这两类事件（详见第 15 章）。

**速记**：expired 事件**删时才发、可能迟到**，开启靠 **notify-keyspace-events Ex**，别当精确闹钟。
