## Redis 简介与安装配置

### Redis 的认识

#### Redis 是什么：定义与出身

**Redis**：即 **Remote Dictionary Server（远程字典服务）**，是一个用 **C 语言**编写的**开源内存键值数据库**，由意大利工程师 **Salvatore Sanfilippo**（网名 **antirez**）于 **2009 年**创造并首次发布。

- Redis 把数据以**键值对**的形式保存在**内存**中，读写延迟在亚毫秒级，单机每秒可执行十万次以上的操作。
- 键是**字符串**，值的类型则覆盖字符串、哈希、列表、集合、有序集合等丰富结构，因此它自称为字典服务，而不只是简单缓存。
- Redis 采用 **C 语言**编写，编译产物轻巧，部署只需要一个可执行文件加一份配置文件。
- Redis 遵循 **BSD 开源协议**，源码托管在 GitHub，任何人都可以免费使用、修改与分发。
- 创造者 antirez 起初是为了解决自己网站的实时统计性能瓶颈而写下 Redis，后来它逐步演化为通用的数据结构服务器。
- Redis 采用**单进程模型**对外服务，所有客户端连接由一个服务进程统一处理。
- Redis 官方站点提供完整的命令参考文档，本系列全部事实均以 Redis 官方文档为依据。

选择 C 语言带来的直接收益有三点：执行效率高、内存布局可控、依赖极少，这使得 Redis 在几乎任何 Linux 发行版上都能顺畅编译部署。

其存储形态可示意如下：

```text
键值对结构示意

user:1001     → Hash 类型的值     → 用 HSET、HGET 等命令操作
queue:orders  → List 类型的值     → 用 LPUSH、RPOP 等命令操作
rank:points   → ZSet 类型的值     → 用 ZADD、ZRANGE 等命令操作
captcha:8848  → String 类型的值   → 用 SET、GET 等命令操作
```

> 从名字 Remote Dictionary Server 出发理解 Redis 最为准确：它是一台远程的、结构化的映射表服务器。理解了这个定位，后续学习各种数据类型时，就不会把它误认为只能存字符串的简单缓存工具。

**速记**：Redis 是 **antirez 在 2009 年用 C 语言写的开源内存键值数据库**，全称远程字典服务。



#### Redis 的定位与核心特点

**Redis 的定位**：是**基于内存的通用数据结构服务器**，同时扮演缓存、数据库与消息中间件三种角色，核心特点可概括为五条。

- **内存读写**：数据主要存放于内存，读写速度远超磁盘数据库，这是它所有能力的性能基础。
- **丰富的数据结构**：原生提供 String、Hash、List、Set、ZSet、Bitmap、HyperLogLog、GEO、Stream 等类型（详见第 3 章至第 9 章）。
- **持久化**：支持 RDB 快照与 AOF 日志两种落盘方式，内存数据可在重启后恢复（详见第 17 章至第 19 章）。
- **高可用**：提供主从复制、哨兵 Sentinel 与集群 Cluster 三套方案，支撑数据冗余、故障转移与水平扩展（详见第 20 章至第 22 章）。
- **单线程命令执行**：命令执行核心为单线程，所有命令串行处理，天然规避并发竞争，单个操作具备原子性（详见第 16 章）。
- **多语言客户端**：官方与社区提供覆盖主流语言的客户端库，任何技术栈都能便捷接入。
- **操作原子性**：所有命令天然原子执行，配合事务与 Lua 脚本可组合出更大粒度的原子操作（详见第 23 章）。

三种角色的分工可用一句话区分：作缓存时数据在数据库中有母本，作数据库时数据以 Redis 为主，作消息中间件时它承担进程之间的信息传递。

> 单线程执行命令不代表 Redis 进程只有一个线程：持久化落盘、异步删除、网络 IO 读写等任务可由后台线程或辅助线程完成，但**命令的执行始终是单线程串行**的。这也是 Redis 事务与原子计数命令能够可靠工作的根本前提。

初学阶段把五条特点当作索引使用即可：读到某条命令行为反直觉时，回头想想它落在哪个特点上，理解就会快很多。

**速记**：Redis 五大特点——**内存快、结构多、能落盘、可高可用、命令单线程**。



#### Redis 与 Memcached 的对比

**Redis 与 Memcached 的对比**：二者都是流行的内存键值存储，但 Redis 在**数据结构、持久化、高可用**三方面全面领先，Memcached 仅在多线程与极简纯缓存场景下保有优势。

- **数据类型**：Memcached 只有字符串一种类型，值就是一串字节；Redis 提供多种数据结构，可直接对列表、集合执行入队、求交并等操作。
- **持久化**：Memcached 不支持持久化，重启即数据全丢；Redis 支持 RDB 与 AOF，重启后可恢复数据。
- **高可用**：Memcached 没有内置的复制与故障转移，扩容依赖客户端一致性哈希；Redis 原生提供主从复制、哨兵与集群。
- **线程模型**：Memcached 采用多线程处理请求，可以利用多核；Redis 命令执行为单线程，6.0 起网络 IO 可选多线程（详见第 16 章）。
- **单值大小**：Memcached 单个键值默认不超过 1MB；Redis 的字符串值最大可达 512MB。
- **功能生态**：Redis 还提供事务、Lua 脚本、发布订阅、权限控制 ACL 等能力，Memcached 的功能面则聚焦于存取本身。
- **社区活跃度**：Redis 的迭代速度、文档完备度与社区规模均明显占优，遇到问题的可检索性更强。

核心维度的对照可归纳如下：

```text
对比速查（Redis 对 Memcached）

数据类型：  多结构        对 单一字符串
持久化：    RDB + AOF    对 无
高可用：    主从/哨兵/集群 对 无内置方案
线程模型：  单线程执行    对 多线程
单值上限：  512MB        对 默认 1MB
附加能力：  事务/脚本/订阅 对 基本存取
```

> 选型上，若只需要纯缓存、键值都很小、希望多线程榨干多核，Memcached 依然可用；只要涉及**结构化数据、持久化、高可用**中任意一项，就直接选 Redis。当前新项目默认选 Redis 已是主流实践。

还应注意两者的运维心智不同：Memcached 是用完即弃的纯缓存，挂了就重建；Redis 因为常被赋予持久化与高可用职责，备份、监控、扩容都有一套完整的运维体系，这也是后续章节用大量篇幅讲它的原因。

**速记**：对比 Memcached，Redis 赢在**结构、持久化、高可用**；Memcached 赢在**多线程与简单**。



#### Redis 的典型应用场景概览

**Redis 的应用场景**：围绕其内存速度与丰富数据结构展开，典型场景有六类，本节各用一句话概览，细节由后续章节逐一展开。

- **缓存**：把热点数据放在 Redis 中挡在数据库之前，用亚毫秒级读取承接绝大部分请求，降低数据库压力（详见第 25 章、第 26 章）。
- **计数器**：利用 INCR 等原子命令实现阅读量、点赞数、限流计数，单线程模型保证计数不重不漏（详见第 3 章）。
- **排行榜**：利用 ZSet 的有序性与分数排序实现实时榜单，插入、更新与按排名取值都是对数级操作（详见第 7 章）。
- **分布式锁**：利用 SET NX EX 命令的原子性实现跨进程、跨主机的互斥锁（详见第 27 章）。
- **消息队列**：利用 List 的阻塞弹出或 Stream 的消费组实现轻量级消息的生产与消费（详见第 24 章）。
- **社交功能**：利用 Set 求共同好友与关注关系、利用 Bitmap 记录签到打卡与在线状态（详见第 6 章、第 8 章）。
- **会话与短数据**：登录会话、验证码等短生命周期数据也可存入 Redis，过期自动清理，用完即弃。

场景与类型的对应关系示意如下：

```text
场景 → 类型 → 代表命令

缓存     → String / Hash → SET GET HSET HGETALL
计数器   → String        → INCR INCRBY
排行榜   → ZSet          → ZADD ZRANGE ZREVRANGE
分布式锁 → String        → SET key value NX EX
消息队列 → List / Stream → LPUSH BRPOP XADD XREAD
社交关系 → Set / Bitmap  → SADD SINTER SETBIT BITCOUNT
```

> 场景与数据结构的对应关系是学习 Redis 的主线：**String 对计数与缓存、ZSet 对排序与榜单、Set 对关系与去重、List 与 Stream 对队列**。记住这组映射，遇到需求就能反推出该用哪种类型，反过来看到类型也能想起典型用法。

这些场景会在不同章节反复出现：同一个缓存，在缓存篇讲怎么挡流量，在一致性篇讲怎么与数据库同步；同一个 ZSet，在类型篇讲命令，在实战篇讲落地。学习时注意这种螺旋上升的编排。

**速记**：六大场景——**缓存、计数、榜单、锁、队列、社交**。



#### 版本演进速览

**Redis 的版本演进**：从 2009 年的 1.0 到 7.x，历经多个里程碑版本，能力从单一键值存储扩展为覆盖分片、消息、安全与脚本生态的完整数据平台。

- **1.0（2009 年）**：最初发布，提供基础的键值读写命令。
- **2.x（2010 至 2012 年）**：引入 Hash、Set、ZSet 等完整数据类型，奠定数据结构服务器的形态。
- **2.8（2013 年）**：引入独立的哨兵进程，复制支持部分重同步，主从架构走向成熟。
- **3.0（2015 年）**：引入 Redis Cluster，官方提供去中心化的分布式分片方案。
- **3.2（2016 年）**：引入 GEO 地理位置类型，支持经纬度与附近的人检索。
- **4.0（2017 年）**：引入模块系统、内存淘汰 LFU 算法、UNLINK 异步删除与惰性释放。
- **5.0（2018 年）**：引入 Stream 原生消息流与 RDB、AOF 混合持久化。
- **6.0（2020 年）**：引入多线程网络 IO、ACL 权限控制、客户端缓存与 RESP3 协议。
- **7.0（2022 年）**：引入 Functions、Multi-part AOF、Sharded Pub/Sub 等特性，持久化与函数能力大幅增强。
- 版本号采用主版本、次版本、修订号三段式，选版时以官方标记的稳定标签为准。
- 判断某个特性是否可用，先查官方文档确认引入版本，再确认当前实例版本。

> [!NOTE]
> **提醒内容**：本章只需建立时间线印象，每个版本的详细特性与选型影响见第 32 章。生产选版时优先选择已进入稳定维护期的版本，而非刚发布的最新版，让社区先行踩坑。

另一条观察版本演进的线索是能力边界的变化：3.0 解决数据太多单机放不下的问题，5.0 解决消息场景缺原生类型的问题，6.0 解决多核机器吃不满的问题，7.0 解决脚本与持久化的工程化问题。每个里程碑都对应一类真实的生产痛点，带着这条线索去看版本列表，比死记编号有效得多。

**速记**：里程碑口诀——**3.0 有集群、4.0 有模块、5.0 有 Stream、6.0 有多线程 IO、7.0 有 Functions**。



### 安装与启动

#### macOS 上用 Homebrew 安装

**macOS 安装 Redis**：推荐使用 **Homebrew** 一条命令完成安装，安装、升级与卸载都由 brew 统一管理，是 macOS 上的标准做法。

- 先执行 brew install redis 安装最新稳定版，brew 会自动处理依赖与路径。
- 安装后可用 brew services 命令把 Redis 注册为后台服务，随系统自启。
- 也可手动执行 redis-server 二进制临时启动一个实例，便于观察实时日志。
- 安装产物位于 brew 的 Cellar 目录，配置文件位于 etc 目录下的 redis.conf。
- 后续升级执行 brew upgrade redis，卸载执行 brew uninstall redis 即可。
- 若本机尚未安装 brew，先按 Homebrew 官网脚本安装 brew 再执行上述命令。
- 开发期更推荐方式三的前台启动，日志直接打在终端里，定位问题最直观。
- Apple Silicon 与 Intel 机型安装路径不同，配置文件位置以 brew --prefix redis 的输出为准。

```bash
# 安装 Redis
brew install redis

# 方式一：注册为后台服务，开机自启
brew services start redis

# 方式二：仅本次登录期间启动，重启后失效
brew services start redis --now

# 方式三：前台手动启动，便于开发时观察日志
redis-server

# 查看服务状态、重启与停止
brew services list
brew services restart redis
brew services stop redis

# 升级与卸载
brew upgrade redis
brew uninstall redis
```

安装完成后立即用 brew services list 确认服务状态为 started，再按本章后面的方法用 redis-cli 完成首次连接，一气呵成搭好环境。

> brew services start redis 默认以守护进程方式常驻，配置文件在 /opt/homebrew/etc/redis.conf（Apple Silicon 机型）或 /usr/local/etc/redis.conf（Intel 机型），修改配置后需执行 brew services restart redis 才能生效。

**速记**：macOS 三步——**brew install、brew services start、redis-cli ping**。



#### Linux 编译源码安装

**Linux 安装 Redis**：官方推荐**下载源码包并 make 编译**的方式，可安装任意指定版本，且不依赖发行版仓库里滞后的包版本。

- 从 Redis 官网下载稳定版源码包并解压，官网首页会给出当前推荐版本号。
- 进入解压目录执行 make 编译，再执行 make install 把可执行文件装入系统路径。
- 编译依赖 gcc 与 make 工具链，缺省时先用发行版的包管理器安装。
- 编译完成后 redis-server 与 redis-cli 即可直接使用，无需额外配置环境变量。
- 若需指定安装目录，使用 make install PREFIX=/your/path 前缀参数。
- 编译期间可并行执行 make test 做功能自检，确保产物完整可用。
- 版本选择上，去官网首页抄当前稳定版号即可，不必追求最新大版本。
- 编译产物与系统 glibc 版本相关，换机器部署时重新编译最稳妥。

```bash
# 安装编译依赖（以 Debian/Ubuntu 为例，CentOS 用 yum install gcc make）
sudo apt update && sudo apt install -y gcc make

# 下载并解压源码包
wget https://download.redis.io/releases/redis-7.2.4.tar.gz
tar xzf redis-7.2.4.tar.gz
cd redis-7.2.4

# 编译并安装，多核机器可加参数加速
make -j4
sudo make install

# 编译后自检（可选）
make test

# 验证安装结果
redis-server --version
redis-cli --version
```

> 编译失败最常见的原因是缺少 gcc 或内存不足，可先确认 gcc --version 可执行再重试；编译期间报内存不足时关闭其他程序或减小并发度。make install 默认装入 /usr/local/bin，使用 PREFIX 参数则装入指定目录下的 bin 子目录。

国内网络环境下 wget 下载源码包可能较慢，可改用镜像站或本地下好再上传；编译耗时与机器性能相关，普通开发机几分钟内即可完成。

**速记**：Linux 装法——**下载源码、make 编译、make install、--version 验证**。



#### Docker 方式安装运行

**Docker 运行 Redis**：用官方镜像一条 docker run 命令即可拉起实例，免去环境依赖与编译过程，适合本地实验、快速验证与容器化部署。

- 用 docker pull 拉取官方 redis 镜像，可用标签指定版本，如 redis:7.2。
- 用 docker run 启动容器，映射 6379 端口并挂载数据目录保证数据持久。
- 在镜像名后追加 redis-server 及参数，可实现开启 AOF、设置密码等启动配置。
- 用 docker exec 进入容器内的 redis-cli，或在宿主机直接连接映射端口均可操作。
- 容器的生命周期与数据是分离的，删容器不等于删数据，关键在于数据卷是否挂载。
- 多实例场景可再 run 一个容器改用 -p 6380:6379，即在本机并行跑多个端口实例。
- 生产容器化部署通常配合配置文件挂载与资源限制参数，本章掌握基本用法即可。

```bash
# 拉取官方镜像（可指定版本标签）
docker pull redis
docker pull redis:7.2

# 启动容器：映射端口、挂载数据目录、开启 AOF 持久化
docker run -d --name my-redis \
  -p 6379:6379 \
  -v /mydata/redis/data:/data \
  redis redis-server --appendonly yes

# 进入容器内的 redis-cli
docker exec -it my-redis redis-cli

# 宿主机直连映射端口
redis-cli -h 127.0.0.1 -p 6379 PING

# 查看容器日志、重启与清理容器
docker logs my-redis
docker restart my-redis
docker rm -f my-redis
```

> [!CAUTION]
> **注意内容**：容器删除后其可写层中的数据会一并消失，务必通过 -v 参数把宿主机目录挂载为数据卷，否则误删或重建容器即丢失全部数据。

用 Docker 方式学习本系列同样顺滑：一条 docker run 即可得到干净实例，学习完执行 docker rm 清理，不留痕迹；后续哨兵与集群章节需要一次性拉起多个节点，容器方式会明显省力。

**速记**：Docker 三件事——**pull 镜像、run 挂卷映射端口、exec 进 cli**。



#### 安装后的验证与产物位置

**安装验证**：安装完成后应先确认**服务端与客户端两个可执行文件都可用**，再进入连接测试，避免把环境问题误判为配置问题。

- 执行 redis-server --version 与 redis-cli --version，两个版本号应一致且来自同一次安装。
- 可执行文件的标准位置是 /usr/local/bin（源码 make install）或 brew 的 bin 目录（macOS）。
- 源码方式在 src 子目录下也会生成未安装的二进制，注意区分来源，避免用了旧版本而不知。
- 配置文件方面，源码安装的示例配置在源码目录的 redis.conf，brew 安装在 etc 目录。
- 找不到命令时用 which redis-server 排查 PATH 是否包含安装路径。

```bash
# 版本验证
redis-server --version
redis-cli --version

# 定位可执行文件
which redis-server
which redis-cli

# 源码安装目录下的关键产物（相对源码根目录）
# redis.conf          示例配置文件
# src/redis-server    服务端二进制
# src/redis-cli       客户端二进制
# src/redis-benchmark 基准测试工具
```

首次启动后用 DBSIZE 确认是空库，避免混入旧数据干扰学习。

> 版本不一致常发生在系统里同时存在 brew 版与手动编译版的情况，用 which 与 version 对照即可定位实际生效的那一个；确认后把不用的那份从 PATH 中移除，避免启动了错误版本还查不出原因。

验证通过后不必急着学习全部配置，先记住最小可用路径：一个 redis-server 起服务，一个 redis-cli 验证连通，其余配置项在后续章节用到时再逐个击破。

**速记**：装完先做三件事——**查版本、which 定位、再连接**。



### 服务端与客户端的使用

#### redis-server 的启动与指定配置文件

**redis-server 启动**：是 Redis 服务端的唯一启动入口，支持**不带参数默认启动**与**指定配置文件启动**两种方式，生产环境一律使用后者。

- 直接执行 redis-server，以默认配置在前台启动，监听 6379 端口，仅接受本机连接。
- 执行 redis-server 加配置文件路径，按文件内容启动，这是标准做法。
- 也可在命令行直接追加启动参数，临时覆盖个别配置项，例如指定端口或密码。
- 命令行参数可与配置文件叠加：先加载文件，再用参数覆盖其中的个别项。
- 启动成功后终端会打印 Redis 的字符标志与版本、端口、进程号等运行信息。
- 端口被占用时启动会立即失败并提示，先用 lsof 命令查清占用进程再处理。

```bash
# 默认配置启动（前台运行，端口 6379）
redis-server

# 指定配置文件启动（生产标准方式）
redis-server /etc/redis/redis.conf

# 命令行临时覆盖配置项：以 6380 端口启动
redis-server --port 6380

# 组合使用：配置文件为基础，命令行覆盖个别项
redis-server /etc/redis/redis.conf --port 6380 --requirepass yourpass

# 排查端口占用
lsof -i :6379

# 检测系统内存（示例为测试 2GB，用于容量规划）
redis-server --test-memory 2
```

> 配置文件启动优于命令行传参：配置可入库、可审计、可复制到多台机器保持一致。源码目录与安装目录提供的示例 redis.conf 覆盖了全部配置项并附注释，是理解每项配置含义的最好材料。

多实例并存是常见的本机实验形态：复制一份配置文件，改动其中的 port、pidfile、dir 等项，即可在同一台机器跑出互不干扰的多个实例，后续学习主从与集群时都要用到这一技巧。

**速记**：启动姿势——**裸跑仅实验，指文件为标准，命令行只做临时覆盖**。



#### daemonize 守护进程启动

**daemonize 配置项**：决定 redis-server 是否以**守护进程（后台进程）**方式运行，取值为 yes 或 no，生产环境通常设置为 yes。

- daemonize no（默认）：前台运行，进程占用当前终端，终端关闭或连接断开则进程随之退出。
- daemonize yes：后台守护进程方式运行，启动后进程脱离终端持续存在。
- 查看进程是否已在后台运行，执行 ps 加 grep 过滤 redis-server 即可。
- 生产配置文件应纳入版本管理，变更留痕、可回滚。
- 配合 pidfile 配置项可把进程号写入指定文件，便于脚本检测与停止进程。
- 配合 logfile 配置项把日志重定向到文件，避免后台模式下日志无处可写。
- 使用 systemd、brew services 等进程管理器托管时，通常保持前台模式，由管理器负责守护。
- 判断当前进程是否存活，可执行 ps aux 加 grep redis-server 查看。

```text
# redis.conf 中的相关配置示例
daemonize yes
pidfile /var/run/redis_6379.pid
loglevel notice
logfile "/var/log/redis/redis-server.log"
dir /var/lib/redis
bind 127.0.0.1
port 6379
```

> 前台运行便于开发期观察日志，后台运行是生产常态，选择依据是进程由谁托管：被 systemd 之类管理器接管就保持前台，无人接管才设置 daemonize yes。两者混用会导致进程被重复管理或意外退出。

以 systemd 托管为例，日常服务管理只需记住以下几条命令：

```bash
# 查看服务状态与最近日志
systemctl status redis

# 启动、停止、重启服务
sudo systemctl start redis
sudo systemctl stop redis
sudo systemctl restart redis

# 设置开机自启
sudo systemctl enable redis
```

**速记**：**daemonize yes 上后台，no 留前台**；交给 systemd 托管就用前台。



#### redis-cli 连接与 PING 测试

**redis-cli**：是 Redis 自带的**命令行客户端**，用于连接服务端、执行命令与调试，服务启动后的第一件事就是用它发送 PING 验证连通性。

- 本机直接执行 redis-cli，默认连接 127.0.0.1 的 6379 端口，进入交互模式。
- 用 -h 与 -p 参数指定主机与端口，用 -a 参数提供密码，用 -n 参数选择数据库编号。
- 连入交互模式后执行 PING，服务端返回 PONG 即表示服务与链路都正常。
- redis-cli 支持非交互式执行单条命令，把命令写在参数里即可，便于脚本调用。
- 交互模式内执行 help 加命令名，可查看任意命令的参数说明与示例。
- 执行 quit 或按 Control 加 C 可退出交互模式。
- 交互模式的提示符会实时显示当前连接的主机与端口，切换数据库后还会带上库号，随时可确认自己连在哪里。
- 用 --version 确认客户端与服务端版本一致，避免协议差异引起怪问题。

```bash
# 交互式连接本机默认端口
redis-cli

# 指定主机、端口、密码连接
redis-cli -h 127.0.0.1 -p 6379 -a yourpass

# 非交互式执行单条命令，适合脚本
redis-cli PING
redis-cli -h 192.168.1.10 -p 6379 SET greeting "hello"
redis-cli GET greeting
```

```text
# 连入交互模式后的典型会话
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> SET greeting "hello"
OK
127.0.0.1:6379> GET greeting
"hello"
127.0.0.1:6379> DBSIZE
(integer) 1
127.0.0.1:6379> SELECT 1
OK
127.0.0.1:6379[1]> QUIT
```

> [!IMPORTANT]
> **重要内容**：PING 返回 PONG 是一切排障的起点。连接失败时按固定顺序排查：进程是否存活、端口与防火墙是否放行、bind 与 protected-mode 是否限制了来源、密码是否正确，逐项确认而不是盲目重启。

redis-cli 的参数远不止本章用到的几个，但日常高频的就是 -h、-p、-a、-n 四个；更进阶的监控与调试用法见第 28 章。

**速记**：连通性自检——**redis-cli 连上发 PING，回 PONG 即健康**。



#### protected-mode 与 bind：远程连接的前提

**protected-mode 与 bind**：是控制 Redis **监听范围与安全模式**的两个核心配置，本机实验默认可用，远程机器连不上时先检查它们。

- **bind 配置项**：指定服务端绑定的网卡地址，默认 bind 127.0.0.1 表示只接受本机连接。
- **protected-mode 配置项**：默认 yes，在没有设置密码且未显式 bind 的情况下，拒绝一切远程连接。
- 想让其他机器访问：把 bind 改为对应网卡地址或 0.0.0.0，同时必须设置 requirepass 密码。
- 配置修改后需重启服务，或执行 CONFIG SET 命令在运行期临时生效。
- 云服务器上还要检查安全组与防火墙对 6379 端口的放行策略。
- 客户端连上后若报 NOAUTH 类错误，说明服务端已启用密码而连接未认证。
- 多实例并存时，每个实例要绑定不同的 bind 与 port 组合，避免端口冲突导致启动失败。
- 学习期可给容器加上 --rm 参数，退出即自动清理。
- requirepass 设置后所有客户端连接都需要先执行 AUTH 认证。

```text
# redis.conf 中的网络相关配置
bind 127.0.0.1
protected-mode yes
port 6379
timeout 0
tcp-keepalive 300
requirepass yourstrongpassword
```

> [!WARNING]
> **警告内容**：把 Redis 直接暴露在公网而未设置密码是重大安全事故来源，历史上有大量未授权访问导致数据被清除或勒索的案例。开启远程访问必须同时设置强密码 requirepass、收紧 bind 范围，生产环境更应只在内网监听。

如果只是本机开发，保持默认配置最安全；需要容器或虚拟机访问宿主机 Redis 时，用 Docker 网络或在 bind 中加入对应内网地址即可，同样不必对公网开放。

**速记**：远程连不上先查三件套——**bind、protected-mode、防火墙**；开放远程必须**配密码**。



#### redis-benchmark 快速性能自测

**redis-benchmark**：是随 Redis 附带的**官方基准测试工具**，可对服务端做吞吐量压测，安装后即可用于验证机器性能水位。

- 用 -q 参数输出精简结果，默认对 PING、SET、GET 等常用命令各压测一轮。
- 用 -c 指定并发连接数，用 -n 指定总请求数，用 -t 指定只测哪些命令。
- 用 -h 与 -p 指定目标实例，测试远程或非默认端口的服务端。
- 结果输出每秒操作数（QPS）与延迟百分位，是评估单机性能的直接依据。
- 自测结论只代表当前机器环境，不能直接套用到其他硬件与数据分布上。
- 压测时注意观察服务端内存与 CPU 占用，性能水位是机器、配置与命令三者共同作用的结果。
- 首次压测前先用 INFO 命令记下基线状态，压测后再对比。

```bash
# 精简模式：对默认命令集做一轮快速压测
redis-benchmark -q

# 指定并发 50、共 10 万次请求，只测 SET 与 GET
redis-benchmark -c 50 -n 100000 -t set,get -q

# 压测远程实例
redis-benchmark -h 192.168.1.10 -p 6379 -q

# 只输出汇总数字，适合脚本采集对比
redis-benchmark -q -n 100000 --csv
```

> 压测会真实写入大量测试键，默认键名形如 key:000001，压测完成后可用 DBSIZE 查看增量并按需清理；对生产实例压测务必避开业务高峰，或使用 -r 参数配合随机键避免污染已有数据。

压测结果的解读重点是相对比较而非绝对数字：同机不同版本、不同配置下的对比才有意义，单看一次 QPS 数字意义有限。

**速记**：自测三参数——**-c 并发、-n 请求数、-t 选命令**。



### 学习路线建议

#### 三阶段学习路线：命令、原理、实战

**Redis 的学习路线**：按 **先命令与数据类型、再内部原理、后高可用与实战** 的三阶段推进，与本书 Redis 主题 33 章的编排一一对应。

- **第一阶段：命令与数据类型**。从通用命令与键管理入手，逐个掌握 String、Hash、List、Set、ZSet 及 Bitmap、GEO、Stream 等拓展类型（详见第 2 章至第 9 章），每学一种类型就动手写一遍操作示例。
- **第二阶段：内部原理**。学习底层数据结构、对象系统与类型编码、数据库空间与过期删除、内存淘汰、事件循环与单线程模型、三种持久化机制（详见第 10 章至第 19 章），理解每种类型在不同数据量下的编码自动切换。
- **第三阶段：高可用与实战**。学习主从复制、哨兵、集群、事务与 Lua 脚本、发布订阅，再进入缓存穿透击穿雪崩、缓存一致性、分布式锁等实战专题，最后落到调试工具、性能优化、安全运维与版本演进（详见第 20 章至第 32 章）。
- 每个阶段都应配一个可运行的环境，用本章的任意一种安装方式准备一个本地实例即可。
- 阶段之间的检验标准：一阶段能不看文档写出常见命令，二阶段能说清命令背后的结构与开销，三阶段能独立设计并落地一套缓存加高可用方案。
- 三个阶段并非严格串行，命令可以在读原理篇时反复回练，但每个阶段的主线任务不要同时铺开。
- 学习时为每章维护一份自己的命令笔记，比单纯阅读留下更深的印象。

> [!TIP]
> **建议内容**：三个阶段不要跳跃。不熟命令就直接看原理，只会记结论而不知来由；不看原理就上实战，容易在缓存穿透、锁失效等问题上踩坑而不自知。本书章节编号即推荐学习顺序，按序推进即可。

对初学者而言，最先体感到的通常是内存读写与数据结构这两条特点：前者让一切操作飞快，后者让许多需求不必自己造轮子；持久化与高可用则要到生产化阶段才会真正接触。

**速记**：路线口诀——**一练命令、二懂原理、三上实战，章节顺序即学习顺序**。
