## 底层数据结构：SDS 与链表

**SDS 与链表**：是 Redis 字符串与线性结构两块最早的基石——SDS（简单动态字符串）给字节数组补上 len、alloc、flags 组成的头部账本，根治 C 字符串取长慢、会溢出、不安全的顽疾，是数据库所有键与字符串值的物理载体；adlist 链表以双端、无环、带计数的通用双向链表形态长期承担列表键的底层实现，3.2 起让位给 quicklist，退守为服务器内部的通用容器。

- 本章先讲 SDS 的来龙去脉：C 字符串的表示方式与四大缺陷，SDS 的结构设计与五种头部选型。
- 再讲 SDS 的核心特性：O(1) 获取长度、空间预分配、惰性空间释放与二进制安全。
- 然后把 SDS 与 C 字符串逐项对比，并交代它对部分 C 函数的兼容边界。
- 最后讲链表：使用场景、listNode 与 list 的结构、五大特性与缺陷，以及 3.2 起 quicklist、7.0 起 listpack 的接棒（细节详见第 12 章）。
- 阅读方法上，抓住「带不带账本」一条主线——SDS 的每个字段、链表的每次退场，都能在单线程、省内存、防阻塞三个约束里找到动机。

### 为什么要造 SDS

#### C 字符串的表示方式

**C 字符串**：是 C 语言中以**空字符 \0 结尾的字符数组**表示的字符串，Redis 用 C 语言开发，最初直接沿用 C 字符串来保存字符串数据。

- C 语言没有内建的字符串类型，字符串保存在**字符数组**中，数组末尾以**空字符 \0** 标记结束。
- 字符串的实际长度**没有被记录在任何字段里**，只能通过寻找 \0 的位置间接得知。
- 依据这一约定，C 标准库提供了 strlen、strcpy、strcat、strcmp 等一系列字符串操作函数，它们全部以 \0 为工作边界。
- Redis 并未全盘抛弃 C 字符串：**无须修改、无须存二进制**的场合（如日志打印、固定字面量）仍直接使用 C 字符串，需要作为值被存取与修改的字符串则交给自建结构 SDS。

```text
C 字符串在内存中的形态（示意）：

+---+---+---+---+---+----+
| r | e | d | i | s | \0 |
+---+---+---+---+---+----+
长度是多少？数组本身不记录，只能从头数到 \0 为止
```

> C 字符串并非一无是处：对**只读、纯文本**的场合，它简单、零额外开销。问题出在 Redis 的字符串键值需要**频繁修改、长度多变、内容任意**，C 字符串的缺陷在这一场景下被成倍放大，这正是本章主角 SDS 的出发点。

**速记**：C 字符串＝**\0 结尾的字符数组**，只读文本够用，动态键值不够用。



#### C 字符串的四大缺陷

**C 字符串的四大缺陷**：获取长度为 O(N)、拼接可能缓冲区溢出、修改必然引发内存重分配、不能保存二进制数据，这四点直接催生了 Redis 的 SDS。

- **获取长度 O(N)**：长度信息未被记录，strlen 函数必须**从数组头遍历到 \0** 才能数出长度，复杂度与字符串长度成正比，串越长扫描越慢。
- **缓冲区溢出**：strcat 等拼接函数假定目标数组有足够剩余空间，调用前若不做容量检查，拼接出的数据就会**写到数组边界之外**，破坏相邻内存中的其他数据。
- **频繁内存重分配**：增长要扩容、缩短要缩容，每一次修改都伴随 malloc 或 realloc 这类**昂贵的系统调用**，耗时且可能失败，高频修改场景下开销被反复支付。
- **不能保存二进制数据**：内容中一旦出现 \0 就被判定为字符串结束，其后的字节全部被忽略，因此只能存文本，不能存图片、压缩数据、序列化对象等**含空字节的二进制**。
- **与 char 数组强耦合**：字符串只能以 char 数组这一种形态表达，结构上没有携带长度、容量等元数据的位置，一切扩展都要在调用者层面另想办法。

```text
strcat 溢出示意：

char buf[5] = "red"        只剩 2 字节余量
strcat(buf, "isverylong")  目标空间不足，调用前无人检查

写入越过数组边界，直接踩到相邻内存
```

> [!WARNING]
> **警告内容**：缓冲区溢出不只是程序错误，而是**内存安全漏洞**。用 strcat 拼接前逐一检查容量，等于把防溢出的责任压给每一个调用者，既繁琐又容易遗漏，这正是 SDS 要从结构层面根除的问题。

> 四大缺陷的共同根源是**信息不足**：数组本身不带长度、不带容量两本账，一切都要靠调用者临时推算与人工保障。SDS 的解法就是给字符串补上这本账，后续小节逐条展开。

**速记**：**求长 O(N)、拼接溢出、改长重分配、\0 断二进制**，加上**char 数组强耦合**，五账齐催 SDS。



### SDS 的结构设计

#### SDS 的定义与基本结构

**SDS（Simple Dynamic String，简单动态字符串）**：Redis 自建的字符串结构，在字节数组之外**附带 len 与 alloc 等元信息字段**，全面取代 C 字符串成为字符串值的底层实现。

- Redis 中凡是字符串值——包括字符串键与字符串值——底层一律使用 SDS 保存；C 字符串只保留给只读字面量。
- SDS 的物理组成是 **header 加 buf**：header 存放元信息，buf 是保存实际内容的字节数组，二者一次连续分配。
- header 的三个核心字段：**len**（已使用字节数，即字符串长度）、**alloc**（分配的总字节数，不含 header）、**flags**（一字节，低 3 位标记 header 类型）。
- buf 末尾保留一个 \0，但它不参与判界，只为兼容部分 C 字符串函数。
- 键与值一视同仁：SET 执行后，键名与键值在数据库里都以 SDS 形式存在，字典的键侧与值侧皆是（详见第 11 章）。
- SDS 并不只服务数据类型：AOF 缓冲区、客户端输入缓冲区等内部缓冲，同样由 SDS 充当（详见第 18 章）。

```c
struct sdshdr8 {
    uint8_t len;         /* 已使用长度 */
    uint8_t alloc;       /* 分配总长度，不含 header */
    unsigned char flags; /* 低 3 位记录 header 类型，高 5 位未用 */
    char buf[];          /* 内容字节数组，末尾补一个 \0 */
};
```

```text
同样保存 "redis"，两种结构的差异（示意）：

C 字符串：  r e d i s \0                              无任何元信息
SDS：       len=5 | alloc | flags | r e d i s \0 + 余量  元信息前置
```

> header 与 buf **一次分配、连续存放**：访问内容时从结构地址向后偏移即可，省去了「结构体与数组分开两段分配」的额外开销，也改善了内存局部性。
> 空间账本的意义在修改前：先看余量够不够，再决定是否扩容，这是 SDS 一切策略的前提。

##### header 与 buf 的偏移关系

**偏移关系**：header 与 buf 同属一次分配，内容指针等于结构地址加上 header 大小。

- 不同 header 类型大小不同，取 buf 的偏移量也不同，由 flags 标记的类型决定走哪条路径。
- C 语言的柔性数组成员让 buf 紧贴结构尾部，取内容零额外寻址。
- 对外呈现的 sds 其实就是指向 buf 的指针，header 藏在指针前方。

> 「指针指向 buf、账本藏在身后」是 SDS 最巧妙的布局：向下兼容 C 字符串的使用习惯，向上提供完整元信息。

**速记**：**len 记长短、alloc 记容量、buf 装内容**，元信息与数据一体分配。



#### header 的五种类型与按长度选型

**header 分型**：SDS 按字符串长度选用 **sdshdr5、sdshdr8、sdshdr16、sdshdr32、sdshdr64** 五种头部，字符串越短，头部越小，内存越省。

- **sdshdr5**：内容小于 32 字节的超短字符串专用，长度只用 **5 个位**记录在 flags 的高 5 位，低 3 位存类型标记；没有 alloc 字段，不适合会被修改的字符串。
- **sdshdr8**：len 与 alloc 各占 1 字节，适用于长度不超过 255 的字符串，是 Redis 中最常见的头部类型。
- **sdshdr16**：len 与 alloc 各占 2 字节，适用于长度不超过 65535 的字符串。
- **sdshdr32 与 sdshdr64**：len 与 alloc 分别占 4 字节与 8 字节，服务更长的字符串；32 位平台上不会用到 sdshdr64。
- 除 sdshdr5 形态特殊外，其余四种**结构完全同形**，只是字段宽度不同，统一由 flags 的低 3 位标识类型。
- 创建 SDS 时按内容长度自动挑选 header；修改导致长度跨档时，Redis 会**升级 header 类型**并搬移数据，整个过程对使用者透明。

```text
五种 header 的字段宽度（示意）：

sdshdr5  ：无 len、alloc 字段，长度存于 flags 的高 5 位
sdshdr8  ：len 1 字节 + alloc 1 字节 + flags 1 字节
sdshdr16 ：len 2 字节 + alloc 2 字节 + flags 1 字节
sdshdr32 ：len 4 字节 + alloc 4 字节 + flags 1 字节
sdshdr64 ：len 8 字节 + alloc 8 字节 + flags 1 字节
```

> 按长度选头部是**按需付费**的设计：存一个十余字节的短键，头部只占 3 字节，而不是一律背上十几字节的大头部。Redis 中短字符串占比极高，这一分型显著降低了整体内存占用。
> 例外是 sdshdr5：它连 alloc 都不要，本质上押注内容不再增长，把极简做到底。

##### sdshdr5 的特殊形态

**sdshdr5**：超短字符串的极简头部，把长度与类型一并塞进一个字节的 flags 里。

- flags 的高 5 位存长度（内容不超过 31 字节），低 3 位存类型标记，一个字段干两份活。
- 没有 alloc 字段，意味着它**不预分配余量**，每次增长都会触发结构升级，故只服务几乎不再变化的短串。
- 典型对象：标记类短键、简短的枚举值、几乎不修改的元数据。

> 极简换省内存，代价是丧失增长能力——sdshdr5 是「空间换时间」策略里唯一选择「一点都不换」的形态。

> [!NOTE]
> **提醒内容**：不同版本的资料对 header 的描述不同。《Redis 设计与实现》基于 3.0 源码，介绍的是 len、free、buf 三字段的统一 header；而 len、alloc、flags 三字段并存、按长度分五种 header 的写法自 3.2 源码引入并沿用至今。核对结论前先对齐版本。

**速记**：**5、8、16、32、64 五种头**，越短越小，按需付费。



#### 结构演进：3.0 的 free 与 3.2 起的 flags 与 alloc

**SDS 的结构演进**：3.0 及之前使用**统一的 sdshdr（len、free、buf）**，3.2 起改为 **len、alloc、flags 三字段并按长度分五种 header**，演进方向是头部更小、分型更细。

- 3.0 及之前的 sdshdr：**len**（已用长度）、**free**（剩余可用空间）、**buf**（字节数组），所有 SDS 共用一种布局，仅字段宽度不同。
- free 的含义是 buf 中**尚未使用的字节数**，等于总容量减去 len，是预分配余量的直接记录。
- 3.2 起：不再显式记录 free，改为记录 **alloc**（总分配量），剩余空间用 **alloc 减 len 现场推算**；同时新增 **flags** 字节标记头部类型，短字符串得以使用更小的头部。
- 4.0、5.0 乃至后续版本沿用三字段布局，仅源码组织与注释微调，结构本身未再变化。

```c
/* 3.0 及之前的统一 header，《Redis 设计与实现》所载形态 */
struct sdshdr {
    unsigned int len;   /* 已使用长度 */
    unsigned int free;  /* 剩余可用空间 */
    char buf[];         /* 内容字节数组 */
};
```

> 从 free 到 alloc 不是等价改名：**free 是结果、alloc 是原因**。记录 alloc 后剩余空间可以推导，而 alloc 与 len 的差值本身就是容量的完整描述；配合 flags 又能把头部按内容长短缩放，一处改动换来两级收益。
> 复习时可用「字段的接力」概括：free 交棒给 alloc，flags 补上一笔，两次字段变更串起整部演进史。

##### 分档升级：header 类型的自动切换

**分档升级**：字符串增长跨越长度档位时，SDS 会自动更换更大的 header 并整体搬移内容，使用者无感知。

- 从 sdshdr8 增长到 256 字节以上时切换为 sdshdr16，以此类推向 sdshdr32、sdshdr64 递进。
- 升级需要重新分配内存并拷贝内容，**跨档的第一次修改成本略高**，之后恢复常态。
- 不存在降级：缩短字符串不会换回更小的 header，避免反复抖动。

> 升级是自动的、单向的、偶发的——把「罕见的高成本」换来「日常的零心智负担」，是一笔划算的交易。

**速记**：3.0 记 **free**，3.2 起记 **alloc 加 flags**，头部更小、分型更细。



### SDS 的核心特性

#### O(1) 获取字符串长度

**O(1) 获取字符串长度**：SDS 把长度常驻在 **len 字段**中，读取长度只需返回字段值，耗时与字符串实际长度无关。

- C 字符串求长须调用 strlen 从头遍历到 \0，复杂度 O(N)；SDS 直接读 len，复杂度恒为 O(1)。
- len 在**每次写入与修改时同步维护**，读到的永远是当前真实长度，不存在过期账目。
- 对 STRLEN 命令而言，值是一字节还是数百 MB，执行时间相同。
- 单线程模型下这一点的意义被放大：没有任何一条命令可以长期占用主线程，O(N) 的求长是与模型冲突的。

```text
保存内容 "redis" 的 sdshdr8 内存布局（示意）：

+------+-------+-------+-------------------------+
| len  | alloc | flags |  buf                    |
|  5   |  10   |  0    |  r e d i s \0 + 余量    |
+------+-------+-------+-------------------------+
```

```text
127.0.0.1:6379> SET greeting "hello world"
OK
127.0.0.1:6379> STRLEN greeting
(integer) 11
```

> 若没有 len，一条 STRLEN 就要扫描整段数据；在单线程的 Redis 里，一次 O(N) 扫描会让排在其后的所有命令排队等待。**O(1) 求长不是锦上添花，而是单线程模型下的生存底线**。

**速记**：长度躺在 **len** 里，STRLEN 恒定耗时。



#### 空间预分配策略

**空间预分配**：SDS 每次增长时**一次多申请一批额外空间**，把未来若干次增长的重分配摊薄为当下的这一次。

- 分配规则按修改后的长度 len 分档：**len 小于 1MB** 时，分配**两倍于 len** 的空间，其中一半留给未来增长使用。
- **len 不小于 1MB** 时，每次**多分配 1MB** 的未使用空间，不再随长度翻倍。
- 多申请的量记入 alloc，体现为 buf 中的**未使用字节**，随时可被后续增长直接复用。
- 效果：连续执行 N 次增长操作，实际发生的内存重分配次数**显著少于按需分配的 N 次**，增长越密集收益越大。
- 未使用空间并非永久占用：配合后文的惰性释放与收紧接口，余量可以在真正缺内存时交还。
- 预分配动作发生在扩容辅助函数 sdsMakeRoomFor 中：仅当余量不够本次写入时才触发，余量充足则直接写入。
- 1MB 分档的动机：超大字符串翻倍一次代价太大，固定 1MB 增量更可控。

##### 一次 APPEND 扩容的完整过程

**扩容过程**：空间不足时，先由扩容辅助函数按预分配策略定出新容量，再搬移数据、更新 len 与 alloc，最后写入新内容。

```text
初始：len=5,  alloc=5   内容 "redis"
APPEND 追加 4 字节，len 将变为 9，余量为 0，触发扩容
新长度 9 小于 1MB，按翻倍策略定出 alloc=18
结果：len=9,  alloc=18  写入新内容后，余下 9 字节未使用
```

> 余量并非浪费：下一次 APPEND 只要不超过 9 字节，就不再触发任何重分配；连续追加的场景下，绝大多数写入都直接落在现成余量里。
> 一次扩容、多次受益，是理解预分配价值的最短路径。

> [!TIP]
> **建议内容**：预估会持续追加的大 value（如日志拼接、计数累加），可留意 APPEND 类操作扩容时的分档行为——**1MB 是翻倍与加 1MB 的分水岭**，超大字符串每次扩容只多 1MB，而不是跟着长度一起翻倍。

> 预分配并非无代价：未使用空间本身占内存。Redis 以**空间换时间**——先用多存的字节换掉反复重分配的开销，再用惰性释放策略控制浪费，两个策略配套生效。

**速记**：**小于 1MB 翻倍、不小于 1MB 加 1MB**，多备粮草少搬家。



#### 惰性空间释放

**惰性空间释放**：SDS 缩短字符串时**不立即回收**多出来的字节，而是把它们留在 buf 中记作未使用空间，等待将来使用。

- 缩短操作只更新 len，多出的字节原样留在 buf 里，体现为 alloc 与 len 差值的扩大。
- 收益：缩短之后往往紧跟着再增长，遗留空间可直接复用，**免去一次重分配**。
- 余量不会永久占着：真正需要归还内存时，可通过收紧接口（源码 sds.c 中的 sdsRemoveFreeSpace 类函数）重新分配，把未使用空间交还。
- 彻底丢弃整个 SDS 时调用 sdsfree，一次性归还全部内存。
- SDSTRIM 类命令截去首尾空白，是典型的缩短操作，走的正是惰性释放路径。
- 缩短的常见来源还包括重写压缩、过期清理等内部调整，服务器层面同样受益于不立即回收。

```text
一次缩短后的余量变化（示意）：

缩短前：len=9,  alloc=18  内容 "redis, hi"
截断为 "redis"：
缩短后：len=5,  alloc=18  多出的 4 字节留在 buf 中，等待复用
```

> [!CAUTION]
> **注意内容**：惰性释放意味着**内存占用不会随内容缩短而立刻下降**。大字符串被大幅缩短后，进程内存水位仍停留在高位，监控上呈现的是「内存没降」而非泄漏；确需回收时才显式收紧。

> 与惰性释放相对的是**立即回收**策略：C 字符串缩短时只能由调用者手动 realloc 缩小数组。Redis 在「留余量」与「立刻还」之间选择了前者，把回收的决定权留给真正缺内存的时刻。
> 两者并不互斥：Redis 默认惰性，但保留显式收紧的出口，主动权始终在使用者手里。

**速记**：缩短**不还房**，余量记在 alloc，真缺内存再收。



#### 二进制安全

**二进制安全**：SDS 以 **len 判断字符串结束**而非依赖 \0，buf 中可以存放**任意字节的序列**，包括空字节。

- buf 按**字节语义**读写：图片、压缩数据、序列化对象、含 \0 的协议帧都可原样保存。
- 写入什么字节就存什么字节，读出什么字节就是什么字节，**中间不会截断**。
- C 字符串以 \0 判界，属于**非二进制安全**，内容里出现空字节即被切断。
- buf 末尾仍补写一个 \0，但只是**兼容 C 函数的礼节性结尾**，判界依据始终是 len。
- String 类型能存任意内容、GEO 与 Bitmap 等特性的存储根基，最终都落到这一性质上。

```text
保存含空字节内容的 SDS（示意）：

len = 8
buf = 0x01 0x02 0x00 0x7F 0xAB 0x00 0x33 0x44 \0
        内容中的两个 0x00 不会截断数据，len 等于 8 说明全部字节有效
```

```text
127.0.0.1:6379> SETBIT bits 7 1
(integer) 0
127.0.0.1:6379> STRLEN bits
(integer) 1
```

> [!IMPORTANT]
> **重要内容**：二进制安全是 String 类型能存图片、Protobuf、压缩包等**任意数据**的根本原因，也是 SDS 区别于 C 字符串最核心的能力差异；Redis 一切「值能存什么」，最终都取决于这一性质。

**速记**：**len 定界不靠 \0**，字节随便装。



### SDS 与 C 字符串的对比

#### 兼容部分 C 字符串函数

**部分兼容 C 字符串函数**：SDS 的 buf 末尾**保留一个 \0**，使其可以直接传给一部分按 C 字符串约定工作的标准库函数。

- \0 写在有效内容之后，**不计入 len**，只是数据区的最后一个字节。
- 由此 SDS 可直接传给 printf、strcasecmp 等**按 C 约定读取内容**的函数，不必先复制转换。
- 涉及精确字节处理的场景仍以 len 为准，不依赖 \0 判界。
- 收益：Redis 在重写字符串管理逻辑的同时，**复用了成熟的 C 工具函数**，降低了实现与调试成本。
- 边界：凡依赖 \0 截断语义的函数，对**内容含空字节**的 SDS 并不可靠，这类场景必须走 len 驱动的自有接口。
- Redis 自有的 sds 系列函数（sdslen、sdscat、sdscmp 等）围绕 len 与 alloc 工作，才是日常操作的主力接口。
- 两套函数并存不冲突：sds 系列负责正确性与扩容，C 函数只做只读的辅助工作。
- 兼容层的价值在边缘处：打印日志、与外部 C 代码交互时，SDS 的 buf 可以直接交给按 C 约定工作的函数，省去一次复制转换。

> 尾部 \0 是**握手礼，不是判界依据**：它换来的是与 C 生态函数的无缝协作，而真正的长度与边界信息始终以 len 为准。兼容与安全在 SDS 里是两条并行的轨道。

**速记**：尾部 **\0 只为兼容 C 函数**，判界永远看 len。



#### SDS 与 C 字符串的整体对比

**整体对比**：从求长、拼接、修改、存储四个维度逐项对照，**SDS 与 C 字符串**的能力差异全部来自「带不带账本」。

- **获取长度**：C 字符串 O(N) 遍历求长；SDS O(1) 读取 len 字段。
- **拼接安全**：C 字符串依赖调用者自查容量，容易缓冲区溢出；SDS 修改前先比较 alloc 与 len 的差值，空间不足则**自动扩容**，杜绝溢出。
- **修改开销**：C 字符串每次增减都可能触发重分配；SDS 用空间预分配与惰性释放把重分配次数压到最低。
- **存储能力**：C 字符串只能存不含 \0 的文本；SDS 二进制安全，可存任意字节。
- **结尾标记**：两者都以 \0 结尾，但 C 字符串以它判界，SDS 只用它兼容 C 函数。
- **适用场合**：C 字符串适合只读字面量；SDS 适合需要存取、修改、长度多变的字符串值。
- **复制与比较**：C 用 strcpy 与 strcmp，按 \0 判界；SDS 用 sdscpy 与 sdscmp，行为对齐但以 len 为界。
- **追加与扩容**：C 用 strcat 且不检查容量；SDS 用 sdscat，内部先检查余量、不足则自动扩容。
- **求长**：C 用 strlen 遍历全串；SDS 用 sdslen 直读字段。

> 记忆锚点：SDS 是**在 C 字符串外面包了一层元信息**的设计——数据仍是那个字节数组，只是多带了 len 与 alloc 两本账；账本齐全，四大缺陷逐一化解。

##### 账本为何是全部差异的根源

**根源**：四个对比维度的差异，全部可以归结到 len 与 alloc 两本账。

- 有 len，求长才从遍历变为读字段。
- 有 alloc 与余量检查，拼接才敢自动扩容，溢出才被杜绝。
- 余量可复用，预分配与惰性释放才有记账的依托。
- 判界改用 len，\0 才退化为兼容符号，二进制安全随之成立。

> 账本即能力：SDS 的每一条优势，都能指到某个具体字段上。

**速记**：**C 裸奔，SDS 记账**，账本在手，长度、安全、二进制全解决。



### 链表的引入与实现

#### 链表的使用场景

**链表**：Redis 自实现的**双端无环链表**，服务于长度可变、需要顺序组织、节点可频繁增删的内部场景。

- **列表键的底层实现之一**：列表键包含较多元素或较长元素时使用链表保存，元素少而短时使用压缩列表，后者的接棒者详见第 12 章。
- **发布与订阅**：频道的订阅者以链表组织，模式订阅同样挂在链表上（详见第 24 章）。
- **慢查询日志**：服务器状态中的慢查询日志以链表按序保存，方便逐条追加与遍历（详见第 29 章）。
- **客户端状态**：服务器的客户端链表把每个连接对应的客户端结构串起来，遍历一次即处理所有连接。
- **监视器与内部队列**：监视器客户端、服务器内部各类待处理队列也大量借助链表组织。
- 理解场景的意义在于把握链表的定位：它服务的是**服务器自身的状态管理**，而非某个面向用户的数据类型命令。
- 这些场景的共同特点是：元素数量不定、以遍历与两端增删为主、几乎不做随机访问，正是链表擅长而数组别扭的形态。
- 反过来说，需要随机访问、元素小而多的场合，链表从来不是答案，这一判断在下一模块得到印证。

> 链表在 Redis 中更多是**服务器内部基础设施**而非用户直接可见的类型：列表键的底层实现后来交给了 quicklist 与 listpack（详见第 12 章），链表则退守为各类状态队列的通用容器。

##### 场景背后的共性

**共性**：这些场景的元素都不做随机访问、长度不定、以两端操作与遍历为主。

- 客户端链表：新连接挂尾、断开摘除、定时遍历——两端加遍历。
- 慢查询日志：新日志插头、超限裁尾、按序读取——两端加遍历。
- 发布订阅：订阅挂链、退订摘除、广播遍历——两端加遍历。

> 抽象成一句话：链表服务的是「队列式」的内部需求，凡需要下标随机访问的地方，链表从不出现。

- 共性判断也是答题的开关：题目从「存什么」转向「怎么组织」，底层结构的答案随之切换。

**速记**：**列表键、发布订阅、慢日志、客户端表**，内部处处见链表。



#### listNode 与 list 的结构

**listNode 与 list**：Redis 链表由**节点结构 listNode** 与**管理结构 list** 两层组成，节点承载元素并串联成链，list 持有首尾指针、长度计数与类型相关函数。

```c
typedef struct listNode {
    struct listNode *prev; /* 前置节点 */
    struct listNode *next; /* 后置节点 */
    void *value;           /* 节点值，万能指针 */
} listNode;
```

- prev 与 next 分别指向前、后节点，构成**双端**链。
- 表头节点的 prev 与表尾节点的 next 均指向 NULL，链表**无环**，以 NULL 为遍历边界。
- value 是 void 类型指针，节点可以承载任意类型的值。

```c
typedef struct list {
    listNode *head;                     /* 表头节点指针 */
    listNode *tail;                     /* 表尾节点指针 */
    unsigned long len;                  /* 节点数量计数器 */
    void *(*dup)(void *ptr);            /* 节点值复制函数 */
    void (*free)(void *ptr);            /* 节点值释放函数 */
    int (*match)(void *ptr, void *key); /* 节点值比较函数 */
} list;
```

- head 与 tail 使**表头、表尾的插入与删除都是 O(1)**，双向遍历也以二者为起点。
- len 是**长度计数器**，统计节点数 O(1)，无须遍历整个链。
- **dup、free、match** 三个函数指针构成多态机制：dup 复制节点值，free 释放节点值，match 判断节点值与给定目标是否相等，均由使用方按值的类型注入。
- 遍历由配套的迭代器结构 listIter 完成，它持有当前节点指针与迭代方向，沿 prev 或 next 逐节点前进。
- 两层结构的连接点是 list 的 head 与 tail：list 不持有节点数组，只握住链的两端。
- listNode 自身并不知道所属链表的存在，节点之间靠 prev 与 next 相互发现，解耦彻底。
- 两层结构之间没有继承关系：list 不是 listNode 的容器，只是握住两个节点指针与一套函数。
- 释放链表时由 list 的 free 函数逐节点释放值，再释放节点本身，避免值类型不同导致的泄漏。

> 双层分工的意义：listNode 只负责「链的形状」，**一切与值类型相关的逻辑都上收到 list 的函数指针**，同一套链表代码得以服务字符串、整数、客户端对象等不同类型的值。
> listIter 虽小，却体现同一分工哲学：形状归节点，方向归迭代器，类型归 list。

##### 三个函数指针的职责

**函数指针三件套**：dup、free、match 分别接管节点值的复制、释放与比较，是链表多态能力的全部来源。

- **dup**：按值的类型复制一份新值，复制链表或节点时使用；无须复制能力可置空。
- **free**：按值的类型释放内存；若值是简单整数或无须释放，可设为 NULL。
- **match**：判断某个值是否为查找目标，链表的查找与删除都经由它完成比较。

> 三个指针都由创建链表的一方注入：服务客户端链表就传客户端的释放与匹配函数，服务订阅频道就传频道的那一套——同一份链表代码因此处处可用。

**速记**：节点三成员 **prev、next、value**，list 六成员 **head、tail、len、dup、free、match**。



#### 链表的特性总结

**Redis 链表的五大特性**：双端、无环、带表头指针与表尾指针、带长度计数器、多态。

- **双端**：每个节点同时持有 prev 与 next 指针，获取某节点的前、后邻节点复杂度 O(1)。
- **无环**：表头节点的 prev 与表尾节点的 next 都指向 NULL，遍历以 NULL 结束，不会绕回成圈。
- **带表头指针与表尾指针**：list 的 head 与 tail 直接定位两端，两端的插入删除与查找都是 O(1)。
- **带长度计数器**：list 的 len 直接给出节点数，求链表长度 O(1)。
- **多态**：dup、free、match 按值的类型注入，同一链表结构可以保存不同类型的值，节点值类型不受限。

```text
list 结构示意：

head ──> [节点] <──> [节点] <──> [节点] <── tail
         prev=NULL            next=NULL
len = 3        dup / free / match 挂在 list 上，按值类型注入
```

- 对命令而言：LPUSH 与 RPUSH 命中 head 或 tail，O(1) 完成插入；LLEN 直读 len，O(1) 返回。
- 正向与反向遍历代价相同，这来自双端特性；迭代器按 direction 字段选择方向即可。
- 特性是结构的「能力清单」，列表类型命令的性能承诺（详见第 5 章）最终都由这些能力兑现。
- 五条特性与结构成员一一对应，可与上一考点的两个结构定义对照背诵。

> 五条特性全部由结构字段直接支撑：前四条来自指针与计数器字段，多态来自函数指针。答题时按「**结构字段决定特性**」的线索逐一回推即可，不必死记。

##### 特性与命令的对应

**对应关系**：每一条特性都能落到具体命令的性能表现上。

- LPUSH 与 RPUSH 得益于 head、tail 双指针，两端插入 O(1)。
- LLEN 得益于 len 计数器，O(1) 返回节点数。
- 遍历类操作得益于双端与无环设计，正反两个方向都能安全终止。

- 命令文档里的复杂度承诺，全部可以从这五条特性推导出来——这是「结构决定性能」最直接的例证。
- 掌握对应关系后，还可以由命令性能反推底层实现，形成双向验证。

**速记**：**双端、无环、头尾指针、长度计数、多态**，五特性一气呵成。



### 链表的缺陷与退场

#### 链表的缺陷

**链表的缺陷**：内存与访问效率双重不佳——逐节点分配、指针冗余、碎片化、CPU 缓存不友好，元素越小越多，代价越突出。

- **逐节点独立分配**：每个 listNode 单独 malloc 与释放，节点一多，分配次数与管理开销同步膨胀。
- **指针开销大**：64 位平台上 prev 与 next 各占 8 字节，value 又是一个指针，哪怕只存一个小整数，节点也要背上三个指针的包袱。
- **内存碎片化**：节点地址在堆上零散分布，加剧碎片，内存的申请、回收与压缩都更困难。
- **CPU 缓存不友好**：遍历沿指针在内存中随机跳转，无法利用缓存局部性与硬件预取；连续内存的数组式结构在同等工作量下访问速度远胜链表。
- 对比压缩列表（详见第 12 章）：后者把元素紧密排在一段连续内存中，正是冲着链表这几条缺陷设计的。
- 与 SDS 的处境相似：链表的问题同样不是「不能用」，而是「单位成本太高」。

##### 指针开销的算术账

**算术账**：把链表与连续内存放在同一杆秤上比较，指针开销的量级差距一目了然。

```text
存 10000 个各 4 字节的小整数（64 位平台，示意）：

链表：      10000 个节点 ×（prev、next、value 共 24 字节指针
            加节点管理与独立分配开销）≈ 数百 KB 起
连续内存：  10000 × 4 字节 ≈ 40 KB
```

> 小元素越多，账面差距越大；这正是列表键的底层实现从链表转向连续内存结构（详见第 12 章）最直接的算术依据。

> 在内存昂贵的数据库进程里，为**每个小元素付出三个指针加一次独立分配**极不划算；列表键动辄成千上万个元素，链表的账单很快变得不可接受，这为后续结构的上位埋下伏笔。
> 注意缺陷清单里没有「功能缺失」：链表功能齐全，输在成本，这为理解 quicklist 的折中设计定了调。

**速记**：**逐个分配、三指针、碎片化、缓存不友好**，链表四大软肋。



#### quicklist 与 listpack 的演进动因

**演进动因**：为消除链表缺陷，Redis 3.2 以 **quicklist** 取代链表与压缩列表成为列表键的底层实现，7.0 又以 **listpack** 取代压缩列表，主线是**连续内存对离散节点的胜利**（结构细节详见第 12 章）。

- quicklist 的思路：把链表的**节点换成连续内存的小段**（ziplist 编码），小段之间仍以双向指针相连，兼得两端快速增删与较好的缓存局部性。
- listpack 的思路：整段**连续编码**、彻底去掉节点间指针，进一步压缩内存与访问成本（详见第 12 章）。
- 演进的结果：链表退出列表键的底层实现，退守为服务器内部各类状态队列的通用容器。
- 演进并未否定链表本身：quicklist 的小段之间仍是双向链表形态，只是把「节点」从单个元素升级为一小段连续内存。
- 一句话概括动因：内存贵、缓存贵，指针的自由因此变得昂贵。
- 对象系统按元素多寡在不同编码间切换的规则，详见第 13 章。
- 本章只交代链表为何退场；quicklist 与 listpack 的结构、编码与转换条件详见第 12 章。
- 阅读老版本源码时，列表键编码字段出现的 ziplist 与 linkedlist 字样，对应本章时间线的两端。

```text
列表键底层实现的演进时间线：

2.6 至 3.0   ziplist 或 linkedlist，按元素数量与大小切换
3.2          quicklist 上位，成为列表键唯一底层实现
7.0          listpack 取代 ziplist，quicklist 节点改由 listpack 编码
```

> [!NOTE]
> **提醒内容**：老资料中「列表键底层是链表或压缩列表」的说法对应 3.2 之前的版本；3.2 起统一为 quicklist，7.0 起引入 listpack。核对结论前先确认所依据的 Redis 版本。

**速记**：**3.2 quicklist、7.0 listpack**，连续内存替离散节点，链表退居幕后。
