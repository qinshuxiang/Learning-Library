## 数据类型：List

### List 的认识

#### List 的定义与双端特性

**List（列表）**：是 Redis 中按插入顺序排序的字符串元素的集合，支持从列表头部（左端）与尾部（右端）两端推入与弹出，属于双端可达的线性结构。

- 元素可重复：List 是列表而非集合，不自动去重，同一字符串可出现多次。
- 有序：顺序即插入顺序，支持按下标访问；下标 0 表示头部第一个元素，-1 表示尾部最后一个元素。
- 容量上限：一个 List 最多可容纳 2 的 32 次方减 1 个元素，超过 42 亿个，实际规模受内存限制。
- 操作成本：头尾推入与弹出时间复杂度 O(1)；按下标定位与按值查找为 O(N)。
- 一个键对应一个 List，键的命名、删除与过期等管理行为服从通用命令规则（详见第 2 章）。
- 与 String 的单值不同，List 的值是元素的有序集合，但元素本身仍只能是字符串，不能嵌套列表（详见第 3 章）。
- 典型定位：消息缓冲、最新记录、待办队列等需要「按到来顺序维护一批条目」的场景，都以 List 为首选。

> List 可以看作双向链表的对外形态：左端与右端都是操作口，既可当队列（一头进另一头出），也可当栈（同一头进出），这两种用法贯穿本章全部命令。
>
> 「按插入顺序」强调顺序来自写入动作本身，不依赖任何排序参数；需要按分数排序的场景属于 ZSet 的职责（详见第 7 章）。

```bash
RPUSH queue:task "a" "b" "c"   # 从右端依次推入 a、b、c
LPUSH queue:task "z"           # 从左端再推入一个
LRANGE queue:task 0 -1         # 查看全量
```

```text
1) "z"
2) "a"
3) "b"
4) "c"
```

**速记**：List 是**双端可达**的有序字符串列表，头尾操作 **O(1)**，容量上限 **2 的 32 次方减 1**。



### 入队与出队

#### LPUSH 与 RPUSH

**LPUSH 与 RPUSH**：是向 List 头部（左端）与尾部（右端）推入元素的两个入队命令，均可一次推入多个值，返回推入后列表的长度。

- 语法：LPUSH key value [value ...] 与 RPUSH key value [value ...]，值为一个或多个字符串。
- 一次推入多个值时按书写顺序依次压入：RPUSH 依次追加到尾部，LPUSH 依次压到头部。
- 键不存在时先创建空列表再推入；键存在但不是列表时返回 WRONGTYPE 错误。
- 返回值：推入操作完成后列表的新长度。
- 两个命令都只接触列表端点，即使列表很长也不影响耗时。
- 二者均为写操作，同样参与持久化与主从复制，语义与普通写命令一致（详见第 17 章与第 20 章）。

```bash
RPUSH log "m1" "m2" "m3"   # 列表从左到右为 m1 m2 m3
LPUSH log "m0"             # 列表从左到右为 m0 m1 m2 m3
LPUSH log "a" "b" "c"      # 多值推入，注意顺序
LRANGE log 0 -1
```

```text
1) "c"
2) "b"
3) "a"
4) "m0"
5) "m1"
6) "m2"
7) "m3"
```

> LPUSH 推入多个值的顺序是易错点：LPUSH key a b c 之后列表从左到右是 c b a——a 先进头部，b 再压到 a 前面，c 再压到 b 前面；RPUSH 则保持 a b c 的书写顺序不变。
>
> 用同一端进出可以模拟栈：LPUSH 进、LPOP 出即后进先出；两端分别进出则模拟队列：LPUSH 进、BRPOP 出即先进先出。

**速记**：RPUSH **顺序进**，LPUSH **倒序进**，二者都返回**新长度**。



#### LPOP 与 RPOP 的 COUNT 参数

**LPOP 与 RPOP**：是从 List 头部（左端）与尾部（右端）弹出并返回元素的两个出队命令，Redis 6.2 起支持可选的 COUNT 参数一次弹出多个。

- 语法：LPOP key [count] 与 RPOP key [count]。
- 不带 count：弹出单个元素并返回其值；列表为空或键不存在时返回 nil。
- 带 count（6.2+）：弹出至多 count 个元素，以数组返回；count 大于列表长度时弹出全部，不报错。
- 弹出即删除：被弹出的元素同时从列表移除；列表变空后键自动消失。
- count 为 0 或负数时返回空数组，不报错。
- 出队方向应与入队方向相反，才能维持先进先出：LPUSH 入队配 BRPOP 出队，RPUSH 入队配 BLPOP 出队。

```bash
RPUSH q "a" "b" "c" "d" "e"
RPOP q 2        # 从右端弹出两个
LPOP q          # 从左端弹出一个
```

```text
1) "e"
2) "d"
```

```text
"a"
```

> 不带 count 与带 count 的返回形态不同：前者返回单个字符串或 nil，后者返回数组；客户端代码要注意区分这两种返回类型。COUNT 参数为 6.2 新增，旧版本只能一次弹一个。
>
> 批量弹出在「一次搬走一批任务」的场景很有用，但一次弹出过多会占用客户端内存，批量大小应与单条业务处理能力匹配。

**速记**：LPOP/RPOP **弹出即删**，6.2 起带 **COUNT 弹多个**。



#### LPUSHX 与 RPUSHX

**LPUSHX 与 RPUSHX**：是「键存在才推入」的保守版入队命令，键不存在时不创建列表、直接放弃本次操作。

- 语法：LPUSHX key value [value ...] 与 RPUSHX key value [value ...]，同样支持一次推入多个值。
- 键存在且为列表：推入并返回新长度；键不存在：返回 0，列表不会被创建。
- 典型用途：防止业务代码拼错键名后悄悄创建出一批只含一个元素的孤儿列表。
- 定长列表场景中，首次初始化用 LPUSH 建键，之后持续写入可改用 LPUSHX 加 LTRIM。

```bash
LPUSHX ghost:key "x"     # 键不存在，返回 0，键仍未创建
RPUSH ghost:key "x"      # 对比：会创建键并推入
EXISTS ghost:key
```

```text
0
1
```

> LPUSHX 返回 0 的语义就是键不存在：容器类型键在变空后会被 Redis 立即删除，不存在「存在但为空列表」的中间态，这一自动删除规则与 Hash、Set 一致（详见第 2 章）。

**速记**：LPUSHX/RPUSHX **键在才推**，返回 **0 即未推**。



### 查看与定位

#### LRANGE 的正负索引

**LRANGE**：是按索引区间读取 List 元素的查看命令，支持正负两套索引，区间两端均为闭区间。

- 语法：LRANGE key start stop，返回区间内元素组成的数组。
- 正索引：0 表示头部第一个元素，1 表示第二个，依此类推。
- 负索引：-1 表示尾部最后一个元素，-2 表示倒数第二个，依此类推。
- 两端闭区间：LRANGE key 0 2 返回第 1 到第 3 个元素，与多数编程语言「含头不含尾」的切片不同。
- 越界容忍：start 或 stop 超出实际范围时按越界端截断，不报错；区间无交集时返回空数组。
- 返回数组按列表从左到右的原顺序排列，与区间书写方向无关；start 大于 stop 的写法只会得到空数组。

```bash
RPUSH nums "a" "b" "c" "d" "e"
LRANGE nums 1 3
LRANGE nums -3 -1
LRANGE nums 0 -1
```

```text
1) "b"
2) "c"
3) "d"
```

> 0 -1 是查看全量的惯用法，但仅适合元素规模可控的列表；对大列表执行 0 -1 是典型性能坑，展开见本章末尾的常见误用一节。
>
> LRANGE 是只读命令，不会改动列表；要「取走并删除」应使用弹出类命令，二者职责不同，不能互相替代。
>
> 分页读取直接换算区间即可：每页 10 条时，第 n 页是 LRANGE key start stop，其中 start 为 n 减 1 再乘 10，stop 为 start 加 9；使用负索引写 LRANGE key -10 -1 可读尾部一页。

**速记**：LRANGE **闭区间**、支持**负索引**、越界**截断不报错**，**0 -1** 取全量。



#### LLEN、LINDEX 与 LPOS

**LLEN、LINDEX 与 LPOS**：是 List 的三个定位查看命令，分别用于获取长度、按下标读取单个元素与按值查找元素位置。

- 语法：LLEN key 返回列表长度；键不存在时返回 0，不报错；长度常驻列表头中，复杂度 O(1)。
- 语法：LINDEX key index 返回指定下标的元素；index 支持负数，-1 即最后一个元素；键不存在时返回 nil。
- 语法：LPOS key element [RANK rank] [COUNT num] [MAXLEN len]，查找元素位置，Redis 6.2 新增。
- LPOS 默认返回元素第一次出现的下标，找不到返回 nil。
- RANK：指定第几次出现的匹配，正数从头数、负数从尾数，RANK 1 与默认行为一致。
- COUNT：返回最多 num 个匹配位置组成的数组，COUNT 0 表示返回全部匹配位置。
- MAXLEN：限制参与比较的元素个数，避免在长列表上做全表扫描。
- 三个选项可组合使用，例如 LPOS key element RANK -2 COUNT 3 MAXLEN 100 表示从尾部起、在至多 100 个元素内找倒数第二个匹配起的 3 个位置。

```bash
RPUSH nums "a" "b" "a" "c" "a"
LLEN nums
LINDEX nums -1
LPOS nums "a"
LPOS nums "a" COUNT 0
LPOS nums "a" RANK -1
```

```text
5
```

```text
"e"
```

```text
0
```

```text
1) "0"
2) "2"
3) "4"
```

> LLEN 等于 0 即「列表为空」，不必用 LRANGE 绕路判断；LINDEX 取头尾元素为 O(1)，取中间元素仍是 O(N)；LPOS 只能定位不能替代成员判断——需要频繁判断「元素是否存在」时，List 的按值查找最坏 O(N)，而 Set 的 SISMEMBER 为 O(1)，应改用 Set（详见第 6 章）。

**速记**：LLEN **O(1) 取长度**，LINDEX **按下标取值**，LPOS **按值查位置**（6.2+）。



### 修改与删除

#### LSET 与 LINSERT

**LSET 与 LINSERT**：分别用于覆写指定下标的元素与在指定元素前后插入新元素，是 List 上仅有的两个原位修改命令。

- 语法：LSET key index element，把下标 index 处的元素替换为 element，成功返回 OK。
- LSET 越界会报错：键不存在时报 no such key，index 超出范围时报 index out of range，与 LRANGE 的越界截断不同。
- 语法：LINSERT key BEFORE|AFTER pivot element，在值为 pivot 的元素之前或之后插入 element。
- LINSERT 返回插入后的列表长度；键不存在时报错，找不到 pivot 时返回 -1 且不执行插入。
- 两个命令都要求先有可定位的目标（下标或 pivot 值），不能向空列表插入。
- 二者复杂度均为 O(N)，N 为到达目标位置需要经过的元素个数；频繁调用应评估数据模型。

```bash
RPUSH nums "a" "b" "c"
LSET nums 0 "A"
LINSERT nums BEFORE "A" "X"
LRANGE nums 0 -1
```

```text
OK
```

```text
4
```

```text
1) "X"
2) "A"
3) "b"
4) "c"
```

> LINSERT 只以匹配到的第一个 pivot 为准；列表中存在多个同值元素时，插入位置取决于从哪端先匹配到，语义并不对称，谨慎用于可能重复的元素。
>
> LSET 适合「修正某一条记录」的场景，例如把任务列表中第 3 个任务改为新内容；若业务需要频繁按下标改写，也应评估是否更适合用 Hash 的字段存取（详见第 4 章）。

**速记**：LSET **改下标**（越界报错），LINSERT **贴着 pivot 插**（找不到返回 -1）。



#### LREM 的三种计数语义

**LREM**：是删除 List 中指定值元素的命令，删除个数由 count 参数的正负与零值决定，共三种语义。

- 语法：LREM key count element，返回实际删除的元素个数。
- count 大于 0：从头部向尾部方向删除至多 count 个等于 element 的元素。
- count 小于 0：从尾部向头部方向删除至多 count 绝对值个等于 element 的元素。
- count 等于 0：删除全部等于 element 的元素。
- 返回值为本次实际删除的个数，可能小于请求个数——列表中匹配元素不足时按实际数量删除。

```bash
RPUSH nums "a" "b" "a" "c" "a"
LREM nums 1 "a"
LREM nums -1 "a"
LREM nums 0 "a"
```

```text
1
```

```text
1
```

```text
1
```

> [!CAUTION]
> **注意内容**：LREM 的时间复杂度为 O(N)，N 是列表长度；在长列表上按值删除会整表扫描，且删除方向由 count 正负决定，正负号写反会出现「删错了方向」的隐性缺陷，排查成本高。

> 顺带区分 List 的三类删除手段：LREM 按值删、LTRIM 按下标划界删、LPOP 与 RPOP 弹出端点，三者的适用条件互不相同，替换使用前先确认删除依据。

**速记**：LREM **正头负尾零全部**，返回**实删个数**。



### 裁剪与定长列表

#### LTRIM 保留区间

**LTRIM**：是裁剪 List 的命令，只保留指定索引区间内的元素，区间外的元素被一并删除。

- 语法：LTRIM key start stop，区间语义与 LRANGE 完全一致：闭区间、支持负索引、越界截断。
- 成功返回 OK；裁剪后列表变空则键自动删除。
- 与 LPUSH 组合是「最新 N 条」的标准写法：先从头部推入新元素，再裁剪保留前 N 个。
- 裁剪是批量删除，效率高于逐个 LREM，且不关心元素值，只按下标划界。
- start 与 stop 可同为负索引，例如 LTRIM key -100 -1 表示只保留尾部 100 条。

```bash
LPUSH news:latest "n3" "n2" "n1"
LTRIM news:latest 0 1
LRANGE news:latest 0 -1
```

```text
OK
```

```text
1) "n1"
2) "n2"
```

> [!TIP]
> **建议内容**：凡是「只要最新 N 条」的列表都应在写入后随手跟一条 LTRIM，例如 LPUSH 后执行 LTRIM key 0 99；这一对命令让列表长度恒定有界，是 List 场景中性价比最高的防膨胀手段。
>
> LTRIM 与 LPUSH 还可组合出「先写后裁、原子间隙」的写法：多客户端并发写入时，各自 LPUSH 后再 LTRIM，最终列表仍收敛到定长，个别瞬间的超长不影响结果正确性。

**速记**：LTRIM **只留区间**，配 LPUSH 做**定长最新列表**。



### 阻塞弹出

#### BLPOP 与 BRPOP

**BLPOP 与 BRPOP**：是 LPOP 与 RPOP 的阻塞版本，列表为空时命令挂起等待，直到有元素可弹或超时，是 List 担任简单消息队列的核心能力。

- 语法：BLPOP key [key ...] timeout，BRPOP 同理；timeout 单位为秒，支持小数。
- timeout 等于 0 表示无限期阻塞，直到任一监听列表出现新元素。
- 多键监听时按给定顺序检查：哪个键先有元素就从哪个键弹出；多个键同时有元素时取书写最靠前的键。
- 唤醒机制：另一客户端对该键执行 LPUSH 或 RPUSH 推入元素时，等待中的客户端立即被唤醒并完成弹出。
- 返回值是两元素数组：第一个是弹出来源的键名，第二个是弹出的值——监听多键时靠它区分来源。
- 多个客户端等待同一键时，按等待先后顺序依次唤醒，先到先得。
- 阻塞期间客户端连接必须保持打开，连接断开即取消等待。
- timeout 支持小数秒，例如 0.1 表示最多等待 100 毫秒。
- BRPOP 与 BLPOP 只差弹出方向，其余语义完全一致。

```bash
# 消费者：阻塞等任务，10 秒无任务则返回 nil
BLPOP queue:task 10
# 生产者：推入任务后消费者立刻收到
LPUSH queue:task "job1"
```

```text
1) "queue:task"
2) "job1"
```

```bash
# 多键监听：先检查 A 再检查 B
BLPOP queue:a queue:b 0
```

> [!IMPORTANT]
> **重要内容**：timeout 为 0 的 BLPOP 会永久阻塞，客户端连接被长期占用；在使用连接池的应用中，若业务线程也一并挂起，可能耗尽连接池拖垮服务，务必为 timeout 设定合理上限，或在独立线程中消费。

> 阻塞等待发生在服务端：连接挂着但并不轮询，Redis 的事件循环在有新元素入队时才唤醒对应客户端，因此长时间等待不消耗 CPU，代价只是占用一条连接。
>
> 超时后 BLPOP 返回 nil 而不是报错，消费循环应把 nil 当作「本轮没有任务」继续下一轮，而不是当作异常中断。

**速记**：BLPOP/BRPOP **空则挂起**，timeout **0 即永久**，返回**键与值**。



### 列表间搬运

#### LMOVE 与安全队列

**LMOVE**：是原子地从源列表弹出元素并推入目标列表的命令，Redis 6.2 新增，是构建「安全队列」模式的核心命令。

- 语法：LMOVE source destination LEFT|RIGHT LEFT|RIGHT，第一个方向决定从源列表哪端弹出，第二个决定推入目标列表哪端。
- 阻塞版：BLMOVE source destination LEFT|RIGHT LEFT|RIGHT timeout，源列表为空时挂起等待，timeout 语义与 BLPOP 相同，0 表示永久阻塞。
- 弹出与推入整体原子：命令执行中间不会有其他客户端观察到「两边都没有」的状态。
- 安全队列模式：列表 A 存待处理任务，消费者用 LMOVE 把任务搬进列表 B（处理中），处理成功后从 B 移除，处理失败再搬回 A 重试。
- 该模式解决「弹出即丢」：普通 LPOP 弹出后客户端崩溃，消息永久丢失；安全队列中消息滞留在 B 里，可追溯、可重试。
- 源列表不存在时：LMOVE 返回 nil 且不做任何操作；BLMOVE 则进入阻塞等待，按 timeout 语义处理。
- 四个方向组合中，LEFT LEFT 与 RIGHT RIGHT 属于同端搬运，适用面较窄；RIGHT LEFT 与 LEFT RIGHT 这两种跨端组合才是队列场景的主用法。

```bash
LMOVE queue:task queue:doing LEFT RIGHT   # 取任务进处理中
LREM queue:doing 1 "job1"                 # 处理成功后移除
LMOVE queue:doing queue:task RIGHT LEFT   # 失败则退回重试
```

> destination 与 source 可以是同一个键：LMOVE key key RIGHT LEFT 会把尾部元素搬到头部，相当于旋转列表，可用来实现循环轮转；BLMOVE src dst RIGHT LEFT timeout 则完整覆盖旧命令 BRPOPLPUSH 的阻塞搬运场景。
>
> 处理中列表还应有兜底巡检：定时检查 queue:doing 中滞留过久的任务并搬回待处理，防止消费者全体掉线后任务永久卡死。

**速记**：LMOVE **原子搬运**，BLMOVE **空源阻塞**，安全队列**取出进处理中、失败可退回**。



#### RPOPLPUSH 已弃用

**RPOPLPUSH**：是从源列表尾部弹出并推入目标列表头部的旧命令，功能已被 LMOVE 的 RIGHT LEFT 组合完全取代，官方已标记弃用。

- 弃用时间：Redis 6.2 起 RPOPLPUSH 标记为 deprecated，其阻塞版 BLPOPLPUSH 同步被 BLMOVE 取代。
- 对应关系一一映射：RPOPLPUSH src dst 等价于 LMOVE src dst RIGHT LEFT；BLPOPLPUSH src dst timeout 等价于 BLMOVE src dst RIGHT LEFT timeout。
- 旧写法迁移零风险：新旧命令语义完全一致，替换后行为不变。
- 迁移检查点：全局搜索代码与运维脚本中的 RPOPLPUSH 与 BLPOPLPUSH，逐一替换为新命令。
- 弃用状态可通过命令文档与客户端库的版本说明确认，升级依赖后可借助静态检查发现存量调用。

```bash
RPOPLPUSH src dst                 # 旧写法，已弃用
LMOVE src dst RIGHT LEFT          # 新写法，等价
```

> [!NOTE]
> **提醒内容**：RPOPLPUSH 目前仍可执行，仅为兼容保留；新代码与面试答案都应使用 LMOVE 与 BLMOVE，不宜再按旧命令组织表述。

**速记**：RPOPLPUSH **已弃用**，等价写法 **LMOVE RIGHT LEFT**。



### 应用场景

#### 时间线与最新列表

**时间线与最新列表**：是 List 最经典的应用场景，用 LPUSH 写入新动态、用 LTRIM 限定长度、用 LRANGE 分页读取，即可实现朋友圈、微博时间线与最新消息列表。

- 写入：新动态产生时执行 LPUSH timeline:userId 动态 id，最新的永远在头部。
- 定长：随手执行 LTRIM timeline:userId 0 999，只保留最新 1000 条，天然防膨胀。
- 读取：首页用 LRANGE timeline:userId 0 9 取第一页，翻页改 start stop 区间即可。
- 变体：最近联系人、最近搜索词等「最新且去重」的列表，可先 LREM 删掉旧记录再 LPUSH 置顶。
- 该模式下列表长度有上界，写入是 O(1)，读取只取所需分页，整体成本可控。
- 定长窗口之外的历史数据若仍需保留，应由异步任务落库，而不是无限留在 Redis。

```bash
LPUSH timeline:1001 "post:9" "post:8"
LTRIM timeline:1001 0 999
LRANGE timeline:1001 0 9
```

```text
1) "post:9"
2) "post:8"
```

> 时间线只需要「最近一段」时，定长 List 足够；若需求升级为完整时间线、按时间排序去重或游标翻页，应改用 ZSet 或 Stream（详见第 7 章与第 9 章）。
>
> 多人读同一份聚合时间线时，可将拉取与合并结果缓存进一个 List 键，配合过期时间实现短时缓存，减少重复计算（详见第 14 章的过期删除机制）。

**速记**：时间线三件套 **LPUSH 写、LTRIM 定长、LRANGE 分页**



#### 简单消息队列与 Stream 对比

**简单消息队列**：用 List 的 LPUSH 加阻塞弹出即可搭出轻量队列——生产者一端推入，消费者一端阻塞取出，多个消费者天然分摊消息。

- 生产者：LPUSH queue:task 任务载荷，任务即一条字符串或序列化后的 JSON。
- 消费者：BRPOP queue:task 30 循环阻塞取出；多消费者并发时，每条消息只会被其中一个消费者拿到。
- 可靠性增强：消费端改用 BLMOVE 把消息搬入处理中列表，即前述安全队列模式。
- 局限一：没有消费组与确认机制，ACK 逻辑要自己在处理中列表上手工实现。
- 局限二：消息没有独立 id，没有历史保留，取出即消费，无法回看与重放。
- 局限三：没有消费者组的负载均衡记录，消费进度完全由消费者自行持有。
- 升级路径：需要确认、消费组、消息回放时改用 Stream（详见第 9 章与第 24 章）。
- 运维要点：队列长度可用 LLEN 监控，积压过多应告警并增加消费者。
- 载荷建议控制在数 KB 以内，超大实体另存、队列里只传引用 id。

```bash
LPUSH queue:order "order:1001"
BRPOP queue:order 30
```

```text
1) "queue:order"
2) "order:1001"
```

> List 队列适合吞吐不大、消息语义简单的内部场景；一旦需要 ACK、消费组或断线续读，自行拼装的成本会超过直接用 Stream，不要为了少用一个类型硬扛。
>
> 发布订阅与消息队列的选型还涉及订阅模式与持久化诉求的权衡，详见第 24 章；本节只覆盖 List 能力边界内的队列形态。

**速记**：List 队列 **LPUSH 加 BRPOP**，要 **ACK 与回放就上 Stream**。



### 内部编码 quicklist

#### quicklist 的结构演进

**quicklist**：是 List 类型的底层内部编码，自 Redis 3.2 起成为 List 的默认编码，本质是「由多个紧凑存储节点串成的双向链表」。

- 3.2 起：quicklist 取代此前 ziplist 与 linkedlist 的双编码方案，成为 List 唯一默认编码。
- 7.0 起：quicklist 的节点从 ziplist 换成 listpack，修复了 ziplist 级联更新的缺陷。
- 结构要点：外层是双向链表，每个节点是一小块 ziplist 或 listpack，兼顾链表的插删效率与紧凑结构的内存效率。
- 成本分布：头尾操作只触碰两端节点，复杂度 O(1)；中间定位需跨节点累计，为 O(N)。
- 查看方式：OBJECT ENCODING key 对 List 的返回值即 quicklist。
- 设计动机：纯链表指针开销大，纯紧凑结构在长列表上连锁更新代价高，quicklist 以「分块」折中两者。
- 编码名不随节点类型变化：无论节点是 ziplist 还是 listpack，OBJECT ENCODING 的返回值都是 quicklist。

```bash
RPUSH demo "x"
OBJECT ENCODING demo
```

```text
quicklist
```

> quicklist 的节点规模由 list-max-listpack-size 控制，中间节点压缩深度由 list-compress-depth 控制；链表与压缩列表、listpack 的内部结构详见第 10 章与第 12 章。
>
> 版本演进的全景与 Redis 7 的其他新特性详见第 32 章。
>
> 编码细节不影响命令语义：无论节点如何组织，本章所有命令的对外行为与复杂度结论一致，业务代码无需感知内部编码变化。

**速记**：quicklist＝**链表串紧凑节点**，**3.2 上位**，**7.0 节点换 listpack**。



### 常见误用

#### LRANGE 拉全量的陷阱

**LRANGE 拉全量**：指对大列表不加节制地执行 LRANGE key 0 -1，一次把全部元素经由网络传到客户端，是 List 最常见的线上误用。

- 危害一：元素多时返回体巨大，占用大量网络带宽与客户端内存，单次命令耗时随列表长度线性增长。
- 危害二：Redis 执行命令与序列化回复都在主线程完成，巨大回复会拖慢同一实例上的其他请求，放大延迟毛刺。
- 危害三：客户端侧还要为巨大数组分配内存，容易触发应用层 GC 抖动甚至进程崩溃。
- 典型失控键：只追加不裁剪的接口日志、爬虫结果集、实时大盘明细，都属于「无界写、偶发全量读」的高危组合。
- 正确做法一：只读需要的一段，分页场景用 LRANGE key start stop 定区间。
- 正确做法二：配合 LTRIM 把列表限定为定长，从源头保证即使 0 -1 也不至于失控。
- 正确做法三：确需全量导出时改用游标类方案或离线任务，避开业务高峰。

```bash
# 反例：日志列表无限增长后拉全量
LRANGE app:log 0 -1
# 正解：定长 + 分页读取
LTRIM app:log 0 4999
LRANGE app:log 0 99
```

> [!WARNING]
> **警告内容**：把 List 当无限增长的日志容器用（只写不裁剪）会让键无限膨胀，直至触发内存淘汰或内存耗尽；任何「只追加」的 List 都必须有 LTRIM 或过期时间兜底，二者至少居其一。
>
> 与之相关的大键治理、慢查询定位手段，属于性能优化的通用议题，详见第 29 章；本节结论先行：定长化是 List 防大键的第一道防线。

**速记**：大列表**禁 0 -1 拉全量**，**LTRIM 定长加分页**才是正解。
