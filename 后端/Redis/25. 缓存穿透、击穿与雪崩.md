## 缓存穿透、击穿与雪崩

**缓存是数据库的护城河**：本章讨论护城河失效的三种典型故障——**缓存穿透**、**缓存击穿**与**缓存雪崩**。三者都发生在「未命中回源」这条路径上，都会把读压力转移给数据库，但成因与对策各不相同，是缓存设计面试与生产事故复盘中的高频考点。学完本章应能准确定义三者、说清对策原理并写出防护骨架代码。

### 缓存读写模型回顾

读写模型是理解三类问题的地基，先复习旁路缓存模式的标准读路径，再定位三类问题发生在哪一步。

#### 旁路缓存的基本读写流程

**旁路缓存（Cache Aside）**：应用代码自己维护缓存，读请求**先查缓存**，未命中再查数据库并回填，是 Redis 最常用的读写模式，与缓存一致性策略的衔接详见第 26 章。

- **读路径**：先查缓存，命中则直接返回，流程结束。
- **未命中分支**：查询数据库，把结果写回缓存并设置 TTL，再返回结果。
- **写路径**：先更新数据库，再删除对应缓存而非更新缓存，理由详见第 26 章。
- **回填成本**：一次数据库查询加一次缓存写入，正常情况下只有少数请求需要支付。
- **理想状态**：绝大部分请求在缓存层结束，数据库只承接少量未命中流量。
- **回填 TTL**：回填时必须设置过期时间，不设 TTL 的回填会让废弃数据永久驻留，也为集体过期埋下隐患。
- **失效主动权**：缓存内容是否新鲜，取决于回填时机与写路径的删除策略，而非缓存自身。

```js
// 旁路缓存读路径骨架
async function readThroughCache(key) {
  const cached = await redis.get(key);
  if (cached !== null) return JSON.parse(cached); // 命中：直接返回

  const dbData = await loadFromDb(key);           // 未命中：回源
  if (dbData === null) return null;               // 空结果的处理见穿透一节
  await redis.set(key, JSON.stringify(dbData), "EX", BASE_TTL_SECONDS);
  return dbData;                                  // 回填后返回
}
```

> 三类缓存故障全部发生在**未命中分支**：穿透让该分支对每个请求都成立，击穿让该分支在同一瞬间集中爆发，雪崩让该分支对绝大多数请求同时成立。看懂这一句，三类问题就有了统一的坐标系。

**速记**：**先查缓存，未命中回源回填**，三类问题都长在这条回源分支上。



### 缓存穿透

穿透的共性是**查询的数据不存在**，缓存无法发挥拦截作用，重点掌握三种对策的适用边界。

#### 穿透的定义与特征

**缓存穿透**：查询**根本不存在的数据**，缓存与数据库中都没有记录，导致每次请求都绕过缓存、直接打到数据库的现象。

- **数据不存在**：数据库查不到结果，回填无从谈起，缓存条目永远建立不起来。
- **请求必达数据库**：不存在缓存拦截层，这类请求的缓存穿透率是百分之百。
- **典型来源**：恶意攻击者用伪造 id 扫描接口、爬虫抓取、业务缺陷传参（负数、超大整数、已删除的 id）。
- **放大效应**：同一批非法 key 被高频重复请求时，数据库压力成倍放大。
- **危害定性**：穿透流量绕过了缓存设计的全部前提，等于让数据库直接面对终端流量。
- **隐蔽性强**：应用层响应正常、缓存命中率看似平稳，往往等到数据库告警才被发现。
- **成本不对称**：攻击者构造一个不存在的 key 成本极低，数据库却要为每一次请求全额支付查询成本。

> 辨析：穿透的关键特征是「数据不存在」，而不是「缓存过期」。若数据库中有数据、只是缓存恰好过期，一次回源后即可回填，属于正常未命中；只有连数据库也查不到、缓存永远无法回填时，才构成穿透。

> 判定方法：抓一个可疑 key 分别查缓存与数据库，两者都为空即可定性；再回溯请求日志确认是重复扫描还是一次性脏请求，据此决定启用哪一层对策。

**速记**：穿透就是**查不存在的数据**，缓存与数据库双双落空。



#### 缓存空值对策

**缓存空值**：数据库查询结果为空时，仍向缓存写入一个**空占位值**并配**短 TTL**，让后续同 key 的请求在缓存层就被拦截。

- **写入约定**：占位值可用固定标记字符串（如 NULL_FLAG）或空对象序列化结果，必须与真实数据明确区分。
- **短 TTL**：占位存活时间通常为几十秒到几分钟，到期后自动清理。
- **返回处理**：读到占位值的应用层直接返回空结果，不再回源。
- **生效逻辑**：同一个非法 key 在 TTL 窗口内无论被请求多少次，都只回源一次。
- **创建时清理**：数据随后真的被创建时要主动删除占位值，让新数据立即可见。
- **批量查询注意**：批量接口中部分 key 命中占位时，只回填存在的部分，不要把整批结果写进缓存。

```js
// 未命中且数据库也查不到时，写入空占位并配短 TTL
const NULL_FLAG = "__NULL__";
const NULL_TTL_SECONDS = 60;

async function cacheNullPlaceholder(key) {
  await redis.set(key, NULL_FLAG, "EX", NULL_TTL_SECONDS);
}
```

> [!WARNING]
> **警告内容**：空值占位是防护强度与一致性的折中。**TTL 过长**会让「数据随后真的被创建」的请求长时间读到空结果，造成一致性事故；**TTL 过短**则拦截窗口太窄、防护效果弱。折中做法是保持较短 TTL，同时在数据创建或更新时主动删除占位值，一致性问题详见第 26 章。

> 适用边界：空值方案适合**非法 key 数量有限**且会被反复查询的场景。若攻击者每次构造不同的随机 key，大量占位值反而污染缓存空间、挤占有效数据的内存（内存淘汰机制详见第 15 章），此时应改用布隆过滤器。

> 组合使用：空值方案实现成本最低，适合作为兜底的第一道防线；与布隆过滤器组合时，空值负责拦截漏网的误判请求，两层过滤可把穿透压到接近零。

**速记**：查不到也**写个短命占位**，把穿透请求挡在缓存层。



#### 布隆过滤器对策

**布隆过滤器（Bloom Filter）**：用**位数组加多个哈希函数**把全部合法 key 的指纹预先登记，置于缓存之前，对「一定不存在的 key」直接拦截，从源头消灭穿透。

- **写入阶段**：把每个合法 key 用 k 个哈希函数算出 k 个下标，将位数组对应位置全部置 1。
- **查询阶段**：对待查 key 计算同样的 k 个下标，只要**有一位是 0**，判定一定不存在，直接返回，不再查缓存与数据库。
- **判定性质**：全部为 1 时只能判定「**可能存在**」，仍需放行走正常读流程。
- **误判率**：位数组越长、哈希函数越多，误判率越低，代价是内存与计算开销。
- **删除困难**：多个 key 共享同一批位，标准布隆过滤器**无法单独删除**某个 key，需要删除能力时改用计数布隆过滤器或布谷鸟过滤器。
- **工程载体**：Redis 4.0 以上可加载 RedisBloom 模块获得原生命令支持。
- **部署位置**：置于缓存查询之前，业务读请求先问过滤器，再走缓存与数据库的正常流程。
- **空间效率**：位数组只存指纹不存原文，上亿规模的 key 用数百 MB 内存即可容纳。
- **初始化代价**：全量登记需遍历合法 key 集合，数据量越大启动加载越慢，可拆分为增量构建加后台重建。

```bash
# RedisBloom 模块提供原生命令
BF.ADD legal_user_ids 1001
BF.EXISTS legal_user_ids 99999
```

```js
// 布隆过滤器判定骨架（示意）
function mayExist(bloom, key) {
  for (const seed of HASH_SEEDS) {
    const pos = hash(key, seed) % BIT_ARRAY_SIZE;
    if (!bitGet(bloom, pos)) return false; // 有一位为 0：一定不存在
  }
  return true; // 全为 1：可能存在，放行走正常读流程
}
```

> 维护要点：过滤器必须**先于流量存在**——服务启动时全量加载合法 key，数据新增时增量写入；删除语义受限，要靠定期全量重建兜底。被误判放行的少数请求仍会走到数据库，属于可接受的残余穿透。

> 参数估算：误判率与位数组大小、哈希个数、已登记 key 数量共同决定。创建前应按预期 key 量与目标误判率估算参数再申请内存，避免运行期频繁扩容重建。

**速记**：布隆过滤器说「**一定没有**就真没有」，说「可能有」才放行。



#### 参数校验与风控限流对策

**接口层防护**：对非法参数在请求进入缓存与数据库之前直接拒绝，把穿透流量消灭在最外层。

- **参数合法性校验**：校验 id 范围、格式正则、枚举白名单，非法取值直接返回错误。
- **鉴权与登录态校验**：未通过身份校验的请求不进入业务查询链路。
- **风控规则**：同一 IP 或用户在短时间内高频访问大量不同 key，判定为扫描行为并封禁。
- **限流**：对可疑接口设置单机或网关层限流，超出阈值的请求直接拒绝。
- **防护定位**：这一层是通用防线，不仅防穿透，对爬虫、刷接口等恶意流量同样有效。
- **实现位置**：网关中间件、框架统一校验层或参数校验装饰器，业务代码零侵入。
- **失败响应**：非法请求统一返回参数错误码，不触发任何下游查询。

```js
// 参数合法性校验示例：非法取值在进入查询前直接拒绝
const USER_ID_PATTERN = /^\d{1,10}$/;

function validateUserId(userId) {
  if (!USER_ID_PATTERN.test(userId)) {
    // 负数、超长、非数字取值均在门口拦截
    throw new BadRequestError("非法的用户 id");
  }
  return true;
}
```

> 场景说明：业务缺陷产生的异常 key（如上游传参错误）靠校验规则就能兜住；蓄意构造的扫描攻击则要靠风控与限流联动。接口层防护与缓存层对策（空值、布隆过滤器）是互补关系，生产上通常叠加使用。

**速记**：**非法请求在门外拒掉**，别让它消耗缓存与数据库。



### 缓存击穿

击穿是**单个热点 key 过期瞬间**的并发风暴，与穿透以「数据是否存在」为本质区别，两大主流对策是互斥锁与逻辑过期。

#### 击穿的定义与特征

**缓存击穿**：**单个热点 key** 在缓存过期失效的瞬间，海量并发请求同时未命中、一齐回源数据库，瞬时把数据库压垮的现象。

- **前提一：热点**：key 的访问频率极高，单位时间并发量大。
- **前提二：过期**：key 设置了 TTL，存在确定的失效时刻。
- **触发点**：过期瞬间的**同时并发**，成百上千个请求在同一毫秒级窗口内一起未命中。
- **与穿透的区别**：击穿的数据**真实存在**，回源一次就能回填；穿透的数据不存在，回填永远不成立。
- **与雪崩的区别**：击穿的范围是**一个 key**，雪崩的范围是大量 key 或整个缓存服务。
- **危害形态**：数据库连接池瞬间占满、响应超时，上游服务连锁堆积，表现酷似数据库自身故障。
- **可预见性**：热点 key 的访问量与 TTL 均可观测，击穿是可以提前评估与预防的故障。

> 「热点、过期、高并发」三要素齐备才构成击穿：不热的 key 过期只是普通未命中；热 key 不设过期则没有触发点；并发量小则回源一次也无伤大雅。三者缺一，风暴都不会发生。

> 场景画像：秒杀商品详情、爆款内容、首页轮播这类 key 是击穿高发对象。评估时先盘出访问量 Top 的 key 名单，再逐个检查其 TTL 设置与并发量级。

**速记**：击穿就是**一个热 key 过期**，瞬间全员回源。



#### 互斥锁单飞重建

**互斥锁重建**：缓存未命中后先抢一把分布式锁，**只放一个线程回源重建缓存**（单飞），其余线程等待重试读缓存，从机制上禁止并发回源。

- **抢锁**：用 set 命令的 nx 与 ex 选项原子加锁，分布式锁的完整用法详见第 27 章。
- **双检**：抢到锁后**先再查一次缓存**，确认确实未命中才回源数据库——排队期间缓存可能已被上一轮持锁线程重建完成，跳过双检会造成重复回源。
- **单飞重建**：双检确认缺失后，抢到锁的线程查询数据库、回填缓存，然后释放锁。
- **等待重试**：未抢到锁的线程休眠几十毫秒后重读缓存，通常此时缓存已重建完成。
- **锁必须带过期时间**：防止持锁线程崩溃后锁永不释放造成死锁。
- **保证效果**：一次失效窗口内数据库最多被回源一次。
- **锁粒度**：锁的 key 一般与缓存 key 一一对应，不同 key 的重建互不干扰。
- **等待策略**：等待线程以短暂休眠加轮询的方式重读缓存，休眠时长通常为几十毫秒。

```bash
# 原子加锁：nx 保证只有一个客户端成功，ex 保证锁自动过期
SET lock:hot:key 1 NX EX 10
```

> [!CAUTION]
> **注意内容**：互斥锁方案有三个常见坑：一是**重建耗时超过锁 TTL**，锁先于重建完成而过期，其他线程可能重复回源，需评估重建耗时或引入锁续期；二是**持锁线程崩溃**，依赖 ex 自动过期兜底，锁 TTL 不能设得过大；三是**等待线程堆积**，重试次数要有上限并配合超时降级，否则等待队列本身会拖垮应用进程。

> 适用性：互斥锁保证**强一致**的回源次数，代价是部分线程阻塞等待；适合一致性要求高、并发量可控的场景。读多写多的极端热点场景可改用逻辑过期方案。

> 变体取舍：等待重试也可以换成「先返回空值或默认值」，减少线程堆积但牺牲一次响应的完整性；两种变体按业务对响应完整性的要求选择。

**速记**：**一把锁放一个线程回源**，其余线程等待读缓存。



#### 逻辑过期与永不物理过期

**逻辑过期**：缓存 key 物理上**永不设置 TTL**，改为在 value 内嵌一个逻辑过期时间字段；读到逻辑过期的数据后由**异步线程重建**，读请求全程不被阻塞。

- **存储结构**：value 为 JSON，同时包含 data（业务数据）与 expire（逻辑过期时间戳）两个字段。
- **读取判断**：当前时间未到 expire，直接返回 data，性能与普通命中无异。
- **过期处理**：抢互斥锁，抢到的线程开启**异步任务**重建缓存后释放锁，当前线程**先返回旧数据**；没抢到的线程同样直接返回旧数据。
- **永不物理过期**：key 不设 TTL，因此不存在「过期瞬间的并发未命中」，击穿的触发点被整体消除。
- **无阻塞特性**：所有读请求都不等待重建完成，响应时间稳定。
- **失效自动续期**：重建会把逻辑过期时间向后推移一轮，数据持续保鲜。

```js
// 逻辑过期：写入与读取骨架
const LOGICAL_TTL_SECONDS = 300;

// 写入：value 内嵌逻辑过期时间，不设物理 TTL
async function wrapWithLogicalExpire(key, data) {
  const payload = {
    data: data,
    expire: Date.now() + LOGICAL_TTL_SECONDS * 1000
  };
  await redis.set(key, JSON.stringify(payload));
}

// 读取：逻辑过期触发异步重建，读请求永不阻塞
async function readWithLogicalExpire(key) {
  const cached = await redis.get(key);
  if (cached === null) return null; // 未预热，返回空或走兜底
  const payload = JSON.parse(cached);

  if (Date.now() < payload.expire) {
    return payload.data; // 未逻辑过期：直接返回
  }

  // 已逻辑过期：抢锁成功的线程触发异步重建
  const lockKey = "lock:" + key;
  const locked = await redis.set(lockKey, "1", "EX", 10, "NX");
  if (locked) {
    rebuildCacheAsync(key); // 异步执行，不等待完成
  }
  return payload.data; // 无论是否抢到锁：先返回旧数据
}

// 异步重建：查询最新数据后覆盖回写并释放锁
async function rebuildCacheAsync(key) {
  try {
    const freshData = await loadFromDb(key);
    await wrapWithLogicalExpire(key, freshData);
  } finally {
    await redis.del("lock:" + key);
  }
}
```

> [!CAUTION]
> **注意内容**：逻辑过期用**短暂返回旧数据**换来了读请求零阻塞——重建完成前的窗口内，所有请求拿到的都是上一版数据。对行情、秒杀库存等强一致业务不可接受；对首页推荐、商品详情等容忍秒级延迟的业务则是理想选择。

> 配套要求：方案需要**后台重建任务**与**热点预热**支撑——上线时主动加载热 key，否则冷启动阶段 value 缺失，方案无从生效；重建任务要有失败重试与监控。

**速记**：**物理不过期、逻辑判新旧**，过期了异步重建、先返回旧数据。



### 缓存雪崩

雪崩是**大面积缓存同时失效**的系统性故障，对策从「打散过期时间」到「高可用架构」再到「数据库自我保护」层层设防。

#### 雪崩的定义与两种成因

**缓存雪崩**：**大量 key 在同一时刻集中过期**，或 **Redis 服务整体不可用**，导致海量请求同时回源、把数据库压垮甚至引发连锁故障的现象。

- **成因一：集体过期**：批量写入的 key 使用相同 TTL，到期集体失效，回源请求瞬间叠加。
- **成因二：整体不可用**：Redis 实例宕机、主从切换抖动、机房或网络故障，缓存服务整体消失。
- **与击穿的区别**：击穿是**一个热点 key**，雪崩是**一大片 key 或整个缓存服务**。
- **连锁后果**：数据库瞬时超载变慢，上游线程堆积，请求超时重试进一步放大流量，最终形成全链路故障。
- **冷启动问题**：缓存重启后内容为空，若不做预热，重启本身就是一次雪崩。
- **时机特征**：集体过期型雪崩常在整点、定时任务周期边界等固定时刻爆发，可从监控曲线上看出周期性。

> 雪崩是三类问题中**破坏面最大**的一种：穿透与击穿尚可靠单点对策解决，雪崩必须依赖架构层的组合拳，且要为缓存重启后的冷启动预留预热手段。

> 经验判断：若数据库压力曲线与某批 key 的过期时刻完全吻合，即为集体过期型雪崩；若无对应关系且伴随 Redis 告警，则指向整体不可用型。两条线索对应完全不同的处置路径。

**速记**：雪崩就是**一大片缓存同时失效**，数据库独木难支。



#### 过期时间随机抖动

**过期时间抖动**：在基础 TTL 上叠加一个**随机增量**，把同一批 key 的过期时刻打散到一个时间区间内，避免集体失效。

- **公式**：实际 TTL 等于基础 TTL 加上 0 到抖动幅度之间的随机值。
- **适用对象**：批量导入、定时任务统一写入的缓存是抖动的重点对象。
- **幅度选取**：按业务对过期精度的敏感度选取，通常取基础 TTL 的一成到两成。
- **实现位置**：写在统一的缓存写入工具方法里，业务方无感知，避免遗漏。
- **存量治理**：发现同批 key 共用相同 TTL 的存量数据，要随刷新逐步替换为抖动后的值。

```js
// 统一写入入口：基础 TTL 加随机抖动
const JITTER_MAX_SECONDS = 600;

function buildTtl(baseSeconds) {
  return baseSeconds + Math.floor(Math.random() * JITTER_MAX_SECONDS);
}
```

> 边界说明：抖动只解决「集体过期」这一种成因；对 Redis 整体宕机无能为力，必须与高可用架构配合（见下文）。对过期精度要求极高的业务（如秒杀资格瞬间生效）要控制抖动幅度或单独豁免。

> 验证手段：把同批 key 的 TTL 拉出来看分布，若集中于同一时刻就是隐患；打散后分布应均匀覆盖整个抖动区间。

**速记**：**TTL 加随机数**，让过期时刻错峰。



#### 热点数据永不过期与后台刷新

**热点永不过期**：对极少数核心热点数据不设物理 TTL，由**后台定时任务主动刷新**或由写路径在数据变更时同步更新，让它们不参与「过期失效」这件事。

- **实现一**：物理不过期加逻辑过期，交给异步重建，实现细节见击穿对策。
- **实现二**：后台定时任务按固定周期全量刷新这批 key，覆盖数据变更。
- **实现三**：写路径更新数据库后同步更新缓存，一致性与更新顺序详见第 26 章。
- **适用范围**：只对**少数核心数据**启用，如首页配置、秒杀商品、白名单。
- **收益**：这类数据永远不会出现「过期瞬间的击穿」与「集体过期的雪崩」。
- **刷新频率**：定时任务的周期按数据可容忍的陈旧度选取，分钟级到小时级不等。

```js
// 后台定时刷新热点 key（示意）
const HOT_KEYS = ["home:config", "seckill:items"];

async function refreshHotKeys() {
  for (const key of HOT_KEYS) {
    const freshData = await loadFromDb(key);
    // 物理不过期：仅覆盖内容，不设置 TTL
    await redis.set(key, JSON.stringify(freshData));
  }
}
```

> [!TIP]
> **建议内容**：热点数据建议配合**大促前预热**执行——活动开始前把预估热 key 批量加载进缓存并刷上随机 TTL，同时启动后台刷新任务，把「过期」与「冷启动」两个风险点提前消除。

> 成本提示：永不过期意味着数据常驻内存，核心热 key 通常体量有限、可以接受；若不加甄别地大范围使用，会挤占内存并干扰淘汰策略的判断（详见第 15 章）。

**速记**：**核心热点不过期**，后台刷新来保鲜。



#### Redis 高可用与 DB 层防护

**高可用加自我保护**：针对「Redis 整体不可用」这一成因，缓存侧要构建高可用架构，数据库侧要有限流熔断的兜底能力，两头同时设防。

- **缓存高可用**：主从复制加哨兵自动故障转移（详见第 21 章），或 Cluster 分片集群（详见第 22 章），单点故障不再导致缓存整体消失。
- **DB 限流**：对回源请求设置阈值，超出部分排队或拒绝，保住数据库的核心水位。
- **熔断降级**：数据库错误率超阈值时暂时熔断回源，返回默认值、旧数据或友好提示。
- **服务多实例**：应用层多实例部署，避免单实例故障放大回源流量。
- **预案联动**：限流熔断开关要支持运行时调整，故障时能快速生效。
- **容量冗余**：集群按峰值流量预留冗余，主从切换期间剩余节点要接得住全部读流量。

> [!IMPORTANT]
> **重要内容**：限流熔断降级是**最后的防线**——当穿透、击穿、雪崩的预防手段全部失效时，宁可让部分用户拿到降级数据，也不能让数据库被打死。数据库一旦崩溃，恢复时间远长于缓存，且会拖垮依赖它的全部服务。

> 架构顺序建议：先保证缓存高可用以降低雪崩概率，再部署限流熔断兜住残余风险，顺序不能颠倒——只有限流而没有高可用，缓存故障照样把服务打瘫。

**速记**：缓存**高可用防宕机**，数据库**限流熔断保命**。



#### 多级缓存体系

**多级缓存**：在 Redis 之前再加一层**进程内本地缓存**，形成本地缓存、Redis、数据库的逐级过滤结构，任何一级失效都还有上一级顶住。

- **第一级：本地缓存**：应用进程内存中的缓存，访问零网络开销，Node 中可用 Map 自建或成熟缓存库实现。
- **第二级：分布式缓存**：Redis 集群，承载跨实例共享的热数据。
- **兜底层：数据库**：仅承接前两级都未命中的少量请求。
- **一致性代价**：本地缓存分散在各实例，失效需借助广播通知或短 TTL 自愈，整体一致性问题详见第 26 章。
- **容量取舍**：本地缓存容量受单进程内存限制，只放最热的少量数据。
- **失效策略**：本地缓存 TTL 通常更短，宁可多回查一次 Redis 也不要 stale 太久。

```js
// 两级缓存读取骨架（示意）
const LOCAL_TTL_MS = 5000;
let localCache = new Map(); // 键为 key，值为 { data, expire }

async function readWithTwoLevels(key) {
  const local = localCache.get(key);
  if (local && Date.now() < local.expire) {
    return local.data; // 第一级：本地缓存命中
  }

  const cached = await redis.get(key); // 第二级：回查 Redis
  if (cached === null) return loadFromDb(key); // 兜底：回源数据库
  const data = JSON.parse(cached);
  localCache.set(key, { data: data, expire: Date.now() + LOCAL_TTL_MS });
  return data;
}
```

> 多级缓存的价值在雪崩场景尤为明显：即便 Redis 整体不可用，本地缓存仍能守住一部分读流量，为数据库挡住第一波冲击；但层级越多，排查一致性问题的复杂度也越高。

**速记**：**本地顶一层，Redis 顶一层**，层层过滤护住数据库。



### 三类问题的本质区别

用「数据存在性」与「故障范围」两个维度可以把三者一刀切开，这是面试与事故复盘时最先要回答的问题。

#### 穿透击穿雪崩的对照辨析

**本质区别**：三者以**故障数据的范围**为分界——穿透查的是**不存在的数据**，击穿是**单个热点 key 失效**，雪崩是**大面积 key 失效或缓存整体不可用**。

- **穿透**：数据在缓存与数据库中都不存在，任何请求都回源，范围是**任意 key**，成因多为攻击或脏请求。
- **击穿**：数据存在且为热点，仅在过期瞬间集中回源，范围是**一个 key**，成因是热点、过期、高并发三者叠加。
- **雪崩**：范围是**大量 key 或整个缓存服务**，成因是集体过期或整体宕机，破坏面最大。
- **对策分野**：穿透靠空值与布隆过滤器前置拦截；击穿靠互斥锁与逻辑过期控制并发回源；雪崩靠抖动、高可用与限流熔断体系化设防。
- **排查视角**：先确认数据是否存在定穿透，再按范围是一个还是一片定击穿或雪崩，两个问题答完对策即确定。

> 对照记忆：穿透是「**查没有的**」——问题在数据本身不存在；击穿是「**热的一个**」——问题在过期瞬间的并发；雪崩是「**倒了一片**」——问题在规模。
> 定位步骤：先问数据存不存在、定是不是穿透，再问范围是一个还是一片、定击穿或雪崩，两问之后对策自然浮出水面。

**速记**：**穿透没有、击穿一个、雪崩一片**。



#### 与缓存污染、缓存颠簸的辨析

**缓存污染与缓存颠簸**：是与三类故障同域但性质不同的两个概念——污染指**无价值数据大量占据缓存空间**，颠簸指**数据在缓存与数据库之间高频来回搬运**，二者是缓存自身效率的慢性劣化，与三类突发回源风暴构成一组易混概念。

- **缓存污染**：一次访问后不再（或极少）再次访问的数据被大量载入缓存并长期驻留，挤占有效数据的内存、拉低整体命中率；典型成因是全表扫描式的批量读取把冷数据灌进缓存。
- **缓存颠簸**：在容量受限的缓存里，数据刚被淘汰又立刻被访问、刚回填又再次被淘汰，在缓存与数据库之间反复搬运，命中率剧烈波动；颠簸一词描述的正是这种来回折腾的状态。
- **与穿透的区别**：穿透查询的是缓存与数据库都**没有**的数据；污染与颠簸里的数据**真实存在**，问题出在缓存空间管理而非数据缺失。
- **与击穿、雪崩的区别**：击穿与雪崩是过期或宕机引发的**瞬时回源风暴**，有明确的爆发时刻；污染与颠簸是**持续性、渐进性**的命中率劣化，不会在某一瞬间把数据库打垮。
- **关联机制**：内存淘汰策略是污染与颠簸的直接战场——淘汰算法对访问模式不敏感时污染加剧、颠簸频发，策略细节详见第 15 章。
- **治理方向**：污染靠设置合理 TTL、隔离冷热数据、选用抗污染的淘汰算法；颠簸靠扩大缓存容量、调整淘汰策略、梳理批量访问的接入方式。

> 观察入口不同是区分二者的钥匙：三类故障先看**数据库水位告警与回源 QPS 尖峰**，污染与颠簸先看**命中率曲线长期走低**；一个看瞬时值，一个看趋势线。

**速记**：穿透击穿雪崩是**突发回源风暴**，污染颠簸是**慢性命中率劣化**。



### 伪代码：互斥锁重建

把击穿的互斥锁对策与穿透的空值对策合并到一个查询函数里，形成生产中常见的防护骨架。

#### 完整防护查询的伪代码

**防护查询骨架**：一个函数同时处理「空值拦截」与「单飞重建」两个动作，未命中后先抢锁、再回源、失败则重试。

```js
// 防穿透与防击穿合一的查询函数（伪代码）
const NULL_FLAG = "__NULL__";
const NULL_TTL_SECONDS = 60;
const BASE_TTL_SECONDS = 1800;
const JITTER_MAX_SECONDS = 600;
const LOCK_KEY_PREFIX = "lock:";
const LOCK_TTL_SECONDS = 10;
const RETRY_INTERVAL_MS = 50;
const MAX_RETRY_TIMES = 20;

// 带防护的缓存查询
async function queryCacheWithProtect(key) {
  const cached = await redis.get(key);
  if (cached !== null) {
    // 命中空值占位：直接返回空，拦截穿透
    if (cached === NULL_FLAG) return null;
    return JSON.parse(cached);
  }

  // 未命中：尝试抢互斥锁，单飞重建
  const lockKey = LOCK_KEY_PREFIX + key;
  const lockOwner = randomOwnerToken();
  const locked = await redis.set(
    lockKey, lockOwner, "EX", LOCK_TTL_SECONDS, "NX"
  );
  if (locked) {
    try {
      // 双检：抢到锁后再查一次缓存，可能已被上一轮持锁线程重建
      const rechecked = await redis.get(key);
      if (rechecked !== null) {
        return rechecked === NULL_FLAG ? null : JSON.parse(rechecked);
      }
      const dbData = await loadFromDb(key);
      if (dbData === null) {
        // 数据库也为空：写入短 TTL 占位，防穿透
        await redis.set(key, NULL_FLAG, "EX", NULL_TTL_SECONDS);
        return null;
      }
      // 正常回填：TTL 加随机抖动，防雪崩
      const ttl = BASE_TTL_SECONDS + Math.floor(Math.random() * JITTER_MAX_SECONDS);
      await redis.set(key, JSON.stringify(dbData), "EX", ttl);
      return dbData;
    } finally {
      // 校验锁持有者后再释放，避免误删他人的锁，详见第 27 章
      await releaseLock(lockKey, lockOwner);
    }
  }

  // 未抢到锁：短暂休眠后重试
  await sleep(RETRY_INTERVAL_MS);
  return queryCacheWithProtect(key);
}
```

> 实现细节提示：上述递归重试仅为表达流程，生产代码应写成循环并校验 MAX_RETRY_TIMES；释放锁必须先比对锁值再删除；sleep 可用定时器 Promise 封装；重建逻辑还应叠加错误处理，数据库异常时返回降级结果而不是抛错。

```js
// 配套工具函数骨架（伪代码）
function randomOwnerToken() {
  return String(Date.now()) + Math.random().toString(36).slice(2);
}

function sleep(milliseconds) {
  return new Promise((resolve) => setTimeout(resolve, milliseconds));
}

async function releaseLock(lockKey, owner) {
  const current = await redis.get(lockKey);
  if (current === owner) {
    // 先比对持有者再删除，避免释放他人的锁
    await redis.del(lockKey);
  }
}
```

**速记**：**先查、再锁、后回源**，空值与抖动顺手一起防。



### 监控与应急预案

代码防线之外，可观测性与预案决定故障能不能被及时发现与控制。

#### 监控指标与事故预案

**监控与预案**：缓存防护体系需要持续观测**命中率类指标**并预备成套预案，故障前兆往往先体现在指标曲线上。

- **命中率指标**：缓存命中率、未命中 QPS、回源 QPS 三条曲线，命中率骤降是雪崩与大面积穿透的共同前兆。
- **DB 水位指标**：连接池占用、慢查询数量与数据库 CPU，回源风暴最先在这里显形（慢查询排查详见第 29 章）。
- **缓存侧指标**：大 key、热点 key、内存占用与淘汰计数（详见第 15 章）。
- **预案清单**：大促前预热热点数据、提前打散 TTL、准备限流熔断开关、演练缓存宕机切换。
- **演练验证**：定期做故障注入，确认降级与重试逻辑真实生效，而不是停留在纸面。
- **告警阈值**：命中率低于历史基线一定比例、回源 QPS 超过容量水位时触发分级告警。
- **容量指标**：Redis 内存使用率与碎片率、连接数，提前发现容量型风险。

> 命中率曲线的典型异常：断崖式下跌对应集体过期或缓存宕机，缓慢爬坡后仍长期低位徘徊对应穿透流量；先看曲线形态再定位成因，能大幅缩短排查时间。

```js
// 命中率统计骨架：按窗口累计命中与未命中次数
const stats = { hit: 0, miss: 0 };

function recordHit(isHit) {
  if (isHit) stats.hit += 1;
  else stats.miss += 1;
}

function currentHitRate() {
  const total = stats.hit + stats.miss;
  return total === 0 ? 1 : stats.hit / total; // 无请求时视作满命中
}
```

**速记**：盯住**命中率曲线**，预案要**提前演练**而不是临场发明。
