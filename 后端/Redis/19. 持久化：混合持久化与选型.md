## 持久化：混合持久化与选型

### 混合持久化的认识

#### 混合持久化的定义与由来

**混合持久化**：指 AOF 重写时先用 RDB 二进制格式记录重写瞬间的全量数据、之后的增量写命令再以 AOF 文本命令追加到文件尾部的持久化组织方式，由配置项 aof-use-rdb-preamble 控制。

- 引入版本为 **Redis 4.0**，引入时默认值为 no（当时官方配置注释写明默认关闭是为了避免格式变化带来的意外，源码宏取值为 0）；**Redis 5.0** 起默认值改为 yes 并沿用至今，混合模式成为官方默认形态。
- 重写产物分两段：前段是重写那一刻的**全量快照**，按 RDB 二进制编码；后段是重写完成后发生的**增量写命令**，按标准 AOF 文本编码。
- 混合模式改造的对象是 **AOF 重写产物**，并非与 RDB、AOF 并列的第三种持久化机制：文件的写入、追加、重写、加载全流程仍由 AOF 机制统一管理。
- 配置支持运行期修改：CONFIG SET 即时生效，但改变只影响**下一次重写**产物的格式，不会立刻改写现有文件。
- 加载端对格式**自动识别**：无论当前开关如何设置，载入时按文件实际开头的魔数判断格式，混合文件与纯文本文件都能正常读取。
- 它解决的是一对具体矛盾：纯 AOF 恢复慢，纯 RDB 丢失多；混合把快照与命令流按时间段拼接，**快照管历史、命令流管当下**。
- 开启混合不影响既有 RDB 机制，save 条件、BGSAVE 与混合持久化相互独立，可以同时存在。
- 混合随 AOF 一起生效：appendonly 关闭时整个 AOF 体系停止，混合自然不参与。
- 增量段的落盘节奏沿用第 18 章的缓冲与 fsync 机制，本章不再展开。

从演进视角看，混合模式是对**恢复路径**的优化：4.0 之前，大数据量实例要么接受 AOF 的慢恢复，要么接受 RDB 的大丢失窗口，必须二选一；混合把二选一变成时间上的拼接，是持久化体系里少见的两全设计。

命名的理解也有帮助：preamble 即前导，RDB 数据作为 AOF 文件的前导部分出现，参数名 aof-use-rdb-preamble 直译就是 AOF 使用 RDB 前导，看懂名字就能记住结构。

> 易混辨析：混合持久化不等于同时开启 RDB 与 AOF 两套机制。混合只有一套 AOF 流程，只是重写产物的全量部分借用了 RDB 编码；同时开启则是 save 与 appendonly 两套配置各自独立运行，二者在配置层完全正交。

```bash
# 4.0 引入时默认 no，需在配置文件中手动开启；5.0 起默认已是 yes
aof-use-rdb-preamble yes

# 运行期查看与动态修改
CONFIG GET aof-use-rdb-preamble
CONFIG SET aof-use-rdb-preamble yes

# 修改后可手动触发一次重写，让新配置体现在产物格式上
BGREWRITEAOF

# 确认配置写入了持久化的配置文件
CONFIG REWRITE
```

> 与第 17、18 章的关系：RDB 章讲快照的生成与文件结构，AOF 章讲命令追加、重写与 fsync，本章把两者在恢复路径上拼接起来，学习时应先掌握前两章的机制细节。

**速记**：混合 = **RDB 骨架** 加 **AOF 血肉**，4.0 引入、5.0 起默认开启。



#### 混合文件的内部构成

**混合文件的结构**：以 RDB 魔数 REDIS 开头、以 AOF 命令文本结尾的二进制与文本混合体，前半部分无法按文本阅读，后半部分按 RESP 协议逐条可读。

- 文件头是标准 RDB 格式：**魔数 REDIS** 开头，随后依次是版本号、辅助字段、键值数据体、结束标记与校验和，结构与第 17 章描述的 RDB 文件完全一致。
- RDB 段之后紧跟 **AOF 命令流**：以 RESP 文本（星号、美元符、回车换行）逐条追加写命令，与纯文本 AOF 的命令部分格式相同。
- 全量段记录的是**重写执行那一刻**的内存数据集，此后到文件末尾之间发生的全部写命令，按执行顺序进入增量段。
- Redis 7.0 起采用**多部分 AOF 结构**：RDB 全量独占基础文件（base），增量命令独占追加文件（incr），清单文件 manifest 记录各部分的文件名、类型与顺序。
- base 文件的扩展名就是 .rdb，内容即一份 RDB 快照；incr 文件扩展名为 .aof，内容是命令流；manifest 是可直接查看的纯文本清单。
- 手工清理旧代次的 base 与 incr 文件前，必须先确认 manifest 不再引用它们，直接删文件会让加载失败。
- 6.x 及之前的单文件形态中，两段物理上拼在同一个 appendonly.aof 文件里；7.0 起物理上拆为多个文件，逻辑上仍是先全量后增量的同一条时间线。
- 两种形态的加载逻辑一致：先反序列化 RDB 段重建基础数据集，再顺序重放增量命令补齐，过程细节见下文载入考点。
- 重写时机一到，基础文件被新生成的 RDB 快照替换，追加文件从零开始重新累积，文件体积随之回落。

```text
6.x 单文件混合 AOF 的逻辑布局

REDIS + 版本号        <- RDB 文件头
RDB 二进制键值数据    <- 重写瞬间的全量快照，不可读
EOF 标记 + 校验和     <- RDB 段结束
*3\r\n$3\r\nSET\r\n   <- 其后按 RESP 追加的命令文本，可读
（增量命令持续追加，直到文件末尾）
```

```text
7.0 多部分 AOF 的目录布局（appendonlydir，📦 结构示意）

appendonly.aof.1.base.rdb    <- 基础文件，RDB 编码的全量
appendonly.aof.1.incr.aof    <- 追加文件，AOF 命令增量
appendonly.aof.manifest      <- 清单文件，记录各部分版本与顺序
```

文件构成决定了混合文件不能整份按文本审阅，也无法用文本编辑器手工修改全量段；人工检查的对象通常是增量段与 manifest，全量段交给校验工具处理。

> 判断一份 AOF 是否为混合格式，看文件开头即可：纯文本 AOF 开头是星号引导的 RESP 命令，混合文件开头是二进制的 REDIS 魔数字节，用 head 或 xxd 查看文件头几个字节即可区分。

> 6.x 升级到 7.0 时，旧的单文件 AOF 仍可直接加载，Redis 会按旧格式读入，并在首次重写后落成多部分结构，无需手工转换。

**速记**：开头 **RDB 全量**，尾部 **AOF 增量**，7.0 拆成 **base 加 incr**。



#### 混合模式的双重收益

**混合模式的收益**：让恢复速度向 RDB 看齐、丢失窗口向 AOF 看齐，同时把重写后的文件体积压到接近 RDB 的水平。

- **加载快**：反序列化 RDB 只需解析二进制结构，逐条重放 AOF 命令却要在内存里真实执行每条写命令，前者通常快一个数量级；混合文件的全量占比越大，整体恢复越快。
  - 重放增量段仍要逐条执行，但增量只是重写之后的少量写入，占比很小。
- **丢失窗口小**：增量段随写命令持续追加，配合 appendfsync everysec，宕机最多丢约**一秒**数据，与纯 AOF 完全一致。
- **体积小**：RDB 二进制远比等价的命令文本紧凑，重写产物体积明显小于纯 AOF 重写结果。
- **重写更轻**：生成 RDB 编码比序列化全部命令文本开销更小，重写期间子进程的 IO 压力也相应降低。
- **历史归零**：每次重写都把历史命令压缩成 RDB 快照，文件不再随时间无限膨胀，纯 AOF 长期不重写的命令堆积问题被根治。
- 收益的取得互不冲突，根源在于**全量与增量分开编码**：快照天然适合二进制，增量天然适合命令流。
  - 重写越频繁，文件越接近纯 RDB 的形态，恢复越快，但重写自身的开销也越频繁，节奏需要平衡。

```bash
# 增量段的丢失窗口由 fsync 策略决定（详见第 18 章）
appendfsync everysec   # 折中：最多丢约一秒，生产默认选择
appendfsync always     # 最强：每条命令落盘，吞吐明显下降
appendfsync no         # 最快：交给操作系统刷盘，丢失窗口不可控
```

收益的量级可用两个极端对照：一个 10GB 数据集的实例，纯文本 AOF 恢复可能需要数分钟，混合加载往往能压缩到数十秒；丢失窗口方面，RDB 方案最坏丢掉两次快照之间的全部写入，混合方案最坏只丢约一秒。

混合的收益在数据集越大时越显著：小数据集上 RDB 与 AOF 的恢复差距本就有限，混合与否体感不明显；数据到 GB 级以上，差距才拉开到需要认真对待的程度。

> 常见误区辨析：开启混合后就完全丢不了数据——错误。混合只改变文件的编码，宕机时丢多少仍由 appendfsync 决定，everysec 档照样有约 1 秒的丢失窗口；它也不提供时间点回滚，误删数据仍要靠定期 RDB 备份找回，备份的价值不因开启混合而消失。

> 一句话概括：混合模式把 RDB 的快与 AOF 的全缝在同一条时间线上。这也是官方在 5.0 将其设为默认的根本原因——对绝大多数实例，混合都是纯赚的改进。

**速记**：恢复**快如 RDB**，丢失**少如 AOF**，体积还更**小**。



#### 关闭混合模式后的文件形态

**关闭混合的代价**：将 aof-use-rdb-preamble 设为 no 后，重写产物退回纯 AOF 文本，整份文件都是 RESP 命令，恢复只能靠逐条重放。

- 文件开头不再是 RDB 魔数，而是与普通 AOF 完全相同的命令文本，全部数据都以 SET、HSET、RPUSH 等写命令表达。
- 加载速度回落到**纯 AOF 的重放速度**，数据集越大、重写间隔越长，恢复越慢。
- 文件体积回落到**纯 AOF 的体积**，同一份数据的命令文本通常比 RDB 编码大数倍。
- 关闭不影响既有混合文件的加载：Redis 仍按文件实际格式识别并读取，改动只体现在下次重写之后。
- 混合关闭与否不影响 RDB 文件，dump.rdb 的生成与格式始终不变。
- 保留纯文本模式的合理场景：需要人工审阅写入历史、用外部工具解析 AOF 内容、或教学演示命令重放原理。
- 关闭混合后重写产物体积增大，磁盘占用与重写 IO 都会相应上升。

```bash
# 关闭混合（5.0 起默认已是 yes，仅在有明确可读性需求时使用）
aof-use-rdb-preamble no

# 修改后手动触发一次重写，观察新产物已变回纯文本
BGREWRITEAOF
```

关闭混合的动机通常只剩两个：兼容依赖纯文本的外部解析工具，或排查问题时需要整份可读文件。两者都可以用临时方案解决——在测试实例上关闭混合生成文本文件，生产实例保持默认开启。

> [!CAUTION]
> **注意内容**：在大数据量实例上关闭混合会显著拉长故障恢复时间。一份重放需要数分钟的 AOF 文件，意味着每次重启实例都要承受数分钟不可用；除非有明确的可读性需求，不建议关闭。

**速记**：关混合 = 整文件**全命令文本**，恢复**慢**、体积**大**、可读**好**。



#### 混合模式的适用前提与重写节奏

**混合的前提是 AOF 重写在正常运转**：混合只改变重写产物的编码，若实例长期不重写或重写被禁用，混合的收益就无从兑现。

- 增量段会随时间持续膨胀：重写间隔越长，需要重放的命令越多，恢复越慢，因此混合模式更需要**稳定的重写节奏**。
- 保持自动重写配置的合理取值，让文件增长到一定比例就触发重写，参数含义与调优详见第 18 章。
- 混合并非免费：每次重写都要 fork 子进程生成 RDB 快照，重写频率过高会放大 fork 与写时复制的开销，见下文性能影响考点。
- 写入特别频繁的实例，两次重写之间的增量也可能很大，恢复耗时需结合实际重写周期评估，不能只看全量段大小。
- 重写期间增量命令会同时写入旧文件与重写缓冲，实例内存与 IO 都有瞬时抬升，容量评估应覆盖该时段。
- 评估恢复时长最可靠的方式是演练：在测试环境用真实大小的 AOF 文件跑一次完整加载，记录耗时作为基线。
- 混合模式的恢复耗时近似等于 RDB 加载耗时加重放少量增量命令的耗时，两者分别受数据集规模与重写间隔控制。

```bash
# 自动重写触发条件（详见第 18 章）
auto-aof-rewrite-percentage 100   # 文件超过上次重写后大小的 100% 时触发
auto-aof-rewrite-min-size 64mb    # 且文件至少达到 64mb 才触发

# 手动触发重写
BGREWRITEAOF
```

判断当前增量段的规模，可查看 incr 文件的体积：增量明显超过全量时，说明重写节奏落后于写入速度，应调低触发比例或缩短检查周期。

重写节奏的规划还应避开业务高峰：重写期间的 fork 与子进程写盘会挤占在线请求的 IO，把重写安排在低峰执行，能显著降低体感影响。

> 压缩恢复时间的两个抓手因此也很明确：控制单实例数据规模、维持规律的重写节奏。前者决定全量段的加载耗时，后者决定增量段的重放耗时，二者都需要在生产环境实测确认。

> 混合模式不是恢复速度的万能药：全量段保证下限，增量段决定上限。写入极端频繁且重写跟不上的实例，恢复耗时仍可能超预期，必须用真实负载演练验证。

**速记**：混合靠**重写续命**，重写节奏决定**增量长短**与恢复快慢。



### RDB 与 AOF 的对比与共存

#### RDB 与 AOF 的全维度对比

**RDB 与 AOF 的本质差异**：RDB 是某一时刻的**全量二进制快照**，AOF 是按执行顺序记录的**增量命令流水**，所有维度的差异都源于这一根本分野。

- **数据丢失窗口**：RDB 的窗口是两次快照之间的全部写入，通常为分钟级甚至更长；AOF 在 everysec 下约为**一秒**，always 下接近零。
  - save 条件越宽松，RDB 的窗口越大，窗口上限就是快照间隔。
  - always 把每条写命令都落盘，窗口最小但吞吐下降明显，一般不作为默认选择。
- **文件体积**：RDB 是紧凑的二进制，体积小；AOF 是命令文本，体积大，即使经过重写仍显著大于 RDB。
- **恢复速度**：RDB 直接反序列化，恢复快；AOF 逐条重放命令，恢复慢，数据量大时差距悬殊，混合模式正是为缓解这一差距而生。
  - 混合模式让恢复速度与丢失窗口不再是单选题，但两者的代价组合仍需按业务取舍。
- **运行时性能影响**：RDB 的 BGSAVE 依赖 fork 与写时复制，大实例 fork 瞬间可造成数十至数百毫秒停顿；AOF 的开销是命令追加与 fsync，everysec 由后台线程刷盘，抖动小但持续存在。
- **可读性**：RDB 是二进制，不可人工阅读；AOF 是文本，可读、可人工核对与编辑。
- **损坏修复能力**：RDB 只能校验不能修复；AOF 末尾残缺可截断修复，工具用法见下文。
- **触发方式**：RDB 由 save 条件、BGSAVE、主从全量同步等触发；AOF 开启后随写命令持续追加，重写由自动配置或 BGREWRITEAOF 触发。
- **版本兼容**：RDB 格式随版本演进，旧版本 Redis 无法加载新版 RDB 文件；AOF 命令文本相对宽松，兼容性更好。
- **异地容灾适配**：RDB 单文件便于传输与归档；AOF 多文件在 7.0 后需整体搬运。
- **运维心智负担**：RDB 配置项少、心智简单；AOF 涉及 fsync、重写、修复，运维面更宽。

```bash
# 两套机制的核心配置对照

# RDB 侧（详见第 17 章）
save 3600 1 300 100 60 10000
dbfilename dump.rdb
dir /data/redis                     # 持久化文件目录，两套机制共用

# AOF 侧（详见第 18 章）
appendonly yes
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

维度之间并非独立：丢失窗口与运行时开销互为代价，恢复速度与文件体积同向变化。选型时先把业务最不能接受的维度定为硬约束，再在其余维度里取最优组合。

把混合并入对照后，三个核心维度的三方速览如下：

- **数据丢失窗口**：RDB 为两次快照间隔（分钟级起）／AOF 由 appendfsync 决定（everysec 约 1 秒）／混合与 AOF 完全相同。
- **文件体积**：RDB 二进制压缩、最紧凑／AOF 重写后仍是命令文本、最大／混合的 RDB 前导接近 RDB、总体接近 RDB。
- **恢复速度**：RDB 直接反序列化、最快／AOF 逐条重放、最慢／混合先快载前导再重放少量增量、接近 RDB。
- **可读性与兼容性**：AOF 全文可读、兼容性最好／RDB 不可读但格式跨版本稳定／混合前导不可读，且 4.0 之前的实例无法载入带 RDB 前导的文件。

> 两者不是竞争关系而是互补关系：RDB 擅长**快速恢复与冷备**，AOF 擅长**尽量少丢数据**。选型不是二选一，而是按丢失容忍度决定以谁为主、以谁为辅，详见下文决策指南。

**速记**：RDB **快而丢**，AOF **全而慢**，混合**快而全**。



#### 同时开启两种持久化时的行为

**同时开启的行为**：RDB 与 AOF 各自独立运行互不干扰，但重启时数据恢复只认 AOF，RDB 文件仅作为备份冗余存在。

- appendonly 为 yes 且 save 条件保留时，**两套持久化同时工作**：AOF 持续追加，RDB 按条件周期性生成快照。
- 重启加载时**以 AOF 为准**：只要 AOF 开启，Redis 一律加载 AOF 文件重建数据集，RDB 文件即使内容更新也不会被读取。
- RDB 在该组合中的价值是**备份与灾备**：周期快照适合复制到异地长期保存，AOF 承担日常恢复职责。
- RDB 的快照还会被主从全量同步复用，双开时快照兼具同步源的作用。
- 官方建议同时开启两种持久化：AOF 保证丢失窗口小，RDB 提供一份便于冷备、可快速恢复的数据副本，二者配合是最稳妥的方案。
- 需要一份反映最新数据的快照时，可在低峰期手动执行 BGSAVE 生成。
- 该组合的代价是持久化相关的 CPU、内存与 IO 开销叠加，快照与重写可能撞车，应通过配置与时间安排错峰。
  - 快照与重写撞车时两者按先后顺序各自执行，fork 的停顿影响会叠加，错峰安排可明显缓解。

```bash
# 同时开启的典型配置
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
save 3600 1 300 100 60 10000
```

判断实际生效的恢复源，看启动日志即可：日志会明确写出从哪类文件加载成功。运维巡检时应核对日志与预期一致，避免配置与认知不符。

> [!IMPORTANT]
> **重要内容**：同时开启时务必记住恢复优先级——AOF 永远优先。若误以为重启会加载更新的 RDB，从而忽视 AOF 文件的状态管理（例如 AOF 已损坏却未处理），重启时将直接失败或加载出异常数据。

> 双开方案的开销不是简单叠加：重写与快照都走 fork，两个子进程并存时写时复制的风险更高，内存余量要按并发期峰值预留。

**速记**：双开不冲突，恢复**只认 AOF**，RDB **管备份**。



#### 启动时的载入优先级与过程

**载入优先级**：启动时若 AOF 开启则只加载 AOF 文件，AOF 关闭时才加载 RDB 文件，两条路径不会叠加恢复。

- 判断只有一步：看 appendonly 的取值。为 yes 则进入 AOF 载入流程；为 no 则载入 RDB 文件。
- AOF 载入过程分两步：先解析文件头识别格式，反序列化 RDB 段重建基础数据集（混合格式时），再顺序重放增量命令直到文件末尾。
- RDB 载入过程：解析二进制结构、校验文件，通过后直接重建数据集，细节见第 17 章。
- 载入完成前实例**不对外服务**，数据量大时启动窗口不可忽视，应在容量规划中计入恢复时长。
- 载入期间可用的只有少量管理类命令，业务连接应等加载完成后接入，健康检查以日志中加载完成的条目为准。
- 从库被全量同步接管数据时，本地持久化文件的加载结果会被覆盖，重启耗时以实际恢复路径为准。
- 主从全量同步是另一条数据重建路径：从库优先与主库同步，可能与本地持久化载入并行或替代，详见第 20 章。

```text
启动日志示意（7.0，AOF 开启且为混合格式时）

* Reading RDB base file on AOF loading...
* RDB base file loaded successfully
* Reading the remaining AOF tail...
* DB loaded from append only file: 3.128 seconds
```

载入优先级的工程含义在于：AOF 开启的实例，重启耗时取决于 AOF 的加载速度，这正是混合模式优化恢复速度的直接落点；AOF 关闭的实例，则由 RDB 文件大小决定启动时长。

> 混合格式的识别是自动的：加载端按文件实际开头格式解析，与当前 aof-use-rdb-preamble 的取值无关，该配置只决定下次重写产物的格式。因此新旧文件混存、配置切换前后，都不影响正常启动。

> 排查启动慢的问题时，先区分是持久化载入慢还是其他初始化慢：日志时间戳的间隔会清楚显示载入阶段占了多久，再看对应环节的优化手段。

**速记**：先看 **AOF 开没开**，开了**只读 AOF**，没开才读 RDB。



### 持久化选型决策

#### 选型决策指南

**选型的核心变量**：是业务的**数据丢失容忍度**与**恢复时长容忍度**，前者决定要不要 AOF 及 fsync 级别，后者决定要不要混合与 RDB 快照的频率。

- **纯缓存场景**：数据全部可由后端重建，可完全关闭持久化（save 置空、appendonly no），或只留低频 RDB 供重启提速；关闭后重启得到空实例，靠业务侧回填。
  - save 后跟空串表示关闭 RDB 快照，配置写法见第 17 章。
  - 缓存实例关闭持久化后重启即冷启动，业务侧需配套预热策略。
- **可容忍分钟级丢失**：可重建的统计、排行榜类数据，只开 RDB，快照周期按容忍度设置，丢失窗口即快照间隔。
- **一般业务数据**：订单、账户、配置等不可丢数据，开启 AOF 并使用 appendfsync everysec，最多丢一秒，性能代价可接受。
- **大数据量且恢复敏感**：实例数据量大、故障恢复时间敏感，在 AOF 之上保持混合模式（5.0 起默认开启），重写后加载速度大幅提升。
- **极端不丢数据要求**：考虑 always，或以主从加哨兵的高可用架构兜底，前者吞吐代价大，后者按第 21 章的架构设计。
- **冷备与容灾需求**：无论哪种选择，都应定期把 RDB 快照复制到异地作为最终兜底，做法见下文备份策略。
- 同一业务的不同实例可以差异化配置：核心库按一般业务配置，缓存库按纯缓存配置，不必全局一刀切。
- 选型还要考虑团队运维能力：AOF 加混合的运维面更宽，能力有限的小团队可从纯 RDB 起步再演进。

```bash
# 典型的通用业务组合（🧭 既有 AOF 快恢复，又有 RDB 冷备）
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
save 3600 1 300 100 60 10000

# 纯缓存场景的极简组合
save ""
appendonly no
```

选型结论要落成配置清单并纳入变更管理：丢失容忍度变化、数据规模变化时重新评估，把每项配置对应的业务前提写进运维手册，便于交接与审计。

> [!TIP]
> **建议内容**：选型先问两个问题——宕机最多能丢多少数据、重启最多能接受多长不可用。前者决定是否开 AOF 与 fsync 级别，后者决定混合与 RDB 快照频率，两个答案组合起来就是配置。

**速记**：问丢多少**定 AOF**，问停多久**定混合与 RDB**，缓存可**全关**。



#### 生产环境的备份策略

**备份的意义**：持久化文件只能防进程崩溃，防不了磁盘损坏、误删与恶意清空，生产环境必须把 RDB 快照**定时复制到异机或异地**。

- 保留 RDB 自动快照：save 条件让实例在写入活跃时周期性落盘，作为备份的原料。
- 用 Cron 定时把最新快照复制到备份机、对象存储或磁带，复制时先写临时文件名再原子改名，避免拷贝到半成品文件。
- 备份文件命名带时间戳，便于快速定位恢复点与滚动清理。
- 大实例的快照耗时更长，Cron 间隔要长于快照耗时，避免快照堆积。
- 备份保留多版本并按策略滚动清理，至少覆盖天级粒度，重要数据覆盖周级、月级。
- 异地备份至少一份，跨机房或跨可用区存放，防止单点灾难同时毁掉数据与备份。
- 定期做**容灾演练**：抽取备份文件在测试实例上真实加载，验证文件可用性与恢复时长，未验证过的备份等于没有备份。
- 演练同时记录恢复耗时，作为选型与容量规划的基线数据，定期更新。

```bash
# 示例：每两小时触发一次快照（Cron 表达式按需调整）
0 */2 * * * redis-cli BGSAVE

# 每日一次的异地同步示例
0 4 * * * rsync -a /data/redis/dump.rdb offsite-host:/backup/redis/daily/

# 等快照完成后再复制：轮询状态比固定等待更可靠
# INFO persistence 中 rdb_last_bgsave_status 为 ok 即可复制
rsync -a /data/redis/dump.rdb backup-host:/backup/redis/
```

备份的新鲜度要求可以低于持久化：RDB 备份承担的是兜底角色，间隔数小时的备份已经足够；越新数据的恢复交给 AOF 与复制链路，分工明确后备份压力小得多。

> BGSAVE 是异步的：脚本中应轮询 INFO persistence 里的 rdb_last_bgsave_status，确认 ok 后再复制；也可直接复制上一次已完成的快照，牺牲一点新鲜度换取脚本简单。

> [!WARNING]
> **警告内容**：只依赖本机持久化文件等于没有容灾。误执行 FLUSHALL、磁盘损坏、机器失联都会让本机文件与数据一起消失，务必保证至少一份备份位于另一台机器或另一个可用区。

**速记**：**本机文件防崩溃，异机备份防灾难**，备份必须**演练**。



#### 主从架构下的持久化角色分配

**主从架构下的分工**：常见做法是让从库承担持久化职责、主库减轻或关闭持久化，但主库完全关闭有放大丢失的风险，需按官方口径权衡。

- 争议做法的内容：主库关闭 RDB 与 AOF，持久化全部交给从库，主库免受 fork 与 fsync 影响，写性能最佳。
- 风险所在：主库无持久化且意外重启时，实例以空数据集启动，从库会同步到空数据，**全量丢失**被复制机制放大。
- 官方口径：主库关持久化的方案可以接受，但前提是**禁止主库崩溃后自动重启**，必须人工介入决策；同时主从至少一方开启持久化，且都应有异机备份。
- 更稳妥的折中：主库保留 RDB（或低频 save 条件），AOF 开在从库；主库兼具一定恢复能力，从库负责细粒度持久化。
- 主库保留 RDB 的另一收益：主从全量同步所需的 RDB 可复用本地快照，减少一次 fork 开销。
- 从库开启 AOF 后同样遵循第 18 章的全部机制，fsync 与重写策略照常生效。
- 角色分配应与故障转移逻辑配合设计：哨兵只关心实例可达性，不感知持久化状态，详见第 21 章。
- 复制链路不等于持久化：复制解决的是读扩展与高可用，持久化解决的是数据落盘，两者各自解决不同的问题，详见第 20 章。

```bash
# 折中方案示例：主库只留 RDB，从库开 AOF

# 主库 redis.conf
save 3600 1 300 100 60 10000
appendonly no

# 从库 redis.conf
appendonly yes
appendfsync everysec
```

角色分配没有唯一答案，判断标准仍是丢失容忍度与性能压力：写压力大且风险可控的实例才适合主库全关，一般场景优先折中方案。

角色调整是变更操作：调整主从持久化配置前，先评估当前复制拓扑与故障转移策略，调整后做一次故障转移演练确认闭环。

> [!CAUTION]
> **注意内容**：主库零持久化加进程守护自动重启是最危险的组合——重启后的空实例会通过复制把空数据集传播给所有从库。采用主库关持久化方案时，必须先关掉自动重启并建立人工介入流程。

**速记**：从库**管持久化**，主库**慎全关**，自动重启**必关**。



### 持久化的性能影响与常见问题

#### 持久化对主线程的影响面小结

**影响面小结**：两种持久化都设计为尽量不阻塞主线程，但 fork、写时复制与 fsync 三个环节仍会周期性地影响服务，是容量规划必须预留的部分。

- **fork 阻塞**：BGSAVE 与 AOF 重写都要 fork 子进程，fork 耗时与页表规模成正比，实例越大瞬间阻塞越久，可达数十至数百毫秒，是大实例最明显的停顿来源。
  - 主从全量同步同样要 fork 生成 RDB，影响机制完全相同。
  - 降低单实例数据规模（拆分实例）是最直接的缓解手段。
  - fork 耗时可用 INFO stats 中的 latest_fork_usec 观察，单位为微秒，是评估实例规模风险的第一手指标。
- **写时复制内存放大**：fork 后父子共享内存页，父进程持续写入触发页复制，快照或重写期间内存可能明显上涨，最坏情况接近翻倍。
  - 按 fork 触发时刻的占用预留内存余量，而不是按稳态数据量预留。
- **fsync 抖动**：everysec 由后台线程刷盘，但当主线程需要写 AOF 而上次 fsync 尚未完成超过两秒时，会强制阻塞等待，磁盘慢的机器上表现为周期性延迟毛刺。
- **子进程 IO 压力**：快照落盘与重写期间子进程大量写盘，与在线请求争抢 IO 带宽，低配云盘上尤为明显。
- INFO 命令可观测 fork 与重写状态，配合监控尽早发现异常，见下文自查考点。
- 混合模式继承了 AOF 的重写与 fsync 影响面，同时新增 RDB 式的快照编码开销，评估时两者都要计入。
- 事件模型中主线程与后台线程的分工见第 16 章，性能优化手段与慢查询排查见第 29 章。

三个影响面都随数据规模增长，持久化的性能问题本质上是容量问题：实例越小，fork 越快、COW 越少、重写越轻，这也是大内存实例普遍建议拆分的理由之一。

> 三种持久化形态在此汇合：RDB 的 save 与 BGSAVE、AOF 的重写与 fsync，落到运行时都是这三个影响面。监测时关注 fork 耗时、内存峰值与磁盘延迟三类指标，即可覆盖绝大部分持久化相关问题。

**速记**：**fork 一顿、COW 一涨、fsync 一抖**，三处都要**预留**。



#### RDB 文件损坏的校验与处理

**损坏校验工具**：redis-check-rdb 是官方随 Redis 发布的 RDB 校验工具，加载失败时先用它判断文件是否损坏与损坏程度。

- 用法：redis-check-rdb 后接 RDB 文件路径，输出文件头信息、各段统计与结尾校验结果。
- RDB 文件尾带校验和，加载时 Redis 会校验，不通过则拒绝加载并在日志中报错。
- 该工具**只读校验、不能修复**：RDB 是二进制整体，无法像 AOF 那样截断修复，损坏位置之后的数据也可能受牵连。
- 处理路径：回退到最近的可用备份（上一份快照或异机副本），再配合 AOF 或从库数据尽量补齐，这正是备份策略的价值所在。
- 加载报校验错误时先保留现场，排查是否为非原子复制了半成品文件、传输介质损坏等原因，不要急于删除原文件。
- 校验通过只说明结构合法，不代表业务数据完整；完整性仍需按备份时间点评估。
- redis-check-rdb 在较新版本中还能输出各类型键的数量统计，可用于备份内容的抽样核对。
- 定期用该工具抽查异机备份文件，把发现损坏的时机提前到真正需要用它之前。

```bash
# 校验当前使用的 RDB 文件，输出各段统计与校验结论
redis-check-rdb /data/redis/dump.rdb

# 抽查异机备份的可用性
redis-check-rdb /backup/redis/dump-20260907.rdb
```

RDB 损坏的常见来源包括磁盘坏块、非原子复制与传输截断；异机备份附上校验和文件核验，能及时发现传输类损坏。

> 与 redis-check-aof 的区别：后者支持 --fix 对末尾残缺做截断修复，前者没有修复能力，只出体检报告。RDB 的可靠性只能靠多副本备份保障，这也是即使选 RDB 方案也建议关注 AOF 的原因。

**速记**：RDB 损坏**只验不修**，恢复靠**备份回退**。



#### AOF 文件的校验与修复

**AOF 的修复能力**：redis-check-aof 可校验 AOF 文件，对末尾残缺命令可用 --fix 截断修复，配合 aof-load-truncated 配置能处理绝大多数宕机留下的不完整写入。

- aof-load-truncated 默认 yes：加载遇到**末尾**命令残缺（宕机导致写了一半）时直接截断加载，保证实例能启动，代价是丢最后一条不完整命令。
- 设为 no 时遇到残缺即报错退出，适合对数据一致性要求极严格的场景，由人工修复后再启动。
- 文件**中部**损坏时 yes 也不会跳过，加载照样失败，必须用 redis-check-aof --fix 修复或回退备份。
- --fix 会先备份原文件再截断到第一个无效位置，修复完成后建议再次校验确认。
- 校验与修复都应在离线状态执行，不要对运行中实例正在写入的 AOF 做操作。
- 7.0 的多部分 AOF 校验以 manifest 清单文件为入口，工具会连带校验基础文件与追加文件，修复同样支持。

```bash
# 校验单文件 AOF
redis-check-aof /data/redis/appendonly.aof

# 末尾残缺时修复（先备份后截断）
redis-check-aof --fix /data/redis/appendonly.aof

# 7.0 多部分 AOF：以 manifest 为入口校验整体
redis-check-aof /data/redis/appendonlydir/appendonly.aof.manifest
```

修复工具的能力边界要记牢：它只处理结构层面的残缺，不校验命令的业务合理性，也不会补齐数据；修复后的数据集可能少于崩溃前的状态。

> 截断修复是有损操作：截断点之后的有效命令同样被丢弃，执行前务必复制一份原始文件。对含中部损坏的文件，截断无能为力，应回退到 RDB 备份或从库数据重建。

**速记**：尾部残缺**可截断**，中部损坏**靠备份**，修复前**先备份**。



#### 磁盘写满导致 AOF 写失败的恢复流程

**磁盘写满的后果**：磁盘空间耗尽时 AOF 追加与 fsync 失败，Redis 会把 AOF 写状态标记为错误并拒绝执行写命令，读命令不受影响，进程通常不退出。

- 现象：写命令被拒绝并报错，日志持续出现 AOF 写入失败相关条目，INFO persistence 中 aof_last_write_status 变为错误状态。
- 读命令不受影响的原因：AOF 只记录写命令，读命令不产生持久化动作，实例仍可对外提供查询服务。
- 恢复流程第一步：清理磁盘或扩容，先消除写失败的根源，让实例恢复可写。
  - 云盘在线扩容通常即时生效，是清理空间之外的首选手段。
- 第二步：校验 AOF 文件完整性，末尾残缺时用 redis-check-aof --fix 修复，流程见上一考点。
- 第三步：重启实例重新加载 AOF，确认日志中加载成功、写状态恢复正常。
- 第四步：评估磁盘满期间的数据完整性，该期间未能持久化的写入已经丢失，必要时从上游业务补偿。
- 恢复后检查 manifest 与文件大小是否正常（7.0），确认没有残留的临时文件。
- 单机多实例共用一块盘时，任一实例写满都会牵连其余实例的持久化，容量规划要按整盘计算。
- 预防手段：磁盘容量告警、为持久化文件单独划分分区、限制实例内存上限以间接控制文件体积。

写失败期间实例的内存数据仍在服务，业务写入在内存中已生效、只是没有落盘；因此故障期间不要急于重启，重启反而会丢掉这些仅存于内存的写入，先恢复磁盘再从容处理。

```bash
# 恢复流程命令序列示意
df -h /data/redis                                    # 确认磁盘水位
redis-check-aof /data/redis/appendonly.aof           # 校验文件
redis-check-aof --fix /data/redis/appendonly.aof     # 末尾残缺时修复
redis-cli INFO persistence | grep aof_last_write     # 确认写状态恢复
redis-cli ping                                       # 重启加载后确认实例健康
```

> [!WARNING]
> **警告内容**：磁盘满导致的写失败若长时间不处理，丢失窗口会随时间持续扩大。收到告警后应先扩容或清理让实例恢复可写，再从容做校验修复，不要让实例停留在拒绝写入的状态。

**速记**：**先腾磁盘，再验文件，后修截断**，修前必**备份**。



#### 持久化状态的自查与监控要点

**自查的核心入口**：INFO persistence 与 INFO stats 暴露了持久化的关键运行状态，巡检与告警应以此为准，而不是等故障发生后才排查。

- rdb_last_bgsave_status：最近一次 BGSAVE 的结果，取值不是 ok 就应立即告警。
- rdb_last_save_time：最近一次成功快照的 Unix 时间戳，距当前超过正常快照间隔过多，说明快照停滞。
- rdb_changes_since_last_save：距上次快照的写入次数，数值越大，下次快照前崩溃的丢失窗口越大。
- aof_enabled、aof_last_write_status：AOF 开关与最近写入状态，写失败时后者转为异常。
- aof_current_size、aof_base_size：当前 AOF 体积与上次重写后的体积，两者比值是判断重写节奏的依据。
- aof_last_bgrewrite_status：最近一次重写的结果，配合 aof_rewrite_in_progress 判断重写是否卡住。
- latest_fork_usec：最近一次 fork 的耗时，监控其趋势可提前发现大实例的 fork 风险。
- aof_delayed_fsync：fsync 延迟发生的累计次数，是磁盘压力的直观信号。

```bash
# 巡检示例：一次取回关键状态
redis-cli INFO persistence
redis-cli INFO stats | grep latest_fork_usec
```

监控告警的建议阈值：两个 status 字段异常即告警，rdb_changes_since_last_save 与 aof_current_size 按容量水位设阈值，latest_fork_usec 按实例规模设基线。持久化异常往往先于故障出现，巡检到位就能把问题挡在早期。

> 持久化状态的巡检应纳入日常运维清单，与第 31 章的运维实践、第 29 章的性能排查共用同一套巡检体系，避免各自为政。

> 巡检频率的建议：status 类字段进实时告警，体积与时间戳类进日报核对，fork 耗时进性能周报，分级告警才能既灵敏又不疲劳。

**速记**：巡检盯 **INFO persistence**，看**状态、体积、时间戳**三组字段。
