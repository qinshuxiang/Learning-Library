## 持久化：RDB

### 持久化与 RDB 的基本认识

#### 持久化的定义与 RDB 的定位

**持久化（Persistence）**：是把内存中的数据**写入磁盘保存**、使进程重启后能够恢复数据的机制；**RDB（Redis Database）**：是 Redis 持久化的第一种手段，在**某一时刻**把内存中的全部数据写成一份**二进制快照文件**。

- Redis 的数据默认全部存放在内存中，进程退出、断电或崩溃都会让数据瞬间清空，持久化正是为解决内存数据的**易失性**而存在。
- RDB 记录的是某一瞬间的**完整数据状态**而非操作过程，相当于给内存拍一张照片，生成的文件默认名为 dump.rdb。
- 文件是紧凑的二进制格式，体积小、传输快，恢复时直接读回内存即可，速度远快于重放写命令的 AOF（详见第 18 章）。
- RDB 是 Redis **默认开启**的持久化方式，redis.conf 中的 save 配置默认生效。
- 典型的恢复场景包括：服务器断电后重启、进程崩溃后拉起、版本升级后重启、把数据整体搬迁到新机器。
- 快照文件一次生成、多次使用：同一份文件既能用于本机重启恢复，也能用于搭建新的从节点或灾备实例。
- 快照的粒度是**实例级**的：一次快照覆盖整个 Redis 进程的全部数据库，无法只对某个键或某个库单独拍快照。
- 文件位置统一由 dir 与 dbfilename 管理，天然适合纳入常规的备份与巡检体系。
- RDB 与 AOF 可以同时开启，二者共存时的载入优先级与选型对比详见第 19 章。

```bash
CONFIG GET save       # 查看当前生效的快照触发条件
CONFIG GET dir        # 查看快照文件的存放目录
CONFIG GET dbfilename # 查看快照文件名
```

```text
1) "save"
2) "900 1 300 10 60 10000"
1) "dir"
2) "/var/lib/redis"
1) "dbfilename"
2) "dump.rdb"
```

> RDB 关注的是**结果**：它不关心这份数据经历了哪些写命令，只在快照时刻把当时内存里的样子完整存下来；至于每一次写入是如何发生的，属于 AOF 的职责范围。

> 快照是**整库级别**的动作，粒度无法细化到某个库或某个键；只需要导出部分数据时应使用对应的读取命令，而不是快照。

> [!NOTE]
> **提醒内容**：即使一行持久化配置都不写，Redis 也会按内置的默认 save 条件周期性生成快照；确认当前实际生效的策略应以加载的配置为准，可用 CONFIG GET save 查看。

**速记**：RDB＝**某一时刻内存的完整二进制快照**，恢复快、体积小，默认开启。



### 手动触发：SAVE 与 BGSAVE

#### SAVE 与 BGSAVE 的本质区别

**SAVE**：在**主线程中同步**生成 RDB 文件，执行期间 Redis 完全阻塞；**BGSAVE**：fork 出**子进程**在后台生成 RDB 文件，主线程继续服务命令。

- SAVE 无参数，主线程亲自遍历数据写盘，客户端要等快照彻底完成才收到 OK。
- BGSAVE 无参数，主线程只负责 fork，实际写盘由子进程完成，写完后子进程向父进程发信号汇报结果。
- BGSAVE 立即返回 Background saving started，之后主线程照常处理读写请求。
- BGSAVE 进行期间再次发送 BGSAVE 会被拒绝，返回 Background save already in progress。
- 两个命令都**直接执行、不受 save 配置条件约束**，是手动备份与运维脚本的入口。
- 两个命令生成的 RDB 文件格式完全相同，差别只在**由谁执行、是否阻塞**。
- 手动触发不受 save 条件的时间窗口限制，任何时候都可以执行，常用于发布前的保底备份。

**SAVE 与 BGSAVE 的逐项对比**：

- **执行者**：SAVE 由主线程执行／BGSAVE 由 fork 出的子进程执行。
- **阻塞情况**：SAVE 执行期间服务完全不可用／BGSAVE 仅 fork 瞬间有停顿。
- **返回时机**：SAVE 写完文件后才返回 OK／BGSAVE 立即返回后台任务已开始。
- **适用场景**：SAVE 仅用于调试与允许停机的维护窗口／BGSAVE 用于生产与自动化脚本。

```bash
SAVE      # 阻塞执行，返回 OK 时快照已生成完毕
BGSAVE    # 立即返回 Background saving started，后台写盘
LASTSAVE  # 查看最近一次成功保存的 Unix 时间戳
```

```text
BGSAVE 执行返回：
Background saving started

启动日志（包含子进程号）：
* Background saving started by pid 1234

写盘完成后日志输出：
* Background saving terminated with success
```

```bash
# 发布前保底备份的脚本节奏
redis-cli BGSAVE
sleep 2
cp /var/lib/redis/dump.rdb /backup/dump-before-release.rdb
```

> [!CAUTION]
> **注意内容**：SAVE 会把主线程完全卡住，数据量大时所有请求都会在快照期间超时，生产环境严禁使用；需要手动触发快照时一律使用 BGSAVE。

> SAVE 的存在更多是给调试与特殊运维场景保留的同步入口；日常脚本与集群、哨兵等内部组件触发的都是 BGSAVE，这决定了 RDB 在生产中的实际形态都是后台快照。

**速记**：SAVE **亲自写盘、全程阻塞**，BGSAVE **fork 子进程、后台干活**。



### fork 与写时复制

#### fork 创建子进程的机制

**fork**：是操作系统提供的**复制当前进程**的系统调用，Redis 借助它把写快照的工作交给子进程，实现持久化不阻塞服务。

- fork 调用后产生一个与父进程**几乎完全相同**的子进程，拥有独立的进程地址空间，子进程代码从 fork 返回处继续执行。
- 子进程继承父进程的**内存数据视图**，从此父进程继续服务命令，子进程专心遍历数据写 RDB。
- 现代操作系统的 fork 并不会真的复制全部物理内存，而是复制**页表**，让父子进程**共享同一批物理页**。
- 子进程从数据库编号 0 开始逐库遍历，把每个键值对按 RDB 格式序列化写入临时文件，最后原子重命名为正式文件。
- 临时文件的命名带有子进程号（形如 temp-1234.rdb），写盘过程中正式的快照文件不受影响。
- 子进程不监听端口、不处理任何客户端请求，只负责把快照写完整。
- fork 造成的停顿表现为该瞬间的命令排队延迟，fork 返回后积压的命令立刻恢复处理。
- 停顿的绝对时长通常只有几毫秒到几十毫秒，对多数业务无感，但高 QPS 实例的积压会被放大。
- 子进程写完 RDB 文件后退出，父进程通过信号获知结果，并更新保存状态与统计信息。
- 父进程在发起 BGSAVE 时会记录任务信息，供 INFO 命令的 rdb_bgsave_in_progress 等字段对外展示。

> fork 复制的是页表而非数据本身，因此 fork 的耗时与数据总量不成正比，而与页表规模相关；这正是 BGSAVE 能够在单线程 Redis 上不阻塞服务的关键（单线程模型详见第 16 章）。

> 命令处理单线程与持久化多进程并不矛盾：Redis 执行命令始终只有一个主线程，fork 出的子进程只做持久化、不碰客户端请求，二者互不干扰。

**速记**：fork 只**复制页表、共享物理内存**，让子进程**拿着同一份视图**去写盘。



#### 写时复制 COW

**写时复制（Copy-On-Write，COW）**：是 fork 之后父子进程**共享物理内存页**、直到某一方**写入时才真正复制对应页**的机制。

- fork 完成时父子进程的虚拟地址映射到**同一批物理页**，此刻并不产生双倍内存占用。
- 内存管理以**页**为单位（常见页大小 4 KB），复制粒度也是页：改到哪个页就复制哪个页，未触及的页始终共享。
- 父进程收到写命令要修改某个页时，操作系统先把该页**复制一份**给父进程改写，子进程继续持有**旧页**。
- 子进程看到的永远是 **fork 那一瞬间**的数据，写出的 RDB 自然是一个时间点完全一致的快照。
- 快照期间的写操作越少，需要复制的页越少，COW 带来的内存开销就越低。
- 只读命令（GET、HGETALL 等）永远不会触发复制，对 COW 开销没有贡献。
- 一个页哪怕只改动一个字节，也要复制整个页，因此**细碎的高频写**比集中的大块写更容易推高内存。
- 举例：10 GB 的实例在快照期间约 20% 的数据被改写，COW 复制的数据量约为 2 GB，内存峰值即 10 GB 加 2 GB。
- COW 复制由操作系统内存管理自动完成，Redis 无需感知，应用层也没有任何额外代码。

```text
fork 时刻：
父进程 ──┐
         ├── 共享物理页 P1、P2、P3（父子只读共享）
子进程 ──┘

父进程执行写命令修改 P2 后：
父进程 ──→ 复制出的新页 P2（写这份）
子进程 ──→ 原来的页 P2（快照读这份）
```

> COW 正是「不停机拍出一致快照」的根基：不需要暂停服务，靠的是让子进程读旧数据、父进程写新副本。Copy-On-Write 的思想在操作系统的进程与内存管理中被广泛复用，Redis 的 bgsave 是它的经典应用场景。

> 透明大页（THP，Transparent Huge Pages）开启时，页粒度从 4 KB 变为 2 MB，COW 的复制放大效应急剧增加，Linux 部署 Redis 的通用建议是关闭 THP，这一点与 bgsave 直接相关。

**速记**：**读共享、写复制**，子进程永远看 **fork 时刻的旧数据**。



#### fork 耗时与内存翻倍风险

**fork 的代价**：与实例的**内存占用**正相关——大内存实例 fork 更慢，且快照期间可能面临内存**接近翻倍**的压力。

- fork 本身会**短暂阻塞主线程**：复制页表、挂起进程、建立映射，实例越大页表越大，停顿越明显。
- 经验上 10 GB 级别的实例 fork 耗时可达百毫秒级，期间所有请求排队，表现为线上毛刺。
- 若快照期间几乎全部数据都被改写，物理页几乎全部复制，内存占用**最坏接近翻倍**。
- 部署时应**预留足够的内存余量**，避免 COW 触发系统内存不足，进而被 OOM Killer 杀掉进程。
- 虚拟机或容器环境中的 fork 通常比物理机更慢，页表复制受宿主机资源争抢影响明显。
- 内存越接近机器物理上限，COW 触发换页与回收的概率越高，fork 停顿会被进一步放大。
- 磁盘性能不影响 fork 本身的耗时，但影响子进程写盘的时长，间接拉长 COW 高风险窗口。
- 运维上可把手动 BGSAVE 安排在业务低峰期执行，避开写高峰以降低 COW 复制量与停顿影响。
- 内存翻倍风险与实例规模正相关：10 GB 实例最坏多占 10 GB，100 GB 实例最坏多占 100 GB，规模越大规划越要保守。
- 云环境的内存型规格常对突发内存与 fork 行为有限制，选型时应确认平台对 COW 的容忍度。

> [!IMPORTANT]
> **重要内容**：规划大内存实例的 bgsave 必须同时考虑 fork 停顿与内存余量两件事：前者影响请求抖动，后者决定进程生死。内存使用率长期偏高的实例开启快照要格外谨慎，容器环境下更要防止 COW 导致超出限额被强制终止。

> fork 的实际耗时可用 INFO 命令 stats 段中的 latest_fork_usec 字段观测，单位为微秒；该值持续偏大是实例内存过大或宿主机负载过重的直接信号，也是评估是否拆分大实例的依据之一。

**速记**：**实例越大 fork 越慢**，**写得多内存翻倍**，部署必须留余量。



### 自动触发机制

#### save 配置的多条件触发

**save 配置**：定义若干「**在 N 秒内至少发生 M 次修改**就自动执行 BGSAVE」的触发条件，是 RDB 在生产中的默认工作方式。

- 默认配置为三档：save 900 1（900 秒内至少 1 次修改）、save 300 10（300 秒内至少 10 次）、save 60 10000（60 秒内至少 10000 次）。
- 配置可写多行，也可一行写多个条件，格式为 save 秒数 修改次数。
- **多个条件之间是或的关系**：任意一个条件满足就触发 BGSAVE，不要求全部满足。
- 条件命中时执行的就是 BGSAVE，与手动触发的后台快照完全一致。
- 修改越频繁的档位时间窗口越短，多档位设计本质是**兼顾冷数据与热数据**的持久化节奏。
- 条件可通过 CONFIG SET save 动态修改，无需重启即可调整快照节奏。
- 已有 BGSAVE 在执行时，即使条件命中也不会重复触发，等这次快照结束后再重新判断。
- 条件判定的秒数窗口以 lastsave 为起点滚动计算，而非固定整点，快照间隔因此是「距上次成功保存」的实际间隔。
- 判定发生在 serverCron 中，精度为 100 毫秒级。

```text
save 条件的判定逻辑（serverCron 每 100 毫秒执行一轮）：

for each (seconds, changes) in 快照条件列表:
    if 当前时间 - lastsave >= seconds 且 dirty >= changes:
        触发 BGSAVE
```

```bash
# redis.conf 默认快照条件，命中任意一条即触发 BGSAVE
save 900 1
save 300 10
save 60 10000
```

```bash
# 关闭自动快照：传入空串即可
CONFIG SET save ""
```

```bash
# 自定义快照节奏示例：7200 秒内 100 次修改触发
CONFIG SET save "7200 100"
```

> 「或」关系是常见考点：900 秒改 1 个键与 60 秒改 10000 个键，只要**任一条件**成立就拍快照；逐条比对判断的是「每个条件自身是否满足」，而非「所有条件同时满足」。

> 关闭自动快照（save 配置为空串）后，RDB 只会因手动 BGSAVE 或 SHUTDOWN、全量复制等场景触发，同时也省去了周期性 fork 的开销；纯缓存场景可用此方式换取更平稳的延迟。

**速记**：save 条件是**秒数加次数**，多条件**任一命中即触发**。



#### dirty 计数与 lastsave 时间

**dirty 计数与 lastsave**：是支撑 save 条件判断的两个内部状态——前者记录**上次成功保存后发生了多少次修改**，后者记录**上次成功保存的 Unix 时间戳**。

- 每执行一次修改数据的命令，dirty 计数按改动累加，改动几个键就加几。
- 每次成功完成 SAVE 或 BGSAVE，dirty 计数**清零**，lastsave 更新为当前时间。
- 周期性任务 serverCron（默认每 100 毫秒执行一次，详见第 16 章）遍历全部 save 条件，用 dirty 与 lastsave 逐条比对，命中即触发 BGSAVE。
- 条件「900 秒内改 1 次」翻译过来就是「当前时间减 lastsave 超过 900，且 dirty 不小于 1」。
- dirty 计数与 lastsave 都保存在服务器状态结构中，随服务运行持续更新，不依赖配置项。
- 客户端可用 LASTSAVE 命令直接读取 lastsave 对应的时间戳。
- dirty 累加的是改动键数：一条 MSET 同时改 5 个键，dirty 就加 5。
- 快照失败时 lastsave 不更新、dirty 不清零，条件会在后续轮次继续尝试触发。
- LASTSAVE 在监控中的典型用法：当前时间戳减去 LASTSAVE 的结果长期大于快照间隔，说明快照已经落后，需要排查。

```bash
LASTSAVE
```

```text
1715000000
```

> dirty 与 lastsave 是 save 条件的**判断原料**：INFO 中的 rdb_changes_since_last_save 正是 dirty 的对外呈现，rdb_last_save_time 则对应 lastsave，二者都可用于外部监控快照是否按时执行。

> BGSAVE 进行期间 dirty 不会暂停累计：快照只覆盖 fork 时刻的数据，快照落地后新产生的修改继续计入 dirty，等待下一轮条件判断。

**速记**：dirty 数**改了几次**，lastsave 记**上次保存时刻**，serverCron **每 100 毫秒比对一次**。



#### shutdown 与主从全量复制的触发

**save 条件之外的触发场景**：执行 SHUTDOWN 关闭命令与主从**全量复制**开始时，Redis 也会主动发起 RDB 保存。

- 客户端执行 SHUTDOWN 时，若配置了至少一个 save 条件，Redis 会**先执行一次阻塞式保存再退出**，保证落盘数据尽量新。
- SHUTDOWN NOSAVE 可跳过这次保存直接关闭，用于明确不需要落盘的场合。
- SHUTDOWN SAVE 则显式要求关闭前必须保存，无论 save 条件如何配置。
- 收到操作系统的 SIGTERM 信号时，Redis 的处理与 SHUTDOWN 类似：先尝试保存快照再退出，保证正常停机不丢已确认的数据。
- 主从复制进行**全量同步**时，主节点会执行 BGSAVE 生成 RDB 文件并发送给从节点，作为从节点重建数据的底版（详见第 20 章）。
- 这两类触发与 save 条件无关，属于特定操作**附带**的快照行为。
- 全量复制期间的快照与周期性快照共用同一套 fork 加 COW 机制，内存压力的影响完全相同。
- 关闭前保存若失败，Redis 仍会退出，日志中留有保存失败的记录，重启后数据停在更早的那次快照。

> 全量复制选择 RDB 而不是逐条转发写命令做初次同步，看中的正是 RDB 体积小、传输快、加载快：从节点收到快照后载入即可进入工作状态，增量部分再靠命令传播补齐。

> 进程崩溃或被 SIGKILL 强杀时**不会触发任何保存**：先保存后退出只在正常关闭流程中出现，异常宕机留下的就是最近一次快照，这也是丢失窗口存在的根源。

**速记**：**SHUTDOWN 先存后关**，**全量复制先拍快照再传输**，**异常宕机不保存**。



### RDB 相关配置项

#### rdbcompression 与 rdbchecksum

**rdbcompression 与 rdbchecksum**：是控制 RDB 文件**是否压缩**与**是否校验**的两个开关，默认均为 yes。

- rdbcompression：对字符串对象使用 **LZF 算法**压缩后写入文件，默认开启，能显著减小文件体积，代价是少量 CPU 消耗。
- rdbchecksum：在文件末尾写入 **CRC64 校验和**，载入时验证文件完整性，默认开启，约带来 10% 左右的性能损耗。
- 关闭 rdbchecksum 后文件末尾的校验和写 0，载入时**跳过校验**，速度略快但失去了发现文件损坏的能力。
- 两个开关只影响**新写入**的 RDB 文件，改动配置对已生成的旧文件不生效。
- 两个开关同样作用于全量复制时生成的传输用 RDB，压缩开启能降低主从间的带宽占用。
- CPU 资源紧张而磁盘宽裕的机器可以选择关闭压缩，用文件体积换取更低的写盘 CPU 开销。
- LZF 压缩只作用于字符串对象，列表、集合等容器数据按其编码原样写入，不做二次压缩。
- 载入时若校验和不匹配，Redis 会报错并拒绝载入该文件，宁可启动失败也不引入坏数据；不会跳过坏块继续恢复。

```bash
CONFIG GET rdbcompression
CONFIG GET rdbchecksum
```

```text
1) "rdbcompression"
2) "yes"
1) "rdbchecksum"
2) "yes"
```

> 校验和的价值在**落盘与传输之后**：文件在拷贝、上传、跨机房同步中任何一处损坏，载入时都能被发现并拒绝，避免把坏数据恢复进内存造成更大范围的污染。

**速记**：rdbcompression 管**压不压**，rdbchecksum 管**验不验**，默认**双开**。



#### 核心配置与配置示例

**RDB 的核心配置**集中在 redis.conf 中，由**触发条件、文件名、存放目录、失败保护、压缩与校验开关**组成。

```bash
# 触发条件：命中任意一条即执行 BGSAVE
save 900 1
save 300 10
save 60 10000

# RDB 文件名与存放目录，dir 指定的目录必须真实存在且可写
dbfilename dump.rdb
dir /var/lib/redis

# 字符串对象以 LZF 算法压缩后写入
rdbcompression yes

# 文件末尾写入 CRC64 校验和，载入时验证完整性
rdbchecksum yes
```

- dbfilename 只定义**文件名**，落盘位置由 dir 决定，二者共同确定 RDB 文件的完整路径。
- 修改配置后可用 CONFIG SET 即时生效，也可写入配置文件等待重启加载。
- CONFIG REWRITE 会把运行中通过 CONFIG SET 做出的修改写回配置文件，避免重启后丢失。
- 执行定时备份时，先确认 dir 指向的目录，再复制其中的 RDB 文件即可获得某一时刻的数据副本。
- 迁移实例时直接把 RDB 文件复制到目标机器的对应目录并重启，是恢复数据最直接的方式。
- 单机多实例部署时，各实例必须配置**不同的 dir 或 dbfilename**，否则快照文件会互相覆盖。
- dir 必须使用绝对路径；目录不存在或不可写时快照会失败，且只能从日志中发现。
- 磁盘写满是快照失败的常见原因，容量监控要同时覆盖内存与磁盘两个维度。

```bash
# crontab 示例：每小时把当前快照复制到备份目录并带上时间戳
0 * * * * cp /var/lib/redis/dump.rdb /backup/dump-$(date +\%H).rdb
```

```text
用 RDB 文件恢复实例的完整步骤：

1. 准备一台安装好 Redis 的目标机器
2. 把备份的 dump.rdb 放入目标实例的 dir 目录
3. 确认 dbfilename 与文件名一致
4. 启动 Redis，等待日志输出载入完成
```

> dbfilename 与 dir 是运维最常打交道的两个配置：备份脚本、恢复流程、跨机迁移全都围绕这两个路径展开，dir 配错会让快照静默写到别处，排查时先查它。

**速记**：**dbfilename 定名、dir 定位**，加上**条件与开关**就是 RDB 配置的全貌。



### RDB 文件结构与载入

#### RDB 文件结构概览

**RDB 文件结构**：由**固定的头部、中间的数据库数据与固定的尾部**串联而成的二进制格式，各段依次排列。

```text
REDIS        ← 5 字节魔数，标识这是一个 RDB 文件
00xx         ← 4 字符版本号，如 0009
辅助字段      ← redis-ver、redis-bits、used-mem 等元信息
SELECTDB 0   ← 选择 0 号数据库
键值对……     ← 过期时间、编码类型、键、值逐对排列
SELECTDB 1   ← 选择 1 号数据库
键值对……
EOF          ← 结束操作码，标识数据区结束
校验和        ← 8 字节 CRC64，rdbchecksum 开启时写入
```

- **REDIS 魔数**：文件最开头 5 个字节恒为字符串 REDIS，用于快速识别文件类型。
- **版本号**：紧随其后的 4 个字符记录 RDB 格式版本，便于高版本 Redis 识别并兼容旧格式文件。
- **辅助字段**：以键值对形式记录生成文件时的元信息，便于排查问题。
- **SELECTDB 与数据库数据**：每个数据库前有一个 SELECTDB 操作码标识库号，其后是该库的全部键值对。
- **键值对内部**：带过期时间的键先记录过期时间戳（0xFD 开头精确到秒、0xFC 开头精确到毫秒），随后是编码类型、键、值。
- **EOF 与校验和**：文件以 EOF 操作码收尾，末尾 8 字节为 CRC64 校验和。

```text
辅助字段的典型内容（键值以冒号分隔）：

redis-ver:7.2.4
redis-bits:64
ctime:1715000000
used-mem:104857600
aof-preamble:0
```

```text
文件开头十六进制示意（前 9 字节）：

52 45 44 49 53 30 30 30 39 → 即 REDIS0009
```

> 整个文件是一串**带类型的序列化记录**，解析器按操作码逐段推进；头部与尾部结构固定，中间数据区的长度完全由数据量决定，因此 RDB 文件没有固定大小。

> 自带工具 redis-check-rdb 可以离线检查一个 RDB 文件的完整性与统计信息，怀疑备份文件损坏时先跑它，不必冒然载入到线上实例。

**速记**：**头部（魔数＋版本号）＋数据区（各库键值对）＋尾部（EOF＋校验和）**。



#### RDB 的载入时机与阻塞

**RDB 的载入**：在**服务器启动时自动进行**——Redis 检测到 RDB 文件存在就把它读回内存，载入期间**处于阻塞状态**、不对外服务。

- 启动时 Redis 按配置的 dir 与 dbfilename 寻找 RDB 文件，找到即开始载入。
- 载入由主线程完成，期间忙于读文件、重建键空间，**拒绝处理任何客户端命令**。
- rdbchecksum 开启时载入过程中会**校验文件完整性**，校验失败则启动失败并报错，防止坏数据进入内存。
- 载入进度会写入启动日志，INFO 命令也能在载入期间读到 loading 相关进度字段。
- 载入时对**已经过期的键直接丢弃**：文件里记录的过期时间若早于当前时间，该键不会恢复进内存。
- 载入完成时日志输出 DB loaded from disk，随后才进入正常服务状态。
- 载入完成后 rdb_last_save_time 即该快照文件的生成时刻，可据此判断恢复出的数据有多新。
- 大实例的载入可能持续数十秒甚至分钟级，容量规划与故障演练时要计入重启时间。
- 若 AOF 同时开启，Redis **优先载入 AOF**，因为 AOF 记录的写入通常比最近一次快照更完整；载入顺序的细节详见第 19 章。

```text
载入期间 INFO 命令可观测的进度字段（persistence 段）：

loading:1
loading_total_bytes:104857600
loading_loaded_bytes:52428800
loading_start_time:1715000500
```

> RDB 文件只会被整体读入、被新文件原子替换，**不存在往旧文件里追加数据**的操作：每次快照都是生成新文件后重命名替换旧文件，这既保证了文件随时可用，也是它结构简单、恢复快的原因。

**速记**：**启动自动载入、载入期间阻塞**，AOF 与 RDB 并存时 **AOF 优先**。



### RDB 的优缺点与观测

#### RDB 的优点

**RDB 的优点**：文件紧凑、恢复迅速、生成过程不阻塞主线程，三者共同构成它在备份容灾场景的核心竞争力。

- **文件紧凑**：二进制加压缩，单个文件即某时刻的全量数据，适合定时备份、异地容灾与跨机迁移。
- **恢复速度快**：载入时直接重建内存数据，比分秒级重放写命令的 AOF 快得多（详见第 18 章）。
- **不阻塞主线程**：BGSAVE 由子进程完成，主线程除 fork 瞬间外持续服务，对线上请求影响小。
- **对父进程性能友好**：快照的磁盘 IO 与 CPU 开销全部发生在子进程中，主进程不参与写盘。
- **单文件易管理**：一个文件就是一个完整数据集，下载、上传、加密、归档都只处理这一个文件。
- **容灾演练简单**：把备份文件放到一台空实例的目录里启动，即可验证备份的可恢复性。
- **恢复流程无需人工干预**：校验和兜底、启动自动载入，不存在像日志断点那样需要人工修复的中间状态。
- **文件小对网络友好**：异地同步、跨机房容灾的传输成本在两种持久化方式中最低。
- **生成时机可预期**：快照节奏由配置显式定义，IO 峰值可以提前规划，不随写流量水涨船高。

> 对「能接受丢失最近几分钟数据」的业务，RDB 是性价比最高的方案：一个文件、一条定时备份策略（例如 cron 定时把 dump.rdb 同步到远程存储），就能构建起基本的容灾能力。

> 版本兼容方面，高版本 Redis 能载入旧版本生成的 RDB 文件，反向则不保证成立：回滚降级前先确认旧版本能否读新版本写出的文件。

**速记**：**紧凑、快恢复、不阻塞**，备份容灾的首选。



#### RDB 的缺点

**RDB 的缺点**：两次快照之间的数据存在丢失窗口，且 fork 带来停顿与内存压力，这些是无法靠调参彻底消除的固有代价。

- **数据丢失窗口**：快照是定时执行的，距上次快照之后的写入若遇宕机会全部丢失，丢失量最长等于快照间隔。
- **fork 停顿**：每次 BGSAVE 都伴随一次 fork，大内存实例的停顿可能达到百毫秒级，造成请求毛刺。
- **内存压力**：COW 在写入活跃时复制物理页，极端情况下内存占用接近翻倍。
- **时效性差**：RDB 无法表达「最近一次快照之后」的数据变化，恢复出的状态天然落后于故障时刻。
- 快照越频繁丢失越少，但 fork 与磁盘 IO 的开销也随之变频繁，**两头无法兼得**。
- 写入量突发上涨时，最短档位（如 60 秒 10000 次）可能连续命中，快照一波接一波执行，fork 与 COW 开销叠加。
- 对延迟敏感的业务，周期性 fork 造成的毛刺需要在容量规划与监控阈值中提前考虑。
- 恢复出的数据不含最近修改，依赖强一致的业务需自备补偿手段，例如重启后重新对账。

> [!WARNING]
> **警告内容**：对数据可靠性要求高、几乎不能丢写的业务，仅靠 RDB 是不够的——调小 save 间隔只能缩小而不能消灭丢失窗口，这类场景应改用或叠加 AOF（详见第 18 章），或在应用层另做持久化。

**速记**：**间隔内的数据会丢、fork 有停顿、内存有压力**，可靠敏感场景别单押 RDB。



#### bgsave 期间的新写命令与快照视图

**bgsave 期间的新写命令不会进入本次快照**：快照记录的是 fork 时刻的数据视图，之后发生的修改只属于下一次快照。

- 子进程基于 **fork 时刻的内存视图**写文件，父进程后续执行的写命令对子进程不可见。
- 写命令照常执行并修改父进程内存，改动通过 COW 落在**新复制的物理页**上，不影响子进程正在读的旧页。
- 因此本次 RDB 是一个**时间点完全一致**的旧视图，新数据由下一次 BGSAVE 收录。
- 期间读命令读到的仍是**最新数据**，线上数据与快照内容从 fork 时刻起分道扬镳。
- 多次快照之间的命令执行顺序不会体现在文件里，文件表达的只有**状态**而非**过程**。
- 一次 bgsave 持续得越久，「文件内容与线上数据的差距」拉得越大，下一轮 COW 的候选页也越多。
- DEL、EXPIRE 等一切修改性命令都遵循同一规则：改动只发生在父进程内存，不会回写进本次快照。

```text
t0  执行 BGSAVE，fork 子进程，此刻内存为 { a:1, b:2 }
t1  客户端执行 SET c 3，父进程内存变为 { a:1, b:2, c:3 }
t2  子进程写完文件退出，文件内容仍是 { a:1, b:2 }
t3  下一次 BGSAVE 才会把 c 收录进快照
```

> bgsave 期间父进程的写入越多，COW 复制的页越多，内存增长越明显——「新写命令不影响快照正确性，但会推高通快照成本」是理解 COW 开销的关键一句。

> 从备份角度看「内容偏旧」反而是优点：文件表达的是一个自洽的时间点状态，不存在半新半旧的中间态，用于恢复与审计都更可靠。

**速记**：快照是 **fork 时刻的旧照片**，期间的新写**进下次快照**。



#### INFO 与 debug 的观测点

**RDB 的运行状态可从 INFO 命令的 persistence 段直接观测**，配合 LASTSAVE 与 DEBUG SLEEP 可覆盖大多数排查场景。

- rdb_last_bgsave_status：**最近一次 BGSAVE 的结果**，ok 表示成功、err 表示失败，是告警最常用的字段。
- rdb_last_save_time：**最近一次成功保存的 Unix 时间戳**，用当前时间减它即可估算距上次快照过去了多久。
- rdb_changes_since_last_save：**自上次保存以来的修改次数**，即 dirty 计数的对外呈现。
- rdb_bgsave_in_progress：**当前是否正在进行 BGSAVE**，值为 1 表示子进程仍在写盘。
- rdb_last_bgsave_time_sec 与 rdb_current_fork_perc：分别反映上次快照的耗时与当前 fork 的进度百分比。
- rdb_last_cow_size：**上次 BGSAVE 期间 COW 复制的内存量**，用于量化快照对内存的真实影响。
- LASTSAVE 命令单独返回最近一次成功保存的时间戳；DEBUG SLEEP 可让服务器睡眠指定的秒数，用于模拟阻塞、观察客户端表现。
- INFO 命令 stats 段中的 latest_fork_usec 记录最近一次 fork 的耗时（微秒），是评估 fork 停顿的核心指标。
- 推荐排查顺序：先看 rdb_last_bgsave_status 定性成败，再用当前时间减 rdb_last_save_time 看新鲜度，最后结合 in_progress 与 fork 耗时定位进行中的问题。

```bash
INFO persistence   # 查看 rdb_last_bgsave_status、rdb_last_save_time 等字段
INFO stats         # 查看 latest_fork_usec 等统计
LASTSAVE           # 返回最近一次成功保存的 Unix 时间戳
DEBUG SLEEP 3      # 让服务器阻塞 3 秒，仅用于测试环境验证
```

```text
# Persistence
loading:0
rdb_changes_since_last_save:12
rdb_bgsave_in_progress:0
rdb_last_save_time:1715000000
rdb_last_bgsave_status:ok
rdb_last_bgsave_time_sec:1
rdb_last_cow_size:31457280
```

> DEBUG 命令在较新版本中默认禁用，需将 enable-debug-command 配置打开才能使用，且只应在测试环境使用，切勿在生产执行。

> [!TIP]
> **建议内容**：把 rdb_last_bgsave_status 与 rdb_changes_since_last_save 接入监控告警——前者非 ok 说明快照连续失败、容灾能力已经失效，后者长期居高不下说明快照迟迟没有执行，二者组合能提前暴露大多数 RDB 故障。

**速记**：盯住 **status、save_time、changes** 三个字段，LASTSAVE 查时刻，DEBUG SLEEP 模拟阻塞。
