## 事务与 Lua 脚本

**事务与 Lua 脚本**：是 Redis 提供**多条命令原子执行**的两条路径——事务以 MULTI 与 EXEC 为核心，把一组命令打包后一次性按序执行，配合 WATCH 提供乐观锁；Lua 脚本以 EVAL 为入口，把一段服务端代码整体作为单条命令执行，真正解决“读后写”的原子逻辑。

- 先讲事务的基本机制：MULTI、EXEC、DISCARD 的完整流程，以及隔离性、原子性的真实定位。
- 再讲错误模型：入队错误与执行错误的两种情形，以及 Redis 不支持回滚的官方理由。
- 然后是 WATCH 乐观锁：CAS 语义、重试循环，以及与 MySQL 事务的逐项对比。
- 后半章进入 Lua：EVAL 语法、KEYS 与 ARGV 规范、EVALSHA 与脚本缓存、错误处理与超时救援。
- 最后收敛到选型与演进：事务、WATCH、Lua 三者的分工，以及 Redis 7.0 Functions 的函数库实践。

### 事务的基本机制

#### Redis 事务的定义与定位

**Redis 事务**：是把多条命令打包、**一次性、按顺序、不带中断**地执行的机制，以 **MULTI** 开启、**EXEC** 提交。

- 事务提供的是**打包执行**能力：命令先进入队列，EXEC 触发时统一执行。
- 事务保证**顺序性**：队列中的命令按入队顺序执行，不会被其他客户端的命令插队。
- 事务**不保证原子性**：某条命令执行失败，其余命令照常执行，不存在回滚。
- 事务队列保存在客户端连接对象中：连接断开而 EXEC 尚未执行时，队列随之丢弃，事务自然消失。
- 事务里只能使用普通命令，MULTI 之后不能再嵌套 WATCH 以外的事务控制命令。
- 与 pipeline 的区别：pipeline 只是把命令缓冲后一次发送，服务端仍逐条独立执行，不提供任何事务语义；事务则由服务端保证打包与顺序。
- EXEC 的返回结果与队列一一对应：每条命令各自的回复按入队顺序排列，便于逐条核对执行结果。
- 定位上，Redis 事务更接近**命令批处理**，而非数据库意义上的完整事务。

> Redis 官方文档对事务执行过程的描述是：事务运行期间，服务端不会插入执行其他客户端的命令；但事务中的某条命令失败并不会导致整个事务回滚。把它当 MySQL 事务用，是最常见的认知错位。

**速记**：一次打包、按序执行、**失败不回滚**。



#### MULTI、EXEC 与 DISCARD 的完整流程

**事务的三个核心命令**：**MULTI** 开启事务块，**EXEC** 执行队列中全部命令，**DISCARD** 清空队列并放弃事务。

- MULTI 执行后客户端进入事务状态，后续命令不再立即执行，而是返回 QUEUED 并进入队列。
- 入队阶段只做命令存在性与参数个数的检查，真正的执行发生在 EXEC。
- EXEC 按入队顺序执行全部命令，并以数组形式返回每条命令各自的结果。
- DISCARD 清空事务队列并退出事务状态，队列中的命令一条也不会执行。
- 事务状态内重复执行 MULTI 会收到嵌套错误，事务不可嵌套。
- 入队后悔不必等到 EXEC：DISCARD 随时可放弃，这也是入队阶段唯一的撤销手段。

```bash
MULTI
SET order:id 1001
INCR order:count
EXEC
```

```text
OK
QUEUED
QUEUED
1) OK
2) (integer) 1
```

```bash
# 含执行错误时，EXEC 的数组按位置保留错误，不中断其余结果
SET counter hello
MULTI
INCR counter
SET msg done
EXEC
```

```text
1) (error) WRONGTYPE Operation against a key holding the wrong kind of value
2) OK
```

```bash
MULTI
SET order:id 1001
DISCARD
```

```text
OK
QUEUED
OK
```

> EXEC 与 DISCARD 都会结束事务状态：前者提交、后者放弃。EXEC 返回的数组元素与队列中的命令一一对应，即使某条命令执行失败，其错误也会占据数组中对应的位置；DISCARD 则永远只回复一个 OK，队列原地清空。

**速记**：MULTI 进队、EXEC 收口、DISCARD 撤单。



#### 事务的隔离性与原子性辨析

**事务的隔离性与原子性**：Redis 事务**具备隔离性**，但**原子性不完整**——这是它区别于 MySQL 事务的核心定位。

- 隔离性：EXEC 执行期间单线程独占，队列命令连续执行完，中间不会插入其他客户端的命令（单线程模型详见第 16 章）。
- 原子性不完整：队列中某条命令运行时报错，报错命令被跳过，其余命令照常生效。
- 持久性无独立保障：是否落盘取决于 RDB 与 AOF 的配置（详见第 17、18 章）。
- 不存在隔离级别的概念，脏读、幻读等讨论在此没有前提。
- 隔离性来自单线程这一实现事实，而非并发控制协议，因此也没有可调的隔离选项。
- 隔离性对 Lua 脚本同样成立：脚本执行期间其他客户端的命令同样无法插入。

> 「一次性、按顺序、不带中断地执行」是官方对事务的完整描述：三个词分别对应打包、排队、不回滚三层含义，回答事务相关问题时三个词要一起说全。

**速记**：事务**有隔离、原子性不完整**，更无隔离级别。



### 事务中的错误处理

#### 入队错误与执行错误的两种情形

**事务中的错误分两种**：**入队错误**发生在命令进队列时，EXEC 会整体放弃事务；**执行错误**发生在命令真正运行时，报错命令被跳过，其余命令照常执行。

- 入队错误的典型：命令名拼写错误、参数个数不对，入队阶段的检查即可发现。
- 入队错误后果：队列中只要存在任一条入队失败的命令，EXEC 直接返回错误并放弃整个事务，所有命令一条都不执行。
- 执行错误的典型：对持有 String 的 key 执行 List 命令，触发 WRONGTYPE，入队阶段无法发现。
- 执行错误后果：Redis 跳过出错命令，继续执行后续命令，已执行的部分不回滚。

```bash
MULTI
SET k1 v1
INCR k1 extra
EXEC
```

```text
OK
QUEUED
(error) ERR wrong number of arguments for 'incr' command
(error) EXECABORT Transaction discarded because of previous errors.
```

```bash
SET counter hello
MULTI
INCR counter
SET msg done
EXEC
```

```text
1) (error) WRONGTYPE Operation against a key holding the wrong kind of value
2) OK
```

> 两种错误的分界线是「能否在入队时发现」：命令拼写、参数个数属于语法层，入队即查；类型不匹配属于数据层，只有真正执行时才暴露。前者放弃整个事务，后者只牺牲出错的那一条。

> [!CAUTION]
> **注意内容**：执行错误不回滚意味着「一半生效」的事务状态是可能存在的。业务上不能指望事务兜底数据类型，应把类型约束放在应用层校验，或改用 Lua 脚本在写之前先做判断（见后文 redis.call 与 redis.pcall 的区别）。

**速记**：入队错**整体放弃**，执行错**只跳出错的那条**。



#### Redis 不支持回滚的两个官方理由

**Redis 不支持回滚**：官方文档给出的核心理由是**支持回滚会显著影响 Redis 的简洁与速度**——事务失败源于编程错误，开发期就应发现并修复，运行时回滚既救不了逻辑，也拖累实现。

- 官方原文的表述：支持回滚会对 Redis 的简洁与性能造成显著影响（significant impact on the simplicity and performance of Redis）。
- 理由一：事务中的运行时错误（如类型不匹配）源于**编程错误**，这类问题应在开发与测试阶段捕获，生产环境不应依赖数据库回滚兜底。
- 理由二：回滚救不了已经写错的**业务逻辑**——即便数据改动被撤销，错误的逻辑本身不会因此变对。
- 附带收益：无需回滚日志与撤销操作，事务执行路径保持极简，运行时几乎零开销。
- 官方的态度明确：因为出错即程序缺陷，不回滚不影响事务语义的正确使用。
- 实践含义：写操作一旦执行就无法撤销，关键数据变更应设计幂等或补偿逻辑兜底。
- 测试含义：入队错误应在开发期被单元测试覆盖，上线后出现的 EXECABORT 即测试缺口的信号。
- 入队错误对应的 EXECABORT 错误自 Redis 2.6.5 起引入，在此之前的版本会跳过出错命令继续执行。

> 这两个理由是高频面试题，一言以蔽之——语法错误挡在入队，运行错误视为 bug；回滚既救不了 bug，也拖慢执行，于是干脆不做。

**速记**：**语法错可先测、回滚救不了逻辑**，故不做回滚。



### WATCH 与乐观锁

#### WATCH 乐观锁与 CAS 机制

**WATCH 乐观锁**：对若干 key 加**监视**，配合 EXEC 实现**检查再设置（CAS，Compare-And-Set）**语义的机制。

- WATCH 在 EXEC 之前调用，服务端记录被监视 key 的当前状态。
- 若在 WATCH 之后、EXEC 之前，被监视的 key 被任何其他客户端修改，EXEC 返回 nil，整个事务不执行。
- 修改包括写入、删除、过期驱逐等一切改变 key 值或存在性的行为。
- EXEC 无论成败都会清除本次全部监视；UNWATCH 可在未开启事务时显式取消监视。
- WATCH 允许在 MULTI 之后、EXEC 之前调用，监视同样生效。
- 监视大量 key 会带来内存与检查开销，监视范围应保持克制。
- 监视不存在的 key 同样有效：若执行期间该 key 被其他客户端创建，EXEC 照样返回 nil。
- 监视粒度是 key 级而非字段级：Hash 中一个字段被改，整个 key 视为被修改。

```bash
WATCH stock:1001
GET stock:1001
MULTI
DECR stock:1001
EXEC
```

```bash
# 另一客户端在 EXEC 之前执行了：SET stock:1001 8
WATCH stock:1001
MULTI
DECR stock:1001
EXEC
```

```text
(nil)
```

```bash
# 值不满足预期，直接放弃监视即可，无需进入事务
UNWATCH
```

> EXEC 返回 nil 代表事务整体未执行，队列里的命令一条都没跑；这与执行错误的「部分执行」完全不同。nil 是 WATCH 唯一的失败信号，客户端据此决定重试或放弃。

**速记**：WATCH 盯住、EXEC 校验——**被改过就 nil**。



#### WATCH 重试循环示例

**WATCH 的标准用法**：监视、读取、判断、入队、EXEC，EXEC 返回 nil 就**回到读取重来**，构成乐观锁重试循环。

- 读取动作在 WATCH 之后、MULTI 之前进行，读到的是监视生效后的最新值。
- 判断逻辑在客户端完成：值不满足条件时可以不入队，直接 UNWATCH 放弃。
- 并发冲突少时一次成功；冲突激烈时重试次数上升，需设置重试上限或退避间隔。
- 每轮重试的 WATCH、GET、MULTI、EXEC 都是完整往返，冲突率高时客户端压力显著，此时应转向 Lua 脚本。
- Lua 版本不需要重试：脚本在服务端单线程内一次跑完，天然不存在中途被改的竞态窗口。
- 该模式在分布式锁出现之前，是 Redis 官方推荐的并发修正手段（分布式锁详见第 27 章）。

```bash
# 伪代码：扣减库存的乐观锁循环
loop:
  WATCH stock:1001
  remain = GET stock:1001
  if remain <= 0:
    UNWATCH
    break
  MULTI
  DECR stock:1001
  result = EXEC
  if result == nil:
    goto loop
```

> 重试循环也可以直接换成 Lua 脚本：把读、判、写收敛进一次服务端原子执行，省掉冲突重试的多次网络往返，这也是高并发场景更常见的选择。

**速记**：**看、读、判、写**四步，nil 就重来。



#### Redis 事务与 MySQL 事务逐项对比

**对比结论**：Redis 事务与 MySQL 事务同名不同物——Redis **无完整 ACID、无隔离级别、无回滚**，仅提供打包顺序执行与 WATCH 乐观锁。

- 原子性：**MySQL** 全成或全败、可回滚；**Redis** 打包执行但不保证全成，无撤销机制。
- 隔离性：MySQL 提供四种隔离级别可选；Redis 靠单线程执行事务天然串行，无级别概念。
- 持久性：MySQL 由存储引擎与日志保证；Redis 取决于 RDB 与 AOF 配置（详见第 17 至 19 章）。
- 一致性：MySQL 由约束与事务共同维护；Redis 无约束体系，一致性完全依赖应用层设计。
- 并发控制：MySQL 靠锁与 MVCC；Redis 靠 WATCH 乐观锁，冲突时客户端重试。
- 命令对应：MySQL 的 BEGIN 与 COMMIT 大致对应 MULTI 与 EXEC，但语义强弱完全不同；MySQL 还有 ROLLBACK，Redis 没有任何对应物。
- 使用建议：需要强一致与回滚的场景不要硬套 Redis 事务，应落到关系库，或借助应用层补偿逻辑。
- 误用代价：指望事务回滚保证数据一致的设计，在 Redis 上会出现半生效状态，且难以排查。

> WATCH 与 MySQL 乐观锁的辨析：两者都是「读时记版本、写时验版本、验不过即放弃」的思路；差别在于 MySQL 靠版本号字段并由 SQL 判断影响行数，WATCH 由服务端自动检测 key 变化并以 EXEC 返回 nil 表达失败，业务代码无需维护版本列。

**速记**：Redis 事务是**打包批执行加乐观锁**，不是缩小版 MySQL 事务。



### Lua 脚本基础

#### Lua 脚本的引入理由

**Lua 脚本引入的理由**：事务只能打包已有命令，解决不了**先读后写**的原子逻辑——读到值、按值判断、再写回，三步必须收敛在一次不可分割的执行里。

- 典型场景：库存判断后再扣减、限流计数后再放行、校验锁持有者后再释放（详见第 27 章）。
- 用 WATCH 也能实现，但需要客户端多轮往返并在冲突时重试，网络开销与失败率都高。
- Lua 脚本把读、判、写收敛为服务端一次执行，天然原子，且能根据判断结果分支处理。
- 代码组织：脚本源码应随业务代码入库做版本管理，而非散落在调用点，摘要变化才可控。
- 附带收益：多条命令一次往返完成，脚本同时起到节省网络 RTT 的作用。
- 脚本内几乎可以使用全部 Redis 命令，能力与普通命令完全一致。
- 脚本以 return 的值作为整次调用的回复，中途各命令的结果不会自动返回给客户端。
- Redis 2.6 起内置 Lua 解释器，EVAL 命令是脚本执行的入口。

> 脚本执行期间单线程独占，效果上等价于一个不可拆分的复合命令；这正是事务做不到、WATCH 做得费劲的那一层原子性，也是 Lua 在 Redis 中不可替代的位置。

**速记**：事务**包命令**，Lua **包逻辑**。



#### EVAL 命令语法

**EVAL 命令签名**：EVAL script numkeys key [key ...] arg [arg ...]，依次为脚本源码、key 参数个数、key 数组与附加参数数组。

- numkeys 声明其后多少个参数属于 key，剩余参数全部进入 ARGV。
- numkeys 传错会导致 KEYS 与 ARGV 错位，脚本读到的数据全部串位，是脚本调试的高频错误。
- 脚本内通过 KEYS 数组按数字下标访问 key，通过 ARGV 数组访问附加参数，下标从 1 开始。
- 脚本的返回值经 Redis 转换后作为命令回复返回；脚本不写 return 时回复为空。
- 脚本以字符串形式随命令传输，源码较长时应改为服务端缓存（见下文 EVALSHA 与脚本缓存）。

```bash
EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 greeting hello
GET greeting
```

```text
OK
"hello"
```

```bash
# 观察参数如何被 numkeys 切分：前 2 个进 KEYS，其余进 ARGV
EVAL "return {KEYS[1], KEYS[2], ARGV[1], ARGV[2]}" 2 user:1001 name qinxiao extra
```

```text
1) "user:1001"
2) "name"
3) "qinxiao"
4) "extra"
```

```bash
EVAL "redis.call('HSET', KEYS[1], ARGV[1], ARGV[2]) return redis.call('HGET', KEYS[1], ARGV[1])" 1 user:1001 name qinxiao
```

```text
"qinxiao"
```

```bash
SET account:a 100
SET account:b 0
EVAL "if tonumber(redis.call('GET', KEYS[1])) >= tonumber(ARGV[1]) then redis.call('DECRBY', KEYS[1], ARGV[1]) redis.call('INCRBY', KEYS[2], ARGV[1]) return 'ok' else return 'insufficient' end" 2 account:a account:b 30
```

```text
"ok"
```

```lua
-- 按当前值分支更新：读、判、写一步完成
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current < tonumber(ARGV[1]) then
  return redis.call('SET', KEYS[1], ARGV[1])
end
return false
```

> EVAL 每次都要把完整脚本传给服务端，脚本较长时网络开销明显；生产环境应配合后文的 EVALSHA 使用，这也是各客户端库的默认做法。

**速记**：**脚本、numkeys、KEYS、ARGV** 四段式记忆签名。



#### KEYS 与 ARGV 的使用规范

**KEYS 与 ARGV 的规范**：key 一律经 KEYS 数组传入、业务数据一律经 ARGV 传入，**集群模式下脚本只能访问 KEYS 中声明的 key**。

- 集群按 KEYS 数组计算 hash slot，据此决定脚本被路由到哪个节点。
- 脚本内部写死 key 或访问 KEYS 之外的 key，会造成跨槽访问，集群直接报错（详见第 22 章）。
- 脚本要操作的多个 key 必须落在同一个槽，否则任何路由方式都无法满足。
- 多 key 无法同槽时，可借助 hash tag 改造 key 命名，如 user:{1001}:profile 与 user:{1001}:orders 共享 1001 的槽位。
- ARGV 承载参数值，如阈值、时间戳、目标值等，不应把 key 混进 ARGV。
- ARGV 中所有参数都按字符串传入，数字也以字符串形式进入脚本，需要时在 Lua 里用 tonumber 转换。
- 主从与哨兵架构没有此硬性约束，但坚持规范可让脚本平滑迁移到集群。

```lua
-- 反例：写死 key，集群下必然跨槽
return redis.call('GET', 'global:config')
```

> [!IMPORTANT]
> **重要内容**：集群环境必须把脚本要用到的所有 key 全部写进 KEYS 数组——它是路由与槽位计算的唯一依据。写死 key 的脚本单机可用、上集群即报 MOVED，是脚本迁移最常见的翻车点（详见第 22 章）。

**速记**：**key 走 KEYS，值走 ARGV**，这是集群模式的生命线。



### 脚本缓存与错误处理

#### EVALSHA 与脚本缓存

**脚本缓存机制**：Redis 会按脚本的 SHA1 摘要缓存已加载的脚本，**EVALSHA** 用摘要代替源码执行，省去每次传输整个脚本的开销。

- SCRIPT LOAD script：预先加载脚本，返回其 SHA1 摘要。
- EVALSHA sha1 numkeys key [key ...] arg [arg ...]：按摘要执行已缓存的脚本。
- SCRIPT EXISTS sha1 [sha1 ...]：检查摘要是否已在缓存中，存在返回 1，不存在返回 0。
- SCRIPT FLUSH：清空全部脚本缓存，多用于开发与调试。
- 摘要由服务端对脚本源码计算 SHA1 得到，同一脚本摘要恒定，可离线预计算后写进配置。
- 脚本缓存为服务端全局所有，所有客户端共享同一份，每个缓存的脚本都占用服务端内存，脚本数量应收敛。

```bash
SCRIPT LOAD "return redis.call('GET', KEYS[1])"
EVALSHA 6b1bf486c81ceb7edf3c69f615fb9ea0e3f3a2e1 1 greeting
SCRIPT EXISTS 6b1bf486c81ceb7edf3c69f615fb9ea0e3f3a2e1
```

```text
"6b1bf486c81ceb7edf3c69f615fb9ea0e3f3a2e1"
"hello"
(integer) 1
```

- NOSCRIPT 错误：EVALSHA 请求的摘要不在缓存中时返回 NOSCRIPT 错误，客户端应降级改用 EVAL 重发完整脚本。
- 缓存可能失效：SCRIPT FLUSH、服务重启、主从切换后摘要都可能丢失，降级重试是必备的兜底逻辑。

```text
(error) NOSCRIPT No matching script. Please use EVAL.
```

```bash
# 客户端通用降级伪代码
result = EVALSHA sha1 numkeys keys args
if result is NOSCRIPT error:
  result = EVAL script numkeys keys args
```

> [!TIP]
> **建议内容**：客户端统一按「先 EVALSHA、捕获 NOSCRIPT、再 EVAL」的降级链路封装脚本调用；ioredis 的 defineCommand 已内置该逻辑（详见第 30 章），业务侧直接复用即可，无需重复造轮子。

**速记**：**LOAD 拿摘要，EVALSHA 省流量，NOSCRIPT 就降级**。



#### redis.call 与 redis.pcall 的区别

**redis.call 与 redis.pcall 的区别**：二者都在脚本内执行 Redis 命令，差别在错误处理——**redis.call 出错即终止脚本并把错误返回客户端**，**redis.pcall 捕获错误并以表的形式返回**，脚本得以继续运行。

- redis.call：命令出错直接抛出，脚本立即中断，客户端收到该错误，行为类似事务中的执行错误。
- redis.pcall：返回一个带 err 字段的 Lua 表，脚本可据此分支判断、降级或返回自定义错误信息。
- 参数写法：命令名与参数逐个传入，如 redis.call('SET', KEYS[1], ARGV[1])。
- 返回值自动转换：Lua 数字转为整数回复、table 转为数组回复、false 转为 nil、true 转为整数 1。
- 选择原则：希望错误立刻暴露、脚本快速失败时用 redis.call；希望脚本对错误负责、自行降级时用 redis.pcall。
- pcall 返回的表内容固定：只有 err 一个字段，值为与命令行错误一致的错误信息字符串。

```lua
-- call 版本：出错即中断，客户端直接收到 WRONGTYPE
local result = redis.call('INCR', KEYS[1])
return result
```

```lua
-- pcall 版本：捕获 WRONGTYPE，脚本自主决定如何回应
local result = redis.pcall('INCR', KEYS[1])
if type(result) == 'table' and result.err then
  return 'key type invalid: ' .. result.err
end
return result
```

```bash
SET counter hello
EVAL "return redis.call('INCR', KEYS[1])" 1 counter
EVAL "return redis.pcall('INCR', KEYS[1]).err" 1 counter
```

```text
(error) WRONGTYPE Operation against a key holding the wrong kind of value
"WRONGTYPE Operation against a key holding the wrong kind of value"
```

> 判断 pcall 失败的通用写法是检查返回值是否为表且带 err 字段；成功时 INCR 返回数字、SET 返回 OK 字符串，类型不同，分支处理时需分别对待。

**速记**：call **抛错即停**，pcall **拿表续跑**。



### 脚本超时、常见坑与选型

#### 脚本超时与 SCRIPT KILL

**脚本超时机制**：脚本执行超过 busy-reply-threshold（Redis 7.0 之前的参数名是 lua-time-limit）后，Redis 开始对其他客户端回复 BUSY 错误，但**脚本本身并不会被自动终止**。

- 该参数单位为毫秒，默认值 5000，可在 redis.conf 或运行时通过 CONFIG SET 调整。
- 超时后主线程仍在执行脚本，其他客户端的请求收到 BUSY Script is running 错误。
- 此时另开连接执行 SCRIPT KILL：若脚本尚未执行过任何写命令，脚本被安全终止，服务恢复正常。
- 若脚本已经写入数据，SCRIPT KILL 无效——强行终止会留下半改状态，唯一出路是 SHUTDOWN NOSAVE 不保存重启，靠持久化文件回退到最近快照。
- 阈值调大只会延长其他客户端的 BUSY 等待窗口，调小则压缩了 SCRIPT KILL 的机会窗口，默认值通常不必改动。
- BUSY 期间连接并不断开，客户端收到的是错误回复而非挂起，重试应退避而非立即重发。

```text
(error) BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.
```

```bash
CONFIG SET busy-reply-threshold 3000
SCRIPT KILL
SHUTDOWN NOSAVE
```

> [!WARNING]
> **警告内容**：SHUTDOWN NOSAVE 会丢弃自上次持久化以来的全部写入，是恢复服务的最后手段而非常规操作。根治之道是控制脚本规模：脚本只做短小的原子逻辑，重循环与大批量操作放回客户端完成（单线程阻塞原理详见第 16 章）。

**速记**：超时先试 **SCRIPT KILL**，写过数据只能 **NOSAVE 重启**。



#### 脚本复制模式与随机命令限制

**脚本复制模式**：主库把脚本同步给从库与 AOF 有两种方式——**逐字复制**把脚本原文重放一遍，**效果复制**只把脚本实际产生的写命令传播出去，Redis 5.0 起默认采用效果复制。

- 逐字复制（verbatim replication）：从库与主库执行同一段脚本，这要求脚本重复执行结果一致，因此早期的规则是脚本一旦执行过写命令，就不得再调用 TIME、SRANDMEMBER 这类产出随机结果的命令。
- 效果复制（effects replication）：主库记录脚本执行期间实际生成的写命令序列，把效果本身传给从库与 AOF，脚本内容是否确定不再重要。
- 版本演进：效果复制在 Redis 3.2 引入（需通过 redis.set_repl 显式开启），5.0 起成为脚本复制的默认模式；7.0 起脚本与函数统一按效果复制，逐字模式退役（版本脉络详见第 32 章）。
- 随机命令限制随复制模式演变：5.0 之前随机命令与写命令的先后顺序受限，5.0 之后该检查不再存在，脚本可以在写命令之后调用随机命令。
- 副作用的边界不变：脚本内的写命令都发生在主库、以效果同步，脚本不应依赖客户端本地的任何状态。
- 与持久化的衔接：效果复制同时服务 AOF——传播的是写命令效果，脚本的持久化粒度与普通命令一致（详见第 18 章）。

> 辨析：效果复制放开的只是「复制确定性」这一约束，脚本内依赖随机结果的业务逻辑仍要自己保证幂等与重试；SRANDMEMBER 这类命令每次返回值不同，把随机结果写进多端共享的键依然是不良设计。

**速记**：**3.2 可选、5.0 默认传效果**，随机命令解禁，副作用照常入 AOF。



#### 常见坑：写死 key 与长脚本阻塞

**脚本两大常见坑**：一是脚本内**写死 key** 导致集群 MOVED 错误，二是**长脚本阻塞主线程**拖垮整个实例。

- 写死 key：脚本直接访问 KEYS 之外的固定 key，集群按 KEYS 路由后必然跨槽报错；解法是把所有 key 逐一列进 KEYS 数组（详见第 22 章）。
- 长脚本：脚本执行期间单线程独占，百万次循环或大集合遍历会让所有请求排队等待，表现与宕机类似。
- 大 key 遍历：脚本内对百万成员的集合逐一循环，效果等同长脚本，应拆分处理或放回客户端。
- 随机性误解：效果复制自 5.0 起成为默认，随机命令限制已不复存在（详见上一考点），不要为早已解除的约束重构脚本。
- 排查思路：客户端大面积 BUSY 或超时，先怀疑有慢脚本在跑，结合慢查询日志定位（详见第 29 章）。

```lua
-- 正确示范：短小、key 全走 KEYS、一次原子完成
if redis.call('EXISTS', KEYS[1]) == 1 then
  return redis.call('INCR', KEYS[1])
end
redis.call('SET', KEYS[1], 1)
return 1
```

> [!NOTE]
> **提醒内容**：脚本的正确定位是「一段短小的原子逻辑」，通常几十行以内；把大批量数据处理塞进脚本，等于亲手把单线程的 Redis 变成串行批处理机，所有在线请求都会跟着遭殃。

**速记**：**key 全进 KEYS、脚本务必短小**，两坑同源于单线程。



#### 事务、WATCH 与 Lua 的对比选型

**选型结论**：纯命令打包用**事务**，读后写原子逻辑用 **Lua 脚本**，多客户端竞争修正用 **WATCH** 或 Lua——三者按需求复杂度递进，🎯 优先选最轻的那一个。

- 事务：只需按序执行一组固定命令、无任何分支判断时使用，开销最小。
- WATCH：竞争不激烈、重试成本可接受、且不想引入 Lua 时使用，客户端逻辑最直观；须配重试上限与退避间隔，避免乐观锁退化成重试风暴。
- Lua：需要条件判断、多步读后写、或要求一次往返完成全部动作时使用，原子性最完备。
- 冲突成本对照：WATCH 冲突即放弃整个事务并重试全流程，热键竞争下重试率飙升、服务端还要维护监视字典；Lua 在服务端一次跑完，不存在执行期冲突。
- 官方口径：事务文档明确指出，凡事务能做的事脚本都能做，且通常更简单也更快——这是选型的总原则。
- 混用原则：同一系统内可以并存——热点读后写用 Lua，固定命令序列用事务，二者并不冲突。
- 三者共同的边界：都不提供回滚，出错路径都要在客户端兜底。

> 辨析边界：只读批量取数无需原子时，用 pipeline 逐条执行即可，不必让脚本独占主线程；跨槽多键的原子性事务与脚本都给不了，只能在应用层拆分或用 hash tag 收拢键（详见第 22 章）。

**速记**：**有判断用 Lua、纯打包用事务、WATCH 留给低冲突**。



#### Functions：服务端函数库的工程实践

**Functions**：Redis 7.0 引入的**服务端具名函数**机制，把脚本以库为单位注册到服务端，用 **FCALL** 按名调用，函数随服务器状态持久化并自动同步，取代零散 EVALSHA 的工程实践。

- 加载：FUNCTION LOAD [REPLACE] library-code，库首行以 #!lua name=库名 声明库名，函数在库内用 redis.register_function 注册；REPLACE 覆盖同名已有库。
- 调用：FCALL 函数名 numkeys key [key ...] arg [arg ...]，参数语义与 EVAL 一致；只读函数（以 no-writes 标志声明）可用 FCALL_RO 调用。
- 管理命令族：FUNCTION LIST 列出已加载库、FUNCTION INFO 查看详情、FUNCTION DELETE 删除指定库、FUNCTION DUMP 导出载荷、FUNCTION RESTORE 恢复、FUNCTION FLUSH 清空全部。
- **持久化与复制**：函数作为服务器状态写入 RDB 与 AOF、随复制流传播，节点重启或新增副本自动带上函数，客户端无需对每个节点重新加载。
- 与 EVALSHA 的本质差别：脚本缓存不入持久化、换节点即失配，客户端必须实现 NOSCRIPT 降级；Functions 从机制上消掉这一层。
- 工程收益：函数库有名字、加载有 REPLACE 语义，可纳入 CI 版本化发布；业务代码只出现函数名，不再内嵌大段 Lua 正文，审计边界更清晰。
- 既有 EVAL 体系不受影响，两者并存；脚本数量多、需要版本管理的团队优先评估 Functions（版本演进详见第 32 章）。

```lua
#!lua name=mylib

local function save_msg(keys, args)
    return redis.call('SET', keys[1], args[1])
end

redis.register_function('save_msg', save_msg)
```

```bash
FUNCTION LOAD REPLACE "$(cat mylib.lua)"
FCALL save_msg 1 greeting hello
FUNCTION LIST
```

> Functions 目前实际使用率低于 EVAL 体系，各客户端库的支持程度也参差；掌握其定位即可——面试能答出「7.0 提供服务端具名函数、FCALL 调用、函数持久化且主从同步」即达标。

**速记**：**事务包命令、WATCH 盯冲突、Lua 包逻辑、Functions 收编脚本**。
