## Node 中使用 Redis：ioredis 实战

### 为什么选择 ioredis

#### ioredis 的定位与功能全景

**ioredis**：是 **Node.js 生态中功能最完整的 Redis 客户端之一**，以**全命令支持、内置集群与哨兵、管道与事务、Lua 自定义命令**见长，是当前社区事实上的主流选择。

- **命令全覆盖**：Redis 的每条命令都被一比一映射为客户端方法，无需逐个适配。
- **高可用拓扑内置**：原生支持 Cluster 集群与 Sentinel 哨兵接入（详见第 21 章、第 22 章）。
- **性能手段齐备**：pipeline 管道、multi 事务、Lua 脚本均有一等公民式 API（详见第 23 章）。
- **连接管理完善**：离线队列、自动重连、重试策略、TLS 加密等连接层能力开箱即用。
- **协议解析自带**：内置 RESP 协议解析器，不依赖额外的解析库。
- 由社区创建，目前托管在 Redis 官方 GitHub 组织下持续维护，大量框架与队列库以其为底层驱动。

ioredis 的方法全部返回 Promise，可以直接配合 async/await 使用：

```js
const Redis = require("ioredis");
const redis = new Redis();

// 一条命令一行，返回 Promise，直接 await
const count = await redis.incr("counter:page:view");
console.log(count); // 自增后的最新值
```

> 兼容 Promise 的同时也保留旧式用法：给任意命令方法传入 Node 风格回调即可按回调返回结果，两种风格可在同一项目中混用，迁移旧代码时尤其方便。

**速记**：ioredis = **全命令 + 集群哨兵 + 管道事务 Lua + 完善连接管理**。



#### ioredis 与 node-redis 的对比

**ioredis 与 node-redis 的对比**：两者都是 Node 端主流 Redis 客户端，**node-redis** 出身更早、贴近官方，**ioredis** 功能更全面、社区采用更广，新项目普遍默认选 ioredis。

- **API 风格**：ioredis 命令即方法、返回 Promise，链式 pipeline 写法顺滑；node-redis 4.x 起也支持 Promise，但方法命名与参数组织不同。
- **集群与哨兵**：ioredis 内置 Redis.Cluster 构造与 sentinels 选项，接入成本低；node-redis 亦有对应实现，但配置项与行为细节有差异。
- **Lua 自定义命令**：ioredis 提供 defineCommand 把脚本注册为实例方法；node-redis 需要自行封装 eval 调用。
- **重连控制**：ioredis 的 retryStrategy、maxRetriesPerRequest、enableOfflineQueue 等开关粒度更细。
- **生态地位**：BullMQ、cache-manager 等流行库默认或推荐以 ioredis 为底层驱动。

> 两个客户端都成熟可用，选型差异主要体现在习惯与生态。项目一旦固定其一，就不建议再引入另一个客户端直连同一批键，连接管理与序列化约定难以统一，排查问题时也会多一层干扰。

**速记**：**node-redis 贴官方，ioredis 功能全**，新项目默认 ioredis。



### 安装与建立连接

#### 安装与三种连接写法

**ioredis 的安装与连接**：安装只需一条 npm 命令，建立连接有**端口、连接串、选项对象**三种写法，均通过 new Redis 构造完成。

```bash
npm install ioredis
```

```js
const Redis = require("ioredis");

// 写法一：只传端口，默认连接本机 6379，无密码
const redisA = new Redis(6379);

// 写法二：连接串，一次写全协议、密码、地址、端口与库号
const redisB = new Redis("redis://:yourPassword@127.0.0.1:6379/0");

// 写法三：选项对象，生产环境最常用，便于从环境变量注入
const redisC = new Redis({
  host: "127.0.0.1",
  port: 6379,
  password: "yourPassword",
  db: 0,
});
```

- 构造完成即**开始建立 TCP 连接**，不需要显式调用 connect。
- 连接串格式为 redis://:密码@主机:端口/库号，省略的部分按默认值处理。
- 需要加密传输时把协议换成 rediss://，对应 TLS 连接。
- 选项对象能组合出连接串表达不了的高级配置，是工程项目的首选写法。

> 构造函数返回的实例**本身就是客户端**：所有 Redis 命令都是它的方法，连接事件也从它身上监听。一个实例对应一条 TCP 连接，需要多条连接时创建多个实例即可。

**速记**：**new Redis 三种姿势**——传端口、给连接串、配选项对象。



#### 常用连接选项与惰性连接

**常用连接选项**：ioredis 通过选项对象暴露连接层的关键开关，其中 **lazyConnect 惰性连接**决定实例创建时是否立刻建连。

- **host 与 port**：服务器地址与端口，默认 127.0.0.1 与 6379。
- **password 与 db**：认证密码与逻辑库编号。
- **keyPrefix**：全局键前缀，此后所有命令的键都会自动加上该前缀。
- **connectTimeout**：建立连接的超时毫秒数，默认 10000。
- **lazyConnect**：默认 false，实例一创建就连；设为 true 则**推迟到第一条命令**执行时才建连。
- **retryStrategy**：自定义重连间隔的函数，详见下文错误处理一节。

```js
const lazyRedis = new Redis({
  host: "127.0.0.1",
  port: 6379,
  lazyConnect: true, // 创建时不连接，首次执行命令时才建立
});
```

- 惰性连接适合**未必用到 Redis 的进程**，例如定时任务、按需加载的脚本，避免无谓的常驻连接。
- lazyConnect 为 true 且从不执行命令时，实例**永远不会发起连接**，也就不会产生连接错误。

> 惰性连接的代价是**首条命令要承担建连耗时**。对常驻服务而言，启动即连接、命令零等待的默认行为反而更合适，不要为了配置而配置。

**速记**：lazyConnect = **用到才连**，省下闲置连接，首命令多付建连耗时。



### 基本读写与序列化

#### 字符串读写、过期时间与空值语义

**字符串读写**：通过 **get 与 set** 完成最常用的键值操作，set 可在写入的同时用附加参数设置**过期时间与存在条件**（字符串命令全集详见第 3 章）。

```js
// 写入与读取
await redis.set("greeting", "hello");
await redis.get("greeting"); // "hello"

// 批量写入与批量读取
await redis.mset("cfg:a", "1", "cfg:b", "2");
await redis.mget("cfg:a", "cfg:b"); // ["1", "2"]

// 写入并设 60 秒过期，等价于 SET greeting hello EX 60
await redis.set("captcha:8848", "668801", "EX", 60);

// 对已存在的键单独补过期时间，单位秒
await redis.expire("greeting", 300);

// NX 表示键不存在才写入，与 EX 搭配是分布式锁的基石（详见第 27 章）
await redis.set("lock:order:1001", "token-abc", "EX", 10, "NX");
```

- set 的完整参数顺序为 **键、值、过期模式、过期数值、存在条件**，后三项可按需组合。
- 过期模式支持 **EX 秒**与 **PX 毫秒**两种，写入自带过期可避免「先 set 再 expire」两步之间的空窗。
- expire 对不存在的键操作返回 0，不做任何事。

> 只有过期没有自动续期的键到期即被删除（详见第 14 章）。验证码、会话、临时令牌等场景应把过期时间并入 set 一次完成，比先写后补 expire 更安全。

**get 的空值语义**：读取不存在的键时 ioredis 返回 **null**，这是 Redis 协议中批量字符串空回复的映射，**不是 undefined**。

```js
const value = await redis.get("not:exist:key");

console.log(value);          // null
console.log(value === null); // true，用严格相等判断空值
```

- 判空应使用 **value === null**；只判断假值会把空字符串、数字 0 一并误判进去，掩盖键值恰好为空的情况。
- 与 null 同源的还有其他类型命令：哈希取不存在的域返回 null，列表、集合取不存在的键返回空数组，语义均为「键不存在」。
- 类型错误的键调用命令会抛出 WRONGTYPE 错误，与空值是两回事。

> [!IMPORTANT]
> **重要内容**：null 与 undefined 的区别是笔试与线上故障的高频考点。Redis 协议用 null 表示「无此数据」，ioredis 忠实映射为 null；undefined 只出现在变量未赋值等语言层场景。若误判成 value === undefined，缓存永远判不中，请求会全部穿透到数据库（详见第 25 章）。

**速记**：set 带 **EX 加 NX** 一步到位；键不存在返回 **null**，判空用**严格相等**。



#### 对象序列化与缓存读写封装

**对象存取的约定**：ioredis 只能直接读写**字符串、数字与缓冲区**，结构化对象须由业务层做 **JSON 序列化**，典型做法是封装 cacheSet 与 cacheGet 两个函数。

```js
async function cacheSet(key, value, ttlSeconds) {
  const payload = JSON.stringify(value);
  if (ttlSeconds) {
    await redis.set(key, payload, "EX", ttlSeconds);
  } else {
    await redis.set(key, payload);
  }
  return "OK";
}

async function cacheGet(key) {
  const payload = await redis.get(key);
  if (payload === null) {
    return null; // 未命中，交由调用方回源数据库并回填
  }
  return JSON.parse(payload);
}
```

- 写入侧统一 JSON.stringify，读取侧统一 JSON.parse，序列化细节被关进封装层。
- 调用方读到 null 即未命中，据此走回源数据库再回填的逻辑（详见第 26 章）。
- 数字可以不序列化直接存，但取出后是字符串，需要时用 Number 转回。

> 序列化方案一旦上线就不宜随意更换：换格式会让存量旧缓存解析失败。升级序列化时应在值内带版本号，或整体切换新前缀后灰度迁移。

**速记**：**对象过 Redis 必序列化**，封装 cacheSet 与 cacheGet 关住细节。



#### Buffer 读写与二进制数据

**Buffer 变体**：每条返回数据的命令都有对应的 Buffer 版本——get 对应 getBuffer，方法名加 Buffer 后缀，返回 Node 的 Buffer 对象而非字符串。

```js
await redis.set("bin:logo", Buffer.from([0x89, 0x50, 0x4e, 0x47]));
const raw = await redis.getBuffer("bin:logo"); // <Buffer 89 50 4e 47>
```

- 写入侧不需要 Buffer 变体：Redis 的值本就二进制安全，set 直接接收 Buffer 与普通字符串。
- 读取侧必须用 Buffer 变体：字符串方法按 UTF-8 解码，非 UTF-8 字节被静默替换，数据损坏且不报错。
- defineCommand 注册的自定义命令同样自动生成同名 Buffer 变体；订阅消息也有 message 与 messageBuffer 两个事件对应。

> 辨析：**写入不挑方法、读取必须变体**——图片、序列化对象、protocol buffer 等非文本数据一律走 getBuffer 一族，字符串方法只配文本键；这类损坏难以从日志发现，规范上应提前禁止对二进制键使用字符串方法。

**速记**：写不用变体、读必须 getBuffer，字符串方法只配文本键。



### 命令调用约定

#### 命令一比一映射与两种传参形式

**命令调用约定**：ioredis 把 Redis 命令**一比一映射为实例方法**，参数按命令文档顺序展开传入，同时也支持把全部参数收进**一个数组**传入。

```js
// 哈希写入：HSET user:1001 name alice
await redis.hset("user:1001", "name", "alice");

// 有序集合写入：ZADD rank:points 95 player:1
await redis.zadd("rank:points", 95, "player:1");

// 数组形式：参数整体收进数组，与展开写法完全等价
await redis.hset(["user:1001", "name", "bob"]);
await redis.zadd(["rank:points", 88, "player:2"]);

// 命令名大小写均可，以下两行等价
await redis.HSET("user:1001", "age", "18");
await redis.hset("user:1001", "age", "18");
```

- 方法名与命令名**大小写不敏感**，习惯上业务代码统一用小写。
- 展开形式直观贴近命令文档；数组形式便于**动态拼装参数**，例如字段个数运行时才知道的场景，可写 redis.hset(["user:1002", ...fields])。
- 返回值一律遵循 Redis 协议映射：整数返回数字、状态回复返回字符串、批量字符串不存在返回 null。

> 参数个数与顺序以 Redis 官方命令文档为准，ioredis 不做参数校验上的二次发明。可变参数命令（如 rpush、sadd）把多个成员依次展开即可，无需再包一层嵌套结构。

**速记**：**命令即方法**，参数**展开或数组**两可，大小写随习惯。



### pipeline 与事务

#### pipeline 管道的两种写法与结果数组

**pipeline 管道**：把多条命令**打包一次发送**、省去逐条往返等待的性能手段，ioredis 提供**链式**与**数组**两种写法，exec 后统一返回结果数组。

```js
// 写法一：链式调用
const replies = await redis
  .pipeline()
  .set("pipeline:a", "1")
  .get("pipeline:a")
  .incr("counter:pv")
  .exec();

// 每条命令的结果是 [错误, 返回值] 二元组，按发送顺序排列
console.log(replies[0]); // [null, "OK"]
console.log(replies[1]); // [null, "1"]
console.log(replies[2]); // [null, 1]

// 写法二：命令与参数收进二维数组
const arrayReplies = await redis.pipeline([
  ["set", "pipeline:b", "2"],
  ["get", "pipeline:b"],
]).exec();
```

- 管道中的命令**不保证原子性**，只是省去网络往返，服务端仍逐条独立执行。
- exec 不传回调返回 Promise；传入 Node 风格回调则结果经回调返回，两种风格等价。
- 结果数组的每项都是二元组，**个别命令失败不影响其余命令**，须逐项检查错误位。

> [!TIP]
> **建议内容**：循环里逐条 await 是最常见的性能反模式（详见第 29 章）。批量写入、批量读取、预热缓存等场景，改用 pipeline 一次往返能把耗时从 N 次往返压缩到 1 次，命令越多收益越大。

**速记**：pipeline = **打包发送**，exec 回**二元组数组**，省往返不保原子。



#### multi 事务的执行与结果解读

**multi 事务**：ioredis 的 multi 方法对应 Redis 的 MULTI 与 EXEC 命令，命令入队后**一次性原子执行**，exec 返回与入队顺序一致的结果数组（详见第 23 章）。

```js
// 服务端逐条入队，每条回显 QUEUED，EXEC 时一并执行
const replies = await redis
  .multi()
  .set("multi:a", "1")
  .incr("multi:count")
  .get("multi:a")
  .exec();

console.log(replies);
// [ [null, "OK"], [null, 1], [null, "1"] ]
```

- 与 pipeline 的核心区别：事务内的命令**要么全执行要么全不执行**，中间不会插入其他客户端的命令。
- 结果数组同样是 [错误, 返回值] 二元组，但**顺序严格等于入队顺序**，可按下标取用。
- 配合 watch 可实现乐观锁：被监视的键在 exec 前被他人改动时，事务整体放弃执行。

> 事务只保证**入队命令的连续执行**，不提供回滚：某条命令在执行阶段失败，其余命令照常生效。需要「检查再操作」的条件逻辑时，multi 内拿不到中间结果，正确工具是 Lua 脚本。

**速记**：multi = **QUEUED 入队、EXEC 原子出结果**，无回滚，条件逻辑找 Lua。



### Lua 脚本与自定义命令

#### defineCommand 定义与调用自定义命令

**defineCommand**：ioredis 提供的脚本注册方法，把一段 Lua 脚本**包装成实例上的自定义命令**，此后可像内置命令一样直接调用（详见第 23 章）。

```js
// 注册自定义命令 rateLimit：占用 1 个键，ARGV[1] 为过期秒数
redis.defineCommand("rateLimit", {
  numberOfKeys: 1,
  lua: `
    local current = redis.call("incr", KEYS[1])
    if current == 1 then
      redis.call("expire", KEYS[1], ARGV[1])
    end
    return current
  `,
});

// 像内置命令一样调用：先传键，再传其余参数
const count = await redis.rateLimit("rate:uid:1001", 60);
console.log(count); // 本窗口内的第几次访问
```

- **numberOfKeys** 声明脚本占用几个键，调用时前若干个参数对应 KEYS，其余对应 ARGV。
- 注册后脚本由 ioredis 缓存到服务端，调用走 EVALSHA；遇到 NOSCRIPT 场景**自动降级重发 EVAL**，无需手工处理。
- 自定义命令与内置命令同等参与 pipeline 与 multi，可组合进批量链。

> [!NOTE]
> **提醒内容**：numberOfKeys 必须与调用时的键个数严格一致，否则 KEYS 与 ARGV 错位，脚本将操作错误的键。键名务必通过 KEYS 传入而非拼进脚本正文，集群模式下客户端据此定位脚本路由到的节点。

**速记**：defineCommand = **Lua 变方法**，numberOfKeys 定键位，NOSCRIPT 自动兜底。



### 发布订阅

#### 订阅连接独立与 message 事件

**发布订阅的接入方式**：订阅端必须使用**独立连接**——连接一旦执行 subscribe 就进入**订阅态**，此后只能收发订阅相关命令，普通读写会报错（详见第 24 章）。

```js
const publisher = new Redis();            // 发布者：普通连接
const subscriber = publisher.duplicate(); // 订阅者：复制出一条独立连接

await subscriber.subscribe("news:sports", "news:tech");
subscriber.on("message", (channel, message) => {
  console.log("频道", channel, "消息", message);
});

// 模式订阅：按通配符匹配一类频道
await subscriber.psubscribe("news:*");
subscriber.on("pmessage", (pattern, channel, message) => {
  console.log("模式", pattern, "命中频道", channel, message);
});

await publisher.publish("news:sports", "比分更新");
```

- duplicate 复制现有连接的配置并建立**新连接**，是拿到订阅专线的标准做法。
- 精确订阅走 subscribe 与 message 事件，模式订阅走 psubscribe 与 pmessage 事件。
- 发布端 publish 返回接收到消息的订阅者数量，返回 0 表示当前无人订阅。
- 订阅消息**不落盘不补发**，订阅方掉线期间的消息即丢失，可靠性要求高的场景应改用 Stream（详见第 24 章）。

> [!WARNING]
> **警告内容**：在同一连接上订阅后又调用 get 或 set 等普通命令，服务端会直接报错，提示该连接处于订阅态、只能执行订阅相关命令。发布订阅的收发双方必须分属两条连接，这是 Redis 协议层的硬约束，不是客户端的坏脾气。

**速记**：**订阅占线**——一条连接进了订阅态就别再发普通命令，duplicate 出专线收消息。



### 分布式锁最小实现

#### acquireLock 加锁与 releaseLock 解锁

**分布式锁的最小实现**：加锁用 **set 加 NX 加 EX** 保证互斥与自动过期，解锁用 **Lua 脚本先比对锁标识再删除**，两个函数构成最小可用闭环（详见第 27 章）。

```js
const crypto = require("crypto");

// 生成一次性锁标识：只有持锁人知道，释放时出示
function buildLockToken() {
  return crypto.randomBytes(16).toString("hex");
}

// 加锁：SET lockKey token EX ttl NX，只有一个客户端能拿到 OK
async function acquireLock(lockKey, ttlSeconds) {
  const token = buildLockToken();
  const result = await redis.set(lockKey, token, "EX", ttlSeconds, "NX");
  if (result === "OK") {
    return token; // 返回标识，调用方保存用于释放
  }
  return null; // 锁被占用
}

// 释放锁：比对标识与删除必须原子完成，防止误删他人的锁
redis.defineCommand("releaseLock", {
  numberOfKeys: 1,
  lua: `
    if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
    else
      return 0
    end
  `,
});

async function releaseLock(lockKey, token) {
  const result = await redis.releaseLock(lockKey, token);
  return result === 1; // 1 表示成功释放，0 表示锁已易主或已过期
}
```

- **EX 保证锁必然过期**：持锁进程崩溃也不会造成死锁。
- **NX 保证互斥**：键已存在时 set 返回 null，拿锁失败的客户端应稍后重试。
- **token 防误删**：锁过期后其他客户端可能已持有新锁，无标识的删除会越权释放他人的锁。
- 比对与删除若拆成 get 再 del 两步，中间存在时间窗，Lua 把它们合并为一次原子执行。

> 这是最小实现，未覆盖锁续期、可重入与红锁等进阶需求。生产环境可直接采用基于 ioredis 的成熟锁库，但先读懂这段代码是读懂一切锁库的前提。

**速记**：加锁 **NX 加 EX**，释放 **Lua 验 token**，过期兜底防死锁。



### 错误处理与重连

#### error 事件与 retryStrategy 重连策略

**error 事件与重连**：连接异常通过 **error 事件**暴露，ioredis 在断线后按 **retryStrategy 函数**的返回值自动重连，两者构成错误处理的底线。

```js
const redis = new Redis({
  host: "127.0.0.1",
  port: 6379,
  // times 是当前第几次重连，返回值是下次重连等待的毫秒数
  retryStrategy(times) {
    return Math.min(times * 200, 5000); // 200ms 起步，封顶 5 秒
  },
});

redis.on("error", (err) => {
  console.error("Redis 连接错误", err.message);
});
redis.on("reconnecting", (delay) => {
  console.log(`将在 ${delay} 毫秒后重连`);
});
```

- error 事件**必须监听**：ioredis 对该事件做了静默处理，未监听不会击穿进程，但所有连接错误也随之无声丢失，故障时既无日志也无告警。
- retryStrategy 返回毫秒数表示按该间隔重连，返回错误对象或 null 表示**放弃重连**。
- 常见策略是**线性或指数递增并封顶**，避免服务端故障时客户端以最高频率冲击重连。
- 连接生命周期还有一组辅助事件：connect 表示 TCP 已建立，ready 表示握手完成可发命令，close 表示连接关闭，end 表示不再重连。
- end 触发后离线队列与重连都已停摆，后续命令将持续失败，应接告警或触发重启编排；健康检查可随时读 status 属性判断当前连接状态。

> retryStrategy 只管「何时再连」，不管「命令怎么办」；断线期间命令的去向由离线队列与 maxRetriesPerRequest 决定，两层机制各司其职。

**速记**：error 必听，retryStrategy **定节奏**，递增封顶别蛮冲。



#### enableOfflineQueue 与 maxRetriesPerRequest 的取舍

**断线期间的命令去向**：由 **enableOfflineQueue**（离线队列开关）与 **maxRetriesPerRequest**（单命令重试上限）共同决定，取舍点是**可用性与报错及时性**的平衡。

- **enableOfflineQueue 默认 true**：连接未就绪时命令进入离线队列排队，连接恢复后自动发出，业务代码无感知。
- 设为 false：断线期间的命令**立即报错**，调用方能第一时间感知故障，但需要业务自行兜底。
- **maxRetriesPerRequest 默认 20**：重连期间某命令跟着重试超过该次数即报错，避免请求无限悬挂。
- 设为 null：命令**永远等待**重连成功，适合绝不允许丢命令的场景。

```js
const strictRedis = new Redis({
  enableOfflineQueue: false, // 未连接就报错，不排队
  maxRetriesPerRequest: 3,   // 重连中每条命令最多陪跑 3 轮
});
```

> [!CAUTION]
> **注意内容**：enableOfflineQueue 设为 false 后，凡在连接建立前或断线期间发出的命令都会直接失败，冷启动阶段的第一批请求可能全部报错。是否关闭离线队列取决于业务语义：缓存读失败可回源的，默认的排队行为反而更稳；下单扣减这类不容许延迟积压的，才值得换取即时报错。

**速记**：离线队列**存命令**，maxRetriesPerRequest **防悬挂**，false 换及时报错。



### cluster 与 sentinel 接入

#### Redis.Cluster 与哨兵选项的写法

**集群与哨兵的接入**：ioredis 把两种高可用拓扑都做成构造函数级支持——集群用 **Redis.Cluster**，哨兵在选项对象中配置 **sentinels 数组与 name**（详见第 21 章、第 22 章）。

```js
// 集群：传入若干种子节点，槽位路由与 MOVED 重定向自动处理
const cluster = new Redis.Cluster([
  { host: "127.0.0.1", port: 7000 },
  { host: "127.0.0.1", port: 7001 },
]);

// 哨兵：列出哨兵地址，name 为主库逻辑名，客户端自动发现当前主库
const sentinelRedis = new Redis({
  sentinels: [
    { host: "127.0.0.1", port: 26379 },
    { host: "127.0.0.1", port: 26380 },
  ],
  name: "mymaster",
  password: "yourPassword",
});
```

- 集群实例上**多键命令受槽位约束**，跨槽位的 mget、multi 需要相关键落在同一槽，可用 hash tag 约束键名。
- 哨兵模式下读写地址跟随主库切换自动迁移，**故障转移对业务透明**。
- 二者的命令调用方式与单机实例完全一致，业务代码无需感知拓扑差异。

> Redis.Cluster 返回的是集群实例而非普通实例，其 pipeline 与事务按节点分组执行，行为与单机略有差异；涉及多键原子性的逻辑迁入集群前，务必重新验证（详见第 22 章）。

**速记**：集群 **new Redis.Cluster**，哨兵配 **sentinels 加 name**，调用姿势不变。



### 实战示例三则

本章把客户端知识落到三个高频场景：缓存读取封装 getOrSet、简单计数限流、简易分布式锁。第三则已在「分布式锁最小实现」一节完整展开，此处给出前两则的最终形态，均可直接抄用。

#### getOrSet 缓存读取封装

**getOrSet**：把读缓存、未命中读库、回填带 TTL 的三步读路径封装成一个函数，是第 26 章旁路缓存读路径的代码落地。

```js
async function getOrSet(key, ttlSeconds, loadFromDb) {
  const payload = await redis.get(key);
  if (payload !== null) {
    return JSON.parse(payload);                 // 命中：直接返回
  }
  const fresh = await loadFromDb();             // 未命中：读库
  if (fresh !== null) {
    await redis.set(key, JSON.stringify(fresh), "EX", ttlSeconds);
  }
  return fresh;
}

// 调用侧：键、TTL、加载函数三要素
const goods = await getOrSet("cache:goods:1001", 300, () =>
  queryGoodsFromDb(1001)
);
```

- 与 cacheGet、cacheSet 的分工：后两者只管存取，getOrSet 把「未命中回源加回填」的编排也收进来，调用方只提供加载函数。
- 回填必须带 TTL：它是后续一切一致性策略失效时的最后防线，理由详见第 26 章。
- 空值与击穿：数据库查不到时本例直接返回不缓存，防穿透的空值缓存与防击穿的互斥锁详见第 25 章，生产实现应补上。

> 封装的价值在于纪律强制：业务方不直接触碰 get 与 set，TTL 必填、回填统一走一处，第 26 章的全员 TTL 纪律就自动执行了——把规范写进代码而不是写进文档。

**速记**：命中返回、未命中读库、回填必带 TTL，三步封进一个函数。



#### 简单计数限流

**计数限流**：用上文注册的 rateLimit 自定义命令实现固定窗口限流——INCR 计数、首次 EXPIRE 定窗、超阈值即拒，原子性由 Lua 保证。

```js
// 每个用户每 60 秒最多 100 次
async function checkRateLimit(userId, limit, windowSeconds) {
  const calls = await redis.rateLimit(`rate:${userId}`, windowSeconds);
  return calls <= limit; // true 表示放行
}
```

- 维度选择：限流键按用户或 IP 粒度拆分，如 rate:uid:1001，避免全局限流误伤正常用户。
- 判断口径：脚本返回当前窗口内的累计次数，超过阈值即拒绝，被拒请求不消耗额外存储。
- 边界提醒：固定窗口在交界处可能放过接近两倍流量，滑动窗口与令牌桶等改进属限流算法专题，此处不展开。

> [!TIP]
> **建议内容**：限流键带上业务语义前缀（如 rate:order:1001），并把阈值与窗口做成配置下发而不是写死——大促时临时调整限流参数是高频操作，改配置远比发版快。

**速记**：INCR 计数、EXPIRE 定窗、超阈值即拒，原子靠 Lua。



### 工程化封装建议

#### 单例连接、键前缀与退出清理

**工程化封装的三个支点**：**单例连接**避免连接数失控，**统一键前缀**避免键空间混乱，**进程退出前 quit** 避免连接与命令的非正常中断。

```js
// db/redis.js：模块级单例，全进程共享一条连接
const Redis = require("ioredis");

const redis = new Redis({
  host: process.env.REDIS_HOST,
  port: Number(process.env.REDIS_PORT),
  password: process.env.REDIS_PASSWORD,
  keyPrefix: "app:cache:", // 所有键自动带上前缀
});

process.on("SIGINT", async () => {
  await redis.quit(); // 发完队列中剩余命令后优雅断开
  process.exit(0);
});

module.exports = redis;
```

- **单例**：一个进程一条长连接足以应付绝大多数负载，随手 new 会积累大量半死连接。
- **键前缀**：keyPrefix 在客户端层统一补前缀，多应用共享一个 Redis 实例时按应用划分命名空间，业务代码调用 get、set 时无需手写前缀。
- **优雅退出**：quit 等待离线队列清空后断开，disconnect（旧版本为 end）则立即断开，按场景二选一。
- **utils 层抽离**：把 cacheSet、cacheGet、buildCacheKey 等工具函数集中到独立模块，让「前缀加分隔符加业务键」的构造规则收敛到一处。

> [!WARNING]
> **警告内容**：进程退出前不调用 quit，离线队列中未发送的命令将随连接直接丢弃，优雅停机变成静默丢数据；开发环境反复热重载时，未清理的旧连接还会持续累积，最终触发服务端最大连接数限制。把 quit 挂进进程退出钩子，一次写好处处受益。

**速记**：**一进程一连**、**keyPrefix 划地盘**、**退出前 quit**，三件套撑起生产接入。
