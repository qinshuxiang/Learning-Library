## WebSocket 实时通信

### 实时通信的三种方案对比

#### 短轮询的局限

**短轮询（Short Polling）**：是客户端**按固定时间间隔反复发起 HTTP 请求**以获取新数据的实时方案，即使没有新数据也照常请求。

- 实现方式：客户端用 setInterval 定时调用 fetch 或 XMLHttpRequest 向服务端拉取。
- 每次请求都是完整的 HTTP 往返，包含请求头与握手开销，浪费带宽。
- 服务端无论有无更新都返回响应，绝大多数请求返回"无变化"。
- 实时性取决于轮询间隔：间隔越短越实时，但请求量与资源消耗越高。

> 短轮询的本质是"用高频请求假装实时"，间隔设大了消息延迟高，设小了服务器被无意义请求淹没。它只在数据更新极不频繁、且实现简单优先于效率时勉强可用。

**速记**：短轮询 **定时发请求，多数空手而归**。



#### 长轮询的折中

**长轮询（Long Polling）**：是服务端**收到请求后不立即返回，而是挂起连接直到有数据或超时**才响应的方案，是短轮询的改进。

- 客户端发出请求后，服务端若暂无数据则保持连接打开，等有新消息再返回。
- 客户端收到响应后立刻再发下一个请求，形成"挂起—响应—重连"的循环。
- 相比短轮询，它减少了空请求，降低了平均延迟与带宽浪费。
- 兼容性极好，不依赖任何新协议，在老旧浏览器与受限网络中也能工作。

> 长轮询仍基于 HTTP 请求响应模型：每个响应结束后连接关闭，下一次仍需重建。服务端挂起大量连接会占用文件描述符与内存，且超时重连在弱网下仍有一定开销。

**速记**：长轮询 **服务端挂起等有数据，兼容好但有开销**。



#### WebSocket 的全双工优势

**WebSocket**：是一条**建立后始终保持打开、客户端与服务端均可主动发送**的全双工长连接，从根本上摆脱了"请求才有响应"的轮询模式。

- 连接建立后不再反复握手，单条 TCP 连接上双向自由收发，开销极小。
- 服务端可主动推送，消息到达即可发送，延迟低、实时性强。
- 协议头开销小（帧头仅 2 至 14 字节），远轻于 HTTP 的请求头。
- 适合聊天、协同编辑、实时行情、游戏同步等高频率双向通信场景。

> WebSocket 不是"更快的 HTTP"，而是"换了通信范式"：HTTP 是一问一答，WebSocket 是建好管道后双方随时说话。它解决了轮询"服务端无法主动找客户端"的根本限制。

**速记**：WebSocket **全双工长连接，服务端能主动推**。



#### 三种方案的适用场景对照

**选型依据**：三者没有绝对优劣，应**按实时性要求、更新频率与部署环境**选择。

- **短轮询**：适合更新极不频繁、实时性要求低、且追求实现最简单的内部工具。
- **长轮询**：适合需要较好实时性但受困于老旧环境、无法用 WebSocket 的兼容场景。
- **WebSocket**：适合高频双向、低延迟要求的业务，如即时通讯、直播弹幕、实时监控。
- 折中思路：只读且低频用短轮询；写少读多用长轮询；双向高频用 WebSocket。

> 不要为"显得先进"而强行上 WebSocket：若只是每隔几分钟刷新一次状态，短轮询反而更省心、更易排错。选型看数据特征，而非技术潮流。

**速记**：看 **频率与实时性**，低频轮询、高频 WebSocket。



### WebSocket 的定义与握手过程

#### WebSocket 是基于 TCP 的全双工协议

**WebSocket 协议**：是定义在 TCP 之上的**应用层全双工通信协议**，经 RFC 6455 标准化，用于在单个长连接上双向传输数据。

- 它位于应用层，与 HTTP 平级，但**复用已建立的 TCP 连接**进行数据帧交换。
- 全双工意味着客户端与服务端**可同时收发**，互不阻塞等待对方。
- 连接一旦建立便长期保持，直到任一方主动关闭，避免反复建连的开销。
- 数据以"帧"为单位传输，而非 HTTP 的"报文"，协议头远小于 HTTP。

> WebSocket 与 HTTP 的底层都是 TCP：区别不在传输层，而在应用层规约。理解这点能避免"WebSocket 取代了 TCP"之类的误解——它只是 TCP 之上的一套帧格式。

**速记**：WebSocket **TCP 之上、全双工、帧传输**。



#### 由 RFC 6455 定义并复用 HTTP 端口

**协议标准化**：WebSocket 的握手与帧格式由 **RFC 6455** 规定，其默认端口**与 HTTP 一致**，加密版本对应 HTTPS 的端口。

- **ws 方案**：对应明文 HTTP，默认端口 80，地址形如 ws://host:port/path。
- **wss 方案**：对应加密 HTTPS（TLS），默认端口 443，地址形如 wss://host:port/path。
- 复用相同端口意味着 WebSocket 可与 HTTP 服务**共享同一监听端口**，便于部署与穿透防火墙。
- 使用 wss 是生产环境的最低安全要求，明文 ws 在公网传输等同于明文 HTTP。

> 端口一致不等于协议一致：ws 与 wss 只是"借用了 HTTP 的端口号"，握手完成后双方便脱离 HTTP 语义。443 上的服务既能处理 HTTPS 请求，也能在握手后切到 WebSocket，靠的是请求头里的升级标记。

**速记**：RFC 6455 **定标准**，ws/wss **同端口、wss 才加密**。



#### 握手阶段从 HTTP 升级到 WebSocket

**协议升级（Upgrade）**：WebSocket 连接**先用一次标准 HTTP 请求完成握手**，服务端同意后将同一条 TCP 连接"升级"为 WebSocket 帧通信。

- 客户端发起的连接初始仍是 HTTP 请求，目的仅为协商升级，而非获取数据。
- 握手成功后，**连接不关闭**，通信方式从"HTTP 报文"切换为"WebSocket 帧"。
- 升级是单向协商：必须由客户端在请求中声明意图，服务端决定是否接受。
- 升级之后，该连接上不再有 HTTP 请求响应的语义，只有 WebSocket 帧的收发。

> 这正是 WebSocket 易于穿透现有 Web 基础设施的原因：它"伪装"成一次 HTTP 请求进门，门一开就换成自己的协议。防火墙与代理看到的是合法 HTTP 握手，通常予以放行。

**速记**：握手 **先走 HTTP，升级后转帧通信**。



#### 客户端发起升级请求

**升级请求**：客户端发送的握手请求是一段**带特定头字段的普通 HTTP GET 请求**，用于表明"我要升级到 WebSocket"。

- 必须包含 **Upgrade 头**，取值为 websocket，声明要切换的协议。
- 必须包含 **Connection 头**，取值为 Upgrade，告知代理这条连接将被升级。
- 必须包含 **Sec-WebSocket-Key 头**，取值为一段随机 Base64 串，用于防止误升级与握手校验。
- 必须包含 **Sec-WebSocket-Version 头**，取值为 13，表示使用的协议版本（RFC 6455）。

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

> Sec-WebSocket-Key 不是加密密钥，它是一段客户端随机串，服务端把它与固定字符串拼接后做 SHA-1 再 Base64 编码，得到 Sec-WebSocket-Accept 回传。该机制用于确认对方确实理解 WebSocket 握手，而非普通 HTTP 服务器误响应。

**速记**：升级请求 **Upgrade 加 Connection 加 Key 加 Version 四件套**。



#### 服务端返回 101 切换协议

**握手响应**：服务端同意升级时返回 **101 Switching Protocols** 状态码，并回传 **Sec-WebSocket-Accept** 完成握手。

- 状态码必须是 **101**，表示协议切换成功，而非 200 等常规 HTTP 状态。
- 响应包含 **Upgrade 头** 取值 websocket、**Connection 头** 取值 Upgrade，确认协议变更。
- 响应包含 **Sec-WebSocket-Accept 头**，其值是服务端按规范对客户端 Key 计算后的固定结果。
- 握手一旦完成，双方即可通过该连接收发 WebSocket 帧，HTTP 语义结束。

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

> 若 Sec-WebSocket-Accept 计算错误或与预期不符，客户端会判定握手失败并关闭连接。该字段是握手合法性的"防伪标记"，并非用于加密，明文传输也不泄露任何密钥。

**速记**：服务端回 **101 加 Accept**，握手即完成。



#### 升级后脱离 HTTP 语义

**升级后状态**：握手成功那一刻起，**这条连接不再遵循 HTTP 请求响应模型**，双方只交换 WebSocket 帧。

- 此后不再有 HTTP 方法、状态码、请求头那一套语义，数据以帧承载。
- 客户端不再发 GET 请求，服务端也不再回 HTTP 响应，彼此平等地收发消息。
- 连接由 WebSocket 子协议（如 chat、superchat）约定的应用层格式接管。
- 若需要再传 HTTP，必须另开新连接，不能在已升级的连接上混用两种语义。

> 常见误解是"升级后还能偶尔发个 HTTP 请求"——不行。一条连接要么 HTTP 要么 WebSocket，升级是单向、不可逆的。这也是为什么鉴权必须在握手阶段（仍是 HTTP 时）完成。

**速记**：升级后 **只讲帧语，不再有 HTTP 语义**。



### 服务端实现选型

#### ws 库是最流行的原生实现

**ws 库**：是 Node 生态中**最流行、最轻量的 WebSocket 实现**，直接遵循 RFC 6455，提供接近原生的 API 而不强加额外抽象。

- 安装方式：npm install ws，引入后使用其导出的 WebSocket.Server 类创建服务。
- 它只实现协议本身，不绑定房间、重连等高层概念，灵活度最高。
- API 简单，事件模型与 Node 的 EventEmitter 一致，学习成本低。
- 本篇所有服务端示例均以 ws 为主，便于看清协议本质。

> 选 ws 还是 socket.io 常被纠结：要"最贴近协议、最小依赖、完全自控"就选 ws；要"开箱即用的工程能力"再考虑 socket.io。本篇以 ws 打底，理解了 ws，再去用 socket.io 是顺理成章的叠加。

**速记**：ws **最流行、最轻、最贴近协议**。



#### socket.io 提供高层封装

**socket.io**：是一个**在 WebSocket 之上提供高层抽象**的库，封装了自动重连、房间、广播与传输降级等工程能力。

- 自动重连：客户端断线后自动尝试恢复，无需手写重连逻辑。
- 房间机制：内置 join 与 leave 与 to 等房间 API，按房间定向广播非常方便。
- 传输降级：在不支持 WebSocket 的旧环境中自动回退到长轮询。
- 代价是引入私有协议，与"纯 WebSocket 客户端"不互通，须前后端都使用 socket.io。

> socket.io 的"房间""命名空间"很香，但要付出"锁定自有协议"的代价：你无法用浏览器原生 WebSocket 客户端直连 socket.io 服务端。选型时权衡"开发效率"与"协议通用性"。

**速记**：socket.io **封装全、省心，但绑定私有协议**。



#### 原生 http 模块不直接支持

**原生实现门槛**：Node 内置的 http 模块**只能处理 HTTP，不直接理解 WebSocket 帧**，若坚持不引第三方库，需自行实现帧解析。

- http 模块能完成握手（识别 Upgrade 头并返回 101），但之后无法解析 WebSocket 帧。
- 完整实现需自行处理帧头解析、掩码、分片、ping/pong 等，工作量大且易错。
- 生产环境几乎都选用 ws 等成熟库，而非从零造轮子。
- 理解这一限制，才能明白"为何 Node 生态普遍依赖 ws 而非裸写"。

> 这并不是说原生 http 模块没用——它常被用来"托管"ws：先由 http 服务器处理普通请求，再把升级请求交给 ws。二者是配合关系，而非替代。

**速记**：原生 http **只管握手，帧解析得自己写**。



### 用 ws 搭建服务端

#### 安装与创建 WebSocket.Server

**WebSocket.Server 构造函数**：用于创建 WebSocket 服务器，其签名为 new WebSocket.Server(options)，options 可含 port 或 server 等字段决定监听方式。

- 参数 **options.port**：指定独立监听的端口，此时 ws 自行创建底层 http 服务器。
- 参数 **options.server**：传入一个已存在的 http.Server 实例，让 WebSocket 复用其端口，实现 HTTP 与 WebSocket 共存。
- 参数 **options.path**：仅接受该路径下的升级请求，便于在同一端口上区分不同服务。
- 创建后服务器即开始工作，新连接通过 connection 事件交付给业务代码。

```js
const WebSocket = require("ws");

// 方式一：独立端口
const wssStandalone = new WebSocket.Server({ port: 8080 });

// 方式二：挂载到已有 http 服务器
const http = require("http");
const server = http.createServer((req, res) => res.end("http"));
const wss = new WebSocket.Server({ server });

server.listen(3000, () => console.log("HTTP 与 WebSocket 同在 3000"));
```

> 选 port 还是 server 取决于是否要共存：单做 WebSocket 用 port 最简单；要同一端口既服务 HTTP 又升级 WebSocket，则必须把 ws 挂到已有 server 上（详见"与 HTTP 服务器共存"一节）。

**速记**：WebSocket.Server **传 port 独立、传 server 共存**。



#### connection 事件拿到连接

**connection 事件**：每当有客户端完成握手、成功建立 WebSocket 连接，ws 服务器便触发 **connection 事件**，回调传入代表该连接的 socket 对象。

- 回调第一参数是 **socket**（即 ws 封装的连接对象），后续收发都围绕它进行。
- 回调第二参数是原始的 **request** 对象，可从中读取握手时的请求头用于鉴权。
- 同一服务器会为每条连接各触发一次 connection，每条连接的 socket 相互独立。
- 通常在此事件里为该 socket 注册 message、close、error 等监听器。

```js
const WebSocket = require("ws");
const wss = new WebSocket.Server({ port: 8080 });

wss.on("connection", (socket, request) => {
  console.log("新连接来自：", request.socket.remoteAddress);
  // 在此为 socket 注册后续事件
});
```

> socket 与 request 的关系：request 是握手那次 HTTP 请求的产物，握手后即完成使命；socket 是升级后长期存在的连接对象。需要握手阶段的信息（如令牌）应趁 connection 时从 request 取，之后 request 不再相关。

**速记**：connection **给 socket 与 request，一条连接触发一次**。



#### message 与 close 与 error 事件

**连接的生命周期事件**：ws 的 socket 通过三个核心事件反映收发与状态变化，正确处理它们是稳定服务的基础。

- **message 事件**：收到客户端发来的消息时触发，回调参数为数据（字符串或 Buffer），是业务处理主入口。
- **close 事件**：连接正常关闭时触发，应在此清理该连接占用的资源与在线状态。
- **error 事件**：连接发生错误（如解析失败、异常断开）时触发，不监听会导致进程崩溃。
- 三个事件都应注册，缺一则可能出现"僵尸连接"或进程退出。

```js
wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    console.log("收到：", data.toString());
  });
  socket.on("close", () => console.log("连接关闭"));
  socket.on("error", (err) => console.error("连接出错：", err.message));
});
```

> message 事件回调的数据类型取决于发送内容：文本消息为字符串，二进制为 Buffer。若用 ws 默认的 handleProtocols 等未改配置，文本与二进制需分别判断（见"消息格式"一节）。务必挂 error，否则一条脏连接就能拖垮整个进程。

**速记**：socket 三事件 **收 message、知 close、捕 error**。



#### socket.send 发送消息

**send 方法**：用于向对端发送数据，其签名为 socket.send(data, options, callback)，data 可为字符串或 Buffer，发送结果通过回调或 error 事件反馈。

- 参数 **data**：要发送的内容，文本传字符串、二进制传 Buffer。
- 参数 **options**：可选，可指定是否压缩、是否二进制（如 { binary: true }）等。
- 参数 **callback**：可选，发送完成（含 flush 到内核）后执行，出错时通过 error 事件而非回调抛出。
- 发送前可判断 socket.readyState，避免向正在关闭或已关闭的连接写入。

```js
wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    const text = data.toString();
    socket.send("服务器收到：" + text); // 发回给同一连接
  });
});
```

> send 不保证对端已收到，它只保证数据已交给底层传输。向已关闭连接 send 会触发 error 事件（code 类似 EPIPE），务必在发送前检查 readyState 或在 error 中清理。readyState 取值包括 CONNECTING、OPEN、CLOSING、CLOSED。

**速记**：send **传字符串或 Buffer，发前查 readyState**。



### 消息格式、广播与房间

#### 文本消息需先序列化

**文本消息约定**：WebSocket 可发送纯文本，但当业务数据含结构（对象、数组）时，**必须先 JSON.stringify 序列化为字符串**再发送。

- 直接 socket.send(对象) 会因对象无法转为帧而报错或发送 "[object Object]"。
- 发送端约定格式后，接收端用 JSON.parse 还原，双方共用同一套字段约定。
- 文本帧默认以 UTF-8 编码传输，中文无需额外处理编码。
- 对体积敏感的场景可再压缩，但需收发双方协商一致。

```js
function buildMessage(type, payload) {
  return JSON.stringify({ type, payload, time: Date.now() });
}

wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    const incoming = JSON.parse(data.toString());
    socket.send(buildMessage("echo", incoming));
  });
});
```

> JSON 是文本协议的通用选择，但并非唯一：二进制可用 ArrayBuffer、TypedArray 或 Buffer 直接发送，避免序列化开销。高频、低延迟场景应评估"JSON 文本"与"二进制编码"的取舍。

**速记**：对象发送 **先 JSON.stringify，接收再 parse**。



#### 接收端判断数据类型

**数据类型判别**：ws 的 message 事件回调中，数据可能是**字符串（文本帧）或 Buffer（二进制帧）**，接收端需按实际情况处理。

- typeof data === "string" 时为文本帧，可直接 JSON.parse 或当普通文本。
- data instanceof Buffer（或 ArrayBuffer）时为二进制帧，需按约定的二进制格式解析。
- ws 提供 binaryType 配置，可决定二进制以 Buffer 还是 ArrayBuffer 形式交付。
- 混用文本与二进制时，务必在业务层标注"这条消息是哪种"，避免解析错位。

```js
wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    if (typeof data === "string") {
      handleText(JSON.parse(data));
    } else {
      handleBinary(data); // data 为 Buffer
    }
  });
});
```

> 许多初学者忽略二进制分支，结果收到文件或音频帧时 JSON.parse 直接抛错。发送端用哪种帧，接收端就要有对应分支；统一只用文本帧能省去判断，但会牺牲二进制效率。

**速记**：接收先 **判 string 还是 Buffer**，再分别处理。



#### 二进制用 Buffer 处理

**二进制消息**：当传输文件、图片、音视频或紧凑数据时，使用**二进制帧并由 Buffer 承载**，可省去文本编码开销、提升吞吐。

- 发送二进制：socket.send(bufferInstance, { binary: true }) 或直接传 Buffer。
- 接收二进制：在 message 事件中拿到 Buffer，按自定义格式（如长度前缀）解析。
- 二进制适合高频、结构化、体积大的数据，如游戏坐标、传感器采样、文件分片。
- 注意：二进制帧的解析逻辑需收发双方严格对齐，否则极易错位。

```js
wss.on("connection", (socket) => {
  socket.on("message", (data) => {
    if (Buffer.isBuffer(data)) {
      const length = data.readUInt32BE(0);
      const body = data.slice(4, 4 + length);
      console.log("二进制消息体长度：", body.length);
    }
  });
});
```

> 二进制虽高效，但可读性与调试性差。调试阶段可先用文本 JSON，确认逻辑无误后再切二进制优化；不要过早优化到难以排查问题。

**速记**：二进制 **用 Buffer 收发，格式需双方对齐**。



#### 用集合维护客户端实现广播

**广播（Broadcast）**：指**把同一条消息发给当前所有已连接客户端**，实现方式是维护一个客户端集合并遍历发送。

- 用 **Set** 保存所有活着的 socket，connection 时加入、close/error 时移除。
- 广播函数遍历该集合，对其中每个 socket 调用 send。
- 发送前检查 socket.readyState 为 OPEN，并跳过已销毁的连接，防止 EPIPE。
- 这是聊天室、实时推送等场景的基础能力。

```js
const clients = new Set();

function broadcastMessage(message, exceptSocket) {
  for (const socket of clients) {
    if (socket !== exceptSocket && socket.readyState === WebSocket.OPEN) {
      socket.send(message);
    }
  }
}

wss.on("connection", (socket) => {
  clients.add(socket);
  socket.on("message", (data) => broadcastMessage(data.toString(), socket));
  socket.on("close", () => clients.delete(socket));
  socket.on("error", () => clients.delete(socket));
});
```

> 广播前务必判 readyState 与 destroyed：一条正在关闭的连接被写入会触发 error 甚至崩溃。把"发前检查"写成广播函数的标配，能同时规避崩溃与泄漏。

**速记**：广播 = **Set 收集 + 遍历 send + 发前判 OPEN**。



#### 排除发送者自身

**定向广播**：在很多场景下，服务器需要把某客户端的消息**转发给除发送者之外的所有其他人**，而回执类消息才发给本人。

- 广播函数增加 exceptSocket 参数，遍历时跳过与发送者相同的 socket。
- 系统通知（如"某某上线"）通常广播给所有人，包括发送者无需特殊处理。
- 聊天消息一般转发给其他人，发送者由前端本地即时渲染，避免回环延迟。
- 是否排除自身取决于业务语义，应作为广播函数的可选参数而非硬编码。

```js
function broadcastToOthers(message, sender) {
  for (const socket of clients) {
    if (socket !== sender && socket.readyState === WebSocket.OPEN) {
      socket.send(message);
    }
  }
}
```

> 忘记排除发送者，会造成"自己发的消息又绕服务器一圈回来"的重复显示，前端若不做去重就会看到两条相同内容。明确"哪些场景排除、哪些不排除"是关键。

**速记**：排除自身 **靠 exceptSocket 参数跳过发送者**。



#### 按房间分组的简易实现

**房间（Room）**：是把客户端**按业务维度（如频道、群组）分组**的机制，使消息只在组内广播，实现多组隔离。

- 用 Map 维护，键为房间名，值为该房间的客户端 Set。
- 客户端通过某条消息（如 { type: "join", room: "A" }）声明加入房间。
- 广播时定位到对应房间的 Set 再遍历，而非全局 clients。
- 客户端离开或断开时，从所在房间的 Set 中移除。

```js
const rooms = new Map(); // 房间名 -> Set<socket>

function joinRoom(socket, roomName) {
  if (!rooms.has(roomName)) rooms.set(roomName, new Set());
  rooms.get(roomName).add(socket);
}

function broadcastToRoom(roomName, message) {
  const room = rooms.get(roomName);
  if (!room) return;
  for (const socket of room) {
    if (socket.readyState === WebSocket.OPEN) socket.send(message);
  }
}
```

> 房间与全局广播是"包含关系"：全局广播是"所有房间一起发"，房间广播是"只发某一组"。复杂业务可支持一个 socket 同时加入多个房间，离开时记得从每个房间都移除，否则仍会泄漏。

**速记**：房间 = **Map 分组，按组遍历广播**。



### 浏览器端 API 与心跳重连

#### 全局 WebSocket 类建立连接

**浏览器 WebSocket 类**：是**浏览器原生提供的全局构造函数**，无需引入任何库即可创建 WebSocket 连接，与服务端 ws 库天然互通。

- 其签名为 new WebSocket(url)，url 为 ws:// 或 wss:// 开头的连接地址。
- 创建即开始握手，浏览器自动构造包含 Upgrade 等头字段的握手请求。
- 连接状态由 readyState 反映：CONNECTING、OPEN、CLOSING、CLOSED 四态。
- 与服务端 ws 库遵循同一 RFC 6455，因此前后端协议天然一致。

```js
const socket = new WebSocket("ws://127.0.0.1:8080/chat");
console.log("连接状态：", socket.readyState); // 0 表示 CONNECTING
```

> 浏览器原生 WebSocket 是"最小可用"的：它没有自动重连、没有房间，一切需自己写。若需要工程化能力且前后端都可控，可改用 socket.io 的浏览器端；但若追求轻量与标准互通，原生 API 足够。

**速记**：浏览器 **new WebSocket(url)** 即建连，前后端互通。



#### onopen 与 onmessage 等事件

**四类事件回调**：浏览器 WebSocket 对象通过 **onopen、onmessage、onclose、onerror** 四个属性回调，反映连接的生命周期与收发。

- **onopen**：连接建立成功（握手完成）后触发，可在此开始发送首条消息。
- **onmessage**：收到服务端消息时触发，event.data 为消息内容（字符串或 Blob/ArrayBuffer）。
- **onclose**：连接关闭时触发，event.code 与 event.reason 说明关闭原因。
- **onerror**：发生错误时触发，通常紧接着会触发 onclose。

```js
const socket = new WebSocket("ws://127.0.0.1:8080/chat");

socket.onopen = () => console.log("连接已建立");
socket.onmessage = (event) => console.log("收到：", event.data);
socket.onclose = (event) => console.log("关闭，code：", event.code);
socket.onerror = (event) => console.error("出错：", event);
```

> onmessage 的 event.data 类型由 binaryType 决定：默认文本为字符串，设了 socket.binaryType = "arraybuffer" 后二进制为 ArrayBuffer。与服务端约定一致即可正确解析。

**速记**：前端四回调 **open、message、close、error**。



#### send 与 close 方法

**前端收发方法**：浏览器 WebSocket 对象提供 **send** 发送数据、**close** 主动关闭连接，二者是客户端最常用的两个动作。

- **send 方法**：签名为 socket.send(data)，data 可为字符串、Blob 或 ArrayBuffer；发送对象前需 JSON.stringify。
- **close 方法**：签名为 socket.close(code, reason)，可带关闭码与原因，调用后连接进入 CLOSING 直至关闭。
- 只有在 readyState 为 OPEN（值为 1）时 send 才有效，否则会抛错。
- 页面卸载（beforeunload）时主动 close，有助于服务端及时清理连接。

```js
socket.onopen = () => {
  socket.send(JSON.stringify({ type: "login", name: "小明" }));
};

function sendChat(text) {
  if (socket.readyState === WebSocket.OPEN) {
    socket.send(JSON.stringify({ type: "chat", text }));
  }
}

// 离开页面时主动关闭
window.addEventListener("beforeunload", () => socket.close());
```

> 很多人直接 socket.send 而不判 readyState，结果在连接尚未 OPEN 时抛出 InvalidStateError。安全的写法是封装一个 send 守卫，状态非 OPEN 时排队或丢弃。

**速记**：前端 **send 发送、close 关闭，发前判 OPEN**。



#### 可运行的前端示例代码

**完整前端片段**：下面是一段可直接放进 HTML 页面的浏览器端代码，连接 WebSocket 服务端、收发聊天消息并展示上下线提示。

- 连接建立后发送登录消息，声明昵称。
- 收到消息按 type 区分：chat 显示对话、system 显示系统提示。
- 提供输入框与发送按钮，把用户输入通过 send 发给服务端。
- 配合下一节的服务端群聊代码即可联调。

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>WebSocket 群聊</title>
</head>
<body>
  <ul id="log"></ul>
  <input id="text" placeholder="说点什么">
  <button id="send">发送</button>

  <script>
    const log = document.getElementById("log");
    const input = document.getElementById("text");
    const socket = new WebSocket("ws://127.0.0.1:8080/chat");

    function append(text) {
      const li = document.createElement("li");
      li.textContent = text;
      log.appendChild(li);
    }

    socket.onopen = () => {
      socket.send(JSON.stringify({ type: "login", name: "访客" + Date.now() }));
    };
    socket.onmessage = (event) => {
      const msg = JSON.parse(event.data);
      if (msg.type === "system") append("【系统】" + msg.text);
      else if (msg.type === "chat") append(msg.name + "：" + msg.text);
    };

    document.getElementById("send").onclick = () => {
      if (socket.readyState === WebSocket.OPEN && input.value) {
        socket.send(JSON.stringify({ type: "chat", text: input.value }));
        input.value = "";
      }
    };
  </script>
</body>
</html>
```

> 该片段刻意保持最小可用：未做重连、未做错误处理、昵称也未去重。它用于验证"前后端能否通"，工程化能力（重连、鉴权）请结合后文补充。

**速记**：前端示例 **连上登录、收消息按 type 分流、输入经 send 发出**。



#### ping 与 pong 帧维持连接

**心跳（Heartbeat）**：是**双方周期性互发轻量探测帧（ping/pong）**以确认连接存活的机制，用于及时发现并清理"逻辑已断"的连接。

- ws 服务端可调用 **socket.ping** 发送 ping 帧，浏览器等客户端收到后自动回 pong。
- ws 在收到对端 pong 时触发 **pong 事件**，可用于刷新"最后活跃时间"。
- 客户端不发应用层 ping 也能被保活：浏览器原生 API 不暴露 ping 发送，但服务端发 ping 时浏览器会自动应答。
- 心跳频率需权衡：太频繁浪费资源，太稀疏发现死连接慢，常见取值 15 至 60 秒。

```js
wss.on("connection", (socket) => {
  socket.on("pong", () => {
    socket.isAlive = true; // 收到 pong 标记存活
  });

  socket.isAlive = true;
  const heartbeat = setInterval(() => {
    if (socket.isAlive === false) {
      clearInterval(heartbeat);
      socket.terminate(); // 未回应则强断
      return;
    }
    socket.isAlive = false;
    socket.ping(); // 发送 ping，等待 pong
  }, 30000);
});
```

> ping/pong 是协议层的控制帧，与业务消息无关，不占用应用数据通道。它解决的是"TCP 连接还在、但应用层已无响应"的半死状态——这正是单纯依赖 TCP keep-alive 不够快所留下的空档。

**速记**：心跳 **服务端 ping、客户端自动 pong，超时即剔除**。



#### 服务端定时剔除无响应连接

**超时剔除**：服务端通过**定时器周期性检查每条连接的最近活跃时间**，对超时未响应心跳的连接主动 terminate，回收资源。

- 维护每个 socket 的 isAlive 或 lastActive 标记，每次收到消息或 pong 时刷新。
- 定时器（如每 30 秒）遍历所有连接，未存活者调用 socket.terminate 强制断开。
- terminate 与 close 不同：terminate 立即销毁底层连接，不等待帧优雅关闭。
- 剔除时同步从 clients 集合或房间中移除，避免向死连接继续发送。

```js
function startHeartbeatCheck() {
  const interval = setInterval(() => {
    for (const socket of clients) {
      if (socket.isAlive === false) {
        socket.terminate();
        clients.delete(socket);
        continue;
      }
      socket.isAlive = false;
      socket.ping();
    }
  }, 30000);
  return interval;
}
```

> terminate 比 close 更"硬"：它不等对端确认就直接切断，适合清理已无响应的连接。但滥用 terminate 会误杀弱网下的慢连接，因此心跳阈值应远大于正常网络抖动时长。

**速记**：剔除 **定时扫存活标记，不活就 terminate**。



#### 客户端指数退避重连

**断线重连**：客户端在连接意外关闭后**自动尝试重新建立连接**，并采用指数退避避免频繁冲击服务端。

- 监听 onclose 与 onerror，在连接非正常关闭时启动重连计时器。
- **指数退避**：每次重连失败后等待时长翻倍（如 1 秒、2 秒、4 秒），上限封顶（如 30 秒）。
- 重连成功则重置退避计数器，恢复正常发送。
- 应设最大重试次数或允许手动取消，避免永久无效重试。

```js
let reconnectDelay = 1000;
const maxDelay = 30000;

function connect() {
  const socket = new WebSocket("ws://127.0.0.1:8080/chat");

  socket.onopen = () => {
    reconnectDelay = 1000; // 重置退避
    socket.send(JSON.stringify({ type: "login", name: "访客" }));
  };
  socket.onclose = () => {
    setTimeout(connect, reconnectDelay);
    reconnectDelay = Math.min(reconnectDelay * 2, maxDelay);
  };
}
connect();
```

> 指数退避的意义是"网络恢复前别雪崩式重连"：若服务端短暂宕机，成百客户端以固定 1 秒狂连会放大故障。翻倍加封顶既给恢复留时间，又避免退避无限拉长导致迟迟连不上。

**速记**：重连 **指数退避翻倍、封顶，连上即归零**。



### 与 HTTP 服务器共存及安全限制

#### 同一端口先处理 HTTP 再升级

**端口共存**：通过把 ws 服务器**挂载到已有的 http.Server 上**，可在同一端口同时处理普通 HTTP 请求与 WebSocket 升级，两者互不干扰。

- 创建 http 服务器处理常规请求（页面、接口），再 new WebSocket.Server({ server }) 复用其端口。
- 客户端发起 HTTP 请求时，http 回调正常响应；发起带 Upgrade 头的请求时，ws 自动接管握手。
- 这样部署只需暴露一个端口，便于防火墙与反向代理配置。
- 注意：两条请求是同一端口上的不同连接，并非"一条连接混用两种协议"。

```js
const http = require("http");
const WebSocket = require("ws");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("这是普通 HTTP 响应");
});

const wss = new WebSocket.Server({ server });
wss.on("connection", (socket) => socket.send("WebSocket 已连接"));

server.listen(3000, () => console.log("3000 同时服务 HTTP 与 WebSocket"));
```

> 共存的关键是"复用 server 而非另开端口"。若分别监听两个端口，反向代理与防火墙就要开两个口子，徒增复杂度。但需确认代理（如 Nginx）对 Upgrade 头做了正确转发。

**速记**：共存 **ws 挂到 http 的 server，同端口分流**。



#### noServer 模式自行处理 upgrade

**noServer 模式**：是 ws 提供的**不自动监听、由开发者手动处理 upgrade 事件**的高级用法，用于完全掌控升级逻辑。

- 创建时传 new WebSocket.Server({ noServer: true })，ws 不再自行绑定任何端口。
- 在 http 服务器的 upgrade 事件里，调用 **wss.handleUpgrade(request, socket, head, callback)** 完成握手。
- 可在 handleUpgrade 之前自行判断 path、鉴权、Origin 等，决定是否允许升级。
- 适合一个 http 服务器要按路径把不同升级请求分发给多个 WebSocket 服务器的场景。

```js
const http = require("http");
const WebSocket = require("ws");

const server = http.createServer((req, res) => res.end("http"));
const wss = new WebSocket.Server({ noServer: true });

server.on("upgrade", (request, socket, head) => {
  wss.handleUpgrade(request, socket, head, (ws) => {
    wss.emit("connection", ws, request);
  });
});

server.listen(3000);
```

> noServer 把"何时、是否升级"的决定权交给你。代价是必须自己接 upgrade 事件并调用 handleUpgrade，漏写会导致升级请求无人处理、连接挂起。它常与鉴权、路径路由配合使用。

**速记**：noServer **手动接 upgrade，自己掌控握手**。



#### 在 upgrade 阶段完成鉴权

**握手鉴权**：由于**升级后连接脱离 HTTP 语义**，令牌校验必须在握手阶段（仍是 HTTP 请求时）完成，最自然的落点是 upgrade 事件。

- 客户端在握手请求的请求头里带上令牌，如 Authorization 或自定义头（注意浏览器原生 API 仅允许少数头，常改用查询参数）。
- 服务端在 upgrade 回调或 handleUpgrade 前解析 request.headers / request.url 取出令牌并校验。
- 校验失败则不调用 handleUpgrade，直接 socket.destroy 拒绝升级，连接以 HTTP 层失败告终。
- 鉴权通过后，可在 connection 时为该 socket 绑定用户身份，供后续广播使用。

```js
server.on("upgrade", (request, socket, head) => {
  const token = new URL(request.url, "http://x").searchParams.get("token");
  if (!isValidToken(token)) {
    socket.destroy(); // 鉴权失败，拒绝升级
    return;
  }
  wss.handleUpgrade(request, socket, head, (ws) => {
    ws.user = getUserFromToken(token);
    wss.emit("connection", ws, request);
  });
});
```

> 浏览器原生 WebSocket 构造时**无法自定义请求头**（除少数安全头外），因此前端常把令牌放在 URL 查询参数里随握手发送。无论用头还是查询，核心原则不变：鉴权必须在升级前做完，因为升级后没有"再登录"的机会。

**速记**：鉴权 **必须放在 upgrade 阶段，升级后无法补**。



#### 使用 wss 加密传输

**wss 加密**：生产环境中 WebSocket 连接**应使用 wss（即 TLS 之上的 WebSocket）**，避免数据以明文在公网传输。

- wss 对应 HTTPS 的 443 端口，在 TCP 之上先做 TLS 握手再走 WebSocket 握手。
- 明文 ws 等同于明文 HTTP，令牌、消息内容均可被中间人窃听或篡改。
- Node 侧可通过 https 模块创建带证书的服务器，再把 ws 挂到该 https 服务器上。
- 反向代理（如 Nginx）通常负责终止 TLS，后端 ws 在内部以明文通信，由代理保障外部加密。

```js
const https = require("https");
const fs = require("fs");
const WebSocket = require("ws");

const server = https.createServer({
  cert: fs.readFileSync("cert.pem"),
  key: fs.readFileSync("key.pem"),
});

const wss = new WebSocket.Server({ server });
server.listen(443, () => console.log("wss 已在 443 提供加密服务"));
```

> 即便内网也建议 wss：内网不等于可信，横向移动攻击常利用明文通道。把"全程加密"作为默认，比事后补救更稳妥。证书可由 Let's Encrypt 等免费签发。

**速记**：生产 **必用 wss，明文 ws 等同裸奔**。



#### 校验 Origin 防止跨站劫持

**Origin 校验**：服务端应在握手时**检查请求头中的 Origin**，拒绝来自非白名单域名的升级请求，防范跨站 WebSocket 劫持。

- 浏览器会在握手请求中带 Origin 头，标明发起页面的源（协议、域名、端口）。
- 服务端比对 Origin 与白名单，不在名单内则拒绝升级（destroy 连接）。
- 这能防止恶意网页偷偷连上你的 WebSocket 服务、冒用用户身份发消息。
- 注意：Origin 可被非浏览器客户端伪造，因此它只是"降低风险"而非"绝对信任"手段。

```js
const ALLOWED = new Set(["https://example.com"]);

server.on("upgrade", (request, socket, head) => {
  const origin = request.headers.origin;
  if (!ALLOWED.has(origin)) {
    socket.destroy(); // 来源不在白名单，拒绝
    return;
  }
  wss.handleUpgrade(request, socket, head, (ws) => {
    wss.emit("connection", ws, request);
  });
});
```

> 不要误以为"校验 Origin 就安全了"：爬虫、恶意脚本可用任意 Origin 发起请求绕过它。Origin 校验是低成本的第一道防线，真正的访问控制仍需配合令牌鉴权。

**速记**：Origin **白名单拦截跨站，但非绝对防线**。



#### 限制消息大小与频率

**流量限制**：为防止单个连接通过**超大消息或高频发送**拖垮服务，应在应用层限制消息体积与发送频率。

- **体积限制**：ws 提供 maxPayload 选项，超出则连接被自动关闭，避免内存被大消息吃满。
- **频率限制**：维护每连接的发送计数，超过阈值（如每秒 N 条）则临时拒绝或断开。
- **慢速攻击**：极慢发送但长期占连也会消耗资源，需配合心跳超时清理。
- 限制应在"来源处"做，而非等消息堆积到内存爆掉再处理。

```js
const wss = new WebSocket.Server({
  server,
  maxPayload: 1024 * 1024, // 单帧最大 1MB，超限自动关闭
});

const sendCounts = new Map();
function rateLimit(socket) {
  const now = Date.now();
  const rec = sendCounts.get(socket) || { count: 0, ts: now };
  if (now - rec.ts > 1000) { rec.count = 0; rec.ts = now; }
  rec.count += 1;
  sendCounts.set(socket, rec);
  return rec.count <= 10; // 每秒最多 10 条
}
```

> maxPayload 只限单条消息大小，限不住"海量小消息"的频率攻击；而频率限制又防不住"单条巨帧"。二者需组合使用，才能覆盖"大"与"多"两类资源耗尽风险。

**速记**：限制 **maxPayload 限大小、计数限频率，双管齐下**。



#### 鉴权不能只依赖前端

**鉴权原则**：WebSocket 的**安全校验必须在服务端完成**，前端传来的身份、权限信息一律不可信，需服务端独立验证。

- 前端可轻易伪造昵称、用户 ID，绝不能用客户端自报身份作为权限依据。
- 令牌应由服务端签发与校验（如 JWT），握手或首条消息中由服务端验证有效性。
- 权限变更（如被踢出、封禁）需服务端主动推送或在其下次操作时校验，而非依赖前端自觉。
- 任何"隐藏元素、禁用按钮"都是 UX 而非安全，真正的闸门永远在服务端。

> 把鉴权寄托于前端是经典误区：前端代码对用户完全可见、可篡改。WebSocket 虽是全双工长连接，但安全模型与 HTTP 一致——"永远不信任客户端输入"。

**速记**：鉴权 **服务端校验，前端输入皆不可信**。



### 实战：完整群聊室

#### 服务端广播与上下线提示

**群聊服务端**：整合前面所学，实现一个**支持昵称、广播消息、上下线系统提示**的群聊室服务端，使用 ws 与同一端口的 http 共存。

- 用 Set 维护所有连接，用 Map 记录每个 socket 的昵称。
- 首条消息视为昵称；之后消息广播给其他人，并附上昵称。
- 有人上线或下线时，向全体广播系统提示。
- 接入心跳剔除，清理掉线连接；接入 Origin 与 maxPayload 做基础防护。

```js
const http = require("http");
const WebSocket = require("ws");

const server = http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("群聊室 HTTP 入口");
});

const wss = new WebSocket.Server({ server, maxPayload: 1024 * 1024 });
const clients = new Map(); // socket -> 昵称

function sendTo(socket, type, payload) {
  if (socket.readyState === WebSocket.OPEN) {
    socket.send(JSON.stringify({ type, ...payload }));
  }
}
function broadcast(type, payload, except) {
  for (const socket of clients.keys()) {
    if (socket !== except) sendTo(socket, type, payload);
  }
}

wss.on("connection", (socket) => {
  clients.set(socket, null);
  socket.isAlive = true;
  socket.on("pong", () => (socket.isAlive = true));

  socket.on("message", (raw) => {
    const msg = JSON.parse(raw.toString());
    if (msg.type === "login") {
      const name = msg.name || "匿名";
      clients.set(socket, name);
      broadcast("system", { text: name + " 上线了" }, socket);
      return;
    }
    if (msg.type === "chat") {
      broadcast("chat", { name: clients.get(socket), text: msg.text }, null);
    }
  });

  socket.on("close", () => {
    const name = clients.get(socket) || "匿名";
    clients.delete(socket);
    broadcast("system", { text: name + " 下线了" }, null);
  });
  socket.on("error", () => clients.delete(socket));
});

const heartbeat = setInterval(() => {
  for (const socket of clients.keys()) {
    if (socket.isAlive === false) { socket.terminate(); clients.delete(socket); continue; }
    socket.isAlive = false;
    socket.ping();
  }
}, 30000);

wss.on("close", () => clearInterval(heartbeat));
server.listen(3000, () => console.log("群聊室运行在 http://127.0.0.1:3000"));
```

> 该服务端把"连接管理、消息广播、上下线提示、心跳"合为一体，是前面各考点的综合演练。工程化时还应补充：昵称去重、敏感词过滤、鉴权、历史消息持久化、水平扩展（多实例需借助 Redis 发布订阅做跨进程广播）。

**速记**：群聊服务端 = **Map 记昵称 + 广播 + 系统提示 + 心跳清理**。



#### 客户端收发与展示

**群聊前端**：在前端示例基础上，连接群聊服务端、发送登录与聊天消息，并把系统提示与对话分别渲染到页面列表。

- 连接后先发 login 消息登记昵称，之后发 chat 消息参与对话。
- onmessage 中按 type 分流：system 渲染为灰色系统行、chat 渲染为"昵称：内容"。
- 配合服务端的上下线广播，页面能实时看到谁来了、谁走了。
- 可叠加前文的指数退避重连，提升弱网体验。

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>群聊室</title>
</head>
<body>
  <ul id="log"></ul>
  <input id="name" placeholder="昵称">
  <button id="login">进入</button>
  <input id="text" placeholder="消息">
  <button id="send">发送</button>

  <script>
    const log = document.getElementById("log");
    const socket = new WebSocket("ws://127.0.0.1:3000");

    function append(text, isSystem) {
      const li = document.createElement("li");
      li.textContent = text;
      if (isSystem) li.style.color = "gray";
      log.appendChild(li);
    }

    socket.onmessage = (event) => {
      const msg = JSON.parse(event.data);
      if (msg.type === "system") append("【系统】" + msg.text, true);
      else if (msg.type === "chat") append(msg.name + "：" + msg.text, false);
    };

    document.getElementById("login").onclick = () => {
      const name = document.getElementById("name").value;
      socket.send(JSON.stringify({ type: "login", name }));
    };
    document.getElementById("send").onclick = () => {
      const text = document.getElementById("text").value;
      if (socket.readyState === WebSocket.OPEN && text) {
        socket.send(JSON.stringify({ type: "chat", text }));
        document.getElementById("text").value = "";
      }
    };
  </script>
</body>
</html>
```

> 把客户端与服务端两段代码分别保存运行，即可获得一个可实时收发的群聊室。这既是本篇内容的综合验收，也是后续扩展（鉴权、房间、持久化）的起点。

**速记**：群聊前端 **先 login 后进 chat，按 type 分流渲染**。



### 常见坑

#### 连接数过多导致内存压力

**连接膨胀**：WebSocket 是长连接，**每一条都长期占用内存与文件描述符**，海量并发连接若不加管理会拖垮服务器。

- 单进程能维持的连接数受文件描述符上限与内存限制，并非无限。
- 未清理的断开连接（见前文泄漏坑）会持续累积，进一步加剧压力。
- 缓解手段：设单实例连接上限、及时心跳剔除死连接、用集群横向扩展。
- 横向扩展时，跨进程广播需借助 Redis 等外部通道，单实例的 clients 集合无法跨进程共享。

> 长连接与短连接的成本模型不同：HTTP 请求来去都快，资源可快速回收；WebSocket 一占就是几分钟甚至几小时。评估容量时必须按"同时在线峰值"而非"每秒请求数"来规划。

**速记**：长连接 **占资源久，按在线峰值规划容量**。



#### 未处理异常导致服务崩溃

**未捕获错误**：与 http、net 一致，WebSocket 的 **socket 或 server 上若发生未监听的 error，Node 会以未处理异常终止进程**，所有在线连接一并断开。

- 每条 socket 都应挂 error 事件，至少打印日志并执行清理（从集合移除）。
- 解析客户端消息时（如 JSON.parse）要用 try/catch 包裹，非法消息不应拖垮连接。
- 服务端整体可挂 process.on("uncaughtException") 兜底，但这只是最后防线，根因仍要修。
- connection 回调里的同步异常同样致命，关键逻辑务必防御性编码。

```js
wss.on("connection", (socket) => {
  socket.on("message", (raw) => {
    try {
      const msg = JSON.parse(raw.toString());
      handle(msg);
    } catch (err) {
      console.error("消息解析失败：", err.message);
      // 仅拒绝该消息，不关闭整个连接
    }
  });
  socket.on("error", () => clients.delete(socket));
});
```

> 单线程模型下，一个未捕获异常就让主线程退出——这是第 8 篇"单线程"结论在 WebSocket 场景的延续。养成"建连接必挂 error、解析必 try"的习惯，是线上稳定的底线。

**速记**：异常 **崩进程、断全部连接，必挂 error 与 try**。



#### 代理与负载均衡未配置协议升级

**代理升级支持**：在 Nginx 等反向代理或负载均衡之后部署 WebSocket 时，**必须显式配置对 Upgrade 与 Connection 头的转发**，否则握手无法完成。

- 默认反向代理常把 WebSocket 握手当作普通 HTTP 请求处理，未转发 Upgrade 头会导致 101 无法返回。
- Nginx 需设置 proxy_set_header Upgrade $http_upgrade 与 proxy_set_header Connection "upgrade" 等指令。
- 负载均衡还需"粘滞会话"或共享状态，否则同一连接的多帧可能被分发到不同后端。
- 代理的超时设置过短会误杀长连接，应调大 proxy_read_timeout 等参数。

```text
location /chat/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
}
```

> 本地直连好好的服务，一上代理就握手失败，十有八九是 Upgrade 头没透传。配置代理时把它当作"WebSocket 能否上线"的前置条件，而非可选项。

**速记**：代理 **必须透传 Upgrade 头，否则握手失败**。
