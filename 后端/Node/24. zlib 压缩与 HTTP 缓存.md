## zlib 压缩与 HTTP 缓存

### zlib 模块定位与三种压缩算法

#### zlib 是内置的压缩模块

**zlib 模块**：是 Node 的**内置核心模块**，无需安装即可 require 引入，提供 gzip、deflate、brotli 三类压缩与解压缩能力，底层基于 Transform 流实现。

- 它封装了 zlib 库（与 libuv 同源的 C 库），在 JavaScript 侧暴露统一的流与缓冲接口。
- 因为是内置模块，直接通过 const zlib = require("zlib") 取用，没有外部依赖。
- 它产生与消费的是**标准压缩格式**，浏览器、Nginx、CDN 都能识别与还原，因此常用于网络传输。

> zlib 与第 13 篇的 Stream 流天然耦合：它的压缩流本质就是 Transform 流，写入明文、读出密文。理解流的管道（pipe）机制，是看懂本文所有示例的前提。

**速记**：zlib **内置、基于 Transform 流的标准压缩**。



#### 三种压缩算法 gzip deflate brotli

**三类算法**：zlib 支持 gzip、deflate、brotli 三种主流压缩格式，它们压缩率与兼容性各不相同，需按场景选择。

- **gzip**：最通用的格式，HTTP 场景几乎必备，所有现代浏览器与代理都支持，扩展名常为 .gz。
- **deflate**：RFC 1951 定义的原始算法，HTTP 中实际以 zlib 格式（带头）传输，兼容性略弱于 gzip，使用较少。
- **brotli**：Google 推出的新算法，压缩率通常高于 gzip，现代浏览器广泛支持，Node 也内置支持，适合追求极致体积的场景。

> gzip 与 brotli 是网页传输的首选；deflate 在 Web 上因历史实现分歧（raw deflate 还是 zlib-wrapped）而较少使用。选型口诀：通用选 gzip，追求更小体积且客户端支持时选 brotli。

**速记**：gzip **最通用**、brotli **更高压缩率**、deflate **少用**。



#### 六种创建压缩流的方法

**创建流方法**：zlib 提供三组对称的创建方法，分别产出对应的压缩流与解压缩流，均为 Transform 流，可直接接入管道。

- 完整创建形如 **zlib.createGzip([options])**，返回一个 gzip 压缩的 Transform 流。
- 完整创建形如 **zlib.createGunzip([options])**，返回对应的 gzip 解压缩流。
- 完整创建形如 **zlib.createDeflate([options])** 与 **zlib.createInflate([options])**，分别是 deflate 的压缩与解压缩流。
- 完整创建形如 **zlib.createBrotliCompress([options])** 与 **zlib.createBrotliDecompress([options])**，分别是 brotli 的压缩与解压缩流，Node 11.11 起内置。

```js
const zlib = require("zlib");

// 六种创建方法，均返回 Transform 流
const gzip = zlib.createGzip();
const gunzip = zlib.createGunzip();
const deflate = zlib.createDeflate();
const inflate = zlib.createInflate();
const brotli = zlib.createBrotliCompress();
const unbrotli = zlib.createBrotliDecompress();

console.log(gzip instanceof require("stream").Transform); // true
```

> 创建流时传入的 options 是可选的，缺省即使用默认压缩级别。压缩与解压缩方法必须成对使用：用 createGzip 压的要用 createGunzip 解，混用会报数据格式错误。

**速记**：六种方法 **压缩与解压成对、均为 Transform 流**。



### 流式压缩与解压

#### 用 createGzip 配合管道压缩文件

**管道压缩**：把**可读流经 createGzip 变换后接入可写流**，即可在恒定内存下完成文件压缩，这正是第 13 篇所述 Transform 流的经典用法。

- 读取源文件用 **fs.createReadStream(path)**，得到可读流。
- 中间插入 **zlib.createGzip()**，明文写入、压缩后流出。
- 末端用 **fs.createWriteStream(path + ".gz")** 接住压缩结果，三段以 .pipe 串联。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");

function compressFile(src, dst) {
  const readable = fs.createReadStream(src);
  const gzip = zlib.createGzip();
  const writable = fs.createWriteStream(dst);
  readable.pipe(gzip).pipe(writable);
  writable.on("finish", () => console.log("压缩完成：" + dst));
}

const src = path.join(__dirname, "note.txt");
compressFile(src, src + ".gz");
```

> pipe 会自动把上游数据推入 gzip 变换、再把压缩结果推入写流，并在源头结束时自动关闭整条链。无需手动监听 data 事件拼接，这正是流相比 readFile 一次性读入的优势。

**速记**：读流 → **createGzip → 写流**，管道串联即压缩。



#### 用 createGunzip 解压文件

**管道解压**：把**压缩文件的可读流经 createGunzip 还原后写入目标文件**，是压缩的逆过程，写法与压缩完全对称。

- 源是 .gz 文件的可读流，中间插入 **zlib.createGunzip()**。
- 解出的明文直接写入目标可读流，三段同样以 .pipe 串联。
- 由于是 Transform 流语义，写入压缩字节、读出原始字节，因果对应。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");

function decompressFile(srcGz, dst) {
  const readable = fs.createReadStream(srcGz);
  const gunzip = zlib.createGunzip();
  const writable = fs.createWriteStream(dst);
  readable.pipe(gunzip).pipe(writable);
  writable.on("finish", () => console.log("解压完成：" + dst));
}

const gz = path.join(__dirname, "note.txt.gz");
decompressFile(gz, path.join(__dirname, "note.restored.txt"));
```

> 解压方法必须与压缩方法匹配：gzip 对应 gunzip、deflate 对应 inflate、brotli 对应 brotliDecompress。用错的解压流会立即抛出 Z_DATA_ERROR 之类的数据错误。

**速记**：解压 = **读压缩流 → createGunzip → 写明文流**。



#### 用 pipeline 统一错误与收尾

**pipeline 优势**：对于**多段流串联**，应优先用 **stream.pipelines**（Promise 版来自 stream/promises）替代裸 pipe，因为它会统一收集任意一段的错误并自动清理。

- 完整签名为 **pipeline(source, ...transforms, destination, callback)**，每段错误都传播到最终结果。
- Promise 版形如 **pipeline(readable, transform, writable)** 配合 await，用 try/catch 兜住全链异常。
- 它会在完成后自动销毁各流，避免句柄泄漏，是官方推荐写法。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");
const { pipeline } = require("stream/promises");

async function compressWithPipeline(src, dst) {
  try {
    await pipeline(
      fs.createReadStream(src),
      zlib.createGzip(),
      fs.createWriteStream(dst)
    );
    console.log("pipeline 压缩完成");
  } catch (err) {
    console.error("任意一段出错都被这里捕获：", err);
  }
}

compressWithPipeline(path.join(__dirname, "note.txt"), path.join(__dirname, "note.txt.gz"));
```

> 裸 pipe 不会把上游错误自动传给下游，每段都需单独挂 error 监听（见第 13 篇）。pipeline 一次性解决了错误处理与资源清理，新代码应优先选用。

**速记**：多段串联 **pipeline 统一错误、自动清理**。



### 回调式、同步式与 Promise 式 API

#### 回调式 gzip 与 gunzip

**缓冲式 API**：除了流，zlib 还提供**直接对 Buffer 整体压缩**的函数，最基础的是回调式 **zlib.gzip(buffer[, options], callback)** 与 **zlib.gunzip(buffer[, options], callback)**。

- 完整签名为 **zlib.gzip(buffer, options, callback)**，buffer 是待压缩的 Buffer，options 可选。
- callback 形如 **(err, buffer) => {}**，成功时 err 为 null、buffer 为压缩结果。
- 解压对称：完整签名为 **zlib.gunzip(buffer, options, callback)**，回调同样返回 (err, buffer)。

```js
const zlib = require("zlib");

const input = Buffer.from("需要压缩的文本内容，可以很长很长……");

zlib.gzip(input, (err, compressed) => {
  if (err) throw err;
  console.log("压缩后字节数：", compressed.length);
  zlib.gunzip(compressed, (err2, restored) => {
    if (err2) throw err2;
    console.log("解压还原：", restored.toString("utf8"));
  });
});
```

> 缓冲式 API 把数据整体读进内存再压，适合**已完整在内存中的小数据**；若数据是文件或大响应，应改回流式 API 以控制内存。回调层层嵌套也让代码不够线性。

**速记**：gzip/gunzip **缓冲式、回调返回 (err, buffer)**。



#### 同步式 gzipSync 适合小数据

**同步 API**：当数据量小且发生在脚本或工具链中时，可用**同步阻塞**版本 **zlib.gzipSync(buffer[, options])**，它直接返回压缩后的 Buffer，不接收回调。

- 完整签名为 **zlib.gzipSync(buffer, options)**，返回值是压缩后的 Buffer。
- 解压对称：**zlib.gunzipSync(buffer[, options])** 直接返回还原的 Buffer。
- 因为是同步阻塞，会**卡住事件循环**，只适合小数据或启动期一次性处理。

```js
const zlib = require("zlib");
const fs = require("fs");

const input = fs.readFileSync("config.json"); // 小文件，一次性读入
const compressed = zlib.gzipSync(input);       // 同步得到结果
fs.writeFileSync("config.json.gz", compressed);
console.log("同步压缩完成，字节数：", compressed.length);
```

> [!CAUTION]
> **注意内容**：同步 API 在**服务器请求处理路径上禁止使用**，否则会阻塞整个事件循环、拖垮所有并发连接；它只适合 CLI 脚本、构建工具、构建期资源预压缩等一次性场景。

**速记**：gzipSync **同步阻塞、仅限小数据或脚本**。



#### Promise 式 API 配合 async/await

**Promise 化**：Node 提供两种方式把缓冲式 API 包装成 Promise——直接取 **zlib.promises** 命名空间，或用 **util.promisify** 包装传统回调式函数，二者都可与 async/await 配合。

- 命名空间用法：**zlib.promises.gzip(buffer[, options])** 返回 Promise，resolve 出压缩 Buffer。
- 包装用法：先 **const { promisify } = require("util")**，再 **const gzipAsync = promisify(zlib.gzip)**，随后 await gzipAsync(buffer)。
- Promise 版本消除了回调嵌套，使压缩逻辑与前后代码线性衔接。

```js
const zlib = require("zlib");
const { promisify } = require("util");

const gzipAsync = promisify(zlib.gzip);
const gunzipAsync = promisify(zlib.gunzip);

async function roundTrip(text) {
  const input = Buffer.from(text);
  const compressed = await gzipAsync(input);
  const restored = await gunzipAsync(compressed);
  return restored.toString("utf8");
}

roundTrip("Hello zlib Promise").then((out) => console.log(out));
```

> 选择建议：仍需要处理大量数据或文件流时，优先用第 13 篇的 stream/promises pipeline；只对**已完整在内存的小 Buffer**使用 zlib.promises 或 promisify 包装。

**速记**：Promise 版 **zlib.promises 或 promisify + await**。



### 压缩选项与压缩率的现实边界

#### level 压缩级别 0 到 9

**压缩级别**：创建压缩流或调用缓冲式函数时，可传入 **level** 选项控制压缩强度，取值为 **0 到 9 的整数**，数值越大压缩率越高但越慢。

- **0** 表示不压缩，仅做格式封装，常用于需要流式格式但不求体积的场景。
- 默认值为 **Z_DEFAULT_COMPRESSION**，在 Node 中一般等价于 **6**，兼顾速度与压缩率。
- **9** 是最高级别，压缩率最高但耗时最长，适合构建期一次性预压缩静态资源。

```js
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");

function compressWithLevel(src, dst, level) {
  const readable = fs.createReadStream(src);
  const gzip = zlib.createGzip({ level });
  const writable = fs.createWriteStream(dst);
  readable.pipe(gzip).pipe(writable);
}

const src = path.join(__dirname, "big.txt");
compressWithLevel(src, src + ".fast.gz", 1);   // 快、体积大
compressWithLevel(src, src + ".best.gz", 9);   // 慢、体积小
```

> 级别并非越高越好：9 级在运行时对每次请求都做，会显著拖慢响应并占用 CPU。线上动态压缩常用 1 至 6，预压缩静态资源才用 9。

**速记**：level **0 不压、6 默认、9 最慢最压**。



#### memLevel 与 strategy 简介

**高级选项**：除 level 外，zlib 还暴露 **memLevel** 与 **strategy** 等底层选项，用于微调压缩的内存占用与数据特征适配，日常用得较少但值得了解。

- **memLevel**：取值 1 到 9，控制压缩时内部缓冲占用多少内存，默认 8；越高占用越多内存、速度略快。
- **strategy**：取值如 Z_DEFAULT_STRATEGY、Z_FILTERED、Z_HUFFMAN_ONLY、Z_RLE 等，针对不同数据特征调整匹配算法。
- 这两个选项对**压缩率边界影响有限**，绝大多数业务用默认即可，不要盲目调参。

```js
const zlib = require("zlib");

const stream = zlib.createGzip({
  level: 9,
  memLevel: 9,
  strategy: zlib.constants.Z_DEFAULT_STRATEGY
});
```

> strategy 仅在数据具有强规律（如已高度重复的日志、纯文本）时才有可感知差异；普通 JSON、HTML 用默认策略即可，调它往往得不偿失。

**速记**：memLevel **控内存**、strategy **控模式，默认够用**。



#### 压缩率的现实边界

**收益边界**：zlib 压缩**对文本类数据收益显著，对已被压缩的二进制格式几乎无收益甚至变大**，这是决定要不要压缩的首要判断。

- **高收益**：HTML、CSS、JavaScript、JSON、SVG、纯文本等可高度去冗余，常能压到原体积 20% 以下。
- **无收益**：PNG、JPEG、MP3、MP4、ZIP、GZIP 本身等**已压缩格式**，再压通常只增不减或基本持平。
- **小文件不划算**：极小的响应（如几十字节）压完可能还要额外带压缩头，得不偿失。

> 是否压缩不能只看算法，要看**数据本身的冗余度**。经验法则：先判断 Content-Type，文本类（text/*、application/json、application/javascript）才压；图片、音视频、已压缩归档一律跳过。

**速记**：文本**大赚**、已压格式**别压**、小文件**不值**。



#### brotli 的质量参数与适用场景

**Brotli 选项**：brotli 通过 **zlib.constants.BROTLI_PARAM_QUALITY** 控制压缩质量，取值 0 到 11，质量越高压缩率越高但越慢，使用方式与 gzip 的 level 类似却更精细。

- 创建时通过 options.params 传入：完整形如 **zlib.createBrotliCompress({ params: { [zlib.constants.BROTLI_PARAM_QUALITY]: 11 } })**。
- 质量 11 压缩率最高，适合**构建期预压缩静态资源**；动态响应用 4 到 6 即可兼顾速度与体积。
- 浏览器需在 Accept-Encoding 中声明 **br** 才会被采用，与 gzip 的协商方式完全一致。

> brotli 虽压缩率更高，但高质量编码极其消耗 CPU，切忌在请求路径上对每个响应都用质量 11；预压缩加长缓存才是它的正确打开方式。

**速记**：brotli **quality 0-11，预压缩用高质、动态用中庸**。



### 在 HTTP 中启用压缩

#### 判断 Accept-Encoding 选择算法

**协商入口**：服务器是否压缩、用哪种算法，取决于客户端请求头 **Accept-Encoding** 声明的能力，服务端必须先读取它再决策。

- 客户端在请求里带 **Accept-Encoding: gzip, deflate, br**，表示自己能解哪些格式。
- 服务端按优先级选一个双方都支持的：优先 br（brotli），其次 gzip，再 deflate。
- 若请求头里完全没有该字段，或不含任何服务端支持的算法，则**不压缩直接原文返回**。

```js
function pickEncoding(req) {
  const accept = req.headers["accept-encoding"] || "";
  if (accept.includes("br")) return "br";
  if (accept.includes("gzip")) return "gzip";
  if (accept.includes("deflate")) return "deflate";
  return null;
}
```

> 注意请求头键名是 Node 已规范化的小写，必须用 accept-encoding 访问。br 代表 brotli、gzip 与 deflate 同名，漏掉 br 会错失更高压缩率。

**速记**：先看 **Accept-Encoding** 再定算法，br 优先。



#### 设置 Content-Encoding 与 Vary

**响应头设置**：一旦决定压缩，必须用 **Content-Encoding** 告知客户端响应体的压缩格式，并建议用 **Vary: Accept-Encoding** 声明按编码区分缓存。

- **Content-Encoding: gzip**（或 br、deflate）紧跟压缩体，浏览器据此先解压再解析。
- **Vary: Accept-Encoding** 告诉缓存层（浏览器、CDN）同一 URL 存在多种编码版本，应按请求头分别缓存，避免把压缩版错发给不支持的客户端。
- 同时必须正确设置 **Content-Type**，否则浏览器不知如何解读解压后的内容。

> [!WARNING]
> **警告内容**：漏设 **Content-Encoding** 会让浏览器把压缩字节当成原文解析，页面直接乱码；漏设 **Vary** 则可能被中间代理把 gzip 版复用到不支持的客户端，属于经典缓存坑（见后文常见坑）。

**速记**：压了就设 **Content-Encoding + Vary + Content-Type**。



#### 用管道把读流经 gzip 接响应

**流式响应**：把**文件可读流经 gzip 变换后直接 pipe 到响应对象**（res 是可写流），即可在传输中实时压缩，且内存恒定。

- 先按 pickEncoding 结果选 createGzip 等变换流。
- 设好 Content-Encoding、Content-Type、Vary 等头，再开始 pipe。
- 用 stream/promises 的 pipeline 把 读流、压缩流、res 串起来，统一错误处理。

```js
const http = require("http");
const fs = require("fs");
const zlib = require("zlib");
const path = require("path");
const { pipeline } = require("stream/promises");

const server = http.createServer(async (req, res) => {
  const encoding = req.headers["accept-encoding"] || "";
  const file = path.join(__dirname, "index.html");

  res.setHeader("Content-Type", "text/html; charset=utf-8");
  res.setHeader("Vary", "Accept-Encoding");

  if (encoding.includes("gzip")) {
    res.setHeader("Content-Encoding", "gzip");
    try {
      await pipeline(fs.createReadStream(file), zlib.createGzip(), res);
    } catch (err) {
      if (!res.writableEnded) res.end();
    }
    return;
  }
  fs.createReadStream(file).pipe(res);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 这里 res 就是第 17 篇所述的可写流，可以直接作为 pipeline 的 destination。务必在第一次 write（pipe 触发）之前把头全部设好，否则会触发 ERR_HTTP_HEADERS_SENT。

**速记**：读流 → **gzip → res**，实时压缩传输。



### 缓存分类、强缓存与协商缓存

#### 缓存的价值与分类

**缓存意义**：HTTP 缓存通过**在客户端或中间代理复用响应**，减少重复传输的带宽与延迟，是前端性能与服务器负载优化的核心手段。

- 价值一：**省带宽**，重复请求不再回源取数。
- 价值二：**降延迟**，就近命中缓存免去网络往返。
- 分类：按是否需回源校验分为 **强缓存** 与 **协商缓存**；按存放位置可分为浏览器缓存与 CDN 等中间代理缓存。

> 强缓存与协商缓存不是二选一，而是**递进关系**：先判强缓存是否新鲜，不新鲜再走协商。两者配合才能既快又准。

**速记**：缓存 **省带宽降延迟，分强缓存与协商缓存**。



#### 强缓存 Cache-Control 与 Expires

**强缓存**：是**服务器一次性告知客户端资源有效期、期内不再发任何请求**的缓存方式，由 **Cache-Control** 的 max-age 或旧式 **Expires** 控制。

- **max-age=秒数**：指定资源可缓存的时长，如 max-age=3600 表示一小时内直接使用本地副本。
- **no-cache**：仍需向服务器校验后才可用缓存；**no-store**：完全不缓存，适合敏感数据。
- **public** 允许任何缓存（含代理）存储；**private** 仅限用户浏览器缓存，禁止代理共享。
- **immutable**：声明内容永不变，连校验都免，常见于带哈希的文件名。
- **Expires**：用绝对时间（GMT）声明过期点，是 HTTP/1.0 旧方案，**依赖客户端本地时钟**，优先级低于 Cache-Control。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Cache-Control", "public, max-age=3600");
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("强缓存一小时");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> no-cache 与 no-store 常被混淆：no-cache 是"缓存但用前先问服务器"，no-store 是"压根别存"。涉及用户隐私或金额时务必用 no-store。

**速记**：强缓存 **max-age 定时效，no-store 最严**。



#### 协商缓存 Last-Modified 与 ETag

**协商缓存**：是**强缓存失效后，客户端带着校验信息回源询问、服务器比对后决定返回 304 还是新内容**的机制，由 Last-Modified 与 ETag 两类配对头实现。

- **Last-Modified / If-Modified-Since**：服务端给最后修改时间，下次客户端用 If-Modified-Since 回传，服务器比对时间。
- **ETag / If-None-Match**：服务端给内容指纹（如哈希），下次客户端用 If-None-Match 回传，服务器比对指纹。
- 服务器比对一致则回 **304 无响应体**，客户端沿用本地副本；不一致则回 **200 与新内容**。
- **ETag 更精确**：能解决秒级精度不足、内容未变但时间变等 Last-Modified 的缺陷。

```js
const http = require("http");
const fs = require("fs");
const path = require("path");

const file = path.join(__dirname, "data.json");
const server = http.createServer((req, res) => {
  const stat = fs.statSync(file);
  const lastModified = stat.mtime.toUTCString();
  res.setHeader("Last-Modified", lastModified);

  if (req.headers["if-modified-since"] === lastModified) {
    res.statusCode = 304;
    res.end();
    return;
  }
  res.setHeader("Content-Type", "application/json; charset=utf-8");
  fs.createReadStream(file).pipe(res);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!IMPORTANT]
> **重要内容**：**ETag 比 Last-Modified 更精确**——Last-Modified 精度通常只到秒，一秒内多次修改无法区分，且内容未变但仅触摸文件（mtime 变）也会误判过期；ETag 用内容哈希能规避这两类问题。

**速记**：协商缓存 **304 空体，ETag 比 Last-Modified 准**。



#### 缓存决策流程

**决策顺序**：一次请求到达时，缓存系统按**先强后协商**的固定顺序判定，决定是直接使用本地副本、回源校验还是返回全新内容。

- 第一步：检查 **强缓存** 是否仍在 max-age 有效期内，是则**完全不发包**，直接命中本地副本。
- 第二步：强缓存过期，客户端带 **If-Modified-Since / If-None-Match** 发起协商请求。
- 第三步：服务器比对，未变返回 **304**（空体），已变返回 **200** 与新响应体。
- 任一环节命中即省下传输；都未命中才真正回源取数。

> 这套顺序解释了"为什么有时 network 面板里请求是灰色的（强缓存）、有时是 304（协商缓存）"。调试缓存问题先分清是哪一环命中的。

**速记**：先 **强缓存、后协商，304 或 200**。



### 用 Node 实现缓存与缓存策略实践

#### 用 Node 为静态资源设置缓存

**完整实现**：下面给出一个可运行的静态服务，对文件同时设置 **Cache-Control、Last-Modified、ETag**，并按请求头比对返回 304，覆盖强缓存与协商缓存两端。

- 用 **fs.statSync** 取文件修改时间生成 **Last-Modified**（toUTCString）。
- 用文件**内容哈希**（crypto 模块）生成 **ETag**，比时间更精确。
- 先后比对 **If-None-Match** 与 **If-Modified-Since**，任一命中即回 **304 空体**。
- 未命中则设 **Cache-Control: public, max-age=3600** 并返回文件流。

```js
const http = require("http");
const fs = require("fs");
const path = require("path");
const crypto = require("crypto");

function computeETag(buffer) {
  return '"' + crypto.createHash("md5").update(buffer).digest("hex") + '"';
}

const server = http.createServer((req, res) => {
  const file = path.join(__dirname, "public" + req.url);
  fs.readFile(file, (err, data) => {
    if (err) {
      res.statusCode = 404;
      res.end("not found");
      return;
    }
    const stat = fs.statSync(file);
    const lastModified = stat.mtime.toUTCString();
    const etag = computeETag(data);

    res.setHeader("Cache-Control", "public, max-age=3600");
    res.setHeader("Last-Modified", lastModified);
    res.setHeader("ETag", etag);
    res.setHeader("Content-Type", "application/octet-stream");

    if (req.headers["if-none-match"] === etag ||
        req.headers["if-modified-since"] === lastModified) {
      res.statusCode = 304;
      res.end();
      return;
    }
    res.end(data);
  });
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!NOTE]
> **提醒内容**：示例中 ETag 用 MD5 对全部内容哈希，文件变大时成本上升；生产可用文件的 **size + mtime** 组合成轻量 ETag。无论哪种，ETag 都要加双引号包裹以符合 HTTP 规范。

**速记**：静态资源 **Cache-Control + Last-Modified + ETag，比对回 304**。



#### 缓存策略实践要点

**策略落点**：缓存不是越久越好，要按**资源类型与内容稳定性**分级设置，才能在性能与及时更新之间取得平衡。

- **带内容哈希的文件名**（如 app.3a9f.js）：内容变则文件名变，可设 **长缓存（max-age 一年 + immutable）**。
- **HTML 入口**：常变且需及时更新，用 **no-cache** 让浏览器每次都校验，避免拿到过期页面。
- **API 响应**：默认 **不缓存**（no-store 或 private），防止不同用户看到彼此数据。
- **敏感信息**（登录态、订单、余额）：一律 **no-store**，禁止任何中间节点留存。

> 文件名哈希 + 长缓存是前端工程的标准组合：哈希保证内容更新时 URL 必变、旧缓存自动失效，于是可放心地长缓存。HTML 不哈希才需 no-cache。

**速记**：哈希名 **长缓存**、HTML **no-cache**、API **不缓存**。



#### 常见坑

**典型陷阱**：压缩与缓存叠加时，有几个高频错误会直接导致乱码、隐私泄露或缓存错乱，需逐一规避。

- **忘记设 Vary**：对已压缩响应不设 Vary: Accept-Encoding，CDN 可能把 gzip 版发给不支持的客户端，造成乱码。
- **重复压缩**：对已压缩的资源（图片、视频、zip）再走 gzip，不仅无收益还可能变大、浪费 CPU。
- **缓存带用户信息响应**：对含用户数据的接口设了 public 缓存，导致 A 用户的数据被 B 用户命中。
- **304 带响应体**：协商命中后返回 304 却仍写响应体，违反规范，部分客户端会忽略 304 或行为异常。

> [!CAUTION]
> **注意内容**：**304 响应体必须为空**。304 的语义是"未修改、请用本地副本"，一旦写了 body 就等于自相矛盾，部分客户端会忽略 304 或缓存校验逻辑出错。

**速记**：坑在 **Vary、别重压、别缓存用户数据、304 须空体**。
