## Docker 与部署运维

### 为什么需要容器化

#### 传统部署的痛点

**环境不一致**：同一份代码在开发机运行正常，到了服务器却报错，是最典型的部署问题。

- 操作系统版本、系统库、Node 版本、依赖版本任一不同都可能导致行为差异。
- 手工在服务器上安装依赖，步骤难以复现，换机器就得重来一遍。
- 多个应用共用一台服务器时，依赖冲突难以隔离。

> 容器化把**应用连同它的运行环境**一起打包，交付的是一个自包含的镜像，而不是一串需要人工执行的安装步骤。

**速记**：交付 **镜像** 而非步骤。



#### 容器与虚拟机的区别

**容器**：在**操作系统层面**做隔离，共享宿主内核，因此轻量、启动快。

- **虚拟机**：虚拟出完整硬件与操作系统，隔离彻底但笨重，启动以分钟计。
- **容器**：共享宿主内核，只包含应用与依赖，启动以秒计，密度高。
- 隔离强度上虚拟机更强，容器更侧重**打包与交付效率**。

> 容器不是"轻量虚拟机"。它本质是一个被限制了可见范围的进程，安全性依赖宿主的隔离机制，不应把容器当作强安全边界使用。

**速记**：容器 **共享内核**，虚拟机 **独享系统**。



### Docker 核心概念

#### 镜像、容器与仓库

**镜像（Image）**：只读的模板，包含运行应用所需的代码、依赖与环境。

- 镜像**分层**存储，每一层对应构建过程的一条指令，相同层可复用。
- **容器（Container）**：镜像的运行实例，在镜像之上加一层可写层。
- **仓库（Registry）**：存放与分发镜像的服务，如 Docker Hub 与各云厂商的镜像仓库。
- 容器删除后其可写层随之消失，**持久化数据必须挂载卷**。

```bash
docker images
docker ps -a
docker rm my-app
```

> 镜像是"类"，容器是"对象"。一个镜像可同时运行多个容器，彼此文件系统相互独立。

**速记**：镜像 **只读模板**，容器 **运行实例**。



#### 层的复用与缓存

**分层缓存**：构建镜像时，若某层及其之前的所有层未变化，Docker 直接复用缓存。

- 每条 Dockerfile 指令生成一层。
- 一旦某层失效，其后所有层都要重建。
- 因此**变化频繁的指令应放在后面**，稳定的指令放在前面。

> 把安装依赖放在复制源码之前，是镜像构建提速的关键。源码每次提交都会变，依赖却很少变，顺序调换后日常构建只需重建最上面几层。

**速记**：**稳定在前、易变在后**，缓存才生效。



### 编写 Dockerfile

#### 常用指令

**Dockerfile**：描述镜像构建步骤的文本文件，每条指令对应镜像的一层。

- **FROM**：指定基础镜像，通常是构建的第一步。
- **WORKDIR**：设置后续指令的工作目录，相当于切换并创建目录。
- **COPY**：把宿主文件复制进镜像。
- **RUN**：在构建期执行命令，如安装依赖。
- **ENV**：设置环境变量。
- **EXPOSE**：声明监听端口，仅起说明作用，不实际发布端口。

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
ENV NODE_ENV=production
CMD ["node", "dist/index.js"]
```

> 基础镜像选 alpine 版本可显著减小体积，但它使用 musl libc，个别依赖原生模块的包可能需要额外编译环境。

**速记**：FROM 定基底，**COPY 与 RUN 分层**。



#### CMD 与 ENTRYPOINT

**启动命令**：决定容器启动时执行什么，两者的组合规则不同。

- **CMD**：提供默认命令与参数，运行容器时**可被命令行覆盖**。
- **ENTRYPOINT**：固定可执行程序，命令行内容作为**追加参数**。
- 两者都推荐使用**数组形式**（exec 形式），避免 shell 包装导致信号无法传递。

```dockerfile
ENTRYPOINT ["node"]
CMD ["dist/index.js"]
```

> [!IMPORTANT]
> **重要内容**：务必使用数组形式。写成 shell 形式时命令会由 sh 启动，Node 进程成为子进程，收到停止信号时**无法正确优雅退出**，容器只能等待超时被强杀。

**速记**：数组形式 **信号可达**，shell 形式会断链。



#### 多阶段构建

**多阶段构建**：在一个 Dockerfile 中分多个阶段，只把最终需要的文件带进运行镜像。

- 前一阶段负责**安装全量依赖并编译**。
- 后一阶段只复制**编译产物与生产依赖**。
- 结果是不把 TypeScript 编译器、测试依赖等打进运行镜像，体积大幅下降。

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]
```

> 多阶段构建的收益与项目类型相关：编译型或需构建的前端项目收益极大，纯 JavaScript 项目收益主要来自剔除开发依赖。

**速记**：builder 负责造，**运行镜像只带产物**。



#### dockerignore 文件

**dockerignore**：列出不参与构建上下文的文件，作用类似 gitignore。

- 排除 **node_modules**，避免把宿主依赖覆盖进镜像。
- 排除日志、本地配置、.git 目录，减小上下文并避免敏感文件入镜像。
- 文件放在项目根目录，名为 .dockerignore。

```text
node_modules
dist
logs
.git
.env
```

> [!CAUTION]
> **注意内容**：构建上下文会把整个目录传给 Docker 守护进程，未排除 node_modules 时**传输量可能达数百兆**，构建明显变慢；更严重的是 .env 一旦被打进镜像，密钥就随镜像分发出去了。

**速记**：先写 **dockerignore** 再写 Dockerfile。



### 构建与运行

#### 构建与启动命令

**docker build**：按 Dockerfile 构建镜像，-t 指定名称与标签。

- 标签格式为 **名称:版本**，不写版本默认 latest。
- 构建上下文是命令最后的路径，通常为英文句点表示当前目录。

```bash
docker build -t my-app:1.0.0 .
docker run -d --name my-app -p 3000:3000 my-app:1.0.0
```

> latest 标签会随新镜像移动，生产部署应**固定具体版本标签**，否则不同机器可能拉到不同版本，出现"配置一致但行为不同"的怪象。

**速记**：生产 **固定版本标签**。



#### 常用运行参数

**docker run 参数**：控制端口、环境变量、挂载与重启策略。

- **-d**：后台运行。
- **-p 宿主端口:容器端口**：发布端口映射。
- **-v 宿主路径:容器路径**：挂载卷，用于持久化或挂载配置。
- **--env-file**：从文件注入环境变量。
- **--restart**：重启策略，如 unless-stopped、always。
- **--name**：为容器命名，便于后续操作。

```bash
docker run -d \
  --name my-app \
  -p 3000:3000 \
  --env-file ./.env \
  --restart unless-stopped \
  my-app:1.0.0
```

> 端口映射格式为宿主在前、容器在后，记反了会导致"启动成功却访问不到"。

**速记**：**宿主在前、容器在后**。



#### 查看日志与进入容器

**运维命令**：排查问题最常用的几个命令。

- **docker ps**：查看运行中的容器，加 -a 查看全部。
- **docker logs**：查看容器输出，加 -f 跟随，加 --tail 看末尾若干行。
- **docker exec**：在运行中的容器内执行命令，常用于进入 shell 排查。

```bash
docker ps
docker logs -f --tail 100 my-app
docker exec -it my-app sh
```

> 应用日志应输出到**标准输出与标准错误**，这样 docker logs 才能直接看到。若把日志只写进容器内文件，排查时必须进入容器，且容器删除后日志随之丢失。

**速记**：日志走 **标准输出**。



### 容器中的 Node 注意事项

#### 监听地址与信号处理

**监听地址**：容器内应用必须监听 **0.0.0.0** 而非 127.0.0.1。

- 127.0.0.1 只接受容器内部连接，宿主无法通过端口映射访问。
- 监听 0.0.0.0 表示接受所有网卡的连接。

```js
const server = app.listen(3000, "0.0.0.0", () => {
  console.log("服务已启动，端口 3000");
});
```

> [!WARNING]
> **警告内容**：容器内监听 127.0.0.1 是**最常见的"容器跑着却访问不了"**的原因。它在开发机正常，进容器就失效，排查时容易误判为端口映射配错。

**速记**：容器里监听 **0.0.0.0**。



#### 优雅退出

**优雅退出**：收到停止信号后先停止接收新请求，处理完存量请求再退出。

- Docker 停止容器时先发 **SIGTERM**，超时未退出才发 SIGKILL。
- 应用应监听 SIGTERM，关闭服务器并等待连接结束。
- 进程必须是容器的**主进程**（PID 1）才能收到信号，用 shell 脚本包裹会断链。

```js
const server = app.listen(3000);

process.on("SIGTERM", () => {
  console.log("收到停止信号，开始优雅退出");
  server.close(() => {
    console.log("连接已处理完毕，退出");
    process.exit(0);
  });

  setTimeout(() => process.exit(1), 10000);
});
```

> server.close 只是停止接收新连接，已有连接会保持。因此必须设置**超时兜底**，防止长连接迟迟不断导致容器无法停止。

**速记**：监听 SIGTERM、**关服务加超时**兜底。



#### 资源感知与安全

**资源限制**：容器看到的资源是宿主的全部，除非显式限制。

- 通过内存与 CPU 限制参数控制容器可用资源。
- **os.cpus().length** 在容器内可能返回宿主的核数，据此启动的进程数会超出配额。
- 应显式指定工作进程数，或读取 cgroup 限制。

```js
const cpuCount = Number(process.env.WORKER_COUNT) || 2;
console.log("按配置启动工作进程数", cpuCount);
```

> [!CAUTION]
> **注意内容**：默认以 root 运行容器**风险很高**，一旦应用被攻破即获得容器内 root 权限。应在 Dockerfile 中用 USER 指令切换到非 root 用户，并注意文件归属。

**速记**：**限资源、降权限、别信核数**。



### Docker Compose

#### 编排多服务

**Docker Compose**：用配置文件定义多个服务及其关系，一条命令启动整套环境。

- 配置文件通常为 **docker-compose.yml**。
- 每个服务对应一个容器，服务之间用**服务名**作为主机名互通。
- **depends_on** 声明启动顺序，但不等待就绪，需配合健康检查。

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=db
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mysql:8
    environment:
      - MYSQL_ROOT_PASSWORD=secret
    volumes:
      - db-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5

volumes:
  db-data:
```

> 服务间访问要用**服务名**而非 localhost。容器内 localhost 只指自己，写 localhost 连数据库必然失败。

**速记**：服务间用 **服务名** 互通。



#### 健康检查

**健康检查**：由 Docker 定期执行命令判断容器是否可用。

- 配置 healthcheck 的测试命令、间隔、重试次数。
- 应用侧应提供**轻量检查接口**，如返回 200 的 /healthz。
- 检查应包含关键依赖状态，但不能过重，否则自身成为负担。

```js
app.get("/healthz", (req, res) => {
  res.status(200).json({ status: "ok", uptime: process.uptime() });
});
```

> 健康检查是编排平台判断实例生死的依据。接口若只返回固定值而不检查依赖，会出现"进程活着但数据库连不上"的实例继续接收流量。

**速记**：健康检查要 **真实反映可用**。



### 部署与运维

#### 部署流程

**标准流程**：构建、推送、拉取、切换，四步构成一次发布。

- 第一步：在构建机执行 **docker build** 生成带版本号的镜像。
- 第二步：**docker push** 推送到镜像仓库。
- 第三步：服务器 **docker pull** 拉取指定版本。
- 第四步：启动新容器，待健康检查通过后切换流量，再停止旧容器。

```bash
docker build -t registry.example.com/my-app:1.2.0 .
docker push registry.example.com/my-app:1.2.0
docker pull registry.example.com/my-app:1.2.0
```

> 先启动新版本再下线旧版本，可实现**零停机切换**。前提是应用支持优雅退出，且新旧版本能短时并存。

**速记**：**先起新、后停旧**。



#### 反向代理与 HTTPS

**反向代理**：由 Nginx 或 Caddy 等在应用前层接收请求，再转发给应用容器。

- 负责**终止 HTTPS**，应用内部走 HTTP，简化证书管理。
- 可托管静态资源、做压缩与缓存、实现负载均衡。
- 转发时应传递真实客户端信息，常用请求头包括 X-Forwarded-For 与 X-Forwarded-Proto。

```text
server {
    listen 443 ssl;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

> 应用若需要判断用户是否为 HTTPS 访问或取真实 IP，必须信任并读取转发头，否则取到的是代理的地址。

**速记**：代理终止 HTTPS，**转发头带真实信息**。



#### 配置与密钥管理

**配置原则**：配置与代码分离，密钥不进镜像。

- 常规配置用**环境变量**注入。
- 密钥应使用**密钥管理服务**或编排平台的密钥机制，不要写进 Dockerfile 或代码库。
- 区分构建期与运行期环境变量，构建期的会固定在镜像层中。

```bash
docker run --env-file ./.env.production my-app:1.2.0
```

> [!WARNING]
> **警告内容**：写进镜像的密钥**无法靠删除文件消除**，因为旧层仍保留该文件的历史。发现密钥泄露必须轮换，而不是重新构建一版删掉它。

**速记**：密钥 **运行时注入**，泄露即轮换。



#### 监控、备份与回滚

**运维闭环**：上线只是开始，需要监控、备份与回滚预案。

- **监控**：采集 CPU、内存、请求量、错误率与响应时长，设置告警阈值。
- **日志**：集中采集到日志平台，支持按请求标识检索。
- **备份**：数据库定期备份并**验证可恢复**，未验证的备份等于没有备份。
- **回滚**：保留上一个可用版本的镜像，出问题时优先回滚而非现场修复。

```bash
docker images | head
docker tag registry.example.com/my-app:1.1.0 my-app:rollback
```

> 回滚是最有效的止损手段。发布前先确认回滚版本可用，比事后排查快得多。

**速记**：**能监控、可备份、先回滚**。
