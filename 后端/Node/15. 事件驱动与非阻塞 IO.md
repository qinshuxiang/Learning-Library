## 事件驱动与非阻塞 IO

### 阻塞与非阻塞：线程是否被调用挂起

**阻塞与非阻塞**：是描述一次 IO 调用在结果返回前如何对待调用线程的两种 IO 行为，核心差别在于调用线程是否被挂起等待。

#### 阻塞 IO 在等待期间挂起调用线程

**阻塞 IO（Blocking IO）**：指发起 IO 调用后，调用线程被操作系统挂起，直到数据就绪并拷贝完成才返回，期间无法执行其他代码。

- 线程在 read、recv 等系统调用上陷入内核等待，CPU 时间片被让出。
- 等待期间该线程完全闲置，既不能处理新请求，也不能做其他计算。
- 结果就绪后线程被唤醒，调用返回并拿到数据，逻辑才继续往下走。

```js
const fs = require("fs");
const data = fs.readFileSync("data.txt"); // 阻塞：线程停在这里直到读完
console.log(data.length);
```

> 阻塞 IO 并非错误用法，而是最简单的编程模型；问题只出在**用单条主线程去阻塞等待**，会令后续所有任务一起停摆。

**速记**：阻塞 IO **调用即挂起，归来才继续**。



#### 非阻塞 IO 立即返回并以后续通知取结果

**非阻塞 IO（Non-blocking IO）**：指发起 IO 调用后，无论数据是否就绪都立即返回，调用者通过轮询或事件通知在将来获取结果。

- 调用立刻返回，线程不被挂起，可继续处理别的逻辑或别的请求。
- 若数据尚未就绪，系统调用返回特殊状态（如 EAGAIN）提示稍后再试。
- 真正结果由运行环境在就绪后回调，调用者"登记意图、过后领取"。

```js
const fs = require("fs");
fs.readFile("data.txt", (err, data) => {
  // 非阻塞：调用后立即返回，数据就绪后此回调被事件循环执行
  console.log(data.length);
});
console.log("主线程立刻继续，不被读文件阻塞");
```

> 非阻塞的本质是**把等待从线程身上移走**：线程只负责发起与善后，等待由运行环境在底层完成。Node 对 JS 层呈现的就是这种形态。

**速记**：非阻塞 IO **发起即返回，就绪再回调**。



#### 阻塞与否由文件描述符标志决定

**系统层面**：是否阻塞取决于套接字或文件描述符是否设置了非阻塞标志，以及 Node 选用哪类系统调用。

- 默认的文件描述符是阻塞的，read 会一直等到有数据才返回。
- 通过 fcntl 或 O_NONBLOCK 设为非阻塞后，read 立即返回状态而非等待。
- Node 由 libuv 在底层统一管理这些标志，JS 层无需手动设置。

```bash
# Linux 下查看某文件描述符是否非阻塞
cat /proc/<pid>/fdinfo/<fd> | grep flags
```

> 普通开发者不必直接操作系统调用；理解"阻塞由底层标志决定"即可，Node 已把复杂度封装进 libuv，业务代码只见到异步回调。

**速记**：阻塞与否 **底层标志定**。



### 同步与异步：正交的两组维度

**同步与异步**：是描述调用者如何取得结果的两种编程范式，核心差别在于结果是通过"当场返回"还是"过后通知"送到调用者手中，与线程是否被挂起是正交的两组概念。

#### 同步关注调用者是否等待结果

**同步（Synchronous）**：指调用者发起操作后，一直停留在该调用处，直到拿到返回值（或抛错）才继续向下执行。

- 调用者主动等待，控制流在调用点"卡住"直到结果到手。
- 写法上是顺序的：上一行的结果直接用于下一行。
- 同步可以是阻塞的（线程被挂起），也可以是忙等（线程仍被占用）。

```js
const fs = require("fs");
const text = fs.readFileSync("a.txt", "utf8"); // 同步：拿到结果才下一行
const upper = text.toUpperCase();
console.log(upper);
```

> 同步描述的是**调用者与结果的"距离"**：结果必须当场拿到，才叫同步。它并不规定底层是阻塞还是非阻塞。

**速记**：同步 **等到结果才走**。



#### 异步关注结果如何后送

**异步（Asynchronous）**：指调用者发起操作后不等待，立即拿到一个占位（如 Promise 或未决状态），真正结果通过回调、事件或 Promise 在将来送回。

- 调用者不卡在调用点，可继续跑后续代码。
- 结果通过注册的回调函数、Promise 的 then、或 await 后续取得。
- 异步天然适合"发起后去干别的"，是事件驱动模型的基石。

```js
const fs = require("fs").promises;
async function load() {
  const text = await fs.readFile("a.txt", "utf8"); // 异步：结果后送，不卡线程
  console.log(text.toUpperCase());
}
load();
console.log("load 尚未完成，这里先打印");
```

> 异步描述的是**结果的送达方式**：当场拿不到，由运行环境"回头通知"你，才叫异步。它同样不规定底层是阻塞还是非阻塞。

**速记**：异步 **发起即走，结果后送**。



#### 同步异步与阻塞非阻塞是正交维度

**正交辨析**：同步异步与阻塞非阻塞是两组互不绑定的维度，可任意组合，常因名字相近而被混为一谈。

- 同步 + 阻塞：最常见，调用等到结果，线程也被挂起。
- 同步 + 非阻塞：发起后立即返回，调用者用循环轮询直到拿到结果，线程仍被占用却未被挂起。
- 异步 + 非阻塞：Node 的典型形态，发起后立刻返回，就绪后回调，线程全程自由。
- 异步 + 阻塞（底层）：libuv 把阻塞的文件 IO 丢进线程池完成，对 JS 层呈现为异步，但线程池线程本身是阻塞的。

> [!IMPORTANT]
> **重要内容**：判断一对概念时先固定维度——**同步异步看"结果何时到调用者手"**，**阻塞非阻塞看"调用线程是否被挂起"**。二者正交，混用会得出错误结论，是面试与排错的高频混淆点。

**速记**：同步异步看 **结果到手时**，阻塞非阻塞看 **线程挂不挂**。



### 事件驱动模型的组成与运转流程

**事件驱动（Event-driven）**：是一种以"事件"为中心的编程模型，程序不主动轮询，而是登记感兴趣的事件与回调，由运行环境在事件发生时回调处理逻辑。

#### 事件驱动的四个组成要素

**四要素**：事件驱动由事件源、事件循环、事件队列、监听器（回调）协同构成，缺一不可。

- **事件源**：能产生 IO 或定时等事件的来源，如套接字、文件、定时器。
- **事件循环**：持续检查事件源、取出就绪事件并派发回调的核心调度器。
- **事件队列**：暂存"已就绪、待执行"的回调，按阶段与优先级排队。
- **监听器/回调**：开发者注册的处理函数，事件发生时被调用以消费结果。

```js
const net = require("net");
const server = net.createServer((socket) => {
  // socket 上有连接事件，回调函数即监听器
  socket.on("data", (chunk) => socket.write(chunk));
});
server.listen(3000);
```

> 四要素中**事件循环是发动机**，队列是等待区，监听器是业务逻辑落点；理解它们各自的角色，就理解了"为什么 Node 不用每连接一线程也能服务海量连接"。

**速记**：事件驱动四件套 **源、环、队、监听器**。



#### 一次异步操作的完整流转

**流转过程**：一个异步 IO 从发起到最后执行回调，经历"发起、返回、等待、入队、执行"五个阶段。

- **发起异步操作**：调用 fs.readFile 等 API，把回调连同意图交给底层。
- **立即返回继续干活**：主线程不等待，接着执行后续同步代码。
- **底层完成操作**：libuv 或操作系统在数据就绪后完成实际 IO。
- **回调入队**：完成事件把回调放进对应阶段的事件队列。
- **循环取回调执行**：事件循环轮到该阶段，取出回调在主线程执行。

```text
发起 readFile ──► 主线程立即返回，去干别的
                        │
                        ▼
               libuv/OS 在底层完成读盘
                        │
                        ▼
               回调被放入 poll 阶段队列
                        │
                        ▼
            事件循环在 poll 阶段取出并执行回调
```

> 关键点：主线程**从未等待 IO**，它只在"回调被取出"那一刻短暂介入；等待与完成都发生在底层，这正是单线程也能高并发的原因。

**速记**：流程 **发起即返，就绪入队，循环取执**。



#### 事件驱动与回调的关系

**回调即监听器**：在事件驱动里，开发者注册的回调就是某事件的监听器，事件循环负责在适当时机调用它，二者是"订阅与触发"关系。

- 回调不主动运行，必须等事件循环把它从队列取出才会执行。
- 同一事件可挂多个监听器，按注册顺序依次触发。
- 回调里的异常不会影响事件循环继续运转，但会进入该回调的错误处理路径。

```js
const EventEmitter = require("events");
const emitter = new EventEmitter();
emitter.on("done", () => console.log("监听 done 事件")); // 注册监听器
emitter.emit("done"); // 事件循环外的同步触发，仅作示意
```

> 事件驱动是模型，回调是实现手段；Promise 与 async/await 只是把回调包装得更平坦，底层仍是"事件就绪后回调"这一机制。

**速记**：回调 **即事件监听器**。



### libuv 与线程池：异步 IO 的真正执行者

**libuv**：是 Node 依赖的跨平台异步 IO 库，提供事件循环与线程池，是"JS 层异步"在底层真正落地的执行者。

#### libuv 对各平台异步 IO 的抽象

**统一抽象**：libuv 把 Linux、macOS、Windows 各异的异步机制封装成一致接口，JS 层只见到异步回调。

- **网络 IO**：在类 Unix 上用 epoll、kqueue，在 Windows 上用 IOCP 等系统多路复用机制。
- **跨平台一致性**：同一段 JS 代码在各操作系统行为一致，差异由 libuv 吸收。
- **向上屏蔽**：开发者不感知底层用哪种机制，只调统一的 fs、net 等模块。

```bash
node -p "process.versions.uv" # 查看当前 libuv 版本
```

> libuv 最初为 Node 而生，现也被其他项目使用；它让"**单线程 JS 拥有高并发 IO**"成为可能，是 Node 异步能力的真正基石。

**速记**：libuv **屏蔽平台差异，统一异步接口**。



#### 并非所有操作都走线程池

**分工原则**：libuv 中并非所有异步操作都占用线程池；能用系统多路复用完成的 IO 不进线程池，只有无法原生异步的才丢进线程池。

- **网络 IO 走多路复用**：TCP/UDP 套接字读写由 epoll、kqueue、IOCP 处理，不占线程池线程。
- **文件 IO 走线程池**：多数 fs 读写在底层由工作线程完成，避免阻塞主线程。
- **DNS 解析走线程池**：dns.lookup 等阻塞型解析交给线程池模拟异步。
- **crypto 与 zlib**：加解密、压缩属于 CPU 密集阻塞操作，也落线程池。

> [!NOTE]
> **提醒内容**：调优时先分清操作归属——**网络 IO 不占线程池**，调大 UV_THREADPOOL_SIZE 对纯网络服务几乎无效；只有当文件 IO、DNS、加密、压缩等阻塞任务并发很高时，线程池才会成为瓶颈。

**速记**：网络 IO **多路复用**，文件 DNS 加密 **线程池**。



#### 线程池默认 4 线程与 UV_THREADPOOL_SIZE

**线程池规模**：libuv 默认维护 **4 个工作线程**，可用环境变量 **UV_THREADPOOL_SIZE** 在 Node 启动前调整，最大值为 **1024**。

- **默认值来源**：libuv 在"并行度"与"线程开销"间做的经验平衡，非硬性上限。
- **调整时机**：必须在启动 Node 之前设置环境变量，运行中修改不生效。
- **上限与代价**：上限 1024，调得过大不线性提升吞吐，反增内存与切换成本。

```bash
export UV_THREADPOOL_SIZE=8
node app.js
```

> [!IMPORTANT]
> **重要内容**：UV_THREADPOOL_SIZE 改变的是**整个进程共用**的那一个线程池，所有文件 IO、DNS、crypto、zlib 共享它；默认 4 不是最优解，IO 密集且阻塞任务多时调到 8 或 16 更顺，但须以压测为依据，盲目拉满只浪费内存。

**速记**：线程池 **默认 4，启动前设，上限 1024**。



### Node 单线程执行与多线程底层

**单线程与多线程的统一**：Node 的 JavaScript 执行是单线程的，但底层 libuv 线程池与 V8 辅助线程是多线程的，二者并不矛盾，矛盾的是"在主线程上做阻塞重活"。

#### JavaScript 执行是单线程

**主线程单线程**：所有 JS 回调在同一条线程上顺序排队执行，互不真正并行，同一时刻只有一段 JS 在跑。

- 无并行计算：两段 JS 不能真正同时执行，只能由事件循环调度交替。
- 共享状态简单：JS 层数据无需加锁，避免了多线程竞态复杂度。
- 阻塞代价高：一段长计算会卡住该线程，使所有后续回调排队。

```js
console.log("A");
console.log("B"); // 永远先 A 后 B，严格顺序
```

> 准确说法是**Node 的 JS 执行是单线程的**；"Node 是单线程"省略了"主线程"限定，容易让人误以为 Node 进程只有一个线程。

**速记**：JS 执行 **一条线程排队跑**。



#### libuv 线程池是多线程

**底层多线程**：除 JS 主线程，libuv 线程池、V8 后台线程等都在与主线程并行工作。

- **libuv 线程池**：默认 4 个，并行处理文件 IO、DNS、压缩、加密。
- **V8 辅助线程**：参与垃圾回收、编译等底层任务，不与 JS 主线程抢执行。
- **协作方式**：主线程派活给线程池，线程池干完把回调回主线程。

```bash
export UV_THREADPOOL_SIZE=8
node app.js
```

> "Node 单线程"是**针对 JS 执行**的缩略；真正干 IO 重活的线程，藏在 libuv 线程池里与主线程并行，二者配合才实现高并发。

**速记**：底层 **线程池并行干重活**。



#### 阻塞主线程才是性能杀手

**矛盾澄清**：单线程与多线程并不冲突，冲突的是"把本该异步的活同步塞进主线程"，导致唯一的 JS 线程被长时间占用。

- 主线程被重计算占满时，定时器、IO 回调、请求响应全部停顿。
- 表现为接口无响应、延迟飙升，甚至被健康检查判为掉线。
- 解法不是避免多线程，而是**别让重活在唯一的主线程久留**。

```js
function handleRequest() {
  let sum = 0;
  for (let i = 0; i < 1e10; i++) sum += i; // 单线程被长时间占用
  return sum;
}
```

> [!WARNING]
> **警告内容**：判断一段代码是否会拖垮服务，看它是否**必须同步跑在主线程**。凡是重度循环、加密、压缩，要么改用异步 API（自动进线程池），要么下放子进程或工作线程，绝不可原地同步执行。

**速记**：杀手是 **主线程被阻塞**，非单线程本身。



### 高并发的代价、边界与并发模型对照

**高并发本质**：Node 通过"非阻塞 IO 加事件循环"在等待 IO 时转去服务其他请求，从而用少量线程支撑大量连接；但该能力有清晰边界，且与传统每连接一线程模型形成对照。

#### 事件驱动为何能高并发

**并发原理**：单线程在等待某请求 IO 时不去空等，转去处理别的请求，用"时间复用"代替"线程叠加"。

- 传统多线程每连接一线程，连接多则线程多，切换与内存开销大。
- Node 单线程复用，省去大量线程切换成本，等待期由底层消化。
- 前提：**业务以 IO 为主**；若全为 CPU 密集计算，单线程反而成瓶颈。

```js
const http = require("http");
http.createServer((req, res) => {
  // 请求在等数据库/网络时，主线程去服务其他请求
  fetchExternal().then((data) => res.end(data));
}).listen(3000);
```

> Node 擅长 **IO 密集型**（网络、文件、数据库）并发，而非 **CPU 密集型**（大量计算）；后者会占满单线程拖慢所有请求。

**速记**：高并发 **IO 等待不空等，转服务他人**。



#### C10K 问题与事件驱动的解法

**C10K 问题**：指单机同时维持一万并发连接时，传统每连接一线程模型因线程数与内存、切换成本爆炸而难以为继的经典难题。

- **背景**：早期服务器用一连接一线程，一万连接即一万线程，内存与上下文切换不堪重负。
- **解法一（多路复用）**：用 epoll、kqueue 单线程监控海量套接字，谁就绪处理谁。
- **解法二（事件驱动）**：Node 借 libuv 把多路复用封装为事件循环，以少量线程支撑海量连接。

```bash
# 查看进程可打开的文件描述符上限（连接数受此约束）
ulimit -n
```

> C10K 催生了事件驱动与非阻塞 IO 的普及；Node 站在 libuv 的肩膀上，让"单机万级并发"成为默认能力而非特例。

**速记**：C10K **线程爆炸，事件复用解**。



#### Node 的适用边界：IO 密集与 CPU 密集

**能力边界**：Node 的优势集中在 IO 密集，遇到 CPU 密集会迅速劣化，选型须先判断负载类型。

- **IO 密集（擅长）**：网络请求、文件读写、数据库访问，等待多、计算少。
- **CPU 密集（不擅长）**：大循环、图像处理、复杂加解密，计算占满主线程。
- **混合负载**：把 CPU 重活下放 worker_threads 或子进程，主线程只管 IO 与调度。

```js
const crypto = require("crypto");
// 量大时用异步 API，自动进线程池，而非同步 pbkdf2 卡主线程
crypto.pbkdf2("pwd", "salt", 100000, 64, "sha512", () => {});
```

> 判断标准一句话：**等待多就选 Node，算得多就加 worker 或换语言**。把 CPU 密集误放主线程，是 Node 服务性能崩坏最常见根因。

**速记**：边界 **IO 密挑选 Node，CPU 密加 worker**。



#### 每连接一线程与事件复用模型对照

**模型对照**：多进程多线程模型与事件驱动模型在资源占用与适用场景上差异显著，是理解 Node 定位的关键对照。

- **多进程多线程模型**：每连接分配一线程或一进程，并发由线程数堆出，逻辑直观但开销大。
- **事件驱动复用模型**：单线程（或少数线程）复用，并发由事件循环调度，开销小但怕重计算。
- **上下文切换**：前者随连接增长切换成本线性上升，后者几乎无切换。
- **内存开销**：前者每线程占用栈内存（常数十 MB 起），后者连接几乎只耗套接字与回调。

> [!NOTE]
> **提醒内容**：两类模型并非替代关系——CPU 密集或需强隔离的场景，多进程仍更稳；IO 密集且连接海量时，事件驱动性价比最高。现代架构常组合：Node 做 IO 网关，重计算交专门服务。

**速记**：对照 **线程堆并发费资源，事件复用省切换**。



### 控制流演进：从回调地狱到 async/await

**控制流演进**：Node 表达异步结果的方式从嵌套回调，经 Promise 链式，发展到 async/await 的同步写法，演进主线是"把异步代码写得更像顺序代码"。

#### 回调嵌套的问题：回调地狱

**回调地狱（Callback Hell）**：多层嵌套回调导致代码向右缩进、难读难维护的反模式，源于步骤间顺序依赖。

- 顺序依赖：下一步必须等上一步结果，只能层层嵌套。
- 错误处理分散：每层都要判 err，样板代码膨胀。
- 结构扭曲：代码呈金字塔状向右无限缩进，改名重构困难。

```js
const fs = require("fs");
fs.readFile("a.txt", (err, a) => {
  if (err) return handleError(err);
  fs.readFile(a, (err, b) => {
    if (err) return handleError(err);
    fs.readFile(b, (err, c) => {
      if (err) return handleError(err);
      console.log(c);
    });
  });
});
```

> 回调地狱的根因是**异步的"后续逻辑"被塞进参数位置**；出路是升级抽象，让后续逻辑回到正常的顺序位置。

**速记**：回调地狱 **金字塔向右缩**。



#### Promise 把嵌套摊平成链式

**Promise 链式**：用 then 把"下一步"从嵌套参数改为顺序链式调用，错误统一由 catch 收口。

- 每个 then 返回新 Promise，可连续点接，不再向右缩进。
- 错误沿链冒泡到最近的 catch，避免每层判 err。
- Node 的 fs.promises 等模块原生返回 Promise，无需手动包装。

```js
const fs = require("fs").promises;
fs.readFile("a.txt", "utf8")
  .then((a) => fs.readFile(a, "utf8"))
  .then((b) => fs.readFile(b, "utf8"))
  .then((c) => console.log(c))
  .catch((err) => handleError(err));
```

> Promise 让"异步顺序"重新变成从上到下的阅读顺序；但它仍是回调式（then 里传函数），表达力够用却不够贴近同步直觉。

**速记**：Promise **链式摊平，catch 收错**。



#### async/await 写成同步样式

**async/await**：是基于 Promise 的语法糖，让异步代码以看似同步的顺序书写，Node 自 7.6 起原生支持。

- async 函数体内可用 await 暂停，等 Promise 兑现后再继续下一行。
- 阅读顺序与同步代码一致，无 then 嵌套，变量作用域更自然。
- 错误用 try/catch 统一捕获，写法和同步代码相同。

```js
const fs = require("fs").promises;
async function readChain() {
  const a = await fs.readFile("a.txt", "utf8");
  const b = await fs.readFile(a, "utf8");
  const c = await fs.readFile(b, "utf8");
  console.log(c);
}
readChain().catch((err) => handleError(err));
```

> [!TIP]
> **建议内容**：新代码优先用 **async/await** 表达异步流程；只有需要精细控制并发（如 Promise.all 并行多个独立请求）时，才配合 Promise 的静态方法。底层 API 仍是回调，await 只是把它们包成了同步样子。

**速记**：async/await **同步写法，异步本质**。



### 异步错误处理的特殊之处

**异步错误处理**：异步代码的异常不走普通调用栈，普通 try/catch 捕获不到回调内的异常，需要专门约定与机制兜底。

#### try/catch 捕获不到回调里的异常

**捕获失效**：在异步回调中抛出的异常，发生在"未来某次事件循环"中，已脱离注册时的 try/catch 作用域，故无法被当时包裹的 try/catch 抓住。

- 同步 try/catch 只在"同一调用栈"内有效，回调执行时已不在该栈。
- 回调内抛错若无人处理，会变为未捕获异常，可能终止进程。
- 错误必须与结果一起，通过回调参数或 Promise  rejection 向外传递。

```js
try {
  fs.readFile("a.txt", (err, data) => {
    throw new Error("回调内抛错"); // 外层的 try/catch 抓不到
  });
} catch (e) {
  console.log("这里不会执行");
}
```

> 这是异步与同步最易踩的坑：**try/catch 管得了同步，管不了回调**。把错误当普通异常去抓，会漏掉真正故障。

**速记**：try/catch **抓不到回调内异常**。



#### 错误优先回调约定

**错误优先（Error-first）**：Node 早期回调统一约定"第一个参数是 err，成功时为 null"，开发者须先看 err 再处理数据。

- 签名形如 function(err, result)，err 在前是铁律。
- 调用后必须先判 if (err) 再使用后续结果，否则易用到未定义值。
- 这是回调时代的标准契约，大量内置模块（如 fs）仍遵循。

```js
fs.readFile("a.txt", "utf8", (err, data) => {
  if (err) {
    handleError(err); // 先看错误
    return;
  }
  console.log(data); // 再处理数据
});
```

> 错误优先约定把"失败"显式塞进回调参数，逼开发者处理；它虽啰嗦，却是回调时代最可靠的错误处理纪律。

**速记**：错误优先 **err 第一，先判后取**。



#### await 配合 try/catch 捕获异步错误

**同步化捕获**：用 async/await 后，Promise 的 rejection 会变成 await 处的异常，可用普通 try/catch 捕获，写法与同步一致。

- await 后若 Promise 拒绝，异常在 await 行抛出，落入外层 try/catch。
- 相比回调的 if (err)，try/catch 结构更直观、不易漏判。
- 函数返回 Promise，调用方仍可用 catch 兜底未捕获的拒绝。

```js
const fs = require("fs").promises;
async function safeRead() {
  try {
    const data = await fs.readFile("a.txt", "utf8");
    console.log(data);
  } catch (err) {
    handleError(err); // 能捕获 await 处的拒绝
  }
}
```

> await 让异步错误"重新回到调用栈"，所以 try/catch 又能用了；这正是 async/await 提升可维护性的关键一环。

**速记**：await **拒绝变异常，try 能抓**。



#### unhandledRejection 兜底未捕获拒绝

**兜底机制**：任何未被 catch 的 Promise 拒绝会触发 unhandledRejection 事件，是最后一道防线，应挂监听避免进程静默崩溃。

- 未处理的拒绝默认会在控制台打印，未来 Node 版本可能直接终止进程。
- 通过 process.on("unhandledRejection", handler) 统一记录与降级。
- 它只兜底"漏网"的拒绝，正确做法仍是在业务处显式处理。

```js
process.on("unhandledRejection", (reason, promise) => {
  console.error("未捕获的 Promise 拒绝：", reason);
  // 记录日志、告警，必要时优雅退出
});
```

> [!CAUTION]
> **注意内容**：unhandledRejection 是**兜底而非常规处理**。若大量拒绝都靠它接住，说明业务缺少显式 try/catch 或 catch；长期依赖会让错误来源模糊，排错困难。Node 文档建议不要在监听里"吞掉"拒绝而不处理。

**速记**：unhandledRejection **兜底未抓拒绝**。



### 主线程实践守则

**实践守则**：编写 Node 服务时，一切以"别阻塞唯一的主线程"为纲，把重活异步化或下放，方能发挥事件驱动的高并发优势。

#### 不在主线程做重计算

**守则一**：任何长时间同步计算都会占满主线程，必须移出或切片让出事件循环。

- 大循环、递归深算、繁重组装，改用 worker_threads 或 child_process 下放。
- 无法下放时，用 setImmediate 把循环切成小片，每片让出控制权。
- 判断标准：一个函数若需数十毫秒以上且必须同步跑，就违反此守则。

```js
function chunkedCompute(total, done) {
  let i = 0, sum = 0;
  function step() {
    const end = Math.min(i + 1000000, total);
    for (; i < end; i++) sum += i;
    if (i < total) setImmediate(step); // 让出事件循环
    else done(sum);
  }
  step();
}
```

> 核心一句话：**重计算别在主线程久留**。setImmediate 分片适合轻量拆分，真正重活应交给工作线程或子进程。

**速记**：重计算 **移出或切片**。



#### 不在请求路径使用同步 IO

**守则二**：生产服务的请求处理路径上，禁止使用同步 IO（如 readFileSync、execSync），它们会卡住主线程、拖垮全部并发请求。

- 启动时读配置可用同步 IO，因仅一次且不在请求热路径。
- 请求中读文件、查 DNS 一律用异步 API，结果经回调或 await 取得。
- 同步 IO 在压测下会暴露为"随机长延迟"，极难定位。

```js
const fs = require("fs").promises;
async function onRequest(res) {
  const html = await fs.readFile("index.html", "utf8"); // 异步，不卡线程
  res.end(html);
}
```

> [!WARNING]
> **警告内容**：哪怕一次 readFileSync 出现在请求路径，也会在该调用期间**冻结整个事件循环**，所有其他请求一起等待。它常被误写为"更简单"，代价却是全站卡顿，生产环境应零容忍。

**速记**：请求路径 **禁用同步 IO**。



#### 善用流处理大文件

**守则三**：处理大文件用流（Stream）而非一次性读入内存，避免内存暴涨并天然契合非阻塞模型。

- 大文件用 createReadStream 分块读取，边读边处理边写。
- 流基于事件，数据就绪才触发 data 事件，不阻塞主线程。
- 管道 pipe 可把读流直接接写流，省去手动缓冲。

```js
const fs = require("fs");
fs.createReadStream("big.log")
  .on("data", (chunk) => processLine(chunk))
  .on("end", () => console.log("处理完成"));
```

> 流是 Node 把"非阻塞 IO"发挥到极致的形式：文件再大，内存占用也只是一条数据块，主线程始终自由。

**速记**：大文件 **用流分块处理**。



#### CPU 密集下放子进程或工作线程

**守则四**：CPU 密集任务应下放，让主线程专注 IO 与调度，保持整体响应。

- **child_process / cluster**：重计算交独立进程，结果经消息回传，隔离最彻底。
- **worker_threads**：同进程内开工作线程做计算，适合需共享内存或轻量并发。
- **选型**：需强隔离用子进程，需线程级并发与内存共享用工作线程。

```js
const { Worker } = require("worker_threads");
const worker = new Worker(`
  const { parentPort } = require("worker_threads");
  let sum = 0;
  for (let i = 0; i < 1e9; i++) sum += i;
  parentPort.postMessage(sum);
`, { eval: true });
worker.on("message", (sum) => console.log("重算结果：", sum));
```

> 选型口诀：**能下放进程就下放进程**，需线程级并发用 **worker_threads**。核心都是"**别让重活在唯一的主线程上久留**"，与高并发模型自洽。

**速记**：CPU 密 **下放进程或 worker**。
