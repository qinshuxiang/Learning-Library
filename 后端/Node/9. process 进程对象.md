## process 进程对象

### process 对象的定位

#### process 是无需 require 的全局对象

**process**：是当前 Node.js 进程的**全局对象**，在任意模块中直接可用，不需要通过 require 引入。

- 它与 global、console 类似，属于运行时预置的全局成员，挂在全局作用域下。
- 直接书写 process 即可访问，无需在文件顶部声明或导入。
- 它是访问进程级信息（标识、环境、标准流、退出控制）的统一入口。

> 与第 3 篇讲过的 global 一致：process 就是 global 上的一个属性，因此 global.process === process 恒成立。把它理解为"进程自身的句柄"即可。

**速记**：process **全局直取，无需 require**。



#### process 是 EventEmitter 的实例

**EventEmitter 实例**：process 继承自 events 模块的 **EventEmitter**，因此可以用 on 方法监听进程级事件、用 emit 触发。

- 常见监听事件包括 exit、beforeExit、uncaughtException、SIGINT 等。
- 因为它具备事件机制，才能在进程退出、收到信号、抛错时"被动通知"你的代码。
- 习惯上通过 process.on(事件名, 监听器函数) 注册回调，事件名多为字符串。

```js
process.on("exit", (code) => {
  console.log("进程即将退出，退出码：" + code);
});
```

> 把 process 当作普通 EventEmitter 使用即可：注册监听器、监听事件、回调里做事。区别在于它监听的是"整个进程"的生命周期事件，而非某个业务对象的状态变化。

**速记**：process 也是 **EventEmitter**，能 on 能 emit。



#### process 与当前 Node 进程一一对应

**一一对应**：每个运行中的 Node 程序只有一个 process 对象，它**唯一代表当前这个进程**，无法用它操作别的进程。

- 你在脚本里读到的 process.pid 就是"此刻这个 Node 进程"的编号。
- 想操作别的进程（如启动子进程），要用 child_process 模块，而非 process 本身。
- 多个 Node 进程同时运行，彼此拥有各自独立的 process 对象。

> 不要把 process 当成"可以 new 出来"的类。它是单例式的运行时句柄：你只能读取它、监听它、通过它结束自身，而不能创建第二个。

**速记**：process **唯一绑定当前进程**。



### 进程标识与运行环境

#### process.pid 与 process.ppid

**process.pid**：是当前进程的**进程号**（整数），由操作系统分配，用于在系统中唯一标识这个 Node 进程。

- 每个进程启动后得到一个正整数编号，进程退出后该编号可被系统复用。
- 常用于写进程锁文件、拼日志路径、向自身发信号等场景。
- **process.ppid**：是当前进程的**父进程号**，即启动本进程的上级进程编号。

```js
console.log("本进程 PID：" + process.pid);
console.log("父进程 PID：" + process.ppid);
```

> ppid 在较新版本的 Node 中提供；通说认为多数现代 Node 发行版均已支持。父进程退出后，子进程的 ppid 可能被系统改为 1（init 进程）。

**速记**：pid 是**自身编号**，ppid 是**父进程编号**。



#### process.platform 与 process.arch

**process.platform**：返回当前操作系统平台的**字符串标识**，用于区分运行环境。**process.arch**：返回 CPU 架构标识。

- platform 常见值：darwin（macOS）、linux、win32（Windows）、freebsd 等。
- arch 常见值：x64、arm、arm64、ia32、ppc64 等，表示处理器位数与指令集。
- 两者均为只读字符串，常在分包下载、原生模块加载时做环境判断。

```js
console.log(process.platform); // 例如 "darwin"
console.log(process.arch); // 例如 "arm64"

if (process.platform === "win32") {
  console.log("Windows 专属逻辑");
}
```

> 注意 platform 在 Windows 上返回的是 **win32** 而非 windows，这是历史命名，判断 Windows 时务必比对 win32。arch 反映的是 Node 编译目标的架构，而不一定是物理 CPU（如 Rosetta 下可能显示 x64）。

**速记**：platform 看**系统**，arch 看**CPU 架构**。



#### process.version 与 process.versions

**process.version**：是当前 Node.js 运行时的**版本字符串**，形如 v18.17.0。**process.versions**：是包含 Node 及所有内置依赖版本的对象。

- version 以字母 v 开头，仅表示 Node 自身版本。
- versions 的字段包括 node、v8、uv、zlib、openssl、npm 等，用于排查环境依赖。
- 两者只读；做版本兼容判断时优先解析 version。

```js
console.log(process.version); // "v18.17.0"
console.log(process.versions.node); // 同 version 去掉 v
console.log(process.versions.v8); // V8 引擎版本
```

> 当依赖某个语言或引擎特性时，应读取 versions.v8 等具体字段，而非只看 node 版本；不同 Node 版本可能绑定不同 V8，特性支持并不只由 Node 大版本决定。

**速记**：version 是**Node 版本**，versions 是**全家桶版本**。



#### process.execPath 与 process.title

**process.execPath**：是当前 Node 可执行文件的**绝对路径**，即启动本进程所用的 node 程序位置。**process.title**：是进程的**显示名称**，可读可写。

- execPath 在启动时确定，常用于重启自身或定位 node 二进制。
- title 默认与脚本或可执行名相关，修改它会影响任务管理器里的展示名。
- title 的写入受平台限制，某些系统下长度与效果不一致。

```js
const { spawn } = require("child_process");

console.log(process.execPath); // 如 "/usr/local/bin/node"

// 用自身可执行文件重启脚本
spawn(process.execPath, [__filename]);
```

> execPath 指向的是**解释器本身**（node），不是你的脚本路径；脚本路径应通过 process.argv[1] 或 __filename 获取。title 在部分平台上无法真正改变系统进程名，仅作展示参考。

**速记**：execPath 是 **node 本体路径**，title 是**展示名**。



### 命令行参数、工作目录与环境变量

#### process.argv 的结构

**process.argv**：是一个数组，保存启动 Node 进程时的**命令行参数列表**，其前两项有固定含义。

- **argv[0]**：Node 可执行文件的路径（通常等于 process.execPath）。
- **argv[1]**：被执行的脚本文件路径（等于 __filename）。
- **argv[2] 及之后**：用户在命令行传入的自定义参数。

```js
// 运行：node app.js --name why 80
console.log(process.argv);
// [ "/usr/local/bin/node", "/path/app.js", "--name", "why", "80" ]
```

> 写命令行工具时，业务参数从 **argv[2] 开始**取；若只需脚本路径而非 node 路径，应优先用 __filename。处理带等号或连字符的参数，可配合 minimist 等解析库。

**速记**：argv 前两项是 **node 路径 + 脚本路径**。



#### process.argv0 与 process.execArgv

**process.argv0**：是 argv[0] 的**原始值**，保留最初传入的可执行名。**process.execArgv**：是专门给 Node 的**启动选项**列表，不进入脚本参数。

- argv0 与 argv[0] 多数情况下相同，但在通过 execvp 等方式改名启动时会保留原名。
- execArgv 收集形如 --max-old-space-size、--harmony、--use-strict 这类 Node 运行参数。
- execArgv 的内容**不会**出现在 argv 中，与用户业务参数严格区分。

```js
// 运行：node --max-old-space-size=2048 app.js --port 3000
console.log(process.execArgv); // [ "--max-old-space-size=2048" ]
console.log(process.argv.slice(2)); // [ "--port", "3000" ]
```

> 区分三者：argv0 是"最原始的启动名"，execArgv 是"给 Node 引擎的开关"，argv 的剩余项才是"给脚本的实参"。混淆三者常导致参数解析错位。

**速记**：argv0 **原名**、execArgv **Node 开关**、argv **脚本实参**。



#### process.cwd 与 process.chdir

**process.cwd**：返回当前**工作目录**的绝对路径（字符串）。**process.chdir**：把进程的工作目录切换到指定路径。

- cwd 的值取决于"你在哪个目录敲下 node 命令"，与脚本文件位置无关。
- chdir 接收一个目录路径，切换失败（目录不存在）会抛出异常。
- 工作目录变化是**进程级**的，会影响后续相对路径的解析基准。

```js
console.log(process.cwd()); // 如 "/Users/why/project"

try {
  process.chdir("/tmp");
  console.log(process.cwd()); // "/tmp"
} catch (err) {
  console.error("切换目录失败：" + err.message);
}
```

> 第 3 篇已强调：读取"相对于脚本"的资源要用 **__dirname** 而非 cwd，因为 cwd 随启动位置变化。chdir 会改变全局基准，多人协作或库代码里随意 chdir 容易引发路径错乱。

**速记**：cwd 是**启动目录**，chdir 改**基准路径**。



#### 环境变量 process.env 的读写

**process.env**：是一个对象，承载当前进程从操作系统继承的**环境变量键值集合**，可读可写。

- 读取：以 process.env.变量名 取得对应值，未定义时得到 undefined。
- 写入：直接给 process.env.变量名 赋值即可注入，仅对当前进程及其后续子进程生效。
- 删除：使用 delete process.env.变量名 可移除某个变量。

```js
console.log(process.env.HOME); // 当前用户主目录
process.env.APP_STAGE = "test"; // 运行时写入
delete process.env.APP_STAGE;
```

> env 的写入只在**当前进程内存**中生效，不会回写到磁盘或父 Shell。子进程通过 child_process 创建时会继承这份环境，但若父进程之后修改则子进程拿不到。

**速记**：env 是**进程环境字典**，读写仅限本进程。



#### process.env.NODE_ENV 的约定用途

**NODE_ENV**：是社区约定俗成的**运行环境标识**，常用值有 development、production、test。

- 框架与库普遍读取它来切换行为，例如生产环境关闭调试日志、启用缓存。
- 它并非 Node 内建强制字段，而是**约定**；不设置时得到 undefined。
- 生产部署应将它设为 production，以避开开发期的额外开销与警告。

```js
if (process.env.NODE_ENV === "production") {
  console.log("生产模式：启用压缩与缓存");
} else {
  console.log("非生产模式：输出详细日志");
}
```

> 不要把任何敏感配置硬编码进源码。用 NODE_ENV 区分环境、用其他环境变量承载密钥，是十二要素应用（12-factor）的基本做法。

**速记**：NODE_ENV **区分开发与生产**。



#### 环境变量值的字符串性与跨平台差异

**字符串性**：process.env 中**所有值都是字符串**（或 undefined），即使你赋数字也会被转成字符串。

- 读取到的端口、数量等数字需自行用 Number 转换后再参与运算。
- 某些平台允许 env 值为空字符串，表示"变量存在但无内容"，与 undefined 不同。
- 跨平台设置方式不同：Unix 用 变量名=值 前缀，Windows 用 set 命令。

```js
process.env.PORT = 3000;
console.log(typeof process.env.PORT); // "string"，不是 number

// Unix / macOS 启动
// PORT=3000 node app.js
// Windows（cmd）
// set PORT=3000 && node app.js
```

> 跨平台脚本不要硬编码 set 或 变量名=值 语法。需统一设置时，优先在代码内用 process.env.变量名 = "3000" 赋值，或借助 cross-env 之类工具抹平平台差异。

**速记**：env 值**一律字符串**，平台**设置语法不同**。



### 标准输入输出流

#### process.stdin、stdout、stderr 的类型

**标准流**：process.stdin 是**可读流**，process.stdout 与 process.stderr 是**可写流**，三者分别对应标准输入、标准输出、标准错误。

- stdin 默认处于暂停模式，需通过事件或 resume 才能读取用户输入。
- stdout 用于正常输出，stderr 用于错误信息，二者在多数终端都指向屏幕。
- 当输出被重定向到文件或管道时，stdout 与 stderr 可被分别捕获，便于区分正常与错误日志。

```js
console.log(typeof process.stdin); // "object"（Stream 实例）
console.log(typeof process.stdout); // "object"
console.log(process.stdout === process.stderr); // false，二者独立
```

> 三者都是 Stream 实例而非普通对象；在 TTY（终端）场景下它们具备额外能力（如颜色、光标控制），在管道场景则是普通流。不要把它们当成字符串变量直接拼接。

**速记**：stdin **可读**、stdout/stderr **可写**。



#### process.stdout.write 的用法

**process.stdout.write**：是向标准输出写入内容的**底层方法**，返回布尔值表示是否已被全部刷出。

- 完整写法为 process.stdout.write(要写入的字符串, 字符编码, 写入完成回调)，后两个参数可选。
- 返回 true 表示数据已刷出，返回 false 表示内核缓冲已满、需等待 drain 事件再继续写。
- 它是 console.log 的底层实现，不自动追加换行符。

```js
const flushed = process.stdout.write("不加换行");
console.log("write 返回值：" + flushed);

process.stdout.write("进度: 50%\r", "utf8"); // 同一行覆盖刷新
```

> 与 console.log 不同，write **不会自动加换行**，适合做进度条、同行动态刷新。写出大量数据时，应监听 stdout 的 drain 事件，避免回调堆积拖慢进程。

**速记**：write **裸写不换行**，返回**是否刷出**。



#### 与 console.log 的关系

**console.log**：本质是**调用 process.stdout.write 并补一个换行符**的便捷封装，二者底层同源。

- console.log 会在末尾追加平台相关的换行符（类 Unix 为换行，Windows 为回车换行）。
- console.error 与 console.warn 写入的是 **stderr**，而 console.log 写入 stdout。
- 在测试中常通过 mock stdout/stderr 来捕获 console 输出，因为 console 只是它们的上层封装。

```js
console.log("hello");
// 等价于：
process.stdout.write("hello\n");

console.error("boom"); // 实际写入 process.stderr
```

> 需要"无换行"或"精确控制缓冲"时应直接用 write；平时打印调试用 console.log 更省心。注意 console.log 与 stdout.write 混用同一流时，输出顺序依赖刷新时机，并非绝对按语句顺序落盘。

**速记**：console.log = **stdout.write + 换行**。



### 进程生命周期、退出与信号事件

#### process.exit 与退出码约定

**process.exit**：用于**立即终止**当前进程，可传入一个整数作为退出码，0 表示成功、非 0 表示异常。

- 完整写法为 process.exit(退出码)，省略时默认使用 process.exitCode（或 0）。
- 调用后 Node 会强制停止，后续代码、未完成的异步回调都不再执行。
- 约定：0 成功；1 未捕获异常；2 命令行参数或用法错误；其余非 0 表示各类失败。

```js
if (!process.env.REQUIRED_TOKEN) {
  console.error("缺少 REQUIRED_TOKEN，退出");
  process.exit(1); // 非零表示启动失败
}
```

> exit 是"硬终止"，不等事件循环清空就结束，因此不要在它之前安排异步清理。需要优雅收尾应改用 exitCode 或监听 beforeExit（见后续考点）。

**速记**：exit **立刻杀进程**，0 成非 0 败。



#### process.exitCode 的正确用法

**process.exitCode**：是进程的**期望退出码**，设置后进程在**自然结束**时以该码退出，而不会像 exit 那样立即中断。

- 它只是一个"待生效"的码，进程仍会走完事件循环、正常退出。
- 若随后调用 process.exit(码)，则显式传入的码会覆盖 exitCode。
- 适合"先做完手里的事，再以指定码收场"的场景。

```js
process.exitCode = 1; // 记下失败，但不立即中断

doSomeAsyncWork(() => {
  // 工作完成，事件循环清空后进程以 1 退出
});
```

> exitCode 与 exit 的关键区别：前者**让进程自然退出并带码**，后者**强制马上退出**。凡是还能继续处理业务，就优先用 exitCode，把"何时停"交给事件循环决定。

**速记**：exitCode **自然带码退**，exit **强停**。



#### exit 事件与 beforeExit 的区别

**exit 事件**：在进程**即将退出时**触发，监听器只能执行**同步**代码。**beforeExit 事件**：在 Node **清空事件循环、本将退出前**触发，监听器可继续安排异步任务挽留进程。

- exit 触发时资源已不可靠，写文件、发网络请求等异步操作不会被完成。
- beforeExit 只在"无更多工作"时触发，若监听器又注册了任务，进程会继续存活。
- 通过 process.exit() 强制退出时**不会**触发 beforeExit，只会触发 exit。

```js
process.on("beforeExit", (code) => {
  console.log("事件循环已空，准备退出，码：" + code);
  // 可在此安排同步收尾；安排异步会令进程继续
});

process.on("exit", (code) => {
  // 只能写同步逻辑，例如：
  console.log("确定性收尾，码：" + code);
});
```

> beforeExit 不是"退出前总会被调用"的钩子：一旦你主动 process.exit()，它就被跳过。exit 监听器务必保持同步——在里面调用异步函数不会等待其完成，日志可能丢失。

**速记**：exit **只跑同步**，beforeExit **可挽留**。



#### 信号 SIGINT、SIGTERM 与 SIGKILL

**信号**：是操作系统向进程发送的**通知事件**，Node 中以 SIG 前缀的字符串事件名暴露；其中 SIGINT、SIGTERM、SIGKILL 用途与"能否捕获"各不相同。

- **SIGINT**：用户按下 Ctrl+C 触发，常被捕获用于优雅退出，可拦截。
- **SIGTERM**：系统或进程管理器请求终止（如 docker stop），可捕获、可拦截。
- **SIGKILL**：强制杀死信号，操作系统**不允许**被捕获或忽略，进程必亡。

```js
process.on("SIGINT", () => console.log("收到 SIGINT"));
process.on("SIGTERM", () => console.log("收到 SIGTERM"));
// SIGKILL 无法 process.on 监听，以下写法不会生效
// process.on("SIGKILL", () => {});
```

> SIGKILL 之所以"无敌"，是为防止进程彻底失控时无法终止。设计优雅退出应监听 SIGINT 与 SIGTERM，而不能依赖捕获 SIGKILL——收到它的进程会瞬间消失，来不及做任何清理。

**速记**：SIGINT/SIGTERM **可捕获**，SIGKILL **不可拦**。



#### process.on("SIGINT") 实现优雅退出

**优雅退出**：通过 process.on(信号名, 监听器) 监听终止信号，在退出前完成**资源释放、连接关闭、日志落盘**等收尾，而非被硬杀。

- 收到 SIGINT 后，先执行清理逻辑，再调用 process.exit 给出明确退出码。
- 清理若含异步（关数据库、刷盘），需用 Promise 或回调确保完成后再 exit。
- 仅捕获不退出会导致进程"收到信号却赖着不走"，需显式结束。

```js
let server;
process.on("SIGINT", () => {
  console.log("收到 SIGINT，开始优雅关闭");
  if (server) server.close(() => process.exit(0));
  else process.exit(0);
});
```

> 优雅退出的要义是"收到信号 → 停收新请求 → 等存量处理完 → 关资源 → 退出"。只监听不退出是不完整的：进程会卡在信号处理里，反而更不优雅。

**速记**：收信号 → **先收拾再走**。



#### uncaughtException 与 unhandledRejection 的兜底

**uncaughtException**：当**未被捕获的同步异常**冒泡到事件循环顶层时触发。**unhandledRejection**：当 **Promise 被拒绝却无人处理**时触发，二者都是最后的错误兜底钩子。

- 默认不监听时，二者都会导致进程以非零码崩溃退出。
- 监听后可阻止崩溃，但**继续运行风险高**：内存与状态可能已损坏。
- 推荐做法是在监听器中记录日志并调用 process.exit，而非默默续命。

```js
process.on("uncaughtException", (err) => {
  console.error("未捕获异常：" + err.stack);
  process.exit(1); // 记录后主动退出，避免带病运行
});

process.on("unhandledRejection", (reason) => {
  console.error("未处理的 Promise 拒绝：" + reason);
  process.exit(1);
});
```

> [!WARNING]
> **警告内容**：用这两个钩子"吞掉"错误并继续运行非常危险——进程可能处于不一致状态，后续行为不可预测。官方建议仅将其用于**记录日志与清理**，随后务必 process.exit，不要当作正常控制流。

**速记**：二者是**最后兜底**，记完**应退出**。



### 资源与性能查看

#### process.memoryUsage 各字段

**process.memoryUsage**：返回当前进程**内存占用详情**的对象，包含 rss、heapTotal、heapUsed、external、arrayBuffers 五个字段，单位均为字节。

- **rss**（resident set size，常驻集大小）：进程占用的物理内存总量，含代码、堆、栈、共享库。
- **heapTotal**：V8 已申请并管理的**堆内存总大小**。
- **heapUsed**：V8 堆中**已被使用**的部分，最直观反映 JS 对象占用。
- **external**：由 C++ 对象绑定到 JS、却不在 V8 堆里的内存（如 Buffer 底层）。
- **arrayBuffers**：ArrayBuffer 与 SharedArrayBuffer 占用的内存，归在 external 之外的独立统计。

```js
const usage = process.memoryUsage();
console.log("rss：" + (usage.rss / 1024 / 1024).toFixed(1) + " MB");
console.log("堆已用：" + (usage.heapUsed / 1024 / 1024).toFixed(1) + " MB");
console.log("堆总计：" + (usage.heapTotal / 1024 / 1024).toFixed(1) + " MB");
```

> rss 大于 heapTotal + heapUsed 是常态，因为 rss 还含栈、代码段与外部分配。排查内存泄漏应重点盯 **heapUsed 的持续增长**；大 Buffer 占用更多体现在 external 而非 heapUsed。

**速记**：rss **物理总占用**，heap **JS 堆**，external **原生外挂**。



#### process.cpuUsage 的测量

**process.cpuUsage**：返回进程**消耗的用户态与内核态 CPU 时间**，单位为微秒（百万分之一秒）。

- 完整写法为 process.cpuUsage(上一次的结果对象)，不传参则返回自进程启动以来的累计值。
- 返回对象的 user 字段是用户态耗时，system 字段是内核态耗时。
- 传入前一次结果可得到**两次调用之间的增量**，便于做区间统计。

```js
const start = process.cpuUsage();
// 执行一段计算
let sum = 0;
for (let i = 0; i < 1e8; i++) sum += i;

const diff = process.cpuUsage(start);
console.log("用户态微秒：" + diff.user);
console.log("内核态微秒：" + diff.system);
```

> cpuUsage 测的是**两个快照的差值**，不传参时是"累计到此刻"。它反映真实 CPU 消耗而非占用率，若想算百分比需结合 uptime 或两次时间差自行换算。

**速记**：cpuUsage **微秒计 CPU**，传参得**增量**。



#### process.uptime 的含义

**process.uptime**：返回当前 Node 进程**自启动以来经过的秒数**，为浮点数，精度到毫秒级以下。

- 它统计的是 Node 进程自身的存活时长，而非操作系统开机时长。
- 常用于健康检查接口，报告服务连续运行了多久。
- 与 Date.now 相减得到的墙钟时间不同，uptime 只算进程活跃区间。

```js
setInterval(() => {
  console.log("已运行 " + process.uptime().toFixed(0) + " 秒");
}, 5000);
```

> 切勿用 uptime 当"当前时间戳"用，它从 0 起步、只记进程寿命。需要真实时间应改用 Date 或 performance 相关 API。

**速记**：uptime **从 0 记进程寿命**。



#### process.hrtime.bigint 高精度计时

**process.hrtime.bigint**：返回以 **BigInt 纳秒**表示的高精度时间，适合做纳秒级耗时测量，且无需像旧式 hrtime 那样手动算差值。

- 它返回一个 BigInt，单位是纳秒（十亿分之一秒）。
- 调用两次相减即可得到精确间隔，精度远高于 Date.now 的毫秒。
- 旧接口 process.hrtime(时间数组) 已不推荐使用，bigint 形式更简洁。

```js
const start = process.hrtime.bigint();
// 执行待测代码
const data = "x".repeat(1000000).split("").reverse().join("");
const end = process.hrtime.bigint();

const nanoseconds = end - start;
console.log("耗时：" + (Number(nanoseconds) / 1e6).toFixed(3) + " 毫秒");
```

> hrtime.bigint 的"起点"是**任意固定的过去时刻**，所以单看一次返回值没有绝对意义，必须做"末减初"的差值才有意义。BigInt 不能与普通数字直接加减，比较或打印前记得转换。

**速记**：hrtime.bigint **纳秒 BigInt**，相减得**真间隔**。
