## Express 路由与中间件

### 中间件的定义与本质

#### 中间件是一个签名为 (req, res, next) 的函数

**中间件（Middleware）**：是 Express 中处理请求的函数，其标准签名接收请求对象、响应对象与一个名为 next 的控制函数三个参数，形如 function (req, res, next)。

- 第一个参数 req 是请求对象，携带方法、路径、头与请求体等信息。
- 第二个参数 res 是响应对象，用于向客户端写回状态、头与响应体。
- 第三个参数 next 是控制函数，调用它可把请求交给后续中间件或路由。
- 中间件内部必须二选一：要么调用 res 的方法结束响应，要么调用 next 交出控制权，否则请求会一直挂起。

> 中间件与第 16 篇 http 模块的回调 (req, res) 同源，只是多了 next 这一环，从而把单回调处理升级为可串联的处理链。正是 next 的存在，让多个中间件能依次协作。

**速记**：中间件 = (req, res, next)，结束或放行。



#### 中间件可以访问请求与响应对象

**访问能力**：任意中间件都能读写 req 与 res，从而在前置阶段加工数据、附加属性或提前响应，这是它区别于普通工具函数的关键。

- 中间件可在 req 上挂载自定义属性，供后续中间件与路由处理函数读取，例如把解析出的用户放进 req.user。
- 中间件可修改 res，例如统一设置响应头、注入跨域头或改写状态码。
- 中间件能决定在此终止还是继续向下，因此既适合做预处理，也适合做短路拦截。

> 在 req 上挂载属性是一种约定俗成的做法，但属性名应避免覆盖内置字段（如不要覆盖 req.query），否则会干扰后续解析。命名上常加前缀或命名空间以降低冲突。

**速记**：中间件可读写 req、res，贯通上下游。



### 中间件的作用与分类

#### 应用级中间件用 app.use 注册

**应用级中间件（Application-level Middleware）**：通过 app.use 或 app.METHOD 绑定到整个应用实例，对匹配请求全局生效。

- 签名：app.use(path, callback)，其中 callback 即中间件函数，path 可省略表示对所有请求生效。
- 不写路径时，app.use(myMiddleware) 会对每一个进来的请求执行。
- 写上路径后只对以该前缀开头的请求生效，路径过滤的细节见后续章节。

```js
const express = require("express");
const app = express();

function requestTime(req, res, next) {
  req.requestTime = new Date().toISOString();
  next();
}

app.use(requestTime); // 全局生效，每个请求都打时间戳

app.get("/", (req, res) => {
  res.send("请求到达于 " + req.requestTime);
});

app.listen(3000);
```

> app.use 与 app.get 等路由方法的区别在于：app.use 只看路径前缀是否匹配，不限定 HTTP 方法；app.get 等方法既看路径又限定方法。二者可叠加使用。

**速记**：应用级 = app.use 全局挂。



#### 路由级中间件用 router.use 注册

**路由级中间件（Router-level Middleware）**：绑定到 express.Router 实例，作用范围被限制在挂载该 Router 的前缀之下，是模块拆分的基石。

- 签名与 app.use 一致：router.use(path, callback)，只是作用域缩到当前 Router。
- 在 Router 上注册的中间件，只影响经由该 Router 处理的请求。
- 通过 app.use(prefix, router) 把 Router 挂到某个前缀，路由级中间件随之生效。

```js
const express = require("express");
const router = express.Router();

router.use((req, res, next) => {
  console.log("进入了用户模块");
  next();
});

router.get("/profile", (req, res) => res.send("profile"));
module.exports = router;
```

> 路由级中间件与应用级中间件本质相同，区别只在挂载点。复杂项目偏好路由级，因为它让某一组路由共用一段逻辑变得自然且不污染全局。

**速记**：路由级 = router.use 限模块。



#### 内置中间件由 Express 直接提供

**内置中间件（Built-in Middleware）**：是 Express 自带、无需额外安装的常用中间件，典型包括 express.json、express.urlencoded 与 express.static。

- express.json 用于解析 JSON 请求体，把结果挂到 req.body，签名：express.json(options)。
- express.urlencoded 解析表单格式请求体，签名：express.urlencoded(options)，常传 { extended: true }。
- express.static 托管静态目录，签名：express.static(root, options)，root 是目录路径。

```js
const express = require("express");
const app = express();

app.use(express.json()); // 解析 application/json 请求体
app.use(express.static("public")); // 托管 public 目录下的文件

app.post("/echo", (req, res) => {
  res.json(req.body); // req.body 已由 express.json 填好
});

app.listen(3000);
```

> express.json 与 express.urlencoded 必须在需要读取 req.body 的路由之前注册，否则 req.body 为 undefined。这是顺序相关性的典型体现，后续会专门讨论。

**速记**：内置 = json、urlencoded、static 三件套。



#### 第三方中间件需单独安装

**第三方中间件（Third-party Middleware）**：由社区维护、通过 npm 安装的中间件，覆盖日志、压缩、跨域等通用能力，安装后同样用 app.use 注册。

- 常见如 morgan 做访问日志、cors 处理跨域、helmet 加固安全头。
- 使用方式：先 npm install 再 require，然后 app.use(require("morgan")("dev"))。
- 选型原则是以成熟库替代手搓，避免重复造轮子与安全盲区。

> 第三方中间件与内置中间件在注册方式上完全相同，区别只在是否需要安装。不要为了练手而自己实现 cors 或压缩这类已有成熟方案的能力。

**速记**：第三方 = npm 装、app.use 挂。



#### 错误处理中间件拥有四个参数

**错误处理中间件（Error-handling Middleware）**：是签名形如 function (err, req, res, next) 的特殊中间件，专门用于集中处理链路中抛出的错误。

- 四个参数依次是错误对象、请求对象、响应对象、控制函数，顺序与数量都固定。
- 它必须定义四个参数；若漏掉 err 写成三个参数，Express 会把它当成普通中间件，从而失去错误处理能力。
- 注册位置放在所有普通路由与中间件之后，详见错误处理章节。

```js
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  throw new Error("演示错误");
});

app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).send("出错了");
});

app.listen(3000);
```

> 错误处理中间件靠参数个数为 4 被识别。把普通中间件误写成四参是常见笔误；反之少写 err 则永远不会被当作错误处理器。

**速记**：错误中间件 = 四参 (err, req, res, next)。



### 洋葱式执行流程与 next 的三种用法

#### 请求依次穿过注册的中间件

**洋葱模型**：请求按注册顺序依次进入各中间件，像穿过一层层包裹的结构；每个中间件都能在 next 调用前与调用后分别执行代码，形成进去一层、出来一层的对称执行。

- 注册顺序即执行顺序，先注册的中间件先接触请求。
- 中间件调用 next 后，控制流下沉到下一个中间件；等后续全部完成，再回到当前中间件 next 之后的代码。
- 这种对称结构非常适合做计时、日志、事务等前后夹击的逻辑。

```js
const express = require("express");
const app = express();

app.use((req, res, next) => {
  console.log("A 前");
  next();
  console.log("A 后");
});
app.use((req, res, next) => {
  console.log("B 前");
  next();
  console.log("B 后");
});
app.get("/", (req, res) => {
  console.log("处理");
  res.send("ok");
});

app.listen(3000);
// 输出顺序：A 前、B 前、处理、B 后、A 后
```

> 洋葱模型的前提是每个中间件都正确调用 next（或结束响应）。一旦某个中间件既没 next 也没结束，整条链就停在那里，后面的后代码永远不执行。

**速记**：洋葱 = 前入后出，对称执行。



#### next 的三种用法

**next 的语义**：next 是中间件交出控制权的开关，按传入参数的不同有三种行为，分别是交给下一个、直接进入错误处理、或不调用导致挂起。

- 调用 next() 不带参：把请求交给下一个中间件或路由，正常流转。
- 调用 next(err) 带错误对象：跳过后续普通中间件，直接落到错误处理中间件。
- 既不调用 next 也不响应：请求在该中间件处挂起，直到客户端超时，是隐患来源。

> next(err) 只能跳到错误处理中间件，普通中间件即便写在后面也不会被它触发；而忘记 next 是最隐蔽的挂起原因，调试时先看每个分支是否都有 next 或 res 结束。

**速记**：next = 空参放行、带错进错误处理、不调挂起。



#### 中间件可在 next 前后都执行代码

**前后执行点**：由于 next 是同步调用、后续逻辑会返回，中间件在 next() 之前的代码先于下游执行，next() 之后的代码后于下游执行，天然形成包裹。

- 典型用途一：next 前记录开始时间，next 后计算耗时并打日志。
- 典型用途二：next 前打开资源、next 后释放资源，做到成对管理。
- 注意 next 之后的代码仍会在响应结束后运行，不要在已结束响应后再写 res。

```js
const express = require("express");
const app = express();

function timing(req, res, next) {
  const start = Date.now();
  next(); // 下沉，等待下游处理完
  const cost = Date.now() - start;
  console.log(req.method + " " + req.url + " 耗时 " + cost + "ms");
}

app.use(timing);
app.get("/", (req, res) => res.send("ok"));
app.listen(3000);
```

> 这种前后都执行的能力依赖 next 同步返回；若下游是异步且未在 next 回调里结束，计时可能不准。需要精确统计异步耗时要用其他方式或异步本地存储。

**速记**：next 前后 = 包裹式前后置逻辑。



### 路径过滤与注册顺序

#### 路径过滤只对该前缀生效

**路径前缀过滤**：app.use 与 app.METHOD 都支持第一参数传路径，表示仅当请求路径以该前缀开头（或在精确匹配规则下相等）时才执行对应中间件或路由。

- 不写路径的 app.use(mw) 对所有请求生效，等价于路径为根斜杠。
- 带前缀的 app.use("/api", mw) 仅匹配以 /api 开头的请求，如 /api/users。
- 路径可写字符串，也可写路径模式或正则表达式，匹配规则与路由一致。

```js
const express = require("express");
const app = express();

app.use("/admin", (req, res, next) => {
  console.log("仅 admin 前缀进入");
  next();
});

app.get("/admin/home", (req, res) => res.send("admin home"));
app.get("/public", (req, res) => res.send("no log"));

app.listen(3000);
```

> 路径过滤是以前缀判断的：app.use("/admin") 会同时匹配 /admin 与 /admin/anything，但不会匹配 /administrator。需要精确匹配请使用路由方法或正则。

**速记**：路径过滤 = 前缀命中才执行。



#### 注册顺序决定执行顺序

**顺序优先**：中间件与路由严格按书写的先后注册，先写先执行；当多个处理器都能匹配同一请求时，只有第一个调用 next 或响应的会真正生效。

- 静态中间件放在路由前：先尝试返回静态文件，未命中再进入路由。
- 静态中间件放在路由后：路由已响应则静态不再执行；若路由都未匹配，仍会尝试静态，但不如放前面直观。
- 404 中间件必须放在所有正常路由之后，才能兜住前面都没匹配的请求。

```js
const express = require("express");
const app = express();

app.use(express.static("public")); // 建议放在业务路由之前
app.get("/", (req, res) => res.send("首页"));
app.use((req, res) => res.status(404).send("未找到")); // 404 必须最后

app.listen(3000);
```

> 顺序错误最常见的后果是某个中间件永远轮不到。例如把 express.json 写在需要 req.body 的路由之后，req.body 就是 undefined。排查时优先核对注册顺序。

**速记**：顺序 = 先写先跑，404 在最后。

> [!TIP]
> **建议内容**：把静态资源、请求体解析、日志这类全局预处理放在业务路由之前，把 404 与错误处理放在所有路由之后，是 Express 应用的标准骨架顺序。



#### 404 中间件必须放在最后

**兜底位置**：404 处理器本质是一个不带路径、且注册在最末尾的中间件，专门捕获前面所有路由都未匹配的请求并响应 404。

- 它不需要路径参数，因为排在最后时只有前面的路由都没处理的请求才会流到这里。
- 必须调用 res.status(404) 之类显式设置状态码，否则默认返回 200。
- 若把它写在正常路由之前，正常路由将永远无法被命中。

```js
const express = require("express");
const app = express();

app.get("/users", (req, res) => res.send("用户列表"));
// 所有未匹配 /users 的请求最终到达这里
app.use((req, res) => {
  res.status(404).send("404 Not Found");
});

app.listen(3000);
```

> 404 中间件与错误处理中间件不同：它接收三个参数 (req, res, next)，不是四参；它处理无匹配路由，错误中间件处理链路中抛出的错误。二者不要混用。

**速记**：404 = 无路径、最末位、状态码 404。



### 路由的定义与路径匹配

#### 路由把方法、路径映射到处理函数

**路由（Route）**：是 Express 把某个 HTTP 方法 + 某个路径绑定到一个或多个处理函数的机制，匹配成功即执行对应函数并写回响应。

- 路由方法对应 HTTP 动词：get、post、put、patch、delete、head、options 等。
- 通用方法 all 表示匹配任意 HTTP 方法，适合做跨方法的统一拦截。
- 每个路由方法的签名：app.METHOD(path, handler)，handler 可连续写多个，形成处理函数链。

```js
const express = require("express");
const app = express();

app.get("/articles", (req, res) => res.send("列表"));
app.post("/articles", (req, res) => res.send("创建"));
app.delete("/articles/:id", (req, res) => res.send("删除"));

app.listen(3000);
```

> 路由方法名必须与 HTTP 方法小写一致；用错方法（如对 POST 请求却只注册了 get 路由）会得到 404。需要不限方法时用 all 或把逻辑抽成中间件。

**速记**：路由 = 方法 + 路径 → 处理函数。



#### 路径参数用冒号声明

**路径参数（Route Parameter）**：是在路径中用冒号加名字声明的一段占位，Express 会把实际值解析出来挂到 req.params 上，便于从 URL 提取资源标识。

- 声明方式：在路径中写冒号加参数名，如 /users/:id 表示第三段的动态 id。
- 取值方式：在处理函数里读取 req.params.id，得到路径中对应的字符串。
- 可声明多个参数，如 /users/:userId/posts/:postId，分别落入 req.params.userId 与 req.params.postId。

```js
const express = require("express");
const app = express();

app.get("/users/:id", (req, res) => {
  res.send("用户 id = " + req.params.id);
});

app.get("/users/:userId/posts/:postId", (req, res) => {
  res.send("用户 " + req.params.userId + " 的文章 " + req.params.postId);
});

app.listen(3000);
```

> 路径参数默认只匹配单个路径段（到下一个斜杠为止），不会跨斜杠。需要匹配含斜杠的内容要用自定义正则或通配，详见后续章节。

**速记**：路径参数 = 冒号声明、req.params 取。



#### 可选参数用问号修饰

**可选参数**：在冒号参数名后加问号，表示该段参数可有可无，匹配带或不带该段的两种路径。

- 写法：/users/:id? 既能匹配 /users，也能匹配 /users/123。
- 与必填参数区别在于：可选参数未出现时，req.params.id 为 undefined。
- 多个参数可分别独立加问号，各自决定可缺省。

```js
const express = require("express");
const app = express();

app.get("/files/:dir/:name?", (req, res) => {
  const name = req.params.name || "默认文件";
  res.send("目录 " + req.params.dir + " 文件 " + name);
});

app.listen(3000);
```

> 可选参数与查询参数用途不同：前者是路径的一部分、语义上属于资源定位；后者是问号后的筛选条件。不要为了省事把本该必填的标识写成可选，会弱化接口约束。

**速记**：可选参数 = 冒号后加问号。



#### 查询参数由 req.query 自动解析

**查询参数（Query String）**：是 URL 中问号之后的键值对，Express 借助底层解析把它自动整理为 req.query 对象，无需手工切分。

- 取值方式：req.query.name 得到字符串；多值键会自动合并为数组。
- 重复键表现：?tag=a&tag=b 时 req.query.tag 为 ["a", "b"]。
- 与路径参数分工：路径参数定位资源，查询参数表达筛选、分页、排序等条件。

```js
const express = require("express");
const app = express();

app.get("/search", (req, res) => {
  const q = req.query.q;
  const tags = req.query.tag; // 可能是字符串或数组
  res.send("搜索 " + q + " 标签 " + JSON.stringify(tags));
});

app.listen(3000);
// 访问 /search?q=node&tag=a&tag=b
```

> req.query 的值永远是字符串或字符串数组，数字、布尔需自行转换；空查询串得到空对象而非 null。这一解析由 Express 内置完成，与第 17 篇手搓 URL 类形成对照。

**速记**：查询参数 = req.query 自动成对象。



#### 通配与正则匹配

**通配符**：路径中的星号表示匹配余下任意多级路径，用于兜底或挂载子路由；正则则用于更精细的匹配规则。

- 星号写法：app.get("/files/*", handler) 匹配 /files/ 之后的所有内容。
- 正则写法：app.get(/^\/u\/(\d+)$/, handler) 用原生正则匹配路径。
- app.all 匹配所有 HTTP 方法，常配合通配做统一拦截。

```js
const express = require("express");
const app = express();

app.all("/api/*", (req, res, next) => {
  console.log("进入 api 任意子路径");
  next();
});

app.get(/\/v1\/users/, (req, res) => res.send("正则命中"));

app.listen(3000);
```

> 通配星号与路径参数的区别：星号不单独命名、整体作为剩余路径；若需要拿到剩余内容，可用命名参数配合正则。过度使用通配会掩盖具体路由，调试时优先写明确路径。

**速记**：通配 = 星号兜底，正则精配。



### 路由链式、route 对象与 express.Router 模块化

#### app.route 链式注册多个方法

**route 对象**：app.route(path) 返回一个针对同一路径的路由对象，可在其上链式调用不同方法，避免重复书写路径、减少笔误。

- 签名：app.route(path)，返回可链式调用的路由构建器。
- 链式写法：app.route("/book").get(h1).post(h2).put(h3) 一次声明多方法。
- 好处是路径只出现一次，后续改路径只改一处。

```js
const express = require("express");
const app = express();

app.route("/book")
  .get((req, res) => res.send("查"))
  .post((req, res) => res.send("增"))
  .put((req, res) => res.send("改"))
  .delete((req, res) => res.send("删"));

app.listen(3000);
```

> app.route 适合同一资源多种操作集中声明，可读性高；但跨多个不同路径的复用仍要靠 express.Router 或中间件。二者互补而非替代。

**速记**：app.route = 同路径、链多方法。



#### 用 express.Router 创建模块化路由

**Router 实例**：express.Router 创建一个独立的最小路由实例，可在其上像 app 一样注册路由与中间件，再用 app.use 挂到前缀，实现按业务拆分。

- 创建签名：express.Router(options)，options 可选，如 { mergeParams: true } 用于继承父路由参数。
- 在 Router 上用 router.get、router.post 等注册路由，语法与 app 一致。
- 挂载签名：app.use(prefix, router)，prefix 决定该模块所有路由的统一前缀。

```js
const express = require("express");
const router = express.Router();

router.get("/", (req, res) => res.send("用户首页"));
router.get("/:id", (req, res) => res.send("用户 " + req.params.id));

module.exports = router;
```

> mergeParams 选项很关键：当父路由带参数（如 /users/:userId/posts）而子 Router 想用 req.params.userId 时，必须设 { mergeParams: true }，否则子路由拿不到父级参数。

**速记**：Router = 独立实例、前缀挂载。



#### 把路由拆成独立文件并用 module.exports 导出

**模块拆分**：将每个业务领域的路由放进独立文件，文件内创建 Router、注册路由、用 module.exports 导出，入口文件再统一挂载，是 Express 工程的标准组织方式。

- 每个路由文件只负责一类资源，关注点单一，便于维护与测试。
- 用 module.exports = router 把 Router 暴露给入口。
- 入口用 app.use(prefix, require("./routes/xxx")) 挂载，前缀即该资源的基路径。

```js
// routes/users.js
const express = require("express");
const router = express.Router();

router.get("/", (req, res) => res.send("用户列表"));
router.get("/:id", (req, res) => res.send("用户 " + req.params.id));

module.exports = router;

// routes/products.js
const express = require("express");
const router = express.Router();

router.get("/", (req, res) => res.send("商品列表"));

module.exports = router;
```

> 拆分粒度以资源域为单位：用户、商品、订单各一文件，而不是按方法拆。文件过多会增加跳转成本，过少则失去拆分意义，通常以一个 Router 管一类资源为宜。

**速记**：拆分 = 一类资源一文件、module.exports 导出。



#### 入口文件统一挂载

**入口装配**：在应用入口用 app.use 把多个 Router 分别挂到各自前缀，组合成完整路由树；同时在此处安排全局预处理与错误处理顺序。

- 全局中间件（解析、日志、跨域）先注册，再挂载各业务 Router。
- 每个 Router 的前缀在入口声明，路由文件内部写相对路径。
- 404 与错误中间件最后注册，确保兜底。

```js
// app.js
const express = require("express");
const usersRouter = require("./routes/users");
const productsRouter = require("./routes/products");

const app = express();

app.use(express.json()); // 全局解析请求体
app.use("/users", usersRouter); // 用户模块挂到 /users
app.use("/products", productsRouter); // 商品模块挂到 /products
app.use((req, res) => res.status(404).send("未找到")); // 404 兜底

app.listen(3000);
```

> 入口文件应保持薄：只做装配与顺序安排，不堆业务。业务逻辑都在各 Router 文件里，这样规模变大后仍清晰可维护。

**速记**：入口 = 薄装配、定顺序、挂前缀。

> [!NOTE]
> **提醒内容**：目录组织建议采用 routes/ 下放各 Router 文件、app.js 做装配、中间件放 middleware/ 目录。这种分层让路径前缀在入口、逻辑在模块各司其职，是 Express 社区的通行做法。



### 错误处理、404 与异步陷阱

#### 错误处理中间件必须放在最后

**错误落点**：四参错误处理中间件要注册在所有普通路由与中间件之后，才能保证链路中抛出的错误都汇聚到这里统一响应。

- 注册顺序：先写业务路由，最后写 app.use((err, req, res, next) => {...})。
- 进入条件：只有调用过 next(err) 或路由处理函数抛出错误时才会触发（Express 4 的同步抛出会触发，异步需特殊处理，见下节）。
- 内部应判断是否已发送响应，已发送则只记录日志、不再写头。

```js
const express = require("express");
const app = express();

app.get("/", (req, res) => {
  throw new Error("同步错误");
});

app.use((err, req, res, next) => {
  if (res.headersSent) {
    return next(err); // 已响应则交给默认处理器
  }
  console.error(err.stack);
  res.status(500).send("服务器内部错误");
});

app.listen(3000);
```

> 错误处理中间件若漏掉第一个 err 参数，会被当成普通中间件且永不接错；若写在普通路由之前，则错误还没产生它就先占了位置，反而吞掉正常请求。位置与四参缺一不可。

**速记**：错误中间件 = 四参、最末、判已发送。



#### 默认错误处理与自定义

**默认处理器**：Express 自带一个底层错误处理中间件，当错误未被自定义处理器接住时，它会把错误栈（非生产环境）返回并设置 500；自定义处理器可覆盖此行为。

- 未注册任何错误中间件时，Express 默认返回 500 与简单文本。
- 生产环境默认处理器不暴露错误栈，避免泄露内部信息。
- 自定义处理器应始终设置合适的状态码与精简错误信息，不要原样回抛堆栈给客户端。

> 即使写了自定义错误中间件，也建议保留已发送响应则 next(err) 的兜底分支，让 Express 默认处理器接管无法安全覆写的情形，避免二次写头报错。

**速记**：默认 = 兜底 500，生产不吐栈。



#### 异步错误需手动转发

**异步陷阱**：Express 4 不会自动捕获异步处理函数（Promise reject、async 抛错）里的异常，错误会逃逸出请求链，导致进程可能崩溃或连接挂起；必须显式 try/catch 并调用 next(err)。

- 在 async 处理函数里用 try/catch 包住逻辑，catch 中调用 next(err) 把错误送入错误中间件。
- 也可写一个包装函数包裹 async 处理器，统一 catch 后 next(err)，减少重复代码。
- Express 5 起原生支持 async 函数抛错自动转发，无需手动包装。

```js
const express = require("express");
const app = express();

function asyncHandler(fn) {
  return (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
}

app.get("/data", asyncHandler(async (req, res) => {
  const result = await Promise.reject(new Error("异步失败"));
  res.send(result);
}));

app.use((err, req, res, next) => {
  res.status(500).send("异步错误：" + err.message);
});

app.listen(3000);
```

> 忘记转发异步错误是 Express 4 最常见的线上事故之一：一个未捕获的 reject 既进不了错误中间件，又可能让请求永久挂起。项目升级到 Express 5 可从根本上消除该陷阱。

**速记**：异步错 = try/catch 转 next，或升 Express 5。

> [!WARNING]
> **警告内容**：Express 4 下 async 函数抛出的异常不会自动进入四参错误中间件。务必用 try/catch 配 next(err) 或 asyncHandler 包装，否则错误逃逸、请求挂起甚至进程崩溃。



#### next 被调用两次导致头已发送

**重复 next 陷阱**：在同一个中间件或路由里多次调用 next、或既调用 next 又响应，会导致响应被写两次，触发 ERR_HTTP_HEADERS_SENT 错误。

- 触发场景：if/else 两个分支都调用了 next，或一个分支 next 另一个分支 res.send。
- 后果：第二次写头时头已发出，抛出头已发送错误，连接异常关闭。
- 防护：确保每条路径只走一次 next 或响应，并在分支后及时 return。

```js
const express = require("express");
const app = express();

app.get("/demo", (req, res, next) => {
  if (req.query.ok) {
    res.send("ok"); // 已响应
    return; // 必须 return，否则会继续到下方 next
  }
  next();
});

app.listen(3000);
```

> ERR_HTTP_HEADERS_SENT 与第 17 篇裸 http 的成因一致：响应已出口又想再写。把出口收口到唯一分支并早 return，是消除该错误的最稳写法。

**速记**：重复 next = 只出口一次、早 return。



#### 中间件顺序错误导致 req.body 未解析

**解析顺序坑**：把读取 req.body 的路由写在 express.json 之前，req.body 为 undefined，因为请求体还没被解析就进入了处理逻辑。

- 根因：express.json 是中间件，必须先注册、先执行才能往 req.body 填值。
- 表现：路由里 req.body 是 undefined，JSON 接口拿不到入参。
- 解法：所有依赖 req.body 的路由之前，务必先 app.use(express.json())。

```js
const express = require("express");
const app = express();

// 错误顺序：路由先注册，express.json 还没跑，req.body 为 undefined
// app.post("/login", (req, res) => res.send(req.body));

app.use(express.json()); // 正确：先解析
app.post("/login", (req, res) => res.send(req.body));

app.listen(3000);
```

> 该坑的本质是顺序即依赖：任何中间件都在它之后的代码中可见其副作用。凡是依赖某中间件产出的属性（req.body、req.user 等），都要确认它已先行注册。

**速记**：顺序错 = req.body 变 undefined。

> [!IMPORTANT]
> **重要内容**：Express 的两条铁律是顺序即执行序与错误靠四参中间件收口。注册时把全局预处理放前、404 与错误处理放后；写异步逻辑时务必把异常转交 next(err)，否则链路既不可控也不安全。
