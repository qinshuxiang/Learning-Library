## CPU 火焰图与 clinic 实测

### 火焰图

#### 读懂火焰图的三个规则

**火焰图（Flame Graph）**：CPU 采样的可视化——横轴是采样时间内各函数占用的比例，纵轴是调用栈深度，宽就是贵。

- **横轴宽度＝CPU 时间占比**：越宽的块占用 CPU 越多，优化从最宽的「平顶」入手；平顶（自身耗时高、不再下钻）即热点函数。
- **纵轴是调用栈**：上面的函数由下面的函数调用，不是时间顺序——火焰图回答「CPU 花在哪」，不回答「什么时候花的」。
- **颜色无性能含义**：随机着色只为区分模块，别从红黄绿里读出任何性能信号。

```bash
# 0x：一条命令生成可交互火焰图（推荐起点）
npx 0x app.js

# 标准链路：V8 采样 → 转换
node --prof app.js
node --prof-process isolate*.log > processed.txt   # 文本摘要，找 [Summary] 与 [Bottom up]
```

> 火焰图定位的是 **CPU 密集**问题：正则回溯（第 10 篇 ReDoS）、大 JSON 序列化、同步加密、图片处理。如果你的症状是「延迟高但 CPU 空闲」，火焰图帮不了你——那是事件循环阻塞或 IO 等待，回到第 36 章的维度判断。

**速记**：**宽就是贵、平顶即热点**，火焰图只管 CPU 密集型问题。



### clinic 实测

#### clinic doctor：先诊断类别

**clinic** 套件：自动对目标服务施压并采集指标，生成可视化诊断报告——`doctor` 回答「病在哪一类」，`flame` 回答「具体哪行代码」。

```bash
npm install -g clinic autocannon

# doctor：压测同时采集 CPU、内存、事件循环、GC，给出诊断结论
clinic doctor -- node app.js
# 另开终端施压（或 clinic 自带 autocannon）
autocannon -c 50 -d 30 http://localhost:3000/api/list
# 结束后自动打开诊断报告页面
```

- doctor 报告的核心判据：**事件循环延迟曲线与 CPU 曲线是否同步攀升**——同步升为 CPU 密集（转 `clinic flame`），CPU 平稳但延迟升为 IO 瓶颈或下游依赖（转链路排查），内存阶梯上升转第 37 章。
- 压测参数要贴近真实：并发数、payload 大小、接口 mix 都按生产流量比例配，否则「诊断」的是编造出来的瓶颈。
- 每次只改一个变量再复测：优化前留基线报告，改动后对比，**没有前后对比的性能工作都是感觉**。

> clinic 的价值是**把「猜测」变成「分流」**：新手性能调优最大的时间黑洞是在错误类别里找原因（CPU 密集的病去调连接池）。doctor 花三十秒给出的类别判断，决定接下来一小时用哪套工具。

**速记**：doctor **定类别**、flame **定代码**，贴近真实流量、留基线对比。



#### CPU 密集问题的两种出路

**定位到热点函数之后**，解法按场景二选一：优化算法或移出主线程。

- **算法层**：正则回溯换更优写法、大循环换批处理、序列化换更轻的格式——多数 CPU 问题的最优解仍在这一层，先看热点函数有没有「傻办法改聪明办法」的空间。
- **移出事件循环**：无法优化的大计算（图片压缩、加解密、报表计算）用 `worker_threads` 或子进程隔离（第 15 篇），主线程只做调度——代价是通信与序列化成本，小任务不值得。
- 任务队列模式：计算任务投给常驻 worker 池，主线程回 `Promise`，是「请求内大计算」的标准形态。

> 判断要不要拆 worker 的标准很简单：**单个任务超过几十毫秒就值得移出**——一次 200 毫秒的同步计算意味着这段时间内所有并发请求的事件循环都在排队。第 8 篇的事件循环原理在这里变成容量问题。

**速记**：先优化算法，**大计算拆 worker**，几十毫秒是拆分线。
