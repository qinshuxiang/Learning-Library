## path 路径模块

### 为什么需要 path 模块

#### 跨平台路径分隔符不同

**路径分隔符**：是操作系统中用于**分隔路径中目录层级的字符**，不同平台使用的字符并不相同，Node 在运行时按所在平台决定它的值。

- Windows 使用反斜杠作为分隔符，例如 C 盘下形如 C 盘下目录层级用反斜杠连接。
- POSIX 系统（Linux、macOS 等）使用斜杠作为分隔符，例如根目录下各层用斜杠连接。
- 路径定界符也随平台变化：Windows 用分号分隔多条路径，POSIX 用冒号分隔。
- 若代码写死某一平台的字符，换到另一平台就会拼接出错甚至路径非法。

```js
// Windows 上正确的分隔写法
const winStyle = "C:\\Users\\why\\project\\app.js";
// POSIX 上正确的分隔写法
const posixStyle = "/home/why/project/app.js";
// 二者字符不一致，写死其一将无法跨平台
console.log(winStyle);
console.log(posixStyle);
```

> 切勿凭印象硬编码分隔符。同一个逻辑路径，在 Windows 与 POSIX 下字符串形态不同；靠肉眼拼字符串既易错又难维护，这正是 path 模块存在的首要理由。

**速记**：Windows **反斜杠**、POSIX **斜杠**，平台不同分隔符不同。



#### 硬编码分隔符的隐患

**硬编码隐患**：指**在源码里直接写死分隔符字符或定界符字符**的做法，它会让路径在跨平台、跨环境时拼接失败或产生歧义。

- 在 Windows 上用斜杠虽多数 API 可容忍，但并非所有场景都兼容，属于脆弱写法。
- 在 POSIX 上用反斜杠会被当作普通文件名字符，导致路径层级错乱。
- 拼接用户输入时，手动补分隔符极易出现双斜杠、缺斜杠、相对段越界等问题。
- 定界符写死分号或冒号，会破坏多路径字符串（如 PATH 类变量）的解析。

```js
// 危险：写死斜杠，在 Windows 上行为不可靠
const badPath = "uploads" + "/" + userName + "/" + "avatar.png";
// 推荐：交给 path.join 处理分隔符
const path = require("path");
const goodPath = path.join("uploads", userName, "avatar.png");
console.log(goodPath);
```

> 手写分隔符最大的坑是"本地能跑、部署就崩"：开发在 macOS 用斜杠看似正常，上线到 Windows 容器立刻路径错误。把分隔符交给 path 模块，是消除这类不确定性的根本手段。

**速记**：硬编码分隔符 **本地行、跨台崩**。



#### path 是无需安装的内置模块

**内置模块**：path 是 Node.js **随运行时一同发布的核心模块**，不需要 npm 安装，通过 require 引入即可在所有平台使用。

- 它不属于第三方包，也不依赖 node_modules，任何 Node 程序都能直接引用。
- 引入写法为 const path = require("path")，之后即可调用其全部方法。
- 内部实现已针对不同平台做适配，调用方无需关心分隔符差异。
- 与 fs、process 等同属运行时预置能力，是处理文件路径的标准入口。

```js
const path = require("path");
console.log(typeof path);        // object
console.log(typeof path.join);   // function
console.log(path.sep);           // 当前平台的分隔符
```

> [!NOTE]
> **提醒内容**：path 只做**纯字符串层面的路径运算**，不读取磁盘、不校验文件是否存在。它能返回"形式上正确"的路径，但是否真实可达，需要 fs 等模块另行确认。

**速记**：path **内置直引，跨台通用**。



### 平台相关属性与常量

#### path.sep 平台路径分隔符

**path.sep**：是当前运行平台的**路径片段分隔符字符串**，由 Node 在启动时按操作系统设定，读取它即可得到正确的分隔字符。

- 完整形态为只读字符串属性 path.sep，无需调用、直接取用。
- Windows 上其值为反斜杠，POSIX 上其值为斜杠。
- 不应自己拼 sep，而应与 path.join 配合；直接读取 sep 主要用于打印、拼接提示语或日志展示。
- 它随"运行平台"而定，与代码写在哪个文件无关。

```js
const path = require("path");
console.log(path.sep); // Windows 输出 \ ，POSIX 输出 /

const parts = ["a", "b", "c"];
const manual = parts.join(path.sep); // 用 sep 手工连接（仅展示，实际请用 join）
console.log(manual);
```

> 读取 sep 后**手工 join 并不等价于 path.join**：它不会消解 . 与 ..，也不会折叠多余分隔符。sep 适合"展示或构造特殊字符串"，真正的路径拼接仍应交给 join 或 resolve。

**速记**：path.sep **当前平台分隔符，只读**。



#### path.delimiter 平台路径定界符

**path.delimiter**：是当前平台用于**分隔多条路径的定界符**，常用于解析或拼装 PATH 这类"多目录并列"的环境变量值。

- 完整形态为只读字符串属性 path.delimiter，直接读取。
- Windows 上其值为分号，POSIX 上其值为冒号。
- 常见用途是把 PATH 字符串按定界符拆成数组，或把多个目录拼回一个定界串。
- 与 sep 不同，它分隔的是"并列的整条路径"，而非"一条路径内部的层级"。

```js
const path = require("path");
const envPaths = process.env.PATH.split(path.delimiter);
console.log(envPaths.length); // PATH 中包含的目录数量

const rebuilt = ["/usr/bin", "/usr/local/bin"].join(path.delimiter);
console.log(rebuilt); // POSIX 下为 /usr/bin:/usr/local/bin
```

> 处理 PATH 等环境变量时务必用 delimiter 而非硬编码分号或冒号，否则在另一平台会拆错。它与 sep 的层级不同：sep 管"一条路径内的斜杠"，delimiter 管"多条路径间的间隔"。

**速记**：delimiter **分隔多条路径，平台定**。



#### path.win32 与 path.posix 模拟另一平台

**平台子模块**：path.win32 与 path.posix 是 **path 下挂载的两套固定实现**，让你在任意平台上按指定平台的规则处理路径，而不受当前运行平台影响。

- path.win32 下的所有方法都按 Windows 规则运算（分隔符为反斜杠）。
- path.posix 下的所有方法都按 POSIX 规则运算（分隔符为斜杠）。
- 直接调用 path.join 等方法，等价于调用"当前平台对应子模块"的同名方法。
- 用途：生成跨平台配置、编写需要在另一平台也能正确解析的路径逻辑（如打包工具、脚手架）。

```js
const path = require("path");

console.log(path.win32.join("a", "b", "c")); // a\b\c
console.log(path.posix.join("a", "b", "c"));  // a/b/c

console.log(path.win32.resolve("C:\\a", "b")); // C:\a\b
console.log(path.posix.resolve("/a", "b"));     // /a/b
```

> 默认 path 的行为跟随"运行平台"；如果你想在 macOS 上生成一段 Windows 风格路径，必须显式用 path.win32，否则 path.join 仍按 POSIX 出斜杠。两者不会读取磁盘，纯按规则做字符串运算。

**速记**：win32/posix **强制指定平台规则**。



### 路径拼接 join 与解析 resolve

#### path.join 拼接并规范化

**path.join**：是把**多个路径片段**按平台分隔符连接成一个字符串，并在连接过程中自动规范化多余分隔符与 . 和 ..，返回的是拼接后的路径（字符串）。

- 完整写法为 path.join(片段1, 片段2, 若干片段)，参数数量不定，逐个按顺序拼接。
- 空字符串片段会被忽略，不影响结果；相邻片段间的多余分隔符会被折叠成单个。
- 自动处理 .（当前目录）与 ..（上级目录），但 .. 不会越出路径最左边界。
- 返回的结果可能仍是相对路径；只有当某片段本身就是绝对路径时，结果才以绝对路径呈现。

```js
const path = require("path");

console.log(path.join("/a", "b", "c"));        // /a/b/c
console.log(path.join("/a", "/b/", "c"));       // /a/b/c（多余斜杠被折叠）
console.log(path.join("/a", "b", "..", "c"));   // /a/c（.. 被消解）
console.log(path.join("a", ".", "b"));          // a/b
console.log(path.join(""));                     // .（空结果返回点号表示当前目录）
```

> join 只做**字符串层面的拼接与规范化**，不查询文件系统、也不基于当前工作目录补全绝对路径。与直接用加号拼接字符串相比，join 自动插入正确分隔符并处理 . 和 ..，避免了手写分隔符在跨平台时出错。

**速记**：join **只拼接规范化，不补绝对路径**。



#### path.resolve 拼成绝对路径

**path.resolve**：把**从右往左的若干路径片段**依次解析、拼成一条绝对路径，只要遇到绝对片段就以其为基准继续向左合并，最终得到从盘符或根开始的完整路径。

- 完整写法为 path.resolve(片段1, 片段2, 若干片段)，从最右片段向左逐个处理。
- 一旦某片段本身是绝对路径，它就成为已解析部分的起点，其左侧片段只被拼到前面、不再参与"补全"。
- 若所有片段拼完仍未得到绝对路径，则以 **process.cwd() 返回的当前工作目录**为最左基准补足（与第 9 篇的 process.cwd 衔接）。
- 不传任何参数时，resolve 直接返回当前工作目录，等价于 process.cwd()。

```js
const path = require("path");

console.log(path.resolve("/a", "b", "c"));      // /a/b/c
console.log(path.resolve("/a", "/b", "c"));      // /b/c（遇到绝对 /b 以它为准）
console.log(path.resolve("a", "b"));             // /当前工作目录/a/b（补 cwd）
console.log(path.resolve());                     // /当前工作目录（同 process.cwd）
```

> resolve 与 cwd 强相关：它的"绝对路径基准"来自进程启动目录而非脚本目录。因此 resolve("data") 在不同启动位置会指向不同磁盘位置，这与 __dirname 的行为不同（详见本篇后段模块变量）。

**速记**：resolve **从右向左拼到绝对，否则补 cwd**。



#### join 与 resolve 的核心差异

**二者差异**：**path.join 只连接并规范化、可返回相对路径**，而 **path.resolve 必然产出绝对路径、并以 cwd 兜底**。这是选用时最关键的分野。

- **结果性质**：join 可返回相对路径；resolve 永远返回绝对路径。
- **基准不同**：join 完全依据传入片段；resolve 在不足绝对时引入 cwd。
- **.. 处理**：两者都消解 ..，但 resolve 因基于绝对基准，.. 不会越出根；join 受片段相对性约束。
- **典型用途**：构造"脚本相关"路径用 join 配合 __dirname；构造"运行相关"绝对路径用 resolve。

```js
const path = require("path");

console.log(path.join("a", "b"));     // a/b（相对）
console.log(path.resolve("a", "b"));  // /当前工作目录/a/b（绝对）
console.log(path.join("/a", ".."));   // /（相对片段被消）
console.log(path.resolve("/a", "..")); // /（绝对基准，不越根）
```

> 一句话对照：join 像"把几段绳子接起来"，resolve 像"从终点往回走直到踩到地面（绝对路径）"。凡需要确定磁盘位置，优先 resolve；凡需要相对片段组合，优先 join。

**速记**：join **给相对拼接**，resolve **给绝对落地**。



### 路径规范化 normalize 与字段拆解

#### path.normalize 规范化

**path.normalize**：是把**一条路径字符串**中的 .、.. 与重复分隔符按规则折叠整理，返回等价但更简洁的路径，且整个过程不触及文件系统。

- 完整写法为 path.normalize(路径字符串)，接收一个待整理的路径并返回字符串。
- 它会消解 .（当前目录）与 ..（上级目录），并合并相邻的多余分隔符为单个。
- 保留尾部斜杠：若输入以分隔符结尾，输出也会保留结尾分隔符，表示这是一个目录。
- 纯字符串运算：normalize 不查询磁盘、不判断路径是否真实存在，只做字符层面的规整。

```js
const path = require("path");

console.log(path.normalize("/a/b/./c"));        // /a/b/c
console.log(path.normalize("/a/b/../c"));       // /a/c
console.log(path.normalize("/a//b///c"));        // /a/b/c（重复斜杠合并）
console.log(path.normalize("/a/b/"));           // /a/b/（尾部斜杠保留）
```

> normalize 不会越过根目录：在 POSIX 上对 /../a 处理成 /a，在 Windows 上盘符之后的 .. 也不会跳出盘符。它不改变"路径指向哪里"，只让字符串形式更规范。

**速记**：normalize **纯字符串规整，留尾斜杠**。



#### path.basename 取文件名

**path.basename**：是从**一条路径里取出最后一段（文件或目录名）**，可选地去掉指定扩展名，返回该段字符串。

- 完整写法为 path.basename(路径, 可选扩展名)，第二个参数若提供，会从结果末尾剔除与之匹配的扩展。
- 只认"最后一段"：以分隔符切分后取末尾部分，不关心前面目录层级。
- 第二参数要与末尾扩展完全一致才会被去掉；它按字面匹配，不做模式推断。
- 返回的是名称本身，不含前面目录；若路径以分隔符结尾，则取倒数第二段。

```js
const path = require("path");

console.log(path.basename("/a/b/c.txt"));        // c.txt
console.log(path.basename("/a/b/c.txt", ".txt")); // c
console.log(path.basename("/a/b/c.txt", "txt"));  // c.txt（不匹配，因缺点号）
console.log(path.basename("/a/b/"));             // b（结尾斜杠被忽略）
```

> 扩展名参数必须带点号且完全匹配末尾，否则不会剔除（上例传 txt 而非 .txt 就残留）。basename 与 extname 配合可分别拿到"名"和"扩展"，但想同时拿更推荐用 parse。

**速记**：basename **取末段，可去扩展**。



#### path.dirname 取目录

**path.dirname**：是从**一条路径里取出除最后一段之外的目录部分**，返回其父目录字符串。

- 完整写法为 path.dirname(路径)，接收一个路径并返回其所在目录。
- 它是 basename 的补集：路径等于 dirname 加分隔符加 basename。
- 若路径只有一段（无分隔符），返回点号表示当前目录。
- 同样不查询磁盘，只按字符串切分最后一段之前的内容。

```js
const path = require("path");

console.log(path.dirname("/a/b/c.txt"));  // /a/b
console.log(path.dirname("/a/b"));        // /a
console.log(path.dirname("c.txt"));       // .（无目录时返回当前目录）
console.log(path.dirname("/"));           // /（根的上层仍是根）
```

> dirname 与 basename 互为补充：path.join(path.dirname(p), path.basename(p)) 在多数情况下还原为 p（尾斜杠等边界略有差异）。需要"换文件名保目录"时，先 dirname 取目录再 join 新名最稳妥。

**速记**：dirname **取父目录，basename 之补**。



#### path.extname 取扩展名

**path.extname**：是从**一条路径的最后一段里取出扩展名**，返回包含点号的扩展字符串；若无扩展名则返回空字符串。

- 完整写法为 path.extname(路径)，返回从最后一个点号到末尾的子串（含点）。
- 只认"最后一段里的最后一个点"：多点文件如 index.coffee.md 取 .md。
- 以点开头且无后续点号的隐藏文件（如 .gitignore）视为"无扩展名"，返回空字符串。
- 若最后一段以点号结尾（如 file.），也返回空字符串，因为其后没有扩展内容。

```js
const path = require("path");

console.log(path.extname("index.html"));     // .html
console.log(path.extname("archive.tar.gz")); // .gz（只取最后一个点）
console.log(path.extname(".gitignore"));     // （空串，隐藏文件无扩展）
console.log(path.extname("Makefile"));       // （空串，无点号）
console.log(path.extname("file."));          // （空串，点后无内容）
```

> 判断"是否某类文件"不要只比对 extname 是否包含某串，而应精确比较整段（如 === ".json"）。隐藏文件以点开头但 extname 为空，这一点常被忽视，处理配置文件名时要特别留意。

**速记**：extname **取最后一点之后，含点**。



### 路径对象 parse 与反向构造 format

#### path.parse 拆成五个字段

**path.parse**：是把**一条路径字符串**拆解为包含五个字段的对象，便于分别读取根、目录、全名、扩展与纯名，返回的对象字段固定为 root、dir、base、ext、name。

- 完整写法为 path.parse(路径)，返回一个普通对象而非路径字符串。
- **root**（根）：路径最顶层的根部分，POSIX 为斜杠，Windows 为盘符加冒号加反斜杠。
- **dir**（目录）：除最后一段外的完整目录，等于 dirname 的结果。
- **base**（基本名）：最后一段全名，等于 basename 的结果，含扩展。
- **ext**（扩展名）：最后一段的扩展，含点，等于 extname 的结果。
- **name**（纯名）：base 去掉 ext 后的部分，即不含扩展的文件名。

```js
const path = require("path");

const info = path.parse("/home/why/project/app.js");
console.log(info.root);  // /
console.log(info.dir);   // /home/why/project
console.log(info.base);  // app.js
console.log(info.ext);   // .js
console.log(info.name);  // app
```

> 五个字段满足恒等式 dir 加 base 还原原路径（边界忽略尾斜杠），且 base 等于 name 拼接 ext。parse 一次拿到全部成分，比反复调用 basename/dirname/extname 更高效、更清晰。

**速记**：parse **五字段：root/dir/base/ext/name**。



#### path.format 逆向构造

**path.format**：是 **path.parse 的逆操作**，把一个含路径字段的对象重新拼回路径字符串；你提供哪些字段，它就按规则组合成路径。

- 完整写法为 path.format(路径对象)，接收一个含 root、dir、base、ext、name 中部分字段的对象。
- 它不接收字符串，只接收对象；与 parse 形成"拆—合"闭环。
- 当提供 base 时，base 已包含 name 与 ext 的信息，format 直接用它。
- 当未提供 base 但提供 name 与 ext 时，format 把二者拼成 base 再组合。

```js
const path = require("path");

// 用 base 整体提供
const fromBase = path.format({
  root: "/",
  dir: "/home/why/project",
  base: "app.js"
});
console.log(fromBase); // /home/why/project/app.js

// 用 name + ext 提供
const fromParts = path.format({
  dir: "/home/why/project",
  name: "app",
  ext: ".js"
});
console.log(fromParts); // /home/why/project/app.js
```

> format 与 parse 互为逆：对 parse 的结果直接 format，通常能得到等价路径（尾斜杠等边界可能微差）。修改路径时常见做法是先 parse 改字段，再 format 回去，避免手工拼错分隔符。

**速记**：format **parse 逆操作，对象拼回串**。



#### format 的属性优先级

**属性优先级**：在 path.format 中，若同时提供相互冲突的字段，**base 优先于 name 与 ext**，dir 优先于 root；这是组合对象时必须遵守的覆盖规则。

- **base 优先**：一旦给了 base，name 与 ext 即便也提供也会被忽略，不会拼到结果里。
- **dir 优先**：给了 dir 时，root 会被忽略，目录以 dir 为准。
- 若既无 base 也无 name，则无法构造出文件名部分，结果取决于 dir 与 root。
- 该优先级避免了"字段互相打架"，让 format 的输出唯一可预测。

```js
const path = require("path");

// base 覆盖 name 与 ext
const r = path.format({
  dir: "/a",
  base: "real.txt",
  name: "ignored",   // 被忽略
  ext: ".md"         // 被忽略
});
console.log(r); // /a/real.txt
```

> 写 format 入参时只给"一套"文件名信息：要么给 base，要么给 name 加 ext，不要两者都给，否则后者静默失效、易让人误以为会拼接。牢记 base 优先，就能预判输出。

**速记**：format **base 压 name/ext，dir 压 root**。



### 相对路径、绝对路径校验与模块变量

#### path.relative 计算相对路径

**path.relative**：是计算**从起始路径 from 到目标路径 to 的相对路径字符串**，让 to 可基于 from 用最少的上层与下层跳转表达。

- 完整写法为 path.relative(起始路径 from, 目标路径 to)，返回相对路径字符串。
- 它会先对 from 与 to 各自调用 resolve，再基于绝对结果求差，因此传入相对路径也会被自动补全。
- 若 from 与 to 解析后完全相同，返回空字符串（表示"就在当前位置"）。
- 返回的可能是 .. 段（需向上）与子目录段（需向下）的组合。

```js
const path = require("path");

console.log(path.relative("/a/b/c", "/a/b/d"));   // ../d
console.log(path.relative("/a/b", "/a/b/c/d"));   // c/d
console.log(path.relative("/a/b/c", "/a/b/c"));   // （空字符串，同路径）
console.log(path.relative("x/y", "x/z"));         // 基于 cwd 解析后再求差
```

> relative 自动 resolve 的特性意味着它受 cwd 影响：传入相对片段时，求差基准是"当前工作目录下的绝对位置"。要得到稳定结果，应传入绝对路径或配合 __dirname 先 resolve。

**速记**：relative **from 到 to 的相对跳法**。



#### path.isAbsolute 只看形式

**path.isAbsolute**：是判断**一条路径字符串在形式上是否为绝对路径**，返回布尔值；它只看字符串形态，不查询文件系统、不判断路径是否真实存在。

- 完整写法为 path.isAbsolute(路径)，返回 true 或 false。
- POSIX 下以斜杠开头即为绝对；Windows 下以盘符加冒号加反斜杠开头（或 UNC 形式）为绝对。
- 它不补全、不解析，因此 isAbsolute("a/b") 为 false，isAbsolute("/a/b") 为 true。
- 与 resolve 配合：resolve 一定产出绝对路径，isAbsolute 则用来"预判"某片段是否已是绝对。

```js
const path = require("path");

console.log(path.isAbsolute("/a/b"));   // true（POSIX 绝对）
console.log(path.isAbsolute("a/b"));    // false（相对）
console.log(path.isAbsolute("C:\\a"));  // true（Windows 绝对）
console.log(path.isAbsolute("./a"));    // false（相对）
```

> isAbsolute 只认"写法"不认"存在"：isAbsolute("/不存在的目录") 仍为 true。它常用来在拼接前判断用户给的片段是否已是绝对路径，从而决定要不要再补基准目录。

**速记**：isAbsolute **只判形式，不查磁盘**。



#### __dirname 与 __filename 模块变量

**模块变量**：__dirname 与 __filename 是 **CommonJS 模块中自动可用的两个路径变量**，分别表示"当前文件所在目录"与"当前文件的绝对路径"，二者都由模块系统注入。

- **__dirname**：是当前执行脚本所在的**目录绝对路径**（不含末尾文件名），字符串类型。
- **__filename**：是当前执行脚本的**完整绝对路径**（含文件名），字符串类型。
- 二者仅在 CommonJS（require 体系）中可用，由模块包装器在加载时注入。
- 它们取决于"脚本文件位置"，与进程启动目录 cwd 无关，因此比 resolve 更适合定位同伴资源。

```js
// 在 /home/why/project/app.js 中运行
console.log(__dirname);   // /home/why/project
console.log(__filename);  // /home/why/project/app.js

const path = require("path");
const configPath = path.join(__dirname, "config", "db.json");
console.log(configPath);  // /home/why/project/config/db.json
```

> 第 9 篇强调过：读取"相对于脚本"的资源要用 __dirname 而非 process.cwd，因为 cwd 随启动位置变化、__dirname 随文件固定。把脚本和资源放在一起时，join(__dirname, ...) 是定位同伴文件的标准写法。

**速记**：__dirname **所在目录**，__filename **文件全路径**。



#### ES Module 中的替代写法

**ESM 替代**：在 **ES Module（import 体系）中，__dirname 与 __filename 不存在**，需改用 import.meta.url 配合 fileURLToPath 推算出等价的目录与文件路径。

- import.meta.url 是当前模块的**文件 URL 字符串**（形如 file 冒号双斜杠绝对路径），在 ESM 中可用。
- 用 url 模块的 fileURLToPath(import.meta.url) 把该 URL 转成普通路径字符串，等价于 __filename。
- 再用 path.dirname 处理上一步结果，即可得到等价于 __dirname 的目录路径。
- 需从 url 与 path 两个模块分别引入对应函数。

```js
import { fileURLToPath } from "url";
import path from "path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

console.log(__filename); // 等价旧 __filename 的绝对路径
console.log(__dirname);  // 等价旧 __dirname 的目录路径
```

> [!CAUTION]
> **注意内容**：在 ESM 文件里直接写 __dirname 会报"未定义"错误，因为模块系统不再注入这两个变量。务必改用 import.meta.url 加 fileURLToPath，不要因为"旧代码能跑"就照搬到 .mjs 或 type 为 module 的项目中。

**速记**：ESM 用 **import.meta.url 配 fileURLToPath**。



#### 常见陷阱

**路径陷阱**：实际项目中路径错误多来自**拼接用户输入导致穿越、把网络 URL 误当文件路径处理、以及混淆 cwd 与脚本目录**三类，需逐一规避。

- **路径穿越**：把用户传入的文件名直接 join 进基准目录，用户可用 .. 逃出目标目录读到敏感文件。
- **URL 误用路径**：网络地址（如 https 冒号双斜杠...）应使用 URL 类处理，而非 path 模块，二者职责不同。
- **cwd 错位**：用 resolve 或相对写法定位资源却依赖启动目录，换目录启动即失效。
- **扩展名误判**：凭 extname 含某子串判断类型，忽略隐藏文件与多点文件的行为。

```js
const path = require("path");

// 危险：用户可控片段引发穿越
const userInput = "../secret/password.txt";
const dangerous = path.join("/var/www/uploads", userInput);
console.log(dangerous); // /var/www/secret/password.txt（逃出了 uploads）

// 安全：限定结果必须仍在基准目录内
function safeJoin(baseDir, child) {
  const target = path.resolve(baseDir, child);
  if (!target.startsWith(path.resolve(baseDir))) {
    throw new Error("非法的路径穿越");
  }
  return target;
}
```

> [!WARNING]
> **警告内容**：拼接**用户提供的路径片段**前必须校验结果未逃出允许目录，否则攻击者可借 .. 读取或写入任意文件（路径穿越漏洞）。对网络 URL 请改用 URL 类，path 只负责本机文件系统路径，不要混用。

```js
const { URL } = require("url");

// 网络地址用 URL 而非 path
const webUrl = new URL("https://example.com/a/b?x=1");
console.log(webUrl.hostname); // example.com
console.log(webUrl.pathname); // /a/b
// 错误示范：path.join 会把 https 当成普通目录名
console.log(path.join("https://example.com", "a")); // 产生无意义字符串
```

> 把"本地文件路径"与"网络 URL"分开对待：前者用 path 模块，后者用 URL 类。path 的所有方法都假设输入是文件系统路径，对含协议、查询串的 URL 处理会得到错误结果。

**速记**：陷阱三连 **穿越、URL 误用、cwd 错位**。
