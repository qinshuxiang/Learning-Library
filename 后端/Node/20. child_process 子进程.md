## child_process 子进程

### 为什么需要子进程

#### 单线程无法利用多核且 CPU 密集会阻塞事件循环

**单线程瓶颈**：是 Node 主线程被长时间同步计算占满、导致所有异步回调无法执行的现象，其根源在于第 8 篇所述的单线程事件驱动模型。

- 主线程同一时刻只跑一段 JavaScript，多核 CPU 的其余核心在纯 JS 计算时处于空闲。
- CPU 密集任务（大循环、加密、图像压缩）占满主线程，定时器、IO 回调、请求响应全部停顿。
- 事件循环被卡住，表现为接口无响应、延迟飙升，甚至被健康检查判定为掉线。

> 第 8 篇与第 15 篇已说明：单线程不等于只能串行，但"重计算占满单线程"是真实瓶颈。把重活移出主线程，子进程是其中隔离最彻底的一种手段。

**速记**：单线程**算满即卡死**，多核**空转浪费**。



#### 需要调用外部命令或复用已有可执行程序

**外部命令调用**：指 Node 程序借助子进程去运行操作系统命令、脚本或第三方可执行文件，而非用 JavaScript 重新实现一遍。

- 复用成熟工具：调用 ffmpeg 转码、git 操作、imagemagick 处理图片，比自写逻辑更稳更快。
- 隔离风险操作：把不可信或易崩的环节放进独立进程，崩掉的是子进程而非整个服务。
- 利用多语言生态：把 Python、Go 写的程序作为子进程调用，补齐 Node 的短板。

> 并非所有外部能力都要用子进程：文件、网络、加密等已有原生异步 API 的，优先用它们（自动进 libuv 线程池），仅在确需调用外部程序时才起子进程。

**速记**：外部命令**复用现成程序**，隔离**崩子不崩主**。



#### 子进程是重量级并发单位且拥有独立内存空间

**子进程（child process）**：是操作系统 fork 出的独立进程，拥有自己的内存空间、事件循环与 V8 实例，与父进程通过操作系统机制通信。

- 重量级：每个子进程独立分配内存与运行时，启动与上下文切换开销大于线程。
- 强隔离：子进程的崩溃、内存泄漏不会直接拖垮父进程，适合跑不可信或易崩代码。
- 数据共享成本高：父子之间不共享内存，只能通过消息或文件等显式方式传递数据。

> 与 worker_threads 对照：工作线程共享同一进程内存、开销小，但隔离弱；子进程隔离强、开销大。选型在后续章节展开。

**速记**：子进程**独立内存、强隔离、开销大**。



### 四个创建方法 spawn、exec、execFile、fork 的定位对比

#### 四个方法 spawn、exec、execFile、fork 的职责定位

**四种创建方式**：child_process 模块提供 spawn、exec、execFile、fork 四个入口，分别面向流式、缓冲、无 shell、纯 Node 四类需求。

- **spawn**：最底层、最通用的方式，返回 ChildProcess 且子进程的标准流以流对象暴露，适合长时间运行与大量输出。
- **exec**：在 shell 中执行命令并缓冲全部输出到回调，适合短命令，默认有 1MB 缓冲上限。
- **execFile**：直接执行可执行文件而不经 shell，更安全，适合运行已知程序。
- **fork**：专用于运行 Node 脚本，自动建立父子间 IPC 通道，是进程间通信的便捷封装。

> 四者底层都基于 spawn 实现：exec、execFile 内部调用 spawn，fork 在 spawn 之上额外配置 IPC。理解 spawn 是理解其余三者的钥匙。

**速记**：spawn **最底层**，exec **走 shell 缓冲**，execFile **无 shell**，fork **专跑 Node**。



#### 按输出方式与是否经 shell 的对比

**选型维度**：四个方法的核心差异集中在"是否经 shell"与"如何交付输出"两点，据此可快速区分适用场景。

- **是否经 shell**：exec 经 shell（可写管道、通配符、分号串联），execFile 与 spawn、fork 不经 shell。
- **输出交付**：spawn 给流（按需读取），exec 与 execFile 给缓冲后的字符串（一次性回调返回）。
- **运行目标**：spawn、exec、execFile 可运行任意命令或程序，fork 只能运行 Node 脚本。
- **通信能力**：仅 fork 默认开通 IPC，其余需借助 stdio 配置才能实现消息传递。

> 经 shell 是把双刃剑：它带来便利（管道、通配），也带来命令注入风险。凡输入来自用户，优先 execFile 或 spawn 配数组参数，避开 shell。

**速记**：经 shell **便利但危险**，给流 **按需读**、给缓冲 **一次性**。



#### 如何根据场景选择创建方法

**选择准则**：先判断"要不要 shell、输出多大、跑不跑 Node、要不要通信"，再映射到具体方法。

- 长时间运行、输出大、需边读边处理：选 **spawn**（stdio 设 pipe）。
- 短命令、输出小、要拼 shell 特性：选 **exec**，但务必注意命令注入。
- 运行固定可执行文件、不接受用户输入拼接：选 **execFile**（最安全）。
- 派发计算或任务给另一个 Node 程序并来回通信：选 **fork**。

> 经验法则：**默认 spawn**，需要 shell 便利用 exec，需要安全执行程序用 execFile，需要 Node 间通信用 fork。不要因为 fork 简单就滥用到非 Node 场景。

**速记**：流用 **spawn**、shell 用 **exec**、安全用 **execFile**、Node 通信用 **fork**。



### spawn 详解：流式输出与长时间任务

#### spawn 的完整签名与参数

**spawn 方法**：是 child_process 中创建子进程的基础函数，签名为 spawn(command, args, options)，返回 ChildProcess 实例，子进程的标准输入输出以流形式暴露。

- **command**（字符串）：要执行的命令或可执行文件路径，不经 shell 解析。
- **args**（数组）：传给命令的参数列表，每个元素是单独一项，绝不做字符串拼接。
- **options**（对象）：可选，控制 cwd、env、stdio、shell、detached 等运行细节。

```js
const { spawn } = require("child_process");

const child = spawn("ls", ["-lh", "/usr"]);
// command 为 ls，args 为 ["-lh", "/usr"]，options 省略走默认
```

> spawn 的 command 若含空格或管道符号会被当作普通字符而非 shell 语法；需要 shell 特性时应显式设置 options.shell 为 true，或改用 exec。

**速记**：spawn(command, args, options) 给**流**不要 shell。



#### args 为数组与命令注入防范

**参数数组化**：spawn 要求把命令与参数分开，command 是程序名、args 是字符串数组，二者都不会被 shell 再度解释，可天然规避注入。

- 每个参数单独成数组元素，例如 spawn("ls", ["-l", "/usr"])，不要写成 spawn("ls -l /usr")。
- 用户输入只作为数组中的某一元素，无法借空格或分号逃逸成额外命令。
- 对比 exec：exec 把整条字符串交给 shell，用户拼接极易触发注入。

```js
const userDir = process.argv[2] || "/usr";
// 用户输入仅作为数组元素，无法注入额外命令
const child = spawn("ls", ["-lh", userDir]);
```

> [!WARNING]
> **警告内容**：切勿把用户输入与外部命令拼成一个字符串传给 shell。即便使用 spawn，也不要为图方便开启 options.shell 再拼用户输入——这会把数组化带来的安全优势一笔勾销。

**速记**：参数**走数组**，用户输入**仅作元素**。



#### stdio 选项 inherit、pipe、ignore

**stdio 配置**：是 options.stdio，决定子进程的三个标准流（输入、输出、错误）如何连接到父进程，常用值为 inherit、pipe、ignore。

- **inherit**：子进程直接使用父进程的标准流，输出直接打印到当前终端，不经由父进程代码。
- **pipe**（默认）：子进程的标准流以管道暴露为父进程可读取的流对象。
- **ignore**：丢弃子进程对应流，既不在终端显示也不供父进程读取。

```js
const { spawn } = require("child_process");

// 让子进程直接沿用父终端，常用于转发命令
spawn("ls", ["-lh"], { stdio: "inherit" });

// 默认 pipe，父进程可监听 stdout 读取输出
const child = spawn("ls", ["-lh"]);
child.stdout.on("data", (chunk) => console.log(chunk.toString()));
```

> stdio 还支持数组形式分别配置每一条流，例如 stdio: ["ignore", "inherit", "pipe"] 表示忽略输入、继承输出、管道化错误。简写字符串等价展开为三条同值配置。

**速记**：inherit **直连终端**，pipe **代码可读**，ignore **直接丢弃**。



#### 监听 data 与 close 事件、退出码与信号

**输出与退出事件**：spawn 的子进程在 pipe 模式下，父进程通过监听 stdout/stderr 的 data 事件读取输出，通过 close 与 exit 事件感知生命周期。

- **data 事件**：流每收到一段数据即触发，回调参数为 Buffer，需用 toString 转为字符串。
- **close 事件**：子进程的标准流全部关闭后触发，回调含退出码 code 与终止信号 signal。
- **exit 事件**：子进程结束时触发，同样给出 code 与 signal，但早于流关闭（区别见后续章节）。

```js
const { spawn } = require("child_process");

const child = spawn("ls", ["/nonexistent-path"]);

child.stdout.on("data", (chunk) => console.log("输出：" + chunk.toString()));
child.stderr.on("data", (chunk) => console.error("错误：" + chunk.toString()));

child.on("close", (code, signal) => {
  console.log("子进程结束，退出码：" + code + "，信号：" + signal);
});
```

> code 为退出码（0 成功、非 0 失败），signal 为终止信号（如 SIGTERM，正常退出时为 null）。判断成败应同时看二者：被信号杀死时 code 为 null 而 signal 非空。

**速记**：data **收输出**，close **流关即终**，code/signal **判成败**。



### exec 与 execFile 详解：缓冲输出与安全执行

#### exec 的回调三参数 error、stdout、stderr

**exec 方法**：在 shell 中执行命令，缓冲全部输出后通过回调一次性返回，签名为 exec(command, options, callback)，回调三参数为 error、stdout、stderr。

- **error**：执行出错时的 Error 对象，退出码非 0 或无法启动时为非空。
- **stdout**：子进程标准输出的完整字符串（受 maxBuffer 限制）。
- **stderr**：子进程标准错误的完整字符串。

```js
const { exec } = require("child_process");

exec("ls -lh /usr", (error, stdout, stderr) => {
  if (error) {
    console.error("命令失败，退出码：" + error.code);
    console.error(stderr);
    return;
  }
  console.log(stdout);
});
```

> 回调遵循错误优先约定：先判 error 再使用 stdout/stderr。命令正常完成但程序自身向 stderr 写日志时，error 仍可能为 null，需结合业务区分。

**速记**：exec 回调 **error、stdout、stderr** 三件套。



#### error 非空时 stdout 仍可能有内容

**部分输出陷阱**：exec 在子进程退出码非 0 时把 error 设为非空，但 stdout 往往已经收集到了部分正常输出，不可在判 error 后直接丢弃 stdout。

- 子进程可能先打印正确结果、再因后续步骤失败而非 0 退出，此时 stdout 有内容、error 非空。
- 仅以 error 是否存在判断"有无产出"会丢失已生成的数据，造成排查困难。
- 正确做法：先使用 stdout/stderr 中可用的信息，再据 error 决定流程走向。

```js
const { exec } = require("child_process");

exec("echo 前半段成功; exit 1", (error, stdout, stderr) => {
  console.log("已产出内容：" + stdout); // 仍可拿到 "前半段成功"
  if (error) console.error("但整体以非 0 退出：" + error.code);
});
```

> 这与 spawn 的流模型不同：spawn 的 data 事件天然分段，而 exec 把全部输出缓存后才回调，所以即便失败也"已经攒下了 stdout"。

**速记**：error 非空 **不代表无产出**，stdout **仍要读**。



#### maxBuffer 限制与超出报错

**缓冲上限**：exec 与 execFile 默认把子进程输出攒进内存，受 options.maxBuffer 约束，默认上限为 1MB，超出即报错并杀死子进程。

- 默认值：maxBuffer 默认约 1024 * 1024 字节（1MB），stdout 与 stderr 各自独立计数。
- 超出后果：触发 error，错误信息含 killed、signal、code 提示缓冲溢出，子进程被终止。
- 调整方式：增大 maxBuffer 可承接更大输出，但无限制放大有内存压力，输出很大时更应改用 spawn 流式读取。

```js
const { exec } = require("child_process");

// 输出可能超过 1MB 时显式放大缓冲
exec("cat huge.log", { maxBuffer: 10 * 1024 * 1024 }, (error, stdout) => {
  if (error) {
    console.error("执行结束但有错误：" + error.message);
    return;
  }
  console.log("读取字节数：" + stdout.length);
});
```

> 1MB 上限是"单条输出"的警戒线而非安全线。日志、dump 等动辄上百 MB 的场景，务必切到 spawn 的 pipe 流，边读边处理，避免内存暴涨。

**速记**：maxBuffer **默认 1MB**，超了**杀进程报错**。



#### shell 选项与命令注入风险

**shell 与注入**：exec 默认经 shell 执行整条命令字符串，若把用户输入拼进命令，攻击者可借空格、分号、管道注入任意指令，属于高危操作。

- 危险写法：exec("ls " + userInput) 中 userInput 若为 "; rm -rf /" 会执行额外命令。
- 安全替代：用 execFile 或 spawn 配参数数组，避开 shell 解析，从根本上杜绝注入。
- 必须拼 shell 时：对用户输入做严格白名单校验，绝不直接拼接，且开启 shell 仅用于可信场景。

```js
const { execFile } = require("child_process");

const userInput = process.argv[2];
// 不经 shell，userInput 仅作为 ls 的参数，无法逃逸成新命令
execFile("ls", ["-lh", userInput], (error, stdout) => {
  if (error) { console.error(error.message); return; }
  console.log(stdout);
});
```

> [!WARNING]
> **警告内容**：绝不用 exec 拼接用户输入。命令注入会让攻击者以你的进程权限执行任意系统命令，危害等同于交出服务器。运行已知程序优先选 execFile，运行系统命令并需参数时选 spawn 配数组。

**速记**：exec 拼用户输入 **等于开门揖盗**。



### fork、IPC 与父子通信实战

#### fork 只能运行 Node 脚本且自带 IPC

**fork 方法**：是 child_process 中专用于运行 Node 脚本的创建方式，签名为 fork(modulePath, args, options)，会在父子之间自动建立 IPC 通道，无需手动配置 stdio。

- **modulePath**（字符串）：要作为子进程运行的 Node 脚本路径，不能是任意 shell 命令。
- **自带 IPC**：相比 spawn，fork 默认开通进程间通信，子进程可通过 process 对象收发消息。
- **继承运行时**：子进程沿用父进程的 Node 可执行文件，等价于 spawn(process.execPath, [modulePath]) 再加 IPC 配置。

```js
const { fork } = require("child_process");

const child = fork("./worker.js");
// worker.js 是另一个 Node 脚本，已具备 IPC 通道
```

> fork 本质是在 spawn 之上封装了 IPC 的便捷入口。若想对非 Node 程序做 IPC，需自行用 spawn 配置 stdio 的 ipc 通道，复杂度更高。

**速记**：fork **只跑 Node 脚本**，自带 **IPC 通道**。



#### child.send 与 child.on("message") 父子通信

**父进程收发**：在父进程侧，通过子进程的 send 方法发送消息，通过监听子进程的 message 事件接收子进程回传的数据。

- **child.send(message)**：向子进程发送可序列化对象，消息会经 IPC 传给子进程。
- **child.on("message", handler)**：注册监听器，handler 收到子进程通过 process.send 发来的消息。
- **消息即对象**：发送的内容会被结构化克隆（JSON 风格），因此需是可序列化数据。

```js
const { fork } = require("child_process");

const child = fork("./worker.js");

child.on("message", (msg) => {
  console.log("父进程收到：" + JSON.stringify(msg));
  child.kill();
});

child.send({ type: "start", payload: 1000 });
```

> send 也可传第二个回调用于确认发送完成（仅部分场景需要）。父进程用 child.kill 或 child.disconnect 可主动结束通信与子进程。

**速记**：父侧 **send 发、on message 收**。



#### process.send 与 process.on("message") 子进程侧

**子进程收发**：在 fork 出的子进程脚本内，使用全局 process 对象的 send 方法回传消息，用 process.on("message") 接收父进程发来的消息。

- **process.send(message)**：子进程把结果发回父进程，是 process 对象在子进程中的 IPC 能力。
- **process.on("message", handler)**：监听父进程 send 过来的消息，handler 参数为消息对象。
- 子进程无需 require 任何模块即可使用 process，因为 process 是第 9 篇所述的全局对象。

```js
process.on("message", (task) => {
  if (task.type === "start") {
    const result = computeInChild(task.payload);
    process.send({ type: "done", value: result });
  }
});

function computeInChild(n) {
  let sum = 0;
  for (let i = 0; i < n; i++) sum += i;
  return sum;
}
```

> 子进程侧的 process.send 与父进程侧的 child.send 是对应的两端；只要一端 send，另一端注册的 message 监听器就会被触发，构成双向通道。

**速记**：子侧 **process.send 回、process.on 收**。



#### 消息经 JSON 序列化故不能传函数与循环引用

**序列化约束**：fork 的 IPC 消息底层以类 JSON 方式结构化克隆，因此发送内容必须是可序列化数据，函数、循环引用、特定原生对象均无法传输。

- 不可传：函数、Symbol、含有循环引用的对象、部分 Node 原生句柄（如 Socket 多数情况不可直接传）。
- 可传：普通对象、数组、字符串、数字、Buffer、TypedArray 等可结构化克隆的数据。
- 循环引用：对象 A 引用 B、B 又引用 A，序列化会抛错或丢失，发送前须先断开环。

```js
const { fork } = require("child_process");

const child = fork("./worker.js");

// 正确：传可序列化的数据与指令
child.send({ cmd: "add", a: 1, b: 2 });

// 错误：函数无法跨进程传递
// child.send({ cmd: "run", fn: () => {} }); // 会被忽略或报错
```

> 若确实需要把"行为"下发，应改传指令字符串或类型标记，由子进程按约定逻辑执行，而不是传函数本身。这是进程间通信与同一进程内函数调用最本质的区别。

**速记**：IPC 消息 **类 JSON**，函数循环引用 **传不了**。



#### 主进程派发计算任务的设计

**任务派发模型**：父进程作为调度者，把 CPU 密集的计算任务连同参数通过 send 下发给 fork 出的子进程，待子进程算完再把结果回传，从而把重活移出主线程。

- 父进程职责：启动子进程、发送任务、接收结果、结束或复用子进程。
- 子进程职责：监听 message、执行计算、把结果 send 回父进程。
- 消息协议：用约定字段（如 type）区分任务类型与结果，避免收发错乱。

> 这正是第 8 篇、第 15 篇所述"CPU 密集下放子进程"的落地方式：主线程保持自由，重计算在独立进程中完成并回传。

**速记**：父**派发**、子**计算回传**，重活**移出主线程**。



#### 子进程计算并回传结果的完整代码

**完整示例**：下面给出可运行的主进程与子进程两份代码，主进程下发一个求和区间，子进程累加后回传结果。

主进程文件 parent.js：

```js
const { fork } = require("child_process");

const child = fork("./child.js");

child.on("message", (msg) => {
  if (msg.type === "result") {
    console.log("子进程算出结果：" + msg.value);
    child.kill();
  }
});

child.on("exit", (code) => {
  console.log("子进程退出，退出码：" + code);
});

child.send({ type: "compute", from: 0, to: 1000000 });
```

子进程文件 child.js：

```js
process.on("message", (task) => {
  if (task.type === "compute") {
    const total = computeRange(task.from, task.to);
    process.send({ type: "result", value: total });
  }
});

function computeRange(from, to) {
  let sum = 0;
  for (let i = from; i < to; i++) sum += i;
  return sum;
}
```

> 运行 node parent.js 即可看到主进程打印计算结果后结束子进程。若需并发处理多个任务，可维护一个子进程池，循环复用同一批子进程而非频繁 fork。

**速记**：两份代码 **parent 派发、child 回传**，fork **一键联通**。



#### 运行结果与消息协议约定

**协议约定**：实战中应对消息结构做稳定约定，常用 type 字段标识意图，用统一字段承载数据，便于扩展与排错。

- **父子约定**：父发 { type: "compute", from, to }，子回 { type: "result", value }。
- **错误传递**：子进程计算异常时应回传 { type: "error", message }，而非静默失败。
- **可扩展性**：新增任务类型只需扩展 type 取值与对应处理逻辑，不影响既有通道。

```js
// 子进程补充错误处理
process.on("message", (task) => {
  if (task.type !== "compute") return;
  try {
    const value = computeRange(task.from, task.to);
    process.send({ type: "result", value });
  } catch (err) {
    process.send({ type: "error", message: err.message });
  }
});
```

> 把错误也纳入消息协议，父进程才能区分"算完了"与"算崩了"。遗漏错误回传会让父进程永久等待，是实战中最常见的逻辑漏洞之一。

**速记**：协议 **type 定意图**，错误 **也要回传**。



### 同步方法、子进程生命周期与退出控制

#### spawnSync、execSync、execFileSync 会阻塞事件循环

**同步创建**：child_process 提供 spawnSync、execSync、execFileSync 三个同步版本，它们会**阻塞调用线程直到子进程结束**，期间事件循环完全停摆。

- **spawnSync**：spawn 的同步版，返回包含 status、signal、stdout、stderr 的结果对象。
- **execSync / execFileSync**：exec / execFile 的同步版，默认返回 Buffer 或字符串形式的输出。
- 阻塞本质：调用期间主线程被卡住，无法处理任何定时器、IO 或请求，与第 15 篇的"请求路径禁用同步 IO"同理。

```js
const { execSync } = require("child_process");

const output = execSync("ls -lh", { encoding: "utf8" });
console.log(output);
// 在 execSync 返回前，整个事件循环被冻结
```

> 同步方法返回值是"结果"而非 ChildProcess，没有流、没有事件可监听；它适合"我要立刻拿到输出"的脚本场景，不适合服务主链路。

**速记**：同步版 **卡住主线程**，返回**结果而非流**。



#### 仅用于脚本启动阶段或 CLI 工具

**适用边界**：同步子进程方法只应在进程启动配置加载、一次性脚本、命令行工具等非并发场景使用，此时阻塞的代价可忽略。

- 启动阶段：读一次配置、探测环境、做一次构建，仅发生一次且不在请求热路径。
- CLI 工具：命令行程序本就是一次性运行，阻塞无并发损失，反而代码更直观。
- 构建脚本：本地构建、部署前检查等离线任务，用同步写法更简洁。

```js
const { execFileSync } = require("child_process");

// 启动阶段探测 git 版本，仅一次，不在请求路径
const gitVersion = execFileSync("git", ["--version"], { encoding: "utf8" });
console.log("git 可用：" + gitVersion.trim());
```

> 判断能否用同步版，看"这次调用是否发生在对外服务的请求链路中"。在链路外、仅一次、离线场景可接受；在链路内一律异步。

**速记**：同步版 **仅限启动与 CLI**，链路内 **一律异步**。



#### 不要在服务器请求路径使用

**请求路径禁令**：生产服务的请求处理函数中禁止使用同步子进程方法，一次同步调用就会冻结整个事件循环，拖垮同时到来的所有请求。

- 危害：execSync 运行期间，同进程所有请求、定时器、IO 回调一起等待，表现为全站随机长延迟。
- 隐蔽性：低频触发时难以复现，压测或高峰时段才暴露，极难定位。
- 替代：请求中需要外部命令，一律用 spawn/exec 的异步版，结果经回调或 await 取得。

> [!CAUTION]
> **注意内容**：哪怕一次 execSync 出现在请求处理函数里，也会在该调用期间**冻结整个事件循环**。它与第 15 篇警告的 readFileSync 性质相同，生产环境应零容忍；改用异步版本并把结果与响应挂接。

**速记**：请求路径 **禁用同步子进程**。



#### exit 事件与 close 事件的区别

**两个结束事件**：exit 在子进程结束时触发，close 在子进程的标准流全部关闭后触发，二者时机不同，close 一定晚于或等于 exit。

- **exit**：子进程本身终止即触发，回调给出退出码 code 与信号 signal，此刻标准流可能尚未冲刷完毕。
- **close**：所有 stdio 流都关闭后才触发，回调同样给 code 与 signal，是"彻底结束"的更稳妥信号。
- 顺序关系：exit 先、close 后；若标准流被管道缓冲，close 会等数据排干再触发。

```js
const { spawn } = require("child_process");

const child = spawn("ls", ["-lh"]);

child.on("exit", (code, signal) => {
  console.log("进程退出：code=" + code + " signal=" + signal);
});

child.on("close", (code, signal) => {
  console.log("流已关闭，彻底结束：code=" + code);
});
```

> 需要"拿最终结果、确认无残留"时监听 close 更可靠；只要关心"进程是否停止"用 exit 即可。二者都给出 code/signal，但 close 多等了流关闭这一步。

**速记**：exit **进程停**，close **流关完**，close **晚于** exit。



#### error 事件（启动失败或信号终止）

**error 事件**：在子进程无法启动、或被信号强制终止时触发，与 exit/close 关注"正常结束"不同，error 聚焦于"启动与中断异常"。

- 启动失败：命令不存在、无执行权限、参数非法等，子进程根本没起来，触发 error 且不会再有 exit。
- 信号终止：某些配置下被信号杀死会先触发 error（携带 code 为 null、signal 非空），再可能触发 exit。
- 必须监听：未处理 error 事件会抛出未捕获异常，在较严格环境下使父进程崩溃。

```js
const { spawn } = require("child_process");

const child = spawn("this-command-not-exist");

child.on("error", (err) => {
  console.error("启动失败：" + err.message);
});

child.on("exit", (code, signal) => {
  console.log("退出：code=" + code + " signal=" + signal);
});
```

> error 与 exit 不完全互斥：启动失败通常只有 error 而无 exit；运行中收到信号有时二者皆来。健壮代码应单独监听 error，不能假设"有 exit 就有全部信息"。

**速记**：error **启动崩/信号杀**，不监听 **会崩父**。



#### kill 方法与信号

**kill 方法**：是 ChildProcess 的 kill(signal) 方法，向子进程发送终止信号，默认发 SIGTERM，可用于主动结束子进程或通知其优雅退出。

- 默认信号：不传参时发送 SIGTERM，子进程可捕获并做清理后再退出。
- 指定信号：kill("SIGKILL") 发送不可捕获的强杀信号，子进程来不及清理即终止。
- 返回值：kill 返回布尔，表示信号是否成功发出（不代表子进程已死），真正的结束仍看 exit/close。

```js
const { fork } = require("child_process");

const child = fork("./worker.js");

setTimeout(() => {
  child.kill("SIGTERM"); // 友好请求子进程退出
}, 2000);

child.on("exit", (code, signal) => {
  console.log("子进程退出，信号：" + signal);
});
```

> 与第 9 篇呼应：SIGTERM 可被捕获、SIGKILL 不可捕获。对子进程发 SIGKILL 虽立刻生效，但会跳过其清理逻辑，可能留下未刷盘数据或半完成状态。

**速记**：kill **发信号**，SIGTERM **可捕**、SIGKILL **强杀**。



### 分离子进程、worker_threads 取舍与常见坑

#### detached 与 unref 让子进程独立存活

**分离机制**：detached 与 unref 配合，可使子进程脱离父进程的控制与事件循环引用，父进程退出后子进程仍能在后台独立运行。

- **detached: true**：在适用平台上让子进程成为新进程组的 leader，不再随父进程的信号联动退出。
- **stdio: "ignore" 或独立文件**：分离时若仍继承父终端，父退出会带走终端，通常把 stdio 设为 ignore 或重定向到文件。
- **child.unref()**：解除父进程事件循环对子进程的引用，父进程可正常退出而不必等子进程，子进程继续存活。

```js
const { spawn } = require("child_process");

const child = spawn("node", ["long-task.js"], {
  detached: true,
  stdio: "ignore"
});

child.unref();
// 父进程到此可立即退出，long-task.js 在后台继续运行
```

> 典型用途是"启动一个守护式后台任务"或"父进程重启而子任务不中断"。注意分离后父进程失去对子进程的便捷控制，需用进程信号或文件锁等其他手段管理。

**速记**：detached **独立进程组**，unref **父退子存**。



#### 与 worker_threads 的取舍

**进程与线程对照**：子进程与 worker_threads 都能把重活移出主线程，取舍关键在"隔离强度"与"开销、通信成本"。

- **子进程**：独立内存、崩溃不连累父进程、隔离最彻底；开销大（每进程 V8 实例）、通信需序列化、启动慢。
- **worker_threads**：同进程内线程、共享内存（可用 SharedArrayBuffer）、开销小、通信快；隔离弱、一处崩可能影响进程、需自行处理并发。
- 选型口诀：**IO 密集且需轻量并发用 worker_threads**，**CPU 密集且需强隔离用子进程**。

> 与第 8、15 篇一致：重活别留主线程。若任务间需要大量共享状态且崩溃可接受，worker_threads 更省；若跑不可信代码或需彻底隔离，子进程更稳。

**速记**：进程 **强隔离重**、线程 **轻量共享**。



#### 常见坑：僵尸进程、缓冲区打满、未处理 error、Windows 命令差异

**四类高频坑**：使用子进程时最易踩的是僵尸进程、缓冲打满、error 未监听、Windows 命令差异，逐一规避可显著降低线上故障。

- **僵尸进程**：父进程退出而子进程未正确回收，或分离后无人管理，残留为僵尸；应监听 exit 做回收，或显式 kill 与 disconnect。
- **缓冲区打满**：用 exec 跑大输出命令触 1MB 上限被杀死，改用 spawn 流式读取或调大 maxBuffer。
- **未处理 error**：命令不存在时 error 未被监听会冒泡崩溃，务必注册 child.on("error")。
- **Windows 命令差异**：Windows 无原生 ls、cat 等命令，跨平台脚本应调用 node 自身或保证命令存在，避免硬编码 Unix 工具。

```js
const { spawn } = require("child_process");

const child = spawn("node", ["worker.js"]);

// 规避"未处理 error"与"僵尸"：监听异常并回收
child.on("error", (err) => console.error("异常：" + err.message));
child.on("exit", (code) => console.log("已回收，退出码：" + code));
```

> [!IMPORTANT]
> **重要内容**：子进程不是"启动即万事大吉"。务必同时监听 **error、exit（或 close）** 完成异常兜底与资源回收；跨平台脚本避免硬编码 Unix 命令，用 spawn 配数组参数而非 shell 拼接，才能稳健运行。

**速记**：四坑 **僵尸、满缓冲、漏 error、Windows 差**。
