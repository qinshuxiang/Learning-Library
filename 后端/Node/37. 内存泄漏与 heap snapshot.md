## 内存泄漏与 heap snapshot

### 内存模型与泄漏判断

#### process.memoryUsage 的读法

**Node 内存三块**：堆内存（V8 管理的 JS 对象）、外部内存（Buffer 等 C++ 层）、RSS（进程总驻留内存），泄漏判断要知道看哪一块。

- `heapUsed`：堆内活跃 JS 对象大小，**JS 对象泄漏看它**；持续单调增长（跨 GC 不回落）是泄漏的直接信号。
- `external`：Buffer 占用（第 7 篇），大文件流处理场景单独观察。
- `rss`：总量，包含代码、堆、外部与线程栈；容器内存限额按 RSS 判定，**RSS 超限被 OOM Kill 时 heapUsed 未必高**。

```js
setInterval(() => {
  const m = process.memoryUsage();
  console.log({
    rss: `${(m.rss / 1048576).toFixed(0)} MB`,
    heapUsed: `${(m.heapUsed / 1048576).toFixed(0)} MB`,
    external: `${(m.external / 1048576).toFixed(0)} MB`,
  });
}, 10000).unref();
```

> 判断泄漏的标准不是「内存高」而是「**只涨不跌**」：正常的峰值回落、GC 抖动都会造成高内存；连续数小时 `heapUsed` 谷值逐级抬升，才叫泄漏。监控上取每日 GC 后的谷值画趋势线，比看瞬时值可靠。

**速记**：JS 泄漏看 **heapUsed 谷值趋势**，容器 OOM 看 **RSS**，只涨不跌才算泄漏。



### 常见泄漏成因

#### 四类高频泄漏源

**泄漏模式高度集中**：绝大多数 Node 内存泄漏落在这四类，排查从它们开始命中率最高。

- **无界缓存**：模块级 `Map`/对象当缓存用，只写不删。对策：上限＋淘汰（LRU 库）、`WeakMap`/`WeakRef` 按键生命周期回收。
- **未清理的定时器与监听器**：`setInterval` 没配 `unref`/清除、`EventEmitter.on` 反复注册不 `off`。特征是伴随句柄数（`process._getActiveHandles()`）增长。
- **闭包持有大对象**：回调捕获了大数组、大响应体，函数生命周期比预期长（挂在长连接上即长期持有）。
- **模块级状态累积**：请求上下文挂到全局数组、日志缓冲无上限——所有「全局变量装请求级数据」的写法都是候选。

```js
// 典型泄漏：全局缓存只进不出
const cache = new Map();
app.get("/user/:id", async (req, res) => {
  if (!cache.has(req.params.id)) {
    cache.set(req.params.id, await loadUser(req.params.id));  // 永不删除
  }
  res.json(cache.get(req.params.id));
});
// 修复：换成 LRU，或用 WeakMap（键为请求相关对象时可自动回收）
```

> 排查优先级就是写代码的「习惯错误榜」：**先查全局 Map 与定时器，再查监听器，最后才是闭包**。前两类能被代码审查规则拦住（缓存必须有淘汰策略、定时器必须有清除配对），纳入团队规范比事后排查便宜。

**速记**：泄漏四源 **无界缓存、失控定时器/监听器、闭包持大、全局装请求**，前两类审查期就该拦。



### heap snapshot 定位

#### 三快照对比法

**Heap Snapshot**：堆的完整对象图快照，在 Chrome DevTools 的 Memory 面板加载分析，是定位「泄漏对象是什么、被谁持有」的最终手段。

- **三快照法**：操作前拍第一张 → 执行嫌疑操作 N 次 → 拍第二张 → 强制 GC 后拍第三张；对比第二、三张间**增量存留**的对象——真正的泄漏会在第三张（GC 后）仍然存在。
- **看什么**：按 Retained Size（持有大小）排序找大对象；用 Retainers 面板看引用链，找到「谁拽着它不放」——引用链的顶端通常就是泄漏点（某数组、某闭包上下文）。
- **构造函数分组**：Snapshot 的 Class 视图按构造函数聚合，`Array`、`Map` 与自家类的对象数量异常即是方向。

```bash
node --inspect app.js
# Chrome 地址栏 chrome://inspect → 打开 DevTools → Memory 面板 → Take snapshot
# 生产环境取证用第 36 章的按需快照接口，文件拿回本地分析
```

> 快照分析的第一步永远是**对比而不是排序**：单张快照里 Retained Size 最大的对象往往是大缓存、大数组——它们可能本来就是设计如此。两张快照之间「无理由增长」的对象才是嫌疑人，对比视图直接给出差集，别在单张快照里猜。

**速记**：三快照 **前、后、GC 后**，看增量存留与引用链，GC 后还在的才是泄漏。

**警告内容**：堆快照会把**全部 JS 对象内容**（含用户数据、令牌、密钥的内存表示）落成文件——生产环境取得的 `.heapsnapshot` 按**敏感数据**对待：限定传输渠道、用后即删，禁止随手丢进聊天工具或公共目录。取证规范与第 36 章「快照即删」是同一条纪律的两半。
