## TypeScript 与 Node 集成

### 为什么在 Node 中引入 TypeScript

#### 静态类型在服务端的收益

**TypeScript**：是 JavaScript 的**超集**，在语法之上增加静态类型系统，最终编译为纯 JavaScript 运行。

- 接口字段、配置项与返回值在**编译期**即被核对，把一部分线上崩溃提前到写代码时暴露。
- 编辑器的补全、跳转与重命名依托类型工作，改动第三方库调用时尤其明显。
- 类型声明本身即**文档**，字段含义不必靠口头约定同步。

> Node 服务长期运行、多人协作，一处字段拼错可能要等到线上请求到来才暴露；类型检查在服务端的收益比一次性脚本大得多。

> [!NOTE]
> **提醒内容**：类型只在编译期存在，运行时会被完全擦除。TypeScript 不做运行时校验，来自请求体、环境变量、数据库的输入仍需自行判断。

**速记**：TypeScript 管 **编译期**，运行时校验另做。



#### 引入的代价与取舍

**代价**：引入类型系统不是零成本，需要构建步骤、类型声明与团队共识。

- 新增**编译环节**，开发期依赖执行器或监视编译。
- 第三方库缺类型时需安装对应的 types 包，或自行编写声明文件。
- 类型写不好会退化为**到处 any**，既没有收益又增加负担。

> 小型脚本或一次性工具未必值得引入。中大型、长期维护、多人协作的服务收益最明显。

> 通用类型语法（基础类型、泛型、映射类型等）与 tsconfig 各项配置已归前端领域的 TypeScript 主题，本篇只讲 TypeScript 与 Node 运行环境、框架和构建流程的对接。

**速记**：长期项目 **值得引入**，临时脚本可省。



### 环境搭建

#### 依赖安装与初始化

**安装方式**：TypeScript 相关依赖装到 **devDependencies**，因为生产运行的是编译后的 JavaScript。

- **typescript**：编译器本体，提供 tsc 命令。
- **ts-node**：直接运行 TypeScript 文件，免去手动编译，适合开发期。
- **@types/node**：Node 内置模块与全局对象的类型声明，缺它则 fs、process 等无类型提示。
- **tsx**：基于 esbuild 的 TypeScript 执行器，启动更快，是社区常用替代方案。

```bash
npm init -y
npm install -D typescript ts-node @types/node
npx tsc --init
```

> tsc --init 生成的 tsconfig.json 带大量注释项，逐项取舍见前端领域 TypeScript 主题第 17 篇。本篇只用到其中少量与 Node 相关的取值。

**速记**：typescript 加 ts-node 加 **@types/node** 三件套。



#### 开发期运行器的选择

**执行器**：开发期直接运行 TypeScript 源码，省去手动编译与产物管理。

- **ts-node**：解释执行，启动略慢，与 tsconfig 严格对齐。
- **tsx**：基于 esbuild 转译，启动快，不参与类型检查。
- **nodemon**：监视文件变化并重启进程，与两者配合使用。

```bash
npx ts-node src/index.ts
npx tsx src/index.ts
npx nodemon --exec tsx src/index.ts
```

> 执行器只做转译或解释，不替代类型检查。持续的类型检查应交给编辑器和 tsc --noEmit，避免只在启动失败的瞬间才暴露错误。

**速记**：开发用 **tsx 或 ts-node**，类型检查另跑。



### Node 内置模块的类型

#### @types/node 提供了什么

**@types/node**：是 Node 运行时 API 的类型声明包，覆盖内置模块、全局对象与全局函数。

- 内置模块：fs、path、http、stream、events、process 等模块的导出均有类型。
- 全局成员：process、Buffer、setTimeout、console 等可直接使用并获得提示。
- 不包含第三方包：express、axios 等需各自安装对应的 types 包。

```ts
import { readFile } from "node:fs/promises";
import path from "node:path";

const configPath = path.join(process.cwd(), "config.json");
const raw = await readFile(configPath, "utf8");
```

> 导入内置模块时写 **node:** 前缀（如 node:fs）可与同名第三方包区分，也便于打包工具与静态分析识别为内置模块。

**速记**：内置模块类型来自 **@types/node**。



#### 扩展 process.env 的类型

**ProcessEnv**：是 @types/node 提供的接口，默认把每个环境变量描述为 string 或 undefined。

- 默认索引签名过于宽泛，拼错变量名不会有提示。
- 用 **declare global** 与接口声明合并扩展 NodeJS.ProcessEnv。
- 扩展后需确保该声明文件被 include 纳入编译。

```ts
declare global {
  namespace NodeJS {
    interface ProcessEnv {
      PORT?: string;
      DATABASE_URL?: string;
      NODE_ENV?: "development" | "production";
    }
  }
}

export {};
```

> 环境变量在进程启动前可能并不存在，字段应声明为**可选**。若希望使用处直接拿到 string，可在启动阶段集中校验并转存为模块级常量，让收窄结果由编译器保留。

**速记**：环境变量 **声明为可选**，启动时集中校验。



#### 声明文件的放置与纳入

**声明文件**：以 **.d.ts** 结尾，只描述类型不含实现，编译后不生成对应 JavaScript。

- 项目内的声明文件通常集中放在 src 下的 types 目录。
- 通过 tsconfig 的 include 纳入编译范围，不需要在代码中 import。
- 为无类型第三方包编写 declare module 声明的完整写法，见前端领域 TypeScript 主题第 16 篇。

```json
{
  "include": ["src", "types"]
}
```

> 声明文件写错位置会静默失效：类型仍报错却不提示原因。若扩展后无效果，先确认文件是否在 include 范围内。

**速记**：声明文件 **只描述类型**，靠 include 纳入。



### 为第三方框架补充类型

#### Express 的请求与响应类型

**@types/express**：为 Express 提供请求、响应与中间件的类型定义。

- **Request 与 Response**：通常从 express 导入，作为处理函数的参数类型。
- 路径参数与查询参数默认是宽泛类型，可用泛型进一步约束。
- 中间件函数的 next 参数类型为 NextFunction。

```ts
import express, { Request, Response, NextFunction } from "express";

const app = express();

app.get("/users/:id", (req: Request, res: Response) => {
  const id = req.params.id;
  res.json({ id });
});

app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  res.status(500).json({ message: err.message });
});
```

> 路径参数的静态类型是字符串，需要数值时应显式转换并校验，不要用类型断言把字符串直接说成数字。

**速记**：Request、Response、**NextFunction** 三件套。



#### 声明合并扩展请求对象

**声明合并**：利用接口的同名合并特性，为 Request 增加自定义字段。

- 常见需求：鉴权中间件解析出用户后挂到 req 上，供后续处理函数读取。
- 做法是在声明文件中扩展 express 模块的 Request 接口。
- 扩展后在所有处理函数中都能获得该字段的类型提示。

```ts
declare global {
  namespace Express {
    interface Request {
      user?: { id: number; role: string };
    }
  }
}

app.get("/profile", (req, res) => {
  if (!req.user) return res.status(401).json({ message: "未登录" });
  res.json(req.user);
});
```

> 扩展字段建议设为**可选**：在鉴权中间件执行之前该字段并不存在，声明为非空会让编译器放行实际会崩溃的访问。

**速记**：扩展 Request 走 **声明合并**，字段设为可选。



### 编译与运行工作流

#### npm scripts 的典型配置

**脚本配置**：把常用命令写进 package.json 的 scripts，统一团队的操作方式。

- **dev**：开发启动，用执行器配合 nodemon 自动重启。
- **build**：清理并编译，输出到 dist。
- **start**：运行编译产物，供生产环境使用。
- **typecheck**：只做类型检查不产出文件，便于接入流水线。

```json
{
  "scripts": {
    "dev": "nodemon --exec tsx src/index.ts",
    "build": "tsc -p tsconfig.json",
    "typecheck": "tsc --noEmit",
    "start": "node dist/index.js"
  }
}
```

> 生产镜像只需安装生产依赖并执行 build 与 start，开发依赖不进入最终镜像，可显著减小体积。

**速记**：dev 跑源码，**start 跑产物**。



#### 路径别名与运行时问题

**路径别名**：用简短前缀替代深层相对路径，改善导入可读性。

- 在 tsconfig 中用 **paths** 配置，配合 baseUrl 使用。
- TypeScript 只做**编译期**解析，运行时 Node 并不认识别名，直接运行会报模块找不到。
- 解决方案：用 tsc-alias 之类工具改写产物中的路径，或在运行时注册解析钩子。

```json
{
  "compilerOptions": {
    "baseUrl": "src",
    "paths": {
      "@services/*": ["services/*"]
    }
  }
}
```

> [!CAUTION]
> **注意内容**：路径别名是**编译期语法糖**。若不做运行时处理，用执行器开发一切正常，一旦用 node 直接跑 dist 就会启动失败，属于典型的开发环境能跑、线上即崩。

**速记**：别名需 **编译期与运行时双配**。



#### 生产环境运行编译产物

**部署流程**：构建阶段编译，运行阶段只执行 JavaScript 产物。

- **构建阶段**：安装全部依赖，执行 build 与 typecheck，产出 dist。
- **运行阶段**：只安装生产依赖，用 node 启动 dist 中的入口文件。
- **sourceMap**：生产可生成并上传到错误监控平台，帮助把堆栈还原到 TypeScript 源码行号。

```bash
npm ci
npm run build
npm prune --production
node dist/index.js
```

> [!WARNING]
> **警告内容**：不要在生产用 ts-node 或 tsx 启动服务。它们会在每次启动时重新转译，拖慢启动速度并占用额外内存，也让运行时代码与构建产物不一致。

**速记**：生产只跑 **dist**，不跑执行器。



### 代码质量工具

#### ESLint 与 Prettier

**分工**：ESLint 负责**代码质量与潜在错误**，Prettier 负责**格式统一**，两者互补。

- **ESLint**：发现未使用变量、不推荐的写法、可疑的异步处理。
- **typescript-eslint**：让 ESLint 读懂 TypeScript 语法，并提供类型感知规则。
- **Prettier**：统一缩进、引号与换行，终结格式争论。
- 二者可能冲突，通常用 eslint-config-prettier 关闭 ESLint 中与格式相关的规则。

```json
{
  "scripts": {
    "lint": "eslint src --ext .ts",
    "format": "prettier --write src"
  }
}
```

> 类型检查与静态检查各有侧重：tsc 管类型正确，ESLint 管写法规范，二者都要跑，不可互相替代。

**速记**：ESLint 查 **质量**，Prettier 管 **格式**。



#### 提交前校验

**Git 钩子**：在提交或推送前自动运行检查，防止问题代码入库。

- **Husky**：管理 Git 钩子，把钩子配置纳入版本控制。
- **lint-staged**：只对**本次改动的文件**执行检查，速度快、打扰少。
- 典型组合：提交前跑 ESLint 与 Prettier，推送前跑类型检查与测试。

```json
{
  "lint-staged": {
    "*.ts": ["eslint --fix", "prettier --write"]
  }
}
```

> 校验规则应**从宽松起步再逐步收紧**。一开始门槛过高，团队会把钩子当障碍绕过，反而失去意义。

**速记**：Husky 管钩子，**lint-staged 只查改动**。



### 项目结构与渐进迁移

#### 分层目录约定

**目录结构**：按职责分层，让每个文件有明确归属。

- **routes**：路由定义，只负责路径与方法的映射。
- **controllers**：处理请求与响应，做参数校验与结果组装。
- **services**：业务逻辑，与 HTTP 无关，便于复用与测试。
- **models 或 repositories**：数据访问层，封装数据库操作。

```text
src
├── index.ts
├── routes
├── controllers
├── services
├── middlewares
└── utils
```

> 分层的意义在于**依赖方向单一**：上层依赖下层，下层不反向依赖。业务逻辑不写在路由里，才能脱离 HTTP 单独测试。

**速记**：路由薄、**服务厚**、数据访问独立。



#### 从 JavaScript 渐进迁移

**渐进迁移**：不必一次性重写，可让两种文件共存，逐步替换。

- **allowJs**：允许 TypeScript 项目编译 JavaScript 文件。
- **checkJs**：对 JavaScript 文件也做类型检查，可配合注释逐文件开启。
- 迁移顺序建议：先工具类与数据模型，再服务层，最后路由与入口。

```json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false
  }
}
```

> 迁移时优先给**被最多地方调用的底层模块**加类型，收益最大。注释抑制手段应作为过渡，不要长期遗留。

**速记**：allowJs **共存**，自底向上替换。
