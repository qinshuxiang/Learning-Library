## URL 与查询字符串处理

### URL 的组成部分

> [!TIP]
> **建议内容**：先掌握一条完整 URL 的字段顺序，再学解析 API 会事半功倍。字段顺序固定，分隔符各司其职，本篇后续所有属性都源于此拆解。

#### 一个完整 URL 的字段拆解

**统一资源定位符（URL）**：是**定位互联网资源**的字符串，由若干有固定顺序的字段拼成，字段之间以特定分隔符衔接。

- **协议 scheme**：http: 或 https:，说明用哪种应用层协议访问资源，后面紧跟两个斜杠。
- **用户名与密码**：user:pass@ 形式，写在主机之前，用于基础认证；现代 URL 已很少在地址里明文带密码。
- **主机 host**：如 www.example.com，是要访问的服务器域名或 IP。
- **端口 port**：主机之后冒号引出的数字，如 :8080；省略时由协议给定默认端口（http 为 80、https 为 443）。
- **路径 pathname**：/api/users，指向服务器上的具体资源位置。
- **查询串 search**：?page=2&sort=name，以问号开头，携带键值对参数。
- **片段 hash**：#section，以井号开头，指向页面内的锚点，不会发送到服务器。

下面用一条完整 URL 拆解各字段：

```text
https://user:pass@www.example.com:8080/api/users?page=2&sort=name#section
└─┬─┘ └─┬─┘ └──────┬──────┘ └┬┘ └──┬───┘ └────────┬────────┘ └─┬─┘
 协议  用户名密码     主机        端口   路径       查询串          片段
```

> 片段 hash 只存在于浏览器端，用于页面内跳转；Node 解析 URL 时会保留它，但 HTTP 请求本身**不会**把 hash 发给服务器。

**速记**：协议主机端口路径查询片段，**顺序固定冒号问号井号分隔**。



#### 各字段在 Node 中的对应属性

**字段到属性**：WHATWG URL 把上面的每个字段映射成 URL 实例的**可读写属性**，属性名与字段一一对应。

- **协议**：对应 **protocol** 属性，结尾带冒号。
- **主机**：对应 **host** 属性，含端口；不含端口的纯域名对应 **hostname**。
- **路径**：对应 **pathname** 属性，以斜杠开头。
- **查询串**：对应 **search** 属性，以问号开头；其键值对再经 **searchParams** 暴露。
- **片段**：对应 **hash** 属性，以井号开头。

```js
const fullUrl = "https://user:pass@www.example.com:8080/api/users?page=2&sort=name#section";
const u = new URL(fullUrl);
console.log(u.protocol); // https:
console.log(u.host);     // www.example.com:8080
console.log(u.hostname); // www.example.com
console.log(u.pathname); // /api/users
```

> host 与 hostname 的差别只在端口：host 含端口、hostname 不含。当端口为默认端口（如 https 的 443）时，URL 构造后会**自动省略**端口，host 与 hostname 此时相同。

**速记**：host **带端口**、hostname **不带端口**。



### WHATWG URL 类与实例化

#### 全局可用的 URL 类无需 require

**URL 类**：是**浏览器与 Node 共用的 WHATWG 标准类**，在 Node 中属于全局对象，直接书写 **new URL(input, base)** 即可，不必引入任何模块。

- 它实现的是 **WHATWG URL 标准**，与浏览器行为一致，便于前后端共用解析逻辑。
- 全局可用意味着**不写 require 也能 new URL(...)**。
- 与之相对，旧版 **url 模块**的 url.parse 属于已不推荐的遗留 API。

```js
const pageUrl = new URL("https://www.example.com/path?x=1");
console.log(pageUrl.href); // https://www.example.com/path?x=1
```

> 全局 URL 类与旧版 url 模块并存于 Node，但官方文档明确推荐优先使用 **WHATWG URL 类**；遗留的 url.parse 仅用于兼容老代码。

**速记**：URL 类**全局即取，无需引入**。



#### new URL 的双参数用法与 base 的作用

**双参数构造**：方法签名为 **new URL(input, base)**，第一个参数是待解析的地址，第二个参数 base 是**基准地址**，用来补全相对路径。

- 当 input 是**绝对 URL**（自带协议与主机）时，base 被忽略。
- 当 input 是**相对路径**（如 /api/list、?page=2）时，base 提供协议、主机与端口，二者拼出完整地址。
- 常见写法：在 HTTP 服务里用 **new URL(req.url, "http://localhost")** 把只有路径的 req.url 补成绝对地址。

```js
const base = "https://www.example.com";
const u1 = new URL("/api/list?page=2", base);
console.log(u1.href); // https://www.example.com/api/list?page=2

const u2 = new URL("?sort=name", "https://www.example.com/items");
console.log(u2.href); // https://www.example.com/items?sort=name
```

> base 只在 input 缺少协议主机时才生效；若 input 已是完整 URL，base 即使写错也不影响结果。但 base 本身必须是合法绝对 URL，否则整体解析会失败。

**速记**：相对靠 base 补，**绝对则 base 失效**。



#### 解析失败抛出 TypeError

**失败语义**：WHATWG URL 在输入无法解析为合法 URL 时，**直接抛出 TypeError**，而不是返回 null 或占位对象。

- 触发场景：base 缺失且 input 是相对路径、base 本身非法、协议不被支持等。
- 这与旧版 **url.parse** 的"尽力解析、错误时返回部分结果"不同，WHATWG 选择**严格失败**。
- 在不确定输入合法性的地方，应**用 try catch 包裹** new URL。

```js
try {
  new URL("/only-path"); // 没有 base，相对路径无法解析
} catch (err) {
  console.log(err instanceof TypeError); // true
}
```

> [!WARNING]
> **警告内容**：凡是解析外部传入的地址（请求行、配置文件、用户输入），务必用 try catch 包裹 new URL。一个非法 URL 不捕获会抛出异常，直接中断当前请求处理链路，甚至拖垮整批请求。

**速记**：非法输入**抛 TypeError**，要 try catch。



### URL 实例的属性与序列化

#### 只读与可写的属性清单

**属性清单**：URL 实例暴露一组属性，**读取**用于取字段、**修改**会同步反映到 href。下面列出常用属性及其取值特征。

- **href**：完整 URL 字符串，是聚合所有字段的总出口。
- **origin**：协议://主机(:端口) 的形式，不含路径与查询串，端口为默认时省略。
- **protocol**：协议加冒号，如 https:。
- **host**：主机加端口；**port** 为单独端口属性；**hostname** 为不含端口的主机。
- **pathname**：以斜杠开头的路径，注意它**不含查询串**。
- **search**：以问号开头的查询串（含问号本身）；其键值对经 **searchParams** 访问。
- **hash**：以井号开头的片段。

```js
const u = new URL("https://www.example.com:8080/p/a?x=1#h");
console.log(u.origin);    // https://www.example.com:8080
console.log(u.host);      // www.example.com:8080
console.log(u.port);      // 8080
console.log(u.pathname);  // /p/a
console.log(u.search);    // ?x=1
console.log(u.hash);      // #h
```

> search 与 pathname 的边界容易混淆：search **以问号开头并包含查询串**，pathname 只到路径为止、**不含问号之后**的内容。混用二者会丢掉或错拼查询参数。

**速记**：search **带问号**，pathname **不含查询**。



#### 属性可修改并自动同步 href

**可写性**：URL 实例的属性**都可赋值修改**，改完之后读 href 会看到最新拼接结果，无需手动重拼。

- 修改 pathname、search、host 等任意属性，href 实时重算。
- searchParams 上的增删改也会反映到 search 与 href。
- 这是 WHATWG URL 相比字符串手拼的**最大便利**：永远得到结构合法的 URL。

```js
const u = new URL("https://www.example.com/old");
u.pathname = "/new";
u.searchParams.set("page", "3");
console.log(u.href); // https://www.example.com/new?page=3
```

> 赋值时不必自己加斜杠或问号：给 pathname 写 /new 而非 new，给 search 写 ?page=3 或改用 searchParams，URL 会按规则正确拼接。手拼分隔符反而容易出双斜杠、缺问号等错误。

**速记**：改属性 **href 自动同步**。



#### toString 与 toJSON 的序列化

**序列化方法**：URL 实例通过 **toString 方法** 与 **href 属性** 得到同一字符串；**toJSON 方法** 则为序列化到 JSON 提供钩子。

- **toString**：返回完整 URL，与读 href 等价，因此字符串上下文（如模板拼接）会直接调用它。
- **href**：属性形式，等于 toString 的结果。
- **toJSON**：返回完整 URL 字符串，使 URL 实例直接 **JSON.stringify** 时输出可读地址而非对象结构。

```js
const u = new URL("https://www.example.com/a?b=2");
console.log(u.toString());     // https://www.example.com/a?b=2
console.log(u.toString() === u.href); // true
console.log(JSON.stringify({ url: u })); // {"url":"https://www.example.com/a?b=2"}
```

> toJSON 的存在意义在于"被 JSON 序列化时返回字符串而非 {...}"。若没有它，JSON.stringify 会展开所有属性；有了它，一个 URL 字段在网络传输里仍是干净的一行地址。

**速记**：toString **等于 href**，toJSON **供 JSON 化**。



### searchParams 与 URLSearchParams 类

#### searchParams 是 URLSearchParams 实例

**searchParams 属性**：每个 URL 实例都带一个 **searchParams** 属性，它是 **URLSearchParams 类**的实例，专门承载查询串的键值对。

- 通过 searchParams 读写查询参数，比直接拼 search 字符串**更安全、更不易错**。
- 它与 search 双向同步：改 searchParams 会更新 search 与 href，反之改 search 也会更新 searchParams。
- URLSearchParams 也可**独立 new** 出来单独使用，不依附于 URL。

```js
const u = new URL("https://www.example.com/?a=1&b=2");
console.log(u.searchParams.get("a")); // 1
u.searchParams.set("b", "9");
console.log(u.search); // ?a=1&b=9
```

> 双向同步是易漏点：直接改 search 字符串后，searchParams 的内容会同步刷新；因此不要同时维护"search 字符串"和"searchParams"两套，认准 searchParams 即可。

**速记**：searchParams **与 search 双向同步**。



#### get、getAll、set、append、has、delete 的基本操作

**增删查改**：URLSearchParams 提供一套针对键值对的原子方法，方法名即语义，覆盖常见的查询串编辑需求。

- **get(name)**：取**第一个**该键的值，键不存在返回 null。
- **getAll(name)**：取该键的**全部**值，返回数组，适合重复键场景。
- **set(name, value)**：设置该键的值，**会删除同名其他值**，只剩一个。
- **append(name, value)**：追加一个值，**保留已有同名值**，形成重复键。
- **has(name)**：判断键是否存在，返回布尔。
- **delete(name)**：删除该键的所有值。

下面给出完整签名与示例。方法签名：**urlSearchParams.get(name)**、**urlSearchParams.getAll(name)**、**urlSearchParams.set(name, value)**、**urlSearchParams.append(name, value)**、**urlSearchParams.has(name)**、**urlSearchParams.delete(name)**。

```js
const p = new URLSearchParams("a=1&a=2&b=3");
console.log(p.get("a"));     // 1
console.log(p.getAll("a"));  // [ '1', '2' ]
console.log(p.has("b"));     // true
p.append("a", "3");
console.log(p.getAll("a"));  // [ '1', '2', '3' ]
p.set("a", "9");
console.log(p.getAll("a"));  // [ '9' ]
p.delete("b");
console.log(p.has("b"));     // false
```

> get 与 getAll 的分工是高频考点：遇到重复键，**get 只给首个**、**getAll 给全部**。若用 get 取一个本应多值的参数（如复选框、多选筛选），会静默丢掉其余值。

**速记**：get **取首个**、getAll **取全部**。



#### forEach 与 entries 遍历

**遍历方式**：URLSearchParams 支持**forEach 方法**逐个回调，也支持**entries 方法**返回迭代器，二者都按"键、值"成对给出。

- **forEach(callback)**：对每个键值对调用 callback(value, name)，注意回调参数顺序是**值在前、键在后**。
- **entries()**：返回可迭代对象，每次产出 [name, value] 数组，可用 for...of 取。
- 此外还有 **keys()** 与 **values()** 分别产出键与值的迭代器。

方法签名：**urlSearchParams.forEach(callback)**、**urlSearchParams.entries()**。

```js
const p = new URLSearchParams("x=1&y=2");
p.forEach((value, name) => {
  console.log(name, value);
});
// 输出：x 1   y 2

for (const [name, value] of p.entries()) {
  console.log(name, value);
}
// 输出：x 1   y 2
```

> forEach 的回调参数顺序是 value 在前、name 在后，与多数"键在前"的遍历（如 Object.entries 是 [key, value]）相反，写代码时别写反，否则会把值当键用。

**速记**：forEach **值前键后**。



#### toString 序列化与重复键处理

**序列化**：URLSearchParams 的 **toString 方法** 把键值对拼回查询串（不含问号），重复键会被保留为多个同名片段。

- 拼接时**自动对特殊字符编码**，空格转为加号。
- 重复键在 toString 后表现为 a=1&a=2 这样的并列形式。
- 直接把结果接到问号后即可作为 search 使用，或交给 URL 的 searchParams。

```js
const p = new URLSearchParams();
p.append("tag", "js");
p.append("tag", "node");
console.log(p.toString()); // tag=js&tag=node
```

> 重复键"get 取首个、getAll 取全部"的规则，到 toString 时表现为并列同名片段。若要唯一值参数，记得用 set 而非 append，否则会越攒越多。

**速记**：toString **并列重复键、自动编码**。



### URLSearchParams 的构造与输入兼容

#### 多种输入形式的构造

**构造输入**：方法签名为 **new URLSearchParams(init)**，init 可以是查询串、普通对象、键值对数组或另一个 URLSearchParams，覆盖日常所有来源。

- **字符串**：如 "a=1&b=2"，可从已有 search 直接喂入（注意去掉问号）。
- **对象**：如 { a: "1", b: "2" }，键为参数名、值为参数值。
- **键值对数组**：如 [["a", "1"], ["b", "2"]]，适合一个键多值的情形。
- **另一个 URLSearchParams**：复制其全部内容，等价于克隆。

```js
console.log(new URLSearchParams("a=1&b=2").toString());      // a=1&b=2
console.log(new URLSearchParams({ a: "1", b: "2" }).toString()); // a=1&b=2
console.log(new URLSearchParams([["a", "1"], ["a", "2"]]).toString()); // a=1&a=2
const src = new URLSearchParams("x=9");
console.log(new URLSearchParams(src).toString());            // x=9
```

> 用对象构造时，值会被强制转成字符串；若对象的某个值是数组，它会被拼成 key=value1,value2（逗号连接）而非多个同名片段——这和直觉不同，需要多值请用键值对数组。

**速记**：对象值**转字符串**，多值用**数组构造**。



#### 与旧 querystring 模块的关系

**模块对照**：URLSearchParams 是 WHATWG 标准、与浏览器一致；**querystring 模块**是 Node 早期自带的遗留模块，两者功能重叠但归属不同。

- 二者都能做查询串的解析与序列化，但 **URLSearchParams 已是官方首选**。
- querystring 的 parse 返回普通对象、stringify 接收对象，接口更"老派"。
- 新代码优先 URLSearchParams；querystring 仅在维护旧项目或需要其特有转义时保留。

```js
const qs = require("querystring");
console.log(qs.parse("a=1&b=2"));    // [Object: null prototype] { a: '1', b: '2' }
console.log(qs.stringify({ a: "1" })); // a=1
```

> querystring.parse 返回的是 **null 原型对象**（无 Object.prototype 上的方法），直接用点访问没问题，但用 Object.keys 之外的方式遍历要注意；URLSearchParams 则始终是标准实例，行为更可预期。

**速记**：新代码**用 URLSearchParams**，旧项目留 querystring。



### 编码与解码

> [!IMPORTANT]
> **重要内容**：编码是 URL 处理的核心，也是绝大多数线上乱码与参数错位的根因。本篇后续所有手拼地址的场景，都应以"是否编码、由谁编码、编码几次"为检查红线。

#### encodeURIComponent 与 decodeURIComponent 的必要性

**编码函数**：方法签名 **encodeURIComponent(component)** 把单个 URL 成分编码为合法串，**decodeURIComponent(str)** 反向解码；二者用于手拼查询参数时避免破坏 URL 结构。

- 当参数值含 &、=、?、空格或中文时，不编码会**被误判为分隔符或非法字符**。
- 只编码"值"本身，不要对整个 URL 调用 encodeURIComponent，否则连协议斜杠、问号都会被编码。
- 与 URLSearchParams 不同，手动拼接字符串时必须**显式**调用这两个函数。

```js
const key = "q";
const value = "a&b=c d";
const query = key + "=" + encodeURIComponent(value);
console.log(query); // q=a%26b%3Dc%20d
console.log(decodeURIComponent(query.split("=")[1])); // a&b=c d
```

> 常见错误：把含特殊字符的值直接拼进 URL，导致 & 被当成参数分隔、= 被当成键值分隔。URLSearchParams 会自动编码从而规避此问题；但凡手拼，必须 encodeURIComponent。

**速记**：手拼值**必编码**，否则分隔符错乱。



#### URLSearchParams 会自动编码

**自动编码**：URLSearchParams 在 append、set 与 toString 时，会**自动对键和值做百分号编码**，开发者无需手动调用编码函数。

- 写入中文、空格、与号等，toString 后已是合法编码串。
- 空格按查询串惯例编码为**加号 +**（而非 %20）。
- 读回时用 get/getAll 得到的是**解码后**的原始值。

```js
const p = new URLSearchParams();
p.append("city", "北京");
p.append("q", "a b");
console.log(p.toString()); // city=%E5%8C%97%E4%BA%AC&q=a+b
console.log(p.get("city")); // 北京
```

> 自动编码是"用 URLSearchParams 优于手拼"的又一理由：编码细节（百分号、加号）由它统一处理，不必关心何时调 encodeURIComponent，也减少了二次编码的风险。

**速记**：URLSearchParams **自动编码、读取自动解码**。



#### 空格编码为加号与 %20 的差异

**空格两种写法**：在查询串里，空格既可编码为**加号 +**，也可编码为**百分号 20（%20）**，二者语义相同但来源不同。

- **URLSearchParams 与 application/x-www-form-urlencoded**：空格编码为 **加号 +**。
- **encodeURIComponent**：空格编码为 **%20**，因为它按通用 URI 成分规则处理，不把加号视作空格特例。
- 服务端解析时通常**两种都认**，但手拼若混用会导致空格与真实加号难以区分。

```js
console.log(new URLSearchParams("q=a b").toString()); // q=a+b
console.log(encodeURIComponent("a b"));               // a%20b
```

> 加号与 %20 互转是常见坑：URLSearchParams 产出的加号，被 encodeURIComponent 再处理会变成 %20（无害）；但若对已经是加号的串再 encodeURIComponent，加号本身会被编码成 %2B，从而把"空格"误变成"真的加号"。

**速记**：表单系用 **加号**，通用编码用 **%20**。



#### encodeURI 与 encodeURIComponent 的区别

**两者分工**：**encodeURI(uri)** 保留 URL 结构字符（冒号、斜杠、问号、井号等），**encodeURIComponent(component)** 把这些都编码掉，只适合编码"片段"。

- encodeURI 用于编码**整条 URL**，保留 :/?#@&=+$, 等结构字符，使结果仍是可用地址。
- encodeURIComponent 用于编码**单个参数值**，把这些结构字符一并编码，防止值里的字符被当结构。
- 记法：**URI 保结构、Component 编码一切**。

```js
console.log(encodeURI("https://a.com/p?x=1&y=2"));
// https://a.com/p?x=1&y=2 （结构字符基本原样）
console.log(encodeURIComponent("https://a.com/p?x=1"));
// https%3A%2F%2Fa.com%2Fp%3Fx%3D1 （全部编码）
```

> 不要拿 encodeURIComponent 去编码整条 URL，否则协议冒号、斜杠都被转义，URL 再也不能直接访问；也不要拿 encodeURI 编码参数值，否则值里的 &、= 仍会泄漏结构。按"整条用 encodeURI、片段用 encodeURIComponent"各司其职。

**速记**：encodeURI **保结构**，encodeURIComponent **编码一切**。



### 旧版 url 模块与 querystring 模块

> [!NOTE]
> **提醒内容**：以下两个模块均为 Node 遗留 API，官方文档明确建议新代码改用 WHATWG URL 与 URLSearchParams。了解它们只为读懂老项目与做迁移，新功能不要再引入。

#### url.parse 已不推荐

**遗留解析**：旧版 url 模块的方法签名 **url.parse(urlString, parseQueryString)** 返回一个**包含各字段的对象**，但它已不在官方推荐之列。

- url.parse 采用"尽力解析"策略，非法输入不会抛错，而是返回部分或空字段，容易掩盖错误。
- 第二个参数 parseQueryString 为 true 时，会把查询串解析为对象；但得到的仍是**旧风格的 Url 对象**，非 WHATWG URL。
- Node 文档明确建议新代码改用 **WHATWG URL 类**。

```js
const url = require("url");
const parsed = url.parse("https://www.example.com/p?x=1", true);
console.log(parsed.hostname); // www.example.com
console.log(parsed.query);    // { x: '1' }
```

> url.parse 不抛错的特性是把双刃剑：它不会因非法输入中断程序，但也让你**难以发现地址其实不合法**。WHATWG 的 new URL 用 TypeError 强制你处理错误，更利于健壮代码。

**速记**：url.parse **尽力解析不抛错**，已不推荐。



#### url.format 与 URL 类的对照

**遗留序列化**：方法签名 **url.format(urlObject)** 把对象拼回 URL 字符串，是 url.parse 的逆操作，对应 WHATWG 里 **URL 实例的 href / toString**。

- url.format 接收旧风格 Url 对象或普通对象，按字段拼串，**不保证结果结构合法**。
- WHATWG 用 new URL(...) 构造、用 href 读取，构造即校验、读写即同步。
- 迁移建议：把 url.parse 换 new URL、url.format 换 urlInstance.href。

```js
const url = require("url");
console.log(url.format({ protocol: "https:", host: "www.example.com", pathname: "/p" }));
// https://www.example.com/p
```

> 对照迁移时最直接的改法是：解析用 new URL、序列化直接读 .href；凡是看到 url.format 老对象拼接，优先重构为 URL 实例的属性赋值，让结构合法性由 URL 类保障。

**速记**：url.format **对应 href**，旧风格不校验。



#### querystring 的 parse、stringify、escape、unescape

**遗留查询串**：querystring 模块提供 **parse(str, sep, eq, options)**、**stringify(obj, sep, eq, options)**、**escape(str)**、**unescape(str)** 四个常用入口，适合简单场景下的查询串读写与转义。

- **parse**：把查询串解析成对象，sep 与 eq 可自定义分隔符（默认 & 与 =）。
- **stringify**：把对象序列化为查询串，同样支持自定义分隔符。
- **escape / unescape**：手动对字符串做百分号编码与解码，等价于内部用的编码步骤。

```js
const qs = require("querystring");
console.log(qs.parse("a=1&b=2"));         // { a: '1', b: '2' }
console.log(qs.stringify({ a: "1", b: "2" })); // a=1&b=2
console.log(qs.escape("北 京"));           // %E5%8C%97%20%E4%BA%AC
console.log(qs.unescape("%E5%8C%97%20%E4%BA%AC")); // 北 京
```

> querystring.escape 与 unescape 是底层工具，日常大多不必直接调；URLSearchParams 已内建编码。保留它们是出于兼容，新代码无需再引入这两对函数。

**速记**：querystring **parse/stringify/escape/unescape** 四件套。



#### 与 URLSearchParams 的取舍

**选型结论**：优先 **URLSearchParams** 处理查询串；只有维护旧代码、或需要 querystring 特有的分隔符与转义控制时，才用 **querystring 模块**。

- URLSearchParams 是标准、自动编码、与 URL 联动，几乎覆盖全部新需求。
- querystring 的 parse 返回 null 原型对象、接口偏老，且不与 URL 实例共享状态。
- 二者不能混用同一份数据：别一边用 URL.searchParams 改、一边用 querystring 重新 parse，否则状态会分叉。

```js
// 推荐
const u = new URL("https://www.example.com/");
u.searchParams.set("page", "1");

// 仅旧项目
const qs = require("querystring");
const obj = qs.parse("page=1");
```

> 取舍的核心就一句话：新代码一律 URLSearchParams；遇到老仓库里的 querystring，不强行改写，但要清楚它已属遗留、不再扩展新用法。

**速记**：新用 **URLSearchParams**，旧留 **querystring**。



### 在 HTTP 服务中解析请求 URL

#### req.url 只有路径与查询串

**请求行的局限**：HTTP 服务里 **req.url** 只含**路径 pathname 加查询串 search**，**不含协议、主机、端口**，也**不含片段 hash**——片段本就不会随请求发送。

- 典型 req.url 形如 /api/users?page=2&sort=name，没有 http:// 与主机。
- 直接用字符串方法切分 req.url 容易出错，尤其查询串含特殊字符时。
- 正确做法是配一个 base，用 **new URL(req.url, "http://localhost")** 得到完整 WHATWG URL。

```js
const http = require("http");
const server = http.createServer((req, res) => {
  const u = new URL(req.url, "http://localhost");
  console.log(u.pathname); // /api/users
  console.log(u.searchParams.get("page")); // 2
  res.end("ok");
});
```

> 必须给 base：因为 req.url 是相对路径，单独 new URL(req.url) 会抛 TypeError。base 取什么主机并不重要（解析结果的主机来自 base），但它必须是合法绝对 URL。

**速记**：req.url **无协议主机**，须配 base。



#### 获取路径做路由、获取查询参数做筛选

**路由与筛选**：拿到完整 URL 后，**pathname 用于匹配路由**，**searchParams 用于读取筛选参数**，二者职责分离、互不干扰。

- 路由判断只看 pathname，例如 /api/users 映射到用户列表处理器。
- 分页、排序、过滤等可变条件从 searchParams 取，不改路径结构。
- 这样路由规则稳定，参数变化不影响匹配逻辑。

```js
const http = require("http");
const server = http.createServer((req, res) => {
  const u = new URL(req.url, "http://localhost");
  if (u.pathname === "/api/users") {
    const page = u.searchParams.get("page") || "1";
    const sort = u.searchParams.get("sort") || "id";
    res.end(`page=${page}&sort=${sort}`);
  } else {
    res.statusCode = 404;
    res.end("not found");
  }
});
```

> 把路径与查询串分开处理，是 REST 风格的基础：资源由路径定位、条件由查询参数表达。混在一起（如把筛选写进路径）会让路由爆炸、难以维护。

**速记**：路径**定路由**，查询**做筛选**。



### 实战：地址解析与 API 构造封装

#### 封装解析请求地址的函数

**解析封装**：下面把"从 req.url 得到路径与参数"封装成 **parseRequestUrl**，统一补 base 并暴露常用字段，避免每处请求都重复写 new URL。

方法签名：**parseRequestUrl(reqUrl, base)**，返回含 pathname 与 params 的对象。

```js
function parseRequestUrl(reqUrl, base = "http://localhost") {
  const u = new URL(reqUrl, base);
  const params = {};
  u.searchParams.forEach((value, name) => {
    params[name] = u.searchParams.getAll(name).length > 1
      ? u.searchParams.getAll(name)
      : value;
  });
  return { pathname: u.pathname, params };
}

// 使用
const result = parseRequestUrl("/api/users?page=2&tag=js&tag=node");
console.log(result.pathname);        // /api/users
console.log(result.params.page);     // 2
console.log(result.params.tag);      // [ 'js', 'node' ]
```

> 该封装对重复键做了"单值取标量、多值取数组"的归一，调用方无需再判断 get 还是 getAll。但注意：归一后可能把"恰好一个值的数组场景"压成标量，若业务严格要求数组，应改为始终返回 getAll 的结果。

**速记**：解析封装 **补 base、归一单多值**。



#### 封装构造带查询参数的 API 地址函数

**构造封装**：下面用 **buildApiUrl** 把基地址与参数对象拼成合法 API 地址，自动处理编码与多值，替代易错的手拼字符串。

方法签名：**buildApiUrl(base, path, query)**，base 为协议主机、path 为路径、query 为参数对象。

```js
function buildApiUrl(base, path, query = {}) {
  const u = new URL(path, base);
  Object.entries(query).forEach(([key, value]) => {
    if (Array.isArray(value)) {
      value.forEach((item) => u.searchParams.append(key, String(item)));
    } else {
      u.searchParams.set(key, String(value));
    }
  });
  return u.href;
}

// 使用
console.log(buildApiUrl("https://api.example.com", "/search", {
  q: "北京 weather",
  page: 1,
  tag: ["js", "node"]
}));
// https://api.example.com/search?q=%E5%8C%97%E4%BA%AC+weather&page=1&tag=js&tag=node
```

> 用 URLSearchParams.append 处理数组值，可正确生成同名多片段；若误用 set，数组会被逗号连接成单个值。空格被自动编码为加号，中文被自动百分号编码，全程无需手写 encodeURIComponent。

**速记**：构造封装 **数组用 append、自动编码**。



#### 处理数组型与嵌套型查询参数

**数组与嵌套**：查询串原生只有"键值对"，**数组型**靠重复键表达，**嵌套型**（对象）需自行约定展平规则，URLSearchParams 本身不内建嵌套结构。

- 数组型：同一键出现多次，用 append 生成 tag=js&tag=node，读取用 getAll。
- 嵌套型：常见约定是用 parent.child 或 parent[child] 作为键名展平，如 user.name=Tom。
- 没有统一标准，前后端须约定同一套展平/还原规则，否则解析错位。

```js
function flattenQuery(obj, prefix = "", out = new URLSearchParams()) {
  for (const [key, value] of Object.entries(obj)) {
    const name = prefix ? `${prefix}.${key}` : key;
    if (Array.isArray(value)) {
      value.forEach((item) => out.append(name, String(item)));
    } else if (value && typeof value === "object") {
      flattenQuery(value, name, out);
    } else {
      out.set(name, String(value));
    }
  }
  return out;
}

console.log(flattenQuery({ user: { name: "Tom" }, tag: ["a", "b"] }).toString());
// user.name=Tom&tag=a&tag=b
```

> 嵌套展平是"约定大于标准"的地带：URLSearchParams 只认扁平键值对，对象结构必须显式展平与还原。若团队已用某框架（如 Express 的查询解析），直接复用其规则，别另起一套造成对接偏差。

**速记**：数组**重复键**、嵌套**点号展平**。



### 常见坑

> [!CAUTION]
> **注意内容**：下面三处是线上事故高发区，皆源于"编码层级错位"或"重复处理"。动手拼地址前先确认：解的是整条还是单值、编了几次、空格用加号还是 %20。

#### 对完整 URL 再 decodeURIComponent 会破坏结构

**破坏结构**：对**已是完整 URL 的字符串**再次调用 decodeURIComponent，会把查询串里本就被编码的分隔结构（如 %26 解码回 &）释放出来，污染参数边界。

- 解码应作用在被编码的**单个值**上，而非整条 URL。
- 若用 URLSearchParams 或 new URL 解析，get 返回的已是解码值，无需再解码。
- 重复解码会让 a=1%26b%3D2 变成 a=1&b=2，使一个参数裂成两个。

```js
const raw = "https://a.com/?q=1%26b%3D2";
console.log(decodeURIComponent(raw));
// https://a.com/?q=1&b=2  —— 查询结构被破坏，参数边界错乱
```

> 这条坑的本质是"解码层级错位"：URL 整体的结构字符（&、=、?）是语法，不该被当作值解码。先 new URL 解析、再用 get 取值，取值已经是正确的解码结果，再 decodeURIComponent 就是画蛇添足。

**速记**：整条 URL **勿再解码**，取值已解。



#### 重复编码导致百分号被二次转义

**二次转义**：对**已经编码过的字符串**再调用 encodeURIComponent，原有的 % 会被编码成 %25，造成百分号翻倍、解码后内容失真。

- 一次编码后 % 已是转义起始符，二次编码把它变成字面 %25。
- 常见于"URLSearchParams 已编码，又手动包一层 encodeURIComponent"。
- 解码时只能还原一层，导致得到的是 %E5... 而非真正中文。

```js
const once = encodeURIComponent("北京");       // %E5%8C%97%E4%BA%AC
const twice = encodeURIComponent(once);        // %25E5%258C%97%25E4%25BA%25AC
console.log(twice); // 双重编码，百分号被转义
```

> 避免二次编码的关键是"只在一个地方编码"。用 URLSearchParams 就别再手动 encodeURIComponent；手动拼就只在拼值时编码一次、之后不再碰它。编码幂等性不存在，多编一次就错一次。

**速记**：编码**只做一次**，再编即翻倍。



#### 中文与空格处理不一致

**不一致来源**：中文与空格在不同编码路径下产物不同（中文走百分号、空格在表单系走加号），若手拼与标准 API 混用，会出现同义不同形的查询串，导致比对或签名失败。

- 中文：URLSearchParams 与 encodeURIComponent 都用 **百分号 UTF-8** 编码，结果一致。
- 空格：URLSearchParams 用 **加号**，encodeURIComponent 用 **%20**，二者不同形。
- 风险点：自己手拼 key=值 时若漏编码，中文或空格会直接出现在 URL 里，某些服务端拒绝或误读。

```js
console.log(new URLSearchParams("q= a").toString()); // q=+a
console.log(encodeURIComponent(" a"));                // %20a
// 同样一个空格，两种写法形态不同
```

> 一致性的底线是"统一走一套编码路径"。要么全程 URLSearchParams（空格变加号），要么全程手动 encodeURIComponent（空格变 %20），不要一半一半。涉及签名校验时尤其要严格一致，否则两端算出的串永远对不上。

**速记**：编码**统一一条路径**，混用即错位。
