## Request 与 Response 对象

### 类型本质与流特征

#### http.IncomingMessage 是可读流

**请求对象（req）**：是 http 模块在处理每次连接时创建的 **http.IncomingMessage 实例**，同时继承自 **可读流（Readable）**，因此既带有请求元数据，又能用流的 API 读取请求体。

- req 由 http 服务器在收到请求时自动生成，回调签名为 (req, res) 中的第一个参数。
- 因为 req 是可读流，请求体不会一次性放进内存，而是以 **chunk（数据块）** 形式逐段到达。
- 读取请求体必须 **主动消费** req，否则底层连接不会释放，会在常见坑一节专门说明。

> http.IncomingMessage 同时对应服务器收到的请求与客户端收到的响应（http.ClientRequest 的响应），二者都继承可读流。本篇只讨论服务器侧的请求对象。

**速记**：req 即 **可读流 + 请求元数据**。



#### http.ServerResponse 是可写流

**响应对象（res）**：是 http 模块在收到请求后为本次连接创建的 **http.ServerResponse 实例**，同时继承自 **可写流（Writable）**，因此既能设置状态与头，又能像写流一样写入响应体。

- res 由 http 服务器随 req 一起创建，是回调签名 (req, res) 中的第二个参数。
- 因为是响应要发回客户端，res 用 **write 与 end** 这类可写流方法把数据送出去。
- 可写流的语义意味着：**先写头、再写体**，头一旦发出就不能再改。

> 可写流的背压（backpressure）机制同样适用于 res.write：当客户端消费慢时，write 会返回 false，提示暂停写入以免内存膨胀。普通小响应无需关心，大文件流式下载时才会触及。

**速记**：res 即 **可写流 + 响应控制面**。



#### 流 API 统一了两端操作

**统一收益**：由于 req 与 res 均继承自流类，开发者可以用 **同一套流心智模型** 处理进与出，也能把二者直接接到管道上。

- 对 req 用 **监听 data 事件** 或 **异步迭代** 来读取，对 res 用 **write 与 end** 来发送。
- 借助 pipe，可以把 req 直接导向文件可写流，实现上传落地，无需手动拼块。
- 流的 **error 事件** 两端都存在，读取或写入异常都要监听，否则可能抛出未捕获错误。

```js
const http = require("http");
const fs = require("fs");

const server = http.createServer((req, res) => {
  if (req.method === "POST" && req.url === "/upload") {
    // req 是可读流，可直接 pipe 到文件可写流
    req.pipe(fs.createWriteStream("./upload.bin"));
    req.on("end", () => res.end("uploaded"));
    return;
  }
  res.end("ok");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> pipe 只转发数据、不转发错误：源流出错不会自动通知目标流，res 端出错也不会回流到 req，任一端异常都可能留下未关闭的句柄。生产代码应改用 stream.pipeline，由它统一传递错误并清理两端流。

**速记**：req 进、res 出，**都按流来用**。



### 请求对象：请求行与请求头

#### req.method 标识请求方法

**req.method**：是请求对象上的 **字符串属性**，存放客户端发出的 HTTP 方法，如 GET、POST、PUT、DELETE 等，且 **全为大写**。

- 常见取值：GET 取资源、POST 提交、PUT 整体替换、PATCH 局部更新、DELETE 删除、HEAD 取头、OPTIONS 探询。
- 字符串直接比较即可判断方法，例如 if (req.method === "POST")。
- 跨域预检会先发 OPTIONS，需单独处理，否则被误判为普通请求。

> method 区分大小写但标准方法一律大写；不要凭经验假设永远是 GET，未匹配的方法应返回 **405** 而不是 404。

**速记**：req.method 是 **大写方法字符串**。



#### req.url 是原始路径加查询串

**req.url**：是请求对象上的 **字符串属性**，存放客户端请求行里的 **原始路径与查询串**，但 **不含协议、域名与端口**。

- 典型内容形如 /user/profile?id=7，其中 /user/profile 是路径，问号后是查询串。
- 它完全由 **客户端发来的请求行** 决定，服务端无法从 req.url 取得域名，域名应去 req.headers.host 取。
- 要拆出路径与参数，需要自行解析，下一节会给出标准做法。

> req.url 不会做 URL 解码，遇到 %20 之类仍需自行处理；解析路径优先用标准 URL 类，而非手动切分字符串，能避免大量边界错误。

**速记**：req.url 只含 **路径 + 查询串**。



#### req.httpVersion 反映协议版本

**req.httpVersion**：是请求对象上的 **字符串属性**，表示客户端使用的 HTTP 协议版本，常见为 1.0 或 1.1；另有 httpVersionMajor 与 httpVersionMinor 两个数字属性拆出主次版本。

- 多数现代客户端使用 HTTP/1.1，故该值通常为字符串 1.1。
- HTTP/2 在 Node 走的是独立 tls 与 http2 模块，传统 http.createServer 拿到的是 1.1。
- 一般业务无需根据版本分支，只有做兼容性或分块传输控制时才关心。

> 不要把它和 req 的其他属性混淆：它与状态码、方法无关，仅描述 **协议版本本身**，且格式是 "1.1" 这样的字符串而非数字。

**速记**：req.httpVersion 是 **协议版本字符串**。



#### req.headers 键名一律小写

**req.headers**：是请求对象上的 **普通对象**，存放所有请求头，键名 **全部被 Node 规范化为小写**，取值为字符串或字符串数组。

- 客户端发来的 Content-Type、User-Agent、Cookie 等，在对象里一律以 **小写键** 访问：req.headers["content-type"]。
- 单个头出现多次时（如重复的 set-cookie 来自响应侧），Node 会把值合并为 **数组**。
- 与原始报文不同，这里 **丢失了原始大小写与出现顺序**，需要这些信息时才用 req.rawHeaders。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  // 键名必须小写访问
  const ct = req.headers["content-type"];
  const ua = req.headers["user-agent"];
  res.end("content-type=" + ct + ", ua=" + ua);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：用大写或驼峰键（如 req.headers["Content-Type"]）会取到 undefined，这是新手最常踩的坑之一。一律用小写字母访问最稳妥。

**速记**：访问请求头 **键名全小写**。



#### req.rawHeaders 保留原始大小写与顺序

**req.rawHeaders**：是请求对象上的 **字符串数组**，按 **名、值、名、值……交替** 的方式存放原始请求头，完整保留客户端发来的大小写与先后顺序。

- 数组下标偶数位是头名（可能带任意大小写），奇数位是对应的值。
- 与 req.headers 的规范化对象不同，rawHeaders 能看到 **原始书写形式** 与 **重复头的全部出现**。
- 仅在需要校验签名、还原报文或调试时才用之；常规业务读 req.headers 即可。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  // 形如 ["Host", "localhost:3000", "Content-Type", "application/json", ...]
  console.log(req.rawHeaders);
  res.end("see console");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!NOTE]
> **提醒内容**：rawHeaders 与 headers 是 **同一批头的两种视图**：前者保真但难用，后者易用但有损。不要试图用 rawHeaders 来做常规取值，代码会写得很啰嗦。

**速记**：rawHeaders **保真、交替存**；headers **易用、已小写**。



#### 常见请求头语义

**常用头**：req.headers 里最常读取的几个头各有固定语义，理解它们才能正确解析请求。

- **host**：目标主机与端口，是取得域名的唯一来源，因为 req.url 不含域名。
- **user-agent**：客户端标识，浏览器、爬虫、脚本各有不同，常用于统计或分流。
- **content-type**：请求体的格式声明，解析请求体前必须先看它。
- **cookie**：客户端带来的会话标识，键值对以分号分隔，需自行解析或由框架处理。
- **authorization**：鉴权凭据，Bearer 令牌或 Basic 凭证都在这里。

> content-length 与 transfer-encoding 描述请求体长度或分块方式，但 Node 已把分块重组进可读流，业务侧通常无需关心这两个头即可读完 body。

**速记**：host 取域名、content-type 定解析、cookie 带会话。



### 查询串与路径拆分

#### 必须手动拆分路径与查询串

**问题本质**：req.url 把路径与查询串合在一起，Node **不会自动拆分**，要分别拿到纯净路径与参数只能自行处理。

- 直接按问号切分会得到两段，但还要对查询串做键值的 URL 解码，手工实现易漏边界。
- 手工解析遇到重复键、编码空格、数组参数等情形会迅速复杂化。
- 标准做法是用 **URL 类** 或 **querystring** 模块，而非自写正则。

> [!CAUTION]
> **注意内容**：切勿用字符串 split 草草了事：请求可能带空查询串、含 # 片段（# 不会发到服务端）、含编码字符，手工逻辑难以全覆盖。

**速记**：req.url **要自己拆**，别硬切。



#### 用 URL 类解析请求地址

**解析方式**：借助全局 **URL 类**，以 req.url 为相对地址、以 host 拼出的绝对地址为基准，即可得到一个结构化的地址对象。

- 构造签名：new URL(url, base)，其中 url 是 req.url，base 是 http:// 加 req.headers.host。
- 解析后得到 **pathname（纯净路径）** 与 **searchParams（查询参数对象）**，无需手动切问号。
- URL 类会自动做 **解码与归一化**，比手工处理可靠得多。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const base = "http://" + (req.headers.host || "localhost");
  const full = new URL(req.url, base);
  // full.pathname 是 /search，full.searchParams 是可用的参数对象
  const q = full.searchParams.get("q");
  res.end("path=" + full.pathname + ", q=" + q);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!CAUTION]
> **注意内容**：必须提供 base，因为 req.url 是相对路径；若 base 缺失，new URL 会抛错。用 req.headers.host 拼 base 既简单又贴近真实请求。

**速记**：new URL(req.url, base) **一步拆干净**。



#### 用 URLSearchParams 取参数

**参数对象**：URL 解析结果上的 **searchParams** 是 URLSearchParams 实例，提供按名取参、取全部、判断存在等标准方法。

- get(name) 取单个参数值，未出现返回 null；getAll(name) 取重复键的全部值。
- has(name) 判断参数是否存在；keys、values、entries 用于遍历。
- 它已对 **百分号编码** 做解码，拿到的就是可读中文或字符串。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const full = new URL(req.url, "http://localhost");
  const params = full.searchParams;
  const tags = params.getAll("tag"); // 支持 ?tag=a&tag=b
  res.end("first tag=" + (params.get("tag") || ""));
});

server.listen(3000, () => console.log("listening on 3000"));
```

> URLSearchParams 与 URL 类配套使用最顺手；若手里只有查询串字符串，也可直接 new URLSearchParams(queryString) 构造。

**速记**：searchParams.get **拿参数、已解码**。



#### querystring 模块的解析方式

**替代方案**：Node 内置的 **querystring 模块** 提供 parse 与 stringify，可把裸查询串解析成普通对象，适合不构造完整 URL 的场景。

- parse 签名：querystring.parse(str[, sep[, eq[, options]]])，sep 默认 &，eq 默认 =。
- 解析结果是 **普通对象**，重复键会合并为数组，编码字符自动解码。
- stringify 则反向把对象拼回查询串，用于构造跳转地址等。

```js
const http = require("http");
const querystring = require("querystring");

const server = http.createServer((req, res) => {
  const questionMark = req.url.indexOf("?");
  const queryString = questionMark === -1 ? "" : req.url.slice(questionMark + 1);
  const params = querystring.parse(queryString); // { id: "7" }
  res.end("id=" + params.id);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 现代代码更推荐 URL 类，因为 querystring 已被文档标记为 **遗留（legacy）**，新增逻辑优先用 URL 与 URLSearchParams。

**速记**：querystring 偏 **遗留**，URL 类更优先。

### 请求体的读取与解析

#### 请求体需要自行以流方式消费

**核心事实**：req 是可读流，请求体 **不会自动存入某个属性**，必须监听事件或异步迭代才能拿到完整内容。

- GET、HEAD 通常无请求体，无需读取；POST、PUT、PATCH 才携带 body。
- 不读取也不结束 req，连接会一直挂起，最终超时或被池耗尽，这是常见坑之一。
- 读取方式有三种：监听 data/end、for await 异步迭代、Buffer.concat 合并数组，下面逐一说明。

> 某些方法（GET）语义上无 body，但客户端仍可能发送；稳妥做法是按 content-length 或方法决定是否消费，避免空等 data 事件。

**速记**：body 不自动存，**流里自己取**。



#### 监听 data 与 end 事件拼接

**事件式读取**：给 req 注册 **data 事件** 收集每一块，注册 **end 事件** 在收齐后合并处理，这是最经典、兼容性最好的写法。

- 每次 data 回调拿到一个 **Buffer 块**，先 push 进数组暂存。
- end 触发表示 **所有块已到齐**，此刻用 Buffer.concat 合并并转字符串。
- 该写法基于回调，可运行于所有 Node 版本，是理解流的入门范式。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (chunk) => chunks.push(chunk));
  req.on("end", () => {
    const body = Buffer.concat(chunks).toString("utf8");
    res.end("length=" + body.length);
  });
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!CAUTION]
> **注意内容**：合并务必用 Buffer.concat 而非数组 join；若直接把 Buffer 当字符串拼，多字节字符（如中文）会被截断成乱码。

**速记**：data 收块、end 合并，**先 push 后 concat**。



#### 用 for await 异步迭代

**异步迭代式读取**：因为可读流实现了 **Symbol.asyncIterator**，可用 **for await...of** 直接逐块迭代 req，写法更贴近同步直觉。

- 语法：for await (const chunk of req) 逐块拿到 Buffer。
- 循环结束后即等价于 end 事件，无需再注册 end。
- 必须在 **async 函数** 内使用，常配合 try/catch 处理读取异常。

```js
const http = require("http");

const server = http.createServer(async (req, res) => {
  const chunks = [];
  for await (const chunk of req) {
    chunks.push(chunk);
  }
  const body = Buffer.concat(chunks).toString("utf8");
  res.end("length=" + body.length);
});

server.listen(3000, () => console.log("listening on 3000"));
```

> for await 本质是包装了 data/end/pause/resume 的语法糖，背后仍是流机制；在需要背压控制的复杂管道中，显式事件写法仍不可替代。

**速记**：for await **逐块迭代 req**。



#### 用 Buffer.concat 合并数组

**合并要点**：无论用哪种读取方式，最终都要把 **零散 Buffer 数组合并成一块**，统一用 **Buffer.concat(list)** 完成，再指定编码转字符串。

- Buffer.concat 接收一个 Buffer 数组，返回拼接后的单个 Buffer。
- 编码统一选 **utf8**，与后续解析、写回保持一致，避免中文乱码。
- 若事先知道总大小，可预先分配，但普通场景直接 concat 即可，无需过度优化。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (chunk) => chunks.push(chunk));
  req.on("end", () => {
    const merged = Buffer.concat(chunks); // 先合并
    const text = merged.toString("utf8"); // 再解码
    res.end(text);
  });
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!CAUTION]
> **注意内容**：不要对每块单独 toString 再相加：一旦某块截断了多字节字符边界，结果立即乱码。先 concat 成完整 Buffer，最后统一解码才正确。

**速记**：先 concat、**后解码 utf8**。



#### 按 Content-Type 区分解析

**解析前提**：拿到原始 body 字符串后，必须依据 **req.headers["content-type"]** 选择对应的解析逻辑，不同格式不可混用。

- **application/json**：按 JSON 解析，适合结构化数据。
- **application/x-www-form-urlencoded**：键值对表单，可用 URLSearchParams 或 querystring 解析。
- **multipart/form-data**：通常用于带文件的表单，结构复杂，需借助 busboy、formidable 等库。
- 解析前可先用 **content-type 的字符串.startsWith** 判断主类型，忽略参数（如 charset）。

```js
const http = require("http");

function parseRequestBody(req, rawBody) {
  const type = req.headers["content-type"] || "";
  if (type.startsWith("application/json")) {
    return JSON.parse(rawBody);
  }
  if (type.startsWith("application/x-www-form-urlencoded")) {
    return new URLSearchParams(rawBody);
  }
  // multipart/form-data 建议交给专门库解析
  return rawBody;
}

const server = http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (c) => chunks.push(c));
  req.on("end", () => {
    const body = parseRequestBody(req, Buffer.concat(chunks).toString("utf8"));
    res.end("ok");
  });
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：multipart/form-data 的边界分隔、文件与字段混排逻辑很繁琐，自己实现既易错又易有安全漏洞；生产环境一律用成熟库，不要手搓。

**速记**：看 **content-type** 选解析器。



#### JSON 解析必须 try/catch 防非法输入

**健壮性要求**：对 JSON 主体调用 **JSON.parse** 时，必须包裹 **try/catch**，因为客户端完全可能发来非法或非 JSON 的内容。

- 非法 JSON 会抛 SyntaxError，若不捕获将演变为未处理异常，可能拖垮进程。
- 捕获后通常返回 **400 Bad Request**，并附简短错误信息。
- 即便 content-type 声明为 json，也不能信任内容一定合法，校验永远必要。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const chunks = [];
  req.on("data", (c) => chunks.push(c));
  req.on("end", () => {
    const raw = Buffer.concat(chunks).toString("utf8");
    let data;
    try {
      data = JSON.parse(raw);
    } catch (err) {
      res.statusCode = 400;
      res.end("invalid json");
      return;
    }
    res.end("name=" + (data.name || ""));
  });
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：不捕获 JSON.parse 是高频线上事故源：一个坏请求就能触发未捕获异常。把解析放进 try/catch 是解析 JSON body 的最低防线。

**速记**：JSON.parse **必包 try/catch**。



#### 体积限制与拒绝超大请求

**防护必要**：请求体应当设 **体积上限**，超过则立即中断并拒绝，防止恶意或失误的大请求耗尽内存与带宽。

- 在 data 事件中累加已收字节数，超过阈值就调用 **req.destroy()** 终止连接。
- 也可在收齐后判断 Buffer.concat 结果的长度，但边收边断更省资源。
- 合理的上限依业务而定，普通 JSON 接口几百 KB 已绰绰有余。

```js
const http = require("http");

const MAX = 1024 * 1024; // 1MB 上限

const server = http.createServer((req, res) => {
  let total = 0;
  const chunks = [];
  req.on("data", (chunk) => {
    total += chunk.length;
    if (total > MAX) {
      res.statusCode = 413;
      res.end("payload too large");
      req.destroy(); // 直接断连，停止接收
      return;
    }
    chunks.push(chunk);
  });
  req.on("end", () => res.end("received"));
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 413 Payload Too Large 是表达"请求体过大"的标准状态码；若不限制，攻击者可发巨量 body 把服务内存打满，属基础防护项。

**速记**：超阈值 **req.destroy 拒收**。



### 响应对象：状态码与响应头

#### 响应对象由 ServerResponse 创建

**创建来源**：res 是 http 服务器在收到请求时 **自动创建** 的 http.ServerResponse 实例，开发者通过回调的第二个参数拿到它，负责把数据写回客户端。

- 它与 req 一一对应：一次请求配一个 res，响应结束即该连接本次生命周期的产出阶段。
- res 既是可写流，也额外提供 **状态、头部** 等 HTTP 语义控制方法。
- 必须调用 **end** 显式结束响应，否则客户端会一直等待。

> res 不应被手动 new；它由 http 模块内部构造并注入回调，手工创建既无意义也无法关联到真实连接。

**速记**：res 随请求 **自动生成**，一一对应。



#### res.statusCode 直接赋值设置状态

**状态码属性**：res 上的 **statusCode** 是可读写数字属性，默认 200，赋值即可改变本次响应的状态，无需调用其他方法。

- 赋值是 **幂等** 的：在头未发送前反复赋值，以最后一次为准。
- 常见取值为 200、201、404、500 等三位数字。
- 也可在 **writeHead** 中一并指定，二者不应混用同一状态两次。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.url === "/missing") {
    res.statusCode = 404;
    res.end("not found");
    return;
  }
  res.statusCode = 200;
  res.end("hello");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 若既用 writeHead 设了状态又用 statusCode 赋值，后者在 writeHead 之前才有效；一旦头已发送，再改状态会触发 ERR_HTTP_HEADERS_SENT，详见常见坑一节。

**速记**：statusCode **直接赋数字**。



#### 常见状态码语义

**状态码体系**：三位数字状态由首位划分大类，记忆其语义是正确响应客户端的基础。

- **2xx 成功**：200 正常、201 已创建、204 成功但无内容返回。
- **3xx 重定向**：301 永久、302 临时、304 未修改（用缓存）。
- **4xx 客户端错误**：400 请求不合法、401 未认证、403 无权限、404 不存在、405 方法不被允许。
- **5xx 服务端错误**：500 内部错误、502 网关错误、503 服务不可用。

> 301 与 302 都触发跳转，区别在"永久"与"临时"，影响浏览器与搜索引擎的缓存策略；API 场景多用 302 或 307/308，避免被浏览器缓存错误。

**速记**：2 成功、3 跳转、4 客错、5 服崩。



#### res.statusMessage 与状态文本

**状态文本**：res 上的 **statusMessage** 是可读写字符串属性，存放随状态码返回的 **原因短语**（如 Not Found），默认按状态码自动推导。

- 不设置时 Node 会用标准短语填充，例如 404 对应 Not Found。
- 可手动覆盖，但客户端通常只看状态码，自定义短语价值有限。
- 它只能在 **头发送前** 设置，随 writeHead 或首段写入一起发出。

> HTTP/2 已不再携带原因短语，且多数框架与浏览器只依赖数字状态码；除非特殊协议要求，否则保持默认即可。

**速记**：statusMessage **可改、常默认**。



#### setHeader 设置响应头

**设头方法**：res 的 **setHeader(name, value)** 方法用于设置单个响应头，可 **多次调用** 设置不同头，值为字符串或字符串数组（同一头多个值）。

- 签名：setHeader(name, value)，name 是头名，value 是字符串或字符串数组。
- 多次对 **同一头名** 调用会覆盖前值；想发多个同名头须传数组。
- setHeader 设置的头会在 **头被发送时** 一并写出，不必立即落盘。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json; charset=utf-8");
  res.setHeader("X-Powered-By", "Node");
  res.end('{"ok":true}');
});

server.listen(3000, () => console.log("listening on 3000"));
```

> setHeader 接受大小写不敏感的头名，内部会规范化；但取值时建议用统一写法。它与 writeHead 的协同关系在后面专门比较。

**速记**：setHeader **可多次、同名为覆盖**。



#### getHeader 与 removeHeader

**读与删**：res 提供 **getHeader(name)** 读取已设置的响应头，以及 **removeHeader(name)** 删除尚未发送的头，二者都只能在头发送前使用。

- getHeader 签名：getHeader(name)，返回之前 setHeader 设的值；若从未设置则返回 undefined。
- removeHeader 签名：removeHeader(name)，把已排队但还没发出的头撤掉。
- 它们便于中间件或框架在最终发送前 **检查并调整** 头集合。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain");
  console.log(res.getHeader("Content-Type")); // text/plain
  res.removeHeader("Content-Type");
  res.end("done");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> getHeader 返回的可能是数组（当原值就是数组）而非永远字符串，使用时不要假定类型，必要时做归一化判断。

**速记**：getHeader **查**、removeHeader **撤**。



#### headersSent 判断是否已发送

**发送哨兵**：res 上的 **headersSent** 是只读布尔属性，指示 **响应头是否已发送给客户端**，是避免"重复写头"的关键判断依据。

- 头一旦随首次 write 或 writeHead 发出，headersSent 变为 true，此后任何 setHeader、writeHead、statusCode 改动都无效并可能报错。
- 在不确定头是否已发的分支里，先判断 if (!res.headersSent) 再安全地设头。
- 它常用于错误处理中间件，防止在已响应后再尝试写头。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.write("hello");
  console.log(res.headersSent); // true，因为首次 write 已触发头部发送
  res.end();
});

server.listen(3000, () => console.log("listening on 3000"));
```

> headersSent 只读不可赋值；试图写它会失败。它是"响应是否已出口"的真相来源，比自己维护标志更可靠。

**速记**：headersSent **只读、防重复写头**。



#### writeHead 与 setHeader 的配合与冲突

**二者关系**：res 的 **writeHead(statusCode[, statusMessage][, headers])** 可一次性设置状态码、状态文本与多个头，它与 setHeader 来自同一套头机制，但 **时机约束不同**。

- 调用顺序：先 setHeader 设头，再 writeHead 设状态与（可选）额外头，二者 **合并生效**。
- writeHead 一旦调用，头即 **立即发送**，之后 setHeader、getHeader 仍可查但不可再改已发头。
- 若 writeHead 已发头，再调用 setHeader 会抛出 **ERR_HTTP_HEADERS_SENT**，这就是下一节常见坑的成因之一。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain");
  // writeHead 会与上面的 setHeader 合并，并立即发送头
  res.writeHead(200, { "X-Mode": "demo" });
  res.end("merged headers");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 推荐统一风格：要么全程用 setHeader + 末尾 end，要么用一次 writeHead 包揽状态与头，混用易在边界处踩到已发送错误。

**速记**：先 set **后 writeHead** 合并，writeHead 后 **不能再设**。



### 响应体写入与响应头内容组合

#### res.write 可多次写入

**分块写入**：res 的 **write(chunk[, encoding][, callback])** 方法把一块数据写入响应体，且 **允许在结束前多次调用**，实现流式或分次输出。

- 签名：write(chunk, encoding, callback)，chunk 可为字符串或 Buffer，encoding 仅字符串时有效。
- 每次 write 会触发底层把数据发向客户端，多次 write 顺序即发送顺序。
- write 返回布尔值表示背压状态，false 时宜暂停后续写入，普通小响应可忽略。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.write("第一行\n");
  res.write("第二行\n");
  res.end("结束\n");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> write 多次调用时，第一次 write 会 **隐式触发响应头发送**（即 headersSent 变 true）。因此所有头必须在第一次 write 之前用 setHeader 设好。

**速记**：write **可多次、首写即发头**。



#### res.end 结束响应

**结束方法**：res 的 **end([chunk[, encoding]][, callback])** 方法结束响应，可选携带 **最后一段数据**，此后本次响应彻底关闭。

- 签名：end(chunk, encoding, callback)，chunk 可省略，只用于收尾最后一块。
- 调用 end 后，Node 会完成底层刷新并关闭响应，连接按 keep-alive 规则决定是否复用。
- 每个请求 **必须且只能调用一次 end**，否则客户端一直等待或后续写入失败。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("这是最后一段"); // 既写数据又结束
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：忘记调用 end 是新手最常见的"接口无返回"原因之一：服务端逻辑跑完却未结束响应，客户端请求就此挂起直到超时。

**速记**：end **收尾并关闭响应**。



#### 写入后再写的报错

**越界写入**：在已调用 end 之后继续调用 write 或 end，会抛出 **ERR_STREAM_WRITE_AFTER_END** 错误，因为可写流已结束。

- 该错误属于流的标准行为：结束态下任何写入都被视为非法。
- 常见于异步回调里忘了判断响应是否已结束，又触发了一次写入。
- 防护办法是写入前检查 **res.writableEnded** 或 res.headersSent，确保未结束再写。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("done");
  try {
    res.write("more"); // 抛出 ERR_STREAM_WRITE_AFTER_END
  } catch (err) {
    console.error(err.code); // ERR_STREAM_WRITE_AFTER_END
  }
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 真正的代码里不要靠 try/catch 兜底这种错误，而应在逻辑上保证"结束路径唯一"。多次可能写入的场景用 res.writableEnded 提前拦截。

**速记**：end 之后写 **抛 WRITE_AFTER_END**。



#### 必须调用 end 否则连接挂起

**挂起后果**：若处理完逻辑却 **始终不调用 end**，响应头与体都不会完整发出，客户端持续等待直至超时，连接被长期占用。

- 即使没有响应体要写，也必须调用一次 **无参 end()** 来收尾。
- 在异步分支多的代码里，要保证 **每个分支** 都有 end，避免某条路径漏写导致挂起。
- 连接挂起会消耗文件描述符与内存，高并发下可能拖垮整个服务。

> 把"确保 end"当作与"确保关闭文件"同等重要的纪律：可以用统一的响应封装函数，把所有出口汇聚到一处 end，降低漏写概率。

**速记**：不 end 就 **挂起占连接**。



#### Content-Type 与 charset

**内容类型头**：**Content-Type** 响应头声明返回体的 **媒体类型**，配合 **charset** 参数指明字符编码，是浏览器正确解析中文与选择渲染方式的前提。

- 常见取值：text/html; charset=utf-8、application/json; charset=utf-8、text/plain; charset=utf-8。
- **charset=utf-8** 必须显式写出，否则浏览器可能以本地默认编码解码中文，产生乱码。
- JSON 接口也建议带 charset，虽多数解析器按 utf8 处理，但声明更严谨。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/html; charset=utf-8");
  res.end("<p>中文内容</p>");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!CAUTION]
> **注意内容**：不写 charset 时浏览器的解码行为依赖默认设置，跨地域、跨浏览器结果不一致；凡含中文文本，charset=utf-8 是硬性要求。

**速记**：Content-Type **带 charset=utf-8**。



#### Content-Length 与分块传输

**长度头**：**Content-Length** 声明响应体的 **字节长度**，设了它浏览器可按长度精确接收；不设时 Node 默认采用 **分块传输编码（chunked）** 边发边知。

- 手动设 Content-Length 需精确等于 body 字节数，字符串要用 Buffer.byteLength 算，而非字符串长度（中文会算错）。
- 用 setHeader 设 Content-Type 并多次 write 时，Node **自动** 走分块传输，无需手工管理长度。
- 二者互斥：一旦显式设了 Content-Length，就不该再多次 write 导致长度不符。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  const body = "中文长度";
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.setHeader("Content-Length", Buffer.byteLength(body, "utf8"));
  res.end(body); // 长度必须与声明一致
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!CAUTION]
> **注意内容**：计算字节长度务必用 Buffer.byteLength(body, "utf8") 而非 body.length：后者按 JS 字符计，中文字符会让声明长度偏短，引发截断或客户端报错。

**速记**：长度用 **Buffer.byteLength** 算。



#### Location 配合重定向

**重定向头**：**Location** 响应头给出跳转目标地址，配合 **3xx 状态码** 即可让客户端自动跳转到新地址。

- 典型组合：res.statusCode = 302 再 res.setHeader("Location", "/login")。
- 301/302/307/308 都依赖 Location，区别在缓存与是否改方法。
- 设了 Location 后通常不再写响应体，或仅写极短提示文本。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.url === "/old") {
    res.statusCode = 302;
    res.setHeader("Location", "/new");
    res.end("redirecting...");
    return;
  }
  res.end("new page");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 302 是"临时"重定向，浏览器通常不缓存；若要永久迁移请用 301，但要警惕被浏览器长期缓存导致难以回滚。

**速记**：Location + **3xx = 跳转**。



#### Set-Cookie 多次设置

**会话头**：**Set-Cookie** 用于在响应里让客户端 **种下 Cookie**，且 **可多次调用 setHeader 或 writeHead 传数组** 来一次设置多个 Cookie。

- 每个 Cookie 写法：键=值，后接属性如 Path=/、HttpOnly、Max-Age=3600、Secure。
- Node 中可用 res.setHeader("Set-Cookie", [cookieA, cookieB]) 一次发多个。
- HttpOnly 与 Secure 等属性对安全很重要，详见第 31 篇身份认证。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Set-Cookie", [
    "sid=abc123; Path=/; HttpOnly",
    "theme=dark; Path=/"
  ]);
  res.end("cookies set");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> cookie 属性大小写不敏感但约定全小写或驼峰；Secure 要求 HTTPS 环境才会被浏览器接受，本地明文 HTTP 调试时该 Cookie 可能不生效。

**速记**：Set-Cookie **可多次、数组形式**。



#### Cache-Control 简介

**缓存头**：**Cache-Control** 是控制响应的 **客户端与中间代理缓存行为** 的核心头，用指令组合表达是否缓存、缓存多久。

- **no-cache**：需先校验再使用缓存；**no-store**：完全不缓存，适合敏感数据。
- **max-age=秒数**：资源可缓存的最长时间，如 max-age=3600 表示一小时。
- 静态资源常用 public, max-age=xxx 提升性能；带用户数据的接口常用 private, no-store。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Cache-Control", "public, max-age=3600");
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("cacheable for 1h");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> 缓存策略关系到正确性与性能的平衡：错误信息、用户私数据切勿被公共缓存；第 24 篇会结合 zlib 与 HTTP 缓存深入展开。

**速记**：Cache-Control **控缓存时效**。



### 乱码、重定向、错误处理与常见坑

#### 乱码问题的根源

**乱码本质**：中文乱码几乎都源于 **响应编码声明与真实编码不一致**——服务端按 utf8 写出，却没有告诉浏览器，浏览器便用本地默认编码解码。

- 响应必须显式声明 **Content-Type 带 charset=utf-8**，浏览器才以 utf8 解读。
- 文件读写与网络响应要 **统一编码**：读文件用 utf8，写响应也用 utf8，链路一致才不乱。
- 拼接 Buffer 时若先 toString 再相加，多字节字符被截断也会乱码，需先 concat 后解码。

> 若已设 charset=utf-8 仍乱码，检查点通常是：源数据本身编码就错、Buffer 截断拼接、或数据库连接返回了非 utf8 字符串。逐段核对编码来源即可定位。

**速记**：乱码 = **编码声明与真实不符**。



#### 302 重定向完整示例

**落地写法**：一个完整的 302 重定向，需要 **设置状态码、设置 Location、结束响应** 三步，顺序上先设头再 end。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  if (req.url === "/admin" && !(req.headers["cookie"] || "").includes("auth=")) {
    res.statusCode = 302;
    res.setHeader("Location", "/login");
    res.end("please login");
    return;
  }
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("welcome");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：重定向分支务必 **return**，避免继续执行后续写响应的代码；否则可能既发了 Location 又写了 body，触发重复响应错误。

**速记**：302 = **状态码 + Location + end + return**。



#### 404 与 500 的统一处理函数

**统一出口**：把 **404 未找到** 与 **500 内部错误** 抽成独立处理函数，让所有分支都汇聚到同一组响应逻辑，减少重复与漏写 end 的风险。

- 404 函数：设 statusCode 404，写 Content-Type 与提示，调用 end。
- 500 函数：设 statusCode 500，捕获异常后写错误提示，调用 end。
- 两者都应在 **头未发送** 时才写头，已发送则仅记录日志。

```js
const http = require("http");

function sendNotFound(res) {
  if (res.headersSent) return;
  res.statusCode = 404;
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("404 Not Found");
}

function sendError(res, err) {
  if (res.headersSent) {
    console.error(err);
    return;
  }
  res.statusCode = 500;
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("500 Internal Server Error");
}

const server = http.createServer((req, res) => {
  if (req.url === "/boom") {
    try {
      throw new Error("demo");
    } catch (err) {
      sendError(res, err);
      return;
    }
  }
  if (req.url === "/missing") {
    sendNotFound(res);
    return;
  }
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("ok");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!IMPORTANT]
> **重要内容**：统一函数里先判断 res.headersSent，是防止"错误发生在已写头之后"再次写头报错的护城河；这是生产代码的基本姿态。

**速记**：404/500 **抽函数、先判已发送**。



#### ERR_HTTP_HEADERS_SENT 成因与排查

**头已发送错误**：**ERR_HTTP_HEADERS_SENT** 在"**响应头已经发出后，又试图设置或写头**"时抛出，是最常见的 Node HTTP 运行时错误之一。

- 触发场景：已调用过 write 或 writeHead，再调用 setHeader、writeHead、或修改 statusCode。
- 也常因 **多个分支都写了响应** 却未 return，导致第二条写头路径被执行。
- 排查要点：搜索所有 res.write/end/setHeader/writeHead 调用，确认每个分支 **只走一条且及时 return**。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.end("first");
  // 下面这行会抛 ERR_HTTP_HEADERS_SENT，因为头已随上面的 end 发出
  res.setHeader("X-Extra", "oops");
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：防御性写法：任何写响应前都先 if (res.headersSent) return；把响应收口到统一函数（见上一节），能从结构上消除这类错误。

**速记**：头已发 **再设即报 HEADERS_SENT**。



#### 异步写响应顺序错乱

**异步竞态**：当响应写在 **多个异步回调** 中、且缺乏同步约束时，可能出现 **先 end 后 write** 或 **重复 end**，造成错乱与报错。

- 典型诱因：在 if/else 分支与 catch 里都写了 end，某个异步时序让两条路径都被执行。
- 后果包括 ERR_STREAM_WRITE_AFTER_END、ERR_HTTP_HEADERS_SENT，或客户端收到残缺响应。
- 解法：用 **单一响应函数 + 早 return**，或在写前用 res.writableEnded / res.headersSent 兜底判断。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  fetchSomething((err, data) => {
    if (err) {
      if (!res.headersSent) {
        res.statusCode = 500;
        res.end("error");
      }
      return; // 关键：错误分支结束，不再落入后续
    }
    if (!res.writableEnded) {
      res.end("data: " + data);
    }
  });
});

function fetchSomething(cb) {
  process.nextTick(() => cb(null, "ok"));
}

server.listen(3000, () => console.log("listening on 3000"));
```

> "先写后判断"胜于"先判断后写但分支发散"；把所有可能的出口汇聚到受限的响应函数，是消除异步顺序错乱最稳的工程实践。

**速记**：异步响应 **唯一出口最稳**。



#### 未消费请求体导致连接不释放

**连接泄漏**：对带请求体的请求 **既不读取也不销毁** req，可读流会一直等待数据，连接长期占用，最终耗尽服务器连接池。

- 表现：服务运行一段时间后 **新请求不再被处理**，netstat 可见大量 ESTABLISHED 挂起连接。
- 根因：Node 不会自动丢弃未读的 body，必须显式消费或调用 req.destroy() 终止。
- GET 等无 body 请求不受影响；风险集中在 POST/PUT/PATCH 等可能带体的方法。

```js
const http = require("http");

const server = http.createServer((req, res) => {
  // 即使不需要 body，也要消费掉，避免连接挂起
  req.on("data", () => {});
  req.on("end", () => {
    res.setHeader("Content-Type", "text/plain; charset=utf-8");
    res.end("body drained");
  });
  // 更省事的做法：直接 req.destroy() 若确定不要 body
});

server.listen(3000, () => console.log("listening on 3000"));
```

> [!WARNING]
> **警告内容**：在反向代理或框架层，往往会统一 drain 掉未读 body；自己写裸 http 服务器时务必记住：**要么读完，要么 destroy**，别让 req 悬空。

**速记**：body 不读 **就 destroy 或 drain**。
