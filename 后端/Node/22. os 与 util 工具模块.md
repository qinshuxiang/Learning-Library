## os 与 util 工具模块

### os 模块：操作系统信息的统一入口

#### os 是无需安装的内置核心模块

**os 模块**：是 Node.js 内置的**操作系统信息工具模块**，通过 require 引入后可直接调用，无需额外安装。

- 引入方式固定为常量 os = require("os")，模块名全小写，与模块文件名保持一致。
- 它封装了底层 libc 与操作系统调用，向开发者暴露**跨平台统一**的接口，屏蔽 Windows、macOS、Linux 的差异。
- 主要用途是**跨平台适配**（按平台走不同逻辑）与**资源监控**（读取 CPU、内存、系统负载）。

```js
const os = require("os");
console.log(typeof os.platform); // "function"
```

> os 与 path、fs 等同属运行时自带模块，凡以 require 引入却不报错、也不在 node_modules 中出现的，多为内置模块。os 直接对接系统，因此不同操作系统下返回的数据天然不同。

**速记**：os **内置直引**，专管**系统信息**。



#### os 的返回值多为平台相关字符串或数字

**平台相关性**：os 暴露的绝大多数方法其返回值**随操作系统而变**，同一段代码在 Windows 与 Linux 上可能拿到完全不同的结果。

- 平台标识、换行符、临时目录等返回值的差异是设计使然，用于在代码内做分支判断。
- 数值类结果（内存、运行秒数）单位统一为**字节**或**秒**，不与人类可读格式挂钩。
- 把 os 的数据用于持久化存储或跨机比较前，需先确认其所在平台的语义。

```js
const os = require("os");
console.log(os.EOL === "\n" ? "类 Unix 换行" : "Windows 换行");
```

> 切勿把 os 在不同机器上返回的临时目录路径硬编码进配置；该路径只在本机有效，换机即失效。os 提供的是"运行时探针"，而非"跨机约定"。

**速记**：os 数据**因机而异**，仅限**本机解读**。



#### os 与 process 获取信息的侧重不同

**职责区分**：os 关注**操作系统本身**的整体信息，process 关注**当前 Node 进程**自身的状态，二者互补而非替代。

- os 提供的是系统级事实（有几个核、系统内存多大、系统跑了多久）。
- process 提供的是进程级事实（本进程占多少内存、进程跑了多久、收到什么信号）。
- 凡是"系统整体"还是"单个进程"的疑问，先用这个边界判断该查 os 还是 process。

```js
const os = require("os");
console.log(os.totalmem());
console.log(process.memoryUsage().rss);
```

> 本篇紧接第 9 篇《process 进程对象》。那里已讲 process.platform、process.arch、process.uptime、process.memoryUsage，本篇会指出它们与 os 同名能力的**底层一致性**与**统计口径差异**，避免重复记忆。

**速记**：os 看**系统整体**，process 看**当前进程**。



### 平台、架构与系统版本

#### os.platform 返回平台标识字符串

**os.platform 方法**：返回标识当前操作系统平台的**小写字符串**，是跨平台分支判断最常用的依据。

- 完整写法为 os.platform()，调用时不需要任何参数，返回值直接是字符串。
- 常见返回值：darwin（macOS）、linux、win32（Windows）、freebsd、openbsd、android。

```js
const os = require("os");
console.log(os.platform()); // 例如 "darwin"

if (os.platform() === "win32") {
  console.log("走 Windows 专属逻辑");
}
```

> 注意 Windows 上返回的是 **win32** 而非 windows，这是历史命名（源于 32 位 Windows API），判断 Windows 务必比对 win32。该值与 process.platform 完全一致。

**速记**：platform 看**系统名**，Windows 比对 **win32**。



#### os.arch 返回 CPU 架构标识

**os.arch 方法**：返回标识当前 CPU 架构的**字符串**，反映 Node 二进制编译时的目标架构。

- 完整写法为 os.arch()，无参数，返回如 x64、arm、arm64、ia32、ppc64、s390x 等。
- 它描述的是**处理器指令集与位数**，与 platform 描述的操作系统是两个维度。

```js
const os = require("os");
console.log(os.arch()); // 例如 "arm64"
```

> arch 反映的是 Node 运行时自身的架构，在 Rosetta、兼容层等环境下**可能与物理 CPU 不符**（如在 Apple Silicon 上以 x64 模式运行 Node 时返回 x64）。需要真实物理架构应另寻系统接口。

**速记**：arch 看**CPU 架构**，未必等于**物理芯片**。



#### os.type、os.release、os.version 系统族与版本

**系统族与版本三元**：os.type 返回操作系统**名称**，os.release 返回**内核版本号**，os.version 返回**发行版层面的版本信息**，三者粒度不同。

- os.type 返回如 Linux、Darwin、Windows_NT，比 platform 更接近"系统族"文字。
- os.release 返回内核或系统版本，例如 Linux 下是内核版本、Windows 下是 10.0.19045 之类。
- os.version 在支持的系统上返回更友好的发行版描述（如 Debian 系、macOS 构建号），部分平台可能为空。

```js
const os = require("os");
console.log(os.type()); // 例如 "Darwin"
console.log(os.release()); // 例如 "23.5.0"
console.log(os.version()); // 例如 "Darwin Kernel Version 23.5.0"
```

> type 与 platform 容易混：type 偏"给人看的系统名"，platform 偏"给代码判断的标识"。通常跨平台逻辑用 platform，日志展示才用 type。release 与 version 在容器或裁剪系统上可能缺失，读取前应做空值兜底。

**速记**：type **系统名**、release **内核号**、version **发行描述**。



#### os 的平台信息底层与 process.platform 一致

**底层一致性**：os.platform、os.arch 等方法返回的数据，与 process.platform、process.arch **完全一致**，因为 process 的平台信息本就取自同一份系统探测结果。

- os.platform() 与 process.platform 在任意时刻返回相同字符串。
- os.arch() 与 process.arch 同样恒等，二者来源相同。
- 区别只在"调用姿势"：os 是模块方法需调用，process 是全局对象属性直接取。

```js
const os = require("os");
console.log(os.platform() === process.platform); // true
console.log(os.arch() === process.arch); // true
```

> 选 os 还是 process 纯属习惯：在已有 os 引用的文件里用 os.platform()，在只操作进程上下文的代码里用 process.platform 更顺手。语义上它们等价，不存在"谁更准"的差别。

**速记**：os 与 process **平台信息同源**，调用姿势不同。



### CPU、内存与资源监控

#### os.cpus 返回每个逻辑核的信息对象

**os.cpus 方法**：返回描述**每一个逻辑 CPU 核心**的对象数组，每个元素包含型号、主频与各类时间累计。

- 完整写法为 os.cpus()，无参数，数组长度即逻辑核数量。
- 每个元素包含 model（型号字符串）、speed（主频，单位 MHz 数字）、times（时间累计对象）。
- times 内部有 user（用户态毫秒）、nice（低优先级用户态毫秒）、sys（内核态毫秒）、idle（空闲毫秒）、irq（中断毫秒）。

```js
const os = require("os");
const cpus = os.cpus();
console.log("逻辑核数：" + cpus.length);
console.log("首核型号：" + cpus[0].model);
console.log("首核时间累计：" + JSON.stringify(cpus[0].times));
```

> times 各字段是**自系统启动以来的累计毫秒数**，单次读取只能看绝对量。要做利用率统计，需"间隔采样两次、相减得增量"再除以总时间，单看一次数值没有相对意义。

**速记**：cpus 每核**一对象**，times **累计毫秒**。



#### os.cpus().length 即逻辑核数，容器环境可能不准

**逻辑核数**：os.cpus().length 给出的是**逻辑处理器数量**（含超线程），据此可推断本机并行能力，但容器里可能失真。

- 它统计的是操作系统向 Node 暴露的逻辑核，超线程会让数值大于物理核。
- 在 Docker、Kubernetes 等容器环境中，若未限制 CPU 配额，可能返回宿主机的全部核数。

```js
const os = require("os");
const logicalCores = os.cpus().length;
console.log("可用逻辑核数：" + logicalCores);
```

> 容器场景的"不准"是真实陷阱：宿主机 64 核、容器限 2 核时，cpus 仍可能返回 64，导致你开 64 个工作线程反而拖垮邻居。生产部署应读取 cgroup 的 cpu quota 来确定真实配额。

**速记**：cpus 长度 = **逻辑核**，容器下**可能虚高**。



#### os.totalmem 与 os.freemem 返回系统字节数

**系统内存查询**：os.totalmem 返回**系统总物理内存字节数**，os.freemem 返回**当前空闲物理内存字节数**，二者单位都是字节。

- 完整写法为 os.totalmem() 与 os.freemem()，均无参数。
- 二者相减可粗略得到"已用内存"，但系统级缓存、缓冲区也计入占用，不精确等同于进程内存。
- 返回值是以字节为单位的整数，需自行换算成 MB、GB 才便于阅读。

```js
const os = require("os");
const total = os.totalmem();
const free = os.freemem();
console.log("总内存：" + total + " 字节");
console.log("空闲内存：" + free + " 字节");
console.log("内存使用率：" + ((1 - free / total) * 100).toFixed(1) + "%");
```

> totalmem/freemem 描述的是**整台机器**的内存，不是当前 Node 进程。多进程或容器混部时，空闲值会被其他进程大量消耗，据此判断"本进程还能不能申请内存"并不准确。判断「机器是否快满了」用 os.freemem，「进程是否内存泄漏」用 process.memoryUsage().heapUsed，二者不可互相替代。

**速记**：totalmem **系统总内存**，freemem **系统空闲内存**，memoryUsage **本进程内存**。



#### 封装 formatBytes 做字节可读化

**字节可读化**：os 与 process 返回的字节数都是裸整数，封装一个 formatBytes 函数把它转成带单位的可读字符串，是日志与监控里的常见需求。

- formatBytes 接收字节数与可选的小数位数，按 1024 进制在 B、KB、MB、GB、TB、PB 间选择单位。
- 先判断字节为 0 直接返回 0 B，再取以 1024 为底的对数确定单位下标。

```js
function formatBytes(bytes, decimals = 2) {
  if (bytes === 0) return "0 B";
  const k = 1024;
  const sizes = ["B", "KB", "MB", "GB", "TB", "PB"];
  const i = Math.floor(Math.log(bytes) / Math.log(k));
  return `${(bytes / Math.pow(k, i)).toFixed(decimals)} ${sizes[i]}`;
}

const os = require("os");
console.log("总内存：" + formatBytes(os.totalmem())); // 例如 "16.00 GB"
console.log("空闲：" + formatBytes(os.freemem())); // 例如 "3.42 GB"
console.log(formatBytes(2048)); // "2.00 KB"
```

> 该换算采用 1024 进制（KiB 严格应称二进制单位），与操作系统显示一致；若需按 1000 进制的 SI 单位，只需把 k 改为 1000。函数名 formatBytes 直述用途，避免缩写或 fn 之类无意义名。

**速记**：formatBytes **字节转单位**，1024 **进制换算**。



### 用户目录、网络接口与系统运行指标

#### os.homedir 与 os.tmpdir 用户目录与临时目录

**关键目录查询**：os.homedir 返回**当前用户主目录**的绝对路径，os.tmpdir 返回**操作系统临时目录**的绝对路径，二者都是跨平台获取标准路径的安全方式。

- 完整写法为 os.homedir() 与 os.tmpdir()，均无参数。
- homedir 常用于定位配置文件、下载目录、SSH 密钥等用户专属位置。
- tmpdir 用于存放临时文件、缓存、解压中间产物，避免硬编码 /tmp。

```js
const os = require("os");
const fs = require("fs");
console.log("主目录：" + os.homedir()); // 如 "/Users/why"
console.log("临时目录：" + os.tmpdir()); // 如 "/var/folders/.../T"

const tmpFile = os.tmpdir() + "/demo.tmp";
fs.writeFileSync(tmpFile, "临时内容");
```

> 硬编码 /tmp 在 Windows 上不存在、在 macOS 上是随机私有的，跨平台代码务必用 os.tmpdir() 而非写死路径。临时文件用后应主动清理，否则会随系统重启或累积占用磁盘。

**速记**：homedir **用户家**，tmpdir **系统临时**。



#### os.homedir 与环境变量 HOME 或 USERPROFILE 的关系

**主目录来源**：os.homedir 返回的正是环境变量 **HOME（类 Unix）或 USERPROFILE（Windows）** 所指向的目录，二者一致，但 os 写法跨平台更省心。

- 在 macOS、Linux 上，homedir 等价于 process.env.HOME 的值。
- 在 Windows 上，homedir 等价于 process.env.USERPROFILE 的值，而非 HOME。
- 用 os.homedir 可免去"按平台选不同环境变量名"的分支判断。

```js
const os = require("os");
console.log(os.homedir());
console.log(process.env.HOME);
console.log(process.env.USERPROFILE);
```

> 若环境变量被人为改写，os.homedir 会以改写后的值为准，因为它本就读取该变量。需要"真正的登录家目录"而怀疑环境变量被污染时，应改用 os.userInfo().homedir 等更权威的来源。

**速记**：homedir 即 **HOME/USERPROFILE**，跨平台**统一入口**。



#### os.networkInterfaces 返回网卡地址信息

**网络接口查询**：os.networkInterfaces 返回**按网卡名索引**的对象，每张网卡下挂着若干地址条目，用于获取本机 IP，尤其是局域网 IPv4。

- 完整写法为 os.networkInterfaces()，无参数，返回对象的键是网卡名（如 lo、eth0、en0）。
- 每个网卡对应一个数组，元素含 address（IP 地址）、family（IPv4 或 IPv6）、internal（是否回环）等字段。
- 过滤 internal 为 false 且 family 为 IPv4 的条目，即可拿到对外通信的本机局域网 IP。

```js
const os = require("os");
const interfaces = os.networkInterfaces();
for (const name of Object.keys(interfaces)) {
  for (const item of interfaces[name]) {
    if (item.family === "IPv4" && !item.internal) {
      console.log(name + " 的外网地址：" + item.address);
    }
  }
}
```

> internal 为 true 表示回环地址（如 127.0.0.1、::1），不能用于对外通信。一台机器往往有多张网卡、多个地址，取局域网 IP 时务必先做 internal 与 family 过滤，否则可能误选 Docker 网桥或回环地址。

**速记**：networkInterfaces **按卡索引**，取 IP 看 **internal 与 family**。



#### os.uptime 系统运行秒数与 process.uptime 区分

**系统运行时长**：os.uptime 返回**操作系统自启动以来经过的秒数**（浮点），与 process.uptime（进程存活秒数）是两个不同口径。

- 完整写法为 os.uptime()，无参数，返回系统开机到现在的秒数。
- 它反映的是**整台机器**的连续运行时间，不受 Node 进程重启影响。
- 与之相对，process.uptime 从 0 开始只算**当前 Node 进程**的寿命，参见第 9 篇。

```js
const os = require("os");
console.log("系统已运行：" + os.uptime().toFixed(0) + " 秒");
console.log("本进程已运行：" + process.uptime().toFixed(0) + " 秒");
```

> 二者极易混淆：问"服务器多久没重启"用 os.uptime，问"这个服务连续跑了多久"用 process.uptime。把 os.uptime 当成进程寿命或时间戳是常见误用。

**速记**：os.uptime **机器寿命**，process.uptime **进程寿命**。



#### os.loadavg 返回系统平均负载

**平均负载**：os.loadavg 返回**系统最近 1、5、15 分钟的平均负载**数组，是衡量系统繁忙程度、尤其 IO 等待的经典指标。

- 完整写法为 os.loadavg()，无参数，返回长度为 3 的数组，依次为 1 分钟、5 分钟、15 分钟负载。
- 负载数值含义随 CPU 核数而变：单核满载约 1.0，n 核满载约 n.0。
- 该指标在 Windows 上历史实现返回恒定低值，跨平台解读需留意。

```js
const os = require("os");
const [one, five, fifteen] = os.loadavg();
console.log("1 分钟负载：" + one);
console.log("5 分钟负载：" + five);
console.log("15 分钟负载：" + fifteen);
```

> 负载高既可能是 CPU 密集，也可能是 IO 等待（磁盘、网络阻塞），它不等同于 CPU 占用率。判断"是否过载"应把负载值除以 os.cpus().length 得到"每核负载"，再结合趋势分析，单看绝对值易误判。

**速记**：loadavg **1/5/15 分钟**，除以**核数**才准。



### 换行符、字节序、常量与错误码

#### os.EOL 平台换行符常量

**换行符常量**：os.EOL 是随平台而变的**换行符字符串常量**，在 Windows 上为回车换行，在其余系统上为换行，用于生成与平台一致的行尾。

- 它是一条不可调用的属性（字符串），直接取用，如 os.EOL。
- Windows 下值为 "\r\n"，macOS 与 Linux 下值为 "\n"。
- 拼接多行文本、写本地文件时优先用它，可避免跨平台行尾错乱。

```js
const os = require("os");
const lines = ["第一行", "第二行"].join(os.EOL);
console.log(JSON.stringify(lines));
```

> 与第 9 篇提到的 console.log 末尾自动追加平台换行是同一来源：底层都用了 os.EOL。若要把文件内容传给另一平台，建议显式统一换行符，而非依赖 EOL，否则在异平台上可能显示成连在一起的一行。

**速记**：EOL **平台换行**，Windows 是**回车换行**。



#### os.endianness 返回字节序

**字节序查询**：os.endianness 返回当前 CPU 的**字节序标识**，用于底层二进制处理的字节排列判断。

- 完整写法为 os.endianness()，无参数，返回 BE（大端）或 LE（小端）。
- 绝大多数现代消费级与服务器 CPU 为小端 LE，少数架构（如部分旧 PowerPC）为大端 BE。
- 在网络协议、二进制文件解析、Buffer 序列化时需要关心字节序，应用层业务通常无需关注。

```js
const os = require("os");
console.log(os.endianness()); // 常见 "LE"
```

> 字节序主要影响**手动拼装/解析二进制**的场景（如 Buffer 读写多字节整数）。Node 的 Buffer 已封装好读写方法，多数业务代码不必直接判断 endianness；一旦做跨平台二进制交换，才需确认双方字节序一致。

**速记**：endianness **BE/LE**，多数机器是 **LE 小端**。



#### os.constants 常量集合

**系统常量**：os.constants 是一组**操作系统级常量**的集合，涵盖信号、错误码、优先级等，供需要做底层系统交互时引用。

- 它是一个对象，常用子对象包括 signals（信号常量）、errno（错误码常量）、priority（调度优先级常量）等。
- 通过如 os.constants.signals.SIGINT、os.constants.errn.ENOENT 这类属性访问具体常量。

```js
const os = require("os");
console.log(os.constants.signals.SIGINT); // 如 2
console.log(os.constants.errno.ENOENT); // 如 34（文件不存在）
```

> 实际开发中直接用到 os.constants 的机会不多，多数场景使用 Node 已封装好的高层 API（如 fs 抛出的错误对象自带 code）。只有在对照底层错误码、处理信号底层逻辑时才需要查阅该集合。

**速记**：constants **系统常量集**，信号错误码**在其中**。



#### os.devNull 等特殊路径

**特殊设备路径**：os.devNull 返回当前平台的**空设备路径**，配合 os.homedir、os.tmpdir 等组成一组"平台相关的标准路径常量"。

- 它是一个字符串属性（非方法），Windows 下为 "\\\\.\\nul"，类 Unix 下为 "/dev/null"。
- 常用于把输出重定向到空设备、在测试或脚本里丢弃不需要的写入。
- 与它同族的还有 os.homedir、os.tmpdir、os.EOL，都是"跨平台取系统路径/符号"的便捷入口。

```js
const os = require("os");
const fs = require("fs");
console.log(os.devNull); // Windows："\\.\nul"，类 Unix："/dev/null"
fs.writeFileSync(os.devNull, "将被丢弃的内容");
```

> devNull 让"跨平台丢弃输出"不再写死路径。它本质是对系统特殊文件的抽象，和 os.tmpdir 一样属于"用 os 拿平台事实"的思路，而非业务配置。

**速记**：devNull **跨平台空设备**，丢弃写入**走它**。



### util 模块：Promise 化与回调化

#### util 模块面向开发者提供辅助工具

**util 模块**：是 Node.js 内置的**通用工具模块**，汇集了一批供开发者在日常编码中复用的辅助函数，无需安装。

- 引入方式固定为常量 util = require("util")，与 os 一样属于运行时自带模块。
- 它既包含**回调与 Promise 互转**工具，也包含**调试、格式化、类型判断**工具。
- 部分历史方法已废弃，官方推荐优先使用语言原生能力或新接口。

```js
const util = require("util");
console.log(typeof util.promisify); // "function"
console.log(typeof util.inspect); // "function"
```

> util 是"瑞士军刀"式的集合：东西杂但每样都小而常用。学习时按"Promise 化、调试输出、类型判断"三类记忆即可，不必逐方法背诵，用到再查官方文档。

**速记**：util **内置工具箱**，小而常用的**辅助函数**。



#### util.promisify 把回调风格函数转为 Promise

**util.promisify 方法**：把**遵循 Node 错误优先回调约定**的函数，包装成返回 Promise 的函数，从而能用 async/await 调用。

- 完整写法为 util.promisify(原函数)，返回一个新的、调用即返回 Promise 的异步函数。
- 仅对"回调签名是 (err, ...values)"的 Node 风格函数有效，回调首个参数是错误对象。
- 把 fs.readFile 这类回调 API 转成 Promise 版后，即可直接 await，告别嵌套回调。

```js
const util = require("util");
const fs = require("fs");

const readFileAsync = util.promisify(fs.readFile);

async function main() {
  const data = await readFileAsync(__filename, "utf8");
  console.log("文件长度：" + data.length);
}
main();
// 输出：文件长度：<本文件字符数>
```

> [!IMPORTANT]
> **重要内容**：promisify 只认**错误优先回调**约定：回调第一个参数是 err。若原函数的回调签名不是 (err, result)，promisify 会拿到错乱的结果甚至永远拿不到值。标准回调库（fs、dns、zlib 等）大多符合约定，自定义函数需先确认。

**速记**：promisify **回调转 Promise**，认准**错误优先约定**。



#### util.promisify.custom 自定义 Promise 化行为

**自定义 Promise 化**：util.promisify.custom 是一个**符号键**，给原函数挂上它，就能让 promisify 使用你自定义的 Promise 化逻辑，而非默认的错误优先转换。

- 完整用法为原函数[util.promisify.custom] = 一个返回 Promise 的函数；之后 util.promisify(原函数) 会优先使用它。
- 适用于原函数回调签名不符合标准、或你想返回多个值经特殊封装的场景。

```js
const util = require("util");

function legacyApi(arg, callback) {
  callback(null, { ok: true, arg });
}
legacyApi[util.promisify.custom] = function (arg) {
  return Promise.resolve({ ok: true, arg, wrapped: true });
};

const promised = util.promisify(legacyApi);
promised("x").then((r) => console.log(r));
// 输出：{ ok: true, arg: "x", wrapped: true }
```

> 自定义符号一旦设置，promisify 会**完全忽略**原函数原本的回调实现，改用你提供的 Promise 版。这要求你保证二者语义一致，否则调用方用 await 拿到的结果会和直接调回调时不同，造成隐性不一致。

**速记**：promisify.custom **自定义转换**，覆盖**默认行为**。



#### util.callbackify 把 async 函数转为回调风格

**util.callbackify 方法**：与 promisify 方向相反，它把**返回 Promise 的函数（或 async 函数）**包装成遵循错误优先回调约定的函数。

- 完整写法为 util.callbackify(原函数)，返回一个 (...args, callback) 形式的回调风格函数。
- 返回的回调风格函数，其最后一个参数仍是 (err, result) 形式的回调。
- 主要用于兼容性：把现代 async 代码接到只认回调的旧接口或老框架下运行。

```js
const util = require("util");

async function fetchUser(id) {
  return { id, name: "用户" + id };
}

const fetchUserCb = util.callbackify(fetchUser);
fetchUserCb(7, (err, user) => {
  if (err) throw err;
  console.log(user); // { id: 7, name: "用户7" }
});
```

> callbackify 对**被拒绝的 Promise** 有特殊处理：rejection 会作为回调的 err 参数传入，且若回调未处理该错误，它会以未捕获异常形式冒泡。与 promisify 配对使用，可在回调与 Promise 两套风格间双向桥接。

**速记**：callbackify **Promise 转回调**，与 **promisify 反向**。



### util 模块：调试、格式化与类型工具

#### util.inspect 把任意值转为调试字符串

**util.inspect 方法**：把**任意 JavaScript 值**转换成便于阅读的字符串，是 console.log 背后的核心实现，专为调试展示而设计。

- 完整写法为 util.inspect(待检查的值, 可选的配置对象)，返回字符串。
- 它对对象、数组、函数、循环引用都能给出结构化的文本表示。
- 处理循环引用时不会像 JSON.stringify 那样抛错，而是用 [Circular] 标注。

```js
const util = require("util");
const obj = { name: "demo", nested: { a: 1 } };
console.log(util.inspect(obj));
// 输出：{ name: 'demo', nested: { a: 1 } }

const circular = {};
circular.self = circular;
console.log(util.inspect(circular));
// 输出：{ self: [Circular] }
```

> 与 JSON.stringify 不同，inspect 能展示函数、Symbol、循环引用、不可枚举属性等 JSON 无法表达的内容，因此更适合调试而非数据交换。需要纯数据传输时仍应使用 JSON.stringify。

**速记**：inspect **值转调试串**，循环引用标 **[Circular]**。



#### util.inspect 的 depth、colors、showHidden 选项

**inspect 配置项**：util.inspect 的第二个配置对象支持 depth、colors、showHidden 等选项，用来控制展开深度、着色与是否显示隐藏属性。

- depth 控制对象**递归展开层数**，默认 2，设 null 表示无限展开。
- colors 为 true 时输出带 ANSI 颜色（终端友好），默认 false。
- showHidden 为 true 时连**不可枚举与 Symbol 属性**一并展示，默认 false。

```js
const util = require("util");
const deep = { a: { b: { c: { d: 1 } } } };
console.log(util.inspect(deep, { depth: 1 }));
console.log(util.inspect(deep, { depth: null, colors: true }));
```

> depth 默认只展开 2 层，深层对象会被折叠成 [Object]，调试时若看不到内部，先检查 depth 是否过小。colors 的颜色仅在**支持 ANSI 的终端**有效，写入文件或日志会留下转义符，生产日志应关掉。

**速记**：depth **控层数**，colors **终端着色**，showHidden **显隐藏**。



#### 对象自定义 inspect 方法与 console.log 的关系

**自定义展示**：对象若定义名为 Symbol.for("nodejs.util.inspect.custom") 的方法，util.inspect（以及 console.log 打印该对象时）会**优先调用它**来生成展示字符串。

- 该方法接收 (depth, inspectOptions) 参数，应返回一个字符串。
- 它让你控制复杂对象的调试输出形态，隐藏内部细节、只暴露关键信息。
- console.log 打印对象时内部正是调用 util.inspect，因此自定义 inspect 会一并生效。

```js
const util = require("util");
const inspect = Symbol.for("nodejs.util.inspect.custom");

class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }
  [inspect]() {
    return `Point(${this.x}, ${this.y})`;
  }
}

console.log(new Point(3, 4)); // 输出：Point(3, 4)
```

> 因为 console.log 底层调用 util.inspect，所以给类加上自定义 inspect 方法后，所有 console.log 输出都会变好看——这是 inspect 与 console 的**内部同源**关系。注意方法名必须用上述 Symbol，旧的 inspect 字符串键已被废弃。

**速记**：自定义 inspect **控输出形态**，console.log **内部同源**。



#### util.format 类 printf 的字符串格式化

**util.format 方法**：提供类似 C 语言 printf 的**占位符格式化**，把若干参数按占位符拼成字符串，是构建日志文本的趁手工具。

- 完整写法为 util.format(格式串, ...参数)，返回拼接后的字符串。
- 支持的占位符包括 %s（字符串）、%d 与 %i（整数）、%f（浮点）、%j（JSON）、%o 与 %O（对象）、%%（字面百分号）。
- 格式串里占位符数量少于参数时，多余参数会**以空格拼接追加**到末尾。

```js
const util = require("util");
console.log(util.format("%s 今年 %d 岁", "小明", 18));
// 输出：小明 今年 18 岁
console.log(util.format("%j", { a: 1 })); // 输出：{"a":1}
console.log(util.format("%s", "a", "b", "c")); // 输出：a b c
```

> %o 与 %O 都展示对象，区别在于 %o 省略部分不可枚举信息、%O 更完整；%j 在对象含循环引用时会输出 "[Circular]"。占位符与参数类型不符时，Node 会尽力做隐式转换，但结果未必符合预期，写入关键日志前应先验证。

**速记**：format **printf 式占位**，多余参数**末尾追加**。



#### util.types 做跨 realm 的类型判断

**util.types 集合**：提供一组**精细的类型判断方法**（如 isDate、isRegExp、isPromise、isTypedArray），用于比 instanceof 更可靠地识别内置对象类型。

- 它是一个对象，方法多为 util.types.isXxx(值) 形式，返回布尔值。
- 关键优势在于**跨 realm 可靠**：不同上下文（如 vm 模块、iframe）创建的同一类对象，instanceof 会失效，util.types 仍准确。
- 它覆盖了 Map、Set、ArrayBuffer、SharedArrayBuffer、WeakMap 等大量内置类型判断。

```js
const util = require("util");
console.log(util.types.isDate(new Date())); // true
console.log(util.types.isRegExp(/abc/)); // true
console.log(util.types.isPromise(Promise.resolve())); // true
console.log(util.types.isTypedArray(new Uint8Array(1))); // true
```

> 普通业务里对 Date、Array 用 instanceof 或原生方法（Array.isArray）通常够用；只有在**多 realm、vm 沙箱、序列化跨上下文**等场景，instanceof 因构造函数不同而失灵时，才必须用 util.types 来判断类型，它比对的是内部类型标签而非构造函数。

**速记**：util.types **类型判别**，跨 realm **比 instanceof 稳**。



#### util.deprecate 标记函数为已废弃

**util.deprecate 方法**：把任意函数**包装成"已废弃"版本**，调用时会向 stderr 打印一次废弃警告，用于温和地引导调用方迁移。

- 完整写法为 util.deprecate(原函数, 废弃说明文字)，返回包装后的新函数。
- 同一进程内**默认只打印一次**警告，避免海量日志刷屏。
- 说明文字通常写明替代方案（如"请改用新方法"），便于调用方跟进。

```js
const util = require("util");

function oldApi() {
  return "旧实现";
}
const deprecatedApi = util.deprecate(oldApi, "oldApi 已废弃，请改用 newApi");

deprecatedApi();
deprecatedApi(); // 警告默认只打印一次
// 首次调用输出：(node:xx) DeprecationWarning: oldApi 已废弃，请改用 newApi
```

> deprecate 只负责"提醒"，不会阻止函数继续执行，旧逻辑照常运行。它适合在版本过渡期标记即将下线的接口；若想真正移除，需后续版本删除该函数。警告经由 process 的弃用警告机制，可被 --no-deprecation 等启动参数抑制。

**速记**：deprecate **标记废弃**，调用**打印一次警告**。



#### util.inherits 与 util.isDeepStrictEqual

**两个实用方法**：util.inherits 用于**基于原型的继承**（现代代码应改用 class extends），util.isDeepStrictEqual 用于**深度严格相等比较**，二者定位不同。

- util.inherits(子类构造函数, 父类构造函数) 把父类原型挂到子类原型链上，是 ES5 时代的继承写法。
- util.isDeepStrictEqual(值一, 值二) 递归比较两值是否在结构与类型上完全相等，返回布尔值。

```js
const util = require("util");

function Animal(name) { this.name = name; }
function Dog(name) { Animal.call(this, name); }
util.inherits(Dog, Animal);

console.log(util.isDeepStrictEqual({ a: 1 }, { a: 1 })); // true
console.log(util.isDeepStrictEqual({ a: 1 }, { a: "1" })); // false（类型不同）
```

> util.inherits 与 ES6 的 class extends 等价但更晦涩，官方文档也建议新代码用 class。isDeepStrictEqual 比 == 或 === 更深、比简单 JSON 比较更严格（区分类型、处理循环引用），是 assertions 库常用底层能力。

**速记**：inherits **旧式继承**（用 class 替代），isDeepStrictEqual **深度严格比**。



#### 已废弃的旧方法与原生替代方案

**废弃清单**：util 早期提供的一批类型判断方法（如 util.isArray、util.isDate、util.isRegExp）**已被废弃**，官方统一推荐使用语言原生能力替代。

- 迁移指引：util.isArray 改用原生 Array.isArray；util.isDate、util.isRegExp 等改用 util.types 对应方法或 instanceof，用法与适用场景详见前文「util.types 做跨 realm 的类型判断」一节。

**速记**：旧 util.isXxx **已废弃**，改用 **原生 / util.types**。
