## 性能剖析方法论与工具全景

### 指标先行

#### 三个维度定义「慢」

**性能问题必须先量化再动手**：延迟、吞吐、资源三个维度的指标定了，「慢」才有可比较的定义。

- **延迟（Latency）**：看分位数不看平均值——P95、P99 反映最差体验，平均值会掩盖长尾（10% 的 5 秒请求被 90% 的快请求摊平）。
- **吞吐（Throughput）**：单位时间处理请求数（RPS），与延迟互为约束（第 39 章的容量关系）。
- **资源**：CPU 使用率、内存（`heapUsed` 趋势）、**事件循环延迟**——Node 特有的第四类指标，事件循环被阻塞时 CPU 不高、内存正常，服务照样「卡死」。

```js
// 用 perf_hooks 测量事件循环延迟：平均延迟持续大于几十毫秒即有阻塞任务
const { monitorEventLoopDelay, performance } = require("perf_hooks");
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  console.log("事件循环 P99:", h.percentile(99) / 1e6, "ms");   // 纳秒转毫秒
  h.reset();
}, 5000).unref();
```

> 排查顺序的铁律是**先定位维度再选工具**：CPU 高走 CPU 剖析（第 38 章），内存涨走堆分析（第 37 章），CPU 与内存都正常但延迟高——大概率是事件循环阻塞或下游依赖慢，本篇的工具定位这里。

**速记**：性能三指标 **延迟分位数、吞吐、事件循环延迟**，先定维度再选工具。



### 工具全景

#### 内置观测与外部工具箱

**工具选型的路径**：从零成本的内置 API 起步，定位到问题类别后再上重量级工具，避免一上来就全套武装。

- **内置轻观测**：`process.memoryUsage()`（内存快照数字）、`process.cpuUsage()`、`perf_hooks`（事件循环与耗时打点）、`process.getActiveResourcesInfo()`（当前活跃的句柄类型）。
- **`node --inspect`＋Chrome DevTools**：Profiler、Memory 面板全功能可用，适合开发环境复现问题。
- **clinic 套件**（`clinic doctor`／`clinic flame`）：自动压测并生成诊断报告与火焰图，第 38 章的主战场。
- **`node --prof`＋火焰图**：V8 采样的标准流程，CPU 类问题的最终定位手段。
- **0x**（npm 包）：一条命令生成交互式火焰图，比 `--prof`＋speedscope 的手工链路省事。

> 工具的分工地图：**「哪里慢」用 clinic doctor 判断类别，「为什么慢」用火焰图或堆快照定位代码**。两层工具别混着用——火焰图解决不了「该不该测内存」的问题。

**速记**：内置 API 定维度，**clinic 定类别，火焰图/堆快照定代码**。



### 生产环境观测

#### 线上问题的取证手段

**生产环境不能随便上 Profiler**：CPU 采样与堆快照本身消耗资源，用法不对会压垮已带病的服务。

- **日志与指标先行**：结构化日志（第 33 章的约定）＋ 事件循环延迟、内存趋势的持续上报，多数问题靠曲线就能定位到「何时开始、与何事件相关」。
- **按需取证**：症状出现时再触发采样——`kill -USR1` 触发 inspector（配合端口隧道接 DevTools），或代码内限时开启 `Session` 采样堆快照，采完即停。
- **环境一致性**：本地能复现的不要去生产取证；压测环境（同等数据量级）是第 38 章工具的主场，生产只留观测与应急。

```js
// 应急堆快照：通过管理接口在故障时刻触发，采完自动落盘
if (req.url === "/__debug/heapdump") {
  const inspector = require("inspector");
  const fs = require("fs");
  const session = new inspector.Session();
  session.connect();
  session.post("HeapProfiler.takeHeapSnapshot", (err, { result }) => {
    fs.writeFileSync(`/tmp/snap-${Date.now()}.heapsnapshot`, result);
    session.disconnect();
  });
}
```

> 生产取证的纪律是**「观测常开、采样按需、快照即删」**：常开的只有低成本指标，采样工具留给故障时刻，堆快照文件（可能几百 MB）取证完立刻清理。把 DevTools 长期挂在生产进程上属于反操作。

**速记**：生产 **指标常开、采样按需、快照即删**，本地能复现就别去线上取证。
