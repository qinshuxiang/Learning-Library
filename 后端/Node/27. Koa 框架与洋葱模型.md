## Koa 框架与洋葱模型

### Koa 的定位与历史

#### Koa 由 Express 原班团队打造

**Koa**：是由 **Express 原班开发团队** 在 Express 之后推出的新一代 Web 框架，定位为更轻、更现代的继任者。

- Koa 与 Express 出自同一批核心维护者，对 Express 中间件写法的痛点有切身体会。
- 设计目标是用更优雅的方式组织中间件，把控制权与灵活性交还给开发者。
- Koa 不追求覆盖 Express 的全部功能，而是提供一块极简的内核。

> Koa 并非 Express 的升级版，而是团队另起炉灶的"下一代"思路：保留经验、舍弃历史包袱。二者长期并存，选型取决于团队偏好与既有资产。

**速记**：Koa 是 **Express 团队** 的轻量新作。



#### Koa 更小更轻、内核不捆绑中间件

**Koa 的内核**：是一个 **几乎为空的应用骨架**，只负责创建服务、串联中间件、提供 Context，其余能力全部外置。

- Koa 的安装体积与运行占用都明显小于 Express，核心代码量以千行计。
- 路由、静态文件托管、请求体解析、模板渲染等都不在内核中，需单独安装社区中间件。
- 这种"小而美"的设计让每个项目只引入自己真正需要的部分，依赖更可控。

> Express 把大量中间件内置进框架，开箱即用但体积偏大；Koa 反其道而行，把选择权交给开发者。代价是新手需要自行拼装，上手门槛略高。

**速记**：Koa 内核 **只管串联**，其余 **按需外挂**。



### Koa 与 Express 的核心差异

#### 中间件模型不同：洋葱模型对比线性

**中间件模型**：Koa 采用 **洋葱模型**，请求像穿过一层层包裹后原路返回；Express 是 **线性串联**，每个中间件处理完即交给下一个，缺少"返回阶段"。

- Koa 的中间件通过调用 next 进入下游，下游完成后代码会回到当前中间件 next 之后的位置。
- Express 的中间件也有 next，但典型的业务逻辑在 next 之前一次执行完，缺少对称的"回程"结构。
- 洋葱模型让"请求进入时"与"响应返回时"的逻辑天然分离，适合做日志、计时、兜底。

> Express 也能通过嵌套或 next 之后的代码近似实现回程，但并非语言级约定，容易写得混乱。Koa 把"等待下游完成"做成 await next 的语法结构，意图一目了然。

**速记**：Koa 是 **洋葱回程**，Express 是 **线性穿过**。



#### 异步写法不同：async/await 对比回调

**异步写法**：Koa **原生依赖 async/await**，中间件本身就是异步函数；Express 历史上以 **回调函数** 驱动，异步易陷入层层嵌套。

- Koa 要求 Node 7.6 及以上，正是从该版本起 async 函数成为语言标配，框架与语言特性同步。
- Koa 中间件内可用 await 直接等待任意异步操作，错误处理用 try/catch 即可。
- Express 的经典回调风格中，异步结果通过回调传出，串联多个异步会形成回调嵌套。

> Express 4 之后也支持 async 函数式中间件，但框架的初始化、错误处理等仍保留回调痕迹。Koa 从第一行代码起就为 async 设计，风格更统一。

**速记**：Koa **生而 async**，Express **起于回调**。



#### Context 对象替代 req 与 res

**Context（上下文）**：是 Koa 为 **每一次请求响应** 创建的专属对象，把 Node 原生的 req 与 res 收拢到一个 ctx 上统一访问。

- 在 Koa 中间件里拿不到 Express 那样的独立 req、res 形参，取而代之的是唯一的 ctx。
- 读请求用 ctx.request（Koa 抽象）或 ctx.req（原生），写响应用 ctx.response（Koa 抽象）或 ctx.res（原生）。
- ctx 贯穿整个洋葱，所有中间件共享同一个实例，便于在层间传递数据。

> 把 req 与 res 合并为 ctx，避免了在多个中间件间反复传递两个对象。代价是习惯了 Express 解构写法的开发者需要重新适应单一入口。

**速记**：Koa 用 **ctx 一统** req 与 res。



#### Koa 不内置路由与模板

**内置能力**：Koa **不提供路由与模板引擎**，这两项与静态托管、请求体解析一样，都需要安装独立的中间件。

- 路由由 koa-router 等社区包承担，Express 的 app.get、app.post 在 Koa 里不存在。
- 模板渲染由 koa-views 承担，Express 的 res.render 在 Koa 里不存在。
- 静态文件与请求体解析同样外置，开发者按需装配整条请求处理链。

> 这不是缺陷而是取舍：内置越多，框架越重、越难裁切。Koa 把"要不要""用哪个"的决定权完全留给项目。

**速记**：Koa **裸内核**，路由模板 **靠外挂**。



### 最小应用：从零启动一个 Koa 服务

#### 安装 koa 并创建实例

**创建实例**：通过 **new Koa()** 构造一个应用对象，它是后续注册中间件与启动监听的入口。

- 安装命令为 npm install koa，安装后通过 require("koa") 或对应的 ESM 导入方式引入 Koa 构造函数。
- 调用 new Koa() 得到的实例通常命名为 app，代表整个 Web 应用。
- Koa 需运行在 Node 7.6 以上，因为中间件使用 async 函数语法。

```bash
npm install koa
```

```js
const Koa = require("koa");
const app = new Koa();
// app 即为 Koa 应用实例，后续中间件都挂在它上面
```

> 若你的 Node 版本低于 7.6，运行 Koa 中间件会报语法错误，根因是 async 函数不被支持，而非 Koa 安装问题。请先升级 Node 运行环境。

**速记**：new Koa() 拿到 **app 入口**。



#### app.use 注册中间件、app.listen 启动

**注册与启动**：中间件用 **app.use(middleware)** 登记，服务用 **app.listen(port)** 在指定端口开始监听。

- app.use 的参数是一个中间件函数，类型为 async (ctx, next) 或普通函数；多个中间件按注册顺序嵌套成洋葱。
- app.listen 的参数与 Node 原生 http 服务的 listen 一致，常见写法是 app.listen(3000) 监听 3000 端口。
- app.listen 本质上内部创建了 http 服务并把请求交给 Koa 处理，返回值即底层的 http.Server。

```js
const Koa = require("koa");
const app = new Koa();

app.use(async (ctx, next) => {
  console.log("收到请求");
  await next();
});

app.listen(3000, () => {
  console.log("服务已启动在 3000 端口");
});
```

> app.listen 的第一个参数是端口号，第二参数是就绪回调。它与 Express 的 app.listen 用法几乎一致，迁移时这部分代码基本可直接复用。

**速记**：app.use 挂 **中间件**，app.listen 开 **端口**。



#### ctx.body 赋值即响应

**响应输出**：向 **ctx.body** 赋值的那一刻，Koa 就把该值当作 HTTP 响应体返回给客户端。

- ctx.body 可以赋字符串、对象、Buffer、流等多种类型，Koa 自动按类型设置合适的响应。
- 赋对象时 Koa 自动序列化为 JSON 并把 Content-Type 设为 application/json，无需手动处理。
- 一旦给 ctx.body 赋值，当前中间件若无下游或下游执行完毕，响应即发送。

```js
const Koa = require("koa");
const app = new Koa();

app.use(async (ctx) => {
  ctx.body = "你好，Koa";
});

app.listen(3000);
```

> 与 Express 的 res.send 不同，Koa 没有独立的"发送"动作，赋值即发送。多次给 ctx.body 赋值，以最后一次为准；若始终不赋值，响应体为空。

**速记**：ctx.body 一赋值，响应 **就发出**。



### Context 对象 ctx 全貌

#### ctx 封装原生 req 与 res

**ctx 封装**：是 Koa 把 **Node 原生请求与响应对象** 统一收口后，提供给中间件使用的请求上下文。

- 每次请求到达，Koa 都会新建一个 Context 实例，并在整条洋葱链中作为唯一参数传递。
- ctx 上同时挂着 Koa 的抽象层与 Node 的原生层，开发者可按需取用。
- 由于 ctx 贯穿所有中间件，把它作为层间数据通道比闭包更直观。

> ctx 是"一次请求一个实例"的对象：并发的多个请求各自拥有独立 ctx，互不干扰。这也是为什么中间件里挂数据优先用 ctx.state，而不是模块的全局变量。

**速记**：ctx 是 **一次请求一实例** 的上下文。



#### ctx.request 与 ctx.response 是 Koa 抽象

**Koa 抽象层**：ctx.request 与 ctx.response 是 **Koa 在原生对象之上封装** 的友好接口，屏蔽了底层差异。

- ctx.request 提供 query、body、header 等便捷属性，读起来比原生 req 更顺手。
- ctx.response 提供 body、status、type、set 等赋值方法，写响应集中于这一处。
- 抽象层对 Node 不同版本的原生差异做了抹平，业务代码更少受运行环境影响。

> 抽象层的属性大多是"语法糖"：读 ctx.request.query 等价于读经过 Koa 解析后的查询对象。优先用抽象层，代码更简洁、可移植性更好。

**速记**：ctx.request/response 是 **好用的抽象层**。



#### ctx.req 与 ctx.res 是原生对象

**原生对象**：ctx.req 与 ctx.res 就是 **Node http 模块的原生 IncomingMessage 与 ServerResponse**，只在需要底层能力时直接使用。

- ctx.req 是未经 Koa 加工的原生请求，拥有 socket、connection 等底层字段。
- ctx.res 是原生响应，理论上可直接调用其 end 方法，但 Koa 不推荐混用。
- 绝大多数业务场景用 ctx.request 与 ctx.response 即可，原生对象留给特殊需求。

> 一旦直接操作 ctx.res（如手动 end），Koa 无法再掌控响应流程，会与 ctx.body 赋值产生冲突。这是常见坑，后文专门说明。

**速记**：ctx.req/res 是 **原生底层对象**。



#### 常用属性 ctx.method、ctx.url、ctx.path、ctx.query、ctx.headers、ctx.state

**常用属性**：ctx 上有一组 **高频读取请求信息** 的便捷属性，覆盖方法、路径、查询与自定义状态。

- **ctx.method（字符串）**：当前请求的 HTTP 方法，如 GET、POST，用于路由与条件分支。
- **ctx.url（字符串）**：完整的请求地址（含查询串），常用于日志记录与转发。
- **ctx.path（字符串）**：去掉查询串后的路径部分，路由匹配最常依赖它。
- **ctx.query（对象）**：解析后的查询参数对象，如 ?a=1 得到 { a: "1" }。
- **ctx.headers（对象）**：请求头键值对，读取客户端传递的元信息。
- **ctx.state（对象）**：Koa 推荐的**层间数据容器**，下游中间件把结果挂在 ctx.state 上供上游取用。

```js
app.use(async (ctx) => {
  const method = ctx.method;
  const path = ctx.path;
  const keyword = ctx.query.keyword;
  ctx.state.visited = true;
  ctx.body = { method, path, keyword };
});
```

> ctx.query 的值永远是字符串类型，?page=2 得到 { page: "2" } 而非数字。需要数字时必须自行转换，否则参与运算会触发隐式类型拼接。

**速记**：method/url/path/query/headers 读请求，**state** 传数据。



### 响应设置：从 ctx.body 到 ctx.redirect

#### ctx.body 支持多种类型

**响应体类型**：ctx.body 可接收 **字符串、对象、Buffer、流** 四类值，Koa 按类型自动决定序列化与 Content-Type。

- 赋字符串：原样返回，Content-Type 默认为 text/plain; charset=utf-8。
- 赋对象或数组：自动 JSON 序列化，Content-Type 设为 application/json。
- 赋 Buffer：按二进制返回，常用于文件下载或图片透传。
- 赋流（如 fs.createReadStream）：Koa 以流式管道回写，适合大文件避免占内存。

```js
app.use(async (ctx) => {
  if (ctx.path === "/json") {
    ctx.body = { ok: true, list: [1, 2, 3] };
  } else {
    ctx.body = "普通文本响应";
  }
});
```

> 同一个请求里 ctx.body 只能有一个最终值，后赋值覆盖前赋值。若同时赋值对象又调用 ctx.body = 流，以最后一次为准，前面白费。

**速记**：ctx.body 认 **字符串/对象/Buffer/流**。



#### ctx.status 设置状态码

**状态码**：ctx.status 用于 **设置 HTTP 响应状态码**，直接赋数字即可，如 200、404、500。

- 默认状态码为 404，只要给 ctx.body 赋了非空值，Koa 会自动改为 200。
- 赋值时用数字，读取值得到数字：ctx.status 与 ctx.response.status 等价。
- 配合 ctx.message 可设置对应的状态描述文本，可不设，使用默认值。

```js
app.use(async (ctx) => {
  if (ctx.path === "/missing") {
    ctx.status = 404;
    ctx.body = { error: "资源不存在" };
  } else {
    ctx.status = 200;
    ctx.body = "正常";
  }
});
```

> 状态码与响应体是两件独立的事：设了 404 也必须给 ctx.body，否则响应体可能为空，客户端只收到状态码。

**速记**：ctx.status 写 **数字状态码**。



#### ctx.set 设置响应头

**响应头**：ctx.set(name, value) 用于 **向响应中添加或修改 HTTP 头**，可一次设一个或传入对象批量设置。

- 单头写法 ctx.set("X-Powered-By", "Koa")，传入字段名与字段值两个参数。
- 多头写法 ctx.set({ "Cache-Control": "no-cache", "X-Trace-Id": id })，一次传入键值对对象。
- 读取已设响应头用 ctx.get(name) 或 ctx.response.get(name)。

```js
app.use(async (ctx, next) => {
  await next();
  ctx.set("X-Response-Time", "12ms");
  ctx.set("X-Powered-By", "Koa");
});
```

> 响应头应在响应体发送前设置。由于洋葱模型中"发送"发生在下游完成后，把 ctx.set 写在 await next 之后，能确保头与最终响应体一起发出。

**速记**：ctx.set 写 **响应头**。



#### ctx.type 设置 Content-Type

**内容类型**：ctx.type 用于 **声明响应体的 MIME 类型**，能自动补全字符集等细节，免去手写完整头。

- 赋扩展名写法 ctx.type = "html"，Koa 自动展开为 text/html; charset=utf-8。
- 赋完整 MIME 写法 ctx.type = "application/json"，适用于非标准或自定义类型。
- 多数情况下无需手动设置：赋字符串默认可文本，赋对象默认 JSON。

```js
app.use(async (ctx) => {
  if (ctx.path === "/page") {
    ctx.type = "html";
    ctx.body = "<h1>标题</h1>";
  } else {
    ctx.type = "json";
    ctx.body = { msg: "ok" };
  }
});
```

> 手动设置 ctx.type 会覆盖 Koa 依据 ctx.body 自动推断的结果。若既赋对象又手动设成 text/html，客户端会收到 JSON 却被标成 HTML，解析即错。

**速记**：ctx.type 定 **MIME 类型**。



#### ctx.redirect 重定向

**重定向**：ctx.redirect(url, alt) 用于 **向客户端发出 302 跳转**，把浏览器导向目标地址。

- 基本写法 ctx.redirect("/login")，默认状态码为 302 Found。
- 需要永久跳转时先设 ctx.status = 301，再调用 ctx.redirect(target)。
- 第二个可选参数 alt 用于无法跳转时回退显示的地址，通常省略。

```js
app.use(async (ctx) => {
  if (ctx.path === "/admin" && !ctx.state.user) {
    ctx.redirect("/login");
    return;
  }
  ctx.body = "后台首页";
});
```

> ctx.redirect 同样依赖 ctx.body 的发送机制，调用后通常紧跟 return 以免后续代码又给 ctx.body 赋值覆盖跳转。忘记 return 是常见错误。

**速记**：ctx.redirect 发 **302 跳转**。



### 洋葱模型：中间件执行顺序

#### 中间件签名为 async (ctx, next)

**中间件签名**：Koa 中间件统一是 **async (ctx, next) 形式** 的函数，ctx 是上下文，next 是进入下游的句柄。

- ctx 携带本次请求的全部信息，next 是一个返回 Promise 的函数，调用它才会把控制权交给下一个中间件。
- 用 async 声明是因为 next 返回 Promise，必须用 await 等待其完成才能拿到"下游返回后"的时机。
- 若中间件不需要进入下游（如直接收尾响应），可以不接收 next 参数。

```js
async function loggerMiddleware(ctx, next) {
  console.log("进入");
  await next();
  console.log("离开");
}
```

> 即使不接收 next，只要不调用它，下游中间件就不会执行。next 是"继续向下"的开关，不是自动触发的。

**速记**：中间件 = **async (ctx, next)**。



#### await next() 前后代码的执行时机

**执行时机**：**await next() 之前的代码在请求进入时执行，之后的代码在响应返回时执行**，二者夹住下游整段处理。

- 请求自外向内穿透：最先注册的中间件，其 next 之前的代码最先运行。
- 遇到 await next() 后暂停，把控制权交给下一个中间件，直到最内层不再调用 next。
- 最内层处理完，逐层回到上游，执行各自 next 之后的代码，响应自内向外返回。

> 这个"进一层、等返回、再出一层"的过程像穿过洋葱：每一层都被进入一次、离开一次。理解它，就理解了 Koa 全部中间件行为的时序基础。

**速记**：next 前 **进**，next 后 **出**。



#### 三中间件演示执行顺序

**顺序演示**：用 **三个依次注册的中间件**，可以完整看到 1 进、2 进、3 进、3 出、2 出、1 出 的对称输出。

```js
const Koa = require("koa");
const app = new Koa();

app.use(async (ctx, next) => {
  console.log("1 进");
  await next();
  console.log("1 出");
});

app.use(async (ctx, next) => {
  console.log("2 进");
  await next();
  console.log("2 出");
});

app.use(async (ctx, next) => {
  console.log("3 进");
  ctx.body = "done";
  console.log("3 出");
});

app.listen(3000);
```

访问一次服务，控制台按如下顺序打印：

```text
1 进
2 进
3 进
3 出
2 出
1 出
```

> 第三个中间件没有调用 next，是因为它已经设置 ctx.body 完成响应，没有更下游需要进入。若它仍调用 next 而后面已无中间件，Koa 会正常结束，不会报错。

**速记**：顺序即 **1进2进3进3出2出1出**。



### 洋葱模型的实际价值

#### 统计响应耗时

**响应计时**：在 **中间件的 next 前后分别打点**，二者时间差即为下游（含自身）处理所耗时长。

- 进入前记录开始时间，await next() 之后记录结束时间，相减得到耗时。
- 把耗时写入响应头或日志，便于监控慢接口、定位性能瓶颈。
- 放在最外层中间件，能统计整条处理链的累计耗时。

```js
async function responseTimeMiddleware(ctx, next) {
  const start = Date.now();
  await next();
  const cost = Date.now() - start;
  ctx.set("X-Response-Time", cost + "ms");
}
```

> 计时中间件必须 await next()，否则拿到的是"还没处理完"的瞬时时间，毫无意义。这也是洋葱模型"回程"价值的直接体现。

**速记**：next 前后 **掐表计时**。



#### 统一错误处理

**错误兜底**：用 **最外层中间件的 try/catch 包裹 await next()**，可捕获下游任意中间件抛出的异常并统一响应。

- 把 try 包住 await next()，catch 里设 ctx.status 与 ctx.body 给出友好错误。
- 下游业务代码只需正常抛错，不必每处都写错误处理，责任上移集中。
- 配合 ctx.app.emit("error", err, ctx) 还能把错误转交全局监听做日志记录。

```js
async function errorHandlerMiddleware(ctx, next) {
  try {
    await next();
  } catch (err) {
    ctx.status = err.status || 500;
    ctx.body = { error: err.expose ? err.message : "服务器内部错误" };
    ctx.app.emit("error", err, ctx);
  }
}
```

> 没有这层兜底时，下游抛错会让 Koa 直接回 500 且响应体为空，客户端拿不到任何线索。统一兜底既保护体验，也便于上报。

**速记**：外层 try/catch **兜住下游错**。



#### 下游完成后追加响应头

**后置增强**：在 **await next() 之后追加响应头或收尾逻辑**，可确保增强作用于下游最终产生的响应。

- 典型做法：进入前记时间、放行下游、返回后补 X-Response-Time、X-Trace-Id 等头。
- 也可以在此统一压缩、统一追加安全头，无需每个业务中间件关心。
- 因为此时 ctx.body 通常已确定，追加头不会干扰响应体本身。

```js
async function headerEnhancerMiddleware(ctx, next) {
  await next();
  ctx.set("X-Frame-Options", "DENY");
  ctx.set("X-Content-Type-Options", "nosniff");
}
```

> 后置增强必须写在 await next() 之后而非之前：写在之前时下游尚未运行，补充的头可能在下游覆盖或响应发送后才设置而失效。

**速记**：next 后 **补头收尾**。



### 中间件注册顺序与合并

#### app.use 按注册顺序嵌套

**注册顺序**：app.use 的调用次序 **决定洋葱从外到内的层级**，先注册者在外层、后注册者在内层。

- 第一个 app.use 注册的中间件最靠外，其 next 之前的代码最先执行。
- 错误处理、日志、计时这类"全局前置/后置"逻辑，应最早注册以包住全部业务。
- 路由、业务中间件后注册，位于洋葱内层，只处理被外层放行的请求。

```js
app.use(errorHandlerMiddleware);   // 最外层：兜底错误
app.use(responseTimeMiddleware);   // 外层：计时
app.use(router.routes());          // 内层：路由分发
```

> 顺序写反会带来隐患：若把错误兜底放在路由之后注册，路由中间件抛出的异常就不在它的包裹范围内，无法被统一捕获。

**速记**：先注册 **在外层**。



#### koa-compose 合并多个中间件

**中间件合并**：koa-compose 把 **一组中间件函数合成一个**，使多个逻辑可以像单个中间件一样被整体挂载或复用。

- 用法为 compose([mw1, mw2, mw3])，返回一个接受 (ctx, next) 的合并中间件。
- 合并后的执行顺序仍遵循洋葱模型，等价于依次 app.use 这三个中间件。
- Koa 内部正是用 koa-compose 来把注册的多个中间件串成一条链，开发者也可直接引用它做模块封装。

```js
const compose = require("koa-compose");

const merged = compose([
  responseTimeMiddleware,
  headerEnhancerMiddleware,
]);

app.use(merged);
```

> koa-compose 的入参必须是数组，且每项都是合法中间件。传入非函数或漏写 next，会在运行时报错而非安装期，需保持每项签名一致。

**速记**：compose 把 **多个合一个**。



### 错误处理

#### 最外层中间件 try/catch 捕获下游异常

**捕获机制**：在 **最外层中间件的 try 块里 await next()**，下游抛出的任何异常都会落到对应的 catch 中。

- 这是 Koa 推荐的错误处理范式，比给每个中间件单独写 try/catch 更集中、更不易遗漏。
- catch 中务必设置 ctx.status 与 ctx.body，否则响应会停留在默认状态。
- 捕获后可通过 ctx.app.emit("error", err, ctx) 把错误事件抛给全局监听，便于落日志。

```js
async function errorHandlerMiddleware(ctx, next) {
  try {
    await next();
  } catch (err) {
    ctx.status = 500;
    ctx.body = { error: "服务器内部错误" };
    ctx.app.emit("error", err, ctx);
  }
}
```

> 若错误发生在最外层中间件自身 next 之前的同步代码里，try 同样能兜住；但若根本没包 try/catch，异常会穿透到 Koa 默认处理器，回 500 且不留业务日志。

**速记**：最外层 try **兜全部**。



#### ctx.throw 抛出带状态码错误

**主动抛错**：ctx.throw(status, message) 是 **Koa 提供的便捷抛错方法**，一键生成带状态码的 HttpError。

- 第一个参数为 HTTP 状态码，如 400、401、404、500；第二个参数为错误描述。
- 抛出的错误对象带 status 与 message 字段，可被上游 try/catch 识别并据 status 响应。
- 还有 ctx.assert(condition, status, message)，条件为假时才抛错，适合参数校验。

```js
app.use(async (ctx) => {
  if (!ctx.query.token) {
    ctx.throw(401, "缺少访问令牌");
  }
  ctx.body = { ok: true };
});
```

> ctx.throw 本质是抛出一个 Error 实例，必须处在 try/catch 包裹的下游才会被优雅处理；若外层没有兜底，它仍会触发 Koa 默认 500。

**速记**：ctx.throw 抛 **带码错误**。



#### app.on("error") 记录未捕获错误

**全局监听**：app.on("error", handler) 用于 **集中接收所有被抛出的错误事件**，常用于写日志而不直接响应。

- 错误事件由中间件里 ctx.app.emit("error", err, ctx) 触发，或 Koa 内部默认错误处理器转发。
- handler 的两个常用参数是错误对象 err 与上下文 ctx，可据此记录堆栈与请求信息。
- 该监听只负责"记录"，不负责"响应"，响应仍由兜底中间件的 catch 完成。

```js
app.on("error", (err, ctx) => {
  console.error("请求出错：", err.message, "路径：", ctx.path);
});
```

> 即便不写 app.on("error")，Koa 也会把未捕获错误打印到 stderr。显式监听的价值是接入日志系统、上报监控，而不是让它消失。

**速记**：app.on("error") **管记录**。



#### err.expose 控制是否暴露详情

**错误暴露**：错误对象的 **expose 字段** 决定 **是否向客户端返回真实错误信息**，避免把内部细节泄露给外人。

- 当 err.expose 为 true 时，Koa 允许把 err.message 作为响应体回给客户端（通常用于 4xx 客户端错误）。
- 当 err.expose 为 false 或缺失时（通常用于 5xx 服务端错误），应只回通用提示，不暴露堆栈与内部路径。
- ctx.throw 在状态码为 4xx 时默认 expose 为 true，5xx 时默认 expose 为 false。

```js
async function errorHandlerMiddleware(ctx, next) {
  try {
    await next();
  } catch (err) {
    ctx.status = err.status || 500;
    ctx.body = { error: err.expose ? err.message : "服务器内部错误" };
  }
}
```

> 暴露控制是安全底线：5xx 错误若把堆栈回显给客户端，等于公开服务器目录与依赖，给攻击者提供线索。生产环境务必默认隐藏详情。

**速记**：expose 控制 **详情是否外泄**。



### 常用社区中间件

#### koa-router 处理路由

**路由中间件**：koa-router 是 **Koa 生态最主流的路由方案**，提供 get、post 等方法把路径映射到处理函数。

- 创建 Router 实例后，用 router.get(path, handler) 与 router.post(path, handler) 注册路由。
- 它弥补了 Koa 内核不内置路由的缺口，能力对标 Express 的路由。
- 支持路由参数、前缀分组、allowedMethods 等特性，后文单独展开。

> koa-router 并非官方内核的一部分，而是社区维护包。选型时注意版本与 Koa 2 的兼容，务必安装支持 async 中间件的版本。

**速记**：koa-router 补 **路由能力**。



#### koa-bodyparser 解析请求体

**请求体解析**：koa-bodyparser 负责 **把 POST 等请求的 JSON 或表单体解析到 ctx.request.body**，免去手动读流。

- 注册后，handler 内可直接读 ctx.request.body 拿到解析后的对象。
- 默认支持 JSON 与表单格式，可按需配置大小限制与允许的格式。
- 对应 Express 的 express.json() 与 express.urlencoded() 内置能力。

```js
const bodyParser = require("koa-bodyparser");
app.use(bodyParser());
```

> 不装 koa-bodyparser 时 ctx.request.body 为 undefined，需自行监听 data/end 事件拼装。这是 Koa"裸内核"带来的典型额外装配。

**速记**：koa-bodyparser 填 **请求体**。



#### koa-static 静态托管

**静态托管**：koa-static 用于 **把指定目录下的文件直接映射为可访问 URL**，适合托管图片、前端产物。

- 用法为 koa-static(rootDir)，rootDir 是要公开的本地目录路径。
- 请求路径命中文件时直接返回内容，未命中才放行给后续中间件。
- 对应 Express 的 express.static() 内置能力。

```js
const staticFiles = require("koa-static");
app.use(staticFiles("public"));
```

> 静态中间件通常注册在路由之前，让文件优先响应；但若放在错误兜底之前，文件缺失引发的异常也可能被计入全局错误，需留意注册次序。

**速记**：koa-static 挂 **静态目录**。



#### koa-views 模板渲染

**模板渲染**：koa-views 为 Koa 提供 **模板引擎集成**，让 handler 用 ctx.render(name, data) 渲染页面。

- 支持 ejs、pug、handlebars 等多种引擎，安装对应引擎后由 koa-views 统一驱动。
- 注册时指定视图目录与默认引擎，调用 ctx.render 传入模板名与数据。
- 对应 Express 的 res.render 内置能力。

```js
const views = require("koa-views");
app.use(views("views", { extension: "ejs" }));

app.use(async (ctx) => {
  await ctx.render("index", { title: "首页" });
});
```

> koa-views 与具体引擎是解耦的：换引擎只改注册配置，业务里仍用 ctx.render。Express 的 res.render 同样思路，迁移成本低。

**速记**：koa-views 接 **模板引擎**。



#### 与 Express 内置能力的差别

**能力对照**：**Express 把路由、静态、请求体、模板内置进框架，Koa 全部外置为社区中间件**，这是二者装配方式的根本差别。

- **路由**：Express 用 app.get/post，Koa 用 koa-router。
- **请求体**：Express 用 express.json，Koa 用 koa-bodyparser。
- **静态**：Express 用 express.static，Koa 用 koa-static。
- **模板**：Express 用 res.render，Koa 用 koa-views 配 ctx.render。

> 差别只在"在哪装、叫什么"，不在"能不能做"。从 Express 迁到 Koa，绝大多数能力都能找到对应包，重点是习惯先装后用的装配节奏。

**速记**：Express **内置**，Koa **外挂**。



### 用 koa-router 写路由

#### 安装与创建 Router

**路由装配**：先 **安装 koa-router 并 new Router() 创建实例**，再用 app.use 把路由挂到应用上。

- 安装命令为 npm install koa-router，引入后得到 Router 构造函数。
- 调用 new Router() 得到 router 实例，其上注册的所有路由都从该实例管理。
- 可传入 { prefix: "/api" } 给全部路由加统一前缀，便于划分版本或模块。

```bash
npm install koa-router
```

```js
const Router = require("koa-router");
const router = new Router({ prefix: "/api" });
```

> 路由实例与 Koa 应用是两个对象：router 只管"路径到处理函数"的映射，最终必须由 app.use(router.routes()) 接入请求链才生效。

**速记**：new Router() 建 **路由表**。



#### 注册 get 与 post 路由

**方法路由**：用 **router.get(path, handler) 与 router.post(path, handler)** 分别绑定读、写两类请求的处理函数。

- handler 是标准 Koa 中间件，签名 async (ctx) 即可，通过 ctx.body 返回结果。
- get 用于查询、post 用于创建或提交，语义与 HTTP 方法一致。
- 同一路径可分别注册不同方法，互不冲突。

```js
router.get("/users", async (ctx) => {
  ctx.body = { list: ["张三", "李四"] };
});

router.post("/users", async (ctx) => {
  ctx.body = { created: true };
  ctx.status = 201;
});
```

> 只注册了 get("/users") 却用 post 访问，会返回 405 Method Not Allowed——前提是挂载了 allowedMethods，见后文。

**速记**：get 查、post 写 **各归其法**。



#### 路由参数 ctx.params

**路径参数**：在 **路径中用冒号声明占位段**，处理函数里通过 **ctx.params** 读取实际传入的值。

- 写法如 router.get("/users/:id")，访问 /users/42 时 ctx.params.id 为字符串 "42"。
- 可声明多个参数，如 /users/:uid/posts/:pid，对应 ctx.params.uid 与 ctx.params.pid。
- 参数值始终为字符串类型，需要数字时自行转换。

```js
router.get("/users/:id", async (ctx) => {
  const id = ctx.params.id;
  ctx.body = { id, type: typeof id };
});
```

> Express 同样用 :id 与 req.params，迁移几乎无缝。区别是取值入口从 req.params 变为 ctx.params，字段结构一致。

**速记**：:id 配 **ctx.params**。



#### router.allowedMethods 的作用

**方法校验**：router.allowedMethods() 返回一个 **补全状态码与 Allow 头的中间件**，处理路由匹配但方法不被允许的情况。

- 当路径存在但请求方法没有对应路由时，它返回 405 Method Not Allowed。
- 当路径本身不存在时，它返回 404 Not Found（若后续无其他中间件响应）。
- 它还会在响应头写入 Allow，告诉客户端该路径支持哪些方法。

```js
app.use(router.routes());
app.use(router.allowedMethods());
```

> allowedMethods 必须挂在 router.routes() 之后。漏挂时，方法不匹配只会落到下游默认 404，缺少标准的 405 与 Allow 头，接口语义不完整。

**速记**：allowedMethods 补 **405 与 Allow**。



#### 挂载到 app

**接入应用**：用 **app.use(router.routes())** 把路由表接入 Koa 请求链，必要时再接 allowedMethods。

- router.routes() 返回的是一个标准中间件，因此能直接传给 app.use。
- 多组路由可分别创建 routerA、routerB，各自加前缀后依次挂载，实现模块拆分。
- 挂载顺序上，路由一般放在错误兜底、日志等外层中间件之后。

```js
const Koa = require("koa");
const Router = require("koa-router");
const app = new Koa();
const router = new Router();

router.get("/", async (ctx) => {
  ctx.body = "首页";
});

app.use(router.routes());
app.use(router.allowedMethods());
app.listen(3000);
```

> 路由中间件没有调用 next 时，请求在此终结；若它之后还挂了其他中间件，那些中间件在路由命中后不会执行，需把全局逻辑放在路由之前注册。

**速记**：app.use(router.routes()) **接入请求链**。



### 从 Express 迁移的注意点

#### res.send 对应 ctx.body

**响应替换**：Express 的 **res.send(value)** 在 Koa 中等价于 **给 ctx.body 赋值**，没有独立的"发送"调用。

- res.send("文本") 对应 ctx.body = "文本"，res.send({ a: 1 }) 对应 ctx.body = { a: 1 }。
- 设置状态码由 res.status(code) 变为 ctx.status = code，二者都是赋值语义。
- 设置响应头由 res.set(name, value) 变为 ctx.set(name, value)，用法基本一致。

```js
// Express 写法
// res.status(200).json({ ok: true });

// Koa 等价写法
ctx.status = 200;
ctx.body = { ok: true };
```

> Koa 没有 res.json 这种"按类型发送"的方法，统一用 ctx.body 赋值，Koa 依据类型自动选序列化方式。迁移时把所有 res.send/res.json 改成 ctx.body 赋值即可。

**速记**：res.send 改 **ctx.body 赋值**。



#### 中间件需改写为 async 形式

**形态改写**：Express 中间件多为 **(req, res, next) 回调形态**，迁到 Koa 要改成 **async (ctx, next)** 并改用 await next()。

- 形参由 req、res、next 换成 ctx、next，原来从 req 读数据改为从 ctx 读。
- 异步等待由回调改为 await，原来串行嵌套的逻辑可拉平成顺序代码。
- 若下游需要继续，必须写 await next()；忘记 await 会卡住洋葱。

```js
// Express 中间件
// function mw(req, res, next) { next(); }

// Koa 等价中间件
async function mw(ctx, next) {
  await next();
}
```

> 改写时最容易漏的是 await：把 next() 当同步调用却忘了 await，下游会异步执行而当前中间件已结束，计时、收尾等回程逻辑全部错位。

**速记**：中间件改 **async + await next**。



#### 错误处理方式变化

**错误范式**：Express 用 **(err, req, res, next) 四参错误中间件** 集中处理，Koa 改用 **最外层 try/catch 包裹 await next()**。

- Express 的四参错误处理函数靠 next(err) 触发，顺序上排在所有普通中间件之后。
- Koa 没有四参错误中间件概念，统一靠 try/catch 捕获下一行 await next() 抛出的异常。
- 主动抛错由 next(new Error()) 改为 ctx.throw(status, message)。

```js
// Express 错误中间件
// function errHandler(err, req, res, next) { res.status(500).send(err.message); }

// Koa 等价：最外层 try/catch
async function errorHandlerMiddleware(ctx, next) {
  try {
    await next();
  } catch (err) {
    ctx.status = err.status || 500;
    ctx.body = { error: err.message };
  }
}
```

> 迁移后要删掉 Express 风格的四参函数，否则 Koa 不会把它当错误处理中间件识别，反而会当作普通中间件导致行为异常。

**速记**：四参错误函数改 **try/catch 兜底**。



### 常见坑

#### 忘记 await next 导致下游不执行

**漏写 await**：在中间件中 **只调用 next() 而不 await**，当前中间件会立即结束，下游被异步推后执行，回程逻辑全部错位。

- 没有 await，next() 返回的 Promise 不被等待，next 之后的代码在下游真正完成前就已运行。
- 表现为计时不准确、后置响应头未生效、统一错误兜底漏捕下游异常。
- 更严重时会因响应提前发送，下游再写 ctx.body 已无效。

```js
// 错误写法：漏了 await
async function badMiddleware(ctx, next) {
  console.log("进");
  next();            // 应写 await next();
  console.log("出");
}

// 正确写法
async function goodMiddleware(ctx, next) {
  console.log("进");
  await next();
  console.log("出");
}
```

> 这是 Koa 新手最高频的错误。记住口诀：凡是调用 next，一律 await next()，除非你明确要"放它自顾自跑"且不在乎回程。

**速记**：调 next 必 **await**。



#### 中间件中抛错未捕获导致 500

**未捕获异常**：下游中间件 **抛出异常却没有外层 try/catch 兜底** 时，Koa 会直接回 500 且响应体为空，客户端拿不到线索。

- 业务里用 ctx.throw 或自然 throw 的错误，必须被某个上层中间件的 try/catch 接住。
- 没有兜底时，Koa 默认处理器会设置 500 并可能把错误打印到 stderr，但响应对客户端不友好。
- 错误还会触发 app.on("error")，若没监听则只在控制台出现，难以排查。

```js
// 风险：没有兜底，下游抛错即裸 500
app.use(async (ctx) => {
  throw new Error("出错了");
});
```

> 防御做法是在最外层固定挂一个 errorHandlerMiddleware，所有业务异常在它之内被捕获并转为结构化响应，详见错误处理章节。

**速记**：异常要 **有外层兜底**。



#### ctx.body 赋值后又调用原生 res.end

**混用原生**：在 **给 ctx.body 赋值之后又手动调用 ctx.res.end()**，会破坏 Koa 对响应流程的控制，导致重复发送或报错。

- Koa 通过 ctx.body 统一管理响应，赋值后由框架在下游完成后统一发送。
- 直接操作原生 ctx.res.end 绕过了框架，Koa 不知道响应已发出，后续可能再次写入而冲突。
- 混用常见于从 Express 迁移时保留了 res.end 习惯，或误以为需要手动结束响应。

```js
// 错误写法：Koa 已用 ctx.body 发包，又手动 end
app.use(async (ctx) => {
  ctx.body = "响应内容";
  ctx.res.end();   // 危险：与原生层冲突
});
```

> 在 Koa 中几乎永远不需要调用 ctx.res.end。需要结束响应就靠赋值 ctx.body 并 return；确需底层能力时，要么全程只用原生 res，要么全程只用 Koa 抽象，二者不要交叉。

**速记**：ctx.body 后 **别碰 res.end**。
