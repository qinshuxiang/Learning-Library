## 安全配置与运维实践

### 鉴权机制与内置角色

#### 内置角色一族

**内置角色（Built-in Roles）**：是 MongoDB 预置的权限模板，每个角色是一组固定权限的集合，授权时把角色绑定到用户与库上，不必逐条勾选操作。

- **read**：指定库的只读权限，能查询与聚合，不能写入。
- **readWrite**：指定库的读写权限，业务应用账号的常规选择。
- **dbAdmin**：指定库的管理权限，覆盖建删索引、收集统计、压缩与校验等管理操作，不含数据读写。
- **userAdmin**：指定库内创建与授权用户的管理权限，能给自己提权，授予需谨慎。
- **跨库一族**：readAnyDatabase、readWriteAnyDatabase、dbAdminAnyDatabase、userAdminAnyDatabase 与上面四个一一对应，作用范围扩到全部库，且只能建在 admin 库。
- **clusterMonitor／clusterManager**：集群层角色，前者供监控工具只读探查，后者可管理副本集与分片。
- **backup／restore**：备份与恢复专用角色，分别匹配 mongodump 与 mongorestore 所需的最小权限。
- **root**：超级角色，拥有全部权限，只建在 admin 库，一个环境只留给极少数管理员。

> [!IMPORTANT]
> **重要内容**：授权的基本盘是「按库授最小角色」：应用账号给目标库的 readWrite，备份账号给 backup 加 restore，监控账号给 clusterMonitor，root 只留给人工运维。跨库一族与 root 一旦泄露，等于整库失守。



#### createUser 与角色授予

**createUser**：是创建数据库用户并绑定角色的命令，用户连同角色信息保存在所建库的 system.users 集合中，跨库角色统一收在 admin 库。

```js
// 应用账号：只授 shop 库读写，另给 report 库只读
use admin
db.createUser({
  user: "appUser",
  pwd: "S3cret-Passw0rd",
  roles: [
    { role: "readWrite", db: "shop" },
    { role: "read", db: "report" }
  ]
})
```

```text
{ ok: 1 }
```

用户的日常管理命令：

- **db.changeUserPassword**：改口令，定期轮换凭据用。
- **db.grantRolesToUser**：追加角色，如临时给只读账号加写权限。
- **db.revokeRolesFromUser**：回收角色，收权比删号更常用。
- **db.dropUser**：删除用户，在哪个库执行就删哪个库的用户。

```js
// 用管理账号登录后给 appUser 追加角色
use admin
db.grantRolesToUser("appUser", [{ role: "read", db: "logs" }])
```

```text
{ ok: 1 }
```

> [!CAUTION]
> **注意内容**：开启鉴权前必须先建管理员账号，否则带着 --auth 重启后没有任何账号能登录。首次操作顺序是：不鉴权启动，在 admin 库建好带 userAdminAnyDatabase 或 root 的管理员，再重启加鉴权；mongosh 的 localhost 豁免（localhost exception）只允许在开启鉴权后于本机创建第一个用户，且仅此一次。



#### SCRAM 鉴权机制

**SCRAM（Salted Challenge Response Authentication Mechanism，加盐质询应答鉴权机制）**：是 MongoDB 的默认鉴权机制，客户端与服务端通过多轮消息交换完成身份证明，全程不传输明文口令。

- **质询应答**：客户端用口令的派生值对服务端的随机质询做运算并回传，服务端用存储的同源派生值验证，网络抓包拿不到可重放的凭据。
- **口令存储**：服务端只存加盐哈希，盐与迭代参数随用户记录保存，数据文件被拖走也还原不出明文口令。
- **算法版本**：SCRAM-SHA-256 是当前默认机制，摘要强度高于早期的 SCRAM-SHA-1，新用户默认按 256 创建。
- **迭代成本**：派生运算带可调迭代次数，抬高离线暴力破解的代价，迭代参数随用户记录一并存储。
- **连接串入口**：鉴权库名通过 authSource 指定，用户建在 admin 库而访问业务库时，连接串必须带 authSource=admin。

```js
// mongosh 用 admin 库账号连接
mongosh "mongodb://appUser:S3cret-Passw0rd@127.0.0.1:27017/shop?authSource=admin"
```

```text
Current Mongosh Log ID: 6650e1a2f1c9b3a4d5e6f708
Connecting to: mongodb://127.0.0.1:27017/shop?authSource=admin
Enter 'exit' or Ctrl+C to exit.
```

> SCRAM 解决「证明你是谁」，不解决「链路被窃听」：鉴权通过后传输仍是明文，防窃听要靠 TLS，两层叠加才是完整的传输安全。口令本身要够长够随机，SCRAM 挡得住抓包，挡不住弱口令被猜中。



### 网络隔离与传输加密

#### bindIp 与防火墙

**bindIp**：是 mongod 监听的网络地址配置，决定进程绑在哪些网卡上；防火墙在网络层再加一道来源过滤，两者配合完成网络隔离。

- **默认行为**：不配置时只绑定 127.0.0.1，仅本机可连，是安全默认。
- **常见误区**：把 bindIp 写成 0.0.0.0 监听所有网卡，实例直接暴露在公网，是最典型的泄露事故来源。
- **正确写法**：按需列出内网地址与 127.0.0.1，副本集成员互写时用各成员的内网 IP。

```bash
# 以命令行参数启动，只绑定本机回环与内网地址，并开启鉴权
mongod --dbpath /data/db --port 27017 --auth --bind_ip 127.0.0.1,10.0.0.5
```

防火墙在 bindIp 之外再收一次口：

```bash
# 仅放行业务网段访问 27017 端口
sudo iptables -A INPUT -p tcp --dport 27017 -s 10.0.0.0/24 -j ACCEPT
# 其余来源一律拒绝
sudo iptables -A INPUT -p tcp --dport 27017 -j DROP
```

> [!WARNING]
> **警告内容**：历史上有大量因 bindIp 配成 0.0.0.0 且未开鉴权而被勒索的公开实例。上线检查必须同时满足两条：bindIp 只含内网与回环地址，且鉴权已开启。云环境再叠加安全组，形成「绑定地址、防火墙、安全组」三层收口。



#### TLS 加密连接

**TLS 加密连接**：是客户端与 mongod 之间、副本集成员之间用传输层加密保护数据的方式，防链路窃听与中间人篡改，与 SCRAM 鉴权互补。

```bash
# 自签一张服务器证书并合成 pem 文件（生产环境用正式 CA 签发）
openssl req -newkey rsa:4096 -nodes -keyout mongodb.key -x509 -days 365 -out mongodb.crt -subj "/CN=mongo.internal"
cat mongodb.key mongodb.crt > mongodb.pem

# 以要求 TLS 的模式启动
mongod --dbpath /data/db --tlsMode requireTLS --tlsCertificateKeyFile /etc/ssl/mongodb.pem
```

客户端连接时同样要带 TLS 参数与信任的 CA 证书：

```bash
mongosh "mongodb://appUser:S3cret-Passw0rd@127.0.0.1:27017/shop?authSource=admin&tls=true&tlsCAFile=/etc/ssl/mongodb.crt" --eval "db.runCommand({ ping: 1 })"
```

```text
{ ok: 1 }
```

- **tlsMode**：disabled、allowTLS、preferTLS、requireTLS 四档，生产环境对外服务用 requireTLS，副本集内部可按迁移节奏用 preferTLS 过渡。
- **证书文件**：tlsCertificateKeyFile 是私钥与证书的合并文件，权限应收紧到服务进程用户可读。
- **证书轮换**：到期前换发新证书并逐台滚动重启成员，副本集避免全员同时换证书造成不可用。
- **成员间加密**：副本集与分片集群的成员之间同样走 TLS，配置在集群参数里，方式与客户端侧一致。
- **校验开关**：客户端始终保留 CA 校验（tlsCAFile 指向受信证书），不做「先跑通再关校验」的妥协。

> 自签证书适合内网与实验，证书校验一旦放松（如客户端关掉 CA 校验），TLS 就只剩加密没有身份验证，中间人仍可伪装服务端。生产环境用内部 CA 或正式证书，并保持客户端校验开启。



### 备份恢复与安全基线

#### mongodump 与 mongorestore

**mongodump**：是官方的逻辑备份工具，把集合导出为 BSON 文件加元数据；**mongorestore** 是配套的恢复工具，把导出文件灌回实例，两者是中小规模数据量的默认组合。

```bash
# 备份 shop 库到指定目录
mongodump --host 127.0.0.1 --port 27017 --db shop --out /backup/shop-20260923
```

```text
2026-09-23T10:30:00.123+0800	writing shop.orders to /backup/shop-20260923/shop/orders.bson
2026-09-23T10:30:01.456+0800	done dumping shop.orders (52000 documents)
2026-09-23T10:30:01.789+0800	writing shop.users to /backup/shop-20260923/shop/users.bson
2026-09-23T10:30:01.902+0800	done dumping shop.users (3800 documents)
```

```bash
# 恢复前先清空目标集合，再整库灌回
mongorestore --host 127.0.0.1 --port 27017 --nsInclude "shop.*" --drop /backup/shop-20260923
```

```text
2026-09-23T11:00:00.123+0800	preparing collections to restore from
2026-09-23T11:00:00.456+0800	reading metadata for shop.orders from /backup/shop-20260923/shop/orders.metadata.json
2026-09-23T11:00:01.789+0800	restoring shop.orders from /backup/shop-20260923/shop/orders.bson
2026-09-23T11:00:05.001+0800	finished restoring shop.orders (52000 documents, 0 failures)
2026-09-23T11:00:05.010+0800	52000 document(s) restored successfully. 0 document(s) failed to restore.
```

归档模式把全部集合收进单文件并压缩，便于传输与归档：

```bash
# 导出为 gzip 压缩的单个归档文件
mongodump --archive=/backup/shop.archive.gz --gzip --db shop

# 从归档文件恢复
mongorestore --archive=/backup/shop.archive.gz --gzip --drop
```

- **常用粒度参数**：--db 与 --collection 控制备份范围，--nsInclude 与 --nsExclude 控制恢复范围。
- **--drop 的含义**：恢复前删除目标集合再重建，避免与现存数据混插出重复文档。
- **凭据最小化**：备份账号配 backup 角色、恢复账号配 restore 角色，不要拿 root 跑定时任务。
- **定时与留存**：定时备份用 cron 驱动，输出目录或归档文件名带日期，保留窗口按「日备近周、周备近月」的节奏收紧，并同步一份到异机或对象存储。

> mongodump 备份的是某一时刻的数据加 oplog 窗口，不是磁盘镜像；大集合上它受限于扫描与网络速度。恢复演练是备份体系的一半——没验证过可恢复的备份，等同于没有备份。



#### 副本集环境下的备份要点

**副本集备份**：核心是两件事——把备份负载挪离主库，以及处理备份期间的持续写入，mongodump 用读写偏好与 oplog 参数覆盖这两点。

- **优先从从库备份**：连接串加 readPreference=secondary，让全量扫描的 IO 落在从库，主库只承受正常业务压力。
- **--oplog 保证一致点**：备份期间主库仍在写入，加 --oplog 让 mongodump 顺带记录备份窗口内的 oplog，恢复后可重放到与备份结束时刻一致的状态。
- **恢复时回放 oplog**：mongorestore 配 --oplogReplay，先灌数据再重放记录到的 oplog，保证外键式引用与时间线一致。
- **一致性判断**：不带 --oplog 的备份在「备份期间有写入」时，各集合的数据不在同一时间点上，含关联引用的数据恢复后可能出现错位。
- **更大规模的替代**：数据量大到 mongodump 窗口难以接受时，改用文件系统或云盘快照（配合 fsync 锁写或从库快照），或采用 Percona Backup for MongoDB 这类物理备份方案。

```bash
# 从从库做带 oplog 的一致性备份
mongodump --host rs0/10.0.0.5:27017 --readPreference=secondary --oplog --out /backup/rs-20260923
```

```text
2026-09-23T12:00:00.123+0800	writing admin.system.version to /backup/rs-20260923/admin/system.version.bson
2026-09-23T12:00:00.456+0800	done dumping admin.system.version (1 document)
2026-09-23T12:00:00.789+0800	writing shop.orders to /backup/rs-20260923/shop/orders.bson
2026-09-23T12:00:03.001+0800	done dumping shop.orders (52000 documents)
2026-09-23T12:00:03.234+0800	writing captured oplog to /backup/rs-20260923/oplog.bson
2026-09-23T12:00:03.240+0800	dumped 120 oplog entries
```

> [!IMPORTANT]
> **重要内容**：oplog 窗口必须盖过备份耗时——备份期间若写入量大到最早的 oplog 条目已被滚动覆盖，--oplog 备份会失败。确认从库 oplog 尺寸足够，或把备份安排在写入低峰，是副本集备份计划的一部分。



#### 日常巡检与常用运维命令

**日常巡检与常用运维命令**：是运维人员定期查看实例健康度的一组命令，覆盖运行中的操作、集合存储统计与复制状态三类视角。

- **db.currentOp**：列出正在执行的操作，用于找出长时间运行的查询与锁等待来源。
- **db.killOp**：按 opid 终止失控操作，与 currentOp 配套使用。
- **db.stats 与 db.collection.stats**：库与集合的存储统计，观察数据体积、索引体积与文档数的水位。
- **db.collection.validate**：校验集合数据与索引的完整性，异常宕机或磁盘故障后排查用。
- **db.printReplicationInfo 与 db.printSecondaryReplicationInfo**：副本集下查看 oplog 窗口与各从库的复制延迟。

```js
// 找出运行超过 10 秒的活跃操作
db.currentOp({ active: true, secs_running: { $gt: 10 } })
  .inprog.forEach(function (op) {
    console.log(op.opid, op.op, op.ns, op.secs_running);
  });
```

```text
123456 query shop.orders 47
123501 getmore shop.orders 12
```

对失控操作先确认来源再终止，killOp 不可逆：

```js
// 终止运行 47 秒的失控查询
db.killOp(123456)
```

```text
{ info: 'attempting to kill op', ok: 1 }
```

集合体积的例行查看：

```js
// 看大集合的体积水位：文档数、数据与索引体积
const st = db.orders.stats();
console.log("文档数:", st.count);
console.log("数据大小(MB):", (st.size / 1048576).toFixed(1));
console.log("索引大小(MB):", (st.totalIndexSize / 1048576).toFixed(1));
```

```text
文档数: 52000
数据大小(MB): 96.4
索引大小(MB): 12.8
```

> [!TIP]
> **建议内容**：巡检的价值在趋势而不在单次：currentOp 看当下负载、stats 看容量水位、复制信息看延迟，三张表每天固定看一遍，容量告急与复制落后往往在业务报障前就能暴露。把巡检命令写进脚本并输出到日志，是最朴素的监控兜底。



#### 安全基线清单

**安全基线**：是一套实例上线与日常运维必须逐项核对的最小安全配置，基线的价值在于把「记得做」变成「照单查」。

- **开启鉴权**：mongod 配 --auth 或 security.authorization: enabled，实例对外提供服务的第一天就生效。
- **最小权限账号**：应用、备份、监控各用独立账号，只授所需角色，root 只留给人工运维。
- **限定监听地址**：bindIp 只写内网地址与 127.0.0.1，绝不出现 0.0.0.0。
- **防火墙与安全组**：27017 端口限定来源网段，公网入口一律拒绝。
- **全链路 TLS**：客户端到服务端、副本集成员之间都启用加密，内网也不传明文。
- **成员间互认**：副本集与分片集群用 keyFile 或 x.509 证书做成员鉴权，防止未授权节点混入。
- **关闭 server 端 JavaScript**：security.javascriptEnabled 保持默认关闭，缩小注入面。
- **审计日志**：合规要求高的环境开启审计（企业版功能），记录登录、授权变更与 DDL 操作。
- **备份可恢复**：备份定时执行、异地存放、加密保存，并定期演练 mongorestore 恢复。
- **及时升级**：跟踪安全修复版本，补丁先在测试环境验证再滚动升级。

> [!CAUTION]
> **注意内容**：安全配置的变更顺序比配置本身更易出错：先建管理员再开鉴权，改 bindIp 前确认副本集成员间的互连地址在名单里，收紧防火墙前确认监控与备份的来源端口已放行。任何基线变更先在测试环境过一遍，再按实例逐台灰度。
