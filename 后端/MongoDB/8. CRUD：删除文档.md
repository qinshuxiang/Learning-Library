## CRUD：删除文档

### 删除方法与样例数据

#### 样例集合 logs

**样例集合 logs**：是后续全部删除示例共同操作的数据底座，五条日志文档带有等级与时间字段，便于按条件演示各类删除。

```js
db.logs.insertMany([
  { _id: 1, level: "info", message: "服务启动", createdAt: ISODate("2026-09-20T08:00:00Z") },
  { _id: 2, level: "warn", message: "响应超时", createdAt: ISODate("2026-09-20T09:30:00Z") },
  { _id: 3, level: "error", message: "数据库连接失败", createdAt: ISODate("2026-09-21T10:00:00Z") },
  { _id: 4, level: "error", message: "磁盘空间不足", createdAt: ISODate("2026-09-21T11:00:00Z") },
  { _id: 5, level: "info", message: "定时任务完成", createdAt: ISODate("2026-09-22T02:00:00Z") }
])
```

```text
{
  acknowledged: true,
  insertedCount: 5,
  insertedIds: { '0': 1, '1': 2, '2': 3, '3': 4, '4': 5 }
}
```

- **字段角色**：level 承载等值删除条件，createdAt 承载范围清理条件，两类字段覆盖全部示例场景。
- **数据量级**：五条文档刚好演示「删一条、删一类、删空」三种规模。

> 后续所有示例都从这份初始数据出发、按文中出现顺序依次执行，集合中剩余的文档随删除逐步减少。整套示例重新执行前，先删掉集合并重建。



#### deleteOne 与 deleteMany

**删除方法**：是按匹配范围划分的两个顶层删除入口，deleteOne 删第一条匹配文档，deleteMany 删全部匹配文档，二者参数都是同一个查询条件。

- **deleteOne(filter)**：只删除匹配到的第一篇文档，按自然序或索引序取第一条。
- **deleteMany(filter)**：删除全部匹配文档，不设上限。
- **filter 语法**：与 find 的查询条件完全一致，$eq、$gt、$in 等操作符全部可用。

```js
db.logs.deleteOne({ _id: 2 })
db.logs.deleteMany({ level: "error" })
```

```text
{ acknowledged: true, deletedCount: 1 }
{ acknowledged: true, deletedCount: 2 }
```

> 删除的匹配语义与查询一致，写删除条件前先跑一遍同条件的 find，看到的就是将被删除的。没有 justOne 这类事后补救参数，deleteOne 与 deleteMany 的差别必须在做选择时就确定。



### 返回结果与弃用命令

#### deletedCount 与返回结构

**删除结果**：是一个包含 acknowledged 与 deletedCount 两个字段的确认文档，deletedCount 是判断实际删了几篇的唯一依据。

```js
db.logs.deleteOne({ _id: 999 })
db.logs.deleteMany({ level: "debug" })
```

```text
{ acknowledged: true, deletedCount: 0 }
{ acknowledged: true, deletedCount: 0 }
```

- **acknowledged**：写入是否被服务端确认，开启写关注后为 true。
- **deletedCount**：实际删除的文档数，0 表示条件没有命中任何文档。
- **无匹配不报错**：条件落空时返回 deletedCount 0 而不是抛异常，业务代码不能依赖异常来感知「没删到」。

> [!IMPORTANT]
> **重要内容**：判断删除是否生效只能看 deletedCount，不能假设「执行成功等于删掉了」。对删除结果有业务依赖时，先取返回值再继续，deletedCount 与预期不符要按异常流程处理。



#### remove 已弃用

**remove**：是旧版驱动与 mongo shell 的删除命令，在 MongoDB 8.0 与 mongosh 2.x 下已被标记弃用，官方要求改用 deleteOne 或 deleteMany。

```js
db.logs.remove({ level: "info" })
```

```text
DeprecationWarning: Collection.remove() is deprecated. Use deleteOne, deleteMany, or bulkWrite instead.
{ acknowledged: true, deletedCount: 1 }
```

- **弃用现状**：命令仍可执行，但每次都会输出弃用警告，后续版本随时可能移除。
- **语义对应**：remove 带 justOne: true 等价于 deleteOne，不带则等价于 deleteMany。
- **迁移写法**：现有代码里的 remove 应逐处改写为 deleteOne 或 deleteMany，语义按 justOne 的有无对号入座。

> [!CAUTION]
> **注意内容**：新代码不得再使用 remove，旧代码迁移时警惕一条——remove 不带 justOne 是全量删除，直接照原条件改成 deleteOne 会让「本想删多条」的语句只删一条，必须逐处核对原意。



### 批量清理与全量清空

#### 按条件批量清理

**按条件批量清理**：是用带查询操作符的条件做 deleteMany，一次性清掉一类文档，日志轮转、过期数据下线都走这条路。

先补入两条新日志，再清理某个时间点之前的全部文档。

```js
db.logs.insertMany([
  { _id: 6, level: "info", message: "健康检查通过", createdAt: ISODate("2026-09-23T08:00:00Z") },
  { _id: 7, level: "warn", message: "慢查询告警", createdAt: ISODate("2026-09-23T09:00:00Z") }
])
db.logs.deleteMany({ createdAt: { $lt: ISODate("2026-09-23T00:00:00Z") } })
```

```text
{
  acknowledged: true,
  insertedCount: 2,
  insertedIds: { '0': 6, '1': 7 }
}
{ acknowledged: true, deletedCount: 1 }
```

- **时间条件**：$lt 配 ISODate 清掉某时刻之前的文档，此处只剩 9 月 23 日的两条。
- **范围控制**：条件越具体删除范围越小，时间段、等级、状态码都能组合进同一条条件。
- **大删除分批**：清理百万级文档时按时间或 _id 分段多次 deleteMany，避免长时间占用与复制集延迟抖动。
- **条件复用**：清理条件与业务查询共用同一套字段口径，避免「查得到却删不到」的错位。

> [!TIP]
> **建议内容**：周期性清理交给应用程序或定时脚本按固定窗口执行，并为 createdAt 这类清理条件建索引，否则每次清理都退化成全集合扫描。



#### 全量清空

**全量清空**：是用空条件做 deleteMany 把集合内文档全部删掉，集合本身、索引与元数据保留。

```js
db.logs.deleteMany({})
db.logs.find()
```

```text
{ acknowledged: true, deletedCount: 2 }
[]
```

- **空条件的含义**：filter 写空对象表示匹配全部文档，集合从有数据变为无数据但依然存在。
- **保留的部分**：索引定义、集合选项、权限配置全部不动，重新插入数据立即生效。
- **find 返回空数组**：集合存在但没有文档时，find 返回空数组而非报错。

> 空对象条件必须显式写出来，deleteMany() 缺参数会直接报错。这一道「手写空对象」的门槛正是防止顺手清空整表的设计。



#### 大删除的分批执行

**大删除的分批执行**：是把一次删百万级的操作拆成多个小批次循环执行的做法，用「先取一批 _id、再按 _id 删除」的固定节奏控制单轮耗时。

先灌入一批待清理的噪声数据，再分批删除。

```js
db.noise.insertMany([
  { _id: 101, level: "noise" },
  { _id: 102, level: "noise" },
  { _id: 103, level: "noise" },
  { _id: 104, level: "noise" },
  { _id: 105, level: "noise" },
  { _id: 106, level: "noise" },
  { _id: 107, level: "noise" }
])
```

```text
{
  acknowledged: true,
  insertedCount: 7,
  insertedIds: {
    '0': 101, '1': 102, '2': 103, '3': 104,
    '4': 105, '5': 106, '6': 107
  }
}
```

```js
while (true) {
  const ids = db.noise.find({}, { _id: 1 })
    .sort({ _id: 1 })
    .limit(3)
    .toArray()
    .map(d => d._id)
  if (ids.length === 0) break
  db.noise.deleteMany({ _id: { $in: ids } })
  print("removed", ids.length)
}
```

```text
removed 3
removed 3
removed 1
```

- **固定批大小**：每轮按 _id 升序取固定条数再按 $in 删除，批大小决定单轮的锁持有时间与复制延迟抖动。
- **退出条件**：取不到 _id 说明集合已清空，循环自然结束，不依赖事先知道总数。
- **可中断续跑**：循环每轮独立，中途失败重新执行即可接着删，不会重复劳动。
- **与一次删除的取舍**：一次 deleteMany 写法简单但长事务占锁，分批总耗时更长、过程更平稳。

> [!CAUTION]
> **注意内容**：大删除安排在业务低峰执行，循环里穿插观察复制集延迟与磁盘指标；一次 deleteMany 千万级文档可能拖垮从节点同步，宁可分批慢删也不追求一把删完。



### drop 集合与防误删

#### 删除文档与 drop 集合的差别

**删除文档与 drop 的差别**：deleteMany 只清数据、集合壳与索引照留，drop 把集合连同索引与元数据整体抹掉，二者不在一个层面。

```js
db.logs.drop()
```

```text
true
```

- **索引归属**：deleteMany 后索引定义原样保留，drop 后索引随集合一起消失，重建集合必须重新建索引。
- **集合归属**：deleteMany 后集合继续存在，find 返回空数组；drop 后集合不存在，find 同样返回空数组但 insert 会触发隐式建集。
- **性能差异**：文档量极大时，drop 走元数据级删除远快于逐篇删除的 deleteMany。
- **统计归零**：drop 同时清掉集合的统计信息与 UUID，监控与审计视角下这是比清数据更重的操作。

> [!CAUTION]
> **注意内容**：只想清数据时误用 drop，重建集合后全部索引消失、查询性能塌方且难以立即察觉。判断标准是「还要不要这个集合」——要，用 deleteMany；不要，才用 drop。



#### 防误删实践

**防误删实践**：是围绕删除操作的一组流程约束，核心是把「确认匹配范围」放在「执行删除」之前。

- **先查后删**：用与删除完全相同的条件先 find，返回的文档就是将被删除的文档。
- **计数比对**：删除前用 countDocuments 对条件计数，与预期条数比对，不一致即中止。
- **优先 _id**：能用 _id 精确定位就不用宽泛条件，把误伤面收敛到一篇。
- **变量化条件**：把 filter 定义成常量供 find、count、delete 复用，避免查询与删除用了两个不同的条件。
- **权限与备份**：生产环境把删除权限收敛到专职账号，重要集合清理前先备份或留存快照。
- **灰度验证**：新写好的删除逻辑先在预发或影子库验证删除范围，确认无误再上生产。

```js
const filter = { level: "warn" }
db.logs.countDocuments(filter)
db.logs.find(filter)
db.logs.deleteMany(filter)
```

```text
1
[ { _id: 7, level: 'warn', message: '慢查询告警', createdAt: ISODate('2026-09-23T09:00:00Z') } ]
{ acknowledged: true, deletedCount: 1 }
```

> [!IMPORTANT]
> **重要内容**：删除操作的风险不在语法而在条件，绝大多数误删源于条件写宽、字段名拼错或复制粘贴残留。先查后删加计数比对两步走，配合变量化条件保证三处同源，能挡住最常见的全部事故。



#### 软删除的取舍

**软删除**：是不执行物理删除、改用删除时间戳做标记的做法，文档留在集合里，查询侧用标记字段过滤出「仍然有效」的数据。

```js
db.tasks.insertMany([
  { _id: 1, title: "整理周报", done: true },
  { _id: 2, title: "更新依赖", done: false }
])
db.tasks.updateMany({ done: true }, { $set: { deletedAt: new Date() } })
db.tasks.find({ deletedAt: null })
```

```text
{
  acknowledged: true,
  insertedCount: 2,
  insertedIds: { '0': 1, '1': 2 }
}
{ acknowledged: true, matchedCount: 1, modifiedCount: 1 }
[ { _id: 2, title: '更新依赖', done: false } ]
```

- **标记方式**：删除动作变成给 deletedAt 写入当前时间，未删除的文档该字段为 null，查找有效数据用 deletedAt 为 null 作条件。
- **可恢复**：把 deletedAt 置回 null 即恢复数据，误删可挽回，这是软删除最大的价值。
- **隐性成本**：集合里所有业务查询都要补过滤条件，唯一索引、统计口径、关联查询随之复杂。
- **选择标准**：要求可追溯或误删代价高的数据用软删除，日志、缓存、可再生数据用物理删除。
- **清理期限**：软删除数据本身也要有到期物理清理策略，否则集合随时间无限膨胀。

> [!TIP]
> **建议内容**：两种删除不互斥，常见分层是业务层一律软删除、后台任务按保留期限对标记数据做物理清理。选择前先确认数据的恢复需求与合规要求，再定删除策略。
