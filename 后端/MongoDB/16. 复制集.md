## 复制集

### 复制集基础

#### 复制集的构成与作用

**复制集（Replica Set）**：是一组**维护同一数据集的 mongod 进程**，通过内部日志复制保持数据一致，对外提供数据冗余与高可用，是 MongoDB 生产部署的最低形态。

- **基本构成**：一个 primary 成员负责处理全部写入，若干 secondary 成员异步复制主节点的写操作，成员数取奇数以保证选举能形成多数派。
- **高可用作用**：primary 宕机时剩余成员自动选举新主，写入在数秒内恢复，无需人工介入。
- **冗余作用**：数据在多个成员上各存一份，单机磁盘损坏不丢数据；备份与慢查询分析可固定在专用 secondary 上，不干扰主库。

```js
// 查看当前成员所属复制集的状态
rs.status()
```

```text
{
  set: 'rs0',
  myState: 1,
  members: [
    { _id: 0, name: 'node1:27017', stateStr: 'PRIMARY', health: 1 },
    { _id: 1, name: 'node2:27017', stateStr: 'SECONDARY', health: 1 },
    { _id: 2, name: 'node3:27017', stateStr: 'SECONDARY', health: 1 }
  ],
  ok: 1
}
```

> 复制集的本质是「多份数据、一个主节点、自动选主」。单机 mongod 故障即服务中断；换成复制集，任意一台 secondary 宕机不影响读写，primary 宕机只损失数秒写入窗口。



#### oplog 操作日志

**oplog（operations log）**：是 primary 记录每一次写操作的**固定大小循环集合**，保存在 local 库的 oplog.rs 中，secondary 持续拉取并按序重放，从而把主节点的修改复制到自己身上。

- **循环集合**：oplog 是 capped collection，写满后从最旧记录开始覆盖，因此只保留最近一段时间的操作，这段保留时长叫 oplog 窗口。
- **幂等重放**：oplog 记录的是操作产生的数据效果（如更新后的目标值），secondary 重复重放同一条记录不会引入偏差。
- **同步下限**：secondary 落后主节点的时间一旦超过 oplog 窗口，增量同步断链，只能触发代价高昂的全量初始同步；写压力越大的集群越要盯紧这个窗口。

```js
// 查看最近两条 oplog 记录
use local
db.oplog.rs.find().sort({ $natural: -1 }).limit(2)
```

```text
switched to db local
{
  op: 'i',
  ns: 'shop.orders',
  ts: Timestamp({ t: 1727000200, i: 1 }),
  o: { _id: ObjectId('665f1a2b3c4d5e6f708192a4'), item: 'keyboard', price: 199 }
}
{
  op: 'u',
  ns: 'shop.orders',
  ts: Timestamp({ t: 1727000100, i: 3 }),
  o2: { _id: ObjectId('665f1a2b3c4d5e6f708192a1') },
  o: { $set: { price: 189 } }
}
```

> oplog 是复制的「心脏」：secondary 有延迟是因为重放异步，全量初始同步昂贵是因为窗口外没有增量可追。运维上把 oplog 窗口时长与最慢 secondary 的落后时长做成监控项，是避免同步断链的标准做法。



#### 初始同步与增量同步

**初始同步（initial sync）**：是新成员加入复制集时把源节点完整数据复制一份的过程；完成之后的日常复制叫增量同步，靠持续重放 oplog 追平进度。

- **同步来源**：初始同步默认从当前 primary 或已有 secondary 拷贝全部集合、文档与索引，选择哪个源由同步源选择策略决定。
- **备份恢复路径**：数据量大时，先用物理备份把数据恢复到新节点磁盘，再让增量同步追平，能显著缩短新节点上线时间。
- **失败重来**：初始同步期间源节点的 oplog 覆盖了同步所需的记录时，同步失败、从头再来；这正是大容量 oplog 的价值所在。
- **链式复制**：secondary 默认从最近的同步源拉取 oplog 而非一定从 primary 拉，链式结构减轻主库压力，但会放大末端的复制延迟。

```js
// 查看当前节点与各从节点的复制进度
rs.printSecondaryReplicationInfo()
```

```text
source: node2:27017
{
  syncedTo: 'Mon Sep 21 2026 10:20:00 GMT+0800 (CST)',
  replLag: '0 secs (0 hrs) behind the primary'
}
---
source: node3:27017
{
  syncedTo: 'Mon Sep 21 2026 10:18:30 GMT+0800 (CST)',
  replLag: '90 secs (0 hrs) behind the primary'
}
```

> 初始同步与增量同步的分界，决定了「加节点要多久」与「副本落后多久」。巡检时重点看 replLag 是否持续增大：持续增大说明重放跟不上，先查 oplog 窗口与从节点负载，再查是否被链式复制放大。



### 成员角色与选举

#### 成员角色：primary、secondary 与 arbiter

**成员角色**：复制集成员按「是否存数据、是否可被选主、是否投票」分为 primary、secondary、arbiter 三类，一个成员在任一时刻只扮演其中一种。

- **primary（主节点）**：唯一接受写入的成员，默认也是读请求的目标，所有写操作先落它的 oplog 再向外复制。
- **secondary（从节点）**：拉取并重放 primary 的 oplog 保持同步，可进一步配置为延迟节点、隐藏节点或优先级为零的纯数据副本。
- **arbiter（仲裁者）**：不存储数据、不可被选为主，只参与投票；用最小的资源把成员数凑成奇数，帮助选举形成多数派。

> [!CAUTION]
> **注意内容**：arbiter 不保存数据，「两个数据成员加一个 arbiter」的集群里数据实际只有两份。生产环境优先采用三个带数据的投票成员，arbiter 只留给数据丢失可容忍或资源极度受限的部署。



#### 选举机制与 priority

**选举（election）**：primary 不可达或被人为触发时，具备资格的投票成员通过类 Raft 协议在数秒内选出新 primary，priority 配置直接干预谁能当选。

- **多数派原则**：候选者必须拿到投票成员的多数票才能成为 primary，因此投票成员数应配成奇数；偶数成员并不能提高可用性，只会让平票更可能出现。
- **priority 的引导作用**：priority 取值 0 到 1000，默认为 1，值高者优先当选；多个成员在线时，高优先级成员会主动发起选举取代低优先级的现任 primary。
- **priority 为 0 的成员**：永远不会成为 primary，也不能发起选举，但仍保留投票权，适合跨机房的冷备或纯数据冗余节点。
- **投票成员上限**：一个复制集最多七个投票成员，超出部分仍可作数据副本，只是不参与投票。

```js
// 把第三个成员的优先级调到最高，让选举倾向于选它做 primary
cfg = rs.conf()
cfg.members[2].priority = 10
rs.reconfig(cfg)
```

```text
{ ok: 1 }
```

> 选举不是随机事件，而是被 priority 引导的确定性过程。跨机房部署时把主机房成员的 priority 调高，机房恢复后主库自动切回，流量随之回归，无需人工干预。



#### 故障自动转移过程

**故障自动转移（automatic failover）**：primary 失联后，复制集在默认约十秒内自动完成检测、选举与切换，对应用表现为短暂写不可用、读请求按读偏好降级。

完整过程分四步：

1. 每个成员每两秒向其余成员发送心跳，对方连续无响应超过默认十秒即判定为失联。
2. 具备被选举资格的成员发起选举，向其他投票成员征求选票。
3. 获得多数票的成员升为 primary；旧 primary 若随后恢复，会降级为 secondary。
4. 驱动感知新拓扑，把写请求路由到新 primary；切换期间未复制到多数派的写会被回滚，回滚数据以文件形式落盘供人工回补。

- **回滚不丢数据**：被回滚的写以 rollback 文件保留在旧 primary 的数据目录，可人工比对后回补。
- **应用侧配合**：可重试写（retryable writes）让驱动在主从切换时自动重试同一次写，对业务透明。
- **写关注兜底**：writeConcern 为 majority 的写一定已复制到多数派，切换后不会回滚，是关键数据的默认选择。

> [!IMPORTANT]
> **重要内容**：故障转移的十秒窗口是设计预期而非故障，应用侧的标准准备是可重试写与 majority 写关注——前者吸收切换抖动，后者保证已确认的写不因回滚消失。两者齐备，十秒级中断对绝大多数业务无感。



#### 延迟节点与隐藏节点

**延迟节点（delayed member）与隐藏节点（hidden member）**：是 secondary 的两种特殊配置——延迟节点把重放推迟固定秒数以保留「误操作现场」，隐藏节点对客户端路由不可见、只承担内部任务。

- **延迟节点**：延迟秒数设为正值（如 3600 秒），oplog 重放比 primary 慢固定时长，误删集合后可以从它抢救数据。
- **隐藏节点**：hidden 设为 true 后读偏好路由永远不选它，但照常投票与复制，常用于承载备份、报表这类不希望影响在线读的负载。
- **组合要求**：延迟节点通常同时设为 hidden，避免客户端读到过期数据；两者都应配 priority 0。

```js
// 把第三个成员配置为一小时的延迟隐藏节点
cfg = rs.conf()
cfg.members[2].priority = 0
cfg.members[2].hidden = true
cfg.members[2].secondaryDelaySecs = 3600
rs.reconfig(cfg)
```

```text
{ ok: 1 }
```

> 延迟节点的价值依赖 oplog 窗口覆盖延迟时长：延迟一小时，oplog 至少要保留一小时以上，否则延迟节点重放断链，反而变成需要全量同步的负担。延迟是误操作的保险，不是备份的替代。



### 读偏好 readPreference

#### 读偏好的五种模式

**读偏好（readPreference）**：是驱动为每次读请求选择目标成员的规则，五种模式覆盖从「必须最新」到「就近可读」的全部取舍。

- **primary**：只读主节点，读到的一定是最新已确认数据，为默认模式。
- **primaryPreferred**：优先主节点，主节点不可用时降级读 secondary。
- **secondary**：只读从节点，用于把报表、分析类流量与主库隔离。
- **secondaryPreferred**：优先从节点，全部从节点不可用时回落主节点。
- **nearest**：读网络延迟最低的成员，不区分主从；驱动以最快成员为基准，把延迟差在默认 15 毫秒窗口内的成员都视为候选，多机房部署下用于压低读延迟。

> secondary 的数据是异步复制的，选 secondary 类模式等于接受「可能读到数秒前的旧数据」。读偏好不是性能开关，而是一致性与延迟之间的选择器，按每次读的容忍度逐类指定。



#### 读偏好的设置层级与一致性代价

**读偏好的设置层级**：连接串、数据库、集合、单次操作四个层级都可指定，越靠近操作优先级越高，跨层级混用时以最内层为准。

```js
// 连接串层指定：本连接的读默认走从节点
// mongodb://node1:27017,node2:27017,node3:27017/shop?replicaSet=rs0&readPreference=secondaryPreferred

// 单次操作层覆盖：下单后的确认查询必须读主节点
db.orders.find({ orderId: 1001 }).readPref("primary")
```

```text
[
  {
    _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
    orderId: 1001,
    item: 'keyboard',
    price: 189,
    status: 'paid'
  }
]
```

- **一致性代价**：以 majority 写入成功后立刻用 secondary 类读偏好查询，仍可能读不到这条新数据，因为从节点尚未重放到。
- **补救手段**：会话级因果一致性（causal consistency）保证「读己之写」；最直接的方案是关键读路径固定走 primary。
- **maxStalenessSeconds**：secondary 类模式下可设置从节点的最大落后秒数（最小 90 秒），落后超限的成员被剔除出读候选，给「读旧」划定上界。

> [!CAUTION]
> **注意内容**：读偏好只决定流量去向，「写后读」的一致性由 writeConcern、会话与读偏好的组合保证，三者不能互相替代。把报表查询指到 secondary 是常规操作，把「下单后立刻查订单」指到 secondary 是生产事故的固定剧本。



#### 标签与定向读取

**标签（tag）**：是给复制集成员打上的自定义键值对，读偏好可以附带标签数组，把读请求定向到符合标签的成员，实现机房级或角色级的流量隔离。

- **配置方式**：rs.conf() 里给成员加 tags 字段（如 region: "hangzhou"），reconfig 后生效。
- **定向读取**：读偏好附带标签数组时，驱动先按模式筛出候选成员，再按标签过滤，两组条件同时满足的成员才有资格承接请求。
- **叠加过滤**：标签可与 maxStalenessSeconds 同时指定，进一步收紧候选范围。
- **典型用法**：给报表专用 secondary 打 role: "report" 标签，让分析流量永远不落在线主从节点上。

```js
// 给成员打标签：报表专用
cfg = rs.conf()
cfg.members[2].tags = { role: "report" }
rs.reconfig(cfg)

// 读请求带标签定向到报表节点
db.orders.find({ status: "paid" }).readPref("secondary", [{ role: "report" }])
```

```text
[
  {
    _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
    orderId: 1001,
    status: 'paid',
    price: 189
  }
]
```

> 标签是把「哪类查询去哪台机器」写成配置的手段。标签与成员一一对应，修改要走 rs.reconfig，频繁变化的维度不适合做成标签。



### 复制集搭建要点

#### 用 rs.initiate 搭建三节点复制集

**rs.initiate**：是把多个以 replSet 模式启动的独立 mongod 组成复制集的入口命令，核心动作是把一份包含全部成员的配置文档写入集群。

第一步，各节点以相同的复制集名启动：

```bash
mongod --dbpath /data/rs0-0 --port 27017 --replSet rs0 --fork --logpath /data/rs0-0/mongod.log
mongod --dbpath /data/rs0-1 --port 27018 --replSet rs0 --fork --logpath /data/rs0-1/mongod.log
mongod --dbpath /data/rs0-2 --port 27019 --replSet rs0 --fork --logpath /data/rs0-2/mongod.log
```

第二步，连接任一节点写入配置：

```js
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "node1:27017" },
    { _id: 1, host: "node2:27017" },
    { _id: 2, host: "node3:27017" }
  ]
})
```

```text
{ ok: 1 }
```

- **启动顺序**：三个 mongod 全部就绪后再执行 rs.initiate，配置里的 host 必须与各节点实际监听的地址一致且互相可解析。
- **验证**：rs.status() 确认成员状态，期望一个 PRIMARY 与两个 SECONDARY，health 均为 1。
- **扩容**：向已初始化的复制集加节点用 rs.add("新主机:端口")，新节点先全量同步再进入常规复制，不需要重跑 rs.initiate。

> 搭建失败的最常见原因是 host 写错：配置里写了某台机器的主机名，而成员之间解析不了这个名字，节点会长期停在 STARTUP2 或 OTHER 状态。先保证主机名互通，再初始化复制集。



#### keyFile 内部认证

**keyFile**：是复制集成员之间做内部认证的共享密钥文件，同一复制集的所有成员持有相同内容；配置它之后成员间通信必须互相验明身份，同时隐式开启客户端访问控制。

生成与分发：

```bash
openssl rand -base64 756 > /etc/mongodb/keyfile
chmod 400 /etc/mongodb/keyfile
chown mongodb:mongodb /etc/mongodb/keyfile
```

成员配置启用：

```bash
# /etc/mongod.conf 增加 security 段
security:
  authorization: enabled
  keyFile: /etc/mongodb/keyfile
```

- **内容要求**：长度 6 到 1024 个字符，只含 base64 字符集，生成后不做手工编辑。
- **权限要求**：文件权限固定为 400，属主为运行 mongod 的系统用户，权限过宽会导致 mongod 拒绝启动。
- **一致要求**：所有成员的文件内容逐字节相同，任何一个成员不一致都会被集群拒绝加入。

> [!WARNING]
> **警告内容**：keyFile 只解决成员间认证，不提供传输加密，是安全方案的底线而非终点。生产环境具备条件时应改用 x.509 证书做内部认证并启用 TLS；无论哪种方案，密钥文件的分发与存放都要纳入安全管理。
