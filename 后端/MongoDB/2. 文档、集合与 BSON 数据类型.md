## 文档、集合与 BSON 数据类型

### 文档的结构

#### 字段与键的书写规则

**文档字段**：是「字符串字段名＋字段值」的成对结构，字段值可以是 BSON 支持的任意类型，一份文档内的字段名不得重复。

- **字段名类型**：字段名一律是字符串，区分大小写，name 与 Name 是两个不同字段。
- **保留字段**：_id 是保留字段，作用等同主键，集合内取值必须唯一，缺省时由服务端自动生成。
- **重复键**：同一文档出现重复字段名时行为未定义，驱动与工具不会拦截，必须从写入侧杜绝。
- **特殊字符**：字段名可以包含中文与空格，但点号与美元符号在查询语法里有特殊含义，命名时应避开。

```json
{
  "_id": 1,
  "name": "林晓",
  "age": 28,
  "name": "重复字段，禁止这样写"
}
```

> [!CAUTION]
> **注意内容**：字段命名一旦上线就很难再改，命名规范要在第一个集合落库前定下来——统一小驼峰、避开点号与美元符号、不用中文做字段名；中文可放进字段值，不宜放进字段本身。



#### 字段的有序性

**字段有序**：BSON 文档保留字段的写入顺序，服务端按原样存储与返回，顺序是文档的一部分。

- **写入顺序保留**：先写 name 后写 age，读回来的顺序仍是 name 在前 age 在后。
- **_id 提前**：服务端写入时会把 _id 挪到文档最前面，其余字段保持相对顺序不变。
- **相等匹配区分顺序**：用整份文档做条件时，{ a: 1, b: 2 } 与 { b: 2, a: 1 } 是两份不同的文档，互不匹配。
- **字段级匹配不区分顺序**：按 { "address.city": "杭州" } 这类路径取值时与顺序无关，只看值。

```js
db.profiles.insertOne({ name: "林晓", age: 28 })
db.profiles.findOne()
```

```text
{
  _id: ObjectId('6ab31680a1b2c3d4e5f60718'),
  name: '林晓',
  age: 28
}
```

> 依赖字段顺序写代码是隐患：新业务插入字段、人工修数都会打乱顺序，查询与投影一律按字段名取值，顺序只当作展示层面的偶然现象。



#### 嵌套文档与数组

**嵌套结构**：文档的字段值本身可以是另一份文档或数组，嵌套深度没有硬性上限， MongoDB 官方建议控制在百层以内。

- **嵌套文档**：字段值是完整文档，用点号路径逐层访问，如 address.city。
- **数组**：字段值是数组，元素类型可混合，可存标量也可存整份文档。
- **文档数组**：数组元素是文档时，构成一对多的内嵌表达，订单与订单项、作者与书籍都这样建模。
- **定位访问**：数组元素按下标访问，规格写成 tags.0 或 items.1.price 这类路径。

```json
{
  "name": "林晓",
  "address": { "city": "杭州", "district": "西湖区" },
  "tags": ["backend", "mongodb"],
  "orders": [
    { "item": "键盘", "price": 199 },
    { "item": "鼠标", "price": 79.9 }
  ]
}
```

> 建模取向是「一起读的数据内嵌，分开长的数据引用」：内嵌减少查询次数，但单份文档上限为 16MB，无限增长的子列表（如所有历史订单）必须拆成独立集合，不能一味内嵌。



### BSON 与 JSON 的关系

#### BSON 的定位

**BSON（Binary JSON）**：是 JSON 的二进制序列化格式，语法上是 JSON 的超集，存储与网络传输均使用 BSON。

- **二进制高效**：每个字段带类型与长度前缀，服务端可以跳过不匹配的字段快速扫描，比逐字符解析文本 JSON 快。
- **类型超集**：JSON 只有 string、number、boolean、null、object、array 六种，BSON 额外定义了 32 位整数、64 位整数、128 位十进制小数、日期、ObjectId、二进制数据等类型。
- **可遍历**：带长度信息意味着不必读完整个文档就能定位字段，这是文本格式做不到的。

> [!IMPORTANT]
> **重要内容**：JSON 与 BSON 的关系要记牢——JSON 是人类可读的表达，BSON 是机器高效的存储；JSON 表达不了整数与小数的精度差异，BSON 用独立类型补齐，两者的类型系统不是一一对应的。



#### BSON 类型与 JSON 类型的对应

**类型对应**：JSON 的六种类型都能映射进 BSON，反向则多出一批 JSON 没有的类型。

- **string 对 string**：文本类型，两端一致。
- **number 对 double 与 int 与 long 与 decimal**：JSON 只有一种数，BSON 细分为 double、int、long、decimal 四种，这是最大的差异点。
- **boolean 与 null 原样对应**：两端语义一致。
- **object 对 document**：JSON 对象映射为 BSON 文档。
- **array 对 array**：两端一致，元素各自映射。
- **BSON 独有**：date（日期）、objectId（文档标识）、binData（二进制）、timestamp（内部时间戳）等类型在纯 JSON 中没有对应物。

> 面向表达时记住一句话：凡 JSON 写得出的 BSON 都能存，BSON 存得下的 JSON 未必写得准，整数、小数、日期三类是最常出问题的位置。



#### Extended JSON 与往返转换

**Extended JSON**：是 BSON 的 JSON 文本表达规范，用保留键表达 BSON 独有类型，是导出导入与调试时的标准桥梁。

- **类型保留**：BSON 转 JSON 时，日期写成 $date，ObjectId 写成 $oid，二进制写成 $binary，转回 BSON 时不丢类型。
- **普通 JSON 的损耗**：不带 Extended JSON 标注的普通 JSON 文件导入后，数字按 double 处理、日期按字符串处理，类型信息丢失。

```json
{
  "_id": { "$oid": "6ab31680a1b2c3d4e5f60718" },
  "item": "键盘",
  "price": { "$numberDecimal": "1999.00" },
  "createdAt": { "$date": "2026-09-23T00:30:00.000Z" }
}
```

> 在不同系统之间导数据时，先确认对端认不认 Extended JSON；两边都支持就用它保住类型，一边不支持就要在应用层手工转换，日期与小数是必查项。



### ObjectId

#### ObjectId 的构成

**ObjectId**：是 12 字节的 BSON 类型，以 24 个十六进制字符的字符串形式展示，是 _id 的缺省类型。

- **前 4 字节**：Unix 时间戳（秒），记录文档创建的大致时刻。
- **中间 5 字节**：进程级随机值，每个 mongod 或 mongosh 进程启动时生成一次，同进程内不变。
- **末 3 字节**：递增计数器，初值随机，同一进程内每生成一个就加一，保证同秒内不重复。

```text
6a b3 16 80 | a1 b2 c3 d4 e5 | f6 07 18
时间戳 4 字节 | 随机值 5 字节   | 计数器 3 字节
```

> [!IMPORTANT]
> **重要内容**：24 个十六进制字符对应 12 字节是换算关系（1 字节＝2 个十六进制字符）；三段式结构保证「不同机器、不同进程、同一秒」生成的 ObjectId 也不冲突，这正是它能放心当缺省主键的原因。



#### ObjectId 的生成与时间提取

**生成规则**：写入文档未给 _id 时，驱动或外壳自动补一个 ObjectId；mongosh 提供方法从现有 ObjectId 反推创建时间。

```js
ObjectId("6ab31680a1b2c3d4e5f60718").getTimestamp()
ObjectId("6ab31680a1b2c3d4e5f60718").valueOf()
```

```text
ISODate("2026-09-23T00:00:00.000Z")
'6ab31680a1b2c3d4e5f60718'
```

- **自动生成时机**：insertOne 等写入命令未带 _id 时由服务端生成，客户端驱动也可提前生成以便分批插入时先行关联。
- **getTimestamp 方法**：把前 4 字节换算为 UTC 时间，精确到秒，可用于按创建时间粗略过滤。
- **手工指定**：业务已有天然唯一键（如订单号）时，可让它充当 _id，不必都用 ObjectId。

> [!CAUTION]
> **注意内容**：ObjectId 只保证「大致时间有序」，不能当精确时间戳用——它取的是生成时刻的秒级时间，且客户端与服务端时钟可能不一致；需要精确的创建时间，应单独存一个 date 字段。



#### 依据 ObjectId 排序与分页

**时间有序的利用**：ObjectId 前段是时间戳，按 _id 升序大致等价于按创建时间升序，缺省无创建时间字段的集合常借它排序分页。

```js
db.logs.find().sort({ _id: 1 }).limit(2)
```

```text
[
  { _id: ObjectId('6ab31680a1b2c3d4e5f60718'), event: 'login' },
  { _id: ObjectId('6ab31680a1b2c3d4e5f60719'), event: 'logout' }
]
```

- **排序即索引**：_id 上自带唯一索引，按 _id 排序走索引，比给大表另建时间字段索引省一次开销。
- **游标分页姿势**：翻页条件写成 { _id: { $gt: 上一页最后一个 _id } } 加 limit，避免 skip 深翻页的扫描浪费。
- **适用边界**：时钟回拨、多客户端并发生成时顺序可能局部颠倒，对顺序严格的流水要另存自增序号或精确时间。

> 「按 _id 排序＝按时间排序」是 ObjectId 时间戳前段的直接推论，也是游标分页的惯用基础；记住它的前提是 ObjectId 由服务端在写入时刻生成，客户端预生成或手工构造会引入偏差。



### 数值与日期类型

#### 数值类型全景

**数值类型**：BSON 提供四种数值类型，精度与范围各不相同，选错类型会直接造成计算误差。

- **Double**：64 位双精度浮点，BSON 的「默认数」，范围大但有二进制精度误差。
- **Int32**：32 位有符号整数，范围约正负 21 亿，计数器、分页数量这类小整数够用。
- **Long**：64 位有符号整数，范围约正负 9.2×10 的 18 次方，大 ID、大计数用它。
- **Decimal128**：128 位十进制小数，34 位有效数字按十进制精确表示，金额计算专用。

```text
Double      二进制浮点    近似值    科学计数、比例
Int32       4 字节整数    精确      小整数计数
Long        8 字节整数    精确      大整数计数
Decimal128  十进制 34 位  精确      金额、费率
```

> 选择口诀按用途走：整数看范围选 Int32 或 Long，金额与小数一律 Decimal128，只有比值、权重、坐标这类允许近似的量才用 Double。



#### mongosh 的默认数值类型

**默认类型**：mongosh 基于 JavaScript 运行时，JS 的 number 只有双精度一种，因此直接写的整数也会按 Double 存入。

```js
db.samples.insertOne({ a: 42, b: 3.14 })
db.samples.aggregate([
  { $project: { ta: { $type: "$a" }, tb: { $type: "$b" } } }
])
```

```text
[ { _id: ObjectId('6ab31680a1b2c3d4e5f60718'), ta: 'double', tb: 'double' } ]
```

- **42 也是 Double**：mongosh 里字面量 42 的 $type 是 double，与直觉相反，这是 mongosh 与旧版 mongo 外壳的最大行为差异之一。
- **显式指定**：需要精确类型时用构造器——Int32(42)、Long("5000000000")、NumberDecimal("19.99")。
- **查询同样生效**：{ price: 19.99 } 匹配的是 Double 类型的 19.99，与 Decimal128 类型的 19.99 不会互相命中。

> [!CAUTION]
> **注意内容**：从旧资料迁移来的写法可能默认整数落为 int，在 mongosh 里是 double；涉及与 Int32 字段做相等查询或索引匹配时，先用 $type 抽查真实存储类型，别凭字面量长相判断。



#### Decimal128 与货币精度

**Decimal128**：按十进制逐位存小数的 128 位类型，19.99 就是精确的 19.99，是金额字段的唯一正确选择。

```js
db.orders.insertOne({ item: "键盘", price: 19.99 })
db.orders.aggregate([
  { $project: { cents: { $multiply: ["$price", 100] } } }
])
```

```text
[ { _id: ObjectId('6ab31680a1b2c3d4e5f60718'), cents: 1998.9999999999998 } ]
```

Double 存的 19.99 实际是二进制近似值，乘 100 后误差显形。换成 Decimal128 再看：

```js
db.orders2.insertOne({ item: "键盘", price: NumberDecimal("19.99") })
db.orders2.aggregate([
  { $project: { cents: { $multiply: ["$price", 100] } } }
])
```

```text
[ { _id: ObjectId('6ab31680a1b2c3d4e5f60719'), cents: Decimal128("1999.00") } ]
```

- **误差来源**：Double 用二进制表示十进制小数，0.01 这类分母含因子 5 的数无法精确表示，累加与乘除后误差暴露。
- **写入姿势**：NumberDecimal 必须接收字符串，写成 NumberDecimal(19.99) 会先经过 Double 再转，误差已经发生。
- **配套纪律**：金额字段全链路（写入、聚合、导出）都用 Decimal128，中途混入一次 Double 就前功尽弃。

> [!IMPORTANT]
> **重要内容**：凡是钱，一律 NumberDecimal 加字符串字面量；Double 只配用于比率与坐标。1998.9999999999998 与 1999.00 的对比是最常考的数值精度题，理解「近似类型」与「精确类型」的差异即可现场推导。



#### 日期类型与时区

**BSON 日期**：date 类型存「距 1970-01-01 的毫秒数」，内部永远是 UTC，外壳显示时也以 UTC 的 ISODate 呈现。

```js
db.events.insertOne({ name: "备份", at: new Date("2026-09-23T08:30:00+08:00") })
db.events.findOne()
```

```text
{
  _id: ObjectId('6ab31680a1b2c3d4e5f60720'),
  name: '备份',
  at: ISODate("2026-09-23T00:30:00.000Z")
}
```

- **写入即转 UTC**：带 +08:00 时区的时间写入后转成 UTC 毫秒数，读回来的 Z 结尾时间与写入的本地时间相差时区偏移，数据本身没有错。
- **范围查询用毫秒语义**：{ at: { $gte: new Date("2026-09-23T00:00:00Z") } } 这类比较在服务端按毫秒数进行，与时区无关。
- **不要用字符串存时间**：字符串日期无法参与范围索引比较与日期运算， Historical 数据迁移时必须先转成 date 类型。

> [!CAUTION]
> **注意内容**：看到 ISODate 的时间「少了八小时」不要急着改数据，那是 UTC 显示与本地时区的差；真正的错误姿势是存字符串时间或手工加减时区，统一「存储用 UTC、展示层转本地」一条路走到底。
