## WiredTiger 存储引擎

### 定位与并发模型

#### 默认存储引擎的地位

**WiredTiger**：是 MongoDB 自 3.2 版本起的默认存储引擎，负责把文档与索引组织落盘、管理内存缓存、提供并发控制与崩溃恢复能力；MongoDB 8.0 只内置这一个引擎，部署时无需再做选择。

- **职责边界**：查询解析与执行计划生成由服务端其他模块完成，存储引擎只决定数据在磁盘与内存之间的组织方式。
- **替代者已退场**：旧引擎 mmapv1 在 4.0 弃用、4.2 移除，如今的 MongoDB 论及存储即指 WiredTiger。
- **可调层面**：缓存大小、块压缩算法、journal 刷盘间隔以配置项形式暴露；树结构、版本链、锁这些内核机制不开放干预。
- **入口统一**：引擎的全部可调项集中在配置文件的 storage 段与建表选项两处，没有游离的开关散落在别的配置里。

> 版本口径记两条就够：3.2 起默认、4.2 起 mmapv1 移除。凡是按 mmapv1 讲锁粒度与内存占用的旧资料，阅读时都要按 WiredTiger 的模型重新换算，结论往往相反。



#### 文档级并发控制

**文档级并发**：指 WiredTiger 的写锁粒度是单个文档——两个请求改不同的文档互不阻塞，只有改同一份文档才会串行等待。

- **对比旧引擎**：mmapv1 的写锁粒度是集合级，一个集合上的写入会挡住同集合的其他写；WiredTiger 把冲突范围缩小到文档，写并发能力由此质变。
- **意向锁**：数据库级与集合级持有的是意向锁，只标记「下层存在文档锁」而不做整集合排斥，读写因此可以大量并行。
- **锁的层次**：从全局、数据库、集合到文档逐层收窄，上层意向锁配合下层文档锁，宽范围的读与细粒度的写各走各路。
- **锁的持有时间**：文档锁随单次修改即取即放，不跨越多条语句，会话层面不需要显式的加锁与解锁命令。
- **热点文档是例外**：计数器、秒杀库存这类被集中写的单文档，会让文档级并发退化成单点排队，建模时应拆分或换方案。

> 「MongoDB 写锁锁全表」是 mmapv1 时代的结论，迁移旧认知时务必更新：现在的争用发生在文档级，性能问题先查热点文档，再谈锁与并发参数。



#### 写冲突与 WriteConflict

**WriteConflict**：是两个写操作竞争同一份文档时，服务端让后到者收到的冲突错误——它不是故障，而是文档级并发的正常调度结果。

- **触发条件**：并发的两个写落在同一份文档上，或正在进行的扫描范围被并发提交的写改变，扫描方收到冲突。
- **冲突的表现**：多数驱动对瞬态冲突自动重试，应用层通常无感；冲突持续发生时错误才冒泡成可见的异常。
- **代价的落点**：每次冲突意味着一次作废重来的工作量，冲突率高的集合，吞吐上限由冲突率而非硬件决定。
- **治本的位置**：冲突治理在建模层——拆分热点文档、把「读改写」改成条件更新，比调任何并发参数都有效。
- **与事务的关系**：事务把多份文档纳入同一个写集合，交集概率随之上升，冲突重试的代价比单文档写更高。

> WriteConflict 频繁出现是一份建模体检报告：它在提示某个文档被过度集中地写。与其在客户端加重试逻辑硬扛，不如把热点拆掉，让并发恢复文档级本来的粒度。



#### mmapv1 的历史脉络

**mmapv1**：是 3.2 之前的默认存储引擎，直接把数据文件映射进进程地址空间读写，4.0 起弃用、4.2 起彻底移除。

- **锁粒度粗**：写锁粒度是集合级，一个集合上的写阻塞同集合的其他写，并发能力远弱于 WiredTiger 的文档级锁。
- **无事务能力**：多文档事务建立在 WiredTiger 的 MVCC 体系之上，mmapv1 从未支持事务。
- **无压缩与预分配**：mmapv1 按预分配文件与填充因子组织数据，磁盘占用与 IO 效率都不如 WiredTiger 的页式加压缩方案。
- **阅读旧资料的标记词**：padding、填充因子、.ns 命名空间文件、集合级写锁，见到这些词即知内容属于 mmapv1 时代，结论不能直接套用。
- **迁移的收益**：换引擎不需要改应用代码，数据文件随升级重建，应用层感知到的只有并发与写入性能的大幅改善。

> mmapv1 的移除不是功能更新，而是整个并发与事务模型的换代：文档级锁、MVCC、多文档事务、块压缩全部建立在 WiredTiger 之上。翻阅 4.2 之前的资料时，先核对存储引擎口径，再决定是否吸收结论。



### MVCC 与快照

#### MVCC 与快照读

**MVCC（多版本并发控制）**：是 WiredTiger 给每次修改保留旧版本、让读操作按某一时刻**快照**取数据的机制——读走旧版本，写追加新版本，读写互不阻塞。

- **读写不互斥**：读拿到快照后沿版本链取数据，写入在旁边继续追加新版本，读不挡写、写也不挡读。
- **快照的含义**：快照定义了「哪些事务的写对本次读可见、哪些不可见」，副本集的 oplog 时间戳为各节点对齐快照提供基准。
- **与 readConcern 的关系**：readConcern 选择读哪个快照——local 读最新可见快照，snapshot 保证一个事务内多次读使用同一快照。
- **与锁的区别**：传统锁让读写排队互斥，MVCC 让读写各自沿着版本与快照并行，代价是磁盘与缓存里多存若干旧版本。
- **快照的生命周期**：单条语句用一个快照读完即弃，事务从开始到提交持有同一个快照，长事务因此拖住旧版本不放。

> MVCC 是引擎层的能力，readConcern 是使用方对能力的选择，两者是机制与策略的关系。理解这一点后，「为什么读不加锁还能一致」与「为什么事务内两次读结果相同」是同一个问题的两种问法。



#### 历史版本的保留与淘汰

**版本链**：是同一文档多次修改在页内串成的更新序列，新版本挂在链头、旧版本依次向后，读方按快照沿链取用，无人引用的旧版本随后被回收。

- **新写不覆盖旧值**：更新把新值挂到链头，旧值保持原位，回滚与快照读因此都只是「不走到链上某个版本」，不需要额外撤销操作。
- **回收时机**：没有任何活跃事务或快照再引用的旧版本，由引擎在后台逐步清出，没有专门的清理停顿。
- **长事务的拖累**：一个存活很久的事务会把它快照所需的整段旧版本全部钉在原地，回收随之停摆。
- **内存代价**：短时间高频修改同一文档会让版本链变长、缓存压力上升，这是热点文档慢的另一个原因，与写冲突重试叠加出现。

> 快照读的免锁是用空间换的：只要还有读方需要旧版本，旧版本就必须留着。压测中观察到缓存占用上涨而数据总量没变，多半是版本链在短期膨胀，缩短事务、降低热点文档的修改频率即可缓解。



#### 因果一致性与读己之写

**因果一致性**：是会话级别的读己之写保证——在开启因果一致性的同一会话里，后一次读保证能看到自己前一次写的结果，跨会话则无此承诺。

```js
// 打开因果一致性会话
const session = db.getMongo().startSession({ causalConsistency: true })
const shop = session.getDatabase("shop")
shop.orders.insertOne({ _id: 9, userId: 42 })
// 同一会话内紧接着读，保证读到刚才的写
shop.orders.findOne({ _id: 9 })
session.endSession()
```

```text
{ _id: 9, userId: 42 }
```

- **解决的问题**：写入后立刻查询却查不到，是读走了回滚旧版本或尚未同步的节点；会话内的因果链保证这种情况不发生。
- **作用范围**：因果链只在同一会话内有效，换一个 session 就回到普通的读关注语义。
- **与事务的关系**：事务内的读己之写由快照隔离天然保证，因果一致性把这种保证延伸到了事务之外的单次读写序列。
- **实现基础**：因果链靠会话内传递操作时间戳实现，每次读写都把 Seen 的时间戳向前推进。

> 「写完读不到」这类诡异现象，先查读写是否落在同一个会话。需要严格的先写后读序列时，用因果一致性会话把两次操作串起来，而不是在应用层反复重试查询。



#### 快照的可见性规则

**快照的可见性规则**：一条修改对某个快照是否可见，取决于它相对快照时刻的提交状态——提交早于快照的可见，未提交或提交晚于快照的不可见，回滚的写视同从未发生。

- **已提交且在前**：提交时间落在快照之前的修改，对所有持有该快照的读可见。
- **未提交一律不可见**：别的会话还在进行中的写，无论改了什么，都不会出现在当前快照的读结果里。
- **提交晚于快照不可见**：同一数据在快照定格之后才提交的新版本，对旧快照的读永远不出现，读到的仍是旧版本。
- **回滚即消失**：随故障回滚的写没有留下任何可读痕迹，这正是 majority 读关注想规避的那类「读到又消失」。
- **判定练习**：拿任意并发时序来套这条规则，凡提交时间落在快照之前即入选，练习多了自然不用背。
- **与隔离级别的对应**：这套规则下读不到脏数据、快照内多次读稳定，正好对应snapshot隔离级别的承诺。

> 可见性规则只有「快照前已提交」一种入选条件，其余一律出局。掌握了这条规则，脏读、不可重复读、幻读这些名词都可以还原成同一句话的不同情形。



### 检查点、journal 与崩溃恢复

#### 页式存储的组织

**页（page）**：是 WiredTiger 在磁盘与缓存之间统一的读写单位——磁盘上的集合树与索引树都按页组织，缓存里驻留的也是页，读入、写出、压缩、淘汰全部以页为边界。

- **页的两类**：内部页存路标，叶页存数据；查询要的那一行在某个叶页里，引擎把整个叶页读进缓存才算拿到。
- **脏页与干净页**：被修改过、尚未刷盘的页是脏页，与磁盘一致的页是干净页；脏页积压到检查点统一写出。
- **访问放大**：哪怕只读一行，代价也是整页；行越小、页内能放的行越多，同样的业务数据触达的页越少。
- **树的层次**：根页到叶页通常三四层，每下一层就把候选范围收窄一个量级，等值查询因此只需触达个位数页。

> 页是理解存储引擎一切行为的分母：缓存占用按页计，IO 次数按页算，压缩在页上做，检查点刷的是脏页。谈性能时把「行」换算成「页」，估算才会准。



#### 检查点机制

**检查点（checkpoint）**：是 WiredTiger 周期性把内存中数据的一致快照整体写入磁盘的动作，默认每 60 秒触发一次，完成后磁盘上总存在一份完整可用的数据状态。

- **落盘内容**：检查点把脏页刷入磁盘并记录一个标记，标记之前的数据全部持久化，之后的新修改留给 journal 接手。
- **触发条件**：默认每 60 秒定时触发，journal 积累的日志量过大时也会提前触发一次，先到者生效。
- **性能影响**：检查点把一段时间的脏页集中写出，磁盘写入出现周期性高峰，压测曲线上规律的锯齿多来自这里。
- **元数据登记**：检查点在磁盘元数据中登记位置，服务重启时按最新有效检查点加载数据。
- **间隔的取舍**：间隔越长，两次检查点之间的修改越依赖 journal 回放，恢复时间越长；60 秒是恢复速度与运行开销之间的折中。

> 检查点回答「磁盘上有多新」的问题：最坏情况下磁盘数据比崩溃时刻旧 60 秒，中间缺口由 journal 补齐。它与 journal 一慢一快分工，在崩溃恢复流程里合拢成完整闭环。



#### journal 日志

**journal**：是预写式日志，写操作先记入 journal 再落数据页，把两次检查点之间的增量改动按时间顺序记录下来，默认约 100 毫秒刷一次盘。

- **先日志后数据**：数据页可以攒到检查点再刷盘，但 journal 必须先行，这是崩溃后能补齐缺口的前提。
- **记录间隔**：由 storage.journal 下的 commitIntervalMs 控制，默认 100 毫秒；配合 writeConcern 的 j 选项，单次写可在确认时保证已落日志。
- **空间占用**：journal 顺序追加持续增长，检查点完成后旧日志段失去存在意义，空间随即被循环复用，磁盘占用因此稳定在可控范围。
- **配置位置**：journal 开关与刷盘间隔都在配置文件的 storage 段里调整。

```bash
# mongod.conf：journal 相关配置
storage:
  journal:
    enabled: true
    commitIntervalMs: 100
```

> journal 的意义是「把随机写变成顺序写」：数据页零散分布，逐页刷盘代价高；journal 顺序追加，廉价且完整。检查点负责定期收口，journal 负责两次收口之间的增量，两者缺一不可。



#### 崩溃恢复流程

**崩溃恢复**：是节点重启后把数据恢复到一致状态的流程——先加载最近的检查点，再按顺序回放检查点之后的 journal，最终停在崩溃前最后一条已记录的写操作上。

- **第一步加载**：从磁盘元数据定位最新有效检查点，把对应的数据树加载进缓存。
- **第二步回放**：从检查点对应的日志位点开始重演 journal，回放是幂等的，重复执行不会造成重复修改。
- **中断的容忍**：崩溃若恰好发生在检查点写出途中，元数据仍指向上一个完整检查点，半成品检查点会被丢弃，不存在加载到一半的数据。
- **结果保证**：恢复点最坏回退到最近一次检查点，其后的写入是否保留取决于 journal 刷盘与写关注的配置；配合 j 选项与 majority 写关注提交的写入不会丢。

> 崩溃恢复是检查点与 journal 的合力：检查点给起点，journal 给增量。运维上关心两件事——检查点间隔决定最坏恢复时长，journal 所在磁盘的写入性能决定日常写延迟的下限。



### 压缩与缓存配置

#### 块压缩与索引前缀压缩

**块压缩**：是 WiredTiger 对磁盘页整体启用的压缩，新建集合默认使用 snappy，另可选 zlib 与 zstd；索引在此之外默认叠加**前缀压缩**——相邻键的公共前缀只存一次。

- **三种块压缩算法**：snappy 压得快、开销低，是默认值；zlib 压缩率最高但 CPU 开销大；zstd 介于两者之间，适合存储敏感的大集合。
- **前缀压缩的主场**：复合索引键常有很长的公共前缀，前缀压缩对索引的收益比集合更明显，且默认开启。
- **指定方式**：块压缩可在配置文件里为新集合设默认算法，也可在创建集合时按集合单独指定。
- **效果验证**：压缩是否生效用统计命令看 collection 的 storageSize 与 count 的比值，比值下降即压缩在起作用。

```bash
# mongod.conf：新建集合默认使用 zstd 块压缩
storage:
  wiredTiger:
    collectionConfig:
      blockCompressor: zstd
```

```js
// 建集合时单独指定压缩算法，覆盖全局默认
db.createCollection("archives", {
  storageEngine: { wiredTiger: { configString: "block_compressor=zlib" } }
})
```

```text
{ ok: 1 }
```

> 压缩发生在磁盘页上，进出缓存的数据是解压后的原文，因此压缩省的是磁盘空间与 IO，不省缓存。切换算法只影响之后新建的集合，存量集合需重建才能生效，改动前先估算重建成本。



#### cacheSizeGB 缓存配置

**WiredTiger 缓存**：是引擎自管的内存区，以页为单位缓存集合与索引数据，大小默认取 256MB 与（物理内存减 1GB）的一半中的较大者，可用 cacheSizeGB 显式指定。

```bash
# mongod.conf：把缓存上限固定为 2GB
storage:
  wiredTiger:
    engineConfig:
      cacheSizeGB: 2
```

- **为何不能占满内存**：同一台机器上还运行着操作系统与文件系统缓存，mongod 进程本身也要内存，把内存全划给引擎会互相挤压。
- **缓存不足的信号**：缓存命中率下降、磁盘读上升、页频繁换入换出，都指向工作集超出缓存容量。
- **调整顺序**：先收缩工作集（减索引、清冷数据），再考虑加缓存或加内存；cacheSizeGB 设得过大，反而挤占文件系统缓存拖慢读盘。
- **取值约束**：cacheSizeGB 以 GB 为单位取数值，下限有引擎内定的最小值保护，设得过小会被自动抬高。

> 缓存配置是划地盘：给 WiredTiger 的每一份内存都从操作系统与文件系统缓存手里拿走。经验起点是默认值，出现缓存压力指标后再动配置，而不是部署之初就把缓存调大。



#### 缓存的观测指标

**缓存的观测**：判断缓存是否够用，看 db.serverStatus().wiredTiger.cache 里的几个计数——当前占用、配置上限，以及页的读入写出速率。

```js
// 当前缓存占用与配置上限，单位是字节
db.serverStatus().wiredTiger.cache["bytes currently in the cache"]
db.serverStatus().wiredTiger.cache["maximum bytes configured"]
// 页级计数：累计读入与写出的页数
db.serverStatus().wiredTiger.cache["pages read into cache"]
db.serverStatus().wiredTiger.cache["pages written from cache"]
```

```text
1073741824
2147483648
52184
39012
```

- **占用逼近上限**：当前占用长期贴近 maximum bytes configured，说明工作集已顶到缓存容量，扩容或瘦身二选一。
- **页计数看增速**：pages read into cache 的增长速度就是缓存miss的频率，斜率陡增说明磁盘读在放大。
- **看趋势不看单点**：单次读数只代表瞬间状态，持续观测占用走势与页换入换出的速率才有判断价值。
- **与业务指标对照**：缓存占用上升但响应没变慢，是引擎在正常利用内存；响应同步变差才是真的缓存不足。
- **与其他指标联动**：缓存压力要和慢查询日志、磁盘 IO 指标放在一起看，单看缓存读数容易归因错位。

> 观测指标把「缓存够不够」从猜测变成读数：先看占用与上限的比值，再看换入换出趋势，最后才决定动配置还是动数据。没有指标支撑的缓存调参都是盲调。



#### 建集合时的引擎选项

**storageEngine 建表选项**：创建集合或索引时可通过 storageEngine 参数把 WiredTiger 的配置下沉到单个对象，覆盖配置文件里的全局默认值。

```js
// 为单个索引关闭前缀压缩
db.orders.createIndex(
  { remark: 1 },
  { storageEngine: { wiredTiger: { configString: "prefix_compression=false" } } }
)
```

```text
remark_1
```

- **粒度从粗到细**：配置文件管新集合的默认值，createCollection 与 createIndex 的选项管单个对象，越细的粒度越适合例外情况。
- **典型用途**：为写入密集的索引关掉前缀压缩换取更简单的键编码，为归档集合指定更高压缩率的算法。
- **验证方式**：建表选项是否生效，可对照 db.collection.stats() 里返回的 creationString 与预期配置。
- **改动的代价**：建表选项在创建时定格，事后要改只能重建集合或索引，线上大集合动手前先评估重建窗口。

> 引擎选项的粒度越细，越要克制使用：每个对象级别的例外都是一笔未来的运维负债。全局默认覆盖九成场景，个别例外用建表选项定点处理，并留下记录说明为什么例外。
