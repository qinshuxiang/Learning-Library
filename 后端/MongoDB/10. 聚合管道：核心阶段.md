## 聚合管道：核心阶段

### 管道的概念与执行模型

#### 聚合管道的定义与数据流

**聚合管道（Aggregation Pipeline）**：是**把文档依次送入多个处理阶段、每个阶段的输出文档作为下一阶段输入**的数据加工流水线，入口方法是 db.collection.aggregate(pipeline, options)。

- **阶段（Stage）**：管道中的一个处理步骤，如 $match、$group，每个阶段是管道数组中的一个元素。
- **数据流**：文档从集合出发逐阶段流转，前一阶段的输出是后一阶段的输入，aggregate 最终返回结果游标。
- **与 find 的边界**：find 只能筛选与投影，管道还能分组、展开数组、连接集合；find 的筛选条件原样写进 $match 即可。

后续示例统一使用 orders 集合，先写入六笔订单作为样例数据：

```js
db.orders.insertMany([
  { _id: 1, user: "张三", item: "键盘", price: 299, qty: 2, tags: ["电子", "外设"], status: "paid", createdAt: ISODate("2026-01-12T08:30:00Z") },
  { _id: 2, user: "李四", item: "鼠标", price: 129, qty: 1, tags: ["电子"], status: "paid", createdAt: ISODate("2026-01-20T14:05:00Z") },
  { _id: 3, user: "张三", item: "显示器", price: 1599, qty: 1, tags: ["电子", "屏幕"], status: "shipped", createdAt: ISODate("2026-02-08T10:00:00Z") },
  { _id: 4, user: "王五", item: "键帽", price: 89, qty: 3, tags: ["外设"], status: "cancelled", createdAt: ISODate("2026-02-15T19:40:00Z") },
  { _id: 5, user: "李四", item: "鼠标垫", price: 39, qty: 2, tags: [], status: "paid", createdAt: ISODate("2026-03-01T09:15:00Z") },
  { _id: 6, user: "王五", item: "显示器支架", price: 249, qty: 1, tags: ["外设", "屏幕"], status: "paid", createdAt: ISODate("2026-03-18T16:20:00Z") }
]);
```

一个最小的三阶段管道：筛出已支付订单，按用户合并出消费总额，再按总额降序排列：

```js
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$user", total: { $sum: { $multiply: ["$price", "$qty"] } } } },
  { $sort: { total: -1 } }
]);
```

```text
[
  { _id: '张三', total: 598 },
  { _id: '王五', total: 249 },
  { _id: '李四', total: 207 }
]
```

> 管道思维的关键是把复杂查询拆成一串简单阶段：$match 决定哪些文档参与，$group 决定按什么维度合并，$sort 决定呈现顺序。每个阶段只做一件事，组合起来完成完整报表。



#### 阶段的组合与文档流转

**阶段的组合**：是**把若干阶段按处理顺序写进同一个数组**的编排方式，文档流过每个阶段时被过滤、整形或重组，前一阶段输出的字段结构决定后一阶段能引用什么。

- **整形改变可用字段**：$project 之后的阶段只能引用保留下来的字段，被排除的字段等同于消失。
- **文档数量中途增减**：$match 与 $limit 只会让文档变少，$unwind 一条变多条，$group 多条并成一条。
- **顺序即语义**：MongoDB 不重排书写顺序，只会在语义等价时做内部优化，例如把 $match 自动前移到 $sort 之前。

观察整形阶段如何塑造后续阶段的输入，注意 $match 引用的是 $project 新算出的 amount 字段：

```js
db.orders.aggregate([
  { $project: { _id: 0, user: 1, item: 1, amount: { $multiply: ["$price", "$qty"] } } },
  { $match: { amount: { $gte: 200 } } },
  { $sort: { amount: -1 } }
]);
```

```text
[
  { user: '张三', item: '显示器', amount: 1599 },
  { user: '张三', item: '键盘', amount: 598 },
  { user: '王五', item: '键帽', amount: 267 },
  { user: '王五', item: '显示器支架', amount: 249 }
]
```

> 流转视角是排错的基本功：结果不对时把管道逐段截短执行，检查每个阶段吐出的文档形状与数量，问题多半出在字段被上游阶段丢掉，或结构被改变导致下游引用不到。



#### 阶段顺序对性能与结果的影响

**阶段顺序**：管道严格按数组书写顺序执行，**顺序不同不仅影响性能，还可能改变最终结果**，这是聚合调优的第一课。

先看性能。先 $match 后 $group 的写法只有四条已支付文档进入分组，条件还能命中 status 上的索引；把顺序对调，$group 就要先吃进全部文档再做筛选，扫描量随集合增大而放大：

```js
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$user", total: { $sum: { $multiply: ["$price", "$qty"] } } } }
]);
```

再看结果。$sort 与 $limit 互换后输出完全不同，先限量再排序只排了前两条文档的子集，先排序再限量才是真正的「全库最贵前两名」：

```js
db.orders.aggregate([
  { $limit: 2 },
  { $sort: { price: -1 } },
  { $project: { _id: 0, item: 1, price: 1 } }
]);
```

```text
[
  { item: '键盘', price: 299 },
  { item: '鼠标', price: 129 }
]
```

```js
db.orders.aggregate([
  { $sort: { price: -1 } },
  { $limit: 2 },
  { $project: { _id: 0, item: 1, price: 1 } }
]);
```

```text
[
  { item: '显示器', price: 1599 },
  { item: '键盘', price: 299 }
]
```

- **$match 前置**：尽早缩小数据量，并让查询条件尽可能利用索引。
- **$sort 在前、$limit 在后**：先限量再排序只排子集，语义通常不是想要的。
- **不依赖优化器兜底**：优化器只会移动语义等价的阶段，写错顺序导致的结果错误它不会纠正。

> [!CAUTION]
> **注意内容**：$match 尽量前置是聚合的第一优化原则，筛选越早、流入后续阶段的文档越少、索引越可能被利用。但前置必须服从语义——对分组结果值的筛选，$match 只能放在 $group 之后，硬挪到前面只会因为原始文档没有该字段而筛掉全部数据。



### 筛选与整形阶段

#### $match 筛选文档

**$match**：是**按查询条件过滤文档、只放行符合条件的文档**的阶段，条件语法与 find 的查询参数完全一致。

- **操作符通用**：$gte、$in、$exists、$regex 等全部查询操作符在 $match 中照常使用。
- **索引友好**：$match 位于管道开头时，条件可直接命中集合上的索引。
- **可多次出现**：一个管道允许写多个 $match，分别承担分组前的粗筛与分组后的精筛。

```js
db.orders.aggregate([
  { $match: { status: "paid", price: { $gte: 100 } } },
  { $project: { _id: 0, user: 1, item: 1, price: 1 } }
]);
```

```text
[
  { user: '张三', item: '键盘', price: 299 },
  { user: '李四', item: '鼠标', price: 129 },
  { user: '王五', item: '显示器支架', price: 249 }
]
```

> $match 的条件写法照搬 find，掌握查询操作符就掌握了 $match。它的最佳位置是管道最前面，越早过滤，后续阶段的计算量越小，这条原则在第 11 篇的实战管道中反复出现。



#### $project 字段投影

**$project**：是**决定输出文档保留、排除或重算哪些字段**的整形阶段，相当于 find 的投影参数，但支持计算字段。

- **保留与排除**：字段名后写 1 保留、写 0 排除，_id 默认保留，需写 _id 配 0 显式排除。
- **计算字段**：新字段由操作符表达式生成，如用 $multiply 把单价与数量相乘得到金额。
- **包含与排除互斥**：除 _id 外，同一个 $project 不能同时出现保留与排除两种写法。

```js
db.orders.aggregate([
  { $project: {
      _id: 0,
      user: 1,
      item: 1,
      amount: { $multiply: ["$price", "$qty"] },
      tagsCount: { $size: "$tags" }
  } },
  { $limit: 3 }
]);
```

```text
[
  { user: '张三', item: '键盘', amount: 598, tagsCount: 2 },
  { user: '李四', item: '鼠标', amount: 129, tagsCount: 1 },
  { user: '张三', item: '显示器', amount: 1599, tagsCount: 2 }
]
```

> [!CAUTION]
> **注意内容**：$project 的保留模式与排除模式混用会直接报错，唯一的例外是 _id，任何模式下都可以将其排除。另外 $project 之后的阶段再也看不到被排除的字段，写管道前先想清楚下游阶段还要用哪些字段，裁剪放在管道末端更安全。



#### $limit 与 $skip 分页

**$limit 与 $skip**：分别**限制输出文档条数**与**跳过指定条数**的阶段，组合起来实现管道内分页。

- **$limit 限量**：只放行前 n 条文档，所谓「前」由上游的 $sort 决定，没有排序就没有稳定的「前 n 条」。
- **$skip 跳过**：跳过前 n 条文档，页码越深需要数过的文档越多，代价线性上涨。
- **分页惯用形**：先 $sort、再 $skip、后 $limit，保证每一页数据稳定可复现。

```js
db.orders.aggregate([
  { $sort: { createdAt: 1 } },
  { $skip: 2 },
  { $limit: 2 },
  { $project: { _id: 0, item: 1, createdAt: 1 } }
]);
```

```text
[
  { item: '显示器', createdAt: ISODate('2026-02-08T10:00:00Z') },
  { item: '键帽', createdAt: ISODate('2026-02-15T19:40:00Z') }
]
```

> $skip 在跳过大量文档时依旧要逐条数过去，深分页越翻越慢。数据量大、需要频繁翻页时，改用「上一页最后一条的排序值」做范围条件（如下单时间早于某时刻）替代 skip，性能不随页码衰减。



### 分组与展开阶段

#### $group 分组重整

**$group**：是**按分组键表达式的值把文档分成若干组、每组输出一条结果文档**的阶段，是聚合统计的核心。

- **_id 即分组键**：写 "$user" 按用户分组，写 $dateToString 表达式按月份分组，写 null 把全部文档合为一组。
- **累加器做统计**：组内统计用累加器表达式完成，如计数的惯用形是 $sum 接常量 1，各累加器详见第 11 篇。
- **输出只含声明字段**：结果文档只包含 _id 与显式声明的累加字段，其余原始字段全部丢弃。

```js
db.orders.aggregate([
  { $group: { _id: "$status", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
]);
```

```text
[
  { _id: 'paid', count: 4 },
  { _id: 'shipped', count: 1 },
  { _id: 'cancelled', count: 1 }
]
```

分组键写 null，把整个集合压成一条汇总：

```js
db.orders.aggregate([
  { $group: { _id: null, totalOrders: { $sum: 1 }, maxPrice: { $max: "$price" } } }
]);
```

```text
[ { _id: null, totalOrders: 6, maxPrice: 1599 } ]
```

> $group 与 SQL 的 GROUP BY 对应：_id 表达式就是 GROUP BY 后面的字段，累加器对应 COUNT、SUM、MAX 等聚合函数。$group 不保证输出顺序，需要有序时在其后追加 $sort。



#### $sort 排序

**$sort**：是**按一个或多个字段对文档排序**的阶段，字段值写 1 升序、写 -1 降序。

- **多字段排序**：status 升序再按 price 降序，表示先按状态分组呈现，状态相同者价格高者在前。
- **内存上限**：排序阶段默认最多用 100MB 内存，超出即报错，需在 aggregate 的选项里打开 allowDiskUse 允许落盘。
- **索引加速**：$sort 位于管道最前且字段与某索引一致时，可直接按索引序读出，免去排序动作。

```js
db.orders.aggregate([
  { $project: { _id: 1, status: 1, price: 1 } },
  { $sort: { status: 1, price: -1 } }
]);
```

```text
[
  { _id: 4, status: 'cancelled', price: 89 },
  { _id: 1, status: 'paid', price: 299 },
  { _id: 6, status: 'paid', price: 249 },
  { _id: 2, status: 'paid', price: 129 },
  { _id: 5, status: 'paid', price: 39 },
  { _id: 3, status: 'shipped', price: 1599 }
]
```

> 大结果集排序报内存超限错误时，先想想能否用 $match 提前缩小数据量，确实需要在全集上排序再打开 allowDiskUse。排序字段上有合适索引的查询，应尽量让 $sort 保持在前部，与索引序对齐。



#### $unwind 数组展开

**$unwind**：是**把数组字段的每个元素拆成一条独立文档**的阶段，一条输入文档按数组长度变成多条输出文档。

- **默认行为**：数组为空、字段缺失或字段值为 null 的文档会被直接丢弃。
- **保留空值文档**：把 preserveNullAndEmptyArrays 置为 true 时，上述文档保留一条，数组字段不出现。
- **记录下标**：includeArrayIndex 接一个字段名，输出文档中额外记录元素在原数组中的下标。

先统计每个标签出现在多少笔订单中，这是 $unwind 与 $group 的经典组合：

```js
db.orders.aggregate([
  { $unwind: "$tags" },
  { $group: { _id: "$tags", count: { $sum: 1 } } },
  { $sort: { count: -1, _id: 1 } }
]);
```

```text
[
  { _id: '电子', count: 3 },
  { _id: '外设', count: 3 },
  { _id: '屏幕', count: 2 }
]
```

对比保留空数组文档的写法，注意鼠标垫订单的 tags 是空数组，两种写法下去留不同：

```js
db.orders.aggregate([
  { $match: { _id: { $in: [4, 5] } } },
  { $unwind: { path: "$tags", preserveNullAndEmptyArrays: true } },
  { $project: { _id: 1, item: 1, tags: 1 } }
]);
```

```text
[
  { _id: 4, item: '键帽', tags: [ '外设' ] },
  { _id: 5, item: '鼠标垫' }
]
```

> $unwind 最常见的坑是「数据悄悄变少」：没意识到空数组与缺失字段会被丢弃，统计结果莫名偏小。做占比类统计前，先确认要不要用 preserveNullAndEmptyArrays 把这部分文档留住，否则总数对不上分母。
