## 模式设计与反模式

### 嵌入与引用

#### 嵌入 vs 引用的决策标准

**嵌入（embedding）**：是把关联数据作为子文档存进同一个文档；**引用（referencing）**：是只存关联文档的 id、查询时二次获取。决策标准是「数据的归属与共同生命周期」，而不是关系型的范式习惯。

- **一起读就嵌入**：子数据总是随父文档一起读取（订单与订单行），嵌入一次读出，省一次查询往返。
- **独立演进就引用**：子数据有自己的更新频率与访问方（商品与所属分类），引用避免大面积同步写。
- **数量封顶才嵌入**：子数据条数有业务上限（一个人的收货地址、一篇文章的标签），嵌入不会失控；无上限的持续增长必须引用。
- **不被单独访问就嵌入**：子数据从不脱离父文档被检索时，嵌入没有代价；需要按子条件高频单独检索时，引用或做字段冗余。

```js
// 嵌入示例：订单行随订单一起读、一起写、条数有限
{
  _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
  userId: 42,
  status: 'paid',
  items: [
    { sku: 'KB-01', price: 199, qty: 1 },
    { sku: 'MS-07', price: 89, qty: 2 }
  ]
}
```

> 一句话判据：嵌入优化读，引用优化写与独立演进。把关系型的范式化习惯原样搬进 MongoDB，是模式设计失败的第一大来源。



#### 一对一与一对多的建模模式

**一对一与一对多**：一对一用「直接嵌入」或「拆成两个集合」，一对多按「多」的数量是否封顶，在子文档数组嵌入与父 id 引用之间二选一。

- **一对一**：主数据与扩展字段读写总是成对出现时直接嵌入；字段过大或更新节奏明显不同时拆成两个集合，各存一份相同 id。
- **少量对多（数十以内且封顶）**：把「多」的一方作为文档数组嵌进「一」的一方，如用户文档内嵌收货地址数组。
- **很多对多（可达数千且不封顶）**：把「多」的一方独立成集合，每个子文档带父文档的 id，如商品与评论；查子靠子集合的父 id 索引，查父靠 id 直取。

```js
// 少量对多：收货地址嵌入用户文档，数量有业务上限
{
  _id: ObjectId('665f1a2b3c4d5e6f708192a2'),
  name: 'chen',
  addresses: [
    { city: 'hangzhou', street: 'wensan rd 1' },
    { city: 'shanghai', street: 'nanjing rd 9' }
  ]
}
```

> 数量封顶是嵌入与引用的分水岭：地址封顶所以嵌入，评论不封顶所以引用。建模时把「这个关系最多多少条」写成评审结论，后面所有查询与索引设计都建立在这个结论上。



#### 多对多的建模模式

**多对多**：在 MongoDB 里的两条常规路径是「固定一端存 id 数组」与「独立关联集合」，取舍由关系规模与双向查询需求决定。

- **少量对多**：一端存另一端的 id 数组，如文章与标签——文章的标签是短数组且数量封顶，一次查询带出全部关联，配合 $in 反查另一端。
- **大量对多**：用户与商品收藏这类百万级关系，任何一端的 id 数组都会无界增长，改为独立关联集合，两个方向各建索引。
- **双向查询需求**：两端都要高频反查时，关联集合上建两个方向的索引；规模小的那端可另存冗余数组加速。

```js
// 很多对多：评论独立成集合，每个子文档带父 id
db.reviews.insertOne({
  sku: 'KB-01',
  userId: 42,
  rating: 5,
  content: 'works great'
})
```

```text
{
  acknowledged: true,
  insertedId: ObjectId('665f1a2b3c4d5e6f708192a4')
}
```

```js
// 大量对多：独立收藏关系集合，userId 与 sku 各建索引
{
  _id: ObjectId('665f1a2b3c4d5e6f708192a3'),
  userId: 42,
  sku: 'KB-01',
  createdAt: ISODate('2026-08-01T10:00:00Z')
}
```

```js
// 两个方向的反查各靠一个索引
db.favorites.createIndex({ userId: 1 })
db.favorites.createIndex({ sku: 1 })
```

> id 数组的长度上限是硬约束：数组一旦可能超过数百条，就改独立关联集合。多对多建模出错几乎都是「低估了关系规模」，评估时按业务峰值取数，不按平均值。



### 文档上限与关联代价

#### 16MB 文档上限与无限增长数组

**16MB 文档上限**：是单个 BSON 文档的硬性尺寸限制，超限写入直接报错；最常见的触雷方式是往文档数组里无限追加数据。

- **硬上限**：16MB 按序列化后的字节数判定，与字段数量无关；触发时报 BSONObjectTooLarge，写入失败、业务中断。
- **无限增长数组**：评论、日志、消息这类持续追加的数据嵌进父文档，数组随业务运行无限变长，最终撞上限或先拖垮更新性能。
- **劣化在先**：数组越长，追加与按下标改写的代价越高，父文档的索引越大、缓存越差，通常在撞上限之前性能已经崩了。
- **正确做法**：会无限增长的子数据独立成集合；父文档只保留计数等汇总字段，用 $inc 维护。

```js
// 评论独立成集合，父文档不承载无限增长的内容
db.comments.insertOne({
  orderId: ObjectId('665f1a2b3c4d5e6f708192a1'),
  content: 'fast delivery',
  createdAt: ISODate('2026-08-01T10:00:00Z')
})
```

```js
// 检查文档的实际字节数，离 16MB 的距离要常态化观测
Object.bsonsize(db.orders.findOne({ orderId: 1001 }))
```

```text
512
```

> [!CAUTION]
> **注意内容**：无限增长数组的危害不在「最终撞上 16MB」那一下，而在撞上之前的漫长劣化期——更新变慢、索引膨胀、文档迁移困难。评审模式时问一句「这个数组五年后多长」，答不出来就拆集合。



#### $lookup 的代价与冗余字段的取舍

**$lookup**：是聚合管道里做集合间关联的阶段，本质是管道执行时发起跨集合查询，代价远高于读嵌在文档里的数据；**冗余字段**：是把关联方的常用字段复制一份存进本文档，用写入时的同步成本换读取时的零关联。

```js
// 订单聚合商品名称：每次查询都要跨集合关联
db.orders.aggregate([
  { $match: { userId: 42 } },
  { $lookup: {
      from: 'products',
      localField: 'sku',
      foreignField: 'sku',
      as: 'product'
  } },
  { $unwind: '$product' },
  { $project: { sku: 1, price: 1, 'product.name': 1 } }
])
```

```text
[
  {
    _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
    sku: 'KB-01',
    price: 199,
    product: { name: 'keyboard' }
  }
]
```

- **lookup 的代价**：无法像单集合查询那样充分吃满索引，数据量大时每层关联都在放大扫描量，分片集群上的关联代价进一步上升。
- **冗余的适用面**：被冗余的字段必须极少变化（如商品名、下单时价格）；高频变化字段做冗余会制造大面积同步写与不一致窗口。
- **业务正确性冗余**：订单冗余下单时的商品名与价格属于业务要求——商品改名不改历史订单，这类冗余优先级最高。
- **同步手段**：源字段变更时批量刷冗余字段，刷库逻辑与源写入放在同一事务边界或做成幂等任务。

> 冗余不是反模式，「无节制的冗余」才是。读多写少、关联字段稳定、读取路径是热路径——三条同时满足才值得冗余；否则保留关联，或回头调整嵌入边界。



### 常见反模式

#### 巨型文档反模式

**巨型文档**：单文档字段数百个、子树多层嵌套、体积逼近 16MB，读写与传输的全链路代价都被放大，是模式失控的终局形态。

- **成因**：把一个业务实体的全部信息、历史快照、统计结果都塞进一个文档，字段只增不减。
- **代价**：任何一次小字段的更新都要移动或重写大文档，索引膨胀，网络传输与反序列化开销随文档尺寸线性上涨。
- **解法**：按访问边界拆分——总是整体读取的留在一起，低频访问的子树拆成独立集合；统计与快照落进单独的结果文档。

```js
// 反例：用户文档里嵌全部订单明细与全部统计，体积无界
// 正例：统计结果独立成集合，按 userId 各存一条
db.userStats.insertOne({
  userId: 42,
  orderCount: 128,
  totalAmount: 45600,
  updatedAt: ISODate('2026-09-01T08:00:00Z')
})
```

> 文档尺寸是模式的体检指标：典型文档的 bsonsize 常态超过数十 KB 就该拆分。拆分的原则是跟着访问边界走，而不是跟着字段分类走。



#### 为每个值单独建集合反模式

**为每个值单独建集合**：按租户、按用户、按月份、按地区给数据各建一个集合，集合数量随业务值增长而爆炸，是关系型分表习惯的直接平移。

- **成因**：沿用分表思维管理数据规模，忽略了 MongoDB 单集合扛海量文档的能力远强于扛海量集合。
- **代价**：每个集合各带一套索引占内存，集合目录开销上涨，跨集合查询、跨集合事务与全局建索引全部变成苦役。
- **判据**：集合的数量应当由「访问模式不同」决定，而不是由「数据的值」决定；同一访问方式的数据放同一集合，用字段区分。

```js
// 反例：按月建集合 orders_202608、orders_202609，跨月统计要合并多集合
// 正例：一个 orders 集合，按 createdAt 建索引做范围查询
db.orders.createIndex({ createdAt: 1 })
```

> [!CAUTION]
> **注意内容**：集合数失控后再合并，要付出全量数据迁移与双写切换的代价，越早纠正越便宜。看到集合名里带变量（用户名、月份、租户号），先按反模式处理，再论证例外。



#### 全部走 $lookup 反模式

**全部走 $lookup**：把 MongoDB 当关系型库用，列表页、详情页层层关联集合，查询延迟随数据量增长失控，是查询侧最常见的系统性反模式。

- **成因**：先按关系型画实体关系图建集合，再原样把 join 翻译成 $lookup，嵌入与冗余一次都没有做。
- **代价**：列表页一次请求触发多层跨集合扫描，索引再好也架不住逐行关联；数据量上去后延迟从毫秒滑向秒级。
- **解法**：热路径上的关联字段做冗余，或按访问边界重新嵌入；$lookup 留给低频的后台任务与报表。

```js
// 列表页反例：每页都要对 products 关联一次
// 正例：下单时冗余商品名进订单，列表页零关联
db.orders.insertOne({
  userId: 42,
  sku: 'KB-01',
  productName: 'keyboard',
  price: 199,
  createdAt: ISODate('2026-08-01T09:00:00Z')
})
```

> $lookup 的合理位置在低频路径：报表、对账、后台任务。凡是出现在线上高频读路径里的关联，都应视为模式设计的欠账，用冗余或嵌入偿还。



#### 缺计算字段反模式

**缺计算字段**：每次查询都对原始字段重算同样的结果（订单总额、文章评论数），同一笔账被 CPU 反复计算，聚合管道越写越长。

- **成因**：只存最原始的事实字段，把一切派生值都留给查询时计算，忽略了派生值也可以落库。
- **代价**：读路径承担计算开销，聚合无法走覆盖索引，热点数据被反复聚合；数据量增长后计算成本线性放大。
- **识别信号**：同一条聚合管道被多个业务反复执行、且输入只有时间段在变——中间结果该落库了。
- **解法**：写入时用 $inc 同步维护总计与计数字段，查询端直接读结果字段。

```js
// 下单时同步维护汇总字段，查询端不再逐行聚合
db.orders.updateOne(
  { _id: ObjectId('665f1a2b3c4d5e6f708192a1') },
  { $inc: { totalAmount: 199, itemCount: 1 } }
)
```

```js
// 查询端直接读汇总字段，毫秒级返回
db.orders.findOne(
  { _id: ObjectId('665f1a2b3c4d5e6f708192a1') },
  { totalAmount: 1, itemCount: 1 }
)
```

```text
{
  _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
  totalAmount: 199,
  itemCount: 1
}
```

> [!TIP]
> **建议内容**：设计新集合时先列出前五个高频查询，倒推哪些值要预先算好。计算字段用写入时的几次 $inc，换掉读取时的整段聚合，是性价比最高的一类反模式修复。



### 访问模式优先的设计

#### 从访问模式出发的设计流程

**访问模式优先（access-pattern-first）**：是 MongoDB 模式设计的标准流程——先枚举查询与写入方式，再决定文档边界、嵌入引用与索引，而不是先画实体关系图。

设计流程分五步：

1. 列出业务的核心操作，标注每个操作的读写频率与一致性要求。
2. 按操作把数据分组：总是被一起读写的字段放进同一个文档。
3. 对跨文档的关联，按数量上限决定嵌入还是引用，按读频率决定是否冗余。
4. 按查询条件建索引，用 explain 验证每个高频查询都命中索引。
5. 上线后持续观测集合尺寸、数组长度与慢查询，发现劣化及早重设计。

- **顺序即立场**：操作决定文档，文档决定索引；关系型的「实体、表、外键」顺序在文档库里会系统性地做出错误设计。
- **迭代而非一次成型**：模式可以随时演进，但重构代价随数据量上涨，第一版就要把最热的两三个访问模式设计对。

> 模式设计的正确顺序是「操作、文档、索引」，数据跟着访问走，而不是访问迁就数据。先写操作清单再画文档结构，一个下午就能避免大半的反模式。



#### 模式评审的落地清单

**模式评审清单**：把反模式变成评审阶段的固定检查项，每个新增集合上线前逐条过一遍，用流程兜住个人经验的不稳定。

- **数组长度**：每个文档数组都写明预期上限与超限方案，无上限的一律拆集合。
- **文档尺寸**：预估典型文档与最大文档的字节数，与 16MB 上限的安全距离纳入评审结论。
- **更新频率**：高频更新字段不与超大文档同住，避免小更新拖动大文档。
- **关联方式**：热路径上不出现 $lookup，出现则必须给出冗余或嵌入的替代方案。
- **计算字段**：被反复聚合的派生值落库，明确维护时机与幂等性。
- **分片预留**：预期会分片的集合提前选好分片键，避免上线后被迫 reshardCollection。

> [!IMPORTANT]
> **重要内容**：MongoDB 的模式可以随时演进，但数据一旦上量，重构模式的代价随数据量线性上涨。评审阶段花一小时过清单，好过线上花一个季度做数据迁移。
