## 性能优化与慢查询诊断

### 慢查询定位与 profiler

#### profiler 三档级别与 system.profile

**数据库分析器（Database Profiler）**：是**把操作按级别写入 system.profile 集合**的内置诊断工具，级别通过 db.setProfilingLevel 设置，共三档。

- **级别 0**：关闭分析器，不记录任何操作，是默认级别。
- **级别 1**：只记录耗时超过 slowms 阈值的慢操作，slowms 默认 100 毫秒，可随级别一并下调。
- **级别 2**：记录全部操作，开销最大，只用于短时排查。

```js
// 开启级别 1，并把慢查询阈值降到 50 毫秒
db.setProfilingLevel(1, { slowms: 50 })

// 查看当前生效的级别与阈值
db.getProfilingStatus()
```

```text
{ was: 1, slowms: 50, sampleRate: 1 }
```

记录落在当前数据库的 system.profile 集合中，它是一个固定大小集合（capped collection），写满后旧记录自动被覆盖，因此总能看到「最近」的慢操作。排查时按耗时倒序筛选：

```js
// 取最近 5 条耗时超过 100 毫秒的记录
db.system.profile.find({ millis: { $gt: 100 } })
  .sort({ ts: -1 })
  .limit(5)
```

每条记录的关键字段：

- **op**：操作类型，如 query、insert、update、remove、command。
- **ns**：命名空间，形如 库名.集合名，用来把记录对应到具体集合。
- **millis**：耗时毫秒数，是排序与筛选的主依据。
- **planSummary**：执行摘要，出现 COLLSCAN 说明走了全集合扫描，IXSCAN 说明走了索引。
- **docsExamined 与 nreturned**：检查的文档数与返回的文档数，前者远大于后者通常意味着索引不理想。

> [!CAUTION]
> **注意内容**：级别 2 会记录全部操作，写 system.profile 本身消耗磁盘与 CPU，生产环境长期开启会拖慢整体性能。排查结束立即调回级别 0 或 1，不要带着级别 2 上线。



#### profiler 的采样率与开销控制

**采样率（sampleRate）**：是级别 1 下的补充参数，表示慢操作被记录的概率，用于在高流量实例上把分析器开销压到可承受范围。

- **取值范围**：0 到 1 之间的小数，sampleRate 为 0.5 表示每条超阈值的操作有一半概率被记录。
- **适用场景**：峰值 QPS 很高的线上实例，全量记录慢操作时写入本身成为负担，抽样本已足以看清慢查询的形态。
- **默认值**：sampleRate 默认为 1，即全量记录。

```js
// 记录 50 毫秒以上的慢操作，且只按一半概率采样
db.setProfilingLevel(1, { slowms: 50, sampleRate: 0.5 })
```

```text
{ ok: 1 }
```

开销控制还有两个配套习惯：

- **按库开启**：分析器按数据库生效，只对出问题的业务库开启，admin 与系统库保持级别 0。
- **限时开启**：与运维窗口配合，排查完成立即 db.setProfilingLevel(0) 关闭，不做常驻配置。

> 分析器的定位是「临时探针」而不是常驻监控：常态化的性能观测交给 mongostat、mongotop 与基于 serverStatus 的监控系统，分析器只在需要逐条看慢语句时登场。



#### 慢查询定位流程

**慢查询定位**：是一条「先抓现象、再看计划、后补索引、最后复测」的排查路径，四个环节按顺序执行，不跳步。

- **第一步 抓取慢操作**：开启级别 1 并下调 slowms，从 system.profile 按 millis 倒序找头部记录，圈定问题命名空间与语句形态。
- **第二步 验证执行计划**：把慢语句放进 explain 的 executionStats 模式，看 winningPlan 里的扫描方式与 totalDocsExamined 数量级。
- **第三步 补建索引**：按「等值字段在前、排序与范围字段在后」的原则建复合索引。
- **第四步 复测确认**：重跑 explain，确认 winningPlan 变为 IXSCAN，且 totalKeysExamined 与 nreturned 量级接近。

```js
// 复测：只打印三个关键计数
const plan = db.orders.find({ userId: 10086, status: "paid" })
  .sort({ createdAt: -1 })
  .explain("executionStats");
console.log("返回数:", plan.executionStats.nReturned);
console.log("索引键检查数:", plan.executionStats.totalKeysExamined);
console.log("文档检查数:", plan.executionStats.totalDocsExamined);
```

```text
返回数: 12
索引键检查数: 12
文档检查数: 12
```

> 优化达成后的理想形态是三个数字同一量级：返回 12 条，只检查 12 个索引键与 12 篇文档。若补索引前文档检查数是数万，与返回数相差三个数量级，索引就是第一嫌疑人。



### 监控工具与服务器指标

#### mongostat

**mongostat**：是**按固定间隔输出整库操作速率**的命令行工具，一行一个采样点，适合观察读写压力、缓存水位与连接趋势。

- **insert／query／update／delete／getmore**：每秒各类操作的次数。
- **command**：每秒命令数，竖线分隔本地与远端的计数。
- **dirty／used**：WiredTiger 缓存的脏页占比与已用占比，used 持续接近 100% 说明缓存不足。
- **flushes**： WiredTiger 检查点相关行为，正常情况多为 0。
- **qrw|arw**：等待读写的队列长度与活跃读写数，持续非零说明吞吐吃紧。
- **conn**：当前连接数。

```bash
mongostat --host 127.0.0.1 --port 27017 --rowcount 3
```

```text
insert query update delete getmore command dirty  used flushes  vsize   res qrw|arw net_in net_out conn     time
   120    450     180      60      15    260|0  0.2% 78.5%       0  12.1G  1.2G    0|0  98.4k 142.1k   38 10:00:01
   115    430     175      58      12    255|0  0.2% 78.6%       0  12.1G  1.2G    0|0  95.1k 138.9k   38 10:00:02
   124    470     186      63      17    268|0  0.3% 78.8%       0  12.1G  1.2G    0|0 101.2k 145.3k   38 10:00:03
```

> [!TIP]
> **建议内容**：mongostat 适合看趋势而不是看单行：把采样间隔拉长到 5 秒、连续观察数十行，再对 dirty、used、qrw|arw 三列下结论，比任何单行快照都可靠。



#### mongotop

**mongotop**：是**按集合维度输出读写耗时**的命令行工具，回答「时间花在哪个集合上」的问题，与 mongostat 的整库视角互补。

```bash
mongotop --host 127.0.0.1 --port 27017 5
```

```text
2026-09-23T10:05:00.123+0800    connected to: mongodb://127.0.0.1:27017/

ns               total    read    write    2026-09-23T10:05:05+0800
shop.orders       152ms    98ms     54ms
shop.users         41ms    41ms      0ms
shop.products      18ms    12ms      6ms
```

解读要点：

- **total／read／write**：一个采样周期内该集合的总耗时与读写耗时，单位毫秒。
- **头部集合**：total 长期排在最前的集合就是负载大头，索引与模式优化优先盯它。
- **间隔参数**：命令末尾的 5 表示每 5 秒采样一次，省略时默认 1 秒。
- **使用姿势**：先 mongostat 确认整体有压力，再 mongotop 定位到集合，最后回到 explain 定位到语句，三步由面到点。

> mongotop 只统计时间分布，不解释原因。看到 shop.orders 占大头后，仍要用分析器与执行计划找出是哪类语句把时间花掉的。



#### db.serverStatus 关键指标

**db.serverStatus**：是**返回服务器运行时状态快照**的诊断命令，覆盖连接、内存、操作计数、缓存与复制等指标，粒度比 mongostat 与 mongotop 更细。

- **opcounters**：insert、query、update、delete、getmore、command 的累计值，两次采样相减即得速率。
- **connections**：current 与 available，当前连接数与剩余可用额度，逼近上限前应扩容或加代理。
- **mem**：resident 与 virtual，常驻内存与虚拟内存，单位 MB，用于判断内存是否吃紧。
- **wiredTiger.cache**：bytes currently in the cache 与 maximum bytes configured，缓存已用字节与配置上限。
- **globalLock.currentQueue**：锁等待队列长度，长期偏高说明吞吐已饱和。
- **repl**：副本集成员身份、复制状态与延迟相关字段，副本集部署时重点观察。

```js
const s = db.serverStatus();
console.log("当前连接数:", s.connections.current);
console.log("可用连接数:", s.connections.available);
console.log("缓存已用(GB):", (s.wiredTiger.cache["bytes currently in the cache"] / 1073741824).toFixed(2));
console.log("查询累计:", s.opcounters.query);
```

```text
当前连接数: 38
可用连接数: 838857
缓存已用(GB): 1.21
查询累计: 208412
```

> serverStatus 是瞬时快照：绝对值只能看水位，速率与趋势必须两次采样相减。Prometheus 的 mongodb_exporter 等监控组件，本质上就是周期性采集这份数据再加工成图表，理解了 serverStatus 就理解了监控面板上每个数字的来源。



### 常见性能问题与优化清单

#### 索引缺失与执行计划验证

**索引缺失**：是查询条件或排序字段没有可用索引、迫使存储引擎做全集合扫描的首要性能问题，在 explain 中表现为 COLLSCAN。

三个典型信号：

- **COLLSCAN**：全集合扫描，耗时随集合大小线性增长，数据量一上来最先爆掉。
- **totalDocsExamined 远大于 nreturned**：翻遍集合只挑出少数文档，说明没有索引或索引选择性太差。
- **SORT 阶段**：排序没借上索引，出现内存排序，结果集超过限制时查询直接报错。

按「等值在前、排序在后」补一个复合索引，并用 explain 前后对比验证：

```js
// 补索引前：全集合扫描
const before = db.orders.find({ userId: 10086, status: "paid" })
  .sort({ createdAt: -1 })
  .explain("executionStats");
console.log("补索引前文档检查数:", before.executionStats.totalDocsExamined);

// 等值字段在前，排序字段在后
db.orders.createIndex({ userId: 1, status: 1, createdAt: -1 });

// 补索引后：走索引
const after = db.orders.find({ userId: 10086, status: "paid" })
  .sort({ createdAt: -1 })
  .explain("executionStats");
console.log("补索引后文档检查数:", after.executionStats.totalDocsExamined);
```

```text
补索引前文档检查数: 52000
补索引后文档检查数: 12
```

> [!IMPORTANT]
> **重要内容**：建索引不等于优化完成，必须用 explain 复测确认 winningPlan 从 COLLSCAN 变为 IXSCAN。索引同时会拖慢写入并占用磁盘，只为高频查询建索引，低频查询可以容忍扫描。



#### $match 后置

**$match 后置**：是把过滤阶段写在聚合管道后部的反模式，上游阶段被迫处理全量数据，索引也用不上。

- **正确位置**：$match 作为管道第一个阶段时，可以直接利用集合索引，后续阶段只处理过滤后的数据。
- **代价**：放在 $group 或 $project 之后时，过滤对象是中间结果，无法走索引，内存与时间双输。

```js
// 反模式：先对全量订单按用户分组，再过滤出单个用户
db.orders.aggregate([
  { $group: { _id: "$userId", total: { $sum: "$amount" } } },
  { $match: { _id: 10086 } }
])
```

```js
// 改进：先过滤单个用户，再对它的订单求和
db.orders.aggregate([
  { $match: { userId: 10086 } },
  { $group: { _id: "$userId", total: { $sum: "$amount" } } }
])
```

> [!CAUTION]
> **注意内容**：$match 提前只在过滤条件引用原始字段时有效。$match 依赖 $group 算出来的字段（如汇总金额）时只能保持后置，此时应确认 $group 的上游已经用 $match 或 $limit 把数据收窄到最小。



#### 返回字段过多

**返回字段过多**：是查询不加投影、整篇文档原样回传的低效模式，网络带宽、驱动反序列化、客户端内存三方买单。

- **网络放大**：大数组与长文本字段随文档全量回传，并发一高带宽先饱和。
- **内存放大**：驱动把整篇 BSON 反序列化为对象，客户端堆压力与垃圾回收频率随之上升。

```js
// 正向投影：列表页只取需要的字段
db.products.find({ category: "book" }, { title: 1, price: 1, summary: 1 })
```

```js
// 反向投影：字段多时只排除大字段，更省事
db.products.find({ category: "book" }, { description: 0, reviews: 0 })
```

两种投影的取舍：

- **正向投影**：字段清单明确时用，返回体积最小，配合投影索引可形成覆盖查询。
- **反向投影**：字段多而大字段少时用，新增小字段后无需改代码。
- **覆盖查询**：查询、排序与投影字段全部落在同一个索引内时，explain 的 totalDocsExamined 为 0，直接从索引取数，这是读优化的上限形态。

> 投影是零成本的优化：不建索引、不改数据，只改一行代码就能把回传体积砍掉一个量级。写查询时先问一句「这一页真的需要整篇文档吗」。



#### 无 batch 控制

**无 batch 控制**：是读取游标与批量写入时不设批次上限、单次拉动或推送过量数据的反模式，表现为内存尖峰与尾延迟抖动。

- **首批规则**：find 返回的是游标，服务端首批最多返回 101 篇文档或 16MB，之后的批次靠 getmore 拉取，每批至多 16MB。
- **batchSize**：用 cursor.batchSize 显式控制每批条数，配合分页消费，避免对大结果直接 toArray 一口气拉完。
- **深翻页**：skip 跳过的条数线性增长，翻到深处越来越慢；改为记住上一页末尾 _id 的范围条件分页，每页代价恒定。
- **写入分批**：insertMany 单请求受最大消息 48MB 与单批 100000 条的上限约束，超限会被驱动自动拆分，主动按千条级别分批更可控。

```js
// 范围分页：记住上一页最后一个 _id，每页 200 条
let lastId = null;
const pageSize = 200;
for (let page = 0; page < 3; page++) {
  const filter = lastId === null ? {} : { _id: { $gt: lastId } };
  const rows = db.orders.find(filter).sort({ _id: 1 }).limit(pageSize).toArray();
  if (rows.length === 0) break;
  lastId = rows[rows.length - 1]._id;
  console.log("第", page + 1, "页条数:", rows.length);
}
```

```text
第 1 页条数: 200
第 2 页条数: 200
第 3 页条数: 200
```

> [!TIP]
> **建议内容**：把「查多少、返回哪些字段、每批多大」当成每个查询的默认三问。导出、对账这类全量扫描任务放到从库或业务低峰期执行，并显式设置 batchSize，不让大查询与在线流量抢资源。
