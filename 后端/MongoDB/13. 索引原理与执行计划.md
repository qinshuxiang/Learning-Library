## 索引原理与执行计划

### WiredTiger 的索引结构

#### B+ 树与索引页组织

**B+ 树**：是 MongoDB 索引在 WiredTiger 引擎下的组织形态，树中只有两类节点——内部节点只存分隔键作路标，叶节点同时存完整索引键与值，查找从根节点出发逐层向下，最终落在叶节点上。

- **内部节点**：只存分隔键，负责把查找范围导向下一层，不直接指向任何文档。
- **叶节点**：存放完整的索引键和对应的 **RecordId**，RecordId 是文档在集合 B+ 树中的定位符。
- **回表过程**：索引命中拿到 RecordId 后，再进入以 RecordId 为键组织的集合 B+ 树取出整份文档，这一步对应执行计划里的 FETCH 阶段。
- **页为读写单位**：磁盘上的树按页组织，缓存以页为单位加载与淘汰，一个查询快不快，很大程度取决于它要触达多少页。
- **为何选 B+ 树**：数据全部落在叶层，内部节点得以存放更多路标，树更矮更胖，一次查找触达的磁盘页更少。

> 判断一个查询快不快，本质是在判断「这棵树要往下走几层、要读多少页」。树高通常只有三四层，单次等值查询的键比较次数极少，这正是索引把全表扫描变成定点查找的原因。



#### 复合索引的键与排序

**复合索引的键**：是由多个字段按声明顺序拼接成的复合值，先按第一个字段排序，第一个字段相同的键再按第二个字段排序，以此类推。

```js
// 在 orders 集合上创建复合索引
db.orders.createIndex({ userId: 1, createdAt: -1 })
```

```text
userId_1_createdAt_-1
```

- **排序规则**：userId 全局有序；userId 相同的键内部按 createdAt 降序排列，方向由创建时的 1 与 -1 决定。
- **前缀可用**：只按 userId 查询能直接走这棵树；只按 createdAt 查询则走不了，因为 createdAt 分散在各个 userId 分组内部。
- **排序免算**：userId 等值条件加上按 createdAt 的排序，恰好等于键的既有排列顺序，优化器因此可以省掉排序阶段，直接按索引顺序回表。
- **方向敏感**：创建索引时指定降序的字段，在计划里以反向遍历匹配升序需求；多字段排序的升降混合与索引方向不一致时，索引帮不上忙。

> 复合索引能服务哪些查询，取决于查询条件与排序要求是否落在键的有序结构上。等值、排序、范围三类字段的先后设计顺序，在第 12 篇《索引：类型与创建》里展开。



### explain 与执行计划

#### explain 的三种模式

**explain 方法**：是把查询交给优化器分析并返回执行计划的接口，挂在游标上调用，参数决定计划的详略程度，共三种模式。

```js
// 三种模式详略递进，不传参等价于 "queryPlanner"
db.orders.find({ userId: 42 }).explain()
db.orders.find({ userId: 42 }).explain("executionStats")
db.orders.find({ userId: 42 }).explain("allPlansExecution")
```

- **queryPlanner**：只回答「优化器打算怎么执行」，输出 winningPlan 与被否决的 rejectedPlans，不真正执行查询，开销最小。
- **executionStats**：按 winningPlan 真实执行一遍，追加返回 nReturned、totalKeysExamined、totalDocsExamined、executionTimeMillis 等统计项，是日常调优的主力模式。
- **allPlansExecution**：在 executionStats 之上把落选计划的执行统计也跑出来，用于评估优化器是否选错了索引，开销最大。

> 排查慢查询先看 executionStats；怀疑优化器选错索引，再升级到 allPlansExecution 对比候选计划。queryPlanner 最便宜，但它给不出「实际扫了多少」这个关键事实，只靠它下结论容易误判。



#### 读懂 winningPlan

**winningPlan**：是优化器从候选计划中选出的获胜计划，以阶段嵌套的形式呈现——从外向内读，外层阶段消费内层阶段的输出，最内层就是数据入口。

```js
// 无索引可走：全表扫描
db.orders.find({ remark: "urgent" }).explain("executionStats")
```

```text
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'COLLSCAN',
      filter: { remark: 'urgent' },
      direction: 'forward'
    },
    rejectedPlans: []
  },
  executionStats: {
    nReturned: 3,
    totalKeysExamined: 0,
    totalDocsExamined: 5000,
    executionTimeMillis: 11
  }
}
```

```js
// 命中复合索引：索引扫描加回表
db.orders.find({ userId: 42 }).sort({ createdAt: -1 }).explain("executionStats")
```

```text
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'FETCH',
      inputStage: {
        stage: 'IXSCAN',
        keyPattern: { userId: 1, createdAt: -1 },
        indexName: 'userId_1_createdAt_-1',
        isMultiKey: false,
        direction: 'backward'
      }
    }
  },
  executionStats: {
    nReturned: 20,
    totalKeysExamined: 20,
    totalDocsExamined: 20,
    executionTimeMillis: 0
  }
}
```

- **COLLSCAN**：全表扫描，逐份文档检查过滤条件，文档量增长时代价线性上涨，出现它通常意味着缺索引。
- **IXSCAN**：索引扫描，沿 B+ 树定位键，是最想看到的入口阶段；direction 为 backward 表示沿索引反方向读，省掉一次显式排序。
- **FETCH**：回表，按 RecordId 取整份文档；它套在 IXSCAN 外面，说明命中索引后还需要读原文。
- **isMultiKey**：为 true 表示索引字段是数组（多键索引），一个键值对应多个文档，计划的范围收窄能力随之打折。
- **计数判读**：nReturned、totalKeysExamined、totalDocsExamined 三者接近是健康形态；keys 远大于 nReturned 说明范围扫得过宽，docs 远大于 keys 说明索引选择性差。

> 读 winningPlan 先看最内层入口是 IXSCAN 还是 COLLSCAN，再看阶段链里有没有多余的 FETCH 与排序，最后对照三个计数是否收敛。阶段结构与计数都与数据量无关，是结构问题，可以一次改到位。



#### SORT 阶段与内存排序

**SORT 阶段**：是执行计划里显式标注的内存排序节点，表示优化器没能借到索引的顺序，只能把结果集全部拉进内存排一遍。

```js
// 范围条件在前、排序字段在后：现有索引帮不上排序，只能内存排序
db.orders
  .find({ createdAt: { $gt: ISODate("2026-01-01T00:00:00Z") } })
  .sort({ userId: 1 })
  .explain("queryPlanner")
```

```text
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'SORT',
      sortPattern: { userId: 1 },
      memLimit: 104857600,
      type: 'simple',
      inputStage: {
        stage: 'COLLSCAN',
        filter: { createdAt: { $gt: ISODate("2026-01-01T00:00:00Z") } },
        direction: 'forward'
      }
    }
  },
  ok: 1
}
```

- **memLimit 的含义**：104857600 即 100MB，是单个查询内存排序的上限；结果集超过上限时查询报错，需要调用方显式声明 allowDiskUse 才允许落盘排序。
- **何时能消掉**：让排序字段接在等值条件字段的索引之后，键的顺序与 sortPattern 一致，SORT 阶段就会消失，退回上一例的 backward 读法。
- **代价定位**：SORT 挂在 COLLSCAN 上是最坏的组合——先扫全表，再对全部结果排序；两步都能被一个设计正确的复合索引消掉。

> SORT 阶段出现不代表查询写错，但每条结果都要参与键比较，数据量一大就拖慢响应并威胁内存上限。看到 SORT 先问一句「能否用复合索引的顺序替代」，答案通常是能。



#### 扫描计数与覆盖查询

**覆盖查询（Covered Query）**：是查询条件与返回字段全部落在同一索引上的查询形态——整条查询只碰索引不碰文档，回表步骤整个消失，totalDocsExamined 为 0。

```js
// 返回字段限定在索引键内，且显式排除 _id
db.orders.find({ userId: 42 }, { createdAt: 1, _id: 0 }).explain("executionStats")
```

```text
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'PROJECTION_COVERED',
      transformBy: { createdAt: 1, _id: 0 },
      inputStage: {
        stage: 'IXSCAN',
        keyPattern: { userId: 1, createdAt: -1 },
        indexName: 'userId_1_createdAt_-1',
        direction: 'forward'
      }
    }
  },
  executionStats: {
    nReturned: 20,
    totalKeysExamined: 20,
    totalDocsExamined: 0,
    executionTimeMillis: 0
  }
}
```

- **成立条件**：投影里的每个字段都在索引键中；_id 默认总被返回，不显式排除就进不了覆盖形态，这是最常见的破绽。
- **计划标志**：出现 PROJECTION_COVERED 阶段且没有 FETCH，即确认覆盖生效。
- **零文档读取**：totalDocsExamined 为 0 意味着最热的数据只有索引页，对高频取字段的列表页是数量级的收益。
- **比率速查**：keys 接近 nReturned 且 docs 为 0 是覆盖查询的典型读数；keys 远大于 nReturned 提示索引范围过宽；docs 远大于 keys 提示该索引选择性不足。

> 覆盖查询把回表归零，是执行计划调优的终点形态。但它要求返回字段克制——投影多要一个非索引字段就破功，为覆盖而把字段全塞进索引反而加重写放大，取舍要看该查询的调用频度。



### 索引选择性与代价

#### 选择性与基数

**索引选择性**：指利用索引把候选文档收窄到目标集合的能力，由索引字段的**基数**决定——基数是字段不同取值的个数，基数越高、单个值命中的文档越少，选择性越好。

```js
// 五千条订单：status 只有三种取值，userId 有四千多种
db.orders.distinct("status").length
db.orders.distinct("userId").length
```

```text
3
4862
```

- **低基数字段**：status 一个值命中上千份文档，命中索引后仍要回表一大片，多数查询收益趋近于零。
- **高基数字段**：userId 几乎每条不同，等值查询一步定位，是索引的第一候选。
- **组合出选择性**：单字段基数不足时，用复合字段补齐，例如 status 配合 createdAt 把「这一状态」收窄到「这一状态下的某段时间」。
- **ESR 顺序**：等值字段在前、排序字段居中、范围字段殿后，让键的有序结构同时服务三件事。

> 低基数不等于不能建索引，而是要看查询是否总带着其他高选择性条件来配合。判断标准只有一个：执行计划里 totalKeysExamined 与 nReturned 是否足够接近，数字会替所有争论收尾。



#### 写放大与内存占用

**索引的代价**：由写放大与内存占用两部分构成——每个索引都是一棵要随写入维护的 B+ 树，同时也是一份希望常驻缓存的数据，两者都随索引数量线性增长。

- **写放大**：插入要向所有索引各写一个键；更新改到被索引字段时，等价于一次键删除加一次键插入；删除同样要清掉全部索引中的对应键。
- **内存占用**：WiredTiger 以页为单位把索引缓存在内存里，工作集中的热索引页常驻，冷索引页在缓存压力下被反复换入换出。
- **缓存兜底**：索引页被换出后每次命中都要读盘，响应时间从内存量级跌到磁盘量级，这是「索引越多不一定越快」的直接原因。
- **缓存默认值**：WiredTiger 缓存默认取 256MB 与（物理内存减 1GB）的一半中的较大者，可用配置显式指定。

```bash
# mongod.conf：把 WiredTiger 缓存上限固定为 2GB
storage:
  wiredTiger:
    engineConfig:
      cacheSizeGB: 2
```

> [!CAUTION]
> **注意内容**：索引数量要按读写比例取舍——读多写少的集合可以索引丰富，写频繁的集合每加一个索引都在加重写放大；同时热索引的工作集必须放得进缓存，放不进去时先减索引或加内存，而不是继续叠加索引。



#### 索引失效的常见写法

**索引失效**：指查询本可走索引却在执行计划里退化成 COLLSCAN 的情况，多数由查询写法破坏了键的有序性引起。

```js
// remark 字段上已有索引，对比两种正则写法
db.orders.createIndex({ remark: 1 })
db.orders.find({ remark: { $regex: "^urgent" } }).explain("queryPlanner")
db.orders.find({ remark: { $regex: "urgent$" } }).explain("queryPlanner")
```

```text
remark_1
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'FETCH',
      inputStage: {
        stage: 'IXSCAN',
        indexName: 'remark_1',
        direction: 'forward'
      }
    }
  },
  ok: 1
}
{
  explainVersion: '1',
  queryPlanner: {
    winningPlan: {
      stage: 'COLLSCAN',
      filter: { remark: { $regex: 'urgent$' } },
      direction: 'forward'
    },
    rejectedPlans: []
  },
  ok: 1
}
```

- **前置通配的正则**：以 ^ 开头的正则能利用键的有序前缀收窄范围，以通配开头的正则只能逐键检查，直接退化为全表扫描。
- **计算型条件**：对字段做运算或函数变换后再比较的条件无法匹配键的形态，$where 这类逐文档执行的判断更是彻底绕开索引。
- **复合索引非前缀**：查询条件落在复合索引的后缀字段上时，有序结构断在前缀处，优化器宁可扫表。
- **写法先行**：失效与否最终以 explain 的输出为准，新查询上线前先跑一次 queryPlanner，成本远低于线上排障。

> 索引存在不等于索引被用上，键的有序结构只认「前缀」这一种入口。写查询时保持条件形态与键形态一致，再用执行计划做最终裁决，失效问题可以事前消灭。
