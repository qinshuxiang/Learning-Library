## 事务与写关注

### 单文档原子性与事务入口

#### 单文档操作的原子性

**单文档原子性**：是指对同一份文档的一次写操作要么全部生效、要么全部不生效，中途不存在只改了一半的中间状态，这是 MongoDB 事务模型的基座。

- **多字段同改**：一条 updateOne 的更新文档里写多少个修改符，都会作为一个整体生效，$inc 与 $push 混在一起也互不拆分。
- **查询即条件**：findOneAndUpdate 把「找到符合条件的文档再改」压缩成一次原子操作，靠条件里的状态字段避免两个请求重复处理同一单。
- **数组的边界**：对文档内数组的增删同样原子，但受 16MB 文档上限约束，数组不能当成无限增长的子表用。

```js
// 一次 updateOne 同时改余额并追加流水，两步要么都生效要么都不生效
db.accounts.updateOne(
  { _id: "a" },
  { $inc: { balance: -100 }, $push: { logs: { type: "withdraw", amount: 100 } } }
)
```

```text
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 1,
  modifiedCount: 1,
  upsertedCount: 0
}
```

```js
// findOneAndUpdate 用条件本身防止重复处理：状态已变的文档匹配不到
db.orders.findOneAndUpdate(
  { _id: 1, status: "pending" },
  { $set: { status: "paid" } },
  { returnDocument: "after" }
)
```

```text
{ _id: 1, status: 'paid' }
```

> 单文档原子性覆盖不到的场景只有一种——一次业务动作要改多份文档。识别出这种场景，才轮到多文档事务登场；在此之前，一切写操作都可以只靠文档本身保证正确。



#### 多文档事务的基本流程

**多文档事务**：是把跨文档、跨集合的多次写操作包进一个会话执行的机制，以 startTransaction 开始、以 commitTransaction 或 abortTransaction 结束，期间的操作对外不可见，要么全提交要么全回滚。

```js
const session = db.getMongo().startSession()
session.startTransaction({
  readConcern: { level: "snapshot" },
  writeConcern: { w: "majority" }
})
try {
  const accounts = session.getDatabase("bank").accounts
  accounts.updateOne({ _id: "a" }, { $inc: { balance: -100 } })
  accounts.updateOne({ _id: "b" }, { $inc: { balance: 100 } })
  session.commitTransaction()
} catch (error) {
  session.abortTransaction()
} finally {
  session.endSession()
}
```

- **startSession**：事务必须挂在会话上，会话是客户端与服务器之间携带事务状态的通道，endSession 负责最终释放。
- **startTransaction**：在参数里一次性指定 readConcern 与 writeConcern，作用于本事务内的全部操作。
- **操作走会话**：事务内的读写必须通过 session.getDatabase 拿到的集合句柄发起，直接用 db 上的句柄写的操作不属于事务。
- **提交与回滚**：commitTransaction 使全部修改对外生效；任何一步抛错就进入 abortTransaction，已做的修改全部作废。

> 这段转账代码是事务的标准骨架：会话开事务、句柄做读写、try 提交 catch 回滚 finally 收尾。readConcern 与 writeConcern 的取值语义，由「读关注与写关注」模块的考点展开。



#### 事务内的读写可见性

**事务内的可见性**：由快照隔离裁定——事务内的读看不到其他事务未提交的中间状态，能读到自己已做的写，且事务内多次读同一数据结果一致。

```js
const session = db.getMongo().startSession()
session.startTransaction()
const accounts = session.getDatabase("bank").accounts
accounts.insertOne({ _id: "tmp", balance: 0 })
// 事务内刚写入的文档，事务内的读立即可见
accounts.findOne({ _id: "tmp" })
session.abortTransaction()
session.endSession()
```

```text
{ _id: 'tmp', balance: 0 }
```

- **读到自己的写**：同一事务内先写后读，读到的是自己刚写的版本，不需要等待提交。
- **隔离别人的中间态**：其他会话此刻看不到 tmp 这份文档，它随本次 abortTransaction 一并消失，从未对外存在过。
- **多次读一致**：快照在事务开始时定格，事务内重复读同一文档拿到的始终是同一版本，不会被并发提交的写「漂移」。

> 事务的可见性规则可以总结成一句话：对内透明、对外隐藏。排障时若怀疑「事务里的读不对」，先确认读操作的句柄是否真的出自同一个 session——跨会话的读不属于本事务的快照。



#### 写冲突与重试

**事务的写冲突**：两个事务同时修改同一份文档时，后到者在提交或写入时收到 WriteConflict——事务不会自动排队等待，持续冲突最终冒泡到客户端，由应用层重跑。

- **触发条件**：两个事务的写集合出现交集，或事务的读范围被并发提交的写改变，都会触发冲突。
- **重试的单位**：冲突发生后整个事务已不可延续，重试必须从 startTransaction 重跑完整流程，而不是只重做出错的那一步。
- **重试要有上限**：热点文档上的两个事务可能反复互相冲突，无上限重试会演变成活循环，封顶几次后失败退出更稳妥。

```js
// 转账事务的完整重试形态
function transferWithRetry(fromId, toId, amount, maxRetry) {
  for (let i = 0; i < maxRetry; i++) {
    const session = db.getMongo().startSession()
    try {
      session.startTransaction({
        readConcern: { level: "snapshot" },
        writeConcern: { w: "majority" }
      })
      const accounts = session.getDatabase("bank").accounts
      accounts.updateOne({ _id: fromId }, { $inc: { balance: -amount } })
      accounts.updateOne({ _id: toId }, { $inc: { balance: amount } })
      session.commitTransaction()
      session.endSession()
      return true
    } catch (error) {
      session.abortTransaction()
      session.endSession()
    }
  }
  return false
}
```

> [!CAUTION]
> **注意内容**：重试解决的是偶发冲突，解决不了热点——同一份秒杀库存上的事务会持续互相冲突，重试再多次也进不去。冲突频繁时先改建模（拆分热点、改用条件更新），再考虑加事务。



### 读关注与写关注

#### readConcern 的三个级别

**readConcern（读关注）**：决定读操作能读到什么持久程度的数据，回答的问题是「这条数据被读到之后，会不会因为故障或选举而消失」。

- **local**：读所在节点当前可见的最新数据，不保证在故障后延续，可能随回滚消失，延迟最低，是读操作的默认级别。
- **majority**：只读已被多数节点确认的数据，读到后不会因主节点掉线选举而回滚，代价是可能读到稍旧的数据。
- **snapshot**：在多数已提交数据之上叠加快照隔离，同一事务内的多次读看到同一时刻的一致视图，是多文档事务的推荐级别。

```js
// 游标级别指定读关注
db.orders.find({ userId: 42 }).readConcern("majority")

// 事务级别指定读关注
session.startTransaction({ readConcern: { level: "snapshot" } })
```

> 三个级别是一条「新与稳」的取舍线：local 最快但可能蒸发，majority 稳定但可能偏旧，snapshot 用一致性视图解决事务内多次读的问题。能容忍极小概率回滚的展示类数据用 local 即可；资金类数据的读走 majority、事务走 snapshot。



#### writeConcern 的语义

**writeConcern（写关注）**：决定写操作要等到什么程度的确认才向客户端返回，回答的问题是「这次写返回成功之后，它在什么故障下仍然保得住」。

- **w 取 1**：主节点确认写入内存即返回，速度最快，但主节点宕机且数据未同步到从节点时，这次写会丢失。
- **w 取 majority**：等待多数节点确认，写入能挺过主节点掉线与选举，是生产环境面对重要数据时的常用取值。
- **j 取 true**：在节点确认之外额外要求写入落到 journal 磁盘日志，即使整机断电重启也不丢，进一步加大延迟。
- **wtimeout**：以毫秒为单位设置等待确认的上限，超时返回错误但写入本身可能已经发生，客户端需要自行核对最终状态。

```js
db.orders.insertOne(
  { userId: 7, amount: 99 },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }
)
```

```text
{
  acknowledged: true,
  insertedId: 7
}
```

> w 取 1 与取 majority 的差别不在快慢，而在故障后的存活性：容忍小概率丢失的日志类写入用 w 取 1 即可；下单、扣款这类不可丢的写入用 majority，必要时叠加 j 取 true。延迟与持久不可兼得，按业务分级指定，而不是全局一刀切。



#### 写超时后的状态确认

**wtimeout 超时后的状态确认**：写关注等待超时返回错误时，写入本身可能已经在主节点生效——超时只说明「没等到确认」，不等于「写失败」，客户端必须复查而不是盲目重发。

```js
try {
  db.orders.insertOne(
    { _id: 2, userId: 8, amount: 199 },
    { writeConcern: { w: "majority", wtimeout: 100 } }
  )
} catch (error) {
  // 超时不代表失败，按 _id 复查确认最终状态
  db.orders.findOne({ _id: 2 })
}
```

```text
{ _id: 2, userId: 8, amount: 199 }
```

- **超时的语义**：wtimeout 耗尽只是确认没等到，主节点上的写入往往已经落内存甚至落日志，数据还在。
- **盲目重发的后果**：把超时当失败直接重发，非 _id 主键的场景会产生重复数据。
- **正确的补救**：以业务唯一键或 _id 复查；确认失败才重试，确认成功就把这次超时记录为已成功。
- **上游配合**：给调用方的接口要把「超时待确认」与「确认失败」区分成两种返回，不能合并成同一个失败态。

> 超时是分布式写入最容易被误读的返回值：它的含义是「未知」，而不是「失败」。所有基于写关注的重发逻辑，都必须先复查再重试，这是幂等设计在写关注上的直接要求。



#### 事务中的默认关注级别

**事务的默认关注级别**：多文档事务在省略参数时默认采用 readConcern snapshot 与 writeConcern majority——事务天生按最稳的一档配置，显式参数只在需要调整时才写。

- **读默认 snapshot**：事务内读只能取 local 或 snapshot 两个值，snapshot 是默认值，保证事务内视图一致。
- **写默认 majority**：事务提交默认等待多数节点确认，保证提交后的事务结果挺过故障切换。
- **显式放宽的场合**：只读的分析型事务对持久性不敏感时，可把写关注降级换取更快的响应；资金类事务可叠加 j 选项把日志落盘也纳入确认。
- **显式收紧的界限**：关注级别只会改变确认的严格程度，不会扩大事务的隔离能力，隔离上限由 snapshot 锁定。

> 事务的默认值已经是生产级配置，多数场景不必显式传参；需要写参数时先想清楚「放宽换什么、收紧护什么」，而不是把默认值原样抄一遍。



### 事务的边界与建模取舍

#### 事务需要副本集环境

**多文档事务的运行前提**：是副本集或分片集群——单机 standalone 模式的 mongod 上开启事务，会在提交时报错。

```js
const session = db.getMongo().startSession()
session.startTransaction()
session.getDatabase("bank").accounts.insertOne({ _id: "a" })
session.commitTransaction()
```

```text
MongoServerError[IllegalOperation]: Transaction numbers are only allowed on a replica set member or mongos
```

- **根因**：事务的提交、回滚与故障恢复依赖副本集各节点之间的协调机制，单机没有这条协作链路。
- **开发环境**：本机调试事务的最简做法是把单机转成单节点副本集，功能与生产语义完全一致。
- **分片集群**：事务跨分片时由路由层协调提交，客户端用法不变，延迟高于单个副本集内的事务。

```js
// 单机开发：初始化单节点副本集后重启 mongod 生效
rs.initiate({ _id: "rs0", members: [{ _id: 0, host: "localhost:27017" }] })
```

```text
{ ok: 1 }
```

> 依赖事务前先确认部署形态：standalone 上写好的事务逻辑无法验证，报错点出现在 commit 而不是建会话，容易被误判成代码问题。本地起一个单节点副本集，是事务开发的最低成本配置。



#### 时长与 oplog 大小的限制

**事务的两条硬边界**：分别卡在时长与体积上——单个事务有默认 60 秒的生命周期上限，且整个事务在 oplog 里只落一条记录，受 16MB 上限约束。

- **时长上限**：事务存活超过 transactionLifetimeLimitSeconds（默认 60 秒）会被服务端中止，客户端收到超时错误，本次事务已做的修改全部回滚。
- **oplog 体积**：一个事务的全部修改打包成一条 oplog 记录，总量超过 16MB 会提交失败，这是 BSON 文档上限在事务上的延伸。
- **控制手段**：缩小事务内的读写数量、让事务内的查询条件走索引避免长扫描、把大事务拆成多个小事务，都是绕开两条边界的正规做法。

> [!CAUTION]
> **注意内容**：事务里跑无索引的全表扫描会同时撞上两条边界——扫描拖长事务寿命，扫过的文档撑大 oplog 条目。事务应当短小、条件应当走索引，把事务当成兜底手段，而非常规写法。



#### 大事务的拆分手法

**大事务的拆分**：当一次业务动作要改的文档多到逼近 16MB 或 60 秒边界时，把一个事务拆成先后提交的多个小事务，并以「可重跑」作为设计目标。

- **按业务单元切**：批量迁移一万条数据，以每百条为一个事务提交，任何一个批次失败只需重跑该批次。
- **每步幂等**：拆分后中间某步可能失败重跑，写操作必须可重复执行而不产生副作用，例如用 $set 覆盖固定值，而不是再 $inc 一次。
- **接受中间可见**：小事务各自提交后，中间状态对 majority 读可见；业务上能接受「改了一半的批处理结果」才允许拆，收银类动作则不可拆。
- **宁可慢不要超**：拆分以守边界为目的，批次大小留出余量，让事务在 60 秒内从容结束。

```js
// 批量迁移：每批独立提交，失败只重跑当前批
const batch = db.source.find({ migrated: { $ne: true } }).limit(100).toArray()
batch.forEach(function (doc) {
  db.target.insertOne(doc)
  db.source.updateOne({ _id: doc._id }, { $set: { migrated: true } })
})
```

> [!CAUTION]
> **注意内容**：拆分只适用于批处理与迁移这类允许中间态的业务动作；转账、扣库存这类要求「要么全成要么全败」的动作不可拆分——宁可缩小单批数量，也不许用拆分绕过原子性要求。



#### 建模取舍：优先单文档原子性

**事务的定位**：是覆盖跨文档场景的兜底机制，而不是默认写法——能用单文档原子性表达的业务动作，就不该升级成事务。

- **优先内嵌**：订单与其明细行、文章与其评论摘要，这类「同生共死」的数据优先内嵌成一份文档，一次写操作天然原子，无需任何事务协调。
- **条件更新替代锁**：需要「检查再改」的竞态场景，把旧状态写进查询条件做条件更新，往往比开事务更轻、并发表现更好。
- **事务的适用面**：转账、库存扣减与订单创建这类必须跨文档且无法内嵌的动作，才是事务的正当场景。
- **代价意识**：事务持有锁与快照、独占会话、受时长与体积双重限制、要求副本集环境，每一项都是单文档写没有的成本。

```js
// 内嵌明细的订单：一次 updateOne 同时改主单金额与明细数量，天然原子
db.orders.updateOne(
  { _id: 1001, "items.sku": "A1" },
  { $inc: { total: -99, "items.$.qty": -1 } }
)
```

```text
{
  acknowledged: true,
  insertedId: null,
  matchedCount: 1,
  modifiedCount: 1,
  upsertedCount: 0
}
```

> 判断顺序固定：先问能不能把数据收进一份文档，再问能不能用条件更新解决，两条路都走不通才开事务。多数「想上事务」的需求，在调整模式设计之后会自行消失。
