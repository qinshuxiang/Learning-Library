## 分片集群

### 分片与集群架构

#### 分片解决的规模问题

**分片（sharding）**：是把一个集合的数据按分片键拆分、横向分布到多台机器的架构手段，解决复制集在数据体量与写入吞吐上的单机天花板。

- **数据体量**：数据集大到单机磁盘装不下、内存装不下工作集时，索引与缓存全面失效，查询延迟陡增；分片把数据切开放进多台机器。
- **写入吞吐**：复制集只有 primary 一个写入点，写入上限被单机锁死；分片让每个分片各有一个 primary 并行接收写入。
- **成本曲线**：垂直扩容依赖更大更贵的机器，价格随规格非线性上升；分片用多台标准机器横向叠加，容量与吞吐随分片数近似线性增长。
- **时间维度**：时间序列、日志、订单这类按时间持续增长的集合，是分片收益最直接的载体；体量稳定的集合通常不必分片。

> 分片不是性能优化的第一步，索引、模式设计、硬件升级能解决绝大多数瓶颈。分片的运维复杂度、选键风险与跨分片查询代价都显著高于复制集，确有持续增长的容量压力时才引入。



#### 三大组件：mongos、config servers 与 shard

**分片集群三大组件**：mongos 负责路由请求，config servers 保存路由所需的元数据，shard 承载数据本体，三者各司其职。

- **mongos（路由进程）**：无状态的查询路由器，按分片键把请求发给目标分片并合并结果；应用只连接 mongos，从不直连 shard，mongos 可随负载随意增加。
- **config servers（配置服务器）**：以复制集形态部署，存储 chunk 分布、区间边界、集合与分片的映射等元数据；集群所有 mongos 共享同一份元数据事实。
- **shard（分片）**：承载真实数据的复制集，自身具备高可用能力；分片数量决定集群的总容量与总吞吐。

```js
// 连接 mongos 执行带分片键的查询，mongos 直接定位目标分片
db.orders.find({ userId: 42 })
```

```text
[
  {
    _id: ObjectId('665f1a2b3c4d5e6f708192a1'),
    userId: 42,
    item: 'keyboard',
    price: 199
  }
]
```

- **定向查询**：条件包含分片键时，mongos 查元数据找到目标 chunk 所在分片，请求只发给一个 shard，代价与单机查询相当。
- **广播查询**：条件不含分片键时，mongos 把请求扇出到全部 shard 再归并结果，分片越多这类查询越贵，分片集群的慢查询大多源于此。

> 三大组件里 mongos 无状态可随意增加，config servers 只存体量很小的元数据，真正的数据与负载全在 shard 上。容量规划的核心问题是「需要几个分片」，分片数由数据总量除以单机容量再加增长余量得出。



### 分片键的选择

#### 分片键的选择标准：基数、频率与单调变化

**分片键（shard key）**：是集合启用分片时选定的字段或复合字段，数据按它的取值被切成 chunk 并分布到各分片；选键标准集中在基数、频率与单调变化三点。

- **基数（cardinality）**：分片键的不同取值数决定 chunk 数上限，只有两三百个取值的键（如国家字段）意味着数据最多被切成几百块，扩分片也切不出新块。
- **频率（frequency）**：单个键值挂载的文档过多会形成无法再拆的热点 chunk，理想状态是数据与访问沿键值均匀摊开。
- **单调变化（monotonicity）**：键值随时间单调递增或递减时，新写入永远落在值域的一端，写入热点集中到单个分片。
- **查询覆盖**：分片键应被高频查询条件覆盖，定向路由才打得开；完全不被查询使用的键只解决均衡，解决不了路由。
- **复合键策略**：单一字段难以同时满足多条标准时，用高基数字段做前缀、能打散写入的字段做后缀组成复合分片键。

> 选分片键是一次决定、长期买单的决策。选键前先穷举核心查询条件，把「路由打得开、写入摊得匀、切得动」三条放在一起权衡，任何一条不过关都应回到选键环节重来。



#### 范围分片与哈希分片

**范围分片（ranged sharding）**与**哈希分片（hashed sharding）**：是切分数据的两种策略，前者按分片键值的区间连续划分，后者按键值的哈希结果打散划分。

```js
// 对 userId 启用哈希分片，把写入打散到各分片
sh.shardCollection("shop.orders", { userId: "hashed" })
```

```text
{ ok: 1 }
```

- **范围分片**：相邻键值落进同一 chunk，按时间、按编号的范围查询可以直接路由到少数分片；代价是键值分布不均或单调递增时产生热点。
- **哈希分片**：键值经哈希后近乎均匀落位，写入负载天然摊平，是单调递增键的解药；代价是范围查询退化为全分片广播。
- **选择依据**：写多、点查多、键单调递增选哈希；范围扫描是核心访问模式选范围；两种需求并存时用复合键，哈希字段扛写入与点查，另一字段扛范围。
- **映射不变量**：两种策略共享同一套 chunk 拆分与 balancer 迁移机制，差别只在「键值如何映射到 chunk」。

```js
// 范围分片示例：按时间字段切分，报表按天查询可直接路由
sh.shardCollection("app.logs", { createdAt: 1 })
```

```text
{ ok: 1 }
```

> 一句话记忆：哈希分片用范围查询换写入均匀，范围分片用写入均匀换范围查询。先明确核心访问模式，再倒推策略，顺序不能反。



#### 分片键选择陷阱：单调递增键热点

**单调递增键热点**：用自增 _id、时间戳、自增订单号这类键做范围分片时，所有新写入的键值都落在当前最大区间，集群退化为「只有一个分片在写」。

- **现象**：监控上某一个分片的写入速率、CPU、内存占用远高于其余分片，增加分片毫无缓解。
- **根因**：范围分片按值域切块，递增键的新值永远落在最后一个区间，balancer 迁移的是存量旧数据，救不了持续产生的新写入。
- **解法**：改用哈希分片打散写入；或用「递增字段加随机性字段」的复合键；或改选业务上无单调性的高基数字段。

```js
// 应用日志的 createdAt 单调递增，范围分片必然热点，改用哈希分片
sh.shardCollection("app.logs", { createdAt: "hashed" })
```

```text
{ ok: 1 }
```

> [!CAUTION]
> **注意内容**：单调递增键加范围分片是最常见的选键事故，且往往业务上线后才暴露，返工成本极高。凡是「每条新数据的键都比旧数据大」的字段，做范围分片前必须改为哈希或复合键。



#### 复合分片键的设计示例

**复合分片键**：是把多个字段组合成一个键的方案，让不同字段分别承担打散写入、支撑路由、保留范围语义的职责，是单一字段过不了选键三标准的标准解法。

- **职责分工**：前缀字段负责写入均匀与点查路由，后续字段保留相邻性，让同用户的数据落在同一 chunk、范围查询不必广播。
- **键构成**：如 userId 加 orderId——userId 打散写入热点，orderId 让单用户的订单按序相邻，二者复合后基数与频率同时达标。
- **评估方法**：列出前五个高频查询，逐一核对每个查询能否被复合键的前缀覆盖；一个都不覆盖的键不合格。

```js
// 哈希前缀打散写入，orderId 保留单用户范围内的相邻性
sh.shardCollection("shop.orders", { userId: "hashed", orderId: 1 })
```

```text
{ ok: 1 }
```

> 复合键是选键的「缝合术」：每个字段只出一份力，合成后同时满足基数、频率与单调变化。字段顺序即职责分配，前缀给写入与路由，后缀给范围，调换顺序等于换一种取舍。



### chunk 与 balancer

#### chunk 的划分与迁移

**chunk（数据块）**：是分片键值域上的一段连续区间，是数据分布与迁移的最小单位；chunk 超大被拆分，分布不均被迁移。

- **拆分（split）**：单个 chunk 的数据量超过默认上限（128MB）时，按分片键把它切成多个 chunk，拆分只改元数据、不搬数据，代价很小。
- **迁移（migration）**：balancer 判断分片间 chunk 数量失衡时，把 chunk 从多的一端搬到少的一端，迁移是真实的数据复制，消耗磁盘 IO 与网络带宽。
- **分布查询**：sh.status() 打印每个集合的分片键与 chunk 分布，是观察均衡状态的第一入口。

```js
sh.status()
```

```text
sharding
{
  configsvr: {
    _id: 'config',
    topology: 'ReplicaSet',
    hosts: [ 'cfg1:27019', 'cfg2:27019', 'cfg3:27019' ]
  },
  shards: [
    { _id: 'shard01', host: 'shard01/n1:27017,n2:27017' },
    { _id: 'shard02', host: 'shard02/m1:27017,m2:27017' }
  ],
  balancer: { mode: 'full', currentlyEnabled: true }
}
```

> chunk 是「逻辑区间」而非物理文件，拆分与迁移改的是 config servers 里的元数据加上分片间的数据搬运。理解这一点就能解释：为什么拆分很快、迁移很慢，为什么 chunk 分布在 mongos 上实时可见。



#### jumbo chunk 的识别与处理

**jumbo chunk**：是因分片键取值过于集中而无法拆分、超过上限的 chunk，balancer 不搬它，长期滞留会让单个分片持续膨胀、均衡目标永远无法达成。

- **成因**：分片键基数不足或频率失衡，例如大量文档的键取同一个值，这个值所在的 chunk 永远拆不开。
- **识别**：sh.status() 或 balancer 日志里出现 jumbo 标记即命中。
- **短期处理**：对单个 chunk 执行手动拆分（splitFind），尝试按内部文档边界切开。
- **根治路径**：改选分片键，走 reshardCollection 重建数据分布，参数调优解决不了键的问题。

```js
// 手动对指定键值所在的 chunk 做一次拆分尝试
sh.splitFind("app.logs", { createdAt: ISODate('2026-09-01T00:00:00Z') })
```

```text
{ ok: 1 }
```

> jumbo chunk 是「分片键没选好」在运维层的显影：搬不走、拆不开的 chunk 会把均衡永远卡住。见到的第一反应不该是调参数，而是回头复查分片键的基数与频率。



#### balancer 均衡器

**balancer（均衡器）**：是运行在 config server 主节点上的后台进程，周期检查分片间 chunk 数量差，超过阈值就把迁移任务下发执行，让数据分布保持均衡。

- **触发条件**：分片间 chunk 数量差超过迁移阈值时开始迁移，目标不是绝对相等，而是把差距压回阈值以内。
- **运行窗口**：迁移消耗磁盘 IO 与网络带宽，生产环境用 activeWindow 把 balancer 限定在业务低峰时段。
- **导入期暂停**：批量导入大数据前先关掉 balancer，导入完成再开，避免导入与迁移互相拖慢。

```js
// 设置均衡器只在凌晨两点到六点运行
db.getSiblingDB("config").settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)
```

```text
{
  acknowledged: true,
  insertedId: 'balancer',
  matchedCount: 0,
  modifiedCount: 0,
  upsertedCount: 1
}
```

```js
// 查看均衡器当前是否在运行
sh.getBalancerState()
```

```text
true
```

> balancer 迁移慢不是故障，搬一个大 chunk 本来就需要时间；真正的故障信号是迁移长期完不成，通常意味着存在 jumbo chunk 或键值分布极端失衡，处理思路回到选键上。



#### 预拆分：大数据导入前的均衡准备

**预拆分（pre-splitting）**：是在大数据导入前按预估的键值范围提前切好 chunk 的操作，避免导入过程中反复触发拆分与迁移。

- **适用场景**：已知数据总量与键值分布的批量导入，如历史数据迁移、日志回灌。
- **操作方式**：用 sh.splitAt 在预估的边界键值处手动切分，或对哈希分片按哈希空间均分预切。
- **配套动作**：导入期间关闭 balancer，导入完成后再开启，让均衡器做收尾而非全程参与。

```js
// 在键值 42 处预切一个边界
sh.splitAt("shop.orders", { userId: 42 })
```

```text
{ ok: 1 }
```

> 预拆分解决的是「导入期抖动」，不是「分布不均」——键值分布本身的问题仍要靠选键解决。大数据导入的标准组合是：预拆分、关 balancer、导入、开 balancer。



### 分片键的变更

#### 启用分片：enableSharding 与 shardCollection

**shardCollection**：是对集合启用分片的入口命令，前置动作是用 enableSharding 声明库级分片能力，再为集合指定分片键；两条命令都在 mongos 上执行。

```js
// 先开库级分片，再给集合定分片键
sh.enableSharding("shop")
sh.shardCollection("shop.orders", { userId: 1 })
```

```text
{ ok: 1 }
```

- **时机**：空集合或小集合时就应定好分片键；数据量大后再启用，初始分片阶段要切分并搬移大量存量数据。
- **键即契约**：shardCollection 之后所有写入按新键路由，之前的存量数据随后被逐步切成 chunk 分布到各分片。
- **哈希键准备**：大集合用哈希分片前可先建哈希索引，减少启用期的建索引与均衡负担。

> 启用分片本身只是一条命令，风险全部集中在「键选什么」。命令在秒级执行完，键的错误要用天级的数据迁移偿还，启用前的选键评审才是真正的工作量所在。



#### 无法更改分片键的代价

**分片键一经确定不可修改**：键的字段、类型、哈希与否都写死在集合元数据里，常规更新不允许触碰；这把选键错误从「可配置问题」变成「数据架构问题」。

- **历史代价**：早期版本改键的唯一路径是新建集合并全量搬数据，TB 级集合的窗口期与双倍存储让返工几乎不可行。
- **键值约束**：已分片文档的分片键字段值不能随意更新，修改分片键值有专门限制，应用层应把键字段视为只读。
- **波及面**：选键失误同时损害查询路由与写入均衡，性能问题随数据增长放大，越晚处理代价越高。
- **轻量补救**：只想在现有键后追加子字段时，refineCollectionShardKey 可微调键构成，比整键重分片轻得多。

> 把分片键字段当成「集合的宪法条款」来对待：建分片前的评审成本以小时计，建分片后的纠错成本以周计。所有分片键字段在应用层都应禁止更新语义。



#### reshardCollection 在线重分片

**reshardCollection**：是在线更换分片键的命令——把数据按新键重新分布，期间持续同步增量写入，完成后原子切换到新布局，业务基本无感。

```js
// 把 orders 的分片键从 userId 范围分片改为 userId 哈希分片
sh.reshardCollection("shop.orders", { userId: "hashed" })
```

```text
{ ok: 1 }
```

- **执行过程**：先按新键把存量数据克隆到临时布局，同步期间的增量写，最终原子切换，旧布局随之丢弃。
- **资源代价**：重分片期间集群同时承载双份数据与额外同步负载，吞吐下降，大集合重分片以小时到天计。
- **执行前提**：所有分片必须在线，新键仍要通过选键三标准；哈希键与范围键之间可以借此互相转换。

> [!IMPORTANT]
> **重要内容**：reshardCollection 降低了改键代价，但没有取消选键责任——它是逃生通道，不是常规操作。凡是「先上线再调键」的计划，都应默认按一次完整的数据重分布来评估窗口与资源。
