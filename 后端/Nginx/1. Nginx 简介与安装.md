## Nginx 简介与安装

### Web 服务器与 Nginx 的定位

#### Web 服务器的定义

**Web 服务器**：是驻留在服务器端、通过 HTTP（HyperText Transfer Protocol，超文本传输协议）或 HTTPS 与客户端通信，接收请求并返回响应的软件系统。它的工作流程可概括为：客户端发起请求，服务器解析请求、定位或生成资源，再把结果封装成 HTTP 响应送回客户端。

- **本职工作**：监听端口（默认 80 对应 HTTP，443 对应 HTTPS）、接受 TCP 连接、解析 HTTP 报文、返回状态码、响应头与响应体。
- **常见 Web 服务器**：Nginx、Apache HTTP Server、IIS、Caddy、Lighttpd 等，其中 Nginx 与 Apache 长期位居各类 Web 服务器使用率统计前列。
- **能力边界**：Web 服务器只负责 HTTP 协议层的收发与资源组织，不承担业务计算——业务逻辑由后端应用（如 Java、Python、Node.js 程序）完成。

> 容易混淆的一对概念：**Web 服务器**（如 Nginx）处理 HTTP 请求与静态资源；**应用服务器**（如 Tomcat、uWSGI）承载业务运行时。实务中两者普遍组合使用——Nginx 在前承接流量，应用服务器在后执行业务。



#### 静态内容与动态内容

Web 服务器返回的内容按生成时机分为**静态内容**与**动态内容**两类，这一区分决定了 Nginx 在整条链路中扮演的角色。

- **静态内容**：请求到达之前就已经以文件形式存在的内容，如 HTML、CSS、JavaScript、图片、字体、音视频。Web 服务器只需把文件原样读出并回传，不执行任何业务代码。
- **动态内容**：请求到达后才由程序实时计算生成的内容，如查询数据库后渲染的页面、JSON 接口数据。Web 服务器自身不生成它，而是转交给后端应用处理。

**静态内容的吞吐能力远高于动态内容，二者的处理成本不在一个量级。**

- 静态内容的热点路径是磁盘（或操作系统页缓存）到网络，Nginx 可借助 sendfile 等机制让数据从内核直接发往网卡，几乎不消耗用户态 CPU。
- 动态内容的成本在于业务计算与数据库查询，通常比静态内容慢一到几个数量级，因此架构上普遍用 Nginx 挡在最前面，把动态请求转发给上游应用。

> 判断一个请求是静态还是动态，看的不是 URL 后缀，而是**由谁生成响应**：由 Nginx 直接读文件返回的是静态，被转发给后端应用生成的是动态。现代开发中常把所有请求都交给后端路由，再由后端决定是否读取静态文件。



#### Nginx 的多重角色定位

**Nginx**（读作 engine-x）是一个开源的高性能 Web 服务器，同时兼备反向代理、负载均衡器与 HTTP 缓存的角色。它由 C 语言编写，以事件驱动架构著称，是当今互联网基础设施中使用最广的基础组件之一。

- **Web 服务器**：直接托管静态资源，处理 HTTP 与 HTTPS 请求，支持虚拟主机、URL 重写、访问控制、压缩、限速等能力。
- **反向代理**：代表服务端接收客户端请求，再把请求转发给内网的真正服务（上游），客户端感知不到上游的存在。
- **负载均衡器**：把流量按策略分摊到多台上游服务器，支持轮询、加权、IP 哈希等分发算法，并能剔除不健康的节点。
- **HTTP 缓存**：缓存上游的响应内容，命中后直接以缓存应答客户端，减轻上游压力、降低响应延迟。

> [!TIP]
> **建议内容**：初学者不必把四个角色背成并列关系——它们其实是同一台 Nginx 在同一份配置里的不同职责层次：最基础的是 Web 服务器能力，反向代理与负载均衡建立在其上，缓存又叠加在反向代理之上。本主题后续章节将按此顺序逐步展开。



### Nginx 的诞生历史

#### C10K 问题

**C10K 问题（Concurrent 10,000 Connections Problem）**：指服务器同时维持一万个客户端连接时，传统网络编程模型与操作系统调度方式难以支撑的现象。该概念由工程师 Dan Kegel 于 1999 年前后提出并撰文总结，是理解 Nginx 架构设计动机的钥匙。

- **问题背景**：万级并发连接所需的内存与带宽在当年已不昂贵，瓶颈不在硬件，而在软件模型。
- **传统模型的做法**：为每个连接分配一个线程（或一个进程），连接的生命周期与执行流绑定。
- **撑不住的原因**：一是内存——每个线程要预留独立调用栈，动辄以兆计，上万线程即是数 GB 到数十 GB 级别的开销；二是调度——线程间上下文切换频繁，CPU 大量时间耗在切换而非干活上；三是锁竞争——共享状态的同步开销随并发数急剧上升。

**C10K 问题的本质不是连接多，而是为每个连接付出一个执行流（线程或进程）的代价不可持续。**

> 注意区分：C10K 说的是同时**维持**一万条连接，不是每秒处理一万个请求。长连接场景（如推送、长轮询）中连接数远大于活跃请求数，每连接一线程的模型会为大量空闲连接白白占用执行流，这正是它失效的典型场景。C10K 问题的标准解法是 I/O 多路复用加事件驱动，详见本主题第 2 章。



#### 诞生与开源历程

Nginx 由俄罗斯工程师 **Igor Sysoev** 开发，其设计动机直接指向 C10K 问题。

- **2002 年前后**：Sysoev 在俄罗斯大型门户 Rambler 工作期间开始开发 Nginx，目标是在低资源消耗下支撑大规模并发连接。
- **2004 年 10 月**：以 0.1.0 版本首次公开发布，采用类 BSD 许可证开源。
- **2011 年**：Sysoev 与 Maxim Konovalov 成立 Nginx 公司（Nginx, Inc.），开始商业化运营。
- **2019 年**：网络设备厂商 F5 收购 Nginx 公司；收购完成后开源版继续维护，商业版 Nginx Plus 由 F5 售卖。

**Nginx 从诞生起就是为高并发而生的，事件驱动是它的基因，而不是后来打补丁的结果。**

> 与之对照，Apache 诞生于 1995 年，早期连接处理模型并非为万级并发设计，这正是 Nginx 问世后迅速被高流量网站采用的原因。务实的说法是：Nginx 的优势不在于功能比 Apache 多，而在于一开始就解决了并发与资源占用这个对的问题。



#### 开源版与商业版

如今的 Nginx 产品线分为两条主线：**开源版**与**商业版并存**。

- **开源版（Nginx Open Source）**：以类 BSD 许可证发布，源码可从 nginx.org 官网获取，包含绝大多数常用能力，免费使用。
- **商业版（Nginx Plus）**：Nginx 公司（现为 F5）提供的付费订阅产品，在开源版基础上增加主动健康检查、会话保持增强、可视化监控与 API 动态配置等企业特性。

> [!NOTE]
> **提醒内容**：学习与绝大多数生产部署使用开源版即可。两个版本的核心架构与配置语法一致，Nginx Plus 的增量属于运维特性而非引擎差异，因此本主题全部内容对两个版本通用。



### Nginx 与 Apache 的对比

#### 连接处理模型之差

Nginx 与 Apache 最本质的差异在连接处理模型：**Nginx 采用事件驱动模型**（少量 worker 进程，worker 内部以事件循环驱动所有连接），**Apache 传统上采用每连接一进程或一线程的模型**。

- **Nginx**：少量 worker 进程，每个 worker 用 I/O 多路复用同时看护成千上万条连接，连接之间不占用独立执行流。
- **Apache（传统 MPM）**：prefork 模式下一连接一进程，worker 模式下一连接一线程；进程或线程的创建、销毁、切换成本随并发数线性放大。
- **Apache 2.4 的补齐**：2.4 版本引入 event MPM，让 Apache 也具备了事件驱动的连接处理能力，与传统模式的差距已明显缩小。

**模型差异决定了资源曲线的形状：连接数增长时，Nginx 的内存与 CPU 占用平缓增长，而每连接一线程的模型则陡峭增长。**

> event MPM 的引入说明两种模型并非不可逾越，Apache 并非做不了高并发。但历史上大量 Apache 模块（尤其是把解释器嵌入进程的动态语言模块）建立在每连接一进程的假设之上，迁移成本高，因此实务中 Nginx 在纯高并发接入场景仍是更省心的默认选择。



#### 动态内容处理与资源占用

两台服务器处理动态内容的方式截然相反，这也是二者生态差异的根源。

- **Apache**：以模块机制把动态语言解释器**内嵌**到自身进程里，经典组合是 mod_php——PHP 解释器直接运行在 Apache 进程内，动态请求不经进程间转发，一体化程度高。
- **Nginx**：自身只做静态服务与转发，动态请求交给**上游应用**处理，经典组合是 php-fpm——Nginx 通过 FastCGI 协议把 PHP 请求转交给独立的进程池。
- **资源占用**：Nginx 空载内存常以个位数兆字节计，静态文件服务吞吐高；Apache 进程池常驻内存更大，但功能模块开箱即用。

> **内嵌**与**转发**各有利弊：内嵌省去进程间通信，却把解释器的稳定性与 Web 服务器绑死，一处内存泄漏可能拖垮整个服务器；转发多一跳开销，却实现了 Web 层与应用层的隔离，应用可独立扩容、独立重启。现代架构几乎一致选择转发路线，Nginx 的定位恰好踩在这条路线上。



#### 配置组织差异

两者的配置哲学同样相反。

- **Apache**：支持**分布式配置**，可在网站目录下放置 .htaccess 文件，对单个目录逐级覆盖主配置，权限灵活但配置分散，且每次请求都可能需要重读配置。
- **Nginx**：坚持**集中式配置**，全部行为写进配置文件，修改须 reload 才生效，没有 .htaccess 的对应物；配置集中、可审计、请求处理路径稳定。

> [!IMPORTANT]
> **重要内容**：场景决定选型，没有绝对优劣。依赖大量历史 .htaccess、依赖 Apache 生态模块、或团队已有 Apache 运维经验时，Apache 仍是合理选择；面向高并发接入、静态资源服务、反向代理与负载均衡，Nginx 是当今的主流默认项。实务中最常见的组合是两者并用：Nginx 在前做接入层，Apache 或各类应用服务器在后做业务层。



### 版本分支

#### mainline 与 stable 的区别

Nginx 官方同时维护两条版本分支：**mainline（主线）**与**stable（稳定）**。

- **mainline（主线）**：承载最新特性与修复的主干分支，新功能先出现在这里，滚动更新较快。
- **stable（稳定）**：从主线分叉出的维护分支，只合入关键缺陷修复，不引入新特性，更新节奏慢、行为可预期。
- **命名规律**：同一主版本下，次级版本号为偶数对应稳定分支，为奇数对应主线，如 1.26.x 为稳定、1.27.x 为主线。

> [!NOTE]
> **提醒内容**：官方文档有一处常被误读的表述——nginx.org 指出主线分支通常被认为比稳定分支更可靠，因为缺陷修复总是先进入主线。这里的可靠指代码质量而非行为稳定性，两个分支都是经过充分验证的正式发布。



#### 分支选型建议

两条分支各有明确的适用人群，选型取决于对新特性的需求强度。

- **选稳定分支**：追求变更最少、升级风险最低，生产环境没有升级压力时优先选择，这是通说中的保守派做法。
- **选主线分支**：需要新特性、新模块或最新缺陷修复时选择；官方文档亦指出主线通常是推荐起点。
- **共同原则**：无论哪条分支，升级都应先在测试环境验证配置兼容性，再滚动到生产。

> 实务中包管理器源决定了可用分支：发行版自带源的版本偏旧，nginx.org 官方源可在稳定与主线之间选择。个人学习与大多数业务场景，跟随官方源的稳定分支即可满足全部需求。



### Nginx 的安装

#### Ubuntu/Debian 下用 apt 安装

在 Ubuntu 与 Debian 系统上，最快的途径是发行版自带的 apt 源。

```bash
sudo apt update
sudo apt install nginx
```

- **优点**：一条命令完成安装，依赖由系统托管，随 apt upgrade 统一升级。
- **缺点**：发行版源里的版本往往明显落后于官方源，新模块与新特性可能缺失。
- **安装后**：服务通常已自动启动，可用 systemctl status nginx 确认。



#### 添加 nginx.org 官方源

需要官方版本时，导入官方签名密钥并添加 nginx.org 软件源，再用 apt 安装。

```bash
# 导入官方签名密钥
curl https://nginx.org/keys/nginx_signing.key | gpg --dearmor \
    | sudo tee /usr/share/keyrings/nginx-archive-keyring.gpg >/dev/null

# 写入官方源（以 Ubuntu 为例，Debian 换用 debian 发行版名）
echo "deb [signed-by=/usr/share/keyrings/nginx-archive-keyring.gpg] \
http://nginx.org/packages/ubuntu $(lsb_release -cs) nginx" \
    | sudo tee /etc/apt/sources.list.d/nginx.list

sudo apt update
sudo apt install nginx
```

- 官方源安装的主配置目录同样在 /etc/nginx/，但目录组织与发行版源略有差异（如默认不含 sites-enabled 目录）。
- 官方源的安装命令细节随版本演进可能调整，动手前以 nginx.org 官网 Linux packages 安装页的当前指引为准。

> [!IMPORTANT]
> **重要内容**：同一台机器上发行版源与官方源提供的 nginx 包同名，混装会造成版本与目录结构混乱。切换来源前先卸载旧包并确认 /etc/nginx 目录状态，避免旧配置被新包静默覆盖或残留。



#### CentOS 下用 yum/dnf 安装

在 CentOS、RHEL、AlmaLinux 等系统上，通过 dnf（旧版为 yum）安装。

```bash
# 新版系统用 dnf，旧版把 dnf 换成 yum 即可
sudo dnf install nginx
```

发行版源不可用或需要官方版本时，写入 nginx.org 的仓库文件再安装。

```bash
sudo tee /etc/yum.repos.d/nginx.repo <<'EOF'
[nginx-stable]
name=nginx stable repo
baseurl=http://nginx.org/packages/centos/$releasever/$basearch/
gpgcheck=1
enabled=1
EOF

sudo dnf install nginx
```

- 仓库文件里把 enabled 置于 nginx-mainline 段可切换主线分支，默认走稳定分支。
- 安装后同样注册为 systemd 服务，用 systemctl start nginx 启动。



#### macOS 下用 Homebrew 安装

macOS 上的标准途径是 Homebrew。

```bash
brew install nginx

# 启动服务（可选，也可前台运行 nginx 命令调试）
brew services start nginx
```

- **配置目录**：/opt/homebrew/etc/nginx/，主配置为 nginx.conf。
- **静态目录**：/opt/homebrew/var/www/，日志在 /opt/homebrew/var/log/nginx/。
- **默认端口**：Homebrew 版默认监听 8080 而非 80，因为 80 端口需要特权；开发调试够用，生产部署则在 Linux 服务器上。

> [!TIP]
> **建议内容**：macOS 适合作为学习环境而非生产环境。本机调试时用 127.0.0.1:8080 访问默认欢迎页即可验证安装成功；配置文件改动后记得先执行 nginx -t 再重载。



#### 源码编译安装

源码编译是获取最大定制自由度的方式，标准流程为 configure、make、make install 三步。

```bash
# 安装编译工具与依赖库（Ubuntu 示例）
sudo apt install build-essential libpcre3-dev zlib1g-dev libssl-dev

# 下载并解压源码
curl -O https://nginx.org/download/nginx-1.26.2.tar.gz
tar zxvf nginx-1.26.2.tar.gz
cd nginx-1.26.2

# 配置：--prefix 指定安装目录，--with 开启默认未编译的模块
./configure \
    --prefix=/usr/local/nginx \
    --with-http_ssl_module \
    --with-http_v2_module \
    --with-http_gzip_static_module

# 编译并安装
make
sudo make install
```

- **--prefix**：指定安装根目录，conf、logs、html 等子目录都生成在其下，默认值为 /usr/local/nginx。
- **--with 参数**：开启默认不编译的可选模块（如 SSL 模块）；相对地，--without 参数用于关闭默认编译的模块。
- **三步语义**：configure 探测环境并生成 Makefile，make 完成编译，make install 把产物复制到安装目录。

> [!CAUTION]
> **注意内容**：源码安装版的升级与模块增删都要重新编译，且不会自动注册系统服务，需自行编写 systemd 单元或用 nginx 命令手动管理。除非需要定制模块或官方源不可用，生产环境优先选择包管理器安装。



### 服务管理与常用命令

#### systemctl 服务管理

包管理器安装的 Nginx 会注册为 systemd 服务，日常运维以 systemctl 为主。

```bash
sudo systemctl start nginx     # 启动
sudo systemctl stop nginx      # 停止
sudo systemctl reload nginx    # 平滑重载配置
sudo systemctl restart nginx   # 重启（先停止再启动）
sudo systemctl status nginx    # 查看运行状态
sudo systemctl enable nginx    # 设置开机自启
```

- **reload 与 restart 的区别**：reload 让 master 重新读配置并平滑替换 worker，存量连接不受影响；restart 彻底停止再启动，期间服务中断。
- **标准两步操作**：改完配置先用 nginx -t 校验语法，校验通过再执行 reload。



#### nginx 命令行参数

nginx 二进制自带的参数用于版本查询、配置校验与信号发送，它们在 systemctl 之外同样可用，且是源码安装版唯一的管理入口。

```bash
nginx -v        # 查看版本号
nginx -V        # 查看版本与全部编译参数（configure arguments）
nginx -t        # 测试配置文件语法，不实际生效
nginx -T        # 测试并把合并后的完整配置打印到标准输出
nginx -s stop   # 快速停止
nginx -s quit   # 优雅停止
nginx -s reload # 平滑重载
nginx -s reopen # 重新打开日志文件（用于日志切割）
```

- **-V（大写）** 的输出包含编译时启用的模块列表与安装路径，排查模块缺失问题时必看。
- **-t** 应成为改配置后的肌肉记忆，操作口径见上文「标准两步操作」。
- **-s 的实质**是向 master 进程发送信号：stop 对应 SIGTERM，quit 对应 SIGQUIT，reload 对应 SIGHUP，reopen 对应 SIGUSR1。



#### stop 与 quit 的区别

**stop 与 quit 是语义不同的两种停止方式：stop 是快速停止，quit 是优雅停止。**

- **stop（快速停止）**：立即通知所有 worker 进程终止，不等待存量请求处理完，连接被直接断开；适合紧急下线或服务异常时使用。
- **quit（优雅停止）**：master 通知 worker 停止接受新连接，把已建立连接上的请求处理完再退出；正常维护与下线应优先使用。

> [!WARNING]
> **警告内容**：stop 会硬切断正在处理的请求，对正在上传或下载的用户表现为连接被重置。日常停止一律先试 quit，只有服务异常、需要立即下线的场景才退而使用 stop。



#### reload 的平滑语义

reload 的语义是：**配置热加载，存量请求不受影响**。

1. master 收到重载信号（SIGHUP）后，先校验新配置的语法与有效性。
2. 校验通过则用新配置启动新的 worker 服务新连接；校验失败则放弃本次重载，维持原配置继续运行。
3. 旧 worker 被通知优雅退出：不再接受新连接，把手上的存量请求处理完后再退出。

**reload 失败不会让服务下线，这是它与 restart 最关键的安全差异。**

> reload 的完整原理与热升级的两步信号流程在本主题第 2 章展开，此处先建立直觉：Nginx 的进程模型天生支持新旧并存，reload 与热升级都建立在这个能力之上。



### 安装后的目录结构

#### 配置文件目录

包管理器安装后的主配置目录在 Debian/Ubuntu 系为 /etc/nginx/，其中的关键成员如下。

- **nginx.conf**：主配置文件，整个 Nginx 行为的入口；worker 数、事件模型、http 块等核心指令都在这里，文件末尾通常用 include 指令引入其余配置。
- **conf.d/**：默认被主配置 include 的附加配置目录，日常新增的站点配置（如 default.conf）放在这里即可被加载，避免直接改动主文件。
- **mime.types**：文件扩展名到 MIME 类型的映射表，决定响应头里 Content-Type 的取值，由主配置 include 生效。
- **sites-available/ 与 sites-enabled/**：Debian 系发行版特有的约定目录，前者存放全部站点配置，后者用软链接挑选启用的站点；nginx.org 官方源的安装包不带这两个目录。

最小可用的 http 块骨架（节选自默认配置）：

```nginx
http {
    include       mime.types;
    default_type  application/octet-stream;

    sendfile           on;
    keepalive_timeout  65;

    include /etc/nginx/conf.d/*.conf;
}
```

> [!TIP]
> **建议内容**：改动配置的纪律只有一条：新增站点放 conf.d/，动 nginx.conf 只为调整全局参数；修改后按上文「标准两步操作」执行即可。



#### 站点与日志目录

配置之外的另外两类目录同样需要认识。

- **默认站点目录**：静态文件的默认根目录，Debian/Ubuntu 系为 /usr/share/nginx/html，其中自带一个欢迎页 index.html；真实站点的根目录由配置中的 root 指令指定，默认目录只是示例。
- **日志目录**：/var/log/nginx/，其中 access.log 记录每一条请求的访问明细（来源 IP、时间、请求行、状态码、字节数等），error.log 记录运行错误与告警，是排障的第一现场。
- **PID 文件**：master 进程号记录在 /run/nginx.pid（默认路径），systemd 与 nginx -s 都靠它找到要发信号的进程。

```bash
# 实时查看访问日志，是排查线上问题的第一步
sudo tail -f /var/log/nginx/access.log

# 出现异常时同时盯错误日志
sudo tail -f /var/log/nginx/error.log
```

> [!IMPORTANT]
> **重要内容**：macOS 的 Homebrew 安装路径与 Linux 不同，具体路径见上文 Homebrew 安装小节；查配置前先用 nginx -V 确认安装前缀，不要凭记忆硬背路径。
