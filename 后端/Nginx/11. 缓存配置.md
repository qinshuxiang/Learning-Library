## 缓存配置

### 缓存的三个层次

#### 缓存层次与本章视角

**Web 缓存**：把一份响应内容保存在离用户更近的位置、后续相同请求直接复用而不必再次回源的技术。一次典型的请求链路是 浏览器 → CDN 边缘节点 → Nginx 反向代理 → 上游应用，链路上每一跳都可以存一份副本，由此形成三个缓存层次。

- **浏览器缓存**：浏览器把响应保存在用户本地的磁盘或内存中，再次访问时完全不发请求（强缓存）或只发条件请求（协商缓存），是最靠近用户、单次命中收益最大的一层。
- **Nginx 代理缓存**：反向代理把上游应用的响应保存在 Nginx 所在服务器的磁盘与共享内存中，命中时由 Nginx 直接应答，上游应用不参与计算，是后端工程师可控性最强的一层。
- **CDN 缓存**：CDN 服务商的边缘节点在离用户最近的机房保存响应，适合静态资源与热点内容；其配置在 CDN 控制台完成，不写进 Nginx 配置文件。

> **辨析**：三层缓存的命中顺序是从近到远，浏览器命中就不出网，CDN 命中就不回源，Nginx 命中就不进应用。同一资源可能同时被三层缓存，排查「内容不更新」类问题时必须逐层确认各自的有效期与失效策略，不能只盯着其中一层。

> **速记线索**：浏览器缓存管「这个用户」，代理缓存管「这台 Nginx 后面的所有用户」，CDN 缓存管「这个区域的所有用户」——越靠前影响面越小、命中越快。



#### 强缓存与协商缓存

**强缓存**：浏览器在有效期内直接使用本地副本、完全不发请求的缓存方式，由 Cache-Control 响应头控制。**协商缓存**：浏览器每次发条件请求，由服务端比对资源标识后决定返回完整内容还是 304 的缓存方式，由 ETag 与 Last-Modified 两套头支撑。

- Cache-Control 各值的语义：

  - **max-age=秒数**：强缓存有效期，如 max-age=600 表示 600 秒内浏览器直接用本地副本，不发任何请求。
  - **no-cache**：允许缓存，但每次使用前必须发起协商请求向服务端确认，不是「不缓存」。
  - **no-store**：彻底不缓存，本地与中间代理都不许保存副本。
  - **private**：只允许浏览器缓存，共享缓存层（代理、CDN）不得保存，常用于带用户信息的响应。
  - **public**：允许任何中间层缓存，是最宽泛的授权。

- 协商缓存的完整流程：首次响应携带 ETag（内容指纹）与 Last-Modified（最后修改时间）；浏览器再次请求时通过 If-None-Match 与 If-Modified-Since 回传这两个值；服务端比对一致则返回 304 不带正文，浏览器改用本地副本；比对不一致则返回 200 与新内容。两者并存时通说认为 ETag 优先级更高。

> **辨析**：no-cache 与 no-store 是高频易混点——no-cache 是「存但每次都问」，no-store 才是「一点都不存」；把带用户隐私的响应配成 max-age 长缓存是事故级错误，应使用 private 或 no-store。

```nginx
# 静态资源：强缓存一档
location /static/ {
    expires 7d;
    add_header Cache-Control "public" always;
}

# 带用户态的接口：明确禁止中间层缓存
location /api/me/ {
    add_header Cache-Control "private, no-cache" always;
    proxy_pass http://backend;
}
```



### proxy_cache_path 与缓存存储

#### proxy_cache_path 指令详解

**proxy_cache_path**：定义一块代理缓存区的存储位置与全部参数的指令，是启用代理缓存的第一步；该指令只能出现在 http 块，location 里只能引用它定义出来的缓存区名字。

```nginx
http {
    proxy_cache_path /data/nginx/cache
                     levels=1:2
                     keys_zone=app_cache:10m
                     max_size=1g
                     inactive=60m
                     use_temp_path=off;

    server {
        listen 80;
        server_name api.example.com;
    }
}
```

- **keys_zone**：共享内存区的名字与大小，如 app_cache:10m。zone 中存放缓存键与元数据，Nginx 判断命中与否先查这块内存而不是磁盘；官方文档给出的经验值是 1m 大小的 zone 约能存 8000 个缓存键，可据此估算。
- **max_size**：缓存目录的磁盘上限，超过后由缓存管理进程按淘汰策略删除不常用的条目；不设置则只受磁盘容量约束，生产环境务必显式设置以防写满磁盘。
- **inactive**：一个缓存条目多久没有被访问就清除，与响应内容本身是否过期无关；它描述的是「访问热度」，长时间无人问津的条目据此回收磁盘。
- **levels**：缓存文件的目录层级哈希，如 1:2 表示用缓存键哈希值的末 1 位、再往前 2 位建两级子目录，把海量缓存文件摊开，避免单目录文件数量过大拖垮文件系统。

> **辨析**：max_size 与 inactive 是两个正交的清除条件——前者按「总量超没超」删最冷的条目，后者按「多久没人访问」删失活的条目；一个管磁盘水位，一个管访问热度，同时设置才完整。

> **速记线索**：proxy_cache_path 一句话记忆——「盘上放哪（path 与 levels）、内存记账（keys_zone）、总量封顶（max_size）、冷了就删（inactive）」。



#### 缓存管理进程与条目生命周期

Nginx 用两个内建进程维护缓存区的运转：**cache manager（缓存管理进程）** 长期驻留，负责在超过 max_size 或超过 inactive 时删除条目；**cache loader（缓存加载进程）** 只在启动后的一小段时间内运行一次，把磁盘上已有缓存文件的元数据读回 keys_zone，避免重启后整块缓存被判为不存在。

- 缓存条目的生命周期：请求回源 → 响应写入临时文件 → 移入缓存目录并以缓存键的哈希命名 → 之后每次命中直接读该文件。
- 缓存文件名是缓存键经哈希运算得到的定长字符串，实务中可据此在缓存目录里定位某个 URI 对应的落盘文件。
- 重启 Nginx 不等于清空缓存：只要缓存目录与 zone 配置不变，cache loader 会把旧缓存重新载入，命中情况大体延续。

> **辨析**：「缓存过期」与「缓存被删」是两回事。过期的条目仍留在磁盘上，回源校验后可能继续使用（协商成功）或被替换（内容有变）；被 inactive 删除的条目则彻底消失，下次请求必然 MISS。排查命中率下降时要区分这两种情形。



### 代理缓存的核心指令

#### 在 location 中启用 proxy_cache

**proxy_cache**：在 location 或 server 中指定使用哪块缓存区的指令，值是 proxy_cache_path 里定义的 keys_zone 名；没有配置该指令的地方完全不使用代理缓存。proxy_cache_path 只声明了缓存区，真正开缓存靠这一步。

```nginx
location /api/static-data/ {
    proxy_pass http://backend;
    proxy_cache app_cache;

    proxy_cache_methods GET HEAD;   # 默认值，只有这两个方法参与缓存
}
```

- proxy_cache 可以放在 http、server、location 三级作用域，沿继承链向下生效，location 内覆盖上级同名配置。
- **proxy_cache_methods**：哪些请求方法的响应参与缓存，默认为 GET 与 HEAD，通说认为不建议把 POST 纳入缓存。
- 想让某 location 明确不用缓存，不需要删配置，写 proxy_cache off 即可显式关闭。

> **辨析**：proxy_cache_path 与 proxy_cache 是「定义」与「引用」的关系——前者只能在 http 块出现一次或多次，后者在 location 里反复引用；缓存区定义了但没有任何 location 引用，等于一块空置的仓库。



#### proxy_cache_valid 的状态码语义

**proxy_cache_valid**：按响应状态码设定缓存时长的指令。写法 proxy_cache_valid 200 301 10m 表示只对状态码为 200 与 301 的响应缓存 10 分钟，未列出的状态码一律不缓存，这是该指令最容易误读的地方。

- proxy_cache_valid 10m（只写时间不写状态码）：通说认为此时只有 200、301、302 三种响应会被缓存。
- proxy_cache_valid any 1m：用 any 兜底，其余所有状态码统一缓存 1 分钟。
- 404 之类错误响应是否缓存需要显式决定：短时间缓存 404 可以缓解恶意扫描穿透到上游，而 5xx 一类服务端错误不应长期缓存。

```nginx
proxy_cache_valid 200 301 10m;
proxy_cache_valid 404      1m;
proxy_cache_valid any      1m;
```

> **辨析**：proxy_cache_valid 只在**上游响应没有携带缓存相关头**时生效。上游返回了 Cache-Control 或 Expires 时，这些头的语义优先于 proxy_cache_valid；如果确要按 Nginx 侧的时间走，可用 proxy_ignore_headers Cache-Control Expires 屏蔽。这是「明明配了 10 分钟却观察到更长的缓存时间」的高频原因。



#### proxy_cache_key 的默认值与自定义

**proxy_cache_key**：决定「两个请求是否算同一个缓存条目」的键值表达式，默认值为 $scheme$proxy_host$request_uri，即协议、代理侧主机名、请求 URI 三者拼接的字符串。

- 默认键的含义：同一 URI 带不同查询参数会生成不同条目；不希望查询参数参与区分时必须自定义键。
- 自定义示例中常用 $host 替代 $proxy_host：$host 是请求行里的 Host 头对应的站点名，多站点共用一块缓存区时用它可避免两个域名互相串缓存。
- 键中不要随手加入 $http_cookie、$http_authorization 这类用户相关变量——那样会把公共缓存切成人均一份，命中率崩塌且变相缓存用户数据。

```nginx
location /api/ {
    proxy_cache app_cache;
    proxy_cache_key "$scheme$host$request_uri";
}
```

> **辨析**：$proxy_host 与 $host 的差别——$proxy_host 是 proxy_pass 指向的、配置里写的主机与端口，$host 是请求自带的 Host（或匹配的 server_name）。默认值用 $proxy_host 强调「对上游的视角」；缓存区被多个 server 共用时，自定义键换用 $host 是通行的修正做法。



### 缓存命中状态的观测与调试

#### $upstream_cache_status 的取值

**$upstream_cache_status**：记录本次请求缓存处理结果的内置变量，是判断代理缓存是否生效的第一现场；它不出现在默认日志与响应头里，必须主动配置才能观察到。

- **MISS**：缓存中没有可用条目，请求转发给上游，响应随后写入缓存。
- **HIT**：命中缓存，直接以缓存条目应答，上游完全不参与。
- **EXPIRED**：条目存在但已过有效期，回源校验或更新后应答。
- **STALE**：条目已过期，且因回源失败等情形按 proxy_cache_use_stale 的配置使用了过期内容应急。
- **UPDATING**：条目过期且正有其他请求在回源更新，当前请求按配置返回旧内容，避免缓存击穿。
- **BYPASS**：命中了 proxy_cache_bypass 的条件，本次请求完全绕过缓存走上游。
- **REVALIDATED**：条目过期后向上游发条件请求（If-None-Match 或 If-Modified-Since），上游确认内容未变，继续使用本地副本。

> **速记线索**：七个取值按「结果」记忆——没存过是 MISS，存了就是 HIT，过期是 EXPIRED，过期后确认没变是 REVALIDATED，应急用旧货是 STALE 与 UPDATING，主动绕开是 BYPASS。



#### 用响应头与日志观察命中状态

观察命中状态有两条配置途径：把变量加进响应头方便用浏览器开发者工具逐条查看，或写进访问日志方便按量统计命中率；两者通常同时配置。

```nginx
log_format cache_watch '$remote_addr [$time_local] "$request" '
                       '$status cache=$upstream_cache_status '
                       'rt=$request_time urt=$upstream_response_time';

server {
    access_log /var/log/nginx/cache_watch.log cache_watch;

    location /api/ {
        proxy_cache app_cache;
        add_header X-Cache-Status $upstream_cache_status always;
        proxy_pass http://backend;
    }
}
```

- 响应头方式：打开开发者工具的网络面板即可看到每个请求是 MISS 还是 HIT，适合单条排查。
- 日志方式：对 cache=HIT 的行数做占比统计即可得到命中率，适合观察整体趋势与发布前后的变化。
- 配合 rt 与 urt 两个耗时变量，还能对比命中与未命中时的响应时间差，量化缓存收益。

> [!NOTE]
> **提醒内容**：add_header 必须带 always 参数，否则 304 这类协商缓存常见的响应不会携带 X-Cache-Status 头，恰好漏掉的又是最需要观察的协商场景。



### 缓存粒度的精细控制

#### proxy_cache_bypass 与 proxy_no_cache

**proxy_cache_bypass**：条件成立时不读缓存、直接回源的指令。**proxy_no_cache**：条件成立时不把响应写入缓存的指令。两者都接受一组字符串参数，只要有任一参数非空且不等于字符串 0 就触发，常成对配置同一组条件以实现「既不读也不写」。

```nginx
location /api/ {
    proxy_cache app_cache;
    # 请求头 X-No-Cache 非空，或 URL 带 ?refresh=1 时，跳过缓存
    proxy_cache_bypass $http_x_no_cache $arg_refresh;
    proxy_no_cache     $http_x_no_cache $arg_refresh;
    proxy_pass http://backend;
}
```

- 典型用途一：管理端点、个性化接口整体不读不写，配置常量参数即可触发。
- 典型用途二：运维调试时用约定的请求头或查询参数对单条请求强制回源，不影响其他用户的缓存。
- 触发后回源拿到的新响应，若 proxy_no_cache 条件不再成立，仍会按正常流程写入并替换同键旧条目。

> **辨析**：bypass 只管「读」，no_cache 只管「写」——只配 bypass 的话，回源结果仍会被写进缓存；只配 no_cache 的话，请求仍会先读到旧缓存。两者的取舍是：想让回源结果刷新缓存就只配 bypass，想让这次响应完全不进缓存就成对配置。



#### 默认不缓存的响应行为

Nginx 对代理缓存有几条源码内置的默认规则，无需配置即生效；官方文档在 proxy_cache 的说明中列出了不缓存的条件，做缓存设计时必须先知道这些例外。

- 响应带有 **Set-Cookie** 头：默认不缓存——会话相关内容通常不该被多个用户共享；确有把握要缓存时用 proxy_ignore_headers Set-Cookie 关闭该判定，但必须想清楚串会话的后果。
- 请求带有 **Authorization** 头：默认不缓存，防止把某用户的凭证态响应返回给其他用户。
- 请求方法不在 proxy_cache_methods 列表内（默认仅 GET 与 HEAD）：不缓存。
- 上游响应的 Cache-Control 值为 no-cache、no-store、private，或 Vary 值为星号：默认不缓存。

> [!IMPORTANT]
> **重要内容**：这些默认规则意味着「配置了 proxy_cache 但接口永远 MISS」未必是配置写错，先检查上游是否在响应里带了 Set-Cookie 或 no-store 一类头——用 curl 观察完整响应头是定位此类问题的第一步。



### 缓存的失效与清理

#### 开源版没有内置的缓存清理指令

开源版 Nginx 没有内置的缓存清理指令：想主动删除或失效某一条缓存，官方没有提供类似 PURGE 的请求方法或指令。商业版 Nginx Plus 提供 proxy_cache_purge 指令；开源版的对应能力靠第三方模块 ngx_cache_purge 或运维手段实现。

- 开源版可用的原生手段只有被动等待：等条目自然过期、等 inactive 回收，或整体重建缓存目录。
- ngx_cache_purge 模块以额外 URI 的方式提供按 key 精确清除的能力，需要重新编译 Nginx 才能引入，属于运维成本较高的路线。
- 是否引入第三方模块要权衡：多数团队最终选择下面列出的应用层替代做法，而不是为清缓存维护一套自编译产物。

> [!WARNING]
> **警告内容**：不要在生产环境高频执行删除缓存目录下文件的脚本——缓存键还在共享内存里、磁盘文件却没了，中间状态可能引发异常回源风暴；确要重建缓存，应停机或切流后整体清空再恢复，而不是边跑边删。



#### 实务中的替代清理做法

不引入第三方模块的前提下，实务中主要有三种替代做法，按改动成本从小到大排列。

- **版本号查询参数**：页面引用资源时带上 v 参数，如 app.js?v=20260907，发版时换新版本号；新参数生成新缓存键，旧条目自然失活，适合静态资源发布。
- **bypass 开关强制刷新**：约定一个查询参数或请求头触发 proxy_cache_bypass，单条请求强制回源；回源到的新响应在键相同的情况下会替换旧条目，等于完成了一次单键刷新。
- **整体重建缓存目录**：切流或低峰期停止 Nginx，清空 proxy_cache_path 指向的目录后重启；一次性放弃全部缓存，属于发布事故或数据错误时的兜底手段。

```bash
# 兜底手段示意：切流停服后整体清空再启动，切勿在正常服务中直接执行
nginx -s quit
rm -rf /data/nginx/cache/*
nginx
```

> **速记线索**：清理思路一句话——「能换键就别删条目」（版本号参数），「能单点刷就别全量清」（bypass 开关），「重建目录永远是最后手段」。



### 浏览器缓存与静态资源策略

#### expires 指令

**expires**：由 Nginx 直接为响应生成浏览器缓存期限的指令，等价于替你同时写好 Expires 与 Cache-Control 的 max-age 两套头，是配置浏览器缓存最常用的一条指令。

```nginx
location /static/ {
    expires 7d;   # 响应头效果：Expires 为一周后，Cache-Control: max-age=604800
}
```

- expires 后接正数时间（如 7d、1y）：生成 Cache-Control 的 max-age 等长有效期，属于强缓存。
- expires -1 或 epoch：生成立即过期的头，配合协商缓存使用，每次都回源确认。
- expires off（默认）：不修改上游或文件系统给出的缓存头。

> **辨析**：expires 与 add_header Cache-Control 都能产生 max-age，同时配置时响应可能出现两条 max-age 语义的头，浏览器行为取最保守值；同一 location 只用一种方式，是避免歧义的通行做法。



#### 文件名 hash 与长效缓存

业界通行的静态资源缓存策略：构建工具在文件名中嵌入内容哈希（如 app.8f3a9c.js），内容一变文件名即变；对这类文件配置最长档的强缓存，对不带 hash 的入口 HTML 配置 no-cache 每次协商。该约定与第 5 章静态资源服务的部署内容相呼应。

- 带 hash 的构建产物：文件名即版本，可放心配置 expires 1y 一类的长效缓存，因为内容变了 URL 必然变了。
- 入口 HTML 与路由清单：文件名固定、内容常变，必须 no-cache 走协商，保证用户每次拿到最新的资源引用。
- 两者配合的效果：绝大多数请求命中浏览器本地缓存不发请求，发布后只有入口页需要回源。

```nginx
# 带内容 hash 的构建产物：长效强缓存
location ~* \.(?:js|css|png|jpg|jpeg|gif|svg|woff2)$ {
    expires 1y;
    add_header Cache-Control "public, immutable" always;
}

# 入口与不带 hash 的文件：每次协商
location / {
    try_files $uri $uri/ /index.html;
    add_header Cache-Control "no-cache" always;
}
```

> [!TIP]
> **建议内容**：immutable 是 Cache-Control 的扩展值，告知浏览器有效期内连协商请求都不必发（针对用户刷新页面的场景也生效）；只对确定带 hash 命名的资源使用，配错对象会让更新长时间不可见。



### 缓存与负载均衡的交互

#### 多机独立缓存的不一致问题

**多机独立缓存不一致**：负载均衡把请求分发到多台 Nginx（或多个各自带缓存的节点）时，每台的磁盘缓存互相独立，同一资源在各节点上的缓存版本与失效时间可能不同，用户在两次请求之间会看到新旧内容来回切换；上游发布新版本后，各节点失步的现象会更明显。

- 现象特征：同一天内部分用户看到新版页面、部分用户看到旧版页面，且同一个用户时而新版时而旧版，与命中到哪台节点相关。
- 根本原因：缓存条目存在于各自的本地磁盘，键相同但内容快照与写入时刻互不同步。
- 该问题在「多台 Nginx 代理缓存 + 上游多实例」的架构中天然存在，扩容节点越多、随机分发越彻底，现象越突出。

> **辨析**：这与负载均衡本身无关——不配缓存的多机分发不会有一致性问题；引入代理缓存后，一致性问题的实质是「缓存副本有几份、由谁统一失效」。



#### 一致性路由与共享存储思路

解决思路有四类，从改路由规则到改存储位置，概念上层层递进。

- **一致性路由**：在 upstream 中用 hash 指令按缓存键的组成部分做一致性哈希，让同一请求总落到同一台节点，天然命中同一份缓存，是多机代理缓存最常用的解法。
- **共享存储**：把缓存目录放到各节点共用的存储层，读写同一份条目；实务中因磁盘 IO 与锁开销，采用面较窄，多用于缓存体量小的场景。
- **收紧有效期**：接受短暂不一致，缩短缓存时长与 inactive，发布后按前述方法主动刷新热点键，用命中率换一致性。
- **上移缓存层**：在 Nginx 之上再设一层统一的专用缓存（如独立的缓存集群），各 Nginx 节点只做转发不做缓存，一致性交由单一层保证。

```nginx
upstream backend {
    # 按请求 URI 做一致性哈希：同一 URI 稳定落到同一台节点
    hash $request_uri consistent;
    server 10.0.0.1;
    server 10.0.0.2;
}
```

> [!NOTE]
> **提醒内容**：一致性哈希路由的代价是负载可能因热点 URI 而倾斜，且增删节点时哈希环重排会带来一轮集中的缓存 MISS；两种副作用都要在容量规划时一并评估。
