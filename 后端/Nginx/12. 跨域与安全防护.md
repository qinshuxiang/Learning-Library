## 跨域与安全防护

### 同源策略

#### 同源的定义与三元组判定

**同源策略**：浏览器最核心的安全机制，规定页面中的脚本只能读写与当前页面**同源**的资源。**同源**：两个 URL 的**协议、域名、端口**三元组完全相同，三者缺一不可，任何一项不同即为**跨源**。

- 协议不同即跨源：http://a.com 与 https://a.com 不是同源。
- 域名不同即跨源：a.com 与 b.com 不同源；a.com 与 sub.a.com 也不同源，子域不豁免。
- 端口不同即跨源：http://a.com:80 与 http://a.com:8080 不同源。
- 判定对象是「源」而不是「路径」：同一站点下 /page/a 与 /page/b 路径不同但同源。

> **辨析**：同源策略限制的是脚本对「响应内容」的读取与对跨源文档的访问，而不是笼统地禁止一切跨源请求——跨源的图片、样式、脚本标签照常加载，被拦下的是脚本拿到跨源响应内容的能力。CORS 正是在这条限制上「依法开洞」的标准机制。



#### 同源策略的作用范围

**单方面施加**：同源策略是浏览器单方面对页面脚本施加的限制，服务端之间不受约束——后端用 HTTP 客户端调用另一台服务器的接口、命令行 curl 请求任意站点，都不存在跨域问题。

- 受约束的场景：脚本通过 fetch 或 XMLHttpRequest 读取跨源响应、脚本访问跨源 iframe 的 DOM、脚本读写跨源的存储。
- 不受约束的场景：img、script、link 等标签的跨源加载（这正是一切 CDN 资源能用、图片被盗链的原因）、服务端之间的相互调用、命令行工具发起的请求。
- 排查含义：跨域报错只在浏览器控制台出现，服务端日志里请求往往正常到达甚至处理成功，这是排查跨域问题时最反直觉的一点。

> **辨析**：「浏览器报 CORS 错误」通常不等于「请求没有到达服务端」——多数跨源请求实际已发出并可能产生副作用，浏览器拦截的是脚本对响应的读取。因此不能把 CORS 当作安全边界来防伪造请求，它的本质是授权读取的协商机制。



### CORS 跨源资源共享

#### CORS 的定义与授权模型

**CORS**：跨源资源共享，由 W3C 制定的标准机制——跨源请求发出后，服务端在响应中携带一组 Access-Control 系列响应头，声明「哪些源被允许读取本响应」，浏览器校验这些头后才把响应交给脚本。

- 核心响应头一组：Access-Control-Allow-Origin（允许的源）、Access-Control-Allow-Methods（允许的方法）、Access-Control-Allow-Headers（允许的请求头）、Access-Control-Allow-Credentials（是否允许携带凭证）、Access-Control-Max-Age（预检结果的缓存秒数）。
- 授权的表达方是服务端（或其代理层），判断方是浏览器：响应头没有正确声明时，浏览器拦截读取并在控制台报错。
- CORS 是对同源策略的放宽通道，而不是又一层拦截墙；没有 CORS 时回到同源策略的默认拦截，有了 CORS 才允许跨源读取。

> **速记线索**：五个核心响应头按「源、方法、头、凭证、有效期」五个问题记忆——允许谁读、允许什么方法、允许带什么头、允不允许带 Cookie、这份授权记多久。



#### 简单请求与预检请求

**简单请求**：满足全部安全条件、可以直接发出的跨源请求。**预检请求**：不满足条件的跨源请求，浏览器必须先发一个 OPTIONS 请求询问服务端是否允许，得到肯定答复后才发真正的请求；两者是 CORS 的基本分类。

- 简单请求的判定条件（三条同时满足）：

  1. 方法限于 GET、HEAD、POST 三种。
  2. 不携带自定义请求头，只允许 CORS 规定的安全列表内的头。
  3. Content-Type 仅限于 text/plain、application/x-www-form-urlencoded、multipart/form-data 三种。

- 不满足任一条即触发预检：浏览器先发 OPTIONS，带上 Access-Control-Request-Method 声明真实请求的方法、Access-Control-Request-Headers 声明真实请求要带的头。
- 服务端对预检的应答需要包含上述 Allow 系列头，并用 Access-Control-Max-Age 告知浏览器可把预检结果缓存多少秒，避免每次请求都先问一遍。
- 现代接口普遍携带 Content-Type: application/json 与 Authorization 头，因此预检是日常开发的常态而非例外。

> **辨析**：预检请求是浏览器自动发出的，代码里没有写它；它只带头部不带业务数据，服务端必须正确应答 OPTIONS 而不能把它当业务请求处理——预检失败时真实请求根本不会发出，表现为控制台的跨域报错。



### Nginx 配置 CORS

#### 标准响应头的写法

在 Nginx 的 location 中用 add_header 添加 Access-Control 系列响应头，是配置 CORS 的标准写法；Allow-Origin 可写死指定的域，也可回显请求头中的 $http_origin 再配合校验。

```nginx
location /api/ {
    add_header Access-Control-Allow-Origin "https://app.example.com" always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;
    add_header Access-Control-Allow-Credentials "true" always;
    add_header Access-Control-Max-Age 86400 always;

    proxy_pass http://backend;
}
```

- 指定域（如 https://app.example.com）是最简单安全的方式，适合源固定的场景。
- 多个域名时无法在一个头里写列表，通说做法是用 map 把 $http_origin 映射为允许列表中的合法源，再写进 Allow-Origin。
- Access-Control-Allow-Headers 必须覆盖前端实际会发送的自定义头，漏写的头在预检阶段就会被拒绝。

> [!WARNING]
> **警告内容**：直接写 add_header Access-Control-Allow-Origin $http_origin 等于放行任意来源网站读取响应，若同时开启 Allow-Credentials，任意第三方页面都能以用户身份读取接口数据；回显 $http_origin 必须先用 map 建立来源白名单，只对白名单内的源回显。



#### 预检 OPTIONS 的放行

放行预检的惯用写法是在 location 内用 if 判断请求方法并直接返回 204：预检请求不需要代理到上游，Nginx 直接带上 CORS 头应答即可。

```nginx
location /api/ {
    add_header Access-Control-Allow-Origin "https://app.example.com" always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;

    if ($request_method = OPTIONS) {
        return 204;
    }

    proxy_pass http://backend;
}
```

- return 204 返回无正文的成功响应，是预检应答的通行选择；return 204 需写在该 location 内、proxy_pass 之前。
- if 与 return 的组合是 Nginx 中被公认可靠的写法，常被讨论的 if 配置陷阱主要出现在 if 内改写内容处理的场景，此处不涉及。
- 预检没被放行、被 proxy_pass 转给后端而后端又不应答 OPTIONS 时，预检超时或报错，真实请求永不发出。

> **辨析**：预检放行块与 CORS 头必须在同一个生效的 location 里——204 响应同样要携带 Allow 系列头，浏览器校验的是预检响应上的头；把头加在另一个 location 而预检 204 里没有头，等于白配。



#### add_header 的 always 参数

add_header 默认只对一组成功类响应码生效——200、201、204、206、301、302、303、304、307、308；4xx 与 5xx 响应默认不会携带 add_header 添加的头，加上 always 参数后才对所有响应码生效。

- 对 CORS 的意义：预检通过但真实请求被上游拒绝（如 401、500）时，不带 always 的 Allow-Origin 头会从错误响应上消失，浏览器把它一并报成跨域错误，掩盖了真实的服务端错误。
- 对安全头的意义：X-Frame-Options 一类防护头若不带 always，恰好在被攻击者诱导产生的错误响应上失效，防护形同虚设。
- 通说结论：CORS 头与安全响应头相关的 add_header 一律加 always，这是排查「响应头时有时无」问题前就该养成的习惯。

> [!IMPORTANT]
> **重要内容**：排查跨域问题时先用命令行看完整响应头，而不是只看浏览器报错——curl 能直接暴露「头缺失」与「头重复」两类问题，后者是下一节的高频坑。

```bash
# 模拟一个跨源请求并查看响应头，确认 CORS 头是否存在、是否重复
curl -sD - -o /dev/null https://api.example.com/api/user \
  -H "Origin: https://app.example.com"
```



#### 与后端重复设置响应头的坑

**重复 CORS 头**：Nginx 与后端应用框架同时配置 CORS 时，同一响应会携带两个 Access-Control-Allow-Origin 头，浏览器视为非法响应、按跨域失败处理——明明「配置了两道保险」，结果是一道都不过。

- 现象确认：用 curl 看响应头，能看到两行 Access-Control-Allow-Origin；浏览器控制台的报错只说跨域失败，不会指出「重复」这个真实原因。
- 原则：CORS 头只在其中一层设置——要么全在 Nginx，要么全在应用层，二选一；团队按「谁负责网关谁负责 CORS」的分工统一即可。
- 迁移方向：生产环境若采用下一节的同源部署，跨域需求从根源消失，两层的 CORS 配置应一并清理，避免残留头继续生效。

> [!NOTE]
> **提醒内容**：改造或排查线上接口时，先 curl 确认当前响应头的现状再决定在哪层改——很多接口在历史演进中早已有后端框架设置的头，网关层再叠一层就是重复的由来。



### 反向代理规避跨域

#### 生产环境的同源部署

**同源部署**：把前端静态资源与后端 API 挂在同一个域名下，由 Nginx 把带前缀的 API 请求反向代理到后端服务；页面与接口对浏览器而言天然同源，CORS 问题从根源上消失。通说认为这是生产环境的首选方案，CORS 头方案留给确需跨域调用的第三方场景。

```nginx
server {
    listen 80;
    server_name app.example.com;

    root /var/www/app/dist;

    # 前端单页应用：静态资源与路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 同源之下的 API：反向代理到后端
    location /api/ {
        proxy_pass http://backend;
        proxy_set_header Host $host;
    }
}
```

- 前提约定：前端所有请求统一走 /api 前缀，前缀由 Nginx 负责摘除或保留后转发给后端。
- 收益：无需任何 Access-Control 头与预检逻辑，Cookie 属于第一方上下文，鉴权链路简单。
- 该方案把「跨域」转化为一个纯粹的部署与路由问题，这也是它成为通说的根本原因。

> **辨析**：同源部署与 CORS 头不是互斥的替代关系——自家站点用同源部署不留跨域，同时网关给第三方合作方按白名单开 CORS 头，是两者并存的常见形态；要避免的是同一接口对同一来源既同源又跨源混用。



#### 开发环境的代理转发

开发环境下前端 dev server 与后端服务通常分属两个端口（如 3000 与 8080），端口不同即跨源；通说做法是让脚手架内置的代理把 /api 请求转发到后端，浏览器只见 dev server 自己的源，与生产的 Nginx 反代是同一思想。

```js
// vite.config.js：开发代理示例（与生产 Nginx 反代同一思路）
export default {
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true,
      },
    },
  },
};
```

- 浏览器请求的是 http://localhost:3000/api/user（同源），转发动作发生在 Node 层，服务端到服务端不受同源策略约束。
- changeOrigin 的作用是把转发请求的 Host 头改写为目标服务，适配后端按域名识别虚拟主机的场景。
- 开发代理与生产反代保持相同的前缀约定，前后端代码无需感知环境差异，这是「约定前缀」的另一半价值。

> **速记线索**：跨域的三条处理路线按场景对号——生产同源部署（首选）、开发脚手架代理（对齐生产）、确需跨域才在网关配 CORS 头（兜底给第三方）。



### 安全响应头基线

#### X-Frame-Options 与点击劫持防护

**X-Frame-Options**：控制页面能否被 iframe 嵌入的响应头，用于缓解**点击劫持**——攻击者把目标页面透明地嵌在自己页面里，诱骗用户在不知情的情况下点击操作目标页面。

- **DENY**：禁止被任何页面（包括同源页面）以 iframe 嵌入。
- **SAMEORIGIN**：仅允许同源页面嵌入，是最常用的折中值。

```nginx
add_header X-Frame-Options "SAMEORIGIN" always;
```

> **辨析**：管理后台、支付与账户设置类页面最需要这个头；营销页若确有被合作方嵌入的需求，用 SAMEORIGIN 之外的 CSP frame-ancestors 指令表达白名单，比直接关掉防护更稳妥。



#### X-Content-Type-Options 与 MIME 嗅探

**X-Content-Type-Options: nosniff**：禁止浏览器对响应做 MIME 嗅探的响应头，要求严格按 Content-Type 头解释响应内容，不得自行猜测并改判类型。

- 关闭嗅探后，声明为 text/plain 或图片类型的响应不会再被浏览器当作脚本或样式执行，缓解「把用户上传的文件喂给浏览器导致执行」一类攻击。
- 该头同时对脚本与样式加载生效：Content-Type 标错类型的外部脚本会被浏览器拒绝执行，也倒逼资源类型声明正确。

```nginx
add_header X-Content-Type-Options "nosniff" always;
```

> **辨析**：MIME 嗅探本是浏览器对历史遗留错标内容的兼容行为，兼容能力被攻击面利用后，业界共识是显式关闭；启用后要连带检查静态资源的 Content-Type 是否标注正确，否则正常脚本可能加载失败。



#### Content-Security-Policy 与 Referrer-Policy

**Content-Security-Policy**：内容安全策略，通过响应头下发一组资源加载白名单规则，限定页面能从哪些来源加载脚本、样式、图片等，是缓解 XSS 的纵深防线；与前端 CSP 知识直接呼应，网关层负责把头统一下发。**Referrer-Policy**：控制浏览器跳转与请求时携带多少来源信息的响应头，现代默认值为 strict-origin-when-cross-origin。

- CSP 的常用起点是 default-src 'self'，再按站点实际的第三方资源来源逐项放开；白名单之外的内联脚本与 eval 默认被禁止。
- Referrer-Policy 的 strict-origin-when-cross-origin 表示同源请求带完整路径、跨源只带源、降级为 HTTP 时不带，兼顾统计与隐私。
- 这类站点级统一头放在 server 块全局下发一次即可，无需在每个 location 重复。

```nginx
server {
    listen 80;
    server_name app.example.com;

    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    # CSP 示例：按站点实际引用的第三方资源定制后再上线
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'" always;
}
```

> [!IMPORTANT]
> **重要内容**：这一组安全头的 add_header 全部要带 always，参数机理与不带 always 的后果见本章「add_header 的 always 参数」一节。



### 版本与信息隐藏

#### server_tokens 指令

**server_tokens off**：关闭 Nginx 在响应头 Server 字段与默认错误页中展示版本号的指令，属于成本最低的信息隐藏手段——版本号本身不是漏洞，但它让攻击者可以精确检索对应版本的已知漏洞，缩小侦察成本。

- 默认行为：响应头形如 Server: nginx/1.24.0，默认错误页底部同样带版本号与 Nginx 签名。
- 配置 off 后：Server 字段仍显示 nginx 一词，只隐藏版本号；默认错误页的签名同步简化。
- 该指令只能出现在 http、server、location 层级，通常在 http 块全局配置一次。

```nginx
http {
    server_tokens off;
}
```

> [!NOTE]
> **提醒内容**：off 之后 Server 头仍保留 nginx 字样，要做到连名称都更换需修改源码重新编译，实务中普遍认为收益有限、一般不做；隐藏版本号的定位是「提高侦察门槛」，不是安全边界。



#### 自定义错误页

**error_page**：把指定状态码的响应重定向到自定义错误页面的指令；自定义错误页既改善体验，也顺带消除默认错误页带版本号签名、暴露技术栈细节的信息泄露。

```nginx
server {
    listen 80;
    server_name app.example.com;

    error_page 404 /error/404.html;
    error_page 500 502 503 504 /error/50x.html;

    location = /error/50x.html {
        root /usr/share/nginx/html;
        internal;
    }
}
```

- error_page 后接状态码列表与内部 URI，可用一条指令聚合多个状态码到同一页面。
- internal 限定该 URI 只能由内部跳转触达，外部直接请求错误页地址会被拒绝，防止错误页本身被探测。
- 502、504 一类网关错误页是用户最常撞见的页面，务必定制并做无依赖的纯静态实现——上游故障时页面里的外部资源同样可能加载不出来。

> **速记线索**：信息隐藏两件事一句话记忆——「对外少说一句」（server_tokens off），「报错体面一点」（error_page 自定义）。



### 路径与目录安全

#### URI 规范化与目录穿越

**URI 规范化**：Nginx 在做 location 匹配与文件映射前，先对请求 URI 做的整理动作——合并连续斜杠（merge_slashes 指令默认 on）、解析点段（./ 与 ../）。**目录穿越**：攻击者用 ../ 构造路径试图读出网站根目录之外文件的攻击手法；Nginx 对它的防护来自「先规范化、再拼接、受 root 与 alias 约束」的默认处理链，而不是靠拦截字符串。

- 默认链路下，/static/../../etc/passwd 这类请求会先被规范化处理，最终参与匹配与文件映射的 URI 已不含点段，无法越出既定根目录。
- merge_slashes on 时 //a//b 被合并为 /a/b；关闭合并会让同一资源出现多个 URI 形态，也给规则匹配留下绕过空间，通说建议保持默认开启。
- 值得警惕的是绕过规范化链路的组合场景：把未经规范化处理的原始 URI 透传给解析行为不同的后端时，两侧对同一路径的理解可能出现分歧；此类组合需要单独评估。

> [!CAUTION]
> **注意内容**：不要依赖应用层的路径黑名单来补 Nginx 的路径安全——规范化发生在匹配之前、黑名单匹配发生在其后，思路不同必然留下缝隙；正确的做法是保持默认规范化开启、用精确的前缀与正则 location 划定可访问范围。



#### alias 与 root 的配置风险

**root**：把 location 匹配后的完整 URI 拼接到 root 值之后得到文件路径。**alias**：用 alias 值替换掉 location 匹配到的那段前缀，再拼接剩余部分。两者拼接规则不同，location 与 alias 的斜杠不严格对齐时，可能拼出预期目录之外的路径，造成越界读取——这是实务中反复出现的经典配置坑。

```nginx
# root 拼接：最终路径 = root + 完整 URI
location /static/ {
    root /var/www;          # /static/a.css -> /var/www/static/a.css
}

# alias 替换：最终路径 = alias + 去掉前缀的剩余部分
location /static/ {
    alias /var/www/assets/; # /static/a.css -> /var/www/assets/a.css
}
```

- root 的语义是「换根」：URI 原样附加在后，root 与 location 的斜杠是否对齐不影响结果。
- alias 的语义是「换段」：前缀被整体替换，location 末尾带不带斜杠必须与 alias 末尾严格对齐，多一个少一个字符都会改变拼接结果。
- 若写成 location /static 配 alias /var/www/assets/ 这类不对齐组合，构造 /static../secret 一类的 URI 时，规范化后的剩余部分与 alias 拼接可能落在预期目录之外；实务中的结论是斜杠严格成对、并用真实请求逐一验证。

> [!WARNING]
> **警告内容**：alias 指向的目录如果比预期更宽（例如把 alias 指到数据根目录而不是资源子目录），等于把更大范围的文件开放给了 URI 映射；alias 的目标目录应当收窄到确需对外服务的最小范围，并避免其父目录存放敏感文件。



#### autoindex 与目录列表暴露

**autoindex**：目录没有索引文件时返回该目录文件列表的指令，默认值为 off；开启后浏览器访问目录 URL 能直接看到目录内全部文件与子目录清单。

- 适用场景仅限公开的下载镜像、日志归档等确需目录浏览的场合，并建议配合开启展示文件时间与大小。
- 风险：目录列表会把未做链接的文件、备份文件、临时文件一并暴露，攻击者据此枚举目标；上传目录、配置目录、备份目录绝不允许开启。
- 检查习惯：对全站 grep 配置中的 autoindex，确认每一处开启都有明确理由与明确的目录范围。

```nginx
location /downloads/ {
    autoindex on;             # 仅限公开下载目录
    autoindex_exact_size off; # 以人类可读单位展示大小
}
```

> **辨析**：autoindex 暴露的是「目录里有什么」，而目录穿越暴露的是「目录外有什么」——前者是主动开了门，后者是墙上有缝；两者都归入路径与目录安全，但成因与修法完全不同。



### 基本认证与访问控制

#### htpasswd 密码文件

**auth_basic_user_file**：存放用户名与密码哈希的明文路径指令，文件本身用 htpasswd 工具生成与追加；这是 HTTP 基本认证的账号数据来源。

```bash
# 首次创建密码文件并添加用户 alice（-c 会覆盖已有文件，仅首次使用）
htpasswd -c /etc/nginx/.htpasswd alice

# 非交互式追加用户 bob，-b 直接在命令行给密码，-B 选用 bcrypt 哈希
htpasswd -B /etc/nginx/.htpasswd bob 'S3cret!'

# 收紧权限：属主可读写、组可读，其他用户不可见
chmod 640 /etc/nginx/.htpasswd
chown root:nginx /etc/nginx/.htpasswd
```

- htpasswd 生成的每行格式为 用户名半角冒号密码哈希，哈希算法常用 bcrypt（-B）或 apr1；通说建议优先 bcrypt。
- 密码文件不要放在站点可访问的目录之下，惯例放在 /etc/nginx 之类的配置目录并收紧文件权限。
- -b 把密码留在 shell 历史与进程列表里，仅适合脚本化场景；人工操作时省略 -b 用交互式输入。

> [!NOTE]
> **提醒内容**：htpasswd 是 apache2-utils 一类系统包自带的工具，个别环境需要先安装；不想引入依赖时也可用 openssl passwd 一类方式生成兼容哈希后手工拼行，但格式必须与所选算法一致。



#### auth_basic 指令

**auth_basic**：开启 HTTP 基本认证的指令，参数为弹窗提示语或表示关闭的 off；与 auth_basic_user_file 成对使用，缺少密码文件时认证必然失败。

```nginx
location /admin/ {
    auth_basic "Admin Area";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
```

- 认证未通过时 Nginx 返回 401 并携带 WWW-Authenticate 头，浏览器据此弹出用户名密码输入框。
- auth_basic 沿作用域继承，子 location 中写 auth_basic off 可对继承到的认证局部豁免。
- 基本认证的凭据以 Base64 编码随每个请求明文携带，本身不加密，必须与 HTTPS 配合使用，这是通说层面的硬前提。

> **辨析**：基本认证是「环境级」的粗粒度门槛，适合内部工具、灰度验证、临时封测入口；它不是替代业务登录体系的方案，账号与权限管理都不宜建在 htpasswd 之上。



#### 与 allow 与 deny 的组合

**allow 与 deny**：按客户端 IP 做访问控制的指令，与 auth_basic 属于两个独立的门——前者基于网络位置，后者基于账号凭据；组合使用可实现「先过 IP 白名单、再过密码」的双层防护。

```nginx
location /admin/ {
    allow 192.168.1.0/24;   # 只放行内网网段
    deny  all;              # 其余一律拒绝
    auth_basic "Admin Area";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
```

- allow 与 deny 按书写顺序逐条匹配，命中一条即停止；常见写法是先列放行网段，末尾 deny all 收口。
- 默认满足模式下，IP 控制与基本认证必须同时通过，两层互为冗余，一层失守还有另一层。
- allow 与 deny 由 ngx_http_access_module 模块提供，指令只认 IP 与网段，做不了按域名或按地区的判断，更复杂的需求交给应用层。

> [!TIP]
> **建议内容**：内部后台的标准组合是「allow 内网网段加 deny all 加 auth_basic」，双门齐下；再配合前面章节的安全响应头与 server_tokens off，就构成一套成本低、见效快的基线加固清单。
