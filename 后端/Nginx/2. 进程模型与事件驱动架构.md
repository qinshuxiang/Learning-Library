## 进程模型与事件驱动架构

### master-worker 进程模型

#### master 进程的职责

**master 进程（主进程）**：Nginx 启动时创建的守护进程，**不直接处理任何请求**，专职负责全局管理与控制面的工作。

- 读取并校验配置文件，语法或取值有误时拒绝启动或拒绝本次重载。
- 创建监听套接字并绑定端口（如 80、443）；端口绑定需要特权，这是 master 以 root 启动的原因之一。
- 按配置派生（fork）若干 worker 子进程，并在 worker 异常退出时重新拉起，维持 worker 数量恒定。
- 接收并分发信号（SIGHUP、SIGTERM、SIGUSR2 等），完成平滑重载与热升级。
- 维护自身进程号等状态，写入 PID 文件供管理命令定位。

**控制面与数据面分离是这套模型的第一要义：管理动作不影响请求处理，请求洪峰也干扰不了管理动作。**

> master 以 root 运行，而 worker 以普通用户运行（由配置中的 user 指令指定），这是刻意的安全设计：处理请求的 worker 权限最小化，即使被攻破也拿不到 root 权限。



#### worker 进程的职责

**worker 进程**：实际干活的一线进程，**接收连接、解析请求、执行配置逻辑、返回响应**，全部请求处理工作都发生在 worker 里。

- 在 master 创建的监听套接字上竞争接受（accept）新连接。
- 在事件循环里驱动每条连接：读请求头、按 server 与 location 匹配配置、读静态文件或转发上游、写回响应。
- 记录访问日志与错误日志。
- worker 之间互不通信，各自独立处理各自的连接。

**worker 之间完全对等、互不感知，任何请求只会由唯一一个 worker 从头处理到尾。**

> 端口绑定动作只由 master 完成，所有监听套接字由 master 创建后继承给 worker，worker 只负责在其上接受连接。因此增减 worker 数量不影响端口占用，这也是平滑重载能无缝衔接的底层前提。



#### worker_processes 指令

**worker_processes**：定义 worker 进程数的核心指令，写在主配置顶层（main 上下文），最常用取值是 auto。

```nginx
# nginx.conf 顶层（main 上下文）
worker_processes auto;
```

- **auto**：由 Nginx 自动探测可用 CPU 核数并取等值，官方文档推荐的写法。
- **数字取值**：显式指定 worker 数，如 worker_processes 4；仅在做特殊资源隔离或配合多实例部署时才需要手写。
- **worker 数超过核数**：通常只增加进程切换开销而无收益；worker 数远小于核数则浪费 CPU。

**worker 数通常配置为 CPU 核数，是因为每个 worker 是单线程的事件循环，一核一线程恰好把每个核喂饱，又避免了多余的进程切换。**

> 事件驱动架构下请求处理几乎不阻塞，worker 数不必像传统服务器那样按请求数或内存估算，跟随 CPU 数即可。磁盘 I/O 密集型负载（大量本地文件读写）实务中有调大 worker 数的做法，但这属于个案优化而非默认建议。



### 事件驱动架构

#### 与每请求一进程模型的本质差异

**事件驱动架构**：用少量执行流配合 I/O 多路复用器同时看护大量连接，哪个连接有事件就处理哪个，处理完立刻回到事件循环继续等待。

- **每请求一进程/线程模型**：执行流数量随连接数线性增长，连接空闲时执行流也跟着阻塞或空转，内存与调度成本都花在了等待上。
- **事件驱动模型**：执行流数量与连接数解耦，等待发生在内核的事件等待调用里，不占用独立的执行流与栈内存。
- **成本换算**：传统模型里等待的代价是线程栈与上下文切换；事件驱动里等待的代价几乎只有一条连接对象自身的内存。

**请求与执行流的绑定关系是两种模型的分水岭：前者一个请求绑定一个执行流，后者一个执行流服务任意多个请求。**

> 代价同样存在：worker 是单线程，任何一个请求的处理逻辑发生阻塞（如同步调用外部服务、长耗时的 CPU 计算），整个 worker 上的所有连接都要跟着等。因此 Nginx 的配置逻辑被刻意设计为快速、非阻塞，重活一律转交给上游应用。



#### I/O 多路复用

**I/O 多路复用（I/O Multiplexing）**：通过一次系统调用同时监视多个文件描述符，返回其中有事件的那些，从而用一个执行流看护成千上万条连接的技术，是事件驱动架构的内核支撑。

- **select**：最古老、可移植性最好的一代；监视的描述符数量有上限（通说为 1024），每次调用都要把整批描述符从用户态拷入内核并线性扫描，连接多时开销显著。
- **poll**：去掉了 select 的数量上限，但每次调用仍需线性扫描全部描述符，本质开销未变。
- **epoll**：Linux 专属的现代实现；描述符在内核中注册一次即可反复使用，事件到来时只返回就绪的描述符，复杂度与活跃连接数相关而非总连接数相关。
- **kqueue**：BSD 系（含 macOS）的对应实现，设计思想与 epoll 同类。

Nginx 编译时根据目标平台自动选择事件机制：Linux 上用 epoll，BSD 与 macOS 上用 kqueue，其他平台回退到 select 或 poll。

> [!IMPORTANT]
> **重要内容**：epoll 与 kqueue 的关键优势不在单次速度，而在**规模下的复杂度**：它们把每次全量扫描的代价，摊薄成注册一次、按事件返回就绪集合。这正是单个 worker 能维持上万连接的底层原因，也是 select 与 poll 在万级连接下被淘汰的原因。



#### 异步非阻塞 I/O

**异步非阻塞 I/O**：发起 I/O 操作后不等待其完成，调用立即返回，I/O 完成时通过事件通知发起方——它是事件循环能够持续运转的前提。

- **非阻塞**：套接字设为非阻塞模式后，读不到数据时调用立即返回而不是挂起执行流；Nginx 把暂时没有数据当作一种事件，先去处理别的连接。
- **异步**：慢操作（如磁盘读写）不阻塞事件循环，完成后由事件机制通知继续处理；Nginx 提供了 sendfile、AIO 等机制配合内核完成。
- **组合效果**：连接的等待（网络未就绪、文件未读完）全部发生在内核，worker 的事件循环只在有事件可处理时才动用 CPU。

**一个 worker 能同时维持上万连接，靠的正是上文多路复用器注册一次、按事件返回就绪集合这一优势。**

> 注意术语的严谨性：日常说的 Nginx 异步非阻塞，主体指 worker 对网络 I/O 的处理方式（非阻塞套接字加事件通知），与操作系统层面严格意义的异步 I/O 接口（AIO）不是同一层概念——前者是架构风格，后者是具体的 I/O 接口。



### 并发上限与系统限制

#### worker_connections 指令

**worker_connections**：限定单个 worker 进程最多同时维持的连接数，写在 events 上下文中。

```nginx
events {
    worker_connections 1024;
}
```

- 官方文档记载的默认值为 512，生产环境普遍按内存与文件描述符上限调大。
- 这里的连接数**包含所有类型的连接**：客户端连接、对上游服务的连接以及其他内部连接，不只是浏览器侧的连接。
- 该值同时受操作系统单进程文件描述符上限的约束，调大它必须同步调整系统限制（见下文 worker_rlimit_nofile）。



#### 理论最大并发的计算

**Nginx 的理论最大并发连接数等于 worker 进程数乘以每 worker 连接上限，即 worker_processes 与 worker_connections 的乘积。**

```nginx
worker_processes  auto;   # 设 CPU 为 4 核，即 4 个 worker
events {
    worker_connections 1024;
}
# 理论最大并发 = 4 × 1024 = 4096 条连接
```

- **纯静态服务场景**：一个客户端请求占用一条连接，乘积即并发上限。
- **反向代理场景**：每个经转发的请求要同时占**两条连接**——一条与客户端之间、一条与上游之间，因此实际可服务的客户端并发约为乘积的一半。
- **排查链条**：并发不足时自上而下核对 worker_processes、worker_connections、文件描述符上限，以及上游自身的连接数限制。

> [!CAUTION]
> **注意内容**：乘积只是理论值，实际并发还受内存（每条连接的缓冲区开销）、带宽与后端处理能力共同封顶。把 worker_connections 盲目调到几万而系统文件描述符上限没有跟上，worker 会持续报 too many open files 错误，反而引发故障。



#### worker_rlimit_nofile 与 ulimit

**worker_rlimit_nofile**：为 worker 进程设置文件描述符数量上限（对应操作系统的 RLIMIT_NOFILE），写在 main 上下文中，是 worker_connections 得以调大的前置条件。

```nginx
worker_processes      auto;
worker_rlimit_nofile  65535;

events {
    worker_connections 65535;
}
```

- **ulimit**：操作系统层面对单进程可打开文件数的限制，Linux 上可用 ulimit -n 查看；每个套接字、每个打开的文件都要消耗一个文件描述符。
- **配置原则**：worker_rlimit_nofile 应大于等于 worker_connections 加上日志文件等杂项开销，常见做法是两者取同值或前者略大。
- **检查手段**：查看 worker 进程实际生效的限额（如读取 /proc/进程号/limits），确认配置已被应用。

> [!NOTE]
> **提醒内容**：systemd 托管的服务有自己的限制配置（如单元文件中的 LimitNOFILE），系统 shell 里修改的 ulimit 不会自动传导给服务进程。发现改了配置不生效时，先核对服务单元的实际限额，再怀疑配置本身。



### 惊群问题

#### 惊群问题的概念

**惊群问题（Thundering Herd）**：多个执行流同时等待同一个事件，事件到来时内核把所有等待者全部唤醒，但最终只有一个能处理成功，其余唤醒全部成为无效开销的现象。

- 在 Nginx 场景下具体表现为：多个 worker 一起等待监听套接字上的新连接，一个新连接到来时所有 worker 被唤醒，却只有一个 accept 成功。
- 无效唤醒的代价不小：进程切换、缓存失效，在高连接速率下这些开销会成倍放大。
- 这是多进程竞争同一监听套接字这一架构选择的固有副作用——Nginx 的多 worker 对等竞争模型无法回避它，只能缓解。



#### accept_mutex 的演进

Nginx 对惊群的应对经历了从互斥锁到交还内核的演进。

- **早期方案 accept_mutex**：worker 之间用互斥锁竞争 accept 的资格，同一时刻只有一个 worker 在监听套接字上等待新连接，从根上避免多个 worker 同时被唤醒。
- **1.11.3 版本的转折**：该版本起 accept_mutex 的默认值改为 off，转而依赖内核的并发接受机制（如 Linux 的 EPOLLEXCLUSIVE 标志）削减惊群，官方认为这样吞吐更优。
- **现状**：两个取值都存在，默认交由内核处理，绝大多数场景保持默认即可。

> [!NOTE]
> **提醒内容**：accept_mutex 属于极少数才需要动的调优项，仅在负载极其敏感、或需要精确控制连接分配方式时考虑；没有实测数据支撑时保持默认值是最稳妥的选择。



#### reuseport 参数

**reuseport**：listen 指令的一个参数，让每个 worker 创建自己独立的监听套接字，由内核把新连接分发到不同套接字上，是比互斥锁更彻底的惊群解法。

```nginx
server {
    listen 80 reuseport;
}
```

- 每个 worker 持有独立的监听套接字，内核按策略把连接直接投递给某个 worker，全程无需 worker 之间抢锁。
- 内核层面的分发还在不同 worker 的套接字之间做了负载均衡，降低锁竞争与唤醒开销。
- 该能力依赖内核的 SO_REUSEPORT 套接字选项，仅在支持的内核上生效，具体引入版本以 nginx.org 官方文档为准。

> [!IMPORTANT]
> **重要内容**：reuseport 与 accept_mutex 解决的是同一个问题，但机制相反——前者让每个 worker 独占一条连接队列由内核分发，后者让 worker 排队共享一条队列。两者不应同时启用，开启 reuseport 后锁机制即失去意义；使用前须确认内核支持，否则 Nginx 无法启动。



### 平滑重载与热升级

#### 平滑重载的原理

**平滑重载（Graceful Reload）**：在不中断服务的前提下让新配置生效的机制，由 master 收到 SIGHUP 信号触发。

完整流程如下：

1. master 收到 SIGHUP（nginx -s reload 与 systemctl reload nginx 的本质都是发这个信号）。
2. master 重新读取并校验配置：校验失败则记入错误日志、放弃重载，旧配置继续生效，服务无感知。
3. 校验通过则用新配置派生一批新 worker，新 worker 立即开始接受新连接。
4. master 向旧 worker 发出优雅退出通知：旧 worker 停止接受新连接，把存量请求处理完再自行退出。

**平滑重载能够成立，依赖本章开头给出的套接字归属结论：替换 worker 不牵连任何一条连接。**

> 与 nginx -s stop（SIGTERM，快速停止）对照：stop 不给存量请求任何交代，连接直接断开；reload 则是先立新、后破旧，旧 worker 善终后才退出。这也是配置改坏时 reload 依然安全的原因——坏配置在校验阶段就被挡下，线上行为不变。



#### 热升级的信号流程

**热升级（Binary Upgrade）**：在不停止服务的情况下，把正在运行的 Nginx 换成新版本二进制（或新编译参数）的机制，靠两个关键信号完成。

1. **替换二进制后向旧 master 发送 SIGUSR2**：旧 master 以新二进制启动一个新 master，新旧 master 并存；新 master 派生新 worker 并继承监听套接字，新请求全部由新进程组处理。
2. **向旧 master 发送 SIGWINCH**：旧 master 通知其 worker 优雅退出，存量请求处理完后旧 worker 消失，旧 master 保留进程身位但不再接待任何连接。
3. **确认新版本运行正常后向旧 master 发送 SIGQUIT**：旧 master 彻底退出；若发现问题，还可向旧 master 发送 SIGHUP 让它重新拉起 worker 完成回滚。

> [!CAUTION]
> **注意内容**：SIGUSR2 触发时旧 master 会把 PID 文件改名让位给新 master，回滚窗口只存在于旧 master 尚未收到 SIGQUIT 之前。生产操作应在业务低峰进行，升级前备份当前二进制与配置，并全程观察错误日志。



#### 常用信号速查

master 进程接收的全部常用信号构成一张控制面命令表，nginx -s 参数、systemctl 动作与 kill 信号三者一一对应。

```bash
# 对 master 进程发送信号的等效写法（以 reload 为例）
nginx -s reload                    # 方式一：nginx 命令行
sudo systemctl reload nginx        # 方式二：systemd 服务
sudo kill -HUP $(cat /run/nginx.pid)  # 方式三：直接发信号
```

- **SIGHUP**：平滑重载配置，等价于 nginx -s reload。
- **SIGTERM / SIGINT**：快速停止，等价于 nginx -s stop。
- **SIGQUIT**：优雅停止，等价于 nginx -s quit。
- **SIGUSR1**：重新打开日志文件，等价于 nginx -s reopen，日志切割脚本的最后一步就是它。
- **SIGUSR2**：热升级第一步，以新二进制启动新 master。
- **SIGWINCH**：通知旧 master 的 worker 优雅退出，热升级第二步。

> 速记线索：HUP 重载、TERM 硬停、QUIT 软停、USR1 重开日志、USR2 换二进制、WINCH 退旧 worker。USR 系列是用户自定义信号，Nginx 把它们分配给了热升级与日志切割这两个低频但关键的动作。



### CPU 亲和性

#### worker_cpu_affinity 指令

**worker_cpu_affinity**：把 worker 进程绑定到指定 CPU 核上运行（CPU 亲和性）的指令，写在 main 上下文，默认不开启。

```nginx
# 4 核 CPU：每个 worker 各绑一核
worker_processes 4;
worker_cpu_affinity 0001 0010 0100 1000;
```

- 绑核通过 CPU 掩码指定绑定关系，每个掩码对应一个 worker，从左到右分别代表第四核到第一核。
- 该指令也支持 auto 取值（按官方文档由 Nginx 自动分配），可简化多核机器上的配置。
- 绑核的前提是 worker_processes 为固定数字而非 auto 的隐式结果，掩码数量必须与 worker 数一致。



#### 默认不开启的原因与启用建议

**worker_cpu_affinity 默认未开启，因为对多数负载而言收益有限，而配置不当的绑核反而制造性能洼地。**

- **收益来源**：worker 长期固定在一核上运行，其数据在 CPU 缓存中的驻留更稳定，减少跨核迁移带来的缓存失效。
- **风险来源**：多个 worker 绑到同一核会让该核过载，其余核空闲；进程间负载不均时绑核会放大失衡。
- **判断标准**：只有在压测中确认存在明显的跨核调度与缓存失效开销时才值得启用。

> [!TIP]
> **建议内容**：CPU 亲和性属于先测量后优化的手段，常规部署保持默认即可，把精力留给连接数与上游链路的调优。启用后务必用系统工具核对每个 worker 实际落在的核，确认掩码写对了。



### 一条请求的完整生命周期

#### 生命周期的阶段拆解

一条 HTTP 请求从建立连接到日志落盘，在 Nginx 内部经历一条固定且高度优化的流水线，理解它是读懂后续章节配置逻辑的总纲。

1. **建立连接**：客户端发起 TCP 连接，内核完成三次握手，连接进入监听套接字队列，某个 worker 通过事件机制接受该连接。
2. **解析请求**：worker 从连接上读取并解析请求行与请求头（方法、URL、HTTP 版本、Host、Content-Length 等），构造内部请求结构。
3. **匹配 server**：根据请求头中的 Host 与监听端口，在所有 server 块中选出唯一的 server 虚拟主机。
4. **匹配 location**：在选中的 server 内按 URI 与各 location 的匹配规则（前缀、精确、正则等）选出处理该请求的 location，并加载其配置。
5. **处理请求**：按配置执行——静态请求由 Nginx 直接读取文件返回；代理请求通过 proxy_pass 转发到上游，再把上游响应中转给客户端；期间可能经历重写、限速、缓存等处理阶段。
6. **写回响应**：拼装状态码与响应头，把响应体写回客户端连接；写完后视 keepalive 配置决定保留连接复用还是关闭。
7. **记录日志**：把请求结果写入 access.log（状态码、字节数、耗时等），请求生命周期至此结束。

> [!IMPORTANT]
> **重要内容**：整条流水线中的每一步都运行在 worker 的事件循环里，任何一步都不允许长时间阻塞——这正是本章事件驱动架构在请求处理上的直接体现。后续章节的虚拟主机、location 匹配、反向代理与缓存，本质上都是在这条流水线的对应阶段插入配置逻辑。



#### 各阶段与配置的对应关系

流水线的每个阶段都对应一块配置入口，记熟这层对应关系，后续学配置时就知道每条指令生效在哪里。

- **建连阶段**：对应 listen、worker_connections 与 keepalive 等连接层指令。
- **匹配阶段**：对应 server_name（选 server 块）与 location（选处理规则），以及 root、alias 等定位指令。
- **处理阶段**：对应 proxy_pass、fastcgi_pass 等转发指令，以及 rewrite、limit_req、proxy_cache 等处理指令。
- **收尾阶段**：对应 add_header（附加响应头）与 access_log（日志格式与落点）。

> 速记线索：建连看连接层、匹配看 server_name 与 location、处理看各类 pass 与 rewrite、收尾看日志与响应头。一条请求卡在哪一步，就去哪一步对应的配置块里找原因，这是排障时定位问题层次的基本功。

以一条反向代理请求为例，上述阶段在配置中的落点一目了然。

```nginx
server {
    listen 80;
    server_name example.com;          # 阶段三：匹配 server

    location /api/ {                  # 阶段四：匹配 location
        proxy_pass http://backend;    # 阶段五：转发上游
        proxy_set_header Host $host;
    }

    access_log /var/log/nginx/api.log;  # 阶段七：记录日志
}
```

> 读完这段配置再回看七阶段流水线，会发现配置文件本质上是对流水线各阶段的声明式描述：Nginx 的工作就是在每个阶段把命中的配置取出来执行，这也解释了为什么配置的层级结构（main、events、http、server、location）与请求处理的层级一一对应。
