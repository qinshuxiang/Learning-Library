## 反向代理

### 正向代理与反向代理

#### 两类代理的定义

**正向代理**：站在**客户端**一侧的代理服务器，代替客户端向目标服务器发起请求，目标服务器只能看到代理的地址，看不到真实客户端。**反向代理**：站在**服务端**一侧的代理服务器，代替服务器接收请求，再转发给内部的真实服务节点，客户端只知道自己访问了代理域名，不知道也不需要知道背后是谁在干活。

- **正向代理**代理的对象是**客户端**：客户端主动配置代理，代理带着客户端的请求出门办事。
- **反向代理**代理的对象是**服务端**：服务端把它部署在门口，所有流量先到它这里再分发。
- 两者本质都是请求的中间转发，差别只在**替谁出面、对谁隐藏谁**。

> 判断口诀：看代理**站在谁的门口、替谁挡脸**。正向代理挡住的是客户端（服务器不知道谁在访问），反向代理挡住的是服务端（客户端不知道谁在响应）。一个藏客户端，一个藏服务器。



#### 典型场景与客户端感知差异

两类代理的典型用途截然不同，客户端是否知情、是否需要配置，是最实用的判别依据。

- **正向代理的典型场景**：内网机器统一出网访问外部资源、企业上网行为管控、抓包调试工具（如Charles、Fiddler）代理本机流量。
- **反向代理的典型场景**：Nginx 作为站点入口做负载均衡、把 HTTP 请求转发给内网的 Node、Java、Python 应用、配合缓存与 TLS 终结。
- **客户端感知**：正向代理必须**显式配置**才会生效，客户端明确知道自己在用代理；反向代理对客户端**完全透明**，浏览器只当自己在访问普通网站，无需任何配置。
- **服务端感知**：正向代理对目标服务器而言就是来访者；反向代理对上游应用而言是唯一固定的直接客户。

> [!NOTE]
> **提醒内容**：日常说的 Nginx 代理几乎都指反向代理。本章其余内容（proxy_pass、upstream、超时与缓冲等）全部围绕反向代理展开。

> **速记**：正向代理配在客户端、替客户端出门；反向代理架在服务端、替服务端守门。



### proxy_pass 与路径拼接规则

#### proxy_pass 的基本形态

**proxy_pass 指令**：把命中 location 的请求转发到指定上游地址，是反向代理的核心指令，地址可为 IP、域名、upstream 块名（见后文），写在 location 或 if 等上下文中。

- 基本写法：proxy_pass http://backend;，把请求原样交给名为 backend 的上游。
- 是否携带 URI 决定路径行为，这是 proxy_pass 全主题最关键的分界线。
- **不带 URI**（仅到端口或域名，结尾无路径）：保留客户端的原始请求 URI，原样转发给上游。
- **带 URI**（结尾有斜杠或路径）：用该 URI **替换** location 中被匹配到的那段路径。

```nginx
server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;   # 不带 URI：原样转发
    }
}
```

> 记忆锚点只有一条：**proxy_pass 后面有没有「尾巴」**。没有尾巴，路径原样带走；有尾巴，尾巴顶替 location 匹配段。



#### 四种组合的路径演算

设配置为 location /api/ 且客户端请求 **/api/users/list**，proxy_pass 的四种写法对应四种到达上游的路径，逐一演算如下。

- **proxy_pass http://backend**：不带 URI，原样保留，上游收到 **/api/users/list**。
- **proxy_pass http://backend/**：尾巴是根斜杠，用 / 替换匹配段 /api/，上游收到 **/users/list**。
- **proxy_pass http://backend/v1**：尾巴是 /v1，用它替换 /api/ 后直接拼接剩余部分，上游收到 **/v1users/list**（v1 与 users 之间无斜杠，斜杠随匹配段一起被吃掉）。
- **proxy_pass http://backend/v1/**：尾巴是 /v1/，替换 /api/ 后拼接，上游收到 **/v1/users/list**。

```nginx
location /api/ {
    # 客户端请求 /api/users/list 时：
    proxy_pass http://backend;        # -> /api/users/list
    # proxy_pass http://backend/;     # -> /users/list
    # proxy_pass http://backend/v1;   # -> /v1users/list
    # proxy_pass http://backend/v1/;  # -> /v1/users/list
}
```

> 两种高频坑：其一，backend/v1 这种**尾巴不带斜杠**的写法会把剩余路径直接贴上去，拼出 v1users 这类畸形路径；其二，location 结尾与 proxy_pass 尾巴的**斜杠必须成对考虑**——location /api/ 配 http://backend/ 才是常见的「剥掉前缀」意图。改完路径规则务必实际请求验证上游日志里的真实路径。

> **速记**：无尾原样传，有尾换前缀；尾巴带斜杠则拼接带斜杠，v1 无杠必翻车。



### 传递请求信息与真实 IP

#### proxy_set_header 与默认透传行为

**proxy_set_header 指令**：设置或改写转发给上游的请求头，可出现在 http、server、location 上下文，同一头多次设置时**内层覆盖外层**。Nginx 默认只做一件事：把 Host 头改为 proxy_host（即 proxy_pass 中的上游主机名），**其余请求头全部原样透传**。

- 默认行为要点：透传不等于完全等价，Host 被改写是唯一主动干预，Connection 等逐跳头由代理机制按 HTTP 规范处理。
- proxy_set_header Host $host;：把原始请求的域名原样传给上游，虚拟主机类应用据此路由。
- proxy_set_header X-Real-IP $remote_addr;：把直连对端地址放进自定义头，供后端读取。
- proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;：在既有 X-Forwarded-For 链尾追加当前对端地址，形成完整代理链。
- proxy_set_header X-Forwarded-Proto $scheme;：告知上游客户端使用的协议（http 或 https），上游生成正确的外链与重定向依赖它。

```nginx
location /api/ {
    proxy_pass http://backend;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

- 后端取用方式：Java 用 request.getHeader("X-Real-IP") 系列方法，Node 的 Express 用 req.headers["x-real-ip"] 与 req.headers["x-forwarded-for"]，头名一律不区分大小写。

> [!IMPORTANT]
> **重要内容**：不设置这四个头是生产环境最经典的翻车点——上游拿到的 Host 变成了 proxy_host、用户 IP 丢失，导致鉴权域名校验失败、日志全是 Nginx 的 IP、生成出 http 的错误链接。**代理配置四件套应作为默认动作写进每个 proxy_pass 所在的 location**。



#### 真实 IP 的链路与伪造风险

**$remote_addr**：与 Nginx 建立 TCP 连接的**直连对端地址**，不可伪造但只代表上一跳；**X-Forwarded-For**：记录转发链的逗号分隔追加链，每经过一层代理就**追加一节**，但**最左侧（最早一节）来自客户端首个请求头，可以伪造**。

- 链路形态：客户端（伪造头 X-Forwarded-For: 1.2.3.4）→ CDN → Nginx → 上游，上游收到的可能是 1.2.3.4, 真实IP, CDN IP 这样的三节链。
- 结论：X-Forwarded-For 的**从左数第二节起**（由可信代理写入的部分）才可信，最左侧可由客户端随意填。
- CDN 场景的实务做法：Nginx 把 CDN 回源 IP 记入 X-Forwarded-For，真实用户 IP 由 CDN 放在专用头（如 CDN 厂商自定义头）中带回，业务以该头为准，或直接信任 CDN 厂商文档声明的头。
- **realip 模块**（ngx_http_realip_module）：用 set_real_ip_from 声明可信代理网段、用 real_ip_header 指定从哪个头（X-Forwarded-For 或 X-Real-IP）提取真实 IP，把 $remote_addr 本身改写为真实地址，使后端无需改动即可拿到正确 IP；配套 real_ip_recursive 控制从链尾向前回溯几层。
- 原则：**只信任自己可控链路上的代理节点**，对不可信来源的头一律不认。

```nginx
# realip 模块概念示例：把可信代理写进 X-Forwarded-For 的地址还原为真实 IP
set_real_ip_from 10.0.0.0/8;          # 内网可信代理网段
set_real_ip_from 203.0.113.0/24;      # CDN 回源网段
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

> 取真实 IP 的一句话原则：**没有可信代理层时看 $remote_addr，有代理层时看链并只信链上自己人**。直接取 X-Forwarded-For 最左侧当用户 IP 供风控、限流使用，属于把伪造入口递给攻击者。



### 超时三件套与 504

#### 三个 proxy 超时指令

**proxy_connect_timeout**、**proxy_send_timeout**、**proxy_read_timeout** 分别约束反向代理与上游交互的三个阶段，默认值均为 60 秒，适用于 http、server、location 上下文，是代理稳定性的第一道闸门。

- **proxy_connect_timeout**：与上游建立 TCP 连接的最长等待时间，超时后放弃；生产环境通说认为取 3 到 5 秒为宜——正常上游建连是毫秒级的，等几十秒毫无意义。
- **proxy_send_timeout**：向上游**发送请求**过程中两次成功写操作之间的最大间隔，不是整次发送的总时限；上游长期收不动请求时触发。
- **proxy_read_timeout**：**等待上游响应**时两次成功读操作之间的最大间隔；上游处理慢、接口卡住时由它兜底，是三件套中最常被调整的一个。
- 典型调优：普通接口保持默认或略降；长任务（导出、大查询）按业务实际耗时放宽 read 超时，或改造为异步任务避免长连接占坑。

```nginx
location /api/ {
    proxy_connect_timeout 5s;
    proxy_send_timeout    60s;
    proxy_read_timeout    120s;
    proxy_pass http://backend;
}
```

> 三个超时都是**间隔而非总时长**：只要上游持续有字节往来，read 超时就不会触发。这也解释了为什么慢速但持续输出的流式接口不会被正常断开，而完全无响应的接口会在超时点被切断。



#### 504 Gateway Timeout 的来源

**504 Gateway Timeout**：Nginx 在规定时间内没有从上游得到应有的进展——建连超时、发送超时或读取超时任一触发，即产生该状态码，含义是**代理与上游之间的等待超限**。

- 建连阶段超时：上游宕机、端口未监听、防火墙丢包，read 根本没开始就卡死在 connect。
- 读响应阶段超时：上游接了请求但处理过慢，超过 proxy_read_timeout 两次读之间的间隔。
- 排查方向：统一按本章后文「标准排查顺序」小节的三步执行，不单独另立流程。

```bash
# 在 error_log 中检索超时记录，确认是哪个阶段超时
grep 'upstream timed out' /var/log/nginx/error.log | tail
```

> [!TIP]
> **建议内容**：调大超时只是把等待拉长，治标不治本。反复出现 504 的接口应优先分析上游为什么慢（慢 SQL、阻塞调用、下游依赖超时链），或改造为异步任务加轮询，让 HTTP 请求快速返回。

> **速记**：connect 管握手，send 管递请求，read 管等答复；三者任一卡死即 504。



### 缓冲与流式

#### proxy_buffering 与缓冲的意义

**proxy_buffering on;**（默认 on）：Nginx 尽可能快地把上游响应**收完收到自己的缓冲区**，再按客户端能接受的速度慢慢喂给它，上游因此被尽快释放，这是缓冲机制保护上游的核心意义。

- **proxy_buffer_size**：存放**响应头**（及响应体首段）的缓冲区，通常为一个内存页（4k 或 8k，随平台而定），头过大导致 upstream sent too big header 错误时调它。
- **proxy_buffers**：存放**响应体**的缓冲区组，默认形如 8 4k（块数 乘 单块大小），响应体在这组缓冲与磁盘临时文件间流转。
- on 的效果：上游接口快速吐完响应即可去处理下一个请求，慢客户端由 Nginx 陪跑，上游连接占用时间被压缩。
- off 的效果：Nginx 收到多少转发多少，上游被慢客户端拖住，连接占用时间等于客户端消化时间。

```nginx
location /api/ {
    proxy_pass http://backend;
    proxy_buffering on;
    proxy_buffer_size 16k;   # 响应头缓冲，特大响应头场景调大
    proxy_buffers 8 16k;     # 响应体缓冲组
}
```

> 缓冲的本质是**用 Nginx 的耐心换上游的效率**：慢客户端的拖延代价由代理层吸收，这正是 Nginx 作为入口网关存在的价值之一。



#### 流式接口的缓冲关闭

SSE（Server-Sent Events）与流式对话类接口按字节逐步推送，若被缓冲截留，客户端会长时间收不到任何数据，出现「接口没响应」的假象，此类 location 必须**关闭缓冲**。

- 方法一：对 SSE 路径单独配置 proxy_buffering off;。
- 方法二：上游在响应中发送头 **X-Accel-Buffering: no**，Nginx 见此头即对该响应禁用缓冲，适合由应用自行决定是否流式的场景。
- 流式场景通常还需配合较长的 proxy_read_timeout 或让应用周期性发心跳，防止空闲间隔触发读超时。
- 另外建议 proxy_cache off;（SSE 不该被缓存）并关闭对这类响应的 gzip 分块干扰，保持推送及时性。

```nginx
# SSE / 流式接口专用 location
location /api/stream/ {
    proxy_pass http://backend;
    proxy_buffering off;          # 逐段转发，不攒
    proxy_cache off;
    proxy_read_timeout 300s;      # 空闲心跳间隔需小于此值
}
```

> [!IMPORTANT]
> **重要内容**：AI 对话、日志推送、事件订阅等流式接口一旦忘记关缓冲，症状清一色是「后端日志在推、前端迟迟无数据」。排查顺序：确认上游确实在分段输出，再看本 location 是否命中 proxy_buffering off 或上游是否返回了 X-Accel-Buffering: no。

> **速记**：普通接口攒着发省上游，流式接口关缓冲保实时。



### upstream 与 keepalive 长连接

#### upstream 块与 keepalive 指令

**upstream 块**：在 http 上下文定义一组上游服务器，proxy_pass 直接指向块名即可享受负载均衡与统一管理；**keepalive 指令**：为该组上游维护一个**空闲长连接池**，后续请求复用已建连的 TCP 连接，不再每次三步握手。

- upstream 块内用 server 项列出节点，可附带权重、最大失败数等参数，负载均衡细节配合本章主题理解即可。
- keepalive 32; 表示为该组上游保留 32 条空闲连接，取值按并发量估算，无固定标准。
- 收益：省去每请求一次的建连开销；更关键的是避免大量短连接在两端机器上堆积 **TIME_WAIT** 状态（主动关闭方需等待约两分钟才能回收端口），高 QPS 下 TIME_WAIT 泛滥会耗尽本地端口。

```nginx
upstream backend {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    keepalive 32;          # 保持 32 条空闲长连接
}

server {
    listen 80;
    location /api/ {
        proxy_pass http://backend;
        # 以下两行是 keepalive 生效的前提，缺一不可
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

> [!IMPORTANT]
> **重要内容**：keepalive 指令单独配置**不会生效**，必须同时满足两个前提：proxy_http_version 1.1（Nginx 默认用 1.0 与上游通信，1.0 难以复用连接）与 proxy_set_header Connection "";（清空 Connection 头，否则默认的 close 语义会让每个请求结束就断连）。三者构成固定搭档，背下来。



#### WebSocket 代理

**WebSocket** 基于 HTTP **升级机制**建立：客户端发出带 Upgrade: websocket 与 Connection: Upgrade 头的请求，服务器同意后返回 101，连接从 HTTP 切换为全双工长连接。代理层必须把这两个头正确映射转发，升级才能完成。

- 惯用写法：用 **map $http_upgrade $connection_upgrade** 把客户端的 Upgrade 头值映射给 Connection 头——客户端请求升级时转发 Upgrade 语义，普通请求时置空。
- 映射块写在 http 上下文：default upgrade; 与空值 close; 两行是通说标准形态。
- location 中配套 proxy_http_version 1.1（升级协议要求）与两条 proxy_set_header。
- **proxy_read_timeout 对空闲长连接的影响**：WebSocket 建立后若无数据往来，Nginx 按读超时切断空闲连接，导致连接莫名掉线，需调大超时或让应用定期发心跳（ping/pong）保活。

```nginx
# http 上下文：Upgrade 头到 Connection 头的映射
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;

    location /ws/ {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;   # 空闲一小时不断线，或改用应用层心跳
    }
}
```

> [!WARNING]
> **警告内容**：WebSocket 掉线的头号元凶是**空闲触发 proxy_read_timeout**，而非网络故障。现象多为连接稳定使用若干秒或若干分钟后被断开，间隔恰好等于配置的超时值；先查超时与心跳配置，再查中间链路上的其他代理层是否也有各自空闲超时。

> **速记**：升级靠 Upgrade 加 Connection 映射，保活靠 1.1 加空 Connection，防掉线靠 read 超时或心跳。



### 常见错误码辨析与排查

#### 502、504 与 503 的区别

**502 Bad Gateway**：上游**连不上**或返回了**非法响应**——连接被拒、进程崩溃、响应残缺；**503 Service Unavailable**：服务**暂时不可用**——常见于临时维护、限流触发或上游被标记为不可用时 Nginx 主动返回。与 504 的一句对比：502 连不上或答非所问，504 连得上但等超时（定义见上一小节），503 我现在不接待。

- 502 的定位：**上游存在但失格**，端口没人听、进程死了、响应不合法都算，责任在上游健康度。
- 504 的定位：**上游活着但太慢**，等待超过 proxy_read_timeout 等超时配置。
- 503 的定位：**代理自己决定不服务**，维护页、limit_req 限流、upstream 中全部节点被置为失败后的默认回应。
- 三者一句话辨析：502 连不上或答非所问，504 等到天荒地老，503 我现在不接待。

> [!NOTE]
> **提醒内容**：三个状态码都由代理层发出，但根因大多在配置与上游侧。看到 503 先查限流与 upstream 节点标记逻辑，再确认是否真的在维护窗口；把三类码混为一谈会直接把排查引向错误方向。



#### 标准排查顺序

502 与 504 的排查有稳定的路径可循：先读日志定位现象，再验证网络连通，最后核对上游进程与超时配置，三步收束。

- 第一步：看 **error_log**。upstream connect refused 指向 502 类，upstream timed out 指向 504 类，日志直接给出阶段与上游地址。
- 第二步：测上游端口连通。在 Nginx 所在机器执行 curl -v http://上游地址 与 telnet 类连通性检查，区分网络问题与进程问题。
- 第三步：查上游进程与超时配置。确认应用进程存活、监听端口正确，再核对 proxy_connect_timeout、proxy_read_timeout 与业务耗时的匹配度。

```bash
# 排查三连：日志、连通、进程
tail -n 50 /var/log/nginx/error.log
curl -sv --max-time 3 http://10.0.0.11:8080/health
ps aux | grep -i 'node\|java\|gunicorn'
```

> [!TIP]
> **建议内容**：给上游准备好 /health 健康检查接口，排障时第二、三步可以一步完成；同时保持 error_log 的级别为默认 error 而不是 debug，既有足够信息又不至于刷爆磁盘。

> **速记**：先日志定阶段，再 curl 验连通，后进程与超时；502 查死活，504 查快慢，503 查限流与维护。
