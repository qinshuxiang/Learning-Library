## 负载均衡

### 负载均衡的定义与实现层级

#### 负载均衡的定义

**负载均衡**（Load Balancing）：把客户端请求按某种规则分摊到多台后端服务器上处理的技术，目的是避免单台服务器过载，提升系统整体的吞吐量与可用性。

- 核心思想：一台机器扛不住的流量，让一组机器共同承担，对外表现为一个统一的服务入口。
- 分发依据：按轮询、权重、连接数、哈希等策略决定这个请求交给谁。
- 附带能力：配合健康检查剔除故障节点，配合重试机制在节点失败时改发其他节点，天然提升可用性。

> 单机容量有上限，扩容有两路：垂直扩容（换更强的机器）成本陡增且有物理极限，水平扩容（加机器、加负载均衡器）是互联网架构的主流选择。负载均衡正是水平扩容的前提设施。



#### 常见的实现层级与代表产品

负载均衡按实现载体可分为 DNS、硬件、软件三个层次，各自工作在流量的不同位置。

- **DNS 轮询**：在 DNS 解析层为同一域名配置多条解析记录，解析结果按顺序轮换，把流量在入口处分流。配置最简单，但解析结果有缓存、感知不到后端死活，精度与可控性最差。
- **硬件负载均衡**：以 F5 为代表的专业设备，性能强、功能全、价格昂贵，多见于金融等对稳定性要求极高的场景。
- **软件负载均衡**：运行在通用服务器上的软件方案，成本灵活、可编程性强，代表有 Nginx、LVS、HAProxy。
- 软件方案的常见分工：LVS 工作在内核态、转发性能极高，常作为第一层流量入口；Nginx 与 HAProxy 功能更丰富，常作为第二层应用网关。

> 实务中大型站点常见多层组合：DNS 做地域分流，LVS 做四层入口，Nginx 做七层网关；中小规模下一台 Nginx 往往就够了。选型看流量规模与预算，不必一步到位。



#### 四层负载均衡与七层负载均衡

**四层负载均衡**：工作在传输层，依据报文的目标 IP 与端口做转发、不理解应用层内容的负载均衡。**七层负载均衡**：工作在应用层，能解析 HTTP 等应用协议、依据 URL 与 Cookie 及请求头等内容做路由的负载均衡。

- **四层负载均衡**：只看 IP 加端口，转发开销极小、吞吐极高，但不具备改写请求、按内容分流的能力；Nginx 中由 stream 块承担。
- **七层负载均衡**：解析 HTTP 报文，可做动静分离、按路径转发、改写头部、缓存压缩等高级功能，代价是解析报文的性能开销；Nginx 中由 http 块承担，是绝大多数 Web 场景的使用方式。
- **Nginx 的 http 块是七层负载均衡，stream 块是四层负载均衡**：两者在配置文件中平级书写，分别服务两类场景。

> [!IMPORTANT]
> **重要内容**：四层与七层是高频对比考点，判断依据只有一条——是否解析应用层报文：四层转发快但看不懂内容，七层功能强但要付出解析成本。对 Nginx 而言，配置写进 http 块就是七层代理，写进 stream 块就是四层代理。



### upstream 块与反向代理

#### upstream 块的定义

**upstream 块**：Nginx 在 http 上下文中定义一组后端服务器的配置段，是 Nginx 实现七层负载均衡的核心载体。**server 指令**：upstream 块内声明单个后端节点的指令，写法为 server 加地址加可选参数。

- upstream 块写在 http 块内、server 块之外，块名自定义，这个名字后续当作虚拟主机地址使用。
- 每条 server 指令描述一个后端节点：写 IP 加端口，或域名加端口；省略端口时按协议默认端口处理。
- 一个 upstream 内可混合任意多个节点，负载均衡策略与节点参数都定义在这个块里。

```nginx
# http 块内定义一组后端，名字叫 backend
upstream backend {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080;
}
```

> upstream 名字只是 Nginx 配置内部的标识，不会对外暴露；命名应体现服务用途（如 app_pool、api_pool），便于多个 location 复用同一组后端。



#### proxy_pass 引用 upstream

proxy_pass 中用 upstream 名字替代主机地址，该 location 的请求即进入负载均衡分发流程。

- 写法：proxy_pass http://upstream名; 把原来的主机地址换成 upstream 块的名字即可。
- 分发过程对客户端完全透明，客户端只感知到 Nginx 这一个入口。
- 每次新请求到来时，Nginx 按当前策略从组内选一个节点转发，再由反向代理模块完成请求与响应的搬运。

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        # 主机地址的位置换成 upstream 的名字 backend
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

> proxy_pass 后面写的仍是协议前缀 http://，只是主机部分变成了 upstream 名。初学阶段掌握名字替代主机这一种写法即可；proxy_pass 与 URI 路径搭配的更多细节属于反向代理专题，不要在负载均衡配置里混用复杂写法。



### 内置负载均衡策略

#### 轮询与权重轮询

**轮询**（Round Robin）：Nginx 的默认策略，不写任何策略指令时，请求按顺序逐一平均分给组内每个正常节点。**权重轮询**：在 server 上用 weight 参数为节点设置权重，权重越高的节点分到的请求越多。

- 轮询是默认行为：upstream 块内只写 server 行、不写任何策略指令，即是轮询，无需任何配置。
- 权重轮询适用于节点性能不均的场景：weight=2 的节点获得的请求数约为 weight=1 节点的两倍。
- 权重值是相对比例而非绝对数量，全组按权重比分摊。

```nginx
# 轮询：什么都不写就是轮询
upstream round_robin_pool {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}

# 权重轮询：性能强的节点多承担流量
upstream weighted_pool {
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=1;
}
```

> 轮询与权重轮询都不关心请求是谁发的，同一客户端的连续请求可能落在不同节点上；这对无状态服务毫无影响，对有会话的服务需要 ip_hash 或集中存储来补救，见会话保持一节。



#### ip_hash 与 least_conn

**ip_hash**：按客户端 IP 的哈希结果分配节点，同一 IP 的请求恒定落在同一后端的策略。**least_conn**：优先把请求分给当前活跃连接数最少的节点的策略。

- ip_hash 的价值是会话保持：客户端 IP 不变则后端不变，应用层保存在单机内存的 Session 不会丢失。
- ip_hash 的代价不小：负载倾斜与节点故障丢会话两类问题，完整分析见下方 WARNING。
- least_conn 适合请求处理时长差异大的场景：长请求占住节点时，新请求自动流向空闲节点。
- least_conn 在组内各节点连接数接近时，效果退化为轮询。

```nginx
# ip_hash：同一客户端 IP 固定打到同一后端
upstream ip_hash_pool {
    ip_hash;
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}

# least_conn：优先分给当前连接数最少的节点
upstream least_conn_pool {
    least_conn;
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}
```

> [!WARNING]
> **警告内容**：ip_hash 只按 IP 维持粘性，不能当作完备的会话保持方案：一是 NAT 出口会让大量用户共享一个 IP，负载倾斜无法避免；二是该节点故障时这些用户的会话仍然丢失。通说认为，会话保持应优先靠应用层无状态化解决，而不是依赖 ip_hash，详见会话保持一节。



#### hash 指令与一致性哈希

**hash 指令**：Nginx 提供的自定义哈希策略，允许指定任意变量作为哈希键，把键值相同的请求固定到同一节点。**一致性哈希**：hash 指令开启 consistent 参数后启用的哈希方式，节点增减时只有部分键的映射变化，而不是全局洗牌。

- 典型写法 hash $request_uri consistent;：相同 URI 的请求固定落在同一节点，后端对同一路径的缓存命中率因此大幅提高。
- 不加 consistent 时是普通哈希：节点数量一变，几乎所有键的映射都会改变，缓存大面积失效。
- 加 consistent 后增删节点只影响相邻区间的键，是缓存类后端的标配选择。

```nginx
upstream cache_pool {
    # 按 URI 做一致性哈希，提高后端缓存命中率
    hash $request_uri consistent;
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080;
}
```

> 速记：ip_hash 是按客户端 IP 的固定哈希，hash 指令是按你指定的任意变量做哈希，consistent 一词开启一致性哈希；前者为会话保持而生，后者为缓存命中而生。



### 会话保持与无状态化

#### 会话保持问题的由来

**会话保持**：保证同一用户的连续请求被转发到同一台后端服务器，使其保存在单机内存中的 Session 数据持续可用的机制。

- 问题根源：应用的 Session 默认存在单机内存里，负载均衡把后续请求分给另一台机器时，那台机器上没有这份 Session，用户被当作未登录处理。
- 需求由此而来：要么让请求认准一台机器，要么让所有机器都能读到同一份 Session。
- 常见手段有三类：ip_hash 等粘性策略、Session 集中存储、客户端令牌化（如 JWT）。

> 会话保持不是负载均衡本身的目标，而是无状态化没做完时欠下的债；理解这一点，才能理解下一条考点中两条路线的优劣排序。



#### 无状态化与集中存储

**无状态化**：应用不把任何与用户相关的状态保存在本机内存或本地磁盘，每个请求携带全部所需信息，任意节点都能处理任意请求的架构性质。

- 无状态化是上策：负载均衡不再需要任何粘性策略，节点可以随意增减、宕机重启不影响用户，弹性伸缩与滚动发布都变得自由。
- 做不到完全无状态时，通说认为应把 Session 集中存储到 Redis 等外部共享存储：所有后端读写同一份 Session，天然跨节点可用，节点宕机也不丢会话。
- 与 ip_hash 对比：Redis 集中存储不破坏负载均衡分布、容忍节点故障、支持水平扩容；ip_hash 只在一个维度上勉强粘住用户，倾斜与故障丢会话两个缺陷都无法根治。

```nginx
# 无状态化后，upstream 回归最朴素的轮询，无需任何粘性策略
upstream app_pool {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}
```

> [!TIP]
> **建议内容**：选型口诀：能用无状态就用无状态，不能就上 Redis 集中存储，ip_hash 只适合小规模过渡或后端不可改造的遗留系统。把会话保持寄托在负载均衡层，等于把应用的架构债转嫁给基础设施。



### server 参数与被动健康检查

#### weight、max_fails 与 fail_timeout

server 指令除地址外还接受一组参数，其中 max_fails 与 fail_timeout 必须联动理解：**fail_timeout**：定义一个时间窗口的参数；**max_fails**：定义在一个窗口内允许失败次数上限的参数。

- 联动语义：在一个 fail_timeout 窗口内，某节点连接失败达到 max_fails 次，Nginx 就把它标记为不可用，并在接下来的一个 fail_timeout 窗口内不再向它分发请求。
- 窗口结束后 Nginx 会以少量请求试探该节点：成功则恢复参与负载均衡，失败则继续等待下一个窗口。
- 两个参数的官方默认值为 max_fails=1、fail_timeout=10s，即默认失败一次就摘除十秒；生产中常调大 max_fails，避免偶发抖动误杀节点。
- weight 与上述参数可同时写在一条 server 上，互不冲突。

```nginx
upstream app_pool {
    # 30 秒窗口内失败 3 次则摘除，再等 30 秒后试探恢复
    server 192.168.1.10:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;
}
```

> 把两个参数读成一对：fail_timeout 管时间刻度，max_fails 管这个刻度内的失败额度；额度用完就停用一个刻度。只调其中一个而不理解另一个，调优往往走偏。



#### backup 与 down

**backup**：把节点标记为备份机、平时不接流量、仅当全部非备份节点不可用时才顶上的 server 参数。**down**：把节点标记为永久不可用、属于手动下线的 server 参数。

- backup 适合部署灾备节点：主机组全部不可用时自动兜底，主机组恢复后自动退回备份位。
- down 常用于计划内维护：发布或检修前先给节点写 down，流量全部避开，维护完删掉 down 并 reload 即可恢复。
- 两者都是写死在配置里的静态状态，变更须经 reload 生效，与运行中自动摘除的被动健康检查不同。

```nginx
upstream app_pool {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080 backup;  # 灾备节点，平时不接流量
    server 192.168.1.13:8080 down;    # 手动下线，计划内维护
}
```

> backup 与 down 改变的是配置层面的资格，被动健康检查改变的是运行层面的状态：前者由人写进配置，后者由 Nginx 依据失败统计自动判定，两者互不替代。



#### 被动健康检查的机制

**被动健康检查**：Nginx 开源版内置的健康检查方式，不主动探测后端，而是在真实请求转发失败时按 max_fails 与 fail_timeout 的规则记录失败并摘除节点。

- 探测由真实流量触发：只有用户请求真的失败（连接拒绝、超时等）时，失败计数才增加。
- 摘除依赖统计窗口：一个窗口内失败达到上限，节点停用一个窗口，之后试探恢复。
- 零额外成本是优点；缺点是发现故障要靠用户请求撞上去，故障感知有延迟，且撞上去的那部分请求已经受损。

```nginx
# 被动健康检查无需专门指令，max_fails 与 fail_timeout 就是它的全部开关
upstream app_pool {
    server 192.168.1.10:8080 max_fails=3 fail_timeout=30s;
    server 192.168.1.11:8080 max_fails=3 fail_timeout=30s;
}
```

> 速记：开源版的健康检查是被动的——被用户请求撞出来的失败才计数；想要主动巡检，要么用商业版，要么加第三方模块，见下一条考点。



#### 主动健康检查的生态现状

**主动健康检查**：由负载均衡器按固定间隔向后端发送探测请求、依据响应判定节点存活的机制，无需等待真实流量触发。

- 开源版 Nginx 核心不包含主动健康检查，upstream 模块只提供上述被动机制。
- 商业版 Nginx Plus 提供官方的主动健康检查，可按周期发送探测请求并依据响应判定节点存活。
- 开源生态的替代方案是第三方模块或基于 OpenResty 加 Lua 自行实现，社区常见的 upstream_check 类模块即为此用途；不同模块的指令集差异较大，以各自文档为准。
- 不引入新组件时的折中：由外部监控系统定期探活，发现异常后联动变更 Nginx 配置并 reload。

> 客观定位：主动健康检查是商业版自带、开源版靠生态的格局；选型时先确认团队能否接受第三方模块的维护成本，再决定是否引入，不要为小规模服务盲目加模块。



### upstream keepalive 连接池

#### keepalive 指令与连接池机制

**keepalive 指令**：在 upstream 块内声明到每个后端节点的空闲长连接缓存数量、使 Nginx 与后端之间复用已建立 TCP 连接的指令，避免每个请求都重新握手。

- 写法：keepalive 数字;。数字是到每个后端可缓存的空闲连接上限，不是全组总量上限。
- 收益：省去每个请求的 TCP 握手与慢启动开销，在高并发短请求场景下，后端负载与请求时延显著下降。
- 适用边界：用于 http 上下文的 upstream；后端必须支持 HTTP 长连接，连接池才立得起来。

```nginx
upstream app_pool {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;

    # 到每个后端最多缓存 16 条空闲长连接
    keepalive 16;
}
```

> keepalive 数字并非越大越好：缓存的连接越多，占用的后端连接资源越多；实务中按单机并发量估算，16、32、64 是常见的起步值，压测后按需调整。



#### 长连接生效的三件套

keepalive 要真正生效，必须三处配置配合，缺一则连接池形同虚设：keepalive 指令、proxy_http_version 1.1、Connection 头置空。

- keepalive 16：建立连接池本身，声明可缓存的空闲连接数量。
- proxy_http_version 1.1：Nginx 反向代理默认以 HTTP/1.0 与后端通信，而 1.0 语义不支持持久连接，必须显式升到 1.1。
- proxy_set_header Connection "";：清空转发给后端的 Connection 头，避免 close 语义让后端逐请求关闭连接。

```nginx
upstream app_pool {
    server 192.168.1.10:8080;
    keepalive 16;
}

server {
    location / {
        proxy_pass http://app_pool;
        proxy_http_version 1.1;          # 第一件：协议升级到 1.1
        proxy_set_header Connection "";  # 第二件：清空 Connection 头
    }
}
```

> [!IMPORTANT]
> **重要内容**：三件套缺一不可，机理见上文两条解释，也是与第 6 章反向代理参数呼应的高频考点。验证方法：在后端抓包观察连接是否复用，或对比后端 TIME_WAIT 数量在开启前后是否骤降。



### proxy_next_upstream 重试机制

#### 默认重试行为

**proxy_next_upstream 指令**：控制在哪些情形下把当前请求改发给 upstream 组内下一台服务器重试的指令，是负载均衡层容错的关键一环。

- 默认情形涵盖 error 与 timeout：连接建立失败（error）或请求超时（timeout）时，Nginx 自动向下一台节点重试，客户端无感。
- 还可按需加入其他情形，如对特定状态码重试等，具体取值以官方文档为准。
- 配套指令 proxy_next_upstream_tries 限制最多尝试几台节点，proxy_next_upstream_timeout 限制重试总耗时，防止一次请求被无限拉长。

```nginx
location /api/ {
    proxy_pass http://app_pool;
    # 默认即对 error、timeout 重试下一台，可显式写出以示提醒
    proxy_next_upstream error timeout;
    # 最多尝试 2 台、总耗时不超过 5 秒
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 5s;
}
```

> 重试是有代价的：每次重试都意味着前一次尝试已经失败，整体时延被拉长；参数设置要在成功率与延迟之间权衡，不宜盲目放大 tries。



#### 非幂等请求的重试风险

重试默认只作用于幂等安全的请求，把 POST 等非幂等请求纳入重试需要显式加 non_idempotent 参数，而这会带来业务层重复执行的风险。**幂等性**：同一请求执行一次与执行多次，对资源产生的效果相同的性质。

- GET 是幂等的，跨节点重试无害；POST 建订单、扣款等操作不幂等，盲目重试可能造成重复下单、重复扣款。
- Nginx 默认不对非幂等请求跨节点重试，正是因为第一台可能已收到并处理了请求，只是响应没能正常送回。
- 加入 non_idempotent 后 POST 也会重试，风险由业务方自行承担：Nginx 无法知道上一台是否已把业务做了一半。

```nginx
location /order/ {
    proxy_pass http://app_pool;
    # 显式开启后 POST 也会重试，必须先确认业务幂等
    proxy_next_upstream error timeout non_idempotent;
}
```

> [!CAUTION]
> **注意内容**：不要为了提高成功率随意加 non_idempotent：请求可能已在第一台机器上执行成功、只是响应没有送回，重试会造成重复下单、重复扣款等资损事故。开启前必须确认业务接口本身幂等（如以唯一请求号去重），否则保持默认。



### stream 块与四层代理

#### stream 块的定义与位置

**stream 块**：Nginx 用于四层（TCP 与 UDP）代理的配置块，与 http 块平级书写在主配置顶层，互不嵌套、互不影响。

- stream 块处理的是纯粹的 TCP 与 UDP 字节流，不解析应用协议，因此 proxy_set_header、rewrite 等 http 模块指令在这里不可用。
- stream 块内同样用 upstream 定义后端组、用 server 定义监听端口，结构上与 http 块一致，但两者分属不同模块、指令不通用。
- 典型用途：给 MySQL、Redis、消息队列等中间件做统一入口代理与负载均衡。
- 使用前提：确认所用 Nginx 编译包含 stream 模块（开源版自 1.9.0 起提供该模块），否则配置无法识别。

```nginx
# nginx.conf 顶层：stream 与 http 平级
stream {
    upstream mysql_pool {
        server 192.168.1.20:3306;
        server 192.168.1.21:3306;
    }

    server {
        listen 3306;
        proxy_pass mysql_pool;
    }
}

http {
    server {
        listen 80;
        server_name example.com;

        location / {
            return 200 "http 七层入口";
        }
    }
}
```

> 四层代理没有 HTTP 语义，因此没有域名匹配、没有 URI 路由，一个 server 监听一个端口对应一种服务；需要按内容分流的场景只能交给七层，http 块才有这种能力。



#### TCP 代理示例

以代理 MySQL 为例给出一套贴近生产的最小可用配置，并说明与 http 代理的差异。

- 监听端口与后端端口可以不同：客户端连 Nginx 的 13306，Nginx 转发到后端的 3306，对客户端完全透明。
- stream 的 server 块内没有 location、没有 HTTP 头处理，核心只有 listen 与 proxy_pass 等少数指令。
- 生产中常配合 allow 与 deny 指令做来源限制，避免数据库端口对全网开放。

```nginx
stream {
    upstream mysql_pool {
        server 192.168.1.20:3306;
        server 192.168.1.21:3306;
    }

    server {
        listen 13306;

        # 来源白名单：仅允许内网网段访问
        allow 192.168.0.0/16;
        deny all;

        proxy_pass mysql_pool;

        # 与后端建连、会话保持的超时保护
        proxy_connect_timeout 5s;
        proxy_timeout 30m;
    }
}
```

> 速记：stream 与 http 平级，各管一层——stream 管字节流转发，配置项少而快；http 管报文解析，配置项多而强。数据库、缓存类中间件的代理放 stream，网站与 API 的代理放 http。
