## 静态资源服务

### 静态资源服务与 Nginx 的优势

#### 静态资源与动态资源

**静态资源**：请求发生之前内容就已固定、每次请求原样返回相同字节的文件，典型如 HTML、CSS、JavaScript、图片、音视频、字体与下载包。与之成对的是**动态资源**：由程序在请求时刻计算生成的内容，如接口返回的 JSON 数据、实时渲染的页面。

- 常见类型：HTML 入口页、样式与脚本、图片（PNG、JPG、WebP、SVG）、音视频、字体文件、压缩安装包。
- 服务特点：以读文件、发字节为主，业务逻辑极轻，性能瓶颈集中在磁盘 IO 与网络吞吐上。
- 交付要求：高并发接入、低延迟、带宽利用充分、对浏览器缓存友好。

> 静态与动态的划分依据是**内容的生成时机**，而不是文件扩展名。同样是 index.html，预先生成好的是静态资源，由模板引擎在请求时实时渲染的则是动态资源。

> **速记**：静态资源是磁盘上的字节原样发出，动态资源是请求来了才算出来。



#### Nginx 的优势：sendfile 零拷贝

**sendfile 零拷贝**：Nginx 调用操作系统的 sendfile 系统调用发送文件，数据在内核态直接从文件缓冲区流向套接字缓冲区，不经过用户态中转，从而消除了传统读文件再发网络数据的多次拷贝。

- 传统路径：read() 把数据从磁盘读到内核缓冲，再复制到用户态缓冲；write() 又把数据从用户态复制到套接字缓冲——数据被拷贝多次，且伴随用户态与内核态之间的反复切换。
- sendfile 路径：数据全程留在内核态，直接由文件系统缓冲送入网络栈，省去用户态中转的两次拷贝与切换。
- 收益：CPU 占用下降、内存带宽节省，大文件与高并发下载场景提升尤为明显。
- Nginx 中由 sendfile on; 指令开启，默认值为 off。

> 零拷贝的「零」指**消除用户态层面的拷贝**，磁盘到内核缓冲的搬运仍然存在。它的价值不是让磁盘更快，而是让数据从磁盘到网卡的路上少绕路。



#### Nginx 的优势：事件驱动与高并发

**事件驱动**：Nginx 采用 master-worker 架构，每个 worker 进程借助操作系统的多路复用机制（Linux 上的 epoll、BSD 上的 kqueue）同时监听大量连接上的事件，哪个连接有数据可读或可写就处理哪个。

- 传统的一连接一进程或一连接一线程模型，连接数一高，内存与上下文切换开销迅速失控。
- Nginx 的单个 worker 可同时维持数千乃至上万个连接，空闲连接几乎不消耗 CPU。
- 静态资源服务大量连接是**短促而密集**的（请求、响应、关闭），事件驱动模型恰好擅长这种形态。
- **高并发能力**与 **sendfile** 结合，使 Nginx 成为静态站点、CDN 边缘节点与对象存储前置网关的通说首选。

> 一句话定位：sendfile 解决**单次请求发文件有多贵**的问题，事件驱动解决**同时接待大量请求有多贵**的问题，两者叠加构成 Nginx 静态服务的核心竞争力。



### root 与 alias 的路径演算

#### root 指令与整站静态部署

**root 指令**：指定文件的根目录，Nginx 把 root 的值与请求 URI **直接拼接**得到磁盘路径。它是静态站点部署最基本的指令，可在 http、server、location 等上下文使用。

- 拼接规则：磁盘路径 = root 值 + 完整请求 URI。
- 例：root /data/www; 收到 /img/logo.png，实际打开 /data/www/img/logo.png。
- 整站部署的惯用做法：在 server 块中设置 root 与 index，location / 接住全部请求。

```nginx
server {
    listen 80;
    server_name example.com;

    # 整站静态部署：root + index 两板斧
    root /data/www/site;
    index index.html;

    location / {
        # 不再重复写 root，直接继承 server 级配置
        try_files $uri $uri/ =404;
    }
}
```

- try_files $uri $uri/ =404; 的含义：先按文件找，再按目录找，都找不到就返回 404，是静态站的标配兜底。

> root 的拼接是**原样追加**：location 里匹配掉多少它一概不关心，URI 整段接在 root 后面。理解了这一点，root 与 alias 的差异就只剩「要不要拼接 URI」一个变量。

> **速记**：root 是加法，路径 = root + URI。



#### alias 指令与路径替换

**alias 指令**：指定磁盘上的真实路径，用它**替换** location 中被匹配到的那段 URI，而不是与 URI 拼接。适合磁盘目录结构与 URL 路径不一致的场景。

- 替换规则：磁盘路径 = alias 值 + （请求 URI 去掉 location 匹配段之后剩下的部分）。
- 例：location /static/ { alias /data/files/; }，请求 /static/a.png 打开 /data/files/a.png，中间的 static 不会出现在磁盘路径里。
- 若用 root 写同一需求（location /static/ { root /data/files; }），则打开 /data/files/static/a.png，多了一层 static 目录。

```nginx
server {
    listen 80;
    server_name example.com;

    # URL 里的 /static/ 在磁盘上对应 /data/files/
    location /static/ {
        alias /data/files/;
        expires 7d;
    }
}
```

> alias 与 location 的斜杠必须**两头对齐**：location 以斜杠结尾时，alias 的值也应以斜杠结尾，否则替换后会丢掉或多出分隔符，出现 404 或路径错乱。这是实务中最常见的坑。

> **速记**：alias 是替换，把 URL 中匹配到的段落整段换掉。



#### root 与 alias 的对照与选型

两种写法服务同一目标——把 URL 映射到磁盘文件，差别只在路径演算方式，面试与排错都围绕这一点展开。

- **root**：拼接到 URI 之后，磁盘目录需要与 URL 路径结构一致；语义直观，是默认推荐。
- **alias**：替换匹配段，磁盘目录可与 URL 结构完全解耦；适合目录重命名、盘符映射等场景。
- location 为 / 时只能用 root（alias 无匹配段可替换，通说认为会出问题）。
- 正则 location（location ~）中使用 alias 时，alias 的值需借助捕获组完整重写路径，写法更易错，实践中能避则避。

```nginx
# 同一请求 /static/a.png 的两种等价实现：
# 写法一（root）：磁盘上必须有 /data/www/static/a.png
location /static/ {
    root /data/www;
}

# 写法二（alias）：磁盘上文件位于 /data/www/static/a.png 之外的任意处
location /static/ {
    alias /data/assets/;
}
```

> 选型口径：目录结构与 URL 一致就用 root，两者对不上才用 alias。

> **速记**：root 拼、alias 换；root 看开头，alias 看两头斜杠。



### index 与 autoindex 目录列表

#### index 指令与默认首页

**index 指令**：定义请求落到目录上时（URL 以斜杠结尾或指向目录）依次尝试的文件名，命中即返回该文件内容，默认值为 index index.html;。

- 请求 / 实际触发的是对 /index.html 的内部查找，再由内部重定向完成响应。
- 可列多个候选：index index.html index.htm;，按顺序尝试，先命中先用。
- 典型用法：静态站入口、SPA 前端把 index.html 作为唯一入口，配合 try_files 把所有路由回退到它。
- index 指定的可以是相对名（相对当前 root/alias 拼出的目录），也可以写成绝对路径或变量，构成多站点共用首页等高级用法。

```nginx
server {
    listen 80;
    server_name app.example.com;

    root /data/www/dist;
    index index.html;

    # SPA 前端路由：磁盘上不存在的路径一律回退到入口页
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

> index 命中后发生的是一次**内部重定向**：Nginx 按新 URI 重新走一遍 location 匹配。因此 index 指到的文件还可能命中别的 location，这一点在配置复杂站点时需要留意。



#### autoindex 与配套参数

**autoindex 指令**：请求落到目录且没有命中 index 文件时，自动生成一份该目录的**文件列表页**（HTML），取值 on 或 off，默认 off。

- autoindex on;：开启目录列表，浏览器访问目录 URL 即可看到全部文件与子目录。
- **autoindex_exact_size**：列表中文件大小的显示方式，on（默认）显示精确字节数，off 显示 KB、MB 等可读单位。
- **autoindex_localtime**：列表中修改时间的时区，off（默认）显示 GMT 时间，on 显示文件在本机时区的修改时间。
- 三者都只影响列表页的呈现，不影响哪些文件被列出。

```nginx
server {
    listen 80;
    server_name files.internal.example.com;

    # 内网下载站：列出 /data/share 下的全部文件
    location / {
        root /data/share;
        autoindex on;
        autoindex_exact_size off;   # 大小显示为可读单位
        autoindex_localtime on;     # 时间按本机时区显示
    }
}
```

> autoindex 只在**目录请求未命中 index 文件**时生效；若目录下存在 index.html，返回的是该文件而不是列表。想让列表页一定出现，可显式写 autoindex on; 并去掉或改名 index 候选。



#### 目录列表的安全风险

autoindex 会把一个目录的全部内容连同文件名、大小、时间公开给任何能访问到该 URL 的访问者，属于必须谨慎对待的功能。

> [!WARNING]
> **警告内容**：生产环境对外服务严禁随意开启 autoindex。目录列表会暴露站点的完整文件结构，备份文件、源码压缩包、.git 目录、数据库导出、临时脚本一旦躺在被列出的目录里，等于把敏感内容直接递给扫描器；历史上大量数据泄露事件正是从目录列表开始的。

- 部署前先审计目录内容，确保目录里只有打算公开的文件。
- 只在内网下载站、CI 产物预览等封闭场景开启，并配合访问控制（如 allow、deny 或认证）。
- 对外服务确需浏览体验时，考虑由应用层生成白名单式的文件页，而不是让 Nginx 全量列出。

> **速记**：autoindex 是一把开目录的钥匙，开之前先确认门后没有不该给的东西。



### 浏览器缓存控制

#### expires 指令与 Cache-Control

**expires 指令**：为响应添加 Expires 与 Cache-Control 头，控制浏览器把资源缓存多久，适用于 http、server、location 上下文，默认 off（不添加这两个头）。

- expires 7d;：响应带上 Expires（当前时间加 7 天）与 Cache-Control: max-age=604800，浏览器 7 天内不再询问服务器。
- expires -1;：Cache-Control: no-cache，资源仍会被缓存，但每次使用前必须向服务器验证。
- expires epoch;：Expires 固定为 1970 年元旦，等价于明确宣告内容已过期，同样产生 no-cache 语义。
- expires max;：给出极长的过期时间（约十年），用于几乎永不变的资源。
- 时间单位支持 s、m、h、d、w、M、y，可正可负。

```nginx
server {
    listen 80;
    server_name example.com;

    # 图片类资源：缓存 7 天
    location ~* \.(png|jpe?g|gif|webp|svg)$ {
        expires 7d;
    }
}
```

> Cache-Control: max-age 是 HTTP/1.1 标准，优先级高于 HTTP/1.0 时代的 Expires；Nginx 用 expires 指令会同时下发两者，兼容旧客户端。



#### 强缓存与协商缓存

**强缓存**：浏览器在有效期内直接使用本地副本，**完全不向服务器发请求**，由 Cache-Control: max-age 或 Expires 驱动。**协商缓存**：浏览器每次使用缓存前向服务器发一个验证请求，服务器对比后要么回答 304（未变，继续用本地副本），要么返回 200 与新内容。

- 两者都依赖浏览器本地保存副本，差别在于**是否发出验证请求**。
- 强缓存的验证请求次数为零，速度最快，但有效期内服务器改了内容也推不下去。
- 协商缓存每次都发请求，但未变化时响应体为空，仅有 304 状态行与头，开销远小于完整下载。
- 强缓存失效后，协商缓存机制仍可继续兜底，二者是接力关系而非互斥关系。

> 一句话对比：**强缓存不打电话直接用，协商缓存先打电话问一句再决定用不用**。 电话是 304 协商，电话费远低于重新下载。



#### ETag、Last-Modified 与 304 流程

Nginx 对静态文件会**自动生成**两个缓存校验标识：**ETag**（文件的修改时间戳与文件长度编码而成的实体标签）与 **Last-Modified**（文件的最后修改时间），无需任何配置，浏览器与服务器的协商据此完成。

- 首次响应：Nginx 返回 200，响应头自带 ETag 与 Last-Modified。
- 再次请求：浏览器把 ETag 放进 If-None-Match、把 Last-Modified 放进 If-Modified-Since 一并发出。
- 服务器比对：文件未变，则校验头与当前文件一致，返回 **304 Not Modified**，无响应体，浏览器沿用本地副本；文件已变，返回 200 与全新内容以及新的校验头。
- 协商未命中时（资源确实变了），200 响应会携带新的 ETag 与 Last-Modified，开始下一轮缓存周期。

```bash
# 观察协商缓存：第一次拿全量，第二次带校验头拿 304
curl -sI http://example.com/style.css | grep -Ei 'etag|last-modified'
curl -sI -H 'If-None-Match: "67a3f-5d1e2b8c9a1f0"' \
     -H 'If-Modified-Since: Mon, 07 Sep 2026 00:00:00 GMT' \
     http://example.com/style.css
```

> 两个校验头是并用的：If-None-Match 优先级高于 If-Modified-Since，二者一致判定未变才算数。Nginx 的 ETag 由修改时间加长度生成，文件内容变了但时间戳与长度碰巧未变的极端情形通说认为极少出现，可放心依赖。



#### 业界缓存策略惯例

生产环境的通行做法是把资源分成两类分别对待：**带内容 hash 的文件名**走超长强缓存，**入口 HTML** 走不缓存，这是前端工程化与 Nginx 缓存配置配合的标准范式。

- 构建工具产出的 app.3f9c2b.js、main.a1d84f.css 等带 hash 的文件：内容一变文件名就变，可放心配置 expires max 或一年的 max-age，老缓存自然作废。
- 入口 index.html：内容必须每次新鲜，配置 expires -1（no-cache），强制每次都协商验证。
- 效果：回访用户的 HTML 请求很小（304 或直接命中），静态资源从磁盘加载甚至内存加载，体验与带宽双赢。

```nginx
server {
    listen 80;
    server_name example.com;
    root /data/www/dist;

    # 带 hash 的静态资源：超长强缓存
    location ~* \.(js|css|png|jpg|webp|woff2)$ {
        expires max;
        add_header Cache-Control "public, immutable";
    }

    # 入口 HTML：不缓存，每次协商
    location = /index.html {
        expires -1;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

> immutable 是对强缓存的补充声明：告诉浏览器资源在有效期内**连 304 验证都不用发**，配合带 hash 文件名使用，能省掉大量本可避免的再验证请求。

> **速记**：有 hash 放心缓存到底，没 hash（HTML）每次都要验货。



### sendfile 三件套与底层 IO 优化

#### sendfile 指令

**sendfile on;**：启用内核的 sendfile 系统调用发送文件响应，零拷贝原理见本章开头「Nginx 的优势：sendfile 零拷贝」小节，此处聚焦指令用法，默认 off。

- 对小文件同样有效，只是绝对收益不如大文件明显。
- 与 gzip 指令冲突时的处理：需要动态压缩的内容无法走 sendfile 直通路，Nginx 会自动按需切换，无需人工干预。
- 实务中静态站点一律开启，属于事实上的标配。

```nginx
http {
    sendfile on;
}
```

> sendfile off 时 Nginx 用普通的读写路径发文件，功能完全正常，只是白白多付拷贝与切换的成本；on 是纯性能开关，不改变任何语义。



#### tcp_nopush 与 tcp_nodelay

**tcp_nopush** 与 **tcp_nodelay** 是一对作用方向相反的套接字优化指令，配合 sendfile 分别服务大文件整包发送与小包低延迟两类场景，均可用于 http、server、location 上下文。

- **tcp_nopush on;**（默认 off）：在 sendfile 发送文件前等待数据包被填满，把响应头与文件数据尽量攒在同一个包里一次发出，减少包数量，提升大文件吞吐。
- **tcp_nodelay on;**（默认 on）：关闭 Nagle 算法，允许小数据包立即发出，降低交互式小包传输的延迟，对 keep-alive 连接上的零碎响应尤其有意义。
- 两者同时开启并不矛盾：nopush 作用于**文件数据的首发阶段**（攒满再发），nodelay 作用于**其余零碎数据**（有就发），Nginx 官方配置样例中三件套同时开启是常见形态。
- 记忆抓手：nopush 攒大包求吞吐，nodelay 拆小包求延迟。

```nginx
http {
    sendfile      on;
    tcp_nopush    on;
    tcp_nodelay   on;
}
```

> Nagle 算法是 TCP 为提高网络利用率而做的攒包策略：上一个包未被确认前，后续小包先攒着。它利于带宽、不利于延迟，因此交互式连接默认用 tcp_nodelay 关掉它。



#### aio 与 directio

**aio** 与 **directio** 是 Nginx 面向大文件与高负载磁盘场景的两个进阶 IO 指令，理解其定位即可，日常静态站不必默认开启。

- **aio on;**：启用异步文件读，worker 把耗时的磁盘读取交给操作系统的异步接口，读盘期间不阻塞事件循环，适合大文件、磁盘较慢或读请求密集的场景；平台相关（Linux 上常配合线程池使用）。
- **directio off|size**（默认 off）：对超过指定大小的文件绕过操作系统页缓存，直接以对齐方式读写磁盘，避免大文件把页缓存里热数据挤出去；适用于以大文件下载为主、页缓存珍贵的场景。
- 两者的共同点都是**为大文件让路**：一个让读盘不堵住事件循环，一个不让大文件污染页缓存。
- 日常小型静态资源仍走页缓存加 sendfile 的常规路径，性能已足够。

> [!TIP]
> **建议内容**：先量后调。常规静态站只开 sendfile 三件套即可；只有在监控发现磁盘 IO 或页缓存成为瓶颈、且确有大文件分发需求时，再评估开启 aio 与 directio，并按 nginx.org 官方文档核对所在平台的限制（如 Linux 上 aio 与 sendfile 对某些文件的配合约束）。



### 大文件与断点续传

#### Range 请求与 206 Partial Content

**Range 请求**：客户端通过请求头 Range 要求服务器只返回文件的某个字节区间，Nginx 对静态文件**原生支持**该能力，命中时返回 **206 Partial Content** 与对应区间的数据，这是下载工具断点续传与视频拖动播放的底层机制。

- 请求示例：头 Range: bytes=0-1048575 表示要前 1 MB，响应状态 206，附 Content-Range: bytes 0-1048575/9216000 说明区间与总长。
- 客户端不发 Range 头时，Nginx 返回完整 200 与整个文件，行为不变。
- 断点续传的流程：下载中断后，客户端以 Range: bytes=已收字节数- 续传，服务端返回剩余部分。
- 视频拖动依赖同一机制：播放器按需请求任意区间的字节，不必下载完整视频。
- 多区间请求（bytes=0-99,200-299）Nginx 也支持，响应使用 multipart 格式，实务中少见。

```bash
# 请求文件前 1024 字节，观察 206 与 Content-Range
curl -sI -H 'Range: bytes=0-1023' http://example.com/big-package.zip
```

> 断点续传与 206 是一套机制的两面：**续传就是一次从断点开始的 Range 请求**。Nginx 无需任何配置即支持，运维侧要做的是别把 Range 头在代理层意外丢掉。



#### max_ranges 与范围数控制

**max_ranges 指令**：限制单个请求允许的字节区间数量，取值为数字，默认 0 表示不限制，适用于 http、server、location 上下文。

- 取 0（默认）：区间数量不限，多区间请求全部受理。
- 取正整数 n：超过 n 个区间的请求被整体拒绝，按无 Range 头处理或返回 416。
- 设 1：只允许单区间请求，即标准的断点续传形态，可挡住用大量小区间消耗资源的滥用。
- 相关的还有 max_range_size（单个区间最大字节数）等指令，均属于对 Range 能力的精细化约束。

```nginx
location /download/ {
    root /data/packages;
    max_ranges 1;   # 只接受单区间请求，满足续传且抑制滥用
}
```

> [!NOTE]
> **提醒内容**：Range 能力默认打开且不限制区间数，绝大多数站点无需调整；只有下载站、视频站等大文件分发场景，才值得用 max_ranges 一族指令做防滥用约束。

> **速记**：Range 要区间，206 给区间，max_ranges 限区间个数。



### 防盗链

#### valid_referers 指令

**valid_referers 指令**：声明哪些 Referer 来源算作合法，命中的请求 $invalid_referer 变量为空（假），未命中的为 1（真），它是 Nginx 防盗链判断的唯一开关，适用于 http、server、location 上下文。

- none：允许没有 Referer 头的请求（直接在地址栏打开、部分 App 内嵌页）。
- blocked：Referer 头存在但值不是规范的 http:// 或 https:// 开头（被代理或防火墙处理过）。
- server_names：Referer 中的主机名与当前 server_name 或虚拟主机名匹配，即本站自己。
- 任意字符串与通配：如 *.example.com，命中即合法。
- 正则：以波浪号开头的正则表达式，灵活匹配复杂来源。

```nginx
server {
    listen 80;
    server_name example.com;

    location ~* \.(png|jpe?g|gif|webp)$ {
        # 本站自身、无 Referer、被抹除的 Referer 均视为合法
        valid_referers none blocked server_names
                       *.example.com example.com;
        if ($invalid_referer) {
            return 403;
        }
        expires 7d;
    }
}
```

> valid_referers 本身不做任何拦截，它只负责给 $invalid_referer 变量打分；真正的拒绝动作由 if 配合 return 或 rewrite 完成，两条指令必须成套出现。



#### 配合 if 拦截无效引用

$invalid_referer 为真时执行什么动作，决定了盗链请求的下场，常见做法是返回 403 禁止访问，或重写到一张占位图。

- return 403;：直接拒绝，最简单也最常用。
- rewrite ^ /hotlink-placeholder.png;：把图片请求重写到本地一张水印占位图，对体验更友好，也能反向宣传版权。
- 作用域建议收窄到图片、视频等易被盗链的资源类型 location，避免误伤正常页面请求。
- 白名单内要放行 none：搜索引擎与大量移动端场景不带 Referer，全禁 none 会误伤真实流量。

```nginx
# 重写方案：盗链请求替换为占位图
location ~* \.(png|jpe?g)$ {
    valid_referers none blocked server_names *.example.com;
    if ($invalid_referer) {
        rewrite ^ /assets/hotlink-placeholder.png permanent;
    }
}
```

> Referer 是客户端**自愿上报**的头，脚本、浏览器插件与抓包工具都可以随意伪造或抹除它。所以防盗链的定位要说清：**Referer 校验只能挡住直接外链的君子，挡不住蓄意伪造的小人**；真正的资产保护要靠签名 URL、时效令牌或鉴权接口。

> [!TIP]
> **建议内容**：防盗链与Referer 校验只是第一道廉价防线，重要资源建议叠加带时效的签名 URL（校验过期时间与签名参数），既防直链也防伪造，Nginx 可借助 secure_link 模块或应用层生成令牌实现。

> **速记**：valid_referers 打分，$invalid_referer 判罚，403 或重写定下场；防线挡君子，签名挡小人。



### 动静分离

#### 动静分离的定义与价值

**动静分离**：在同一个 Nginx 入口下，把静态资源请求与动态接口请求拆分到不同 location，分别交给文件系统与应用服务器处理。它与反向代理分工配合——静态走本地文件，动态走 proxy_pass 转发给上游（详见第 6 章反向代理）。

- 拆分依据：请求路径或扩展名，如 /static/ 与 /api/ 各占一个 location。
- 价值一：静态请求不占用应用服务器的进程与连接，应用只处理业务。
- 价值二：两类流量可独立调优，静态侧上缓存与 sendfile，动态侧调超时与缓冲。
- 价值三：故障隔离与扩容独立，静态资源可推 CDN，应用可水平扩容，互不牵连。

> 动静分离的判断顺序是**先分层再分流**：入口 Nginx 先把流量按动静切开，动态一侧再做上游转发。只做代理不做分离，等于让应用服务器继续兼职工文件搬运工。



#### 典型动静分离配置

同一 server 块内，静态资源 location 直接服务文件，API location 反向代理到后端应用，剩余请求交给前端入口页，三者各司其职。

```nginx
server {
    listen 80;
    server_name example.com;

    # 静态资源：本地文件 + 长缓存
    location /static/ {
        alias /data/www/static/;
        expires 7d;
    }

    # 动态接口：反代到后端应用
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 其余请求：前端 SPA 入口
    location / {
        root /data/www/dist;
        index index.html;
        try_files $uri $uri/ /index.html;
    }
}
```

- /static/ 与 /api/ 的前缀精确切开两类流量，location / 兜住页面路由。
- 静态侧可继续叠加 expires、防盗链等本章配置，动态侧衔接第 6 章的代理参数。

> location 匹配遵循最长前缀优先等规则，/api/ 必须写在能覆盖其路径的位置；配置变更后用 nginx -t 验证语法、nginx -s reload 平滑生效，是动静态改造的标准收尾动作。

> **速记**：一个入口、三个出口——静态给文件、动态给上游、其余给前端。
