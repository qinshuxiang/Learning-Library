## 配置文件结构与指令语法

### 配置文件的层级结构

Nginx 配置文件是一个**单根的嵌套结构**：所有指令都挂在唯一的根层级之下，逐层向内收缩作用范围。理解每一层管什么，是读懂任何一份 nginx.conf 的前提。

#### 五层结构与其职责

**层级结构**：Nginx 配置由外向内分为 **main（全局块）**、**events 块**、**http 块**、**server 块**、**location 块** 五层，外层块包住内层块，内层指令只作用于更小的请求范围。

- **main（全局块）**：配置文件最外层、未被任何花括号包裹的部分，配置与业务无关的进程级参数，如 user、worker_processes、error_log、pid。
- **events 块**：配置网络连接事件相关的全局参数，如每个 worker 的最大连接数 worker_connections，整个配置文件只能有一个。
- **http 块**：所有 HTTP 服务相关配置的容器，如 mime 类型引入、日志格式、sendfile、keepalive_timeout、gzip，以及一个或多个 server 块。
- **server 块**：一台**虚拟主机**，由 listen 与 server_name 界定它响应哪些请求，内部再按 URI 划分 location。
- **location 块**：针对某一类 URI 的处理规则，静态文件定位（root、alias）、反向代理（proxy_pass）、重写（rewrite）都定义在这里。

> 作用范围从外向内逐层收窄：main 管进程、events 管连接、http 管协议、server 管站点、location 管路径。除 http 外，Nginx 还有与 http 平级的 mail、stream 等顶层块，分别服务邮件代理与四层 TCP/UDP 代理，个人 Web 场景以 http 块为主。



#### 各层允许出现哪些指令

每条指令都有明确的合法层级，写错层级时 nginx -t 会直接报 directive is not allowed here 一类错误，配置根本无法生效。

- worker_connections 只能写在 events 块；listen 与 server_name 只能写在 server 块。
- root 可写在 http、server、location 三层，越靠外生效范围越大。
- 大多数 http 指令遵循 http 允许、server 允许、location 允许的梯度逐层放开，个别指令被限定在单一层级。

> [!TIP]
> **建议内容**：不确定某条指令能写在哪一层时，直接查 nginx.org 官方文档中该指令的 Context 一行，它是层级问题的唯一权威依据；写完后用 nginx -t 即可当场验证。



#### nginx.conf 默认文件逐段解读

以下是一份带完整解读注释的默认配置（结构与官方编译安装生成的 nginx.conf 一致）：

```nginx
# ===== 全局块（main 层）=====
#user  nobody;                  # worker 进程运行身份，注释表示使用默认
worker_processes  1;            # worker 进程数，生产环境常写 auto（等于 CPU 核数）

#error_log  logs/error.log;     # 全局错误日志与级别
#error_log  logs/error.log  notice;
#pid        logs/nginx.pid;     # 主进程号文件

events {                        # events 块：整个文件仅一个
    worker_connections  1024;   # 每个 worker 可同时维持的连接数
}

http {                          # http 块：HTTP 服务总容器
    include       mime.types;   # 引入扩展名到 Content-Type 的映射表
    default_type  application/octet-stream;   # 查表失败时的默认响应类型

    #log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
    #                  '$status $body_bytes_sent "$http_referer" '
    #                  '"$http_user_agent" "$http_x_forwarded_for"';
    #access_log  logs/access.log  main;

    sendfile           on;      # 启用高效的文件发送方式
    keepalive_timeout  65;      # 长连接空闲超时秒数
    #gzip  on;

    server {                    # server 块：一台虚拟主机
        listen       80;        # 监听 80 端口
        server_name  localhost; # 该主机响应的域名

        #charset koi8-r;

        location / {            # 匹配所有以 / 开头的请求（兜底）
            root   html;        # 静态文件根目录
            index  index.html index.htm;   # 目录默认页
        }

        #error_page  404              /404.html;

        error_page   500 502 503 504  /50x.html;   # 错误码内部重定向到错误页
        location = /50x.html {  # 精确匹配错误页本身
            root   html;
        }
    }
}
```

- 全局块定了进程与日志，events 块定了连接容量，http 块定了协议层公共参数。
- server 块给出唯一一台默认虚拟主机，先保证首页与错误页能返回。
- 生产环境通常把 server 块拆到独立文件，用 include 汇入主文件。

> root html 是相对路径，相对于编译安装时指定的前缀目录（官方默认为安装目录下的 html 子目录），而不是磁盘根目录；排查静态文件 404 时先确认相对路径的基准点。



### 指令与注释的语法

Nginx 配置只有两种语句形态：以分号结束的**简单指令**，与以花括号划定范围的**块指令**；再辅以 # 注释，全部语法即此。

#### 简单指令与块指令

**简单指令**：指令名后接零到多个**参数**、以**分号**结束的单行语句；**块指令**：指令名（可带参数）后跟**花括号**，花括号内继续包含简单指令或更内层的块指令。

```nginx
worker_processes  auto;          # 简单指令：指令名 + 参数 + 分号

http {                           # 块指令：花括号划定作用域
    include       mime.types;    # 花括号内可以继续嵌套
    server {
        listen       80;
        location / {
            root   html;
        }
    }
}
```

- 参数之间以**空白字符**分隔，个数与含义由指令自身定义。
- 块指令的花括号之后不写分号，分号只属于简单指令。
- 同一条指令在允许的层级可以出现多次，多次出现是叠加还是替换取决于指令类型（数组型指令见下文继承一节）。

> 最常见的语法错误是漏写分号，报错信息中出现 expecting 分号一类字样，且报错行号往往指向漏写分号那一行的下一行，排查时应往前看一行。



#### 注释的写法

**注释**：以 # 开头、延伸到行尾的内容，解析阶段被整体忽略，不参与任何语义。

```nginx
# 整行注释：说明下一行配置的用途
worker_processes  auto;   # 行尾注释：官方文件习惯在指令后空两格再写
```

- 注释与删除等效，官方默认文件用注释保留大量可选配置供按需启用。
- 注释不能插在指令参数的中间，一行内 # 之前的内容仍然有效。



#### 单参数与多参数指令

指令按参数个数分为**单参数**与**多参数**两类，多参数指令的各参数按固定顺序解释。

```nginx
worker_processes  auto;                     # 单参数
pid  logs/nginx.pid;                        # 单参数：文件路径

listen       80;                            # 单参数
error_page   500 502 503 504  /50x.html;    # 多参数：前四个是错误码，最后是目标 URI
index        index.html index.htm;          # 多参数：依次尝试的默认页
log_format   main  '$remote_addr - $request';   # 参数二为格式名，参数三为带引号的格式串
```

- 引号包裹的参数内部空格不作为分隔符，日志格式串是典型用法。
- 参数中的反斜杠用于转义正则特殊字符，常见于 server_name 正则与 rewrite 模式。



### include 指令与 mime.types

#### include 指令

**include**：在书写位置原样插入另一个文件的配置内容，支持通配符展开，是拆分配置文件的唯一手段。

```nginx
http {
    include       mime.types;                # 相对路径：相对配置目录
    include       /etc/nginx/conf.d/*.conf;  # 绝对路径 + 通配符
}
```

- 相对路径相对于编译时确定的配置目录，发行版包通常为 /etc/nginx。
- 通配符命中的文件按文件名字母序展开，展开结果与手写在原处完全等效。
- 拆分的动机：主文件只保留骨架与公共参数，每个站点、每个上游独立成文件，改动互不牵连，也便于版本管理。

> [!NOTE]
> **提醒内容**：新增站点文件后请求不通的第一步排查，是确认文件名落在 include 通配符的覆盖范围内（如扩展名是否为 conf），再用 nginx -T 查看 include 展开结果。



#### mime.types 与响应类型

**mime.types**：Nginx 自带的**扩展名到 Content-Type 的映射表**，是每个静态响应头 Content-Type 的直接来源。

```nginx
# mime.types 文件内部即一个 types 块，节选如下
types {
    text/html                 html htm shtml;
    text/css                  css;
    application/javascript    js;
    application/json          json;
    image/png                 png;
    application/octet-stream  bin exe dll;
}
```

- 请求 /style.css 时按扩展名 css 查表，得到 text/css 写入响应头。
- 浏览器依据 Content-Type 决定渲染、播放还是下载，与文件实际内容无关。
- 类型映射独立成文件的原因：映射条目庞大、与业务无关，独立文件便于整体升级与复用，主配置得以保持精简。



#### default_type 的作用

**default_type**：当扩展名在 types 表中查不到时使用的兜底响应类型，默认值为 application/octet-stream。

- octet-stream 表示未知二进制流，浏览器的默认动作是下载而非渲染。
- 无扩展名的接口文件、脚本动态生成的响应都可能落到该兜底。
- 需要时可在自己的配置里再写一个 types 块补充映射，不必改动 mime.types 本身。

> [!WARNING]
> **警告内容**：给网站新增一种静态资源后出现浏览器直接下载而不是渲染，多半是该扩展名未收录进 mime.types，响应被 default_type 兜底成了 octet-stream；补上映射即可修复。



### 指令的继承与覆盖

#### 继承与覆盖的基本规则

**继承**：内层块未显式写出某指令时，自动沿用外层同名指令的值；**覆盖**：内层块显式写出同名指令时，以内层为准，与外层取值无关。

```nginx
http {
    access_log  /var/log/nginx/access.log;

    server {
        # 本层未写 access_log：继承 http 层配置
        location /api/ {
            access_log  /var/log/nginx/api.log;   # 显式覆盖
        }
    }
}
```

- 继承只发生在父子层级之间，方向永远是外向内，内层配置不会影响外层。
- 覆盖是**整条替换**：内层写了就与外层彻底无关，不存在合并。
- 阅读配置时先问两个问题：这条指令处在哪一层、本层是否显式写了。

> **绝大多数指令遵循上述简单继承语义**；例外是数组型指令，它们的继承单位是层而不是条，见下一考点。



#### 数组型指令的继承陷阱

**数组型指令**：允许在同一层级重复出现、取值叠加生效的指令，典型如 add_header、allow、deny、proxy_set_header。

**数组型指令的继承以层为单位：内层只要出现任意一条，外层同名的整组指令即全部失效，而不是逐条合并。**

```nginx
server {
    add_header  X-Frame-Options  SAMEORIGIN;   # 对下面两个 location 的差异：

    location /a/ {
        # 本层没有 add_header：继承 X-Frame-Options，生效
    }

    location /b/ {
        add_header  X-Cache  HIT;   # 本层出现了一条：X-Frame-Options 在此失效
    }
}
```

> [!WARNING]
> **警告内容**：这是 Nginx 配置最高频的坑之一：只想给某个 location 加一条响应头，结果它连外层配置的安全头（如 X-Frame-Options、Content-Security-Policy）一并丢失。修复办法是把需要保留的外层数组指令在该 location 内完整抄写一遍；allow、deny、proxy_set_header 的行为与此相同。



### 变量体系

**变量**：Nginx 在请求处理过程中求值的命名值，全部以 $ 开头，可嵌入指令参数的任意位置；内置变量之外还可通过 set 与 map 自建。

#### 常用内置变量

常用内置变量逐个定义如下：

- **$host**：请求的目标域名，依次取请求行中的主机名、Host 头的主机部分、命中的 server_name，**不含端口**。
- **$http_host**：请求头 Host 的原始完整值，**含端口**。
- **$uri**：当前请求的规范化 URI，**不含参数、已解码**，会被 rewrite 与内部重定向改写。
- **$request_uri**：客户端发来的**原始完整 URI，含参数、未解码**，整个请求生命周期内永不改变。
- **$args**：URL 中问号后的参数串，同义变量为 $query_string。
- **$is_args**：有参数时为 ?，无参数时为空字符串，几乎总与 $args 搭配使用。
- **$remote_addr**：客户端地址；未部署 realip 模块改写时即直连对端地址。
- **$scheme**：请求协议，值为 http 或 https。
- **$request_method**：请求方法，如 GET、POST。
- **$request_filename**：按当前 root 或 alias 计算出的最终文件完整路径。
- **$document_root**：当前请求生效的 root 或 alias 指令值。

> $host 与 $http_host 的差别是高频细节：$host 去掉端口且取值有三级兜底，$http_host 原样保留请求头。构造跳转地址、缓存键优先用 $host；需要完整还原 Host 头转发给上游时用 $http_host。



#### $uri 与 $request_uri 的区别

**$uri**：随 rewrite 与内部重定向**变化**的当前值；**$request_uri**：请求进入时固定、**永不变化**的原始值。两者的差异在三个维度上展开：

- 是否含参数：$uri 不含；$request_uri 含完整参数串。
- 是否解码：$uri 已完成百分号解码并规范化；$request_uri 保持客户端发来的原样字节。
- 是否被改写：rewrite、try_files 兜底跳转、error_page 内部重定向都会更新 $uri；$request_uri 始终不变。

```nginx
location /old/ {
    rewrite ^/old/(.*)$ /new/$1 last;   # 跳转后 $uri 变为 /new/...
}

location /new/ {
    return 200 "uri=$uri request_uri=$request_uri";
}

# 请求 /old/page?id=1 的响应：
# uri=/new/page request_uri=/old/page?id=1
```

**$uri 回答当前处理到哪一步的什么地址，$request_uri 回答用户当初到底请求了什么；文件定位与前缀判断用 $uri，日志还原与上游透传用 $request_uri。**



#### set 指令自定义变量

**set**：创建或改写一个自定义变量的指令，属于 rewrite 模块，可写在 server、location 与 if 块中。

```nginx
location /api/ {
    set $backend "127.0.0.1:8080";
    proxy_pass http://$backend;
}
```

- set 的第一个参数是变量名（带 $），第二个参数是取值，取值本身可以引用其他变量。
- Nginx 变量是**惰性求值**的：set 只登记映射关系，真正求值发生在变量被使用的那一刻。
- set 的执行时机受请求处理阶段约束，先后顺序问题见下一章请求处理阶段。



#### map 指令按映射生成变量

**map**：以一个源变量的取值查表，生成一个新变量，写在 http 块，是按条件生成配置值的标准做法。

```nginx
http {
    map $http_upgrade $connection_upgrade {
        default upgrade;
        ''      close;
    }

    server {
        location /ws/ {
            proxy_pass http://127.0.0.1:8080;
            proxy_http_version 1.1;
            proxy_set_header Upgrade    $http_upgrade;
            proxy_set_header Connection $connection_upgrade;   # 按映射结果取值
        }
    }
}
```

- 上例是 WebSocket 代理的经典搭配：客户端带 Upgrade 头时 Connection 置为 upgrade，否则置为 close。
- 映射值支持 default 兜底、精确字符串与正则（~ 区分大小写、~* 不区分大小写）。
- map 同样惰性求值，结果变量没被用到就不计算。
- map 只能写在 http 块，不能写进 server。



### server_name 与虚拟主机

#### 三种虚拟主机类型

**虚拟主机**：同一台 Nginx 通过区分请求特征，对外表现为多个互相独立的站点。按区分维度分三类：

- **基于域名**：同一 IP、同一端口，靠请求头 Host 中的域名区分 server 块，是互联网站点的主流方式。
- **基于端口**：同一 IP 上不同 listen 端口对应不同站点，常见于 80 对外、8080 放管理后台。
- **基于 IP**：服务器持有多个 IP 地址，不同 listen 地址对应不同站点，多用于内外网隔离场景。

```nginx
http {
    server {                       # 基于域名：站点一
        listen       80;
        server_name  blog.example.com;
    }

    server {                       # 基于域名：站点二
        listen       80;
        server_name  api.example.com;
    }

    server {                       # 基于端口
        listen       8080;
        server_name  admin.example.com;
    }
}
```



#### server_name 的匹配优先级

**server_name**：声明当前 server 块响应哪些域名，可写多个名字、支持通配符与正则。多个 server 监听同一地址端口时，按以下顺序选定：

1. **精确名**：完整写出的域名，如 api.example.com，优先级最高。
2. **前缀通配**：以星号开头的名字中取最长者，如 *.example.com。
3. **后缀通配**：以星号结尾的名字中取最长者，如 mail.*。
4. **正则**：以 ~ 开头的名字，按配置文件书写顺序取第一个命中的。
5. **default_server**：以上全部未命中时交给默认主机；无显式标记时取监听同地址端口的第一个 server。

```nginx
server {
    listen       80;
    server_name  example.com  www.example.com;   # 精确名，可并列多个
}

server {
    listen       80;
    server_name  *.example.com;                  # 前缀通配
}

server {
    listen       80;
    server_name  ~^api\.\d+\.example\.com$;      # 正则名
}
```

> 通配符只能出现在名字的开头或结尾、且紧邻点号；*.example.com 不仅匹配 www.example.com，也匹配多级子域如 a.b.example.com。写法 .example.com 是精确名 example.com 与通配 *.example.com 的合并简写。



#### default_server 的兜底语义

**default_server**：listen 指令的可选参数，把当前 server 指定为该地址端口的默认主机，承接所有未命中 server_name 的请求。

- 同一地址端口上不写该标记时，第一个被读取的 server（include 按文件名字母序展开）充当默认。
- 经典用途：对未绑定到本站的域名扫描与恶意 Host 请求直接断开。

```nginx
server {
    listen       80  default_server;
    server_name  _;          # 一个不会匹配任何真实域名的占位名
    return       444;        # Nginx 特殊状态码：不发送响应直接关闭连接
}
```

> [!IMPORTANT]
> **重要内容**：server_name _ 本身没有任何通配含义，它只是一个不可能匹配的占位串；真正起作用的是 listen 上的 default_server 标记，两者必须成对出现才有兜底效果。



### listen 指令

#### listen 的监听形式

**listen**：声明 server 块监听的地址与端口，只能写在 server 块，是请求进入虚拟主机的入口。

```nginx
listen 80;                        # 只写端口：监听所有 IPv4 地址的 80 端口
listen 127.0.0.1:8080;            # 地址 + 端口：仅本机回环可访问
listen [::]:80;                   # IPv6 地址写进方括号
listen unix:/var/run/nginx.sock;  # unix 套接字：仅本机进程可连接
```

- 只写端口等价于监听 0.0.0.0 的该端口。
- unix 套接字用于同机反向代理，省去 TCP 栈开销，需注意套接字文件的属主与权限。
- 地址端口组合相同的多个 server 才会互相竞争 server_name 匹配；端口不同则天然分流。



#### listen 的常用附加参数

listen 在监听地址之外还可挂载多个附加参数，用来指定默认主机、启用 TLS 或调整连接队列。

- **default_server**：该地址端口的默认主机标记。
- **ssl**：在该监听上启用 TLS，对外提供 HTTPS 服务。
- **backlog**：内核等待队列长度上限，高并发场景可调大。

```nginx
listen 443 ssl default_server;
```

> [!TIP]
> **建议内容**：HTTPS 站点的常见做法是同时保留 80 与 443 两个 server：443 承载业务，80 只做一条 301 跳转到 https，跳转地址用 $host 拼接以适配多域名。



### 配置校验与生效

#### nginx -t 与 -T

**nginx -t**：只做配置文件语法与语义检查，不改变运行中的服务；**nginx -T**：在检查之外把 include 展开与继承合并后的**最终生效配置**整体输出到标准输出。

```bash
nginx -t                            # 检查默认配置文件
nginx -t -c /etc/nginx/nginx.conf   # 检查指定路径的配置
nginx -T | grep -n "server_name"    # 输出合并结果并检索，确认改动真的会被加载
```

- -t 的通过标准是输出 syntax is ok 与 test is successful 两行。
- -T 是排查配置是否真的被读到的利器：include 展开与继承合并后的结果一目了然。
- 固定流程为三步：改配置、nginx -t、通过后 reload，缺一不可。



#### reload 的正确姿势

**reload**：让主进程重新读取配置而不中断服务的操作：主进程先校验新配置，通过后拉起新 worker，再通知旧 worker 处理完存量连接后退出。

```bash
nginx -t && nginx -s reload   # 命令行方式
systemctl reload nginx        # systemd 方式，效果等同
```

- reload 与 restart 的区别：reload 平滑换配置、不断连接；restart 整体停止再启动，会出现服务空窗。
- reload 失败时旧配置继续生效，服务不受影响，但错误只体现在命令输出与错误日志中。

> [!CAUTION]
> **注意内容**：不要用直接杀主进程的方式强制生效，也不要在配置有错的情况下反复 reload；每次改动后先 nginx -t 再 reload，是保证服务不中断的最小纪律。



#### 改配置不生效的常见原因

排查时建议从近到远逐项排除：

- 忘记执行 reload，或 reload 因权限不足而失败。
- 改错了文件：conf.d 与 sites-enabled 存在同职责的冲突文件，或站点文件名不符合 include 通配符（如扩展名不是 conf）。
- server_name 被抢先：另一个 server 监听同端口且名字匹配优先级更高（精确名压过通配，通配压过正则）。
- 请求进了别的 location：正则 location 按书写顺序抢在目标前缀之前命中。
- 客户端侧缓存：浏览器缓存、CDN 缓存返回旧内容，与服务端配置无关。
- 请求根本没到达本机：DNS 未指向、防火墙或云安全组未放行端口。

> [!TIP]
> **建议内容**：排查路径固定化：先 curl -I http://127.0.0.1 在本机直接验证服务端行为，排除网络与缓存因素；再 nginx -T 确认配置已合并生效；最后核对 server_name 与 location 的匹配归属。
