## 分布式锁选型对比

### 锁的问题域

#### 为什么单机锁失效

**分布式锁**：多个进程实例互斥访问共享资源时（防重复任务、防并发超卖），单机语言级锁只锁住本进程，必须借助外部组件让「多个机器看见同一把锁」。

- 典型场景：定时任务多实例部署只允许一份执行（Node 主题的 cluster 是单机多进程，跨机器失效）；秒杀扣减前的资源预占；缓存重建防击穿（Redis 主题第 25 章的场景）。
- 本质要求：锁状态存放在**所有实例共享的第三方**（Redis、etcd、MySQL），加锁与释放是原子的。

> 先自问一句「**真的需要锁吗**」：多数并发写冲突可以用第 5 章的幂等与乐观锁（唯一约束、版本号）在数据库层化解，锁是它们不够用时的第二选择——数据库方案天然无锁服务依赖，能兜底就不要多引一个组件。

**速记**：锁状态必须在 **共享第三方**，但先想想唯一约束和乐观锁够不够。



### Redis 锁

#### SET NX PX 与安全释放

**Redis 单实例锁**：`SET key value NX PX 30000` 一条命令原子地完成「不存在才写入＋过期时间」，是 Redis 锁的标准加锁姿势。

```js
const { v4: uuid } = require("uuid");
const token = uuid();                       // 锁标识：谁加的锁谁释放
const ok = await redis.set("lock:job", token, "NX", "PX", 30000);
if (!ok) return;                            // 没抢到

try {
  await runJob();
} finally {
  // Lua 保证「比对标识＋删除」原子执行，防止误删他人的锁
  const script = `if redis.call("get", KEYS[1]) == ARGV[1]
    then return redis.call("del", KEYS[1]) else return 0 end`;
  await redis.eval(script, 1, "lock:job", token);
}
```

- **必须带过期时间**：持有者崩溃后锁能自动释放，否则死锁。
- **释放必须验标识**：不能拿到就 DEL——业务超时后锁已过期、被他人持有，无脑 DEL 是删了别人的锁。
- **续期问题**：业务比过期时间长，锁提前失效。看门狗模式（持有期间定时续期）可解，引入复杂度；先评估业务能否拆小。

> 「SET NX＋验标识释放」能防住绝大多数事故，但它的安全边界要清楚：**主从异步复制下，主库加锁成功、还没同步给从库就宕机，新主上锁不存在**，另一个实例会加锁成功——两个持有者并存。这正是 Redlock 论战的核心场景（Redis 主题第 27 章）。

**速记**：`SET NX PX`＋**Lua 验标识释放**＋过期兜底，主从切换是它的安全边界。



#### Redlock 与其他组件

**Redlock**：向 N 个独立 Redis 主节点同时加锁，半数以上成功且耗时小于锁有效期才算持有——用多个独立实例对冲单点的不确定性。

- 争议（Martin Kleppmann 与 antirez 的论战，见 Redis 主题第 33 章）：Redlock 依赖时钟假设，进程暂停、网络延迟下仍可能出现两个持有者。
- **务实结论**：要求极高正确性的互斥（资金类），锁只做「效率优化」不做「正确性保证」——正确性交给数据库唯一约束或版本号兜底（第 5 章）。
- **etcd / ZooKeeper 锁**：基于共识协议（第 2 章），租约自动释放、会话断开即失锁，一致性强于 Redis 锁，代价是吞吐低、运维重。

| 方案 | 一致性强度 | 吞吐 | 依赖 | 适用 |
|---|---|---|---|---|
| Redis 单实例锁 | 中（主从切换有窗口） | 极高 | Redis（已有） | 常规防重任务、缓存重建 |
| Redlock | 中高（有争议） | 高 | 多个独立 Redis | 多实例 Redis 的强需求场景 |
| etcd / ZK 锁 | 强 | 中 | 共识集群 | 会话感知、强互斥要求 |
| MySQL 唯一键 | 强 | 低 | MySQL（已有） | 低频任务、零新组件 |

**警告内容**：分布式锁的失效模式是**静默的双持有**——两个实例同时认为自己在持锁，没有报错、只有数据错乱。所以生产铁律是：**锁只能挡重复，不能保正确**；正确性永远由幂等（唯一约束/乐观锁）兜底，锁之上再叠加一层兜底，两道防线各自独立生效。

**速记**：常规场景 **Redis 单实例锁**，强一致 **etcd/ZK**，零依赖 **MySQL 唯一键**，锁不保正确、幂等才保。
