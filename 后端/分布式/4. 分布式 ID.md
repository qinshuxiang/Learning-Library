## 分布式 ID

### 需求与约束

#### 为什么自增主键不够用

**分布式 ID**：多库多服务的环境下，为每条数据分配全局唯一标识——分库分表后自增主键在各片必然重复（见 MySQL 主题第 40 章）。

- **四个基本要求**：全局唯一；**趋势递增**（保住 InnoDB 主键的顺序插入，随机主键导致页分裂与缓存劣化，见 MySQL 主题第 35、36 章）；高可用（ID 服务挂了整个写入链路停摆）；信息安全（连续 ID 会泄露单量，订单号类 ID 需要跳变）。
- UUID（v4）满足唯一但**完全无序**，36 字符长且索引不友好，只适合日志追踪类场景，不适合做数据库主键。

> 趋势递增不是洁癖，是 **InnoDB 的存储特性决定的**：主键乱序插入会把新行塞进页中间，触发页分裂；单调插入则永远追加在尾部，写入快、页利用率高。分布式 ID 方案的分水岭就在「能不能保住顺序性」。

**速记**：分布式 ID 四要求 **唯一、趋增、高可用、不泄密**，UUID 乱序不宜做主键。



### 主流方案

#### 号段模式：数据库发号

**号段模式**：每次从数据库批量取一段 ID（如 1 万个）缓存在服务内存里，用完再取下一段，数据库压力被批量摊薄。

- 实现：一张发号表存当前最大值，服务用 `UPDATE id_alloc SET max_id = max_id + 10000` 抢号段，拿到的区间在内存内自增分配。
- 优点：实现极简、ID 严格趋势递增、强依赖只有一个数据库。
- 缺点：服务重启浪费未用完的段；DB 恢复期间发号会中断——**双 buffer 预取**（用到 10% 时异步取下一段）可平滑过渡。
- 美团 Leaf 的号段模式是该方案的成熟参考实现。

> 号段模式适合**中小规模、能接受一个数据库依赖**的团队：半天就能上线，ID 趋势递增。业务量再大、或多机房部署时，再考虑雪花算法的本地生成。

**速记**：号段＝**批量抢区间、内存内分配**，双 buffer 防抖，实现最简。



#### 雪花算法：本地生成

**Snowflake**：64 位整数按位段拆分——1 位符号＋41 位毫秒时间戳＋10 位机器号＋12 位序列号，单机每毫秒可发 4096 个 ID。

```text
64 位结构：
| 1 bit 符号 | 41 bit 时间戳（约 69 年）| 10 bit 机器号（1024 台）| 12 bit 序列号 |
```

- **优点**：纯内存生成、无外部依赖、毫秒级趋势递增，吞吐上限极高。
- **前提约束**：10 位机器号必须全局唯一分配（机器重复会生成重复 ID）；依赖服务器时钟。
- **时钟回拨问题**：NTP 校时让时钟倒退，可能发出与过去重复的 ID。标准对策：回拨小于阈值（如 5 毫秒）就自旋等待，超阈值直接报错拒发——**宁可拒发也不发重复**。

```js
// 语义示意（生产使用成熟库，如 snowflake-id / @sapphire/snowflake）
function nextId(lastTs, seq, workerId) {
  let now = Date.now();
  if (now < lastTs) throw new Error("clock moved backwards");  // 回拨拒发
  seq = now === lastTs ? (seq + 1) & 0xfff : 0;               // 同毫秒内递增
  return { ts: now, seq, id: (BigInt(now - EPOCH) << 22n) | (BigInt(workerId) << 12n) | BigInt(seq) };
}
```

> 雪花算法的运维重心不在算法而在**机器号分配**：用配置中心、数据库注册表或 K8s StatefulSet 序号统一分配并保证不重复。机器号管好了，算法本身几乎不会出错。

**速记**：雪花＝**时间戳＋机器号＋序列号**，本地生成零依赖，防线是机器号唯一与时钟回拨拒发。



### 选型与演进

#### 方案对比

**选型逻辑**：按「能不能养一个发号基础设施」分级，多数中小项目从号段模式起步即可。

| 方案 | 趋势递增 | 外部依赖 | 吞吐 | 主要风险 |
|---|---|---|---|---|
| 数据库自增＋步长错位 | 单库内递增 | 单个 MySQL | 低 | 步长方案扩容困难，已少用 |
| 号段模式 | 严格递增 | 一个 MySQL | 中高 | 发号库故障影响发号 |
| 雪花算法 | 毫秒级递增 | 无（需机器号管理） | 极高 | 机器号重复、时钟回拨 |
| 发号服务（Leaf-Segment/雪花托管） | 可控 | 自建服务 | 极高 | 多一套基础设施要运维 |

- 步长错位方案（各库起点不同、步长等于库数）只适合**库数确定且永不扩容**的老场景，新项目不建议。
- 演进路径：单库自增 → 号段模式 → 雪花算法本地生成，每一步都是加法，旧 ID 无需迁移。

> 判断标准一句话：**每秒 ID 需求低于几千、团队只有一个 MySQL 依赖，用号段模式**；再往上或要多机房，上雪花。不要一开始就架发号服务——那是吞吐与团队规模都到了才值得养的东西。

**速记**：中小项目 **号段起步**，高并发多机房 **雪花本地生成**，发号服务是规模化后的选择。
