## CAP 与 BASE

### CAP 定理

#### 三性质的准确含义

**CAP 定理**：分布式系统无法同时完全满足一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者，网络分区发生时必须在 C 与 A 之间取舍。

- **一致性（C）**：所有节点在同一时刻看到**相同的数据**——写完成后，任何读都返回最新值。
- **可用性（A）**：每个收到请求的节点都给出**合理的响应**（不保证是最新数据），不因别的节点失联而拒绝服务。
- **分区容错（P）**：节点间网络中断（分区）时系统仍能继续运行。分布式环境下网络故障不可避免，**P 不是选项而是前提**。

> 最常见的误读是「三选二」。准确表述是：**P 必保，分区发生时 C 与 A 二选一**。无分区时两者可以兼得；分区一出现，要么拒绝部分请求保一致（CP），要么继续响应可能过期的数据保可用（AP）。

**速记**：**P 是前提，分区时 C 与 A 二选一**。



#### CP 与 AP 的取舍实例

**选型逻辑**：按「业务能容忍旧数据，还是不能容忍不一致」来判断，而不是按技术偏好。

| 类型 | 分区时行为 | 典型系统 | 适合场景 |
|---|---|---|---|
| CP | 为一致性拒绝部分请求 | etcd、ZooKeeper、MySQL 组复制 | 配置中心、选主、金融账务 |
| AP | 继续响应可能过期的数据 | Cassandra、Eureka、DNS | 社交动态、商品浏览、服务发现 |

- 注册中心选 AP 的理由：一个节点拿着几秒前的服务列表仍能工作，但注册中心本身不可用会放大成全站故障。
- 账务选 CP 的理由：余额不一致的代价比暂时不可用高得多。
- **实际系统几乎都是灰度的**：Redis 主从异步复制在多数场景当 AP 用，开了半同步就向 CP 靠，同一套架构可调（见 MySQL 主题第 38 章）。

**速记**：**不容错选 CP，容旧数据选 AP**，同一系统可按场景混用。



### BASE 理论

#### 从强一致到最终一致

**BASE**：基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent），是 AP 路线的工程化纲领。

- **基本可用**：分区或过载时允许降级服务——响应变慢、部分功能关闭、限流排队，但服务不整体崩。
- **软状态**：允许副本之间存在中间状态（主从延迟窗口内的新旧差异），不要求实时一致。
- **最终一致**：停止写入后经过一段时间（通常秒级），所有副本收敛到相同值。

```text
下单流程的最终一致示例：
写主库（订单已创建，状态：处理中）
  → 发布「订单已创建」事件
  → 库存服务消费事件、扣减库存（存在秒级窗口）
  → 扣减完成，订单状态改为：已确认
窗口期内查库存是旧值 —— 软状态；事件消费完成后收敛 —— 最终一致
```

> 最终一致不是「不用管」，它把一致性问题从数据库层转移到**业务设计层**：窗口期的用户体验怎么说、事件丢了怎么补、消费失败怎么重试——这些正是第 3 章（分布式事务）与第 5 章（幂等）要解决的问题。BASE 是纲领，工程手段在第 3、5 章。

**速记**：BASE＝**降级可用＋容忍中间态＋最终收敛**，代价转移到业务设计。
