## 幂等设计

### 为什么需要幂等

#### 重复调用的四个来源

**幂等（Idempotency）**：同一操作执行一次与执行多次，结果完全相同。分布式环境下重复调用不是异常而是常态，幂等是所有跨服务写操作的基础卫生。

- **网络重试**：请求超时后客户端重试，但服务端可能已执行成功——第一次的响应只是没送达。
- **消息重投**：队列的至少一次投递（见第 3 章本地消息表）必然带来重复消费。
- **用户行为**：双击提交、刷新重发、App 弱网下的自动重试。
- **故障恢复**：服务重启后重放未确认的任务，任务可能已做过一半。

> 幂等的本质是**把「是否执行过」与「是否成功返回」解耦**：重复请求到达时，服务端能识别出「这单我处理过了」，直接返回上次的结果而不是再执行一遍。识别凭据的设计（唯一键、令牌）就是幂等设计的全部内容。

**速记**：重复调用是常态不是异常，幂等＝**识别「处理过」并返回原结果**。



### 实现手段

#### 唯一约束：最可靠的兜底

**数据库唯一约束**：给业务唯一键（订单号、流水号）建唯一索引，重复插入直接报错，是所有方案的最后防线。

```js
// 以客户端生成的唯一业务号为幂等键
await db.query(
  "INSERT INTO orders(order_no, user_id, amount) VALUES (?, ?, ?)",
  [orderNo, uid, amount]        // order_no 有唯一索引
);
// 重复请求 → ER_DUP_ENTRY → 捕获后查询已有订单并返回
```

- 幂等键必须由**发起方生成并全链路传递**（前端生成或网关生成），服务端自己生成等于没防。
- 唯一约束兜底的含义：无论上层方案（Redis 防重、令牌）怎么写，**数据库这层永远在**——上层方案失效时数据依然不脏。
- 已存在时的正确行为：查回已有记录、返回与首次相同的结果，而不是报错给用户。

> 判断一个写接口有没有认真做幂等，就看一个问题：**同一个请求打两遍，第二遍的返回值和第一遍一样吗**。返回一样才叫幂等，返回报错只是「没重复入库」，用户体验上仍是失败。

**速记**：唯一索引是 **永远在场的兜底**，幂等键由发起方生成、第二遍返回原结果。



#### 令牌与去重表

**令牌机制**：先领一次性令牌，提交时携带，服务端原子地「取出令牌＋执行业务」，令牌不存在则拒绝重复执行。

```text
1. 客户端进入表单页 → 服务端发放 token 并存入 Redis（SETNX，带过期）
2. 提交时携带 token → 服务端用 GETDEL 原子取走
   - 取到：执行业务
   - 没取到：说明已提交过，返回上次结果或拒绝
```

- 去重表是同一思想的数据库版：以请求 ID 为唯一键插入去重表，插入成功才执行业务，与业务同事务。
- 两者适合**没有天然业务唯一键**的操作（如「点赞」「发放优惠券」），有唯一键的场景直接用唯一约束即可。
- Redis 方案的窗口风险：取走令牌后业务执行失败，令牌已消耗——需要「业务失败归还令牌」或改用带状态的流水表。

> 令牌方案比唯一约束多一层「防重复提交」的用户体验（快速双击在数据库层之前就被拦住），但**它不能替代唯一约束**——Redis 数据丢失、过期策略误配都会让防线消失。正确结构是：令牌挡高频重复，唯一约束兜最终底。

**速记**：令牌挡 **高频重复**、约束兜 **最终底线**，两层缺一不可。



#### 乐观锁与状态机

**条件更新**：用「版本号」或「状态前置条件」让更新语句天然幂等——重复执行时条件已不满足，更新影响行数为零。

```sql
-- 乐观锁：带版本号更新，重复执行第二次影响 0 行
UPDATE accounts SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;

-- 状态机：只有特定前置状态允许流转
UPDATE orders SET status = 'shipped'
WHERE order_no = 'A001' AND status = 'paid';
```

- 乐观锁适合**更新类**操作（余额、库存），配合「影响行数为 0 时的业务判定」（是重复请求还是并发冲突）。
- 状态机适合**流程类**操作（订单状态流转），重复消息命中已完成的状态后自然失效。
- 两者都建立在单条 SQL 的原子性上，无额外组件，是工程成本最低的幂等形式。

> 三类手段按操作类型对号入座：**新建用唯一约束，更新用乐观锁/状态机，无键操作用令牌**。同一个系统里三种并存是正常形态，没有「一个方案包打天下」。

**速记**：新建 **唯一键**、更新 **版本号/状态机**、无键 **令牌**，按操作类型对号。

**警告内容**：幂等键的**作用范围与有效期**必须明确——按用户＋商品去重的「领取优惠券」接口，活动第二期还沿用同一批键就会误拦正常请求。设计时写清两件事：键由哪些字段构成、防重窗口是多久；跨活动的防重，键里必须带活动标识。
