## 分布式事务：2PC、TCC 与本地消息表

### 问题的边界

#### 什么时候需要分布式事务

**分布式事务**：一次业务操作横跨多个数据库、服务或消息系统，需要保证「要么全成、要么全不动」——跨库写、跨服务调用是它的两个来源。

- 微服务拆库后（见 MySQL 主题第 41 章的垂直分库），订单扣库存跨库，本地事务覆盖不了。
- 「先落库、再发消息」两步之间进程崩溃，就会出现库存扣了、消息没发的裂缝。
- **先问要不要**：能合并进同一数据库事务的操作不要拆服务；能接受最终一致的业务不要上强一致协议。分布式事务是代价极高的工具。

> 分布式事务的选型顺序基本是固定的：**优先本地消息表（可靠消息最终一致），次选 TCC，2PC/XA 只在少数强一致场景**。绝大多数互联网业务的答案是消息驱动的最终一致。

**速记**：先问「能不能不用」，多数业务的答案是**消息驱动的最终一致**。



### 强一致方案

#### 2PC 与 XA

**两阶段提交（2PC）**：协调者先问所有参与者「能否提交」（Prepare），全部同意再下令统一提交（Commit），XA 是它在数据库层的标准接口。

- **阶段一**：协调者向所有参与者发 Prepare，参与者锁住资源、写好 redo/undo 后应答 yes/no。
- **阶段二**：全部 yes 则发 Commit，任一 no（或超时）则发 Rollback。
- **固有缺陷**：Prepare 后参与者**持有锁等待**协调者指令，协调者单点崩溃则全体阻塞；网络分区下可能部分提交，一致性与可用性都受损；吞吐低。

```text
协调者                 参与者 A / B
   │── Prepare ────────→  锁资源、写日志、应答 yes
   │── Commit ─────────→  释放锁、正式提交
   （协调者在两阶段间宕机 → A/B 持锁阻塞）
```

> 2PC 的锁跨越「准备到提交」的整个窗口，**窗口越长系统越脆**。它是数据库层面跨库写的一致性兜底（如 MySQL XA、组复制的底层思想），不是业务系统的首选。

**速记**：2PC＝**先问后做**，锁跨全窗口、协调者单点，吞吐低。



#### TCC：业务层的两阶段

**TCC（Try-Confirm-Cancel）**：把「提交资源」改写为三个业务方法，由业务自己实现预留、确认、回滚。

- **Try**：预留资源——冻结库存、冻结余额，不实际扣减。
- **Confirm**：全部 Try 成功后执行，把冻结转为真实扣减。
- **Cancel**：任一 Try 失败后执行，解冻回滚。
- **难点在业务侧**：三个方法都要自己写，还必须满足幂等（见第 5 章）、空回滚（没收到 Try 先收到 Cancel）与悬挂（Cancel 后才到的 Try）三个工程问题。

> TCC 用「业务侵入换性能」：不长时间锁资源，预留即可，吞吐远高于 2PC。适合资金、库存这类**必须强一致且tps 高**的核心链路；外围业务用不起也用不着——写三个接口的成本不是小数目。

**速记**：TCC＝**冻结→确认/解冻**，性能好但要自写三接口＋防幂等三坑。



### 最终一致方案

#### 本地消息表（Outbox 模式）

**本地消息表**：把「发消息」变成「与业务同事务地写一条消息记录」，再由后台任务投递，保证业务成功则消息必达。

```sql
-- 与业务更新在同一个本地事务中
BEGIN;
UPDATE inventory SET stock = stock - 1 WHERE sku_id = 1;
INSERT INTO outbox(topic, payload, status)
  VALUES ('order.created', '{"orderId": 1001}', 'pending');
COMMIT;
```

```js
// 独立投递任务：扫表发送，成功后标记；失败靠下一轮重试
const rows = await db.query("SELECT * FROM outbox WHERE status = 'pending' LIMIT 100");
for (const r of rows) {
  await producer.send(r.topic, r.payload);
  await db.query("UPDATE outbox SET status = 'sent' WHERE id = ?", [r.id]);
}
```

- **可靠性来自同事务**：业务回滚消息也回滚，业务提交消息必在——「库里有记录」和「消息已发出」的裂缝被消除。
- **投递方保证至少一次（at-least-once）**：发送成功但标记失败会重复发送，所以**消费端必须幂等**（第 5 章），这是本模式不可拆解的前提。
- 事务消息（RocketMQ 半消息）是同一思想的中间件化实现；只有 MySQL＋任意队列时，本地消息表零依赖即可落地。

> 本地消息表是**性价比最高的分布式事务**：一个表、一个定时任务、消费端幂等，三件事换来业务级最终一致。中小项目没有理由直接跳到更重的方案。

**速记**：**消息与业务同事务落库**，后台扫表至少一次投递，消费端必须幂等。



#### Saga 与方案对比

**Saga**：长事务拆为一串本地事务，每步配一个**补偿操作**，某步失败则逆向执行已完成步骤的补偿。

- 适合**流程长、外部调用多**的场景（跨行转账、旅行预订），链路中的每一段都可用普通本地事务。
- 补偿是业务逆操作不是数据库回滚：已发的券收不回就计负向流水，**中间状态对外可见**是 Saga 的固有特征。
- 编排方式两选：中心式编排器统一调度，或事件链式（每步完成后发事件触发下一步）。

| 方案 | 一致性 | 侵入性 | 性能 | 适用 |
|---|---|---|---|---|
| 2PC / XA | 强一致 | 低（协议层） | 低 | 数据库层跨库写兜底 |
| TCC | 强一致（业务视角） | 高（三接口） | 高 | 资金、库存核心链路 |
| 本地消息表 | 最终一致 | 低（一表一任务） | 高 | 绝大多数跨服务写 |
| Saga | 最终一致（中间态可见） | 中（补偿链） | 高 | 长流程多外部系统 |

> 选型口诀：**强一致看 TCC，最终一致看消息，长流程看 Saga**。拿不准就从本地消息表起步——它的复杂度最低，向上迁移的路径也最短。

**速记**：Saga＝**本地事务串＋逆向补偿**，中间态可见；选型 **强 TCC、终消息、长 Saga**。

**警告内容**：所有最终一致方案的共同前提是**消费端幂等**，消息至少一次投递必然带来重复。先做第 5 章的幂等、再上任何消息驱动的分布式事务，顺序不能反——否则每次重试都是一次重复扣减。
