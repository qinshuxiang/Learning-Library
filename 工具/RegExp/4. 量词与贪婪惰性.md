## 量词与贪婪惰性

### 量词

#### 六种基础量词

**量词（Quantifier）**：紧跟在某个**原子**（单个字符、字符类、分组）之后，指定它重复的次数。

- *****：0 次或多次。
- **+**：1 次或多次。
- **?**：0 次或 1 次。
- **{n}**：恰好 n 次。
- **{n,}**：至少 n 次。
- **{n,m}**：n 到 m 次。

```js
console.log(/a*/.test("bbb"));        // true（0 次也算匹配）
console.log(/a+/.test("bbb"));        // false（至少 1 次）
console.log(/colou?r/.test("color")); // true（u 可有可无）
console.log(/\d{2,4}/.test("123"));   // true（2 到 4 个数字）
```



#### 量词的作用对象与优先级

**量词只作用于紧邻它的那一个原子**，这一条的推论是“想让一整段重复就必须先分组”，也是很多模式意思写反的根源。

- **/ab+/**：只有 b 重复，匹配 a 后跟一个以上 b。
- **/(ab)+/**：ab 作为一个整体重复。
- **/(?:ab)+/**：同样是整体重复，但不产生捕获组。
- **量词不能修饰锚点**：/^*/ 直接抛 Nothing to repeat 的 SyntaxError。
- **量词修饰断言分模式**：非 u 模式下 /(?=a)*/ 被宽容放行，u/v 模式下抛 Invalid quantifier。

```js
console.log(/ab+/.exec("abbb")[0]);   // "abbb"（b 重复）
console.log(/ab+/.exec("abab")[0]);   // "ab"（第一个 ab 就够，a 不参与重复）
console.log(/(ab)+/.exec("abab")[0]); // "abab"（整体重复）
console.log(/(ab)+/.exec("abab")[1]); // "ab"（捕获组只留最后一次）

console.log(/^a*b/.exec("aaab")[0]);  // "aaab"
// console.log(/^*/);                 // SyntaxError: Nothing to repeat
// new RegExp("(?=a)*", "u");         // SyntaxError: Invalid quantifier
```



#### 星号与加号的零次陷阱

**星号量词允许零次**这一性质是若干“莫名其妙就匹配成功”的根源：模式里带 \* 的部分永远可以“什么都不匹配”，导致整个正则变成几乎永真。

```js
// /\d*/ 几乎对任何字符串都返回 true——0 个数字也算匹配
console.log(/\d*/.test("abc"));  // true！
console.log(/\d+/.test("abc"));  // false（+ 至少要求 1 个）

// 可选部分用 ? 或 {0,n} 写清楚下限，避免 * 的零次歧义
console.log(/^1\d{0,2}$/.test("1")); // true（明确允许 0 到 2 位）
```

> [!CAUTION]
> **注意内容**：写验证类正则时优先用 **+** 与 **{n,m}**，慎用 **\***：星号允许零次重复，校验 /\d*/.test(空串) 也是 true，“形同虚设”。确实允许为空时，用量词明示（\d{0,11}）比用 \* 更可读。



#### 花括号量词的书写规则

**花括号量词 {n}、{n,}、{n,m} 有三条硬规则**：数字之间不允许空格、下限不允许大于上限、JavaScript 不支持省略下限的 {,m} 写法。

- **{1, 3} 带空格**：非 u 模式下被当成字面文本，不报错但失配；u 模式下直接 SyntaxError。
- **{3,1} 下限大于上限**：两种模式下都是 SyntaxError。
- **{,3} 省略下限**：这不是 JavaScript 的量词——其它语言用它表示 0 到 3 次，JS 里整个花括号连同内容都是字面文本，必须写成 {0,3}。
- **{0} 合法**：a{0} 匹配零个 a，等价于什么都没写，语法合法但无实义。

```js
console.log(/a{2}/.test("a"));      // false（恰好 2 个，这里只有 1 个）
console.log(/a{0}/.test("bbb"));    // true（0 次也算匹配）

console.log(/a{,3}/.test("a"));     // false！它匹配的是字面文本
console.log(/a{,3}/.test("a{,3}")); // true（证据：花括号被当成普通字符）
console.log(/a{0,3}/.test("a"));    // true（省略下限的正确写法是补 0）

console.log(/a{1, 3}/.test("a"));      // false（带空格的量词没有量词效果）
console.log(/a{1, 3}/.test("a{1, 3}")); // true（它在找字面文本）
```

> [!WARNING]
> **警告内容**：{,m} 与 {n, m} 是从其它语言或手写习惯迁移模式时的最高频写法错误：前者不报错、不生效，整个花括号按字面字符参与匹配，故障完全静默；后者同样静默失配。从 Python、PCRE 迁移正则到 JavaScript 时，逐个检查花括号量词的写法。



#### 占有量词与 JavaScript 的替代方案

**JavaScript 没有占有量词**：PCRE、Java 支持的 a++、a*+、a?+（吃掉就不吐回）在 JS 里是语法错误，但也**不需要**它们——用“先行断言加反向引用”可以模拟出同样的“不回溯”效果。

- **占有量词的语义**：量词一次吃满，之后**永不吐出**，因此不产生回溯点。
- **JS 的等价手法**：把要“原子化”的部分放进先行断言，再用反向引用把它取回来。
- **作用**：把“多种拆法”压成“只有一种拆法”，从根上消除指数级回溯。
- **写法代价**：模式可读性下降，且反向引用会占用组号，能用排除型字符类时优先用后者。

```js
// 普通量词：a+ 会因为后面的 a 失败而吐回字符，于是匹配成功
console.log(/a+ab/.exec("aaab")[0]); // "aaab"（a+ 从三个退到两个）

// 原子化写法：先行断言里已经吃满，外面不再重试，匹配失败
const atomicReg = /(?=(a+))\1ab/;
console.log(atomicReg.test("aaab")); // false（a+ 一次吃满三个，不给退）

// 原子化后再把 a+ 的“吃满”放宽一格，就能像普通写法一样工作
console.log(/(?=(a{2}))\1ab/.test("aaab")); // true
```

> [!NOTE]
> **提醒内容**：原子化的代价是**丢掉了量词的部分匹配能力**，只在明确“这段不该回溯”时才用。日常写业务正则，减少回溯的正确姿势仍是**换用排除型字符类**，原子化属于最后手段。



### 贪婪与惰性

#### 两种模式的定义

**贪婪（greedy）**：量词默认行为，在能让整体匹配成功的前提下**尽可能多地吃字符**；**惰性（lazy）**：在量词后加 ?，改为**尽可能少地吃字符**。

```js
const html = "<p>标题</p><p>正文</p>";

console.log(html.match(/<p>.*<\/p>/)[0]);
// "<p>标题</p><p>正文</p>"（贪婪：一路吃到最后一个 </p>）

console.log(html.match(/<p>.*?<\/p>/)[0]);
// "<p>标题</p>"（惰性：遇到第一个 </p> 就收手）

console.log(html.match(/<p>[^<]*<\/p>/)[0]);
// "<p>标题</p>"（排除型字符类：既精准又无需回溯，推荐）
```

> 惰性不是“匹配更短”，而是“**先少拿、拿不动了再多加**”。/a*?/.exec("aaa") 得到的是空串而不是 “aaa”——因为它允许 0 次重复。真正的取舍口诀是：**能用排除型字符类 [^x] 解决，就别用 .\*?**，前者几乎不产生回溯。



#### 贪心与惰性的零次优先表现

**惰性的“最少”下限由量词本身决定**：\*? 的下限是 0，+? 的下限是 1，? 的后加 ? 只是把“优先选有”改成“优先选无”。理解下限，才能解释惰性在全局匹配下的怪异输出。

- **\*? 的下限是 0**：因此它在任何位置都能“成功”，全局匹配会产出大量空串。
- **+? 的下限是 1**：至少吃一个，空串不会出现。
- **?? 优先选“不出现”**：/colou??r/ 会先尝试 color，失败才试 colour。
- **零长匹配要防死循环**：带 g 的 exec 遇到空匹配必须手工推进 lastIndex。

```js
// 下限为 0 的惰性量词，全局匹配产出大量空串
console.log("aaa".match(/a*?/g)); // ["", "", "", ""]（四个位置各空一次）

// 下限为 1 的惰性量词，就不会产出空串
console.log("aaa".match(/a+?/g)); // ["a", "a", "a"]

// ?? 优先“不出现”
console.log(/colou??r/.exec("color")[0]);  // "color"（先试少的那一支）
console.log(/colou??r/.exec("colour")[0]); // "colour"（少了不行才多）

// 空匹配导致的死循环：必须手工推进
const emptyReg = /a*/g;
console.log(emptyReg.exec("bbb")[0], emptyReg.lastIndex); // "" 0（位置没动）
```

> [!CAUTION]
> **注意内容**：看到全局匹配输出里出现**连续空串**，先查模式里有没有下限为 0 的量词（\*、\*?、{0,n}）。这类模式做校验没问题，做**遍历替换**时极易产出意料之外的重复文本或陷入死循环，遍历场景请改用下限至少为 1 的量词，或显式处理空匹配。



#### 引号配对的经典案例

**成对引号提取**是区分贪婪与惰性的教科书案例：贪婪会吞掉中间的多段文本，惰性或排除型写法才能正确切分。

```js
const text = 'a "witch" and her "broom" is one';

// 排除型：引号之间不允许再出现引号（首选）
console.log(text.match(/"[^"]+"/g));  // ["\"witch\"", "\"broom\""]

// 惰性：同样能切成两段
console.log(text.match(/".+?"/g));    // ["\"witch\"", "\"broom\""]

// 贪婪：从第一个引号一路吞到最后一个引号
console.log(text.match(/".+"/g));     // ["\"witch\" and her \"broom\""]
```

> 三种写法只有一种语义是错的，但三种都能通过“测试串里有一对引号”的粗检。**写多段提取的模式时，构造一个至少含两段目标的测试串**，一行输出就能暴露贪婪错误。



#### 贪婪惰性在分段提取中的表现

贪婪与惰性的差异在**多段提取**时最为直观：

```js
const config = "a=1;b=2;c=3;";

console.log(config.match(/\w=\d+;/g)); // ["a=1;", "b=2;", "c=3;"]

// 从“键=值”中逐段取出键与值
const pairReg = /(\w)=(\d+);/g;
for (const m of config.matchAll(pairReg)) {
  console.log(m[1], m[2]); // a 1、b 2、c 3
}

// 带量词的捕获组只记住最后一次重复，要用它包住整体时请改用非捕获组
console.log(/(\d)+/.exec("12345")[1]);   // "5"，不是 "12345"
console.log(/(?:\d)+/.exec("12345")[0]); // "12345"
```



### 回溯

#### 逐帧拆一次回溯过程

**回溯的“逐帧”读法**：把量词的每一次“再吃一个”或“吐出一个”当成一帧，模式失败时引擎一帧一帧倒带，直到某帧能继续或全部试完。用 /^(a{1,3})b$/ 去匹配 aaaab（四个 a 加一个 b），可以完整看到倒带全程。

```js
console.log(/^(a{1,3})b$/.exec("aaaab")); // null（三种读法全部失败）

// 引擎内部的逐帧过程：
// 第 1 帧：a{1,3} 贪婪吃下 aaa → 下一个要 b，遇到 a → 失败，吐回一个
// 第 2 帧：a{1,3} 保有 aa   → 下一个要 b，遇到 a → 失败，再吐回一个
// 第 3 帧：a{1,3} 保有 a    → 下一个要 b，遇到 a → 失败，已到下限 1，整体失败
// ^ 锁定了起点，前面没有别的位置可挪，于是整次匹配宣告失败

// 同样的模式换三个 a，第 1 帧就直接成功，一次回退都不需要
console.log(/^(a{1,3})b$/.exec("aaab")[0]); // "aaab"（a{1,3} 吃满三个正好接上 b）
```

再看一个**成功**的例子，看清“吐回之后就通过”的那一帧：

```js
console.log(/a+ab/.exec("aaab")[0]); // "aaab"

// 第 1 帧：a+ 吃下 aaa → 后面要 a，遇到 b → 失败，吐回一个
// 第 2 帧：a+ 保有 aa  → 后面要 a，遇到 a → 成功 → 再要 b，遇到 b → 整串成立
```

> 惰性量词的逐帧方向相反：a{1,3}? 从吃 1 个开始，不够再“多加一个”。无论贪婪还是惰性，帧数都受**量词上限**约束——{1,3} 最多三帧；而嵌套量词的帧数是各层上限的**乘积**，这正是灾难性回溯的数学根源，展开见系列第 9 篇《性能与安全》。



#### 回溯的代价随嵌套层级相乘

**单层量词的回溯路径是线性的加法，嵌套量词是乘法**：每套一层量词，就多出一个独立的“拆分方案”维度，输入每长一个字符，组合数就乘一次。

- **单层**：a+ 对 n 个 a 只有 n 种“吃几个”的选择，路径数随 n 线性增长。
- **两层**：(a+)+ 对 n 个 a 要给每一段分配长度之和为 n，路径数随 n 指数增长。
- **三层**：((a+)+)+ 更陡，n 稍微大一点就彻底卡死。
- **判定口诀**：**同一个字符能被两个量词分别认领，就有歧义；歧义嵌套，就是指数**。

```js
// 同一串 a 的三种读法（单层），路径数最多 3
console.log(/^a+b$/.exec("aaab")); // null，试了 3 种长度

// 两层嵌套：n 个 a 有 2 的 n-1 次方种拆分方式
const nestedReg = /^(a+)+$/;
console.log(nestedReg.test("aaaa"));      // true（很快）
console.log(nestedReg.test("aaaa" + "!")); // false，但已经试遍了所有拆分

// 安全改写：把嵌套压平成单一量词，意思一样、路径只剩一条
console.log(/^a+$/.test("aaaa!")); // false，一次扫描就结束
```



#### 惰性量词并非银弹

**惰性只改变尝试顺序，不消灭回溯**：.\*? 在“找不到目标”的失败场景下同样会穷举位置，某些输入下甚至比贪婪更慢。

```js
// 惰性在成功场景下更省事
console.log("x123y".match(/x.*?y/)[0]); // "x123y"（最短匹配）

// 但失败场景下惰性一样要走到头
console.log(/x.*?z/.test("x123y")); // false（同样穷举后失败）
```

> [!IMPORTANT]
> **重要内容**：性能优化的首选不是“贪婪换惰性”，而是**用排除型字符类收缩搜索空间**：[^<]* 只能在非尖括号字符上尝试，位置数量天然有限，从根上减少回溯分支。**先精确，再惰性，最后才考虑贪婪**。



#### 用排除型字符类替代点星

**替换手法只有一条规则**：先问“我要匹配的内容里绝对不会出现哪个字符”，把那个字符写进 [^...]，点星就失去了用武之地。

- **替代 .\***：知道不会出现 x 时，写成 [^x]*，一步到位。
- **替代 .\*?**：目标段内不含定界符时，用排除型字符类比惰性更省资源。
- **多个禁区一起排除**：[^<>"\n] 把尖括号、引号、换行全部挡在外面。
- **允许换行**：[^x] 天然包含换行，无需 s 标志，也不会因为 s 而放宽结构约束。

```js
const html = "<p>标题</p><p>正文</p>";
const csv = 'a,"含,逗号",c';
const log = "2026-04-12 01:30:00 [ERROR] 连接被拒绝";

// 提取标签内容：内容里不会有尖括号
console.log(html.match(/<p>[^<]*<\/p>/g).length); // 2

// 提取 CSV 中被引号包裹的字段：字段里不会再有引号
console.log(csv.match(/"[^"]*"/g)); // ["\"含,逗号\""]

// 提取方括号里的级别：括号内不会有右方括号
console.log(log.match(/\[[^\]]*\]/)[0]); // "[ERROR]"
```

> [!TIP]
> **建议内容**：改写的固定动作是**把 .\*? 圈出来，逐个问“这里绝对不该出现什么”**。答得出来就换成 [^x]*，答不出来才说明这段内容真的可能包含任意字符，此时再考虑惰性量词配合锚点。这个动作能将绝大多数慢正则一次性解决。
