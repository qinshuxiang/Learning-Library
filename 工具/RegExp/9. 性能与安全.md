## 性能与安全

### 回溯与灾难性回溯

#### 回溯的工作机制

**回溯（backtracking）**：正则引擎在某条匹配路径走不通时，**退回上一个可选分支**再试。它是惰性与贪婪、量词与分组能协同工作的基础，但也可能被滥用。

**灾难性回溯（Catastrophic Backtracking，也称 ReDoS）**：当模式里出现**嵌套量词**（如 (a+)+、(a*)*）且最终匹配失败时，引擎要枚举的组合数随输入长度**指数级增长**，导致脚本卡死。

```js
const riskyReg = /(a+)+$/; // 嵌套量词，危险

// 下面这行会让主线程长时间卡住：26 个 a 的每一种拆分都要试一遍
console.log(riskyReg.test(`${"a".repeat(26)}!`));
```

> ReDoS 的触发需要两个条件同时成立：**存在多种拆分方式的嵌套量词**，且**最终匹配失败**（失败才会穷举所有可能）。用于校验用户输入（尤其是用户名、URL、邮箱这类公开表单字段）的正则，必须专门排查这一点。



#### 复杂度的三个等级

**正则的匹配耗时随输入长度的增长曲线分三档**，识别自己写的是哪一档比背规则更重要。

- **线性 O(n)**：安全。每个字符只被处理一次，如 /^[a-z]+$/、^\d{1,10}$。
- **多项式 O(n²)、O(n³)**：危险。多个 .\* 并排扫描同一段文本，如 /.\*a.\*a.\*/。
- **指数 O(2ⁿ)**：致命。嵌套量词与重叠分支，如 /^(a+)+$/、/(a|a)\*$/、/([a-z]+)+$/。

```js
// 三档的代表性写法
console.log(/^[a-z]+$/.test("abc"));        // 线性：一次扫描
console.log(/.*a.*a.*/.test("abcabc"));     // 多项式：两个 .* 反复回扫
console.log(/^(a+)+$/.test("aaaaaX"));      // 指数：n 个 a 有 2 的 n 次方种拆分
```

> 判断口诀：**同一串字符能被同一个量词结构“拆成几种读法”，就有几倍回溯**。线性模式对输入只有一种读法；指数模式对 n 个字符有 2ⁿ 种读法，30 个字符就是十亿级组合。



#### 攻击输入的三段式构造

**ReDoS 攻击串有固定的构造公式**：前缀 + 泵 + 后缀。理解它，就能站在攻击者视角审查自己的模式。

- **前缀（prefix）**：让模式进入歧义状态，通常很短甚至为空。
- **泵（pump）**：重复的同一字符（如 30 个 a），每多一个就翻倍回溯组合。
- **后缀（suffix）**：一个让整体匹配必然失败的字符（如 !），逼迫引擎穷举所有拆分。

```js
// 以 ^(a+)+$ 为例
const pump = "a".repeat(30);       // 泵：30 个 a
const suffix = "!";                 // 后缀：匹配必然失败

// pump + suffix 组成的 31 字符串即可让引擎穷举十亿级组合
// 无需流量、无需肉机，一个请求就能占满一个 CPU 核
```

```js
// 更贴近真实的攻击：nth-check 的漏洞模式，泵是空格而不是字母
// 受影响版本里解析 CSS 序号时使用的子模式：\s*(?:([+-]?)\s*(\d+))?
// 攻击串形如 "2n" 加上一万个空格再加一个叹号
const attack = "2n" + " ".repeat(10000) + "!";
// 实测数据（原漏洞通告）：1 万字符耗时约 174 毫秒，5 万字符约 7.5 秒
```

> [!WARNING]
> **警告内容**：ReDoS 的可怕在于**短输入、低成本**：几十个字符的精心构造输入即可钉死一个 CPU 核，Node.js 这类单线程运行时里还会阻塞整个事件循环，所有并发请求一起陪绑。安全审计把 ReDoS 列为服务器端最常见的漏洞类型之一，名不虚传。



#### 歧义结构的识别清单

**“这段字符只有一种吃法吗”**是唯一需要问的问题。列出容易产生多种吃法的结构，审查模式时逐条对照即可。

- **嵌套量词**：(a+)+、(a*)*、([a-z]+)+，外层与内层都在争抢同一段字符。
- **相邻的重叠量词**：\s*\s*、a*a*、.\*.\*，两个量词覆盖的范围完全重合。
- **量词套在含 \s* 的分组上**：(\s*(\d+))? 这类“可选组里又有可空量词”，是 nth-check 漏洞的成因。
- **多分支可匹配同一串**：(a|a)、([a-z]|[ab])，不同分支对同一输入都能成功。
- **可选的边界与量词叠加**：(\d+\.?)+\d 之类，点号可有可无让拆分方式翻倍。

```js
// 逐个对照：这些模式都能对同一段字符给出多种拆法
const suspicious = [
  /(a+)+/,           // 嵌套量词
  /a*a*/,            // 相邻重叠量词
  /(\s*(\d+))?/,     // 可选组内含可空量词
  /(a|a)+/,          // 分支重复
];

// 改写方向：让同一段字符只有一种归属
console.log(/^\d+$/.test("123")); // 原模式 /^(\d+)+$/ 的等价安全写法
```



### 真实事故案例

#### moment.js 的经典漏洞

**moment.js 在 2.29.4 之前存在 ReDoS（CVE-2022-31129）**：rfc2822 日期解析在预处理阶段用正则剥除括号包裹的遗留注释，该正则对超长输入呈平方级复杂度，超长字符串即可让解析耗时从毫秒级飙升到分钟级，阻塞整个 Node.js 事件循环。

```js
// 官方通告给出的复现方式：50 万个左括号
// moment("(".repeat(500000)) 需要数分钟才能处理完
// 受影响区间为 2.18.0 至 2.29.3，修复版本为 2.29.4

// 更早的 2.19.3 之前版本还修复过一次格式化正则的回溯问题（CVE-2017-18214），
// 同一个库数年间两次栽在回溯上
```

> 修复思路有两条：**消除歧义**（重写模式，让每段输入只有一种读法）或**封顶**（给重复加 {0,10} 这类上限，把组合数从指数压回线性）。两条路都指向同一个原则——**同一串字符只允许一种读法**。官方在修复之外还建议对用户输入的日期串先做长度上限（如 200 字符）检查，与下文“限制输入长度”的防线一致。



#### Stack Overflow 与 Cloudflare 的宕机

**两家顶级技术公司都栽在一条正则上**，这不是巧合，而是回溯灾难在真实世界的常态。

- **Stack Overflow（2016 年 7 月 20 日）**：帖文空白裁剪正则遇到某用户输入的特定空白组合，触发灾难性回溯，全站宕机 34 分钟。
- **Cloudflare（2019 年 7 月 2 日）**：Web 应用防火墙的一条解析正则被构造输入钉死 CPU，全球网络中断 27 分钟。
- **共同点**：两条正则都通过了正常测试、运行多年无恙，只在**特定长度的特定输入**下暴露指数级最坏情况。

> 事故复盘的共同教训是：**正则的功能测试发现不了性能炸弹**——它只在“够长且最终失败”的输入上触发，而正常测试用例几乎总是成功且很短。上线前对校验类正则做一次“长输入 + 失败后缀”的压力测试，是最便宜的保险。



#### 依赖库里的 ReDoS

**ReDoS 是供应链漏洞的重灾区**：自己没写正则，也可能被依赖里的一条慢正则拖垮。

- **lodash**：toNumber、trim、trimEnd 在 4.17.21 之前存在 ReDoS（CVE-2020-28500）。
- **semver**：版本区间字符串可触发灾难性回溯（CVE-2022-25883），它是 npm 生态被依赖最多的包之一。
- **minimatch**：braceExpand 处理重复花括号时被拖入灾难性回溯（CVE-2022-3517），3.0.5 修复。
- **marked**：Markdown 解析器在特定列表与标题输入下挂起渲染（CVE-2022-21681）。
- **nth-check**：CSS 序号解析的子模式 \s*(?:([+-]?)\s*(\d+))? 存在重叠歧义（CVE-2021-3803），受影响版本小于 2.0.1，经 svgo、css-select 传递进大量构建工具链。

> [!CAUTION]
> **注意内容**：依赖审计工具（npm audit、Snyk、GitHub Dependabot）会标出已知 ReDoS 编号的 CVE，**不要因为“只是性能问题”而忽略**：在单线程的 Node 服务里，一条慢正则约等于一次完整的拒绝服务。

> 生态层面的统计同样值得记住：Staicu 与 Pradel 的研究发现，约**一成的 Node.js 网络服务**因间接依赖含 ReDoS 漏洞的 npm 模块而受影响；Davis 等人对 npm 与 PyPI 生态做过正则的批量提取与超线性分析，发现数千条风险正则波及上万个上游模块；Snyk 2021 年的开源安全报告也在被分析的热门 npm 包中命中约一成。三份来源口径不同，但结论一致——**这是普遍存在的缺陷类型，不是边缘个例**。



### 防御与优化

#### 常见优化建议

优化手段围绕消除歧义与提前失败展开：压平嵌套量词、用排除型字符类、校验前先卡长度。

- **用排除型字符类替代 .\***：匹配一对 p 标签时，用“非尖括号字符”的排除型字符类，比用点星加惰性量词快且不会回溯失控。
- **避免嵌套量词**：/(a+)+/、/(\s*\w+)\*/ 这类写法要拆开重写。
- **锚点尽早失败**：把 ^、字面前缀放在最前面，让不匹配的字符串迅速被排除。
- **限制输入长度**：在校验前先用 length 属性卡一道，是最廉价的防护。
- **非捕获组优先**：不需要结果时用 (?:...)。
- **复杂文本用专用解析器**：HTML、URL、Markdown 都不该用正则硬啃，浏览器有 DOMParser 与 URL 可用。

```js
// 重写消除歧义的示范：嵌套量词压平为单一量词
const risky = /^(\d+)+$/;  // 嵌套量词，指数风险
const safe = /^\d+$/;      // 同样的验证意图，线性耗时

// 校验前先卡长度：正则再慢，短输入也慢不到哪去
function validate(input) {
  if (typeof input !== "string" || input.length > 64) return false;
  return safe.test(input);
}
```

> 一句话准则：**正则适合“匹配模式”，不适合“解析结构”**。嵌套结构（HTML 标签、JSON、代码）在理论上就无法用正则正确解析，任何“看起来能用”的正则都只是特定输入的近似解。

```js
// 校验 URL：先用内置 API，别硬写正则
function isValidUrl(value) {
  try {
    new URL(value);
    return true;
  } catch {
    return false;
  }
}

console.log(isValidUrl("https://example.com/a?b=1")); // true
console.log(isValidUrl("不是网址"));                    // false
```



#### 安全改写对照

**改写的手法只有两类：消除歧义与加边界**。下面几组对照覆盖了生产代码里最常见的风险写法。

- **嵌套量词 → 单一量词**：/^(\d+)+$/ 改为 /^\d+$/，语义不变、复杂度回到线性。
- **相邻重叠量词 → 合并**：/a*a*/ 改为 /a*/，同一个量词吃掉即可。
- **点星 → 排除型类**：/".*?"/ 改为 /"[^"]*"/，位置数量从“任意”降到“非引号”。
- **无界量词 → 有界量词**：/\s*/ 改为 /\s{0,10}/，把组合数封顶。
- **内层可空量词 → 必选**：/(\s*(\d+))?/ 改为 /(?:\s{1,10})?(\d+)?/，不让内层量词“可以什么都不吃”。
- **分支合并 → 单分支**：/(a|a)+/ 改为 /a+/，重复分支只保留一条。

```js
// 有界量词 vs 无界量词：功能近似，最坏情况差一个数量级
const unboundedReg = /^\s*(\w+)\s*$/;      // 无界，长空白串上回退很多
const boundedReg = /^\s{0,64}(\w+)\s{0,64}$/; // 有界，组合数被封顶

console.log(unboundedReg.test("abc"), boundedReg.test("abc")); // true true

// 内层可空量词的危险写法与安全写法
const riskyInner = /(?:\s*(\d+))?$/;   // 内层可空，外层可选，两种“空”都在争
const safeInner = /(?:\s{1,32})?(\d+)?$/; // 外层可选但内层不再可空
console.log(riskyInner.test("123"), safeInner.test("123")); // true true
```

> [!IMPORTANT]
> **重要内容**：改写后**必须重新跑一遍正样本与负样本**——消除歧义的过程中很容易把“允许的输入”一并改掉。改写与限长可以同时上，两者不冲突：限长负责把最坏情况压到可接受范围，改写负责从根上消除风险。



#### 转义用户输入

把用户输入的字符串拼进正则时，其中的 .、*、(、[ 等元字符必须转义，否则轻则匹配异常，重则触发 ReDoS。

```js
// 传统手写转义
function escapeRegExp(text) {
  return text.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
}

const keyword = "a.b";
const safeReg = new RegExp(escapeRegExp(keyword), "g");
console.log(safeReg.test("xxa.bxx")); // true
console.log(safeReg.test("xxaxbxx")); // false（点已被当作普通字符）
```

> 现代标准提供了 **RegExp.escape(text)**，直接返回转义后的字符串（ES2025 特性，V8 13.6 即 Node 24 及以上、Chrome 136 及以上、Firefox 134 及以上已提供）。在它可用之前，上面的 escapeRegExp 是社区通行的等价实现；无论用哪种，**“用户输入进正则前必须转义”是安全红线**。

```js
// RegExp.escape 的实际输出：与手写写法不逐字相同，但语义等价
console.log(RegExp.escape("abc"));    // "\x61bc"（首字符是字母，用 \x 形式转义）
console.log(RegExp.escape("123"));    // "\x3123"
console.log(RegExp.escape("a.b-c"));  // "\x61\.b\x2dc"
console.log(RegExp.escape("a b"));    // "\x61\x20b"（空白也用 \x 形式）
console.log(RegExp.escape("()"));     // "\(\)"
console.log(RegExp.escape("价格128元")); // "价格128元"（非语法字符原样保留）
```

> [!CAUTION]
> **注意内容**：**不要把 RegExp.escape 的输出当成“和手写转义一样的结果”去比对**——它会额外用 \x 或 \u 形式转义首字符、空白与部分符号，因此输出字符串长得不一样，但**语义完全等价**，可以直接拼进构造函数。真正需要注意的是**运行环境**：Node 22 及更早版本没有这个方法，直接调用会得到 RegExp.escape is not a function，务必保留手写实现作为兜底。



#### 检测工具与防御层次

**ReDoS 防御是多层的**，单靠肉眼审查模式远远不够。

- **静态检测**：eslint-plugin-security 的 detect-unsafe-regex 规则、safe-regex 与 eslint-plugin-redos 等 npm 包、GitHub CodeQL，能在合并前标出嵌套量词与歧义分支。
- **运行时防线**：输入长度上限、匹配超时（部分运行时支持）、把高风险匹配挪进独立进程。
- **非回溯引擎**：Google RE2 及其绑定、Rust 的 regex crate 从设计上拒绝回溯，保证线性耗时，代价是不支持反向引用等特性。
- **依赖审计**：npm audit、Snyk、Dependabot 覆盖了已知 CVE 编号的依赖漏洞。

```js
// 把“长度上限 + 模式校验”封成一个校验函数，是业务侧最容易落地的一层
function makeSafeValidator(reg, maxLength) {
  return function validate(input) {
    if (typeof input !== "string" || input.length > maxLength) return false;
    return reg.test(input);
  };
}

const validateCode = makeSafeValidator(/^[A-Z0-9]{6,12}$/, 12);
console.log(validateCode("A1B2C3"));                      // true
console.log(validateCode("A1B2C3D4E5F6G7H8I9"));           // false（超长，正则根本不跑）
```

> [!IMPORTANT]
> **重要内容**：防御优先级从高到低是**重写模式 > 限长 > 静态检测接入 CI > 运行时兜底**。重写（消除歧义）是根治，其余都是缓解；但四层一起上的成本很低，生产服务值得配齐。
