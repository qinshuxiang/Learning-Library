## 权限模型与最小权限

### 命名权限与主机权限

扩展的权限分两类，写在 manifest.json 的两个不同键里，对应两种不同的授权粒度。

- 命名权限：写在 permissions 键里，是从已知字符串列表中选取的能力开关，例如 storage、scripting、alarms，决定对应 API 是否可用。
- 主机权限：写在 host_permissions 键里，是一个或多个匹配模式，决定扩展可以访问哪些网址，进而决定跨源请求、读取标签页敏感字段、注入内容脚本这些能力是否成立。

MV3 把两者拆成独立的键，原因是授予方式不同：命名权限整体授予，主机权限可以按站点范围授予，也能在运行期由用户逐站追加或撤回。

```json
{
  "manifest_version": 3,
  "name": "Site Notes",
  "version": "1.0.0",
  "permissions": ["storage", "scripting", "activeTab"],
  "host_permissions": ["https://*.example.com/*"],
  "optional_permissions": ["topSites"],
  "optional_host_permissions": ["https://*/*"]
}
```

主机权限与跨域能力直接相关：从 Service Worker 或扩展页面发起 fetch 时，只有声明了目标主机的主机权限才能跨源取数。内容脚本的跨源请求始终按注入页面的来源计算同源策略，有没有主机权限都不改变这一点。



### 权限警告与用户感知

安装时 Chrome 会把带警告的权限列成清单给用户确认，在 content_scripts.matches 与 host_permissions 里增删匹配模式同样可能触发警告。警告条数越少，用户对扩展的信任越高，商店审核对宽权限的审查也更严格。

全站匹配模式只有一种写法，它会把警告拉到最重：

```json
{
  "host_permissions": ["<all_urls>"]
}
```

> [!WARNING]
> **警告内容**：全站匹配模式会显著拉长商店审核时间，也会让用户在权限页看到覆盖所有网站的授权范围。扩展实际只需要少数站点时精确列出域名，既能减少警告，也避免用户因授权范围不合理而放弃安装。



### activeTab 临时主机权限

activeTab 是一份按需发放的临时主机权限，只在用户主动调用扩展时授予当前标签页，并且不产生任何权限警告。

触发授予的用户手势有四种：点击扩展的操作图标、点击扩展创建的上下文菜单项、按下 commands API 注册的键盘快捷键、在多功能框中接受扩展给出的建议。

授权范围与失效时机都很明确：用户在某个页面调用扩展后，扩展在该页面停留期间持续拥有访问权；导航到同一来源的其它路径不失效，离开该来源或关闭标签页即撤销。

```js
chrome.action.onClicked.addListener((tab) => {
  if (tab.url.startsWith("chrome://")) return;
  chrome.scripting.executeScript({
    target: { tabId: tab.id },
    func: collectArticle,
  });
});
```

在 activeTab 生效期间，扩展可以配合 scripting 权限调用 executeScript 与 insertCSS；可以通过返回 Tab 对象的 API 读取该标签页的网址、标题与网站图标；还可以用 webRequest 拦截发往该标签页主框架来源的请求。这三项能力本质上都是临时主机权限带来的。



### 可选权限的声明与申请

可选权限适合非核心功能：用户只在启用该功能时才看到权限提示，扩展平时以更小的权限集运行，升级时新增可选权限也不会导致 Chrome 停用扩展。

声明分两个键，optional_permissions 放命名权限，optional_host_permissions 放主机匹配模式。要在运行期请求届时才能确定的主机，可在 optional_host_permissions 里写通配来源，之后请求其中任意同方案来源。

```json
{
  "optional_permissions": ["topSites"],
  "optional_host_permissions": ["https://*/*"]
}
```

并非所有权限都能声明为可选，被排除的九项是 debugger、declarativeNetRequest、devtools、geolocation、mdns、proxy、tts、ttsEngine 与 wallpaper。

chrome.permissions.request(permissions) 必须在用户手势中调用，返回 Promise，敲定值表示用户是否授予。

```js
document.querySelector("#enable-stats").addEventListener("click", async () => {
  // 必须在用户手势内发起，放在 await 之后会丢失手势上下文
  const granted = await chrome.permissions.request({
    permissions: ["topSites"],
    origins: ["https://www.google.com/"],
  });
  if (granted) {
    renderTopSites();
  }
});
```

请求的权限必须已经写在清单的 optional_permissions 或 optional_host_permissions 里，或者是用户此前拒绝授予的必需权限。origins 里各项的路径部分会被忽略，因此可以只请求可选来源集合中的一个子集。新增权限带来的警告若与用户此前已接受的警告不同，Chrome 会弹出确认框。

> [!IMPORTANT]
> **重要内容**：权限申请只能在用户手势的同步阶段发起。把 request 调用放在 await 或 setTimeout 之后，手势上下文已经过期，请求会被拒绝。需要先做异步准备时，把准备结果缓存起来，等用户下一次点击时再发起申请。



### 权限查询与移除

chrome.permissions 的四个方法返回值均为 Promise（Chrome 96 起）。

- contains(permissions)：判断是否已拥有指定权限，返回布尔值。
- getAll()：返回当前的完整权限集，即 Permissions 对象。
- request(permissions)：申请权限，返回用户是否授予。
- remove(permissions)：移除权限，出现问题时 Promise 被拒绝。

Permissions 对象只有两个可选数组字段：permissions 放命名权限，origins 放主机来源。

```js
async function hasSiteAccess(origin) {
  return chrome.permissions.contains({
    permissions: ["scripting"],
    origins: [origin],
  });
}
```

移除权限后再次调用 request 通常直接授予，不会重新弹窗。移除必需权限则不会成功，remove 的返回值或拒绝原因可以用来区分这两种情况。



### 权限变更的连锁反应

两个事件报告权限集的变化，回调都接收一个 Permissions 对象。

```js
chrome.permissions.onAdded.addListener(({ permissions, origins }) => {
  console.log("新增权限", permissions, origins);
});

chrome.permissions.onRemoved.addListener(({ permissions, origins }) => {
  console.log("移除权限", permissions, origins);
});
```

> [!NOTE]
> **提醒内容**：onAdded 与 onRemoved 只报告运行期的权限集变化，扩展本身不会因为这两个事件而重载。让扩展被停用的是另一件事：扩展更新时新增了必需权限或扩大了主机权限范围，Chrome 会禁用该扩展并要求用户重新确认。用户在 chrome://extensions 手动打开「允许访问文件网址」与「在无痕模式下启用」也会改变实际能力，这两个状态分别用 extension.isAllowedFileSchemeAccess() 与 extension.isAllowedIncognitoAccess() 查询。



### 最小权限的组合原则

把权限拆成必需与可选两档，判断标准是这项能力缺了之后扩展还能不能完成它的核心用途。

- 核心用途必需的能力放 permissions，例如内容整理类扩展的 activeTab 与 scripting。
- 只在用户打开某个开关后才需要的能力放 optional_permissions，例如统计功能需要的 topSites。
- 能靠 activeTab 完成的场景不要写具体的 host_permissions。一次用户点击换一份临时授权，既没有警告，也不需要维护站点清单。
- 主机权限能写具体域名就不要写通配子域，能写通配子域就不要写全站匹配。

```json
{
  "permissions": ["storage", "scripting", "activeTab"],
  "optional_permissions": ["topSites"],
  "optional_host_permissions": ["https://*.partner.example/*"]
}
```

按这套组合，扩展在全新安装时只申请存储与注入能力，不触发任何站点访问警告；站点访问在用户点击图标时按标签页临时授予；统计与特定合作站点的访问留到对应功能被开启时再申请。

其代价是每次访问新站点都要等一次用户点击，需要在设计阶段确认这个交互代价可以接受。对确实要长期驻留在固定站点的扩展，把该站点的精确匹配模式写进 host_permissions 是更合适的选择，此时应把权限说明写进扩展描述与隐私政策，让用户在安装前就知道这份访问范围用来做什么。
