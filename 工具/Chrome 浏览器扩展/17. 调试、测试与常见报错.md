## 调试、测试与常见报错

调试扩展的难点在于一个扩展同时活在多个上下文里，每个上下文有自己的执行环境、自己的生命周期和自己的控制台。Service Worker 没有界面且随时可能被终止，内容脚本跑在别人页面的渲染进程里，popup 打开即加载、关闭即销毁。这三处的日志分散在不同入口，找不到入口是排查卡住的首要原因。

### 三层调试入口

扩展的日志按运行上下文分散在三处：Service Worker 的日志在扩展自身的 DevTools 里，扩展页面的日志在该页面的 DevTools 里，内容脚本的日志在宿主网页的 DevTools 里。三处的入口不同，必须先确认异常发生在哪一层，再去对应入口取日志。

#### Service Worker 的检查视图

Service Worker 的入口在 chrome://extensions 页面本条扩展卡片上的「检查视图」链接，点击后打开的 DevTools 面板就是该 Service Worker 的控制台。这是排查后台逻辑唯一可靠的入口。

进入之后可以按如下方式观察它的唤醒与停止行为：先复制「检查视图」上方的扩展 ID，在新标签页打开 chrome-extension://扩展 ID/manifest.json 让面板认出扩展来源，再切到应用面板的 Service Workers 窗格，用「状态」旁边的链接手动启动或停止 Service Worker。

需要注意一个副作用：打开检查视图本身会让 Service Worker 保持活跃。调试完成后应当关闭 DevTools，否则无法观察到它在真实使用中因空闲而被终止的行为。



#### 扩展页面的检查方式

扩展页面包括 popup、options、side panel 与替代页，它们的检查方式是右键点击页面内容后选择「检查」。popup 会在一段时间后自行关闭，若网络请求在面板打开前就已发出，可以在网络面板中刷新一次，这会重载 popup 而不会关闭 DevTools 面板。

替换 Chrome 内置页面的扩展页面与全页形式的选项页本身就是普通标签页，按普通网页的方式打开 DevTools 即可，也可以从扩展管理页进入它们的日志。



#### 内容脚本的检查方式

内容脚本运行在宿主网页里，日志出现在该网页的控制台。在网页 DevTools 的控制台面板中，把执行上下文下拉框从 top 切换为本扩展的上下文，就能看到内容脚本的输出。

这里有一个高频误判：扩展管理页的错误面板只记录运行时错误中的 warn 与 error 级别，内容脚本抛出的异常不会出现在扩展管理页上。网页行为异常但扩展管理页无报错时，应当直接去网页控制台查找。



### 错误面板的读法

chrome://extensions 上每条扩展卡片都有「详情」「移除」「错误」三个按钮，出现错误时「错误」按钮的文字变红，点击后展开该扩展累积的错误日志。面板右上角有「全部清除」用于清空历史日志，定位新问题时应当先清空再复现。

```text
Failed to load extension
Required value version is missing or invalid.
It must be between 1-4 dot-separated integers each between 0 and 65536.
Could not load manifest.

Permission 'activetab' is unknown or URL pattern is malformed.

Service worker registration failed. Status code: 15.
```

读这份日志要分两类对待。清单键非法会导致整个扩展加载失败并弹出对话框，Chrome 会在对话框里直接说明缺了什么；权限名拼错一类问题不会阻止加载，只在错误面板里累积一条提示。第二类是 Service Worker 注册失败，它意味着后台脚本在顶层就抛了异常，此时无法打开检查视图，必须先修掉注册阶段的错误。



### Service Worker 休眠后的排查

Service Worker 会被终止，这属于设计行为而不是故障，因此排查重点在于区分「逻辑写错」与「状态没落盘」。全局变量在 Service Worker 关闭后全部丢失，只有 chrome.storage 里的数据会跨重启保留；Web Storage 在扩展的 Service Worker 里不可用。

```js
// 每次唤醒都自检一次闹钟是否还存在，缺失则补建。
chrome.runtime.onStartup.addListener(() => void ensureAlarm());
chrome.runtime.onInstalled.addListener(() => void ensureAlarm());

async function ensureAlarm() {
  const existing = await chrome.alarms.get("sync-tick");
  if (existing) return;
  await chrome.alarms.create("sync-tick", { periodInMinutes: 1 });
}
```

另一类休眠相关故障来自监听器注册位置。事件监听器必须在 Service Worker 顶层同步注册，放在异步回调或条件分支内部时，事件唤醒 Service Worker 后找不到监听器，表现就是「第一次能用，之后再也不触发」。检查方法是在顶层逐条核对 addListener 的调用路径，确认它们不依赖任何 await 结果。

> [!IMPORTANT]
> **重要内容**：排查 Service Worker 问题时必须先关闭它的 DevTools 面板。打开检查视图会让 Service Worker 保持活跃，此时观察到的「一直不终止」是调试器的效果而非扩展行为，会掩盖真正的空闲终止缺陷。



### 未捕获异常的定位

未捕获异常指的是没有被 try 与 catch 捕获、也没有在 Promise 链上挂 catch 的错误，它会直接冒泡到所在上下文的控制台。扩展里的未捕获异常有三个常见来源：顶层代码的错误拼写、回调里访问了尚未就绪的对象、以及 Promise 链断在中间。

```js
async function loadSettings() {
  try {
    const stored = await chrome.storage.local.get("settings");
    return stored.settings ?? DEFAULT_SETTINGS;
  } catch (error) {
    console.error("[settings] 读取失败", error);
    return DEFAULT_SETTINGS;
  }
}
```

把日志写成带前缀与原始错误对象的形态，可以在控制台里用前缀过滤出本模块的输出，也可以在错误面板里直接看到堆栈。异步回调式 API 的错误不会抛出，需要通过 runtime.lastError 读取，改成 await 风格后异常才会以 Promise 拒绝的形式被 catch 捕获。



### 用 Puppeteer 加载扩展做端到端测试

端到端测试是把打包好的扩展真正装进浏览器，再用自动化工具模拟用户操作。Puppeteer 当前版本用启动选项 enableExtensions 声明要加载的扩展目录，并能在运行时用 installExtension 拿到扩展 ID。

```js
import puppeteer from "puppeteer";
import path from "path";

const extensionPath = path.join(process.cwd(), "dist");

const browser = await puppeteer.launch({
  enableExtensions: [extensionPath],
});

const workerTarget = await browser.waitForTarget(
  (target) => target.type() === "service_worker" && target.url().endsWith("background.js"),
);
const worker = await workerTarget.worker();

await worker.evaluate("chrome.action.openPopup();");

await browser.close();
```

旧版 Puppeteer 的写法是直接传 Chrome 启动参数，用 --disable-extensions-except 与 --load-extension 指定扩展目录。这两个标志是侧载扩展的底层机制，但 Google Chrome 与 Microsoft Edge 已经移除了这些命令行标志，因此新代码应优先用 enableExtensions 选项或改用自带 Chromium 的测试工具链。



### 用 Playwright 加载扩展做端到端测试

Playwright 加载扩展只能通过持久化上下文，即 chromium.launchPersistentContext(userDataDir, options) 这一个入口，因为它需要固定的用户数据目录保存已安装的扩展。测试中通常把它包成 fixture，同时把扩展 ID 一并导出。

```js
import { test as base, chromium } from "@playwright/test";
import path from "path";

export const test = base.extend({
  context: async ({}, use) => {
    const extensionPath = path.join(__dirname, "dist");
    const context = await chromium.launchPersistentContext("", {
      channel: "chromium",
      args: [
        `--disable-extensions-except=${extensionPath}`,
        `--load-extension=${extensionPath}`,
      ],
    });
    await use(context);
    await context.close();
  },
  extensionId: async ({ context }, use) => {
    let [serviceWorker] = context.serviceWorkers();
    if (!serviceWorker) serviceWorker = await context.waitForEvent("serviceworker");
    await use(serviceWorker.url().split("/")[2]);
  },
});

export const expect = test.expect;
```

关于无头模式，官方给的准确说法是：Chrome 的全新无头模式允许 Chrome 在无人值守环境中运行，启动时传入 --headless=new 标志即可，而旧的无头模式不支持加载扩展。Playwright 侧的对应做法是显式指定 chromium 渠道，它允许在无头模式下运行扩展。

```js
test("popup 显示同步结果", async ({ page, extensionId }) => {
  await page.goto(`chrome-extension://${extensionId}/popup.html`);
  await expect(page.locator("#status")).toHaveText("已同步");
});
```

> [!NOTE]
> **提醒内容**：Playwright 侧需要使用它自带的 Chromium，官方明确说明 Google Chrome 与 Microsoft Edge 已移除侧载扩展所需的命令行标志。测试中如遇扩展装不上，先确认启动的是哪个浏览器通道，而不是先去改启动参数。



### 单元测试中隔离 chrome API

单元测试的目标是不启动浏览器就验证纯逻辑，做法是把 chrome 命名空间替换成可控的模拟对象。官方给出的示例用 Jest 的 setupFiles 在全部测试之前注入一个全局 chrome 桩，再用 jest.spyOn 在单个用例里替换返回值。

```js
// mock-extension-apis.js
global.chrome = {
  tabs: { query: async () => { throw new Error("Unimplemented."); } },
};

// getActiveTabId.test.js
test("getActiveTabId 返回当前活动标签页 ID", async () => {
  jest.spyOn(chrome.tabs, "query").mockResolvedValue([
    { id: 3, active: true, currentWindow: true },
  ]);
  expect(await getActiveTabId()).toBe(3);
});
```

桩对象里的每个方法都应当默认抛出「未实现」，这样一旦业务代码调用了没有显式 mock 的 API，测试会立刻失败而不是静默返回 undefined。更省事的做法是依赖注入，把需要调用扩展 API 的部分抽出成参数传入，使待测函数本身不直接引用 chrome 命名空间。



### 按现象分组的常见报错清单

常见报错按出现的时机可以分成三组：加载与清单类问题让扩展根本装不上，消息与序列化类问题发生在上下文通信时，Service Worker 与生命周期类问题只在运行一段时间后暴露。按组定位比逐条搜索报错文本更快。

#### 清单与权限类报错

这一组报错出现在扩展加载或重新加载时。典型的文本与含义是：Required value version is missing or invalid 表示 version 字段缺失或格式不合法，合法格式是 1 到 4 个以点分隔的整数，每段介于 0 与 65536 之间；Could not load manifest 表示清单无法解析，通常来自 JSON 语法错误或键名拼写错误；Permission 某某 is unknown or URL pattern is malformed 表示权限名或匹配模式写错；content_security_policy.extension_pages 相关的 Insecure CSP value 表示在扩展页面策略里加入了超出最低策略的宽松来源。



#### 消息与序列化类报错

这一组报错发生在上下文之间通信时。Receiving end does not exist 一类连接失败通常有三个成因：目标上下文在当前时刻并不存在，例如内容脚本尚未注入或页面不匹配声明；接收方的监听器注册在异步回调内部，事件到达时还没有注册；以长连接通信时端口另一端已经卸载。另一类是响应无法序列化导致的发送失败，报错文本会说消息无法序列化，成因是把函数、DOM 节点或循环引用对象放进了响应体。



#### Service Worker 与生命周期类报错

这一组报错表现为「刚安装能用、过一会儿失效」。带错误的注册失败会给出注册状态码与随后的未捕获异常，两者要一起读，状态码只说明注册没成功，真正的原因在紧跟其后的 TypeError 或 ReferenceError 里。另一类表现是事件不再触发，绝大多数情况是监听器被放进了异步流程，修复方式是把它移回顶层同步注册。

> [!TIP]
> **建议内容**：排障时按固定顺序收敛范围：先看 chrome://extensions 的错误面板确认扩展是否加载成功，再用检查视图确认 Service Worker 是否被唤醒，接着切到宿主网页的控制台确认内容脚本是否注入，最后才去读业务逻辑。跳过前三个检查点直接读代码，是排查时间变长的主要原因。
