## 扩展沙箱、CSP 与代码安全边界

扩展的代码安全边界由三条互相配合的机制构成：远程代码禁令决定代码能从哪里来，内容安全策略决定代码能怎样被执行，沙箱与可网络访问资源声明决定执行环境与包内资源能被谁碰到。

这三条机制共同划出了 MV3 与 MV2 最大的差别。MV2 的后台页面是普通网页，可以加载远程脚本、可以用 eval 拼表达式；MV3 把扩展改造成安装包内自洽的程序，全部逻辑随包分发，运行期不再引入新的可执行内容。

### MV3 的远程代码禁令

远程代码禁令是 MV3 的硬约束：扩展的全部逻辑必须是扩展包的一部分，运行期不得加载与执行远程托管文件。它同时是平台限制与商店政策。

#### 什么算远程代码

判定口径是「这段内容是否会被当作代码执行」，而不是「它从哪里下载」。以下都在禁止之列：

```text
从开发者服务器拉取的 JavaScript 文件
来自 CDN 的任何脚本
第三方库自带、运行期才去取远程代码的逻辑
把 fetch 回来的字符串交给 eval 或 new Function
把远程返回的内容拼进脚本元素再插入页面
远程托管的 WebAssembly 模块
把远程返回的 JSON 当作代码解释执行
```

间接引入同样被禁止。第三方库如果在运行期按需拉取额外代码，责任在集成它的扩展身上；有些库在打包时工作正常，上线后才在特定路径触发动态导入，问题会以偶发的 CSP 报错形式出现。

> [!IMPORTANT]
> **重要内容**：禁令针对的是远程内容的执行，不是远程内容的获取。同一个字符串，作为 JSON 解析后读字段是合规的，交给 eval 执行就是违规。改写、混淆与分片加载都不能改变判定，因为判定发生在代码真正被执行的那一刻。



#### 仍然允许的远程数据与三个例外通道

从远程取数据并在扩展里使用完全合规，这类用法构成大量扩展的主体逻辑：运行期拉取 JSON 配置，由本地代码根据配置决定启用哪些功能；调用远程 Web 服务做服务端计算，扩展只负责发请求与展示结果；展示远程图片、音频与视频。

```js
async function loadRuleConfig() {
  const response = await fetch('https://example.com/rules.json');
  if (!response.ok) throw new Error(`配置拉取失败：${response.status}`);
  const config = await response.json();
  await chrome.storage.local.set({ ruleConfig: config });
  return config;
}
```

需要在页面里用外部库时，把库文件下载进包里，在注入时与业务脚本一并列入 files 数组，由浏览器从扩展包读取；需要更强动态性时用 func 注入函数并通过 args 传值。

平台在严格禁令之外保留三个窄口：scripting.insertCSS 的 css 字段可注入远程托管的样式内容；devtools.inspectedWindow.eval 可在被检查页面上下文中执行脚本；debugger.sendCommand 可在调试目标中执行脚本。三者的共同点是执行位置不在扩展自己的上下文里，因此不构成把远程代码搬进扩展进程的路径。



### 扩展页面的默认 CSP

内容安全策略在清单里由 content_security_policy 键声明，MV3 下它是一个对象，分别对应扩展页面与沙箱页面。

#### extension_pages 的确切取值

未声明时的默认值等同于下面这段：

```json
{
  "content_security_policy": {
    "extension_pages": "script-src 'self'; object-src 'self';",
    "sandbox": "sandbox allow-scripts allow-forms allow-popups allow-modals; script-src 'self' 'unsafe-inline' 'unsafe-eval'; child-src 'self';"
  }
}
```

extension_pages 作用于扩展里的网页上下文与工作线程上下文，包括弹出窗口、后台 Service Worker，以及扩展打开的含 HTML 或框架的标签页。这段策略的效果是：脚本与对象只能来自扩展包自身，WebAssembly 被停用，内联脚本不能运行，字符串不能被当作代码求值。



#### 可改的取值与安装期报错

扩展页面还受一条最低策略约束，等价于 script-src 取 self 与 wasm-unsafe-eval、object-src 取 self。开发者可以在最低策略之内收紧，但不能放宽：script-src、object-src 与 worker-src 三个指令只允许出现 self、none、wasm-unsafe-eval 三种取值，未打包加载的扩展额外允许本地主机来源。

```text
'content_security_policy.extension_pages': Insecure CSP value "'unsafe-eval'" in directive 'script-src'.
```

越界的取值会在安装时直接抛出上面这类错误。因此扩展页面里无法恢复 eval，也无法恢复内联脚本，这一点与沙箱页面形成明确分工，沙箱页面的策略没有这套限制。



### sandbox 清单键与沙箱页面

sandbox 键把随包分发的一批页面标记为沙箱页面，它们运行在唯一的来源下，与扩展的其它部分隔开。

#### 声明写法与默认沙箱 CSP

```json
{
  "sandbox": {
    "pages": ["sandbox/template.html"]
  },
  "content_security_policy": {
    "extension_pages": "script-src 'self'; object-src 'self';",
    "sandbox": "sandbox allow-scripts; script-src 'self' https://example.com"
  }
}
```

pages 是相对扩展根目录的路径数组，只需要列出预期会在窗口或框架中加载的页面；作为资源被引用的文件不必列入，因为它们随嵌入方一起进入沙箱。未声明 sandbox 策略时使用默认值，其中的 script-src 同时允许 unsafe-inline 与 unsafe-eval，这就是沙箱页面里 eval 能工作的原因。自定义策略可以比默认值更严，但必须包含 sandbox 指令，且不得包含 allow-same-origin 令牌。

> [!WARNING]
> **警告内容**：不要在沙箱策略里加 allow-same-origin。加上之后沙箱页面的来源会与嵌入它的页面一致，页面里的脚本便能反过来操作嵌入方的文档对象，隔离随即失效，而这个失效是静默的，不会产生任何报错。



#### 能力边界与通信方式

进入沙箱带来两处封禁与一处放开。封禁一是无法访问扩展 API，全部命名空间都不可见；封禁二是无法直接访问未经沙箱化的页面，两者之间只能通过 postMessage 通信。放开的是内容安全策略，沙箱页面可以使用内联脚本，也可以使用 eval 与 new Function。

这套设计的意图很明确：把必须求值字符串的模板库、语法解析库关进一个既没有数据也没有 API 的房间，即便库存在漏洞，攻击者能拿到的也只是沙箱内部的东西。因此沙箱页面的定位应严格限定为纯计算与渲染。

```html
<iframe
  id="sandboxFrame"
  src="sandbox/template.html"
  sandbox="allow-scripts"
  style="display: none">
</iframe>
```

```js
function renderInSandbox(frame, payload) {
  return new Promise((resolve) => {
    const onMessage = (event) => {
      if (event.source !== frame.contentWindow) return;
      window.removeEventListener('message', onMessage);
      resolve(event.data.result);
    };
    window.addEventListener('message', onMessage);
    frame.contentWindow.postMessage(payload, '*');
  });
}
```

数据必须可序列化，函数与类实例不能直接传递。接收侧同样要校验来源，只处理来自预期框架的消息；沙箱页面返回的内容仍属外部输入，写入扩展界面之前要按不可信数据处理。

> [!TIP]
> **建议内容**：把沙箱当成可执行的第三方代码的隔离间，而不是可以随便运行东西的地方。凡是不需要求值字符串的逻辑都应留在扩展页面里，沙箱页面越小、职责越单一，被攻破时的暴露面就越小。



### web_accessible_resources 的暴露面

默认情况下扩展包内的所有资源都不可被网页访问。这条默认值本身就是安全设计：恶意网站若能探测已安装的扩展，就能据此对用户做指纹识别，也能顺着扩展暴露的接口去寻找漏洞。

#### MV3 的写法与四个字段

MV3 下这个键改为对象数组，每项把一组资源映射到一组可访问者。

```json
{
  "web_accessible_resources": [
    {
      "resources": ["images/logo.png", "styles/injected.css"],
      "matches": ["https://example.com/*"]
    },
    {
      "resources": ["widget/*.html"],
      "matches": ["https://*.example.com/*"],
      "use_dynamic_url": true
    },
    {
      "resources": ["bridge.js"],
      "extension_ids": ["abcdefghijklmnopabcdefghijklmnop"]
    }
  ]
}
```

resources 是从扩展根目录出发的相对路径数组，支持星号通配。matches 是匹配模式数组，只有来源参与匹配，且来源匹配包含子域名。extension_ids 是允许访问这些资源的扩展 ID 数组。use_dynamic_url 为 true 时资源只能通过动态 ID 访问，动态 ID 每个会话生成一次，浏览器重启或扩展重新加载都会重新生成，因此网页无法把它当作稳定指纹长期追踪用户。每个数组元素必须同时含 resources 以及 matches 或 extension_ids 中的一个，二者都不给会直接被拒绝。

MV2 里这个键是路径字符串的平铺数组，暴露给全部网页且没有范围控制；MV3 强制显式声明每一项暴露给谁，原因就是 MV2 的写法让绝大多数扩展在不自知的情况下扩大了暴露面。



#### 暴露风险与收敛方式

资源可被网页访问带来三类风险：探测，网页通过加载成功与失败判断哪些资源存在，进而推断用户装了哪些扩展及版本；接口暴露，被暴露的脚本与页面含有的可被外部触发的逻辑成为攻击入口；数据泄漏，网页可以自行加载被暴露的内部页面并观察其行为。

收敛手段按效果排序：把 resources 从通配改为列出具体文件；把 matches 从全网址收窄到实际需要的站点；为纯静态资源开启 use_dynamic_url；只暴露不得不暴露的内容。

> [!CAUTION]
> **注意内容**：内容脚本自身不需要列进这个键，这是它与被注入资源的本质区别。反过来，把内容脚本的依赖文件批量暴露出去，等于把注入逻辑与内部数据结构一并交给任何网页读取；需要共享的样式与图片应按最小集合单独列出。

资源通过扩展协议加包 ID 与路径的网址访问，该网址可用 runtime.getURL 生成，响应会带上正确的跨源头，因此 fetch 可以直接取用。从网页来源发起的导航默认被拦截，只有被列出的资源才允许；无痕模式下还要求清单的 incognito 字段取值为 split，否则导航会被屏蔽。



### 扩展来源、内容脚本与页面 CSP

扩展页面运行在扩展协议提供的独立来源下，每个扩展一个来源，与任何网站的来源都不同。这条来源边界是扩展安全模型的地基：扩展页面默认无法读取网页的 DOM，网页也无法读取扩展页面的内容，跨来源的交互一律回到消息传递。

内容脚本是一个受控的例外。它被注入页面框架中，可以操作 DOM，但脚本运行在隔离世界里。隔离世界与页面世界共享同一个文档对象模型，却使用各自独立的 JavaScript 环境：页面脚本定义的全局变量在隔离世界里不可见，反之亦然，两个世界能共享的只有 DOM 节点本身以及显式挂到节点上的数据。

内容脚本不受宿主页面内容安全策略的约束。它执行的是扩展包内的文件，运行在隔离世界，加载与执行由扩展自身的 CSP 管辖，页面禁止内联脚本或限制脚本来源都不会影响它的运行。

这条特性有明确的边界：内容脚本一旦把内容交给页面世界，那段内容就重新落回页面 CSP 的管辖之下。在隔离世界里用动态创建的脚本元素去执行字符串，仍会被页面策略拦截；即便不被拦截，这种写法也会把逻辑暴露给页面。

> [!NOTE]
> **提醒内容**：内容脚本能够看到页面 DOM 与挂到 DOM 上的数据，因此任何被当成「已经校验过」的东西都不能停在 DOM 上。校验只能在扩展侧进行，DOM 只用于传达界面结果，用 DOM 交换数据时双方都能读到节点内容，这条通道不能承载秘密。



### 必须留在扩展侧的数据

把边界机制落到实处，就是把「哪些数据永远不进入页面」这件事定下来。以下三类数据必须只存在于扩展的来源内。

第一类是凭据与令牌：接口密钥、刷新令牌、用户身份标识、设备标识。它们一旦进入页面世界或 DOM 属性，任何页面脚本都能读取，等价于公开。第二类是内部逻辑与配置：规则表、端点清单、功能开关、内部接口的字段结构，页面拿到它们就能构造针对性请求或绕过功能限制。第三类是用户行为数据：浏览记录、采集内容、标签页元数据，这类数据的读取本身已是高敏感的权限行为，写入页面 DOM 会让读取权限在用户不知情的情况下扩散到网页侧。

对应做法有三条：跨上下文只传最小必要字段，传聚合结果而不是原始数据；用消息通道而不是 DOM 交换需要保密的数据；扩展页面与服务端交互时把请求能力留在 Service Worker 里，让页面只负责发起意图。
