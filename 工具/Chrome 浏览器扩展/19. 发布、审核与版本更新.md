## 发布、审核与版本更新

发布是把构建产物交给 Chrome 应用商店、再通过审核进入用户浏览器的过程。这条链路上有三个独立的门槛：账号门槛决定能不能提交，政策门槛决定提交会不会被拒，审核时长门槛决定多久能上线。三者互相牵连，宽权限与模糊的功能描述会同时拉高后两道门槛。

### 开发者账号与注册费

注册 Chrome 应用商店开发者账号是一次性付费流程，费用为 5 美元，付费后账号可长期发布商品，不再按年或按商品收费。首次访问开发者信息中心会直接跳转到注册页，同意开发者协议与政策并完成支付后该页不再出现。

注册邮箱的选择比金额更值得留意：所有与扩展有关的重要邮件都会发送到该地址，因此应当使用专门且经常查看的邮箱；账号一旦被删除，与该邮箱绑定的身份不能再次用于注册新账号。账号页面还需要填写发布商名称、验证联系邮箱，实际地址只在提供付费功能或订阅时才必填。受信任的测试人员可以在这里按邮箱逐个列出，但该字段不接受群组邮箱，需要用内容级的公开范围加 Google 群组来实现分组测试。

单个开发者账号已发布的扩展数量上限是 20 个，主题不受此限制。达到上限后可以申请提高配额，审核会参考现有商品质量与账号历史，账号曾被暂停、曾因违规下架或商品长期被评为低质量时会更容易被拒。



### 发布者账号的成员与角色

发布商账号支持直接邀请成员协作，自 2026 年 4 月起开发者可以在信息中心内邀请成员并为其分配四种角色之一。这套机制取代了此前为每位协作者单独创建发布商、或把成员加入 Google 群组的做法，并且不再收取注册费。

按账号级权限划分的做法有一个直接好处：商品级的操作记录与申诉入口都归属到具体账号，不会因为共用凭据而失去可追溯性。团队协作时应当按最小职责分配角色，把删除、转移与申诉这类高风险操作的权限收拢到少数人手里。

> [!NOTE]
> **提醒内容**：成员邀请功能免除的是新增协作账号的 5 美元注册费，账号本身的首次注册费不受影响。分配角色前先确认邀请对象使用的 Google 账号就是他将长期持有的账号，后续更换会牵涉商品归属与审核事件的追溯。



### 上架流程与商店素材要求

上架流程分四步：在开发者信息中心点击添加新商品并上传 ZIP 压缩包，在打包标签页确认产物信息，逐项填写商品详情、隐私与分发三个标签页，最后点击提交审核。压缩包中清单与内容均有效时才能进入下一步，打包标签页在首次创建后不可修改。

商店素材按官方要求逐项准备：128x128 像素的商店图标；至少一张 1280x800 像素的屏幕截图，最多五张；440x280 像素的小宣传图块；1400x560 像素的滚动式宣传图块，Marquee 宣传图块为可选；同一节还要求提供一段展示功能的 YouTube 视频链接。此外需要填写详细说明、主要类别与商品语言。图片质量会影响商品在商店中的曝光程度。

```text
商品详情  →  说明、类别、语言、图标与宣传图片
隐私      →  单一用途说明、逐权限理由、远程代码声明、数据使用方式
分发      →  是否含应用内购买、公开范围、地理分布
```

分发标签页的公开范围有三档：公开会在商店中列出并允许所有用户安装；不公开列出不创建商品详情，但只要知道商品网址就能安装；不公开则只允许指定用户安装，常用于公开发布前的测试。三档的政策要求与审核流程完全相同。

> [!CAUTION]
> **注意内容**：与正式版并行提交 Beta 版时，必须在扩展名称末尾添加「开发版本」或「测试版」标签，并在说明中写明该扩展用于 Beta 测试。缺少这两处标注时，两条商品都可能按重复内容垃圾政策被移除。



### 单一用途与最低功能政策

单一用途政策要求扩展必须有一个狭窄且易于理解的单一用途，不允许要求用户接受互不相关的功能组合。若两块功能明显独立，正确做法是拆成两个扩展，由用户分别安装与卸载。官方列举的典型违规形态包括：既展示评分与评论又向网页注入广告，大而全的工具栏式入口，邮件通知叠加新闻聚合，以及篡改搜索体验且不尊重用户既有搜索设置的新标签页扩展。

最低功能政策收紧了下限：不允许发布以安装或启动另一个应用、主题、网页或扩展为唯一用途的扩展；功能损坏的扩展不被接受，例如所指向的站点已下线或声明的功能不可用；扩展必须提供基本可用的功能与价值。此外，仅提供跳转链接、实际功能由第三方服务承担的扩展，以及仅在模板上做微小改动、价值极低的扩展，都在这条政策的射程内。



### 最小权限、数据用途声明与隐私政策

权限使用政策要求申请实现功能所必需的最窄权限；如果同一功能可以用多种权限实现，必须选择对数据或功能访问面最小的那一种；不得为了尚未实现的功能预留权限。凡是清单里出现却无法解释的权限，都应当在提交前删除而不是留在隐私标签页里辩解。

隐私标签页需要填写四类内容：单一用途说明、逐权限理由、是否执行远程代码、以及数据使用方式。数据使用方式由两组复选框构成，第一组用于披露扩展收集的数据类型，第二组用于确认遵守各项披露声明并认证符合有限使用政策。合规的底线是：披露声明会直接展示给 Chrome 用户，并且必须与账号页面中填写的隐私政策网址保持一致。

隐私政策链接是必填项，政策内容应当说明数据的收集、使用与披露方式。有限使用政策进一步规定：只能把用户数据用于已披露的做法；只能收集、使用或传输为实现已披露单一用途所必需的数据（含由此聚合、匿名化或派生的数据，以及抓取或自动采集的数据）；除面向用户并在商店页面与产品界面显著说明的功能外，禁止收集与使用浏览活动；不得允许人工读取用户数据，除非取得用户对特定数据的明确同意等有限例外。

```text
用途限制：只把用户数据用于已披露的做法
数据范围：只收集、使用或传输实现已披露单一用途所必需的数据
浏览活动：除在商店页面与产品界面显著说明的用户功能外，一律禁止收集与使用
人工读取：默认禁止，仅用户对特定数据的明确同意等有限情形例外
```

```json
{
  "manifest_version": 3,
  "name": "Meter Reader",
  "version": "1.5.0",
  "minimum_chrome_version": "122",
  "permissions": ["storage", "alarms"],
  "host_permissions": ["https://portal.example.com/*"]
}
```

清单里的 minimum_chrome_version 声明了可安装的最低 Chrome 版本，低于该版本的浏览器会拒绝安装。把版本号写成实际依赖能力的最低值是一种主动收敛：它既避免用户装上一个必然报错的版本，也让审核看到的权限组合与实现方式一致。

> [!WARNING]
> **警告内容**：在隐私标签页的远程代码一栏声明为未使用、而代码实际存在远程逻辑通道时，提交会被直接拒绝。官方明确说明调用远程代码却未在对应字段声明并说明理由的扩展将被拒绝，远程代码本身也会触发额外审查并拉长审核时间。



### 常见拒绝原因与整改方式

违规处置按严重程度分四档，整改方式各不相同。第一档是拒绝：提交内容违反政策但不构成严重违规时，该次提交被拒，商店中的商品详情、说明文字、图片资源、隐私披露与已发布的安装包都保持不变，最终用户也不会收到通知，此时按拒绝邮件点明的政策条目修正后重新提交即可。

第二档是警告：定期审核发现已发布内容存在轻微违规时，审核方向发布商邮箱发出警告邮件，通常给出 7 到 30 天的整改期，期间商品仍在商店中可下载、现有用户也能更新到最新成功发布的版本；用标准提交流程提交修复版本即可解除警告，超期未解决则扩展被移除。

第三档是移除：审核者在已发布版本中发现中等或更严重违规时立即移除，或警告期过后延迟移除。移除通常不是永久性的，发布者可以提交修复问题并通过审核的新版本重新上线；扩展被移除后商店列表返回 404，几周内未解决的扩展会被 Chrome 自动停用并通知用户。

第四档是恶意软件与严重违规：涉及恶意软件分发、规避审核的欺骗行为或屡次严重违规时，团队会采取更严厉措施，不向发布商提供违规细节，严重情况下永久暂停开发者账号，扩展在所有用户设备上被停用且无法重新启用。



### 审核时长的影响因素

审核时长可能差异很大。官方给出的历史基准是：2021 年初大多数提交在 24 小时内完成审核，其中 90% 以上在三天内完成；若等待超过三周仍未审完，可以联系开发者支持请求协助。需要留意的是，所有提交无论来自新开发者还是有大量活跃用户的资深开发者，都走同一套审核系统，并且新商品与版本更新都要完成同样的审核流程。

有四类信号会使审核人员更仔细地检查扩展，从而拉长审核：新开发者、新的附加信息、危险的权限请求、重大代码更改。在扩展被拒或收到警告之后，后续审核也可能比平常更慢。

在此之上还有两类结构性因素。一是权限规模：请求广泛主机权限（覆盖全部站点的通配模式）或敏感执行权限时，审核必须逐项验证权限是否确实必需且使用得当，其中 tabs 与 downloads 一类权限会直接执行，cookies 与 webRequest 一类权限需要叠加主机权限授予才会生效。二是代码数量与格式：代码越多验证工作量越大，官方明确禁止混淆，因为混淆会显著增加验证复杂度；压缩允许但同样可能让代码更难审阅，因此官方建议尽可能按作者原有状态提交代码并保持结构易于理解。



### 申诉流程

申诉是就政策执行措施请求复核的正式渠道，自 2026 年 4 月起可以直接在 Chrome 应用商店开发者信息中心内发起，不再需要先在一站式支持页面手工填写独立表单。商品详情页面与发布商账号页面上都提供申诉按钮。

新流程替代了大部分手工步骤：发起申诉时系统自动预填扩展 ID、违规详情与开发者联系信息，无需自行查找参考代码；由于发起者已登录，系统会自动验证其是否有权针对该商品或账号申诉，避免账号不匹配错误；创建申诉后，后续沟通仍通过电子邮件进行。

提交逻辑上还有两条约束需要提前规划。若发布商账号被暂停，商品级申诉按钮会被停用，必须先解决或申诉账号中止，之后才能针对商品申诉，因为账号级问题通常是根本原因。系统还会阻止针对同一审核事件的重复申诉，但有一条例外：与交易者验证相关的申诉单独处理，仍需通过一站式支持表单提交。

> [!IMPORTANT]
> **重要内容**：政策明确开发者对同一违规只有一次申诉机会，复核结论作出后不再受理针对同一违规的再次申诉。提交前应当把证据、整改说明与时间线一次讲清；同时官方鼓励善意申诉，轻率申诉或滥用申诉流程可能导致后续申诉权被取消。



### 更新、灰度与版本号处理

更新走与首次发布相同的机制：递增清单中的 version 字段，重新打包并按标准流程提交，全部提交都要经过完整审核。发布节奏上有三种控制手段：取消自动发布复选框或事后选择延迟发布，可以把上线时间控制在审核通过之后；审核通过后必须在 30 天内完成发布，超期未发布会退回草稿状态并需要重新提交审核；地理分布可以设为所有地区或指定国家与地区。

灰度发布借助公开范围实现：先用受信任的测试人员或不公开列出做小范围验证，确认稳定后再切换到公开。上传的版本号必须严格递增，版本号不合法或未递增时提交不会被接受。

```text
1.4.0  → 1.4.1   补丁：修 bug，权限不变
1.4.1  → 1.5.0   次版本：新增功能，可能新增权限
1.5.0  → 2.0.0   主版本：架构调整或移除能力
```

每次新增权限都会在用户侧触发权限变更提示，部分用户此时会停用扩展，因此版本规划应当把权限增长集中到少数几个版本，而不是零散地一轮加一个。



### 向外部组织私有发布

向外部组织私有发布用于把扩展交付给企业客户而不公开上架，自 2026 年 2 月起成为商店内的一个正式企业发布选项。此前的企业发布只能面向开发者自己所属的企业，现在可以把扩展不公开地部署到批准该开发者的外部组织。

启用与流程分三步。第一，在账号页面的组织发布区域点击生成审批链接，得到一条供组织管理员使用的链接，通过任意沟通渠道发给对方管理员联系人。第二，管理员访问该链接后会看到发布商名称、联系邮箱与交易者声明等信息，确认后即可批准；验证联系邮箱、完成交易者验证并取得发布商徽章能让审批页展示尽可能完整的信息。第三，获得批准后在分发页面选择新增的发布范围，像平常一样提交商品，商品进入标准审核流程，发布后只有被选定的组织可见。

```text
账号页面 → 组织发布 → 生成审批链接
管理员访问审批链接 → 核对发布商名称、联系邮箱、交易者声明 → 批准
分发页面 → 选择面向该组织的发布范围 → 照常提交，走标准审核
```

发布后的管理仍由对方的组织管理员承担，他们用现有的商品级控件管理具体扩展，例如通过策略决定是否强制安装或列入许可名单。与之并行的另一条企业通道是网域发布，它只允许把扩展发布到本组织专用的 Chrome 应用商店内，组织外无法查看。



### 上架后核对清单

提交前的核对按顺序走一遍，能滤掉绝大多数可避免的退回。同一份清单也适用于每次版本更新。

```text
清单 version 已递增，minimum_chrome_version 与实现匹配
压缩包根目录直接包含 manifest.json，无多余父目录与源码
权限与主机权限逐条能在隐私页面写出理由
隐私政策网址可达，内容覆盖收集、使用与披露
素材尺寸齐全：128x128 图标、至少一张 1280x800 截图、440x280 与 1400x560 宣传图块
公开范围与地理分布已确认，Beta 版已添加相应标签
发布者账号已启用两步验证（发布与更新均要求）
```

提交后可以按状态推进预期：新商品与更新都走同一套审核，多数提交在数天内出结果；若等待超过三周仍无结论，应当通过开发者支持请求协助而不是重复提交。审核结果与后续申诉都会发送到发布商邮箱，因此保持该邮箱可正常接收外部邮件是必要前提。

> [!TIP]
> **建议内容**：把上架核对清单固化进发布脚本，能在打包阶段自动断言的部分就不要留到人工检查：清单必填字段、版本递增、产物根目录位置、压缩包内是否混入源码与映射文件，这四项都可以在 CI 里自动失败，人工只负责素材与文案。
