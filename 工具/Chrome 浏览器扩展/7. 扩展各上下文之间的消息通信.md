## 扩展各上下文之间的消息通信

### 消息通信的两种模型

一个扩展由 Service Worker、扩展页面与内容脚本三类上下文组成，扩展消息 API 是它们之间唯一通用的数据通道。

消息 API 有两种模型，共用同一套序列化规则与同一批监听事件：

- 一次性请求：调用 runtime.sendMessage 或 tabs.sendMessage 发出一条消息，接收端可选地回一条响应，通道随响应结束。
- 长期连接：调用 runtime.connect 或 tabs.connect 建立一条命名通道，两端各持一个 runtime.Port 对象，可反复双向收发，直到任一端断开。

选择依据是消息是一条还是持续一串。单次查询与命令用一次性请求，需要推送进度、订阅事件或按会话维护状态时用长期连接。



### 一次性消息的发送与响应

chrome.runtime.sendMessage(extensionId?, message, options?) 向扩展内的监听器发一条消息，返回 Promise，在扩展上下文内部使用时自 Chrome 99 起支持 Promise 写法。options 里的 includeTlsChannelId 字段控制是否把 TLS 通道 ID 传给 onMessageExternal。

Chrome 122 补齐了全部异步扩展 API 方法的 Promise 支持，回调式签名同时保留。本文示例统一使用 await 写法，等价的回调写法在任何受支持的版本上同样可用。

```js
// 内容脚本侧：发起一次请求并等待响应
const tabId = await getTabId();
const response = await chrome.runtime.sendMessage({ type: "queryTitle", tabId });
if (response?.ok) {
  renderTitle(response.title);
}
```

接收端用 chrome.runtime.onMessage 监听，监听器签名为 (message, sender, sendResponse) => boolean | Promise | undefined。

```js
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type !== "queryTitle") return;
  sendResponse({ ok: true, title: lookupTitle(message.tabId) });
});
```

sendResponse(response?) 同步调用即可完成响应，不传参数调用它时发送端收到 null。sender 是 MessageSender 对象，常用字段有 id（发送方扩展 ID）、url、origin（Chrome 80 起）、tab、frameId 与 documentId（Chrome 106 起）。sender.url 表示发送方所在文档的网址，发送方位于 iframe 时给的是该框架的网址，而不是宿主页面的网址。



### 异步响应的两种写法

默认要求同步调用 sendResponse。异步操作完成后才回复时，有两种写法。

返回字面量 true 让通道保持打开，直到 sendResponse 被调用。

```js
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type !== "fetchPrice") return;
  fetch("https://api.example.com/price")
    .then((res) => res.json())
    .then((data) => sendResponse({ ok: true, price: data.price }))
    .catch((error) => sendResponse({ ok: false, error: error.message }));
  // 必须返回字面量 true，返回其它真值不起作用
  return true;
});
```

从 Chrome 148 起，监听器可以直接返回 Promise，其敲定值作为响应发回。该能力在逐步放量，扩展需要兼容尚未开启该行为的浏览器；无论是否开启，返回 true 的写法始终有效。

```js
chrome.runtime.onMessage.addListener(async (message) => {
  if (message.type !== "fetchPrice") return;
  const res = await fetch("https://api.example.com/price");
  if (!res.ok) throw new Error(`Fetch failed: ${res.status}`);
  const data = await res.json();
  return { ok: true, price: data.price };
});
```

> [!WARNING]
> **警告内容**：把监听器写成 async 函数后它总返回 Promise，即使函数体内一个 return 语句都没有。此时 Promise 隐式敲定为 undefined，Chrome 把它翻译成 null 发给发送端，可能抢在另一个监听器之前结束通道。监听器内需要条件分支时，用普通函数加显式 return true；如果确实用 async 函数，要让每个分支都有返回值。

Chrome 146 起，监听器同步抛错或返回被拒绝的 Promise 时，发送端的 sendMessage 调用会被拒绝并带上错误消息。拒绝值必须是 Error 实例，用 null 或 undefined 拒绝只能得到一条笼统的错误。监听器若返回无法序列化的响应，发送端收到 Could not serialize message 这类错误。

同一事件注册多个监听器时，只有最先响应、最先拒绝或最先抛错的那个会影响发送端，其余监听器的结果一律被忽略。



### 长连接与 Port 接口

chrome.runtime.connect(extensionId?, connectInfo?) 返回 runtime.Port 对象。connectInfo 含 name 与 includeTlsChannelId 两个字段，name 会出现在对端 onConnect 收到的 Port.name 上，用于区分不同用途的通道。

```js
// 内容脚本侧：建立通道并持续收发
const port = chrome.runtime.connect({ name: "inspector" });

port.onMessage.addListener((message, fromPort) => {
  if (message.type === "highlight") highlightNode(message.selector);
});

port.onDisconnect.addListener((closedPort) => {
  console.warn("通道已关闭", closedPort.name, chrome.runtime.lastError?.message);
});

port.postMessage({ type: "ready", url: location.href });
```

```js
// Service Worker 侧：接住每一条进来的连接
const inspectedByTab = new Map();

chrome.runtime.onConnect.addListener((port) => {
  if (port.name !== "inspector") return;
  port.onMessage.addListener((message) => {
    inspectedByTab.set(port.sender.tab.id, message);
    port.postMessage({ type: "ack" });
  });
});
```

Port 的成员分工如下：

- name：通道名，取自 connect 时 connectInfo 的 name 字段。
- postMessage(message)：向通道另一端发消息，端口已断开时抛错。
- onMessage：事件，回调签名为 (message, port) => void。
- onDisconnect：事件，回调签名为 (port) => void。
- disconnect()：立即断开端口，对已断开的端口调用没有任何效果。
- sender：MessageSender 对象，只存在于传给 onConnect、onConnectExternal、onConnectNative 的端口上。

onDisconnect 在下列情形触发：另一端没有 onConnect 监听器；承载端口的标签页卸载；调用 connect 的框架卸载；所有收到端口的框架都卸载；另一端主动调用了 disconnect。本端自己调用 disconnect 时，该事件只在另一端触发。一个端口可以同时接到多个接收端，因此 onDisconnect 可能触发多次。

> [!CAUTION]
> **注意内容**：端口断开不代表对端一定消失，也不代表会话应当结束。tabs.connect 会让标签页里每个框架各触发一次 onConnect，收到端口的框架只要卸载一个就可能触发一次 onDisconnect。按端口维护状态时，先确认本端是否还持有其它存活端口，再决定是否清理。



### 定向发送与帧选择

chrome.tabs.sendMessage(tabId, message, options?) 从扩展侧向标签页里的内容脚本发消息，返回 Promise（Chrome 99 起）。runtime.sendMessage 不能发往内容脚本，这是两个 API 的分工。

options 的两个字段都把消息限制到特定目标：

- frameId：只发给指定框架，不指定则发给标签页内所有框架。
- documentId：只发给指定文档，Chrome 106 起可用。

```js
async function askFrame(tabId, frameId, message) {
  try {
    return await chrome.tabs.sendMessage(tabId, message, { frameId });
  } catch (error) {
    // 该帧没有监听器时，Promise 以「接收端不存在」类错误被拒绝
    return null;
  }
}
```

不指定 frameId 时，标签页内每个装了监听器的框架都会收到消息，但只有最先调用 sendResponse 的那个能被发送端看到。需要多个框架各回一份数据时，改用 tabs.connect 建长连接，或让每个框架带上自己的 frameId 分别回传。



### 跨扩展程序与网页通信

向另一个扩展发消息时，把扩展 ID 作为 sendMessage 或 connect 的第一个参数，对端用 chrome.runtime.onMessageExternal 与 onConnectExternal 接收。

```js
chrome.runtime.onMessageExternal.addListener((request, sender, sendResponse) => {
  // 外部事件任何来源都能触发，先校验发送方扩展 ID
  if (sender.id !== "abcdefghijklmnoabcdefhijklmnoabc") return;
  if (request.query === "capabilities") {
    sendResponse({ capabilities: listCapabilities() });
  }
});
```

> [!IMPORTANT]
> **重要内容**：onMessageExternal 与 onConnectExternal 的触发来源不受本扩展控制，任何知道扩展 ID 的扩展或网页都能调用。处理请求前先比对 sender.id 或 sender.url，只暴露最小必要的数据，不要把内部能力包装成通用代理。

网页与扩展通信需要在 manifest.json 里声明 externally_connectable 键，用 matches 列出允许发消息的网站。

```json
{
  "externally_connectable": {
    "matches": ["https://*.example.com/*"]
  }
}
```

网页侧用 chrome.runtime.sendMessage(extensionId, message) 或 chrome.runtime.connect(extensionId) 发起，对端同样是 onMessageExternal 与 onConnectExternal。方向是单向的：扩展不能主动向网页发消息，只能应答网页的请求。



### 序列化格式与结构化克隆

默认序列化是 JSON，消息与响应都必须是 JSON.stringify 能处理的值。undefined 会被转成 null，函数、Map、Set、BigInt 等类型无法传输。

Chrome 148 起可以改用结构化克隆，在 manifest.json 里加一个键即可对整份扩展全局启用。

```json
{
  "manifest_version": 3,
  "name": "Data Bridge",
  "version": "1.0.0",
  "message_serialization": "structured_clone"
}
```

启用后 Map、Set、Date、Error、File、Blob 等类型可以直接传输，代价是一组明确的限制：

- 不支持 SharedArrayBuffer 这类共享对象，既无法序列化也无法反序列化。
- ArrayBuffer 与 Uint8Array 等可转移对象只做拷贝不做转移，发送方手里的原对象仍然可用。
- 会忽略自定义的 toJSON 方法，直接复制属性值，依赖它做脱敏的代码会失效。

> [!WARNING]
> **警告内容**：结构化克隆要求通信双方的序列化格式一致。一方用 JSON、另一方用结构化克隆时，runtime.sendMessage 与 runtime.connect 都无法送达，端口会被关闭。使用 externally_connectable 的网页会自动跟随目标扩展的格式，因此网页与扩展对格式的预期必须同步更新。原生消息传递通道恒定使用 JSON，BigInt 这类结构化克隆专有类型在消息离开扩展之前就会失败。



### 常见错误与排查路径

发送端遇到的失败信息集中在三类。

- Could not establish connection. Receiving end does not exist.：目标上下文里没有对应的监听器。常见成因是内容脚本尚未注入、页面已导航到不匹配的网址、扩展刚重载而页面里仍是旧脚本、tabs.sendMessage 指定的 frameId 没有匹配框架，或网页发消息时发送方不在 externally_connectable 的 matches 内。
- A listener indicated an asynchronous response by returning true, but the message channel closed before a response was received.：监听器返回了 true 却始终没调用 sendResponse，通常是页面在响应前被刷新或关闭，通道随文档一起销毁。
- Could not serialize message 类错误：监听器返回了无法序列化的值，检查返回值里有没有函数或循环引用。

回调式写法里这些信息挂在 chrome.runtime.lastError 上，该属性只在对应函数的回调作用域内有效；返回 Promise 的 API 不设置该属性，错误直接表现为 Promise 被拒绝。

> [!NOTE]
> **提醒内容**：排查消息不通时先确认监听器的注册位置。Service Worker 的监听器必须在顶层同步注册，写在异步回调里或写在某个事件处理之后，事件到达时浏览器就找不到监听器，发送端看到的现象正是「接收端不存在」。
