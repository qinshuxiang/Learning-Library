## Chrome 浏览器扩展简介与技术形态

### 扩展是什么

Chrome 浏览器扩展是一组用网页技术编写、由浏览器在受控权限内加载运行的打包文件，用来为 Chrome 增加它自身没有的功能。

扩展不是网页。它拥有独立的扩展来源，地址形如 chrome-extension://扩展ID/，代码运行在浏览器提供的上下文里而不是某个网站的上下文里；它的入口是根目录下的清单文件 manifest.json，浏览器读这份清单决定加载哪些脚本、在哪些网站上生效、需要向用户申请哪些权限。

安装到本地的扩展就是一个目录，目录里放清单、脚本、HTML 页面与图标。发行渠道下发的是打包后的 CRX 文件，本地开发则直接把未打包目录交给浏览器加载。

> [!NOTE]
> **提醒内容**：Chrome 148 起，全部扩展 API 同时挂在 browser 命名空间下，它是 chrome 命名空间的跨浏览器别名，两套写法能力完全相同。本系列示例统一使用 chrome 命名空间，与官方文档保持一致。



### 扩展能做什么

扩展的能力边界由「它在哪个上下文里跑」和「用户批了哪些权限」两条线共同决定，落到功能上大致分六类：

- 改写网页：向匹配的页面注入脚本与样式，读写文档结构，拦截页面事件。
- 改写网络请求：用声明式规则集阻断、重定向请求或修改请求头与响应头。
- 操作浏览器数据：读写标签页与窗口、书签、历史记录、下载项、分组与恢复会话。
- 提供浏览器级界面：工具栏图标与徽章、弹出窗口、侧边栏、选项页面、开发者工具面板，以及覆盖新标签页等内置页面。
- 在后台响应事件：闹钟、上下文菜单、键盘命令、桌面通知、安装与更新钩子。
- 发起跨域请求：扩展页面与 Service Worker 的 fetch 请求不受页面同源策略限制，只受主机权限约束；这一点是内容脚本拿不到的。



### 扩展不能做什么

几条边界是硬性的，不因写法或权限而改变：

- 不能执行远程托管代码。所有可执行 JavaScript 必须打进安装包，从服务器下载脚本再求值在 Manifest V3 下被明确禁止。
- Service Worker 里没有 DOM，也没有 localStorage。需要在隐藏文档中使用 DOM 时只能开辟离屏文档，持久状态一律落 chrome.storage。
- 不能绕过权限读数据。没有 tabs 权限或对应主机权限时，标签页对象的网址与图标字段读不到值。
- 不能注入浏览器内部页面。chrome:// 开头的页面与网上应用店页面不向内容脚本开放。
- 不能改造其他扩展的内部实现。扩展之间只能走消息与公开接口，没有共享内存与直接调用。
- 沙箱页面可以跑 eval 与远程脚本，但换来的代价是拿不到任何扩展 API，只能靠消息与扩展其他部分通信。

> [!WARNING]
> **警告内容**：Manifest V2 已彻底退场，新扩展只能用 Manifest V3。Chrome 138（2025-07）停用全部 MV2 扩展，Chrome 150（2026-06）移除最后一个放行 MV2 的开发者标志，Chrome 网上应用店已于 2026-08-31 清除全部残留 MV2 应用。MV2 在本系列中只作为「为什么改成现在这样」的对照出现。



### Manifest V3 的强制现状与 MV2 退场

Manifest V3 是一次平台级重构，它相对 MV2 有三处架构性变化，理解这三处就理解了整套 MV3 的写法约束：

- 后台从常驻的 background page 换成事件驱动的 Service Worker。后台不再长期驻留，随时可能被终止，因此状态不能放全局变量。
- 阻塞式 webRequest 换成声明式 declarativeNetRequest。请求拦截由浏览器按预先声明的规则执行，扩展不再逐条同步决策。
- 禁止远程托管代码。全部 JavaScript 必须随安装包分发，安装包内的代码内容在审核时可被检视。

本系列的基线与行为标注一律以本机 Chrome 稳定版 153.0.8010.36 为准，与版本相关的行为都会写明「Chrome 多少起」。



### 与相邻技术的区别

扩展容易被与三类相邻技术混为一谈，选型前需要先分清各自的能力归属。

#### 与渐进式网页应用的区别

渐进式网页应用是一个网站，安装动作只是登记入口并缓存资源，代码始终运行在页面上下文与站点权限之内。扩展是独立来源、独立权限模型的浏览器组件，可以跨标签页操作、改写浏览器界面、访问浏览器数据，代价是要经过权限授权与商店审核。能做进网页的用网页做，需要越出网页边界的才写扩展。



#### 与用户脚本管理器的区别

用户脚本管理器本身就是一个扩展，它提供一个通用容器来运行用户自写的脚本，脚本是运行时数据而非安装包的一部分。若自己的扩展需要承载用户提供的代码，对应的官方能力是 chrome.userScripts API，Chrome 120 起可用，它按用户脚本世界执行代码并配有独立的 CSP 与消息入口。



#### 与浏览器内置功能的区别

cookie 管理、密码管理、页面翻译、阅读模式这类能力由 Chrome 直接实现，隐私边界与稳定性由浏览器负责，用户不需要额外授权。扩展要做到同等效果，必须出现在权限告警里并承担数据用途声明的义务。能用网页标准或内置功能解决的问题不值得另写扩展。



### 四种运行上下文

一个扩展的代码可能落在四个互不相同的执行环境中，它们能调用的 API 与能触碰的数据完全不同。

#### Service Worker 上下文

Service Worker 上下文是扩展的后台脚本，它由事件唤醒、无界面、无 DOM，负责协调各上下文、处理跨域请求、管理状态与闹钟。它是 MV3 里唯一没有页面依托的上下文，因此也被称为事件页面。



#### 扩展页面上下文

扩展页面上下文是扩展自带的 HTML 页面，包括弹出窗口、选项页面、侧边栏、开发者工具页面与被覆盖的内置页面。它们以扩展来源加载，可以调用几乎全部扩展 API，受扩展默认内容安全策略约束，禁止 eval 与远程脚本。



#### 内容脚本上下文

内容脚本上下文是注入进网页的脚本，默认运行在隔离世界，与页面 JavaScript 的变量互不可见。它能读写页面 DOM，但拿不到扩展的跨域特权，也不能直接操作浏览器界面，需要经消息把请求转给 Service Worker。



#### 页面主世界上下文

页面主世界上下文是脚本与页面 JavaScript 共享的执行环境，注入时把 world 设为 MAIN 即可进入。它能直接读写页面的全局变量与框架实例，但同样拿不到扩展 API，并且受页面自身内容安全策略限制。

> [!IMPORTANT]
> **重要内容**：隔离世界只隔离变量，不构成沙箱。内容脚本与页面共享同一个 DOM，页面仍可通过 DOM 事件影响内容脚本；跨上下文传值的正确姿势是消息通道加来源校验，而不是把对方数据当成可信输入。



### 一个扩展的最小文件构成

一份清单加一个入口即可构成可加载的扩展。清单是唯一必需文件，其余文件按用到的界面形态增补：

```text
hello-extension/
  manifest.json        清单：唯一必需文件
  service-worker.js    后台脚本：由 background 键声明
  popup.html           弹出窗口：由 action.default_popup 声明
  icons/icon128.png    扩展图标：由 icons 键声明
```

清单用 JSON 描述入口与权限，下面这份已可直接加载：

```json
{
  "manifest_version": 3,
  "name": "Hello Extension",
  "version": "1.0.0",
  "description": "最小可运行的扩展示例",
  "icons": { "128": "icons/icon128.png" },
  "background": { "service_worker": "service-worker.js" },
  "action": { "default_popup": "popup.html" },
  "permissions": ["storage"]
}
```

后台脚本在顶层同步注册监听器，浏览器随时可以把它唤醒：

```js
chrome.runtime.onInstalled.addListener(async (details) => {
  if (details.reason !== 'install') return;
  await chrome.storage.local.set({ installedAt: Date.now() });
  console.log('扩展已安装', details.reason);
});
```

需要进入网页时，内容脚本由清单静态声明匹配模式，或由后台经 chrome.scripting 在运行时注入：

```js
chrome.action.onClicked.addListener(async (tab) => {
  await chrome.scripting.executeScript({
    target: { tabId: tab.id },
    files: ['content.js']
  });
});
```



### 开发与发布全流程

从空目录到上架，整个过程是固定的一条线：

- 建目录与清单，在 chrome://extensions 打开开发者模式，用「加载已解压的扩展程序」加载目录。
- 修改代码后按需重载：清单、Service Worker、内容脚本改完要重载扩展，弹出窗口与选项页面刷新即可生效。
- 用命令行参数加载扩展可配合自动化测试，脚本化的加载方式见第 2 篇《开发环境与第一个扩展》。
- 打包为 zip 或使用 --pack-extension，得到 CRX 安装包与 PEM 私钥，私钥用于保持扩展 ID 不变。
- 注册发布者账号并上传到开发者信息中心，填写商店素材、隐私实践与数据用途声明。
- 通过审核后发布，用户侧按清单里的 version 字段自动更新。

```bash
chrome --load-extension=/abs/path/hello-extension \
       --disable-extensions-except=/abs/path/hello-extension
```

> [!TIP]
> **建议内容**：本地开发一律用未打包目录加载，不要用自行打包的 CRX。未打包扩展的改动重载成本最低，且错误会直接暴露在扩展管理页的错误按钮里，打包流程只在提审前跑一次。
