## 构建与打包

扩展的构建与普通前端项目的差别在于产物不是一个页面，而是一份由清单驱动的多入口包。构建的验收标准很具体：把产物目录交给「加载已解压缩的扩展」能装上、能跑起来，并且目录根部的 manifest.json 与产物里的文件名一一对应。

### 多入口打包的三个难点

难点一是入口散落在清单各处。Service Worker、popup、options、side panel、内容脚本、可网络访问资源分别由不同的清单键声明，每个键都要有对应的产物文件；打包器默认只认 HTML 入口，清单里的其余入口需要额外插件补齐。

难点二是路径基准不统一。清单里的路径以扩展根目录为基准，HTML 里的脚本与样式路径以该页面为基准，CSS 里的资源路径又以其所在目录为基准。构建工具若按源码目录结构输出，产物里的相对引用很容易整体错位。

难点三是清单本身也可能成为构建产物。版本号要跟着发布流程递增，开发环境与生产环境的主机权限与远程配置地址不同，目标浏览器不同还要换掉一部分键名。这些差异无法用静态文件表达。

```json
{
  "manifest_version": 3,
  "name": "Meter Reader",
  "version": "1.4.0",
  "background": { "service_worker": "background.js", "type": "module" },
  "action": { "default_popup": "popup.html" },
  "options_page": "options.html",
  "content_scripts": [
    { "matches": ["https://portal.example.com/*"], "js": ["content.js"], "css": ["content.css"] }
  ],
  "web_accessible_resources": [
    { "resources": ["assets/spinner.svg"], "matches": ["https://portal.example.com/*"] }
  ]
}
```



### Vite 与 CRXJS

CRXJS 是面向 Vite 的扩展开发插件，当前包名是 @crxjs/vite-plugin，用 npm create crxjs@latest 从模板起项目。它把清单当作入口描述文件，自动为清单里声明的每个入口建立构建入口，并生成对应的产物路径。

```bash
npm create crxjs@latest
cd meter-reader
npm install
npm run dev
```

模板项目的根目录有 manifest.config.ts 与 vite.config.ts 两个配置文件，源码目录按 popup、content 等功能分子目录。插件的几项行为对工程实践影响较大：原生 HMR 对内容脚本同样生效，代码里直接引用图片与字体时会被当作静态资源处理，web_accessible_resources 的清单条目会被自动补齐而不必手工维护。Manifest V2 的构建需要换用同组织的 rollup 插件。



### WXT

WXT 是另一套扩展开发框架，当前包名是 wxt，用 npx wxt@latest init 创建项目。它的核心差异是源码里不存在 manifest.json，清单由 wxt.config.ts 的 manifest 键、各入口文件自带的清单选项、以及项目加载的模块与钩子合并生成，构建后输出到 .output/{目标浏览器}/manifest.json。

```ts
// wxt.config.ts
export default defineConfig({
  manifest: {
    permissions: ["storage", "alarms"],
    host_permissions: ["https://portal.example.com/*"],
  },
});
```

清单里有若干字段由 WXT 自动补齐而不必手写：name 默认取 package.json 的 name，version 与 version_name 由 package.json 的 version 派生，其中 version 是去掉非法后缀后的合法值、version_name 保留原字符串；图标会按文件名规则从 public 目录自动发现，例如 16、48、128 像素的图标分别命名为 icon-16.png、icon-48.png、icon-128.png；开发模式下会自动加入 tabs 与 scripting 权限以支持热重载；存在 sidepanel 入口时会自动加入 sidepanel 权限。

```bash
npx wxt@latest init
npm run dev     # 等价于 wxt，启动带扩展的开发浏览器
npm run build   # 等价于 wxt build
npm run zip     # 等价于 wxt zip，产出可上传商店的压缩包
```



### webpack 多入口与清单生成

用 webpack 自行搭建时需要手工完成三件事：为清单里的每个入口配置 entry，用 CopyWebpackPlugin 一类插件把图标与静态资源原样复制到产物目录，再用一段自定义逻辑生成 manifest.json 而不是复制一份静态文件。

```js
// webpack.config.js
const path = require("path");
const CopyPlugin = require("copy-webpack-plugin");

module.exports = {
  entry: {
    background: "./src/background.js",
    popup: "./src/popup.js",
    content: "./src/content.js",
  },
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].js",
    clean: true,
  },
  plugins: [
    new CopyPlugin({ patterns: [{ from: "public", to: "." }] }),
  ],
};
```

生成清单时应当从一份基础配置出发，按目标环境改写版本号、主机权限与远程配置地址，最后序列化写入 dist/manifest.json。这样产物目录根部始终有完整清单，避免出现「构建成功但装不上」的情况。



### TypeScript 类型来源

官方推荐的类型包是 chrome-types，它由 Chromium 源码自动生成并随源码变化更新，官方文档明确要求经常更新该包以匹配最新的 Chromium 版本。另一个常见来源是 DefinitelyTyped 的 @types/chrome，它由社区维护，覆盖范围与更新节奏与前者不同。

两种来源都不需要在代码里引入运行时依赖，安装后由 tsconfig 自动识别全局的 chrome 命名空间。选型时以能否跟上当前 Chromium 版本为判断标准，因为扩展 API 的版本差异密集，类型落后会直接把可用方法标记成不存在。



### 开发期热重载的原理与限制

热重载指改完源码后不手动点击重新加载就能看到效果，它的实现方式是由构建工具监听文件变化、重新打包受影响的入口，并通过开发服务器或自动刷新机制让浏览器侧生效。CRXJS 与 WXT 都内置了这套机制，WXT 还会在开发模式下自动补上所需的权限。

限制来自扩展自身的加载规则，官方给出的重载对照表区分了哪些组件改完必须重新加载扩展：清单变更需要重载，Service Worker 变更需要重载，内容脚本变更也需要重载（包括已经打开的托管网页），而弹出式窗口、选项页面以及其它扩展 HTML 页面不需要重载，刷新页面即可。

> [!NOTE]
> **提醒内容**：热重载能覆盖页面与样式的改动，但清单、Service Worker 与内容脚本的变更仍然要经过一次真正的扩展重载，且已打开页面里的旧内容脚本不会自行消失。调试「改了没效果」一类问题时，先手动点一次重新加载再判断。



### 构建产物的目录结构

产物目录的结构与源码结构无关，只由清单里的路径决定。一个可直接加载的最小产物目录如下，清单必须位于目录根部，其余文件名与清单中的声明逐字对应。

```text
dist/
  manifest.json
  background.js
  popup.html
  popup.js
  options.html
  content.js
  content.css
  assets/
    spinner.svg
  icons/
    icon-16.png
    icon-48.png
    icon-128.png
```

把 dist 这类产物目录交给「加载已解压缩的扩展」是开发期的标准做法，而打包上架时上传的压缩包根目录同样必须直接包含 manifest.json，多套一层父目录是最常见的一类上传失败原因。



### zip 打包与命令行打包

商店上传用的是 ZIP 文件，打包时应当只包含产物内容，排除源码、依赖目录与版本控制目录。验证方法是把压缩包解到一个新目录，确认 manifest.json 位于最外层。

```bash
cd dist && zip -r ../meter-reader.zip . -x "*.map" "*.git*"
unzip -l ../meter-reader.zip | head -5
```

需要产出 crx 文件时可以用 Chrome 自身的打包能力：扩展管理页面上的「打包扩展程序」按钮，或命令行调用 chrome.exe 并传入 --pack-extension 指定扩展目录、--pack-extension-key 指定私钥文件。

```bash
chrome.exe --pack-extension=C:\myext --pack-extension-key=C:\myext.pem
```

首次打包时不要填写私钥输入框，Chrome 会同时生成 crx 文件与 pem 私钥文件。私钥文件是后续所有版本更新的唯一凭据，一旦丢失就无法再用同一个身份发布新版本。

> [!WARNING]
> **警告内容**：pem 私钥文件绝不可提交到版本库或随构建产物分发。任何持有该私钥的一方都能以其名义签发扩展更新，等价于接管该扩展在用户侧的代码执行权限；CI 环境中应当把它放入加密的密钥存储，只以环境变量注入。



### key 文件与扩展 ID 的固定

扩展 ID 的派生方式取决于扩展是否已打包。已打包且清单中带 key 的扩展，其 ID 由公钥派生并且固定不变；未打包加载的扩展，其 ID 由扩展目录的绝对路径派生，换机器或换目录路径都会改变。测试环境、服务器白名单、外部页面的 externally_connectable 与可网络访问资源都依赖稳定 ID，因此需要固定。

固定方式是用清单的 key 字段写入公钥：把扩展目录打成 zip 上传到开发者信息中心但不发布，在打包标签页点击查看公钥，复制其中的公钥内容并去掉换行符，粘贴为 key 的值。带 key 的扩展在本地加载时会得到与商店一致的商品 ID，便于用同一套配置做端到端测试。

> [!IMPORTANT]
> **重要内容**：扩展 ID 变了会连带三处配置失效：服务器侧按扩展源下发的许可名单、网页侧按 ID 调用的 runtime.sendMessage、以及允许访问可网络访问资源的 matches 规则。凡是涉及跨主体协作的项目，都应当把固定 key 作为仓库中的必备配置项，并在 CI 里断言产物 ID 与线上一致。



### 环境区分、配置注入与自动上传

环境区分的目标是让同一份源码产出开发与生产两份产物，差异只体现在清单字段与少量常量上。注入方式有两种：构建期用打包器把常量替换进代码，运行期用远端配置接口在启动时拉取。后者受 MV3 政策约束，远端配置可以携带数据与开关，但不能携带任何可执行逻辑。

```bash
curl -H "Authorization: Bearer $TOKEN" \
  -H "x-goog-api-version: 2" \
  -X POST \
  -T dist.zip \
  https://www.googleapis.com/upload/chromewebstore/v1.1/items/$ITEM_ID
```

自动化上传走 Chrome Web Store Publish API：更新已有商品用 PUT 请求把压缩包发到 items 加商品 ID 的端点，发布用 POST 请求发到该商品的 publish 端点，向受信任测试人员发布时在 publish 端点追加 publishTarget 参数。访问令牌通过 OAuth 2.0 获取，作用域是 chromewebstore，有效期为一小时，发布者账号必须启用两步验证。发布更新前必须先递增清单中的 version，否则接口不会接受。

> [!CAUTION]
> **注意内容**：构建配置里注入的常量最终会进入安装包，用户可以直接读取。任何 API 密钥、签名私钥、内部接口地址都不应当出现在清单、源码常量或被自动生成的可网络访问资源中；需要在包内使用凭据时，正确做法是由服务端在运行时下发短期凭据，而不是打包时写死。
