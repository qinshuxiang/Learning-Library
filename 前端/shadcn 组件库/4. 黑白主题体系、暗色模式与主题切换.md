## 黑白主题体系、暗色模式与主题切换

主题不是一组颜色，而是一套「面与前景成对出现」的令牌约定加上两套取值。本篇说明令牌清单与配对规则、暗色模式靠什么机制生效、切换控件如何写才不会闪白，以及单色方案下应当调整哪一层。令牌的具体取值与达标依据见第 13 篇，样式层的映射机制见第 3 篇。

### 语义令牌的配对体系

组件里出现的颜色全部是令牌名。理解这套令牌，关键是掌握「一个面配一个前景」的命名约定。

#### 面与前景的配对约定

**语义令牌**：是按用途命名的样式变量，取值为颜色；**配对约定**：是每个面令牌配一个同名前景令牌的命名规则。

- 命名规则：面令牌不加后缀，其上的文字与图标用同名加前景后缀的令牌。
- 配对含义：前景令牌的取值必须保证在该面上可读，两者是绑定关系而非独立取值。
- 用途命名：令牌名描述用途不描述外观，因此换主题不需要改组件里的类名。
- 强制成对：新增一个面令牌时必须同时给出它的前景令牌，不许只加一半。
- 校验方式：任何前台令牌与其所在面的对比度都要单独算，见第 13 篇的实测表。

```css
/* 面与前景成对；组件写作 bg-primary text-primary-foreground */
:root {
  --primary: oklch(0.205 0 0);
  --primary-foreground: oklch(0.985 0 0);
}
```

```tsx
// 组件里只写语义类，不关心当前是哪一套主题
<div className="bg-primary text-primary-foreground">提交</div>
```

> 只加面令牌不加前景令牌，组件就会落到从背景继承的文字色上。这类缺陷在默认主题下往往看不出，一切换主题就整块不可读。

**速记**：面令牌不加后缀、前景令牌加前缀，二者成对定义且必须单独校验对比度。



#### 令牌清单与用途

**令牌清单**：是这套主题提供的全部语义颜色，按界面层次分为页面、浮层、侧栏、状态与图表五组。

- 页面层：默认背景与默认文字，用于页面外壳与页面分区。
- 浮层组：卡片面与浮层面各配前景，用于面板、下拉与气泡这类抬升元素。
- 强调组：主色、次色与弱色三组，分别承担高强调操作、低强调填充与弱化内容。
- 交互组：强调交互面用于悬停、聚焦与选中态，是后台列表行高亮与菜单高亮的主力。
- 组件组：边框、输入框边框与焦点环三个非填充令牌，承担分隔与可聚焦标记。
- 侧栏组：一套独立的侧栏令牌，让侧栏在不改动页面令牌的前提下单独调色。
- 状态组：危险色单独成令牌，其余状态色按需扩展。
- 图表组：五个图表令牌，单色方案下只有前三级可用，见第 11 篇。

```css
@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-card: var(--card);
  --color-card-foreground: var(--card-foreground);
  --color-popover: var(--popover);
  --color-popover-foreground: var(--popover-foreground);
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);
  --color-secondary: var(--secondary);
  --color-secondary-foreground: var(--secondary-foreground);
  --color-muted: var(--muted);
  --color-muted-foreground: var(--muted-foreground);
  --color-accent: var(--accent);
  --color-accent-foreground: var(--accent-foreground);
  --color-destructive: var(--destructive);
  --color-border: var(--border);
  --color-input: var(--input);
  --color-ring: var(--ring);
  --color-sidebar: var(--sidebar);
  --color-sidebar-foreground: var(--sidebar-foreground);
  --color-sidebar-border: var(--sidebar-border);
}
```

> 弱色与强调交互面在单色方案下取值极近，容易混用。分工是固定的：弱色用于承载低优先级的静态内容，强调交互面只用于可点击的状态变化。

**速记**：令牌分页面、浮层、强调、交互、组件、侧栏、状态、图表八组，强调与弱色分工不可混用。



#### 令牌缺省与兜底

**缺省兜底**：是当某个令牌未被定义或未在主题指令里映射时，组件表现出来的退化行为。

- 未定义变量：引用不到的变量使该条声明失效，元素落到继承值。
- 未参与映射：变量已定义但没映射进颜色命名空间，对应工具类根本不生成。
- 表现差异：前者是样式错乱，后者是类名完全不起作用，排查入口不同。
- 兜底写法：组件内可用变量回退语法给一个备用取值，但不作为常规手段。
- 检查手段：新增令牌后必须同时改三处——根选择器、深色选择器、主题指令。

```css
/* 三处齐改：根选择器、深色选择器、主题指令 */
:root {
  --warning: oklch(0.84 0.16 84);
  --warning-foreground: oklch(0.28 0.07 46);
}

.dark {
  --warning: oklch(0.41 0.11 46);
  --warning-foreground: oklch(0.99 0.02 95);
}

@theme inline {
  --color-warning: var(--warning);
  --color-warning-foreground: var(--warning-foreground);
}
```

> [!IMPORTANT]
> **重要内容**：漏改深色选择器是最常见的失误。浅色下一切正常，切到深色时该令牌继承浅色取值，表现为深底上出现一块刺眼的浅色区域，而构建与类型检查都不会报错。

**速记**：新增令牌必须同时改根选择器、深色选择器与主题指令三处，漏改深色处不会报错。



### 暗色模式的实现

暗色不是另一套组件，而是同一批令牌的另一套取值。切换机制要解决的核心问题是「什么时候加类名」。

#### 类名策略与变体声明

**类名策略**：是以根元素上的类名作为主题开关，配合自定义变体让深色样式可在任意元素上表达。

- 开关位置：类名加在文档根元素上，全站生效，不需要逐层传递。
- 变体声明：在全局样式里声明深色变体，使深色前缀在全部工具类上可用。
- 令牌覆盖：深色选择器里只改取值，不改令牌名，组件零改动。
- 局部反色：个别元素需要固定外观时，直接在元素上写深色前缀，不走全局开关。
- 禁止两套：不要同时维护一套独立的深色令牌名，那等于把组件写两遍。

```css
@import "tailwindcss";
@custom-variant dark (&:is(.dark *));

:root {
  --background: oklch(1 0 0);
  --foreground: oklch(0.145 0 0);
}

.dark {
  --background: oklch(0.145 0 0);
  --foreground: oklch(0.985 0 0);
}
```

> 深色主题的取值不是浅色取值的取反。两套取值要各自按对比度门槛单独定值，这一点在第 13 篇有实测依据。

**速记**：类名挂在根元素上作开关，深色选择器只改取值不改名，禁止另起一套深色令牌。



#### 首屏闪烁的成因与规避

**首屏闪烁**：是页面首次渲染时先用浅色绘制、脚本执行后再切成深色所造成的瞬时白屏。

- 成因：根元素类名由脚本添加，脚本晚于首次绘制执行。
- 表现：停留时间随脚本体积与网络状况变化，短则一瞬，长则可见半秒。
- 规避一：在页面头部的内联脚本里同步读取偏好并立刻加类名。
- 规避二：使用框架级主题方案，它已内置了这段预置脚本。
- 规避三：服务端渲染时把主题状态写入初始标记，由服务端直接输出类名。
- 副作用：预置脚本阻塞首屏渲染，内容应当极短，只做读存储与加类名两件事。

```html
<script>
  (function () {
    var key = "admin-theme";
    var saved = localStorage.getItem(key);
    var prefersDark = window.matchMedia("(prefers-color-scheme: dark)").matches;
    var dark = saved ? saved === "dark" : prefersDark;
    document.documentElement.classList.toggle("dark", dark);
  })();
</script>
```

> [!WARNING]
> **警告内容**：后台系统多在早晨与夜间长期停留，首屏闪白在深色偏好用户处每天会出现很多次，是被用户直接感知为「不稳」的缺陷。深色主题一旦上线，预置脚本就是必选项而不是优化项。

**速记**：闪白源于脚本晚于首绘执行，必须在页面头部用内联脚本同步加类名，脚本只做读存储与加类名。



#### 系统偏好与用户选择

**主题偏好**：分为跟随系统、强制浅色、强制深色三种，三者需要一个明确的优先级关系。

- 初始取值：首次访问跟随系统，用媒体查询读取系统偏好。
- 用户覆盖：用户显式选择后写入本地存储，此后不再跟随系统。
- 跟随系统：选择跟随系统时，需要监听系统偏好的实时变化并同步类名。
- 存储键：同名键在不同项目间会互相干扰，存储键应带项目前缀。
- 清除状态：提供恢复跟随系统的入口，否则用户无法退回初始行为。

```tsx
// 跟随系统时监听系统偏好变化，用户显式选择后停止跟随
useEffect(() => {
  const root = window.document.documentElement
  root.classList.remove("light", "dark")

  if (theme === "system") {
    const systemTheme = window.matchMedia("(prefers-color-scheme: dark)").matches
      ? "dark"
      : "light"
    root.classList.add(systemTheme)
    return
  }

  root.classList.add(theme)
}, [theme])
```

> 三种偏好必须都有出口：缺少「跟随系统」会让用户觉得主题设置不讲道理，缺少显式选择则等于替用户决定。

**速记**：首次跟随系统、显式选择后写入存储并停止跟随、必须提供退回跟随系统的入口。



### 主题切换的工程实现

切换功能的代码量很小，但有三处容易做错：状态来源、持久化时机与切换控件的语义。

#### 主题提供者与持久化

**主题提供者**：是以上下文向组件树提供当前主题与设置方法的组件，同时负责读写本地存储。

- 状态来源：初始值优先取本地存储，无存储值时取默认主题。
- 写入时机：在设置方法里写入存储，而不是在副作用里判断变化后写。
- 上下文兜底：上下文缺省值给一个空实现，避免未包裹时直接抛错。
- 越界检查：读取上下文的自定义钩子在提供者缺失时抛出明确错误，便于定位。
- 包裹位置：包在应用入口最外层，早于任何读取主题的组件。

```tsx
type Theme = "dark" | "light" | "system"

const [theme, setTheme] = useState<Theme>(
  () => (localStorage.getItem(storageKey) as Theme) || defaultTheme
)

const value = {
  theme,
  setTheme: (theme: Theme) => {
    localStorage.setItem(storageKey, theme)
    setTheme(theme)
  },
}
```

> [!TIP]
> **建议内容**：需要多套配色方案时，把「主题」与「配色」拆成两个独立状态分别持久化。合成一个状态会让取值的组合数随方案数成倍增长，切换控件也会随之变复杂。

**速记**：提供者以上下文下发主题与设置方法，初值取存储、写入在设置方法内完成，包裹在入口最外层。



#### 切换控件的写法

**切换控件**：是让用户在三档偏好间切换的界面元素，通常是一个图标按钮加一个浮层菜单。

- 图标处理：两个图标叠放，用深色前缀控制缩放与旋转，避免切换时布局跳动。
- 无障碍：图标按钮必须带仅供辅助技术读取的文字说明。
- 菜单项：三项分别对应浅色、深色、跟随系统，措辞与当前选中态要一致。
- 位置：放在顶栏右侧固定位置，属于全局设置而非页面级操作。
- 状态回显：菜单里应显示出当前所处档位，否则用户无法判断是否跟随系统。

```tsx
<DropdownMenu>
  <DropdownMenuTrigger asChild>
    <Button variant="ghost" size="icon">
      <Sun className="size-4 scale-100 rotate-0 transition-all dark:scale-0 dark:-rotate-90" />
      <Moon className="absolute size-4 scale-0 rotate-90 transition-all dark:scale-100 dark:rotate-0" />
      <span className="sr-only">切换主题</span>
    </Button>
  </DropdownMenuTrigger>
  <DropdownMenuContent align="end">
    <DropdownMenuItem onClick={() => setTheme("light")}>浅色</DropdownMenuItem>
    <DropdownMenuItem onClick={() => setTheme("dark")}>深色</DropdownMenuItem>
    <DropdownMenuItem onClick={() => setTheme("system")}>跟随系统</DropdownMenuItem>
  </DropdownMenuContent>
</DropdownMenu>
```

> [!CAUTION]
> **注意内容**：切换控件里用绝对定位叠放两个图标时，父元素必须带相对定位。缺了这一条，图标会以整个页面为参照定位，表现为图标出现在意料之外的位置，而这类问题在组件库示例页里往往看不出来。

**速记**：切换控件用图标按钮加浮层菜单三档，图标叠放控制缩放旋转，必须带辅助技术说明文字。



#### 服务端渲染下的处理

**服务端渲染**：是先在服务端产出标记再由浏览器接管的渲染方式，它使「当前是哪个主题」在服务端不可知。

- 矛盾点：服务端不知道用户偏好，输出任一档都会与实际不符。
- 常规解法：服务端输出中性标记，由客户端脚本在首绘前补上类名。
- 属性抑制：类名由脚本添加时，需要抑制相应元素上的属性不一致告警。
- 状态同步：客户端接管后要把真实主题写回状态，避免后续渲染退回默认值。
- 表单交互：主题切换属于纯客户端行为，标记为客户端组件后再读存储。

```tsx
// 服务端渲染场景：由客户端脚本改写根元素类名，抑制该元素的属性告警
export function ThemeScript() {
  return (
    <script
      dangerouslySetInnerHTML={{
        __html: `document.documentElement.classList.toggle("dark",
          (localStorage.getItem("admin-theme") || "system") !== "light" &&
          window.matchMedia("(prefers-color-scheme: dark)").matches)`,
      }}
    />
  )
}
```

> 主题是这套体系里少数必须在客户端决定的状态。接受这一点，比试图让服务端猜出正确取值要省事得多。

**速记**：服务端渲染下由客户端脚本在首绘前补类名并抑制属性告警，主题属于客户端状态。



### 单色主题的定制手法

定制方案集中在三件事：改哪一层、该不该新增令牌、彩色放在哪里。

#### 调整亮度阶梯而非更换色相

**亮度阶梯**：是单色方案里全部令牌的明度取值序列，是唯一有信息量的可调维度。

- 调整对象：需要强调就压低明度，需要弱化就抬高明度，不动色度通道。
- 阶梯完整：从页面底色到主文字应当形成一条连续可辨的序列，不留空档。
- 边界值：底面的明度不得与文字面的明度过近，否则无论怎么调都过不了对比度。
- 取值依据：每一档的取值都要有对应的对比度实测，见第 13 篇。
- 禁止手法：不要为了让某块「跳出来」而临时引入一个彩色，那会破坏单色前提。

```css
/* 单色方案的亮度阶梯：色度与色相全部为零，只调第一个参数 */
:root {
  --background: oklch(1 0 0);
  --sidebar: oklch(0.985 0 0);
  --muted: oklch(0.97 0 0);
  --border: oklch(0.922 0 0);
  --ring: oklch(0.64 0 0);
  --muted-foreground: oklch(0.54 0 0);
  --primary: oklch(0.205 0 0);
  --foreground: oklch(0.145 0 0);
}
```

> 单色方案的可调维度只有一个，因此每一档的取值都必须有理由。凭手感加的中间档不会产生层次，只会让灰度显得脏。

**速记**：单色定制只调亮度阶梯，强调压暗、弱化提亮，每一档取值都要有对比度实测支撑。



#### 新增语义令牌的时机

**新增令牌**：是在既有八组之外补一项语义颜色，用于表达现有令牌覆盖不到的新用途。

- 增加时机：同一组取值在多个组件上反复出现，且它有独立语义时才新增。
- 拒绝时机：只是某个组件的一次性特殊外观，用工具类就地解决即可。
- 命名要求：按用途命名，不按外观命名，避免出现「浅灰背景」这类名字。
- 成对要求：面与前景一并新增，不允许只加面。
- 同步要求：三处齐改，并补齐对应用户文档与对比度实测记录。

```css
/* 新增一项状态令牌：面与前景成对，并在深色下单独取值 */
:root {
  --warning: oklch(0.84 0.16 84);
  --warning-foreground: oklch(0.28 0.07 46);
}

.dark {
  --warning: oklch(0.41 0.11 46);
  --warning-foreground: oklch(0.99 0.02 95);
}
```

> 令牌数量是成本：每增加一项，深色取值、对比度校验与文档同步都要多做一遍。先问「这个语义真的独立吗」，再动手加。

**速记**：同一取值反复出现且语义独立才新增令牌，面与前景成对，三处齐改并补实测记录。



#### 品牌色与状态色的位置

**受控彩色**：是单色方案里被允许保留的少量彩色，只有品牌色与状态色两类，且都有明确的出场条件。

- 品牌色：只在登录页、品牌标识与空状态插图出现，不参与常规交互。
- 危险色：用于破坏性操作与错误态，是使用频率最高的一个状态色。
- 警告与成功：按业务需要扩展，但每屏出现的次数要有限，超出就失去信号价值。
- 图表例外：图表用色属于数据编码而非界面状态，按第 11 篇的灰阶规则处理。
- 统一约束：所有彩色一律以令牌形式存在，深色主题下单独取值。

```tsx
// 状态色只落在徽标、提示条与破坏性按钮三类元素上
<Badge variant={record.ok ? "secondary" : "destructive"}>{record.statusLabel}</Badge>
```

```css
/* 状态色在深色下需要单独取值，浅色的取值放到深底上往往过暗 */
:root {
  --destructive: oklch(0.577 0.245 27.325);
}

.dark {
  --destructive: oklch(0.704 0.191 22.216);
}
```

> [!NOTE]
> **提醒内容**：状态色的稀有程度决定它的信号强度。当一屏里超过两成的元素带彩色时，彩色就不再指示异常，只被读成背景噪声，此时应当先减彩色数量而不是再加一层图例。

**速记**：受控彩色只有品牌色与状态色，品牌色限于登录页与品牌标识，状态色越稀有信号越强。
