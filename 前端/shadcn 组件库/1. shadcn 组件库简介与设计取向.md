## shadcn 组件库简介与设计取向

本主题讲一套后台管理界面从选型到规范落地的完整链路，基调统一为黑白单色。本篇是全系列的入口：说明这套代码为什么不是组件包、它靠什么机制分发、以及在什么前提下适合拿它做单色后台系统。命令清单与初始化步骤见本主题第 2 篇，样式底座见第 3 篇，单色令牌的取值依据见第 13 篇。

### 定位与设计取向

理解这套代码的第一步，是把它和「组件库」这一常见形态区分开。两者的差别不在组件数量，而在使用方拿到的是什么。

#### 与组件库的分野

**组件库**：是以依赖包形式一次性提供全部组件的分发形态，使用方通过导入组件名获得渲染结果，源码留在依赖目录内。

- 获取方式：传统组件库向包管理器安装，产物流入依赖目录，使用方只消费编译结果。
- 定制方式：需要改动时在组件外包一层，或用更高优先级的样式覆盖，改动与上游版本绑死。
- 本库方式：不发布组件包，把组件源码文件直接写进项目目录，改动即改源码。
- 保留边界：无障碍行为、键盘交互与焦点管理仍由底层依赖提供，改动集中在结构与样式层。
- 直接后果：不存在「覆盖样式」这一层，样式冲突从一个对抗问题变成一次普通编辑。

```bash
# 获取方式是把源码写进项目，而不是安装一个组件包
pnpm dlx shadcn@latest add button card table

# 写入位置由 components.json 的 aliases.ui 决定，默认如下
# src/components/ui/button.tsx
# src/components/ui/card.tsx
# src/components/ui/table.tsx
```

> 判断标准只有一条：要改组件时，改的是自己仓库里的文件，还是往别人的产物上叠覆盖样式。前者是这套代码，后者是组件库。

**速记**：本库把组件源码写进项目目录，改组件即改源码，因此不存在覆盖样式这一层。



#### 五项设计原则

**设计原则**：是这套代码在长期演进中固定下来的五条取舍，它们解释了为什么组件可以被自由改写而不会失控。

- 开放代码：组件顶层代码可读可改，没有黑盒部分，调试与定制都不需要绕过封装。
- 组合式接口：所有组件共用一套可组合的接口约定，学会一个组件即可类推其余组件。
- 分发模型：用一份扁平的组件描述加上命令行工具，把组件分发到任意项目。
- 克制的默认样式：默认外观经过挑选，不额外配置即可达到可交付的观感。
- 面向模型：开放代码使语言模型能直接读懂组件结构，进而生成风格一致的新组件。

```tsx
// 组合式接口的典型形态：一个组件由若干语义化子组件拼装
import { Card, CardContent, CardHeader, CardTitle } from "@/components/ui/card"

export function MetricCard({ title, value }: { title: string; value: string }) {
  return (
    <Card>
      <CardHeader>
        <CardTitle>{title}</CardTitle>
      </CardHeader>
      <CardContent className="text-2xl font-medium tabular-nums">{value}</CardContent>
    </Card>
  )
}
```

> [!IMPORTANT]
> **重要内容**：开放代码意味着上游修复不会自动送达。升级靠命令行工具的差异比对命令逐处合并，团队必须把「定期比对上游」写进维护流程，否则会长期停留在初始化当天的那一版。

**速记**：开放代码、组合接口、扁平分发、克制默认、面向模型，五条原则共同支撑「组件即项目源码」这一形态。



#### 三套底层实现的选择

**底层实现**：是组件无障碍行为与交互逻辑的实际提供方，在建项目时选定，决定了组合写法与属性透传约定。

- Base UI：以 render 属性替换渲染元素，把内层组件的属性合并到自定义标签上。
- Radix UI：以 asChild 布尔属性把样式与行为下放给唯一子元素，是历史上最广为人知的写法。
- React Aria：面向无障碍语义与国际化，交互细节最完整，属性命名自成一套。
- 选定时机：初始化时用 base 参数确定，之后同一项目内保持一致，不要混用三种写法。
- 组件归属：三种实现对同一组件的默认外观统一，差别集中在属性如何透传到自定义元素上。

```bash
# 初始化时指定底层实现，三种取值分别对应三套实现
pnpm dlx shadcn@latest init -t next -b radix
pnpm dlx shadcn@latest init -t vite -b base
pnpm dlx shadcn@latest init -t vite -b aria
```

> [!CAUTION]
> **注意内容**：网上大量现有示例基于 Radix 实现的 asChild 写法，直接照抄到 Base UI 实现的组件上不会报错，只会把属性透传悄悄失效，表现为点击无反应或锚点不跳转。抄代码前先确认本项目的底层实现。

**速记**：底层实现决定组合写法，Radix 用 asChild、Base UI 用 render，初始化时一次选定并在项目内保持一致。



### 代码归属与分发机制

把源码写进项目之后，「谁负责维护」与「怎么更新」这两个问题必须重新回答。

#### 源码归属与上游同步

**源码归属**：指组件文件写入项目后即视为项目自有代码，由项目维护者承担阅读、修改与评审责任。

- 责任转移：组件一旦落入 ui 目录，其行为缺陷属于本项目的缺陷，不能推给上游。
- 修改记录：对组件文件的改动应能追溯到具体诉求，避免出现来源不明的调整。
- 上游比对：命令行工具提供差异比对与文件预览命令，用于查看本地与上游的偏离。
- 合并策略：上游确实修了缺陷才合并，纯样式差异按本项目规范取舍，不做无差别同步。
- 评审纳入：组件文件与业务代码走同一套评审流程，不因「来自上游」而跳过。

```bash
# 查看指定文件相对上游的差异与内容，合并前先看清楚改了什么
pnpm dlx shadcn@latest add button --diff
pnpm dlx shadcn@latest add button --view
```

> 把组件文件当作项目自有代码，是这套方案能长期维护的前提；把它当成只读依赖，改起来方便的优势会立刻变成失控的理由。

**速记**：组件落库即为项目自有代码，改动可追溯、评审不跳过，上游更新靠逐处比对合并。



#### 注册表与分发模型

**注册表（registry）**：是以扁平结构描述组件、依赖与文件的一份数据，命令行工具据此把组件写入目标项目。

- 描述内容：组件名、文件清单、类型、所依赖的包与其它组件。
- 分发路径：默认从官方注册表读取，也可配置到私有地址，支持多注册表并存。
- 命名空间：配置后以 at 加名称的写法区分来源，便于区分官方组件与内部组件。
- 私有注册表：支持请求头与环境变量占位，用于内部组件库的鉴权分发。
- 内部收益：团队可以把自研组件按同一份结构发布，业务项目用同一条命令拉取。

```json
{
  "registries": {
    "@shadcn": "https://ui.shadcn.com/r/{name}.json",
    "@internal": {
      "url": "https://internal.company.com/r/{name}.json",
      "headers": { "Authorization": "Bearer ${REGISTRY_TOKEN}" }
    }
  }
}
```

> [!TIP]
> **建议内容**：团队内部若已有多个后台项目，应尽早把重复出现的自研组合组件（如筛选栏、指标卡、可编辑表格）按注册表结构发布，让新项目用一条命令获得与本规范一致的基础件。

**速记**：注册表用扁平描述定义组件与依赖，可自建私有注册表并多源并存，是内部组件复用的通道。



#### 版本与升级策略

**升级策略**：是把上游变更分批引入本项目的节奏安排，目的是让视觉回归与业务改动互不纠缠。

- 分批原则：一次只升级一组相关组件，与业务功能提交分开，避免定位困难。
- 基线冻结：大版本发布前冻结组件目录，升级期间不接受自定义改动。
- 回归范围：升级后按第 14 篇的检查清单覆盖焦点、禁用态与浮层定位三类易回归项。
- 依赖联动：组件升级常伴随底层依赖主版本变化，需同步核对破坏性变更说明。
- 回滚手段：升级以独立提交落地，出问题直接回退该提交，不回退业务代码。

```bash
# 升级前先看组件目录有没有未提交的自定义改动
git status --short src/components/ui

# 升级以独立提交落地，回滚时只需回退这一个提交
git add src/components/ui && git commit -m "chore(ui): 同步上游按钮与徽标组件"
```

> 升级的风险不在组件本身，而在组件与业务样式互相牵动的那部分；把升级做成独立提交，风险就被限制在一个可回退的范围内。

**速记**：升级分批、独立提交、先冻结后回归，出问题回退该提交而不动业务代码。



### 黑白单色的适用理由

单色不是省事的结果，而是一套有明确收益与明确代价的选择。这一节把收益与代价都说清楚。

#### 无彩色的信息分工

**无彩色配色**：是只用明度一个维度组织界面的配色方式，色相与饱和度全部置零，层次全靠明度差表达。

- 层次来源：明度差承担绝大部分层级区分，因此明度阶梯必须等距且有据可依。
- 语义让位：中性色不携带情绪，把「强调」的语义完整让给位置、字重、边框与留白。
- 状态处理：成功、警告、危险等状态在单色方案里退化为一小撮饱和度有限的彩色，属于受控的例外。
- 图表约束：系列区分不能再靠色相，必须靠明度阶梯与图案叠加，见第 11 篇。
- 衰减特性：去除色相后，界面在高亮、低色域、打印与截图压缩等场景下的表现更稳定。

```css
/* 单色方案里层次只由明度承担，色度与色相通道全部置零 */
:root {
  --background: oklch(1 0 0);
  --card: oklch(1 0 0);
  --muted: oklch(0.97 0 0);
  --border: oklch(0.922 0 0);
  --muted-foreground: oklch(0.54 0 0);
  --foreground: oklch(0.145 0 0);
}
```

> 面与面之间的区分在单色方案里只能靠明度和边框，一旦明度阶梯取值随意，界面会立刻显得脏而不是简洁。

**速记**：无彩色把层次全部交给明度，强调交给位置与字重，彩色只保留给必须被识别的状态。



#### 后台管理系统的使用场景

**后台管理系统**：是以数据密集、操作重复、停留时间长为主要特征的管理界面，与面向浏览的展示型页面诉求不同。

- 信息密度：一屏要容纳比展示页多得多的字段与操作，配色越安静越有利于扫读。
- 使用时长：长时间停留使高饱和度配色的疲劳感被放大，无彩色方案在这一项上天然占优。
- 状态克制：绝大多数元素是中性状态，只有少量记录处于异常，彩色应当稀缺才显得有效。
- 一致性压力：表单、表格、筛选器大量复用同一种零件，对组件一致性的要求高于展示页。
- 主题诉求：深浅两套外观是常见诉求，单色方案的两套取值可以一一对应，落地成本低。

```tsx
// 数据密集界面：状态用文字与边框区分，不靠整行填色
<td className="px-4 py-2 text-sm tabular-nums">{amount}</td>
<td className="px-4 py-2">
  <Badge variant={record.status === "failed" ? "destructive" : "secondary"}>
    {record.statusLabel}
  </Badge>
</td>
```

> [!WARNING]
> **警告内容**：单色不等于把状态也做成灰色。全灰状态下异常记录与正常记录无法区分，会直接造成业务误判；状态必须保留可识别的差异，只是把这个差异的体积压到最小。

**速记**：后台系统数据密集、停留时间长、状态以中性为主，单色方案在扫读效率与疲劳度上占优。



#### 与品牌色的关系

**品牌色**：是组织视觉识别体系中的主色，在单色后台方案里被压缩到极少数必须出现的位置。

- 保留位置：登录页、空状态插图、顶部品牌标识与产品名，以及少数确认类关键操作。
- 剔除位置：常规按钮、选中态、链接与图标一律回到中性色，不参与品牌表达。
- 实现方式：品牌色以独立令牌存在，组件默认不引用它，只有明确标注的位置才取值。
- 冲突处理：品牌色与状态色同屏时，品牌色让位，避免出现两种强调互相争夺注意力。
- 演进空间：品牌色单独成令牌后，换品牌只需改一个取值，不影响界面层级结构。

```css
/* 品牌色独立成令牌，组件默认不引用；只在与品牌相关的位置取值 */
:root {
  --brand: oklch(0.52 0.19 255);
  --brand-foreground: oklch(0.99 0 0);
}
```

> 单色后台不是没有品牌色，而是把品牌色的出场次数压到最低，让每一次出场都仍然有效。

**速记**：品牌色独立成令牌、只在登录页与品牌标识等处出场，常规交互一律回到中性色。



### 本系列的阅读顺序

本主题十五篇按「先有底座、再分组件、后定规范」的顺序组织，可按需跳读。

- 底座三篇：第 2 篇讲初始化与命令，第 3 篇讲样式与变量，第 4 篇讲主题体系，是其余各篇的共同前提。
- 组件六篇：第 5 篇到第 10 篇按按钮、表单、展示、表格、导航、反馈分组，可直接查用。
- 图表与布局两篇：第 11 篇讲单色图表，第 12 篇讲后台骨架，是组件落到页面的第一层组合。
- 规范与检查两篇：第 13 篇给出令牌取值与判定标准，第 14 篇给出可执行的可访问性检查清单。
- 参考一篇：第 15 篇汇总官方文档入口与延伸阅读。

```bash
# 按依赖顺序阅读的推荐路径
# 2 初始化 -> 3 样式底座 -> 4 主题体系 -> 13 设计规范
# 5 至 10 组件族可插在读 -> 11 图表 -> 12 布局 -> 14 检查
```

> 顺序不是硬性的：已经会用这套组件时，直接从第 13 篇的规范开始反向查组件篇更省时间。

**速记**：先底座、再组件、后规范，组件六篇可插读，规范篇是反向查阅的入口。
