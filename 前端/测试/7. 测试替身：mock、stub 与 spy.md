## 测试替身：mock、stub 与 spy

### 测试替身的概念分类

**测试替身的概念分类** 模块回答两个问题：哪些协作对象需要被替换，以及常见的替身形态各自承担什么职责。后续模块逐个展开 Vitest 提供的三个入口 vi.fn、vi.spyOn 与 vi.mock。

#### 测试替身与真实依赖

**测试替身（test double）**：是在测试中替代真实协作对象的可控对象，用来隔离外部依赖、固定用例输入并暴露被调用过程。

- 隔离：真实依赖可能访问网络、数据库或系统时钟，执行结果随环境变化。
- 可控：替身可以指定返回值、抛出错误、延迟敲定，让分支被精确触发。
- 可观测：替身记录被调用的次数、参数与返回值，断言不必依赖副作用。
- 代价：替身一旦偏离真实实现，用例通过而线上仍然出错，这时的绿灯是假绿灯。

```js
// src/api/subscribe.js
export async function sendNotification(channel, text) {
  const response = await fetch(`https://api.example.com/${channel}/messages`, {
    method: "POST",
    body: JSON.stringify({ text }),
  });
  return response.json(); // 依赖真实网络，测试环境不可控
}
```

> 测试替身替换的是「协作对象」，不是「被测对象」；被测模块本身始终跑真实实现，这条边界决定了用例到底验证了什么。

**速记**：测试替身替代真实协作对象，换来隔离、可控与可观测。



#### 五类替身的分工

**五类替身**：是业界按「提供了什么、记录了什么」划分的替身分类，依次为 dummy、stub、spy、mock 与 fake。

- dummy 占位对象：只用于填满参数表，被调用也不会产生断言价值。
- stub 桩：返回预设结果，让被测代码走进指定分支。
- spy 侦测：在真实实现外面包一层，记录调用并允许临时替换实现。
- mock 模拟：预先约定期望的调用，断言「是否按要求被调用」。
- fake 假实现：带简化逻辑的可用替代品，例如基于内存 Map 的仓库实现。

```js
const paymentGatewayStub = {
  charge: () => ({ id: "pay_1", status: "succeeded" }),
};

const auditSpy = vi.fn();
auditSpy({ action: "charge", id: paymentGatewayStub.charge().id });

console.log(auditSpy.mock.calls.length); // 1
console.log(auditSpy.mock.calls[0][0].action); // "charge"
```

> 五类替身在日常讨论中常被统称为 mock，读第三方文档时需要按上下文判断作者指的是哪一类；Vitest 的 vi.fn 既能当 stub 也能当 spy。

**速记**：dummy 占位、stub 给结果、spy 记录、mock 验期望、fake 带简化逻辑。



#### 替身的适用边界

**替身的适用边界**：是以「依赖是否跨越进程、时间或网络边界」为判据的替换范围，标准是可控制性而不是代码是否好写。

- 应当替换：网络请求、文件系统与数据库、系统时钟、随机数、消息队列、第三方 SDK。
- 不应替换：被测模块内部的计算规则、普通数据结构的读写、纯函数。
- 灰区：同进程内的其他业务模块，替换后用例更稳，但会与模块划分绑定，按团队约定处理。
- 反例：为了「让测试跑得更快」而替换纯计算逻辑，用例于是不再验证任何业务规则。

```js
// 纯计算逻辑：不需要替身，直接跑真实实现
export function calculateDiscount(subtotal, memberLevel) {
  return memberLevel === "gold" ? subtotal * 0.9 : subtotal;
}

console.log(calculateDiscount(200, "gold")); // 180
```

> [!CAUTION]
> **注意内容**：把业务规则也用替身挡掉，会让测试只验证「替身被调用了」，得到的是关于替身本身的结论，不是关于产品的结论。

**速记**：只替换不可控的跨边界依赖，业务规则与纯计算跑真实实现。



### vi.fn 创建模拟函数

**vi.fn 解决的问题**：是不依赖任何既有对象，凭空造出一个可指定行为、可记录调用的函数，用于替代回调、事件处理器与注入的协作函数。

#### vi.fn 的签名与返回值

**vi.fn(implementation?)**：是 Vitest 的模拟函数工厂，implementation 为可选的初始实现，可以传普通函数、箭头函数或类，返回一个 Mock 实例。

- 省略参数：返回的模拟函数被调用时返回 undefined，调用记录照常写入。
- 传入函数：以该函数作为实现，之后仍可用实例方法整体覆盖。
- 传入类：生成实例时保留实现类的原型链，instanceof 检查通过。
- 记录字段：mock.calls、mock.results、mock.instances、mock.contexts 在每次调用后更新。

```js
const formatPrice = vi.fn((cents) => `$${(cents / 100).toFixed(2)}`);

console.log(formatPrice(1250)); // "$12.50"
console.log(formatPrice.mock.calls); // [[1250]]
console.log(formatPrice.mock.results); // [{ type: "return", value: "$12.50" }]
console.log(typeof formatPrice); // "function"
```

> 模拟函数是普通函数加记录字段，因此可以直接作为回调传给被测代码，不需要额外的包装层。

**速记**：vi.fn 的可选参数就是初始实现，返回值同时是可调用函数与调用记录器。



#### 调用记录与断言

**调用记录**：是 Mock 实例保存在 mock 属性上的历史数据，用来断言函数的调用次数、参数与返回情况。

- mock.calls：二维数组，每一项是一次调用的参数列表。
- mock.results：每一项形如对象，type 取 return、throw 或 incomplete，value 为返回值或抛出的错误。
- 承诺特例：模拟函数返回承诺时 results 中的 type 始终为 return，即使该承诺已经被拒绝。
- mock.lastCall：最后一次调用的参数，方便快速查看。
- 匹配器：toHaveBeenCalled、toHaveBeenCalledTimes、toHaveBeenCalledWith、toHaveReturnedWith。

```js
const recordMetric = vi.fn();
recordMetric("page_view", { path: "/pricing" });
recordMetric("click", { path: "/pricing" });

expect(recordMetric).toHaveBeenCalledTimes(2);
expect(recordMetric).toHaveBeenCalledWith("page_view", { path: "/pricing" });
expect(recordMetric.mock.calls[1][0]).toBe("click"); // "click"
expect(recordMetric).toHaveReturnedWith(undefined);
```

> 断言参数优先使用 toHaveBeenCalledWith 做深度相等比较，直接读取 mock.calls 下标只在需要检查调用顺序或额外字段时使用。

**速记**：mock.calls 记参数、mock.results 记结果，断言优先走匹配器。



#### 实现函数与返回值控制

**实现控制**：是用实例方法替换模拟函数内部实现或返回值的做法，覆盖 mockImplementation、mockReturnValue、mockResolvedValue 等方法。

- mockImplementation(fn)：整体替换实现，适合需要读取参数的场景。
- mockReturnValue(value) 与 mockReturnValueOnce(value)：固定返回值，Once 版本只生效一次。
- mockResolvedValue(value) 与 mockRejectedValue(error)：让调用返回已敲定或已拒绝的 Promise。
- 消费顺序：Once 系列按注册顺序优先消费，用尽后回退到非 Once 的默认实现。

```js
const loadUserProfile = vi
  .fn()
  .mockResolvedValueOnce({ id: 1, displayName: "Ada Lovelace" })
  .mockRejectedValueOnce(new Error("profile service unavailable"));

await loadUserProfile(); // { id: 1, displayName: "Ada Lovelace" }
await loadUserProfile().catch((error) => console.log(error.message));
// "profile service unavailable"
```

> [!TIP]
> **建议内容**：替身要显式覆盖失败分支，网络错误、超时与空结果各写一条用例，只测成功路径等于放弃异常处理代码的验证。

**速记**：mockImplementation 换逻辑，mockReturnValue 定返回，Once 系列只生效一次。



#### 模拟函数的类型标注

**类型标注**：是让 TypeScript 把原函数的类型套回模拟函数上的做法，由辅助函数 vi.mocked 完成。

- vi.mocked(fn)：运行时原样返回传入值，只改变类型，不改变行为。
- 作用：让 mockResolvedValue 等方法的参数受原函数返回类型约束，写错立即报错。
- 深度声明：vi.mocked(object, { deep: true }) 告知类型系统整个对象都被模拟。
- 收益：编辑器能补全 mock 属性，避免使用 as 类型断言绕过检查。

```ts
import { fetchUserProfile } from "../src/api/profile";

vi.mock("../src/api/profile");

const mockedFetchUserProfile = vi.mocked(fetchUserProfile);

it("在资料接口可用时应返回用户档案", async () => {
  mockedFetchUserProfile.mockResolvedValue({ id: 7, displayName: "Grace Hopper" });
  await expect(mockedFetchUserProfile(7)).resolves.toMatchObject({ id: 7 });
});
```

> 自动模拟生成的替身会丢失原有类型，vi.mocked 是恢复类型信息的标准手段，比手写 as ReturnType 更稳。

**速记**：vi.mocked 只改类型不改行为，让替身上的方法与断言保持原函数签名。



### vi.spyOn 侦测既有方法

**vi.spyOn 解决的问题**：是在不拥有该对象的情况下观察或临时改写它的某个成员，用于替换被测代码从外部拿到的对象上的方法。

#### vi.spyOn 的签名与访问类型

**vi.spyOn(object, methodName, accessType?)**：是在既有对象成员上安装侦测的 API，object 为宿主对象，methodName 为被侦测的属性名，可选的 accessType 取 get 或 set 用于侦测取值器与设值器，返回 Mock 实例。

- 保留原实现：不调用 mockImplementation 时被侦测的方法仍然执行原有逻辑。
- 记录行为：调用历史写入 mock.calls 等字段，断言方式与 vi.fn 一致。
- 类型约束：methodName 必须是 object 的键，TypeScript 下拼写错误会编译报错。
- 与 vi.fn 的差别：vi.fn 创建全新函数，vi.spyOn 依附既有对象并支持还原。

```js
const logger = {
  info(message) {
    process.stdout.write(`[info] ${message}\n`);
  },
};

const infoSpy = vi.spyOn(logger, "info");
logger.info("cache warmed");
// [info] cache warmed

expect(infoSpy).toHaveBeenCalledWith("cache warmed");
```

> 侦测类上的方法时，替换实现必须使用 function 或 class 关键字书写，箭头函数没有构造能力，会在实例化时报 anonymous is not a constructor。

**速记**：vi.spyOn 在既有对象上装侦测，默认保留原实现，签名是对象、属性名与可选访问类型。



#### 侦测内置对象与全局方法

**内置对象侦测**：是把 vi.spyOn 用在 globalThis、Date、Math、Storage 等宿主提供的对象上，从而消除环境侧的不确定性。

- 时间：侦测 Date.now 固定时间戳，避免用例在跨天或跨秒时抖动。
- 随机：侦测 Math.random 让随机分支可复现。
- 存储：jsdom 与 happy-dom 环境中可侦测 Storage.prototype 上的 getItem 与 setItem。
- 网络：侦测 globalThis 上的 fetch，也可用 vi.stubGlobal 整体替换一个全局属性。

```js
vi.spyOn(Math, "random").mockReturnValue(0.5);

const pickReviewer = (candidates) =>
  candidates[Math.floor(Math.random() * candidates.length)];

console.log(pickReviewer(["Ada", "Grace"])); // "Grace"
console.log(Math.random.mock.calls.length); // 1
```

> [!WARNING]
> **警告内容**：侦测内置对象后若没有还原，同一测试文件内后续用例会继续使用被替换的实现，失败现象会扩散到与被测功能无关的用例上。

**速记**：侦测 Date、Math、fetch 等内置对象可消除环境噪声，但必须在用例结束后还原。



#### mockRestore 与还原策略

**mockRestore()**：是 Mock 实例上的还原与清理方法，在 mockReset 的基础上把被侦测对象的原始属性描述符还原回去，效果是清空调用记录加还原本体。

- mockClear()：把 mock 上的全部状态清回初始值，不重置实现。
- mockReset()：清空状态并重置实现，其中 vi.fn(implementation) 回到该实现，vi.fn() 回到返回 undefined 的空实现，once 系列一并清空。
- mockRestore()：在 mockReset 基础上还原被侦测对象的原始属性描述符，对 vi.fn 创建的模拟函数与 mockReset 等价。
- 批量还原：vi.restoreAllMocks() 处理全部侦测，但不重置自动模拟生成的替身。

```js
function currentBillingMonth(now) {
  return new Date(now).toISOString().slice(0, 7);
}

afterEach(() => {
  vi.restoreAllMocks();
});

it("在固定时间下应返回当月账单周期", () => {
  vi.spyOn(Date, "now").mockReturnValue(new Date("2026-09-01T00:00:00Z").getTime());
  expect(currentBillingMonth(Date.now())).toBe("2026-09");
});
```

> 还原动作放在 afterEach 中只对当前文件生效；若担心遗漏，可在配置中打开 restoreMocks，让 Vitest 在每条用例之前统一处理。

**速记**：mockClear 只清状态，mockReset 连实现一起重置，mockRestore 额外还原描述符且只对 spyOn 有差别。



### vi.mock 模块模拟入门

**vi.mock 解决的问题**：是在模块边界上整体替换导入结果，让被测文件依赖的 api、配置或第三方 SDK 在执行之前就换成替身。

#### vi.mock 的路径与工厂

**vi.mock(path, factory?)**：是把指定模块的全部导入替换为替身的 API，path 为模块路径且支持 Vite 配置的别名，factory 为返回替身对象的工厂函数，调用会被提升到文件所有 import 之前执行。

- 提升：无论写在文件哪个位置都先于 import 求值，因此工厂内不能引用文件顶部的变量。
- 工厂返回值：模块的每个导出都取自工厂返回的对象，默认导出需要显式写在 default 键上。
- 省略工厂：Vitest 自动模拟该模块的全部导出，函数返回 undefined，属性保持原结构。
- 执行次数：工厂只运行一次，结果被缓存，直到 vi.unmock 或 vi.doUnmock 解除。
- 适用范围：只作用于 import 语法导入的模块，CommonJS 的 require 不在处理范围内。

```js
import { fetchUserProfile } from "../src/api/profile";

vi.mock("../src/api/profile", () => ({
  fetchUserProfile: vi.fn().mockResolvedValue({ id: 7, displayName: "Grace Hopper" }),
  default: vi.fn(),
}));

it("在资料接口可用时应返回用户档案", async () => {
  await expect(fetchUserProfile(7)).resolves.toEqual({ id: 7, displayName: "Grace Hopper" });
});
```

> [!IMPORTANT]
> **重要内容**：工厂函数在 import 之前执行，直接读取文件顶部定义的变量会抛出变量未初始化错误；需要在工厂内外共享数据时，必须先用 vi.hoisted 把变量提到导入之前。

**速记**：vi.mock 的工厂整体替换模块导出，调用被提升，工厂内不能引用外部变量。



#### 部分模拟与保留原实现

**部分模拟**：是只替换模块中的少数导出、其余导出继续使用原实现的做法，通过工厂的 importOriginal 参数或 vi.importActual 取得原模块后再选择性覆盖。

- importOriginal：工厂函数的第一个参数，调用后返回原模块的导出对象。
- vi.importActual(path)：绕过 mock 注册表直接导入原模块，适合需要提前取值的场景。
- 异步工厂：工厂可以写成 async 函数，Vitest 会等待返回的 Promise 解析后再使用结果。
- 应用场景：模块内同时混有纯函数与 I/O 函数时，只替换 I/O 部分，纯函数保持真实。

```js
vi.mock("../src/api/profile", async (importOriginal) => {
  const actual = await importOriginal();
  return {
    ...actual,
    fetchUserProfile: vi.fn().mockResolvedValue({ id: 7, displayName: "Grace Hopper" }),
  };
});

import { fetchUserProfile, normalizeProfile } from "../src/api/profile";

expect(fetchUserProfile).toBeDefined();
expect(normalizeProfile({ id: 7 })).toEqual({ id: 7, displayName: "未知用户" });
```

> 使用动态路径时必须与导入语句中的路径写法完全一致，别名与相对路径混用会让替换失效，表现为替身没有被安装。

**速记**：部分模拟用 importOriginal 取回原模块，只覆盖需要隔离的那几个导出。



### 替身清理与常见滥用

**替身清理与常见滥用** 模块解决替身带来的状态残留问题，并给出判定替身是否写过头的方法。清理不当的典型症状是单跑通过、全量运行失败。

#### 清理 API 与配置项

**清理策略**：是在用例之间复位替身状态的做法，既可显式调用清理 API，也可在配置中声明由 Vitest 自动执行。

- vi.clearAllMocks()：对全部替身调用 mockClear，清空调用记录与结果。
- vi.resetAllMocks()：对全部替身调用 mockReset，清空记录并重置实现。
- vi.restoreAllMocks()：还原 vi.spyOn 建立的侦测，不影响自动模拟生成的替身。
- 配置项：test.clearMocks、test.mockReset、test.restoreMocks 分别对应上述三种行为，在每条用例之前自动执行。
- 环境与全局：test.unstubEnvs 与 test.unstubGlobals 负责收回 vi.stubEnv 与 vi.stubGlobal 的改动。

```bash
npm install --save-dev vitest
npx vitest run
# Test Files  1 passed (1)
# Tests  4 passed (4)
npx vitest
# 进入监听模式，按 u 更新快照，按 q 退出
```

```js
// vitest.config.js
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    clearMocks: true,
    restoreMocks: true,
    unstubEnvs: true,
    unstubGlobals: true,
  },
});
```

> 配置项在每条用例之前执行，与在 afterEach 中手动调用等效；两者同时存在不会报错，只是重复清理没有必要。

**速记**：clear 清记录、reset 重置实现、restore 还原侦测，配置项可让它们在用例前自动执行。



#### 常见滥用与自查

**常见滥用**：是把替身写到超出隔离边界，导致用例通过而真实集成仍然失败的做法，自查的标准是「删掉替身后这条用例还剩多少验证价值」。

- 断言实现细节：断言内部函数的调用次数与顺序，会让正常重构必然改测试。
- 替身无处不在：连纯函数与数据结构也替换，用例不再验证任何真实逻辑。
- 忘记还原：状态跨用例泄漏，表现为单跑通过、全量失败，且报错位置与改动无关。
- 替身漂移：替身返回值与接口契约长期不一致，测试成为掩盖问题的假绿灯。
- 过度断言：对内部协作对象的每一次调用都写断言，用例与实现强绑定。

```js
// 反例：断言内部调用顺序，调整实现顺序后必然失败
const saveDraft = vi.fn();
const cacheDraft = vi.fn();

saveDraft();
cacheDraft();

expect(saveDraft.mock.invocationCallOrder[0]).toBeLessThan(
  cacheDraft.mock.invocationCallOrder[0],
);
```

```bash
# 定位「单跑通过、全量失败」的用例顺序污染
npx vitest run src/api/subscribe.test.js   # 单文件复现
npx vitest run --no-file-parallelism       # 排除文件间并发干扰
```

> 替身的数量与用例的稳定性不成正比：每增加一个替身，就多一处可能与真实行为漂移的地方，替换范围越小越好。

**速记**：替身只挡跨边界依赖，少断言调用细节，多断言可观察结果。
