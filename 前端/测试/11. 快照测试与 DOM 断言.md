## 快照测试与 DOM 断言

### 快照测试的原理与生成

**快照测试**：是把一段可序列化的值（组件渲染结果、数据对象、报错信息等）第一次运行时写入文件，后续运行时逐字比对是否变化的测试方式。

本模块讲清快照的工作方式、生成流程与落盘位置，先建立对快照文件的基本认识。

#### 快照测试的定义与工作方式

**快照测试的工作方式**：是「首次记录、后续比对」的两段式流程，首次运行没有基准文件时写入快照，之后运行把实际值与快照文本逐字比较。

- 断言入口：使用 toMatchSnapshot 建立基准，使用 toMatchInlineSnapshot 把基准写在用例文件内。
- 比对粒度：比对的是序列化后的文本，任何空白、属性顺序与内容差异都会判定为不匹配。
- 值域广泛：可快照任意可序列化的值，组件渲染结果只是其中最常见的一种。
- 更新语义：比对失败不会自动覆盖基准，必须显式执行更新命令。

```js
import { describe, it, expect } from "vitest"
import { mount } from "@vue/test-utils"
import UserCard from "../src/components/UserCard.vue"

describe("UserCard", () => {
  it("在传入姓名时应渲染出与基准一致的 DOM 结构", () => {
    const wrapper = mount(UserCard, { props: { name: "Ada Lovelace" } })
    expect(wrapper.html()).toMatchSnapshot()
  })
})
```

> 快照测试记录的是「当时长什么样」，它不解释为什么应该是这样，因此常与显式断言配合使用。

**速记**：快照首次记录、后续逐字比对，差异需显式更新才会覆盖。



#### 首次生成与后续比对

**首次生成**：是基准快照不存在时，运行器把实际序列化结果写入快照文件并把该用例标记为新增。**后续比对**：是基准存在后，运行器把实际值与基准逐字比较并报告差异。

- 首次运行：用例通过，快照文件被创建，输出中标注新增的快照数量。
- 一致运行：实际值与基准完全相同，用例通过，不做任何写入。
- 不一致运行：报告差异位置，用例失败，等待人工判断是缺陷还是预期变更。
- 基准缺失：快照文件被误删时行为等同于首次生成，会重新写入而不再校验。

```bash
npx vitest run
# Snapshot files written: 1
# Tests  1 passed
```

> 快照文件必须与测试文件一同提交，否则其他环境每次运行都会重新生成基准，比对形同虚设。

> [!IMPORTANT]
> **重要内容**：快照文件漏提交会让持续集成上的首次运行无条件通过，看似绿灯实则完全没有校验。

**速记**：首跑写入、二跑比对，基准文件缺一不可。



#### 快照文件的位置与命名

**快照文件名**：由测试文件名加 .snap 后缀构成，默认存放在测试文件同级目录的 __snapshots__ 目录下。

- 目录约定：__snapshots__ 与测试文件同级，便于就近审阅与随测试一起提交。
- 文件命名：测试文件为 user-card.test.js 时，快照文件为 __snapshots__/user-card.test.js.snap。
- 条目命名：同一文件内多条快照按用例全名区分，用例重命名会导致旧条目成为孤儿。
- 路径定制：可通过配置项 resolveSnapshotPath 改写快照落盘位置，适配集中存放的仓库。

```bash
ls src/components/__snapshots__
# user-card.test.js.snap
```

```js
// vitest.config.js 中改写快照路径的写法
export default {
  test: {
    resolveSnapshotPath: (testPath, snapshotExtension) =>
      testPath.replace("src/", "tests/snapshots/") + snapshotExtension
  }
}
```

> 旧条目成为孤儿时不会自动清除，需用更新命令重新生成或手工删除，避免快照文件长期膨胀。

**速记**：快照落在同级 __snapshots__ 目录，命名沿用测试文件名加 .snap。



### 快照更新与评审

**更新**：是用新结果覆盖基准快照的过程。**评审**：是判断新结果是否为预期变化的过程。二者顺序固定，先评审再更新，不可颠倒。

本模块讲清更新的命令、评审的要点与持续集成中的处理方式。

#### 更新命令与更新时机

**更新命令**：是让运行器把不一致的快照改写为当前实际值的命令，Vitest 使用 -u 或 --update，Jest 使用 -u。

- Vitest：执行 npx vitest run -u 更新全部不一致快照，默认先跑一遍用例。
- Jest：执行 npx jest -u，同样以一次完整运行作为更新前提。
- 定点更新：可用文件路径或用例名筛选，只更新受影响的快照文件。
- 时机把握：仅在确认差异来自预期变更时更新，绝不能把 -u 当成让红灯变绿的快捷方式。

```bash
npx vitest run -u src/components/UserCard.test.js
# Snapshots  1 updated
```

> 更新前先运行一次不带 -u 的命令，看清差异内容再决定是否更新，这是防止误覆盖的最小流程。

> [!WARNING]
> **警告内容**：在未查看差异的情况下直接加 -u 提交，会把真实回归写进基准，此后测试永远为绿灯。

**速记**：确认差异属于预期变更后再用 -u 更新，禁止不看差异直接更新。



#### 快照评审的要点

**快照评审**：是在代码评审中逐条检查快照差异，确认差异位置与期望的变更范围一致。

- 看差异不看数量：差异行数多不代表错误，关键是有没有出现意料之外的节点或文案。
- 对齐变更意图：需求改动应只影响与之相关的那几条快照，其余条目不应变动。
- 拒绝整片重写：大量无关快照同时变动通常意味着序列化器或环境发生了变化。
- 关注删除项：只剩删除的差异要确认对应功能是否真的被移除。

```bash
git diff --stat -- "**/__snapshots__/*.snap"
# 观察变动是否集中在与本次需求相关的文件中
```

> 快照差异是可读的文本，把它当作代码来评审，才可能发现被掩盖的渲染回归。

**速记**：评审快照差异要看位置与意图是否匹配，而不是看差异行数多少。



#### 持续集成中的快照校验

**持续集成中的快照校验**：是在流水线中以非交互方式运行快照测试，禁止静默写入新基准，并对不匹配直接判失败。

- 运行模式：使用一次性运行命令而非监听模式，保证进程跑完即退出。
- 写入限制：流水线环境不应产出新的快照文件，新增基准一律在本地生成并提交。
- 失败即阻断：快照不匹配应让流水线失败，交由人工判断是缺陷还是预期变更。
- 产物留痕：把失败时的差异输出保留在日志或报告产物中，便于事后定位。

```bash
CI=true npx vitest run --reporter=default
# 快照不匹配时进程以非零状态码退出，流水线随即失败
```

> 在流水线上自动生成新快照会绕过评审，等于让校验失效；新增基准只应来自本地提交。

**速记**：流水线只比对不写入，不匹配即失败并保留差异输出。



### 内联快照与序列化

**内联快照**：是把基准文本直接写在用例文件内的快照形式。**序列化**：是把任意值转换为稳定文本的过程，它决定快照里能看到什么、看不到什么。

本模块讲清内联写法与序列化的可控点。

#### 内联快照 toMatchInlineSnapshot

**toMatchInlineSnapshot**：是把基准直接写入用例源码的快照断言，签名为 toMatchInlineSnapshot(snapshot)，snapshot 为可选的初始字符串，省略时由运行器填入。

- 阅读优势：基准与断言同处一行区域，改代码时无需跳转到另一个文件。
- 更新方式：执行带 -u 的运行命令，运行器会把新文本回写到源码中。
- 长度限制：适合短小稳定的值，结构很长的组件树写入源码会严重挤压可读性。
- 格式约束：回写会按格式化规则整理缩进，与手写内容不一致时以运行器回写结果为准。

```js
it("在传入姓名时应内联记录渲染文本", () => {
  const wrapper = mount(UserCard, { props: { name: "Ada Lovelace" } })
  expect(wrapper.text()).toMatchInlineSnapshot(`"Ada Lovelace"`)
})
```

> 内联快照把基准放进源码，评审时与逻辑改动出现在同一处差异里，比外部文件更容易被注意到。

**速记**：内联快照写在用例内，用 -u 回写，只适合短小稳定的值。



#### 自定义序列化器

**序列化器**：是决定某个值如何转换为快照文本的对象，需提供 test 判断函数与 serialize 输出函数，通过 expect.addSnapshotSerializer 注册。

- 注册入口：调用 expect.addSnapshotSerializer(serializer) 为当前测试文件追加序列化规则。
- 接口约定：test 接收值并返回布尔值，serialize 接收值并返回字符串。
- 典型用途：把时间对象、DOM 节点、金额对象等类型转成稳定且可读的文本。
- 生效顺序：后注册的规则优先匹配，具体类型应优先于宽泛类型。

```js
expect.addSnapshotSerializer({
  test: (value) => value instanceof Date,
  serialize: (date) => `Date(${date.toISOString().slice(0, 10)})`
})

expect({ createdAt: new Date("2026-09-13") }).toMatchSnapshot()
// "{\n  \"createdAt\": Date(2026-09-13)\n}"
```

> 自定义序列化器也能用于抹平无关差异，但抹平范围需写进命名或注释，避免隐藏真实信息。

**速记**：序列化器用 test 与 serialize 两个方法描述转换规则，登记后按序生效。



#### 不稳定字段的处理

**不稳定字段**：是每次运行取值都不同的数据，如当前时间、随机数、自增标识与请求追踪号，它们会让快照永远无法稳定匹配。

- 固定时间：用假定时器把系统时间钉在某一刻，再运行快照断言（详见本主题第 9 篇 异步测试与定时器控制）。
- 属性匹配：用 toMatchSnapshot 的属性匹配参数声明哪些字段只校验类型，如 expect.any(String)。
- 序列化过滤：在自定义序列化器中把不稳定字段替换为固定占位文本。
- 结构拆分：把不稳定字段从事被测对象中剥离，只快照稳定部分。

```js
import { vi } from "vitest"

vi.useFakeTimers()
vi.setSystemTime(new Date("2026-09-13T00:00:00Z"))

expect({ id: "u_1", createdAt: new Date() }).toMatchSnapshot({
  createdAt: expect.any(Date)
})
```

> 用属性匹配放宽字段时，字段的存在性与类型仍在校验范围内，比直接删除字段更安全。

**速记**：不稳定字段用固定时间、属性匹配或序列化替换三种手段收敛。



### DOM 断言方案

**DOM 断言**：是直接对渲染出的节点文本、属性与样式状态做判断的断言方式，它不依赖基准文件，表达的是明确的期望。

本模块讲清快照与显式断言的取舍、常用 DOM 断言的写法与组件树断言的组织方式。

#### 快照断言与显式断言的取舍

**快照断言**：用一段基准文本覆盖大量细节，写起来快、覆盖广。**显式断言**：逐条写出期望值与期望状态，意图清楚、失败信息精确。

- 快照长处：适合结构稳定、改动频率低的整块输出，一次断言覆盖节点顺序与属性。
- 显式长处：适合关键行为与关键文案，失败时直接指出「期望什么、实际是什么」。
- 组合策略：用少量显式断言锁定关键节点，再用一条快照兜住整体结构。
- 反例识别：一个用例里塞入整页快照，又没有任何显式断言，属于典型失衡。

```js
it("在传入姓名与角色时应渲染关键节点且结构稳定", () => {
  const wrapper = mount(UserCard, { props: { name: "Ada Lovelace", role: "工程师" } })

  expect(wrapper.get("h2").text()).toBe("Ada Lovelace")   // 显式断言锁定关键文案
  expect(wrapper.find("[data-testid=role]").exists()).toBe(true)
  expect(wrapper.html()).toMatchSnapshot()                 // 快照兜住整体结构
})
```

> 显式断言回答「必须成立什么」，快照回答「整体是否照旧」，两者的职责并不重叠。

**速记**：关键行为用显式断言，整体结构用快照，两者互补而非替代。



#### 常用 DOM 断言方式

**DOM 断言方式**：是围绕查询结果展开的一组判断，既可用包裹器自带方法取值后比较，也可用 DOM 专用匹配器直接断言节点状态。

- 包裹器取值：text()、html()、classes()、attributes()、element 取到原始节点后再用通用匹配器比较。
- 存在与可见：exists() 判断节点是否存在，isVisible() 判断是否处于可见状态。
- DOM 匹配器：@testing-library/jest-dom 提供 toBeVisible、toHaveClass、toHaveAttribute、toHaveTextContent、toBeChecked 等断言。
- 接入方式：在测试启动文件中引入该库的注册入口，匹配器即挂到 expect 上。

```js
// vitest.config.js
export default {
  test: {
    environment: "jsdom",
    setupFiles: ["./vitest.setup.js"]
  }
}
```

```js
// vitest.setup.js
import "@testing-library/jest-dom/vitest"
```

```js
const submit = wrapper.get("[data-testid=submit]")

expect(submit).toHaveTextContent("提交")
expect(submit).toBeVisible()
expect(submit).not.toHaveClass("is-disabled")
expect(wrapper.find("[data-testid=remember]")).toBeChecked()
```

> DOM 匹配器失败时会输出节点结构，比通用的布尔比较更容易定位问题。

**速记**：先查询再用 DOM 匹配器断言存在、可见、类名、属性与文本。



#### Vue 组件树的断言写法

**组件树断言**：是沿父子关系查询子组件并断言其收到的 props 与渲染结果，用于验证组件之间的数据传递。

- 组件查询：用 findComponent 按组件定义查找，findAllComponents 取全部匹配实例。
- props 断言：读取子组件包裹器的 props 字段，比断言其内部 DOM 更贴近契约。
- 层级控制：用 shallowMount 时子组件被存根，只适合断言是否渲染出占位，不适合断言内部结构。
- 组织建议：父组件用例只断言传给子组件的输入，子组件自身行为交给子组件的用例。

```js
import { mount, shallowMount } from "@vue/test-utils"
import TodoList from "../src/components/TodoList.vue"
import TodoItem from "../src/components/TodoItem.vue"

const items = [{ id: 1, text: "写测试" }, { id: 2, text: "跑测试" }]
const wrapper = mount(TodoList, { props: { items } })

const firstItem = wrapper.findAllComponents(TodoItem)[0]
expect(firstItem.props("text")).toBe("写测试")

const shallow = shallowMount(TodoList, { props: { items } })
expect(shallow.findAllComponents(TodoItem).length).toBe(2)
```

> 断言子组件收到的 props，等于在验证组件之间的接口，比断言子组件内部结构更稳定。

**速记**：用 findComponent 取子组件实例，断言其 props 而非内部结构。



### 快照的适用与反模式

**适用范围**：是快照能够稳定发挥作用的场景；**反模式**是看似省事、实际上不断制造维护负担的用法。

本模块给出取舍标准与排查清单。

#### 适用场景

快照只在结构稳定且差异会被人审阅的场景才划算，典型适用场景有四类。

- 结构稳定的展示组件：props 少、分支少、改动频率低，快照能有效兜住整体结构。
- 序列化产物：配置对象、打包清单、错误对象等结构固定且需要逐字段留痕的值。
- 迁移校验：重构前后用同一份快照比对，快速发现意外的渲染差异。
- 接口契约：对外返回的数据结构变化时，快照差异能直接暴露字段增删。

```js
it("在导出配置时应保持结构稳定", () => {
  const config = buildExportConfig({ base: "/app", outDir: "dist" })
  expect(config).toMatchSnapshot()
})
```

> 判定某处是否值得加快照，可以问一句：这些内容发生变化时，是否必然会有人去审阅差异。

**速记**：稳定结构、序列化产物、迁移校验与接口契约适合用快照。



#### 反模式清单

六种常见用法看似省事，实际会让快照持续制造维护负担与评审噪声。

- 巨型快照：对整页或最外层组件做快照，任何细微改动都引发大片差异，评审形同虚设。
- 无脑更新：遇红就加 -u，跳过评审，把回归当基准写回。
- 快照替代断言：用快照代替本可写清的精确期望，失败信息变成一大段文本差异。
- 不稳定值入库：时间、随机数与自增标识直接进快照，用例反复无常。
- 快照数量膨胀：为每个 props 组合各存一份快照，文件远超用例本身的可读容量。
- 断言实现细节：对带有大量内部类名与包装节点的结构做快照，重构一次全线失败。

```bash
npx vitest run src/components
# 若失败用例几乎全部指向同一条快照，说明该快照粒度过粗
```

> [!CAUTION]
> **注意内容**：巨型快照失效时，评审者往往直接跳过差异，快照由此从保障退化为噪声。

**速记**：巨型快照、无脑更新、快照代替断言与不稳定值入库都是反模式。



#### 快照的生命周期管理

**快照的生命周期**：是从新增、稳定、变更到废弃的完整过程，每个阶段都需要对应的动作，否则快照文件会持续臃肿并逐渐失去校验价值。

- 新增阶段：新写的快照必须审阅一遍内容，确认没有把调试残留与不稳定值一并写入基准。
- 稳定阶段：用例只做比对，不允许顺手改基准；基准的变动一律伴随需求或缺陷修复。
- 变更阶段：差异经确认后集中更新，并在提交信息中说明变更原因，便于追溯。
- 废弃阶段：用例删除或重写后同步清理孤儿条目，避免快照文件中堆积无人认领的基准。
- 规模控制：单个快照文件条目过多时考虑拆分测试文件，让每个文件的职责边界更清楚。

```bash
npx vitest run -u --reporter=verbose | grep -E "added|updated|removed"
# 新增、更新与删除的条目数应与本次改动预期一致
```

> 快照文件属于测试资产而非构建产物，需要与测试用例一同评审、一同提交、一同清理。

**速记**：快照按新增、稳定、变更、废弃四阶段管理，孤儿条目定期清理。



#### 常见问题排查

快照出错的原因集中在三类，按现象逐一核对即可定位。

- 快照反复不匹配：定位不稳定字段，用固定时间、属性匹配或序列化替换处理。
- 新增快照未提交：核对版本控制状态，确认 .snap 文件已随测试文件一并提交。
- 孤儿快照：用例改名或删除后旧条目残留，用更新命令重新生成或手工清理。
- 平台差异：换行符与路径分隔符在不同系统上不同，序列化时应统一为固定文本。
- 更新未生效：确认运行的是带 -u 的命令，且过滤条件确实命中了目标文件。

```bash
npx vitest run -u --reporter=verbose 2>&1 | tail -n 20
# 确认 updated 计数与目标文件一致
```

> [!TIP]
> **建议内容**：把快照文件的变动纳入代码评审必看项，并在合并前抽查差异位置，可显著降低误更新概率。

**速记**：快照问题集中在不稳定字段、漏提交与孤儿条目三类，逐项排查即可。
