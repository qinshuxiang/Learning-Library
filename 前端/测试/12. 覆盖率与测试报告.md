## 覆盖率与测试报告

### 覆盖率的四种指标

**代码覆盖率**：是衡量测试执行时触及了多少源码的量化指标，通常以百分比表示。**测试报告**：是把覆盖率数据、用例结果与耗时汇总成可阅读产物的输出。

本模块先逐个解释四种指标的统计对象与含义，再讲采集器与报告。

四种指标在同一次运行中一并产出，汇总输出的形式如下：

```bash
npx vitest run --coverage
# % Coverage report from v8
# File          % Stmts  % Branch  % Funcs  % Lines
# All files       86.21     74.36    91.30    84.62
# src/utils       95.00     88.88   100.00    95.00
# src/api         72.50     50.00    83.33    71.42
```

#### 行覆盖率 lines

**行覆盖率**：是被测试执行到的可执行代码行数占可执行代码总行数的比例，它回答「有多少行代码至少跑过一次」。

- 统计对象：可执行语句所在的物理行，空行、注释与仅声明不产生执行行为的部分不计入。
- 计数方式：某一行只要被执行过一次即算已覆盖，重复执行不提高数值。
- 常见误导：一行内包含多个子表达式时，整行被判定为覆盖，实际仍有分支未走。
- 阈值键名：配置中使用 lines 键设置该指标的下限。

```json
{
  "coverage": {
    "thresholds": {
      "lines": 80
    }
  }
}
```

> 行覆盖率最容易达标，也最容易虚高，单独看它无法判断测试是否触及边界情况。

**速记**：行覆盖率衡量「至少跑过一次的代码行」占比，粒度最粗。



#### 语句覆盖率 statements

**语句覆盖率**：是被测试执行到的语句数占语句总数的比例，它回答「有多少条语句被执行过」。

- 统计对象：解析后的语句节点，一条语句可以跨多行，也可以与另一条语句同行。
- 与行覆盖率的关系：多数场景下两者数值接近，压缩代码或一行多语句时会出现差异。
- 差值含义：语句覆盖率明显低于行覆盖率，说明存在同一行内未被执行的语句。
- 阈值键名：配置中使用 statements 键设置该指标的下限。

```json
{
  "coverage": {
    "thresholds": {
      "statements": 80
    }
  }
}
```

> 行与语句两项指标通常一起看，二者出现明显偏差的地方值得单独检查。

**速记**：语句覆盖率按语句节点计数，与行覆盖率接近但更贴近实际执行单位。



#### 分支覆盖率 branches

**分支覆盖率**：是被测试执行到的分支路径数占分支路径总数的比例，它回答「每个判断的每条路径是否都走过」。

- 统计对象：条件语句的真假两支、三元表达式的两个结果、逻辑运算符的短路两侧。
- 计数方式：一个条件表达式贡献两条分支路径，两条都执行才计为完全覆盖。
- 价值所在：未覆盖分支往往对应异常处理与边界条件，是缺陷最集中的位置。
- 阈值键名：配置中使用 branches 键设置该指标的下限，通常低于其余三项。

```json
{
  "coverage": {
    "thresholds": {
      "branches": 70
    }
  }
}
```

> 四种指标中分支覆盖率最难提升，也最能反映测试用例是否覆盖了异常与边界。

**速记**：分支覆盖率按判断路径计数，覆盖异常与边界，最有参考价值。



#### 函数覆盖率 functions

**函数覆盖率**：是被测试调用过的函数数占函数总数的比例，它回答「有多少个函数被真正执行过」。

- 统计对象：函数声明、箭头函数、对象方法与类方法。
- 计数方式：函数体被执行过一次即算覆盖，调用次数与参数取值不影响数值。
- 常见情形：工具函数被其他模块间接调用即计入，不必被用例直接 import。
- 阈值键名：配置中使用 functions 键设置该指标的下限。

```json
{
  "coverage": {
    "thresholds": {
      "functions": 80
    }
  }
}
```

> 函数覆盖率为零说明该函数从未被任何测试路径触及，是排查死代码的直接线索。

**速记**：函数覆盖率按函数体是否被执行计数，可快速定位完全无人调用的代码。



### 采集器选择

**采集器**：是负责统计代码执行轨迹并换算成覆盖率数据的组件，Vitest 提供基于 V8 引擎与基于插桩的两套实现。

本模块讲清两套采集器的原理、取舍与安装启用方式。

#### V8 采集器

**V8 采集器**：是直接读取 V8 引擎内建覆盖率数据的采集器，通过调试协议采集执行轨迹，再把转译后的位置回填到源码。

- 原理：运行时不改写源码，由引擎记录哪些行被解释执行，运行时开销小。
- 优点：启动与采集速度快，对大型测试集友好，不改变源码体积。
- 限制：位置映射依赖源码映射，转译层级较多时映射精度下降，可能给出偏乐观的结果。
- 适用：以速度为先的大型项目，或作为日常开发时的快速反馈手段。
- 忽略注释：支持 v8 ignore 系列注释标记不需要统计的代码。

```bash
npm install --save-dev @vitest/coverage-v8
```

> V8 采集器是 Vitest 的默认方案，多数项目无需更换即可满足日常使用。

**速记**：V8 采集器靠引擎内建数据采集，快、省，精度受源码映射影响。



#### Istanbul 采集器

**Istanbul 采集器**：是在转译阶段向源码注入计数语句的采集器，运行时由这些计数器记录执行情况，运行后汇总为覆盖率。

- 原理：编译期在每个分支与语句前插入计数调用，运行后读取计数结果。
- 优点：计数点在源码层面明确，对转译后的代码定位更准，分支判定更严格。
- 限制：插桩带来额外运行开销与产物体积增长，大型测试集下更明显。
- 适用：对精度与一致性要求较高的项目，或需要与既有覆盖率平台沿用同一口径。
- 忽略注释：支持 istanbul ignore 系列注释标记不需要统计的代码。

```bash
npm install --save-dev @vitest/coverage-istanbul
```

> 两套采集器给出的数字不完全可比，切换采集器时应重新评估阈值，不宜直接沿用旧值。

**速记**：Istanbul 采集器插桩计数，精度高、开销大，忽略注释自成一套。



#### 安装与启用

**启用覆盖率**：是安装对应采集器包并通过配置或命令行打开覆盖率输出，二者缺一不可。

- 安装：V8 方案安装 @vitest/coverage-v8，Istanbul 方案安装 @vitest/coverage-istanbul，二者按需选一。
- 命令行启用：执行 npx vitest run --coverage，一次性运行并产出覆盖率。
- 配置启用：在配置中打开 enabled 开关，使覆盖率随每次运行产出。
- 指定采集器：通过 provider 键在 v8 与 istanbul 之间切换，未安装对应包会直接报错。
- 常用选项：可通过命令行覆盖 reporter、reportsDirectory、thresholds 等键。

```json
{
  "scripts": {
    "test": "vitest run",
    "coverage": "vitest run --coverage"
  }
}
```

```bash
npx vitest run --coverage --coverage.reporter=html --coverage.provider=istanbul
```

> 覆盖率默认不产生输出，必须显式启用；把覆盖率命令写进脚本可避免每次手敲长参数。

> [!NOTE]
> **提醒内容**：采集器是独立安装的包，只写配置不装包会在启用覆盖率时直接报模块找不到。

**速记**：先装采集器包，再用 --coverage 或 enabled 开关启用，provider 决定用哪套。



### 阈值配置与忽略

**覆盖率阈值**：是允许的最低覆盖率数值，运行结果低于阈值时命令以非零状态码退出，用于把覆盖率变成可执行的质量门禁。

本模块讲清阈值的写法、按目录细化阈值的方式与忽略规则的边界。

#### coverage.thresholds 配置

**coverage.thresholds**：是声明四项覆盖率下限的配置对象，键为 lines、functions、branches、statements，值为 0 到 100 的数字。

- 全局阈值：四项同时配置时任意一项低于对应值即失败，只配置部分键时其余项不校验。
- 每文件校验：打开 perFile 后逐文件比对阈值，避免少数文件的高覆盖掩盖大量低覆盖文件。
- 失败语义：阈值不达标时进程以非零状态码退出，可直接作为流水线的质量门禁。
- 渐进设置：存量项目先设为当前实际值，再随迭代逐步上调，避免一次性卡死提交。

```json
{
  "coverage": {
    "thresholds": {
      "lines": 85,
      "functions": 85,
      "branches": 75,
      "statements": 85,
      "perFile": true
    }
  }
}
```

> perFile 是阈值能否真正起作用的关键开关，不开它时个别文件可以低到零而不触发失败。

**速记**：阈值按四项指标分别设置，开启 perFile 才能逐文件把关。



#### 按目录设置阈值

**按目录设置阈值**：是在 thresholds 下以路径 glob 为键、以指标对象为值，为不同目录声明不同标准。

- 键为 glob：如 src/utils/** 匹配该目录下的全部文件，按最长匹配优先适用。
- 值为对象：同一键下可只声明部分指标，其余指标沿用全局值或不校验。
- 分层依据：核心工具与状态模块要求高覆盖，遗留适配层可暂时放宽。
- 维护成本：目录结构调整后 glob 会失配，需随目录迁移同步更新配置。

```json
{
  "coverage": {
    "thresholds": {
      "src/utils/**": { "lines": 95, "branches": 90 },
      "src/api/**": { "lines": 80, "branches": 70 },
      "src/legacy/**": { "lines": 0 }
    }
  }
}
```

> 给遗留目录显式写 0 比直接排除它更诚实：数字仍在报告里，技术债可见而不被隐藏。

**速记**：目录级阈值用 glob 作键、指标对象作值，核心模块严、遗留模块宽。



#### 忽略文件与忽略注释

**忽略文件**：是通过 include 与 exclude 决定哪些文件进入统计。**忽略注释**：是在源码中标记不需要统计的具体代码块。

- include 与 exclude：用 glob 声明统计范围，exclude 会覆盖默认排除项，需把测试文件与配置文件写回。
- 文件级忽略：在文件首部加 istanbul ignore file 注释，整个文件不进入统计。
- 代码块忽略：用 v8 ignore next、v8 ignore start 与 v8 ignore stop 标记，或对应的 istanbul 写法。
- 使用纪律：只忽略确实无法测试的代码，如环境探针与第三方适配壳，不用于掩盖未写的测试。

```js
// src/utils/browserSupport.js
/* v8 ignore next 3 */
export function detectLegacyEngine() {
  // 依赖特定浏览器行为，测试环境无法复现
}
```

```json
{
  "coverage": {
    "include": ["src/**/*.{js,vue}"],
    "exclude": ["**/*.test.js", "src/main.js", "src/**/*.d.ts"]
  }
}
```

> [!CAUTION]
> **注意内容**：自定义 exclude 会替换默认排除列表，漏写测试文件会让测试代码本身进入覆盖率统计。

**速记**：范围用 include 与 exclude 划定，个别代码用忽略注释排除，不滥用。



### 报告格式与查看

**覆盖率报告**：是把统计结果按指定格式输出的产物，同一份数据可同时输出多种格式以适配终端阅读与平台上传。

本模块讲清格式选择、查看方式与流水线衔接。

#### reporter 报告格式

**reporter**：是声明输出何种报告格式的配置项，值为格式名或格式名数组，一次运行可同时产出多种格式。

- text：在终端打印逐文件明细，适合本地开发时快速查看。
- text-summary：只在终端打印汇总数字，适合日志中保留一行结论。
- html：产出可交互的网页报告，支持按目录下钻与查看未覆盖行。
- lcov：产出 lcov.info 标准文件，用于上传到覆盖率平台或编辑器插件。
- json 与 json-summary：产出机器可读的汇总数据，便于脚本二次处理。

```json
{
  "coverage": {
    "reporter": ["text", "html", "lcov"],
    "reportsDirectory": "./coverage"
  }
}
```

> 默认格式已包含终端明细与网页报告，需要对接外部平台时再追加 lcov 即可。

**速记**：reporter 决定输出格式，text 看终端、html 看细节、lcov 供上传。



#### 报告输出目录与查看方式

**报告输出目录**：是覆盖率产物落盘的位置，由 reportsDirectory 指定，默认是项目根下的 coverage 目录。

- 目录约定：默认目录名为 coverage，通常写入版本控制忽略清单，不随代码提交。
- 清理时机：每次运行覆盖同名文件，历史产物不会自动清理，必要时手工删除后重建。
- 网页查看：用系统命令打开报告目录下的入口页面即可浏览。
- 报告定位：页面中以颜色标注未覆盖行，点击文件可直接定位到源码对应行。

```bash
npx vitest run --coverage
open coverage/index.html
# Linux 环境改用 xdg-open coverage/index.html
```

> 报告产物属于构建输出而非源码，写入忽略清单可避免把成百上千个页面文件提交进仓库。

**速记**：报告默认落在 coverage 目录并加入忽略清单，用浏览器打开入口页面查看。



#### 与持续集成的衔接

**持续集成中的覆盖率**：是在流水线中以非交互方式运行覆盖率命令，把产物归档并依赖阈值判定构建结果。

- 运行命令：使用带 --coverage 的一次性运行命令，保证进程结束即产出结果。
- 门禁判定：阈值不达标时进程退出码非零，流水线随即失败，无需额外脚本判断。
- 产物归档：把 coverage 目录作为构建产物保留，供评审时下载查看。
- 平台上传：使用 lcov 格式上传到覆盖率平台，观察趋势而非只看单次数字。
- 分工提示：流水线的分片、缓存与并行策略详见本主题第 15 篇 测试与持续集成。

```bash
npx vitest run --coverage --coverage.reporter=lcov --coverage.reporter=text-summary
# 退出码非零即表示存在指标低于阈值
```

> [!IMPORTANT]
> **重要内容**：覆盖率门禁必须配合阈值配置才有意义，否则流水线无论覆盖多少都会显示通过。

**速记**：流水线跑覆盖率命令，用退出码做门禁，归档产物并上传趋势平台。



### 覆盖率的使用边界

**使用边界**：是覆盖率能够回答与不能回答的问题范围。越过边界把它当成质量总评，就会误导投入方向。

本模块给出判断标准与排查方法。

#### 覆盖率不能证明什么

- 不证明断言有效：只有执行没有断言的用例同样计入覆盖，代码跑了不等于结果被校验。
- 不证明逻辑正确：被覆盖的分支可能返回错误结果，覆盖率对此完全无感。
- 不证明边界完整：覆盖率只统计被写下的分支，缺失的校验与遗漏的异常路径不在统计范围内。
- 不证明集成可用：单元层面的覆盖无法反映模块之间的真实协作与运行环境差异。
- 不证明需求实现：代码被执行与被需求覆盖是两件事，后者需要用例设计来保证。

```bash
# 反例：只有执行、没有断言，覆盖率仍然上升
# it("应当能调用格式化函数", () => {
#   formatDate(new Date())   // 无断言，覆盖率照样记满
# })
```

> 覆盖率是发现「哪些代码从来没被跑过」的探照灯，不是衡量「测试写得好不好」的标尺。

> [!WARNING]
> **警告内容**：把覆盖率设成唯一考核指标，会诱导写出大量无断言的空用例，测试数量上升而质量下降。

**速记**：覆盖率只说明代码被执行过，不说明断言有效与逻辑正确。



#### 合理的使用方式

- 看趋势不看单点：关注覆盖率随时间的变化方向，避免为某个百分点的波动反复返工。
- 看未覆盖行不看总分：从报告中优先处理零覆盖与关键分支未覆盖的部分。
- 分层设阈值：核心模块从严、边缘模块从宽，让标准与风险等级匹配。
- 结合变更范围：评审时关注本次改动是否带来新的未覆盖代码，比追求全局数字更有效。
- 与用例设计互补：覆盖率用来发现遗漏，边界与异常的完整性仍靠用例设计保证。

```json
{
  "coverage": {
    "thresholds": {
      "src/core/**": { "lines": 95, "branches": 90 },
      "src/ui/**": { "lines": 75, "branches": 65 }
    }
  }
}
```

> 合理的目标是「关键路径无遗漏」，而不是「总分尽可能高」；两者在投入产出上差别很大。

**速记**：看趋势、看未覆盖行、分层设阈值，覆盖率与用例设计互补。



#### 常见问题排查

- 启动报错找不到采集器：确认已安装与 provider 对应的采集器包，且包与运行器版本匹配。
- 文件没有出现在报告里：检查是否未被任何测试导入，以及 include 与 exclude 是否覆盖了该路径。
- 覆盖率异常偏高：确认采集器与源码映射是否匹配，V8 方案在多层转译下可能出现偏差。
- 全局汇总达标却判定失败：开启 perFile 后逐文件比对，失败往往来自某个具体的低覆盖文件。
- 汇总数字远超阈值仍判定失败：检查是否按目录配置了更严格的 glob 阈值，局部标准会高于全局。
- 报告页面无法打开：确认 reportsDirectory 与实际落盘位置一致，并已启用 html 格式。
- 产出目录被提交：把 coverage 目录加入版本控制忽略清单，避免构建产物进入仓库。
