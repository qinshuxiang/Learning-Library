## 异步测试与定时器控制

### 异步测试的写法

**异步测试的写法** 解决一个核心问题：让运行器知道用例什么时候才算结束。同步用例返回即结束，异步用例必须显式地把等待过程交回给运行器，否则断言会在数据到达之前执行。

#### 异步测试与同步测试的差别

**异步测试**：是被测代码的完成时机不在当前执行栈内的用例，运行器必须等待一个承诺或回调，才能判断它是否通过。

- 同步用例：函数返回即结束，断言在返回之前已经执行完毕。
- 异步用例：函数返回时数据可能还在路上，运行器需要额外的结束信号。
- 反例：在被测函数返回的承诺上忘记等待，断言读到的是 undefined。
- 后果：断言失败会被吞掉，用例以通过结束，失败推迟到线上才暴露。

```js
// 反例：断言先于数据到达执行
it("在接口正常时应返回用户档案", () => {
  const profile = fetchUserProfile(7); // 返回的是 Promise
  expect(profile.displayName).toBe("Grace Hopper"); // undefined
  // AssertionError: expected undefined to be 'Grace Hopper'
});
```

> 运行器无法凭代码结构猜出「应该等什么」，它只认两件事：测试函数返回的承诺，或测试函数显式交出的完成信号。

**速记**：异步测试的关键是让运行器知道何时结束，漏掉这一步就会得到没有意义的通过。



#### async 与 await 写法

**async 函数**：是返回承诺的函数，测试函数写成 async 后，Vitest 会等到该承诺敲定才判定用例结果，承诺被拒绝则用例失败。

- 写法：测试函数加 async 关键字，需要等待的调用前加 await。
- 错误传播：await 到的拒绝会直接抛出，用例失败并保留原始调用栈。
- 顺序：多个 await 按书写顺序串行执行，避免并发带来的不确定。
- 返回值：测试函数返回的承诺一旦拒绝，Vitest 直接把拒绝原因记为失败原因。

```js
it("在两次异步加载后应合并出完整资料", async () => {
  const profile = await fetchUserProfile(7);
  const team = await fetchUserTeam(profile.teamId);

  expect(profile.displayName).toBe("Grace Hopper");
  expect(team.name).toBe("编译器小组");
});
```

> async 与 await 是默认推荐写法，它与同步代码读起来几乎一致，错误通过 await 自然向上传播；回调风格与裸承诺写法只在特定场景使用。

**速记**：测试函数写成 async，需要等待的调用加 await，Vitest 等承诺敲定再判定结果。



#### 断言计数与未等待的断言

**未等待的断言**：是写在承诺上却没有 await 的断言，Vitest 会在用例结束时检测到它并把用例判为失败。

- expect.hasAssertions()：要求本条用例至少执行过一次断言，防止回调里的断言根本没跑到。
- expect.assertions(n)：要求断言恰好执行 n 次，适合断言落在循环或分支中的场景。
- 配置开关：test.expect.requireAssertions 为真时，全部用例都必须至少有一次断言。
- 断言计数不是必选项，只在断言位于回调、循环、条件分支中时才需要。

```js
it("在资料项非空时每项都应有标识", async () => {
  expect.assertions(2);

  const profile = await fetchUserProfile(7);
  expect(profile.id).toBe(7);
  expect(profile.displayName).toBeDefined();
});
```

```js
// vitest.config.js
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    expect: {
      requireAssertions: true,
    },
  },
});
```

> [!WARNING]
> **警告内容**：忘记 await 的断言不会立刻报错，用例会以通过结束，覆盖率与成功数也照常统计；这类假通过只能靠断言计数与代码评审发现。

**速记**：断言落在回调或分支中时用断言计数兜底，未等待的断言会被运行器判为失败。



### 返回 Promise 与回调风格

**返回 Promise 与回调风格** 处理两种非 async 的写法：直接返回承诺，以及把旧式回调适配成承诺。两者都要给运行器一个明确的结束信号。

#### 直接返回 Promise 的写法

**返回承诺的写法**：是测试函数不写 async，而是把承诺作为返回值交回给运行器的做法，效果与 await 后断言等价。

- 写法：测试函数返回 expect 链或业务调用产生的承诺。
- 等价性：运行器等待该承诺敲定，拒绝即失败。
- 适用：单条断言链、无需中间变量的场景。
- 注意：返回语句必须真的返回，写成语句块后忘记 return 会退化成同步用例。

```js
it("在用户存在时应解析出用户档案", () => {
  return expect(fetchUserProfile(7)).resolves.toMatchObject({ id: 7 });
});
```

> 返回承诺与 async 加 await 在行为上等价，选择哪种取决于可读性：链式断言适合返回写法，多步操作适合 async 加 await。

**速记**：测试函数返回的承诺被运行器等待，拒绝即失败，忘记 return 会退化成同步用例。



#### 回调风格与 Promise 包装

**回调风格适配**：是把接收回调的旧式 API 包进 Promise 的做法。Vitest 不支持 Jest 的 done 回调形式，测试函数接受一个 done 参数时会被当作普通同步函数执行。

- 包装方式：在 new Promise 的执行函数里调用旧式 API，成功时 resolve，失败时 reject。
- 结束信号：resolve 被调用后测试函数返回的承诺才敲定，运行器随之继续。
- 常见错误：调用 done 的旧写法在 Vitest 中没有任何等待效果，用例会提前结束。
- 现代替代：Node.js 的 fs/promises、fetch 等已原生支持承诺，可直接 await。

```js
// 旧式回调 API：把回调包进 Promise，由 resolve 结束等待
function loadThemeConfig(callback) {
  setTimeout(() => callback(null, { theme: "dark" }), 100);
}

it("在配置加载完成时应返回主题名", async () => {
  const config = await new Promise((resolve, reject) => {
    loadThemeConfig((error, value) => (error ? reject(error) : resolve(value)));
  });

  expect(config.theme).toBe("dark");
});
```

```js
// Vitest 不支持 done 回调：下面的写法不会等待，用例会提前结束
// it("在配置加载完成时应返回主题名", (done) => {
//   loadThemeConfig(() => done());
// });
```

> [!TIP]
> **建议内容**：遇到回调风格的老库，先在项目内包一层返回承诺的适配函数，测试与业务代码都直接 await 这层适配，避免每处用例重复写包装。

**速记**：旧式回调包进 Promise 再 await，Vitest 不支持 done 回调，写了也不会等待。



#### resolves 与 rejects 断言

**resolves 与 rejects**：是把承诺展开后再套用匹配器的断言修饰符，前者针对敲定值，后者针对拒绝原因，两者都必须被 await。

- resolves：断言承诺最终敲定出的值，后面接普通匹配器，如 toBe、toMatchObject。
- rejects：断言承诺被拒绝的原因，常配合 toThrow 检查错误信息。
- 必须等待：这两个修饰符返回承诺，漏掉 await 会被判定为未等待的断言。
- 适用：只需要断言结果、不需要中间变量的场景。

```js
it("在用户存在时应解析出用户档案", async () => {
  await expect(fetchUserProfile(7)).resolves.toMatchObject({
    displayName: "Grace Hopper",
  });
});

it("在用户不存在时应以用户不存在拒绝", async () => {
  await expect(fetchUserProfile(404)).rejects.toThrow("用户不存在");
});
```

> rejects 只能证明承诺被拒绝，无法证明拒绝得「正确」；断言错误类型与错误信息，才能避免任意异常都被当成预期失败。

**速记**：resolves 看敲定值、rejects 看拒绝原因，两个修饰符前面都要加 await。



### 超时设置与失败排查

**超时设置与失败排查** 处理最常见的一类异步失败：用例没有报断言错误，而是一直等到超时。理解超时的含义，才能区分「真的慢」与「永远等不到」。

#### 默认超时与自定义超时

**用例超时**：是运行器为单个用例设定的最长等待时间，超过该时间即判定失败并终止该用例。

- 默认值：单条用例 5 秒，由 testTimeout 控制；钩子默认 10 秒，由 hookTimeout 控制。
- 单例改写：把毫秒数作为 it 的第三个参数，或写进第二个选项对象的 timeout 字段。
- 文件级改写：调用 vi.setConfig({ testTimeout: 30000 })，只影响当前测试文件。
- 全局改写：在配置中设置 test.testTimeout，或在命令行加 --testTimeout 参数。
- 取舍：调大超时只是给慢操作让路，若承诺永远不会敲定，调多大都会失败。

```js
it("在导出全部订单时应写入同一个文件句柄", async () => {
  await exportAllOrders();
}, 30_000);

// 需要同时指定其他选项时，把超时写进选项对象
it("在跳过导出时不应产生文件", { skip: true, timeout: 30_000 }, async () => {
  await exportAllOrders();
});
```

```json
{
  "scripts": {
    "test": "vitest run",
    "test:watch": "vitest",
    "test:slow": "vitest run --testTimeout=30000"
  }
}
```

> 超时值应当反映「这条用例在最坏情况下需要多久」，而不是「调大以后终于不红了」；后者通常意味着存在未敲定的承诺。

**速记**：单例超时写在第三个参数或选项对象，全局超时归 testTimeout 与 --testTimeout，调大不能解决永远不敲定的承诺。



#### 挂起与未处理拒绝的排查

**挂起**：是用例等待的承诺既没有敲定也没有拒绝，运行器只能等到超时后终止它，报错信息只说明等待超时，不指出卡在哪里。

- 定位手段：在可疑的 await 前后各打一条日志，或用 --testTimeout 缩小等待区间。
- 常见成因：替身返回的承诺没有被敲定、事件监听器没有被触发、条件永远不会满足。
- 报错文本：超时失败会给出明确的等待时长与改写提示。
- 未处理拒绝：Vitest 默认把未处理的拒绝记为错误，可用 onUnhandledError 过滤，或用 dangerouslyIgnoreUnhandledErrors 关闭检查。

```text
FAIL  src/api/profile.test.js > 在接口返回较慢时应返回用户档案
Error: Test timed out in 5000ms.
If this is a long-running test, pass a timeout value as the last argument
or configure it globally with "testTimeout".
```

```js
// 反例：忘记 await，拒绝既没有被断言也没有被捕获
it("在接口异常时不应写入缓存", () => {
  expect(fetchUserProfile(500)).rejects.toThrow("请求失败");
  // 用例已结束，随后抛出的拒绝成为未处理拒绝
});
```

> [!IMPORTANT]
> **重要内容**：不要为了让套件变绿而关闭未处理拒绝检查；未处理拒绝通常意味着存在忘记 await 的调用，是异步代码里最容易漏掉的真实缺陷。

**速记**：超时只说明等待没有结果，先找没有敲定的承诺；未处理拒绝必须修掉，不要关掉检查。



### 假定时器

**假定时器** 把真实的计时器换成可手动推进的替身，让「等待两小时」的用例在毫秒内完成，同时消除时间带来的不确定性。

#### useFakeTimers 与 useRealTimers

**vi.useFakeTimers()**：是把全局计时器与日期替换为可控实现的 API，启用后所有定时调用都进入假定时器队列，直到调用 vi.useRealTimers() 恢复。

- 启用：在 beforeEach 中调用，保证每条用例都从干净的队列开始。
- 恢复：在 afterEach 中调用 vi.useRealTimers，恢复真实计时器并丢弃队列中已排队的定时器。
- 配套清理：同时清空替身与假定时器队列，避免状态跨用例残留。
- 注意：恢复之前排队的定时器不会补跑，需要补跑的用例必须显式推进。

```js
function scheduleReminder(callback, delayMs) {
  return setTimeout(callback, delayMs);
}

beforeEach(() => {
  vi.useFakeTimers();
});

afterEach(() => {
  vi.clearAllTimers();
  vi.useRealTimers();
});

it("在定时器推进两小时后应触发提醒", () => {
  const sendReminder = vi.fn();
  scheduleReminder(sendReminder, 1000 * 60 * 60 * 2);

  vi.advanceTimersByTime(1000 * 60 * 60 * 2);
  expect(sendReminder).toHaveBeenCalledTimes(1);
});
```

> 假定时器并不改变代码，只把「时间前进」这件事变成显式调用；因此启用之后，只有调用推进方法才会触发到期的回调。

**速记**：beforeEach 启用假定时器，afterEach 清空队列并恢复真实计时器，时间只随推进方法前进。



#### 假定时器覆盖的范围与配置

**覆盖范围**：指 vi.useFakeTimers 默认替换的全局 API 集合，默认包含 setTimeout、clearTimeout、setInterval、clearInterval、setImmediate、clearImmediate 与 Date。

- 默认不替换：process.nextTick 与 queueMicrotask 保持原生，需要时通过 toFake 显式加入。
- toFake：只替换列出的 API，用于避开某些库对原生实现的依赖。
- toNotFake：只保留列出的 API 为原生，与 toFake 互斥，不能同时指定。
- now：设定启用瞬间的系统时间，等价于随后调用 vi.setSystemTime。
- loopLimit：runAllTimers 系列遇到不会停止的定时器时的最大循环次数，默认 10000。

```js
vi.useFakeTimers({
  toFake: ["setTimeout", "clearTimeout", "setInterval", "clearInterval", "Date"],
  now: new Date("2026-09-01T00:00:00Z"),
});

console.log(new Date().toISOString()); // "2026-09-01T00:00:00.000Z"
console.log(vi.isFakeTimers()); // true
```

> [!CAUTION]
> **注意内容**：在 forks 进程池中运行且代码依赖 process.nextTick 时，把 nextTick 加入 toFake 可能让用例永久挂起，因为 Node.js 内部同样依赖它。

**速记**：默认替换六个定时器 API 与 Date，nextTick 与 queueMicrotask 需显式加入，toFake 与 toNotFake 互斥。



#### 典型使用场景

**典型场景**：是需要精确控制时间流逝的代码，包括防抖与节流、轮询与重试退避、心跳与定时刷新、缓存过期。

- 防抖与节流：验证在指定间隔内只触发一次，以及最后一次输入被采用。
- 轮询与退避：验证失败后按指数间隔重试，以及达到上限后停止。
- 心跳与刷新：验证按时触发的副作用次数，不需要真的等待。
- 缓存过期：配合 vi.setSystemTime 跳过过期时间，验证过期后的重新加载。

```js
function debounce(fn, delayMs) {
  let timerId;
  return (...args) => {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delayMs);
  };
}

it("在连续输入停止 300 毫秒后应只触发一次搜索", () => {
  const search = vi.fn();
  const debouncedSearch = debounce(search, 300);

  debouncedSearch("vit");
  debouncedSearch("vite");
  debouncedSearch("vitest");
  expect(search).not.toHaveBeenCalled();

  vi.advanceTimersByTime(299);
  expect(search).not.toHaveBeenCalled();

  vi.advanceTimersByTime(1);
  expect(search).toHaveBeenCalledTimes(1);
  expect(search).toHaveBeenCalledWith("vitest");
});
```

> 假定时器最适合验证「时间长度」这类断言：用例不再依赖真实等待，因此不会因为机器负载而偶发失败。

**速记**：防抖、轮询、心跳、缓存过期都靠假定时器验证，时间长度变成可以断言的量。



### 时间推进与微任务刷新

**时间推进与微任务刷新** 是假定时器的使用细节：推进方式决定哪些回调被触发，而回调内部还有异步操作时必须使用异步版本。

#### advanceTimersByTime 与 runAllTimers

**vi.advanceTimersByTime(ms)**：是把假时钟向前推进指定毫秒数并触发期间到期的回调的 API，ms 为推进的毫秒数，返回 vi 以便链式调用。

- advanceTimersToNextTimer()：只推进到下一个定时器到期，适合逐个验证间隔触发。
- runOnlyPendingTimers()：处理当前已排队的定时器，不处理执行期间新排出的定时器。
- runAllTimers()：反复触发直到队列为空，执行期间新排出的定时器同样会被触发。
- getTimerCount()：返回队列中尚未触发的定时器数量，可用于断言没有残留任务。
- 无限循环保护：runAllTimers 系列遇到不停重新排队的定时器，达到 loopLimit 后抛出错误。

```js
vi.advanceTimersByTime(1000);      // 触发这 1 秒内到期的回调
vi.advanceTimersToNextTimer();     // 只触发下一个到期的回调
vi.runOnlyPendingTimers();         // 处理当前排队中的回调
vi.runAllTimers();                 // 清空队列，含期间新排出的回调
console.log(vi.getTimerCount());   // 剩余待触发数量，例如 0
```

> runAllTimers 与 runOnlyPendingTimers 的差别在「执行期间新排出的定时器」：轮询类代码用后者可以避免无限推进。

**速记**：advanceTimersByTime 按毫秒推进，runOnlyPendingTimers 只管当前队列，runAllTimers 会清空队列。



#### 异步推进与微任务刷新

**异步推进**：是 vi.advanceTimersByTimeAsync(ms) 与 vi.runAllTimersAsync() 的统称，它们在触发回调后继续等待回调内部产生的承诺，从而把微任务队列一并排空。

- 问题来源：定时器回调里常有 await，同步推进只会触发回调，不会等回调里的承诺敲定。
- 同步后果：断言在回调真正完成之前执行，读到的是中间状态。
- 解决方式：使用 Async 版本并 await，时间推进与微任务刷新一次完成。
- 原生微任务：Promise.resolve 与 queueMicrotask 不在默认伪造范围内，普通的 await 依然可用。
- 等待轮询：启用假定时器后，vi.waitFor 会在每次检查之间自动推进时间，适合等待条件成立。

```js
function scheduleRefresh(loadProfile, renderProfile, delayMs) {
  setTimeout(async () => {
    const profile = await loadProfile(7);
    renderProfile(profile);
  }, delayMs);
}

it("在刷新定时器到期后应渲染用户档案", async () => {
  const loadProfile = vi.fn().mockResolvedValue({ id: 7, displayName: "Grace Hopper" });
  const renderProfile = vi.fn();

  scheduleRefresh(loadProfile, renderProfile, 500);
  await vi.advanceTimersByTimeAsync(500);

  expect(renderProfile).toHaveBeenCalledWith({ id: 7, displayName: "Grace Hopper" });
});
```

> [!NOTE]
> **提醒内容**：同步版本会触发回调但不会等待回调里的承诺，回调内部只要出现 await，就应改用对应的 Async 版本。

**速记**：回调里有 await 就必须用 Async 版本推进，同步推进只能触发回调本身。



#### 系统时间与清理

**系统时间控制**：是把 Date 与 performance 的读数固定到指定时刻的能力，由 vi.setSystemTime 提供，它只改变读数，不触发任何定时器。

- vi.setSystemTime(date)：接受字符串、数字或 Date，修改当前时间读数，不推进定时器队列。
- vi.getMockedSystemTime()：读取被伪造的当前时间，未启用假定时器时返回 null。
- vi.getRealSystemTime()：读取真实毫秒时间戳，用于计算用例自身的耗时。
- vi.clearAllTimers()：丢弃队列中全部未触发的定时器，不影响 Date 读数。
- vi.useRealTimers()：恢复全部原生实现，未触发的定时器一并丢弃。

```js
vi.useFakeTimers();
vi.setSystemTime(new Date("2026-09-01T00:00:00Z"));

console.log(new Date().toISOString()); // "2026-09-01T00:00:00.000Z"
console.log(vi.getMockedSystemTime().toISOString()); // "2026-09-01T00:00:00.000Z"

vi.clearAllTimers();
vi.useRealTimers();
console.log(vi.isFakeTimers()); // false
```

> 时间读数与定时器队列是两件独立的事：固定当前时间不会让到期的回调自动执行，反过来推进队列也不会改变当前时间的读数。

**速记**：setSystemTime 改读数不触发回调，getMockedSystemTime 读假时间，clearAllTimers 清队列，useRealTimers 全部恢复。
