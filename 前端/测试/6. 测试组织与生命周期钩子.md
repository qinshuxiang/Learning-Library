## 测试组织与生命周期钩子

### describe 与 it 的组织

测试文件的可读性由用例的命名与分组决定。本节说明 describe 与 it 的职责、等价写法与标题规范。

#### describe 的定义与嵌套

**describe(name, fn)**：是把一组相关用例聚合为测试套件的函数，name 是套件名，fn 是套件体，套件体内部可以继续声明用例或嵌套子套件。

- 作用：为一组用例提供公共标题与作用域，钩子与用例都能按套件分组。
- 嵌套：describe 可以嵌套，内层套件继承外层套件的名字与钩子。
- 执行时机：套件体在收集阶段同步执行，用于登记用例；用例体在运行阶段执行。

```js
import { describe, expect, it } from "vitest";
import { parsePort } from "@/utils/parsePort";

describe("parsePort", () => {
  describe("合法输入", () => {
    it("parsePort 在十进制字符串下应返回整数端口号", () => {
      expect(parsePort("8080")).toBe(8080);
    });
  });

  describe("非法输入", () => {
    it("parsePort 在非数字字符串下应抛出范围错误", () => {
      expect(() => parsePort("abc")).toThrow(RangeError);
    });
  });
});
```

> [!TIP]
> **建议内容**：套件嵌套控制在三层以内，过深的层级会让用例的完整标题冗长，反而降低可读性。

**速记**：describe 把相关用例聚合成套件，可嵌套，套件体在收集阶段执行。



#### it 与 test 的等价写法与标题规范

**it(name, fn, timeout)**：是声明单条测试用例的函数，name 是用例标题，fn 是用例体，timeout 是可选的超时毫秒数。**test** 是 it 的完全等价别名。

- 等价关系：it 与 test 指向同一实现，但同一文件应统一用其中一种。
- 标题句式：写成「某函数在某输入下应某结果」的中文陈述句，不用问句与缩写。
- 三段信息：标题含被测对象、输入条件与期望结果，失败输出即可自解释。
- 唯一性：筛选与报告按标题定位，同一套件内标题重复会导致难以分辨。
- 描述行为：标题描述行为而不是内部写法，重构实现时不需要改标题。

```js
import { describe, expect, it } from "vitest";
import { formatDate } from "@/utils/formatDate";

describe("formatDate", () => {
  it("formatDate 在合法日期下应输出短横线格式", () => {
    expect(formatDate(new Date("2026-09-13"))).toBe("2026-09-13");
  });

  it("formatDate 在无效日期下应抛出类型错误", () => {
    expect(() => formatDate(new Date("invalid"))).toThrow(TypeError);
  });
});
```

> 标题是给失败报告看的：半年后只看到标题与堆栈，也应能判断是哪条业务规则被破坏。

**速记**：it 与 test 等价，标题写成含对象、输入与期望结果的中文陈述句且套件内唯一。



### 生命周期钩子

钩子负责在用例前后准备与清理环境，是把重复代码从用例中抽出的官方手段。本节说明四个钩子的分工与作用域。

#### beforeEach 与 afterEach

**beforeEach(fn, timeout)**：是在当前作用域的每条用例执行前运行的函数，fn 是钩子体，timeout 是可选超时。**afterEach(fn, timeout)**：是在每条用例执行后运行的函数。

- beforeEach：准备每个用例都需要的新鲜数据，避免用例之间共享可变对象。
- afterEach：清理副作用，如恢复替身、销毁挂载的组件、关闭连接。
- 失败也执行：用例失败后 afterEach 仍会运行，适合做兜底清理。

```js
import { afterEach, beforeEach, describe, expect, it, vi } from "vitest";
import { createUserStore } from "@/stores/userStore";

describe("userStore", () => {
  let store;

  beforeEach(() => {
    store = createUserStore();
  });

  afterEach(() => {
    vi.restoreAllMocks();
  });

  it("userStore 在新增用户后应增加一条记录", () => {
    store.add({ id: 1, name: "Ada Lovelace" });
    expect(store.list()).toHaveLength(1);
  });
});
```

> [!WARNING]
> **警告内容**：在 beforeEach 之外创建共享对象而又不在 afterEach 中重置，用例会读到上一条用例留下的状态，失败原因极难定位。

**速记**：beforeEach 准备新鲜状态，afterEach 清理副作用，用例失败后后者仍执行。



#### beforeAll 与 afterAll

**beforeAll(fn, timeout)**：是在当前作用域的用例开始前只运行一次的钩子。**afterAll(fn, timeout)**：是在该作用域全部用例结束后只运行一次的钩子。

- beforeAll：用于昂贵且只读的准备，如启动服务、建立连接、加载固定数据集。
- afterAll：用于释放上述资源，如关闭连接、停止服务。
- 只运行一次：同一作用域内无论有多少用例，两者各执行一次。
- 共享风险：在 beforeAll 中创建的可变对象被所有用例共享，修改会互相影响。

```js
import { afterAll, beforeAll, expect, it } from "vitest";
import { startTestDatabase } from "./helpers/testDatabase";

let database;

beforeAll(async () => {
  database = await startTestDatabase();
});

afterAll(async () => {
  await database.close();
});

it("testDatabase 在启动后应能查询到空表", async () => {
  expect(await database.count("users")).toBe(0);
});
```

> 判定标准很简单：每个用例都要重新准备就用 beforeEach，整套只准备一次才用 beforeAll。

**速记**：beforeAll 与 afterAll 各只执行一次，用于昂贵资源与只读准备。



#### 钩子的参数与超时

**钩子的参数**：四个钩子都接收钩子体与可选超时两个参数，钩子体可以是同步函数，也可以是返回 Promise 的异步函数。

- 同步与异步：钩子返回 Promise 时运行器会等待其完成，无需额外写法。
- 超时：第二个参数指定该钩子的超时毫秒数，默认取配置中的 hookTimeout。
- 错误传播：钩子抛错会让其作用域内的用例失败，beforeAll 抛错则整套跳过。
- 上下文：钩子不接收用例参数，需要共享数据时用外层变量传递。

```js
import { beforeEach, expect, it } from "vitest";

let store;

beforeEach(async () => {
  store = await createUserStore();
}, 20000); // 该钩子单独指定 20 秒超时

it("userStore 在初始化后应为空", () => {
  expect(store.list()).toHaveLength(0);
});
```

> 钩子超时与用例超时是两套配置：调大 testTimeout 不会放宽钩子的等待时间。

**速记**：钩子接收函数与超时两个参数，返回 Promise 即被等待，抛错会连累用例。



#### 钩子的作用域与嵌套规则

**钩子的作用域**：由声明位置决定，写在 describe 内部的钩子只作用于该套件及其子套件，写在外层的钩子对内层全部生效。

- 就近生效：内层套件的用例同时受外层与内层钩子影响。
- 执行次数：内层 beforeEach 只在内层用例前后运行，不对外层用例运行。
- 顶层钩子：写在文件顶层的钩子作用于该文件的所有用例。
- 顺序：外层钩子先于内层钩子的对应阶段运行。

> 作用域由「写在哪个 describe 里」而非「写在哪个文件里」决定，把钩子放在正确的层级是不出错的关键。

**速记**：钩子按声明位置限定作用域，外层先于内层，子套件继承父套件的钩子。



### 钩子执行顺序

钩子的相对顺序决定了准备与清理是否配对。本节说明同级与嵌套场景下的固定顺序，并给出可复现的验证方式。

#### 同级钩子的先后

**同级钩子顺序**：指同一作用域内多个同类钩子按声明顺序执行，after 类钩子同样按声明顺序而非逆序执行。

- beforeEach：多个按声明顺序依次执行。
- afterEach：多个同样按声明顺序执行，不自动反转。
- beforeAll 与 afterAll：各自独立，与其他阶段互不交叉。
- 与用例的关系：beforeEach 全部完成后才进入用例体，用例体结束后才开始 afterEach。

```js
import { afterEach, beforeEach, it } from "vitest";

beforeEach(() => console.log("beforeEach 1"));
beforeEach(() => console.log("beforeEach 2"));
afterEach(() => console.log("afterEach 1"));
afterEach(() => console.log("afterEach 2"));

it("日志用例在两条钩子下应输出四条记录", () => {
  console.log("用例体");
});
```

```bash
npx vitest run order.test.js
# beforeEach 1
# beforeEach 2
# 用例体
# afterEach 1
# afterEach 2
```

> afterEach 不反转顺序这一点与部分测试框架不同，涉及资源释放顺序时应显式安排声明次序。

**速记**：同级钩子一律按声明顺序执行，afterEach 不自动逆序。



#### 嵌套套件下的顺序

**嵌套套件下的顺序**：指钩子按由外到内的层级进入、再由内到外退出的顺序执行。

- 进入阶段：外层 beforeAll、外层 beforeEach、内层 beforeEach 依次运行。
- 用例体：在内层 beforeEach 结束后执行。
- 退出阶段：内层 afterEach、外层 afterEach、外层 afterAll 依次运行。
- beforeAll 与 afterAll：外层的 beforeAll 最先，外层的 afterAll 最后。

```js
import { afterAll, afterEach, beforeAll, beforeEach, describe, it } from "vitest";

beforeAll(() => console.log("outer beforeAll"));
beforeEach(() => console.log("outer beforeEach"));
afterEach(() => console.log("outer afterEach"));
afterAll(() => console.log("outer afterAll"));

describe("内层套件", () => {
  beforeEach(() => console.log("inner beforeEach"));
  afterEach(() => console.log("inner afterEach"));

  it("内层用例应输出完整的进出顺序", () => {
    console.log("用例体");
  });
});
```

> 记法：准备阶段由外向内，清理阶段由内向外，beforeAll 与 afterAll 分别占据两端。

**速记**：钩子进入由外到内，退出由内到外，beforeAll 最先、afterAll 最后。



#### 执行顺序示例复盘

**执行顺序复盘**：指把上述规则套进一个真实用例，逐行核对钩子的实际输出与预期是否一致。

- 单用例场景：beforeAll 一次、beforeEach 一次、afterEach 一次、afterAll 一次。
- 多用例场景：beforeAll 与 afterAll 仍各一次，beforeEach 与 afterEach 按用例数重复。
- 核对方法：在钩子中把事件名推入数组，测试结束后断言该数组的内容。
- 排查价值：顺序不符时，多半是钩子写在了错误的层级或异步没有被等待。

```js
import { afterAll, afterEach, beforeAll, beforeEach, describe, expect, it } from "vitest";

const events = [];

beforeAll(() => events.push("beforeAll"));
beforeEach(() => events.push("beforeEach"));
afterEach(() => events.push("afterEach"));
afterAll(() => events.push("afterAll"));

describe("顺序核对", () => {
  it("顺序核对 在单个用例下应符合固定顺序", () => {
    events.push("用例体");
    expect(events).toEqual(["beforeAll", "beforeEach", "用例体"]);
  });
});
```

> 报告中的用例标题带套件前缀，这也是标题需要保持唯一的原因之一。

**速记**：beforeAll 与 afterAll 各一次，beforeEach 与 afterEach 按用例数重复。



#### 顺序错乱的常见成因

**顺序错乱**：指实际执行顺序与预期不符，通常由声明位置或异步写法引起。

- 层级错放：把需要每用例重置的钩子写成 beforeAll，导致只准备一次。
- 忘记等待：钩子体返回 Promise 却未写成 async，运行器不会等待。
- 异步未收敛：钩子中启动异步任务却不返回它，资源尚未就绪用例已开始。
- 顶层遗漏：把钩子写在 describe 之外，作用范围扩大到整个文件。

```js
import { beforeAll } from "vitest";

let store;

// 错误：异步未返回，钩子立即结束，store 可能仍是 undefined
beforeAll(() => {
  createUserStore().then((value) => {
    store = value;
  });
});

// 正确：写成 async 并 await，运行器会等待准备完成
beforeAll(async () => {
  store = await createUserStore();
});
```

> 钩子中的异步逻辑必须可等待：返回 Promise 或使用 async 与 await，二者选其一。

**速记**：顺序错乱多源于层级放错与异步未等待，钩子中的异步必须可被等待。



### 跳过与仅运行与标记

开发过程中常需要只跑一条用例或暂时跳过某条，运行器为此提供了标记方法。本节说明各类标记的用途与风险。

#### skip 与 only

**it.skip(name, fn)**：声明一条被跳过的用例，用例体不执行，报告中标记为跳过。**it.only(name, fn)**：只运行被标记的用例，同级其他用例全部跳过。

- skip：保留代码但暂不执行，适合已知失败或依赖未就绪的功能。
- only：临时聚焦，运行时间与噪声都降到最低。
- 套件级：describe.skip 跳过整组，describe.only 只跑该组。
- 组合：describe 与 it 上的标记可以叠加，内层标记决定最终结果。

```js
import { describe, expect, it } from "vitest";

describe("parsePort", () => {
  it.skip("parsePort 在八进制字符串下应返回整数", () => {
    expect(parsePort("0o755")).toBe(493);
  });

  it.only("parsePort 在十进制字符串下应返回整数", () => {
    expect(parsePort("8080")).toBe(8080);
  });
});
```

> [!WARNING]
> **警告内容**：it.only 会让同文件的其他用例全部跳过，提交前务必删除；可用静态检查规则禁止 only 进入主干代码。

**速记**：skip 保留代码不执行，only 只跑标记项，only 留在提交里会漏掉大量用例。



#### todo 与 fails

**it.todo(name)**：登记一条尚未实现的用例，报告中标记为待办且不计入失败。**it.fails(name, fn, timeout)**：标记一条预期失败的用例，实际失败时算通过，意外通过时算失败。

- todo：占位用，写明标题即可，不提供用例体。
- fails：用于记录已知缺陷，缺陷修复后会立即报错提醒删除标记。
- 报告差异：todo 与 fails 在统计中单独计数，不与正常通过混淆。
- 组合：describe.todo(name) 可整组登记待办。

```js
import { expect, it } from "vitest";

it.todo("parsePort 在带空格字符串下应忽略首尾空白");

it.fails("parsePort 在十六进制字符串下应返回整数", () => {
  expect(parsePort("0xFF")).toBe(255); // 已知缺陷：当前实现不支持十六进制
});
```

> fails 是缺陷记录而不是缺陷豁免：它保证已知问题不会被遗忘，而不是让问题从报告中消失。

**速记**：todo 登记未实现用例，fails 标记预期失败，缺陷修复后标记会转为失败。



#### 条件跳过与条件运行

**条件跳过**：指按运行时条件决定是否执行用例，Vitest 提供 it.skipIf(condition) 与 it.runIf(condition) 两种工厂方法。

- skipIf：条件为真时跳过，适合某环境下不可用的用例。
- runIf：条件为真时运行，等价于条件取反的 skipIf。
- 典型场景：仅在浏览器环境运行、仅在 CI 运行、依赖特定平台运行。
- 判定时机：条件在收集阶段求值，因此不能用用例内部产生的状态。

```js
import { expect, it } from "vitest";

const isCI = Boolean(process.env.CI);

it.skipIf(!isCI)("buildReport 在 CI 环境下应生成报告文件", async () => {
  expect(await buildReport()).toHaveProperty("path");
});

it.runIf(process.platform === "darwin")("readFile 在 macOS 下应返回换行符", () => {
  expect(readFile("./fixtures/line.txt")).toContain("\n");
});
```

> 条件跳过只是让用例不执行，报告中仍会显示被跳过，因此不会悄悄消失。

**速记**：skipIf 在条件为真时跳过，runIf 在条件为真时运行，条件在收集阶段求值。



### 并发与顺序依赖

运行器在文件之间并行、在用例之间默认串行。本节说明并发能力的开启方式与共享状态的代价。

#### 顺序执行与并发执行

**顺序执行**：是同一测试文件内用例按声明顺序逐条运行的默认形态。**并发执行**：指多条用例同时启动、互不等待的执行形态。

- 文件级并行：不同测试文件默认由多个工作线程并行执行。
- 用例级串行：同一文件内的用例默认串行，避免共享状态相互干扰。
- 用例级并发：需显式开启，用 it.concurrent 或 describe.concurrent。
- 并发上限：由 maxConcurrency 控制，默认 5。

> 文件之间并行是无配置的默认行为，正因如此，不同文件不应共享可变的外部资源。

**速记**：文件默认并行，文件内用例默认串行，用例并发需要显式开启。



#### test.concurrent 与 test.sequential

**it.concurrent(name, fn, timeout)**：把单条用例标记为并发执行。**it.sequential(name, fn, timeout)**：在并发套件中把单条用例标记为串行执行。

- concurrent：必须用在异步用例上，同步用例并发没有意义。
- describe.concurrent：让套件内全部用例并发执行。
- sequential：用于并发套件中需要独占资源的个别用例。
- 交互影响：并发用例之间不保证顺序，beforeEach 与 afterEach 仍各自运行。

```js
import { describe, expect, it } from "vitest";

describe.concurrent("远程配置加载", () => {
  it("loadConfig 在区域 A 下应返回区域标识", async () => {
    expect(await loadConfig("A")).toHaveProperty("region", "A");
  });

  it("loadConfig 在区域 B 下应返回区域标识", async () => {
    expect(await loadConfig("B")).toHaveProperty("region", "B");
  });

  it.sequential("loadConfig 在写入缓存后应立即可读", async () => {
    await loadConfig("C");
    expect(await readCache("C")).toBeDefined();
  });
});
```

> 并发只减少等待时间，不改变断言语义；把串行依赖的用例标成并发只会带来随机失败。

**速记**：concurrent 标记并发，sequential 在并发套件中退回串行。



#### 用例之间的状态隔离

**状态隔离**：指每条用例只依赖自己准备的状态，不依赖其他用例的执行结果或残留。

- 模块级变量：顶层 let 变量会被同文件用例共享，必须在 beforeEach 中重置。
- 全局对象：修改 globalThis、document 等对象后应在 afterEach 中还原。
- 替身与定时器：替身与假定时器必须恢复，否则影响后续用例（详见本主题第 7 篇 测试替身：mock、stub 与 spy）。
- 外部资源：数据库、缓存等应每个用例使用独立命名空间或回滚事务。

```js
import { afterEach, beforeEach, expect, it } from "vitest";
import { createUserStore } from "@/stores/userStore";

let store;

beforeEach(() => {
  store = createUserStore();   // 每条用例拿到全新实例
});

afterEach(() => {
  store = undefined;           // 显式清空，避免下一条用例误用
});

it("userStore 在新增用户后应只保留一条记录", () => {
  store.add({ id: 1, name: "Grace Hopper" });
  expect(store.list()).toHaveLength(1);
});
```

> [!CAUTION]
> **注意内容**：并发用例共享模块级状态时不会互相等待，写入顺序不确定，会出现只在高负载下复现的随机失败。

**速记**：状态隔离要求每条用例自备数据并在清理钩子中还原全局改动。



#### 顺序依赖的风险

**顺序依赖**：指用例的通过与否取决于其他用例是否先执行，这类用例单独运行会失败。

- 表现：全量运行通过，单独运行或调整顺序后失败。
- 成因：共享状态未重置、依赖上一条用例写库、依赖全局初始化顺序。
- 代价：失败原因指向无关用例，重跑与筛选都失去可信度。
- 排查：用 -t 单独运行可疑用例，能复现失败即说明存在顺序依赖。
- 修复：把前置数据移入 beforeEach，或把共享准备移入 beforeAll 并保持只读。

> 顺序依赖是测试套件最隐蔽的腐化方式：它不会整片失败，只会让失败变得无法解释。

**速记**：顺序依赖指用例依赖其他用例的执行结果，单独运行即可复现并据此修复。
