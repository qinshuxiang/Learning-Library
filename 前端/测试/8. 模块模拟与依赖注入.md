## 模块模拟与依赖注入

### 模块模拟的时机与边界

**模块模拟与依赖注入** 模块处理替身之外的两件事：替换的落点选在哪里，以及如何改造代码让替换不再必要。理解这两点，才能把测试从「能跑」推进到「值得维护」。

#### 模块模拟与函数替身的选择

**选择依据**：是看被替换的依赖是否已被导入语句写死在模块顶部，写得越死，替换的位置就越靠外。

- 函数替身：依赖能从函数参数或对象属性上拿到，用 vi.fn 或 vi.spyOn 替换，影响范围最小。
- 模块模拟：依赖在被测模块顶部以 import 引入且没有出口可注入，只能用 vi.mock 整块替换。
- 依赖注入：模块允许改造时，把依赖外移，测试不再需要了解模块内部从哪里取依赖。
- 优先顺序：先考虑注入，其次侦测，最后才整模块模拟。
- 判据：替换位置越靠内，用例越快、越稳；替换位置越靠外，用例越接近真实集成。

```js
// 难以注入：依赖写死在模块顶部
import { fetchUserProfile } from "./api/profile";

export async function greetUser(userId) {
  const profile = await fetchUserProfile(userId);
  return `你好，${profile.displayName}`;
}
```

```js
// 容易注入：协作函数由调用方传入
export async function greetUser(userId, loadProfile) {
  const profile = await loadProfile(userId);
  return `你好，${profile.displayName}`;
}

const greet = await greetUser(7, async () => ({ displayName: "Grace Hopper" }));
console.log(greet); // "你好，Grace Hopper"
```

> 两种写法在运行时的行为相同，差别只在装配权归谁：写死在内部由模块决定，注入后由调用方决定，而测试就是调用方。

**速记**：依赖能注入就注入，注入不了用侦测，最后才整模块模拟。



#### 模拟的边界与副作用

**模拟的边界**：是 vi.mock 生效的范围与其留下的状态，范围内所有导入都会被换掉，范围内的缓存会在用例之间延续。

- 作用范围：同一测试文件内所有导入该路径的模块，替换是文件级而不是用例级。
- 结果缓存：工厂函数只求值一次，后续用例复用同一份替身对象与同一份调用记录。
- 提升：调用被提到 import 之前，因此工厂内不能读取文件顶部定义的变量。
- 不覆盖的部分：setup 文件中已导入的模块不受影响，需要时改用 vi.doMock 或先调用 vi.resetModules。
- 副作用：模块顶层的初始化代码在导入时执行一次，替换之后原本的初始化不再运行。

```js
// 反例：工厂引用了外部变量，提升后变量仍处于暂时性死区
const fakeProfile = { id: 7, displayName: "Grace Hopper" };
vi.mock("../src/api/profile", () => ({ fetchUserProfile: () => fakeProfile }));
// ReferenceError: Cannot access 'fakeProfile' before initialization
```

```js
// 正解：用 vi.hoisted 把变量提到 import 之前
const fakeProfile = vi.hoisted(() => ({ id: 7, displayName: "Grace Hopper" }));

vi.mock("../src/api/profile", () => ({
  fetchUserProfile: vi.fn().mockResolvedValue(fakeProfile),
}));
```

> [!WARNING]
> **警告内容**：vi.mock 是文件级替换，写在某条用例内部的调用同样会在文件加载时执行完毕，以为它只对该用例生效会让后续用例读到被替换的模块。

**速记**：vi.mock 作用于整个文件并缓存工厂结果，工厂内引用外部变量必须走 vi.hoisted。



### 虚拟模块与路径别名

**虚拟模块与路径别名** 决定模块能否被解析到：别名解决路径太长，虚拟模块解决模块本不存在，两者都直接影响 vi.mock 能否命中目标。

#### 路径别名与模块解析

**路径别名**：是 resolve.alias 配置的短路径到真实目录或文件的映射，用来让导入语句摆脱层层相对路径。

- 配置位置：vite.config 或 vitest.config 的顶层 resolve.alias，不写在 test 属性内部。
- vi.mock 的 path 同样经过别名解析，可以直接写 @/api/profile。
- 一致性：测试与业务共用同一份别名配置，避免出现两套路径规则。
- 排查：替身未生效时先核对 import 语句与 vi.mock 的路径写法是否一致，再检查别名是否只在一边生效。

```js
// vitest.config.js
import { defineConfig } from "vitest/config";
import { fileURLToPath } from "node:url";

export default defineConfig({
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
  test: {
    environment: "node",
  },
});
```

```js
import { fetchUserProfile } from "@/api/profile";

vi.mock("@/api/profile", () => ({
  fetchUserProfile: vi.fn().mockResolvedValue({ id: 7, displayName: "Grace Hopper" }),
}));

it("在替身生效时应返回用户档案", async () => {
  await expect(fetchUserProfile(7)).resolves.toMatchObject({ id: 7 });
});
```

> 别名写在配置的顶层而非 test 内部，原因是解析规则属于 Vite 的能力，不属于测试运行器本身的配置。

**速记**：别名写在 resolve.alias，import 与 vi.mock 两处路径写法必须一致。



#### 虚拟模块的替身方式

**虚拟模块**：是不落磁盘、由构建插件的解析与加载钩子实时提供的模块，命名上常用 virtual: 前缀或反斜杠加零开头的内部标识。

- 前置条件：测试环境必须注册提供该模块的插件，否则导入语句在解析阶段就直接失败。
- 复用配置：vitest.config 通过 plugins 引入同一插件，或直接复用 vite.config 中的插件数组。
- 替身方式：模块能被解析之后，即可用 vi.mock 安装工厂，或把别名指向测试专用实现。
- 形状一致：虚拟模块的默认导出常是纯数据对象，替身必须保持同样的字段结构。

```js
// vitest.config.js 注册业务插件，让 virtual:build-info 可以在测试中解析
import { defineConfig } from "vitest/config";
import buildInfoPlugin from "./plugins/build-info.js";

export default defineConfig({
  plugins: [buildInfoPlugin()],
  test: {
    environment: "node",
  },
});
```

```js
vi.mock("virtual:build-info", () => ({
  default: { version: "0.0.0-test", commit: "test" },
}));

import buildInfo from "virtual:build-info";

it("在测试替身下应返回占位版本号", () => {
  expect(buildInfo.version).toBe("0.0.0-test");
});
```

> [!TIP]
> **建议内容**：把虚拟模块的默认导出设计成纯数据对象，测试里就能用工厂一次替换，不必为它维护一套假的插件实现。

**速记**：虚拟模块先要能在测试环境解析，再用 vi.mock 或别名指向替身实现。



### 依赖注入与可测性设计

**依赖注入与可测性设计** 是让测试不再依赖替换的正面做法：依赖由外部提供，替换变成调用方的选择，而不是对模块内部的入侵。

#### 依赖注入的三种形式

**依赖注入（dependency injection）**：是把协作对象由外部传入而不是在模块内部创建的做法，常见形式为参数注入、构造函数注入与工厂注入。

- 参数注入：把协作函数作为参数传入，适合无状态的服务函数。
- 构造函数注入：把协作对象保存为实例字段，适合有状态的服务类。
- 工厂注入：模块导出接收依赖并返回实例的工厂函数，由组合根统一装配。
- 共同点：依赖在调用处显式可见，测试不需要知道模块内部从哪里取依赖。

```js
export class OrderService {
  constructor(paymentGateway, orderRepository) {
    this.paymentGateway = paymentGateway;
    this.orderRepository = orderRepository;
  }

  async submit(order) {
    const receipt = await this.paymentGateway.charge(order.total);
    await this.orderRepository.save({ ...order, receiptId: receipt.id });
    return receipt.id;
  }
}
```

```js
const paymentGateway = { charge: vi.fn().mockResolvedValue({ id: "pay_1" }) };
const orderRepository = { save: vi.fn().mockResolvedValue(undefined) };
const orderService = new OrderService(paymentGateway, orderRepository);

it("在支付成功时应保存带凭据的订单", async () => {
  await expect(orderService.submit({ id: 1, total: 9900 })).resolves.toBe("pay_1");
  expect(orderRepository.save).toHaveBeenCalledWith({
    id: 1,
    total: 9900,
    receiptId: "pay_1",
  });
});
```

> 构造函数注入把依赖关系写在了类签名上，阅读者不必翻实现就能知道这个类需要什么，测试也只需照着签名造替身。

**速记**：参数注入、构造函数注入、工厂注入，共同点是依赖由外部显式传入。



#### 可测性设计的取舍

**可测性设计**：是为测试方便而在生产代码中引入的接缝，判据是这条接缝对其他协作者是否同样有价值。

- 值得引入：把副作用收进少数适配器、把纯逻辑抽成独立函数、用默认参数提供生产实现。
- 不值得引入：仅为测试而增加的分支、仅为测试而暴露的私有成员、仅为测试而设置的全局开关。
- 默认参数：缺省时使用真实实现，测试显式传入替身，生产调用不受影响。
- 分层收益：把取数据与算规则拆开后，规则层用普通输入即可验证，不需要任何替身。

```js
// 纯计算：不接触外部世界，直接跑真实实现
export function calculateShippingFee(weightKg, ratePerKg) {
  return Number((weightKg * ratePerKg).toFixed(2));
}

it("在重量为 3 千克、单价 4.5 元时应返回 13.5 元", () => {
  expect(calculateShippingFee(3, 4.5)).toBe(13.5);
});
```

```js
// 适配器：跨越网络边界，测试中用替身替换
export async function loadShippingRate(region) {
  const response = await fetch(`https://api.example.com/shipping/rates?region=${region}`);
  return (await response.json()).ratePerKg;
}
```

> [!IMPORTANT]
> **重要内容**：为可测性改造生产代码时，必须在同一次提交内更新全部调用方；留下半改造状态会让依赖来源变得不确定，比完全不改造更难维护。

**速记**：可测性接缝要对真实使用者也成立，否则就是给测试挖的坑。



#### 全局单例与容器

**全局单例**：是在模块顶层创建并导出的唯一实例，它把依赖固定在了模块内部，是替换依赖时最常见的障碍。

- 症状：模块顶部导出 const 客户端实例，测试无法把它换成替身。
- 出路一：改为导出创建函数，由调用方装配，测试自行构造副本。
- 出路二：同时导出工厂与默认实例，生产代码继续使用默认实例。
- 出路三：用 vi.mock 替换整个模块，代价是与模块结构强耦合，属于兜底手段。
- 组织方式：依赖较多时由一个组合根集中装配，测试在组合根上换掉需要替换的那几项。

```js
// 反例：模块顶层单例，内部依赖无法替换
export const apiClient = createApiClient({ baseUrl: "https://api.example.com" });
```

```js
// 正解：同时导出工厂与默认实例，调用方与测试各取所需
export function createApiClient(config) {
  return {
    async getUser(userId) {
      const response = await fetch(`${config.baseUrl}/users/${userId}`);
      return response.json();
    },
  };
}

export const defaultApiClient = createApiClient({ baseUrl: "https://api.example.com" });
```

> 改造单例需要同步更新调用方，动作比写一条 vi.mock 大；项目早期就采用工厂导出，后续测试成本会低很多。

**速记**：顶层单例挡住替换，改为导出工厂并保留默认实例，调用方与测试各取所需。



### 网络请求与存储的隔离

**网络请求与存储的隔离** 处理两类最常见的不可控依赖：出网的调用与落到浏览器里的状态。两者都应在用例边界上被替换或复位。

#### 网络请求的替身

**网络请求替身**：是拦在 fetch 等出网调用上的替身，用来固定响应内容、模拟延迟与错误，并断言实际发出的请求。

- 全局替换：vi.stubGlobal("fetch", vi.fn()) 一次替换整个文件的 fetch，配合 vi.unstubAllGlobals 收回。
- 局部侦测：vi.spyOn(globalThis, "fetch") 保留还原能力，适合只替换少数用例的场景。
- 响应形状：替身需要返回带 ok、status 与 json 方法的对象，结构与真实 Response 保持一致。
- 错误分支：用 mockRejectedValue 模拟网络失败，用非 2xx 状态模拟接口报错。
- 请求断言：检查调用参数中的地址、方法与请求体，确认请求被正确组装。

```js
// src/api/profile.js
export async function fetchUserProfile(userId) {
  const response = await fetch(`https://api.example.com/users/${userId}`);
  if (!response.ok) throw new Error(`请求失败：${response.status}`);
  return response.json();
}
```

```js
import { fetchUserProfile } from "../src/api/profile";

const fetchStub = vi.fn().mockResolvedValue({
  ok: true,
  status: 200,
  json: async () => ({ id: 7, displayName: "Grace Hopper" }),
});

beforeEach(() => {
  vi.stubGlobal("fetch", fetchStub);
});

afterEach(() => {
  vi.unstubAllGlobals();
});

it("在接口返回 200 时应解析出用户档案", async () => {
  await expect(fetchUserProfile(7)).resolves.toEqual({ id: 7, displayName: "Grace Hopper" });
  expect(fetchStub).toHaveBeenCalledWith("https://api.example.com/users/7");
});
```

> Node.js 18 起自带全局 fetch，Node 环境下无需额外安装；更早的版本或部分 jsdom 组合中侦测会提示 fetch 未定义，需要先补上实现。

**速记**：网络替身要造出与 Response 同形的对象，并覆盖错误分支与请求参数断言。



#### 浏览器存储的隔离

**存储隔离**：是把 localStorage、sessionStorage、cookie 与 IndexedDB 的状态在用例之间复位或替换，避免用例相互污染。

- 真实实现加清理：jsdom 提供 localStorage，在 beforeEach 中调用 clear 即可，最贴近真实行为。
- 侦测方法：vi.spyOn(Storage.prototype, "getItem") 可拦截全部存储实例上的读取。
- 整体替换：vi.stubGlobal("localStorage", 自建对象) 适合验证存储读写失败的分支。
- IndexedDB：jsdom 不提供实现，需要引入 fake-indexeddb，并在每个用例前重建实例。
- cookie：通过 document.cookie 读写，隔离时逐条设置过期时间，相关会话语义详见 后端/Node 主题第 31 篇 身份认证：Cookie、Session 与 JWT。

```js
function resolveEntryPath() {
  return localStorage.getItem("sessionToken") ? "/workspace" : "/login";
}

beforeEach(() => {
  localStorage.clear();
});

it("在缺少会话令牌时应跳转登录页", () => {
  expect(resolveEntryPath()).toBe("/login");
});

it("在存在会话令牌时应进入工作台", () => {
  localStorage.setItem("sessionToken", "token_abc");
  expect(resolveEntryPath()).toBe("/workspace");
});
```

```js
// test/setup.js
import "fake-indexeddb/auto";
import { IDBFactory } from "fake-indexeddb";

beforeEach(() => {
  globalThis.indexedDB = new IDBFactory();
});
```

> [!CAUTION]
> **注意内容**：jsdom 中的 localStorage 内容会跨用例保留，未清理时上一条用例写入的令牌会让本条用例走错分支，报错现象与存储功能本身无关。

**速记**：存储优先用真实实现加清理，需要验证失败分支时再整体替换。



### 外部服务的替身策略

**外部服务的替身策略** 回答替换应该落在哪一层：手写替身换函数，测试服务器换网络边界，真实环境则不换。

#### 契约与手写替身

**契约替身**：是按接口约定手写的最小实现，不依赖真实服务，但必须与真实服务遵守同一份约定。

- 优点：零外部依赖、启动快、断言直接，适合单元测试与联调前的早期开发。
- 风险：服务契约变更时替身不会自动发现，容易长期偏离真实行为。
- 缓解：把约定写成共享的类型或示例数据，替身与真实调用方共用同一份定义。
- 适用：接口数量少、结构简单的第三方服务，以及需要精确控制异常分支的场景。

```js
// test/doubles/paymentGateway.js
export function createPaymentGatewayDouble() {
  return {
    async charge(amountCents) {
      if (amountCents <= 0) throw new Error("金额必须大于 0");
      return { id: `pay_${amountCents}`, status: "succeeded" };
    },
  };
}
```

> 手写替身最容易出的问题是「替身对了、真实错了」：替身按自己理解的契约返回数据，而真实服务返回的字段名早已不同。

**速记**：手写替身轻便但易漂移，必须用一份共享契约约束它。



#### 用测试服务器替代手写替身

**测试服务器**：是在本进程内拦截并响应网络请求的替身方案，Mock Service Worker 是常用实现，Node 环境通过 setupServer 注册请求处理器。

- 安装：执行 npm install --save-dev msw；浏览器端调试还需要执行 npx msw init public/ 生成服务工作线程。
- 处理器：用 http.get 与 http.post 注册路由，用 HttpResponse.json 构造响应。
- 生命周期：beforeAll 调用 server.listen，afterEach 调用 server.resetHandlers，afterAll 调用 server.close。
- 收益：业务代码完全不知道替身存在，网络层以上都是真实实现，更接近集成测试。
- 临时覆盖：单条用例可用 server.use 追加处理器，覆盖默认响应而不影响其他用例。

```js
// test/mocks/server.js
import { setupServer } from "msw/node";
import { http, HttpResponse } from "msw";

export const server = setupServer(
  http.get("https://api.example.com/users/:userId", ({ params }) =>
    HttpResponse.json({ id: Number(params.userId), displayName: "Grace Hopper" }),
  ),
);
```

```js
import { server } from "./mocks/server";
import { fetchUserProfile } from "../src/api/profile";

beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

it("在服务正常时应返回用户档案", async () => {
  await expect(fetchUserProfile(7)).resolves.toEqual({
    id: 7,
    displayName: "Grace Hopper",
  });
});
```

> [!WARNING]
> **警告内容**：注册了处理器却不在用例之间调用 resetHandlers，某条用例临时覆盖的响应会泄漏给后续用例，表现为随机出现的失败。

**速记**：测试服务器把替身下沉到网络边界，业务代码零改动，但处理器必须逐例复位。



#### 替身策略的选型

**替身策略选型**：是按测试层级决定替换位置的做法，替换位置越靠外，用例越接近真实集成。

- 单元测试：用 vi.fn 与 vi.spyOn 替换函数级依赖，追求速度与失败定位精度。
- 组件与集成测试：用测试服务器或存储替身，保留真实的数据流与序列化过程。
- 端到端测试：使用真实后端或专用测试环境，验收集成结果，工具与写法详见本主题第 13 篇 端到端测试：Playwright。
- 服务端范围：接口测试与数据库测试的方案属于服务端主题，详见 后端/Node 主题第 30 篇 MySQL2 与数据库操作。
- 混合策略：多数用例走测试服务器，少数边界用例用手写替身覆盖异常分支。

```bash
npx vitest run src/api/profile.test.js
# 单文件运行，确认替身只在该文件内生效
npx vitest run --coverage
# 替身实现自身也会被计入覆盖率，模块划分越细越容易看清真实覆盖
```

> 选型不看工具强弱，看这一层测试要回答什么问题：回答「这段逻辑对不对」就替换得越靠内越好，回答「系统连起来对不对」就替换得越靠外越好。

**速记**：单元测试换函数、集成测试换网络边界、端到端不换，替换位置随测试目标外移。
