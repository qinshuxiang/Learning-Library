## 端到端测试：Playwright

### 端到端测试的定位

端到端测试位于测试金字塔顶端，用例数量最少而单条覆盖面最广。本节界定它与下层测试的边界，并说明 Playwright 在这一层承担的角色。

#### 端到端测试是什么

**端到端测试（end-to-end test）**：是从用户可见入口出发，驱动真实浏览器与真实服务完成一条完整业务链路的测试，验证的是多个模块组装之后的业务结果。

- 链路真实：浏览器渲染、网络请求、服务端处理与数据读写均按接近生产环境的方式发生。
- 结果导向：只关心用户能否完成目标操作，不关心内部由哪些函数协作完成。
- 成本偏高：需要启动服务与浏览器，单条用例的耗时通常是单元测试的数十倍。

```ts
// tests/login.spec.ts
import { test, expect } from "@playwright/test";

test("输入正确账号密码后应跳转到购物车页", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("用户名").fill("ada");
  await page.getByLabel("密码").fill("secret");
  await page.getByRole("button", { name: "登录" }).click();

  await expect(page).toHaveURL(/\/cart/);
});
```

> 端到端测试与下层测试不是替代关系：单元测试保证逻辑正确，端到端测试保证链路可用，分层见本主题第 1 篇 测试简介与测试体系。

**速记**：端到端测试驱动真实浏览器走完整链路，只验证业务结果。



#### 与集成测试的边界

**集成测试（integration test）**：是验证两个以上模块协作是否正确、外部依赖可用替身或测试容器替换的测试，关注模块接缝而不是完整链路。

- 依赖处理：集成测试允许替换数据库与第三方服务，端到端测试尽量保持真实。
- 观察角度：集成测试从代码入口调用，端到端测试从用户界面操作。
- 划分依据：是否需要真实浏览器与真实部署环境，是区分两者的主要标准。

```ts
// 集成测试：模块协作加外部服务替身
import { test, expect, vi } from "vitest";
import { submitOrder } from "./orderService";

vi.mock("./paymentClient", () => ({
  charge: vi.fn().mockResolvedValue({ status: "paid" }),
}));

test("下单服务在支付成功时应返回已支付状态", async () => {
  const result = await submitOrder({ sku: "A-1", count: 2 });
  expect(result.status).toBe("paid");
});
```

> Playwright 的定位是这一层的通用工具：同一套 API 既能驱动 Chromium、Firefox、WebKit 三种内核，也能发起接口请求做前置准备。

**速记**：集成测试验证模块接缝并允许替身，端到端测试保持真实链路。



### 安装与浏览器下载

Playwright 的运行器与浏览器二进制分开安装，配置文件的默认项决定后续所有用例的行为。本节给出从零接入与既有工程增量接入两条路径。

#### 安装依赖与初始化

**@playwright/test**：是 Playwright 的测试运行器包，内含测试运行、断言、浏览器驱动与报告能力，安装后提供 npx playwright 命令。

- 脚手架方式：执行 npm init playwright@latest，按提示选择语言、测试目录与是否立即下载浏览器。
- 增量方式：执行 npm install -D @playwright/test，再把配置文件与测试目录加入既有工程。
- 环境要求：需要 Node.js 18 及以上版本，脚手架生成的工程自带示例用例与配置文件。

```bash
# 方式一：脚手架，一次生成配置、示例用例与依赖
npm init playwright@latest

# 方式二：在既有工程中增量接入
npm install -D @playwright/test
```

**速记**：装 @playwright/test 得到运行器与断言，浏览器需要单独下载。



#### 下载浏览器二进制

**浏览器二进制（browser binary）**：是 Playwright 为每个受支持浏览器版本准备的独立可执行文件，与系统已安装的浏览器互不影响。

- 全量下载：执行 npx playwright install，安装 Chromium、Firefox、WebKit 三套内核。
- 按需下载：执行 npx playwright install chromium 只装一个内核，适合精简流水线镜像。
- 系统依赖：Linux 环境下执行 npx playwright install --with-deps，一并安装运行所需的系统库。
- 缓存目录：默认写入用户缓存目录，可用环境变量 PLAYWRIGHT_BROWSERS_PATH 改写位置。

```bash
npx playwright install
npx playwright install chromium
npx playwright install --with-deps
```

> 浏览器版本与 @playwright/test 版本绑定：升级依赖包之后必须重新执行安装命令，否则运行时报找不到可执行文件。

**速记**：浏览器二进制由 install 命令下载，与系统浏览器无关，升级依赖后要重装。



#### playwright.config.ts 基础字段

**playwright.config.ts**：是 Playwright 的配置文件，把配置对象传给 defineConfig(config) 即可获得类型提示，集中声明测试目录、超时、浏览器项目与报告方式。

- testDir：测试文件所在目录，默认是配置文件所在目录。
- projects：浏览器与设备的组合，每个项目会把全部用例各跑一遍。
- use：项目级默认选项，等价于在文件顶部写一行 test.use(options)。
- webServer：测试前自动拉起本地服务，url 字段用于等待服务就绪。
- retries 与 workers：失败重试次数与并行进程数，常按环境变量区分本地与流水线。

```ts
// playwright.config.ts
import { defineConfig, devices } from "@playwright/test";

export default defineConfig({
  testDir: "./tests",
  timeout: 30_000,
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  reporter: [["html", { open: "never" }], ["list"]],
  use: {
    baseURL: "http://localhost:4173",
    trace: "on-first-retry",
  },
  projects: [
    { name: "chromium", use: { ...devices["Desktop Chrome"] } },
    { name: "webkit", use: { ...devices["Desktop Safari"] } },
  ],
  webServer: {
    command: "npm run preview",
    url: "http://localhost:4173",
    reuseExistingServer: !process.env.CI,
  },
});
```

> [!IMPORTANT]
> **重要内容**：只有配置了 use.baseURL，用例中的 page.goto("/login") 才会解析成绝对地址；写成完整 URL 会绕过该配置，换环境时需逐条修改。

**速记**：配置文件用 defineConfig 声明目录、超时、projects、use 默认项与本地服务。



### 用例结构与选择器

用例写法决定后续维护成本。本节从用例与分组入手，再给出定位器的选择顺序，最后落到页面对象的封装方式。

#### test 与 test.describe 的组织

**test 函数**：是声明单条测试用例的入口，签名是 test(title, callback)，title 为用例标题，callback 接收包含 page 等夹具的对象。

- test.describe(title, callback)：把若干用例归入一组，组内共享标题路径与钩子。
- test.beforeEach(callback)：每条用例前执行，常用于打开页面与准备数据。
- test.afterEach(callback)：每条用例后执行，用于清理数据与还原替身。
- 夹具注入：回调参数里的 page 由运行器按用例创建，不需要手工管理生命周期。

```ts
// tests/login.spec.ts
import { test, expect } from "@playwright/test";

test.describe("登录页", () => {
  test.beforeEach(async ({ page }) => {
    await page.goto("/login");
  });

  test("密码为空时应提示必填", async ({ page }) => {
    await page.getByRole("button", { name: "登录" }).click();
    await expect(page.getByText("请输入密码")).toBeVisible();
  });
});
```

**速记**：test 声明用例，test.describe 分组共享钩子，page 由夹具注入。



#### 定位器与选择器优先级

**定位器（locator）**：是描述如何在页面中查找元素的对象，由 page.getByRole(role, options) 等方法创建，查找发生在每次操作时而不是创建时。

- 优先语义定位：getByRole(role, { name }) 依据可访问性角色，其次 getByLabel(text)、getByPlaceholder(text) 与 getByText(text)。
- 兜底测试标识：getByTestId(testId) 读取测试专用属性，需要在组件上预留。
- 通用选择器：page.locator(selector) 接受 CSS 选择器，page.locator("xpath=...") 接受 XPath，两者稳定性最差。
- 链式筛选：locator.filter({ hasText }) 与 locator.nth(index) 用于在多个匹配中精确定位。
- 惰性求值：定位器保存的是查询策略，页面更新后再次操作会重新解析，不存在引用过期。

```ts
// 推荐：按可访问性角色定位，按钮文案调整时仍能命中
const submitButton = page.getByRole("button", { name: "提交订单" });

// 次选：按表单标签定位输入框
const emailInput = page.getByLabel("邮箱");

// 兜底：显式测试标识
const totalPrice = page.getByTestId("total-price");

// 不推荐：依赖 DOM 层级的 CSS 选择器，布局调整后立即失效
// const totalPrice = page.locator("div.cart > ul > li:nth-child(3) > span");
```

> [!CAUTION]
> **注意内容**：page.locator(selector) 的选择器写错不会在创建时报错，只会在等待超时后失败；排查时先用浏览器开发者工具确认选择器能命中元素。

**速记**：定位器是惰性查询策略，按角色、标签、文本、测试标识的顺序选择。



#### 页面对象与交互动作

**页面对象（page object）**：是把某个页面的定位器与操作封装成类的模式，让用例只表达业务意图，页面改动集中在一处修改。

- 常用交互：locator.click(options)、locator.fill(value)、locator.selectOption(values)、locator.check() 与 locator.press(key)。
- 封装收益：页面改版只改页面对象，用例不动。
- 职责边界：页面对象只提供操作，断言留在用例中，保证预期集中可读。
- 构造注入：把 page 通过构造函数传入页面对象，便于在夹具中复用。

```ts
// tests/pages/LoginPage.ts
import type { Page } from "@playwright/test";

export class LoginPage {
  constructor(private readonly page: Page) {}

  async open() {
    await this.page.goto("/login");
  }

  async signIn(username: string, password: string) {
    await this.page.getByLabel("用户名").fill(username);
    await this.page.getByLabel("密码").fill(password);
    await this.page.getByRole("button", { name: "登录" }).click();
  }
}
```

```ts
// tests/login.spec.ts
import { test, expect } from "@playwright/test";
import { LoginPage } from "./pages/LoginPage";

test("输入正确账号密码后应进入购物车页", async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.open();
  await loginPage.signIn("ada", "secret");

  await expect(page).toHaveURL(/\/cart/);
});
```

**速记**：页面对象集中定位器与操作，用例保留断言。



### 断言与自动等待

端到端测试的失败多数来自时序，而不是逻辑。本节说明网页优先断言的用法、自动等待的判定条件，以及导航时如何声明等待目标。

#### expect 与网页优先断言

**网页优先断言（web-first assertion）**：是 expect(locator) 之后调用的一组断言方法，条件未满足时自动重试直至超时，避免手工等待。

- locator 断言：toBeVisible(options)、toHaveText(expected, options)、toContainText(expected)、toHaveValue(value)、toHaveCount(count) 与 toBeEnabled()。
- 页面断言：expect(page).toHaveURL(url, options) 与 expect(page).toHaveTitle(title) 验证导航结果。
- 自动重试：断言在超时窗口内反复求值，网络延迟造成的时序抖动不会立刻变成失败。
- 失败信息：第二个参数传中文说明，失败报告中会直接显示。

```ts
test("购物车应显示两件商品与合计金额", async ({ page }) => {
  await page.goto("/cart");

  const items = page.getByRole("listitem");
  await expect(items).toHaveCount(2, { timeout: 5_000 });
  await expect(page.getByTestId("total-price")).toHaveText("￥199.00");
  await expect(page.getByRole("button", { name: "结算" })).toBeEnabled();
});
```

**速记**：expect 配定位器的断言会自动重试，比手工等待稳定。



#### 自动等待与超时

**自动等待（auto-waiting）**：是 Playwright 在执行动作前检查元素可操作性、在执行断言前重试求值的机制，是多数用例无需显式等待的原因。

- 可操作性条件：元素已挂载、可见、位置稳定、可接收事件且未被其他元素遮挡。
- 超时层级：整条用例由 timeout 控制，动作由 use.actionTimeout 控制，断言由 expect.timeout 控制。
- 显式等待：page.waitForSelector(selector, options) 与 page.waitForURL(url, options) 等待特定状态出现。
- 反模式：page.waitForTimeout(milliseconds) 只用于临时调试，写进用例会同时牺牲速度与稳定性。

```ts
// playwright.config.ts 片段
import { defineConfig } from "@playwright/test";

export default defineConfig({
  timeout: 30_000,
  expect: { timeout: 5_000 },
  use: { actionTimeout: 10_000, navigationTimeout: 15_000 },
});
```

> [!WARNING]
> **警告内容**：用固定时长暂停替代等待条件会掩盖真实的时序问题，本机通过而换机器运行后失败，且很难复现。

**速记**：动作与断言自带等待，超时按层配置，固定时长暂停只用于调试。



#### 导航与等待条件

**页面导航（navigation）**：由 page.goto(url, options) 触发，options.waitUntil 决定何时算加载完成，取值有 load、domcontentloaded、networkidle 与 commit。

- 默认取值：waitUntil 默认是 load，即等待 load 事件触发。
- 等待跳转：点击触发跳转后，用 page.waitForURL(url, options) 或直接断言地址。
- 多标签页：context.newPage() 建新页面，page.waitForEvent("popup") 捕获弹窗式打开。
- 网络空闲：networkidle 表示 500 毫秒内没有新请求，适合等待首屏数据加载，代价是增加等待时长。

```ts
await page.goto("http://localhost:4173/products", { waitUntil: "domcontentloaded" });

await page.getByRole("link", { name: "我的订单" }).click();
await page.waitForURL(/\/orders$/);
await expect(page.getByRole("heading", { name: "我的订单" })).toBeVisible();
```

**速记**：goto 的 waitUntil 决定加载完成的判定点，跳转后用 waitForURL 等待地址变化。



### 调试工具与追踪报告

端到端测试的失败现场转瞬即逝，工具链的价值在于把现场留存下来。本节覆盖录制、交互式调试、命令行筛选与追踪报告四类手段。

#### codegen 录制与生成

**codegen**：是 Playwright 的命令行代码生成器，打开浏览器并记录操作，把每一步转换为可运行的测试代码。

- 启动：执行 npx playwright codegen http://localhost:4173。
- 指定内核：附加 --browser=webkit 切换到 WebKit。
- 指定设备：附加 --device="iPhone 13" 模拟移动端视口与触摸事件。
- 产物整理：录制结果给出初始定位器，仍需按页面对象与命名规范改写。

```bash
npx playwright codegen http://localhost:4173
npx playwright codegen --browser=webkit --device="iPhone 13" http://localhost:4173
# 生成的代码实时显示在 Playwright Inspector 窗口中
```

> codegen 产出的是能跑通的脚本，不是可维护的用例；定位器优先级与断言仍需人工收敛。

**速记**：codegen 用于快速采集定位器，产出必须人工整理。



#### UI 模式与断点调试

**UI 模式**：是 Playwright 的交互式图形界面，执行 npx playwright test --ui 启动，可逐条运行用例并查看动作时间线与 DOM 快照。

- 筛选：左侧列表按文件、项目与标题过滤，可只看失败用例。
- 时间线：每个动作对应一次快照，可回退到任意一步查看页面当时的 DOM 与网络。
- 断点：在代码中调用 await page.pause() 暂停，或用 npx playwright test --debug 启动单步执行。
- 有头运行：npx playwright test --headed 打开真实窗口，观察操作过程。

```bash
npx playwright test --ui
npx playwright test --debug tests/login.spec.ts
npx playwright test --headed --project=chromium
```

**速记**：UI 模式看时间线，page.pause 与 --debug 做单步，--headed 肉眼观察。



#### 常用命令行与筛选

**playwright test 命令**：是运行用例的统一入口，读取配置后按文件、标题与项目三个维度筛选。

- 全量运行：npx playwright test，默认并行执行全部项目。
- 指定文件：npx playwright test tests/login.spec.ts，在文件后附加冒号与行号可只跑一条用例。
- 按标题：npx playwright test -g "登录"，匹配 describe 与 test 的标题文字。
- 按项目：npx playwright test --project=chromium 只跑指定浏览器。
- 列出用例：npx playwright test --list 只列不跑，用于确认筛选范围。
- 稳定性排查：npx playwright test --repeat-each=3 重复执行，复现偶发失败。

```bash
npx playwright test --list
# Listing tests:
#   [chromium] > tests/login.spec.ts:8:3 > 登录页 > 密码为空时应提示必填
#   [chromium] > tests/login.spec.ts:14:3 > 登录页 > 输入正确账号密码后应跳转到购物车页
```

**速记**：playwright test 按文件、标题、项目筛选，--list 先确认范围。



#### trace 追踪与报告查看

**追踪（trace）**：是 Playwright 按操作步骤记录的快照、网络与控制台信息的集合，用于失败之后还原现场。

- 开关：use.trace 取值有 off、on、retain-on-failure 与 on-first-retry。
- 查看：执行 npx playwright show-trace trace.zip 打开 Trace Viewer，逐帧查看 DOM、网络与控制台。
- 报告：reporter 配置成 html 后执行 npx playwright show-report 打开报告页面。
- 保留策略：本地调试临时取 on，流水线取 on-first-retry 或 retain-on-failure，避免产物过大。

```ts
// playwright.config.ts 片段：只为重试的失败用例保留追踪
import { defineConfig } from "@playwright/test";

export default defineConfig({
  retries: 2,
  use: { trace: "on-first-retry", video: "retain-on-failure" },
});
```

```bash
npx playwright test
npx playwright show-report
npx playwright show-trace test-results/login-chromium/trace.zip
```

> [!NOTE]
> **提醒内容**：trace 全量开启会显著增大产物体积并拖慢运行，只在需要还原失败现场时开启。

**速记**：trace 记录操作与网络现场，用 show-trace 打开，按失败策略保留。
