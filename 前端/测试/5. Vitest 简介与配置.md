## Vitest 简介与配置

### Vitest 是什么与优势

本节回答三个问题：Vitest 是什么、它解决了传统方案里的哪些痛点、适合在什么项目里使用。

#### Vitest 的定义与定位

**Vitest**：是基于 Vite 构建的测试运行器，复用 Vite 的配置、插件与模块解析能力，在开发期以监视模式运行测试，并提供与 Jest 兼容的 expect 断言接口。

- 底层依赖：模块转换与依赖解析交给 Vite，测试文件按需转换，不生成中间产物。
- 接口兼容：describe、it、expect、vi 等全局与 Jest 大体一致，迁移成本低。
- 暴露面：提供命令行工具、可编程 API startVitest，以及与编辑器、CI 的集成方式。
- 定位：面向使用 Vite 的前端项目，尤其是 Vue、React、Svelte 组件测试场景。

```bash
node --version
# v20.11.1
npx vitest --version
# 3.2.4
```

> [!NOTE]
> **提醒内容**：Vitest 3 要求 Node.js 18 及以上版本，Node 16 需停在 Vitest 1 或先升级运行时。

**速记**：Vitest 是复用 Vite 的测试运行器，接口向 Jest 对齐，面向 Vite 项目。



#### 与传统方案相比的优势

**与传统方案相比的优势**：指 Vitest 在配置复用、执行速度与开发体验三方面相对 Jest 等方案更契合 Vite 工程。

- 配置复用：直接读取 vite.config 中的别名、插件与 define，测试与构建使用同一套解析规则。
- 启动更快：依赖预构建与按需转换让首次启动和增量重跑都更快。
- 原生 ESM：源码按 ES 模块处理，不需要额外配置转换，TypeScript 也由 Vite 直接处理。
- 监视体验：默认监视模式，配合界面可只重跑受改动影响的测试。

```bash
npx vitest run
# ✓ src/utils/format.test.ts (3 tests) 21ms
# Test Files  1 passed (1)
#      Tests  3 passed (3)
#   Duration  512ms
```

> Jest 在 CJS 与 ESM 互操作、路径别名、TypeScript 转换上通常需要额外配置，Vitest 把这些交给 Vite 统一处理。

**速记**：配置复用、启动快、原生 ESM、监视体验好是 Vitest 的四项主要优势。



### 安装与配置文件

安装只需要一个开发依赖，真正的差异在配置文件放在哪里、用什么字段表达意图。本节说明安装步骤与两种配置文件的取舍。

#### 安装步骤

**安装**：指把 vitest 及其可选配套包加入项目的 devDependencies，并准备一个测试脚本。

- 核心包：执行 npm install --save-dev vitest，安装后即可使用 vitest 命令。
- 覆盖配套：npm install --save-dev @vitest/coverage-v8，使用 v8 采集覆盖率。
- 界面配套：npm install --save-dev @vitest/ui，启用浏览器界面。
- DOM 环境：npm install --save-dev jsdom 或 happy-dom，用于浏览器环境测试。
- 脚本：在 package.json 的 scripts 中加 test、test:run、test:coverage 三条命令。

```bash
npm install --save-dev vitest @vitest/coverage-v8 jsdom
```

```json
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run",
    "test:coverage": "vitest run --coverage"
  },
  "devDependencies": {
    "vitest": "^3.2.4",
    "@vitest/coverage-v8": "^3.2.4",
    "jsdom": "^25.0.1"
  }
}
```

> 监视模式与单次运行的差别在脚本命名上体现：test 用于本地开发，test:run 用于 CI 与提交前检查。

**速记**：安装 vitest 加可选配套包，在 scripts 中区分监视与单次运行两条命令。



#### 配置文件与 defineConfig

**vitest.config.ts**：是 Vitest 的专用配置文件，用 defineConfig 导出配置对象，其中 test 字段承载全部测试相关选项。

- defineConfig：从 vitest/config 导入，为配置对象提供类型提示与校验。
- test 字段：测试选项统一放在 test 之下，与构建选项并列互不干扰。
- 导出形式：默认导出配置对象，也可以是返回配置对象的函数。

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "jsdom",
    globals: true,
    include: ["src/**/*.test.ts"],
    setupFiles: ["./tests/setup.ts"],
    testTimeout: 10000,
    coverage: {
      provider: "v8",
      reporter: ["text", "html"],
      thresholds: { lines: 80, functions: 80, branches: 70, statements: 80 },
    },
  },
});
```

> defineConfig 只是类型包装，运行时等价于直接导出一个普通对象；它带来的收益是编辑器能提示 test 下有哪些字段。

**速记**：vitest.config.ts 用 defineConfig 导出，测试选项集中在 test 字段。



#### 配置文件命名与优先级

**配置文件命名与优先级**：指 Vitest 按固定顺序查找配置文件，找到第一个即停止，并据此决定是否读取 Vite 配置。

- 查找顺序：先找 vitest.config，再找 vite.config，两者都支持 ts、js、mts、mjs 等扩展名。
- 优先级：存在 vitest.config 时只读它，vite.config 中的构建配置不再自动生效。
- 读取方式：默认读取 vite.config 以复用其中的别名与插件，因此单配置文件项目无需额外设置。
- 合并方式：需要同时保留两者时，用 mergeConfig 手动合并（见本篇最后一节）。

> 多数 Vite 项目可以直接在 vite.config.ts 中追加 test 字段，省掉第二个配置文件；配置变复杂后再拆出 vitest.config.ts。

**速记**：vitest.config 优先于 vite.config，找到即停，两者共存需手动合并。



### 常用配置项

配置项决定测试在哪里找、在什么环境跑、有哪些全局能力。本节按使用频率列出最常调整的五组选项。

#### test.include 与 exclude

**test.include**：是字符串或字符串数组，用 glob 模式声明哪些文件是测试文件。**test.exclude**：声明哪些路径不参与匹配。

- 默认值：include 默认为 **/*.{test,spec}.?(c|m)[jt]s?(x)，即文件名含 test 或 spec 的脚本。
- 默认排除：exclude 默认排除 node_modules、dist、.git、.cache 等目录。
- 覆盖规则：显式设置 include 会替换默认值，需要保留默认时用扩展数组的方式写。
- 常见写法：按目录限定，如 src 下只收 .test.ts，tests 下收全部脚本。

```ts
// vitest.config.ts 片段
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    include: ["src/**/*.test.ts", "tests/**/*.spec.ts"],
    exclude: ["**/node_modules/**", "**/dist/**", "**/e2e/**"],
  },
});
```

> glob 中的问号表示可选段，因此 .test.js 与 .test.ts 可以被同一条默认模式同时匹配。

**速记**：include 声明测试文件范围，exclude 排除目录，显式设置会替换默认值。



#### test.environment

**test.environment**：是字符串或对象，声明测试运行的环境，决定全局对象是 Node 的 process 还是浏览器的 window 与 document。

- node：默认值，不注入浏览器全局对象，适合纯函数与 Node 模块测试。
- jsdom：注入基于 jsdom 的浏览环境，适合 DOM 与组件测试。
- happy-dom：轻量替代方案，启动更快，兼容度略低。
- edge-runtime：模拟边缘运行时环境，用于特定平台的代码。
- 文件级覆盖：在测试文件顶部写环境注释，或使用 docblock 声明单文件环境。

```ts
// vitest.config.ts 片段
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { environment: "jsdom" },
});
```

```js
// dom-utils.test.js
// @vitest-environment jsdom
import { expect, it } from "vitest";

it("document 在 jsdom 环境下应可用", () => {
  expect(typeof document.createElement).toBe("function");
});
```

> 选 jsdom 还是 happy-dom 取决于对浏览器 API 的覆盖要求：前者更完整，后者更快。

**速记**：environment 决定全局对象，默认 node，DOM 测试用 jsdom 或 happy-dom。



#### test.globals

**test.globals**：是布尔值，默认 false，开启后 describe、it、expect、vi 等不需要逐文件导入。

- 默认关闭：关闭时每个测试文件显式 import，依赖关系清晰。
- 开启方式：把 globals 设为 true，并在 tsconfig 的 types 中加入 vitest/globals 以获得类型。
- 影响范围：开启后上述标识符成为全局变量，需注意与既有全局名冲突。
- 取舍：小型项目常开启以减少样板，库与大型项目常保持关闭以便静态分析。

```json
{
  "compilerOptions": {
    "types": ["vitest/globals"]
  }
}
```

> [!CAUTION]
> **注意内容**：只把 globals 设为 true 而不在 tsconfig 中声明 vitest/globals，编辑器会把这些标识符报为未定义。

**速记**：globals 默认关闭，开启后免导入，但必须同步配置 TypeScript 类型。



#### setupFiles 与钩子注册入口

**test.setupFiles**：是文件路径数组，在每条测试文件执行之前运行，用于注册全局钩子、扩展匹配器或准备全局配置。

- 执行时机：在每个测试文件的最前面执行一次，早于该文件内的 beforeAll。
- 常见用途：注册清理钩子、扩展 expect 匹配器、导入全局样式或初始化测试数据库。
- 与配置的差别：配置文件在启动时执行一次，setupFiles 对每个测试文件分别执行。
- 顺序：数组按声明顺序依次执行。

```ts
// tests/setup.ts
import { afterEach, vi } from "vitest";

afterEach(() => {
  vi.restoreAllMocks();
});
```

```ts
// vitest.config.ts 片段
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { setupFiles: ["./tests/setup.ts"] },
});
```

> setupFiles 适合放与所有测试相关的清理逻辑；只与某个用例相关的准备应写在用例内部。

**速记**：setupFiles 在每个测试文件执行前运行，用于注册钩子与扩展匹配器。



#### 超时与重试

**test.testTimeout**：是每个测试用例的超时毫秒数，默认 5000。**test.hookTimeout**：是钩子的超时毫秒数，默认 10000。**test.retry**：是用例失败后的重试次数，默认 0。

- 顺序：testTimeout 控制用例，hookTimeout 控制 beforeEach 等钩子，二者独立。
- 局部覆盖：it 的第三个参数可单独指定该用例的超时，优先于全局配置。
- 重试语义：retry 只对失败用例重新执行，重试通过后仍记为通过并给出提示。
- 使用边界：重试用于掩盖偶发抖动，不应替代对不稳定原因的修复。

```ts
// vitest.config.ts 片段
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { testTimeout: 10000, hookTimeout: 20000, retry: 1 },
});
```

```js
import { expect, it } from "vitest";
it("loadRemoteConfig 在网络缓慢时应最终返回配置", async () => {
  const config = await loadRemoteConfig();
  expect(config.retries).toBeGreaterThan(0);
}, 30000); // 该用例单独指定 30 秒超时
```

> 超时值是上限而不是等待时间：用例提前完成即立即返回，调大超时不会拖慢通过的用例。

**速记**：testTimeout 与 hookTimeout 分别管用例与钩子，retry 只补偿偶发抖动。



### 命令行与筛选与监听

配置决定默认行为，命令行决定本次运行的范围与形态。本节说明常用命令、筛选方式与监听模式。

#### 常用子命令与选项

**vitest 子命令**：是命令行工具提供的运行形态，run 表示单次运行，watch 表示持续监听，dev 与 watch 等价。

- vitest：缺省命令，本地终端下进入监视模式，检测到 CI 环境时自动单次运行。
- vitest run：只运行一次并退出，CI 与提交前检查使用此形态。
- vitest watch：显式进入监视模式。
- 常用选项：--config 指定配置文件，--environment 临时切换环境，--silent 抑制控制台输出，--passWithNoTests 在无用例时返回成功。
- 退出码：存在失败用例或收集错误时返回非零，供流水线判定。

```bash
npx vitest run --config ./vitest.config.ts
npx vitest run --environment jsdom
npx vitest run --passWithNoTests
# Test Files  no tests found, passed 0
```

> 本地用 vitest 获得即时反馈，流水线一律用 vitest run，避免进程挂起不退出。

**速记**：run 单次执行，watch 持续监听，CI 必须用 run 以免进程挂起。



#### 用例与文件的筛选

**筛选**：指在命令行上限定本次运行的文件或用例，避免全量重跑。

- 文件筛选：在命令后直接写路径或路径片段，如 npx vitest run src/utils。
- 用例筛选：用 -t 传入用例标题的子串或正则，如 npx vitest run -t 在空数组下。
- 关联筛选：vitest related 传入源码文件，只运行与这些文件有导入关系的测试。
- 改动筛选：--changed 只运行与版本控制中改动文件相关的测试。
- 分片：--shard=1/3 把用例切成三片，本机只跑第一片，用于并行加速。

```bash
npx vitest run src/utils/format.test.ts
npx vitest run -t "在空数组下"
npx vitest run --changed
npx vitest run --shard=1/3
```

> -t 匹配的是用例标题字符串，标题写成完整的中文陈述句时筛选最方便（详见本主题第 6 篇 测试组织与生命周期钩子）。

**速记**：文件用路径筛，用例用 -t 筛，关联与改动筛选能大幅缩小范围。



#### 监听模式与界面

**监听模式**：是文件变更后自动重跑受影响用例的运行形态，默认在本地终端启用。

- 触发方式：修改源码或测试文件后自动重跑，按回车可手动触发一次全量重跑。
- 终端快捷键：a 全量重跑，f 只跑失败用例，p 按文件名过滤，q 退出。
- 界面模式：加 --ui 启动浏览器界面，可视化查看用例树、耗时与失败详情。
- 依赖：界面模式需要安装 @vitest/ui。

```bash
npx vitest --ui
# UI started at http://localhost:51204/__vitest__/
```

> 监视模式只适合本地开发；在 CI 中运行会因进程不退出而卡住流水线。

**速记**：监听模式在改动后自动重跑，--ui 提供可视化界面但需额外安装。



#### 报告器与输出

**报告器（reporter）**：决定运行结果的输出格式，通过 --reporter 选项或 test.reporters 配置。

- default：默认报告器，逐文件列出结果，失败时展示完整错误与堆栈。
- verbose：展开每个用例的结果，适合定位具体失败项。
- dot：每个测试点一个字符，用例很多时最紧凑。
- json 与 junit：结构化输出，供流水线采集与归档。
- 多报告器：数组形式可同时输出到终端与文件。

```bash
npx vitest run --reporter=verbose
npx vitest run --reporter=junit --outputFile=./reports/junit.xml
```

```ts
// vitest.config.ts 片段
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { reporters: ["default", ["junit", { outputFile: "./reports/junit.xml" }]] },
});
```

> 本地看 verbose，流水线归档 junit 或 json，两者用途不同，可按环境分别配置。

**速记**：报告器决定输出格式，本地用 verbose，流水线归档 junit 或 json。



### 与 Vite 项目共享配置

Vitest 复用 Vite 的解析与转换链路，这意味着别名、插件与环境变量可以只写一遍。本节说明复用方式与合并策略。

#### 复用 Vite 配置的方式

**复用 Vite 配置**：指让测试与构建读同一份 resolve、plugins 与 define 配置，避免两套路径规则不一致。

- 单文件方案：在 vite.config.ts 中加 test 字段，并在文件顶部加类型引用以获得提示。
- 双文件方案：保留独立 vitest.config.ts，需要时用 mergeConfig 引入 Vite 配置。
- 类型引用：在 vite.config.ts 首行写三斜杠引用 vitest/config，让 test 字段通过类型检查。
- 生效范围：resolve.alias、plugins、define、css 等构建侧配置对测试同样生效。

```ts
// vite.config.ts
/// <reference types="vitest/config" />
import { defineConfig } from "vite";

export default defineConfig({
  resolve: {
    alias: { "@": new URL("./src", import.meta.url).pathname },
  },
  test: {
    environment: "jsdom",
  },
});
```

> 三斜杠引用只提供类型，不改变运行时行为；忘记写它时编辑器会把 test 字段标为未知属性。

**速记**：vite.config 加 test 字段即可复用构建配置，类型靠三斜杠引用补上。



#### 别名与插件的复用

**别名与插件的复用**：指测试进程沿用构建期的模块解析路径与插件转换规则，使导入写法在两端一致。

- 路径别名：resolve.alias 中的 @ 等前缀在测试文件中同样可用，不需要重复声明。
- 插件复用：Vue、React 等框架插件同时对测试文件生效，组件可直接被测试文件导入。
- 环境变量：define 与 import.meta.env 的取值规则与构建期一致（详见 前端/构建工具 主题第 6 篇 Vite 开发服务器与环境变量）。
- 注意事项：插件副作用在测试中同样发生，性能敏感的插件可用条件判断在测试期关闭。

```ts
// src/utils/format.ts 可被测试以别名导入
import { formatDate } from "@/utils/format";
```

```js
// format.test.js
import { expect, it } from "vitest";
import { formatDate } from "@/utils/format"; // 别名沿用 Vite 配置

it("formatDate 在给定日期下应输出短横线格式", () => {
  expect(formatDate(new Date("2026-09-13"))).toBe("2026-09-13");
});
```

> 别名复用是减少配置漂移的关键：同一路径在两处写两遍，迟早会不一致。

**速记**：别名与插件随 Vite 配置一并复用，测试与构建的导入规则保持一致。



#### 配置合并策略

**配置合并策略**：指 vitest.config 与 vite.config 同时存在时的取舍方式，默认是前者覆盖后者。

- 默认行为：vitest.config 存在时不再读取 vite.config，构建期配置不会自动带入。
- 合并函数：从 vitest/config 导入 mergeConfig，把 Vite 配置作为第一个参数、测试配置作为第二个参数。
- 覆盖规则：对象按字段深度合并，数组整体替换而非拼接。
- 适用场景：需要为测试单独调整插件顺序或换用不同别名时使用。

```ts
// vitest.config.ts
import { defineConfig, mergeConfig } from "vitest/config";
import viteConfig from "./vite.config";

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: { environment: "jsdom", setupFiles: ["./tests/setup.ts"] },
  }),
);
```

> [!WARNING]
> **警告内容**：新建 vitest.config.ts 后若不做合并，vite.config.ts 中的别名与插件会全部失效，测试将报模块解析错误。

**速记**：vitest.config 默认覆盖 vite.config，需要保留构建配置时必须 mergeConfig。



#### 多项目与分环境配置

**多项目配置**：指在同一份配置中声明多个测试项目，各自使用不同的环境、包含范围与文件命名。

- 声明位置：test.projects 数组，每一项可以内联配置，也可以指向配置文件路径。
- 项目命名：每项用 name 字段命名，命令行可用 --project 只运行其中一项。
- 典型切分：单元测试跑 node 环境，组件测试跑 jsdom 环境，端到端测试单独一个项目。
- 收益：一次命令覆盖全部测试，同时保留各环境互不干扰的隔离性。

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    projects: [
      {
        test: { name: "unit", include: ["src/**/*.test.ts"], environment: "node" },
      },
      {
        test: { name: "dom", include: ["tests/**/*.test.ts"], environment: "jsdom" },
      },
    ],
  },
});
```

> 环境差异越大，多项目配置收益越明显；只有单一环境时拆项目反而增加维护成本。

**速记**：test.projects 声明多个测试项目，按环境与目录切分，用 --project 单独运行。
