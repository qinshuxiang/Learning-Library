## 测试与持续集成

### 流水线中运行测试的要点

**持续集成（continuous integration，CI）**：是把代码频繁合入主干、并由自动化流水线在每次提交后执行安装、构建与测试的实践，其目标是在最短时间内发现集成缺陷。

#### 触发时机与流水线结构

**触发时机**：是流水线开始执行的入口条件，由事件类型与分支规则共同定义。

- 推送事件：向功能分支推送提交时触发，用于开发期的快速反馈。
- 合并请求事件：针对合并请求的目标分支触发，用于合并前把关。
- 手动触发：用于发布、回归等低频场景，在配置中声明为可手动发起。
- 定时触发：用于每日全量回归，与提交触发的快速检查形成两档节奏。

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

**流水线（pipeline）**：由若干作业（job）组成，作业内部由若干步骤（step）顺序执行，作业之间默认并行。

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx vitest run
```

> 作业之间默认并行，存在数据依赖时用 needs 声明顺序，例如端到端测试声明 needs 指向单元测试作业，前置失败则不启动。

**速记**：推送与合并请求两类事件构成 CI 的入口，作业内串行、作业间并行的结构决定了反馈速度。



#### 非交互模式与退出码

**非交互模式**：是测试运行器在无终端、无人工介入条件下一次性执行并直接返回退出码的运行方式。

- 监听模式：本地默认进入 watch 模式，文件变化即重跑，适合开发期。
- 一次性执行：流水线中必须显式要求单次运行，Vitest 写作 vitest run，等价于开启 --run。
- 退出码：全部用例通过返回 0，存在失败用例返回非 0，流水线据此判定作业成败。
- 提前终止：用 --bail=1 在首个失败用例出现后立即停止，缩短反馈时间。
- 输出重定向：无终端时彩色输出与进度条会退化，应改用适合日志的简洁输出。

```bash
npx vitest run --bail=1
echo $?
# 0 表示全部通过；非 0 表示存在失败用例
```

> 若流水线中误用监听模式，作业会一直等待文件变化直到超时，表现为流水线长时间挂起。

> [!CAUTION]
> **注意内容**：以管道方式传递测试输出时，若管道末端命令先退出，上游的失败退出码可能被吞掉，导致失败被判定为通过；可开启 shell 的 pipefail 选项规避。

```bash
set -o pipefail
npx vitest run 2>&1 | tee test-output.log
```

**速记**：CI 里用 vitest run 单次执行，靠退出码判定成败，注意管道对退出码的吞并。



#### 运行环境的一致性

**运行环境一致性**：指本地与流水线使用相同的主语言版本、依赖版本与系统时区，避免出现本机通过、流水线失败的假象。

- 主语言版本：用版本文件声明，流水线按文件读取并安装同一版本。
- 依赖版本：以锁文件为准做确定性安装，不重新解析版本范围。
- 系统差异：文件路径大小写、行尾符、时区都会影响断言结果，开发机与 Linux 容器之间差异最明显。
- 浏览器依赖：端到端测试所需的浏览器与系统库应固化进镜像或按缓存安装，减少每次运行开销。

```yaml
- uses: actions/setup-node@v4
  with:
    node-version-file: .nvmrc
    cache: npm
```

> 断言中不要写死绝对路径与本机时区。时间相关断言应固定时区，或在测试内注入可控的当前时间。

```ts
import { describe, expect, it, vi } from "vitest";

describe("formatDeadline", () => {
  it("在固定时钟下应输出稳定的截止时间", () => {
    vi.useFakeTimers();
    vi.setSystemTime(new Date("2026-09-13T00:00:00Z"));
    expect(new Date().toISOString()).toBe("2026-09-13T00:00:00.000Z");
    vi.useRealTimers();
  });
});
```

**速记**：环境一致性来自版本文件、锁文件与可控时钟三件事，缺一项就可能复现出只在流水线发生的失败。



### 分片与并行

**分片（sharding）**：是把同一测试套件按规则切成若干互不重叠的子集、分散到多个执行单元上并发运行的做法，用于压缩大型套件的墙钟耗时。

#### 测试分片

**测试分片**：是把用例集合划分成固定份数并给每份编号，由执行者只运行其中一份。

- 命令行参数：Vitest 写作 --shard=<当前分片>/<总分片数>，如 --shard=2/4 表示运行第 2 份、共 4 份。
- 切分粒度：按测试文件顺序切分，单个文件不会跨分片拆开。
- 调度方式：用矩阵（matrix）为每个分片生成一个并发作业，各作业跑完后再聚合结果。
- 均衡性：单文件用例数悬殊时各分片耗时会有差异，可通过调整文件划分改善。

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx vitest run --shard=${{ matrix.shard }}/4
```

> 分片数不等于加速比。安装依赖与构建等公共开销在每个分片上都要重复一次，分片越多，公共开销占比越高。

**速记**：分片把文件按份数摊开并行跑，用矩阵生成作业，注意公共开销会抬高分片下限。



#### 并行执行的粒度

**并行执行的粒度**：指并发单元是文件、用例还是进程，粒度越细隔离成本越高。

- 文件级并行：Vitest 默认为每个测试文件分配独立的工作线程，文件之间并行、文件内部串行。
- 进程池选择：--pool=threads 使用工作线程，--pool=forks 使用子进程，后者隔离更彻底但启动更慢。
- 并发上限：--maxWorkers 与 --minWorkers 控制并发数量，流水线机器核心数少于本地时应下调。
- 用例级并发：同一文件内的用例默认串行，需要并发时用 test.concurrent 显式声明。

```bash
npx vitest run --pool=forks --maxWorkers=4
```

```ts
import { expect, test } from "vitest";

test.concurrent("并发执行的用例应各自返回结果", async () => {
  const value = await Promise.resolve(42);
  expect(value).toBe(42);
});
```

> 用例级并发只适合彼此独立、不共享可变状态的用例；共享同一临时文件或全局单例时，并发会引入随机失败。

**速记**：默认按文件并行、文件内串行，进程池与并发上限决定资源占用，用例级并发要显式开启。



#### 共享资源竞争

**共享资源竞争**：是多个并行执行单元同时读写同一资源（端口、临时目录、数据库、全局状态）而互相干扰的现象。

- 端口：需要绑定固定端口的服务在并行时会冲突，应改为申请随机空闲端口。
- 数据：多个分片写同一数据库时要用独立库名或独立 schema，并在结束时清理。
- 时间：依赖系统时间的用例在不同机器上会因时区差异偶发失败，应注入可控时钟。
- 随机值：断言依赖随机数时固定随机种子，或把随机来源替换为替身。
- 外部服务：并行调用同一测试账号或第三方沙箱会互相影响，应使用隔离的凭据与命名空间。

```ts
function pickTestPort(): number {
  return Number(process.env.TEST_PORT ?? 0);
}

console.log(pickTestPort()); // 0 表示由操作系统分配空闲端口
```

> [!WARNING]
> **警告内容**：偶发失败一旦被自动重跑掩盖，就失去了真实缺陷的信号。应先定位竞争原因，再把重跑作为临时缓解而非最终方案。

**速记**：并行的代价是资源竞争，端口、数据、时间、随机值四处隔离到位，偶发失败才会减少。



### 依赖与缓存加速

**依赖安装与缓存**：是流水线中耗时占比最高的两个环节，优化的核心是让重复工作只做一次，同时保证结果可复现。

#### 确定性安装

**确定性安装**：是不重新解析版本范围、严格按锁文件复原依赖树的安装方式，保证每次安装结果一致。

- npm：使用 npm ci，它依据 package-lock.json 精确安装，并要求锁文件与声明同步。
- pnpm：使用 pnpm install --frozen-lockfile，锁文件与声明不一致时直接失败。
- Yarn：使用 yarn install --immutable，语义与前者一致。
- 前提：安装前要确认 package.json 与锁文件都已提交，否则确定性安装会失败而不是让依赖悄悄漂移。

```bash
npm ci
# 依据 package-lock.json 精确复原依赖树

pnpm install --frozen-lockfile
# 锁文件过期时直接报错退出
```

> 确定性安装的价值在于可复现：同一个提交在任意机器上得到同一棵依赖树，避免只有某台机器失败的排查困境。

**速记**：CI 里用 npm ci 或 pnpm 的冻结锁文件安装，把可复现性放在速度之前。



#### 依赖缓存

**依赖缓存**：是把包管理器的下载与存储目录在多次流水线运行之间复用，跳过重复下载的机制。

- 缓存对象：npm 的缓存目录、pnpm 的存储目录，而不是 node_modules 本身。
- 缓存键：应包含操作系统、语言版本与锁文件哈希，锁文件变化时自动失效。
- 命中回退：缓存未命中时流水线仍应正常安装，缓存只加速而不承担正确性。
- 内置能力：setup-node 提供 cache 选项，可直接按包管理器类型开启缓存，无需手写缓存步骤。
- 失效排查：缓存越用越慢通常是键过粗导致命中错误内容，应收紧键的定义。

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: pnpm
- uses: pnpm/action-setup@v4
  with:
    version: 9
- run: pnpm install --frozen-lockfile
```

> 键里包含锁文件哈希后，依赖未变则命中、依赖一变则重建，速度与正确性可以同时满足。

> 缓存键不要只写分支名。分支名频繁变化会导致缓存反复未命中，反而拖慢每一次运行。

**速记**：缓存包管理器目录并用锁文件哈希做键，命中只是加速，未命中也必须能正常安装。



#### 构建产物与运行期缓存

**构建产物缓存**：是把构建输出在运行之间复用的做法，其收益大，风险也高于依赖缓存。

- 键要覆盖源码：缓存构建产物时，键必须包含源码哈希，否则会复用与当前提交不符的过期产物。
- 预构建目录：Vite 在 node_modules/.vite 下的预构建缓存在依赖变化后需要重建，不宜跨依赖变更复用。
- 作业依赖：测试若依赖上一步骤产出的构建物，应显式声明作业顺序，避免读到残缺产物。
- 度量优先：先测量各阶段耗时再决定缓存对象，安装与构建通常排在前两位。

```bash
# 先量出各阶段耗时，再决定缓存哪一段
time npm ci
time npx vitest run
```

> 缓存不是越宽越好。把源码产物一并缓存会让过期产物难以察觉，宁可少缓存也不要错误命中。

**速记**：构建产物缓存的键必须覆盖源码，缓存不到时可回退，宁可慢一点也不能读到过期产物。



### 失败诊断与报告归档

**失败诊断**：是从运行器输出中定位失败原因并留下可复现证据的过程，诊断效率直接决定流水线的可信度。

#### 失败日志与重跑策略

**失败日志**：是测试运行器在用例失败时输出的错误类型、消息与调用栈，是诊断的第一手材料。

- 打印完整：流水线中不要截断输出，必要时提高日志级别以保留失败用例的上下游信息。
- 阅读顺序：先读错误类型与消息，再读调用栈中属于本项目的帧。
- 自动重跑：用 --retry=2 对失败用例重试，用于区分偶发失败与稳定失败，次数不宜过多。
- 禁止掩盖：重跑成功不代表问题消失，应把偶发失败单独记录并安排排查。
- 失败隔离：用 --bail 控制失败后的停止行为，快速反馈与完整报告按场景取舍。

```bash
npx vitest run --retry=2
# 失败用例自动重试，偶发失败被稀释，需配合日志确认
```

```text
FAIL  src/total.spec.ts > total 在输入为空数组时应返回 0
AssertionError: expected 1 to be 0
 ❯ src/total.spec.ts:12:20
```

> 重跑只用于区分偶发与稳定两类失败。稳定失败不会因重跑而消失，反而消耗流水线时间。

**速记**：日志读全栈、定位到本项目帧，重跑只用于识别偶发失败而不能当成修复。



#### 报告格式与查看

**测试报告**：是把用例结果结构化为机器可读文件的输出，常见格式为 JUnit XML 与 JSON。

- JUnit XML：代码托管平台与 CI 平台的测试结果面板普遍支持，便于按用例查看历史与耗时。
- JSON：字段最全，适合二次加工与自建看板。
- 指定方式：Vitest 用 --reporter 指定格式，用 --outputFile 指定落盘路径。
- 多格式：需要同时给人看和给机器看时，可同时开启默认报告器与结构化报告器。

```bash
npx vitest run --reporter=default --reporter=junit --outputFile=reports/junit.xml
```

```yaml
- run: npx vitest run --reporter=junit --outputFile=reports/junit.xml
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: test-report
    path: reports/
```

> [!IMPORTANT]
> **重要内容**：上传报告的步骤必须使用 if: always()，否则测试失败时后续步骤会被跳过，最需要报告的场合反而拿不到报告。

**速记**：结构化报告交给平台面板看趋势，用 upload-artifact 归档，且上传步骤要无条件执行。



#### 失败证据归档

**失败证据**：是失败时的截图、视频、追踪文件与覆盖率产物，用于在没有人工复现的条件下还原现场。

- 截图与视频：端到端测试失败时保留截图、视频与追踪文件，作为复现依据（详见本主题第 13 篇 端到端测试：Playwright）。
- 覆盖率产物：覆盖率报告与测试报告一并归档，便于对比历史变化。
- 保留周期：按存储配额设置保留天数，失败记录保留得更久一些。
- 命名可检索：产物名包含提交标识与作业名，便于按提交定位具体一次运行。
- 触发条件：取证步骤应区分失败时归档与始终归档两类，避免无意义占用配额。

```yaml
- name: 归档失败证据
  if: failure()
  uses: actions/upload-artifact@v4
  with:
    name: failure-evidence
    path:
      - test-results/
      - coverage/
    retention-days: 7
```

> 产物归档的意义在于缩短平均修复时间。没有证据时，失败只能靠反复重跑与猜测定位。

**速记**：失败时自动归档截图、报告与追踪文件，按提交命名并设置保留期，让问题可回溯。



### 质量门禁与合并前检查

**质量门禁（quality gate）**：是合并请求必须满足的一组自动化检查，未全部通过则不允许合并，用于把缺陷挡在主干之外。

#### 门禁项设计

**门禁项**：是纳入流水线的检查条目及其执行顺序，设计目标是尽早失败、避免无效等待。

- 基础三项：单元测试、类型检查、静态检查是多数前端项目的必跑项。
- 顺序：快检查放前面以尽早失败，慢检查放后面，减少等待时长。
- 单一事实来源：命令写进 package.json 的 scripts，本地与流水线执行同一条命令。
- 路径过滤：与本次改动无关的重型检查可按路径过滤，但默认应保守，宁可多跑。
- 超时上限：为作业设置 timeout-minutes，防止挂起占用执行器。

```json
{
  "scripts": {
    "test": "vitest run",
    "test:ci": "vitest run --reporter=junit --outputFile=reports/junit.xml",
    "typecheck": "tsc --noEmit",
    "lint": "eslint ."
  }
}
```

> 门禁命令必须与本地一致。若流水线执行的是另一套命令，本地通过就失去意义（详见 前端/构建工具 主题第 13 篇 ESLint 与 Prettier：代码规范工具链）。

**速记**：门禁项按快慢排序、命令与本地共用同一份脚本，并为作业设置超时上限。



#### 覆盖率门禁

**覆盖率门禁**：是把代码覆盖率阈值写进配置、未达阈值即判定失败的做法。

- 四种指标：语句、分支、函数、行，阈值应逐项设置而非只看总行数。
- 作用域：让阈值只对本次改动涉及的文件生效最有针对性，全量阈值容易被历史欠账长期拖住。
- 棘轮策略：阈值只升不降，允许逐步提高而不要求一步到位。
- 使用边界：覆盖率高低不等于测试质量，不能作为唯一门禁（详见本主题第 12 篇 覆盖率与测试报告）。

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      thresholds: {
        statements: 80,
        branches: 70,
        functions: 80,
        lines: 80,
      },
    },
  },
});
```

> 覆盖率跌破阈值时先判断是新增代码未测还是统计范围扩大，前者补测试，后者修正统计的包含与排除范围。

> [!WARNING]
> **警告内容**：不要为了让门禁通过而排除难测文件或写入无断言的用例，这会让覆盖率数字失去参考价值。

**速记**：覆盖率门禁逐项设阈值，优先约束本次改动的文件，且阈值只升不降。



#### 合并前检查与分支保护

**分支保护（branch protection）**：是代码托管平台针对目标分支设置的规则，要求指名的检查全部通过才允许合并。

- 必需检查：把测试作业声明为必需状态检查，未通过时合并按钮不可用。
- 最新提交：要求检查针对最新提交运行，避免用旧结果去合并新代码。
- 并发取消：同一分支连续推送时取消上一次运行，节省执行器资源。
- 人工复核：自动化门禁不替代代码评审，两者并行，各管一面。
- 合并队列：多人同时提交时按队列逐个验证，避免各自通过、合起来失败的集成问题。

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run test:ci
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: test-report
          path: reports/
```

> [!NOTE]
> **提醒内容**：务必为作业设置 timeout-minutes 上限。测试挂起时若无超时，作业会占用执行器直到平台默认上限，拖慢整个队列。

**速记**：把测试设为必需状态检查、只认最新提交的结果，并用并发取消与合并队列控制资源与集成风险。
