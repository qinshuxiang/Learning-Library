## 测试工具链与运行器选型

**测试工具链**：是围绕「发现用例、判断结果、替换依赖、统计覆盖」四件事组装起来的一整套工具。本篇只做分工梳理与横向对比，给出选型的判断依据，不写任何工具的完整配置；各工具的具体用法分别归后续篇目。

### 运行器与断言库与替身库的分工

本模块先拆开工具链的四个角色，回答「每类工具负责什么、哪些可以互相替换」。

#### 测试运行器

**测试运行器（test runner）**：是负责发现用例文件、执行用例、汇总结果并决定进程退出码的程序。

- 发现：按命名约定或配置扫描测试文件，收集其中注册的用例。
- 调度：控制用例的执行顺序、并发数量与超时上限。
- 汇总：统计通过、失败、跳过与耗时，并在失败时输出详情。
- 决策：以退出码表达整体结果，供命令链与流水线判断。

```bash
# 运行器是测试入口的三种典型形态
npx jest
npx vitest run
node --test
```

**速记**：运行器负责发现、调度、汇总与退出码，是整条链的入口。



#### 断言库

**断言库（assertion library）**：是提供断言语句的库，负责把预期写成可执行判断，并在失败时生成可读信息。

- 两种风格：内置函数式断言（如 node:assert）与链式 expect 风格断言（如 Jest、Vitest 内置）。
- 职责边界：只判断值与关系、只报告差异，不负责发现与调度用例。
- 可替换：同一运行器往往可以搭配不同断言库，风格差异会直接影响用例可读性。
- 失败信息：断言库决定报告中给出多少上下文，直接影响排查速度。

```js
import assert from "node:assert/strict";

function normalizeTitle(title) {
  return title.trim().toLowerCase();
}

assert.equal(normalizeTitle("  Hello World  "), "hello world");
console.log("断言通过"); // 断言通过
```

**速记**：断言库只管判断与报告，风格分为函数式与链式两类。



#### 测试替身库

**测试替身库（test double library）**：是提供模拟、桩与侦测能力的库，用于替换被测代码所依赖的对象或模块。

- 替换对象：把外部函数换成可控的假实现，并记录调用参数与次数。
- 替换模块：按模块路径整体替换，常用于隔离网络请求与存储读写。
- 常见来源：Vitest 提供 vi 对象，Jest 提供 jest 对象，sinon 可独立接入 Mocha 等运行器。
- 与断言的关系：替身负责「换成假的并记录」，断言负责「检查调用是否符合预期」。

```js
// 假实现的可控性：返回值由用例决定
function createFakeClock(fixedNow) {
  return { now: () => fixedNow };
}

const clock = createFakeClock(1700000000000);
console.log(clock.now()); // 1700000000000
```

**速记**：替身库负责换成假对象并记录调用，断言负责检查记录。



#### 覆盖率与报告工具

**代码覆盖率（code coverage）**：是统计测试执行时源代码被触达比例的一组指标。**覆盖率采集器**：是生成该统计的工具，常见实现有 v8 与 istanbul 两类。

- 采集对象：语句、分支、函数与行四个维度。
- 报告格式：终端文本用于快速查看，HTML 用于逐行定位，lcov 用于外部平台展示。
- 接入方式：多数运行器内置采集开关，也可通过插件引入。
- 定位：覆盖率是辅助指标，说明「哪些代码没被跑到」，不代表「跑到的代码都对」。

```bash
# 覆盖率通常作为独立命令运行，而非每次调试都开
npx vitest run --coverage
npx jest --coverage
node --test --experimental-test-coverage
```

**速记**：覆盖率采集器统计语句、分支、函数与行的触达比例，仅是辅助指标。



### Jest 与 Vitest 与 Mocha 与 node:test 对比

本模块按「一体化程度、模块兼容、启动速度、生态与上手成本」四条线索对比四个主流运行器。

#### Jest

**Jest**：是 Meta 维护的一体化测试框架，内置运行器、断言、测试替身与覆盖率采集，安装一个包即可开始写用例。

- 一体化：断言、替身、覆盖率开箱可用，减少拼装工作。
- 生态：出现最早，社区插件、框架适配与迁移资料最丰富。
- 模块加载：基于自有模块解析与转换，对原生 ESM 需要额外配置。
- 成本：首次启动要完成依赖图转换，大型项目冷启动明显偏慢。

```bash
npm install --save-dev jest
npx jest
# PASS  test/format-price.test.js
# Tests: 3 passed, 3 total
```

**速记**：Jest 一体化程度最高、生态最厚，代价是启动偏慢与 ESM 需配置。



#### Vitest

**Vitest**：是基于 Vite 的测试框架，复用 Vite 的转换与解析管线，原生支持 ESM 与 TypeScript。

- 与构建同源：可直接读取构建配置中的别名、插件与转换规则，避免两份定义。
- 速度：按需转换加监听重跑，开发期反馈快。
- API 兼容：expect 风格断言与设备替身 API 接近 Jest，迁移改写量小。
- 前提：项目本身使用 Vite 时收益最大，否则需要自行补齐转换链路。

```bash
npm install --save-dev vitest
npx vitest run
# ✓ test/format-price.test.js (3)
# Tests  3 passed (3)
```

**速记**：Vitest 复用 Vite 管线，原生 ESM 与 TypeScript，且迁移成本低。



#### Mocha

**Mocha**：是早期流行的测试运行器，只提供用例组织与执行调度，断言、替身与覆盖率需要自行搭配。

- 组装式：断言常用 chai 或 node:assert，替身常用 sinon，覆盖率另有采集器。
- 灵活：不绑定模块格式与构建工具，能与多种老项目共存。
- 配置负担：需要自行维护多条依赖及其版本兼容。
- 现状：新项目采用率下降，历史项目与部分服务端项目仍在使用。

```bash
npm install --save-dev mocha chai sinon
npx mocha "test/**/*.test.js"
# 3 passing (12ms)
```

**速记**：Mocha 只做运行与组织，断言与替身靠自组装，灵活但配置多。



#### node:test

**node:test**：是 Node.js 内置的测试运行器模块，自 Node 18 起稳定可用，无需安装任何第三方依赖。

- 零依赖：随 Node 版本提供，测试依赖不进入依赖树与锁文件。
- 能力范围：提供用例注册、套件分组、并发、超时与监视模式。
- 断言来源：配合内置的 node:assert 使用，无独立断言风格。
- 局限：不含测试替身与组件测试能力，浏览器环境需另行处理。

```bash
node --test
# ✔ normalizeTitle 在含首尾空格输入下应返回小写结果 (0.6ms)
# tests 1
# pass 1
```

**速记**：node:test 零依赖、随 Node 提供，能力基础但不含替身与浏览器支持。



### 与构建工具的衔接

本模块回答「运行器如何复用构建期的转换与解析规则」，以及不一致时会出什么问题。

#### 转译管线

**转译管线**：是测试运行前把 TypeScript、JSX 与新语法转成可执行 JavaScript 的处理链。

- 复用方案：Vitest 直接使用 Vite 的插件与转换，测试与构建行为一致。
- 独立方案：Jest 通过 babel-jest 或 ts-jest 单独配置转译。
- 取舍：复用减少重复配置，独立方案可控但容易与构建产物行为分叉。
- 校验点：转换目标语法若与构建不一致，测试可能通过而线上报错。

```bash
# 独立转译方案需要额外安装转译器
npm install --save-dev babel-jest @babel/preset-typescript
npx jest
# PASS  test/greet.test.ts
```

**速记**：转译管线可复用构建工具的插件，也可独立配置，但两者必须对齐。



#### 模块格式与解析

**模块解析**：是运行器把 import 或 require 说明符映射到真实文件的过程。

- 格式互操作：ESM 与 CommonJS 的混用是测试配置最常见的出错点。
- 路径别名：别名必须在测试侧同步声明，否则解析失败直接报找不到模块。
- 条件导出：前端包常按 browser 或 development 条件导出不同入口，运行器需对齐。
- 排查口径：解析失败先比对测试配置与构建配置的解析字段是否一致。

```bash
npx jest
#  FAIL  test/api-client.test.js
#  Cannot find module '@/utils/request' from 'api-client.test.js'
# 提示：该别名只在构建配置中声明，测试配置未同步
```

**速记**：别名与模块格式必须在测试配置中同步，否则解析直接失败。



#### 与 Vite 共享配置

**配置共享**：是让测试运行器读取同一份构建配置，避免别名、插件与环境变量出现两份定义。

- 做法：在测试配置中引用构建配置并合并，测试专用项单独追加。
- 收益：别名与插件只维护一份，测试与构建的行为保持一致。
- 边界：超时、环境、覆盖率等测试专属选项仍写在测试侧。
- 前提：项目本身使用 Vite，否则没有可复用的配置来源。

```js
// 测试配置引用构建配置的思路（示意，不含完整选项）
import { defineConfig } from "vitest/config";
import viteConfig from "./vite.config.js";

export default defineConfig({
  resolve: viteConfig.resolve,
});
```

**速记**：共享构建配置让别名与插件只维护一份，测试专属项仍留在测试侧。



#### 与 TypeScript 的衔接

**类型衔接**：是让测试代码享受类型检查、同时保持执行速度的配置方式。

- 两条路径：执行前只剥离类型，或执行前做一次完整类型检查。
- 常见做法：运行器只剥离类型，类型检查交给独立的类型检查命令。
- 开销：全量类型检查慢，不适合放进每次监听重跑。
- 报告分离：类型错误与测试失败是两类信号，分开报告更容易定位。

```bash
# 执行与类型检查分成两条命令
npx vitest run
npx tsc --noEmit
# src/cart.ts:12:5 - error TS2322: 类型 string 不能赋给类型 number
```

**速记**：运行器只剥类型求快，类型检查交给独立的类型检查命令。



### 选型考量

本模块给出四条可逐项打分的判断依据，用于在多个可行方案间确定取舍。

#### 启动与运行速度

**启动速度**：是运行器从命令执行到第一条用例开始运行之间的耗时，受模块转换方式与依赖图规模影响。

- 冷启动：一体化框架通常更慢，基于原生 ESM 的运行器更快。
- 监听重跑：只重跑受影响文件的能力，决定开发期的反馈节奏。
- 整体时长：并行、分片与缓存策略决定全量运行的墙钟时间。
- 度量口径：以项目真实规模下的冷启动耗时与全量耗时为准，不用小程序样本。

```bash
# 以真实仓库为基准测量冷启动与全量耗时
time npx vitest run
time npx jest
```

**速记**：速度要按真实规模的冷启动与全量耗时度量，不看小样本。



#### 生态与插件

**生态成熟度**：是围绕运行器可用的文档、插件、框架适配与社区答疑的总和。

- 框架适配：组件测试、路由与状态库的集成支持是否现成。
- 插件覆盖：覆盖率、报告格式、流水线适配是否已有官方或社区实现。
- 迁移资料：从其他运行器迁移的对照说明与兼容 API 是否完整。
- 风险：小众方案出问题时可参考的经验少，排查更依赖自身。

```bash
# 生态适配通常体现为一组可安装的配套包
npm install --save-dev @vue/test-utils jsdom @vitest/coverage-v8
```

**速记**：生态看框架适配、插件覆盖与迁移资料，小众方案排查成本更高。



#### 团队熟悉度与迁移成本

**迁移成本**：是把既有测试与配置改到新运行器所需的工作量，含 API 差异、配置差异与用例改写。

- API 差异：expect 风格接近时改写量小，运行器专有 API 需逐个替换。
- 配置差异：别名、转译、环境模拟与全局注入都要重新搭建。
- 并行阶段：新旧运行器可短期并存，按目录逐步迁移以缩小单次风险。
- 决策口径：没有明显收益时优先复用团队已经熟悉的方案。

```bash
# 迁移期两套运行器并存，脚本中分别暴露
npm run test:legacy
npm run test:next
```

**速记**：迁移成本看 API 与配置差异，无明显收益时优先选熟悉的方案。



#### 稳定性与维护状态

**维护状态**：是项目最近的发布节奏、问题响应速度与对运行时新版本的跟进情况。

- 活跃度：近期是否有稳定版本发布与安全修复。
- 兼容跟进：是否随 Node 版本、模块标准与语言新特性同步更新。
- 锁定风险：依赖单一维护者的方案需要评估替代路径与退出成本。
- 长期支持：企业项目应确认关键依赖有明确的支持周期。

> [!IMPORTANT]
> **重要内容**：选型前确认运行器对当前 Node 版本与模块格式的官方支持状态，避免选中已停止跟进标准变化的方案。

**速记**：维护状态看发布节奏、兼容跟进与锁定风险，避免选停止跟进的方案。



### 常见组合方案

本模块给出三类项目的可落地组合，以及组合之间的取舍口径。

#### 新项目主流组合

**新项目组合**：是使用 Vite 与现代模块体系的项目的默认搭配，通常以 Vitest 为核心，断言与替身使用其内置能力。

- 运行器：Vitest，与构建配置共享别名与插件。
- 断言与替身：直接使用内置能力，不额外引入断言库与替身库。
- 组件测试：配合框架专用测试工具与所需的浏览器环境模拟。
- 端到端：由独立的端到端工具承担，不混入单元测试配置。

```bash
npm install --save-dev vitest jsdom @vue/test-utils
npx vitest run
# Test Files  4 passed (4)
```

**速记**：新项目以 Vitest 加内置断言与替身为主，端到端另用独立工具。



#### 库与工具包组合

**库与工具包组合**：是发布到 npm、需要广兼容的项目的搭配，优先选择零依赖且贴近标准的方案。

- 运行器：node:test 或 Vitest，前者零依赖、后者能力更全。
- 断言：node:assert 或内置 expect 风格断言。
- 目标：测试依赖不进入发布产物的依赖树，且能在多个 Node 版本上运行。
- 版本矩阵：在流水线中按 Node 版本分别运行同一套用例。

```json
{
  "scripts": {
    "test": "node --test"
  },
  "engines": {
    "node": ">=18"
  }
}
```

**速记**：库与工具包优先零依赖方案，并在多版本 Node 上跑同一套用例。



#### 遗留项目渐进方案

**遗留项目方案**：是在既有 Jest 或 Mocha 测试之上分阶段引入新能力的做法，不追求一次性重写。

- 保留存量：既有用例与配置维持原状，避免迁移期同时引入功能改动。
- 增量迁移：新目录使用新运行器，旧目录继续用旧运行器。
- 报告统一：两套结果汇入同一份流水线报告，保证质量门禁口径一致。
- 收敛终点：存量用例迁移完成后移除旧运行器与相关依赖。

```bash
# 渐进期同时保留两套入口，按目录区分范围
npm run test:legacy -- test/legacy
npm run test:next -- src/features
```

**速记**：遗留项目按目录增量迁移，新旧并存且汇报统一，最后移除旧运行器。



#### 组合的取舍

**组合取舍**：是在「一体化便利」与「组装式可控」之间按项目约束做出的选择。

- 一体化：上手快、配置少、各部分默认对齐，但替换其中一环较难。
- 组装式：每部分可单独替换，但依赖更多，版本兼容需要自行维护。
- 一致优先：同一仓库内尽量只保留一套运行器与一种断言风格。
- 可逆性：在能力相当的前提下，优先选择迁移路径更清晰的方案。

> [!TIP]
> **建议内容**：先把断言风格与测试目录约定固定下来，运行器与配套小工具都可在后续按需要替换。

**速记**：按一体化与组装式各自的代价取舍，同一仓库只保留一套主链路。
