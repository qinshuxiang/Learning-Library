## 测试质量与反模式

### 好测试的标准

用例数量与覆盖率数字都不能直接代表质量，真正决定收益的是测试能否稳定给出可信结论。本节给出三条可判定的标准，后续的脆弱成因都由此推导。

#### 测试可靠且可重复

**可靠（reliable）**：指同一份代码在任意机器、任意时间、任意执行顺序下运行同一批用例，结果保持一致。

- 无外部依赖：不访问真实第三方服务与共享数据库，改用夹具或本地替身。
- 无顺序依赖：任意单独运行一条用例都应当通过。
- 结果确定：固定输入产生固定输出，不受本机时区、语言与缓存影响。

```ts
// 反例：直接访问真实外网，网络抖动就会失败
// test("应展示首页标题", async ({ page }) => {
//   await page.goto("https://example.com");
//   await expect(page.getByRole("heading")).toHaveText("Example Domain");
// });

// 正例：拦截网络请求并返回固定数据
test("应展示首页标题", async ({ page }) => {
  await page.route("**/api/title", (route) => route.fulfill({ json: { title: "学习库" } }));
  await page.goto("/");
  await expect(page.getByRole("heading", { level: 1 })).toHaveText("学习库");
});
```

> 可靠性优先于覆盖率：一条偶发失败的用例会消耗全部成员的排查时间，代价高于它覆盖的那几行代码。

**速记**：可靠意味着换机器、换时间、单独运行都能得到同样结果。



#### 测试快速且相互独立

**独立（independent）**：指用例之间不共享可变状态，执行顺序与并行度都不影响结果。

- 自建数据：在 beforeEach 中准备，在 afterEach 中清理。
- 禁共享变量：模块级变量在并行执行时会被其他用例改写。
- 分层控时：单元测试按毫秒、集成测试按秒、端到端测试只保留关键路径。

```ts
test.describe("购物车", () => {
  let cartItems: string[];

  // 反例：把 cartItems 声明在 describe 之外，多个用例会互相污染
  // let cartItems: string[] = [];

  test.beforeEach(() => {
    cartItems = [];
  });

  test("加入一件商品后长度应为一", () => {
    cartItems.push("咖啡豆");
    expect(cartItems).toHaveLength(1);
  });

  test("未操作时长度应为零", () => {
    expect(cartItems).toHaveLength(0);
  });
});
```

**速记**：独立要求用例自建自清数据，不靠执行顺序传递状态。



#### 测试可读且失败可诊断

**可诊断（diagnosable）**：指用例失败时，报告中的信息足以直接指出失败步骤、预期值与实际值。

- 断言具体：报告里带上实际值与预期值，而不是布尔比较的结果。
- 单一失败点：一条用例失败只指向一个行为，排查范围小。
- 组织清晰：describe 与用例标题构成一条可读路径。

```ts
// 反例：失败时只能看到 false 不等于 true
// expect(items.length > 0).toBe(true);

// 正例：失败信息给出实际数量与预期数量
expect(items).toHaveLength(2);
```

> [!IMPORTANT]
> **重要内容**：覆盖率是观察指标而不是目标，把覆盖率阈值当作唯一验收标准会催生大量无断言或重复断言的用例。

**速记**：好用例失败时报告本身就能说明问题出在哪一步。



### 三段式结构与命名

结构决定用例能否被快速读懂，命名决定失败时能否被快速定位。本节给出三段式结构、标题写法与用例粒度的统一口径。

#### 三段式结构的写法

**三段式结构（arrange-act-assert）**：是把一条用例拆成准备、执行、断言三段，用空行分隔，每段只做一件事。

- 准备段：构造输入、替身与被测对象。
- 执行段：触发被测行为，通常只有一行。
- 断言段：验证结果，断言集中放在最后。
- 例外情形：需要验证中间状态时允许在执行过程中插入断言，但仍应保持段落分明。

```ts
type Order = { items: Array<{ price: number; count: number }> };

function calcSubtotal(order: Order): number {
  return order.items.reduce((sum, item) => sum + item.price * item.count, 0);
}

function calcShippingFee(order: Order): number {
  return calcSubtotal(order) >= 199 ? 0 : 12;
}

test("订单满 199 元时应免运费", () => {
  // 准备
  const order: Order = { items: [{ price: 199, count: 1 }] };

  // 执行
  const shippingFee = calcShippingFee(order);

  // 断言
  expect(shippingFee).toBe(0);
});
```

**速记**：三段式让准备、执行、断言各归其位，执行段只留一行。



#### 用例标题的命名

**用例标题**：是一句中文陈述，说明在什么场景下应当得到什么结果，读标题即可判断覆盖了哪条需求。

- 句式：场景在前、预期在后，用「应」连接。
- 写业务结果：标题描述调用方或用户看到的结果，不描述调用了哪个函数。
- 避免笼统：测试运费计算这类写法无法说明覆盖范围与预期。

```ts
// 反例：标题只说明被测对象，看不出预期
// test("测试运费计算", () => {
//   expect(calcShippingFee(order)).toBe(12);
// });

// 正例：场景与预期都在标题里
test("订单金额不足 199 元时应收取 12 元运费", () => {
  const order: Order = { items: [{ price: 100, count: 1 }] };
  expect(calcShippingFee(order)).toBe(12);
});
```

> 同一行为的多组输入不必写成标题雷同的多条用例，可用循环生成并在标题中带上参数。

```ts
const cases = [
  { subtotal: 99, expected: 12 },
  { subtotal: 199, expected: 0 },
  { subtotal: 500, expected: 0 },
];

for (const { subtotal, expected } of cases) {
  test(`订单金额 ${subtotal} 元时运费应为 ${expected} 元`, () => {
    const order: Order = { items: [{ price: subtotal, count: 1 }] };
    expect(calcShippingFee(order)).toBe(expected);
  });
}
```

**速记**：标题写清场景与预期，读标题就能判断覆盖了什么需求。



#### 一个用例只验证一个行为

**一个用例一个行为**：指单条用例只触发一次被测行为，失败时不需要猜测问题出在哪一处。

- 失败定位：断言越聚焦，失败原因越明确。
- 参数化替代：同类场景用循环生成多条用例，而不是堆在一条用例里。
- 合理例外：同一次执行可以对应多条断言，只要它们验证同一行为的不同侧面。

```ts
test("登录成功后应跳转并写入会话 Cookie", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("用户名").fill("ada");
  await page.getByLabel("密码").fill("secret");
  await page.getByRole("button", { name: "登录" }).click();

  await expect(page).toHaveURL(/\/cart/);
  await expect(page.context().cookies()).resolves.toEqual(
    expect.arrayContaining([expect.objectContaining({ name: "session" })]),
  );
});
```

**速记**：一个用例一个行为，多个侧面共享一次执行但断言聚焦。



### 脆弱测试的成因

脆弱测试的特征是行为没变而测试失败。本节拆解三类最常见成因：耦合实现、耦合时间与随机源、耦合共享状态与外部环境。

#### 依赖实现细节

**实现细节耦合**：指测试断言了内部调用顺序、私有状态或 DOM 层级，这些内容随重构变化，而对外行为并未改变。

- 断言调用次数：验证内部协作次数，重构后行为不变也会失败。
- 断言 DOM 层级：依赖正斜杠链条的 CSS 选择器，布局微调即失效。
- 替代做法：断言对外可见的输出与副作用。

```ts
function sumWithLog(values: number[], log: (value: number) => void): number {
  return values.reduce((sum, value) => {
    log(value);
    return sum + value;
  }, 0);
}

test("三个数相加应等于六", () => {
  // 反例：断言内部回调的调用顺序，与求和结果无关
  // const visited: number[] = [];
  // sumWithLog([1, 2, 3], (value) => visited.push(value));
  // expect(visited).toEqual([1, 2, 3]);

  // 正例：只断言返回值
  const total = sumWithLog([1, 2, 3], () => {});
  expect(total).toBe(6);
});
```

**速记**：脆弱测试常源于断言实现路径，而不是对外行为。



#### 依赖时间与随机数

**时间与随机依赖**：指测试结果受当前时间、时区或随机值影响，同一份代码在不同时刻会得到不同结论。

- 时间来源：直接读取当前时间，跨零点或换时区运行会改变预期。
- 随机来源：随机数与随机标识生成的值不可复现。
- 控制手段：把时间与随机源作为参数注入，测试中传入固定值。
- 工具手段：用假定时器推进时间，详见本主题第 9 篇 异步测试与定时器控制。

```ts
type Token = { expiresAt: number };

// 反例：内部直接读取当前时间，结果不可复现
// function isExpired(token: Token): boolean {
//   return token.expiresAt < Date.now();
// }

// 正例：当前时刻由调用方传入
function isExpired(token: Token, now: number): boolean {
  return token.expiresAt < now;
}

test("过期时间早于当前时刻时应判定为已过期", () => {
  const token: Token = { expiresAt: 1_700_000_000_000 };
  expect(isExpired(token, 1_800_000_000_000)).toBe(true);
});
```

**速记**：把时间与随机源变成可传入的依赖，用例才能给出固定预期。



#### 依赖共享状态与外部环境

**共享状态**：指多条用例或多轮运行共同读写同一份数据，结果取决于执行顺序与残留数据。

- 数据残留：上一轮插入的记录影响本轮断言的数量。
- 全局单例：模块级缓存跨用例存活，清理不彻底会污染后续用例。
- 外部服务：真实第三方接口的限流与波动直接变成测试失败。

```ts
// 反例：依赖前一条用例先写入数据，单独运行必然失败
// test("待办列表应显示两条", async ({ page }) => {
//   await page.goto("/todos");
//   await expect(page.getByRole("listitem")).toHaveCount(2);
// });

// 正例：用例自己准备数据
test("添加两条待办后应显示两条", async ({ page }) => {
  await page.goto("/todos");
  await page.getByLabel("新待办").fill("写测试");
  await page.getByRole("button", { name: "添加" }).click();
  await page.getByLabel("新待办").fill("跑测试");
  await page.getByRole("button", { name: "添加" }).click();

  await expect(page.getByRole("listitem")).toHaveCount(2);
});
```

> [!WARNING]
> **警告内容**：用例依赖执行顺序时，并行运行与随机排序都会触发随机失败，这类失败最难复现与定位。

**速记**：共享状态让用例互为前提，正确做法是每条用例自带数据。



### 过度替身与实现耦合

替身是隔离外部依赖的手段，一旦替身数量或替身断言超出必要范围，测试验证的对象就从业务逻辑变成替身约定。本节给出两类症状与对应的替代写法。

#### 替身过度的表现

**替身过度（over-mocking）**：指替身数量超过隔离外部依赖所需，测试实际验证的是替身之间的约定，而不是真实逻辑。

- 全量替换：被测模块的全部依赖都被替换，模块协作无从验证。
- 只断言调用：只确认依赖被调用过，不确认最终结果。
- 假阳性：替身契约与真实实现不一致时测试全绿，集成后立即报错。

```ts
// 反例：把纯计算依赖也换成替身，断言只剩替身的自证
// const spy = vi.fn().mockReturnValue(180);
// expect(spy).toHaveBeenCalled();

// 正例：只隔离外部 httpClient，计算部分使用真实实现
vi.mock("./httpClient", () => ({
  fetchPrice: vi.fn().mockResolvedValue(199),
}));

test("查到价格后应返回格式化金额", async () => {
  await expect(loadPriceLabel("sku-1")).resolves.toBe("￥199.00");
});
```

> 替身数量与协作紧密度成反比：模块之间联系越松，越适合用替身隔离，细节见本主题第 7 篇 测试替身：mock、stub 与 spy。

**速记**：替身只用于隔离外部依赖，纯逻辑使用真实实现。



#### 实现耦合的表现

**实现耦合**：指测试的通过与否取决于代码内部结构，重构内部实现而不改行为时测试也会失败。

- 侦测私有方法：对内部方法建立侦测并断言其被调用。
- 断言日志与顺序：把协作细节当成对外契约。
- 快照过大：整页快照包含大量无关结构，任何改动都要更新，更新即失去把关意义。

```ts
type Promotion = { subtotal: number; coupon?: { code: string; discount: number } };

function applyPromotion({ subtotal, coupon }: Promotion): number {
  if (!coupon) return subtotal;
  return Math.max(0, subtotal - coupon.discount);
}

test("使用优惠券后应从总额中扣减", () => {
  // 反例：断言内部方法被调用，与最终价格无关
  // const spy = vi.spyOn(pricing, "applyDiscount");
  // expect(spy).toHaveBeenCalled();

  // 正例：断言对外返回的价格
  expect(applyPromotion({ subtotal: 200, coupon: { code: "SAVE20", discount: 20 } })).toBe(180);
});
```

> 快照的作用是提示差异而不是判定对错，快照更新的评审口径详见本主题第 11 篇 快照测试与 DOM 断言。

> [!CAUTION]
> **注意内容**：快照更新命令会把当前输出直接写成新基线，若不逐条确认差异，快照会退化成永远通过的记录。

**速记**：实现耦合让测试成为重构阻力，断言应停留在对外契约。



#### 重构安全的测试写法

**重构安全**：指测试只依赖公开契约，内部实现替换后不需要修改测试。

- 从公共入口断言：调用导出函数或操作可见界面。
- 替身按契约准备：让替身返回符合契约的值，不约束调用次数与顺序。
- 集成优先：协作紧密的模块保留少量真实集成测试，减少替身带来的偏差。
- 边界清晰：对外契约用单元测试固定，跨模块协作交给集成测试。

```ts
test("无优惠券时金额应保持不变", () => {
  expect(applyPromotion({ subtotal: 200 })).toBe(200);
});

test("折扣大于总额时金额不应为负数", () => {
  expect(applyPromotion({ subtotal: 10, coupon: { code: "BIG", discount: 30 } })).toBe(0);
});
```

**速记**：重构安全的测试只认公开契约，实现怎么换都不必改动。



### 可维护性自查清单

把前述标准固化成提交前的固定动作，可以让测试质量不依赖个人经验。本节给出清单本身，以及触发测试重构的信号与收敛手段。

#### 提交前的自查清单

**自查清单**：是一组在提交测试代码之前逐条确认的检查项，把质量要求变成可执行动作。

- 可靠：连续运行三次结果一致，随机顺序下同样通过。
- 独立：单独运行任意一条用例都能通过。
- 可读：标题写清场景与预期，三段式分隔明显。
- 断言：断言对外可见的结果，失败信息能定位问题。
- 简洁：没有复制粘贴的准备代码，重复逻辑已抽成夹具。
- 范围：覆盖关键路径与边界条件，不以覆盖率数字为唯一目标。

```bash
# 连续三次运行，检验可重复性与相互独立性
npx playwright test --repeat-each=3
npx vitest run --sequence.shuffle

# 只运行与改动文件相关的用例，缩短本地反馈时间
npx vitest related src/cart/pricing.ts
```

**速记**：清单化自查把好测试的标准落到提交前的具体动作。



#### 测试重构的时机

**测试重构**：是在不改变覆盖目标的前提下，重新组织定位器、替身与夹具的过程。

- 触发信号：同一批断言连续多次因实现变更而修改；新增用例需要复制大段准备代码。
- 优先动作：抽取页面对象与夹具，把重复准备收敛到一处。
- 保持覆盖：重构前后用例数量与覆盖场景不变，先跑通再提交。
- 小步推进：每次只改一个文件，不做全库一次性重排。

```ts
// tests/fixtures.ts
import { test as base } from "@playwright/test";
import { LoginPage } from "./pages/LoginPage";

type Fixtures = { loginPage: LoginPage };

export const test = base.extend<Fixtures>({
  loginPage: async ({ page }, use) => {
    await use(new LoginPage(page));
  },
});

export { expect } from "@playwright/test";
```

> [!TIP]
> **建议内容**：把重复的准备逻辑抽成夹具之后，新增用例只需声明所需夹具名，用例长度与维护面同步下降。

**速记**：出现重复准备与频繁修改断言时重构测试，小步推进且覆盖不变。
