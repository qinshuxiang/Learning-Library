## 测试简介与测试体系

**测试（test）**：是对程序行为是否满足预期所做的检查，做法是给定输入、执行代码、再把实际结果与预期结果比对。**测试体系**：是按被测范围把测试划分为若干层次、并约定各层职责与配比的一套整体安排。本篇只建立体系框架，回答测试为什么存在、分成哪几层、各层解决什么问题，不展开任何工具的具体用法。

### 测试解决什么问题

本模块回答「不写测试要付出什么代价」，以及自动化测试相对手工验证改变了什么。

#### 手工验证的局限

**手工验证**：是由人按既定步骤操作程序、用肉眼核对输出是否符合预期的验证方式。

- 成本随改动次数线性上升：每次修改都要重走一遍全部检查步骤。
- 结果不稳定：不同人执行同一份步骤，结论可能不一致，边界输入容易被漏掉。
- 无持久留痕：步骤与结论停留在个人记忆或临时文档里，无法在后续变更中自动重放。
- 难以覆盖组合：参数、分支、状态的组合数量增长很快，人工逐个检查不现实。

```js
// 手工验证的典型形态：改一次、跑一次、看一眼
function calculateDiscount(price, rate) {
  return price * (1 - rate);
}

console.log(calculateDiscount(100, 0.2)); // 80
console.log(calculateDiscount(100, 0));   // 100
// 每次修改实现后，上面的每一行都要人工重跑并核对
```

**速记**：手工验证不可重放、结果不稳，改一次就要重跑一遍。



#### 自动化测试的定义

**自动化测试**：是把验证步骤写成可被程序重复执行的代码，由测试运行器统一调度并汇总结果。

- 可重复：同一份测试代码在任意机器、任意时间执行的结论一致。
- 可回归：改动之后重跑全部测试，就能发现旧功能是否被破坏。
- 可集成：测试结果可以接入流水线，作为合并与发布的判定条件。
- 有成本：编写与维护测试本身需要投入，且测试代码也可能写错。

```js
// 自动化形态：把预期写进代码，交给运行器判断
function calculateDiscount(price, rate) {
  return price * (1 - rate);
}

const actual = calculateDiscount(100, 0.2);
const expected = 80;
console.log(actual === expected); // true
// 断言失败时由运行器报告，不需要人工逐行核对
```

**速记**：自动化测试把验证写成代码，可重复执行、可自动判定失败。



#### 测试与调试的区别

**调试（debugging）**：是在已经观察到异常之后，定位并修复其成因的过程。**测试**：是在问题被线上发现之前，用可控输入主动暴露偏差的手段。

- 目标不同：测试追求「证明行为符合预期」，调试追求「找出为什么会这样」。
- 时机不同：测试在提交之前反复执行，调试只在需要定位问题时进行。
- 产物不同：测试的产物是留在仓库里的用例，调试的产物是修复补丁。
- 关系：测试失败往往会触发一次调试，但两者不能互相替代。

```js
function divideScore(total, count) {
  return total / count;
}

console.log(divideScore(10, 0)); // Infinity
// 测试先断言「除以 0 应给出明确结果」，调试才有清晰目标
```

**速记**：测试负责提前暴露偏差，调试负责事后定位成因。



#### 回归与信心

**回归（regression）**：指新增改动破坏了原本正常的功能，是长期项目最主要的一类缺陷来源。**回归测试**：是用来在每次改动后重新确认既有行为未被破坏的测试集合。

- 冻结既有行为：把当前正确行为固化成用例，后续改动一旦破坏就会被指出。
- 支撑重构：有测试兜底时，重构可以放心调整内部实现。
- 建立信心：测试通过是「本次改动没有破坏已知行为」的可核查证据，而不是「程序绝对正确」的证明。
- 存在边界：测试只能覆盖写出来的输入，未写到的分支依然可能出错。

> 测试提供的是「已知行为未被破坏」的信心，而不是「程序没有缺陷」的保证。

**速记**：回归测试把既有行为冻结起来，为改动与重构提供信心。



### 测试金字塔与分层

本模块给出分层模型，回答「测试应该按什么比例分布」。

#### 什么是测试金字塔

**测试金字塔（test pyramid）**：是由 Mike Cohn 提出的分层模型，把测试按范围由小到大排成底部宽、顶部窄的塔形，主张底层用例多、顶层用例少。

- 纵向含义：越往下，单个用例数量越多、执行越快、越稳定。
- 横向含义：越往上，被测范围越大，启动与执行成本越高。
- 核心主张：把大部分验证放在快速稳定的底层，用少量高层用例覆盖端到端链路。
- 定位：它是配比的经验参考，不是必须遵守的硬指标。

```js
// 分层配比示意：底部最宽，向上逐层收窄
// 单元测试      数量多、速度快、结论稳定
// 集成测试      数量居中
// 端到端测试    数量少、速度慢、成本高
const pyramidShape = ["unit", "integration", "e2e"];
console.log(pyramidShape.length); // 3
```

**速记**：测试金字塔主张底层用例多而快、顶层用例少而贵。



#### 金字塔的层数与比例

**层数**：通常取三层，即单元测试、集成测试、端到端测试；复杂系统可再细分为组件测试与服务测试。

- 单元测试：数量最多，通常占全部用例的大多数。
- 集成测试：数量居中，覆盖模块之间的协作。
- 端到端测试：数量最少，只覆盖最关键的用户链路。
- 比例不是定额：收益取决于系统结构，模块边界清晰时底层收益更高。

```js
// 分层配比的一种可用起点：单元多、集成中、端到端少
const layerPlan = { unit: 70, integration: 20, e2e: 10 };
console.log(layerPlan.unit); // 70
console.log(layerPlan.unit + layerPlan.integration + layerPlan.e2e); // 100
```

**速记**：三层分层，单元最多、集成居中、端到端最少，比例按系统调整。



#### 冰淇淋反模式

**冰淇淋反模式（ice cream cone）**：是把大量用例堆在端到端层、底层几乎没有测试的倒置结构，因形似倒置的甜筒而得名。

- 表现：端到端用例数量最多，单元测试几乎空缺。
- 后果：测试耗时长、失败原因难定位、轻微改动就大面积报错。
- 成因：端到端测试最贴近用户视角，写起来直观，容易成为唯一选择。
- 纠正路径：把可独立验证的逻辑逐步下沉为单元测试，端到端只保留关键链路。

> [!WARNING]
> **警告内容**：端到端用例占比过高会让测试套件又慢又脆，一旦失败往往需要人工分辨是产品缺陷还是测试自身不稳定。

**速记**：端到端堆得过多、底层空缺就是冰淇淋反模式，需要把验证下沉。



#### 分层的取舍依据

**分层取舍**：是依据「失败时能否快速定位」「执行成本是否可接受」「覆盖的是逻辑还是链路」三条来分配用例归属。

- 定位速度：底层失败直接指向某个函数，高层失败只能定位到一段流程。
- 执行成本：单元测试以毫秒计，端到端测试以秒计，还可能依赖网络与浏览器。
- 覆盖对象：纯计算逻辑放底层，跨模块协作放中层，真实用户路径放顶层。
- 稳定性：依赖越少越稳定，外部依赖越多越容易偶发失败。

```js
// 同一需求的分层归属判断
function isEligibleForFreeShipping(orderTotal, isMember) {
  return orderTotal >= 99 || isMember;
}

console.log(isEligibleForFreeShipping(120, false)); // true
// 该判定逻辑适合单元测试；下单到收货的完整流程才需要端到端测试
```

**速记**：按定位速度、执行成本、覆盖对象与稳定性决定用例落在哪一层。



### 单元与集成与端到端

本模块逐层展开三类测试的范围、依赖与适用场景。

#### 单元测试

**单元测试（unit test）**：是针对一个最小可验证单元（通常是单个函数或单个类）的测试，不启动网络、数据库与浏览器等外部依赖。

- 范围：一个函数、一个类，或一组强内聚的小逻辑。
- 依赖：外部依赖用测试替身替代，保证结论只反映被测单元。
- 速度：单条用例通常在毫秒级，上千条也能在秒级内完成。
- 价值：精确定位缺陷位置，是回归防护的主力层。

```js
// 被测单元：纯函数，无需任何外部环境
function formatPriceInCents(cents) {
  return `¥${(cents / 100).toFixed(2)}`;
}

console.log(formatPriceInCents(1999)); // "¥19.99"
console.log(formatPriceInCents(0));    // "¥0.00"
```

**速记**：单元测试隔离外部依赖，只验证一个最小单元，快且定位准。



#### 集成测试

**集成测试（integration test）**：是验证两个以上单元或模块协作时行为是否正确、接口是否对得上的测试。

- 范围：模块之间的调用、数据结构约定、真实依赖的接入。
- 依赖：允许使用真实数据库、真实文件系统或简化后的下游替身。
- 关注点：参数传递、数据格式、错误传播、事务与副作用。
- 与单元的差别：单元测试关心「这个函数算得对不对」，集成测试关心「它们拼起来对不对」。

```js
// 集成视角：查询函数与内存数据源的协作
const memoryStore = new Map([[1, { id: 1, name: "Ada Lovelace" }]]);

function findUserById(id) {
  return memoryStore.get(id);
}

console.log(findUserById(1)); // { id: 1, name: "Ada Lovelace" }
console.log(findUserById(2)); // undefined
```

**速记**：集成测试验证多个模块拼起来是否对得上，允许接真实依赖。



#### 端到端测试

**端到端测试（end-to-end test）**：是从用户入口出发、走完整个真实链路的测试，通常由浏览器或接口客户端驱动完整系统。

- 范围：从界面操作或接口请求开始，到数据落库、页面更新为止。
- 依赖：真实的前端、后端、数据库与网络链路。
- 数量：只覆盖登录、下单、支付等最关键的核心路径。
- 代价：执行慢、易受环境影响、失败时定位成本高。

> 端到端测试验证的是「整条链路通不通」，而不是某个逻辑分支对不对，因此不追求覆盖率。

**速记**：端到端测试从用户入口走完真实链路，覆盖核心路径，慢且贵。



#### 三者的边界与选择

**边界**：由「被测范围」与「是否使用真实依赖」两个维度共同划定；分不清边界时，先写下待验证的那句话再归类。

- 只有一句可判定的逻辑断言：归单元测试。
- 需要两个模块协作才能得出结果：归集成测试。
- 需要真实环境与完整链路才能复现：归端到端测试。
- 同一需求可分层：核心计算公式下沉到单元测试，界面提交链路留给端到端测试。

```js
// 同一个「满 99 免运费」需求的两种验证口径
const orderTotal = 120;

// 单元口径：只验证判定逻辑
const shippingFeeUnit = orderTotal >= 99 ? 0 : 8;
console.log(shippingFeeUnit); // 0

// 端到端口径：提交订单后核对结算页展示的运费
// 断言结算结果中的 shippingFee 字段为 0
```

> [!CAUTION]
> **注意内容**：把本可用单元测试覆盖的逻辑写成端到端测试，会让套件变慢且失败难定位，维护成本明显恶化。

**速记**：按被测范围与依赖真实性归类，能下沉到单元层的不要留在端到端层。



### 断言与测试用例的关系

本模块说明测试用例由哪些部分组成，以及断言在其中扮演的角色。

#### 测试用例的构成

**测试用例（test case）**：是一次可独立判定的验证单元，由被测对象、输入、执行动作、预期结果四部分组成。

- 被测对象：本次要检查的函数、模块或流程。
- 输入：驱动被测对象所需的参数、状态与前置数据。
- 执行动作：调用被测对象并捕获结果的方式。
- 预期结果：判断通过与否的基准，由断言表达。

```js
// 一个完整用例的四个部分
function addItemToCart(cart, item) {
  return { items: [...cart.items, item] };
}

const cart = { items: [] };
const nextCart = addItemToCart(cart, { sku: "A-1", qty: 2 }); // 执行动作
console.log(nextCart.items.length); // 1，预期结果
```

**速记**：用例等于被测对象、输入、执行动作与预期结果四部分。



#### 断言的作用

**断言（assertion）**：是把「实际结果与预期结果的关系」写成可执行判断的语句，判断为假即标记用例失败。

- 表达预期：把口头预期固化成机器可判定的条件。
- 定位失败：断言失败时给出实际值与预期值的差异。
- 终止用例：多数运行器在断言抛出异常后停止该用例的后续步骤。
- 区分用例边界：一个用例内的多个断言共享同一组前置条件。

```js
function toCelsius(fahrenheit) {
  return Math.round(((fahrenheit - 32) * 5) / 9);
}

console.log(toCelsius(32));  // 0
console.log(toCelsius(212)); // 100
// 把上面的期望值写成断言，运行时即可自动判定
```

**速记**：断言把预期写成可执行判断，失败即标记用例不通过。



#### 一个用例失败的判定

**用例失败**：指用例执行过程中出现断言不成立、抛出未捕获异常或超出超时限制中的任意一种情况。

- 断言失败：实际值与预期值不一致，报告会并列显示两者。
- 未捕获异常：被测代码抛出错误而用例没有处理。
- 超时：异步操作在限定时间内未完成，运行器判定失败。
- 两类原因要分开看：产品行为变了会失败，断言本身写错了也会失败。

> [!NOTE]
> **提醒内容**：测试失败先判断是产品行为变了，还是断言本身写错了，二者的处理方式完全不同。

**速记**：断言不成立、抛异常、超时三者之一出现，用例即判定失败。



#### 三段式结构

**三段式结构（arrange-act-assert）**：是把用例正文按准备、执行、断言三个阶段依次书写的组织方式。

- 准备（arrange）：构造输入、初始状态与测试替身。
- 执行（act）：调用被测对象，只做一次关键的触发动作。
- 断言（assert）：核对输出与副作用是否符合预期。
- 收益：结构统一后，用例的意图与失败位置都更容易定位。

```js
function applyCoupon(amount, coupon) {
  return coupon.valid ? amount - coupon.discount : amount;
}

// 准备
const amount = 200;
const coupon = { code: "NEW20", discount: 20, valid: true };

// 执行
const payable = applyCoupon(amount, coupon);

// 断言
console.log(payable); // 180
```

**速记**：用例按准备、执行、断言三段书写，结构统一、意图清晰。
