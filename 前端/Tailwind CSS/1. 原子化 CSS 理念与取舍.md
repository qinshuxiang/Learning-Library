## 原子化 CSS 理念与取舍

### 原子化是什么

#### 从语义类名到工具类

**原子化 CSS（Atomic / Utility-First CSS）**：不用描述组件语义的类名，而是把每条 CSS 属性封装成极小的工具类，在 HTML 里组合使用。

```html
<!-- 传统语义类名：样式在 CSS 文件里，HTML 里只有「名字」 -->
<button class="btn btn-primary">提交</button>

<!-- 原子化：样式就写在 HTML 上，每个类对应一条规则 -->
<button class="inline-flex items-center rounded-md bg-blue-600 px-4 py-2 text-sm text-white hover:bg-blue-700">
  提交
</button>
```

- 每个工具类职责单一且固定（`flex`、`pt-4`、`text-sm`），全站复用同一批类，**CSS 总量不随页面增长**。
- 删除页面即删除样式：没有「CSS 文件里哪些规则没人用了」的死代码问题（配合第 7 章的扫描机制）。
- 样式与结构同居一处，改一个按钮不必在 HTML 与 CSS 两处来回跳——这是原子化最直接的工程收益。

> 原子化的争议集中在「HTML 变丑」，但它的实质是**把样式的组织单位从「组件语义」换成了「视觉原语」**。样式本就该跟随组件的变体与状态变化，放在模板旁边比放在千里之外的 CSS 文件里更贴近变更现场——实践过中大型项目的人都体会过「改个按钮全项目找 .btn」的痛。

**速记**：**工具类即样式**，类名组合出界面，CSS 总量恒定、删页面不残留。



### 取舍

#### 优势、代价与适用边界

**选型判断**：原子化的收益与代价都很明确，适合组件化开发与设计系统统一的场景。

- **优势**：命名不再纠结（BEM 的层级地狱消失）；约束在预设体系内（间距、字号只能是刻度值），设计一致性被工具强制；与组件框架天然契合——组件封装变体后，模板里的类名串就是「样式源码」（第 5 章）。
- **代价**：模板里长类名串的可读性（靠组件封装与格式化缓解）；新人需要查文档学类名体系；**深度选择器、复杂动画、第三方组件样式覆盖仍是传统 CSS 的领地**。
- **不适用**：内容渲染不可控的场景（CMS 富文本输出无法贴类名，用 Typography 插件或传统 CSS 兜底）、纯静态小页面（引入构建链不划算）。

| 维度 | 语义类名＋SCSS | 原子化 |
|---|---|---|
| 样式组织 | 按「组件语义」 | 按「视觉原语」 |
| CSS 体积 | 随页面增长，需治理 | 恒定，按需生成 |
| 一致性约束 | 靠规范自觉 | 刻度体系强制 |
| 变体与状态 | 手写修饰类 | 变体前缀直接表达 |

> 你的既有基建是 SCSS＋shadcn-ui（shadcn 组件库主题第 3 篇已建立 Tailwind 与 CSS 变量体系），这个组合正是原子化的主流形态：**Tailwind 管布局与间距刻度，CSS 变量管主题色板**，两者互补而非替代。本篇的理念理解后，第 6 章处理与存量 SCSS 的共存。

**速记**：组件化项目收益最大，**刻度强制一致性**；富文本与静态小页面不必上。
