## 与 SCSS 共存及迁移

### 共存策略

#### 分工边界与 Preflight 冲突

**共存可行且常见**：存量 SCSS 项目不必一刀切，关键是给两者划出清晰的分工边界。

- **推荐分工**：Tailwind 管布局、间距、尺寸等**结构类**样式（刻度体系价值最大的地方）；SCSS 保留**品牌视觉与复杂样式**（主题色渐变、复杂动画、第三方组件皮肤、富文本样式）。
- **Preflight 冲突**：Tailwind 的基础样式重置（Preflight）会清空标题字号、列表符号、按钮背景——引入后存量页面的「默认外观」会变，这是共存阶段第一踩坑点。对策：先在低风险页面灰度，或用 `@import "tailwindcss/theme.css" layer(utilities)` 类的方式暂缓引入 Preflight。
- **选择器优先级**：SCSS 的深层选择器（`.sidebar .menu li a`）与原子类的单类名优先级博弈，覆盖第三方组件时统一走 SCSS 层，避免两套体系互相加 `!important` 打架。

> 共存期的判断标准是「**一段 UI 的样式只属于一套体系**」：一个组件要么全工具类，要么全 SCSS 类，不做半个。混写单个组件时，改样式的维护者要同时理解两套体系，是最差的组织形态。

**速记**：**Tailwind 管结构、SCSS 管品牌**，单组件不混体系，警惕 Preflight 重置。



### 迁移路径

#### 渐进式迁移的四个步骤

**渐进迁移**：存量项目按「新代码先行、存量按页面跟进」推进，不做停机式重写。

```text
1. 接入 Tailwind（第 2 章），Preflight 按共存策略处理
2. 新组件一律原子化，存量不动 —— 收益立现、风险为零
3. 改造高价值页面：改动频繁、样式债重的页面优先迁
4. 迁完的模块删对应 SCSS 段落，随迁随删，防止两套并存膨胀
```

- **迁移顺序的反直觉点**：从改动频繁的页面开始而不是从简单页面开始——迁移是顺手行为（反正要改样式），专门为迁移去碰没人动的页面是纯成本。
- 迁移单个组件的对照法：打开 SCSS 文件，逐条规则换算成工具类（`margin-bottom: 16px` → `mb-4`），换算时**优先归入最近刻度**而不是用任意值精确复刻——这是把旧值收敛进体系的机会。
- 每个模块迁完跑一遍视觉走查（尤其 Preflight 影响的表单与标题），确认后再删 SCSS 源。

> 迁移的完成标志不是「SCSS 文件清零」，而是**「团队默认写工具类」**。残留的 SCSS（第三方皮肤、富文本）有明确的存在理由与存放边界，与「没迁完」是两回事，不必追求字面上的清零。

**速记**：新代码先行、改到哪迁到哪、**随迁随删**，完成标志是习惯不是清零。

**警告内容**：迁移期间最危险的盘点方式是「**全量搜索类名判断是否还在用**」——SCSS 的类名可能被 JS 动态拼接、被第三方主题引用，删了编译不报错、运行时才缺样式。删除 SCSS 段落前先全项目（含 JS 字符串）搜索类名，并优先依赖构建产物的未用 CSS 检测，而不是肉眼搜索。
