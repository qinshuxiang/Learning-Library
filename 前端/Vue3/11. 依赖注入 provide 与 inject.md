## 依赖注入 provide 与 inject

### prop 逐层透传与依赖注入的定位

#### prop drilling 是深层组件的数据传递负担

**prop drilling（prop 逐层透传）**：指数据从顶层组件出发，必须经由中间组件的 props 一层一层向下转发，才能到达真正使用它的深层组件。

- 顶层数据（如主题、当前用户）往往被深层组件需要，二者在组件树中相隔多个层级。
- 中间组件**不使用**这些数据，却必须声明并继续转发，沦为纯粹的传递管道。
- 层级链越长，受牵连的中间组件越多，任何字段改名都要沿链逐层修改。

```html
<!-- 中间组件本不关心 userName，却必须声明并转发 -->
<script setup>
defineProps(["userName"]);
</script>

<template>
  <Footer :userName="userName" />
</template>
```

> [!CAUTION]
> **注意内容**：prop drilling 的代价不在功能而在维护。中间组件被无关 props 污染后，其可复用性与可读性同步下降，链路上任何一处改名或增删都会引发连锁修改。

**速记**：深层要数据，中间**被迫当管道**。



#### 依赖注入定位为祖先向后代跨层传递

**依赖注入**：是 Vue 提供的祖先组件向**任意层级后代**跨层传递数据的机制，由 provide 与 inject 成对完成。

- provide 由**祖先组件**调用，声明沿子树向下可用的依赖。
- inject 由**后代组件**调用，沿父链向上查找并取得该依赖。
- 中间组件完全不参与传递，数据像直达电梯一样从祖先到达后代。

```text
App（provide 主题数据）
└── Layout（不参与传递）
    └── Sidebar（不参与传递）
        └── ThemeToggle（inject 取得主题数据）
```

> 依赖注入解决的是**层级距离**问题，而不是数据共享问题：它让数据跨过中间层直达使用者，但提供方与使用方仍然依托父子链，脱离这条链注入就不存在。

**速记**：祖先 **provide**，后代 **inject**，中间层**免转发**。



#### 依赖注入与 props 的分工

**分工原则**：props 负责**相邻父子**之间的显式传参，依赖注入负责**跨层级**的数据投递，二者互补而非替代。

- props：层级浅、要求来源显式可见、需要类型与必填校验的常规传参。
- 依赖注入：层级深、全局性强的数据（主题、语言、当前用户）、需避免逐层转发的场景。
- 判断标准是**层级与数据性质**：相邻组件一律 props；跨多层且数据全局性强的才考虑注入。

> [!TIP]
> **建议内容**：遇到中间组件纯转发的代码时优先考虑依赖注入；但不要为了少写 props 而把所有数据都改为注入，显式契约仍是组件设计的第一选择。

**速记**：相邻用 **props**，跨层用**注入**。



### provide 与 inject 的基本用法

#### provide 在祖先组件声明可注入的值

**provide 方法**：签名 provide(键, 值)，由祖先组件调用，向其后代声明一个可被注入的值。

- 第一个参数是**注入键**，可以是字符串或 Symbol，供后代查找。
- 第二个参数是**提供的值**，任意类型，包括 ref、computed、reactive 等响应式数据。
- 同一组件可**多次调用** provide，用不同键提供多份数据。

```js
import { provide } from "vue";

provide("theme", "dark");
provide("appName", "学习库");
```

> [!NOTE]
> **提醒内容**：provide 必须在组件的 setup 中同步调用，不能放进异步回调或推迟到生命周期之后；否则 Vue 无法建立它与当前组件实例的关联。

**速记**：provide **声明**依赖，键唯一、值任意。



#### inject 按键取值并支持默认值

**inject 方法**：签名 inject(键, 默认值)，由后代组件调用，沿父链查找注入键并取得对应值。

- 沿**父组件链**向上查找，取得**最近的祖先**提供的同键值。
- 提供的值若是 ref，则按**原样返回**、不自动解包，从而保留与提供方的响应连接。
- 键在父链上找不到时回退到**默认值**；既无提供又不写默认值，开发环境会给出运行时警告。

```js
import { inject } from "vue";

const theme = inject("theme", "light");
```

> 辨析：默认值不是兜底缓存，而是可选依赖的声明——只有父链上没有任何祖先提供该键时才启用；一旦父链上存在同键提供，无论多远都以提供的值为准。

**速记**：inject **就近取值**，取不到用**默认值**。



#### 默认值可用工厂函数按需创建

**工厂默认值**：当默认值需要调用函数或实例化类来创建时，可传入**工厂函数**并把**第三个参数设为 true**，让 Vue 仅在真正用到默认值时才执行创建。

- 写法：inject(键, 工厂函数, true)，第三个参数表示把第二个参数**按工厂函数对待**。
- 目的是避免未用到可选依赖时也执行昂贵构造，减少不必要的计算与副作用。
- 字符串、数字等廉价默认值直接传值，无需工厂。

```js
const fallbackConfig = inject("config", () => createDefaultConfig(), true);
```

**速记**：昂贵默认值用**工厂**，第三参数传 **true**。



#### 二者须在 setup 中同步调用

**调用时机约束**：provide 与 inject 都必须**在 setup 执行期间同步调用**，这是二者能正确关联组件实例的前提。

- script setup 语法下写在顶层即是同步调用。
- 使用 setup 选项时也要直接写在函数体内，不能包进定时器回调或 await 之后。
- 违反约束时 Vue 无法确定提供者或消费者，注入结果不可预期。

```js
// 错误示范：把 provide 放进异步回调
export default {
  setup() {
    fetchUserInfo().then((info) => {
      provide("userInfo", info); // 此时 setup 已结束，注入失效
    });
  },
};
```

> 选项式 API 对应的写法是 provide 与 inject 选项，本篇以组合式 API 为口径；两种风格可按团队约定选择，但同步时机的要求一致。

**速记**：provide 与 inject **只在 setup 同步窗口**有效。



### 响应式注入

#### provide 传 ref 与 computed 保持响应性

**响应式注入的前提**：要让注入值随数据变化自动更新，provide 方必须传入 **ref 或 computed 这类响应式引用**，而不是取值后的普通数据。

- provide("count", count) 传的是 ref 本身，后代与提供方建立**响应连接**。
- provide("count", count.value) 传的是**当次快照**，之后无论如何修改都不再同步。
- 派生数据用 computed 包裹后提供，后代读到的始终是最新计算结果。

```js
// 提供方组件
import { ref, computed, provide } from "vue";

const count = ref(0);
const doubleCount = computed(() => count.value * 2);

provide("count", count);
provide("doubleCount", doubleCount);
```

```js
// 注入方组件
const count = inject("count");
// 模板中 {{ count }} 作为顶层绑定自动解包
// JS 逻辑中读取或修改须用 count.value
```

> [!IMPORTANT]
> **重要内容**：响应性的边界在 provide 调用的那一刻决定——传入引用则建立持续连接，传入 .value 则只留一次快照。落笔前先自问：传的是**引用**还是**值**。

**速记**：传 **ref 保持连通**，传 **.value 只留快照**。



#### 注入方使用与解构规则

**解构规则**：注入方拿到的是**响应式引用本身**，整体持有、放进 computed 或 watch 才能保持响应；对注入结果**直接取值或随意展开**会丢失响应性。

- 保持整体：const count = inject("count")，之后统一用 count.value。
- 在 computed 或 watch 内读取，响应链继续生效。
- 需要单独使用 reactive 对象的某个字段时，用 toRef 逐字段保响应。
- 官方示例中注入方可以解构出 location 与 updateLocation，前提是对象内的 location 字段本身仍是 ref——解构保留的是字段里的引用，而不是把响应数据拆散。

```js
import { inject, computed, toRef } from "vue";

const state = inject("userState");

// 正确：整体放入 computed
const displayName = computed(() => state.name);

// 正确：单字段保响应
const name = toRef(state, "name");

// 错误：一次取值变成快照，后续修改不再同步
const brokenName = state.name;
```

> [!CAUTION]
> **注意内容**：丢失响应性通常表现为改了数据页面不动，且不报错、排查困难。

**速记**：注入拿**引用**，单字段用 **toRef**，取值即**断链**。



#### 直接 provide 普通对象的隐患

**普通对象的陷阱**：直接 provide 一个普通对象时，后代即便修改其属性，变更也**不会触发任何视图更新**，响应链从源头就已缺失。

- 普通对象不是响应式代理，属性读写不会进入依赖收集。
- 后代修改这类对象属于**静默失败**：值变了、界面不变，且没有任何警告。
- 正确做法是在提供方先用 ref、reactive 或 computed 声明数据，再进行 provide。

```js
// 反例：普通对象无响应性
provide("settings", { fontSize: 14 });

// 正例：先声明响应式数据再提供
import { reactive, provide } from "vue";

const settings = reactive({ fontSize: 14 });
provide("settings", settings);
```

> [!WARNING]
> **警告内容**：直接 provide 普通对象还会带来**双向污染**——多个后代同时修改同一份非响应数据时，谁改的、何时改的都无从追踪，问题往往到联调阶段才集中暴露。

**速记**：provide 之前先**响应式化**，普通对象**注入即失效**。



### 数据所有权模式

#### 所有权保留在 provide 方

**数据所有权模式**：数据的定义、存储与变更逻辑全部保留在 provide 方，注入方只负责读取与调用修改函数，不做任何直接修改。

- 官方建议：使用响应式 provide 与 inject 时，**尽量把对状态的修改放在提供方组件内**，使状态与变更逻辑同处一处、便于维护。
- 该模式把谁能改数据收敛到唯一组件，避免多方直改引发的竞态与混乱。

> [!IMPORTANT]
> **重要内容**：所有权模式是官方推荐的责任收敛方式：状态与它的变更函数**共同提供、同处一地**，注入方永远通过函数间接修改，数据流向单一、可追溯。

标准结构是把状态与更新函数组织在一个对象里**一次 provide**，注入方解构后即可使用：

```js
// 提供方组件
import { ref, provide } from "vue";

const location = ref("North Pole");

function updateLocation() {
  location.value = "South Pole";
}

provide("location", { location, updateLocation });
```

```html
<!-- 注入方组件 -->
<script setup>
import { inject } from "vue";

const { location, updateLocation } = inject("location");
</script>

<template>
  <button @click="updateLocation">{{ location }}</button>
</template>
```

> 解构后 location 仍是 ref，模板中自动解包显示；updateLocation 是提供方拥有的函数，写入路径唯一。这个结构同时满足响应式、只读意图、修改收敛三个诉求。

**速记**：数据**归提供方所有**，**状态加函数**打包 provide，注入方**只读加调函数**。



#### readonly 包裹对外只读数据

**readonly 的作用**：readonly 接收一个响应式对象或 ref，返回其**深度只读代理**，后代对它的任何修改都不生效，从而保证数据只能经提供方的函数变更。

- provide("count", readonly(count))：后代能读、能响应，但不能写。
- 修改入口单独提供：provide("increment", increment)。
- readonly 不做拷贝也不做加密，只是在代理层**拦截写入**，底层数据仍归提供方所有。

```js
import { ref, provide, readonly } from "vue";

const count = ref(0);
function increment() {
  count.value++;
}

provide("count", readonly(count));
provide("increment", increment);
```

> 官方文档口径：若希望注入方**完全无法改动** provide 传递的数据，就用 readonly 包裹；若只希望改动经过统一入口，则提供修改函数即可，二者常配合使用。

**速记**：对外 **readonly 锁写**，入口**单独给函数**。



### 注入键的类型选择

#### 字符串键与 Symbol 键

**注入键的两种形态**：注入键既可以是**字符串**，也可以是 **Symbol**；Symbol 的核心价值是全局唯一，天然避免不同模块之间键名冲突。

- 字符串键：直观、易调试，适合小型应用或键名可控的场景。
- Symbol 键：适合大型应用、多个依赖提供方或发布给他人使用的组件库。
- 官方建议：把 Symbol 键**统一导出到独立文件**，提供方与注入方共用同一份键。

```js
// keys.js：集中管理注入键
export const myInjectionKey = Symbol();

// 提供方组件
import { provide } from "vue";
import { myInjectionKey } from "./keys.js";

provide(myInjectionKey, { /* 提供的数据 */ });

// 注入方组件
import { inject } from "vue";
import { myInjectionKey } from "./keys.js";

const injected = inject(myInjectionKey);
```

> Symbol 的唯一性只在**同一份键对象**上成立：若两个模块各自执行 Symbol("theme")，得到的是两个互不相同的键，注入将查不到值。集中导出正是为了共享同一键实例。

**速记**：小应用**字符串**，大应用 **Symbol 集中导出**。



#### TypeScript 下的键标注

**类型安全的注入键**：用 vue 提供的 InjectionKey 泛型类型标注 Symbol 键，可让 provide 与 inject 在编译期校验值类型，注入结果自动获得类型推断。

- 定义：userKey 以 InjectionKey 泛型标注为 UserInfo 类型，键值是 Symbol("userKey")，完整写法见下方代码块。
- provide(userKey, value) 的 value 必须满足 UserInfo，类型不符即编译报错。
- inject(userKey) 未声明默认值时，返回类型推断为 UserInfo 或 undefined。
- 多个键可进一步收拢为 **Symbol 联合类型**，约束辅助函数只能接受已知的键集合。

```ts
import { type InjectionKey } from "vue";

interface UserInfo {
  name: string;
  role: string;
}

export const userKey: InjectionKey<UserInfo> = Symbol("userKey");
export const themeKey = Symbol("themeKey") as InjectionKey<string>;

type AppKey = typeof userKey | typeof themeKey;

function isAppKey(key: symbol): key is AppKey {
  return key === userKey || key === themeKey;
}
```

> 该标注只对组合式 API 的 provide 与 inject 生效；选项式的 provide 与 inject 选项无法携带键类型，TypeScript 项目应优先使用组合式写法。

**速记**：**InjectionKey 标注 Symbol**，provide 与 inject **同受类型约束**。



### 应用层 provide 与组件层 provide

#### app.provide 面向全局注入

**应用层注入**：app.provide 在应用实例上声明依赖，对应用内**所有组件**可见，无需任何组件亲自提供。

- 写法：在 createApp 之后、mount 之前调用 app.provide(键, 值)。
- 典型场景是**插件**：插件无法预知使用方的组件树，只能通过应用层把配置、客户端实例等注入全应用。
- 应用层提供与组件层提供可以并存，组件层同键的提供会**就近覆盖**应用层的值。

```js
import { createApp } from "vue";
import App from "./App.vue";

const app = createApp(App);
app.provide("appVersion", "1.0.0");
app.provide("apiBase", "https://api.example.com");
app.mount("#app");
```

**速记**：app.provide **全局可用**，是插件注入的**首选位置**。



#### 组件层 provide 的相对性与就近原则

**相对性与就近原则**：组件层 provide 只对该组件的**子树**生效；父链上多个祖先提供同一键时，inject 解析为**距离最近的祖先**提供的值。

- provide 是相对声明：写在哪个组件，就只服务哪个组件的后代，兄弟分支不受影响。
- 同键多层提供时，**内层覆盖外层**，后代自动拿到最近值。
- 该特性可用于局部覆盖：外层给默认主题，某个子树内重新提供深色主题，子树内的组件无需任何改动。

```text
App：provide("theme", "light")
└── Dashboard：provide("theme", "dark")
    ├── ChartPanel：inject 得到 "dark"（最近祖先）
    └── Header：inject 得到 "light"（不在 Dashboard 子树内）
```

> 就近原则意味着注入结果取决于**组件挂在哪棵子树**，同一个 inject 调用在不同位置可能得到不同值。排查注入问题时，先画清组件树，再看键由谁、在哪一层提供。

**速记**：provide **只管子树**，inject **就近覆盖**。



### 与组合式函数结合

#### 在 provide 中调用组合式函数组织逻辑

**组合式组织**：provide 的值不必是裸数据，可以在提供方**先调用组合式函数**组织出状态与方法，再把结果整体提供，让复杂依赖有清晰的组织单元。

- 组合式函数负责生成状态与操作，例如计数逻辑、请求逻辑。
- 提供方组件调用组合式函数后，把结果经 provide 下发。
- 注入方对内部实现无感知，只依赖注入值的形状。

```js
// useCounter.js：组合式函数封装计数逻辑
import { ref } from "vue";

export function useCounter(initial = 0) {
  const count = ref(initial);
  function increment() {
    count.value++;
  }
  return { count, increment };
}

// 提供方组件
import { provide } from "vue";
import { useCounter } from "./useCounter";

const counter = useCounter(10);
provide("counter", counter);
```

**速记**：逻辑进**组合式函数**，provide 负责**下发成品**。



#### 提供注入访问器并校验缺失

**访问器模式**：为每一组注入封装一对函数——provideXxx 负责提供，useXxx 负责注入并校验，注入方永远不直接书写裸键，缺失时报错清晰。

- provideXxx 在祖先组件调用，内部完成 provide。
- useXxx 在后代组件调用，内部完成 inject，并在取值为空时**抛出明确错误**，避免 undefined 一路传染。
- 封装同时把键（尤其 Symbol 键）隐藏在模块内部，调用方不会写错键名。

```js
// userState.js
import { provide, inject, readonly, ref } from "vue";

const userKey = Symbol("userKey");

export function provideUserState() {
  const user = ref({ name: "访客", role: "guest" });
  function rename(next) {
    user.value.name = next;
  }
  provide(userKey, { user: readonly(user), rename });
}

export function useUserState() {
  const state = inject(userKey);
  if (!state) {
    throw new Error("useUserState 必须在 provideUserState 的后代组件中使用");
  }
  return state;
}
```

> [!TIP]
> **建议内容**：注入键从调用方视野中消失后，整个应用只有 provideXxx 与 useXxx 两个入口，键改名、换类型都只动一个文件，这是依赖注入可维护性的关键一步。

**速记**：**provideXxx 与 useXxx 成对封装**，缺失即抛错。



### 慎用边界

#### 不要用依赖注入替代 props

**边界结论**：依赖注入不能替代 props 作为常规传参手段，组件的常规数据一律走 props，注入只留给跨层级与全局性数据。

- 注入让**数据来源不透明**：看单个组件的代码无法知道数据从哪来，必须回溯整棵组件树。
- 组件失去独立可测性：脱离特定祖先树后注入为空，复用与测试成本上升。
- props 是显式契约，类型、必填、校验齐备；注入的约束全靠约定与封装。

> [!WARNING]
> **警告内容**：滥用注入会让组件之间的依赖关系隐式化，重构时无法从单个文件判断数据流向，改一处 provide 可能波及整棵子树。判断口诀：**能 props 就 props，非跨层不注入**。

**速记**：注入是**逃生通道**，不是**默认通道**。



#### 与状态库 Pinia 的边界

**状态库边界**：依赖注入适合**少量、结构性**的跨层数据（配置、主题、实例句柄）；跨组件的**复杂共享状态**（多组件高频读写、需要调试工具与持久化）应交给状态库，本项目采用 Pinia，详见《21. Pinia 状态管理.md》。

- 注入的长项：随组件树天然作用域化，适合主题、布局、插件上下文这类**依附于子树**的数据。
- Pinia 的长项：全局单例 store、devtools 调试、模块化拆分、持久化插件，适合购物车、用户会话等**全局业务状态**。
- 简单判据：数据**只在某个子树内**有意义，用注入；数据**与应用全局**相关且被多处复杂读写，用 Pinia。

> [!NOTE]
> **提醒内容**：二者不是互斥关系。常见的协作方式是 Pinia 保存全局业务状态，组件层再通过 provide 把 store 实例或其派生数据下发到深层子组件。

**速记**：**子树数据用注入，全局状态上 Pinia**。
