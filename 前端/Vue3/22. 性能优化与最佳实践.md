## 性能优化与最佳实践

### 优化总纲：先测量后优化

#### 优化必须以测量为前提

**性能优化第一原则**：任何优化动手前必须先用工具**测量并定位瓶颈**，凭感觉优化往往白费力气甚至适得其反。

- **Vue DevTools**：其性能面板可查看组件的渲染耗时与更新频率，快速定位重渲染的组件。
- **浏览器 Performance 面板**：录制一段交互过程，观察脚本执行、渲染、重排重绘的火焰图，找出耗时大头。
- **Lighthouse**：对首屏加载给出评分与建议清单，适合评估加载线性能。
- 优化的正确顺序是：**测量 → 定位瓶颈 → 针对性优化 → 复测对比**，闭环验证效果。

> 没有数据就没有优化。一个页面慢，可能慢在包体积、慢在某组件每秒重渲几十次、也可能慢在接口返回；三种病因对应三种药方，测量就是先确诊再开药。

**速记**：先**测量定位**，再**对症优化**，最后**复测闭环**。



#### 加载性能与更新性能两条主线

**Vue 应用性能的两条主线**：一条是**加载性能**（页面从请求到可交互有多快），一条是**更新性能**（交互后视图响应有多快），二者的瓶颈与药方完全不同。

- **加载性能**关注：首屏时间、包体积、请求数、缓存策略，核心手段是**代码分割与产物优化**。
- **更新性能**关注：组件渲染与重渲染的耗时，核心手段是**减少不必要的响应式开销与重渲染**。
- 两条线要分开诊断：加载慢看网络面板与打包产物，更新卡看渲染耗时与组件更新次数。

> 常见误区是把所有问题归因于“代码写得烂”。加载慢多半是**工程化配置**问题（没分割、没压缩、缓存失效），更新卡多半是**响应式设计**问题（深层响应式滥用、无节流、key 不稳定），先分类再解决。

**速记**：加载线看**体积与缓存**，更新线看**渲染与响应式**。



### 加载性能之代码分割

#### 路由懒加载按需加载页面组件

**路由懒加载**：把每个页面组件的代码**单独切成一个 chunk**，只有导航到该路由时才下载对应文件，从而避免首屏打包全部页面。

- 写法：路由配置的 component 不直接引入组件，而是返回动态导入的函数。
- 与第 20 篇《Vue Router 4》衔接：createRouter 配置中，懒加载是路由表的标准写法。
- 效果：首屏只加载入口与首页代码，其余页面**随用随取**，首屏体积显著下降。

```js
import { createRouter, createWebHistory } from "vue-router";

const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: "/", component: () => import("./views/Home.vue") },
    { path: "/about", component: () => import("./views/About.vue") },
  ],
});
```

> [!TIP]
> **建议内容**：所有页面级路由一律写懒加载，这是几乎零成本、收益最大的加载优化；动态导入返回 Promise，构建工具会自动把每个目标文件切分为独立 chunk，无需手工配置。

**速记**：路由组件写成动态导入箭头函数，**用到哪页下哪页**。



#### defineAsyncComponent 定义异步组件

**异步组件**：通过 defineAsyncComponent 把一个组件**延迟到真正渲染时再加载**，适合首屏之外的弹窗、抽屉等重组件。

- 基本用法：传入一个返回动态导入的工厂函数。
- 进阶用法：传入配置对象，可指定加载中组件 loadingComponent、失败组件 errorComponent、延迟显示 loading 的 delay、超时时间 timeout。
- 与路由懒加载的差别：路由懒加载作用于**页面切换**，异步组件作用于**同一页面内的条件渲染**，二者互补。

```js
import { defineAsyncComponent } from "vue";

// 基本写法
const HeavyChart = defineAsyncComponent(() =>
  import("./components/HeavyChart.vue")
);

// 带加载态与错误态的完整写法
const RichEditor = defineAsyncComponent({
  loader: () => import("./components/RichEditor.vue"),
  loadingComponent: LoadingSpinner,
  errorComponent: LoadError,
  timeout: 10000,
});
```

> [!NOTE]
> **提醒内容**：delay 的默认值是 200 毫秒，若加载在 200 毫秒内完成，loadingComponent 完全不会闪现，这是为避免加载态闪烁的刻意设计；timeout 到期后自动切换到 errorComponent，避免用户无限等待。

**速记**：**重组件按需弹**，defineAsyncComponent 配 loading 与 error 兜底。



#### 打包体积分析找出大依赖

**体积分析**：优化包体积前先用工具**可视化构建产物**，看清每个依赖占了多少字节，再决定优化目标。

- Vite 项目用 rollup-plugin-visualizer 生成分析报告，构建后打开统计页面即可查看各模块占比。
- 常见发现：某个图标库、日期库或工具库占了几百 KB；整个 lodash 或整个组件库被打包进来。
- 对策按优先级：**换轻量库**（dayjs 替代 moment）、**按需导入**（只引入用到的函数或组件）、**彻底移除**未用的依赖。

```text
优化体积的标准动作清单：
1. 生成分析报告，找出占比最大的模块
2. 判断该模块是否真的被使用
3. 未使用则移除依赖
4. 使用中但体积过大则寻找轻量替代或改为按需导入
5. 重新构建，对比产物体积验证效果
```

> [!IMPORTANT]
> **重要内容**：分析报告要先于任何体积优化动作。没有报告支撑就删依赖、换库，很可能删掉的是不占体积的小模块，而真正的大头原封不动。

**速记**：先看**体积地图**，再按**移除、替代、按需**三步走。



### 加载性能之产物优化

#### 生产构建压缩与 Tree-shaking

**生产构建优化**：开发环境与生产环境产物差异巨大，生产构建会自动完成**代码压缩**与 **Tree-shaking**（摇掉未使用代码），二者都依赖构建工具配置正确。

- 压缩：Vite 生产构建默认用 esbuild 压缩，去除空白、缩短变量名、简化死代码。
- Tree-shaking 前提：库以 **ES 模块**导出且标记了无副作用，打包器才能安全删除未引用的导出。
- 按需导入配合：从组件库只导入用到的组件、从工具库只导入用到的函数，未用部分在构建时被摇掉。

```js
// 按需导入：未引入的组件不会进入产物
import { Button, Input } from "some-ui-lib";
import { debounce } from "lodash-es";
```

> [!NOTE]
> **提醒内容**：Tree-shaking 失效的常见原因是引入了 CommonJS 版本或从入口文件整包导入（如 import _ from lodash）。选择标明支持 ES 模块的包（如 lodash-es）并始终用具名导入，摇树才能生效。

**速记**：压缩**自动做**，摇树靠 **ES 模块加按需导入**。



#### 去除生产环境的开发警告

**开发警告的去留**：Vue 的校验警告（无效 props、重复 key、模板语法错误提示等）**只在开发构建中存在**，生产构建会通过条件分支整体剔除，无需手工处理。

- 原理：源码中以开发环境判断包裹警告代码，生产打包时被静态替换为假并删除死分支。
- 收益：生产包既更小也不受警告逻辑干扰，这是框架免费提供的优化。
- 需要自查的是**业务代码里的调试残留**：console 打印、调试组件、mock 数据开关应在发布前清理或用环境变量隔离。

```js
// 业务调试代码用环境变量隔离，生产构建中会被摇掉
if (import.meta.env.DEV) { console.log("调试信息", someState); }
```

> [!CAUTION]
> **注意内容**：不要在生产代码里依赖这些环境判断执行业务逻辑。import.meta.env.DEV 之类的判断是**编译期替换**，生产环境中分支被整体删除，运行时再切换环境变量不会生效。

**速记**：框架警告**生产自除**，业务调试**靠环境变量隔离**。



#### sourcemap 的取舍策略

**sourcemap 策略**：source map 是构建产物到源码的映射文件，能让压缩后的报错还原到源码位置；生产环境是否发布它需要在**可排障**与**源码暴露**之间取舍。

- 开发环境：默认开启且不落盘，直接内联，保证调试体验。
- 生产环境常见选择：不发布 sourcemap（体积最小、源码不暴露）；或生成但不随静态资源公开，仅在报错平台内部使用。
- Vite 配置：通过 build.sourcemap 控制，值可为 false、true 或内联。

```js
// vite.config.js 片段
export default defineConfig({
  build: { sourcemap: false }, // 需要排障时改为 true 或 'hidden'
});
```

> [!TIP]
> **建议内容**：接入了前端错误监控平台的项目，推荐 hidden 模式——生成映射文件但不让浏览器直接访问，把映射上传到监控平台内部还原堆栈，兼顾排障能力与源码安全。

**速记**：sourcemap 是**排障利器也是源码地图**，生产按需 hidden 上传。



#### CDN 加速与 HTTP 缓存

**静态资源分发**：构建产物是纯静态文件，部署时应借助 **CDN 就近分发**与 **HTTP 缓存**让二次访问接近零加载，这与 HTML 系列第 23 篇《性能与加载策略》的浏览器缓存机制一脉相承。

- 文件名加内容哈希：Vite 构建产物自带哈希文件名，内容一变哈希就变，可放心设置长缓存。
- 缓存策略分层：带哈希的 js、css、图片设置一年强缓存；入口 html 设置协商缓存，保证发版后能立刻拿到新哈希清单。
- 第三方库上 CDN：稳定的公共库可走公共 CDN 或自建 CDN 域名，与业务资源分流并行下载。

```text
缓存配置要点：
1. /assets/ 下带哈希的产物：Cache-Control 强缓存一年
2. 入口 index.html：协商缓存，不设长强缓存
3. 发版流程：先传新哈希产物，再更新 html，避免新旧不一致
```

> [!WARNING]
> **警告内容**：若把入口 html 也设成一年强缓存，用户会在发版后**长期停留在旧版本**，旧页面引用的旧 chunk 可能已被清理导致白屏。哈希产物可长缓存，html 必须可及时更新。

**速记**：**哈希产物强缓存，html 协商保发版**。



### 更新性能之静态内容缓存

#### v-once 跳过后续更新

**v-once 指令**：让一段模板**只在首次渲染时求值**，之后数据再怎么变，这部分内容都不再更新。

- 适用场景：内容渲染后**确定不再变化**的静态区块，如协议条款、活动说明、一次性展示的统计快照。
- 效果：该区块的虚拟 DOM 被标记为静态，后续组件更新时**整块跳过**比对与重建。
- 代价：使用后该区域与响应式数据**彻底脱钩**，数据变了界面也不变。

```html
<template>
  <!-- 渲染一次后永久静止 -->
  <div v-once>
    <p>{{ agreement.title }}：{{ agreement.content }}</p>
  </div>
  <!-- 数据仍会继续变化 -->
  <p>当前在线人数：{{ onlineCount }}</p>
</template>
```

> [!WARNING]
> **警告内容**：v-once 是**单方面放弃更新**，不是延迟更新。一旦加上，后续任何数据变化都不会反映到该区块，且无法通过改数据来“恢复”更新，只能重渲染组件本身。

**速记**：v-once = **渲一次就定格**。



#### v-memo 按依赖数组缓存渲染结果

**v-memo 指令**：给一段模板声明一个**依赖数组**，只有依赖项发生变化时该区块才重新渲染，否则直接复用上次结果。

- 基本形式：v-memo 后接数组，如 v-memo="[item.id, item.selected]"。
- 典型用法：在 v-for 的大列表里，只把**真正影响显示的字段**写进依赖数组，列表整体更新时未变化的行跳过渲染。
- 空数组 v-memo="[]" 表示首次渲染后不再更新，效果类似 v-once，但可以配合条件让组件级更新时恢复。

```html
<template>
  <ul>
    <li v-for="item in list" :key="item.id" v-memo="[item.id, item.selected]">
      <span>{{ item.name }}</span>
      <p>已选：{{ item.selected }}</p>
    </li>
  </ul>
</template>
```

> [!IMPORTANT]
> **重要内容**：v-memo 的依赖数组必须**穷尽该区块内用到的所有响应式字段**。上例中若依赖只写 item.id 而模板里展示了 item.selected，那么选中状态变化后视图不会刷新，造成界面与数据不一致。依赖设计原则是：模板里读了什么，数组里就得有什么；与此无关的重型字段变化则能被挡在渲染之外。

**速记**：v-memo = **依赖不动就复用**，依赖要**穷尽模板所读**。



### 更新性能之计算缓存

#### 用 computed 替代模板内联复杂表达式

**计算缓存优先**：模板里出现**复杂表达式、多次重复的运算或方法调用**时，应改为计算属性，借助依赖缓存避免每次渲染重复计算，这是第 4 篇《计算属性与侦听器》核心结论在性能视角的落地。

- 内联表达式的代价：组件每次重渲染，表达式都要**重新求值一遍**，放在 v-for 里就是每行各算一次。
- 方法调用的代价：模板中的方法在**每次渲染时都被执行**，没有缓存语义。
- 计算属性的优势：依赖不变时**直接返回缓存**，同样的结果只算一次。
- 判断标准：表达式里出现**过滤、排序、拼接、格式化**等运算，或同一逻辑被多处引用，就应抽成 computed。

```html
<template>
  <!-- 反例：每次渲染都对全量列表做过滤排序 -->
  <li v-for="item in list.filter(i => i.active).sort((a, b) => a.score - b.score)">
    {{ formatDate(item.createdAt) }}
  </li>

  <!-- 正例：computed 依赖不变时零开销 -->
  <li v-for="item in activeListSorted">
    {{ item.createdAtText }}
  </li>
</template>

<script setup>
import { computed } from "vue";

const activeListSorted = computed(() =>
  list.value
    .filter((i) => i.active)
    .sort((a, b) => a.score - b.score)
);
const createdAtText = computed(() => formatDate(item.createdAt));
</script>
```

> 方法并非不能用：计算**没有响应式依赖**、或每次渲染确实需要重新执行（如传变化参数的格式化函数）时，方法反而正确；此时计算属性会因依赖为空而永不更新。要的是**值**用 computed，要的是**动作**用方法。

**速记**：模板里**只写引用**，复杂运算**进 computed 吃缓存**。



### 更新性能之响应式开销控制

#### shallowRef 减少大列表深层代理

**shallowRef**：只对 .value 的**整体替换**建立响应式，其内部属性不做深层代理，适合数据量大但**整存整取**的场景。

- 响应式开销的来源：ref 与 reactive 会把对象**递归转换成深层代理**，属性越多层级越深，初始化与追踪的开销越大。
- shallowRef 的行为：替换整个 .value 会触发更新；直接改内部属性**不会**触发更新。
- 大列表的正确用法：用普通数组配合 shallowRef，更新时**先改数据、再整体赋值**新数组引用。
- 需要强制触发时，配合 triggerRef 手动通知。

```js
import { shallowRef, triggerRef } from "vue";

const bigList = shallowRef([]);

// 正确：整体替换触发更新
function loadList(newList) {
  bigList.value = newList;
}

// 修改内部后手动触发
function updateOne(index, patch) {
  bigList.value[index] = { ...bigList.value[index], ...patch };
  triggerRef(bigList);
}
```

> [!CAUTION]
> **注意内容**：shallowRef 下直接修改内部属性后忘记整体替换或 triggerRef，界面会**静默不更新**且无任何报错，是隐蔽的坑。只有在确信“列表渲染只由整体替换驱动”时才选 shallowRef。

**速记**：shallowRef **只认整换**，内改要配 triggerRef。



#### markRaw 隔离无需响应式的对象

**markRaw**：给对象打上永不转为响应式代理的标记，用于**明确不需要响应式**的数据，省去代理开销。

- 典型场景一：第三方库实例——地图实例、图表实例、播放器实例，它们自成体系，包一层代理反而破坏内部逻辑或拖慢性能。
- 典型场景二：海量展示数据中无需追踪的只读部分，如纯展示的静态配置、大型字典数据。
- 用法：在把对象存入响应式容器之前调用 markRaw 包裹。

```js
import { reactive, markRaw } from "vue";

const state = reactive({
  // 第三方实例不做代理，避免功能异常与额外开销
  chartInstance: markRaw(createChartInstance()),
});
```

> [!IMPORTANT]
> **重要内容**：markRaw 打过标记的对象**无法再被转为响应式**，若日后业务又需要对它做响应式追踪，只能换一个未标记的新对象。所以它只应使用在“确定永不响应”的数据上，不要当作常规性能手段滥用。

**速记**：markRaw = **免代理通行证**，发给**第三方实例与静态数据**。



#### 按需选择响应式 API 的层级

**响应式分层选择**：Vue 提供了从深到浅的多档响应式能力，应根据数据**体量与读取频率**选择合适档位，避免全量 deep 代理带来的无谓开销。

- **ref / reactive**：默认档，深层代理，适合表单、配置等中小体量、需要细粒度追踪的数据。
- **shallowRef / shallowReactive**：浅层档，只代理第一层，适合大列表、大数据结构整存整取。
- **markRaw / raw 对象**：零开销档，完全脱离响应式，适合第三方实例、永不变化的数据。
- **非响应式普通变量**：不在模板与依赖中展示的数据（如临时缓存、SDK 对象）根本不必进响应式系统。

```text
选型决策顺序：
1. 这份数据需要展示或驱动视图吗？不需要 → 普通变量
2. 需要驱动视图，但整体替换即可？ → shallowRef
3. 需要细粒度深层追踪？ → ref / reactive
4. 是第三方实例或确定永不响应？ → markRaw 包裹
```

> [!TIP]
> **建议内容**：性能敏感页面的自查口诀是“**能浅不深、能不响应就不响应**”。把本应零开销的数据塞进深层响应式，是更新性能问题里最常见也最容易被忽略的源头。

**速记**：响应式**按档选用**——**深、浅、零**三级递减。



### 列表渲染 key 的稳定性

#### 忌用数组下标作为 key

**key 必须稳定唯一**：v-for 的 key 是虚拟 DOM 就地复用的身份标识，应使用数据的**唯一业务 id**；用数组下标作 key 在**插入、删除、排序**场景会导致状态错位与多余的 DOM 重建。

- 复用机制：diff 时 Vue 按 key 匹配新旧节点，key 相同就**就地复用**并打补丁，而不是销毁重建。
- 下标的缺陷：下标只代表**位置**，不绑定数据本身。头部插入一项后，原来第 0 项的数据现在下标 0 换成了新项，复用判断随之错乱。
- 三种典型恶果：**输入类组件的内部状态串位**（输入框内容跑到别的行）、**过渡动画错乱**、**组件多走销毁重建**拉低更新性能。
- 与第 5 篇《条件渲染与列表渲染》衔接：key 的身份语义在那里已给出，此处强调其性能后果。

```html
<template>
  <!-- 反例：下标作 key，头部插入后输入状态串位 -->
  <input v-for="(item, index) in list" :key="index" v-model="item.text" />

  <!-- 正例：唯一业务 id 作 key，复用判断永远正确 -->
  <input v-for="item in list" :key="item.id" v-model="item.text" />
</template>
```

> [!WARNING]
> **警告内容**：静态只读、渲染后永不增删排序的列表，用下标作 key 虽不致出错，但会让人养成坏习惯；只要列表存在任何动态变化（插入、删除、过滤、排序），下标 key 就必然埋雷。想省 id 就给数据结构补上 id，而不是拿位置充数。

**速记**：key 是**数据身份证**，不是**座位号**——动态列表**永远用 id**。



### 缓存与清理

#### KeepAlive 缓存组件的激活与失活

**KeepAlive 组件**：包裹动态组件后，被切走的组件实例**不销毁而是缓存**，切回时直接复用原实例，保留其全部内部状态。

- 常用属性：include 按组件名白名单缓存，exclude 黑名单排除，max 限制缓存实例上限。
- 生命周期配套：被缓存的组件切走时触发 **deactivated 钩子**，切回时触发 **activated 钩子**，而不是执行卸载与重新挂载。
- 组合式写法：onActivated 与 onDeactivated 注册，常用于恢复或暂停轮询、重新拉取最新数据。

```html
<template>
  <KeepAlive include="UserList" :max="10">
    <component :is="currentView" />
  </KeepAlive>
</template>

<script setup>
import { onActivated, onDeactivated } from "vue";

onActivated(() => startPolling());   // 切回：恢复轮询、刷新数据
onDeactivated(() => stopPolling());  // 切走：暂停轮询，避免后台空转
</script>
```

> [!CAUTION]
> **注意内容**：被 KeepAlive 缓存的组件**不会执行 onUnmounted**，切走时只触发 onDeactivated。若把定时器清理写在卸载钩子里，缓存切走后定时器会**在后台持续运行**，既浪费资源又可能重复请求。缓存组件的暂停逻辑必须写在 onDeactivated。

**速记**：KeepAlive **缓实例不销毁**，配对钩子是 **activated 与 deactivated**。



#### 定时器与监听器必须随组件清理

**清理纪律**：组件内创建的**定时器、事件监听器、订阅**，凡生命周期短于页面级的资源，必须在组件卸载时**成对清理**，否则构成内存泄漏，这是第 17 篇《执行上下文与内存管理》中“闭包持有引用导致无法回收”在组件场景的直接体现。

- 泄漏路径：定时器回调持有组件作用域引用 → 组件卸载后回调仍在队列 → 引用链不断 → 组件与其捕获的数据**无法被回收**。
- 全局监听同理：window 或 document 上注册的监听器不会随组件卸载自动移除，必须手动 removeEventListener。
- 组合式 API 的自动清理范围：watch、watchEffect、组件内 emit 的自定义事件由框架自动停止；**浏览器原生资源不享受此待遇**。

```js
import { ref, onMounted, onUnmounted } from "vue";

const windowWidth = ref(window.innerWidth);
let timerId = null;

function handleResize() { windowWidth.value = window.innerWidth; }onMounted(() => {
  window.addEventListener("resize", handleResize);
  timerId = setInterval(refreshData, 5000);
});

// 与注册一一对应，成对清理
onUnmounted(() => {
  window.removeEventListener("resize", handleResize);
  clearInterval(timerId);
});
```

> [!IMPORTANT]
> **重要内容**：判断一个资源要不要手动清理，看它的**宿主是谁**——宿主是 Vue 组件系统的（watch、响应式副作用）框架自动管；宿主是浏览器或外部的（定时器、原生事件、WebSocket、第三方 SDK）一律自己管，卸载钩子里**注册几对就清理几对**。

**速记**：**谁注册谁清理**，定时器监听器**成对出现成对销毁**。



### 高频事件的节流与防抖

#### 防抖 debounce 合并连续触发

**防抖**：事件触发后延迟一段时间才执行回调，若延迟期内**再次触发则重新计时**，最终只执行**最后一次**，适合“等用户停下来再做”的场景。

- 典型场景：搜索框输入联想（停止输入 300 毫秒后才请求）、窗口 resize 结束后的重算、表单校验。
- 实现要点：闭包保存定时器 id，每次触发先 clearTimeout 再重设 setTimeout；组合式封装时在组件卸载钩子里清掉未决定时器。
- 与第 14 篇《组合式函数 composables》衔接：防抖、节流最适合封装成组合式函数跨组件复用。

```js
// composables/useDebounce.js
import { onUnmounted } from "vue";

export function useDebounce(fn, delay = 300) {
  let timerId = null;

  function debouncedFn(...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delay);
  }

  // 卸载时丢弃未执行的回调，避免组件销毁后仍运行
  onUnmounted(() => clearTimeout(timerId));
  return debouncedFn;
}
```

> [!TIP]
> **建议内容**：输入框搜索联想场景中，防抖比节流更合适——用户要的是**最终输入**的结果，中间态请求纯属浪费；把 delay 控制在 300 毫秒左右，可在响应速度与请求数之间取得平衡。

**速记**：防抖 = **停手才执行**，只认**最后一次**。



#### 节流 throttle 固定频率触发

**节流**：无论事件触发多密集，回调都按**固定时间间隔最多执行一次**，适合“持续操作中保持稳定频率响应”的场景。

- 典型场景：滚动加载（监听 scroll 判断是否触底）、拖拽跟随、鼠标移动绘制、按钮防连点。
- 时间戳版实现：记录上次执行时间，距上次不足间隔则直接忽略，够间隔则执行并更新时间。
- 防抖与节流的对比：防抖**合并为一最后次**，节流**稀释成均匀频次**；等停下来才做用防抖，操作过程中持续做用节流。

```js
// composables/useThrottle.js
export function useThrottle(fn, interval = 200) {
  let lastTime = 0;

  function throttledFn(...args) {
    const now = Date.now();
    if (now - lastTime < interval) return;
    lastTime = now;
    fn(...args);
  }

  return throttledFn;
}

// 使用：滚动事件每 200 毫秒最多检查一次触底
const handleScroll = useThrottle(checkReachBottom, 200);
```

> [!IMPORTANT]
> **重要内容**：scroll、resize、mousemove、input 是前端更新性能的四大高频源头，监听它们的回调**一律先节流或防抖再注册**；回调里还应避免触发强制同步布局（读取 offsetTop 等）与大批量响应式写入。

**速记**：节流 = **按表执行**，密集触发**稀释成固定频次**。



### 代码组织最佳实践

#### SFC 命名与组件规范

**组件命名规范**：单文件组件文件名应使用**多个单词的大驼峰命名**，组件在模板中引用时保持同样的多词形态，避免与原生 HTML 元素冲突。

- 多词是硬要求：单单词名（如 Item、Header）可能与现有或未来的 HTML 元素重名，多词名（如 ListItem、PageHeader）天然隔离。
- 大驼峰是统一形态：文件名 UserList.vue、注册与模板中使用 UserList，保持一致便于检索与 KeepAlive 的 include 按名匹配。
- 文件即组件：一个文件只放一个组件，文件名即组件名，不做多组件混居。

```html
<!-- 反例：单单词，易与原生元素或第三方组件撞名 -->
<!-- Item.vue / Table.vue / Button.vue -->

<!-- 正例：多词大驼峰，语义清晰且无冲突 -->
<!-- UserList.vue / OrderDetail.vue / PageHeader.vue -->
<template>
  <UserList />
</template>
```

> [!NOTE]
> **提醒内容**：KeepAlive 的 include 与 exclude 按**组件 name** 匹配，script setup 语法下 Vue 会自动以文件名推断 name；若文件名不规范，缓存名单也会跟着失效，这是命名规范影响运行行为的实际入口。

**速记**：组件名 = **多词 + 大驼峰 + 文件名一致**。



#### props 与 emits 的显式声明

**显式契约**：组件的 props 与 emits 必须用 defineProps 与 defineEmits **完整显式声明并标注类型**，把组件对外的输入输出变成可校验、可追溯的契约。

- props 用对象语法逐个声明类型，必填项标 required，可选项给 default。
- emits 数组声明全部事件名，可校验事件参数；未声明的事件在开发环境会收到警告。
- Vue 3.5 起 defineProps 支持**响应式 props 解构**（稳定特性），解构后仍保持响应性，默认值直接用原生写法配合。
- 声明的收益：模板类型检查、开发警告、文档化三重保障，排查数据流问题时可快速定位契约。

```html
<script setup>
// props：逐个类型 + 必填与默认值
const props = defineProps({
  userId: { type: Number, required: true },
  status: { type: String, default: "active" },
});

// emits：显式声明全部对外事件
const emit = defineEmits(["update", "remove"]);

function handleUpdate() {
  emit("update", props.userId);
}
</script>
```

> [!WARNING]
> **警告内容**：靠组件实例上“顺手取属性”或“静默透传事件”的隐式数据流，短期省事、长期失控。props 与 emits 声明不全的组件，在使用方看来等于没有接口文档，重构与排查成本都会成倍上升。

**速记**：**props 定输入，emits 定输出**，契约**显式可校验**。



#### 单向数据流纪律

**单向数据流**：数据只能从父组件经 props **流向**子组件，子组件**不得直接修改** props，必须通过事件把变更意图上报父组件，由数据拥有者完成修改。

- 禁止行为一：在子组件内给 props 赋值，开发环境会直接收到警告。
- 禁止行为二：修改 props 传入的引用类型内部属性（如直接 push 传入的数组），虽无警告，却让数据变更来源变得不可追踪。
- 正确姿势：子组件 emit 事件携带新值，父组件修改源数据后经 props 流回；本地展示需要加工时用 computed 基于props 派生，而非复制再篡改。

```html
<!-- 子组件 ChildList.vue -->
<script setup>
const props = defineProps({ items: { type: Array, required: true } });
const emit = defineEmits(["remove-item"]);

function handleRemove(id) {
  emit("remove-item", id); // 上报意图，不直接动 props
}
</script>

<!-- 父组件持有数据并完成修改 -->
<!-- <ChildList :items="list" @remove-item="removeItem" /> -->
```

> [!IMPORTANT]
> **重要内容**：单向数据流不是形式主义，而是**数据归属权**设计——props 的所有权在父组件，子组件只有使用权与上报权。破坏单向流的代码，出现 bug 时无法回答“这次变更是谁改的”，这是调试成本飙升的总根源。

**速记**：**数据向下流，意图向上报**，改数者必须是拥有者。



#### 组合式函数抽离复用逻辑

**逻辑抽离**：同一组件内超过一屏的 setup 逻辑、或被两个以上组件重复使用的状态与行为，应抽成**组合式函数**（以 use 开头的驼峰函数），让组件专注视图、函数专注逻辑。

- 命名与结构：文件与函数都以 use 开头，如 useDebounce、useUserList；内部用 ref、computed 等组合，返回对象或数组暴露状态与方法。
- 收益一：**复用**——多个组件共享同一份实现，修一处全局生效。
- 收益二：**解耦**——组件按“用了哪些 use”组织代码，替代混杂的巨型 setup。
- 收益三：**可测**——纯逻辑函数可以脱离组件单独测试。
- 与第 14 篇《组合式函数 composables》衔接：该篇详细给出设计原则（输入参数化、副作用清理、返回值约定），本节强调其在性能与维护上的双重价值。

```js
// composables/useUserList.js：逻辑下沉，组件只剩调用
import { ref, computed } from "vue";

export function useUserList(fetchUsers) {
  const users = ref([]);
  const loading = ref(false);

  const activeCount = computed(
    () => users.value.filter((u) => u.active).length
  );

  async function load() {
    loading.value = true;
    users.value = await fetchUsers();
    loading.value = false;
  }

  return { users, loading, activeCount, load };
}
```

> [!TIP]
> **建议内容**：抽离时机遵循“**三处重复必抽离，一处超长可抽离**”。不要为尚无复用场景的逻辑过早抽象，也不要放任组件无限膨胀——组合式函数是 Vue 3 代码组织的默认答案。

**速记**：use 开头**装逻辑**，组件**只管视图**。



### 长列表虚拟滚动

#### 虚拟滚动的思路与适用场景

**虚拟滚动（Virtual Scrolling）**：只渲染**视口内可见的少量列表项**，滚动时动态替换渲染内容，让 DOM 数量恒定，从根源上解决长列表渲染卡顿。

- 原理三要素：外层容器监听滚动 → 根据 scrollTop 计算当前可见区间 → 只渲染区间内条目并用上下占位元素撑起真实滚动高度。
- 效果：一万个条目任何时刻也只有十几个 DOM 节点参与渲染与 diff，内存与更新开销双降。
- 何时需要：列表条目**成百上千**且单项渲染不轻时才启用；几十条的普通列表用 key 优化加 v-memo 足够，引入虚拟滚动反而增加复杂度。
- 方案选型：VueUse 的 useVirtualList 开箱即用，社区还有 vue-virtual-scroller 等成熟库；变高条目、多列网格等复杂场景优先选支持该特性的库而非自研。

```js
// VueUse 的 useVirtualList 最小用法
import { useVirtualList } from "@vueuse/core";

const { list, containerProps, wrapperProps } = useVirtualList(bigData, { itemHeight: 48 });
// 模板中：containerProps 绑滚动容器，wrapperProps 绑占位内层，
// v-for 只遍历返回的 list（可见区切片，item.data 才是原始条目）
```

> [!NOTE]
> **提醒内容**：虚拟滚动与第 5 篇的分页加载是两类方案——分页解决**数据传输量**，虚拟滚动解决 **DOM 渲染量**，二者可以叠加使用。数据条目多但单项极轻（纯文本行）时，先测再决定是否需要虚拟化，避免为不存在的瓶颈引入复杂度。

**速记**：虚拟滚动 = **只渲染看得见的**，DOM 数量**恒定不随数据涨**。
