## Pinia 状态管理

### 状态管理的定义与动机

#### 状态管理是多组件共享状态的提取与托管

**状态管理（State Management）**：把**多个组件共同依赖的数据**从组件内部提取出来，交给一个**独立的集中存储**统一维护，任何组件都能读取与修改，修改后所有依赖处自动更新。

- **局部状态**：只属于单个组件的数据，如输入框内容、弹窗开关，留在组件内即可。
- **共享状态**：被多处依赖的数据，如**登录用户**、**购物车**、**主题配色**、**权限信息**，适合提取托管。
- 共享状态的三个核心动作：**读取**、**修改**、**通知**——集中存储让这三个动作都有唯一入口。
- 托管之后数据流向单一：谁改的、改了什么、谁会受影响，都可预测、可追踪。

> 状态管理的意义不在“数据放在哪里”，而在“**谁能改、按什么规则改**”。把散落各处的修改收拢到一个地方，是状态库存在的根本理由。

**速记**：共享状态**提取出来、集中托管**，读写有唯一入口。



#### props 传值在全局共享上的局限

**props 的定位**：props 适合**父子组件之间**的定向传值，一旦用于全局共享，就会暴露三个结构性局限。

- **逐层透传**：深层组件需要的数据，中间每一层都得声明并转发 props，形成无意义的传递链。
- **兄弟通信绕路**：互不相邻的兄弟组件要共享数据，只能把状态提升到**共同父级**，再各自向下传。
- **修改回传繁琐**：子组件改数据要走“向父级发事件、父级改数据、父级再传回来”的往返。

> 《8. 组件基础与 props.md》已说明 props 是单向数据流，这保证了组件间的清晰契约；但全局共享要求的是“处处可读、处处可写”，两者目标不同，props 不该承担全局状态托管的角色。

**速记**：props 管**父子定向**，不管**全局共享**。



#### provide 与 inject 在全局共享上的局限

**provide 与 inject 的定位**：依赖注入解决的是**祖先到后代**的深层传递问题，但它依然不是全局状态方案。

- **方向受限**：数据只能从祖先流向后代，脱离这条组件链的其他组件拿不到。
- **隐式性强**：注入的数据来源分散在各层祖先里，追踪“这份状态是谁提供的、被谁改的”很困难。
- **缺少统一修改入口**：inject 拿到数据后各自随意修改，没有集中约束，调试时难以定位变更源头。

> 《11. 依赖注入 provide 与 inject.md》中的定位是“跨层级的组件内通信”；当共享范围扩大到**整个应用、与组件树无关**时，就应换成集中式的 Pinia。

**速记**：注入管**深层定向**，状态库管**全局无关组件树**。



### Pinia 的定位与优势

#### Pinia 是 Vue 官方推荐的状态管理库

**Pinia**：由 Vue 官方团队维护的**状态管理库**，自 2025 年起的当前大版本为 **Pinia 3**，仅支持 Vue 3，是官方推荐的全局状态方案。

- 出身：Pinia 最初是 **Vuex 5 的原型**，实验过程中验证了更简洁的设计，最终以独立品牌发布。
- 现状：官方文档明确推荐新项目使用 Pinia，Vuex 仅用于维护存量项目。
- 能力：完整支持 **DevTools 调试**、**热更新**、**SSR 服务端渲染**、**TypeScript**。
- 体验：API 极简，没有 mutations 一层，会写组合式函数就会写 Pinia。

> 判断一个库是否是“官方推荐”，看 Vue 官方文档的生态页即可：Pinia 与 Vue Router 并列，是仅有的两个官方核心生态库。

**速记**：Pinia 是 **Vuex 5 原型演化**来的**官方首选**。



#### Pinia 与 Vuex 的核心差异

**核心差异**：Pinia 砍掉了 Vuex 的 **mutations** 层，让 store 更扁平、类型推导更自然。

- **无 mutations**：actions 直接承担**同步与异步**的修改，少一层提交仪式。
- **天然 TypeScript 支持**：类型自动推导，不需要 Vuex 那样的复杂泛型包装。
- **store 自由拆分**：每个 store 是独立单元，用到的才导入，无全局单一大仓库。
- **无嵌套模块**：没有 Vuex 的 module 嵌套与命名空间，所有 store 平级，需要关联时在 action 或 getter 里互相调用。
- **DevTools 支持**：时间旅行、状态快照、action 追踪一应俱全，不因结构简化而牺牲调试能力。

> 结构上的取舍：Vuex 用“state、getters、mutation、action”四层保证严格流程，Pinia 认为**流程约束可以交给约定与类型**，换来更少的样板代码。迁移存量 Vuex 项目时可渐进进行，两者甚至可短期共存。

**速记**：Pinia 对 Vuex 的差别记一条主线——**去掉 mutations、拆平模块、类型白送**。



### 安装与注册

#### 安装 pinia 并注册到应用实例

**安装注册**：只有两步——**安装依赖包**，再**创建 Pinia 实例并挂载到应用**，之后任何组件都能创建 store。

- 安装：npm install pinia。
- 创建：调用 createPinia() 得到一个 Pinia 实例。
- 注册：用 app.use(pinia) 把实例装进 Vue 应用。
- 使用：此后所有组件与插件中都可以调用 defineStore 派生的 useStore 函数。

```js
// main.js
import { createApp } from "vue";
import { createPinia } from "pinia";
import App from "./App.vue";

const app = createApp(App);

app.use(createPinia()); // 创建并注册 Pinia 实例
app.mount("#app");
```

> [!IMPORTANT]
> **重要内容**：app.use(createPinia()) 必须发生在**第一次使用 store 之前**。路由守卫这类可能先于挂载执行的代码若要用 store，同样以“pinia 已注册”为前提，处理方式见后文组件外使用 store 一节。

**速记**：安装两步走——**createPinia 创建，app.use 注册**。



### defineStore 定义 store

#### 选项式风格定义 store

**选项式风格（Option Store）**：以 **id、state、getters、actions** 四个选项定义 store，写法与组件的选项式 API 一致。

- **id**：字符串，store 的唯一标识，惯例与应用名保持一致，如 "counter" 对应 useCounterStore。
- **state**：一个**函数**，返回初始状态对象，保证每次创建 store 都拿到独立副本。
- **getters**：对象，每个成员是基于 state 的派生值，相当于 store 的计算属性。
- **actions**：对象，每个成员是修改状态的方法，同步异步都可以。

```js
import { defineStore } from "pinia";

export const useCounterStore = defineStore("counter", {
  // state 必须是函数，返回初始状态
  state: () => ({
    count: 0,
    step: 1,
  }),
  // getters 相当于 store 的计算属性
  getters: {
    double: (state) => state.count * 2,
  },
  // actions 是修改状态的方法
  actions: {
    increment() {
      this.count += this.step;
    },
  },
});
```

> state 写成函数与 data 写成函数是同一个理由：**对象是引用类型**，若直接写字面量，多处导入会共享同一个对象，重置与隔离都会失效。

**速记**：选项式四件套——**id、state 函数、getters、actions**。



#### 组合式风格定义 store

**组合式风格（Setup Store）**：defineStore 的第二个参数传入一个 **setup 函数**，在其中定义响应式状态并返回，ref 等价 state、computed 等价 getters、函数等价 actions。

- **ref 与 reactive**：定义的响应式数据就是 **state**。
- **computed**：定义的计算属性就是 **getters**。
- **普通函数**：修改状态的方法就是 **actions**。
- **返回值**：函数体内定义了什么，就要**返回什么**，未返回的内容不会被暴露。

```js
import { defineStore } from "pinia";
import { ref, computed } from "vue";

export const useCounterStore = defineStore("counter", () => {
  // ref 等价于 state
  const count = ref(0);
  const step = ref(1);

  // computed 等价于 getters
  const double = computed(() => count.value * 2);

  // 函数等价于 actions
  function increment() {
    count.value += step.value;
  }

  // 必须把要暴露的 state、getter、action 全部返回
  return { count, step, double, increment };
});
```

> [!NOTE]
> **提醒内容**：组合式风格里没有 state 选项，但 id 依然必须有，且**两个 id 不可重复**。setup 函数只会在 store 首次使用时执行一次，之后所有调用共享同一份实例。

**速记**：组合式三对应——**ref 即 state，computed 即 getter，函数即 action**，最后**全部 return**。



#### 两种风格的选型

**选型标准**：两种风格**没有性能与能力上的本质差异**，按团队习惯与代码形态选择即可。

- **选选项式**：团队熟悉组件选项式写法，希望 state、getters、actions 结构一目了然，且需要直接使用 $reset。
- **选组合式**：团队全面使用 script setup，希望在 store 内复用组合式函数（如请求封装、本地存储），享受自然的类型推导。
- **可混用**：同一项目里不同 store 可以各选各的风格，互不影响。
- **附加能力**：组合式风格还允许返回**非响应式的普通变量与函数**，作为 store 的私有工具。

> 官方文档的口径是：选让自己**写起来最舒服**的那种。若拿不定主意，团队以组合式 API 为主就选组合式，以选项式为主就选选项式，关键是全项目保持一致。

**速记**：两风格**能力等价**，按团队习惯选，全项目统一。



### store 的解构

#### 直接解构 store 会失去响应性

**解构失响应陷阱**：把 store 实例直接解构，得到的只是**当时的值快照**，之后状态更新，这些变量**不会再变**，视图也随之失联。

- store 实例本质是一个**响应式对象**，属性读取经过代理追踪依赖。
- 解构是一次**普通取值**，拿到原始值后就与响应式系统断开。
- 症状：解构出的变量在模板里渲染正常，但点按钮改状态后**界面不更新**。

```js
// 错误示范：解构后失去响应性
const store = useCounterStore();

const { count, double } = store; // count、double 变成静态值

store.increment();
console.log(count); // 仍是旧值，不会随 store 更新
```

> [!WARNING]
> **警告内容**：直接解构 state 或 getters 是 Pinia 最常见的新手错误，编译器不会报错，症状只出现在**运行时视图不更新**。凡是从 store 里“拿出来用”的响应式数据，一律走 storeToRefs。

**速记**：store 直接解构等于**剪断响应线**，只留一张旧值快照。



#### storeToRefs 保证 state 与 getters 的响应性

**storeToRefs**：Pinia 提供的专用解构函数，把 store 的 **state 与 getters** 转换成对应的 ref，解构后依然保持响应式连接。

- 从 storeToRefs 的结果里解构，state 得到 **ref**，getters 得到 **computed ref**。
- 脚本里读取要带 .value，模板里照常用，Vue 会自动解包。
- getters 转出的是**只读**的 computed，赋值会被拒绝。

```js
import { storeToRefs } from "pinia";

const store = useCounterStore();

// state 与 getters 都保持响应性
const { count, double } = storeToRefs(store);

store.increment();
console.log(count.value); // 1，随 store 同步更新
console.log(double.value); // 2
```

> storeToRefs 的管辖范围只有 **state 与 getters**；对 actions 调用它是多余的——函数不存在“响应性”一说，转出来反而不方便。

**速记**：响应式数据要带走，用 **storeToRefs** 打包成 ref。



#### actions 可以直接解构

**actions 无需 storeToRefs**：action 是**函数**不是状态，直接从 store 上解构就能用，不存在失去响应性的问题。

- 函数是“行为”，解构拿到的引用与原方法一致，调用结果不变。
- Pinia 已把 action 内部的 this **绑定到 store 实例**，解构后调用依然正确读写原 store。
- 实践中常见写法：状态用 storeToRefs 解构，方法直接从 store 上解构。

```js
const store = useCounterStore();

// state 与 getters 走 storeToRefs
const { count, double } = storeToRefs(store);

// actions 直接解构即可
const { increment } = store;

increment();
console.log(count.value); // 1，方法与状态依然联动
```

> 一句话分工：**响应式数据用 storeToRefs，方法直接解构**。二者混用正是规范写法，不要为了“统一”把 action 也塞进 storeToRefs。

**速记**：action 是函数不是值，**直接解构不丢功能**。



### state 的修改方式

#### 直接修改与 $patch 批量修改

**state 的修改方式**：有三条路径——组件里**直接赋值**、用 **$patch 批量修改**、在 **action 里封装修改**，三者都合法。

- **直接赋值**：store.count = 10，简单直接，适合改单个字段。
- **$patch 对象式**：传入一个部分状态对象，一次提交多个字段的修改。
- **$patch 函数式**：传入接收 state 的函数，可基于**旧值运算**，适合复杂变更。

```js
const store = useCounterStore();

// 方式一：直接赋值
store.count = 10;

// 方式二：$patch 对象式，一次改多个字段
store.$patch({
  count: 20,
  step: 5,
});

// 方式三：$patch 函数式，基于旧值运算
store.$patch((state) => {
  state.count += state.step;
  state.step *= 2;
});
```

> $patch 的价值在于**批量与合并**：一次 $patch 修改多个字段，只会触发**一次订阅回调与一条 DevTools 记录**；逐个赋值则每改一个字段就通知一次，调试时间线也更碎。

**速记**：单字段**直接改**，多字段**$patch 一次提交**，复杂逻辑**交给 action**。



#### $reset 重置 store 状态

**$reset()**：无参数调用，把 store 的 state 恢复为**定义时的初始值**，是选项式 store 的专属方法。

- 内部逻辑：重新执行 state 函数，用返回的新对象替换当前状态。
- 选项式 store 直接可用：store.$reset()。
- 组合式 store **没有 $reset**，调用会报错，需要自行实现一个 reset 函数。

```js
// 选项式 store：直接使用 $reset
store.$reset(); // count、step 恢复为初始值

// 组合式 store：自行实现重置
export const useCounterStore = defineStore("counter", () => {
  const count = ref(0);
  const step = ref(1);

  function reset() {
    count.value = 0;
    step.value = 1;
  }

  return { count, step, reset };
});
```

> [!CAUTION]
> **注意内容**：在组合式 store 上调用 $reset 会直接**抛出异常**，因为 Pinia 无法得知各 ref 的初始值。把重置逻辑封装成同名 action 返回，是对齐两种风格惯用做法。

**速记**：$reset 是**选项式专属**，组合式**自己写 reset**。



### getters 派生状态

#### getter 通过 this 访问同 store 的其他 getter

**getter 的定位**：getter 是 store 上的**计算属性**，基于 state 派生并缓存；选项式风格里除了接收 state 参数，还能用 **this** 访问同一个 store 的其他 getter 与状态。

- 箭头函数写法只能拿 state 参数，看不到 this。
- 普通 function 写法里，this 指向 **store 实例**，可以级联引用其他 getter。
- getter 之间可以互相组合，形成派生链。

```js
export const useCounterStore = defineStore("counter", {
  state: () => ({
    count: 2,
  }),
  getters: {
    // 箭头函数：只用 state
    double: (state) => state.count * 2,
    // 普通 function：用 this 引用其他 getter
    quadruple() {
      return this.double * 2; // 依赖 double getter
    },
  },
});
```

> 使用 this 时必须写**普通函数**而非箭头函数，否则 this 不指向 store；TypeScript 下官方建议给 getter 标注返回类型，以获得完整的 this 类型推导。

**速记**：getter 就是 **store 的 computed**，this 串起**派生链**。



#### 返回函数实现传参 getter

**传参 getter**：getter 默认不能接收参数，需要参数时让它**返回一个函数**，由调用处传参，典型场景是“按条件查询列表”。

- 定义：getters 里返回 state.items.filter((item) => item.id === id) 的函数。
- 调用：在组件里像调方法一样传参：getTodoById(3)。
- 适用：根据 id 查条目、按分类筛选列表、格式化指定文本等。

```js
export const useTodoStore = defineStore("todo", {
  state: () => ({
    todos: [
      { id: 1, text: "学习 Pinia", done: true },
      { id: 2, text: "复习 Vuex", done: false },
    ],
  }),
  getters: {
    // 返回函数，实现传参
    getTodoById: (state) => {
      return (id) => state.todos.find((todo) => todo.id === id);
    },
  },
});

// 组件中调用
const store = useTodoStore();
console.log(store.getTodoById(1)); // { id: 1, text: "学习 Pinia", done: true }
```

> [!IMPORTANT]
> **重要内容**：**缓存边界**要认清——返回函数的 getter，外层函数的执行结果会被缓存，但**内层函数每次调用都会重新执行**，结果不做缓存。它语义上更像“带缓存外壳的方法”；若查询逻辑昂贵且调用频繁，改用组件内 computed 把参数变成响应式依赖。

**速记**：传参 getter = **getter 返回函数**，注意**内层不缓存**。



### actions 处理同步与异步

#### action 是同步与异步统一的修改入口

**action**：封装“修改 state 的成套业务逻辑”的方法，**同步与异步一视同仁**，这正是 Pinia 取消 mutations 的直接体现。

- 同步逻辑：普通函数体里直接通过 this 改 state。
- 异步逻辑：声明为 async 函数，内部用 await 等待接口结果，再更新 state。
- Vuex 中的分工“同步走 mutation、异步走 action 再提交 mutation”，在 Pinia 里合并为“**都走 action**”。
- 官方建议：凡是成套的修改逻辑（校验、请求、整理数据、写入），都收进 action，组件只负责调用。

```js
export const useUserStore = defineStore("user", {
  state: () => ({
    profile: null,
    loading: false,
  }),
  actions: {
    // 同步 action
    clearProfile() {
      this.profile = null;
    },
    // 异步 action：同步异步写法一致
    async fetchProfile(userId) {
      this.loading = true;
      try {
        const response = await fetch("/api/users/" + userId);
        this.profile = await response.json();
      } finally {
        this.loading = false;
      }
    },
  },
});
```

> action 内部的 this 指向 store 实例，能直接调用其他 action 与 getter；组合式风格里则直接读写闭包中的 ref，连 this 都不需要。

**速记**：action **同步异步一锅端**，没有 mutations 这一层。



#### action 内组合其他 store

**组合 store**：在一个 action 里**直接调用另一个 store 的 useXxxStore 函数**，即可跨 store 读写，这是 Pinia 组织复杂状态的方式。

- 用法：在 action 体内 const cartStore = useCartStore()，随后读写它的状态或调用它的 action。
- 时机：在 action 内调用是**惰性**的，运行到这一行才创建或获取实例，无初始化顺序负担。
- 典型场景：下单 action 读取购物车 store 的数据、结算后清空购物车。

```js
import { useCartStore } from "./cart";

export const useOrderStore = defineStore("order", {
  state: () => ({
    orders: [],
  }),
  actions: {
    async checkout() {
      // 在 action 内组合另一个 store
      const cartStore = useCartStore();

      const response = await fetch("/api/orders", {
        method: "POST",
        body: JSON.stringify({ items: cartStore.items }),
      });
      const order = await response.json();

      this.orders.push(order);
      cartStore.clear(); // 调用另一个 store 的 action
    },
  },
});
```

> 注意边界：跨 store 调用写在 **action 内部**是安全的；但若在两个 store 文件的**顶层定义处**互相 import 并立即调用，可能形成循环依赖。保持“用到才调”，就不会踩坑。

**速记**：store 之间**action 里互相调用**，用到才取不循环。



### 组件外使用 store

#### 非组件上下文使用 store 的时机与方式

**组件外使用 store**：路由守卫、请求拦截器等**非组件上下文**也能调用 useStore，但必须满足前提——**pinia 实例已被安装**。

- 前提一：app.use(pinia) 已经执行，否则上下文中没有 Pinia 可查。
- 常规场景：组件挂载之后调用的任何代码，直接 useStore 即可，无需传参。
- 特殊场景：**路由守卫的首次导航可能发生在 app.mount 之前**，此时把 pinia 实例作为参数传入 useStore(pinia)。
- 第二参数的意义：显式指定“从哪个 Pinia 实例创建 store”，绕开对全局安装状态的依赖。

```js
// router/index.js
import { createRouter, createWebHistory } from "vue-router";
import { useUserStore } from "@/stores/user";
import pinia from "@/stores/pinia"; // 单独导出的 pinia 实例

const router = createRouter({
  history: createWebHistory(),
  routes: [],
});

router.beforeEach((to) => {
  // 守卫可能先于 app.mount 执行，显式传入 pinia 实例
  const userStore = useUserStore(pinia);

  if (to.meta.requiresAuth && !userStore.profile) {
    return "/login";
  }
});

export default router;
```

> 把 createPinia() 的结果单独放在 stores/pinia.js 中导出，是组件外使用 store 的常用组织方式：main.js 用它注册应用，守卫与拦截器用它显式创建 store，同一实例保证状态共享。

**速记**：组件外用 store——**先装 pinia，必要时 useStore(pinia) 显式传实例**。



### 订阅与插件

#### $subscribe 订阅 state 变化

**$subscribe(回调函数, 可选配置对象)**：监听 store 中 **state 的任何变化**，变化发生时回调收到变更信息与当前状态，适合做日志、同步存储、埋点。

- 回调参数：mutation 对象（含事件类型、storeId 等）与 state（变化后的完整状态）。
- 默认行为：在组件 setup 中调用时，订阅**绑定当前组件**，组件卸载自动取消。
- **detached 选项**：传入 { detached: true }，订阅与组件解绑，组件卸载后仍持续生效。

```js
const store = useCounterStore();

store.$subscribe((mutation, state) => {
  console.log("状态变化：", mutation.type);
  console.log("当前状态：", state.count);

  // 常见用法：整份持久化到 localStorage
  localStorage.setItem("counter", JSON.stringify(state));
});
```

> 与 watch 的差别：watch 盯**指定的某个数据源**，$subscribe 盯**整个 store 的所有 state**，一次订阅覆盖全部字段；粒度粗但零遗漏，二者按需选用。

**速记**：$subscribe 盯**全 store 的 state**，detached 让订阅**独立于组件**。



#### $onAction 订阅 action 执行

**$onAction(回调函数, 可选 detached 布尔值)**：监听 store 中 **action 的调用**，回调收到包含名称、参数的上下文对象，并可通过 after 与 onError 钩子跟踪成功与失败。

- 上下文对象：name（action 名）、args（调用参数）、after（注册成功回调）、onError（注册失败回调）。
- after 在 action **成功结束后**执行，onError 在 action **抛出异常时**执行。
- 典型用途：统一日志、性能埋点、错误上报。
- 第二参数传 true 等价于 detached，订阅独立于组件存活。

```js
const store = useCounterStore();

store.$onAction(({ name, args, after, onError }) => {
  const startTime = Date.now();

  after((result) => {
    console.log(name, "执行成功，耗时", Date.now() - startTime, "ms");
  });

  onError((error) => {
    console.error(name, "执行失败：", error);
  });
});
```

> [!TIP]
> **建议内容**：$onAction 是实现**统一埋点层**的最佳挂载点——在入口文件对所有 store 订阅一次，后续新增 action 无需任何改动即可被记录。配合 detached 使用，可覆盖应用全生命周期。

**速记**：$onAction 拦截**每次 action 调用**，after 收成功，onError 收失败。



#### 持久化插件 pinia-plugin-persistedstate

**持久化插件**：社区插件 pinia-plugin-persistedstate 可以把 store 的 state **自动写入 localStorage**，刷新页面后自动恢复，免去手写同步代码。

- 安装：npm install pinia-plugin-persistedstate。
- 注册：创建 pinia 实例后调用 pinia.use(piniaPluginPersistedstate)。
- 开启：store 的选项里写 persist: true，即对整个 state 持久化。
- 进阶：persist 支持配置 key、存储介质与**部分字段**（paths），可只持久化指定状态。

```js
// main.js：注册插件
import { createPinia } from "pinia";
import piniaPluginPersistedstate from "pinia-plugin-persistedstate";

const pinia = createPinia();
pinia.use(piniaPluginPersistedstate);
```

```js
// store 内按需开启
export const useUserStore = defineStore("user", {
  state: () => ({
    token: "",
    profile: null,
  }),
  // 整个 state 自动持久化
  persist: true,
});
```

> [!NOTE]
> **提醒内容**：插件的具体配置项以 **pinia-plugin-persistedstate 官方文档**为准，不同大版本之间配置格式有差异。持久化的是**明文 localStorage**，token 等敏感信息要评估安全策略后再决定是否落盘。

**速记**：持久化三步——**装插件、pinia.use 注册、store 里 persist: true**。



### 用 store 替代事件总线

#### 事件总线在 Vue 3 中被移除

**事件总线的消失**：Vue 3 从组件实例上**移除了 $on、$off、$once** 三个方法，Vue 2 时代“把组件实例当事件总线”的跨组件通信模式不再可用。

- Vue 2 的做法：用一个空 Vue 实例（或根实例）调用 $on 注册、$emit 触发，充当全局事件枢纽。
- Vue 3 的变化：实例不再实现事件接口，$on 与 $off 被彻底移除，官方将此定位为“全局事件总线不适合大型应用的可维护性”。
- 官方替代方向：**集中式状态管理**——跨组件“通知”的本质是共享状态的变化与流转。
- Pinia 对应关系：总线上的“事件携带数据”对应 store 的 **state**，“触发事件”对应调用 **action**，“监听事件”对应组件对状态的响应或 $subscribe。

```js
// Vue 2 事件总线写法（Vue 3 已不可用）
// bus.$on("cart-changed", handler);
// bus.$emit("cart-changed", items);

// Vue 3 用 store 表达同样的通信
export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [],
  }),
  actions: {
    addItem(item) {
      this.items.push(item); // 相当于"发出事件"并携带数据
    },
  },
});

// 任何组件读取 items 即相当于"监听事件"
```

> 《12. 事件处理.md》里的自定义事件讲的是**组件之间的显式通信**，那是事件机制的正确舞台；而“任意组件、任意方向”的全局通知，本质是**共享状态问题**，交给 store 更可追踪、可调试。确需轻量事件通道的边缘场景，可引入 mitt 这类专用库，但先审视是否真的绕得开 store。

**速记**：Vue 3 移除 **$on 与 $off**，跨组件通知**交给 store**——state 当数据，action 当通知。
