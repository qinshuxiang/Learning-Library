## 响应式原理：Proxy 与依赖收集

### 响应式系统的定义

#### 响应式系统是自动追踪与触发的机制

**响应式系统（Reactivity System）**：是框架**自动追踪状态的读取**，并在**状态变化时触发依赖它的副作用重新执行**的一套机制。

- **追踪（track）**：某段代码读取了响应式数据，系统把这次读取记录下来，建立数据与代码的关联。
- **触发（trigger）**：数据被修改时，系统根据记录找到所有依赖它的代码，通知它们重新执行。
- **副作用（effect）**：依赖响应式数据的函数统称副作用，组件渲染、计算属性、侦听器都是副作用。
- 最终效果：开发者只修改数据，框架自动完成界面更新，无需手动操作 DOM。

> 响应式的本质是**数据与视图的自动同步**：读取时记录谁用了它、变化时通知谁重跑。本篇的所有机制，都是围绕 track 与 trigger 这两个动作展开的。

**速记**：响应式 = **读取时追踪** + **变化时触发**。



#### 响应式系统的两个核心环节

**依赖收集与派发更新**：是响应式系统运转的两个核心环节，前者发生在读取时，后者发生在写入时。

- **依赖收集（依赖追踪）**：副作用执行过程中访问响应式数据，系统将「哪个副作用依赖了哪条数据」登记到存储结构中。
- **派发更新**：数据被写入后，系统从存储结构中取出依赖它的全部副作用，按某种调度策略让它们重新执行。
- 两个环节必须配套：只收集不派发，改了数据没反应；只派发不收集，系统不知道该通知谁。

> [!IMPORTANT]
> **重要内容**：依赖收集发生在**副作用执行期间**，靠的是「执行副作用时先把它标记为当前活跃副作用，读取数据时顺手登记」。没有这个标记机制，track 就不知道该把谁登记为依赖，这是理解全篇的关键前提。

**速记**：**收集在读、派发在写**，两环缺一不可。



### Vue2 的响应式方案与局限

#### Object.defineProperty 的劫持方式

**Vue2 的响应式基础**：是 Object.defineProperty，它在**初始化时递归遍历对象的每个属性**，把每个属性都改造成带 getter 与 setter 的存取属性。

- Object.defineProperty(对象, 属性名, 描述符) 只能针对**已存在的单个属性**定义拦截。
- getter 里做依赖收集，setter 里做派发更新，思路与 Vue3 相同。
- 问题出在拦截粒度：它劫持的是**属性**而非**对象**，凡是「属性集合发生变化」的操作都无法感知。

```js
const data = { count: 0 };

Object.defineProperty(data, "count", {
  get() {
    console.log("读取 count，可在此收集依赖");
    return data._count;
  },
  set(value) {
    console.log("写入 count，可在此触发更新");
    data._count = value;
  },
});

data.count = 1; // 触发 set，可以触发更新
data.newKey = 2; // 静默成功，set 完全不知情
```

> 手动封装示例只用于展示原理：真实 Vue2 由 observe 函数递归遍历 data 的全部属性逐个劫持。劫持粒度是属性这一点，直接决定了后面三个局限。

**速记**：Vue2 劫持的是**属性**，不是对象，先天缺陷由此而来。



#### 新增与删除属性监听不到

**Vue2 无法侦测属性的新增与删除**：因为 Object.defineProperty 只能劫持初始化时已存在的属性，对后来新增或删除的属性无能为力。

- 给响应式对象添加新属性：新属性**没有 getter 与 setter**，赋值不会触发更新。
- 删除已有属性：deleteProperty 的拦截在 defineProperty 方案里根本不存在。
- Vue2 的补丁是提供 Vue.set 与 Vue.delete（实例内为 this.$set 与 this.$delete）：由这两个方法**代替开发者手动触发更新**，属于 API 层面的补救而非能力修复。
- 常见踩坑场景：直接用索引给数组元素赋值、直接给对象添加新字段，视图都不更新。

> [!CAUTION]
> **注意内容**：在 Vue2 项目里绕过 $set 直接添加属性，数据确实改成功了，但界面纹丝不动，这类「数据变了视图不变」的 bug 排查成本很高。Vue3 的 Proxy 从拦截层面根治了这个问题，不再需要 $set。

**速记**：Vue2 新增删除**侦测不到**，只能靠 $set 打补丁。



#### 数组索引与 length 监听不到

**Vue2 监听不到数组的下标赋值与 length 修改**：defineProperty 语法上无法对数组索引与 length 这样的特殊属性生效，这是语言的限制而非实现疏忽。

- arr[索引] = 新值：无法被劫持，Vue2 内部干脆放弃了这条路径。
- arr.length = 新值：同样监听不到。
- Vue2 的对策是**重写数组的七个变更方法**：push、pop、shift、unshift、splice、sort、reverse，让这些方法在执行原逻辑后手动派发更新。
- 后果是「变异方法可以触发更新，直接改下标不行」，开发者被迫统一用 splice 或 $set 改数组。

```js
const list = [1, 2, 3]; // Vue2 中 list 是被观察的数组

list.push(4); // 重写过的 push，能触发更新
list[3] = 99; // 直接改下标，不触发更新
list.length = 0; // 改 length，不触发更新
```

> 重写方法只能覆盖「调用方法」这一种修改方式，无法覆盖「直接赋值」这种更自然的写法。Vue3 的 set 捕获器对数组下标赋值同样生效，从根上消除了这组特殊规则。

**速记**：Vue2 数组靠**重写七个方法**，下标赋值**听不见**。



#### 初始化需全量递归遍历

**Vue2 的响应式转换是初始化时全量递归**：组件创建时就递归遍历整个 data 对象，把所有层级的所有属性全部提前劫持。

- 无论某个属性最终是否被视图用到，初始化时都会被劫持一遍，存在**无谓的开销**。
- 层级越深、字段越多，初始化代价越大，大对象会明显拖慢首屏。
- 初始不存在的属性不会被劫持，这也是「新增属性监听不到」的另一面。

> Vue3 改为**惰性转换**：只有真正被读取的嵌套对象才在读取那一刻被代理，未用到的部分完全不付出代理成本。这一对比是 Vue2 与 Vue3 性能差异的经典考点。

**速记**：Vue2 **初始化全量递归**，Vue3 **用到处才代理**。



### Vue3 的 Proxy 方案与优势

#### Proxy 代理整个对象

**Vue3 的响应式基础**：是 ES6 的 Proxy，它代理的是**整个对象**而非单个属性，对象上的任何读写操作都会先经过代理层。

- new Proxy(target, handler) 返回代理对象，handler 中定义各类**捕获器（trap）**拦截对应操作。
- get 捕获器拦截读取，在其中做 track；set 捕获器拦截写入，在其中做 trigger。
- 拦截发生在**操作对象这一层**，属性是原有的还是新增的、是对象属性还是数组下标，统统经过代理，能力天然完整。

```js
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key); // 读取时收集依赖
      return Reflect.get(target, key, receiver);
    },
    set(target, key, value, receiver) {
      const result = Reflect.set(target, key, value, receiver);
      trigger(target, key); // 写入后触发更新
      return result;
    },
  });
}

const state = reactive({ count: 0 });
state.count = 1; // set 捕获器触发 trigger
```

> Proxy 与 Reflect 的基础语法与捕获器全貌，在《29. Proxy、Reflect 与响应式》中已系统讲解并给出手写示例，本篇聚焦二者在 Vue 响应式中的职责分工。

**速记**：Vue3 用 Proxy **代理整个对象**，get 里 track、set 里 trigger。



#### 十三种捕获器覆盖全部对象操作

**Proxy 提供十三种捕获器**：覆盖对象的全部底层操作，Vue3 从中选用若干种来支撑响应式的各个角落。

- **get**：拦截属性读取，是 track 的挂载点。
- **set**：拦截属性写入，是 trigger 的挂载点。
- **has**：拦截 in 操作，支撑模板中 key in obj 一类判断的依赖追踪。
- **deleteProperty**：拦截 delete 操作，使删除属性也能触发更新。
- **ownKeys**：拦截 Object.keys、for...in、Object.getOwnPropertyNames 等，支撑 v-for 遍历对象与 Object.keys 的依赖追踪。
- **getPrototypeOf、setPrototypeOf、apply、construct** 等：其余捕获器负责原型、函数调用等操作，响应式系统按需使用。

> [!TIP]
> **建议内容**：不必背全十三个捕获器的签名，优先记住响应式最依赖的四个——get、set、has、deleteProperty，再知道 ownKeys 管遍历即可，其余在《29. Proxy、Reflect 与响应式》中按需查阅。

**速记**：Proxy **十三捕获器**，响应式主打 **get、set、has、deleteProperty**。



#### 新增、删除属性与数组操作都可拦截

**Proxy 对属性集合的变化天然可拦截**：新增属性走 set、删除属性走 deleteProperty、成员判断走 has、数组下标赋值同样走 set，全部都能触发更新。

- 新增属性：state.newKey = 值，命中 set 捕获器，与修改已有属性走同一条路，无需 $set。
- 删除属性：delete state.key，命中 deleteProperty，可在其中对删除这一变更做 trigger。
- 数组下标：arr[5] = 值 本质是属性写入，命中 set；push 等方法内部也是下标写入与 length 写入，一并被拦截。
- 这组能力让 Vue2 的 $set、$delete 与数组变异方法重写全部成为历史。

```js
const state = reactive({ list: [1, 2] });

state.extra = "新属性"; // set 捕获器，触发更新
delete state.extra; // deleteProperty 捕获器，触发更新
state.list[0] = 99; // 数组下标赋值，set 捕获器，触发更新
```

> Proxy 直接拦截操作本身，不区分「老属性」与「新属性」，这正是它比 defineProperty 更完善的根本原因。

**速记**：**增、删、改、遍历**，Proxy 全部拦得住，$set 退休。



#### Set 与 Map 的支持

**Vue3 的响应式可以作用于 Set 与 Map**：defineProperty 只能劫持普通对象的属性，对集合类型完全无效，而 Proxy 能拦截集合的读写操作。

- Set 与 Map 的增删查走的是方法调用而非属性赋值，defineProperty 无从下手。
- Proxy 通过 get 捕获器拦截集合方法的读取，对 add、delete、has、get、set 等方法做包装，实现集合的响应式。
- WeakMap、WeakSet 同理可被代理，Vue3 内部为集合类型准备了一套独立的处理逻辑。

```js
const set = reactive(new Set([1, 2]));
set.add(3); // 可被追踪，触发依赖更新
set.has(3); // 可被收集为依赖

const map = reactive(new Map([["a", 1]]));
map.set("b", 2); // 可被追踪，触发依赖更新
```

> Vue2 时代想在响应式数据里用 Set 与 Map 基本只能绕道普通对象；Vue3 中它们是一等公民，这正是 Proxy「拦截操作而非属性」的又一个直接收益。

**速记**：集合类型 **Set 与 Map**，Vue3 原生支持，Vue2 无能为力。



#### 嵌套对象惰性代理

**Vue3 的深层响应式是惰性的**：reactive 只代理最外层对象，嵌套的子对象要等到**被读取的那一刻**才被转换为代理。

- get 捕获器返回属性值时，若值是对象，则先把这个子对象也包一层 reactive 再返回。
- 于是访问路径走到哪一层，哪一层才付出代理成本，未被访问的深层对象零开销。
- Vue2 则在初始化时递归转换全部层级，代价提前一次性付清（见前文）。

```js
const state = reactive({
  profile: { name: "张三" },
});

// 此刻 profile 还是普通对象，尚未被代理
const profile = state.profile; // 读取触发 get，profile 在此刻才被代理
profile.name = "李四"; // 已是代理对象，可触发更新
```

> [!NOTE]
> **提醒内容**：惰性代理是「读取时逐层转换」的简化心智模型，Vue3 内部还有缓存已代理对象、避免重复包装等细节。把握「用到哪层、代理哪层」这一结论即可，不必深究内部实现。

**速记**：嵌套对象**读到才代理**，深层未用不花钱。



### 依赖收集的三个角色

#### effect：副作用函数

**effect（副作用函数）**：是依赖响应式数据的函数，是依赖收集的基本单位——系统追踪与触发的对象都是它。

- 执行 effect 时，函数体内读取的每个响应式属性都会把该 effect 登记为自己的依赖。
- 组件的渲染函数、computed 的 getter、watch 的回调，在框架内部都被包装成 effect。
- 依赖收集依赖一个全局标记 **activeEffect（当前活跃副作用）**：effect 执行前把自己设为 activeEffect，执行结束后还原，读取数据时 track 只登记 activeEffect。

```js
let activeEffect = null;

function effect(fn) {
  activeEffect = fn;
  fn(); // 执行期间读取响应式数据，触发 track 登记 activeEffect
  activeEffect = null;
}
```

> effect 执行期间嵌套执行另一个 effect 时，单个全局变量的标记会互相覆盖，Vue 内部用 effect 栈来处理嵌套场景；简化模型中记住 activeEffect 的作用即可。

**速记**：effect 是**依赖的单位**，靠 activeEffect 标记谁正在跑。



#### track：读取时收集依赖

**track（追踪）**：是读取响应式属性时执行的收集动作，把当前 activeEffect 登记到该属性的依赖集合中。

- 挂载位置：Proxy 的 get 捕获器内，每次读取都先 track 再返回值。
- 登记对象：只有 activeEffect 存在时才登记，普通代码（不在任何 effect 中）读取数据不产生依赖。
- 登记去向：存入三层结构 targetMap → depsMap → dep，详见下节。
- 一个属性可以有多个依赖（多处模板用了同一个数据），dep 用集合天然去重与容纳。

```js
function track(target, key) {
  if (!activeEffect) return; // 不在任何 effect 中，无需收集
  let depsMap = targetMap.get(target);
  if (!depsMap) targetMap.set(target, (depsMap = new Map()));
  let dep = depsMap.get(key);
  if (!dep) depsMap.set(key, (dep = new Set()));
  dep.add(activeEffect); // 登记：当前副作用依赖了 target 的 key
}
```

> track 回答的问题是「**谁在用我**」。它在读取路径上执行，因此依赖关系是在副作用首次执行时自然建立的，无需开发者声明。

**速记**：track 在 **get 里登记 activeEffect**，回答「谁在用我」。



#### trigger：写入时触发更新

**trigger（触发）**：是写入响应式属性后执行的派发动作，从存储结构中取出该属性名下的全部依赖并让它们重新执行。

- 挂载位置：Proxy 的 set 捕获器内，先完成真正的赋值（Reflect.set），再 trigger。
- 取出依赖：按 target 与 key 定位到 dep，遍历其中每个 effect 重新执行。
- 重新执行的 effect 会再次读取数据，从而**重新收集依赖**，依赖关系随代码分支的变化自动修正。
- Vue3 中 effect 重新执行通常不直接调用函数本身，而是交给调度器排队，详见后文「从状态更新到视图更新」。

```js
function trigger(target, key) {
  const depsMap = targetMap.get(target);
  if (!depsMap) return;
  const dep = depsMap.get(key);
  if (dep) dep.forEach((fn) => fn()); // 通知所有依赖它的副作用
}
```

> [!WARNING]
> **警告内容**：trigger 里直接同步执行副作用会带来两个问题——一次同步代码里改多个属性会触发多轮重复渲染，effect 内部再改状态可能无限递归。真实 Vue3 为每个 effect 配备调度器，把重执行排入队列延后批量处理，本节代码仅是原理演示。

**速记**：trigger 在 **set 里取出 dep 重跑**，回答「该通知谁」。



### 依赖的存储结构

#### 三层嵌套的 targetMap、depsMap 与 dep

**依赖的存储结构是三层嵌套**：WeakMap 套 Map 再套 Set，回答「哪个对象、哪个属性、被哪些副作用依赖」。

- **targetMap（第一层，WeakMap）**：以原始对象 target 为键，值为该对象的依赖映射；一个对象对应一条。
- **depsMap（第二层，Map）**：以属性名 key 为键，值为该属性的依赖集合；一个属性对应一条。
- **dep（第三层，Set）**：存放依赖该属性的 effect 集合；Set 自动去重，同一 effect 重复读取只登记一次。
- 整体形状可用类型签名概括：

```text
WeakMap<target, Map<key, Set<effect>>>
```

> 三层各司其职：WeakMap 按**对象**分桶，Map 按**属性**分格，Set 装**副作用**。这个结构与《29. Proxy、Reflect 与响应式》中手写实现的依赖桶完全一致，两篇可对照阅读。

**速记**：**WeakMap 分对象、Map 分属性、Set 装依赖**。



#### WeakMap 带来的 GC 友好

**targetMap 选用 WeakMap 而非 Map**：是为了让依赖结构**不妨碍对象被垃圾回收**，组件销毁后相关依赖自动可回收。

- WeakMap 的键是**弱引用**：对象在其他地方都不再被引用后，即使 targetMap 里还留着它的键，垃圾回收也能将其连同对应依赖一起回收。
- 若换成普通 Map，键是强引用，组件销毁后对象仍被 targetMap 持有，内存无法释放，长页面会持续累积。
- 弱引用的代价是 WeakMap 不可遍历、拿不到键列表，而依赖收集恰好只需要「拿着对象查依赖」，不需要遍历，二者完美匹配。

> [!IMPORTANT]
> **重要内容**：弱引用与垃圾回收的底层原理，在《17. 执行上下文与内存管理》中已系统讲解。targetMap 是「弱引用工程应用」的经典案例：数据结构的选择直接决定了内存行为。

**速记**：WeakMap **弱引用键**，组件销毁依赖随对象**自动回收**。



#### 简化版手写实现

**手写最小响应式系统**：把 effect、track、trigger 与 reactive 组合起来，即可得到一个能跑通「数据变、副作用自动重跑」的最小实现。

```js
// 依赖桶：WeakMap<target, Map<key, Set<effect>>>
const targetMap = new WeakMap();
let activeEffect = null;

// 注册副作用：执行一次 fn，期间读到的响应式属性都会收集它
function effect(fn) {
  activeEffect = fn;
  fn(); // 首次执行，完成依赖收集
  activeEffect = null;
}

// 读取时收集：把 activeEffect 登记到 target 的 key 名下
function track(target, key) {
  if (!activeEffect) return;
  let depsMap = targetMap.get(target);
  if (!depsMap) targetMap.set(target, (depsMap = new Map()));
  let dep = depsMap.get(key);
  if (!dep) depsMap.set(key, (dep = new Set()));
  dep.add(activeEffect);
}

// 写入时触发：取出 target 的 key 名下全部副作用并重跑
function trigger(target, key) {
  const depsMap = targetMap.get(target);
  if (!depsMap) return;
  const dep = depsMap.get(key);
  if (dep) dep.forEach((fn) => fn());
}

// 用 Proxy 把普通对象变成响应式对象
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key);
      return Reflect.get(target, key, receiver);
    },
    set(target, key, value, receiver) {
      const result = Reflect.set(target, key, value, receiver);
      trigger(target, key);
      return result;
    },
  });
}

const state = reactive({ count: 0 });
effect(() => console.log("count 是", state.count)); // 打印 count 是 0
state.count = 1; // 自动重跑，打印 count 是 1
```

> 这份实现与《29. Proxy、Reflect 与响应式》的思路一致，可视为其响应式部分在本篇语境下的重组。真实 Vue3 还要处理依赖清理（重跑前先移除旧依赖再重新收集）、effect 嵌套栈、调度器、集合类型与只读代理等，工程细节远多于此，但核心链路就是这几十行。

**速记**：**effect 标记、track 登记、trigger 派发**，三件套构成最小响应式。



### ref 的实现思路

#### RefImpl 类拦截 value 的读写

**ref 的底层是一个 RefImpl 类**：它把原始值包装成对象，通过 **value 属性的 getter 与 setter** 实现读取时 track、写入时 trigger。

- constructor 把传入值存到内部私有字段，作为真实数据。
- get value：执行 track(this, "value")，再返回内部值——ref 的依赖也走同一套三层结构。
- set value：先更新内部值，再执行 trigger(this, "value")，通知依赖此 ref 的副作用。
- .value 这个看似麻烦的写法，正是依赖收集的**必要入口**：系统拦截的就是 value 这一个属性的读写。

```js
class RefImpl {
  constructor(value) {
    this._value = value;
  }
  get value() {
    track(this, "value"); // 读取 .value 时收集依赖
    return this._value;
  }
  set value(newValue) {
    this._value = newValue;
    trigger(this, "value"); // 写入 .value 时触发更新
  }
}

function ref(value) {
  return new RefImpl(value);
}

const num = ref(0);
effect(() => console.log("num 是", num.value)); // 打印 num 是 0
num.value = 5; // 自动重跑，打印 num 是 5
```

> getter 与 setter 拦截属性读写的语法基础（存取属性、this 指向），在《22. 严格模式与对象属性描述符》与《29. Proxy、Reflect 与响应式》中均有铺垫，此处组合使用。

**速记**：ref = **类实例 + value 的 getter 与 setter**，track 与 trigger 挂在 value 上。



#### ref 不使用 Proxy 的原因

**ref 不用 Proxy 是因为值类型无法被代理**：Proxy 只能代理对象，而 ref 要承载的恰恰是 number、string、boolean 这类原始值。

- new Proxy(0, handler) 直接报错：Proxy 的 target 必须是对象，原始值不能作为代理目标。
- 即便原始值可以被代理，也没有属性读写可供拦截，track 与 trigger 无处挂载。
- 唯一出路是**包装**：把原始值装进一个对象的 value 属性里，再用类或 getter 与 setter 拦截这个属性，这就是 RefImpl 的由来。
- 若 ref 的初始值是对象，Vue 内部会借助 reactive 转换该对象，使 object ref 的深层也具备响应式。

> [!NOTE]
> **提醒内容**：脚本中读写 ref 必须带 .value，模板中则自动解包，这一语法差异的根源就在实现方式——ref 是「带 value 属性的实例」而非代理对象。相关使用规则见《3. 响应式基础：ref 与 reactive》。

**速记**：**Proxy 管不了原始值**，ref 用包装加 getter 与 setter 补位。



### computed 的惰性求值

#### dirty 脏标记机制

**computed 的缓存由 dirty（脏标记）控制**：依赖变化时只把 dirty 置回 true 表示缓存过期，**并不立即重算**，等到下一次读取 value 时才真正求值。

- computed 内部维护两个私有量：value 缓存上次结果，dirty 标记缓存是否有效。
- computed 自身也是一个 effect：依赖它的响应式数据变化时，通过调度器只执行 dirty = true，跳过真正的求值。
- 读取 value 时先检查 dirty：为 true 才执行 getter 求值并更新缓存，随后把 dirty 置为 false；为 false 则直接返回缓存。
- 若依赖变化后始终没人读取，getter 就一次也不执行——这就是「惰性」的含义。

```js
function createComputed(getter) {
  let value; // 缓存的计算结果
  let dirty = true; // 脏标记：true 表示缓存过期，需要重算

  const computedRef = {
    get value() {
      if (dirty) {
        value = getter(); // 只有「被读取且已脏」才真正求值
        dirty = false;
      }
      return value;
    },
  };

  // 真实实现：computed 内部 effect 的调度器只做 dirty = true
  // 依赖变化 → 调度器把 dirty 置回 true → 等下次读取再重算
  return computedRef;
}
```

> [!IMPORTANT]
> **重要内容**：dirty 是理解「computed 缓存」的钥匙——缓存不是靠时间，而是靠脏标记：**依赖没变 dirty 为 false，读多少次都直接用缓存；依赖变了 dirty 为 true，下次读取才重算**。这与《4. 计算属性与侦听器》中 computed 与方法的行为差异一一对应。

**速记**：依赖变化**只标脏不重算**，读取时**脏了才算**。



### 从状态更新到视图更新

#### 组件渲染本身就是 effect

**组件的渲染函数就是一个 effect**：模板编译产出的 render 函数在渲染时读取了大量响应式数据，框架把它包装成副作用交给响应式系统管理。

- render 函数执行过程中访问模板里用到的每个 ref 与 reactive 属性，这些读取全部触发 track。
- 于是「组件的更新函数」被登记为它所用到的每一条数据的依赖。
- 数据一变，trigger 找到的依赖正是「这个组件的更新函数」，通知它重新渲染——所谓视图自动更新，本质是渲染 effect 被重新执行。

```text
模板 → 编译成 render 函数 → 包装为渲染 effect
渲染 effect 执行 → 读取状态 → track 收集「渲染 effect」为依赖
状态变化 → trigger → 找到渲染 effect → 重新渲染
```

> 由此可以打通一个认知：ref 与 reactive 的更新之所以能驱动界面，不是因为视图有特殊通道，而是因为**视图本身被纳入了同一套依赖系统**。组件树、computed、watch 在框架内部统一为不同用途的 effect。

**速记**：**渲染即副作用**，视图更新就是渲染 effect 被重跑。



#### 调度器与 queueJob 批量去重

**trigger 并不直接重跑渲染 effect，而是交给调度器排队**：同一个更新函数在一次同步流程里无论被触发多少次，都只入队一次，微任务时统一刷新。

- 每个 effect 可配置调度器（scheduler）：trigger 找到依赖后不直接执行，而是调用其调度器。
- 渲染 effect 的调度器是 queueJob：把更新函数 job 加入队列，队列是 Set，**天然去重**。
- 同步代码里连改十个状态、触发十次 trigger，渲染 job 也只入队一次。
- 入队时若当前没有刷新任务在途，则通过 Promise.resolve().then 注册一次微任务刷新。
- 微任务真正执行时统一清空队列：逐个执行 job，完毕后清空队列与刷新标记。

```js
const queue = new Set(); // 去重的任务队列
let isFlushing = false;

function queueJob(job) {
  queue.add(job); // Set 保证同一 job 只存在一份
  if (!isFlushing) {
    isFlushing = true;
    Promise.resolve().then(flushJobs); // 微任务时机统一刷新
  }
}

function flushJobs() {
  queue.forEach((job) => job()); // 批量执行所有排队的更新
  queue.clear();
  isFlushing = false;
}
```

> [!TIP]
> **建议内容**：这套「入队去重加微任务批量刷新」的设计，解释了一个高频面试题——同步代码里连改三次 count，视图只更新一次。去重靠 Set 队列，批处理靠微任务，两个机制各管一半。

**速记**：trigger 后**先入队去重**，微任务里**一次刷新**，改 N 次只渲染一次。



#### 微任务时机与 nextTick 的对应关系

**queueJob 的刷新时机是微任务**：这决定了 nextTick 的行为——在 nextTick 回调里读到的 DOM 已是本次批量更新完成后的结果。

- Promise.resolve().then 进入的是**微任务队列**，在当前同步代码（宏任务）结束后立即清空执行。
- 时序：同步代码修改状态并入队渲染 job → 同步代码执行完毕 → 清空微任务 → 渲染 job 执行、DOM 更新 → 排在其后的 nextTick 回调执行，能拿到新 DOM。
- 若 nextTick 回调在状态修改之后注册，它必然排在渲染 job 之后（先注册先入队），这就是 nextTick 能拿到更新后 DOM 的原因。

```js
count.value = 1;
console.log("同步：DOM 未更新");
nextTick(() => {
  console.log("nextTick：DOM 已更新");
});
```

> 微任务、宏任务与执行顺序的完整模型，在《32. async、await 与事件循环》中已系统讲解；Vue 的批量更新只是微任务机制的一个应用场景，两篇对照可以互相印证。

**速记**：渲染排在**微任务**里，nextTick 排在渲染 job **之后**，故能拿到新 DOM。



### Vue 3.5 的重写要点

#### 版本计数与双向链表依赖

**Vue 3.5 用版本计数与双向链表重写了响应式内核**：依赖的存储与脏检查方式发生结构性变化，对外 API 保持不变。

- **版本计数（version counting）**：每条数据维护一个版本号，写入时版本号递增；computed 判断「是否变脏」只需比较版本号，无需遍历全部依赖。
- 3.5 之前的脏检查需要遍历 dep 集合逐个比对，依赖越多越慢；版本计数把判断降到近乎常数开销。
- **双向链表依赖**：dep 不再是简单的 Set，effect 与 dep 之间以双向链表相连，依赖的增删可以从链表任意一端高效操作。
- 双向链表让「清理旧依赖、重建新依赖」的过程更省，尤其利于分支切换频繁的副作用。

> [!NOTE]
> **提醒内容**：以上是便于理解的**简化后的心智模型**，内部实现细节以官方源码与发布说明为准。对学习者而言，需要记住的结论是：3.5 的重写改变了依赖的数据结构与脏检查算法，但 track 收集、trigger 派发的总体框架与前文一致。

**速记**：3.5 换内核——**版本号定脏**、**双向链表存依赖**，API 不变。



#### 重写带来的性能收益

**Vue 3.5 的响应式重写带来明确的性能收益**：官方公布内存占用降低约 56%，大数组操作明显提速。

- **内存占用降约 56%**：双向链表与更精简的依赖表示，减少了每个依赖关系占用的内存，大规模应用收益显著。
- **大数组操作提速**：遍历大数组时触发的依赖管理开销大幅下降， v-for 大列表等场景受益。
- **计算属性更稳**：版本计数让 computed 的脏检查不再随依赖规模变慢，深层依赖链的更新更可预测。
- 对开发者而言零迁移成本：这次重写完全在框架内部，业务代码无需任何改动即可受益。

> 性能数字来自 Vue 官方 3.5 发布公告的口径，具体数值随场景浮动，引用时注明「官方数据、约数」为宜。

**速记**：3.5 重写——内存**降约 56%**、大数组**提速**、业务代码**零改动**。



### Vue 3.6 与 alien signals 展望

#### 信号思想的统一趋势

**Vue 3.6 在探索基于 alien signals 的响应式实现**：信号（signals）正成为前端响应式方案的统一思想，Vue 也在向这一方向演进。

- **信号（signals）**：一种细粒度响应式原语，值本身携带依赖与版本信息，读取与订阅合为一体，SolidJS、Preact、Svelte 等框架的响应式内核均属此列。
- **alien signals**：一个高性能的信号实现库，目标是成为多框架可复用的响应式内核，Vue 官方已基于它开展 3.6 的响应式实验。
- 对 Vue 的意义：若落地，响应式的更新粒度与调度效率有望进一步提升，且 Vue 的使用方式（ref、computed、effect）保持不变——底层换引擎，上层 API 稳定。
- 学习建议：信号与 Vue 现有响应式在「依赖收集加派发更新」的骨架上同构，掌握本篇模型后，理解 signals 只是换了一套更细粒度的数据结构。

**速记**：信号是**响应式的下一站**，Vue 3.6 借 alien signals 探路，**骨架仍是 track 与 trigger**。
