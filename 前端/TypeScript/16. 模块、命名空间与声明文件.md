## 模块、命名空间与声明文件

### 模块的导入导出

**模块（module）**：是以文件为单位的封装单元，文件顶层声明的变量、函数、类与类型默认只在本文件可见，通过 export 暴露、通过 import 引入。

含顶层 import 或 export 的文件是模块，作用域彼此隔离；两者都不含的文件是脚本，顶层声明直接进入全局作用域。

> [!NOTE]
> **提醒内容**：给脚本加一行 export {} 即可把它变成模块，该语句不导出任何名字，只切换文件的作用域语义。

#### 命名导出与默认导出

**命名导出（named export）**：是按名字暴露声明的导出形式，一个模块可有任意多个。**默认导出（default export）**：是模块唯一的主出口，至多一个。

- 命名导出：声明前加 export，或先声明再统一写 export { 名字 }；导入端名字必须对应，可用 as 重命名。
- 默认导出：export default 后跟表达式，导入端名字自取；二者可共存于同一模块。

```ts
// math.ts
export const pi = 3.14;
export function double(value: number): number { return value * 2; }
export default class Vector { constructor(public x: number) {} }

// main.ts
import Vector, { pi, double } from "./math";
console.log(double(pi) + new Vector(1).x); // 7.28
```

**速记**：命名导出可有多个、导入名字须对应；默认导出至多一个、导入名字自取；二者可同时存在。



#### import 的形态与再导出

同一个模块入口可以按需要选择导入形态，模块之间也能直接转手导出。

- 具名与默认导入：import { double, pi as PI } from "./math"、import Vector from "./math"。
- 命名空间导入：import * as geometry from "./math"，把全部导出挂在一个只读对象上。
- 仅副作用导入：import "./polyfill"，只为执行模块顶层代码。
- 再导出：export { double } from "./math"、export * from "./math"、export * as vectors from "./vector"。

```ts
// barrel.ts —— 汇总出口，常见于组件库与工具库
export { double } from "./math";
export * as vectors from "./vector";
```

**速记**：import 有具名、默认、命名空间、仅副作用四种形态；再导出用 export ... from，本地不产生绑定。



#### 类型专用导入与 export type

**类型专用导入（import type）**：是只引入类型、编译后被整条擦除的导入形式，用于把类型依赖与运行时依赖分开。

- 整条语句：import type { User } from "./models"，该语句只能用在类型位置。
- 行内修饰符：import { type User, fetchUser } from "./models"，只给单个具名导入标类型。
- 再导出：export type { User } from "./models"，或写成 export { type User } from "./models"。
- 类型查询：typeof import("./models") 取得整个模块的类型，用于标注变量或参数。

```ts
// models.ts
export interface User { id: number; name: string; }
export function fetchUser(id: number): User { return { id, name: "why" }; }

// main.ts
import { type User, fetchUser } from "./models";
type ModelsShape = typeof import("./models");
const user: User = fetchUser(1);
const mod: ModelsShape = { fetchUser };
console.log(mod.fetchUser(2).name); // "why"
```

**速记**：import type 整条只导类型、编译后被擦除；行内 type 只标单个具名导入；export type 只再导出类型；typeof import("路径") 取模块整体类型。



#### isolatedModules 与 verbatimModuleSyntax

两个开关把「类型导入要显式标注」从风格建议变成硬性要求，因为单文件转译器看不到跨文件信息。

- 背景：Babel、esbuild、swc 逐文件转译，无法判断某个导入名是类型还是值，只能保守保留 import 语句。
- isolatedModules：要求每个文件都能被独立转译，类型导入必须显式标注，否则被当类型用的导入会残留到运行时。
- verbatimModuleSyntax：按源码原样保留 import 与 export，不做删除改写，并禁用 import x = require() 这类旧式语法。
- 连带规则：在 isolatedModules 下把纯类型再导出写成 export { User } 会报错，需改为 export type { User }。

```ts
// import { User } from "./models";   // 报错：User 只作类型使用，需写成 import type
import type { User } from "./models";
export type { User };
```

> [!WARNING]
> **警告内容**：使用 Babel、esbuild、swc 且未开启相关检查时，类型导入会残留为运行时 import，在浏览器或 Node 中抛出不存在的导出错误。

**速记**：isolatedModules 要求单文件可独立转译、类型导入必须显式；verbatimModuleSyntax 进一步要求源码原样保留 import/export。



### 命名空间与环境声明

**环境声明（ambient declaration）**：是只描述类型、不含实现的声明，用 declare 表示，用于告诉编译器某个值在运行时已经存在。

环境声明不参与代码生成，声明与运行时是否一致由外部保证，编译器只按声明检查使用方式。

#### namespace 的写法与历史用途

**命名空间（namespace）**：是 TypeScript 早期提供的内部模块方案，用 namespace 关键字把一组相关声明收进一个具名容器。

- 写法：namespace 名 { ... }，块内成员须加 export 才对容器外部可见，容器可嵌套。
- 编译产物：展开为立即执行函数，成员挂在一个真实对象上，属运行时结构。
- 历史用途：ES 模块普及前用于划分全局代码、规避命名冲突，也为声明文件提供类型容器。

```ts
namespace Geometry {
  export const pi = 3.14;
  export function area(radius: number): number { return pi * radius * radius; }
}

console.log(Geometry.area(2)); // 12.56
```

**速记**：namespace 用具名容器组织声明，成员需 export 才对外；编译后是真实的 IIFE 对象，可在运行时访问。



#### declare 关键字的作用

**declare**：是告诉编译器「该声明只有类型、没有实现，不要生成代码」的修饰符。

- declare const / let / var：声明已存在的变量。
- declare function 与 declare class：只给函数签名与类的构造签名、实例成员，都不含实现。
- declare namespace 与 declare module：分别声明环境命名空间与模块形状。

```ts
declare const appVersion: string;
declare function formatDate(value: Date): string;

console.log(appVersion.length); // 可以编译，运行时必须存在对应的值
```

**速记**：declare 表示只描述不实现、不生成代码，变量、函数、类、命名空间与模块都可用它声明。



#### 全局声明与 declare global

**全局声明**：是让声明进入全局作用域、成为全局变量或全局类型的手段。

- 模块内写法：declare global { ... }，块内声明提升到全局作用域。
- 脚本内写法：没有 import 与 export 的文件，顶层 declare 本身就是全局声明。
- 接口增强：在 declare global 块内写 interface Window { ... }，会与内置 Window 接口合并。
- 常见场景：给 window 或 globalThis 补属性、给全局脚本挂少量函数。

```ts
export {};

declare global {
  interface Window { analytics: { track(event: string): void } }
}

window.analytics.track("pageview");
```

> [!IMPORTANT]
> **重要内容**：declare global 只能出现在模块内，脚本中写它会被判定为错误，仍需用空导出把文件变成模块。

**速记**：模块内用 declare global 把声明提升到全局并与已有接口合并；脚本顶层 declare 本就是全局，无需 declare global。



#### 命名空间的现代定位

ES 模块成为标准后，命名空间的适用面大幅收窄，只在这几类场合仍有价值。

- 仍可用：声明文件中组织全局库的多层类型、给全局脚本挂少量成员、表达一组需要声明合并的常量。
- 不再建议：业务代码里用 namespace 代替模块，它生成运行时 IIFE、无法摇树优化，还造成值与类型的双重身份；迁移时拆成一个文件一个模块，调用方由 名.成员 改为导入后引用。

```ts
// 推荐：用模块替代命名空间
export function findUserById(id: number): string { return `user-${id}`; }
```

**速记**：命名空间是 ES 模块之前的组织方案；现代代码用模块，namespace 只保留在声明文件与全局类型容器等少数场景。



### 声明文件

**声明文件（declaration file）**：是以 .d.ts 结尾、只含类型声明、编译后不产生任何 JavaScript 的文件，用来向编译器描述已存在的运行时结构。

它是类型世界与运行时世界之间的契约，内容要么由编译器从源码自动生成，要么手写补充。

#### 声明文件只声明不实现

- 内容限制：只能出现类型与 declare 声明，带函数体或初始化表达式的语句会报错。
- 自动生成：开启 declaration 后每个 .ts 生成伴生 .d.ts，只留对外签名；手写则用于描述没有类型来源的第三方脚本与资源文件。
- 语义约定：.d.ts 中一切顶层声明等价于加了 declare，不必逐条重复写。

```ts
// math.d.ts
export declare function double(value: number): number;
export interface Point { x: number; y: number; }

// export function double(value: number) { return value * 2; } // 报错：声明文件不允许有实现
```

**速记**：.d.ts 只含声明、不含实现、不产出 JavaScript；可由 declaration 自动生成，也可手写描述第三方代码。



#### declare module 为无类型包补声明

**declare module**：是为一个模块名提供类型形状的声明，常用于给没有自带类型的包或非代码资源补声明。

- 具名模块：declare module "legacy-chart" { ... }，块内用 export 描述该包成员。
- 通配匹配：declare module "*.css" 让资源导入获得统一类型，declare module "untyped-*" 给一批包统一兜底。
- 展开式简写：declare module "pkg"; 只声明模块存在，成员一律按 any 处理。

```ts
declare module "legacy-chart" {
  export interface ChartOptions { width: number; height: number }
  export function render(target: string, options: ChartOptions): void;
}
```

> [!CAUTION]
> **注意内容**：declare module "*" 一类宽泛通配会把所有解析失败的模块静默降级为 any，掩盖真实错误，只宜在迁移过渡期临时使用。

**速记**：declare module 为无类型模块补形状；具名匹配单个包、通配匹配资源或整批包、简写只声明存在；宽泛通配会掩盖错误。



#### 模块增强扩展已有类型

**模块增强（module augmentation）**：是在不修改源码的前提下，为已有模块的声明补充成员的写法。

- 写法：在自身是模块的文件里写 declare module "目标模块" { ... }，块内同名接口与目标合并。
- 判断依据与场景：目标模块已有类型时是增强、没有类型时是新建声明；典型场景是给第三方库的配置接口加字段。
- 与 declare global 的区别：模块增强作用在某个模块上，declare global 作用在全局作用域上。

```ts
// chart-augment.d.ts
import "legacy-chart";

declare module "legacy-chart" {
  export interface ChartOptions { theme?: "light" | "dark" }
}
```

> [!IMPORTANT]
> **重要内容**：增强文件自身必须是模块，通常写一行 import "目标模块" 空导入作标记，否则 declare module 会被当成新建声明。

**速记**：模块增强在模块文件内对已存在的模块做接口合并；同一语法对不存在的模块则是新建声明，靠空导入标记自身为模块。



#### 全局声明与声明文件的放置

- 全局变量与全局函数：declare const / let / var 加类型，declare function 加完整参数与返回类型，都只给声明不给实现。
- 全局类型：顶层直接写 interface 或 type，不必加 declare，类型声明本就不产生代码。
- 放置与纳入：手写声明放源码目录或约定的 types 目录，靠 include 覆盖；全局类型包目录用 typeRoots 指定。
- 生效前提：只有被 include 覆盖或被 import 链引到的声明文件才参与检查，放在仓库里但没被收录等于没写。

```ts
// globals.d.ts
declare const APP_VERSION: string;
declare function uuid(): string;

interface AppConfig { debug: boolean }
```

**速记**：全局变量与函数用顶层 declare 写全签名；全局类型直接写 interface 或 type；声明文件须被 include 覆盖或被 import 链引到才生效。



### 类型声明查找与 @types

编译器处理一个 import 时，按「包自带类型、@types 目录、手动声明」的顺序寻找类型来源，三者依次兜底；理解这条链路才能判断「找不到类型」的错误该往哪一步查。

#### @types 包的来源与命名规则

**@types 包**：是社区为没有自带类型的 npm 包补写的类型声明包，统一发布在 @types 作用域下。

- 命名规则：包 foo 对应 @types/foo；带作用域的 @scope/foo 对应 @types/scope__foo，斜杠换成双下划线。
- 安装方式：npm install --save-dev 加包名，装在 devDependencies 中。
- 自动生效：默认情况下 node_modules/@types 下的所有包都会被自动纳入编译，无需 import。

```bash
npm install --save-dev @types/lodash
```

**速记**：@types 作用域存放社区类型包，foo 对应 @types/foo，@scope/foo 对应 @types/scope__foo；默认自动纳入编译。



#### DefinitelyTyped 与社区维护

**DefinitelyTyped**：是 @types 包的唯一上游仓库，所有 @types 包都由它自动发布。

- 仓库结构：每个包一个目录，含 index.d.ts、测试用例、tsconfig 与 package.json。
- 更新流程：提交 PR，仓库自动跑类型检查，合并后由发布机器人同步到 @types。
- 适用判断：上游包已自带类型时不应再安装 @types 包，二者同时存在会造成来源竞争。

```bash
npm view @types/react version
```

> [!TIP]
> **建议内容**：优先选用上游自带的类型；需要补 @types 时优先参与 DefinitelyTyped 修复，本地手写声明只作临时兜底。

**速记**：DefinitelyTyped 是 @types 的上游仓库，PR 合并后自动发布；上游已自带类型时不要再装 @types。



#### package.json 的 types 与 exports 类型入口

- types 与 typings：两个字段等价，指向包的类型入口，例如 "types": "./dist/index.d.ts"；typesVersions 按 TypeScript 版本给出不同入口。
- exports 类型条件：在 exports 的每个条件分支里用 "types" 指定声明文件，与 import、require 并列。
- 顺序要求：types 必须排在该分支最前面，否则会被 import 或 require 抢先匹配。

```json
{
  "name": "geometry-kit",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

**速记**：types 字段是包的类型入口，exports 用 types 条件给出条件化入口且必须排在最前；声明入口必须与实现入口成对存在。



#### types 与 typeRoots 简介

- typeRoots：指定到哪几个目录寻找全局类型包，默认是 node_modules/@types。
- types：给自动纳入的全局类型包设白名单，只列出的包会被纳入，空数组表示一个都不自动纳入。
- 作用范围：二者只管全局自动纳入这一条路径，通过 import 解析到的库类型不受影响。
- 配置归属：完整取值、与 include 和 exclude 的配合以及典型模板，归本主题第 17 篇。

```json
{
  "compilerOptions": {
    "typeRoots": ["./node_modules/@types", "./types"],
    "types": ["jest", "lodash"]
  }
}
```

> [!CAUTION]
> **注意内容**：types 写成空数组会关闭全部 @types 自动纳入，测试框架提供的全局函数随之消失，需显式 import 或重新加回白名单。

**速记**：typeRoots 定搜索目录、types 定纳入白名单，二者只管全局自动纳入；库自身类型仍走 import 解析。



### 模块解析基础

**模块解析（module resolution）**：是把 import 中的模块路径映射到具体实现文件与声明文件的过程，由 tsconfig 的 moduleResolution 选择策略。

不同策略对扩展名、目录入口与 package.json 字段的处理不同，选错会出现「代码能跑、类型报错」或相反的情况。

#### 经典解析：classic 与 node10

- classic：从当前目录逐级向上查找同名文件，不识别 node_modules 的包入口，仅剩历史价值。
- node10：旧名 node，沿用 Node 的 CommonJS 规则，依次尝试精确文件、补扩展名、目录 index、逐级向上找 node_modules，只认 main 与 types、不识别 exports。
- 适用场景：老项目与纯 CommonJS 库，新项目不应再选这两者。

```json
{
  "compilerOptions": {
    "moduleResolution": "node10"
  }
}
```

**速记**：classic 逐级查文件、不看 node_modules；node10 按 CommonJS 规则查找、不识别 exports；二者仅适合老项目。



#### node16 与 nodenext

- 目标：对齐 Node.js 的真实解析行为，读取 package.json 的 exports 与 type 字段；nodenext 跟随最新语义，node16 固定在 Node 16 的行为。
- 扩展名必须写全：ESM 下相对导入写成 "./math.js"，即使源文件是 math.ts，因为运行时按 .js 解析。
- 模块格式判定：.mts 恒为 ESM，.cts 恒为 CommonJS，.ts 由最近的 package.json 的 type 字段决定。
- 与 node10 的差别：不再补扩展名、不再回退到目录 index，导出条件按 import 与 require 分支精确匹配。

```ts
// ESM 包内的相对导入必须写扩展名
import { double } from "./math.js"; // 源文件为 math.ts，导入路径写 .js
```

> [!WARNING]
> **警告内容**：从 node10 切到 node16 或 nodenext 时，所有省略扩展名的相对导入会集体报错，需要逐一补上 .js 后缀。

**速记**：node16 与 nodenext 对齐 Node 真实行为，认 exports 与 type 字段；ESM 下相对导入必须写 .js 扩展名，.mts/.cts 强制模块格式。



#### bundler 解析与导出条件

**bundler 解析**：是模拟 Vite、webpack、esbuild、Rollup 行为的解析策略，允许省略扩展名，同时识别 exports 的导出条件。

- 适用项目：源码交给打包器处理、不直接由 Node 运行的前端工程，module 需为 esnext 或 preserve。
- 选择口径：产物直接由 Node 运行就用 node16 或 nodenext，产物经打包器就用 bundler。
- 导出条件取值：import 对应 ESM，require 对应 CommonJS，types 对应类型，另有 node、browser、default 等环境条件。
- 子路径导出：import "pkg/sub" 只有在 exports 里显式声明了 "./sub" 时才可解析。

```json
{
  "compilerOptions": {
    "module": "esnext",
    "moduleResolution": "bundler"
  }
}
```

**速记**：bundler 面向 Vite 与 webpack 等打包器，可省扩展名并识别 exports，要求 module 为 esnext 或 preserve；子路径导出须在 exports 中显式声明。



#### 找不到类型声明时的排查顺序

- 分错误码：TS2307 是模块本身没解析到；TS7016 是模块解析到了但没有声明文件，二者排查方向不同。
- 查包自带类型：读包内 package.json 的 types 与 exports 的 types 条件，确认路径存在且指向真实文件。
- 查 @types：是否存在对应 @types 包并已安装，types 白名单是否恰好把它排除在外。
- 查解析模式与收录：node16 下是否漏写 .js 扩展名，手写的 .d.ts 是否被 include 覆盖或位于 typeRoots 目录内。
- 兜底：以上都无果时用 declare module 写最小声明，而不是把整包关掉类型检查。

```ts
declare module "no-types-widget" {
  export function mount(target: string): void;
}

// 优于：把该包整体断言为 any，会连带丢失包内所有类型检查
```

> [!TIP]
> **建议内容**：优先让上游包自带类型或安装 @types 包，手写 declare module 只作最后兜底；换成 any 只解决了报错，没有解决类型缺失。

**速记**：先分 TS2307 与 TS7016，再依次查包自带 types、@types、解析模式与扩展名、声明文件收录；最后才手写最小声明兜底。
