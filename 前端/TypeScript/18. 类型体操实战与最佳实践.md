## 类型体操实战与最佳实践

### 类型编程的思维

#### 把类型当作集合运算

**集合视角**：是把联合类型读作并集、交叉类型读作交集、never 读作空集、unknown 读作全集，把类型变换读作集合运算。

- 并集由 | 构造，交集由 & 构造；never 是底部类型，与任何类型求并仍是对方。
- keyof T 是键全集，T[K] 是取某个键上的取值集合（详见本主题第 10 篇）；T extends U ? X : Y 是一次子集判断（本主题第 12 篇）。

```ts
type FieldKey = "id" | "name" | "email";
type Dropped = Exclude<FieldKey, "email">; // "id" | "name"
```

- 并集可交给映射类型逐键展开成对象，交集不能凭空展开；要取交叉类型里可枚举的部分，先把它化成并集。

> 集合视角的用途是排错：结果不符预期时先问「输入是哪个集合、运算后应剩哪些成员」，多数错误在这一步即可定位。

**速记**：联合是并集、交叉是交集、never 是空集，extends 是一次子集判断。



#### 从用例反推类型形状

**类型形状**：是一个类型在调用点表现出的成员结构，包括有哪些键、键是否可选、值是什么类型、是否只读。

- 先写下三到五个期望通过编译的调用，把实参、返回值、该报错的位置都写全，等于先固定验收标准。
- 再找共性：随输入变化的位置留作类型参数，固定不变的位置写成约束；最后才选运算符（改键名用 as 子句、改修饰符用映射类型、按类型分派用条件类型）。

> 先写调用方的另一层收益在实现阶段：只剩「让这几行通过」，避免先造一个复杂类型再到处迁就它。

**速记**：先写调用方用例，再从用例反推类型参数与运算符。



#### 先写调用方再写实现

**签名先行**：是把类型别名与函数签名先落地、实现体最后补上的做法，让类型设计的错误在成本最低时暴露。

- 实现体最后写，此时签名已把每个参数收窄到确定类型，实现里几乎不需要断言。
- 类型层同理：先定目标类型，再逐个补分支，遇到不合预期的分支就地调整输入模型。

```ts
type ParseResult<T> = T extends string ? { kind: "text"; value: string } : { kind: "number"; value: number };

declare function parseInput<T extends string | number>(input: T): ParseResult<T>;
```

**速记**：签名与类型先落地并验收，实现体最后补。



#### 可读性优先于炫技

**可读性优先**：是当类型的表达力与可维护性冲突时，选择更短、更容易读懂与修改的写法。

- 同一段类型能拆成两个具名别名时不要写成一个长表达式；别名本身就是文档。
- 能用内置工具类型组合出来就不手写；嵌套条件超过三层或递归没有明确上限时，先回到需求层确认精度是否必要。

> [!WARNING]
> **警告内容**：类型体操的复杂度不留在写法里，而是留在每个后来者看到的报错信息里；一处类型写错会以难以定位的错误扩散到全部引用点。

**速记**：表达力与可维护性冲突时，选可读的那一侧。



### 实战手写类型

本节手写类型都由前几篇机制拼成：分支判断来自条件类型（第 12 篇），逐键变形来自映射类型（第 11 篇），键的取值来自索引访问类型（第 10 篇），字符串模式匹配来自模板字面量类型（第 13 篇），类型参数与约束来自泛型（第 9 篇）。

#### DeepPartial 递归可选

**DeepPartial<T>**：是把 T 及其所有嵌套对象类型的属性都递归变为可选的类型。

```ts
type DeepPartial<T> = T extends readonly (infer U)[]
  ? readonly DeepPartial<U>[]
  : T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T;

type DraftConfig = DeepPartial<{ host: string; retry: { times: number } }>;
// { host?: string; retry?: { times?: number } }
```

- 分支判断用条件类型、infer U 取数组元素（第 12 篇）；对象分支是同态映射类型，? 写在键参数后加可选（第 11 篇）；DeepPartial<T[K]> 递归，T[K] 是索引访问类型（第 10 篇）。
- 末尾的 T 是基础分支，递归到非对象类型时停下，缺了它编译器会报类型别名循环引用；先判数组是因为数组也满足 object，走对象分支会得到一串数字键属性。

**速记**：条件类型挑分支、同态映射逐键加 ?、递归处理嵌套、基础分支收口。



#### DeepReadonly 递归只读

**DeepReadonly<T>**：是把 T 及其所有嵌套对象类型的属性都递归变为只读的类型。

```ts
type DeepReadonly<T> = T extends readonly (infer U)[]
  ? readonly DeepReadonly<U>[]
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } : T;

declare const frozen: DeepReadonly<{ nested: { fontSize: number } }>;
frozen.nested.fontSize = 16; // 报错：只读属性不能赋值
```

- 与 DeepPartial 同构，只把键上的 ? 换成 readonly；修饰符写法来自本主题第 11 篇，同态映射保留原属性的可选性并只叠加只读。
- 函数类型也匹配 object，递归会只读其属性但不改变调用签名；不需要时可在 object 分支前加一层函数判断提前返回 T。

**速记**：与 DeepPartial 共用递归骨架，把 ? 换成 readonly 即可。



#### 手写 Omit 与 Awaited

**Omit 的手写形态**：是用 Pick 与 Exclude 组合出「保留除指定键以外的全部键」的类型。**Awaited 的手写形态**：是用条件类型与 infer 递归取出 Promise 的解析值。

```ts
type MyOmit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
type MyAwaited<T> = T extends Promise<infer U> ? MyAwaited<U> : T;

type PublicProfile = MyOmit<{ id: number; name: string; hash: string }, "hash">;
// { id: number; name: string }
type ResolvedText = MyAwaited<Promise<Promise<string>>>; // string
```

- Exclude 由分布式条件类型实现，从键并集里剔除 K（第 12 篇）；Pick 是同态映射，只保留剩余键（第 11 篇，Omit 的基础形态在该篇已述）。
- MyAwaited 用条件类型判断是否为 Promise，infer U 取解析值后继续递归（第 12 篇）；内置 Awaited 还处理带 then 方法的对象，日常应直接用内置版本。

**速记**：Omit 是 Pick 加 Exclude，Awaited 是条件类型加 infer 加递归。



#### UnwrapPromise 拆包

**UnwrapPromise<T>**：是把对象类型中所有值为 Promise 的属性替换为其解析值、非 Promise 属性保持原样的类型。

```ts
type UnwrapPromise<T> = { [K in keyof T]: T[K] extends Promise<infer U> ? U : T[K] };

type Loaded = UnwrapPromise<{ user: Promise<string>; label: string }>;
// { user: string; label: string }
```

- 外层是同态映射，键与修饰符原样保留（本主题第 11 篇）；值位置放条件类型做按属性分派，infer U 取解析值（本主题第 12 篇）。
- 被检查位置写的是 T[K] 而不是裸类型参数，因此不触发分发（第 12 篇）；每个属性各判断一次，正是按属性分派需要的行为。

**速记**：同态映射逐键走一遍，值位置用条件类型分派并 infer 取解析值。



#### ApiResponse 统一响应包装

**ApiResponse<T>**：是把接口返回统一成「成功携带数据」与「失败携带信息」两种形态的可辨识联合类型。

```ts
type ApiResponse<T> =
  | { ok: true; status: number; data: T }
  | { ok: false; status: number; message: string; details?: string[] };

function readData<T>(response: ApiResponse<T>): T | undefined {
  if (response.ok) return response.data; // 收窄为成功分支
  console.warn(response.message);        // 收窄为失败分支
  return undefined;
}
```

- ok 是字面量判别字段，两个分支构成可辨识联合，进入分支后自动收窄（定义见第 5 篇，收窄手法见第 8 篇）。
- 泛型 T 只出现在成功分支，调用方判断一次 ok 即可，不必再对 data 判空；details 用可选数组表达「有明细时才有」。

**速记**：把成功与失败建成可辨识联合，判别字段用字面量，数据只挂在成功分支。



#### 类型安全的事件总线签名

**事件总线**：是维护「事件名到回调参数」映射、按名注册与触发的发布订阅结构；类型安全的写法让事件名与其负载一一绑定。

```ts
type EventMap = { "user:login": { userId: string }; "cart:update": { items: string[] } };

type EventBus<Events extends Record<string, unknown>> = {
  on<K extends keyof Events>(name: K, handler: (payload: Events[K]) => void): void;
  emit<K extends keyof Events>(name: K, payload: Events[K]): void;
};

declare const bus: EventBus<EventMap>;
// bus.emit("cart:update", { items: "shirt" }); // 报错：items 应为 string[]
```

- Events extends Record<string, unknown> 是泛型约束，限定键为字符串、负载可任意（本主题第 9 篇）。
- K extends keyof Events 与 Events[K] 让事件名与负载联动（keyof 与索引访问见第 10 篇），写错事件名或参数都在编译期报错。

**速记**：用泛型约束加 keyof 建立事件名到负载的映射，编译期锁死注册与触发两侧。



### 条件类型与工具组合实战

#### 按参数类型分派不同返回类型

**返回类型分派**：是让函数返回类型由入参类型决定，用条件类型在签名里建立「入参到出参」的映射表。

```ts
type MediaKind<T> =
  T extends string ? { kind: "text"; value: string } :
  T extends number ? { kind: "number"; value: number } : never;

declare function labelOf<T extends string | number>(input: T): MediaKind<T>;
const countLabel = labelOf(3); // { kind: "number"; value: number }
```

- 条件类型在类型参数未绑定时延迟求值，实参传入后才逐分支计算（本主题第 12 篇）。
- T 的约束把可取值域限制在两种类型，使兜底分支 never 在正常调用下不可达（泛型约束见第 9 篇）；传入联合入参会被分发成结果并集，调用方需先收窄。

**速记**：返回类型由条件类型按入参分派，联合入参会被分发成并集。



#### 可辨识联合驱动的 reducer 类型

**reducer**：是形如 (state, action) => state 的纯函数，action 携带判别字段决定状态如何变化。

```ts
type CartState = { items: string[]; total: number };
type CartAction =
  | { type: "add"; item: string; price: number }
  | { type: "remove"; item: string }
  | { type: "reset" };

function reduceState(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "add": return { items: [...state.items, action.item], total: state.total + action.price };
    case "remove": return { items: state.items.filter((one) => one !== action.item), total: state.total };
    case "reset": return { items: [], total: 0 };
  }
}
```

- switch 对判别字段收窄，分支内 action 是具体成员（本主题第 8 篇）；三个成员全覆盖后函数末尾不再报缺少返回值，漏掉一个该错误立即出现，这就是穷尽检查。
- 单个 action 可写作 Extract<CartAction, { type: "add" }>，由分布式条件类型从并集里挑出符合某形状的成员（第 12 篇），用于给分支处理函数声明签名。

**速记**：action 联合靠判别字段收窄，漏分支即报错，单个分支用 Extract 取。



#### 表单校验结果与错误信息的类型建模

**校验结果**：是把「通过」与「逐字段错误」建成联合，并让错误字段名与表单字段名同源的类型。

```ts
type SignupValues = { email: string; age: number };
type FieldErrors<T> = { [K in keyof T]?: string[] };
type ValidationResult<T> = { valid: true; values: T } | { valid: false; errors: FieldErrors<T> };

declare const checked: ValidationResult<SignupValues>;
if (!checked.valid) checked.errors.email; // string[] | undefined
```

- FieldErrors 是同态映射类型，键来自 keyof T，与表单字段同源（本主题第 11 篇）；字段改名后旧键立刻报错。
- valid 是字面量判别字段，构成可辨识联合（第 5 篇），分支内 values 与 errors 各自确定可用；每个字段错误是可选数组，表达「只有失败字段才有信息」。

**速记**：错误类型由同态映射从表单类型派生，通过与否用字面量判别字段区分。



#### 类型安全的路由参数提取

**路由参数提取**：是用模板字面量类型匹配路径、用 infer 取出参数名片段，再映射成参数对象类型的写法。

```ts
type PathParams<Path extends string> =
  Path extends `${infer Head}/${infer Tail}`
    ? (Head extends `:${infer Param}` ? { [K in Param]: string } : {}) & PathParams<`/${Tail}`>
    : Path extends `:${infer Param}` ? { [K in Param]: string } : {};

type PostParams = PathParams<"/user/:userId/post/:postId">; // { userId: string } & { postId: string }

declare function navigate<Path extends string>(path: Path, params: PathParams<Path>): void;
```

- 两个 infer 把路径按第一个斜杠切成 Head 与 Tail 后递归（模板字面量类型与 infer 的组合见本主题第 13 篇）；navigate 的参数写成 PathParams<Path>，参数名或值类型写错即在编译期报错。
- Head 匹配冒号开头的模板时用 infer Param 取参数名，{ [K in Param]: string } 由取出的字面量构造对象键（第 11 篇）；各段结果用 & 累积（交叉类型见第 5 篇），无参数的段落返回空对象，不影响交集。

**速记**：模板字面量类型切段、infer 取参数名、映射类型建键、交叉类型累积。



### 性能与可维护性

#### 类型复杂度对编译速度的影响

**类型实例化**：是编译器把类型实参代入泛型类型、求出具体类型的过程；实例化次数与单次深度共同决定类型检查耗时。

- 耗时来自实例化数量（大联合被逐成员分发）与单次深度（递归展开层数）；用编译器自带的诊断输出定位，不要凭感觉重写类型。

```bash
tsc --noEmit --diagnostics
```

- 常见高成本写法：把成百上千成员的联合交给映射类型或分发条件类型；对深度很大的对象类型做递归深只读；在热路径的签名里写多层嵌套条件类型。

> [!NOTE]
> **提醒内容**：类型耗时只在超大型项目里才明显；多数业务代码的瓶颈不是编译慢，而是类型表达式难以维护。

**速记**：成本等于实例化次数乘深度，用诊断输出定位，不要凭感觉优化。



#### 避免深递归与不必要分发

**分发成本**：是条件类型在联合入参上逐成员求值带来的实例化开销；递归与分发是类型耗时的两个主要来源。

- 递归类型必须有基础分支并逐层收敛，例如每层剥掉元组头部；只要某层不再减小输入，就会报类型实例化过深。
- 深度超过约五十层会触发编译器的保护性报错，这不是可关闭的开关，只能把输入规模改小。
- 不需要逐成员处理时把类型参数放进单元素元组即可关闭分发（第 12 篇）；一次整体判断比 N 次成员判断便宜，也不会合成出过大的并集。

**速记**：递归要逐层收敛，不需要分发就套元组关掉。



#### 报错信息可读性优化

**报错可读性**：是类型不满足约束时编译器给出的信息能否让读者直接定位问题类型与原因。

- 首选手段是把类型别名拆小：报错指向有业务含义的名字，而不是一屏展开的映射表达式。
- 类型参数用有含义的名字（Payload、PayloadOf、Name），比 T、U 更容易读懂「约束不满足」这类提示；约束抽成具名类型后，报错会显示它的定义位置。
- 用 never 兜底会把错误推迟到使用处，提示变成「不能赋给 never」；需要就地报错时改用联合穷尽检查，让错误落在当前行。

```ts
type PayloadOf<Name extends "user:login" | "cart:update"> =
  Name extends "user:login" ? { userId: string } : { items: string[] };

declare function track<Name extends "user:login" | "cart:update">(name: Name, payload: PayloadOf<Name>): void;
// track("cart:update", { userId: "u1" }); // 报错：类型与事件名不匹配
```

**速记**：拆具名别名、起有含义的类型参数名、少用 never 兜底。



#### 类型测试与类型断言测试的写法

**类型测试**：是不运行代码、只验证「某类型是否可赋值给另一类型」的测试，断言完全靠编译器执行。

- 正向断言声明目标类型的变量并赋值，编译通过即成立；反向断言用 @ts-expect-error 标注必须报错的行，该行若不报错编译器会提示指令未生效。
- 等价断言用条件类型比较两个类型是否互相可赋值，再用 never 卡住不等价的情况；这些断言只存在于测试文件，不需要运行时依赖。

```ts
type Expect<T extends true> = T;
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;

type CaseDeep = Expect<Equal<DeepPartial<{ a: { b: string } }>, { a?: { b?: string } }>>;
```

- Equal 用两个函数类型比较而不是直接写 A extends B，是为了避开结构化类型下「成员更多仍互相兼容」的漏判（条件类型见第 12 篇）；类型测试文件同样参与 tsc 检查，要纳入类型检查脚本。

**速记**：正向靠赋值、反向靠 @ts-expect-error、等价靠函数类型比较。



#### 为复杂类型加注释

**类型注释**：是在类型别名上说明输入输出、机制来源与限制，让读者不必逐行拆解运算符的写法。

- 类型别名上方写一句「输入是什么、输出是什么」，比在实现里逐行解释运算符更有价值。
- 递归类型注明终止条件，有层数或输入规模限制的把限制写进注释；引用其他机制的位置写「见第 N 篇」，分支说明写在行尾，不要插在尖括号结构内部。

**速记**：别名上方写输入输出，递归写终止条件与上限，机制处写篇号指代。



### 工程约定与反模式清单

#### 类型定义的组织与放置

**类型组织**：是按复用范围决定每个类型定义放在哪个文件、与哪段代码相邻的约定。

- 只在单个文件内使用的类型留在使用处上方；跨模块复用的提到该模块的 types.ts，按「领域对象、请求响应、组件契约」分段。
- 与某个函数强绑定的类型紧贴该函数，例如 labelOf 与 MediaKind 放在一起，避免签名与类型分居两个文件。
- 不把业务类型塞进全局声明文件：全局声明会污染所有文件，改名时无法靠编译器找到全部引用；类型文件只做类型导出，导入其他模块用 import type，避免它被当成运行时代码参与打包（声明文件规则见本主题第 16 篇）。

**速记**：按复用范围决定放置，就近优先，不进全局声明文件。



#### 导出策略

导出面越小越好：只导出调用方需要的类型，纯类型用 export type 标注。

- 只导出调用方需要的类型：组件的 Props 导出，内部状态类型不导出；导出面越小，改动波及面越小。
- 对外暴露别名而不是裸的映射或条件表达式，日后调整实现时引用方不受影响。
- 用 export type 标注纯类型导出，在启用 isolatedModules 与 verbatimModuleSyntax 时不会被误当作值导出（第 17 篇）；不用 export 加星号聚合类型，具名重导出能让跳转与报错都落到准确位置。

> 导出一个复杂类型之前先问「外部需要它的哪部分能力」；多数情况对外只需要一个更窄的具名别名，完整实现留在模块内部。

**速记**：只导出必要类型，对外给别名，用 export type 明确标注。



#### any 与 unknown 与 as 的使用边界

**any**：是关闭该位置类型检查的退路。**unknown**：是类型安全的顶部类型，可接收任何值但使用前必须收窄。

- 外部输入（网络响应、事件负载、本地存储读出）一律先用 unknown，收窄后再使用；只有迁移期遗留代码可短期保留 any。
- as 只用在「不改变运行时行为、且编译器确实无法推断」的位置；不要用 as 掩盖真实的不匹配，双重断言 as unknown as T 说明类型定义已经脱节，应回去修数据源或补校验。
- 需要校验字面量同时保留窄类型时用 satisfies（本主题第 3 篇），它比 as 更安全。

```ts
function readFeatureFlag(raw: unknown): boolean {
  return typeof raw === "boolean" ? raw : false;
}
```

**速记**：外部输入用 unknown 收窄，as 只补推断缺口，双重断言视为待修缺陷。



#### 与运行时校验方案的衔接

**运行时校验**：是在系统边界检查真实数据的形状、与编译期类型互为补充的手段，实现方式包括校验库与手写守卫函数。

- 类型在运行时被擦除，外部数据没有类型保证；网络响应、本地存储、URL 查询参数、第三方回调四处必须在入口校验。
- 从校验 schema 推导类型可让类型与校验同源，避免手写两份定义后逐渐漂移；无法引入校验库时，写类型谓词形式的守卫函数做最小收窄（类型谓词见本主题第 8 篇）。
- 类型断言不能替代校验：as 只影响编译期，运行时不做任何检查。

```ts
function isSessionUser(value: unknown): value is { id: number; name: string } {
  if (typeof value !== "object" || value === null) return false;
  const record = value as Record<string, unknown>;
  return typeof record.id === "number" && typeof record.name === "string";
}
```

**速记**：边界处用 schema 或类型谓词校验，类型断言不算校验。



#### 常见反模式

清单收拢了六类典型反模式，涵盖 any 兜底、断言代校验、枚举膨胀与过深嵌套条件类型。

- 用 any 兜住整个接口响应：此后所有字段访问都不受检查，错误漂到运行时；改为声明领域类型并在入口收窄。
- 用类型断言代替校验：as SessionUser 只作用于编译期，坏数据照样进入程序；改为守卫函数或 schema。
- 把枚举展开成几百个成员的联合：每次映射与分发都变贵；改为分组或从常量数组推导（详见本主题第 6 篇）。
- 给只出现一次的类型位置也加泛型参数（本主题第 9 篇），或手写已有内置语义的工具类型（本主题第 11 篇）：前者只是噪音，后者在边界情形上比内置版本更弱。
- 用条件类型承担运行时分支，或写不带终止条件与上限的深递归：前者不会生成任何运行时代码，后者最终以类型实例化过深报错收场。
- 在业务组件里堆三层以上嵌套条件类型：改一处要读很久，应拆成具名别名或简化数据模型。

> [!CAUTION]
> **注意内容**：类型体操的收益只在「阻止真实错误」时成立；一段没人能读懂、也不阻止任何错误的类型，成本最终全部由维护者承担。

**速记**：先问这段类型挡住了哪个错误，挡不住的复杂度就该删掉。
