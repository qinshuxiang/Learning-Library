## TypeScript 简介与编写方式

### 什么是 TypeScript

**TypeScript** 是微软于 2012 年发布的编程语言，由 Anders Hejlsberg 主导设计，其定位是 JavaScript 的超集加上一套可选的静态类型系统，最终编译为纯 JavaScript 运行。

本篇只回答四件事：TypeScript 是什么、为什么需要它、怎么写、怎么跑。具体的类型语义从第 2 篇开始逐个展开。

#### TypeScript 与 JavaScript 的关系

**TypeScript 与 JavaScript 的关系**：是「超集与宿主语言」的关系，任何合法的 JavaScript 代码都是合法的 TypeScript 代码，TypeScript 在其之上追加类型语法。

- 语法层面：TypeScript 是 JavaScript 的超集（superset），保留全部 JavaScript 语法，再扩展类型注解、接口、泛型等写法。
- 执行层面：浏览器与 Node.js 只认识 JavaScript，TypeScript 必须经过编译（compile）才能运行。
- 生态层面：npm 上的 JavaScript 包可以直接在 TypeScript 项目中导入，常见库由官方或社区维护类型声明。

```js
// 纯 JavaScript 写法，在 TypeScript 项目中同样合法
function formatDate(date) {
  return date.toISOString().slice(0, 10);
}
```

```ts
// 追加类型后，编译器会检查调用方传入的值
function formatDateTyped(date: Date): string {
  return date.toISOString().slice(0, 10);
}

console.log(formatDateTyped(new Date("2026-09-13"))); // "2026-09-13"
```

> 需要区分「语言」与「类型检查」两件事：浏览器执行的是编译后的 JavaScript，类型检查发生在编译之前，属于开发期的工具能力。

**速记**：TypeScript 是 JavaScript 的超集，类型检查在编译期完成，产物是普通 JavaScript。



#### 超集与类型系统的定位

**类型系统（type system）**：是一组给程序中的值分配类型、并据此判断代码是否自洽的规则集合；TypeScript 的类型系统是可选（optional）且结构化（structural）的。

- 可选：类型标注可以只写一部分，未标注处由类型推断（type inference）补全，也可以整体写回普通 JavaScript。
- 渐进：可以在既有 JavaScript 项目里逐步加入类型检查，不必一次性迁移。
- 结构化：类型能否兼容由成员结构决定，而不是由类型名或声明来源决定，与 Java、C# 的标称类型系统不同。

```ts
// 同一段代码，变量的类型由推断补全
const userIds = [1, 2, 3];        // 推断为 number 数组
const firstId = userIds[0];       // 推断为 number
console.log(typeof firstId);      // "number"
```

> 类型系统的定位是「开发期护栏」：它描述代码应该怎样被使用，不替代 JavaScript 的运行时行为。

**速记**：类型系统可选、渐进、结构化，只服务于开发期。



#### 编译产物

**编译产物**：是 TypeScript 源码经编译器处理后的 JavaScript 文件，类型标注在输出中被整体移除，文件结构与源码一一对应。

- 输入：扩展名为 .ts 的源文件，可以包含类型注解与 JavaScript 语句。
- 输出：扩展名为 .js 的普通文件，内容是不含类型的 JavaScript，浏览器与 Node.js 可直接执行。
- 控制项：输出目录、目标语法版本、是否生成声明文件等由 tsconfig.json 决定（详见本主题第 17 篇 tsconfig 工程化配置）。

```ts
// src/greet.ts
export function greet(name: string): string {
  return `Hello, ${name}!`;
}
```

```js
// 产物 dist/greet.js（目标语法为 ES2020 时）
export function greet(name) {
  return `Hello, ${name}!`;
}
```

> 编译产物的可读性与源码接近，因为 TypeScript 只做类型移除与少量语法降级，不做跨文件打包。

**速记**：编译产物是不含类型的 JavaScript，文件结构与源码一一对应。



### 类型系统解决什么问题

**类型系统解决的问题**：是把错误从运行时提前到编译期，并把代码意图以机器可校验的方式显式化。

#### 编译期发现错误

**编译期发现错误**：指在代码运行之前，由编译器依据类型规则指出不可能成立的调用与赋值。

- 拼写错误：访问对象上不存在的属性会在编辑器与编译命令中同时报错。
- 参数错误：参数个数或参数类型不匹配，在调用处即被拦下。
- 空值遗漏：可能为空的值在未处理之前不能直接使用（详见本主题第 8 篇 类型收窄与控制流分析）。

```ts
function getUserById(id: number) {
  return { id, name: "Ada Lovelace" };
}

const user = getUserById(1);
console.log(user.name); // "Ada Lovelace"
// console.log(user.nmae); // 报错：属性 nmae 不存在
// getUserById("1");       // 报错：string 不能赋给 number
```

> 编译期错误的修复成本远低于运行时错误：前者在提交前暴露，后者可能只在生产环境的某条分支上触发。

**速记**：编译期错误是在运行之前被编译器拦下的错误，越早暴露越便宜。



#### 编辑器补全与重构

**编辑器补全与重构**：指编辑器依据类型信息提供精确的成员列表、跳转、重命名等能力。

- 补全：输入对象名加点的瞬间列出可用成员，减少来回查文档。
- 跳转与重命名：重命名符号时能安全更新全部引用，而不是按文本盲目替换。
- 重构：提取函数、修改变量名等操作可跨文件进行，编辑器据此校验结果是否自洽。

```ts
const user = { id: 1, name: "Ada Lovelace", email: "ada@example.com" };

user.name;   // 编辑器可补全 id、name、email
// user.age; // 报错：属性 age 不存在
```

> 语言服务（language service）是编译器的另一个出口：命令行编译与编辑器补全共用同一套类型信息。

**速记**：类型信息是编辑器智能补全与安全重构的数据来源。



#### 类型即文档

**类型即文档**：指函数签名与接口声明本身描述了「需要什么、返回什么」，可以承担一部分注释的职责。

- 签名自解释：参数名配合类型直接说明调用契约，阅读者不必翻实现。
- 随代码演进：实现改动引发类型不匹配时会立即报错，而注释容易过期。
- 工具可读：类型可被文档生成器提取，形成结构化接口说明。

```ts
interface DateRange {
  start: Date;
  end: Date;
}

function formatRange(range: DateRange): string {
  const start = range.start.toISOString().slice(0, 10);
  const end = range.end.toISOString().slice(0, 10);
  return `${start} ~ ${end}`;
}

console.log(formatRange({ start: new Date("2026-01-01"), end: new Date("2026-01-31") }));
// "2026-01-01 ~ 2026-01-31"
```

> 类型不等于文档：它只描述结构与取值约束，无法表达业务背景和取舍原因，二者互补。

**速记**：类型是机器可校验的文档，但它不承载业务语义。



#### 团队协作收益

**团队协作收益**：指类型声明成为模块之间的公共契约，让多人协作与跨模块改动能够被自动校验。

- 接口先行：先约定类型，多人可并行实现，编译结果即一致性检查。
- 减少沟通：调用方不必追问参数格式，类型已经写明。
- 安全升级：依赖库升级后类型不兼容会在下游编译时报错，而不是等到线上异常。

```ts
interface UserProfile {
  id: number;
  displayName: string;
}

function buildUserProfile(id: number, displayName: string): UserProfile {
  return { id, displayName };
}

console.log(buildUserProfile(7, "Grace Hopper"));
// { id: 7, displayName: "Grace Hopper" }
```

> 项目越大、迭代越快，类型的收益越明显；小脚本与一次性原型可以不引入类型检查。

**速记**：类型是团队之间的可执行契约，协作规模越大收益越高。



### 编写与运行方式

**编写与运行方式** 决定 TypeScript 代码如何进入执行环境：一条路径是编译后运行，另一条是借助运行器直接执行 .ts 文件。

#### tsc 编译

**tsc（TypeScript Compiler）**：是 TypeScript 官方编译器，把 .ts 文件编译为 .js 文件，同时报告类型错误。

- 安装：执行 npm install --save-dev typescript，安装后即可使用 tsc 命令。
- 初始化：执行 npx tsc --init 生成 tsconfig.json，编译选项集中在该文件。
- 编译：执行 npx tsc 按配置编译整个项目，也可指定单个文件。
- 产物：默认与源文件同目录输出，可用 outDir 指定输出目录。

```bash
npm install --save-dev typescript
npx tsc --init
npx tsc
```

```ts
// src/greet.ts
export function greet(name: string): string {
  return `Hello, ${name}!`;
}
```

```js
// 产物 dist/greet.js
export function greet(name) {
  return `Hello, ${name}!`;
}
```

> tsc 只负责类型检查与语法转换，不做打包；打包交给 Vite、esbuild、webpack 等构建工具。

**速记**：tsc 读 tsconfig.json，输出移除类型后的 JavaScript。



#### ts-node 与 tsx 直接运行

**ts-node**：是在 Node.js 中直接执行 .ts 文件的运行器，通过注册模块加载钩子在载入时即时编译。**tsx**：是基于 esbuild 的同类工具，启动更快，对模块格式的兼容更好。

- ts-node：执行 npx ts-node src/index.ts，类型检查较完整，按需编译，启动相对慢。
- tsx：执行 npx tsx src/index.ts，不做完整类型检查，只剥离类型后运行，速度接近原生。
- 原生剥离：较新的 Node.js 版本内置类型剥离（type stripping）能力，可直接用 node 运行 .ts 文件。
- 取舍：开发期用 tsx 求速度，提交前用 npx tsc --noEmit 单独做一次完整类型检查。

```bash
npx ts-node src/index.ts
npx tsx src/index.ts
npx tsc --noEmit
```

```ts
// src/index.ts
function makeCounter(start: number) {
  let count = start;
  return () => ++count;
}

const next = makeCounter(0);
console.log(next()); // 1
console.log(next()); // 2
```

> 直接运行的工具体不产出文件，适合开发调试与一次性脚本；对外发布仍要走 tsc 或构建工具。

**速记**：ts-node 边编译边跑，tsx 只剥类型跑得快，类型检查交给 tsc --noEmit。



#### 编辑器与 Playground

**编辑器与 Playground**：是两种免配置的上手途径，前者提供实时反馈，后者用于快速试验语法与查看产物。

- 编辑器：VS Code 内置 TypeScript 语言服务，打开 .ts 文件即获得补全、悬停类型与错误波浪线。
- Playground：TypeScript 官网的在线试验场，左侧写代码，右侧实时显示编译产物与错误。
- 结论一致：编辑器与 Playground 调用同一套类型检查逻辑，结论与 tsc 相同。
- 版本切换：编辑器可切换所用编译器版本，项目内安装的版本优先。

> [!NOTE]
> **提醒内容**：Playground 的编译器版本可能高于项目本地版本，结论不一致时以项目内安装的版本为准。

**速记**：编辑器与 Playground 复用同一编译器，结论与命令行一致。



#### npm 安装与最小示例

**最小示例**：是能完成一次「安装、编写、运行」闭环的最少文件与命令集合。

- 初始化：执行 npm init -y 生成 package.json。
- 安装：执行 npm install --save-dev typescript tsx。
- 配置：执行 npx tsc --init 生成 tsconfig.json，可先只关注 strict 与 target。
- 运行：开发时用 npx tsx 直接跑，发布时用 npx tsc 编译后再用 node 运行产物。

```bash
mkdir ts-demo && cd ts-demo
npm init -y
npm install --save-dev typescript tsx
npx tsc --init
```

```ts
// src/index.ts
function formatUserName(firstName: string, lastName: string): string {
  return `${firstName} ${lastName}`;
}

const label = formatUserName("Ada", "Lovelace");
console.log(label); // "Ada Lovelace"
```

```bash
npx tsx src/index.ts
# Ada Lovelace
```

> 类型语法从第 2 篇开始逐项讲解；此处只需确认一条链路：写 .ts 文件、编译检查、运行。

**速记**：npm 安装 typescript 与 tsx，开发用 tsx 跑，产出用 tsc 编译。



### 编译期与运行时的边界

**编译期与运行时的边界**：是 TypeScript 最重要的一条心智模型。类型只在编译期存在，运行时的 JavaScript 对它一无所知。

#### 类型擦除

**类型擦除（erasure）**：指编译产物中不保留任何类型信息，类型只存在于源码与编译过程中。

- 输出无类型：注解、接口、类型别名在编译后全部消失，JavaScript 中找不到痕迹。
- 不可反射：运行时无法查询某个值在 TypeScript 中是什么类型。
- 例外情形：装饰器元数据方案会额外附加信息，那是库的产物，不是语言行为（详见本主题第 15 篇 装饰器）。

```ts
// 输入：src/addScore.ts
function addScore(current: number, delta: number): number {
  return current + delta;
}

console.log(addScore(1, 2)); // 3
```

```js
// 输出：dist/addScore.js，类型标注被移除
function addScore(current, delta) {
  return current + delta;
}

console.log(addScore(1, 2)); // 3
```

> 类型擦除决定了运行时判断仍要用 typeof、instanceof 等 JavaScript 手段（详见本主题第 8 篇 类型收窄与控制流分析）。

**速记**：类型只活在编译期，产物里没有任何类型痕迹。



#### 类型不做运行时校验

**类型不做运行时校验**：指类型注解不会检查运行时的真实数据，外部输入可以违反声明的类型而不被自动拦截。

- 外部数据：来自网络响应、JSON.parse、命令行参数的数据不受编译期约束。
- 断言有限：类型断言只改变编译器的看法，不改变运行时的值（详见本主题第 3 篇 类型注解、类型推断与类型断言）。
- 补位方案：需要运行时校验时应引入 schema 校验库，或手写守卫函数。

```ts
const payload = JSON.parse('{"id":"1"}');   // 编译期无法得知字段类型
const userId: number = payload.id;          // 编译通过
console.log(typeof userId);                 // "string"
```

> 这条边界是初学者最常见的误解来源：编译通过不等于运行正确，类型不能替代输入校验。

> [!WARNING]
> **警告内容**：把接口返回的数据直接断言为业务类型，会让编译期失去保护，错误将推迟到运行时才暴露。

**速记**：类型不校验运行时数据，外部输入必须另行校验。



#### 结构化类型系统初识

**结构化类型（structural typing）**：指两个类型只要成员结构兼容就可以互相赋值，与类型名无关，也称鸭子类型（duck typing）的类型化版本。

- 成员决定兼容：不需要显式继承或实现声明，结构相同即可赋值。
- 与标称类型对比：Java、C# 要求类型名一致，TypeScript 只比较结构。
- 双向后果：同名不同源的类型可以互换，也可能带来意料之外的兼容。

```ts
interface Point2D {
  x: number;
  y: number;
}

interface Vector2D {
  x: number;
  y: number;
}

const origin: Vector2D = { x: 0, y: 0 };
const position: Point2D = origin;   // 允许：成员结构一致
console.log(position.x);            // 0
```

> 结构化类型是类型系统的底层规则，接口、类、泛型约束的行为都建立在它之上，后续篇目会反复用到。

**速记**：结构兼容即可赋值，类型名不参与兼容判断。
