## Rollup 简介与设计取向

### Rollup 是什么

本节先给出 Rollup 的一句话定义，再说明它与打包器的关系与核心能力。

#### Rollup 的定位

**Rollup**：是以 ES Module（ESM，JavaScript 的官方模块规范）为主要输入、把多个模块汇总为少量干净产物的打包器（bundler），长期是 JavaScript 库打包的默认工具。

- 名字含义：Rollup 的字面意思为卷起与汇总，指把分散的模块汇总为一份产物。
- 输入偏好：以 ESM 为主，模块的导入导出关系在语法层面即可静态确定。
- 输出取向：默认不做模块包装，产物接近手写代码，便于阅读与再次打包。
- 主要用途：组件库、工具库、SDK 等需要发布给其他构建工具消费的包。
- 使用形态：既有命令行，也可作为函数库被上层工具调用。

```bash
# 以 ESM 入口直接产出一份 ESM 产物
npx rollup src/index.js --file dist/index.mjs --format es
```

> 判断一个工具是否属于打包器，看它是否解析 import 依赖图并把多个文件合并，Rollup 的核心工作正在于此。

**速记**：Rollup 是以 ESM 输入、汇总为干净产物的打包器，主要用于发布库。



#### 与打包器的关系

**打包器（bundler）**：是沿着模块的导入关系遍历依赖图、把多个源文件合并为少量产物的工具，Rollup 属于其中的一类实现。

- 同属一类：与 webpack、esbuild 一样解析依赖图并合并产物，职责层面平行。
- 差异在取向：Rollup 把库打包作为第一场景，配置面围绕产物控制展开。
- 分工定位：上层框架与脚手架把它当作构建内核复用，而非直接面向业务开发者。
- 能力边界：不做类型检查、不做开发服务器，这些由相邻工具承担。
- 接口形态：核心是构建选项与插件接口两部分，插件接口后来被多个工具借鉴。

```js
// Rollup 也提供编程式接口，供上层工具在自己的流程中调用
import { rollup } from "rollup";

const bundle = await rollup({ input: "src/index.js" });
await bundle.write({ file: "dist/index.mjs", format: "es" });
await bundle.close();
```

> 打包器之间不是替代关系，同一项目里常见生产构建用 Rollup、开发期预构建用 esbuild 的组合。

**速记**：Rollup 是打包器的一种，靠构建选项与插件接口完成依赖图合并与产物控制。



#### 核心能力

**核心能力**：指 Rollup 在构建链路上实际承担的职责，覆盖依赖解析、模块合并、静态分析与多格式产出四块。

- 依赖图构建：从入口出发递归解析 import，确定模块的处理顺序与相互关系。
- 模块合并：默认把所有模块提升到同一作用域，消除模块包装带来的开销。
- 静态分析：在合并过程中判定导出被谁引用，为树摇优化（tree shaking）提供依据。
- 多格式产出：同一次构建可产出 ESM、CommonJS、UMD、IIFE 等不同模块规范的产物。
- 代码分割：在 ESM 输出下按动态导入拆出独立块，供运行时按需加载。

```js
export default {
  input: "src/index.ts",
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named" },
  ],
  external: ["vue"],
};
```

> [!IMPORTANT]
> **重要内容**：Rollup 只做构建，不负责类型检查与开发期服务，类型把关需在流水线中另设类型检查步骤。

**速记**：依赖解析、模块合并、静态分析、多格式产出与代码分割构成 Rollup 的核心能力。



### 与 webpack 的定位差异

本节按服务对象、分析时机与产物形态三条线，说明 Rollup 与 webpack 的取向差异。

#### 面向库与面向应用的取向差异

**面向库**：指产物要被其他构建工具再次消费，因此结构清晰、依赖外部化是首要目标；**面向应用**：指产物直接交付浏览器运行，因此资源处理与运行时装载是首要目标。

- Rollup 侧重点：库与包，输入输出都围绕可复用的模块结构设计。
- webpack 侧重点：应用，围绕入口、资源加载、开发服务器与热更新组织能力。
- 资源处理：webpack 用加载器（loader）统管样式、图片与字体，Rollup 依靠插件按需接入。
- 开发体验：webpack 自带开发服务器与热更新方案，Rollup 只提供监听重建。
- 结论：取向差异先于性能差异，选工具应从产物要被谁消费开始判断。

```js
// 库配置的关键是外部依赖与产物结构，而不是资源加载规则
export default {
  input: "src/index.ts",
  external: ["react", "react-dom"],
  output: { file: "dist/index.mjs", format: "es" },
};
```

> 同一个项目可以两者并存：库用 Rollup 产出可复用模块，应用用 webpack 或 Vite 产出可运行页面。

**速记**：Rollup 面向库、强调模块可复用，webpack 面向应用、强调资源与开发体验。



#### 静态分析与运行时的机制差异

**静态分析**：是在不执行代码的前提下，仅依据语法结构推断模块关系与引用关系；**运行时机制**：是在代码执行过程中通过函数封装与注册表完成模块装载。

- Rollup 路线：以 ESM 语法为准做静态分析，合并后可直接删除未被引用的导出。
- webpack 路线：以函数包装与模块注册表承载模块，可兼容 CommonJS 与 ESM 混用。
- 兼容代价：运行时机制能容纳动态结构，但会保留部分难以静态判定的代码。
- 分析代价：静态路线对代码形态有要求，遇到 CommonJS 依赖需要先转换。
- 取舍依据：产物要再被消费选静态路线，需要兼容存量代码选运行时路线。

```js
// 静态结构可判定：导入名与使用位置在语法上固定
import { formatDate } from "./format.js";
export const stamp = (value) => formatDate(value);
```

> 两条路线的差别不在优劣，而在可分析程度，能被静态判定的代码更容易被安全删除。

**速记**：Rollup 靠静态分析做删除，webpack 靠运行时装载换兼容，代价与收益相反。



#### 产物形态与可读性差异

**产物形态**：指构建结果的文件组织与代码包装方式，直接决定产物能否被阅读与二次处理。

- 包装程度：Rollup 默认不额外包一层模块函数，webpack 的产物带运行时代码与模块表。
- 作用域：Rollup 把模块提升到同一作用域，命名冲突通过重命名解决。
- 可读性：库产物常需要人工核对导出，扁平结构更易比对。
- 体积构成：运行时代码在应用里占比很小，在小型库里却可能超过业务代码本身。
- 二次消费：产物越接近源码结构，越容易被使用方的打包器继续优化。

```text
Rollup 产物结构
  └─ 单一作用域 + 直接导出
webpack 产物结构
  └─ 运行时引导代码 + 模块注册表 + 模块函数
```

> [!NOTE]
> **提醒内容**：产物可读性只在未压缩时成立，开启压缩后两边都变成难读的单行代码，比对应放在未压缩产物上做。

**速记**：Rollup 产物扁平、可直接阅读与二次消费，webpack 产物自带运行时装载代码。



### 树摇优先的设计

本节从 ESM 的静态特性出发，说明摇树优化为何在 Rollup 上效果更好，以及这种优先取向带来的设计代价。

#### 基于 ESM 的静态分析

**ESM 的静态结构**：指 import 与 export 只能出现在模块顶层、导入导出名在语法层面固定，因此无需执行代码即可确定模块间的引用关系。

- 语法约束：导入导出的位置与名称固定，不能在条件分支里临时决定。
- 分析结果：构建器可直接知道某个导出是否被任何模块引用。
- 引用传递：导出被引用后会继续分析其内部引用，形成完整的可达集合。
- 与 CommonJS 的差别：后者可在运行时给导出对象任意添加属性，静态分析无法穷尽。
- 分析前提：源码需保持 ESM 形态，混入 CommonJS 依赖会削弱分析精度。

```js
// 静态可判定：helper 与 defaultExport 的引用关系在语法上固定
export function helper(value) {
  return value * 2;
}

export default function buildConfig() {
  return { scale: helper(2) };
}
```

> 模块化规范的完整原理见本主题第 3 篇，本节只讨论它给摇树优化提供的静态前提。

**速记**：ESM 的导入导出在语法上固定，构建器无需执行代码即可判定引用关系。



#### 摇树效果更好的原因

**摇树优化（tree shaking）**：是在构建期删除未被引用的导出及其独占依赖的过程，Rollup 的效果通常优于同类工具。

- 分析时机：在模块合并前完成，删除动作发生在产物生成的上游。
- 作用域处理：模块提升后跨文件的引用关系仍然可见，可以继续向上裁剪。
- 副作用判定：对顶层无副作用的模块可整块删除，不必保留包装外壳。
- 内联优化：单次使用的小函数可被内联，进一步减少中间变量。
- 结果差异：同一份源码在 Rollup 下的产物体积通常小于带运行时包装的方案。

```js
// 只导入其中一个函数，另一个及其独占依赖会被裁剪
import { parseQuery } from "./query.js";
export const params = parseQuery("?page=2");
```

```js
// 产物形态：未被引用的导出消失，仅保留可达代码
function parseQuery(input) {
  return new URLSearchParams(input);
}
const params = parseQuery("?page=2");
export { params };
```

> [!NOTE]
> **提醒内容**：摇树效果取决于代码形态，顶层带副作用的模块无法整块删除，写法会直接抵消优化收益。

**速记**：模块提升加静态引用分析让 Rollup 能跨文件裁剪，产物体积因此更小。



#### 树摇优先带来的设计代价

**设计代价**：指把可分析性放在兼容性之前所付出的成本，体现为对输入形态的要求与插件依赖。

- 输入要求：以 ESM 为基准，CommonJS 依赖需先用插件转换后才能进入分析。
- 解析要求：默认不解析依赖目录，第三方包需显式开启解析插件。
- 动态结构受限：运行时拼装导出名的写法无法被静态分析识别。
- 配置成本：每补一类输入形态就多一层插件与顺序约束。
- 收益回收：换来的是产物干净、体积可控，适合对包大小敏感的发布场景。

```js
// 让 CommonJS 依赖先转成 ESM，才能进入静态分析
import resolve from "@rollup/plugin-node-resolve";
import commonjs from "@rollup/plugin-commonjs";

export default {
  input: "src/index.js",
  output: { file: "dist/index.mjs", format: "es" },
  plugins: [resolve(), commonjs()],
};
```

> 对输入形态的约束是树摇优先的直接代价，配置中的解析与转换插件正是为补齐这一环。

**速记**：树摇优先要求保持 ESM 形态，代价是必须接入解析与 CommonJS 转换插件。



### 适用场景与不适用场景

本节先列出适合库与工具包的用法，再说明应交给其他工具的边界。

#### 库与组件包的典型场景

**库打包**：是把源码构建为可被使用方再次打包的模块产物的过程，产物质量优先于构建速度。

- 组件库：单文件组件与样式分离，产物需保留按需引入能力。
- 工具库：函数集合，依赖少、导出多，最能体现树摇的收益。
- 多格式发布：一次构建同时给出 ESM 与 CommonJS，覆盖不同使用方。
- 依赖外部化：框架与运行时依赖列为外部依赖，避免产物内出现副本。
- 声明文件：类型声明由类型编译器单独产出，与构建产物并列发布。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: [
    { file: "dist/index.mjs", format: "es" },
    { file: "dist/index.cjs", format: "cjs", exports: "named" },
  ],
};
```

> 库产物的第一读者是使用方的构建工具，因此保留模块结构比压缩体积更重要。

**速记**：组件库、工具库与多格式发布是 Rollup 的主场，核心是外部依赖与产物结构。



#### 工具包与 SDK 的场景

**工具包与 SDK**：是能力单一、面向外部调用方的代码集合，产物常需要同时支持多种引入方式。

- 能力单一：导出集合稳定，树摇后使用方只加载实际调用的部分。
- 多引入方式：既有模块引入，也可能需要脚本标签直引，需要多格式产物。
- 体积敏感：SDK 常被嵌进他人页面，产物体积直接影响宿主页面。
- 全局名暴露：脚本标签直引的格式需要指定全局变量名。
- 版本稳定：对外接口不宜频繁变动，构建配置随之保持稳定。

```js
export default {
  input: "src/index.ts",
  output: [
    { file: "dist/sdk.mjs", format: "es" },
    { file: "dist/sdk.umd.js", format: "umd", name: "TrackSdk" },
  ],
};
```

> [!TIP]
> **建议内容**：面向浏览器的 SDK 可先产出 ESM 供打包器消费，再补一份脚本标签直引格式，两种场景互不影响。

**速记**：工具包与 SDK 体积敏感、引入方式多样，适合用多格式产物覆盖。



#### 不适用场景与边界

**不适用场景**：指 Rollup 因缺少对应能力而不应承担的任务，应交由具备该能力的工具。

- 开发服务器：Rollup 不提供开发期服务与热更新，页面开发需换用上层方案。
- 资源密集型应用：图片、字体、样式的统一处理不是它的长处，需大量插件补齐。
- CommonJS 存量工程：大量依赖为 CommonJS 时，转换环节会成为维护负担。
- 类型检查：构建过程不做类型校验，错误不会阻断产物生成。
- 大型应用构建：缓存与并行能力有限，超大型工程的构建耗时明显。

```bash
# 监听模式只负责重建，不提供开发期服务
npx rollup -c -w
```

> 判断是否适用的一条简则：产物要被其他构建工具继续处理时选 Rollup，产物要直接跑在浏览器里时选应用侧工具。

**速记**：开发服务器、资源密集处理与类型检查都不在 Rollup 职责内，需另选工具。



### 生态位置

本节说明 Rollup 被哪些上层工具复用，以及它与另外几个构建工具的分工。

#### 被上层工具复用

**构建内核**：指被上层框架或脚手架以依赖形式引入、承担实际打包工作的底层工具。

- Vite 的生产构建：开发期由 esbuild 承担预构建，生产构建交由 Rollup 打包。
- 插件接口的输出：其插件接口被其他工具借鉴或兼容，配置心智可以迁移。
- 配置形态的复用：上层工具常把构建选项以透传方式暴露给使用者。
- 版本耦合：升级上层工具可能同时更换底层版本，配置前需确认实际承担者。
- 生态收益：插件与配置经验在直接使用与间接使用之间可以互通。

```bash
# 上层工具透传构建选项后，最终执行打包的仍是 Rollup
npm run build
```

> [!CAUTION]
> **注意内容**：上层工具升级可能连带更换底层打包器版本，构建结果的差异要先归因到版本变更，再改配置。

**速记**：Rollup 是 Vite 生产构建的底层内核，插件与配置经验可直接迁移。



#### 与 webpack 的分工

**分工**：指按产物消费方把库与应用分配给不同工具，两者在同一工程内并存。

- 库侧：Rollup 产出可复用模块，依赖外部化，交由使用方继续处理。
- 应用侧：webpack 或 Vite 负责页面产物、资源处理与开发体验。
- 衔接点：库的产物通过包入口字段被应用侧解析，两边通过标准模块格式对接。
- 常见组合：组件库里用 Rollup 打包，示例站点与文档站用应用侧工具构建。
- 选型依据：先定产物消费方，再定工具，避免用应用工具硬做库产物。

```json
{
  "name": "@my-scope/ui",
  "version": "1.0.0",
  "module": "./dist/index.mjs",
  "main": "./dist/index.cjs",
  "scripts": {
    "build": "rollup -c"
  }
}
```

> 库与应用的分工是选型的主线，其余差异都是这条主线的延伸。

**速记**：库交 Rollup、应用交 webpack 或 Vite，两者通过标准模块格式衔接。



#### 与 esbuild、SWC 的关系

**关系**：指三类工具在构建链路中承担不同环节，可以组合而非互相替代。

- 环节划分：Rollup 负责打包与产物控制，esbuild 与 SWC 擅长单文件转译与压缩。
- 组合方式：转译交给快工具，打包与产物组织交给 Rollup，各取所长。
- 速度取舍：Rollup 在大型项目上更依赖插件与缓存，速度不及 Go 或 Rust 实现。
- 产物取舍：快工具的产物控制粒度较粗，库场景仍以 Rollup 为主。
- 能力与用法的细节见本主题第 12 篇，本节只作环节划分上的衔接。

```text
源码 → 转译（esbuild／SWC 类工具）→ 打包与产物组织（Rollup）→ 发布产物
```

> esbuild 与 SWC 的能力与用法见本主题第 12 篇，本节只作环节划分上的衔接。

**速记**：Rollup 管打包与产物，esbuild 与 SWC 管转译压缩，三者按环节组合。
