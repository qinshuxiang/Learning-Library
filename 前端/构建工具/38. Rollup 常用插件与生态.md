## Rollup 常用插件与生态

### 解析与转换类插件

#### 依赖解析插件

**依赖解析插件（bare import resolver）**：是把裸模块说明符映射到依赖目录中真实文件路径的插件，Rollup 自身只解析相对与绝对路径。

- 解决对象：写在导入语句里的裸包名，未经解析时不会被纳入模块图。
- 解析依据：读取被依赖包的清单字段，按入口字段与条件导出依次尝试。
- 常用选项：extensions 补全扩展名，mainFields 指定优先读取的清单字段，browser 优先浏览器入口。
- 内置模块：Node 内置模块需显式外部化，解析插件一般提供开关把它标记为外部依赖。
- 与别名关系：别名在先把自定义前缀改写成路径，解析插件在后把路径落到实体文件。

```js
import { defineConfig } from "rollup";
import resolve from "@rollup/plugin-node-resolve";   // 官方依赖解析插件

export default defineConfig({
  input: "src/index.js",
  output: { file: "dist/index.js", format: "es" },
  plugins: [
    resolve({
      extensions: [".mjs", ".js", ".json"],
      mainFields: ["module", "main"],
      browser: true,
      preferBuiltins: true,
    }),
  ],
});
```

> [!WARNING]
> **警告内容**：缺少解析插件时，裸包导入只以未解析导入的警告收场且不进入产物，库产物随即在运行时报模块找不到，构建配置里必须显式声明解析能力。

**速记**：解析插件把裸包名落到实体文件，靠 extensions 与 mainFields 决定命中哪份入口。



#### CommonJS 转换插件

**CommonJS 转换插件（commonjs plugin）**：是把 CommonJS 模块改写为 ES Module 形态、让静态分析得以进行的插件，处理 require、module.exports 与 __dirname 等写法。

- 转换目标：把导出与导入改写成 Rollup 能分析的静态形式，未命中的写法仍留在产物中。
- 动态写法：运行期拼接的 require 表达式无法静态确定，需要显式登记或改用静态导入。
- 混合项目：同时含 ESM 与 CJS 的依赖目录，需要该插件与解析插件配合才能完整打包。
- 命名导出：CJS 的导出对象转换后可能拿不到具名导出，必要时补充导出名映射。
- 与外部化配合：已列入 external 的依赖不应再被转换，两者混用会让同一模块既打包又外部化。

```js
import { defineConfig } from "rollup";
import resolve from "@rollup/plugin-node-resolve";
import commonjs from "@rollup/plugin-commonjs";        // 官方 CommonJS 转换插件

export default defineConfig({
  input: "src/index.js",
  external: ["fs"],
  output: { file: "dist/index.js", format: "es" },
  plugins: [
    resolve({ preferBuiltins: true }),
    commonjs({ include: /node_modules/, transformMixedEsModules: true }),
  ],
});
```

> [!IMPORTANT]
> **重要内容**：已声明的外部依赖要排除在 CommonJS 转换范围之外，否则同一依赖会被先转成 ESM 再打入产物，外部化声明形同虚设。

**速记**：CommonJS 转换插件把 require 与 module.exports 改写成 ESM，须与外部化范围划清边界。



#### 替换与别名插件

**替换插件（replace plugin）**：是在构建期把指定字符串替换为固定值的插件，用于注入环境常量；**别名插件（alias plugin）**：是把自定义导入前缀映射到真实路径的插件。

- 替换范围：默认按标识符边界匹配，需要更宽的匹配时显式开启字符串替换。
- 分隔符：配置替换的边界字符，避免把变量名的一部分误替换。
- 别名条目：以查找串与替换串成对声明，可声明多条并按数组顺序匹配。
- 与配置对齐：别名需与编辑器、类型检查器使用的路径映射一致，否则两边解析结果不同。
- 执行位置：替换与别名都应在解析之前完成，改写结果才能被后续解析命中。

```js
import { defineConfig } from "rollup";
import replace from "@rollup/plugin-replace";
import alias from "@rollup/plugin-alias";

export default defineConfig({
  input: "src/index.js",
  output: { file: "dist/index.js", format: "es" },
  plugins: [
    replace({
      preventAssignment: true,
      values: { "process.env.NODE_ENV": JSON.stringify(process.env.NODE_ENV ?? "development") },
    }),
    alias({ entries: [{ find: "~utils", replacement: "./src/utils" }] }),
  ],
});
```

> 替换得到的是字面量，替换值必须序列化为代码文本，直接传普通字符串会得到未加引号的标识符而报语法错误。

**速记**：替换插件注入构建期常量，别名插件改写导入前缀，两者都要排在解析之前。



### 压缩与优化类插件

#### 代码压缩插件

**代码压缩插件（minify plugin）**：是对最终产物做标识符改写、空白剔除与死代码删除的插件，在输出阶段对每个产物各执行一次。

- 接入位置：放在插件数组末尾，确保压缩作用于全部转换与替换完成后的代码。
- 常用选项：压缩级别、标识符混淆、顶层作用域压缩与注释保留按需开启。
- 保留清单：需要保留的函数名与类名用保留选项声明，避免反射与序列化场景失效。
- 剔除语句：调试类语句与断言可在压缩时移除，直接减少产物体积。
- 多格式注意：压缩插件对每个输出各执行一次，多格式产物需各自配置压缩选项。

```js
import { defineConfig } from "rollup";
import terser from "@rollup/plugin-terser";            // 官方压缩插件

export default defineConfig({
  input: "src/index.js",
  output: { file: "dist/index.min.js", format: "es", sourcemap: true },
  plugins: [
    terser({
      compress: { drop_console: true, drop_debugger: true, passes: 2 },
      mangle: { toplevel: true, reserved: ["DateKit"] },
      format: { comments: false },
    }),
  ],
});
```

> 库产物是否压缩由发布约定决定，供打包器消费的入口通常保留未压缩版本，另出一份压缩版供浏览器直接引用。

**速记**：压缩插件放数组末尾，混淆与剔除按需开启，保留清单留给需要反射的名字。



#### 辅助代码与体积精简

**辅助代码重复**：是转译与降级过程中产生的同一段工具函数在多个模块中各出现一份、推高产物体积的现象。

- 成因：每个模块单独转译时，转译器为该模块内联一份辅助函数。
- 表现：产物中出现大量同名短函数，重复部分随模块数近似线性增长。
- 精简手段：让转译阶段共享一份辅助实现，或由压缩插件合并等价函数。
- 打包差异：转译与打包在同一链路上完成时，重复更容易被后续压缩消除。
- 核对方式：压缩前后对比产物体积，重复量越大压缩带来的降幅越明显。

```text
未处理：src/a.js 内联一份 helper   ≈ 0.4 kB
        src/b.js 内联一份 helper   ≈ 0.4 kB
精简后：dist/index.js 共用一份      ≈ 0.4 kB
```

> 辅助代码重复在模块数量少时不明显，模块数上百后可能占据产物的可观比例，库打包时应优先核对。

**速记**：辅助代码重复来自逐模块转译，靠共享辅助实现或压缩后合并来精简。



#### 压缩与 source map 的配合

**压缩与 source map**：是把压缩前的位置映射到压缩后位置的映射数据，缺失时线上报错的堆栈无法还原到源码。

- 开启方式：在输出配置中打开 sourcemap 选项，压缩插件会据此生成并串联映射。
- 映射链：转译插件的映射与压缩插件的映射需要逐段衔接，任一段缺失都会让链条断开。
- 内容保留：产物中的映射可带源码内容，便于在不发布源码时也能定位来源。
- 发布策略：映射可跟随产物发布，也可上传到错误监控平台而不进入发布包。
- 体积影响：映射体积通常远超产物本身，是否随包分发需按发布约定决定。

```js
import terser from "@rollup/plugin-terser";

export default {
  input: "src/index.js",
  output: {
    file: "dist/index.min.js",
    format: "es",
    sourcemap: true,
    sourcemapExcludeSources: true,
  },
  plugins: [terser()],
};
```

> [!CAUTION]
> **注意内容**：压缩开启而映射关闭时，线上堆栈只指向压缩后的一行代码，排查效率极低，压缩与映射必须成对开启或成对关闭。

**速记**：映射要在转译与压缩之间逐段衔接，压缩与映射成对开启才有定位价值。



### 分析与可视化插件

#### 产物体积分析

**产物体积分析插件**：是读取产物与模块图、输出各模块与依赖占体积比例的插件，用于定位体积异常的来源。

- 数据来源：模块图中的每个模块及其在产物中的贡献，含依赖目录中的包。
- 呈现形式：常见为可交互的矩形分区图与可排序列表，按体积从大到小排列。
- 关注指标：同时在意的还有压缩后体积与传输体积，两者与原始体积的差距可能很大。
- 定位方法：先看体积最大的依赖，再判断它是否必要、能否替换或改为按需引入。
- 使用时机：产物体积异常增长或上线前做体积审计时开启，不必常驻构建链路。

```text
dist/index.js   182.4 kB │ gzip 58.1 kB
├─ lodash-es      96.2 kB   52.8%
├─ src/core       41.7 kB   22.9%
└─ dayjs          30.5 kB   16.7%
```

> 原始体积大不等于传输体积大，判断是否值得优化要先看压缩与传输后的数值，再决定是否替换依赖。

**速记**：体积分析先看最大依赖，再比原始、压缩与传输三个口径，按需开启不常驻。



#### 依赖关系可视化

**依赖关系可视化**：是把模块之间的导入关系导出为图结构或描述文件的插件能力，用于发现循环依赖与意外的耦合。

- 输出形式：常见为图描述文件交给外部渲染，或直接生成可查看的页面。
- 关键用途：识别循环依赖、确认某模块是否被意外引入、核对模块之间的划分。
- 与解析的关系：可视化读的是构建产出的模块图，只能反映真实被解析到的模块。
- 观察成本：大型仓库的完整图节点过多，通常按入口或按目录范围过滤后再导出。
- 使用时机：重构依赖结构或排查循环依赖时使用。

```js
export default {
  input: "src/index.js",
  output: { dir: "dist", format: "es" },
  plugins: [graphExportPlugin({ include: /^src\// })],   // 依赖图导出插件，包名以插件文档为准
};
```

```text
src/index.js
├── src/core/render.js
│   └── src/utils/dom.js
└── src/utils/dom.js
```

> 同一模块在图里出现两次通常意味着它被多个上层模块引用，若两个上层模块又互相引用，就构成需要拆开的循环依赖。

**速记**：依赖图导出用于找循环依赖与核对模块划分，大仓库先过滤范围再导出。



#### 构建统计与日志

**构建统计**：是记录模块数量、产物体积与各阶段耗时并在构建结束时汇总输出的做法，用于建立体积与耗时基线。

- 采集位置：模块相关数据取自模块分析类钩子，体积与耗时取自输出与收尾钩子。
- 汇总方式：在收尾钩子中一次性打印，避免逐模块输出淹没终端。
- 基线用途：把每次构建的数值记录下来，体积或耗时突变时能立刻察觉。
- 与警告配合：未解析导入、循环依赖等警告应计入同一份输出，便于对照。
- 落地形式：可打印到终端，也可写成产物旁的报告文件随构建归档。

```js
export default {
  input: "src/index.js",
  output: { file: "dist/index.js", format: "es" },
  onwarn(warning, warn) {
    if (warning.code === "CIRCULAR_DEPENDENCY") {
      console.warn(`[circular] ${warning.ids.join(" -> ")}`);
      return;
    }
    warn(warning);
  },
};
```

> 循环依赖警告指向的是一组互相导入的模块，处理时按组梳理导入方向，逐个改成单向依赖为止。

**速记**：统计在收尾钩子汇总一次，体积与耗时同步记录，才能建立可对照的基线。



### 插件的组合与顺序

#### 顺序为何重要

**插件顺序**：是插件数组的排列次序，它同时决定首命中钩子的归属与串行钩子的执行先后，顺序本身就是配置的一部分。

- 首命中影响：解析与加载类钩子取首个非空返回值，顺序不同结果可能完全不同。
- 串行影响：转换类钩子逐个串联，前一个改写的代码即后一个的输入。
- 依赖方向：别名与替换要排在解析之前，压缩要排在全部转换之后。
- 复现要求：同一份插件清单在任何机器上都产生同样的顺序，配置中不要用不确定的顺序拼接。

```js
import replace from "@rollup/plugin-replace";
import alias from "@rollup/plugin-alias";
import resolve from "@rollup/plugin-node-resolve";
import commonjs from "@rollup/plugin-commonjs";
import terser from "@rollup/plugin-terser";

export default {
  input: "src/index.js",
  output: { file: "dist/index.js", format: "es" },
  plugins: [
    replace({ values: { __DEV__: "false" }, preventAssignment: true }),
    alias({ entries: [{ find: "@", replacement: "./src" }] }),
    resolve(),
    commonjs(),
    terser(),
  ],
};
```

> [!IMPORTANT]
> **重要内容**：把压缩插件排在转换插件之前，会让后续转换在压缩后的代码上进行，产物可能因此无法正确运行，顺序错误往往不报错只出错。

**速记**：顺序决定首命中归属与串行次序，替换别名在前、压缩在后是硬约束。



#### 常见顺序约定

**常见顺序约定**：是按插件职责把数组分成替换别名、解析转换、分析统计、压缩后处理四段，段内顺序可调、段间顺序固定。

- 第一段替换与别名：先做字面替换与路径改写，为后续解析准备好说明符。
- 第二段解析与转换：解析依赖、转换模块格式、执行语法降级与资源处理。
- 第三段分析与统计：读取模块图与产物信息，通常是只读操作，段内顺序不敏感。
- 第四段压缩与后处理：压缩、追加头注释与体积校验放在最后一段。
- 段内原则：同一段内功能相近的插件紧邻摆放，便于看出谁与谁存在竞争。

```text
plugins 数组的推荐分段
1. replace / alias          字面替换与路径改写
2. resolve / commonjs       解析依赖与模块格式统一
3. transform / 资源处理      语法转换与资源接入
4. 分析统计                  模块图与产物读取
5. terser / 体积校验         压缩与后置检查
```

> 分段只是排列约定，不改变钩子的执行时机：构建阶段钩子仍先于输出阶段钩子，输出阶段钩子仍按产物重复触发。

**速记**：按替换别名、解析转换、分析统计、压缩后处理四段排列，段内可调段间固定。



#### 能力重叠与冲突

**能力重叠**：是多个插件在同一钩子上做同类改写的现象，表现为重复转换、产物出现重复代码或警告来源不清。

- 识别方式：同一文件被两次改写、产物出现成对重复代码、警告里的插件名与预期不符。
- 常见组合：两个都做替换的插件、解析插件与别名插件覆盖同一前缀、压缩插件装了两个。
- 后果：除体积浪费外，还可能因两次改写互相抵消而丢失代码。
- 处理方式：保留职责最匹配的一个，把另一个的能力合并进配置而不是叠加。
- 预防：引入新插件前先核对其钩子与已有插件是否重叠。

```js
// 同一份配置中重复挂载压缩插件，等价于对产物压缩两次
export default {
  input: "src/index.js",
  output: { file: "dist/index.js", format: "es" },
  plugins: [
    terser({ compress: { drop_console: true } }),
    terser({ compress: { passes: 2 } }),
  ],
};
```

> [!CAUTION]
> **注意内容**：能力重叠不一定立刻报错，重复改写可能只表现为产物变大或行为偏移，插件清单变更后应重新核对体积与警告输出。

**速记**：重叠表现为重复改写与成对代码，保留职责最匹配的一个，不做叠加。



### 插件选型建议

#### 必要插件与可选插件

**必要插件**：是不装就无法完成常见构建的插件；**可选插件**：是按产物形态与发布方式决定是否引入的插件。

- 必要集合：依赖解析与 CommonJS 转换是处理第三方依赖的前提，多数项目都要装。
- 视格式而定：压缩只在需要压缩产物时引入，ESM 与 CJS 双份发布通常各自决定。
- 视资源而定：类型、样式与资源的处理插件取决于项目是否使用对应文件类型。
- 视阶段而定：分析与可视化只在审计时挂载，常驻会拖慢每轮构建。
- 最小起步：先装必要集合跑通构建，再按实际报错增量添加，避免一次装齐。

```bash
npm install --save-dev rollup
npm install --save-dev @rollup/plugin-node-resolve @rollup/plugin-commonjs
# 先装解析与 CommonJS 转换，其余按需追加
```

> [!NOTE]
> **提醒内容**：插件装得越多，构建耗时与升级成本越高，每引入一个都应能说清它解决的报错或需求，否则从清单中移除。

**速记**：解析与 CommonJS 转换是必要集合，压缩、资源与分析类按产物与阶段引入。



#### 插件的来源与维护状态

**插件来源**：是插件由官方维护、社区维护还是内部维护的属性，直接决定版本兼容性与问题响应速度。

- 官方集合：与构建器同一组织维护的插件，版本与主版本升级同步，优先级最高。
- 社区插件：功能更专一但维护状态不一，引入前查看最近发布与未处理问题。
- 内部插件：只在本仓库维护，缺少外部使用者，稳定性取决于内部测试覆盖。
- 更新节奏：随构建器主版本升级重新核对插件，避免跨主版本组合未经验证。
- 替代准备：对维护停滞的插件预先准备替代方案，避免被迫长期锁定旧版本。

```bash
npm view @rollup/plugin-node-resolve version
npm view @rollup/plugin-commonjs time.modified
# 查看最近发布与最近修改时间，判断维护节奏
```

> 判断插件是否可靠的最低标准是能否在构建器主版本升级后持续发布，长期停更的插件会成为升级阻力。

**速记**：官方优先、社区看维护状态、内部靠测试覆盖，升级前统一核对插件。



#### 自研与选用的边界

**自研插件**：是当现成插件无法满足、或引入成本高于自写成本时自行编写的插件，判据是需求与维护成本的对比。

- 适用情形：需求专属于本项目、现成插件回调过多、或只需几十行的轻量替换。
- 不适用情形：涉及解析、压缩这类已有成熟实现且边界复杂的环节。
- 成本核算：自研插件要承担文档、测试与后续构建器升级适配的成本。
- 组合策略：先用现成插件覆盖通用能力，只对缺口部分自研小插件补足。
- 退出机制：自研插件出现等价现成方案时应评估迁回，减少长期自维护面。

```js
export default function defineHeaderPlugin(entries = {}) {
  const header = Object.entries(entries)
    .map(([key, value]) => `/* ${key}: ${value} */`)
    .join("\n");
  return {
    name: "define-header",
    renderChunk(code, chunk) {
      return chunk.isEntry ? { code: `${header}\n${code}`, map: null } : null;
    },
  };
}
```

> [!TIP]
> **建议内容**：自研插件优先做成只依赖钩子参数、不依赖其他插件的形态，减少与插件清单的耦合，后续替换或删除时影响面更小。

**速记**：通用能力用现成插件，专属缺口自研轻量插件，并核算文档与升级成本。
