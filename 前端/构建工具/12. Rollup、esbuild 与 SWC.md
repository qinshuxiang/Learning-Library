## Rollup、esbuild 与 SWC

### Rollup 与库打包

**Rollup**：是以 ES Module 为输入、产出高度干净产物的打包器（bundler），长期是 JavaScript 库打包的首选工具。

本模块说明 Rollup 的定位、安装与配置方式、以及多格式产物的输出方法。

#### Rollup 的定位与适用场景

**Rollup 的定位**：是面向库与应用两端的打包器，因静态分析彻底而产出无包装的扁平代码，尤其适合发布可被再次打包的库。

- 输入形态：以 ES Module 为主要输入，静态结构让摇树优化更彻底。
- 产物质量：默认不做模块包装，输出接近手写代码，便于阅读与二次打包。
- 适用场景：组件库、工具库、SDK 等需要同时发布多种模块格式的包。
- 应用场景：Vite 的生产构建底层即使用 Rollup，说明其在应用侧同样可用。
- 差异点：动态导入与代码分割依赖产物格式，CommonJS 输出下分割能力受限。

```bash
npm install --save-dev rollup
npx rollup src/index.js --file dist/index.js --format es
```

> Rollup 的核心竞争力不在速度，而在静态分析与产物的干净程度，这决定了它在库打包上的长期地位。

**速记**：Rollup 以 ESM 为输入、产物干净、摇树彻底，是库打包的默认答案。



#### 安装与配置文件

**Rollup 配置文件**：是导出构建选项的对象或数组，默认文件名 rollup.config.mjs，也可用 rollup.config.js。

- 依赖安装：核心包是 rollup，常用插件按需安装，如解析与 CommonJS 转换插件。
- 配置文件：用 defineConfig 包裹配置对象即可获得类型提示，配置可导出对象或对象数组。
- 关键字段：input 指定入口，output 指定产物位置与格式，plugins 指定插件列表。
- 命令行用法：rollup 命令加上 -c 表示读取配置文件，加 -w 表示监听源码变化重建。
- 多份配置：导出数组即可一次构建多个目标，例如分别产出 ESM 与 CommonJS。

```bash
npm install --save-dev rollup @rollup/plugin-node-resolve @rollup/plugin-commonjs
```

```js
// rollup.config.mjs
import { defineConfig } from "rollup";
import resolve from "@rollup/plugin-node-resolve";
import commonjs from "@rollup/plugin-commonjs";

export default defineConfig({
  input: "src/index.js",
  output: {
    file: "dist/index.js",
    format: "es",
    sourcemap: true,
  },
  plugins: [resolve(), commonjs()],
});
```

```bash
npx rollup -c
npx rollup -c -w
```

> Rollup 只理解 ES Module，默认不解析 node_modules 中的依赖，也不识别 CommonJS，缺失时需补上解析与转换插件。

**速记**：rollup -c 读配置、-w 监听，input 与 output 与 plugins 三个字段撑起基本配置。



#### 输出格式与 external

**输出格式（format）**：决定产物使用的模块规范，取 es、cjs、umd 或 iife，需与发布目标的使用方匹配。

- es：输出 ES Module，供现代打包器与原生模块环境使用，是首选格式。
- cjs：输出 CommonJS，供 Node.js 与旧打包器使用，与 es 并列发布最为常见。
- umd 与 iife：输出可直接以脚本标签加载的全局产物，适合浏览器直引场景，需指定全局变量名。
- external：声明不打包进产物的依赖，通常把运行时依赖与同伴依赖列入其中。
- 目录模式：output.dir 配合 preserveModules 保留源码的模块结构，便于逐文件按需引用。

```js
export default defineConfig({
  input: "src/index.js",
  external: ["lodash-es"],
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named", sourcemap: true },
    { file: "dist/index.umd.js", format: "umd", name: "DateKit", globals: { "lodash-es": "_" } },
  ],
});
```

```json
{
  "name": "date-kit",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "files": ["dist"]
}
```

> [!WARNING]
> **警告内容**：external 漏写运行时依赖会把该依赖整体打包进产物，使用方再安装时会出现两份实例，单例状态与 instanceof 判断随之失效。

**速记**：format 决定模块规范，external 把依赖排除在外，exports 字段把多格式产物的入口声明清楚。



### esbuild 的能力与用法

**esbuild**：是用 Go 编写的极快打包器与转译器，支持打包、转译、压缩与代码分割，配置面小、启动毫秒级。

本模块讲清 esbuild 的能力边界、命令行选项与编程式调用方式。

#### esbuild 的特点与能力

**esbuild 的特点**：是把解析、转译、打包、压缩与代码分割集中在一个可执行文件中的构建工具，以速度为主要卖点。

- 速度来源：Go 编写并充分利用多核并行，基准场景下比同类工具快一至两个数量级。
- 内置能力：支持 TypeScript 与 JSX 语法转译、CSS 打包、环境变量替换与代码压缩。
- 输入类型：通过 loader 机制识别 JSON、CSS、图片与文本等资源，可内联为 data URL。
- 代码分割：仅在输出格式为 es 且开启 splitting 时生效，用于按需加载场景。
- 能力边界：插件接口比 Rollup 简单，部分 Babel 插件能力缺失，类型相关限制见下文。

```bash
npx esbuild src/index.ts --bundle --outfile=dist/index.js --platform=browser --target=es2017
# dist/index.js  12.4kb
# ⚡ Done in 9ms
```

> esbuild 的快来自「少做转换、直接扫描」，代价是舍弃了部分高度可配置的转换能力，两者取舍需按场景判断。

**速记**：esbuild 以 Go 并行实现极快速度，内置打包与转译，但不做类型检查。



#### 命令行与常用选项

**esbuild 命令行选项**：是控制入口、输出、目标环境与优化行为的参数集合，多数配置在命令行即可完成。

- 入口与输出：入口作为位置参数给出，--outfile 指定单文件输出，--outdir 指定多文件输出目录。
- 打包开关：--bundle 把依赖一并打包，缺省时只做转译不合并文件。
- 目标环境：--target 指定输出语法版本，--platform 取 browser 或 node，决定默认条件与外部依赖处理。
- 优化选项：--minify 压缩，--sourcemap 生成映射，--define 在构建期替换标识符。
- 开发选项：--watch 监听重建，--serve 启动静态服务并支持自动刷新。
- 资源处理：--loader 为指定扩展名指定类型，如把图片转成 data URL。

```bash
npx esbuild src/index.ts \
  --bundle \
  --outdir=dist \
  --format=esm \
  --target=es2019 \
  --platform=browser \
  --minify \
  --sourcemap \
  --define:process.env.NODE_ENV='"production"'
```

```bash
npx esbuild src/index.tsx --loader:.png=dataurl --loader:.json=json --bundle --outfile=dist/app.js
```

> 命令行适合一次性构建与简单项目；选项增多后应改用配置文件或编程式调用，便于复用与版本管理。

**速记**：--bundle 决定是否打包，--target 与 --platform 决定环境，--define 在构建期做常量替换。



#### 编程式调用与构建脚本

**编程式调用**：是在 Node.js 脚本中引入 esbuild 包并调用 build 或 context 方法，适合复杂配置与集成到自定义流程。

- build 方法：一次性构建，返回产物信息，适合持续集成中的单次打包。
- context 方法：创建构建上下文，可调用 watch 与 serve，适合本地开发。
- 插件机制：插件通过 onResolve 钩子决定模块如何解析，通过 onLoad 钩子决定模块内容如何生成。
- 环境区分：在脚本中按环境变量拼装选项，避免维护多份配置文件。
- 声明文件：需要类型声明时另行调用 tsc 生成，esbuild 自身不产出声明文件。

```js
// build.mjs
import { build, context } from "esbuild";

const sharedOptions = {
  entryPoints: ["src/index.ts"],
  bundle: true,
  target: "es2019",
  platform: "browser",
  sourcemap: true,
};

if (process.env.NODE_ENV === "development") {
  const ctx = await context({ ...sharedOptions, outdir: "dist" });
  await ctx.watch();
} else {
  await build({ ...sharedOptions, outdir: "dist", minify: true });
}
```

```js
// 自定义插件：把特定模块替换为桩实现
const stubLoggerPlugin = {
  name: "stub-logger",
  setup(build) {
    build.onResolve({ filter: /^logger$/ }, () => ({ path: "logger", namespace: "stub" }));
    build.onLoad({ filter: /.*/, namespace: "stub" }, () => ({
      contents: "export const log = () => {};",
      loader: "js",
    }));
  },
};
```

> [!IMPORTANT]
> **重要内容**：esbuild 只剥离 TypeScript 类型不做检查，类型错误不会让构建失败，需在流水线中单独跑 tsc --noEmit 把关。

**速记**：build 一次性构建、context 支持监听与服务，插件用 onResolve 与 onLoad 两个钩子。



### SWC 与 Rust 系工具

**SWC**：是用 Rust 编写的高性能 JavaScript 与 TypeScript 转译器，定位为 Babel 的替代实现，只做转译不做打包。

本模块说明 SWC 的定位、配置文件写法与相对 Babel 的取舍。

#### SWC 的定位

**SWC 的定位**：是提供语法转译、压缩与目标环境降级的编译器，可作为 Babel 与 Terser 的替代品接入既有构建链。

- 核心能力：把 TypeScript、JSX 与新语法转译为目标环境可执行的代码，同时支持代码压缩。
- 性能表现：以 Rust 实现并多线程执行，转译速度通常显著快于 Babel。
- 接入形态：既有命令行，也有 webpack 的 swc-loader、Jest 的 @swc/jest 与 Vite 的 SWC 版 React 插件。
- 使用范围：被 Next.js 等框架选为默认编译器，说明其在生产链路上的成熟度。
- 定位边界：不做模块打包、不做类型检查，这两项仍分别交给打包器与类型检查器。

```bash
npm install --save-dev @swc/core @swc/cli
npx swc src -d dist
# Successfully compiled 12 files with swc
```

> SWC 与 Babel 是同一环节的两种实现，替换发生在转译层，打包与压缩链路其余部分保持不变。

**速记**：SWC 是 Rust 写的高性能转译器，替代 Babel 与压缩器，不做打包与类型检查。



#### .swcrc 配置写法

**.swcrc**：是 SWC 的配置文件，JSON 格式，按解析器、目标版本、转换插件与模块格式分组声明。

- 解析器：jsc.parser.syntax 指明语法为 typescript 或 ecmascript，tsx 与 decorators 按需开启。
- 目标版本：jsc.target 指定输出语法版本，或改用 env.targets 按浏览器范围决定。
- 转换选项：jsc.transform.react.runtime 取 automatic 启用新运行时，legacyDecorator 兼容旧装饰器语义。
- 环境降级：env.mode 取 usage 时按代码实际使用注入垫片，coreJs 指定垫片版本。
- 模块格式：module.type 取 es6 保留 ESM，取 commonjs 输出 CommonJS。
- 压缩选项：minify 为 true 时启用内置压缩，替代单独的压缩工具。

```json
{
  "jsc": {
    "parser": {
      "syntax": "typescript",
      "tsx": true,
      "decorators": true
    },
    "target": "es2019",
    "transform": {
      "react": { "runtime": "automatic" },
      "legacyDecorator": true,
      "decoratorMetadata": true
    }
  },
  "env": {
    "targets": "> 0.5%, last 2 versions, not dead",
    "mode": "usage",
    "coreJs": "3.37"
  },
  "module": {
    "type": "es6"
  },
  "minify": false
}
```

> jsc.target 与 env.targets 同时存在时以后者为准，二者混用会让目标范围难以判断，配置中只保留一处。

**速记**：.swcrc 分 jsc、env、module 三块，语法、目标与模块格式各归其位。



#### SWC 与 Babel 的差异

**SWC 与 Babel 的差异**：集中在实现语言、插件生态与配置形式上，能力覆盖接近但不完全重合。

- 实现语言：Babel 用 JavaScript 编写，SWC 用 Rust 编写，后者在多核环境下吞吐更高。
- 插件生态：Babel 的插件与预设数量庞大且写法成熟；SWC 插件机制较新，可移植的自定义插件有限。
- 配置形式：Babel 用 JavaScript 配置便于动态计算；SWC 以 JSON 为主，逻辑表达受限。
- 垫片策略：两者都支持按目标范围与按使用情况注入垫片，字段名不同，语义相近。
- 迁移判断：未使用自定义 Babel 插件时通常可直接替换；依赖特定插件语义时需逐一验证。

```js
// webpack 中使用 swc-loader 替代 babel-loader
module.exports = {
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: "swc-loader",
          options: { jsc: { parser: { syntax: "typescript", tsx: true } } },
        },
      },
    ],
  },
};
```

> [!CAUTION]
> **注意内容**：项目若依赖某个自定义 Babel 插件或插件执行顺序，直接换成 SWC 会改变转换语义，迁移前需在测试环境比对产物行为。

**速记**：SWC 更快、Babel 插件更多；无自定义插件时可换，有依赖时需逐项验证。



### 三者定位对比

**定位对比**：是把 Rollup、esbuild 与 SWC 放在同一条构建链路上，按「打包／转译」这一主维度划分职责。

本模块从能力、性能与生态三个角度给出区分依据，避免把转译器当打包器使用。

#### 三者能力对比

三者在构建链上分属不同环节，按打包与转译两类职责逐项对照。

- Rollup：打包器，输入以 ESM 为主，产出扁平干净的多格式产物，摇树与代码分割能力强。
- esbuild：打包器加转译器，内置打包、转译、压缩与代码分割，速度极快但配置面窄。
- SWC：转译器，负责语法降级与压缩，不解析依赖图，不产出打包产物。
- 交集与差集：esbuild 同时覆盖 Rollup 与 SWC 的部分能力，但不提供 Rollup 那样的插件深度与产物控制。
- 组合关系：三者不是互斥选项，常见做法是 SWC 或 esbuild 负责转译、Rollup 负责打包。

```bash
# 同一份源码，三种工具的典型用法
npx rollup -c                                       # 打包并产出多格式产物
npx esbuild src/index.ts --bundle --outfile=dist/index.js   # 打包
npx swc src -d dist                                 # 仅转译，不打包
```

> 判断工具归属的最快方式：看它是否解析 import 依赖图，解析并合并的是打包器，只改写单个文件的是转译器。

**速记**：Rollup 与 esbuild 是打包器，SWC 是转译器，esbuild 兼有两类能力但深度较浅。



#### 性能与产物差异

**性能与产物差异**：是选择工具时的第二组依据，速度与产物质量往往不可兼得。

- 转译速度：esbuild 与 SWC 通常显著快于 Babel，适合开发期与大规模代码库。
- 打包速度：esbuild 快于 Rollup，后者在大型项目上更依赖插件与缓存优化。
- 产物可读性：Rollup 产物最接近手写代码，esbuild 次之，压缩后的差异会缩小。
- 摇树效果：Rollup 的静态分析最彻底，对库产物体积的控制更精细。
- 缓存与增量：Rollup 与 esbuild 都提供监听模式，esbuild 的重建延迟更低。

```js
// Vite 的默认组合即体现了这种分工：开发期预构建用 esbuild，生产构建用 Rollup
export default {
  build: {
    target: "es2019",
    minify: "esbuild",
  },
};
```

> 性能数字与项目规模强相关，选型应以本仓库的实际基准测试为准，而不是照搬第三方对比图。

**速记**：esbuild 与 SWC 赢在速度，Rollup 赢在产物质量与摇树深度。



#### 生态与插件机制

**生态与插件机制**：决定工具能否覆盖项目的特殊需求，是长期维护成本的主要来源。

- Rollup 生态：插件接口稳定，官方与社区插件覆盖别名、虚拟模块、压缩与类型处理等常见需求。
- esbuild 生态：插件接口轻量，只提供解析与加载两个主导钩子，复杂转换需自行拼装。
- SWC 生态：以配置驱动为主，自定义转换能力弱于 Babel，遇到特殊语法时可能需要回退。
- Babel 的存量优势：语法提案与框架定制的插件最齐全，短时间内仍难以完全替代。
- 组合策略：用 esbuild 或 SWC 处理通用转译，把必须依赖 Babel 插件的少数文件单独交给 Babel。

```js
// 只让少数文件走 Babel，其余走 esbuild 的思路体现在插件过滤上
const babelOnlyPlugin = {
  name: "babel-only",
  setup(build) {
    build.onLoad({ filter: /src[\\/]legacy[\\/].*\.js$/ }, async (args) => {
      const { code } = await import("fs").then((fs) => fs.promises.readFile(args.path, "utf8"));
      const babel = await import("@babel/core");
      const result = await babel.transformAsync(code, { presets: ["@babel/preset-env"] });
      return { contents: result.code, loader: "js" };
    });
  },
};
```

> 特殊语法需求集中在少数文件时，用工具过滤把这部分单独交给 Babel，其余代码享受新工具的速度，避免整体回退。

**速记**：Rollup 插件生态最成熟，esbuild 插件最轻，SWC 靠配置，Babel 存量插件仍是兜底。



### 选型与组合方式

**选型**：是按项目类型与团队约束在三种工具及其组合之间做决定，先定场景再定工具，最后定组合。

本模块给出库开发、应用开发与迁移三条路径的决策依据。

#### 库开发的选型

**库开发的选型**：以产物质量与多格式发布为第一优先，典型答案是 Rollup。

- 默认选择：Rollup 产出干净且可摇树的产物，配合 external 排除同伴依赖。
- 快速替代：esbuild 适合追求构建速度且不依赖复杂插件的库。
- 类型声明：无论选谁，声明文件都由 tsc 单独生成，构建器不负责。
- 多格式：同时产出 ESM 与 CommonJS，并在清单中用 exports 字段声明条件入口。
- 体积校验：发布前用工具检查产物大小与是否含重复依赖。

```json
{
  "scripts": {
    "build": "rollup -c",
    "build:types": "tsc -p tsconfig.build.json --emitDeclarationOnly",
    "size": "npx size-limit"
  }
}
```

```bash
npm run build
npm run build:types
# dist/index.mjs 3.2 kB
```

#### 应用开发的选型

**应用开发的选型**：以开发体验与构建速度为先，通常不直接拼装工具，而是选择已组合好的上层方案。

- 推荐方案：Vite 已按上文分工组合好两端工具，直接选用即可。
- 单体应用：esbuild 可直接承担中小型应用的打包，配置简单、启动快。
- 框架集成：Next.js 等框架默认使用 SWC，无需单独配置转译链路。
- 自定义需求：需要深度控制产物结构时，可退回 Rollup 配置或编写插件。
- 类型检查：构建链路普遍不做类型检查，需在流水线中保留独立的类型检查步骤。

```js
// vite.config.ts 中按需切换压缩与目标环境
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    target: "es2019",
    minify: "esbuild",
    sourcemap: "hidden",
  },
  esbuild: {
    tsconfigRaw: { compilerOptions: { target: "es2019" } },
  },
});
```

> [!NOTE]
> **提醒内容**：应用构建链路中的转译器与打包器通常由框架封装，升级框架版本可能同时更换底层工具，配置前先确认当前实际使用的工具。

**速记**：应用选 Vite 这类组合方案，开发用 esbuild、生产用 Rollup，类型检查单独跑。



#### 组合与迁移

**组合与迁移**：是在既有工程中逐步引入新工具，用可验证的小步替换降低风险。

- 分步替换：先把压缩器从 Terser 换成 esbuild，再把转译器从 Babel 换成 SWC。
- 局部试点：选一个子应用或一个目录先行替换，比对产物体积与运行行为。
- 插件兜底：仅对依赖自定义 Babel 插件的文件保留 Babel，其余文件切换新工具。
- 双跑校验：迁移期同时运行新旧两套构建，对产物做体积与功能比对。
- 回退预案：保留原配置与锁定版本，确认稳定后再清理旧工具与依赖。

```bash
npm uninstall babel-loader @babel/core
npm install --save-dev swc-loader @swc/core
npx webpack --mode production
# 比对迁移前后的 assets 列表与 time 字段
```

```bash
# 用体积快照比对迁移前后的产物规模
npx size-limit --json > size-after.json
```

> [!WARNING]
> **警告内容**：一次性移除 Babel 及其插件会让依赖旧插件语义的代码在运行时出错，应保留旧配置一个发布周期再彻底清理。

**速记**：迁移按压缩器、转译器分步走，局部试点加双跑比对，并保留可回退的旧配置。
