## Gulp 的错误处理与任务健壮性

### 错误的传播方式

错误从管道（pipeline）内部向上传递，最终决定任务与进程的结局。本节说明流（stream）错误的默认行为、任务中断的后果与三种完成信号各自的错误路径。

#### 流中的错误默认行为

**流错误**：是管道中某个环节在处理文件时抛出的异常，默认行为是让整个流进入错误状态并停止后续文件的处理。

- 触发来源：编译语法错误、文件读取失败、插件参数不合法。
- 传播路径：错误沿管道向后传播，直到被监听器捕获，无人处理时成为未捕获异常。
- 中断范围：错误发生后，同一批次的其余文件不再进入后续环节。
- 观察方式：控制台错误堆栈的首行通常指向具体插件。

```js
const { src, dest } = require('gulp');
const compileSass = require('样式编译插件');

function buildStyle() {
  return src('src/styles/main.scss')
    .pipe(compileSass())
    .pipe(dest('dist/styles'));
}

exports.buildStyle = buildStyle;
```

> 源文件存在语法错误时，上面的任务会以流错误的形式中断，产物目录中不会出现该文件的输出。

**速记**：流错误默认让管道停止并把异常向上抛出，无人监听的错误会终止进程。



#### 任务中断与进程退出

**任务中断**：是任务在处理过程中因错误停止、不再执行后续动作的状态，Gulp 会据此把命令行退出码置为非零。

- 中断时点：错误发生时任务立即停止，尚未处理的文件全部被放弃。
- 残留产物：错误之前已经写出的文件保留在磁盘上，产物处于不一致状态。
- 退出码：任务失败让命令行进程以非零状态结束，便于外部脚本判断结果。
- 监听差异：监听模式下任务失败不会结束进程，监听继续等待下一次变更。

```bash
npx gulp buildStyle
# 出错后输出错误堆栈并以非零状态退出
echo $?
```

> [!IMPORTANT]
> **重要内容**：一次性构建失败后产物目录停留在中间状态，再次执行前应先清理，避免新旧文件混杂。

**速记**：任务出错即中断，已写出的文件保留，进程退出码随之变为非零。



#### 异步任务的错误传递

**异步完成信号**：是任务用来告知 Gulp 执行结果的方式，返回流、返回 Promise 与接收回调三种写法各对应一条错误传递路径。

- 返回流：流的错误事件会转化为任务失败，这是最常见的形式。
- 返回 Promise：Promise 被拒绝即任务失败，错误需要继续抛出而不是被吞掉。
- 回调写法：回调的第一个参数传入错误对象即失败，传空值表示成功。
- 混用风险：回调写法中同时返回流会让完成信号触发两次，行为难以预期。

```js
const { src, dest } = require('gulp');
const compileScript = require('脚本转译插件');

function buildScriptByCallback(done) {
  const stream = src('src/scripts/**/*.ts').pipe(compileScript()).pipe(dest('dist/scripts'));
  stream.on('error', done);
  stream.on('end', done);
}

exports.buildScriptByCallback = buildScriptByCallback;
```

> 既不返回流也不调用回调时任务会立即结束，错误不会被上报，这是任务静默失败的主要原因。

**速记**：流、Promise、回调各对应一条错误传递路径，混用会导致重复完成。



### 错误拦截与容错

容错的目标是让单个文件的失败不影响其余文件，同时保证失败信息被完整报告。本节说明拦截插件、拦截点的位置与容错的适用边界。

#### 用于拦截流错误的插件

**错误拦截插件**：是监听管道 error 事件、阻止错误继续向后传播的插件，接入后流不会因单个文件的失败而停止。

- 作用范围：只覆盖它之后的管道，放在管道开头会漏掉后续环节的错误。
- 两种策略：记录错误后继续处理其余文件，或立即终止并输出完整错误。
- 与日志的关系：拦截只负责避免中断，错误内容仍需自行输出到控制台。
- 顺序要求：应紧跟在容易出错的编译与压缩环节之后。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');

function buildStyleTolerant() {
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(catchStreamError()).pipe(dest('dist/styles'));
}

exports.buildStyleTolerant = buildStyleTolerant;
```

> 拦截插件的价值在监听场景最明显：一个语法错误不应让整条开发流水线停下。

**速记**：拦截插件接在易错环节之后，用记录代替中断以保住其余文件的处理。



#### 在管道中插入错误拦截点

**拦截点**：是管道中用于接管错误的位置，位置决定哪些环节的错误会被拦下、哪些仍会中断任务。

- 前置拦截：编译之前插入，只能拦下读取阶段的错误。
- 后置拦截：编译之后插入，可覆盖编译与压缩环节的错误。
- 多点拦截：不同环节分别插入可获得更具体的错误上下文。
- 判断方法：按管道顺序列出可能出错的环节，把拦截点放在其后一位。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');
const minifyStyle = require('样式压缩插件');

function buildStyleGuarded() {
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(minifyStyle()).pipe(catchStreamError())
    .pipe(dest('dist/styles'));
}

exports.buildStyleGuarded = buildStyleGuarded;
```

> 拦截点的位置比拦截插件本身更关键，放在管道末尾等于放弃了中间环节的容错。

**速记**：拦截点应位于全部易错环节之后，按环节清单逐位核对即可确定位置。



#### 报错后继续执行的取舍

**容错执行**：是拦截错误后继续处理剩余文件的做法，代价是产物可能缺少出错文件对应的结果。

- 适用场景：监听模式下的样式与脚本编译，单个文件出错不应阻塞其余文件。
- 不适用场景：一次性生产构建，缺少任一文件都会让产物不可用。
- 一致性要求：容错时必须在流结束时汇总错误并明确提示。
- 产物核对：容错构建结束后比对产物与源文件清单，确认缺失条目。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileScript = require('脚本转译插件');
const failureList = [];

function buildScriptTolerant() {
  const catcher = catchStreamError(function collectFailure(error) {
    failureList.push(error.message);
  });
  return src('src/scripts/**/*.ts').pipe(compileScript()).pipe(catcher).pipe(dest('dist/scripts'));
}

exports.buildScriptTolerant = buildScriptTolerant;
```

> [!CAUTION]
> **注意内容**：容错构建会正常结束且退出码为零，缺失的产物不会被自动发现，必须在流结束时显式汇总失败。

**速记**：容错适用于监听场景，一次性构建必须让错误中断任务，否则缺失产物会被忽略。



### 任务失败与退出码

Gulp 依据任务的完成结果设置命令行退出码，这一步决定外部脚本能否感知失败。本节说明失败如何表达、退出码如何产生，以及失败时的清理。

#### 回调与 Promise 的失败表达

**失败表达**：是通过完成信号把错误交给 Gulp 的方式，回调传入错误对象或 Promise 被拒绝都表示任务失败。

- 回调写法：回调的第一个参数为错误对象即失败，为空值或省略即成功。
- Promise 写法：被拒绝的 Promise 让任务失败，成功时的解决值不参与后续逻辑。
- 同步抛错：任务体内的同步异常同样被 Gulp 捕获并记为失败。
- 检查方式：失败后查看命令行输出与退出码，确认任务确实被标记为失败。

```js
const { src, dest } = require('gulp');
const compileScript = require('脚本转译插件');

function buildScriptByPromise() {
  return new Promise(function runBuild(resolve, reject) {
    src('src/scripts/**/*.ts').pipe(compileScript()).pipe(dest('dist/scripts'))
      .on('error', reject)
      .on('end', resolve);
  });
}

exports.buildScriptByPromise = buildScriptByPromise;
```

> 完成信号只有一次机会，写成就不能再用回调，否则失败信息会被后来的成功信号覆盖。

**速记**：回调传错误、Promise 被拒绝、同步抛错都表示失败，混用会让结果不可信。



#### 退出码的产生与查看

**退出码**：是命令行进程结束时返回给调用方的整数，Gulp 在存在失败任务时以非零状态结束。

- 产生规则：任一任务失败即置非零，全部任务成功则为零。
- 与容错的关系：错误被拦截后任务视为成功，退出码仍为零。
- 查看方式：命令行输出之后读取状态，或在外部脚本中直接判断退出码。
- 常见误区：仅依据控制台是否出现错误文字判断结果，会漏掉被容错的失败。

```bash
npx gulp build
echo $?
# 0 表示全部任务成功，非 0 表示存在失败任务
npx gulp build && echo "构建通过"
# 退出码非零时，后续命令不会执行
```

> [!NOTE]
> **提醒内容**：被拦截的错误不会改变退出码，仅凭退出码判断构建结果前，需要确认流水线中没有启用容错。

**速记**：任务失败即非零退出，容错过的错误不影响退出码，判断结果需结合两者。



#### 失败时的清理动作

**失败清理**：是任务在出错路径上执行的收尾动作，用于避免中间状态的文件残留到下一次构建。

- 清理对象：本次任务已写出的半成品与临时文件。
- 执行方式：在错误回调中删除临时目录，或把中间产物写到独立目录。
- 更稳做法：先写入临时目录，全部成功后一次性移动到输出目录。
- 与编排的关系：多任务组合时的失败处理见本主题第 52 篇。

```js
const fs = require('fs');
const { src, dest } = require('gulp');
const compileScript = require('脚本转译插件');

function buildScriptAtomically() {
  return src('src/scripts/**/*.ts').pipe(compileScript()).pipe(dest('dist/scripts.tmp'))
    .on('error', function removeTemporary() {
      fs.rmSync('dist/scripts.tmp', { recursive: true, force: true });
    });
}

exports.buildScriptAtomically = buildScriptAtomically;
```

> 先写临时目录再整体移动，可以把失败时的清理成本降到一次目录删除。

**速记**：失败清理针对半成品，写入临时目录再整体移动是最省事的做法。



### 日志与提示

日志决定失败现场是否可读。本节说明日志的输出位置、分级与前缀约定，以及错误上下文应当包含哪几项信息。

#### 日志在任务中的位置

**任务日志**：是任务在执行过程中向控制台输出的信息，用于反映当前处理进度与每个环节的结果。

- 输出时机：任务开始、单个环节完成、整个任务结束三处各有用途。
- 统计来源：需要输出的文件数量与名称来自流中的文件对象。
- 与 Gulp 输出的区别：Gulp 自身只报告任务起止，不反映处理细节。
- 输出量控制：监听场景下应减少逐文件输出，只保留汇总信息。

```js
const { src, dest } = require('gulp');
const compileSass = require('样式编译插件');

function buildStyleWithLog() {
  let fileCount = 0;
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(dest('dist/styles'))
    .on('data', function countFile() {
      fileCount += 1;
    })
    .on('end', function reportSummary() {
      console.log('处理文件数：' + fileCount);
    });
}

exports.buildStyleWithLog = buildStyleWithLog;
```

> 在流上绑定数据事件只观察文件对象，不改变流的内容，是统计数量的常用手段。

**速记**：日志应给出任务起止与处理数量，监听场景下只保留汇总以免刷屏。



#### 输出可读性与分级

**日志分级**：是按信息的性质区分普通信息、警告与错误并采用不同输出形式的做法。

- 三类分级：进度与统计用普通输出，可恢复的问题用警告输出，阻断性问题用错误输出。
- 前缀约定：每条日志带上任务名或文件路径，便于在多任务并行时辨认来源。
- 噪音控制：调试信息通过开关控制，避免在正式构建中输出。
- 去重：插件自身也会输出日志，含义重复的信息应裁剪。

```js
function makeReporter(taskName) {
  const verboseEnabled = process.argv.includes('--verbose');
  return function reportStep(message) {
    if (verboseEnabled) {
      console.log('[' + taskName + '] ' + message);
    }
  };
}

exports.makeReporter = makeReporter;
```

> [!TIP]
> **建议内容**：日志前缀统一写入任务名，多任务并行时能直接看出信息出自哪条任务。

**速记**：日志分信息、警告、错误三级，统一前缀与控制开关兼顾可读性与噪音。



#### 错误上下文的最小信息

**错误上下文**：是错误输出中定位问题所必需的最少信息，包括出错文件、来源环节与原始错误。

- 必需三要素：文件路径、来源环节与原始错误信息。
- 来源环节：标明错误来自编译、压缩还是写出，可把排查范围缩小到单个插件。
- 原始错误：保留底层错误信息，避免只输出自定义提示而丢失细节。
- 避免淹没：批量失败时按文件汇总，不要逐条刷屏。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');

function buildStyleWithContext() {
  const catcher = catchStreamError(function reportWithContext(error) {
    console.error('样式编译失败，来源环节：' + (error.plugin || '未知'));
    console.error(error.message);
  });
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(catcher).pipe(dest('dist/styles'));
}

exports.buildStyleWithContext = buildStyleWithContext;
```

> 最容易被忽略的是来源环节，加上环节名往往能把排查范围缩小到单个插件。

**速记**：错误输出至少给文件路径、来源环节与原始错误三样，批量失败按文件汇总。



### 健壮任务的写法

健壮的任务把错误处理收敛到固定位置，让新增任务自动获得同样的容错与日志行为。本节说明任务工厂、前置检查与失败范围的隔离。

#### 任务工厂与统一错误处理

**任务工厂**：是接收配置并返回任务函数的函数，用于把错误拦截与日志集中在一处，避免每个任务重复编写。

- 结构：外层函数接收配置，内层返回符合 Gulp 约定的任务函数。
- 统一处理：错误拦截与日志在工厂内部接入，每个任务自动获得相同行为。
- 参数差异：不同任务的差别通过配置传入，而不是复制整段管道。
- 维护收益：修改容错策略只需改工厂一处。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');

function makeStreamTask(taskName, pattern, outputDir, makeTransform) {
  return function runStreamTask() {
    const catcher = catchStreamError(function reportFailure(error) {
      console.error(taskName + ' 失败：' + (error.plugin || '未知环节'));
    });
    return src(pattern).pipe(makeTransform()).pipe(catcher).pipe(dest(outputDir));
  };
}

exports.buildStyle = makeStreamTask('样式构建', 'src/styles/**/*.scss', 'dist/styles', compileSass);
```

> 工厂把容错与日志从每个任务里抽走，任务只剩下读取、转换与写出三件事。

**速记**：任务工厂把错误拦截与日志收敛到一处，任务本身只保留资源处理逻辑。



#### 参数校验与前置检查

**前置检查**：是任务开始处理文件之前对输入条件做的判断，用于把可预期的配置错误提前暴露。

- 检查对象：源目录是否存在、必填配置是否传入、输出目录是否落在源码目录之内。
- 失败方式：校验不通过时直接以错误对象结束任务，不进入后续管道。
- 提示要求：错误信息应指出缺少哪一项以及如何补上。
- 时机选择：检查放在任务开头，代价极低却能省去大量无效处理。

```js
const fs = require('fs');
const { src, dest } = require('gulp');
const compileSass = require('样式编译插件');

function buildStyleChecked() {
  if (!fs.existsSync('src/styles')) {
    return Promise.reject(new Error('源目录 src/styles 不存在，请确认项目结构'));
  }
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(dest('dist/styles'));
}

exports.buildStyleChecked = buildStyleChecked;
```

> [!IMPORTANT]
> **重要内容**：输出目录与源码目录重叠会形成写回循环，必须在任务开头以校验拦截，不能等到监听阶段才发现。

**速记**：任务开头校验源目录、必填配置与输出目录位置，失败即以错误提前结束。



#### 失败范围的隔离

**失败隔离**：是让单个任务或单个文件的失败不影响其余处理单元的做法，通过限定错误拦截的范围实现。

- 文件级隔离：在单个任务内部拦截，一个文件失败不波及其他文件。
- 任务级隔离：组合执行时让各任务的错误各自承担，组合语义见第 52 篇。
- 范围代价：拦截范围越大，越难判断哪些产物是可靠的。
- 记录要求：被隔离的失败必须汇总输出，隔离不等于忽略。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');

const failureSummary = [];
function collectFailure(error) {
  failureSummary.push(error.message);
}

function buildStyleIsolated() {
  return src('src/styles/**/*.scss').pipe(compileSass()).pipe(catchStreamError(collectFailure)).pipe(dest('dist/styles'));
}

exports.buildStyleIsolated = buildStyleIsolated;
```

> 隔离的边界即拦截点的位置，边界越小越容易判断哪些产物可以信任。

**速记**：失败隔离靠限定拦截范围实现，隔离后的失败仍要汇总输出而不能静默。
