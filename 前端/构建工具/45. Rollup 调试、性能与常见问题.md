## Rollup 调试、性能与常见问题

Rollup 的问题多数不表现为构建失败，而是产物与预期不符：多打了一份依赖、少了一个导出、某个模块没被摇掉。本篇只写 Rollup 自身的核对与排查手段；构建性能的通用清单见本主题第 15 篇 构建性能优化与缓存策略，报错排查的通用方法见本主题第 16 篇 构建问题排查与常见报错，树摇机制的原理见本主题第 42 篇 Rollup 的 Tree Shaking 与副作用控制。

### 构建产物核对

产物核对是排查的起点，先确认产物里有什么，再讨论为什么。本节按文件与导出项、内容阅读、未预期代码三步展开。

#### 产物文件与导出项核对

**产物核对**：是把构建产出的文件清单与导出项同预期逐条比对的检查动作，用于确认构建结果与配置意图一致。

- 文件清单：确认产物目录中的文件数量、命名与格式和配置里的 output 一致。
- 导出项：逐个列出产物的导出名，确认与外层约定一致、没有多出内部符号。
- 空产物排查：产物只有几十字节时，通常说明入口指向了没有导出的文件。
- 残留文件：构建前未清理目录会留下历史文件，导致清单核对出现偏差。
- 目录模式：保留模块结构输出时，核对条目应改为逐目录比对而不是只比入口。

```bash
npx rollup -c
ls -la dist
# index.mjs  index.cjs  index.mjs.map
node --input-type=module -e "import('./dist/index.mjs').then((m) => console.log(Object.keys(m)))"
# 列出实际导出项，与约定逐条比对
```

> 导出项多出内部符号，往往是本该拆成独立模块的工具函数被写在了入口文件里。

**速记**：先核对产物文件清单，再核对导出项，两者都与配置意图一致才算构建正确。



#### 产物内容的阅读方法

**产物阅读**：是直接打开构建结果、按结构顺序观察模块如何被合并与改写的检查方式。

- 阅读顺序：先看头部注释与导入语句，再看模块体的排列顺序，最后看导出收尾。
- 导入语句：保留下来的导入都是外部化声明命中的依赖，可据此核对外部化清单。
- 包装痕迹：出现模块包装函数说明该依赖未被外置或未成功转换为 ESM。
- 顺序信息：模块体的顺序反映依赖图顺序，循环依赖会让顺序变得难以阅读。
- 来源映射：开启 sourcemap 后可在浏览器中定位产物代码对应的源码位置。

```bash
head -n 40 dist/index.mjs
# 观察头部注释与 import 语句，确认外部依赖是否按预期保留
npx rollup -c --sourcemap
# 产物旁生成映射文件，调试时可按源码位置断点
```

> 阅读产物比读配置更可靠：配置只表达意图，产物才是使用方真正拿到的东西。

**速记**：按头部注释、导入语句、模块顺序与导出收尾的顺序读产物，导入语句可反查外部化清单。



#### 未预期代码的定位

**未预期代码定位**：是在产物中发现不该出现的实现后，反查它由哪个模块或依赖引入的过程。

- 特征字符串：选取该实现中独有的一段文本，在产物与源码中双向搜索。
- 模块边界：产物中相邻的模块体通常来自同一条导入链，可据此缩小范围。
- 依赖来源：用依赖树查询确认该实现属于本包源码还是某个依赖。
- 外部化核对：若来自依赖，先检查外部化清单是否漏写了该包或其子路径。
- 副作用核对：若来自本包，检查对应模块是否被入口以带副作用的语句引入。

```bash
grep -rn "formatCurrency" dist/index.mjs
# 命中位置的前后上下文即为引入它的模块
npm ls date-fns
# 确认该实现来自哪个依赖及其版本
```

> [!TIP]
> **建议内容**：给每个待排查的实现取一段足够独特的字符串再搜索，用通用的变量名搜索会命中大量无关代码。

**速记**：用特征字符串双向搜索，先判断实现来自本包还是依赖，再回到外部化与副作用两项配置。



### 常见报错与成因

Rollup 的报错信息通常指明模块标识与出错阶段，按阶段分类能更快定位。本节列出三类高频报错。

#### 模块解析失败

**模块解析失败**：是 Rollup 未能把某个导入标识定位到文件时的报错，表现为找不到模块或无法解析导入。

- 原因一：引用了依赖包，但未接入解析插件，Rollup 默认只解析相对路径。
- 原因二：引用了 CommonJS 包，未接入转换插件，导入形式无法被识别。
- 原因三：别名只在编译器配置里声明，构建配置中没有对应的解析规则。
- 原因四：导入路径缺少扩展名，而该扩展名不在解析插件的候选列表内。
- 定位方式：按报错给出的模块标识判断它属于源码路径、别名还是依赖包。

```bash
npx rollup -c
# [!] Error: Could not resolve "./utils/format" from src/index.js
# 报错给出的标识即待解析的模块，先判断它属于哪一类
```

> [!IMPORTANT]
> **重要内容**：解析插件与转换插件是两类不同能力，只接入其中一个会在遇到另一类模块时继续报错，配置时两者都要检查。

**速记**：解析失败先判断标识属于相对路径、别名还是依赖包，再补对应的解析或转换插件。



#### 外部化配置错误

**外部化错误**：是外部化清单与实际导入不匹配导致的报错或产物异常，常见漏写子路径或误把自身源码当作依赖。

- 漏写子路径：清单里只写包名，代码引用的是该包的深层路径，匹配不到即被打入产物。
- 误写自身包：把本包名写进外部化清单，会让入口对自己的导入无法解析。
- 过度外部化：把需要随包分发的内部依赖也外置，使用方安装后无法解析。
- 与全局名配对：声明外部化却未给出全局名映射时，全局格式产物会取到未定义值。
- 定位方式：在产物中搜索被外置依赖的特征字符串，命中即说明外部化未生效。

```js
// rollup.config.mjs 用函数形式覆盖包名与全部子路径
import { defineConfig } from "rollup";

const externalPackages = ["vue", "@my-scope/shared"];

export default defineConfig({
  input: "src/index.js",
  external: (id) => externalPackages.some((name) => id === name || id.startsWith(`${name}/`)),
  output: [{ file: "dist/index.mjs", format: "es" }],
});
```

> 外部化清单的写法要覆盖子路径，用等值判断匹配包名时，深层导入必然会漏。

**速记**：外部化错误集中在漏写子路径、误写自身与过度外置三类，用函数形式按前缀匹配最稳。



#### 格式与导出冲突

**格式冲突**：是配置的产物格式与代码的导出写法不匹配时的报错或行为偏差。

- 混合导出：同时存在具名导出与默认导出时，部分格式要求显式声明导出模式。
- 全局名缺失：产出全局格式时未给出 name，构建直接报错。
- 顶层 await：目标格式不支持顶层 await 时无法产出对应格式。
- 动态导入：不支持的格式下动态导入无法拆分，会被内联或直接报错。
- 定位方式：报错中出现的配置字段名即冲突项，按字段名回到 output 配置核对。

```json
{
  "output": {
    "file": "dist/index.cjs",
    "format": "cjs",
    "exports": "named"
  }
}
```

> 产物格式是给使用方看的接口，改格式等同于改契约，出现冲突时优先调整代码导出写法而不是格式。

**速记**：格式冲突看混合导出、全局名、顶层 await 与动态导入四点，报错字段名即定位线索。



### 构建性能优化

Rollup 的速度瓶颈多数来自插件与解析范围。本节按插件开销、缓存与构建范围三处展开。

#### 插件开销的定位

**插件开销定位**：是识别哪个插件在转换阶段消耗了主要构建时间的过程。

- 逐段计时：在插件钩子内记录时间戳并输出差值，定位耗时集中在哪个阶段。
- 按名称过滤：构建日志中的插件名称可用来区分不同插件的输出与耗时。
- 常见热点：语法转换与压缩插件通常是耗时大头，解析插件次之。
- 转换范围：转换钩子对所有文件执行时，依赖目录内的文件也会被逐个处理。
- 处理方式：用文件路径判断提前返回，让转换只发生在源码目录。

```js
// 一个带计时的转换插件，用来定位耗时集中在哪个模块
export default function timedTransformPlugin() {
  return {
    name: "timed-transform",
    transform(code, id) {
      if (!id.includes("/src/")) return null;
      const startedAt = Date.now();
      const next = code.replace(/\bDEBUG\b/g, "false");
      this.info(`transform ${id} ${Date.now() - startedAt}ms`);
      return { code: next, map: null };
    },
  };
}
```

> 转换钩子里尽早按路径判断并返回，是降低插件开销最直接的手段，比事后压缩代码更有效。

**速记**：用钩子内计时与插件名过滤定位热点，转换钩子要按路径提前返回。



#### 缓存与监听模式

**监听模式（watch）**：是 Rollup 常驻进程、只重建受影响模块的构建方式，与一次性构建的耗时结构不同。

- 增量基础：监听模式下 Rollup 保留已解析的模块信息，重建只处理变更链。
- 缓存对象：构建缓存可在进程间传递，用于跨次构建复用解析与转换结果。
- 监听范围：默认跟踪依赖图内的文件，配置范围过宽会引入无关重建。
- 清缓存时机：改动构建配置、解析规则或插件选项后应清缓存，避免旧结果被复用。
- 常见假象：只改了被外部化的依赖时不会触发重建，因为该文件不在依赖图内。

```js
// rollup.config.mjs 显式给监听模式设定范围与清缓存条件
import { defineConfig } from "rollup";

export default defineConfig({
  input: "src/index.js",
  output: { file: "dist/index.mjs", format: "es" },
  watch: {
    include: "src/**",
    exclude: "node_modules/**",
    clearScreen: false,
  },
});
```

```bash
npx rollup -c -w
# 常驻监听，改动后只重建受影响的模块
```

> 缓存复用带来的问题常表现为改动不生效，此时先清缓存再判断是配置问题还是缓存问题。

**速记**：监听模式靠保留模块信息做增量重建，改配置后要清缓存，注意外部化文件不在依赖图内。



#### 构建范围的收窄

**构建范围收窄**：是通过配置减少参与解析与转换的文件数量，从而直接缩短构建时间。

- 入口数量：非必要的入口不应纳入同一次构建，多入口会放大解析与分包开销。
- 外部化：把不需要打包的依赖外置，省去对整棵依赖树的解析与转换。
- 产物结构：需要保留模块结构时，产物文件数会明显增加，写入阶段耗时随之上升。
- 压缩取舍：库产物通常不压缩，压缩阶段的开销可以直接省掉。
- 声明产出：类型声明与打包是两条链路，可并行执行而不必串在同一进程里。

```json
{
  "scripts": {
    "build:js": "rollup -c",
    "build:types": "tsc -p tsconfig.build.json --emitDeclarationOnly",
    "build": "npm run build:js && npm run build:types"
  }
}
```

> [!TIP]
> **建议内容**：把声明产出与打包放在两个进程串行执行，可让两条链路各自利用满核而互不争抢，构建总时长通常短于单进程串联。

**速记**：收窄入口、外部化依赖、按需压缩与拆分声明链路，是缩短 Rollup 构建时间的四步。



### 产物体积问题

体积异常多数有明确成因，按「多打了什么」分类排查比逐行读产物高效。本节列出三类成因。

#### 依赖被整体打入

**依赖整体打入**：是外部化清单未命中导致依赖的完整实现被并入产物的情形。

- 表现：产物体积显著大于预期，并出现大量与业务无关的实现代码。
- 成因：外部化声明漏写依赖名或漏写子路径，或是用导入语句绕过了配置规则。
- 检查：在产物中搜索该依赖的特征字符串，命中条数能反映被打入的范围。
- 修复：补齐外部化清单，并把该依赖同时写进同伴依赖声明。
- 校验：修复后比对产物体积与依赖树版本数量，两项都应下降。

```bash
grep -c "date-fns" dist/index.mjs
# 条数大于 0 说明该依赖被打入，回到外部化清单核对
npx rollup -c
# 修复后体积变化即为被打入部分的规模
```

> 依赖被打入不一定立刻报错，它会延迟到使用方出现两份实例时才暴露，因此需要在发布前主动核对。

**速记**：在产物里搜依赖特征字符串即可判断是否被打入，修复靠补齐外部化清单与同伴依赖。



#### 树摇未生效

**树摇未生效**：是未被使用的导出仍然留在产物中的情形，成因分本包代码与依赖包两类。

- 前提缺失：源码被转成 CommonJS 后不再具备静态结构，摇树无法进行。
- 标注过宽：包级副作用声明过于保守，打包器不敢裁掉任何模块。
- 顶层副作用：模块顶层执行了有实际影响的语句，该模块整体必须保留。
- 依赖形态：依赖只提供 CommonJS 产物时，本包的摇树无法延伸到其中。
- 检查方式：在产物中搜索未被引入的导出名，命中即说明该导出未被摇掉。

```js
// 把有副作用的注册语句收进函数，只在显式调用时执行
export function registerFormat(name, handler) {
  formatRegistry.set(name, handler);
}

// 模块顶层不再执行注册，未使用的模块可以被整体裁掉
```

```json
{
  "sideEffects": ["./src/register-all.js"]
}
```

> 副作用标注要尽量精确到文件，整包标为无副作用会让真正带副作用的模块被裁掉。

**速记**：摇树不生效先查模块格式与副作用标注，再用「未被引入的导出名是否出现在产物中」验证。



#### 辅助代码与重复代码

**辅助代码**：是转译器为支持新语法自动注入的运行时片段；**重复代码**：是同一模块被多条路径引入后被多次写入的情形。

- 辅助代码成因：转译器逐文件处理且未开启共享辅助，每个文件各带一份实现。
- 处理方式：改用提供共享辅助注入的配置，把辅助集中到一处。
- 重复代码成因：格式与目录结构叠加导致同一模块在多份产物中各出现一次。
- 多格式代价：ESM 与 CJS 两份产物天然各含一份实现，这属于预期而非缺陷。
- 检查方式：按模块名统计产物中的出现次数，多于一次即需要定位引入路径。

```bash
grep -o "classCallCheck" dist/index.mjs | wc -l
# 计数明显偏高说明辅助代码未共享
grep -c "formatCurrency" dist/index.cjs dist/index.mjs
# 两份产物各命中一次属于多格式的正常结果
```

> [!CAUTION]
> **注意内容**：辅助代码与会话无关的重复逻辑会随入口数量成倍增长，多入口库尤其要在发布前统计一次出现次数。

**速记**：辅助代码靠共享注入收敛，重复代码靠按模块名计数定位，多格式的两份实现属预期。



### 排查工具

工具的价值在于把猜测变成可核对的数字。本节按产物构成分析、日志与配置输出、最小复现三步收尾。

#### 产物构成分析

**产物构成分析**：是把产物按模块与依赖拆解、统计各自占比的做法，用于判断体积由谁贡献。

- 统计维度：按模块、按依赖、按产物的粒度分别统计占比。
- 接入方式：分析插件加入插件数组，构建后输出各模块的体积明细。
- 使用时机：先定位体积贡献最大的模块，再决定外部化还是改写实现。
- 对照基线：每次发布记录一次体积快照，回归时与基线对比。
- 结果判读：分析结果包含注释与映射时，占比会偏高，应按同一口径比较。

```js
// rollup.config.mjs 接入体积分析插件，具体包名与选项按插件文档填写
import { defineConfig } from "rollup";
import visualizer from "rollup-plugin-visualizer";

export default defineConfig({
  input: "src/index.js",
  output: { file: "dist/index.mjs", format: "es" },
  plugins: [visualizer({ filename: "stats.html", gzipSize: true })],
});
```

> 体积分析的意义在于确定优先级，占比最大的模块才是下一步优化的目标。

**速记**：用分析插件按模块与依赖统计占比，定位最大贡献者后再决定外部化还是改写实现。



#### 构建日志与配置输出

**构建日志**：是 Rollup 在构建过程中输出的模块解析、警告与耗时信息，是排查的第一手材料。

- 解析记录：日志会列出每个模块的来源与处理方式，可用于核对解析是否符合预期。
- 警告信息：未解析的导入与循环依赖会以警告形式输出，不当成错误就容易被忽略。
- 日志级别：用日志级别参数提高输出详细程度，定位后再恢复到默认级别。
- 配置输出：打印最终生效的配置，可确认导出的数组与字段与预期一致。
- 落盘保存：把构建输出重定向到文件，便于在长日志中检索关键字。

```bash
npx rollup -c --logLevel debug > build.log 2>&1
```

#### 最小复现的构造方法

**最小复现**：是把问题压缩到单个入口、单个依赖、最少插件的最小工程，用于隔离成因。

- 截断入口：从复现入口开始删减导出与调用，直到问题消失，最后删掉的那部分即成因所在。
- 逐个插件：一次只保留一个插件，二分法排除与插件有关的成因。
- 固定依赖：锁定依赖版本与产物格式，避免变量过多导致结论不可信。
- 保留条件：记录解析出的依赖版本、目标格式与外部化清单三项关键条件。
- 收尾方式：确认成因后把结论写进项目说明，避免同类问题重复排查。

```bash
mkdir -p repro/src
# 项目内只留一个入口与一个依赖，配置从零写起
npx rollup -c
# 逐步加回原始配置的字段，直到症状重现
```

> [!NOTE]
> **提醒内容**：最小复现要连依赖版本一起固定，同一份源码在不同版本下表现不同，是排查中最常见的干扰因素。

**速记**：用逐步删减与逐插件二分构造最小复现，并固定依赖版本与产物格式。
