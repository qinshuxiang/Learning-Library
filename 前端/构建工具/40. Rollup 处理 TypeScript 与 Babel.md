## Rollup 处理 TypeScript 与 Babel

### TypeScript 插件的接入

Rollup 只理解 JavaScript 与 ES Module，TypeScript 源码必须先转成 JavaScript 才能进入模块图。本节说明编译插件如何接线、编译选项从哪里来、以及编译范围如何划定。

#### 官方编译插件的安装与接线

**官方编译插件**：是 Rollup 官方维护的 @rollup/plugin-typescript，调用 TypeScript 编译器把 TypeScript 源码转成 JavaScript，再把结果交回 Rollup 继续打包。

- 安装内容：rollup、typescript 与插件同装为开发依赖，插件与 TypeScript 的大版本需互相兼容。
- 接线位置：插件放入 plugins 数组，Rollup 在转换阶段逐模块调用它，转换结果留在内存中。
- 编译器来源：插件按模块解析规则查找 typescript 包，项目内安装的版本优先于全局版本。
- 调试开关：插件一般提供输出诊断信息的选项，构建报错时先打开它看清编译器给出的原始提示。
- 适用判断：需要 Rollup 参与转译并保留其静态分析能力时选这条路线。

```js
// rollup.config.mjs
import { defineConfig } from "rollup";
import typescript from "@rollup/plugin-typescript";

export default defineConfig({
  input: "src/index.ts",
  output: { dir: "dist", format: "es" },
  plugins: [typescript({ tsconfig: "./tsconfig.build.json" })],
});
```

> 插件选项以所用版本的官方文档为准，大版本之间选项名与默认值可能变化，升级时对照变更日志逐项核对。

**速记**：官方编译插件在内存中把 TypeScript 转成 JavaScript，转换结果直接进入 Rollup 的模块图。



#### 编译配置的来源与覆盖

**编译配置的来源**：是插件读取 tsconfig 文件得到的 compilerOptions，插件自身选项再对其中若干项做覆盖。

- 默认读取：插件默认在当前工作目录查找 tsconfig.json，目录不明确时应显式传入路径。
- 覆盖方式：插件选项里可直接写 compilerOptions 字段，逐项覆盖 tsconfig 中的同名值。
- 模块格式：module 必须保留 ESM 形态，否则 Rollup 收到 CommonJS 输出，摇树与代码分割同时失效。
- 输出开关：noEmit 需交由插件接管，emitDeclarationOnly 为真时只产出声明文件。
- 优先级：插件选项高于 tsconfig 本体，构建专用设置建议写入单独的 tsconfig 文件。

```js
typescript({
  tsconfig: "./tsconfig.build.json",
  compilerOptions: {
    module: "ESNext",
    target: "ES2019",
    declaration: false,
  },
})
```

> [!IMPORTANT]
> **重要内容**：构建专用配置应单独建一份 tsconfig 文件，直接改动编辑器使用的那份配置会让类型提示与构建同时变化，出问题时难以定位来源。

**速记**：编译选项来自 tsconfig，插件选项做局部覆盖，module 一项必须保持 ESM 形态。



#### 编译范围与插件顺序

**编译范围**：是编译插件实际处理的文件集合，由插件的 include 与 exclude 以及 Rollup 的模块图共同决定。

- 默认范围：插件只处理进入 Rollup 模块图的模块，未被任何入口引用的源码不参与编译。
- 显式收窄：include 与 exclude 按 glob 匹配，用于把检查文件与产物目录排除在外。
- 顺序原则：解析类插件负责给出真实文件路径，应排在转换类插件之前。
- 并存顺序：多个转换插件同时改写同一批文件时按语义先后排列，先做语法转换再做代码注入。
- 观察方式：临时输出被处理的文件列表，确认目标文件确实命中，而非插件静默失效。

```js
typescript({
  include: ["src/**/*.ts"],
  exclude: ["**/*.test.ts", "dist/**"],
})
```

> 插件未生效往往不报错，只表现为产物里仍是原始语法，遇到这种情形应先把被处理的文件列表打出来看。

**速记**：编译范围默认跟随模块图，解析插件先于转换插件，未命中时用文件列表确认。



### 类型声明文件的产出

声明文件是发布给使用方的类型信息，Rollup 本身不产出它，需要与 JavaScript 产物编排在一起。本节说明产出路线、目录对应与编排方式。

#### 声明文件的两条产出路线

**声明文件（declaration file）**：是以 d.ts 结尾、只含类型信息的文件，供使用方获得类型提示，不参与运行时执行。

- 路线一：由 TypeScript 编译器单独生成，命令上加 emitDeclarationOnly，只写声明不写 JavaScript。
- 路线二：由声明打包插件把多份声明合并成单个文件，产物集中、引用简单。
- 路线一产物：每个源文件对应一份声明，目录层级与源码结构一致。
- 路线二代价：需要额外插件与依赖，对源码中较新的类型语法可能支持不全。
- 选择依据：使用方按整包引用还是按子路径逐文件引用。

```bash
# 只产出声明文件到 dist/types，不产出 JavaScript
npx tsc -p tsconfig.build.json --emitDeclarationOnly --outDir dist/types
```

> 声明打包插件的名称与选项按所选插件的文档填写，两条路线产出的声明内容一致，差别在文件数量与引用方式。

**速记**：声明文件由编译器单独产出，或用声明打包插件合成单文件，按使用方的引用粒度选择路线。



#### 声明与产物目录的对应

**目录对应**：是声明文件落点与 JavaScript 产物落点之间的位置关系，两者必须能被同一个包入口同时解析到。

- 同层布局：声明与 JavaScript 放在同一目录、文件名相同而扩展名不同，引用关系最直观。
- 分层布局：声明单独放 types 目录，需要在包字段中指明类型入口。
- 结构一致：声明目录的层级应与源码模块结构一致，逐文件引用才不会错位。
- 保留结构：多文件产物保留模块结构时，声明也要保留同样的相对路径。
- 核对方式：构建后逐个目录比对，确认每个 JavaScript 文件都有同名声明。

```text
dist/
  index.js
  index.d.ts
  utils/
    format.js
    format.d.ts
```

> 声明与实现的相对位置一旦错位，使用方会出现类型能找到而实现找不到的报错，发布前须成对核对。

**速记**：声明与产物要么同层同名，要么分层但路径结构一致，错位会在使用方处报错。



#### 声明产出与打包的编排

**编排**：是把打包命令与声明生成命令组织成一次构建的步骤安排，保证两套产物始终成对出现。

- 两条命令：一条跑 Rollup 产出 JavaScript，一条跑编译器产出声明，二者读同一份源码。
- 先后关系：两项产出落在不同目录，先后顺序不影响最终结果。
- 并行执行：两条命令互不阻塞，可在脚本中并行以缩短总时长。
- 失败处理：任一命令失败即视为构建失败，避免半套产物进入发布流程。
- 校验方式：构建完成后统计产物目录中成对出现的文件数量。

```bash
npm run build:js
npm run build:types
# 两步都成功才进入发布流程
```

> [!CAUTION]
> **注意内容**：只发布 JavaScript 而不发布声明，使用方在编辑器中会丢失全部类型提示，且这类缺失不会在构建阶段暴露。

**速记**：打包与声明生成是两步，都成功才算构建完成，脚本里要把两步串进同一个入口。



### Babel 与语法降级

TypeScript 编译器的降级能力有边界，需要额外语法转换或垫片注入时再串一层 Babel。本节说明何时需要它、如何接线、以及与 TypeScript 插件如何分工。

#### 何时需要 Babel 介入

**Babel 介入**：是在 TypeScript 去类型之后追加的转换环节，用来覆盖 TypeScript 编译器不处理的语法降级与代码改写。

- 使用前提：依赖某个 Babel 插件才能完成的转换，例如特定框架的编译期改写。
- 典型需求：装饰器相关的额外处理、按使用情况注入垫片、条件编译与常量内联。
- 无须使用：只把语法降到目标版本以内时，单个 TypeScript 插件即可完成。
- 主要代价：多一层转换拖慢构建，两处目标版本容易写得互不一致。
- 边界说明：Babel 的预设与插件规则属于转译工具自身的话题，本篇只处理它在 Rollup 中的接线方式。

```js
// 仅在确有需要时追加，Babel 负责 TypeScript 插件不覆盖的转换
import { babel } from "@rollup/plugin-babel";

babel({
  babelHelpers: "bundled",
  extensions: [".js", ".ts"],
  exclude: "node_modules/**",
})
```

> 每追加一层转换就多一份配置与一处出错来源，先确认 TypeScript 插件确实无法完成，再引入 Babel。

**速记**：TypeScript 插件覆盖不到的转换才交给 Babel，接入代价是多一层配置与构建耗时。



#### Babel 插件的接入方式

**Babel 插件接线**：是把 @rollup/plugin-babel 放进 plugins 数组并传入选项，让它在转换阶段处理指定扩展名的文件。

- 配置来源：预设与插件列表可写在独立的 Babel 配置文件中，也可由插件选项直接传入。
- 助手策略：babelHelpers 取 bundled 时助手代码随产物打包，取 runtime 时改由运行时依赖提供。
- 扩展名：extensions 必须显式包含 ts，否则 TypeScript 文件不会被它处理。
- 排除范围：node_modules 通常排除，避免第三方包被二次转换而改变行为。
- 分工：Babel 只改写单个模块的内容，模块合并与摇树仍由 Rollup 负责。

```js
export default defineConfig({
  input: "src/index.ts",
  output: { dir: "dist", format: "es" },
  plugins: [
    typescript({ compilerOptions: { declaration: false } }),
    babel({ babelHelpers: "bundled", extensions: [".js", ".ts"] }),
  ],
});
```

> 助手的存放策略直接影响产物结构：随产物打包时使用方零依赖，改由运行时提供时会多出一条依赖声明。

**速记**：Babel 插件排在 TypeScript 插件之后，extensions 要含 ts，助手策略决定是否引入运行时依赖。



#### 两套转译的目标与重叠处理

**目标重叠**：是 TypeScript 编译器与 Babel 各自配置了一份语法目标，同一段新语法可能被两次降级或两边都不处理。

- 责任划分：TypeScript 负责去掉类型与基础降级，Babel 负责其余转换与垫片，职责不交叉。
- 目标声明：语法目标只在一处声明，另一处保持默认，减少两边不一致的可能。
- 类型语法：Babel 不识别 TypeScript 的类型注解，两个插件顺序颠倒会直接报语法错误。
- 垫片范围：垫片按目标环境与代码实际使用情况注入，避免全量注入撑大体积。
- 验证方式：在目标运行时或降级语法检查工具中实跑产物，确认没有超出范围的语法。

```text
TypeScript 插件：去掉类型 -> 基础语法降级 -> 产出标准 JavaScript
Babel 插件：读取标准 JavaScript -> 补充转换与垫片 -> 写回模块内容
Rollup：解析依赖图 -> 合并与摇树 -> 输出产物
```

> [!WARNING]
> **警告内容**：把 Babel 排在 TypeScript 插件之前，Babel 会拿到带类型注解的源码并直接抛出语法错误，构建中断且报错位置指向配置文件而非源码。

**速记**：TypeScript 先去掉类型，Babel 再做其余转换，语法目标只在一处声明并实跑验证。



### 路径别名与模块解析

Rollup 不读编辑器的路径配置，也不自动解析依赖目录，别名与解析都靠插件补齐。本节说明别名写在哪、如何与编辑器对齐、以及解析插件的顺序。

#### 别名的配置位置与写法

**别名（alias）**：是把导入路径的某段前缀映射到实际目录的规则，在 Rollup 侧由解析类插件承担。

- 插件位置：规则写在别名插件的 entries 数组中，该插件应排在转换类插件之前。
- 规则结构：每条规则给出 find 与 replacement，find 可以是字符串或正则表达式。
- 前缀匹配：find 写 @/ 这类前缀时要带上结尾斜杠，避免同前缀的其他包被误伤。
- 与解析插件的关系：别名先改写路径，解析插件再按改后的路径定位真实文件。
- 本侧声明：Rollup 不读 tsconfig 的 paths，别名必须在构建配置里再声明一次。

```js
import path from "node:path";
import { fileURLToPath } from "node:url";
import alias from "@rollup/plugin-alias";

const projectRoot = fileURLToPath(new URL(".", import.meta.url));

export default defineConfig({
  plugins: [
    alias({
      entries: [{ find: /^@\//, replacement: path.join(projectRoot, "src") + "/" }],
    }),
  ],
});
```

> 别名是纯字符串替换，不命中时不会回退到相对路径，规则写错的表现是模块解析失败而非静默跳过。

**速记**：别名用 entries 的 find 与 replacement 表达，前缀带结尾斜杠，且必须在构建侧单独声明。



#### 别名与编辑器配置的对齐

**对齐**：是让构建侧的别名规则与编辑器使用的 TypeScript paths 指向同一批目录，避免编辑器能跳转而构建找不到文件。

- 两处声明：paths 服务于编辑器与类型检查，别名服务于打包，两者互相独立。
- 单一事实源：把映射表写在一处再分别读取，或用校验脚本比对两份规则。
- 匹配范围：paths 的 @/* 与别名的前缀写法要覆盖同样的路径集合。
- 一致校验：任一侧改动后跑一次构建，确认没有出现解析失败。
- 常见后果：只有编辑器认识别名时，构建期直接报模块无法解析。

```text
tsconfig paths：  "@/*": ["./src/*"]
Rollup 别名：     { find: /^@\//, replacement: "<root>/src/" }
两处必须覆盖同一段前缀与同一个目标目录
```

> [!NOTE]
> **提醒内容**：编辑器与构建使用两套路径配置是常态，改动别名后要同时更新两侧，只改一侧会立刻出现解析不一致。

**速记**：paths 管编辑器、别名管构建，两处映射覆盖同一前缀与目录，改动后跑构建校验。



#### 解析插件的顺序与扩展名

**模块解析**：是 Rollup 把导入语句里的路径字符串转成磁盘真实文件路径的过程，默认只处理相对路径与带扩展名的导入。

- 默认行为：不解析依赖目录中的包，也不自动补全 ts、tsx 一类扩展名。
- 解析插件：开启后按包字段与扩展名列表查找依赖，extensions 决定自动补全的候选顺序。
- 顺序要求：别名与解析插件排在转换插件之前，转换器才能拿到真实文件。
- 外部依赖：声明为 external 的包跳过解析，导入语句原样保留在产物里。
- 排查方式：解析失败时看报错给出的路径与候选列表，再核对 extensions 是否包含该扩展名。

```js
import resolve from "@rollup/plugin-node-resolve";

resolve({
  extensions: [".mjs", ".js", ".json", ".ts"],
  preferBuiltins: false,
})
```

> 扩展名列表既影响能否找到文件，也影响同名不同扩展名文件并存时的选中结果，顺序需按项目约定固定。

**速记**：别名先改写路径、解析插件再补扩展名与依赖目录，两者都要排在转换插件之前。



### 常见配置问题

编译链路的故障大多表现为构建通过但产物不对。本节列出声明缺失、助手代码重复与目标不一致三类高频问题。

#### 声明文件缺失

**声明文件缺失**：是构建结束后产物目录只有 JavaScript、使用方无法获得类型提示的状况。

- 成因一：构建只执行了 Rollup，声明生成命令从未被调用。
- 成因二：tsconfig 中 declaration 为假，或被 noEmit 一并屏蔽。
- 成因三：声明写到了产物目录之外，未被一起纳入发布范围。
- 排查：先数构建脚本的步骤，确认声明生成确实执行过。
- 修复：把声明生成并入统一构建入口，并在发布前核对产物目录。

```bash
npx tsc -p tsconfig.build.json --emitDeclarationOnly
ls dist
# index.js  index.d.ts
```

> 声明缺失不会让构建失败，只能在发布后由使用方反馈，因此需要一项发布前核对产物目录的检查。

**速记**：声明缺失多因命令未执行或输出路径在外，把声明生成并入构建入口并核对产物。



#### 辅助代码重复注入

**辅助代码重复**：是产物中每个模块都内联同一份编译期助手函数，使多个文件出现近乎相同的代码块。

- 成因：去类型与降级过程中产生的助手函数默认按模块内联。
- 表现：多个产物文件里出现重复的类继承或对象展开包装函数。
- 处理一：开启按需引入助手的编译选项，并把助手包列为运行时依赖。
- 处理二：把这部分交给 Babel 的助手策略统一处理，两套机制只用其一。
- 核对：在产物中搜索助手函数名，确认定义只出现一次。

```bash
grep -c "classCallCheck" dist/index.js
# 计数大于 1 说明助手代码被逐模块内联
```

> 两种助手机制同时启用会各注入一份，产物体积不降反升，配置时只保留其中一套。

**速记**：助手代码默认逐模块内联，开启按需引入或交给 Babel 统一处理，两套机制只用其一。



#### 编译目标不一致

**目标不一致**：是模块格式、语法降级目标与压缩器目标各按一套设置，使产物混用多种语法风格。

- 三处目标：产物格式决定模块规范，编译器目标决定语法版本，压缩器另有自己的目标设置。
- 冲突一：产物声明为 ESM 而内部残留 CommonJS 包装，摇树与按需加载随之失效。
- 冲突二：编译器已降级到旧语法，压缩器按新语法优化，结果反而更长更慢。
- 统一做法：先确定目标运行环境支持的最低版本，再让三处设置指向同一版本。
- 验证：用语法检查或在目标运行时实跑产物，确认没有超出范围的语法。

```bash
npx rollup -c && node --check dist/index.mjs
```
