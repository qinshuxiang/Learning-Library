## webpack 打服务端产物

### target 与运行环境

#### web 与 node 的差异

**目标环境（target）**：是 webpack 声明的产物运行环境，它决定分块如何加载、内置模块如何处理以及全局对象以哪一端为前提。

- 分块加载：web 目标用异步脚本注入的方式加载分块，node 目标用模块系统直接引入。
- 内置模块：node 目标把文件系统、路径等内置模块保留为外部引用，web 目标则尝试替换或禁止。
- 全局对象：web 目标假设窗口对象与文档对象存在，node 目标假设全局对象与进程对象存在。
- 输出格式：node 目标通常产出供服务端直接加载的模块文件，而非脚本文件。
- 调优侧重：服务端产物更关心启动速度与内存占用，首屏体积不再是主要指标。

```js
// 服务端产物：目标环境声明为 node
module.exports = {
  target: 'node',
  entry: './src/server/index.ts',
  output: {
    path: path.resolve(__dirname, 'dist/server'),
    filename: 'server.js',
    library: { type: 'commonjs2' }
  }
};
```

> 目标环境一旦写错，最先暴露的问题往往不是报错，而是产物里混入了浏览器专属的加载逻辑。

**速记**：target 决定分块加载方式、内置模块处理与全局对象前提，服务端产物更看重启动速度。



#### target 的取值与声明方式

**target 取值**：是构建工具按环境组合出的预设名称，常见为 web 与 node，也支持带版本后缀的形式。

- 预设差异：node 预设会关闭浏览器专属的分块加载与垫片注入。
- 版本后缀：带版本后缀的写法可限定运行时能力，避免产出依赖过新语法的代码。
- 多目标：需要同时产出浏览器与服务端产物时，导出配置数组，各自声明 target。
- 与浏览器清单配合：浏览器目标可结合目标浏览器清单决定语法降级程度。
- 单项覆盖：预设不合适时可在配置中显式开启或关闭某一项能力。

```js
module.exports = [
  {
    name: 'client',
    target: 'web',
    entry: './src/client/index.ts',
    output: {
      path: path.resolve(__dirname, 'dist/client'),
      filename: '[name].js'
    }
  },
  {
    name: 'server',
    target: 'node',
    entry: './src/server/index.ts',
    output: {
      path: path.resolve(__dirname, 'dist/server'),
      filename: 'server.js'
    }
  }
];
```

> [!IMPORTANT]
> **重要内容**：客户端与服务端共用一次构建调用时，必须写成配置数组并分别声明 target 与输出目录，用同一份配置先后改 mode 切换会产出互相覆盖的产物。

**速记**：target 可用预设名或带版本后缀的形式声明，两端产物应拆成配置数组分别声明。



#### 运行时特性假设与语法降级

**运行时特性假设**：是产物可以放心使用的语言特性与全局能力，由目标环境与目标运行时版本共同确定。

- 语法降级：服务端运行时版本较新时可保留新语法，减少转译开销与产物体积。
- 全局能力：产物可假设进程对象与模块系统存在，但不可假设浏览器全局对象存在。
- 环境分支：同一份源码区分两端行为时，应在构建期确定分支，而不是在运行时探测浏览器。
- 条件解析：依赖可能按环境提供不同入口，需要确认解析到的是服务端分支。
- 中立写法：两端共享的源码不引用任一端专属的全局对象，差异由调用方传入。

```ts
// 共享源码不引用两端专属的全局对象，由调用方注入差异
export interface Logger {
  write(line: string): void;
}

export function createReporter(logger: Logger) {
  return (event: string, detail: Record<string, unknown>) => {
    logger.write(JSON.stringify({ event, detail, at: Date.now() }));
  };
}
```

> 共享源码保持运行环境中立，是把同一份代码打包到两端时最省事的做法，也是两类产物能各自降级的前提。

**速记**：按目标运行时决定语法降级程度，共享源码不依赖任一端专属的全局对象。



### externals 的用法

#### externals 的作用与判定

**外部化（external）**：是把指定依赖排除出产物、留给运行时由外部模块系统解析的配置。

- 作用：减小产物体积，避免把服务端依赖重复打包进产物。
- 判定依据：依赖是否随产物一起分发、是否需要在运行时保持唯一实例。
- 常见对象：数据库驱动、日志库、原生模块与体积较大的服务端框架。
- 配置写法：按依赖名声明为外部，产物中改为外部模块引用。
- 主要风险：外部化后的依赖必须存在于运行环境的依赖目录，否则启动即失败。

```js
module.exports = {
  target: 'node',
  externalsPresets: { node: true },
  externals: {
    // 键为源码中的导入名，值为运行时解析方式
    pg: 'commonjs pg',
    pino: 'commonjs pino'
  }
};
```

> 判定标准可以简化为一句话：该依赖是否需要按平台或版本在运行环境单独安装，需要就外部化。

**速记**：externals 把依赖留给运行时解析，判定看是否随产物分发与是否需要唯一实例。



#### 按环境区分外部化清单

**环境化清单**：是把外部依赖列表按开发、测试与生产环境分别维护，避免把只在开发期需要的包带进生产产物。

- 生产取向：生产环境尽量外部化，依赖由部署环境的依赖目录提供。
- 开发取向：开发期可把部分依赖打进产物，便于单文件运行与调试。
- 生成方式：从依赖字段读取包名自动生成清单，比手工维护更不易遗漏。
- 例外清单：必须在产物内保留的依赖单独列出，从自动清单中排除。
- 一致性校验：打包后核对产物的外部引用是否都能在目标环境解析到。

```js
const { dependencies } = require('./package.json');

// 需要在产物内保留的小依赖，其余生产依赖统一外部化
const keepBundled = new Set(['tiny-invariant', 'nanoid']);

module.exports = {
  externals: Object.fromEntries(
    Object.keys(dependencies)
      .filter((name) => !keepBundled.has(name))
      .map((name) => [name, `commonjs ${name}`])
  )
};
```

> 自动生成清单的前提是运行时安装的依赖与生产依赖字段严格对应，两者不一致时自动化只会放大错误。

**速记**：从依赖字段自动生成外部化清单，小依赖留白名单，打包后必须核对可解析性。



#### 外部化与依赖安装的关系

**外部化依赖的安装**：是产物在运行环境启动时对其依赖目录的要求，外部化越多，运行环境需要提供的包越多。

- 安装来源：平台的依赖字段决定运行环境实际安装哪些包。
- 归类要求：被外部化的包必须出现在运行时安装的依赖分类中，而非仅开发期分类。
- 版本一致：运行环境安装的版本可能与构建机不同，需要在流水线上锁定。
- 打包取舍：外部化减少产物体积但增加环境依赖，产物自包含的策略正好相反。
- 核对手段：在干净环境中仅安装运行时依赖并启动产物，验证是否可运行。

```json
{
  "dependencies": {
    "pg": "^8.11.0",
    "pino": "^8.15.0"
  },
  "devDependencies": {
    "webpack": "^5.90.0",
    "webpack-cli": "^5.1.0"
  }
}
```

> [!IMPORTANT]
> **重要内容**：把外部化的包留在开发期分类里，构建机可以正常打包，运行环境却会在启动时直接报模块找不到，依赖分类必须与外部化清单对齐。

**速记**：外部化的包必须归入运行时安装的依赖分类，并在干净环境中验证一次启动。



### Node 依赖与原生模块

#### 原生模块不打包的处理

**原生模块**：是包含按平台与架构编译出的二进制文件、打包器无法在目标平台重建这些文件的依赖。

- 形态特征：包内包含按平台划分的二进制目录或编译后的文件。
- 处理原则：整包排除出打包范围，交由运行时从依赖目录加载。
- 部分打包：包内 JavaScript 封装可打包而二进制必须保留时，按文件粒度排除。
- 架构差异：构建机与运行环境的平台或架构不同会直接导致加载失败。
- 验证方式：在与运行环境一致的镜像中启动产物，确认二进制能被加载。

```js
module.exports = {
  externals: {
    // 含二进制的依赖整包外部化
    bcrypt: 'commonjs bcrypt',
    sharp: 'commonjs sharp'
  }
};
```

> [!WARNING]
> **警告内容**：把原生模块打进产物即使能构建成功，也只是复制了一份与构建机架构绑定的二进制，运行环境架构不同时会在加载阶段直接失败。

**速记**：原生模块整包外部化，构建机与运行环境架构必须一致，并在目标镜像中验证加载。



#### 动态 require 与上下文模块

**动态 require**：是依赖名由变量拼出的运行时加载写法，打包器无法静态确定具体是哪个模块。

- 静态限制：打包器只能分析字面量形式的导入，变量形式会退化为范围匹配或直接报错。
- 上下文模块：构建工具会把匹配目录内的候选文件一起纳入产物，再在运行时按参数挑选。
- 体积影响：上下文模块会把整个目录打包进来，需要限定目录范围与文件类型。
- 排查信号：出现找不到模块但路径确实存在的报错，多为动态拼接所致。
- 处理方式：把动态加载改为显式映射表，或明确声明需要包含的范围。

```js
// 不推荐：依赖名由变量拼出，打包器无法静态分析
const driver = require(`./adapters/${process.env.ADAPTER}`);

// 推荐：显式映射，产物可控且报错可读
const adapters = {
  memory: require('./adapters/memory'),
  postgres: require('./adapters/postgres')
};
const driver = adapters[process.env.ADAPTER];
```

> [!CAUTION]
> **注意内容**：上下文模块会无声地把整个目录并入产物，其中可能包含密钥样例或测试文件，限定匹配范围时要同时检查文件类型与子目录层级。

**速记**：动态 require 无法静态分析，改为显式映射表或明确限定上下文范围。



#### 只在服务端存在的模块

**服务端专属模块**：是只在服务端运行、不应出现在浏览器产物中的模块与内置能力。

- 内置能力：文件系统、路径与进程相关能力只在服务端存在，浏览器侧需要替换或禁用。
- 单侧引用：仅服务端使用的代码应放在独立入口，避免被浏览器入口间接引入。
- 解析控制：可通过解析回退把浏览器侧指向空实现或替代实现，服务端侧保持原模块。
- 副作用隔离：初始化连接这类副作用代码不应写在模块顶层，避免构建期或导入期执行。
- 边界清晰：两端共享的模块保持无副作用，便于分别打包与按环境替换。

```js
module.exports = {
  resolve: {
    // 浏览器产物把服务端专属模块指向空实现
    fallback: {
      fs: false,
      path: false
    }
  }
};
```

> 浏览器侧出现服务端专属模块的引用时，优先检查是否由共享模块间接引入，而不是逐个补垫片。

**速记**：服务端专属模块在浏览器侧要显式禁用或替换，共享模块必须保持无副作用。



### 服务端产物的构建要点

#### 产物入口与导出形式

**服务端产物入口**：是服务端启动时加载的文件，它的导出形式决定了外部如何引用。

- 单入口：一个启动文件，通常导出创建服务或启动函数，由外部命令调用。
- 多入口：按进程角色拆成多个入口，如接口服务与后台任务各产出一个文件。
- 导出形式：产出为运行时模块格式，与外部加载方式保持一致。
- 配置读取：端口与连接串等通过运行时环境变量读取，不写进产物。
- 启动方式：产物入口由进程管理命令或平台启动配置调用，不再经过开发期命令。

```js
module.exports = {
  target: 'node',
  entry: {
    api: './src/server/api.ts',
    worker: './src/server/worker.ts'
  },
  output: {
    path: path.resolve(__dirname, 'dist/server'),
    filename: '[name].js',
    library: { type: 'commonjs2' },
    clean: true
  }
};
```

> [!CAUTION]
> **注意内容**：把端口、连接串或密钥写进构建期常量，会让产物与一套环境绑定，跨环境部署时必须重新构建，运行时读取环境变量才能让同一份产物随处可用。

**速记**：入口按进程角色拆分，导出为运行时模块格式，配置一律从环境变量读取。



#### source map 与体积取舍

**服务端映射文件**：是把压缩后的产物映射回源码的调试信息，服务端同样需要，但产出方式与前端不同。

- 调试需求：服务端报错栈默认指向产物位置，缺少映射时定位困难。
- 产出方式：可产出独立映射文件并在启动时加载，也可压缩但保留可读的变量名。
- 体积影响：映射文件体积可能超过产物本身，是否随产物分发需要按环境决定。
- 安全考虑：映射文件包含源码内容，对外提供服务的产物不应公开该文件。
- 取舍原则：服务端压缩收益有限时，保留可读产物比压缩后再配映射更省事。

```js
module.exports = {
  target: 'node',
  devtool: 'source-map',
  optimization: {
    // 服务端压缩收益有限，排查优先时可关闭压缩
    minimize: false
  }
};
```

> 映射文件的生成方式与各类取值的差异见本主题第 10 篇与第 15 篇，服务端场景只需确认它不随静态资源对外发布。

**速记**：服务端同样需要映射信息，但映射文件含源码，不得对外公开，收益有限时可放弃压缩。



#### 排除前端专属资源

**产物排除**：是在服务端构建中关闭或跳过与浏览器相关的处理步骤，避免无用工作与误报。

- 资源处理：关闭图片与字体等资源模块规则，服务端不需要产出这些文件。
- 页面模板：不生成页面模板与静态资源清单，这些属于前端构建产物。
- 样式提取：服务端不需要抽取样式文件，样式相关的处理链可整体跳过。
- 环境常量：只为浏览器注入的常量不在服务端配置中重复声明。
- 目录隔离：两端产物写入不同目录，避免清理步骤互相删除文件。

```js
module.exports = {
  target: 'node',
  module: {
    rules: [
      {
        test: /\.(ts|tsx)$/,
        exclude: /node_modules/,
        use: 'ts-loader'
      }
      // 服务端配置不包含样式与静态资源规则
    ]
  }
};
```

> 两端配置共用一个基础片段时，前端专属规则应在服务端配置中被显式移除，而不是期待它们不被命中。

**速记**：服务端配置不引入资源、模板与样式规则，两端产物目录隔离以免清理互相影响。



### 调试与部署衔接

#### 本地直接运行产物

**本地运行产物**：是在开发机上直接执行构建后的服务端文件，用于验证打包结果是否可用。

- 前置条件：运行环境的依赖需已安装，被外部化的包缺一不可。
- 环境变量：用环境变量提供端口与连接串，与线上保持一致。
- 校验点：启动日志、健康检查接口与一次真实请求的返回。
- 常见差异：开发机上的全局依赖可能掩盖缺失的依赖，需要在干净环境中重复验证。
- 快速定位：启动报错中的模块名可直接对应到外部化清单，便于逐条核对。

```bash
npm run build:server
node dist/server/api.js
# 启动后访问健康检查接口确认产物可用
curl -s http://127.0.0.1:3000/health
```

> 本地能跑通只说明依赖齐全，不能说明资源占用与并发行为符合预期，性能层面的验证仍需在目标环境完成。

**速记**：本地直接运行产物能快速验证依赖齐全与启动路径，性能结论仍需目标环境给出。



#### 与镜像构建的衔接

**镜像衔接**：是把服务端产物与运行时依赖一起放入运行环境的过程，镜像本身的细节属于后端部署主题。

- 输入清单：产物目录与运行时依赖清单是镜像构建的两项输入。
- 分层考虑：产物与依赖分开拷贝可提升缓存命中率，属于镜像侧优化。
- 源码排除：构建产物已包含业务代码，源码目录不必进入运行环境。
- 启动命令：镜像启动命令指向产物入口，而不是源码或开发期命令。
- 衔接校验：镜像内执行一次启动自检，确认外部化依赖均已安装。

```bash
npm run build:server
# 产出 dist/server 与运行时依赖清单，交给镜像构建使用
ls dist/server
```

> [!NOTE]
> **提醒内容**：镜像分层、基础镜像选择与容器编排规则详见 后端/Docker 主题，此处只确认产物与依赖清单是否齐全。

**速记**：镜像构建的输入是产物目录与运行时依赖清单，启动命令指向产物入口。



#### 产物清单与依赖清单核对

**产物核对**：是把构建产出与运行环境的依赖清单逐项对照，确认产物在目标环境可以启动。

- 产物清单：入口文件、分块文件与映射文件，确认数量与命名符合预期。
- 外部引用：从产物中提取外部模块名，与运行环境依赖清单求差集。
- 版本核对：外部依赖的版本与构建期声明的范围做一次比对。
- 体积核对：产物异常偏大通常意味着某个大依赖未被外部化。
- 自动化：把核对步骤写入构建脚本，作为发布前的固定检查。

```bash
npm run build:server
ls -lh dist/server
# 逐个确认外部依赖能在运行环境解析
node -e "require.resolve('pg'); require.resolve('pino')"
```

> 核对清单要跟着产物走：新增一个外部化依赖，就新增一条核对项，人工记忆必然遗漏。

**速记**：核对产物清单、外部引用、版本与体积，并把核对步骤固化进构建脚本。
