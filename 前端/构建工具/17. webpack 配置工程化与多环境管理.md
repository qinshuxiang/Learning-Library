## webpack 配置工程化与多环境管理

webpack 的配置最终是一份导出配置对象的 JavaScript 文件，项目扩大后，多环境差异、公共片段与敏感值都会压在这一份文件上。本篇讲配置怎么组织、构建期变量怎么注入、多环境怎么合并复用、类型提示与校验怎么补上，以及应当守住的约定与常见反例。webpack 的基础概念与 entry、output、mode 的写法详见本主题第 8 篇 webpack 核心概念与配置；缓存与 source map 策略见第 15 篇，产物体积分析见第 10 篇。

### 配置文件的组织方式

配置的组织方式决定一次环境改动要落在几个文件上。本节先讲单文件写法，再讲函数式导出，最后讲按环境拆分与公共片段抽取。

#### 单文件配置与静态导出

**静态导出配置**：是把配置写成普通对象、用 module.exports 直接导出的形式，webpack 启动时读取该对象，不做任何运行时判定。

- 适用规模：入口少、loader 规则少、只需要一种运行环境的项目。
- 优点：结构直观，配置即数据，阅读时不必跟踪函数分支。
- 局限：环境差异只能靠手改或用命令行参数变通，差异一多就散落各处。
- 读取方式：默认读取项目根目录的 webpack.config.js，也可用配置文件参数显式指定路径。
- 演进信号：同一份文件里开始出现按环境判断的分支时，就该转向函数式导出。

```js
// webpack.config.js
const path = require("node:path");

module.exports = {
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "bundle.js",
  },
  mode: "production",
};
```

> 静态导出的配置只能表达一种结果，命令行传入的模式参数不会自动改变它，必须在配置里自行读取才生效。

**速记**：静态导出即一份对象配置，直观但无法承载环境差异，出现分支时就该改造。



#### 函数式导出与运行时判定

**函数式导出配置**：是把配置写成接收 env 与 argv 两个参数并返回配置对象的函数，webpack 在启动时调用该函数，返回值才是最终配置。

- 参数来源：env 来自命令行传入的环境标记，argv 是解析后的命令行参数，含 mode 与 watch 等字段。
- 判定位置：环境分支集中在函数体内，避免把判断散落到各个配置字段。
- 返回值：必须返回对象或对象数组，返回数组用于一次构建产出多套配置。
- 执行时机：每次构建执行一次，函数体内不要写有副作用的耗时操作。
- 与静态导出关系：函数式是静态导出的超集，简单项目无须为形式而形式。

```js
// webpack.config.js
module.exports = (env, argv) => {
  const path = require("node:path");
  const isProduction = argv.mode === "production";

  return {
    mode: isProduction ? "production" : "development",
    entry: "./src/index.js",
    output: {
      path: path.resolve(__dirname, "dist"),
      filename: isProduction ? "[name].[contenthash:8].js" : "[name].js",
    },
  };
};
```

> [!NOTE]
> **提醒内容**：函数体内早于返回语句执行的异步操作不会被等待，配置所需的数据必须在返回前同步就绪。

**速记**：函数式导出用 env 与 argv 做判定，把环境分支收敛到一处，返回值即最终配置。



#### 按环境拆分配置与公共片段抽取

**配置拆分**：是把配置按公共、开发、生产三类写成多个文件，再由入口文件组合，公共部分只维护一份。

- 公共文件：放 entry、resolve、loader 规则等与环境无关的部分。
- 环境文件：只写该环境独有的差异，如 mode、产物命名与压缩设置。
- 入口文件：按命令行传入的标记选择对应环境文件并导出，是唯一的判定点。
- 片段抽取：loader 规则与插件集合可进一步拆成独立模块，按需引用。
- 目录约定：拆分后的文件统一放在 config 目录，避免与源码目录混放。

```text
config/
  webpack.common.js      入口、resolve 与共用 loader 规则
  webpack.dev.js         开发环境差异
  webpack.prod.js        生产环境差异
  webpack.config.js      按环境标记选择并导出
```

> 拆分的收益来自差异集中，若三个文件里仍各写一遍 entry 与 output，拆分只会增加跳转成本。

**速记**：公共与各环境配置分文件维护，入口文件是唯一的环境判定点。



### 环境变量与构建期注入

构建期变量是在打包时被替换进代码的常量，与运行时读取的环境变量是两回事。本节讲变量从哪来、注入插件做了什么，以及值的类型最常出的错。

#### 构建期变量与运行时变量

**构建期变量**：是在打包阶段被读取并替换为字面量的值，打包完成后源码里不再存在变量读取动作。

- 来源：命令行前置的环境变量、持续集成平台注入的变量、本地 shell 导出的变量。
- 读取时机：只在配置脚本执行期间读取一次，产物生成后修改环境变量不会改变结果。
- 与运行时变量：运行时变量在进程启动时由服务端注入，构建期变量已被固化进产物。
- 命名约定：自定义变量使用统一前缀，便于在配置里筛出需要注入的项。
- 传递方式：命令行以键值对形式前置，配置脚本通过 process.env 读取（process 对象细节见后端/Node 主题）。

```bash
# 构建时注入，产物中该值被固化
BUILD_ENV=staging npm run build

# 配置脚本内读取
node -e "console.log(process.env.BUILD_ENV)"
# staging
```

> 产物里的构建期变量是快照，同一份产物换环境部署不会改变它，需要不同值就必须重新构建。

**速记**：构建期变量只在配置执行时读一次并被写死进产物，改值必须重新构建。



#### DefinePlugin 的替换原理

**DefinePlugin**：是 webpack 内置的插件，在编译阶段把源码中指定的标识符替换成给定值对应的代码片段，默认不做作用域判断。

- 配置形式：以标识符为键、以代码片段字符串为值的对象，键名区分大小写。
- 替换范围：源码与模板中出现的该标识符都会被替换，第三方依赖内的同名出现同样命中。
- 值的要求：值会被当作代码插入，字符串必须先用 JSON.stringify 序列化，否则变成变量名。
- 典型用途：注入环境名、接口地址与功能开关，配合压缩工具让死分支被消除。
- 边界：它不做运行时查找，替换只发生在构建期，无法随运行环境变化。

```js
// webpack.config.js
const webpack = require("webpack");

module.exports = {
  plugins: [
    new webpack.DefinePlugin({
      __BUILD_ENV__: JSON.stringify(process.env.BUILD_ENV || "production"),
      __ENABLE_DEBUG__: JSON.stringify(false),
    }),
  ],
};
```

> [!IMPORTANT]
> **重要内容**：替换是文本级动作，标识符要足够独特，避免与依赖包中的同名标识符冲突而产生难以定位的运行时报错。

**速记**：DefinePlugin 在编译期把标识符换成代码片段，值必须序列化，键名要避免撞名。



#### 注入值的类型陷阱

**类型陷阱**：是把非字符串值直接交给注入插件时，值被当作代码片段而非数据，导致产物里出现错误类型或直接报错。

- 字符串：未序列化的字符串会被当成变量名，产物里出现未定义标识符。
- 布尔与数字：直接写布尔或数字字面量可省去序列化，写成字符串形式的真会被当作标识符。
- 对象与数组：必须整体序列化，部分序列化的对象会变成语法错误的片段。
- 缺失值：值不存在时序列化结果仍是字符串形式的 undefined，运行时读取会被判为真。
- 兜底写法：读取环境变量并给出默认值，再统一序列化，避免缺失值进入产物。

```js
// 反例：值未序列化，产物中的标识符指向不存在的变量
new webpack.DefinePlugin({ __API_HOST__: process.env.API_HOST });

// 正例：先取值与兜底，再整体序列化
new webpack.DefinePlugin({
  __API_HOST__: JSON.stringify(process.env.API_HOST ?? "https://example.com"),
});
```

> [!WARNING]
> **警告内容**：未序列化的字符串不会在构建时报错，只在运行时抛出未定义标识符，问题往往到部署后才暴露，注入后应检查产物核对替换结果。

**速记**：注入值必须序列化并给默认值，否则字符串变标识符、缺失值变真值。



### 多环境配置的合并与复用

环境之间的差异通常只占配置的一小部分，合并函数与派生规则决定这部分差异怎么叠加到公共配置上。本节讲合并边界、按模式派生与环境判定入口。

#### 配置合并函数与合并边界

**配置合并函数**：是把公共配置与环境配置按键深度合并、返回新对象的工具函数，典型实现由社区包 webpack-merge 提供。

- 数组合并：默认把两个数组拼接，可配置策略改为按索引或按键覆盖。
- 对象合并：递归合并同键对象，冲突时以后传入的值为准。
- 不修改原值：合并返回新对象，传入的公共配置对象保持原样。
- 合并边界：loader 规则数组与插件数组通常都用拼接，二者顺序敏感，注意传入次序。
- 使用范围：合并函数只负责结构叠加，不负责判定该不该合并。

```js
// config/webpack.prod.js
const { merge } = require("webpack-merge");
const common = require("./webpack.common.js");

module.exports = merge(common, {
  mode: "production",
  output: { clean: true },
});
```

> 合并顺序决定覆盖方向，公共配置放第一个参数、环境配置放第二个参数，顺序颠倒会让公共值覆盖环境值。

**速记**：合并函数按键深度叠加并返回新对象，数组按拼接处理，覆盖方向由参数顺序决定。



#### 按 mode 派生配置

**mode**：是 webpack 的内置运行模式字段，取值为 development、production 或 none，内置插件会据此设置一组默认优化行为。

- 内置行为：生产模式默认开启压缩与作用域提升，开发模式默认给出更可读的报错。
- 派生写法：以 mode 为唯一判定源，避免再引入一套自定义环境名导致两套语义并存。
- 组合写法：mode 与命令行传入的环境标记可共存，但应约定各自负责的差异范围。
- 默认值：未声明时按生产模式处理并给出提示，容易与预期不符。
- 覆盖顺序：配置对象里显式写的字段优先于模式内置的默认值。

```js
// config/webpack.base.js
const path = require("node:path");

module.exports = (mode) => ({
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "../dist"),
    filename: mode === "production" ? "[name].[contenthash:8].js" : "[name].js",
  },
});
```

> 用自定义环境名重复表达开发与生产的差异，会让压缩与报错风格等内置行为需要手工补齐，优先复用 mode。

**速记**：mode 决定一组内置默认行为，环境差异优先挂在 mode 上，避免与自定义环境名双重判定。



#### 环境判定入口与配置片段复用

**环境判定入口**：是集中读取环境标记并选择配置的唯一位置，通常是一个极短的入口文件，其余文件只导出纯配置对象。

- 判定来源：命令行参数优先，其次环境变量，最后取默认值。
- 单一职责：入口文件只做选择与组装，不写具体 loader 或插件配置。
- 片段复用：loader 规则与插件集合拆成函数或模块，由多个环境文件共同引用。
- 导出形态：入口可导出单个对象、对象数组或函数，按构建目标数量选择。
- 可核对性：纯配置对象便于用脚本直接引用并断言关键字段。

```text
argv.mode 传入
  → 入口文件读取标记
  → 命中环境配置文件
  → 与公共片段合并
  → 导出最终配置
```

> [!TIP]
> **建议内容**：环境标记只允许在入口处读取一次，判定散落多处时，同一环境在两处得出不同结论的问题极难排查。

**速记**：环境判定只在入口文件做一次，其余文件保持纯配置，片段以函数或模块复用。



### 配置的类型提示与校验

配置字段多、拼写错误只在构建时报出，类型提示与结构校验能把一部分错误提前到编辑期。本节讲类型注释、校验来源与报错读法。

#### JSDoc 类型注释与编辑器提示

**JSDoc 类型注释**：是在配置对象上方用注释声明其类型、由编辑器据此给出字段补全与类型检查的写法。

- 声明位置：写在配置变量上方，或在函数式导出的返回值处声明。
- 类型来源：从 webpack 的类型声明包导入 Configuration 类型，无须安装额外工具。
- 检查开关：编辑器在开启 JavaScript 类型检查后才会按注释报错，仅补全则无须开关。
- 收益：字段拼写、取值类型与互斥选项能在编辑期发现。
- 覆盖范围：注释只描述结构，不校验取值是否被 webpack 接受。

```js
// webpack.config.js
/** @type {import("webpack").Configuration} */
const config = {
  mode: "production",
  entry: "./src/index.js",
};

module.exports = config;
```

> 只用注释做提示不会让构建失败，配置能否通过校验仍由 webpack 自身的结构校验决定。

**速记**：用 JSDoc 声明 Configuration 类型换取编辑期补全与类型检查，但不改变构建期的校验结果。



#### 配置结构校验与错误字段

**配置结构校验**：是 webpack 在启动时按内置 schema 逐字段检查配置对象、发现未知字段或类型不符即终止构建的机制。

- 触发时机：构建启动阶段，早于模块解析与编译。
- 检出项：未知字段名、字段类型不符、互斥写法同时出现。
- 报送内容：给出出错字段的路径、期望的类型与常见原因。
- 无法检出：字段取值语义错误、插件顺序错误等结构判断之外的问题。
- 应对方式：先修正校验报出的结构性错误，再处理运行期报错，避免两类问题互相掩盖。

```text
Invalid configuration object.
 - configuration.resolve has an unknown property 'aliasx'.
 - configuration.output.path should be an absolute path.
```

> 结构校验只认字段结构，不认业务意图，字段拼写正确但语义写错的情况仍要靠构建结果判断。

**速记**：webpack 启动即按 schema 校验配置结构，未知字段与类型不符会直接终止构建。



#### 配置报错的读法与定位

**配置报错**：是构建在读取配置阶段抛出的错误，通常包含出错字段路径与期望值，按路径回查配置即可定位。

- 定位顺序：先看报错的字段路径，再回到配置文件按同名键查找。
- 常见成因：字段名拼写错误、把数组写成对象、把相对路径当成绝对路径。
- 环境相关：多个环境配置合并后才出错，需确认最终合并结果而非单个文件。
- 核对方式：在配置入口临时打印合并结果，对照报错路径逐层查看。
- 插件相关：插件配置错误由插件自身抛出，与 webpack 结构校验的报错格式不同。

```js
// config/webpack.config.js 末尾临时打印，核对合并结果
const config = require("./webpack.prod.js");
console.log(JSON.stringify(config, null, 2));
module.exports = config;
```

> [!TIP]
> **建议内容**：合并链较长时，把最终配置对象序列化打印一次，比逐个文件猜测取值来源更快，排查完应及时删除该打印。

**速记**：按报错里的字段路径回查配置文件，合并场景要查看最终合并结果而非单份片段。



### 配置工程化的约定与反例

配置是长期演进的代码，约定决定它是否仍然可读。本节讲目录与命名、敏感值处理，以及配置膨胀的识别与拆分。

#### 配置目录与命名约定

**配置目录约定**：是把配置与脚本集中放在项目根的 config 目录、按用途命名文件的组织习惯。

- 目录位置：配置集中在项目根一层，避免散落到各子目录。
- 命名规则：公共、开发、生产三类分别以 common、dev、prod 结尾，含义稳定。
- 扩展名：与项目模块规范一致，模块项目用 .js 或 .mjs，类型项目另有约定。
- 脚本入口：包管理脚本里固定传配置文件路径，避免依赖默认查找顺序。
- 环境示例：提供不含真实值的示例文件，说明需要哪些变量及其用途。

```text
项目根/
  config/
    webpack.common.js
    webpack.dev.js
    webpack.prod.js
    webpack.config.js
  .env.example
```

> 命名一旦确定就应在文档里固定下来，新增环境沿用同一构词规则，避免 local、test、staging 三种风格混用。

**速记**：配置集中放 config 目录，按 common 与各环境后缀命名，入口路径在脚本里固定。



#### 敏感值不进配置仓库

**敏感值**：是密钥、令牌、私有仓库凭据等一旦泄露即造成损失的取值，不允许写进配置文件并提交到版本库。

- 判定标准：泄露后需要轮换才能恢复的值都算敏感值。
- 注入位置：由持续集成或本地 shell 传入环境变量，配置脚本只读取变量名。
- 提交边界：提交示例文件与变量清单，不提交真实取值。
- 产物风险：注入进产物的值对使用者完全可见，前端产物尤其不能承载密钥。
- 历史风险：取值曾进入版本库历史后，删除文件不足以消除泄露，必须轮换。

```js
// 反例：真实密钥随配置提交，且被打进产物
new webpack.DefinePlugin({
  __API_SECRET__: JSON.stringify("replace-with-real-secret"),
});

// 正例：只读取外部注入的变量，缺失即报错退出
const apiSecret = process.env.API_SECRET;
if (!apiSecret) {
  throw new Error("缺少 API_SECRET 环境变量");
}
```

> [!CAUTION]
> **注意内容**：任何被打进前端产物的值都应视为公开信息，密钥只能留在服务端，构建期注入不能改变这一点。

#### 配置膨胀的信号与拆分策略

**配置膨胀**：是单份配置在字段与分支持续增加后变得难以维护的状态，表现为同一规则被反复复制、判定散落各处。

- 信号一：同一组 loader 规则在多个环境文件里重复出现。
- 信号二：环境判定出现在配置对象的内部字段而非入口。
- 信号三：文件长度超过数百行且缺乏分段注释，改一处需要通读。
- 拆分策略：按职责拆出 loader 规则、插件集合与产物命名三类片段。
- 合并策略：片段以函数接收参数，用参数表达差异，避免在片段内再写环境分支。

```js
// config/parts/plugins.js
const webpack = require("webpack");

module.exports = function makePlugins({ apiHost }) {
  return [
    new webpack.DefinePlugin({
      __API_HOST__: JSON.stringify(apiHost),
    }),
  ];
};
```

> 拆分的判据是差异能否用参数表达，能用参数表达的重复就合并，不能用参数表达的才保留分支。

**速记**：重复规则、散落判定与超长文件是膨胀信号，按职责拆片段、用参数表达差异。
