## Gulp 任务编排与依赖

一个任务只描述一段处理，可用的构建流程来自多个任务的组合。本篇讲串行（series）与并行（parallel）两种组合的执行语义、任务如何拆分与复用、导出与私有的边界如何划分、异步任务怎样报告完成，以及开发、构建、发布三条任务线怎么编排。任务的定义与安装见本主题第 47 篇，文件流的读写与 glob 匹配见第 48 篇。

### 串行与并行

组合函数把任务函数当作可拼装的构件，其返回值本身仍是任务函数。本节先分别说明两种组合的执行语义，再说明嵌套组合时顺序的确定方式。

#### 串行组合的语义

**串行组合（series）**：是 gulp.series 接收若干任务并按传参顺序依次执行、前一个报告完成后再启动下一个的组合方式。

- 参数类型：任务函数、已注册的任务名字符串、另一个组合函数，三者可以混用。
- 执行顺序：严格按书写顺序推进，顺序在运行前即已确定，不依赖运行时判断。
- 完成判定：只有当前任务的完成信号被 Gulp 收到，下一个任务才会启动。
- 返回值：series 返回一个新的组合函数，可以继续被 series 或 parallel 包裹。
- 适用场景：存在读写依赖的步骤，如先清理再编译、先编译再做指纹。

```js
const { src, dest, series } = require("gulp");
const { rm } = require("node:fs/promises");

function cleanDist() {
  return rm("dist", { recursive: true, force: true });
}

function copyPages() {
  return src("src/pages/**/*.html").pipe(dest("dist"));
}

// 清理必须先于拷贝，否则刚写出的文件中途被删除
exports.build = series(cleanDist, copyPages);
```

> 串行的顺序是显式书写的，读 gulpfile 时按组合函数的参数顺序读即可，不需要推断任务之间是否存在依赖。

**速记**：series 按参数顺序串起来，前一个完成才启动下一个，用于有读写依赖的步骤。



#### 并行组合的语义

**并行组合（parallel）**：是 gulp.parallel 接收若干任务并同时启动、等全部报告完成后才算结束的组合方式。

- 参数类型：与 series 相同，任务函数、任务名与组合函数都可传入。
- 启动时机：组合被调用后全部任务立即启动，互不等待。
- 结束判定：全部任务的完成信号都收到，组合才算完成。
- 收益来源：互不依赖的步骤同时占用输入输出，编译类任务的总耗时下降明显。
- 适用场景：写往不同目录的编译与拷贝步骤，如脚本与样式各自输出到不同子目录。

```js
const { src, dest, parallel, series } = require("gulp");

function buildScripts() {
  return src("src/scripts/**/*.js").pipe(dest("dist/scripts"));
}

function buildStyles() {
  return src("src/styles/**/*.css").pipe(dest("dist/styles"));
}

// 两个任务写往不同子目录，可安全并发
exports.build = series(parallel(buildScripts, buildStyles));
```

> [!WARNING]
> **警告内容**：并行任务若写往同一个文件或同一目录下的同名文件，最终内容取决于完成先后，表现为产物随机变化，必须先把写入目标拆开再并行。

**速记**：parallel 同时启动全部任务、等全部完成才结束，前提是各任务的写入目标互不重叠。



#### 嵌套组合与执行顺序

**嵌套组合**：是把组合函数的返回值再次传入组合函数、用层次结构表达整体串行与局部并行混合顺序的做法。

- 组合结果：组合函数的返回值是任务函数，与普通任务具有同等地位。
- 层次表达：外层决定大阶段顺序，内层决定同一阶段内哪些步骤可以并发。
- 名称显示：组合函数的显示名由参数推导，可通过 displayName 字段改写。
- 展开视角：嵌套只影响启动顺序，不会自动分析任务之间的真实读写依赖。
- 排查方式：用任务清单命令确认实际暴露的入口与预期一致。

```js
const { series, parallel } = require("gulp");

// 阶段一清理，阶段二编译与拷贝并发，阶段三校验
exports.build = series(
  cleanDist,
  parallel(buildScripts, buildStyles, copyAssets),
  verifyOutput
);
```

> 组合只描述调度，不描述依赖；把两个写同一目录的任务放进 parallel 不会报错，只会产生不确定的结果。

**速记**：嵌套组合用层次表达混合顺序，组合只负责调度，写入目标必须互不重叠。



### 任务的组合与复用

编排的可维护性取决于任务的拆分方式。本节说明如何把流程拆成普通函数、如何把函数拼装成入口，以及如何用工厂消除同构任务的重复代码。

#### 任务拆分为普通函数

**任务拆分**：是把流程中的每个阶段写成一个独立命名的普通函数、只在需要时导出，使单段逻辑可被多次引用与单独验证的做法。

- 命名要求：函数名描述动作与对象，如 buildScripts、hashAssets，不用抽象编号。
- 单一职责：一个函数只做一件事，其输入范围与输出位置保持稳定。
- 复用能力：普通函数不依赖任务注册表，可以在任意组合里被引用多次。
- 可验证性：函数的输出是流或 Promise，可以在脚本中直接调用验证。
- 与注册的区别：写成函数不等于注册任务，未导出的函数命令行看不到。

```js
const { src, dest } = require("gulp");

function buildScripts() {
  return src("src/scripts/**/*.js").pipe(dest("dist/scripts"));
}

function buildStyles() {
  return src("src/styles/**/*.css").pipe(dest("dist/styles"));
}

// 两个函数都不导出，只能在模块内部被组合函数引用
```

> 拆分的粒度以「能否独立描述一次输出」为准，过细会带来大量只被调用一次的函数，反而增加阅读成本。

**速记**：每个阶段写成一个命名清晰的普通函数，需要时才导出，便于复用与单独验证。



#### 用组合函数拼装流程

**流程拼装**：是把已拆分的小任务按阶段组装成面向使用者的入口任务，入口只负责调度、不含具体处理逻辑的做法。

- 入口命名：入口任务按使用者视角命名，如 dev、build、release。
- 阶段划分：按清理、编译、优化、校验划分阶段，段内并发、段间串行。
- 逻辑下沉：文件处理逻辑留在小任务里，入口任务不出现路径与流操作。
- 增量演进：新增阶段只需改动入口的组合表达式，既有小任务不受影响。
- 可读性：入口任务的组合表达式即构建流程的说明书，应保持简短。

```js
const { series, parallel } = require("gulp");

exports.build = series(
  cleanDist,
  parallel(copyPages, copyAssets),
  parallel(buildScripts, buildStyles),
  hashAssets
);
```

> 入口任务一旦出现具体的读写代码，说明该逻辑应当下沉为独立任务，否则复用与验证都会受限。

**速记**：入口任务只做调度，按清理、编译、优化、校验分段，段内并发、段间串行。



#### 参数化任务工厂

**任务工厂**：是接收路径、输出目录等参数并返回任务函数的高阶函数，用一份处理逻辑产出多个同构任务。

- 参数透传：源路径与输出路径由参数传入，处理链路在工厂内只写一次。
- 命名区分：工厂返回的函数要设置 displayName 字段，命令行才显示可读名字。
- 求值时机：工厂在模块加载阶段调用一次，把返回的函数赋给变量再参与组合。
- 常见用途：同一种处理套用到多个目录，如按语言目录产出多个站点分支。
- 避免重复：不要为每个参数组合重写一份相同代码，工厂是消除重复的正当手段。

```js
const { src, dest } = require("gulp");

function makeCopyTask(label, source, output) {
  const task = () => src(source).pipe(dest(output));
  task.displayName = "copy:" + label;
  return task;
}

const copyDocs = makeCopyTask("docs", "src/docs/**/*.md", "dist/docs");
const copyImages = makeCopyTask("images", "src/images/**/*", "dist/images");

module.exports = { copyDocs, copyImages };
```

> 工厂函数在模块加载阶段就求值，因此参数必须是常量或环境读取结果，不能依赖另一个任务运行后的产物。

**速记**：任务工厂用参数产出同构任务，返回的函数要设 displayName 才能在命令行中辨识。



### 私有任务与导出任务

对外能调用什么，完全由导出清单决定。本节说明导出与注册的对应关系、哪些任务应当保持私有，以及如何控制命令行可见范围。

#### 导出即注册的约定

**任务注册**：是从 gulpfile 导出成员即登记任务、导出名即命令行任务名的约定，Gulp 不提供独立的注册接口。

- 导出对象：module.exports 的每个成员被登记为一个任务，键名即任务名。
- 单独导出：按成员方式赋值的函数以成员名登记，函数自身的名称不影响任务名。
- 默认任务：导出名为 default 的成员即默认任务，命令行不带任务名时触发。
- 组合成员：组合函数的返回值可以直接作为导出值，不需要额外包装。
- 覆盖规则：同名导出会覆盖先前的登记，最终以最后一次赋值为准。

```js
const { series, parallel } = require("gulp");

exports.clean = cleanDist;
exports.build = series(cleanDist, parallel(buildScripts, buildStyles));
exports.default = exports.build;
```

> 导出名即公开接口，改名意味着使用者的命令行与流水线脚本同时失效，必须同步修改。

**速记**：导出即注册、导出名即任务名，default 是默认任务，改名等于改公开接口。



#### 私有任务的边界

**私有任务**：是只在模块内被组合函数引用、不写入导出对象的任务函数，命令行无法直接调用它。

- 可见性：未导出的函数不出现在任务清单里，避免被误当作入口执行。
- 依赖保护：私有任务隐含「必须先有前置步骤」的约定，不导出即无法跳过前置。
- 典型对象：清理目录、写临时文件、校验中间产物这类步骤应保持私有。
- 组合可用：私有任务与导出任务在组合函数中地位相同，不受可见性影响。
- 命名提示：私有任务可用内部前缀命名，与对外入口在视觉上区分开。

```js
const { series } = require("gulp");

// 不导出：命令行无法单独执行，只能经由 build 触发
function cleanDist() {
  return rm("dist", { recursive: true, force: true });
}

exports.build = series(cleanDist, buildScripts, buildStyles);
```

> 让中间步骤保持私有，是保证「先清理后写出」这类顺序不被绕过的最简单手段。

**速记**：不导出的任务命令行不可见，用于保护必须先执行的中间步骤。



#### 命令行可见范围的控制

**可见范围**：是由导出清单决定、可在任务清单命令中查看的命令行能力边界，导出什么就暴露什么。

- 清单命令：带清单参数的命令行调用可以列出当前可调用的任务及说明。
- 说明字段：任务函数的 description 字段会出现在清单中，用于解释用途。
- 精简暴露：只导出开发、构建、发布三个入口，其余全部保持私有。
- 兼容入口：为常用流程保留少数细粒度入口，便于排障时单独运行。
- 版本影响：清单输出格式随主版本变化，流水线不应解析清单文本。

```js
const { series } = require("gulp");

cleanDist.description = "清空产物目录";
exports.build = series(cleanDist, buildScripts, buildStyles);
exports.build.description = "编译全部资源到 dist";
```

```bash
npx gulp --tasks
# 列出可调用任务及其说明
npx gulp build
# 只调用导出的入口
```

> [!CAUTION]
> **注意内容**：流水线脚本若解析任务清单的文本来判断任务是否存在，会在 Gulp 升级改变输出格式后失效，应改为直接调用固定任务名并让失败暴露出来。

**速记**：导出清单决定命令行能力，用说明字段提升可读性，流水线只依赖固定任务名。



### 返回值与异步约定

Gulp 靠任务函数的返回值判断一段处理何时结束。本节列出三种完成信号：返回流、返回 Promise 与声明回调形参。

#### 返回流表达完成

**流完成信号**：是任务函数返回一个流对象、Gulp 监听该流的结束事件以判定任务完成的做法。

- 判定方式：返回流即视为异步任务，Gulp 等流读取完毕再继续。
- 常见写法：把 src 到 dest 的管道整体返回，不返回则任务在管道完成前就被视为结束。
- 连接处：管道中间不插入不返回流的分支，否则 Gulp 的监听目标不明确。
- 错误传播：流中的错误默认中断任务，收敛方式见本主题第 51 篇。
- 空流：源匹配不到文件时流仍会正常结束，任务不会因此失败。

```js
const { src, dest } = require("gulp");

function buildScripts() {
  // 整体返回，Gulp 以流的结束事件作为完成信号
  return src("src/scripts/**/*.js").pipe(dest("dist/scripts"));
}
```

> 忘记返回是最常见的编排错误：任务瞬间「完成」，后续串行步骤在文件尚未写出时就启动了。

**速记**：返回流即以流的结束为完成信号，管道要整体返回，不能只写在语句里。



#### 返回 Promise 表达完成

**Promise 完成信号**：是任务函数返回一个 Promise、Gulp 依据其落定状态判断任务成功或失败的做法。

- 判定方式：返回 Promise 后，Gulp 等待其变为已完成或已拒绝。
- 异步函数：标注 async 的函数天然返回 Promise，适合包装不涉及文件流的异步步骤。
- 失败表达：抛出异常或返回已拒绝的 Promise 会让任务失败并终止串联流程。
- 返回值限制：返回普通值不构成完成信号，任务会被判定为未声明异步。
- 组合使用：Promise 任务可以与流任务混排在同一条串行链里。

```js
const { src, dest } = require("gulp");
const { rm, mkdir } = require("node:fs/promises");

async function prepareDirs() {
  await rm("dist", { recursive: true, force: true });
  await mkdir("dist/assets", { recursive: true });
}

function copyAssets() {
  return src("src/assets/**/*").pipe(dest("dist/assets"));
}
```

> 返回已拒绝的 Promise 等价于任务失败，串行链停在失败处，后续任务不再执行。

**速记**：async 函数返回 Promise，Gulp 按其落定判断成败，拒绝即中断串联流程。



#### 使用回调参数表达完成

**回调完成信号**：是任务函数声明一个形参、在异步工作结束时调用它，以此告知 Gulp 任务已完成的约定。

- 形参约定：函数最后一个形参为回调，Gulp 调用任务时自动注入。
- 调用时机：全部异步工作结束后调用一次，可传入错误对象表示失败。
- 一次性：回调只应调用一次，重复调用属于错误用法并会触发相应提示。
- 形参命名：按习惯取名为 done，明确的形参名便于阅读。
- 错误传递：传入 Error 实例即宣告失败，错误会向上冒泡给组合函数。

```js
const { series } = require("gulp");
const { execFile } = require("node:child_process");

function runPostBuild(done) {
  execFile("node", ["scripts/postbuild.js"], (error) => {
    // 传入错误对象即任务失败
    done(error);
  });
}

exports.verify = series(runPostBuild);
```

> [!IMPORTANT]
> **重要内容**：任务既不返回流或 Promise，也不声明回调形参时，Gulp 会立刻把任务判定为已完成并提示缺少异步完成信号，串行链的后续步骤随即在错误前提下执行。

**速记**：声明回调形参并在结束时调用即完成信号，传入错误对象表示失败。



### 编排实践

任务线是按使用场景划分的入口组合。本节给出开发、构建、发布三条线的结构与各自的约束。

#### 开发任务线

**开发任务线**：是先做一次全量编译、再并行启动监听与本地服务的编排，目标是尽快看到改动效果。

- 阶段结构：首次全量编译结束后，监听与本地服务同时启动。
- 顺序要求：监听必须在首次编译之后启动，否则会对刚写出的产物重复处理。
- 监听范围：只监听源目录，不监听产物目录，避免写回触发循环（详见本主题第 50 篇）。
- 服务任务：长期运行的任务不报告完成，进程因它而保持存活。
- 退出处理：收到中断信号时关闭服务与监听，避免占用端口与文件句柄。

```js
const { series, parallel } = require("gulp");

// startServer 由所选的本地服务插件提供，此处只体现它在编排中的位置
function serveSources() {
  return startServer({ root: "dist", port: 3000 });
}

exports.dev = series(
  parallel(buildScripts, buildStyles, copyPages),
  parallel(watchSources, serveSources)
);
```

> 开发线只追求反馈速度，不压缩、不加指纹，产物形态与发布线刻意不同。

**速记**：开发线先全量编译，再并行启动监听与本地服务，长期任务不报告完成。



#### 构建任务线

**构建任务线**：是从清理开始、依次完成编译、优化与指纹的一次性编排，任何时刻都可在干净目录上重跑。

- 阶段顺序：清理、编译、优化、指纹四段串行，编译段内按资源类型并发。
- 可重复性：不依赖上一次的产物，每次执行都从空目录开始。
- 幂等性：同一份输入重复执行得到相同产物，指纹步骤据此稳定。
- 失败即停：任一步失败即中止后续，保留日志便于定位。
- 与开发线共用：编译类小任务在两条线里复用同一份实现。

```js
const { series, parallel } = require("gulp");

exports.build = series(
  cleanDist,
  parallel(buildScripts, buildStyles, copyPages, copyAssets),
  optimizeImages,
  hashAssets
);
```

> [!NOTE]
> **提醒内容**：构建线必须从清理开始，跳过清理会让上一次的残留文件混进本次产物，指纹与上传清单随之失真。

**速记**：构建线按清理、编译、优化、指纹分段，可重复执行且失败即停。



#### 发布任务线

**发布任务线**：是以构建线为前置、包含产物校验与上传的独立入口，供有线上影响的动作单独触发。

- 前置条件：构建线完成并通过校验，才允许进入上传阶段。
- 包含内容：产物校验、版本信息写入、上传与结果通知。
- 可重试：上传步骤应支持重试，并在失败时给出回滚指引。
- 人工确认：涉及线上环境的步骤放在独立入口，不并入普通构建。
- 手动触发：发布入口不暴露给默认任务，避免误触。

```js
const { series } = require("gulp");

exports.release = series(exports.build, verifyOutput, uploadDist);

exports.default = exports.build;
```

> [!TIP]
> **建议内容**：把上传与部署留在独立的 release 入口、让 default 只指向 build，可以显著降低误发布概率，也让日常构建保持无副作用。

**速记**：发布线以构建线为前置，独立入口、可重试，默认任务不指向它。
