## webpack 的样式工程

### 样式处理链路回顾

样式在 webpack 里不是被独立处理的资源，而是先转成 JavaScript 模块再进入产物图；这条链路的走向决定了样式能否被提取、能否热更新。loader 的入门清单见本主题第 9 篇，本节只讲工程侧的链路与取向。

#### 从入口到样式产物的链路

**样式处理链路**：是样式文件被导入语句引用后，经多个 loader 依次转换，最终由产物生成阶段决定内联或抽离的完整路径。

- 起点：JavaScript 或模板中通过导入语句引用样式文件，样式随即登记为模块依赖。
- 解析：css-loader 处理样式内部的导入与资源引用，把样式转成可被脚本消费的模块。
- 落地：style-loader 把样式写入页面，提取插件把样式汇总为独立文件，二者互斥。
- 前置转换：预处理器 loader 在 css-loader 之前执行，把扩展语法转成标准样式。
- 分流点：开发期与生产期走不同落地方式，配置需按环境区分。

```js
// 入口中的样式引用，链路由此开始
import "./styles/reset.css";
import "./styles/theme.scss";
```

> 只有被导入语句引用到的样式文件才进入依赖图，未被引用的样式不会出现在产物中。

**速记**：样式从导入语句起步，经预处理器与 css-loader 解析，最后由落地 loader 决定内联或抽离。



#### loader 的执行方向与顺序

**执行方向**：是配置数组中多个 loader 从右向左依次应用的规则，位于最右侧的 loader 最先拿到源文件内容。

- 方向：数组右侧的 loader 先执行，其返回值交给左侧的 loader，形成管道。
- 样式链顺序：从右到左依次为预处理器 loader、postcss-loader、css-loader、落地 loader。
- 顺序反例：把 css-loader 放在预处理器之前，扩展语法会因无法解析而直接报错。
- 与 enforce 的关系：normal 阶段按上述方向执行，pre 与 post 阶段分别提前与延后。
- 排查方法：在自定义 loader 中打印输入内容，确认每一步拿到的东西符合预期。

```js
{
  test: /\.scss$/,
  // 右侧先执行，顺序为 sass-loader、postcss-loader、css-loader、style-loader
  use: ["style-loader", "css-loader", "postcss-loader", "sass-loader"]
}
```

> [!IMPORTANT]
> **重要内容**：loader 顺序写反不会报出明确的顺序错误，而是以语法解析失败或选择器失效的形式暴露，接入新的样式类型时应先核对顺序。

**速记**：数组最右侧的 loader 先执行，样式链固定为预处理器、postcss、css-loader、落地 loader。



#### 注入与提取两种落地方式

**样式注入**：是 style-loader 在运行时把样式写入页面文档的方式；**样式提取**：是把样式汇总为独立文件、由页面以链接方式加载的方式。

- 注入特点：样式随脚本执行写入，改动后无需重新加载页面，热更新链路完整。
- 提取特点：样式与脚本可并行加载，避免脚本执行前的样式缺失，产物更利于缓存。
- 选择依据：开发期偏注入以换取热更新，生产期偏提取以换取加载性能。
- 切换方式：按环境分别配置落地 loader，用条件判断在配置中二选一。
- 内容一致：两种方式产出的样式内容相同，差异只在加载时机与缓存粒度。

```js
module.exports = (env) => ({
  module: {
    rules: [
      {
        test: /\.css$/,
        use: [env.production ? MiniCssExtractPlugin.loader : "style-loader", "css-loader"]
      }
    ]
  }
});
```

> 两种方式不能同时作用于同一类样式文件，配置时按环境明确二选一，不要在同一数组里并列。

**速记**：开发期用注入换取热更新，生产期用提取换取并行加载与更稳的缓存。



### 样式提取与压缩

开发期追求的即时反馈与生产期追求的加载性能方向相反，提取与压缩正是这对矛盾的落点。本节讲提取插件的接入、生产压缩，以及提取与热更新之间的取舍。

#### 提取插件的接入与常用选项

**样式提取插件**：是把多个样式模块汇总为独立文件的 webpack 插件，通过替换落地 loader 接管样式内容并交给产物生成阶段。

- 安装与引入：作为开发依赖安装，在配置中引入后放入 plugins 数组。
- 替换 loader：把 style-loader 换成插件提供的 loader，其余 loader 的位置不变。
- 命名模板：用占位符控制输出文件名，配合内容哈希获得稳定的缓存粒度。
- 汇总范围：默认把所有样式汇总为一个文件，可按入口或代码块拆分。
- 引用注入：插件可与模板插件配合，把生成的文件自动挂到页面中。
- 作用对象：只接管通过导入语句引用的样式，页面内联样式不受影响。

```js
const MiniCssExtractPlugin = require("mini-css-extract-plugin");

module.exports = {
  module: {
    rules: [
      { test: /\.css$/, use: [MiniCssExtractPlugin.loader, "css-loader"] }
    ]
  },
  plugins: [
    new MiniCssExtractPlugin({
      filename: "css/[name].[contenthash:8].css"
    })
  ]
};
```

> [!TIP]
> **建议内容**：在文件名中加入内容哈希，可以让样式文件的缓存粒度与内容一致，内容不变时命中旧缓存、改动后自动失效。

**速记**：提取插件替换落地 loader 并汇总样式，用命名模板与内容哈希控制产物与缓存。



#### 生产环境的样式压缩

**样式压缩**：是在产物生成阶段移除空白、注释与冗余规则以缩短样式文件体积的处理，由压缩插件在优化阶段完成。

- 接入位置：放在 optimization.minimizer 中，替换或追加默认的压缩设置。
- 生效条件：生产模式下需要显式指定样式压缩插件才会压缩样式。
- 压缩范围：空白与注释、冗余分号、重复规则以及可合并的简写属性。
- 风险点：激进的压缩选项可能改变层叠行为，需要回归验证视觉结果。
- 调试衔接：压缩会让调试信息与源码错位，source map 策略见本主题第 15 篇。

```js
const CssMinimizerPlugin = require("css-minimizer-webpack-plugin");

module.exports = {
  optimization: {
    minimize: true,
    // 保留默认压缩器，并追加样式压缩
    minimizer: ["...", new CssMinimizerPlugin()]
  }
};
```

> 压缩只减少传输体积、不改变样式语义，出现视觉差异时应优先怀疑压缩选项而非源码。

**速记**：样式压缩在优化阶段完成、需显式配置压缩插件，激进选项要做视觉回归。



#### 提取与 HMR 的取舍

**热更新冲突**：是样式被提取为独立文件后，模块替换无法再把新样式注入页面、只能退回整页刷新的现象。

- 冲突成因：提取后的样式不再由 JavaScript 模块持有，替换模块不会改写已加载的文件。
- 常见做法：开发期用注入、生产期用提取，两套落地方式按环境隔离。
- 折中方案：部分配置支持在开发期关闭提取，按插件文档开启即可保留样式热更新。
- 后果表现：样式改动触发整页刷新，页面状态丢失，调试体验明显下降。
- 验证方式：改动样式后观察页面是否整页刷新，即可判断当前用的是哪种落地方式。

```js
// 按环境选择落地 loader，开发期不启用提取
const isProduction = process.env.NODE_ENV === "production";
const styleLoader = isProduction ? MiniCssExtractPlugin.loader : "style-loader";
```

> [!CAUTION]
> **注意内容**：在开发配置中启用提取，会让样式热更新静默退化为整页刷新，且不会有任何报错提示，只能在改动样式时才察觉。

**速记**：提取会切断样式热更新，开发期注入、生产期提取是最稳的分工。



### CSS 模块化与作用域隔离

全局选择器在大型项目里会互相污染，模块化通过为类名生成唯一标识，把作用域收敛到单个文件。本节讲开启方式、局部与全局的边界，以及组合与命名约定。

#### modules 选项的开启方式

**样式模块化（CSS Modules）**：是把样式文件中的类名默认视为局部、导入后返回类名映射的写法，用于隔离不同文件的选择器。

- 开启方式：在 css-loader 的选项对象中把 modules 设为真，或按文件名后缀条件开启。
- 导入结果：导入得到的是原始类名到实际类名的映射对象，使用时取属性拼接到元素上。
- 命名生成：局部标识符默认由哈希与原始类名组合，可在命名模板中约定格式。
- 适用范围：只影响类名与标识符选择器，标签选择器与全局声明不受约束。
- 预处理器并用：模块化由 css-loader 承担，预处理器只做语法转换，二者不冲突。

```css
/* 样式文件中直接写类名，实际名称由构建生成 */
.cardTitle {
  font-size: 18px;
}

.cardWrapper .cardTitle {
  margin-bottom: 8px;
}
```

```js
import styles from "./card.module.css";

// 导入得到类名映射，取属性拼接到元素上
element.className = styles.cardTitle;
```

> 导入得到的是映射对象而非字符串，把它当成字符串直接使用会得到未定义的类名。

**速记**：模块化在 css-loader 层开启，导入得到类名映射，实际标识符由构建生成。



#### 局部作用域与全局样式的边界

**局部作用域**：是模块化默认把类名视为本文件私有的行为；**全局作用域**：是用显式标记让类名保持原名、可被任意文件命中的写法。

- 默认局部：模块化开启后，未被标记的类名一律加上哈希后缀。
- 全局声明：用 global 包裹的规则保持原始类名，供第三方库或动态拼接使用。
- 逃逸写法：为单条规则加全局标记，适合需要覆盖外部库样式的场景。
- 外部样式：来自依赖包的样式文件通常不启用模块化，避免类名被改写。
- 混合风险：全局与局部混用时，哈希后缀会让按类名查找元素变得不可靠。

```css
/* 全局声明保持原始类名，同时限定容器范围 */
:global(.vendorButton) {
  border-radius: 4px;
}
```

> 需要覆盖第三方库样式时，把对应选择器标为全局，并限定容器范围，避免污染其他区域。

**速记**：默认局部、显式全局，指向第三方库的样式应保持原名并限定范围。



#### 组合与命名约定

**组合（composes）**：是模块化中把另一个类的声明并入当前类的写法，用于复用声明而不必重复书写或依赖继承。

- 本文件组合：在当前类中写 composes 后接目标类名，声明在编译期合并。
- 跨文件组合：目标可指向其他模块，写作来源路径加类名。
- 与继承的区别：组合是声明层面的合并，元素上只需挂一个类名。
- 命名约定：常见做法是按组件与用途命名，如容器类与状态类分开书写。
- 可读性代价：哈希后缀让浏览器中的类名难以对应源码，需借 source map 定位。

```css
.baseButton {
  padding: 6px 16px;
  border-radius: 4px;
}

.primaryButton {
  composes: baseButton;
  background: #1677ff;
  color: #fff;
}
```

> [!TIP]
> **建议内容**：组合只用于纯样式的声明复用，语义与结构仍由元素自身承担，避免组合层数过深导致排查困难。

**速记**：组合在编译期合并声明，跨文件需写来源路径，命名按组件与用途区分。



### 预处理器与 PostCSS 接入

原生样式缺少变量、嵌套与兼容性处理，预处理器和 PostCSS 分别在语法层与后处理层补齐。本节只讲构建期如何接入与配置透传，语法本身见 前端/CSS 主题。

#### Sass 的接入链路

**预处理器 loader**：是把扩展语法的样式文件编译为标准样式的 loader，位置固定在 css-loader 的右侧。

- 安装：同时安装预处理器实现与对应的 loader，两者的版本需匹配。
- 规则位置：在 use 数组中位于 css-loader 右侧、紧邻源文件。
- 选项透传：通过选项对象把实现包名、附加数据与输出风格传给编译器。
- 模块引入：样式内的部分文件与变量文件由预处理器自己解析，不走 webpack 解析。
- 共享变量：需要跨端共享的变量可另建配置文件，供样式与脚本各自读取。

```js
{
  test: /\.scss$/,
  use: [
    "style-loader",
    "css-loader",
    {
      loader: "sass-loader",
      options: {
        // 实现包名与其他选项按所用实现包的文档填写
        additionalData: "$radius: 4px;"
      }
    }
  ]
}
```

> 预处理器自己解析样式内部的导入，因此这些路径不受 resolve.alias 影响，别名写法与脚本不同。

**速记**：预处理器 loader 位于 css-loader 右侧，用选项对象透传设置，样式内导入不走 webpack 解析。



#### PostCSS 插件的串联位置

**PostCSS**：是把样式解析为语法树、由插件依次改写再序列化的后处理工具，在 webpack 中以 postcss-loader 的形式接入。

- 位置：位于 css-loader 左侧、预处理器右侧，负责处理已编译的标准样式。
- 配置来源：插件清单写在独立的 PostCSS 配置文件中，由 loader 自动查找。
- 插件顺序：按数组顺序依次执行，顺序会影响前缀与降级的最终结果。
- 与预处理器的分工：预处理器管扩展语法，PostCSS 管兼容性与规范化。
- 生效范围：同时作用于原生样式与预处理器输出，接入一次即覆盖全部样式。

```js
// PostCSS 配置文件的常见形态
module.exports = {
  plugins: [
    require("autoprefixer")
  ]
};
```

> [!NOTE]
> **提醒内容**：PostCSS 插件的执行顺序由配置数组决定，颠倒顺序可能让前缀或降级结果与预期不符。

**速记**：PostCSS 经 postcss-loader 接入，位于预处理器与 css-loader 之间，插件顺序影响结果。



#### 浏览器前缀与目标浏览器声明

**浏览器前缀**：是厂商为实验性属性添加的标识；**目标浏览器声明**：是用查询语法描述需要兼容的浏览器范围、供前缀与降级工具读取的配置。

- 声明位置：写在项目清单的对应字段中，前缀工具与降级工具都读取它。
- 生效范围：同一份声明同时影响脚本降级与样式前缀，两处应保持一致。
- 前缀策略：由工具按声明自动添加，不再手写前缀，避免遗漏与冗余。
- 查询粒度：可按使用占比、最后若干版本或指定浏览器区间书写。
- 一致性检查：产物中的前缀集合应与声明范围吻合，偏差说明配置未被读取。

```json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead"
  ]
}
```

> 目标浏览器声明的完整查询语法与降级策略见本主题第 11 篇，此处只处理它在前缀生成中的作用。

**速记**：前缀由工具按目标浏览器声明自动添加，一份声明同时驱动脚本降级与样式前缀。



### 样式产物体积与常见问题

样式问题往往不在语法，而在依赖关系与执行时机。本节列出三类高频问题：重复引入、顺序错乱与开发期闪烁，排查的通用方法见本主题第 16 篇。

#### 重复引入与依赖共用

**样式重复引入**：是同一份样式内容被多条路径分别引用、在产物中出现多份副本的情形。

- 成因：同一基础样式被多个组件或入口直接引用，且落地阶段未做去重。
- 表现：产物中同类声明重复出现，体积增大，覆盖关系变得难以预测。
- 治理方式：把基础样式收敛到单一位置统一引入，其余文件只引局部样式。
- 与分包的关系：把样式按入口分流可减少单文件体积，但要注意公共部分的归属。
- 核对手段：在产物中检索特征声明，确认其出现次数与来源文件。

```bash
# 统计产物中某条特征声明的出现次数
grep -rc "border-box" dist/css
```

> 样式去重依赖引用结构，构建工具不会自动判断两份样式是否等价，收敛引入位置才是根本手段。

**速记**：重复引入源于多路径引用同一基础样式，收敛引入位置并在产物中核对出现次数。



#### 样式顺序错乱

**样式顺序**：是多个样式文件进入最终产物时的排列次序，由模块依赖图的遍历结果决定，而非源文件在配置中的书写顺序。

- 决定因素：导入语句的位置与模块图遍历顺序共同决定样式的排列。
- 常见后果：后加载的样式覆盖先加载的样式，与源码书写的意图相反。
- 局部修法：调整导入语句的位置，或在必要处提高选择器的特异性。
- 结构修法：让样式依赖关系与组件依赖关系一致，避免跨层引用。
- 覆盖面：提取后的顺序在产物生成阶段固化，运行时无法再调整。

```js
// 基础样式在前、覆盖样式在后，顺序随导入语句确定
import "./styles/reset.css";
import "./styles/theme.css";
import "./styles/overrides.css";
```

> [!WARNING]
> **警告内容**：依赖运行时加载顺序来保证覆盖关系，一旦导入位置调整或分包变化，覆盖结果就会反转，正确性无法长期保证。

**速记**：样式顺序由模块图遍历决定，覆盖关系应靠结构保证而非导入的偶然顺序。



#### 开发期样式闪烁

**样式闪烁（FOUC）**：是页面在样式生效前以无样式状态短暂渲染的现象，常见于样式由脚本注入的开发期。

- 成因：样式随脚本执行才写入页面，脚本加载与执行期间元素尚无样式。
- 开发期表现：热更新与首次加载时较明显，生产期通常由提取方式规避。
- 缓解方式：把首屏关键样式单独提取，或在页面中优先加载。
- 提取的作用：样式以链接方式在文档头部加载，解析前不会渲染无样式内容。
- 与缓存的关系：提取文件的缓存粒度更稳定，闪现在构建缓存变化后更易出现。

```html
<!-- 关键样式以链接形式置于文档头部，先于脚本加载 -->
<link rel="stylesheet" href="/css/critical.css" />
<script src="/js/app.js" defer></script>
```

> [!NOTE]
> **提醒内容**：开发期的样式闪烁多由注入方式导致，属于预期内的开发体验差异，不应与生产环境的加载性能问题混为一谈。

**速记**：样式闪烁源于样式随脚本注入，提取关键样式并置于文档头部可规避。
