## Gulp 与 webpack 协作

Gulp 与 webpack 不是替代关系：前者负责按文件批量加工，后者负责按模块依赖打包。两者并用时，难点不在工具本身，而在边界、调用方式与产物衔接。本篇只讲这些协作问题；webpack 的配置项、加载器与插件细节见本主题第 8 篇至第 10 篇与第 17 篇至第 25 篇，Gulp 的任务编排见第 52 篇。

### 职责划分

职责划分的判据只有一条：处理对象之间是否存在模块引用关系。本节按这一条线把两侧的工作切开，并给出边界的判定路径。

#### 模块打包交给 webpack

**模块打包**：是以入口为起点递归分析模块依赖、产出可被浏览器加载的产物的工作，由 webpack 承担。

- 承担内容：入口解析、依赖图构建、加载器转换、代码分割与产物命名。
- 判断标志：被处理文件之间存在 import 或 require 关系时属于这一侧。
- 配置归属：webpack 的配置与加载器插件全部留在打包侧，Gulp 不介入其内部规则。
- 产物形态：产出若干打包文件与一份资源清单，供后续步骤引用。
- 与 Gulp 的接口：Gulp 只负责触发打包与接收结果，不改写打包规则。

```js
// webpack.config.js 打包侧自持全部模块处理规则，字段含义见本主题第 8 篇
const path = require("node:path");

module.exports = {
  mode: "production",
  entry: { app: "./src/entries/app.js" },
  output: {
    path: path.resolve(__dirname, "dist/assets"),
    filename: "[name].[contenthash:8].js",
  },
};
```

> 边界可以压缩成一句话：文件之间需要模块解析就归 webpack，只需要搬运与加工就归 Gulp。

**速记**：有模块依赖关系的交给 webpack，其配置与加载器插件全部留在打包侧。



#### 静态资源交给 Gulp

**静态资源加工**：是对不参与模块解析的文件做拷贝、压缩、改名与注入等批处理的工作，由 Gulp 的流式管道完成。

- 典型对象：图片、字体、图标、纯页面文件、站点地图与验证文件。
- 处理特点：以文件为单位批量处理，步骤之间用管道串联。
- 任务组织：每条流水线一个任务，再用系列与并行组合，见本主题第 52 篇。
- 与打包的差别：不做依赖分析，不需要入口概念，也不需要运行时包装。
- 输出目标：与打包产物写入同一产物根目录下的不同子目录。

```js
const { src, dest } = require("gulp");

function copyFonts() {
  return src("src/fonts/**/*.{woff2,woff}").pipe(dest("dist/assets/fonts"));
}

function copyStatics() {
  return src(["src/robots.txt", "src/sitemap.xml"]).pipe(dest("dist"));
}
```

> 落在两侧的文件最容易出问题的不是处理逻辑，而是产物路径：两侧必须约定同一个产物根目录与互不重叠的子目录。

**速记**：不需要模块解析的文件批量加工交给 Gulp，输出到与打包产物并列的子目录。



#### 边界的判定依据

**边界判定**：是按文件是否被模块系统引用、处理是否需要依赖信息来判断归属哪一侧的方法。

- 判定问题一：该文件是否被 import 或 require 引用，是则归 webpack。
- 判定问题二：处理是否需要知道依赖关系，需要则归 webpack。
- 判定问题三：处理是否只是按规则批量变换文件，是则归 Gulp。
- 灰色地带：被模块引用的图片若按体积内联，属于打包器的资源模块能力，见本主题第 19 篇。
- 重复风险：同一个文件被两侧同时处理时，产物中出现两份内容相同而命名不同的文件。

```text
文件是否需要模块解析？
  ├─ 是 ──> webpack：入口 + 依赖图 + 加载器
  └─ 否 ──> Gulp：glob + 管道 + 写出
```

> [!CAUTION]
> **注意内容**：同一个文件若既被打包侧的加载器引用、又被 Gulp 的拷贝任务处理，产物里会出现两份内容相同而命名不同的文件，指纹与页面引用随即对不上，必须先划清归属再写任务。

**速记**：按是否被模块引用、是否需要依赖信息三问判定归属，避免同一文件被两侧重复处理。



### 在 Gulp 中调用 webpack

调用打包器有两条路：直接使用其 Node 接口，或使用把输出包装为流的社区封装。本节以直接调用为主，说明一次性构建、监听构建与结果接收三件事。

#### 直接调用打包函数

**打包调用**：是在 gulpfile 中引入打包函数、传入配置对象并用回调接收构建结果的做法。

- 调用形式：打包函数接收配置对象与回调，回调拿到错误对象与统计对象。
- 完成信号：把调用包进 Promise 或以回调形式表达，任务才能正确报告完成。
- 配置来源：配置文件由打包侧维护，Gulp 只读取并传入。
- 结果判定：通过统计对象判断有无编译错误，而不是只看回调的错误参数。
- 失败表达：编译出错时让任务失败，串行链停止而不是继续处理残缺产物。

```js
const { series } = require("gulp");
const webpack = require("webpack");
const webpackConfig = require("./webpack.config.js");

function bundleScripts() {
  return new Promise((resolve, reject) => {
    webpack(webpackConfig, (error, stats) => {
      if (error) {
        reject(error);
        return;
      }
      if (stats.hasErrors()) {
        reject(new Error(stats.toString({ all: false, errors: true })));
        return;
      }
      resolve();
    });
  });
}

exports.build = series(bundleScripts);
```

> [!IMPORTANT]
> **重要内容**：回调的错误参数只表示打包过程本身失败，编译错误位于统计对象内部，只判断错误参数会让带编译错误的产物被当作成功继续流向后续步骤。

**速记**：用打包函数加回调调用并包成 Promise，错误参数与统计对象要分别判断。



#### 开发模式下的多次构建

**监听构建（watch）**：是让打包进程常驻、文件变化后自动重跑的构建方式，由打包器的监听接口发起。

- 接口形式：以监听选项与回调调用编译器的监听方法，返回可关闭的监听对象。
- 首次构建：启动后立即执行一次完整构建，回调在每次构建后被调用。
- 持续运行：监听期间进程保持存活，任务不报告完成，与长期运行的服务任务一致。
- 关闭方式：保存监听对象，在中断信号到达时关闭，避免文件句柄泄漏。
- 与 Gulp 监听的分工：模块侧变化由打包器监听，资源侧变化由 Gulp 监听，见本主题第 50 篇。

```js
const webpack = require("webpack");
const webpackConfig = require("./webpack.config.js");

function watchScripts(done) {
  const compiler = webpack(webpackConfig);
  const watching = compiler.watch({ aggregateTimeout: 300 }, (error, stats) => {
    if (error || stats.hasErrors()) {
      console.error("[webpack]", error || stats.toString({ all: false, errors: true }));
      return; // 监听模式不退出，等待下一次变更
    }
    console.log("[webpack] 构建完成");
  });
  process.on("SIGINT", () => watching.close(() => done()));
}
```

> 开发期的打包错误只打印不终止进程，否则一次语法错误就会让整个监听退出，改回正确写法也不会自动恢复。

**速记**：用编译器的监听接口做常驻构建，首次立即构建、变更后重跑，中断时关闭监听对象。



#### 构建结果与错误的接收

**结果接收**：是把统计对象中的错误、警告与产物清单读出来，转成 Gulp 侧的失败判定与日志输出的做法。

- 错误读取：用统计对象的错误判断与错误列表获取问题条目。
- 警告处理：警告默认不终止流程，但应打印出来供排查。
- 产物清单：统计对象的资源列表给出本次写出的文件名与体积。
- 日志格式：转字符串时只选择需要的字段，避免输出整棵模块树。
- 传递方式：把清单写入文件或保存在模块变量中，供指纹与注入步骤使用。

```js
function bundleForRelease() {
  return new Promise((resolve, reject) => {
    webpack(webpackConfig, (error, stats) => {
      if (error) {
        reject(error);
        return;
      }
      if (stats.hasErrors()) {
        reject(new Error(stats.toString({ errors: true, warnings: false })));
        return;
      }
      const report = stats.toJson({ all: false, assets: true, warnings: true });
      if (report.warnings.length > 0) {
        console.warn("[webpack] 警告", report.warnings.length, "条");
      }
      resolve(report);
    });
  });
}
```

> 资源清单是两侧交接的凭据：Gulp 凭它决定后续要处理哪些文件，而不是靠猜文件名或目录通配。

**速记**：从统计对象读错误、警告与资源清单，错误转成任务失败，清单留给后续步骤。



### 产物衔接与顺序

两侧共用产物目录时，顺序与路径约定决定协作是否稳定。本节说明处理次序、目录划分与清单对接三件事。

#### 先打包后处理

**处理顺序**：是让打包先产出文件、Gulp 再对产物做注入与指纹的固定次序。

- 顺序依据：后续处理依赖打包产物的真实文件名，其中包含内容哈希。
- 组合写法：用串行把打包任务排在资源处理任务之前。
- 禁止并行：两侧写同一目录且存在读写关系时，并行会读到不完整的产物。
- 例外情况：与打包无引用关系的静态资源可以先行，但仍建议保持固定次序。
- 常见错误：跳过串行直接并行，表现为指纹步骤偶尔拿不到入口文件。

```js
const { series, parallel } = require("gulp");

exports.build = series(
  cleanDist,
  parallel(bundleScripts, buildStyles, copyStatics),
  injectBundle,
  hashAndRewrite
);
```

> [!IMPORTANT]
> **重要内容**：注入与指纹步骤必须排在打包任务之后并与之串行，任何形式的并行都可能让它们读到上一次的清单或尚未写出的文件，且失败是间歇性的、难以复现。

**速记**：打包先、注入与指纹后，读写同一目录的两侧一律串行。



#### 产物路径与引用约定

**路径约定**：是两侧共同遵守的产物根目录、子目录划分与引用写法。

- 根目录统一：两侧写入同一个产物根目录，避免发布时还要合并两个位置。
- 子目录划分：打包产物、样式、图片、字体各占子目录，避免同名覆盖。
- 公共路径：打包侧的公共路径前缀与 Gulp 输出的相对位置必须一致。
- 引用写法：页面引用产物时写成相对产物根目录的路径，便于整体搬迁。
- 目录清理：清理任务只清空整个产物根目录，两侧不各自清理局部。

```text
dist/
  index.html          <- Gulp 注入与压缩
  assets/
    app.8f3a1c2d.js   <- webpack 打包
    app.4b7e0c91.css  <- Gulp 样式流水线
    fonts/            <- Gulp 拷贝
    images/           <- Gulp 处理
```

> 公共路径与目录层级一旦错位，构建会成功而浏览器里全部 404，这类问题只能靠打开产物页面验证。

**速记**：两侧共用一个产物根目录、各占子目录，公共路径前缀与目录层级必须对齐。



#### 清单与入口的对接

**清单对接**：是把打包产物的资源清单交给注入任务、由注入任务把带哈希的文件名写进页面的衔接方式。

- 清单来源：打包侧写出的清单文件，或统计对象中的资源列表。
- 读取方式：注入任务读取清单，按逻辑名查到带哈希的实际文件名。
- 页面注入：把查到的路径写入页面模板中的脚本与样式引用位置。
- 顺序保证：清单必须来自本次构建，读取上一次的清单会引用到不存在的文件。
- 校验手段：注入完成后检查每条引用在产物目录中确实存在。

```js
const { src, dest } = require("gulp");
const { readFile } = require("node:fs/promises");
const { Transform } = require("node:stream");

function injectEntryPaths(manifest) {
  return new Transform({
    objectMode: true,
    transform(file, encoding, callback) {
      if (file.isBuffer()) {
        const page = file.contents.toString();
        file.contents = Buffer.from(page.replace("__ENTRY_JS__", "/assets/" + manifest["app.js"]));
      }
      callback(null, file);
    },
  });
}

async function injectBundle() {
  const manifest = JSON.parse(await readFile("dist/assets/manifest.json", "utf8"));
  return src("dist/**/*.html").pipe(injectEntryPaths(manifest)).pipe(dest("dist"));
}
```

> 清单的意义在于把「文件名带哈希」这件事限制在注入步骤内部，页面模板只写逻辑名，模板因此不必随哈希变化而改动。

**速记**：注入任务按清单把逻辑名换成带哈希的文件名，清单必须来自本次构建。



### 开发与生产两条流水线

两期的目标不同：开发期要求快速反馈，生产期要求产物可长期缓存。本节说明两期的编排差异与配置分离方式。

#### 开发期的分工与转发

**开发期流水线**：是打包常驻监听、静态资源由 Gulp 监听、浏览器刷新由同一个触发点统一引起的安排。

- 模块侧：打包器的监听模式负责重跑打包。
- 资源侧：Gulp 的监听负责重跑对应资源的处理任务。
- 刷新触发：由开发服务器或刷新能力触发页面重载，两类变更接入同一个触发点。
- 产物目录：开发期可写入临时目录，需与生产产物目录区分开。
- 速度取舍：开发期不做压缩与指纹，缩短单次重建时间。

```js
exports.dev = series(
  parallel(buildStyles, copyStatics),
  parallel(watchScripts, watchStyles, serveSources)
);
```

> [!NOTE]
> **提醒内容**：开发期把打包产物写入内存时，Gulp 的指纹与页面注入任务读不到这些文件，因此指纹与注入只放在生产线上执行，不要加进开发线。

**速记**：开发期由打包器监听模块、Gulp 监听资源、统一触发刷新，不做压缩与指纹。



#### 生产期的一次性构建

**生产期流水线**：是清理产物目录后依次打包、处理资源、注入、指纹并校验的一次性流程。

- 触发方式：由流水线命令触发一次，构建结束即退出。
- 无监听：不启动任何监听与本地服务，避免进程无法退出。
- 生产选项：压缩、指纹与按环境注入常量在这条线上开启。
- 校验步骤：构建结束后检查入口文件与清单文件的完整性。
- 失败处理：任一步失败即中止并返回非零退出码。

```js
exports.build = series(
  cleanDist,
  parallel(bundleScripts, buildStyles, optimizeImages, copyFonts),
  injectBundle,
  hashAndRewrite,
  verifyOutput
);
```

> 生产线的每一步都应能从干净目录重跑，否则产物会隐含「上一次构建留下的状态」。

**速记**：生产线一次性执行，无监听、开压缩与指纹，失败即返回非零退出码。



#### 两期的配置分离

**配置分离**：是按构建期次派生两套打包配置、避免开发专用选项进入生产产物的做法。

- 派生方式：打包配置写成接收环境的函数或按环境导出多个对象，见本主题第 17 篇。
- 开关项：开发期保留可读模块标识且不压缩，生产期开启压缩与更细的分割。
- 常量注入：环境相关常量在两期取不同值，不得共用一个写死的值。
- Gulp 侧对应：两期用不同的任务线表达，而不是在任务内部写条件分支。
- 校验方式：生产构建后用资源清单核对是否混入开发专用项。

```js
const { series, parallel } = require("gulp");

exports.dev = series(parallel(bundleInWatchMode, buildStyles), serveSources);
exports.build = series(cleanDist, parallel(bundleForRelease, buildStyles), hashAndRewrite);
```

> 两期差异集中到配置派生的那一处，Gulp 侧只切换调用的任务，避免同一个任务内部塞满环境判断。

**速记**：打包配置按环境派生，Gulp 侧用不同任务线切换两期，不在任务内写环境分支。



### 与迁移方案的取舍

两者并用的前提是边界清晰。本节只判断这种并用本身还有没有收益，整体迁移路径与时机的完整讨论见本主题第 56 篇。

#### 仍然值得并用的情形

**并用场景**：是同时需要模块打包与大量非模块资源批处理的工程，用打包器管模块、用 Gulp 管资源的组合方式。

- 遗留项目：已有大量 Gulp 任务处理图片、字体与多语言页面，改造收益低于成本。
- 定制流水线：构建步骤包含与外部系统交互、批量生成文件等打包器不覆盖的动作。
- 静态站点：页面由模板与数据批量生成，再由打包器处理其中的脚本与样式。
- 过渡阶段：新代码用现代工具，老任务分批搬迁，过渡期内两者并存。
- 前提条件：两侧的目录、命令与触发方式已经分开，维护成本可控。

```text
并用收益较高的组合
  模块依赖复杂  +  存在大量非模块资源批处理
  模块依赖复杂  +  构建步骤需要调用外部程序
  模块依赖复杂  +  已有可用的 Gulp 任务资产
```

> 判断标准不是「能否做到」，而是「并存的边界是否已经清晰」，边界清晰时并用是低成本方案。

**速记**：遗留资产、定制流水线与静态站点三类场景并用收益最高，前提是边界清晰。



#### 应当结束并用的情形

**结束并用**：是把资源处理也交给打包器或现代构建工具的插件体系、只保留一条构建链路的做法。

- 资源已模块化：图片与字体都通过 import 引用时，打包器的资源模块即可覆盖。
- 步骤可由插件覆盖：压缩、改名与注入都有成熟插件时，另起一条流水线收益有限。
- 两期差异难维护：开发与生产两套编排之间的隐含依赖不断增多。
- 协作成本：需要同时理解流式管道与模块图两套模型，新人上手更慢。
- 路径与时机：完整迁移讨论见本主题第 56 篇，此处只判断并用本身是否还有收益。

```bash
npx gulp build
# 并用期：资源处理走 Gulp
npx webpack --config webpack.config.js
# 收拢期：只保留一条链路，行为更容易预测
```

> [!CAUTION]
> **注意内容**：并用期最危险的状态是两侧都能「大致完成」构建，两条命令都能跑通却产出不同结果，交付前必须明确以哪一条链路为准。

**速记**：资源已模块化、步骤可由插件覆盖时应收拢为一条链路，并用只在收益明确时保留。



#### 并用的成本与退出条件

**并用成本**：是维护两套配置、两套产物规则与两套文档的固定开销，退出条件据此设定。

- 配置成本：两套配置风格不同，排错需要同时掌握两边的心智模型。
- 产物成本：两侧的命名与路径规则需手工对齐，任何一侧变更都要同步。
- 文档成本：构建命令与产物目录要写进项目说明，否则协作时反复踩坑。
- 退出条件：新增的资源处理需求全部能由打包器覆盖时，即停止在 Gulp 侧新增任务。
- 渐进退出：先停止新增任务，再逐个迁移既有任务，最终移除入口链路。

```js
const { series, parallel } = require("gulp");

// 并用期只保留尚未迁移的资源任务，模块打包交由独立的构建命令
exports.build = series(parallel(copyAssets, buildStyles), verifyOutput);
```

> [!TIP]
> **建议内容**：为并用期设定一条可判定的退出条件，例如「连续两次迭代没有新增 Gulp 任务」，条件达成即启动收拢，避免并存状态长期固化。

**速记**：并用成本集中在配置、产物与文档三处，退出以停止新增任务并逐个迁移为路径。
