## ESLint 与 Prettier：代码规范工具链

> [!IMPORTANT]
> **重要内容**：本篇只讲工具怎么配置、怎么接入构建与提交流程，不讲「缩进几个空格、是否书写分号」这类代码风格约定本身；风格取值由团队自行约定，工具只负责执行。

### 静态检查与格式化的分工

**代码规范工具链**：是由静态检查、自动格式化与提交前钩子串联而成的自动化链路，目标是在代码进入仓库之前统一其正确性与外观。

链路的分工是固定的：ESLint 判断代码有没有问题，Prettier 决定代码长什么样，钩子决定这些检查在什么时机运行。

#### ESLint 与 Prettier 的职责边界

**ESLint**：是 JavaScript 与 TypeScript 的静态检查工具，读取源码解析出的抽象语法树（abstract syntax tree，AST），按规则集报告可疑写法并可自动修复其中一部分。

- 检查对象：变量是否未使用、是否误用等号、是否遗忘了 await、是否存在循环依赖等逻辑性问题。
- 可修复范围：带扳手标记的规则可由 eslint --fix 自动改写，其余只能提示人工处理。
- 输出形式：控制台按文件分组列出问题，支持 stylish、json 等格式器（formatter）。

```bash
npx eslint src --max-warnings 0
# /src/utils/parseDate.js
#   3:7  error  'year' is assigned a value but never used  no-unused-vars
# ✖ 1 problem (1 error, 0 warnings)
```

> ESLint 的规则分语法层面与语义层面两类，后者需要完整的类型信息，配置成本更高，本主题第 13 篇后半部给出接入方式。

**速记**：ESLint 管逻辑正确性，靠规则集在语法树上做静态分析。



#### Prettier 的定位与不可配置之处

**Prettier**：是主张观点式（opinionated）的代码格式化器，把源码重新打印成统一外观，几乎不提供风格开关。

- 关注外观：缩进、换行、引号、分号、行宽、尾随逗号等排版问题。
- 少开关：只暴露少量影响可读性判断的选项，团队无需为每个排版细节投票。
- 幂等：同一份输入反复格式化结果一致，适合挂在钩子里自动执行。

```bash
npx prettier --check "src/**/*.{js,ts,vue}"
# Checking formatting...
# [warn] src/main.ts
# [warn] Code style issues found in 1 file. Run Prettier with --write to fix.
```

> Prettier 不读懂变量含义，也不判断逻辑错误；它只保证解析出的语法树被重新打印成同一副样子。

**速记**：Prettier 管外观、开关极少、输出幂等，只做排版不做判断。



#### 工具链组成与最小安装

**最小安装**：是把 ESLint、Prettier 与消解冲突所需的关键依赖装进开发依赖，并为每类工具各生成一份配置文件。

- 必需项：eslint 与 prettier 两个包。
- 关键项：eslint-config-prettier 负责关掉与格式化冲突的规则，是消解冲突的核心一环。
- 触发项：husky 与 lint-staged 负责在提交前只检查改动的文件，详见本篇末节。

```bash
npm install --save-dev eslint prettier eslint-config-prettier
# added 89 packages in 6s
npx eslint --version   # v9.13.0
npx prettier --version # 3.3.3
```

> ESLint 9 起默认使用平面配置（flat config），配置文件名为 eslint.config.js；旧版 .eslintrc 系列在 9 中默认不再读取，见本主题第 13 篇下一节。

**速记**：装 eslint、prettier、eslint-config-prettier 三个包，各配一份文件即可成链。



### 平面配置与规则继承

**平面配置（flat config）**：是从 ESLint 9 起取代 .eslintrc 系列的新配置格式，配置文件导出一个配置对象数组，数组内按顺序合并生效。

配置模型的改变，是把「逐级向上查找 .eslintrc」换成「显式声明每个对象作用于哪些文件」，作用范围全部写在配置里，不再依赖目录位置。

#### eslint.config.js 的平面配置结构

**eslint.config.js**：是 ESLint 的平面配置文件，默认以 ES 模块导出 default 数组，每个数组元素是一个配置对象。

- files：该对象作用的文件匹配模式，省略时作用于所有被检查的文件。
- ignores：忽略项；只写 ignores 而不写 files 的对象是全局忽略。
- languageOptions：ecmaVersion、sourceType 与 globals 等解析环境设置。
- rules：规则名到严重级别的映射。

```js
// eslint.config.js
import js from "@eslint/js";

export default [
  { ignores: ["dist/**", "coverage/**"] },
  js.configs.recommended,
  {
    files: ["src/**/*.js"],
    languageOptions: {
      ecmaVersion: 2024,
      sourceType: "module",
      globals: { window: "readonly", document: "readonly" },
    },
    rules: {
      "no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
      eqeqeq: ["warn", "always"],
    },
  },
];
```

> [!NOTE]
> **提醒内容**：平面配置不再读取 .eslintignore 文件，目录忽略一律写在配置对象的 ignores 字段里，集中一处维护。

**速记**：平面配置是一个对象数组，文件范围由 files 与 ignores 显式声明。



#### 规则级别与选项写法

**规则级别（severity）**：是决定规则命中时以何种强度报告的三档取值，可写英文词也可写数字。

- "off" 或 0：关闭该规则，完全不检查。
- "warn" 或 1：输出警告，默认不影响命令退出码。
- "error" 或 2：输出错误，退出码非零，流水线据此判定失败。
- 附带选项：写成数组，首项为级别，次项为规则选项，可继续追加更多选项。

```js
// 规则级别的四种写法
export default [
  {
    rules: {
      "no-console": "warn",
      "no-debugger": "error",
      "no-unused-vars": 0,
      "max-len": ["error", { code: 120, ignoreUrls: true }],
    },
  },
];
```

> 想让警告在流水线里也阻断合并，运行检查时加 --max-warnings 0，警告数量超过阈值即返回非零退出码。

**速记**：级别取 off、warn、error 或 0、1、2，带选项时写成数组。



#### 配置对象的合并顺序

**配置合并顺序**：是平面配置数组元素的生效次序，越靠后的对象优先级越高，作用于同一文件的同名规则以后写的为准。

- 方向：数组从前往后依次叠加，后面的 rules 覆盖前面的级别与选项。
- 作用域：只有 files 匹配到的对象才参与合并，全局对象对所有文件生效。
- 排查：不确定某条规则最终取值时，用 --print-config 打印指定文件合并后的完整配置。

```bash
npx eslint --print-config src/main.js | head -8
# {
#   "languageOptions": { "sourceType": "module", "ecmaVersion": 2024 },
#   "rules": { "eqeqeq": ["warn", "always"], "no-console": ["warn"] }
# }
```

> 顺序即优先级，这一点与 .eslintrc 时代的 extends 数组方向一致，平面配置只是把「谁覆盖谁」写得更直白。

**速记**：数组从前往后合并，后写的对象覆盖先写的同名规则。



### 插件与共享配置

**插件（plugin）**：是以包的形式分发的一组规则、解析器与预设配置的集合，安装后需在配置对象里显式启用才会生效。

插件机制解决「规则从哪来」，共享配置解决「一套规则怎么复用」，两者在平面配置里常一起出现。

#### 插件、解析器与预设的关系

**解析器（parser）**：是把源码文本转成 ESLint 可遍历的语法树的组件，处理非标准语法时必须替换默认解析器。

- 插件提供规则：例如 eslint-plugin-vue 提供 vue/ 前缀的规则。
- 解析器提供语法：例如 @typescript-eslint/parser 让 ESLint 读懂类型标注。
- 预设打包规则：插件通常附赠几套预设，如 flat/recommended，展开一条即可启用。

```js
// eslint.config.js 片段：启用 Vue 插件预设
import pluginVue from "eslint-plugin-vue";

export default [
  ...pluginVue.configs["flat/recommended"],
  {
    rules: {
      "vue/multi-word-component-names": "off",
    },
  },
];
```

> 插件名到规则前缀的映射是约定：eslint-plugin-vue 的规则在配置里写作 vue/规则名，前缀在插件启用后自动可用。

**速记**：插件给规则，解析器给语法，预设把常用规则打包成一条可展开项。



#### TypeScript 项目的接入

**typescript-eslint**：是让 ESLint 检查 TypeScript 代码的官方方案，由解析器、插件与预设配置三部分组成。

- 安装：安装 typescript-eslint 与 typescript 两个开发依赖。
- 预设：tseslint.configs.recommended 给出一组基础规则，recommended-type-checked 额外启用需要类型信息的规则。
- 类型信息：使用带类型的预设要在 languageOptions.parserOptions 指定 projectService，检查耗时随之上升。

```js
// eslint.config.js：TypeScript 项目
import js from "@eslint/js";
import tseslint from "typescript-eslint";

export default tseslint.config(
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ["**/*.ts"],
    rules: { "@typescript-eslint/no-explicit-any": "warn" },
  },
);
```

> 类型感知规则更准也更慢：它要为每个文件构建类型信息，大型仓库通常只在流水线跑一次，本地只跑基础规则。

**速记**：TypeScript 项目用 typescript-eslint 的解析器加预设，需要类型信息时再开 projectService。



#### 共享配置的复用方式

**共享配置**：是发布到包仓库的规则集合，安装后作为对象插入平面配置数组，供多个项目复用同一套约定。

- 官方预设：@eslint/js 的 js.configs.recommended 是最小起点。
- 社区预设：框架与团队各自维护配置包，按需引入即可。
- 本地共享：团队把内部约定抽成本地包，业务仓库安装后一行引入，避免逐仓复制规则。

```json
{
  "name": "@acme/eslint-config",
  "version": "2.1.0",
  "type": "module",
  "main": "index.js",
  "peerDependencies": { "eslint": ">=9" }
}
```

> [!WARNING]
> **警告内容**：共享配置必须把 eslint 声明为同伴依赖（peerDependency），否则各业务仓库会装出多份互不兼容的 ESLint，规则行为因版本而异。

**速记**：共享配置是分发的规则集合，引入即复用，eslint 走同伴依赖统一版本。



### 格式冲突消解

**格式冲突**：是 ESLint 的排版类规则与 Prettier 的输出互相改写、导致 --fix 结果反复震荡的现象。

冲突的根源是职责重叠：ESLint 里存在大量只管缩进与换行的规则，而这类规则本应交给 Prettier。

#### 关闭与格式化重叠的规则

**eslint-config-prettier**：是一份只含关闭项的共享配置，把与 Prettier 冲突的 ESLint 规则统一置为 off。

- 位置：必须放在平面配置数组的最后，否则后写的规则会再次开启冲突项。
- 范围：它只关规则、不改其他配置，可与框架预设共存。
- 校验：可用其自带的命令行工具检查配置中是否残留冲突规则。

```js
// eslint.config.js：把 prettier 配置放在数组末尾
import js from "@eslint/js";
import eslintConfigPrettier from "eslint-config-prettier";

export default [
  js.configs.recommended,
  {
    rules: { indent: ["error", 2], quotes: ["error", "double"] },
  },
  eslintConfigPrettier, // 必须最后：关掉上面写下的排版规则
];
```

```bash
npx eslint-config-prettier src/main.js
# No rules that are unnecessary or conflict with Prettier were found.
```

> [!IMPORTANT]
> **重要内容**：eslint-config-prettier 一旦被放到数组中间，排在它后面的任何规则都会重新开启冲突项，震荡问题将原样复现。

**速记**：eslint-config-prettier 关掉排版规则，务必放在数组最后一位。



#### 用 Prettier 独占格式化的做法

**独占格式化的做法**：是把排版全权交给 prettier --write，不让 ESLint 参与缩进与换行，从而消除双写冲突。

- 禁止混用：不要用 eslint-plugin-prettier 把 Prettier 包装成一条 ESLint 规则，那会让报错定位变差、检查变慢。
- 编辑器：开启保存时格式化，格式来源选 Prettier，避免编辑器自带格式化器争夺控制权。
- 校验：流水线里运行 prettier --check 而不是 --write，未格式化即判定失败。

```json
{
  "semi": true,
  "singleQuote": false,
  "printWidth": 100,
  "tabWidth": 2,
  "trailingComma": "all"
}
```

```bash
npx prettier --write "src/**/*.{js,ts,vue,json}"
# src/main.ts 32ms
npx prettier --check .
# All matched files use Prettier code style!
```

> Prettier 3 把尾随逗号的默认值改为 all，跨版本升级时显式写明 trailingComma 可以避免产物外观意外变化。

**速记**：排版只认 prettier，用 --check 校验、用 --write 修复。



#### 冲突排查的常用手段

**冲突排查**：是通过打印最终生效配置与逐文件比对，定位「究竟是谁把规则改了」的过程。

- 打印配置：npx eslint --print-config 某文件，查看合并后 rules 中目标规则的最终取值。
- 二分范围：临时注释掉配置数组中的对象，定位是哪一层引入了冲突。
- 查看文件：prettier --check 会列出未格式化文件，据此判断是残留旧格式还是规则真的冲突。

```bash
npx eslint --print-config src/App.vue > /tmp/eslint-final.json
grep -n '"indent"' /tmp/eslint-final.json
# 5:    "indent": 0,   // 已被 eslint-config-prettier 关闭
```

> 冲突往往来自共享配置自带的排版规则，而不是本地写法，排查时优先看引入的预设。

**速记**：打印最终配置定位取值，二分注释定位引入层。



### 提交前检查与流水线接入

**提交前检查**：是在 git commit 触发时自动运行的检查，能在问题进入仓库之前拦下它们，修复成本最低。

#### husky 与 Git 钩子

**husky**：是把 Git 钩子脚本纳入版本管理的工具，通过安装钩子目录让仓库内的钩子对所有协作者生效。

- 初始化：执行 npx husky init，会创建 .husky 目录并把 prepare 脚本写入 package.json。
- 钩子文件：在 .husky 下按钩子名建文件，如 pre-commit、commit-msg，文件内容即待执行命令。
- 生效方式：安装依赖时 prepare 脚本自动执行，把钩子目录挂到 .git/hooks。

```bash
npx husky init
# 生成 .husky/pre-commit
printf 'npx lint-staged\n' > .husky/pre-commit
```

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

> [!CAUTION]
> **注意内容**：本地钩子可以被 git commit --no-verify 绕过，它挡的是疏忽而非有意行为，不能替代流水线上的强制检查。

**速记**：husky init 生成 .husky 目录，钩子文件的内容就是待执行的命令。



#### lint-staged 只检查改动文件

**lint-staged**：是读取 Git 暂存区文件列表并对其运行指定命令的工具，只处理本次改动的文件，避免全仓检查过慢。

- 配置位置：写在 package.json 的 lint-staged 字段，或独立的配置文件里。
- 匹配与命令：键是文件匹配模式，值是命令数组，按数组顺序执行。
- 传参方式：lint-staged 把匹配到的文件路径追加到命令末尾，故命令中不写具体文件名。

```json
{
  "lint-staged": {
    "*.{js,ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{json,md,css}": ["prettier --write"]
  }
}
```

```bash
git add src/main.ts
git commit -m "feat: 调整入口"
# ✔ Preparing lint-staged...
# ✔ Running tasks for staged files...
# ✔ Applying modifications from tasks...
```

> --fix 与 --write 改动过的文件会被 lint-staged 自动重新加入本次提交，无需手动再执行 git add。

**速记**：lint-staged 只跑暂存区文件，命令按模式分组、按数组顺序执行。



#### 流水线中的 lint 任务

**流水线 lint 任务**：是在持续集成中对全仓运行一次检查，作为合并前门禁，弥补本地钩子可被绕过的缺口。

- 分工：钩子做快速自检，流水线做全量与不可绕过的门禁。
- 缓存：把依赖安装与 ESLint 的缓存文件纳入 CI 缓存，显著缩短任务时长。
- 失败即阻断：ESLint 加 --max-warnings 0，Prettier 用 --check，任一失败即判定本次提交不通过。

```yaml
name: lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npx eslint . --max-warnings 0
      - run: npx prettier --check .
```

> ESLint 默认把检查结果缓存到 .eslintcache，CI 中缓存该文件可在二次运行时只重查变化的文件。

**速记**：流水线跑全量 lint 并缓存依赖，--max-warnings 0 与 --check 共同充当门禁。
