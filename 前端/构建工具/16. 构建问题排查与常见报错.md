## 构建问题排查与常见报错

**构建报错排查**：是按「现象、成因、排查、修复」四步定位构建中断原因的方法；本篇覆盖模块解析、模块格式互操作、环境变量、内存与资源路径五类高频问题。

**模块解析**：是构建工具把导入说明符（import specifier，import 语句中写的路径字符串）映射到真实文件的过程，其结果是构建依赖图（dependency graph，模块之间引用关系构成的图）的输入。报错原文取自 Vite、webpack 与 Node.js 的真实输出，修复手段以官方配置项为准。

### 模块解析失败

**模块解析失败**：是构建工具无法把导入说明符定位到真实文件或目录入口的报错，发生在依赖图构建阶段，构建不会进入打包与压缩。

- 解析是所有后续阶段的前置条件，因此这类报错通常最先暴露。
- 排查的共同入口是报错信息中的两个值：无法解析的说明符，以及发起导入的文件。

#### 找不到模块与路径写错

**现象**：开发服务器或构建在解析导入路径时中断，终端输出 Failed to resolve import 或 Can't resolve。

```bash
[vite] Internal server error: Failed to resolve import "./utils/formatDate" from "src/App.vue". Does the file exist?
Module not found: Error: Can't resolve './utils/formatDate' in '/project/src'
```

**成因**：导入路径与实际文件名不匹配，或路径大小写在区分大小写的文件系统上不一致。

**排查**：核对报错信息中 from 之后的引用方文件，按该文件所在目录计算相对路径深度；在项目根执行 ls 比对目录与文件名的实际大小写。

**修复**：把相对路径改为与文件位置一致，统一文件名大小写；引用目录时补上目录下的入口文件名。

> 相对路径的基准是引用文件自身的目录，不是项目根目录；移动文件后必须同步修改引用方的路径层级。

**速记**：解析失败先看说明符与引用方两个值，再回推相对路径与大小写。



#### 扩展名与目录入口识别

**现象**：导入语句省略扩展名时，打包器可以解析，原生 ESM 环境却报找不到模块。

```bash
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/project/src/utils' imported from /project/src/index.js
```

**成因**：原生 ESM 不做扩展名补全，也不做目录入口推断；打包器只补全 resolve.extensions 中列出的后缀。

**排查**：查看报错信息中 imported from 之后的文件，确认说明符是否省略了后缀；检查构建配置中的 resolve.extensions 是否覆盖该后缀。

**修复**：原生 ESM 写全扩展名并显式指向入口文件；打包器项目把所需后缀加入 resolve.extensions。

```js
// vite.config.js
export default {
  resolve: {
    extensions: [".mjs", ".js", ".mts", ".ts", ".jsx", ".tsx", ".json"],
  },
};
```

> Vite 默认补全 .mjs、.js、.mts、.ts、.jsx、.tsx、.json；webpack 默认只补全 .js、.json、.wasm，配置前先确认默认值。

**速记**：扩展名缺失是原生 ESM 的硬约束，打包器靠 resolve.extensions 放宽。



#### 别名与子路径导出不匹配

**现象**：使用 @ 等别名时打包器报无法解析；导入依赖包内部路径时报包导出未开放。

```bash
Failed to resolve import "@/components/Header.vue" from "src/main.js". Does the file exist?
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/format' is not defined by "exports" in /project/node_modules/some-lib/package.json
```

**成因**：别名只写在 tsconfig.json 的 paths 字段，构建工具不知道这层映射；依赖包用 exports 字段封闭了可导入的子路径。

**排查**：搜索构建配置中的 resolve.alias，确认与 tsconfig 的 paths 是否一致；打开依赖包 package.json 查看 exports 字段列出了哪些子路径。

**修复**：在构建配置与 tsconfig 中同时声明别名；导入依赖时改用 exports 已公开的入口。

```js
// vite.config.js
import { fileURLToPath, URL } from "node:url";

export default {
  resolve: {
    alias: { "@": fileURLToPath(new URL("./src", import.meta.url)) },
  },
};
```

> tsconfig.json 的 paths 只影响类型检查，构建工具各自维护一份别名表，两边缺一都会出现编辑器不报错、构建报错的错位。

**速记**：别名要两处同时声明，依赖子路径以 exports 字段为准。



### CJS 与 ESM 互操作问题

**CJS 与 ESM 互操作**：是 CommonJS（CJS，用 require 与 module.exports 的模块格式）与 ES Module（ESM，用 import 与 export 的模块格式）在同一依赖图中互相引用时的格式适配问题。

- 两种格式的导出语义不同：CJS 导出的是运行时的一个对象，ESM 导出的是静态可分析的绑定。
- 打包器只做一层兼容处理，跨格式引用报错时仍要回到源格式判断。

#### 默认导出与命名导出错配

**现象**：导入依赖时报它不提供指定导出，或报默认导出不存在。

```bash
SyntaxError: The requested module 'lodash-es' does not provide an export named 'default'
"default" is not exported by node_modules/some-cjs-lib/index.js, imported by src/main.js
```

**成因**：CJS 包把全部导出挂在 module.exports 上，导入方却按 ESM 的命名导出或默认导出去读取，两套语义没有对应关系。

**排查**：查看依赖包 package.json 的 module 与 exports 字段，判断它提供哪种格式；在 Node 中执行 node -e "import('some-cjs-lib').then((m) => console.log(Object.keys(m)))" 打印真实导出键。

**修复**：对 CJS 包改用默认导入后再解构；该包存在 ESM 版本时优先切到 ESM 入口。

```js
// CJS 包只挂 module.exports 时，先取默认导出再解构
import someCjsLib from "some-cjs-lib";

const { formatName } = someCjsLib;
console.log(formatName("Ada")); // "Ada"
```

> 构建配置中的 esModuleInterop 与 synthetic default 只提供一层兼容，报 default 相关错误时不能靠继续加开关解决。

**速记**：默认导出报错先看包的真实导出键，CJS 包先取默认再解构。



#### require 与 import 混用

**现象**：ESM 文件中出现 require 报未定义，或 CJS 文件加载纯 ESM 包时报不支持。

```bash
ReferenceError: require is not defined in ES module scope, you can use import instead
Error [ERR_REQUIRE_ESM]: require() of ES Module /project/node_modules/some-esm-only/index.js from /project/main.cjs not supported.
```

**成因**：package.json 声明 type 为 module 后，同目录的 .js 文件一律按 ESM 解析，require 不存在；反向地，require 无法同步加载 ESM。

**排查**：查看出错文件最近的 package.json 的 type 字段，确认该文件被按哪种格式解析；确认出错文件的扩展名是 .js 还是 .cjs。

**修复**：ESM 中改用 import；必须保留 CJS 的文件把扩展名改为 .cjs；CJS 需要加载 ESM 包时改用动态导入。

```js
// CJS 中加载 ESM 包只能走动态导入
async function loadRenderer() {
  const { render } = await import("some-esm-only");
  return render;
}
```

> 依赖只在某个大版本改为纯 ESM 或纯 CJS 发布时，处置手段是换到提供双格式的版本；同一个依赖开发期正常、构建后报错，说明构建工具做了转换而运行时环境没有。

**速记**：require 与 import 的可用性由 type 字段与扩展名决定，跨格式加载走动态导入。



#### 动态导入与顶层 await

**现象**：使用顶层 await 的模块在打包时报输出格式不支持该语法。

```bash
ERROR: Top-level await is currently not supported with the "cjs" output format
Module format does not support top-level await
```

**成因**：顶层 await 只在 ES2022 规范之后的 ESM 中合法，输出格式为 cjs 或 target 低于 es2022 时构建失败。

**排查**：查看构建配置中的 build.target 与 output.format；确认该文件是否处于 ESM 解析范围。

**修复**：把输出格式设为 esm，target 提到 es2022 及以上；不需要顶层等待时把逻辑包进异步函数。

```js
// vite.config.js
export default {
  build: { target: "es2022" },
};
```

> 打包为库时，顶层 await 会限制使用方的模块格式，应在 package.json 的 exports 中用 import 条件标注 ESM 入口，并对 CJS 使用方提供降级实现。

**速记**：顶层 await 是 ESM 与 es2022 的专属能力，cjs 产物必须改写。



### 环境变量与全局变量缺失

**环境变量缺失**：是客户端代码读取构建期未注入的变量、或读取浏览器不存在的全局标识符时抛出的错误，两类问题的定位路径不同：前者查注入配置，后者查运行环境。

- 变量注入由构建工具在构建期完成，注入结果只包含被显式开放的键。
- 全局标识符决定于运行环境，浏览器没有任何 Node.js 全局对象。

#### 自定义变量未被注入

**现象**：代码读取自定义变量得到 undefined，而同文件中带固定前缀的变量有值。

```js
// 变量名缺少 VITE_ 前缀，构建期不会注入
console.log(import.meta.env.MY_KEY); // undefined
console.log(import.meta.env.VITE_API_BASE); // "https://api.example.com"
```

**成因**：Vite 默认只把 VITE_ 前缀的键注入客户端代码，其余键仅对配置文件可见，因此未加前缀的变量在浏览器侧读不到。

**排查**：用 console.log(import.meta.env) 打印全部注入结果，确认键名、前缀与实际加载的 .env 文件。

**修复**：给变量名补上 VITE_ 前缀；需要换前缀时配置 envPrefix；修改 .env 文件后重启开发服务器，环境变量在启动时读取一次。

```json
{
  "scripts": {
    "dev": "vite",
    "build:staging": "vite build --mode staging"
  }
}
```

> import.meta.env 是构建期的静态文本替换，只有写成字面量成员的键会被替换；用变量拼出的键在产物中保留原样，取不到值。

> [!WARNING]
> **警告内容**：带 VITE_ 前缀的变量会被内联进客户端产物，任何访问者都能从源码中读出，令牌与密钥不得放入其中。

**速记**：客户端变量要靠前缀开放，改完 .env 必须重启开发服务器。



#### 浏览器全局变量未定义

**现象**：页面运行时报 global、Buffer 或 __dirname 未定义，多出现在引入 Node 生态工具库之后；沿用旧脚手架 process.env 写法的代码则报 process 未定义。

```bash
Uncaught ReferenceError: global is not defined
Uncaught ReferenceError: Buffer is not defined
Uncaught ReferenceError: process is not defined
```

**成因**：global、Buffer、__dirname、process 都是 Node.js 运行时的标识符，浏览器环境不存在，而 Vite 不再像 webpack 4 那样自动注入 Node 垫片。

**排查**：按堆栈定位引用这些标识符的模块，判断是项目代码还是依赖在浏览器侧的残留引用。

**修复**：项目代码用 globalThis 与 Uint8Array 等标准对象替代，读取环境变量改用 import.meta.env；依赖必须依赖 Node 全局时，用 define 把标识符映射到具体表达式。

```js
// vite.config.js
export default {
  define: { global: "globalThis" },
};
```

> 全局注入会改变所有模块对该名字的解释，能用升级依赖解决就不要注入；必须注入时把键收窄到具体表达式而非整个对象。

**速记**：Node 专有全局在浏览器不存在，能用标准对象替代就不做全局注入。



#### define 静态替换的边界

**现象**：配置了 define 之后变量仍未生效，或替换结果不是预期值。

```bash
Uncaught ReferenceError: process is not defined
```

**成因**：define 在构建期做纯文本替换，键必须是完整的成员访问表达式；运行时才拼出的键不会被替换，值若不是合法字面量会输出成裸标识符。

**排查**：搜索构建配置中的 define 或 DefinePlugin，逐条核对键是否为完整表达式、值是否用 JSON.stringify 包过。

**修复**：键写成完整表达式，字符串值统一用 JSON.stringify 包裹；替换键与源码标识符重名时改名规避歧义。

```js
// 键是完整表达式，值是 JSON 字符串
export default {
  define: {
    __BUILD_TIME__: JSON.stringify(new Date().toISOString()),
  },
};
```

> 替换只作用于字面量形式的键，动态访问的对象属性不受影响，这也是 import.meta.env 必须写成静态成员的原因。

**速记**：define 是构建期文本替换，键要完整、值要序列化。



### 内存溢出与栈溢出

**构建期内存问题**：是 Node.js 进程在构建过程中耗尽堆内存或被系统强制终止的错误，表现分为堆溢出、栈溢出与进程被信号杀死三类。

- 堆用于存放对象，栈用于记录函数调用，两类溢出的成因与处置手段不同。
- 构建工具本身也是 Node.js 程序，因此受同一套内存限制约束。

#### 堆内存溢出

**现象**：构建进行到某个阶段后进程退出，终端输出堆内存不足的致命错误。

```bash
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
 1: 0xb85b0 node::Abort() [node]
```

**成因**：Node.js 默认堆上限约 2 GB（64 位环境，随版本与可用内存浮动），构建峰值超过该上限时进程被中止；依赖数量激增、巨型 source map（源码映射表）、大量资源内联都会推高峰值。

**排查**：确认是否开启了 source map、是否存在同一依赖的多份副本、是否有大文件被内联为字符串。

**修复**：先削减内存占用来源，再按需提高堆上限。

```bash
NODE_OPTIONS=--max-old-space-size=4096 npx vite build
node --max-old-space-size=4096 ./node_modules/vite/bin/vite.js build
```

> [!CAUTION]
> **注意内容**：提高堆上限会让进程占用更多宿主内存，在配额固定的容器中可能连带影响同机其他任务，应与并行度、配额一起调整。

> 本地构建正常而持续集成环境报 Killed 与退出码 137 时，成因是配额低于本地机器加并行任务叠加，处置方式是在流水线环境显式设置堆上限并降低并行构建数。

**速记**：堆溢出先找峰值来源，再用 max-old-space-size 兜底。



#### 栈溢出与循环依赖

**现象**：构建或页面初始化时报调用栈超限，堆栈中反复出现同一批模块。

```bash
RangeError: Maximum call stack size exceeded
```

**成因**：模块之间形成循环依赖（模块 A 引用 B，B 又引用 A），在初始化阶段互相触发求值形成递归；构建插件在钩子里处理自身输出时也会出现同类递归。

**排查**：用依赖分析工具检测环，并核对报错堆栈中重复出现的模块路径。

```bash
npx madge --circular --extensions js,ts src
# Processed 42 files
# 1) src/store/index.js > src/api/client.js > src/store/index.js
```

**修复**：抽离双方共用的部分到第三个模块以打破环；把只在运行时需要的引用改为函数内部延迟引用。

> 循环依赖不必然报错，只有叠加求值顺序与副作用时才崩溃，因此应主动检测而不是等问题暴露。

**速记**：栈溢出常源于循环依赖，先用依赖分析工具定位环再拆环。



#### 压缩与 source map 阶段的内存峰值

**现象**：构建在压缩或写 source map 阶段被终止，或耗时远超预期。

```bash
FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory
```

**成因**：压缩器需要在内存中展开抽象语法树与源码映射表，产物越大峰值越高；terser 的内存占用与耗时通常高于 esbuild 压缩器。

**排查**：临时关闭 source map 复测峰值；对比不同压缩器表现；查看是否某个 chunk（代码块）体积异常突出。

**修复**：生产产物不外发 source map，或仅在需要排查时开启；改用 esbuild 做压缩。

```js
// vite.config.js
export default {
  build: {
    sourcemap: false,
    minify: "esbuild",
  },
};
```

> 内联 source map 与外链 source map 都需要先生成再落盘，两者对峰值内存的影响接近，区别只在产物形式。

**速记**：压缩与 source map 是内存峰值高发区，先关 source map 再换压缩器。



### 样式与资源路径异常

**样式与资源路径异常**：是样式文件未被正确处理、或产物中的资源地址与实际部署位置不一致导致的报错与 404，前者由 loader 与文件命名规则决定，后者由 base 与资源引用写法决定。

- 样式在打包器眼中是普通模块，需要专门的转换规则才能进入依赖图。
- 资源地址在构建期被重写或加哈希，手写路径无法随产物变化。

#### 样式文件缺少转换规则

**现象**：在 webpack 项目中导入 CSS 文件后构建失败，提示需要合适的 loader。

```bash
Module parse failed: Unexpected token (1:0)
You may need an appropriate loader to handle this file type, currently no loaders are configured to process this file.
```

**成因**：webpack 默认只认识 JavaScript 与 JSON，CSS 需要 loader 转换成模块；Vite 内置样式处理链路，因此同样写法在 Vite 中不报此错。

**排查**：核对报错文件的扩展名与 module.rules 中 test 正则是否匹配，确认对应 loader 是否已安装。

**修复**：配置 css-loader 解析样式，再用 style-loader 注入页面，或改用 MiniCssExtractPlugin 抽成独立文件。

```js
// webpack.config.js
export default {
  module: {
    rules: [{ test: /\.css$/, use: ["style-loader", "css-loader"] }],
  },
};
```

> use 数组的执行顺序是从右到左，css-loader 必须先于 style-loader 执行；两者顺序写反会得到解析失败的报错（详见本主题第 9 篇 webpack loader 与 plugin）。

**速记**：样式在 webpack 中必须配 loader，use 数组从右向左执行。



#### 样式类名映射取不到值

**现象**：按 CSS Modules 的写法导入样式后，取到的类名是 undefined。

```js
// 普通 css 文件不会导出类名映射
import styles from "./card.css";

console.log(styles.card); // undefined
console.log(styles); // 空对象或注入函数
```

**成因**：只有文件名含 .module 段的样式才按 CSS Modules 处理并导出类名到标识符的映射，普通 .css 文件只做样式注入。

**排查**：核对样式文件名是否含 .module；打印导入结果，确认拿到的是空对象还是映射对象。

**修复**：把文件重命名为 card.module.css，并按映射取类名；不需要映射时直接在结构中写字符串类名。

```css
/* src/components/card.module.css */
.card {
  border: 1px solid #ddd;
}
```

> [!TIP]
> **建议内容**：需要类名映射的样式统一使用 .module.css 后缀，普通全局样式保留 .css 后缀，靠命名把两种意图分开，可避免大量取值失败的误用。

**速记**：类名映射只对 .module.css 生效，普通 .css 只注入样式。



#### 资源 404 与 base 配置

**现象**：本地开发正常，部署到子路径后浏览器报资源 404。

```bash
GET https://example.com/assets/logo.4f2a1c.png 404 (Not Found)
```

**成因**：产物中的资源地址以站点根路径开头，而站点实际部署在子路径下，浏览器按错误前缀请求文件。

**排查**：打开产物的 HTML 文件查看资源地址前缀，与访问站点的实际路径对比；确认构建配置中的 base 取值。

**修复**：把 base 设为部署子路径；代码中拼接地址时使用 import.meta.env.BASE_URL 而非手写斜杠。

```js
// vite.config.js
export default {
  base: "/admin/",
};
```

> base 在开发服务器与构建产物两端都生效，本地验证产物路径要用 vite preview 预览构建结果（详见本主题第 7 篇 Vite 构建与产物优化）。

**速记**：404 先比对产物路径前缀与部署路径，base 决定拼接结果。



#### 静态资源引用方式错误

**现象**：引用静态资源时报 404，路径中出现多余的 public 段；或产物更新后原地址失效。

```bash
GET https://example.com/public/logo.png 404 (Not Found)
```

**成因**：public 目录下的文件按原样复制到产物根目录，不带 public 前缀；而经过导入链路的资源会按内容加哈希，文件名不可预测。

**排查**：查看产物目录中文件的落点，确认引用写法来自导入返回值还是手写字符串。

**修复**：public 目录中的资源用根路径引用；参与构建流程的资源一律通过 import 取值。

```js
import logoUrl from "./assets/logo.png";

console.log(logoUrl); // "/assets/logo.4f2a1c.png"
```

> 手写产物文件名会在文件内容变化、哈希更新后立即失效，凡经过导入链路的资源都不应手写名字。

**速记**：public 资源用根路径，参与构建的资源用 import 取回最终地址。
