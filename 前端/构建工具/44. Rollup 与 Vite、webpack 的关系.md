## Rollup 与 Vite、webpack 的关系

三个工具不是同一条赛道上的竞品：Rollup 是打包器，Vite 是在打包器之上搭建的开发与构建方案，webpack 是自带运行时与扩展点的应用打包平台。本篇只讲三者如何分工与如何选型；esbuild 与 SWC 的能力对比见本主题第 12 篇 Rollup、esbuild 与 SWC，Vite 的配置细节见本主题第 4 篇 至第 7 篇，webpack 的配置细节见本主题第 8 篇 至第 10 篇。

### Vite 生产构建为何用 Rollup

Vite 在开发期与构建期使用不同的承担者，这是理解三者关系的起点。本节从两期分工、开发期的模块加载方式与生产期的工具选择三处展开。

#### 开发期与构建期的分工

**开发期与构建期的分工**：是 Vite 在两种模式下把工作交给不同承担者的安排，开发期由开发服务器按请求转换模块，构建期由 Rollup 打包产出静态文件。

- 开发期承担者：开发服务器按请求即时转换模块，预构建与语法转换由 esbuild 完成。
- 构建期承担者：Rollup 负责解析依赖图、做代码分割并渲染出最终产物。
- 共同基础：两期共用同一份配置与同一套插件接口，插件可同时介入两种模式。
- 差异根源：开发期要求首个请求尽快返回，构建期要求产物尽量小且可长期缓存。
- 边界：开发期不做完整打包，构建期不做按请求的增量转换。

```js
// vite.config.js 两期的配置分属不同段
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    port: 5173,
    open: true,
  },
  build: {
    target: "es2019",
    sourcemap: "hidden",
  },
});
```

> 判断某段配置在哪一期生效，看它挂在 server 段还是 build 段：挂在 server 段的配置对生产产物没有任何影响。

**速记**：开发期由开发服务器按请求转换，构建期由 Rollup 打包，两期共用插件接口。



#### 开发期以原生模块为基础

**原生模块加载（native ESM）**：是浏览器直接用 import 语句按需加载未打包模块文件的机制，开发服务器据此把模块逐个返回。

- 请求粒度：每个模块一次请求，改动只影响该模块所在的依赖链。
- 转换时机：请求到达才转换，未被访问的模块不付出转换成本。
- 依赖处理：第三方依赖先做预构建，把大量内部模块合并为少量文件以降低请求数。
- 与打包的差别：不做代码合并与作用域提升，模块边界与源码结构保持一致。
- 代价：模块数量极多时请求数上升，这是开发期不使用打包器的直接成本。

```html
<script type="module" src="/src/main.js"></script>
<!-- 浏览器直接按 import 关系逐个请求模块文件 -->
```

> 开发期看到的是源码模块边界，构建期看到的是合并后的产物，两者的模块数量与文件形态都不相同。

**速记**：开发期靠浏览器原生 ESM 按需加载，依赖做预构建以减少请求数。



#### 生产期选择 Rollup 的理由

**生产期打包**：是把多个模块合并成少量文件、同时完成常量替换与代码分割的过程，Vite 把它交给 Rollup 完成。

- 静态分析彻底：以 ESM 为输入，树摇能精确到导出项，产物中不留未使用的代码。
- 代码分割成熟：动态导入与手动分包的控制点完整，分包结果可预期。
- 插件接口稳定：钩子覆盖解析、加载、转换、渲染与写入各阶段，生态插件可直接复用。
- 与开发期同源：开发服务器的插件容器复用了 Rollup 的钩子约定，两期插件写法一致。
- 产物干净：默认不引入运行时包装，接近手写代码，便于调试与二次处理。

```js
// vite.config.js 生产构建的选项通过 rollupOptions 透传给 Rollup
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        entryFileNames: "assets/[name]-[hash].js",
        chunkFileNames: "assets/[name]-[hash].js",
      },
    },
  },
});
```

> 生产构建的产物结构由 Rollup 决定，因此需要控制分包与命名时，改的是 Rollup 的选项而不是 Vite 自身的字段。

**速记**：生产期交给 Rollup，因为它静态分析彻底、分包控制完整、插件接口稳定。



### 三者职责划分

把三个工具放在同一张图上，职责可以用「产物给谁用」这条线切开。本节按库与应用、开发与构建、判定依据三组对照展开。

#### 库与应用的分工

**库与应用的分工**：是按产物归宿划分的职责，库产物供下一个构建器消费，应用产物直接交给浏览器运行。

- 库侧工具：Rollup 直接使用，产出多格式、可逐模块引用的产物。
- 应用侧工具：Vite 或 webpack 使用，产出带内容哈希、已压缩、可长期缓存的静态资源。
- 依赖归属：库把框架外置，应用把框架打进产物。
- 语法降级：库保留较新语法，应用按目标浏览器范围降级。
- 交集情形：应用内部也可以把某个子包按库的方式构建，开发期用别名指回源码。

```js
// vite.config.js 应用侧把内部包别名指向源码，产物侧仍按库的方式构建
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  resolve: {
    alias: {
      "@my-scope/date-kit": fileURLToPath(new URL("./packages/date-kit/src/index.js", import.meta.url)),
    },
  },
});
```

> 库与外部的边界是包字段：库通过字段对外承诺产物，应用通过字段解析产物，两侧不共享构建配置。

**速记**：库产物给构建器用、应用产物给浏览器用，依赖归属与语法策略随之分叉。



#### 开发服务器与构建器的分工

**开发服务器与构建器的分工**：是同一工程里负责交互式开发与负责产出发布文件的两种角色，二者的产物不可互换。

- 开发服务器：不产出可用于部署的文件，只按请求转换并推送热更新。
- 构建器：不提供按请求服务，一次性产出完整文件集合。
- 配置入口：开发服务器读取 server 段，构建器读取 build 段，插件数组共用。
- 产物差异：开发期不压缩、不加内容哈希；构建期默认压缩并按规则加哈希。
- 一致性风险：只在开发期验证过的代码，可能因构建期产物形态不同而暴露问题。

```bash
npx vite
# 启动开发服务器，产物只在内存中，不作为发布文件
npx vite build
# 一次性产出 dist 目录，用于部署
```

> [!IMPORTANT]
> **重要内容**：开发服务器通过不代表构建通过，样式顺序、动态导入路径与资源引用都可能在构建期才出错，交付前必须各跑一次。

**速记**：开发服务器只管按请求转换与热更新，构建器只管产出发布文件，两者要各验一次。



#### 职责划分的判断依据

**职责判断**：是按产物消费方、是否需要交互式开发、是否需要多格式三问确定使用哪一层工具的方法。

- 第一问：产物给谁用，给浏览器用选应用构建器，给构建器用选库构建器。
- 第二问：是否需要交互式开发，需要则在构建器之外接入开发服务器。
- 第三问：是否需要多种模块格式，需要则用 Rollup 的多格式输出。
- 团队因素：已有 webpack 资产的项目，升级既有配置常比整体替换成本更低。
- 组合允许：库用 Rollup、应用用 Vite 的组合是常见且被推荐的形态。

```text
待构建对象
  ├─ 产物给浏览器用 ──> 应用构建器（Vite／webpack）
  ├─ 产物给构建器用 ──> 库构建器（Rollup）
  └─ 两者都有 ────────> 按目录分别配置，用工作区串联
```

> 三问的答案互不冲突，同一个仓库可以同时存在库构建与应用构建两条链路，只要目录与命令分开即可。

**速记**：按产物消费方、开发需求与格式需求三问判断，允许同一仓库并存两条构建链路。



### 配置心智的迁移

从 Rollup 换到 Vite、或在两者之间搬运配置，难点不在语法而在概念对应。本节给出名词映射、插件接口对应与迁移注意点。

#### 概念对应关系

**概念对应**：是 Rollup 与 Vite、webpack 在入口、产物、插件等名词之间的映射关系，掌握映射才能读懂对方的配置。

- 入口：Rollup 的 input 对应 Vite 的 build.rollupOptions.input，对应 webpack 的 entry。
- 产物：Rollup 的 output 对应 Vite 的 build.rollupOptions.output，webpack 拆成 output 与 optimization 两处。
- 扩展点：Rollup 与 Vite 都用插件对象，webpack 用加载器与插件两类扩展点。
- 钩子：Rollup 的构建阶段与输出阶段钩子在 Vite 中直接可用。
- 开发服务器：Rollup 不内置开发服务器，Vite 与 webpack 各自提供。

```text
Rollup              Vite                        webpack
input          ->   build.rollupOptions.input   entry
output         ->   build.rollupOptions.output  output + optimization
external       ->   build.rollupOptions.external  externals
plugin         ->   plugins                     loader + plugin
（无）          ->   server                      devServer
```

> [!NOTE]
> **提醒内容**：映射表只覆盖主干概念，两侧同名的字段也可能语义不同，改配置时以各自文档为准。

**速记**：input 与 output 与 external 与 plugin 四项在两侧一一对应，开发服务器是 Rollup 缺失的一环。



#### 插件接口的对应

**插件接口的对应**：是把 Rollup 插件接入 Vite 的方式，Vite 插件对象在 Rollup 插件对象之上扩展了若干专属钩子。

- 直接复用：仅使用 Rollup 钩子的插件可原样放进 Vite 的插件数组。
- 专属扩展：Vite 增加配置解析、开发服务器与页面模板相关钩子，供开发期使用。
- 顺序控制：插件用 enforce 声明执行时机，排在其他插件之前或之后。
- 作用范围：与产物渲染强相关的钩子只在构建期触发，开发期不会执行。
- 调试方式：用插件的 name 字段定位耗时与顺序，按名称过滤日志。

```js
// 一个同时兼容 Rollup 与 Vite 的插件：只使用通用钩子
export default function injectBannerPlugin(banner) {
  return {
    name: "inject-banner",
    buildStart() {
      this.info(`banner: ${banner}`);
    },
    transform(code, id) {
      if (!id.endsWith(".js")) return null;
      return { code: `${banner}\n${code}`, map: null };
    },
  };
}
```

> 只依赖通用钩子的插件在两个工具间可移植；一旦使用 Vite 专属钩子，插件就只能在 Vite 内使用。

**速记**：Vite 插件是 Rollup 插件的超集，只用通用钩子的插件可直接搬运。



#### 迁移时的注意点

**迁移注意点**：是从 Rollup 配置迁到 Vite、或从 Vite 迁到纯 Rollup 时容易失配的几处差异。

- 环境变量：纯 Rollup 用替换插件注入常量，Vite 用 import.meta.env 前缀机制，替换规则不同。
- 目录约定：Vite 以项目根下的页面模板与静态目录为默认入口，纯 Rollup 需要显式声明入口。
- 依赖外置：库场景要在 Rollup 的 external 与 Vite 的 rollupOptions.external 之间对齐写法。
- 资源处理：Vite 内置资源处理规则，纯 Rollup 需要自行接入资源相关插件。
- 校验方式：迁移后比对产物清单与体积，逐项确认没有能力被漏配。

```bash
ls dist
# 迁移前
# index.mjs  index.cjs
# 迁移后逐条比对文件名与数量，差异项回到配置里定位
```

> 应用侧的迁移路径见本主题第 32 篇 从 webpack 迁移到 Vite，本篇只覆盖库构建与配置搬运的部分。

**速记**：环境变量、目录约定、外部化写法与资源处理四处最容易失配，迁移后要比对产物清单。



### 组合使用的场景

三个工具可以在同一个工程里各司其职，组合的关键是把边界写清楚。本节给出三种典型组合及其衔接方式。

#### 库与应用分离的组合

**库与应用分离**：是在同一仓库内把库按 Rollup 构建、把应用按 Vite 或 webpack 构建，应用通过工作区引用库产物的组合方式。

- 目录划分：库与应用各占一个工作区，库产物写入自身的产物目录供应用引用。
- 引用方式：开发期用别名指向库源码以获得快速反馈，发布期指向库产物以验证真实链路。
- 顺序约束：应用构建前必须先完成库构建，流水线按依赖顺序排任务。
- 类型声明：库的声明文件随产物一起产出，应用才能获得类型提示。
- 常见问题：应用引用到库的旧产物，表现为改动不生效。

```js
// vite.config.js 应用侧按环境切换引用的目标
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

const toLibrary = (target) =>
  fileURLToPath(new URL(`../packages/date-kit/${target}`, import.meta.url));

export default defineConfig(({ mode }) => ({
  resolve: {
    alias: {
      "@my-scope/date-kit":
        mode === "development" ? toLibrary("src/index.js") : toLibrary("dist/index.mjs"),
    },
  },
}));
```

> [!CAUTION]
> **注意内容**：开发期指向源码时，库的构建错误不会暴露；发布前必须用指向产物的模式再构建一次应用，否则问题会留到集成阶段。

**速记**：库用 Rollup、应用用 Vite，开发期别名指源码、发布期指产物，构建顺序由依赖决定。



#### 在 Vite 中直接使用 Rollup 选项

**Rollup 选项透传**：是通过 build.rollupOptions 把 Rollup 的配置直接交给 Vite 生产构建的用法。

- 入口与产物：用 input 与 output 覆盖默认命名与目录，多入口时尤其需要。
- 外部化：external 与 output.globals 在库模式下决定哪些依赖不进产物。
- 手动分包：output.manualChunks 用于把指定依赖拆到独立分包。
- 插件追加：在插件数组里追加只使用通用钩子的 Rollup 插件。
- 生效范围：这些选项只作用于生产构建，开发期行为由开发服务器与专属配置决定。

```js
// vite.config.js 用 Rollup 的 manualChunks 拆分依赖
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    rollupOptions: {
      external: ["vue"],
      output: {
        globals: { vue: "Vue" },
        manualChunks: {
          charts: ["echarts"],
        },
      },
    },
  },
});
```

> 透传的选项由 Rollup 直接解释，Vite 不做二次包装，因此写错时的报错信息也来自 Rollup。

**速记**：Vite 用 rollupOptions 透传 Rollup 配置，入口、外部化与分包都在这里改。



#### webpack 项目引用库产物的组合

**跨工具引用**：是 webpack 应用把 Rollup 构建的库作为普通依赖安装并打包进自身产物的方式，两端通过包字段对接。

- 解析入口：webpack 按 main、module 与 exports 字段解析到对应产物。
- 树摇条件：引用到 ESM 产物且库标注了副作用范围时才能有效裁剪。
- 双份实例：库把框架外置而应用自持同一框架时，必须保证只解析出一个版本。
- 转译范围：库产物保留了较新语法，应用应把它排除在加载器范围之外以免二次降级。
- 核对方式：构建后用体积分析确认库只被打入使用到的部分。

```js
// webpack.config.js 应用侧排除对库产物的二次转译
module.exports = {
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: { loader: "swc-loader" },
      },
    ],
  },
};
```

> 跨工具组合能否成功，取决于两端对包字段的理解是否一致，因此字段设计要优先覆盖最常见的两种解析方式。

**速记**：webpack 按包字段解析 Rollup 产物，注意树摇条件、版本单一与转译范围三点。



### 选型决策

选型不是比谁更先进，而是把场景约束代入几条固定问题。本节按产物类型、团队生态与共存策略收尾。

#### 按产物类型判定

**按产物类型判定**：是把待构建对象先归类为库产物还是应用产物，再据此选择工具的最快路径。

- 库产物：需要多格式与外部化，选 Rollup，必要时叠加转译器完成语法降级。
- 应用产物：需要开发服务器、热更新与资源处理，选 Vite 或 webpack。
- 混合产物：同一仓库里两类都有，按目录分别配置，用工作区串起构建顺序。
- 产物极小：单文件脚本且无依赖，可以不引入打包器，直接交给转译器处理。
- 判定依据：产物是否需要二次分发，是最省事的判别问题。

```text
需要二次分发？
  ├─ 是 ──> 库构建器：Rollup（多格式 + 外部化）
  └─ 否 ──> 应用构建器：Vite／webpack（开发服务器 + 资源处理）
```

> 一次分发的产物若将来需要被别的工程引用，也应尽早按库的方式构建，避免后续补做产物契约。

**速记**：先判断产物是否需要二次分发，是则 Rollup，否则选带开发服务器的应用构建器。



#### 按团队与生态判定

**生态判定**：是把团队既有资产与维护成本纳入考量，避免只按技术指标做替换决定。

- 既有配置资产：webpack 项目已有大量定制加载器与插件时，替换成本高。
- 插件可得性：需要的转换能力只有某个生态有现成插件时，优先选该生态。
- 排错经验：团队对工具的熟悉度直接影响故障恢复速度，属于真实成本的一部分。
- 框架绑定：采用框架官方方案可减少自维护配置，但底层工具会随框架升级而变化。
- 迁移节奏：小步替换、双跑比对、保留回退路径，比一次性重写风险更低。

```bash
npx vite build
# 迁移期同时保留旧链路
npx webpack --mode production
# 比对两者的产物清单与体积后再决定去留
```

> [!NOTE]
> **提醒内容**：框架官方方案可能在其升级中更换底层打包器，配置前应确认当前版本实际使用的工具，不要按旧文档推断。

**速记**：既有配置资产、插件可得性与团队熟悉度共同决定选型，迁移宜小步并保留回退。



#### 迁移与共存的决定路径

**共存策略**：是保留两类构建器各司其职、不做整体替换的安排，适用于长期演进的项目。

- 分工共存：库交给 Rollup，应用交给 Vite，非模块资源按需保留原处理方式。
- 边界固定：只有库的构建配置能改动产物契约，应用侧只消费不改写。
- 版本锁定：两类工具链各自锁定版本，避免升级互相牵连。
- 文档同步：构建命令与产物路径写进项目说明，降低新成员的理解成本。
- 退出条件：当库与应用可以合并为同一个构建目标时，才考虑收掉其中一条链路。

```json
{
  "scripts": {
    "build:lib": "rollup -c packages/date-kit/rollup.config.mjs",
    "build:app": "vite build",
    "build": "npm run build:lib && npm run build:app"
  }
}
```

> [!IMPORTANT]
> **重要内容**：共存的前提是边界清晰，两条链路各有自己的入口、配置与产物目录，任何一方都不读取对方的中间状态。

**速记**：库与应用各留一条链路、版本各自锁定、边界写进文档，合并目标出现时再收链路。
