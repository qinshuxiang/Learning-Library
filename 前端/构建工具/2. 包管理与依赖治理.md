## 包管理与依赖治理

### package.json 与依赖字段

包管理器的一切行为都以 package.json 为输入：装什么、装到哪一层、是否随包分发，都由其中字段决定。本节按字段类型拆开，先讲通用字段，再讲三类依赖字段。

#### package.json 的定位与常用字段

**package.json**：是 Node.js 项目与 npm 包的元数据清单，声明包名、版本、入口、脚本与依赖，包管理器据此解析并安装依赖。

- 身份字段：name 与 version 共同构成包的唯一标识，发布到注册表时必填。
- 入口字段：main、module 与 exports 决定导入该包时实际加载哪个文件。
- 脚本字段：scripts 定义命令别名，通过 run 前缀调用，避免手工敲长命令。
- 约束字段：engines 与 packageManager 声明运行时与包管理器版本要求。
- 私有标记：private 为真时禁止发布，业务项目通常设为真以避免误发布。

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "engines": {
    "node": ">=18"
  },
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  }
}
```

> 字段的完整清单与常用命令详见 后端/Node 主题第 6 篇 npm 与包管理，本篇只处理依赖字段与版本治理。

**速记**：package.json 是依赖与元数据的清单，name、version、scripts 与三类依赖字段是核心。



#### dependencies 与 devDependencies

**dependencies**：是包在运行时被引用、必须随包一起安装的依赖；**devDependencies**：是只在开发与构建阶段使用、不随包分发的依赖。

- 判断标准：产物运行时是否会被加载，会被加载即归入 dependencies。
- 典型归属：框架与运行时库属于 dependencies，构建工具与检查工具属于 devDependencies。
- 安装写法：npm install 包名 默认写入 dependencies，附加 --save-dev 写入 devDependencies。
- 分发影响：发布为库时，使用者的安装过程不会带上本包的 devDependencies。
- 项目差异：应用项目最终会打包，两类依赖的区别主要体现在可读性与发布行为上。

```bash
npm install vue
npm install --save-dev vite
# package.json 中分别写入 dependencies 与 devDependencies
```

> [!IMPORTANT]
> **重要内容**：把只在构建期使用的工具写进 dependencies，会让使用者安装到无用的包并扩大安全面，务必按运行时是否加载来归类。

**速记**：运行时会加载的进 dependencies，只在开发与构建期使用的进 devDependencies。



#### peerDependencies 与 optionalDependencies

**peerDependencies**：是包声明「需要宿主项目提供」的依赖版本范围；**optionalDependencies**：是安装失败时允许跳过、不阻断整体安装的依赖。

- 同伴依赖：插件类包声明所适配的框架版本，由宿主项目统一安装，避免同一框架出现多份副本。
- 安装行为：较新的包管理器会自动安装未满足的同伴依赖，旧版本只给出警告。
- 可选依赖：用于平台相关或非必需的本地模块，安装失败不视为整体失败。
- 冲突处理：同伴依赖版本不满足会在安装时报告冲突，需要显式对齐或升级。
- 组合使用：可选依赖与同伴依赖都用于表达「不强求」的依赖关系，语义不同。

```json
{
  "peerDependencies": {
    "vue": "^3.4.0"
  },
  "optionalDependencies": {
    "fsevents": "^2.3.0"
  },
  "peerDependenciesMeta": {
    "vue": {
      "optional": false
    }
  }
}
```

> 同伴依赖的版本范围由被依赖的包声明，实际安装的版本由宿主项目决定，出现冲突时应调整宿主项目而非忽略警告。

**速记**：同伴依赖交给宿主项目安装，可选依赖安装失败可跳过，两者都表达不强求。



### 语义化版本与范围符

版本号与范围符共同决定「允许安装哪些版本」。本节先拆解版本号的三段含义，再列出常用范围符，最后说明解析与预发布版本的规则。

#### 语义化版本的构成

**语义化版本（semver）**：是形如 主版本.次版本.修订号 的版本号约定，三段分别表示不兼容变更、向后兼容的功能新增与向后兼容的问题修复。

- 主版本：出现不兼容的接口改动时递增，次版本与修订号归零，如 1.4.2 到 2.0.0。
- 次版本：新增向后兼容的功能时递增，修订号归零，如 1.4.2 到 1.5.0。
- 修订号：只做向后兼容的修复时递增，如 1.4.2 到 1.4.3。
- 预发布标识：在主版本号后追加连字符与标识，如 2.0.0-beta.1，排序低于同号正式版。
- 构建元数据：再追加加号与标识，只作标记用，不参与版本比较。

```json
{
  "version": "1.4.2",
  "description": "主版本 1、次版本 4、修订号 2"
}
```

> 语义化版本是一份约定而非强制，发布方是否严格遵守需要在采用前核实，必要时查看变更日志。

**速记**：主版本管不兼容、次版本管新增、修订号管修复，预发布版排序更低。



#### 常见范围符

**范围符（range specifier）**：是依赖字段中描述可接受版本区间的写法，安装时在区间内选取满足条件的最高版本。

- 精确版本：写 1.4.2，只接受该版本，适合需要完全固定的依赖。
- 插入号：^1.4.2 允许次版本与修订号上浮，锁定主版本，是默认推荐写法。
- 波浪号：~1.4.2 只允许修订号上浮，锁定次版本，比插入号更保守。
- 通配写法：1.x 与星号表示接受整个主版本，范围最宽，风险也最大。
- 区间写法：>=1.4.0 <2.0.0 用比较符显式表达上下界，最直观。

```json
{
  "dependencies": {
    "vue": "^3.4.0",
    "lodash-es": "~4.17.21",
    "typescript": ">=5.0.0 <6.0.0"
  }
}
```

> [!WARNING]
> **警告内容**：直接使用星号或过宽的范围，会让每次安装都可能引入未经验证的新版本，是线上故障的常见来源。

**速记**：^ 锁主版本、~ 锁次版本、写全版本即精确锁定，区间写法显式表达上下界。



#### 范围解析与预发布版本

**范围解析**：是把范围符与注册表中的可用版本求交、选出可安装的最高版本的过程，预发布版本默认不参与该过程。

- 解析时机：安装时依据范围与注册表元数据挑选版本，结果写入锁文件。
- 预发布默认排除：范围未显式包含预发布标识时，不会选中 2.0.0-beta.1。
- 显式包含：写 2.0.0-beta.1 或使用满足该预发布版本的区间才可选中。
- 结果固化：解析结果写入锁文件后，后续安装复用同一版本，直到范围或锁文件更新。
- 版本漂移：删除锁文件后重新安装，范围不变也可能落到更高的次版本。

```bash
npm view vue versions --json | tail -n 5
# 查看可用版本，确认范围内最高版本
npm view vue@^3.4.0 version
# 3.4.21
```

> 范围决定「允许哪些版本」，锁文件决定「本次实际用哪个版本」，两者配合才能稳定复现。

**速记**：范围只定义可选集合，预发布版本需显式包含，实际版本由锁文件固化。



### 锁文件与安装策略

锁文件把范围解析的结果固化下来，安装命令则决定要不要复用这份结果。本节说明锁文件的记录内容、冻结安装的用法，以及依赖树的布局方式。

#### 锁文件的作用

**锁文件（lockfile）**：是包管理器记录依赖树中每个包的确切版本、来源地址与完整性校验值的文件，用于复现完全一致的依赖树。

- 记录内容：包名、解析出的版本、下载地址、完整性哈希与依赖关系。
- 命名差异：npm 使用 package-lock.json，pnpm 使用 pnpm-lock.yaml，yarn 使用 yarn.lock。
- 复现能力：同一锁文件在不同机器上解析出相同版本，减少环境差异导致的问题。
- 提交要求：应用项目应提交锁文件，库项目是否提交按团队约定。
- 更新时机：主动升级依赖时锁文件随之更新，其余情况不应被改动。

```json
{
  "lockfileVersion": 3,
  "packages": {
    "node_modules/vue": {
      "version": "3.4.21",
      "resolved": "https://registry.npmjs.org/vue/-/vue-3.4.21.tgz",
      "integrity": "sha512-xxx"
    }
  }
}
```

> 锁文件与依赖字段必须一起提交，只提交其中一个会导致版本在两台机器上不一致。

**速记**：锁文件固化确切版本与完整性哈希，与依赖字段一起提交才能复现依赖树。



#### 安装命令与冻结安装

**冻结安装**：是不改动锁文件、严格按锁文件解析结果安装的方式，用于流水线与只读环境。

- 常规安装：install 会依据范围更新锁文件，允许版本在范围内上浮。
- 冻结安装：npm ci 先校验锁文件与依赖字段是否一致，再按锁文件精确安装。
- 对应写法：pnpm install --frozen-lockfile 在锁文件与清单不一致时直接失败。
- 清理行为：冻结安装会先清空现有依赖目录，保证结果干净、不受本地残留影响。
- 使用场景：持续集成、部署流水线与需要可复现构建的任何环境。

```bash
npm ci
# 按 package-lock.json 精确安装，适合流水线
pnpm install --frozen-lockfile
# 锁文件与 package.json 不一致时直接报错退出
```

> [!CAUTION]
> **注意内容**：在持续集成中混用常规安装，可能因范围上浮引入与本地不同的版本，导致构建结果不可复现。

**速记**：本地用 install 允许更新锁文件，流水线用 ci 或 frozen-lockfile 严格复现。



#### 依赖提升与依赖树

**依赖提升（hoisting）**：是包管理器把版本兼容的依赖尽量放到顶层依赖目录、减少重复安装的布局策略。

- 目的：让多处依赖共用同一份副本，减少安装体积与安装时间。
- 代价：提升会让未声明的包恰好可用，形成幽灵依赖，成因与治理见下文专节。
- 冲突场景：同一包的两个不兼容版本无法共用顶层位置，其中一个被放到子目录。
- 观察方式：用依赖树命令查看实际解析出的版本与嵌套层级。
- 布局差异：不同包管理器的提升策略不同，这也是切换后报错变化的常见原因。

```bash
npm ls vue
# my-app@1.0.0
# └── vue@3.4.21
npm ls --all | head -n 20
# 列出完整依赖树的前若干行
```

> 依赖提升是布局优化，不改变依赖声明本身。

**速记**：提升减少重复副本，代价是幽灵依赖，用依赖树命令确认实际版本与层级。



### npm 与 pnpm 与 yarn 的差异

三者的目标一致，差异集中在文件如何存放、依赖目录如何组织以及工作区怎么表达。本节从布局、命令与选型三方面对照。

#### 安装布局：扁平与内容寻址

**扁平布局**：是把依赖尽量平铺到顶层依赖目录的存放方式；**内容寻址存储**：是按文件内容哈希集中存放、再以硬链接连接到各项目的存放方式。

- 传统布局：多数包管理器采用扁平或半扁平布局，同一版本在不同项目间会重复下载。
- 内容寻址：依赖文件集中存放在全局仓库，项目内通过硬链接指向，磁盘占用显著降低。
- 结构严格：部分包管理器的依赖目录只暴露显式声明的包，未声明即无法导入。
- 兼容问题：依赖硬链接的布局对少数按真实路径查找文件的包不友好。
- 判断方式：对比同一项目在不同包管理器下的依赖目录体积即可看出差异。

```bash
pnpm store path
# /Users/example/.pnpm-store/v3
du -sh node_modules
# 对比不同包管理器下同一项目的依赖目录占用
```

> 布局差异会直接影响幽灵依赖能否出现，依赖目录越严格，越早暴露未声明的导入。

**速记**：扁平布局易产生重复与幽灵依赖，内容寻址按哈希集中存放并硬链到项目。



#### 常用命令对照

**命令对照**：是把常用操作在各包管理器中的写法并列，便于迁移既有项目与统一团队脚本。

- 安装全部依赖：npm install、pnpm install 与 yarn install 语义一致。
- 安装单个包：npm install 包名、pnpm add 包名、yarn add 包名。
- 移除包：npm uninstall、pnpm remove 与 yarn remove 对应同一动作。
- 运行脚本：npm run 脚本名、pnpm run 脚本名，yarn 可直接写脚本名。
- 升级依赖：npm update、pnpm update 与 yarn upgrade 的默认范围略有差别。

```bash
pnpm add vue
pnpm remove lodash-es
pnpm run build
# 日常操作与 npm 一一对应，迁移时逐条替换即可
```

> 各命令的完整选项与注册表配置详见 后端/Node 主题第 6 篇 npm 与包管理，本篇只比较与依赖治理相关的差异。

**速记**：安装、移除与运行脚本三家语义相近、写法有别，迁移时逐条替换即可。



#### 工作区与选型

**工作区（workspace）**：是在单个仓库内管理多个包的机制，包之间可以互相引用而不必先发布到注册表。

- 协议引用：用 workspace 前缀声明引用本地包，解析时直接指向仓库内目录。
- 依赖统一：工作区可在根目录统一安装与锁定版本，减少跨包版本漂移。
- 目录声明：工作区成员通过配置文件里的路径通配符声明，如 packages 与 apps 两类目录。
- 选型依据：新项目优先考虑磁盘占用与依赖严格性，老项目优先考虑生态与团队熟悉度。
- 迁移成本：切换包管理器需要重新生成锁文件，并在流水线同步调整命令。

```yaml
packages:
  - "packages/*"
  - "apps/*"
```

```json
{
  "name": "@my-scope/shared",
  "version": "0.1.0",
  "dependencies": {
    "@my-scope/utils": "workspace:^"
  }
}
```

> 工作区组织与任务编排详见本主题第 14 篇 Monorepo 与工作区管理，此处只涉及依赖解析层面的差异。

**速记**：工作区用 workspace 协议引用本地包，选型看磁盘占用、依赖严格性与迁移成本。



### 依赖治理常见问题

依赖治理的难点不在安装本身，而在依赖树变化后暴露的隐性问题。本节列出三类高频问题：幽灵依赖、版本冲突与安全升级。

#### 幽灵依赖与重复安装

**幽灵依赖（phantom dependency）**：是代码导入了未在自身依赖字段中声明的包，仅因该包被其他依赖提升到顶层而恰好可用。

- 成因：扁平布局把未声明的包也放到顶层，导入不会立即失败。
- 风险：上游依赖调整或升级后被提升的包不再位于顶层，构建随即中断。
- 排查：用依赖树命令确认该包是否由本项目直接声明，还是来自其他包的依赖。
- 修复：把实际使用的包补进依赖字段，而不是依赖提升的偶然结果。
- 预防：依赖目录结构越严格，幽灵依赖越难成立，问题越早暴露。

```bash
npm ls lodash-es
# 若仅出现在其他包的依赖之下，说明本项目的导入属于幽灵依赖
npm explain lodash-es
# 输出引用该包的完整依赖链
```

> [!CAUTION]
> **注意内容**：幽灵依赖在本地可以正常构建，却可能在任何一次依赖变更后突然报模块找不到，必须在依赖字段中显式声明。

**速记**：幽灵依赖靠提升偶然可用，必须在依赖字段里显式声明才算稳定。



#### 版本冲突与同伴依赖

**版本冲突**：是依赖树中对同一个包出现多个不兼容版本要求的情形，处理方式取决于冲突发生在普通依赖还是同伴依赖。

- 普通依赖冲突：多个版本可以并存，但会增大体积，并可能导致类型定义不一致。
- 同伴依赖冲突：宿主项目只能提供一个版本，范围不重叠时安装直接失败。
- 排查手段：查看依赖树中该包的版本分布与各自来源，再决定从哪一环对齐。
- 解决路径：对齐版本、升级依赖链，或在必要时用覆盖字段强制统一。
- 风险控制：覆盖字段会掩盖真实的兼容问题，只在不影响正确性时使用。

```bash
npm ls vue
# 若出现多个版本并列，需要定位各自来源
npm explain vue
# 打印引用该包的依赖链，定位冲突位置
```

> 覆盖字段可以强制统一版本，但不会修复上游的兼容问题，使用时需记录原因。

**速记**：普通依赖可多版本并存，同伴依赖必须对齐，冲突用依赖树与说明命令定位。



#### 安全审计与升级策略

**安全审计**：是把依赖树中的版本与漏洞数据库比对、报告受影响包与修复版本的过程。

- 审计命令：npm audit 输出漏洞等级、受影响包与修复建议。
- 自动修复：npm audit fix 只在语义化范围内升级，跨主版本需人工确认。
- 落后检查：npm outdated 列出当前版本、期望版本与最新版本，用于规划升级。
- 升级策略：定期小步升级优于长期停滞后的集中大版本跳跃。
- 范围控制：生产依赖保持较严的范围，减少不可控变更进入产物。

```bash
npm audit
# found 0 vulnerabilities
npm outdated
# 列出当前版本、期望版本与最新版本
npm audit fix --dry-run
# 预演修复动作，不实际改动依赖
```

> [!IMPORTANT]
> **重要内容**：审计报告里的修复建议可能要求跨主版本升级，落地前要评估接口变更与回归测试成本，不能盲目执行自动修复。

**速记**：审计定期做，修复分范围内自动与跨主版本人工两类，升级宜小步持续。
