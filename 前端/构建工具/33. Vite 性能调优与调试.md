## Vite 性能调优与调试

### 速度瓶颈的定位

本节先区分开发期与构建期两类速度问题，再给出耗时观测手段与验证顺序。构建性能的通用清单见本主题第 15 篇，本节只写 Vite 特有的观测入口与调优项。

#### 启动慢与构建慢的两类成因

**速度瓶颈分类**：是按开发期冷启动与生产构建两条链路分别归因，两者的主要耗时来源并不相同。

- 开发期冷启动：耗时集中在依赖预构建与入口模块的转换，依赖越多首个页面等待越长。
- 开发期热更新：单次更新耗时取决于受影响的模块范围，边界不当会退化为整页刷新。
- 生产构建：耗时集中在模块转换、分包计算与压缩三个阶段。
- 共同因素：插件数量与每个插件的转换范围，是两条链路共有的主要变量。
- 区分方法：先确定问题出现在哪条链路，再进入对应手段，避免两类调优互相干扰。
- 依赖状态：依赖未预构建或缓存被清空时，首次数值不具备可比性。

```text
开发期冷启动耗时构成
  依赖预构建 -> 入口与首个页面涉及模块的转换 -> 浏览器首个请求返回
生产构建耗时构成
  模块转换 -> 分包与依赖图计算 -> 压缩与产物写入
```

> 两类链路的耗时构成不同，同一条优化手段在两条链路上未必都有效。

**速记**：先分清开发期与构建期，前者看预构建与转换，后者看转换、分包与压缩。



#### 耗时输出与阶段拆分

**耗时输出**：是 Vite 在启动与构建时打印的阶段明细，用于把总耗时归到具体环节。

- 启动输出：开发服务器就绪时打印预构建与服务器启动的耗时。
- 构建输出：构建结束时按阶段列出模块转换与产物生成的耗时。
- 明细开关：构建命令加 --debug 可打印更细的阶段耗时与插件处理步骤。
- 观测位置：阶段耗时打印在终端，插件自身耗时需借助调试级别输出或统计工具。
- 基线要求：优化前后在相同机器与相同依赖状态下对比，否则数据不可比。
- 多次取值：单次打印受系统负载影响，同一状态取多次结果再比较。
- 记录方式：把每次实测的阶段耗时写下来，避免多次改动后无法还原结论。

```bash
# 开发服务器启动耗时
npm run dev
# 构建阶段耗时明细
npx vite build --debug
```

> 阶段耗时是把总耗时定位到具体环节的依据，先量后调，避免凭直觉改动配置。

**速记**：用启动输出与 build --debug 的耗时分段定位环节，优化前后需同一基线。



#### 定位顺序与改动验证

**定位顺序**：是按先范围后细节、先配置后源码的次序缩小问题范围，每次只改一处并复测。

- 先比基线：记录未优化时的启动与构建耗时，作为后续对比基准。
- 再缩范围：判断问题落在依赖、业务源码还是插件转换，确定后再选手段。
- 单点改动：一次只改一项配置，改动后复测，避免多项改动叠加无法归因。
- 双向验证：开发期与构建期分别复测，确认改动没有把耗时转移到另一条链路。
- 关注正确性：任何提速改动都要回归功能，速度提升不能以产物错误为代价。
- 记录结论：把有效改动与提升幅度记录下来，形成项目自己的调优清单。

> [!NOTE]
> **提醒内容**：性能调优的结论依赖具体项目的依赖构成与代码规模，通用清单只提供候选手段，最终以本项目的实测数据为准。

**速记**：先记基线，再缩范围，每次只改一处并双向复测。



### 预热与预转换

本节说明 Vite 通过预热与按需转换减少首次请求等待的手段，两者都作用于开发期。

#### 预热的作用与配置

**预热（warmup）**：是在开发服务器就绪后提前转换指定文件，让浏览器首次请求这些模块时直接命中转换结果。

- 触发时机：服务器就绪后按配置转换文件，不阻塞启动过程本身。
- 配置位置：server.warmup.clientFiles 声明需要在客户端侧提前处理的文件。
- 取值形式：可写路径通配字符串或匹配模式数组，与项目目录结构对应。
- 收益：首个页面涉及的模块在浏览器发起请求前已完成转换，首屏等待下降。
- 代价：预热文件过多会占用启动后的处理能力，范围要按实际入口控制。
- 增量行为：预热与依赖预构建并行推进，两者同时开启会争夺处理能力，需按耗时取舍先后。
- 适用场景：入口文件导入链路较深、首屏模块数量多的项目收益最明显。

```ts
export default {
  server: {
    warmup: {
      clientFiles: ["./src/main.ts", "./src/routes/**/*.ts"],
    },
  },
};
```

> 预热把转换提前到请求之前，属于用启动后的空闲时间换取首屏响应速度。

**速记**：预热在服务器就绪后提前转换入口文件，用启动后的空档换首屏速度。



#### 按需转换与首屏请求

**按需转换**：是开发服务器在浏览器请求某个模块时才转换该模块的方式，未请求的模块不参与转换。

- 请求驱动：转换范围由浏览器实际请求的模块决定，入口越简单首屏越快。
- 请求瀑布：模块的静态导入会形成链式请求，层级越深首个页面就绪越晚。
- 优化方向：减少入口的静态导入面，把非首屏依赖改为动态导入。
- 桩对象：开发期对未访问的模块可能返回占位对象，访问时再补齐，属于预期行为。
- 观测方法：在浏览器网络面板查看首屏请求数量与耗时分布。
- 对照方式：与构建产物的加载顺序对照，可发现开发期特有的长请求链。

```js
// 把非首屏依赖改为动态导入，缩短首屏请求链
async function openEditor() {
  const { createEditor } = await import("./editor/index.js");
  return createEditor("#editor");
}
```

> 按需转换让开发期速度与首屏请求量挂钩，控制入口的静态导入面是主要手段。

**速记**：转换由请求驱动，缩短首屏请求链的关键是控制入口的静态导入。



#### 减少首次请求等待的取舍

**首次请求等待**：是浏览器发起第一个模块请求到拿到可执行代码之间的时间，由预构建、转换与网络往返共同决定。

- 预构建已就绪：首次启动时依赖预构建会带来一次性等待，缓存命中后消失。
- 缓存位置：预构建缓存位于依赖目录下，删除后会重新生成，需要重新等待。
- 预热补充：预热覆盖入口与高频页面，减少首次请求时的转换耗时。
- 依赖数量：第三方依赖数量直接影响预构建时长与请求数量，精简依赖见效直接。
- 本地缓存：浏览器侧缓存影响二次访问，清空缓存后的数值才是首次等待的真实值。
- 取舍：预热与预构建都增加启动后的开销，范围要与真实入口匹配。

> [!TIP]
> **建议内容**：把预热文件限定为入口与首屏路由，其余模块交给按需转换，可同时避免启动变慢与首屏变慢。

**速记**：首次等待由预构建、转换与往返组成，预热范围按真实入口限定。



### 依赖与产物层面的优化

本节只写 Vite 侧的依赖与产物优化项，缓存策略、体积监控与通用性能清单见本主题第 15 篇。

#### 依赖瘦身与预构建范围

**依赖瘦身**：是减少进入预构建与最终产物的第三方依赖数量，从源头降低转换量与请求量。

- 替换体积大的依赖：改用按需引入或轻量替代包，减少被打入的代码量。
- 检查重复副本：同一依赖出现多个版本会重复预构建，需在依赖树中对齐。
- 预构建白名单：只把形态特殊、必须处理的包加入 include，避免无谓开销。
- 链接依赖排除：本地链接包不参与预构建，改动即时生效并减少预构建量。
- 导入写法：从依赖的深路径或子模块入口引入，避免把整包拖入产物。
- 核对方式：对比依赖变更前后的启动耗时与产物体积。

```ts
export default {
  optimizeDeps: {
    include: ["package-needing-prebuild"],
    exclude: ["linked-local-package"],
  },
};
```

> 依赖层面的优化收益最直接，先减少依赖数量，再考虑配置层面的调整。

**速记**：依赖数量与重复副本是根本变量，预构建范围按实际需要控制。



#### 分包调整与并行加载

**分包调整**：是通过 build.rollupOptions.output.manualChunks 控制模块被分到哪个产物文件，影响首屏可并行度与缓存命中。

- 拆分依据：按访问频率与变更频率拆分，稳定的公共依赖单独成块。
- 并行加载：拆成多个体积均衡的块可利用浏览器并行请求，单块过大则首屏阻塞。
- 缓存收益：公共依赖单独成块后，业务代码变更不会使其缓存失效。
- 避免过度拆分：块数过多会增加请求数与依赖解析开销，得不偿失。
- 告警配合：构建时的分块体积告警指向具体分块，可用于判断拆分是否失衡。
- 核对方式：对比调整前后的分块清单、各块体积与首屏加载顺序。

```ts
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["framework-runtime", "state-library"],
        },
      },
    },
  },
};
```

> 分包以首屏可并行与长期缓存为目标，块数与体积需要平衡，不宜一味细分。

**速记**：按稳定性与访问频率分包，均衡体积换并行加载与缓存命中。



#### 压缩与构建目标选项

**压缩与目标选项**：是控制产物压缩方式与语法降级目标的配置，直接影响构建耗时与产物体积。

- 压缩器选择：默认压缩器之外可换用其他压缩工具，需要权衡构建耗时与体积。
- 压缩开关：构建期可临时关闭压缩用于定位问题，定位完成后恢复。
- 构建目标：build.target 决定语法降级程度，目标越旧转换步骤越多、产物越大。
- 样式目标：build.cssTarget 控制样式降级目标，与脚本目标可分别设置。
- 取舍：目标越新产物越小且构建越快，但浏览器兼容范围越窄。
- 验证：改动目标后要在目标浏览器实测，确认产物可正常执行。

```ts
export default {
  build: {
    target: "esnext",
    minify: true,
    cssTarget: "esnext",
  },
};
```

> [!CAUTION]
> **注意内容**：为缩短构建时间把压缩目标设得过新，会让旧版浏览器无法运行产物，必须在兼容范围与构建耗时之间确认取舍。

**速记**：压缩方式与 build.target 同时影响构建耗时与体积，目标越旧产物越大。



### 调试工具与日志

#### 日志级别与输出控制

**日志级别**：是控制终端输出详细程度的配置，级别越高输出越少。

- 配置位置：命令行 --logLevel 或配置项 logLevel，取值从详细到精简递增。
- 常用取值：info 为默认，warn 与 error 只打印问题，silent 完全静默。
- 调试取值：debug 打印内部步骤，用于定位插件顺序与转换过程。
- 输出分工：终端输出用于过程观测，浏览器控制台用于运行期问题。
- 使用原则：日常用默认级别，定位问题时临时提升，避免长期使用详细级别淹没关键信息。
- 静默场景：脚本化调用或持续集成中可调高静默等级，只保留失败信息。

```bash
npx vite --logLevel info
npx vite build --logLevel debug
```

> 日志级别越高越安静，只有定位插件与转换问题时才临时降到 debug。

**速记**：logLevel 控制终端详细程度，默认 info，排查时才用 debug。



#### 插件耗时与钩子调试

**插件耗时**：由各插件在转换与构建阶段的处理时间构成，是构建耗时的主要变量之一。

- 观测方式：以调试级别输出各插件的处理步骤，定位耗时集中的环节。
- 关注对象：转换类插件按文件调用，命中范围过宽时会显著拖慢构建。
- 收窄范围：检查插件的包含与排除配置，把不需处理的目录移出。
- 顺序影响：插件顺序影响每个文件被处理的次数，排序机制见本主题第 26 篇。
- 重复能力：多个插件处理同一类文件会造成重复转换，应合并同类能力。
- 复测方式：调整插件范围后重新构建，对比阶段耗时而非总耗时。

```bash
# 用调试级别输出插件与钩子的处理步骤
npx vite build --logLevel debug
# 在输出中按插件名与钩子名定位耗时集中的环节
```

> 插件耗时定位的关键是看转换类插件的命中范围，而非只看插件数量。

**速记**：插件耗时集中在转换类插件，收窄包含范围比增删插件更有效。



#### 产物分析与体积核对

**产物分析**：是把构建产物按模块与依赖拆分展示，用于定位体积占比异常的来源。

- 分析入口：按所用分析工具的文档接入构建配置，生成体积报告。
- 观察指标：按压缩前后体积、按模块与按依赖分别查看占比。
- 定位路径：先看体积占比高的依赖，再看被整体打入的第一方模块。
- 与告警配合：构建时的分块体积告警指向具体分块，可与分析报告互相印证。
- 回归防护：把关键分块的体积阈值写入检查流程，防止体积无感增长。
- 处理闭环：定位到来源后回到导入写法与依赖声明修改，再复测体积。

```text
产物体积核对顺序
  1. 读构建输出的分块体积与告警
  2. 用分析报告按依赖与模块拆分排序
  3. 核对导入写法与依赖版本是否重复
```

> 分析报告只回答体积去了哪里，回到导入写法与依赖声明才能把体积降下来。

**速记**：先读分块告警再按依赖拆分，定位后回到导入写法与依赖声明。



### 常见性能问题处置

本节只列 Vite 特有的三类性能问题，报错排查的通用方法见本主题第 16 篇。

#### 全量刷新过多

**全量刷新过多**：是开发期本应局部热更新却频繁整页重载的现象，表现为状态丢失与刷新次数偏多。

- 成因一：模块未声明热更新边界，更新向上冒泡到入口后提交整页刷新。
- 成因二：被改动的文件位于热更新链路之外，如全局样式或入口配置。
- 成因三：运行期报错使客户端与开发服务器断开，重连后触发整页刷新。
- 排查：观察终端输出的是热更新还是整页刷新，先确定是哪个文件触发。
- 处置：为高频修改的模块声明边界，或依赖框架插件提供的边界处理。
- 判定口径：偶发的整页刷新不必处理，单位时间内反复出现才计入问题。
- 附带收益：刷新次数下降后单次改动后的等待时间同步缩短。

```bash
# 终端输出区分两类更新
# hmr update 表示热更新
# page reload 表示整页刷新
```

> 区分热更新与整页刷新是定位刷新过多的第一步，输出中的文件名指向触发源。

**速记**：看终端输出区分 hmr update 与 page reload，为高频模块补热更新边界。



#### 产物体积异常

**产物体积异常**：是产物体积明显超出预期，常见于依赖被整体打入、分包不当或资源未处理。

- 整包打入：只用到一个依赖的少部分能力，却因导入写法把整包带入产物。
- 重复依赖：同一依赖的多个版本同时进入产物，需要先对齐版本。
- 大资源未处理：图片与字体未压缩或未按需内联，直接抬升产物体积。
- 分包失衡：单个分块过大，或在多个分块中重复出现同一模块。
- 核对顺序：先看分块体积告警，再用分析报告定位具体模块。
- 收尾动作：修改导入写法或依赖版本后复测，并补充体积阈值检查。

```text
产物体积异常核对顺序
  1. 读构建输出的分块体积与告警
  2. 按依赖与模块拆分定位占比最高的来源
  3. 核对导入写法、依赖版本与资源处理
```

> [!WARNING]
> **警告内容**：只看总体积不看分块构成，容易把优化方向指向压缩配置，而真正的来源往往是被整体打入的依赖。

**速记**：先看分块告警再按依赖拆分，多为整包导入、重复版本与大资源未处理。



#### 构建内存溢出

**构建内存溢出**：是构建过程占用内存超过运行时上限导致进程被终止，表现为日志中断或堆内存报错。

- 触发环节：模块转换、分包计算与压缩阶段的内存峰值最高。
- 常见诱因：单次处理的模块范围过大、统计信息全量生成、并行度过高。
- 处置一：减少构建期不必处理的目录，缩小模块转换的输入范围。
- 处置二：按需关闭或降低产物映射精度，减小中间数据的占用。
- 处置三：调整运行时可用内存上限，该配置属 Node 运行时范畴，详见后端/Node 主题。
- 观察方式：记录构建中断的环节与当时的模块规模，判断是峰值超限还是持续增长。

```bash
# 提高可用内存上限（参数取值以 Node 文档为准）
NODE_OPTIONS=--max-old-space-size=4096 npx vite build
```

> [!NOTE]
> **提醒内容**：内存溢出先缩小处理范围，再考虑放宽内存上限；放宽上限只是容纳峰值，并不会降低实际占用。

**速记**：内存峰值集中在转换、分包与压缩，先缩范围再调上限。
