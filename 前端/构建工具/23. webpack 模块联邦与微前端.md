## webpack 模块联邦与微前端

### 模块联邦要解决的问题

#### 多应用共享代码的现实困境

**多应用共享代码**：是多个独立前端应用需要复用同一份组件、工具函数或状态逻辑时，在打包层面遇到的复用障碍。

- 共享范围：常见于设计系统组件、鉴权逻辑、埋点工具与跨业务的公共页面。
- 直接复制：代码被复制到各应用，修改要在多处同步，行为逐渐分叉。
- 版本分发：抽成独立包后，每次改动都要走发布、升级与重新构建的完整链路。
- 构建隔离：各应用独立构建，构建产物之间无法在运行时直接互相引用。
- 时效矛盾：公共代码更新后，尚未重新构建的应用无法立即获得新版本。

```text
组件库改动 → 发布新版本 → 各应用升级依赖 → 各应用重新构建 → 各应用重新部署
      ↑                                                        ↓
      └──────────── 任一应用漏跟，版本分叉 ──────────────────────┘
```

> 困境的本质是复用粒度被构建边界锁死：跨应用复用必须先经过一次完整的打包与发布。

**速记**：多应用共享代码的痛点是复用必须经过发布与重新构建，构建边界挡住了运行时复用。



#### 独立发布与独立部署的诉求

**独立发布**：是每个应用或模块各自构建、各自上线、互不等待的交付方式。

- 团队自治：各团队按自身节奏迭代，不被其他团队的发布窗口阻塞。
- 故障隔离：单个应用的构建失败或上线回滚不影响其他应用。
- 灰度能力：新增功能可以只对部分应用或部分用户生效。
- 技术栈差异：不同应用可以使用不同框架版本，只要共享部分约定了接口。
- 交付频率：公共模块的更新不必等待所有消费方排期。

```bash
# 各应用独立构建与部署，共享模块单独产出并发布
npm run build --workspace apps/shell
npm run build --workspace apps/catalog
npm run build --workspace packages/design-system
```

> [!IMPORTANT]
> **重要内容**：独立发布要求共享模块的接口保持向后兼容，任何破坏性改动都必须与消费方约定升级节奏，否则先构建的应用会在运行时直接报错。

**速记**：独立发布追求团队自治与故障隔离，代价是接口必须自行维持向后兼容。



#### 与打包成 npm 包复用的差异

**npm 包复用**：是把公共代码发布为包、由各应用安装并打进各自产物的复用方式；**模块联邦（Module Federation）**：是把共享模块留在提供方的构建产物里、由消费方在运行时加载的复用方式。

- 加载时机：npm 包在构建期被并入消费方产物，联邦模块在运行时按需请求。
- 更新生效：npm 包需要消费方重新安装并构建，联邦模块可由提供方单侧更新。
- 版本控制：npm 包用版本号与锁文件约束，联邦模块用共享作用域在运行时协商。
- 构建开销：npm 包会重复出现在每个消费方产物中，联邦模块只保留一份。
- 风险位置：npm 包的问题在构建期暴露，联邦模块的问题在运行时暴露。

```json
{
  "name": "@my-scope/design-system",
  "version": "2.1.0",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "peerDependencies": {
    "react": ">=17"
  }
}
```

> 两种方式不是替代关系：稳定的公共代码用包分发更简单，需要频繁更新且跨应用同步的模块更适合联邦。

**速记**：包复用胜在构建期可控，联邦复用胜在运行时不重建即可更新，风险从构建期挪到运行时。



### 配置结构与角色划分

#### host 与 remote 的两种角色

**host**：是主动加载其他应用模块的消费方；**remote**：是暴露自身模块供他人加载的提供方；同一应用可以同时扮演两种角色。

- 角色判定：按模块流向判定，加载别人的是 host，被别人加载的是 remote。
- 双向引用：两个应用互相暴露并互相加载时，双方既是 host 也是 remote。
- 构建独立：两种角色各自的构建互不依赖，只需约定远程入口地址。
- 部署顺序：一般先部署 remote，再让 host 引用新地址。
- 复用粒度：暴露的单位是模块路径，可以是一个组件、一个页面或一个初始化函数。

```text
remote（提供方）── remoteEntry.js ──▶ host（消费方）
  exposes: { "./Button": ... }        remotes: { designSystem: "designSystem@<地址>/remoteEntry.js" }
```

> 角色由配置声明而非代码结构决定，同一个工程切换角色只需改动插件参数。

**速记**：host 加载他人模块，remote 暴露自身模块，角色由配置声明，可同时兼任。



#### exposes 与 remotes 的写法

**exposes**：是 remote 在插件配置里声明对外提供哪些模块的字段；**remotes**：是 host 声明可以从哪里加载远程模块的字段。

- 暴露写法：exposes 的键是消费方使用的模块名，值是指向源文件的相对路径。
- 引用写法：remotes 的键是本地使用的别名，值是容器名加真实地址的字符串。
- 路径规则：暴露路径以点斜杠开头，消费方按同样的字符串导入。
- 地址来源：远程入口地址可以写成运行时变量，便于按环境切换。
- 命名一致：remotes 的键要与消费方代码里的导入前缀一致，否则解析失败。

```js
// remote 侧：声明对外提供的模块
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'designSystem',
      filename: 'remoteEntry.js',
      exposes: {
        './Button': './src/components/Button.tsx',
        './formatPrice': './src/utils/formatPrice.ts'
      },
      shared: { react: { singleton: true } }
    })
  ]
};
```

```js
// host 侧：声明远程入口，之后即可按别名导入
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'shell',
      remotes: {
        designSystem: 'designSystem@https://cdn.example.com/design-system/remoteEntry.js'
      },
      shared: { react: { singleton: true } }
    })
  ]
};
```

> 地址写死在配置里会让同一份配置只能服务一个环境，通常结合环境变量注入远程入口地址。

**速记**：exposes 声明对外提供的模块路径，remotes 声明远程入口地址与本地别名，两侧字符串必须一致。



#### 入口文件与容器约定

**容器（container）**：是 remote 构建产物中约定的入口文件，对外暴露初始化共享作用域与获取模块的接口，由构建工具生成。

- 生成方式：插件按 name 与 filename 生成容器文件，不需要手写。
- 关键接口：初始化共享作用域与按路径取模块两类方法由容器提供。
- 异步边界：共享依赖要求在入口处先完成共享作用域初始化，再执行应用代码。
- 入口写法：应用启动代码放进动态导入的回调或独立启动文件，保证初始化在前。
- 路径可达：容器文件必须能被 host 通过网络请求到，通常配合绝对公共路径。

```js
// host 入口：先初始化共享作用域，再启动应用
import('./bootstrap');

// bootstrap.ts 内正常创建应用
import { createRoot } from 'react-dom/client';
import { App } from './App';

createRoot(document.getElementById('root')).render(<App />);
```

```js
// webpack 配置：远程容器以绝对地址对外发布
module.exports = {
  output: {
    publicPath: 'https://cdn.example.com/design-system/',
    uniqueName: 'designSystem'
  }
};
```

> [!CAUTION]
> **注意内容**：把应用启动代码直接写在入口顶层，会让共享依赖在这段代码执行时尚未进入共享作用域，容易出现同一框架被加载两份，表现为状态丢失或初始化异常。

**速记**：容器由插件生成并暴露两类接口，入口需留异步边界，先初始化共享作用域再启动应用。



### 共享依赖与版本协商

#### shared 配置的声明方式

**shared**：是声明哪些依赖进入共享作用域、由多个应用共用的配置字段。

- 简写形式：数组写法只声明包名，按包的元数据推断版本范围。
- 完整形式：对象写法可为每个包单独声明是否单例、是否立即加载与所需版本。
- 版本依据：所需版本默认取自本应用安装的版本，可与依赖字段解耦。
- 加载时机：标记为立即加载的依赖随容器一起加载，其余在首次使用时加载。
- 适用范围：框架与状态管理必须共享，纯工具函数可共享也可不共享。

```js
new ModuleFederationPlugin({
  name: 'shell',
  remotes: {
    designSystem: 'designSystem@https://cdn.example.com/design-system/remoteEntry.js'
  },
  shared: {
    react: {
      singleton: true,
      requiredVersion: '^18.0.0',
      eager: false
    },
    'react-dom': {
      singleton: true,
      requiredVersion: '^18.0.0'
    }
  }
});
```

> 未列入 shared 的依赖会被打进各自产物，框架类依赖未共享时页面上会出现两份实例。

**速记**：shared 决定哪些依赖进入共享作用域，数组写法用默认行为，对象写法逐包声明单例与版本。



#### 单例依赖与运行时实例唯一

**单例（singleton）**：是同一依赖在整个页面内只保留一个实例的共享模式，用于框架与全局状态类依赖。

- 必要性：依赖内部持有模块级状态时，多实例会导致状态不互通与判断错误。
- 典型对象：组件框架、上下文容器、路由器与全局事件总线。
- 配置方式：在 shared 中把该包的 singleton 设为真。
- 即时加载：标记为立即加载可避免初始化顺序造成的重复实例。
- 反面情形：无状态且体积小的工具包不需要单例，强制单例会挤占协商空间。

```js
shared: {
  react: { singleton: true, eager: true },
  'react-dom': { singleton: true, eager: true },
  'date-fns': { singleton: false }
}
```

> [!IMPORTANT]
> **重要内容**：框架及其配套渲染库必须同时声明为单例，只对其中一个设单例会让两套渲染协调逻辑混用，出现难以定位的渲染异常。

**速记**：持有模块级状态的依赖必须单例，框架与渲染库要成对声明。



#### 版本不匹配的后果与处置

**版本协商**：是多个应用在同一共享作用域内对同一依赖提出不同版本要求时、挑选唯一可用版本的过程。

- 挑选规则：在满足各消费方范围的前提下选用最高版本，范围互斥时无法同时满足。
- 单例约束：单例依赖只能保留一份，范围不重叠时其中一个应用会拿到非期望版本。
- 表现症状：接口缺失报错、行为不一致，且常出现在特定跳转路径上。
- 暴露时机：问题通常在路由切换触发远程模块加载时出现，构建期无任何提示。
- 处置方式：统一各应用主版本、放宽所需版本范围，或把该依赖移出共享清单。

```text
应用 A 需要 react 主版本 18
应用 B 需要 react 主版本 17
单例协商：范围无交集 → 只能保留一份 → B 侧按 18 的行为运行，可能出现不兼容调用
```

```js
// 放宽范围，允许同一主版本区间内协商
shared: {
  react: { singleton: true, requiredVersion: '>=17 <19' }
}
```

> [!WARNING]
> **警告内容**：共享依赖版本不匹配的故障在构建期不可见，只能在运行时暴露，验收必须覆盖跨应用路由跳转与状态传递这类真实路径。

**速记**：协商取满足条件的高版本，单例遇范围互斥只能留一份，故障只在运行时可发现。



### 运行时远程模块加载

#### 远程模块的动态导入与加载时机

**动态导入**：是 host 侧用导入函数在运行时按需请求远程模块的方式，返回一个 Promise。

- 触发时机：通常在路由匹配、点击交互或条件渲染时触发，而非应用启动时。
- 加载内容：先请求远程容器文件，再按需请求该模块对应的分块。
- 分包配合：远程模块自身的依赖会拆成独立分块，随容器地址解析。
- 状态处理：加载期间需要展示加载态，避免界面空白无反馈。
- 提前加载：对高概率使用的远程模块可在空闲时提前请求，减少等待。

```js
import { lazy, Suspense } from 'react';

const RemoteChart = lazy(() => import('designSystem/Chart'));

export function Dashboard() {
  return (
    <Suspense fallback={<div>模块加载中</div>}>
      <RemoteChart series={[12, 30, 18]} />
    </Suspense>
  );
}
```

> 远程模块的解析依赖公共路径，部署在子目录或内容分发网络时必须保证容器地址与分块地址都可达。

**速记**：远程模块用动态导入按需加载，配合加载态与提前请求，地址解析依赖公共路径。



#### 加载失败的兜底与降级

**加载失败兜底**：是远程容器或分块请求失败时，用本地实现或错误界面替代的处理方式。

- 失败来源：网络不可达、地址变更、容器文件名改动与版本不兼容。
- 捕获位置：在动态导入返回的 Promise 上接错误处理，或由上层错误边界统一接收。
- 降级策略：回退到内置的简化组件、提示重试，或隐藏该功能入口。
- 超时控制：对远程请求设置超时，避免长时间停留在加载态。
- 监控上报：记录失败的远程名与地址，便于区分是发布问题还是网络问题。

```js
const loadRemoteWidget = async () => {
  try {
    const mod = await import('designSystem/Widget');
    return mod.default;
  } catch (error) {
    reportLoadFailure({ remote: 'designSystem', reason: String(error) });
    return FallbackWidget;
  }
};
```

> [!CAUTION]
> **注意内容**：只依赖默认的错误边界会让加载失败表现为整页崩溃，每个远程模块的调用点必须单独提供降级分支。

**速记**：远程加载失败要捕获、降级并上报，避免把局部失败放大成整页崩溃。



#### 跨应用类型共享的落地

**类型共享**：是让消费方在编译期获得远程模块类型信息的手段，运行时机制本身不传递类型。

- 类型来源：由提供方在构建时产出声明文件并单独分发。
- 分发方式：把声明文件随组件包发布，或放入独立的类型包供各应用安装。
- 路径映射：消费侧用路径别名把远程模块名映射到本地声明文件。
- 同步要求：接口变更时声明文件与产物必须同版本更新，否则类型与实现脱节。
- 兜底处理：缺少类型时先补充模块声明，避免为了类型错误阻断构建。

```ts
// types/remotes.d.ts：为远程模块补充声明，模块名与导入字符串保持一致
declare module 'designSystem/Chart' {
  export interface ChartProps {
    series: number[];
  }
  const Chart: (props: ChartProps) => JSX.Element;
  export default Chart;
}
```

> 类型声明不参与运行时，接口演进的同步要纳入发布流程，否则编辑器提示会滞后于真实行为。

**速记**：类型由声明文件单独分发并用路径映射接入，必须与产物同版本更新。



### 落地成本与替代方案

#### 构建与部署的耦合约束

**构建约束**：是模块联邦对共享依赖清单、公共路径与发布顺序提出的强制要求。

- 共享清单一致：参与共享的应用必须对同一批依赖声明共享，否则出现重复实例。
- 公共路径固定：远程入口地址一旦发布就被引用，改动需要通知所有消费方。
- 发布顺序：新增或改名暴露模块时，先发布提供方再更新消费方配置。
- 回滚复杂：只回滚消费方而不回滚提供方，可能加载到不兼容的接口。
- 环境管理：开发、预发与生产各有独立地址，配置需要按环境注入。

```text
约束清单
1. 各应用共享依赖的主版本保持一致
2. 每个 remote 的容器地址在环境配置中集中维护
3. 暴露模块只增不改名，废弃时先标记再移除
4. 发布与回滚以提供方和消费方成组为单位
```

> [!WARNING]
> **警告内容**：把远程入口地址直接写死在业务代码里，会让地址变更变成一次全量代码改动，地址必须集中在一处按环境维护。

**速记**：联邦要求共享清单一致、地址固定、发布有序、回滚成组，这些约束要写进流程。



#### 与 iframe 方案的分工

**iframe 方案**：是把子应用放入独立文档上下文、通过地址嵌入主应用的方式，与应用内模块级集成属于两条不同路线。

- 隔离程度：iframe 拥有独立文档与样式作用域，隔离最彻底。
- 集成成本：跨文档通信需要约定消息协议，无法直接共享状态与路由。
- 体验差异：弹窗、拖拽与尺寸自适应受文档边界限制。
- 适用场景：第三方系统、强隔离要求或技术栈差异极大的场景。
- 配合方式：页面级嵌入用 iframe，组件级复用用模块联邦。

```text
iframe：页面级嵌入，隔离强，通信通过消息传递
模块联邦：组件级复用，共享运行时，可直接调用与传参
```

> [!NOTE]
> **提醒内容**：选型先看复用粒度，需要共享路由与运行时状态的场景不适合用 iframe 承载。

**速记**：iframe 隔离强但通信成本高，适合页面级嵌入；组件级复用交给模块联邦。



#### 与 npm 包复用的取舍

**复用取舍**：是按模块的更新频率、消费方数量与稳定性，在包分发与联邦共享之间选择。

- 选包分发：接口稳定、更新不频繁、消费方需要独立控制版本的公共库。
- 选联邦共享：更新频繁、需要一次发布全量生效、消费方无法及时重建的模块。
- 混合使用：基础库用包分发，业务级模块用联邦共享。
- 团队条件：联邦需要平台侧维护地址配置与发布流程，团队规模小时成本偏高。
- 迁移路径：先从单个低频模块试点，验证发布流程后再扩大范围。

```text
基础工具与类型定义 → npm 包，版本稳定，构建期可控
跨应用业务模块     → 模块联邦，运行时更新，一次发布全量生效
强隔离第三方系统   → iframe，页面级嵌入
```

> 复用方式的决定因素是可接受的风险位置：构建期可控优先包分发，运行时可更新优先联邦。

**速记**：稳定的基础库用包分发，频繁变更的跨应用模块用联邦共享，强隔离场景用 iframe。
