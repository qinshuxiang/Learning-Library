## webpack 与框架项目集成

### React 项目的 webpack 配置

#### JSX 的转译接入

**JSX 转译**：是把 JSX 语法转换为普通函数调用的编译步骤，由转译器承担，与构建工具本身无关。

- 两条路线：用 TypeScript 编译器转译，或用 Babel 转译，二者都能处理 JSX 语法。
- 匹配范围：规则需要覆盖两类扩展名，并排除依赖目录以减少无谓转译。
- 与类型检查的关系：转译只做语法转换，不做类型校验，类型问题在单独环节处理。
- 运行时依赖：转换产物会引用框架的运行时函数，需要按所选模式确保入口可用。
- 缓存配置：开启转译缓存可显著缩短二次构建时间。

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: 'babel-loader',
          options: {
            presets: [
              ['@babel/preset-env', { targets: 'defaults' }],
              ['@babel/preset-react', { runtime: 'automatic' }]
            ]
          }
        }
      }
    ]
  }
};
```

> 转译规则的匹配范围与类型检查的范围必须一致，范围不一致时会出现编辑器不报错而构建报错，或反之。

**速记**：JSX 由转译器处理，规则要覆盖两类扩展名并排除依赖目录，转译与类型校验分属两个环节。



#### 开发期刷新方案接入

**开发期刷新**：是在保留组件状态的前提下替换被改动模块的机制，React 侧由配套插件与运行时实现。

- 接入位置：转译阶段的开发期转换与运行时的注入代码必须成对出现。
- 与热更新关系：刷新方案建立在模块热更新之上，热更新未开启时刷新不生效。
- 边界设置：入口等无法刷新的模块需要设置接受边界，否则会退化为整页重载。
- 生产排除：刷新相关的运行时只在开发配置中出现，不进入生产产物。
- 组合方式：插件负责注入运行时，转译选项负责加入对应的开发期转换。

```js
const ReactRefreshPlugin = require('@pmmmwh/react-refresh-webpack-plugin');

module.exports = {
  plugins: [new ReactRefreshPlugin()],
  module: {
    rules: [
      {
        test: /\.[jt]sx?$/,
        exclude: /node_modules/,
        use: {
          loader: 'babel-loader',
          options: {
            plugins: [require.resolve('react-refresh/babel')]
          }
        }
      }
    ]
  }
};
```

> [!WARNING]
> **警告内容**：只接入转译侧的开发期转换而漏掉运行时插件，构建不会报错，但每次改动都会整页重载，很容易被误判为热更新完全失效。

**速记**：刷新方案需要转译侧转换与运行时插件成对接入，且只在开发配置中出现。



#### 开发与生产的配置差异

**开发与生产差异**：是同一框架项目在两套模式下需要不同的转译目标、调试信息与优化开关。

- 转译目标：开发期面向当前运行时保留新语法，生产期按目标清单降级。
- 调试信息：开发期使用完整的映射信息，生产期按发布策略另行决定。
- 压缩与命名：生产期开启压缩与内容哈希命名，开发期使用可读名称。
- 刷新插件：开发期接入刷新，生产期移除相关插件与运行时代码。
- 环境判定：生产构建注入生产环境判定，让框架走生产分支并去掉开发期校验。

```js
const isProduction = process.env.NODE_ENV === 'production';

module.exports = {
  mode: isProduction ? 'production' : 'development',
  devtool: isProduction ? false : 'eval-cheap-module-source-map',
  plugins: [
    // 仅开发期接入刷新插件
    ...(isProduction ? [] : [new ReactRefreshPlugin()])
  ]
};
```

> 两套差异项应以一个环境判定变量为唯一入口来派生，散落写成多个判断后很难保证开发与生产路径一致。

**速记**：开发与生产在转译目标、映射信息、压缩命名与刷新插件上分歧，统一由一个环境判定派生。



### Vue 项目的 webpack 配置

#### 单文件组件的 loader 链

**单文件组件（SFC）**：是把模板、脚本与样式写在同一文件中的组件格式，需要专用 loader 拆块后分别处理。

- 入口 loader：负责解析文件并拆出各语言块，再把块交给后续 loader。
- 配套插件：负责把样式与模板规则复制到各语言块的子请求上，缺失时块内容不会被处理。
- 版本对应：loader 与插件版本必须与框架主版本匹配，是集成报错的首要排查项。
- 转译方式：脚本块可交给 Babel 或 TypeScript 转译器处理。
- 缓存与性能：单文件组件转换有一定开销，开启缓存可缩短二次构建时间。

```js
const { VueLoaderPlugin } = require('vue-loader');

module.exports = {
  module: {
    rules: [
      { test: /\.vue$/, loader: 'vue-loader' },
      { test: /\.js$/, loader: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] }
    ]
  },
  plugins: [new VueLoaderPlugin()]
};
```

> [!WARNING]
> **警告内容**：漏掉配套插件时构建通常不会失败，但样式块与模板块会被原样跳过，表现为页面无样式、模板不生效，排查时应先确认插件是否已加入。

**速记**：单文件组件由入口 loader 拆块，配套插件负责把规则分发给各语言块，两者缺一不可。



#### 模板与样式块的分别处理

**块级处理**：是按单文件组件内部的语言块分别套用规则，模板走编译、样式走样式处理链。

- 模板块：由 loader 编译为渲染函数，可选运行时编译与预编译两种模式。
- 样式块：每个样式块独立进入样式处理链，作用域属性由 loader 注入。
- 样式语言：使用预处理器时需为对应块声明额外规则并安装预处理器依赖。
- 块标识：可为样式块声明唯一标识，便于处理同一文件内的多个样式块。
- 顺序影响：样式规则的先后会影响最终注入结果，需要与样式处理链保持一致。

```js
module.exports = {
  module: {
    rules: [
      { test: /\.vue$/, loader: 'vue-loader' },
      {
        test: /\.scss$/,
        use: ['style-loader', 'css-loader', 'sass-loader']
      }
    ]
  }
};
```

> 样式块的规则与普通样式文件的规则应尽量复用同一段配置，分别维护两套规则时容易出现只在组件内失效的差异。

**速记**：模板块编译为渲染函数，样式块走样式处理链，预处理器需要为对应块单独声明规则。



#### 资源引用与路径别名

**资源引用**：是单文件组件模板与样式块中书写资源路径、再由构建解析到产物的方式。

- 路径转换：模板中的相对路径与别名会被转换为产物路径并在产物中正确引用。
- 别名对齐：构建别名与编辑器的路径配置需要指向同一目录，否则提示与构建结果不一致。
- 绝对路径：以斜杠开头的路径默认按公共路径处理，需要显式声明转换规则。
- 样式内引用：样式块中的资源引用由样式处理链的解析器负责。
- 大小写问题：路径大小写与真实文件名不一致在部分系统上不报错，跨系统构建才会暴露。

```js
module.exports = {
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src'),
      '@components': path.resolve(__dirname, 'src/components')
    },
    extensions: ['.ts', '.js', '.vue', '.json']
  }
};
```

> [!CAUTION]
> **注意内容**：别名只写在构建配置里而不更新编辑器配置，会长期出现编辑器标红、构建正常的状态，路径配置必须以一处为唯一来源。

**速记**：模板与样式中的资源路径由构建解析，别名要与编辑器配置指向同一目录。



### JSX 与 TSX 的处理差异

#### 转译与类型检查的分工

**转译与检查分工**：是把语法转换交给转译器、把类型校验交给独立进程或独立命令的两条并行链路。

- 职责边界：转译器只保证语法正确，类型错误不会阻断转换过程。
- 检查方式：类型检查在独立进程或独立命令中执行，失败时阻断流水线。
- 覆盖差异：检查需要包含声明文件与 TSX 文件，转译规则的匹配范围需与之一致。
- 顺序无关：两条链路互不依赖，可以并行执行以缩短总耗时。
- 结果对齐：检查通过不代表产物可用，运行时行为仍以实际执行为准。

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "webpack --config webpack.prod.js",
    "verify": "npm run typecheck && npm run build"
  }
}
```

> 把类型检查放进发布前的固定校验命令，是避免转译绕过类型错误的唯一可靠手段。

**速记**：转译只管语法、类型检查独立执行，两条链路并行但都要进入发布前校验。



#### 运行时选择与自动注入

**运行时选择**：是 JSX 转换后调用哪套框架入口的配置，分经典与自动两种模式。

- 经典模式：转换结果引用作用域中的框架对象，需要在使用处显式导入。
- 自动模式：转换结果自行导入运行时函数，源码无需导入框架。
- 配置位置：模式在转译器预设或编译器选项中声明，与构建配置的其余部分无关。
- 一致性：所选模式与安装的框架版本入口必须匹配，否则运行时报未定义。
- TSX 特有项：TSX 的运行时选择由编译器选项决定，需与转译配置保持一致。

```json
{
  "compilerOptions": {
    "jsx": "react-jsx",
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler"
  }
}
```

> 两种模式混用时，显式导入框架的代码与自动注入的代码会同时存在，产物中出现重复引用，配合出现报错时优先核对这里。

**速记**：JSX 运行时分经典与自动两种模式，转译配置与编译器选项必须选同一种。



#### 文件扩展名与解析顺序

**扩展名解析**：是按声明的顺序为无扩展名的导入尝试候选文件的过程，决定同名文件谁被选中。

- 顺序声明：解析扩展名的顺序即尝试顺序，列在前面的优先命中。
- 同名冲突：同目录下同时存在同名不同扩展名的文件时，顺序决定实际导入。
- 显式导入：组件导入建议写全扩展名，避免顺序调整带来意外替换。
- 框架文件：单文件组件与普通组件混用时，需要把对应扩展名纳入列表。
- 性能影响：候选扩展名越多，解析尝试次数越多，列表应保持精简。

```js
module.exports = {
  resolve: {
    extensions: ['.tsx', '.ts', '.jsx', '.js', '.vue']
  }
};
```

> [!WARNING]
> **警告内容**：随意调整扩展名顺序，可能让原本命中的文件被同类同名的另一份取代，出现改动代码却看不到变化的假象，调整顺序前先核对同目录是否存在同名文件。

**速记**：解析扩展名顺序决定同名文件的命中结果，列表要精简且调整前先核对同名文件。



### 静态资源与样式约定

#### 框架约定的资源目录

**资源目录约定**：是框架脚手架为不同类型静态资源划定的默认位置，构建配置据此决定拷贝范围。

- 公共目录：存放不参与打包、按原路径直接访问的文件，如站点图标与说明文件。
- 源码资源：参与打包的图片与字体通常放在源码目录内，由导入语句引用。
- 拷贝策略：公共目录的文件由拷贝插件原样复制，不经过资源模块处理。
- 引用差异：源码资源经导入得到最终路径，公共目录资源按固定路径直接书写。
- 冲突风险：同名文件同时存在于两处时，最终以拷贝与产出的先后顺序决定。

```js
const CopyPlugin = require('copy-webpack-plugin');

module.exports = {
  plugins: [
    new CopyPlugin({
      patterns: [{ from: 'public', to: '.', globOptions: { ignore: ['**/index.html'] } }]
    })
  ]
};
```

> 公共目录的文件不经处理，也就拿不到内容哈希与压缩，把需要长期缓存的大资源放进去会失去缓存控制手段。

**速记**：公共目录原样拷贝、不参与打包，源码资源走导入，同名文件以拷贝与产出顺序决定。



#### 样式作用域与模块化

**样式作用域**：是限定样式只作用于当前组件的策略，框架侧与构建侧各有对应开关。

- 组件级作用域：框架在编译期为选择器添加属性选择器，使样式局部生效。
- 模块化样式：启用样式模块后以对象形式导入，构建侧需要开启对应选项。
- 共存写法：全局样式与模块化样式可在同一项目并存，按文件命名区分。
- 第三方覆盖：覆盖组件库样式时需提高选择器权重或使用全局样式文件。
- 写法一致：作用域策略应与团队规范一致，避免同项目存在两种写法。

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.module\.css$/,
        use: ['style-loader', { loader: 'css-loader', options: { modules: true } }]
      },
      {
        test: /\.css$/,
        exclude: /\.module\.css$/,
        use: ['style-loader', 'css-loader']
      }
    ]
  }
};
```

> [!CAUTION]
> **注意内容**：模块化样式与全局样式使用同一条规则时，两类文件的命名冲突会让类名突然被哈希化，规则必须按文件名模式区分并明确排除关系。

**速记**：组件作用域由框架编译期实现，模块化样式由构建选项开启，两类文件规则需按命名区分。



#### 全局样式与入口引入

**全局样式**：是不属于任何组件、需要在应用启动时统一加载的样式，如重置样式与主题变量。

- 引入位置：在应用入口文件中导入，保证在组件渲染前生效。
- 加载顺序：全局样式的引入顺序决定覆盖关系，顺序需要固定。
- 提取策略：生产构建通常把样式提取为独立文件，与入口脚本一同产出。
- 变量共享：主题变量可借助预处理器的变量文件在全局与组件样式间共享。
- 避免重复：全局样式文件不应被组件重复导入，否则会在产物中出现多份内容。

```js
// 入口文件：先加载全局样式，再启动应用
import './styles/reset.css';
import './styles/theme.css';
import { startApp } from './startApp';

startApp();
```

> 全局样式的引入语句保持集中在入口一处，是让覆盖顺序可预期的最简单办法。

**速记**：全局样式集中在入口引入并按固定顺序加载，生产构建通常将其提取为独立文件。



### 从脚手架产物反查配置

#### 读取隐藏配置的方法

**配置反查**：是在脚手架封装了构建配置时，导出或查看真实生效配置的手段。

- 导出命令：多数脚手架提供导出配置或打印配置的子命令，导出结果是合并后的最终配置。
- 校验入口：配置校验子命令可在改动后快速确认配置文件语法是否合法。
- 统计输出：以详细统计运行一次构建，可核对实际命中的入口、产物与规则。
- 差异比对：把导出结果与默认配置对比，可定位脚手架额外加入的能力。
- 记录方式：把关键字段整理成清单，作为自定义配置的依据。

```bash
npx webpack configtest webpack.config.js
# 校验配置文件语法并输出错误
npx webpack --config webpack.config.js --stats detailed
# 用详细统计核对实际生效的入口、产物与规则命中
```

> 反查的目标不是照抄脚手架，而是确认哪些能力是项目真正依赖的，照抄会把无关能力一并带入维护成本。

**速记**：用导出与校验命令查看合并后的真实配置，再与默认值比对定位脚手架额外能力。



#### 可裁剪与必保留项

**裁剪项判定**：是判断脚手架默认配置里哪些能力与当前项目无关、哪些一旦删除就会破坏构建。

- 可裁剪：与未使用框架相关的规则、未启用的预处理器、面向旧运行时的额外降级。
- 必保留：入口与输出定义、解析别名、框架转译规则与静态资源规则。
- 谨慎处理：影响开发体验的缓存与构建信息项，关闭前先评估收益。
- 裁剪方式：先注释再验证，逐项确认构建与运行结果没有变化。
- 回归成本：每次裁剪后完整跑一遍开发与生产构建，避免问题延迟暴露。

```js
// 裁剪后保留的最小可用配置：入口、输出、框架转译与资源规则
module.exports = {
  entry: './src/index.tsx',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash:8].js'
  },
  resolve: {
    extensions: ['.tsx', '.ts', '.js'],
    alias: { '@': path.resolve(__dirname, 'src') }
  },
  module: { rules: [babelRule, assetRule] }
};
```

> [!IMPORTANT]
> **重要内容**：一次只裁剪一项并立刻验证，是唯一能把问题定位到具体条目的做法，批量删除后再逐个排查等于重新做一次集成。

**速记**：按是否被项目实际使用区分可裁剪与必保留，一次裁一项并立即验证。



#### 迁移前的清点清单

**迁移清点**：是更换构建工具或升级脚手架前，把现有配置里真正生效的能力逐项列出。

- 能力清单：转译目标、别名、代理、环境变量注入与资源规则逐项记录。
- 行为基线：记录当前构建的产物目录、文件名规则与体积，作为对照基准。
- 特殊处理：自定义 loader 与插件、特殊文件类型与平台判断逻辑单独标注。
- 验证顺序：先迁移能一次替换的项，再处理需要替代方案的能力。
- 回退准备：保留旧配置与旧产物，直到新构建在测试环境验证通过。

```text
清点表（逐项记录，作为迁移依据）
```
