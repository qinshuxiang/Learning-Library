## webpack DevServer 与热更新机制

### DevServer 常用配置

开发服务器把产物放在内存中并通过 HTTP 提供，同时承担代理、回退与热更新推送。开发服务器与热更新的基础概念见本主题第 8 篇，本节只讲机制与实战配置。

#### static 与内容目录

**静态内容目录**：是开发服务器直接以文件形式提供的目录，未命中编译产物的请求会回落到该目录。

- 默认行为：默认以当前工作目录为内容目录，配置后改为指定目录。
- 产物优先：内存中的编译产物优先于磁盘上的同名文件。
- 多目录：以数组形式配置多个目录，靠前的优先命中。
- 访问前缀：可给内容目录设定访问前缀，避免与前端的路由路径冲突。
- 与 publicPath 的关系：产物访问路径由 output.publicPath 决定，不受内容目录影响。

```js
const path = require("path");

module.exports = {
  devServer: {
    static: {
      directory: path.resolve(__dirname, "public"),
      publicPath: "/assets"
    }
  }
};
```

> 内容目录只影响直接以文件形式访问的资源，编译产物仍按 output.publicPath 给出的路径访问。

**速记**：静态内容目录承接未命中的请求，产物优先于同名磁盘文件，访问前缀可与路由错开。



#### port 与 open 与 client

**客户端选项**：是开发服务器下发给浏览器运行时代码的一组配置，控制连接地址、日志级别与提示样式。

- port：指定监听端口，被占用时按配置决定是报错还是自动换端口。
- open：启动后自动打开浏览器，可按配置指定要打开的路径。
- client：控制浏览器端的日志级别、覆盖层显示与断线重连行为。
- host：指定监听地址，需要局域网访问时要显式放开。
- 覆盖层：编译错误以全屏浮层呈现，可按错误与告警分别开关。

```js
module.exports = {
  devServer: {
    port: 8080,
    open: true,
    client: {
      logging: "warn",
      overlay: { errors: true, warnings: false }
    }
  }
};
```

> [!TIP]
> **建议内容**：把错误与告警的覆盖层分开开关，可以避免告警遮住页面影响调试，同时保留错误提示。

**速记**：port 与 open 管启动行为，client 管浏览器侧的日志、覆盖层与重连。



#### hot 与 liveReload 的区别

**热更新（HMR）**：是在不刷新页面的前提下替换发生变化的模块；**实时刷新（liveReload）**：是检测到变化后整页重新加载。

- 粒度：热更新按模块替换，实时刷新以整个页面为单位。
- 状态：热更新可保留页面状态，实时刷新会重置页面与表单内容。
- 包含关系：开启热更新后，无法替换的变更仍会回退到整页刷新。
- 默认值：热更新通常默认开启，可显式关闭退回刷新模式。
- 判断方式：改动后观察页面是否被重置，即可分辨当前生效的是哪种方式。

```js
module.exports = {
  devServer: {
    hot: true,
    liveReload: false
  }
};
```

> [!NOTE]
> **提醒内容**：热更新并不意味着永不刷新，无法确定替换边界时仍会整页刷新，二者是包含关系而非互斥关系。

**速记**：热更新按模块替换并保留状态，无法替换时回退为整页刷新。



### HMR 的工作机制

热更新的关键在于浏览器与开发服务器之间的双向通道，以及一份描述哪些模块需要替换的更新清单。本节讲链路、替换判定与失败回退。

#### 从编译到推送的链路

**热更新链路**：是文件变化后，增量编译、更新清单生成、浏览器拉取并应用替换的完整过程。

- 监听：开发服务器监听源文件变化，触发增量编译。
- 通知：编译完成后通过长连接通知浏览器有新的更新可用。
- 拉取：浏览器运行时代码按清单请求变化的模块与新清单。
- 应用：运行时按模块边界执行替换，无需重新加载页面。
- 通道：两端通过 WebSocket 保持连接，断线后自动尝试重连。

```text
文件变化 → 增量编译 → 生成更新清单 → 经 WebSocket 通知浏览器
浏览器 → 拉取清单与变更模块 → 按边界替换 → 页面状态保留
```

> 更新以模块为单位传输，只有被替换的模块内容会重新下发，未变化的模块保持原样。

**速记**：变化经增量编译生成更新清单，由长连接通知浏览器拉取并替换。



#### 更新清单与替换判定

**替换判定**：是从发生变化的模块沿依赖关系向外查找「接受点」的过程，找到接受点才执行替换，找不到则退化为刷新。

- 清单内容：记录本次更新涉及的模块标识与对应新模块的地址。
- 向外查找：从变化的模块出发，逐层向引用它的模块方向寻找接受声明。
- 接受点：声明了可以接受该依赖更新的模块，替换从它向内生效。
- 无接受点：一路向外都没有接受声明，只能整页刷新。
- 范围影响：变化模块被越靠外的模块接受，替换覆盖的范围越大，状态丢失越多。

```text
变化模块 a.js
  ← 被 b.js 引用，b.js 声明接受 a.js  → 替换范围：a.js
  ← 若 b.js 未声明，继续向 c.js 查找 → 替换范围逐层扩大
  ← 直至入口仍无接受声明            → 整页刷新
```

> 接受声明的粒度越靠近叶子模块，替换范围越小，页面状态保留得越完整。

**速记**：替换从变化模块向外找接受点，找到才局部生效，找不到就整页刷新。



#### 更新失败与整页刷新

**回退刷新**：是替换无法完成时由运行时主动执行的整页重载，用于保证页面回到与最新产物一致的状态。

- 触发条件：找不到接受点、模块执行抛错、更新清单请求失败。
- 一致性：回退刷新后页面回到与最新产物一致的状态。
- 状态代价：表单内容与滚动位置丢失，开发体验下降。
- 定位方法：在浏览器控制台查看替换过程的输出，确认回退原因。
- 改善方向：在合适的层级补上接受声明，减少回退频率。

```text
[HMR] Updated modules: ./src/panel.js
[HMR] App is up to date.
[HMR] Cannot apply update. Need to do a full reload!
```

> [!WARNING]
> **警告内容**：把整页刷新当作热更新已生效，会掩盖真实的接受边界缺失，改动后频繁刷新应先查接受声明而非先改配置。

**速记**：找不到接受点或替换出错即回退整页刷新，用控制台日志定位回退原因。



### 接入 HMR 的方式

热更新需要模块主动声明接受边界，或由框架配套插件代为生成。本节讲自接受写法、样式处理与框架方案的接入位置。

#### 模块自接受写法

**自接受模块**：是调用模块热替换接口、声明本模块或其依赖可被替换的模块，替换时执行注册回调而不刷新页面。

- 环境判断：在模块顶层的条件判断中调用接受接口，保证生产环境不会执行。
- 自身接受：不传参数时表示接受本模块自身的更新。
- 依赖接受：传入依赖标识时表示接受该依赖的更新，由本模块负责重新渲染。
- 回调参数：接受回调可拿到更新后的模块导出，用于重新挂载。
- 清理注册：另注册清理函数，在替换前撤销上一次挂载产生的副作用。

```js
import { renderPanel } from "./panel.js";

renderPanel();

if (module.hot) {
  module.hot.accept("./panel.js", () => {
    // 依赖更新后重新渲染，页面状态保留
    renderPanel();
  });
}
```

> 接受声明写在会重新挂载的那一层，越靠近叶子模块，替换范围越小、状态保留越完整。

**速记**：用接受接口声明边界，可自身接受或接受指定依赖，替换时执行回调重新挂载。



#### 样式热更新

**样式热更新**：是样式模块被修改后，在不刷新页面的前提下把新样式写入文档、替换旧样式节点的方式。

- 前提：样式由注入方式落地，注入器记录了样式节点的位置。
- 应用方式：替换时改写对应样式节点的内容，不重建整个样式表。
- 与提取冲突：样式被提取为独立文件后无法局部替换，只能整页刷新。
- 模块化场景：模块化开启时只有受影响文件的类名映射变化，其余保持一致。
- 验证方式：改动样式后页面不刷新而外观更新，说明链路正常。

```js
// 开发期用注入方式落地样式，样式热更新才可用
module.exports = {
  module: {
    rules: [{ test: /\.css$/, use: ["style-loader", "css-loader"] }]
  },
  devServer: { hot: true }
};
```

> 样式热更新依赖注入方式，提取与热更新在开发期只能二选一，取舍见本主题第 20 篇。

**速记**：样式热更新改写已有的样式节点，前提是样式以注入方式落地且未被提取。



#### 框架侧热更新方案

**框架热更新方案**：是由框架配套的转译插件生成接受边界、把组件更新替换为局部刷新的集成方式。

- 接入位置：在脚本转译链中挂上框架对应的开发期插件，并开启热更新。
- 边界生成：插件为组件模块自动注入接受声明，无需手工编写。
- 状态保留：组件级刷新通常保留全局状态，局部状态按实现略有差别。
- 与转译独立：热更新插件挂在转译阶段，与选用的转译器相互独立。
- 常见问题：同一条规则重复挂载多个改写插件，会出现边界重复或替换异常。

```text
转译链：框架对应的开发期插件挂在脚本 loader 之前
热更新：devServer 开启 hot，插件自动为组件注入接受边界
刷新粒度：组件级局部刷新，全局状态通常保留
```

> [!NOTE]
> **提醒内容**：框架热更新方案的插件名与选项随框架版本变化，接入时以框架官方文档为准，不要照搬旧版示例。

**速记**：框架方案由插件自动生成接受边界，接入位置在转译链中，细节以官方文档为准。



### 代理与单页应用回退

开发期的前端与后端往往不同源，代理负责转发接口请求，回退负责把前端路由交给同一个入口。本节讲两者的配置结构。

#### proxy 配置结构

**代理（proxy）**：是把匹配到指定前缀的请求转发到目标服务器、并把响应回传给浏览器的开发期配置。

- 基本形式：以路径前缀为键、以目标地址为值构成的映射对象。
- 使用场景：后端接口与前端开发服务器不同源时，用代理规避跨域限制。
- 目标地址：写协议、域名与端口，路径前缀本身不会自动去除。
- 匹配范围：键可以是字符串前缀，也可以是更精细的匹配规则。
- 生效范围：只在开发服务器中生效，不进入产物，也不影响生产部署。

```js
module.exports = {
  devServer: {
    proxy: {
      "/api": {
        target: "http://localhost:3000",
        changeOrigin: true
      }
    }
  }
};
```

> 代理只在开发期生效，生产环境的同源问题由部署时的反向代理承担。

**速记**：proxy 以前缀为键、目标为值，只在开发期转发请求，不进入产物。



#### 路径重写与请求头处理

**路径重写**：是在转发前把请求路径按规则改写，去掉或替换开发期前缀；**请求头处理**：是在转发时补充或修改请求头，满足后端对来源与凭据的要求。

- 去前缀：后端接口不带开发期前缀时，用重写规则把前缀去掉。
- 改来源：开启来源改写后，请求头中的来源与目标地址保持一致。
- 凭据：需要携带 Cookie 时按配置放开凭据转发。
- 自定义头：可按函数逐请求追加请求头，用于传递鉴权标识。
- 排除项：个别路径需要直连而非代理时，用排除规则单独列出。

```js
module.exports = {
  devServer: {
    proxy: {
      "/api": {
        target: "http://localhost:3000",
        pathRewrite: { "^/api": "" },
        changeOrigin: true,
        onProxyReq: (proxyReq, req) => {
          proxyReq.setHeader("x-request-source", "dev-server");
        }
      }
    }
  }
};
```

> [!IMPORTANT]
> **重要内容**：目标地址与路径重写不匹配时，请求会以错误的路径到达后端，表现为接口一律返回未找到，需同时核对两者。

**速记**：重写负责去掉前缀，请求头处理负责来源与凭据，两者需与后端约定保持一致。



#### historyApiFallback

**单页应用回退**：是把未匹配到静态资源的请求改写到入口页面的配置，使前端路由在刷新与直达时仍能加载。

- 作用：刷新深层路由时浏览器会请求该路径，回退把它交给入口页面处理。
- 生效条件：只作用于接受文本类型的请求，静态资源请求不受影响。
- 常见写法：把回退开关设为真即可使用默认的入口页面。
- 定制重写：需要指向其他页面时，用重写规则显式指定。
- 与代理的关系：代理优先级更高，接口路径已匹配时不会再触发回退。

```js
module.exports = {
  devServer: {
    historyApiFallback: {
      rewrites: [{ from: /^\/app\/.*$/, to: "/app.html" }]
    }
  }
};
```

> 回退只解决开发期的路由直达问题，生产环境需要由服务器配置同样的重写规则。

**速记**：回退把未命中的文本请求交给入口页面，只作用于开发期，需在生产端复现。



### 调试与常见问题

热更新与代理的问题多与监听方式、连接状态和凭据传递有关。本节列出三类高频问题及定位思路，报错排查的通用方法见本主题第 16 篇。

#### 热更新不生效

**热更新不生效**：是配置已开启但改动后页面仍整页刷新或毫无反应的状态，需要按配置、边界与连接三层排查。

- 配置层：确认热更新开关开启，且样式没有被提取方式接管。
- 边界层：确认改动的模块向外能找到接受点，否则必然回退刷新。
- 连接层：确认浏览器与开发服务器之间的长连接没有被拦截。
- 产物层：确认改动的文件确实在监听范围内，没有被排除规则跳过。
- 定位顺序：依次核对控制台日志、配置项与网络连接。

```bash
npx webpack serve --mode development
# 启动后控制台会打印监听地址与长连接的连接、重连信息
```

> [!CAUTION]
> **注意内容**：在容器或远程主机中开发时，长连接地址可能被解析为容器内部地址，浏览器无法连接，热更新会表现为静默失效。

**速记**：热更新失效按配置、边界、连接三层排查，控制台日志是第一入口。



#### 文件监听与轮询

**文件监听**：是开发服务器感知文件变化的机制；**轮询监听**：是定时比对文件状态、以额外开销换取跨环境可靠性的替代方式。

- 默认机制：依赖操作系统的文件事件通知，开销小、响应快。
- 失效场景：网络文件系统、容器挂载卷等环境中事件通知常常不可靠。
- 轮询代价：定时扫描目录，文件越多、间隔越短，资源占用越高。
- 配置方式：按配置开启轮询并设定间隔，也可用环境变量统一控制。
- 权衡建议：默认监听失效时才启用轮询，并从较长的间隔试起。

```js
module.exports = {
  devServer: {
    watchFiles: {
      paths: ["src/**/*", "public/**/*"],
      options: { usePolling: true, interval: 1000 }
    }
  }
};
```

> [!TIP]
> **建议内容**：轮询间隔过短会让编辑器与构建工具同时占用大量 CPU，先确认默认监听确实失效再开启，并适当放长间隔。

**速记**：默认监听靠系统事件，容器与网络卷中改用轮询，代价是定时扫描的资源开销。



#### 跨域与凭据传递

**跨域与凭据**：是开发期前端与后端不同源时，请求是否被允许以及 Cookie 等凭据能否随请求发送的问题。

- 代理路径：同源转发从根上规避跨域，是配置成本最低的方式。
- 直连路径：保持跨域直连时，需要后端显式允许来源与凭据。
- 凭据要求：允许凭据时，来源不能写通配，必须指定具体源。
- Cookie 作用域：代理转发会改变请求的域，Cookie 的写入域需随之核对。
- 排查手段：在浏览器网络面板中查看请求头与响应头，比对两端配置。

```js
// 后端允许跨域与凭据的响应头示意
res.setHeader("Access-Control-Allow-Origin", "http://localhost:8080");
res.setHeader("Access-Control-Allow-Credentials", "true");
```

> 允许凭据与通配来源不能同时成立，出现该组合时浏览器会直接拒绝请求，且提示往往不指向真正原因。

**速记**：同源用代理规避跨域，直连需后端指定具体来源并允许凭据，Cookie 作用域随之核对。
