## webpack 与 TypeScript 集成

### 三种集成方式与取舍

webpack 只认识 JavaScript，TypeScript 必须先转译才能进入依赖图；类型检查则与转译是两件事，可以分开选型。本节对照三条主流路线的分工，tsconfig 的通用配置见 前端/TypeScript 主题第 17 篇。

#### ts-loader 的定位与适用面

**ts-loader**：是调用 TypeScript 编译器完成转译的 webpack loader，转译与类型检查可以在同一次编译中完成。

- 职责：读取 tsconfig 配置，把 TypeScript 转成 JavaScript 并处理部分语法特性。
- 优点：与语言服务同源，转译行为与编辑器一致，配置项直接复用 tsconfig。
- 代价：类型检查在同一进程内进行，项目越大编译越慢。
- 适用：中小型项目，或需要转译行为与 tsconfig 严格一致的场景。
- 不适用：对构建速度敏感、已经使用其他转译器的项目。

```bash
npm install --save-dev typescript ts-loader
# 两者的版本需兼容，安装后核对 TypeScript 版本
```

> 三条路线的差异集中在「谁来转译」与「谁来检查类型」两个问题，两者可以分开选型，不必捆绑。

**速记**：ts-loader 转译与检查一次完成，与编辑器行为一致，代价是编译速度随项目规模下降。



#### babel-loader 转译路线

**babel-loader 转译路线**：是用 Babel 的 TypeScript 预设剥离类型、只输出 JavaScript 的接入方式，转译过程不做类型检查。

- 原理：Babel 按语法剥离类型标注，不解析类型语义，速度接近普通 Babel 转译。
- 配置：在 Babel 预设中加入 TypeScript 预设，webpack 侧的规则与普通脚本一致。
- 类型检查：完全交给独立进程，构建不再因类型错误中断。
- 限制：少数依赖类型信息的语法特性无法处理，需按配置开启对应解析能力。
- 适用：已经使用 Babel 生态、希望统一转译管线的项目。

```json
{
  "presets": [
    ["@babel/preset-env", { "targets": "defaults" }],
    "@babel/preset-typescript"
  ]
}
```

> [!NOTE]
> **提醒内容**：Babel 只剥离类型、不做检查，类型错误若不另行检查，会一路进入产物并在运行时才暴露。

**速记**：Babel 路线只剥离类型、速度接近普通转译，类型检查必须另行安排。



#### swc 转译路线与选择依据

**swc 转译路线**：是用以 Rust 实现的高性能编译器替代 Babel 完成 TypeScript 与新版语法转译的接入方式。

- 能力：与 Babel 定位相近，覆盖语法降级与类型剥离，速度明显更快。
- 接入：通过对应的 loader 接进 webpack 规则，配置写在它自己的配置入口中。
- 一致性风险：降级细节与 Babel 不完全等价，切换后需核对产物行为。
- 配置双份：转译目标与语法开关与 tsconfig 分开维护，改动时要同步。
- 选择依据：构建耗时是主要矛盾、且能接受配置双份维护时选用。

```js
{
  test: /\.tsx?$/,
  exclude: /node_modules/,
  use: {
    loader: "swc-loader",
    options: {
      jsc: { parser: { syntax: "typescript" } }
    }
  }
}
```

> swc 与 esbuild 的能力、配置与适用边界见本主题第 12 篇，此处只讨论它在 webpack 中的接入位置。

**速记**：swc 路线以速度换取配置双份维护与降级细节的重新核对。



### ts-loader 路线

选定 ts-loader 后，工程侧要处理三件事：规则如何配置、转译范围如何限定、以及是否放弃内联的类型检查。本节逐项说明。

#### 安装与规则配置

**规则配置**：是在 module.rules 中为 TypeScript 文件指定匹配范围、loader 与选项的过程。

- 匹配范围：test 匹配 ts 与 tsx 扩展名，exclude 排除依赖目录。
- 解析扩展名：把 ts 与 tsx 加入 resolve.extensions，省略扩展名的导入才能解析。
- 选项：用 configFile 指定 tsconfig 路径，用 compiler 指定所用的编译器实现。
- 单一转译器：同一规则中不要同时挂多个转译器，避免重复处理同一文件。
- 产物形态：loader 输出标准 JavaScript，后续仍可接其他脚本 loader。

```js
module.exports = {
  resolve: {
    extensions: [".ts", ".tsx", ".js"]
  },
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        exclude: /node_modules/,
        use: "ts-loader"
      }
    ]
  }
};
```

> [!IMPORTANT]
> **重要内容**：忘记把 ts 与 tsx 加入解析扩展名，省略扩展名的导入会直接解析失败，报错信息通常只提示模块找不到。

**速记**：规则负责匹配与排除，解析扩展名必须同步补齐，否则省略扩展名的导入无法解析。



#### 转译范围的限定

**include**：是显式声明参与编译的目录，用于收紧转译范围；**exclude**：是声明跳过处理的目录，两者配合可减少无效编译。

- 收紧范围：把 include 指向源码目录，避免把产物目录与依赖目录纳入扫描。
- 依赖处理：依赖包中的 TypeScript 已编译为 JavaScript 时无需再次转译。
- 配置独立：tsconfig 中的 include 与 webpack 规则的 include 作用不同，需分别设置。
- 性能影响：范围越大，读取与检查的文件越多，构建与增量耗时同步上升。
- 排查方式：用编译器的耗时诊断输出了解到底处理了哪些文件。

```js
const path = require("path");

module.exports = {
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        include: path.resolve(__dirname, "src"),
        use: {
          loader: "ts-loader",
          options: {
            configFile: path.resolve(__dirname, "tsconfig.json")
          }
        }
      }
    ]
  }
};
```

> 规则中的 include 与 tsconfig 中的 include 是两套独立设置，只改一处不会同步另一处。

**速记**：用 include 与 exclude 收紧转译范围，规则与 tsconfig 的范围需分别维护。



#### transpileOnly 的取舍

**transpileOnly**：是 ts-loader 的一个布尔选项，设为真时只转译、不做类型检查，把检查职责让给独立进程。

- 效果：单次编译不再解析类型语义，构建耗时明显下降。
- 代价：类型错误不再阻断构建，产物可能带类型问题。
- 补偿：与独立类型检查进程配对使用，才能既快又不漏错。
- 增量：开启后 loader 侧可复用缓存，二次构建更快。
- 回退条件：类型定义与实现频繁不一致、且没有独立检查时不宜开启。

```js
{
  loader: "ts-loader",
  options: {
    transpileOnly: true
  }
}
```

> [!CAUTION]
> **注意内容**：单独开启 transpileOnly 而不接类型检查，等于放弃了类型系统的最后一道拦截，类型错误会直接进入产物。

**速记**：transpileOnly 以放弃检查换取速度，必须搭配独立类型检查才成立。



### 独立类型检查与并行构建

把类型检查从转译中剥离，是 TypeScript 项目在 webpack 里提速的主要手段。本节讲分离的意义、检查插件的接入，以及检查结果如何影响构建流程。

#### 类型检查与转译分离的意义

**检查与转译分离**：是让转译器只负责产出代码、由独立进程读取源码做类型分析的分工方式。

- 速度来源：转译器按文件独立处理，不再等待全项目的类型推导。
- 并行推进：检查在独立进程中进行，与 webpack 的模块处理同时推进。
- 结论一致：检查进程读取 tsconfig，结论与编辑器保持一致。
- 失败策略：类型错误按配置决定是仅提示还是中断构建。
- 结果呈现：错误随编译输出到终端，可按文件与行号定位。

```text
转译阶段：按文件剥离类型，产出 JavaScript，速度快
检查阶段：读取全项目做类型推导，在独立进程中执行
汇合点：构建结束时汇总错误，按配置决定是否中断
```

> 分离的收益随项目规模放大，小项目直接使用 ts-loader 的完整模式反而更省配置。

**速记**：转译与检查各占一个进程，速度来自并行与按文件处理，结论仍以 tsconfig 为准。



#### fork-ts-checker 的接入

**fork-ts-checker**：是把 TypeScript 类型检查放到子进程执行的 webpack 插件，常与 transpileOnly 搭配使用。

- 安装：作为开发依赖安装，在配置中引入并放入 plugins 数组。
- 典型组合：loader 侧开启 transpileOnly，插件侧承担类型检查。
- 检查范围：默认读取 tsconfig 的 include，也可显式指定类型声明文件。
- 选项：可配置检查模式、内存上限与错误输出形式。
- 增量：插件在后续编译中只检查改动相关的部分，减少重复工作。

```js
const ForkTsCheckerWebpackPlugin = require("fork-ts-checker-webpack-plugin");

module.exports = {
  module: {
    rules: [
      { test: /\.tsx?$/, use: { loader: "ts-loader", options: { transpileOnly: true } } }
    ]
  },
  plugins: [
    new ForkTsCheckerWebpackPlugin({
      typescript: { configFile: "tsconfig.json" }
    })
  ]
};
```

> [!TIP]
> **建议内容**：把检查模式设为只报告错误、由持续集成承担严格校验，可以让本地开发保持流畅而不错过拦截。

**速记**：fork-ts-checker 把检查移入子进程，与 transpileOnly 搭配构成标准组合。



#### 检查结果与构建流程的衔接

**构建失败策略**：是类型错误出现时构建应当中断还是继续的取舍，决定了检查结果如何影响产物生成与发布。

- 中断模式：出现类型错误即失败，适合持续集成与发布流水线。
- 提示模式：错误只在终端提示、构建继续，适合本地开发的迭代过程。
- 退出码：中断模式通过非零退出码向流水线传递失败信号。
- 与产物的关系：检查结果不改变已生成的产物内容，只决定发布流程是否放行。
- 环境区分：按环境切换失败策略，本地宽松、流水线严格。

```bash
npm run type-check
# 单独跑一次全量类型检查，作为发布前的门槛
```

> 类型检查是发布门槛而非打包步骤，放在流水线的校验阶段比塞进构建阶段更清晰。

**速记**：本地提示、流水线中断，检查结果只决定发布是否放行而不改变产物。



### 声明文件与路径别名对齐

类型系统依赖声明文件认识外部模块，依赖路径映射认识非相对导入；两者在 webpack 侧都要与 TypeScript 侧对齐。本节讲声明的纳入与别名的对应关系。

#### 声明文件的纳入与忽略

**类型声明文件**：是以 d.ts 结尾、只描述类型不产出代码的文件，用于为无类型的依赖或全局变量补充声明。

- 作用：为第三方包、全局变量与资源导入提供类型，供检查进程读取。
- 纳入方式：放在源码目录下由检查进程自动读取，或用配置项显式列出。
- 生成声明：库项目需要把声明一并输出时，由编译器在构建中生成。
- 忽略范围：依赖包自带的声明不应被重复转译，通过 exclude 跳过。
- 与打包的关系：声明文件不进入产物，只服务于检查与外部消费。

```json
{
  "include": ["src", "types/global.d.ts"],
  "exclude": ["node_modules", "dist"]
}
```

> 声明文件只参与类型检查，不会出现在 JavaScript 产物中，打包时无需为它配置 loader。

**速记**：声明文件只供检查与外部消费读取、不进入产物，用 include 与 exclude 划定范围。



#### alias 与 paths 的对应关系

**路径别名对齐**：是让 webpack 的 resolve.alias 与 tsconfig 的 paths 指向同一组映射，使导入语句在编辑器与构建期解析到同一文件。

- webpack 侧：resolve.alias 用绝对路径把别名前缀映射到目录。
- TypeScript 侧：paths 以 baseUrl 为基准，把同一别名映射到目录。
- 对齐要求：两侧的别名键名与目标目录必须一一对应，不能只改一边。
- 基准差异：TypeScript 的路径相对基准目录计算，webpack 的别名要求绝对路径。
- 维护方式：把别名抽成一份共享清单，两侧配置从同一来源派生。

```js
const path = require("path");

module.exports = {
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "src")
    }
  }
};
```

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

> [!IMPORTANT]
> **重要内容**：只配置一侧的别名，会出现编辑器能跳转、构建报模块找不到，或构建通过、编辑器满屏标红两种割裂现象。

**速记**：resolve.alias 与 tsconfig 的 paths 必须同键名、同目标，维护时一并改动。



#### 别名不一致的后果

**配置割裂**：是两侧别名映射不一致导致的解析分歧，表现为编辑器与构建期给出相反的结论。

- 编辑器正常、构建失败：编辑器按 paths 解析成功，webpack 因缺少 alias 找不到模块。
- 构建正常、编辑器报错：webpack 有别名而 paths 缺失，检查进程无法定位文件。
- 类型错位：别名指向不同目录时，编辑器读到的类型可能来自另一份文件。
- 排查顺序：先核对两侧别名清单，再检查基准目录与结尾通配符是否匹配。
- 预防：别名变更时把两侧配置视为一个改动单元，避免只改一侧。

```bash
# 构建报模块找不到时，先确认该别名在两侧是否都存在
npm run build 2>&1 | head -n 20
```

> 别名问题在构建成功时不会暴露，只会在编辑器或类型检查环节显现，因此两侧必须成对修改。

**速记**：别名不一致会让编辑器与构建各说各话，核对键名、目标与通配符是排查第一步。



### 集成常见坑

集成后的故障大多不是语法问题，而是「检查是否拦得住」与「配置读的是哪一份」。本节列出三类高频坑：类型报错不阻断、声明跳过校验、编辑器与构建不一致。

#### 类型报错不阻断产物

**类型报错不阻断产物**：是转译与检查分离后，类型错误不再阻止 JavaScript 生成的默认结果。

- 成因：转译器按语法剥离类型，不读取类型语义，因此无从判断类型对错。
- 后果：类型错误可能一路进入产物，直到运行时才以行为异常暴露。
- 兜底：在流水线中单独执行类型检查，以非零退出码拦截。
- 本地习惯：把检查命令并入开发脚本，改动后即时看到反馈。
- 边界认知：类型正确性由检查保证，转译只保证语法可运行。

```json
{
  "scripts": {
    "build": "webpack --mode production",
    "type-check": "tsc --noEmit",
    "verify": "npm run type-check && npm run build"
  }
}
```

> [!WARNING]
> **警告内容**：以产物能生成为依据判断代码正确，会放过所有类型错误，发布前的校验步骤必须包含独立类型检查。

**速记**：转译不判类型，产物能生成不等于类型正确，流水线必须单独拦截。



#### skipLibCheck 的取舍

**skipLibCheck**：是让类型检查跳过声明文件内部校验的编译器选项，开启后显著减少检查量。

- 收益：不再逐条校验依赖包的声明文件，检查耗时明显下降。
- 代价：声明文件内部的类型冲突不再报告，可能掩盖依赖间的类型不一致。
- 常见冲突：多个依赖各自引用不同版本的类型包时，冲突集中在声明文件内部。
- 建议取向：应用项目通常开启，对外发布的库项目谨慎评估。
- 排查用途：临时关闭该选项，可用于定位声明文件类型冲突的来源。

```json
{
  "compilerOptions": {
    "skipLibCheck": true
  }
}
```

> 该选项的完整语义与其余编译选项见 前端/TypeScript 主题第 2 篇，此处只讨论它在集成中的取舍。

**速记**：skipLibCheck 以放弃声明文件校验换取检查速度，应用项目常用、库项目慎用。



#### 编辑器与构建期不一致

**编辑器与构建期不一致**：是同一份代码在编辑器中与构建时的解析、转译或检查结论不同，根源多为两者读取了不同的配置。

- 配置来源：编辑器读取就近的 tsconfig，构建读取规则中显式指定的配置。
- 版本差异：编辑器内置的 TypeScript 版本与项目依赖的版本不一致。
- 别名差异：一侧配置了别名而另一侧缺失，解析结果随即分歧。
- 范围差异：tsconfig 的 include 与规则的 include 不一致，检查的文件集合不同。
- 核对方法：在两侧打印所用的配置路径与版本号，逐一比对。

```bash
npx tsc --version
# 与编辑器状态栏显示的 TypeScript 版本对比
```

> [!NOTE]
> **提醒内容**：出现编辑器与构建结论相反时，优先核对配置路径与编译器版本，而不是先改代码。

**速记**：结论分歧多来自配置路径、编译器版本与别名三处，先核对来源再改代码。
