## webpack 的模块解析机制与 resolve

webpack 把源码里的每条导入语句都当成一个解析请求，从书写形式出发找到磁盘上的真实文件，这个过程由 resolve 选项控制。解析规则写错时报错出现在编译阶段且信息有限，排查成本很高。本篇讲解析的基本流程、常用选项、包字段与条件导出、别名统一，以及解析异常的读法与性能排查。webpack 的基础配置见本主题第 8 篇 webpack 核心概念与配置，loader 与 plugin 见第 9 篇；模块化规范与打包原理见第 3 篇，类型侧路径别名的通用配置见 前端/TypeScript 主题第 17 篇。

### 模块解析的基本流程

解析从导入语句的书写形式开始，经历匹配、补后缀与目录查找几个阶段。本节按阶段拆解这条链路。

#### 三类模块路径的区分

**模块路径**：是导入语句里书写的目标位置，按书写形式分为相对路径、绝对路径与模块路径三类，各自的解析起点不同。

- 相对路径：以点或双点开头，相对当前模块所在目录解析，同一写法在不同文件里指向不同文件。
- 绝对路径：以斜杠开头，从文件系统根开始解析，配置中不推荐使用，因为换机器后极易失效。
- 模块路径：不以路径符号开头，交给模块目录逐层向上查找，依赖包与路径别名都走这一类。
- 协议前缀：带冒号的写法交由对应协议处理，配置中一般只用于声明忽略某个模块。
- 书写建议：源码内一律用相对路径与别名，绝对路径只出现在构建配置里。

```text
./utils/format        相对路径：相对当前模块所在目录
/src/utils/format     绝对路径：从文件系统根开始
lodash-es             模块路径：交给模块目录逐层查找
```

> 三类路径的差别只在解析起点，与文件是否真实存在无关，形式写错时的表现同样是找不到模块。

**速记**：相对路径与绝对路径都有明确起点，模块路径交给模块目录逐层向上查找。



#### 解析顺序与后缀探测

**解析顺序**：是 webpack 拿到一个路径后依次尝试的候选集合，先按原样精确匹配，再补后缀，最后按目录规则查找。

- 精确匹配：先尝试导入语句写出的完整路径，命中即结束解析。
- 补后缀：未命中时按 resolve.extensions 的顺序逐个追加后缀再试。
- 目录查找：候选是目录时，先读该目录下的包描述文件定位入口，再退化为查找目录内的索引文件。
- 别名前置：命中别名时先替换成目标路径，再从替换结果重新走完整流程。
- 结果复用：同一请求在一个构建进程内只解析一次，结果供后续请求复用。

```text
./utils/format
  → 精确匹配 ./utils/format
  → 追加后缀 ./utils/format.js
  → 追加后缀 ./utils/format.json
  → 作为目录读包描述文件
  → 作为目录查索引文件
```

> 探测顺序决定同名前缀文件里谁被选中，同名不同后缀并存时应显式写全后缀，避免结果依赖顺序。

**速记**：先精确匹配、再按 extensions 补后缀、最后按目录查入口与索引文件。



#### 解析失败与回退行为

**回退行为**：是解析连续失败后 webpack 采取的兜底动作，包括继续向上查找模块目录、使用配置的兜底模块与直接报错三类。

- 向上查找：模块路径会在各级父目录的 node_modules 中逐层尝试，直到文件系统根。
- 兜底模块：resolve.fallback 为浏览器环境下缺失的 Node 内置模块名指定替代实现或声明忽略。
- 忽略写法：把目标写成 false 时该请求被替换为空模块，运行时得到空对象。
- 立即报错：所有候选都失败时中断构建，报错内容包含请求原文与发起该请求的文件。
- 不静默：解析失败不会退化成运行时错误，构建阶段一定给出提示。

```js
// webpack.config.js 片段
module.exports = {
  resolve: {
    fallback: {
      // 浏览器环境没有对应的内置模块，声明为忽略
      path: false,
      fs: false,
    },
  },
};
```

> [!IMPORTANT]
> **重要内容**：把内置模块声明为忽略只在打包层面消除报错，代码若真在浏览器里调用其能力，运行阶段仍会失败，必须确认该调用不会发生。

**速记**：模块路径逐层向上查找，失败可用 fallback 兜底或忽略，兜底不改变运行时的真实缺失。



### resolve 常用选项

解析行为由一组选项共同决定，改动任何一项都会改变候选集合。本节按后缀、别名与模块目录三类展开。

#### extensions 与后缀探测顺序

**resolve.extensions**：是补后缀阶段尝试的后缀数组，类型为字符串数组，默认值通常为 .js、.json 与 .wasm，按数组顺序自左向右尝试。

- 顺序敏感：把项目中最常见的后缀放最前，减少无效的文件探测。
- 覆盖写法：配置该项会整体替换默认值，需要自行补齐框架自有后缀。
- 配全原则：源码里用到的所有后缀都要出现在列表里，否则报找不到模块。
- 写法要求：后缀必须以点开头，省略点会让探测结果异常。
- 性能影响：列表越长，未命中时的探测次数越多，应只保留必要项。

```js
// webpack.config.js 片段
module.exports = {
  resolve: {
    // 覆盖默认值时必须补齐 JS 与 JSON
    extensions: [".ts", ".tsx", ".js", ".jsx", ".json"],
  },
};
```

> 显式写全后缀的导入语句不依赖该列表，列表只服务于省略后缀的写法。

**速记**：extensions 是补后缀的尝试顺序，配置即替换默认值，列表越短探测越快。



#### alias 与目录映射

**resolve.alias**：是把导入语句中的前缀替换成另一个路径的映射表，用于缩短深层路径并把目录统一到固定入口。

- 键的匹配：按书写前缀匹配，命中后把匹配部分替换为对应值。
- 常用写法：把源码根目录映射为短前缀，把框架运行时映射到固定的单份副本。
- 精确匹配：键名末尾加美元符号表示只有完全相等时才替换。
- 忽略模块：值写成 false 时该请求解析为空模块。
- 作用范围：别名对源码与依赖包内的导入同时生效，命名不宜过于通用。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "src"),
      "@components": path.resolve(__dirname, "src/components"),
    },
  },
};
```

> 别名让同一文件存在多种导入写法，团队内应只保留一种约定，混用会让依赖关系难以检索。

**速记**：alias 把前缀替换成目标路径，键末尾加美元符号表示精确匹配，值写 false 即忽略。



#### modules、mainFields 与 conditionNames

**resolve.modules**：是查找模块路径时依次尝试的目录名数组，默认只含 node_modules 并逐层向上查找；**resolve.mainFields**：是读取包描述文件时用来定位入口的字段名顺序；**resolve.conditionNames**：是在条件导出中参与匹配的条件名集合。

- modules 的写法：可写目录名，也可写绝对路径，绝对路径能省去逐层向上查找。
- mainFields 的顺序：按 target 而定，Web 目标默认优先浏览器字段与模块字段、再回退主字段，具体顺序以官方文档为准。
- conditionNames 的来源：默认值由 target 与模式共同决定，并按导入类型补充对应条件名。
- 自定义条件：包内使用自定义条件名时必须在这里补上，否则只能走到兜底分支。
- 组合影响：三项都改变候选集合，调试解析问题时先确认三者的最终取值。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  resolve: {
    modules: [path.resolve(__dirname, "src"), "node_modules"],
    mainFields: ["browser", "module", "main"],
    conditionNames: ["import", "browser", "default"],
  },
};
```

> [!TIP]
> **建议内容**：把源码目录写进 modules 能在依赖冲突时优先命中本地目录，但它会削弱路径的可读性，团队更常选择别名达到同一目的。

**速记**：modules 决定去哪找包，mainFields 决定读哪个入口字段，conditionNames 决定条件导出的分支。



### package.json 字段与条件导出

解析进入包目录后，入口由包描述文件里的字段决定。本节讲传统字段、条件导出字段与两者的优先级。

#### main、module 与 browser 字段

**入口字段**：是包描述文件中声明包入口的三个常见字段，main 指向通用入口，module 指向 ES 模块入口，browser 指向浏览器环境专用入口或文件替换表。

- main：历史最久、兼容性最好，指向构建工具与运行时都能消费的入口。
- module：社区约定，打包工具优先采用它，用于让构建阶段拿到可静态分析的 ES 模块。
- browser：取值为字符串时替换整个包入口，取值为对象时按文件逐一替换。
- 并存冲突：三个字段同时存在时选谁由 mainFields 顺序决定，不同工具的判断可能不同。
- 类型信息：以上字段都不含类型入口，类型声明另有约定。

```json
{
  "name": "example-lib",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "browser": {
    "./dist/node-fetch.js": "./dist/browser-fetch.js"
  }
}
```

> module 字段不是标准字段，消费方是否采用取决于自身实现，库作者保留 main 才能覆盖所有消费方。

**速记**：main 管通用入口、module 管打包期的 ES 模块入口、browser 按环境替换入口或具体文件。



#### exports 字段与条件分支

**exports**：是包描述文件中声明对外入口的新式字段，用一层或按条件的多层映射限定外部可以导入哪些路径，并把不同环境指向不同文件。

- 封装作用：字段一旦声明，包内未列出的路径不再允许外部导入，子路径因此受控。
- 单入口写法：值直接写成字符串，等价于只暴露主入口。
- 条件写法：值写成以条件名为键的对象，按条件命中顺序取第一个匹配项。
- 常见条件：import 与 require 区分模块体系，node 与 browser 区分运行环境，types 指向类型声明，default 作为兜底。
- 顺序规则：条件按书写顺序自上而下匹配，兜底条件必须放在最后。

```json
{
  "name": "example-lib",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.mjs"
    },
    "./package.json": "./package.json"
  }
}
```

> [!WARNING]
> **警告内容**：同时声明 main 与 exports 时，支持新字段的工具按 exports 解析、旧工具仍读 main，两者指向不同文件会让同一依赖在不同工具下行为不一致。

**速记**：exports 限定可见路径并按条件分流，条件按书写顺序匹配，兜底项必须放最后。



#### 条件匹配的优先级与限制

**条件优先**：是多个入口来源同时可用时的取舍规则，解析从最具体的形式开始，逐级退到较宽的形式。

- 优先级：exports 中的精确子路径优先于通配子路径，条件分支优先于顶层字符串写法。
- 字段取舍：声明了 exports 后，main 与 module 基本不再参与解析。
- 通配限制：通配只匹配路径片段，且被匹配的片段不能逃出包目录。
- 扩展名限制：exports 中的路径必须是完整文件路径，不参与后缀补全。
- 影响面：以上规则来自包描述文件本身，构建配置只能通过条件名间接影响选择。

```text
解析包内子路径时的尝试顺序
  → exports 中的精确子路径
  → exports 中的通配子路径
  → exports 根入口的条件分支
  → 传统入口字段（仅有 main 等时）
  → 报找不到模块
```

> 路径必须写全后缀这一条最容易踩坑，包内文件改名或换后缀时 exports 要同步更新，否则对外立即失效。

**速记**：exports 精确路径优于通配、条件优于兜底，声明即接管 main，且路径必须写全后缀。



### 别名与路径统一

别名解决深层路径难写的问题，但它同时影响构建与编辑器两套解析。本节讲写法、与类型别名的对齐以及通配用法。

#### alias 的三种取值写法

**别名取值**：是 alias 映射中值的三种形态，分别代表替换为固定路径、替换为按模块解析的目标与声明忽略。

- 字符串值：直接替换为给定路径，是使用最多的一种。
- 模块名值：值写成包名时替换为该模块，解析继续按模块路径进行。
- false 值：把该请求替换为空模块，用于屏蔽确定不用的可选依赖。
- 数组写法：以对象数组形式声明，按数组顺序逐条匹配，适合把别名拆到多个片段后再合并。
- 与合并配合：数组写法与配置合并函数配合时不会被同名键覆盖。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  resolve: {
    alias: [
      { name: "legacy-utils", alias: path.resolve(__dirname, "src/legacy") },
      { name: "optional-native", alias: false },
    ],
  },
};
```

> 数组写法与对象写法不能混用在同一个配置里，选哪种取决于是否需要与合并函数协作。

**速记**：alias 的值可为路径、模块名或 false，数组写法便于与合并函数协作。



#### 与 TypeScript 路径别名对齐

**路径别名对齐**：是让构建配置中的别名与类型检查器中的路径映射指向同一组目录，避免编辑器能跳转而构建报错，或者反过来。

- 两套配置：构建读 webpack 的 alias，类型检查读类型配置文件里的路径映射。
- 不一致表现：编辑器标红或构建报找不到模块，两种症状指向同一处缺失。
- 对齐方式：让构建配置读取类型配置文件里的路径映射并转换成别名表，避免两处手写。
- 前缀选择：别名前缀要避开依赖包名，防止把正常依赖解析到源码目录。
- 通用配置：类型配置文件本身字段的语义详见 前端/TypeScript 主题第 17 篇。

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

> 手写两份映射在项目早期没有问题，路径数量增长后必然出现偏差，让两者共享同一份来源是唯一稳定的做法。

**速记**：构建别名与类型路径映射必须指向同一目录，共享一份来源可根治不一致。



#### 通配别名与精确匹配

**通配匹配**：是别名键中带通配符的写法，把一个前缀下的所有子路径整体映射到目标目录，同时保留剩余路径片段。

- 写法：键与值中的通配符位置一致，匹配到的片段原样拼到目标路径之后。
- 生效范围：通配别名只处理该前缀下的导入，不影响其他前缀。
- 精确优先：带美元符号的精确键优先于同一前缀的通配键。
- 片段处理：匹配片段为空时命中该前缀本身，需要注意目标是否支持。
- 调试方法：解析结果不确定时先单独取一条导入语句验证，再推广到整个前缀。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  resolve: {
    alias: {
      "utils/*": path.resolve(__dirname, "src/utils/*"),
      "utils$": path.resolve(__dirname, "src/utils/index.js"),
    },
  },
};
```

> [!CAUTION]
> **注意内容**：通配别名的键写得过宽会拦截本应来自依赖包的导入，表现为找不到模块或版本错乱，键应尽量收紧到自有目录。

**速记**：通配别名把前缀下的子路径整体映射，精确键优先于通配键，键不宜过宽。



### 解析异常与性能排查

解析问题的两种表现是报错与变慢。本节讲报错的读法、如何减少探测与如何定位耗时。

#### 找不到模块报错的读法

**找不到模块报错**：是解析全部候选失败后抛出的错误，报错文本包含请求原文、发起请求的文件与已尝试的候选说明。

- 请求原文：报错首行给出未解析成功的字符串，先确认它是依赖包名还是相对路径。
- 发起者：报错会指出从哪个文件发起该导入，据此判断它来自业务代码还是依赖包。
- 候选信息：部分报错会列出已尝试的路径，直接对照即可判断是后缀缺失还是目录不存在。
- 常见成因：拼写错误、后缀未列入 extensions、别名前缀写错、依赖未安装。
- 排查顺序：先确认包是否安装，再确认解析规则，最后核对文件是否真实存在。

```text
Module not found: Error: Can't resolve './utils/format' in '/project/src'
 - 请求原文：./utils/format
 - 发起文件：/project/src/index.js
 - 首查：包是否安装、后缀是否在 extensions 中、别名前缀是否正确
```

> [!NOTE]
> **提醒内容**：报错里的路径是解析起点而非最终目标，判断成因时要结合 extensions 与别名实际生效的取值。

**速记**：先读请求原文与发起文件，再对照已尝试的候选，按安装、规则、文件的顺序排查。



#### 减少路径探测与目录层级

**探测开销**：是解析过程中为每个候选路径查询文件系统带来的开销，候选越多、目录越深，开销越大。

- 精简后缀：extensions 只保留项目实际用到的后缀。
- 收紧别名：用别名替代深层相对路径，减少逐层向上尝试的次数。
- 绝对目录：modules 中写绝对路径目录，省去逐层查找各级依赖目录。
- 收敛依赖：依赖安装位置越集中，向上查找的层级越少。
- 控制深度：源码目录层级过深会让相对路径的解析链变长，目录结构应保持扁平。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  resolve: {
    extensions: [".js", ".json"],
    modules: [path.resolve(__dirname, "src"), "node_modules"],
    symlinks: false,
  },
};
```

> symlinks 设为假能跳过链接解析、减少一次真实路径查询，代价是链接目录被当作独立模块，可能引入重复副本。

**速记**：后缀列表短、别名替代深路径、模块目录写绝对路径，是降低探测开销的三条主线。



#### 解析耗时定位与缓存

**解析耗时定位**：是借助构建统计输出找出耗时异常的模块与解析请求，再针对性地收紧规则。

- 开启方式：构建时打开性能分析开关并输出统计文件，得到模块级耗时数据。
- 观察指标：看解析与文件读取相关的耗时字段，而非只看总耗时。
- 常见异常：某个依赖包入口指向巨大的单文件，或某条路径反复触发深度探测。
- 缓存手段：resolve.unsafeCache 让解析结果在进程内按请求缓存，跳过重复的文件系统查询。
- 使用边界：缓存与实际解析选项、文件系统状态相关，解析规则频繁变动时应关闭或按依赖类型收敛。

```bash
# 输出带耗时信息的构建统计，便于定位解析热点
npx webpack --config config/webpack.config.js --mode production --profile --json > stats.json
```

> [!TIP]
> **建议内容**：解析优化先用统计输出确认热点再改配置，凭直觉精简后缀列表通常收益有限，还可能引入新的解析失败。

**速记**：先用模块级耗时统计定位热点，再用精简规则与解析缓存收敛，改前先有数据。
