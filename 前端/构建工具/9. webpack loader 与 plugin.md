## webpack loader 与 plugin

webpack 本体只处理 JavaScript 与 JSON，其余一切文件类型与构建动作都交给 loader 与 plugin。本篇讲清两者的具体用法：loader 链怎么排、脚本与样式与资源各用什么 loader、常用 plugin 怎么配、自定义扩展怎么写。webpack 的基础概念与 entry、output、mode 的写法详见本主题第 8 篇 webpack 核心概念与配置。

### loader 链与执行顺序

loader 把非 JavaScript 文件转换成模块，链式声明与执行方向决定了转换结果是否正确。

#### 规则的写法与匹配字段

**module.rules**：是 loader 规则的集合，每一项通过匹配字段决定哪些文件走哪些 loader。

- test：必需项，正则或正则数组，匹配模块的绝对路径。
- include 与 exclude：限定或排除目录，通常用 include 收紧到 src 以减少无关文件的处理开销。
- use：声明 loader，取值为字符串、数组或以 loader 与 options 为字段的对象。
- type：直接声明资源模块类型，取值为 asset、asset/resource、asset/inline、asset/source。
- resourceQuery：按导入语句上的查询串匹配，用于区分同一文件的不同用途。

```js
// webpack.config.js 片段
const path = require("node:path");

module.exports = {
  module: {
    rules: [
      {
        test: /\.js$/,
        include: path.resolve(__dirname, "src"),
        use: [
          {
            loader: "babel-loader",
            options: { cacheDirectory: true },
          },
        ],
      },
    ],
  },
};
```

> 一条规则命中多个 loader 时，use 中的写法同时决定了执行方向与传参方式，传参写在对象形式的 options 字段里。

**速记**：rules 用 test 匹配文件、use 声明 loader，include 收紧范围能显著减少处理量。



#### 执行方向与顺序

**loader 执行顺序**：是链式调用中最容易出错的一条规则。数组形式从右到左执行，多个规则之间按 enforce 分组决定先后。

- 数组方向：use 数组中靠右的 loader 先执行，其返回值交给左侧 loader。
- 分组顺序：enforce 为 pre 的规则先于普通规则，普通规则先于 enforce 为 post 的规则。
- 阶段划分：每个 loader 有 normal 与 pitch 两个阶段，pitch 阶段自左向右执行，适合提前跳过后续处理。
- 记忆口诀：转换顺序与书写顺序相反，书写时把最先接触源文件的 loader 放在最右。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ["style-loader", "css-loader"],
      },
    ],
  },
};
```

> [!WARNING]
> **警告内容**：把 loader 顺序写反通常不会在构建时报配置错误，而是产出一份运行时报错的代码，排查时优先核对 use 数组方向。

**速记**：use 数组自右向左执行，enforce 决定规则分组先后，pitch 阶段方向相反。



#### 规则筛选与 enforce

**enforce**：是规则的执行分组字段，取值为 pre 或 post，用于保证某些 loader 在所有普通规则之前或之后运行。

- pre 组：先于普通规则执行，常见于把统一的前置处理提前到转换之前。
- post 组：后于普通规则执行，用于在最终结果上做收尾处理。
- oneOf：同一数组内只应用第一个命中的规则，可避免多规则叠加导致的重复转换。
- 行内写法：导入语句里用感叹号可直接指定 loader，与数组顺序一样从右到左。
- 优先级：行内 loader 与配置文件规则同时存在时按前置、普通、后置的顺序合并执行。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.js$/,
        enforce: "pre",
        use: ["source-map-loader"],
      },
      {
        test: /\.js$/,
        oneOf: [
          { include: /src\/legacy/, use: ["babel-loader"] },
          { use: ["esbuild-loader"] },
        ],
      },
    ],
  },
};
```

> 用 oneOf 替代多个宽泛规则，能让同一文件只走一条转换链，显著降低意外叠加的概率。

**速记**：enforce 分 pre 与 post 两段，oneOf 保证单文件只命中一条规则。



### 处理脚本的 loader

JavaScript 与 TypeScript 的转换由转译类 loader 承担，选型取决于是否需要类型检查与构建速度要求。

#### babel-loader 接入

**babel-loader**：是调用 Babel 完成 JavaScript 转译的 loader，把源码按预设与插件改写成目标环境可运行的代码。

- 配置位置：可在 use 的 options 里写 presets 与 plugins，也可使用项目根目录的 Babel 配置文件。
- cacheDirectory：设为 true 后把转换结果缓存到磁盘，二次构建明显加快。
- 范围控制：务必用 include 或 exclude 排除 node_modules，避免把依赖一并转译。
- 与构建工具分工：babel-loader 只做语法转换，垫片注入与目标范围由配置决定（详见本主题第 11 篇 Babel 与 PostCSS：转译与语法降级）。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.jsx?$/,
        exclude: /node_modules/,
        use: {
          loader: "babel-loader",
          options: {
            presets: [["@babel/preset-env", { targets: "defaults" }]],
            cacheDirectory: true,
          },
        },
      },
    ],
  },
};
```

> 转译范围与浏览器范围是两件事：preset-env 的 targets 决定降到什么语法，webpack 的 output 决定打包形态。

**速记**：babel-loader 调 Babel 转译，cacheDirectory 加速，include 与 exclude 控制范围。



#### TypeScript 的 loader 选择

**ts-loader**：是调用 TypeScript 编译器处理 ts 与 tsx 的 loader；**esbuild-loader** 与 **swc-loader** 是基于原生编译器的同类替代，速度快但类型检查能力弱。

- ts-loader：默认做完整类型检查，构建较慢；设 transpileOnly 为 true 可只转译。
- 类型检查补偿：禁用类型检查后通常配合 fork-ts-checker-webpack-plugin 在独立进程校验。
- esbuild-loader：以 esbuild 完成转译，配置少、速度快，适合只求产物不要求类型检查的场景。
- swc-loader：以 SWC 完成转译，能力与 esbuild-loader 接近，需额外声明 jsc 相关选项。
- 选型口径：类型检查交给 tsc 或编辑器时，构建链可优先选速度更快的转译 loader。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        exclude: /node_modules/,
        use: [
          {
            loader: "ts-loader",
            options: { transpileOnly: true },
          },
        ],
      },
    ],
  },
  resolve: {
    extensions: [".ts", ".tsx", ".js", ".json"],
  },
};
```

> [!NOTE]
> **提醒内容**：ts-loader 的 transpileOnly 为 true 时构建不再报类型错误，需另配 fork-ts-checker-webpack-plugin 或单独的 tsc --noEmit 检查，否则类型问题会漏到运行时。

**速记**：ts-loader 保类型检查但慢，transpileOnly 或 esbuild 与 swc 求速度，类型检查另起进程补。



#### 转译缓存与构建速度

**转译缓存**：是把 loader 的处理结果落盘复用的机制，第二次构建只重新处理改动过的文件。

- loader 自带缓存：babel-loader 的 cacheDirectory 与 ts-loader 的 transpileOnly 配合文件监听即可生效。
- 构建级缓存：webpack 5 的 cache 字段可把整个编译结果缓存在内存或文件系统（详见本主题第 10 篇 webpack 优化与分包实践）。
- 失效条件：loader 版本、配置内容或依赖内容变化时缓存自动失效。
- 权衡取舍：开启缓存会占用磁盘空间，持续集成环境中需保证缓存目录可跨次构建保留。

> 缓存不改变构建结果，但会让「改了配置却没生效」的错觉频繁出现；现象异常时先删缓存目录复验。

**速记**：loader 缓存与 webpack 文件系统缓存叠加生效，配置或依赖变化时自动失效。



### 处理样式与资源的 loader

样式与静态资源的处理是一条典型的多 loader 链，资源部分则由内置的资源模块类型接管。

#### css-loader 与 style-loader 的分工

**css-loader**：是把 CSS 文件解析成 JavaScript 模块的 loader，处理其中的 @import 与 url 引用并返回样式字符串。**style-loader**：把上一步得到的样式字符串在运行时注入页面的 style 标签。

- 顺序：use 写作 style-loader 在前、css-loader 在后，执行时 css-loader 先解析再交给 style-loader。
- modules：css-loader 的 modules 选项开启后返回类名映射对象，用于样式模块化。
- 提取：生产构建通常把 style-loader 换成 MiniCssExtractPlugin 提供的 loader，输出独立样式文件。
- 内联代价：style-loader 让样式随脚本加载，首屏可能短暂无样式，这是生产环境改用抽取的原因。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: [
          "style-loader",
          {
            loader: "css-loader",
            options: { modules: { localIdentName: "[name]__[local]--[hash:base64:5]" } },
          },
        ],
      },
    ],
  },
};
```

> 开发期用 style-loader 获得样式热替换，生产期用抽取插件输出文件，两者共用同一条 css-loader 前置链。

**速记**：css-loader 负责解析，style-loader 负责注入，开发期用它换取样式热替换。



#### 预处理器与 postcss-loader 串联

**postcss-loader**：是调用 PostCSS 处理样式的 loader，用于自动前缀、语法降级与自定义转换。**sass-loader**：调用 Dart Sass 把 Sass 源文件编译为 CSS。

- 链式顺序：sass-loader 最靠右最先执行，接着是 postcss-loader，再由 css-loader 与 style-loader 收尾。
- 依赖条件：使用 sass-loader 需要安装 sass 依赖，可在 options 中选择 implementation 与 sassOptions。
- PostCSS 配置：插件清单写在 postcssOptions.plugins 或独立的 postcss.config.js 中。
- 原理归属：PostCSS 的插件机制与配置格式详见 前端/CSS 主题第 23 篇 工程化与最佳实践。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.scss$/,
        use: [
          "style-loader",
          "css-loader",
          {
            loader: "postcss-loader",
            options: {
              postcssOptions: { plugins: ["autoprefixer"] },
            },
          },
          "sass-loader",
        ],
      },
    ],
  },
};
```

> 链越长越要先想清执行方向：每个 loader 的输出是左侧 loader 的输入，顺序错误会得到语法无法解析的中间结果。

**速记**：sass 与 postcss 依次接在 css-loader 右侧，先编译再补前缀最后解析。



#### 资源模块类型

**资源模块（asset module）**：是 webpack 5 内置的静态资源处理方式，用 rules 的 type 字段声明，取代了 file-loader、url-loader 与 raw-loader。

- asset/resource：把文件输出为独立文件并返回其 URL，对应 file-loader。
- asset/inline：把文件编码为 base64 数据写入产物，对应 url-loader。
- asset/source：把文件内容按字符串导出，对应 raw-loader。
- asset：按体积阈值自动在输出文件与内联之间选择。
- generator.filename：为单个规则指定输出模板，覆盖全局的 output.assetModuleFilename。
- parser.dataUrlCondition.maxSize：asset 类型下的内联阈值，单位为字节。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.(png|jpe?g|gif)$/,
        type: "asset",
        parser: { dataUrlCondition: { maxSize: 8 * 1024 } },
        generator: { filename: "assets/images/[name].[contenthash:8][ext]" },
      },
    ],
  },
};
```

> [!CAUTION]
> **注意内容**：把 asset/inline 用于大文件或把内联阈值调得过大，会让 base64 数据重复写进多个产物，体积与内存占用同时上升。

**速记**：asset/resource 出文件、asset/inline 出内联、asset 按阈值自动选择，生成路径由 generator.filename 决定。



### 常用 plugin 清单

plugin 面向整次编译，常用能力集中在产物生成、样式与资源处理、环境注入与构建诊断四类。

#### 产物生成：HtmlWebpackPlugin

**HtmlWebpackPlugin**：是按模板生成 HTML 并自动注入产物脚本与样式的 plugin，解决带哈希文件名无法手写引用的问题。

- template：模板文件路径，未指定时使用内置模板。
- filename：输出 HTML 的文件名，默认为 index.html。
- chunks：只注入指定入口的产物，多入口时用它区分页面。
- inject：控制注入位置，取值为 head、body 或 false。
- minify：生产构建下压缩 HTML，可传布尔值或选项对象。

```js
// webpack.config.js 片段
const HtmlWebpackPlugin = require("html-webpack-plugin");

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({
      template: "./src/index.html",
      filename: "index.html",
      chunks: ["app"],
      inject: "body",
      minify: { collapseWhitespace: true },
    }),
  ],
};
```

> 多入口项目通常为每个页面实例化一个 HtmlWebpackPlugin，用 chunks 指定各自的产物集合，避免把全部脚本注入同一页面。

**速记**：HtmlWebpackPlugin 按模板生成 HTML 并注入带哈希的产物，多页面用 chunks 区分。



#### 样式抽取与文件搬运

**MiniCssExtractPlugin**：是把 CSS 从产物中抽取为独立文件的 plugin，与它提供的 loader 配合使用。**CopyWebpackPlugin**：是把静态文件从源目录原样复制到产物的 plugin。

- 抽取插件：loader 位置填 MiniCssExtractPlugin.loader，plugin 位置用 filename 指定样式输出模板。
- 样式来源：抽取的样式来自 css-loader 的解析结果，因此必须成链配置。
- 复制插件：pattern 数组声明 from 与 to，可用 globOptions.ignore 排除文件。
- 与输出目录清空的关系：output.clean 会先清空目录再复制，复制目标写在产物内即可。
- 默认类型：CopyWebpackPlugin 默认按文件路径原样复制，不做内容处理。

```js
// webpack.config.js 片段
const MiniCssExtractPlugin = require("mini-css-extract-plugin");
const CopyWebpackPlugin = require("copy-webpack-plugin");

module.exports = {
  module: {
    rules: [
      { test: /\.css$/, use: [MiniCssExtractPlugin.loader, "css-loader"] },
    ],
  },
  plugins: [
    new MiniCssExtractPlugin({ filename: "assets/css/[name].[contenthash:8].css" }),
    new CopyWebpackPlugin({
      patterns: [{ from: "public", to: ".", globOptions: { ignore: ["**/*.md"] } }],
    }),
  ],
};
```

> [!IMPORTANT]
> **重要内容**：MiniCssExtractPlugin 的 loader 与 plugin 必须同时配置，只写其一不会抽取样式，产物中也不会出现独立样式文件。

**速记**：MiniCssExtractPlugin 的 loader 与 plugin 成对出现，CopyWebpackPlugin 用 patterns 搬运资源。



#### 环境注入与构建诊断

**DefinePlugin**：是 webpack 内置的全局常量替换 plugin，用于把编译期确定的值注入源码。**BundleAnalyzerPlugin**：来自 webpack-bundle-analyzer，用于可视化产物构成。

- DefinePlugin：键为源码中的标识符，值必须用 JSON.stringify 序列化后传入。
- 替换范围：只替换完整匹配的表达式文本，不做语法层面的作用域判断。
- 分析插件：analyzerMode 设为 static 时输出静态报告文件，openAnalyzer 控制是否自动打开。
- 报告口径：报告按代码块与模块展示压缩前体积，用于定位体积来源而非精确传输体积。
- 其他常用项：IgnorePlugin 用于忽略不需要的语言包文件，减少产物体积。

```js
// webpack.config.js 片段
const webpack = require("webpack");
const { BundleAnalyzerPlugin } = require("webpack-bundle-analyzer");

module.exports = {
  plugins: [
    new webpack.DefinePlugin({
      __APP_VERSION__: JSON.stringify("1.4.0"),
      "process.env.NODE_ENV": JSON.stringify("production"),
    }),
    new BundleAnalyzerPlugin({ analyzerMode: "static", openAnalyzer: false }),
  ],
};
```

> DefinePlugin 的书写法是替换文本而非求值，字符串值必须自带引号，否则产物会变成未定义的标识符。

**速记**：DefinePlugin 做编译期常量替换，取值需 stringify；分析插件输出静态体积报告。



### 自定义 loader 与 plugin 入门

现成方案无法覆盖时，可自行编写 loader 与 plugin，二者的代码形态与调试方式都不相同。

#### 自定义 loader 的写法

**自定义 loader**：是一个导出函数的 JavaScript 模块，接收文件内容，返回新的模块代码或 undefined。

- 函数签名：参数 source 为字符串或 Buffer，返回值作为转换结果交给下一个 loader。
- 上下文能力：this.getOptions 读取 options，this.addDependency 声明额外依赖，this.emitFile 输出文件。
- 异步处理：需要异步时调用 const callback = this.async()，处理完成后执行 callback(null, result)。
- 代码返回：返回的字符串会被当作模块源码解析，非模块内容需自行拼接导出语句。
- 声明方式：options 可用 this.getOptions 读取，配合 schema 校验更稳妥。

```js
// loaders/text-block-loader.js
module.exports = function textBlockLoader(source) {
  const options = this.getOptions();
  const language = options.language || "text";
  const escaped = JSON.stringify(source);
  return `export default { language: ${JSON.stringify(language)}, content: ${escaped} };`;
};
```

> 自定义 loader 的路径写法可用绝对路径或 npm 包名，本地文件通常放在项目根目录的 loaders 目录并用 path.resolve 定位。

**速记**：loader 是导出转换函数的模块，用 this.getOptions 读参数，异步时用 this.async() 回调。



#### 自定义 plugin 的写法

**自定义 plugin**：是一个包含 apply 方法的类实例，构造时接收选项，apply 时通过钩子接入编译流程。

- 类形态：构造函数保存选项，apply(compiler) 中注册钩子。
- 钩子选择：compiler 管整次构建，compilation 管单次编译，按需求阶段选择。
- 注册方式：同步钩子用 tap，异步钩子用 tapAsync 或 tapPromise。
- 产物写入：向 compilation.assets 写入内容或调用 compilation.emitAsset 输出文件。
- 命名约定：钩子名与 plugin 名保持一致，便于排查时定位来源。

```js
// plugins/build-report-plugin.js
const webpack = require("webpack");

class BuildReportPlugin {
  constructor(options) {
    this.options = options || {};
  }

  apply(compiler) {
    compiler.hooks.emit.tapAsync("BuildReportPlugin", (compilation, callback) => {
      const files = Object.keys(compilation.assets).sort();
      const report = JSON.stringify({ output: this.options.outputName, files }, null, 2);
      compilation.emitAsset(
        this.options.outputName || "build-report.json",
        new webpack.sources.RawSource(report)
      );
      callback();
    });
  }
}

module.exports = BuildReportPlugin;
```

> 钩子的执行时机决定能拿到什么数据：太早取不到最终产物列表，太晚则无法再影响产物内容。

**速记**：plugin 是带 apply 的类，选对钩子并用 tap 系列注册，产物通过 emitAsset 写入。



#### 调试与复用要点

**调试与复用**：指自定义扩展从本地试验到发布成包的注意事项，核心是错误定位、参数校验与版本约束。

- 错误定位：在 loader 内抛出错误时用 this.emitError，报错会带上文件路径，比抛普通异常更易追踪。
- 缓存影响：自定义 loader 的返回值参与缓存，改动实现后需提升版本或清理缓存才能生效。
- 参数校验：用 schema 校验 options，避免使用方传入错误类型后症状出现在产物中。
- 依赖声明：发布成 npm 包时把 webpack 写入 peerDependencies，避免打包多份运行时。
- 复用边界：能通过现成 loader 组合实现时优先组合，自定义代码的维护成本更高。

> 自定义扩展最容易踩的坑是缓存：实现改动后旧结果仍被复用，现象是修改不生效，清理缓存目录即可确认。

**速记**：自定义 loader 与 plugin 要认真对待缓存、参数校验与同伴依赖，能组合复用就不新写。
