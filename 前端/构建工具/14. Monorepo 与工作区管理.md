## Monorepo 与工作区管理

> [!IMPORTANT]
> **重要内容**：本篇只讲单仓多包的组织方式与任务编排，不涉及任何具体包发布平台的上传流程；发布步骤随平台而异，以所用平台文档为准。

### 单仓多包的动机

**monorepo（单仓多包）**：是把多个相互关联的包放进同一个代码仓库、共用一套工具与依赖安装的仓库组织方式。

单仓多包要解决的核心问题是：多个包之间频繁互相引用时，跨仓改动的联调与版本对齐成本过高。

#### monorepo 与 multirepo 的取舍

**multirepo（多仓多包）**：是每个包独占一个仓库、各自独立安装与发布的组织方式，与单仓多包构成一对取舍。

- 单仓优势：跨包改动一次提交完成，类型与接口变更可被同一次构建整体验证。
- 单仓代价：仓库体积与构建耗时随包数量增长，权限与发布节奏被迫统一。
- 多仓优势：各包独立演进，权限边界清晰，适合由不同团队长期独立维护。
- 多仓代价：联动升级要发多个版本并对齐依赖，联调需借助本地链接。

```bash
# 多仓联调的典型做法：把本地包临时链入宿主项目
cd ../acme-ui && npm link
cd ../acme-web && npm link @acme/ui
# 升级到发布版本时要记得解除链接，否则线上装的是本地目录
```

> 取舍的判据是耦合度：包之间改动频繁联动时倾向单仓，彼此独立、发布节奏差异大时倾向多仓。

**速记**：单仓换联动效率、付统一成本；多仓换独立性、付对齐成本。



#### 单仓多包的目录结构

**目录结构**：是按用途把包分到不同顶层目录的约定，常见划分是 apps 放可部署应用、packages 放可复用的库。

- apps：直接产出可部署站点的应用包，如面向用户的 Web 应用与管理后台。
- packages：被应用引用的库包，如组件库、工具函数库与配置包。
- 其他：按团队习惯可加 services 放服务端包、examples 放示例工程。

```text
acme-monorepo/
├── apps/
│   ├── web/          # 面向用户的 Web 应用
│   └── admin/        # 管理后台
├── packages/
│   ├── ui/           # 组件库 @acme/ui
│   ├── utils/        # 工具函数库 @acme/utils
│   └── tsconfig/     # 共享配置 @acme/tsconfig
├── pnpm-workspace.yaml
└── package.json
```

> 目录名不是硬约定，apps 与 packages 只是社区通行叫法；关键是每个子目录都有自己的 package.json，可被工作区识别。

**速记**：apps 放应用、packages 放库，每个子目录各持一份 package.json。



#### 适用与不适用场景

**适用场景**：是包之间存在真实依赖关系、需要频繁联动修改的项目形态。

- 适合：组件库加多个消费方、共享工具包加多个应用、前后端共用类型定义的工程。
- 不适合：包之间毫无耦合、由不同团队独立发布且发布节奏差异悬殊的集合。
- 慎用：单个应用即可满足需求时，引入工作区只增加配置与构建的复杂度。

```json
{
  "name": "acme-monorepo",
  "private": true,
  "packageManager": "pnpm@9.12.0"
}
```

> 判断标准是「是否存在跨包改动」：一个季度都不会同时修改两个包时，单仓带来的收益接近于零。

**速记**：有真实跨包联动才用单仓，无耦合的包集合留在各自仓库更省成本。



### 工作区协议与 pnpm workspace

**工作区（workspace）**：是包管理器对单仓内多个包的统称，也是安装器把内部包互相链接、统一安装依赖的机制。

#### 工作区的概念与根配置

**根配置**：是仓库顶层 package.json 与工作区声明文件共同定义的包清单与安装策略。

- npm 与 yarn：在根 package.json 写 workspaces 字段，值为包目录的匹配模式数组。
- pnpm：用独立的 pnpm-workspace.yaml 声明包目录，根 package.json 不再写 workspaces 字段。
- 根包：根 package.json 承载全仓脚本与公共开发依赖，本身通常不产出任何发布物。

```json
{
  "name": "acme-monorepo",
  "private": true,
  "workspaces": ["apps/*", "packages/*"],
  "scripts": {
    "build": "pnpm -r run build"
  }
}
```

```yaml
# pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
```

> [!WARNING]
> **警告内容**：根 package.json 必须声明 private 为 true，否则一次误执行的发布命令会把整个仓库当作一个包上传。

**速记**：npm 与 yarn 在根 package.json 写 workspaces，pnpm 改用 pnpm-workspace.yaml。



#### 安装与依赖安置

**依赖安置**：是工作区安装时决定「依赖装在根还是装在某个子包」的规则，直接影响包能否独立运行。

- 根公共依赖：全仓共用的开发工具（如构建器、检查工具）装在根，子包可直接调用其命令。
- 子包依赖：只有某个包需要的运行期依赖装在子包包内，保证该包被单独提取时仍能工作。
- 统一安装：在根执行一次安装即处理全部子包，提升频率为每个包一次。
- 严格结构：pnpm 只把已声明的依赖暴露给包，未声明的包即使被传递安装也无法直接引用。

```bash
pnpm install
# Scope: all 5 workspace projects
# packages/ui        | Progress: resolved 128, reused 120, downloaded 0
# apps/web           | Progress: resolved 402, reused 380, downloaded 0
# Done in 4.2s

pnpm --filter @acme/ui add lodash-es
pnpm --filter @acme/ui add -D typescript
pnpm add -Dw eslint
```

> 依赖装在哪一层，决定了该包单独构建时能否找到它；运行期依赖一律装到使用它的子包，不要图省事全塞根目录。

**速记**：公共工具装根、运行期依赖装子包，一次安装在根执行。



#### 过滤与递归命令

**过滤（filter）**：是按包名或目录路径筛选出部分工作区包、只对它们执行命令的选择器。

- 按包名：pnpm --filter 包名 run 脚本，只在该包内执行。
- 按目录：pnpm --filter ./packages/ui run 脚本，用路径选择。
- 递归：pnpm -r run 脚本，对全部工作区包依次执行。
- 并行：pnpm -r --parallel run 脚本，多个包同时执行，适合彼此独立的开发任务。
- 依赖展开：包名后加三个点表示连同其依赖一起选中，三个点加在包名前表示连同其依赖者一起选中。

```bash
pnpm -r run build
pnpm -r --parallel run dev
pnpm --filter "@acme/*" run test
pnpm --filter @acme/web... run build   # @acme/web 及其全部依赖
pnpm --filter ...@acme/utils run test  # @acme/utils 及其全部依赖者
```

> 过滤是控制构建规模的主要手段：只跑受影响的包，是把全仓构建从分钟级压回秒级的第一步。

**速记**：--filter 按名或路径选包，-r 递归全仓，--parallel 并行，三个点控制依赖方向。



### 包之间的依赖与引用

**包之间的依赖**：是工作区内一个包在 package.json 中声明对另一个包的引用，安装时被链接到本地目录而非远端仓库。

#### workspace 协议声明内部依赖

**workspace 协议**：是在依赖版本位置写 workspace: 前缀的声明方式，明确告知安装器该依赖解析到工作区内的本地包。

- 精确：workspace:* 表示使用本地包当前版本，常用于锁死内部包。
- 兼容范围：workspace:^ 与 workspace:~ 在打包或发布时被替换为对应范围符。
- 稳定性：写死具体版本号会让本地未发布的改动无法生效，写 workspace: 协议最稳妥。

```json
{
  "name": "@acme/web",
  "dependencies": {
    "@acme/ui": "workspace:*",
    "@acme/utils": "workspace:^"
  }
}
```

> [!IMPORTANT]
> **重要内容**：内部依赖必须使用 workspace 协议，手写固定版本号会让本地改动无法被引用，也会与远端同名包混淆。

**速记**：内部依赖写 workspace: 前缀，安装时链接本地目录，发布时再替换为版本范围。



#### 内部包的引用方式

**引用方式**：是消费方从内部包导入代码时指向源码还是指向构建产物的选择。

- 指向源码：exports 指向 src，消费方构建时一并转译，改动即时可见，但要求消费方具备编译能力。
- 指向产物：exports 指向 dist，消费方拿到已构建文件，速度快但对产物时效敏感。
- 类型引用：类型声明随 exports 一并暴露，否则编辑器无法补全内部包导出。

```json
{
  "name": "@acme/utils",
  "version": "1.4.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": ["dist"]
}
```

```ts
// apps/web/src/main.ts
import { formatPrice } from "@acme/utils";
console.log(formatPrice(1999)); // "¥19.99"
```

> 指向产物的方案必须先构建内部包再构建消费方，否则会引用到过期的 dist，这也是任务编排要解决的顺序问题。

**速记**：引用要么指向源码要么指向产物，前者即时、后者需先构建，类型都要一并暴露。



#### 依赖图与拓扑顺序

**依赖图**：是以包为节点、内部依赖为有向边构成的图；拓扑顺序是保证被依赖者先于依赖者处理的排序。

- 顺序依据：安装与构建都按依赖图推导顺序，被依赖的包先构建。
- 循环依赖：两个包互相依赖时无法确定顺序，属于必须消除的结构问题。
- 观察方式：可用工作区命令列出依赖关系，确认改动的影响范围。

```bash
pnpm ls -r --depth 1
# @acme/web@1.0.0
# dependencies:
#   @acme/ui link:../ui
#   @acme/utils link:../utils
```

```text
构建顺序推导（src 模式）：
utils  →  ui  →  web
         ↘        ↗
            admin
```

> 循环依赖通常意味着职责划分错了：把共享部分下移到更底层的包，即可打破环。

**速记**：构建按依赖图拓扑排序，被依赖者先构建，循环依赖必须消除。



### 任务编排与增量构建

**任务编排**：是在依赖图之上按拓扑顺序调度各包脚本、并复用已有结果的执行方式。

#### 任务编排器的作用

**任务编排器**：是读取工作区依赖图、决定任务执行顺序与并行度、并跳过已命中缓存任务的工具。

- 顺序：把「先构建依赖包」这类约束显式声明，避免手工排序。
- 并行：无依赖关系的任务同时执行，充分利用多核。
- 跳过：相同输入已产出过的任务直接复用结果，只重算真正变化的部分。

```bash
pnpm exec turbo run build
# • Packages in scope: @acme/ui, @acme/utils, @acme/web
# • Running build in 3 packages
# Tasks:    3 successful, 3 total
# Cached:   3 cached, 3 total
# Time:     142ms >>> FULL TURBO
```

> 编排器本身不解包、不转译，它只负责调度与缓存；真正的构建仍由各包自己的脚本完成。

**速记**：编排器按图定序、按无依赖并行、按缓存跳过，自身不做构建。



#### Turborepo 的最小配置与运行

**Turborepo**：是面向 JavaScript 工作区的任务编排器，用一份 JSON 配置声明任务之间的依赖与产出目录。

- tasks：任务名到任务定义的映射，任务名与 package.json 的 scripts 同名。
- dependsOn：声明前置任务，带尖括号前缀表示「先跑依赖包的同名任务」。
- outputs：声明产物目录，缓存命中时据此恢复文件。

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    }
  }
}
```

```bash
pnpm exec turbo run build --filter=@acme/web...
# • @acme/utils:build: cache miss, executing
# • @acme/ui:build:    cache miss, executing
# • @acme/web:build:   cache hit, replaying logs
```

> [!NOTE]
> **提醒内容**：Turborepo 2.0 起把配置里的 pipeline 字段改名为 tasks，沿用旧字段名会读不到任务定义。

**速记**：turbo.json 用 tasks 声明任务，^build 表示先构建依赖包，outputs 决定缓存内容。



#### 缓存与增量命中

**增量命中**：是任务输入未变化时直接复用上次结果、跳过执行的行为，判据由编排器对输入计算哈希得出。

- 输入内容：任务涉及的文件内容、依赖版本、环境变量与配置共同参与哈希。
- 局部命中：只有输入变化的包重新执行，未变化的包从缓存回放。
- 本地缓存：命中结果存在本地目录，换机器后失效。
- 远程缓存：把结果上传到远端存储，团队成员与流水线之间共享命中。

```bash
pnpm exec turbo run build --dry=json
# {"tasks":[{"taskId":"@acme/web#build","cache":{"status":"MISS"}}]}
```

> 缓存正确性的前提是输入被完整纳入哈希：配置里漏声明环境变量，会让不同环境下错误地复用同一份产物。

**速记**：输入哈希决定命中，局部命中只重算变化包，远程缓存让结果跨机器复用。



### 发布与版本管理

**版本管理**：是为工作区内各包确定下一个版本号、生成变更记录并保持依赖声明同步的过程。

#### 内部包与外部包的边界

**内部包**：是只在工作区内消费、不对外分发的包；外部包是被发布出去供其他项目安装的包。

- 内部包：可不写完整的 exports 与 files，版本号也常保持为占位值。
- 外部包：需要完整的入口、类型声明与 files 白名单，版本号要有意义。
- 边界判定：只有仓库内消费的包不必对外发布，减少了版本对齐与兼容负担。

```json
{
  "name": "@acme/tsconfig",
  "version": "0.0.0",
  "private": true,
  "files": ["base.json", "vue.json"]
}
```

> 把确定不外发的包标记为 private，可以从命令层面阻止误发布，比靠人记住更可靠。

**速记**：只在内网消费的包标 private 保持占位版本，对外分发的包才需要完整入口与语义化版本。



#### 版本策略与变更记录

**变更记录（changelog）**：是按版本汇总本次对外可见改动的说明文件，版本号提升幅度与改动性质一一对应。

- 提升规则：破坏性改动升主版本，新增能力升次版本，缺陷修复升修订版本。
- 记录方式：由工具依据提交或变更声明自动汇总，避免手工维护遗漏。
- 工作区特例：内部依赖使用 workspace 协议时，版本同步由工具按依赖图连带更新。
- 工具：Changesets 一类的工具把「本次改动属于哪一级」记成变更声明，再据此统一升版。

```json
{
  "$schema": "https://unpkg.com/@changesets/config@3.0.0/schema.json",
  "changelog": "@changesets/cli/changelog",
  "commit": false,
  "access": "restricted",
  "baseBranch": "main"
}
```

```bash
npx changeset
# 🦋  Which packages would you like to include? @acme/ui
# 🦋  What kind of change is this for @acme/ui? minor
npx changeset version
# 已按变更声明更新各包版本号并生成变更记录
```

> 单仓里版本号的意义容易被稀释：只有对外分发的包才需要严格遵循语义化版本，内部包只需保持唯一。

**速记**：改动的性质决定升版幅度，变更声明由工具汇总成记录，内部包版本从宽。



#### 工作区常见问题

**常见问题**：是单仓在长期演进中最容易积累的几类结构性缺陷。

- 幽灵依赖：包引用了自己没有声明、只因提升而恰好可见的包，换包管理器即报错。
- 版本漂移：同一依赖在不同包内声明了互不兼容的范围，安装结果随包而异。
- 循环依赖：两个包互相引用，导致拓扑排序失败或缓存永远不命中。
- 构建顺序错：消费方读到了内部包过期的 dist，成因见前文引用方式一节。

```bash
pnpm why lodash
# legend: production dependency, optional only, dev only
# @acme/web@1.0.0
# dependencies:
# lodash 4.17.21        # 只有声明过 lodash 的包才会列出
```

> [!CAUTION]
> **注意内容**：幽灵依赖越早用只声明即可用的策略约束，返工越少。

**速记**：幽灵依赖、版本漂移、循环依赖、构建顺序错是四类高发结构问题，靠严格声明与依赖图校验规避。
