## Gulp 简介与设计取向

### Gulp 是什么

本节先给 Gulp 的定义，再拆出任务与流两个核心概念，说明它把构建过程组织成可复用流水线的方式。

#### 任务驱动的构建工具

**Gulp**：是基于任务驱动的构建工具，把每个构建动作封装为具名任务，任务既能单独运行，也能组合成完整流水线。

- 定位：承担资源转换、文件搬运、代码压缩等重复性构建工作，替代逐个手工操作。
- 组织单位：任务（task），一个任务对应一段可独立执行的构建逻辑。
- 调用方式：任务被导出后成为命令行入口，按名称单独触发。
- 运行环境：依托 Node 运行时执行，任务体是普通函数或异步函数。
- 可复现性：任务以配置文件固化，同一任务在任意机器上执行同样的动作序列。

```js
const { src, dest } = require('gulp');

// 最小任务：把源目录下的文本文件搬到产物目录
function copyText() {
  return src('src/text/*.txt').pipe(dest('dist/text'));
}

exports.copyText = copyText;
```

> 任务只有被导出才成为命令行可调用的入口，未导出的函数只能由其他任务内部调用。

**速记**：Gulp 以任务为组织单位，任务导出后即可从命令行单独调用。



#### 任务与流两个核心概念

**任务（task）**：是构建逻辑的最小执行单位；**流（stream）**：是任务之间传递数据的方式，任务内部通过流读写文件而不直接操作磁盘。

- 任务粒度：一个任务只做一件事，便于单独重跑与自由组合。
- 数据载体：流中的每个数据块是一个文件对象，携带路径与内容。
- 连接方式：任务之间不直接调用，而由管道把处理步骤串联起来。
- 组合关系：多个任务可按先后或并行关系拼装成更大的任务。
- 心智模型：写任务等于描述数据从哪里来、经过哪些处理、写到哪里去。

```js
const { src, dest } = require('gulp');

// 任务的三个要素：来源、处理、去向
function buildScripts() {
  return src('src/scripts/*.js')
    .pipe(dest('dist/scripts'));
}

exports.buildScripts = buildScripts;
```

> 任务与流是正交的两层抽象，任务决定什么时候做，流决定数据怎么流。

**速记**：任务定义做什么，流决定数据怎么流，两者共同构成 Gulp 的心智模型。



#### 插件化的处理步骤

**插件（plugin）**：是输入输出都是文件流的单一职责处理单元，把转换逻辑封装成可复用的管道步骤。

- 单一职责：一个插件一般只做一件事，如编译、压缩、重命名。
- 流的接口：插件输入文件流、输出文件流，因此能插入管道的任意位置。
- 组合方式：多个插件按顺序串联，前一个的输出直接成为后一个的输入。
- 复用性：同一步骤可在不同任务中反复使用，无需重复实现。
- 替代写法：逻辑简单时也可自行定义转换流，不必引入外部插件。

```js
const { src, dest } = require('gulp');
const { Transform } = require('stream');

// 自定义转换流：把文本内容统一转为大写，代替外部插件
function makeUppercase() {
  return new Transform({
    objectMode: true,
    transform(file, encoding, done) {
      const text = file.contents.toString().toUpperCase();
      file.contents = Buffer.from(text);
      done(null, file);
    }
  });
}

function uppercaseText() {
  return src('src/text/*.txt')
    .pipe(makeUppercase())
    .pipe(dest('dist/text'));
}

exports.uppercaseText = uppercaseText;
```

> [!IMPORTANT]
> **重要内容**：插件的本质是转换流，引入前要确认其输入输出都是文件流，否则无法直接插入管道。

**速记**：插件是单一职责的转换流，输入输出都是文件流，因此能任意拼接进管道。



### 流式管道模型

管道模型决定了 Gulp 的内存行为与执行顺序。本节先交代 Node 流的基础，再说明管道的连接语义与落盘时机。

#### Node 流的基本概念

**流（stream）**：是 Node 按块读写数据的抽象，数据分块流动、边读边处理，避免一次性把全部内容载入内存。

- 可读流：数据来源，按需产出数据块。
- 可写流：数据终点，接收并写入数据块。
- 转换流：既读又写，在数据流过时改写内容。
- 背压：下游处理慢于上游时，流自动降低读取速度，避免内存堆积。
- 对象模式：Gulp 的文件流处于对象模式，流动的每个数据块是一个文件对象而非字节块。

```js
const fs = require('fs');

// 可读流直接对接可写流，数据分块从源文件流向目标文件
fs.createReadStream('src/big.log')
  .pipe(fs.createWriteStream('dist/big.log'));
```

> 流的核心价值是内存占用与吞吐的平衡，大文件不会整体读入内存再写出。

**速记**：流按块传递数据，分可读、可写、转换三类，背压防止内存堆积。



#### 管道串联与顺序执行

**管道（pipeline）**：是把上游输出接到下游输入、形成单向数据通路的连接方式，在 Gulp 中表现为连续的 pipe 调用。

- 顺序性：pipe 自上而下执行，前一步的输出即后一步的输入。
- 返回值：管道末端返回流对象，任务返回它即表达尚未完成、完成时会收到通知。
- 复用性：同一处理步骤能在不同管道中反复拼接。
- 边界：管道描述单条处理链，多任务之间的先后由组合关系表达。
- 错误传播：链条中任一步出错会沿管道向下传播，默认中断整个任务。

```js
const { src, dest } = require('gulp');
const { Transform } = require('stream');

function makeStamped() {
  return new Transform({
    objectMode: true,
    transform(file, encoding, done) {
      const text = file.contents.toString() + '\nprocessed';
      file.contents = Buffer.from(text);
      done(null, file);
    }
  });
}

function buildHtml() {
  return src('src/pages/*.html')
    .pipe(makeStamped())
    .pipe(dest('dist/pages'));
}

exports.buildHtml = buildHtml;
```

> 管道的书写顺序就是执行顺序，改变 pipe 的先后会直接改变处理结果，调整前要确认每一步的输入输出类型。

**速记**：管道自上而下单向传递，顺序即执行顺序，末端返回流对象表示任务的完成信号。



#### 内存处理与落盘时机

**落盘**：是把流中的文件对象真正写入目标目录的动作，在 Gulp 中由 dest 触发，此前所有处理都在内存中完成。

- 默认行为：处理步骤只修改内存中的文件对象，不触碰磁盘。
- 触发点：只有调用 dest 才会创建目录并写出文件。
- 中间产物：未调用 dest 的中间结果不会留下临时文件。
- 失败影响：任务中途出错且尚未写出时，目标目录保持原样。
- 多次写出：同一条管道可以在不同位置多次调用 dest，产出多份结果。

```text
读取 src 目录
  → 文件对象进入内存，携带路径与内容
  → 各插件在内存中依次改写文件对象
  → 调用 dest 时按基准目录还原路径并写入磁盘
  → 管道结束，任务完成
```

> 内存中处理让中间步骤不产生临时文件，代价是大批量文件同时驻留内存时占用会升高。

**速记**：处理都在内存完成，只有 dest 才落盘，中途失败不会污染目标目录。



### 与其他构建工具的差异

Gulp 与打包器解决的不是同一类问题。本节从驱动方式、编排方式与职责边界三方面做区分，不展开工具链全景。

#### 任务驱动与模块图驱动

**任务驱动**：是以要做什么为单位组织构建，执行顺序由任务清单决定；**模块图驱动**：是从入口出发递归分析模块依赖、以依赖图决定处理顺序。

- 组织单位：任务驱动以资源类型或阶段划分任务，模块图驱动以模块为节点、以依赖为边。
- 分析时机：任务驱动不分析代码依赖，模块图驱动必须先构建依赖图。
- 顺序来源：任务驱动的顺序由写作者指定，模块图驱动的顺序由图的拓扑自动得出。
- 适用范围：任务驱动擅长处理非模块化资源，模块图驱动擅长处理有导入关系的代码。
- 结果形态：任务驱动产出逐个文件，模块图驱动产出按图合并或拆分的产物。

```text
任务驱动：   输入文件集合 → 逐文件处理 → 输出文件集合
模块图驱动： 入口 → 递归解析依赖 → 依赖图 → 合并或拆分 → 输出产物
```

> 两种驱动方式解决不同问题，任务驱动处理一批文件，模块图驱动处理一张依赖网。

**速记**：任务驱动按清单逐文件处理，模块图驱动按依赖拓扑处理，二者适用范围不同。



#### 手工编排与自动分析

**手工编排**：是由写作者显式声明任务之间的先后与并行关系；**自动分析**：是工具读取代码中的导入语句自动推导处理顺序。

- 声明成本：手工编排需要逐条写出任务关系，自动分析几乎无需声明。
- 灵活性：手工编排可以插入任意步骤，自动分析受限于依赖图的语义。
- 出错方式：手工编排漏写依赖会导致顺序错乱，自动分析漏判会产生打包错误。
- 调试难度：手工编排的失败点容易定位，自动分析的失败点往往藏在图中。
- 适用判断：流程越定制越倾向手工编排，代码越规范越倾向自动分析。

```text
手工编排：
  写作者列出任务清单 ── clean → styles → scripts → assets
  顺序由清单决定，任一环可单独重跑

自动分析：
  工具读取入口 ── 解析模块导入 ── 生成依赖图 ── 按拓扑处理
  顺序由依赖关系自动推导，无需手工列出
```

> 手工编排把顺序责任交给写作者，组织得当则流程清晰，组织不当则任务之间出现隐式耦合。

**速记**：手工编排顺序显式、灵活但需自己维护，自动分析省声明但受依赖图约束。



#### 与打包器的职责边界

**职责边界**：是 Gulp 与打包器各自承担的处理范围，前者管非模块化的资源流转，后者管模块之间的依赖与打包。

- 打包器职责：解析模块导入、合并或拆分代码、处理模块化的样式与资源引用。
- Gulp 职责：搬运与转换不参与模块导入的文件，如静态页面、字体、文档与图片。
- 交叉区域：需要按文件流处理的优化步骤，如批量压缩与目录整理。
- 协作方式：由打包器先产出模块产物，再由 Gulp 处理其周边的非模块资源。
- 避免重复：同一份资源不要既交给打包器又交给 Gulp，否则产物互相覆盖。

```text
打包器负责： src/entries 下的模块代码 → 合并、拆分、压缩 → dist/assets
Gulp 负责：  src/static 下的非模块资源 → 搬运、优化、整理 → dist/static
协作顺序：   先打包模块，再处理周边资源
```

> [!NOTE]
> **提醒内容**：两者并用时先划定目录归属，模块代码归打包器、非模块资源归 Gulp，不要按文件类型交叉切分。

**速记**：打包器管模块依赖与打包，Gulp 管非模块资源流转，按目录划清归属避免重复处理。



### 适用场景

Gulp 的价值集中在文件集合的重复处理上。本节列出三类典型场景，并说明各自的适配理由。

#### 批量资源处理

**批量资源处理**：是对同类文件施加同一套转换或搬运的场景，如统一压缩图片、批量替换文档中的路径。

- 特征：输入是同构文件集合，处理逻辑对每个文件一致。
- 优势：无需分析依赖，按通配模式取文件、按流水线逐个处理即可。
- 典型动作：压缩、格式转换、尺寸裁剪、重命名、目录归档。
- 结果核对：产物与输入一一对应，便于比对数量与体积。
- 注意点：源目录与目标目录要区分，避免处理结果再次被通配模式匹配。

```js
const { src, dest } = require('gulp');

// 批量搬运并按目录结构还原图片
function copyImages() {
  return src('src/images/**/*.{png,jpg,svg}')
    .pipe(dest('dist/images'));
}

exports.copyImages = copyImages;
```

> [!CAUTION]
> **注意内容**：产物目录若落在源通配模式的范围内，下一次执行会把产物当成输入再次处理，形成无意义的循环。

**速记**：同构文件套同一套处理用批量场景，重点是通配模式精确、源与目标目录分离。



#### 多步流水线

**多步流水线**：是把多个处理步骤按固定顺序串成一条链、每个文件依次流经全部步骤的场景。

- 特征：单个文件需要多次转换，步骤之间有严格先后。
- 优势：步骤可拆可合，便于按需插入或移除某一环。
- 典型顺序：编译、兼容处理、压缩、加校验标记。
- 可读性：每一步对应一次 pipe 调用，流水线结构在代码里一目了然。
- 注意点：顺序写反会得到错误结果，调整前要确认每步的输入输出类型。

```js
const { src, dest } = require('gulp');
const { Transform } = require('stream');

function appendBanner() {
  return new Transform({
    objectMode: true,
    transform(file, encoding, done) {
      const banner = '/* generated file */\n';
      file.contents = Buffer.from(banner + file.contents.toString());
      done(null, file);
    }
  });
}

function buildStyles() {
  return src('src/styles/*.css')
    .pipe(appendBanner())
    .pipe(dest('dist/styles'));
}

exports.buildStyles = buildStyles;
```

> 流水线的步骤顺序与代码书写顺序一致，读代码即可还原处理过程。

**速记**：多步流水线把有先后的转换串成链，一次 pipe 一步，顺序即语义。



#### 静态站点构建

**静态站点构建**：是把模板、数据与静态资源组合成可直接部署的 HTML 站点，Gulp 在其中承担资源流转与产物整理。

- 组成：页面模板、内容数据、样式脚本与非模块资源。
- 处理链：模板渲染、资源注入、路径改写、产物清理。
- 优势：站点结构简单、构建步骤固定，用任务描述比引入打包器更直接。
- 扩展点：多页面、多语言、按目录批量生成都归结为遍历与替换。
- 边界：模板引擎与数据组织属站点自身设计，此处只关注构建期的接法。

```js
const { src, dest } = require('gulp');

// 按目录批量输出页面，保持原有层级
function buildPages() {
  return src('src/pages/**/*.html')
    .pipe(dest('dist'));
}

exports.buildPages = buildPages;
```

> 静态站点的构建复杂度取决于模板与数据的组织方式，Gulp 只负责把渲染结果搬运到目标结构。

**速记**：静态站点用任务串起模板渲染与资源流转，把页面按目录批量输出。



### 现状与定位

在现代工程中 Gulp 的角色已从全流程构建收缩为资源流转与定制流水线。本节说明它的位置、沿用原因与常见误解。

#### 在现代工程中的位置

**位置**：是 Gulp 在当前工具分工中的角色，从早期的全流程构建工具转为承担资源流转与定制化流水线的辅助工具。

- 角色变化：模块打包交给打包器后，Gulp 不再负责代码层面的依赖处理。
- 保留场景：非模块资源较多、构建步骤高度定制的项目仍以任务描述流程。
- 生态状态：核心稳定，周边插件更新节奏不一，选型时需要核实维护状态。
- 团队因素：已有流水线的迁移成本往往高于收益，沿用是常见选择。
- 判断依据：看流程是否以文件流为主，是则任务模型仍然贴合。

```text
早期角色： 代码编译 + 依赖处理 + 资源优化 + 部署准备（全流程）
当前角色： 非模块资源流转 + 定制流水线 + 与打包器协作
```

> [!WARNING]
> **警告内容**：把模块打包、代码分割这类依赖图相关工作交给 Gulp 手工编排，会迅速演变成难以维护的脚本堆积。

**速记**：Gulp 从全流程构建收缩为资源流转工具，模块依赖处理交给打包器。



#### 仍被使用的原因

**沿用原因**：是使既有项目继续选择 Gulp 的现实条件，集中在流程贴合度、迁移成本与团队熟悉度三方面。

- 流程贴合：以文件集合为单位的构建用任务模型表达最直接。
- 迁移成本：重写既有流水线并回归验证的代价不低，收益有限时不必迁移。
- 定制能力：任意步骤都能写成一段函数插入管道，约束少。
- 心智简单：任务的输入输出都是文件流，理解成本低于依赖图模型。
- 生态存量：大量早期项目使用 Gulp，维护期内的改动仍要在此完成。

```text
判定继续使用：
  - 构建以批量文件处理为主
  - 流水线高度定制、无法用现成配置表达
  - 迁移收益不明或缺少回归验证条件
```

> 继续沿用不等于不动，遗留流水线仍需补齐错误处理与增量处理，否则维护成本会持续累积。

**速记**：流程以文件流为主、迁移收益有限、团队熟悉时，沿用 Gulp 是合理选择。



#### 定位边界与常见误解

**定位边界**：是 Gulp 能力范围的准确描述，超出边界的用法会把简单流程做成难维护的脚本。

- 误解一：把 Gulp 当成打包器，试图在任务里手工实现依赖分析。
- 误解二：把所有构建都塞进一个任务，导致无法单独重跑某一环。
- 误解三：依赖大量插件拼装，忽视插件的维护状态与职责重叠。
- 正确理解：Gulp 描述文件流转过程，不替代模块打包与依赖解析。
- 判断方法：若流程的核心是一批文件按顺序加工，任务模型才成立。

```text
贴合边界的用法：
  取一批文件 → 依次处理 → 写出到目标目录
超出边界的用法：
  在一个任务里解析模块导入、手工计算依赖顺序
```

> [!CAUTION]
> **注意内容**：任务承担了不属于文件流转的职责后，流程会依赖大量自定义代码，后续接手与排错的成本显著上升。

**速记**：Gulp 只管文件流转，越界去做依赖分析与打包会让流程难以维护。
