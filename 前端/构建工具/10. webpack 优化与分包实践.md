## webpack 优化与分包实践

### splitChunks 分包策略

**splitChunks 分包策略**：是 webpack 在构建期按规则把模块归并进多个 chunk 的配置体系，配置入口为 optimization.splitChunks，服务于首屏体积与浏览器缓存命中率两个指标。

本模块回答三个问题：不配置时 webpack 怎么拆、粒度多大合适、常用字段各自控制什么。

#### 默认分包行为与 cacheGroups

**cacheGroups**：是 splitChunks 下定义模块分组的字段，每个分组给出筛选条件与产物参数，命中同一分组的模块会被合并进同一个 chunk。

- 内置分组：webpack 默认提供 vendors 与 default 两个分组，前者用正则匹配 node_modules 下的模块，后者收纳其余满足最小体积的模块。
- 筛选条件：test 接受正则、字符串或函数，用于挑选模块；chunks 取 async、initial 或 all，决定只对异步块、只对初始块还是对两者生效。
- 产物参数：name 指定 chunk 名称，minSize 指定进入该分组的最小字节数，priority 指定分组优先级，数值大者优先命中。
- 配置继承：cacheGroups 内未写的字段回落至 splitChunks 顶层的同名配置，顶层设 minSize 可省去每个分组的重复书写。

```js
// webpack.config.js
const path = require("path");

module.exports = {
  mode: "production",
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].[contenthash:8].js",
    clean: true,
  },
  optimization: {
    splitChunks: {
      chunks: "all",
      minSize: 20000,
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: "vendors",
          priority: 10,
        },
      },
    },
  },
};
```

> chunks 默认值为 async，只拆异步块；同步引入的第三方库要进入独立 chunk，必须显式写成 all。

**速记**：cacheGroups 用 test 挑模块、chunks 定范围、priority 定先后，缺省字段回落顶层值。



#### 分包粒度与缓存命中

**分包粒度**：是拆出 chunk 的数量与体积分布，粒度太粗会让单个 chunk 频繁失效，过细则拉高请求数与协议开销。

- 内容指纹：文件名使用 contenthash，内容不变则哈希不变，浏览器可长期缓存；使用 hash 会因任意模块变动而整体失效。
- 运行时分离：optimization.runtimeChunk 设为 single，把 webpack 的加载与模块映射逻辑单独成块，避免主包因运行时变化而连带失效。
- 变动频率：把长期稳定的第三方库与频繁改动的业务代码分到不同 chunk，业务迭代不会击穿依赖缓存。
- 请求成本：初始请求数量仍需控制，避免把每个小模块都拆成独立文件。

```js
optimization: {
  runtimeChunk: "single",
  splitChunks: {
    chunks: "all",
    minSize: 30000,
    cacheGroups: {
      framework: {
        test: /[\\/]node_modules[\\/](react|react-dom|vue)[\\/]/,
        name: "framework",
        priority: 20,
      },
    },
  },
}
```

> maxSize 只是建议值：webpack 会尝试继续拆分超过该体积的分组，但受模块边界限制，不一定精确达成。

**速记**：contenthash 保缓存、runtimeChunk 隔离运行时、按变动频率分块。



#### splitChunks 常用配置项

**splitChunks 常用配置项**：是控制拆分下限与请求上限的字段集合，用于防止产物过度碎片化。

- minChunks：模块被多少个 chunk 引用后才允许拆出，默认 1，提升该值可只拆公共度高的模块。
- maxInitialRequests：入口初始并行请求数上限，默认 30，超出后 webpack 把剩余模块合并，不再新开 chunk。
- maxAsyncRequests：按需加载的并行请求数上限，默认 30，作用对象是异步块。
- enforce：分组上设为 true 时忽略 minSize 与 minChunks 限制，强制拆分，适合必须独立的运行时或框架包。
- enforceSizeThreshold：默认 50000，超过该体积的分组强制执行拆分，即使违反请求数上限。
- reuseExistingChunk：命中已存在的 chunk 时直接复用，避免同一模块被复制进多个 chunk。

```js
splitChunks: {
  chunks: "all",
  minSize: 20000,
  maxInitialRequests: 6,
  maxAsyncRequests: 10,
  enforceSizeThreshold: 80000,
}
```

> [!TIP]
> **建议内容**：先用默认值构建一次，再用 stats 观察 chunk 数量与体积，只在确有重复或超限时才收紧阈值。

**速记**：minChunks 管门槛、两组 maxRequests 管上限、enforce 强制拆、reuseExistingChunk 防重复。



### 摇树优化与 sideEffects

**摇树优化在 webpack 中的落地**：是把未被使用的导出在打包时删除的能力，webpack 5 通过 usedExports 标记、sideEffects 声明与作用域提升三步配合完成。

本模块讲清三件事：如何在配置中开启、如何用字段标注副作用、哪些写法会让优化失效。

#### 在 webpack 中开启摇树

**摇树优化的开启条件**：是生产模式、ESM 源码与正确的副作用声明三者同时成立，缺一不可。

- 生产模式：mode 为 production 时，webpack 自动启用 usedExports 与代码压缩，被标记为未使用的导出由压缩器删除。
- 显式配置：也可在 optimization 中手动写出 usedExports 与 minimize，便于理解每一步的来源。
- 作用域提升：optimization.concatenateModules 让多个 ESM 模块合并进同一作用域，使跨模块的未使用导出更容易被判死。
- 内部图分析：innerGraph 默认开启，让压缩器沿模块内部引用继续判断导出是否真的被使用。
- 前提是 ESM：模块必须保持 import 与 export 的静态结构，一旦转译为 CommonJS，静态分析即失效。

```js
optimization: {
  usedExports: true,
  concatenateModules: true,
  innerGraph: true,
  minimize: true,
}
```

```bash
npx webpack --mode production
# asset main.a1b2c3d4.js 3.1 KiB
```

> 摇树删除的是未被引用的导出，而不是未被引用的文件；文件只要被引入了至少一个成员，模块顶层代码仍会保留。

**速记**：生产模式加 ESM 加副作用声明，是摇树生效的三个前提。



#### sideEffects 字段标注

**sideEffects 字段**：是 package.json 中声明模块是否含副作用的字段，取值为 false、true 或字符串数组，供打包器判断能否安全删除未被引用的模块。

- 取值 false：声明包内所有模块均无副作用，未被引用的模块可整体删除，适用于纯函数工具库。
- 取值数组：列出含副作用的文件路径或通配模式，如样式引入与全局注册文件，其余文件仍按无副作用处理。
- 默认行为：字段缺省时 webpack 视为可能含副作用，未引用的模块被保守保留，摇树收益下降。
- 样式例外：CSS 与其他副作用资源必须在数组中标出，否则压缩阶段可能误删样式引入语句。

```json
{
  "name": "date-utils",
  "version": "1.2.0",
  "sideEffects": ["*.css", "./src/register-globals.js"]
}
```

```json
{
  "name": "math-kit",
  "version": "2.0.0",
  "sideEffects": false
}
```

> [!WARNING]
> **警告内容**：把含全局注册、样式引入或原型扩展的包声明为 sideEffects 取 false，会在生产构建中删掉这些模块，运行时出现功能缺失且不报错。

**速记**：sideEffects 取 false 表示整包无副作用，取数组时逐项列出有副作用的文件。



#### 摇树失效的常见写法

**摇树失效**：是源码结构让打包器无法证明某个导出未被使用，从而只能保留全部代码的情形。

- CommonJS 引入：使用 require 的模块无法静态分析导出集合，整个文件被纳入产物。
- 顶层副作用：模块顶层执行了写文件、注册事件或修改全局对象的语句，该模块即使导出未被引用也不能删除。
- 命名空间整体使用：写成命名空间整体导入后把该对象传出，压缩器无法确定成员访问范围，只能全部保留。
- 动态属性访问：用方括号加变量读取导出，静态分析无法确定读取的是哪个成员。
- 转译目标过低：转译器把 ESM 降级为 CommonJS 后再交给 webpack，静态结构已被破坏，应让打包器保留 ESM（详见本主题第 11 篇 Babel 与 PostCSS：转译与语法降级）。

```js
// 反例：命名空间整体传出，摇树失效
import * as formatters from "./formatters.js";
export function getFormatters() {
  return formatters; // 压缩器无法判断哪些成员会被访问
}
```

```js
// 正例：只引用需要的成员，未引用导出可被删除
import { formatDate } from "./formatters.js";
export function formatOrderDate(value) {
  return formatDate(value);
}
```

> 副作用标注与纯函数注解是两条互补路径：前者写在包清单，后者写在调用点，用于标记无副作用的函数调用。

**速记**：CommonJS、顶层副作用、命名空间整体使用与动态访问，是摇树失效的四个高发点。



### 缓存与持久化缓存

**webpack 的缓存**：是把模块编译结果与依赖信息落盘或驻留内存、使后续构建跳过重复工作的机制，分为内存缓存与文件系统缓存两类。

本模块说明缓存的开启方式、关键字段与失效清理策略。

#### 文件系统缓存

**文件系统缓存**：是 webpack 5 把构建中间结果写入磁盘的缓存类型，通过 cache.type 设为 filesystem 启用，跨进程重启仍然有效。

- 开启方式：在配置顶层写 cache 对象，type 取 filesystem，默认写入 node_modules/.cache/webpack 目录。
- 开发期收益：二次启动与热更新重编译的速度提升明显，依赖频繁改动时收益更大。
- 生产期收益：持续集成中缓存该目录可缩短重复构建时间，但需保证缓存键与源码、依赖版本对应。
- 内存缓存的区别：type 取 memory 时结果只留在进程内，构建结束即丢失，适合一次性构建。

```js
module.exports = {
  mode: "development",
  cache: {
    type: "filesystem",
    cacheDirectory: "./node_modules/.cache/webpack",
  },
};
```

> 缓存目录属于源码之外的文件，提交代码时应加入忽略清单，不纳入版本控制。

**速记**：cache.type 取 filesystem 才会落盘，默认目录在 node_modules/.cache/webpack。



#### 持久化缓存的常用配置项

**持久化缓存配置项**：是 cache 对象中控制缓存标识、失效条件与存储方式的字段。

- name：区分多份配置的缓存空间，多份 webpack 配置共用同一目录时必须各自命名，否则互相污染。
- version：手动失效开关，改动该字符串即令旧缓存整体作废，适合配置结构变化后强制重建。
- buildDependencies：声明构建依赖的文件集合，默认包含 webpack 配置文件，配置文件改动时缓存自动失效。
- store：取 pack 时把多个缓存项打包为单个文件，减少小文件数量，提升读取效率。
- maxAge：缓存条目的最长保留时间，单位毫秒，超时条目在下次构建时被丢弃。

```js
module.exports = {
  cache: {
    type: "filesystem",
    name: "web-app",
    version: "v1",
    buildDependencies: {
      config: [__filename],
    },
    store: "pack",
    maxAge: 5184000000,
  },
};
```

> buildDependencies 需包含所有影响产物形态的文件，如自定义 loader 与构建脚本，否则改了这些文件仍会命中旧缓存。

**速记**：name 隔离、version 强刷、buildDependencies 声明依赖、store 与 maxAge 管存储。



#### 缓存失效与清理

**缓存失效**：是当源码、依赖或构建配置变化时让对应缓存条目不再被使用，从而保证产物正确。

- 自动失效：webpack 记录模块的内容哈希与依赖关系，文件内容变化时只重编译受影响的模块。
- 配置变化：webpack 配置文件自身改动会触发失效；自定义 loader 与插件代码放入 buildDependencies 才会被追踪。
- 手动清理：删除 cacheDirectory 目录即可彻底重置，出现无法解释的陈旧产物时可先做这一步。
- 版本升级：升级 webpack 主版本或关键 loader 后应改用新的 version 或新目录，避免新旧缓存格式混用。
- 产物侧配合：output.filename 使用 contenthash，让未变化的 chunk 在浏览器端继续命中缓存。

```bash
rm -rf node_modules/.cache/webpack
# 缓存目录被清空，下次构建全量执行
```

> [!CAUTION]
> **注意内容**：持续集成上并发使用同一缓存目录会让多个构建互相写入，导致缓存损坏或产物不稳定，应使用各自独立的缓存目录。

**速记**：内容变化自动失效，配置与自定义 loader 要靠 buildDependencies 追踪，手动清理即删缓存目录。



### source map 策略

**source map**：是把产物中的行列位置映射回源码位置的索引文件，调试器据此在原始源码上断点并还原错误栈。

本模块讲清 source map 的作用、devtool 取值差异与生产环境的上报策略。

#### source map 的作用与代价

**source map 的作用**：是在产物经过压缩与改名后，仍能把错误位置还原到开发者书写的源码行列。

- 调试断点：浏览器开发者工具依据映射把断点打在源码上，而不是压缩后的单行产物上。
- 错误还原：错误监控平台收到堆栈后可用映射文件还原真实文件与行号，定位线上问题。
- 代价：生成映射会增加构建时间与产物文件数，映射文件体积可达原产物的数倍，需要额外部署或存放。
- 暴露风险：完整映射会把源码原文交给任何能下载它的人，公开站点不应直接部署完整映射。

```js
module.exports = {
  mode: "development",
  devtool: "eval-cheap-module-source-map",
};
```

> 映射质量与构建速度互相牵制：越精确的映射越慢，开发期取速度、生产期取精度是常见取舍。

**速记**：source map 把产物位置还原到源码行列，代价是构建变慢、源码可能外泄。



#### devtool 取值与选择

**devtool**：是 webpack 配置顶层控制映射生成方式的字符串字段，取值由是否内联、是否映射到源码、精确程度三组特征组合而成。

- eval：把模块包进 eval 并附上行内映射，重建最快，只精确到行，无法还原到原始源码。
- cheap-module-source-map：映射到原始源码但只到行级别，体积较小，适合日常开发。
- source-map：生成独立的映射文件，行列都精确，适合生产构建与错误上报。
- inline-source-map：把映射以内嵌数据形式写进产物，不产生额外文件，会显著增大单文件体积。
- nosources-source-map：映射保留位置信息但不含源码原文，适合需要上传但不想暴露源码的场景。
- hidden-source-map：生成映射文件但不在产物末尾写注释指向它，配合错误监控手动上传。

```js
const devtoolByMode = {
  development: "eval-cheap-module-source-map",
  production: "hidden-source-map",
};

module.exports = {
  mode: process.env.NODE_ENV || "production",
  devtool: devtoolByMode[process.env.NODE_ENV] || "source-map",
};
```

> 多数场景从 source-map 出发即可；只在构建耗时成为瓶颈或安全策略有要求时，才换成 cheap 系列或隐藏系列。

**速记**：eval 求快、source-map 求准、nosources 隐藏源码、hidden 不外链映射。



#### 生产环境的 source map 策略

**生产环境 source map 策略**：是在保留线上错误可还原能力的同时，避免把源码原文公开发布。

- 隐藏外链：devtool 取 hidden-source-map，产物不写映射注释，浏览器默认不会请求映射文件。
- 独立上传：把生成的映射文件上传到错误监控平台，由平台在服务端完成堆栈还原。
- 访问控制：映射文件放在带鉴权的静态路径或对象存储，设置为非公开读。
- 关闭映射：安全要求极高且不依赖线上还原时，devtool 取 false，完全不生成映射。
- 上传时机：错误监控插件在打包完成钩子中上传映射并关联本次发布的版本号，便于按版本检索。

```js
module.exports = {
  mode: "production",
  devtool: false,
};
```

> [!IMPORTANT]
> **重要内容**：发布新版本时映射文件必须与产物同版本，映射与产物版本错配会让还原出的行号完全错位，反而误导排查。

**速记**：生产用 hidden-source-map 加服务端上传，或直接关掉映射。



### 体积分析与性能排查

**体积分析**：是借助构建统计与可视化工具找出产物体积的主要来源与重复模块，为优化提供证据而非猜测。

本模块说明统计数据怎么拿、分析工具怎么看、常见体积问题如何定位。

#### stats 与构建耗时输出

**stats**：是 webpack 输出的构建统计对象，包含模块、chunk 与资源的体积和耗时信息，可打印到终端或写成 JSON 文件。

- 命令输出：webpack --profile 输出每个模块的耗时，webpack --stats detailed 输出更详细的体积与依赖信息。
- JSON 导出：webpack --json 把完整统计写到标准输出，重定向后即得 stats.json，供分析工具读取。
- 关键字段：assets 给出各产物体积，modules 给出模块来源与体积，chunks 给出分块关系，time 给出总耗时。
- 体积阈值：performance 字段可设置 maxAssetSize 与 maxEntrypointSize，超过阈值时构建输出告警。

```bash
npx webpack --mode production --profile --json > stats.json
# 观察输出中的 time 与 assets 两项
```

```js
module.exports = {
  performance: {
    hints: "error",
    maxEntrypointSize: 512000,
    maxAssetSize: 256000,
  },
};
```

> performance 只对入口对应的资源给出提示，不会中断构建，适合作为提交前的健康度参考。

**速记**：--profile 看耗时、--json 导 stats，performance 阈值做体积告警。



#### 产物分析工具

**webpack-bundle-analyzer**：是把 stats 数据渲染成矩形树图的插件，矩形面积与体积成正比，用于快速定位占比最大的来源。

- 安装：npm install --save-dev webpack-bundle-analyzer。
- 插件用法：在 plugins 中加入 BundleAnalyzerPlugin，构建结束后自动打开本地页面。
- 离线用法：先用 --json 生成 stats.json，再执行分析器命令读取文件，适合在流水线产物上事后分析。
- 读图要点：同色多个小块说明模块被拆得过散，重复出现的同名模块说明依赖未去重。
- 压缩视图：分析器可切换到压缩后体积视图，更接近实际传输量。

#### 体积问题定位清单

**体积问题定位清单**：是按优先级逐项排查产物体积的固定顺序，先找重复与全量引入，再找可延迟与可压缩项。

- 重复依赖：同一库的不同版本同时进入产物，多因依赖树存在版本冲突，可用包管理器的去重与提升能力收敛。
- 全量引入：整体导入带大量成员的库而不是按成员导入，或未启用按需加载入口，导致整包进入初始 chunk。
- 多语言与本地化数据：日期库的语言包、货币与地区数据常被整体打包，应改为按需引入或使用轻量替代库。
- 垫片与降级产物：为目标浏览器追加的垫片与降级代码体积可观，需按 browserslist 精确控制范围（详见本主题第 11 篇 Babel 与 PostCSS：转译与语法降级）。
- 未抽离的第三方库：未配置 splitChunks 或 chunks 未取 all，导致依赖全部塞进入口 chunk。
- 静态资源：图片、字体与图标未压缩或未按尺寸拆分，应检查资源类型是否被当作模块整体内联。

```bash
npm ls lodash
# └── lodash@4.17.21
```

```bash
pnpm why lodash
# 列出引用 lodash 的全部依赖链
```

> 优化顺序应从影响最大的来源开始：先消除重复与全量引入，再考虑分包与延迟加载，最后才微调压缩参数。

**速记**：先查重复版本与全量引入，再查本地化数据、垫片与资源，最后才调分包。
