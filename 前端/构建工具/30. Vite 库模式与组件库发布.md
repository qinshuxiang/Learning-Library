## Vite 库模式与组件库发布

库构建的终点不是可部署的网页，而是一组供其它项目导入的模块文件。build.lib 的字段清单与最小示例见本主题第 7 篇，本篇承接它讲完整链路：多格式与多入口的产物组织、外部依赖如何声明、类型声明从哪来、package.json 的字段如何与产物逐一对上。包字段中三类依赖的分工见本主题第 2 篇，打包器层面的树摇与副作用机制见第 42 篇，本篇不重复。

### 库模式的基本配置

库与应用共用同一套构建器，但在入口、依赖归属与产物形态上目标不同。本节先确立判断依据，再说字段之间的配合。

#### 库构建与应用构建的差别

**库构建**：是产出供其它项目导入的模块文件、而不是交给浏览器直接加载的网页的构建形态。

- 入口对象：应用以 HTML 为入口并由此推导脚本；库以源码模块为入口，不处理页面模板。
- 依赖归属：应用把依赖打进产物；库把框架一类依赖留给使用方，由使用方提供。
- 样式处理：应用的样式由页面引入；库的样式随包分发，由使用方按约定路径显式引入。
- 产物清单：应用的产物含 HTML、脚本、样式与资源；库的产物只有脚本与样式。
- 运行环境：应用按目标浏览器转译；库通常保留较新的语法，把降级交给使用方的构建链。

```bash
npm run build
# dist/my-widget.js        24.18 kB │ gzip: 8.42 kB
# dist/my-widget.umd.cjs   25.07 kB │ gzip: 8.71 kB
# dist/style.css            3.12 kB │ gzip: 1.04 kB
```

> 判断依据只有一条：产物是被 import 或 require 使用，还是被页面直接加载。前者走库模式，后者走应用构建。

**速记**：库以源码模块为入口、框架依赖留给使用方、产物只有脚本与样式。



#### build.lib 的字段组合

**build.lib**：是库模式的配置对象，字段含义已在第 7 篇列出，这里关注缺省值与字段之间的配合。

- formats 缺省：未指定时按 es 与 umd 两种格式各产出一份文件。
- name 的生效范围：只在 umd 与 iife 格式下作为全局变量名使用，其余格式忽略该字段。
- fileName 的签名：取值为函数时接收 format 与 entryName 两个参数，按二者拼出文件名。
- entry 用对象：键名会成为入口名，进而参与默认的文件名推导。
- 样式文件名：可用 build.lib.cssFileName 指定，缺省时按入口名生成样式文件。

```js
// vite.config.js
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    lib: {
      entry: fileURLToPath(new URL("./src/index.js", import.meta.url)),
      name: "MyWidget",
      fileName: (format, entryName) => `${entryName}.${format}.js`,
      formats: ["es", "cjs", "umd"],
    },
  },
});
```

> [!IMPORTANT]
> **重要内容**：formats 中包含 umd 或 iife 时，name 必须提供且为合法的全局变量名，缺失会让构建直接失败。

**速记**：formats 缺省为 es 与 umd，name 只服务全局格式，fileName 函数接收格式与入口名。



#### 库模式的入口形态

**入口形态**：指 build.lib 的 entry 取字符串、数组还是对象，三者决定产出的文件数量与文件名推导规则。

- 字符串：单入口，产物文件名取自 fileName 或入口文件名。
- 数组：多入口，入口名由文件路径推导，适合同名不同目录的松散入口集合。
- 对象：多入口且键名可自定义，产物名与键名一致，是组件库的常用形态。
- 共享代码：多个入口引用的公共模块由打包器提升为共享代码块，入口之间不会重复打包。
- 结构保留：需要按源码目录逐个模块产出时，改用保留模块结构的输出选项，细节见 Rollup 系列。

```js
// vite.config.js 组件库按组件逐个产出入口
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    lib: {
      entry: {
        index: fileURLToPath(new URL("./src/index.js", import.meta.url)),
        button: fileURLToPath(new URL("./src/components/button/index.js", import.meta.url)),
        dialog: fileURLToPath(new URL("./src/components/dialog/index.js", import.meta.url)),
      },
      formats: ["es", "cjs"],
    },
  },
});
```

> 入口名是产物文件名与使用方导入路径的公共部分，一旦发布就属于对外契约，改动等同于破坏性变更。

**速记**：字符串、数组、对象三种入口形态对应不同的命名规则，对象形式最可控。



### 多格式与多入口产物

一次构建可以同时产出多种模块格式，格式的组合决定了包能被哪些工具消费。本节按格式取舍与产物组织展开。

#### ESM 与 CJS 的取舍

**ESM 产物**：是使用 import 语法加载、可被上层构建器做静态分析的模块格式；**CJS 产物**：是使用 require 加载的模块格式，兼容较早的工具链与部分 Node 场景。

- 优先 ESM：现代构建器与较新的 Node 都能直接消费，且便于上层做依赖裁剪。
- 保留 CJS：使用方在 Node 环境用 require 加载，或工具链尚未支持 ESM 时需要提供。
- 双份风险：使用方的不同依赖分别走两种格式时，同一库会被加载两份，模块级状态不共享。
- 文件扩展名：ESM 产物在声明了模块类型的包内按 .js 命名即可，其余情况用 .mjs 与 .cjs 区分。
- 默认导出：CJS 产物中的默认导出会被包一层 default 属性，使用方解构方式与 ESM 下不同。

```js
// vite.config.js 同时产出两种格式
export default defineConfig({
  build: {
    lib: {
      entry: fileURLToPath(new URL("./src/index.js", import.meta.url)),
      formats: ["es", "cjs"],
      fileName: (format) => (format === "es" ? "index.mjs" : "index.cjs"),
    },
  },
});
```

> 双份实例的后果与同伴依赖的处理方式一致：状态不共享、体积翻倍，根因是同一模块被两条路径加载。

**速记**：优先 ESM，需要兼容旧工具链时补 CJS，注意两种格式并存带来的双份实例。



#### UMD 与 IIFE 的适用场合

**UMD 产物**：是同时支持模块加载、AMD 与全局变量挂载的格式；**IIFE 产物**：是只能以全局变量形式被脚本标签直接引用的格式。

- UMD 场景：使用方既可能用模块加载器、也可能用脚本标签直接引入时提供一份。
- IIFE 场景：明确只通过脚本标签引入、不需要模块加载能力，产物略小。
- 共同前提：两种格式都依赖 name 与 output.globals 才能在没有模块环境时找到依赖。
- 体积代价：这两种格式无法被上层构建器做细粒度裁剪，通常不用于现代项目内部。
- 趋势判断：包管理器与构建器普及后，UMD 的主要用途退化为演示页与 CDN 直引。

```html
<script src="https://cdn.example.com/my-widget.umd.js"></script>
<script>
  MyWidget.create({ target: "#app" });
</script>
```

> [!CAUTION]
> **注意内容**：全局变量名会挂在页面的全局对象上，与同名变量冲突时直接覆盖，发布前应选用不易碰撞的名字。

**速记**：UMD 兼顾模块与全局两种加载方式，IIFE 只服务脚本标签直引，两者都需要全局名。



#### 多入口的产物组织

**多入口产物组织**：是多个入口在同一次构建中如何分目录、如何共享代码块、样式如何与入口对应的安排。

- 目录分组：用 fileName 函数按入口名把文件放进子目录，便于使用方按路径引用。
- 共享块命名：用 chunkFileNames 指定共享代码块的位置与命名，避免散落在产物根目录。
- 样式对应：默认按入口产出对应样式文件，需要用 build.cssCodeSplit 调整是否拆分。
- 声明同构：类型声明的目录结构应与脚本产物的结构保持一致，方便按入口引用类型。

```js
// vite.config.js
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        entryFileNames: "[name]/index.mjs",
        chunkFileNames: "shared/[name]-[hash].mjs",
        assetFileNames: "styles/[name][extname]",
      },
    },
  },
});
```

> 命名模板里是否保留内容哈希取决于消费方式：库入口文件名需要稳定，共享代码块则可以带哈希。

**速记**：多入口用命名模板分目录，共享块单独收拢，样式与声明跟随入口结构。



### 外部依赖处理

把不该打进产物的依赖留到运行期解析，是库构建与应用的第二个关键差异。本节说明判断与写法。

#### 应当外部化的依赖

**外部化（external）**：是把依赖保留为运行期导入、不并入产物的处理，判断依据是使用方是否已经持有该依赖。

- 框架与运行时：宿主项目必然已安装，外置可避免出现两份实例导致的状态隔离。
- 版本敏感库：使用方需要统一版本时外置，由其自行决定具体版本。
- 大型可选依赖：仅在特定功能中使用且体积可观时外置，让使用方按需安装。
- 内部小工具：只在本库内部使用、体积很小的依赖不必外置，避免增加使用方的安装负担。
- 同伴依赖：外置的框架通常写进 peerDependencies 声明版本范围，字段分工见本主题第 2 篇。

```js
// vite.config.js 把框架与运行时外置
export default defineConfig({
  build: {
    rollupOptions: {
      external: ["vue", "vue-router"],
    },
  },
});
```

> 外部化是一份契约：产物里保留了导入语句，使用方必须能解析到这些包，否则导入即报模块找不到。

**速记**：使用方已持有的框架与大型可选依赖应外置，内部小工具不必外置。



#### external 的写法

**rollupOptions.external**：是声明外部依赖的选项，取值为字符串数组、正则表达式或接收模块标识的函数。

- 数组形式：按包名精确匹配，最直观，但必须覆盖子路径导入。
- 函数形式：接收模块标识，返回布尔值，适合用前缀判断批量外置作用域包。
- 正则形式：按模式匹配，便于同时命中一个组织下的多个包。
- 子路径覆盖：引用了依赖的深层路径时，数组里只写包名不会命中，需要额外写出子路径或用函数形式。
- 与 globals 配对：外置后如果还要产出 UMD，必须为每个被外置的依赖补上全局变量名。

```js
// vite.config.js 用函数形式批量外置作用域包
export default defineConfig({
  build: {
    rollupOptions: {
      external: (id) => id.startsWith("@my-scope/") || id === "vue",
    },
  },
});
```

> [!WARNING]
> **警告内容**：忘记把框架写进外部化名单，产物会把整个框架打进去，使用方最终加载两份实例，出现事件失效与状态读写错乱。

**速记**：数组写包名、函数按前缀判断，子路径导入必须一并覆盖，外置后要为 UMD 补全局名。



#### 全局变量映射与同伴依赖

**全局变量映射（globals）**：是给外部依赖在 UMD 与 IIFE 产物中指定全局变量名的配置，取值为依赖名到全局名的对象。

- 键的写法：与外部化声明中的模块标识保持一致，子路径导入需要单独给出键。
- 值的来源：取依赖在浏览器全局环境下的实际变量名，按依赖文档确认。
- 缺失后果：产物中以全局形式查找依赖却找不到，运行时报未定义而不是明确的依赖缺失提示。
- 同伴依赖：把外置的依赖写进 peerDependencies 并给出可接受范围，让包管理器在安装期提示版本不符。
- 可选同伴：仅在部分功能中需要的框架可用可选标记声明，避免非必要项目被强制安装。

```js
// vite.config.js 外置并映射 UMD 全局名
export default defineConfig({
  build: {
    lib: {
      entry: fileURLToPath(new URL("./src/index.js", import.meta.url)),
      name: "MyWidget",
      formats: ["es", "umd"],
    },
    rollupOptions: {
      external: ["vue"],
      output: {
        globals: { vue: "Vue" },
      },
    },
  },
});
```

> 全局名映射只对无模块系统的加载方式生效，ESM 与 CJS 产物按模块标识解析，不读取该映射。

**速记**：UMD 产物需要 globals 把依赖名映射到全局变量名，同时用同伴依赖声明版本范围。



### 类型声明产物

类型声明不随脚本产物自动出现，它是另一条独立的产出链路。本节说明原因与两条可选路线。

#### 为什么构建不产出类型

**类型声明文件**：是描述模块导出类型的 .d.ts 文件，构建器只做语法转译，不做跨文件类型推断，因此声明必须单独产出。

- 分工原因：转译器逐文件去掉类型标注即可完成工作，不需要也不掌握完整的类型信息。
- 直接后果：只跑构建时，使用方导入该包后编辑器中没有任何类型提示。
- 常见误解：把 build.lib 的入口指向 TypeScript 源文件不会让声明自动产出。
- 类型来源：声明可以由类型检查器生成，也可以由声明插件在打包过程中生成。
- 对齐要求：声明的目录与文件名要和脚本产物保持一致，包字段才能同时指向两者。

```bash
npm run build
# 产物中只有脚本与样式，没有 .d.ts
ls dist
# index.mjs  index.cjs  style.css
```

> 声明文件的缺失在使用方侧表现为整个包类型为任意值，本地开发不易察觉，发布前应实际安装验证一次。

**速记**：构建器只转译不产出声明，声明必须由类型检查器或声明插件单独生成。



#### 用类型检查器产出声明

**声明产出命令**：是用类型检查器以只输出声明的模式把源码编译成 .d.ts 的命令，参数在命令行或配置文件里声明。

- 命令行参数：--declaration 开启声明输出，--emitDeclarationOnly 表示只输出声明，--outDir 指定目录。
- 配置字段：在 tsconfig.json 中对应 declaration 与 declarationDir 两项。
- 单文件组件：.vue 一类非标准模块需要配套的检查器命令生成声明，具体命令按框架文档选择。
- 执行顺序：声明产出与打包互不依赖，但清理命令不能把声明目录一并删掉。
- 路径对应：声明目录写进包字段的 types，路径必须与产物目录结构一致。

```json
{
  "compilerOptions": {
    "declaration": true,
    "declarationDir": "dist/types",
    "emitDeclarationOnly": true
  }
}
```

> [!IMPORTANT]
> **重要内容**：清理命令与声明产出必须成对设计，构建前清空产物目录会连带删除声明，导致发布的包里缺少类型文件。

**速记**：用类型检查器的仅声明模式产出 .d.ts，声明目录与清理范围要分开设计。



#### 用构建插件产出声明

**声明插件**：是在打包过程中生成声明文件并写入产物目录的插件，适合声明需要按入口聚合或多入口产出的项目。

- 接入方式：加入构建配置的插件数组，按插件文档指定输出目录、入口与是否包含源码文件。
- 适用情形：多个入口需要各自一份声明，或声明需要跟随产物的目录结构。
- 路线取舍：与类型检查器路线二选一，两条链路同时写同一个目录会互相覆盖。
- 配置来源：插件通常读取 tsconfig 的编译选项，路径别名需要与构建配置一致才能解析。
- 结果校验：产出后用类型检查器对声明做一次消费验证，确认导入路径与类型可用。

```js
// vite.config.js 接入声明插件，包名与选项按插件文档填写
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    declarationPlugin({ outDir: "dist/types", entryRoot: "src" }),
  ],
});
```

> 插件产出声明的速度通常快于整包类型检查，代价是类型校验的完整性下降，关键库仍建议独立跑一次全量检查。

**速记**：声明插件跟随打包产出声明，与类型检查器路线二选一，产出后仍需校验可用性。



### 发布配置与包字段

产物构建完成只完成一半工作，剩下的问题是使用方从哪里加载它。本节按字段对应、样式导出与发布清单收尾。

#### 入口字段与产物对应

**入口字段**：是 package.json 中告诉使用方从哪个文件加载模块的字段，取值必须与构建产出的真实文件名逐一对上。

- main：指向 CJS 入口，供 require 场景使用。
- module：指向 ESM 入口，该字段不是标准字段但被主流构建器识别。
- exports：用条件分支按 import、require 与 types 分流，存在时优先级高于前两者。
- 路径写法：一律以点斜杠开头写相对路径，省略前缀会被当作包名解析而失败。
- 同步要求：产物改名或换目录后必须同步字段，否则使用方导入直接报文件不存在。

```json
{
  "name": "my-widget",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/types/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

> [!WARNING]
> **警告内容**：入口字段指向不存在的文件是发布后最常见的事故，使用方在安装成功后才在构建阶段报错，排查成本高；发布前应实际安装一次验证导入。

**速记**：main 指 CJS、module 指 ESM、exports 按条件分流，路径必须与产物逐一对应。



#### 样式与副作用标注

**样式产物**：是随包分发的样式文件，需要在导出字段中作为子路径暴露；**副作用标注**：是 sideEffects 字段，用于告诉打包器哪些文件不能被安全丢弃。

- 样式导出：在 exports 中增加样式文件的子路径，使用方按该路径显式引入。
- 文件名：库内样式通常合并为固定文件名，不带内容哈希，便于使用方写稳定的引入路径。
- 副作用判断：纯逻辑且无模块级副作用的包可标为无副作用，让上层更彻底地裁掉未使用代码。
- 与样式共存：包含样式导入的包必须把样式文件列入副作用的匹配范围，否则样式会被一并裁掉。
- 机制细节：剪裁的依据与边界条件见本主题第 42 篇，此处只处理发布时的标注。

```json
{
  "sideEffects": ["**/*.css"],
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./style.css": "./dist/style.css"
  }
}
```

> 样式是否自动注入是取舍：自动注入使用方便但无法按需，显式引入多一行代码却能控制加载顺序与裁剪。

**速记**：样式作为子路径导出并保持固定文件名，sideEffects 要把样式文件纳入范围以免被裁掉。



#### 发布清单与文件范围

**发布清单**：是 files 字段声明的随包发布路径集合，决定使用方最终下载到的内容。

- 白名单优先：用 files 显式列出产物目录，比用忽略文件黑名单更不容易漏配。
- 目录范围：只需发布产物与声明目录，源码、配置与脚本不必进入包内。
- 必发文件：说明文件与授权文件始终随包发布，无需列入清单。
- 构建前置：发布前必须完成构建，用发布钩子或流水线保证产物先于打包动作生成。
- 本地预演：用打包预览命令生成待发布压缩包并检查其内容清单，确认无多余文件与缺失文件。

```json
{
  "files": ["dist"]
}
```

```bash
npm pack --dry-run
# 输出将发布的文件清单，确认产物与声明都在其中
```

> [!CAUTION]
> **注意内容**：漏跑构建直接发布，使用方安装到的是上一次的旧产物或空目录，本地源码无关的测试无法发现这类问题。

**速记**：files 用白名单只发产物与声明，发布前先构建再用打包预览核对清单。
