## 构建性能优化与缓存策略

> [!IMPORTANT]
> **重要内容**：优化必须建立在测量之上，先定位瓶颈再动手；未经验证就替换工具或加线程，通常只是把耗时挪到别处。

### 构建慢的成因定位

**构建性能**：是从命令发起到产物落盘的时间与资源开销，由依赖解析、转译、打包、压缩四类工作共同决定。

#### 构建耗时的构成

**构建耗时**：是各阶段耗时的总和。

- 依赖解析：读取与解析大量模块文件，node_modules 越大越慢。
- 转译：把 TypeScript、新语法与新样式转成目标环境可执行的代码，是 CPU 密集环节。
- 打包与图分析：构建模块依赖图、做摇树优化与代码分割。
- 压缩与写盘：压缩产物、生成 source map 并写入磁盘。

```bash
npx vite build
# vite v6.0.3 building for production...
# ✓ 1587 modules transformed.
# dist/assets/index-8f3a1c2.js   186.42 kB │ gzip: 62.11 kB
# ✓ built in 3.21s
```

> 同一份源码在冷启动与热启动下的耗时差异通常来自缓存，比较优化效果前必须先固定缓存状态。

**速记**：耗时来自解析、转译、打包、压缩四段，先看哪段占比最大。



#### 定位手段与耗时剖析

**耗时剖析**：是用工具输出各阶段或各模块的时间占比，据此确定优化目标的过程。

- 打包器日志：Vite 与 webpack 默认打印各阶段耗时与产物体积。
- 产物分析：把打包统计导出为 JSON，用可视化工具查看模块构成与体积占比。
- 模块耗时：查看解析与转译阶段的逐模块耗时，定位异常大的模块。
- 配置核对：打印最终生效的配置，确认优化选项确实生效。

```bash
npx vite build --debug
# 输出解析后的完整配置，确认 minify、target 等取值

npx webpack --profile --json > dist/stats.json
npx webpack-bundle-analyzer dist/stats.json
# 浏览器打开交互式体积构成图
```

> 剖析结果要换算成绝对值：一个模块占总体积的百分比再高，绝对体积很小也不值得优化。

**速记**：打包器日志看阶段、产物分析看图与体积、--debug 看生效配置。



#### 优化的优先级

**优化优先级**：是按「收益除以成本」排序的处理次序，先做影响面最大的结构性改动。

- 先减少工作量：能缓存就缓存、能跳过就跳过、能只做受影响部分就不做全量。
- 再并行：把可并行的 CPU 密集型任务分配到多个核。
- 后换工具：换用更快的转译器或打包器往往改动面大，放在最后考虑。
- 常被忽略的一步：升级依赖版本，许多性能改进已包含在工具自身的新版本里。

```bash
npx vite build --mode production
# 与默认生产构建等价，用于确认模式切换未引入额外开销
```

> [!TIP]
> **建议内容**：优先复用已有的增量与缓存能力，它通常一次配置即可长期生效，收益远高于手工并行化。

**速记**：优先级是缓存跳过、并行分核、换工具、升版本，结构性改动排在最前。



### 依赖预构建与缓存

**依赖预构建（dependency pre-bundling）**：是开发服务器启动时把第三方依赖预先转成一个模块文件的过程，目的是减少后续请求数量并统一模块格式。

#### 依赖预构建的意义与配置

**预构建**：解决的是第三方包数量多、格式混杂导致的开发期请求风暴与格式转换开销。

- 合并请求：把依赖内部的成百上千个小文件合并为少量文件，避免逐个请求。
- 格式统一：把 CommonJS 依赖转成 ES 模块，使浏览器能统一按 import 处理。
- 缓存结果：预构建产物写入缓存目录，未变化时直接复用。
- 手动声明：include 与 exclude 的使用场景见下文常见问题一节。

```json
{
  "optimizeDeps": {
    "include": ["lodash-es", "echarts/core"],
    "exclude": ["@acme/local-link"]
  },
  "cacheDir": "node_modules/.vite"
}
```

```bash
npx vite --force
# Forced re-optimization of dependencies
# 预构建缓存被忽略并重新生成
```

> 预构建缓存目录被删除或依赖变更后，首次启动会明显变慢，这是重建缓存而非性能退化。

**速记**：预构建合并请求、统一模块格式，产物落缓存目录，未声明到的依赖要写 include。



#### 依赖预构建的常见问题

**预构建异常**：表现为依赖未被打入缓存、页面报模块解析错误或改动依赖后行为不一致。

- 漏扫：动态拼接路径引用的依赖扫描不到，需显式 include。
- 本地链接：被链接的本地包若走预构建，改动不会即时反映，通常应 exclude。
- 缓存陈旧：依赖版本变更后仍用旧缓存，需强制重建。
- 循环引入：依赖内部结构复杂时预构建报错，可尝试换用该包的其他入口或被排除的包一并排除。

```bash
rm -rf node_modules/.vite
npx vite --force
# 重建预构建缓存后再启动
```

> 上述问题多半一次性出现在开发服务器启动阶段，与生产构建无关；生产构建不复用预构建产物。

**速记**：漏扫要 include、本地链接要 exclude、缓存陈旧要 --force 或清目录。



#### 依赖安装层的缓存

**安装缓存**：是包管理器对已下载依赖包的本地存储，避免同一版本重复从网络获取。

- 存储位置：pnpm 与 yarn 有全局存储目录，npm 用本地缓存目录。
- 复用方式：命中缓存的安装只做链接，不重新下载。
- 流水线要点：在 CI 中缓存全局存储目录与锁文件派生键，避免每次全量拉取。
- 锁文件：提交锁文件保证依赖版本稳定，也使缓存键可被准确计算。

```bash
pnpm install --frozen-lockfile
# Lockfile is up to date, resolution step is skipped
# Already up to date
```

> 依赖层的缓存是上游缓存：它把安装时间压短，从而让构建总耗时中真正属于构建的部分占比更高。

**速记**：安装缓存是全局依赖存储，命中即链接，CI 用锁文件派生键缓存它。



### 并行与多线程

**并行化**：是把互不依赖的工作同时交给多个 CPU 核心处理，从而缩短整体墙钟时间。

#### 并行化的层次

**并行层次**：是从文件、模块到任务三个粒度上分别展开的并行机会。

- 文件级并行：转换与压缩按文件切分，交给线程池处理。
- 图构建并行：解析模块依赖图时可并发读取与解析。
- 任务级并行：工作区内互不依赖的包同时构建，详见本主题第 14 篇 Monorepo 与工作区管理。
- 进程级并行：多个包各自起独立进程，避免同一进程内的资源争用。

```bash
pnpm -r --parallel run build
# 三个互不依赖的包同时构建，总耗时接近单包最长耗时
```

> 粒度越粗的并行越容易受益，任务级与进程级并行的收益通常比文件级线程池更稳定。

**速记**：并行分文件级、图级、任务级、进程级，粒度越粗收益越稳定。



#### 多线程转译工具

**多线程转译**：是用线程池把转译这一 CPU 密集环节分摊到多个核心的做法。

- thread-loader：把后续 loader 放进 worker 池执行，适合耗时的转译 loader。
- esbuild：以原生代码实现转译，单进程内的速度已足够快，常直接替换慢速链。
- SWC：同样以原生代码实现，可作为 Babel 的替代以减少转译时间。
- 数据边界：跨线程传递模块数据有序列化成本，只应把耗时足够大的 loader 放进线程池。

```js
// webpack.config.js：把 babel-loader 放入线程池
module.exports = {
  module: {
    rules: [
      {
        test: /\.js$/,
        include: /src/,
        use: ["thread-loader", "babel-loader"],
      },
    ],
  },
};
```

```json
{
  "jsc": {
    "parser": { "syntax": "typescript", "tsx": true },
    "target": "es2020"
  },
  "module": { "type": "es6" }
}
```

> [!CAUTION]
> **注意内容**：thread-loader 的启动与序列化开销固定，项目规模较小时反而更慢。

**速记**：thread-loader 分池、esbuild 与 SWC 换实现，线程池只给耗时足够的 loader。



#### 并行化的边界与代价

**并行边界**：是并行度提升不再带来收益、甚至转为负收益的临界点。

- 核心数上限：并行度超过可用核心数只会增加切换开销。
- 内存上限：每个进程都占内存，并行过高会触发内存不足而中断构建。
- 一致性代价：多进程下共享状态的插件可能失效，需要确认插件是否支持并行。
- 观测方式：调整并行度前后对比墙钟时间，找到收益拐点。

```bash
NODE_OPTIONS=--max-old-space-size=4096 npx vite build
# 提高堆上限，避免并行构建时触发内存不足
```

> 优化顺序上先并行后加内存：盲目调大内存上限会掩盖真正的内存泄漏。

**速记**：并行度受核心数与内存约束，超限转负，需实测找拐点。



### 增量与持久缓存

**增量构建**：是只重新处理自上次构建以来发生变化的输入，其余部分复用既有结果的做法。

#### 开发期缓存

**开发期缓存**：是开发服务器在内存或缓存目录中保留的编译结果，用于支撑快速的热更新与刷新。

- 依赖预构建：产物落在缓存目录，见本篇依赖预构建一节。
- 模块图缓存：未变化模块的转换结果被保留，改动只重算受影响子图。
- 文件监听：监听文件变化触发热更新，避免整页刷新。
- 预转换：启动时预先转换入口可达的文件，减少首次访问的等待。

```js
// vite.config.js：启动时预热客户端入口文件
export default {
  server: {
    warmup: {
      clientFiles: ["./src/main.ts", "./src/views/**/*.vue"],
    },
  },
};
```

> 开发期缓存的收益体现在「改一个文件到浏览器更新」的延迟上，与生产构建耗时是两套不同的指标。

**速记**：开发期缓存含预构建产物、模块图与预热转换，优化的是热更新延迟。



#### 构建期持久缓存

**持久缓存**：是把构建结果写入磁盘并在下次构建时复用的机制，跨进程与跨命令生效。

- Vite：打包器缓存默认写在缓存目录，重复构建时复用不变模块的处理结果。
- webpack：把 cache.type 设为 filesystem 即启用磁盘缓存，并在 buildDependencies 中声明参与缓存键的配置文件。
- 命中条件：模块内容、依赖版本、配置与运行环境全部一致时才能复用。
- 失效方式：缓存键不匹配时该模块自动重算，无需手工清理。

```js
// webpack.config.js
module.exports = {
  cache: {
    type: "filesystem",
    buildDependencies: {
      config: [__filename],
    },
  },
};
```

> [!IMPORTANT]
> **重要内容**：必须把配置文件本身加入 buildDependencies，否则改动配置后仍会命中旧缓存，产出与配置不符的产物。

**速记**：持久缓存落磁盘跨命令复用，缓存键由内容、依赖、配置与环境共同决定。



#### 缓存失效与远程缓存

**缓存失效**：是输入变化导致既有缓存不再可用、必须重算的情形，正确性优先于命中率。

- 输入变化：源码、依赖版本、环境变量、配置任一变化都应使相关缓存失效。
- 版本标记：为缓存显式写版本号，可在工具升级后强制重建。
- 远程缓存：把命中结果上传到共享存储，团队成员与流水线之间复用，适合大型单仓。
- 风险：缓存一致性依赖哈希输入的完整性，漏掉任一输入都会产生错误产物。

```bash
pnpm exec turbo run build --dry=json
# {"cache":{"status":"MISS"}} 表示该任务需要重新执行
```

> 持久缓存目录属于本地产物，不要提交到版本库，否则会把某台机器上的结果分发给所有人。

**速记**：输入变化即失效，版本号可强制重建，远程缓存跨机器共享但依赖哈希完整。



### 产物层面的优化

**产物优化**：是在工作方式不变的前提下，通过拆分、压缩与裁剪减少需要传输与解析的字节数。

#### 分包与按需加载

**分包（code splitting）**：是把产物按使用时机拆成多个文件，使首屏只加载必需部分。

- 手动分包：把稳定的第三方依赖拆成独立文件，利用浏览器缓存。
- 路由级拆分：按路由动态导入，进入路由时才加载对应代码块。
- 动态导入：用 import 函数在运行时加载模块，返回 Promise。
- 共享块：多个入口共用的模块抽成公共块，避免重复打包。

```js
// vite.config.js：把体积大且稳定的依赖单独分包
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["vue", "vue-router"],
          charts: ["echarts"],
        },
      },
    },
  },
};
```

```ts
// 路由级按需加载
const loadDashboard = async () => {
  const { renderDashboard } = await import("./views/Dashboard");
  return renderDashboard;
};
```

> 拆得太细会带来额外的请求与调度开销，分包依据应是「加载时机是否一致」而非「体积是否小」。

**速记**：分包按加载时机切分，动态导入做路由级拆分，稳定依赖单独成块吃缓存。



#### 压缩与资源处理

**压缩**：是在不改变行为的前提下减小产物字节数的处理，分语法压缩与传输压缩两层。

- 语法压缩：删除空白与注释、压缩标识符、做常量折叠，由 minify 选项控制。
- 传输压缩：服务端以 gzip 或 br 提供产物，构建日志中的压缩后体积可作参考。
- 资源内联：小于阈值的静态资源转成内联形式，减少请求数。
- 图片处理：超过内联阈值的图片单独输出，必要时转成现代格式。

```js
// vite.config.js
export default {
  build: {
    minify: "esbuild",
    assetsInlineLimit: 4096,
    reportCompressedSize: true,
  },
};
```

> 传输压缩在服务端启用，构建工具只负责把产物体积与压缩后体积打印出来供评估。

**速记**：压缩分语法与传输两层，资源按阈值内联，压缩体积看构建日志。



#### 体积监控与回归防护

**体积监控**：是把产物体积固化为可校验的门槛，在体积超标时让流水线失败。

- 预算：为入口文件与关键代码块设定体积上限。
- 回归防护：每次提交后对比体积，超出上限即失败，防止体积悄悄增长。
- 报告：把体积变化写进流水线输出，便于评审时查看。
- 定位：体积突增时用可视化分析定位到具体模块。

```json
{
  "size-limit": [
    { "path": "dist/assets/index-*.js", "limit": "180 kB" },
    { "path": "dist/assets/vendor-*.js", "limit": "260 kB", "gzip": true }
  ]
}
```

```bash
npx size-limit
# Size limit: 180 kB
# dist/assets/index-8f3a1c2.js: 176.4 kB (limit 180 kB) ✓
```

> [!WARNING]
> **警告内容**：为缩小体积而关闭 source map 或去掉错误采集，会让线上问题无法定位，可观测性的损失远大于省下的字节。

**速记**：体积预算入流水线形成回归门禁，超标即失败，突增时分包定位到模块。
