## Gulp 与现代工具链的取舍

Gulp 与 Vite、webpack 的取舍不是新旧之争，而是两类模型各自适配的场景不同。本篇只从 Gulp 视角给出判断：什么场景继续用、什么信号该迁移、迁移怎么走、以及两边长期共存如何划边界；现代工具自身的定位与 Vite 的迁移细节见本主题第 4 篇至第 10 篇与第 32 篇，Gulp 与 webpack 的调用示范见第 53 篇。

### Gulp 的优势场景

判断是否继续使用 Gulp，先看它相对现代工具多出来的那部分能力用在哪里。本节从资源批处理、遗留项目与定制流水线三处展开。

#### 非模块化资源的批处理

**非模块化资源**：是不参与模块图解析、只需按规则批量转换的静态文件，如样式、模板、图片与字体。

- 处理特征：每个文件独立处理，文件之间没有依赖关系需要分析。
- 表达方式：一条管道对应一类资源的完整加工过程，读代码即读流程。
- 增量友好：按文件粒度判断是否需要重跑，比按模块图重算更直接。
- 组合灵活：不同资源可以插入任意数量的定制步骤，不受打包器约束。
- 产物形态：产物是常规静态文件，不需要任何运行时包装。

```js
import gulp from "gulp";

export function copyAssets() {
  return gulp
    .src("src/assets/**/*", { base: "src/assets" })
    .pipe(gulp.dest("dist/assets"));
}
```

> 判断一类资源是否适合 Gulp，看它是否需要被静态分析出依赖图：不需要依赖图，管道就是最合适的模型。

**速记**：不参与模块图的资源按文件独立处理，用管道表达流程最直接。



#### 遗留项目的低改造成本

**低改造成本**：是在既有 gulpfile 上增量追加步骤即可满足新需求、无需替换构建主体的特性。

- 现状基础：既有流水线已在运行，新增一类资源只需追加一条管道。
- 风险范围：改动局限在管道内部，不触及模块打包方式与产物契约。
- 人员因素：熟悉流式写法的成员可以直接改动，不需要先学新的配置模型。
- 版本稳定：Gulp 自身接口多年保持稳定，既有配置不会因升级大面积失效。
- 代价分布：主要维护代价在插件侧，而不在 Gulp 本体。

```bash
npx gulp --tasks
# 列出当前 gulpfile 导出的任务清单，作为改造前的现状盘点
```

> 存量项目的改造收益，通常来自把重复的手工步骤固化成任务，而不是更换构建主体。

**速记**：遗留项目增改只需追加管道，风险局限在管道内，代价主要在插件维护状态。



#### 定制化流水线的表达力

**定制化流水线**：是需要按业务规则加工文件、且这些规则难以用声明式配置表达的场景。

- 自由编排：任意步骤可以插入管道，包括调用脚本、读写外部数据与条件分支。
- 数据驱动：可以从接口或本地数据文件取值，参与模板与样式的生成。
- 条件处理：按文件路径或内容走不同步骤，用条件插件即可表达。
- 可读性：一个任务一段代码，流程与代码结构一致，便于交接。
- 使用边界：自由编排也意味着缺少约束，规则堆多之后维护成本上升。

```js
import gulpIf from "gulp-if";
import terser from "gulp-terser";

const isProduction = process.env.NODE_ENV === "production";

export function buildScripts() {
  return gulp
    .src("src/scripts/**/*.js")
    .pipe(gulpIf(isProduction, terser()))
    .pipe(gulp.dest("dist/scripts"));
}
```

> [!NOTE]
> **提醒内容**：能自由编排不等于应当自由编排，流水线的每一步都应有明确目的，否则会退化成难以接手的历史脚本。

**速记**：定制规则难以声明式表达时，管道加条件分支最直接，但要给步骤设边界。



### 与现代构建工具的差异

两类工具在驱动方式、配置心智与生态维护上取向不同。本节逐项对照，作为取舍的事实依据。

#### 驱动模型的差异

**驱动模型**：是决定构建过程如何被展开的机制，Gulp 由显式任务驱动，现代打包工具由模块图驱动。

- Gulp：按任务与管道顺序执行，处理的是文件集合，不解析文件之间的依赖。
- 模块图驱动：从入口出发解析导入关系，自动得到完整依赖图并据此打包。
- 增量依据：前者按文件比对，后者按模块图比对，更新粒度不同。
- 能力边界：依赖图解析与按需分包是打包器独有，管道给不出来。
- 选型含义：需要依赖分析时用打包器，不需要时管道足够。

```text
任务驱动（Gulp）
  任务 A ──> 管道 ──> 产物
  任务 B ──> 管道 ──> 产物

模块图驱动（打包器）
  入口 ──> 解析导入 ──> 依赖图 ──> 分包 ──> 产物
```

> 两种模型不互斥，处理不需要依赖图的资源时，任务驱动的开销更低。

**速记**：Gulp 按任务处理文件集合，打包器按入口解析依赖图，需要依赖分析时只有后者能胜任。



#### 配置与心智成本

**心智成本**：是理解与改动构建配置所需的认知负担，两种模型在这一点上取向不同。

- Gulp：概念少、以代码表达流程，读一遍 gulpfile 即可知道构建做了什么。
- 声明式配置：概念与选项更多，但常见需求有成熟的默认值。
- 默认能力：现代工具内置开发服务器、依赖解析与资源处理，不必逐个选插件。
- 自建成本：用 Gulp 实现同等能力需要自行挑选并组合插件。
- 学习曲线：熟悉 JavaScript 的成员上手 Gulp 更快，熟悉配置模型的成员上手打包器更快。

```js
// Gulp：流程即代码，读管道即知构建做了什么
export function buildStyles() {
  return gulp
    .src("src/styles/**/*.scss", { base: "src/styles" })
    .pipe(compileSass())
    .pipe(postcss(postcssPlugins))
    .pipe(cleanCss())
    .pipe(gulp.dest("dist/styles"));
}
```

> 心智成本不是绝对的优劣，而是把复杂度放在配置里还是放在代码里的选择。

**速记**：Gulp 概念少、流程即代码，现代工具默认能力多、配置概念也多。



#### 生态与维护状况

**生态状况**：是插件数量、维护活跃度与失效风险的综合，Gulp 的主要风险集中在插件侧。

- 插件粒度：Gulp 的能力由大量单职责插件拼装，任一环节都可能停更。
- 替代路径：部分插件的能力已被上游工具内置，直接调用底层库反而更稳。
- 维护判断：选用前查最近发布时间与仓库状态，避免依赖长期无人维护的插件。
- 降级方案：能直接调用底层库时优先直连，减少一层封装。
- 关注重点：Gulp 本体接口稳定，插件清单才是需要持续维护的部分。

```bash
npm view gulp version
# 确认当前使用的主版本，判断升级影响范围
npm outdated
# 列出落后于声明范围的依赖，插件清单需要单独核对维护状态
```

> 插件停更不等于立刻不可用，但一旦与新版运行时或新语法冲突，替换成本会落到维护者身上。

**速记**：Gulp 本体稳定、插件易停更，能直接调用底层库时优先直连，插件按维护状态选用。



### 迁移时机判断

迁移的前提是收益明确大于成本。本节给出触发迁移的信号、不必迁移的情形，以及评估时要留下的基线。

#### 触发迁移的信号

**迁移信号**：是流水线已无法低成本支撑当前需求、继续维护的代价明显超过替换代价的征兆。

- 需求信号：需要按路由分包、按需加载或框架级热更新，管道给不出这些能力。
- 性能信号：全量重跑耗时已经影响日常开发节奏。
- 维护信号：多个关键插件停更，升级运行时时需要逐个替换。
- 人力信号：新成员理解 gulpfile 的成本高于理解配置模型的成本。
- 组合信号：构建脚本里既有管道又有打包调用，两边职责开始重叠。

```text
出现以下任意两条，进入迁移评估：
  需要依赖图与分包         ── 是
  全量重跑已影响开发节奏   ── 是
  关键插件停更且无替代     ── 是
```

> 单一信号通常不足以支撑迁移，两条以上同时出现时才值得启动一次完整评估。

**速记**：需求、性能、维护、人力四类信号中任意两条同时出现，才启动迁移评估。



#### 不必迁移的情形

**不必迁移**：是当前需求在既有模型内可以低成本满足、迁移收益低于成本的情形。

- 无模块化需求：只做样式、模板与资源转换，管道完全够用。
- 产物简单：产物是常规静态文件，没有分包与按需加载的要求。
- 稳定优先：项目进入维护期，替换构建的风险高于收益。
- 规则定制：业务规则高度定制，搬进打包器生态反而更绕。
- 收益偏低：跑得足够快、故障足够少，替换只带来一次性成本。

```bash
npx gulp build
# 记录一次完整构建的耗时
npx gulp --tasks | wc -l
# 统计任务数量，评估迁移时需要映射的配置量
```

> [!TIP]
> **建议内容**：把「不迁移」也当成一次明确的决定记录下来并写明理由，避免每次有人提起都重新评估一轮。

**速记**：无模块化需求、产物简单、项目进入维护期或规则高度定制时，不迁移更划算。



#### 评估清单与验证口径

**评估清单**：是在迁移前把当前流水线的能力逐项列清、确认目标工具能否覆盖的核对表。

- 能力项：把每个任务对应的能力列成条目，如编译、压缩、指纹、刷新。
- 覆盖判定：逐条标注目标工具有内置能力、有插件，还是需要自建。
- 产出基线：记录产物数量、目录结构与命名规则，作为迁移后的比对基准。
- 耗时基线：记录完整构建与增量构建的耗时，作为验收数据。
- 风险项：标出无覆盖或覆盖不完整的条目，这些是迁移后必须重点验证的部分。

```text
能力清单（逐项标注覆盖情况）
  预处理器编译 ── 内置 / 插件 / 需自建
  样式后处理   ── 内置 / 插件 / 需自建
  资源指纹     ── 内置 / 插件 / 需自建
  页面模板     ── 内置 / 插件 / 需自建
```

> [!IMPORTANT]
> **重要内容**：评估阶段必须先记录产物基线与耗时基线，没有基线就无法判断迁移是否真的成功。

**速记**：逐项列出能力、覆盖情况与产物基线，没有基线就无法验收迁移结果。



### 迁移路径与步骤

迁移不是把 gulpfile 翻译一遍就结束，而是按能力映射、分批切换、保留回退三步推进。

#### 从任务清单反推配置

**反推配置**：是把 gulpfile 中的每个任务翻译为目标工具的入口、插件与产物选项的过程。

- 起点：先列出全部导出任务，区分开发用与发布用两类。
- 映射：管道每一步对应目标工具的一个能力或插件，逐条落位。
- 合并：多个管道处理同一类资源时，在目标工具侧合并为一个入口或一条规则。
- 特例：无法映射的定制步骤先保留为独立脚本，在构建之后单独执行。
- 留痕：映射结果写进仓库文档，迁移结束后仍可作为配置的说明。

```text
Gulp 任务                     目标侧对应
compileStyles ──────────────> 入口：src/styles/main.scss
copyAssets ─────────────────> 静态资源目录声明
buildScripts ───────────────> 入口：src/scripts/index.js
watch + serve ──────────────> 开发服务器命令
```

> 反推的顺序是先能力后配置：先确认要什么能力，再去目标工具里找对应字段。

**速记**：先列任务、再逐条映射到能力与配置，无法映射的临时保留为独立脚本。



#### 分阶段替换与并行运行

**分阶段替换**：是按资源类型或页面对应批次迁移、新旧两条链路同时可用，避免一次性切换。

- 批次划分：按资源类型分，或按页面的访问量分。
- 并行方式：两条链路各自产出到不同目录，用命令行分别调用。
- 比对方法：对同一份源码分别构建，逐项比对产物清单与页面表现。
- 停止条件：某个批次连续稳定运行后，再从旧链路中移除对应任务。
- 进度记录：用清单记录每个批次的迁移状态，避免半途失焦。

```json
{
  "scripts": {
    "build:legacy": "gulp build",
    "build:next": "vite build",
    "build": "npm run build:next"
  }
}
```

> [!CAUTION]
> **注意内容**：并行期间两条链路处理同一份源码，改动源码结构前必须确认两边都能通过，否则容易只修好其中一条。

**速记**：按资源类型或页面分批替换、双链路并行产出并比对，稳定后再拆掉旧任务。



#### 回退路径与验收标准

**回退路径**：是迁移出现短期无法解决的问题时，能立即切回旧流水线的安排。

- 触发条件：明确写出什么情况下回退，如产物缺文件、页面空白或关键样式缺失。
- 保留期限：旧链路保留到新链路稳定运行若干发布周期之后再清理。
- 验收标准：以产物清单、体积、首屏表现与运行报错四项为准，不看构建是否成功。
- 验证范围：覆盖所有页面类型与关键交互，不只验证首页。
- 收尾动作：验收通过后归档旧配置并记录替换说明，不直接删除历史。

```bash
npm run build:legacy
# 回退时执行旧链路，产物写回原目录
ls dist
# 确认产物清单与原基线一致
```

> 回退能力本身就是迁移方案的一部分，没有回退路径的迁移等于把风险全部留给发布当天。

**速记**：先定回退触发条件与验收四项，旧链路保留到稳定运行若干周期后再收。



### 共存策略

长期看，最省事的状态往往不是二选一，而是把两类工具的能力按边界分配。

#### 按资源类型分工

**分工共存**：是把需要依赖图的脚本交给打包器、把其余资源留给 Gulp 的长期安排。

- 划分依据：是否需要静态分析出依赖图，需要则交给打包器。
- 典型归属：样式、模板、图片、字体与站点文件留给 Gulp。
- 交接方式：打包器只产出脚本产物，Gulp 负责把它写进最终目录。
- 顺序约束：打包先于引用改写，避免改写时产物还不存在。
- 边界固化：哪一类资源由哪条链路负责，写进项目文档且不做例外。

```js
// gulpfile.js 把打包产出的脚本并入最终产物目录
export function collectBundles() {
  return gulp
    .src("build/**/*.js", { base: "build" })
    .pipe(gulp.dest("dist/scripts"));
}
```

> 与打包器的调用写法与产物衔接见本主题第 53 篇 Gulp 与 webpack 协作，本篇只固定职责边界。

**速记**：靠是否需要依赖图来划分，脚本交给打包器，其余资源留在 Gulp，产物由 Gulp 汇总。



#### 边界与产物交接

**产物交接**：是两条链路之间只通过产物目录交换结果、不读取对方中间状态的约定。

- 单向依赖：Gulp 读取打包产物，打包器不读取 Gulp 的任何中间文件。
- 中间目录：打包器写入独立的中间目录，由 Gulp 搬运到最终产物目录。
- 清理范围：清理任务区分中间目录与最终目录，避免顺序出错删空输入。
- 配置归属：产物契约由写出的一方定义，读取的一方只消费不改写。
- 排错切面：产物对不上时先看中间目录内容，再判断问题出在哪一端。

```bash
npx webpack --config webpack.config.js
# 打包器写入 build 中间目录
npx gulp build:site
# Gulp 读取中间目录并汇总到 dist
```

> [!NOTE]
> **提醒内容**：中间目录必须写进忽略清单，它不属于发布产物，误提交会把构建结果带进仓库。

**速记**：两条链路只通过产物目录交接、单向读取，清理与忽略清单按中间目录单独处理。



#### 命令与文档同步

**命令同步**：是把两条链路的构建命令统一到少量入口、并把产物约定写进文档的做法。

- 命令收敛：对外只暴露开发、构建、清理三条命令，内部顺序固定。
- 命名一致：命令名与产物目录名保持稳定，避免流水线随改名失效。
- 文档内容：写明每条链路负责的资源、产物目录与执行顺序。
- 变更同步：改动任一条链路的产物目录时，必须同时更新命令与文档。
- 交接价值：新成员按文档即可复现构建，不必先读完整配置文件。

```json
{
  "scripts": {
    "dev": "gulp dev",
    "build": "npm run build:bundle && npm run build:site",
    "build:bundle": "webpack --config webpack.config.js",
    "build:site": "gulp build:site",
    "clean": "gulp clean"
  }
}
```

> [!IMPORTANT]
> **重要内容**：命令顺序要写进脚本而不是靠记忆执行，构建步骤一旦顺序颠倒，产物缺失往往只在发布后才发现。

**速记**：对外只留开发、构建、清理三条命令，负责范围与产物目录写进文档并随改动同步。
