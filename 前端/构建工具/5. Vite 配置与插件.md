## Vite 配置与插件

上一篇跑通了开发链路，本篇处理「默认值不够用」的场景：别名、代理、样式预处理、插件接入与配置复用。开发服务器细节见本主题第 6 篇，生产构建见本主题第 7 篇。

### 配置文件与 defineConfig

本节确立配置文件的加载规则与书写形式，是后续所有配置字段的载体。

#### 配置文件的位置与命名

**配置文件**：是项目根目录下名为 vite.config.js 的文件，启动时被自动查找并加载。

- 命名：vite.config.js、vite.config.ts、vite.config.mjs、vite.config.cjs 均可，按模块格式选择。
- 位置：默认在项目根目录，可用 --config 指定其他路径。
- 类型脚本：使用 TypeScript 时无需额外配置，Vite 会自行转译配置文件。
- 缺省：没有配置文件时 Vite 以内置默认值运行。

```ts
// vite.config.ts 的最小内容
import { defineConfig } from "vite";

export default defineConfig({});
```

> 项目根目录指执行 vite 命令时的工作目录，可用 root 配置项改变。

**速记**：配置文件默认叫 vite.config.ts，放在项目根目录自动加载。



#### defineConfig 与基础结构

**defineConfig**：是 Vite 导出的辅助函数，接收配置对象或返回配置对象的函数，为其提供类型推断与字段补全。

- 作用：只做类型包装，运行时不改变配置内容。
- 结构：顶层字段按功能分组，如 plugins、resolve、server、build、css。
- 类型检查：在 TypeScript 中写错字段名会直接报错。
- 等价写法：直接导出对象同样生效，但会失去类型检查。

```ts
import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";

export default defineConfig({
  plugins: [vue()],
  server: { port: 5173 },
  build: { outDir: "dist" },
});
```

```js
// 纯 JavaScript 配置缺少类型检查，字段名写错不会报错
export default {
  server: { prot: 5173 }, // 拼写错误不会被提示，端口配置实际未生效
};
```

> 顶层字段名与官方文档一一对应；纯 JavaScript 配置中拼错的字段会被静默忽略，改动配置后应确认是否真的生效。

**速记**：defineConfig 包装配置以换取类型安全，字段按功能分区。



#### 函数式配置与条件配置

**函数式配置**：是导出一个接收 ConfigEnv 参数的函数，按 command 与 mode 动态返回不同配置。

- 参数：ConfigEnv 含 command 与 mode，command 取值为 serve 或 build。
- 用途：开发与构建使用不同插件、不同端口或不同输出目录。
- 常见做法：只有生产构建才加载体积分析类插件。
- 注意：函数每次启动执行一次，不要在其中写依赖网络请求的副作用。

```ts
import { defineConfig } from "vite";

export default defineConfig(({ command, mode }) => {
  return {
    define: {
      __IS_DEV__: JSON.stringify(command === "serve"),
    },
    server: { port: mode === "staging" ? 5174 : 5173 },
  };
});
```

> mode 的取值来源与加载优先级详见本主题第 6 篇 Vite 开发服务器与环境变量。

**速记**：配置可写成函数，按 command 与 mode 分支返回不同结果。



### 插件机制与常用插件

本节说明插件是什么、如何排序，以及日常最常引入的官方插件。

#### 插件的形态与钩子

**插件**：是带 name 字段并实现若干钩子函数的对象，Vite 在生命周期的固定阶段调用这些钩子。

- 必需字段：name 用于报错与调试时标识插件来源。
- 钩子：config、configResolved、configureServer、transform、buildStart、generateBundle 等。
- 返回形式：可以是对象，也可以是一个返回对象的函数。
- 兼容性：Rollup 插件接口被 Vite 兼容，多数 Rollup 插件可直接使用。

```js
// 一个最小插件：统计被转换的模块数量
export function countModules() {
  let total = 0;
  return {
    name: "count-modules",
    transform(code, id) {
      total += 1;
      return code;
    },
    buildEnd() {
      console.log(`transformed ${total} modules`);
    },
  };
}
```

> transform 钩子接收 code 与 id 两个参数，前者是模块源码，后者是模块的绝对路径或虚拟标识。

**速记**：插件是带 name 与钩子的对象，Rollup 插件可直接复用。



#### 插件顺序与 enforce

**插件顺序**：是 Vite 决定多个插件在生命周期中执行先后的规则，由配置数组次序与 enforce 字段共同确定。

- 默认次序：数组中越靠前的插件越先执行。
- enforce 取 pre：提前到 Vite 核心插件之前执行，常用于预处理源码。
- enforce 取 post：延后到 Vite 核心插件之后，常用于产物后处理。
- apply 字段：取值为 serve 或 build，限定插件只在某一阶段生效。

```js
import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";
import legacy from "@vitejs/plugin-legacy";

export default defineConfig({
  plugins: [
    vue(),
    legacy({ targets: ["defaults", "not IE 11"] }),
    { name: "html-tweak", enforce: "post", transformIndexHtml: (html) => html },
  ],
});
```

> 顺序敏感的场景以 transform 类插件最典型：前一个插件的输出是后一个插件的输入。

**速记**：顺序由数组位置与 enforce 共同决定，pre 提前、post 延后。



#### 常用插件与选择

**常用插件**：是官方维护的框架接入与兼容插件，覆盖单文件组件、JSX、旧浏览器降级等高频需求。

- @vitejs/plugin-vue：支持 .vue 单文件组件，Vue 项目必装。
- @vitejs/plugin-vue-jsx：支持以 JSX 语法书写 Vue 组件。
- @vitejs/plugin-react：提供 React 的快速刷新与 JSX 转译。
- @vitejs/plugin-legacy：为旧浏览器生成降级产物与垫片。
- 社区插件：命名通常为 vite-plugin-xxx，安装前需确认兼容的 Vite 主版本。

```bash
npm install --save-dev @vitejs/plugin-vue @vitejs/plugin-legacy
```

```ts
// 插件按需引入：只在需要旧浏览器兼容的项目里追加降级插件
import legacy from "@vitejs/plugin-legacy";

export default {
  plugins: [legacy({ targets: ["defaults", "not IE 11"] })],
};
```

> [!CAUTION]
> **注意内容**：社区插件与 Vite 主版本的兼容性需逐一确认，升级 Vite 大版本时应同步检查插件版本与迁移说明，否则可能在启动或构建阶段直接失败。

**速记**：官方插件管框架接入与降级，社区插件按需引入并核对版本。



### 路径别名与 resolve 配置

本节解决导入路径过长与依赖重复实例两类解析问题。

#### resolve.alias 路径别名

**resolve.alias**：是 Vite 的路径别名配置项，把导入路径中的前缀映射到实际目录，避免深层相对路径。

- 写法：值是对象或数组，键为别名，值为绝对路径。
- 路径构造：用 node:path 的 resolve 配合 fileURLToPath 得到绝对路径。
- 使用：源码中写 @/App.vue 会解析到 src/App.vue。
- 构建兼容：Vite 与 Rollup 共用该配置，构建期同样生效。

```ts
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
});
```

```js
// src/main.js 中使用别名，避免逐层回退的相对路径
import { formatPrice } from "@/utils/formatPrice.js";

console.log(formatPrice(1299)); // "¥12.99"
```

> 别名只影响模块解析，不改变文件真实位置；值必须以绝对路径给出，写相对路径在部分场景下会解析错误。

**速记**：resolve.alias 把 @ 映射到 src，键与值都写清楚再用。



#### 别名与编辑器类型提示同步

**类型提示同步**：是让编辑器的 TypeScript 语言服务识别同一套别名的做法，否则编辑器报找不到模块而构建正常。

- 配置位置：tsconfig.json 的 compilerOptions.paths 字段。
- 对应关系：paths 的键要与 resolve.alias 保持一致，值为相对 baseUrl 的路径数组。
- 自动生成：使用 create-vue 等脚手架时该配置已就绪。
- 排查：编辑器报错但构建通过时，优先检查 paths 是否缺失。

```json
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

> 构建器与编辑器的解析规则相互独立，两处都配置别名才能真正一致。

**速记**：别名要在 vite.config.ts 与 tsconfig.json 两处同时声明。



#### 解析相关选项

**解析相关选项**：是 resolve 下除 alias 之外的常用字段，控制扩展名补全与依赖去重。

- resolve.extensions：省略扩展名时的尝试顺序，默认含 .mjs、.js、.mts、.ts、.jsx、.tsx、.json。
- resolve.dedupe：强制某些依赖只解析到一份实例，常用于避免出现多个框架副本。
- resolve.mainFields：决定从 package.json 的哪个字段取包入口，库项目可能需要调整。
- resolve.preserveSymlinks：控制是否保留软链接路径，工作区项目按需开启。

```js
export default {
  resolve: {
    dedupe: ["vue"],                            // 避免重复实例导致的状态不共享
    extensions: [".mjs", ".js", ".ts", ".json"],
  },
};
```

> [!WARNING]
> **警告内容**：dedupe 只应在确实出现重复实例时使用，滥用会把本应多版本并存的依赖强制合并，引发难以定位的运行时错误。

**速记**：extensions 管补全、dedupe 管去重，都要有明确理由才改。



### 样式与静态资源配置

本节处理样式语言、作用域与资源引用三类常见接入需求。

#### CSS 预处理器与 PostCSS

**CSS 预处理器**：是把 Sass、Less、Stylus 等源码编译为标准 CSS 的工具，Vite 通过安装对应依赖即可识别。

- 安装：使用 Sass 时执行 npm install --save-dev sass。
- 使用：直接导入 .scss 文件，无需额外 loader 配置。
- 参数：通过 css.preprocessorOptions 传入，如 additionalData 注入公共变量。
- PostCSS：存在 postcss.config.js 时自动加载，接入细节详见本主题第 11 篇 Babel 与 PostCSS。

```bash
npm install --save-dev sass
```

```scss
// src/styles/theme.scss
$brand-color: #3b82f6;

.button {
  color: $brand-color;
}
```

```ts
// vite.config.ts
export default {
  css: {
    preprocessorOptions: {
      scss: {
        additionalData: '@use "@/styles/variables.scss" as *;',
      },
    },
  },
};
```

> 预处理器依赖按需安装，未安装 sass 时导入 .scss 文件会在转换阶段直接报错。

**速记**：装 sass 即可用 .scss，参数走 css.preprocessorOptions。



#### CSS Modules 与作用域

**CSS Modules**：是让类名默认局部生效的 CSS 组织方式，Vite 对 .module.css 结尾的文件自动启用。

- 命名约定：文件名为 xxx.module.css，导入后得到类名到实际类名的映射对象。
- 配置：通过 css.modules 调整命名规则与作用域行为。
- 与预处理器组合：xxx.module.scss 同样生效。
- 全局样式：非 module 结尾的样式文件仍按全局样式处理。

```css
/* src/components/Card.module.css */
.card {
  border: 1px solid #e5e7eb;
  border-radius: 8px;
}
```

```js
import styles from "./Card.module.css";

const cardElement = document.createElement("div");
cardElement.className = styles.card;
```

> [!NOTE]
> **提醒内容**：CSS Modules 的映射对象是转换阶段产物，构建后类名会带哈希，不要在业务代码里硬编码原始类名。

**速记**：module 后缀自动开启 CSS Modules，导入得到类名映射对象。



#### 静态资源处理与 public 目录

**静态资源处理**：是 Vite 对图片、字体等资源的分流规则，按引用方式分为参与构建与原样拷贝两类。

- 参与构建：源码中导入或页面中引用的资源进入构建图，得到带哈希的文件名。
- 原样拷贝：public 目录下的文件直接复制到产物根目录，路径保持不变。
- 引用方式：导入得到最终 URL，适合有版本变化的资源；public 适合 favicon 等固定路径资源。
- 特殊后缀：加 ?url 强制返回 URL，加 ?raw 读取文件文本内容。

```js
import logoUrl from "./assets/logo.svg";     // 参与构建，返回最终 URL
import notes from "./assets/notes.txt?raw";  // 返回文件原始文本内容

console.log(logoUrl); // "/assets/logo-a1b2c3.svg"
console.log(notes);   // 文件原始文本内容
```

> public 目录下的文件不参与哈希与优化，也不应使用导入方式引用。

**速记**：导入的资源参与构建并加哈希，public 的资源原样拷贝。



### 配置的合并与复用

本节处理多环境差异与团队内共享配置的组织方式。

#### 按模式拆分配置

**按模式拆分配置**：是利用 ConfigEnv 的 mode 参数在同一配置文件内区分不同环境的取值。

- 取值来源：命令行 --mode 指定，未指定时开发期默认 development，构建期默认 production。
- 常见做法：测试环境与生产环境使用不同的接口前缀与 source map 策略。
- 判定写法：在函数式配置中判断 mode 后返回对应字段。
- 环境变量的加载细节详见本主题第 6 篇 Vite 开发服务器与环境变量。

```ts
import { defineConfig } from "vite";

export default defineConfig(({ mode }) => ({
  define: {
    __API_PREFIX__: JSON.stringify(mode === "production" ? "/api" : "/dev-api"),
  },
}));
```

> 模式只影响环境变量加载与配置分支，不改变产物格式；产物形态由构建命令与构建配置决定。

**速记**：同一配置文件内按 mode 分支取值，模式由 --mode 指定。



#### 用 mergeConfig 组合配置

**mergeConfig**：是 Vite 导出的合并函数，把多份配置对象深度合并为一份，常用于抽出共享预设。

- 签名：mergeConfig(defaultConfig, overrideConfig)，后者覆盖前者。
- 合并规则：数组字段默认拼接，标量字段以后者为准。
- 典型场景：把公共配置抽成共享包，各项目只追加差异项。
- 返回：新的配置对象，不改动入参。

```ts
import { defineConfig, mergeConfig } from "vite";
import sharedConfig from "./config/shared.js";

const localConfig = {
  server: { port: 5173 },
};

export default defineConfig(mergeConfig(sharedConfig, localConfig));
```

> 数组字段是拼接而非替换，插件出现冲突时需在合并前手动取舍。

**速记**：mergeConfig 深度合并多份配置，数组拼接、标量覆盖。



#### 共享配置与团队约定

**共享配置**：是把团队通用的别名、代理、插件收进一份可复用文件，各项目只保留差异项。

- 组织形式：放在内部包中导出，或放在项目内的 config 目录。
- 命名导出：按用途拆分，如 baseConfig、styleConfig。
- 注释化：共享配置的每个字段应注明用途，避免形成无人敢改的配置。
- 版本约束：共享配置随 Vite 主版本升级而升级，避免跨版本复用。

```js
// config/shared.js
import { fileURLToPath, URL } from "node:url";

export default {
  resolve: {
    alias: { "@": fileURLToPath(new URL("../src", import.meta.url)) },
  },
  server: {
    port: 5173,
    strictPort: true,
  },
};
```

> [!IMPORTANT]
> **重要内容**：共享配置提升复用度，也把耦合引入项目；修改前需确认所有引用方已评估影响，避免一处改动引发多处构建失败。

**速记**：共享配置收敛公共字段，升级与改动都要同步全体引用方。
