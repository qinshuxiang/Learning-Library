## Gulp 常用插件清单

### 编译类插件

编译类插件处在管道（pipeline）的前段，把浏览器或运行环境无法直接解析的源码转换成标准产物。本节说明三类编译插件的职责、输入输出与接入位置。

#### 预处理器编译插件

**预处理器编译插件**：是把 Sass、Less 一类预处理器的源码编译成标准 CSS 的插件，接入位置在读取样式源文件之后的第一个环节。

- 解决的问题：预处理器语法浏览器无法解析，必须先编译为 CSS 才能交付。
- 输入输出：输入是预处理器源码，输出扩展名统一为 css，内容为浏览器可解析的样式。
- 接入位置：紧接 gulp.src 之后，输出的流（stream）仍可继续用于补全与压缩环节。
- 关键选项：是否产出 source map、输出样式的排版风格、预处理器自身选项的透传方式。
- 错误来源：语法错误与导入路径错误由预处理器抛出，以流错误的形式向上传播。

```js
const { src, dest } = require('gulp');
// 示例中的插件包名一律以代称书写，实际安装时替换为注册表中的真实包名
const compileSass = require('样式编译插件');

function compileStyle() {
  return src('src/styles/main.scss')
    .pipe(compileSass({ outputStyle: 'expanded' }))
    .pipe(dest('dist/styles'));
}

exports.compileStyle = compileStyle;
```

> 本篇示例不给出具体包名，只保留插件在管道中的位置与职责，安装时按注册表核对包名。

**速记**：预处理器编译插件承接源码到标准样式，位置固定在被读入之后、其余样式环节之前。



#### 脚本转译插件

**脚本转译插件**：是把 TypeScript 或较新语法版本的 JavaScript 转换成目标运行环境可执行代码的插件，位置在脚本被读入之后、优化环节之前。

- 两类职责：剥离类型语法与降级语言特性，两类职责可由不同插件分别承担。
- 输入输出：输入为 ts 文件或带有新语法特性的 js 文件，输出仍为 js。
- 接入位置：与样式编译插件并列，是脚本管道的第一段。
- 与类型检查的分工：转译不做类型校验，类型问题需由独立环节报告。
- 常见现象：缺少必要配置时插件原样透传，产物仍是新语法却没有任何提示。

```js
const { src, dest } = require('gulp');
const compileScript = require('脚本转译插件');

function buildScript() {
  return src('src/scripts/**/*.ts')
    .pipe(compileScript({ target: 'es2019' }))
    .pipe(dest('dist/scripts'));
}

exports.buildScript = buildScript;
```

> 转译与类型检查是两条独立的链路，转译成功不代表类型正确，二者需要分别配置。

**速记**：脚本转译插件只管把语法搬到目标环境，类型问题不由它负责。



#### 模板编译插件

**模板编译插件**：是把模板语言源码渲染成 HTML 字符串的插件，位置在数据准备之后、写出之前。

- 解决的问题：模板语法浏览器无法直接解析，需先渲染为 HTML 再交付。
- 数据来源：渲染所需数据由任务内部传入的对象或外部数据文件提供。
- 接入位置：通常位于页面处理链路的末端，产物为 HTML 文件。
- 命名规则：产物文件名默认沿用模板文件名，调整扩展名需配合重命名环节。
- 错误来源：模板语法错误与数据字段缺失会终止当前文件的处理。

```js
const { src, dest } = require('gulp');
const renderTemplate = require('模板编译插件');

function buildPage() {
  const pageData = { title: '首页', env: 'production' };

  return src('src/pages/**/*.tpl')
    .pipe(renderTemplate(pageData))
    .pipe(dest('dist/pages'));
}

exports.buildPage = buildPage;
```

> 模板数据在任务内聚合成对象后一次性传入，避免在管道中途反复读取数据文件。

**速记**：模板编译插件在管道末端产出页面，数据由任务准备、命名由重命名环节调整。



### 优化类插件

优化类插件处在管道的后段，作用于已经编译完成的产物，目标是缩小交付体积。本节列出压缩、图片处理与去冗余三个方向的插件职责与接入位置。

#### 压缩类插件

**压缩类插件**：是删除产物中的空白、注释与冗余写法以缩小体积的插件，按资源类型分为脚本、样式与 HTML 三类。

- 分工方式：三类压缩各由一个插件承担，彼此不能互相替代。
- 接入位置：位于全部编译与转换环节之后，是写出前的最后一步。
- 选项取舍：标识符混淆会改变调试体验，需要与 source map 一并开启。
- 适用对象：可对单文件压缩，也可对合并后的完整文件压缩，后者效果更充分。
- 风险点：压缩可能改变依赖求值顺序，副作用敏感的代码需关闭重排类选项。

```js
const { src, dest } = require('gulp');
const minifyScript = require('脚本压缩插件');

function compressScript() {
  return src('dist/scripts/**/*.js')
    .pipe(minifyScript({ mangle: true, sourceMap: true }))
    .pipe(dest('dist/scripts'));
}

exports.compressScript = compressScript;
```

> [!WARNING]
> **警告内容**：压缩会改写标识符与语句结构，未同步开启 source map 的产物在生产环境报错时无法定位回源码。

**速记**：压缩类插件按资源类型各司其职，统一放在写出前的最后一步。



#### 图片优化插件

**图片优化插件**：是在不改变可见画质的前提下重编码图片、清除元数据以减小体积的插件，输入输出都是图片二进制流。

- 解决的问题：设计工具导出的图片带有冗余元数据与未优化的编码参数。
- 处理模式：有损与无损两类，按业务对画质的要求选择。
- 收益特点：首次处理收益明显，对已优化的图片重复执行不会继续变小。
- 接入位置：与编译类插件没有先后依赖，可独立成一个任务。
- 格式转换：转换到新一代格式通常由独立插件承担，需要与引用替换环节配合。

```js
const { src, dest } = require('gulp');
const optimizeImage = require('图片优化插件');

function buildImage() {
  return src('src/assets/images/**/*.{png,jpg}')
    .pipe(optimizeImage({ quality: 80 }))
    .pipe(dest('dist/assets/images'));
}

exports.buildImage = buildImage;
```

> 图片优化是无依赖的独立环节，放在编译任务之前或之后都不影响结果，只影响整体耗时分布。

**速记**：图片优化插件独立成任务，有损与无损按画质要求选择。



#### 精简与去冗余类插件

**精简与去冗余类插件**：是删除产物中未被使用或重复的代码与样式片段的插件，用于进一步压缩交付体积。

- 典型能力：移除未引用的选择器、合并重复规则、删除调试语句。
- 前提条件：需要能静态分析引用关系，动态拼接的名称会让分析失效。
- 顺序要求：应排在压缩之前，压缩之后可供分析的结构信息已经丢失。
- 主要风险：误删动态引用的样式，上线前需在真实页面逐屏核对。
- 边界说明：通用优化策略与体积清单见本主题第 15 篇，本节只说明插件位置。

```js
const { src, dest } = require('gulp');
const pruneStyle = require('去冗余插件');

function shrinkStyle() {
  return src('dist/styles/**/*.css')
    .pipe(pruneStyle({ html: ['dist/**/*.html'] }))
    .pipe(dest('dist/styles'));
}

exports.shrinkStyle = shrinkStyle;
```

> [!CAUTION]
> **注意内容**：去冗余依赖静态分析，模板中拼接出的类名会被判定为未使用而删除，上线前必须逐页核对。

**速记**：去冗余插件排在压缩之前，收益可观但必须以真实页面核对误删。



### 文件操作类插件

文件操作类插件不改变文件内容，只改变文件的路径、数量与存在状态，是连接编译与写出两端的中间环节。

#### 重命名插件

**重命名插件**：是在流中改写文件路径与文件名的插件，用于调整输出扩展名、追加内容摘要或改变目录层级。

- 解决的问题：源文件名与产物命名规则不一致，或产物需要携带内容摘要以便长期缓存。
- 两种写法：按固定规则批量改写，或传入函数按当前文件信息逐个计算。
- 目录行为：只指定文件名规则时目录保持不变，改写相对路径才会改变目录层级。
- 摘要命名：摘要取自文件内容，内容未变则文件名不变，可安全设置长期缓存。
- 衔接要求：改名后引用该文件的页面仍指向旧路径，必须与引用替换环节配合。

```js
const { src, dest } = require('gulp');
const renameFile = require('重命名插件');

function renameScriptOutput() {
  return src('dist/scripts/**/*.js')
    .pipe(renameFile({ suffix: '.min' }))
    .pipe(dest('dist/scripts'));
}

exports.renameScriptOutput = renameScriptOutput;
```

> 重命名只影响流中的文件名，不会改写文件内容，也不会自动更新引用它的页面。

**速记**：重命名插件改的是路径与文件名，摘要命名必须与引用替换成对出现。



#### 合并与拼接插件

**合并与拼接插件**：是把流中多个文件按顺序合并成单个文件的插件，用于减少请求数量并固定加载顺序。

- 解决的问题：文件数量过多带来多次请求，加载顺序也需要显式管理。
- 顺序控制：合并结果的文件名由插件参数给出，各文件按流中出现的顺序拼接。
- 接入位置：位于编译与转译之后、压缩之前，作用于已转换完成的代码。
- 适用场景：非模块化脚本与样式，或需要固定合并顺序的资源。
- 不适用场景：模块依赖解析属于打包器职责，合并插件不分析模块之间的关系。

```js
const { src, dest } = require('gulp');
const concatFiles = require('合并插件');

function bundleVendor() {
  return src('src/vendor/*.js')
    .pipe(concatFiles('vendor.js'))
    .pipe(dest('dist/scripts'));
}

exports.bundleVendor = bundleVendor;
```

> 合并顺序即拼接顺序，依赖顺序敏感的资源应先按路径排序再进入合并环节。

**速记**：合并插件按流中顺序拼接文件，只做拼接不解析模块依赖。



#### 清理与拷贝插件

**清理与拷贝插件**：是删除构建输出目录与复制不需要编译的静态文件的插件，用于保证产物干净且完整。

- 清理时机：生产构建开始前删除旧产物，避免历史文件混入交付内容。
- 清理范围：只允许指向构建输出目录，指向源码目录会造成不可恢复的数据丢失。
- 拷贝场景：字体、第三方脚本、根目录下的说明文件等无需处理但需交付的资源。
- 路径保持：拷贝时指定基准目录，产物内保持与源码一致的目录结构。
- 顺序要求：清理必须发生在任何写出动作之前，任务的组合方式见本主题第 52 篇。

```js
const { src, dest } = require('gulp');
const cleanDir = require('清理插件');

async function cleanDist() {
  await cleanDir(['dist']);
}

function copyStatic() {
  return src('src/static/**/*', { base: 'src/static' })
    .pipe(dest('dist'));
}

exports.cleanDist = cleanDist;
exports.copyStatic = copyStatic;
```

> [!IMPORTANT]
> **重要内容**：清理插件的目标只能是构建输出目录，把路径写成源码目录会在一次误执行后直接删除源文件。

**速记**：清理只针对输出目录且必须先于写出，拷贝需要显式指定基准目录保持结构。



### 工具类插件

工具类插件不参与内容转换，而是为整条管道提供映射、状态与错误控制的支持能力。

#### 生成 source map 的插件

**生成 source map 的插件**：是在编译与压缩环节产出源码映射文件、并在产物末尾写入映射注释的插件，用于把产物的错误位置还原到源码。

- 解决的问题：经过编译与压缩之后，报错的行列号与源码不再对应。
- 启用方式：在需要映射的环节打开对应选项，由管道统一写出映射文件。
- 串联要求：链路上每个转换环节都要开启映射，逐级映射才能最终对应源码。
- 交付取舍：映射文件通常只在预发环境提供，不进入生产产物。
- 加载方式：配套的加载插件把映射注册进开发工具的解析链路，调试才能生效。

```js
const { src, dest } = require('gulp');
const mapSource = require('source map 插件');
const compileSass = require('样式编译插件');

function buildStyleWithMap() {
  return src('src/styles/main.scss')
    .pipe(compileSass({ sourceMap: true }))
    .pipe(mapSource.write('../maps'))
    .pipe(dest('dist/styles'));
}

exports.buildStyleWithMap = buildStyleWithMap;
```

> source map 的通用策略与产物体积关系见本主题第 10 篇与第 15 篇，本节只说明插件在管道中的位置。

**速记**：映射插件负责写出映射文件与注释，链路上每个转换环节都要同步开启。



#### 记录构建状态的缓存插件

**记录构建状态的缓存插件**：是保存上一次任务处理过的文件与时间戳、使后续运行可以跳过未变更文件的插件，用于缩短重复构建的耗时。

- 解决的问题：每次运行都全量读取与编译，未变更的文件被反复处理。
- 状态存放：记录写在磁盘固定位置，跨命令行调用依然有效。
- 与监听的关系：监听场景下任务被反复触发，缓存带来的收益最明显。
- 失效条件：记录文件被删除、任务名变更或插件配置改变时，缓存回到全量处理。
- 边界说明：通用缓存原理与优化清单见本主题第 15 篇，增量任务写法见第 50 篇。

```js
const { src, dest } = require('gulp');
const buildCache = require('缓存插件');

function copyChangedStyle() {
  return src('src/styles/**/*.scss', { since: buildCache.lastRun('compileStyle') })
    .pipe(dest('dist/styles'));
}

exports.copyChangedStyle = copyChangedStyle;
```

> 缓存记录的是文件与时间戳的对应关系，产物出现来源不明的问题时可以先删掉记录再重跑一次。

**速记**：缓存插件把上次处理的时间戳落盘，下次以它为门槛跳过未变更文件。



#### 拦截流错误的插件

**拦截流错误的插件**：是监听管道中的错误事件、阻止错误继续向下传播的插件，用于让单个文件的失败不中断整次构建。

- 解决的问题：管道中任一环节抛错会让流停止，后续文件不再被处理。
- 拦截位置：放在容易出错的编译与压缩环节之后，覆盖其后的全部管道。
- 两种策略：记录错误后继续处理其余文件，或终止当前文件并保留完整错误信息。
- 报告时机：错误应集中到流结束时统一输出，否则会被后续日志淹没。
- 分工说明：任务级错误传播与退出码见第 51 篇，本节只说明插件在管道中的接入点。

```js
const { src, dest } = require('gulp');
const catchStreamError = require('拦截流错误的插件');
const compileSass = require('样式编译插件');

function buildStyleTolerant() {
  return src('src/styles/**/*.scss')
    .pipe(compileSass())
    .pipe(catchStreamError())
    .pipe(dest('dist/styles'));
}

exports.buildStyleTolerant = buildStyleTolerant;
```

> [!TIP]
> **建议内容**：错误拦截插件覆盖的是它之后的管道，放在管道开头会漏掉后续环节抛出的错误。

**速记**：拦截插件接在易错环节之后，让单文件失败不再中断整条管道。



### 插件选用原则

插件的数量与质量直接决定流水线的维护成本，选用时按引入必要性、职责边界与维护状态三项判断。

#### 按需引入与最小依赖

**按需引入**：是只安装当前流水线实际用到的插件、以任务需要为唯一依据的引入方式。

- 判断依据：管道中存在该环节才安装，不为可能用到而预装。
- 依赖代价：每个插件都带来传递依赖，数量越多安装与升级成本越高。
- 替代方案：核心 API 已能完成的操作不引入插件，例如读取、写出与目录拷贝。
- 版本匹配：插件声明支持的 Gulp 主版本需与项目一致，安装前核对兼容范围。
- 记录方式：新增插件时同步更新依赖清单，避免环境之间出现差异。

```bash
npm install --save-dev 样式编译插件
# 只把流水线中实际使用的插件写入开发依赖
```

> 依赖清单是环境的唯一事实来源，手工在本地安装而不写入清单会让其他环境无法复现。

**速记**：插件以任务实际需要为准安装，能由核心 API 完成的操作不引入插件。



#### 避免功能重叠

**功能重叠**：是两个插件在同一环节提供同类能力、导致产物被重复处理或处理顺序难以判断的情形。

- 表现：同一份样式被压缩两次，或前缀被重复补全产生冗余声明。
- 成因：按零散示例逐个拼接插件，未清点每个插件的职责边界。
- 排查方式：按管道顺序列出每个环节的输入与输出，标出重复的职责。
- 处理方式：同类能力只保留一个，或明确划分各自负责的文件范围。
- 隐性重叠：编译插件自带的压缩能力与独立压缩插件通常只保留其一。

```text
读取源文件
  → 编译（预处理语法到标准语法）
  → 转换（语法降级与兼容处理）
  → 合并（多文件到单文件）
  → 压缩（去空白与混淆）
  → 写出产物
```

> 按环节排列职责，重复的环节一眼可见，这比逐个核对插件文档更快。

**速记**：同一环节只留一个插件，按输入输出清点职责即可发现重叠。



#### 关注维护状态与替代方案

**维护状态**：是插件最近发布时间、问题响应情况与所声明支持的 Gulp 主版本的总体状况，决定流水线能否长期运行。

- 判断信号：长期没有发布、问题长期无人回应、声明支持的版本明显落后。
- 替代路径：选用仍在维护的同类插件，或改为用核心 API 实现。
- 集中风险：把维护停滞的插件留在关键路径上，会在环境升级时集中暴露。
- 迁移成本：尽早替换的成本远低于流水线停摆后再被动处理。
- 核对方式：安装前在注册表页面确认包名、最近发布时间与依赖声明。

```bash
npm outdated
# 列出流水线内插件的当前版本与最新版本
npm view 样式编译插件 time.modified
# 查看该插件最近一次发布时间
```

> [!NOTE]
> **提醒内容**：名称相似、功能相近的包很多，安装前需在注册表确认包名与发布时间，避免引入同名或已停止维护的包。

**速记**：选插件先看维护状态，信号是最近发布、问题响应与声明支持的版本。
