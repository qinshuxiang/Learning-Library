## Vite 开发服务器与环境变量

**开发服务器（dev server）**：是 Vite 在开发期启动的本地服务进程，负责按需转换模块、推送热更新，并为前后端联调提供代理。

前两篇解决了「怎么启动」与「怎么配置」，本篇聚焦开发期的运行时能力：热模块替换、环境变量、模式、接口代理与依赖预构建。生产构建与产物优化详见本主题第 7 篇 Vite 构建与产物优化。

### 开发服务器与热模块替换

本节说明开发服务器的可控项，以及热模块替换的工作方式与失效判定。

#### 开发服务器的启动与配置

**开发服务器**：是 Vite 在开发期启动的本地 HTTP 服务，负责按需转换模块并通过 WebSocket 推送更新。

- 启动：执行 vite 或脚本 dev，默认监听 5173 端口。
- server.port：指定端口；server.strictPort 为 true 时端口占用直接报错而不顺延。
- server.host：设为 true 或 0.0.0.0 时可被局域网访问，默认仅本机。
- server.open：设为 true 时启动后自动打开浏览器。
- server.https：传入 true 或证书配置即可启用 HTTPS。

```ts
// vite.config.ts
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    port: 5173,
    strictPort: true,
    host: true,
    open: true,
  },
});
```

```bash
npm run dev
# VITE v7.0.0  ready in 305 ms
# Local:   http://localhost:5173/
# Network: http://192.168.1.20:5173/
```

> [!WARNING]
> **警告内容**：server.host 设为 true 后开发服务器对同网络设备开放，源码与本地接口都可能被访问，共享网络环境中应先确认访问范围是否可控。

**速记**：server.port 与 server.host 控制监听范围，strictPort 禁止端口顺延。



#### 热模块替换的原理

**热模块替换（hot module replacement，HMR）**：是开发期在不整页刷新的前提下替换模块的机制，Vite 通过 WebSocket 把更新推送给浏览器。

- 通道：客户端注入的脚本与开发服务器维持一条 WebSocket 连接。
- 触发：文件保存后服务器判断受影响的模块，向客户端发送更新消息。
- 边界：模块需声明 HMR 边界，否则更新向上冒泡到入口并退化为整页刷新。
- 框架支持：Vue、React 等插件已内置边界处理，业务代码多数无需手写。

```js
// 手动声明 HMR 边界的写法
export function renderCounter(count) {
  document.querySelector("#count").textContent = String(count);
}

if (import.meta.hot) {
  import.meta.hot.accept();
  import.meta.hot.dispose(() => {
    document.querySelector("#count").replaceChildren();
  });
}
```

> 热更新只替换模块，不重建整个应用；模块级副作用需要在 dispose 回调中主动清理。

**速记**：HMR 走 WebSocket 推送，模块不声明边界就退化为整页刷新。



#### HMR 边界与常见失效

**HMR 失效**：是改动后浏览器整页刷新或状态丢失的现象，成因通常是模块未被插件接管或依赖了不可热替换的资源。

- 语法错误：模块解析失败时回退为整页刷新，控制台打印错误堆栈。
- 非模块资源：改动 CSS 走样式替换，改动环境变量文件则触发服务器重启。
- 状态丢失：模块未声明 accept 时更新冒泡到入口，应用状态被重置。
- 排查路径：观察终端打印 hmr update 还是 page reload，据此判断是否走了热更新通道。

```bash
# 触发热更新时的终端输出
# 3:12:04 PM [vite] (client) hmr update /src/components/Counter.vue

# 回退为整页刷新时的输出
# 3:12:41 PM [vite] (client) page reload src/main.js
```

> 修改 vite.config.ts 或 .env 文件会触发开发服务器整体重启，不属于热更新失效，重启后页面仍需重新加载。

**速记**：看终端输出区分 hmr update 与 page reload，前者才是热更新。



### 环境变量与 .env 文件

本节说明环境变量文件如何被加载，以及哪些变量会进入客户端代码。

#### .env 文件族与加载顺序

**.env 文件族**：是 Vite 按约定命名的环境变量文件集合，按优先级从低到高依次加载并合并。

- .env：所有模式都会加载的基础变量。
- .env.local：所有模式加载，用于本地覆盖，通常不提交版本库。
- .env.[mode]：仅指定模式加载，如 .env.production。
- .env.[mode].local：指定模式的本地覆盖，优先级最高。

```bash
.env                    # 基础变量
.env.local              # 本地覆盖，不入库
.env.production         # 生产模式
.env.production.local   # 生产模式的本地覆盖
```

> 合并时高优先级文件覆盖低优先级的同名键，不同文件之间不会互相追加内容。

**速记**：优先级从 .env 到 .env.[mode].local 递增，local 文件通常不入库。



#### VITE_ 前缀的安全约束

**VITE_ 前缀**：是 Vite 用来标记「允许暴露给客户端」的变量命名约定，只有带该前缀的变量才会注入前端代码。

- 暴露机制：前缀变量在构建期被静态替换进产物，属于明文可见。
- 未加前缀：普通变量只对配置文件与构建脚本可见，不进入客户端代码。
- 安全边界：任何密钥、令牌、私有地址都不能放进前缀变量。
- 服务端取值：需要保密的数据由后端服务持有，经接口鉴权后下发。

```bash
# .env
VITE_API_BASE_URL=/api
DB_PASSWORD=not-for-client
```

```js
console.log(import.meta.env.VITE_API_BASE_URL); // "/api"
console.log(import.meta.env.DB_PASSWORD);       // undefined
```

> [!IMPORTANT]
> **重要内容**：VITE_ 前缀变量会被写入最终产物，浏览器用户可完整读取；密钥与内部地址必须留在服务端，由接口鉴权后下发。

**速记**：只有 VITE_ 前缀进客户端，前缀变量一律按公开信息对待。



#### 在配置文件中读取环境变量

**loadEnv**：是 Vite 导出的函数，用于在配置文件中读取 .env 文件，签名为 loadEnv(mode, envDir, prefixes)。

- 参数：mode 指当前模式，envDir 指 .env 文件所在目录，prefixes 指要保留的变量前缀。
- 前缀为空：传入空字符串会加载全部变量，需自行控制后续的使用范围。
- 用途：把变量注入 define，或写入 server.proxy 的 target。
- 注意：配置文件中的变量不会自动进入客户端，仍需 VITE_ 前缀。

```ts
import { defineConfig, loadEnv } from "vite";

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), "");

  return {
    server: {
      proxy: {
        "/api": { target: env.API_TARGET, changeOrigin: true },
      },
    },
  };
});
```

> loadEnv 读取到的变量只用于配置计算，不会自动成为 import.meta.env 的成员。

**速记**：loadEnv 按模式读 .env 供配置使用，前缀参数决定读取范围。



### import.meta.env 与模式

本节说明客户端可用的环境变量对象、类型声明方式，以及模式与 NODE_ENV 的区别。

#### import.meta.env 的内置字段

**import.meta.env**：是 Vite 在客户端代码中注入的环境变量对象，包含若干内置字段与自定义前缀变量。

- MODE：当前模式字符串，开发期为 development，构建期为 production。
- BASE_URL：应用部署的基础路径，对应 base 配置。
- DEV：布尔值，开发期为 true。
- PROD：布尔值，生产构建为 true。
- SSR：布尔值，服务端渲染环境下为 true。

```js
console.log(import.meta.env.MODE);      // "development"
console.log(import.meta.env.DEV);       // true
console.log(import.meta.env.BASE_URL);  // "/"
```

> DEV 与 PROD 是互斥的两个布尔值，用它们判断环境比直接比较 MODE 更稳妥。

**速记**：import.meta.env 内置 MODE、BASE_URL、DEV、PROD、SSR 五个字段。



#### 自定义变量与类型提示

**自定义变量类型提示**：是在类型脚本项目中为 import.meta.env 补充声明，否则访问自定义变量会被判定为类型错误。

- 声明文件：在 src 下新建 vite-env.d.ts，脚手架通常已生成。
- 写法：扩展 ImportMetaEnv 接口，把字段类型声明为 string。
- 约束：声明的键名要与 .env 中的键名严格一致。
- 生效：改动声明文件后，编辑器需重新加载类型信息。

```ts
// src/vite-env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_BASE_URL: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

> [!TIP]
> **建议内容**：把自定义变量集中在一个声明文件里维护，并在变量增删时同步更新，可把拼写错误提前暴露在编译阶段。

**速记**：自定义变量要在 vite-env.d.ts 里补 ImportMetaEnv 声明。



#### 模式与生产开发区分

**模式（mode）**：是 Vite 用来选择 .env 文件与配置分支的字符串标识，与打包器内部的 NODE_ENV 不是同一件事。

- 默认值：开发命令默认 development，构建命令默认 production。
- 指定方式：命令行 --mode staging，或在配置函数中使用 mode 参数。
- 与 NODE_ENV 的关系：Vite 按模式给 process.env.NODE_ENV 赋默认值，两者可分别读取。
- 用途：预发、灰度等环境通过自定义模式区分变量与接口地址。

```bash
npx vite --mode staging
npx vite build --mode staging
# 两个命令都会加载 .env.staging
```

> 模式只影响变量与配置分支，不改变构建行为；产物是否压缩由构建配置决定。

**速记**：mode 选 .env 文件，NODE_ENV 供依赖判断，两者用途不同。



### 代理配置 server.proxy

本节解决开发期前后端分离带来的跨域问题，并给出代理的完整配置形态。

#### 代理的作用与跨域

**server.proxy**：是开发服务器把匹配到的请求转发到目标服务器的配置，用于绕开浏览器的同源策略。

- 同源策略：浏览器限制页面脚本请求不同源的接口，开发期前后端端口不同即会受限。
- 代理路径：浏览器请求开发服务器，由开发服务器在服务端转发，不受同源策略限制。
- 生产差异：生产环境的转发由网关或反向代理承担，开发代理不随产物部署。
- 前端写法：请求仍写同源路径，如 /api/users。

```js
fetch("/api/users")
  .then((response) => response.json())
  .then((users) => console.log(users.length));
```

> 代理解决的是开发期联调问题，跨域的根本方案仍由服务端设置响应头或同源部署解决。

**速记**：开发期代理靠服务器转发绕开同源策略，生产环境要另配网关。



#### 基础代理配置

**基础代理配置**：是 server.proxy 下按路径前缀定义的转发规则，键为匹配前缀，值为转发选项。

- target：目标服务器地址，如 http://localhost:8080。
- changeOrigin：为 true 时把请求头中的 Host 改写为目标地址，多数后端需要开启。
- rewrite：把匹配到的前缀改写为其他路径后再转发。
- secure：目标为 HTTPS 且证书自签名时设为 false。

```ts
// vite.config.ts
export default {
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true,
      },
    },
  },
};
```

> [!CAUTION]
> **注意内容**：代理只在开发服务器生效，构建产物不含转发规则；上线前必须确认网关已配置等价规则，否则接口会全部 404。

**速记**：proxy 的键是前缀，target 与 changeOrigin 是必配的两项。



#### 路径重写与多规则

**路径重写**：是通过 rewrite 字段在转发前修改请求路径，用于后端接口不带前缀的场景。

- 写法：rewrite 是接收 path 参数的函数，返回改写后的路径。
- 常用替换：path.replace(/^\/api/, "") 去掉前缀。
- 多规则：配置对象可写多个键，按最长匹配优先。
- 正则键：键可以写成正则表达式，用于匹配更复杂的路径形态。

```ts
export default {
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ""),
      },
      "/uploads": {
        target: "http://localhost:9000",
        changeOrigin: true,
      },
    },
  },
};
```

> 重写发生在转发之前，只在开发服务器一侧改写，浏览器地址栏不会发生变化。

**速记**：rewrite 在转发前改路径，多规则按最长前缀匹配。



### 依赖预构建

本节说明开发期为何要预构建依赖、缓存放在哪里，以及出现异常时如何配置与排查。

#### 依赖预构建的作用

**依赖预构建（dependency pre-bundling）**：是开发期启动时用 esbuild 把第三方依赖提前打包为单个模块的过程。

- 目的之一：把 CommonJS 依赖转换为 ES Module，使浏览器可以直接加载。
- 目的之二：把由大量小文件组成的包合并为一个文件，避免成百上千次请求。
- 执行工具：由 esbuild 完成，速度快于常规打包器。
- 执行时机：首次启动或依赖变化时执行，结果写入缓存供后续复用。

```bash
# 首次启动时的终端输出
# Pre-bundling dependencies:
#   vue
#   vue-router
# (this will be run only when your dependencies or config have changed)
```

> 预构建只针对依赖，业务源码不参与；业务源码始终由浏览器按模块加载。

**速记**：预构建把依赖转成 ESM 并合并文件，解决 CJS 与请求数量问题。



#### 缓存与重新预构建

**预构建缓存**：是依赖预构建结果在文件系统上的持久化存储，默认位于 node_modules/.vite 目录。

- 缓存目录：node_modules/.vite，删除后下次启动会重新预构建。
- 失效条件：锁文件、相关配置字段或依赖版本变化时缓存失效。
- 手动重建：执行 vite --force，或把 optimizeDeps.force 设为 true。
- 版本隔离：缓存按依赖哈希命名，不同浏览器目标不会混用。

```bash
rm -rf node_modules/.vite
npx vite --force
# 强制重新预构建依赖
```

> [!NOTE]
> **提醒内容**：排查依赖相关的异常报错时，先删除 node_modules/.vite 再启动，可排除缓存陈旧造成的影响。

**速记**：缓存放在 node_modules/.vite，改动依赖或配置后会重新预构建。



#### optimizeDeps 配置与排查

**optimizeDeps**：是控制依赖预构建行为的配置项，用于处理动态导入与本地链接包带来的识别问题。

- include：强制把某些依赖加入预构建，常见于只被动态导入引用的包。
- exclude：排除指定依赖，避免其被预构建。
- esbuildOptions：向底层 esbuild 透传选项，如 target。
- 常见报错：504 Outdated Optimize Dep 表示客户端引用了过期的预构建结果。

```ts
export default {
  optimizeDeps: {
    include: ["some-cjs-package"],
    exclude: ["linked-local-package"],
  },
};
```

```bash
# 终端出现下面这类报错时，重启开发服务器即可
# 504 (Outdated Optimize Dep)
```

> 工作区中的本地包若通过软链接引用，加入 exclude 并让其以源码形式参与转换，可避免预构建缓存导致改动不生效。

**速记**：include 补收录、exclude 排除，504 报错先重启服务器。
