## Rollup 库打包实践与包字段

库构建的终点是一组供其它项目导入的模块文件，而不是交给浏览器直接加载的页面。本篇从 Rollup 的输出配置出发，讲清产物目标、字段对应、依赖归属、格式取舍与发布收尾五件事；字段的通用语义见本主题第 2 篇 包管理与依赖治理，Vite 库模式下的同类做法见本主题第 30 篇 Vite 库模式与组件库发布。

### 库产物的目标

库产物不直接面向浏览器，它的第一读者是使用方的构建器。本节先列出消费方，再说明需求差异，最后交代产物契约的稳定性要求。

#### 谁在消费库产物

**库产物的消费方**：是最终加载该库的构建器或运行时，包括使用方的打包器、Node.js 运行时、浏览器与类型检查器四类。

- 使用方的打包器：读取包的入口字段解析到产物文件，再按自身规则做树摇与代码分割。
- Node.js 运行时：按包的模块类型与文件扩展名决定以 import 还是 require 加载产物。
- 浏览器：只在脚本标签直引或无构建步骤的场景下直接加载产物文件。
- 类型检查器：读取声明文件完成类型推断，与脚本产物分属两条独立链路。
- 文档与演示工具：按入口字段定位类型定义，据此生成提示与跳转。

```json
{
  "name": "date-kit",
  "version": "1.0.0",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/types/index.d.ts",
  "files": ["dist"]
}
```

> 四类消费方各取所需，任何一个入口字段写错都只会在对应那一类消费方处暴露，因此发布前需要逐类覆盖验证。

**速记**：库产物由使用方打包器、Node 运行时、浏览器与类型检查器四类角色消费，四类都要覆盖。



#### 不同消费方的需求差异

**需求差异**：是各消费方对模块格式、语法版本与产物结构提出的不同要求，直接决定要产出几份文件。

- 模块格式：打包器与较新的 Node 接受 ESM，旧工具链与部分 Node 场景要求 CJS。
- 语法版本：库通常保留较新语法，把降级交给使用方的构建链，避免重复转换。
- 产物结构：需要按模块逐个引用的场景要求保留源码结构，整体引用则只需单个入口文件。
- 体积侧重：库产物优先保证可分析性，压缩与去重交给使用方统一处理。
- 副作用标注：声明哪些文件不可被安全丢弃，让使用方的树摇能裁掉未用到的模块。

```js
// rollup.config.mjs 同一份源码按消费方产出两种格式
import { defineConfig } from "rollup";

export default defineConfig({
  input: "src/index.js",
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named", sourcemap: true },
  ],
});
```

> [!NOTE]
> **提醒内容**：库产物默认保持未压缩状态更利于使用方做树摇与调试，压缩只在面向脚本标签直引的场景才有必要。

**速记**：格式、语法、结构与副作用标注四项按消费方分别确定，产物份数由此推导。



#### 产物契约的稳定性

**产物契约**：是入口字段、产物路径与导出名三者共同构成的对外承诺，一旦发布即被使用方的导入语句依赖。

- 路径即承诺：产物换目录或改名属于破坏性变更，使用方的导入语句会直接失败。
- 导出名即承诺：导出的函数名与类型名被使用方按名引用，重命名需要同步升级主版本。
- 目录结构即承诺：保留模块结构发布时，子路径导入同样属于契约的一部分。
- 扩展点：新增导出与新增子路径导出属于向后兼容的扩展，可以放在次版本。
- 变更记录：契约变动写进变更日志，使用方据此判断是否需要改导入语句。

```bash
npm view date-kit exports --json
# 查看已发布版本的导出映射，与本次改动逐条比对
```

> [!WARNING]
> **警告内容**：把入口字段指向尚未产出的文件名，会让使用方在安装成功之后才于构建阶段报模块不存在，发布前必须实际安装一次并执行导入验证。

**速记**：入口字段、产物路径与导出名构成对外契约，破坏性改动只在主版本进行。



### 包字段设计

字段的作用是把产物接到使用方的解析流程上。字段的通用语义与依赖分类见本主题第 2 篇 包管理与依赖治理，本节只处理发布库时字段与产物的对应关系与写法。

#### 入口字段与产物的对应关系

**入口字段**：是 package.json 中把包名映射到具体产物文件的字段，每个字段服务一种加载场景。

- main：指向 CJS 入口，服务 require 场景与未识别条件导出的旧工具链。
- module：指向 ESM 入口，该字段不是标准字段，但被主流打包器读取以获取可树摇的产物。
- types：指向声明文件入口，与脚本入口分开维护，路径需与产物目录结构一致。
- browser：指向浏览器专用产物，只在浏览器与 Node 的行为需要分叉时提供。
- 对应原则：每个字段指向的文件都必须在构建产物中真实存在，产物改名时同步修改。

```json
{
  "name": "date-kit",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/types/index.d.ts",
  "sideEffects": false
}
```

> 路径一律以点斜杠开头写相对路径，省略前缀会被当作包名解析，报错信息指向一个并不存在的依赖。

**速记**：main 指 CJS、module 指 ESM、types 指声明，字段指向的文件必须真实存在。



#### 条件导出的写法与分支顺序

**条件导出（conditional exports）**：是 exports 字段中以条件名分支、按运行时环境返回不同产物的写法，条件顺序决定命中结果。

- 顺序敏感：条件自上而下求值，先命中的分支生效，类型条件必须排在最前。
- import 与 require：分别对应 ESM 与 CJS 加载，两者指向不同文件。
- types 条件：在每个分支内单独声明声明文件路径，保证两种格式都有类型可读。
- 子路径导出：为样式与深层模块额外声明键，键名即使用方书写的导入路径。
- 兜底分支：用 default 条件接住未识别的环境，避免解析直接失败。

```json
{
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.mjs"
    },
    "./style.css": "./dist/style.css"
  }
}
```

> exports 字段存在时优先级高于 main 与 module，两处不一致会让不同工具解析到不同文件，出现难以复现的行为差异。

**速记**：条件自上而下命中，types 排在最前，import 与 require 分流，子路径单独声明。



#### 字段与产物的核对方法

**字段核对**：是在发布前把 package.json 中的每条路径与产物目录逐一对上、确认没有悬空指向的检查动作。

- 文件存在性：把字段里的路径逐个与产物目录比对，确认每个文件都已生成。
- 本地导入验证：用链接安装或本地路径安装的方式，在临时项目中实际导入一次。
- 两种加载方式：ESM 用 import 验证、CJS 用 require 验证，两条路径都要走通。
- 类型可用性：在临时项目中确认编辑器能读到类型，而不是把整个包退化为任意值。
- 打包预览：用打包预览命令查看待发布文件清单，确认字段指向的文件在其中。

```bash
npm pack --dry-run
# 输出待发布的文件清单，逐条核对字段指向
node --input-type=module -e "import('date-kit').then((m) => console.log(Object.keys(m)))"
# 以 ESM 方式实际导入一次，确认导出项齐全
```

> 字段核对无法靠读配置完成，只有实际安装并导入一次，才能覆盖解析路径上的全部环节。

**速记**：路径存在性、两种加载方式与类型可用性三项都实测，字段核对才算完成。



### 同伴依赖与外部化

外部化决定哪些依赖不进产物，同伴依赖决定这些依赖由谁安装，两者必须成对配置才能成立。

#### 什么依赖应当外部化

**外部化（external）**：是把依赖保留为运行期导入、不并入产物的处理，判断依据是使用方是否已经持有该依赖。

- 框架与运行时：使用方必然安装，外置可避免出现两份实例。
- 版本敏感的库：需要与使用方保持一致版本时外置，由使用方决定具体版本。
- 体积可观的按需依赖：仅在特定功能中使用时外置，让使用方按需安装。
- 内部小工具：只在本库内使用且体积很小则不必外置，避免增加使用方的安装负担。
- 路径匹配：用函数形式按前缀判断，把作用域包及其子路径一次性全部外置。

```js
// rollup.config.mjs 用函数形式批量外置依赖
import { defineConfig } from "rollup";

export default defineConfig({
  input: "src/index.js",
  external: (id) => id === "vue" || id.startsWith("vue/") || id.startsWith("@my-scope/"),
  output: [{ file: "dist/index.mjs", format: "es", sourcemap: true }],
});
```

> 外部化是把依赖解析的责任交给使用方，产物里保留的导入语句必须在使用方的依赖树中可解析。

**速记**：使用方已持有或版本敏感的依赖一律外置，内部小工具留在产物内。



#### 同伴依赖的声明与版本范围

**同伴依赖（peer dependencies）**：是声明本包需要宿主项目提供哪些依赖与版本范围的字段，安装期由包管理器校验。

- 职责分离：外置的依赖必须同时写进同伴依赖，否则使用方不会被告知需要自行安装。
- 范围写法：给出经过验证的主版本范围，过宽会让未验证的版本进入使用方环境。
- 可选同伴：仅在部分功能中需要的依赖用可选标记声明，避免非必要项目被强制安装。
- 与普通依赖的区别：同伴依赖不随本包安装副本，普通依赖会在本包目录下再装一份。
- 冲突处理：版本范围不重叠时以调整宿主项目为准，不通过放宽范围掩盖问题。

```json
{
  "peerDependencies": {
    "vue": "^3.4.0"
  },
  "peerDependenciesMeta": {
    "vue": {
      "optional": false
    }
  }
}
```

> 同伴依赖写的是经过验证的范围，范围之外的版本可以正常安装但不保证行为正确，需要在变更日志中说明。

**速记**：外置的依赖必须同时声明为同伴依赖，范围按实际验证过的版本给出。



#### 双份实例的成因与规避

**双份实例**：是同一模块被两条解析路径各加载一份、导致模块级状态不共享的现象。

- 成因一：依赖未外置，产物内自带一份，使用方又安装了一份。
- 成因二：格式分流不当，使用方的不同依赖分别走 ESM 与 CJS 产物，加载到两个文件。
- 表现：单例状态被读写两处、标识比较失败、事件订阅与派发落在不同实例上。
- 检查方式：在产物中搜索该依赖的特征字符串，命中即说明它被打进了产物。
- 规避方式：外置加同伴依赖，并保持两种格式产物的行为一致。

```bash
grep -c "vue/dist" dist/index.mjs
# 结果为 0，说明框架未被整体打入产物
npm ls vue
# 确认依赖树中该框架只解析出一份
```

> [!CAUTION]
> **注意内容**：双份实例在开发环境往往表现正常，只在特定调用顺序下才暴露，接入前应在依赖树中确认只有一个版本。

**速记**：未外置与格式分流都会造成双份实例，外置加同伴依赖并核对依赖树可规避。



### 多格式产物的取舍

格式越多，覆盖的消费方越广，维护成本与产物总量也越高。本节给出三种格式的取舍依据与最终的决定路径。

#### 是否必须提供 CommonJS

**CommonJS 产物**：是使用 require 加载的模块格式，服务旧工具链与在 Node 环境中以 require 引入的场景。

- 需要提供的信号：使用方工具链不支持 ESM，或使用方在 Node 脚本中直接 require 本包。
- 可以不提供的信号：目标使用方均为现代打包器，且本包不在 Node 侧被 require。
- 维护代价：多一份产物需要同步维护，入口字段与条件分支也随之增加。
- 默认导出差异：CJS 产物中的默认导出被包在 default 属性下，解构写法与 ESM 不同。
- 过渡做法：在改为纯 ESM 发布前，保留一份 CJS 产物并附上废弃说明。

```json
{
  "exports": {
    ".": {
      "types": "./dist/types/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

> 双格式并存时同一模块在使用方的依赖树中可能被加载两次，判断是否保留 CJS 要连双份实例的风险一并考虑。

**速记**：使用方仍有 require 需求就保留 CJS，纯现代消费方可以只发 ESM。



#### 是否必须提供 UMD

**UMD 产物**：是同时支持模块加载、AMD 与全局变量挂载的格式，服务没有构建步骤的脚本标签直引场景。

- 需要提供的信号：文档需要在无构建步骤的页面中直接演示，或通过 CDN 直引分发。
- 可以不提供的信号：全部使用方都经过打包器或包管理器，此时候选格式只剩 ESM 与 CJS。
- 成本：全局格式无法被使用方细粒度裁剪，且需要额外维护全局变量名映射。
- 命名冲突：全局变量挂在页面全局对象上，与同名变量冲突时直接覆盖。
- 替代做法：演示页用单独构建的页面承载，主包不再发布全局格式。

```js
// rollup.config.mjs UMD 产物需要同时给出全局名与依赖的映射
import { defineConfig } from "rollup";

export default defineConfig({
  input: "src/index.js",
  external: ["vue"],
  output: {
    file: "dist/index.umd.js",
    format: "umd",
    name: "DateKit",
    globals: { vue: "Vue" },
    sourcemap: true,
  },
});
```

> [!IMPORTANT]
> **重要内容**：产出 UMD 或 IIFE 时 name 必须提供且为合法的全局变量名，被外置的每个依赖也必须给出全局名映射，缺失会让运行期取到未定义值。

**速记**：只有无构建步骤的直引场景才需要 UMD，产出时必须补齐全局名与依赖映射。



#### 格式组合的决定路径

**格式组合**：是最终发布的格式集合，按消费方清单推导，而不是按格式越多越好的直觉堆叠。

- 第一步：列出全部消费方，区分经打包器引入、Node 引入与脚本标签直引三类。
- 第二步：为经打包器引入的消费方产出 ESM，按需保留源码结构供逐模块引用。
- 第三步：存在 Node 侧 require 时补一份 CJS，两者用条件导出分流。
- 第四步：存在脚本标签直引时补一份 UMD，并准备全局名映射。
- 收尾：删除没有消费方对应的格式，减少产物总量与字段维护面。

```bash
npm run build
# dist/index.mjs      3.2 kB
# dist/index.cjs      3.4 kB
# 产物条数与消费方清单逐条对应，无多余格式
```

> 格式取舍的判据是消费方清单，缺少对应消费方的格式只会增加发布体积与长期维护成本。

**速记**：先列消费方再定格式，ESM 为基线，Node 侧补 CJS，直引场景补 UMD。



### 发布与版本管理

构建完成只完成一半，收尾一步是控制发布范围，并让版本号如实反映契约变动。

#### 发布文件范围的划定

**发布范围**：是 files 字段声明的随包发布路径集合，决定使用方最终下载到的内容。

- 白名单优先：用 files 显式列出产物目录，比忽略文件黑名单更不容易漏配。
- 目录范围：只需产物、声明与必要的样式文件，源码与构建配置不必进入包内。
- 必发文件：说明文件与授权文件始终随包发布，无需列入清单。
- 构建前置：发布前必须完成构建，用发布钩子或流水线保证产物先于打包动作生成。
- 本地预演：用打包预览命令检查待发布清单，确认没有多余文件与缺失文件。

```json
{
  "files": ["dist"],
  "scripts": {
    "build": "rollup -c",
    "prepublishOnly": "npm run build"
  }
}
```

> 发布钩子能挡住忘记构建的情况，但本地源码与产物的对应关系仍要靠打包预览逐条确认。

**速记**：files 用白名单只发产物与声明，发布前先构建再用打包预览核对清单。



#### 语义化版本的触发条件

**版本递增规则**：是把本次改动与契约变动对应到主、次、修订号三段的判断依据。

- 主版本：入口字段路径变更、导出名重命名、删除子路径导出、最低运行时要求提高。
- 次版本：新增导出、新增子路径导出、扩大同伴依赖的可选范围。
- 修订号：仅产物内部的实现调整，对外契约与运行行为均无变化。
- 预发布版本：正式发布前用于验证，排序低于同号正式版，不进入使用方的范围解析。
- 范围影响：使用方的范围符决定改动能被自动采纳到哪一段，跨主版本必然需要人工确认。

```bash
npm run build
npm version minor
# 本次新增了子路径导出，递增次版本
npm publish
```

> [!NOTE]
> **提醒内容**：只改构建配置而未改源码的版本也应如实递增，产物内容变化对使用方同样属于变更。

**速记**：契约破坏递增主版本，向后兼容的新增递增次版本，内部实现调整递增修订号。
