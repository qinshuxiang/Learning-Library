## 从 webpack 迁移到 Vite

### 迁移前的评估

本节先判断项目是否具备迁移条件，再列出必须改造的项，最后给出收益与成本的取舍依据。webpack 侧配置本身的写法见本主题第 8 至 10 篇与第 17 至 25 篇，本节只处理迁移视角下的清点与决策。

#### 代码与依赖的前提清点

**迁移前提清点**：是在改动任何配置前，对源码模块形态、依赖构成与框架版本做的一次系统性盘查，用于估算迁移工作量与风险。

- 模块形态：源码是否以 ES Module 编写，仍使用 require 与 module.exports 的文件需要先改造。
- 依赖构成：列出依赖树中只以 CommonJS 形态发布的包，它们是迁移后最可能报错的部分。
- 框架与插件：确认框架、路由、状态管理是否有对应的 Vite 插件，缺少插件的部分要单独评估。
- 产物消费方：产物被谁加载，浏览器、服务端或其他应用对格式与路径的约束要逐条记录。
- 环境相关代码：源码与构建脚本中所有读取 process.env 的位置，迁移时都要逐一改写。
- 构建脚本外延：持续集成命令、本地调试脚本与产物上传脚本是否绑定了 webpack 的命令行。

```bash
# 列出依赖树，识别仍以 CommonJS 形态发布的包
npm ls --all | head -n 40
# 扫描源码中的模块与全局变量用法
grep -rn "require(" src | head -n 20
grep -rn "process.env" src | head -n 20
```

> [!NOTE]
> **提醒内容**：清点阶段只做记录与归类，不改动代码；把改造点列成清单后，迁移进度与风险都可量化。

**速记**：先清点模块形态、CommonJS 依赖、框架插件与环境变量用法，再决定是否开工。



#### 必须改造的点

**必须改造点**：是迁移后无法保持原样、必须改写源码或配置的项，集中在模块引用方式、环境变量读取与资源引用三处。

- require 改写：源码中的 require 调用改为 import 语句，导出改为 export。
- 环境变量读取：process.env.XXX 改为 import.meta.env.VITE_XXX，键名补上前缀。
- 全局常量注入：原由 DefinePlugin 注入的常量，改用 Vite 的 define 配置或环境变量承载。
- 资源引用：以字符串路径拼接的资源地址改为 import 引入，交给构建期处理。
- 条件编译分支：依赖 process.env.NODE_ENV 的分支改写为 import.meta.env.MODE 或 DEV 与 PROD。
- 配置侧残留：原配置文件里只为打包器服务的字段，迁移后无对应项的要删除，避免留下误导。

```js
// 迁移前
const apiBase = process.env.API_BASE;
if (process.env.NODE_ENV === "production") {
  enableReport();
}
```

```js
// 迁移后
const apiBase = import.meta.env.VITE_API_BASE;
if (import.meta.env.PROD) {
  enableReport();
}
```

> 改造点清单越早定稿，越能避免迁移中途反复调整模块引用方式。

**速记**：模块引用、环境变量、全局常量与资源引用是四类必改项。



#### 迁移收益与成本判断

**收益成本判断**：是把迁移带来的开发期提速与改造投入放在一起比较，用于决定是否启动迁移以及投入多大幅度。

- 收益侧：开发服务器冷启动与热更新延迟下降，配置文件总量与插件数量减少。
- 成本侧：源码改写、依赖兼容处理、构建脚本与持续集成命令同步调整。
- 高风险项目：深度定制插件链、依赖大量加载器特有能力的项目改造成本高。
- 低风险项目：由标准框架脚手架搭建、配置只涉及别名与代理的项目改造量小。
- 决策依据：先改造一个独立子应用或分支做试点，用实际耗时校准预估。
- 时间安排：把迁移排在业务低峰期，避免与功能迭代同时进行。

> 迁移决策应基于一次真实试点的数据，而不是配置文件的相似度。

**速记**：收益在开发期速度与配置量，成本在源码与依赖改造，用试点数据校准。



### 配置项对照

本节把 webpack 中常见的配置职责映射到 Vite 的对应位置，只列出映射关系与改造点，两侧配置的完整写法见本主题既有篇目。

#### 入口与产物的映射

**入口与产物映射**：是把 webpack 的 entry 与 output 职责对应到 Vite 的根目录约定与 build.outDir 上。

- 入口：webpack 在 entry 中显式声明；Vite 默认以根目录下的 index.html 为入口，由 HTML 中的脚本标签驱动。
- 多入口：webpack 写多个 entry 键；Vite 用 build.rollupOptions.input 声明多个 HTML 入口。
- 产物目录：output.path 对应 build.outDir，两者默认值不同，需按部署约定显式设置。
- 文件名模板：output.filename 与 output.chunkFilename 对应 build.rollupOptions.output 下的入口与分块命名。
- 公共路径：output.publicPath 对应 base，取值形式与部署路径保持一致。
- 资源目录：output.assetModuleFilename 对应 build.assetsDir 与资源命名模板。

```ts
// vite.config.ts
import { defineConfig } from "vite";

export default defineConfig({
  base: "/app/",
  build: {
    outDir: "dist",
    rollupOptions: {
      input: {
        main: "index.html",
        admin: "admin.html",
      },
    },
  },
});
```

> [!IMPORTANT]
> **重要内容**：Vite 以 HTML 为入口，迁移时若原项目由 JavaScript 入口动态生成页面，需要先补齐 HTML 文件，否则构建找不到入口。

**速记**：入口从 entry 迁到 HTML 与 rollupOptions.input，产物目录对应 build.outDir，公共路径对应 base。



#### 别名与解析的映射

**别名与解析映射**：是把 webpack 的 resolve 配置对应到 Vite 的 resolve 配置，重点是别名写法与扩展名取舍的差异。

- 别名：resolve.alias 的职责不变，Vite 同样用 resolve.alias，推荐写成绝对路径。
- 扩展名：resolve.extensions 在 Vite 中已有默认覆盖，通常无需再显式声明。
- 目录入口：resolve.mainFields 在 Vite 中由依赖预构建与解析策略接管，多数情况不必手工配置。
- 条件导出：resolve 的 conditionNames 语义由 Vite 预设，改动前要确认影响范围。
- 导入后缀：Vite 不推断默认扩展名之外的写法，导入时按实际文件名书写更稳妥。
- 编辑器对齐：别名改动要同步到类型脚本的 paths，否则编辑器报错而构建通过。

```ts
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  resolve: {
    alias: {
      "@": fileURLToPath(new URL("./src", import.meta.url)),
    },
  },
});
```

> 别名写成绝对路径可避免工作目录不同导致解析结果不一致。

**速记**：resolve.alias 平移即可，扩展名与 mainFields 多交给默认策略，别名要与类型配置同步。



#### 开发服务器与代理的映射

**开发服务器映射**：是把 webpack 的 devServer 配置对应到 Vite 的 server 配置，字段名与语义接近但默认值不同。

- 静态目录：devServer.static 对应 server 的根目录与 publicDir 约定，公开资源默认放 public 目录。
- 端口与主机：devServer.port 与 devServer.host 对应 server.port 与 server.host，默认端口值不同。
- 代理：devServer.proxy 对应 server.proxy，转发选项与路径重写写法基本一致。
- 单页回退：historyApiFallback 由 Vite 开发服务器默认处理，无需单独开启。
- 热更新：devServer.hot 对应 Vite 默认开启的热更新，原字段可以直接删除。
- 目录列表与压缩：devServer 中面向产物服务的选项在 Vite 中无对应项，随配置一并清理。

```ts
export default {
  server: {
    host: "0.0.0.0",
    proxy: {
      "/api": {
        target: "http://api.internal.example",
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ""),
      },
    },
  },
};
```

> 开发服务器的转发规则不进入产物，迁移后要确认生产网关有等价配置。

**速记**：static、port、proxy 三项平移，单页回退与热更新由 Vite 默认承担。



### 环境变量的迁移

本节只讲从 process.env 迁移到 import.meta.env 的动作与规则差异，Vite 环境变量机制本身见本主题第 6 篇。

#### 读取方式的改写

**读取方式改写**：是把源码中 process.env.XXX 的取值位置替换为 import.meta.env.XXX，并确认替换发生在构建期。

- 逐处替换：按清点清单把每一处 process.env 改为 import.meta.env，不遗漏工具函数与常量文件。
- 配置脚本例外：配置文件与构建脚本仍可读取 process.env，因为它们在服务端环境执行。
- 动态取值失效：以变量名拼接的访问方式不会被静态替换，必须改成点号加固定属性名。
- 依赖内部：第三方包内部的 process.env.NODE_ENV 由构建期统一处理，业务代码不必改写。
- 兜底默认值：字段缺失时取到 undefined 且不报错，读取处要给出默认值。
- 一次性收敛：把取值集中到一个配置模块，避免迁移后散落各处难以维护。

```js
// 迁移前
const baseUrl = process.env.API_BASE || "/api";

// 迁移后：键名带前缀，取不到时给默认值
const baseUrl = import.meta.env.VITE_API_BASE || "/api";
```

> [!CAUTION]
> **注意内容**：import.meta.env 是构建期静态替换，写法必须是点号加固定属性名；方括号动态取键只会得到 undefined，且运行时不会报错。

**速记**：process.env 逐处改为 import.meta.env，必须用固定属性名，缺失值自行兜底。



#### 前缀与替换规则的差异

**前缀规则差异**：是两套体系暴露变量给客户端的判定方式不同，webpack 靠显式注入，Vite 靠命名前缀。

- 暴露条件：webpack 由 DefinePlugin 显式列出注入键；Vite 只暴露带 VITE_ 前缀的变量。
- 键名变化：迁移后原有键名要补 VITE_ 前缀，否则客户端取不到值。
- 注入形态：两者都在构建期做字面量替换，产物中为明文，安全性一致。
- 无法整体豁免：不能只改配置文件让旧键名自动生效，源码中的键名必须同步改。
- 服务端变量：不带前缀的变量仍可在配置文件中读取，用于计算代理地址等配置。
- 命名习惯：业务变量与公开变量前缀统一后，未加前缀即默认不公开，暴露范围更清晰。

```bash
# 迁移前的变量名
API_BASE=/api
# 迁移后同一变量补前缀
VITE_API_BASE=/api
```

> 前缀是暴露范围的开关，键名是否带前缀决定它能否进入客户端代码。

**速记**：webpack 靠显式注入、Vite 靠 VITE_ 前缀，迁移时必须同步改键名。



#### 类型声明与配置读取

**类型声明迁移**：是为 import.meta.env 的自定义字段补充声明，使迁移后的环境变量在类型脚本项目中可被识别。

- 声明位置：在源码目录下的 vite-env.d.ts 中扩展 ImportMetaEnv 接口。
- 字段迁移：把原环境变量的类型声明逐条搬过来，键名与 .env 文件严格一致。
- 全局清理：原通过全局声明注入的常量改为环境变量传递后，旧的全局声明要删除。
- 配置读取：配置函数中改用 loadEnv(mode, envDir, prefixes) 读取指定前缀的变量。
- 同步时机：字段增删时同步更新声明，让拼写错误在编译阶段暴露。
- 提交策略：声明文件与 .env 文件放在同一次提交，便于整体回滚。

```ts
// src/vite-env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_BASE: string;
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}
```

> [!TIP]
> **建议内容**：迁移时把环境变量声明与 .env 文件放在同一次提交里，回退时可以一起回滚，避免声明与变量脱节。

**速记**：在 vite-env.d.ts 里补 ImportMetaEnv，配置侧用 loadEnv 读取无前缀变量。



### 常见不兼容点

#### CommonJS 依赖的处理

**CommonJS 依赖**：是只以 require 与 module.exports 形式发布的包，迁移后需要预构建或构建期转换才能被浏览器加载。

- 自动转换：开发期由依赖预构建把 CommonJS 依赖转为 ESM，多数包无需额外处理。
- 生产构建：构建期由转换插件完成同样的工作，配置位于 build.commonjsOptions 等选项中。
- 命名导出：CommonJS 包转为 ESM 后，命名导出依赖静态分析，取不到时应改用默认导出再解构。
- 失效场景：动态 require 与运行时拼路径加载的模块无法被静态转换，需要改为显式导入。
- 加载顺序：少数依赖要求先初始化再使用，转换后初始化时机变化会暴露问题。
- 排查手段：按报错模块名定位其发布形态，再决定是否加入预构建白名单。

```ts
export default {
  optimizeDeps: {
    include: ["some-commonjs-package"],
  },
  build: {
    commonjsOptions: {
      include: [/node_modules/],
    },
  },
};
```

> 预构建与构建期转换只解决模块形态，无法处理依赖内部对 Node 运行环境的假设。

**速记**：CommonJS 依赖靠预构建与构建期转换，命名导出取不到时改默认导出。



#### Node 内置模块与全局变量

**Node 内置模块**：是仅在 Node 运行时提供的模块，浏览器环境不存在，迁移后会在解析阶段失败。

- 报错形态：构建阶段报模块无法解析，或运行阶段提示对应对象不存在。
- 前端侧处理：真正属于浏览器逻辑的代码不应引用内置模块，需要先拆分出服务端逻辑。
- 全局变量：Node 独有的全局对象在浏览器中不存在，引用它们的代码要在迁移时删除或替换。
- 环境判断保留：process 对象只用于判断环境的部分，可改为 import.meta.env 的内置字段。
- 服务端产物：确需在服务端运行的代码走服务端构建链路，不进入前端产物。
- 依赖连带：某些前端依赖间接引用了内置模块，需要替换该依赖或改用浏览器版本字段。

```js
// 迁移前的环境判断
const isDev = process.env.NODE_ENV !== "production";

// 迁移后改用内置字段
const isDev = import.meta.env.DEV;
```

> [!WARNING]
> **警告内容**：为让构建通过而给 Node 内置模块加浏览器端垫片，会把服务端逻辑打进前端产物，体积增大且容易在运行时出错，应优先拆分代码。

**速记**：Node 内置模块不能进入浏览器产物，环境判断改用 import.meta.env 的字段。



#### 资源与样式的处理差异

**资源处理差异**：是 webpack 依赖加载器与资源模块处理静态文件，Vite 用内置规则与导入语法处理，两者对引用方式的要求不同。

- 引用方式：Vite 要求通过 import 引入资源以获得处理后的地址，字符串拼接的路径不会被处理。
- 大资源外链：超过内联阈值的资源输出为独立文件，阈值由 build.assetsInlineLimit 控制。
- 样式导入：样式文件的导入语句保持 import 形式，处理链路从加载器改为预处理器与 PostCSS 配置。
- 公开资源：不经处理、直接拷贝的文件放 public 目录，以根路径引用。
- 类名模块：CSS 模块的开关从加载器选项改为文件后缀命名约定。
- 引用校验：迁移后逐一核对资源地址是否随内容变化，未变化说明未走构建期处理。

```css
/* 样式文件由构建期处理，作用域由文件命名约定决定 */
.card {
  color: #334155;
}
```

```js
import logoUrl from "./assets/logo.svg";
// 构建期返回处理后的资源地址
document.querySelector("#logo").src = logoUrl;
```

> 迁移资源引用时以 import 为准，字符串路径只适用于 public 目录下的文件。

**速记**：资源走 import 获取地址，公开文件放 public，样式链路改为预处理器与 PostCSS 配置。



### 分阶段迁移与回退

#### 并行运行与双构建

**并行运行**：是在迁移期间让旧构建与 Vite 两套链路同时存在，用同一份源码分别产出，便于逐项比对差异。

- 脚本并列：保留原构建脚本，新增 Vite 的启动与构建脚本，两者互不覆盖。
- 依赖共存：两套工具链的依赖同时安装，注意配置文件名不冲突。
- 产物隔离：两套构建输出到不同目录，避免相互覆盖。
- 差异比对：以旧构建产物为基准，逐页比对渲染结果与接口行为。
- 配置拆分：公共变量与别名尽量由一份共享文件提供，减少两套配置的漂移。
- 清理时机：确认新链路稳定后，再删除旧配置与旧依赖。

```json
{
  "scripts": {
    "dev:legacy": "webpack serve",
    "dev:vite": "vite",
    "build:legacy": "webpack",
    "build:vite": "vite build"
  }
}
```

> [!NOTE]
> **提醒内容**：并行阶段两套构建的产物必须隔离目录，否则比对时无法判断差异来自构建器还是产物覆盖。

**速记**：两套脚本并存、产物分目录，以旧产物为基准逐页比对。



#### 按页面试点

**按页面试点**：是先迁移一部分页面或子应用到 Vite，其余页面继续走旧构建，缩小单次变更的影响面。

- 试点范围：选择依赖简单、改动可控的页面或独立子应用作为第一批。
- 路由衔接：同一应用内两种构建产物共存时，按路由或按子应用划分边界。
- 共享代码：公共模块在两套构建下都要能解析，路径别名与导入写法保持一致。
- 验证重点：优先验证环境变量、资源引用与第三方依赖三类高风险点。
- 推进节奏：每批试点通过后再扩大范围，每批都保留可回退的状态。
- 指标观察：记录试点页面的首屏耗时与错误率，与旧链路同页面对比。

#### 回退条件与收尾

**回退条件**：是触发退回旧构建链路的判定标准，需要在迁移开始前约定，避免问题出现时临时决策。

- 功能判据：出现功能不可用且短时间无法定位的问题即回退。
- 性能判据：开发期速度或产物体积明显劣于旧链路且无优化空间。
- 依赖判据：关键依赖与构建器不兼容且无替代方案。
- 回退动作：切换构建脚本指回旧链路，保留源码改动供后续修复。
- 演练要求：试点阶段至少演练一次回退，确认旧链路随时可用。
- 收尾清单：旧配置、旧依赖、旧脚本与相关说明一并清理，避免长期双轨。
