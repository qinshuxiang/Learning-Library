## 输出格式与产物形态

### 常见输出格式

本节按 format 的取值说明四种产出形态的代码特征与适用对象。

#### ESM 输出：保留模块语法的现代格式

**ESM 输出**：是 format 取 es 时产出的模块形态（ESM，即 ES Module，JavaScript 的官方模块规范），产物保留 import 与 export 语句，交由使用方或运行时解析。

- 语法保留：导入导出以语句形式写出，未被使用的导出可被使用方的打包器继续做树摇优化（tree shaking）。
- 依赖引用：外部依赖原样保留为导入语句，路径由使用方解析。
- 文件约定：扩展名用 .mjs，或在包字段中声明该文件按 ESM 解析。
- 产物结构：模块默认被提升到同一作用域，不额外包一层装载函数。
- 消费对象：现代打包器、支持 ESM 的运行时与浏览器模块脚本。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: { file: "dist/index.mjs", format: "es", sourcemap: true },
};
```

```text
产物内容示意
  import { ref } from "vue";
  function createStore(initial) { ... }
  export { createStore };
```

> ESM 是发布库时的首选格式，它把摇树与路径解析的决定权交回使用方，产物只承担模块声明的职责。

**速记**：ESM 产物保留导入导出语句，外部依赖留待使用方解析，是库发布的首选格式。



#### CommonJS 输出：改写导出表达式的兼容格式

**CommonJS 输出**：是 format 取 cjs 时产出的模块形态（CommonJS，以导出对象承载模块的规范），产物把导出改写为对导出对象的属性赋值，把依赖改写为 require 调用。

- 导出改写：导出语句转为对导出对象或模块导出对象的赋值，具体形态由 exports 字段控制。
- 依赖改写：外部依赖转为 require 调用，由运行时的模块解析机制查找。
- 文件约定：扩展名用 .cjs，避免在模块类型声明为模块的包中被当作 ESM 处理。
- 结构调整：导出对象可在运行期增减属性，使用方难以对其做静态摇树。
- 消费对象：旧版 Node、只识别 CommonJS 的工具与部分测试运行环境。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: { file: "dist/index.cjs", format: "cjs", exports: "named" },
};
```

```text
产物内容示意
  "use strict";
  var vue = require("vue");
  function createStore(initial) { ... }
  exports.createStore = createStore;
  Object.defineProperty(exports, "__esModule", { value: true });
```

> [!CAUTION]
> **注意内容**：CommonJS 产物的默认导出会落在导出对象的 default 属性上，使用方直接 require 得到的是对象而不是函数，取用方式须与导出字段的设置保持一致。

**速记**：CommonJS 产物把导入导出改写成 require 与属性赋值，兼容旧工具但不利于摇树。



#### UMD 与 IIFE：脚本直引的两种形态

**UMD**：是兼容 CommonJS、AMD 与全局变量三种装载方式的模块格式；**IIFE**：是立即执行函数表达式，包装后只向全局对象暴露一个变量。

- UMD 判定：产物首部检查当前环境具备哪种装载能力，据此选择挂载位置。
- IIFE 简化：不做环境判定，直接执行函数体并把导出挂到全局属性上。
- 全局命名：两种格式都需要 name 给出全局属性名，否则使用方没有稳定引用名。
- 依赖前提：外部依赖须已存在于页面，并通过 globals 映射为对应的全局变量名。
- 体积代价：两种格式都带装载样板代码，且无法被使用方进一步摇树。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: [
    { file: "dist/index.umd.js", format: "umd", name: "DataKit", globals: { vue: "Vue" } },
    { file: "dist/index.iife.js", format: "iife", name: "DataKit", globals: { vue: "Vue" } },
  ],
};
```

> [!NOTE]
> **提醒内容**：脚本直引格式的服务对象是没有打包器的页面，只有在消费方明确以脚本标签引入时，维护这一份产物才有收益。

**速记**：UMD 兼容多种装载方式、IIFE 只挂全局变量，两者都依赖 name 与 globals 才能被正确引用。



### 外部依赖与全局变量

本节说明外部依赖的声明写法、全局名映射的规则与外部化的判定边界。

#### external 的三种声明写法

**external**：是声明哪些模块不进入产物、保留为对外导入的输入侧字段，命中的标识符交给使用方或运行环境提供。

- 字符串写法：单个标识符精确匹配，适合依赖数量固定的场景。
- 数组写法：并列多个标识符，语义与逐条字符串写法一致。
- 函数写法：接收标识符与该标识符的引入方两个参数，返回布尔值决定是否外部化。
- 前缀判定：函数写法可对同一包的全部子路径按前缀统一处理，不必逐条枚举。
- 生效范围：external 位于配置顶层，对同一次构建下的所有输出统一生效。

```js
// 以函数写法把某个包及其全部子路径一次性外部化
export default {
  input: "src/index.ts",
  external: (id) => id === "vue" || id.startsWith("vue/"),
  output: { file: "dist/index.mjs", format: "es" },
};
```

> 外部化的对象是包标识符，相对路径模块属于产物内部结构，不应出现在 external 声明里。

**速记**：external 可用字符串、数组或函数声明，函数写法便于按前缀批量外部化子路径。



#### globals 与全局名映射规则

**globals**：是把外部依赖的标识符映射为页面全局变量名的输出字段，只在 UMD 与 IIFE 产物中生效。

- 键值对应：键为 external 中的标识符，值为该库在页面上的全局属性名。
- 必填条件：全局格式下的每一条外部依赖都必须有映射，缺一条就少一个取值表达式。
- 默认行为：未给映射时标识符本身被当作全局变量名取出，通常与页面实际挂载名不符。
- 子路径处理：按子路径引入的依赖需与函数式 external 配合，逐条补映射。
- 作用范围：ESM 与 CommonJS 产物忽略该字段，映射只对全局格式有意义。

```js
export default {
  input: "src/index.ts",
  external: ["vue", "vue-router"],
  output: {
    file: "dist/index.umd.js",
    format: "umd",
    name: "AdminKit",
    globals: { vue: "Vue", "vue-router": "VueRouter" },
  },
};
```

> [!IMPORTANT]
> **重要内容**：全局格式下遗漏 globals 映射不会导致构建失败，但产物会在运行期取到未定义值，构建成功与产物可用是两件事。

**速记**：globals 把外部标识符映射为页面全局名，只作用于 UMD 与 IIFE，缺映射会构建通过而运行报错。



#### 外部化的判定与常见边界

**外部化判定**：是判断某个依赖由产物自带还是由使用方提供的过程，判据是运行环境能否自行提供该模块。

- 应当外部化：框架与运行时、要求全局单实例的依赖、使用方已安装且体积较大的库。
- 不应外部化：仅本项目使用的工具函数与配置常量，这些应由产物自带。
- 类型导入：纯类型引用不产生运行期代码，不会进入依赖图，无需外部化。
- 声明来源：external 清单应与包字段中的同伴依赖（peer dependencies）保持一致，字段设计见第 43 篇。
- 风险两侧：外部化不足会把依赖副本打进产物，外部化过度会在运行期报模块缺失。

```text
判定路径
  依赖由使用方安装 → 列入 external，必要时补同伴依赖字段
  依赖属于本项目内部实现 → 保留在产物内
  仅类型引用 → 不作为运行期依赖处理
```

> 外部化没有统一清单，判断依据始终是该模块在运行期由谁提供。

**速记**：外部化按运行期由谁提供来判定，清单需与包字段一致，不足与过度都会出问题。



### 多产物输出

本节比较两种一次产出多份产物的组织方式，并说明命名规则与字段归属的处理。

#### 输出数组与配置数组两种组织

**多产物输出**：是在一次构建中产出多份不同格式产物的做法，可用输出数组或配置数组两种方式组织。

- 输出数组：单个配置对象的 output 写成数组，各元素共享同一次依赖图与插件执行。
- 配置数组：多个配置对象并列，各自独立完成解析与打包，互不共享分析结果。
- 复用程度：输出数组只分析一次依赖图，配置数组按元素重复分析。
- 使用时机：格式之间只差渲染结果时用输出数组，插件或入口本身不同时用配置数组。
- 顺序关系：两种方式的产物生成都按声明顺序执行，排查问题时可据此定位。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  plugins: [],
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named", sourcemap: true },
  ],
};
```

> 输出数组让多份产物共用同一份依赖图，是格式差异较小时的首选组织方式。

**速记**：格式只差渲染结果用输出数组复用依赖图，插件或入口不同才拆成配置数组。



#### 多格式产物的命名与区分

**产物命名**：是让不同格式与不同入口的产物在目录中可区分、可被包入口字段稳定指向的命名约定。

- 扩展名区分：.mjs 表示 ESM，.cjs 表示 CommonJS，.js 用于全局格式产物。
- 目录区分：也可按格式各占一个子目录存放，便于整体替换某一格式的产物。
- 命名模板：entryFileNames 控制入口产物名，chunkFileNames 控制分包名，assetFileNames 控制资源名。
- 字段对应：命名一旦确定，包的入口字段必须与产物路径逐字一致。
- 稳定性要求：命名模板不随构建机器与时间变化，才能保证引用长期有效。

```js
export default {
  input: "src/index.ts",
  output: {
    dir: "dist",
    format: "es",
    entryFileNames: "index.mjs",
    chunkFileNames: "chunks/[name]-[hash].mjs",
    assetFileNames: "assets/[name]-[hash][extname]",
  },
};
```

> [!TIP]
> **建议内容**：多格式产物的命名规则集中写在一处生成，避免各输出元素各写一套、日后改扩展名时漏改。

**速记**：用扩展名或目录区分格式，命名模板集中定义并与包入口字段逐字对齐。



#### 输出选项的共享与差异

**输出选项**：是 output 中控制渲染结果与落点的字段集合，多产物时须分清哪些由各输出共享、哪些必须逐份声明。

- 顶层共享：input、external、plugins 位于配置顶层，被同一次构建的所有输出共用。
- 逐份声明：format 与 file 或 dir 属于 output，每份产物各自给出。
- 按份设置：sourcemap 可为不同产物分别取值，例如仅给发布产物生成映射文件。
- 格式专属：name、globals、exports 只在对应格式下有语义，写成共享字段会造成理解混乱。
- 常见错误：把 output 专属字段写到配置顶层，构建会提示未知选项。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  plugins: [],
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named", sourcemap: true },
    { file: "dist/index.umd.js", format: "umd", name: "DataKit", globals: { vue: "Vue" } },
  ],
};
```

> 分辨字段归属是多产物配置不出错的前提：输入侧字段写顶层，输出侧字段写 output 内的各元素。

**速记**：输入侧字段在顶层共享，format、落点与格式专属字段必须逐份写进 output。



### 产物目录与命名

本节说明产物目录的组织方式、内容哈希（content hash）的取舍与构建前的清理处理。

#### 产物目录的组织方式

**产物目录**：是构建结果的落点与内部结构，决定包入口字段的书写方式与发布内容的范围。

- 单一目录：全部产物放入一个目录，靠扩展名区分格式，结构最简。
- 分格式目录：按格式各占一个子目录，便于整体替换某一格式的产物。
- 与源码分离：产物目录与源码目录分开，产物目录不纳入版本控制。
- 路径基准：目录结构就是包入口字段里相对路径的书写依据，两者必须同步。
- 发布范围：发布时只带产物目录与必要的说明文件，不带源码与配置。

```text
产物目录示意
  dist/
    index.mjs
    index.cjs
    index.umd.js
    index.d.ts
```

> 目录结构在首次发布后即成为对外契约，调整目录需同步修改包入口字段，属于破坏性变更。

**速记**：单目录靠扩展名区分、分格式用子目录隔离，目录结构须与包入口字段同步。



#### 内容哈希与库产物的取舍

**内容哈希**：是把产物内容的摘要写进文件名的做法，内容变化时文件名随之变化，用于驱动缓存失效。

- 模板占位：命名模板中以哈希占位符引入，取值来自产物内容，而非构建时间。
- 生效场景：面向浏览器的产物与长期缓存的静态资源收益最明显。
- 库产物取舍：发布到包管理器的库通常不加哈希，稳定文件名便于包字段固定引用。
- 映射文件：开启哈希后映射文件名也需带哈希，或改为外部映射注记的方式引用。
- 多格式一致：希望多格式共用同一哈希时，需确认各格式内容确实相同，否则会相互污染缓存。

```js
export default {
  input: "src/app.ts",
  output: {
    dir: "build",
    format: "es",
    entryFileNames: "assets/[name]-[hash].mjs",
    assetFileNames: "assets/[name]-[hash][extname]",
  },
};
```

> [!WARNING]
> **警告内容**：库产物一旦加入内容哈希，包入口字段就无法写死路径，安装方也无法稳定引用，名称稳定与缓存失效只能二选一。

**速记**：内容哈希服务于缓存失效，应用产物受益、库产物受损，二者不可兼得。



#### 产物清理与写入行为

**产物清理**：是在构建前移除上一轮产物、避免旧文件混入发布内容的处理步骤。

- 写入语义：构建写入同名文件会直接覆盖，但已不再产出的旧文件不会被删除。
- 残留风险：改动命名模板或入口后，旧文件留在目录中，可能被一并发布出去。
- 清理方式：常见做法是构建前删除整个产物目录，或由清理插件在构建开始时执行。
- 范围限定：清理范围必须限定在产物目录内，不得扩展到源码目录与配置目录。
- 结果核对：构建后核对产物清单，确认文件集合与命名模板的预期一致。

```bash
# 先清空产物目录再执行构建，避免旧文件残留
rm -rf dist && rollup -c
```

```json
{
  "scripts": {
    "build": "rm -rf dist && rollup -c"
  }
}
```

> [!CAUTION]
> **注意内容**：清理命令的路径一旦写错指向源码目录，会直接删除源文件，执行前须确认路径以产物目录为唯一目标。

**速记**：构建只覆盖同名文件、不删旧文件，清理须限定在产物目录内并在构建前执行。



### 格式选择的实践建议

本节按消费方类型给出格式组合，并说明取舍原则与常见误区。

#### 面向包管理器的格式组合

**面向包管理器的格式组合**：是以被其他项目安装消费为目标时给出的格式集合，通常以 ESM 为主、CommonJS 为辅。

- 主格式：ESM 作为现代消费方的默认入口，保留可摇树的模块结构。
- 兼容格式：CommonJS 覆盖仍不识别 ESM 的消费方与运行时。
- 字段对应：包入口字段与两类产物一一对应，字段细节见第 43 篇。
- 声明文件：类型声明与产物并列落盘，路径按格式分别组织。
- 不必多给：消费方都经打包器处理时，额外的全局格式没有收益。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: [
    { file: "dist/index.mjs", format: "es", sourcemap: true },
    { file: "dist/index.cjs", format: "cjs", exports: "named", sourcemap: true },
  ],
};
```

> 格式集合由消费方的能力决定，不由构建工具的默认值决定。

**速记**：面向包管理器给 ESM 主格式加 CommonJS 兼容格式，并与包入口字段逐一对应。



#### 面向浏览器直引的格式补充

**浏览器直引**：是通过脚本标签等非打包方式直接引入产物的用法，要求产物自带装载能力。

- 格式选择：UMD 兼容多种装载环境，IIFE 更精简但只向全局对象暴露一个变量。
- 全局命名：用 name 指定固定属性名，供页面代码按名调用。
- 依赖前提：外部依赖须已在页面上以全局变量形式存在，并逐一给出 globals 映射。
- 压缩版本：直引产物通常额外给一份压缩版本，减小宿主页面的加载负担。
- 适用判断：只有在消费方明确不使用打包器时，才值得长期维护这一份产物。

```js
export default {
  input: "src/index.ts",
  external: ["vue"],
  output: {
    file: "dist/track.umd.js",
    format: "umd",
    name: "TrackSdk",
    globals: { vue: "Vue" },
  },
};
```

> 直引格式的服务对象是页面本身，与包管理器的消费方式可以并存，但两者的取舍依据不同。

**速记**：直引格式选 UMD 或 IIFE，需给出全局名与依赖映射，仅在消费方不用打包器时才维护。



#### 取舍原则与常见误区

**取舍原则**：是按消费方能力裁剪格式数量、不为不存在的使用场景预留产物的判断准则。

- 按消费方裁剪：先列清有哪几类使用方，再据此决定格式，不做无对象的预留。
- 成本核算：每多一种格式就多一份产物、一组命名与一处包字段需要维护。
- 来源一致：多份产物应来自同一份源码与同一组插件，避免格式之间行为漂移。
- 误区一：为兼容极少数场景长期保留全局格式，扩大维护面而收益有限。
- 误区二：把依赖未外部化当成格式问题排查，实际成因是 external 声明缺失。

```text
裁剪顺序
  列出使用方 → 对应选取格式 → 写出包入口字段 → 移除无使用方的格式
```

> [!TIP]
> **建议内容**：格式数量按当前使用方定，新增格式应有明确的引用方，否则会长期占用构建与核对成本。

**速记**：按使用方裁剪格式，多一种格式多一份维护成本，无对象的产物应当删除。
