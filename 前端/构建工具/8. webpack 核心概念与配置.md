## webpack 核心概念与配置

webpack 是 2012 年发布的前端模块打包器，用依赖图把入口与它引用的一切模块聚合为产物。本篇只讲 webpack 与 Vite 机制不同的部分：入口与输出怎么写、loader 与 plugin 各自扮演什么角色、mode 与配置文件如何组织、开发服务器与热更新怎么开。通用概念不重讲，loader 与 plugin 的具体清单详见本主题第 9 篇 webpack loader 与 plugin。

### 为什么仍有 webpack

webpack 与 Vite 的开发期路线不同，由此带来不同的适用面。

#### 开发期机制差异

**开发期机制差异**：是 webpack 与 Vite 最根本的分野。Vite 在开发期把源码作为原生 ESM 交给浏览器按需请求，webpack 在开发期也要先构建出可运行的产物或内存中的依赖图。

- 请求粒度：Vite 按浏览器发起的模块请求即时转译单个文件，webpack 则以入口为起点一次性解析整张图。
- 启动成本：项目越大，webpack 首次构建越慢，Vite 的启动时间与项目规模关联更弱。
- 产物一致：webpack 的开发与生产流程共用同一套模块解析规则，两端的差异来源更集中。
- 缓存策略：webpack 的持久化缓存把构建结果落盘，二次启动可以复用（详见本主题第 10 篇 webpack 优化与分包实践）。

```bash
npx webpack --mode development
# asset main.js 42.6 KiB [emitted] (name: main)
# webpack 5.94.0 compiled successfully in 812 ms
```

> 两种路线的差别在构建期与开发期各占一半：Vite 把成本压在构建期，webpack 则在两端都要付出构建图的开销。

**速记**：Vite 开发期按请求即时转译，webpack 先构建整张依赖图再交付产物。



#### 生态与存量资产

**生态与存量资产**：是 webpack 至今仍在大量项目中使用的原因，围绕 loader 与 plugin 积累的处理能力覆盖了几乎全部资源类型。

- loader 数量：从 TypeScript、Sass 到 YAML、GraphQL，几乎所有文件类型都有现成 loader。
- plugin 能力：静态资源复制、环境变量注入、包体积分析等长期由 plugin 承担。
- 存量配置：企业项目里多年沉淀的 webpack.config.js 迁移成本高，稳定运行优先于更换工具。
- 文档与经验：遇到奇怪报错时，可检索的历史案例远多于新兴工具。

> [!NOTE]
> **提醒内容**：选择 webpack 常常是选择既有生态与团队经验，而不是认定它在机制上优于其他打包器；新项目应先评估迁移与维护成本。

**速记**：webpack 的优势来自 loader 与 plugin 的积累，以及存量配置与团队经验。



#### 能力边界与选型

**能力边界**：指 webpack 能直接覆盖而其他工具需要额外拼装的场景，这些场景是它仍然成立的现实理由。

- 多入口与多页面：原生支持多入口构建与公共依赖提升，配置集中在 entry 与 output。
- 模块联邦：Module Federation 让多个独立构建在运行时互相引用模块，适合微前端拆分。
- 细粒度控制：loader 链与 plugin 钩子可介入解析、转换、生成、输出每个阶段。
- 选型建议：需要极致启动速度的常规应用优先 Vite，需要深度定制产物与运行时分发时评估 webpack。

```js
// webpack.config.js
const path = require("node:path");

module.exports = {
  entry: {
    main: "./src/main.js",
    dashboard: "./src/dashboard.js",
  },
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].[contenthash].js",
  },
};
```

> webpack 的可定制性同时意味着配置量更大：插件之间的顺序、loader 之间的配合都需要手工维护。

**速记**：多入口、模块联邦与全链路钩子是 webpack 的独有能力，代价是配置复杂度。



### entry 与 output

entry 声明依赖图的起点，output 决定产物的位置与命名，两者共同决定构建的骨架。

#### entry 的取值形式

**entry**：是 webpack 构建依赖图的起点，取值为字符串、数组、对象或返回前述取值的函数。

- 字符串：单入口写法，例如 "./src/index.js"，产物名取默认值 main。
- 数组：多个文件依次进入同一入口代码块，例如先加载垫片再加载业务代码。
- 对象：多入口写法，键为入口名并作为 [name] 占位符的取值。
- 函数：接收环境参数并动态返回入口配置，适合按命令切换入口。
- 描述对象：可写成 { import, dependOn, filename, runtime, layer }，用于声明入口之间的依赖与运行时分包。

```js
// webpack.config.js
module.exports = {
  entry: {
    polyfills: "./src/polyfills.js",
    app: {
      import: "./src/app.js",
      dependOn: "polyfills",
    },
  },
};
```

> 数组形式只是把多个文件拼进同一代码块，彼此之间仍是同一作用域下的顺序执行，不等价于多入口。

**速记**：entry 取字符串、数组、对象或函数，对象形式的键名会进入产物文件名。



#### output 的路径与文件名模板

**output**：是产物输出配置，其中 path 指定输出目录、filename 指定入口产物命名、chunkFilename 指定非入口代码块命名。

- path：输出目录，必须是绝对路径，惯例写成 path.resolve(__dirname, "dist")。
- filename：入口代码块命名模板，可取 [name]、[contenthash]、[id]、[fullhash]。
- chunkFilename：异步代码块命名模板，缺省时 Webpack 会给出默认命名。
- assetModuleFilename：静态资源输出模板，例如 "assets/[name].[contenthash][ext]"。
- clean：设为 true 时在构建前清空输出目录，替代早期的清理插件。
- publicPath：产物中资源引用的前缀，webpack 5 默认取 auto，按运行时位置自动推断。

```js
// webpack.config.js
const path = require("node:path");

module.exports = {
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "assets/js/[name].[contenthash:8].js",
    chunkFilename: "assets/js/[name].[contenthash:8].js",
    assetModuleFilename: "assets/media/[name].[contenthash:8][ext]",
    clean: true,
    publicPath: "/",
  },
};
```

> [!WARNING]
> **警告内容**：output.path 必须写成绝对路径，直接写相对路径会以配置错误中断构建，报 configuration.output.path must be an absolute path。

**速记**：path 必须绝对路径，filename 与 chunkFilename 用 [contenthash] 保证缓存失效。



#### 多入口与公共依赖

**多入口与公共依赖**：指对象形式的 entry 产出多个入口代码块，被多处引用的模块会被提升为共享代码块，避免重复打包。

- 共享判定：同一模块被两个以上入口引用时，可提升为独立代码块由入口共同加载。
- 运行时代码：每个入口默认各自带一份 webpack 运行时，可设 optimization.runtimeChunk 提取为公共文件。
- 命名冲突：入口键名重复或与输出模板冲突时构建报错，需保证键名唯一。
- 适用场景：多页面应用、后台与前台分开发布、渐进式迁移中的新旧入口并存。

```js
// webpack.config.js
module.exports = {
  entry: {
    web: "./src/web/index.js",
    admin: "./src/admin/index.js",
  },
  output: {
    filename: "[name].[contenthash:8].js",
  },
  optimization: {
    runtimeChunk: "single",
  },
};
```

> 多入口之间共享的第三方依赖不一定自动合并，具体切分策略由 splitChunks 决定（详见本主题第 10 篇 webpack 优化与分包实践）。

**速记**：对象 entry 产出多入口，公共模块可提升为共享块，运行时也可单独提取。



### loader 与 plugin 的角色

webpack 只认识 JavaScript，其余一切文件类型与构建动作都靠 loader 与 plugin 接入，二者分工明确。

#### loader 的职责

**loader**：是作用于单个文件的转换函数，接收文件内容并返回新的内容，webpack 把返回值当作模块继续解析。

- 作用粒度：一次只处理一个文件，不感知依赖图的整体结构。
- 配置位置：写在 module.rules 数组的每一项里，用 test 匹配文件、用 use 声明 loader 链。
- 链式调用：多个 loader 串联时按从右到左的顺序执行，前一个的输出交给后一个。
- 典型用途：把 TypeScript、Sass、图片等转成 webpack 能理解的 JS 或资源模块。

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ["style-loader", "css-loader"],
      },
    ],
  },
};
```

> loader 链的顺序决定结果：写反顺序通常会得到语法错误或意外产物，具体规则见本主题第 9 篇 webpack loader 与 plugin。

**速记**：loader 按文件工作，配置在 module.rules，链式执行方向是从右到左。



#### plugin 的职责

**plugin**：是注册到 webpack 编译流程上的对象，通过钩子在构建的各个阶段介入，可以改变产物、生成文件或收集统计。

- 作用粒度：面向整个编译过程，能访问依赖图、代码块与输出文件。
- 接入方式：plugin 在 plugins 数组中实例化，实例需实现 apply(compiler) 方法。
- 钩子体系：compiler 管整次构建，compilation 管单次编译，钩子分同步与异步两类。
- 典型用途：生成 HTML、抽取样式文件、注入环境变量、清理与复制目录。

```js
// webpack.config.js 片段
const HtmlWebpackPlugin = require("html-webpack-plugin");

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({ template: "./src/index.html" }),
  ],
};
```

> plugin 必须用 new 生成实例后放进 plugins 数组，直接把构造函数写进数组不会生效。

**速记**：plugin 面向整个编译过程，用钩子介入，需实例化后放入 plugins 数组。



#### 二者的边界与配合

**二者的边界**：是能力划分的判断依据，转换单个文件内容归 loader，影响构建流程与产物集合归 plugin。

- 转换型需求：语法降级、样式编译、资源编码等逐文件操作写成 loader。
- 流程型需求：产物生成、文件搬运、体积统计、变量注入写成 plugin。
- 协作方式：plugin 可以在编译过程中动态追加 loader 规则，实现按条件启用转换。
- 判断口诀：只关心「这个文件变成什么」用 loader，关心「这次构建产出什么」用 plugin。

> 少数功能两侧都有实现，例如样式处理既需要 loader 完成转换，也需要 plugin 完成文件抽取，选型时看是否要产出独立文件。

**速记**：逐文件转换用 loader，构建流程与产物集合用 plugin，两者常成对出现。



### mode 与配置文件

mode 决定 webpack 内置优化的开关组合，配置文件则把这些选项组织成可维护的形态。

#### mode 的取值与内置行为

**mode**：是构建模式开关，取值为 development、production、none，webpack 依此启用一组内置优化。

- production：开启代码压缩、作用域提升与摇树优化的相关配置，并注入 production 的环境判断。
- development：保留可读产物，启用便于调试的模块标识与较快的构建策略。
- none：关闭全部内置优化，产物完全由显式配置决定，适合排查配置本身的影响。
- 环境判断：production 会把 process.env.NODE_ENV 替换为 "production"，供运行时分支使用。

```js
// webpack.config.js
const webpack = require("webpack");

module.exports = {
  mode: "production",
  plugins: [
    new webpack.DefinePlugin({
      "process.env.API_BASE": JSON.stringify("https://api.example.com"),
    }),
  ],
};
```

> [!IMPORTANT]
> **重要内容**：mode 应显式声明。缺省时 webpack 会告警并回退到 production，容易让开发构建意外开启压缩而难以排查。

**速记**：mode 三选一并决定内置优化组合，production 会替换 NODE_ENV 为 production。



#### 配置文件的结构

**webpack.config.js**：是 webpack 的默认配置文件，导出配置对象、配置函数或配置数组，支持 CommonJS 与 ESM 两种书写形式。

- 对象导出：最简形式，适合配置固定的项目。
- 函数导出：接收 env 与 argv 参数，按命令与环境动态返回配置。
- 数组导出：一次构建多份配置，例如同项目输出浏览器与 Node 两套产物。
- 顶部字段：entry、output、module、plugins、resolve、optimization、devServer 是常用一级字段。
- 模块解析：resolve.extensions 声明省略扩展名的查找顺序，默认是 js、json、wasm。

```js
// webpack.config.js
const path = require("node:path");

module.exports = (env, argv) => ({
  mode: argv.mode || "development",
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "[name].[contenthash:8].js",
  },
  resolve: {
    extensions: [".js", ".jsx", ".json"],
    alias: {
      "@": path.resolve(__dirname, "src"),
    },
  },
});
```

> 用 ESM 书写时文件名需写成 webpack.config.mjs，或在 package.json 中声明 type 为 module。

**速记**：配置文件可导出对象、函数或数组，函数形式能拿到 env 与 argv。



#### 配置的环境区分与合并

**配置合并**：是把公共配置与环境专属配置拼装成完整配置的做法，webpack 官方推荐用 webpack-merge 的 merge 函数完成。

- 拆分方式：公共项放进 webpack.common.js，开发与生产各自维护增量文件。
- 合并语义：merge 对数组做拼接、对对象做深合并，plugin 数组会合并而不是覆盖。
- 命令选择：用 --config 指定文件，例如 webpack --config webpack.prod.js。
- 命令行覆盖：--mode 与 --env 传入的参数在配置函数中可读取，优先于文件内的固定值。

```js
// webpack.prod.js
const { merge } = require("webpack-merge");
const common = require("./webpack.common.js");

module.exports = merge(common, {
  mode: "production",
});
```

```bash
npx webpack --config webpack.prod.js
# asset assets/js/main.3f9c1ab2.js 86.4 KiB [emitted] [minimized]
```

> 手工做深合并容易漏掉数组字段，例如 plugins 被整体覆盖而丢失公共插件，这是配置拆分后最常见的故障。

**速记**：公共配置加环境增量用 webpack-merge 合并，数组字段会拼接而非覆盖。



### 开发服务器与热更新

webpack-dev-server 把构建结果放进内存并提供本地服务，热模块替换让改动在不刷新页面的前提下生效。

#### devServer 常用选项

**webpack-dev-server**：是 webpack 官方开发服务器，读取 devServer 字段，在内存中提供产物并支持模块热替换。

- static：声明静态文件目录，取值为目录路径或含 directory 的对象，替代早期的 contentBase。
- port 与 open：分别指定监听端口与是否自动打开浏览器。
- hot：设为 true 开启热模块替换，缺省即为 true。
- historyApiFallback：设为 true 时把找不到的路径回退到 index.html，供前端路由使用。
- client：控制浏览器端日志与错误覆盖层，例如 overlay 用来在页面上显示编译错误。

```js
// webpack.config.js 片段
module.exports = {
  devServer: {
    static: { directory: path.resolve(__dirname, "public") },
    port: 8080,
    open: true,
    hot: true,
    historyApiFallback: true,
    client: { overlay: true },
  },
};
```

```bash
npx webpack serve --config webpack.config.js
# <i> [webpack-dev-server] Project is running at http://localhost:8080/
# <i> [webpack-dev-server] compiled successfully
```

> 从 webpack-dev-server 4 起目录类选项统一收敛到 static，从 3 升级时需要改写旧字段。

**速记**：devServer 的 static、port、hot、historyApiFallback 是最常用字段，产物存放在内存中。



#### 代理转发配置

**devServer.proxy**：是把开发服务器的部分请求转发到后端服务的选项，取值为对象数组，用于绕开浏览器同源限制。

- context：匹配需要转发的路径前缀，取值为字符串或字符串数组。
- target：转发目标地址，例如 http://localhost:3000。
- changeOrigin：设为 true 时把请求头的 Host 改写为目标地址，虚拟主机部署时需要。
- pathRewrite：对转发路径做重写，例如去掉接口前缀。
- ws：设为 true 时同时代理 WebSocket 连接。

```js
// webpack.config.js 片段
module.exports = {
  devServer: {
    proxy: [
      {
        context: ["/api"],
        target: "http://localhost:3000",
        changeOrigin: true,
        pathRewrite: { "^/api": "" },
      },
    ],
  },
};
```

> [!NOTE]
> **提醒内容**：webpack-dev-server 3 的 proxy 是以路径为键的对象，4 与 5 改为数组并用 context 声明匹配，升级时需改写配置形态。

**速记**：proxy 用数组声明 context 与 target，changeOrigin 与 pathRewrite 解决跨域与路径差异。



#### 热模块替换的接入

**热模块替换（hot module replacement）**：是在页面不整体刷新的前提下替换被改动模块的机制，由 devServer 的 hot 选项开启。

- 自动注入：hot 为 true 时，热替换运行时被自动加入每个入口代码块。
- 样式资源：经 style-loader 处理的样式改动天然支持热替换，无需额外代码。
- JS 模块：需要在模块内调用 module.hot.accept 声明可接受的依赖与更新回调，否则会回退为整页刷新。
- 状态保留：热替换不重置应用状态，适合保持表单内容与滚动位置进行调试。

```js
// src/renderApp.js 的调用方
import renderApp from "./renderApp.js";

renderApp(document.getElementById("root"));

if (module.hot) {
  module.hot.accept("./renderApp.js", () => {
    renderApp(document.getElementById("root"));
  });
  console.log("accepting updates for renderApp"); // 更新时重新执行
}
```

> [!CAUTION]
> **注意内容**：devServer 与热替换只服务于开发期，其内存产物与运行时钩子不能直接用于生产部署，生产仍应交付 webpack 的构建产物。

**速记**：hot 开启后样式自动热替换，JS 需 module.hot.accept 声明接受范围，生产不引入。
