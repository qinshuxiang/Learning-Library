## Vite 依赖预构建与 optimizeDeps

**依赖预构建（dependency prebuild）**：是开发服务器启动后把依赖目录中的包提前转换成可被浏览器直接执行的 ESM 模块、并写入缓存目录的过程，由 optimizeDeps 系列配置项控制。

预构建的概览见本主题第 6 篇的开发服务器一节，本篇深入其机制：转换的目的与产物位置、入口扫描的范围与补齐方式、缓存失效的条件，以及链接依赖与 CommonJS 依赖两类高频问题的处置。

### 预构建的目的与产物

预构建要解决的是依赖数量带来的请求量问题与模块格式不被浏览器支持的问题，产物本身是纯缓存。

#### 为什么需要预构建

**依赖预构建**：是把依赖目录中的包打包成少量 ESM 文件并缓存起来的过程，用于降低开发期的请求数量并统一模块格式。

- 请求数量问题：浏览器按导入语句逐条请求模块，由数百个文件组成的依赖会产生同等数量的请求。
- 格式问题：CommonJS 与 UMD 格式的依赖无法在浏览器中原生执行，必须先转换成 ESM。
- 转换成本问题：把转换结果缓存成文件，避免每次请求都重新处理依赖源码。
- 处理范围：只处理依赖目录中的包，项目自身源码仍由开发服务器按需转换。
- 合并效果：同一依赖内部的多个文件被打包成一个模块，请求数量降到个位数。
- 阶段限定：预构建只服务开发期，生产构建走完整的打包流程，两者不共用产物。
- 触发时点：首次启动或缓存失效时执行，完成后才开始处理源码请求。

```bash
# 未预构建时，网络面板中来自同一个依赖的请求会有几十到上百条
# 预构建完成后，同一个依赖通常只剩一条请求
```

> 预构建不改变依赖的功能，只改变开发期依赖的交付形态，生产产物的体积与行为不受影响。

**速记**：预构建解决请求数量与模块格式两个问题，只作用于开发期。



#### 预构建产物落到哪里

**预构建产物**：是依赖被打包成 ESM 后写入缓存目录的文件，默认位于依赖目录下的 .vite/deps。

- 默认位置：项目根目录下依赖目录中的 .vite/deps 目录。
- 目录内容：每个依赖一个转换后的文件，另有一份描述文件记录本轮预构建的输入。
- 位置调整：cacheDir 配置项改变缓存根目录，预构建产物位于其下的 deps 子目录。
- 浏览器缓存：产物响应带长期缓存头与版本查询参数，版本变化时自动失效重新拉取。
- 可否删除：删除该目录不影响项目，下次启动会重新生成。
- 提交约定：该目录加入忽略清单，不提交到仓库。
- 结构差异：不同 Vite 主版本的缓存目录命名与内部结构可能变化，以实际输出为准。

```bash
ls node_modules/.vite/deps
# vue.js  vue.js.map  chunk-XXXX.js  _metadata.json
```

> [!TIP]
> **建议内容**：预构建产物是纯缓存，出现依赖相关的怪异报错时直接删除整个缓存目录并重启开发服务器，通常比逐项排查更快。

**速记**：产物默认在依赖目录的 .vite/deps 下，可删可重建，不提交到仓库。



#### 预构建与开发请求的关系

**路径重写**：是把源码中的裸包导入替换为指向预构建产物路径的过程，替换发生在开发服务器返回模块之前。

- 改写对象：导入说明符为裸包名时被替换为缓存文件路径。
- 请求命中：浏览器请求改写后的路径，直接读到缓存文件而不是依赖目录中的原始文件。
- 依赖内部引用：预构建时依赖之间的相互引用被打包进同一文件，不再各自产生请求。
- 共用产物：同一依赖被多个入口引用时共用同一份产物，避免出现两份实例。
- 观察方式：网络面板中来自依赖目录的请求数量是判断预构建是否生效的直接依据。
- 版本参数：改写后的路径带版本查询参数，缓存更新后参数随之变化。
- 开发者可见：改写结果可通过查看开发服务器返回的模块源码确认。

```text
源码    import { createApp } from "vue"
改写后  import { createApp } from "/node_modules/.vite/deps/vue.js?v=1a2b3c4d"
```

> 版本查询参数由预构建结果的摘要决定，删除缓存目录后重新生成会得到新的参数值。

**速记**：裸导入被改写成缓存文件路径并带版本参数，依赖内部引用被打包合并。



### 入口分析与扫描

预构建的第一步是找出本次需要转换哪些依赖，这一步依赖对源码导入语句的静态分析。

#### 自动扫描的入口范围

**入口扫描**：是从项目根目录的 HTML 文件出发、沿模块导入向下分析并收集裸包名的过程。

- 默认入口：项目根目录下的 HTML 文件是扫描起点，沿其中的模块脚本向下分析。
- 扫描对象：静态导入与可静态分析的动态导入都会被收录。
- 收录条件：导入说明符是裸包名时计入依赖清单，相对路径与绝对路径不计入。
- 扫描边界：只扫描应用源码，依赖目录内部不再单独扫描。
- 多页面：存在多个 HTML 页面时按实际请求的页面各自分析并补充依赖。
- 增量特点：开发服务器运行期间发现新依赖时会自动补充预构建并刷新页面。

```bash
# 启动日志中出现发现新依赖的提示，说明扫描补上了遗漏项
# newly discovered dependencies, restarting server and reloading page...
```

> 扫描的输入是源码文本而非运行结果，因此运行期才能确定的导入说明符无法被收录。

**速记**：扫描从 HTML 入口沿模块导入向下走，只收录裸包名。



#### 扫描遗漏与显式 include

**optimizeDeps.include**：是把指定包强制加入预构建清单的配置项，用于补齐静态分析无法发现的依赖。

- 遗漏原因：拼接而成的导入说明符无法静态分析，扫描器读不到变量部分对应的包。
- 补齐方式：把包名写入 include 数组。
- 配置取值：可以是包名数组，也可以是对象形式，具体格式以官方文档为准。
- 其他场景：只被插件转换后引入的依赖，或由全局变量拼出的依赖名。
- 判定依据：开发期报找不到模块、而该包确实已安装并声明时，优先怀疑扫描遗漏。
- 验证方式：查看启动日志列出的依赖清单是否包含该包。

```ts
import { defineConfig } from "vite";

export default defineConfig({
  optimizeDeps: {
    include: ["some-lib", "another-lib/deep/entry"],
  },
});
```

> [!IMPORTANT]
> **重要内容**：include 只把包加入预构建清单，不修正模块格式与版本问题，报错原因不在扫描环节时补它无用。

**速记**：扫描不到的动态导入在 include 里显式列出，包名与包内路径都可写。



#### exclude 的适用情形

**optimizeDeps.exclude**：是把指定包排除在预构建之外的配置项，被排除的包按原始文件结构提供给浏览器。

- 作用：保留依赖的原始文件结构，不再打包成单个文件。
- 适用一：包本身就是可被浏览器执行的 ESM，且内部文件数量很少。
- 适用二：包在开发期需要被单独更新，预构建缓存反而拖慢反馈。
- 适用三：预构建对该包直接报错，临时排除以判断问题是否出在预构建环节。
- 代价：被排除的包会产生较多请求，且不再享受依赖引用的合并。
- 冲突处理：同一包不应同时出现在包含与排除两个列表中，同时出现时的判定以官方文档为准。

```ts
export default {
  optimizeDeps: {
    exclude: ["local-debug-lib"],
  },
};
```

> exclude 更适合作为排查手段与特例开关，长期排除了本该预构建的依赖会明显增加开发期请求。

**速记**：exclude 保留原始结构、增加请求数，多用于排查与少量特例。



### 缓存与失效

预构建结果被持久化到缓存目录，是否复用由本轮输入摘要与缓存中记录的摘要比对决定。

#### 缓存的位置与内容

**缓存目录**：是存放预构建产物与描述文件的目录，默认位于依赖目录下的 .vite。

- 默认位置：依赖目录下的 .vite 目录，预构建产物位于其 deps 子目录。
- 描述文件：_metadata.json 记录本轮预构建的输入摘要与依赖清单。
- 摘要来源：锁文件、配置项、环境取值等共同参与计算。
- 内容范围：既有转换后的依赖文件，也有被拆分出的公共 chunk。
- 目录差异：工作区项目会把缓存放到工作区根目录，多个子项目共用。
- 大小影响：依赖越多缓存目录越大，必要时可整体删除重建。

```bash
ls node_modules/.vite
# deps  _metadata.json
cat node_modules/.vite/deps/_metadata.json | head -n 20
```

> 缓存目录是构建系统的内部状态，不做手工修改，也不提交到仓库。

**速记**：缓存落在 .vite 目录，由转换产物与描述文件两部分组成。



#### 缓存失效的条件

**缓存失效**：是输入摘要与缓存中记录的摘要不再一致、需要重新执行预构建的情形。

- 锁文件变化：依赖版本变化后摘要不再匹配，需要重新预构建。
- 配置变化：与预构建相关的配置项改动会让摘要变化。
- 依赖树结构变化：新增、删除或替换依赖都会触发重新预构建。
- 环境变化：影响配置解析结果的环境取值变化同样会触发。
- 失效表现：启动日志提示缓存失效并重新预构建，随后页面重新拉取依赖。
- 局部重建：新增单个依赖时通常只补齐该依赖，不必全部重建。

```text
锁文件摘要变化    -> 重新计算并重建
单个依赖新增      -> 只补齐该依赖
配置项变化        -> 重新计算并重建
```

> 缓存失效是正常机制，遇到改了配置却没生效时，先看启动日志是否提示重新预构建。

**速记**：锁文件、配置、依赖树三类输入任一变化都会让缓存失效。



#### 强制重新预构建

**强制重新预构建**：是忽略已有缓存、重新扫描并生成全部预构建产物的操作。

- 命令行方式：执行 vite 命令时附加 --force 参数。
- 配置方式：打开 optimizeDeps.force 或服务器侧的强制开关。
- 效果：忽略已有缓存，重新扫描并生成全部预构建产物。
- 适用时机：缓存处于异常状态，或怀疑缓存与依赖不一致时临时使用。
- 常规顺序：先删除缓存目录并重启，仍不正常再用强制参数。
- 长期代价：团队脚本中长期开启会每次启动都重建，明显拖慢启动速度。

```bash
npx vite --force
# 忽略现有缓存，重新执行依赖预构建
```

> [!CAUTION]
> **注意内容**：把强制重建写进日常开发脚本，会让每次启动都重新预构建全部依赖，启动耗时成倍增加，只在排查时开启。

**速记**：强制重建用命令行参数或配置开关，属临时手段，不进常规脚本。



### 常见预构建问题

预构建相关的问题往往报错指向依赖内部，而根因出在扫描、缓存或解析环节。

#### 新增依赖未生效

**新增依赖未生效**：是安装新包之后开发服务器仍未提供该依赖、导入时直接报找不到模块的现象。

- 现象：安装新包并写入导入语句后，开发服务器报找不到该模块。
- 成因：开发服务器运行期间新装的依赖可能尚未进入已完成的预构建结果。
- 常规处置：重启开发服务器，检测到新依赖后会自动补充预构建并刷新页面。
- 主动手段：把该依赖写入 optimizeDeps.include，避免依赖自动检测。
- 验证方式：查看启动日志是否列出该依赖已加入预构建清单。
- 相关清理：包管理器缓存与项目依赖目录不一致时，先重新安装再重启。

```bash
npm install some-lib
# 重启开发服务器，观察启动日志中的依赖清单
```

> 开发服务器运行中改动依赖树属于配置层面的变更，重启是最直接的处置方式。

**速记**：新依赖不生效先重启，仍不生效就写进 include。



#### 依赖出现多份副本

**多份副本**：是同一个依赖在运行期存在两个不同模块实例、导致单例状态不共享的现象。

- 现象：运行时报出需要同一个实例类的错误，或状态在两个副本之间不共享。
- 成因：一份来自预构建产物，另一份由源码路径直接引入。
- 典型来源：以本地链接方式引入的依赖、被解析到源码目录的包。
- 处置方式：把该包写入 optimizeDeps.include，使其统一走预构建产物。
- 核对方式：借助插件上下文在构建开始时打印某个导入的最终解析结果。
- 相关提示：日志中出现旧依赖缓存未清理的提示时，按提示重新构建。

```js
export function traceResolvePlugin(target) {
  return {
    name: "trace-resolve",
    async buildStart() {
      const resolved = await this.resolve(target, undefined);
      console.log(resolved && resolved.id);
    },
  };
}
```

> [!WARNING]
> **警告内容**：同一个依赖出现两份实例会让单例状态、响应式系统与全局注册表全部失效，排查时优先确认解析路径是否唯一。

**速记**：副本问题源于一份走预构建、一份走源码，统一用 include 收敛。



#### CommonJS 依赖报错

**CommonJS 依赖报错**：是预构建在处理以 CommonJS 或 UMD 组织、且引用关系无法静态分析的依赖时失败的现象。

- 现象：预构建阶段直接失败，报错指向某个依赖的内部文件。
- 成因一：依赖内部使用无法静态分析的动态引用，预构建无法确定要打包哪些文件。
- 成因二：依赖引用了浏览器不具备的运行时能力，例如内置模块。
- 处置顺序：先升级依赖到较新的版本，再考虑排除该依赖。
- 排除前提：被排除的包必须自身可被浏览器执行，否则需要引入插件接管转换。
- 读报错：预构建报错会列出失败文件与原始错误，先读原始错误再决定处置动作。

```bash
# 预构建失败时的报错大致形态
# Failed to resolve entry for package "some-cjs-lib"
# Pre-transform error: Could not resolve "./lib/legacy"
```

> 报错中的文件路径指向依赖内部时，问题通常在依赖自身的模块组织方式，而非项目配置。

**速记**：CommonJS 依赖报错先升级、再排除，排除后必须确认它可被浏览器执行。



### 链接依赖与 monorepo 场景

以本地链接方式引入的依赖不在依赖目录中真实存在，预构建对它们有单独一套处理规则。

#### 链接依赖不被预构建的原因

**链接依赖（linked dependency）**：是通过本地链接方式引入、不在依赖目录中真实存在的包，预构建默认不处理这类包。

- 默认行为：Vite 不预构建链接依赖，把它视为项目源码的一部分。
- 直接后果：其源码参与按需转换，它导入的第三方包可能与预构建结果形成两份副本。
- 日志提示：启动日志会提示某个链接依赖需要加入预构建清单。
- 处置方式：把该包名写入 optimizeDeps.include。
- 判定依据：解析结果是否位于依赖目录之外，与包的来源方式无关。
- 相关组织：工作区的整体组织方式见本主题第 14 篇，此处只处理它对预构建的影响。

```ts
export default {
  optimizeDeps: {
    include: ["@my-scope/ui"],
  },
};
```

> 链接依赖被当作源码处理是为了让本地改动即时生效，代价是依赖关系更复杂、副本风险更高。

**速记**：链接依赖默认走源码转换，需要时用 include 纳入预构建。



#### 本地包的预构建策略

**本地包的预构建策略**：是按本地包的改动频率决定是否纳入预构建的取舍，纳入则依赖关系稳定，不纳入则反馈更快。

- 策略一：不纳入，本地包改动立即生效，代价是副本风险与请求数量上升。
- 策略二：纳入，依赖关系稳定，代价是本地包改动后需等待重新预构建。
- 判断依据：该包是否被前端源码直接引用，是否依赖浏览器不兼容的模块格式。
- 配置写法：把本地包名逐个写进 optimizeDeps.include。
- 变动影响：被纳入的本地包源码变化会触发重新预构建，反馈比源码转换慢。
- 分类做法：改动频繁的包不纳入，作为稳定依赖的包纳入。

```text
改动频繁的本地包   不纳入预构建   反馈快，请求多
稳定的本地依赖包   纳入预构建     请求少，改动后需重建
```

> 取舍的核心是反馈速度与依赖关系稳定性的权衡，按包的改动频率分类即可，不必追求统一。

**速记**：本地包按改动频率取舍，稳定的纳入、频繁改的不纳入。



#### 工作区下的缓存共享

**缓存共享**：是工作区中多个子项目共用同一份预构建结果的做法，缓存被上提到工作区根目录存放。

- 缓存位置：预构建会向上查找工作区根目录，把缓存放在根目录的依赖目录下。
- 共享收益：多个子项目共用同一份预构建结果，减少重复转换与磁盘占用。
- 失效范围：根目录的锁文件或子项目配置变化都会影响缓存的判定。
- 冲突场景：不同子项目对同一依赖的预构建配置不一致时，缓存可能反复失效。
- 排查入口：缓存异常时先确认实际使用的缓存目录位置与描述文件内容。
- 作用边界：以上机制只作用于开发期的预构建，生产构建的产物与缓存无关。

```bash
# 在子项目中查看实际使用的缓存目录
ls ../../node_modules/.vite/deps | head
```

> [!NOTE]
> **提醒内容**：工作区下多个子项目共用缓存目录，任一子项目的依赖或配置变化都可能让其他子项目重新预构建，属正常现象。

**速记**：工作区把缓存上提到根目录共用，任一子项目变更都可能触发重建。
