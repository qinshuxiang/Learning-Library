## 构建工具简介与生态

### 什么是构建工具

构建工具处理的是「源码怎样变成产物」，而不是「代码实现什么功能」。本节先给出定义，再区分构建期与运行时，最后说明产物的形态。

#### 构建工具的定义

**构建工具（build tool）**：是一类把项目源码与静态资源按既定规则转换为可部署产物的程序，输入是开发者编写的源文件，输出是浏览器或运行时可直接消费的文件。

- 输入层：JavaScript 与 TypeScript 源文件、样式文件、图片、字体与第三方依赖。
- 处理层：解析语法、转换语法、合并模块、压缩体积、拆分产物、改写引用路径。
- 输出层：产物目录中的脚本、样式、静态资源与资源清单。
- 触发层：命令行一次性构建，或开发服务器常驻并按改动增量更新。
- 定位层：只负责从源码到产物的转换，不改变代码的业务语义。

```bash
npm run build
# 构建命令的产物示意
# index.html          0.46 kB
# assets/index.js   142.31 kB
# built in 1.24s
```

> 构建工具与框架处于不同层次：框架提供组件与状态模型等运行时能力，构建工具负责把框架代码转换为可执行产物。

**速记**：构建工具把源码与资源按规则转换为可部署产物，输入是源码，输出是产物目录。



#### 构建期与运行时的边界

**构建期（build time）**：是构建命令执行、源码被转换与优化的阶段；**运行时（runtime）**：是产物在浏览器或 Node.js 中实际执行的阶段。

- 构建期负责：语法降级、模块打包、资源处理、体积优化与环境常量注入。
- 运行时负责：执行逻辑、处理交互、发起网络请求与读写存储。
- 边界举例：环境常量在构建期被替换为字面量，运行时读到的已是替换后的值。
- 判断依据：构建命令只跑一次，运行时在每次访问页面时都会发生。

```js
// 源码中的写法
const apiBase = import.meta.env.VITE_API_BASE;
```

```js
// 产物中的写法：常量已在构建期被替换为字面量
const apiBase = "https://api.example.com";
```

> 构建期的错误出现在构建命令的输出里，运行时的错误出现在浏览器控制台，排查位置完全不同。

> [!WARNING]
> **警告内容**：把只有运行时才能确定的值当作构建期常量使用，产物会在构建后固定下来，环境切换时必须重新构建。

**速记**：构建期只发生一次，负责转换与优化；运行时每次执行，负责真实逻辑。



#### 构建产物的形态

**构建产物**：是构建命令在输出目录中生成的文件集合，常见形态包括入口页面、带哈希名的脚本与样式、静态资源以及资源清单。

- 带内容哈希：文件名包含一段内容哈希，内容不变则文件名不变，便于长期缓存。
- 按需拆分：入口之外的代码被拆成若干代码块，访问到对应功能时才加载。
- 资源内联：体积很小的资源被编码进产物，减少一次网络请求。
- 资源清单：记录源文件与产物文件名的映射关系，供服务端或工具读取。

```bash
dist/
  index.html
  assets/
    index-8f2c1d.js
    vendor-2a4b7e.js
    index-3c9d0a.css
  favicon.svg
```

> 产物目录是构建工具的输出契约，部署系统只消费这个目录，不必了解源码结构。

**速记**：产物包含入口、带哈希的脚本与样式、静态资源与资源清单，部署只依赖产物目录。



#### 构建工具与相邻概念的区分

**相邻概念区分**：是把构建工具与运行时框架、包管理器、任务运行器三类容易混淆的对象分开，明确各自处理的问题。

- 与框架的区别：框架提供组件与状态模型等运行时能力，构建工具在构建期把源码转换为产物。
- 与包管理器的区别：包管理器负责下载与解析依赖，构建工具负责把依赖与源码组织成产物。
- 与任务运行器的区别：任务运行器编排多条命令的执行顺序，构建工具聚焦源码到产物的转换。
- 与运行时的区别：运行时在浏览器或 Node.js 中执行产物，构建工具不参与产物的执行过程。

```bash
# 三者在一次发布流程中的先后关系
npm install           # 包管理器：准备依赖
npm run build         # 构建工具：产出 dist 目录
node dist/server.js   # 运行时：执行产物
```

> [!TIP]
> **建议内容**：排查问题时先判断问题属于哪一层，依赖装不上看包管理器，产物报错看构建工具，页面行为异常看运行时。

**速记**：包管理器备依赖、构建工具出产物、运行时执行产物，三者职责不重叠。



### 为什么需要构建

浏览器只认识标准化的 JavaScript、CSS 与静态资源，而工程实践中使用的语法、模块与资源类型远多于此。构建的价值在于填平这段落差，本节给出四类典型动机。

#### 兼容性：语法降级与垫片

**语法降级（transpile down）**：是把较新的语言特性转换为目标浏览器可识别的等价写法；**垫片（polyfill）**：是补齐运行时缺失内置对象的代码。

- 语法层面：可选链、空值合并等新语法可被改写为等价的旧写法。
- 能力层面：Promise、Array.prototype.includes 等缺失的内置对象由垫片补上。
- 目标范围：转换到哪个版本由目标浏览器范围（browserslist）决定，而非一刀切。
- 成本权衡：目标越旧，产物越大、转换越多，需要按实际用户分布取舍。

```js
// 源码
const city = user?.address?.city ?? "unknown";
console.log(city);
```

```js
// 降级后的产物
var _a, _b;
const city = (_b = (_a = user === null || user === void 0 ? void 0 : user.address) === null || _a === void 0 ? void 0 : _a.city) !== null && _b !== void 0 ? _b : "unknown";
console.log(city);
```

> 语法降级只改写写法，垫片只补内置对象，二者解决的不是同一类兼容问题，需要分别配置。

> [!CAUTION]
> **注意内容**：把目标浏览器范围定得过旧会显著增大产物并提高转换出错的概率，应按实际访问数据而非「越兼容越好」来设定。

**速记**：降级改写法，垫片补能力，目标范围由 browserslist 决定，越旧代价越大。



#### 模块依赖：从多次请求到统一产物

**模块依赖**：是源文件之间通过导入与导出语句建立的引用关系；浏览器逐个请求源文件会产生大量往返，构建工具据此把它们合并或拆分成合适的产物。

- 开发期写法：源文件按功能拆成很多小模块，便于阅读与复用。
- 直接运行的问题：一个页面可能引入上百个模块文件，请求数过多，加载变慢。
- 构建期处理：沿依赖关系把模块组织进少数几个产物，或按路由边界拆包。
- 兼容处理：浏览器不支持某些模块格式时，构建工具负责改写为可执行的等价代码。

```js
// src/utils/formatDate.js
export function formatDate(date) {
  return date.toISOString().slice(0, 10);
}
```

```js
// src/main.js
import { formatDate } from "./utils/formatDate.js";
console.log(formatDate(new Date("2026-09-13"))); // "2026-09-13"
```

```html
<script type="module" src="./src/main.js"></script>
<!-- 未经构建时，浏览器需沿导入关系逐级请求源文件 -->
```

> 模块格式的差异与打包原理详见本主题第 3 篇 模块化与打包原理，此处只说明构建的动机。

**速记**：构建工具沿依赖关系组织模块，把大量源文件收敛为少量产物并处理格式兼容。



#### 资源与性能：压缩、拆分与内联

**资源处理**：是构建工具对样式、图片、字体等非脚本文件的转换与优化，目标是在不改变功能的前提下减少请求数、体积与加载时间。

- 压缩：删除空白与注释，缩短局部变量名，移除不会被执行的代码。
- 拆分：把不常变动的第三方依赖与业务代码分开，提高缓存命中率。
- 内联：小于阈值的图片转成数据形式写入样式或脚本，省去一次请求。
- 校验：产物文件名带内容哈希，内容未变则浏览器直接命中缓存。

```bash
# 压缩前后对比示意
# 压缩前   index.js   142.31 kB
# 压缩后   index.js    48.90 kB
# gzip 后  index.js    16.20 kB
```

> 优化的前提是度量：先看体积构成与加载顺序，再决定压缩、拆分还是懒加载，避免凭直觉调参。

**速记**：资源处理的三个手段是压缩、拆分与内联，效果必须靠体积数据验证。



#### 开发期的效率与一致性

**开发期收益**：是构建工具在编码阶段提供的即时反馈能力，包括启动开发服务器、修改后自动更新、路径别名与依赖解析等。

- 即时更新：保存文件后只更新受影响的模块，页面无需整体刷新即可生效。
- 模块解析：支持省略扩展名、路径别名与样式预处理语法，写法更贴近源码组织。
- 环境一致：同一份配置在开发期与构建期共用，减少「本地正常、线上异常」。
- 团队统一：代码检查与格式化工具挂在同一条链路里，减少风格分歧。

```bash
npm run dev
# dev server running at:
#   Local:   http://localhost:5173/
#   ready in 320 ms
```

> 开发期的启动速度与构建期的产物质量是两套指标，快的开发服务器不意味着产物更小。

**速记**：开发期收益是即时更新、统一解析与团队一致，与产物体积是两套指标。



### 工具链全景与分工

构建链上通常同时存在打包器、转译器、开发服务器与质量工具，各自负责一段流程。本节按职责把它们拆开，明确谁调用谁。

#### 打包器

**打包器（bundler）**：是沿模块依赖关系把多个源文件组织成少量产物的工具，代表有 webpack、Rollup、esbuild 与 Vite 的构建底层。

- 核心能力：依赖解析、模块合并、代码分割与产物输出。
- 职责边界：通常不直接负责语法降级与样式预处理，而是调用转译器与插件完成。
- 典型差异：webpack 生态成熟，Rollup 适合库打包，esbuild 以并行处理的速度见长。
- 选择依据：应用打包看生态与配置能力，库打包看输出格式的完整度与产物体积。

```bash
# 打包器的最小用法示意（以 esbuild 为例）
npm install --save-dev esbuild
npx esbuild src/main.js --bundle --outfile=dist/main.js
# dist/main.js   12.4kb
```

> 打包器是构建链的调度中心，转译与资源处理以插件或 loader 的形式挂在它上面。

**速记**：打包器的职责是解析依赖、合并模块、切分产物，转译与资源处理由插件承担。



#### 转译器

**转译器（transpiler）**：是把一种语言或语法版本转换为另一种等价形式的工具，在构建链中承担语法降级与类型移除。

- 处理对象：TypeScript、较新的 JavaScript 语法、JSX 与 CSS 预处理语法。
- 典型代表：Babel 负责语法降级，tsc 负责类型检查与移除，PostCSS 处理样式语法。
- 工作方式：按文件独立处理，不负责跨文件打包，通常由打包器调用。
- 配置要点：目标范围、插件或预设顺序、是否生成来源映射。

```bash
# 单独调用转译器
npx tsc --noEmit
npx babel src --out-dir lib
# lib 目录与 src 目录结构一致，只是语法被改写
```

> 转译器以文件为单位工作，所以它不知道项目里一共有多少个模块，跨文件的事情归打包器。

**速记**：转译器逐文件改写语法，不参与跨文件组织，由打包器在入图前调用。



#### 开发服务器

**开发服务器（dev server）**：是在本地提供文件服务并支持修改后即时更新的进程，把源码按浏览器可执行的形式返回。

- 静态服务：监听端口，把请求映射到项目文件或内存中的编译结果。
- 即时更新：文件变化后只推送差异，尽量保留页面当前状态。
- 接口代理：把接口请求转发到后端服务，规避浏览器跨域限制。
- 配置一致：尽量让开发期的解析规则与构建期一致，减少行为差异。

```bash
npm run dev
# Local:   http://localhost:5173/
# Network: use --host to expose
```

> [!NOTE]
> **提醒内容**：开发服务器只服务本地开发，不做压缩与兼容处理，不能直接当作线上服务使用。

**速记**：开发服务器负责本地服务、即时更新与接口代理，与线上服务的职责不同。



#### 校验工具与脚手架

**脚手架（scaffold）**：是生成项目初始目录与配置的工具；**静态检查工具**：是在不运行代码的前提下按规则指出问题的工具。

- 脚手架：按模板生成目录、依赖清单与常用脚本，减少重复搭建。
- 静态检查：ESLint 负责代码规则检查，Prettier 负责格式统一。
- 协同位置：两者挂在构建链或提交钩子上，与打包器互不替代。
- 边界说明：校验工具不参与产物生成，只影响代码质量与提交结果。

```bash
npm create vite@latest my-app -- --template vue
cd my-app && npm install && npm run dev
# 生成项目骨架并启动开发服务器
```

> 工具之间是调用关系而非竞争关系：脚手架生成项目，开发服务器跑开发期，打包器产出产物，转译器在链中被调用。

**速记**：脚手架搭项目，开发服务器管开发期，转译器改文件，打包器出产物，校验工具管质量。



### 原生 ESM 时代的变化

浏览器原生支持模块标准之后，开发期不再必须先整体打包。本节说明原生模块的加载方式、免打包开发的分工，以及这一变化没有改变的部分。

#### 原生 ESM 的加载方式

**原生 ESM（ECMAScript Modules）**：是浏览器与 Node.js 直接支持的模块标准，通过引入与导出语句在运行时按依赖关系加载文件。

- 语法：源文件使用 import 与 export 声明依赖，脚本需以模块方式加载。
- 浏览器行为：按需请求每个模块文件，支持顶层 await 与动态导入。
- 限制：裸包名不能被浏览器直接解析，需要映射表或开发服务器改写。
- 影响：开发期可以不再预先整体打包，改由服务器按请求返回模块。

```html
<script type="module" src="/src/main.js"></script>
```

> 原生模块的加载规则与解析细节详见 后端/Node 主题第 4 篇，此处只关心它对开发期流程的影响。

**速记**：原生 ESM 由浏览器按需请求模块，裸包名需映射表或服务器改写。



#### 免打包开发与依赖预构建

**免打包开发（no-bundle dev）**：是开发服务器把源模块按请求返回、不做整体打包的启动方式；**依赖预构建**：是把第三方依赖提前转换成少量模块文件以降低请求数。

- 启动快：不需要先扫描并打包全部源码，冷启动时间显著缩短。
- 按请求编译：浏览器请求哪个模块，服务器就转换并返回哪个模块。
- 依赖预构建：把上百个依赖内部模块合并成少量文件，并统一转换为 ESM。
- 缓存复用：预构建结果缓存到本地目录，依赖未变则直接复用。

```bash
# 依赖预构建产物缓存在项目内的缓存目录
# node_modules/.vite/deps/vue.js
```

> 预构建针对的是第三方依赖，业务源码仍按请求逐个转换，两类文件的处理策略不同。

**速记**：免打包开发按请求转换源码，依赖预构建把第三方包合并成少量 ESM 文件并缓存。



#### 取舍与边界

**取舍**：是免打包开发与整体打包在生产产物上的分工，开发期追求启动与更新速度，构建期追求体积与兼容性。

- 开发期：不打包、按请求转换，代价是请求数多、首屏依赖网络往返。
- 构建期：仍然整体打包与优化，产物面向真实用户的缓存与体积要求。
- 兼容边界：原生 ESM 需要现代浏览器，老浏览器仍依赖构建期的格式转换。
- 结论：免打包改变的是开发期流程，没有取消构建期。

> [!NOTE]
> **提醒内容**：开发服务器跑得快不等于可以省略构建期，线上产物仍要经过打包、压缩与兼容处理。

**速记**：免打包只优化开发期，构建期依然负责打包、压缩与兼容。

> Vite 四篇按「上手、配置、开发期、构建期」切分，webpack 三篇按「概念、loader 与 plugin、优化与分包」切分，两者不重复通用概念。

**速记**：17 篇分五段，基础三篇打底，Vite 与 webpack 各成一组，专项与工程实践收尾。



#### 各阶段的学习重点

- 基础段：理解构建的动机与产物形态，掌握依赖字段与版本范围，读懂模块格式与打包过程。
- Vite 段：能创建项目、编写配置、接入插件，并区分开发期与构建期的行为差异。
- webpack 段：理解入口与输出、loader 与 plugin 的职责，能做基础分包与优化。
- 专项段：知道转译、样式处理与代码检查各自接在哪一环，能按需组合。
- 实践段：能排查解析失败与内存问题，能为多包仓库设计构建与缓存策略。

> 基础段的三篇是后续所有篇目的公共词汇表，跳读会让后续配置项失去上下文。

**速记**：先懂动机与大图，再学配置与插件，最后练排查与优化。



#### 建议顺序

- 顺序阅读：第 1 篇至第 17 篇依次推进，每篇末尾的速记可用于复习。
- 按需跳读：以 Vite 为主的项目优先读第 1 篇至第 7 篇与第 11 篇至第 13 篇。
- 维护旧项目：补读第 8 篇至第 10 篇的 webpack 内容与第 15 篇的缓存策略。
- 优化提速：先读第 15 篇定位瓶颈，再按结论回到具体工具篇调整配置。
- 查阅型阅读：遇到具体报错先看第 16 篇，再回到对应工具篇定位配置。
- 只做库开发：优先读第 3 篇、第 12 篇与第 7 篇的库模式部分，应用侧篇目可按需略读。
- 后续衔接：模块加载规则与 npm 基础命令详见 后端/Node 主题第 6 篇 npm 与包管理。

> 与测试相关的工具链不在本系列范围，需要时详见 前端/测试 主题第 2 篇 测试工具链与运行器选型。

**速记**：顺序读打底，按工具栈跳读，遇到报错先看第 16 篇再回配置篇。
