## Babel 与 PostCSS：转译与语法降级

### Babel 的作用与配置文件

**Babel**：是把较新的 JavaScript 语法转译为向后兼容语法的转译器（transpiler），读取源码与配置，输出在目标环境可解析的等价代码。

本模块说明 Babel 做什么、配置写在哪些文件、预设与插件如何组织。

#### Babel 的职责与工作流程

**Babel 的职责**：是把浏览器或 Node.js 尚不支持的语法改写成支持的写法，不负责打包、类型检查与压缩。

- 解析：@babel/parser 把源码解析为抽象语法树（AST），语法树是源码结构的内存表示。
- 变换：按插件遍历语法树并改写节点，预设是一组插件的集合，按目标环境挑选。
- 生成：@babel/generator 把改写后的语法树输出为字符串，可附带 source map。
- 边界：模块打包、代码压缩、类型检查分别交给构建工具、压缩器与类型检查器。

```bash
npm install --save-dev @babel/core @babel/cli @babel/preset-env
npx babel src --out-dir dist
```

```js
// 输入：src/format.js
const formatLabel = (name) => `Hello, ${name}`;
```

```js
// 输出：dist/format.js（目标为 ES5 时）
var formatLabel = function formatLabel(name) {
  return "Hello, ".concat(name);
};
```

> 插件决定改哪一类语法，预设是对插件按场景打包后的集合；两者是原子与组合的关系。

**速记**：解析、变换、生成三步，Babel 只管语法转译，不打包不压缩。



#### 配置文件的格式与查找顺序

**Babel 配置**：是声明预设、插件与选项的文件，按作用范围分为项目级配置与文件级配置两类。

- 项目级配置：babel.config.json 或 babel.config.js 放在项目根目录，作用范围是整个项目。
- 文件级配置：.babelrc.json 或 .babelrc.js 从被编译文件所在目录向上查找，就近生效。
- 清单内联：package.json 中的 babel 字段等价于一份文件级配置，适合简单项目。
- 查找顺序：先加载项目级配置，再为每个文件叠加就近的文件级配置，同名选项由文件级覆盖。
- 选择建议：单包项目用 babel.config.json，单仓多包用项目级配置配合 overrides 按目录区分。

```json
{
  "presets": [["@babel/preset-env", { "targets": "defaults" }]],
  "plugins": []
}
```

```js
// babel.config.js 便于按环境分支
module.exports = {
  presets: [["@babel/preset-env", { "targets": "defaults" }]],
  env: {
    test: { presets: [["@babel/preset-env", { "targets": { "node": "current" } }]] },
  },
};
```

> 同一项目同时存在项目级与文件级配置时容易产生难以排查的叠加效果，优先只保留一份。

**速记**：项目级看根目录、文件级就近查找，两种配置会叠加，尽量只留一份。



#### 常用 preset 与 plugin 组合

**预设（preset）**：是若干插件的有序集合，解决一类场景的语法转换；**插件（plugin）** 是转换单一语法特性的最小单位。

- @babel/preset-env：按目标环境自动决定需要的语法转换插件，是应用项目的默认选择。
- @babel/preset-typescript：剥离 TypeScript 类型语法，不做类型检查，检查仍由 tsc 负责。
- @babel/preset-react：转换 JSX 语法，新版可配置为自动运行时，免去手动引入运行时对象。
- @babel/plugin-transform-runtime：把内联的辅助函数改为从运行时包引入，并隔离对全局的改动，适合库开发。
- 执行顺序：插件先于预设执行，插件之间按数组正序，预设之间按数组逆序。

```js
module.exports = {
  presets: [["@babel/preset-react", { "runtime": "automatic" }], "@babel/preset-typescript"],
  plugins: ["@babel/plugin-transform-runtime"],
};
```

> 预设逆序执行是有意设计：后写的预设先跑，便于让更贴近语法的转换优先落地；preset-typescript 只剥离类型，类型检查需另跑 tsc --noEmit。

**速记**：preset-env 管目标、preset-typescript 只剥类型、transform-runtime 隔离全局，插件先于预设。



### preset-env 与 browserslist

**目标环境**：是代码需要兼容的浏览器或运行时集合，Babel 由它推导出所需的最小转换集合，配置来源是 preset-env 的 targets 或 browserslist。

本模块讲清目标范围怎么写、preset-env 如何据此取插件、常用字段怎样配。

#### preset-env 的作用与写法

**@babel/preset-env**：是依据目标环境自动挑选语法转换插件的预设，输入目标范围，输出该范围所需的转换集合。

- 自动选插件：不再手工罗列数十个语法插件，新增目标环境只需改范围。
- targets：显式指定目标环境，省略时读取项目中的 browserslist 配置。
- modules 字段：取 false 时保留 ES Module 交给打包器；取 auto 或 commonjs 会转成 CommonJS。
- bugfixes：只启用修复真实缺陷所需的插件，缩小产物体积。
- debug：输出本次命中的目标范围与插件清单，便于验证配置是否生效。

```json
{
  "presets": [
    ["@babel/preset-env", {
      "targets": "> 0.5%, last 2 versions, not dead",
      "modules": false,
      "bugfixes": true,
      "debug": true
    }]
  ]
}
```

```bash
npx babel src --out-dir dist
# @babel/preset-env: Using targets: {...}
# @babel/preset-env: Using plugins: [...]
```

> [!IMPORTANT]
> **重要内容**：把 modules 设为 commonjs 会把 ES Module 降级为 CommonJS，打包器的摇树优化随即失效，应保留 false。

**速记**：preset-env 按范围挑插件，交给打包器时必须把 modules 设为 false。



#### browserslist 的配置方式

**browserslist**：是用查询语句描述目标浏览器范围的配置，被 Babel、PostCSS 与构建工具共同读取，是转译与样式降级的统一输入。

- 配置文件：项目根写 .browserslistrc，每行一条查询语句。
- 清单字段：package.json 中 browserslist 字段，取值为查询语句数组。
- 查询语法：last 2 versions 取各浏览器最近两个版本，大于 0.5% 取全球使用率超过该比例的版本，not dead 排除停止维护的版本，defaults 是推荐组合。
- 环境分节：配置文件可用 production 与 development 分节，为不同场景给出不同范围。
- 唯一来源：同一仓库只保留一处配置，避免 Babel 与 PostCSS 读到不同范围。

```text
last 2 versions
> 0.5%
not dead
```

```json
{
  "name": "web-app",
  "version": "1.0.0",
  "browserslist": ["> 0.5%", "last 2 versions", "not dead"]
}
```

```bash
npx browserslist
# 列出当前配置命中的全部浏览器与版本
```

> 范围越宽，需要转译的语法与需要注入的垫片越多，产物体积随之上升；范围应以真实用户分布为依据。

**速记**：browserslist 用查询语句写范围，Babel 与 PostCSS 共用一份配置。



#### targets 与 include 与 exclude

**targets 字段**：是 preset-env 中直接指定目标环境的选项，优先级高于 browserslist 配置。

- 优先级：targets 与 browserslist 同时存在时以 targets 为准。
- 写法：可为查询字符串，也可为对象，按键给出最低版本，如 chrome 取 90。
- include：强制启用某个转换插件，即使目标环境已原生支持。
- exclude：强制禁用某个转换插件，用于规避该插件的已知缺陷。
- 排查手段：debug 输出会列出最终目标与生效插件，include 与 exclude 的结果可直接看到。

```json
{
  "presets": [
    ["@babel/preset-env", {
      "targets": { "chrome": "90", "node": "18" },
      "include": ["@babel/plugin-transform-nullish-coalescing-operator"],
      "exclude": ["@babel/plugin-transform-classes"]
    }]
  ]
}
```

> 只在确有兼容缺陷或必须强制转换时才用 include 与 exclude，否则交由 preset-env 自动判断。

**速记**：targets 优先于 browserslist，include 强开、exclude 强关，debug 可核对结果。



### 垫片与 core-js

**垫片（polyfill）**：是补上运行环境缺失的全局对象或内置方法的代码，改变的是运行时能力，而不是代码写法。

本模块区分转译与垫片、说明 core-js 的接入方式与按需注入策略。

#### 垫片与转译的区别

**转译与垫片的分工**：转译解决语法层面的不兼容，垫片解决运行时 API 的缺失，二者不可互相替代。

- 转译的问题域：新增语法在旧环境无法解析，如箭头函数、可选链、类字段。
- 垫片的问题域：新增 API 在旧环境不存在，如 Promise、Array.from、Object.assign。
- 可降级与不可降级：语法总有等价旧写法，API 往往没有，方法是原生提供的能力，无法由语法转换补出。
- 运行时开销：垫片是额外代码，进入产物并占用启动时间，应按目标范围精确注入。
- 判断口径：解析报错看转译，方法未定义或对象不存在看垫片。

```js
// 语法问题：旧环境解析失败，由转译解决
const first = list?.[0];
```

```js
// API 问题：旧环境没有 includes 方法，只能由垫片解决
const hasAdminRole = roles.includes("admin");
```

> 报错信息形如某个值 is not a function 或某个对象 is not defined，通常优先怀疑缺少垫片，而不是转译配置。

**速记**：语法不兼容靠转译，API 缺失靠垫片，两者职责不重叠。



#### core-js 的接入方式

**core-js**：是提供标准库垫片与标准实现的开源包，Babel 通过 preset-env 的 useBuiltIns 与 corejs 字段决定如何注入。

- 安装位置：core-js 需作为生产依赖安装，产物在运行时需要它提供的代码。
- 版本字段：corejs 指明所用主次版本，如 3.37，必须与实际安装版本匹配。
- entry 方式：在入口显式引入 core-js 与 regenerator-runtime，preset-env 按目标范围裁剪为子集。
- usage 方式：不写引入语句，Babel 按代码实际用到的 API 自动插入对应垫片。
- 库的差别：库不应污染全局，改用 @babel/plugin-transform-runtime 与 @babel/runtime 按引用注入。

```bash
npm install core-js@3
npm install --save-dev @babel/plugin-transform-runtime
npm install @babel/runtime
```

```js
// 采用 useBuiltIns 取 entry 时，在入口写整体引入
import "core-js/stable";
import "regenerator-runtime/runtime";
```

> [!WARNING]
> **警告内容**：core-js 装在生产依赖之外、或 corejs 字段写的主次版本与实际安装版本不一致，构建会直接失败或产出缺少垫片的代码。

**速记**：core-js 装生产依赖，corejs 版本要与实际安装一致，库改用 transform-runtime。



#### useBuiltIns 的三种取值

**useBuiltIns**：是 preset-env 控制垫片注入时机的字段，取 false、entry 或 usage，直接决定垫片范围与引入方式。

- false：默认值，不自动插入垫片，是否引入完全由代码负责。
- entry：把入口处的整体引入按目标范围改写为所需子集，需要手写引入语句。
- usage：按每个文件实际使用的 API 插入垫片，粒度最细，无需手写引入。
- 选择依据：应用常用 usage；需要显式控制引入位置与顺序时用 entry。
- 局限：usage 只分析当前文件的 API 使用，第三方依赖内部用到而自身未声明的 API 仍需兜底。

```json
{
  "presets": [
    ["@babel/preset-env", {
      "useBuiltIns": "usage",
      "corejs": "3.37",
      "targets": "> 0.5%, last 2 versions, not dead"
    }]
  ]
}
```

```js
// 源码只写业务逻辑，垫片由 Babel 自动插入
const ids = new Set([1, 2, 3]);
const list = Array.from(ids);
```

> usage 与 entry 不能同时生效，同一份 preset-env 配置只能取其一；两者都要求写明 corejs 版本。

**速记**：false 不注入、entry 按入口裁剪、usage 按文件按需插入，且都必须标明 corejs 版本。



### PostCSS 与 autoprefixer

**PostCSS**：是把 CSS 解析为语法树、交由插件逐个改写的样式处理工具；本模块只讲它在构建链中的接入位置与配置写法，原理详见 前端/CSS 主题第 23 篇 工程化与最佳实践。

本模块讲清 autoprefixer 的作用、postcss.config 怎么写、如何接进 Vite 与 webpack。

#### autoprefixer 的作用与接入

**autoprefixer**：是按目标浏览器范围给 CSS 属性补厂商前缀的 PostCSS 插件，数据源来自 Can I Use 的兼容数据。

- 数据来源：读取项目中的 browserslist 配置，与 Babel 共用同一份范围。
- 安装方式：作为开发依赖安装，仅在构建期使用。
- 配置项：overrideBrowserslist 可就地覆盖范围，grid 取 auto 时按需补充网格布局前缀。
- 执行位置：放在样式处理链末端、压缩之前，确保前缀作用在最终属性上。
- 更新时机：兼容数据随插件版本更新，定期升级即可获得新属性支持。

```bash
npm install --save-dev postcss postcss-cli autoprefixer
npx postcss src/style.css --use autoprefixer -o dist/style.css
```

```js
module.exports = {
  plugins: {
    autoprefixer: { grid: "autofix" },
  },
};
```

> 前缀由目标范围自动决定，源码中一律手写无前缀的标准属性，避免范围收窄后残留无用前缀。

**速记**：autoprefixer 读 browserslist 补前缀，装在开发依赖，位置在链尾、压缩之前。



#### postcss.config 的写法

**postcss.config 文件**：是构建工具自动读取的 PostCSS 配置文件，声明插件及其选项与执行顺序。

- 文件形式：postcss.config.js 导出对象，plugins 字段为插件映射。
- 插件写法：键为插件名，值为选项对象，无选项时写空对象即可。
- 数组形式：也可用数组逐项列出插件，数组项为插件函数或插件名与选项的数组。
- 顺序规则：对象形式的键顺序即执行顺序，数组形式的顺序更直观，动作有依赖时应改用数组。
- 放置位置：配置文件放在项目根，构建工具与命令行工具都会自动读取。

```js
module.exports = {
  plugins: {
    "postcss-import": {},
    autoprefixer: {},
    cssnano: { preset: "default" },
  },
};
```

```json
{
  "plugins": {
    "autoprefixer": {},
    "postcss-preset-env": { "stage": 3 }
  }
}
```

> [!TIP]
> **建议内容**：插件之间存在顺序依赖时改用数组写法，键值对象的顺序在阅读与维护中容易被误改。

**速记**：postcss.config.js 的 plugins 键顺序即执行顺序，有依赖时改用数组。



#### 与构建工具的衔接

**构建链接入**：是把 PostCSS 插进样式处理链的固定环节，不同工具读取配置的方式不同，但都支持在工具配置内联。

- Vite：项目根存在 postcss.config.js 时自动读取；也可在 vite.config.js 的 css.postcss 字段内联。
- webpack：使用 postcss-loader，位置在 css-loader 之后、预处理器 loader 之前。
- 链顺序：预处理 loader、postcss-loader、css-loader、style-loader 或抽取插件，从右向左依次执行。
- 作用范围：工具配置内的内联配置对该工具处理的全部样式生效。
- 验证方式：用 postcss-cli 对单个文件试跑，确认插件与顺序符合预期。

```js
// vite.config.js
export default {
  css: {
    postcss: {
      plugins: [require("autoprefixer")({ grid: "autofix" })],
    },
  },
};
```

```js
// webpack.config.js 片段
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ["style-loader", "css-loader", "postcss-loader"],
      },
    ],
  },
};
```

> [!CAUTION]
> **注意内容**：在 Vite 中写了 css.postcss 内联配置后，项目根的 postcss.config.js 不再被读取，两处配置同时存在时会误以为存在却未生效。

**速记**：Vite 自动读根配置或内联 css.postcss，webpack 用 postcss-loader，链从右向左执行。



### 样式模块化接入

**样式模块化接入**：是在构建链中把类名作用域化的配置方式，本模块只讲接入步骤与配置字段，作用域生成原理详见 前端/CSS 主题第 23 篇 工程化与最佳实践。

本模块讲清命名约定与导出形式、在 Vite 与 webpack 中各自如何开启。

#### 命名约定与导出形式

**CSS Modules**：是让样式文件导出一个类名映射对象、由构建工具改写类名的接入方式。

- 文件约定：以 .module.css 结尾的文件按模块处理，普通 .css 文件保持全局样式。
- 导入结果：导入得到一个对象，对象的键是源码中的类名，值是改写后的实际类名。
- 使用方式：把映射值作为类名赋给元素，未在映射中出现的类名不参与作用域化。
- 导出格式：localsConvention 可配置为 camelCase 等，让连字符类名以驼峰键访问。
- 全局例外：在局部文件中用全局选择器语法引用全局类名，该部分不做改写。

```css
/* user-card.module.css */
.card { border: 1px solid #ddd; }
.cardTitle { font-weight: 600; }
```

```js
import styles from "./user-card.module.css";

export function buildCardClassName() {
  return styles.card;
  // 形如 "user-card_card__a1b2c"
}
```

> 类名映射对象的键名取决于 localsConvention，键名写错会得到 undefined，表现为元素没有样式而不报错。

**速记**：.module.css 后缀触发模块化，导入得到类名映射，localsConvention 决定键的形态。



#### 在 Vite 中启用

**在 Vite 中启用样式模块化**：是把 .module.css 文件按模块处理并配置类名生成规则，Vite 内置支持，无需额外插件。

- 开箱即用：文件名带 .module 即生效，无需安装依赖或改写配置。
- 生成规则：css.modules.generateScopedName 自定义类名模板，取值可为字符串或函数。
- 导出一致性：css.modules.localsConvention 控制键名形态，取 camelCase 时连字符类名也可用驼峰访问。
- 与预处理器：.module.scss 等组合同样有效，由对应的预处理器插件处理后再进入模块化流程。
- 类型支持：为模块样式声明类型，可在编辑器中获得键名补全。

```js
// vite.config.js
export default {
  css: {
    modules: {
      localsConvention: "camelCaseOnly",
      generateScopedName: "[name]__[local]--[hash:base64:5]",
    },
  },
};
```

```js
// 使用全局样式与模块样式并存
import "./global.css";
import styles from "./user-card.module.css";

console.log(styles.card); // "user-card__card--x9k2m"
```

> 自定义 generateScopedName 会降低类名的可读性或唯一性，非必要不改，默认规则已兼顾可读与唯一。

**速记**：Vite 内置支持，.module 后缀即生效，配置集中在 css.modules。



#### 在 webpack 中启用

**在 webpack 中启用样式模块化**：是通过 css-loader 的 modules 选项完成的接入，需在样式规则中显式开启。

- 开启位置：css-loader 的 options.modules 字段，设为对象即启用。
- 类名模板：localIdentName 控制改写后的类名形态，开发期可读、生产期取短哈希。
- 精确启用：用 oneOf 或 include 只对 .module.css 应用模块化，普通 .css 保持全局。
- 与预处理器：sass-loader 位于链的右端，编译完成的 CSS 再交给 css-loader 处理类名。
- 生产优化：生产环境使用较短的哈希模板，减小样式体积。

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.module\.css$/,
        use: [
          "style-loader",
          {
            loader: "css-loader",
            options: {
              modules: { localIdentName: "[name]__[local]--[hash:base64:5]" },
            },
          },
        ],
      },
    ],
  },
};
```

> [!NOTE]
> **提醒内容**：同时匹配到多条样式规则时 loader 会重复执行，用 oneOf 或更精确的 test 让一个文件只走一条链路。

**速记**：webpack 靠 css-loader 的 modules 选项启用，用 oneOf 区分模块样式与全局样式。
