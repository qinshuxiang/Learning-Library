## Vite 的 SSR 与预渲染

Vite 的开发服务器与生产构建默认面向浏览器端应用，页面由脚本在浏览器里生成。当首屏标记需要先在服务端渲染成 HTML、再交给浏览器接管时，入口、构建产物与资源注入都要另配一套链路。本篇只讲 Vite 侧提供的接口与开发期、生产期的差异，基于框架约定的路由与数据获取属框架职责，详见 前端/SSR 与跨端 主题。开发服务器与生产构建的基础用法见本主题第 6、7 篇。

### SSR 的基本模型

服务端渲染改变的是首屏标记的产出位置，不改变组件本身的写法。本节先给出模型与对照，再说明同构代码的边界。

#### 服务端渲染与客户端注水

**服务端渲染（server-side rendering，SSR）**：是在每次请求到达时由服务端把组件渲染成 HTML 字符串返回、再由浏览器端同一份组件代码接管页面的渲染方式。

- 首次响应：服务端返回完整的页面标记，浏览器在脚本下载完成前即可显示内容。
- 客户端注水（hydration）：浏览器执行同构组件代码，把事件监听与状态绑定到已存在的 DOM 上。
- 服务端入口：导出一个接收请求信息的渲染函数，返回 HTML 字符串与本次渲染用到的数据。
- 数据来源：请求期可读取请求头、Cookie 与后端接口，首屏数据不必依赖客户端发起二次请求。
- 主要代价：每次请求都要执行一次渲染，运行环境必须能够执行组件代码与相关依赖。

```js
// src/entry-server.js 服务端入口：接请求，返回标记
import { renderPage } from "./renderPage.js";

export async function render(request) {
  const { html, state } = await renderPage(request.url);
  return { html, state };
}
```

```js
// src/entry-client.js 客户端入口：对已有标记注水
import { hydratePage } from "./renderPage.js";

hydratePage(document.getElementById("root"));
```

> [!NOTE]
> **提醒内容**：注水要求服务端与客户端的首屏结构与数据完全一致，只在其中一端成立的分支会在开发控制台报注水不匹配。

**速记**：服务端产出首屏标记，客户端用同一份组件代码对已有 DOM 注水接管。



#### 与纯静态构建的差异

**纯静态构建**：是在构建完成时就把所有页面渲染为静态文件、运行期不再执行渲染逻辑的构建方式。

- 产物形态：静态构建的产物目录只有 HTML、脚本与样式；SSR 多出一份供服务端加载的渲染入口产物。
- 运行依赖：静态产物交给任意静态服务器即可；SSR 需要一个能执行渲染入口的常驻进程或函数。
- 数据时效：静态产物的数据固定在构建时刻；SSR 的每次请求都可以读到最新数据。
- 缓存策略：静态文件可按文件名长期缓存；SSR 通常对渲染结果做短时缓存或按路径缓存。
- 部署复杂度：静态构建的发布即替换文件；SSR 还涉及进程伸缩、健康检查与日志。

```bash
# 纯静态构建：产物可直接托管
npm run build

# SSR 构建：客户端与服务端各构建一次
npm run build:client
npm run build:server
node server.js
```

> 两种方式可以并存：内容页用静态产物，需要登录态与实时数据的路径交给 SSR，由网关按路径分流。

**速记**：静态构建的产物只有文件、运行期不渲染；SSR 需要常驻渲染进程，换来请求期的数据时效。



#### 同构代码与两端入口

**同构代码（isomorphic code）**：是同一份组件与状态逻辑既在服务端执行、也在浏览器端执行的代码，两端共用模块但各自有入口文件。

- 共用模块：组件、状态容器、数据格式化函数放在两端都引用的模块里，避免复制两份实现。
- 入口拆分：客户端入口负责挂载与注水，服务端入口负责渲染并返回字符串，两个文件互不引用。
- 浏览器 API：服务端不存在 window 与 document，访问这些对象必须放在只在客户端执行的钩子或判断分支里。
- 模块级副作用：服务端进程长期存活，模块级全局变量会在多次请求之间共享，需要按请求创建实例。
- 条件分支：用 import.meta.env.SSR 判断当前执行环境，或用动态导入把仅浏览器可用的模块延后加载。

```js
// 只在客户端执行的逻辑要显式判断环境
const storage = import.meta.env.SSR ? null : window.localStorage;

export function readTheme() {
  return storage ? storage.getItem("theme") : "light";
}
```

> [!CAUTION]
> **注意内容**：把请求相关的数据写进模块级变量，会让并发请求相互覆盖，表现为偶发的串数据；这类状态必须按请求创建。

**速记**：同构代码两端共用模块，入口分开；浏览器 API 与请求级状态都必须显式隔离。



### Vite 的 SSR 接口

Vite 在开发期提供在 Node 进程内加载源码的能力，在构建期提供单独产出服务端入口的入口参数。本节按开发、构建、资源三块说明。

#### 开发期的模块加载

**SSR 模块加载**：是开发服务器提供的服务端执行入口，把源码按开发期规则转换后在 Node 进程内加载，返回模块的导出对象。

- 中间件模式：创建开发服务器时把 server.middlewareMode 设为 true，并以 appType 取 custom 关闭内置 HTML 处理，由业务服务自行接管请求。
- 加载接口：服务端调用开发服务器实例的 ssrLoadModule 方法，参数为模块的 URL 或绝对路径，得到该模块的导出对象。
- 环境形式：较新版本引入环境 API 后，等价能力由服务端环境的模块运行器提供，加载语义与前者一致。
- 静态服务：中间件模式下模板与静态资源需要由业务服务显式挂载，通常把开发服务器的 middlewares 接在业务路由之前。
- 复用收益：模块转换结果进入同一张模块图，改动一个组件后无需重启服务即可看到新的渲染结果。

```js
// server.js 开发期把 Vite 作为中间件使用
import express from "express";
import { createServer } from "vite";

const app = express();
const vite = await createServer({
  server: { middlewareMode: true },
  appType: "custom",
});

app.use(vite.middlewares);

app.get("*", async (request, response) => {
  const { render } = await vite.ssrLoadModule("/src/entry-server.js");
  const { html } = await render(request);
  response.status(200).set({ "Content-Type": "text/html" }).end(html);
});

app.listen(3000);
```

> 中间件模式下开发服务器不再自行返回页面，模板的读取、占位符替换与错误处理都由业务服务负责。

**速记**：中间件模式下用 ssrLoadModule 在 Node 内加载源码，转换结果与开发期模块图共用。



#### 服务端产物构建

**SSR 构建**：是以服务端入口为输入、产出面向 Node 运行环境的打包结果的过程，用 vite build 加 --ssr 参数触发。

- 入口参数：vite build --ssr src/entry-server.js，参数值是服务端入口的路径。
- 配置等价：在配置里写 build.ssr 与命令行传参效果相同，适合入口路径固定的项目。
- 两次构建：客户端与服务端各构建一次，通常用两个脚本分别指定产物目录，避免互相覆盖。
- 多入口：服务端同样支持多入口，用 build.rollupOptions.input 的对象形式声明，键名进入产物文件名。
- 外部依赖：服务端构建默认把依赖保留为运行时导入，只有需要内联的依赖才另行声明。

```json
{
  "scripts": {
    "build:client": "vite build --outDir dist/client",
    "build:server": "vite build --ssr src/entry-server.js --outDir dist/server"
  }
}
```

```bash
npm run build:client && npm run build:server
# dist/client 交给静态托管，dist/server 交给 Node 进程
```

> [!IMPORTANT]
> **重要内容**：客户端与服务端是两份产物，必须来自同一次提交且成对发布，只更新其中一份会造成清单里的文件名与实际文件不匹配。

**速记**：vite build --ssr 指定服务端入口，客户端与服务端分目录产出并成对发布。



#### 客户端清单与资源注入

**客户端清单（manifest）**：是构建生成的一份入口到真实文件名及依赖资源的映射，供服务端在返回标记时查找并注入脚本与样式。

- 开启方式：把 build.manifest 设为 true，构建后输出到产物目录下的 .vite/manifest.json。
- 关键字段：file 是入口产物名，css 是该入口用到的样式文件数组，imports 是该入口依赖的其它代码块。
- 注入对象：服务端渲染时把入口脚本、样式链接与预加载提示写入模板，替代开发期由开发服务器注入的内容。
- 存在原因：产物文件名带内容哈希，服务端无法在源码里写死，只能按入口名反查清单。
- 版本对齐：清单由客户端构建产出，服务端进程读取的是同一次构建的结果，两份产物不可混用。

```json
{
  "src/entry-client.js": {
    "file": "assets/entry-client-D4m1q7kf.js",
    "src": "src/entry-client.js",
    "isEntry": true,
    "css": ["assets/entry-client-B7xq2p0d.css"],
    "imports": ["assets/vendor-C9dq1f7k.js"]
  }
}
```

```js
// 服务端按清单拼出标记中的资源标签
const entry = clientManifest["src/entry-client.js"];
const scriptTag = '<script type="module" src="/' + entry.file + '"></script>';
```

> 清单只描述入口与资源的对应关系，不包含渲染结果；服务端渲染函数的返回内容仍需拼接在模板占位符处。

**速记**：客户端清单把入口名映射到带哈希的真实文件，服务端据此注入脚本与样式。



### 开发期与生产期的差异

同一份源码在两期的加载方式、样式处理与运行环境都不相同，这些差异是 SSR 问题的主要来源。本节逐项对照。

#### 模块加载方式的差异

**模块加载差异**：开发期的服务端代码由开发服务器按请求转换后直接执行源码，生产期执行的是一份预先打包好的产物。

- 开发期：依赖默认按 Node 的规则解析并外部化，源码模块按需转换，改动立即生效。
- 生产期：依赖是否内联由 ssr.noExternal 与 ssr.external 决定，其余模块由打包器静态分析后合并。
- 解析差异：开发期能容忍的运行时拼接路径在生产期可能被静态分析改写，出现两期行为不一致。
- 实例差异：外部化的依赖由 Node 加载一份实例，内联的依赖与客户端产物各自持有一份，状态不共享。
- 回归方式：只在开发期验证过的 SSR 代码，必须用 node 直接运行服务端产物再验证一次。

```js
// vite.config.js 按包名决定哪些依赖不参与外部化
import { defineConfig } from "vite";

export default defineConfig({
  ssr: {
    noExternal: ["my-ui-lib"],
  },
});
```

> noExternal 中的依赖会被打包进服务端产物，适合源码为 ESM 但发布为 CommonJS、Node 无法直接加载的包。

**速记**：开发期执行源码并外部化依赖，生产期执行打包产物，两期行为需各验证一次。



#### 样式与静态资源的差异

**样式处理差异**：开发期样式在模块转换阶段被收集并随注入逻辑生效，生产期样式被提取为独立文件，文件名从清单读取。

- 开发期：样式由模块图收集后随开发服务器注入，页面里没有独立样式文件，也不会有样式请求失败。
- 生产期：样式被提取为带哈希的文件，服务端必须在标记中写入对应的样式链接，否则首屏无样式。
- 闪烁成因：样式链接写在页面底部或由客户端脚本插入，会在注水后重新应用一次，表现为样式闪动。
- 资源引用：图片与字体的地址在服务端渲染时同样要带上 base 前缀，直接拼接相对路径在子目录部署下会 404。
- 只读接口：服务端渲染期间不要写入浏览器存储或操作布局相关对象，这些调用在服务端没有对应实现。

```js
// 模板占位符处同时写入样式链接与入口脚本
const styles = entry.css
  .map((file) => '<link rel="stylesheet" href="/' + file + '">')
  .join("");
```

> [!WARNING]
> **警告内容**：生产期遗忘注入客户端清单中的样式数组，页面会先以无样式状态显示再被脚本补上，出现肉眼可见的样式闪烁与布局跳动。

**速记**：开发期样式随注入生效，生产期样式是独立文件且必须由清单注入，否则闪烁。



#### 运行环境与条件分支

**运行环境差异**：开发期由 Node 直接执行转换后的源码，生产期执行打包产物，两者的堆栈、全局对象与条件编译结果都不同。

- 环境判断：import.meta.env.SSR 在服务端为真、在浏览器端为假，用于隔离两端行为。
- 编译替换：import.meta.env 与 define 声明的常量在两期都被静态替换，服务端构建不存在的变量会整体替换为空值。
- 堆栈还原：服务端报错的堆栈指向转换后的代码，需用开发服务器实例的 ssrFixStacktrace 方法处理 Error 对象后再打印。
- 全局对象：process、Buffer 只在服务端存在，window、navigator 只在浏览器端存在，跨端引用会直接抛错。
- 服务端专用模块：仅服务端使用的依赖应避免被客户端入口间接引用，否则会被打进客户端产物。

```js
// 捕获渲染异常后还原可读堆栈
try {
  const { html } = await render(request);
  response.end(html);
} catch (error) {
  vite.ssrFixStacktrace(error);
  console.error(error.stack);
  response.status(500).end("render failed");
}
```

> ssrFixStacktrace 只在开发期有意义，生产期的产物自带生成时的映射信息。

**速记**：两期的全局对象与堆栈格式不同，用 import.meta.env.SSR 隔离分支并还原开发期堆栈。



### 预渲染与静态生成

预渲染把服务端渲染的结果提前到构建期生成，在保留首屏标记优势的同时去掉常驻渲染进程。本节说明适用场景与执行方式。

#### 预渲染的适用场景

**预渲染（prerender）**：是在构建期把路由逐个渲染成静态 HTML 文件、运行期不再执行渲染逻辑的做法。

- 适用范围：页面集合固定且数据可在构建期取得的内容型站点，例如营销页、文档站与博客。
- 收益来源：首屏标记随构建产出，搜索引擎与社交平台能直接抓取，部署形态与纯静态一致。
- 前置条件：路由清单必须可枚举，页面数量与构建时间成正比，页面过多会显著拉长构建。
- 不适用情形：依赖登录态、实时价格或按用户定制的页面，其内容在构建期无法确定。
- 混合形态：首页与内容页预渲染，交互密集的应用页仍走纯客户端渲染，两者共用一个产物目录。

```text
构建期：枚举路由 -> 逐个渲染 -> 写出 HTML 文件
运行期：静态服务器按路径返回文件，不执行渲染
更新：内容变化后重新构建并发布
```

> 预渲染与纯静态构建的差别在于标记的来源：前者用组件渲染出标记，后者由模板或手写文件直接提供。

**速记**：预渲染适合路由可枚举的内容型站点，构建期生成标记，运行期只需静态托管。



#### 预渲染的执行方式

**预渲染脚本**：是在构建完成之后加载服务端产物、按路由清单渲染并写出 HTML 文件的独立脚本。

- 顺序：先构建客户端产物，再构建服务端产物，预渲染脚本在两次构建之后执行并读取产物文件。
- 加载方式：脚本用动态导入加载服务端入口产物，调用其中的渲染函数，不需要再启动开发服务器。
- 路由来源：路由清单可以来自配置文件、构建参数或对源码目录的扫描结果，清单需与真实路由保持一致。
- 写出位置：每个路由写成产物目录下的对应路径，文件名为 index.html，与静态服务器的目录索引规则配合。
- 模板处理：用一个模板文件承接占位符替换，把渲染结果、样式链接与入口脚本写入同一份标记。

```js
// scripts/prerender.js 构建后逐路由产出静态文件
import { mkdir, readFile, writeFile } from "node:fs/promises";
import { dirname, join } from "node:path";
import { render } from "../dist/server/entry-server.js";

const routes = ["/", "/about", "/docs/intro"];
const template = await readFile("dist/client/index.html", "utf-8");

for (const route of routes) {
  const { html } = await render({ url: route });
  const page = template.replace("<!--app-html-->", html);
  const file = join("dist/client", route, "index.html");
  await mkdir(dirname(file), { recursive: true });
  await writeFile(file, page);
}
```

```bash
node scripts/prerender.js
# 产物目录中出现按路由组织的静态 HTML 文件
```

> [!TIP]
> **建议内容**：把路由清单放在独立的配置文件中并在脚本里校验路径合法性，可避免清单与真实路由表长期脱节。

**速记**：预渲染脚本在两次构建之后加载服务端产物，按路由清单渲染并写出静态标记。



#### 与 SSR 的取舍

**预渲染与 SSR**：两者的渲染函数与同构代码可以共用，区别在渲染发生的时刻与所需的运行环境。

- 时效性：预渲染的数据固定在构建时刻；SSR 每次请求都能取到最新数据。
- 运行成本：预渲染没有常驻渲染进程；SSR 需要进程或函数承载每次请求。
- 伸缩方式：预渲染靠增加静态节点或分发网络扩容；SSR 靠扩充渲染实例并配合缓存。
- 缓存能力：预渲染天然可长期缓存；SSR 的输出通常按路径做短时缓存，缓存命中时才接近静态性能。
- 降级策略：SSR 服务不可用时页面整体不可访问，预渲染在渲染服务故障后仍能继续提供旧版本。

```text
形态       运行期依赖   数据时效   缓存粒度
纯静态     无           构建期     长期
预渲染     无           构建期     长期
SSR        渲染进程     请求期     短时按路径
```

> 同一项目常见做法是首页与内容页预渲染、个性化路径走 SSR，渲染函数与同构组件在两条链路中复用。

**速记**：预渲染省掉渲染进程、数据停在构建期；SSR 数据更新但需常驻渲染，可混合使用。



### SSR 的常见问题

SSR 的问题集中在依赖加载、标记一致性与状态传递三处。本节按症状给出成因与处置方向。

#### 依赖外部化与加载报错

**外部化（external）**：是构建时把依赖保留为运行时导入、不并入产物的处理；服务端构建默认把依赖全部外部化。

- 典型症状：启动服务端产物时报模块格式错误，或依赖内部使用了 Node 无法直接执行的语法。
- 处置方式：把该依赖加入 ssr.noExternal 数组，让它随源码一起被打包转换；整表关闭外部化则传入布尔值。
- 链接依赖：工作区内以链接方式引用的本地包默认需要显式加入不外部化的名单，否则会加载到未转换的源码。
- 影响范围：该配置只作用于服务端构建，客户端产物的依赖处理规则不受影响。
- 双份实例：同一个依赖既被外部化又被内联时会加载出两份模块，模块级状态不共享，需按包名收敛归属。

```js
// vite.config.js
export default defineConfig({
  ssr: {
    noExternal: ["my-ui-lib", "@my-scope/utils"],
    external: ["native-image-tool"],
  },
});
```

> [!CAUTION]
> **注意内容**：为了解决报错而把整条依赖链都设为不外部化，会同时放大产物体积与服务端冷启动时间，应只针对实际报错的包处理。

**速记**：服务端依赖默认外部化，报格式错误时按包名加入不外部化名单，并检查是否出现双份实例。



#### 样式收集与注水不一致

**注水不一致（hydration mismatch）**：是服务端产出的标记与客户端首次渲染结果不同所致的不匹配，表现为控制台警告与局部重渲染。

- 常见成因：渲染结果依赖当前时间、随机数、屏幕尺寸或浏览器语言。
- 分支写法：服务端与客户端走了不同的条件路径，例如一端判断了浏览器存储的取值。
- 列表稳定：列表项缺少稳定且两端一致的键，会导致节点复用错位。
- 样式顺序：样式被客户端脚本二次插入时，顺序与构建期不同，表现为短暂的无样式。
- 处置方向：把仅客户端可得的取值放到挂载后写入，让首次渲染结果与标记保持一致。

```js
// 首次渲染与标记保持一致，客户端专属取值在挂载后写入
export function useNow() {
  return import.meta.env.SSR ? "" : new Date().toLocaleTimeString();
}
```

> 注水不一致通常不会立刻中断页面，但会让局部的状态与事件绑定失效，出现看着正常却点不动的组件。

**速记**：两端首屏结果必须一致，时间、随机数与浏览器专属取值不能参与首次渲染。



#### 状态序列化与内存

**状态序列化**：是把渲染期取得的数据转换成字符串嵌入标记、供客户端在注水时复用的过程。

- 传递方式：把数据挂到全局变量上并在客户端入口读取，或用一次接口请求重新获取。
- 转义处理：序列化结果写入标记前必须转义可能闭合脚本标签的字符序列，否则会截断页面脚本。
- 数据裁剪：只传递首屏真正需要的字段，完整数据留给客户端按需请求，避免标记体积失控。
- 内存增长：开发期服务端反复加载模块会累积旧模块实例，长时间运行后内存占用明显上升，需要定期重启。
- 兼容方式：优先使用能在两端直接解析的序列化结果，避免在字符串里传递函数与类实例。

```js
// 序列化时替换会闭合脚本标签的字符，再写入标记
function serializeState(state) {
  return JSON.stringify(state)
    .replace(/</g, "\\u003c")
    .replace(/\u2028/g, "\\u2028");
}
```

> [!WARNING]
> **警告内容**：直接把用户可控数据序列化进标记而不做转义，等于把注入入口交给外部输入，必须按标记上下文转义后再写入。

**速记**：状态要裁剪、转义后再嵌入标记，客户端只复现首屏所需的数据。
