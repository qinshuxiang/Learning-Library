## Service Worker：后台脚本的生命周期

### 事件驱动的后台模型

Manifest V3 的后台脚本是一个事件驱动的 Service Worker，它为响应事件而被启动、处理完毕后被浏览器终止，不再像 MV2 的 background page 那样常驻内存。

后台脚本的入口在清单的 background.service_worker 字段中声明，加 type 设为 module 后可用 import 语句拆分文件：

```json
{
  "background": {
    "service_worker": "service-worker.js",
    "type": "module"
  }
}
```

这个 Worker 没有页面依托，因此没有 DOM、没有 window、也没有 localStorage。它的职责是协调各上下文、处理跨域请求、管理持久状态与闹钟，以及承载所有需要在扩展生命周期外持续响应的监听器。

> [!NOTE]
> **提醒内容**：Service Worker 的 import 有两种可用形式：顶层 import 语句与 importScripts 方法。不支持动态 import()，需要按需加载模块时要改用消息触发另一段逻辑，而不是在后台里动态引入。



### 三种终止条件

Chrome 在满足下列任一条件时终止后台 Worker，终止对扩展代码是不可预期的，必须当作随时可能发生：

- 无操作满 30 秒。接收到事件或调用扩展 API 会重置这个计时器。
- 单个请求的处理时间超过 5 分钟。这里的请求指一次事件派发或一次 API 调用。
- fetch 请求的响应到达时间超过 30 秒。

被终止后，新的传入事件会把它重新唤醒。唤醒是一个重新执行整个脚本的过程，顶层代码会再跑一遍，但上一轮的内存状态不复存在。

> [!WARNING]
> **警告内容**：Service Worker 空闲 30 秒即被回收，任何依赖「后台一直挂着一个定时器或一个内存队列」的设计都会失效。每分钟执行一次以上的周期任务必须用 chrome.alarms，跨事件共享的数据必须落 chrome.storage，不能依赖模块级变量。



### 安装与启动的事件顺序

安装过程依次触发三个事件，顺序固定：

1. install：Service Worker 自身的标准事件。
2. chrome.runtime.onInstalled：扩展层面的安装事件。
3. activate：Service Worker 自身的标准事件。

chrome.runtime.onInstalled 在三种情况下都会触发，靠 details.reason 区分：首次安装是 install，扩展更新是 update，Chrome 本身升级是 chrome_update。用它对一次性初始化与迁移做分支处理：

```js
chrome.runtime.onInstalled.addListener((details) => {
  if (details.reason === 'install') {
    chrome.storage.local.set({ schemaVersion: 1, enabled: true });
  }
  if (details.reason === 'update' && details.previousVersion < '2.0.0') {
    migrateToV2();
  }
});
```

与 Web 平台的 Service Worker 不同，activate 在扩展安装后立即触发，因为扩展没有「页面重新加载」这个对应动作。个人资料启动时触发的是 chrome.runtime.onStartup，它不会调用任何 Service Worker 事件，因此它只在 Worker 因其他原因已经运行时才有机会被处理。



### 全局变量为什么不可靠

Worker 一旦被终止，所有全局变量与模块级变量全部丢失，下次唤醒时脚本从头执行，回到初始值。

因此状态只有两个可靠去处：需要跨重启保留的用 chrome.storage.local，只需在当前浏览器会话内保留的用 chrome.storage.session。Web Storage 在扩展 Service Worker 里不可用，localStorage 直接读取会报错。

```js
// 错误：SW 被回收后计数归零
let counter = 0;

// 正确：状态落在 storage，每次读回
const bumpCounter = async () => {
  const { counter = 0 } = await chrome.storage.local.get('counter');
  await chrome.storage.local.set({ counter: counter + 1 });
  return counter + 1;
};
```

需要缓存的昂贵初始化结果也适用同一规则。常见做法是在顶层启动一个 Promise 作为单次初始化闸门，但闸门本身只对当前这一次 Worker 存活期有效：

```js
let bootstrapPromise;

const bootstrap = () => {
  bootstrapPromise ??= (async () => {
    const { config } = await chrome.storage.local.get('config');
    return config ?? { schemaVersion: 1 };
  })();
  return bootstrapPromise;
};
```

chrome.storage 的四个区域、精确配额与可见性规则见第 8 篇《数据存储：chrome.storage》。



### 监听器必须在顶层同步注册

事件监听器必须在脚本顶层同步注册，不能放进异步回调、条件分支或事件处理函数内部。

原因是唤醒机制：Chrome 收到事件后启动 Worker 并执行顶层代码，靠这一轮同步执行收集到全部监听器，然后才把事件派发下去。若注册被 Promise 或 await 推迟到下一个微任务之后，本轮收集已经结束，事件找不到处理者而被丢弃，现象是「功能时好时坏，重启浏览器后第一次必失败」。

```js
// 正确：顶层同步注册
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  handleMessage(message).then(sendResponse);
  return true;
});

// 错误：注册被 await 推迟，唤醒时会漏掉事件
(async () => {
  const { options } = await chrome.storage.local.get('options');
  if (options.verbose) {
    chrome.tabs.onUpdated.addListener(logTabUpdate);
  }
})();
```

注册动作本身可以在顶层同步完成，监听器内部再按条件判断是否处理，这样既不丢事件，也能实现条件逻辑。

> [!CAUTION]
> **注意内容**：监听器内使用 sendResponse 进行异步回复时必须返回 true，否则消息通道会在处理函数返回时立刻关闭。返回 true 只是保持通道开启，真正的回复仍由 sendResponse 完成，二者缺一不可。



### 延长生命周期的机制

Chrome 陆续加入了若干保持 Worker 活跃或放宽超时的机制，各自有明确版本，支持低版本 Chrome 时不能假定它们存在：

- Chrome 105：使用 chrome.runtime.connectNative 连接原生消息宿主会使 Worker 保持活跃。宿主进程崩溃或关闭后端口断开，Worker 会在计时器走完时被终止，因此要在端口的 onDisconnect 里重新调用 connectNative。
- Chrome 109：从离屏文档发出的消息会重置空闲计时器。
- Chrome 110：扩展 API 调用会重置计时器。在此之前只有正在运行的事件处理函数才算「活跃」，已排队但尚未派发的事件不计入。
- Chrome 114：持久消息传递的端口保持 Worker 活跃，同时打开端口本身不再重置计时器。
- Chrome 116：活跃的 WebSocket 收发消息会重置空闲计时器；desktopCapture.chooseDesktopMedia、identity.launchWebAuthFlow、management.uninstall、permissions.request 四个需要用户操作的 API 允许突破 5 分钟超时。
- Chrome 118：chrome.debugger 创建的调试会话使 Worker 保持活跃。
- Chrome 120：闹钟周期下限对齐到 30 秒，可与 Worker 生命周期配合使用。

```js
// Chrome 105 起：原生消息端口保活，断开后重连
const port = chrome.runtime.connectNative('com.example.host');
port.onDisconnect.addListener(() => {
  chrome.runtime.connectNative('com.example.host');
});
```

> [!IMPORTANT]
> **重要内容**：不要为了省事让 Worker 长期常驻。官方明确建议避免无限期保活，因为常驻会持续占用内存与进程资源。只有消息端口、WebSocket、原生消息、调试会话这类确实需要持续收发的场景才值得保活，且要在断开时主动释放。



### 用 alarms 替代 setInterval

chrome.alarms 是扩展里唯一可靠的周期任务机制，需要 alarms 权限。它在 Worker 被回收后仍由浏览器维持，到点唤醒 Worker 执行回调。

chrome.alarms.create(name?, alarmInfo) 的第二个参数取 when 或 delayInMinutes 之一，再加可选的 periodInMinutes；重复闹钟只设 periodInMinutes 时，它同时充当首次延迟。

```js
chrome.alarms.create('refresh', { periodInMinutes: 30 });

chrome.alarms.onAlarm.addListener(async (alarm) => {
  if (alarm.name !== 'refresh') return;
  await refreshRemoteConfig();
});
```

几条必须记住的约束：

- 最短周期为 30 秒，delayInMinutes 或 periodInMinutes 小于 0.5 时不生效并给出告警；when 设成不足 30 秒后不告警，但实际仍要等满 30 秒。
- 未打包加载的扩展不受这一限制，因此开发期测不出周期问题，必须在打包后复测。
- 设备休眠期间闹钟不唤醒设备，唤醒后补响；重复闹钟最多补响一次，随后按周期从唤醒时刻重新排。
- 闹钟名自 Chrome 150 起强制 1024 字节上限，超长会抛 TypeError。
- persistAcrossSessions 属性自 Chrome 150 起可用，表示闹钟是否跨浏览器重启保留，Chrome 默认值为 true。

get、getAll、clear、clearAll 自 Chrome 91 起返回 Promise，create 自 Chrome 111 起返回 Promise，因此可以直接 await 使用。

> [!TIP]
> **建议内容**：每次 Service Worker 启动时都检查关键闹钟是否存在，缺失就补建。理由有两条：跨浏览器与 Chrome 150 之前没有 persistAcrossSessions，闹钟未必能存活到下次重启；扩展更新会重建 Worker，补建逻辑放在顶层执行成本极低，却能消除一整类「定时任务某天不再运行」的问题。



### 无 DOM 的能力缺口与 offscreen

Service Worker 没有 DOM，直接后果是若干只在文档环境里可用的能力缺失：剪贴板读写、音频播放、用 DOMParser 解析 HTML 字符串、URL.createObjectURL 处理 Blob、getUserMedia 取媒体流、以及 localStorage。

chrome.offscreen 用来补齐这些缺口，它自 Chrome 109 起可用，需要 offscreen 权限。离屏文档是一份与扩展同源的静态 HTML，创建后不会被聚焦，opener 恒为 null。

```js
await chrome.offscreen.createDocument({
  url: 'offscreen.html',
  reasons: ['CLIPBOARD'],
  justification: '把用户复制的内容写入系统剪贴板'
});
```

参数中 url 必须是打包内的静态页面，reasons 取 Reason 枚举值，justification 是给用户看的理由说明。Reason 的取值包括 TESTING、AUDIO_PLAYBACK、IFRAME_SCRIPTING、DOM_SCRAPING、BLOBS、DOM_PARSER、USER_MEDIA、DISPLAY_MEDIA、WEB_RTC、CLIPBOARD、LOCAL_STORAGE、WORKERS、BATTERY_STATUS、MATCH_MEDIA、GEOLOCATION。

reason 决定生命周期：AUDIO_PLAYBACK 在停止播放 30 秒后自动关闭文档，其余 reason 不设使用期限。一个已安装扩展同时只能打开一个离屏文档，无痕与常规个人资料在 split 模式下各算一个。runtime 是离屏文档支持的唯一扩展 API，其余能力全靠消息传回 Worker。

offscreen.hasDocument 自 Chrome 150 起可用；在此之前用 runtime.getContexts 传入 contextTypes 为 OFFSCREEN_DOCUMENT 来判断，Chrome 116 之前的版本只能退回到 clients.matchAll。离屏文档的完整用法与媒体捕获见第 14 篇《无 DOM 环境的能力补齐：offscreen 与媒体捕获》。



### 排查 Service Worker 意外常驻

意外常驻会让扩展持续占用内存，也可能掩盖状态设计缺陷。排查从三个入口入手：

- 扩展管理页点该扩展的「检查视图」，该窗口即 Worker 的 DevTools，可在 Performance 与 Memory 面板观察是否有长期不释放的句柄。
- chrome://serviceworker-internals 查看 Worker 的启停时间线，判断它是否在被反复唤醒或从未休眠。
- 代码侧排查保活源：是否有 open 后未断开的 runtime.connect 端口、未关闭的 WebSocket、未释放的 debugger 会话、未断开的原生消息端口。

最常见的误用是把 setInterval 放在顶层当作周期任务：它既不能跨越 Worker 回收，又会让 Worker 在处理期间无法正常休眠。周期任务一律改写成 chrome.alarms，单次延迟任务也优先用闹钟而不是 setTimeout。
