## 数据存储：chrome.storage

### storage 的定位

chrome.storage 是扩展专用的键值存储 API，按键保存 JSON 可序列化的值，供扩展的各个上下文读写。使用时在 manifest.json 里声明 storage 权限。

```json
{
  "manifest_version": 3,
  "name": "Reading Notes",
  "version": "1.0.0",
  "permissions": ["storage"]
}
```

它相对网页存储方案有几条固有特征：所有扩展上下文（含 Service Worker 与内容脚本）都能访问；API 全异步且支持批量读写；用户清除缓存与浏览记录不会影响其中的数据；拆分无痕模式下写入的设置仍然保留；另有一个只读的受管区域专供企业策略下发。



### 四个存储区域

storage 分四个区域，寿命、容量与用途各不相同。

- local：数据存在本机，随扩展卸载一起清除。适合放批量数据与需要长期保留的本地状态。
- sync：用户开启同步时随登录的 Chrome 一起同步；关闭同步时行为等同 local。适合放跨设备的用户设置。
- session（Chrome 102 起）：数据只保留在内存中，扩展被停用、重载、更新以及浏览器重启都会清空。适合放临时状态与敏感数据。
- managed：由管理员通过企业策略配置，对扩展只读，尝试写入会报错。

```js
await chrome.storage.local.set({ lastSyncAt: Date.now() });
const { lastSyncAt } = await chrome.storage.local.get(["lastSyncAt"]);

await chrome.storage.session.set({ authToken: token });
```



### 配额常量与超限行为

各区域公开的配额常量如下。

- local 的 QUOTA_BYTES 为 10485760 字节，即 10 MB，Chrome 113 及更早为 5 MB；声明 unlimitedStorage 权限后该值被忽略。
- session 的 QUOTA_BYTES 为 10485760 字节，即 10 MB，Chrome 111 及更早为 1 MB。
- sync 的 QUOTA_BYTES 为 102400 字节，即 100 KB；QUOTA_BYTES_PER_ITEM 为 8192 字节，即 8 KB；MAX_ITEMS 为 512 项；MAX_WRITE_OPERATIONS_PER_HOUR 为 1800 次；MAX_WRITE_OPERATIONS_PER_MINUTE 为 120 次。
- MAX_SUSTAINED_WRITE_OPERATIONS_PER_MINUTE 已弃用，sync 不再有持续写入配额。

字节数的计算口径是每个值的 JSON 字符串化长度加上键的长度，不是原始字符串的字节数。超限时写入立刻失败，不存在部分写入：回调式写法会设置 chrome.runtime.lastError，await 写法让 Promise 被拒绝。

```js
try {
  await chrome.storage.sync.set({ profile: buildProfileSummary() });
} catch (error) {
  console.warn("超出 sync 配额，降级写入 local", error);
  await chrome.storage.local.set({ profile: buildProfileSummary() });
}
```

> [!IMPORTANT]
> **重要内容**：sync 的 8 KB 单项上限与 512 项上限都是硬性上限，超限即抛错。该区域适合放设置项与轻量索引，不适合放大对象、日志或二进制数据的 base64 副本，后者应改用 local 并配合 unlimitedStorage 权限。



### 读写方法与变更监听

四个区域都实现 StorageArea 接口，方法签名一致。

- get(keys?)：读取一个或多个键，键可以是字符串、字符串数组或带默认值的对象。
- getKeys()：返回区域内的全部键。
- getBytesInUse(keys?)：返回占用的字节数。
- set(items)：批量写入，items 为键值对象。
- remove(keys)：删除指定键。
- clear()：清空整个区域。
- setAccessLevel(accessOptions)：设置该区域的访问级别。

```js
const defaults = { theme: "light", pageSize: 20 };
const settings = await chrome.storage.local.get(defaults);

await chrome.storage.local.set({ theme: "dark" });
await chrome.storage.local.remove(["pageSize"]);

const usedBytes = await chrome.storage.local.getBytesInUse();
```

变更监听用 chrome.storage.onChanged，回调签名为 (changes, areaName) => void。changes 是一个以键名为属性的对象，每一项含 oldValue 与 newValue 两个字段；areaName 是发生变更的区域名。

```js
chrome.storage.onChanged.addListener((changes, areaName) => {
  if (areaName !== "local") return;
  for (const [key, { oldValue, newValue }] of Object.entries(changes)) {
    console.log(key, "由", oldValue, "变为", newValue);
  }
});
```

该事件在写入完成后触发，本上下文自己发起的写入同样会收到通知，因此不能靠它判断变更来源。需要在回调里忽略自己刚写入的值时，在写入前记录本地版本号或时间戳，回调里比对后再决定是否重放逻辑。



### 访问级别与内容脚本可见性

setAccessLevel(accessOptions) 接收一个含 accessLevel 字段的对象（Chrome 102 起可用），取值来自 AccessLevel 枚举。

- TRUSTED_CONTEXTS：只有来源属于扩展自身的上下文可以访问。
- TRUSTED_AND_UNTRUSTED_CONTEXTS：来源在扩展外部的上下文同样可以访问。

三个区域的默认可见性并不一致：local、sync、managed 默认对内容脚本可见，session 默认不可见。要把 session 开放给内容脚本，需要显式调用一次。

```js
await chrome.storage.session.setAccessLevel({
  accessLevel: "TRUSTED_AND_UNTRUSTED_CONTEXTS",
});
```

> [!CAUTION]
> **注意内容**：把区域开放给内容脚本后，注入到任意匹配页面的扩展代码都能读到该区域的全部内容。网页虽不能直接访问，但通过页面与内容脚本之间的消息边界可以间接触达。令牌、密钥一类数据只留在 Service Worker 侧使用，不要为了省一次消息往返而放开访问级别。



### 配额管理与写入节流

getBytesInUse 用于在写入前估算余量，把配额判断放进写入路径可以在失败之前给出可读提示。

```js
const SYNC_SAFE_LIMIT = 90 * 1024;

async function saveSettingsSafely(settings) {
  const used = await chrome.storage.sync.getBytesInUse();
  const incoming = JSON.stringify(settings).length;
  if (used + incoming > SYNC_SAFE_LIMIT) {
    throw new Error("sync 余量不足，请先清理历史项");
  }
  await chrome.storage.sync.set({ settings });
}
```

sync 的写入次数按操作计数而不是按键计数：一次 set 写入十个键仍然只算一次操作。把多次修改合并成一次批量写，既降低写入频次，也减少同步往返。

> [!TIP]
> **建议内容**：高频变化的状态（滚动位置、输入草稿、心跳时间）先用内存变量累积，再按固定间隔或事件间隙合并成一次 set 写入。这样既避开 sync 的每分钟 120 次上限，也避免给存储层制造无意义的写放大。



### 与网页存储方案的取舍

localStorage 在扩展的 Service Worker 里不可用，这是 MV3 下无法绕过的限制。即使放在 popup 这类有 window 的上下文里可用，它也有两处不适用：内容脚本与宿主网页共享同一份 localStorage，写入会互相污染；用户清除浏览记录时数据会一并丢失。

IndexedDB 与 CacheStorage 容量更大，也没有单项与写入频次限制，适合结构化的大量记录与需要按索引查询的场景，代价是不参与跨设备同步，也不在 chrome.storage 的变更事件体系内。

选择的分界大致如此：设置项、轻量状态、需要跨设备或需要对内容脚本可见的数据放 chrome.storage；上百 MB 的缓存、二进制大对象与需要索引查询的记录放 IndexedDB；不需要跨会话的临时状态与敏感数据放 session。



### Service Worker 中的异步预加载

Service Worker 随时可能被终止，事件处理器里的代码不能假设全局变量已经初始化完毕。常用做法是在顶层启动一次读取并把结果 Promise 保存下来，在每个事件处理器的开头 await 它。

```js
const storageCache = {};

const initStorageCache = chrome.storage.local.get().then((items) => {
  Object.assign(storageCache, items);
});

chrome.action.onClicked.addListener(async (tab) => {
  try {
    await initStorageCache;
  } catch (error) {
    console.error("存储初始化失败", error);
  }
  storageCache.openCount = (storageCache.openCount ?? 0) + 1;
  await chrome.storage.local.set({ openCount: storageCache.openCount });
});
```

关键是 initStorageCache 在顶层同步创建。Service Worker 被唤醒后会重新求值顶层代码，于是自动重新发起一次读取；事件处理器只等待同一个 Promise，不必各自重复读写。

> [!NOTE]
> **提醒内容**：storage 是异步 API，一次 get 在 Service Worker 冷启动时可能耗时数十毫秒。事件处理器如果必须在读取完成后才能继续，就让 await 拦住后续逻辑，不要用同步的默认值先跑一遍再异步补正，否则会先写回一份错误结果。
