## 用户脚本与 chrome.userScripts

chrome.userScripts 是让扩展执行「不由扩展包提供、而由用户提供」的脚本的 API，Chrome 120 起在 MV3 下可用，权限为 userScripts，同时需要为要注入的站点声明 host 权限。

它解决的问题是：内容脚本与 chrome.scripting 注入的代码都必须是扩展包内的固定文件，而用户脚本管理器一类扩展拿到的是用户当场写下的任意代码，这些代码在扩展发布时并不存在。MV3 禁止远程托管代码，也不允许把字符串当代码执行，用户脚本 API 正是为这类扩展留出的合法出口。

### 与内容脚本的能力差别

内容脚本与用户脚本都运行在被注入的页面里，但授权路径、注入范围与信任级别都不同。

#### 定位与注入环境

内容脚本的注入范围由扩展在清单或注册调用中写死，脚本来源是包内文件，开发者对其行为负全责。用户脚本的范围同样由注册信息决定，但脚本内容是外部输入，设计上必须当作不可信数据对待。

执行环境上，内容脚本默认进入隔离世界，拿得到扩展 API 的一部分；用户脚本默认进入名为 USER_SCRIPT 的世界，这个世界是用户脚本独有的隔离环境，不受宿主页面 CSP 限制，网页与其它扩展都看不到它。需要直接改写页面框架内部状态时可切到 MAIN 世界，代价是脚本暴露给页面并受页面 CSP 约束。

注册脚本时至少要给出 id、matches 与 js 三项，js 是 ScriptSource 数组，每项用 file 指向包内文件或用 code 直接给出代码字符串，二者只能取其一。

```js
await chrome.userScripts.register([{
  id: 'highlight-keywords',
  matches: ['*://*.example.com/*'],
  excludeMatches: ['*://*.example.com/admin/*'],
  js: [{ code: 'document.body.style.outline = "1px solid red";' }],
  runAt: 'document_idle',
  world: 'USER_SCRIPT',
}]);
```



#### 消息通道与可信度区分

用户脚本与扩展其它部分的通信方式与内容脚本相同，都用 runtime.sendMessage 与 runtime.connect；差别在接收端：用户脚本的消息走专门的事件，不会进入普通的 onMessage 与 onConnect。

```js
chrome.userScripts.configureWorld({ messaging: true });

chrome.runtime.onUserScriptMessage.addListener((message, sender, sendResponse) => {
  if (message?.type !== 'save-note') return;
  saveNote(sender.tab?.id, String(message.text));
  sendResponse({ ok: true });
});
```

> [!NOTE]
> **提醒内容**：用户脚本的专用接收端是 Chrome 115 起提供的 runtime.onUserScriptMessage 与 runtime.onUserScriptConnect。这一隔离是刻意的：它让扩展能在同一处代码里区分「自己打包的内容脚本」与「用户临时写下的脚本」两种可信度完全不同的来源，而不必靠消息字段自行猜测。

消息通道默认关闭，必须先调用 configureWorld 并传入 messaging 为 true，用户脚本才能发消息。



### 权限与用户开关

除了在清单声明 userScripts 权限，这一 API 还有一道由用户掌握的运行时开关。缺少开关时，API 在扩展上下文里根本不存在。

#### 清单声明

用户脚本注册需在清单声明 userScripts 与 host 两项权限方可生效。

```json
{
  "manifest_version": 3,
  "name": "script-runner",
  "version": "1.0.0",
  "minimum_chrome_version": "120",
  "permissions": ["userScripts", "storage"],
  "host_permissions": ["*://*.example.com/*"],
  "background": { "service_worker": "service-worker.js" }
}
```

host_permissions 决定脚本能注入到哪些站点，注册时的 matches 必须落在 host 权限覆盖范围内，向未授权的站点注册不会生效。



#### 用户侧开关的两种形态

开关的形态随版本变化，扩展需要在运行时判断用哪一种。

```js
const version = Number(navigator.userAgent.match(/(Chrome|Chromium)\/([0-9]+)/)?.[2] ?? 0);

if (version >= 138) {
  // 使用扩展详情页上的「允许用户脚本」开关
} else {
  // 使用 chrome://extensions 顶部的「开发者模式」开关
}
```

Chrome 138 之前，用户必须开启开发者模式，扩展才能使用这一 API。Chrome 138 起，开关下移到每个扩展的详情页，用户打开 chrome://extensions/?id=扩展 ID 后可单独为此扩展打开「允许用户脚本」。

> [!IMPORTANT]
> **重要内容**：开关未打开时 chrome.userScripts 是 undefined，访问它会直接抛错；开关在 Service Worker 运行期间被撤销时，名称仍然存在，但调用任何方法都会抛错。因此可用性判断不能只看对象是否存在，必须尝试调用一次方法。



#### 可用性探测与降级提示

探测写法对全部版本通用，靠一次真实调用判断。

```js
function isUserScriptsAvailable() {
  try {
    chrome.userScripts.getScripts();
    return true;
  } catch {
    return false;
  }
}
```

探测结果为 false 时，扩展应把入口降级为一段说明文字，指引用户到扩展详情页打开开关，而不是把错误直接抛给用户。这一步无法由扩展代替，只能由用户完成。



### 执行世界与 configureWorld

用户脚本可以运行在两个世界里，世界的选择同时决定它能看到什么与受什么约束。USER_SCRIPT 是缺省值，也是隔离世界；MAIN 指页面自身的执行环境。

#### worldId 与独立的内容安全策略

Chrome 133 起，注册时可以额外给出 worldId，把脚本放进一个具名的子世界。具名世界彼此隔离，可以各配一套 CSP，让不同来源的用户脚本拥有不同的执行约束。

```js
await chrome.userScripts.configureWorld({
  worldId: 'trusted-scripts',
  csp: "script-src 'self' 'unsafe-eval'",
});

await chrome.userScripts.register([{
  id: 'helper',
  matches: ['*://*.example.com/*'],
  worldId: 'trusted-scripts',
  js: [{ code: 'window.__helperReady = true;' }],
}]);
```

configureWorld 接受 WorldProperties 三个字段：csp 指定该世界的内容安全策略，缺省时沿用隔离世界的 CSP；messaging 决定是否向该世界暴露消息传递接口，缺省为 false；worldId 指明要配置哪个世界，省略时配置默认的用户脚本世界。以单个下划线开头的 worldId 是保留值。

getWorldConfigurations 返回全部已注册的世界配置，resetWorldConfiguration 把某个世界恢复为默认配置，两者都自 Chrome 133 起提供。

> [!WARNING]
> **警告内容**：放宽 csp 只对 USER_SCRIPT 世界有效，对 MAIN 世界无效，因为 MAIN 世界受页面自身的 CSP 约束，扩展无法替页面松绑。在具名世界里写入 unsafe-eval 之前要确认该世界只会执行可信来源的脚本，用户提供的脚本应留在使用默认 CSP 的世界中。



### 注册、查询与注销

注册是这一 API 的主路径：脚本先注册，之后由浏览器在匹配页面加载时注入。getScripts 返回本扩展全部动态注册的用户脚本，可传 UserScriptFilter 的 ids 数组做筛选。

#### register 的字段约束

RegisteredUserScript 中，id 与 js 在注册时必填。id 不得以单个下划线开头，该前缀留给浏览器生成的脚本 id。matches 同样必填，excludeMatches、includeGlobs 与 excludeGlobs 用于缩小范围。runAt 缺省为 document_idle；allFrames 缺省为 false，即只注入顶层框架，开启后逐框架单独校验网址条件；world 缺省为 USER_SCRIPT；worldId 自 Chrome 133 起可用，且只在 world 省略或为 USER_SCRIPT 时有意义。

```js
const registered = await chrome.userScripts.getScripts({ ids: ['highlight-keywords'] });
console.log(registered[0]?.runAt, registered[0]?.matches);
```



#### unregister、update 与更新后的重建

unregister 省略参数时注销本扩展全部动态注册的脚本，给出 filter 时只注销匹配的部分。update 接收完整的 RegisteredUserScript 数组，并且只覆盖数组中显式给出的属性；只要有一条脚本在解析或文件校验阶段失败，或者给出的 id 找不到对应脚本，整批更新都不会生效。这种「全成或全不成」的行为适合把一批相关脚本作为整体升级。

```js
await chrome.userScripts.unregister({ ids: ['highlight-keywords'] });
await chrome.userScripts.update([{ id: 'highlight-keywords', js: [{ file: 'scripts/highlight-v2.js' }] }]);
```

扩展更新会清空已注册的用户脚本，注册信息不随更新保留。

```js
chrome.runtime.onInstalled.addListener(async (details) => {
  if (details.reason !== 'update') return;
  const { savedScripts = [] } = await chrome.storage.local.get('savedScripts');
  if (savedScripts.length > 0) await chrome.userScripts.register(savedScripts);
});
```

把用户写下的脚本正文与注册参数一并存进 chrome.storage，更新后按存储内容重建，是这一 API 的标准配套做法。onInstalled 在首次安装、扩展更新与 Chrome 更新三种情形下都会触发，只有 reason 为 update 时才需要重建。

> [!TIP]
> **建议内容**：注册与注销会立刻影响之后加载的匹配页面，但已经注入到现有页面里的脚本不会被撤回。用户改完脚本后除了重新注册，还应提示需要刷新页面才能看到效果，或由扩展主动调用 chrome.tabs.reload 完成这一动作。



### 一次性注入 execute 与 Chrome 149 的同步校验

chrome.userScripts.execute 自 Chrome 135 起提供，用于把脚本临时注入指定目标，不经过注册，因此不会留下持久的注入规则。

```js
const results = await chrome.userScripts.execute({
  target: { tabId: targetTabId, allFrames: false },
  js: [{ code: 'document.querySelectorAll("h2").length' }],
  world: 'USER_SCRIPT',
  injectImmediately: true,
});

const failure = results.find((item) => item.error);
if (failure) showEditorError(failure.error);
else console.log('标题数量：', results[0].result);
```

UserScriptInjection 的必填字段是 js 与 target。target 使用 InjectionTarget，其中 tabId 必填，可选 allFrames、frameIds 与 documentIds；allFrames 为 true 时不得同时指定 frameIds，documentIds 与 frameIds 也不能并存。injectImmediately 为 true 时脚本不等页面加载完成就注入，但脚本到达目标时页面可能已经加载完毕，因此它不构成时序保证。

返回的是 InjectionResult 数组，每项含 frameId、documentId，以及 result 或 error 中的一个，两者互斥。脚本求值为 Promise 时浏览器会等待它敲定，并把敲定值作为结果返回。Chrome 149 起，execute 会在注入之前同步校验脚本语法，并把诊断结果放进返回数组的 error 字段，语法有误时不再是一次静默失败的注入，扩展可以据此把可读的错误直接反馈给写脚本的用户。

> [!NOTE]
> **提醒内容**：一次性注入不会在扩展更新时被重建，也没有对应的查询接口，脚本被注入后的状态只存在于页面里。需要长期生效的脚本应走注册路径，execute 适合「用户按下按钮才跑一次」的场景。



### 与用户脚本管理器生态的关系

第三方用户脚本管理器在 MV3 下必须依赖这一 API 才能执行用户提供的代码。它们与普通扩展的差别在于：脚本正文由用户随时写入、随时修改，因此注册信息是动态的，扩展只提供运行时与编辑器。

这类扩展的典型架构是三段式：编辑与存储界面负责脚本正文与元数据的增删改查；Service Worker 负责读取存储、按变更重建注册，并在 onInstalled 的 update 分支恢复全部脚本；运行时通过消息把脚本需要的数据在页面与扩展之间搬运。

使用这一 API 而不自建执行环境，换来的是脚本进入独立世界、不污染页面全局、由浏览器统一管理注入时机，代价是必须让用户理解并手动打开那道开关。脚本能否注入同时取决于注册条件、host 权限与用户开关三关，逐层判断并给出明确的失败原因，是这类扩展与普通扩展在体验上最大的差别。
