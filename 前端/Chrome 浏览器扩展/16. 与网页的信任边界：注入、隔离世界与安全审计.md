## 与网页的信任边界：注入、隔离世界与安全审计

信任边界是扩展代码与网页代码之间的一条判定线，它规定哪些数据只能当作不可信输入、哪些能力只能在扩展侧调用。Chrome 的隔离世界让内容脚本与页面各自持有独立的 JavaScript 变量环境，但两者共享同一个 DOM、同处一个渲染进程，因此隔离世界解决的是命名冲突问题而不是安全问题。前半篇按开发者视角梳理必须守住的边界，后半篇按审计与取证视角说明如何判断一个扩展是否可信。

### 隔离世界的能力边界

内容脚本是注入网页但与网页脚本分属不同世界的脚本，它只被授予扩展 API 的一个子集，其余能力必须通过消息交给 Service Worker 代办。官方文档给出的可直接访问清单是 dom、i18n、storage、runtime.connect()、runtime.getManifest()、runtime.getURL()、runtime.id、runtime.onConnect、runtime.onMessage、runtime.sendMessage()，超出这份清单的 API 内容脚本都无法直接调用。

#### 隔离世界隔离了什么

隔离世界是一个专用执行环境，网页与其他扩展都无法访问该环境。它的实际效果是内容脚本里的 JavaScript 变量对宿主网页不可见，网页里的变量对内容脚本同样不可见，二者只能通过共享的 DOM 交换信息。这套机制最初是为了给浏览器标签页提供隔离而引入的。

```js
// 页面脚本执行过 window.greeting = "hello"，
// 内容脚本读到的仍是一个干净的作用域，拿不到页面的变量。
const submitButton = document.getElementById("submit-button");
submitButton.dataset.injectedBy = "extension";
console.log(typeof window.greeting); // "undefined"
```

隔离的是变量与函数作用域，不隔离的是 DOM、事件流、CSS 以及渲染进程本身。内容脚本改写的 DOM 会被页面脚本读到，页面脚本注册的事件监听器也会收到内容脚本派发的事件。



#### 隔离世界不等于沙箱

沙箱是清单中用 sandbox 键显式声明的页面，按政策要求扩展加载的远程代码只能运行在这类页面里。沙箱页面可以用 eval 与远程脚本，代价是完全拿不到扩展 API，只能靠消息与扩展的其它部分通信。

隔离世界与沙箱是两个不同维度的机制。隔离世界是上下文标记，页面脚本看不到内容脚本的变量；沙箱是内容安全策略层面的降级，代价是 API 被剥夺。内容脚本运行在网页所在的渲染进程里，一旦渲染进程被攻破，同一进程内的内容脚本与页面就没有硬隔离可言。

> [!WARNING]
> **警告内容**：隔离世界不是安全边界，不能把「变量互相看不见」当成「数据可信」。内容脚本与宿主页面共享 DOM、共享渲染进程、共享生命周期，任何从页面读到的字符串都必须按攻击者可控来对待，凭据与会话令牌一律只留在扩展侧。



### 内容脚本与页面世界的互操作

内容脚本与页面之间没有直接函数调用通道，唯一合法的通信路径是共享 DOM，常用做法是用 window.postMessage 在两侧传递消息。这条通道是双向开放的，页面上任何第三方脚本都能读写同一通道。

#### 页面消息通道的打开方式

网页侧调用 window.postMessage(message, targetOrigin) 把数据投递到自身窗口，内容脚本用 window 上的 message 事件接收。消息体应当是结构化的普通对象，并带一个自有的类型字段用于区分用途。

```js
const requestButton = document.getElementById("request-quote");

requestButton.addEventListener("click", () => {
  window.postMessage({ type: "FROM_PAGE", payload: "quote-42" }, "*");
});
```

网页无法主动向扩展发送消息，扩展也无法主动向网页发送消息，两侧都只能通过这条 DOM 通道中转。需要扩展响应网页请求时，由内容脚本接收后再用 runtime.sendMessage 转交给 Service Worker。



#### 页面消息通道的来源校验

内容脚本的 message 监听器收到的每一个事件都可能由页面上的任意脚本伪造，因此监听器必须先做三道判定：事件源必须是当前窗口，来源必须是当前页面自己的源，消息体必须通过形状与长度校验。这三道判定缺一不可，只判类型字段等于把入口交给攻击者。

```js
const PAGE_MESSAGE_TYPE = "FROM_PAGE";
const MAX_PAYLOAD_LENGTH = 128;

function isPagePayload(data) {
  return data !== null
    && typeof data === "object"
    && data.type === PAGE_MESSAGE_TYPE
    && typeof data.payload === "string"
    && data.payload.length <= MAX_PAYLOAD_LENGTH;
}

window.addEventListener("message", (event) => {
  if (event.source !== window) return;
  if (event.origin !== location.origin) return;
  if (!isPagePayload(event.data)) return;
  void chrome.runtime.sendMessage({ kind: "page-payload", text: event.data.payload });
});
```

校验通过之后仍然只允许做无特权动作。内容脚本能触发的特权操作范围应当被限制在最小集合内，例如只允许查询本地缓存、不允许携带页面数据发起任意跨域请求。



### 把页面数据写进 DOM 的风险

跨站脚本攻击是扩展最现实的代码执行面，它来自把不可信来源的数据当作标记语言解释。不可信来源包括用户输入、通过内容脚本读到的其它网站数据以及第三方接口返回的内容，这些数据一旦被当成 HTML 或代码执行，攻击者就在扩展的权限下获得执行机会。

```js
// 安全：以文本写入，页面数据只会成为文字节点。
function renderText(target, text) {
  target.textContent = text;
}

// 不安全：页面数据被当作标签解析，等于把页面的 XSS 面搬进扩展页面。
function renderHtml(target, html) {
  target.innerHTML = html;
}
```

同一条原则适用于消息通道：用 JSON.parse 处理响应文本不会执行攻击者的脚本，用 eval 或 new Function 处理响应文本就是在执行攻击者的脚本。选择不执行脚本的 API 是唯一可靠的做法。

> [!CAUTION]
> **注意内容**：扩展页面的默认内容安全策略已经禁掉内联脚本与 eval，但仍放开 innerHTML 一类不触发 CSP 的注入面。渲染任何来自页面、接口或用户的数据时，一律使用文本写入方式，需要富文本时先用白名单过滤再交给受控的渲染器。



### 消息入参的最小可信假设

消息是扩展内部和外部的统一输入口，最小可信假设指的是把所有进入监听器的参数都当作未经校验的外部输入。这条假设对内容脚本发来的消息同样成立，官方文档明确指出内容脚本的信任度低于 Service Worker，且要假设发往内容脚本的数据可能泄露给网页。

```js
const TRUSTED_EXTENSION_ID = "abcdefghijklmnoabcdefhijklmnoabc";

function readSearchKeyword(request) {
  if (typeof request !== "object" || request === null) return null;
  if (request.action !== "search") return null;
  if (typeof request.keyword !== "string") return null;
  const keyword = request.keyword.trim();
  if (keyword.length === 0 || keyword.length > 64) return null;
  return keyword;
}

chrome.runtime.onMessage.addListener((request, sender, sendResponse) => {
  const keyword = readSearchKeyword(request);
  if (keyword === null) return false;
  runSearch(keyword).then((hits) => sendResponse({ hits }));
  return true;
});

chrome.runtime.onMessageExternal.addListener((request, sender, sendResponse) => {
  if (sender.id !== TRUSTED_EXTENSION_ID) return false;
  const keyword = readSearchKeyword(request);
  if (keyword === null) return false;
  runSearch(keyword).then((hits) => sendResponse({ hits }));
  return true;
});
```

外部消息入口还有一层来源约束。清单中的 externally_connectable 决定哪些网页可以通过 runtime.sendMessage(extensionId, …) 与本扩展通信，扩展间通信则由 sender.id 做白名单判定；网页侧消息的 sender 带 url 字段，需要在监听器里比对允许列表。

> [!IMPORTANT]
> **重要内容**：内容脚本低信任度是官方文档的明确结论，恶意网页可能入侵运行内容脚本的渲染进程。凡由内容脚本消息触发的特权动作都要重新校验参数，并把可触发的动作范围收窄到必要集合；假设发往内容脚本的数据最终会泄露给网页，因此不要把凭据、令牌或内部状态经这条通道下发。



### 扩展页面自身的攻击面

扩展页面指 popup、options、side panel、新标签页替换页这类以 chrome-extension:// 开头的页面，它们运行在扩展源下并拥有完整的扩展 API。这类页面的默认内容安全策略等价于 script-src 'self'; object-src 'self';，即只从打包资源加载脚本与对象、禁用 WebAssembly、禁止内联脚本、禁止把字符串当作可执行代码求值。

Chrome 对扩展页面强制一条最低内容安全策略，等价于 script-src 'self' 'wasm-unsafe-eval'; object-src 'self';。这条最低策略意味着扩展页面的策略不能比它更宽松，例如往 script-src 里追加 'unsafe-eval' 会在安装时直接报错。WebAssembly 只有在声明了 wasm-unsafe-eval 之后才能使用。

因此扩展页面的 XSS 面不来自 CSP 绕过，而来自两类实现疏漏：一类是把不可信数据写进 innerHTML 或写入内联事件处理器，另一类是把页面数据当作模板交给动态代码执行。这两类都发生在 CSP 管辖不到的语义层面，只能靠代码规范约束。



### 从审计视角读权限清单

权限清单是判断扩展能力上限的第一手材料，读法是先把权限分成主机权限与 API 权限两组，再逐个回答「这个权限能不能被宣称功能解释」。主机权限决定扩展能读取和改写哪些站点的流量，API 权限决定扩展能触碰哪些浏览器数据，两组权限相乘才是真实能力。

审计时值得逐项确认的高价值权限包括：tabs 与主机权限共同决定标签页网址等字段是否可见，cookies 可读写站点 Cookie，webRequest 在 MV3 中退化为观察者，declarativeNetRequest 可按规则拦截与改写请求，debugger 可附加调试协议读取页面内部状态，nativeMessaging 可与本机程序通信，management 可枚举与操作其它扩展，proxy 可改写网络路径，downloads、bookmarks、history 分别触及下载记录、书签与浏览历史。

权限与功能是否匹配是审计的核心判断。商店政策要求申请实现功能所必需的最窄权限，若同一功能有多种权限可选则必须选数据或功能访问面最小的一种，并且不允许为尚未实现的功能预留权限。清单里出现与宣称用途无关的宽主机权限，或出现广泛主机权限叠加敏感执行权限的组合，都是需要追问的组合。



### 可网络访问资源与远程代码的攻击面

可网络访问资源是指声明为网页或其它扩展可以访问的扩展内置文件，默认情况下所有扩展资源都不可通过网络访问。官方文档给出的理由是恶意网站可以利用这类资源对用户已安装的扩展做指纹识别，或利用扩展自身漏洞实施注入。只有从扩展源加载的页面或脚本本来就能访问扩展资源，不需要额外放行。

```json
{
  "web_accessible_resources": [
    {
      "resources": ["assets/injector.css", "assets/spinner.svg"],
      "matches": ["https://portal.example.com/*"],
      "use_dynamic_url": true
    }
  ]
}
```

清单声明的写法是对象数组，每个对象必须包含 resources，并且必须包含 matches 或 extension_ids 之一。use_dynamic_url 为真时资源只能通过按会话生成的动态标识访问，浏览器重启或扩展重载后该标识重新生成，这可以削弱跨会话的指纹识别能力。声明范围越宽，可被网页探测到的表面越大。

> [!NOTE]
> **提醒内容**：资源被声明为可网络访问后会附带 CORS 响应头，任何匹配到该规则的网页脚本都能用 fetch 取到它，包括同一页面上的第一方与第三方脚本。审计时应核对声明的 matches 是否精确到必要来源，以及是否把源码、映射文件或内部配置一并暴露了出去。



### 远程代码禁令的判定口径

MV3 的远程代码禁令要求扩展的全部功能都能从提交的代码中辨别出来，各功能逻辑必须自包含。允许引用和加载扩展之外的数据与信息源，但这些外部资源不能承载任何逻辑，这一点把「取数据」和「取代码」明确分开。

按官方列举的常见违规形态，以下做法均在禁止之列：在页面里放入指向扩展包外资源的 script 标签；用 eval 或其它机制执行从远端取回的字符串；构建解释器来执行从远端取回的复杂命令，即使这些命令是以数据形式取回。允许的远程执行只有两条窄通道，即 debugger API 与 User Scripts API，豁免仅覆盖这两个 API 所涉及的那段代码。

与远端服务器通信本身仍然允许，例如同步账号数据、拉取用于 A/B 测试或功能开关的远端配置文件、拉取图片一类不参与逻辑求值的资源、以及用数据在服务端做运算。判定边界在于配置是否只影响分支选择，而不携带可执行逻辑。如果审核方无法确定扩展的完整功能，提交会被拒绝或商品会被下架。



### 更新通道与代码形态的风险信号

更新通道决定代码将来会变成什么，它是审计中容易被忽略的一环。商店分发走浏览器自动更新，签名的私钥决定谁能发布下一个版本；自托管分发需要在清单里写 update_url，只对 Linux 平台的用户可用，且新版本必须用与当前已安装版本相同的私钥签名；企业强制安装通道由管理员用 ExtensionInstallForcelist 一类的策略下发，用户无法停用或移除。权限一旦扩大、序列化格式一旦变更，都会沿这些通道在用户侧静默生效。

代码形态的风险信号按可信度从高到低排列如下。混淆代码是最强信号，商店政策明确禁止混淆或隐藏功能，只允许压缩这一种变形，具体包括移除空白与注释、缩短变量与函数名、合并文件；在混淆之上再叠加远程配置拉取，就等于把「提交时代码可读」这一点彻底架空。请求权限与宣称功能不匹配、发布前后功能发生实质变化、代码量巨大或结构难以审阅，都会显著拉长审核时间，也同样是审计时的重点。



### 机构与个人的限制手段

限制手段按主体分两类，机构侧依赖策略下发与私有分发通道，个人侧依赖浏览器界面上的开关与逐站点授权。两侧能覆盖的风险面不同，机构侧可以预先禁止安装，个人侧只能在安装后收窄权限或移除。

机构侧的可用策略包括：ExtensionInstallBlocklist 阻止指定扩展安装，ExtensionInstallAllowlist 放行指定扩展，ExtensionInstallForcelist 静默强制安装且用户无法停用，ExtensionInstallSources 限定扩展的安装来源，ExtensionAllowedTypes 限定可安装的扩展类型，ExtensionSettings 用一段 JSON 统一管理安装模式与按权限的封禁，BlockExternalExtensions 阻止从注册表等外部渠道装载扩展。管理员还可以用 Chrome 应用商店权限设置决定哪些店铺内容可见。

分发侧另有两条私有通道。网域发布只允许把扩展发布到本组织的专用商店，组织外无法查看，通过网域发布的扩展通常审核更快。向外部组织私有发布则面向被批准的外部组织，开发者先在账号页面生成审批链接，管理员在审批页确认发布者名称、联系邮箱与交易者披露信息后放行，之后在分发页面选择对应发布范围，扩展只对该组织可见。

个人侧的可用手段包括：在 chrome://extensions 中停用或移除扩展；用扩展详情里的站点访问权限把主机权限收窄为点击时、指定站点或所有站点；关闭开发者模式以阻止未打包扩展加载；在无痕模式下默认不加载扩展；安装前阅读权限告警与隐私披露。需要留意的是，浏览器界面上的开关只影响本机当前用户配置，无法阻止扩展在此前的运行期间已经写入的数据流出。

审计落到结论时，判断依据应当是权限清单、可网络访问资源声明、代码可读性与更新通道这四项的组合，而不是单一信号。宽权限可以合法存在，混淆代码也未必等于恶意，但多项信号同时出现时，扩展的实际风险就不再由它的宣称功能决定。

> [!TIP]
> **建议内容**：把四项依据整理成固定的取证清单再逐一核对顺序：先读权限与主机权限是否被宣称功能解释，再读可网络访问资源与沙箱页面的暴露面，接着确认代码是否可读、是否存在远端逻辑通道，最后确认更新通道与签名归属。固定顺序能避免被单一信号误导。
