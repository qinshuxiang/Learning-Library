## 网络请求与请求拦截

### 扩展上下文的跨源请求

每个扩展运行在自己的独立安全来源上。不申请任何主机权限时，扩展仍可以 fetch 安装包内的资源。

```js
const response = await fetch("/config_resources/config.json");
const config = await response.json();
```

请求扩展来源之外的地址时，这条请求按跨源处理，只有声明了目标主机的主机权限才会成功。

```json
{
  "host_permissions": [
    "https://www.example.com/",
    "https://*.example.com/"
  ]
}
```

主机权限按主机与方案分别授予，http 与 https 是两个独立的授权项，需要同时访问就都要写。主机之后的路径信息会被忽略，惯例用斜杠加星号占位。fetch 是 Service Worker 里唯一可用的请求 API，Service Worker 之外的扩展上下文还支持 XMLHttpRequest，新代码统一使用 fetch。



### 内容脚本的请求边界

内容脚本代表注入页面的来源发请求，因此始终受同源策略约束，即使扩展声明了该站点的主机权限也不改变。跨源取数只能绕开内容脚本，交给 Service Worker 执行。

```js
// 内容脚本侧：只传业务参数，不传完整网址
const price = await chrome.runtime.sendMessage({ type: "queryPrice", itemId });

// Service Worker 侧：由扩展凭主机权限发起跨源请求
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type !== "queryPrice") return;
  const endpoint = "https://api.example.com/price";
  const url = `${endpoint}?itemId=${encodeURIComponent(message.itemId)}`;
  fetch(url)
    .then((res) => res.json())
    .then((data) => sendResponse(data.price))
    .catch(() => sendResponse(null));
  return true;
});
```

> [!IMPORTANT]
> **重要内容**：让内容脚本提交完整网址、由 Service Worker 原样转发，等于把扩展的全部主机权限开放给任何能发消息的页面。请求地址应由扩展侧根据业务字段拼装，处理逻辑里不接受外部传入的网址或请求头。



### webRequest 在 MV3 中的定位

chrome.webRequest 在 MV3 中仍然可用，但它已经从可拦截的执行者退化为观察者：注册阻塞式处理脚本所需的 webRequestBlocking 权限自 MV3 起只适用于通过政策安装的扩展，普通扩展只能用它的信息性事件。

使用它需要同时声明 webRequest 权限与所需的主机权限，并且只能看到扩展有权限查看的请求。事件按请求生命周期排列：onBeforeRequest 在建立 TCP 连接之前触发，onBeforeSendHeaders 在初始请求头就绪时触发，onHeadersReceived 在每次收到响应头时触发，onCompleted 在请求成功后触发，onErrorOccurred 在请求失败时触发。对每个请求，onCompleted 与 onErrorOccurred 中必定有一个作为最后事件触发。

需要真正改动请求或响应时，改用 declarativeNetRequest。



### declarativeNetRequest 的三类规则集

declarativeNetRequest 让扩展用声明式规则描述拦截与修改，由浏览器在网络栈里执行，扩展代码不参与每一次请求。规则集分三类，生命周期各不相同。

- 静态规则集：打包进扩展，在安装或升级时按文件更新，用于固定的规则集合。
- 动态规则集：由扩展在运行期用 updateDynamicRules 管理，跨浏览器会话与扩展升级保留。
- 会话级规则集：由扩展在运行期用 updateSessionRules 管理，浏览器关闭或安装新版本扩展时清除。

清单里只需要列出静态规则集文件，权限按需要选择。

```json
{
  "declarative_net_request": {
    "rule_resources": [
      { "id": "ruleset_ads", "enabled": true, "path": "rules/ads.json" },
      { "id": "ruleset_trackers", "enabled": false, "path": "rules/trackers.json" }
    ]
  },
  "permissions": ["declarativeNetRequest"],
  "host_permissions": ["https://*.example.com/*"]
}
```

声明权限有两条路线：declarativeNetRequest 在安装时触发权限警告，但隐式提供 block、allow、allowAllRequests 三类规则所需的访问权；declarativeNetRequestWithHostAccess 不显示警告，但必须先取得目标主机的主机权限才能对其生效。两者功能一致，差别只在权限何时被请求。调试时另加 declarativeNetRequestFeedback 权限，它只为未打包扩展开启 getMatchedRules 与 onRuleMatchedDebug。

动态规则集的增删走一次调用，用 removeRuleIds 与 addRules 成对描述。

```js
await chrome.declarativeNetRequest.updateDynamicRules({
  removeRuleIds: [1001],
  addRules: [
    {
      id: 1001,
      priority: 2,
      action: { type: "block" },
      condition: { urlFilter: "||tracker.example.com^" },
    },
  ],
});
```



### 规则结构与数量上限

每条规则四个字段：id 为大于等于 1 的唯一数字；priority 为可选数字，默认 1，指定时必须大于等于 1；action 描述命中后的操作；condition 描述触发条件。

```json
{
  "id": 1,
  "priority": 1,
  "action": { "type": "block" },
  "condition": {
    "urlFilter": "||ads.example.com^",
    "resourceTypes": ["script", "image"]
  }
}
```

各类规则集的数量上限如下。

- 静态规则集最多声明 100 个，同时最多启用 50 个，即 MAX_NUMBER_OF_ENABLED_STATIC_RULESETS；Chrome 120 之前这两个数字分别是 50 与 10。
- 静态规则保证至少 30000 条可用，即 GUARANTEED_MINIMUM_STATIC_RULES。
- 会话规则上限 5000 条，即 MAX_NUMBER_OF_SESSION_RULES。
- 动态规则中的安全规则自 Chrome 121 起上限提升到 30000 条，即 MAX_NUMBER_OF_DYNAMIC_RULES；不安全规则至少 5000 条，即 MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES。Chrome 120 之前动态规则与会话规则合计只有 5000 条。
- 需要停用的静态规则最多 5000 条。

安全规则指 action 为 block、allow、allowAllRequests 或 upgradeScheme 的规则，这几类享受提高后的动态配额。正则规则另有独立上限：每种类型合计不超过 1000 条，即 MAX_NUMBER_OF_REGEX_RULES，且单条规则编译后必须小于 2 KB，超限时未打包扩展会收到告警并忽略该规则。

> [!CAUTION]
> **注意内容**：规则超出上限时 updateDynamicRules 与 updateSessionRules 整体失败，不会部分生效，已有规则保持不变。批量更新前先用 getAvailableStaticRuleCount() 或已用条数估算余量，不要假设单条规则一定会被接受。



### 匹配条件与 urlFilter 语法

condition 里常用的键如下。

- urlFilter：按网址模式匹配，与 regexFilter 二选一。
- regexFilter：按 RE2 语法做正则匹配，必须全部由 ASCII 字符组成。
- isUrlFilterCaseSensitive：是否区分大小写，默认 false。
- resourceTypes 与 excludedResourceTypes：按资源类型过滤。allowAllRequests 规则必须指定 resourceTypes，且只能含 main_frame 与 sub_frame。
- requestMethods 与 excludedRequestMethods：限定请求方法，Chrome 91 起可用；指定它会同时排除非 http 与 https 的请求。
- initiatorDomains 与 excludedInitiatorDomains：匹配发起请求的域名而非请求网址自身的域名，Chrome 101 起可用，取代此前的 domains 与 excludedDomains。
- requestDomains 与 excludedRequestDomains：匹配请求网址自身的域名，同样自 Chrome 101 起可用。
- domainType：取 firstParty 或 thirdParty。
- tabIds 与 excludedTabIds：按标签页限定，Chrome 92 起可用，仅会话级规则支持。
- responseHeaders 与 excludedResponseHeaders：Chrome 128 起可用。
- topDomains 与 excludedTopDomains：匹配顶层框架的域名，Chrome 145 起可用。

urlFilter 由四类记号组成：星号是通配符，匹配任意长度字符；竖线是左右锚点，写在模式两端分别表示网址的开头与结尾；双竖线是域名锚点，写在开头表示网址的域名起点；脱字符匹配分隔符，指除字母、数字以及下划线、连字符、句点、百分号之外的任意字符，同时也匹配网址末尾。

不允许写成双竖线紧跟星号的组合，需要该语义时直接写星号。urlFilter 与 regexFilter 都不能是空串，省略 urlFilter 即匹配所有网址。两者都只能由 ASCII 字符组成。

> [!NOTE]
> **提醒内容**：regexFilter 使用 RE2 语法，不支持回溯引用与环视。国际化域名在匹配前会被转换成 Punycode，其它非 ASCII 字符按 UTF-8 做网址编码，因此规则里不能直接写中文路径，要写成编码后的形式。



### 动作类型与优先级

action 的 type 取以下六种之一。

- block：屏蔽网络请求。
- redirect：重定向网络请求，redirect 字段可指定 url、extensionPath、transform 或 regexSubstitution。
- allow：允许请求，命中后该请求不再被本扩展拦截。
- allowAllRequests：允许框架层级中的全部请求，含框架请求自身，必须配合 resourceTypes 使用。
- upgradeScheme：把 http 或 ftp 网址升级为 https。
- modifyHeaders：修改请求头或响应头，用 requestHeaders 与 responseHeaders 字段描述改动。

```json
{
  "id": 2,
  "priority": 1,
  "action": {
    "type": "modifyHeaders",
    "requestHeaders": [
      { "header": "user-agent", "operation": "set", "value": "SiteAudit/1.0" }
    ]
  },
  "condition": {
    "urlFilter": "||api.example.com^",
    "resourceTypes": ["xmlhttprequest"]
  }
}
```

同一扩展内的多条规则同时命中时，先按 priority 排序；priority 相同时按动作排序，顺序为 allow 与 allowAllRequests 高于 block，block 高于 upgradeScheme，upgradeScheme 高于 redirect。多个扩展都想处理同一个请求时，跨扩展的排序是 block 高于 redirect 与 upgradeScheme，这两者又高于 allow 与 allowAllRequests；同类型规则取最近安装的那个扩展。

> [!WARNING]
> **警告内容**：动作相同且优先级相同的规则之间，执行顺序没有标准化，规范不做保证。需要依赖先后顺序的规则必须显式写出不同的 priority，否则换一个浏览器版本或换一个安装顺序就可能得到不同结果。

modifyHeaders 的改动分 set、remove、append 三种操作。append 只对一份固定白名单内的请求头生效，包括 accept、accept-encoding、accept-language、cache-control、cookie、user-agent 等，且白名单区分大小写。



### 规则验证与调试

规则命中情况用两个方法核对。getMatchedRules 列出当前标签页内已经命中的规则，需要 declarativeNetRequestFeedback 权限且仅对未打包扩展可用；testMatchOutcome 接收一组假设的请求参数，返回哪些规则会命中，Chrome 103 起可用。

```js
const outcome = await chrome.declarativeNetRequest.testMatchOutcome({
  url: "https://cdn.ads.example.com/banner.png",
  type: "image",
  initiator: "https://news.example.com",
  method: "get",
});

if (outcome.matchedRules.length === 0) {
  console.warn("规则未命中，检查 resourceTypes 与优先级");
}
```

规则文件的错误提示只在以未打包方式加载扩展时给出，打包后的扩展里无效的静态规则会被直接忽略。改完规则文件要重新加载扩展，再在 chrome://extensions 的错误面板里看告警。

> [!TIP]
> **建议内容**：动态与会话规则在调试期反复调参，比反复重载静态规则文件快得多。先用 updateSessionRules 把规则调通，确认 condition 与 priority 的行为符合预期，再把已经稳定的部分固化进静态规则文件。

declarativeNetRequest 的作用范围有明显边界：它只作用于到达网络栈的请求，不影响 Service Worker 的 onfetch 处理程序生成的响应，也不影响从 CacheStorage 取出的响应，但会影响 Service Worker 内发起的 fetch 调用；规则同样不能把请求重定向到未声明为网络可访问资源的扩展内文件。

这些边界决定了广告拦截类扩展的能力上限：请求在到达扩展规则之前就由缓存满足的部分拦不住，页面内脚本自己拼装并注入的内容同样拦不住，规则总数还受静态、动态、会话三套配额与正则条数上限的共同约束。
