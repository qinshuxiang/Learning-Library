## 测试与工程实践

### React 组件测试的定位

组件测试验证的是用户看到什么、操作后发生什么，而不是组件内部调用了哪些函数。本节先确定测试边界与职责划分。

> 测试体系、运行器配置、覆盖率与端到端测试归 前端/测试 主题，详见该主题第 2 篇 测试工具链与运行器选型；本篇只讲 React 特有的查询、事件与 Hook 测试，示例中的 vi 与 expect 由测试运行器提供。

#### 测行为而非实现的原则

**行为测试（behavior testing）**：是以用户可观察的输入与输出为断言对象的测试方式，输入是点击、输入文字等交互，输出是渲染出的文本、可访问状态与回调结果。**实现测试（implementation testing）**：是断言组件内部结构、state 取值或私有函数的测试方式，组件一重构即失效。

- 断言点落在渲染结果与回调调用上，重构内部实现不影响测试。
- 不直接读写组件的 state，不依赖组件内部函数名与变量名。
- 测试名描述用户场景，不描述内部方法。

```jsx
import { render, screen } from "@testing-library/react";

test("显示传入的标题", () => {
  render(<ArticleCard title="React 状态管理" />);
  expect(screen.getByText("React 状态管理")).toBeInTheDocument();
});
```

> 判断一条断言是否属于实现测试，可以问：把组件内部的 useState 换成 useReducer，这条断言需要改吗？需要改就说明它依赖了实现。

**速记**：断言渲染结果与交互结果，不断言内部 state 与函数名。



#### 单元与集成测试在 React 中的落点

**组件单元测试**：是只渲染一个组件或一个自定义 Hook、其余依赖用替身替代的测试。**组件集成测试**：是渲染若干真实子组件、只替换网络与路由等边界的测试。

- 单元落点：纯展示组件、格式化函数、自定义 Hook 的返回值。
- 集成落点：表单提交、列表增删、跨组件的状态流转。
- 比例建议：以集成测试为主，关键工具函数补单元测试，端到端只覆盖主流程（详见 前端/测试 主题第 13 篇 端到端测试：Playwright）。

> 组件测试的粒度由「一次渲染覆盖多少真实代码」决定，粒度粗细比数量多少更能决定测试价值。

**速记**：纯展示与 Hook 走单元，表单与状态流转走集成，端到端只保主流程。



#### 什么不该写组件测试

**不该写组件测试的内容**：是那些由上游库、框架或样式负责、重复断言只会增加维护成本的命题。

- 第三方库行为：路由、日期库、请求库已由上游测试覆盖，重复断言只会随版本升级而失败。
- 纯结构与样式：断言 class 名或 DOM 层级会在改样式时必然失败。
- 框架自身保证：不要断言 useState 会触发重新渲染这类框架层面的行为。
- 数字目标：为凑覆盖率写的空断言不提升信心（详见 前端/测试 主题第 12 篇 覆盖率与测试报告）。

> 排除这些内容不是降低标准，而是把维护预算集中到本项目的业务逻辑上。

**速记**：上游库行为、纯结构与样式、框架保证、覆盖率数字都不写组件测试。



### React Testing Library 与查询

React Testing Library 是 @testing-library/react 提供的渲染与查询工具集，它按用户可感知的方式定位元素，而不是按组件结构定位。

#### render 与 screen

**render**：是渲染 React 元素到测试 DOM 的函数，签名是 render(ui, options)，ui 为待渲染的 React 元素，options 可含 wrapper、container、baseElement 等字段，返回值含 container、rerender、unmount、asFragment 等成员。**screen**：是绑定当前 document.body 的查询对象，提供全部查询方法。

- rerender(ui)：用新的 props 重新渲染同一棵树，用于验证更新行为。
- unmount()：卸载组件，用于触发清理函数并断言清理结果。
- screen：查询范围是整份文档，不必从 render 的返回值上取查询方法。

```jsx
import { render, screen } from "@testing-library/react";

test("重新渲染后标题更新", () => {
  const { rerender } = render(<ArticleCard title="初稿" />);
  expect(screen.getByText("初稿")).toBeInTheDocument();

  rerender(<ArticleCard title="终稿" />);
  expect(screen.getByText("终稿")).toBeInTheDocument();
});
```

> 渲染前不需要手工创建容器，render 会把组件挂到 document.body 内的容器中，并在用例结束后自动清理。

**速记**：render 返回 rerender 与 unmount，查询统一从 screen 取。



#### 按角色与文本查询优先

**优先级查询**：是按用户感知顺序排列的查询方法序列，从 getByRole、getByLabelText、getByText 到 getByTestId 依次降低。

- getByRole(role, options)：按可访问角色定位，options 可用 name 过滤可访问名称。
- getByLabelText(text)：按关联的表单标签文本定位，适合输入框。
- getByText(text)：按可见文本定位，适合按钮与段落。
- getByTestId(id)：按 data-testid 定位，作为无法从用户视角区分时的兜底。

```jsx
test("登录表单可被填写", () => {
  render(<LoginForm onSubmit={vi.fn()} />);

  const emailInput = screen.getByLabelText("邮箱");
  const submitButton = screen.getByRole("button", { name: "登录" });

  expect(emailInput).toBeVisible();
  expect(submitButton).toBeEnabled();
});
```

> [!TIP]
> **建议内容**：优先用角色与标签查询，能顺带约束组件的可访问性；把 getByTestId 留给实在无法从用户视角区分的元素。

**速记**：查询按角色、标签、文本、测试 id 的优先级选择。



#### getBy、queryBy 与 findBy 的差别

三种前缀查询的差别集中在「找不到元素时的行为」这一条上，按断言对象选择即可：

- getBy：同步查询，找到返回元素，找不到直接抛错，用于断言元素存在。
- queryBy：同步查询，找不到返回 null，用于断言元素不存在。
- findBy：返回 Promise，默认在超时前轮询直到元素出现，用于断言异步出现。
- 成组对应：getByRole、queryByRole、findByRole 共用同一套参数。

```jsx
test("加载态结束后显示列表", async () => {
  render(<TodoList />);

  expect(screen.queryByRole("list")).toBeNull();
  expect(await screen.findByRole("list")).toBeInTheDocument();
});
```

> [!NOTE]
> **提醒内容**：断言元素不存在只能用 queryBy，用 getBy 会在元素缺失时抛错，失败原因指向查询本身而不是断言意图。

**速记**：getBy 抛错、queryBy 返回 null、findBy 返回 Promise 并轮询等待。



#### 测试可访问性的副产品

**可访问性（accessibility）**：是组件对辅助技术的可用程度，由角色、名称、标签等语义信息决定。按角色与标签查询会把可访问性要求固化成测试断言。

- 语义匹配：无角色的可点击元素无法通过 getByRole 的 button 找到，测试直接失败。
- 名称约束：可访问名称缺失时，getByRole 的 name 选项无法匹配。
- 复用成本低：这批断言在引入自动化可访问性检查后可继续使用。

```jsx
function SubmitButton({ onSubmit }) {
  return <button type="submit" onClick={onSubmit}>提交</button>;
}
```

> 把视觉上像按钮的元素写成 button，既满足可访问性，也免去为测试额外添加 data-testid。

**速记**：按角色与标签查询等价于顺带执行一轮轻量可访问性检查。



### 事件与异步断言

交互测试要先触发事件，再等待 React 完成状态更新，最后断言 DOM 结果。本节讲事件触发方式、更新包裹与等待时机。

#### fireEvent 与 userEvent 的差别

**fireEvent**：是同步派发单个 DOM 事件的工具，签名是 fireEvent.click(element, init)，调用后立即触发一次事件。**userEvent**：是模拟完整用户交互的库，先调用 userEvent.setup() 得到 user 对象，再用 user.click(element)、user.type(element, text) 等方法，内部包含焦点移动与指针事件序列。

- 调用方式：fireEvent 为同步函数；userEvent 的方法返回 Promise，需要 await。
- 交互真实度：userEvent 先聚焦元素再触发 pointer 与 mouse 事件序列，更接近真实操作。
- 选择建议：新测试统一用 userEvent，仅在需要精确控制底层事件时用 fireEvent。

```jsx
import userEvent from "@testing-library/user-event";

test("输入关键词后清空", async () => {
  const user = userEvent.setup();
  render(<SearchBar />);

  const input = screen.getByRole("textbox");
  await user.type(input, "hooks");
  expect(input).toHaveValue("hooks");

  await user.clear(input);
  expect(input).toHaveValue("");
});
```

> [!WARNING]
> **警告内容**：userEvent 的方法都是异步的，漏写 await 会让断言在状态更新之前执行，表现为随机失败。

**速记**：fireEvent 同步派发单事件，userEvent 用 setup 后逐个 await，更接近真实交互。



#### act 与更新包裹

**act**：是 React 提供的测试工具，签名是 act(callback)，用于把会触发状态更新的代码包起来并等待更新完成，返回 callback 的返回值，异步 callback 时返回 Promise。

- 必要场景：手工调用 store 方法、推进定时器或调用自定义 Hook 返回的函数后，需要等待 React 完成更新。
- 自动包裹：RTL 的 render、fireEvent 与 userEvent 内部已用 act 包裹，常规写法不需要手写。
- 常见提示：更新未被 act 包裹时，RTL 会在控制台打印告警，指明该更新发生在 act 之外。

```jsx
import { act } from "react";
import { renderHook } from "@testing-library/react";

test("手动递增触发更新", () => {
  const { result } = renderHook(() => useCounter());

  act(() => {
    result.current.increment();
  });

  expect(result.current.count).toBe(1);
});
```

> act 不改变代码行为，只负责通知 React 这批更新已经结束，便于把断言放在确定的状态上。

**速记**：会触发状态更新的手工调用放进 act，RTL 的渲染与事件方法已自带包裹。



#### waitFor 与 findBy 的等待时机

**waitFor**：是轮询等待断言通过的工具，签名是 waitFor(callback, options)，options 可含 timeout 与 interval，callback 在超时前被反复执行，直到不再抛错。

- 选择顺序：只等某个元素出现用 findBy；要等多条断言同时成立才用 waitFor。
- 超时参数：默认超时约一千毫秒，网络类场景可在单条断言上调大。
- 反模式：不要在 waitFor 内写副作用代码，callback 可能被执行多次。

```jsx
test("提交后提示保存成功", async () => {
  const user = userEvent.setup();
  render(<SettingsForm />);

  await user.click(screen.getByRole("button", { name: "保存" }));

  await waitFor(() => {
    expect(screen.getByText("保存成功")).toBeInTheDocument();
    expect(screen.getByRole("button", { name: "保存" })).toBeEnabled();
  });
});
```

> 出现间歇失败时先怀疑等待不充分，再检查断言是否写在了网络响应到达之前。定时器与异步控制的细节详见 前端/测试 主题第 9 篇 异步测试与定时器控制。

**速记**：单个元素出现用 findBy，多条断言同时成立用 waitFor，callback 必须无副作用。



#### 断言 DOM 变化与禁用态

交互结束后要断言的是用户可见的变化，常见变化有内容、可用性、可见性与存在性四类：

- 文本变化：断言查询结果的内容，而不是先取元素再比较内部字段。
- 可用性变化：用 toBeDisabled 与 toBeEnabled 断言表单控件的状态。
- 可见性变化：用 toBeVisible 断言元素是否对用户可见，比检查样式属性稳定。
- 移除断言：元素消失时用 queryBy 加 toBeNull。

```jsx
test("提交中禁用按钮", async () => {
  const user = userEvent.setup();
  render(<LoginForm onSubmit={() => new Promise(() => {})} />);

  await user.click(screen.getByRole("button", { name: "登录" }));
  expect(screen.getByRole("button", { name: "登录中" })).toBeDisabled();
});
```

> 上述匹配器由 @testing-library/jest-dom 提供，需在测试启动文件中注册一次。

**速记**：文本、可用性、可见性、移除四种变化各选对应匹配器断言。



### Hook 与自定义 Hook 的测试

Hook 不能脱离组件调用，测试时需要一个最小宿主组件。RTL 提供 renderHook 生成这个宿主，本节讲它的用法与配套约定。

#### renderHook 的签名与 act 的配合

**renderHook**：是渲染测试用宿主组件并执行 Hook 的函数，签名是 renderHook(callback, options)，callback 为调用目标 Hook 的函数，options 可含 initialProps 与 wrapper，返回值含 result、rerender、unmount 等成员。

- result：持有 Hook 最近一次渲染的返回值，用 result.current 读取。
- rerender(newProps)：用新的 props 重新执行 callback，验证 props 变化后的行为。
- unmount()：卸载宿主组件，用于触发清理函数。
- 配合原则：任何会让 Hook 更新 state 的调用都放进 act。

```jsx
test("useCounter 从初始值开始", () => {
  const { result } = renderHook(() => useCounter(5));

  expect(result.current.count).toBe(5);
});
```

> renderHook 只是把 Hook 放进一个不渲染任何内容的宿主组件，测试的仍是 Hook 自身的逻辑。

**速记**：renderHook 接收 callback 与 options，返回 result、rerender 与 unmount。



#### 用 result.current 读写返回值

**result.current**：是 Hook 最近一次渲染返回值的快照，每次重新渲染后更新；调用 Hook 返回的函数不会自动触发更新，需要在 act 中执行并重新读取。

- 读值：断言 result.current 上的字段。
- 写值：在 act 内调用 result.current 上的函数。
- 时序：act 返回之后，result.current 才是更新后的值。
- 陷阱：把 result.current 存进局部变量后，重新渲染不会更新该变量。

```jsx
test("切换开关状态", () => {
  const { result } = renderHook(() => useToggle(false));

  expect(result.current.on).toBe(false);

  act(() => {
    result.current.toggle();
  });

  expect(result.current.on).toBe(true);
});
```

> 断言前重新读取 result.current，不要在测试开头把它解构保存。

**速记**：result.current 是最近一次渲染的返回值快照，更新后必须重新读取。



#### 用 wrapper 提供 Provider 并验证清理

**wrapper**：是 renderHook 与 render 的 options 字段，值为接收 children 的组件，用于在 Hook 外层提供必需的 Provider 与 Context。

- 写法：options 传 { wrapper: createWrapper(store) }，createWrapper 返回包好 Provider 的组件。
- 必要性：Hook 依赖 Redux store 或 Context 时，缺少 wrapper 会直接报错。
- 清理验证：涉及订阅与定时器的 Hook 用 unmount 触发清理，再断言不再继续推进或调用。

```jsx
function createWrapper(store) {
  return function Wrapper({ children }) {
    return <Provider store={store}>{children}</Provider>;
  };
}

test("useUserProfile 在 Provider 下读取用户", () => {
  const store = configureStore({ reducer: { user: userReducer } });
  const { result } = renderHook(() => useUserProfile(1), {
    wrapper: createWrapper(store),
  });

  expect(result.current.displayName).toBe("Ada Lovelace");
});
```

```jsx
test("useInterval 卸载后停止推进", () => {
  vi.useFakeTimers();
  const { result, unmount } = renderHook(() => useInterval(1000));

  act(() => {
    vi.advanceTimersByTime(3000);
  });
  expect(result.current.ticks).toBe(3);

  unmount();
  act(() => {
    vi.advanceTimersByTime(3000);
  });
  expect(result.current.ticks).toBe(3);

  vi.useRealTimers();
});
```

> 清理函数是 Hook 正确性的一半：订阅、定时器与请求在卸载后仍运行会造成内存泄漏与状态串写。

**速记**：wrapper 为 Hook 提供 Provider，unmount 后断言清理函数确实生效。



### 项目结构与工程约定

React 项目没有强制的目录结构，但团队需要一套共同约定，让新增文件的位置与命名可以预测。本节给出常见的组织方式与配套的自动化约束。

#### 按功能分目录与按类型分目录

**按类型分目录**：是按文件职责建立 components、hooks、utils 等顶层目录。**按功能分目录**：是按业务域建立 features 目录，每个功能自带组件、Hook 与状态切片。

- 按类型：目录浅、同类文件集中，文件数量增长后定位成本上升。
- 按功能：改动集中在单个目录内，适合多人并行与按域拆分。
- 混合做法：通用组件与工具留在类型目录，业务代码按功能组织。

```text
src/
  components/
    Button.jsx
  features/
    todo/
      TodoList.jsx
      useTodoFilter.js
      todosSlice.js
  hooks/
    useInterval.js
```

> 目录结构服务于查找与改动范围，判断标准是「改一个功能需要打开哪几个目录」，而不是哪种方案更流行。

**速记**：目录按类型集中、按功能隔离，混合使用最实用。



#### 组件、Hook 与工具函数的归置

三类文件的归置遵循同一条思路：按复用范围决定位置。

- 组件：一个文件导出一个主组件，文件名与组件名一致，用大驼峰。
- 自定义 Hook：以 use 开头，放在被复用的功能目录或 hooks 目录，返回对象便于后续扩展字段。
- 纯函数：与 React 无关的格式化与校验放进 utils，便于单独测试。
- 子组件：只被一个组件使用的子组件留在同一目录，不急于提升到公共目录。

```jsx
// features/todo/useTodoFilter.js
function useTodoFilter(items, filter) {
  return useMemo(
    () => items.filter((todo) => (filter === "all" ? true : todo.status === filter)),
    [items, filter]
  );
}

export default useTodoFilter;
```

> 归置规则的目标是让依赖方向单向：通用代码不反向依赖业务目录。

**速记**：组件大驼峰同名文件，自定义 Hook 以 use 开头，纯函数放 utils。



#### 命名、导出约定与提交钩子

命名与导出约定只有在工具强制执行时才会长期成立，规则与落地手段如下：

- 命名：组件用大驼峰，Hook 与函数用小驼峰，常量用全大写下划线分隔。
- 导出：组件默认导出一个主组件，工具与 Hook 用具名导出，改名时调用处能同步暴露。
- 强制手段：用 ESLint 规则约束 Hook 命名与依赖数组，用提交钩子在提交前执行检查。
- 配置归属：ESLint 与 Prettier 的规则集与插件配置详见 前端/构建工具 主题第 13 篇 ESLint 与 Prettier：代码规范工具链。

```json
{
  "scripts": {
    "lint": "eslint src",
    "test": "vitest run"
  }
}
```

> [!CAUTION]
> **注意内容**：约定只写在文档里必然退化为摆设，至少要让 Lint 在提交前失败一次，否则新成员会按自己的习惯新增文件。

**速记**：命名与导出约定交给 ESLint 与提交钩子强制执行，而不是靠口头约定。
