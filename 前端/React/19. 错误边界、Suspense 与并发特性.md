## 错误边界、Suspense 与并发特性

错误边界、Suspense 与并发特性共同回答一个问题：某部分 UI 出错或尚未就绪时，页面如何继续可用。错误边界把渲染错误限制在局部，Suspense 表达等待，并发特性与 React 19 的新写法让等待与提交更顺畅。

### 错误边界是什么

错误边界是渲染层面的容错机制，它把子树崩溃的后果限制在局部，避免整棵组件树被整体卸载。

#### 错误边界的定义

**错误边界（error boundary）**：是渲染树中一类能捕获子组件树在渲染期抛出的错误、并改用备用 UI 渲染的组件。

- 捕获对象：渲染阶段同步抛出的错误，包括组件函数体、构造函数与生命周期方法中的错误。
- 兜底动作：捕获后不再渲染原子树，改渲染边界自己定义的备用 UI。
- 保护范围：一个边界保护其整棵子树，子树内的错误不会再被更外层的边界捕获。

```jsx
import { ErrorBoundary } from "./ErrorBoundary";

export function App() {
  return (
    <ErrorBoundary fallback={<ErrorFallback />}>
      <UserDashboard />
    </ErrorBoundary>
  );
}
```

> 错误边界的定位是界面容错。业务数据错误应在请求层处理成明确的加载、空态与失败状态，不要依赖边界兜住可预期的失败。

**速记**：错误边界是捕获渲染期错误并渲染备用 UI 的组件。



#### 能捕获与不能捕获的范围

**捕获范围**：指错误边界只覆盖渲染期同步抛出的错误，异步代码与事件回调中的错误不在其内。

- 能捕获：渲染函数、构造函数、生命周期方法中同步抛出的错误。
- 不能捕获：事件处理函数中的错误（详见本主题第 4 篇 事件处理与合成事件）。
- 不能捕获：定时器、Promise 回调等异步代码中的错误，以及边界组件自身抛出的错误。

```jsx
function UserList() {
  const [items, setItems] = useState(null);

  useEffect(() => {
    fetch("/api/users")
      .then((response) => response.json())
      .then(setItems)
      .catch((error) => console.error(error)); // 此处错误不会被错误边界捕获
  }, []);

  if (items === null) return <p>加载中</p>;
  return items.map((user) => <p key={user.id}>{user.name}</p>);
}
```

> [!IMPORTANT]
> **重要内容**：事件处理与异步回调中的错误必须自行捕获或写入错误状态，否则错误边界无法感知，界面会停在失败之后的状态。

**速记**：只捕获渲染期同步错误，事件与异步错误要自己处理。



#### 为什么需要错误边界

**错误边界的必要性**：来自 React 的错误传播规则。渲染期未被捕获的错误会一路冒泡到根节点，导致整棵组件树被卸载。

- 无边界时：任一组件的渲染抛错，整个应用卸载为空白页，用户失去全部上下文。
- 有边界时：只有受保护的子树被替换为备用 UI，导航与其余模块仍可继续使用。
- 分级保护：在路由页、局部卡片等位置分别放置边界，可把影响面压到最小。

**速记**：没有错误边界时一次渲染错误会卸载整棵树，边界把影响限制在局部。



### 实现与局限

错误边界需要组件具备保存错误状态、在渲染前拦截错误的能力。现行实现只能用类组件完成，这是本系列少数必须写类组件的位置。

#### 用类组件实现错误边界

**类组件实现**：是指继承 Component、实现静态方法 getDerivedStateFromError 与实例方法 componentDidCatch、并在 render 中依据错误状态决定渲染内容的写法。

- 继承基类：必须继承 Component，才能获得错误边界的拦截能力。
- 错误状态：用 state 保存捕获到的错误，初始值为 null。
- 渲染分支：state 中存在错误时返回备用 UI，否则返回 this.props.children。
- 场景说明：这是少数仍需类组件的场景，本系列其余位置一律写函数组件。

```jsx
import { Component } from "react";

class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };
  }

  componentDidCatch(error, info) {
    reportError(error, info.componentStack); // 上报监控
  }

  render() {
    if (this.state.error) return <ErrorFallback message={this.state.error.message} />;
    return this.props.children;
  }
}
```

> 现行 React 未提供函数组件版的错误边界 API，因此这里必须使用类组件，与其他篇目统一写函数组件并不冲突。

**速记**：错误边界只能写成类组件，这是少数仍需类组件的场景。



#### getDerivedStateFromError 与 componentDidCatch 的分工

**getDerivedStateFromError(error)**：是静态方法，接收抛出的错误对象，返回一个用于更新 state 的对象，决定接下来渲染什么。**componentDidCatch(error, info)**：是实例方法，接收错误对象与含 componentStack 的信息对象，用于执行上报等副作用。

- 前者管渲染：在渲染阶段调用，只做状态更新，必须返回新状态对象。
- 后者管记录：在提交阶段调用，可发送日志与上报监控，不需要返回值。
- 二者可只用其一：只求降级渲染可省略 componentDidCatch，但上报应当保留。

```jsx
class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                        // 触发降级渲染
  }

  componentDidCatch(error, info) {
    reportError(error, info.componentStack); // 提交阶段上报
  }
}
```

> 在静态方法里写副作用不会生效，它只负责给出下一份 state；需要副作用的动作全部放在 componentDidCatch。

**速记**：前者决定降级渲染的状态，后者执行错误上报。



#### 重置错误状态

**重置错误状态**：是指在错误原因排除后让错误边界恢复渲染子树的动作，常用做法是给边界传一个会变化的 key，强制其重新挂载。

- 问题：错误一旦写入 state，边界会持续渲染备用 UI，不会自动重试。
- key 重建：改变 key 会让 React 卸载旧实例、挂载新实例，state 重置为初始值。
- 主动复位：也可向边界暴露一个重置方法，在备用 UI 的重试按钮中调用。

```jsx
export function UserPage({ userId }) {
  return (
    <ErrorBoundary key={userId} fallback={<ErrorFallback />}>
      <UserDetailPage userId={userId} />
    </ErrorBoundary>
  );
}
```

**速记**：改变 key 让边界重新挂载，是重置错误状态最直接的办法。



#### 开发期错误覆盖层的干扰

**开发期错误覆盖层**：是开发模式下 React 与构建工具显示的报错浮层，它在错误发生后覆盖页面，使错误边界的备用 UI 不易观察。

- 行为差异：开发模式下错误仍会抛到浮层，生产构建中才由边界静默接管。
- 处理顺序：先在开发期按浮层提示修复真实错误，再关闭浮层确认备用 UI。
- 验证途径：用生产构建的产物验证降级效果，而不是只看开发模式。

> [!WARNING]
> **警告内容**：开发期显示的错误与生产环境的表现并不一致，验证错误边界必须以生产构建为准，否则会得到错误结论。

**速记**：开发期覆盖层会遮住备用 UI，降级效果要在生产构建中确认。



### Suspense 与数据获取

Suspense 把等待从组件内部的状态提升为渲染树的声明，让加载占位由最近的边界统一提供。

#### Suspense 的定义与 fallback

**Suspense**：是 React 提供的等待占位组件，在子树尚未就绪时渲染 fallback 属性指定的内容，就绪后再切换为真实子树。

- 属性 fallback：等待期间渲染的占位 UI，可以是元素或组件。
- children：真实子树，其中某个组件通过抛出 Promise 表示尚未就绪。
- 触发条件：子树中任一处进入等待，最近的 Suspense 边界就显示 fallback。

```jsx
import { Suspense } from "react";

export function App() {
  return (
    <Suspense fallback={<p>加载中</p>}>
      <UserProfile />
    </Suspense>
  );
}
```

**速记**：Suspense 在子树未就绪时渲染 fallback，就绪后切换为真实内容。



#### 配合 lazy 做代码分割

**配合 lazy**：是指由 lazy 创建的分包组件在首次渲染时尚未下载完成，需要外层 Suspense 提供加载占位。分包机制本身详见本主题第 18 篇 性能优化：memo、懒加载与代码分割。

- 触发时机：首次渲染到该组件时才发起对应分包的下载。
- 占位来源：下载期间由最近的 Suspense 渲染 fallback。
- 加载失败：分包下载失败属于异步错误，需要额外的错误边界接管。

```jsx
import { lazy, Suspense } from "react";

const UserDashboard = lazy(() => import("./UserDashboard"));

export function App() {
  return (
    <Suspense fallback={<p>正在加载面板</p>}>
      <UserDashboard />
    </Suspense>
  );
}
```

**速记**：lazy 分包依赖 Suspense 提供下载期间的占位。



#### 配合支持 Suspense 的数据读取方案

**支持 Suspense 的数据读取**：是指数据层按未就绪时抛出 Promise 的约定与 React 协作，使组件在等待数据期间由外层 Suspense 接管渲染。

- 协议约定：读取中抛出 Promise，成功后返回数据，失败则抛出错误。
- 结果缓存：同一请求的结果被缓存复用，避免每次渲染都重新进入等待。
- 分工：抛出的错误交给错误边界，等待交给 Suspense，两类边界各司其职。

```jsx
// 数据层按约定实现：读取中抛出 Promise，成功返回缓存数据
function loadUserProfile(userId) {
  const cached = profileCache.get(userId);
  if (cached) return cached;

  const promise = fetchProfile(userId).then((profile) => {
    profileCache.set(userId, profile);
  });
  throw promise; // 通知 React 进入等待
}
```

**速记**：支持 Suspense 的读取方案在未就绪时抛出 Promise，成功后返回数据。



#### 嵌套 Suspense 的分层降级

**嵌套 Suspense**：是在一个 Suspense 内部再放 Suspense，让不同区域按各自的就绪时间独立显示占位，实现分层降级。

- 就近接管：子树的等待由最近的 Suspense 接管，不会让外层整块变成占位。
- 独立切换：内层先就绪时先显示内层内容，外层其余部分仍可继续等待。
- 用法建议：页面骨架放外层，局部慢区块放内层，避免一个慢接口拖住整屏。

```jsx
export function DashboardPage() {
  return (
    <Suspense fallback={<DashboardSkeleton />}>
      <Header />
      <Suspense fallback={<p>列表加载中</p>}>
        <SlowUserList />
      </Suspense>
      <StatsPanel />
    </Suspense>
  );
}
```

**速记**：嵌套 Suspense 按区域就近降级，慢区块不会拖住整屏。



### 过渡更新与 useDeferredValue

并发特性把状态更新分成紧急与可延后两类，让输入这类即时反馈不被重计算阻塞。

#### 过渡更新的含义

**过渡更新（transition）**：是把一次状态更新标记为非紧急的机制，React 先完成紧急更新，再在可打断的低优先级渲染中处理它。

- 紧急更新：输入、点击等直接反馈用户操作的更新，必须立即完成。
- 过渡更新：结果刷新、大列表过滤等可以稍后完成的更新，允许被打断。
- 渲染体验：紧急更新不被长任务阻塞，输入框保持即时响应。

```jsx
const [query, setQuery] = useState("");
const [list, setList] = useState(allItems);
const [isPending, startTransition] = useTransition();

function handleChange(event) {
  const next = event.target.value;
  setQuery(next);                                 // 紧急更新：输入框立即回显
  startTransition(() => {
    setList(allItems.filter((item) => item.name.includes(next))); // 过渡更新
  });
}
```

**速记**：过渡更新把非紧急更新标记为可打断，优先保障输入反馈。



#### useTransition 的签名与用法

**useTransition**：是无参数的 Hook，返回 isPending 与 startTransition 组成的二元数组。**startTransition**：接收一个无参数的回调函数，把回调中的状态更新标记为过渡更新，返回值为 undefined。

- 返回值一：isPending 是布尔值，表示是否有过渡更新尚未提交完成。
- 返回值二：startTransition 的签名为 startTransition(callback)，callback 内写同步的状态更新逻辑。
- 用法：用 isPending 挂起类名或禁用按钮，告知用户正在处理而界面未卡顿。

```jsx
import { useState, useTransition } from "react";

export function FilterPanel({ allItems }) {
  const [query, setQuery] = useState("");
  const [list, setList] = useState(allItems);
  const [isPending, startTransition] = useTransition();

  function handleSearch(event) {
    const next = event.target.value;
    setQuery(next);
    startTransition(() => setList(allItems.filter((item) => item.name.includes(next))));
  }

  return (
    <div className={isPending ? "panel pending" : "panel"}>
      <input value={query} onChange={handleSearch} />
      <ItemList items={list} />
    </div>
  );
}
```

> [!TIP]
> **建议内容**：过渡更新只包住需要降优先级的 setState，输入框自身的回显更新留在外面，否则输入仍会卡顿。

**速记**：useTransition 无参返回 isPending 与 startTransition，后者接收回调。



#### useDeferredValue 的签名与用法

**useDeferredValue**：是接收 value 并返回其延后版本的 Hook，签名 useDeferredValue(value)，返回一个在紧急更新结束后才跟上的旧值。

- 入参 value：需要延后的值，通常是频繁变化的 state 或 props。
- 返回值：延后版本，紧急更新期间保持旧值，空闲后再更新为新值。
- 与过渡的差别：不需要把更新包进回调，适合值已算好、只需延后展示的场景。

```jsx
import { useState, useDeferredValue } from "react";

export function SearchPage({ allItems }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  const result = allItems.filter((item) => item.name.includes(deferredQuery));

  return (
    <div>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />
      <ItemList items={result} dimmed={isStale} />
    </div>
  );
}
```

**速记**：useDeferredValue 接收 value，返回空闲后才跟上的延后版本。



#### 适用场景与取舍

**适用场景**：指输入立即回显、派生结果稍后跟上的交互，用过渡更新或延后值把重计算从紧急路径上挪开。

- 搜索联想：输入框即时响应，匹配结果与高亮稍后更新。
- 大列表筛选：过滤与排序耗时较长，避免阻塞输入与滚动。
- 取舍：能改数据层就不要只靠渲染层缓冲，真正昂贵的计算应做缓存或分页。

**速记**：过渡与延后值只改善调度，重计算的成本要靠缓存、分页或服务端化解。



### React 19 的 Actions 与 use

React 19 引入一组围绕异步提交的新写法，把加载态、错误态与乐观更新交给框架托管，减少手写样板。

#### 表单动作与 useActionState

**表单动作（Action）**：是可直接传给表单 action 属性的异步函数，提交后由 React 自动管理进行中的状态。**useActionState**：是接收 action 与初始 state、返回当前 state、包装后的表单动作与挂起状态三元数组的 Hook，签名 useActionState(action, initialState)。

- action 签名：接收上一个 state 与表单数据 FormData，返回新的 state。
- 返回值：state 为最新结果，formAction 传给表单 action，isPending 表示是否正在提交。
- 好处：按钮禁用与错误展示都来自返回值，无需手写加载状态。

```jsx
import { useActionState } from "react";

async function submitProfile(previousState, formData) {
  const name = formData.get("name");
  if (!name) return { error: "姓名不能为空" };
  await saveProfile({ name });
  return { error: null, savedAt: Date.now() };
}

export function ProfileForm() {
  const [state, formAction, isPending] = useActionState(submitProfile, { error: null });

  return (
    <form action={formAction}>
      <input name="name" />
      <button disabled={isPending}>{isPending ? "提交中" : "保存"}</button>
      {state.error ? <p>{state.error}</p> : null}
    </form>
  );
}
```

> [!NOTE]
> **提醒内容**：表单动作提交完成后会自动重置非受控字段；受控字段仍需自行处理，同一字段不要混用两种方式。

**速记**：useActionState 管住表单的提交状态与结果，省去手写加载与错误状态。



#### use 读取 Promise 或 Context

**use**：是 React 19 提供的读取 API，接收 Promise 或 Context 并返回其解析值，在渲染中调用。

- 读取 Promise：use(promise) 在数据未就绪时挂起组件，由外层 Suspense 接管。
- 读取 Context：use(SomeContext) 与 useContext 等价，但不属于 Hook 调用规则的约束范围。
- 位置限制：use 可以出现在条件与循环中；但它仍不能在事件回调里调用。

```jsx
import { use, Suspense } from "react";

function UserProfile({ profilePromise }) {
  const profile = use(profilePromise); // 未就绪时挂起，由外层 Suspense 接管
  return <h2>{profile.name}</h2>;
}

export function UserPage({ profilePromise }) {
  return (
    <Suspense fallback={<p>加载中</p>}>
      <UserProfile profilePromise={profilePromise} />
    </Suspense>
  );
}
```

> [!IMPORTANT]
> **重要内容**：传给 use 的 Promise 必须由外部缓存后再传入。每次渲染都新建 Promise 会让组件反复挂起，这也是支持 Suspense 的数据方案的共同要求。

**速记**：use 在渲染中读取 Promise 或 Context，未就绪时由 Suspense 挂起。



#### 乐观更新 useOptimistic

**useOptimistic**：是接收当前状态与更新函数、返回乐观状态与提交函数的 Hook，签名 useOptimistic(state, updateFn)，updateFn 接收当前 state 与乐观更新的参数并返回乐观状态。

- 思路：用户操作后立即按预期结果渲染，服务端确认后再用真实数据替换。
- 回退：请求失败或尚未提交完成时，乐观状态自动回到真实 state。
- 边界：仅用于大概率成功的展示性更新，不作为最终数据来源。

```jsx
import { useOptimistic } from "react";

export function TodoList({ todos, addTodo }) {
  const [optimisticTodos, addOptimisticTodo] = useOptimistic(
    todos,
    (currentTodos, newTitle) => [...currentTodos, { id: "pending", title: newTitle }]
  );

  async function handleAdd(formData) {
    const title = formData.get("title");
    addOptimisticTodo(title); // 先按预期渲染
    await addTodo(title);     // 再由服务端结果替换
  }

  return (
    <form action={handleAdd}>
      <input name="title" />
      {optimisticTodos.map((todo) => <p key={todo.id}>{todo.title}</p>)}
    </form>
  );
}
```

**速记**：useOptimistic 先按预期渲染，失败或完成后回落到真实状态。



#### 新写法与手动加载态对比

**对比**：是把手动维护加载中、错误、结果三个状态，与交给表单动作及新 API 托管两种写法的差别。

- 手动写法：需要用 useState 分别保存三个状态，多个异步入口容易遗漏重置与竞态处理。
- 新写法：useActionState 的 isPending 与 state 覆盖提交过程，useOptimistic 覆盖展示层的即时反馈。
- 取舍：新写法适合提交入口固定、决策链清晰的表单；缓存、重试与失效仍应交给专门的数据层。

**速记**：新写法把提交状态与结果交给框架，手写三份状态容易遗漏。
