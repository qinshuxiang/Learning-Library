## 状态提升与单向数据流

### 单向数据流模型

**单向数据流（one-way data flow）** 是 React 的数据流动约定：数据沿组件树自上而下传递，变化由事件自下而上通知。本篇讨论状态该放在哪一层、如何提升，以及如何避免派生出冗余状态。

#### 数据自顶向下的流动

**数据自顶向下的流动**：指父组件通过 props（组件的只读输入参数）把数据传给子组件，子组件只读取不修改，方向始终向下。

- 传参：父组件在 JSX 中以属性形式传值，子组件通过函数参数接收。
- 只读：子组件不能改写收到的 props，需要变化时必须向上通知。
- 一致性：同一次渲染中，界面各处显示的数据来自同一份 state。

```jsx
function ProfileCard({ user }) {
  return <p>{user.name} 来自 {user.city}</p>;
}

function ProfilePage() {
  const user = { name: "Ada Lovelace", city: "London" };

  return <ProfileCard user={user} />;
}
```

> 数据向下流动意味着子组件不关心数据从哪里来，只按 props 的形状渲染。

**速记**：数据通过 props 自父向子流动，方向只有一个。



#### 父传子用 props、子通父用回调

**子通父用回调**：指父组件把一个函数作为 prop 传给子组件，子组件在事件发生时调用它，把变化通知上去。

- 下行数据：值通过普通 props 传递。
- 上行意图：函数通过 props 传递，调用时以参数说明「发生了什么」。
- 结果：状态的持有者始终是父组件，子组件只发出请求。

```jsx
function SearchInput({ keyword, onKeywordChange }) {
  return (
    <input
      value={keyword}
      onChange={(event) => onKeywordChange(event.target.value)}
    />
  );
}

function SearchPage() {
  const [keyword, setKeyword] = useState("");

  return <SearchInput keyword={keyword} onKeywordChange={setKeyword} />;
}
```

> 子组件不直接改父组件的数据，只调用父组件给的函数，改不改、怎么改由父组件决定。

**速记**：值向下传，事件向上报，状态由父组件统一持有。



#### 为什么不做双向绑定

**双向绑定（two-way binding）**：指视图与数据模型自动互相同步，改一处另一处随之变化。React 不采用这种模型，而用值加事件回调的显式写法。

- 显式：数据从哪里来、变化后由谁处理，在代码中一眼可见。
- 可预测：一次渲染只依赖 props 与 state，同样输入得到同样输出。
- 可调试：变化都由状态更新函数触发，便于加日志与断点。
- 代价：表单类场景样板代码更多，社区用表单库以语法糖形式补足。

> 双向绑定不是被禁止的能力，而是一种被放弃的默认：需要时可在受控组件之上自行封装。

**速记**：React 用值与回调显式表达同步，不用双向绑定的隐式同步。



### 状态提升

**状态提升（lifting state up）** 是把多个子组件共用的 state 上移到最近的共同父组件的做法，它直接落实了单向数据流的分工。

#### 什么情况下该提升

**该提升的判断**：指出现两份状态必须一起变化、或一个组件的数据由另一个组件的操作决定时，就应当上移。

- 联动：两个输入框的内容需要互相换算，各自持有 state 无法保持一致。
- 共享：列表与统计数字读取同一批数据，分别保存会出现不同步。
- 反例：只有单个组件使用、与其他组件无关的数据留在原地。

**速记**：多个组件共用或联动变化的状态，上移到最近的共同父组件。



#### 提升的步骤

**提升的步骤**：指按固定顺序把 state 从子组件搬到共同父组件，并改接数据与回调。

1. 在子组件中找到要共享的 state，删除它的声明。
2. 在最近的共同父组件中声明同一份 state。
3. 把这份 state 的值作为 props 传给子组件。
4. 把状态更新函数作为 props 传给子组件，替换子组件中原有的调用。

```jsx
// 提升前：子组件自己持有内容，父组件无从知晓
function CelsiusInput() {
  const [value, setValue] = useState("");

  return (
    <input value={value} onChange={(event) => setValue(event.target.value)} />
  );
}

// 提升后：值由父组件持有，子组件只负责显示与通知
function TemperatureInput({ label, value, onValueChange }) {
  return (
    <label>
      {label}
      <input value={value} onChange={(event) => onValueChange(event.target.value)} />
    </label>
  );
}
```

> 搬迁后子组件从状态持有者变成受控组件，它显示什么完全由 props 决定。

**速记**：删、搬、传值、传回调，四步完成一次状态提升。



#### 提升后的 props 与回调传递

**提升后的 props 与回调**：指父组件持有 state，向下同时传递当前值与更新函数，子组件据此受控。

- 值 prop：命名与数据语义一致，如 temperature、keyword。
- 回调 prop：命名以 on 开头，如 onTemperatureChange。
- 多层透传：中间组件如果只是转发，仍要原样传递，这层样板可用组合模式或 Context 缓解。

```jsx
function TemperaturePage() {
  const [temperature, setTemperature] = useState("");
  const [scale, setScale] = useState("c");

  function handleCelsiusChange(value) {
    setScale("c");
    setTemperature(value);
  }

  return (
    <div>
      <TemperatureInput
        label="摄氏度"
        value={scale === "c" ? temperature : ""}
        onValueChange={handleCelsiusChange}
      />
      <TemperatureInput
        label="华氏度"
        value={scale === "f" ? temperature : ""}
        onValueChange={handleCelsiusChange}
      />
    </div>
  );
}
```

> 同一份 state 被多个子组件读取时，任一子组件的变化都会让父组件重新渲染，从而让所有读取方同步。

**速记**：父组件传值与 on 开头的回调，子组件受控显示并上报变化。



#### 提升带来的重新渲染代价

**提升带来的重新渲染代价**：指状态上移后，父组件的重新渲染会连带其全部子组件一起渲染，范围比原来更大。

- 范围扩大：原本只渲染一个子组件，现在父组件及其兄弟子树一并渲染。
- 定位：用 React DevTools 的 Profiler 观察一次交互触发了哪些组件，方法见第 18 篇。
- 缓解：缩小持有状态的组件边界，或用第 11 篇的 useMemo 与 useCallback 稳定引用，必要时配合 React.memo。

> [!CAUTION]
> **注意内容**：状态提升会扩大重新渲染范围，交互高频或子树庞大时要评估代价，不能一味上移。

**速记**：状态越高重新渲染覆盖的子树越大，提升要权衡范围。



### 回调函数向下传递

回调是单向数据流里的上行通道。它的传递方式、命名与参数形状，决定了父子组件之间的契约是否清晰。

#### 把更新函数作为 props 传下去

**把更新函数作为 props 传下去**：指父组件把自己的状态更新函数或包装后的处理函数交给子组件，由子组件在合适时机调用。

- 直接传递：onValueChange={setKeyword}，不在中间再包一层。
- 间接传递：需要附加规则时传自定义函数，如 handleAddTodo。
- 边界：子组件只描述发生了什么，不决定状态如何变化。

```jsx
function AddButton({ onAddTodo }) {
  return <button onClick={() => onAddTodo("新任务")}>添加任务</button>;
}

function TodoPanel() {
  const [todos, setTodos] = useState([]);

  function handleAddTodo(text) {
    setTodos([...todos, { id: crypto.randomUUID(), text, done: false }]);
  }

  return <AddButton onAddTodo={handleAddTodo} />;
}
```

> 向下传的是更新入口，而不是可以随意改写的状态对象，子组件因此绕不过父组件的更新规则。

**速记**：回调 prop 是父组件交出的更新入口，子组件只调用不改写。



#### 命名约定与参数设计

**回调 prop 的命名与参数设计**：指回调名以 on 开头描述事件，处理函数名以 handle 开头描述动作，参数只带必要信息。

- 组件属性：onAddTodo、onRemoveTodo、onValueChange。
- 处理函数：handleAddTodo、handleRemoveTodo，与回调 prop 一一对应。
- 参数：传最小信息，如 id 或新对象，由父组件决定如何合并进当前 state。

```jsx
function TodoRow({ todo, onToggleTodo, onRemoveTodo }) {
  return (
    <li>
      <span>{todo.text}</span>
      <button onClick={() => onToggleTodo(todo.id)}>切换</button>
      <button onClick={() => onRemoveTodo(todo.id)}>删除</button>
    </li>
  );
}
```

> 参数传 id 而不是数组下标，父组件才能独立于列表顺序实现更新逻辑。

**速记**：属性用 on 开头，处理函数用 handle 开头，参数只传最小必要信息。



#### 避免不必要的包装函数

**避免不必要的包装函数**：指回调不需要附加逻辑时，直接把函数引用传下去，不再套一层箭头函数。

- 直接传引用：onChange={setKeyword}，子组件调用时参数原样传入。
- 需要预处理才包装：如把字符串裁掉首尾空格后再交给状态更新函数。
- 代价：内联箭头函数每次渲染都新建，传给被 memo 的子组件会使其失效，见第 18 篇。

```jsx
// 无需附加逻辑：直接传函数引用
<SearchInput value={keyword} onValueChange={setKeyword} />

// 需要预处理：包装一层，裁掉首尾空格
<SearchInput
  value={keyword}
  onValueChange={(next) => setKeyword(next.trim())}
/>
```

> [!TIP]
> **建议内容**：把内联箭头函数集中到命名处理函数中，既能减少重复创建，也让 JSX 更易读。

**速记**：不加逻辑就直接传引用，需要预处理才包装成命名函数。



#### 与事件处理函数的衔接

**与事件处理函数的衔接**：指回调 prop 由子组件内部的事件处理函数调用，事件对象在此处被转换成业务参数后上报。

- 转换：在子组件中从 event 取出需要的数据，调用回调时只传业务值。
- 不传事件对象：事件对象是合成事件，跨层传递会造成耦合，事件写法见第 4 篇。
- 命名一致：子组件内的事件处理函数同样以 handle 开头。

```jsx
function KeywordInput({ keyword, onKeywordChange }) {
  function handleChange(event) {
    onKeywordChange(event.target.value); // 事件对象在此转换为业务值
  }

  return <input value={keyword} onChange={handleChange} />;
}
```

> 事件对象属于子组件的实现细节，回调 prop 的契约只描述业务数据的形状。

**速记**：子组件在事件处理函数里把 event 转成业务值，再调用回调上报。



### 派生状态与冗余状态

**派生状态（derived state）** 是能由其他数据算出来的数据。识别它并把它从 state 中移除，是最常见的状态整理手段。

#### 派生状态的定义

**派生状态**：指可以由已有 state 或 props 计算得出的数据，它本身不需要作为独立 state 保存。

- 来源：来自其他 state、props，或两者的组合。
- 特征：任何时刻都能由来源重新算出，不引入新的信息。
- 判断：删掉这份 state 后界面信息没有丢失，说明它是派生的。

**速记**：能由现有数据算出的数据是派生状态，不必单独保存。



#### 能从现有数据算出来的不要另存

**不要另存可算出的数据**：指把派生结果也放进 state 会让两份数据需要人工同步，是缺陷的常见来源。

- 同步负担：来源变化时必须记得同时更新派生 state，漏一次就出现不一致。
- 典型错误：列表另存一份筛选结果，筛选条件变化后忘记重算。
- 做法：state 只保留最小数据，其余在渲染时计算。

```jsx
function TodoPanel() {
  const [todos, setTodos] = useState([
    { id: 1, text: "读书", done: true },
    { id: 2, text: "跑步", done: false },
  ]);
  const [hideDone, setHideDone] = useState(false);

  // 每次渲染直接算出要显示的内容，不额外保存一份
  const visibleTodos = hideDone
    ? todos.filter((todo) => !todo.done)
    : todos;

  return (
    <button onClick={() => setHideDone(!hideDone)}>
      显示 {visibleTodos.length} 项
    </button>
  );
}
```

> [!IMPORTANT]
> **重要内容**：state 只保存无法由其他数据推导出的最小信息，重复保存的内容必然需要人工同步，最终产生不一致。

**速记**：state 里只留最小数据，可算出的内容一律渲染时现算。



#### 渲染期直接计算的写法

**渲染期直接计算**：指在组件函数体内、return 之前用普通变量或表达式算出派生结果，不调用任何 Hook。

- 位置：与 state 声明同层，位于 return 语句之前。
- 手段：filter、map、reduce、字符串拼接等纯计算皆可。
- 成本：数据量小且每次渲染只算一遍时，这是最简单也最不易出错的做法。

```jsx
function CartSummary({ items }) {
  const totalCount = items.reduce((sum, item) => sum + item.count, 0);
  const totalPrice = items.reduce((sum, item) => sum + item.count * item.price, 0);

  return <p>共 {totalCount} 件，合计 {totalPrice} 元</p>;
}
```

> 每次渲染重算听起来浪费，但组件内部只是几次遍历，通常远低于重新渲染本身的开销。

**速记**：派生值在 return 之前用普通变量算出，不占 state 也不进 Hook。



#### 确需缓存时用 useMemo

**确需缓存时用 useMemo**：指计算开销确实很大或需要稳定引用时，才用 useMemo 缓存派生结果，签名与依赖规则归第 11 篇。

- 触发条件：遍历规模大、计算复杂，或结果引用需要保持稳定。
- 判断依据：先用 Profiler 测量再决定，不要凭感觉提前优化，方法见第 18 篇。
- 衔接：useMemo(callback, dependencies) 的具体用法见第 11 篇，此处不展开。

```jsx
function ReportView({ rows, keyword }) {
  // 数据量很大时缓存筛选结果，只在 rows 或 keyword 变化时重算
  const matchedRows = useMemo(
    () => rows.filter((row) => row.name.includes(keyword)),
    [rows, keyword]
  );

  return <span>匹配 {matchedRows.length} 行</span>;
}
```

**速记**：默认渲染期现算，只有实测确认昂贵时才用 useMemo 缓存。



### 状态放在哪一层

状态放在哪一层，决定了数据流向、重新渲染范围与组件复用难度。这一节给出可操作的判断顺序。

#### 判断准则

**状态归属的判断准则**：指依据「谁读、谁改、影响谁」三个问题决定 state 声明在哪个组件。

- 谁需要读：所有读取方的最近共同祖先，就是要放的位置。
- 谁需要改：改动方应当是持有者的后代，通过回调上报。
- 影响范围：状态越高影响越广，能在低层满足就不要上移。

**速记**：按读取方的最近共同祖先定位，按影响范围收敛层级。



#### 就近原则

**就近原则**：指在没有共享需求时，把 state 放在使用它的组件自身，保持局部性。

- 局部优先：只有该组件用到的展开状态、输入内容，留在组件内部。
- 好处：改动只让该组件重新渲染，边界清晰，也便于复用与测试。
- 检验：把组件连同它的 state 一起搬到别处仍能工作，说明位置合适。

```jsx
function AccordionItem({ title, children }) {
  const [isOpen, setIsOpen] = useState(false); // 只服务本组件，就近声明

  return (
    <section>
      <button onClick={() => setIsOpen(!isOpen)}>{title}</button>
      {isOpen ? <div>{children}</div> : null}
    </section>
  );
}
```

> 状态尽可能靠近使用它的地方，是避免无谓重新渲染最省事的手段。

**速记**：无共享需求时状态就近留在使用它的组件内部。



#### 过度提升与过度局部化的代价

**过度提升与过度局部化**：指两种失衡各有代价，前者扩大渲染范围，后者造成数据重复与同步困难。

- 过度提升：把只用一次的数据提到顶层，任何变化都影响整棵树，组件也难以独立复用。
- 过度局部化：把本应共享的数据分别存在多个组件中，需要人工保持它们一致。
- 折中：以「是否存在共享与联动」为界，有则上移，无则就近。

> 判断失衡的信号很直接：出现需要手动同步的两份数据，或出现为了传一个值而逐层透传的组件。

**速记**：提升过度伤性能与复用，局部过度伤一致性，边界看是否共享。



#### 跨多层时的替代方案

**跨多层传递的替代方案**：指数据需要穿过大量中间组件时，改用 Context 或全局状态方案，避免逐层透传 props。

- Context：适合主题、语言、当前用户等变化不频繁的跨层数据，用法见第 14 篇。
- 全局状态：适合多页面共享、更新频繁的业务数据，选型见第 21 篇。
- 组合模式：把组件作为 children 或 render props 传递可以跳过中间层，见第 13 篇。

> [!TIP]
> **建议内容**：先用就近与提升解决多数问题，只有确需跨多层且无法用组合绕过时，才引入 Context 或全局状态库。

**速记**：跨多层优先用 Context，业务级共享再考虑全局状态方案。
