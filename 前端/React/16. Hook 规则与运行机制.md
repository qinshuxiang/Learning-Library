## Hook 规则与运行机制

**Hook 规则与运行机制** 回答两个问题：为什么 Hook 只能在固定位置调用，以及 React 靠什么数据结构把每个 Hook 的状态对应起来。规则是表象，以调用顺序索引的存储模型是成因；Fiber 节点的完整结构见本主题第 17 篇 渲染原理：Fiber 与协调。

### 两条 Hook 规则

**Hook 规则**：是 React 对 Hook 调用位置的两条强制约束，目的是保证同一组件在每次渲染时的 Hook 调用顺序完全一致。

#### 只能在函数组件或自定义 Hook 顶层调用

**合法调用点**：只有函数组件与自定义 Hook 的函数体顶层可以调用 Hook，普通函数、事件回调、类方法都不在其中。

- 函数组件：以大写字母开头的函数，返回 JSX，内部可以调用 Hook。
- 自定义 Hook：以 use 开头、内部调用其他 Hook 的函数，本身也可以被调用。
- 普通函数：不以 use 开头、不返回 JSX 的函数，调用 Hook 会立即报错。
- 顶层含义：调用语句直接位于函数体第一层，不包裹在任何控制结构里。

```jsx
function useWindowWidth() { // 自定义 Hook：可以调用 Hook
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);
  return width;
}
// 普通函数里调用 useState：报错，Hook 只能在组件或自定义 Hook 中调用
```

> 报错信息来自运行时校验，规则检查在开发期更早暴露同类问题；名称前缀 use 是两者共同的识别依据。

**速记**：Hook 只能在函数组件或自定义 Hook 的函数体顶层调用。



#### 不能在条件、循环与嵌套函数里调用

**禁止的位置**：if 分支、switch 分支、for 与 while 循环、try 块，以及定义在函数体内的嵌套函数，都不允许出现 Hook 调用。

- 条件：Hook 不能写在 if 里，条件只能影响 Hook 内部的行为或返回值。
- 循环：Hook 不能按次数调用，否则不同渲染的调用个数会不一致。
- 嵌套函数：定义在组件内部、传给事件或其他 Hook 的普通函数里也不能直接调用 Hook。
- 提前返回：在调用完所有 Hook 之前 return，同样会改变后续渲染的调用序列。

```jsx
function UserPanel({ isAdmin }) {
  // 错误：Hook 出现在 if 分支里，两次渲染的调用个数可能不同
  // if (isAdmin) {
  //   const [permissions, setPermissions] = useState([]);
  // }

  // 正确：Hook 无条件放在顶层，条件只影响后续逻辑
  const [permissions, setPermissions] = useState([]);
  useEffect(() => {
    if (isAdmin) setPermissions(["read", "write"]);
  }, [isAdmin]);

  return <p>{permissions.length}</p>;
}
```

> [!IMPORTANT]
> **重要内容**：Hook 的调用顺序就是它读取自身状态的索引，任何会改变调用顺序的写法都会让 state 落到错误的 Hook 上。

**速记**：条件、循环、嵌套函数与提前返回之前都不允许调用 Hook。



#### 用规则约束替代运行时检测

**用规则约束替代运行时检测**：指 React 不在运行时逐次核对 Hook 的调用意图，而是要求顺序恒定，从而用廉价的位置对应取代复杂的意图推断。

- 顺序即可靠标识：只要每次渲染的调用顺序相同，第几个调用就应该拿到第几份状态。
- 运行时无法判断意图：同一个调用语句在两次渲染中是否「意思相同」，运行时无从得知。
- 规则优先：把顺序固定下来，运行时只需按序取用，不需要额外记账。
- 代价转移：约束由开发者承担，换来的是渲染路径上极低的存储开销。

> class 组件不使用 Hook，它把状态写在实例字段上，不存在顺序约束；Hook 是 React 16.8 引入的写法。

**速记**：固定调用顺序后，运行时只需按位置取用状态，无需推断意图。



#### 检查工具与团队约定

**检查工具**：是静态分析 Hook 规则的手段，在代码运行之前指出违规调用与依赖缺失。

- 规则一：检查 Hook 是否只在组件或自定义 Hook 顶层调用，捕获条件、循环里的越界写法。
- 规则二：检查 Effect 的依赖数组是否遗漏了内部读取的响应式值。
- 编辑器集成：插件在编码时以波浪线提示，不必等到运行。
- 团队约定：新增 Hook 一律先写 use 前缀，代码评审把规则告警视为阻断项。

> 详细的插件安装、共享配置与提交钩子设置属于工程配置，详见 前端/构建工具 主题。

**速记**：用规则检查工具拦住越界调用，并把告警当作阻断项。



### 为什么不能写在条件里

**为什么不能写在条件里** 是 Hook 唯一硬性约束的核心原因：调用顺序承担了身份标识的职责，条件分支会破坏这个标识。

#### 调用顺序是 Hook 的身份标识

**调用顺序即身份**：指 React 不靠变量名或代码位置区分 Hook，而是靠它在本次渲染中是第几个被调用的。

- 无显式标识：代码里没有给每个 Hook 指定键或名字，顺序是唯一可用的坐标。
- 按次对应：第 1 次调用对应第 1 份状态，第 2 次调用对应第 2 份状态。
- 稳定性要求：这个对应关系必须跨渲染保持不变。
- 直接后果：顺序一旦改变，取到的状态就会错位。

```jsx
function SearchPage() {
  const [keyword, setKeyword] = useState("");   // 第 1 次调用 → 第 1 份状态
  const [page, setPage] = useState(1);          // 第 2 次调用 → 第 2 份状态
  const [results, setResults] = useState([]);   // 第 3 次调用 → 第 3 份状态
  return <p>{keyword} / {page} / {results.length}</p>;
}
```

> 注释里的「第几次调用」不是修辞，它就是 React 内部匹配状态的依据。

**速记**：Hook 的身份由调用顺序决定，不由名字或代码位置决定。



#### 条件分支会让顺序错乱

**顺序错乱**：指某次渲染跳过了条件内的 Hook，导致其后所有 Hook 的位置整体前移，与已存状态一一错配。

- 分支跳过的情形：条件为假时不调用，条件为真时多调用一次。
- 位置前移：被跳过的调用之后，每个 Hook 都读到了前面某个 Hook 的状态。
- 类型不匹配：读到别的 Hook 的状态后，值可能不是期望的类型或形态。
- 状态数量增长：多次交替会让状态列表在数量上持续膨胀。

```jsx
function Profile({ user }) {
  const [name, setName] = useState("anonymous"); // 恒为第 1 次调用

  // 若 user 存在时才调用下面这个 Hook，user 从有到无会让位置整体前移
  // if (user) {
  //   const [email, setEmail] = useState("");    // 有时是第 2 次调用
  // }

  return <p>{name}</p>;
}
```

> 第一次渲染 user 存在，email 对应第 2 份状态；第二次渲染 user 为空，后面的 Hook 就会顶替这份状态。

**速记**：条件跳过一次调用，其后所有 Hook 的采集位置整体前移。



#### 错位取值的具体后果

**错位取值**：指 Hook 读到了本属于另一个 Hook 的状态，从而产生值类型不符、更新错对象、界面表现异常等问题。

- 类型异常：把数组状态读进应存字符串的状态，后续字符串运算得到意外结果。
- 更新错位：调用某个更新函数却改动了另一个 Hook 的状态。
- 难排查：现象常表现为值偶尔串台，与具体分支组合相关，复现条件苛刻。
- 最坏情况：在读取后立即使用该值的代码处抛出运行时异常。

```jsx
function SettingsPanel({ enableAdvanced }) {
  const [label, setLabel] = useState("");
  const [options, setOptions] = useState([]);
  // 若把 Hook 放进 if (enableAdvanced) 内，关闭开关后 options 会读到
  // 状态 1 的位置，得到字符串而不再是数组
  return <p>{options.length}</p>;
}
```

> [!WARNING]
> **警告内容**：这类错误往往只在特定分支组合下出现，且报错位置远离真正的原因，排查成本极高。

**速记**：错位取值会让 Hook 读到他人状态，出现类型不符与更新错对象。



#### 循环与提前返回同样禁止

**循环与提前返回**：这两种写法与条件分支同类，都会让 Hook 调用次数随本次渲染的数据变化。

- 循环：按数组长度调用 Hook，长度变化即次数变化。
- 提前返回：在校验失败时提前 return，后续 Hook 被跳过。
- 正确做法：Hook 全部前置，循环与返回放在其后。
- 例外边界：普通函数内部可以循环，只要不在循环体里调用 Hook。

```jsx
function TagList({ tags }) {
  const [selected, setSelected] = useState(null);

  // 错误：循环次数随 tags 长度变化，Hook 不能这样调用
  // tags.forEach((tag) => {
  //   const [active, setActive] = useState(false);
  // });

  // 正确：状态只有一个，逐项渲染列表
  return <ul>{tags.map((tag) => <li key={tag}>{tag}</li>)}</ul>;
}
```

> 需要为多个条目保存状态时，用一份对象或数组状态统一管理，而不是为每个条目创建独立 Hook。

**速记**：循环与提前返回同样改变调用次数，Hook 必须全部前置。



### Hooks 链表的存储模型

**Hooks 链表的存储模型** 解释规则背后的实现：每个组件有一条按调用顺序排列的 Hook 链表，链表节点与 Hook 调用一一对应。

#### 每个组件对应一条 Hook 链表

**Hook 链表**：是 React 为每个组件维护的顺序结构，按 Hook 被调用的先后，把每个 Hook 各自的状态挂在链表的相邻节点上。

- 一组件一链表：两个组件各自持有一条，互不共用。
- 顺序即索引：链表按调用顺序串联，不含名字或显式键。
- 节点内容：每个节点保存对应 Hook 的状态，例如 state 的值、Effect 的创建与清理函数。
- 只增不减：可用的节点数量随调用次数增长，超出已有链表的调用会新建节点。

```jsx
function Editor() {
  const [title, setTitle] = useState("");        // 节点 1：保存 title
  const [content, setContent] = useState("");    // 节点 2：保存 content
  const [isDirty, setIsDirty] = useState(false); // 节点 3：保存 isDirty
  return <p>{title}</p>;
}
```

> 链表是公开共识层面的模型描述，用于解释规则成因；具体实现细节随版本演进，不影响理解与使用。

**速记**：每个组件一条 Hook 链表，节点按调用顺序保存各 Hook 的状态。



#### 首次渲染按顺序创建节点

**首次渲染**：指组件挂载时的那一次渲染。React 在执行函数体的过程中，按 Hook 调用出现的先后逐个创建链表节点。

- 边执行边建：每遇到一次 Hook 调用，就在链表尾部追加一个节点。
- 初值写入：useState 的 initialState、useEffect 的 setup 函数写入对应节点。
- 顺序固化：函数体执行完毕，链表顺序就是本次渲染的调用顺序。
- 后续依据：这条链表成为之后所有渲染取用状态的唯一依据。

```jsx
function TimerPanel() {
  const [seconds, setSeconds] = useState(0);     // 建节点 1
  const [running, setRunning] = useState(false); // 建节点 2
  useEffect(() => {                              // 建节点 3
    if (!running) return;
    const timer = setInterval(() => setSeconds((value) => value + 1), 1000);
    return () => clearInterval(timer);
  }, [running]);
  return <p>{seconds}</p>;
}
```

> 首次渲染创建的节点数量，就是之后每次渲染必须对上的调用数量。

**速记**：首次渲染按调用顺序在链表尾部逐个创建节点并写入初值。



#### 后续渲染按顺序逐个取用

**后续渲染取用**：指重新渲染时 React 不再新建节点，而是从链表头部出发，每遇到一个 Hook 调用就取下一个节点。

- 逐个前进：第 n 次调用读取第 n 个节点，取完即前进一格。
- 不按语义匹配：取用时不做字段名或类型校验，位置对上即视为同一个 Hook。
- 数量必须一致：调用次数少于或多于链表节点数，都会导致状态错配或重建。
- 这解释了规则：条件与循环之所以被禁止，就是为了保证每次取用的序列不变。

> 取用过程只看顺序不看名字，因此改变调用顺序等价于换了一份状态。

**速记**：后续渲染从链表头出发按顺序取节点，位置对上即同一个 Hook。



#### 链表挂在 Fiber 节点上

**Fiber 节点**：是 React 用于描述组件实例的协调单元，Hook 链表就挂在这个节点上，随组件的挂载与卸载一起创建与销毁。

- 归属明确：链表存放在组件对应的 Fiber 节点上，因此状态随组件存亡。
- 多实例隔离：同一组件渲染出多个实例时，每个实例各有自己的 Fiber 节点与链表。
- 更新衔接：重新渲染时新旧节点相互配合，链表在更新过程中被复用而非重建。
- 延伸阅读：Fiber 的结构与协调流程详见本主题第 17 篇 渲染原理：Fiber 与协调。

```jsx
function TeamRoster() {
  // 两个 UserAvatar 实例各有独立的 Fiber 节点与 Hook 链表
  return <div><UserAvatar userId="ada" /><UserAvatar userId="grace" /></div>;
}
```

> 组件卸载时它的 Fiber 节点与链表一并丢弃，所以重新挂载会回到初值，而不是恢复上次的状态。

**速记**：Hook 链表挂在组件的 Fiber 节点上，随组件挂载与卸载存亡。



### 闭包与每次渲染的快照

**闭包与每次渲染的快照** 说明另一个常见困惑的来源：组件函数每次渲染都会重新执行，函数内捕获的是当次渲染的值。

#### 每次渲染有独立的 props 与 state 快照

**渲染快照**：指每一次渲染都会形成一份独立的函数作用域，其中的 props、state 与局部变量固定为本次渲染时的取值。

- 每次重跑：渲染即调用组件函数，函数执行一次产生一份新的作用域。
- 值冻结：本次渲染中读到的 count 就是这次渲染时的 count。
- 函数翻新：每次渲染都会重新创建作用域内的函数，包括事件处理函数。
- 与链表配合：状态的持久化交给 Hook 链表，函数读取的仍是当次快照。

```jsx
function Greeting({ name }) {
  const [count, setCount] = useState(0);
  const message = "hello " + name; // 本次渲染的局部变量
  return <button onClick={() => setCount(count + 1)}>{message}: {count}</button>;
}
// 第 1 次渲染：message 为 "hello Ada"，count 为 0
// 第 2 次渲染：count 为 1，两次作用域互不共享
```

> 状态值持久保存，但每次渲染读到的是一份新的快照，二者并不矛盾。

**速记**：每次渲染形成独立快照，其中的 props、state 与局部变量当次固定。



#### 函数内读到的是当次渲染的值

**读到当次值**：指渲染函数体内以及该次渲染创建的函数中，读到的都是本次渲染的 props 与 state，而不是最新值。

- 同步读取：渲染期间读 state 得到的是本次渲染的快照值。
- 异步回调：定时器、事件订阅等回调里读到的仍是创建它的那次渲染的值。
- 与直觉相反：界面上已经更新，回调里可能还是旧值。
- 时间差来源：回调创建于旧渲染，执行发生在之后的某个时刻。

```jsx
function ChatBox() {
  const [draft, setDraft] = useState("");
  const handleSend = () => {
    setTimeout(() => console.log(draft), 3000); // 点击发送那一刻的 draft
  };
  return <button onClick={handleSend}>send</button>;
}
// 点击后 3 秒内继续输入，打印的仍是点击时的 draft
```

> 这不是数据出错，而是回调捕获了创建它那次渲染的快照。

**速记**：函数内读到的永远是创建该函数那次渲染的快照值。



#### 陈旧闭包现象与三种应对写法

**陈旧闭包（stale closure）**：指长时间存活或延迟执行的回调始终捕获旧渲染的值，导致行为与最新状态不一致。

- 写法一：补齐依赖数组，让 Effect 或回调在依赖变化时重新创建，从而读到新值。
- 写法二：用状态更新函数形式 setCount((current) => current + 1)，从参数拿最新值而不是从快照读。
- 写法三：用 useRef 保存最新值，回调内读 ref.current，ref 的更新不依赖闭包重建。
- 选择依据：需要触发副作用重建用写法一，只是累加或覆盖用写法二，既要读最新值又不想重建副作用用写法三。

```jsx
function AutoSave({ content }) {
  const latestContent = useRef(content);
  useEffect(() => {
    latestContent.current = content; // 同步到 ref，不参与闭包重建
  });
  useEffect(() => {
    const timer = setInterval(() => console.log(latestContent.current), 5000);
    return () => clearInterval(timer);
  }, []); // 只建立一次，读到的始终是最新内容
  return <p>{content.length}</p>;
}
```

> [!CAUTION]
> **注意内容**：为了读到最新值而故意省略依赖数组，会掩盖陈旧闭包问题，并在下次改动时演变成难以定位的错误。

**速记**：陈旧闭包用补齐依赖、状态更新函数或 ref 三种写法化解。



#### 与依赖数组的关系

**依赖数组与闭包**：依赖数组决定 Effect 或回调是否重新创建，也就是决定闭包捕获哪一次渲染的快照。

- 空数组：只在挂载时创建一次，闭包永久捕获首次渲染的值。
- 有依赖：依赖变化时先执行清理函数，再用新快照创建新的闭包。
- 省略数组：每次渲染都重新创建并执行，闭包始终是最新快照。
- 与链表的关系：依赖数组不在 Hook 链表的顺序结构之内，它的变化只影响该 Hook 的更新判断。

```jsx
function RoomHeader({ roomId }) {
  useEffect(() => {
    console.log("connecting to", roomId); // 闭包捕获本次渲染的 roomId
    return () => console.log("disconnecting from", roomId);
  }, [roomId]);
  return <p>{roomId}</p>;
}
// roomId 从 "lobby" 变为 "studio"：
// 依次打印 disconnecting from lobby、connecting to studio
```

> 依赖数组写全不是额外负担，它正是让闭包拿到正确快照的开关。依赖相关写法详见本主题第 9 篇 useEffect 与副作用。

**速记**：依赖数组决定闭包何时重建，也决定它捕获哪次渲染的快照。



### 严格模式下的双调用

**严格模式下的双调用** 是开发期特有现象：React 会在开发构建中对组件的部分行为执行两次，以暴露副作用中的问题。

#### 开发期严格模式的重复调用行为

**严格模式（StrictMode）**：是包裹在应用外层用于开启额外开发期检查的组件；开启后，组件的渲染与部分副作用会被重复执行。

- 渲染重复：函数组件体在开发期会被调用两次，意在暴露渲染期间的不纯操作。
- 副作用重复：挂载时 Effect 按「执行、清理、再执行」的顺序走一遍，用于暴露缺失的清理函数。
- 输出表现：日志打印两遍、请求发出两次，是常见的第一现场现象。
- 代码不变：开启严格模式不需要改动业务代码，只调整最外层包裹。

```jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";

function App() {
  console.log("render");
  useEffect(() => {
    console.log("effect");
    return () => console.log("cleanup");
  }, []);
  return <p>app</p>;
}

createRoot(document.getElementById("root")).render(
  <StrictMode><App /></StrictMode>
);
// 开发构建：render、render、effect、cleanup、effect
// 生产构建：render、effect
```

> 表现为多跑一次的开发期行为，用来说明纯渲染与清理函数的必要性，不改变最终界面结果。

**速记**：严格模式在开发期重复执行渲染与副作用，按执行、清理、再执行推进。



#### 目的是暴露不纯的渲染与副作用

**暴露不纯**：指重复执行让「依赖于只执行一次才正确」的代码立刻显出问题，从而在开发期被发现。

- 不纯渲染：渲染期间写外部变量、发起请求、直接修改 DOM，重复执行会留下痕迹。
- 副作用缺失清理：没有清理函数的订阅会重复建立，出现双份监听。
- 违反幂等：同样的输入重复执行却得到不同结果，说明代码有隐藏状态。
- 正向价值：把问题挡在开发期，避免在生产环境以偶发缺陷的形式出现。

```jsx
function SearchBox() {
  const [keyword, setKeyword] = useState("");
  useEffect(() => {
    const controller = new AbortController();
    fetch("/api/search?q=" + keyword, { signal: controller.signal });
    return () => controller.abort(); // 有清理函数，重复执行只保留一次有效请求
  }, [keyword]);
  return <input value={keyword} onChange={(event) => setKeyword(event.target.value)} />;
}
```

> 有清理函数的副作用在重复执行下依然安全；没有清理函数才会留下重复订阅与多余请求。

**速记**：重复调用的目的是暴露不纯渲染与缺少清理函数的副作用。



#### 重复调用只发生在开发期的原因

**仅开发期**：指重复调用是开发构建开启的检查手段，生产构建不会执行，以避免额外的性能开销与副作用。

- 成本考虑：生产路径追求最短执行时间，重复渲染与副作用没有收益。
- 语义不变：能否重复执行属于开发期的质量属性，不影响产品的最终行为。
- 判断方式：同一份代码在开发环境有两次输出、生产构建只有一次，即为严格模式所致。
- 构建差异：生产构建会移除开发期检查，这是构建工具的固定行为。

**速记**：重复调用只用于开发期检查，生产构建不会重复执行。



#### 如何判断某现象是它导致的

**判断是否为严格模式所致**：指通过环境、组件包裹与日志顺序三方面确认，把开发期检查现象与真实缺陷区分开。

- 看环境：只在开发构建出现、生产构建消失，基本可判定为严格模式行为。
- 看顺序：日志呈现 render、render、effect、cleanup、effect 的固定节奏，即为典型特征。
- 临时对照：在开发环境移除最外层严格模式包裹再看一次，现象消失则确认归因。
- 残留问题：若移除后仍重复，例如订阅翻倍、请求迟迟不结束，那就是需要修复的真实缺陷。

```jsx
function useInterval(callback, delay) {
  useEffect(() => {
    const timer = setInterval(callback, delay);
    return () => clearInterval(timer); // 有清理函数，重复执行不会叠加
  }, [callback, delay]);
}
```

> [!NOTE]
> **提醒内容**：先确认是否为开发构建，再判断重复执行是否伴随清理函数缺失，避免把开发期检查误判为线上缺陷。

**速记**：用环境差异、日志顺序与去包裹对照三步判断是否为严格模式所致。
