## useMemo 与 useCallback

### 重渲染与计算成本

重新渲染是函数组件的基本工作方式，理解它的触发条件与执行范围，才能判断哪些开销值得处理。

#### 重新渲染的定义

**重新渲染（re-render）**：是函数组件在 state 或 props 变化后再次执行函数体、产生一份新 JSX 的过程。

- 触发来源：组件自身的 state 更新、父组件传入的 props 变化、订阅的 Context 值变化。
- 执行内容：函数体从头到尾再跑一遍，其中的局部变量与函数声明全部重新创建。
- 结果比对：新返回的元素与上次的比较，差异部分才反映到真实 DOM（机制详见本主题第 17 篇 渲染原理：Fiber 与协调）。

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const label = `当前计数 ${count}`; // 每次重新渲染都重新计算
  console.log("render", label);

  return <button onClick={() => setCount(count + 1)}>{label}</button>;
}
// 首次渲染输出 "render 当前计数 0"，点击后输出 "render 当前计数 1"
```

**速记**：重新渲染就是函数组件再执行一次，其中的局部变量与函数全部重建。



#### 子组件的默认重新渲染行为

**子组件的默认重新渲染**：是父组件重新渲染时，子组件无论 props 是否变化都会跟着重新执行的默认行为。

- 不受 props 约束：React 默认只比较元素类型，不逐项比较 props 内容是否相等。
- 例外情形：被 React.memo 包裹的组件会做浅比较，props 不变时跳过重新渲染（完整用法详见本主题第 18 篇 性能优化：memo、懒加载与代码分割）。
- 影响范围：子树中每个未被 memo 的组件都会重新执行，层级越深累计开销越明显。

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(count + 1)}>加一</button>
      <Child title="固定标题" />
    </div>
  );
}

function Child({ title }) {
  console.log("Child render");
  return <p>{title}</p>;
}
// Parent 每次重新渲染时 Child 都会打印 "Child render"
```

**速记**：默认情况下父组件重新渲染会带动整棵子树重新渲染，props 相同也不例外。



#### 什么算昂贵计算

**昂贵计算**：是单次执行耗时在毫秒量级、且耗时随数据规模增长的计算。

- 规模敏感：对上千条数据排序、过滤、聚合，成本随条数上升。
- 纯计算：只依赖输入返回结果，不读写外部状态，可以安全地跳过或复用。
- 与渲染耦合：这类计算若直接写在组件函数体内，就会在每次重新渲染时重跑一遍。

```jsx
function RankedList({ scores }) {
  // 每次重新渲染都对全部数据排序
  const ranked = [...scores].sort((left, right) => right.value - left.value);
  return <ul>{ranked.map((item) => <li key={item.id}>{item.name}</li>)}</ul>;
}
```

> 组件函数体内的一切运算都属于重新渲染的一部分：数据量小时代价可以忽略，数据量大时才值得处理。

**速记**：昂贵计算指耗时随数据规模增长的纯计算，写在组件体内会被反复执行。



#### 先测量再优化

**先测量再优化**：是先定位真实的耗时位置、再决定是否引入缓存的次序。

- 测量优先：用 React DevTools 的 Profiler 记录一次交互中各组件耗时，看排行榜而不是凭直觉（工具用法详见本主题第 18 篇 性能优化：memo、懒加载与代码分割）。
- 确认瓶颈：只有确认某次计算或某个子组件占据主要耗时，才考虑引入 useMemo 或 useCallback。
- 避免臆测：数据量小、渲染频率低的组件加缓存只会增加复杂度。

```jsx
// 先用一次计时观察计算成本，再决定是否缓存
function Report({ rows }) {
  console.time("buildReport");
  const summary = buildReport(rows);
  console.timeEnd("buildReport");
  return <pre>{summary}</pre>;
}
// buildReport: 0.2 ms —— 成本可忽略，不值得缓存
```

**速记**：先测量出真实瓶颈再决定是否缓存，不凭直觉提前优化。



### useMemo 的签名与用法

useMemo 用于缓存计算结果，把重复的昂贵运算收敛为一次，并在依赖不变时复用。

#### useMemo 的完整签名

**useMemo**：是用于缓存计算结果的内置 Hook，签名是 useMemo(calculateValue, dependencies)，参数 calculateValue 是返回待缓存值的工厂函数，dependencies 是依赖数组，返回本次或上次缓存的结果。

- 首次渲染：执行 calculateValue，并把返回值存入缓存。
- 后续渲染：逐项对比 dependencies，全部与上次相同则直接返回缓存值，不再调用 calculateValue。
- 依赖为空数组：calculateValue 只在首次渲染时执行，结果长期复用。

```jsx
function ProductList({ products, keyword }) {
  const visibleProducts = useMemo(
    () => products.filter((product) => product.name.includes(keyword)),
    [products, keyword]
  );

  return <ul>{visibleProducts.map((product) => <li key={product.id}>{product.name}</li>)}</ul>;
}
```

**速记**：useMemo(calculateValue, dependencies) 缓存计算结果，依赖不变就复用缓存。



#### 缓存失效的判据

**缓存失效**：是依赖数组中任意一项与上一次比较不相等时，React 丢弃旧缓存并重新调用 calculateValue 的行为。

- 比较方式：逐项做 Object.is 比较，原始值按值比较，对象与函数按引用比较。
- 引用陷阱：每次渲染新建的对象字面量或箭头函数作为依赖，会让缓存在每轮渲染都被判失效。
- 稳定来源：state、useRef 的 current、模块级常量作为依赖才具备稳定引用。

```jsx
function UserCard({ user }) {
  // user 引用变化时才重算
  const displayName = useMemo(() => `${user.firstName} ${user.lastName}`, [user]);

  // 错误：依赖是每次渲染新建的对象，缓存必然失效
  const options = useMemo(() => ({ theme: "dark" }), [{ theme: "dark" }]);
  return <p>{displayName}</p>;
}
```

> 依赖比较用的是引用相等而不是内容相等：对象内容一致但引用不同，缓存照样失效。

**速记**：依赖逐项做 Object.is 比较，引用变了缓存就失效。



#### 典型使用场景

**典型使用场景**：是缓存能被下游用于跳过工作的值，分昂贵派生数据与稳定对象引用两类。

- 昂贵派生数据：对列表排序、过滤、聚合的结果，避免每次渲染重算。
- 稳定对象引用：把配置对象、参数对象缓存下来，让作为依赖的其他 Hook 或子组件判断其保持不变。
- 传递依赖链：useMemo 的结果常作为另一个 useMemo 或 useEffect 的依赖项。

```jsx
function TodoBoard({ todos, filter }) {
  const visibleTodos = useMemo(
    () => todos.filter((todo) => (filter === "done" ? todo.done : !todo.done)),
    [todos, filter]
  );

  const stats = useMemo(
    () => ({ total: todos.length, visible: visibleTodos.length }),
    [todos, visibleTodos]
  );

  return <p>{stats.visible} / {stats.total}</p>;
}
```

**速记**：useMemo 用在昂贵派生数据与需要稳定引用的对象上。



#### 不要用 useMemo 做副作用

**在 useMemo 中写副作用**：是把请求、订阅、写日志等改变外部状态的操作放进 calculateValue 的错误做法。

- 语义不符：useMemo 是计算语义，不保证执行时机，React 可能在后续渲染中丢弃缓存并重跑。
- 重复执行：依赖变化会让 calculateValue 重跑，副作用因此被触发多次。
- 正确载体：副作用统一交给 useEffect（详见本主题第 9 篇 useEffect 与副作用）。

```jsx
function Profile({ userId }) {
  // 错误：在计算函数里发请求
  // const user = useMemo(() => fetchUser(userId), [userId]);

  const user = useMemo(() => pickUser(userMap, userId), [userMap, userId]);
  return <p>{user.name}</p>;
}
```

> [!WARNING]
> **警告内容**：useMemo 的计算函数必须是纯函数，放入副作用会导致请求重发、状态重复写入等难以复现的问题。

**速记**：useMemo 只做纯计算，副作用一律交给 useEffect。



### useCallback 与函数引用稳定

useCallback 缓存的是函数本身，用来让回调在多次渲染之间保持同一身份。

#### useCallback 的完整签名

**useCallback**：是用于缓存函数引用的内置 Hook，签名是 useCallback(fn, dependencies)，参数 fn 是需要缓存的函数，dependencies 是依赖数组，返回依赖不变时保持同一引用的函数。

- 首次渲染：返回 fn 本身，并记下依赖数组。
- 后续渲染：依赖逐项不变则返回上次缓存的同一个函数，变了则返回新函数。
- 与 useMemo 的关系：useCallback(fn, deps) 等价于 useMemo(() => fn, deps)，只是少了一层工厂函数。

```jsx
function SearchBox({ onSearch }) {
  const [keyword, setKeyword] = useState("");

  const handleSubmit = useCallback(
    () => onSearch(keyword),
    [onSearch, keyword]
  );

  return <button onClick={handleSubmit}>搜索</button>;
}
```

**速记**：useCallback(fn, dependencies) 缓存函数引用，依赖不变就返回同一个函数。



#### 函数引用每次渲染都会重建

**函数引用重建**：是组件函数体每执行一次、内部用函数声明或箭头函数创建的函数都成为新对象的现象。

- 引用不同：两个函数体完全相同的箭头函数，引用比较也不相等。
- 连锁影响：把新函数作为 props 传给被 memo 的子组件，会击穿 memo 的浅比较。
- 依赖影响：把新函数放进其他 Hook 的依赖数组，会让那些 Hook 在每轮渲染都重新执行。

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  const handleClick = () => setCount(count + 1); // 每次渲染都是新函数

  console.log(typeof handleClick); // "function"
  // 本轮渲染内的 handleClick 自比相等，但与上一轮渲染的引用不同
  return <button onClick={handleClick}>加一</button>;
}
```

**速记**：组件体内声明的函数每次渲染都是新对象，跨轮次的引用比较必然不等。



#### 稳定引用的价值

**稳定引用**：是同一函数或对象在多次渲染之间保持同一身份的属性，它让下游的相等比较有意义。

- 配合 memo 子组件：被 memo 包裹的子组件收到同一引用的回调时，可以跳过重新渲染。
- 作为其他 Hook 的依赖：useEffect 依赖一个稳定函数时，不会因无关渲染而反复重建订阅。
- 自定义 Hook 返回值：对外暴露稳定的回调，调用方才能安全地把它放进依赖数组。

```jsx
function TaskList({ tasks, onToggle }) {
  const handleToggle = useCallback((id) => onToggle(id), [onToggle]);

  return (
    <ul>
      {tasks.map((task) => (
        <TaskRow key={task.id} task={task} onToggle={handleToggle} />
      ))}
    </ul>
  );
}
```

> 真正需要稳定引用的场合分两类：传给被 memo 的子组件，以及作为其他 Hook 的依赖项。

**速记**：稳定引用让下游的相等比较成立，是 memo 与依赖数组生效的前提。



### 依赖与闭包

依赖数组不是可选的装饰，它决定了缓存值与被缓存函数读取到的到底是哪一轮数据。

#### 依赖数组必须写全

**依赖数组必须写全**：是因为缓存值或缓存函数只在依赖不变时复用，而函数内读取的每个外部值都参与其行为。

- 读取即依赖：calculateValue 或 fn 内部用到的 props、state、外层变量都应列入依赖。
- 行为正确性：漏列会让缓存值对应到过期的输入，输出与当前数据不符。
- 静态检查：使用 eslint-plugin-react-hooks 的 exhaustive-deps 规则可自动提示缺失项。

```jsx
function PriceTag({ price, discount }) {
  // 正确：把用到的 discount 也写进依赖
  const finalPrice = useMemo(() => price * (1 - discount), [price, discount]);
  return <span>{finalPrice}</span>;
}
```

**速记**：函数体内读取的外部值都是依赖，漏写会让缓存对应过期的输入。



#### 漏写依赖导致的闭包旧值

**闭包旧值**：是缓存下来的函数在其依赖缺失时，仍然引用创建那一轮渲染的变量快照的现象。

- 快照机制：每次渲染的变量都是那一轮的值，函数记住的是创建时的环境（机制详见本主题第 16 篇 Hook 规则与运行机制）。
- 表现症状：计数永远停在初始值、提交的是上一次的输入、定时器回调读取旧的 state。
- 常见根因：为了让回调引用稳定而故意写成空依赖数组。

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  const showCount = useCallback(() => {
    console.log("count 是", count); // 依赖漏写 count，读到的永远是 0
  }, []);

  return <button onClick={() => { setCount(count + 1); showCount(); }}>加一</button>;
}
```

> [!CAUTION]
> **注意内容**：故意漏写依赖换来的引用稳定，会让回调读到过期数据，问题往往在交互若干次之后才暴露。

**速记**：依赖漏写时缓存函数持有旧一轮渲染的变量快照，读到的是过期值。



#### 用函数式更新规避

**函数式更新**：是把状态更新写成接收旧值的函数形式 setState(previous => next)，从而不必把当前值列为依赖的手段。

- 写法：setCount((previous) => previous + 1)，参数 previous 由 React 传入最新值。
- 收益：回调不再读取外层 count，依赖数组可以合法地保持稳定。
- 适用范围：更新结果只依赖旧值本身，不依赖其他外部变量的场景。

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = useCallback(() => {
    setCount((previous) => previous + 1); // 不读取外层 count
  }, []); // 依赖为空也安全

  return <button onClick={handleClick}>{count}</button>;
}
```

**速记**：用函数式更新代替读取当前值，回调就能在依赖为空时保持正确。



#### 不要用忽略依赖的写法掩盖问题

**忽略依赖**：是通过禁用检查规则、隐藏依赖或把值转存到 ref 来逃避依赖数组校验的做法。

- 禁用注释：关闭 exhaustive-deps 提示会把真正的依赖缺失一并掩盖。
- 转存 ref：把值塞进 ref 可以绕开依赖，但更新时不会触发重新渲染，语义已经改变。
- 正确顺序：先判断这个值是否该由当前组件持有，再考虑拆分组件或改用函数式更新。

```jsx
function Editor({ draft }) {
  // 错误：注释禁掉检查并没有解决依赖缺失
  // eslint-disable-next-line react-hooks/exhaustive-deps
  const save = useCallback(() => sendDraft(draft), []);

  return <button onClick={save}>保存</button>;
}
```

> [!IMPORTANT]
> **重要内容**：依赖数组是正确性的一部分而不是性能开关，唯一可接受的空依赖情形是不读取任何会变化的值。

**速记**：禁用依赖检查只是掩盖问题，正确做法是消除依赖本身。



### 何时不该用

缓存只在必要时才划算，判断依据应当是测量结果与引用稳定性，而不是「多用更保险」。

#### 把 useMemo 当默认优化

**把 useMemo 当默认优化**：是对每个计算结果都套一层缓存、而不判断收益的错误习惯。

- 无收益：基础数值运算与字符串拼接的成本远低于缓存本身的记账开销。
- 递增复杂度：每个 useMemo 都要求维护一份依赖列表，改动时容易出错。
- 判断标准：只有测量显示该处确为瓶颈，或该值必须保持引用稳定时才使用。

```jsx
function Badge({ count }) {
  // 收益极低：一次类型转换不值得缓存
  const text = useMemo(() => String(count), [count]);
  return <span>{text}</span>;
}
```

**速记**：不是所有计算都值得缓存，只有确认瓶颈或需要稳定引用时才用 useMemo。



#### 缓存本身的成本

**缓存成本**：是 useMemo 与 useCallback 为了保存并比较依赖而付出的内存与计算开销。

- 保存开销：React 需要为每个 Hook 保留上一次的值与依赖数组。
- 比较开销：每次渲染都要逐项做 Object.is 比较，依赖越长成本越高。
- 首次无收益：首次渲染没有缓存可复用，缓存只对后续渲染产生作用。

```jsx
function ScoreRow({ score }) {
  // 依赖数组越长，每次渲染的比较成本越高
  const label = useMemo(
    () => `${score.name}: ${score.value}`,
    [score.name, score.value]
  );
  return <td>{label}</td>;
}
```

**速记**：缓存要付出保存与逐项比较的开销，依赖越多成本越高。



#### 语义保证与性能优化的区别

**语义保证**：是代码在任何情况下都必须成立的正确性约束；**性能优化**：是让代码更快但去掉后结果不变的手段。

- useMemo 不保证语义：React 保留在必要时丢弃缓存的权利，因此不能用它保证某段代码只执行一次。
- 正确性依赖 state：需要「只执行一次」的语义时，应当用 state、useRef 或 useEffect 表达。
- 区分方法：把缓存去掉后结果是否改变，改变说明写错了载体。

```jsx
function PermissionGate({ user }) {
  // 错误：把 useMemo 当作「只算一次」的保证
  const canEditByMemo = useMemo(() => checkPermission(user), [user]);

  // 正确：需要持有计算结果时用 state
  const [canEdit, setCanEdit] = useState(false);
  useEffect(() => setCanEdit(checkPermission(user)), [user]);

  return <p>{String(canEdit)}</p>;
}
```

> [!NOTE]
> **提醒内容**：useMemo 是性能提示而非语义保证，React 保留在需要时丢弃缓存的权利，正确性不能挂在它上面。

**速记**：useMemo 只是性能优化，去掉后结果必须不变，语义保证交给 state 与 useEffect。



#### 推荐的优化顺序

**推荐的优化顺序**：是先做结构层面的拆分与下移、再用缓存做微观调整的次序。

- 第一步拆分：把频繁更新的 state 收进更小的子组件，缩小重新渲染的范围。
- 第二步下移：把不依赖上层 state 的内容向下移动，让昂贵的子树不参与上层更新。
- 第三步缓存：以上手段仍不够时，才用 useMemo 与 useCallback 稳定计算与引用（memo 的完整用法详见本主题第 18 篇 性能优化：memo、懒加载与代码分割）。

```jsx
function Page() {
  const [keyword, setKeyword] = useState("");
  // 把输入框独立成组件，输入时只有它自己重新渲染
  return (
    <main>
      <SearchInput keyword={keyword} onChange={setKeyword} />
      <ExpensiveChart />
    </main>
  );
}
```

**速记**：先拆分组件与下移 state，最后才用缓存收尾。
