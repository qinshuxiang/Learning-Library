## useEffect 与副作用

渲染（render）只负责把 state 与 props 计算成 JSX，一切与外部世界交互的动作归入副作用（side effect），由 useEffect 在提交（commit）之后统一执行。本篇讲清副作用的边界、useEffect 的签名与执行时机、依赖数组的三种形态、清理函数的配对写法，以及数据请求中的竞态处理。

### 副作用与纯渲染的边界

本节先划清一条界线：哪些事可以放在渲染中做，哪些事必须放到渲染之外。

#### 副作用是什么

**副作用（side effect）**：是组件在计算渲染结果之外，对组件外部世界造成的可观察影响，例如修改 DOM、发起网络请求、启动定时器、订阅事件。

- 判定标准：一段代码除了返回结果之外，还改变了外部状态或与外部系统交互，就是副作用。
- 典型对象：浏览器 API、网络、计时器、全局事件、本地存储。
- 与渲染的关系：渲染函数的返回值只应由 state 与 props 决定，不应携带外部影响。

```jsx
function SearchBox() {
  const label = "搜索"; // 渲染只做计算
  return <input aria-label={label} />;
}
```

**速记**：副作用是渲染之外的对外影响，判断依据是有无改变外部世界。



#### 渲染期必须保持纯粹

**纯渲染**：指同一个 state 与 props 输入必然得到同一个 JSX 输出，且渲染过程中不修改任何外部值。

- 可重复：渲染可能被多次调用，结果必须一致，不能依赖调用次数。
- 不可外部写：渲染中不修改 DOM、不发请求、不写全局变量、不写 ref 的 current。
- 后果：渲染期做副作用会在并发渲染下重复执行或提前执行，导致界面与数据不同步。

> 渲染的纯粹性是 React 并发特性得以成立的前提；渲染中一旦夹带外部写操作，输出就会随时序漂移。

**速记**：纯渲染是同输入同输出且无外部写，渲染过程中不做任何外部交互。



#### 副作用的归属位置

**副作用的归属位置**：是按触发原因把副作用分配给不同载体，而不是一律塞进 useEffect。

- 由用户操作触发：写在事件处理函数中，如点击提交、输入变化。
- 由渲染结果触发且需要与外部同步：写在 useEffect 中，如订阅、请求。
- 由 state 计算得出：不要写成副作用，直接用变量计算，属于派生状态。
- 只需在初始化时求值一次：用惰性初始化，而不是放进副作用。

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const handleClick = () => {
    setCount(count + 1);
    console.log("clicked", count + 1); // 用户触发的副作用写在处理函数里
  };
  return <button onClick={handleClick}>{count}</button>;
}
```

> 判断口诀：先问这件事由谁引发，用户引发放事件处理，渲染结果引发放 useEffect，能计算出来的不做副作用。

**速记**：用户引发放事件处理，渲染引发放 useEffect，能计算出来的不做副作用。



#### 常见副作用清单

**常见副作用清单**：是把高频副作用与其撤销动作成对列出，便于排查遗漏。

- 订阅类：事件监听、WebSocket、外部数据源订阅，对应取消订阅。
- 计时类：setTimeout、setInterval，对应 clearTimeout、clearInterval。
- 请求类：fetch 与 XMLHttpRequest，对应 AbortController 取消。
- 命令式 DOM 类：聚焦、滚动、测量尺寸、第三方控件初始化，对应状态还原或实例销毁。

```jsx
useEffect(() => {
  const controller = new AbortController();
  const url = "https://example.com/users/" + userId;
  fetch(url, { signal: controller.signal })
    .then((response) => response.json())
    .then(setUser);
  return () => controller.abort(); // 请求类副作用对应取消
}, [userId]);
```

> 第三方控件（地图、图表、编辑器）通常在副作用中初始化，并在清理函数中销毁实例，否则会残留 DOM 与监听器。

**速记**：订阅、计时、请求、命令式 DOM 四类副作用都必须配一份清理动作。



### useEffect 的签名与执行时机

useEffect 把副作用安排在提交之后执行，本节给出完整签名并说明它的时序。

#### useEffect 的完整签名

**useEffect**：是接收一个 setup 函数与一个可选依赖数组、用于在提交后同步副作用的 Hook，签名为 useEffect(setup, dependencies?)，自身不返回值。

- setup：函数，内部编写副作用逻辑，可以返回一个清理函数，也可以不返回。
- dependencies：可选，依赖数组（dependency array），列出 setup 中读取的响应式值。
- 返回值：useEffect 返回 undefined，setup 返回的可选函数才是清理函数。
- 执行位置：setup 只在提交阶段之后执行，绝不在渲染期间执行。

```jsx
// useEffect(setup, dependencies?)
function useDocumentTitle(title) {
  useEffect(() => {
    document.title = title;                      // setup
    return () => { document.title = "学习库"; }; // 可选清理函数
  }, [title]);                                   // 依赖数组
  return null;
}
```

> setup 每次渲染后都可能重新执行，是否执行由依赖数组决定，详见本篇依赖数组的三种形态。

**速记**：useEffect(setup, dependencies?) 接收副作用函数与可选依赖数组，setup 可返回清理函数，自身无返回值。



#### 提交阶段之后执行

**执行时机**：是浏览器完成 DOM 更新之后，React 再运行 useEffect 中的 setup，此时新界面已经写入文档。

- 顺序：渲染阶段计算 JSX，提交阶段写入 DOM，之后执行副作用。
- 可见性：副作用运行前浏览器可能已经完成一次绘制，属于被动效应（passive effect）。
- 阻塞性：被动效应不阻塞绘制；若副作用必须在绘制前同步完成，应改用 useLayoutEffect。

```jsx
function TimerPanel() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    console.log("DOM 已更新，副作用开始执行"); // 在提交之后
  }, [seconds]);
  return <p>{seconds}</p>;
}
```

> [!NOTE]
> **提醒内容**：useEffect 属于被动效应，不保证在浏览器绘制之前运行；需要同步读取布局再绘制时改用 useLayoutEffect。

**速记**：useEffect 在提交并写入 DOM 之后运行，不阻塞浏览器绘制。



#### 执行顺序与浏览器绘制

**执行顺序**：指同一轮更新中多个副作用的运行次序，以及它们与浏览器绘制之间的相对关系。

- 同组件内：按声明顺序依次执行多个 useEffect。
- 跨组件：按组件在树中的完成顺序执行，子组件的副作用先于父组件。
- 与绘制的关系：被动效应安排在绘制之后，用户可能先看到新界面再看到副作用结果。

```jsx
useEffect(() => console.log("第一个副作用"), []);
useEffect(() => console.log("第二个副作用"), []);
// 输出顺序：第一个副作用 → 第二个副作用
```

> 依赖绘制结果的测量逻辑若写成被动效应，会多触发一次布局计算，此时应改用 useLayoutEffect。

**速记**：同组件按声明顺序、跨组件按完成顺序执行，被动效应在绘制之后运行。



#### 与渲染流程阶段的对应关系

**阶段对应关系**：是把副作用挂到渲染流程的阶段上理解，用三句话覆盖全部时序语义。

- 挂载后执行一次：依赖数组为空时，setup 在首次提交后执行一次。
- 依赖变化时执行：上一轮清理函数先执行，再执行新的 setup。
- 卸载前执行：组件从树中移除时执行最后一次清理函数。
- 统一模型：三种情形共用同一条规则，即先清旧、再跑新，卸载时只清不跑。

```jsx
function PageTitle({ page }) {
  useEffect(() => {
    document.title = "第 " + page + " 页";
    return () => { document.title = "学习库"; }; // 卸载前或依赖变化前清理
  }, [page]);
  return <span>{page}</span>;
}
```

> 描述行为时用「提交后执行一次」「依赖变化时先清后跑」「卸载前清理」三句话，即可完整表达时序。

**速记**：挂载后一次、依赖变化先清后跑、卸载前清理，三句话覆盖全部时序。



### 依赖数组的三种形态

依赖数组决定 setup 的执行频率，三种写法对应三种语义，写错是死循环与陈旧值的常见来源。

#### 不传依赖数组

**不传依赖数组**：指省略第二个参数，每次渲染并提交之后都执行一次 setup。

- 频率：每次渲染都执行，包含首次挂载与任意 state、props 变化引发的更新。
- 清理：每一轮执行前先执行上一轮的清理函数。
- 风险：若 setup 中调用状态更新函数且更新无法收敛，会形成执行副作用、更新状态、再次渲染的循环。

```jsx
useEffect(() => {
  console.log("每次渲染后都执行"); // 没有依赖数组
});
```

> [!CAUTION]
> **注意内容**：省略依赖数组时若在 setup 中无条件调用状态更新函数，会触发无限循环，必须补上依赖数组或加上收敛条件。

**速记**：不传依赖数组等于每次提交后都执行，必须警惕状态更新引发的循环。



#### 传入空数组

**传入空数组**：指第二个参数传一个空数组字面量，setup 只在首次挂载后的提交中执行一次。

- 频率：整个组件存活期只执行一次，更新与重新渲染都不会再次执行。
- 清理：只在组件卸载时执行一次清理。
- 适用：只需建立一次的外部连接、只在初始化时读取一次的数据。
- 代价：setup 中读取的 state 与 props 停留在首次渲染的值，形成闭包陈旧值。

```jsx
useEffect(() => {
  console.log("只在挂载后执行一次"); // 空数组
}, []);
```

> 空数组表示没有依赖，而不是不追踪依赖；只要 setup 里用到了会变化的值，就必须把它写进数组。

**速记**：空数组等于仅挂载后执行一次，代价是 setup 只能看到首次渲染的值。



#### 传入依赖值

**传入依赖值**：是把 setup 中读取的响应式值逐项列进数组，依赖不变则跳过执行。

- 判定：数组内每一项与上一轮比较，全部相等则跳过本轮副作用。
- 完整性：setup 中读取的每个 state、props 与派生值都应列入，缺失项会读到陈旧值。
- 变化即执行：任一项改变都会先执行清理，再执行新的 setup。

```jsx
function SearchBox({ keyword }) {
  useEffect(() => {
    console.log("只在 keyword 变化时执行：" + keyword);
  }, [keyword]); // 依赖 keyword
  return <span>{keyword}</span>;
}
```

> 依赖表越完整，副作用与渲染结果越一致；把缺失依赖靠注释屏蔽，等于把陈旧值问题留给线上。

**速记**：列出 setup 读取的所有响应式值，全等则跳过，任一变化则先清后跑。



#### 依赖的比较方式

**Object.is 比较**：是 React 判断依赖项是否变化的算法，与严格相等几乎一致，仅两处差异。

- 判定规则：Object.is 上一轮值与本轮值的结果为真，则视为未变化。
- 两处差异：Object.is 认为两个 NaN 相等，认为正零与负零不相等。
- 引用类型：对象、数组、函数按引用比较，每次渲染新建的字面量都会被视为新值。
- 后果：把内联对象或内联函数写进依赖，会因引用变化而每轮都执行副作用。

```jsx
function OptionList() {
  const [page, setPage] = useState(1);
  useEffect(() => {
    loadOptions({ page: 1 }); // 每轮都传入新对象
  }, [{ page: 1 }]); // 引用不同即视为变化，正确写法是改为 [page]
  return <button onClick={() => setPage(page + 1)}>{page}</button>;
}
```

> [!WARNING]
> **警告内容**：在依赖数组中放内联对象或内联函数，会因引用每次不同而使副作用每轮触发，应先把值提到变量或改用原始值。

**速记**：依赖用 Object.is 比较，引用类型按引用判定，内联字面量等于每轮都变。



### 清理函数与订阅

清理函数（cleanup function）是 setup 返回的函数，用于撤销这一轮副作用建立的外部影响。

#### 清理函数何时被调用

**清理函数的调用时机**：是在依赖变化前后、组件卸载时，以及开发环境下严格模式的双调用中执行。

- 依赖变化：先运行上一轮的清理函数，再运行新的 setup，保证旧影响已撤销。
- 组件卸载：执行最后一次清理函数，释放订阅与计时器。
- 开发严格模式：React 19 的开发模式会额外挂载与卸载一次组件，用双调用暴露清理缺失。

```jsx
useEffect(() => {
  const id = setInterval(() => console.log("tick"), 1000);
  return () => clearInterval(id); // 依赖变化或卸载时调用
}, []);
```

> [!NOTE]
> **提醒内容**：开发环境严格模式下的双调用是刻意设计，用于暴露未清理的副作用，生产环境不会重复挂载。

**速记**：清理函数在依赖变化前与卸载时调用，严格模式下的双调用用于暴露缺失清理。



#### 清理的顺序

**清理的顺序**：指同一次更新里多个清理函数与多个 setup 的相对次序。

- 组件内：清理函数按声明顺序执行。
- 跨组件：父组件的清理先于子组件的清理。
- 与 setup 的关系：同一轮里先执行完全部清理，再执行全部新的 setup。

```jsx
function CleanupOrder() {
  useEffect(() => () => console.log("清理 A"), []);
  useEffect(() => () => console.log("清理 B"), []);
  return <span>order</span>;
}
// 卸载时按声明顺序输出：清理 A → 清理 B
```

> 清理与建立严格配对，才能让任意时刻的外部资源数量与组件树的当前状态一致。

**速记**：清理按声明顺序执行，先清完再建立，跨组件时父先于子。



#### 订阅与取消订阅的配对写法

**订阅与取消订阅**：是在同一处 setup 中建立监听、在同一处清理函数中移除监听，两者的函数引用必须一致。

- 配对原则：addEventListener 与 removeEventListener 的第二个参数传同一个函数引用。
- 常见错误：把箭头函数直接传给 addEventListener，移除时传的是新函数，导致监听器残留。
- 外部数据源：订阅接口返回的取消订阅函数应原样从清理函数返回。

```jsx
function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);
  return <span>{width}</span>;
}
```

> 监听器函数必须先保存为具名常量，才能在清理函数中被同一个引用移除；内联箭头函数无法被移除。

**速记**：建立与移除使用同一个函数引用，外部订阅返回的取消函数直接作为清理函数。



#### 定时器的正确清理与内存泄漏

**内存泄漏（memory leak）**：是副作用建立的外部资源在组件卸载后仍被引用而无法回收的状态。

- 定时器：setInterval 必须在清理函数中 clearInterval，否则回调持续运行并持有组件闭包。
- 请求：未取消的请求在组件卸载后写入状态，会引发告警与无效渲染。
- 监听与连接：未移除的事件监听、未关闭的 WebSocket 会持续占用内存与网络。
- 自查方法：为每个 setup 中的建立动作写下对应的撤销动作，缺一即为泄漏点。

```jsx
function TimerPanel() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setSeconds((previous) => previous + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{seconds}</p>;
}
```

> 清理函数是防止内存泄漏的唯一保证：只要副作用建立了长期存活的对象，就必须在清理函数中处理它。

**速记**：每个建立动作配一个撤销动作，定时器、请求、监听的清理缺失即内存泄漏。



### 数据请求的写法与竞态

数据请求是 useEffect 最常见的用途，本节给出基本写法、竞态处理、状态维护与抽取方式。

#### 在副作用中发起请求

**在副作用中发起请求**：是把请求放进 setup，使请求随组件提交发起，并随卸载或依赖变化取消。

- 基本形态：setup 中调用请求函数，用 then 或内部 async 函数处理结果。
- 直接 async：setup 本身不能是 async 函数，它返回的是 Promise 而不是清理函数。
- 依赖：请求参数放进依赖数组，参数变化时重新请求。

```jsx
function UserCard({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    async function loadUser() {
      const response = await fetch("https://example.com/users/" + userId);
      setUser(await response.json());
    }
    loadUser();
  }, [userId]);
  return <p>{user ? user.name : "loading"}</p>;
}
```

> setup 写成 async 函数会返回 Promise，React 会把它当作清理函数调用并报错，务必用内部 async 函数包裹异步逻辑。

**速记**：请求写在 setup 中，setup 不能是 async 函数，参数变化时靠依赖数组重新发起。



#### 竞态与忽略过时响应

**竞态（race condition）**：是多个请求并发返回时，后发请求先返回导致旧响应覆盖新结果的现象。

- 成因：请求耗时不同，响应到达顺序与发起顺序无关。
- 标志位方案：在 setup 内维护 aborted 标志，清理函数中置为真，响应返回后先判断再写入状态。
- 控制器方案：创建 AbortController，把 signal 传给 fetch，清理函数中调用 abort 真正中断请求。
- 取舍：标志位方案兼容性好，控制器方案能节省网络与解析开销。

```jsx
useEffect(() => {
  let aborted = false;
  async function loadUser() {
    const response = await fetch("https://example.com/users/" + userId);
    if (!aborted) setUser(await response.json()); // 只在未过时时写入
  }
  loadUser();
  return () => { aborted = true; }; // 清理时标记为过时
}, [userId]);
```

> [!IMPORTANT]
> **重要内容**：请求随组件卸载或参数变化取消，是避免竞态与卸载后写入状态的必要条件，缺少取消环节会直接导致界面显示过期数据。

**速记**：用 aborted 标志或 AbortController 在清理时取消旧请求，只让最新请求写入状态。



#### 加载态与错误态的维护

**加载态与错误态**：是与数据并列的两种状态，用于表达请求进行中与请求失败。

- 加载态：请求发起时置为真，返回后置为假，用于显示占位或骨架。
- 错误态：捕获异常后写入错误信息，并清空数据，避免展示半成品。
- 一致性：三种状态在同一处更新，避免出现有数据又同时加载中的矛盾组合。

```jsx
function UserPanel({ userId }) {
  const [state, setState] = useState({ user: null, loading: true, error: null });
  useEffect(() => {
    setState((previous) => ({ ...previous, loading: true, error: null }));
    async function loadUser() {
      try {
        const response = await fetch("https://example.com/users/" + userId);
        if (!response.ok) throw new Error("请求失败：" + response.status);
        setState({ user: await response.json(), loading: false, error: null });
      } catch (caught) {
        setState({ user: null, loading: false, error: caught.message });
      }
    }
    loadUser();
  }, [userId]);
  if (state.loading) return <p>加载中</p>;
  if (state.error) return <p>{state.error}</p>;
  return <p>{state.user.name}</p>;
}
```

> 加载态、数据、错误态三者构成一次请求的完整视图；只维护数据会无法区分没有值与此刻还没来。

**速记**：请求同时维护加载态、数据与错误态，并在 finally 中结束加载态。



#### 抽成自定义 Hook

**自定义 Hook（custom Hook）**：是以 use 开头、内部调用其他 Hook 来复用状态逻辑的函数。

- 命名：必须以 use 开头，便于规则检查工具识别。
- 职责：把请求、取消与三态维护整体封装，组件只消费结果。
- 返回：按使用方需要返回数据、加载态、错误态，必要时附带重新请求的函数。
- 边界：自定义 Hook 只复用逻辑，不复用 UI，UI 复用属于组合模式（详见本主题第 13 篇 组件组合：children、render props 与 HOC）。

```jsx
function useUserProfile(userId) {
  const [state, setState] = useState({ user: null, loading: true, error: null });
  useEffect(() => {
    let aborted = false;
    async function loadUser() {
      try {
        const response = await fetch("https://example.com/users/" + userId);
        if (!aborted) setState({ user: await response.json(), loading: false, error: null });
      } catch (caught) {
        if (!aborted) setState({ user: null, loading: false, error: caught.message });
      }
    }
    loadUser();
    return () => { aborted = true; };
  }, [userId]);
  return state; // { user, loading, error }
}
```

> 自定义 Hook 与使用它的组件共享同一套 state 语义，但每次调用都有独立的内部状态，不在调用方之间共享。更完整的抽取步骤与返回值设计详见本主题第 15 篇 自定义 Hook。

**速记**：把请求与三态封装成 use 开头的自定义 Hook，组件只消费返回值。
