## 性能优化：memo、懒加载与代码分割

### 性能问题的定位

在没有测量之前，任何优化都是猜测。本模块给出定位 React 性能问题的流程与判断依据；渲染流程本身详见本主题第 17 篇渲染原理：Fiber 与协调。

#### 先测量再优化的原则

**先测量再优化的原则**：是先确认瓶颈确实存在、并确定它发生在哪一步，再选择对应手段；未经测量的优化往往只改变代码形状，并不改善真实开销。

- 建立基线：先记录当前的关键数字（渲染耗时、交互响应时间），作为改动后对比的基准。
- 定位位置：区分耗时来自渲染阶段的计算，还是来自某棵过重的子树。
- 一次只改一处：每次改动后重新测量，才能确认收益来自哪一处。
- 保留记录：把测量结果与改动写在一起，避免把偶然波动当成收益。

```jsx
// 用 performance.now 粗略记录一段工作的耗时，作为改动的对比基线
function measureRenderCost(label, action) {
  const start = performance.now();
  action();
  const cost = performance.now() - start;
  console.log(label, Math.round(cost), "ms"); // 例如 交互耗时 18 ms
  return cost;
}

measureRenderCost("交互耗时", () => {
  const squares = Array.from({ length: 1000 }, (_, i) => i * i);
  return squares.length;
});
```

> [!TIP]
> **建议内容**：优化前先记录基线并区分渲染次数与单次开销，改动后重新测量，否则无法判断收益是否真实存在。

**速记**：先测出瓶颈在哪，再一次只改一处并复测，优化才可验证。



#### React DevTools Profiler 的用法

**React DevTools Profiler**：是浏览器开发者工具的 React 面板提供的性能录制功能，记录一段时间内每次提交（commit）涉及的组件、耗时与渲染原因。

- 录制：点击录制按钮，操作页面后停止录制，得到一串提交记录。
- 火焰图：按提交展示组件树的渲染耗时，横条越长表示该组件本次渲染占比越高。
- 排名视图：按耗时从高到低列出组件，便于先处理占比最大的部分。
- 提交耗时：每次提交的总耗时与各组件耗时分别列出，用于判断问题出在哪一层。
- 渲染原因：标注本次渲染由 props 变化、state 变化还是父组件渲染引起。

```jsx
function handleRender(id, phase, actualDuration, baseDuration) {
  // Profiler 在每次提交后调用 onRender，actualDuration 是本次提交实际耗时
  // baseDuration 是该子树在不做记忆化时的估算耗时，两者对比可判断记忆化收益
  console.log(id, phase, Math.round(actualDuration), Math.round(baseDuration));
// 例如 "SearchResults update 12 3"
}

function SearchResultsPage({ keyword }) {
  return (
    <Profiler id="SearchResults" onRender={handleRender}>
      <SearchResults keyword={keyword} />
    </Profiler>
  );
}
```

**速记**：Profiler 按提交记录组件耗时并标注渲染原因，火焰图与排名视图用于找占比最大的组件。



#### 定位高频重新渲染的组件

**高频重新渲染**：指同一组件在短时间内被反复渲染，多数时候并不是它自身的数据在变，而是被父组件的渲染带动。

- 计数：在组件函数体里打印日志，确认它一次交互被调用了多少次。
- 看来源：用 Profiler 的渲染原因判断是 props 变化、state 变化还是父组件渲染。
- 看层级：渲染由父组件带动时，问题应在上层解决，而不是在子组件里加缓存。
- 看 props：确认传入的 props 是否每次都是新对象或新函数，这类变化会让浅比较失效。

```jsx
function SearchResultItem({ item }) {
  // 每次渲染都会打印，用于确认该组件被调用的频率
  console.log("render SearchResultItem", item.id);
  return <li>{item.title}</li>;
}
```

> 开发环境的日志行数会因严格模式的重复调用而翻倍，成因详见本主题第 16 篇 Hook 规则与运行机制。

**速记**：高频重新渲染要从渲染原因与所在层级上定位，而不是直接在子组件里加缓存。



#### 渲染次数与单次开销的区分

**渲染次数与单次开销的区分**：是把性能问题归为「同一组件被渲染太多次」还是「某次渲染本身太重」两类，二者的解法不同。

- 次数问题：单次渲染不慢，但被频繁触发；解决方向是减少触发来源或跳过不必要的渲染。
- 开销问题：渲染次数不多，但单次渲染里计算量或子树规模过大；解决方向是减少单次工作量。
- 判断依据：Profiler 的组件耗时占比高且提交次数少，属于开销问题。
- 组合情形：两者同时存在时，先处理单次开销大的一处，再处理高频触发的一处。

> 次数问题与开销问题混在一起时，优化手段会互相抵消：为高频组件加记忆化，并不能减少它每次渲染里的计算量。

**速记**：先分清是渲染次数多还是单次开销大，再选择减少触发来源或减少单次工作量。



### React.memo 与浅比较

React.memo 是跳过不必要渲染的入口，它的效果完全取决于 props 的比较方式，因此必须理解默认浅比较的边界。

#### React.memo 的定义与签名

**React.memo**：是接收一个组件并返回经过记忆化的新组件的高阶组件，签名写作 memo(Component, arePropsEqual?)，其中 arePropsEqual 是可选参数，接收 prevProps 与 nextProps 并返回布尔值。

- 返回值：返回一个新组件，用法与传入的组件一致，可以照常接收 props 与 children。
- 生效条件：父组件重新渲染时，React 先比较新旧 props，比较结果表明未变化就跳过该组件的渲染。
- 比较方式：不传 arePropsEqual 时使用默认的浅比较。
- 适用范围：只对函数组件生效，对组件自身 state 变化引起的渲染无效。
- 使用边界：只跳过该组件的渲染，不阻止父组件自身的渲染过程。

```jsx
import { memo } from "react";

function UserCard({ user, onSelect }) {
  console.log("渲染 UserCard", user.id);
  return <button onClick={() => onSelect(user.id)}>{user.name}</button>;
}

// 返回的新组件与 UserCard 用法一致，父组件渲染时若 props 未变则跳过
export const MemoUserCard = memo(UserCard);
```

**速记**：memo(Component, arePropsEqual?) 返回记忆化组件，props 比较结果未变化时跳过该组件的渲染。



#### 默认的浅比较 props

**浅比较（shallow comparison）**：是逐项比较两个对象第一层属性的比较方式，值用 Object.is 判断相等，引用类型只比较引用而不深入比较内容。

- 只比一层：对象、数组、函数等引用类型比较的是引用是否相同，不比较内部成员。
- 原始值：字符串、数字、布尔值等按值比较。
- 结果含义：所有第一层属性都相等才认为 props 未变，任一项不同就重新渲染。
- 与深比较的区别：深比较会递归比较内容，代价随数据规模增长，React 默认不采用。

> 浅比较对嵌套结构天然保守：内层数据变了，只要外层引用没变，memo 组件就不会重新渲染，这也是原地修改数据特别危险的原因。

**速记**：默认浅比较只比 props 第一层，引用类型的引用变了就算 props 变化。



#### 浅比较的失效场景

**浅比较失效**：指 props 在内容上没有变化、却因为传入的是新引用而被判定为变化，使 memo 失去作用。

- 内联对象：在 JSX 里写对象字面量，每次渲染都创建新对象。
- 内联函数：把箭头函数直接传给子组件，每次渲染都是新函数。
- 内联数组：直接书写数组字面量同样每次新建。
- 局部计算：在渲染过程中用 map、filter 直接生成待传数据，也会得到新引用。

```jsx
function UserList({ users }) {
  return (
    <ul>
      {users.map((user) => (
        // 每次渲染都新建箭头函数，MemoUserCard 的浅比较必然失败
        <MemoUserCard key={user.id} user={user} onSelect={(id) => console.log(id)} />
      ))}
    </ul>
  );
}
```

> 浅比较失效时 memo 不会带来收益，反而多了一次比较开销，因此要先修正 props 的稳定性。

**速记**：内联对象、内联函数与每次新建的数组会让浅比较判定为变化，memo 随之失效。



#### 与 useMemo 及 useCallback 的配合

**配合方式**：是用 useMemo 稳定计算出的对象或数组、用 useCallback 稳定函数引用，使传给 memo 组件的 props 在内容不变时保持同一引用。

- useMemo：签名 useMemo(calculateValue, dependencies)，依赖未变时返回上一次的计算结果。
- useCallback：签名 useCallback(fn, dependencies)，依赖未变时返回同一个函数引用。
- 配合顺序：先稳定子组件收到的 props，再让 memo 生效，二者缺一不可。
- 职责边界：两个 Hook 只做缓存，不改变计算本身仍需保持纯函数的事实（用法详见本主题第 11 篇 useMemo 与 useCallback）。

```jsx
function UserList({ users, onSelect }) {
  const sortedUsers = useMemo(
    () => [...users].sort((a, b) => a.name.localeCompare(b.name)),
    [users]
  );
  const handleSelect = useCallback((id) => onSelect(id), [onSelect]);

  return (
    <ul>
      {sortedUsers.map((user) => (
        <MemoUserCard key={user.id} user={user} onSelect={handleSelect} />
      ))}
    </ul>
  );
}
```

> [!CAUTION]
> **注意内容**：给 memo 组件传入自定义比较函数时，比较逻辑若遗漏了某个会影响展示的 props，界面会在数据变化后不更新，这类问题排查成本很高。

**速记**：用 useMemo 与 useCallback 稳定 props 引用，memo 才能真正跳过渲染。



### 列表与子组件优化

列表是重新渲染问题最集中的地方：条目多、层级深、props 又容易写成新引用。本模块给出针对列表的处理手段。

#### 长列表的渲染代价

**长列表的渲染代价**：指列表项数量增加时，每次渲染需要创建的元素与执行的工作量随之线性增长，单次渲染的开销也就随之上升。

- 数量放大：每个条目对应一组元素与组件调用，条目越多单次渲染越慢。
- 重复创建：滚动或输入触发的渲染会重建整份列表元素。
- 内存占用：树中同时存在的节点越多，比较与提交阶段的工作量越大。
- 判断门槛：条目数量大且每次渲染都全量重建时，才需要专门处理。

> 列表优化的第一选择通常是减少每次渲染要处理的条目数量与元素创建次数，而不是给每个条目都套上记忆化。

**速记**：列表项数量增加会线性放大单次渲染的元素创建与提交工作量。



#### 把不变的部分上提或抽取

**不变部分上提**：是把与列表数据无关、又需要传给每个条目的值移到组件外部或上层，避免每次渲染重新创建。**组件抽取**：是把列表项拆成独立组件，把渲染边界缩到真正变化的那一项。

- 常量上提：不依赖 props 与 state 的配置对象、样式对象定义在组件外部。
- 组件抽取：把列表项抽成独立组件，让每个条目的渲染可以单独评估。
- 缓存计算：对由 items 派生的结果用 useMemo 缓存，避免每次渲染重新计算。
- 固定兄弟：与列表无关的兄弟节点尽量不受列表更新影响。

```jsx
const itemStyle = { padding: "8px", borderBottom: "1px solid #eee" };

function TodoItem({ todo }) {
  return <li style={itemStyle}>{todo.title}</li>;
}

function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <TodoItem key={todo.id} todo={todo} />
      ))}
    </ul>
  );
}
```

**速记**：把常量上提到组件外、把列表项抽成独立组件，可把渲染边界缩小到真正变化的部分。



#### 为列表项传稳定 props

**稳定 props**：指在多次渲染之间保持同一引用或同一原始值的 props，配合 memo 才能让列表项跳过不必要的渲染。

- 传标识而非对象：能在条目内部按 id 取值时，不要传整个大对象。
- 传稳定函数：事件处理函数用 useCallback 固定，或改为在条目内部调用上层传入的稳定引用。
- 避免内联：不要把对象字面量、数组字面量与箭头函数直接写在映射里。
- 比较代价：条目数量极大时，memo 的比较成本也要计入，必要时改用虚拟滚动。

```jsx
function ItemRow({ itemId, onSelect }) {
  // itemId 是原始值，onSelect 引用稳定，再用 memo 包一层时浅比较可以通过
  return <li onClick={() => onSelect(itemId)}>{itemId}</li>;
}

const handleSelect = useCallback((id) => console.log("选中", id), []);
const MemoItemRow = memo(ItemRow);
```

**速记**：给列表项传原始值与稳定函数，避免内联对象与内联函数，浅比较才能通过。



#### 虚拟滚动的思路与适用条件

**虚拟滚动（virtual scrolling）**：是只渲染视口内可见的列表项、用占位空间维持滚动条长度的做法，使实际渲染的节点数量与列表总长度无关。

- 计算窗口：根据滚动位置与行高算出当前可见的起始索引与数量。
- 占位撑高：用一个高度等于总行高的容器维持滚动条比例，可见项按偏移绘制。
- 适用条件：行高相对固定、条目数量极大，且确实测出渲染是瓶颈时才值得引入。
- 引入代价：实现复杂度上升，无障碍与查找定位等能力需要额外处理，通常优先使用成熟库。

```jsx
function WindowedList({ items, rowHeight, viewportHeight }) {
  const [scrollTop, setScrollTop] = useState(0);
  const startIndex = Math.floor(scrollTop / rowHeight);
  const visibleCount = Math.ceil(viewportHeight / rowHeight);
  const visibleItems = items.slice(startIndex, startIndex + visibleCount);
  const offsetTop = startIndex * rowHeight;

  return (
    <div
      style={{ height: viewportHeight, overflowY: "auto" }}
      onScroll={(event) => setScrollTop(event.currentTarget.scrollTop)}
    >
      <div style={{ height: items.length * rowHeight }}>
        <div style={{ transform: `translateY(${offsetTop}px)` }}>
          {visibleItems.map((item) => (
            <div key={item.id} style={{ height: rowHeight }}>{item.title}</div>
          ))}
        </div>
      </div>
    </div>
  );
}
```

> [!NOTE]
> **提醒内容**：虚拟滚动改变的是渲染节点数量，若瓶颈来自单次渲染里的计算，应先把计算结果缓存起来，再考虑引入虚拟滚动。

**速记**：虚拟滚动只渲染可见项并用占位撑高滚动条，适用于行高固定且条目极多的列表。



### lazy 与 Suspense 分包

代码分割（code splitting）把一份入口产物拆成多份按需下载，React.lazy 与 Suspense 负责在组件层面表达「这份代码还没有到位」。

#### React.lazy 的签名

**React.lazy**：是接收一个返回动态导入 Promise 的函数、返回可渲染组件的 API，签名写作 lazy(load)，其中 load 是无参数函数，调用后返回 Promise，其 resolve 值是带有 default 导出的模块。

- 调用位置：必须在组件外部调用，不能在渲染过程中调用，否则每次渲染都会新建组件。
- 默认导出：要求模块提供 default 导出，具名导出需要补一层转换。
- 返回值：返回一个组件，首次渲染时才开始下载对应模块。
- 缓存：同一次调用只加载一次，后续渲染复用已解析的模块。

```jsx
import { lazy } from "react";

const UserPanel = lazy(() => import("./UserPanel"));
// 具名导出需要补一层转换
const UserSetting = lazy(() =>
  import("./settings").then((module) => ({ default: module.UserSetting }))
);
```

**速记**：lazy(load) 接收返回 Promise 的函数并返回组件，必须在组件外部调用且模块需有 default 导出。



#### 配 Suspense 的 fallback

**Suspense**：是负责在包裹的懒加载组件尚未就绪时渲染备用内容的组件，它接收 fallback 属性，fallback 是等待期间显示的元素。

- 包裹范围：lazy 组件必须处于某个 Suspense 之内，否则加载期间会抛错。
- 备用内容：fallback 建议使用与最终内容尺寸相近的占位，减少布局跳动。
- 边界粒度：Suspense 的粒度决定等待时整块替换的范围，粒度越细等待区域越小。
- 职责边界：此处只负责分包加载；错误边界与 Suspense 配合数据获取的用法归本主题第 19 篇错误边界、Suspense 与并发特性。

```jsx
import { lazy, Suspense } from "react";

const UserPanel = lazy(() => import("./UserPanel"));

function App({ userId }) {
  return (
    <Suspense fallback={<p>正在加载用户面板……</p>}>
      <UserPanel userId={userId} />
    </Suspense>
  );
}
```

> [!IMPORTANT]
> **重要内容**：lazy 组件必须放在 Suspense 之内；Suspense 只处理加载中的等待，运行期抛出的错误要交给错误边界处理。

**速记**：Suspense 用 fallback 承接等待期间的内容，lazy 组件必须被它包裹，错误处理另归第 19 篇。



#### 路由级分包的常见做法

**路由级分包**：是把每个路由对应的页面组件各自拆成一份按需加载的产物，通常按页面边界挑选分包点。

- 分包粒度：以页面或大块面板为单位，避免切得太碎导致请求数过多。
- 首屏优先：首屏必须用到的组件直接打包进入口，其余按路由懒加载。
- 共享模块：多个分包共用且体积较大的模块由构建工具提取成公共产物。
- 路由接入：与路由库的接入方式详见本主题第 20 篇 React Router，本篇只到组件这一层。

```jsx
const UserSettings = lazy(() => import("./UserSettings"));
const BillingPanel = lazy(() => import("./BillingPanel"));

function RoutedPage({ route }) {
  if (route === "settings") {
    return <UserSettings />;
  }
  if (route === "billing") {
    return <BillingPanel />;
  }
  return <p>请选择页面</p>;
}
```

**速记**：路由级分包按页面边界切分，首屏同步打包、其余按需加载，共享模块单独提取。



#### 预加载的时机

**预加载（prefetch）**：是在用户真正需要之前提前触发模块下载的做法，用于减少点击后的等待，代价是提前消耗带宽。

- 触发时机：用户悬停、聚焦或进入可能的下一步时才触发，命中率较高。
- 保持克制：对多数用户不会访问的分包不要预加载，否则等于放弃分包的意义。
- 复用加载函数：把动态导入抽成一个函数，懒加载与预加载共用同一份调用。
- 弱网反馈：加载时间可能较长时，应给等待状态更明显的提示。

```jsx
function loadUserPanel() {
```

### 性能分析工具

测量工具决定了能否把「感觉慢」变成可比较的数字。本模块给出 React 侧的观察手段与指标口径。

#### 组件高亮与渲染原因追踪

**组件高亮**：是 React DevTools 提供的可视化开关，开启后每次渲染的组件边框会闪动，用于直观观察哪些组件正在渲染。**渲染原因追踪**：是 Profiler 在录制时标注每次渲染由 props、state 还是父组件引起的能力。

- 开启高亮：在开发者工具的 React 面板打开对应开关，操作页面即可观察。
- 区分来源：边框闪动说明该组件重新渲染，结合渲染原因判断触发点。
- 辅助记录：在组件内打印关键 props，可以定位是哪一项变化引起渲染。
- 结合使用：高亮用于快速发现，Profiler 用于量化，二者配合使用。

```jsx
function logChangedProps(componentName, prevProps, nextProps) {
  const keys = new Set([...Object.keys(prevProps), ...Object.keys(nextProps)]);
  keys.forEach((key) => {
    if (prevProps[key] !== nextProps[key]) {
      // 例如 SearchList props 变化： data
      console.log(componentName, "props 变化：", key);
    }
  });
}

logChangedProps("SearchList", { keyword: "a" }, { keyword: "b" });
```

**速记**：组件高亮用于发现谁在渲染，渲染原因与 props 变化日志用于判断为什么渲染。



#### 严格模式对测量的影响

**严格模式（StrictMode）**：是开发环境下用来暴露潜在问题的包装组件，它会让部分函数在开发环境被重复调用，其中包括组件函数与副作用。

- 重复调用：开发环境下组件函数可能被调用两次，日志行数与计数器会翻倍。
- 只影响开发：这类重复调用在生产构建中不存在。
- 测量提醒：据日志判断真实渲染次数会得出错误结论，应以 Profiler 的提交记录或生产构建为准。
- 保留价值：重复调用是为了提前暴露不纯的渲染逻辑，不应为了测量方便而长期移除（成因详见本主题第 16 篇 Hook 规则与运行机制）。

```jsx
import { StrictMode } from "react";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

**速记**：严格模式在开发环境重复调用组件函数，会放大日志与计数，测真实渲染次数应以提交记录或生产构建为准。



#### 性能指标与用户体验指标的分工

**性能指标**：是描述运行过程耗时的技术数字，例如单次提交耗时与组件渲染耗时。**用户体验指标**：是从用户感知角度描述响应速度的数字，例如交互后多久出现变化、多久可以稳定操作。

- 分工：性能指标用于定位代码内部问题，用户体验指标用于判断整体是否达标。
- 换算关系：渲染耗时只是交互延迟的一部分，此外还包含网络与浏览器自身的工作。
- 采集归属：真实用户的采集与监控体系归 前端/构建工具 与 前端/测试 主题，本篇只到 React 侧的分析手段。
- 目标设定：以用户可感知的指标作为验收标准，用性能指标指导具体改动。

> 只看技术耗时容易得到「数字变好但用户没感觉」的结论，最终仍要以用户可感知的指标作为验收口径。

**速记**：性能指标用于定位代码，用户体验指标用于验收效果，真实用户采集归构建工具与测试主题。
