## Context 与跨层级传递

Context 是 React 提供的跨层级数据传递机制：在祖先组件处提供值，任意深度的后代组件都可以直接读取，不必经过中间组件逐层转交。

本篇讲 Context 的适用边界、createContext 与 Provider 的用法、useContext 的签名，以及 value 变化带来的渲染开销与拆解方式。

> Context 解决的是「怎么传」，不是「怎么管」。全局状态的组织方式属于另一个话题，详见本主题第 21 篇 状态管理：Redux Toolkit 与 Zustand。

### Context 解决什么

Context 的出发点是一条具体的痛点：当数据需要跨越很多层组件时，逐层透传会让中间组件承担与自己无关的负担。

#### 跨层级传参的困境

**props 逐层透传（prop drilling）** 是指数据从祖先组件一路通过中间组件的 props 传到深层组件，中间组件并不使用该数据却必须转交。

```jsx
function App() {
  const theme = "dark";
  return <Toolbar theme={theme} />;
}

function Toolbar({ theme }) {
  return <ThemedButton theme={theme} />;
}

function ThemedButton({ theme }) {
  return <button className={theme}>提交</button>;
}
// theme 经过 Toolbar 中转，Toolbar 本身并不使用它
```

- 中间层受累：每新增一层就要多写一次 props 转交。
- 改名成本：数据改名会波及所有中转组件。
- 结构耦合：中间组件被迫知道与自己无关的数据。

**速记**：逐层透传让中间组件被迫转交自己用不到的数据。



#### Context 的适用场景

Context 的适用判据是：数据被多个层级、多个组件共享，且变化不频繁。

- 主题：颜色、间距、圆角等全局外观配置。
- 语言：当前语言标识与翻译函数。
- 当前用户：登录用户信息与权限标记。
- 例外：只有父子两层用到的数据，直接传 props 更清晰。

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Toolbar />
    </ThemeContext.Provider>
  );
}

function ThemedButton() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>提交</button>;
}
// ThemedButton 跨过 Toolbar 直接取得 theme
```

**速记**：主题、语言、当前用户这类跨层级共享数据适合放进 Context。



#### 不适合放进 Context 的数据

有几类数据放进 Context 会带来明显副作用，需按特征提前排除。

- 高频变化：鼠标位置、输入框实时值等，放进去会引发大范围重新渲染。
- 仅单层使用：只有父子两层用到的数据，直接传 props 更清晰。
- 需要精细订阅：字段级更新用专门的状态库更合适（详见本主题第 21 篇 状态管理：Redux Toolkit 与 Zustand）。
- 业务数据缓存：请求结果缓存属于服务端状态，见本主题第 9 篇 useEffect 与副作用。

```jsx
// 反面示例：把鼠标坐标放进 Context，每次移动都让全部消费者重新渲染
const CursorContext = createContext({ x: 0, y: 0 });
// 坐标变化频率高，适合留在使用它的组件内部
```

> [!CAUTION]
> **注意内容**：把高频变化的值放进 Context，会让与其无关的消费者在每次变化时都重新渲染。

**速记**：高频变化、单层使用与需精细订阅的数据不放 Context。



### createContext 与 Provider

建立一条 Context 传递链需要两步：先创建 Context 对象，再用 Provider 在祖先处提供值。

#### createContext 的签名

**createContext** 是创建 Context 对象的函数，签名是 createContext(defaultValue)，参数 defaultValue 是找不到 Provider 时使用的默认值，返回一个 Context 对象，该对象带有 Provider 组件。

```jsx
const ThemeContext = createContext("light");

// 需要传多个字段时，默认值按对象形状给全
const LocaleContext = createContext({ language: "zh", setLanguage: () => {} });
```

- 参数：defaultValue 只在没有匹配 Provider 时生效，类型不限。
- 返回值：Context 对象，包含 Provider 与 Consumer 两个属性。
- 位置：在模块顶层调用一次并导出，不要在组件内部创建。

> [!IMPORTANT]
> **重要内容**：createContext 必须在模块顶层调用一次并导出；在组件内部创建会让每次渲染都产生新的 Context 对象，导致消费者全部重新挂载。

**速记**：createContext(defaultValue) 返回 Context 对象，默认值只在无 Provider 时生效。



#### Provider 的 value 属性

**Context.Provider** 是 Context 对象上的组件，通过 value 属性向下提供值，写法为 Context.Provider 加 value props，其整棵子组件树都可以读取该值。

```jsx
function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext.Provider value={theme}>
      <Page />
      <button onClick={() => setTheme(theme === "light" ? "dark" : "light")}>
        切换主题
      </button>
    </ThemeContext.Provider>
  );
}
// Page 及其所有后代都能读到当前 theme
```

- value：必填，类型不限，通常传对象以承载多个字段。
- 作用范围：Provider 之下的整棵子树。
- 更新方式：value 变化时，读取该 Context 的组件重新渲染。

**速记**：Provider 用 value 属性向整棵子树提供值。



#### 默认值何时生效

默认值是兜底，只在组件树中找不到对应 Provider 时才会被读到。

- 生效条件：组件所在的树中，向上找不到任何该 Context 的 Provider。
- 常见来源：组件被单独测试或独立复用时。
- 设计建议：默认值应是一个可用的合理值，而不是空占位。

```jsx
const ThemeContext = createContext("light");

function ThemedText() {
  const theme = useContext(ThemeContext);
  return <span className={theme}>正文</span>;
}

function App() {
  // 没有 Provider 包裹，ThemedText 读到默认值 "light"
  return <ThemedText />;
}
```

**速记**：默认值只在向上找不到 Provider 时生效。



#### 嵌套 Provider 的覆盖关系

多层 Provider 叠加时按就近原则取值，内层的作用范围只覆盖自身子树。

- 就近优先：消费者读到的是向上最近的 Provider 的 value。
- 局部覆盖：内层 Provider 只覆盖自己的子树，不影响兄弟节点。
- 常见用法：全局提供默认主题，局部页面覆盖为特定主题。

```jsx
function App() {
  return (
    <ThemeContext.Provider value="light">
      <Header />
      <ThemeContext.Provider value="dark">
        <Sidebar />
      </ThemeContext.Provider>
    </ThemeContext.Provider>
  );
}
// Header 读到 "light"，Sidebar 读到 "dark"
```

**速记**：嵌套 Provider 就近生效，内层只覆盖自己的子树。



### useContext 的签名与用法

读取 Context 值的唯一途径是 useContext，本节给出它的签名与正确取用位置。

#### useContext 的签名

**useContext** 是读取 Context 值的 Hook，签名是 useContext(SomeContext)，参数 SomeContext 是 createContext 返回的 Context 对象，返回该 Context 的当前值。

```jsx
const ThemeContext = createContext("light");

function Badge() {
  const theme = useContext(ThemeContext);
  return <em className={theme}>新</em>;
}
// 返回向上最近 Provider 的 value，没有则返回默认值
```

- 参数：Context 对象，不是 Provider，也不是 value。
- 返回值：当前值，类型与 createContext 的默认值一致。
- 调用位置：必须在组件或自定义 Hook 的顶层调用。

**速记**：useContext(SomeContext) 返回该 Context 的当前值。



#### 在最接近的 Provider 中取值

取值沿组件树向上找最近的 Provider，中间层组件完全不参与。

- 查找规则：沿组件树向上找最近的 Provider。
- 跨层读取：中间组件不必知道该 Context 的存在。
- 与逐层透传对比：读取点直接，中间层无感。

```jsx
function Layout() {
  return (
    <div>
      <Header />
      <Content />
    </div>
  );
}

function Content() {
  const theme = useContext(ThemeContext);
  return <main className={theme}>内容区</main>;
}
// Layout 不接触 theme，Content 直接取值
```

**速记**：useContext 沿树向上取最近 Provider 的值。



#### 值变化触发消费者重新渲染

value 与新值不相等时，读取该 Context 的组件会重新渲染。

- 触发条件：Provider 的 value 与新值不相等时，读取该 Context 的组件重新渲染。
- 比较方式：React 用 Object.is 比较新旧 value。
- 影响范围：包括读取该 Context 的全部组件，与是否用到具体字段无关。

```jsx
function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext.Provider value={{ theme }}>
      <ExpensivePanel />
      <button onClick={() => setTheme("dark")}>切换</button>
    </ThemeContext.Provider>
  );
}
// value 每次渲染都是新对象，ExpensivePanel 会跟着重新渲染
```

> [!CAUTION]
> **注意内容**：把内联对象直接写进 value，会让 Provider 每次渲染都产生新引用，导致消费者无条件重新渲染。

**速记**：value 引用变化即触发读取该 Context 的组件重新渲染。



#### 封装成自定义 Hook 的推荐写法

推荐把取值与校验合并成一个自定义 Hook，调用方只需一行即可取到值。

- 目的：把 useContext 调用与错误检查收在一处，使用方只调一个函数。
- 命名：以 use 开头，如 useTheme、useAuth。
- 校验：没有 Provider 时给出明确报错，避免默认值掩盖配置缺失。

```jsx
const ThemeContext = createContext(null);

function useTheme() {
  const theme = useContext(ThemeContext);
  if (theme === null) {
    throw new Error("useTheme 必须在 ThemeContext.Provider 内部使用");
  }
  return theme;
}

function Badge() {
  const { name } = useTheme();
  return <em>{name}</em>;
}
```

**速记**：把 useContext 与校验封装成 use 开头的自定义 Hook。



### 更新 Context 的性能问题

Context 的更新是广播式的：值一变，所有消费者都要重新渲染。控制影响面的手段都围绕「让 value 尽量少变」展开。

#### value 变化导致全部消费者重新渲染

Provider 重新渲染时若 value 是新对象，所有消费者都会被牵连更新。

- 现象：Provider 重新渲染时，value 若是新对象，读取该 Context 的组件都会重新渲染。
- 原因：消费者只关心「值是否变化」，不区分具体字段。
- 后果：与本次更新无关的消费者也被牵连，页面开销放大。

```jsx
// 每次渲染都新建对象，消费者无法跳过更新
<AuthContext.Provider value={{ user, signOut }}>
  <Dashboard />
</AuthContext.Provider>
```

**速记**：value 是新对象时，读取该 Context 的组件都会被牵连重新渲染。



#### 用 useMemo 稳定 value

缓存 value 对象并写全依赖数组，可让引用在依赖不变时保持稳定。

- 做法：用 useMemo 缓存 value 对象，依赖数组写真正影响它的字段。
- 效果：依赖不变时 value 引用不变，消费者不重新渲染。
- 前提：依赖数组必须完整，否则值会过期。

```jsx
function App() {
  const [user, setUser] = useState(null);
  const signOut = useCallback(() => setUser(null), []);
  const authValue = useMemo(() => ({ user, signOut }), [user, signOut]);
  return (
    <AuthContext.Provider value={authValue}>
      <Dashboard />
    </AuthContext.Provider>
  );
}
// user 与 signOut 不变时，authValue 引用稳定，消费者跳过更新
```

> useMemo 的签名与取舍详见本主题第 11 篇 useMemo 与 useCallback。

**速记**：用 useMemo 缓存 value，让引用在依赖不变时保持稳定。



#### 把 state 与更新函数拆成两个 Context

state 频繁变化而更新函数稳定，把两者拆开可让只读函数的组件免疫更新。

- 问题：更新函数通常稳定，state 变化频繁，混在一个 value 里会一起变。
- 做法：拆成 AuthStateContext 与 AuthDispatchContext 两个 Context。
- 收益：只读更新函数的组件不受 state 变化影响。

```jsx
const AuthStateContext = createContext(null);
const AuthDispatchContext = createContext(null);

function App() {
  const [user, setUser] = useState(null);
  const signOut = useCallback(() => setUser(null), []);
  return (
    <AuthStateContext.Provider value={user}>
      <AuthDispatchContext.Provider value={signOut}>
        <Dashboard />
      </AuthDispatchContext.Provider>
    </AuthStateContext.Provider>
  );
}
// 只用 signOut 的组件不会因 user 变化而重新渲染
```

**速记**：把不常变的更新函数与常变的 state 拆成两个 Context。



#### 结合 memo 控制影响面

memo 能拦住父传子的更新，Context 广播需靠稳定的 value 化解。

- 手段：给消费者组件套 memo，避免父组件重新渲染时被顺带更新。
- 边界：Context 值变化时 memo 无法阻止消费者更新。
- 配合：稳定 value 加 memo，才能同时拦住父传子与 Context 广播两条路径。

```jsx
const ThemeLabel = memo(function ThemeLabel({ name }) {
  return <span>{name}</span>;
});

function ThemePanel() {
  const name = useContext(ThemeContext);
  return <ThemeLabel name={name} />;
}
// name 不变时 ThemeLabel 跳过重新渲染
```

> React.memo 的用法与浅比较详见本主题第 18 篇 性能优化：memo、懒加载与代码分割。

**速记**：memo 挡住父传子，稳定 value 挡住 Context 广播，两者配合才完整。



### Context 的拆分与默认值

Context 的粒度与默认值设计决定了它是否好用：拆得合理则影响面小，默认值合理则配置错误早暴露。

#### 按变化频率拆分

拆分的第一条判据是变化频率，频率相近的字段才适合共用一个 value。

- 判据：变化频率相近的字段放在同一个 value 里。
- 例子：主题偶尔变，光标位置高频变，二者不应共用 value。
- 收益：低频消费者的更新次数大幅下降。

```jsx
const ThemeContext = createContext("light");
const CursorContext = createContext({ x: 0, y: 0 });
// 主题与光标各用各的 Provider，互不牵连
```

**速记**：按变化频率拆 Context，让低频消费者少受影响。



#### 按主题域拆分

第二条判据是业务含义，用户、主题、语言一类领域各建一个 Context。

- 判据：按业务含义归类，如用户、主题、语言各成一个 Context。
- 好处：职责清晰，读取点一眼看出依赖了哪个领域。
- 做法：每个领域单独建文件，导出 Context 与配套的自定义 Hook。

```jsx
// src/context/ThemeContext.jsx
const ThemeContext = createContext("light");
export { ThemeContext };

// src/context/LocaleContext.jsx
const LocaleContext = createContext("zh");
export { LocaleContext };
```

**速记**：按业务领域拆 Context，读取点即依赖说明。



#### 默认值不要留成无意义的空对象

空对象默认值会把配置缺失掩盖到深层使用处，应改为合理值或 null 加校验。

- 问题：默认值写成空对象，缺少字段时错误会在深层使用处才暴露。
- 做法：要么给可用的合理默认值，要么用 null 加显式校验。
- 校验：自定义 Hook 里检查 null 并抛出明确错误。

```jsx
const ThemeContext = createContext(null);

function useTheme() {
  const theme = useContext(ThemeContext);
  if (!theme) throw new Error("缺少 ThemeContext.Provider");
  return theme;
}
// 少了 Provider 会在使用时立刻报错，而不是读到 undefined 字段
```

**速记**：默认值给合理值或 null 加校验，不留空对象掩盖问题。



#### 不用 Context 替代状态管理

Context 只承担传递职责，中间件、时间旅行与选择器订阅需由状态库提供。

- 定位：Context 解决「怎么传」，不解决「怎么管」。
- 局限：没有中间件、时间旅行调试、选择器订阅等能力。
- 边界：全局状态需要这些能力时用专门的状态库（详见本主题第 21 篇 状态管理：Redux Toolkit 与 Zustand）。
- 组合：小型应用可用 useReducer 加 Context 承担简单全局状态。

```jsx
function App() {
  const [state, dispatch] = useReducer(reducer, initialState);
  const value = useMemo(() => ({ state, dispatch }), [state]);
  return (
    <AppContext.Provider value={value}>
      <Routes />
    </AppContext.Provider>
  );
}
// 规模变大后应迁移到状态管理库
```

**速记**：Context 只管传递，全局状态管理交给专门的状态库。
