## useReducer 与复杂状态

### useReducer 的签名与用法

当多个状态值互相关联、更新分支逐渐增多时，分散的更新函数难以维护，useReducer 把状态转换收敛到一处。

#### useReducer 的完整签名

**useReducer**：是管理复杂状态的内置 Hook，签名是 useReducer(reducer, initialArg, init)，参数 reducer 是状态转换函数，initialArg 是初始状态或初始参数，可选参数 init 是惰性初始化函数，返回一个二元数组，第一项是当前 state，第二项是 dispatch 函数。

- 首次渲染：用 init(initialArg) 或 initialArg 本身得到初始 state。
- 更新入口：调用 dispatch(action) 把 action 交给 reducer，由 reducer 返回新 state。
- 返回值：dispatch 的引用在整个组件生命周期内保持稳定，可作为依赖安全使用。

```jsx
function counterReducer(state, action) {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };
    case "decrement":
      return { count: state.count - 1 };
    default:
      return state;
  }
}

function Counter() {
  const [state, dispatch] = useReducer(counterReducer, { count: 0 });
  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: "increment" })}>加一</button>
      <button onClick={() => dispatch({ type: "decrement" })}>减一</button>
    </div>
  );
}
```

**速记**：useReducer(reducer, initialArg, init) 返回 state 与 dispatch 二元数组。



#### reducer 的完整签名

**reducer**：是接收当前 state 与 action、返回新 state 的纯函数，签名是 reducer(state, action)。

- 参数：第一个是当前状态，第二个是描述本次变更的 action 对象。
- 返回值：必须返回新的状态值，不能就地修改传入的 state。
- 无匹配分支：未被处理时返回原 state，React 据此判断本次更新无需重新渲染。

```jsx
function todoReducer(state, action) {
  switch (action.type) {
    case "add":
      return [...state, { id: action.payload.id, text: action.payload.text, done: false }];
    case "toggle":
      return state.map((todo) =>
        todo.id === action.payload.id ? { ...todo, done: !todo.done } : todo
      );
    default:
      return state;
  }
}
```

**速记**：reducer(state, action) 接收旧状态与 action，返回新状态而不是就地修改。



#### 惰性初始化函数

**惰性初始化**：是把初始 state 的计算推迟到首次渲染时执行的写法，形态是 useReducer(reducer, initialArg, init)。

- 第三个参数 init：接收 initialArg 并返回初始 state 的函数。
- 使用动机：初值需要从 props 或本地存储派生时，避免每轮渲染都重复计算。
- 与直接传入的区别：不传 init 时，initialArg 本身就是初始 state。

```jsx
function buildDraft(baseText) {
  return { text: baseText, dirty: false };
}

function DraftEditor({ baseText }) {
  const [draft, dispatch] = useReducer(draftReducer, baseText, buildDraft);
  return (
    <textarea
      value={draft.text}
      onChange={(event) => dispatch({ type: "edit", payload: event.target.value })}
    />
  );
}
```

> 惰性初始化只在首次渲染时执行一次，之后重新渲染不会再调用 init。

**速记**：init 参数把初始状态的计算延后到首次渲染，适合从 props 派生初值。



#### 与 useState 的替换关系

**替换关系**：是 useState 与 useReducer 可以互相改写——单一值用 useState，多个相关联值用 useReducer。

- 等价改写：把一个计数交给 useReducer 管理，reducer 返回新的数字，效果与 useState 相同。
- 选择依据：看状态之间是否相关、更新分支是否多。
- 迁移方向：状态数量增长、逻辑变复杂时，从 useState 迁移到 useReducer，不必一开始就选重的方案。

```jsx
function Counter({ initialCount }) {
  const [count, setCount] = useReducer(
    (state, action) => (action.type === "set" ? action.payload : state),
    initialCount
  );

  return <button onClick={() => setCount({ type: "set", payload: count + 1 })}>{count}</button>;
}
```

**速记**：useState 与 useReducer 可互相改写，状态相关且分支多时选 useReducer。



### action 与 reducer 的设计

action 负责描述发生了什么，reducer 负责决定状态怎么变，两者的形态约定决定了代码是否可读、可测。

#### action 的形态约定

**action**：是描述「发生了什么」的普通对象，约定形态为带 type 字段、必要时附加 payload 字段。

- type：字符串常量，唯一标识一种变更意图，如 "add"、"toggle"。
- payload：承载该次变更所需的数据，可以是任意类型的值。
- 约定：action 只描述意图，不含具体计算逻辑，计算全部放在 reducer 中。

```jsx
const addTodo = (text) => ({ type: "add", payload: { id: nextId(), text } });
const toggleTodo = (id) => ({ type: "toggle", payload: { id } });

// 两个 action 只描述意图，"id 如何生成" 不影响 reducer
console.log(addTodo("买牛奶")); // { type: "add", payload: { id: 1, text: "买牛奶" } }
```

**速记**：action 是带 type 与可选 payload 的普通对象，只描述意图不做计算。



#### reducer 必须是纯函数

**纯函数**：是相同输入必定得到相同输出、且不产生任何外部可观察变化的函数。

- 禁止副作用：不在 reducer 里发请求、写日志、读写本地存储。
- 禁止随机与时间：Date.now()、Math.random() 会让相同输入产生不同结果。
- 严格模式校验：React 严格模式会重复调用 reducer，借此暴露副作用（机制详见本主题第 16 篇 Hook 规则与运行机制）。

```jsx
function scoreReducer(state, action) {
  switch (action.type) {
    case "add":
      // 纯：新值完全由旧状态与 action 决定
      return { total: state.total + action.payload.value };
    // case "log":
    //   console.log("changed"); // 错误：reducer 内不写副作用
    //   return state;
    default:
      return state;
  }
}
```

> [!WARNING]
> **警告内容**：在 reducer 内写副作用会因严格模式的重复调用或并发渲染而被执行多次，结果不可预期。

**速记**：reducer 必须是纯函数，相同输入得到相同输出且不产生外部影响。



#### 用分支处理 action

**分支处理**：是用 switch 或条件分支按 action.type 分派到对应转换逻辑的写法。

- switch 写法：每个 case 返回新状态并直接 return，default 返回原状态。
- 条件写法：分支较少时用 if 判断 type，可读性与 switch 相当。
- 未知 action：落到兜底分支返回原 state，保证函数在任何输入下都有返回值。

```jsx
function formReducer(state, action) {
  if (action.type === "change") {
    return { ...state, [action.payload.field]: action.payload.value };
  }
  if (action.type === "reset") {
    return action.payload.initial;
  }
  return state;
}
```

> default 分支返回原 state 是必要的：dispatch 可能收到任何 action，reducer 不能有返回 undefined 的路径。

**速记**：按 action.type 分支处理，未匹配的 action 返回原状态。



#### 不可变更新的写法

**不可变更新**：是不修改旧对象、而是返回一份包含改动的新对象的写法。

- 对象字段：用展开语法复制旧对象再覆盖字段，如 { ...state, title: nextTitle }。
- 数组新增：用展开语法生成新数组，如 [...state, newItem]。
- 数组修改：用 map 生成新数组，命中项返回新对象，其余原样返回。

```jsx
function boardReducer(state, action) {
  switch (action.type) {
    case "rename":
      return { ...state, title: action.payload.title };
    case "addColumn":
      return { ...state, columns: [...state.columns, action.payload.column] };
    case "renameColumn":
      return {
        ...state,
        columns: state.columns.map((column) =>
          column.id === action.payload.id ? { ...column, name: action.payload.name } : column
        ),
      };
    default:
      return state;
  }
}
```

> [!CAUTION]
> **注意内容**：在 reducer 里直接修改旧 state 对象会因引用未变而让 React 跳过更新，界面看起来毫无变化。

**速记**：不可变更新靠展开语法与 map 生成新对象，绝不就地修改旧 state。



### 与 useState 的取舍

选择哪种 Hook 取决于状态之间的耦合程度与转移的数量，而不是代码长短。

#### 状态互相关联时用 useReducer

**互相关联的状态**：是取值受彼此约束、必须一起变化才能保持一致的一组状态值。

- 症状：一个状态更新后必须同步更新另一个，否则出现中间不一致。
- 收敛：把相关字段放进同一个状态对象，用一次 dispatch 同时改完。
- 例子：加载状态、数据与错误信息三者往往需要一起变化。

```jsx
function requestReducer(state, action) {
  switch (action.type) {
    case "start":
      return { status: "loading", data: null, error: null };
    case "success":
      return { status: "done", data: action.payload.data, error: null };
    case "failure":
      return { status: "done", data: null, error: action.payload.error };
    default:
      return state;
  }
}
```

**速记**：互相关联的状态放进一个对象，用一次 dispatch 保证同时更新。



#### 更新逻辑集中便于测试

**更新逻辑集中**：是把所有状态转换写进一个纯函数、从而可以脱离组件单独测试的收益。

- 可测性：reducer 是纯函数，给定 state 与 action 直接断言返回值，无需渲染组件。
- 可读性：全部转移写在一处，阅读 reducer 即可掌握状态的完整变化范围。
- 可复用：同一个 reducer 可以被多个组件共用。

```jsx
// 脱离 React 即可验证
const next = counterReducer({ count: 1 }, { type: "increment" });
console.log(next); // { count: 2 }
```

**速记**：reducer 是纯函数，可脱离组件测试全部状态转换。



#### 状态转移较多时可读性更好

**状态转移较多**：是同一份状态需要处理许多种不同事件、且每种事件的更新规则各不相同时的情形。

- 对比：用 useState 会写出一串命名各异的更新函数，调用点分散在各处。
- 收敛：用 useReducer 时调用点统一为 dispatch(action)，变更意图写在 type 上。
- 边界：转移只有一两处时，useReducer 反而增加样板代码。

```jsx
dispatch({ type: "submit" });
dispatch({ type: "succeed", payload: { orderId: "A1024" } });
dispatch({ type: "fail", payload: { reason: "库存不足" } });
```

**速记**：事件种类多、更新规则各异时，统一的 dispatch 比成串更新函数更清晰。



#### 简单独立值仍用 useState

**简单独立值**：是与其他状态无关、更新规则只有一条的单一值。

- 继续用 useState：布尔开关、输入框文本、单个计数等场景不必引入 reducer。
- 成本对比：useReducer 需要额外定义 action 类型与分支，而收益为零。
- 判断方法：若 reducer 里只有一个 case，就是选错了工具。

```jsx
function SearchBox() {
  const [keyword, setKeyword] = useState("");
  return <input value={keyword} onChange={(event) => setKeyword(event.target.value)} />;
}
```

**速记**：单一独立值继续用 useState，只有一条分支的 reducer 属于设计过重。



### 配合 Context 分发

当派发动作的组件藏在深层、逐层传递回调代价过高时，把 dispatch 放进 Context 是一种常见做法。

#### 通过 Context 提供 dispatch

**通过 Context 提供 dispatch**：是把 dispatch 放进 Context 的值里、让任意深度的后代无须逐层传 props 即可派发 action 的做法。

- 动机：多步表单、看板等结构中，深层组件需要触发顶层的状态变更。
- 方式：在 Provider 的 value 中放入 dispatch，后代组件用 useContext 取出后调用。
- 边界：Context 的创建、默认值与更新的完整用法详见本主题第 14 篇 Context 与跨层级传递。

```jsx
const TaskDispatchContext = createContext(null);

function TaskBoardProvider({ children }) {
  const [tasks, dispatch] = useReducer(taskReducer, []);
  return (
    <TaskDispatchContext.Provider value={dispatch}>
      {children}
    </TaskDispatchContext.Provider>
  );
}
```

**速记**：dispatch 放进 Context，后代组件无须逐层传 props 即可派发 action。



#### dispatch 引用保持稳定

**dispatch 的稳定性**：是同一处 useReducer 返回的 dispatch 在整个生命周期内引用不变的特性。

- 可作依赖：把 dispatch 放进 useEffect 或 useCallback 的依赖数组不会引发重复执行。
- 无须缓存：不需要再用 useCallback 包裹 dispatch 或调用它的函数。
- 与 state 不同：state 每次更新都是新对象，dispatch 始终是同一个函数。

```jsx
function TaskRow({ task }) {
  const dispatch = useContext(TaskDispatchContext);

  const handleToggle = useCallback(() => {
    dispatch({ type: "toggle", payload: { id: task.id } });
  }, [dispatch, task.id]);

  return <button onClick={handleToggle}>{task.done ? "已完成" : "待办"}</button>;
}
```

**速记**：dispatch 引用永久稳定，可以放心放进依赖数组而不会引发重复执行。



#### 避免 state 与 dispatch 同框

**state 与 dispatch 同框**：是把当前 state 与 dispatch 放进同一个 Context 值的写法，它会让只负责派发 action 的组件也随 state 变化重新渲染。

- 问题：Context 按引用比较，state 变化即整个 value 变化，全部消费者重新渲染。
- 拆分：把状态放进一个 Context，把 dispatch 放进另一个 Context。
- 收益：只需要派发能力的组件订阅 dispatch Context，不受数据更新波及。

```jsx
function Board() {
  const tasks = useContext(TaskStateContext);
  const dispatch = useContext(TaskDispatchContext);

  return (
    <ul>
      {tasks.map((task) => <TaskRow key={task.id} task={task} />)}
      <button onClick={() => dispatch({ type: "clear" })}>清空</button>
    </ul>
  );
}
```

> [!TIP]
> **建议内容**：把 state 与 dispatch 拆成两个 Context 提供，能让纯操作型组件免于随数据更新而重新渲染。

**速记**：state 与 dispatch 分属两个 Context，纯派发组件才不会随数据更新重新渲染。



### 状态机的思路

把交互建模成有限状态之间的转移，可以从根上消除互相矛盾的中间状态。

#### 把状态与合法转移显式化

**状态机（state machine）**：是用一组有限状态与状态之间允许的转移来描述交互的模型。

- 状态有限：任何时刻只处于其中一个状态，如 idle、submitting、success、error。
- 转移显式：每次变化都是从一个具名状态到另一个具名状态，而不是给多个布尔值反复赋值。
- 表达方式：把状态与转移直接写进 reducer 的分支中。

```jsx
function submitReducer(state, action) {
  switch (state.status) {
    case "idle":
      return action.type === "submit" ? { status: "submitting" } : state;
    case "submitting":
      if (action.type === "succeed") return { status: "success" };
      if (action.type === "fail") return { status: "error", reason: action.payload.reason };
      return state;
    default:
      return state;
  }
}
```

**速记**：状态机用有限状态与显式转移描述交互，任何时刻只处于一个状态。



#### 非法转移不写进 reducer

**非法转移**：是当前状态下不允许发生的事件，正确做法是让 reducer 对它不做任何处理。

- 不处理即拒绝：不为非法转移写分支，落到返回原状态的路径，界面自然保持不变。
- 好处：规则集中在 reducer，调用点不必事先判断「现在能不能点」。
- 例子：提交中重复点击提交，reducer 保持 submitting 状态。

```jsx
function submitReducer(state, action) {
  if (state.status === "submitting" && action.type === "submit") {
    return state; // 提交中再次提交：忽略
  }
  if (state.status === "idle" && action.type === "submit") {
    return { status: "submitting" };
  }
  return state;
}
```

**速记**：非法转移不为它写分支，reducer 返回原状态即等于拒绝。



#### 用状态机组织多步流程

**多步流程**：是先后依赖、每一步只在前一步完成后才允许进入的交互序列。

- 适用：提交订单、向导式表单、支付确认等有明确阶段的过程。
- 组织方式：用一个 status 字段表示所处阶段，用 action 驱动阶段前进或回退。
- 界面派生：按钮可用性与提示文案由 status 计算得出，不另设布尔标志。

```jsx
function Wizard({ initialStep }) {
  const [state, dispatch] = useReducer(wizardReducer, { step: initialStep, data: {} });

  return (
    <section>
      {state.step === 1 && (
        <StepOne onNext={(data) => dispatch({ type: "next", payload: data })} />
      )}
      {state.step === 2 && <StepTwo onBack={() => dispatch({ type: "back" })} />}
    </section>
  );
}
```

**速记**：多步流程用一个 status 字段表示阶段，用 action 驱动阶段前进。



#### 与布尔标志堆叠的对比

**布尔标志堆叠**：是用多个互相独立的布尔值拼出状态的写法，状态数量随标志数呈组合增长。

- 组合爆炸：三个标志产生八种组合，其中多数是无意义的非法组合。
- 渲染矛盾：可能出现加载中与出错同时为真，界面无从选择该显示哪一个。
- 替换方案：用一个取值受限的 status 字段取代全部标志，非法组合在结构上就不存在。

```jsx
// 布尔堆叠：可能出现 loading 与 error 同时为真的矛盾状态
const [loading, setLoading] = useState(false);
const [error, setError] = useState(null);

// 状态机：任意时刻只有一个 status 取值
const [state, dispatch] = useReducer(requestReducer, { status: "idle" });
```

> 布尔标志适合描述互相独立的开关；一旦它们之间存在互斥与先后约束，就应合并成单一状态字段。

**速记**：多个布尔标志会组合出非法状态，合并成单一 status 字段才能排除矛盾。
