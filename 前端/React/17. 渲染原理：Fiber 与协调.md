## 渲染原理：Fiber 与协调

### 渲染与提交两阶段

一次更新从触发到界面上看到结果，中间分成两个阶段：渲染阶段负责计算要改什么，提交阶段负责把改动写入宿主环境。Fiber 架构的全部设计都围绕这条划分展开。

#### 渲染阶段算出要改什么

**渲染阶段（render phase）**：是 React 调用组件函数、执行协调（reconciliation）并构建新的 Fiber 树的阶段，其产物是一棵描述本次界面应为何样的工作树，而不是真实的 DOM 变更。

- 执行内容：自根节点向下遍历，逐个调用组件函数得到新的元素（element），再与上一次的元素比较并标记需要变更的节点。
- 纯计算：只做计算与标记，不读写浏览器 DOM，也不执行副作用（side effect）。
- 可丢弃：结果在被打断时可以被整体丢弃并重做，React 不保证组件函数只被调用一次。

```jsx
import { createRoot } from "react-dom/client";

function UserBadge({ user }) {
  // 渲染阶段：只根据 props 与 state 算出界面，不写副作用
  const label = `${user.name}（${user.role}）`;
  console.log("渲染阶段执行", user.id); // 可能被执行多次
  return <span>{label}</span>;
}

createRoot(document.getElementById("root")).render(
  <UserBadge user={{ id: 1, name: "Ada", role: "admin" }} />
);
// 控制台输出：渲染阶段执行 1
```

> 渲染阶段要满足纯函数要求：相同输入得到相同输出，不修改外部变量、不发请求、不设置定时器（原因见本主题第 3 篇组件基础与 props）。

**速记**：渲染阶段只计算与标记，产出新的 Fiber 树，不碰 DOM、不执行副作用。



#### 提交阶段把改动写入 DOM

**提交阶段（commit phase）**：是 React 把渲染阶段算出的变更一次性写入宿主环境的阶段，它是同步执行的，中途不能被中断。

- 写入内容：按标记执行插入、更新、删除等 DOM 操作，附加 ref，运行布局副作用与被动副作用。
- 同步完成：一旦开始提交，会走完全部节点的提交工作，界面不会停在「改了一半」的中间状态。
- 触发绘制：提交结束后浏览器才有机会进行样式计算与绘制，用户这时才看到新界面。

```jsx
function SaveButton({ onSave }) {
  const buttonRef = useRef(null);

  useLayoutEffect(() => {
    // 布局副作用：DOM 已更新、浏览器尚未绘制，适合读取尺寸
    console.log("布局副作用，按钮宽度", buttonRef.current.offsetWidth); // 例如 80
  });

  return <button ref={buttonRef} onClick={onSave}>保存</button>;
}
```

> 提交阶段按节点逐一执行变更，任何一处提交逻辑抛错都会中断后续变更，这也是错误边界只作用于提交阶段的原因（详见本主题第 19 篇错误边界、Suspense 与并发特性）。

**速记**：提交阶段同步写入 DOM、附加 ref、执行副作用，结束后浏览器才能绘制。



#### 两阶段的可中断性差别

**两阶段的可中断性差别**：渲染阶段可以被打断、暂停和重做，提交阶段必须一次跑完，这条差别是 Fiber 架构最重要的行为分野。

- 渲染阶段可中断：遍历中若本次分配的时间用完，React 保存进度、让出主线程，等下一次空闲再继续。
- 提交阶段不可中断：DOM 变更必须连续完成，否则界面会在半更新状态下被绘制，产生用户可见的错乱。
- 副作用与提交同步：ref 附加与两类副作用都发生在提交阶段，因此同样不可中断。

> [!IMPORTANT]
> **重要内容**：渲染阶段随时可能被中断并重新执行，任何写操作、订阅或请求都必须放进副作用，否则会被重复触发。

**速记**：渲染阶段可中断可重做，提交阶段必须一次完成且与副作用同步。



#### 划分两阶段的意义

**划分两阶段的意义**：是把「计算」与「生效」解耦，让 React 能够在不影响界面的前提下自由调度计算过程。

- 调度自由：只有计算与生效分离，React 才能在计算阶段暂停、合并或丢弃工作。
- 界面一致：提交阶段作为原子操作，保证用户看到的始终是一棵完整的树。
- 并发基础：可中断的渲染阶段是并发特性（concurrent features）成立的前提，优先级高的更新可以先完成。
- 开发者约束：两阶段的分工解释了为什么渲染要纯、副作用要放进 effect、ref 要等到提交后才可读。

> 并发特性本身的使用方式归本主题第 19 篇错误边界、Suspense 与并发特性，本篇只讲清楚其底层为何可行。

**速记**：两阶段解耦让计算可调度、让生效保持原子，是并发能力的前提。



### Fiber 节点与工作循环

Fiber 是 React 用来描述工作单元的数据结构。整棵 Fiber 树替代了早期依赖递归调用栈的渲染方式，使得渲染工作可以被显式地推进、暂停与恢复。

#### Fiber 节点的定义

**Fiber 节点**：是协调过程中描述一个工作单元（unit of work）的数据结构，一个节点对应一个组件或一个元素，节点上保存了类型、props、state 以及与相邻节点的连接关系。

- 一一对应：每个被渲染的元素或组件实例对应一个 Fiber 节点，节点之间组成一棵与元素树同构的树。
- 携带信息：节点的类型（函数组件、宿主元素等）、本次使用的 props 与 state，以及指向关联 DOM 节点的引用。
- 工作标记：节点上记录本次更新需要对它做什么，例如插入、更新或删除。
- 双缓冲：React 同时维护当前树（current tree）与正在构建的工作树（work-in-progress tree），提交时整体切换。

> 本篇不展开 Fiber 的内部字段名与实现细节，只使用公开共识层面的模型：节点携带类型与数据，节点之间用引用相连。

**速记**：Fiber 节点是描述单个工作单元的数据结构，多个节点组成与元素树同构的 Fiber 树。



#### 节点之间的父子与兄弟指针

**父子与兄弟指针**：是 Fiber 节点之间用引用串成的连接方式，每个节点保存指向其子节点、下一个兄弟节点与父节点的引用，把整棵树变成一张可以按顺序访问的结构。

- 向下：每个节点保存指向子节点的引用，从父节点进入子节点只需一次跳转。
- 横向：每个节点保存指向下一个兄弟节点的引用，访问同级节点依次后移。
- 向上：每个节点保存指向父节点的引用，子节点全部处理完后可以回到父节点。
- 遍历顺序：三种引用配合即可完成深度优先遍历，不需要依赖函数的调用栈。

```jsx
// 用普通对象模拟指针连接，演示深度优先的访问顺序
const fiberTree = {
  name: "App",
  children: [
    { name: "Header", children: [] },
    { name: "List", children: [{ name: "Item", children: [] }] },
  ],
};

function visitInOrder(node, visit) {
  visit(node.name);
  node.children.forEach((child) => visitInOrder(child, visit));
}

const order = [];
visitInOrder(fiberTree, (name) => order.push(name));
console.log(order); // ["App", "Header", "List", "Item"]
```

> 递归函数依赖调用栈，无法在中途保存进度后返回，因此真正的协调过程用带指针的循环推进，而不是递归。

**速记**：节点用子指针与兄弟指针相连，配合父指针即可不依赖调用栈地深度优先遍历。



#### 工作循环的推进方式

**工作循环（work loop）**：是 React 反复「取出一个工作单元、处理它、再取出下一个」的循环结构，循环以迭代方式推进，因此可以在任意一次迭代后停下并保存当前位置。

- 向下优先：拿到一个节点后先处理它，若有子节点就进入子节点。
- 处理内容：读取新的 props 与 state、调用组件函数、比较新旧元素并标记变更。
- 回溯：没有子节点时查看是否有兄弟节点，有则转向兄弟节点，没有则回退到父节点。
- 结束条件：回到根节点且没有待处理节点时，本次渲染阶段结束。

```jsx
// 用栈模拟迭代式工作循环，避免递归带来的调用栈依赖
const rootNode = {
  name: "App",
  children: [
    { name: "Header", children: [] },
    { name: "List", children: [{ name: "Item", children: [] }] },
  ],
};

function runWorkLoop(root, processNode) {
  const stack = [root];
  const processed = [];

  while (stack.length > 0) {
    const node = stack.pop();          // 取出一个工作单元
    processNode(node);
    processed.push(node.name);
    for (let i = node.children.length - 1; i >= 0; i -= 1) {
      stack.push(node.children[i]);    // 子节点逆序入栈，保证按原顺序处理
    }
  }

  return processed;
}

console.log(runWorkLoop(rootNode, () => {})); // ["App", "Header", "List", "Item"]
```

> 循环结构本身不关心时间：是否继续、是否暂停由调度器决定，循环只负责「有工作就推进一步」。

**速记**：工作循环以迭代方式取节点、处理节点、转向下一个节点，可在任意一步暂停。



#### 时间切片与让出主线程

**时间切片（time slicing）**：是把一段连续的渲染工作拆成若干小片段、每片执行完就把主线程交还给浏览器的调度手段。**让出主线程（yield）**：指渲染工作在片段边界主动停止，让浏览器有机会处理输入事件、动画与绘制。

- 片段预算：每个片段只占用很短的时间，超过预算就停止推进工作循环。
- 让出方式：让出后通过调度器安排一个后续任务继续未完成的工作，而不是占用当前任务不放。
- 抢占：用户输入等更高优先级的更新到来时，正在进行的低优先级渲染可以被放弃并重新开始。
- 不饿死：调度器会安排低优先级工作最终仍被执行完。

```jsx
// 演示把一批任务切片执行，每片用完预算就让出主线程
function runInSlices(tasks, onDone) {
  let index = 0;

  function nextSlice() {
    const deadline = performance.now() + 5;   // 每片最多占用 5 毫秒
    while (index < tasks.length && performance.now() < deadline) {
      tasks[index]();
      index += 1;
    }

    if (index < tasks.length) {
      setTimeout(nextSlice, 0);               // 让出主线程，下一轮继续
    } else {
      onDone();
    }
  }

  nextSlice();
}

runInSlices(
  [0, 1].map((n) => () => console.log("处理", n)),
  () => console.log("全部完成")
);
// 处理 0
// 处理 1
// 全部完成
```

**速记**：时间切片把渲染拆成小片段，片段边界让出主线程，高优先级更新可以抢先执行。



### 协调与 diff 策略

协调决定每次更新要保留哪些节点、替换哪些节点。React 用一组启发式规则，把「求两棵树的最小编辑距离」这一高成本问题降为逐层线性比较。

#### 协调的定义

**协调（reconciliation）**：是比较新旧两棵元素树、计算出最小必要变更的过程，它发生在渲染阶段，结果以「需要插入、更新或删除」的标记记录在 Fiber 节点上。

- 输入：上一次渲染得到的元素树与本次渲染得到的元素树。
- 过程：自根向下逐层比较，命中可复用的节点就更新，否则重建。
- 输出：一组对 Fiber 节点的变更标记，供提交阶段执行。
- 目标：在多数真实场景下得到接近最优的更新，同时把复杂度控制在可接受范围。

> 协调只比较新旧两棵元素树，不读取 DOM 的真实结构；DOM 的真实状态不作为复用判断的依据。

**速记**：协调比较新旧元素树并标记最小必要变更，发生在渲染阶段。



#### 按类型与 key 匹配的原则

**类型与 key 的匹配原则**：是同层比较时判断两个元素能否复用的规则，类型相同且 key 相同就复用对应节点，任一条件不满足就卸载旧节点、挂载新节点。

- 类型优先：函数组件、宿主元素分别视作不同的类型，类型不同一律重建。
- key 区分同级：同一层里多个同类元素依靠 key 互相区分，key 是 React 判断「谁是谁」的依据。
- 复用代价：复用只更新变化的属性，重建会丢弃子树里的 state 与 DOM 节点。
- 位置参与：没有 key 时按同层顺序位置配对。

```jsx
function TaskList({ tasks }) {
  return (
    <ul>
      {tasks.map((task) => (
        // key 相同则复用该任务对应的节点，key 不同则视为新节点
        <li key={task.id}>{task.title}</li>
      ))}
    </ul>
  );
}
```

> [!NOTE]
> **提醒内容**：类型不同时 key 相同也不会复用；把条件渲染的两个分支写成不同类型的元素，切换分支必然重建节点。

**速记**：同层比较时类型与 key 同时相同才复用，否则卸载重建。



#### 同层比较不跨层移动

**同层比较**：是协调的启发式规则之一，React 只在树的同一层级内比较节点，不尝试跨层级搬动节点。**跨层移动**：指把一个节点从树的一处移到另一处的操作，React 遇到这种变化时按「卸载旧的、挂载新的」处理。

- 只比同层：父节点变更时整棵子树重建，不会把子树搬到别的位置。
- 移动即重建：把元素从子容器移到兄弟容器，state 与 DOM 状态都会丢失。
- 性能取舍：放弃全局最优的树编辑算法，换取每层线性时间的比较。
- 实践含义：真正的「移动」应通过同层内改变顺序加稳定 key 来表达。

> 跨层移动带来重建，是「调整布局后组件状态莫名重置」这类问题的常见来源。

**速记**：协调只在同层比较，跨层移动会被当作卸载与挂载，state 随之丢失。



#### 列表用 key 的匹配规则

**列表的 key 匹配规则**：是协调处理同级多元素时的配对方式，React 先用 key 把新旧列表中的元素配对，配对成功的复用，剩余的先标记删除、后标记插入。

- 按 key 配对：旧列表与新列表各自建立 key 到节点的映射，key 相同的节点被复用。
- 顺序无关：位置改变但 key 不变时，节点被复用并调整顺序，state 得以保留。
- 索引作 key：仅在列表不重排、不增删中间项时可用，否则会把 state 配错到别的数据上。
- 唯一与稳定：key 应取自数据的稳定标识，且在同一个列表内唯一。
- 选择原则的完整写法详见本主题第 5 篇条件渲染与列表渲染。

```jsx
function ScoreList({ scores }) {
  // 用 id 作 key：重排后节点仍与同一条数据配对
  const rows = [...scores].sort((a, b) => b.value - a.value);

  return (
    <ol>
      {rows.map((score) => (
        <li key={score.id}>{score.name}</li>
      ))}
    </ol>
  );
}
```

> [!CAUTION]
> **注意内容**：用数组索引当 key，在中间插入或重排列表项时会把原有 state 与 DOM 状态错配到别的数据上，可能表现为输入框内容跟着错位。

**速记**：列表按 key 配对复用节点，key 要唯一且取自稳定标识，索引作 key 只适用于不重排的列表。



### re-render 的触发条件

重新渲染（re-render）是组件函数被再次调用的过程。弄清哪些操作会触发它，是理解渲染次数与渲染成本的前提。

#### state 更新与更新排队

**state 更新**：是通过状态更新函数写入新值并安排一次重新渲染的操作；**更新排队与合并**：指多次更新被放进同一个队列、由 React 统一调度，在同一渲染周期里合并处理。

- 入队：每次调用状态更新函数都把一条更新记录压入该组件对应的队列。
- 批处理：同一次事件处理或同一个微任务内产生的多条更新被一起处理，只渲染一次。
- 顺序：队列中的更新按入队顺序依次应用到 state 上，最终得到本次渲染使用的值。
- 值相等时：新值与旧值相同时，React 可能跳过该组件及其子树的渲染，但不保证一定跳过。

```jsx
function BatchDemo() {
  const [count, setCount] = useState(0);
  const [label, setLabel] = useState("待处理");

  function handleClick() {
    setCount(count + 1);   // 两条更新进入同一队列，只触发一次渲染
    setLabel("已处理");
  }

  return <button onClick={handleClick}>{label}：{count}</button>;
}
```

> 每次渲染中的 state 都是一份快照，事件处理函数读到的始终是它被创建时那次渲染的值，依赖闭包的写法详见本主题第 7 篇 State 与 useState。

**速记**：状态更新先入队再合并，同一批内的多条更新只触发一次重新渲染。



#### 父组件重新渲染

**父组件重新渲染**：指父组件因自身原因重新渲染时，其子树中未被阻止的组件也会跟着重新渲染，与子组件的 props 是否变化无关。

- 默认向下：父组件重新渲染会继续渲染其子组件，形成一路向下的递归。
- props 未变也渲染：子组件的 props 引用与内容都没变时，React 默认仍会调用它。
- 阻止手段：把组件包进 memo，或把子组件作为已固定的元素通过 props 传入，可以跳过默认的向下渲染（优化手段见本主题第 18 篇性能优化：memo、懒加载与代码分割）。
- 位置影响：父组件中元素类型改变会使对应子组件卸载重建，而不是重新渲染。

> 父组件重新渲染不等于子组件 props 变化，二者是两个独立的事实；本篇只描述默认行为。

**速记**：父组件重新渲染会默认带动整棵子树重新渲染，除非子树被显式阻止。



#### Context 值变化

**Context 值变化**：指 Provider 提供的值发生改变时，所有读取该 Context 的组件都会重新渲染，即使中间隔着未重新渲染的父组件。

- 穿透层级：useContext 订阅的是 Context 的值，值变化时消费者直接收到通知，不依赖父组件逐层传递 props。
- 只影响消费者：没有读取该 Context 的组件不会因它的变化而重新渲染。
- 引用敏感：Provider 的 value 在两次渲染间引用不同时，同样视为值发生变化。
- 拆分建议：把频繁变化的值与稳定的值放进不同的 Context，可以缩小重新渲染的范围（用法详见本主题第 14 篇 Context 与跨层级传递）。

> Provider 的 value 若传入每次渲染都新建的对象，消费者会因引用变化而重新渲染，稳定的引用能减少这类渲染。

**速记**：Context 值变化只让读取它的组件重新渲染，value 的引用变化同样算值变化。



#### 同一位置的元素类型变化

**同一位置的元素类型变化**：指同一个位置上的元素从一种类型换成另一种类型时，React 卸载旧节点并挂载新节点，而不是在原节点上更新。

- 判定依据：位置由父节点与在该父节点下的顺序共同确定，类型不同即视为不同节点。
- 后果：旧子树的 DOM 节点被移除，其中的 state 与 ref 全部丢弃，新子树的副作用重新执行。
- state 丢失：把条件渲染的两个分支写成不同类型，切换分支会重置分支内部的状态。
- 保留状态的办法：让两个分支共用同一个组件类型，或显式把状态提升到父组件（状态放置见本主题第 8 篇状态提升与单向数据流）。

```jsx
function Profile({ isEditing }) {
  // 两个分支类型不同：切换时旧节点卸载、新节点挂载，输入内容被清空
  return isEditing ? <input defaultValue="编辑中" /> : <p>只读内容</p>;
}
```

> [!WARNING]
> **警告内容**：把两个分支写成不同类型的元素，会让分支内部本来想保留的表单内容与滚动位置在每次切换时全部重置。

**速记**：同一位置元素类型变化等于卸载加重建，旧子树的 state 与 DOM 状态全部丢失。



### 提交阶段与副作用列表

提交阶段把渲染阶段记录下来的变更逐条兑现，并在兑现前后安排副作用。哪些节点的副作用需要运行或清理，由渲染阶段收集的副作用列表决定。

#### 提交阶段执行的动作

**提交阶段执行的动作**：是按固定顺序把变更落到宿主环境上的一组操作，包括宿主节点的增删改、ref 的附加与解绑，以及副作用函数的执行与清理。

- 变更宿主节点：对标记为插入、更新、删除的节点执行对应的 DOM 操作。
- 处理 ref：把新的 DOM 节点写入 ref 对象，或在卸载时把 ref 置空。
- 执行副作用：运行 useEffect 与 useLayoutEffect 注册的函数，并先执行上一次遗留的清理函数。
- 分段推进：提交阶段内部有先后次序，先完成 DOM 变更，再运行布局副作用，最后运行被动副作用。

```jsx
function SearchBox({ onQuery }) {
  const inputRef = useRef(null);

  useEffect(() => {
    inputRef.current.focus(); // 提交完成后才能拿到真实节点
  }, []);

  return <input ref={inputRef} onChange={(event) => onQuery(event.target.value)} />;
}
```

> ref 在提交阶段才被赋值为真实的 DOM 节点，因此渲染阶段读取 ref 只能拿到上一次的值或 null。

**速记**：提交阶段按次序完成 DOM 变更、ref 附加与副作用执行，副作用在 DOM 更新之后运行。



#### effect 的执行顺序

**effect 的执行顺序**：指同一次提交中多个副作用之间的运行次序，规律是子组件的副作用先于父组件，且每个组件的清理函数都先于它新的副作用执行。

- 子先父后：挂载时的深度优先遍历使子组件的副作用先运行，父组件的副作用后运行。
- 清理先行：组件更新时先执行上一次副作用返回的清理函数，再执行本次的副作用。
- 依赖决定执行：依赖数组未发生变化的副作用会被跳过，其清理函数也不会运行。
- 不依赖顺序：多个组件清理函数之间的先后与遍历实现有关，业务逻辑不应依赖这一顺序。

```jsx
function ChildEffect() {
  useEffect(() => {
    console.log("子组件副作用");
    return () => console.log("子组件清理");
  });
  return <span>子</span>;
}

function ParentEffect() {
  useEffect(() => {
    console.log("父组件副作用");
    return () => console.log("父组件清理");
  });
  return <ChildEffect />;
}

// 首次挂载输出顺序
// 子组件副作用
// 父组件副作用
// 更新时：先执行清理函数，再执行新的副作用
```

> 子先父后与清理先行这两条规律在挂载、更新两种情形下都成立，是判断副作用时序问题的基本依据。

**速记**：副作用子先父后，同一组件的清理函数先于新的副作用，依赖未变化则整体跳过。



#### 布局副作用与浏览器绘制的关系

**布局副作用（layout effect）**：是在 DOM 变更之后、浏览器绘制之前同步执行的副作用；**被动副作用（passive effect）**：是在浏览器完成绘制之后被调度的副作用，即 useEffect 默认的行为。

- 时机差别：布局副作用在绘制前同步执行，被动副作用在绘制后执行。
- 阻塞与否：布局副作用会阻塞绘制，耗时过长会让界面出现可感知的卡顿。
- 选用依据：需要抢在用户看到新界面之前读取布局或同步调整样式时使用布局副作用；数据请求、订阅、日志等使用被动副作用。
- 服务端渲染：服务端没有 DOM 也没有绘制过程，布局副作用在服务端不会执行。

```jsx
function Tooltip({ anchorRef, children }) {
  const tooltipRef = useRef(null);

  useLayoutEffect(() => {
    const rect = anchorRef.current.getBoundingClientRect();
    tooltipRef.current.style.left = `${rect.left}px`; // 绘制前定位，避免闪烁
  }, [anchorRef]);

  return <div ref={tooltipRef}>{children}</div>;
}
```

> [!WARNING]
> **警告内容**：在布局副作用里执行耗时计算会推迟浏览器绘制，表现为明显的掉帧，耗时逻辑应移入被动副作用或拆分为后续任务。

**速记**：布局副作用在绘制前同步执行并可阻塞绘制，被动副作用在绘制后运行，按是否需要抢在绘制前选择。
