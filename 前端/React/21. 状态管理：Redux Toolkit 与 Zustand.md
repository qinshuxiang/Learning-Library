## 状态管理：Redux Toolkit 与 Zustand

### 什么时候需要全局状态

组件树中的状态默认属于定义它的那个组件，只有当多棵互不相邻的子树需要读写同一份数据时，把状态放到组件树之外才划算。本节先给出判据，再给出引入状态管理库之前的过渡手段。

#### 局部状态与全局状态的判据

**局部状态（local state）**：是只被一个组件或它的直接子组件读写、生命周期与该组件一致的状态。**全局状态（global state）**：是组件树中多个互不相邻的分支都需要读写的状态，必须存放在组件树之外的容器里。

判断一份状态属于哪一类，按顺序问三个问题：

- 读写者是否同属一棵子树：只有父组件与直接子组件参与，用局部状态即可。
- 是否存在跨分支读取：兄弟分支、跨路由分支要读取同一份数据，才考虑提升到组件树之外。
- 写入频率与范围：写入频繁但只有一处消费的状态留在局部，否则会把无关节点的更新成本放大。

```jsx
// 局部状态：关键词只被 SearchBar 与其父组件使用
function SearchBar({ onSearch }) {
  const [keyword, setKeyword] = useState("");

  function handleSubmit(event) {
    event.preventDefault();
    onSearch(keyword);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={keyword} onChange={(event) => setKeyword(event.target.value)} />
    </form>
  );
}
```

> 判据的核心是读写者是否重叠：读写者集合互不相交时，局部状态无法表达共享，此时才需要全局状态。

**速记**：只有跨分支共享的状态才升级为全局状态，依据是读写者集合是否重叠。



#### 跨多层共享且频繁更新的场景

**跨多层共享**：指一份状态的读取者与写入者分布在组件树的不同深度，中间隔着若干层并不关心该状态的组件。

- 传参噪音：中间层组件被迫接收并转发与自己无关的 props，组件接口被污染。
- 更新代价：中间层组件因 props 变化而重新渲染，即使它并不消费该数据。
- 一致性风险：同一份数据被复制到多个局部状态后需要手工同步，容易产生不一致。

```jsx
// 中间层 Layout 与 Sidebar 都不消费 theme，却要逐层转发
function App() {
  const [theme, setTheme] = useState("light");
  return <Layout theme={theme} setTheme={setTheme} />;
}

function Layout({ theme, setTheme }) {
  return (
    <div>
      <Sidebar theme={theme} setTheme={setTheme} />
      <main>{/* 内容区 */}</main>
    </div>
  );
}
```

> 频繁更新与跨多层共享叠加时才最需要状态管理库：单次读取的配置类数据用 Context 已经够用。

**速记**：跨深度共享且高频更新会同时放大传参噪音与渲染成本，这才是引入状态管理库的信号。



#### 不要用全局状态替代所有状态

**用全局状态替代所有状态**：是把本可以留在组件内部的状态（表单输入、弹窗开关、鼠标悬停）也搬进全局容器，导致状态所有权与生命周期脱节。

- 所有权脱节：状态在组件卸载后仍留在 store 中，需要额外的重置逻辑。
- 调试困难：任意组件都可能修改同一份数据，改动来源难以追踪。
- 复用受限：组件依赖外部容器才能工作，无法单独挂载与测试。

> [!CAUTION]
> **注意内容**：把所有状态塞进全局容器会丢失状态的生命周期边界，组件卸载后残留的数据需要手工清理，组件也难以独立测试。

**速记**：跟随组件生命周期、只服务一处 UI 的状态必须留在局部。



#### 先用 useState 与 Context 的推进顺序

**状态放置的推进顺序**：是从局部状态开始，依次升级为状态提升、Context、状态管理库的一条路径，每上升一级都要有明确理由。

- 第一级：单个组件内部使用，直接 useState。
- 第二级：兄弟组件共享，提升到最近的共同祖先，用 props 与回调传递（详见本主题第 8 篇 状态提升与单向数据流）。
- 第三级：跨多层且更新频率低，用 Context 免去逐层转发（详见本主题第 14 篇 Context 与跨层级传递）。
- 第四级：跨多层、更新频繁、需要中间件与调试工具，才引入状态管理库。

> 推进顺序本质是成本排序：每上升一级都要多付一层抽象与一份样板代码，收益不足时不要升级。

**速记**：局部状态、状态提升、Context、状态管理库四级递进，够用即止。



### Redux Toolkit 的切片与 store

Redux Toolkit 是 Redux 官方维护的工具集，把旧版手写 action 类型、action creator、reducer 的流程收敛为 configureStore 与 createSlice 两个入口。本节只讲 store 的创建与切片的定义。

#### configureStore 的用法

**configureStore**：是创建 Redux store 的函数，签名是 configureStore(options)，options 为配置对象，可含 reducer、middleware、preloadedState、devTools 四个字段，返回值是 store 对象；store 提供 getState()、dispatch(action)、subscribe(listener) 三个方法。

- reducer：必填，接受单个 reducer 函数，或「切片名到 reducer」的对象。
- middleware：可选，用于追加中间件；传入函数时会收到默认中间件列表。
- devTools：可选，布尔值或配置对象，默认开启 Redux DevTools 集成。
- 默认行为：内置 thunk 中间件、不可变检查与可序列化检查。

```jsx
// store.js
import { configureStore } from "@reduxjs/toolkit";
import todosReducer from "./todosSlice";

const store = configureStore({
  reducer: {
    todos: todosReducer,
  },
});

console.log(store.getState()); // { todos: { items: [], status: "idle" } }
```

> configureStore 返回的 store 已经装配好常用中间件与检查逻辑，不需要手工组合 applyMiddleware。

**速记**：configureStore 接收 reducer 字段，返回装配了 thunk 与检查能力的 store。



#### createSlice 的签名

**createSlice**：是定义切片（slice）的函数，签名是 createSlice(config)，config 为对象，必填 name、initialState、reducers 三个字段，返回值是含 name、reducer、actions 的对象，其中 actions 是按 reducer 名自动生成的 action creator 集合。

- name：字符串，作为 action 类型的公共前缀，例如 name 为 todos 时生成 todos/addTodo。
- initialState：该切片的初始 state，取值需可序列化。
- reducers：对象，键是 reducer 名，值是同步 reducer 函数，接收 state 与 action；函数内可直接以赋值方式修改 state，由 Immer 转换为不可变更新。
- 返回值：reducer 注册进 store，actions 供组件派发。

```jsx
// todosSlice.js
import { createSlice } from "@reduxjs/toolkit";

const todosSlice = createSlice({
  name: "todos",
  initialState: { items: [] },
  reducers: {
    addTodo(state, action) {
      state.items.push({ id: action.payload.id, title: action.payload.title });
    },
    removeTodo(state, action) {
      state.items = state.items.filter((todo) => todo.id !== action.payload);
    },
  },
});

export const { addTodo, removeTodo } = todosSlice.actions;
export default todosSlice.reducer;
```

> [!IMPORTANT]
> **重要内容**：reducers 内写的是可变的赋值语句，由 Immer 据此生成新 state；既修改 state 又返回新值会直接报错。

**速记**：createSlice 接收 name、initialState、reducers，产出 reducer 与同名 action creator。



#### 在 store 中注册 reducer

**在 store 中注册 reducer**：是把 createSlice 导出的 reducer 放进 configureStore 的 reducer 字段，字段键名即该切片在 state 中的路径。

- 键名决定路径：键名为 todos 时，该切片的 state 位于 state.todos。
- 组合方式：多个切片各占一个键，由 configureStore 合并成一棵 state 树。
- 新增流程：新建切片文件、导出 reducer、在 reducer 字段加一行。

> 切片之间不直接引用彼此的 state，跨切片协作放在组件层或 thunk 中组合，避免切片互锁。

**速记**：切片的 reducer 按键名注册进 store，键名就是它在 state 树中的路径。



#### Redux DevTools 的调试价值

**Redux DevTools**：是浏览器扩展形式的 Redux 调试器，通过订阅 store 的 action 流，显示每次 action 的类型、payload 与前后 state。

- 时间旅行：可回放任意一条 action 前后的完整 state，定位是哪次改动引入问题。
- action 日志：显示 action 类型与 payload，直接看出触发更新的是哪个行为。
- 状态快照：把当前 state 导出为 JSON，复现问题时可直接载入。
- 使用前提：state 与 action 需可序列化，configureStore 的默认检查会提示不可序列化的值。

> 调试高频更新时先按 action 类型过滤，再展开 payload，比在完整日志中逐条排查更快。

**速记**：DevTools 以 action 为粒度做时间旅行与快照，是可回溯的调试依据。



### 在组件中使用与异步 thunk

切片定义完成后，组件需要读到 state 并派发 action；异步流程还要借助 createAsyncThunk 把请求的三个阶段接入 reducer。

#### Provider 包裹应用

**Provider**：是 react-redux 提供的组件，签名是 Provider 接收 store 与 children 两个 props，把 store 注入 React 的 Context，使内部任意层级的组件都能通过 Hook 访问同一个 store。

- 位置：包在应用根组件外层，全应用只写一次。
- 唯一性：一次应用只挂载一个 Provider，配一个 store 实例。
- 服务端渲染：每个请求需要独立 store，不能复用模块顶层创建的实例。

```jsx
// main.jsx
import { Provider } from "react-redux";
import { createRoot } from "react-dom/client";
import store from "./store";
import App from "./App";

createRoot(document.getElementById("root")).render(
  <Provider store={store}>
    <App />
  </Provider>
);
```

> [!WARNING]
> **警告内容**：模块顶层创建的 store 在服务端渲染时会被多个请求共享，用户之间的状态可能串号，必须改为按请求创建。

**速记**：Provider 接收 store 与 children，在根组件外层注入唯一的 store。



#### useSelector 的签名

**useSelector**：是从 store 读取 state 的 Hook，签名是 useSelector(selector, equalityFn)，selector 为接收完整 state、返回所需片段的函数，equalityFn 为可选比较函数，默认按引用比较，返回值是选择结果。

- 入参是完整 state，返回值决定组件订阅的数据范围。
- 每次 dispatch 后重新执行 selector，结果发生变化才触发重新渲染。
- 返回对象或数组时每次都是新引用，需配合浅比较选择器避免无谓渲染。

> 选择函数返回的值越细，组件被无关更新牵动的概率越低；不要在选择函数里创建新对象。

**速记**：useSelector 接收 selector 与可选的比较函数，返回选中的 state 片段。



#### useDispatch 的签名

**useDispatch**：是取得派发函数的 Hook，签名是 useDispatch()，无参数，返回值是 store 的 dispatch 函数，调用 dispatch(action) 即触发对应 reducer。

- 用法：dispatch(addTodo({ id: 2, title: "写测试" }))。
- 稳定性：同一个 store 下 dispatch 引用稳定，可安全写入依赖数组。
- 分工：组件只负责派发，异步逻辑放进 thunk。

```jsx
import { useDispatch, useSelector } from "react-redux";
import { addTodo } from "./todosSlice";

function TodoPanel() {
  const items = useSelector((state) => state.todos.items);
  const dispatch = useDispatch();

  return (
    <button onClick={() => dispatch(addTodo({ id: 3, title: "整理笔记" }))}>
      新增（当前 {items.length} 条）
    </button>
  );
}
```

> 组件不直接持有 store 实例，统一经 useSelector 与 useDispatch 访问，测试时才便于替换 store。

**速记**：useDispatch 无参数，返回稳定的 dispatch 函数。



#### createAsyncThunk 的三态与 extraReducers

**createAsyncThunk**：是定义异步 action 的函数，签名是 createAsyncThunk(typePrefix, payloadCreator)，typePrefix 为字符串前缀，payloadCreator 为接收 arg 与 thunkAPI、返回 Promise 的函数，返回值是一个 thunk action creator；该 creator 派发后自动产生 pending、fulfilled、rejected 三种 action。

- pending：请求发出时派发，类型为 typePrefix/pending，可在此把状态置为加载中。
- fulfilled：成功时派发，payload 为 payloadCreator 的返回值。
- rejected：失败时派发，error 字段承载序列化后的错误信息。

```jsx
// todosSlice.js 续
import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

export const loadTodos = createAsyncThunk("todos/load", async (userId) => {
  const response = await fetch(`/api/users/${userId}/todos`);
  return response.json();
});

const todosSlice = createSlice({
  name: "todos",
  initialState: { items: [], status: "idle", error: null },
  reducers: {},
  extraReducers(builder) {
    builder
      .addCase(loadTodos.pending, (state) => {
        state.status = "loading";
      })
      .addCase(loadTodos.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(loadTodos.rejected, (state, action) => {
        state.status = "failed";
        state.error = action.error.message;
      });
  },
});

export default todosSlice.reducer;
```

**extraReducers**：是 createSlice 配置中承载外部 action 的字段，值为接收 builder 的函数，用 builder.addCase(actionCreator, reducer) 把 thunk 的三态接到本切片。

> createAsyncThunk 的结果按状态序列化，payload 必须是可序列化的纯数据；错误细节默认放在 error.message。

**速记**：createAsyncThunk 派发 pending、fulfilled、rejected 三态，用 extraReducers 的 addCase 分别处理。



### Zustand 的极简写法

Zustand 是把状态集中放在一个 store 中、但不依赖 Context 的轻量状态库，组件通过它返回的自定义 Hook 订阅所需片段。本节讲创建、订阅、组件外读写与持久化。

#### create 的签名

**create**：是 Zustand 创建 store 的函数，签名是 create(initializer)，initializer 是接收 set 与 get、返回 store 对象的函数，返回值是一个自定义 Hook；调用该 Hook 并传入选择器即可取用状态。

- set：更新函数，签名是 set(partial, replace)，partial 为部分状态或返回部分状态的函数。
- get：读取函数，签名是 get()，返回当前完整 state。
- 用法：const count = useCounterStore((state) => state.count)。

```jsx
// counterStore.js
import { create } from "zustand";

const useCounterStore = create((set, get) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  readDouble: () => get().count * 2,
}));

export default useCounterStore;
```

> Zustand 的 store 不依赖 Context，任意模块都可直接导入，不需要在组件树顶部包 Provider。

**速记**：create 接收 initializer，返回一个可传选择器的自定义 Hook。



#### 选择器订阅与浅比较

**选择器订阅**：是把选择函数传给自定义 Hook，让组件只订阅选择结果对应的片段，结果按引用比较，未变化则不重新渲染。

- 单值选择：const count = useCounterStore((state) => state.count)，只订阅 count。
- 多值选择：返回对象时每次都是新引用，必须传入浅比较函数。
- 浅比较：zustand/shallow 导出的 shallow 只比较一层成员，成员都相等时视为未变化。

```jsx
import { shallow } from "zustand/shallow";
import useCounterStore from "./counterStore";

function CounterBadge() {
  const { count, increment } = useCounterStore(
    (state) => ({ count: state.count, increment: state.increment }),
    shallow
  );

  return <button onClick={increment}>当前计数：{count}</button>;
}
```

> [!CAUTION]
> **注意内容**：选择器返回新对象且不传浅比较时，每次 store 更新都会触发重新渲染，选择器越复杂代价越明显。

**速记**：选择器决定订阅粒度，返回对象时必须用 shallow 做浅比较。



#### 在组件外读写状态

**在组件外读写状态**：是直接使用自定义 Hook 上挂载的 getState、setState、subscribe 三个静态方法，在非组件代码中读取、写入与监听 store。

- getState()：返回当前完整 state，用于工具函数与事件回调。
- setState(partial, replace)：更新状态，语义与组件内的 set 一致。
- subscribe(listener)：注册监听，listener 接收新 state 与旧 state，返回取消订阅的函数。

> 路由守卫、请求拦截器一类不渲染 UI 的代码通过静态方法访问 store，无需借助组件。

**速记**：自定义 Hook 上挂着 getState、setState、subscribe，供非组件代码读写与监听。



#### 中间件与持久化

**中间件（middleware）**：是包裹 initializer 的高阶函数，签名是 middleware(initializer)，用于在 set、get 之外追加能力。**persist**：是 Zustand 官方的持久化中间件，把指定状态写入 Web Storage，并在初始化时恢复。

- 写法：create(persist(initializer, options))，options 含 name 与 partialize 等字段。
- name：存储键名，必填，用于在存储介质中定位该 store 的数据。
- partialize：选择需要持久化的字段，返回对象，避免把函数与临时状态写进存储。
- 时机：恢复发生在水合阶段，首帧渲染读到的可能是默认值。

```jsx
import { create } from "zustand";
import { persist } from "zustand/middleware";

const useSettingsStore = create(
  persist(
    (set) => ({
      theme: "light",
      setTheme: (theme) => set({ theme }),
    }),
    {
      name: "app-settings",
      partialize: (state) => ({ theme: state.theme }),
    }
  )
);

export default useSettingsStore;
```

> persist 只适合保存少量可序列化配置；业务数据与服务端缓存不要写进本地存储，以免与远端不一致。

**速记**：中间件包裹 initializer，persist 用 name 与 partialize 控制键名与持久化字段。



### 选型与服务端状态提示

两个库都能承载全局状态，差别集中在样板代码、调试能力与学习成本上；此外还有一类常被误放进状态管理库的数据需要单独说明。

#### 按团队规模与调试需求选型

选型依据集中在三项：团队规模、调试需求与迁移成本。

- 团队规模：多人协作、需要统一 action 与目录约定时，Redux Toolkit 的约束更有价值。
- 调试需求：需要时间旅行、action 日志与状态快照时，Redux DevTools 是决定性优势。
- 体积与上手成本：小型应用或单人维护，Zustand 的接入成本更低。
- 迁移成本：已有 Redux 代码继续用 Redux Toolkit 收敛样板；新项目可从 Zustand 起步，规模增长后再评估。

```jsx
// 同一个计数需求在 Zustand 中的最小实现
import { create } from "zustand";

const useCounterStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
}));

useCounterStore.getState().increment();
console.log(useCounterStore.getState().count); // 1
```

> 选型不是阵营问题：两者可以并存，按模块复杂度分别选择。

**速记**：团队约束与调试需求偏 Redux Toolkit，体积与上手成本偏 Zustand。



#### 样板代码量与学习成本对比

两库的成本差异体现在定义、概念、约定与测试四个方面。

- 定义成本：Redux Toolkit 需要 store、切片、Provider 与 Hook 四件套；Zustand 只需一次 create 调用。
- 概念数量：Redux Toolkit 涉及 action、reducer、dispatch、中间件、thunk；Zustand 只需 set、get 与选择器。
- 约定强度：Redux Toolkit 的约定更强，多人协作时代码形态更统一；Zustand 更自由，需要团队自行约束。
- 测试成本：两者都可在组件外断言 store，不必渲染 UI。

```jsx
import { configureStore, createSlice } from "@reduxjs/toolkit";

const counterSlice = createSlice({
  name: "counter",
  initialState: { count: 0 },
  reducers: {
    increment(state) {
      state.count += 1;
    },
  },
});

const store = configureStore({ reducer: { counter: counterSlice.reducer } });
store.dispatch(counterSlice.actions.increment());
console.log(store.getState().counter.count); // 1
```

> 评估选型时用同一段真实业务分别写出最小实现，比较新增文件数与需要理解的新概念数。

**速记**：Redux Toolkit 概念多但约定强，Zustand 代码少但需要团队自律。



#### 服务端状态不属于状态管理库

**服务端状态（server state）**：是存放在远端、由网络请求获取、可能被其他客户端变更的数据，它与组件内部状态的关键区别在于所有权不在当前客户端。

- 失效问题：本地副本随时可能过期，需要按时间或事件重新校验。
- 去重与竞态：同一份请求可能被多个组件同时触发，需要共享结果并丢弃过期响应。
- 分页与乐观更新：滚动加载与提交前的本地预演都需要缓存层支持。

这类问题的解法是数据请求与缓存设计，不是状态管理库的职责；请求的发起时机、取消与竞态处理按本主题第 9 篇 useEffect 与副作用中的写法处理。

> [!IMPORTANT]
> **重要内容**：不要把服务端响应整份复制进全局状态再手工维护，副本一旦不同步，排查成本远高于重新请求。

**速记**：服务端状态的缓存与失效交给数据请求层，全局状态库只管理客户端自有状态。
