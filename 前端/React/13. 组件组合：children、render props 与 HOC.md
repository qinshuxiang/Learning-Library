## 组件组合：children、render props 与 HOC

组件组合（composition）是 React 组织界面的主要方式：用小组件拼出大组件，把「传什么内容」与「放在哪个位置」分开，让组件通过嵌套与 props 协作，而不是靠继承获取能力。

本篇讲三种复用模式：children、render props 与高阶组件 HOC。三者都工作在 UI 层，复用的是结构与渲染方式。

> 逻辑复用优先用自定义 Hook（详见本主题第 15 篇 自定义 Hook）；只有需要复用 UI 结构或渲染方式时，才用本篇的组合模式。

### children 与组合优于继承

本节解决的问题是：父组件如何把内容交给子组件，由子组件决定摆放位置，父组件决定具体内容。

#### children 作为 props 的一种

**children** 是 React 为 props 保留的字段：写在组件标签之间的 JSX 内容会自动归入该组件的 props.children，读取方式与普通 props 一致。

```jsx
function Card({ children }) {
  return <section className="card">{children}</section>;
}

function OrderSummary() {
  return (
    <Card>
      <h2>订单详情</h2>
      <p>共 3 件商品</p>
    </Card>
  );
}
// 渲染结果：section.card 内部依次是 h2 与 p
```

- 不必显式声明：标签之间的内容由 React 自动放进 children。
- 取值形态：单个子元素时是元素本身，多个子元素时是数组，没有子元素时是 undefined。
- 内容类型：可以是字符串、元素、数组、条件表达式结果，也可以是 null。

**速记**：children 是标签之间的内容自动归入 props 的那一个字段。



#### 用 children 做容器与包裹

**容器组件** 是只负责布局与样式的组件，它不知道内部内容是什么，通过 children 接收内容，因此可以复用于任意数据结构。

```jsx
function Panel({ title, children }) {
  return (
    <div className="panel">
      <header>{title}</header>
      <div className="panel-body">{children}</div>
    </div>
  );
}

function UserList({ users }) {
  return (
    <Panel title="用户列表">
      <ul>
        {users.map((user) => <li key={user.id}>{user.name}</li>)}
      </ul>
    </Panel>
  );
}
// Panel 只管外观，列表结构由 UserList 决定
```

- 内容在父组件构造：UserList 决定渲染什么，Panel 只决定外壳。
- 组件解耦：Panel 不依赖具体数据结构，可以复用于任意内容。
- 引用稳定：父组件重新渲染时，children 对应的元素不会因为 Panel 重新渲染而重建。

**速记**：容器组件靠 children 接收内容，只决定外壳不决定数据。



#### 具名插槽式 props 的写法

**具名插槽** 指用多个 props 分别接收不同区域的 UI 内容，如 header、footer、actions，用来表达多个可替换位置。

- 命名约定：用语义化的 props 名（header、footer、actions、icon）表示区域。
- 与 children 的关系：children 是默认插槽，具名插槽是它的补充。
- 传值方式：props 的值可以是元素，接收方直接渲染即可。

**速记**：具名插槽用多个 props 表示多个可替换区域。



#### 组合优于继承的原因

**组合优于继承** 指 React 组件的复用能力靠嵌套与 props 完成，而不是靠类继承共享实现。

- 继承的局限：子类只能继承一个父类，能力来源单一，父类的内部实现会成为耦合点。
- 组合的自由：一个组件可以同时嵌套任意多个组件，能力来源不受数量限制。
- 关系方向：组合是「持有并渲染」，继承是「是某一种」，前者不要求类型同源。
- 官方立场：React 没有提供继承式复用的推荐写法，组合是默认手段。

```jsx
// 组合：LoadingButton 拥有 BaseButton 的能力，二者没有继承关系
function BaseButton({ children, ...rest }) {
  return <button className="btn" {...rest}>{children}</button>;
}

function LoadingButton({ loading, children, ...rest }) {
  return (
    <BaseButton disabled={loading} {...rest}>
      {loading ? "提交中…" : children}
    </BaseButton>
  );
}
// LoadingButton 通过包裹复用 BaseButton，而不是继承它
```

> 旧版 React 的类组件可以用继承扩展，但官方文档明确指出组合是更合适的复用方式。

**速记**：组件复用靠嵌套与 props，不靠类继承。



### render props 模式

render props 要解决的问题是：把「渲染什么」交给调用方决定，组件本身只负责提供数据与状态。

#### render props 的定义

**render props** 是一种组件模式：组件接收一个返回可渲染内容的函数类型 props，由该函数决定最终渲染结果，组件负责调用并传入数据。

```jsx
function MouseTracker({ render }) {
  const [point, setPoint] = useState({ x: 0, y: 0 });
  return (
    <div onMouseMove={(event) => setPoint({ x: event.clientX, y: event.clientY })}>
      {render(point)}
    </div>
  );
}

function App() {
  return <MouseTracker render={(point) => <p>坐标 {point.x}, {point.y}</p>} />;
}
// 组件提供坐标，渲染内容由调用方决定
```

- props 名不固定：约定俗成叫 render，也可以叫任何有意义的函数名。
- 职责分工：组件管状态与行为，函数管输出。
- 类型约定：props 的类型是函数，接收组件传入的参数，返回可渲染内容。

**速记**：render props 用一个函数类型的 props 决定渲染内容。



#### children 作为函数

**children 作为函数** 是 render props 的常见变形：把标签之间的内容写成一个函数，组件调用它并传入数据。

```jsx
function Toggle({ children }) {
  const [on, setOn] = useState(false);
  return <div onClick={() => setOn((prev) => !prev)}>{children(on)}</div>;
}

function App() {
  return <Toggle>{(on) => <span>{on ? "已开启" : "已关闭"}</span>}</Toggle>;
}
// Toggle 提供开关状态，显示内容由调用方决定
```

- 写法差别：不用额外的 props 名，标签之间直接写函数。
- 等价性：children 作为函数与 render props 在能力上等价。
- 注意点：写成函数后，标签之间不能再混入普通元素。

**速记**：children 传函数是 render props 的等价变形。



#### 传参与回调用法

- 传参：组件把内部状态或查询结果作为参数传给渲染函数。
- 回调：渲染函数接收数据后返回 JSX，也可以在其中再调用父级传入的处理函数。
- 多参数：需要传多个值时，传一个对象比排长参数列表更清晰。

```jsx
function DataLoader({ url, renderItem }) {
  const [items, setItems] = useState([]);
  useEffect(() => {
    fetch(url)
      .then((res) => res.json())
      .then(setItems);
  }, [url]);
  return <ul>{items.map((item) => renderItem(item))}</ul>;
}

function ProductList() {
  return (
    <DataLoader
      url="/api/products"
      renderItem={(product) => <li key={product.id}>{product.name}</li>}
    />
  );
}
// 数据加载逻辑复用，每一项的渲染由调用方决定
```

**速记**：组件把数据作为参数交给渲染函数，由函数返回 JSX。



#### 适用场景与可读性代价

- 适用：需要复用状态或行为，同时允许调用方自由决定渲染结果。
- 代价一：嵌套加深，多层 render props 形成金字塔形缩进。
- 代价二：函数内联，每次渲染都会创建新函数，不利于引用稳定。
- 替代：纯逻辑复用改用自定义 Hook，只有渲染方式需要参数化时才用 render props。

```jsx
// 同一份坐标逻辑，改用自定义 Hook
function useMousePoint() {
  const [point, setPoint] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handleMove = (event) => setPoint({ x: event.clientX, y: event.clientY });
    window.addEventListener("mousemove", handleMove);
    return () => window.removeEventListener("mousemove", handleMove);
  }, []);
  return point;
}

function CoordinateLabel() {
  const point = useMousePoint();
  return <p>坐标 {point.x}, {point.y}</p>;
}
// 逻辑复用交给 Hook，渲染不再需要函数 props
```

**速记**：render props 灵活但嵌套深、函数多，纯逻辑复用应改用自定义 Hook。



### 高阶组件 HOC

HOC 要解决的问题是：在不修改原组件的前提下，为组件附加横切能力，如鉴权、埋点、加载状态。

#### HOC 的定义

**高阶组件（Higher-Order Component，HOC）** 是一个函数：接收一个组件作为参数，返回一个新的组件，用于附加 props 或行为。

```jsx
function withLoading(WrappedComponent) {
  return function WithLoading({ loading, ...rest }) {
    if (loading) return <p>加载中…</p>;
    return <WrappedComponent {...rest} />;
  };
}

function UserTable({ users }) {
  return <ul>{users.map((user) => <li key={user.id}>{user.name}</li>)}</ul>;
}

const UserTableWithLoading = withLoading(UserTable);
// loading 为真时渲染占位，否则渲染 UserTable
```

- 输入输出：输入组件，输出组件，原组件本身不被修改。
- 命名约定：HOC 名以 with 开头，如 withAuth、withTheme。
- 用途：注入 props、包裹条件渲染、订阅外部数据。

**速记**：HOC 是接收组件返回新组件的函数。



#### 典型写法与 props 透传

- 透传：用展开运算符把剩余 props 交给被包裹组件，避免逐一列举。
- 不覆盖：HOC 注入的 props 名要避免与使用方的 props 冲突。
- 转发 ref：需要透传 ref 时用 forwardRef 包裹，否则 ref 会指向 HOC 自身。

```jsx
function withAuth(WrappedComponent) {
  return function WithAuth(props) {
    const { user } = useCurrentUser();
    if (!user) return <p>请先登录。</p>;
    return <WrappedComponent {...props} user={user} />;
  };
}

function Profile({ user, compact }) {
  return <p>{compact ? user.name : user.name + " 的主页"}</p>;
}

const AuthProfile = withAuth(Profile);
// 有登录用户时渲染 Profile，并把 user 注入其 props
```

**速记**：HOC 用展开运算符透传其余 props，注入名须避开冲突。



#### 命名与静态属性处理

- 显示名：给返回的组件设置 displayName，便于在开发者工具中辨认。
- 静态属性：被包裹组件上的静态属性不会自动带到新组件，需要手动复制。
- 引用转发：HOC 会额外产生一层组件，调试时链路上会多出节点。

```jsx
function withAuth(WrappedComponent) {
  function WithAuth(props) {
    const { user } = useCurrentUser();
    if (!user) return <p>请先登录。</p>;
    return <WrappedComponent {...props} user={user} />;
  }
  const name = WrappedComponent.displayName || WrappedComponent.name || "Component";
  WithAuth.displayName = "withAuth(" + name + ")";
  return WithAuth;
}
// 开发者工具中显示 withAuth(Profile)，而不是匿名的 WithAuth
```

> 现代项目更倾向于用 Hook 取代「注入 props」这类 HOC，HOC 的剩余价值主要在包裹渲染与接入第三方库。

**速记**：HOC 需手动维护 displayName 与静态属性。



#### HOC 的历史地位与现状

- 历史：在 Hooks 出现之前，HOC 与 render props 是复用逻辑的主要手段。
- 现状：React 16.8 引入 Hooks 之后，逻辑复用基本由自定义 Hook 承担。
- 保留场景：需要在渲染层面统一包裹、拦截，或对接只提供 HOC 的第三方库。
- 叠加成本：多个 HOC 嵌套会形成包裹链，参数来源难以追踪。

```jsx
// 多个 HOC 叠加：参数来源需要逐层向上找
const EnhancedTable = withAuth(withLoading(withTheme(UserTable)));
// 读取 props 时无法一眼看出 user 由哪一层注入
```

> [!CAUTION]
> **注意内容**：多个 HOC 叠加后，props 的注入层级与顺序难以追踪，调试成本随层数增加。

**速记**：Hooks 之后 HOC 退居渲染包裹与库对接场景。



### 三种模式对比与取舍

三种模式都能复用，但复用的东西不同，选型的依据是「要共享的是结构、行为，还是横切能力」。

#### 复用维度对比

- children：复用 UI 结构，不涉及逻辑共享，改造最小。
- render props：复用行为或状态，渲染结果由调用方决定。
- HOC：复用横切行为，作用于整个组件，包裹关系在组件外部。
- 自定义 Hook：复用逻辑，不改变组件树结构（详见本主题第 15 篇 自定义 Hook）。

**速记**：children 复用结构，render props 复用行为，HOC 复用横切能力，Hook 复用逻辑。



#### 现代偏好：自定义 Hook 优先

- 判据一：只共享逻辑、不共享 UI，用自定义 Hook。
- 判据二：需要共享 UI 结构与摆放方式，用 children 或具名插槽。
- 判据三：需要按调用方参数化渲染，用 render props。
- 判据四：需要统一拦截渲染或对接第三方库，用 HOC。

```jsx
// 逻辑复用：Hook 版本，组件树不新增层级
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);
  return width;
}
```

> [!TIP]
> **建议内容**：新写复用代码时先判断「共享的是逻辑还是 UI」，前者用自定义 Hook，后者才考虑组合模式。

**速记**：共享逻辑用 Hook，共享 UI 才用组合模式。



#### 同一需求三种写法的对比示例

以「为一段内容提供展开与收起」为例，三种写法分别对应不同的复用粒度。

```jsx
// 写法一：render props，把展开状态交给调用方
function Collapsible({ render }) {
  const [open, setOpen] = useState(false);
  return <div onClick={() => setOpen((prev) => !prev)}>{render(open)}</div>;
}

// 写法二：HOC，为组件注入展开状态
function withCollapsible(WrappedComponent) {
  return function WithCollapsible(props) {
    const [open, setOpen] = useState(false);
    const toggle = () => setOpen((prev) => !prev);
    return (
      <div onClick={toggle}>
        <WrappedComponent {...props} open={open} />
      </div>
    );
  };
}

// 写法三：自定义 Hook，组件自行渲染
function useCollapsible(initialOpen = false) {
  const [open, setOpen] = useState(initialOpen);
  const toggle = () => setOpen((prev) => !prev);
  return { open, toggle };
}

function CollapsiblePanel() {
  const { open, toggle } = useCollapsible();
  return <button onClick={toggle}>{open ? "收起" : "展开"}</button>;
}
// 写法三结构最简、逻辑可复用，是当前推荐写法
```

**速记**：同一份状态复用，Hook 写法层级最少、可读性最好。



#### 何时仍值得用组合模式

- 需要统一外观：希望所有子组件共享一层外壳时，用 children 容器。
- 需要多个可替换区域：用具名插槽表达 header、footer 等位置。
- 渲染结果依赖调用方数据：用 render props 把渲染权交给调用方。
- 第三方库只提供 HOC：按其接口接入，不强行改写为 Hook。

**速记**：UI 结构、多区域替换与库对接场景，组合模式仍是最佳选择。



### 避免嵌套地狱

嵌套地狱是组合模式最主要的副作用：包裹层数一多，缩进膨胀、来源不清、改动风险上升。本节给出压平手段。

#### 多层包裹的可读性问题

- 缩进膨胀：每层包裹向右推进，深层内容的缩进可达十几列。
- 视线断裂：开标签与闭标签相隔很远，对应关系难以核对。
- 参数分散：同一组数据在不同层之间传来传去，来源不明确。

```jsx
// 四层包裹，内容被推到很深的缩进位置
<ThemeProvider>
  <AuthProvider>
    <DataLoader url="/api/user" render={(user) => (
      <Collapsible render={(open) => <p>{open ? user.name : "点击展开"}</p>} />
    )} />
  </AuthProvider>
</ThemeProvider>
```

> [!WARNING]
> **警告内容**：包裹层数超过三层时，组件树的阅读与改动成本会显著上升，应优先考虑用 Hook 扁平化。

**速记**：多层包裹造成缩进膨胀与来源不清，是组合模式的主要代价。



#### 用参数化与配置合并减少层数

- 合并 props：把多个布尔与配置项合并到一个 props 对象，减少包装组件数量。
- 参数化：用一个组件加不同参数，替代为每种情况各写一个包装组件。
- 提取 Hook：把状态逻辑移出组件树，包裹层随之消失。

```jsx
// 合并前需要三层包装，合并后一个组件加配置
function Box({ bordered = false, padding = 0, children }) {
  const style = { border: bordered ? "1px solid" : "none", padding };
  return <div style={style}>{children}</div>;
}

function App() {
  return <Box bordered padding={16}>内容</Box>;
}
// 层数从三层降到一层
```

**速记**：合并配置项与参数化组件，是压平包裹层数的直接手段。



#### 拆分与组合的平衡

- 拆分过度：组件过细会出现大量只做转发的中间组件，反而增加跳转成本。
- 组合适度：以「是否独立可测、是否会被复用」作为拆分判据。
- 就近抽象：只在出现第二处相同需求时才抽成通用组件，避免提前抽象。

```jsx
// 过度拆分：只做透传，没有独立逻辑
function TitleWrapper({ children }) {
  return <div>{children}</div>;
}

// 合理拆分：承担标题层级与样式约定
function SectionTitle({ level = 2, children }) {
  const Tag = "h" + level;
  return <Tag className="section-title">{children}</Tag>;
}
```

**速记**：拆分以可测与可复用为判据，不为透传而增设中间层。



#### 目录组织建议

- 通用组件：放在 components 目录，与业务解耦。
- 组合包装：与所用组件同目录，或以 with 前缀命名，便于检索。
- 业务组件：按功能域分目录，如 features/order、features/profile。
- 自定义 Hook：统一放 hooks 目录，文件名以 use 开头。

**速记**：通用组件、包装、业务组件与 Hook 分目录归置，按用途检索。
