## React 简介与编写方式

### 什么是 React

**什么是 React** 这一节回答三件事：React 是什么、它在技术选型中处于什么位置、它与同类的 Vue 有何取向差异。

#### React 是什么

**React**：是 Meta（原 Facebook）于 2013 年开源的用于构建用户界面的 JavaScript 库，核心职责是把界面描述为组件树，并在数据变化时高效地更新视图。

- 定位：只覆盖视图层，不内置路由、状态管理与数据请求方案，这些由生态中的独立库补充。
- 基本单元：组件（component），一个组件是接收 props 并返回元素（element）的函数。
- 数据入口：props 与 state，props 由父组件传入且只读，state 是组件自身持有的内部状态。
- 更新机制：数据变化触发重新渲染（re-render），由协调（reconciliation）算法计算并提交最小改动。

```jsx
function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

// 把组件写成元素交给框架渲染
// <Greeting name="Ada" /> 渲染出标题「Hello, Ada!」
```

> React 19 是当前稳定大版本；React 16.8 引入 Hooks，函数组件自此可以持有 state 与副作用，class 组件逐步被取代。

**速记**：React 是构建用户界面的 JavaScript 库，组件是函数，视图是数据的映射结果。



#### 库而非框架的定位

**库（library）与框架（framework）的区别**：是控制权的归属不同，框架规定代码的调用顺序并由框架调用代码，库只提供能力并由代码调用库。

- 控制反转：框架要求按框架的约定组织代码，React 把组合权交给使用方，由使用方决定结构。
- 可替换性：视图层之外的部件可以自由替换，路由选 React Router，全局状态选 Redux Toolkit 或 Zustand。
- 生态代价：自由度高的另一面是选型成本，项目需要自行确定路由、状态、数据请求与样式方案。
- 常见说法：「React 是一个用于构建用户界面的库」是官方文档的表述，「React 框架」是口语化的泛指。

```jsx
// React 只负责把数据渲染成界面，页面如何组织由使用方决定
function App() {
  return (
    <main>
      <Header />
      <TodoList />
    </main>
  );
}
```

> 把 React 当作框架来理解会带来错误预期：它不会替项目决定目录结构、路由方式与数据流架构。

**速记**：React 是库不是框架，视图之外的方案由项目自行选择。



#### React 与 Vue 的取向差异

**React 与 Vue 的取向差异**：是同一目标下的两种实现取向，React 把界面写成 JavaScript 的延伸，Vue 把 JavaScript 组织进模板语法。

- 模板与表达式：Vue 使用模板语法并内置指令，React 直接使用 JSX，结构、条件与循环都写成 JavaScript 表达式。
- 更新来源：Vue 依赖响应式代理自动追踪依赖，React 依靠显式调用状态更新函数触发重新渲染。
- 心智负担：React 的自由度更高，需要团队自行约定范式；Vue 的约定更多，上手路径更短。
- 共同点：两者都以组件为基本单元，都支持单向数据流与组件组合。

```jsx
// React 中条件与列表都是 JavaScript 表达式
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>{todo.title}</li>
      ))}
    </ul>
  );
}
```

> 选型没有绝对优劣；本篇及本系列只讨论 React 的机制与用法，Vue 相关内容见 前端/Vue3 主题。

**速记**：React 用 JSX 与显式状态更新，Vue 用模板与响应式代理，差异在控制方式不在能力。



### React 解决什么问题

React 要解决的核心问题是界面如何随数据变化而更新，它把手工操作 DOM 的过程替换为对期望界面的描述。

#### 手动操作 DOM 的困境

**手动操作 DOM 的困境**：是应用规模变大后，由开发者逐个定位并修改节点所带来的状态不一致与维护成本。

- 状态分散：真实数据存在 JavaScript 变量里，界面状态存在 DOM 里，两份状态需要人工保持同步。
- 更新遗漏：一处数据变化要同步修改多个节点，漏改一处就会出现界面与数据不符。
- 顺序耦合：插入、删除、排序依赖精确的节点操作顺序，相关逻辑难以跨场景复用。
- 性能粗糙：逐节点操作无法自动区分必要与不必要，也不能自动合并批量更新。

```js
// 手动方式：数据变化后需要自行找到节点并改写内容
const listNode = document.getElementById("todo-list");
// 数据新增一条后，还要重新创建节点、维护顺序并处理删除
```

> 手动操作并非不可用，问题在于规模：节点越多、状态越复杂，人工同步的出错概率越高。

**速记**：手动操作 DOM 的代价是两套状态需要人工同步，规模一大就容易漏改。



#### 声明式与命令式之别

**声明式编程（declarative programming）**：是描述结果应该是什么样、由运行时把描述转换为操作步骤的编程方式。**命令式编程（imperative programming）**：是描述每一步该怎么做、由开发者编排执行过程的编程方式。

- React 的声明式：组件根据当前 props 与 state 返回元素描述，框架据此把真实 DOM 同步到该描述。
- 命令式的代价：步骤与目标耦合，目标变化时需要重写步骤，复用只能停留在片段层面。
- 判断标准：代码在表达是什么还是在表达怎么做，前者更接近声明式。
- 边界：底层实现仍然是命令式的 DOM 操作，声明式是使用方看到的抽象层。

```jsx
function CountLabel({ count }) {
  // 只声明界面与数据的关系，不关心 DOM 如何被改写
  return <button>点击次数：{count}</button>;
}
```

> 声明式不等于不写过程，而是把过程交给框架：使用方描述目标，更新步骤由 React 负责。

**速记**：声明式描述结果，命令式编排步骤，React 把 DOM 更新过程交给框架。



#### 组件化与复用

**组件化（componentization）**：是把界面拆分为独立、可组合、可复用的单元，每个单元自描述其结构与数据依赖。

- 单元边界：一个组件对应界面上一个相对独立的区域，接收 props 并输出元素。
- 复用方式：同一组件在多处使用，通过不同的 props 呈现不同内容。
- 隔离性：组件的内部实现对外不可见，修改内部实现不影响调用方。
- 组合能力：小组件拼装成区块，区块再拼装成页面，层级可以按需要加深。

```jsx
function UserCard({ name, title }) {
  return (
    <article>
      <h2>{name}</h2>
      <p>{title}</p>
    </article>
  );
}

// 复用同一组件，传入不同 props
// <UserCard name="Ada Lovelace" title="数学家" />
// <UserCard name="Grace Hopper" title="计算机科学家" />
```

> 组件化的收益随规模增长：复用减少重复代码，边界清晰降低单次改动的影响面。

**速记**：组件是自描述、可组合、可复用的界面单元。



#### 单向数据流初识

**单向数据流（one-way data flow）**：是数据由父组件通过 props 流向子组件、事件由子组件向上通知父组件的传递模型。

- 方向固定：props 只能由父传给子，子组件不能改写收到的 props。
- 变化来源：变化由持有 state 的组件发起，再向下重新传递，形成可追踪的因果链。
- 调试友好：数据流向单一，出现问题时可以沿组件树自顶向下定位。
- 反例排除：双向绑定会让变化来源难以追踪，React 不采用该模型。

```jsx
function SearchBox({ keyword, onChange }) {
  // 数据向下传入，输入变化时通过 onChange 向上通知
  return (
    <input
      value={keyword}
      onChange={(event) => onChange(event.target.value)}
    />
  );
}
```

> 状态放在哪一层、状态提升与派生状态的取舍详见本主题第 8 篇状态提升与单向数据流。

**速记**：数据沿组件树向下传递，事件向上通知，变化的来源唯一且可追踪。



### 声明式与组件化

这一节把前面两条主线落到可以指导写代码的原则上：如何用声明式视角组织代码，如何用组件化拆分界面。

#### 声明式编程的含义

**声明式编程的含义**：是把注意力从如何一步步更新转移到当前状态下界面应该长什么样。

- 视图是函数：界面等于组件对当前 props 与 state 的映射结果。
- 幂等描述：同一组输入得到同一份元素描述，不依赖此前执行过哪些操作。
- 数据驱动：先改数据，再由框架推导界面，不直接拼装节点。
- 可测试性：给定输入即可断言输出，界面描述可以脱离浏览器环境检查。

```jsx
function StatusBadge({ status }) {
  // 同一份数据决定同一份界面，不需要记录上一次的样子
  return <span>{status === "done" ? "已完成" : "进行中"}</span>;
}
```

> 声明式的判断标准是代码在描述结果还是编排步骤，而不在于是否出现了函数调用。

**速记**：声明式把界面看作数据的映射函数，先改数据再让框架推导界面。



#### 组件作为基本单元

**组件作为基本单元**：指应用中一切可复用、可组合、可测试的界面逻辑都以组件为容器组织。

- 命名约定：组件名用大驼峰（如 UserCard、TodoList），首字母大写用于与宿主标签名区分。
- 输入输出：输入是 props，输出是元素，可以没有输入，也可以不输出可视内容。
- 纯函数倾向：理想状态下同样的 props 渲染同样的结果，不修改组件之外的变量。
- 文件粒度：通常一个文件导出一个组件，文件名与组件名保持一致。

```jsx
// components/UserCard.jsx
export function UserCard({ name, title }) {
  return (
    <article>
      <h2>{name}</h2>
      <p>{title}</p>
    </article>
  );
}
```

> 组件可以理解为返回元素的函数，这个定义在本主题第 3 篇组件基础与 props 中正式展开。

**速记**：组件是界面逻辑的容器，输入 props 输出元素，命名用大驼峰。



#### 组合优于继承

**组合优于继承**：是 React 推荐的复用方式，通过把一个组件作为另一个组件的内容传入完成功能拼装，而不是通过类继承扩展组件。

- 传递内容：通过 props 的 children 把元素传给子组件，由子组件决定放置位置。
- 任意嵌套：组合可以叠加多层，行为叠加而不产生继承链的脆弱性。
- 继承的问题：继承要求子类了解父类实现细节，改动父类容易波及全部子类。
- 两条路径：UI 结构复用走组合，逻辑复用走自定义 Hook，二者分工不同。

```jsx
function Panel({ title, children }) {
  return (
    <section>
      <h3>{title}</h3>
      <div>{children}</div>
    </section>
  );
}

// 内容由调用方传入，Panel 不需要知道里面是什么
// <Panel title="统计"><p>共 12 条记录</p></Panel>
```

> children、render props 与高阶组件三种组合模式的完整讨论详见本主题第 13 篇组件组合。

**速记**：用传入 children 等 props 的方式拼装功能，而不是用继承扩展组件。



### 编写与运行方式

这一节说明 React 代码从源码到浏览器的链路，以及上手所需的最少步骤。

#### 现代前端工程的运行链路

**现代前端工程的运行链路**：是源码、构建工具处理、浏览器执行三段，构建工具负责编译 JSX、解析模块、启动开发服务器并在改动后刷新页面。

- 源码：以 .jsx 或 .js 结尾的文件，包含 JSX 与 ES 模块语法，浏览器无法直接执行。
- 构建：把 JSX 编译为普通函数调用，解析 import 依赖，按需做语法降级与代码分割。
- 开发服务器：提供本地地址与热更新（hot module replacement），保存文件后界面即时刷新。
- 生产产物：输出压缩后的静态资源，部署时只需托管这些文件，不需要在服务器上运行 Node.js。

```bash
# 开发：启动本地服务器，具备热更新
npm run dev

# 构建：产出可部署的静态资源
npm run build
```

> 构建工具的插件、路径别名与环境变量配置详见 前端/构建工具 主题，本系列只说明运行方式。

**速记**：React 源码由构建工具编译 JSX 并解析模块，开发用本地服务器，上线用构建产物。



#### 从 CDN 直接引入与 JSX 转译

**从 CDN 直接引入**：是不经过构建工具、通过脚本标签加载 React 的方式，适合一次性试验与最小示例。

- 脚本引入：先加载 React 与 ReactDOM 的运行时脚本，再让页面中的 JSX 得到转译。
- JSX 转译：Babel 的独立版本可以在浏览器中把 JSX 转成函数调用，代价是额外的运行开销与体积。
- 使用限制：无法使用 npm 依赖、无法按需打包、无法做语法降级，生产环境不推荐。
- 适用场景：验证单个语法点、编写演示页面、在受限环境中临时跑通。

```html
<!-- 依次引入运行时脚本与浏览器内转译脚本 -->
<script src="react.production.min.js"></script>
<script src="react-dom.production.min.js"></script>
<script src="babel.min.js"></script>
<script type="text/babel">
  const container = document.getElementById("root");
  const root = ReactDOM.createRoot(container);
  root.render(<h1>Hello, React</h1>);
</script>
```

> [!WARNING]
> **警告内容**：在浏览器中实时转译 JSX 会带来明显的体积与运行开销，只能用于演示，不得用于生产环境。

**速记**：CDN 方式靠脚本标签与浏览器内转译运行，仅适合演示。



#### 用 Vite 创建 React 项目

**Vite**：是面向现代浏览器的前端构建工具，开发阶段基于原生 ES 模块直接服务源码，生产构建时打包输出静态资源。

- 创建项目：执行创建命令并按交互提示选择 React 模板，得到可运行的最小工程。
- 安装依赖：进入项目目录执行安装命令，安装 react、react-dom 与开发依赖。
- 启动开发：执行 dev 脚本获得本地地址，修改源码后页面自动更新。
- 构建预览：执行 build 脚本产出静态资源，用 preview 脚本在本地预览构建产物。

```bash
# 创建项目并按交互提示选择 React 模板
npm create vite@latest my-app
cd my-app
npm install

npm run dev      # 启动开发服务器
npm run build    # 产出生产构建
npm run preview  # 本地预览构建产物
```

> [!TIP]
> **建议内容**：本地开发应使用 Node.js 的当前 LTS 版本，版本过旧会导致构建工具与依赖安装失败。

**速记**：用 Vite 一条创建命令起步，dev 开发、build 构建、preview 预览。



#### 文件与目录的基本约定

**文件与目录的基本约定**：是 React 工程模板给出的初始结构，入口文件负责挂载根组件，其余组件按功能拆分到独立文件。

- index.html：页面模板，包含唯一的挂载节点与入口脚本引用。
- src/main.jsx：应用入口，创建根（root）并把根组件渲染进去。
- src/App.jsx：根组件，通常是页面结构与路由配置的落点。
- package.json：记录依赖与脚本命令，脚本以 dev、build、preview 为常规命名。

```jsx
// src/main.jsx：把根组件挂载到页面的挂载节点上
import { createRoot } from "react-dom/client";
import App from "./App.jsx";

const container = document.getElementById("root");
const root = createRoot(container);
root.render(<App />);
```

> 目录如何进一步划分（按功能、按路由、按类型）属于工程约定，详见本主题第 22 篇测试与工程实践。

**速记**：index.html 提供挂载节点，main.jsx 负责挂载，App.jsx 是根组件。

#### 各阶段的学习重点

四段各有明确的能力目标，从写出可交互组件起步，逐段推进到机制理解与工程落地。

- 基础段：掌握 JSX、props、事件与 state 四件套，能独立写出可交互的单个组件。
- Hooks 与数据流段：理解副作用的边界与依赖数组，掌握状态分层与跨层级传递。
- 原理与性能段：能读懂渲染流程与协调过程，在出现性能问题时定位到具体原因。
- 生态与工程段：按项目需要接入路由、状态管理与测试，形成可维护的工程结构。

```jsx
// 基础段结束时应能独立写出的组件形态：结构、props 与事件齐备
function TaskItem({ title, done, onToggle }) {
  return (
    <li>
      <label>
        <input type="checkbox" checked={done} onChange={onToggle} />
        {title}
      </label>
    </li>
  );
}
```

> 基础段决定后续上限：props 的只读性与 state 的不可变更新若理解不牢，后面遇到闭包与依赖数组的问题会成倍放大。
