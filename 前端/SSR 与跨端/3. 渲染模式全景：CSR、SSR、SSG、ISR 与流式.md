## 渲染模式全景：CSR、SSR、SSG、ISR 与流式

**渲染模式全景**：是把内容生成的时间与位置铺开成一张完整的坐标，客户端渲染与服务端渲染只是其中两端，中间还有构建期生成、部署后再生与分块输出等形态。

客户端渲染与服务端渲染的机制与差异属于本主题第 2 篇 客户端渲染与服务端渲染，本篇不再重述。本篇讨论其余模式的机制、它们各自回答的问题，以及一个项目如何把多种模式组合使用。

### 静态站点生成是什么

**静态站点生成（static site generation，SSG）**：是在构建阶段运行页面代码并把结果写成静态文件的做法，请求到来时服务端只负责返回已经存在的产物。

#### 构建期预渲染

构建期预渲染把渲染从请求链路上整体摘出来：页面在构建时被执行一次，产出的 HTML 与静态资源被写入输出目录，运行时不再有渲染步骤。

- 执行时机：构建命令运行期间，每个页面各渲染一次。
- 输入数据：构建时可访问数据源，但拿到的是构建那一刻的数据快照。
- 输出形态：每个路径对应一个 HTML 文件，另有共享的脚本与样式文件。
- 运行时角色：服务端只做文件读取与传输，不执行页面代码。

```bash
npm run build
# ● 生成静态页面：/articles/1
# ● 生成静态页面：/articles/2
# ○ 输出目录：dist/
```

```js
// 构建期执行的页面逻辑：数据在此刻被取回并写入产物
export async function buildArticlePage(articleId) {
  const article = await getArticleById(articleId);
  return { path: `/articles/${articleId}`, html: renderToString(article) };
}

const page = await buildArticlePage(1);
console.log(page.path); // "/articles/1"
```

- 构建是幂等的：同一份源码与同一份数据重复构建，产物应当一致。
- 构建可并行：页面之间互不依赖时，构建器可以并发渲染以缩短总时长。
- 构建失败即整体失败：任一页面取数异常通常会中断构建，需要为可选数据准备兜底。

**增量构建**：是只重新生成发生变化页面的做法，它把构建时长与全站页面数解耦，变为与改动范围相关。

- 依据来源：以内容标识或上次构建记录判断哪些产物已过期。
- 适用范围：页面数量大、且每次发布只影响少量页面的站点。
- 代价：需要额外维护构建缓存与依赖关系，配置复杂度上升。

> 构建期预渲染的产物是文件而不是进程，因此部署时不需要为渲染准备常驻服务。

**速记**：构建期预渲染在构建命令中把页面写成静态文件，运行时不再执行渲染。



#### 产物的托管与缓存

**静态产物托管**：是把生成的 HTML、脚本与样式交由静态服务器或内容分发网络承载的做法，服务端只按路径返回文件。

- 缓存策略：静态文件内容与路径绑定，可设置长期缓存并由内容分发网络边缘节点命中。
- 回源行为：缓存未命中时才回到源站取文件，源站压力远低于逐请求渲染。
- 失效方式：内容更新依靠重新发布产物或刷新缓存，不依靠运行时计算。
- 一致性：同一路径在缓存有效期内返回内容一致，天然避免了渲染抖动。

```text
请求 /articles/1 → 边缘节点缓存命中 → 直接返回 HTML
请求 /articles/2 → 边缘节点未命中 → 回源取文件 → 写入缓存 → 返回 HTML
```

- 首字节时间通常最短，因为省去了取数与渲染。
- 可用的承载方式多，对象存储加内容分发网络即可支撑。
- 代价是内容新鲜度由发布频率决定。

**缓存键**：是缓存系统用来区分不同响应的标识，对静态产物而言通常是请求路径与查询参数的组合。

- 键过粗：不同内容的请求落到同一份产物上，出现内容错配。
- 键过细：每个查询参数都产生一份产物，缓存命中率被拉低。
- 处理原则：只把真正影响内容的参数纳入缓存键。

> 托管的便利来自产物不可变：只要路径相同、内容不变，缓存就可以放心长期有效。

**速记**：静态产物按路径缓存并可由边缘节点直接返回，源站只承担回源压力。



#### 静态生成的适用与代价

**静态生成的适用与代价**：适用于内容在较长时间内保持一致的页面，代价是构建时长随页面数增长且内容更新有延迟。

- 适用内容：文档、博客、帮助中心、营销页与不依赖登录状态的公开页面。
- 规模限制：页面数量很大时构建时间显著增长，构建资源成为瓶颈。
- 更新延迟：内容变更到用户可见之间隔了一次完整构建与发布。
- 个性化缺失：同一路径对所有访问者输出相同内容，无法按用户定制。

```text
页面数 100：构建约数十秒
页面数 10000：构建时间随页面数增长，需考虑增量构建与并行
```

**构建产物可核查**：构建日志通常会标出每个路由最终采用的渲染方式，把日志与页面的内容特征对照，是最直接的复核手段。

> [!NOTE]
> **提醒内容**：静态生成的产物在构建时定形，任何依赖请求上下文的内容都无法在构建期获得，遇到这类内容要改用其他模式。

**速记**：静态生成内容稳定、托管便宜，但构建时长随页面数增长，且更新有延迟。



### 增量静态再生成与按需生成

**增量静态再生成与按需生成**：是在静态生成的基础上补上更新能力的两条路径，前者按时间间隔在后台重新生成，后者由事件显式触发。

#### 时间驱动的再生成

**增量静态再生成（incremental static regeneration，ISR）**：是让静态页面在部署后按配置的时间间隔在后台重新生成的做法，用户始终拿到已生成的产物，不等待重新生成完成。

- 再生成间隔：为页面设置一个有效期，超过有效期后由下一次请求触发后台更新。
- 服务策略：重新生成期间继续返回旧产物，避免用户等待。
- 适用范围：内容更新有节奏、可容忍一个间隔内延迟的页面。
- 与静态生成的差别：构建不再是内容更新的唯一入口。

```ts
// 元框架通常以路由段配置声明再生成间隔
export const revalidate = 60; // 单位为秒

export default async function ArticlePage() {
  const article = await getArticleById(1);
  return <ArticleDetail article={article} />;
}
```

```text
t=0s    首次请求 → 返回已生成产物，同时开始后台再生成
t=0.3s  后台再生成完成 → 缓存替换为新产物
t=60s   有效期到 → 下一次请求再次触发后台再生成
```

- 旧产物兜底：再生成失败时继续服务旧内容，可用性不受影响。
- 间隔取舍：间隔越短内容越新，源站压力越大。
- 冷启动代价：页面从未生成过时，第一个请求需要等待一次完整渲染。

> 再生成间隔是内容新鲜度与源站压力之间的调节旋钮，没有适用于所有页面的取值。

**速记**：时间驱动的再生成按间隔在后台刷新静态页面，用户始终拿旧产物，不等待刷新。



#### 事件驱动的按需生成

**事件驱动的按需生成**：是在内容发生变化时由业务代码显式通知渲染层失效，只重新生成受影响的页面，不等待时间间隔。

- 触发来源：内容发布、后台编辑保存、数据同步完成等明确事件。
- 失效粒度：可按路径失效，也可按标签失效，粒度决定重新生成的范围。
- 与时间驱动的差别：更新时刻由业务决定，而不是由定时器决定。
- 适用范围：内容更新不规律、且要求发布后尽快可见的页面。

```ts
// 内容发布后按标签失效，只重建引用该标签的页面
import { revalidateTag } from "next/cache";

export async function publishArticle(articleId: number) {
  await markArticlePublished(articleId);
  revalidateTag(`article-${articleId}`);
}
```

```text
编辑保存 → 触发失效 → 标记相关页面待再生成 → 下次请求返回新产物
```

- 精确失效可避免全站重建，代价是要维护好标签与页面的对应关系。
- 事件到达顺序异常时要能重复执行，也就是失效操作应当幂等。
- 批量变更时按最小公共粒度失效，避免逐条触发造成大量重复重建。

> [!IMPORTANT]
> **重要内容**：按需生成要求失效动作与内容写入在同一业务链路中完成，漏掉失效调用会让页面长期停留在旧内容上。

**速记**：事件驱动的按需生成由业务事件触发失效，更新更及时，但要求失效调用可靠。



#### 缓存失效与一致性

**缓存失效与一致性**：描述重新生成与返回给用户的内容之间可能出现的暂时不一致，以及如何把这种窗口控制在可接受范围内。

- 多级缓存：边缘节点、渲染层缓存与数据层缓存各自有有效期，任一层未刷新都会读到旧内容。
- 推广窗口：失效是异步的，从触发到全部节点更新之间存在时间差。
- 数据与页面：页面已更新但数据层仍返回旧值时，会生成内容错误的产物。
- 状态码与回退：再生成失败时应继续返回旧产物，而不是直接把错误暴露给用户。

```text
写入数据 → 失效页面缓存 → 后台再生成 → 边缘缓存更新
若数据层缓存未同步失效，再生成的产物仍可能是旧数据
```

- 排查顺序：先确认数据层是否为最新，再确认页面是否已再生成，最后确认边缘节点是否已更新。
- 观测手段：为再生成次数与失败次数打点，异常堆积通常是失效粒度过粗的信号。

> [!CAUTION]
> **注意内容**：只失效页面缓存而不同步失效数据缓存，会生成一份看似更新、实际仍是旧数据的产物，比完全不更新更难排查。

**速记**：一致性取决于多层缓存的同步失效，失效窗口要能返回旧产物而不是报错。



### 流式渲染与部分预渲染

**流式渲染与部分预渲染**：是把「一次请求产出一整份 HTML」拆成可提前输出的片段的两条思路，前者控制传输方式，后者控制哪些部分在构建期就固定下来。

#### 分块传输与骨架

**流式渲染（streaming rendering）**：是服务端边渲染边把 HTML 分块写入响应的做法，浏览器收到前一块就能开始解析与绘制，不必等待整页渲染完成。

- 传输形态：响应保持打开状态，片段按渲染完成顺序依次写入。
- 绘制时机：先到达的部分先被解析，用户更早看到标题与页面骨架。
- 阻塞范围：慢数据只影响它所在片段的到达时间，不阻塞其余部分。
- 兼容方式：浏览器按常规方式解析 HTML，无需额外的客户端能力。

```html
<!-- 响应中片段的到达顺序 -->
<!-- 片段一：文档头与静态外壳 -->
<html><body><main><h1>文章标题</h1>
<!-- 片段二：慢数据占位 -->
<section id="comments">评论加载中</section>
<!-- 片段三：慢数据就绪，替换占位 -->
<script>document.getElementById("comments").textContent = "评论内容";</script>
</main></body></html>
```

- 首字节时间与整页渲染完成时间解耦，前者只取决于外壳。
- 内容到达顺序由数据快慢决定，不再由模板顺序唯一决定。
- 出错处理要按片段进行，已发送的片段无法撤回。

**分块顺序不等于视觉顺序**：片段到达后由浏览器按文档结构落位，先到达的片段未必出现在页面更靠前的位置。

- 外壳内容承担主要信息量时，提前到达的收益最明显。
- 慢数据位于首屏时，占位内容要能代表最终布局。
- 传输层已开始发送后无法改状态码，错误处理要提前到片段生成之前。

> 流式渲染改变的是内容的到达节奏，页面的最终结构与整体式渲染没有差别。

**速记**：流式渲染分块写入响应，让页面外壳与快数据先到达，慢数据后补。



#### 边界划分与等待策略

**边界**：是流式渲染中标记「这一部分可以稍后到达」的范围，边界之外的内容按正常顺序输出，边界之内的内容在数据就绪后补入。

- 划分依据：把依赖慢数据的组件单独划入边界，其余部分保持同步输出。
- 占位内容：边界内需要提供与最终结构接近的占位，减少布局跳动。
- 嵌套关系：边界可以嵌套，内层慢数据不会阻塞外层外壳的输出。
- 划分成本：边界过细会增加请求数与调度开销，过粗则失去提前输出的意义。

```tsx
import { Suspense } from "react";

export default function ArticlePage({ params }: { params: { id: string } }) {
  return (
    <article>
      <h1>文章标题</h1>
      <Suspense fallback={<p>评论加载中</p>}>
        <CommentSection id={params.id} />
      </Suspense>
    </article>
  );
}
```

```text
同步输出：标题、正文、页脚
边界之内：评论区（依赖较慢的接口）
结果：标题与正文先到达，评论区随后补入
```

- 先测量各数据源的耗时，再决定边界放在哪里。
- 占位内容的高度尽量贴近最终内容，避免内容补入后页面大幅位移。
- 边界内的组件也要有错误兜底，否则单点异常会破坏整页结构。

> [!TIP]
> **建议内容**：划分边界时优先看数据耗时分布，把明显慢于其他部分的数据单独划出，比按组件层级切分更有效。

**速记**：边界用来限定慢数据的影响范围，边界外先输出，边界内以占位过渡后再补入。



#### 部分预渲染的思路

**部分预渲染（partial prerendering，PPR）**：是把页面切分为静态外壳与动态空洞两部分的做法，静态外壳在构建期生成并可长期缓存，动态空洞在请求时渲染后填入。

- 静态外壳：与请求无关的部分在构建期固定，能被边缘缓存直接命中。
- 动态空洞：依赖请求上下文的组件留到请求时渲染，避免整页转为逐请求渲染。
- 组合效果：一个页面同时获得静态托管的速度与逐请求渲染的个性化。
- 落地状态：不同元框架对该思路的支持程度不同，部分框架仍以实验性能力提供。

```text
构建期：生成静态外壳，动态空洞处留下占位标记
请求时：取出外壳 → 渲染空洞所需组件 → 拼接后返回
缓存：外壳命中边缘缓存，只有空洞部分消耗渲染算力
```

- 判断标准：组件是否读取请求头、Cookie 或用户身份，是划分外壳与空洞的主要依据。
- 收益来源：页面上静态部分占比越高，可复用的缓存越多。
- 兼容要求：空洞的填入方式依赖流式响应，两项能力通常配套出现。

> 部分预渲染不是新增的传输机制，它把「哪些部分与请求无关」这一判断提前到了构建期。

**速记**：部分预渲染让静态外壳长期缓存、动态空洞按请求渲染，兼顾速度与个性化。



### 模式取舍与组合

**模式取舍与组合**：是把多种渲染模式放到同一个站点里各司其职，判断依据是每个页面的内容特征，而不是框架的默认值。

#### 按页面特征选模式

**按页面特征选模式**：是依据内容是否随请求变化、更新频率与首屏要求三个维度为页面选择渲染方式。

- 不随请求变化、更新极少：静态生成。
- 不随请求变化、更新有节奏：增量静态再生成。
- 随请求变化、要求首屏与可抓取：服务端渲染。
- 仅登录后可见、交互密集：客户端渲染。

```text
公开文档页          → 静态生成
商品详情页          → 静态生成 + 按需失效
新闻首页            → 增量再生成
个性化推荐页        → 服务端渲染 + 流式输出
后台管理界面        → 客户端渲染
```

- 先判断内容与请求的关系，再判断更新频率，最后判断首屏要求。
- 同一类页面在不同时段可能有不同要求，模式选择要随业务变化复核。
- 内容特征相近的页面归为一类统一处理，避免逐页配置带来的维护成本。

**判定顺序**：先把站点所有路由列出，逐条标注内容来源与更新方式，再对照模式特性落位；这一步产出的清单本身就是后续配置的依据。

> 模式属于页面而不属于框架，一个项目里出现多种模式是常态而非例外。

**速记**：内容是否随请求变化定大方向，更新频率定再生成方式，首屏要求定是否需要流式。



#### 混合渲染与逐页配置

**混合渲染**：是在同一个应用中按路由分别声明渲染方式的做法，各页面独立配置，互不影响。

- 配置粒度：以页面或路由段为单位声明，公共布局取其中更动态的一种。
- 边界清晰：列表页静态、详情页按需更新、账户页客户端渲染，可以并存。
- 缓存继承：布局与页面各有缓存策略，嵌套时以内层更具体者为准。
- 迁移便利：改造既有项目时可以逐页切换，不必一次性重写。

```ts
// 逐页声明渲染方式：页面级配置覆盖上层默认值
export const dynamic = "force-static"; // 该页面在构建期生成
export const revalidate = 300;         // 并在 300 秒后允许后台再生成

export default async function DocsPage() {
  const docs = await getDocList();
  return <DocList docs={docs} />;
}
```

- 配置只影响所在路由段及其子路由，不会改变其他页面。
- 页面与其数据来源的缓存策略要一致，否则会出现内容与数据不匹配。
- 上线的配置组合应有明确注释，避免后续维护者误删。
- 公共布局引入动态能力时，会向上污染原本可静态化的子页面。

> [!WARNING]
> **警告内容**：逐页配置分散在多个文件中时容易失去整体视图，应维护一份渲染方式清单，标明每个路由的模式与依据。

**速记**：混合渲染按路由声明模式，逐页可控、便于迁移，但要维护一份整体清单。



#### 迁移路线与验证方法

**迁移路线与验证方法**：是把既有页面从一种模式迁到另一种模式时的推进顺序与验证手段，核心是先度量再改动。

- 第一步度量：记录当前首字节时间、可绘制时刻与抓取结果，作为对照基线。
- 第二步试点：选一个内容特征典型、流量适中的页面先行改造。
- 第三步推广：按页面类型分批推进，每批观察服务端负载与缓存命中率。
- 第四步复核：改造后重新采集同一组指标，与基线对比确认收益。

```bash
# 构建后逐页检查产物形态，确认哪些页面被静态化
npm run build
# ● /docs/1        静态生成
# ● /products/1    静态生成 + 再生成间隔 300 s
# ƒ /dashboard     按请求渲染
```

```text
验证清单：首字节时间、可绘制时刻、缓存命中率、服务端每秒请求数、页面内容正确性
```

- 产物标记可直接反映每个路由最终采用的渲染方式，是最快的核对入口。
- 迁移后若首字节变慢，优先检查服务端取数是否串行。
- 缓存命中率下降往往说明失效范围过大或缓存键设计过细。
- 每次只改一个变量，便于把指标变化归因到具体的改动上。

> 迁移的目标是让每个页面落在合适的模式上，而不是把所有页面统一到同一种模式。

**速记**：迁移先度量基线、再试点分批推进，用产物标记与指标对比验证收益。
