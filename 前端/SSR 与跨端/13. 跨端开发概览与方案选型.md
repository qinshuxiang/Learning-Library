## 跨端开发概览与方案选型

**跨端（cross-platform）**：是用一套代码基础产出多个运行端形态的开发方式，端包括 Web、微信小程序、支付宝小程序、iOS、Android 与桌面端。本篇回答四件事：跨端要解决什么问题、技术路线如何分类、主流方案各自的能力边界、按什么依据做选型。

本篇只做路线分类与取舍判断，不写任何框架的代码；具体框架的项目结构与构建细节，从本主题第 17 篇 uni-app 跨端开发开始逐篇展开。

### 跨端要解决什么问题

**跨端要解决的问题**：是在运行端数量增长时，抑制重复开发带来的成本上升与端间体验偏差。

#### 多端的成本结构

**多端的成本结构**：是同一业务功能在每个运行端上都要重复投入的研发、测试与维护工作量，端越多，重复投入越大。

- 研发重复：同一页面在 Web、iOS、Android 各实现一遍，业务逻辑与样式无法直接复用。
- 测试重复：兼容性验证、回归测试与发布验收要在每个端单独走一遍。
- 维护重复：需求变更要在多套代码中同步落地，漏改一处即产生端间体验差异。
- 协作重复：各端由不同技术栈的团队负责时，接口联调与排期对齐的成本进一步上升。

```text
多端并行开发的典型结构

Web 团队      --> Web 产物
iOS 团队      --> iOS 产物
Android 团队  --> Android 产物
小程序团队    --> 小程序产物
共享资产：接口协议、设计稿、需求文档、埋点口径
```

> 判断是否需要跨端，先看重复度：当同一功能在三个以上端重复实现时，跨端的收益才开始显著。

**速记**：端越多，重复的研发、测试与维护成本越高。



#### 一套代码与多套代码的取舍

**一套代码与多套代码的取舍**：是在复用率与端原生体验之间寻找平衡点，而不是在「全部复用」与「全部重写」之间二选一。

- 全量复用：复用率最高，但共享层要同时满足所有端的约束，能力上限被限制在最弱的一端。
- 分层复用：把纯逻辑、数据访问与视图拆开，纯逻辑完全共享，视图按端分别实现。
- 全量重写：每端体验最好，但成本随端数线性增长，只适合端差异极大的产品。
- 现实选择：多数项目采用分层复用，共享比例取决于各端相似程度。

```text
分层复用的边界划分

共享层    业务逻辑、状态管理、接口封装、工具函数、类型定义
分端层    页面结构、样式实现、平台专有能力的调用
桥接层    WebView 与原生、逻辑层与渲染层之间的通信适配
```

> 取舍的核心问题是「哪些代码与端无关」；判断标准是这段代码是否依赖渲染机制、平台接口或设备能力。

**速记**：复用的关键是把与端无关的逻辑抽出来，视图按端分别实现。



#### 跨端的收益与代价

**跨端的收益与代价**：是复用带来的效率提升，与抽象层引入的约束和排错难度之间的一笔总账。

- 收益项：需求一次实现、多端生效，发布节奏可以对齐，人力从重复实现转向端特有体验。
- 代价项：跨端抽象会遮蔽平台差异，问题定位需要同时理解框架层与平台层。
- 代价项：框架能力滞后于平台新特性，新能力往往要等框架适配之后才能使用。
- 代价项：极端性能场景受限于抽象层实现，可能仍需回落到底层写法。

```text
跨端方案的成本曲线

端数量增加  --> 多套代码的总成本线性上升
端数量增加  --> 跨端的总成本近似持平，但初始化成本较高
两条曲线的交点取决于：端数量、端差异程度、框架成熟度
```

> [!WARNING]
> **警告内容**：跨端不是零成本方案，抽象层引入的约束会在性能敏感与平台特性密集的场景中集中暴露，评估时必须一并计入。

**速记**：跨端把重复成本换成抽象成本，端越多收益越明显。



#### 端差异的来源

**端差异的来源**：是渲染机制、平台能力、分发方式与更新机制四个层面上的不一致，跨端方案必须为每一层给出适配策略。

- 渲染机制：浏览器引擎、宿主渲染层与原生绘制对同一布局的呈现方式不同。
- 平台能力：文件系统、通知、支付、设备传感器等接口的开放程度因端而异。
- 分发方式：Web 靠地址分发，小程序靠宿主平台分发，原生应用靠应用商店分发。
- 更新机制：Web 发布即生效，小程序与应用需要经过平台审核，存在生效延迟。

```text
端差异的四个层面与应对

渲染机制  --> 样式与布局的适配层
平台能力  --> 统一接口封装与降级方案
分发方式  --> 多端构建与提审流程
更新机制  --> 版本兼容与灰度策略
```

> 差异无法被消除，只能被封装；封装得越彻底，上层代码就越接近「与端无关」。

**速记**：端差异来自渲染、能力、分发与更新四层，只能封装不能消除。



### 技术路线分类

**技术路线分类**：是按「代码在什么阶段、以什么方式变成目标端可运行形态」对跨端方案做出的划分，分为编译型、桥接型、容器型与自绘型四条主线。

#### 编译型路线

**编译型路线**：是在构建阶段把一套源码转换为各端原生语法或目标框架语法的做法，产物在目标端仍由原生机制渲染。

- 转换对象：模板标记、样式规则与组件调用在构建时被重写为目标端语法。
- 典型产物：小程序端输出模板与配置文件，原生端输出可继续编译的工程源码。
- 优点：产物接近目标端原生实现，运行时没有额外的解释层。
- 缺点：平台差异要在源码中显式处理，框架需要为每个端维护一套编译器。

```text
编译型路线的转换过程

一套源码
  --> 编译器按端拆分
      --> Web 产物：HTML、CSS、JavaScript
      --> 小程序产物：模板、样式、配置、逻辑
      --> 原生产物：可编译的工程源码
```

> 编译型路线的成熟度取决于编译器对各端语法的覆盖程度，未覆盖的写法需要降级或走平台专有通道。

**速记**：编译型在构建期转换源码，产物由目标端原生机制渲染。



#### 桥接型路线

**桥接型路线**：是在目标端内置 JavaScript 运行时，由框架把上层组件映射为原生组件，并通过桥接通道完成两侧调用。

- 渲染方式：由原生组件负责绘制，上层只描述组件树与属性。
- 通信方式：业务代码的调用经序列化后跨语言边界传递，结果再回传。
- 优点：复用主流的组件化写法，交互接近原生体验。
- 缺点：频繁跨边界的通信会带来延迟，复杂动效与长列表需要专门优化。

```text
桥接型路线的调用链

业务代码
  --> 框架运行时
      --> 序列化
          --> 原生侧组件与模块
      <-- 事件与结果回传
  <-- 视图更新
```

> [!CAUTION]
> **注意内容**：桥接通道的往返是性能瓶颈的主要来源，把高频更新合并成批量调用是这类方案的常规优化方向。

**速记**：桥接型靠原生渲染加跨语言通道，性能取决于通信频率。



#### 容器型与自绘型路线

**容器型与自绘型路线**：是把「页面运行在 WebView 容器内」与「框架自行绘制全部界面」这两类做法并列归类的合称。

- 容器型：页面本质是 Web 页面，由目标端提供 WebView 与桥接能力，开发方式与 Web 一致。
- 容器型优点：上手成本最低，既有 Web 资产可以直接迁移。
- 自绘型：框架接管渲染管线，界面由自身引擎绘制，不依赖目标端控件。
- 自绘型优点：多端表现高度一致；缺点是包体积较大，观感与系统原生控件存在差异。

```text
两类路线的渲染归属

容器型    页面 --> WebView --> 目标端渲染引擎
自绘型    页面 --> 框架渲染引擎 --> 系统图形接口
```

> 容器型方案的体验波动主要来自 WebView 的版本差异；自绘型方案的一致性由框架自身保证，与系统版本关系较小。

**速记**：容器型复用 WebView，自绘型接管渲染，一致性更强但体积更大。



#### 路线的组合使用

**路线的组合使用**：是在同一个产品中按页面性质分别选用不同路线，而不是全产品只绑一条路线。

- 组合原则：以体验要求最高的端为基准确定主路线，其余端用同一套源码产出。
- 常见组合：容器型外壳承载活动页，编译型页面承载主流程，原生模块承载设备能力。
- 边界管理：组合方案要明确各路线之间的跳转、通信与状态同步方式。
- 代价：组合会引入多套构建链路与两套调试手段，团队需要具备对应的维护能力。

```text
组合方案的分层

外壳层    容器与宿主能力，负责启动、鉴权与降级
页面层    编译型产物，承载业务主流程
扩展层    原生模块或宿主插件，承载设备与专有能力
```

> 组合的收益来自「按页面选路线」，代价是工程复杂度上升；只有当单一路线确实覆盖不了需求时才值得采用。

**速记**：组合方案按页面选路线，收益是覆盖度，代价是工程复杂度。



### 主流方案对比

**主流方案对比**：是按目标端覆盖、开发写法、能力边界与维护成本四个维度，对现实中广泛使用的几类方案做并列说明。本节不作推荐，只列特征。

#### Web 与渐进式 Web 应用

**渐进式 Web 应用（Progressive Web App，PWA）**：是在 Web 页面之上叠加可安装、离线缓存与消息推送能力，使其接近应用形态的做法。

- 覆盖端：Web 全平台，桌面端与移动端浏览器均可使用。
- 开发写法：沿用 HTML、CSS 与 JavaScript，不引入新的语言。
- 能力边界：受浏览器沙箱限制，对文件系统、蓝牙、通知等能力的开放程度因平台而异。
- 维护成本：最低，单一产物，无需应用商店分发。
- 适用场景：内容型与工具型产品，或作为原生应用的补充入口。

```text
Web 与 PWA 的能力来源

页面结构    HTML
样式        CSS
行为        JavaScript
增强能力    离线缓存、可安装清单、消息推送
```

> 在部分平台上，离线缓存与推送能力受到限制，PWA 的能力上限由目标浏览器决定。

**速记**：Web 与 PWA 覆盖最广、成本最低，能力受浏览器沙箱约束。



#### 小程序与小程序容器

**小程序（Mini Program）**：是运行在宿主应用内的轻量应用形态，由宿主提供运行环境、组件与接口，代码通过宿主平台分发，不经过应用商店。

- 覆盖端：各宿主平台各自的小程序，同一份逻辑通常需要按平台分别构建。
- 开发写法：宿主定义的模板、样式与配置语言，接口由宿主统一提供。
- 能力边界：能力由宿主开放的清单决定，用户身份、支付、分享等能力都要走宿主通道。
- 维护成本：中等，逻辑可复用，但每个宿主平台都要单独构建与提审。
- 适用场景：依托宿主流量的业务，或需要触达用户但不愿承担原生开发成本的产品。

```text
小程序方案的分层

宿主应用    提供运行环境、组件库、接口与分发渠道
小程序代码  模板、样式、配置、逻辑四类文件
平台差异    各宿主平台的能力清单与审核规则不同
```

> [!NOTE]
> **提醒内容**：小程序不等同于 Web，宿主环境不提供完整的浏览器接口，DOM 与浏览器事件模型均不可用，写法需要按宿主规范组织。

**速记**：小程序依托宿主环境与分发，逻辑可复用但需按平台分别构建。



#### 原生渲染式框架

**原生渲染式框架**：是上层用声明式写法描述界面、下层映射为目标端原生组件并自行管理渲染与通信的框架类型。

- 覆盖端：通常覆盖 iOS 与 Android，部分框架扩展到 Web 与桌面端。
- 开发写法：接近主流前端框架的组件写法，样式系统与 Web 存在差异。
- 能力边界：可通过编写原生模块扩展能力，代价是维护两套语言栈。
- 维护成本：较高，需要处理原生工程配置、依赖与各端版本兼容。
- 适用场景：需要原生体验与性能，同时希望复用业务逻辑与研发人力的产品。

```text
原生渲染式框架的组成

上层       组件描述、状态管理、样式
框架层     布局计算、渲染调度、通信桥接
原生侧     平台组件、原生模块、宿主工程
```

> 这类框架的收益集中在业务逻辑与组件组织的复用，最终体验仍取决于原生组件能力与框架映射的完整度。

**速记**：原生渲染式框架复用上层写法、落地为原生组件，性能与维护成本都更高。



#### 方案对比的常见误区

**方案对比的常见误区**：是把「代码能跑起来」当作「方案可长期使用」，忽略能力边界与维护成本这两项隐性支出。

- 误区一：认为跨端等于零成本，忽略抽象层带来的约束与排错难度。
- 误区二：认为 Web 资产可以直接搬进宿主环境，忽略 DOM 与浏览器接口的缺失。
- 误区三：只看首版开发速度，不评估构建链路与依赖升级的长期投入。
- 误区四：用单一端的体验标准推断全部端，忽略各端能力清单的差异。
- 纠偏方式：把能力边界、维护成本与退出成本与前四项放在同一张评估清单里比较。

```text
评估清单的六个维度

目标端覆盖    是否满足必须覆盖的端
开发写法      团队是否熟悉
能力边界      平台特性是否可落地
性能表现      是否满足产品的体验下限
维护成本      构建、升级与回归的常态投入
退出成本      方案被替换时的迁移难度
```

> 误区多数来自评估维度的缺项，而不是对某个方案的判断失误；补齐维度比挑选方案更重要。

**速记**：对比方案要补齐能力、维护与退出成本，别用首版速度代替长期判断。



### 选型依据

**选型依据**：是把产品目标、团队条件与长期成本折算成可比较的判断项，再据此匹配技术路线。

#### 目标端清单与优先级

**目标端清单与优先级**：是先列出必须覆盖的端与可选端，再按业务权重排序，作为筛选方案的第一道条件。

- 必须覆盖：缺失即无法交付的端，直接决定方案的可选范围。
- 体验下限：对每个端能接受的体验水平做底线约定，避免用最弱端的标准约束全部端。
- 增量端：未来可能新增的端，决定方案是否需要保留扩展能力。
- 排序结果：把端清单转换成筛选条件，先淘汰覆盖不全的方案。

```text
端清单的筛选方式

必须覆盖：Web、微信小程序、iOS、Android
体验下限：交互流畅、首屏可用
增量端：桌面端（次要）
筛选结果：只保留能同时产出四端的路线
```

> 端清单是硬条件，其余维度是软条件；硬条件不满足的方案不再进入后续比较。

**速记**：先定必须覆盖的端，再用它淘汰覆盖不全的方案。



#### 团队技术栈与生态成熟度

**团队技术栈与生态成熟度**：是团队既有的语言与框架经验，以及候选方案在组件库、工具链与社区支持上的可用程度。

- 技术栈匹配：与团队既有写法越接近，上手与协作成本越低。
- 生态完备：组件库、调试工具、脚手架与第三方库的覆盖程度决定开发效率。
- 问题可解：遇到平台差异与疑难问题时，是否有稳定的资料与社区支持。
- 演进活跃：方案的维护活跃度影响长期可用性，需要观察版本迭代与问题响应。

```text
生态成熟度的四个观察点

组件库      常用业务组件是否齐备
工具链      构建、调试、发布是否配套
社区        疑难问题是否有稳定解法
迭代节奏    版本更新与问题响应是否持续
```

> 生态成熟度是长期成本的主要变量：写出第一版不难，难的是三年后仍能升级与排错。

**速记**：选方案先看团队能否驾驭，再看生态能否长期支撑。



#### 能力边界与长期维护成本

**能力边界与长期维护成本**：是方案在当前与未来能覆盖的功能范围，以及维持这套代码所需的持续投入。

- 能力边界：平台专有能力能否通过扩展或降级方案落地，是可行性的关键。
- 性能边界：高频交互、长列表与复杂动效能否达到产品要求。
- 维护成本：构建链路、依赖升级与多端回归测试的常态化投入。
- 退出成本：方案被替换时，既有代码与工程配置能否平滑迁移。

```text
成本随时间的分布

首版开发    复用率决定投入，通常显著低于多套代码
功能迭代    与端相关的改动仍需按端验证
依赖升级    框架与原生工程的版本兼容成本
```

**速记**：能覆盖能力边界且维护成本可承受，才是可长期使用的方案。



#### 选型决策的记录与复盘

**选型决策的记录与复盘**：是把选型时的假设、验证指标与退出条件写下来，供后续按事实校正判断。

- 记录假设：写明当时认为的目标端、团队条件与能力边界。
- 验证指标：约定用哪些可观测的指标判断方案是否达标，如首屏表现与构建时长。
- 退出条件：提前约定在什么情况下更换方案，避免沉没成本拖延决策。
- 定期复盘：在新端接入或平台大版本更新后回看记录，校正原有假设。

```text
选型决策记录的要素

背景        产品目标、目标端清单、时间约束
候选方案    进入评估的方案与淘汰原因
关键假设    关于团队、生态与能力边界的判断
验证指标    上线后可用于校验的具体指标
退出条件    触发更换方案的情形
```

> 记录的价值在于把「当时为什么这么选」留下来，避免后续用结果倒推过程。

**速记**：把假设、指标与退出条件记录下来，选型才能被验证与修正。
