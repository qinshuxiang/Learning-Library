## SSR 与跨端概览

**SSR 与跨端**：是前端工程向外延伸的两条主线，**服务端渲染（server-side rendering，SSR）** 让 HTML 在服务端生成后直出给浏览器，**跨端（cross-platform）** 让一套业务代码产出 Web、小程序与原生等多个运行端的形态。

本系列共 22 篇，按「渲染模式的地图 → 同构与元框架实践 → 跨端与多端落地」三段推进。本篇回答四件事：这个系列要解决什么问题、渲染模式有哪些、跨端有哪些技术路线、这些篇目按什么顺序读。

### 本系列要解决什么问题

**本系列要解决的问题**：是在单页应用成为主流之后，如何让内容更快到达用户、更容易被搜索引擎获取，以及如何用一份代码同时交付多个运行端。

#### 首屏与可被抓取的困境

**首屏（first screen）**：是用户在一次页面访问中，视口内出现的首批可见内容，其到达时刻取决于浏览器从收到响应到完成首次绘制所经历的全部工作。

- 空壳文档：由浏览器端脚本执行后才填充内容的应用，服务端返回的文档往往只有一个挂载节点。
- 串行等待：浏览器必须先下载并执行 JavaScript，再发起数据请求，最后才渲染，链路被整体拉长。
- 抓取受限：只执行少量脚本或不执行脚本的抓取程序，可能拿不到正文，索引质量随之下降。

```html
<!-- 客户端渲染应用返回的初始文档：正文为空 -->
<main id="root"></main>
<script src="/assets/app.js"></script>
```

**两个子问题**：可被抓取性关乎正文是否出现在初始 HTML 中，首屏速度关乎这份 HTML 到达并完成绘制所需的时间，二者可以独立改善，也可以同时改善。

- 只优化首屏：用骨架屏与资源预加载缩短等待，初始 HTML 仍可能不含正文。
- 只优化抓取：服务端直出正文，浏览器侧仍要等脚本加载后才能交互。
- 同时优化：服务端直出正文，并对脚本与数据做预加载，这是服务端渲染的主要目标。

```text
骨架到达 → 脚本下载 → 脚本执行 → 数据请求 → 内容渲染
```

> 首屏与可抓取性是两件事：前者是时间问题，后者是内容可见性问题。服务端渲染能同时缓解二者，但不是唯一手段，详见本主题第 6 篇 SEO 与首屏性能。

**速记**：空壳文档把渲染成本全部推给浏览器，首屏被拖长，正文也可能抓不到。



#### 一套代码与多个端的成本

**跨端（cross-platform）**：是用一套源码，经编译或运行时适配，产出多个运行端可执行形态的做法；目标不是让代码完全相同，而是共享大部分业务逻辑。

- 端的分裂：同一业务常常要同时交付 Web、微信小程序、支付宝小程序、iOS、Android 与桌面端。
- 重复实现：各端独立开发会带来多份业务逻辑、多套状态管理与多轮回归测试。
- 收益与代价：跨端降低重复劳动，但引入抽象层，个别平台能力与极致的性能仍要回到原生实现。

```text
共享层：业务逻辑 / 状态 / 数据模型 / 请求封装
适配层：组件映射 / 样式转换 / 平台接口差异
运行端：Web、微信小程序、支付宝小程序、iOS、Android、桌面端
```

**共享的边界**：跨端框架共享的是与平台无关的部分，包括业务规则、数据模型、状态管理与请求封装；与平台强相关的部分，包括导航、支付、推送与文件系统，通常要按端分别实现。

- 平台无关：纯函数、数据转换、校验规则与状态机。
- 平台相关：界面控件、路由跳转、系统权限与硬件能力。
- 判断方法：在不引入任何平台接口的前提下能运行的代码，才适合放进共享层。

> 跨端不是「一套代码跑遍所有端」，而是把可共享的部分抽出来，把不可共享的部分收敛到少量适配代码里。

**速记**：跨端共享业务逻辑而非全部代码，抽象层换来效率，也换来适配成本。

**本系列的定位**：是讲清「页面在哪个环节被生成为内容」与「一份代码如何适配多个端」这两组机制与工程取舍，不承担语言与框架基础的教学。

- 上游依赖：JavaScript 语言基础、类型标注、React 与 Vue3 的组件模型属于其他主题，本系列只在需要处简要衔接。
- 下游输出：元框架的配置、数据获取、部署与多端发布，在本系列内按框架与流程分篇展开。
- 判断标准：读完前六篇应能判断一个页面该选哪种渲染模式，读完跨端部分应能判断该选哪条技术路线。

**三条主线**：渲染模式回答内容在哪里生成，同构与水合回答两端如何协作，跨端回答一份代码如何落到多个端；三条主线各有独立的判断标准，可以分开学习。

- 选模式：看内容的变化频率与首屏要求。
- 看机制：看服务端产出什么、客户端接管什么。
- 定路线：看目标端清单与性能下限。

> [!IMPORTANT]
> **重要内容**：渲染模式与跨端路线都随框架版本演进，本系列给出的是机制与取舍依据；具体配置字段以所使用版本的官方文档为准。

**速记**：本系列讲机制与选型，语言与框架基础归其他主题。



### 渲染模式的谱系

**渲染模式的谱系**：是一组按「内容在何时、何地被生成为 HTML」划分的连续区间，从请求时服务端生成，到构建时静态生成，再到浏览器端生成，彼此并非对立选项。

#### 从静态页面到客户端渲染

**客户端渲染（client-side rendering，CSR）**：是浏览器下载并执行 JavaScript 后由脚本生成页面结构并填充内容的渲染模式，服务端只返回一个几乎不含内容的文档骨架。

**静态页面**：是内容在编写或构建阶段就已写进 HTML 的形态，服务端只需读出文件返回，不执行任何组件渲染。

- 静态页面：内容固定，改一次要重新发布一次。
- 客户端渲染：内容在浏览器生成，页面退化为「骨架加脚本」。
- 变化动因：交互复杂度上升，同一份 HTML 无法承载所有人的个性化内容。

```html
<!-- 静态页面：正文直接写在文档里 -->
<article>
  <h1>文章标题</h1>
  <p>正文内容</p>
</article>
```

- 生成时机：客户端渲染的内容在浏览器运行时生成，服务端不参与页面内容拼装。
- 资源形态：HTML 为固定骨架，内容依赖脚本与接口请求。
- 典型收益：页面切换无需整页刷新，路由与交互由前端接管。
- 代价：首屏依赖脚本下载与执行，正文对不执行脚本的抓取程序不可见。

```js
// 浏览器端挂载后请求数据并渲染列表
const list = document.querySelector("#article-list");

async function renderArticleList() {
  const response = await fetch("/api/articles");
  const articles = await response.json();
  list.innerHTML = articles.map((item) => item.title).join("");
}

renderArticleList(); // 首屏内容在脚本执行后才出现
```

> 客户端渲染是单页应用（single page application，SPA）的默认形态，它把渲染责任整体交给了浏览器。

**速记**：客户端渲染在浏览器里生成内容，交互灵活，首屏与可抓取性都依赖脚本执行。



#### 服务端渲染与同构渲染

**服务端渲染（server-side rendering，SSR）**：是在收到请求时由服务端把组件渲染成 HTML 字符串并直接返回的渲染模式，浏览器拿到的是已经含有内容的文档。

**同构渲染（isomorphic rendering）**：是同一份组件代码既能在服务端渲染成 HTML、又能在浏览器接管交互的做法，服务端与客户端共享组件与路由定义。

- 首屏直出：响应体已含内容，浏览器无需等待脚本即可绘制首屏。
- 客户端接管：脚本加载完成后在既有 DOM 上附加事件与状态，这一步称为水合（hydration）。
- 数据流：服务端取数并随 HTML 一并下发，浏览器不必再发起首轮数据请求。
- 适用范围：内容随请求变化、又要求首屏速度与可抓取性的页面。

```html
<!-- 服务端渲染返回的文档：正文已在响应体中 -->
<article>
  <h1>文章标题</h1>
  <p>正文内容</p>
</article>
```

用命令行取回页面即可验证两种模式的差别：服务端渲染的响应体含正文，客户端渲染的响应体只有骨架。

```bash
curl -s https://example.com/articles/1 | head -n 3
# 输出中直接包含文章标题与正文
```

```tsx
// 同一组件在服务端与客户端被引用
type Article = { id: number; title: string };

export function ArticleList({ articles }: { articles: Article[] }) {
  return (
    <ul>
      {articles.map((item) => (
        <li key={item.id}>{item.title}</li>
      ))}
    </ul>
  );
}
```

> [!NOTE]
> **提醒内容**：服务端渲染只保证首屏 HTML 含有内容，交互能力仍要等脚本加载并完成水合，二者是两个阶段。

**速记**：服务端渲染首屏直出 HTML，同构渲染让同一份组件在两端复用，交互靠水合恢复。



#### 静态生成与增量再生成

**静态站点生成（static site generation，SSG）**：是在构建阶段把页面预渲染为静态 HTML 的做法，请求到来时直接返回已生成的产物，不经过运行时的服务端渲染。

**增量静态再生成（incremental static regeneration，ISR）**：是在静态生成的基础上，允许页面在部署后按时间间隔或事件重新生成，兼顾静态产物的速度与内容的更新。

- 生成时机：静态生成发生在构建期，产物可放到内容分发网络，命中缓存时无需回源。
- 适用内容：文档、博客、营销页等不随请求变化或变化缓慢的页面。
- 更新方式：原始形态下内容变更需重新构建，增量再生成把这一步推迟到运行时按需触发。
- 关键取舍：构建时间与内容新鲜度之间存在矛盾，增量再生成用来折中。

```js
// 页面在构建阶段预渲染，产物可直接由静态服务器返回
export async function getArticles() {
  const response = await fetch("https://example.com/api/articles");
  return response.json();
}

console.log("build time pre-render"); // 该调用发生在构建阶段
```

- 全量静态：所有页面在构建时一次生成，构建时长随页面数线性增长。
- 按需生成：首次访问某个页面时才生成，生成结果随后缓存复用。
- 失效更新：已达到再生成间隔的页面在后台重新生成，旧产物继续服务直至新产物就绪。

> 静态生成把服务端渲染的成本前移到构建期，代价是内容更新不再实时。

**速记**：静态生成在构建期产出 HTML，增量再生成让静态页在部署后按需更新。



#### 流式渲染与部分预渲染

**流式渲染（streaming rendering）**：是服务端边渲染边把 HTML 分块发送给浏览器的做法，浏览器可以先显示已到达的部分，不必等待整页生成完毕。

**部分预渲染（partial prerendering，PPR）**：是把页面的静态外壳与依赖请求的动态部分分开处理的做法，静态部分预先渲染并缓存，动态部分在请求时补入。

- 传输方式：响应以分块形式持续输出，先到达的片段先被绘制。
- 等待策略：慢数据被隔离在边界之内，不阻塞整页的首字节到达时间。
- 组合方式：静态外壳复用缓存，动态部分单独渲染后替换占位内容。
- 适用场景：页面中存在明显快慢差异的数据块，或希望更早显示骨架与关键内容。

```html
<!-- 响应分块到达的顺序示意 -->
<!-- 第 1 块：静态外壳先输出 -->
<html><body><article><h1>文章标题</h1>
<!-- 第 2 块：占位内容先替换骨架 -->
<p>评论加载中</p>
<!-- 第 3 块：慢数据就绪后补入 -->
<section>评论内容</section></article></body></html>
```

- 首字节更早：只要外壳可输出，浏览器就能开始解析与绘制。
- 感知更快：用户先看到标题与骨架，数据到位后再替换局部。
- 实现成本：页面需要按数据快慢切分边界，切分不当反而增加请求数。

> [!TIP]
> **建议内容**：页面首字节时间被最慢数据拖住时，优先用流式渲染把慢数据隔离到边界内，而不是让整页一起等待。

**速记**：流式渲染分块输出 HTML，部分预渲染把静态外壳与动态部分拆开处理。



### 跨端的技术路线

**跨端的技术路线**：是按「最终以什么形态运行在各端」划分的几条路径，包括复用网页渲染引擎、复用原生控件、把一套源码编译到各端自有语法等；路线不同，性能上限与适配成本也不同。

#### Web 与原生的取舍

**Web 渲染与原生渲染**：是跨端最上层的两种呈现方式，前者用浏览器或网页视图承载界面，后者调用操作系统提供的原生控件绘制界面。

- Web 渲染：界面由 HTML 与 CSS 描述，跨端一致性好，长列表与复杂手势的性能上限受网页视图限制。
- 原生渲染：界面由原生控件绘制，滚动与动画更接近系统体验，但不同平台的控件与样式需要分别适配。
- 折中方案：小程序与部分框架采用自绘或半自绘引擎，在两种方式之间取平衡。
- 判断依据：交付速度优先选 Web 渲染，体验与性能优先选原生渲染或混合方案。

```text
Web 渲染：HTML / CSS → 网页视图 → 各端一致的界面
原生渲染：组件树 → 原生控件 → 各端各自的界面
折中方案：组件树 → 自绘引擎 / 半自绘引擎 → 接近原生的界面
```

界面之外还有一层差异：Web 渲染能直接使用浏览器的调试工具与开发习惯，原生渲染则要依赖平台提供的构建与调试链路，团队上手成本随之变化。二者的代码组织方式也不同，前者贴近网页的文档结构，后者贴近平台的控件树。

- 调试体验：网页视图可用浏览器开发者工具，原生渲染要看平台日志与调试器。
- 样式能力：网页视图的样式表达力完整，原生渲染只支持各平台控件支持的样式子集。
- 迁移成本：已有网页资产的团队偏向 Web 渲染，已有客户端团队的偏向原生渲染。

> 取舍的核心不是「哪种更好」，而是业务能接受多长的适配周期、多高的性能下限。

**速记**：Web 渲染换一致性与速度，原生渲染换体验与性能，折中方案介于两者之间。



#### 编译型与解释型跨端

**编译型跨端**：是在构建阶段把一套源码转换为各端各自的语法或产物，运行端执行的是转换后的代码，例如把统一组件编译为小程序模板或原生组件调用。

**解释型跨端**：是运行端加载统一的运行时与业务代码，由运行时在端内解释执行并映射为平台能力，业务代码不经过逐端编译。

- 编译型：产物贴近各端原生写法，启动路径短，但每个端要维护独立的构建目标。
- 解释型：一套产物加运行时即可运行，新增端成本低，但运行时本身带来体积与性能开销。
- 混合做法：编译与运行时并用，公共能力在构建期定形，动态能力交由运行时处理。
- 选型依据：端数量多且差异大时偏向解释型，追求极致启动速度与包体积时偏向编译型。

```json
{
  "targets": ["web", "weapp", "alipay", "ios", "android"],
  "compileMode": "per-target",
  "shared": ["business", "state", "request"]
}
```

```text
编译型：源码 → 构建 → 各端产物 → 运行端直接执行
解释型：源码 + 运行时 → 运行端加载 → 运行时解释执行
```

判断一条路线偏向哪一侧，可以看构建产物的形态：产物中出现各端特有的模板或控件调用，属于编译型；产物中只有一段通用代码外加一个体积可观的运行时，属于解释型。两者常在同一条流水线里共存，构建阶段负责静态差异，运行时负责动态差异。

> 编译型与解释型不是互斥的标签，不少框架同时使用两种手段，只是侧重点不同。

**速记**：编译型把源码翻成各端产物，解释型用统一运行时在端内执行。



#### 小程序容器与生态约束

**小程序（Mini Program）**：是运行在宿主应用内的应用形态，页面由宿主提供的渲染容器绘制，系统能力通过宿主开放的接口调用。

**双线程模型（dual-thread model）**：是小程序把逻辑层与视图层分到两个线程执行的运行机制，两层之间通过消息通信。

- 运行环境：逻辑层执行脚本与业务逻辑，视图层负责渲染，二者不共享内存。
- 通信代价：跨线程通信存在开销，高频同步通信会拖慢交互响应。
- 生态约束：代码包体积、可调用接口与审核规范均由宿主平台规定。
- 跨端影响：面向小程序做跨端时，需把能力差异收敛到适配层，不能假设浏览器接口全部可用。

```json
{
  "pages": ["pages/index/index", "pages/detail/detail"],
  "window": {
    "navigationBarTitleText": "示例"
  }
}
```

小程序路线与其他跨端路线最大的不同在于发布环节：代码要提交到宿主平台审核通过后才能对用户生效，紧急修复无法立即上线，这一点会反过来影响技术选型与发布节奏。

- 审核周期：发布依赖平台审核，灰度与回滚手段比自建应用受限。
- 包体上限：主包与分包有体积约束，静态资源多时要改用网络加载。
- 能力边界：部分系统能力需要用户授权或平台开通，未开通时要有降级路径。

> [!CAUTION]
> **注意内容**：小程序的逻辑层与视图层不共享内存，把依赖共享内存状态的库直接搬入小程序，容易出现难以定位的行为差异。

**速记**：小程序跑在宿主容器内，逻辑与视图分属两个线程，能力与包体受平台约束。



#### 路线的适用条件

**路线的适用条件**：是判断某条跨端路线是否匹配当前团队与业务的依据，取决于目标端清单、性能要求、迭代节奏与团队技术栈四方面。

- 目标端：只需覆盖 Web 与小程序时，编译型多端框架足够；需同时覆盖原生应用时，要考虑原生渲染路线。
- 性能要求：长列表、复杂动画、重度交互对渲染路线更敏感，应先在关键场景上验证。
- 迭代节奏：发布频率高、需要脱离商店审核更新时，运行时解释的方案更灵活。
- 团队栈：团队已有的框架经验直接决定迁移成本，跨端框架应尽量贴近既有写法。

```text
需要覆盖 Web + 小程序               → 编译型多端框架
需要覆盖 Web + 小程序 + 原生应用     → 原生渲染框架 + 多端框架组合
仅需覆盖原生应用                     → 原生渲染框架
```

```ts
// 选型时可先用一张评分表对齐团队认知
type RouteScore = {
  targetCoverage: number;  // 目标端覆盖程度
  performanceHeadroom: number; // 性能余量
  iterationSpeed: number;  // 迭代与发布效率
  teamFamiliarity: number; // 团队熟悉度
};

function pickRoute(scores: RouteScore[]): number {
  return scores
    .map((item, index) => ({ index, total: Object.values(item).reduce((a, b) => a + b, 0) }))
    .sort((a, b) => b.total - a.total)[0].index;
}
```

选型结论应写成可复核的依据，而不是一句「效果更好」：哪几个端、每个端的关键场景、可接受的性能下限、发布节奏与维护人力，这些条件发生变化时，结论也应重新评估。

> [!WARNING]
> **警告内容**：先按热度选定跨端框架、再回头确认目标端与性能要求，通常会在后期因个别端不适配而返工，选型应从端清单与性能下限出发。

**速记**：端清单定路线，性能定渲染方式，迭代节奏与团队栈定框架。



### 本系列结构与学习路径

**本系列共 22 篇**，按「渲染模式与同构原理 → 元框架实践 → 跨端与多端落地」三段推进。本节给出分段、重点与建议顺序，便于按需跳读。

#### 篇目分段

- 原理段（第 1 篇至第 6 篇）：SSR 与跨端概览、客户端渲染与服务端渲染、渲染模式全景、同构渲染原理、水合机制与常见问题、SEO 与首屏性能。
- 框架段（第 7 篇至第 12 篇）：Next.js 入门、Next.js 数据获取与缓存、Next.js 进阶的服务端组件与流式渲染、Next.js 工程实践与部署、Nuxt 入门与实践、SSR 应用的鉴权状态与安全。
- 跨端段（第 13 篇至第 21 篇）：跨端开发概览与方案选型、小程序基础与开发与进阶、uni-app 跨端开发、Taro 跨端开发、React Native 与原生跨端、多端适配、跨端工程化调试与发布。
- 收束（第 22 篇）：参考资料与延伸阅读。

- 原理段不依赖任何框架，讲的是可迁移的机制。
- 框架段以一个元框架为主线，另一套作对照。
- 跨端段从小程序讲到跨端框架，再到多端适配与发布。
- 收束篇只列资料与方向，不再引入新概念。

> 原理段是后两段的地基；框架段与跨端段彼此独立，可按需分别阅读。

**速记**：22 篇分三段，1 至 6 讲原理，7 至 12 讲元框架，13 至 21 讲跨端。



#### 各阶段的学习重点

- 原理段：搞清楚内容在哪个环节被生成，理解服务端渲染与水合的先后关系，能判断某类页面该选哪种模式。
- 框架段：掌握文件路由约定、服务端取数与缓存、服务端组件与客户端组件的边界，并能把项目部署到合适的运行时。
- 跨端段：理解双线程、编译与运行时的差异，能按端清单选出路线，并处理多端适配与发布流程。

原理段的知识几乎不随框架版本变化，值得一次学透；框架段与跨端段的细节与工具链绑定紧密，更适合在项目中边用边查。学习重点因此也不同：前者重理解，后者重能落地。

- 重理解：能用一组问题判断页面该用哪种渲染模式。
- 重排查：能根据报错定位到水合、取数还是缓存环节。
- 重落地：能走完从本地开发到多端发布的完整链路。

> 原理段知识密度最高，建议顺序推进；框架段中 Next.js 与 Nuxt 二选一深入即可，另一套作对照阅读。

**速记**：原理段建立判断力，框架段建立实现力，跨端段建立选型与适配力。
