## SSR 应用的鉴权、状态与安全

### 会话与鉴权在双端的分工

本节确立一条总原则：判定在服务端，呈现在客户端。围绕这条原则，会话用什么承载、令牌怎么校验、路由如何保护分别展开。

#### 鉴权判定的责任划分

**鉴权分工**：是把「谁能访问什么」的判定放在服务端、把「界面如何响应」的表现放在客户端的分工方式，判定本身不依赖任何客户端代码。

- 服务端判定：在渲染层与接口层完成身份与权限校验，未通过即返回对应状态。
- 客户端表现：按下发状态显示登录入口或隐藏操作，只改变呈现，不构成保护。
- 双端差异：客户端代码可被查看与修改，把放行条件写在客户端等同于公开条件。
- 单次判定：同一请求内只判定一次，结果沿请求向下传递，避免重复计算。

```ts
// 服务端读取会话并判定，未通过即中止后续渲染
export async function requireUser(request: Request) {
  const cookie = request.headers.get("cookie");
  const user = await verifySession(cookie);
  if (!user) {
    throw new Error("unauthorized"); // 上层据此返回登录页或未授权状态
  }
  return user;
}
```

> 判定结果在请求内是一次性事实：渲染层已经确认过身份，下层函数不必再查一遍，重复查询只会增加首屏耗时。

**速记**：鉴权判定只放服务端，客户端只负责呈现，隐藏界面不等于保护数据。



#### 基于 Cookie 的会话

**Cookie 会话**：是把会话标识放在 Cookie 中随请求自动携带的机制，服务端据此还原用户身份，是服务端渲染场景最常用的会话载体。

- 只放标识：Cookie 中只存不可猜测的随机标识，用户信息留在服务端。
- HttpOnly：禁止脚本读取该 Cookie，切断脚本窃取会话标识的一条路径。
- Secure 与 SameSite：限定只在安全连接上发送，并限制跨站请求时是否携带。
- 服务端写入：三个属性在服务端写响应头时一并声明。

```ts
// Node 服务端脚本：登录成功后写会话 Cookie
function setSessionCookie(headers: Headers, sessionId: string) {
  headers.append(
    "Set-Cookie",
    `session=${sessionId}; HttpOnly; Secure; SameSite=Lax; Path=/`,
  );
}
```

> 会话标识必须足够随机且可服务端撤销；自增编号或可预测值会让伪造会话变得容易。

**速记**：会话 Cookie 只存随机标识，HttpOnly 与 Secure 与 SameSite 三属性在服务端写入。



#### 令牌与服务端校验

**令牌校验**：是把签名凭证交给服务端逐次验证的鉴权方式，与 Cookie 会话的差别在于身份信息随令牌传递，而不是存在服务端。

- 存储位置：放 HttpOnly Cookie 中可免于脚本读取，放本地存储则直接暴露给脚本。
- 逐次校验：服务端校验签名与有效期，不通过即视为未登录。
- 撤销困难：自包含令牌在有效期内难以撤销，需配合短有效期与刷新机制。
- 双端取值：客户端要展示用户名一类信息时，由服务端解析后作为首屏数据下发。

```ts
type SessionPayload = { userId: number; expiresAt: number };

export async function verifyToken(token: string): Promise<SessionPayload | null> {
  const payload = await decodeAndVerifySignature(token);
  if (!payload || payload.expiresAt < Date.now()) {
    return null;
  }
  return payload;
}
```

> 令牌放在哪里决定了它的暴露面：只要脚本能读到，一次跨站脚本就足以把长期凭证带走。

**速记**：令牌由服务端逐次校验签名与有效期，优先放 HttpOnly Cookie 而非法脚本可读处。



#### 路由保护与页面级守卫

**路由保护**：是在进入页面或接口之前统一拦截未授权访问的做法，服务端渲染场景要求在渲染之前完成，避免先渲染再跳转。

- 渲染前拦截：在请求进入页面之前判断会话，未通过即重定向（详见本主题第 10 篇 Next.js 工程实践与部署）。
- 双端执行：同构守卫在两端都会跑，判定失败时的处理必须在两端都成立。
- 直出保护：未授权时首屏就不应包含受保护数据，而不是数据到了浏览器再隐藏。
- 接口独立：页面有守卫不代表接口安全，接口必须自行校验身份与权限。

```ts
// 渲染前的统一守卫：未授权时不进入页面渲染
export async function guardRoute(request: Request) {
  const user = await getSessionUser(request);
  if (!user) {
    return { redirectTo: "/login", status: 302 };
  }
  return null;
}
```

> 页面守卫与接口校验是两条独立防线，任何一条都不能替代另一条。

**速记**：守卫在渲染前完成判定，未授权时首屏不含受保护数据，接口须独立校验。



### 服务端与客户端状态共享

本节回答三个问题：什么状态必须留在服务端、什么状态可以下发到客户端、共享时用什么载体以及为什么必须按请求隔离。

#### 什么状态必须留在服务端

**服务端状态**：是只允许存在于服务端进程、任何情况下都不随首屏下发的状态，判定标准是泄露后会不会造成越权或损失。

- 访问密钥：数据库口令、第三方服务私钥、签名用盐值。
- 判定依据：具体的权限规则与校验逻辑，暴露判定依据等于给出绕过思路。
- 会话标识本体：只经 HttpOnly Cookie 往返，不进入首屏数据。
- 原始记录：含内部字段的数据在服务端裁剪后只下发所需字段。

```ts
// 服务端只挑选需要下发的字段
export function toPublicUser(row: UserRow) {
  return { id: row.id, displayName: row.displayName };
  // 刻意不返回 email、token、internalNote
}
```

> 判定标准只有一条：这份数据被浏览器读到会不会造成损失，会就留在服务端。

**速记**：密钥、判定依据、会话标识与未经裁剪的原始记录必须留在服务端。



#### 什么状态可以下发到客户端

**可下发状态**：是渲染与交互确实需要、且泄露不造成损失的状态，下发时遵循最小必要原则。

- 展示数据：当前页面要渲染的列表与详情，本身就是给用户看的内容。
- 用户可见信息：显示名、头像地址、语言偏好。
- 界面状态：主题、侧栏展开状态、当前分页。
- 最小化：逐字段确认必要性，能算出来的不下发，能查一次的不重复下发。

```ts
type PublicUser = { id: number; displayName: string; avatarUrl: string };

export function buildViewer(row: UserRow): PublicUser {
  return { id: row.id, displayName: row.displayName, avatarUrl: row.avatarUrl };
}
```

> 下发数据的字段名与结构同时构成对外契约，改动时需按兼容性处理，不能随手增删。

**速记**：只下发渲染与交互必需且泄露无害的状态，字段以最小必要为准。



#### 单次请求隔离与模块级状态的陷阱

**请求隔离**：是每个请求拥有独立状态存储的约束，服务端进程并发处理多个请求，跨请求共享的变量即构成数据污染。

- 模块级变量：模块被首次加载后长期存活，多个请求共用其中的值。
- 典型故障：把当前用户写进模块级变量，其他请求会读到上一个用户的数据。
- 正确做法：请求级数据挂到当前请求上下文，或使用框架提供的按请求隔离的共享状态。
- 客户端差异：浏览器中一个页面实例只服务一个用户，同样的写法在客户端看不出毛病。

```ts
// 正确做法：把用户挂到按请求创建的上下文，而不是模块级变量
export function createRequestContext(user: PublicUser) {
  return { user, startedAt: Date.now() };
}

// 错误做法（已注释）：模块级变量会被并发请求互相覆盖
// let currentUser: PublicUser | null = null;
```

> [!CAUTION]
> **注意内容**：开发模式下通常只有一个人访问，模块级状态污染往往到线上并发时才暴露，代码评审应专门检查服务端模块里的可变变量。

**速记**：服务端并发处理请求，请求级数据必须按请求隔离，模块级可变变量会串数据。



#### 状态共享的载体与选型

**共享载体**：是把服务端已取到的状态交给客户端的通道，常见为序列化后的首屏数据与按请求隔离的共享状态两种。

- 首屏数据：随 HTML 一起下发，客户端接管时直接读取，不需再发一次请求。
- 共享状态：在服务端写入后序列化下发，键与初始值在两端保持一致。
- 全局状态库：用于长期业务状态，其中的内容同样会被序列化。
- 选型依据：页面渲染数据用首屏数据，请求级数据用共享状态，长期业务状态交给状态库。

```ts
export function useViewerState() {
  return useState<PublicUser | null>("viewer", () => null);
}
```

> 三种载体的区别在生命周期而不是可见性：只要被序列化，客户端就一定读得到。

**速记**：首屏数据、按请求隔离的共享状态与全局状态库是三种载体，区别在生命周期。



### 首屏数据注入与序列化

本节讨论数据如何从服务端流到客户端：注入位置是什么、能序列化什么类型、为什么必须转义，以及体积如何控制。

#### 首屏数据注入的机制

**首屏数据注入**：是服务端把渲染所用数据序列化后写进 HTML、客户端接管时读取同一份数据以避免重复请求的机制。

- 注入方式：数据以 JSON 字符串写入内联脚本，或挂在浏览器的全局对象上。
- 接管读取：客户端运行时从该位置读取并作为初始状态，界面不再闪烁。
- 框架差异：不同框架的注入位置与全局对象名各不相同，读取接口通常由框架封装。
- 一致前提：两端必须读到同一份数据，否则会出现水合不匹配（详见本主题第 5 篇 水合机制与常见问题）。

```js
// 序列化后的首屏数据随 HTML 下发，客户端接管时读取为初始状态
const initialState = globalThis.__APP_STATE__ ?? {};
```

> 注入位置属于框架约定，业务代码不应自行拼接内联脚本，手写注入最容易漏掉转义。

**速记**：首屏数据序列化后随 HTML 下发，客户端读同一份数据接管，两端必须一致。



#### 序列化的类型边界

**序列化边界**：是数据跨端传递时能否被转换与还原的类型限制，超出边界的数据会丢失或报错。

- 支持类型：字符串、数字、布尔、空值、数组与纯对象。
- 不支持类型：函数、类实例、循环引用与部分内置对象无法直接还原。
- 日期处理：日期通常被转成字符串，客户端还原时需显式解析。
- 大整数：超出安全整数范围的值序列化后丢精度，应改为字符串传递。

```ts
export function toSerializable(value: unknown): unknown {
  return JSON.parse(JSON.stringify(value));
  // 注意：日期变成字符串，undefined 与函数被静默丢弃
}
```

> [!IMPORTANT]
> **重要内容**：序列化会静默丢弃无法表达的值，函数、未定义与类实例会直接消失，接口返回前应按目标类型显式裁剪，避免下游拿到缺字段的数据。

**速记**：序列化只支持可表达的基础类型，日期转字符串、大整数丢精度、函数被丢弃。



#### 序列化与脚本注入风险

**脚本注入风险**：是序列化结果被直接写进内联脚本时，数据中的特殊字符提前闭合脚本并执行任意代码的风险。

- 危险字符：小于号、大于号、与号，以及行分隔符等脚本上下文中具有特殊意义的字符。
- 通用做法：把这些字符替换为等价的转义序列，保持 JSON 语义不变。
- 双重编码：含富文本的字段先做 HTML 转义，再参与序列化。
- 内容安全策略：用一次性随机数标记允许执行的内联脚本，其余内联脚本一律拒绝。

```ts
export function serializeForInlineScript(value: unknown): string {
  return JSON.stringify(value)
    .replace(/</g, "\\u003c")
    .replace(/>/g, "\\u003e")
    .replace(/&/g, "\\u0026");
}
```

> 转义的目的不是改变数据，而是让数据在脚本上下文中失去语法意义，读取时仍是原值。

**速记**：内联脚本中的序列化结果必须转义尖括号与与号，或改用内容安全策略的随机数标记。



#### 数据去重与体积控制

**体积控制**：是限制首屏数据大小并去掉重复内容的处理，首屏数据全部随 HTML 下发，多一份就多一份首屏成本。

- 只取所需：列表页只下发当前页所需字段，不下发整条记录。
- 去重共享：多处用到同一实体时按标识引用一次。
- 推迟加载：首屏不需要的数据改为交互后再取（详见本主题第 6 篇 SEO 与首屏性能）。
- 压缩协同：响应压缩能减小传输体积，但不改变序列化内容本身的体积上限。

```ts
// 列表页只下发渲染需要的字段
export function toListItem(row: ArticleRow) {
  return { id: row.id, title: row.title, summary: row.summary };
}
```

> [!CAUTION]
> **注意内容**：把整条数据库记录序列化下发，既暴露未使用字段，也让首屏体积随记录增大，HTML 体积会直接拖慢首屏渲染。

**速记**：首屏数据只下发所需字段、共享实体去重、非首屏数据推迟到交互后再取。



### 常见安全风险与防护

本节只覆盖服务端渲染特有的风险面：注入点从客户端前移到服务端、数据以可执行形式随 HTML 分发、渲染发生在服务端带来的凭据处理差异。通用 Web 安全通论不在本节范围。

#### 服务端渲染场景的跨站脚本

**跨站脚本（cross-site scripting，XSS）**：是把用户可控内容当作代码执行的一类注入问题，在服务端渲染中风险面更大，因为拼接发生在服务端且产物直接分发给所有访问者。

- 主要注入点：首屏数据内联脚本、服务端拼接的富文本、属性值中的用户输入。
- 放大效应：一次注入会被写进缓存或静态产物，影响之后的所有访问者。
- 防护一：默认转义，任何用户输入进入 HTML 上下文之前先转义。
- 防护二：内容安全策略限制可执行来源与内联脚本，使注入即使存在也难以执行。

```ts
export function escapeHtml(input: string): string {
  return input
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;");
}
```

> [!WARNING]
> **警告内容**：服务端拼接的 HTML 一旦被缓存或静态化，注入内容会跟随缓存分发给所有用户，排查时还需同时清理缓存与产物。

**速记**：服务端拼接是 SSR 特有的注入面，缓存会让一次注入影响全部访问者。



#### 状态注入与数据污染

**状态注入**：是攻击者控制首屏数据中的字段、让客户端接管时把恶意值当作可信初始状态使用的问题，本质是把不可信数据当成程序输入。

- 输入路径：查询参数、Cookie 与请求头都可能被回填进首屏数据。
- 污染后果：客户端把该值用于跳转、接口地址或渲染，形成二次注入。
- 防护一：首屏数据只放服务端查库得到的值，不回填请求参数。
- 防护二：客户端使用前按类型与取值范围做运行时校验，不假定数据可信。

```ts
// 错误写法（已注释）：把查询参数直接回填进下发数据
// const state = { next: request.nextUrl.searchParams.get("next") };

// 正确写法：只下发服务端确定过的值
const state = { next: "/dashboard" };
```

> 判断依据是数据的来源而不是数据的形状：来自请求的数据即使结构正确也不可信。

**速记**：首屏数据只回填服务端确定的值，客户端使用前仍需按类型与范围校验。



#### 敏感数据泄露到首屏数据

**首屏泄露**：是服务端把内部字段一并序列化下发、使敏感数据出现在 HTML 中可被直接读取的问题，其影响面是全部能访问该页面的人。

- 常见来源：直接把数据库记录整体下发，未做字段裁剪。
- 隐蔽形式：错误堆栈、调试信息与内部标识随首屏数据一起下发。
- 防护一：按显式白名单构造下发对象，而不是从完整对象中删除字段。
- 防护二：生产环境关闭详细错误输出，日志留在服务端。

```ts
type UserRow = { id: number; email: string; token: string; displayName: string };

// 白名单构造：只列出允许下发的字段
export function toPublicUser(row: UserRow) {
  return { id: row.id, displayName: row.displayName };
}
```

> 删除字段的写法容易漏，白名单构造在字段新增时默认不下发，方向更安全。

**速记**：下发对象用白名单构造，生产关闭详细错误，日志不回传浏览器。



#### 跨站请求伪造与服务端凭据携带

**跨站请求伪造（cross-site request forgery，CSRF）**：是攻击者借用浏览器自动携带凭据的行为、诱导用户在已登录状态下发出非本意请求的问题，而服务端渲染场景的 Cookie 会话恰好依赖这种自动携带。

- 成因：Cookie 随请求自动附带，服务端只看凭据分不清请求由谁发起。
- 同站限制：把会话 Cookie 设为同站严格或宽松模式，可挡掉多数跨站发起的请求。
- 令牌校验：对写操作校验一次性令牌，且令牌只出现在本站页面中。
- 写操作约束：把有副作用的操作限制为特定方法，并校验来源头等请求信息。

```ts
export function readCsrfToken(cookieHeader: string | null): string | null {
  if (!cookieHeader) {
    return null;
  }
  const match = cookieHeader.match(/(?:^|;\s*)csrf_token=([^;]+)/);
  return match ? decodeURIComponent(match[1]) : null;
}
```

> 同站属性越严格，安全性越高而从外部站点跳回本站的登录态越容易丢失，取值前先明确业务是否需要跨站跳转。

**速记**：Cookie 自动携带是伪造的成因，防护靠同站属性、一次性令牌与写操作的额外校验。
