## Next.js 数据获取与缓存

**数据获取**：是在组件渲染过程中把外部数据读入并交给视图的过程；Next.js 的做法是在渲染阶段直接调用取数逻辑，由框架决定这次渲染发生在构建期还是请求期。

本篇只回答四件事：服务端怎么取数、缓存与再验证怎么控制、客户端怎么取数、几种模式怎么选。服务端组件的定义与边界从第 9 篇展开，数据在双端的共享与序列化详见本主题第 12 篇 SSR 应用的鉴权、状态与安全。

### 服务端数据获取

本节确立主路径：在服务端组件里直接写异步取数逻辑，不需要额外的生命周期函数、加载状态或全局状态容器。

#### 在 async 组件中直接取数

**服务端取数**：是在 async 组件体内直接调用异步函数并把结果用于 JSX 的方式，代码按从上到下的顺序执行，取数结果不进入客户端状态。

- 声明方式：组件函数加 async，内部 await 数据请求，再返回 JSX。
- 无额外钩子：不使用 useEffect，也不需要维护加载状态，取数在渲染阶段完成。
- 结果可见：渲染结果直接包含数据对应的 HTML，首屏即有内容，爬虫也能读到。
- API 调用：可调用数据库、文件系统或内部服务，这些代码不会进入浏览器产物。

```tsx
// app/users/page.tsx
async function getUsers(): Promise<{ id: number; name: string }[]> {
  const res = await fetch("https://api.example.com/users");
  return res.json();
}

export default async function UsersPage() {
  const users = await getUsers();
  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

取数函数写成组件外部的独立函数，便于在多个页面复用，也让组件本体只保留「数据怎么用」这一层逻辑。

> 在服务端组件里取数不需要加载态与错误态分支，这两类界面由 Suspense 与 error 约定文件承担（详见本主题第 9 篇 Next.js 进阶：服务端组件与流式渲染）。

**速记**：服务端组件直接 async 取数，结果参与服务端渲染，不进客户端状态。



#### 并行请求与请求去重

**并行请求**：是把互不依赖的取数调用同时发起，用 Promise.all 等待全部完成，避免串行等待叠加耗时。

- 串行代价：两个各需 200 ms 的请求串行执行需 400 ms，并行执行约 200 ms。
- 写法：用 Promise.all 接收请求数组，一次性解构结果。
- 去重：同一次渲染中对同一地址的 fetch 会自动合并为一次请求，无需手动缓存。
- 判定边界：去重按请求地址与选项判断，选项不同视为两次不同请求。

```tsx
// 并行取数，总耗时取决于最慢的一个
const [userRes, orderRes] = await Promise.all([
  fetch("https://api.example.com/user"),
  fetch("https://api.example.com/orders"),
]);
const user = await userRes.json();
const orders = await orderRes.json();
```

```tsx
// 串行写法：总耗时是两个请求之和，应尽量避免
const userRes = await fetch("https://api.example.com/user");
const orderRes = await fetch("https://api.example.com/orders");
```

> [!TIP]
> **建议内容**：把与首屏主体无关的请求下移到更深的子组件并用 Suspense 包裹，让主要内容先到达浏览器。

**速记**：互不依赖的请求用 Promise.all 并行，同一次渲染中相同地址的 fetch 自动去重。



#### 静态渲染与动态渲染的判定

**静态渲染（static rendering）**：指页面在构建期生成一次 HTML，之后由缓存直接响应；**动态渲染（dynamic rendering）**指每次请求都重新执行渲染。

- 判定依据：组件是否读取了随请求变化的信息，如 cookies、headers 与查询参数。
- 倾向静态：不含请求相关信息的页面在构建期生成，响应最快且可被 CDN 直接分发。
- 显式切换：在较新版本中，路由段可导出 dynamic 为 force-dynamic，强制每次请求重新渲染。
- 取数选项：单次 fetch 也能声明不复用，用 cache 为 no-store 表示每次都重新请求。

```tsx
// app/dashboard/page.tsx
// 该段依赖实时指标，声明为按请求渲染
export const dynamic = "force-dynamic";

export default async function DashboardPage() {
  const res = await fetch("https://api.example.com/metrics", {
    cache: "no-store",
  });
  const metrics = await res.json();
  return <p>今日访问：{metrics.today}</p>;
}
```

判定顺序通常是先写默认（尝试静态），构建日志里出现该路由被标记为静态或动态的提示，再按需要显式声明。

> 静态与动态是针对「渲染时机」的判断，与是否在服务端取数无关：动态渲染的页面同样在服务端完成取数。

**速记**：读取请求相关信息即转为动态渲染，可用 dynamic 常量显式声明。



### 缓存与再验证

本节说明数据被复用的层次与失效方式，是首屏速度与内容新鲜度之间唯一的调节旋钮。

#### 缓存的分层

**缓存分层**：是 Next.js 在取数与渲染链路上设置的复用点，知道数据被哪一层复用，才知道该在哪一层调整。

- 请求层：同一次渲染内相同地址的请求合并，只在单次渲染中有效。
- 数据层：fetch 的结果按地址与选项持久复用，可跨请求、跨构建生效。
- 路由层：整段渲染产物可被复用，静态路由直接命中缓存而不再执行组件。
- 客户端层：客户端导航时会复用已经取过的路由片段（详见本主题第 7 篇 Next.js 入门）。

```tsx
// 默认行为：不额外声明时，数据请求结果可被复用
const res = await fetch("https://api.example.com/posts");
const posts = await res.json();
```

> [!WARNING]
> **警告内容**：把用户相关的数据当作可复用数据缓存，会让不同用户看到彼此的内容；个性化数据必须走不缓存的请求。

**速记**：缓存分请求、数据、路由与客户端四层，个性化数据不得进入可复用缓存。



#### 基于时间的再验证

**基于时间的再验证（time-based revalidation）**：是给数据设定有效期，超过有效期后下一次请求触发后台重新获取，期间先返回旧内容。

- 请求级：fetch 的 next.revalidate 字段以秒为单位设定该次请求的有效期。
- 路由级：导出 revalidate 常量，设定整段路由的默认有效期。
- 行为：过期后先返回旧值并触发刷新，刷新完成后后续请求得到新值。
- 取舍：时间越短数据越新、回源次数越多；时间越长越省资源、越可能展示陈旧内容。

```tsx
// app/news/page.tsx
export const revalidate = 60; // 60 秒内复用渲染结果

async function getNews() {
  const res = await fetch("https://api.example.com/news", {
    next: { revalidate: 60 },
  });
  return res.json();
}

export default async function NewsPage() {
  const news = await getNews();
  return <p>最新条目数：{news.length}</p>;
}
```

路由级声明与请求级声明同时存在时，请求级的值作用于该次请求，路由级的值作为整段的兜底，两者可以并存。

> 再验证是「先给旧值、后台刷新」的策略，不阻塞用户请求，代价是短时间内的数据延迟。

**速记**：revalidate 以秒设定有效期，过期后后台刷新，期间先返回旧值。



#### 按需再验证

**按需再验证（on-demand revalidation）**：是在数据实际变化时主动让指定缓存失效，由事件触发而不是等待时间到期。

- 按路径：调用 revalidatePath 并传入路由路径，使该路径的缓存立即失效。
- 按标签：取数时给请求打上 tags，再用 revalidateTag 让同标签的缓存一并失效。
- 触发时机：内容后台发布、第三方回调或表单提交成功后调用。
- 优势：内容一变更立即可见，同时不必为每条数据设置很短的过期时间。

```tsx
// app/posts/[slug]/page.tsx：给请求打标签
const res = await fetch("https://api.example.com/posts/" + slug, {
  next: { tags: ["posts", "post-" + slug] },
});
```

```tsx
// app/api/revalidate/route.ts：一次发布让同标签缓存失效
import { revalidateTag } from "next/cache";

export async function POST() {
  revalidateTag("posts");
  return Response.json({ revalidated: true });
}
```

> [!NOTE]
> **提醒内容**：标签失效作用于所有带同一标签的缓存，标签粒度不宜过粗，否则一次发布会让大量无关页面重新生成。

**速记**：revalidatePath 按路径失效，revalidateTag 按标签失效，用于事件驱动的更新。



### 客户端数据获取

本节说明哪些数据适合放在浏览器里取，以及随之而来的加载、错误与竞态问题。

#### 何时在客户端取数

**客户端取数**：是在浏览器中发起请求并更新界面的方式，适用于随用户操作持续变化的数据。

- 适用：分页与筛选、轮询与实时更新、依赖浏览器状态的数据。
- 不适用：首屏必需内容，放到客户端会让用户先看到空壳，也削弱可索引性。
- 混合：首屏由服务端给出，后续交互再由客户端续取。
- 代价：需要自行处理加载态、错误态与请求竞态。

```tsx
"use client";

import { useEffect, useState } from "react";

export function LiveCount() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(async () => {
      const res = await fetch("/api/count");
      const data = await res.json();
      setCount(data.count);
    }, 5000);
    return () => clearInterval(timer);
  }, []);

  return <p>在线人数：{count}</p>;
}
```

> 客户端取数的数据不参与服务端渲染，加载态与错误处理都需要自己承担。

**速记**：交互频繁、依赖浏览器状态的数据放客户端，首屏内容仍归服务端。



#### 请求库与缓存复用

**客户端请求库**：是替开发者管理请求缓存、重试与失效的工具，常见选择是 SWR 与 TanStack Query。

- 作用：以键为单位缓存响应，多个组件共享同一份数据，避免重复请求。
- 能力：内置加载与错误状态、窗口重新聚焦时刷新、失效与重试策略。
- 与框架的关系：这类库工作在浏览器侧，不影响服务端取数路径。
- 选型：请求数量少时可手写 useEffect；需要跨组件共享时再引入请求库。

```tsx
"use client";

// 以 SWR 为例，同一 key 的请求在多个组件间共享
import useSWR from "swr";

function fetcher(url: string) {
  return fetch(url).then((res) => res.json());
}

export function UserBadge() {
  const { data, error, isLoading } = useSWR("/api/me", fetcher);

  if (isLoading) return <span>加载中</span>;
  if (error) return <span>加载失败</span>;
  return <span>{data.name}</span>;
}
```

键的组织方式决定缓存命中率：把筛选条件完整拼进键，条件不同自然拿到不同结果，条件相同则直接复用。

> [!CAUTION]
> **注意内容**：在客户端组件中直接连接数据库或读取服务端密钥会导致构建失败或密钥泄露，浏览器侧的请求必须走公开接口。

**速记**：SWR 与 TanStack Query 为客户端请求提供缓存与状态，跨组件共享时再引入。



#### 加载态与竞态处理

**竞态（race condition）**：指先发出的请求后返回，用旧数据覆盖新结果的现象，快速切换筛选条件时最容易出现。

- 成因：响应到达顺序与请求发出顺序不一致。
- 处理：在清理函数中标记本次请求已失效，响应回来时不再写入状态。
- 取消：用 AbortController 取消已经不需要的请求，减少无效流量。
- 简化：使用请求库时，按键缓存天然隔离不同条件的结果。

```tsx
"use client";

import { useEffect, useState } from "react";

export function SearchResult({ keyword }: { keyword: string }) {
  const [items, setItems] = useState<string[]>([]);

  useEffect(() => {
    let active = true;
    fetch("/api/search?q=" + encodeURIComponent(keyword))
      .then((res) => res.json())
      .then((data) => {
        if (active) setItems(data.items); // 只接受最新一次请求的结果
      });
    return () => {
      active = false;
    };
  }, [keyword]);

  return <p>命中 {items.length} 条</p>;
}
```

> 竞态属于客户端取数的固有代价，只要请求与用户操作并发存在，就需要显式处理。

**速记**：用失效标记或 AbortController 丢弃过期响应，避免旧数据覆盖新结果。



### 数据获取模式选型

本节把前面的手段收成一套判断顺序：先问数据是否因用户而异，再问数据多久变一次。

#### 静态优先的判断标准

**静态优先**：是默认把页面做成构建期生成，只在确有必要时才切到动态的策略。

- 看数据：内容对所有用户一致且更新不频繁，适合静态生成加再验证。
- 看时效：可接受分钟级延迟的场景，用 revalidate 换取稳定与速度。
- 看权限：页面内容随登录身份变化时，必须走动态渲染。
- 看交互：强交互部分交给客户端，主体内容仍然可以静态生成。

```tsx
// 内容型页面：静态生成加定时再验证
export const revalidate = 300;

export default async function DocsPage() {
  const res = await fetch("https://api.example.com/docs", {
    next: { revalidate: 300 },
  });
  const docs = await res.json();
  return <p>文档条目：{docs.length}</p>;
}
```

> 选型的第一问不是「用哪个选项」，而是「这份数据是否因用户或时间而异」。

**速记**：数据是否因用户而异决定动态与否，是否频繁变化决定再验证周期。



#### 动态与个性化数据

**动态与个性化数据**：是必须按请求或按用户实时生成的内容，不能进入共享缓存。

- 判定：读取 cookies、headers 或当前用户会话的数据。
- 写法：把请求声明为不缓存，或导出 dynamic 常量要求每次渲染。
- 范围控制：动态渲染应限制在必要的路由段，避免整站动态化拖慢响应。
- 安全：会话与鉴权的完整做法详见本主题第 12 篇 SSR 应用的鉴权、状态与安全。

```tsx
// app/profile/page.tsx
import { cookies } from "next/headers";

export default async function ProfilePage() {
  const store = await cookies();
  const token = store.get("session")?.value;
  const res = await fetch("https://api.example.com/me", {
    headers: { authorization: "Bearer " + token },
    cache: "no-store",
  });
  const profile = await res.json();
  return <p>你好，{profile.name}</p>;
}
```

> [!IMPORTANT]
> **重要内容**：一旦渲染过程读取了 cookies 或 headers，该路由段即按请求动态渲染，缓存策略也随之改变。

**速记**：读取会话或请求头的页面必须动态且不缓存，动态范围应尽量收窄。



#### 服务端预取加客户端续取

**组合模式**：是首屏数据由服务端取回并渲染、后续交互数据由客户端按需请求的搭配方式。

- 首屏：服务端取数并渲染，用户不需要等待脚本执行即可看到主要内容。
- 后续：翻页、筛选与实时刷新交给客户端请求完成。
- 数据传递：服务端把首屏数据渲染进 HTML，需要跨组件共享时由框架把初始数据交给客户端（序列化规则详见本主题第 12 篇）。
- 一致性：两端共用同一份数据模型，避免字段命名与结构分叉。

```tsx
// app/posts/page.tsx：服务端给出首屏，客户端负责加载更多
import { PostList } from "@/components/PostList";

export default async function PostsPage() {
  const res = await fetch("https://api.example.com/posts");
  const initialPosts = await res.json();
  return <PostList initialPosts={initialPosts} />;
}
```

```tsx
"use client";

// 客户端组件接收首屏数据，后续翻页自行请求
export function PostList({ initialPosts }: { initialPosts: { id: number; title: string }[] }) {
  const [posts, setPosts] = useState(initialPosts);
  return <ul>{posts.map((post) => <li key={post.id}>{post.title}</li>)}</ul>;
}
```

> 组合模式的判断点是「哪些数据首屏必需」：必需的在服务端取，其余按交互节奏在客户端取。

**速记**：首屏服务端取数直出，交互数据客户端续取，两端共用同一数据模型。
