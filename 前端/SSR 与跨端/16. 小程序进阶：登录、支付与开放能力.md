## 小程序进阶：登录、支付与开放能力

登录、支付与开放能力决定小程序能否承载真实业务：登录让服务端认得同一个用户，支付让交易闭环成立，开放能力与审核规范划出功能边界。

本篇回答四件事：登录与用户标识如何建立、微信支付经过哪些阶段、消息订阅与分享如何工作、开放能力与审核有哪些约束。小程序的运行机制详见本主题第 14 篇 小程序基础：双线程模型与运行机制，页面与基础 API 详见本主题第 15 篇 小程序开发：页面、组件与 API。

### 登录与用户标识

小程序没有浏览器自动携带的 Cookie 会话，用户标识必须由一次显式登录换取，登录态由开发者自己维护，这是与 Web 会话最本质的差别。

#### 登录的整体流程

**登录（login）**：是小程序取得一次性临时凭证、再由服务端用该凭证换取用户标识的过程，客户端不直接接触用户标识。

- 第一步：客户端调用登录接口，取得一次性临时凭证。
- 第二步：客户端把临时凭证交给自己的服务端，途中不解析其内容。
- 第三步：服务端用临时凭证向平台换取用户标识与会话密钥。
- 第四步：服务端签发自己的会话标识，下发给客户端保存。

```js
// 小程序端：取得一次性临时凭证，交给自己的服务端
wx.login({
  success(res) {
    sendCodeToServer(res.code); // res.code 只能使用一次
  },
  fail(err) {
    console.error("登录失败", err.errMsg);
  },
});
```

```js
// 服务端：用临时凭证换取用户标识（字段名以官方文档为准）
async function exchangeCodeForSession(code) {
  const url = `https://api.weixin.qq.com/sns/jscode2session?appid=${appId}&secret=${appSecret}&js_code=${code}&grant_type=authorization_code`;
  const res = await fetch(url);
  return res.json(); // { openid, session_key, unionid }
}
```

> 登录接口不弹授权窗口、不返回昵称头像，用户全程无感知，因此可以在启动时静默调用。

**速记**：登录分两步，客户端取一次性临时凭证，服务端换用户标识。



#### 用户唯一标识与多应用打通

**openid**：是同一用户在单个小程序内的唯一标识。**unionid**：是同一开放平台账号下多个应用的统一标识。

- openid：与小程序绑定，同一用户在不同小程序中的 openid 互不相同。
- unionid：账号绑定到开放平台后才会返回，用于跨应用识别同一用户。
- session_key：会话密钥，只用于服务端校验与解密，不得下发到客户端。
- 存储：服务端把 openid 关联到自己的用户表，客户端只持有服务端签发的会话标识。

```js
// 服务端：把用户标识登记进自己的账号体系
function issueSession(openid, unionid) {
  const account = accountRepo.upsertByOpenid(openid, { unionid });
  return signToken({ accountId: account.id, issuedAt: Date.now() });
}
```

> [!IMPORTANT]
> **重要内容**：openid 与 session_key 属于服务端凭据，一旦下发到客户端就可能被冒用，客户端只应持有自己服务端签发的会话标识。

**速记**：openid 认单应用，unionid 认同一开放平台下的多应用，密钥只留服务端。



#### 用户信息与头像昵称

**用户信息授权**：是取得昵称、头像等资料的另一条流程，与登录彼此独立，必须由用户主动点击触发。

- 触发方式：由带授权类型的按钮触发，不能在页面加载时自动弹出。
- 头像昵称：较新版本提供头像选择与昵称填写的组件能力，用户可自行选择或修改。
- 最小化：只请求业务真正使用的字段，未使用的资料不采集。
- 存储：头像地址可能是临时地址，需转存到自己的存储后再持久化。

```html
<!-- 页面模板：两个独立的授权入口，均由用户点击触发 -->
<button open-type="chooseAvatar" bind:chooseavatar="onChooseAvatar">选择头像</button>
<input type="nickname" placeholder="请输入昵称" bind:blur="onNicknameBlur" />
```

```js
Page({
  onChooseAvatar(e) {
    const { avatarUrl } = e.detail; // 临时地址，需转存
    this.uploadAvatar(avatarUrl);
  },
  onNicknameBlur(e) {
    console.log(e.detail.value);
  },
});
```

> 昵称与头像属于个人信息，收集前应在隐私政策中说明用途，未声明的字段不应采集。

**速记**：资料授权与登录分开，必须用户点击触发，按需最少收集。



#### 登录态维护与服务端校验

**登录态（session）**：是服务端签发的、代表用户已登录的凭据，客户端每次请求业务接口都需携带。

- 本地存储：会话标识写入本地存储，启动时读取并可先做一次有效性探测。
- 携带方式：业务请求把会话标识放进请求头，由服务端统一校验。
- 失效处理：服务端返回未授权时清理本地会话并重新走登录流程。
- 服务端兜底：以身份为前提的接口一律在服务端校验，不能只信客户端。

```js
function requestWithSession(options) {
  const sessionToken = wx.getStorageSync("sessionToken");
  return new Promise((resolve, reject) => {
    wx.request({
      ...options,
      header: { ...options.header, Authorization: `Bearer ${sessionToken}` },
      success: resolve,
      fail: reject,
    });
  });
}
```

```text
# 会话失效时服务端的典型响应
HTTP 401 Unauthorized
{ "code": 401, "message": "session expired" }
```

> [!WARNING]
> **警告内容**：把身份判断放在客户端，攻击者伪造请求即可绕过；所有鉴权必须以服务端校验结果为准。

**速记**：会话标识存本地、随请求携带、由服务端校验，客户端判断不作数。



### 微信支付流程

微信支付把资金流转拆成若干有序阶段，小程序本身只参与其中两段，金额计算与订单落库必须放在服务端。

#### 支付的整体阶段

**微信支付**：是围绕商户订单完成的资金结算过程，可划分为商户下单、客户端调起支付、支付结果通知、商户校验四段。

- 商户下单：商户服务端向支付接口提交订单信息，取得一次性预支付标识。
- 调起支付：客户端用预支付标识与签名参数唤起收银台，由用户确认付款。
- 支付结果通知：支付平台在付款完成后回调商户服务端，告知订单结果。
- 商户校验：服务端核对通知真伪与订单金额后，才更新订单状态。

```text
# 四个阶段的先后顺序
1. 商户服务端下单  -> 取得一次性预支付标识
2. 小程序调起支付  -> 用户确认付款
3. 支付结果通知    -> 支付平台回调商户服务端
4. 商户校验入账    -> 核对签名与金额后更新订单
```

> 金额、订单归属与状态流转的判断都在服务端，客户端只承担唤起收银台与展示结果。

**速记**：支付分下单、调起、通知、校验四段，判断权在服务端。



#### 服务端下单与预支付标识

**商户下单**：是商户服务端用订单信息向支付接口发起请求、换取预支付标识的过程。

- 订单要素：商户订单号、金额、商品描述、用户标识等由服务端生成并落库。
- 金额权威：应收金额以服务端记录为准，客户端传来的金额只作展示。
- 预支付标识：下单成功后得到的一次性凭证，转交客户端用于唤起收银台。
- 签名：下单请求按平台规则签名，签名密钥只保存在服务端。

```js
// 服务端：下单成功后返回带签名的一次性支付参数
async function createPrepay(order) {
  const prepayId = await payClient.unifiedOrder({
    outTradeNo: order.id,
    total: order.amount,
    description: order.subject,
    openid: order.openid,
  });
  return signForClient(prepayId); // 交给客户端唤起收银台
}
```

> 订单金额必须由服务端依据商品数据计算，直接采用客户端传入的金额会造成被篡改的风险。

**速记**：下单在服务端，金额以服务端为准，产物是一次性预支付标识。



#### 客户端调起支付

**调起支付**：是小程序用服务端返回的一次性参数唤起收银台、由用户确认付款的动作。

- 参数透传：下单返回的时间戳、随机串、签名等字段原样交给调起接口。
- 用户操作：用户在收银台确认后才真正扣款，取消或失败进入失败分支。
- 结果含义：调起接口返回的成功只表示唤起成功，不代表资金已到账。
- 前端职责：成功与失败都只做界面反馈，最终状态以服务端查询为准。

```js
wx.requestPayment({
  timeStamp: payParams.timeStamp,
  nonceStr: payParams.nonceStr,
  package: payParams.package,
  signType: payParams.signType,
  paySign: payParams.paySign,
  success() {
    pollOrderStatus(); // 仅表示已唤起，需等服务端确认到账
  },
  fail(err) {
    console.warn("支付未完成", err.errMsg);
  },
});
```

> 唤起收银台与实际扣款是两回事，页面跳转应以后端确认的订单状态为条件。

**速记**：客户端只负责唤起收银台，成功回调不等于到账。



#### 支付结果通知与校验

**支付结果通知**：是支付平台在用户付款后主动回调商户服务端、告知订单结果的消息。

- 回调入口：商户服务端暴露一个公网可访问的接收接口。
- 验签：先校验消息签名，确认来自支付平台。
- 核额：再核对订单号与金额，与本地记录一致才继续。
- 幂等：同一订单可能收到多次通知，入账逻辑必须可重复执行而不重复生效。

```js
// 服务端：先验签、再核额、最后幂等入账
async function handlePayNotify(rawBody, headers) {
  if (!payClient.verifySignature(rawBody, headers)) {
    return { status: 400, body: "invalid signature" };
  }
  const notice = parseNotice(rawBody);
  const order = await orderRepo.findById(notice.outTradeNo);
  if (!order || order.amount !== notice.total) {
    return { status: 400, body: "order mismatch" };
  }
  await orderRepo.markPaidOnce(order.id); // 重复通知不重复入账
  return { status: 200, body: "success" };
}
```

> [!WARNING]
> **警告内容**：回调接口若不验签、不核额或不做幂等，会遭遇伪造通知与重复入账，造成资损。

**速记**：回调先验签、再核额、后幂等入账，三关缺一不可。



### 消息订阅与分享

消息与分享是小程序连接用户的出口：订阅消息在用户授权后由平台下发，分享把页面扩散到会话与群聊。

#### 订阅消息是什么

**订阅消息**：是小程序在用户主动授权后，由平台按模板向用户下发的一次性通知能力。

- 一次授权一次下发：用户每授权一次，对应一条可用的下发额度。
- 模板化：内容按预先选定的模板字段填充，不能自行拼长文本。
- 场景限制：只能在用户有明确操作后请求授权，不能诱导或强制。
- 触发方：真正的下发动作由服务端发起，客户端无法直接下发。

```js
// 客户端：在用户点击后请求订阅授权
wx.requestSubscribeMessage({
  tmplIds: ["TEMPLATE_ID_A"],
  success(res) {
    console.log(res["TEMPLATE_ID_A"]); // 用户对该模板的选择结果
  },
});
```

> 授权额度是逐次消耗的，承诺长期推送而不逐次请求授权是常见误解。

**速记**：订阅消息一次授权一次下发，模板化、由服务端触发。



#### 服务端下发订阅消息

**下发**：是服务端用用户标识、模板与字段数据调用发送接口投递消息的过程。

- 调用凭证：服务端先取得接口调用凭证，凭证有有效期需缓存复用。
- 必填字段：模板中标记为必填的字段必须提供，否则发送失败。
- 逐个发送：按要触达的用户逐个发送，不能群发同一份内容。
- 失败降级：授权耗尽或用户拒收时接口返回失败，业务据此降级处理。

```js
// 服务端：先取缓存凭证，再按用户与模板字段投递
async function sendSubscribeMessage(openid, pagePath, data) {
  const accessToken = await tokenStore.getAccessToken();
  const url = `https://api.weixin.qq.com/cgi-bin/message/subscribe/send?access_token=${accessToken}`;
  const res = await fetch(url, {
    method: "POST",
    body: JSON.stringify({ touser: openid, page: pagePath, data }),
  });
  return res.json();
}
```

> 接口调用凭证应在服务端集中缓存并提前刷新，每次发送都重新获取会触发频率限制。

**速记**：下发在服务端，先取缓存凭证，再按用户与模板字段逐个投递。



#### 分享转发与自定义

**分享**：是把页面以卡片形式转发到会话或群聊的能力，由页面定义转发内容与落点。

- 主动转发：页面开启转发菜单后，用户可通过右上角菜单转发。
- 按钮转发：页面内放置带转发类型的按钮，点击即触发。
- 自定义内容：可设置标题与封面图，决定卡片在会话中的呈现。
- 落点路径：落点路径决定打开后的页面，可携带参数区分来源。

```js
Page({
  onShareAppMessage() {
    return {
      title: "邀请你查看这篇文章",
      path: "/pages/article/detail?id=42&from=share",
      imageUrl: "/assets/share-cover.png",
    };
  },
});
```

> [!TIP]
> **建议内容**：转发落点尽量指向内容详情页而非首页，并携带来源参数，便于统计分享效果与后续引导。

**速记**：分享由页面定义标题、封面与落点，落点路径可带来源参数。



#### 群标识与分享回流

**群标识**：是页面经分享后在群聊中打开时可取得的、与该次分享对应群聊的临时标识。

- 取得入口：由转发信息查询接口返回，分享时需先声明需要该信息。
- 时效：只在本次分享的接收者打开时有效，每次分享对应新的标识。
- 用途：把同一次分享带来的多个用户归到同一群，支撑群体互动玩法。
- 边界：标识只代表一次分享，不能长期当作群聊的唯一标识使用。

```js
Page({
  onLoad(options) {
    if (options.shareTicket) {
      wx.getShareInfo({
        shareTicket: options.shareTicket,
        success: (res) => console.log(res),
      });
    }
  },
});
```

> 群标识随分享次数变化，仅在一次分享的生命周期内有效。

**速记**：群标识一次分享一换，用于归并同群来源，不能长期复用。



### 开放能力与审核规范

小程序能调用的能力受账号主体与服务类目约束，上线前还需通过平台审核，二者共同决定功能边界。

#### 常用开放能力

**开放能力**：是小程序在基础运行环境之外、需要申请或授权才能使用的平台接口集合。

- 身份类：登录、用户标识、手机号等与用户身份相关的能力。
- 交易类：支付、退款、订单等与资金相关的能力。
- 设备与媒体类：扫码、拍照、录音、定位等与硬件相关的能力。
- 内容安全类：文本与图片的安全检测，用于发布前的内容治理。

```js
// 扫码：由用户点击触发，返回扫码内容
wx.scanCode({
  scanType: ["qrCode", "barCode"],
  success(res) {
    console.log(res.result);
  },
});
```

> 开放能力的可用范围随账号主体与服务类目变化，开发前应先在平台后台确认已开通的权限。

**速记**：开放能力分身份、交易、设备媒体、内容安全四类，可用范围随账号变化。



#### 接口权限与调用凭证

**调用凭证**：是服务端调用平台接口时所需的临时票据，代表该小程序账号的调用资格。

- 获取：用账号的唯一标识与密钥向平台换取，凭证有有效期。
- 缓存：凭证需集中缓存并在过期前刷新，避免重复获取。
- 保管：账号密钥只存服务端，泄露会导致账号被冒用。
- 限频：获取接口本身有限频，多实例部署时应集中管理。

```js
// 服务端：集中管理凭证，多实例共用一份
class AccessTokenStore {
  constructor() {
    this.token = null;
    this.expiresAt = 0;
  }

  async getAccessToken() {
    if (this.token && Date.now() < this.expiresAt) return this.token;
    const { access_token, expires_in } = await fetchAccessToken();
    this.token = access_token;
    this.expiresAt = Date.now() + (expires_in - 300) * 1000; // 提前 5 分钟过期
    return this.token;
  }
}
```

> 账号密钥一旦写进客户端代码或公开仓库，任何人都能以该小程序身份调用接口，必须只保存在服务端。

**速记**：凭证有有效期需缓存刷新，账号密钥只能留在服务端。



#### 用户体验与合规红线

**合规**：是小程序在功能设计上必须遵守的平台规则与法律要求，违规会导致功能被驳回或下架。

- 授权自愿：不得诱导或强制授权，拒绝授权后应给出可用路径而非直接不可用。
- 隐私告知：收集个人信息前需提供隐私政策并取得用户同意。
- 内容治理：用户生成内容需接入安全检测，并保留违规内容的处置能力。
- 类目相符：实际功能须落在已开通的服务类目范围内，超范围能力无法开通。

```text
# 常见的驳回原因
- 功能与所选服务类目不符
- 未经用户同意收集个人信息
- 诱导分享、诱导关注
```

> [!IMPORTANT]
> **重要内容**：服务类目决定可用能力，功能设计要落在已开通类目内，超出范围的功能即使接口已开通也无法通过审核。

**速记**：授权自愿、隐私告知、内容治理、类目相符是四条硬线。



#### 版本发布与灰度

**发布**：是小程序把开发版本经审核后对外生效的过程，依次经过开发、体验、审核与发布几个状态。

- 开发版本：在开发者工具中预览与真机调试，仅开发者可见。
- 体验版本：供指定体验成员使用的版本，用于内部验收。
- 审核版本：提交平台审核，通过后需手动点击发布才对外生效。
- 灰度与回退：发布后可逐步放量，出现问题可回退到上一版本。

```text
# 版本推进的典型流程
开发版 -> 体验版 -> 提交审核 -> 审核通过 -> 发布上线
                            -> 审核驳回 -> 修改后重新提交
```

> 审核通过不等于自动上线，仍需手动发布，发布前的最后确认不可省略。

**速记**：开发、体验、审核、发布四态推进，审核通过后仍需手动发布。
