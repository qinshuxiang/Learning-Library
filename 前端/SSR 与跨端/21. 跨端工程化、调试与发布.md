## 跨端工程化、调试与发布

**跨端工程化**：是在一套源码需要产出多个端形态的前提下，对构建、调试、版本与发布建立统一流程的工程实践。

本篇回答四件事：多端如何构建与组织产物、各端如何调试、版本如何管理与发布、出问题如何定位。第 17、18 篇只讲各框架的构建命令与产物形态，流程、调试、版本与排错统一归本篇。

### 多端构建与产物组织

本节确立工程化的第一件事：一次源码如何变成多个端的产物，以及产物如何组织才便于分发与回溯。

#### 构建目标与命令

**构建目标**：是一次构建产出的运行端形态，通常包括 Web、微信小程序、支付宝小程序、iOS、Android 与桌面端。

- 目标划分：把需要产出的端列成固定清单，避免漏构建导致某端停留在旧版本。
- 命令约定：每端一条构建命令，命名保持统一的前缀与后缀，便于脚本批量调用。
- 差异化配置：编译差异由框架配置承载，业务代码不感知当前构建目标。
- 持续集成：全部端在同一条流水线中构建，产物统一归档，避免本地构建与流水线结果不一致。

```bash
npm run build:web
npm run build:mp-weixin
# 产物分别写入 dist/web 与 dist/mp-weixin
```

需要一条命令跑完所有端时，用脚本把各端命令串起来，任一端失败即中断，避免不完整的产物被误发布。

```json
{
  "scripts": {
    "build:all": "npm run build:web && npm run build:mp-weixin && npm run build:mp-alipay"
  }
}
```

> [!IMPORTANT]
> **重要内容**：每次发布必须构建全部目标端，只构建被改动的那一端会掩盖其他端的编译错误，等到发布时才暴露会直接阻塞上线。

**速记**：构建目标列成固定清单，每端一条命令，全部端在同一流水线构建。



#### 产物目录结构

**产物目录**：是构建输出按端隔离存放的目录结构，各端产物互不覆盖，便于分别部署与回溯。

- 按端隔离：每个目标端一个顶层目录，目录名与目标端一一对应。
- 静态资源：图片、字体等资源由构建工具加哈希后输出到资源目录，页面按引用加载。
- 源码映射：保留源码映射文件用于错误定位，是否随产物一并发布由环境决定。
- 归档策略：产物以构建号归档，回滚时可直接取用历史归档，不需要重新构建。

```text
dist/
  web/            页面与静态资源，可直接托管
  mp-weixin/      小程序代码包目录，用开发者工具上传
  mp-alipay/      支付宝小程序代码包目录
  ios/            原生工程或打包产物
  android/        原生工程或打包产物
```

产物目录名还会影响部署配置：静态托管的站点根目录要指向对应端的目录，小程序上传时也要选择该端的目录，目录选错会造成构建成功但线上未更新的假象。

> 产物目录本身不应手工修改，任何需要长期保留的配置都必须回写到源码或构建配置中，否则下次构建即被覆盖。

**速记**：产物按端顶层隔离，资源加哈希，产物以构建号归档。



#### 环境变量与多环境配置

**环境变量**：是构建期注入、用于区分运行环境的键值配置，只有可公开的值才允许写入前端产物。

- 环境划分：常见为开发、测试、预发布、生产四套，键名一致而取值不同。
- 注入位置：构建期读取配置文件并替换到代码中，运行时代码读到的是替换后的字面量。
- 命名前缀：框架通常要求注入变量带固定前缀，未带前缀的变量不会进入产物。
- 安全边界：密钥、令牌一律不写入前端可读变量，只能放在服务端（详见 后端/Node 主题）。

```bash
# 按环境选择配置文件
npm run build:web -- --mode production
# 读取 .env.production 中的公开变量
```

```json
{
  "scripts": {
    "build:web": "vite build",
    "build:mp-weixin": "uni build -p mp-weixin"
  }
}
```

业务代码只读取注入后的变量，不直接读取进程环境变量，这样同一份源码在各端构建时都能拿到该端的正确取值。

```js
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL;

export function buildRequestUrl(path) {
  return new URL(path, apiBaseUrl).toString();
}

console.log(buildRequestUrl("/articles/42")); // https://api.example.com/articles/42
```

四套环境只需替换取值，键名保持不变，构建脚本通过模式参数决定加载哪个文件。

```text
.env.development   VITE_API_BASE_URL=http://localhost:3000
.env.test          VITE_API_BASE_URL=https://api.test.example.com
.env.production    VITE_API_BASE_URL=https://api.example.com
```

> [!CAUTION]
> **注意内容**：以固定前缀注入的变量会原样打包进产物，写进去的密钥等于公开，检查构建配置时应把这一条列为固定检查项。

**速记**：环境变量按环境分套、构建期注入，密钥不得进入前端产物。



### 各端调试手段

本节说明第二件事：不同端的运行环境不同，调试手段也各自独立，需要把入口与常见限制区分清楚。

#### Web 与小程序调试

**Web 调试**：是依托浏览器开发者工具查看结构、样式、网络与执行栈的调试方式。

- 浏览器开发者工具：元素面板查结构与样式，网络面板查请求与缓存，性能面板查长任务。
- 断点调试：在源码面板下断点或写调试语句，配合源码映射定位压缩后的代码。
- 小程序开发者工具：提供页面结构查看、数据面板、网络与存储查看、真机预览。
- 差异注意：小程序的布局异常需在逻辑层与视图层分别观察，错误栈也分属两层。

```bash
npm run dev:web
# 打开 http://localhost:5173 使用浏览器开发者工具调试
```

开发服务器与构建产物之间可能仍存在差异，接口代理、路径前缀与资源基路径都只在构建配置中体现。联调通过后再跑一次生产构建并预览产物，是成本很低的一道保险。

排错时优先看控制台的第一条错误，后续错误多为它的连带结果；按错误时间对齐网络面板的请求，可以快速判断是数据问题还是代码问题。

> 小程序开发者工具与浏览器工具界面相似，但小程序的逻辑层与视图层分离，状态更新与界面渲染不同步时会表现为数据已变而界面未刷新。

**速记**：Web 用浏览器开发者工具，小程序用宿主开发者工具，且需分两层观察。



#### 移动端真机调试

**真机调试**：是在真实设备上运行应用、通过连接或局域网把调试信息回传到开发机的调试方式。

- 连接方式：USB 连接或同一局域网内按地址访问开发服务器。
- 原生工程调试：用平台自带的集成开发环境查看原生日志与崩溃堆栈。
- 日志桥接：JavaScript 日志通过调试通道回传，原生日志在平台工具中查看。
- 网络环境：真机可能处于代理、弱网或不同网段，接口不通首先排查网络路径。

```bash
npx expo run:android
npx expo run:ios
# 设备连接后自动安装并启动，日志回传到终端
```

小程序在真机上的表现与开发者工具模拟器差异明显，尤其是滚动、键盘与录音等需要真实硬件的场景，发布前必须在真机预览中走一遍主流程。

```bash
# 小程序真机预览：开发者工具生成预览二维码，用宿主客户端扫码
# 崩溃与原生日志在平台集成开发环境的日志面板中查看
```

> [!TIP]
> **建议内容**：真机验证至少覆盖一台低端机与一台高分屏设备，性能问题与布局问题在这两类设备上最容易暴露。

**速记**：真机靠 USB 或局域网连接，脚本日志与原生日志分两处查看。



#### 日志与错误监控

**统一日志**：是把各端日志收敛到同一封装、按级别输出并保留上下文的做法，发布环境还需接入错误上报。

- 分级输出：按调试、信息、警告、错误分级，生产环境只保留后两级。
- 统一入口：业务代码只调用封装后的日志函数，不直接使用各端原生打印接口。
- 错误上报：捕获运行时错误与未处理的拒绝，附带版本、端与页面信息上报。
- 源码映射：上报平台需要源码映射才能还原压缩代码，构建时一并上传。

```ts
type LogLevel = "debug" | "info" | "warn" | "error";

function writeLog(level: LogLevel, message: string, context?: Record<string, unknown>) {
  if (level === "debug") {
    return;
  }
  const payload = { level, message, context, time: Date.now() };
  console[level](JSON.stringify(payload));
}

export function logError(message: string, context?: Record<string, unknown>) {
  writeLog("error", message, context);
}
```

上报通道本身也要防错：上报失败不能再抛错，否则会形成错误循环。常见做法是给上报加超时与失败丢弃策略，保证日志系统永远不阻塞业务。

> 日志封装应先于业务开发落地：等到线上出问题再补日志，往往会发现关键分支全程没有输出。

**速记**：日志统一封装、分级输出，生产环境接入错误上报并上传源码映射。



### 版本与发布流程

本节说明第三件事：多端产物的版本需要分开管理，发布流程也需要按端区分。

#### 版本号与变更管理

**版本号**：是用主版本、次版本与修订号三段描述一次发布的标识，各端版本号相互独立。

- 版本结构：主版本表示不兼容变更，次版本表示向下兼容的功能新增，修订号表示向下兼容的问题修复。
- 各端独立：同一个业务迭代在 Web 与小程序上的版本号通常不同，不能用一套编号硬对齐。
- 变更记录：每次发布记录变更条目并与版本号绑定，便于定位问题引入的版本。
- 发布标记：Web 端除版本号外还需记录构建号，产物文件名带上构建号便于缓存失效。

```bash
npm version patch --no-git-tag-version
# 更新 package.json 中的版本号，随后走构建流程
```

多个端同时发布时，还需要一份记录端与版本对应关系的发布清单，人工或由流水线自动生成均可。故障时先看清单，能立刻知道当时各端跑的是哪一份代码。

版本号在代码内也应可读：把版本注入为构建期变量并显示在设置页，用户反馈问题时可以直接报出版本，减少一轮沟通。

> 版本号的意义在于可追溯，而不是好看：出现问题时能由版本号反查代码与产物，才算真正在管理版本。

**速记**：版本号三段语义明确，各端独立编号，每次发布记录变更条目。



#### 各端发布差异

**发布差异**：是同一份业务代码发布到不同端时流程与约束的不同，主要体现在审核、分发与生效方式上。

- Web：产物上传静态托管或服务端，发布即生效，可即时回滚。
- 小程序：用宿主开发者工具上传代码包，提交平台审核，审核通过后发布。
- 原生应用：打包签名后提交应用商店，审核周期更长，用户更新覆盖是渐进的。
- 桌面端：打包安装包或走应用商店分发，需要处理签名与自动更新。

```text
Web：构建 -> 上传 -> 生效（分钟级，可直接回滚）
小程序：构建 -> 上传 -> 提交审核 -> 发布（受平台排期影响）
原生：构建 -> 签名 -> 提交商店 -> 审核 -> 用户更新（覆盖最慢）
```

发布节奏的安排应顺着生效速度来：先发 Web 端验证功能，再发小程序与原生端；反过来则可能出现修复已经完成、用户却还在旧版本上复现问题的窗口期。

> 生效速度不同意味着修复窗口不同：一端线上问题在 Web 端可以立刻回滚，在小程序与原生端则需要等待审核与用户更新。

**速记**：Web 即发即生效，小程序需审核后发布，原生依赖商店与用户更新。



#### 灰度与回滚

**灰度发布**：是先让一部分用户使用新版本、确认无异常后再全量放量的发布策略。

- 分流维度：按用户标识、设备、地域或端种类分流，同一用户应稳定落在同一分组。
- 功能开关：把新功能包在服务端下发的开关之后，可在不发版的情况下关闭。
- 回滚预案：每次发布前明确回滚方式与触发条件，Web 端回滚产物，小程序回滚版本，原生端改用开关兜底。
- 观察指标：错误率、接口成功率与关键路径完成率是通用观察项。

```js
function hashToBucket(userId) {
  let sum = 0;
  for (const char of userId) {
    sum = (sum * 31 + char.charCodeAt(0)) % 100;
  }
  return sum;
}

function isFeatureEnabled(userId, rolloutPercent) {
  return hashToBucket(userId) < rolloutPercent;
}

console.log(isFeatureEnabled("user-1024", 20)); // true 或 false，同一用户结果稳定
```

分流比例由服务端配置下发，而不是写死在客户端，这样才能在观察到异常时立即把比例调到零，不必等待新版本发布。

```json
{
  "flags": {
    "newCheckoutFlow": { "enabled": true, "rolloutPercent": 20 },
    "newSearchRank": { "enabled": false, "rolloutPercent": 0 }
  }
}
```

> [!WARNING]
> **警告内容**：功能开关必须设定清理时间，长期保留的开关会让代码分支不断累积，最终没人敢删也没人知道它当前处于什么状态。

**速记**：灰度按用户稳定分流，开关兜底，发布前先定好回滚预案。



### 跨端项目排错

本节说明第四件事：多端排错的关键是先把问题定位到某一层，再进入该层对应的手段。

#### 分层定位思路

**分层定位**：是按构建层、运行时层、平台能力层与数据层逐层排除的排查方法。

- 构建层：判断问题是否只在某一个端的产物中出现，更换目标端构建能否复现。
- 运行时层：区分逻辑错误与渲染错误，逻辑错误在客户端接管前后都可能出现。
- 平台能力层：确认该端是否具备对应能力，能力缺失导致的问题往往不是代码缺陷。
- 数据层：核对接口返回与本地缓存，排除环境与数据差异之后再怀疑代码。

```text
问题是否只在单一端出现？
  是 -> 优先查平台能力层与平台样式差异
  否 -> 查构建层与运行时层
构建产物是否可复现？
  可复现 -> 查构建配置与依赖版本
  不可复现 -> 查环境变量与数据
```

定位过程中应同步记录已排除的假设，尤其是「换端复现」这类结论，它是后续判断问题归属的最重要依据，凭记忆回溯容易重复劳动。

> 分层定位的意义是减少无效尝试：在未确定层次之前修改代码，往往只是把问题挪到别处。

**速记**：先判断问题出在哪一端与哪一层，再选择对应的排查手段。



#### 常见问题与排查清单

**排查清单**：是把反复出现的跨端问题固化为检查项的清单，用于发布前与故障时逐项核对。

- 环境配置：各端环境变量是否齐全，接口地址是否指向正确环境。
- 构建配置：目标端清单是否完整，产物目录是否正确，依赖版本是否一致。
- 样式与布局：单位是否统一，安全区域是否处理，真机与模拟器差异是否核对。
- 能力与降级：调用前是否做能力探测，缺失能力是否有降级路径。
- 版本与缓存：产物文件名是否带构建号，缓存策略是否会让用户拿到旧版本。

```bash
# 发布前核对：清理依赖后重新安装并全端构建
rm -rf node_modules
npm install
npm run build:web && npm run build:mp-weixin
```

清单的价值在于沉淀：每解决一个线上问题，就把可复用的判定条件补进对应条目，清单会随项目运行时间增长而变得更有效。

> [!NOTE]
> **提醒内容**：跨端问题的复现信息至少要包含端、系统版本、应用版本与网络环境，缺少任一项都会让定位时间成倍增加。

**速记**：把环境、构建、样式、能力、缓存五类检查项固化下来，逐项核对。



#### 平台差异引发的坑

**平台差异坑**：是同一段代码因各端运行环境不同而表现不同的问题，集中出现在时间处理、存储与网络等基础能力上。

- 时间与格式：日期解析对各端格式的容忍度不同，统一按固定格式解析并显式指定时区。
- 本地存储：容量上限与同步异步行为不同，写入失败需要捕获并降级。
- 网络：并发连接数、超时默认值与跨域规则不同，超时与重试策略应由业务显式定义。
- 渲染与事件：滚动容器嵌套、事件冒泡顺序、键盘避让在原生端与 Web 端差异明显。

```js
// 避免依赖各端对日期字符串的宽松解析
function parseDate(input) {
  const matched = /^(\d{4})-(\d{2})-(\d{2})$/.exec(input);
  if (!matched) {
    return null;
  }
  const [, year, month, day] = matched;
  return new Date(Number(year), Number(month) - 1, Number(day));
}

console.log(parseDate("2026-09-13")); // Sun Sep 13 2026
```

这类问题的共同特征是「代码没错、环境不同」，因此修复方式通常是补齐显式约束，而不是改写业务逻辑。为每个基础能力补一层薄封装，可以一次性覆盖大部分差异。

```ts
type TimerHandle = ReturnType<typeof setTimeout>;

export function delay(ms: number): Promise<void> {
  return new Promise((resolve) => {
    const handle: TimerHandle = setTimeout(resolve, ms);
    if (typeof handle === "object" && handle !== null && "unref" in handle) {
      // 服务端定时器需要显式 unref，避免进程被挂住
      (handle as unknown as { unref: () => void }).unref();
    }
  });
}
```

> 差异坑的通用对策是先抽象后实现：由适配层提供统一接口，再在内部按端处理，具体做法详见本主题第 20 篇 多端适配：布局、样式与平台差异。

**速记**：时间、存储、网络与事件是差异高发区，统一封装后再按端实现。
