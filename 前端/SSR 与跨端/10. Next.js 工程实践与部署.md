## Next.js 工程实践与部署

### 样式与静态资源配置

本节解决工程落地的第一类问题：样式如何组织、图片与字体如何优化、静态资源放在哪里以及如何被引用。这些内容决定项目的产物体积与首屏体验，也影响后续的构建与部署方式。

#### 全局样式与 CSS Modules

**全局样式（global stylesheet）**：是在整个应用范围内生效的样式表，在 App Router 中只能由根布局引入，其余位置引入会被构建设置拒绝。

- 引入位置：根布局文件引入一次，作用于全部路由。
- 作用范围：全局样式的类名对所有组件可见，容易相互覆盖。
- 组件级方案：以 .module.css 结尾的文件是 CSS Modules，类名在构建时被改写为局部唯一名称。
- 组合方式：全局样式承担重置与主题变量，组件样式用 CSS Modules 承担结构。

```tsx
// app/layout.tsx
import "./globals.css";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
```

> 变量与重置放进全局样式，具体组件的类名放进 CSS Modules；两者职责分开后，样式冲突大多可以避免。

**速记**：全局样式只由根布局引入，组件级样式用 CSS Modules 隔离类名。



#### 样式方案的选择与取舍

**样式方案取舍**：是在全局样式、CSS Modules、原子化 CSS（atomic CSS）与 CSS-in-JS 之间按项目约束作选择，依据是隔离性、构建开销与服务端组件的兼容性。

- 原子化 CSS：每个类名对应一条声明，产物只包含用到的声明，适合统一视觉规范。
- CSS-in-JS：样式写在 JavaScript 中，部分方案依赖运行时注入，接入服务端组件前需确认方案支持（详见本主题第 9 篇 Next.js 进阶：服务端组件与流式渲染）。
- 隔离性：CSS Modules 与原子化 CSS 都避免全局类名污染，选择时更应关注团队熟悉度。
- 迁移成本：方案一旦铺开，替换成本很高，新项目阶段再定更省力。

```tsx
// 原子化写法的组件：类名直接表达样式
export function PriceTag({ amount }: { amount: number }) {
  return <span className="text-lg font-semibold text-red-600">{amount}</span>;
}
```

> [!TIP]
> **建议内容**：需要跨端复用同一套视觉规范时，先抽出设计令牌（design token）作为变量，再让各样式方案引用，避免样式值散落在组件里。

**速记**：样式方案的取舍看隔离性、构建开销与是否支持服务端组件。



#### 图片与字体优化

**图片与字体优化**：是在构建与请求阶段自动处理这两类体积大户，前者按需生成尺寸与格式，后者自托管以避免外部请求与布局偏移。

- 图片组件：next/image 导出的 Image 组件在构建期与请求期生成多尺寸产物，默认懒加载并预留占位空间。
- 关键图：首屏关键图片标记为优先加载，避免被懒加载推迟。
- 字体：next/font 在构建期下载并自托管字体文件，同时计算回退字体以减少布局偏移。
- 尺寸声明：图片组件要求给出宽高或填充模式，缺少尺寸会导致布局计算失效。

```tsx
import Image from "next/image";

export function CoverImage() {
  return (
    <Image src="/cover.png" alt="文章封面" width={640} height={360} priority />
  );
}
```

> 图片组件同时负责尺寸生成、格式选择与懒加载，手写 img 标签只能得到原图，需要自行补齐这些能力。

**速记**：图片组件按需生成尺寸并懒加载，字体组件自托管以减少外部请求与布局偏移。



#### 静态资源与 public 目录

**public 目录**：是原样拷贝到站点根路径的静态资源目录，其中的文件不参与打包与哈希处理，通过以斜杠开头的路径直接访问。

- 访问路径：public/logo.svg 对应站点根下的 /logo.svg。
- 缓存处理：文件内容不变则路径不变，浏览器缓存需要自行通过响应头控制。
- 参与构建的资源：需要哈希文件名或体积优化时改用模块导入，交给构建器处理。
- 命名建议：公共静态资源使用稳定路径，带版本的文件放进子目录便于整体替换。

```tsx
// public/logo.svg 通过 /logo.svg 直接访问
export function Brand() {
  return (
    <img src="/logo.svg" alt="品牌标识" width={120} height={32} />
  );
}
```

> public 中的资源不经过哈希，发布新版本后旧文件仍可能被浏览器缓存命中，更新频繁的资源应走模块导入让文件名带哈希。

**速记**：public 按原样与固定路径提供资源，需要哈希与优化的资源走模块导入。



### 中间件与请求处理

本节处理请求进入渲染之前的环节：什么逻辑放在中间件、中间件的能力边界在哪、接口如何在同一工程内实现，以及 Cookie 与重定向如何配合。

#### 中间件与匹配规则

**中间件（middleware）**：是在请求到达页面或接口之前执行的函数，定义在项目根目录的 middleware.ts 中，通过导出的匹配配置限定生效路径。

- 文件位置：与 app 目录同级的 middleware.ts，一个项目只保留一个。
- 匹配配置：导出的 config 对象的 matcher 字段声明生效路径，支持路径参数写法。
- 执行时机：每个匹配的请求在渲染之前执行一次，同一请求只执行一次。
- 返回行为：返回响应对象则直接结束请求，返回继续指令则进入后续渲染。

```ts
// middleware.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const token = request.cookies.get("session");
  if (!token) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = { matcher: ["/dashboard/:path*"] };
```

> 中间件适合做每个请求都要做一次的轻量判定；登录态的完整设计详见本主题第 12 篇 SSR 应用的鉴权、状态与安全。

**速记**：中间件在渲染前按匹配规则执行一次，返回响应即短路请求。



#### 中间件的能力边界

**能力边界**：是中间件运行环境的固有限制，它运行在边缘运行时，可用的接口与 Node.js 运行时并不相同。

- 运行时差异：边缘运行时面向短时、低延迟的执行，不提供完整的 Node.js 接口。
- 不可直接访问：数据库连接、文件系统读写等操作不适合放在中间件里。
- 适合的场景：读取 Cookie 与请求头、设置响应头、重定向、路径改写。
- 超出的处理：需要查库判断的逻辑放到渲染层或路由处理程序中。

```ts
// middleware.ts：只做基于请求头的轻量标记
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const response = NextResponse.next();
  response.headers.set("x-request-path", request.nextUrl.pathname);
  return response;
}
```

> [!WARNING]
> **警告内容**：在中间件里执行数据库查询或大量计算会显著抬高每个请求的延迟，还可能让下游服务被不当调用，应把这类逻辑下沉到渲染层。

**速记**：中间件跑在边缘运行时，只做轻量判定，查库与重计算下沉到渲染层。



#### 路由处理程序

**路由处理程序（Route Handler）**：是在 App Router 中用 route.ts 文件定义的接口实现，按目录约定映射到对应路径，用标准请求与响应对象收发数据。

- 文件约定：目录下的 route.ts 导出以 HTTP 方法命名的大写函数。
- 参数签名：处理函数接收请求对象，另有包含路径参数的上下文参数。
- 返回方式：返回响应对象，可直接返回 JSON 或流式响应。
- 与页面共存：同一目录可以同时存在页面与路由处理程序，但同名路径会冲突。

```ts
// app/api/articles/[id]/route.ts
import { NextResponse } from "next/server";

export async function GET(
  request: Request,
  context: { params: Promise<{ id: string }> },
) {
  const { id } = await context.params;
  return NextResponse.json({ id, title: "示例文章" });
}
```

> 路由处理程序中的路径参数在较新版本中返回 Promise，取值需要 await；升级时留意这一变化。

**速记**：目录下的 route.ts 按目录映射为接口，导出对应 HTTP 方法的函数。



#### Cookie 与重定向、重写

**响应改写手段**：是对请求与响应施加的三类操作，分别是读写 Cookie、把请求重定向到新地址、把请求重新映射到另一个内部路径。

- Cookie 读取：从请求对象读取，用于判断登录态与语言偏好。
- Cookie 写入：在响应对象上设置，可同时声明有效期与作用范围。
- 重定向：让浏览器换一个地址重新发起请求，地址栏随之改变。
- 重写：在服务端把请求映射到另一路径，地址栏不变，适合灰度与本地化。

```ts
// middleware.ts：按语言偏好重写请求路径
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const locale = request.cookies.get("locale")?.value ?? "zh";
  const target = `/${locale}${request.nextUrl.pathname}`;
  return NextResponse.rewrite(new URL(target, request.url));
}
```

> 重定向与重写混用容易形成循环，设置前先确认目标路径不会再命中同一条匹配规则，否则请求会反复跳转直至报错。

**速记**：Cookie 做状态读写，重定向改地址栏，重写在服务端换路径且地址栏不变。



### 渲染模式与运行时配置

本节说明在 Next.js 中如何为路由选择渲染方式、如何选择运行时、环境变量在什么阶段注入，以及配置文件承担哪些职责。

#### 按路由选择静态与动态渲染

**按路由选择渲染**：是按路由段生效的默认行为加显式声明，路由在没有动态来源时于构建期静态生成，出现动态来源时转为每次请求渲染。

- 默认静态：不使用请求相关接口且未声明动态的路由，在构建期生成静态产物。
- 转为动态：读取请求头、Cookie，或声明为动态渲染的路由，改为每次请求生成。
- 显式控制：可在页面或布局文件顶层导出再验证周期与渲染方式两个配置值。
- 粒度：静态与动态按路由段生效，同一应用可以两种并存。

```ts
// app/blog/page.tsx
export const revalidate = 60;
// export const dynamic = "force-dynamic"; // 需要每次请求渲染时改用这一行

export default async function BlogPage() {
  return <h1>博客列表</h1>;
}
```

> 缓存与再验证在数据层的行为详见本主题第 8 篇 Next.js 数据获取与缓存；此处只讨论渲染方式的选择。

**速记**：默认静态、出现动态来源即转动态，也可用顶层导出显式指定。



#### 运行时选择与边缘运行时

**运行时（runtime）**：是执行服务端代码的环境，Next.js 提供面向完整 Node.js 接口的默认运行时与面向边缘节点的边缘运行时两种选择。

- 默认运行时：可使用完整 Node.js 接口，适合数据库驱动、文件处理等依赖原生模块的代码。
- 边缘运行时：启动快、分布广，接口是 Web 标准的子集，不支持原生模块。
- 声明方式：在页面或布局文件顶层导出运行时名称，未声明时使用默认值。
- 选择依据：依赖 Node.js 原生模块的代码必须留在默认运行时。

```ts
// app/edge/page.tsx
export const runtime = "edge";

export default function EdgePage() {
  return <p>在边缘运行时渲染的页面</p>;
}
```

> [!IMPORTANT]
> **重要内容**：运行时按路由段声明并向子路由继承，在布局上声明边缘运行时会连带约束其下所有页面，选择前先确认子树中是否有人依赖 Node.js 原生模块。

**速记**：默认运行时提供完整 Node.js 接口，边缘运行时接口受限但启动更快。



#### 环境变量与注入时机

**环境变量**：是由构建或运行环境提供的配置值，Next.js 按前后端可见性分成两类，注入时机决定它们在什么阶段被读取。

- 服务端变量：只在服务端代码中可读，适合密钥与数据库地址。
- 公开变量：以固定前缀命名的变量会被编译进客户端产物，前端代码可读。
- 注入时机：构建期读取的变量在构建时固化，运行期读取的变量在进程启动时生效。
- 常见错误：把密钥写成公开前缀，值会被打进浏览器可下载的文件。

```bash
# .env.local
API_BASE_URL=https://api.example.com
# 上一行仅服务端可读
NEXT_PUBLIC_SITE_NAME=学习库
# 上一行会进入客户端产物
```

> 判断一个变量该不该下发，只需问它在浏览器里被读到会不会造成损失；会造成损失的一律留在服务端。

**速记**：服务端变量不下发，公开前缀的变量会被编译进客户端产物。



#### next.config 的常见配置

**next.config**：是项目根目录下的框架配置文件，负责声明构建与运行期的框架级行为，与业务代码分离。

- 文件格式：next.config.ts 或 next.config.js，导出配置对象。
- 常见用途：登记远程图片来源、声明路径重写与重定向、设置输出模式、接入构建插件。
- 类型支持：用 TypeScript 编写时可以获得配置项的类型提示。
- 慎改原则：默认值适用大多数项目，逐项添加并说明原因，避免堆积无法解释的配置。

```ts
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // 登记允许图片组件处理的远程图片来源
  images: { remotePatterns: [{ protocol: "https", hostname: "cdn.example.com" }] },
  // 产出便于自托管的独立产物
  output: "standalone",
};

export default nextConfig;
```

> 配置文件只写框架行为，业务开关放进环境变量，两类配置的变更代价不同，混在一起会让排查变难。

**速记**：next.config.ts 管框架级行为，逐项添加并写明用途。



### 部署方式与自托管

本节把工程配置落到运行环境：产物形态与部署方式如何对应、自托管需要准备什么、缓存如何与 CDN 协同，以及部署前应当做哪些校验。

#### 部署形态与产物关系

**部署形态**：是承载应用的运行方式，由框架的输出模式决定，常见类别为容器化 Node 服务、无服务器函数与静态托管三类。

- 容器化 Node 服务：以常驻进程运行，支持全部服务端能力，需要自行负责扩缩容与进程管理。
- 无服务器函数：按请求执行，免运维，但冷启动与执行时长存在约束。
- 静态托管：只产出静态文件，动态能力不可用，需确认所有路由都可预渲染。
- 对应关系：产物里是否包含服务端运行时代码，决定了能否走静态托管。

```bash
npm run build
# 构建输出会标注每个路由的渲染方式
# ○ (Static) prerendered as static content
# ƒ (Dynamic) server-rendered on demand
```

> 判断能否静态托管只看一条：所有路由是否都能在构建期产出静态内容；存在任一动态路由时静态托管不可行。

**速记**：产物含服务端代码就走容器或无服务器，全部可预渲染才可静态托管。



#### standalone 产物与 Node 服务自托管

**standalone 产物**：是框架提供的一种精简输出，只包含运行所需的最少依赖文件，便于复制到镜像中直接启动。

- 生成方式：在配置中把输出模式设为 standalone，构建后得到独立目录。
- 目录内容：服务端代码与所需依赖，静态资源则需按产物说明另行复制。
- 启动方式：用 Node 运行产物中的入口文件，端口由环境变量指定。
- 补充文件：public 目录与构建期生成的静态资源目录要放到约定位置。

```bash
npm run build
# 把产物目录与静态资源按官方说明复制进镜像
node server.js
# Server listening on http://localhost:3000
```

> [!TIP]
> **建议内容**：容器镜像只在构建阶段安装开发依赖，运行阶段只保留 standalone 产物与生产依赖，可显著缩小镜像体积并减少暴露面。

**速记**：standalone 只带最少依赖，复制到镜像后用 Node 直接启动。



#### 缓存与 CDN 协同

**缓存协同**：是页面产物、数据缓存与 CDN 三层缓存的分工，配置不一致会让内容更新延迟或反复回源。

- 页面产物：静态路由产出可被 CDN 缓存的文件。
- 数据缓存：服务端数据获取的缓存与再验证周期决定内容新鲜度。
- CDN 层：响应头中的缓存指令决定边缘节点保留多久，需与再验证周期对齐。
- 失效路径：更新内容后若 CDN 仍返回旧文件，优先检查响应头与再验证配置是否一致。

```ts
// 用响应头显式声明缓存策略
export async function GET(): Promise<Response> {
  const headers = {
    "Cache-Control": "public, s-maxage=60, stale-while-revalidate=300",
  };
  return new Response(JSON.stringify({ ok: true }), { headers });
}
```

> [!WARNING]
> **警告内容**：把带用户信息的页面交给 CDN 缓存会造成用户之间互相看到对方数据，凡是按登录态渲染的响应都必须避免公开缓存。

**速记**：页面缓存、数据缓存与 CDN 缓存必须对齐，按登录态渲染的响应不得公开缓存。



#### 部署前的构建校验与常见问题

**部署前校验**：是在本地或流水线中用生产模式构建并启动一次，提前暴露只在生产环境出现的问题。

- 完整构建：以生产模式执行构建与启动，验证类型检查与构建期数据获取。
- 关键路径：逐一访问首页、动态路由与接口，确认渲染方式与预期一致。
- 环境变量：按目标环境补齐变量，确认服务端变量未被打进客户端产物。
- 常见问题：动态接口在静态导出时不可用、远程图片未登记、运行时声明与依赖不匹配。

```bash
npm run build
npm run start
```
