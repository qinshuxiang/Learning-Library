## SEO 与首屏性能

### 搜索引擎如何抓取与索引

搜索引擎优化（search engine optimization，SEO）讨论的是内容如何被爬虫发现、读懂并纳入索引。本模块先说明抓取与索引的流程、渲染发生的时机，以及内容可被抓取的前提。

#### 抓取与索引的基本流程

**抓取与索引的基本流程**：是爬虫发现网址、请求页面、解析内容并把结果写入索引供检索使用的一串环节，每个环节都可能成为内容不被收录的原因。

- 发现：爬虫从已知网址、站点地图与站内链接出发，收集待抓取的地址。
- 抓取：向地址发起请求，取回响应状态与响应体，按规则决定是否继续深入。
- 渲染：对依赖脚本生成内容的页面，按需要执行脚本来取得最终结构。
- 索引：把解析出的正文、标题与链接写入索引，检索时据此匹配与排序。
- 状态影响：响应状态码与页面质量决定抓取频率与是否继续抓取站内其它链接。

```bash
# 用命令行请求检查服务端是否直接返回了正文
curl -s https://example.com/articles | grep -o "最新文章"
# 最新文章
```

```text
抓取与索引的链路
发现网址 → 请求页面 → 解析内容 → 渲染脚本 → 写入索引 → 参与检索
```

> 服务端渲染的价值在于让「解析内容」这一步就能拿到正文，而不必依赖后续的脚本渲染环节（模式对比详见本主题第 2 篇 客户端渲染与服务端渲染）。

**速记**：抓取与索引依次经过发现、请求、渲染、入库，任一步受阻都会影响收录。



#### 渲染发生的时机

**渲染发生的时机**：指页面的可见内容是在服务端请求时生成，还是等脚本在客户端执行后才生成，这个时机直接决定抓取方能否在解析阶段读到内容。

- 服务端生成：响应体内即含正文，解析阶段就能读取，不依赖脚本执行。
- 客户端生成：响应体多为空容器，正文要等脚本取数后写入，抓取成本更高。
- 混合形态：首屏骨架由服务端产出，局部细节由客户端补齐，正文仍可被抓取。
- 差异根源：内容出现的位置不同，抓取方需要付出的等待与执行程度也不同。
- 结论取向：以内容传播为目标的页面，应让主要内容在服务端响应中就已存在。

```tsx
// 服务端组件：正文随响应到达，抓取方无需执行脚本即可读取
export default async function ArticlePage({ params }: { params: { id: string } }) {
  const article = await getArticleById(params.id);
  return (
    <article>
      <h1>{article.title}</h1>
      <p>{article.summary}</p>
    </article>
  );
}
```

> [!IMPORTANT]
> **重要内容**：把正文完全交给客户端脚本生成，会让内容依赖抓取方的脚本执行能力与等待策略，收录结果因此不可控。

**速记**：内容在服务端生成时抓取方解析即可读到，客户端生成则依赖脚本执行。



#### 内容可被抓取的前提

**内容可被抓取的前提**：是页面允许被抓取、链接可被跟随、正文以可解析的形式出现在响应或渲染结果中，三者同时满足才能进入索引。

- 抓取许可：站点抓取规则文件需放行目标路径，被禁止的路径不会被抓取。
- 链接可达：站内导航使用可跟随的链接，而不是只能通过脚本点击才生成的地址。
- 正文可读：正文不依赖用户操作（如点击展开）才出现在结构中。
- 结构清晰：用恰当的语义化结构组织标题与段落，解析方更容易判断主次。
- 状态正常：目标地址返回正常状态，而非跳转或错误状态。

```html
<!-- 可跟随的站内链接：地址直接写在响应中，抓取方可沿链接深入 -->
<a href="/articles/1024">同构渲染原理</a>
```

```tsx
// 用语义化结构标注主次，标题层级与内容层级一致
export function ArticleHeader({ title, author }: { title: string; author: string }) {
  return (
    <header>
      <h1>{title}</h1>
      <p>作者：{author}</p>
    </header>
  );
}
```

> 结构语义化属于标记语言本身的话题，详见 前端/HTML 主题；此处只需确认正文与标题在响应中即可分辨。

**速记**：放行抓取、链接可跟随、正文可解析，三者齐备内容才可能被收录。



#### 抓取与索引的常见问题

**抓取与索引的常见问题**：是内容明明存在却未被收录或收录质量不佳的一组典型情形，多数与内容出现时机和页面结构有关。

- 空容器页面：响应中只有脚本引用与空容器，正文全靠脚本生成。
- 内容需交互：正文藏在标签页、折叠面板或点击加载之后，默认状态为空。
- 重复内容：多个地址输出同一内容而未声明首选地址，权重被分散。
- 跳转链过长：为替代地址设置多层跳转，增加抓取成本。
- 屏蔽过度：抓取规则误伤了脚本或样式资源，使渲染环节无法还原页面。

```html
<!-- 问题写法：正文位置只有空容器，解析阶段读不到内容 -->
<div id="app"></div>
<script src="/static/client.js"></script>
```

```html
<!-- 改进写法：正文随响应下发，脚本只负责接管交互 -->
<article id="app">
  <h1>同构渲染原理</h1>
  <p>同构渲染是同一套代码在服务端产出 HTML、在客户端接管交互的渲染方式。</p>
</article>
<script src="/static/client.js" defer></script>
```

> 排查顺序建议先看响应体里有没有正文，再看抓取规则有没有误伤资源，最后检查是否存在重复地址。

**速记**：空容器、需交互才出现的内容与重复地址是收录不佳的主要来源。



### 元信息与结构化数据

元信息决定页面在检索结果与社交分享中的呈现，结构化数据帮助检索方理解内容类型。本模块给出四类常用元信息与声明方式。

#### 标题与描述

**标题与描述**：是页面在检索结果中最常被展示的两段文本，标题说明页面主题，描述概括页面内容，二者应逐页唯一且贴合正文。

- 标题唯一：同一站点的不同页面使用不同标题，避免多页共用同一标题。
- 描述准确：描述写实质内容，不堆砌关键词，长度控制在可完整展示的范围。
- 与正文一致：标题与描述反映页面实际内容，夸大或错配会降低可信度。
- 动态生成：列表页与详情页按数据生成标题与描述，而非套用站点统一文案。
- 分级覆盖：站点可设默认值，具体页面再逐级覆盖。

```tsx
// app/articles/page.tsx：为单个页面声明标题与描述
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "文章列表",
  description: "按时间排列的全部文章，支持按标签筛选与关键词检索。",
};
```

```tsx
// 动态页面按数据生成，标题逐条不同
export async function generateMetadata({ params }: { params: { id: string } }) {
  const article = await getArticleById(params.id);
  return {
    title: article.title,
    description: article.summary,
  };
}
```

> 标题与描述的生成依赖首屏数据，因此这类声明通常放在与服务端数据获取相同的环节（数据获取详见本主题第 8 篇 Next.js 数据获取与缓存）。

**速记**：标题逐页唯一、描述贴合正文，并可按数据动态生成。



#### 社交分享用的元信息

**社交分享用的元信息**：是页面在被分享到聊天工具与社交平台时用于生成卡片标题、摘要与缩略图的声明，与检索结果用的元信息相互独立。

- 卡片标题与摘要：分享方按这些声明生成卡片正文，缺省时回退到页面标题。
- 缩略图：指定一张能代表页面的图片，尺寸与比例影响卡片呈现效果。
- 页面类型与站点名：声明内容类型与站点标识，帮助分享方选择卡片样式。
- 完整地址：声明页面的规范地址，避免分享链接带上一串追踪参数。
- 独立配置：同一页面可在检索元信息之外单独声明分享用内容。

```tsx
export const metadata: Metadata = {
  title: "文章列表",
  description: "按时间排列的全部文章。",
  openGraph: {
    title: "文章列表",
    description: "按时间排列的全部文章，支持按标签筛选。",
    images: ["/og/articles.png"],
    type: "website",
  },
};
```

> 分享卡片的呈现效果由接收方决定，声明内容只提供素材，不保证最终样式与之一致。

**速记**：分享元信息独立于检索元信息，主要提供标题、摘要与缩略图素材。



#### 结构化数据与富媒体结果

**结构化数据与结构化结果**：是用约定的字段描述页面内容类型与关键属性，使检索方能识别出文章、商品、问答等结构并生成更丰富的展示结果。

- 字段约定：按公开的词汇表声明内容类型、标题、作者、发布时间等字段。
- 呈现形式：可用于生成带评分、时间、作者等附加信息的展示条目。
- 与可见内容一致：声明的内容必须与页面上真实可见的内容相符。
- 序列化方式：常以内嵌脚本块的形式随页面下发，解析方读取该脚本块。
- 分类型声明：文章、商品、活动各自使用对应的内容类型与必填字段。

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "同构渲染原理",
  "datePublished": "2026-09-13",
  "author": { "@type": "Person", "name": "Ada" }
}
</script>
```

> [!WARNING]
> **警告内容**：结构化数据声明与页面可见内容不符，属于误导性声明，可能导致展示资格被取消，必须以真实内容填写字段。

**速记**：结构化数据按公开词汇表描述内容类型，且必须与可见内容一致。



#### 站点地图与规范化声明

**站点地图与规范化声明**：前者列出站点希望被收录的地址与更新时间，后者为内容相同的多个地址指定唯一首选地址，两者共同降低抓取与收录的歧义。

- 站点地图：集中列出希望被索引的页面及其更新时间，帮助抓取方发现深层页面。
- 规范地址：内容相同时指定唯一首选地址，避免权重分散到多条地址。
- 分页与筛选：带参数的筛选与排序地址可声明规范地址指回主列表页。
- 自动生成：站点地图可由应用按路由与数据自动生成，避免人工维护遗漏。
- 抓取规则配合：抓取规则文件放行被收录路径，与站点地图保持一致。

```ts
// app/sitemap.ts：由路由与数据自动生成站点地图
import type { MetadataRoute } from "next";

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    { url: "https://example.com/", lastModified: new Date(), priority: 1 },
    { url: "https://example.com/articles", lastModified: new Date(), priority: 0.8 },
  ];
}
```

```tsx
// 为筛选后的地址声明规范地址，指回主列表页
export const metadata: Metadata = {
  alternates: { canonical: "https://example.com/articles" },
};
```

> 站点地图是「邀请抓取」，规范声明是「说明首选」，两者解决的是不同方向的歧义。

**速记**：站点地图负责发现，规范声明负责指定首选地址，二者共用一套地址口径。



### 首屏性能指标

首屏性能指标把「快到什么程度」翻译成可测量的时间与数值，用于判断优化是否有效。本模块介绍四组常用指标的含义与观测方式。

#### 首次字节时间

**首次字节时间（Time to First Byte，TTFB）**：是从发起请求到收到响应第一个字节所经历的时间，反映服务端处理与网络往返的合计耗时。

- 构成：包含网络往返、服务端排队与处理、应用生成首屏响应的时间。
- 意义：它是后续所有首屏指标的起点，起点偏高会整体推后其余指标。
- 观测：可从导航计时中取响应开始与请求开始之差。
- 关注点：服务端渲染的页面若数据等待过长，该指标会明显偏高。
- 优化方向：减少串行请求、缩短服务端处理链路、就近分发内容。

```ts
// 从导航计时中读取首次字节时间
const [nav] = performance.getEntriesByType("navigation") as PerformanceNavigationTiming[];
console.log(nav.responseStart - nav.requestStart);   // 毫秒
```

> 该指标只描述响应开始到达的时间，不代表内容已经可见，需要与后续指标一起解读。

**速记**：首次字节时间衡量响应第一个字节到达的耗时，是首屏链路的起点。



#### 首次内容绘制与最大内容绘制

**首次内容绘制（First Contentful Paint，FCP）**：是页面首次绘制出任意文本或图像内容的时间点。**最大内容绘制（Largest Contentful Paint，LCP）**：是视口内最大块内容完成绘制的时间点，通常用来代表主要内容的可见速度。

- 首次内容绘制：回答「用户何时看到第一点内容」，用来判断是否白屏过久。
- 最大内容绘制：回答「主要内容何时可见」，比首次内容绘制更贴近用户感受。
- 影响因素：服务端响应速度、资源加载顺序与渲染阻塞资源都会影响这两个时间点。
- 常见拖累：大图未压缩、字体延迟、首屏关键样式被后置都会推迟它们。
- 观测：可用性能观察接口订阅对应条目，记录每次变化。

```ts
// 订阅最大内容绘制，记录主要内容可见的时间点
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log("主要内容可见于", last.startTime, "毫秒");
}).observe({ type: "largest-contentful-paint", buffered: true });
```

```html
<!-- 预加载首屏关键字体，减少文字延迟出现 -->
<link rel="preload" as="font" href="/fonts/serif.woff2" crossorigin>
```

> 服务端渲染把正文随响应送达，主要内容的可见时间主要取决于响应速度与关键资源，而不是脚本执行。

**速记**：首次内容绘制看是否白屏，最大内容绘制看主要内容何时可见。



#### 交互延迟指标

**交互延迟指标（Interaction to Next Paint，INP）**：是页面在用户交互后到界面给出下一次绘制之间的延迟，反映交互的响应是否及时。

- 定义口径：统计整个访问期间各次交互的响应延迟，取其中的高位值。
- 常见成因：主线程被长任务占满、脚本解析与执行过重、渲染与状态更新过多。
- 与水合相关：水合阶段的主线程工作会直接影响首批交互的响应速度（机制详见本主题第 5 篇 水合机制与常见问题）。
- 观测：订阅交互相关条目并按元素与耗时归类，定位最慢的交互点。
- 优化方向：拆分长任务、推迟非关键脚本、缩小首屏需要接管的组件范围。

```ts
// 订阅交互延迟条目，按耗时排查最慢的交互
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.duration);   // 事件类型与延迟毫秒数
  }
});
observer.observe({ type: "event", buffered: true });
```

> 页面可见不代表可交互，交互延迟指标衡量的正是「看得见但点不动」这段体验。

**速记**：交互延迟衡量交互到下一次绘制的耗时，主线程长任务是主要成因。



#### 布局稳定性指标

**布局稳定性指标（Cumulative Layout Shift，CLS）**：是页面在整个加载过程中因元素位置意外变动而累积的偏移分数，用来衡量内容的视觉稳定程度。

- 计分方式：统计每次可见元素位置变化对分数的影响并累加。
- 常见成因：未预留尺寸的图片与广告、后插入的内容、字体替换引起的行高变化。
- 与水合相关：水合后由客户端替换占位内容，若尺寸不同会造成可见位移。
- 观感影响：内容跳动会让用户误点，也会打断阅读。
- 优化方向：为媒体预留尺寸、避免在已有内容上方插入元素、固定字体度量。

```css
/* 为媒体预留比例，加载前后占据同一空间 */
.hero-media {
  aspect-ratio: 16 / 9;
  width: 100%;
}
```

```css
/* 为字体预留回退度量，减少字体替换引起的跳动 */
@font-face {
  font-family: "SerifText";
  src: url("/fonts/serif.woff2") format("woff2");
  font-display: swap;
  size-adjust: 100%;
}
```

> [!CAUTION]
> **注意内容**：两段式渲染若让占位与真实内容的尺寸差距过大，水合完成瞬间会出现明显位移，应让两者占据相近空间。

**速记**：布局稳定性衡量内容意外位移的累积，靠预留尺寸与固定度量改善。



### SSR 场景的性能优化

服务端渲染已经把正文提前送到，性能优化的重点就落在服务端响应、关键资源、呈现方式与缓存四方面。本模块按这四方面给出可落地的做法。

#### 缩短服务端响应时间

**缩短服务端响应时间**：是压缩服务端从收到请求到产出首个字节的耗时，直接决定首次字节时间与后续所有指标的起点。

- 并行取数：同一页面内彼此独立的请求并行发起，把总耗时压到最慢的一路。
- 减少往返：把多次串行的接口调用合并或下沉到服务端直连数据源。
- 控制渲染量：首屏只渲染必要内容，长列表按需分段或延后渲染。
- 尽早输出：先送出页面骨架与头部，再逐步补齐数据依赖的部分。
- 复用连接：保持与数据源的长连接与连接池，减少重复握手开销。

```tsx
// 并行取回互不依赖的数据，避免串行等待叠加
export default async function DashboardPage() {
  const [profile, orders, notice] = await Promise.all([
    getProfile(),
    getRecentOrders(),
    getNotice(),
  ]);
  return <Dashboard profile={profile} orders={orders} notice={notice} />;
}
```

> [!WARNING]
> **警告内容**：对携带用户身份的首屏响应不能按公共内容缓存，否则会把一个人的数据下发给另一个人，个性化内容必须走不缓存或按用户区分的策略。

**速记**：并行取数、减少往返、尽早输出，是压缩服务端响应的主要手段。



#### 关键资源与加载优先级

**关键资源与加载优先级**：是让首屏渲染必需的资源尽早开始加载、把非必需资源推迟，从而缩短内容可见时间。

- 关键样式：首屏所需样式应内联或优先加载，避免样式到位前内容以错乱形态显示。
- 关键字体：首屏正文用字体提前加载，其余字重按需取用。
- 图片策略：首屏主图优先加载并声明尺寸，视口外图片延后加载。
- 脚本策略：非关键脚本延迟或异步加载，避免阻塞内容解析。
- 优先级提示：对首屏关键资源给出高优先级提示，帮助浏览器调整取用顺序。

```html
<!-- 首屏关键样式内联，其余样式异步加载 -->
<style>main { max-width: 72ch; margin: 0 auto; }</style>
<link rel="stylesheet" href="/styles/extra.css" media="print" onload="this.media='all'">
```

```html
<!-- 首屏主图优先加载并声明尺寸，避免位移与延迟 -->
<img src="/images/hero.jpg" width="1200" height="675" fetchpriority="high" alt="首屏主图">
```

> 资源优先级的本质是排序：总带宽与主线程时间有限，把有限的资源先给首屏关键内容。

**速记**：关键样式与字体优先、首屏主图声明尺寸、非关键脚本延后，是资源侧的排序原则。



#### 流式输出与渐进呈现

**流式输出与渐进呈现**：是服务端先送出已完成的页面骨架与内容、再随着数据就绪补齐后续部分，让用户先看到可用内容再看到完整内容。

- 分块送达：响应按块陆续到达，浏览器可先解析并渲染已到达的部分。
- 骨架先行：先输出不依赖数据的布局与标题，主要内容随后补齐。
- 局部回退：处于等待中的区域显示占位，就绪后替换为真实内容。
- 收益：首次内容绘制明显提前，用户感知的等待缩短。
- 代价：流式输出对缓存与错误处理的要求更高，出错重试的空间更小。

```tsx
import { Suspense } from "react";

export default function Page() {
  return (
    <main>
      <h1>最新文章</h1>
      <Suspense fallback={<p>正在加载文章…</p>}>
        <ArticleList />
      </Suspense>
    </main>
  );
}
```

```tsx
// ArticleList 在服务端取数，就绪后替换 Suspense 的占位内容
async function ArticleList() {
  const articles = await getArticles();
  return <ul>{articles.map((item) => <li key={item.id}>{item.title}</li>)}</ul>;
}
```

> 流式输出在渲染模式与组件模型中的完整机制，详见本主题第 9 篇 Next.js 进阶：服务端组件与流式渲染；此处只从首屏呈现的角度使用它。

**速记**：流式输出先送骨架与就绪内容，再逐步补齐，用分块送达换取更早的可见时间。



#### 缓存与分发

**缓存与分发**：是把可以复用的响应或数据结果保存在离用户更近的位置，减少每次请求都重新渲染与重新取数的开销。

- 页面缓存：对公共页面按时间窗口缓存整个响应，命中时直接返回。
- 数据缓存：对变化不频繁的数据结果缓存并按时间窗口失效（策略详见本主题第 8 篇 Next.js 数据获取与缓存）。
- 就近分发：把静态资源与可缓存响应放到离用户更近的节点，缩短网络往返。
- 失效策略：设置合理的过期时间与后台刷新，兼顾新鲜度与命中率。
- 区分内容：公共内容可缓存，个性化内容不可缓存，两类内容使用不同策略。

```json
{
  "Cache-Control": "public, s-maxage=60, stale-while-revalidate=300"
}
```

```text
缓存分层
浏览器缓存 → 就近节点缓存 → 应用数据缓存 → 数据源
逐层命中即逐层省下渲染与取数的开销
```

```js
// 只对公共内容启用缓存，个性化响应绕过缓存
export function buildCachePolicy(isPersonalized) {
  if (isPersonalized) return "private, no-store";
  return "public, s-maxage=60, stale-while-revalidate=300";
}
```

> 缓存的收益与风险同源：命中率越高越省，但要确保不会把带身份的内容错发给他人。

**速记**：页面与数据分别缓存、就近分发、按内容类型定策略，命中即可省下渲染开销。
