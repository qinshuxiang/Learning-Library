## Taro 跨端开发

**Taro**：是面向多端的统一开发框架，用 React 等前端框架的语法编写，经编译产出 Web、多个小程序平台与原生应用等多端产物。

本篇回答四件事：Taro 是什么、项目结构与路由怎么组织、多端构建的原理是什么、它与 uni-app 如何取舍。跨端方案的总体选型详见本主题第 13 篇 跨端开发概览与方案选型，小程序的内置组件与基础 API 详见本主题第 15 篇 小程序开发：页面、组件与 API，本篇不重复。

### Taro 是什么

本节确立 Taro 的定位：它以 React 组件模型为编写基础，把编译期转换作为跨端的主要手段，理解这一点是后续所有约定的前提。

#### Taro 的定位

**Taro**：是以 React 组件为基本编写单位、通过编译把同一份源码转换为多个目标端运行形态的跨端框架。

- 编写基础：以组件为单位编写界面，模板部分用 JSX 表达，配合 TypeScript 做类型检查。
- 基础元素：界面由框架提供的跨端组件搭建，而非直接使用浏览器标签。
- 编译产物：小程序端产出代码包，Web 端产出静态资源，原生应用端产出前端资源。
- 差异隔离：确需分端的逻辑用条件判断或编译标记隔离，其余代码各端共用。

```tsx
import { useState } from "react";
import { View, Text, Button } from "@tarojs/components";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <View className="counter">
      <Text>{count}</Text>
      <Button onClick={() => setCount(count + 1)}>加一</Button>
    </View>
  );
}
```

> 跨端组件不是浏览器元素的别名：它由框架映射到各端实现，因此部分浏览器专有属性与事件并不可用。

**速记**：Taro 用 React 组件统一编写，基础元素由框架提供，靠编译产出多端产物。



#### 编译时方案与运行时方案

**编译时方案**：是在编译阶段把组件与语法转换为目标端原生代码。**运行时方案**：是在产物中携带适配层、在运行时解释执行组件与接口调用。

- 编译时：产物接近手写代码，体积更小，平台兼容性由编译期决定。
- 运行时：产物携带适配运行时代码，对框架语法的支持更灵活，体积略大。
- 选择方式：可在项目配置中选用方案，新项目通常优先编译时方案。
- 影响面：方案决定产物形态、包体大小与部分语法的可用范围。

```js
// config/index.js：编译配置的总体结构（字段以官方文档为准）
module.exports = {
  compiler: { type: "webpack5" },
  mini: {
    /* 小程序端编译配置 */
  },
  h5: {
    /* Web 端编译配置 */
  },
};
```

> 两种方案并非纯优劣关系：语法灵活性与产物体积在多数项目中需要权衡。

**速记**：编译时把语法转成原生代码，运行时在产物里解释执行，按项目需要选择。



#### 与 React 生态的关系

**React 生态**：指 Taro 复用 React 的组件模型与状态管理思路，业务层写法与 Web 端 React 项目接近。

- 组件模型：函数组件与 Hooks 是主要编写方式。
- 状态管理：可用社区通用方案组织跨页面共享状态。
- 类型检查：配合 TypeScript 获得组件属性与接口数据的类型约束（详见 前端/TypeScript 主题第 1 篇 TypeScript 简介与编写方式）。
- 边界：跨端渲染不提供完整的浏览器 DOM 能力，依赖 DOM 的第三方库需先评估。

```tsx
import { useState, useEffect } from "react";
import { View } from "@tarojs/components";
import Taro from "@tarojs/taro";

export default function ArticleList() {
  const [titles, setTitles] = useState<string[]>([]);

  useEffect(() => {
    Taro.request({ url: "https://api.example.com/articles" }).then((res) => {
      setTitles(res.data.map((item: { title: string }) => item.title));
    });
  }, []);

  return (
    <View>
      {titles.map((title) => (
        <View key={title}>{title}</View>
      ))}
    </View>
  );
}
```

> 语法一致只解决编写方式，运行环境差异仍需单独处理（详见本主题第 20 篇 多端适配：布局、样式与平台差异）。

**速记**：Taro 复用 React 组件模型与 Hooks，但浏览器 DOM 能力并不完整。



#### 版本与生态

**生态**：是围绕 Taro 的插件、跨端组件库与项目模板集合，用于补齐跨端开发中的通用能力。

- 插件：提供打包、样式处理与框架适配等扩展点。
- 组件库：多套跨端界面组件库可选，一套代码在各端渲染。
- 项目模板：官方提供适配不同框架版本与目标端的初始化模板。
- 版本策略：不同大版本对框架版本与编译方案的支持范围不同，升级前需确认兼容性。

```bash
# 用官方脚手架创建项目（命令名与参数以官方文档为准）
npx @tarojs/cli init myApp
```

> 生态插件需确认维护状态与目标端覆盖，尤其是依赖浏览器能力的库。

**速记**：插件、组件库与模板补齐能力，升级前先确认大版本兼容范围。



### 项目结构与路由

本节说明 Taro 约定的目录组织与路由方式：页面与配置分列不同位置，路由由配置文件的页面列表集中声明。

#### 目录结构

**目录结构**：是 Taro 约定的源码组织方式，页面、组件与编译配置各占固定位置。

- src：源码目录，页面与业务组件都放在其中。
- src/pages：页面目录，每个页面对应一个组件文件。
- config：编译配置目录，按环境与目标端拆分配置文件。
- 应用入口：应用级组件承担全局逻辑与公共布局，其同名配置文件声明全局配置。

```text
project/
├─ src/
│  ├─ app.tsx            # 应用入口组件
│  ├─ app.config.ts      # 应用级配置
│  └─ pages/
│     ├─ index/index.tsx
│     └─ detail/detail.tsx
├─ config/
│  ├─ index.js
│  ├─ dev.js
│  └─ prod.js
└─ package.json
```

> 应用入口组件与其同名配置文件配对出现，前者写逻辑，后者写页面列表与窗口表现。

**速记**：页面在 src/pages，编译配置在 config，应用入口配置由配对文件承担。



#### 页面注册与路由配置

**路由配置**：是用配置文件集中声明页面路径与窗口表现的方式，由编译期收集并生成各端路由。

- 页面列表：应用级配置声明全部页面路径，列表顺序决定首页。
- 页面表现：每个页面目录下用同名配置文件登记该页面的窗口表现。
- 编程式导航：用导航接口在页面之间跳转并携带参数。
- 参数读取：页面组件通过路由钩子读取跳转时携带的参数。

```ts
// src/app.config.ts：登记页面列表与全局窗口样式
export default defineAppConfig({
  pages: ["pages/index/index", "pages/detail/detail"],
  window: { navigationBarTitleText: "首页" },
});
```

```tsx
import Taro from "@tarojs/taro";

function goDetail(articleId: string) {
  Taro.navigateTo({ url: `/pages/detail/detail?id=${articleId}` });
}
```

> [!WARNING]
> **警告内容**：页面文件存在但未写入应用级配置的页面列表时，该页面不会被注册为可导航页面，跳转会直接失败，新增页面必须同步登记。

**速记**：页面列表在应用级配置登记并决定首页，窗口表现写页面同名配置。



#### 组件编写与样式

**组件编写**：是用 React 函数组件描述界面、并以跨端组件作为基础元素的方式。

- 基础元素：界面由框架提供的跨端组件搭建，不直接写浏览器标签。
- 属性与事件：属性名与事件名按框架约定书写，编译期映射到各端。
- 自定义组件：业务组件按普通 React 组件编写，可跨页面复用。
- 样式：样式文件与组件同名，作用域与可用单位受平台限制。

```tsx
import { View, Text } from "@tarojs/components";
import type { FC } from "react";

interface ArticleCardProps {
  title: string;
  summary: string;
}

const ArticleCard: FC<ArticleCardProps> = ({ title, summary }) => (
  <View className="article-card">
    <Text className="article-card__title">{title}</Text>
    <Text className="article-card__summary">{summary}</Text>
  </View>
);

export default ArticleCard;
```

> 类名与选择器的跨端支持有限，复杂选择器在部分端可能不生效，应优先使用简单选择器。

**速记**：界面由跨端组件搭建，业务组件仍是 React 组件，样式受平台限制。



#### 生命周期与页面通信

**生命周期**：是页面从加载、显示到卸载各阶段触发的回调，跨端场景下需与组件生命周期配合使用。

- 页面钩子：框架提供页面级钩子，用于读取路由参数与处理显示时机。
- 组件钩子：React 的副作用钩子负责数据请求与订阅清理。
- 传参：跳转时把参数拼进路径，页面钩子中读取。
- 回传与共享：返回结果可通过事件通道或全局状态传递。

```tsx
import { useRouter, useDidShow } from "@tarojs/taro";

export default function Detail() {
  const router = useRouter();

  useDidShow(() => {
    console.log(router.params.id); // 跳转时携带的参数
  });

  return null;
}
```

> 页面显示钩子会在每次回到该页时触发，适合放置需要刷新的逻辑；加载钩子只触发一次。

**速记**：页面级钩子读参数与处理显示时机，数据请求交给副作用钩子。



### 多端构建原理

本节说明 Taro 把一份源码变成多端产物的机制：编译期做语法转换，运行时方案补充适配层，差异处靠条件判断兜底。

#### 编译时转换流程

**编译流程**：是从源码入口出发解析依赖、按目标端生成对应代码并输出的过程。

- 解析：读取组件与配置文件，构建页面与依赖关系。
- 转换：把跨端组件与 JSX 语法转换为目标端可识别的形式。
- 生成：产出各端的模板、样式与逻辑文件。
- 输出：按端输出到独立目录，供各平台工具或托管服务使用。

```bash
# 开发与生产构建按端触发
npm run dev:weapp    # 微信小程序端开发模式
npm run build:weapp  # 微信小程序端生产构建
npm run build:h5     # Web 端生产构建
```

> 构建命令按端划分，同一份源码在不同命令下走同一套解析流程，只有转换与生成规则不同。

**速记**：解析、转换、生成、输出四步，按端触发并产出到独立目录。



#### 运行时适配层

**适配层**：是运行时方案在产物中携带的支撑代码，用于在目标端解释执行统一的组件与接口调用。

- 职责：把统一的组件与接口调用翻译为目标端的实际操作。
- 代价：适配层会增加产物体积，编译时方案可减少其比重。
- 边界：依赖浏览器专有对象的能力在适配层下不可用。
- 调试：出错时的调用栈包含适配层，与 Web 端原生调用栈不同。

```text
# 适配层职责示意
统一组件调用 -> 适配层 -> 目标端组件实现
统一接口调用 -> 适配层 -> 目标端原生能力
```

> 运行时方案换来了语法灵活性，代价是产物变大与调用链变长。

**速记**：适配层把统一调用翻译为目标端操作，代价是体积变大、部分能力不可用。



#### 组件与接口的多端映射

**多端映射**：是统一命名的组件与接口在编译期或运行时被替换为目标端实现的过程。

- 组件映射：跨端组件在编译期转换为目标端的对应结构。
- 接口映射：统一接口调用在目标端转发为原生能力调用。
- 覆盖差异：个别组件属性或接口在部分端不实现，需要条件判断兜底。
- 验证方式：以各端真机表现与官方支持说明为准。

```tsx
import { View } from "@tarojs/components";

export default function ShareBar() {
  // process.env.TARO_ENV 在构建时被替换为目标端名
  if (process.env.TARO_ENV === "weapp") {
    return <View>微信小程序端的分享入口</View>;
  }
  return <View>其他端的分享入口</View>;
}
```

> [!WARNING]
> **警告内容**：用目标端名称做条件判断时，环境变量由构建时替换，未覆盖到的端会落入默认分支，新增目标端后必须回头检查全部分支。

**速记**：统一组件与接口在编译或运行时映射到目标端，差异处条件判断兜底。



#### 构建产物与分包

**产物与分包**：是构建输出的文件组织方式，小程序端受代码包体积限制，需要把页面拆分到多个代码包。

- 分包配置：在应用级配置中声明分包与各分包包含的页面。
- 主包控制：主包只保留首屏必需内容，其余页面下沉到分包。
- 公共依赖：多个分包共用的模块抽到公共分包，避免重复打包。
- 体积核对：各端对单包与总包体积有上限，构建后应核对产物体积。

```ts
// app.config.ts：声明分包，把详情页下沉到独立代码包
export default defineAppConfig({
  pages: ["pages/index/index"],
  subPackages: [
    {
      root: "packageDetail",
      pages: ["detail/index"],
    },
  ],
});
```

> [!CAUTION]
> **注意内容**：分包体积超出平台上限时上传会直接失败，新增依赖后应在构建产物中重新核对各包体积，而不是等到提交上传时才发现。

**速记**：首屏留主包、其余下沉分包，公共依赖抽公共分包，构建后核对体积。



### uni-app 与 Taro 的取舍

**取舍**：是在两个跨端框架之间做选择时需要权衡的若干维度，维度之间往往不能同时最优。

#### 技术栈取向

**技术栈取向**：是框架要求的语言与组件模型，决定团队的迁移成本与代码复用范围。

- uni-app：以 Vue 单文件组件为编写单位，适合 Vue 技术栈团队。
- Taro：以 React 组件与 JSX 为编写单位，适合 React 技术栈团队。
- 复用能力：两者都能跨端复用业务代码，差异集中在调用平台特有能力处。
- 迁移成本：已有 Web 项目改造为跨端项目时，与现有技术栈一致的一方改造成本更低。

```text
# 技术栈与框架的对应关系
Vue 技术栈   -> uni-app
React 技术栈 -> Taro
```

> 框架选择的第一约束通常是团队既有技术栈，而不是框架之间的功能清单差异。

**速记**：Vue 技术栈选 uni-app，React 技术栈选 Taro，与既有栈一致者改造成本最低。



#### 生态与插件

**生态**：是框架周边可用的组件库、插件与模板的丰富程度与质量。

- uni-app：插件市场体量大，覆盖多端模板与业务组件。
- Taro：与前端社区生态衔接紧密，多套跨端组件库可用。
- 依赖风险：插件质量参差，需确认维护状态与目标端覆盖。
- 自建成本：生态缺位的能力需要自行封装，成本随目标端数量上升。

```text
# 引入第三方能力前的检查项
1. 最近是否有维护更新
2. 是否声明支持项目需要的全部端
3. 是否依赖浏览器专有对象
```

> 生态规模大不等于可用能力多，逐个确认目标端覆盖比看数量更可靠。

**速记**：生态丰俭影响自建成本，插件需按目标端逐项确认可用性。



#### 多端覆盖与产物

**多端覆盖**：是框架能产出的目标端范围与各端产物的成熟度。

- 端覆盖：两者都覆盖 Web 端、多个小程序平台与原生应用端。
- 产物形态：小程序端出代码包，Web 端出静态资源，应用端出前端资源。
- 一致性：跨端一致性由框架的组件层与接口层保证，专有能力仍需逐端适配。
- 验证成本：目标端越多，逐端验证与回归的成本越高。

```text
# 各端产物形态对照
小程序端 -> 代码包，交平台工具上传
Web 端   -> 静态资源，交静态托管部署
应用端   -> 前端资源，交原生打包流程
```

> 产物形态由目标端决定，与框架选择无关，两者在这条上差异不大。

**速记**：端覆盖相近，差异在产物成熟度与逐端验证成本。



#### 选型建议

**选型**：是结合团队技术栈、目标端清单与长期维护成本给出结论的过程。

- 先定端：明确必须覆盖的目标端，再核对框架的支持情况。
- 再看栈：团队熟悉 Vue 优先 uni-app，熟悉 React 优先 Taro。
- 重维护：考察官方迭代节奏与社区活跃度，避免选中停更方案。
- 小验证：用最小项目在全部目标端各跑通一次，再定案。

```text
# 选型检查顺序
1. 目标端是否全部覆盖
2. 团队技术栈是否匹配
3. 生态能否补齐关键能力
4. 最小项目能否各端跑通
```

> [!IMPORTANT]
> **重要内容**：跨端框架只解决一套代码多端运行，布局、单位与平台差异的适配仍需单独处理（详见本主题第 20 篇 多端适配：布局、样式与平台差异），选型时不能把它当作差异适配的替代方案。

**速记**：先定端、再看栈、重维护、小验证，四步走完再定案。
