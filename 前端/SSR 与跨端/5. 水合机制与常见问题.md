## 水合机制与常见问题

### 水合是什么

水合是服务端产出 HTML 之后、页面真正可交互之前必须经过的一步。本模块界定它的定义、要解决的问题以及它与首次渲染的关系，后续模块再拆解执行过程、不匹配成因与优化手段。

#### 水合的定义

**水合（hydration）**：是客户端在服务端产出的 HTML 之上挂载组件树、为已有节点恢复事件监听与组件状态的过程，它是同构渲染链路中连接「可见」与「可交互」的环节。

- 输入：服务端产出的 HTML 结构与随响应下发的首屏数据。
- 动作：客户端执行同一份组件代码，把结果与服务端结构逐块对应，并为节点挂上事件。
- 输出：事件可触发、状态可更新、后续路由可由客户端接管的页面。
- 别名：该过程也称注水或激活，本系列统一写「水合（hydration）」。
- 命名由来：干枯的 HTML 结构被注入逻辑后才「活」起来，因此得名。

```tsx
// 客户端入口：水合把服务端结构接上交互
import { hydrateRoot } from "react-dom/client";
import { App } from "./App";

const container = document.getElementById("app");
const data = window.__APP_DATA__;

hydrateRoot(container, <App data={data} />);
```

```html
<!-- 服务端产出的结构：可见，但按钮点击没有任何反应 -->
<button class="counter">0</button>
```

> 水合与首次渲染的区别在于是否复用节点：前者在已有结构上补事件，后者从空容器开始创建结构。

**速记**：水合是在服务端 HTML 上挂组件树、补事件与状态的过程。



#### 水合要解决的问题

**水合要解决的问题**：是让服务端产出的静态结构获得交互能力，从而在不重建首屏节点的前提下把可见内容变成可用界面。

- 静态到可交互：HTML 本身只是一份标记，没有事件监听与组件状态。
- 避免重复成本：从头重建首屏节点会让浏览器再做一次创建与布局，与复用节点相比更慢。
- 保留首屏收益：内容已经随响应到达，用户不必等脚本下载完才看到文字。
- 维持单一逻辑源：两端执行同一份组件代码，交互逻辑只在客户端实现一次。
- 兼顾抓取与体验：抓取方拿到完整内容，用户随后获得完整交互。

```tsx
// 服务端渲染把数据变成结构，水合把结构变成可交互组件
export function ArticleLike({ articleId, initialCount }: {
  articleId: number;
  initialCount: number;
}) {
  const [count, setCount] = useState(initialCount);
  return (
    <button onClick={() => setCount((value) => value + 1)}>
      点赞 {count}
    </button>
  );
}
```

> [!IMPORTANT]
> **重要内容**：水合要求服务端与客户端渲染出相同结构，若两端结果不一致，框架会放弃复用并退化为客户端重建，首屏收益随之消失。

**速记**：水合解决的是把静态首屏接上交互，同时避免重建节点的重复开销。



#### 水合与首次渲染的关系

**水合与首次渲染的关系**：是同一组件树在两端各被执行一次，服务端那次产出结构，客户端那次核对结构并接管，两次结果应当一致。

- 执行顺序：服务端渲染在前，客户端水合在后，中间隔着脚本下载与解析。
- 结果要求：两次执行得到的节点层级与文本内容应当相同。
- 差异来源：读取时间、随机值、浏览器能力与数据版本不一致都会打破这份一致。
- 框架处理：发现不一致时给出警告，并对受影响区域改为以客户端结果为准。
- 收敛方向：把不确定性从渲染期挪到挂载之后，是消除差异的通用办法。

```text
一次请求的两条执行路径
服务端：组件树 → HTML 字符串 + 首屏数据
客户端：同一组件树 + 同一份数据 → 核对并接管已有结构
```

```tsx
// 两端共用同一份数据，渲染结果才可能一致
export function Profile({ name }: { name: string }) {
  return <h2>{name}</h2>;   // 服务端与客户端都只依赖入参
}
```

> 一致性不是主观要求而是机制前提：水合本质上是「对照」，对照不成立就只能重建。

**速记**：水合是客户端对服务端首次渲染结果的核对与接管，两次结果必须一致。



### 水合的执行过程

水合的执行过程可以拆成定位根节点、遍历比对、绑定事件与状态、判定完成四步。本模块按这一步序展开，并指出每步的失败表现。

#### 定位根节点与准备数据

**定位根节点与准备数据**：是水合的起点，客户端先找到服务端产出的根容器，再取回随响应下发的首屏数据。

- 根节点：客户端按固定标识找到根容器，水合范围即为该容器的子树。
- 数据读取：从内联脚本或约定的全局变量中取回首屏数据，作为组件树的入参。
- 次序保证：数据必须在渲染前就绪，否则首次执行就会得到与服务端不同的结果。
- 空容器情形：容器内没有任何服务端结构时，水合会退化为首次渲染。
- 重复调用：对同一容器重复水合会产生警告，入口只应执行一次。

```tsx
import { hydrateRoot } from "react-dom/client";
import { App } from "./App";

const container = document.getElementById("app");
if (!container) throw new Error("缺少根容器");

hydrateRoot(container, <App data={window.__APP_DATA__} />);
```

> 根容器的标识由服务端与客户端共同约定，改动其中一端而不改另一端会导致水合找不到目标而与整页不匹配。

**速记**：水合从定位根容器、读取首屏数据开始，数据必须渲染前就绪。



#### 遍历比对与复用节点

**遍历比对与复用节点**：是客户端按组件树顺序遍历服务端结构，逐块核对节点类型与文本是否相符，相符则直接复用，不符则记入不匹配。

- 顺序推进：按深度优先顺序同时前进组件树与已有节点，逐块核对。
- 属性核对：关键属性参与比对，差异会造成该节点不被复用。
- 文本核对：文本内容不一致同样触发不匹配，常见于时间与格式化结果。
- 复用判定：相符的节点保留原对象，跳过创建与样式计算。
- 差异范围：不匹配的影响通常局限于出错子树，而非整棵组件树。

```tsx
// 结构相符时逐层复用，不会重新创建这些节点
export function Badge({ level }: { level: "新" | "热" }) {
  return <span className="badge">{level}</span>;
}
```

> 比对成功的关键是「结构的可预测」：同一份数据在两端必须走同一条渲染分支。

**速记**：水合按顺序遍历现有节点，结构相符即复用，不符则记为不匹配。



#### 事件绑定与状态恢复

**事件绑定与状态恢复**：是在复用节点之上注册事件处理函数、恢复组件内部状态的过程，这一步完成后页面才真正可交互。

- 事件委托：在根容器上统一注册监听，由框架按目标元素分发到对应处理函数。
- 状态初始化：组件以其初始状态启动，需要与首屏数据对齐以免跳变。
- 受控输入：输入框等元素的初始值来自服务端，水合时保持同一取值。
- 未完成区间：水合进行中的区域可见但不可交互，需要占位与反馈兜底。
- 分批推进：允许按区域分批完成，让先就绪的部分先可用。

```tsx
"use client";

import { useState } from "react";

export function SearchBox({ keyword }: { keyword: string }) {
  const [value, setValue] = useState(keyword);           // 与首屏数据对齐
  return <input value={value} onChange={(e) => setValue(e.target.value)} />;
}
```

> 水合期间发生过早的用户输入可能被随后的初始化覆盖，因此可交互时间应尽量早于用户首次操作到达。

**速记**：事件绑定与状态恢复完成后页面可交互，输入初值须与首屏一致。



#### 水合完成的时机

**水合完成的时机**：指整棵水合范围内的事件与状态均已就绪、页面进入完全可交互状态的时间点，它是衡量首屏体验的关键节点之一。

- 整树完成：整棵子树完成接管后，页面才算完全可交互。
- 分批完成：按区域推进时，局部可在整树完成前先可用。
- 与可见解耦：内容可见时间早于可交互时间，两者需分别衡量。
- 影响因素：脚本体量、组件数量与首屏数据大小共同决定完成的早晚。
- 观测方式：可借助浏览器性能面板观察主线程在接管阶段的工作分布。

```text
首屏时间线
HTML 到达 → 内容可见 → 脚本下载执行 → 水合完成 → 完全可交互
```

> 把水合完成时间往前挪的手段集中在两处：减少首屏需要接管的代码量，以及推迟非关键区域的水合。

**速记**：水合完成是全树接管就绪的时间点，晚于内容可见时间。



### 水合不匹配的成因

水合不匹配（hydration mismatch）指客户端渲染结果与服务端结构不一致，框架因此放弃复用受影响区域。本模块按四类常见成因给出可复现示例与处理方式。

#### 时间与随机数导致的不一致

**时间与随机数导致的不一致**：指渲染期直接读取当前时刻或随机值，服务端与客户端两次取值必然不同，从而渲染出不同内容。

- 当前时间：两端执行时刻不同，若再叠加时区差异，结果差异更大。
- 随机值：每次调用结果不同，用于宽度、标识或排序都会造成不一致。
- 递增计数：模块级计数器在服务端按请求累加，两端取值难以对齐。
- 判定方法：凡是渲染输出依赖「渲染发生的确切时刻」的写法都属此类。
- 处理方向：改用入参传入的确定值，或先渲染占位、挂载后再更新。

```tsx
// 错误：渲染期直接读取当前时间，两端时区与时刻都不同
export function PublishTime() {
  return <time>{new Date().toLocaleString()}</time>;
}
```

```tsx
// 正确：时间由服务端确定后作为入参传入，两端渲染同一结果
export function PublishTime({ iso }: { iso: string }) {
  return <time dateTime={iso}>{iso.slice(0, 10)}</time>;
}
```

```tsx
// 错误：随机值参与渲染，两端取到的值不同
export function Skeleton() {
  return <div style={{ width: `${Math.random() * 100}%` }} />;
}
```

> [!WARNING]
> **警告内容**：把时间、随机数与自增标识直接写入渲染结果，会在每次水合时触发不匹配警告并让受影响区域重建，首屏结构随之抖动。

**速记**：渲染期读时间或随机值必然两端不同，应改为入参传入或挂载后更新。



#### 浏览器专属 API 导致的不一致

**浏览器专属 API 导致的不一致**：指渲染期读取只在浏览器存在的对象或能力，服务端无法取得同样的值，两端输出因此不同。

- 窗口尺寸：屏幕宽度、滚动位置在服务端不存在，默认值常与浏览器实测值不同。
- 本地存储：主题、语言与登录态常存于本地存储，服务端读取不到。
- 媒体查询：按视口判断的布局分支在服务端只能退化为某个默认分支。
- 直接引用：在渲染期引用浏览器对象，严重时在服务端直接抛出引用错误。
- 处理方向：把这类读取挪到挂载后的副作用中，首屏先渲染两端一致的安全值。

```tsx
// 错误：渲染期读取本地存储，服务端不存在该对象且取值不同
export function ThemeBadge() {
  const theme = localStorage.getItem("theme");
  return <span>{theme}</span>;
}
```

```tsx
// 正确：挂载后再读取，首屏两次渲染同一个占位
"use client";

import { useEffect, useState } from "react";

export function ThemeBadge() {
  const [theme, setTheme] = useState<string | null>(null);
  useEffect(() => {
    setTheme(localStorage.getItem("theme"));
  }, []);
  return <span>{theme ?? "默认主题"}</span>;
}
```

> [!CAUTION]
> **注意内容**：把首屏外观完全交给挂载后的更新会造成一次可见的闪烁，重要视觉应尽量给出与服务端一致的安全初值。

**速记**：渲染期读浏览器能力必然两端不同，应挪到挂载后并对齐安全初值。



#### 标签嵌套被修正导致的不一致

**标签嵌套被修正导致的不一致**：指服务端产出的标记违反标记语言的嵌套约束，浏览器解析时自动改写结构，使实际节点与客户端预期不符。

- 合法约束：段落内不能再嵌块级容器，列表项外不能出现孤立的列表单元。
- 浏览器行为：解析到非法嵌套时，浏览器会提前闭合外层标签，节点层级随之改变。
- 结果表现：服务端字符串是一种层级，浏览器解析后是另一种层级，两边对不上。
- 框架提示：控制台会给出「某元素不能作为某元素后代」之类的结构提示。
- 处理方向：按合法嵌套重写组件结构，把外层标签换成能容纳子元素的容器。

```tsx
// 错误：段落内嵌块级元素，浏览器会提前闭合段落标签
export function Description() {
  return (
    <p>
      文章简介
      <div>作者：Ada</div>
    </p>
  );
}
```

```html
<!-- 浏览器实际解析结果：段落标签在块级元素之前被自动闭合 -->
<p>文章简介</p>
<div>作者：Ada</div>
```

```tsx
// 正确：改用可以容纳块级子元素的容器
export function Description() {
  return (
    <div>
      <p>文章简介</p>
      <p>作者：Ada</p>
    </div>
  );
}
```

> 这类不匹配与数据无关，纯由标记结构引起，因此换一份数据也不会消失，必须改结构。

**速记**：非法嵌套会被浏览器改写层级，必须按合法结构重写组件。



#### 数据与语言环境差异导致的不一致

**数据与语言环境差异导致的不一致**：指服务端与客户端使用了不同的数据版本或不同的区域设置，同一份输入被格式化成不同文本。

- 时区差异：服务端按服务器时区格式化日期，浏览器按本地时区，文本因此不同。
- 区域设置：未指定区域时格式化结果随运行环境的默认值变化。
- 数据版本：响应与接口数据在两端的获取时刻不同，取值可能不同步。
- 精度约定：货币与小数位未固定时，两端舍入结果可能不同。
- 处理方向：把时区、区域与格式显式固定，并让两端共用同一份首屏数据。

```tsx
// 错误：未指定区域与货币，格式化结果随运行环境变化
export function Price({ cents }: { cents: number }) {
  return <span>{new Intl.NumberFormat().format(cents / 100)}</span>;
}
```

```tsx
// 正确：显式固定区域与货币，两端格式化结果一致
const priceFormatter = new Intl.NumberFormat("zh-CN", {
  style: "currency",
  currency: "CNY",
});

export function Price({ cents }: { cents: number }) {
  return <span>{priceFormatter.format(cents / 100)}</span>;
}
```

```tsx
// 日期同理：显式指定时区，避免服务端与浏览器各按本地时区渲染
const dateFormatter = new Intl.DateTimeFormat("zh-CN", {
  timeZone: "Asia/Shanghai",
  dateStyle: "medium",
});

export function PublishDate({ iso }: { iso: string }) {
  return <time dateTime={iso}>{dateFormatter.format(new Date(iso))}</time>;
}
```

> 只要格式化参数显式且数据来自同一次响应，这类不匹配就能从源头消除。

**速记**：格式化必须显式固定区域与时区，数据以同一次响应为准。



### 水合的优化手段

水合的优化目标是压缩「内容可见」到「完全可交互」之间的窗口。本模块给出四类手段及其代价，取舍取决于页面里哪部分最需要尽早可用。

#### 减少首屏客户端组件

**减少首屏客户端组件**：是让首屏尽可能由服务端产出、只把真正需要交互的小块标为客户端组件，从而减少水合阶段需要接管的范围。

- 叶子化：把交互收敛到尽量小的叶子组件，外层保持服务端渲染。
- 传参而非取数：客户端组件的数据由外层作为入参传入，不在组件内自行取数。
- 拆分边界：一个庞大客户端组件拆成多个小块后，可分别安排水合优先级。
- 收益：接管范围缩小，脚本体量下降，水合完成时间提前。
- 代价：需要按交互边界拆分组件，拆分过细会增加文件数量与传参层级。

```tsx
// 服务端组件承载结构与数据，只有点赞按钮是客户端组件
export default async function ArticlePage({ params }: { params: { id: string } }) {
  const article = await getArticleById(params.id);
  return (
    <article>
      <h1>{article.title}</h1>
      <p>{article.summary}</p>
      <ArticleLike articleId={article.id} initialCount={article.likes} />
    </article>
  );
}
```

> 判断标准是「这块是否需要响应事件或持有频繁变化的状态」，不满足的都不必成为客户端组件。

**速记**：把交互收敛到最小客户端组件，首屏其余部分留给服务端。



#### 用挂载标记两段式渲染

**用挂载标记两段式渲染**：是首屏先渲染一个两端一致的占位，挂载后再切换到依赖浏览器或时刻的真实内容，用一次可见切换换取水合一致。

- 占位初值：状态初值取一个两端都成立的值，服务端与首次客户端渲染都输出它。
- 挂载后更新：在挂载后的副作用里读取真实值并更新状态，触发第二次渲染。
- 适用范围：时间、主题、视口相关的局部展示，不适合承载主要可见内容。
- 取舍：一致性得到保证，代价是这些位置会经历一次从占位到真实值的切换。
- 配套：占位与真实内容尺寸接近时，切换带来的位移最小。

```tsx
"use client";

import { useEffect, useState } from "react";

export function LocalClock() {
  const [now, setNow] = useState<string | null>(null);   // 两端一致的占位
  useEffect(() => {
    const timer = setInterval(() => {
      setNow(new Date().toLocaleTimeString());
    }, 1000);
    return () => clearInterval(timer);
  }, []);
  return <span>{now ?? "加载中"}</span>;
}
```

> [!CAUTION]
> **注意内容**：把主要可见内容放进挂载后才渲染的分支，会让首屏对这些内容而言退化为客户端渲染，抓取与观感都会受损。

**速记**：两段式渲染用一致占位换水合一致，只适合局部且非主要的内容。



#### 延迟水合与按需水合

**延迟水合与按需水合**：是把暂时不在视口内或不常用的交互区域的水合推迟到需要时再执行，从而把主线程优先让给首屏关键区域。

- 视口触发：区域进入视口时再开始该区域的水合。
- 交互触发：用户首次与本区域交互时再水合，代价是首次点击可能略有延迟。
- 空闲触发：在浏览器空闲时段逐步完成剩余区域的水合。
- 优先级：按区域重要性安排水合顺序，先关键后次要。
- 代价：推迟期间区域仍可见但不可交互，需要有可感知的过渡状态。

```tsx
"use client";

import { useEffect, useRef, useState } from "react";

export function CommentSection() {
  const holderRef = useRef<HTMLDivElement | null>(null);
  const [ready, setReady] = useState(false);

  useEffect(() => {
    const holder = holderRef.current;
    if (!holder) return;
    const observer = new IntersectionObserver((entries) => {
      if (entries[0].isIntersecting) setReady(true);   // 进入视口后再水合
    });
    observer.observe(holder);
    return () => observer.disconnect();
  }, []);

  return <div ref={holderRef}>{ready ? <CommentList /> : <p>评论区加载中</p>}</div>;
}
```

```tsx
// 也可按需加载整个交互模块，把它的代码推迟到首次需要时
import dynamic from "next/dynamic";

const CommentSection = dynamic(() => import("./CommentSection"), {
  loading: () => <p>评论区加载中</p>,
});
```

> 延迟水合不减少代码总量，只是重排主线程的先后顺序，因此应配合代码分割一起使用。

**速记**：延迟与按需水合把非关键区域推迟，让首屏关键交互先就绪。



#### 抑制警告与修复的取舍

**抑制警告与修复的取舍**：是在时间、随机值等无法消除的极少数场景下选择局部屏蔽不匹配提示，但仍需承担结构被重建的后果。

- 局部屏蔽：可在单个元素上声明忽略不匹配提示，范围仅限该元素。
- 适用场景：确实无法在服务端与客户端取得一致、且差异无关紧要的展示位。
- 残留风险：屏蔽只消除提示，不改变结构被重建的事实，性能收益仍会损失。
- 排查顺序：先确认差异来源属于哪一类成因，再决定修复还是屏蔽。
- 顺序原则：屏蔽是最后手段，不应作为逃避结构错误与数据错误的常规做法。

```tsx
// 仅在确认无法对齐时局部屏蔽，并注明原因
export function ServerRenderedTimestamp({ iso }: { iso: string }) {
  return <time dateTime={iso} suppressHydrationWarning>{iso}</time>;
}
```

> [!WARNING]
> **警告内容**：用抑制提示掩盖由非法嵌套或数据不一致引起的问题，会让结构被静默重建，缺陷留在代码里并在后续改动中反复出现。

**速记**：抑制提示只适合确实无法对齐的极少数场景，先定位成因再决定屏蔽。
