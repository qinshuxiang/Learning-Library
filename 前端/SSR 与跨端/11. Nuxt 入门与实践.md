## Nuxt 入门与实践

### Nuxt 是什么

本节确立 Nuxt 的定位：它是 Vue 生态里的应用级框架，把路由、数据获取、状态与全栈能力按约定收进同一工程。理解它与 Next.js 的对应关系后，后续三节都只是约定细节的展开。

#### Nuxt 的定义与定位

**Nuxt**：是建立在 Vue 之上的应用级框架（meta-framework），提供文件路由、自动导入、服务端渲染与内置服务端引擎，默认输出同构渲染应用。

- 定位：与 Next.js 之于 React 的关系相同，Nuxt 是 Vue 生态的应用框架，而非构建工具。
- 默认渲染：默认开启服务端渲染，也可切换为纯客户端渲染或静态生成。
- 全栈能力：内置服务端引擎，可在同一工程内直接编写接口。
- 开发方式：以组合式函数提供数据与状态能力，配合组合式脚本写法使用。

```json
{
  "devDependencies": {
    "nuxt": "^3.0.0"
  }
}
```

> Nuxt 的约定优先设计意味着多数项目不必手写路由表与组件注册，代价是必须先了解目录约定才能定位代码。

**速记**：Nuxt 是 Vue 的应用级框架，默认开启服务端渲染并内置全栈能力。



#### 与 Next.js 的对照

**对照要点**：两者同属元框架这一类别，问题域一致，差别集中在渲染库、约定细节与生态工具链三处。

- 渲染库：Nuxt 基于 Vue，Next.js 基于 React，组件写法与响应式模型随之不同。
- 路由约定：都以文件路径映射路由，特殊文件名与目录名的约定不同。
- 数据获取：Nuxt 用组合式函数取数，Next.js 在服务端组件中直接等待异步结果（详见本主题第 8 篇 Next.js 数据获取与缓存）。
- 生态跟随：状态管理与组件库分别跟随 Vue 与 React 生态，选型不必跨界。

> 概念对应关系是理解两套约定的捷径：Next.js 的布局对应 Nuxt 的布局与页面嵌套，Next.js 的路由处理程序对应 Nuxt 的服务端接口目录。

**速记**：Nuxt 对 Vue、Next.js 对 React，问题域相同而约定细节不同。



#### 创建项目与最小示例

**创建项目**：是用官方脚手架生成可运行骨架的命令行流程，交互中选择包管理器与初始化选项。

- 创建命令：执行 npm create nuxt@latest 并输入项目名。
- 安装与启动：进入目录安装依赖，再执行开发命令。
- 页面位置：页面组件放在 pages 目录，根组件由框架约定提供。
- 产物命令：开发模式带热更新，构建与预览使用各自独立命令。

```bash
npm create nuxt@latest my-nuxt-app
cd my-nuxt-app
npm install
npm run dev
# Nuxt  http://localhost:3000
```

```vue
<!-- pages/index.vue -->
<template>
  <h1>{{ title }}</h1>
</template>

<script setup lang="ts">
const title = "学习库首页";
</script>
```

> 脚手架按选项生成对应形态的骨架，创建时选定的渲染模式可以事后在配置文件中改回。

**速记**：npm create nuxt@latest 生成骨架，页面写入 pages 目录即可访问。



#### 自动导入与约定优先

**自动导入（auto-import）**：是框架在构建期为模板与脚本自动注入常用接口和约定目录导出内容的能力，无需手写导入语句。

- 框架接口：响应式能力与数据获取函数可直接使用，不必逐行导入。
- 项目文件：components 与 composables 目录下的导出会被自动识别。
- 显式导入：需要清晰来源或避免歧义时仍可手写导入，两种方式并存。
- 编辑器支持：先生成类型声明文件，编辑器才能提示自动导入的内容。

```vue
<!-- components/ArticleCard.vue：无需导入即可在其他组件中使用 -->
<template>
  <article class="card">
    <h2>{{ item.title }}</h2>
  </article>
</template>

<script setup lang="ts">
const { item } = defineProps<{ item: { title: string } }>();
</script>
```

> [!TIP]
> **建议内容**：自动导入的便利以显式来源的缺失为代价，团队应在代码风格约定里写明哪些目录允许自动导入，避免阅读时找不到定义位置。

**速记**：框架接口与约定目录的导出自动可用，可读性问题用目录约定约束。



### 目录约定与路由

本节解决「文件放在哪、访问路径是什么」的问题：目录职责、文件路由、布局与路由中间件四件事构成了 Nuxt 工程的骨架。

#### 目录结构与职责

**目录职责**：是框架按目录名划分功能的约定，每个目录承担一类角色，放入其中的文件自动获得对应能力。

- pages 目录：页面组件，文件路径即访问路径。
- components 目录：可被自动导入的组件。
- layouts 目录：布局组件，供页面套用外壳。
- composables 目录：可复用的组合式函数。
- server 目录：服务端接口与中间件。
- nuxt.config.ts：框架级配置文件。

```text
my-nuxt-app/
  pages/
    index.vue
    blog/[id].vue
  components/
  composables/
  layouts/default.vue
  server/api/articles.get.ts
  nuxt.config.ts
```

> server 目录中的文件名带方法后缀时，框架按该后缀生成对应的接口处理函数，无需再写路由声明。

**速记**：pages 出路由、server 出接口，components 与 composables 出自动导入。



#### 文件路由与动态路由

**文件路由**：是 pages 目录下的文件名与目录结构直接映射为访问路径的约定，支持参数段与捕获全部段。

- 静态段：pages/blog/index.vue 对应 /blog。
- 动态段：pages/blog/[id].vue 对应 /blog/1，参数名写在方括号中。
- 捕获全部：pages/docs/[...slug].vue 匹配其下的多级路径。
- 嵌套：目录与同名父组件配合时形成嵌套路由，子页面渲染在父级出口内。

```vue
<!-- pages/blog/[id].vue -->
<template>
  <article>
    <h1>{{ article?.title }}</h1>
  </article>
</template>

<script setup lang="ts">
const route = useRoute();
const { data: article } = await useFetch(`/api/articles/${route.params.id}`);
</script>
```

> 动态段中的参数通过当前路由对象读取，参数名与文件名中的段名保持一致，改文件名即改参数名。

**速记**：pages 下的路径与文件名直接决定访问路径，方括号段承载路径参数。



#### 布局与嵌套视图

**布局（layout）**：是把多个页面共用的外壳抽出的组件，页面可声明使用哪个布局，不声明时套用默认布局。

- 默认布局：layouts/default.vue 自动套用于页面。
- 显式指定：页面通过元信息声明所用布局名。
- 嵌套视图：父级路由组件内放置子页面出口，承载侧边栏与详情这类结构。
- 过渡效果：布局切换与页面切换可配置过渡。

```vue
<!-- layouts/default.vue -->
<template>
  <div class="shell">
    <header>学习库</header>
    <main>
      <slot />
    </main>
  </div>
</template>
```

> 布局只负责外壳，页面级头部信息用页面元信息声明，二者职责不重叠，改布局时不必担心影响单页逻辑。

**速记**：布局抽公共外壳，页面用元信息选择布局，嵌套视图由父级出口承载。



#### 路由中间件

**路由中间件（route middleware）**：是在进入路由之前执行的函数，可中止导航或改写去向，按作用范围分为全局与页面级。

- 全局中间件：放在 middleware 目录并以 .global 命名，所有导航都执行。
- 页面级中间件：在页面元信息中声明，只对声明它的页面生效。
- 返回值：返回导航结果可改写去向，不返回则放行。
- 执行环境：默认在客户端与服务端都会执行，需按双端条件编写（详见本主题第 12 篇 SSR 应用的鉴权、状态与安全）。

```ts
// middleware/auth.global.ts
export default defineNuxtRouteMiddleware((to) => {
  const session = useCookie("session");
  if (!session.value && to.path.startsWith("/dashboard")) {
    return navigateTo("/login");
  }
});
```

> [!WARNING]
> **警告内容**：路由中间件默认双端执行，在其中直接访问浏览器专有对象会在服务端渲染阶段报错，涉及窗口或文档对象的逻辑必须先判断当前所处环境。

**速记**：全局中间件覆盖全部导航，页面级中间件按元信息生效，默认双端执行。



### 数据获取与状态管理

本节处理数据在两端的流动：首屏数据如何在服务端取回、请求如何按唯一键去重、跨端共享状态如何建立，以及复杂状态交给谁管理。

#### 服务端数据获取的两种方式

**服务端数据获取**：是在页面或组件创建阶段取回数据并随首屏直出，Nuxt 以组合式函数的形式提供，返回值在服务端与客户端之间自动同步。

- 基础形式：useAsyncData 接收唯一键与取数函数，返回数据、状态与错误。
- 便捷形式：useFetch 在其之上封装请求，接收地址与选项。
- 唯一键：同一键在同一次渲染中只取数一次，用于请求去重。
- 首屏收益：取数发生在服务端，页面直出时已带数据（详见本主题第 6 篇 SEO 与首屏性能）。

```vue
<!-- pages/articles.vue -->
<template>
  <ul>
    <li v-for="item in articles" :key="item.id">{{ item.title }}</li>
  </ul>
</template>

<script setup lang="ts">
const { data: articles, pending, error } = await useAsyncData(
  "article-list",
  () => $fetch("/api/articles"),
);
</script>
```

> [!IMPORTANT]
> **重要内容**：服务端取回的数据会被序列化后随首屏一起下发，取数函数只能返回可序列化且不含敏感字段的数据，敏感内容应在服务端裁剪后再返回。

**速记**：useAsyncData 以唯一键取数，useFetch 是其便捷封装，数据在服务端取回并随首屏下发。



#### 请求去重与刷新控制

**请求去重**：是同一唯一键在首屏与后续导航中共享同一次取数结果的机制，配合刷新与监听选项控制何时重新请求。

- 键的作用：键相同即认为数据相同，避免同一份数据被重复请求。
- 手动刷新：返回的刷新函数可重新执行取数。
- 监听重取：可声明监听来源，来源变化时自动重取。
- 参数区分：键写成返回字符串的函数时，参数变化即得到不同的数据。

```vue
<script setup lang="ts">
const route = useRoute();
const { data, refresh } = await useAsyncData(
  () => `article-${route.params.id}`,
  () => $fetch(`/api/articles/${route.params.id}`),
  { watch: [() => route.params.id] },
);
</script>

<template>
  <button type="button" @click="refresh">重新加载</button>
</template>
```

> 键既可以是固定字符串，也可以是返回字符串的函数；后者把参数纳入键中，参数不同即视为不同数据。

**速记**：键相同即复用同一次取数，用刷新函数与监听来源控制重取时机。



#### 跨端共享状态

**共享状态**：是在服务端与客户端之间共享并保持同步的响应式数据，Nuxt 用 useState 建立按请求隔离的共享值。

- 创建方式：useState 接收键与初始值，返回响应式引用。
- 隔离性：每个请求拥有独立实例，不同用户之间不串数据。
- 同步方式：服务端取值后序列化下发，客户端直接接管，不再多请求一次。
- 适用场景：登录用户信息、当前语言、请求级统计等首屏就要用的数据。

```ts
// composables/useCurrentUser.ts
export function useCurrentUser() {
  return useState<{ id: number; name: string } | null>("current-user", () => null);
}
```

> 共享状态的键取值在整个应用内唯一，两份数据必须用两个键，否则后写入的值会覆盖前者。

**速记**：useState 建立按请求隔离的共享状态，服务端取值后序列化下发并由客户端接管。



#### 集成状态管理库

**状态管理库集成**：是在框架自带共享状态之外引入完整状态库的路径，Nuxt 以官方模块对接 Pinia 这类库。

- 安装模块：以模块形式注册后，状态库实例在两端都可获取。
- 适用场景：状态结构复杂、需要调试工具与持久化插件时。
- 边界划分：请求级数据用共享状态，长期业务状态交给状态库。
- 服务端注意：库中状态同样会随首屏序列化，需避免放入敏感数据。

```ts
// stores/user.ts
import { defineStore } from "pinia";

export const useUserStore = defineStore("user", {
  state: () => ({ displayName: "", theme: "light" }),
  actions: {
    setDisplayName(name: string) {
      this.displayName = name;
    },
  },
});
```

> [!CAUTION]
> **注意内容**：把访问令牌放进全局状态库后，首屏序列化会把它写进页面，任何客户端代码都能读到，令牌应改为只存于服务端可读的 Cookie。

**速记**：复杂业务状态交给 Pinia，请求级数据仍用共享状态，敏感值不进全局状态。



### 渲染模式配置与部署

本节只讲配置与命令层面的取舍：渲染模式在哪里声明、如何按路由微调、三条命令各自产出什么，以及产物以什么形态运行。渲染模式的机制原理归本主题第 3 篇。

#### 渲染模式配置

**渲染模式配置**：是在框架配置文件中声明整个应用的渲染方式，决定产物是否包含服务端运行时代码。

- 同构渲染：默认开启，服务端渲染首屏后由客户端接管。
- 纯客户端渲染：关闭服务端渲染后成为单页应用，首屏由客户端生成。
- 静态生成：以生成命令产出静态文件，适合内容变化不频繁的站点。
- 模式取舍：三种模式的机制与适用条件详见本主题第 3 篇 渲染模式全景：CSR、SSR、SSG、ISR 与流式。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  ssr: true,
  // ssr: false 时改为纯客户端渲染
});
```

> 渲染模式影响产物形态与部署方式，切换前先确认所有页面在目标模式下都能正常工作。

**速记**：渲染模式在配置中一处置定，同构、纯客户端与静态生成三者对应不同产物。



#### 混合渲染与路由规则

**混合渲染**：是按路径为不同路由指定不同渲染与缓存策略的配置方式，在同构应用内逐路由调整。

- 按路径声明：在路由规则中为匹配路径指定渲染与缓存策略。
- 预渲染：把少量路径在构建期提前生成静态文件。
- 缓存：为接口或页面声明缓存与再验证时长。
- 常见组合：内容页预渲染、个性化页按请求渲染、控制台页走纯客户端。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    "/": { prerender: true },
    "/blog/**": { swr: 60 },
    "/dashboard/**": { ssr: false },
  },
});
```

> 路由规则按最长匹配生效，同一路径存在多条可用规则时以更具体的为准。

**速记**：路由规则按路径分别指定预渲染、缓存与渲染方式，组合出混合渲染。



#### 构建命令与产物

**构建与产物**：是框架提供的三条常用命令与它们对应的输出目录，分别用于本地开发、生产构建、产物预览与静态生成。

- 开发：执行开发命令启动带热更新的服务。
- 构建：执行构建命令产出生产产物，默认输出到固定目录。
- 预览：执行预览命令在本地以生产模式启动产物。
- 静态生成：执行生成命令产出纯静态文件，可交给静态托管。

```bash
npm run dev
npm run build
npm run preview
# Local: http://localhost:3000/
npm run generate
# 静态文件输出到 .output/public
```

> 预览命令运行的是构建产物，行为与开发服务器不同，发布前的核对应以预览结果为准。

**速记**：dev 开发、build 出生产产物、preview 验产物、generate 出静态文件。



#### 部署形态与环境变量

**部署形态**：由服务端引擎的部署预设决定，同一份产物可以面向常驻 Node 服务、无服务器函数或静态托管。

- 常驻服务：产物在 Node 进程中常驻运行，适合容器化部署。
- 无服务器：产物打包为可被平台调用的函数形态，按请求执行。
- 静态托管：只在静态生成模式下可行，产物为纯文件。
- 环境变量：公开变量以固定前缀在构建期注入，其余在服务端进程读取。

```bash
# 以 Node 服务形态运行构建产物
node .output/server/index.mjs
# Listening on http://localhost:3000
```

> [!TIP]
> **建议内容**：在流水线中固定部署预设，避免本地与线上使用不同形态导致行为差异；构建期注入的公开变量需随镜像一同固化。

**速记**：产物形态由部署预设决定，公开变量构建期注入，其余在服务端读取。
