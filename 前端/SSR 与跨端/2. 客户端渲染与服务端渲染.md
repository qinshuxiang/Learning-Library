## 客户端渲染与服务端渲染

**客户端渲染与服务端渲染**：是内容生成位置的两端，前者把渲染放在浏览器，后者把渲染放在服务端；两者的差异贯穿资源形态、首屏时序、可抓取性与部署形态。

本篇只讨论这两种最基本的模式：各自的机制、彼此的差异与选择依据。静态生成、增量再生成与流式渲染属于本主题第 3 篇 渲染模式全景：CSR、SSR、SSG、ISR 与流式；服务端产出 HTML 之后客户端如何接管的完整链路，属于本主题第 4 篇 同构渲染原理。

### 客户端渲染是什么

**客户端渲染（client-side rendering，CSR）**：是服务端返回一个不含正文的文档骨架，由浏览器下载并执行 JavaScript 后生成页面结构与内容的渲染模式。

#### 内容在浏览器生成

内容生成的位置是区分两种模式的第一把尺子：客户端渲染的响应体中没有正文，正文由浏览器在脚本执行后组装。

- 文档骨架：服务端返回的 HTML 通常只含一个挂载节点与若干脚本标签。
- 执行主体：渲染工作由浏览器完成，服务端不参与组件树到 DOM 的转换。
- 内容来源：页面数据由前端在运行时发起接口请求获得，接口与页面分开部署。

```html
<!-- 服务端返回的文档：正文为空 -->
<!DOCTYPE html>
<html lang="zh-CN">
  <head>
    <title>文章详情</title>
  </head>
  <body>
    <main id="root"></main>
    <script type="module" src="/assets/app.js"></script>
  </body>
</html>
```

```js
// 浏览器端在挂载完成后请求数据并渲染
const container = document.querySelector("#root");

async function renderArticlePage(articleId) {
  const response = await fetch(`/api/articles/${articleId}`);
  const article = await response.json();
  container.innerHTML = `<h1>${article.title}</h1><p>${article.body}</p>`;
}

renderArticlePage(1); // 正文在脚本执行并拿到数据后才出现
```

**挂载节点**：是骨架文档中预留给前端渲染的容器，前端脚本需要先找到它才能插入内容；挂载节点为空是客户端渲染页面的外在特征。

- 容器定位：脚本按选择器找到挂载点，找不到时不执行任何渲染。
- 脚本入口：入口脚本负责装载框架、挂载根组件并启动路由。
- 静默失败：容器缺失或脚本报错时，用户只看到空白页，没有降级内容。

```text
骨架文档：挂载节点为空，等待脚本填充
脚本执行：找到挂载节点 → 装载框架 → 渲染组件树 → 插入内容
```

> 判断一个页面是否属于客户端渲染，直接查看首次请求的响应体即可：正文不在响应体中，就属于客户端渲染。

**速记**：客户端渲染的响应体只有骨架，正文由浏览器执行脚本后生成。



#### 首次加载与路由切换

**首次加载**：是浏览器从发起页面请求到页面可用的整个过程，客户端渲染在这一过程中要串行完成脚本下载、脚本执行与首轮数据请求。

**客户端路由**：是在不整页刷新的前提下切换视图的做法，路由库拦截链接点击，用浏览器历史接口改动地址栏并按路由匹配渲染新页面。

- 首次加载：耗时集中在脚本体积与首轮接口请求，脚本越大、接口越慢，等待越久。
- 路由切换：后续跳转只请求数据与目标视图代码，不再重复下载公共脚本。
- 代码分割：路由级懒加载把各页面代码拆成独立文件，首屏只加载当前页面所需部分。
- 状态保持：整页不刷新使得全局状态与播放进度等上下文可以延续。

```js
// 客户端路由的最小形态：拦截点击并用历史接口改地址
function navigateTo(path) {
  window.history.pushState({}, "", path);
  renderRoute(path);
}

document.addEventListener("click", (event) => {
  const link = event.target.closest("a[data-route]");
  if (!link) return;
  event.preventDefault();
  navigateTo(link.getAttribute("href"));
});

window.addEventListener("popstate", () => renderRoute(location.pathname));
```

```text
首次加载：HTML 骨架 → 下载脚本 → 执行脚本 → 请求数据 → 渲染 → 可交互
路由切换：捕获点击 → 改地址 → 请求数据 → 替换视图（不刷新整页）
```

**按需加载**：是把非首屏所需的代码推迟到需要时再下载的做法，它把首次加载体积与路由切换速度解耦。

- 路由级分割：每个页面成为独立文件，跳转时才加载对应文件。
- 预取：在浏览器空闲时或用户悬停链接时提前下载目标页面代码。
- 预热数据：跳转前发起数据请求，与代码下载并行，减少串行等待。

> 路由切换快并不等于首次加载快：前者是站内跳转体验，后者才是新用户与抓取程序面对的门槛。

**速记**：客户端渲染的首屏由脚本与首轮请求决定，站内跳转则靠客户端路由避免整页刷新。



#### 客户端渲染的收益与代价

**客户端渲染的收益与代价**：是同一套机制的两面，收益来自渲染与路由都由前端掌握，代价来自首屏与可抓取性对脚本执行的依赖。

- 收益：前后端职责清晰，页面切换流畅，部署时前端产物可作为静态资源托管。
- 收益：组件与状态都留在浏览器，交互密集的应用无需为每次操作往返服务端。
- 代价：首屏要等脚本下载与执行，弱网或低端设备上的等待被放大。
- 代价：不执行脚本的抓取程序拿不到正文，可抓取性依赖额外的预渲染或服务端渲染手段。

```text
乐观网络：骨架 0.2 s → 脚本 0.5 s → 数据 0.4 s → 首屏约 1.1 s
弱网环境：骨架 1.5 s → 脚本 3.0 s → 数据 2.5 s → 首屏约 7.0 s
```

**成本归属**：客户端渲染把渲染成本从服务端转移到用户设备，CPU 与内存开销由访问者的浏览器承担，这解释了低端设备上的体验落差为何更明显。

- 首屏压力：脚本体积、首轮接口数量与设备性能共同决定等待时长。
- 交互收益：页面内操作不产生整页请求，状态延续成本低。
- 部署收益：产物是静态文件，可交给内容分发网络承载。

> [!NOTE]
> **提醒内容**：客户端渲染的收益集中在交互阶段，代价集中在首次加载阶段，评估时要把两个阶段分开计算。

**速记**：客户端渲染交互灵活、部署简单，但首屏与可抓取性都押在脚本执行上。



### 服务端渲染是什么

**服务端渲染（server-side rendering，SSR）**：是在收到请求时由服务端运行组件代码，把结果拼接为完整 HTML 文档直接返回的渲染模式。

#### 内容在服务端生成

内容生成的位置在服务端：组件在服务端运行一次，产出的是完整 HTML，浏览器拿到的响应体本身就含有正文。

- 执行主体：组件代码在服务端运行，服务端需要能执行应用代码的运行时。
- 每请求一次：默认情况下每个请求都会触发一次渲染，内容可随请求参数变化。
- 数据就近获取：服务端可以在渲染前访问数据库或内部接口，把数据直接拼进 HTML。
- 产出形态：响应体是完整文档，浏览器无需等待脚本即可绘制正文。

```js
// 服务端渲染的最小骨架：取数、渲染、返回完整 HTML
async function renderArticlePage(articleId) {
  const article = await getArticleById(articleId);
  return buildHtml("ArticlePage", { article });
}

const html = await renderArticlePage(1);
console.log(html);
// <article><h1>文章标题</h1><p>正文内容</p></article>
```

- 数据可达：服务端与数据源同处内网时，取数不必绕行公网。
- 输出可控：可按请求特征输出不同内容，也可按内容特征设置缓存头。
- 错误前置：渲染失败可以返回合适的错误状态码，而不是把错误留给浏览器。

> 服务端渲染要求服务端能执行组件代码，这与只托管静态文件的客户端渲染在部署形态上完全不同。

**速记**：服务端渲染在服务端运行组件，每个请求产出一份含正文的完整 HTML。



#### 一次请求的响应内容

**一次请求的响应内容**：是服务端渲染与客户端渲染最直接的差别所在，前者返回含正文的文档，后者返回等待脚本填充的骨架。

- 正文可见：响应体中能直接读到页面内容，脚本未执行时页面仍有内容。
- 数据内联：服务端取到的数据可以随 HTML 一并下发，供客户端接管时复用。
- 首字节更晚：服务端要先完成取数与渲染才能返回，首个字节的到达时间晚于静态托管。
- 体积更大：响应体包含正文与内联数据，传输体积高于骨架文档。

```html
<!-- 服务端渲染的响应体 -->
<!DOCTYPE html>
<html lang="zh-CN">
  <head>
    <title>文章详情</title>
  </head>
  <body>
    <main id="root">
      <article>
        <h1>文章标题</h1>
        <p>正文内容</p>
      </article>
    </main>
    <script type="module" src="/assets/app.js"></script>
  </body>
</html>
```

```bash
curl -s https://example.com/articles/1 | grep -c "正文内容"
# 1
```

> 用命令行取回两种页面的源码并对比正文所在位置，是最省事的验证方式。

**速记**：服务端渲染的响应体含正文与内联数据，代价是首字节更晚、报文更大。



#### 服务端渲染的收益与代价

**服务端渲染的收益与代价**：收益集中在首屏与可抓取性，代价集中在服务端负载与部署复杂度。

- 收益：正文随首个响应到达，浏览器不必等待脚本即可绘制首屏。
- 收益：不执行脚本的抓取程序也能读到正文，页面更容易被抓取与索引。
- 收益：数据在服务端聚合，页面只需一次往返即可拿到完整内容。
- 代价：每个请求都要执行一次渲染，服务端需要承担相应的计算开销。
- 代价：需要常驻的渲染运行时，缓存策略、错误处理与扩容都要一并考虑。

```text
收益项：首屏更早、正文可抓取、首轮请求更少
成本项：服务端算力、常驻进程、缓存与降级设计、双端代码差异
```

**成本与内容变化频率相关**：内容极少变动的页面若仍逐请求渲染，等于为不变的内容反复付出算力；把这类页面改为构建期生成即可消除这部分成本，具体做法属于本主题第 3 篇。

> [!IMPORTANT]
> **重要内容**：服务端渲染让服务端从静态文件服务器变成应用运行时，容量规划与故障降级必须一并设计，否则首屏收益会被服务端抖动抵消。

**速记**：服务端渲染换到更好的首屏与可抓取性，付出的是服务端算力与部署复杂度。



### 两种模式的差异

**两种模式的差异**：可以从内容生成的位置与时机、首屏与交互的时序、服务端负载与部署形态三方面逐项对照，差异不是程度问题，而是链路结构不同。

#### 内容生成时机与位置

**内容生成时机与位置**：是两种模式的分水岭，客户端渲染在浏览器运行时生成内容，服务端渲染在服务端请求时生成内容。

- 位置：前者在浏览器，后者在服务端。
- 时机：前者在脚本执行之后，后者在响应返回之前。
- 频率：前者每次进入页面都可能重新生成，后者以请求为单位各生成一次。
- 依赖：前者依赖浏览器执行能力，后者依赖服务端运行环境与数据可达性。

```text
客户端渲染：服务端（骨架）→ 浏览器（内容）
服务端渲染：服务端（骨架 + 内容）→ 浏览器（绘制 + 接管）
```

- 抓取程序视角：客户端渲染要看脚本能否执行，服务端渲染只看响应体。
- 用户视角：客户端渲染先看到空白或骨架，服务端渲染先看到正文。
- 开发者视角：客户端渲染的调试重心在浏览器，服务端渲染还要看服务端日志。

**不可互换**：一条请求链路上只能有一个正文生成位置，把两者同时当作正文来源会导致内容重复或互相覆盖；常见组合是服务端生成正文、浏览器接管交互，接管过程属于本主题第 4 篇同构渲染原理。

- 客户端渲染的内容在用户设备上生成，不受服务端缓存与降级策略支配。
- 服务端渲染的内容在服务端生成，可以被服务端缓存与监控覆盖。
- 二者可以共存于同一站点，但同一页面内只保留一个正文来源。

> 位置差异决定了其余差异：内容一旦在服务端生成，就必须回答服务端算力、数据可达与降级的问题。

**速记**：内容生成的位置与时机是分水岭，其余差异都由它派生。



#### 首屏与交互的时序

**首屏与交互的时序**：描述从发出请求到页面可交互之间各阶段的先后顺序，两种模式的阶段构成不同，因此瓶颈位置也不同。

- 客户端渲染：骨架、脚本、数据三段串行，任一段变慢都会推迟首屏，脚本执行完成后页面即可交互。
- 服务端渲染：服务端取数与渲染占用首字节之前的时间，HTML 到达后即可绘制，交互仍要等脚本水合。
- 瓶颈差别：客户端渲染的瓶颈常在脚本体积与首轮接口，服务端渲染的瓶颈常在服务端取数。
- 优化方向：前者做代码分割与接口聚合，后者做缓存、并发取数与流式输出。

```text
客户端渲染：T1 骨架 → T2 脚本就绪 → T3 数据就绪 → T4 首屏 → T5 可交互
服务端渲染：T1 服务端取数 → T2 含正文的 HTML → T3 首屏 → T4 脚本就绪 → T5 可交互
```

- 首屏可绘制与可交互是两个时刻，服务端渲染把前者提前，后者仍取决于脚本。
- 服务端渲染的 T1 包含取数时间，慢接口会直接推迟首字节。
- 客户端渲染的 T4 与 T5 通常接近，服务端渲染的 T4 明显早于 T5。

**指标对应**：可绘制时刻对应首次内容绘制，可交互时刻对应首次输入延迟与交互就绪时间；指标的定义与测量方式属于本主题第 6 篇 SEO 与首屏性能。

> 评价两种模式时要把「可绘制」与「可交互」分开看，否则容易把服务端渲染的首屏收益误当作交互收益。

**速记**：客户端渲染串行等脚本与数据，服务端渲染提前可绘制、但仍要等水合才能交互。



#### 服务器负载与部署形态

**服务器负载与部署形态**：指两种模式对服务端的角色要求，客户端渲染只需托管静态文件与接口，服务端渲染还需要执行渲染的常驻运行时。

- 客户端渲染：静态产物可放到内容分发网络，服务端只承担接口请求。
- 服务端渲染：每个页面请求都要经过渲染进程，算力开销与请求量正相关。
- 缓存差异：静态产物可长期缓存，服务端渲染的结果要按内容变化频率决定缓存策略。
- 扩容方式：前者横向扩展接口服务即可，后者还要考虑渲染实例的伸缩与冷启动。

```bash
# 客户端渲染：只需静态托管与接口服务
npx serve dist

# 服务端渲染：需要常驻进程处理每次页面请求
node server.js
# Server running at http://localhost:3000
```

- 容量估算：按峰值每秒请求数乘以单次渲染耗时，估算所需渲染实例数。
- 缓存分层：页面级缓存与数据级缓存分别设置，避免同一份数据被反复渲染。
- 降级路径：渲染超时或异常时回退到静态骨架或错误页，保住可用性。

> [!CAUTION]
> **注意内容**：把服务端渲染的实例当作静态服务器扩容，会在流量峰值时因渲染排队导致首屏反而慢于客户端渲染。

**速记**：客户端渲染的服务端只做接口，服务端渲染的服务端还要承担每次请求的渲染算力。



#### 常见误解辨析

**常见误解辨析**：是澄清关于两种模式的几个高频错误判断，避免把相关性当作因果。

- 误解一：服务端渲染一定更快。服务端取数过慢时，首字节可能晚于客户端渲染的骨架到达。
- 误解二：客户端渲染一定不可被抓取。配合预渲染或在构建期生成静态页，同样可以提供完整正文。
- 误解三：用了服务端渲染就不需要客户端渲染。接管后的跳转与交互仍由浏览器执行的前端代码完成。
- 误解四：服务端渲染就是返回静态 HTML。没有缓存时它是逐请求计算的，与静态文件是两回事。

```text
判断「是否可被抓取」：看首次响应体是否含正文，而不是看用了哪种框架
判断「首屏是否更快」：看首字节与可绘制时刻，而不是看渲染发生在哪一端
```

> 框架默认开启某种模式，不代表该模式适合当前页面；模式选择应由内容特征决定。

> [!WARNING]
> **警告内容**：把服务端渲染当作性能兜底手段全站开启，会在只有登录用户可见的页面上白白消耗服务端算力，并放大故障面。

**速记**：服务端渲染不必然更快，客户端渲染不必然抓不到，模式要按页面特征选。



### 何时选择服务端渲染

**何时选择服务端渲染**：是在内容特征、访问场景与成本约束之间做取舍，判断依据是页面内容对首屏可见性与可抓取性的依赖程度。

#### 内容与可抓取性要求

**内容与可抓取性要求**：是选择服务端渲染的首要条件，页面正文需要被搜索、分享或第三方读取时，正文必须出现在首次响应中。

- 内容型页面：文章、商品详情、问答与文档，正文本身就是主要交付物。
- 分享场景：链接被转发到聊天工具或社交平台，抓取程序读取的是首次响应。
- 无脚本环境：部分抓取程序与老旧设备不执行脚本，响应体是唯一内容来源。
- 边界判断：内容仅在登录后可见，或本就无抓取价值时，可抓取性不构成选择理由。

```text
需要正文出现在首次响应：文章页、商品详情、公开主页、文档页
不需要：登录后的个人面板、内部管理后台、纯交互工具
```

- 强依赖：正文即交付物的公开内容页。
- 弱依赖：正文可在浏览器补齐、抓取价值有限的功能页。
- 无依赖：仅登录可见或仅内部使用的页面。

**验证方式**：在浏览器中关闭脚本执行后重新打开页面，正文仍然可见说明正文来自服务端；正文消失则说明它由脚本补齐。

> 可抓取性的机制与指标属于本主题第 6 篇 SEO 与首屏性能，本篇只把它作为选择依据之一。

**速记**：正文需要被抓取或被直接读取时，服务端渲染是必要条件之一。



#### 首屏体验与弱网场景

**首屏体验**：是用户对页面可用速度的直接感受，在脚本体积大或网络条件差的场景下，服务端渲染能显著提前正文的出现时刻。

- 弱网环境：移动网络下脚本下载耗时被放大，先拿到含正文的 HTML 收益明显。
- 低端设备：脚本解析与执行成本高，减少首屏对脚本的依赖可降低卡顿。
- 关键内容优先：首屏承担转化或阅读任务的页面，正文越早出现越好。
- 成本对价：若服务端取数本身很慢，需要先做缓存与并发，否则收益会被抵消。

```text
弱网首屏（客户端渲染）：骨架 1.5 s → 脚本 3.0 s → 数据 2.5 s → 约 7.0 s
弱网首屏（服务端渲染）：服务端取数 0.8 s → 含正文 HTML → 约 1.2 s
```

> [!TIP]
> **建议内容**：服务端取数链路较长时，先把串行请求改为并发并加缓存，再评估是否值得为同一页面引入服务端渲染。

**速记**：脚本重、网络差、首屏关键时，服务端渲染提前正文的收益最明显。



#### 不适合服务端渲染的场景

**不适合服务端渲染的场景**：是那些首屏与可抓取性收益不足以抵偿服务端成本的页面，选择客户端渲染更合适。

- 登录后页面：内容只对特定用户可见，抓取无意义，个性化也可在浏览器内完成。
- 交互密集型应用：编辑器、绘图与实时协作类工具，首屏之后几乎全部由浏览器承担。
- 更新极不频繁的内容：文档与营销页更适合在构建期生成静态产物，不必逐请求渲染。
- 流量极高的公共接口：若内容对所有用户一致，缓存静态产物比逐请求渲染更省算力。

```text
不适合服务端渲染：个人面板、管理后台、编辑器、实时协作工具
更适合静态生成：帮助文档、营销页、公告页
```

- 判断顺序：先确认可抓取性与首屏是否必需，再看交互是否密集，最后看内容是否可静态化。
- 混合做法：同一站点内按页面分别选择模式，不必全站统一。

**替代手段**：这些页面并非只能选客户端渲染，构建期生成静态产物同样是常见做法；两种替代手段的共同点是避免逐请求的渲染开销。

> 这些场景并不排斥服务端渲染技术本身，只是使用它的边际收益低，把算力留给出收益的页面更合理。

**速记**：内容私有、交互密集或可静态化时，客户端渲染或静态生成比服务端渲染更划算。
