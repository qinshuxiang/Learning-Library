## 参考资料与延伸阅读

### 官方文档

#### Next.js 官方文档

**Next.js 官方文档**：是 Next.js 路由约定、数据获取与部署能力的权威出处，地址为 nextjs.org。

- 应用路由章节按目录约定逐条说明页面、布局、加载与错误文件的文件名与作用，是核对约定细节的第一入口。
- 数据获取与缓存章节说明请求级缓存的开关与再验证机制，是排查「数据不更新」类问题的起点（详见本主题第 8 篇 Next.js 数据获取与缓存）。
- 渲染章节区分服务端组件与客户端组件的适用边界，并给出可交互组件标记的最小示例（详见本主题第 9 篇 Next.js 进阶：服务端组件与流式渲染）。
- 部署章节分别给出静态导出、服务端运行与边缘运行的构建产物差异，用于判断目标平台是否支持所选渲染模式。

> 文档站以当前稳定大版本为准，页面上的示例默认采用最新的路由约定；与旧写法混用时先确认所在版本。

**速记**：Next.js 的路由约定、缓存开关与部署产物都在 nextjs.org，排查数据不更新先看缓存章节。



#### Nuxt 官方文档

**Nuxt 官方文档**：是 Nuxt 目录约定、数据获取与渲染模式配置的权威出处，地址为 nuxt.com。

- 目录约定章节列出页面、组件、组合式函数等自动导入目录的扫描规则，是理解「文件即路由」的依据。
- 数据获取章节说明服务端与客户端两套取数组合式函数的差异与适用场景。
- 渲染模式章节给出预渲染、服务端渲染与客户端渲染三种策略的配置方式与混合用法。
- 模块生态页面集中列出官方与社区模块，接入前先确认模块支持的目标渲染模式。

> Nuxt 的自动导入会掩盖模块来源，排查「找不到变量」类报错时先确认文件名是否落在约定目录内。

**速记**：Nuxt 按目录约定自动导入，渲染模式与取数方式在 nuxt.com 的对应章节查。



#### Web 平台与性能规范文档

**Web 平台与性能文档**：指 MDN 与 web.dev 两个站点，前者是 HTML、CSS、浏览器 API 的参考手册，后者是性能与最佳实践的教程站点。

- MDN：developer.mozilla.org，用于核对标签语义、属性取值与浏览器兼容性表格。
- web.dev：给出核心网页指标的定义、测量方式与优化清单，指标与采集口径以此为准（详见本主题第 6 篇 SEO 与首屏性能）。
- 两个站点都提供交互示例，可直接在页面内验证行为，不必本地搭环境。

> 性能指标的定义会随标准演进而调整，引用指标名称与阈值前先确认页面更新日期。

**速记**：语义与兼容性查 MDN，性能指标的定义与优化清单查 web.dev。



#### 小程序与跨端框架文档

**小程序与跨端框架文档**：指各平台开放文档与跨端框架的官方文档，用于核对平台能力、兼容性与构建配置。

- 微信开放文档：developers.weixin.qq.com，含运行机制、组件、接口与基础库版本说明，是本主题第 14 至第 16 篇的主要依据。
- uni-app 文档：uniapp.dcloud.net.cn，按平台分别标注支持情况，跨端差异以各平台的标注为准。
- Taro 文档：docs.taro.zone，说明多端构建配置与各端产物形态。
- React Native 文档：reactnative.dev，含核心组件、样式属性与原生模块接口；Expo 文档：docs.expo.dev，覆盖工具链与云端构建流程。

> [!WARNING]
> **警告内容**：各平台文档中「支持」与「部分支持」的标注随基础库版本变化，接入前必须确认目标用户的基础库版本下限，不能只看文档首页的结论。

**速记**：平台能力以各平台开放文档的版本标注为准，跨端差异看框架文档的分平台说明。



#### 框架官方文档

**框架官方文档**：指 React、Vue 等渲染库的官方文档，用于核对组件写法与状态管理约定。

- React：react.dev，组件、Hook 与并发特性的说明以该站为准，本主题的示例以此为基础（详见 前端/React 主题）。
- Vue：vuejs.org，组合式 API 与响应式系统的说明以该站为准（详见 前端/Vue3 主题）。
- 两个站点都提供交互式教程，适合在阅读框架层文档前先建立写法直觉。

> 本主题不重讲框架基础，遇到组件与响应式细节时按上述站点补齐，避免把渲染模式的问题误判为框架用法问题。

**速记**：框架基础查 react.dev 与 vuejs.org，本主题只讲框架之上的一层。



### 规范与提案

#### 元信息与抓取协议

**元信息与抓取协议**：指描述页面标题、摘要、结构化数据与站点地图的一组公开约定，决定页面在搜索结果与社交分享中的呈现方式。

- Open Graph 协议：ogp.me，定义社交平台抓取的标题、描述、图片等元信息字段。
- 结构化数据：schema.org，定义机器可读的数据类型与字段，用于标注文章、商品等实体。
- 站点地图与抓取规则：sitemaps.org 定义站点地图格式，机器人排除协议定义允许与禁止抓取的范围。
- 规范链接（canonical）用于声明同一内容的主地址，避免多份地址被判为重复内容。

> 这些约定不是强制标准，平台会自行决定是否采用；写法正确不等于一定被抓取，投放前用各平台的调试工具实测。

**速记**：元信息按 Open Graph 与 schema.org 写，抓取范围看站点地图与机器人排除协议。



#### 渲染与组件模型提案

**渲染与组件模型提案**：指围绕服务端组件、流式传输与部分预渲染的公开说明，用于判断某项能力是否已进入稳定阶段。

- 服务端组件的边界规则由框架实现约定，跨框架尚未统一，选型时按框架自身的说明为准。
- 流式传输依赖分块响应，中间层与代理必须关闭响应缓冲，否则流式失效（详见本主题第 9 篇 Next.js 进阶：服务端组件与流式渲染）。
- 部分预渲染把页面拆为静态外壳与动态洞，属较新能力，落地前先确认托管环境是否支持。

> 提案阶段的特性名称与行为都可能调整，生产项目引入前先核对框架当前版本的说明，不要照搬早期文章。

**速记**：服务端组件与流式的规则按框架文档判，引入前先确认托管环境是否配套。



#### 部署与运行时约定

**部署与运行时约定**：指服务端运行环境与边缘运行环境在可用接口上的差异说明，决定同一份代码能否跨环境运行。

- 边缘环境通常只提供受限的运行时接口与受限的执行时长，依赖原生模块的代码无法直接运行。
- 服务端运行环境可按常规方式使用文件系统与长连接，适合需要持久连接或较重计算的场景。
- 静态导出要求页面在构建期即可确定内容，运行期无法再访问请求上下文。

> [!CAUTION]
> **注意内容**：本地开发默认走服务端运行环境，代码在边缘环境可能整体不可用；选择边缘部署前必须在目标环境完成一次完整验证。

**速记**：先定运行环境再写代码，边缘环境的接口与时长限制是硬约束。



#### 小程序基础库与兼容性

**小程序基础库版本**：指各平台客户端内置的能力集合版本，决定某个组件或接口在用户设备上是否可用。

- 接口与组件均标注最低基础库版本，低于该版本时调用会失败或降级。
- 版本分布可查平台后台的统计，用于确定需要兼容的下限。
- 需要在低版本上提供等价能力时，用能力探测加降级分支处理。

> 版本下限定得过高会丢掉旧版客户端的用户，定得过低会显著增加兼容代码，取舍依据应是目标用户的实际版本分布。

**速记**：接入前先查目标平台的基础库版本分布，兼容代码按探测加降级写。



### 经典文章与书籍

#### 渲染模式的对比文章

**渲染模式对比文章**：指系统比较各类渲染策略适用场景的文章，用于建立模式与业务场景的对应关系。

- 关注三个维度：内容时效性、是否依赖请求上下文、是否要求可被搜索引擎抓取。
- 纯静态内容与营销页优先静态生成，需登录且变化频繁的页面走客户端渲染，二者之间再考虑服务端渲染。
- 阅读顺序建议先看模式总览，再看具体框架的落地写法（详见本主题第 3 篇 渲染模式全景：CSR、SSR、SSG、ISR 与流式）。

> 对比类文章的结论多基于特定业务场景，不能直接套用；判断依据应回到本主题第 2、3 篇给出的三维度取舍。

**速记**：模式选型看时效性、请求上下文与可否被抓取三个维度。



#### 同构与水合主题文章

**同构与水合主题文章**：指讲解服务端产出与客户端接管衔接机制的文章，是排查首屏交互异常的背景材料。

- 关注三类知识点：标记的产出与还原、状态的下发与恢复、事件监听的绑定时机。
- 水合不匹配的典型成因包括时间与随机数、浏览器专属接口、标签结构非法嵌套（详见本主题第 5 篇 水合机制与常见问题）。
- 事件绑定完成前的交互空窗期是首屏体验的常见短板，相关文章给出的测量与缓解手段值得参考。

> 社区文章常把水合与首屏加载混为一谈，阅读时注意区分：前者是接管机制，后者是资源加载过程。

**速记**：水合文章抓三件事——标记还原、状态恢复、事件绑定时机。



#### 跨端方案的实践文章

**跨端方案实践文章**：指比较各跨端路线落地成本的文章，用于补充选型所需的工程经验。

- 关注四个维度：渲染承载方式、可复用代码的比例、原生能力的可达深度、调试与发布链路。
- 以 Web 视图承载的方案上限受视图层限制，编译为原生控件的方案在复杂交互上表现更接近原生。
- 阅读时优先选择标注了框架版本与实际平台范围的篇目（详见本主题第 13 篇 跨端开发概览与方案选型）。

> 实践文章的作者立场常与所用方案绑定，横向对比多篇再下结论比采信单篇更可靠。

**速记**：跨端选型看承载方式、复用比例、能力深度与发布链路四个维度。



#### 中文书籍与系统教程

**中文书籍与系统教程**：指系统讲解服务端渲染与跨端开发的中文出版物与在线教程。

- 服务端渲染方向的中文出版物多成书于较早版本，路由与数据获取章节需要对照框架当前文档重读。
- 跨端方向的中文资料以小程序的出版物最为成熟，其运行机制与组件体系部分仍然适用。
- 官方教程（如框架自带的入门课程）更新最及时，适合作为上手的第一份材料，出版物用于补齐原理与体系。

> [!NOTE]
> **提醒内容**：本领域版本迭代快，出版物的配置示例常落后一到两个大版本，阅读重点应放在机制与取舍上，代码以官方文档为准。

**速记**：旧书读机制与体系，配置与 API 一律回到官方文档核对。



### 工具与在线调试

#### 首屏与性能评测工具

**首屏与性能评测工具**：用于量化加载与交互表现，是优化前后的对比依据。

- 浏览器开发者工具的性能与网络面板：查看请求瀑布、主线程任务与长任务分布，定位阻塞渲染的环节。
- 页面质量评测工具：对给定地址输出核心指标与改进建议，适合建立基线。
- 框架自带的构建分析输出：列出各路由的产物体积，用于判断首屏包体是否超预算。

> 评测结果受网络与设备影响较大，对比优化效果时须固定网络与设备条件，否则数据没有可比性（详见本主题第 6 篇 SEO 与首屏性能）。

**速记**：先固定网络与设备，再拿指标做前后对比。



#### 抓取与分享效果调试

**抓取与分享效果调试**：用于验证页面在搜索结果与社交分享中的实际呈现，属于上线前的必查项。

- 平台提供的链接调试工具：输入地址后可查看抓取到的标题、描述与图片，并触发重新抓取。
- 结构化数据校验工具：按标注类型检查字段是否完整、是否被正确解析。
- 分享卡片调试工具：核对社交平台的卡片字段是否生效，缓存未刷新时先用调试工具刷新。

> [!IMPORTANT]
> **重要内容**：服务端渲染解决了「能否被抓取」，但不保证「呈现是否正确」；元信息标注错误时，渲染再完整也拿不到理想的展示效果。

**速记**：抓取用平台调试工具实测，呈现效果看元信息标注是否正确。



#### 跨端调试与真机工具

**跨端调试工具**：用于在各端查看运行状态，弥补浏览器调试器无法覆盖的部分。

- 平台开发者工具：提供模拟器、页面结构与网络面板，可在开发期完成大部分逻辑调试。
- 真机调试与远程调试：模拟器无法复现的问题（如输入法、字体、硬件能力差异）必须回到真机验证。
- 跨端框架的调试模式：把各端运行时差异映射回源码位置，便于定位平台分支中的错误。

> 模拟器与真机表现存在系统性差异，涉及布局与硬件能力的改动一律以真机结论为准（详见本主题第 21 篇 跨端工程化、调试与发布）。

**速记**：逻辑在模拟器调，布局与硬件能力差异必须上真机。



#### 依赖与包体积检查

**依赖与包体积检查工具**：用于控制跨端与服务端渲染项目的产物体积，避免首屏包超出预算。

- 包体积查询站点：查看依赖在压缩前后的体积，作为选型依据。
- 框架的构建分析输出：按路由列出产物构成，定位体积异常的来源。
- 依赖健康检查：找出未被使用与重复安装的依赖，减少无用产物。

> 体积数据随版本变化，选型与优化都应基于当前版本重新测量，不要沿用旧结论。

**速记**：体积预算靠构建分析输出把关，选型体积以当前版本实测为准。



### 进阶方向

#### 边缘渲染与流式传输

**边缘渲染方向**：以把渲染推近用户为目标，涵盖边缘运行环境、流式响应与缓存分层。

- 边缘节点擅长处理静态外壳与轻量逻辑，重计算与持久连接仍需回到中心服务端。
- 流式传输把页面分块下发，首字节时间与首屏可见时间可显著改善，但需要中间层配合关闭缓冲。
- 缓存分层决定命中率，静态资源与数据缓存的失效策略需分别设计。

> 边缘化不是默认更优：当渲染依赖数据库或重计算时，跨区域的往返反而会拉长响应时间。

**速记**：边缘适合外壳与轻逻辑，流式要中间层配合，缓存分层分别设计。



#### 服务端组件与数据缓存

**服务端组件方向**：以缩小客户端产物并把数据获取移向服务端为目标，涵盖组件边界划分与缓存策略。

- 边界划分的原则是让可交互部分尽量下沉到叶子节点，避免整棵子树转为客户端组件。
- 数据缓存的粒度决定复用程度，与请求上下文绑定的数据无法跨请求复用。
- 缓存失效既要考虑时间，也要考虑数据变更事件，纯时间策略会产生可感知的陈旧窗口。

> [!WARNING]
> **警告内容**：缓存的默认开启与默认关闭在不同框架版本中可能相反，误判会使数据长期陈旧或请求量陡增；上线前必须验证一次数据更新的端到端时延。

**速记**：边界下沉到叶子，缓存粒度按请求上下文定，失效兼顾时间与变更事件。



#### 跨端原生能力与性能

**跨端原生能力方向**：以在跨端方案中调用原生能力并改善复杂交互表现为目标。

- 原生模块封装：把各端差异收敛到统一接口，业务层只依赖统一接口。
- 长列表与动画：以视图层承载的方案需借助虚拟列表与原生动画能力避让性能瓶颈。
- 包体与启动：按需加载与分包能显著改善小程序的启动时间。

> 引入原生模块会同时引入各端维护成本，只有在性能或能力确为硬约束时才值得承担。

**速记**：原生能力统一封装到一层接口，长列表与动画优先用原生能力。



#### 可观测性与线上排错

**可观测性方向**：以在线上还原问题现场为目标，涵盖错误采集、性能采样与版本对照。

- 错误采集需区分服务端与客户端两侧，同构应用中的同一异常可能在两侧各报一次，需去重。
- 用户侧性能采样应记录渲染模式与产物版本，否则无法判断劣化来自哪一次发布。
- 线上排错依赖可回滚的发布流程，灰度与回滚能力应在项目初期建立（详见本主题第 21 篇 跨端工程化、调试与发布）。

> 服务端渲染把错误从浏览器搬到了服务端，采集与告警链路需要相应补齐，沿用纯客户端方案会丢掉大部分首屏异常。

**速记**：双侧采集去重，采样记录渲染模式与版本，排错依赖灰度与回滚。
