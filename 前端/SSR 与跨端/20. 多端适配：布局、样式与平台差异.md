## 多端适配：布局、样式与平台差异

**多端适配**：是让同一套界面代码在 Web、微信小程序、支付宝小程序、iOS、Android、桌面端等不同视口与运行环境中都能正确呈现与交互的工程处理。

本篇回答四件事：布局如何随视口变化、样式如何避免互相污染、尺寸单位如何换算、平台能力差异如何收敛。四件事分别对应布局层、样式层、单位层与能力层，是有先后依赖的适配顺序。

### 响应式与自适应布局

本节确立适配的第一层：布局本身要能随可用空间伸缩，而不是为每个端各写一套结构。

#### 视口与设备宽度差异

**视口（viewport）**：是页面用于布局的可用区域尺寸，在浏览器中由窗口与缩放决定，在小程序与原生应用中由设备逻辑尺寸决定。

- Web：视口等于布局视口，受视口元信息与用户缩放影响，桌面端还可任意拖动窗口。
- 小程序：各宿主提供各自逻辑像素宽度的视口，取值范围通常跨越手机与平板。
- iOS 与 Android：视口为设备逻辑宽度，还需扣除刘海与系统手势区域的遮挡。
- 桌面端：窗口可缩放且可多窗口并存，宽度变化范围最大，还存在鼠标悬停等指针差异。

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

各端可用的布局宽度范围差异明显，这是不能用一套固定尺寸覆盖全部端的根本原因。适配前应先明确各端需要覆盖的宽度区间，再据此决定断点位置。

```text
Web 桌面端：宽度可连续变化，从约 320 到数千逻辑像素
Web 移动端：常见区间约为 320 至 480 逻辑像素
小程序：常见区间约为 320 至 768 逻辑像素
iOS 与 Android：手机约为 320 至 480，平板可达 1024 以上
```

> 视口差异决定了适配策略：宽度范围越大，越依赖流式布局与容器级断点，而不是针对具体机型写死尺寸。

**速记**：视口是布局可用区域，各端宽度范围与遮挡情况不同。



#### 断点与流式布局

**断点（breakpoint）**：是布局结构发生变化的视口宽度阈值，常见做法是在移动宽度与桌面宽度之间设置一到两个关键节点。

- 移动优先：默认样式按最窄视口编写，再用最小宽度条件逐级增强。
- 流式尺寸：宽度用百分比或弹性单位，配合最小宽度与最大宽度约束伸缩范围。
- 自适应网格：用自动填充与最小最大函数让列数随容器宽度自动增减，减少手写断点。
- 断点数量：控制在少量关键节点，断点越多越难维护，也越容易出现中间宽度错位。

```css
.card-list {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));
  gap: 16px;
}
```

结构确实需要变化时，断点条件写成最小宽度即可。移动优先的写法让窄视口不必重复声明默认值，后续断点只追加差异。

```css
.sidebar {
  display: none;
}

@media (min-width: 768px) {
  .sidebar {
    display: block;
    width: 240px;
  }
}
```

> [!TIP]
> **建议内容**：优先用弹性布局与自适应网格解决伸缩，只在结构确实要改变时（例如侧栏折叠为抽屉）才引入断点，可以减少大量边界样式的调试成本。

**速记**：移动优先加少量断点，能伸缩的交给弹性布局与自适应网格。



#### 容器查询与组件自适应

**容器查询（container query）**：是让组件依据自身容器的宽度而非视口宽度切换样式的机制，适合同一组件在不同布局位置复用的场景。

- 声明容器：在父元素上声明为可查询容器，并指定按宽度还是按尺寸查询。
- 组件内查询：组件内部按容器宽度写条件样式，与页面整体宽度解耦。
- 适用场景：卡片在宽栏中横排、在窄栏中竖排，无需页面级断点介入。
- 回退方案：不支持容器查询的环境退化为媒体查询或固定布局。

```css
.card-wrap {
  container-type: inline-size;
}

@container (min-width: 360px) {
  .card {
    display: flex;
    align-items: center;
  }
}
```

容器查询的代价是调试时需要同时关注页面宽度与容器宽度两个变量，因此容器本身应保持单一职责：要么是整块内容区，要么是列表项，不要出现容器套容器又各自查询的写法。

> 组件级自适应让适配责任下沉到组件内部，页面只负责排布容器，这一分工比把所有断点写在页面样式里更易维护。

**速记**：容器查询按容器宽度切换样式，组件自适应不依赖页面断点。



### 样式作用域与隔离

本节确立适配的第二层：样式必须限定作用范围，否则多端复用与组件复用都会带来覆盖问题。

#### 全局样式与类名冲突

**全局样式表**：是所有规则共享同一命名空间、后加载者覆盖先加载者的样式组织方式，在样式文件分散时容易产生冲突。

- 命名空间共享：类名在整个页面内有效，不同组件使用相同类名会互相影响。
- 加载顺序敏感：最终生效取决于样式注入顺序，而顺序可能随构建拆分发生变化。
- 影响范围：选择器越宽泛影响面越大，元素选择器与后代选择器风险最高。
- 排查成本：冲突往往在特定页面组合下才出现，线上难以稳定复现。

```css
/* 两个组件都声明了 .title，后加载者覆盖前者 */
.title {
  color: #333;
}

.title {
  color: #ffffff;
}
```

命名约定可以降低冲突概率，例如给类名加组件前缀，但它依赖人工遵守，也不解决选择器权重与加载顺序问题。真正可靠的做法是由构建工具生成唯一名称，把作用域交给机器保证。

> [!CAUTION]
> **注意内容**：依赖加载顺序决定样式的写法在开发环境可能正常，构建产物拆分或按需加载后会突然失效，必须用作用域手段规避。

**速记**：全局类名共享命名空间，冲突结果取决于加载顺序，不可依赖。



#### CSS Module 与局部作用域

**CSS Module**：是在构建期为样式文件中的类名生成唯一名称、把映射关系作为对象导出的方案，让样式默认只对本组件生效。

- 构建期改写：类名被改写为带哈希的唯一标识，跨文件不会重名。
- 引用方式：导入后按对象属性使用，属性名与源码中的类名一致。
- 组合能力：可用组合语法复用另一个类的声明，在保持局部作用域的同时减少重复。
- 适用范围：适合用类名组织样式的技术栈，各端构建链均可支持。

```css
/* card.module.css */
.title {
  color: #111111;
  font-weight: 600;
}
```

```tsx
import styles from "./card.module.css";

export function Card({ title }: { title: string }) {
  return <div className={styles.title}>{title}</div>;
}
```

需要覆盖第三方组件样式时，作用域方案并不阻塞全局样式：把覆盖规则写在全局入口，并用足够具体的选择器限定范围即可。关键是覆盖规则要集中管理，不要散落在业务组件中。

> [!TIP]
> **建议内容**：组件样式一律使用作用域方案，只在全局入口保留重置样式与主题变量，可以让样式覆盖问题在编译期就变得不可能。

**速记**：CSS Module 把类名改写为唯一标识，样式默认只对本组件生效。



#### 影子树与样式隔离

**影子树（shadow tree）**：是与主文档树分离的子树，子树内外的样式互不影响，小程序自定义组件也采用同类隔离思路。

- Shadow DOM：元素内部结构对外不可见，外部选择器无法穿透，样式天然封闭。
- 小程序组件：自定义组件默认样式隔离，页面样式与组件样式互不污染。
- React Native：样式没有级联与继承链，每个元素只接受显式传入的样式对象。
- 跨端取舍：隔离越彻底，主题定制与样式覆盖越需要约定好的入口。

```css
:host {
  display: block;
}

.item {
  color: #333333;
}
```

跨端项目里隔离程度并不一致，同一个组件在 Web 端可能被外部样式影响，在小程序与原生端却不会。这种不对称是排查样式问题的常见盲区，处理时应以隔离最强的那一端为基准设计组件接口。

> 样式隔离不是终点，主题与定制需要通过设计变量或配置属性开放，否则使用方只能靠穿透选择器破坏封装。

**速记**：影子树与组件级隔离让样式不外泄，定制入口要用变量或属性开放。



### 屏幕单位与适配方案

本节确立适配的第三层：长度单位与换算基准统一，是不同设计稿宽度能在各端等比还原的前提。

#### 常见长度单位与设备像素比

**设备像素比（device pixel ratio，DPR）**：是物理像素与逻辑像素的比值，决定一个逻辑单位对应多少物理像素。

- 逻辑像素：布局使用的单位，各端以逻辑像素描述尺寸与间距。
- 设备像素比：高分屏上大于一，位图资源需按倍数准备以保持清晰。
- 相对单位：rem 相对根字号，vw 相对视口宽度的百分之一，rpx 是小程序中以固定设计稿宽度为基准的相对单位。
- 原生单位：iOS 与 Android 各有自己的逻辑像素单位，跨端框架会将其统一映射。

```css
/* 根字号随视口宽度变化，使用 rem 的元素随之等比缩放 */
html {
  font-size: clamp(14px, 4vw, 20px);
}
```

小程序的相对单位以固定设计稿宽度为基准，运行时由宿主按屏幕宽度换算，因此标注值可以直接照抄设计稿，不需要手工计算。Web 端没有等价单位，需要用根字号或视口单位自行换算。

```text
rpx：以 750 逻辑像素的设计稿宽度为基准，1rpx 等于屏幕宽度的七百五十分之一
rem：相对根元素字号，需配合根字号设置才能随视口缩放
vw：视口宽度的百分之一，与视口强绑定，适合页面级尺寸而不适合组件内部
```

> 单位混用是最常见的适配缺陷来源：同一页面里既有固定像素又有相对单位，等比缩放的意图就会被固定值破坏。

**速记**：布局用逻辑像素，高分屏按设备像素比准备资源，单位口径必须统一。



#### 设计稿等比换算

**等比换算**：是以设计稿宽度为基准，把稿上标注的像素值按运行时视口宽度与设计稿宽度的比例换算为实际长度的做法。

- 基准确定：先固定设计稿宽度，取值全项目统一，常见为某一种手机或平板的逻辑宽度。
- 换算公式：实际长度等于标注值除以设计稿宽度，再乘以运行时视口宽度。
- 单位落地：Web 端通常换算为 vw 或 rem，小程序可直接使用以设计稿宽度为基准的相对单位。
- 边界处理：超过最大宽度时应钳制到上限，避免在大屏上无限拉伸文字与图片。

```js
const designWidth = 375;

function convertToVw(designPx) {
  return ((designPx / designWidth) * 100).toFixed(3) + "vw";
}

console.log(convertToVw(75)); // "20.000vw"
```

等比换算适合页面级的块状尺寸与间距，不适合所有属性一律照搬。合理的边界是：容器宽高、图片尺寸、大块间距参与等比换算；字号、行高、描边与图标线宽按可读性单独定义一套档位。

```ts
const designWidth = 375;
const minFontSize = 12;

// 先按视口等比得到像素值，再除以根字号得到 rem，最后钳制可读性下限
function convertToRem(designPx: number, rootFontSize: number): number {
  const scaledPx = (designPx / designWidth) * 375; // 以 375 宽视口为例
  return Math.max(scaledPx / rootFontSize, minFontSize / rootFontSize);
}

console.log(convertToRem(32, 16)); // 2
```

> [!WARNING]
> **警告内容**：等比换算不应作用于字号与描边等需要保持可读性的属性，无上限放大字体会在大屏幕上破坏信息层级与阅读体验。

**速记**：以设计稿宽度为基准按比例换算，字号与描边要设上限。



#### 安全区域与刘海屏

**安全区域（safe area）**：是屏幕中不被圆角、刘海或系统手势条遮挡、适合放置可交互内容的区域。

- Web 端：可用安全区域内边距环境变量取到四边遮挡量，配合内边距使用。
- 小程序：部分宿主提供安全区域信息，底部操作区需按遮挡量抬高。
- 原生侧：用安全区域容器包裹页面内容，或按系统给出的内边距调整。
- 落地原则：固定定位的底部栏、悬浮按钮与全屏背景需要分别处理遮挡。

```css
.footer {
  position: fixed;
  inset: auto 0 0 0;
  padding-bottom: calc(12px + env(safe-area-inset-bottom));
}
```

横屏状态下的安全区域与竖屏不同，遮挡会从左或右侧边出现。以宽度为主导的布局在横屏时需要额外取出左右内边距，否则内容会被圆角切掉。

> 安全区域只在真机与模拟器的特定机型上才体现差异，验收时需要在带刘海与带手势条的设备上各走一遍。

**速记**：安全区域用环境变量或安全区域容器处理，底部固定栏必须抬高。



### 平台能力差异的抽象

本节确立适配的第四层：把各端能力差异收敛到一处，让业务代码只面对统一接口。

#### 平台判断与条件渲染

**平台判断**：是依据运行端标识选择不同实现的做法，适合差异小、分支少的场景。

- 标识来源：各跨端框架都提供当前运行端的标识，运行时读取即可。
- 样式差异：不同端的外观差异可写成平台到样式对象的映射，运行时取用。
- 结构差异：结构差异较大的部分单独拆组件，在入口处按平台选择性渲染。
- 使用尺度：平台判断应集中在少量文件，散落各处会让差异难以追踪。

```tsx
import { Platform, StyleSheet } from "react-native";

const styles = StyleSheet.create({
  floatCard: {
    elevation: Platform.select({ android: 4, default: 0 }),
    shadowRadius: Platform.select({ ios: 4, default: 0 }),
  },
});
```

平台标识还常用在文件命名约定上：同名文件按端后缀区分，构建时自动选用对应实现，这样调用方完全不需要写判断语句。判断与命名约定可并存，前者用于零星差异，后者用于成建制的实现差异。

> [!IMPORTANT]
> **重要内容**：平台判断只应用于无法统一的行为差异，能用统一接口抹平的部分不应引入分支，否则每增加一个端就要改一遍业务代码。

**速记**：平台判断宜集中、宜少量，只处理无法统一的差异。



#### 适配层设计

**适配层**：是把平台差异收敛到单一模块、对上暴露统一函数签名的设计，业务代码只调用适配层而不感知当前端。

- 统一签名：同一功能在各端提供相同名称与相同参数、相同返回值。
- 差异实现：模块内部按端选择实现，缺失能力时返回明确的降级结果。
- 能力分级：把能力分为必须支持与尽力支持两类，前者缺失直接报错，后者可降级。
- 测试入口：适配层是唯一需要按端分别验证的模块，测试范围因此可控。

```ts
type SharePayload = { title: string; link: string };

export async function shareToPlatform(payload: SharePayload): Promise<boolean> {
  if (typeof navigator !== "undefined" && "share" in navigator) {
    await navigator.share(payload);
    return true;
  }
  return false;
}
```

适配层应保持纯函数式的外部形态：输入参数与返回值只使用基础类型与普通对象，不暴露平台特有的对象。这样对上层而言它就是普通工具函数，替换实现不影响调用方。

```ts
type StorageAdapter = {
  getItem: (key: string) => Promise<string | null>;
  setItem: (key: string, value: string) => Promise<void>;
};

export function createStorageAdapter(): StorageAdapter {
  return {
    async getItem(key) {
      return globalThis.localStorage?.getItem(key) ?? null;
    },
    async setItem(key, value) {
      globalThis.localStorage?.setItem(key, value);
    },
  };
}
```

> 适配层的价值在于把「多端」限制在一个目录里，业务层的条件分支与条件编译随之减少。

**速记**：适配层统一签名、内部按端实现，业务层不感知平台。



#### 设备能力探测

**能力探测（feature detection）**：是在运行时检查某项能力是否存在，而不是依据设备型号或系统版本推断。

- 优先探测：检查对象与方法的可用性，得出的结论最直接。
- 避免版本推断：按版本号判断能力会随系统更新失效，也覆盖不全厂商定制。
- 降级路径：能力缺失时给出替代交互，例如用复制链接替代原生分享。
- 与服务端协同：影响渲染结果的能力应在服务端与客户端做一致判断，避免两端结构不一致。

```js
const supportsClipboard =
  typeof navigator !== "undefined" && "clipboard" in navigator;

export async function copyText(text) {
  if (supportsClipboard) {
    await navigator.clipboard.writeText(text);
    return true;
  }
  return false;
}
```

> 同一份界面在服务端渲染与客户端接管时可能读到不同的能力判断结果，涉及结构差异时必须保证两端一致，否则会触发水合不匹配（详见本主题第 5 篇 水合机制与常见问题）。

**速记**：能力探测优于版本判断，缺失能力要走降级路径。
