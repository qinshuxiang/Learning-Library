## 同构渲染原理

### 同构渲染是什么

同构渲染回答的是同一套组件代码如何既在服务端产出完整 HTML、又在客户端继续接管交互这一问题。本模块界定它的概念与组成部分，后续三个模块再按一次请求的时间顺序拆解服务端产出、客户端接管与双端差异。

#### 同一份代码两端运行

**同构渲染（isomorphic rendering）**：是同一套应用代码既能在服务端执行并输出 HTML 文本，又能在客户端执行并为该 HTML 恢复交互能力的渲染方式，也称通用渲染（universal rendering）。

- 代码复用：组件定义、路由规则与数据格式化逻辑在两端共享，不维护两套模板。
- 首屏产出：服务端返回带内容的 HTML，浏览器在脚本下载完成之前即可渲染出文字与结构。
- 后续接管：客户端脚本加载后复用同一份组件代码接管页面，页内跳转与局部更新不再请求整页。
- 数据同源：两端渲染使用同一份数据与同一套格式化函数，降低两端结果不一致的概率。
- 环境无关：组件本身只描述「给定数据渲染成什么」，把环境相关的能力下沉到边界之外。

```tsx
// components/ArticleList.tsx：两端复用同一个组件
type Article = { id: number; title: string };

export function ArticleList({ items }: { items: Article[] }) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.title}</li>
      ))}
    </ul>
  );
}
```

上面这个组件不含任何环境判断，因此服务端可以把它求值为字符串，浏览器也可以把它渲染成真实节点，两端得到一致的结构。

> 同构渲染与服务端渲染描述的角度不同：前者强调代码在两端复用，后者强调首屏 HTML 的产出位置，同一份应用通常同时具备这两个特征。

**速记**：同构渲染是同一套代码在服务端产出 HTML、在客户端接管交互。



#### 同构渲染的三个组成部分

**同构渲染的三个组成部分**：是服务端渲染产出、首屏数据传递与客户端水合（hydration），三者按时间顺序衔接，构成一次请求的完整链路。

- 服务端渲染产出：把组件树求值为 HTML 文本，作为响应体发给浏览器。
- 首屏数据传递：把服务端渲染时用到的数据序列化后随 HTML 一起下发，供客户端复用。
- 客户端水合：客户端复用服务端产出的节点结构，为它恢复事件与状态，水合环节详见本主题第 5 篇 水合机制与常见问题。
- 三者缺一不可：只有服务端产出而无水合，页面看得见却点不动；只有客户端接管而无服务端产出，首屏退化回客户端渲染。
- 顺序固定：数据先于渲染准备，渲染先于水合发生，任意一步中断都会让链路降级。

```html
<div id="app"><ul><li>第一篇</li><li>第二篇</li></ul></div>
<script id="__APP_DATA__" type="application/json">[{"id":1,"title":"第一篇"},{"id":2,"title":"第二篇"}]</script>
<script src="/static/client.js" defer></script>
```

三段内容在响应中各占一块：容器承载结构，内联数据承载首屏值，脚本引用承载接管逻辑。三者由同一次请求产出，浏览器按顺序消费。

> 首屏数据的序列化格式由元框架决定，手写注入方案与序列化取舍属于另一话题，详见本主题第 12 篇 SSR 应用的鉴权、状态与安全。

**速记**：服务端产出、数据传递、客户端水合三部分缺一不可，顺序固定。



#### 同构不等于服务端渲染

**同构不等于服务端渲染**：同构描述代码的组织方式，服务端渲染描述首屏 HTML 的产出位置，两个概念可以同向也可以分离。

- 同构而纯客户端：同一份组件代码只在浏览器执行，仍然属于客户端渲染，首屏没有服务端产出。
- 服务端渲染而不完全同构：服务端用另一套模板产出 HTML，客户端用组件库接管，两端代码不共享。
- 判别标准：看两端是否执行同一份组件代码，而不是看是否发生过服务端请求。
- 实际收益：同构让服务端渲染与客户端导航共享逻辑，减少两套渲染结果走向不一致的风险。
- 常见误用：把「服务端请求了数据」当成同构的标志，实际上数据来自何方与代码是否复用无关。

```tsx
// 反例：服务端用字符串模板产出，客户端用组件渲染，两端不是同一份代码
export function renderArticleHtml(title: string): string {
  return `<article><h1>${title}</h1></article>`; // 模板与组件两套写法
}
```

上面这种写法虽然也产生了服务端 HTML，但客户端要重新实现一遍文章结构，结构漂移只能靠人工同步，不构成同构。

> 概念辨析的价值在于选型：追求首屏与抓取时关注服务端产出，追求两端一致时关注代码是否共享。

**速记**：同构看代码是否两端复用，服务端渲染看首屏 HTML 是否由服务端产出。



### 服务端渲染流程

服务端渲染流程描述的是：一次请求到达服务器之后，应用如何从路由匹配走到数据准备，再把组件树求值为 HTML 并连同数据一起返回。本模块按执行顺序拆成四个环节。

#### 请求进入与路由匹配

**请求进入与路由匹配**：是服务端收到 HTTP 请求后，按请求路径找到对应路由段、并确定本次要渲染的组件树的过程。

- 入口：服务器把请求交给应用的请求处理器，处理器读取请求方法、路径与查询参数。
- 匹配：文件路由或路由表按路径匹配到页面组件，动态段被解析为参数。
- 上下文：请求对象、响应对象与路径参数组装成这次渲染的上下文，供后续环节使用。
- 分支处理：未匹配到路由时返回未找到响应，匹配到受保护路由时可能先跳转。
- 流式前提：匹配完成后即可判断哪些部分可以先输出、哪些部分需要等待数据。

```bash
# 构建并启动一个服务端渲染应用
npm run build
npm run start
# Server running at http://localhost:3000
```

```js
// server.js：把请求交给应用的请求处理器
import { createServer } from "node:http";
import { handleRequest } from "./app.js";

createServer(async (req, res) => {
  const result = await handleRequest(req);      // 1. 匹配路由并渲染
  res.statusCode = result.status;
  res.setHeader("content-type", "text/html; charset=utf-8");
  res.end(result.html);                          // 2. 返回 HTML
}).listen(3000);
```

> 路由匹配发生在服务端，因此首屏 HTML 对应的路由与浏览器地址栏一致；客户端脚本加载后会接管同一个路由。

**速记**：路由匹配在服务端完成，结果决定本次要渲染的组件树。



#### 数据预取与准备

**数据预取与准备**：是在渲染组件树之前，把这次渲染需要的数据从接口、数据库或文件系统取回并整理成可渲染形态的过程。

- 服务端执行：数据获取代码在服务端运行，可以直连数据库与内部服务，不必绕行公网。
- 并行发起：同一页面内的多个请求可以并行等待，把串行等待的总耗时压回最慢的一路。
- 失败处理：请求失败时需要明确返回错误页、降级内容还是向上抛出，不能静默返回空数据。
- 依赖串联：后一步依赖前一步结果时按序发起，避免为并行牺牲正确性。
- 数据归属：取回的数据随后被组件读取，也会被序列化后下发给客户端，因此应保持精简。

```tsx
// app/articles/page.tsx：服务端组件内直接取数据
async function getArticles(): Promise<Array<{ id: number; title: string }>> {
  const res = await fetch("https://example.com/api/articles");
  return res.json();
}

export default async function ArticlesPage() {
  const articles = await getArticles();          // 服务端取回数据
  return <ArticleList items={articles} />;       // 交给组件渲染
}
```

> [!WARNING]
> **警告内容**：服务端执行的数据获取代码不得把单次请求的上下文写入模块级变量，多个并发请求会互相覆盖彼此的数据，导致内容串页。

**速记**：数据在服务端取回后再渲染，并发请求之间不得共享可变状态。



#### 组件树求值为 HTML

**组件树求值为 HTML**：是从根组件开始递归调用每个组件函数、把返回值拼装成 HTML 字符串或 HTML 流的过程。

- 递归求值：从根组件开始，逐一求值子组件，遇到数据读取则读取已经准备好的数据。
- 字符串产出：整棵树求值结束后得到完整 HTML 文本，一次性作为响应体返回。
- 流式产出：也可以边求值边输出，把先完成的部分先发给浏览器（模式差异详见本主题第 3 篇 渲染模式全景：CSR、SSR、SSG、ISR 与流式）。
- 与浏览器无关：这一阶段不产生真实节点，只是把结构写成文本，因此不依赖浏览器环境。
- 错误边界：子树求值抛错时由最近的错误边界接管，避免整个页面渲染失败。

```tsx
// 求值顺序示意：根组件先拿到数据，再向下传递
export default async function HomePage() {
  const articles = await getArticles();          // 1. 取数据
  return (
    <main>
      <h1>最新文章</h1>
      <ArticleList items={articles} />            {/* 2. 向下传数据 */}
    </main>
  );
}
```

```text
求值顺序
根组件 → 读取数据 → 求值子组件 → 拼装字符串 → 完整 HTML
```

> 服务端求值得到的是文本而不是真实节点；客户端随后用同一份组件代码把这串文本对应回可交互的节点。

**速记**：服务端把组件树递归求值为 HTML 文本或流，过程不依赖浏览器。



#### 数据序列化与响应组装

**数据序列化与响应组装**：是把服务端渲染时用到的数据转换成可嵌入 HTML 的形式，并与 HTML、脚本引用一起组成最终响应的过程。

- 序列化：把对象、数组、日期等值转成可写入 HTML 的格式，通常内联在脚本标签中。
- 标记根节点：HTML 中需要一个根容器，客户端据此找到接管的范围。
- 引用脚本：同时输出客户端入口脚本的引用，浏览器据此下载并执行接管逻辑。
- 响应头：状态码、内容类型与缓存相关头部一并设置，决定浏览器与缓存的后续行为。
- 体量控制：只序列化首屏渲染与接管真正需要的字段，无关的大对象留在服务端。

```html
<div id="app"><ul><li>第一篇</li></ul></div>
<script>window.__APP_DATA__ = [{"id":1,"title":"第一篇"}]</script>
<script src="/static/client.js" defer></script>
```

```json
{
  "status": 200,
  "contentType": "text/html; charset=utf-8",
  "cacheControl": "public, max-age=60"
}
```

> 序列化的数据只应包含渲染与接管所需的最小集合，把与首屏无关的大对象一并下发会推迟可交互时间。

**速记**：数据序列化后与 HTML、脚本引用组装成响应，只下发首屏所需的数据。



### 客户端接管流程

客户端接管流程描述的是：浏览器拿到服务端 HTML 之后，如何加载脚本、恢复数据并让静态结构变成可交互页面。本模块拆解这一过程的四个环节。

#### 客户端脚本的加载与执行

**客户端脚本的加载与执行**：是浏览器解析响应后请求入口脚本、解析并在页面中运行的过程，HTML 中的脚本引用方式与加载策略决定它何时开始。

- 引用方式：响应中的脚本标签指向客户端入口，浏览器按该地址发起请求。
- 加载时机：延迟或异步加载可以避免阻塞 HTML 解析，代价是接管时间相应后移。
- 代码分割：入口只包含首屏需要的代码，其余部分在路由切换或需要时按需加载。
- 执行环境：脚本在浏览器中运行，可以访问文档对象与浏览器 API。
- 失败影响：脚本请求失败或被拦截时页面仍可见，但不会获得交互能力。

```html
<script src="/static/client.js" defer></script>
<!-- defer：HTML 解析完成后再按顺序执行，不阻塞首屏渲染 -->
```

> 脚本下载是接管之前无法绕开的等待；把首屏内容全部依赖脚本生成，会让用户在脚本到达前看到空白页。

**速记**：客户端脚本按引用地址下载，加载策略决定接管从何时开始。



#### 复用服务端标记而非重建

**复用服务端标记而非重建**：指客户端不为首屏内容重新创建节点，而是找到服务端已经产出的节点并复用，只补齐事件与状态。

- 定位根节点：客户端按根容器的标识找到服务端产出的节点树。
- 校验一致性：客户端渲染结果需与服务端结构一致，不一致即为水合不匹配。
- 复用收益：省去首屏的重复创建与布局计算，可见内容直接可用。
- 边界处理：若根节点内已有内容，客户端需要决定清空重建还是尝试复用。
- 范围控制：只接管根容器覆盖的节点，容器之外的静态资源不受影响。

```tsx
// 客户端入口：把组件树挂到服务端产出的根节点上
import { hydrateRoot } from "react-dom/client";
import { App } from "./App";

const container = document.getElementById("app");
hydrateRoot(container, <App data={window.__APP_DATA__} />);
```

```js
// 对比：纯客户端渲染会清空根节点后重建
import { createRoot } from "react-dom/client";

const container = document.getElementById("app");
createRoot(container).render(<App />);   // 首屏内容全部由脚本生成
```

> 复用而非重建是同构渲染与纯客户端渲染在首屏阶段的核心差别，也是水合环节存在的根本原因。

**速记**：客户端复用服务端产出的节点，只补齐事件与状态，不重建首屏结构。



#### 事件绑定与状态恢复

**事件绑定与状态恢复**：是在复用节点之上注册事件监听、恢复组件内部状态的过程，这一步完成后页面才真正可交互；该环节即水合，完整机制详见本主题第 5 篇 水合机制与常见问题。

- 事件注册：为服务端产出的元素挂上事件处理逻辑，点击、输入等行为开始生效。
- 状态恢复：组件初始状态与首屏数据对齐，避免接管瞬间发生视觉跳变。
- 可交互标记：水合完成前页面可见但不可交互，完成时间是可交互时间的决定因素。
- 等待反馈：等待期间应给出明确的占位与反馈，避免用户误以为页面无响应。
- 逐块推进：现代做法允许按区域分批完成水合，让局部先可用。

```tsx
// 水合阶段只注册监听，不重新创建节点
"use client";

import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((value) => value + 1)}>{count}</button>;
}
```

> 页面「看得见」与「点得动」是两个时间点，二者之间的等待是该环节要压缩的目标。

**速记**：水合在复用节点上注册事件并恢复状态，完成后页面才可交互。



#### 接管之后的客户端导航

**接管之后的客户端导航**：是水合完成之后，后续路由跳转交给客户端处理、只请求数据与组件资源而不重载整页的过程。

- 拦截跳转：客户端接管站内链接点击，改为按路由加载目标页面的资源。
- 增量更新：只替换变化的部分，保留布局与浏览器状态，避免整页闪烁。
- 数据获取：目标页面所需数据由客户端按约定获取，而非重新走一次完整服务端渲染。
- 回退路径：首次直达或脚本未就绪时仍由服务端产出完整 HTML，保证可用性。
- 预取：视图内的链接可提前请求目标资源，使点击后的等待降到最低。

```tsx
// 客户端导航：点击站内链接后仅按路由加载目标页
import Link from "next/link";

export function NavBar() {
  return (
    <nav>
      <Link href="/articles">文章列表</Link>
    </nav>
  );
}
```

> 服务端渲染负责首次直达的首屏，客户端导航负责其后的站内跳转，二者共用同一份路由定义与组件代码。

**速记**：水合后站内跳转由客户端接管，只换内容不重载整页。



### 双端代码差异与处理

同一份代码在服务端与浏览器中的运行条件并不相同：可用的全局对象、生命周期的时机与副作用的执行次数都有差别。本模块列出这些差异及其处理方式。

#### 运行时全局对象差异

**运行时全局对象差异**：指服务端没有浏览器提供的窗口对象、文档对象与本地存储等全局能力，直接引用会在服务端执行时报错。

- 浏览器独有：窗口对象、文档对象、本地存储与部分浏览器 API 只在浏览器中存在。
- 服务端独有：进程信息、文件系统与网络底层能力只在服务端存在。
- 报错形态：在服务端执行到浏览器独有对象时会抛出引用错误，导致整个页面渲染失败。
- 判断方式：访问之前先判断对象是否存在，再决定是否调用。
- 收敛位置：把环境判断封装成小函数，供各组件复用，避免判断散落各处。

```ts
// 判断运行环境，避免在服务端引用浏览器对象
const isBrowser = typeof window !== "undefined";

export function readScrollTop(): number {
  if (!isBrowser) return 0;
  return window.scrollY;
}
```

> [!WARNING]
> **警告内容**：在模块顶层直接引用浏览器独有对象会在服务端导入该模块的瞬间抛错，必须把访问推迟到函数体内并加环境判断。

**速记**：服务端没有浏览器全局对象，引用之前必须先判断环境。



#### 副作用与生命周期时机差异

**副作用与生命周期时机差异**：指同一段副作用代码在服务端与客户端执行的时机和次数不同，服务端可能每次请求都执行，客户端只在浏览器中执行一次。

- 服务端副作用：按请求执行，不能依赖「只执行一次」的假设，且不能触碰浏览器能力。
- 客户端副作用：在节点挂载之后执行，可安全访问浏览器能力与订阅外部事件。
- 执行次数：服务端渲染阶段不执行挂载后的副作用，因此不能指望它准备首屏内容。
- 清理责任：订阅与定时器需要在卸载时清理，否则客户端会累积重复的监听。
- 状态初值：依赖浏览器结果的状态应给一个两端一致的安全初值，挂载后再更新。

```tsx
"use client";

import { useEffect, useState } from "react";

export function ViewportWidth() {
  const [width, setWidth] = useState(0);             // 两端一致的安全初值
  useEffect(() => {
    setWidth(window.innerWidth);                     // 仅在浏览器中执行
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return <span>{width}</span>;
}
```

> 依赖浏览器能力的逻辑应放进客户端组件与挂载后的副作用中，服务端组件保持纯求值。

**速记**：副作用在服务端按请求执行、在客户端挂载后执行，依赖浏览器的逻辑放挂载后。



#### 浏览器专属 API 的隔离

**浏览器专属 API 的隔离**：是把依赖浏览器能力的代码集中到受控位置，使服务端渲染路径完全不触碰这些能力。

- 组件标记：把依赖浏览器能力的部分标为客户端组件，服务端只渲染它周边的结构。
- 挂载后取值：需要在首屏展示的尺寸、时区等值，先在两端渲染同一占位，挂载后再更新。
- 动态导入：只在浏览器使用的第三方库改为动态导入，避免服务端打包与求值。
- 构建检查：构建阶段提示在服务端引用了浏览器模块的位置，据此调整边界。
- 边界标注：在文件顶部用统一标记声明运行端，让越界导入更容易被发现。

```tsx
"use client";

import dynamic from "next/dynamic";

// 富文本编辑器只在浏览器中加载，服务端渲染占位内容
const RichEditor = dynamic(() => import("./RichEditor"), {
  ssr: false,
  loading: () => <p>编辑器加载中</p>,
});

export function EditorShell() {
  return <RichEditor />;
}
```

> [!CAUTION]
> **注意内容**：关闭服务端渲染的组件在首屏没有任何服务端产出，若它占据主要可见区域，会直接损害首屏内容呈现与抓取效果。

**速记**：依赖浏览器的代码用客户端组件与动态导入隔离，服务端路径不触碰它们。



#### 双端共享代码的组织方式

**双端共享代码的组织方式**：是按「能否在服务端安全执行」把模块分成共享、仅服务端与仅客户端三类，并用目录与标记把边界固定下来。

- 共享模块：纯计算与格式化逻辑，不引用任何环境独有对象，可被两端直接导入。
- 仅服务端模块：直连数据库、读取密钥等代码，只在服务端组件或服务端脚本中使用。
- 仅客户端模块：事件处理与浏览器能力封装，标记为客户端组件后使用。
- 边界检查：构建与类型检查应能提示越界的导入，避免服务端代码被打进浏览器产物。
- 命名约定：目录名与文件后缀直接反映运行端，减少阅读时的推断成本。

```text
src/
  components/     共享的展示组件
  server/         仅服务端：数据访问、密钥读取
  client/         仅客户端：浏览器能力封装、交互逻辑
```

```tsx
// components/PriceTag.tsx：共享模块示例，两端结果一致
export function formatPrice(cents: number): string {
  return `￥${(cents / 100).toFixed(2)}`;
}

export function PriceTag({ cents }: { cents: number }) {
  return <span>{formatPrice(cents)}</span>;
}
```

> 边界清晰的收益是排错成本下降：服务端报错与客户端报错可以快速定位到对应目录。

**速记**：代码按共享、仅服务端、仅客户端三类组织，边界由目录与标记固定。
