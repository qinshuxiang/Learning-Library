## 小程序基础：双线程模型与运行机制

**小程序（Mini Program）**：是运行在宿主应用内部的轻量应用形态，由宿主提供运行环境、渲染机制、组件与接口，代码通过宿主平台分发而不经过应用商店。本篇以微信小程序为具体例子，回答四件事：小程序是什么、双线程模型如何工作、运行环境与生命周期如何组织、代码包如何加载。

本篇讲运行机制，不展开页面用法与接口调用清单；页面结构、内置组件与常用接口详见本主题第 15 篇 小程序开发：页面、组件与 API，登录、支付与开放能力详见本主题第 16 篇 小程序进阶：登录、支付与开放能力。

### 小程序是什么

**小程序的定义**：是一份由宿主解释执行的代码包，加上宿主提供的运行时、组件与接口，共同构成的应用形态。

#### 小程序的定义与形态

**小程序的定义与形态**：是「代码包加宿主运行时」的组合，代码包不包含浏览器或系统控件，一切渲染与能力都来自宿主。

- 代码形态：由模板、样式、配置与逻辑四类文件组成，编译后打包成代码包上传到宿主平台。
- 运行形态：宿主在自身进程内创建运行环境，加载代码包并渲染页面。
- 分发形态：由宿主平台完成分发与更新，用户通过扫码、搜索或会话卡片进入。
- 权限形态：可访问的能力由宿主的接口清单决定，清单之外的能力无法调用。

```text
小程序在宿主中的位置

宿主应用
  --> 小程序运行环境（逻辑层 + 视图层）
      --> 代码包（模板、样式、配置、逻辑）
      --> 宿主组件与宿主接口
  --> 宿主的分发与更新机制
```

> 代码包与宿主运行时的组合关系决定了小程序的边界：能做什么由宿主决定，不由代码包自身决定。

**速记**：小程序是代码包加宿主运行时，能力上限由宿主决定。



#### 与 Web 应用的差异

**与 Web 应用的差异**：是运行环境、渲染方式与接口集合三方面的不同，小程序不是浏览器页面的另一种写法。

- 渲染载体：Web 由浏览器渲染，小程序由宿主的视图层渲染，不直接操作 DOM。
- 接口集合：Web 使用浏览器提供的标准接口，小程序使用宿主定义的一组接口。
- 页面导航：Web 靠地址跳转，小程序靠宿主提供的页面路由接口。
- 资源加载：Web 可自由请求任意域名，小程序需要预先在宿主平台登记合法域名。

```text
对照关系

Web          浏览器引擎 + 标准接口 + 地址路由
小程序       宿主视图层 + 宿主接口 + 页面路由
共通点       都是声明式模板 + 样式 + 逻辑
```

> [!NOTE]
> **提醒内容**：小程序环境没有 DOM，也没有浏览器的全局事件模型，依赖直接操作节点的第三方库通常无法直接使用。

**速记**：小程序换掉了渲染载体、接口集合与路由方式，不是换了写法的网页。



#### 与原生应用的差异

**与原生应用的差异**：是分发渠道、更新方式与系统能力开放程度的不同，小程序以受限换取了分发与更新上的便利。

- 分发渠道：原生应用经应用商店审核上架，小程序经宿主平台审核发布。
- 更新方式：原生应用需要用户更新版本，小程序由宿主在启动时下载最新代码包。
- 系统能力：原生应用可调用系统接口，小程序只能调用宿主封装后开放的能力。
- 安装成本：原生应用需要安装，小程序即开即用，不占用独立的安装入口。

```text
能力与成本的取舍

原生应用    能力最全、体验最好，但安装与更新成本高
小程序      免安装、更新快，但能力受限、受宿主规则约束
```

> 小程序的「免安装」来自宿主常驻，因此它的运行依赖宿主存在；宿主不可用时小程序也不可用。

**速记**：小程序以能力受限换取免安装与快速更新，运行依赖宿主。



#### 小程序的适用场景

**小程序的适用场景**：是依托宿主流量的轻量业务，以及对安装与更新成本敏感、但对系统能力要求不高的功能。

- 适合：活动页、轻量工具、会员与订单查询、需要快速触达用户的业务。
- 适合：已经在使用宿主生态的能力，如登录、支付与消息通知。
- 不适合：需要长时间后台运行、深度依赖系统接口或重度图形计算的产品。
- 不适合：需要跨宿主统一体验且不接受按平台分别构建的产品。

```text
场景判断的两个问题

一、业务是否依赖宿主的流量与能力
二、功能是否落在宿主开放的能力清单之内
```

> 场景判断的落点通常是能力清单：清单能覆盖就适合，覆盖不到就需要原生应用或跨端框架补充。

**速记**：依赖宿主流量的轻量业务适合小程序，重系统能力的产品不适合。



### 双线程模型与通信

**双线程模型（dual-thread model）**：是把逻辑层与视图层分开在两条线程上运行，两层之间只能通过消息传递交换数据的运行模型。

#### 逻辑层与视图层的分工

**逻辑层**：是运行业务代码、维护页面数据的线程，负责数据处理、接口调用与页面路由。**视图层**：是运行模板与样式、把数据渲染成界面的线程。

- 逻辑层职责：执行页面与组件代码、维护数据、调用宿主接口、发起网络请求。
- 视图层职责：解析模板、应用样式、绑定事件、把数据变化反映到界面。
- 分层原因：把计算与渲染隔离，页面渲染不阻塞逻辑执行，逻辑异常也不直接破坏渲染。
- 数据是唯一桥梁：视图层不直接读写业务数据，一切变化都由逻辑层发出。

```text
双线程结构

逻辑层线程
  App 与 Page 代码、数据、接口调用
      |
      |  消息通道（序列化传输）
      v
视图层线程
  模板、样式、事件绑定、渲染结果
```

> 分层带来的直接约束是「数据与视图不能互相直接访问」，这也是小程序写法与 Web 写法最根本的分野。

**速记**：逻辑层管数据与调用、视图层管渲染，两层只能靠消息传递交换数据。



#### 两层之间的通信机制

**两层之间的通信机制**：是逻辑层与视图层之间的双向消息通道，通信内容必须可序列化。

- 逻辑层到视图层：发送数据与渲染指令，视图层据此更新界面。
- 视图层到逻辑层：上报用户事件与节点信息，逻辑层在事件处理函数中响应。
- 序列化要求：传输内容会被序列化，函数、循环引用与部分特殊对象无法通过通道传递。
- 异步特征：消息传递是异步的，逻辑层发出数据后不能立即读取视图层的结果。

```text
一次交互的消息往返

用户点击 --> 视图层捕获事件 --> 序列化上报 --> 逻辑层事件处理函数
逻辑层更新数据 --> 序列化下发 --> 视图层重渲染
```

> 通信是异步的：涉及布局尺寸的计算需要等视图层回传结果，不能期望在同一行代码里拿到。

**速记**：两层之间靠可序列化的异步消息通信，函数不能穿过通道。



#### 数据驱动的更新流程

**数据驱动的更新流程**：是逻辑层通过页面的 setData 方法提交数据，由框架把变化同步到视图层并触发重渲染的过程。

**setData(data, callback)**：data 是要合并进页面数据层的对象，callback 是渲染完成后的回调函数；回调不返回渲染结果。

- 合并语义：传入的对象与当前页面数据做浅层合并，未出现的字段保持原值。
- 局部更新：可以只传变化的字段路径，框架据此缩小需要传输与重渲染的范围。
- 异步生效：界面在下一次渲染周期才更新，读取界面结果要放在回调中。
- 与直接赋值不同：直接修改页面数据对象不会触发渲染，必须经过 setData。

```js
Page({
  data: {
    count: 0,
    list: [],
  },
  onAddCount() {
    // 只传变化的字段，减少通道传输量
    this.setData({ count: this.data.count + 1 }, () => {
      // 回调在渲染完成后执行
    });
  },
});
```

> [!WARNING]
> **警告内容**：在定时器或滚动回调中高频调用 setData，会让消息通道与重渲染持续排队，直接表现为界面卡顿，应合并更新或改用局部路径更新。

**速记**：数据变化必须经 setData 提交，框架再序列化下发并重渲染。



#### 通信的性能约束

**通信的性能约束**：是消息通道的传输量与往返次数对性能的影响，减小数据量与调用次数是这类方案的核心优化方向。

- 数据量：一次传输的数据越大，序列化与反序列化耗时越长。
- 调用次数：调用越频繁，渲染排队的压力越大，界面越容易出现掉帧。
- 更新范围：整块替换数据会让框架做更宽的重渲染，局部路径更新更省。
- 避免回传大数据：只把界面需要展示的字段放进页面数据，原始数据留在逻辑层。

```text
优化方向与手段

减小数据量    只保留展示所需字段
减少调用次数  合并多次变化，一次提交
缩小更新范围  使用字段路径更新
减少往返      避免高频读取布局结果
```

> 优化的基准是「界面真正需要的字段」：不属于界面的数据不应进入页面数据。

**速记**：传输量与调用次数决定通信成本，少传、合并、缩小范围是通用手段。



### 运行环境与生命周期

**运行环境与生命周期**：是宿主提供的运行时能力，以及代码包在启动、显示、隐藏与销毁各阶段依次触发的回调机制。

#### 运行环境与基础库

**运行环境**：是宿主为小程序提供的 JavaScript 执行引擎、渲染引擎与接口集合。**基础库**：是宿主提供运行环境与接口的实现版本，决定当前可用的接口与语法能力。

- 引擎差异：不同操作系统上逻辑层使用的 JavaScript 引擎不同，语言特性支持以基础库为准。
- 版本分布：用户端基础库版本不一致，新接口需要判断可用性并准备降级方案。
- 语法支持：模板与逻辑代码经过编译进入运行环境，转译规则由开发工具与基础库共同决定。
- 兼容判断：可通过宿主提供的接口比较基础库版本，或直接判断某接口是否存在。

```text
运行环境的构成

逻辑层引擎    执行 App、Page 与组件代码
视图层渲染    解析模板与样式，产出界面
宿主接口      网络、存储、设备、媒体等能力封装
基础库        上述能力的实现版本与兼容边界
```

> 版本兼容是小程序开发的常态事项：使用新接口前先确认目标用户的基础库版本分布。

**速记**：运行环境由宿主提供，能用的接口与语法由基础库版本决定。



#### 应用生命周期

**应用生命周期**：是小程序整体从启动到销毁过程中触发的回调集合，注册在 App 入口中。

- onLaunch：小程序启动时触发，只触发一次，常用于初始化全局状态。
- onShow：小程序从后台进入前台时触发，每次进入前台都会触发。
- onHide：小程序从前台进入后台时触发，常用于保存临时状态。
- onError：脚本错误或接口调用失败时触发，用于统一错误上报。

```js
App({
  onLaunch() {
    // 全局只执行一次，适合读取本地配置、初始化埋点
  },
  onShow() {
    // 每次从后台回到前台都会触发
  },
  onHide() {
    // 进入后台，适合保存未提交的临时数据
  },
  onError(message) {
    // 统一收集错误信息
    console.log(message);
  },
});
```

> 应用级回调只有一份注册入口，多个页面共享同一份全局状态。

**速记**：应用生命周期管整体启动与前后台切换，注册在 App 入口。



#### 页面生命周期

**页面生命周期**：是单个页面在加载、显示、就绪、隐藏与卸载各阶段的回调集合，注册在页面配置对象中。

- onLoad：页面加载时触发一次，携带路由参数，适合发起初始请求。
- onShow：页面显示时触发，从其他页面返回也会再次触发。
- onReady：页面首次渲染完成时触发一次，此时可以读取节点信息。
- onHide 与 onUnload：页面隐藏与卸载时触发，卸载后数据不再保留。
- 顺序关系：加载与显示先于就绪，卸载只发生在页面出栈时。

```js
Page({
  data: {
    detail: null,
  },
  onLoad(options) {
    // options 携带路由参数，只触发一次
    this.fetchDetail(options.id);
  },
  onShow() {
    // 每次显示都会触发，适合刷新会变化的数据
  },
  onReady() {
    // 首次渲染完成后触发，可读取节点尺寸
  },
  onUnload() {
    // 页面出栈，清理定时器与订阅
  },
  fetchDetail(id) {
    // 省略具体实现
  },
});
```

> 区分 onLoad 与 onShow 的判断标准是「需要执行一次还是每次显示都要执行」。

**速记**：页面生命周期按加载、显示、就绪、隐藏、卸载依次触发，注册在页面对象。



#### 自定义组件生命周期

**自定义组件生命周期**：是组件实例在创建、挂载、就绪、移动与销毁各阶段的回调集合，注册在组件的 lifetimes 字段中。

- created：组件实例刚被创建，此时不能操作节点。
- attached：组件进入页面节点树，适合初始化数据与订阅。
- ready：组件布局完成，可以读取节点信息。
- detached：组件从节点树移除，用于清理订阅与定时器。
- pageLifetimes：组件感知所在页面的显示与隐藏，用于跟随页面切换状态。

```js
Component({
  lifetimes: {
    created() {
      // 实例创建，不能访问节点
    },
    attached() {
      // 进入节点树
    },
    ready() {
      // 布局完成
    },
    detached() {
      // 移除，执行清理
    },
  },
  pageLifetimes: {
    show() {
      // 所在页面显示
    },
    hide() {
      // 所在页面隐藏
    },
  },
});
```

> [!CAUTION]
> **注意内容**：生命周期回调必须在注册对象中声明，写在回调外部或试图在渲染期间读取节点都会出错，节点访问只能放在就绪之后。

**速记**：组件生命周期注册在 lifetimes，清理逻辑放在 detached。



### 代码包与加载机制

**代码包与加载机制**：是把代码按主包与分包组织、并在需要时按路径下载与注入的运行流程。

#### 主包与分包的结构

**主包**：是小程序启动时必须下载的代码集合，包含全局配置、公共资源与首页等基础页面。**分包**：是按业务模块拆分、在进入对应页面时才下载的代码集合。

- 拆分依据：按业务模块或功能域划分，把非首屏必需页面放进分包。
- 依赖方向：分包可以引用主包的公共资源，主包不能引用分包的内容。
- 独立分包：可配置为不依赖主包即可运行的分包，适用于活动页等独立入口。
- 目录组织：分包以目录为单位，配置中以根目录名标识。

```text
常见的目录组织

app.js、app.json、app.wxss      全局配置与逻辑
pages/                          主包页面
packageOrder/                   订单分包
  pages/list/list
  pages/detail/detail
packageActivity/                活动分包
  pages/index/index
```

> 主包应只保留启动必需的资源，把体积压力转移给按需下载的分包。

**速记**：主包随启动下载，分包按需下载，引用方向只能由分包指向主包。



#### 代码包加载与启动流程

**代码包加载与启动流程**：是小程序从被打开到首屏可见所经历的下载、注入与渲染步骤。

- 下载代码包：宿主在启动前检查本地缓存，必要时下载并校验最新代码包。
- 注入逻辑层：加载主包代码，创建应用实例并触发应用启动回调。
- 渲染首屏：视图层解析首页模板与样式，产出首屏界面。
- 触发页面回调：依次触发页面加载、显示与就绪回调。
- 打开分包页面：首次进入分包页面时才下载该分包，随后再渲染。

```text
启动时序

下载代码包 --> 注入逻辑层 --> 应用 onLaunch --> 页面 onLoad
--> 页面 onShow --> 首屏渲染 --> 页面 onReady
```

> 首屏时间由代码包下载与首屏渲染共同决定，控制主包体积对启动体验的影响最直接。

**速记**：启动走下载、注入、渲染、回调四步，首屏体验主要受主包体积影响。



#### 分包预下载与按需注入

**分包预下载**：是在进入指定页面时提前下载后续可能用到的分包，把下载耗时从跳转时刻提前到用户浏览期间。

- 触发条件：在配置中指定某页面进入时预下载哪些分包，可限定网络环境。
- 收益：用户跳转到分包页面时无需等待下载，跳转更顺畅。
- 代价：预下载会占用网络与存储，配置过多会浪费用户流量。
- 按需注入：较新版本提供按需注入能力，只注入当前页面用到的代码，减少启动时的注入量。

```json
{
  "pages": ["pages/index/index"],
  "subPackages": [
    {
      "root": "packageOrder",
      "pages": ["pages/list/list", "pages/detail/detail"]
    }
  ],
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["packageOrder"]
    }
  }
}
```

> 预下载的取舍标准是「跳转概率」：高频入口才值得预下载，低频入口宁可让用户等待。

**速记**：预下载把分包下载提前到浏览期间，配置要按跳转概率取舍。



#### 体积约束与优化方向

**体积约束**：是宿主对单个代码包与整体代码包设定的体积上限，超出后无法上传或无法运行。

**体积约束的应对**：是把首屏必需资源留在主包，其余资源移入分包，并持续压缩静态资源。

- 拆分页面：把非首屏页面整体移入分包，按业务域组织。
- 资源外置：图片、音频等静态资源改用网络地址，避免进入代码包。
- 精简依赖：只引入用到的模块，避免整包引入体积较大的依赖。
- 压缩代码：开启构建期压缩，移除未使用代码与调试信息。
- 复用公共模块：把多个分包共用的代码抽到主包或独立的分包中。

```text
优化优先级

一、把非首屏页面移入分包
二、把静态资源改为网络加载
三、精简第三方依赖
四、开启压缩与按需注入
```

> [!IMPORTANT]
> **重要内容**：体积上限是上传与运行的硬门槛，超限的代码包无法发布，拆分方案必须在开发早期确定而不是发布前临时整改。

**速记**：体积上限是硬约束，靠分包拆分、资源外置与依赖精简来满足。
