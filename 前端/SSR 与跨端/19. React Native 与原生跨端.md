## React Native 与原生跨端

**React Native**：是 Meta（原 Facebook）于 2015 年开源的移动应用框架，用 React 的组件写法与 JavaScript 语言编写代码，运行时把组件树映射为宿主平台的原生控件，而不是把网页装进 WebView 渲染。

本篇回答四件事：React Native 是什么、组件与样式怎么写、原生能力怎么接、开发与发布走什么链路。前三件对应它在原生渲染路线上的技术特征，最后一件对应工具链与工作流。

### React Native 是什么

本节确立 React Native 在跨端方案谱系中的位置：它属于原生渲染路线，与小程序路线的差异不只是语法，而是运行环境与能力边界的差异。

#### 定义与原生渲染路线

**原生渲染路线**：是把上层组件映射为平台原生控件、由平台负责绘制与手势的跨端实现方式，React Native 是该路线的代表方案。

- 语言与范式：沿用 React 的声明式组件与 Hooks，逻辑代码与 Web 端共享同一套心智模型。
- 渲染目标：iOS 上映射为 UIView 及其子类，Android 上映射为 android.view.View 及其子类。
- 与 WebView 方案的区别：Cordova、Ionic 把网页装入 WebView，交互与滚动由浏览器内核负责；React Native 使用原生控件，手势与滚动接近原生体验。
- 与小程序路线的区别：小程序运行在宿主划定的沙箱中，能力由宿主开放清单决定；React Native 运行在完整的 JavaScript 环境中，直接调用平台 SDK。

跨端能力由三层构成：上层是与平台无关的 React 组件与业务逻辑，中层是框架给出的组件映射与 API，下层是各平台的原生实现与桥接。三层中只有上层完全共享，中下层需要按平台分别维护，这也是原生跨端方案维护成本高于 Web 同构方案的原因。

```tsx
import { View, Text, StyleSheet } from "react-native";

export default function GreetingCard() {
  return (
    <View style={styles.card}>
      <Text style={styles.title}>Hello, React Native</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  card: { padding: 16, borderRadius: 8, backgroundColor: "#f5f5f5" },
  title: { fontSize: 18, fontWeight: "600" },
});
```

> 是否直接使用平台原生控件，是判断跨端方案体验上限的分水岭：原生控件方案在滚动惯性、键盘避让、系统手势上天然接近系统应用。

**速记**：React Native 用 React 写法驱动原生控件渲染，不走 WebView。



#### 与小程序路线的区别

**小程序路线**：是由宿主应用提供运行环境与渲染层、开发者按宿主规范编写页面与 API 调用的跨端实现方式，运行边界由宿主定义。

- 运行环境：小程序代码运行在宿主划定的沙箱中，页面结构经宿主渲染层绘制，开发者不直接接触平台控件。
- 能力来源：可用能力只包括宿主开放的接口，清单外的系统能力无法调用。
- 分发方式：小程序依托宿主入口分发，无需上架应用商店，更新无需审核商店版本。
- 选择依据：以微信生态获客与轻量服务为主时选小程序，需要深度使用系统能力并上架应用商店时选原生跨端。

除能力边界外，两条路线的交付节奏也不同：小程序的发布由宿主审核，周期较短且可分版本灰度；原生应用受应用商店审核与用户更新意愿影响，新版本覆盖率爬升更慢，因此原生跨端更依赖热更新补丁与服务端配置来兜底。

```text
小程序路线：模板语法 + 双线程 + 宿主渲染层 + 宿主开放 API
React Native 路线：React 组件树 + JS 运行时 + 原生控件 + 平台 SDK
```

> 两条路线并非互斥：同一业务可以一端做小程序获客、一端做原生应用承载完整体验。跨端方案的整体取舍详见本主题第 13 篇 跨端开发概览与方案选型。

**速记**：小程序受宿主能力边界约束，React Native 直接触达平台原生能力。



#### 运行架构概览

**运行架构**：是 React Native 应用在设备上的线程与模块分工，业务代码、界面绘制与原生调用分布在不同的执行单元中。

- JavaScript 线程：执行 React 组件渲染与业务逻辑，由 JavaScript 引擎承载。
- 原生主线程：负责界面布局与绘制，涉及原生控件与动画的操作必须回到主线程执行。
- 桥（bridge）：JavaScript 线程与原生线程之间的通信通道，消息异步传递（详见本篇「原生模块与桥接」）。
- 后台线程：图片解码、文件读写等耗时任务可交给后台线程，避免阻塞主线程。

线程之间的边界带来两条实践约束：其一，界面状态的修改必须回到 JavaScript 线程的渲染流程中完成，不要在原生回调里直接改 React 状态；其二，启动阶段应尽量减少需要跨线程往返的初始化调用，否则冷启动会明显变慢。

```tsx
import { Animated } from "react-native";

export function useFadeIn() {
  const opacity = new Animated.Value(0);
  Animated.timing(opacity, {
    toValue: 1,
    duration: 300,
    useNativeDriver: true, // 动画交由原生侧执行，不逐帧过桥
  }).start();
  return opacity;
}
```

> 理解线程分工是排查卡顿与崩溃的基础：任何跨线程调用都不是零成本的，动画与滚动尤其敏感。

**速记**：JS 线程跑逻辑、原生线程画界面，两者靠桥通信。



### 组件与样式系统

本节说明上层写法：组件名与 Web 标签不同，样式用 JavaScript 对象描述且没有级联。掌握这两点即可读懂绝大多数 React Native 代码。

#### 核心组件与组件映射

**核心组件**：是 React Native 提供的一组跨平台基础组件，每个组件的名称与职责对应各平台的原生控件。

- 容器类：View 对应 iOS 的 UIView 与 Android 的 ViewGroup 子类，用于布局包裹。
- 文本类：Text 承载文字显示，文字必须写在 Text 内，不能像浏览器那样直接写在容器中。
- 输入类：TextInput 对应原生输入控件，受控写法用 value 与 onChangeText 两个属性。
- 图片与列表：Image 承载图片资源，FlatList 承载长列表。
- 交互类：Pressable 提供按压反馈与触摸事件。

```tsx
import { Pressable, Text, TextInput, View } from "react-native";

type SearchBoxProps = {
  keyword: string;
  onChangeKeyword: (next: string) => void;
  onSubmit: () => void;
};

export function SearchBox({ keyword, onChangeKeyword, onSubmit }: SearchBoxProps) {
  return (
    <View>
      <TextInput
        value={keyword}
        onChangeText={onChangeKeyword}
        placeholder="请输入关键词"
      />
      <Pressable onPress={onSubmit}>
        <Text>搜索</Text>
      </Pressable>
    </View>
  );
}
```

> 组件名与 Web 标签不通用：Web 用 div、span、input，React Native 用 View、Text、TextInput，迁移代码时不能直接套用标签名。

**速记**：核心组件一一对应原生控件，文字必须包在 Text 内。



#### 样式以 JavaScript 对象描述

**样式系统**：是用 JavaScript 对象描述外观规则、属性名采用小驼峰写法的样式方案，长度默认按与设备无关的逻辑像素计算。

- 对象形式：style 属性接收普通对象或对象数组，数组按顺序合并，后者覆盖前者。
- 命名转换：CSS 的 background-color 写作 backgroundColor，font-size 写作 fontSize。
- 注册复用：StyleSheet.create 把样式对象注册为标识符，避免每次渲染重复创建对象。
- 无级联：不存在选择器与继承链，样式只能显式写在元素上或通过属性下传。

样式组合靠数组完成，条件样式用三元表达式选择对象即可，不需要拼接类名字符串。把常用组合抽成模块级的样式常量，可以让组件渲染函数保持干净，也避免每次渲染都新建对象。

```tsx
import { StyleSheet, Text } from "react-native";

export function PriceLabel({ price }: { price: number }) {
  return <Text style={styles.price}>¥{price.toFixed(2)}</Text>;
}

const styles = StyleSheet.create({
  price: { fontSize: 16, color: "#dd1144", fontWeight: "700" },
});
```

> [!NOTE]
> **提醒内容**：样式中的数值是设备无关的逻辑单位，跨设备的物理尺寸换算由运行时按屏幕密度处理，不要手工再乘一次密度系数。

**速记**：样式写小驼峰对象，无级联无选择器，StyleSheet.create 负责注册复用。



#### 布局模型与 Flexbox

**布局模型**：是 React Native 采用的 Flexbox 子集，主轴默认纵向，与 Web 默认横向的约定相反。

- 默认方向：flexDirection 默认值为 column，子元素纵向排列；Web 默认值为 row。
- 常用属性：flex、justifyContent、alignItems、gap、padding、margin 覆盖绝大多数布局需求。
- 伸缩尺寸：尺寸可写百分比字符串，配合 flex 数值实现剩余空间分配。
- 与 Web 差异：不支持浮动与表格布局，定位只保留 absolute 与 relative 两种取值。

注意文字样式的传递方式：Text 之下的嵌套 Text 会继承外层文字样式，这一点与 Web 的字体继承相似；但 View 上的样式不会自动传给子元素，需要逐层设置或通过属性下传。

```tsx
import { StyleSheet } from "react-native";

const styles = StyleSheet.create({
  page: { flex: 1, padding: 16 },
  row: {
    flexDirection: "row",
    justifyContent: "space-between",
    alignItems: "center",
    gap: 12,
  },
  grow: { flex: 1, minWidth: 0 },
});
```

> 从 Web 迁移时最常见的错误是忘记把 flexDirection 设为 row，导致原本横向的一行变成纵向堆叠，而且不会报错。

**速记**：默认纵向 Flexbox，无浮动无表格，flexDirection 决定主轴方向。



#### 列表与滚动组件

**列表组件**：是面向长列表优化的滚动容器，通过回收与按需渲染控制同时挂载的元素数量。

- ScrollView：一次性渲染全部子元素，适合内容少、需要整体滚动的场景。
- FlatList：按需渲染可视区域内的列表项，关键属性为 data、renderItem、keyExtractor。
- 性能属性：initialNumToRender 控制首屏渲染数量，onEndReached 用于触发分页加载。
- 选择依据：列表项数量不确定且可能很多时用 FlatList，固定的小规模内容用 ScrollView。

```tsx
import { FlatList, Text } from "react-native";

type Article = { id: string; title: string };

export function ArticleList({ articles }: { articles: Article[] }) {
  return (
    <FlatList
      data={articles}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => <Text>{item.title}</Text>}
      onEndReachedThreshold={0.5}
    />
  );
}
```

> FlatList 的 renderItem 返回的是组件元素而非字符串，列表项组件应保持轻量，避免在渲染函数内创建大对象或匿名组件。

滚动容器还有一个易被忽略的约束：同类滚动容器不应深层嵌套，纵向滚动套纵向滚动会让手势判定变得难以预测，也影响长列表的回收效率。需要分段滚动时，优先用列表的头部与尾部插槽承载固定区域。

```tsx
import { ScrollView, Text } from "react-native";

export function TermsPanel({ paragraphs }: { paragraphs: string[] }) {
  return (
    <ScrollView contentContainerStyle={{ padding: 16 }}>
      {paragraphs.map((text) => (
        <Text key={text}>{text}</Text>
      ))}
    </ScrollView>
  );
}
```

**速记**：长列表用 FlatList 按需渲染，短内容用 ScrollView 一次渲染。



### 原生模块与桥接

本节说明 React Native 如何触达平台能力：跨线程通信有明确的异步与序列化约束，理解约束才能正确封装原生模块。

#### 通信桥与异步调用

**桥（bridge）**：是传统架构中 JavaScript 线程与原生线程交换消息的通道，消息经序列化后异步传递，调用方不能立即取得返回值。

- 异步特性：跨桥调用返回 Promise 或经回调回传结果，不阻塞 JavaScript 线程。
- 批量传递：一帧内的多次调用会被合并为批量消息发送，减少通信次数。
- 序列化限制：只能传递可序列化的数据，函数与类实例不能直接过桥。
- 性能影响：高频、大数据量的通信会造成队列积压，表现为掉帧或响应延迟。

```tsx
import { NativeModules } from "react-native";

type DeviceInfoModule = {
  getModel: () => Promise<string>;
};

const { DeviceInfo } = NativeModules as { DeviceInfo: DeviceInfoModule };

export async function readDeviceModel(): Promise<string> {
  const model = await DeviceInfo.getModel();
  return model;
}
```

> 桥的异步与序列化约束是传统架构性能瓶颈的主要来源，判断一段逻辑该留在 JavaScript 侧还是下沉到原生侧，依据就在这里。

**速记**：桥是异步序列化通道，过桥数据必须可序列化。



#### 原生模块的封装

**原生模块（native module）**：是用平台原生代码实现并暴露给 JavaScript 调用的功能单元，用于访问核心组件与桥覆盖不到的平台能力。

- 声明方式：原生侧注册模块名与方法，JavaScript 侧通过 NativeModules 按名称取用。
- 平台分工：iOS 与 Android 各写一份实现，对外暴露同样的方法签名。
- 降级处理：调用前判断模块是否存在，避免在未链接原生代码的环境直接崩溃。
- 封装建议：把原生调用收敛到单独的适配模块，业务层只依赖稳定的接口与返回类型。

封装层还要处理错误语义的统一：原生侧的错误码各不相同，适配层应把它们转换为业务可识别的错误类型，并明确哪些错误可以降级、哪些必须冒泡到调用方。

```tsx
import { NativeModules, Platform } from "react-native";

type AppMetaModule = {
  getVersionName: () => Promise<string>;
};

export async function readAppVersion(): Promise<string> {
  const module = NativeModules.AppMeta as AppMetaModule | undefined;
  if (!module) {
    return Platform.OS === "ios" ? "unknown-ios" : "unknown-android";
  }
  return module.getVersionName();
}
```

> [!CAUTION]
> **注意内容**：原生模块缺失或方法名不一致会在调用处直接抛错，未做存在性判断的代码在真机上可能崩溃，而调试环境因为模块已链接而看不出来。

**速记**：原生模块一端写两份实现、一套签名，调用前必须做存在性判断。



#### 新架构的方向

**新架构**：是以 JavaScript Interface、Fabric 渲染器与 TurboModules 为核心的重构方向，目标是降低序列化与桥队列带来的开销。

- JavaScript Interface：让 JavaScript 与原生对象直接互操作，不再完全依赖消息序列化。
- Fabric 渲染器：把渲染流程改为更可控的同步布局与提交，改善列表与手势表现。
- TurboModules：原生模块按需加载，降低启动阶段的初始化成本。
- 兼容策略：新旧架构在一段时期内并存，迁移通常按模块逐步推进，不必一次到位。

```text
传统架构：JS 线程 --序列化消息--> 桥 --> 原生线程 --> 原生控件
新架构：  JS 线程 --JSI 直接调用--> 原生对象（TurboModules / Fabric 渲染器）
```

> 具体启用方式与兼容范围随版本变化，落地时应以所用版本的官方文档为准，不要照搬旧版本的配置写法。

**速记**：新架构用 JSI 与 Fabric 取代桥的消息序列化，按模块逐步迁移。



### Expo 与开发工作流

本节说明工程与工具链：从脚手架到构建、从热重载到发布，React Native 项目有一套区别于 Web 的工作流。

#### Expo 是什么

**Expo**：是围绕 React Native 构建的工具链与云服务，提供开箱即用的开发客户端、项目脚手架以及托管式构建与发布能力。

- 脚手架：用 create-expo-app 生成项目，内置路由、资源与配置约定。
- 开发客户端：Expo Go 可直接在真机加载项目，无需本地配置完整的原生工具链。
- 预构建：执行 prebuild 生成 ios 与 android 原生工程目录，之后可脱离托管模式自行修改原生代码。
- 云构建：托管构建服务负责签名与打包，省去本地安装完整原生 SDK 的步骤。

引入 Expo 的收益集中在前期：无需立刻配置 Xcode 与 Android SDK 即可跑起真机应用，团队可以在验证产品方向之后再决定是否转入裸工程。代价是与工具链和云服务的耦合，需要评估构建配额与私有原生模块的接入成本。

```bash
npx create-expo-app my-app
cd my-app
npx expo start
# 用开发客户端扫码，或选择模拟器打开项目
```

> 托管模式与裸工程模式的边界取决于是否要写原生代码：一旦引入第三方原生模块，通常需要转为预构建或裸工程模式。

**速记**：Expo 提供脚手架、开发客户端与云构建，是否预构建取决于要不要写原生代码。



#### 开发与调试工作流

**开发工作流**：是以打包服务器为中心的开发与热重载流程，打包服务器监听源码变更并重新打包，客户端按需拉取更新后的模块。

- 打包服务器：负责模块解析与语法转换，保存文件后界面即时重载。
- 日志查看：JavaScript 日志输出到终端或调试面板，原生日志则走各平台的日志工具。
- 元素检查：可用调试工具查看组件树与样式，循环依赖等构建问题在终端报出。
- 环境选择：模拟器便于快速迭代，真机用于验证性能、手势与平台能力。

界面层之外，网络请求与本地存储在两端的行为也需要分别核对：证书、代理与本地存储容量在不同平台上并不一致，调试期应至少在 iOS 与 Android 各跑一遍核心链路。

```bash
npx expo start --clear   # 清空打包缓存后启动，排除缓存导致的异常
npx expo run:ios         # 生成并运行 iOS 原生工程
npx expo run:android     # 生成并运行 Android 原生工程
```

> [!TIP]
> **建议内容**：修改依赖或原生配置后先清空打包缓存再启动，多数「改了没生效」的问题源于缓存未失效，而不是代码本身有错。

**速记**：打包服务器负责热重载与打包，改动不生效时先清缓存再排查。



#### 热更新与发布链路

**热更新（over-the-air update）**：是把打包后的 JavaScript 与静态资源下发到已安装客户端、由客户端在启动时替换本地脚本的更新方式。

- 更新单元：下发的通常是打包后的 JavaScript 包与资源文件，不含原生二进制。
- 生效时机：客户端启动时检查并下载新包，一般在下一次启动时生效。
- 平台约束：应用商店对动态下发可执行代码有政策限制，改动原生部分必须走商店版本。
- 发布链路：原生包走应用商店审核，纯脚本层修复走热更新通道，两者版本需对应记录。

```bash
npx expo install expo-updates
npx eas update --branch production --message "fix payment button"
# 已安装的客户端在下一次启动时拉取该分支的新包
```

> [!WARNING]
> **警告内容**：热更新只能替换脚本与资源，涉及新增原生模块、变更权限或启动资源时必须发布新的商店版本，否则客户端可能在启动时直接崩溃。

**速记**：热更新下发脚本包、启动生效，原生变更仍须走商店版本。
