## 源码导览与执行原理

### 仓库布局

#### 目录地图

**Automa 是标准的浏览器扩展工程**：核心目录各管一层职责。

- src/workflowEngine：执行引擎核心，含引擎、块处理器、模板求值
- src/background：扩展后台服务，触发调度与消息监听
- src/content：注入页面的内容脚本，页面侧动作执行
- src/sandbox：后台执行 JS 的沙箱 iframe
- src/db：IndexedDB 封装（日志与存储）
- src/newtab 与 src/popup：仪表盘页面与弹窗界面
- src/components、src/stores：界面组件与状态管理

> 读源码的入口在 workflowEngine：它把“画布上的块”变成“真实执行的动作”。UI 目录可以最后看，引擎目录建议按 WorkflowEngine、WorkflowWorker、blocksHandler、templating 四站顺序读。

**速记**：**引擎、后台、内容、沙箱四层，入口在引擎**。



#### 技术栈

**Vue3 加 webpack 的扩展工程**：依赖清单决定能力边界。

- 界面层 Vue 3.4 加 Pinia 加 Vuex，样式 Tailwind
- 表达式求值依赖 object-path（路径取值）与 jsonpath（$filter）
- 日期用 dayjs，随机 id 用 nanoid，跨浏览器用 webextension-polyfill
- 构建 webpack，配置区分 Chrome 与 Firefox 两套 manifest

> 读懂依赖就读懂了行为：表达式的取值语义其实来自 object-path 的 get 规则，$filter 的语法就是 jsonpath 库的原生语法——查这两个库的文档等于查 Automa 表达式的底层手册。

**速记**：**Vue3 做皮，object-path 与 jsonpath 做骨**。



### 执行引擎

#### 引擎与工作器的分工

**WorkflowEngine 管全局，WorkflowWorker 管推进**：一次执行两级结构。

- WorkflowEngine 持有块图、连线表、referenceData 与表格列定义
- 每个块的执行由 WorkflowWorker 推进：取下一块连线、执行、回传数据
- 连线表按键“块 id 加 output 序号”组织，条件块的多出口即多 output
- 执行状态可销毁（destroy），失败、停止与完成都走统一出口

> 引擎与工作器的分工对应画布与运行时的关系：画布上的连线被解析成 connectionsMap，运行时按 handle 找下一块。理解这个映射，条件分支与循环的跳转行为就完全可预测。

**速记**：**引擎持图，工作器走块，连线即路径**。



#### referenceData 数据结构

**referenceData 是全部运行时数据的容器**：表达式的数据源与它一一对应。

- 结构：variables、table、secrets、loopData、workflow、googleSheets、globalData 七个关键字段
- activeTabUrl 与 prevBlockData 在工作器层动态注入，不在引擎常驻结构里
- 表格列定义独立存放，写入时按列名对位
- 代码块只接收它用到的关键字段（按代码文本是否包含关键字过滤）

> 七字段清单与 6 篇的数据源清单对上后，源码与文档互相印证：表达式能取什么，取决于 referenceData 有什么。secrets 字段的存在说明凭据是头等公民（16 篇展开解密细节）。

**速记**：**七字段即七数据源，代码块按需下发**。



#### 块处理器与分发

**53 个块处理器各管一类的执行**：handler 目录即块说明书。

- blocksHandler 目录下每个 handlerXxx.js 对应一个块的执行逻辑
- 引擎按块类型分发到对应 handler，返回 nextBlockId 与输出数据
- 触发器的 handler 极简：直接返回下一块连线，真正的触发条件在后台调度层
- 禁用的块被跳过（disableBlock 标记），断点用 $breakpoint 标记

> 想弄清某个块的真实行为，直接读对应 handler 是最短路径：文档没写的默认值、边界条件，源码一目了然。53 个处理器也给出了块的完整官方清单。

**速记**：**一 handler 一块，源码即最全说明书**。



### 触发与调度

#### 触发的真实实现

**触发条件的调度全在后台层**：chrome.alarms 加页面监听。

- 定时触发走 chrome.alarms，触发时 BackgroundWorkflowTriggers.scheduleWorkflow 启动工作流
- 访问页面触发走 webNavigation.onCompleted，按 URL 匹配已注册的触发器
- 右键菜单触发走 contextMenus 监听
- 浏览器启动时 reRegisterTriggers 重新登记全部触发器，保证重启不丢

> “定时任务需要浏览器存活”的文档结论在源码得到解释：调度依赖扩展后台的 alarms 事件，后台活着才有可能触发。启动时重新注册是防御性设计，alarms 在浏览器重启后并非总是自愈。

**速记**：**alarms 管定时，webNavigation 管访问，启动重登记**。



#### 状态与日志的持久化

**执行状态与日志落在浏览器存储**：重启即清理运行态。

- 执行中的状态（workflowStates）存 storage.local，浏览器启动时主动清除
- 运行日志走 src/db 封装的 IndexedDB
- 日志支持从通知点击回跳详情
- 表格数据只存在于执行实例内，导出才有持久形态

> 运行态与历史日志分家是清晰的边界设计：状态随进程生死，日志跨重启可查。排查历史失败去日志库，排查正在发生的去看 workflowStates。

**速记**：**状态随进程灭，日志跨重启存**。
