## 大数据量与渲染性能优化

数据量上升之后，绘制慢的成因可能出现在数据处理、绘制调用、线程调度或交互反馈中的任意一环。本篇只讲跨渲染层的通用优化手法：先定位问题，再从数据、渲染、并行、交互四面入手，最后用监控与基准守住效果。ECharts 自身的大数据量配置详见本主题第 15 篇，Three.js 的实例化详见本主题第 10 篇。

### 性能问题定位

优化之前必须先知道瓶颈在哪一环。本节说明量化优先的原则、常见瓶颈阶段的区分方式，以及可用的定位指标。

#### 先量化再优化

**性能优化**：是在明确指标与瓶颈之后，用可验证的改动换取可测量的收益；没有度量就动手，改的多半不是真正的瓶颈。

- 定指标：先写清目标，例如交互保持在每秒六十帧、首屏绘制在两百毫秒内完成。
- 建场景：用接近真实规模的数据集复现，不要拿几百条样本推断十万条的表现。
- 测基线：改动前记录一次数据，改动后再测一次，收益才有对照。
- 单一变量：一次只改一处，多处同时改会无法判断哪一处起了作用。

```bash
# 用浏览器的性能面板记录一段交互，重点看主线程上的长任务
# 一次绘制超过 16 ms 就意味着已无法稳定维持每秒六十帧
# frame time  p95: 38 ms
# long task   count: 7
```

> 优化不是把代码写得更短，而是让关键时刻的耗时下降；收益要用数据说明，不能靠主观感受。

**速记**：先定指标、复现规模、记录基线，再一次只改一处，用数据验证收益。



#### 区分瓶颈所在阶段

**瓶颈阶段**：是导致整体卡顿的主要耗时来源，通常落在数据处理、布局与样式计算、绘制调用或线程调度四者之一，不同阶段的优化手段完全不同。

- 数据处理：排序、分组、聚合发生在主线程且数据量大，表现为操作后长时间无响应。
- 布局与样式：频繁读写尺寸触发反复重排，表现为交互时整页抖动。
- 绘制调用：图元数量极多，表现为帧率稳定偏低但主线程并不忙。
- 线程调度：多个任务挤在同一帧内执行，表现为间歇性掉帧而非持续低帧率。
- 判断方法：持续低帧率多为绘制瓶颈，间歇卡死多为数据处理或调度瓶颈。

```js
// 用时间标记把一段操作拆开计时，快速判断耗时落在哪一步
performance.mark("transform-start");
const series = transformRows(rows);
performance.mark("transform-end");
performance.measure("transform", "transform-start", "transform-end");
console.log(performance.getEntriesByName("transform")[0].duration);
```

> [!CAUTION]
> **注意内容**：把绘制瓶颈当成数据处理瓶颈来修，只会增加代码复杂度而帧率毫无变化，定位阶段是优化的前提。

**速记**：瓶颈可能落在数据处理、布局、绘制或调度，持续低帧率多为绘制，间歇卡死多为处理与调度。



#### 用帧率与耗时指标定位

**关键指标**：是能够直接反映流畅度的几组数字，包括帧间隔、单帧耗时、长任务数量与交互响应延迟。

- 帧间隔：相邻两帧的时间差，分布中的高分位比平均值更能暴露卡顿。
- 单帧耗时：一帧内从回调开始到绘制结束的时间，超过一帧预算即会掉帧。
- 长任务：占用主线程过久的单个任务，会推迟后续的输入响应与绘制。
- 交互延迟：从输入事件到画面更新之间的时间，直接影响操作手感。
- 观察窗口：短时采样容易受偶发因素干扰，应在一段持续交互中统计分布。

```js
let previousTime = performance.now();
let frameCount = 0;

function measureFrame(now) {
  const frameTime = now - previousTime;
  previousTime = now;
  frameCount += 1;
  if (frameTime > 32) {
    console.log("掉帧", frameCount, frameTime.toFixed(1));
  }
  requestAnimationFrame(measureFrame);
}
requestAnimationFrame(measureFrame);
```

> 平均值会掩盖卡顿：一次两百毫秒的停顿混在大量流畅帧里，看均值几乎察觉不到，必须看高分位。

**速记**：看帧间隔、单帧耗时、长任务与交互延迟四项，关注高分位而非平均值，短时采样不足为凭。



### 数据侧优化

进入绘制之前先削减数据，是所有渲染层都受益的手段。本节说明数据量与图元的关系、抽样聚合分箱，以及数据格式与传输的优化。

#### 数据量与图元数量的关系

**图元数量**：是数据点最终映射成的可见形状个数，它而非原始行数决定绘制成本。

- 非一一对应：一行数据可能映射成折线的一段，也可能映射成散点、柱体或标签。
- 隐藏元素：被裁剪到可视区之外、或透明度为零的图元，仍可能参与绘制与命中计算。
- 标签代价：文字标签的排版成本远高于同样数量的几何图形。
- 重叠浪费：大量点落在同一像素范围内时，重叠部分对视觉没有贡献却照常消耗算力。
- 估算方式：先按当前视图范围估算实际可见图元数，再决定是否需要削减。

```js
function estimateVisiblePoints(points, viewport) {
  let count = 0;
  for (const point of points) {
    if (
      point.x >= viewport.minX &&
      point.x <= viewport.maxX &&
      point.y >= viewport.minY &&
      point.y <= viewport.maxY
    ) {
      count += 1;
    }
  }
  return count;
}
```

> 优化前先算清实际可见图元数：屏幕上只放得下有限像素，超出部分往往是纯粹的浪费。

**速记**：绘制成本由图元数量而非数据行数决定，裁剪外的元素与重叠点都可能在白耗算力。



#### 抽样、聚合与分箱

**抽样**：是按规则从原始数据中挑出代表点；**聚合**：是把一组数据合并成少数汇总值；**分箱**：是把取值区间切成若干段后按段汇总。

- 等距抽样：按固定间隔取点，实现简单，但会漏掉局部极值。
- 极值保留抽样：按像素列取每列的最大值与最小值，折线形态与峰值都不丢。
- 聚合：按时间粒度求和或求均值，把秒级数据压到分钟级展示。
- 分箱：把连续字段切成区间做直方统计，用于看清整体分布。
- 提示抽样：抽样后要在界面上明确标注，避免读者把抽样结果当作全量。

```js
function sampleByColumn(points, columnWidth) {
  const buckets = new Map();
  for (const point of points) {
    const key = Math.floor(point.x / columnWidth);
    const bucket = buckets.get(key) || { min: point, max: point };
    if (point.y < bucket.min.y) bucket.min = point;
    if (point.y > bucket.max.y) bucket.max = point;
    buckets.set(key, bucket);
  }
  return [...buckets.values()].flatMap((bucket) => [bucket.min, bucket.max]);
}
```

> 抽样规则要与图形语义匹配：折线保留每列的极值才有意义，散点按密度抽样更能反映分布。

**速记**：抽样减点、聚合降粒度、分箱看分布，折线按列保留极值，抽样结果必须在界面上标注。



#### 数据格式与传输优化

**数据格式**：是数据在内存与网络中的组织方式，紧凑的格式可以减少解析耗时、内存占用与传输体积。

- 类型化数组：数值批量存放为定长数组，避免为每个点创建独立对象。
- 列式存放：按字段分组存放，便于只读取参与绘制的字段并连续访问内存。
- 紧凑编码：整数用更小的位宽存放，或按增量差分后再还原。
- 传输压缩：网络传输启用压缩，必要时用二进制格式替代文本格式。
- 预计算：把稳定的派生字段在预处理阶段算好，避免每次交互重复计算。

> [!TIP]
> **建议内容**：把转换、聚合这类稳定计算放到构建期或服务端完成，客户端只负责把结果画出来，交互路径上的计算越少越好。

**速记**：数值用类型化数组与列式存放，传输启用压缩或二进制，稳定的派生字段提前算好。



### 渲染侧优化

绘制阶段的成本主要来自绘制调用次数与每帧重绘的像素面积。本节说明批量合并、分层与按需重绘、静态图层缓存。

#### 减少绘制调用与批量合并

**绘制调用**：是向渲染层提交一次绘制指令的动作，次数越多，固定开销累计越明显。

- 同批合并：样式与坐标系统相同的图元尽量一次提交，减少指令条数。
- 同材质复用：重复创建样式对象会导致状态切换，应复用同一份样式定义。
- 合并几何：把大量小形状合并成少量大形状，代价是失去逐个图元的选择能力。
- 近似替代：密集小点可用一幅位图或体素化图形替代，视觉接近而指令数骤降。
- 权衡：合并会削弱交互粒度，需要在绘制效率与点选精度之间做取舍。

```js
function drawPoints(ctx, points, style) {
  ctx.beginPath();
  for (const point of points) {
    ctx.moveTo(point.x + style.radius, point.y);
    ctx.arc(point.x, point.y, style.radius, 0, Math.PI * 2);
  }
  ctx.fill();
  // 一次路径提交完成整批点的绘制
}
```

> 绘制调用的固定开销与图元数量无关：指令条数多到一定程度时，减少条数比优化单条更快。

**速记**：同批合并、复用样式、合并几何或改用替代图形，用更少的绘制指令画完同样的内容。



#### 分层与按需重绘

**分层**：是把内容按更新频率拆到多个画布或多个层上，只重绘发生变化的那一层；**按需重绘**：是在内容没有变化时不重绘。

- 分层依据：底图、数据层、交互层、标注层分开，静态层不必逐帧重绘。
- 脏区域：只重绘发生变化的矩形范围，适合局部动画与拖拽中的元素。
- 变化检测：把上一次的绘制输入与本次比较，无差异则跳过整帧。
- 时序分离：数据更新与画面更新解耦，多次数据变更合并为一次绘制。
- 合并策略：把同一帧内的多次重绘请求合并到一次，避免重复劳动。

```js
let dirtyRect = null;

function markDirty(rect) {
  dirtyRect = dirtyRect ? unionRect(dirtyRect, rect) : rect;
}

function renderFrame(ctx) {
  if (!dirtyRect) return;
  ctx.clearRect(dirtyRect.x, dirtyRect.y, dirtyRect.width, dirtyRect.height);
  redrawRegion(ctx, dirtyRect);
  dirtyRect = null;
}
```

> 分层与脏区域的前提是能准确界定变化范围，范围算错会留下残影，需要靠重绘整层兜底。

**速记**：静态分层只重绘变化层，按需重绘配合脏区域把每帧工作量压到最小。



#### 缓存静态图层与位图

**图层缓存**：是把不常变化的内容预先绘制到位图并复用，后续帧只做一次贴图，省去重复的路径绘制。

- 位图缓存：把复杂的静态图形绘制到离屏位图，之后直接作为整块图像使用。
- 缓存失效：尺寸、样式或数据变化时缓存必须重建，需要显式管理失效时机。
- 分辨率匹配：缓存位图按设备像素比创建，否则会发虚。
- 内存代价：缓存占用显存或内存，缓存对象过多时需要淘汰策略。
- 适用判断：静态且重绘频繁的图层收益最大，只画一次的图层不值得缓存。

```js
function buildLayerCache(width, height, pixelRatio) {
  const layer = document.createElement("canvas");
  layer.width = width * pixelRatio;
  layer.height = height * pixelRatio;
  const layerCtx = layer.getContext("2d");
  layerCtx.scale(pixelRatio, pixelRatio);
  drawStaticContent(layerCtx, width, height);
  return layer;
}
```

> [!IMPORTANT]
> **重要内容**：位图缓存一旦建立就与数据脱钩，数据变化后必须显式重建，否则画面会停留在旧数据上。

**速记**：静态图层预绘制成位图并复用，缓存要按设备像素比建立、按数据与尺寸变化失效。



### 并行与后台渲染

把耗时计算从主线程挪走，是避免交互被阻塞的关键。本节说明工作线程、离屏画布协作，以及不阻塞主线程的调度方式。

#### 把重计算移出主线程

**工作线程**：是运行在独立线程中的脚本环境，与主线程通过消息传递交换数据，不共享内存，因此不会阻塞渲染。

- 适用任务：解析、排序、聚合、坐标换算等纯计算。
- 通信成本：跨线程传递大数据结构会被复制，传输量本身可能成为新瓶颈。
- 可转移对象：把类型化数组的缓冲区标记为转移，可避免复制。
- 任务划分：把可并行的大任务切成块，避免单块过久导致反馈延迟。
- 兼容兜底：不支持工作线程的环境需要退回主线程执行。

```js
// worker.js
self.onmessage = (event) => {
  const { rows, columnWidth } = event.data;
  const sampled = sampleByColumn(rows, columnWidth);
  self.postMessage(sampled);
};

// 主线程
const worker = new Worker("./worker.js");
worker.postMessage({ rows, columnWidth: 4 });
worker.onmessage = (event) => updateSeries(event.data);
```

> 工作线程只解决计算占用，不解决绘制调用过多；把两类问题混为一谈会误判优化效果。

**速记**：解析、排序、聚合等纯计算移入工作线程，用转移缓冲区避免复制，注意环境兼容兜底。



#### 离屏画布与工作线程协作

**离屏画布（offscreen canvas）**：是可以在工作线程中直接绘制的画布对象，主线程把画布控制权转交后，绘制不再占用主线程。

- 转移控制权：把画布转交工作线程后，主线程不再能直接在上面绘制。
- 线程内绘制：工作线程拿到绘制上下文后按帧绘制，主线程只管收事件与转达交互。
- 数据传递：工作线程需要的数据通过消息传入，交互事件由主线程转发。
- 适用场景：需要持续高频绘制且计算量大的场景，收益最明显。
- 版本差异：不同浏览器对该能力的支持程度不一致，使用前需要探测。

```js
const offscreen = canvas.transferControlToOffscreen();
const renderWorker = new Worker("./renderWorker.js");

renderWorker.postMessage({ canvas: offscreen }, [offscreen]);
renderWorker.postMessage({ type: "resize", width, height });
```

> 控制权一旦转移就不可逆，主线程不能再调用该画布的绘图上下文，页面结构要提前按此约定设计。

**速记**：离屏画布把绘制搬到工作线程，主线程只转发事件与数据，控制权转移后不可逆。



#### 避免主线程阻塞的调度方式

**任务调度**：是决定各项计算在什么时机执行、每次执行多久的安排，目的是让每帧给渲染与输入留出时间。

- 分片执行：把长任务切成若干小块，块间让出线程，避免单次占用过久。
- 空闲时机：把可延迟的计算放到浏览器空闲时段执行。
- 帧内预算：为每帧的计算设定时间上限，超出部分推迟到下一帧。
- 优先级：交互相关的更新优先于后台统计与预计算。
- 合并触发：短时间内的多次触发合并成一次执行，减少重复计算。

```js
function runInChunks(tasks, onDone) {
  let index = 0;
  function step(deadline) {
    while (index < tasks.length && deadline.timeRemaining() > 4) {
      tasks[index]();
      index += 1;
    }
    if (index < tasks.length) {
      requestIdleCallback(step);
    } else {
      onDone();
    }
  }
  requestIdleCallback(step);
}
```

> [!WARNING]
> **警告内容**：把一个耗时数百毫秒的任务整块放在主线程执行，再快的绘制也救不回交互的卡顿，长任务必须切分或移出主线程。

**速记**：长任务切块执行、放到空闲时段、设定帧内预算，并优先保证交互相关的更新。



### 交互侧优化

交互会在短时间内产生大量事件与重算，处理不当会把绘制预算吃光。本节说明节流防抖、命中检测的降复杂度与反馈降级。

#### 节流与防抖

**节流**：是限制单位时间内回调执行次数；**防抖**：是在事件停止触发一段时间后才执行一次。

- 节流适用：拖拽、缩放、滚轮这类持续发生且需要即时反馈的操作。
- 防抖适用：输入框筛选、窗口尺寸变化这类只需最终结果的操作。
- 帧对齐：把回调对齐到下一次绘制时机执行，避免同一帧内多次计算。
- 参数快照：回调里读取事件参数后立即复制，避免后续访问到已失效的数据。
- 体验平衡：限制过严会让拖拽发涩，需要按交互类型选择合适间隔。

```js
function throttleByFrame(callback) {
  let pendingArgs = null;
  let scheduled = false;

  return (...args) => {
    pendingArgs = args;
    if (scheduled) return;
    scheduled = true;
    requestAnimationFrame(() => {
      scheduled = false;
      callback(...pendingArgs);
    });
  };
}

const handlePan = throttleByFrame((delta) => updateViewport(delta));
```

> 节流与防抖都在牺牲一部分即时性来换取稳定帧率，间隔要与操作的视觉预期匹配。

**速记**：持续操作用节流并尽量对齐帧，最终结果类用防抖，回调参数要当场复制。



#### 命中检测的降复杂度

**命中检测**：是判断某个坐标落在哪个图元上的计算，逐图元遍历在数据量大时会成为交互瓶颈。

- 空间索引：用网格或四叉树把图元按位置分桶，只检测落在附近的候选。
- 包围盒先行：先用外接矩形做粗筛，通过后再做精确判定。
- 像素查询：需要逐像素精度时可读取画布像素判断是否命中，代价是一次同步读取。
- 粗粒度选择：优先命中聚合后的区块或柱体，下钻到明细再放开精度。
- 距离排序：候选较多时按距离取最近者，避免返回互相遮挡的多个结果。

```js
function buildGridIndex(points, cellSize) {
  const grid = new Map();
  points.forEach((point, index) => {
    const key = `${Math.floor(point.x / cellSize)}:${Math.floor(point.y / cellSize)}`;
    const bucket = grid.get(key);
    if (bucket) bucket.push(index);
    else grid.set(key, [index]);
  });
  return grid;
}
```

> 空间索引的收益随数据量放大：几千条以内直接遍历未必更慢，几万条以上差距才明显。

**速记**：用网格或四叉树缩小候选范围，包围盒粗筛后再精判，也可用像素查询换取精度。



#### 交互反馈的降级

**反馈降级**：是在交互进行中主动降低绘制精度，交互结束后再恢复，用短暂的粗糙换取操作的跟手。

- 过程简化：拖拽时只画轮廓或骨架，松手后再绘制完整细节。
- 精度下调：交互中减少抗锯齿、阴影与渐变等昂贵效果。
- 局部更新：只重绘被操作对象覆盖的区域，其余部分保持不动。
- 分两级渲染：先给出粗略结果，稍后再补上精细版本。
- 恢复时机：交互结束的判定要稳，避免在连续操作中被反复触发。

> [!NOTE]
> **提醒内容**：降级只应发生在交互过程中，静止画面必须回到完整精度，否则用户会拿到一个长期粗糙的结果。

**速记**：交互中画骨架、降精度、只更新局部，松手后恢复完整绘制，静止画面不宜停留降级状态。



### 监控与基准

优化效果需要长期守住。本节说明性能埋点、基准场景与回归，以及上线后的持续观察。

#### 性能埋点与指标采集

**性能埋点**：是在关键路径上记录耗时与状态并上报的机制，用于判断线上是否真的达到了预期。

- 分段计时：在数据处理、绘制、交互响应处分别打点，上报各段耗时。
- 分位统计：上报耗时分布的高分位，而不是只报平均值。
- 环境维度：带上设备类型、屏幕尺寸与浏览器信息，便于按环境对比。
- 采样上报：全量上报会拖慢端上，按比例采样即可反映整体趋势。
- 异常关联：把卡顿与当次数据量、交互类型关联起来，才能定位成因。

```js
function reportTiming(name, duration, context) {
  if (Math.random() > 0.1) return;
  const payload = { name, duration, ...context };
  navigator.sendBeacon("/metrics", JSON.stringify(payload));
}

reportTiming("render", renderDuration, { pointCount, device: "mobile" });
```

> 上报本身也要算进成本：埋点过密会成为新的性能负担，采样与合并上报是常见做法。

**速记**：在数据处理、绘制与交互处分段打点，上报分位而非均值，按比例采样并关联数据量。



#### 基准场景与回归

**基准场景**：是一组固定输入与固定操作步骤构成的测试用例，用于在改动前后做可比对的性能测量。

- 固定数据：数据集与随机种子固定，避免输入差异掩盖性能变化。
- 固定操作：明确要执行的操作序列，如连续拖拽、连续缩放、切换数据源。
- 固定指标：关注同一组指标的高分位，保证不同轮次可比。
- 自动化：把基准跑成可在本地与流水线上重复执行的脚本。

```bash
# 基准脚本示意：同一数据集跑三轮，输出关键指标
npm run bench -- --dataset large --rounds 3
# render p95      24 ms
# interaction p95 68 ms
# long task max  120 ms
```

> 没有基准就无法判断一次改动是优化还是回退，尤其在优化手段相互叠加时更需要固定对照。

**速记**：基准要固定数据、操作与指标，做成可重复执行的脚本，并用阈值判定回归。



#### 上线后的持续观察

**持续观察**：是把性能指标纳入日常监控，按真实用户环境发现劣化并追溯原因。

- 真实环境：实验室数据无法覆盖全部设备与网络，线上分布更接近事实。
- 趋势优先：关注指标随时间的变化趋势，而非单次绝对值。
- 分环境下钻：按设备档位与数据规模分组，找出拉低整体的那一群。
- 关联发布：把指标拐点与版本发布时间对齐，便于定位引入问题的改动。
- 回路闭合：观察结论要回到基准用例，补上此前缺失的场景。

```js
function collectSlowFrame(metrics) {
  if (metrics.frameTime < 50) return;
  slowFrames.push({
    frameTime: metrics.frameTime,
    pointCount: metrics.pointCount,
    action: metrics.action,
    time: Date.now(),
  });
}
```

> 性能是可回归的：一次数据规模增长或一处新增标注，都可能抵消此前所有优化，观察必须长期进行。

**速记**：用真实环境的指标趋势发现劣化，按设备与数据规模下钻，并把结论补回基准用例。
