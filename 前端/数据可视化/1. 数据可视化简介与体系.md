## 数据可视化简介与体系

### 数据可视化是什么

数据可视化涉及的边界常被含糊处理：有人把它等同于画图，有人把它等同于某个图表库。本节先给定义，再区分相邻概念、产出形态与处理流程，划定讨论范围。

#### 数据可视化的定义

**数据可视化**：是把数据编码为图形标记与视觉通道的形式，使阅读者借助视觉感知直接完成比较、识别模式与发现关系的方法与技术。

- 数据侧：数值、分类、时间与空间位置等字段被绑定到图形属性。
- 图形侧：位置、长度、面积、颜色与形状等视觉通道承载数据差异。
- 目标侧：降低理解成本，让趋势、异常与关系在一眼之间可辨。
- 产物侧：静态图、交互图表、仪表盘与数据大屏。
- 边界侧：可视化不改变数据本身，只改变数据的呈现形式。

```json
{
  "date": "2026-09-01",
  "channel": "search",
  "visits": 12480,
  "conversion": 0.034
}
```

> 「可视化」强调把数据呈现出来，「可视分析」强调在图形界面上反复查询与推理，二者常配合使用但不互相替代。

**速记**：数据可视化是把数据映射为图形标记与视觉通道，目标是让模式和关系一眼可辨。



#### 可视化与相关概念的区分

**信息可视化（information visualization）**：是面向抽象非空间数据的可视化；**科学可视化（scientific visualization）**：是面向带空间坐标的物理场数据的可视化；**可视分析（visual analytics）**：是把交互式可视化与自动分析结合的分析方法。

- 信息可视化：处理抽象数据，如统计表格、网络关系与层级结构。
- 科学可视化：处理连续物理场，如流场、温度场与医学影像。
- 可视分析：以图形界面为核心，支持筛选、下钻与假设检验。
- 数据可视化：工程语境中常作上位词，泛指把数据转成图形的全部工作。
- 相邻工程概念：图表库、绘图接口与渲染引擎是实现手段，不等同于可视化方法本身。

```js
// 三类场景的输入形态不同，处理链路也不同
const tabularInput = [{ region: "华东", sales: 320 }]; // 信息可视化：抽象表格数据
const fieldInput = { grid: [32, 32], values: new Float32Array(1024) }; // 科学可视化：规则网格场
// 可视分析在这类输入之上再叠加筛选、缩放与联动等交互
```

> 本系列面向工程实现，主要覆盖信息可视化与日常工作报表，科学可视化的专用算法不在范围内。

**速记**：信息可视化管抽象数据，科学可视化管空间场，可视分析叠加交互推理。



#### 可视化的产出形态

**产出形态**：是可视化成果对外的载体形式，按交互程度与使用场景可分为静态图、交互图表、仪表盘与数据大屏四类。

- 静态图：导出为位图或矢量文件，用于报告、文章与印刷。
- 交互图表：在网页中响应悬停、筛选与缩放，用于探索与自助查询。
- 仪表盘：把多个指标与图表组织在一屏内，用于持续监控。
- 数据大屏：面向展示场景，强调远距离可读与整体观感。
- 共同约束：无论形态如何，数据映射的准确性优先于视觉表现。

```bash
# 一次发布链路中的三种产出形态
report.png          # 静态图：由脚本导出
dashboard/          # 交互图表：网页应用
wall/index.html     # 数据大屏：自适应页面
```

> [!NOTE]
> **提醒内容**：渲染精美不等于表达正确，交互丰富也不等于信息有效，产出形态的选择应服从阅读者要完成的任务。

**速记**：产出形态分静态图、交互图表、仪表盘与数据大屏，形态选择服从阅读任务。



#### 可视化的处理流程

**处理流程**：是从原始数据到可用图形的固定链路，通常包括获取、清洗转换、映射编码、渲染、交互与发布几个环节。

- 获取：从接口、文件或数据库取得原始数据。
- 转换：清洗缺失与异常，聚合到适合表达的粒度。
- 映射：把数据字段绑定到视觉通道，确定比例尺与坐标系。
- 渲染：用具体技术把图形绘制到页面。
- 交互与发布：补充事件响应、导出与部署。

```js
// 链路的函数骨架，各环节职责清晰、可单独替换
const rawRows = loadRows(source);
const tidyRows = cleanRows(rawRows);
const seriesData = buildSeries(tidyRows, "month");
const chart = renderChart(seriesData, { type: "line" });
```

> 映射环节是可视化的核心，它决定了数据差异是否被正确传达；其余环节都可以替换实现而不改变表达。

**速记**：链路是获取、转换、映射、渲染、交互发布五步，映射是可视化的核心环节。



### 为什么需要可视化

图形之所以有效，不是因为它更好看，而是因为它匹配人眼的感知方式与认知任务的节奏。本节从感知、任务、载体分工与决策链路四个方面说明可视化的价值。

#### 视觉感知的效率优势

**前注意加工（pre-attentive processing）**：是人眼在极短时间内无需刻意注意即可完成的视觉特征识别，位置、长度、颜色与朝向都属于这类特征。

- 并行识别：颜色与位置的差异可在大约几百毫秒内被整体察觉。
- 串行阅读：逐行读取表格数字需要依次比较，耗时随行数增长。
- 带宽差异：一条折线胜过逐条数字的对比，尤其在寻找趋势与拐点时。
- 适用边界：需要精确数值时必须回到表格或数值标注，图形擅长的是比较与模式。

```bash
# 同一组数据的两种呈现
# 表格：需要逐行阅读二十余个数字才能完成比较
# 折线图：趋势与拐点在一眼之内可见
```

> 视觉优势来自感知的并行性，图形适合「找出模式」，表格适合「读出数值」，二者互补而非替代。

**速记**：视觉感知可并行识别模式，图形用于找趋势，表格用于读精确值。



#### 可视化的四类任务

**分析任务**：是阅读者使用图表时要完成的认知工作，常用概览、缩放与筛选、按需查看细节、关联四步描述。

- 概览：先看整体分布与异常，再决定深入方向。
- 缩放与筛选：按时间、分类或数值条件收窄范围。
- 按需细节：在需要时查看单点数值与上下文说明。
- 关联：比较多个视图，寻找字段之间的关系。
- 落实方式：任务决定交互设计，而非交互决定任务。

```js
// 以任务为中心组织交互清单
const interactions = {
  overview: ["brush", "miniMap"],          // 概览
  filter: ["legendToggle", "rangeSlider"], // 筛选
  detail: ["tooltip", "clickDrill"],       // 细节
  relate: ["linkedHighlight"]              // 关联
};
```

> 这套任务分类来自可视化信息检索的经典框架，此处只取其中四个动作，便于直接对应到交互设计。

**速记**：任务分概览、筛选、细节与关联四步，交互设计从任务出发。



#### 图表与表格的分工

**分工原则**：是依据阅读者要回答的问题类型选择呈现形式，比较与模式用图表，精确数值与逐项查阅用表格。

- 用图表：趋势、分布、构成、关系与地理分布。
- 用表格：精确数值、多字段对照与逐条明细。
- 混用：图表给出全局，表格补充明细，二者在同一页面按主次排列。
- 判断标准：问题含「大约」「趋势」「相比」时用图表，含「多少」「具体」时用表格。

```bash
# 选择依据的快速对照
# 今年的营收在增长吗    -> 折线图
# 各区域营收分别是多少   -> 表格或带数值标注的柱状图
```

> 把明细表硬塞进图形，或把趋势硬读成表格，都会增加阅读成本，形式应由问题而非习惯决定。

**速记**：比较趋势用图表，精确数值用表格，混用时按主次排列。



#### 从数据到决策的链路

**决策链路**：是数据经采集、处理、可视化与解读后进入行动的完整过程，可视化承担其中的沟通与判断环节。

- 数据质量：上游错误会原样进入图形，可视化的可信度受制于数据。
- 解释偏差：图形可能被有选择地呈现，阅读者需要保持审视。
- 沟通效率：一页图胜过一段描述，是跨角色对齐的通用语言。
- 行动闭环：图表需要与阈值、责任与后续动作绑定才有意义。

```bash
# 监控闭环的要素
# 指标 -> 阈值 -> 告警 -> 处置 -> 复核
```

> [!CAUTION]
> **注意内容**：把可视化当作结论展示的终点，会忽略解读偏差与数据质量问题，图形只是判断的输入而非结论本身。

**速记**：可视化是数据到决策的中转站，其可信度受数据质量与解释方式两方面影响。



### 可视化技术栈全景

一张图表从数据到屏幕要穿过若干层次，每层都有可替换的方案。本节按渲染层、图表库层、工程支撑层与设计工具层梳理全景，为后续篇目定位坐标。

#### 渲染层：SVG、Canvas 与 WebGL

**渲染层**：是最终把图形写到屏幕上的底层技术，主流有 SVG、Canvas 与 WebGL 三条路线。

- SVG：可缩放矢量图形（Scalable Vector Graphics），用文档元素描述图形，天然支持事件与矢量缩放。
- Canvas：画布，用绘图接口逐帧绘制像素，图形数量大时性能好，但命中检测需自行处理。
- WebGL（Web Graphics Library，网页图形库）：直接调用 GPU 渲染，适合海量图形与三维场景。
- 选型线索：元素数量、是否需要逐元素交互、是否涉及三维，三条线索决定方向。
- 本系列位置：第 4 篇至第 11 篇专门展开三条路线与选型方法。

```html
<svg viewBox="0 0 120 60" width="120" height="60">
  <rect x="8" y="24" width="24" height="28" fill="#4c78a8"></rect>
  <rect x="44" y="12" width="24" height="40" fill="#4c78a8"></rect>
</svg>
```

> SVG 的图形即文档元素，Canvas 的图形是绘制指令的结果，这一差别决定了事件模型与性能特征完全不同。

**速记**：渲染层分 SVG、Canvas 与 WebGL，元素数量、交互粒度与是否三维决定选型。



#### 图表库层：配置式与语法式

**配置式图表库**：是开发者填写声明式配置、由库内部完成图形生成与交互的方案；**语法式工具**：是提供图形语法构件、由开发者显式描述映射与标记的方案。

- 配置式：按配置项组织，开箱即用，适合标准图表与快速交付。
- 语法式：按数据与映射组织，灵活度高，适合非标准图形与深度定制。
- 声明式规格：以 JSON 描述图表结构，工具据此渲染，便于跨语言复用。
- 选择依据：需求标准化程度、定制深度与团队熟悉度。
- 本系列位置：第 12 篇至第 16 篇分别展开。

```json
{
  "mark": "bar",
  "data": { "values": [{ "region": "华东", "sales": 320 }] },
  "encoding": {
    "x": { "field": "region" },
    "y": { "field": "sales" }
  }
}
```

> 配置式以「填表」换效率，语法式以「组装」换自由，二者解决的是不同阶段的成本问题。

**速记**：图表库分配置式与语法式，前者换效率，后者换自由，声明式规格便于跨端复用。



#### 工程支撑层：数据通道与框架集成

**工程支撑层**：是让图表在真实项目中可靠运行的数据获取、状态管理与组件集成能力。

- 数据通道：接口请求、轮询、长连接推送与离线文件。
- 状态管理：加载态、错误态、空数据态与刷新策略。
- 框架集成：把图表封装为组件，在生命周期内完成初始化与销毁。
- 自适应：监听容器尺寸变化，重新计算布局并重绘。
- 本系列位置：第 14 篇、第 15 篇、第 19 篇与第 20 篇覆盖集成与交付。

```js
// 组件内管理图表生命周期的骨架
function mountChart(container, data) {
  const chart = createChart(container);
  chart.setOption(buildOption(data));
  return () => chart.destroy(); // 卸载时释放资源
}
```

> [!TIP]
> **建议内容**：把数据获取、状态处理与图表渲染分成三层编写，接口更换或库替换时只需改动其中一层。

**速记**：工程支撑层负责数据通道、状态管理、框架集成与自适应，分层编写可降低替换成本。



#### 工具与设计层

**设计层**：是配色、版式与设计规范等决定图表观感与可读性的工作；**工具层**：是产出与校验设计结果的软件。

- 设计工具：矢量绘图与协作工具用于出图与标注规范。
- 配色工具：调色板生成与对比度检查工具用于保证可读性。
- 数据工具：表格与脚本环境用于探索数据分布。
- 规范载体：把颜色、字号与间距固化为变量，减少逐图手工调整。
- 本系列位置：第 3 篇讲配色与版面，第 19 篇讲大屏视觉。

```css
/* 设计令牌示例：把图表用色与间距统一为变量 */
:root {
  --chart-font-size: 12px;
  --chart-gap: 8px;
  --chart-series-1: #4c78a8;
}
```

> 工具只是执行者，决定图表质量的是映射是否恰当与减法是否到位，工具无法替代判断。

**速记**：设计工具层负责配色、版式与规范，把样式固化为令牌才能保证全站一致。



### 经典案例与失败案例

方法论的来源往往不是口号而是具体作品。本节从经典案例提炼准则，从失败案例归纳反例，给出可迁移的判断依据。

#### 经典案例的共同特征

**经典可视化案例**：是被长期引用的可视化作品，其价值不在作图技巧，而在用最简单的图形回答了明确的问题。

- 霍乱地图：以点位叠加街区边界，直观呈现病例围绕同一水源聚集。
- 拿破仑东征图：用线宽表达兵力、用横向位置表达进军与撤退，把多个变量压进一张图。
- 南丁格尔玫瑰图：以扇区面积对比不同月份的死亡原因构成，推动了公共卫生改革。
- 共同特征：问题明确、映射直接、无关装饰被刻意去除。
- 可迁移之处：先确定要回答的问题，再选择能承担该问题的图形。

```bash
# 从经典案例反推的设计步骤
# 1 明确问题 -> 2 选数据变量 -> 3 定视觉通道 -> 4 去掉无关装饰
```

> 经典案例之所以成立，一半靠图形，一半靠它回答的问题足够重要，模仿图形而不理解问题会形似而神不似。

**速记**：经典案例的共同点是用直接映射回答明确问题，而非追求复杂图形。



#### 失败案例的常见类型

**可视化失败**：是图形在表达上产生误解、噪声或错误结论的情形，常见于数据、编码与装饰三个层面。

- 数据层面：口径混乱、样本不全、单位不统一。
- 编码层面：用面积表达一维数值，或用无顺序的配色表达连续量。
- 装饰层面：立体柱形、重阴影与无关背景图遮挡数据。
- 布局层面：一屏堆叠过多图表，缺少主次与阅读顺序。
- 后果：阅读者得到错误结论，而且往往毫无察觉。

```js
// 反面取向：用三维立体柱与重阴影表达单变量数值
// 立体透视会改变柱体的可见高度，比较失去意义，属于错误做法
const badOption = { type: "bar3d", itemStyle: { shadowBlur: 20 }, backgroundImage: "cloud.png" };
```

> [!WARNING]
> **警告内容**：用面积或体积表达一维数值、用带顺序含义的配色表达无序分类，都会稳定地产生误读，属于必须避免的做法而非风格选择。

**速记**：失败多源于数据口径、编码方式、多余装饰与布局堆叠，后果是误读而不易察觉。



#### 误导手法的识别清单

**误导手法**：是通过截断坐标轴、改变基线或选择性呈现数据来放大或掩盖差异的做法，识别它们是阅读图表的基本功。

- 截断纵轴：纵轴起点远离零时，柱形高度差异被放大。
- 改变基线：把图线平移到不同起点，制造趋势差异。
- 双轴错配：两套纵轴刻度被人为调整，制造虚假相关。
- 选择性取样：只展示有利时间段，忽略完整序列。
- 应对话术：先看坐标轴范围，再看数据完整性与口径。

```js
// 识别截断纵轴的检查点（数值型坐标轴）
const axisTicks = [95, 97, 99, 101, 103];
// 刻度起点远离零且图形为柱状时，需要警惕比例被放大
```

> 数据失真的完整原理与规避方法见本主题第 2 篇 数据与视觉编码原理。

**速记**：识别误导先看坐标轴范围，再看数据完整性与口径，截断与双轴是高频手法。



#### 从案例中提炼的判断准则

**判断准则**：是评价一张图表是否成立的检查项，覆盖问题、数据、映射与呈现四个角度。

- 问题是否明确：这张图要回答什么，阅读者能否在数秒内说出结论。
- 数据是否可信：口径、单位、时间范围与样本是否交代清楚。
- 映射是否恰当：图形属性与数据类型的对应是否合理。
- 呈现是否克制：装饰是否压过数据，配色是否服务于区分。
- 是否可复现：数据来源与生成脚本是否可追溯。

```bash
# 交付前自查四问
# 1 要回答的问题是什么
# 2 数据口径是否写清
```

### 本系列结构与学习路径

本系列共 21 篇，按「先建立原理认知、再打图形底座、再做图表实现、最后落工程与性能」五段推进。本节给出分段、各阶段重点与建议顺序。

#### 篇目分段

- 原理层（第 1 篇至第 3 篇）：数据可视化简介与体系、数据与视觉编码原理、色彩与图表设计原则。
- 图形底座（第 4 篇至第 11 篇）：SVG 绘图基础、SVG 进阶、Canvas 2D 绘图基础、Canvas 进阶、Canvas 动画与交互、WebGL 与 GPU 渲染基础、Three.js 三维可视化入门、渲染技术选型。
- 图表实现与库应用（第 12 篇至第 16 篇）：D3 数据驱动与选择集、D3 比例尺坐标轴与布局、ECharts 快速上手与配置体系、ECharts 进阶、AntV 与其它图表方案。
- 空间、性能与工程（第 17 篇至第 20 篇）：地理与空间数据可视化、大数据量与渲染性能优化、大屏与仪表盘实战、可视化可访问性与工程化。
- 收尾（第 21 篇）：参考资料与延伸阅读。

```bash
# 前端/数据可视化 篇目分段
# 原理层          1-3
# 图形底座         4-11
# 图表实现与库应用  12-16
# 空间性能与工程    17-20
# 收尾            21
```

> 分段遵循「先懂原理、再练底座、后用成品库、终至工程调优」的顺序，颠倒会让配置项失去依据。

**速记**：21 篇分五段，原理层打底，图形底座决定表现力，库应用决定效率，工程段负责交付。



#### 各阶段的学习重点

- 原理层：理解可视化的目标与任务，掌握数据类型与视觉通道的对应，能做出正确的图表选型。
- 图形底座：能直接操作 SVG 与 Canvas，理解动画与三维的基本机制，能按需求选择渲染技术。
- 图表实现与库应用：能用 D3 组装自定义图形，用 ECharts 快速交付标准图表，并能读懂图形语法。
- 空间、性能与工程：能处理地理数据，能定位并解决渲染性能问题，能交付大屏与无障碍方案。
- 收尾：建立持续查阅官方文档与规范的能力。

> 原理层三篇是后续所有篇目的公共词汇表，跳读会让比例尺、通道与配色的讨论失去上下文。

**速记**：各阶段从建立认知、掌握渲染、熟练用库到工程交付逐层递进。



#### 建议顺序

- 顺序阅读：第 1 篇至第 21 篇依次推进，每篇末尾的速记可用于复习。
- 偏设计方向：优先第 1 篇至第 3 篇、第 16 篇与第 19 篇，再按需补图形底座。
- 偏工程方向：以第 1 篇、第 2 篇、第 6 篇至第 15 篇、第 18 篇至第 20 篇为主线。
- 做地图：先读第 2 篇与第 17 篇，再回第 11 篇确认渲染技术。
- 做三维：第 3 篇之后进入第 9 篇、第 10 篇，再回第 11 篇做选型。
- 排查性能：先读第 18 篇定位瓶颈，再按结论回到对应渲染篇调优。
- 衔接说明：CSS 的过渡与动画详见 前端/CSS 主题第 13 至 15 篇，通用 DOM 与 ARIA 详见 前端/HTML 主题第 17 篇。
