## 渲染技术选型：SVG、Canvas 与 WebGL

### 三种渲染模型的机制对照

选型的前提是理解三种底座在「图形如何被记住、如何被画出来」上的根本差异。本节只做机制对照，不展开任何一方的 API 用法。

#### 保留模式与立即模式

**保留模式（retained mode）**：由渲染系统长期保存图形对象并负责重绘，代码只描述画面里有什么；**立即模式（immediate mode）**：不保存图形对象，每帧由代码重新发出全部绘制指令。

- 图形归属：保留模式的图形是常驻对象，可被单独查询与修改；立即模式只有像素结果，没有可查询的图形对象。
- 更新单位：保留模式可以只改一个对象；立即模式每次都要重放或局部重绘整块画布。
- 状态管理：保留模式无需手动保存绘图状态；立即模式需要自行维护与恢复上下文状态。
- 代价分布：保留模式随元素数增长维护成本，立即模式随每帧指令数增长单帧成本。

```js
// 立即模式的心智模型：一帧等于一次完整的指令执行
function renderFrame(surface, drawScene) {
  surface.clear();
  drawScene(surface);
}

// 保留模式的心智模型：只改动发生变化的那一个对象
function moveOneMark(graph, markId, nextX) {
  const mark = graph.findById(markId);
  mark.setPosition(nextX, mark.y);
}
```

**速记**：保留模式保存图形对象、支持单点更新，立即模式不保存图形、每帧重放指令。



#### 矢量输出与位图输出

**矢量输出**：用几何描述生成画面，任意缩放都重新光栅化；**位图输出**：把结果落到固定像素网格，缩放会暴露像素。

- 分辨率：矢量与显示密度无关，位图必须按显示密度准备足够的像素。
- 放大表现：矢量放大不糊，位图放大出现锯齿或模糊。
- 导出：矢量可直接导出为可编辑的矢量文件，位图导出需选择目标分辨率。
- 文本表现：位图中的文字不参与字体渲染管线，小字号下更易发虚。

```js
// 位图底座需要按显示密度计算实际像素数
function requiredPixelSize(cssWidth, cssHeight, dpr) {
  const width = Math.round(cssWidth * dpr);
  const height = Math.round(cssHeight * dpr);
  return { width, height, pixels: width * height };
}

console.log(requiredPixelSize(800, 400, 2));
// { width: 1600, height: 800, pixels: 1280000 }
```

**速记**：矢量按几何重绘、与显示密度无关，位图落在固定像素网格、放大有损。



#### CPU 与 GPU 的分工

**CPU 路径**：由主线程执行绘制与合成，适合指令数不多的场景；**GPU 路径**：把顶点与像素计算交给显卡并行执行，适合大量图元或复杂像素效果。

- 并行度：CPU 核心数有限且要兼顾脚本与布局，GPU 面向大规模并行计算。
- 传输成本：GPU 方案需要把数据上传到显存，数据量小或每帧重建时反而更慢。
- 状态切换：GPU 绘制调用之间存在状态切换，把相同状态的图元合批能显著提速。
- 适用规模：指令数在千级以下时三种方案差别不大，进入万级后路径选择才成为关键。

```js
// 判断运行环境是否具备 GPU 绘制能力
function hasGpuDrawingSupport() {
  const probe = document.createElement("canvas");
  const context = probe.getContext("webgl2") || probe.getContext("webgl");
  return Boolean(context);
}

console.log(hasGpuDrawingSupport()); // true 或 false
```

**速记**：CPU 路径通用但并行有限，GPU 路径并行度高但有数据上传与状态切换成本。



#### 三者的优势与代价

**综合对照**：把三种底座在交互、无障碍、规模与实现成本四个方面的表现并列，作为选型的直觉入口。

- SVG：交互粒度细、可被辅助技术读取、样式与事件体系完整；代价是元素数量上升后 DOM 与重绘成本快速增加。
- Canvas：单帧绘制成本可控、可做像素级处理；代价是内容不可查询、文本不进入无障碍体系、高分屏需自行适配。
- WebGL：能承载十万级图元与复杂特效；代价是开发成本高、需要着色器与资源管理知识、调试更困难。
- 共同点：三者最终都要经过合成进入屏幕，差异在于谁来保存图形、谁来执行绘制。

```js
// 用统一的描述对象记录候选方案的特征，供后续决策函数使用
const rendererProfiles = {
  svg: { granularity: "element", accessible: true, maxMarks: 2000, effort: "low" },
  canvas: { granularity: "pixel", accessible: false, maxMarks: 100000, effort: "medium" },
  webgl: { granularity: "batch", accessible: false, maxMarks: 1000000, effort: "high" },
};
```

> [!NOTE]
> **提醒内容**：这里的数量级只是参考值，实际拐点受图形复杂度、更新频率与设备性能影响，必须用本机实测结果替代经验值。

**速记**：SVG 强在交互与无障碍、Canvas 强在单帧控制、WebGL 强在规模与特效，代价依次递增。



### 选型维度与判定顺序

机制差异要落到可操作的判断上。本节给出维度清单、判定顺序与常见场景的结论。

#### 关键选型维度

**选型维度**：是需要逐项确认的约束条件，共同决定哪种底座能同时满足表现与成本。

- 元素数量：同屏需要出现的图形个数，是划分三种方案的最主要依据。
- 更新频率：是静态展示、偶发更新，还是每帧变化。
- 交互粒度：需要单个图形响应事件，还是只做整体平移缩放。
- 无障碍要求：内容是否需要被屏幕阅读器与搜索引擎读取。
- 缩放与导出：是否需要无损放大与矢量导出。
- 维护成本：团队是否具备相应技术储备，后续由谁维护。

```js
// 把选型维度组织成一个输入对象，便于逐项确认
const selectionInput = {
  markCount: 5000,
  updatesPerSecond: 60,
  needsPerMarkEvents: true,
  needsAccessibility: true,
  needsVectorExport: false,
  teamFamiliarity: { svg: true, canvas: true, webgl: false },
};
```

**速记**：数量、更新频率、交互粒度、无障碍、导出与维护成本共同决定方案，数量是首要变量。



#### 判定顺序

**判定顺序**：是按先排除、后优化组织的决策流程，先用硬性要求筛掉不可行项，再在可行项中选成本最低者。

- 第一步：确认是否需要逐元素交互或无障碍，若必须，则优先 SVG。
- 第二步：估算同屏图形数量与每帧更新量，超过万级且每帧变化时排除 SVG。
- 第三步：确认是否已有 GPU 技术储备，没有则优先在 Canvas 内解决。
- 第四步：检查是否有单帧像素级效果或十万级图元需求，有则选择 WebGL。
- 第五步：剩余情形选实现成本最低的方案，并预留后续迁移的抽象层。

```js
// 逐步排除的判定函数，返回建议的渲染路径
function pickRenderer(input) {
  if (input.needsPerMarkEvents && input.markCount <= 2000) return "svg";
  if (input.markCount >= 100000 && input.teamFamiliarity.webgl) return "webgl";
  if (input.updatesPerSecond >= 30 || input.markCount >= 5000) return "canvas";
  return "svg";
}

console.log(pickRenderer({ markCount: 200, updatesPerSecond: 0,
  needsPerMarkEvents: true, teamFamiliarity: { webgl: false } })); // "svg"
```

> [!TIP]
> **建议内容**：判定顺序的第二步最容易被跳过，很多项目在元素上万后才发现卡顿，重新选型的代价远高于一开始就按数量做预估。

**速记**：先按交互与无障碍排除，再按数量与更新量排除，最后按团队成本择优。



#### 常见场景的对应结论

**场景结论**：是把典型可视化需求提前对应到推荐方案，减少重复决策。

- 折线图、柱状图、饼图等常规图表，元素数在数百级：SVG，配合成熟图表库。
- 带大量标注与提示的仪表盘，元素数在数千级且更新不频繁：SVG 或 Canvas 均可，优先看交互需求。
- 散点图与热力图，点数上万且随平移缩放重绘：Canvas。
- 实时更新的流式曲线与监控大屏，每帧重绘：Canvas。
- 三维地形、粒子系统、十万级连线网络：WebGL。
- 需要导出矢量文件用于印刷：SVG，必要时把位图结果作为预览。

```js
// 场景到方案的映射，用对象表达以便按场景名查询
const scenarioToRenderer = {
  standardChart: "svg",
  annotatedDashboard: "svg",
  largeScatter: "canvas",
  streamingLine: "canvas",
  particleField: "webgl",
  vectorExport: "svg",
};
```

**速记**：常规图表用 SVG，大点集与实时流用 Canvas，三维与超大规模用 WebGL。



### 混合渲染方案

单一方案不必覆盖全部画面。本节说明分层叠加的结构、分层边界的划分与事件合并方式。

#### 分层叠加的结构

**分层叠加**：是在同一容器内叠放多个渲染层，各层使用不同底座，只有内容变化的那一层需要重绘。

- 静态层：坐标轴、网格、图例等不随交互变化的内容放在底层。
- 动态层：随数据或交互变化的内容放在上层。
- 交互层：命中区域与提示锚点可单独成层，用最轻的方式实现。
- 顺序：层的堆叠顺序由文档顺序与层级决定，交互层通常在动态层之上。

```html
<!-- 静态轴层用 SVG，动态数据层用 Canvas，叠在同一容器内 -->
<div class="chart-stack">
  <svg class="layer layer--axis" viewBox="0 0 800 400"><!-- 坐标轴与文字 --></svg>
  <canvas class="layer layer--marks" width="800" height="400"></canvas>
  <div class="layer layer--hit" role="presentation"><!-- 命中区域 --></div>
</div>
```

**速记**：按内容变化频率分层，静态用 SVG、动态用 Canvas、命中单独成层。



#### 分层的边界划分

**边界划分**：是决定哪些元素放哪一层的规则，划分不当会让两层的数据都要频繁同步。

- 按更新频率：每帧变化的放动态层，只在数据切换时变化的放静态层。
- 按交互需求：需要逐元素事件的少量元素留在可交互层，其余进入动态层。
- 按绘制成本：数量大且样式统一的标记放位图层，便于批量绘制。
- 一致性：两层的坐标必须来自同一套映射，否则平移缩放时会出现错位。

```js
// 按更新频率把数据拆到两层，避免动态层承担静态内容
function splitByUpdateFrequency(marks, isAnimated) {
  const dynamic = [];
  const staticLayer = [];
  marks.forEach((mark) => {
    (isAnimated(mark) ? dynamic : staticLayer).push(mark);
  });
  return { dynamic, staticLayer };
}
```

> [!WARNING]
> **警告内容**：两层使用各自独立的坐标换算时，缩放或平移后必然出现错位；坐标映射必须有唯一来源，两层都从同一函数取值。

**速记**：按更新频率、交互需求与绘制成本划分归属，两层共享同一坐标映射。



#### 事件与交互的合并

**事件合并**：是把分散在各层的交互统一到容器上处理，避免为每个图形单独绑定监听器。

- 事件代理：在容器上监听一次，按坐标反查最近的目标元素。
- 命中归属：位图层的元素无法直接命中，需要维护一份坐标与数据的对应关系。
- 提示框：提示内容由命中结果驱动，渲染位置与所在层无关。
- 层级冲突：上层容器会遮挡下层事件，必要时给非交互层关闭指针事件。

```js
// 在容器上监听一次，按坐标查找最近的标记
function attachHitTest(container, marks, onPick) {
  container.addEventListener("pointermove", (event) => {
    const rect = container.getBoundingClientRect();
    const x = event.clientX - rect.left;
    const y = event.clientY - rect.top;
    const hit = marks
      .filter((mark) => Math.abs(mark.x - x) < 6 && Math.abs(mark.y - y) < 6)
      .sort((a, b) => Math.hypot(a.x - x, a.y - y) - Math.hypot(b.x - x, b.y - y))[0];
    onPick(hit);
  });
}
```

**速记**：交互在容器上用事件代理统一处理，位图内容靠坐标反查命中，非交互层关闭指针事件。



### 性能边界与实测方法

经验值只能给方向，真实拐点必须测。本节说明影响性能的变量、拐点判断与测量写法。

#### 影响性能的变量

**性能变量**：是决定单帧成本的可控因素，识别它们才能设计有效的对照实验。

- 图形数量：同屏需要绘制的图形个数，是最主要的变量。
- 单图形复杂度：一个图形包含多少段路径、多少顶点与多少描边细节。
- 更新方式：整幅重绘与局部更新的成本差异可达数量级。
- 每帧数据量：每帧写入的属性数与分配的对象数，会触发垃圾回收。
- 显示密度：高分屏的物理像素更多，位图方案的单帧填充成本随之上升。

```js
// 构造对照实验的变量组合，每次只改变一个因素
const experimentFactors = {
  markCounts: [500, 2000, 10000, 50000],
  updateModes: ["full", "partial"],
  vertexCounts: [4, 16, 64],
  pixelRatios: [1, 2],
};
```

**速记**：图形数量、单图形复杂度、更新方式、每帧数据量与显示密度共同决定单帧成本。



#### 数量级拐点的判断

**拐点**：是帧率或单帧耗时开始明显变差的数量级位置，通常表现为耗时随数量从平缓转为陡增。

- 观察指标：稳定状态下的平均单帧耗时，以及第 95 百分位耗时，后者更接近卡顿感。
- 判断方法：保持其他变量不变，按数量级递增图形数，记录耗时首次超过预算的位置。
- 预算基准：60 帧每秒对应约 16.7 毫秒每帧，交互场景应留出一半余量。
- 结论使用：把拐点作为方案的适用上限，并预留冗余应对设备差异。

```js
// 逐档增加图形数，记录单帧耗时并标出是否在预算内
const frameBudgetMs = 16.7;

async function probeScaling(benchmarkAt, markCounts) {
  const results = [];
  for (const count of markCounts) {
    const avgMs = await benchmarkAt(count);
    results.push({ count, avgMs, withinBudget: avgMs <= frameBudgetMs });
  }
  return results;
}
```

> [!CAUTION]
> **注意内容**：在高性能开发机上测出的拐点不能直接当作线上容量，低端设备与高显示密度的组合可能只有其几分之一，需要按目标设备分层测试。

**速记**：拐点靠保持变量不变、按数量级递增测得，用第 95 百分位耗时与帧预算共同判定。



#### 基准测量的写法

**测量写法**：是先预热、再统计多次运行的分布，避免把首次执行的编译与分配成本当成稳定值。

- 预热：先跑若干帧触发编译与缓存建立，再开始计时。
- 计时入口：performance.now() 返回毫秒级高精度时间戳，适合测量短区间。
- 采样：用 requestAnimationFrame 统计连续帧的间隔，比单次入口耗时更贴近真实体验。
- 排除干扰：关闭无关动画与开发者工具，避免后台任务污染结果。

```js
// 统计连续帧的耗时分布，输出平均值与第 95 百分位
function measureFrameTiming(totalFrames) {
  return new Promise((resolve) => {
    const samples = [];
    let last = 0;
    let count = 0;
    function onFrame(now) {
      if (last) samples.push(now - last);
      last = now;
      count += 1;
      if (count < totalFrames) {
        requestAnimationFrame(onFrame);
        return;
      }
      const sorted = samples.slice().sort((a, b) => a - b);
      const avg = samples.reduce((sum, v) => sum + v, 0) / samples.length;
      resolve({ avg, p95: sorted[Math.floor(sorted.length * 0.95)] });
    }
    requestAnimationFrame(onFrame);
  });
}
```

**速记**：先预热再取样，用高精度时间戳与逐帧间隔统计，结论看平均值与第 95 百分位。



### 迁移与重构路径

选型可能随数据规模变化而改变。本节说明两种迁移方向、迁移时机与抽象层的取舍。

#### 从 SVG 迁移到 Canvas

**迁移方向**：把以节点为核心的绘制改成以数据为核心的绘制，图形的可查询性随之消失，需要补上命中等补偿机制。

- 保留的部分：坐标映射、比例尺与数据变换逻辑可以原样复用。
- 重写的部分：创建节点的逻辑改为绘制指令，样式改为绘制参数。
- 补偿的部分：命中检测、提示框定位与可访问性替代形式需要另行实现。
- 控风险：先迁移数据量最大的序列，保留 SVG 层处理交互密集的少量元素。

```js
// 用统一接口隔离底座差异，迁移时只替换实现
function createSvgRenderer(interfaceSpec) {
  return { ...interfaceSpec, kind: "svg" };
}

function createCanvasRenderer(interfaceSpec) {
  return { ...interfaceSpec, kind: "canvas" };
}
```

**速记**：迁移保留数据与映射逻辑，重写绘制与样式，补齐命中与无障碍补偿。



#### 从 Canvas 迁移到 WebGL

**迁移方向**：把逐图形调用改为批量顶点数据与着色器，重心从绘制指令转移到数据组织与显存管理。

- 数据组织：同一批次共享属性的图元合并成一组顶点数据上传。
- 状态控制：减少批次间的状态切换，把相同材质的图元排在一起。
- 回退路径：为不支持 GPU 绘制的环境保留 Canvas 实现，按能力选择。
- 验证方式：迁移后先比对同一数据集下的像素结果，再对比性能。

```js
// 按能力选择实现，保留低端环境的回退路径
function createRendererFor(env) {
  if (env.hasWebgl && env.markCount >= 100000) return createWebglRenderer();
  if (env.hasCanvas) return createCanvasRenderer();
  return createSvgRenderer();
}
```

**速记**：迁移把逐图元调用改为批量顶点数据，需合批、回退并逐像素校验结果。



#### 迁移时机的判断

**迁移时机**：是决定现在就换方案还是先优化现有实现的分界，过早迁移会付出不必要的重写成本。

- 先优化：出现卡顿时先排查数据量、更新范围与绘制频率，多数问题不必换底座。
- 看趋势：数据规模预计持续增长且已接近拐点时，提前规划迁移更划算。
- 看边界：只有交互粒度或无障碍要求发生变化时，才必须跨越大类边界。
- 看成本：迁移涉及命中、提示与无障碍补偿，需与可获得的性能收益一并评估。

```js
// 结合当前耗时与增长趋势判断是否值得迁移
function shouldMigrate(currentAvgMs, frameBudgetMs, growthPerQuarter) {
  const projected = currentAvgMs * (1 + growthPerQuarter) ** 4;
  return currentAvgMs > frameBudgetMs * 0.8 || projected > frameBudgetMs;
}
```

**速记**：先优化再迁移，只有规模增长逼近拐点或硬性要求变化时才跨大类重写。



#### 抽象层与渐进式替换

**抽象层**：是在业务代码与具体渲染底座之间插入的一层接口，使替换实现时业务逻辑基本不动。

- 接口边界：只暴露与业务相关的方法，如绘制一帧、更新数据、命中查询与销毁。
- 成本控制：抽象层只为确实会变化的维度设计，过度抽象会拖慢开发。
- 渐进替换：按图层或序列逐个替换实现，同一页面允许两种底座并存。
- 回归保障：替换后用数据快照与视觉快照比对，确认图形与交互均未退化。

```js
// 抽象层按注入的实现工作，业务侧不感知底座类型
class ChartSurface {
  constructor(implementation) {
    this.implementation = implementation;
  }

  render(dataset, scales) {
    this.implementation.draw(dataset, scales);
  }

  pick(pointerX, pointerY) {
    return this.implementation.hitTest(pointerX, pointerY);
  }
}
```

> [!IMPORTANT]
> **重要内容**：抽象层应围绕确实会变化的边界设计，若项目已确定长期只用一种方案，引入抽象层只会增加维护成本而没有收益。

**速记**：抽象层隔离底座差异，按图层渐进替换，用数据与视觉快照验证回归。
