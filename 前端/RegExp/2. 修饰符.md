## 修饰符

### 修饰符总览

#### 八个标志一览

**修饰符（flags，也称标志）**：是写在正则末尾、改变匹配行为的一组单字母开关。每个标志在 RegExp 对象上都有一个对应的只读布尔属性。

- **d（hasIndices）**：为匹配结果附加起止索引 indices，ES2022 引入。
- **g（global）**：全局匹配，一次匹配成功后把 lastIndex 推到匹配末尾，可继续向后查找。
- **i（ignoreCase）**：忽略大小写；配合 u 时启用 Unicode 大小写折叠。
- **m（multiline）**：让 ^ 和 $ 匹配**每一行**的开头与结尾。
- **s（dotAll）**：让 . 也能匹配行终止符。
- **u（unicode）**：按 **Unicode 码点**而非 UTF-16 码元处理，启用 Unicode 属性转义与码点转义。
- **v（unicodeSets）**：u 的升级版，支持字符类的集合运算，ES2024 引入。
- **y（sticky）**：粘性匹配，**只在 lastIndex 位置**尝试，不向后搜索。

```js
console.log(/a/g.test("aaa"));     // true
console.log(/a/i.test("A"));       // true
console.log(/^b/m.test("a\nb"));   // true（m 让 ^ 匹配每行开头）
console.log(/a.b/s.test("a\nb"));  // true（s 让 . 匹配换行）
console.log(/^.$/u.test("𝄞"));      // true（u 让 . 按码点匹配，𝄞 是非 BMP 字符）
```



#### 标志的组合与互斥

**八个标志可以任意组合**，书写顺序不影响语义；其中 **u 与 v 互斥**，同时使用直接抛 SyntaxError。

- **组合自由**：/abc/gi 与 /abc/ig 完全等价，flags 属性会按 d g i m s u v y 的固定顺序重排。
- **u 与 v 互斥**：v 是 u 的增强版，同时写 uv 会抛 SyntaxError；开启 v 后 unicodeSets 属性为 true，而 **unicode 属性仍为 false**——后者只反映“有没有显式写 u”。
- **状态类标志只有两个**：g 与 y 会让匹配带上“进度”，其余六个都是纯粹的行为开关。

```js
console.log(new RegExp("a", "yusmigd").flags); // "dgimsuy"（顺序被规范化）

// v 与 u 的属性取值：v 不把 unicode 置为 true
console.log(new RegExp("a", "v").unicode, new RegExp("a", "v").unicodeSets); // false true
console.log(new RegExp("a", "u").unicode, new RegExp("a", "u").unicodeSets); // true false

// u 与 v 互斥：任何环境都会在此抛 SyntaxError
// new RegExp("a", "uv");
// → SyntaxError: Invalid flags supplied to RegExp constructor 'uv'
```

> [!CAUTION]
> **注意内容**：只有 **g 与 y** 会让 test 与 exec 在连续调用之间“记住进度”，也只有它们会引发时对时错的经典故障。写校验类正则时，其余六个标志都可以放心保留，g 与 y 则要按“是否需要连续推进”来决定留不留。



### g 修饰符与 lastIndex

#### lastIndex 的定义

**lastIndex**：是 RegExp 实例上的一个可写整数，表示**下一次匹配从字符串的哪个位置开始**。只有带 g 或 y 标志的正则才会用到它。

```js
const digitReg = /\d/g;

console.log(digitReg.test("a1")); // true，匹配到索引 1，lastIndex 变为 2
console.log(digitReg.test("a1")); // false，从索引 2 起无匹配，lastIndex 归零
console.log(digitReg.test("a1")); // true，lastIndex 已归零，重新从头匹配
```

把同一个带 g 的正则用在**不同的字符串**上，问题更隐蔽：

```js
const wordReg = /\w+/g;

console.log(wordReg.test("hello")); // true，lastIndex 停在 5
console.log(wordReg.test("world")); // false！从索引 5 开始，新串根本没有索引 5
```

> [!WARNING]
> **警告内容**：lastIndex 陷阱的两条规避原则：**做“是否存在”的验证时不要加 g**；**复用带 g/y 的正则前，显式把 lastIndex 重置为 0**。带 g 的 exec 循环结束时若匹配失败，lastIndex 会自动归零，但成功后不会，这正是坑的来源。



#### lastIndex 的精确语义

**lastIndex 是普通可写属性，不是一个只读的“游标”**：可以手工赋值，甚至能赋成负数或小数；但取值时机由引擎控制，写入者永远只能改变“下一次从哪儿开始”。

- **可写**：reg.lastIndex = 5 立即生效，下一次匹配就从下标 5 开始尝试。
- **失败归零**：一次匹配失败后引擎把 lastIndex 置为 0，无需手工清理。
- **成功推进**：成功时推进到**匹配结束的下标**，注意这是**结束位置而不是长度**。
- **test 与 exec 同步**：两者对 lastIndex 的处理完全一致，混用也会互相影响。
- **非字符串参数先转换**：传入数字、布尔值等会被转成字符串再匹配，而 lastIndex 仍按转换后的字符串计算。

```js
const scanReg = /b/g;

scanReg.lastIndex = 0;
console.log(scanReg.exec("abcb")); // ["b"]，index 1，lastIndex 推到 2
console.log(scanReg.lastIndex);    // 2

scanReg.lastIndex = 3;
console.log(scanReg.exec("abcb")[0]); // "b"，从下标 3 正好命中，lastIndex 推到 4
console.log(scanReg.lastIndex);       // 4

console.log(scanReg.exec("abcb")); // null，越界失败
console.log(scanReg.lastIndex);    // 0（失败自动归零）

// 非字符串参数：先被转成字符串
console.log(/\d/.test(123)); // true（123 被转成 "123"）
```



#### 跨字符串复用的隐蔽故障

**验证场景是最容易踩 lastIndex 陷阱的地方**：同一个带 g 的正则实例被多个输入轮流使用时，前一个输入消耗掉的位置会让后一个本应通过的输入返回 false，故障表现为“时对时错、毫无规律”。

```js
// 典型事故：表单校验器复用了一个带 g 的正则
const validator = /\d{6}/g; // 验证码应为 6 位数字

function check(code) {
  return validator.test(code); // 带状态！
}

console.log(check("123456")); // true
console.log(check("123456")); // false！上一次调用把 lastIndex 推到了 6
```

> 排查这类故障的要点是**看正则实例的生命周期**：只要一个带 g 的正则被存进变量、模块顶层或对象属性里供多处调用，test 与 exec 的连续调用就会互相影响。修复只需去掉 g，或每次调用前重置 lastIndex。



#### 重置 lastIndex 的三种写法

**重置的优先级是“换写法优于改状态”**：能让状态根本不产生，就不要事后去擦。

- **首选：干脆不加 g**。只做“有没有”判断时，g 没有任何收益，还会引入状态。
- **次选：每次用前置零**。必须在多处共享同一个带 g 的实例时，进入使用前写 reg.lastIndex = 0。
- **新代码首选 matchAll**：它内部会**克隆一份正则**，不污染原对象的 lastIndex，从根上避开这个坑。

```js
// 写法一：去掉 g，状态不复存在
const noStateReg = /\d{6}/;
console.log(noStateReg.test("123456"), noStateReg.test("123456")); // true true

// 写法二：每次用前重置
const resetReg = /\d{6}/g;
function checkWithReset(code) {
  resetReg.lastIndex = 0;
  return resetReg.test(code);
}
console.log(checkWithReset("123456"), checkWithReset("123456")); // true true

// 写法三：matchAll 内部克隆，原对象不受影响
const clonedReg = /\d{6}/g;
console.log([..."123456".matchAll(clonedReg)].length); // 1
console.log(clonedReg.lastIndex); // 0（原对象没被推进）
```



### y 修饰符与粘性匹配

#### y 与 g 的分水岭

**y 修饰符（sticky，粘性模式）**：要求匹配**必须正好从 lastIndex 位置开始**，不允许向后搜索。

```js
const reg = /a/y;

reg.lastIndex = 1;
console.log(reg.exec("ba")); // ["a"]（位置 1 正好是 a）

reg.lastIndex = 0;
console.log(reg.exec("ba")); // null（位置 0 是 b，粘性匹配不放宽）
console.log(reg.lastIndex);  // 0（失败后自动归零）
```

> y 与 g 的分水岭在于**能不能往后找**：g 是“从 lastIndex 起向后找到第一个匹配”，y 是“就在 lastIndex 这个位置，成则成、不成则败”。

- **g 的定位**：向后搜索，找到为止，失败即结束。
- **y 的定位**：原地判断，不允许移动起点。
- **共同的起点**：都从 lastIndex 开始，成功后都推进 lastIndex。
- **共同的状态风险**：都是由 lastIndex 驱动的有状态匹配。



#### 用 y 写一个词法分析器

粘性匹配真正的用武之地是**逐段切分**：一段一段地切，切不动就说明位置错了，这正是词法分析器（tokenizer）的判定逻辑。

```js
const input = "42 + 7 * 3";
const tokenReg = /\s+|\d+|[+*/-]/y; // 空白、数字、运算符
let cursor = 0;

while (cursor < input.length) {
  tokenReg.lastIndex = cursor; // 把粘性正则的起点交给游标
  const match = tokenReg.exec(input);
  if (!match) {
    console.log("无法识别的字符：", input[cursor]);
    break;
  }
  cursor = tokenReg.lastIndex;
  if (/^\s+$/.test(match[0])) continue;      // 空白跳过
  console.log(/\d/.test(match[0]) ? "数字" : "符号", match[0]);
}
// 数字 42、符号 +、数字 7、符号 *、数字 3
```

> [!TIP]
> **建议内容**：写词法分析器时**把整串交给粘性正则、只改 lastIndex**，不要每轮都 slice 出剩余子串。后者每次复制字符串，长文本下开销随轮数线性累积；前者原地推进，且报错时能直接拿出出错位置的下标。



### m 修饰符与多行锚点

#### m 改变了什么

**m 修饰符**：改变 ^ 与 $ 的含义，使其匹配**每一行的行首行尾**，而非只匹配整个字符串的开头结尾。

```js
const lines = "第一行\n第二行\n第三行";

console.log(lines.match(/^第/g));   // ["第"]（无 m，只匹配开头一次）
console.log(lines.match(/^第/gm));  // ["第", "第", "第"]（有 m，每行开头都算）

console.log(/行$/m.test(lines));    // true（最后一行以“行”结尾）
```

> ^ 与 $ 只匹配**位置**、不消耗字符，属于**锚点**。m 影响的只有这两个锚点，不影响 .，也不影响 \b。



#### 多行文本的批量校验

多行文本校验靠 m 让锚点逐行生效，逐行全部合法时仍须按行拆开判断。

```js
// m 的实战场景：逐行校验粘贴的多行文本
const bulk = "张三,13800138000\n李四,13900139000\n王五,13700137000";

console.log(/^.+,\d{11}$/m.test(bulk)); // true（存在一行符合“名字,手机号”）

// 配合 g m 提取每一行的行首内容
console.log(bulk.match(/^[^\n,]+/gm)); // ["张三", "李四", "王五"]
```

**逐行校验必须用 m**，这是把“整串匹配”升级为“每行匹配”的唯一开关；但要注意 **m 只让锚点按行生效，不会自动把字符串拆成行**——想逐行处理仍然要靠 split 或 matchAll。

```js
const input = "13800138000\n1380013800\n13900139000";

// 只要有一行合法就通过：适合“整段文本里有可用值”的场景
console.log(/^1[3-9]\d{9}$/m.test(input)); // true

// 要求每一行都合法：m 帮不上忙，必须逐行判断
const allValid = input.split("\n").every((line) => /^1[3-9]\d{9}$/.test(line));
console.log(allValid); // false（第二行少一位）
```



### s 修饰符与 dotAll

#### s 改变了什么

**s 修饰符（dotAll）**：让 . 也能匹配**行终止符**。

```js
console.log(/a.b/.test("a\nb"));  // false（. 默认不匹配换行）
console.log(/a.b/s.test("a\nb")); // true（s 模式下 . 匹配换行）

// 旧写法：用“任意空白 + 任意非空白”绕开限制
console.log(/a[\s\S]b/.test("a\nb")); // true
```

> 默认情况下 . 匹配除 \n、\r、\u2028、\u2029 之外的任意字符。开启 s 后 . 能匹配一切，/[\s\S]*/ 这类绕路写法就可以退休了。



#### 三种“匹配任意字符”的写法对比

**三种写法在语义与性能上各有取舍**，选哪一种取决于是否需要结构性约束。

- **. 加 s**：语义最直白，跨行也照吃，代价是完全没有结构约束，回溯空间最大。
- **[\s\S]**：不依赖标志，效果与 . 加 s 相同，老环境的兼容写法。
- **[^x]**：**排除型字符类**，只要目标里不会出现 x，它就是三者中最快的，因为它把“任意字符”收缩成了“非 x”。

```js
const code = "const a = 1;\n/* 说明第一行\n说明第二行 */\nconst b = 2;";

// s 的实战场景：匹配跨行的块注释
console.log(code.match(/\/\*[\s\S]*?\*\//) !== null); // true（传统写法）
console.log(code.match(/\/\*.*?\*\//s) !== null);     // true（s 写法语义更直白）

// 排除型字符类：明确“注释里不会再有斜杠星号”时最省资源
console.log(code.match(/\/\*[^*]*\*\//) !== null);    // true（无回溯风险）

// 换行符的四种形态：. 默认一个都不匹配
console.log(/./.test("\r"), /./.test("\u2028"), /./.test("\u2029")); // false false false
```



### i 修饰符与大小写折叠

#### 大小写折叠的范围

**i 修饰符（ignoreCase）**：匹配时忽略大小写。对 ASCII 字母而言它做的是简单的同字母大小写等价；配合 u 修饰符时则执行 **Unicode 大小写折叠**，连变音字母、特殊大小写规则都能对上。

```js
console.log(/hello/i.test("HELLO"));  // true
console.log(/hello/.test("HELLO"));   // false（默认区分大小写）

// 配合 u：按 Unicode 简单大小写折叠，同一字母的大小写形态互配
console.log(/café/iu.test("CAFÉ"));  // true（é 与 É 互配）
console.log(/σ/iu.test("Σ"));        // true（希腊字母的大小写形态互配）

// 注意折叠不跨“音调与拼写”：é 与 e 是不同字母，互不相等
console.log(/café/iu.test("CAFE"));  // false
console.log(/strasse/iu.test("straße")); // false（ß 与 ss 的全折叠 JavaScript 不支持）
```

> [!CAUTION]
> **注意内容**：i 的“忽略大小写”在 u 模式下按 **Unicode 简单大小写折叠**执行：同一字母的大小写形态互配（é 与 É、σ 与 Σ），但**不做音调剥离与拼写展开**——é 与 e 互不相等，ß 与 ss 也不相等。做**身份证后缀 X 与 x**、**十六进制颜色值**这类“只差大小写”的匹配时用 i 没有副作用；涉及多语言文本的等价判断时，先实测再上线。



#### i 在哪些场景没有副作用

**i 的安全使用边界是“同一字母的大小写形态”**：目标里只可能出现同一字母的大小写变体时，i 用起来毫无风险。

```js
// 场景一：文件后缀（PDF 与 pdf 是同一种格式）
console.log(/\.pdf$/i.test("报告.PDF")); // true

// 场景二：十六进制颜色值（FF 与 ff 是同一个值）
console.log(/^#[0-9a-f]{6}$/i.test("#FF8800")); // true

// 场景三：协议名与 HTTP 方法（规范本身不区分大小写）
console.log(/^(get|post)$/i.test("POST")); // true

// 场景四：身份证末位的 X（大写小写都合法）
console.log(/^\d{17}[\dX]$/i.test("11010519491231002x")); // true
```

> [!NOTE]
> **提醒内容**：**不要把 i 当成“文本归一化”手段**。需要处理的如果是全角半角、繁体简体、组合变音符，i 一概不管——那些属于第 8 篇《Unicode 与中文处理》的范畴，得靠 normalize 与属性转义解决。



### u 修饰符与 Unicode 码点

#### 从码元到码点

**u 修饰符**：让正则按 **Unicode 码点**而非 UTF-16 码元工作，并启用 Unicode 属性转义 \p{...} 与码点转义 \u{...}。

```js
// 𝄞（U+1D11E，音乐符号）超出 BMP，由两个代理项码元组成
console.log("𝄞".length);      // 2
console.log(/^.$/.test("𝄞"));  // false（无 u：. 只匹配一个码元）
console.log(/^.$/u.test("𝄞")); // true（有 u：. 匹配一个完整码点）

console.log(/^\u{1D11E}$/u.test("𝄞")); // true（码点转义，必须配合 u）

// Unicode 属性转义 \p{...}
console.log(/\p{Script=Han}/u.test("中"));    // true（汉字）
console.log(/\p{Script=Greek}/u.test("α"));   // true（希腊字母）
console.log(/\p{Emoji}/u.test("🚔"));          // true（emoji 集合）
```

> u 模式下，正则的“字符”概念从**码元**升级为**码点**：量词、字符类、. 全部按码点计数，emoji、生僻汉字不再被拦腰截断。凡是要处理中文、emoji、多语言文本，都应默认加上 u。属性的完整用法见系列第 8 篇《Unicode 与中文处理》。



#### u 与 v 的关系

**v 是 u 的语法超集，但不是 u 的属性翻版**：v 模式下的匹配行为与 u 完全一致（\p{...}、\u{...} 都可用），字符类还额外获得集合运算能力；但 **unicode 属性不会因为写 v 而变成 true**，判断“是否按码点工作”要改看 unicodeSets。

```js
console.log(/\p{Script=Han}/v.unicode);     // false（v 不设置 unicode 属性）
console.log(/\p{Script=Han}/v.unicodeSets); // true
console.log(/\p{Script=Han}/v.test("中"));  // true（匹配行为与 u 一致）

// v 模式允许的集合运算
console.log(new RegExp("[\\p{Letter}--[ae]]", "v").test("b")); // true

// v 模式收紧转义：字符类里的 (、)、[、]、{、}、/、| 等必须转义
// new RegExp("[a-z--[ae]]", "v");  → SyntaxError
console.log(new RegExp("[a-z--[ae]]").source); // "[a-z--[ae]"（非 v 模式下 -- 只是字面短横线）
```

> [!IMPORTANT]
> **重要内容**：迁移策略是**从 u 迁到 v，而不是从无标志直接跳到 v**：先在 u 模式下把模式跑通，再把标志换成 v，让收紧的转义规则一次性暴露所有隐含写法。反过来直接从无标志跳到 v，会同时面对两类报错，很难定位。



### d 修饰符与匹配索引

#### indices 的结构

**d 修饰符（hasIndices）**：给匹配结果附加 indices 属性，记录每个匹配（含捕获组）在原串中的**起止位置**。

```js
const dateReg = /(?<year>\d{4})-(\d{2})/d;
const match = dateReg.exec("今天是 2024-01-15");

console.log(match.index);               // 4
console.log(match.indices);             // [[4, 11], [4, 8], [9, 11]]
console.log(match.indices.groups.year); // [4, 8]（命名分组也有索引）
```

> indices 是一个二维数组，第 0 项是整个匹配的 start 与 end，其后依次是各捕获组；命名分组额外挂在 indices.groups 上。做**关键词高亮、代码定位、编辑器插件**这类“必须知道匹配落在哪”的场景时，d 是唯一省事的方案。注意 end 是**开区间**（不含该下标）。



#### 用索引做精准替换与高亮

**indices 的价值在于“拿到位置而不动原串”**：需要把多个匹配按顺序改写成另一段文本时，用索引从后往前替换，可以完全避开“替换后下标集体漂移”的问题。

```js
// 场景一：按索引切原串，零误差取出命中片段
const log = "09:12:01 [E404] 页面不存在 [E500]";
const errReg = /\[(?<code>E\d{3})\]/gd;
const m = errReg.exec(log);

const start = m.indices[0][0];
const end = m.indices[0][1];
console.log(log.slice(start, end)); // "[E404]"（用索引切原串，零误差）

// 场景二：从后往前替换，避开下标漂移
const text = "价格 128 元，折扣 32 元";
const numReg = /\d+/gd;
const hits = [...text.matchAll(numReg)].map((item) => item.indices[0]);

let result = text;
for (let i = hits.length - 1; i >= 0; i--) {
  const [from, to] = hits[i];
  result = result.slice(0, from) + "**" + result.slice(from, to) + "**" + result.slice(to);
}
console.log(result); // "价格 **128** 元，折扣 **32** 元"
```

> 从后往前替换是**文本改写的通用技巧**：每改一次，前面所有未处理片段的下标都不受影响。反过来从前向后改，每插入一个字符，后面所有记录的索引就全部失效一位。



### v 修饰符与集合表示法

#### 集合运算三件套

**v 修饰符（unicodeSets）**：是 u 的增强版，在字符类中引入**集合运算**与**多字符字符串**匹配，ES2024 引入。

```js
// 差集 --：所有字母，排除 a、e
console.log(/[\p{Letter}--[ae]]/v.test("b")); // true
console.log(/[\p{Letter}--[ae]]/v.test("a")); // false

// 交集 &&：既是希腊字母又是字母
console.log(/[\p{Script=Greek}&&\p{Letter}]/v.test("α")); // true

// 并集：直接并列书写
console.log(/[\p{Script=Han}\p{Script=Latn}]/v.test("中")); // true

// \q{} 匹配多字符字符串（字符类里可以放“串”而不只是“字符”）
console.log(/[\q{元|美元}]/v.test("100元")); // true
console.log(/[\q{元|美元}]/v.test("美元"));  // true（并集里的两个串都能命中）
```

> v 让字符类从“字符的集合”升级为“字符串的集合”，语法上支持 --（差集）、&&（交集）与并列（并集）。代价是**字符类里的 -、(、)、[、]、{、}、/、| 等必须转义**，原本在 u 模式下能用的部分写法会直接报 SyntaxError。这是较新的特性，写业务代码前先确认目标运行环境与构建工具的转译能力。



#### v 模式的实用写法

**v 真正省事的地方是“emoji 与集合的差”**：按推荐序列整字匹配 emoji、从一类字符里做减法，这两件事在 u 模式下手写极其冗长。

- **\p{RGI_Emoji}**：按 Unicode 推荐的 emoji 序列整字匹配，一句顶一长串区间。
- **\p{Emoji_Keycap_Sequence} 等序列属性**：旗帜、键帽、肤色修饰等组合序列都有对应属性。
- **差集做黑白名单**：从全字母中排掉易混字符（如 l、I、1、O、0），是生成短码的常用手段。

```js
// 整字匹配一个带肤色修饰的 emoji
console.log(/\p{RGI_Emoji}/v.test("👍🏻")); // true

// 生成去掉了易混字符的短码字符集
const codeCharReg = /^[[\p{Letter}\p{Number}]--[lIO01]]+$/v;
console.log(codeCharReg.test("abcXYZ")); // true
console.log(codeCharReg.test("abcIlO")); // false（含易混字符）

// 单位后缀的集合匹配
const unitReg = /^\d+(?:\.\d+)?[\q{元|万元|美元}]$/v;
console.log(unitReg.test("12.5万元")); // true
console.log(unitReg.test("12.5日元"));  // false
```

> [!WARNING]
> **警告内容**：v 的**浏览器与运行时支持面明显窄于 u**，且部分构建工具（旧版 Babel、旧版 Terser）无法正确解析 v 模式的字符类，会把集合运算当成普通转义处理甚至直接报错。生产环境用 v 之前，务必确认目标浏览器基线与构建链版本，必要时保留一份等价的 u 写法作为降级。
