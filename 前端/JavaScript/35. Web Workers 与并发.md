## Web Workers 与并发

### 为什么需要 Worker

#### 单线程模型的瓶颈

**JS 单线程**：一个页面里所有脚本任务共用一个主线程，重计算会阻塞渲染与交互。

> [!NOTE]
> **提醒内容**：主线程被长任务占住时，事件回调排队等待，表现为页面卡顿掉帧。凡是毫秒级以上的纯计算（大数组处理、编解码、哈希运算），都值得考虑移出主线程。



#### Worker 的定位

**Web Worker**：在浏览器里另开的独立线程，与主线程互不阻塞，通过消息通信协作。

- 能做：跑纯计算、用 fetch 与 WebSocket、用 setTimeout 等定时器、访问 IndexedDB。
- 不能做：直接操作 DOM、访问 window 与 document、使用 localStorage。
- 生命周期：随创建者页面存在，页面关闭即销毁；也可手动 terminate 提前结束。



### 三种 Worker

#### 专用 Worker

**专用 Worker**：一个创建者独占一个 Worker，最常用的形态。

```js
// worker.js —— 子线程脚本
self.onmessage = (event) => {
  const { start, end } = event.data;
  let sum = 0;
  for (let i = start; i <= end; i++) sum += i;
  self.postMessage(sum);
};

// 主线程
const worker = new Worker("worker.js");

worker.postMessage({ start: 1, end: 5 });

worker.onmessage = (event) => {
  console.log("主线程收到:", event.data);
  worker.terminate();
};
```

```text
主线程收到: 15
```

> 消息传递是异步双向的：postMessage 立即返回不阻塞，onmessage 收到再处理。子线程里 self 就是该线程的全局对象，terminate 立即杀死子线程，未处理的消息全部丢弃。



#### 共享 Worker

**共享 Worker**：多个同源页面、多个 iframe 可连接同一个 Worker 实例，靠端口区分会话。

- 主线程经 new SharedWorker(url) 创建，通过 worker.port 收发消息，且必须 port.start() 或显式收发后端口才会工作。
- 子线程里用 onconnect 事件接收每个新连接，event.ports[0] 是与该页面一对一的端口。
- 典型用途：多标签页共享同一个 WebSocket 连接或同一份缓存。

```js
// shared-worker.js —— 每个 tab 接进来广播一次消息
onconnect = (event) => {
  const port = event.ports[0];
  port.onmessage = (e) => {
    port.postMessage("回执: " + e.data);
  };
};

// 主线程
const sw = new SharedWorker("shared-worker.js");

sw.port.postMessage("hello");
sw.port.onmessage = (e) => console.log(e.data);
```

> 共享 Worker 调试难度高于专用 Worker：Chrome 里要在 DevTools 的 Sources 面板按 URL 单独打开。连接数可以用 onconnect 里维护计数感知，页面关闭时端口自动断开。



#### Service Worker 概况

**Service Worker**：代理整个页面网络请求的常驻 Worker，是 PWA 离线能力的核心。

- 生命周期独立于页面：注册、安装、激活后持续存在，不受页面刷新影响。
- 通过 fetch 事件拦截并改写或应答网络请求，配合 Cache API 实现离线缓存。
- 只能运行在 HTTPS 或 localhost 环境，作用域由注册路径决定。

> [!IMPORTANT]
> **重要内容**：Service Worker 是独立的进阶主题，本文只交代它在 Worker 家族里的位置。缓存策略、版本更新、fetch 拦截细节应在网络与服务端线的专门篇目展开。



### 消息通信机制

#### 结构化克隆与转移

**结构化克隆**：postMessage 传对象时按克隆算法深拷贝，收发两侧各持独立副本。

```js
const orig = { arr: [1, [2, 3]], set: new Set([1, 2]) };
const cloned = structuredClone(orig);

cloned.arr[1].push(99);

console.log(orig.arr[1], cloned.arr[1]);
console.log(cloned.set instanceof Set);
```

```text
[ 2, 3 ] [ 2, 3, 99 ]
true
```

> 结构化克隆支持多数内置类型（数组、Map、Set、Date、RegExp、TypedArray、Blob），不支持函数、DOM 节点与原型链——对象过一趟 postMessage 后只剩数据、丢失方法。大对象克隆有拷贝开销，明显偏大的数据改用转移。



#### 转移与所有权

**转移**：postMessage 的第二参数里列出可转移对象（ArrayBuffer、MessagePort 等），所有权整体移交给接收方，零拷贝。

```js
const buf = new ArrayBuffer(8);

console.log("转移前:", buf.byteLength);
```

```text
转移前: 8
```

- 主线程写法：worker.postMessage(buf, [buf])，发出后原引用 byteLength 归 0，不能再用。
- 适用场景：子线程处理完的大缓冲区（图像帧、文件片段）直接移交主线程，免去整块复制。
- 转移后对象在发送侧已「分离」，再访问属性不会报错但全是 0 长度，容易埋雷。



#### MessageChannel 与端口

**MessageChannel**：一对直连的通信端口，让 Worker 之间、页面与 iframe 之间点对点传消息。

```js
const { port1, port2 } = new MessageChannel();

port1.onmessage = (event) => {
  console.log("收到:", event.data);
};

port2.postMessage({ type: "scan", ip: "10.0.0.8" });
```

```text
收到: { type: 'scan', ip: '10.0.0.8' }
```

> 两个端口天生互连，postMessage 到任何一端都会出现在另一端的 onmessage。把 port2 转移给某个 Worker，主线程就能用 port1 与它建立专用通道，多个 Worker 各持一个端口即可组网通信，不必都挤在主线程转发。



#### 双向请求应答协议

**请求应答协议**：在消息体里带上任务编号，让多条并发任务的结果可以各回各家。

```js
let seq = 0;
const pending = new Map();

function callWorker(worker, payload) {
  const id = ++seq;
  return new Promise((resolve) => {
    pending.set(id, resolve);
    worker.postMessage({ id, payload });
  });
}

worker.onmessage = (event) => {
  const resolve = pending.get(event.data.id);
  if (resolve) {
    pending.delete(event.data.id);
    resolve(event.data.result);
  }
};
```

> 消息本身没有请求关联语义，谁先回来都进同一个 onmessage，靠编号配对是唯一可靠的办法。共享 Worker、MessageChannel 通道都套用同一思路。



#### Worker 的错误处理

**错误处理**：Worker 内部抛出的异常不会出现在主线程的 try-catch 里，只能靠错误事件接住。

- worker.onerror：接住子线程里未捕获的运行时错误，event.message 带错误信息。
- worker.onmessageerror：接住反序列化失败，即对方发来的数据无法结构化克隆还原。
- 子线程脚本加载失败（404、语法错误）同样走 onerror，可借此做降级与重试。

```js
worker.onerror = (event) => {
  console.log("子线程错误:", event.message, "行", event.lineno);
};

worker.onmessageerror = () => {
  console.log("消息无法克隆还原");
};
```

> 主线程的 try-catch 包住 postMessage 只能拦截发送侧的同步错误（如克隆失败），子线程执行期的错误一律走 onerror。不做错误兜底的 Worker 调用失败时页面表现为「发了消息再也没回音」。



### 共享内存与原子操作

#### SharedArrayBuffer

**SharedArrayBuffer**：可在多个线程间共享读写的底层内存块，转移之外的第二种跨线程数据共享方式。

```js
const sab = new SharedArrayBuffer(8);
const view = new Int32Array(sab);

Atomics.store(view, 0, 0);
console.log("初始:", Atomics.load(view, 0));
console.log("加后:", Atomics.add(view, 0, 5));
console.log("再读:", Atomics.load(view, 0));
```

```text
初始: 0
加后: 0
再读: 5
```

> SharedArrayBuffer 必须配 TypedArray 视图读写，且页面需处于跨域隔离状态（COOP 与 COEP 响应头齐全）才能创建，否则构造直接抛错。Atomics.add 的返回值是加之前的旧值，不是新值。



#### Atomics 原子操作

**Atomics**：一组原子读写、算术与等待唤醒方法，保证共享内存上的操作不被线程交错打断。

- store 与 load：原子写入与读取指定下标。
- add、sub、and、or、xor：原子算术位运算，返回旧值。
- wait 与 notify：线程在整数下标上休眠等待，另一线程改值后唤醒，用于自旋锁与生产者消费者模型。

> Atomics.wait 在浏览器主线程被禁止调用（会冻结页面），只能用在 Worker 里。共享内存加原子操作是性能敏感场景的方案，普通业务一律走消息传递，复杂度低一个量级。



### 主线程侧的卸载模式

#### 计算任务封装

**任务封装**：把可序列化的计算包成「发参数、收结果」的消息协议，主线程当 Promise 用。

```js
function runInWorker(worker, payload) {
  return new Promise((resolve, reject) => {
    worker.onmessage = (e) => resolve(e.data);
    worker.onerror = (e) => reject(e.message);
    worker.postMessage(payload);
  });
}

const hashWorker = new Worker("hash-worker.js");

runInWorker(hashWorker, { text: "hello" })
  .then((digest) => console.log("摘要:", digest))
  .catch((err) => console.log("失败:", err));
```

> 调用点的 Promise 包装与并发任务的编号配对，直接复用上文「双向请求应答协议」一节的现成实现；本节只需注意 runInWorker 用赋值方式挂 onmessage，重复赋值会覆盖旧监听。



#### Worker 池

**Worker 池**：预建固定数量的 Worker，任务排队轮流分发，避免每任务新建销毁的开销。

- 初始化：按 navigator.hardwareConcurrency 决定池大小，一般不超过它。
- 分发：空闲即取队首任务；全忙则入队等待。
- 回收：常驻任务场景不销毁；偶发批量任务完成后统一 terminate。

> [!TIP]
> **建议内容**：不追求极致吞吐时，一个复用的单 Worker 加 Promise 协议已覆盖多数需求。Worker 池值得写的信号是任务频繁、单任务耗时短、主线程排队明显。



#### 分治汇总的实战

**分治汇总**：把一大段计算切成若干块，分发给多个 Worker 并行跑，主线程归并结果。

```js
const pool = Array.from(
  { length: navigator.hardwareConcurrency || 2 },
  () => new Worker("sum-worker.js")
);

function sumRange(start, end) {
  const size = Math.ceil((end - start + 1) / pool.length);
  const jobs = [];

  for (let i = 0; i < pool.length; i++) {
    const from = start + i * size;
    const to = Math.min(from + size - 1, end);
    jobs.push(callWorker(pool[i], { start: from, end: to }));
  }
  return Promise.all(jobs).then((parts) =>
    parts.reduce((sum, n) => sum + n, 0)
  );
}

sumRange(1, 1000000).then((total) => console.log("总和:", total));
```

> 切块数与 Worker 数对齐，每块用 callWorker 独立配对，Promise.all 等全部到齐后归并。数据规模不足够大时，切块与消息的开销会超过并行收益，小块计算留在主线程反而更快。



### 常见陷阱

#### 忽视消息开销

**消息开销**：postMessage 的克隆与调度并非零成本，高频小消息会反噬性能。

> 主循环里每帧向 Worker 发几十条小消息，克隆开销与事件调度会吃掉收益。合并策略：攒批发送（一次传数组）、传 TypedArray 而非普通数组、大数据走转移。普通数组每项克隆，TypedArray 视图按整块处理，差距是数量级的。



#### 子线程里用错全局对象

**全局对象错用**：Worker 里没有 window、document 与 localStorage，混用直接抛引用错误。

- 拿全局对象写 self，主线程与 Worker 通用。
- 需要操作 DOM 的逻辑留在主线程，Worker 只回传数据。
- 判断环境可用 typeof WorkerGlobalScope !== "undefined"。

> [!CAUTION]
> **注意内容**：把主线程脚本原样搬进 Worker 文件，凡触碰 DOM 与 window 的代码都会在运行时才报错。迁移前先过一遍全局引用，报错点在线程内部时主线程控制台只显示笼统的 onerror 信息，排查成本高。
