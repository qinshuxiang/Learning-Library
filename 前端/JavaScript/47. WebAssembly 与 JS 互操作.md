## WebAssembly 与 JS 互操作

### wasm 是什么与定位

#### 二进制指令格式

**WebAssembly（简称 wasm）**：是一种以二进制字节码分发的可移植指令格式，在各类运行时里以接近原生的速度执行，并带静态类型校验。

- 二进制分发：文件以魔数 0x00 0x61 0x73 0x6d 起头、4 字节版本号紧随，内容是指令与数据段，不可直接阅读。
- 模块单位：一个 wasm 文件或一段字节数组构成一个模块，模块内以段组织类型、函数、内存、全局变量与导出项。
- 基于栈的虚拟机：指令从栈上取操作数、把结果压回栈，无寄存器概念，校验器可在加载前静态推导每一步的类型。
- 沙箱执行：模块默认没有宿主能力，碰不到文件与网络，只能操作自带的线性内存，能力全部由宿主注入。

> [!NOTE]
> **提醒内容**：沙箱是双向的——wasm 摸不到宿主环境，宿主给什么能力它就有什么能力。这个模型是安全分析的基线：样本表现出任何外联或持久化行为，必然经由它导入的宿主函数。



#### 与 JS 的关系是补充不是替代

**wasm 补 JS 之短**：重计算下放给 wasm，界面与生态仍留在 JS，两者经明确的边界交换数据。

- 分工格局：音视频编解码、密码学运算、游戏物理、图像处理等计算密集任务交给 wasm；DOM 操作、事件、网络仍由 JS 承担。
- 性能来源：wasm 指令格式稳定、可提前编译为机器码，省去 JS 引擎对动态类型的推测与回收。
- 互操作成本：跨边界传值只支持数值类型，复杂对象要经线性内存序列化，边界本身有固定开销，粒度过细反而更慢。
- 不替代的理由：wasm 不能直接持有 DOM 节点，生态工具链、包管理与调试体验也仍以 JS 为中心。

> 把整段业务重写成 wasm 通常不划算：只有被测出热点、且热点逻辑不碰 DOM 的部分才值得下沉。跨边界调用按次数收费，一次传大块数据远胜一百次传小值。



#### 浏览器与 node 双端支持

**WebAssembly 全局对象**：浏览器与 node 都内置同名全局，API 完全一致，同一份字节码两端通用。

```js
console.log(typeof WebAssembly);
console.log(typeof WebAssembly.instantiate);
console.log(typeof WebAssembly.Module);
console.log(typeof WebAssembly.Instance);
```

```text
object
function
function
function
```

- 编译入口：WebAssembly.instantiate(bytes, importObject) 异步编译并实例化，返回带 module 与 instance 的对象；WebAssembly.Module 与 WebAssembly.Instance 提供同步版本。
- 流式编译：浏览器端还有 instantiateStreaming，可直接消费网络响应，省一次缓冲。
- 验证时机：字节码在编译期做全量类型校验，不合法的字节直接报 CompileError，不会带病运行。

> 上述输出取自 node 实跑，浏览器控制台里结果一致。写教程或排查时优先用 node 验证字节码本身，把浏览器差异留给真正依赖浏览器能力的部分。



### 最小模块实跑

#### 手写字节数组：魔数与版本头

**wasm 二进制头部**：固定 8 字节，前 4 字节是魔数 0x00 0x61 0x73 0x6d（即 ASCII 的空字符加 asm），后 4 字节是版本号 1。

```js
// 只含魔数与版本头的空模块，本身就是合法的 wasm
const bytes = new Uint8Array([0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00]);

WebAssembly.instantiate(bytes).then(({ instance }) => {
  console.log(Object.keys(instance.exports).length);
  console.log(instance instanceof WebAssembly.Instance);
});
```

```text
0
true
```

- 头部之后是段序列，每段以 1 字节段号加 LEB128 编码的段长起头，段体长度必须与声明严格一致。
- 常用段号：1 类型、2 导入、3 函数、5 内存、6 全局、7 导出、10 代码，段号决定解析顺序。
- 魔数写错或段长对不上，instantiate 直接以 CompileError 拒绝，这是手写字节时最先撞上的两道墙。

> 空模块没有任何导出却通过了校验，说明二进制格式本身可逐字节验证。手写字节是理解 wasm 结构的最短路径：所有工具链产物，最终都能还原成这样的字节数组。



#### 类型段与函数段结构概述

**段结构**：类型段声明函数签名，函数段把每个函数映射到某个签名，两者配合让校验器不执行代码就能核对每次调用。

- 类型段（段号 1）：条目以 0x60 起头，依次是参数个数、参数类型、返回值个数、返回值类型；i32 写作 0x7f、i64 写作 0x7e、f32 写作 0x7d、f64 写作 0x7c。
- 函数段（段号 3）：只列每个函数用的类型索引，函数体在代码段。
- 导出段（段号 7）：条目为名字长度、名字、导出种类（0 函数、2 内存、3 全局）与索引。
- 代码段（段号 10）：每个函数体以局部变量声明起头，随后是指令序列，以 0x0b 收尾。

以导出 add 函数的模块为例，八个字节一段地读，全部内容一目了然。

```text
00 61 73 6d 01 00 00 00        头部：魔数与版本
01 07 01 60 02 7f 7f 01 7f     类型段：1 个签名 (i32, i32) -> i32
03 02 01 00                    函数段：1 个函数，用 0 号签名
07 07 01 03 61 64 64 00 00     导出段：名字 add（61 64 64），函数 0 号
0a 09 01 07 00 20 00 20 01 6a 0b   代码段：函数体取两参相加
```

- 函数体逐指令读：0x00 声明无局部变量，0x20 0x00 与 0x20 0x01 依次压入两个参数，0x6a 是 i32.add，0x0b 结束。

> 段长是手写字节最容易算错的地方：段长声明的是段体字节数，不含段号与段长自身。逐段累加字节数再回填长度，比一次写完再改可靠得多。



#### 导出 add 函数并在 node 实跑

**最小可调用模块**：把上面五个段拼成完整字节数组，交给 WebAssembly.instantiate 实例化后，导出的 add 就是一个普通 JS 函数。

```js
// 最小 wasm 模块：导出 add(i32, i32) -> i32
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00, // 魔数与版本
  0x01, 0x07, 0x01, 0x60, 0x02, 0x7f, 0x7f, 0x01, 0x7f, // 类型段
  0x03, 0x02, 0x01, 0x00, // 函数段
  0x07, 0x07, 0x01, 0x03, 0x61, 0x64, 0x64, 0x00, 0x00, // 导出段 "add"
  0x0a, 0x09, 0x01, 0x07, 0x00, 0x20, 0x00, 0x20, 0x01, 0x6a, 0x0b, // 代码段
]);

WebAssembly.instantiate(bytes).then(({ instance }) => {
  const { add } = instance.exports;
  console.log(add(2, 3));
  console.log(add(-7, 100));
  console.log(typeof add);
});
```

```text
5
93
function
```

- 导出的函数直接按 JS 函数调用，参数与返回值自动在 JS number 与 wasm i32 之间转换。
- 整数溢出按 32 位回绕处理，调用方传入超范围数值会被截断，边界校验要留在 JS 侧。

> 上述输出逐行取自 node 实跑。这段字节数组共 44 字节，无任何依赖即可运行，是排查工具链问题的对照组：工具产物行为异常时，先用它能确认运行时本身没问题。



### 线性内存与数据交换

#### 导出 memory 与字节视图

**线性内存**：模块自带的连续可读写字节区，按 64 KiB 一页分配，导出后 JS 与 wasm 共享同一块 ArrayBuffer。

```js
// 导出线性内存的 wasm 模块（1 页 = 64 KiB）
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00, // 魔数与版本
  0x05, 0x03, 0x01, 0x00, 0x01, // 内存段：1 个内存，初始 1 页
  0x07, 0x07, 0x01, 0x03, 0x6d, 0x65, 0x6d, 0x02, 0x00, // 导出段 "mem"
]);

WebAssembly.instantiate(bytes).then(({ instance }) => {
  console.log(instance.exports.mem.buffer.byteLength);

  const view = new Uint8Array(instance.exports.mem.buffer);
  view[0] = 0x41;
  view[1] = 0x42;
  view.set([104, 105], 16);
  console.log(view[0], view[1], view[16], view[17]);
});
```

```text
65536
65 66 104 105
```

- 内存段（段号 5）声明初始页数与可选最大页数，0x05 0x03 0x01 0x00 0x01 表示一个内存、初始 1 页。
- JS 侧用 Uint8Array 按字节读写，用 DataView 按多字节整数读写，两侧看到的是同一块物理内存，零拷贝。
- 越界访问在 JS 侧按 TypedArray 规则静默忽略，在 wasm 指令侧则触发运行时错误，两侧行为不对称。

> [!IMPORTANT]
> **重要内容**：线性内存是 JS 与 wasm 交换复杂数据的唯一大通道——先把数据写进内存，再把偏移量与长度作为整数传给 wasm。理解了这个约定，就能读懂绝大多数 wasm 互操作接口的设计。



#### DataView 多字节读写实跑

**多字节整数交换**：DataView 以指定字节序读写 16、32、64 位整数与浮点数，是跨语言对齐数据布局的标准工具。

```js
// 同一块线性内存，用 DataView 按多字节整数读写
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00,
  0x05, 0x03, 0x01, 0x00, 0x01,
  0x07, 0x07, 0x01, 0x03, 0x6d, 0x65, 0x6d, 0x02, 0x00,
]);

WebAssembly.instantiate(bytes).then(({ instance }) => {
  const dataView = new DataView(instance.exports.mem.buffer);
  dataView.setUint32(32, 20260923, true); // 小端写入
  console.log(dataView.getUint32(32, true));
  console.log(dataView.getUint8(32), dataView.getUint8(35));
});
```

```text
20260923
59 1
```

- 第三参数 true 表示小端序，与多数平台的原生字节序一致；字节序不一致时同一个数会读成天差地别的值。
- 偏移 32 处的 4 字节，按 8 位读是 59 与 1，按 32 位读回是 20260923，说明布局约定比存储本身更重要。

> 上述输出取自 node 实跑。跨边界传结构体时，先在纸面固定每个字段的偏移与字节序，JS 与 wasm 两侧严格照写，任何一侧擅自改布局都会读出错误数据。



### 导入与导出

#### JS 函数导入进 wasm

**函数导入**：模块可声明依赖外部函数，实例化时由宿主经 importObject 提供，这是 wasm 获得一切宿主能力的唯一入口。

```js
// 把 JS 函数导入进 wasm：wasm 侧两次调用 env.double 实现 quadruple
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00, // 魔数与版本
  0x01, 0x06, 0x01, 0x60, 0x01, 0x7f, 0x01, 0x7f, // 类型段：(i32) -> i32
  0x02, 0x0e, 0x01, 0x03, 0x65, 0x6e, 0x76, 0x06, 0x64, 0x6f, 0x75, 0x62, 0x6c, 0x65, 0x00, 0x00, // 导入段：env.double
  0x03, 0x02, 0x01, 0x00, // 函数段
  0x07, 0x08, 0x01, 0x04, 0x71, 0x75, 0x61, 0x64, 0x00, 0x01, // 导出段 "quad"
  0x0a, 0x0a, 0x01, 0x08, 0x00, 0x20, 0x00, 0x10, 0x00, 0x10, 0x00, 0x0b, // 代码段
]);

const importObject = {
  env: {
    double: (x) => x * 2, // JS 侧提供的实现
  },
};

WebAssembly.instantiate(bytes, importObject).then(({ instance }) => {
  console.log(instance.exports.quad(3));
  console.log(instance.exports.quad(21));
  return WebAssembly.instantiate(bytes, {});
}).catch((err) => {
  console.log(err instanceof TypeError); // 缺少导入时实例化被拒绝
});
```

```text
12
84
true
```

- 导入段条目为模块名、成员名、种类与签名索引，实例化时 importObject 里必须有同名同签名的函数，缺了或类型不符即失败。
- 索引空间规则：导入项排在自有项之前，本例导入函数占 0 号，自有的 quad 因此是 1 号，导出段与调用指令都按这个序号引用。
- 代码段里的 0x10 0x00 是 call 指令调用 0 号导入函数，quad 即 double(double(x))。

> 上述输出取自 node 实跑。安全视角下 importObject 就是模块的能力清单：一个模块声明导入网络或文件类函数，等于明示它需要这些能力，审计时先读导入段。



#### global 导入导出

**WebAssembly.Global**：跨边界共享的带类型变量，JS 与 wasm 双向可读写，适合存放配置值与计数器这类小状态。

```js
// global 导入导出：从 JS 导入不可变 global，wasm 内自建可变 global 并双向互通
const bytes = new Uint8Array([
  0x00, 0x61, 0x73, 0x6d, 0x01, 0x00, 0x00, 0x00, // 魔数与版本
  // 类型段：两个类型，(i32) -> i32 与 () -> ()
  0x01, 0x09, 0x02, 0x60, 0x01, 0x7f, 0x01, 0x7f, 0x60, 0x00, 0x00,
  // 导入段：env.base，i32 不可变 global
  0x02, 0x0d, 0x01, 0x03, 0x65, 0x6e, 0x76, 0x04, 0x62, 0x61, 0x73, 0x65, 0x03, 0x7f, 0x00,
  // 函数段：两个函数分别用类型 0 与类型 1
  0x03, 0x03, 0x02, 0x00, 0x01,
  // 全局段：模块自建 i32 可变 global，初始值 100（有符号 LEB128 编码为 0xe4 0x00）
  0x06, 0x07, 0x01, 0x7f, 0x01, 0x41, 0xe4, 0x00, 0x0b,
  // 导出段：addBase、increment 两个函数与 counter 这个 global
  0x07, 0x21, 0x03,
  0x07, 0x61, 0x64, 0x64, 0x42, 0x61, 0x73, 0x65, 0x00, 0x00,
  0x09, 0x69, 0x6e, 0x63, 0x72, 0x65, 0x6d, 0x65, 0x6e, 0x74, 0x00, 0x01,
  0x07, 0x63, 0x6f, 0x75, 0x6e, 0x74, 0x65, 0x72, 0x03, 0x01,
  // 代码段：addBase 为参数加 base；increment 给 counter 加 1
  0x0a, 0x13, 0x02,
  0x07, 0x00, 0x20, 0x00, 0x23, 0x00, 0x6a, 0x0b,
  0x09, 0x00, 0x23, 0x01, 0x41, 0x01, 0x6a, 0x24, 0x01, 0x0b,
]);

const importObject = {
  env: {
    base: 1000, // JS 侧注入的不可变 global
  },
};

WebAssembly.instantiate(bytes, importObject).then(({ instance }) => {
  const { addBase, increment, counter } = instance.exports;
  console.log(addBase(5));
  console.log(counter.value);
  increment();
  increment();
  console.log(counter.value);
});
```

```text
1005
100
102
```

- 导入段末尾的 0x7f 0x00 表示 i32 不可变；全局段里的 0x01 表示可变，不可变 global 在 wasm 侧无法改写。
- JS 侧经导出对象的 value 属性读写 global，wasm 侧用 0x23 取值、0x24 存值。
- 立即数按 LEB128 有符号编码：100 需要两个字节 0xe4 0x00，单字节 0x64 会被解码成 -28，这是手写字节时极易踩中的静默错误。

> 上述输出取自 node 实跑，counter 的三次读数完整呈现了 wasm 侧自增、JS 侧可见的全过程。global 适合小状态同步，大块数据仍应走线性内存。



### 实战与安全视角

#### 编译工具链概况

**wat 与 wat2wasm**：wasm 有官方文本格式 wat，与二进制一一对应，wat2wasm 命令负责把 wat 汇编成二进制，是手写字节的工业化替代。

- wat 语法直观：S 表达式书写，(func (export "add") (param i32 i32) (result i32) ...) 一行就是上一节的 add 函数。
- 工具命令：wat2wasm add.wat -o add.wasm 产出二进制，wasm2wat 反向反汇编，wasm-objdump 带段级注释逐段转储。
- 生产工具链：C、C++、Rust 经 clang 或 rustc 输出 wasm，wasm-pack、Emscripten 负责打包与胶水代码生成。

```text
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

> 手写字节用于教学与排查，工程产出一律走工具链。拿到可疑 wasm 文件时，wasm2wat 反汇编是第一件该做的事。



#### 挖矿木马样本中的 wasm 特征

**wasm 挖矿**：浏览器端挖矿脚本把哈希运算编译成 wasm 内嵌或远程加载，用受害者 CPU 换取虚拟货币收益。

- 行为特征：CPU 占用异常飙高且集中在少数线程，风扇狂转，笔记本断电后功耗骤降是典型线索。
- 静态特征：脚本里出现 WebAssembly.instantiate 调用与大片高熵字节常量，或页面加载体积异常的 .wasm 文件。
- 历史脉络：CoalMine 类家族与使用 Coinhive 门罗币脚本的站点是最早一批公开样本，此后深层混淆与按域名开关成为常态。
- 载体形态：wasm 字节可内嵌成 JS 里的 base64 字符串再解码，也可由远程地址拉取，后者在 Network 面板留下明确请求记录。

> [!WARNING]
> **警告内容**：wasm 本身是中立技术，加密、游戏、音视频大量正当使用它，不能见 .wasm 就定性挖矿。定性依据是哈希运算循环加矿池通信的组合证据，单一线索只能立为疑点。



#### 页面加载 wasm 文件的排查点

**排查入口**：浏览器 DevTools 为 wasm 提供了完整的观察面，从网络加载到执行耗时可全程取证。

- Network 面板：按 .wasm 后缀过滤，记录加载来源域名、体积与时间，右键可保存原始字节留证。
- Sources 面板：Chromium 里 wasm 模块以 wasm-加序号的伪文件形式出现，可逐条查看反汇编指令。
- Performance 面板：火焰图里长任务帧会标出 wasm 函数名，持续满载的重计算一目了然。
- 代码检索：在页面脚本里全局搜 instantiate 与 WebAssembly 关键字，定位加载调用点与字节来源。
- 留证要点：对下载的 .wasm 计算哈希，反汇编导出 wat 文本一并归档，与已知家族样本库比对。

> [!TIP]
> **建议内容**：固定证据时先存网络原始字节再动 DevTools 的其他面板，避免刷新页面丢掉加载现场。来源域名、文件哈希、反汇编文本三件套齐备，才具备与样本库比对的起码条件。
