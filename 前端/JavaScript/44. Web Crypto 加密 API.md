## Web Crypto 加密 API

### 定位与全局对象

#### crypto 与 crypto.subtle

**Web Crypto API**：浏览器与 Node 都内置的加密能力接口，全局对象 crypto 下分两层——crypto 负责随机数，crypto.subtle 负责算法运算。

- crypto.getRandomValues(typedArray)：向传入的 TypedArray 填充密码学安全随机字节，同步返回同一对象。
- crypto.randomUUID()：生成 RFC 4122 版本 4 的随机 UUID 字符串。
- crypto.subtle 的所有方法都是异步的，返回 Promise，算法统一以字符串名传入。

> [!NOTE]
> **提醒内容**：subtle 有「只在安全环境可用」的限制——HTTPS 或 localhost 之外的页面访问 crypto.subtle 直接是 undefined。本地写脚本调试时若拿不到对象，先检查访问协议。



#### 两类随机数的选择

**密码学随机**：crypto.getRandomValues 从安全熵源取数；Math.random 是确定性伪随机，不可用于任何安全场景。

```js
const token = crypto.getRandomValues(new Uint8Array(4));
console.log("随机字节长度:", token.length);
console.log("UUID:", crypto.randomUUID().length);
```

```text
随机字节长度: 4
UUID: 36
```

> 会话令牌、口令重置链接、IV 一律走 getRandomValues；Math.random 只能用于演示与抽样。UUID 长度固定 36 个字符（含连字符），可直接当请求标识用。



### 摘要与编码

#### digest 计算哈希

**digest(algorithm, data)**：计算数据的哈希摘要，algorithm 支持 SHA-1、SHA-256、SHA-384、SHA-512。

```js
const data = new TextEncoder().encode("涉案文件内容");

const md = await crypto.subtle.digest("SHA-256", data);
const hex = [...new Uint8Array(md)].map((b) => b.toString(16).padStart(2, "0")).join("");
console.log("SHA-256:", hex.slice(0, 16) + "...");

const sha1 = await crypto.subtle.digest("SHA-1", data);
console.log("SHA-1 位数:", new Uint8Array(sha1).length * 8);
```

```text
SHA-256: 58a89864887fc32f...
SHA-1 位数: 160
```

- 输入必须是 BufferSource：字符串先过 TextEncoder 转 Uint8Array。
- 输出是 ArrayBuffer：常用展开写法转 Uint8Array，再转十六进制或 Base64 字符串。
- MD5 不在清单内，传入直接抛 NotSupportedError——前端算不了 MD5，涉及 MD5 校验的场景用服务端或第三方库。

> [!WARNING]
> **警告内容**：SHA-1 已被证实可构造碰撞，涉及证据完整性的哈希校验一律用 SHA-256 起步。文件比对取哈希时，哈希只能证明「两份内容相同」，不能证明「内容未被替换前属于谁」，同一文件不同人持有是常态。



#### 字节与字符串的互转

**编码转换**：Web Crypto 全程以字节为对象，与字符串、十六进制的互转是每个流程的第一步和最后一步。

```js
function bytesToHex(buffer) {
  return [...new Uint8Array(buffer)]
    .map((b) => b.toString(16).padStart(2, "0"))
    .join("");
}

function bytesToBase64(buffer) {
  const bytes = new Uint8Array(buffer);
  let binary = "";
  for (const b of bytes) binary += String.fromCharCode(b);
  return btoa(binary);
}

const encoded = new TextEncoder().encode("哈希输入");
console.log(bytesToHex(encoded).slice(0, 20));
```

> TextEncoder 与 TextDecoder 按 UTF-8 处理字符串与字节；btoa 与 atob 只接受二进制字符串（每字符一个字节），中文字符串直接进 btoa 会抛错，须先经 Uint8Array 中转。十六进制便于肉眼比对与日志记录，Base64 便于放进 JSON 与 URL。



### 对称加密

#### AES-GCM 加解密

**AES-GCM**：带认证的对称加密模式，一次调用同时完成加密与完整性保护，是 Web Crypto 里的默认推荐。

```js
const key = await crypto.subtle.generateKey(
  { name: "AES-GCM", length: 256 }, true, ["encrypt", "decrypt"]
);

const iv = crypto.getRandomValues(new Uint8Array(12));
const plain = new TextEncoder().encode("机密信息 AES 加密");

const cipher = await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, plain);
console.log("密文字节数:", cipher.byteLength);

const restored = await crypto.subtle.decrypt({ name: "AES-GCM", iv }, key, cipher);
console.log("解密:", new TextDecoder().decode(restored));
```

```text
密文字节数: 39
解密: 机密信息 AES 加密
```

- encrypt(algorithm, key, data) 的 algorithm 里带 iv：12 字节随机数，GCM 标准推荐长度。
- 密文比明文多出的部分是 GCM 的认证标签（16 字节），解密时包含在密文里传入。
- 密钥经 generateKey 生成，第二个参数 true 表示可导出，第三个参数限定密钥用途。



#### IV 与篡改检测

**IV 复用与篡改**：GCM 的安全性依赖 IV 不重复，认证标签让任何改动在解密时直接暴露。

```js
const badIv = crypto.getRandomValues(new Uint8Array(12));

try {
  await crypto.subtle.decrypt({ name: "AES-GCM", iv: badIv }, key, cipher);
} catch (e) {
  console.log("换 IV 解密抛错:", e.name);
}
```

```text
换 IV 解密抛错: OperationError
```

> 密文或 IV 被改动一个比特，解密都抛 OperationError，而不是解出错误内容——这就是认证加密的价值。IV 用密钥加密次数必须唯一：同一密钥下每次加密都换新 IV，把 IV 与密文一起存储传输即可，IV 本身不是秘密。



### 非对称签名

#### RSA-PSS 签名验签

**签名**：私钥对数据生成签名，任何持公钥者可验证数据出自私钥持有者且未被改动。

```js
const rsa = await crypto.subtle.generateKey(
  {
    name: "RSA-PSS",
    modulusLength: 2048,
    publicExponent: new Uint8Array([1, 0, 1]),
    hash: "SHA-256",
  },
  true,
  ["sign", "verify"]
);

const signature = await crypto.subtle.sign(
  { name: "RSA-PSS", saltLength: 32 }, rsa.privateKey, data
);

console.log("签名字节数:", signature.byteLength);
console.log("验签:", await crypto.subtle.verify(
  { name: "RSA-PSS", saltLength: 32 }, rsa.publicKey, signature, data
));

const tampered = new TextEncoder().encode("涉案文件内容2");
console.log("改文验签:", await crypto.subtle.verify(
  { name: "RSA-PSS", saltLength: 32 }, rsa.publicKey, signature, tampered
));
```

```text
签名字节数: 256
验签: true
改文验签: false
```

- generateKey 的第三个参数对 RSA 密钥对整体声明用途，sign 与 verify 都要写上。
- saltLength 通常取所用哈希的输出长度（SHA-256 对应 32）。
- 2048 位 RSA 签名固定 256 字节；原文改一个字符，验签立即变 false。

> 签名验证的是「这条数据是谁确认过的」，与加密保护的「内容不被第三方读走」是两件事。需要既有保密又有归属确认时，签名与加密分开做或选带签名的信封方案，不要想当然地以为加密自带防抵赖。



#### ECDSA 与 HMAC 的选型

**ECDSA**：椭圆曲线签名，同样安全强度下签名体积远小于 RSA；**HMAC**：对称的带密钥哈希，用于接口防篡改的通用方案。

```js
const ec = await crypto.subtle.generateKey(
  { name: "ECDSA", namedCurve: "P-256" }, true, ["sign", "verify"]
);

const msg = new TextEncoder().encode("电子笔录正文");

const sig = await crypto.subtle.sign(
  { name: "ECDSA", hash: "SHA-256" }, ec.privateKey, msg
);

console.log("P-256 签名字节数:", sig.byteLength, "（RSA 2048 为 256）");
console.log("验签:", await crypto.subtle.verify(
  { name: "ECDSA", hash: "SHA-256" }, ec.publicKey, sig, msg
));

const hmacKey = await crypto.subtle.generateKey(
  { name: "HMAC", hash: "SHA-256" }, true, ["sign", "verify"]
);

const mac = await crypto.subtle.sign("HMAC", hmacKey, msg);
console.log("HMAC 位数:", new Uint8Array(mac).length * 8);
```

```text
P-256 签名字节数: 64 （RSA 2048 为 256）
验签: true
HMAC 位数: 256
```

> 移动端与高并发场景优先 ECDSA（P-256），存储与带宽敏感时签名体积优势明显；接口防篡改双方共享密钥时用 HMAC，它比 RSA 签名快两个数量级，代价是密钥双方一致、无法抵赖到单一方。分析涉案接口的鉴权头时，HMAC 签名串与时间戳成对出现是最常见的形态。



#### 信封加密的组合实战

**信封加密**：用随机数据密钥加密大块数据，再用非对称公钥加密这个数据密钥，兼顾对称的速度与非对称的分发能力。

```js
const dataKey = await crypto.subtle.generateKey(
  { name: "AES-GCM", length: 256 }, true, ["encrypt", "decrypt"]
);

const rsa = await crypto.subtle.generateKey(
  {
    name: "RSA-OAEP",
    modulusLength: 2048,
    publicExponent: new Uint8Array([1, 0, 1]),
    hash: "SHA-256",
  },
  true,
  ["encrypt", "decrypt"]
);

const iv = crypto.getRandomValues(new Uint8Array(12));
const cipher = await crypto.subtle.encrypt(
  { name: "AES-GCM", iv }, dataKey, new TextEncoder().encode("整卷证据数据")
);

const wrappedKey = await crypto.subtle.encrypt(
  { name: "RSA-OAEP" }, rsa.publicKey,
  await crypto.subtle.exportKey("raw", dataKey)
);

console.log("密文字节数:", cipher.byteLength, "包裹密钥字节数:", wrappedKey.byteLength);

const rawKey = await crypto.subtle.decrypt(
  { name: "RSA-OAEP" }, rsa.privateKey, wrappedKey
);

const dataKey2 = await crypto.subtle.importKey(
  "raw", rawKey, { name: "AES-GCM" }, false, ["decrypt"]
);

const plain = await crypto.subtle.decrypt(
  { name: "AES-GCM", iv }, dataKey2, cipher
);

console.log("还原:", new TextDecoder().decode(plain));
```

```text
密文字节数: 34 包裹密钥字节数: 256
还原: 整卷证据数据
```

- 解开信封的顺序固定：先用 RSA 私钥解出数据密钥，再用数据密钥解密文。
- 换人共享时只需重加密一层密钥（256 字节级），不必重加密整块数据。
- 这就是「端到端加密」类产品的基本骨架：识别涉案系统的密文存储格式时，按「密文加包裹密钥并存的组合」去找信封结构。



### 密钥管理

#### exportKey 与 importKey

**exportKey(format, key)**：把密钥导出为指定格式；**importKey(format, keyData, algorithm, extractable, usages)**：把外部密钥材料导入。

```js
const raw = await crypto.subtle.exportKey("raw", key);
console.log("raw 导出字节数:", raw.byteLength);

const jwk = await crypto.subtle.exportKey("jwk", key);
console.log("jwk 算法族:", jwk.kty);
```

```text
raw 导出字节数: 32
jwk 算法族: oct
```

- 格式对照：对称密钥用 raw 与 jwk；RSA 公钥可用 spki、私钥用 pkcs8，两者也支持 jwk。
- 生成时 extractable 设 false 的密钥导出会直接抛错，页面关闭即消失，适合一次性会话密钥。
- 导出的密钥材料就是明文秘密，落日志、写 localStorage、拼进 URL 都是泄漏点。



#### PBKDF2 口令派生

**deriveKey**：从口令这类低熵输入派生出可用密钥，PBKDF2 通过加盐与多轮迭代抬高暴力破解成本。

```js
const baseKey = await crypto.subtle.importKey(
  "raw", new TextEncoder().encode("口令123"), "PBKDF2", false, ["deriveKey"]
);

const salt = crypto.getRandomValues(new Uint8Array(16));

const aesKey = await crypto.subtle.deriveKey(
  { name: "PBKDF2", salt, iterations: 100000, hash: "SHA-256" },
  baseKey,
  { name: "AES-GCM", length: 256 },
  false,
  ["encrypt"]
);

console.log("派生成功:", aesKey.type, aesKey.algorithm.name);
```

```text
派生成功: secret AES-GCM
```

- 口令直接当 AES 密钥是常见错误：先经 PBKDF2 派生，迭代次数取十万级起步。
- 盐必须每次随机生成并与密文一起保存；同口令不同盐派生出不同密钥，彩虹表失效。
- 派生目标密钥的 extractable 设 false，让密钥只在内存里活着。

> [!IMPORTANT]
> **重要内容**：纯前端加密的密钥与口令都在用户浏览器内存里，页面脚本（包括注入的恶意脚本）拿得到。前端加密适合「传输前加一层」与本地临时保护，真正的机密保护必须以服务端密钥管理为准，这一点在取证判断「数据到底谁能看到」时是关键依据。



### 常见陷阱

#### 算法名与参数拼错

**算法参数**：Web Crypto 的算法名区分大小写且参数结构逐算法不同，拼错在运行期才报错。

- AES-GCM 必须带 iv；RSA 系必须带 modulusLength、publicExponent 与 hash。
- usages 与算法不匹配（如拿只许 encrypt 的密钥去 decrypt）抛 InvalidAccessError。
- 算法名写小写或写别名（aes-gcm）不被识别，报 NotSupportedError 的第一反应先查拼写。



#### 忽略安全环境与兼容差异

**环境差异**：subtle 在非安全环境缺失；Node 与浏览器的算法支持清单不完全一致。

- 页面侧用前先判 crypto 与 crypto.subtle 是否存在，缺失时提示换 HTTPS 访问。
- Node 侧经 node:crypto 的 webcrypto 导出使用，API 形状一致，脚本可双端跑。
- 老浏览器对 RSA-OAEP、ECDSA 等的支持差异大，跨端需求先查目标环境的实现矩阵。

> [!CAUTION]
> **注意内容**：把浏览器示例原样搬进 Node 脚本时，全局 crypto 在较老版本 Node 不存在，报错点在 crypto 而不是算法本身。遇到 subtle undefined，先确认运行环境与协议，再排查算法拼写。
