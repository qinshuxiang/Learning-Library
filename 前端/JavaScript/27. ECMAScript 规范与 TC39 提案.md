## ECMAScript 规范与 TC39 提案

### TC39 与提案流程

#### TC39 的组织与会议

**TC39（Technical Committee 39）**：是 ECMA 国际下属的技术委员会，**负责制定和维护 ECMAScript 标准**（即 JavaScript 的语言规范）。

- 成员来自各大科技公司（浏览器厂商、框架作者等）。
- **定期开会**（约每两个月一次），讨论和推进提案。
- 共识驱动的决策机制。

> TC39 是 JavaScript 的"**立法机构**"：语言的所有新特性、语法变更，都要经过它的讨论与表决。理解 TC39，才能理解"为什么新特性要等很久""某个语法为何这样设计"。



#### 提案的五个阶段

TC39 的提案从提出到正式纳入标准，要经历**五个阶段（Stage 0 ~ 4）**。

- **Stage 0（Strawman，草案）**：想法刚提出，尚未正式进入流程。
- **Stage 1（Proposal，提议）**：正式提案，描述要解决的问题。
- **Stage 2（Draft，草稿）**：有初步规范草案，开始实验实现。
- **Stage 3（Candidate，候选）**：规范基本完成，等待浏览器实现与反馈。
- **Stage 4（Finished，完成）**：已实现并通过测试，纳入下一版标准。

> 提案阶段是判断"**一个特性是否可用**"的重要依据：**Stage 3 及以上**的特性基本稳定、可尝试使用；Stage 0~2 的特性还可能大幅变动甚至被废弃。关注提案阶段，能避免使用"半成品"特性。



#### 阶段晋升的硬条件

**阶段晋升条件**：每个阶段对提案材料有硬性要求，不满足就不能上会表决，避免提案停留在空想。

- Stage 1：指定一名** champion**（负责人），写清要解决的问题、解决方向与示例 API。
- Stage 2：提交**初版规范文本**，用规范语言写清语法与语义。
- Stage 3：规范文本定稿，须有**两名以上评审人签字**，并完成与 HTML 标准的集成审阅。
- Stage 4：**test262** 官方测试套件覆盖通过，**至少两个独立实现**（通常是两个浏览器引擎）落地，规范文本合入 ECMA-262 主文档。

> [!IMPORTANT]
> **重要内容**：两个独立实现是 Stage 4 的核心门槛，它保证特性不依赖单一引擎的特殊行为。看到某特性「进标准了」，等价于看到两大引擎都已稳定支持，日常生产环境可以放心跟随 Stage 4 清单，不必追 Stage 3 的实验实现。



#### 从提案到年度版本

从提案到正式发布，是一条清晰的时间线。

- 每年 6 月左右，TC39 会发布**年度版本**（如 ES2024、ES2025）。
- 达到 **Stage 4** 的提案，会被纳入**当年的标准版本**。
- 版本命名从 ES2015 起改为**年份命名**。

```js
// ES2015（ES6）→ ES2016 → ... → ES2026
// 每年一个小版本，增量添加特性
```

> 现代 ECMAScript 采用"**年度小版本**"策略：不再像 ES5 到 ES6 那样憋几年发一个大版本，而是**每年发布**、增量更新。这降低了学习门槛，也加快了特性落地速度。



#### 提案的跟踪与查询

**提案跟踪**：TC39 的工作全部公开在 GitHub 上，任何特性的现状都能查到一手信息。

- 总入口：tc39/proposals 仓库，按阶段分类列出全部活跃提案，Stage 4 汇总进当年版本清单。
- 单个提案：每个提案有独立仓库，README 记录动机、语法示例、阶段变更时间线。
- 会议纪要：tc39/notes 仓库存全部会议记录，重大分歧与否决原因都能溯源。

> 查一个特性「为什么被砍」「API 为什么改了」时，直接搜提案仓库的 README 与会议纪要，比二手文章可靠得多。执法调查中判断某语法出现的时间点（能否在当时环境存在），提案时间线也是一手依据。



### 阅读 ECMA-262 规范

#### 规范文档的结构

**ECMA-262**：是 ECMAScript 的**官方规范文档**，定义了语言的**精确行为**。

- 文档包含**语法**、**类型**、**抽象操作**、**内置对象**等章节。
- 用**精确的算法语言**描述每个特性的行为。

```js
// 规范用"抽象操作"描述行为，如：
// ToNumber、ToPrimitive、OrdinaryCallEvaluateBody 等
```

> 规范是语言的"**最高权威**"：所有实现（V8、SpiderMonkey）都须遵循它。规范写得**极其精确**（甚至定义每个边界情况），是解决"这个行为到底该怎样"的最终依据。



#### 抽象操作与内部方法

**抽象操作（Abstract Operation）**：是规范中定义的**内部算法**，用名字描述操作步骤，实际引擎可自由实现。

常见的抽象操作：

- **ToNumber**：转为数字。
- **ToString**：转为字符串。
- **ToPrimitive**：转为原始值。
- **ToBoolean**：转为布尔。

```js
// 规范层面：Number("123") 内部调用 ToNumber
// 隐式转换（如 "3" - 1）内部也调用 ToNumber
```

> 抽象操作是理解**类型转换、比较运算**等"隐式行为"的钥匙。如 == 的宽松相等，本质是规范定义的一系列 ToNumber/ToPrimitive 抽象操作的组合。看懂抽象操作，就能精确预测任何"诡异"行为。



#### 内部槽与 Record

**内部槽（Internal Slot）** 与 **Record**：是规范用来描述**对象内部状态**的机制。

- **内部槽**：对象内部的**隐藏状态**，用 [[Name]] 表示（如 [[Prototype]]）。
- **Record**：规范中用花括号描述的数据结构。

```js
// 内部槽示例（规范写法，非 JS 代码）
// 每个对象都有 [[Prototype]] 内部槽
// 数组有 [[ArrayLength]] 内部槽
```

> 内部槽解释了"**为什么有些行为无法用普通 JS 代码实现**"：如数组的 length 自动更新，背后是 [[ArrayLength]] 等内部槽在起作用。理解内部槽，有助于理解对象、数组的底层行为。



#### Completion Record

**Completion Record**：是规范描述**语句执行结果**的统一数据结构，记录"执行是正常完成、还是抛错、还是 return/break"等。

- 有类型字段：normal、return、throw、break、continue。
- 有值字段：执行产生的值。

```js
// 每条语句执行都会产生一个 Completion Record
// 如 return 语句产生 { type: "return", value: 42 }
// throw 产生 { type: "throw", value: error }
```

> Completion Record 解释了**控制流的底层机制**：return、throw、break 都是通过"**产生特定类型的 Completion Record**"来改变执行流的。理解它，能深入理解异常、循环控制等机制。



#### 规范算法的记号读法

**算法记号**：ECMA-262 的算法用结构化伪码书写，有几个高频记号，认出它们才能顺畅读规范。

- 步骤句式：Let x be ...（令 x 为）、Assert:（断言成立）、Return ...（返回）、Repeat（循环）。
- 问号记号 **?**：调用抽象操作时若产生 abrupt completion 就原样向上抛，等价于自动透传异常。
- 叹号记号 **!**：断言该调用绝不可能抛出，属于算法作者的保证而非运行时检查。

```text
// 规范写法示例（伪码，非 JS）：
// 1. Let result be ? ToPrimitive(value).
// 2. Assert: result is not a Completion Record.
// 3. Return ! ToString(result).
```

> 问号与叹号是读规范时最容易懵的两个符号：问号等于「失败就抛」，叹号等于「这里不可能失败」。把它们当 JS 里的 throw 透传与断言理解，算法步骤的阅读障碍就去掉大半。



#### Annex B 与遗留行为

**Annex B**：ECMA-262 的附录 B，收录仅为 Web 兼容而保留的**遗留语法与行为**，不属于语言核心。

- 浏览器专属：HTML 式注释、字符串转义里的八进制、函数声明在块级作用域里的 Web 语义。
- 宽松模式专属：八进制字面量、with 语句、arguments 与形参的映射等，严格模式一律禁用。
- 新引擎不强制实现：非浏览器宿主（嵌入式、老 Node 场景）可以不带 Annex B。

> 看到规范里「仅在 Annex B 中定义」「仅浏览器适用」的表述，就当作「为兼容老网页而留的暗门」。写新代码时不依赖 Annex B 行为，依赖了就意味着代码只能在浏览器里按老规则运行。



### 已落地与值得关注的提案

#### Temporal 现代日期时间

**Temporal**：是**下一代日期时间 API**，旨在替代问题重重的 Date。

- Date 的问题：时区处理混乱、不可变缺失、API 不一致。
- Temporal 提供：**不可变**的日期时间对象、清晰的时区/无时区区分、丰富的运算。

```js
// Temporal 的典型用法（已纳入 ES2026）
const now = Temporal.Now.plainDateTimeISO();
const later = now.add({ days: 7 });
console.log(later.toString());
```

> Temporal 已于 **2026 年 3 月达到 Stage 4、纳入 ES2026**，是未来日期时间处理的标准方向。它区分「**墙上时钟时间**」（PlainDateTime）与「**绝对时间**」（ZonedDateTime/Instant），并支持时区换算与安全的日期运算。



#### 装饰器 Decorator

**装饰器（Decorator）**：是一种**元编程**语法，用于**增强/修改类及其成员**（提案中）。

- 用 @decorator 语法标注类、方法、属性。
- 用于日志、校验、依赖注入等**横切关注点**。

```js
// 装饰器提案的目标用法（API 可能变动）
// function logged(target, context) { ... }
// @logged
// class Example { ... }
```

> 装饰器是 TypeScript 早已支持、Angular/NestJS 大量使用的特性。原生 JS 的装饰器提案几经反复，目前处于 **Stage 2.7**（尚未到 Stage 3，仍可能变动）。它适合"**给类/方法统一附加能力**"的场景，是值得关注的元编程方向。新项目建议先使用 TypeScript 的标准装饰器（已稳定），原生装饰器需等 Stage 3 后再评估。



#### using 声明与资源管理

**using 声明**：是**显式资源管理**的语法，用于自动释放资源（如文件句柄、锁）。

- 类似 C# 的 using、Python 的 with。
- 声明用 using 的变量，在**作用域结束时自动调用 Symbol.dispose**。

```js
// using 已纳入 ES2026
{
  using file = openFile("data.txt");
  // 作用域结束时，自动调用 file[Symbol.dispose]() 关闭文件
}
```

> using 解决"**资源忘释放导致泄漏**"的问题：在作用域退出时**自动**调用清理逻辑（Symbol.dispose），无需手动 close/release。它是资源管理（文件、连接、锁）的优雅方案。
>
> **同步与异步**：同步资源用 using（调用 Symbol.dispose）；异步资源用 await using（调用 Symbol.asyncDispose），适合需异步清理的数据库连接、网络连接等。



#### 特性的可用性判断与检测

**特性检测**：运行环境是否支持某特性，用代码在运行期探测，而不是按浏览器型号硬编码判断。

```js
function hasTemporal() {
  return typeof Temporal !== "undefined";
}

console.log(hasTemporal());       // 当前 node 22 环境
console.log(typeof Array.prototype.group); // 尚未落地的方法
console.log("abc".at(1));         // 已落地的 ES2022 方法
```


> **建议内容**：新特性上生产前先做特性检测并准备降级路径，typeof 探测全局、探测原型方法是否存在、try-catch 包裹语法特性都是标准做法。构建期再用 browserslist 类工具收窄目标环境，两侧配合，比「按 UA 猜版本」可靠得多。
