## JS 安全专题

### 客户端攻击面总览

#### JS 代码的位置决定风险

**客户端安全**：浏览器里运行的 JS 拥有页面内几乎全部权限，能读 DOM、发请求、碰存储，攻击者只要能让自己的代码混进这段执行流，就能做这些事。

> [!NOTE]
> **提醒内容**：网安执法视角下，前端漏洞是 Web 案件现场最常见的痕迹来源。XSS 脚本、被污染的原型、被篡改的第三方脚本，最终都落到「谁的 JS 在跑、谁授权它跑」这个问题上。



#### 三类高频客户端攻击

**XSS（跨站脚本）**：把恶意脚本注入页面让受害者浏览器执行。**原型链污染**：借对象合并等路径改写共享原型，劫持全部对象的默认行为。**供应链投毒**：第三方依赖或脚本被植入恶意代码，随构建与加载进入页面。



### 原型链污染

#### 污染原理与演示

**原型链污染**：攻击者借 JSON 输入里的 __proto__ 键，把属性写进 Object.prototype，让所有对象共享恶意属性。

```js
// 不安全的深合并：递归拷贝时未过滤特殊键
function merge(dst, src) {
  for (const k in src) {
    if (typeof src[k] === "object" && src[k] !== null) {
      if (!dst[k]) dst[k] = {};
      merge(dst[k], src[k]);
    } else {
      dst[k] = src[k];
    }
  }
  return dst;
}

const payload = JSON.parse('{"__proto__":{"isAdmin":true}}');

merge({}, payload);
console.log("污染演示:", ({}).isAdmin);
delete Object.prototype.isAdmin; // 演示完恢复，避免影响后续示例
```

```text
污染演示: true
```

> JSON.parse 把 __proto__ 当普通键解析成自有属性，但递归合并时 dst[k] = {} 建出普通对象，下一层对 __proto__ 的赋值就触发了原型改写。污染生效后任何新建对象都能读到 isAdmin，权限判断、模板渲染、命令拼接的默认值都可能被改。



#### 防护写法

**键过滤**：合并与拷贝前拦截 __proto__、constructor、prototype 三个危险键。

```js
function safeMerge(dst, src) {
  for (const k in src) {
    if (k === "__proto__" || k === "constructor" || k === "prototype") continue;
    if (typeof src[k] === "object" && src[k] !== null) {
      if (!dst[k]) dst[k] = {};
      safeMerge(dst[k], src[k]);
    } else {
      dst[k] = src[k];
    }
  }
  return dst;
}

const payload = JSON.parse('{"__proto__":{"isAdmin":true}}');

safeMerge({}, payload);
console.log("防护演示:", ({}).isAdmin);
```

```text
防护演示: undefined
```

> [!IMPORTANT]
> **重要内容**：凡是接收外部 JSON 做深合并、深克隆、配置覆盖的代码路径都是污染入口，第三方工具库的 merge 类函数历史上多次爆出此类漏洞，升级依赖与自查过滤两者都要做。



#### 无原型对象与 Map

**Object.create(null)**：创建没有原型的对象，从根上杜绝 __proto__ 链；**Map**：键值集合不受原型链影响，任意字符串键都安全。

```js
const clean = Object.create(null);
console.log(Object.getPrototypeOf(clean));

const mp = new Map();
mp.set("__proto__", "data");
mp.set("toString", "data2");
console.log(mp.get("__proto__"), mp.get("toString"), mp.size);
```

```text
null
data data2 2
```

> 键来自用户输入的场景优先用 Map 而不是普通对象做字典：普通对象上 set 与 get 语义会被原型链同名属性干扰，Map 完全按自有键存取。无原型对象连 toString 都没有，混入字符串拼接会报错，需注意使用场景。



### XSS 的 JS 视角

#### 危险的执行与注入 API

**危险 sink**：把字符串当代码或 HTML 执行的 API，是 XSS 的落点。

- eval 与 new Function：字符串直接当代码执行，权限与页面脚本等同。
- setTimeout 与 setInterval 的字符串首参：等价于隐式 eval。
- innerHTML 与 outerHTML 赋值：字符串按 HTML 解析，脚本与事件属性随之中招。
- document.write：直接向文档流写 HTML，同样不经过任何过滤。

```js
const calc = new Function("a", "return a * 2");
console.log(calc(3));

try {
  eval("notDefined++");
} catch (e) {
  console.log(e instanceof ReferenceError);
}
```

```text
6
true
```

> 运行期拼字符串进这些 API，等于把输入方提权为页面作者。数值运算、对象查表、模板引擎等替代写法都能覆盖 eval 的正当用途，代码评审里见到字符串版定时器与 eval 直接按缺陷处理。



#### 输出编码与安全赋值

**输出编码**：数据进 HTML 前把五个敏感字符转成实体，解除其语法身份。

```js
const raw = "<img src=x onerror=alert(1)>";
const escaped = raw.replace(/[&<>"']/g, (c) => (
  { "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" }[c]
));

console.log(escaped);
```

```text
&lt;img src=x onerror=alert(1)&gt;
```

> [!TIP]
> **建议内容**：纯文本落 DOM 用 textContent 赋值，天然免编码；确需富文本时用成熟的净化库过滤后再入 innerHTML。自写正则净化 HTML 是反模式，绕过手法远比过滤规则多。



#### 数字类输入的收口

**类型收口**：数字类输入先转数值再使用，拼接语句自动失去语法意义。

```js
const input = "1; alert(1)";

console.log(Number.isFinite(Number(input)), parseInt(input, 10));
```

```text
false 1
```

> Number 全串转换对混入代码的输入返回 NaN，可作为合法性闸门；parseInt 截取前缀数字适用于宽松场景，但两侧语义不同，按需选择。凡进 SQL、命令、模板的值同理，先收口类型再进语句。



### CSP 与 SRI

#### 内容安全策略

**CSP（内容安全策略）**：服务端或 meta 标签下发的白名单策略，浏览器按策略拦截违规脚本与请求。

```html
<!-- 仅允许加载同源脚本，禁止内联脚本与 eval -->
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; object-src 'none'">
```

> CSP 是 XSS 的纵深防线：即使注入成功，脚本不在白名单来源就执行不了。script-src 里避免出现 unsafe-inline 与 unsafe-eval，二者等于给策略开洞。响应头下发优于 meta 标签，因为 meta 方式下 report 能力受限。



#### 子资源完整性

**SRI（子资源完整性）**：给外部脚本与样式带 integrity 属性，浏览器校验哈希不匹配即拒绝执行。

```html
<script src="https://cdn.example.com/lib.min.js"
        integrity="sha384-_base64哈希值_"
        crossorigin="anonymous"></script>
```

> SRI 防的是 CDN 或中间链路被投毒后脚本身份被顶替的场景，执法办案中对应「页面引用了境外被篡改的库文件」一类线索。库升级时哈希必须同步换，否则合法新版也会被拦。



### 依赖与供应链

#### 依赖投毒与锁定

**供应链风险**：npm 包被抢注、被维护者出卖或版本被篡改，恶意代码随 install 与 build 进入产物。

- 锁文件：package-lock.json 提交进仓库，CI 安装一律用 npm ci 而不是 npm install，保证依赖树与锁定哈希逐位一致。
- 版本收紧：第三方包不用大范围的版本通配，升级走显式变更与审查。
- 来源核查：引入新包前查维护者、下载量、仓库与发布历史，警惕名称与热门包近似的仿冒包。

> [!WARNING]
> **警告内容**：构建产物里出现的恶意第三方代码会随页面分发给全部访问者，影响面远大于单个接口漏洞。生产构建必须锁定依赖哈希，任何绕过锁文件直接安装的流水线配置都应视为安全缺陷。



#### 依赖审计的实操

**npm audit**：npm 自带的漏洞审计命令，对照公开漏洞库逐条报告依赖里的已知问题与修复建议。

```bash
npm install lodash@4.17.15 --no-audit
npm audit
```

#### 敏感信息不进前端

**前端即公开**：浏览器拿到的 JS 与数据用户全部可见，混淆与压缩只是可读性处理，不是加密。

- 密钥、内部接口地址、调试后门不写入前端代码与环境变量。
- 鉴权与校验逻辑放服务端，前端校验只做体验优化。
- 排查页面时优先看 Network 与 Sources 面板里实际下发的数据，与代码注释里声称的权限对照。

> 混淆与压缩不是加密：变量名替换与代码压缩可逆，断点跟一遍就能还原控制流，攻击者拿到的永远是等价明文逻辑，混淆只增加阅读成本。安全设计必须假设前端代码完全公开，机密逻辑与凭据只存在于服务端。



### 常见陷阱

#### 只防注入不防泄漏

**信息泄漏面**：报错堆栈、接口响应、localStorage 与全局变量都会把敏感数据摆在页面上。

- 生产环境关掉详细报错回显，异常统一收口为通用提示。
- 登录态与权限信息不落 localStorage，改用 HttpOnly Cookie 由服务端管控。
- 全局 window 上挂载的调试对象与临时数据在发布前清理。

> [!CAUTION]
> **注意内容**：取证与渗透测试场景里，前端泄漏点往往在开发者工具里一翻即见，攻击者同样看得到。上线前的安全清单里，存储、全局变量、报错回显三项必须逐页核对。



#### 弹窗与引用方的安全属性

**window.opener**：经 target 为 _blank 的链接或 window.open 打开的新页面，默认持有对原页面的引用，可改写原页面地址。

```html
<a href="https://other.example.com" target="_blank" rel="noopener noreferrer">外部链接</a>
```

> 新页面执行 window.opener.location = 钓鱼地址 即可把原页面偷偷换掉（反向标签劫持）。加 rel 为 noopener noreferrer 后新页面拿不到 opener 引用，window.open 的返回值等于 null 时同理。跳转目标不受自己控制时，这个属性必加。

> 链接、iframe、弹窗三类跳转出口是钓鱼案件里最常见的引流入口，执法取证时优先检查页面里带 target 属性的跳转代码与注入的可疑 a 标签。
