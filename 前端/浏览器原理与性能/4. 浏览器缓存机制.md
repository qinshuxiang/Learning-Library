## 浏览器缓存机制

本篇讨论浏览器在本地保存了什么、依据什么判定副本能否直接使用、用户操作又如何改变判定结果。缓存头的服务端配置（例如 Nginx 的过期指令与后端响应头下发）属 后端/Nginx 领域，本篇只讲浏览器侧的判定规则与命中结果。

### 缓存的层次与位置

**缓存的层次与位置** 决定了副本保存在哪里、能存活多久、由谁决定它的去留。这一节先列清层次，再看命中顺序与缓存键。

#### 缓存的层次结构

**浏览器缓存**：是浏览器把已获取的响应副本保存在本地、在后续请求中直接复用或先做验证的机制。

- 内存缓存：副本存活于当前进程的内存中，生命周期最短，多用于同一页面内立刻重复使用的资源。
- 磁盘缓存：副本落在磁盘上，可以跨页面、跨会话复用，读取速度低于内存但容量更大。
- 脚本缓存：由 Cache Storage 接口管理的独立存储区，条目由脚本显式写入与读取。
- 应用层存储：localStorage 与 IndexedDB 保存的是数据而不是响应，能否复用完全由代码决定。
- 容量约束：内存缓存容量最小，磁盘缓存与脚本缓存的可用容量受存储配额约束（详见本主题第 12 篇 浏览器存储机制）。
- 存活边界：内存缓存随标签页关闭而消失，磁盘缓存可以跨会话保留。
- 选择依据：需要跨页面复用时依赖磁盘缓存，只在当前页面内重复使用则内存缓存已足够。

```text
内存缓存        当前进程内存，生命周期最短
磁盘缓存        落盘保存，可跨会话复用
Cache Storage   由脚本管理的独立响应存储区
应用层存储      保存数据而非响应，复用逻辑由代码决定
```

> 内存缓存与磁盘缓存属于浏览器实现内部的划分，各浏览器的命名、容量与淘汰策略并不一致，不作跨浏览器保证。

**速记**：缓存分布在内存、磁盘与脚本管理的存储区，生命周期依次变长。



#### 缓存位置与命中顺序

**命中顺序**：是浏览器收到请求后依次查找可用副本的顺序，先找到的层优先返回。

- 查找顺序：通常先查内存缓存，再查脚本管理的缓存存储，最后查磁盘缓存。
- 全部未命中：此时发起网络请求，并按响应首部的策略把结果写入相应缓存。
- 层间约束：脚本管理的缓存需要脚本在拦截逻辑中显式读取，不参与 HTTP 缓存的自动判定。
- 可观测性：开发者工具的网络面板用 from memory cache、from disk cache 标记条目来源。
- 顺序并非规范：具体查找顺序属于实现细节，各浏览器之间存在差异。
- 请求类型影响：文档导航与子资源的查找路径不同，文档更倾向于先确认能否复用。
- 观测价值：区分条目来源有助于判断本次请求是缓存命中还是验证后复用。

```js
// 用 transferSize 判断响应是否来自本地（0 表示没有发生网络传输）
performance.getEntriesByType("resource").slice(0, 5).forEach((entry) => {
  console.log(entry.name, entry.transferSize); // 0 通常意味着未走网络传输
});
```

> [!NOTE]
> **提醒内容**：transferSize 为 0 只说明没有发生网络传输，命中的可能是缓存，也可能是复用了验证后的 304 响应，需要结合状态码判断。

**速记**：先内存、再脚本缓存、后磁盘，全部未命中才走网络。



#### 缓存键与缓存分区

**缓存键（cache key）**：是浏览器查找缓存条目时使用的标识，由请求方法与 URL 共同构成。**缓存分区（cache partitioning）**：是现代浏览器按顶层站点与资源所在的源对缓存条目分组，避免跨站点推断用户数据。

- 键的组成：请求方法与 URL 决定条目归属，方法不同即视为不同条目。
- 分区作用：同一资源在不同顶层站点下保存为不同条目，条目之间不能互相命中。
- 变体处理：响应声明按首部做变体时，浏览器按该首部的取值区分条目。
- 实际影响：分区削弱了跨站点复用第三方资源的能力，第三方资源的缓存命中率随之下降。
- 两步定位：先按方法与 URL 找到条目候选，再按站点分区确定具体分组。
- 首部影响：除变体声明之外，其余请求首部默认不参与缓存键的构成。
- 排查提示：同一 URL 在不同页面下命中情况不同时，先考虑分区带来的影响。
- 实践建议：公共静态资源集中在少量固定的源上，可以减少条目被重复保存。

```http
HTTP/1.1 200 OK
Content-Type: text/css
Vary: Accept-Encoding
Cache-Control: max-age=3600
```

> 分区带来的结果是同一份公共资源可能被多次保存，静态资源放置在哪个源上比过去更值得权衡。

**速记**：缓存键由方法与 URL 构成，现代浏览器再按站点分区，跨站点不再共享条目。



### 强缓存与 Cache-Control

强缓存解决的是「副本能不能直接用」，这一能力完全由响应首部控制。

#### 强缓存的判定过程

**强缓存**：是副本仍处于有效期内时，浏览器直接使用本地副本、不向服务端发送请求的命中方式。**新鲜度（freshness）**：是副本被视为可用的时间区间，由响应首部计算得出。

- 判定输入：响应首部中的新鲜度信息，以及副本到达本地的时间。
- 判定结果：仍在有效期内时直接返回本地副本，不产生网络请求。
- 过期之后：进入验证阶段，先发请求确认副本是否仍然可用。
- 不可缓存：声明为不存储的响应不会进入缓存，每次都需要重新请求。
- 起算时刻：新鲜期从响应到达浏览器时起算，而不是服务端生成响应的时刻。
- 与验证的关系：强缓存命中不产生任何请求，协商缓存必然产生一次请求。
- 结果差异：命中表现为来源为缓存，验证命中表现为状态码 304。
- 常见误判：网络面板出现 304 属于协商缓存命中，不是强缓存命中。

```http
HTTP/1.1 200 OK
Content-Type: text/css
Cache-Control: max-age=31536000
```

> 强缓存的判定只使用本地信息，命中时开发者工具不会显示服务器响应，只标记条目来源为缓存。

**速记**：副本仍在新鲜期内就直接使用，不发请求。



#### Cache-Control 的常用指令

**Cache-Control**：是响应首部中控制缓存行为的字段，由逗号分隔的多条指令组成，可以同时出现。**max-age**：是用秒表示副本新鲜期长度的指令。

- max-age：副本自到达本地起算，超过该秒数即视为过期。
- no-store：不保存任何副本，响应不得写入任何缓存。
- no-cache：允许保存副本，但每次使用之前必须向服务端验证。
- private 与 public：区分只允许浏览器私有缓存保存，还是共享缓存也可以保存。
- must-revalidate：副本一旦过期，必须先验证才能使用，不允许在离线等情况下直接复用。
- 组合使用：多条指令并列时按各自语义共同生效，相互冲突时以更严格的限制为准。
- 请求侧用法：max-age 也可以出现在请求首部，表示本次请求可接受的最大副本年龄。
- 共享缓存：与浏览器私有缓存相对的是共享缓存，由代理与网关维护，其配置属服务端领域。
- 离线相关：声明 no-store 的响应在离线时无法从缓存取到，只能依赖脚本管理的存储。

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=3600, must-revalidate
Content-Type: application/javascript
```

```http
HTTP/1.1 200 OK
Cache-Control: no-store
Content-Type: application/json
```

> [!IMPORTANT]
> **重要内容**：no-cache 的名字容易被误解，它并不禁止缓存，而是要求每次使用之前必须验证；真正禁止保存的指令是 no-store。

**速记**：max-age 定期限，no-store 禁止保存，no-cache 允许保存但必须验证。



#### Expires 与 max-age 的优先级

**Expires**：是早于 Cache-Control 出现的响应首部，用绝对时间表示副本的过期时刻，取值来自服务端时钟。**优先级规则**：两者同时出现时，以 max-age 为准，Expires 被忽略。

- 绝对时间：Expires 是一个具体时刻，要求服务端与浏览器两端的时钟一致。
- 相对时间：max-age 从响应到达时起算，不受两端时钟偏差影响。
- 同时下发：此时以 max-age 为准，Expires 不参与判定。
- 取舍：不要同时下发两者，以免排查缓存问题时产生歧义。
- 判定顺序：先看 Cache-Control 是否带有 max-age，有则直接使用该值。
- 缺失回退：响应没有提供 max-age 时才回退到 Expires 的绝对时刻。
- 存量影响：早期服务端只能通过 Expires 表达过期时间，因此该字段仍需兼容。
- 排查建议：两个字段取值互相矛盾时，先按 max-age 推导实际新鲜期。

```http
HTTP/1.1 200 OK
Expires: Wed, 21 Oct 2026 07:28:00 GMT
Cache-Control: max-age=3600
```

> 上例的实际新鲜期是一小时，从响应到达浏览器的那一刻起算，Expires 指向的绝对时刻不参与判定。

**速记**：max-age 与 Expires 同时出现时以 max-age 为准，后者是历史兼容字段。



### 协商缓存与验证器

协商缓存解决的是「副本还能不能接着用」，判定发生在服务端，浏览器负责带上验证信息。

#### Last-Modified 与 If-Modified-Since

**Last-Modified**：是响应首部中标注资源最后修改时刻的字段。**If-Modified-Since**：是浏览器在副本过期后发起请求时携带的请求首部，取值来自此前收到的 Last-Modified。

- 流程：副本过期后浏览器带上 If-Modified-Since 请求，服务端比较资源的修改时间。
- 未改动：返回 304 状态码且不带正文，浏览器继续使用本地副本。
- 已改动：返回 200 状态码与新内容，本地条目被替换。
- 精度限制：字段取值精确到秒，同一秒内的多次修改可能无法区分。
- 请求前提：只有本地存在条目且条目已过期时，浏览器才会发出带条件的请求。
- 与强缓存的关系：副本仍然新鲜时不会走到验证这一步。
- 状态码记忆：304 表示可以继续使用本地副本，且该响应不带正文。
- 排查提示：请求首部缺少 If-Modified-Since，说明本地没有可用副本或副本缺少验证器。

```http
GET /app.css HTTP/1.1
Host: example.com
If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT
```

```http
HTTP/1.1 304 Not Modified
Cache-Control: max-age=3600
```

> 除精度限制外还存在「内容改回原样」的情形：修改时间变了但内容一致，仍会触发一次完整传输。

**速记**：Last-Modified 配 If-Modified-Since，未改动返回 304 且没有正文。



#### ETag 与 If-None-Match

**ETag**：是响应首部中表示资源内容版本的标识字段，取值由服务端生成。**If-None-Match**：是浏览器携带此前收到的 ETag 发出的请求首部。

- 流程：副本过期后浏览器带上 If-None-Match 请求，服务端比较资源的内容标识。
- 命中：标识一致时返回 304，浏览器复用本地副本。
- 未命中：标识不一致时返回 200 与新内容，本地条目被替换。
- 强弱之分：带弱验证器前缀的 ETag 表示语义等价而非字节完全一致，两类取值不可混用比较。
- 请求前提：与时间类验证相同，仅当副本过期后才带条件请求。
- 与时间类并用：两类验证器同时存在时，条件请求可以同时携带两类信息。
- 服务端生成：取值由服务端决定，浏览器不做解析，只做原样回传。
- 弱验证器用途：语义等价即可视为命中，适合压缩或编码等不改变语义的处理。

```http
GET /app.css HTTP/1.1
Host: example.com
If-None-Match: "33a64df5"
```

```http
HTTP/1.1 304 Not Modified
ETag: "33a64df5"
```

> ETag 与 Last-Modified 可以同时下发，验证时浏览器会把两类信息一并带上，由服务端决定采用哪一个。

**速记**：ETag 配 If-None-Match，标识一致返回 304，内容标识比时间更精确。



#### 两类验证器的取舍

**验证器（validator）**：是用于判断本地副本是否仍然有效的元数据，分为以修改时间为依据与以内容标识为依据两类。

- 时间类：实现成本低，精度到秒，无法判断内容是否真的发生变化。
- 标识类：由服务端计算内容标识，精度更高，但需要额外的计算或存储开销。
- 常见组合：两者同时下发，服务端按自身能力选择比较依据。
- 排查要点：验证失败时先确认响应是否真的带有验证器，缺少验证器的响应只能整体重新下载。
- 比较优先级：响应同时提供两类验证器时，服务端通常优先比较内容标识。
- 精度差异：时间类在同一秒内的连续修改无法区分，标识类可以区分。
- 成本差异：标识类需要服务端计算或存储内容标识，时间类直接读取文件时间。
- 结果一致：无论采用哪一类，命中都表现为 304 并复用本地副本。

```js
// 304 响应没有正文，用 transferSize 与 encodedBodySize 组合识别复用
performance.getEntriesByType("resource").forEach((entry) => {
  const reused = entry.transferSize === 0 && entry.encodedBodySize > 0;
  console.log(entry.name, reused ? "验证后复用本地副本" : "读取了网络内容");
});
```

> [!TIP]
> **建议内容**：排查缓存问题时先确认响应是否带有 ETag 与 Last-Modified，两者齐备时浏览器可以在副本过期后走 304 复用，而不是整体重新下载。

**速记**：时间类实现简单但精度低，标识类更精确但成本更高，两者常配合使用。



### 浏览器缓存策略与用户操作

同一份缓存，用户用不同方式打开页面会得到不同结果。这一节把用户操作与请求首部对应起来。

#### 刷新行为对缓存的影响

**刷新行为**：是用户在地址栏、刷新按钮或开发者工具中触发的重新加载操作，不同操作会给请求附加不同的缓存指令。

- 前进后退：通常直接使用本地副本，或从页面缓存中恢复，不重新发起验证。
- 普通刷新：对主文档要求重新验证，子资源仍按各自的缓存策略处理。
- 强制刷新：对主文档与子资源都要求重新验证，并跳过缓存取完整响应。
- 开发者工具：勾选停用缓存后，当前调试会话内所有请求都绕过缓存。
- 地址栏输入：等同于一次普通导航，是否验证取决于副本自身的新鲜度。
- 刷新与验证：普通刷新给主文档附加的正是要求重新验证的指令。
- 强制刷新代价：全部资源重新下载会明显拉长加载时间，但它不改变缓存条目的存储策略。
- 调试建议：排查缓存问题时用停用缓存选项，判断线上行为时回到常规操作。

```http
GET / HTTP/1.1
Host: example.com
Cache-Control: max-age=0
Pragma: no-cache
```

> [!WARNING]
> **警告内容**：普通刷新与强制刷新只影响本次请求，都不会清空磁盘缓存；据此判断线上用户的缓存命中情况会得出错误结论。

**速记**：普通刷新验证主文档，强制刷新绕过全部缓存，二者都不清空磁盘缓存。



#### 请求首部与缓存模式

**缓存模式（cache mode）**：是发起请求时选择的缓存使用策略，决定该请求允许使用缓存、必须重新验证还是完全绕过缓存。

- 默认模式：有可用副本且仍然新鲜时直接使用，未命中或已过期时按规则验证。
- 强制重载：忽略本地副本，向服务端请求完整响应并更新缓存条目。
- 禁止存储：既不使用已有副本，也不把本次响应写入缓存。
- 只读缓存：只允许读取缓存，未命中即失败，且仅在同源请求中可用。
- 作用范围：缓存模式只约束本次请求，不改变响应首部对缓存提出的要求。
- 页内差异：同一页面中的不同请求可以使用不同的缓存模式。
- 排查用法：需要确认服务端当前返回内容时，选用强制重载模式。
- 与缓存头的关系：模式决定是否使用缓存，响应首部决定副本能存活多久。

```text
default          有副本且新鲜时直接使用，过期后验证
no-store         不使用也不写入缓存
reload           跳过缓存取完整响应，并更新缓存
force-cache      优先使用缓存，没有副本时才请求网络
only-if-cached   只读缓存，未命中即失败，仅限同源
```

> 请求的发送方式与参数写法详见 前端/JavaScript 主题第 13 篇，本篇只关心这些模式在缓存判定上的效果。

**速记**：缓存模式决定使用、验证还是绕过缓存，作用范围限于本次请求。



#### 一次请求的缓存判定流程

**缓存判定流程**：是浏览器从收到请求到决定使用本地副本、验证副本或发起完整请求的步骤序列。

- 查缓存：按请求方法与 URL 组装缓存键，并按站点分区查找条目。
- 判新鲜：条目仍在新鲜期内则直接返回本地副本，流程结束。
- 做验证：条目已过期时检查是否带有验证器，有则发出协商请求。
- 取完整响应：没有可用条目、没有验证器或验证失败时，发起完整请求并按策略写入缓存。
- 触发时机：每次请求都会走一遍判定，命中位置越靠前，等待时间越短。
- 路径一致：文档导航与子资源请求共享同一套判定规则。
- 写入时机：完整响应返回后才写入缓存，304 只更新条目的新鲜度信息。
- 排查价值：把实际现象对回这条路径，可以判断问题出在缓存还是网络。

```text
请求 → 查缓存 ──命中且新鲜──→ 直接返回本地副本
        │
        ├─ 命中但过期 ─→ 有验证器 ─→ 304 复用本地副本
        │                          └─ 200 替换为新副本
        └─ 未命中 ────→ 完整请求 → 按响应策略写入缓存
```

> 这条路径由浏览器自动执行，理解它的价值在于解释网络面板中每一项缓存标记的来由。

**速记**：先查缓存，再判新鲜，过期则验证，无验证器才发完整请求。



### Cache Storage 与 HTTP 缓存的关系

Cache Storage 与 HTTP 缓存是两套并行的存储，理解二者的分工才能决定什么时候该用哪一个。

#### Cache Storage 的定位

**Cache Storage**：是浏览器提供的独立响应存储区，条目由脚本显式写入与读取，不参与 HTTP 缓存的自动判定。

- 独立性：条目与 HTTP 缓存互不覆盖，容量分别统计。
- 显式管理：写入、读取与删除都由脚本发起，浏览器不会自动把网络响应存入其中。
- 作用域：每个源拥有独立的缓存存储，条目按请求 URL 定位。
- 归类：其接口的完整用法与离线能力相关，详见本主题第 15 篇 Service Worker 与 PWA。
- 存储位置：条目保存在浏览器的存储区内，与磁盘缓存共用存储配额。
- 过期语义：条目没有新鲜度的概念，是否过期完全由脚本判断。
- 清理方式：只能由脚本删除，或随整个站点的存储被清理而消失。
- 调试入口：开发者工具的缓存存储面板可以查看与删除条目。

```text
                HTTP 缓存                     Cache Storage
写入方式        浏览器按响应首部自动写入        脚本显式写入与更新
读取时机        每次请求自动判定               脚本在拦截逻辑中主动读取
命中依据        缓存键、新鲜度与验证器          请求 URL 匹配
容量与淘汰      随浏览器存储清理策略            随脚本管理与存储清理
```

> [!CAUTION]
> **注意内容**：HTTP 缓存的条目过期或被清理，不会连带删除 Cache Storage 中的同名条目，两类缓存的内容可能长期不一致。

**速记**：Cache Storage 由脚本显式管理，条目与 HTTP 缓存各自独立。



#### 与 HTTP 缓存的分工

**分工关系**：HTTP 缓存负责常规请求的自动命中，Cache Storage 负责离线可用与自定义回退策略，两者不是替代关系。

- 自动与显式：常规请求走 HTTP 缓存的自动判定，离线场景由脚本读取 Cache Storage。
- 叠加顺序：请求先经过脚本的拦截逻辑，脚本再决定读缓存、走网络或复用 HTTP 缓存。
- 优先级归属：拦截逻辑存在时，本次请求是否使用 HTTP 缓存由脚本决定。
- 一致性维护：两类缓存的内容可能不同步，资源更新时需要在同一处逻辑里同时处理。
- 选择依据：需要浏览器自动命中时用 HTTP 缓存，需要离线可控时用 Cache Storage。
- 失效处理：资源更新时既要写入新条目，也要避免旧条目继续被读到。
- 观测差异：HTTP 缓存命中在网络面板中标记来源，脚本缓存命中只在脚本逻辑中体现。
- 组合效果：两者配合可以同时获得自动缓存的性能收益与离线能力的可控性。

```text
请求进入
  ├─ 存在脚本拦截逻辑 → 脚本决定读 Cache Storage 还是走网络
  └─ 无拦截逻辑       → 浏览器按 HTTP 缓存规则自动判定
```

> 使用 Cache Storage 承担离线能力时，条目更新与清理必须由脚本自己负责，浏览器不会代为处理。

**速记**：HTTP 缓存管自动命中，Cache Storage 管离线与自定义策略，更新要一起处理。
