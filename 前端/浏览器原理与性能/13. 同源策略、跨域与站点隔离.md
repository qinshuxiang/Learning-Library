## 同源策略、跨域与站点隔离

### 同源策略与源的判定

**同源策略（same-origin policy）** 是浏览器划分安全边界的基本模型，它按源把文档、脚本与数据分隔开，限制一个源读取另一个源的内容。判定是否跨源、限制什么、如何申请放行，是理解浏览器安全的第一组问题，跨源资源共享与站点隔离都建立在这一判定之上。

#### 源的定义与三元组

**源（origin）**：是协议（scheme）、主机（host）、端口（port）三元组构成的安全标识，三者全部相同才视为同源。

- 参与判定的三项：协议、主机、端口；端口省略时按协议默认值补齐，http 默认 80，https 默认 443。
- 不参与判定：路径、查询字符串与片段标识符，主机名的大小写会被规范化后再比较。
- 典型跨源情形：协议不同（http 与 https）、主机不同（example.com 与 api.example.com）、端口不同（443 与 8443）。
- 序列化写法：URL 对象的 origin 属性给出三元组的标准形式，主机与端口取默认值时端口部分省略。

```js
function isSameOrigin(urlA, urlB) {
  return urlA.protocol === urlB.protocol
    && urlA.hostname === urlB.hostname
    && urlA.port === urlB.port;
}

const page = new URL("https://example.com/page");
console.log(isSameOrigin(page, new URL("https://example.com/other")));  // true
console.log(isSameOrigin(page, new URL("http://example.com/page")));    // false：协议不同
console.log(isSameOrigin(page, new URL("https://api.example.com/x")));  // false：主机不同
console.log(isSameOrigin(page, new URL("https://example.com:8443/x"))); // false：端口不同
console.log(page.origin);                                              // "https://example.com"
```

> 默认端口的判定以协议为准：https 访问省略的端口补为 443，与 http 的 80 不同，因此同一主机上的 http 与 https 仍属跨源。

**速记**：源由协议、主机、端口三元组唯一确定，路径与查询串不参与判定。



#### 同源策略限制与放行

**同源策略的作用范围**：是限制跨源读取与跨源文档互操作，而不是禁止一切跨源网络行为。

- 被限制：读取跨源请求的响应体、访问跨源框架或弹窗的文档对象、读取跨源页面的存储、共享脚本执行上下文。
- 未被禁止：发起请求（表单提交、资源标签、fetch 与 XMLHttpRequest 都能发出）、按标签嵌入资源（图片、脚本、样式表、框架）、提交表单等写操作。
- 正规通道：postMessage 传递消息、CORS 授权后读取响应、以及受 Cookie 自身属性与浏览器第三方策略约束的凭据请求。
- 判定粒度：限制以源为单位，同一源内的任何路径之间不再隔离。

```js
// 页面位于 https://example.com，页内嵌有 https://widget.example.net 的框架
const frame = document.querySelector("iframe#widget");

// 反例：跨源文档不可读，直接访问将抛出异常
// console.log(frame.contentDocument.title);

try {
  frame.contentWindow.postMessage({ type: "ping" }, "https://widget.example.net");
} catch (error) {
  console.log(error.name);
}
```

> 同源策略的核心是「可发送、不可读」：请求能够到达目标服务器，但在缺少明确授权时，响应内容不会交给发起方的脚本。

**速记**：同源策略限制跨源读取与文档互操作，不阻止跨源请求的发送。



#### 源继承与不透明源

**不透明源（opaque origin）**：是不含可序列化协议、主机与端口的源，任意两个不透明源互不同源，也不与任何普通源同源。

- 产生场景：以 data: 方式加载的文档、未授予同源权限的沙箱框架、以及部分由脚本创建的 blob: 文档。
- 字符串化：这类源序列化为空串或字符串 null，不能作为白名单的依据。
- 请求表现：来自不透明源的请求，其 Origin 请求头为 null，服务端据此放行等同于对任意站点放行。
- 继承规则：空地址与脚本地址创建的文档继承创建者的源，与不透明源的产生条件不同。

```html
<!-- 沙箱化嵌入：脚本可运行，但不获得被嵌入站点的同源身份 -->
<iframe src="https://widget.example.net/embed"
        sandbox="allow-scripts"
        title="embed"></iframe>
```

> [!WARNING]
> **警告内容**：沙箱属性同时包含 allow-scripts 与 allow-same-origin 时，被嵌入文档可以自行移除沙箱限制；两者并用会使沙箱形同虚设。

**速记**：不透明源无法序列化，Origin 头为 null，不可用于来源白名单。



### 跨源资源嵌入与限制

**跨源资源嵌入** 是浏览器为兼容既有网页而保留的通道：脚本、样式、图片与字体等资源标签可以跨源加载，但加载结果不会把响应内容暴露给发起方脚本。看清这条通道的边界，才能理解 fetch 与资源标签的差异。

#### 可跨源嵌入的资源

**跨源嵌入（cross-origin embedding）**：是通过资源标签引入跨源内容的方式，标签本身允许跨源，但脚本无法读取响应内容。

- 常见标签：图片、脚本、样式表、音视频、框架以及网页字体，都允许跨源加载。
- 请求特征：由标签发起的请求不带自定义头，浏览器不要求目标站点先行授权。
- 结果限制：响应以不透明形式交给元素处理，脚本读不到字节内容，只能通过加载与错误事件感知成败。
- 副作用：这条限制造就了一批旁路技巧，例如借助加载时序或资源尺寸推断跨源页面的状态。

```html
<!-- 资源标签可以跨源引入，不需要目标站点配置 CORS -->
<img src="https://cdn.example.com/photo.png" alt="photo">
<script src="https://cdn.example.com/analytics.js"></script>
<link rel="stylesheet" href="https://cdn.example.com/theme.css">
```

> 嵌入通道是历史兼容的产物，也是诸多侧信道问题的源头；能改为显式跨源请求的场景应优先改造。

**速记**：资源标签可跨源加载，但响应内容不交给脚本，只能通过事件感知成败。



#### crossorigin 属性与凭据模式

**crossorigin 属性**：是写在嵌入标签上的属性，取值 anonymous 或 use-credentials，用于把该元素的请求纳入跨源授权流程。

- anonymous：不携带凭据，跨源响应只需给出与请求来源匹配的 Allow-Origin。
- use-credentials：请求携带 Cookie 与客户端证书，服务端必须回传允许凭据的标记且不得使用通配符来源。
- 实际用途：让画布读取跨源图片像素（否则画布被污染，读取像素的方法会抛异常）、让跨源脚本的错误细节进入全局错误处理。
- 默认行为：不写该属性时元素走无凭据嵌入模式，响应不透明，跨源脚本的错误信息也被屏蔽。

```html
<!-- 带跨源授权的图片与脚本：允许读取画布像素，允许拿到脚本错误详情 -->
<img src="https://cdn.example.com/photo.png"
     crossorigin="anonymous"
     alt="photo">
<script src="https://cdn.example.com/reporter.js"
        crossorigin="anonymous"></script>
```

> crossorigin 是发起方的声明，目标服务端仍需返回匹配的跨源响应头；只有一侧配置时元素会以加载失败告终。

**速记**：crossorigin 取 anonymous 或 use-credentials，让嵌入请求进入跨源授权流程。



#### 响应遮蔽与跨源读取阻塞

**跨源读取阻塞（CORB）与不透明响应阻塞（ORB）**：是渲染进程对无授权的跨源响应施加的过滤，把可能泄露内容的部分整体替换为空。

- 判定依据：响应声明的内容类型与实际内容特征是否匹配，例如以文本或脚本类型返回却是结构化数据。
- 行为：可疑响应体在进入脚本可见范围前被剥离，脚本拿到空内容，从而堵住借助嵌入标签读取跨源数据的路径。
- 与授权的关系：通过跨源授权校验的响应按授权结果交付，不进入遮蔽流程。
- 与无凭据请求的关系：这类请求仍可发出，但响应类型为不透明、状态码读作 0，内容不可读，故不能用于取数。

```js
// 无凭据嵌入模式只能用于「发出请求」，不能用于「读取响应」
fetch("https://api.example.com/items.json", { mode: "no-cors" })
  .then((response) => {
    console.log(response.type);   // "opaque"
    console.log(response.status); // 0
  });
```

> [!CAUTION]
> **注意内容**：把无凭据嵌入模式当作绕过跨源限制的取数手段是无效的，响应内容必然不可读；跨源取数只能依靠服务端授权或同源代理。

**速记**：无授权的跨源响应会被遮蔽，无凭据请求可发但内容读不到。



### CORS 的浏览器侧行为与预检

**CORS（Cross-Origin Resource Sharing，跨源资源共享）** 是浏览器与服务端共同实现的放行协议，服务端用响应头声明允许哪些源读取，浏览器负责校验与执行。本节只讨论浏览器侧的判定与请求形态，服务端的配置写法详见 前端/JavaScript 主题第 13 篇 网络请求与跨域。

#### 简单请求与预检的判定

**简单请求（simple request）**：是方法、请求头与内容类型都落在安全列表内的跨源请求，可以直接发出，无需先询问服务端。

- 方法限制：GET、HEAD、POST 三种。
- 请求头限制：仅安全列表头，如 Accept、Accept-Language、Content-Language、Range 与少数受控头。
- 内容类型限制：Content-Type 只能是表单编码、多部分表单与纯文本三类。
- 超出任一条即成为需预检的请求，浏览器会先发一次 OPTIONS 询问。

```js
// 携带 JSON 内容类型与自定义头，超出简单请求范围，浏览器先发预检
fetch("https://api.example.com/items", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Request-Id": "3f2a9c71"
  },
  body: JSON.stringify({ name: "sample" })
});
```

> 简单请求是历史遗留的宽松通道，它只说明「无需预检」，并不意味着目标站点的授权是稳妥的。

**速记**：方法、请求头、内容类型三者都在安全列表内才是简单请求，否则先预检。



#### 预检请求与关键响应头

**预检请求（preflight request）**：是浏览器自动发出的 OPTIONS 请求，用于在发送真实请求前确认方法与请求头是否被允许。

- 请求头：Access-Control-Request-Method 声明真实请求的方法，Access-Control-Request-Headers 声明真实请求的自定义头。
- 关键响应头：Access-Control-Allow-Origin 允许的来源、Access-Control-Allow-Methods 允许的方法、Access-Control-Allow-Headers 允许的请求头。
- 缓存：Access-Control-Max-Age 指定预检结果可缓存的秒数，缓存有效期内同类请求不再预检。
- 命中失败：任一校验不通过，浏览器中止真实请求，并在控制台报出跨源错误。

```http
OPTIONS /items HTTP/1.1
Host: api.example.com
Origin: https://example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,x-request-id

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type, X-Request-Id
Access-Control-Max-Age: 600
```

> 预检缓存按来源、地址与请求头组合生效，接口契约变更后需要等待旧缓存过期才能观察到新策略。

**速记**：预检是浏览器自动发出的 OPTIONS，服务端用 Allow 系列头声明放行范围与缓存时长。



#### 凭据请求与通配符限制

**凭据模式（credentials mode）**：决定请求是否携带 Cookie 与认证信息，fetch 用 credentials 选项取 omit、same-origin、include，XMLHttpRequest 用 withCredentials 布尔值控制。

- include：携带目标源的 Cookie，要求服务端回传具体的允许来源，并声明允许凭据。
- 通配符禁令：凭据模式下允许来源不得写为通配符，也不得使用同样宽松的占位写法。
- Cookie 生效：跨源响应下发的 Set-Cookie 是否被接受，还取决于 Cookie 自身的 SameSite 与浏览器的第三方 Cookie 策略（详见本主题第 12 篇 浏览器存储机制）。
- 默认值：fetch 的默认凭据模式为 same-origin，同源请求自动带 Cookie，跨源请求不带。

```js
fetch("https://api.example.com/profile", {
  method: "GET",
  credentials: "include"
}).then((response) => response.json())
  .catch((error) => console.log(error.name)); // "TypeError"
```

```text
Access to fetch at 'https://api.example.com/profile' from origin 'https://example.com'
has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin'
header in the response must not be the wildcard '*' when the request's
credentials mode is 'include'.
```

> [!WARNING]
> **警告内容**：凭据模式下使用通配符来源的响应会被浏览器整体拒绝，且失败发生在响应阶段，脚本只会捕获到一个 TypeError，而不是可读的业务错误。

**速记**：带凭据的跨源请求必须回传具体来源并声明允许凭据，通配符会被拒绝。



#### 响应头校验与失败表现

**响应头校验**：是浏览器在收到真实响应后按跨源规则逐项比对的过程，校验对象包括来源、凭据与可读响应头集合。

- 来源：允许来源需与请求来源精确匹配，或在不带凭据时取通配符。
- 可读头：非安全列表响应头默认对脚本不可读，需要用 Access-Control-Expose-Headers 显式声明。
- 失败表现：控制台输出跨源错误，Promise 以 TypeError 拒绝；浏览器有意不区分网络失败与授权失败，避免泄漏探测信息。
- 作用范围：跨源校验由浏览器执行，服务端之间、命令行工具与原生应用不受其约束，因此它不构成接口访问控制。

```js
fetch("https://api.example.com/items")
  .then((response) => {
    console.log(response.headers.get("Content-Type"));  // "application/json"
    console.log(response.headers.get("X-Total-Count")); // 未暴露时为 null
  });
```

> 跨源机制保护的是浏览器中的用户，不是服务端接口本身；越权控制必须由服务端的鉴权实现。

**速记**：跨源校验比对来源、凭据与可读头，失败统一表现为 TypeError，不构成服务端访问控制。



### 跨源隔离：COOP、COEP 与 CORP

**跨源隔离（cross-origin isolation）** 是一组响应头共同声明的文档状态：通过切断跨源窗口引用并限制跨源子资源，使文档获得独立且可信的执行环境。它服务于需要强隔离的接口与站点隔离的进程划分。

#### 跨源隔离的动机与判定

**跨源隔离的动机**：是让文档运行在一个与其他源互不共享的上下文中，从而可以安全使用高精度计时与共享内存类接口。

- 隔离前提：本文档不与跨源窗口共享浏览上下文组，且所有跨源子资源都显式声明允许被嵌入。
- 开放能力：共享内存缓冲以及按文档粒度统计内存用量之类的高精度接口，要求页面处于跨源隔离状态。
- 判定接口：window.crossOriginIsolated 返回布尔值，为 true 表示当前文档已跨源隔离。
- 状态整体性：隔离是全有或全无，任一环节不满足即回到普通状态。

```js
console.log(self.crossOriginIsolated); // 未开启跨源隔离时为 false
console.log(typeof SharedArrayBuffer); // 未隔离时通常为 "undefined"
```

**速记**：跨源隔离让文档脱离共享上下文，是共享内存类接口的启用前提。



#### COOP 的取值与作用

**COOP（Cross-Origin-Opener-Policy，跨源打开者策略）**：是控制本文档与被它打开的窗口是否保留引用关系的响应头，取值 same-origin、same-origin-allow-popups 与 unsafe-none。

- same-origin：仅同源打开的窗口进入同一浏览上下文组，跨源窗口的打开者引用被切断。
- same-origin-allow-popups：保留与本文档打开的弹窗的引用关系，同时切断其他跨源引用。
- unsafe-none：默认值，不做限制。
- 效果：引用被切断后，双方无法通过窗口引用互相操作，也无法共享同一上下文中的可读数据。

```http
Cross-Origin-Opener-Policy: same-origin
```

> 弹窗登录等依赖打开者引用的流程需要重新评估：引用切断后应改用 postMessage 显式传参。

**速记**：COOP 取 same-origin 时切断跨源窗口引用，是跨源隔离的窗口侧条件。



#### COEP 与 CORP 的分工

**COEP（Cross-Origin-Embedder-Policy，跨源嵌入者策略）**：是要求本文档加载的跨源子资源必须显式授权的响应头，取值 require-corp、credentialless 与 unsafe-none。**CORP（Cross-Origin-Resource-Policy，跨源资源策略）**：是资源方声明自身响应允许被哪些文档嵌入的响应头，取值 same-origin、same-site 与 cross-origin。

- COEP 的立场：由加载方声明只接受显式授权的跨源资源，未授权的资源加载失败。
- CORP 的立场：由资源方声明响应允许被同源、同站点或任意来源嵌入。
- 与跨源授权的分工：脚本发起的数据请求归跨源授权管，被标签嵌入的静态资源归 CORP 管。
- 兼容取值：credentialless 允许在不带凭据的前提下加载未声明 CORP 的资源，适用于难以改造第三方资源的场景。

```http
Cross-Origin-Embedder-Policy: require-corp
Cross-Origin-Resource-Policy: same-site
```

> [!CAUTION]
> **注意内容**：开启 COEP 后，未声明 CORP 且未通过跨源授权的跨源图片与脚本会直接加载失败，页面可能出现空白区域或功能缺失，需先盘点并改造资源再上线。

**速记**：COEP 由加载方要求显式授权，CORP 由资源方声明可被嵌入的范围。



#### 组合生效与灰度部署

**组合生效条件**：文档要进入跨源隔离状态，需要 COOP 与 COEP 同时满足要求，且页面上不存在未授权的跨源子资源。

- 必要条件：COOP 取 same-origin，同时 COEP 取 require-corp 或 credentialless。
- 资源盘点：自建资源补发 CORP，第三方资源确认支持情况，或改为由服务端代理的同源地址。
- 灰度手段：使用只报告形式先收集违规清单，不改变实际加载行为。
- 回退代价：任一遗漏资源都会让文档退出隔离状态，依赖隔离的接口随之不可用。

```text
GET https://static.example.net/logo.svg net::ERR_BLOCKED_BY_RESPONSE
```

> 跨源隔离要求参与各方同时就位，任何一方未就位都会让整个文档退回普通状态。

**速记**：跨源隔离要求 COOP 与 COEP 同时生效且资源全部授权，灰度阶段先用只报告形式收集。



### 站点隔离与进程边界

**站点隔离（site isolation）** 是把不同站点放进不同渲染进程的架构策略，用进程边界兜住渲染引擎漏洞带来的跨源读取风险，它把同源策略的边界从文档内检查下沉到进程间隔离。进程与线程的总体分工详见本主题第 1 篇 浏览器简介与多进程架构。

#### 站点与源的粒度差异

**站点（site）**：是协议加可注册域（eTLD+1）构成的粒度，忽略子域与端口的差异，比源更粗。

- 聚合原因：为每个源单独开进程的开销不可接受，按站点聚合可在安全与开销之间取得平衡。
- 同站点不同源：两个不同的子域属于同一站点，可能被分配到同一进程。
- 站点不同：协议不同即属不同站点，同名主机的 http 与 https 分属两个站点。
- 结论：站点隔离不等于源隔离，同源策略仍在文档层面执行细粒度校验。

```js
// 源判定看三元组，站点判定只看协议加可注册域
const pageA = new URL("https://a.example.com/dashboard");
const pageB = new URL("https://b.example.com/report");

console.log(pageA.hostname === pageB.hostname);      // false：两者不同源
console.log(pageA.hostname.endsWith("example.com")); // true：同属 example.com 站点
console.log(pageA.protocol === pageB.protocol);      // true：站点还要求协议一致
```

**速记**：站点是协议加可注册域，粒度比源粗，站点隔离不等于源隔离。



#### 进程边界的防护与代价

**进程边界的防护**：是让不同站点的数据分处不同进程，使渲染引擎的内存越界读取无法触及别的站点。

- 防护逻辑：旁路读取类漏洞利用的是同进程共享地址空间，跨站点数据不在该进程内即可阻断。
- 代价：进程数量与内存占用上升，进程间通信增加，跨站点框架需要独立进程与额外往返。
- 兼容影响：依赖同进程同步访问的旧写法失效，跨站点框架内的脚本无法与宿主同步互操作。
- 实现形态：跨站点框架以独立进程渲染，宿主与框架之间只能异步通信。

```js
// 跨站点框架只能通过 postMessage 异步通信
const frame = document.querySelector("iframe#payment");

frame.contentWindow.postMessage(
  { type: "resize", height: 320 },
  "https://pay.example.net"
);

window.addEventListener("message", (event) => {
  if (event.origin !== "https://pay.example.net") return;
  console.log(event.data); // { type: "ready" }
});
```

> [!WARNING]
> **警告内容**：依赖「跨站点框架与宿主同进程、可同步读写」的代码在站点隔离下会直接失败，迁移时应改为 postMessage 异步通信并显式校验来源。

**速记**：进程边界阻断跨站点内存读取，代价是更多进程与只能异步通信。



#### 相关头字段与观测手段

**Origin-Agent-Cluster 响应头**：是请求把文档从站点粒度的代理集群切换到源粒度的声明，取值为 ?1 表示启用。

- 作用：让同站点不同源在代理集群层面分开，配合站点隔离得到更细的隔离粒度。
- 观测：window.crossOriginIsolated 反映跨源隔离状态，浏览器任务管理器可查看进程与站点映射。
- 浏览器差异：桌面端普遍默认开启站点隔离，移动端受内存限制可能按设备能力取舍。
- 排查思路：出现跨源访问异常时先确认框架是否被分配到独立进程，再检查通信是否走 postMessage。

```http
Origin-Agent-Cluster: ?1
```

> 隔离粒度越细，安全上限越高，开销也越大；取值应结合页面是否真的处理跨站点敏感数据。

**速记**：Origin-Agent-Cluster 可把文档降到源粒度集群，进程与站点映射可用任务管理器观测。
