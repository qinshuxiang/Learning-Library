## 浏览器网络与 HTTP 协议演进

本篇回答浏览器侧的四类问题：网络分层中浏览器负责到哪一层、连接如何建立与复用、HTTP 的三个版本分别解决了什么瓶颈、协议版本又如何反过来决定资源组织方式。报文字段定义与 TCP、TLS 的握手细节属 架构/计算机网络 领域，本篇只保留浏览器侧的连接管理与协议选择依据。

### 网络分层与浏览器侧的职责

**网络分层与浏览器侧的职责** 要解决的第一件事是边界：哪些工作由浏览器完成，哪些交给操作系统。这一节先定分层，再看承担请求的网络服务。

#### TCP/IP 分层与浏览器所在的层

**TCP/IP 分层模型**：是把网络通信拆成应用层、传输层、网络层、链路层四层的抽象，每层只向上层提供接口，不暴露下层实现。

- 应用层：HTTP、HTTP/2、HTTP/3、DNS、TLS 位于该层，浏览器直接构造与解析这部分数据。
- 传输层：TCP 与 UDP 提供端到端传输，可靠性、重传与拥塞控制由操作系统内核实现。
- 网络层：IP 负责寻址与路由，把数据包送往目标主机。
- 链路层：以太网、Wi-Fi 等负责物理介质上的帧传输，由网卡与驱动处理。
- 分层的价值：每层只依赖相邻层的接口，浏览器可以只替换应用层的实现而不影响传输层。
- 演进依据：应用层改动不需要操作系统配合，这正是 HTTP 版本能够快速迭代的前提。

```text
应用层    HTTP / HTTP/2 / HTTP/3 / DNS / TLS     浏览器构造与解析
传输层    TCP / UDP                              操作系统内核负责
网络层    IP                                     操作系统内核负责
链路层    以太网 / Wi-Fi                          网卡与驱动负责
```

> 浏览器的工作范围止于应用层：它把请求写成字节流交给操作系统的套接字（socket），连接可靠性由内核保证。

**速记**：浏览器只对应用层负责，传输层及以下交给操作系统内核。



#### 网络服务与一次请求的组成

**网络服务（network service）**：是浏览器内负责发起网络请求的模块，在多进程架构下通常运行于浏览器进程之外的独立进程，渲染进程通过进程间通信把请求交给它。

- 请求发起：脚本、解析器或预加载扫描器提出的请求，统一由网络服务执行。
- 策略校验：发包之前完成同源策略、跨源资源共享与 Cookie 属性的校验。
- 资源管理：DNS 缓存、连接池、HTTP 缓存与 TLS 会话缓存都由网络服务维护。
- 响应交付：响应字节回传给请求方，由渲染进程解析为文档、样式表或数据。
- 隔离收益：网络服务出问题不会连带渲染进程，请求队列与缓存状态也不被页面脚本直接改写。

```js
// 查看页面中首个脚本资源的协议与建连耗时口径
const entries = performance.getEntriesByType("resource");
const firstScript = entries.find((entry) => entry.name.endsWith(".js"));
console.log(firstScript.nextHopProtocol);                           // 例如 "h2" 或 "h3"
console.log(firstScript.domainLookupStart, firstScript.connectEnd); // 从导航开始计的毫秒值
```

> 网络服务是浏览器内唯一发起真实网络输入输出的地方，缓存、连接复用与协议协商因此都集中在它内部完成。

**速记**：网络服务统一发起请求，缓存、连接与协议协商都在它内部完成。



### 连接建立：DNS、TCP 与 TLS

取回一个资源之前，浏览器要先知道目标地址，再建立可用连接。这一节只看浏览器侧能够观测与能够复用的部分。

#### DNS 解析与浏览器侧的缓存

**DNS 解析（domain name system resolution）**：是把域名翻译成 IP 地址的过程，浏览器侧参与的部分是多级缓存查找与解析时序的调度。

- 浏览器缓存：网络服务对本进程解析过的域名做短期缓存，命中时跳过后续查询。
- 分层查找：浏览器缓存未命中时依次落到操作系统缓存与本地解析服务，任一层命中都会提前返回。
- 时序观测：Resource Timing 中的 domainLookupStart 与 domainLookupEnd 描述解析区间，时间从导航开始计。
- 缓存过期：条目有存活时间，过期后重新解析，域名记录变更不会对所有用户同时生效。
- 结果不可见：DNS 缓存是否命中无法从页面脚本直接区分，只能从解析时序区间推断。
- 排查层次：本地解析服务的缓存与主机配置同样影响解析结果，排查时按层确认。

```bash
# 从命令行查看域名解析结果，不代表浏览器缓存的命中情况
dig example.com +short
nslookup example.com
```

```js
// 从 Resource Timing 读取 DNS 解析区间
const [entry] = performance.getEntriesByType("resource");
console.log(entry.domainLookupStart, entry.domainLookupEnd); // 毫秒，从导航开始计
```

> 浏览器 DNS 缓存、操作系统缓存与本地解析服务的缓存层层叠加，缩短解析时间的收益只在新域名首次解析时体现。

**速记**：DNS 解析在浏览器侧表现为多级缓存查找，时序用 Resource Timing 观测。



#### TCP 与 TLS 握手的浏览器侧视角

**TCP 握手**：是传输数据前双方确认连接可用的三次报文交换。**TLS 握手**：是在已建立的 TCP 连接上协商加密参数、验证证书并生成会话密钥的过程。两者的报文细节属 架构/计算机网络 领域，此处只关心它们给浏览器增加的往返成本。

- 逐段累加：一次全新连接要付出 DNS、TCP、TLS 三段往返，未复用时逐次累加。
- 会话复用：会话票据（session ticket）与会话缓存能让后续连接跳过部分握手步骤。
- 版本差异：较新的 TLS 版本把完整握手压缩到一次往返，并允许恢复会话时在首次往返中携带数据。
- 受控首部：Connection 与 Keep-Alive 属受控首部，脚本无法改写，跨源连接由网络服务统一管理。
- 顺序固定：DNS 必须先于 TCP，TLS 必须后于 TCP，三段无法并行，只能靠复用压缩总量。
- 观测方式：Resource Timing 中 secureConnectionStart 大于 0，才说明该请求走过 TLS。

```js
// 拆出单个资源的 DNS、TCP、TLS 三段时间
const [entry] = performance.getEntriesByType("resource");
const dns = entry.domainLookupEnd - entry.domainLookupStart;
const tcp = entry.connectEnd - entry.connectStart;
const tls = entry.secureConnectionStart > 0 ? entry.connectEnd - entry.secureConnectionStart : 0;
console.log(dns, tcp, tls); // 毫秒；secureConnectionStart 为 0 表示该请求未走 TLS
```

> [!NOTE]
> **提醒内容**：secureConnectionStart 为 0 表示该请求未经 TLS，此时不能把 connectEnd 与 secureConnectionStart 之差当作握手耗时。

**速记**：浏览器只承担握手往返的成本与会话复用的收益，报文细节不属本篇范围。



### HTTP/1.1 的瓶颈

HTTP/1.1 是纯文本协议，一条连接在同一时刻只处理一组请求响应。资源数量一多，瓶颈就暴露出来。

#### 队头阻塞与同域连接数限制

**HTTP/1.1 队头阻塞（head-of-line blocking）**：是一条连接上的响应必须按请求顺序交付，前一个响应未完成时后续响应只能排队。**同域连接数限制**：是浏览器对同一主机允许并发打开的连接数上限。

- 串行交付：连接内的响应按请求先后返回，慢响应会阻塞排在它之后的响应。
- 连接上限：同一主机的并发连接数有上限，具体取值随浏览器与版本不同，属实现细节。
- 排队放大：大量同域小资源并发时，排队等待可能超过资源本身的传输时间。
- 部分缓解：现代浏览器对连接做了优化，但同一连接内的串行交付语义没有改变。
- 资源类型：脚本、样式表与文档都会占用连接，图片与字体同样排在队列里。
- 判断方法：网络面板中大量请求处于排队状态时，先确认它们是否集中在同一主机。

```text
连接 A   [请求 1 ....................] [请求 4 ---]
连接 B   [请求 2 ..........] [请求 5 -----------]
连接 C   [请求 3 ---]     [请求 6 排队等待]
         一条连接同一时刻只有一组请求响应对在传输
```

> 队头阻塞的根源在于 HTTP/1.1 报文没有请求标识，接收方只能靠到达顺序把响应与请求对应起来。

**速记**：一条连接串行返回，同域连接数又有上限，排队由此产生。



#### 绕过手段与其代价

**资源合并与内联**：是把多个文件合并为一个文件、或直接把内容写进文档，以减少请求数量并绕开连接排队的做法。

- 文件拼接：多个脚本或样式合并为一个文件，请求数量下降。
- 图片雪碧图：多张小图合并为一张大图，靠背景定位取出其中一块。
- 内容内联：把体积小的关键内容直接写入文档，省去一次请求。
- 代价：合并破坏缓存粒度，任一处的改动都会让整个合并文件失效；内联增大文档体积，且无法被独立缓存。
- 内联边界：需要在多个页面复用的内容不适合内联，否则每份文档都要重复传输一次。

```css
/* 雪碧图：多张小图合并为一张大图，用背景定位取出其中一块 */
.icon-home {
  width: 24px;
  height: 24px;
  background-image: url("/assets/sprite.png");
  background-position: -48px 0;
}
```

> [!CAUTION]
> **注意内容**：按页面维度随意合并资源会放大缓存失效范围，一处文案改动可能让用户重新下载数百 KB 的合并文件。

**速记**：合并与内联降低请求数量，代价是牺牲缓存粒度与按需加载。



#### 首部冗余与无状态的开销

**首部冗余**：是 HTTP/1.1 每次请求都要重复发送 Cookie、User-Agent 等首部字段，同域请求越多重复量越大的现象。

- 纯文本首部：首部以明文重复发送，重复字段不享有跨请求的压缩。
- Cookie 随行：同域请求自动携带 Cookie，即使静态资源完全用不到身份信息。
- 无状态设计：协议本身不保存会话，重复首部正是无状态带来的必然开销。
- 浏览器侧结果：同域请求数量越多，上行字节的浪费越明显，弱网下尤为突出。
- 判断依据：同一域名下的请求越多、Cookie 越大，无状态设计带来的开销越显著。

```http
GET /assets/app.css HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (示例值，仅供观察首部形态)
Accept: text/css
Cookie: sessionId=abc123; theme=dark
```

> 首部冗余对上行带宽敏感，移动网络的上传带宽通常远小于下载带宽，重复首部的代价因此被放大。

**速记**：同域请求逐个重复发送首部与 Cookie，无状态设计的代价落在上行流量上。



### HTTP/2 的多路复用与队头阻塞

HTTP/2 保留请求方法、状态码与首部语义，改动集中在承载方式：把文本报文换成二进制分帧。

#### 二进制分帧与多路复用

**HTTP/2**：是保留 HTTP 语义、把报文改为二进制帧格式并支持在同一连接上并行传输多个请求的协议版本。**多路复用（multiplexing）**：是在一条连接上交错传输多个请求与响应，并由标识区分归属的能力。

- 二进制分帧：报文被切成带流标识（stream id）的帧，接收方按流重新组装。
- 流标识：每个请求独占一条流，响应与请求靠流标识对应，不再依赖到达顺序。
- 单连接：一个源通常只需一条连接，通过增加连接数来提升并发的必要性下降。
- 帧类型：HEADERS 帧承载首部，DATA 帧承载正文，SETTINGS 帧用于参数协商。
- 与 HTTP/1.1 的差异：一个源一条连接即可满足并发需求，连接数不再是主要瓶颈。
- 可观测性：nextHopProtocol 为 h2 时，网络面板中的连接数会明显少于请求数。

```js
// 统计页面中各资源实际使用的应用层协议
const protocols = performance.getEntriesByType("resource")
  .map((entry) => entry.nextHopProtocol)
  .filter((value, index, all) => all.indexOf(value) === index);
console.log(protocols); // 例如 ["h2", "h3"]
```

> 服务器推送（server push）曾被视为 HTTP/2 的配套能力，但推送内容难以与缓存状态对齐，主流浏览器已停止支持该机制。

**速记**：HTTP/2 把报文切成带流标识的帧，一条连接内并行传输多个请求。



#### 头部压缩与传输层队头阻塞

**HPACK 头部压缩**：是 HTTP/2 用静态表与动态表对首部字段做索引化编码的机制，重复出现的首部只发送索引。**传输层队头阻塞**：是一条 TCP 连接出现丢包时，该连接上所有流的数据都要等待丢包重传，因为 TCP 保证字节按序交付。

- 静态表：高频首部字段与取值预先编号，重复出现时只发索引。
- 动态表：同一连接内出现过的首部加入动态表，后续引用索引即可。
- 残余阻塞：多路复用解决应用层的串行交付，却无法绕开 TCP 的按序交付要求。
- 影响面：丢包率高的链路上，丢一个包会拖住该连接上的全部流，HTTP/2 的并行优势被削弱。
- 与首部冗余的关系：动态表按连接维护，连接越多压缩收益越分散，这也是域名分片在 HTTP/2 下失效的原因之一。

```text
一个 DATA 帧丢失时各流的状态：
流 1  [已到达][已到达][丢包][等待重传]
流 3  [已到达][已到达][内核暂存，不交付上层]
流 5  [已到达][已到达][内核暂存，不交付上层]
```

> [!IMPORTANT]
> **重要内容**：多路复用只解决应用层的排队问题，传输层的丢包阻塞必须更换传输协议才能消除，这正是 HTTP/3 的出发点。

**速记**：HPACK 让重复首部只发索引，多路复用仍受 TCP 按序交付牵制。



### HTTP/3 与 QUIC

HTTP/3 的语义与 HTTP/2 相同，改动全部落在传输层：把 TCP 换成基于 UDP 的 QUIC。

#### QUIC 的传输特性

**QUIC**：是构建在 UDP 之上的通用传输协议，把可靠性、拥塞控制与加密整合到用户态实现，并让每条流独立处理丢包。**HTTP/3**：是使用 QUIC 作为传输层的 HTTP 版本。

- 基于 UDP：协议实现位于用户态，演进节奏不再受操作系统内核更新约束。
- 流内可靠：重传只影响发生丢包的流，其余流继续正常交付。
- 分层整合：多路复用与可靠传输在同一层实现，不需要为每条流维护额外的连接语义。
- 默认加密：QUIC 的传输层默认加密，加密协商与传输协商合并进行。
- 与 TCP 的差别：TCP 的可靠性属于连接，QUIC 的可靠性属于流，阻塞的影响面因此更细。
- 代价：基于 UDP 的实现在部分网络环境下可能被限速，回退能力因此必不可少。

```text
HTTP/2    HTTP 语义 + TCP 传输 + 独立的 TLS 握手
HTTP/3    HTTP 语义 + QUIC 传输（集成加密与可靠性）
```

> HTTP/3 没有新增请求方法或状态码，改动集中在下半部分：同样的语义由不同的传输方式承载。

**速记**：HTTP/3 把传输换成基于 UDP 的 QUIC，丢包只阻塞单条流。



#### 建连与连接迁移

**连接迁移（connection migration）**：是 QUIC 用连接标识而非 IP 与端口的组合来标识一条连接，网络切换后连接可以继续使用。

- 建连合并：传输协商与加密握手合并，新建连接的往返次数少于 TCP 与 TLS 叠加的组合。
- 会话恢复：恢复已有会话时可以在首次往返中携带数据，进一步压缩等待时间。
- 连接标识：连接由标识符认定，设备从 Wi-Fi 切到蜂窝网络时不必然重建连接。
- 浏览器侧收益：切换网络时正在进行的请求不必全部重发，长连接场景收益更明显。

```js
// 网络类型变化时触发 change 事件（仅适用于实现该接口的浏览器）
const connection = navigator.connection;
if (connection) {
  connection.addEventListener("change", () => {
    console.log(connection.effectiveType, connection.downlink); // 例如 "4g" 10
  });
}
```

> Network Information 接口并非所有浏览器都实现，读取 navigator.connection 之前需要先判断该属性是否存在。

**速记**：QUIC 建连往返更少，连接迁移让网络切换不再必然重连。



#### 浏览器侧的协商与回退

**协议协商**：是浏览器在选择 HTTP 版本时先尝试较高版本、失败或不被支持时逐级回退的过程。

- Alt-Svc：服务端用该响应首部声明同一源在其他端口或协议上可用，浏览器据此缓存备用端点。
- HTTPS 记录：DNS 的 HTTPS 记录可以声明服务端支持的协议，浏览器在解析阶段就获知能力。
- 首次访问：首次访问可能先走较低版本，后续请求再升级到较新版本。
- 安全回退：任一环节不可用时回退到 HTTP/2 或 HTTP/1.1，页面不会因此加载失败。
- 排查顺序：先确认服务端是否声明可升级，再确认浏览器是否完成了升级。
- 缓存影响：协议版本不改变缓存键的组成，命中规则与 HTTP/1.1 下一致。

```js
// 按协议维度汇总资源数量，判断版本升级是否生效
const summary = performance.getEntriesByType("resource")
  .reduce((acc, entry) => {
    const key = entry.nextHopProtocol || "unknown";
    acc[key] = (acc[key] || 0) + 1;
    return acc;
  }, {});
console.log(summary); // 例如 { h3: 42, h2: 6 }
```

> [!TIP]
> **建议内容**：排查协议升级问题时先看 Resource Timing 的 nextHopProtocol，再区分是服务端未声明还是浏览器未升级成功。

**速记**：浏览器按服务端声明逐级尝试，任一环节不可用即回退到较低版本。



### 连接复用与域名分片

连接的建立成本决定要不要复用，协议版本又决定资源该如何分布到域名上。这一节把两者放在一起看。

#### 连接复用与连接池

**连接复用（connection reuse）**：是在请求之间保留已建立的连接，省去重复的 DNS、TCP 与 TLS 开销。**连接池**：是网络服务按源分组的连接集合，并对同时打开的连接数加以限制。

- 按源分组：连接以源为键管理，跨源不能复用同一条连接。
- 空闲超时：空闲连接在一段时间后被关闭，超时取值由服务端与浏览器共同决定。
- 受控首部：Connection 与 Keep-Alive 不允许脚本改写，复用策略由浏览器决定。
- 收益差异：HTTP/1.1 下复用减少排队，HTTP/2 与 HTTP/3 下复用主要省去建连往返。
- 与协议的配合：HTTP/2 与 HTTP/3 下每个源的连接数很少，连接池的管理成本随之下降。
- 复用边界：同源判断依据协议、主机与端口三者，任一不同即为不同源。

```js
// connectStart 与 connectEnd 相等说明当前请求复用了已有连接
performance.getEntriesByType("resource").forEach((entry) => {
  const reused = entry.connectStart === entry.connectEnd;
  console.log(entry.name, reused ? "复用已有连接" : "新建连接");
});
```

> 连接池按源隔离是安全模型的延伸：跨源复用连接会让响应归属难以校验，因此被禁止。

**速记**：连接按源分组复用，省去重复握手；跨源不能共用连接。



#### 域名分片与其代价

**域名分片（domain sharding）**：是把同一站点的资源分散到多个域名下，使同时打开的连接数突破单域上限的做法。

- 动机：HTTP/1.1 下并发连接数受限于单域，多个域名等于多份并发配额。
- 建连成本：每个域名都要各自付出 DNS、TCP 与 TLS 成本，连接池与缓存条目随之增多。
- 与多路复用冲突：HTTP/2 与 HTTP/3 下一条连接即可并行，额外域名反而拆散连接。
- 收益变化：分片削弱首部压缩与流管理的整体收益，从优化手段变为反模式。
- 历史场景：分片域名常与不带 Cookie 的静态域名配合使用，以减少请求首部的体积。

```bash
# 观察同一站点分布在不同域名下时的建连次数（示意）
curl -s -o /dev/null -w "%{num_connects}\n" https://static.example.com/logo.png
curl -s -o /dev/null -w "%{num_connects}\n" https://cdn.example.com/app.js
```

> [!WARNING]
> **警告内容**：在已启用 HTTP/2 或 HTTP/3 的站点上继续做域名分片，会拆散连接并放大建连开销，同时削弱首部压缩的收益。

**速记**：域名分片只在 HTTP/1.1 下有意义，多路复用时代它变成负担。



#### 协议版本对资源组织方式的影响

**资源组织方式**：是资源在域名、文件与请求数量上的分布策略，与所用协议版本的瓶颈相互对应。

- HTTP/1.1 时代：瓶颈是连接数与排队，策略偏向合并文件、内联内容、分散域名。
- HTTP/2 之后：瓶颈变成单连接利用率，策略偏向细粒度拆分以保住缓存粒度。
- HTTP/3 之后：传输层阻塞进一步减弱，策略重心回到缓存分层与按需加载。
- 判断依据：先确认线上实际使用的协议，再决定是否沿用旧的合并与分片习惯。
- 验收方式：改动资源组织方式后，对比协议分布与关键资源的加载时序，确认收益来自何处。

```js
// 确认线上协议分布，作为是否调整资源组织方式的依据
const versions = performance.getEntriesByType("resource")
  .map((entry) => entry.nextHopProtocol)
  .filter((value, index, all) => all.indexOf(value) === index)
  .sort();
console.log(versions); // 例如 ["h2"] 或 ["h2", "h3"]
```

> 协议升级不会自动带来收益：沿用为 HTTP/1.1 设计的合并与分片策略，往往抵消掉多路复用与首部压缩的效果。

**速记**：先按实际协议判断瓶颈，再决定合并还是拆分、单域还是分片。
