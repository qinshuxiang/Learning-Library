## HTML 解析与 DOM 树构建

**HTML 解析（HTML parsing）**：是把字节流形式的 HTML 文档转换成 DOM 树（document object model，文档对象模型）的过程，由词法分析与语法分析两个协作阶段完成，运行在渲染进程的主线程上。

本篇讨论解析阶段本身：字符如何被切成标记、标记如何被组装成树、脚本为何会中断解析、defer 与 async 与模块脚本如何改变中断时机，以及加载事件在这些工作结束后按什么顺序触发。DOM 的查询与修改方法属于运行时 API，归 前端/JavaScript 主题第 9 篇 DOM 操作，本篇不重复其用法。

### 解析器与词法与语法分析

解析 HTML 需要先回答两个问题：一段字符流由哪些构件组成，这些构件如何嵌套成一棵树。前者是词法分析，后者是语法分析。

浏览器把两步拆成两个独立推进的组件，因为它们的性质不同：标记化是流式的字符到标记的转换，树构建是带状态的标记到节点的转换，前者不关心上下文，后者的每一步判断都依赖当前状态。

#### 标记化与词法分析

**标记化（tokenization）**：是把字符流按 HTML 的书写规则切分为标记（token）的过程，属于词法分析（lexical analysis），执行者是标记化器（tokenizer）。

- 输入：解码后的字符流，编码由响应头、字节顺序标记或文档内的元信息声明决定。
- 输出：标记序列，常见类型有文档类型声明、开始标签、结束标签、字符、注释与结束标记。
- 驱动方式：有限状态机，读到不同字符切换到不同状态，例如标签名状态、属性名状态、属性值状态。
- 判定边界：元素能否省略结束标签由树构建阶段决定，标记化阶段不判定嵌套合法性。

```js
// 标记序列的形状示意，用于说明该阶段的产物
const tokenStream = [
  { type: "doctype", name: "html" },
  { type: "startTag", name: "p", attrs: {} },
  { type: "character", data: "正文" },
  { type: "endTag", name: "p" },
  { type: "eof" }
];
console.log(tokenStream.length); // 5
```

> 标记化只负责切分：切出结束标签后是否与开放元素栈顶匹配，留给树构建器判断。

**速记**：标记化用状态机把字符流切成标记序列，不判定嵌套是否合法。



#### 树构建器与语法分析

**树构建（tree construction）**：是把标记序列组装成 DOM 树的步骤，属于语法分析（syntactic analysis），执行者是树构建器（tree builder）。

- 状态：树构建器维护开放元素栈（stack of open elements）与当前插入模式（insertion mode），二者共同决定下一个标记的处理方式。
- 动作：开始标签创建元素并入栈，结束标签按规则弹栈，字符插入到栈顶元素之下。
- 与上下文无关文法的差异：合法结构依赖当前插入模式，无法用一套固定的产生式覆盖，实现上是状态机加按上下文切换的规则集。
- 产物：Document 对象与其中的元素树，节点对象在解析过程中即可由脚本访问。

```js
console.log(document.documentElement.nodeName); // "HTML"
console.log(document.head.parentNode === document.documentElement); // true
```

> 语法分析不是先验证全文再建树，而是边读边建：任何时刻已解析的部分都已经存在于 DOM 中。

**速记**：树构建器以开放元素栈与插入模式为状态，把标记组装成 DOM 树。



#### 容错解析与错误恢复

**容错解析（error recovery）**：是解析器遇到不合规范的标记时按规范预设规则修复并继续解析的行为，HTML 解析不会因语法错误中止文档加载。

- 未闭合元素：开始标签未闭合时，后续结束标签按开放元素栈逐层回退。
- 交叉嵌套：错位的嵌套被拆分成合法嵌套，段落元素内的块级元素会隐式关闭段落。
- 非法属性：无法解析的属性被丢弃，其后的属性继续读取。
- 结果一致：修复规则写在同一份规范里，同一份错误文档在各浏览器中产生相同的 DOM 树。

```html
<ul>
  <li>第一项
  <li>第二项
  <strong>加粗<b>与斜体</strong></b>
</ul>
```

> 容错规则解释了畸形 HTML 仍可渲染的原因，但不代表可以依赖修复结果书写结构混乱的文档。

**速记**：解析器遇错即按规范修复并继续，畸形文档不会中断加载。



#### 编码判定与解码时机

**编码判定（encoding sniffing）**：是解析器把字节转换成字符之前确定所用字符编码的过程，判定顺序为字节顺序标记、传输层声明的字符集、文档内的元信息声明，最后回落到规范推荐的回退编码。

- 字节顺序标记：位于字节流最前的标记直接决定编码，优先级最高。
- 传输层声明：响应头中的字符集参数优先于文档内的元信息声明。
- 元信息声明：只在文档靠前位置有效，解析器读到它之前已经按前述规则开始解码。
- 回退编码：前述规则都得不出结论时使用规范推荐的回退编码 UTF-8。
- 错误的后果：解码结果错误会让标记切分整体错位，DOM 结构与预期相差甚远。

```js
// 查询浏览器实际采用的编码
console.log(document.characterSet);  // "UTF-8"
console.log(document.inputEncoding); // "UTF-8"，同一信息的兼容写法
```

> 出现乱码或结构错位时，应先核对响应头与元信息声明是否一致，而不是检查标签嵌套。

**速记**：编码按字节顺序标记、传输层声明、元信息声明的顺序判定，回退值为 UTF-8。



### DOM 树的构建过程

解析器的产物是一棵树，树上每个节点都对应规范中的接口。理解构建过程需要先明确节点类型的划分，再明确树构建器在不同上下文下如何决定节点的挂载位置，最后理解「边解析边可用」这一性质对脚本的影响。

#### Document 与节点类型

**DOM（Document Object Model，文档对象模型）**：是把文档表示为节点树并允许脚本读写这棵树的接口规范，由 WHATWG 维护并持续修订。

- 接口层次：Node 是基础接口，Element、Text、Comment、Document、DocumentFragment 均由 Node 派生。
- 节点类型：元素的 nodeType 为 1，文本节点为 3，注释节点为 8，文档节点为 9。
- 分工：Element 承载标签名与属性，Text 承载字符数据，二者都是独立节点，元素之间的空白同样构成文本节点。
- 与渲染的关系：元素与文本参与样式计算，注释与文档类型节点不参与渲染。

```js
console.log(document.documentElement.nodeType); // 1
console.log(document.body.firstChild.nodeName); // "#text"
```

> 空白文本节点的存在是子节点数量与预期不符的常见来源：查询接口只返回元素，而遍历子节点会连同文本与注释一起返回。

**速记**：DOM 树由 Node 派生的多类节点构成，空白也是文本节点。



#### 树构建器的插入模式

**插入模式（insertion mode）**：是树构建器的一组上下文状态，每种模式规定当前标记应当插入到哪个位置，常见取值对应文档初始、文档头部、文档主体、表格相关等阶段。

- 切换依据：当前开放元素与刚读到的标记共同决定下一个插入模式。
- 隐式包装：表格结构缺失时解析器按规范补入隐式包装元素，最终 DOM 与书写结构并不完全一致。
- 上下文判定：同一标记在不同插入模式下产生的节点不同，这是解析结果依赖上下文的原因。
- 与脚本的关系：脚本读取到的 DOM 是解析到当前位置为止的结果，其后的内容尚不存在。

```html
<table>
  <tr><td>单元格</td></tr>
</table>
```

```js
// 解析完成后，表格行被自动包在与表格相关的包装元素中
console.log(document.querySelector("table").firstElementChild.tagName); // "TBODY"
```

> 隐式包装是解析阶段的规范行为，与后续的布局阶段无关，检查 DOM 结构时会直接看到被补入的元素。

**速记**：插入模式决定标记的挂载位置，表格等结构会补入隐式包装元素。



#### 增量构建与可查询性

**增量构建（incremental parsing）**：是解析器边接收字节边产出节点的行为，DOM 树在文档下载结束之前就已部分可用。

- 分块解码：网络数据按块解码后送入解析器，块边界与标记边界无关，跨块的中间状态保存在解析器内部。
- 可查询时机：遇到脚本时解析器先处理完已收到的标记，因此脚本能读到此前全部内容。
- 观察方式：MutationObserver 的构造函数接收 callback 参数，observe 方法接收 target 与 options 两个参数，options 中的 childList 与 subtree 决定观察范围。
- 后果：脚本位置直接改变它看到的内容，这是解析顺序敏感性的来源。

```js
const observer = new MutationObserver((records) => {
  console.log(records.length); // 每次回调收到一批变更记录
});
observer.observe(document.body, { childList: true, subtree: true });
```

> 变更记录在同一次回调中成批送达，回调的调度属于微任务机制，详见 前端/JavaScript 主题第 31 篇 async、await 与事件循环。

**速记**：DOM 边解析边生成，脚本只能看到它之前已解析的节点。



### 解析中断与脚本阻塞

树构建是单线程的串行过程，脚本执行需要同一根线程。解析过程一旦遇到脚本，两者的串行性就表现为互相等待。本模块讨论这种等待的成因、代价与缓解手段。

#### 脚本为何阻塞解析

**经典脚本（classic script）**：是未声明模块类型的脚本。**解析阻塞（parser blocking）**：是经典脚本在下载与执行期间暂停树构建器继续处理标记的行为。

- 原因：脚本可能调用 document.write 向输入流追加内容，也可能读取或修改 DOM，解析器无法在脚本执行期间安全推进。
- 代价：停顿时间包含脚本的下载时间与执行时间，外链脚本的网络延迟会直接计入首屏时间。
- 范围：只阻塞树构建，标记化产生的待处理标记排队等待。
- 位置影响：脚本之前的节点已可用，脚本之后的节点在脚本执行结束前不存在。

```html
<!-- 头部没有 defer 的经典脚本会让解析在此处暂停 -->
<head>
  <script src="/analytics.js"></script>
</head>
```

> [!WARNING]
> **警告内容**：解析期间调用 document.write 会把内容插入当前位置，而解析结束后再调用会清空整个文档，动态插入内容应改用 DOM 方法。

**速记**：经典脚本执行期间树构建暂停，停顿包含下载与执行两段耗时。



#### 预加载扫描器

**预加载扫描器（preload scanner）**：是主解析器被阻塞时代替它继续扫描后续标记、提前发起子资源请求的轻量扫描器，也称推测性解析器（speculative parser）。

- 工作方式：只识别影响资源加载的标记与属性，例如脚本、样式表、图片的地址属性，不构建 DOM。
- 收益：解析阻塞期间后续资源的下载已经并行开始，等待时间被重叠。
- 边界：扫描器不能执行脚本，脚本运行时才产生的地址不会被它发现。
- 布局影响：把关键资源尽量前移，可以让扫描器更早发出请求。

```html
<!-- head 中的脚本阻塞解析时，扫描器仍会提前发现后续资源 -->
<link rel="stylesheet" href="/main.css">
<img src="/hero.png" alt="首屏图">
```

> 扫描器只做资源发现的加速，它不改变解析结果，也不影响脚本执行顺序。

**速记**：预加载扫描器在解析阻塞期间提前发现并请求后续子资源。



#### 样式表对脚本的连带阻塞

**样式与脚本的连带阻塞**：是外链样式表尚未就绪时紧随其后的脚本不执行、进而延长解析停顿的现象。

- 规则：脚本可能读取元素的最终样式，浏览器会在执行脚本前等待此前已出现的样式表加载并解析完毕。
- 连带效果：样式表下载缓慢时，脚本之后的解析段一并延后。
- 不涉及的范围：样式表本身不阻塞 HTML 解析，只阻塞脚本执行与首屏渲染。
- 应对思路：把不依赖样式的脚本与样式表解耦，或改变脚本的加载方式。

```html
<link rel="stylesheet" href="/slow.css">
<script src="/app.js"></script>
<!-- app.js 会等待 slow.css 就绪后才执行 -->
```

> [!NOTE]
> **提醒内容**：等待样式表再执行脚本是规范要求的行为，用于保证脚本读到一致的样式结果，它不因浏览器实现不同而改变。

**速记**：样式表不阻塞解析却阻塞脚本，脚本又被解析等待，形成连带延后。



### defer 与 async 与模块脚本

脚本阻塞解析的根源是下载与执行都发生在解析途中。defer 与 async 把下载从解析路径上摘出，模块脚本则把延迟执行作为默认行为。三个属性的差别集中在两件事：下载是否并行、执行时机是否固定。

#### defer 的语义与执行时机

**defer**：是外链经典脚本上的布尔属性，表示脚本在后台下载，并在文档解析完成后、DOMContentLoaded 之前按文档顺序执行。

- 下载：与解析并行，不阻塞树构建。
- 执行：解析结束后按脚本在文档中出现的顺序依次执行，顺序有保证。
- 适用：多个脚本之间存在依赖关系且都需要完整 DOM 时使用。
- 限制：只对外链脚本生效，写在无 src 的内联脚本上会被忽略。
- 等待项：defer 脚本同样要等待此前的样式表就绪。

```html
<script src="/vendor.js" defer></script>
<script src="/app.js" defer></script>
<!-- 执行顺序固定为 vendor.js、app.js -->
```

> defer 保留了书写顺序这一信息，因此它比 async 更适合承担应用入口的角色。

**速记**：defer 并行下载、解析后按书写顺序执行、在 DOMContentLoaded 之前。



#### async 的语义与适用场景

**async**：是外链脚本上的布尔属性，表示脚本在后台下载并在下载完成后立即执行，执行时刻与解析进度无关。

- 顺序：先下载完成者先执行，多个 async 脚本之间没有顺序保证。
- 与解析的关系：下载期间不阻塞解析，执行瞬间仍会占用主线程并暂停解析。
- 与事件的关系：DOMContentLoaded 不等待 async 脚本，事件可能在其执行之前触发。
- 适用：相互独立、不依赖 DOM 完整性的脚本，例如统计与埋点。

```html
<script src="/analytics.js" async></script>
<script src="/chat-widget.js" async></script>
```

> [!CAUTION]
> **注意内容**：async 脚本可能在任意时刻执行，其中直接访问文档后部的元素可能取到空值，取值前需要判空或改用 defer。

**速记**：async 并行下载、下载完即执行、顺序不保证、不被 DOMContentLoaded 等待。



#### 模块脚本的默认延迟

**模块脚本（module script）**：是 type 属性取值为 module 的脚本，默认行为等同于 defer，并按依赖关系决定执行顺序。

- 默认延迟：不加 async 时在解析完成后执行，不阻塞解析。
- 依赖顺序：模块之间的执行顺序由 import 关系决定，而不是书写顺序。
- 执行环境：模块代码始终以严格模式运行，顶层声明不进入全局作用域。
- 内联模块：内联的模块脚本同样是延迟执行，这一点与内联经典脚本不同。
- 加 async：声明 async 后，模块也改为下载完成即执行。

```html
<script type="module" src="/main.js"></script>
<script type="module">
  import { initChart } from "/chart.js";
  initChart();
</script>
```

> 模块脚本的加载受同源策略与 MIME 类型约束，以文件协议直接打开本地页面时通常会被拒绝执行。

**速记**：模块脚本默认延迟、按依赖顺序执行、始终运行在严格模式下。



#### 三种加载方式的对比与选择

**加载方式选择**：是根据脚本与 DOM、与其他脚本之间的依赖关系，在经典脚本、defer、async 与模块脚本之间取舍的过程。

- 需要完整 DOM 且有顺序依赖：使用 defer。
- 需要完整 DOM 且无顺序依赖：使用 async，或同样使用 defer。
- 不依赖 DOM 且希望尽早执行：使用 async，例如错误上报与埋点。
- 存在模块依赖关系：使用模块脚本，执行顺序由 import 关系决定。
- 内联脚本：只能在书写位置立即执行，需要延迟时应改写为外链并加 defer。

```html
<!-- 同一份文档中四种加载方式的书写形式 -->
<script src="/immediate.js"></script>
<script src="/ordered.js" defer></script>
<script src="/independent.js" async></script>
<script type="module" src="/app.js"></script>
```

> 四种方式的差别可归纳为两个问题：下载是否占用解析时间、执行时刻是否可预测。defer 与模块脚本的回答是不占用且可预测，async 的回答是不占用但不可预测。

**速记**：有顺序依赖用 defer，无依赖且求早执行用 async，有模块依赖用模块脚本。



### 事件与 DOMContentLoaded 的时机

解析与脚本执行的顺序最终体现在事件上。加载相关事件把「结构可用」与「资源就绪」两个阶段分开报告，理解它们的触发条件才能选对监听时机。

#### 加载相关事件的顺序

**文档加载事件序列**：是文档从解析开始到全部资源就绪期间按固定顺序发生的一组状态变化与事件。

- 状态变化：document.readyState 依次取 loading、interactive、complete 三个值，每次变化触发 readystatechange。
- 事件顺序：解析结束并将状态置为 interactive 后触发 DOMContentLoaded，全部子资源就绪并将状态置为 complete 后触发 load。
- 阻塞项：DOMContentLoaded 之前要执行完 defer 脚本与模块脚本；load 之前要加载完图片、样式表、字体等子资源。
- 触发对象：DOMContentLoaded 在 document 上触发，load 在 window 上触发。

```js
document.addEventListener("readystatechange", () => {
  console.log(document.readyState); // loading、interactive、complete 依次出现
});
window.addEventListener("load", () => {
  console.log(document.readyState); // complete
});
```

> readystatechange 的触发次数不固定，判断当前阶段应以 readyState 的取值为准，而不是回调次数。

**速记**：状态先 interactive 后 complete，事件先 DOMContentLoaded 后 load。



#### DOMContentLoaded 与 load 的触发条件

**DOMContentLoaded**：是在文档解析完成且延迟脚本执行完毕后于 document 上触发的事件。**load**：是在文档及其全部依赖资源加载完成后于 window 上触发的事件。

- DOMContentLoaded 的条件：树构建结束、defer 脚本与模块脚本执行结束，不等图片与字体。
- 例外情况：解析完成前文档被替换时事件不再触发。
- load 的条件：所有子资源加载结束，加载失败也视为结束。
- 选择依据：需要尽早访问 DOM 时监听 DOMContentLoaded，需要完整加载耗时或依赖图片尺寸时监听 load。
- 与交互的关系：可交互时间晚于 DOMContentLoaded，因为交互还要求主线程空闲（详见本主题第 9 篇 事件循环与渲染时机）。

```js
document.addEventListener("DOMContentLoaded", () => {
  console.log(document.readyState); // interactive
});
window.addEventListener("load", () => {
  console.log(document.readyState); // complete
});
```

> 监听器要在事件触发之前注册，注册晚于触发时回调不会补执行，此时可用 readyState 判断当前阶段。

**速记**：DOMContentLoaded 等解析与延迟脚本，load 还要等全部子资源。



#### 事件时序的观测方式

**导航计时（navigation timing）**：是 Performance API 中记录导航各阶段时间戳的一组条目，用于核对事件的实际触发时刻。

- 获取方式：调用 performance.getEntriesByType 并传入 "navigation"，得到首条导航条目。
- 关键字段：domInteractive、domContentLoadedEventStart、domContentLoadedEventEnd、loadEventStart、loadEventEnd。
- 口径：全部时间戳以从导航开始计的毫秒数（ms）表示。
- 用途：对比 domContentLoadedEventEnd 与 loadEventEnd 的差值，可判断延迟来自解析与脚本还是来自子资源加载。

```js
const [navigation] = performance.getEntriesByType("navigation");
console.log(navigation.domInteractive);           // 412.3
console.log(navigation.domContentLoadedEventEnd); // 430.8
console.log(navigation.loadEventEnd);             // 1024.6
```

> [!TIP]
> **建议内容**：核对解析与事件时序时优先读取导航计时条目，它来自浏览器内部的阶段记录，比在回调中打印时间戳更能反映真实顺序。

**速记**：导航计时条目给出各阶段的毫秒时间戳，可用于核对事件时序。
