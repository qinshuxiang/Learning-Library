## 性能指标与优化实战

性能优化若没有统一口径就会变成各说各话：有人说页面很快，有人说首屏很慢，分歧往往来自度量方式不同。本篇先确立指标与度量体系，再给出可执行的优化清单，最后落到两个日常工具的使用方法。

贯穿全篇的一条原则：先度量、再优化、再验证。没有基线数据的优化无法判断收益，也无法阻止后续退化。

### 性能度量体系与核心指标

度量体系回答「用什么数据判断快慢」。实验室数据与真实用户数据各司其职，核心指标则把「快」拆成加载、交互与视觉稳定三个可测量的侧面。

#### 实验室数据与真实用户数据

**实验室数据（lab data）** 与 **真实用户数据（field data，即真实用户监控 RUM）** 是什么：前者是在固定设备与网络条件下用工具跑出的可复现结果，后者是采集真实访问者指标得到的结果。

- 实验室：条件可控、可复现，能精确复现某个问题，但不代表真实用户分布。
- 真实用户：覆盖真实设备、网络与地域差异，能反映长尾用户的实际体验。
- 分工：实验室用于定位与回归，真实用户用于判定影响面与是否达标。
- 聚合口径：真实用户数据通常取第 75 百分位作为达标判定依据。
- 差异来源：实验室常低于真实值，因为真实设备更慢、网络更差。

> 判定站点是否达标看真实用户数据的第 75 百分位；实验室数据只用于定位问题与防止回归。

**速记**：实验室数据用于定位，真实用户数据用于判定，达标看第 75 百分位。



#### Core Web Vitals 的构成

**Core Web Vitals（核心网页指标）** 是什么：是一组由浏览器厂商提出、用于描述用户体验质量的指标集合，包含加载、交互与视觉稳定性三个方面。

- LCP：最大内容绘制，衡量主内容何时渲染完成，属于加载体验。
- INP：交互到下次绘制，衡量交互响应速度，属于交互体验。
- CLS：累积布局偏移，衡量非预期偏移，属于视觉稳定性。
- 演进：INP 取代了此前的 FID（首次输入延迟），FID 只测首次输入的延迟部分。
- 辅助指标：FCP、TTFB 与 TBT 不在核心集合内，但常用于诊断与回归。

> 三项核心指标是并列关系，任何一项不达标都视为体验未达标，不存在用一项换另一项的说法。

**速记**：核心指标为 LCP、INP 与 CLS，分别对应加载、交互与视觉稳定性。



#### 指标口径与统计方式

**指标口径** 是什么：是指标的时间起点、单位与聚合方式，口径不一致的数据无法比较。

- 时间口径：时间类指标以从导航开始计的毫秒为单位，不从页面可见起算。
- 百分位：第 75 百分位表示按访问量排序后有 75% 的访问不差于该值。
- 分组：按页面、设备类型与连接类型分组统计，平均值会掩盖长尾。
- 会话窗口：CLS 与 INP 在页面整个生命周期内累积，单页应用需按路由划分窗口。
- 采样：上报应抽样与聚合，逐条上报会带来额外开销并影响被测指标本身。

> [!NOTE]
> **提醒内容**：同一份数据用平均值与第 75 百分位会得出不同结论，对外报告与内部看板必须写明所用口径。

**速记**：口径包含起点、单位与聚合方式，第 75 百分位是通行的达标判定口径。



#### 导航类型与指标差异

**导航类型** 是什么：是本次页面进入的方式，不同方式对应不同的起点与缓存状态，指标不可直接横向比较。

- navigate：常规进入，指标最完整，是统计的主要对象。
- reload：刷新，可能命中缓存而偏快，需单独看待。
- back_forward：前进后退，可能直接来自往返缓存（back/forward cache），部分指标缺失。
- prerender：预渲染命中时起点与其他类型不同。
- 处理方式：区分导航类型后再聚合，避免把往返缓存带来的快误判为优化成果。

```js
const [nav] = performance.getEntriesByType('navigation');
console.log(nav.type);          // navigate / reload / back_forward / prerender
console.log(nav.responseStart); // TTFB，从导航开始计的毫秒
```

**速记**：导航类型决定起点与缓存状态，统计前须分类，往返缓存不算优化成果。



### 关键指标的含义与阈值

该模块逐个说明指标的构成、触发条件与公认阈值，并给出可直接在控制台运行的采集片段。阈值只使用业界通行的三档口径：良好、需改进、差。

#### LCP：最大内容绘制

**LCP（Largest Contentful Paint，最大内容绘制）** 是什么：是视口内面积最大的内容元素完成绘制的时间点，用于衡量主内容何时对用户可见。

- 元素范围：图片、视频封面、块级文本容器等可被测量面积的内容元素。
- 阈值：不超过 2.5 s 为良好，不超过 4 s 为需改进，超过 4 s 为差。
- 影响来源：首字节时间、关键资源的加载优先级、阻塞渲染的样式与脚本。
- 更新机制：页面持续上报新的候选项，直到用户发生交互为止。
- 相关条目：largest-contentful-paint 条目带 startTime、element 与 size 等字段。

```js
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log(last.startTime, last.element); // 绘制时间与命中的元素
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

> 图片类 LCP 元素还应关注加载延迟与尺寸是否匹配，文本类则更多受字体与样式阻塞影响。

**速记**：LCP 是最大内容元素的绘制时间点，不超过 2.5 s 为良好。



#### INP：交互到下次绘制

**INP（Interaction to Next Paint，交互到下次绘制）** 是什么：是页面生命周期内交互响应耗时的代表值，取各次交互中最慢的一批作为判定依据。

- 三段构成：输入延迟、事件处理时间、下次绘制前的呈现延迟，三者之和为单次交互耗时。
- 阈值：不超过 200 ms 为良好，不超过 500 ms 为需改进，超过 500 ms 为差。
- 判定方式：按交互分组统计，真实用户数据取第 75 百分位的近似值。
- 与 FID 区别：FID 只测首次输入的延迟，INP 覆盖全部交互与整条响应链路。
- 主要来源：长任务占用主线程，机制详见本主题第 9 篇 事件循环与渲染时机。

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.interactionId) {
      console.log(entry.name, entry.duration); // 交互事件名与耗时
    }
  }
}).observe({ type: 'event', buffered: true, durationThreshold: 16 });
```

> [!WARNING]
> **警告内容**：只在首次点击上做优化无法改善 INP，滚动、输入与键盘操作产生的交互同样计入判定。

**速记**：INP 取交互响应耗时的代表值，不超过 200 ms 为良好，长任务是主要来源。



#### CLS：累积布局偏移

**CLS（Cumulative Layout Shift，累积布局偏移）** 是什么：是对页面整个生命周期内非预期布局偏移的累加得分，得分由偏移影响区域与移动距离共同决定。

- 阈值：不超过 0.1 为良好，不超过 0.25 为需改进，超过 0.25 为差。
- 排除项：用户交互后短时间内产生的偏移不计入，条目上表现为 hadRecentInput 为真。
- 常见成因：未声明尺寸的图片与广告位、动态插入的内容、字体切换导致的回流式移动。
- 采集方式：订阅 layout-shift 条目，过滤掉 hadRecentInput 为真的条目后累加。
- 归因手段：条目带 sources 字段，可定位到发生偏移的元素。

```js
let clsValue = 0;

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) clsValue += entry.value;
  }
  console.log(clsValue);
}).observe({ type: 'layout-shift', buffered: true });
```

> 为图片与视频预留宽高，是消除绝大多数偏移的最直接手段。

**速记**：CLS 累加非预期偏移，不超过 0.1 为良好，预留尺寸是最直接的改善手段。



#### FCP、TTFB 与 TBT

**FCP（First Contentful Paint，首次内容绘制）** 是什么：是视口内首次出现文本或图片等内容的时间点，表示页面开始有内容可见。

**TTFB（Time to First Byte，首字节时间）** 是什么：是从导航开始到收到响应第一个字节的时间，考核服务端处理与网络链路，不超过 800 ms 为良好。

**TBT（Total Blocking Time，总阻塞时间）** 是什么：是主线程上长任务超出 50 ms 部分的累计时长，只在实验室数据中存在。

- 条目来源：TTFB 取自 navigation 条目的 responseStart，FCP 取自 paint 条目。
- 类型判定：TTFB 偏大应查服务端与缓存，FCP 偏大应查阻塞渲染资源。
- 关系：TTFB 决定了下限，FCP 反映首个内容，TBT 反映主线程被占用程度。
- 用途区别：TBT 用于实验室定位卡顿来源，不对应真实用户阈值。

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.name, entry.startTime); // first-paint / first-contentful-paint
  }
}).observe({ type: 'paint', buffered: true });
```

> [!TIP]
> **建议内容**：把 TTFB 与 FCP 放在一起看，若两者差距很大，问题多半在阻塞渲染的资源而不是服务端。

**速记**：FCP 是首个内容可见，TTFB 良好阈值为 800 ms，TBT 只在实验室数据中使用。



### 度量方式：Performance API 与 PerformanceObserver 与真实用户监控

该模块给出采集指标的三层手段：手工打点、事件驱动的观察者，以及集成上报的监控体系。三者共用同一份浏览器时间线数据。

#### performance.mark 与 performance.measure

**performance.mark(name, options)** 是什么：是在浏览器的性能时间线上打一个命名时间点的方法，options 支持 startTime 与 detail 两个字段。

**performance.measure(name, startOrOptions, endMark)** 是什么：是计算两个时间点或两个条目之间时长的方法，结果以 measure 条目返回。

- 读取结果：performance.getEntriesByType('measure') 或 getEntriesByName(name)。
- 清理：clearMarks 与 clearMeasures 用于移除记录，避免时间线无限增长。
- 适用场景：给自定义阶段打点，如首屏接口返回、列表渲染、组件挂载。
- 注意：事件处理函数的执行时间只覆盖同步执行，异步链路的耗时需要用标记人工框定。

```js
performance.mark('list-render-start');
renderList(items);
performance.mark('list-render-end');
performance.measure('list-render', 'list-render-start', 'list-render-end');

const [measure] = performance.getEntriesByName('list-render');
console.log(measure.duration); // 渲染耗时，单位毫秒
```

**速记**：mark 打时间点、measure 算时长，结果以 measure 条目读取，用完应清理。



#### PerformanceObserver 与条目类型

**PerformanceObserver(callback, options)** 是什么：是订阅性能条目并接收回调的接口，callback 收到条目列表与观察者实例两个参数。

- 构造选项：options 可传 type 或 entryTypes 指定关注范围；entryTypes 一次订阅多种类型。
- 订阅方式：observer.observe({ type, buffered }) 在实例上开启订阅。
- buffered 字段：为 true 时补发订阅之前已产生的条目，适合较晚注册的采集脚本。
- 支持检测：PerformanceObserver.supportedEntryTypes 列出当前浏览器支持的条目类型。
- 结束观察：disconnect() 停止回调，takeRecords() 取走尚未处理的条目。

```js
console.log(PerformanceObserver.supportedEntryTypes.includes('layout-shift'));

for (const entry of performance.getEntriesByType('resource')) {
  console.log(entry.name, entry.duration); // 资源地址与加载耗时
}
```

**速记**：PerformanceObserver 按 type 或 entryTypes 订阅条目，buffered 补发历史条目。



#### 关键指标的采集

**关键指标采集** 是什么：是用观察者持续记录 LCP、CLS 与交互条目，并在页面离开前汇总出最终值的过程。

- 汇总时机：LCP 与 CLS 在生命周期内持续变化，需在页面隐藏时的回调中提交。
- 中间值处理：回调会多次触发，需保留最新值而非累加，CLS 除外。
- 缓存边界：已经上报过的值不应重复上报，可记录上次上报值做差。
- 单页应用：路由切换不产生新的 navigation 条目，需自行划分采集窗口。
- 校验：采集值与生产报表差异较大时，先检查上报时机与采样率。

```js
let lcpValue = 0;

new PerformanceObserver((list) => {
  const entries = list.getEntries();
  lcpValue = entries[entries.length - 1].startTime;
}).observe({ type: 'largest-contentful-paint', buffered: true });

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') console.log('最终 LCP', lcpValue);
});
```

**速记**：指标值在页面隐藏时汇总上报，回调多次触发时保留最新值。



#### 上报：sendBeacon 与真实用户监控

**真实用户监控（real user monitoring，RUM）** 是什么：是在页面内采集指标并上报到服务端、再由服务端聚合成现场数据的整套体系。

- 采集：用 PerformanceObserver 或 web-vitals 这类封装库得到指标值。
- 上报时机：页面隐藏与卸载阶段仍需可靠投递，可用 navigator.sendBeacon(url, data) 发送。
- 备选方案：fetch 配合 keepalive 选项，请求体会受限，适合小体积上报。
- 上下文维度：附带页面地址、设备类型、导航类型、连接类型等信息便于分群。
- 服务端聚合：按第 75 百分位与分组维度计算，形成可比较的现场数据。

```js
function reportVital(name, value) {
  const payload = JSON.stringify({ name, value, path: location.pathname });
  navigator.sendBeacon('/rum', payload);
}

reportVital('lcp', 2100); // 实际使用中传入采集到的指标值
```

> 封装库（如 web-vitals）已处理阈值判定与生命周期边界，自行实现时应先核对其口径再替换。

**速记**：真实用户监控用 sendBeacon 在页面隐藏时上报，服务端按分组与百分位聚合。



### 优化清单：加载、渲染、交互三条线

该模块把指标映射为可执行动作。三条线分别对应加载阶段、渲染阶段与交互阶段，同一项指标通常需要多条线共同改善。

#### 加载线：从 TTFB 到首屏

**加载线** 是什么：是围绕首字节时间与首屏资源到达顺序展开的一组优化动作。

- 首字节：TTFB 偏高时先查服务端处理与缓存命中，浏览器侧只看是否命中强缓存、是否走了协商请求（详见本主题第 4 篇 浏览器缓存机制）。
- 传输体积：启用文本压缩、按需加载图片与脚本，避免首屏加载全部资源。
- 关键资源：内联首屏所需的关键样式，延后非关键脚本，保证首屏资源最先到达。
- 图片：按显示尺寸输出正确尺寸与格式，首屏之外的图片延迟加载。
- 验证：用真实用户数据的第 75 百分位对比改动前后的 TTFB 与 LCP。

**速记**：加载线抓首字节与首屏资源顺序，服务端与传输体积的问题优先排查。



#### 资源提示：preload、prefetch、preconnect 与 fetchpriority

**资源提示** 是什么：是写在页面里、用于改变浏览器发现与调度资源顺序的若干声明，只影响调度优先级，不减少资源总量。

- preload：以较高优先级提前抓取当前页面马上要用的资源，需写明资源的类型，跨源资源还需声明凭据模式。
- prefetch：以较低优先级抓取未来导航可能用到的资源，是否命中取决于后续页面。
- preconnect：提前完成域名解析与连接建立（含传输层握手），适合确定会用到的跨源源。
- dns-prefetch：只提前做域名解析，作为 preconnect 的兜底选择。
- fetchpriority：在图片、脚本等元素上标注 high、low 或 auto，影响该请求的相对优先级。
- 取舍：提示过量会与关键资源争抢带宽，抓来不用的 preload 反而拖慢首屏。

```html
<link rel="preconnect" href="https://cdn.example.com" />
<link rel="preload" as="font" type="font/woff2" href="/fonts/app.woff2" crossorigin />
<link rel="prefetch" href="/next-page.js" />
<img src="/hero.jpg" width="800" height="450" fetchpriority="high" alt="" />
```

> [!CAUTION]
> **注意内容**：为同一资源重复声明多种提示，或在首屏已紧张时大量使用 preload，会挤占关键资源带宽并让指标变差。

**速记**：资源提示只改调度顺序，preload 用于当前页、prefetch 用于后续导航、preconnect 提前建连。



#### 渲染线：关键渲染路径与 CLS

**渲染线** 是什么：是围绕关键渲染路径展开的优化动作，目标是让首个内容尽快出现且不产生视觉跳动。

- 阻塞资源：内联关键样式，非关键脚本异步加载，避免样式表长时间阻塞首次绘制。
- 布局稳定：为图片、视频与广告位预留固定尺寸或宽高比，从源头消除偏移。
- 字体：用 font-display 控制字体加载期间的表现，或选用尺寸接近的回退字体。
- 首屏内容：首屏元素不做延迟加载，避免 LCP 元素被人为推迟。
- 动画：只改动 transform 与 opacity，避免引发重排与重绘，成因与改写手段详见本主题第 8 篇 渲染性能：重排、重绘与合成层优化。

```css
.hero {
  aspect-ratio: 16 / 9;
  width: 100%;
}

@font-face {
  font-family: "AppFont";
  src: url("/fonts/app.woff2") format("woff2");
  font-display: swap;
}
```

> 渲染线的收益通常体现在 LCP 与 CLS 上；交互指标的改善要回到主线程调度去解决。

**速记**：渲染线内联关键样式、预留元素尺寸，动画只改 transform 与 opacity。



#### 交互线：长任务与 INP

**交互线** 是什么：是围绕主线程占用展开的优化动作，目标是缩短交互发生到画面更新之间的耗时。

- 长任务：主线程上连续占用超过 50 ms 的任务，是 INP 偏差的主要来源，调度机制详见本主题第 9 篇 事件循环与渲染时机。
- 任务拆分：把大任务切成小段，在段与段之间让出主线程。
- 脚本成本：解析与执行成本直接计入交互耗时，构建期的代码分割与体积优化归 前端/构建工具 主题。
- 事件处理：避免在输入与滚动事件的回调里做重计算或强制同步布局。
- 归因：用 event 条目的 interactionId 把慢交互对应到具体元素与事件类型。

```js
async function handleSearchInput(query) {
  const chunks = splitIntoChunks(buildSearchIndex(query));
  for (const chunk of chunks) {
    renderSearchChunk(chunk);
    await new Promise((resolve) => setTimeout(resolve, 0));
  }
}
```

**速记**：交互线拆长任务、压脚本成本，用 interactionId 把慢交互归因到具体事件。



### 工具实操：Lighthouse 与性能面板

该模块讲清两个工具能回答什么问题。Lighthouse 给出一份带评分的实验室报告，性能面板给出一次录制内的时间线细节，二者互补而不互相替代。

#### Lighthouse 的类别与评分

**Lighthouse** 是什么：是一套对页面进行实验室审计并生成报告的工具，可从开发者工具面板、命令行或持续集成中运行。

- 审计类别：性能、可访问性、最佳实践与 SEO，各自独立评分。
- 性能指标：报告包含 FCP、LCP、TBT、CLS 与速度指数等指标，并按权重合成性能分。
- 运行条件：固定设备与网络模拟，便于复现，但不能代表真实用户分布。
- 波动性：单次运行存在波动，宜多次运行取中位数或对比同一环境下的多次结果。
- 版本差异：评分权重与指标组成随版本调整，跨版本比较分数意义有限。

```bash
# 用命令行跑一次审计并查看报告
npx lighthouse https://example.com --view
# 报告生成后自动在浏览器中打开
```

**速记**：Lighthouse 是实验室审计工具，按类别评分，运行条件固定但结果有波动。



#### 指标解读与诊断项

**诊断项** 是什么：是报告中解释指标为何偏低的附加说明，分为机会与诊断两类。

- 机会类：指出可节省的字节与毫秒，例如未使用的脚本、未压缩的图片、阻塞渲染的资源。
- 诊断类：补充上下文，例如过大的文档结构、过多的主线程工作、缓存策略问题。
- 阅读顺序：先看指标确认差在哪，再看诊断项确认为什么，最后看机会类估算收益。
- 定位与修复：按影响面与修复成本排序，先处理影响最大且可稳定复现的项。
- 校验：修复后用真实用户数据验证，而不是只看报告分数是否上升。

```text
Performance 68
  First Contentful Paint    1.8 s
  Largest Contentful Paint  3.4 s
  Total Blocking Time     620 ms
  Cumulative Layout Shift   0.12
（示例报告片段，数值随环境变化）
```

**速记**：先看指标、再看诊断、最后估收益，修复效果用真实用户数据验证。



#### 性能面板的读法

**性能面板** 是什么：是开发者工具中录制并展示一次加载或交互全过程时间线的面板，用于定位具体耗时来源。

- 总览区：展示 CPU 占用随时间的变化，主线程被长时间占用的区间以醒目色块标出。
- 火焰图：展示主线程调用栈，横向宽度表示耗时，可逐层下钻到具体函数。
- 网络轨道：展示请求瀑布，用于确认关键资源是否被推迟或串行等待。
- 帧与合成信息：反映帧率与合成层情况，用于判断动画是否掉帧。
- 交互与偏移轨道：记录交互耗时与偏移发生点，用于 INP 与 CLS 的归因。

> 使用顺序是先在总览区找到异常区间，再在火焰图中定位到具体任务，最后回到代码修改。

**速记**：性能面板先看总览找区间，再用火焰图与轨道定位到具体任务与元素。



#### 现场数据与实验室数据的配合

**数据配合** 是什么：是把真实用户数据的广度与实验室数据的细节结合起来判断问题优先级的方法。

- 分工：现场数据回答有多少用户受影响，实验室数据回答为什么慢。
- 复现：按现场数据反映的设备与网络条件在性能面板中复现，避免只看平均值。
- 分群：按设备与连接类型分组查看，长尾设备往往是达标瓶颈。
- 回归：把关键指标写入持续集成，在合并前拦截明显退化，框架用法详见 前端/测试 主题。
- 验证：改动后对比同期真实用户数据的第 75 百分位，而非单次实验室结果。

> [!NOTE]
> **提醒内容**：实验室报告与现场报表的口径不同，二者直接对比数值会得出错误结论，比较应在同一口径内进行。

**速记**：现场数据定优先级，实验室数据查原因，回归与验证都看同口径数据。
