## 浏览器简介与多进程架构

**浏览器**：是运行在操作系统之上的应用软件，其职责是把地址指向的远程资源取回、解析并绘制为可交互的页面。

本篇回答架构层面的三个问题：浏览器由哪些部分组成、页面运行在哪个进程与线程里、进程之间如何隔离。渲染管线的阶段细节见本主题第 7 篇，网络协议细节见本主题第 3 篇。

### 浏览器是什么与它的组成

**浏览器组成** 是认识浏览器的起点：先明确内部有哪些模块，再理解这些模块为何被拆进不同进程。

#### 浏览器的定义与基本职责

**浏览器（browser）**：是面向最终用户的应用程序，它解析用户给出的地址、取回远程资源、把资源转换为可见且可交互的页面，并管理与页面相关的存储与安全边界。

- 地址解析：判断输入是待导航的地址还是检索词，并补全为绝对地址。
- 资源获取：发起请求、接收响应，按响应头的规则决定缓存与复用。
- 内容呈现：解析文档结构、计算样式、布局（layout，旧称回流 reflow）、绘制与合成。
- 脚本执行：为页面脚本提供宿主环境，并调度脚本与渲染的先后关系。
- 交互响应：接收输入事件并把结果反馈到页面上。
- 状态管理：保存会话、缓存与本地数据，并在源之间相互隔离。

```text
用户输入地址或点击链接
  -> 解析地址并决定导航
  -> 发起请求并接收响应
  -> 解析文档并构建 DOM 树
  -> 计算样式、布局、绘制、合成
  -> 执行脚本并响应用户输入
```

> 上述五个环节在实现上分属不同进程与线程，本主题第 2 篇（从输入 URL 到页面呈现：导航与加载流程）按时间顺序把它们串成一条完整链路。

**速记**：浏览器是取回、解析并绘制页面的应用软件，职责覆盖从地址到交互的全链路。



#### 浏览器的主要组成模块

**浏览器的主要组成模块**：是按职责划分的若干子系统，包括用户界面、浏览器引擎、渲染引擎、网络、JavaScript 引擎、UI 后端与数据存储。

- 用户界面：地址栏、书签、标签页与前进后退等控件，不参与页面内容的绘制。
- 浏览器引擎：协调各模块与各进程，管理标签页的生命周期。
- 渲染引擎：解析 HTML 与 CSS，输出页面画面，见下一节。
- 网络：发起请求、管理连接复用与缓存查找。
- JavaScript 引擎：解析并执行脚本，详见本主题第 10 篇 V8 引擎与 JavaScript 执行优化。
- UI 后端：绘制窗口与原生控件，提供跨平台的界面能力。
- 数据存储：持久化 Cookie、缓存与各类本地存储，详见本主题第 12 篇 浏览器存储机制。

```text
用户界面        地址栏、书签、标签页、前进后退
浏览器引擎      模块与进程的协调、标签页管理
渲染引擎        解析 HTML 与 CSS，输出画面
网络            请求发起、连接复用、缓存查找
JavaScript 引擎 脚本的解析与执行
UI 后端         窗口与原生控件的绘制
数据存储        Cookie、缓存与本地存储
```

> 这七个模块是逻辑划分；多进程架构把它们分配到不同进程里，模块之间因此从函数调用变为跨进程消息。

**速记**：浏览器按职责分成七个模块，多进程架构把模块分配到不同进程。



#### 浏览器与标准规范

**Web 标准**：是由标准组织维护、公开描述浏览器行为的一组规范，浏览器按规范实现，页面因此在不同的浏览器上获得一致行为。

- WHATWG：维护 HTML、DOM、Fetch、URL、Streams 等与页面直接相关的规范。
- W3C：维护 CSS、Web 性能、无障碍等规范。
- IETF：维护 HTTP、TLS、QUIC 等网络协议规范。
- TC39：维护 ECMAScript 语言规范，语言层面的用法见 前端/JavaScript 主题。
- Khronos：维护 WebGL、WebGPU 等图形接口规范。

```text
WHATWG   HTML、DOM、Fetch、URL、Streams
W3C      CSS、Web 性能、无障碍
IETF     HTTP、TLS、QUIC
TC39     ECMAScript
Khronos  WebGL、WebGPU
```

> 规范规定的是可观察行为，不规定内部实现：不同浏览器用各自的引擎实现同一份规范，性能与内存表现因此可能不同。

**速记**：标准组织定义可观察行为，浏览器用各自的引擎实现同一份规范。



### 主流浏览器与内核

**内核** 是浏览器差异的主要来源：渲染引擎决定页面如何被解析与绘制，JavaScript 引擎决定脚本如何被执行。本节先区分两款引擎的对应关系，再给出跨引擎兼容的处理方式。

#### 主流浏览器与渲染引擎

**渲染引擎（rendering engine）**：是把 HTML 与 CSS 转换为屏幕像素的核心模块，也称排版引擎，浏览器之间的渲染差异主要由它带来。**JavaScript 引擎**：是解析并执行脚本的模块，详见本主题第 10 篇。

- Blink：由 Chromium 项目维护，Chrome、Edge、Opera、Brave 等浏览器使用。
- WebKit：由苹果维护，Safari 使用；iOS 上的全部浏览器都被要求基于 WebKit。
- Gecko：由 Mozilla 维护，Firefox 使用。
- 历史引擎：Edge 早期使用的 EdgeHTML 与 IE 使用的 Trident 已停止演进。

```text
Blink   Chrome、Edge、Opera、Brave
WebKit  Safari，以及 iOS 上的全部浏览器
Gecko   Firefox
```

> 引擎与浏览器不是一一对应：Chromium 是开源项目，多个浏览器在它之上构建；同一浏览器在不同平台上也可能使用不同引擎。

**速记**：渲染引擎决定渲染差异，主流引擎是 Blink、WebKit 与 Gecko。



#### 引擎差异与兼容处理

**兼容处理**：是在不依赖浏览器身份的前提下，按能力是否存在选择代码路径的做法，也称特性检测（feature detection）。

- 特性检测：先判断接口是否为函数，再决定使用新接口还是回退方案。
- 接口签名：IntersectionObserver 的构造器接收 callback 与 options 两个参数，options 可指定 root、rootMargin 与 threshold。
- 避免嗅探：读取 navigator.userAgent 判断浏览器型号的做法会在版本更新后失效。
- 缺陷补丁：针对个别引擎的渲染缺陷写条件样式或脚本，并注明原因与移除条件。
- 语法降级：把新语法编译为旧语法由构建工具完成，不属于浏览器侧的兼容问题。

```js
// 特性检测：按能力存在与否决定走哪条分支
function createVisibilityObserver(target, onVisible) {
  if (typeof IntersectionObserver !== "function") {
    return null; // 回退：调用方改用滚动事件自行判断
  }
  return new IntersectionObserver(function handleIntersect(entries) {
    entries.forEach(function notifyVisible(entry) {
      if (entry.isIntersecting) onVisible(entry.target);
    });
  }, { threshold: 0.2 });
}
```

> [!NOTE]
> **提醒内容**：特性检测的结论只与当前浏览器是否提供该接口有关，与浏览器版本号无关，因此不会随版本更新失效。

**速记**：按能力分支而不是按浏览器身份分支，代码才经得起版本更新。



### 多进程架构与进程职责

**多进程架构**：是把浏览器拆分成多个独立进程、每个进程承担一类职责的架构；进程之间通过进程间通信（IPC，inter-process communication）交换消息，而不是共享内存。

#### 进程类型与职责划分

**进程（process）**：是操作系统分配资源的基本单位，拥有独立的地址空间与资源句柄，进程内的崩溃默认不影响其他进程。

- 浏览器进程：窗口、标签页、地址栏、书签与权限提示，并协调其他进程。
- 渲染进程：解析文档、执行脚本、计算布局与绘制，一个进程通常负责一个站点。
- GPU 进程：统一承担光栅化与合成相关的图形工作。
- 网络服务：请求的发起、连接复用与缓存查找。
- 工具进程：音频与视频解码、数据解码等可以独立运行的任务。

```text
浏览器进程  窗口、标签页、地址栏、权限，协调其他进程
渲染进程    解析文档、执行脚本、布局与绘制，通常一个站点一个进程
GPU 进程    光栅化与合成中的图形计算
网络服务    请求发起、连接复用、缓存查找
工具进程    音频、视频与数据解码等独立任务
```

> 进程划分不属于规范规定的内容，各浏览器实现不同，Chromium 的划分常被作为讨论基准。

**速记**：进程按职责划分，浏览器进程协调，渲染进程干活，GPU 与网络各司其职。



#### 浏览器进程与进程间通信

**浏览器进程（browser process）**：是浏览器的核心进程，持有窗口与标签页等全局状态。**进程间通信（IPC）**：是进程之间传递消息的机制，跨进程调用必须序列化参数并等待回复。

- 持有全局状态：标签页列表、地址栏、下载、权限与设置。
- 决定导航：收到地址变更后创建或复用渲染进程，并把请求交给网络服务。
- 代理特权操作：渲染进程申请文件访问、权限或跨源资源时，一律经浏览器进程转交。
- 通信成本：消息需要序列化与调度，高频 IPC 会带来可测量的额外开销。

```bash
# macOS 上查看浏览器的进程树：主进程与其派生的子进程
ps -ax -o pid,ppid,comm | grep -i "chrome"
```

> 进程隔离换来稳定性与安全性，代价是内存占用上升与跨进程通信开销增加，这是进程模型的长期取舍。

**速记**：浏览器进程是协调中心，跨进程访问一律经 IPC 转交。



#### 渲染进程与沙箱

**渲染进程（renderer process）**：是承载页面文档与脚本执行的进程，一个渲染进程通常对应一个站点，也可能同时承载该站点下多个同源页面。**沙箱（sandbox）**：是限制进程可访问系统资源的隔离机制，使进程无法直接读写文件系统或访问设备。

- 权限受限：渲染进程内的脚本不能直接访问本地文件与设备，需经浏览器进程代理。
- 崩溃隔离：单个渲染进程崩溃只影响其承载的标签页，其他标签页继续运行。
- 进程复用：同源页面可能共用一个进程；启用站点隔离后，跨站点内容不再共用。
- 进程数量：标签页数量、内嵌文档数量与站点数量共同决定进程数量。

```js
// 渲染进程内的脚本运行在沙箱中，没有文件系统与模块加载能力
console.log(typeof fetch);   // "function"，只提供浏览器的网络接口
console.log(typeof require); // "undefined"，页面环境没有 require
console.log(window.origin);  // "https://example.com"，当前文档的源
```

> [!IMPORTANT]
> **重要内容**：渲染进程不得直接访问文件系统与设备，任何特权操作都必须交由浏览器进程校验后执行，绕开这一层即等同于本地代码执行。

**速记**：渲染进程跑在沙箱里，特权操作一律经浏览器进程代理。



### 渲染进程内的线程分工

**线程（thread）** 是进程内的执行单元，同一进程的线程共享地址空间。渲染进程内部按工作性质切分线程：主线程承担确定性的解析、脚本与布局，合成线程与光栅线程保证滚动与动画不被主线程阻塞。

#### 主线程

**主线程（main thread）**：是渲染进程中执行脚本、解析 HTML、计算样式、布局与生成绘制指令的线程，同一时刻只执行一段任务，任务之间按队列顺序执行。

- 解析与构建：解析文档生成 DOM 树，解析样式生成样式树。
- 脚本执行：按脚本被解析到的位置与属性决定何时执行，详见本主题第 5 篇 HTML 解析与 DOM 树构建。
- 样式与布局：匹配选择器、计算层叠结果，再计算每个盒子的大小与位置。
- 绘制指令：把可见内容转换为绘制指令列表，交给光栅线程。

```js
// 主线程被占满时，输入事件与渲染帧都要排队等待
function spinMainThread(durationMs) {
  const startTime = performance.now();
  while (performance.now() - startTime < durationMs) {}
}

spinMainThread(200); // 阻塞主线程 200 ms，期间页面无法响应输入
```

> [!WARNING]
> **警告内容**：长任务指运行时间超过 50 ms 的任务，在主线程上执行长任务会造成掉帧与交互延迟，应拆分为小段或移入工作线程，调度细节见本主题第 9 篇 事件循环与渲染时机。

**速记**：主线程单执行、按顺序处理任务，长任务会同时拖慢渲染与交互。



#### 合成线程与光栅线程

**合成线程（compositor thread）**：是与主线程并行的线程，负责把已经光栅化的合成层按变换关系合成为最终画面。**光栅线程（raster thread）**：是把绘制指令转换为位图的线程，其工作可分散到多个线程并借助 GPU 完成。

- 合成线程：处理合成层的位置与透明度变化，驱动滚动与不依赖主线程的动画。
- 光栅线程：把绘制指令渲染为位图，按需光栅化可见区域。
- 并行收益：滚动与合成动画不需要等待主线程，因此主线程繁忙时页面仍能滚动。
- 边界条件：改变几何尺寸的样式会触发重新布局，必须回到主线程执行。

```text
主线程    解析、脚本、样式计算、布局、生成绘制指令
光栅线程  绘制指令 -> 位图
合成线程  合成层变换与合并，输出最终画面
GPU 进程  承担光栅化与合成中的图形计算
```

> 合成线程只能处理不改变几何结构的属性变化，凡是影响布局的改动仍要回到主线程，因此动画属性应优先选择不触发布局的属性，详见本主题第 8 篇 渲染性能：重排、重绘与合成层优化。

**速记**：合成线程与光栅线程分担合成与光栅化，滚动因此不必等主线程。



#### 工作线程与线程边界

**工作线程（worker）**：是页面创建的独立执行线程，拥有自己的全局环境与事件循环，不共享主线程的调用栈，也不能直接访问 DOM。

- 能力范围：适合纯计算、数据解析与批量处理，不适合操作页面结构。
- 通信方式：与主线程通过 postMessage 传递结构化数据，数据会被结构化克隆。
- 线程类型：Worker 与 SharedWorker 服务于页面计算，Service Worker 承担网络代理与离线能力，详见本主题第 15 篇 Service Worker 与 PWA。
- 创建成本：线程启动与消息往返都有开销，任务过小不适合移出主线程。

```js
// main.js：主线程创建工作线程并发送数据
const worker = new Worker("sum-worker.js");
worker.postMessage({ values: [1, 2, 3, 4] });
worker.onmessage = function handleMessage(event) {
  console.log(event.data); // 10
};
```

```js
// sum-worker.js：工作线程接收数据并把结果发回主线程
self.onmessage = function handleMessage(event) {
  const total = event.data.values.reduce(function sum(addend, value) {
    return addend + value;
  }, 0);
  self.postMessage(total);
};
```

> 工作线程换来了并行计算的能力，代价是不能直接访问 DOM，任何依赖文档结构的操作仍要回到主线程。

**速记**：工作线程并行计算但不碰 DOM，跨线程数据一律走消息传递。



### 站点隔离与进程模型演进

**进程模型** 决定页面之间的隔离强度。本节先说明单进程模型的问题，再说明站点隔离如何按站点切分进程，以及隔离带来的开销。

#### 单进程模型的局限

**单进程模型**：是把所有标签页、网络与插件放在同一进程内运行的早期形态，实现简单但稳定性与安全性都差。

- 崩溃牵连：任一页面的未捕获错误或内存越界都可能终止整个进程，导致全部标签页退出。
- 数据可读：同一地址空间内的页面可以互相读写内存，绕过同源策略的检查。
- 资源不设限：无法按站点单独限制内存与计算资源，一个页面即可拖垮整个浏览器。

```text
单进程模型  全部标签页共享一个进程，崩溃与内存错误互相牵连
多进程模型  每个标签页独立进程，崩溃互不影响
站点隔离    每个站点独立进程，跨站点数据在进程层面不可读
```

> 稳定性、安全性与内存占用构成三角取舍：隔离越彻底，进程数量越多，内存开销越高。

**速记**：单进程实现简单但崩溃牵连全局，多进程是稳定性与安全性的底线。



#### 站点隔离与进程边界

**站点隔离（site isolation）**：是把不同站点分配到不同渲染进程、使跨站点数据在进程层面无法被读取的机制。

- 判定单位是站点：通常取「协议加上可注册域名」，同一站点下的多个源可能共用一个渲染进程。
- 内嵌文档：跨站点内嵌的文档由独立进程承载，与其父文档之间只保留受限的接口。
- 安全收益：即使某个渲染进程被攻破，也无法直接读取另一站点的内存。
- 性能代价：进程数量随站点数量增长，内存占用与进程切换成本随之上升。

```js
// 每个文档都拥有独立的 window 对象与全局环境
console.log(window.document === document); // true
console.log(window.top === window);        // false，当前文档位于内嵌框架中
console.log(window.origin);                // "https://example.com"
```

> window、location、history 与 navigator 等对象的 API 清单归 前端/JavaScript 主题第 12 篇，本篇只关心这些对象所属的浏览上下文与进程边界。

> [!CAUTION]
> **注意内容**：站点隔离会明显增加进程数量与内存占用，低内存设备上浏览器可能按策略回收后台标签页的进程。

**速记**：站点隔离按站点切分进程，用内存换跨源数据不可读。



### 本系列结构与学习路径

**本系列共 16 篇正文与 1 篇参考资料**，按「先建立架构与全局流程的认识、再掌握网络与渲染机制、最后落到度量与优化」三段推进。

#### 篇目分段

17 篇按认识顺序划为六段，从架构总览一路推进到度量与优化。

- 总览段（第 1 篇至第 2 篇）：浏览器简介与多进程架构、从输入 URL 到页面呈现。
- 网络与存储段（第 3 篇至第 4 篇）：浏览器网络与 HTTP 协议演进、浏览器缓存机制。
- 解析与渲染段（第 5 篇至第 8 篇）：HTML 解析与 DOM 树构建、CSS 解析与样式计算、渲染管线、渲染性能。
- 运行机制段（第 9 篇至第 12 篇）：事件循环与渲染时机、V8 引擎与 JavaScript 执行优化、内存管理与垃圾回收、浏览器存储机制。
- 安全与离线段（第 13 篇至第 15 篇）：同源策略与跨域与站点隔离、Web 安全、Service Worker 与 PWA。
- 度量与优化段（第 16 篇至第 17 篇）：性能指标与优化实战、参考资料与延伸阅读。

#### 各阶段学习重点

六个阶段各有可检验的产出，衡量标准是能否画出链路并定位环节。

- 总览段：能画出页面从地址到首屏的链路，并能说出每一步落在哪个进程或线程。
- 网络与存储段：理解连接复用与缓存命中如何决定首字节时间。
- 解析与渲染段：掌握从字节到像素的各个阶段，以及每个阶段的阻塞来源。
- 运行机制段：理解任务调度、脚本执行与内存行为对页面流畅度的影响。
- 安全与离线段：理解源、进程边界与安全策略之间的关系，以及离线能力的组织方式。
- 度量与优化段：能把现象对应到具体指标，并按指标定位优化手段。

> 总览段与解析渲染段的知识密度最高，建议顺序推进；网络与存储段可以按需要单独查阅。

**速记**：先能画链路，再能说清每段机制，最后能把现象对应到指标。
