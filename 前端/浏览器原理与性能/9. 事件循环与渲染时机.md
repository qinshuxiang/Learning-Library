## 事件循环与渲染时机

### 事件循环与任务队列的浏览器视角

**事件循环与任务队列的浏览器视角** 关注的是主线程如何在执行脚本、响应输入与更新画面之间轮流分配时间。

#### 主线程上的事件循环

**事件循环（event loop）**：是浏览器渲染进程主线程上持续运转的调度循环，它从任务队列取出任务执行，并在任务之间的间隙判断是否插入渲染。

- 主线程职责：执行 JavaScript、派发输入事件、运行渲染管线的样式计算与布局等阶段（渲染管线的完整阶段详见本主题第 7 篇 渲染管线：布局、绘制与合成）。
- 调度职责：维护任务队列与微任务队列，决定何时清空微任务、何时给出渲染机会。
- 单线程约束：任一时刻只有一段 JavaScript 在执行，正在执行的任务不会被打断。

```js
console.log("start");
setTimeout(() => console.log("timer"), 0);
console.log("end");
// 输出：start → end → timer
// 同步代码先跑完，定时器回调进入队列等待
```

> 事件循环不由 JavaScript 语言规范定义，而在 HTML 规范中描述，因此浏览器与 Node.js 的循环细节并不相同。

**速记**：事件循环是主线程上的调度循环，负责取出任务并安排渲染机会。



#### 任务与任务队列

**任务（task）**：是事件循环调度的最小单位，一次任务运行一段完整脚本或一个事件回调，任务与任务之间不会互相穿插。

- 入队方式：定时器到期、事件触发、网络响应完成都会把对应回调包装成任务入队。
- 任务源：同一任务源的任务进入同一条任务队列，不同任务源之间由浏览器决定取舍顺序。
- 执行前提：只有调用栈为空、且微任务已清空时，事件循环才会取出下一个任务。

```js
setTimeout(() => console.log("timer task"), 0);
const channel = new MessageChannel();
channel.port1.onmessage = () => console.log("message task");
channel.port2.postMessage(null);
// 两者属于不同任务源，先后由浏览器调度决定，不可依赖固定次序
```

> 任务队列并非只有一条：规范为不同任务源维护各自的队列，渲染步骤与微任务队列另算，三者共同决定一段代码的先后。

**速记**：任务是调度的最小单位，任务源决定它进入哪一条队列。



#### 轮次与调用栈的关系

**一次事件循环轮次**：是事件循环取出一个任务、执行完毕、清空微任务、再判断是否渲染的完整过程，只有调用栈为空时轮次才能推进。

- 栈空条件：正在运行的脚本或回调构成调用栈，栈未清空说明当前任务尚未结束。
- 轮次推进：任务结束后先清空微任务，再交给渲染步骤，然后回到取任务。
- 阻塞后果：一次任务里长时间占用调用栈，输入事件、定时器与渲染都会推迟到它结束之后。

```js
function blockMainThread(duration) {
  const endTime = performance.now() + duration;
  while (performance.now() < endTime) {
    // 空转占用主线程，期间点击事件与渲染都无法进行
  }
}
blockMainThread(200);
console.log("阻塞结束，输入与渲染在此之后才能推进");
```

> [!IMPORTANT]
> **重要内容**：主线程没有抢占式调度，任何一段同步代码一旦开始就必须跑完，因此控制单次同步执行时长是保持页面可交互的前提。

**速记**：一次轮次处理一个任务并清空微任务，调用栈不清空则轮次无法推进。



### 宏任务与微任务与渲染时机

**宏任务（macro task）** 与 **微任务（micro task）** 是任务的两种粒度，二者与渲染步骤的先后关系决定页面在何时更新。

#### 任务末尾清空微任务

**微任务（micro task）**：是在当前任务结束后立即被清空的高优先级任务，其语言层面的调度语义（Promise、async 与 await 的执行顺序）详见 前端/JavaScript 主题第 31 篇 async、await 与事件循环。

- 清空时机：每个任务执行完毕后，微任务队列被完整清空，期间新产生的微任务同样在本轮处理。
- 浏览器侧意义：微任务总在渲染之前清空，因此微任务里改动的 DOM 会在同一次渲染中生效。
- 顺序约束：一个任务处理完毕，循环先清空微任务，再考虑渲染与下一个任务。

```js
Promise.resolve().then(() => console.log("microtask"));
console.log("task body");
// 输出：task body → microtask
// 微任务在当前任务的同步代码之后、渲染之前执行
```

> [!WARNING]
> **警告内容**：在微任务中持续产生新的微任务会让队列无法清空，渲染机会被无限推迟，页面表现为完全无响应。

**速记**：微任务在任务末尾清空，位置固定于渲染之前。



#### 渲染机会出现在任务之间

**渲染机会（rendering opportunity）**：是事件循环在轮次之间判断需要更新画面时插入的一段流程，依次包含样式计算、布局、绘制与合成。

- 触发条件：渲染并非每轮都发生，浏览器依据是否存在视觉更新与显示设备的刷新节奏决定是否渲染。
- 位置约束：渲染只出现在两个任务之间，绝不打断正在执行的任务或微任务。
- 被挤占：前一任务耗时越长，渲染机会出现得越晚，甚至被本轮直接跳过。

```js
const box = document.getElementById("box");
box.style.width = "100px";
box.style.width = "200px";
// 两次赋值都在同一任务内，渲染只看到最终值 200px
```

> 渲染机会被跳过不会丢样式，只会丢中间态：连续多次修改样式，最终呈现的仍是最后一次的值。

**速记**：渲染机会只出现在任务之间，任务越长它来得越晚。



#### 一轮之内的执行顺序

**一轮之内的执行顺序**：是同一轮中任务体、微任务与渲染帧的固定先后，即任务体执行完毕后清空微任务，需要更新画面时再插入渲染帧。

- 任务体：当前任务的全部同步代码。
- 微任务：任务结束后整队清空，是修改 DOM 的最后时机之一。
- 渲染帧：仅在需要更新画面时插入，rAF 回调在该阶段最先执行。

```js
requestAnimationFrame(() => console.log("frame"));
Promise.resolve().then(() => console.log("micro"));
console.log("task body");
// 输出：task body → micro → frame
// 微任务先于渲染帧，渲染帧先于下一批任务
```

> 顺序中「本轮是否渲染」由浏览器决定，代码输出里 frame 与后续任务的相对位置会随是否发生渲染而变化。

**速记**：一轮之内先任务体、再微任务、后渲染帧，渲染是否发生由浏览器决定。



### requestAnimationFrame 与渲染帧

**requestAnimationFrame** 把回调排到下一次渲染帧，是页面动画与逐帧测量的标准入口。

#### requestAnimationFrame 的签名与时机

**requestAnimationFrame**：是接收 callback 一个参数、返回 number 型句柄的浏览器 API，它把 callback 注册到下一次渲染帧，在微任务清空之后、样式计算与布局之前执行。

- callback 参数：接收一个 DOMHighResTimeStamp 类型的时间戳，表示该帧开始的时间点。
- 返回值：number 型句柄，可传给 cancelAnimationFrame 取消注册。
- 时机收益：在回调里先读布局再写样式不会额外触发一次渲染，适合逐帧动画与测量。

```js
let frameId = 0;
function runFrameTask(timestamp) {
  box.style.transform = "translateX(" + (timestamp % 300) + "px)";
  frameId = requestAnimationFrame(runFrameTask);
}
frameId = requestAnimationFrame(runFrameTask);
// 取消：cancelAnimationFrame(frameId);
```

> [!NOTE]
> **提醒内容**：回调参数是帧开始时间戳而非当前时刻，计算动画进度应以传入的时间戳为准，避免用 Date.now 引入抖动。

**速记**：rAF 回调在微任务之后、布局之前执行，并返回可取消的句柄。



#### 与定时器驱动的取舍

**定时器驱动动画**：是用 setInterval 或 setTimeout 按固定毫秒反复修改样式的方式，它与刷新率无关，因此容易产生抖动或多余渲染。

- 对齐刷新：rAF 与显示设备的刷新节奏对齐，定时器按绝对时间触发，二者难以长期同步。
- 后台行为：标签页不可见时 rAF 自动暂停，定时器仍会按最小间隔触发，造成无谓开销。
- 选用建议：位移、缩放、透明度等逐帧动画优先用 rAF，与渲染管线配合更稳定。

```js
// 反例：用定时器做动画，刷新率与触发间隔不匹配时出现抖动
// setInterval(() => {
//   box.style.left = (Date.now() % 200) + "px";
// }, 16);
```

```js
// 正例：用 rAF 驱动同一动画，回调与渲染帧对齐
let stepCount = 0;
function runStep() {
  stepCount += 1;
  box.style.left = (stepCount % 200) + "px";
  requestAnimationFrame(runStep);
}
requestAnimationFrame(runStep);
```

> 定时器的最小延迟由浏览器钳制，嵌套层级越深钳制越明显，因此它不适合作为动画时钟。

**速记**：动画时钟交给 rAF，定时器只用于与刷新无关的延时逻辑。



#### 句柄的取消与复用

**句柄管理**：是用 requestAnimationFrame 的返回值配合 cancelAnimationFrame 控制注册状态，避免同一动画被重复注册多份回调。

- 保存句柄：把返回值存入变量，取消时传给 cancelAnimationFrame。
- 幂等注册：注册前先判断是否已有待执行句柄，避免重复叠加回调。
- 收尾清理：动画结束或节点被移除时取消句柄，防止回调继续执行。

```js
let rafHandle = 0;
function startAnimation() {
  if (rafHandle) return;
  const stepFrame = () => {
    updateFrame();
    rafHandle = requestAnimationFrame(stepFrame);
  };
  rafHandle = requestAnimationFrame(stepFrame);
}
function stopAnimation() {
  cancelAnimationFrame(rafHandle);
  rafHandle = 0;
}
```

> 忘记取消的句柄会让回调在页面不可见后仍被重新注册，恢复可见时可能出现多份动画同时推进。

**速记**：注册前判重、结束时取消，句柄归零表示没有待执行的帧回调。



### requestIdleCallback 与空闲调度

**requestIdleCallback** 把可延后的工作放进帧末尾的空闲期，用于不要求与下一帧同步的任务。

#### requestIdleCallback 的签名与空闲期

**requestIdleCallback**：是接收 callback 与 options 两个参数、返回 number 型句柄的浏览器 API，它把 callback 排入空闲期执行，即当前帧渲染工作完成之后、下一帧开始之前的剩余时间。

- callback 参数：接收一个 IdleDeadline 对象，其 timeRemaining 方法返回当前空闲期的剩余毫秒数，didTimeout 属性表示是否已因超时被强制调用。
- options 参数：timeout 指定最长等待毫秒数，超出后即使没有空闲期也会执行。
- 预算口径：空闲期一般不超过 50 ms，回调应把工作切成小块，每轮循环检查 timeRemaining 并在不足时让出。

```js
const pendingItems = [];
function scheduleIdleTask(deadline) {
  while (deadline.timeRemaining() > 2 && pendingItems.length > 0) {
    processItem(pendingItems.shift());
  }
  if (pendingItems.length > 0) {
    requestIdleCallback(scheduleIdleTask, { timeout: 1000 });
  }
}
requestIdleCallback(scheduleIdleTask, { timeout: 1000 });
```

> 空闲期是「渲染没有占满帧预算」的副产品，帧预算被长任务或重渲染吃满时，空闲期会非常短甚至为零。

**速记**：rIC 在帧末尾的空闲期执行，依靠 timeRemaining 分批让出。



#### 空闲回调与渲染回调的分工

**空闲回调与渲染回调的分工** 按「是否影响下一帧画面」划分：影响画面的放 rAF，可延后的放 rIC。

- 时机差异：rAF 在渲染帧开头执行，rIC 在本帧渲染结束后的间隙执行。
- 内容差异：动画与逐帧测量用 rAF；数据统计、资源预取、缓存清理、非关键节点构造用 rIC。
- 兼容差异：requestIdleCallback 存在浏览器支持差异，使用前需做特性检测并降级。

```js
const requestIdle = window.requestIdleCallback || function (callback) {
  return setTimeout(() => callback({ timeRemaining: () => 0, didTimeout: true }), 1);
};
requestIdle(() => console.log("idle work"));
```

> [!TIP]
> **建议内容**：为空闲任务设置 timeout 兜底，避免页面长期繁忙时空闲回调永不执行，使可延后的工作一直积压。

**速记**：影响下一帧的用 rAF，可延后的用 rIC 并配超时兜底。



#### 空闲调度的边界与替代

**空闲调度的边界**：指 requestIdleCallback 不保证在期望时间内执行、也不保证每帧都有空闲期，因此只适合完全可延后的工作。

- 不保证时延：页面持续繁忙时可能长时间不触发，必须用 options 的 timeout 兜底。
- 支持差异：部分浏览器不支持该 API，需要先做特性检测。
- 替代方案：用 setTimeout 把工作切成小片轮流执行，牺牲优先级换取普遍可用。

```js
function runChunked(items, handleItem) {
  let cursor = 0;
  const runStep = () => {
    const stepEnd = Math.min(cursor + 20, items.length);
    while (cursor < stepEnd) {
      handleItem(items[cursor]);
      cursor += 1;
    }
    if (cursor < items.length) {
      setTimeout(runStep, 0);
    }
  };
  runStep();
}
runChunked([1, 2, 3], (item) => console.log(item));
```

> 空闲调度与分片执行解决的是同一类问题：把不影响下一帧的工作挪出关键路径，二者可互相替代。

**速记**：rIC 不保证时延与支持度，可用 setTimeout 分片作为通用替代。



### 长任务与掉帧的判定

**长任务** 是渲染卡顿的主要成因，判定它需要一个明确的时间阈值与可观测的采集手段。

#### 长任务的定义与观测

**长任务（long task）**：是主线程上运行时间超过 50 ms 的任务，超过该阈值后浏览器难以在两个渲染帧之间完成输入响应与渲染。

- 阈值口径：50 ms 为业界通用的判定口径，60 fps 下一帧的预算约为 16.7 ms。
- 实际危害：任务执行期间输入事件与渲染只能排队，用户点击与滚动得不到即时反馈。
- 观测方式：PerformanceObserver 接收 callback 一个参数，通过 observe 传入 entryTypes 为 longtask 的配置采集，buffered 为真时可读取注册前已产生的条目。

```js
const longTaskObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log("长任务时长", entry.duration, "ms");
  }
});
longTaskObserver.observe({ entryTypes: ["longtask"], buffered: true });
```

> [!CAUTION]
> **注意内容**：把长任务拆成多个 50 ms 以内的小任务只是把耗时摊开，总工作量并未减少，真实体感仍取决于负载本身。

**速记**：长任务是超过 50 ms 的主线程任务，用 longtask 条目观测。



#### 掉帧的判定方法

**掉帧（dropped frame）**：是某一帧未能在显示设备的刷新间隔内完成、导致上一帧画面被重复显示的现象，连续掉帧即表现为卡顿。

- 帧预算：60 fps 下每帧可用时间约为 16.7 ms，任务超出预算即错过该帧的提交时机。
- 测量方法：用 rAF 记录相邻两次回调时间戳的差值，差值稳定大于刷新间隔说明存在掉帧。
- 常见成因：长任务、强制同步布局与过量的样式重算都会挤占帧预算（优化手段详见本主题第 8 篇 渲染性能：重排、重绘与合成层优化）。

```js
let lastFrameTime = performance.now();
function measureFrameCost(timestamp) {
  const delta = timestamp - lastFrameTime;
  lastFrameTime = timestamp;
  if (delta > 20) {
    console.log("疑似掉帧，帧间隔", delta.toFixed(1), "ms");
  }
  requestAnimationFrame(measureFrameCost);
}
requestAnimationFrame(measureFrameCost);
```

> 单次帧间隔偏大可能是调度抖动，判定掉帧应看一段时间内的比例，而非单帧数值。

**速记**：掉帧是帧超预算被丢弃，用 rAF 相邻时间戳的差值判定。



#### 长任务的拆分策略

**长任务拆分**：是把一段耗时工作切成多个可中断的小块，块与块之间让出主线程，使输入与渲染有机会插入。

- 切片粒度：单块控制在 50 ms 以内，越靠近帧预算越容易被插入渲染。
- 让出方式：用 setTimeout 把下一块排到新任务，在微任务里让出不会产生新的渲染机会。
- 保留状态：用外部游标记录进度，每块处理完保存位置再续跑。

```js
function splitLongTask(items, handleItem, onDone) {
  let cursor = 0;
  const runChunk = () => {
    const chunkEnd = Math.min(cursor + 50, items.length);
    while (cursor < chunkEnd) {
      handleItem(items[cursor]);
      cursor += 1;
    }
    if (cursor < items.length) {
      setTimeout(runChunk, 0);
    } else if (onDone) {
      onDone();
    }
  };
  runChunk();
}
splitLongTask([1, 2, 3], (item) => console.log(item), () => console.log("done"));
```

> 拆分后用 longtask 条目复测，确认没有再产生超阈值任务，再据此调整单块的处理量。

**速记**：长任务按 50 ms 以内切片，用新任务续跑并保留游标进度。
