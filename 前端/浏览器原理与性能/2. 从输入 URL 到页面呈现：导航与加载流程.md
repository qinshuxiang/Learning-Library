## 从输入 URL 到页面呈现：导航与加载流程

**导航（navigation）**：是从用户在地址栏输入地址或点击链接开始，到浏览器把新文档提交为当前文档并开始呈现的完整过程。

本篇按时间顺序走一遍端到端流程，每一阶段的实现细节留给后续篇：网络协议见本主题第 3 篇 浏览器网络与 HTTP 协议演进，缓存判定见第 4 篇，解析见第 5 篇，样式见第 6 篇，渲染管线见第 7 篇。

### 输入到发起请求

**输入到发起请求** 是导航的准备阶段：浏览器先判定输入内容是什么，再决定是导航还是检索，最后把请求交给网络服务。

#### 地址栏输入的判定

**地址栏判定**：是浏览器把输入字符串映射为「可导航地址」或「检索词」的过程，判定依据包括是否含空格、是否含协议前缀、是否形似域名。

- 含协议前缀：按绝对地址处理，不做补全。
- 形似主机名：补全为默认的安全协议地址，例如补全为 https 开头。
- 形似主机与端口：保留端口并按地址处理。
- 含空格或检索特征：按检索词交给默认搜索引擎。
- 多行粘贴：只取其中第一行可用地址，其余内容被丢弃。

```text
输入 https://example.com/docs    -> 含协议前缀，直接作为地址
输入 example.com                 -> 形似域名，补全为 https://example.com
输入 localhost:8080              -> 形似主机与端口，作为地址
输入 浏览器 原理                 -> 含空格，作为检索词交给搜索引擎
```

> 判定结果只影响首次请求：一旦发生导航，地址栏内容由提交后的文档地址接管。

**速记**：地址栏先判定输入是地址还是检索词，再决定是否发起导航。



#### 导航的起点与文档的归属

**导航**：是把一个新文档设为当前文档的过程，它由某个浏览上下文（browsing context，可理解为标签页、内嵌框架或独立窗口）发起，并最终改属该上下文。

- 发起方式：地址栏输入、点击链接、脚本触发、表单提交与前进后退。
- 唯一当前文档：每个浏览上下文同一时刻只有一个当前文档。
- 历史追加：导航按会话历史条目记录，前进后退即在这些条目之间移动。
- 文档替换：新文档提交后，旧文档进入卸载流程。
- 内嵌框架：框架内的导航只替换该框架的文档，顶层地址与历史都不受影响。
- 新窗口：在独立窗口中打开时，导航属于新创建的浏览上下文，不替换原文档。

```js
// URL 构造器把地址字符串拆成协议、主机、端口、路径与查询串
const url = new URL("https://example.com:8443/docs?q=1#top");
console.log(url.protocol); // "https:"
console.log(url.hostname); // "example.com"
console.log(url.port);     // "8443"
console.log(url.search);   // "?q=1"
```

> [!NOTE]
> **提醒内容**：同一个页面里的每个内嵌框架都是一个独立浏览上下文，拥有各自的 window 对象与历史记录，顶层地址变化不代表内嵌文档的地址也变化。

**速记**：导航改变某个浏览上下文的当前文档，每个上下文各有独立的历史。



#### 请求交给网络服务

**网络服务（network service）**：是浏览器进程中负责发起请求、管理连接与查找缓存的组件，渲染进程不直接管理套接字。

- 请求接管：导航请求由浏览器进程交给网络服务，渲染进程只接收结果。
- 缓存先行：网络服务先查找缓存，命中则直接返回响应。
- 连接建立：未命中时依次进行域名解析、连接建立与协议协商，详见本主题第 3 篇。
- 响应回流：响应按规则写入缓存并交付给渲染进程，缓存规则详见本主题第 4 篇。

```text
浏览器进程决定导航
  -> 网络服务接收请求
  -> 查找缓存，命中则直接返回
  -> 未命中：域名解析 -> 连接建立 -> 发送请求
  -> 响应回流：缓存写入与交付渲染进程
```

> 缓存命中与未命中决定了是否要经过域名解析与连接建立，这是不同页面首字节时间差异的主要来源。

**速记**：导航请求统一交给网络服务，缓存命中与否决定是否要重新建立连接。



### 导航与提交

**导航阶段** 覆盖请求发出、服务器响应与文档提交三件事，重定向与导航取消都可能在这期间发生。

#### 导航请求的构造与重定向

**导航请求**：是浏览器为获取文档而发出的请求，带有与子资源请求不同的默认请求头与优先级。**重定向**：是服务器用 3xx 状态码与 Location 响应头指示浏览器改用新地址的行为。

- 请求头：导航请求默认带上接受的内容类型与语言偏好。
- 历史影响：重定向会追加历史条目，并使浏览器向新地址重新发起请求。
- 跨源限制：重定向的目标源与请求源不同时，响应会受同源策略相关规则约束，详见本主题第 13 篇。
- 性能影响：重定向链每增加一跳就增加一次往返，首字节时间被逐跳推迟。

```http
GET /docs HTTP/1.1
Host: example.com
Accept: text/html,application/xhtml+xml
Accept-Language: zh-CN,zh;q=0.9
```

```http
HTTP/1.1 302 Found
Location: https://example.com/docs/overview
Cache-Control: no-store
```

> [!WARNING]
> **警告内容**：把重定向当作常规路由手段会串行增加往返次数，每一跳都推迟首字节时间，服务端应尽量避免把重定向用在稳定的页面路由上。

**速记**：导航请求带专属请求头，重定向会重新发起请求并追加历史条目。



#### 导航提交与文档替换

**导航提交（commit）**：是浏览器把新文档正式设为当前文档的时刻，提交之后地址栏、历史记录与渲染进程都指向新文档。

- 提交之前：旧文档仍然显示在屏幕上，用户看到的还是上一个页面。
- 提交之后：地址栏更新，旧文档进入卸载流程，新文档获得渲染进程与网络请求权。
- 首帧之前：提交到首帧绘制之间仍有空窗，页面靠首屏内容逐步填充。
- 替换语义：同一浏览上下文内的提交是替换，不是叠加，旧文档不会保留在屏幕上。

```text
导航开始       -> 旧文档继续显示
收到响应头     -> 决定是否提交
提交           -> 新文档成为当前文档，地址栏更新
首次绘制       -> 页面出现可见内容
```

> 从提交到首帧的这段时间仍然显示旧页面，其长度取决于新文档关键资源的到位速度。

**速记**：提交是新旧文档的分界点，提交之后地址栏与历史都指向新文档。



#### 导航的取消与竞态

**导航竞态**：是同一浏览上下文中先后发起多次导航、先前的导航响应晚于后发导航而必须被丢弃的情形。

- 取消范围：后发导航会取消尚未提交的先前导航，被取消的响应不进入渲染阶段。
- 已提交文档：已经提交的文档无法被取消，只能由下一次导航替换。
- 服务端副作用：请求可能已经到达服务器并被处理，因此写操作不适合由导航触发。
- 排错线索：网络面板中出现被标记为已取消的请求，通常就是导航竞态的表现。

```js
// 连续点击两个链接时，第二次导航会取消第一次尚未提交的导航
document.addEventListener("click", function handleLinkClick(event) {
  const link = event.target.closest("a[data-route]");
  if (!link) return;
  console.log("即将导航到", link.href);
});
```

```text
t0  第一次导航发起，等待响应
t1  第二次导航发起，第一次导航被标记为已取消
t2  第一次导航的响应到达，被丢弃
t3  第二次导航的响应到达并提交
```

> 导航取消只影响尚未提交的请求，已经发生的服务端副作用需要由接口自身的幂等设计来消化。

**速记**：后发导航取消先发导航，已提交的文档只能被下一次导航替换。



### 响应处理与文档解析启动

**响应处理** 从收到响应头开始：浏览器要先判断内容是什么类型、交给哪个进程，再决定何时启动解析。

#### 响应的类型判定与进程选择

**MIME 类型**：是响应头 Content-Type 给出的内容类型标识，浏览器据此决定把响应当作可解析文档、可嵌入资源还是下载文件。

- 文档类型：text/html 会触发导航提交，并让浏览器为该文档选择渲染进程。
- 进程选择：浏览器进程按站点归属与已有进程情况挑选或新建渲染进程，规则见本主题第 1 篇。
- 其他类型：图片、音视频等按各自规则处理，无法就地展示的类型转为下载。
- 缺失类型：缺少 Content-Type 时浏览器依据内容嗅探判断，判断结果可能不是文档。
- 编码判定：charset 写在 Content-Type 中或由文档自身声明，决定字节到字符的解码方式。
- 安全响应头：响应头中的策略决定文档能加载哪些子资源，详见本主题第 14 篇 Web 安全：XSS、CSRF 与 CSP。

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: gzip
Content-Length: 14523
Cache-Control: max-age=3600
```

> [!IMPORTANT]
> **重要内容**：Content-Type 缺失或与实际内容不符时，浏览器会把响应当作纯文本或下载处理，文档结构与脚本都不会被执行。

**速记**：响应类型由 Content-Type 决定，它同时决定响应是否进入渲染管线的第一步。



#### 文档解析的启动与预加载扫描器

**预加载扫描器（preload scanner）**：是与主解析器并行的轻量扫描机制，在主解析器被阻塞时继续扫描后续标记，提前发现并请求关键子资源。

- 并行扫描：主解析器等待脚本或样式时，扫描器继续向后读取文档内容。
- 提前请求：发现样式、脚本与图片后立即发起请求，减少串行等待。
- 覆盖范围：能覆盖标记中静态写出的资源，脚本动态插入的资源不会被提前发现。
- 与解析器的分工：扫描器只负责发现与请求，不负责构建 DOM 树。

```js
// 文档解析的三个状态，可用于观察解析进度
console.log(document.readyState); // "loading"：文档仍在解析
document.addEventListener("DOMContentLoaded", function handleReady() {
  console.log(document.readyState); // "interactive"：文档解析完成
});
window.addEventListener("load", function handleLoad() {
  console.log(document.readyState); // "complete"：子资源也加载完成
});
```

> 状态切换的确切时机、解析中断与脚本执行的对应关系见本主题第 5 篇 HTML 解析与 DOM 树构建。

**速记**：预加载扫描器在解析被阻塞时继续发现资源，提前把关键请求发出去。



#### 解析期间的阻塞与文档状态

**解析阻塞**：是指解析器遇到必须等待的资源时暂停构建 DOM 树的状况，常见来源是同步脚本与尚未就绪的样式表。

- 同步脚本：下载并执行期间解析暂停，脚本之后的标记不会被解析。
- 样式表：样式表会阻塞其后脚本的执行，因为脚本可能读取计算样式。
- 阻塞期间：预加载扫描器的发现工作不受影响，请求继续发出。
- 解除方式：defer、async 与模块脚本改变脚本的执行时机，规则详见本主题第 5 篇。

```text
解析阻塞的常见来源
  同步脚本   下载并执行期间解析暂停
  样式表     阻塞其后脚本的执行
  阻塞期间   预加载扫描器继续发现资源
  非阻塞写法 defer、async 与模块脚本
```

> 阻塞本身不是缺陷：它保证了脚本执行时文档结构与样式状态可预期，代价是把加载时间转成了等待时间。

**速记**：同步脚本与样式表会暂停解析，阻塞期间的资源发现由预加载扫描器承担。



### 子资源加载与预解析

**子资源加载** 是文档提交之后的持续过程：浏览器按已发现的资源清单并发加载，并在过程中不断调整优先级。

#### 子资源的发现与加载顺序

**子资源**：是文档呈现所依赖的样式、脚本、字体与图片等资源，由解析器与预加载扫描器共同发现。

- 关键资源优先：样式、字体与首屏图片先于首屏之外的图片加载。
- 发现顺序不等于执行顺序：脚本的下载顺序与执行顺序可能不同。
- 并发上限：同一域名下的并发连接数有限，超出部分排队，连接管理详见本主题第 3 篇。
- 字体影响：字体文件延迟到位会触发回退字体的重新排版，进而影响布局稳定性。

```html
<link rel="preconnect" href="https://cdn.example.com">
<link rel="preload" as="font" type="font/woff2" href="/fonts/main.woff2" crossorigin>
<link rel="stylesheet" href="/styles/main.css">
<script src="/scripts/app.js" defer></script>
<img src="/images/hero.jpg" width="1200" height="630" alt="">
```

> 为图片写明宽高可以让浏览器提前预留位置，避免图片到位后引发布局偏移。

**速记**：子资源由解析器与预加载扫描器共同发现，关键资源优先加载。



#### 资源提示与加载优先级

**资源提示**：是通过标记或响应头向浏览器声明资源用途与重要程度的元信息，包括 preconnect、preload、prefetch 与 fetchpriority。

- preconnect：提前完成域名解析与连接建立，适合已知的第三方关键域名。
- preload：声明当前导航马上要用的资源，必须写对 as 属性，否则会重复下载。
- prefetch：声明后续导航可能用到的资源，优先级低，在空闲时加载。
- fetchpriority：覆盖单个资源的默认相对优先级，可上调也可下调。
- 使用条件：提示只能提前请求时机，不能减少资源本身的体积，因此只对发现偏晚的关键资源有意义。
- 未使用代价：资源到位后没有被使用的 preload 会触发控制台警告，应连同标记一起移除。

```text
preconnect    提前完成连接建立，适合已知的第三方关键域名
preload       声明当前导航必需的关键资源，as 写错会触发重复下载
prefetch      声明后续导航可能用到的资源，空闲时加载
fetchpriority 覆盖单个资源的默认相对优先级
```

> [!TIP]
> **建议内容**：只对首屏渲染必需的少数资源使用 preload，滥用会挤占真正关键资源的带宽，并在控制台产生未使用警告。

**速记**：资源提示按用途分工，preload 只留给当前导航的关键资源。



#### 脚本与样式的加载顺序

**脚本加载顺序**：是多个脚本被下载与执行时的相对次序，由写法决定：同步脚本按出现顺序阻塞执行，defer 脚本按出现顺序在解析完成后执行，async 脚本先下载完成者先执行。

- 同步脚本：出现在文档中的位置决定了它能看到多少已解析的结构。
- defer：只对外部脚本有效，保序并在解析完成后执行。
- async：只对外部脚本有效，执行顺序不确定，适合彼此独立的脚本。
- 模块脚本：默认具有 defer 语义，并支持依赖图的加载。
- 样式优先：样式表先于脚本就绪，脚本读取计算样式时才不会拿到未完成的结果。

```js
// 同步脚本执行时，其后的文档结构尚未被解析
console.log(document.body ? "body 已存在" : "body 尚未解析"); // "body 尚未解析"
```

```text
同步脚本  下载并执行完毕才继续解析，按出现顺序执行
defer     解析期间并行下载，解析完成后按出现顺序执行
async     下载完成后立即执行，执行顺序不确定
模块脚本  默认 defer 语义，按依赖图顺序执行
```

> 顺序规则、解析中断与 DOMContentLoaded 的精确关系见本主题第 5 篇 HTML 解析与 DOM 树构建。

**速记**：同步阻塞按序执行、defer 保序延后、async 先到先执行，顺序决定脚本能看到多少结构。



### 首屏呈现与关键渲染路径

**关键渲染路径（critical rendering path）**：是从文档与样式的字节数据到屏幕上首次出现像素所必须经过的一系列阶段。本节给出阶段链路与它的时间构成。

#### 关键渲染路径的阶段

**关键渲染路径**：是解析、构建渲染树、布局、绘制与合成这一串决定首次可见内容何时出现的阶段。

- 构建 DOM 树：解析 HTML 字节，详见本主题第 5 篇。
- 构建样式树：解析 CSS 字节、匹配选择器并计算层叠，详见本主题第 6 篇。
- 合并与几何计算：DOM 树与样式树合并为渲染树，再计算几何，即布局（layout，旧称回流 reflow），详见本主题第 7 篇。
- 绘制与合成：生成绘制指令、光栅化为位图并合成为屏幕像素，详见本主题第 7 篇。

```text
HTML 字节 -> DOM 树
CSS 字节  -> 样式树
DOM 树 + 样式树 -> 渲染树
渲染树 -> 布局（几何计算）
布局 -> 绘制指令 -> 光栅化 -> 合成 -> 屏幕像素
```

> 路径上任一阶段被阻塞，首次像素都会推迟，因此缩短首屏时间的通用手段是减少关键资源的数量与体积。

**速记**：关键渲染路径是 DOM 树与样式树合流到首次像素的最短链路。



#### 首次绘制与首次内容绘制

**首次绘制（first paint，FP）**：是屏幕上出现第一个非空白像素的时间点。**首次内容绘制（first contentful paint，FCP）**：是屏幕上首次出现文字、图片等文档内容像素的时间点。

- 口径基点：两者都以导航开始为零点计时，单位为 ms。
- 区别：FP 可能只是背景色变化，FCP 标志内容开始可见。
- 观察方式：通过 PerformanceObserver 监听绘制条目，回调收到 first-paint 与 first-contentful-paint 两类条目。
- 内嵌文档：内嵌框架的绘制条目属于该框架自身的导航，不并入顶层文档口径。

```js
// 用 PerformanceObserver 观察绘制条目，时间以导航开始为基准
const observer = new PerformanceObserver(function handleEntries(list) {
  list.getEntries().forEach(function logPaint(entry) {
    console.log(entry.name, Math.round(entry.startTime), "ms");
  });
});
observer.observe({ type: "paint", buffered: true });
// 输出示例：first-paint 412 ms
// 输出示例：first-contentful-paint 598 ms
```

> 指标的含义、阈值与优化目标见本主题第 16 篇 性能指标与优化实战：Core Web Vitals 与 Lighthouse。

**速记**：FP 是第一个非空白像素，FCP 是首批内容像素，二者都以导航开始计时。



#### 从导航到首屏的时间构成

**首字节时间（time to first byte，TTFB）**：是从导航开始到浏览器收到响应首字节的时间，它之后才进入文档下载与渲染阶段。

- 阶段一：地址判定与导航请求发出，耗时取决于判定逻辑与排队情况。
- 阶段二：连接建立与服务器处理，对应 TTFB，优化手段集中在连接复用与缓存。
- 阶段三：文档下载与解析，耗时取决于文档体积与解析阻塞。
- 阶段四：关键资源就绪到首次绘制，耗时取决于关键资源的数量与关键渲染路径的长度。
- 观测口径：实际观测中还包含进程调度与排队时间，因此四段之和是对总时间的近似分解。

```text
导航开始
  -> 地址判定与请求发出
  -> 连接建立与服务器处理        TTFB
  -> 文档下载、解析与子资源加载
  -> 样式就绪、布局、绘制、合成
  -> 首次内容绘制               FCP
```

> 各阶段的度量方式、工具读法与优化清单见本主题第 16 篇，本主题后续各篇分别深入其中一段。

**速记**：首屏时间由连接、下载、解析与渲染四段构成，TTFB 只是其中的第二段。
