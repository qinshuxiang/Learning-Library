## Web 安全：XSS、CSRF 与 CSP

### Web 安全的威胁模型与同源策略的地位

**威胁模型（threat model）** 是对保护对象、攻击者能力与信任边界的系统化描述，Web 安全的每一项措施都应回答它防住的是哪一类攻击。本节给出资产与信任边界，再说明同源策略在其中承担的角色与它无法承担的部分。

#### 资产与信任边界

**资产（asset）**：是攻击者试图获取或破坏的目标，Web 场景中包括会话凭据、页面内的敏感数据与接口的授权能力。

- 会话凭据：Cookie 中的会话标识与浏览器中保存的令牌，被窃取即可冒充用户。
- 页面数据：渲染在文档中的个人信息与接口返回的业务数据。
- 授权能力：借助受害者身份调用接口的权限，例如转账、改密与删除。
- 信任边界：浏览器在文档内不区分脚本来源，页面引入的第三方脚本与自家脚本拥有同等权限。
- 输入假设：来自地址栏、表单、接口与第三方组件的所有数据都不可信。

```js
// 文档内的脚本不区分来源：任一脚本都能读取同一份文档与存储
const accountText = document.querySelector("#account").textContent;
console.log(accountText.length); // 第三方脚本同样可以读取
```

**速记**：保护对象是凭据、数据与授权能力，文档内的脚本不分来源共享同一权限。



#### 同源策略在安全模型中的地位

**同源策略的地位**：是浏览器侧的隔离基线，它限制跨源读取，但不构成完整的授权体系。

- 它能做：阻止跨源脚本读取响应、访问文档与存储，限制跨源窗口互操作。
- 它不能做：阻止同源内部的注入执行、阻止浏览器按规则自动携带 Cookie、替代服务端的鉴权与业务校验。
- 配套关系：跨源放行、跨源隔离与进程边界详见本主题第 13 篇 同源策略、跨域与站点隔离。
- 结论：安全判断必须落在正确的一层，浏览器限制只减少攻击面，不决定谁能执行什么操作。

```js
function assertCanDeletePost(session, postId) {
  const post = postStore.find(postId);
  if (!post || post.ownerId !== session.userId) {
    throw new Error("forbidden"); // 授权判断只能在服务端完成
  }
  postStore.remove(postId);
}
```

> [!WARNING]
> **警告内容**：把同源策略或前端的界面限制当作授权手段，攻击者直接调用接口即可越权；授权必须在服务端对每个请求独立判定。

**速记**：同源策略是浏览器侧隔离基线，授权必须由服务端逐请求判定。



#### 威胁分类与防御思路

**威胁分类**：是按根因把常见问题归入注入、伪造、传输与依赖四组，便于对症选择防护手段。

- 注入类：跨站脚本、模板注入与服务端结构化查询注入，根因是把数据当成代码。
- 伪造类：跨站请求伪造与点击劫持，根因是把浏览器的自动行为当作用户意图。
- 内容与传输类：混合内容、不安全的跳转目标与明文传输。
- 依赖类：第三方脚本被篡改、依赖存在已知漏洞。
- 防御原则：输入校验负责格式，输出编码负责上下文，鉴权负责权限，最小权限与纵深防御负责兜底。

```http
Content-Security-Policy: default-src 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

> 同一份数据在不同上下文需要不同处理：入库前做格式校验，出库时按所在位置选择对应的编码规则。

**速记**：注入靠编码，伪造靠令牌与来源校验，越权靠服务端鉴权。



### XSS 的类型与成因与防护

**XSS（Cross-Site Scripting，跨站脚本）**：是攻击者把可执行脚本注入受害者访问的页面，使其在页面的源下运行的攻击。脚本一旦在页面源下运行，便与页面自身脚本无异，因此这类问题常被称为客户端注入。

#### 成因与危害

**跨站脚本的成因**：是把不可信数据交给 HTML 解析器或脚本执行器处理，数据因此在页面上下文中被当作代码执行。

- 拼接注入：服务端或客户端用字符串拼接生成页面结构，未对插值做上下文编码。
- 危险接收器：写入元素内部结构的属性、写入整段结构的属性、插入相邻结构的接口与文档写入接口，都会把字符串按 HTML 解析。
- 执行入口：字符串形式的定时器参数、动态求值与动态函数构造会把字符串当代码执行。
- 危害范围：读取页面数据、以受害者身份发起请求、操纵文档与表单、窃取可被脚本读取的令牌。

```js
const params = new URLSearchParams(location.search);
const keyword = params.get("q");

// 反例：把不可信数据交给 HTML 解析器
document.querySelector("#result").innerHTML = keyword;
// 输入形如 <img src=x onerror=alert(1)> 的内容时，脚本会在页面源下执行
```

**速记**：跨站脚本的根因是把不可信数据当页面结构或代码处理，脚本遂以页面源身份运行。



#### 三种类型与差异

**跨站脚本的分类**：按恶意内容的来源与注入时机分为存储型、反射型与 DOM 型，三者注入位置不同，防护手段一致。

- 存储型：恶意内容先写入服务端（评论、昵称、上传文件名），在后续请求中被回显给受害者。
- 反射型：恶意内容来自当前请求（地址参数、表单），被服务端直接拼进响应。
- DOM 型：注入与执行都发生在客户端，服务端响应中不含恶意内容，问题出在前端代码。
- 差异总结：类型只影响排查路径与影响面，防护都归结为输出编码与安全接收器。

```js
// DOM 型：数据全程未经过服务端
const hash = decodeURIComponent(location.hash.slice(1));

document.querySelector("#title").textContent = hash;  // 安全：按文本写入
// document.querySelector("#banner").innerHTML = hash; // 反例：按页面结构解析
```

> 服务端做了转义并不意味着客户端一定安全：DOM 型的注入点不在服务端响应里，需要单独审计前端接收器。

**速记**：存储型入库后回显、反射型即时回显、DOM 型全在客户端，防护手段相同。



#### 上下文编码与安全接收器

**上下文编码（contextual encoding）**：是按数据将要落入的位置选择对应转义规则的做法，同一段数据在文本、属性、地址与脚本中的安全写法互不相同。

- 文本上下文：转义尖括号、和号与引号，或改用按纯文本写入的接口。
- 属性上下文：为属性值加引号并转义引号；事件属性不应拼接不可信数据。
- 地址上下文：使用 encodeURIComponent 处理参数值，避免可执行协议被当作跳转目标。
- 脚本与样式上下文：不把不可信数据写入脚本或样式，确需传递时改为序列化后经数据属性中转。
- 首选接口：按纯文本写入的 textContent、创建元素的 createElement 与校验属性名后的 setAttribute。

```js
function renderComment(container, text) {
  const node = document.createElement("p");
  node.textContent = text;   // 按纯文本写入，不做页面结构解析
  container.appendChild(node);
}

renderComment(document.querySelector("#comments"), "<b>hello</b>");
// 页面显示字面量文本，不会被解析为元素
```

> [!CAUTION]
> **注意内容**：用正则从页面结构里过滤脚本标签并不可靠，畸形标签、属性事件与编码变形都能绕过；需要接受富文本的场景应使用维护良好的白名单净化库。

**速记**：输出编码按上下文选择，优先使用按纯文本写入的接口。



#### 纵深防御

**纵深防御（defense in depth）**：是在输出编码之外叠加多层限制，使单层失效时仍有其他防线拦住攻击。

- Cookie 属性：为会话 Cookie 加上 HttpOnly 与 Secure，脚本读不到令牌，窃取的收益随之下降。
- 内容安全策略：用策略限制脚本来源与内联脚本，阻断大部分注入执行（见后文）。
- 模板默认转义：现代前端框架的模板语法默认转义插值，避免手工拼接。
- 净化与白名单：对允许提交富文本的场景使用净化库，只保留允许的标签与属性。

```http
Set-Cookie: session=8f14e45f; HttpOnly; Secure; SameSite=Lax; Path=/
```

> 防护层次之间不互相替代：HttpOnly 阻止令牌被读走，但注入脚本仍能以受害者身份发请求，编码与策略同样不可省略。

**速记**：输出编码之外再用 HttpOnly、内容安全策略与净化库叠加纵深防御。



### CSRF 的成因与防护

**CSRF（Cross-Site Request Forgery，跨站请求伪造）**：是攻击者诱导受害者的浏览器向已登录的目标站点发送一个携带凭据的请求，从而以受害者身份执行操作。与跨站脚本不同，请求伪造不注入脚本，利用的是浏览器自动携带凭据这一行为。

#### 成立条件与攻击路径

**请求伪造的成立条件**：是目标站点仅凭 Cookie 识别身份、请求参数可被预测或构造、且浏览器会自动为该请求附带凭据。

- 身份识别：服务端仅靠会话 Cookie 判断用户，不校验请求的实际来源。
- 参数可控：收款对象与金额等参数以固定格式提交，攻击者可自行构造。
- 自动携带：浏览器发起请求时附带目标域的 Cookie，页面脚本无法阻止。
- 攻击目标：只让请求被执行，不需要读取响应，因此同源策略不构成障碍。

```html
<!-- 攻击页面上的自动提交表单：目标为用户已登录的站点 -->
<form action="https://bank.example.com/transfer" method="POST" id="transferForm">
  <input type="hidden" name="to" value="acct-9911">
  <input type="hidden" name="amount" value="1000">
</form>
<script>document.getElementById("transferForm").submit();</script>
```

**速记**：请求伪造成立需凭据自动携带、身份仅凭 Cookie、参数可构造三个条件。



#### 令牌与 SameSite

**CSRF 令牌（CSRF token）**：是服务端随页面下发并与当前会话绑定的随机值，服务端在处理请求时校验其存在且匹配。**SameSite 属性**：是 Cookie 上控制跨站请求是否携带该 Cookie 的属性，取值 Strict、Lax 与 None。

- 令牌要点：不可预测、与会话绑定、在写操作的服务端逻辑中强制校验，且不能出现在地址中。
- SameSite=Lax：跨站请求默认不携带该 Cookie，顶层导航的 GET 请求例外；取 None 时必须配合 Secure。
- 判定粒度：SameSite 按站点而非源判定，同站点的子域之间默认视为同一站。
- 双提交模式：把随机值同时写入 Cookie 与请求参数，服务端比对两者是否一致。
- 组合效果：令牌挡住跨站构造的请求，SameSite 从源头减少凭据被携带的机会。

```http
Set-Cookie: csrf=6f1d2b9a; SameSite=Strict; Secure; Path=/
```

```js
// 前端从文档元数据中读取令牌，随请求放入自定义头
const token = document.querySelector("meta[name='csrf-token']").content;

fetch("/api/transfer", {
  method: "POST",
  credentials: "same-origin",
  headers: { "X-CSRF-Token": token },
  body: JSON.stringify({ to: "acct-22", amount: 100 })
});
```

**速记**：令牌与会话绑定并在服务端强制校验，SameSite 按站点控制凭据是否携带。



#### 来源校验与方法约束

**来源校验**：是服务端检查 Origin 与 Referer 请求头，确认请求由本站页面发起的手段。

- Origin 头：跨站发起的请求通常附带该头，服务端策略应为「不在允许列表内即拒绝」。
- Referer 头：作为补充信息，可能因引用策略被裁剪或缺失，不应作为唯一依据。
- 自定义头：要求写请求携带自定义头，利用简单请求无法携带自定义头的限制，把请求推入预检流程。
- 方法约束：把写操作限定在 POST 等方法，让 GET 与 HEAD 保持无副作用，避免被图片或链接直接触发。

```http
POST /api/transfer HTTP/1.1
Host: bank.example.com
Origin: https://evil.example.net
Content-Type: application/json
```

```text
服务端判定：Origin 不在允许列表内，返回 403，不进入业务逻辑。
```

**速记**：来源校验以 Origin 为主、Referer 为辅，并对写操作施加方法约束。



#### 与跨站脚本的关系

**请求伪造与跨站脚本的关系**：是防护优先级上的包含关系，跨站脚本一旦成立即可绕过大部分请求伪造防护。

- 令牌失效：注入脚本能读取页面中的令牌，再以同源身份发出请求，令牌校验形同虚设。
- SameSite 失效：请求由同站页面脚本发起，SameSite 不参与拦截。
- 修复顺序：先消除注入点，再补请求伪造防护；只做令牌校验无法覆盖注入的影响。
- 运行环境差异：移动端与内嵌浏览器对 SameSite 与第三方 Cookie 的处理可能与桌面浏览器不同，需实测确认。

```js
// 同源脚本发起的请求会正常携带 Cookie，SameSite 无法区分发起者是用户还是注入脚本
fetch("/api/profile", { credentials: "same-origin" })
  .then((response) => response.json())
  .then((data) => console.log(data));
```

> [!WARNING]
> **警告内容**：在存在注入的页面上，令牌与 SameSite 都会被绕过，请求伪造防护必须先建立在无注入的前提之上。

**速记**：跨站脚本能读取令牌并同源发起请求，故需先修注入再谈请求伪造。



### CSP 的指令与部署与报告

**CSP（Content Security Policy，内容安全策略）**：是一组由响应头或文档内声明下发的策略，指示浏览器只允许加载和执行指定来源的资源。它的定位是纵深防御的一层，既不能替代输出编码，也不解决服务端的鉴权问题。

#### 定位与生效原理

**内容安全策略的生效原理**：是浏览器按白名单模型对每类资源做来源比对，未列出的来源一律拒绝。

- 白名单模型：默认拒绝，只有策略中声明允许的来源、关键字或凭据才能加载。
- 分类型控制：脚本、样式、图片、字体、网络连接与框架各有对应指令。
- 作用点：在资源加载与内联执行之前拦截，并把违规记录到控制台或上报端点。
- 适用边界：策略在浏览器侧执行，服务端之间的调用不受其约束，它降低注入的实际影响而不修复注入本身。

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com
```

> 内容安全策略的价值在于把一次注入降级为一次被拦截的加载，是缩小影响面而非消灭漏洞。

**速记**：内容安全策略按白名单拦截资源与内联执行，是缩小影响面的纵深防御。



#### 常用指令语义

**指令（directive）**：是策略中以分号分隔的配置项，每条指令负责一类资源或一类行为。

- 取源指令：default-src 作为其他取源指令的兜底，script-src、style-src、img-src、font-src、connect-src 与 frame-src 分别作用于对应资源与连接。
- 行为指令：base-uri 限制文档基准地址，form-action 限制表单提交目标，object-src 限制插件类内容。
- 嵌入控制：frame-ancestors 声明本页可被哪些来源以框架方式嵌入，用于防御点击劫持。
- 常用关键字：'self' 表示同源，'none' 表示全部禁止，'unsafe-inline' 允许内联，'unsafe-eval' 允许字符串求值，'strict-dynamic' 允许受信脚本动态插入脚本。
- 凭据形式：nonce 为每次响应生成的随机值，哈希形式按脚本内容计算，两者都用于放行特定的内联脚本。

```http
Content-Security-Policy: script-src 'nonce-rAnd0m123' 'strict-dynamic'; object-src 'none'; base-uri 'none'
```

```html
<script nonce="rAnd0m123" src="/app.js"></script>
```

> 名称中带 inline 与 eval 的关键字会把对应风险重新打开；策略收敛的目标通常是去掉这两类关键字。

**速记**：default-src 兜底，各取源指令分管资源，frame-ancestors 管嵌入，关键字控制内联与求值。



#### 部署方式与 nonce 方案

**部署方式**：是策略通过响应头或文档内声明下发的途径，两者的覆盖范围不同。

- 响应头优先：可对所有响应统一生效，支持全部指令，包括 frame-ancestors 与报告相关指令。
- 文档内声明：只能表达部分指令，不能使用 frame-ancestors 与报告指令，适合无法修改服务端配置的场景。
- nonce 方案：服务端为每次响应生成不可预测的随机值，同时写入策略与脚本标签，浏览器只执行携带该值的脚本。
- strict-dynamic：在 nonce 或哈希基础上，允许受信脚本动态创建的脚本执行，此时主机来源白名单不再生效。
- 迁移路径：先用只报告模式运行一段时间，收集违规清单，策略收敛后再切换为强制模式。

```js
function buildCspHeader(nonce) {
  return [
    "default-src 'self'",
    "script-src 'self' 'nonce-" + nonce + "' 'strict-dynamic'",
    "object-src 'none'",
    "base-uri 'none'",
    "frame-ancestors 'none'"
  ].join("; ");
}

console.log(buildCspHeader("rAnd0m123"));
// "default-src 'self'; script-src 'self' 'nonce-rAnd0m123' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'"
```

> [!IMPORTANT]
> **重要内容**：nonce 必须每次响应唯一且不可预测，并配合禁止缓存该响应的策略；固定或可猜测的 nonce 会让内联脚本限制失去意义。

**速记**：优先用响应头下发，nonce 每次响应唯一，配合动态脚本关键字与灰度迁移。



#### 报告机制

**报告机制**：是把被拦截的违规行为发送到指定端点的能力，用于上线前评估与线上监控。

- 报告指令：较早的写法直接给出上报地址，后来引入基于端点分组的报告方式，两者可在过渡期内并存。
- 端点声明：配合相应响应头声明上报地址与分组名，具体头名与字段随规范演进，应以目标浏览器当前支持为准。
- 报告内容：通常包含被违反的指令、被拦截资源的地址、发生违规的文档地址与当时生效的策略。
- 报告模式：只报告不拦截的形式用于灰度，便于在不影响线上的前提下收集完整违规清单。
- 运维要求：上报端点需要限流与鉴权，避免被伪造的报告淹没。

```http
Content-Security-Policy-Report-Only: default-src 'self'; report-uri https://report.example.com/csp
```

```text
报告字段示意（字段名以浏览器实际实现为准）：
violated-directive、blocked-uri、document-uri、original-policy
```

**速记**：报告机制把违规集中到服务端，灰度阶段用只报告模式收集清单，端点需限流与鉴权。



### 其他常见问题：点击劫持、混合内容与供应链

**其他常见问题** 覆盖三类与注入和请求伪造形态不同的风险：把页面当作点击目标、把明文资源混入加密页面、把信任传递给第三方代码。三者都需要在响应头与依赖管理上显式处理。

#### 点击劫持与框架控制

**点击劫持（clickjacking）**：是把目标页面嵌入到不可见或经过伪装的框架中，诱导用户在不知情的情况下点击目标页面的控件。

- 攻击形态：透明覆盖层、用容器裁剪只露出按钮、或诱导用户完成连续操作。
- 首选防护：内容安全策略的 frame-ancestors 指令，可精确到允许的来源列表。
- 兼容防护：X-Frame-Options 取 DENY 或 SAMEORIGIN，粒度较粗，只能整站或同源。
- 前提说明：跨源嵌入框架本身是被允许的行为，因此需要显式的框架控制（跨源嵌入的规则详见本主题第 13 篇 同源策略、跨域与站点隔离）。
- 辅助手段：对敏感操作要求二次确认或输入验证码，降低误点成功的概率。

```http
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
```

**速记**：点击劫持借不可见框架诱导点击，用 frame-ancestors 精确控制嵌入来源。



#### 混合内容与传输安全

**混合内容（mixed content）**：是加密页面中加载了明文 HTTP 资源的情形，使页面的安全承诺被打折。

- 主动内容：脚本、样式表、框架与请求等可改变页面行为的资源，浏览器默认阻止加载。
- 被动内容：图片、音视频与字体等资源，浏览器通常先尝试升级为加密地址，失败再给出提示或阻止。
- 处理方式：把资源地址改为完整的加密地址，避免协议相对写法；用升级指令统一重写页面内的明文请求。
- 传输强制：配合严格传输安全头，让浏览器在指定时长内只以加密方式访问该站点。

```http
Content-Security-Policy: upgrade-insecure-requests
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

> 混合内容的处理顺序是先升级、再清理；长期保留明文地址会让页面在被动内容被阻止后出现缺图或功能异常。

**速记**：混合内容按主动与被动分类处理，统一升级为加密地址并用传输安全头强制。



#### 供应链与依赖风险

**供应链风险（supply chain risk）**：是页面把执行权限交给第三方代码或未审计依赖后引入的风险。

- 第三方脚本：外部脚本在页面源下运行，权限与自家脚本相同，被篡改即可读取全部页面数据。
- 完整性校验：为跨源脚本声明内容哈希，浏览器在加载前比对，内容不符则拒绝执行。
- 来源收敛：通过 script-src 限制允许的脚本来源，减少可被引入的外部脚本数量。
- 依赖治理：锁定版本、定期更新、审计已知漏洞、移除不再维护的依赖。
- 其他要点：开放重定向、服务端模板注入与不安全的反序列化属于服务端侧问题，需与后端联合排查。

```html
<!-- 跨源脚本声明内容哈希，加载时比对 -->
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-1qaz2wsx3edc4rfv"
        crossorigin="anonymous"></script>
```

> [!WARNING]
> **警告内容**：无完整性校验的第三方脚本一旦被篡改，等同于在页面中直接植入任意脚本；引入前应评估来源可信度并声明内容哈希。

**速记**：第三方脚本与页面同权，用完整性哈希与来源收敛控制供应链风险。



#### 安全配置核对清单

**安全配置核对清单**：是把前述措施按传输、内容、框架与数据四层归类核对的最小集合。

- 传输层：全站使用加密传输，配置严格传输安全头并覆盖子域。
- 内容层：输出编码与内容安全策略并行，先用只报告模式收集违规再收敛策略。
- 框架层：frame-ancestors 与 X-Frame-Options 控制嵌入，Referrer-Policy 控制来源信息外泄。
- 数据层：会话 Cookie 带 HttpOnly、Secure 与合适的 SameSite，令牌不写入可被脚本读取的位置。
- 流程层：依赖审计、第三方脚本评估与上线前的安全头检查。

```text
响应头核对清单：
Content-Security-Policy
Strict-Transport-Security
X-Content-Type-Options: nosniff
Referrer-Policy
```

> 清单的价值在于可核对：每次上线前逐项确认，比事后排查省力得多。

**速记**：按传输、内容、框架、数据四层核对安全头与凭据属性。
