## 浏览器存储机制

**浏览器存储**：是浏览器为核心源提供的一组本地数据保存设施，涵盖随请求发送的 Cookie、同步键值型的 Web Storage、异步事务型的 IndexedDB、面向响应副本的 Cache Storage，以及以文件为单位的源私有文件系统。

本篇讨论存储区如何分类与选型、Cookie 在浏览器侧的行为与安全属性、各存储区的配额与逐出规则，以及存储隔离与跨标签通信的机制。各存储 API 的具体调用写法详见 前端/JavaScript 主题第 15 篇 客户端存储；Service Worker 的缓存生命周期与缓存策略详见本主题第 15 篇 Service Worker 与 PWA；HTTP 缓存头的判定规则详见本主题第 4 篇 浏览器缓存机制。

### 存储方式的分类与选择

选型的前提是弄清数据要存在哪一层、由谁负责它的生命周期。这一模块先给出两组分类维度，再给出一条可复用的决策顺序。

#### 按生命周期与作用域分类

**生命周期**：是一份存储数据从写入到被清除所跨越的时间范围，由存储区的类型与浏览器策略共同决定。**作用域**：是能读到这份数据的上下文范围，由源、标签页或顶层站点决定。

- 会话级：sessionStorage 与页面内变量随标签页会话结束而消失，刷新保留、关闭标签页清除。
- 持久级：localStorage、IndexedDB、Cache Storage 与 Cookie 在没有被逐出或清理前长期保留。
- 请求级：Cookie 除本地保存外还会随匹配的请求发送给服务器，其余存储区不参与请求。
- 作用域差异：Cookie 可跨子域共享，Web Storage 与 IndexedDB 严格按源隔离，sessionStorage 再加一层标签页隔离。

```js
function describeScope(storeName) {
  const table = {
    cookie: "按域与路径匹配，可跨子域",
    localStorage: "按源隔离，同源标签页共享",
    sessionStorage: "按源隔离，再按标签页隔离",
    indexedDB: "按源隔离",
    cacheStorage: "按源隔离，随缓存版本管理",
  };
  return table[storeName];
}

console.log(describeScope("sessionStorage"));   // "按源隔离，再按标签页隔离"
```

> 判断一份数据能活多久，先看它所在存储区的生命周期，再看它是否落在会被逐出或清理的范围内。类型选择错误带来的问题通常不是读不到，而是数据在预期之外消失。

**速记**：先按生命周期分会话级与持久级与请求级，再按作用域分源级与标签页级。



#### 按数据模型与访问方式分类

**数据模型**：是存储区对数据的组织形态，决定能存什么形状的数据与如何检索。**访问方式**：是脚本读写存储区的调用形态，分为同步阻塞与异步回调两类。

- 键值字符串型：Cookie 与 Web Storage 只能保存文本，结构化数据需自行序列化。
- 文档对象型：IndexedDB 保存结构化克隆的对象，支持索引、游标与事务。
- 请求响应型：Cache Storage 以请求为键、响应为值，天然适合保存资源副本。
- 文件型：源私有文件系统按目录与文件读写，支持分片与流式处理。
- 访问方式：Cookie 通过请求头与文档属性，Web Storage 同步读写，IndexedDB 与 Cache Storage 异步返回。

```js
// 能力探测：不同环境的支持情况不同，运行时先探测再决定降级路径
const supports = {
  indexedDb: "indexedDB" in globalThis,
  cacheStorage: "caches" in globalThis,
  cookieStore: "cookieStore" in globalThis,
  broadcastChannel: "BroadcastChannel" in globalThis,
};

console.log(Object.entries(supports));
```

> 数据模型决定上限：Web Storage 只能存文本，写入结构化数据要靠序列化，读出后还要反序列化，这一步在大数据量下会成为主线程的时间成本。

**速记**：键值字符串型最简单，文档对象型能查询，请求响应型存副本，文件型存大块数据。



#### 选型维度与决策顺序

**选型维度**：是决定一份数据放进哪个存储区时依次比较的四个维度，分别为数据规模、读写频率、生命周期与是否需要随请求发送。

- 第一问是否需要随请求自动发送：需要则只能用 Cookie，且只放标识类小数据。
- 第二问数据规模与是否需要查询：超过键值存储的合理范围或需要索引查询时选 IndexedDB。
- 第三问是否属于资源副本：静态资源与离线页面选 Cache Storage，属于第 15 篇的缓存策略范围。
- 第四问生命周期：标签页级状态用 sessionStorage，长期偏好用 localStorage，且两者都只放小数据。
- 一致性要求：需要事务与原子写入的场景必须排除 Web Storage，它没有事务语义。

```js
function pickStorage(sizeInBytes, needsQuery, lifetime) {
  if (needsQuery) return "IndexedDB";
  if (lifetime === "session") return "sessionStorage";
  if (sizeInBytes > 100 * 1024) return "IndexedDB";   // 超过百 KB 不再用同步键值存储
  return "localStorage";
}

console.log(pickStorage(2048, false, "persistent"));   // "localStorage"
console.log(pickStorage(500000, false, "persistent")); // "IndexedDB"
```

> 决策顺序的价值在于先排除再细化：先按「是否需要随请求发送」排除 Cookie，再按数据规模与查询需求排除 Web Storage，剩下的候选就很少了。

**速记**：先看是否随请求发送，再看规模与查询，再看生命周期，最后确认是否需要事务。



### Cookie 的作用与限制与安全属性

Cookie 的特殊之处在于它是唯一会随请求发送的存储区，因此它的限制与安全属性都围绕这一条展开。这一模块只讨论浏览器侧的写入、保存、携带与校验行为，读写语法详见 JavaScript 主题第 15 篇。

#### Cookie 的写入与携带链路

**Cookie**：是由服务器通过 Set-Cookie 响应头写入、由浏览器保存并在后续匹配请求中自动附加到 Cookie 请求头的小段文本数据。

- 写入来源：服务器用 Set-Cookie 响应头下发，脚本可通过 document.cookie 或 Cookie Store API 写入，但脚本无法写入 HttpOnly。
- 保存标识：Cookie 按名称、域、路径三元组唯一标识，同名不同域或不同路径的 Cookie 可以共存。
- 携带条件：目标地址的域与路径匹配、协议满足 Secure、跨站场景通过 SameSite 判定，四项都通过才附加。
- 请求开销：命中的 Cookie 会拼接进请求头随每个请求发送，包含图片、脚本等静态资源请求。

```bash
# 服务器下发的响应头片段
curl -i https://api.example.com/login
# HTTP/1.1 200 OK
# set-cookie: sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
# set-cookie: theme=dark; Path=/; Max-Age=2592000
```

```http
GET /profile HTTP/1.1
Host: api.example.com
Cookie: theme=dark; sessionId=abc123
```

> 携带是自动的、响应是脚本可读的，这两点的组合决定了 Cookie 的两个后果：一是每个请求都付出带宽代价，二是脚本可以读到的 Cookie 需要在服务端做校验而不能作为可信凭据。

**速记**：服务端写 Cookie，浏览器按域、路径、Secure、SameSite 四项筛选后随请求自动携带。



#### 域与路径与 SameSite 的匹配规则

**Domain 属性**：是 Cookie 允许被发送到的域范围，省略时限定为写入方的主机名，指定时覆盖其子域。**Path 属性**：是 Cookie 允许被发送到的路径前缀，路径越具体的 Cookie 越优先出现在请求头中。**SameSite 属性**：是控制跨站请求是否携带 Cookie 的策略，取值 Strict、Lax 与 None。

- Strict：任何跨站请求都不携带，安全性最高，但会让从外站跳回本站的导航丢失登录态。
- Lax：允许顶级导航的 GET 请求携带，是现代浏览器对未声明 SameSite 的 Cookie 采用的默认处理。
- None：允许跨站携带，必须同时声明 Secure，适用于需要嵌入第三方页面的场景。
- 路径优先：同一名称的 Cookie 在更具体路径下存在时，请求头中按路径从具体到宽泛的顺序排列。

```js
async function saveThemeCookie(theme) {
  await cookieStore.set({
    name: "theme",
    value: theme,
    path: "/",
    sameSite: "lax",
  });
  return await cookieStore.get("theme");
}

saveThemeCookie("dark");   // 显式声明 sameSite，避免依赖浏览器默认
```

> [!WARNING]
> **警告内容**：SameSite=None 的 Cookie 必须同时具备 Secure，否则浏览器会拒绝写入该 Cookie，跨站会话会直接失效而不会给出明显的界面提示。

**速记**：Domain 决定域范围，Path 决定路径前缀，SameSite 决定跨站能否携带。



#### 安全属性与体积开销

**HttpOnly 属性**：是禁止脚本读取该 Cookie 的标记，document.cookie 与 Cookie Store API 都看不到它。**Secure 属性**：是限定该 Cookie 只在 HTTPS 连接上发送的标记。

- HttpOnly：降低 XSS 直接读取会话标识的风险，但攻击者仍可借脚本发起已授权请求。
- Secure：阻止 Cookie 在明文连接上被发送，是 SameSite=None 的前置条件。
- 名称前缀：__Host- 要求同时满足 Secure、Path 为根且不带 Domain；__Secure- 要求具备 Secure。
- 体积约束：单个 Cookie 约 4 KB，同域 Cookie 的总数与总量由浏览器限制，全部内容计入每个请求的头部大小。
- 脚本可见性：非 HttpOnly 的 Cookie 对脚本完全可读，因此不应存放权限判定所依赖的可信数据。

```bash
# 名称前缀要求同时满足多项条件，不满足时浏览器拒绝写入
# set-cookie: __Host-sessionId=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
# set-cookie: __Secure-preferences=compact; Path=/; Secure
```

> 体积开销是 Cookie 容易被忽视的成本项：Cookie 越大，每个请求的头部越大，首字节时间随之变差。静态资源域名上不下发 Cookie，能直接省下这部分开销。

**速记**：HttpOnly 挡脚本读取，Secure 限定 HTTPS，前缀约束组合条件，体积计入每个请求。



### Web Storage 与 IndexedDB 与 Cache Storage 的定位

三个存储区分别服务于三类数据：小配置、结构化数据与资源副本。这一模块只比较三者的定位与代价，不展开各自的 API 用法。

#### Web Storage 的同步语义与适用边界

**Web Storage**：是 localStorage 与 sessionStorage 共用的同步键值存储接口，读写在主线程上完成，并受同源限制。

- 同步语义：setItem 与 getItem 调用期间主线程被占用，调用方无法让出执行权。
- 写入成本：写入大字符串时可能触发磁盘写入，耗时可被主线程直接感知。
- 共享与隔离：localStorage 在同源的所有标签页共享，sessionStorage 限于当前标签页。
- 适用边界：少量、非敏感、读写不频繁的配置类数据，如主题、语言、上次访问位置。

```js
const payload = "x".repeat(200_000);
const start = performance.now();
localStorage.setItem("largeDraft", payload);
const elapsed = performance.now() - start;

console.log(`${elapsed.toFixed(2)} ms`);   // 同步写入，主线程在此期间被占用
localStorage.removeItem("largeDraft");
```

> [!TIP]
> **建议内容**：超过百 KB 量级的数据不要用 Web Storage 读写，改用 IndexedDB 让序列化与写入在异步流程中完成；确需用同步存储时，写入应放在空闲期而不是交互回调里。

**速记**：Web Storage 同步读写、占用主线程，只适合小体量的配置类数据。



#### IndexedDB 的异步事务与适用边界

**IndexedDB**：是浏览器提供的异步事务型对象数据库，读写以事务为单位在后台完成，容量与并发能力都强于 Web Storage。

- 异步语义：请求以成功与失败回调返回，主线程不必等待磁盘操作完成。
- 事务语义：读写必须在事务内进行，同一事务内的操作要么全部生效要么全部回退。
- 结构能力：对象仓库可建索引与游标，支持按非主键字段检索与范围遍历。
- 适用边界：结构化的大量数据、离线数据、需要查询与批量更新的数据集。
- 成本构成：序列化、事务调度与索引维护都有开销，简单配置项不必使用它。

```js
// 请求以回调形式返回结果，主线程在等待期间可继续执行其他任务
function requestToPromise(request) {
  return new Promise((resolve, reject) => {
    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
  });
}

console.log(typeof requestToPromise);   // "function"
```

> 异步带来的是调用形态的变化：任何依赖读取结果的逻辑都要放进回调或等待 Promise，不能像 Web Storage 那样在下一行直接使用读到的值。这一差异决定了上层代码的组织方式。

**速记**：IndexedDB 异步加事务，能查询能存大数据，代价是调用链变长。



#### Cache Storage 在存储版图中的定位

**Cache Storage**：是以请求为键、响应为值的异步存储区，用于保存 HTTP 响应副本，由 Service Worker 的缓存策略驱动。本节只讨论它在存储版图中的位置，生命周期与缓存策略详见本主题第 15 篇 Service Worker 与 PWA。

- 数据模型：键是 Request，值是 Response，可以整份保存网络响应与其响应头。
- 与 HTTP 缓存的关系：独立存储、独立清理，查找时不受强缓存与协商缓存规则约束。
- 淘汰规则：属于源的存储数据，受配额与逐出策略约束，持久化需申请。
- 适用边界：静态资源、离线页面与可重复使用的接口响应副本，不适合存业务结构化数据。

```js
function describeCacheStorage() {
  return {
    keyType: "Request",
    valueType: "Response",
    managedBy: "Service Worker 的缓存策略",
    scope: "源级别",
  };
}

console.log(describeCacheStorage().keyType);   // "Request"
```

> 与 HTTP 缓存相比，Cache Storage 的取舍是「完全由脚本控制」：什么时候缓存、缓存哪一版、何时清理都由代码决定，代价是这套策略需要自行维护，包括版本与失效处理。

**速记**：Cache Storage 以请求为键响应为值存资源副本，由脚本控制，与 HTTP 缓存互不影响。



#### 其他存储形态的定位

**源私有文件系统（Origin Private File System，缩写 OPFS）**：是按文件与目录组织、面向源的存储区，支持流式读写与分片处理，由部分浏览器实现，使用前需查兼容性表。**内存缓存**：是页面内变量、Map 与数组构成的一层数据缓存，随页面销毁而消失，不写入磁盘。

- 内存缓存：速度最快、容量受堆限制，适合单次会话内的计算结果复用。
- OPFS：适合大文件与需要按分片处理的二进制数据，访问形态接近文件系统。
- HTTP 缓存：由浏览器按响应头自动管理，脚本只能间接影响（详见本主题第 4 篇 浏览器缓存机制）。
- 选择顺序：临时计算结果放内存，小配置放 Web Storage，结构化数据放 IndexedDB，资源副本放 Cache Storage，大文件放 OPFS。

```js
const opfsSupported = typeof navigator.storage?.getDirectory === "function";

async function describeStorageRoot() {
  if (!opfsSupported) return null;
  const root = await navigator.storage.getDirectory();
  return root.name;   // 源私有文件系统的根目录名
}

describeStorageRoot().then((name) => console.log(name));
```

> 存储区之间不是替代关系而是分层关系：内存层放最热的数据，持久层放需要跨会话的数据，缓存层放可重建的数据。分层得当可以减少序列化次数与磁盘写入次数。

**速记**：内存放热数据，Web Storage 放小配置，IndexedDB 放结构化数据，Cache Storage 放副本，OPFS 放大文件。



### 存储配额与淘汰与逐出

本地存储不是无限资源，浏览器既要保证站点可用，也要防止单个站点占满磁盘。这一模块说明配额的来源、逐出的策略与写入失败的应对。

#### 配额的来源与查询

**配额（quota）**：是浏览器为每个源分配的本地存储可用空间上限，由浏览器按站点使用情况与磁盘剩余空间动态给出，不保证固定数值。

- 分配口径：配额与源绑定，不同源的用量互不占用；具体数值由浏览器实现与设备状态决定。
- 查询接口：navigator.storage.estimate() 返回含 usage 与 quota 两个字节数属性的对象。
- 持久化状态：navigator.storage.persisted() 返回该源是否已获得持久化存储资格。
- 使用建议：把 usage 与 quota 的比值作为写入前的判断依据，不要把任何具体阈值写死在代码里。
- 统计范围：estimate 的 usage 覆盖该源名下的各类存储区，Cookie 是否计入由实现决定。

```js
async function reportStorageUsage() {
  const estimate = await navigator.storage.estimate();
  return {
    usedInKB: Math.round(estimate.usage / 1024),
    quotaInKB: Math.round(estimate.quota / 1024),
    ratio: estimate.usage / estimate.quota,
  };
}

reportStorageUsage().then((result) => console.log(result));   // 三个字段均由浏览器给出
```

> 配额随磁盘压力变化，同一份代码在不同设备、不同时刻读到的 quota 可能不同。因此容量规划应以「当前比值」驱动，而不是以某个固定容量假设驱动。

**速记**：配额由浏览器按源与磁盘情况动态给出，用 estimate 读 usage 与 quota，不写死阈值。



#### 持久化请求与逐出策略

**逐出（eviction）**：是浏览器在磁盘压力下按策略清除源的存储数据以回收空间的行为。**best-effort 存储**：是随时可能被整体清除的默认存储级别。**persistent 存储**：是通过 navigator.storage.persist() 申请、获批后不因磁盘压力被自动清除的级别。

- 默认级别：多数存储区按 best-effort 处理，磁盘紧张时可能被整体清除。
- 申请持久化：persist() 返回是否获批，结果受用户交互历史、站点使用度与浏览器策略影响。
- 逐出粒度：通常以源为单位，Cookie 与应用数据是否同时清除取决于浏览器实现。
- 应对原则：把本地数据视为可重建的缓存副本，权威数据保存在服务端。
- 用户清理：用户主动清除站点数据的效果强于逐出策略，会移除该源的全部本地存储。

```js
async function ensurePersistentStorage() {
  if (await navigator.storage.persisted()) return true;
  return await navigator.storage.persist();   // 未获批时返回 false，仍按 best-effort 存储
}

ensurePersistentStorage().then((granted) => console.log(granted));
```

```text
清除站点数据时一并移除的存储：
Cookie 与站点权限
localStorage 与 sessionStorage
IndexedDB 数据库
Cache Storage 缓存
源私有文件系统中的文件
```

> [!CAUTION]
> **注意内容**：被逐出的数据无法恢复，也不能假设用户不会清理站点数据。把唯一副本放在本地存储的站点，在逐出或清理后会丢失用户数据。

**速记**：默认 best-effort 可能被逐出，persist 获批后不被自动清除，权威数据留在服务端。



#### 超配额的写入失败处理

**QuotaExceededError**：是存储写入超出配额时产生的错误名，Web Storage 在调用处同步抛出该错误，IndexedDB 的事务会因该错误被中止。

- 同步表现：localStorage.setItem 超限时同步抛出异常，调用方必须用 try 与 catch 处理。
- 异步表现：IndexedDB 的写入请求以错误回调返回，所在事务随之回退。
- 失败语义：写入失败不会破坏已有数据，但也不会自动腾出空间。
- 处理策略：捕获后清理可重建的旧条目、降低写入频率，或提示用户清理站点数据。
- 禁忌做法：静默忽略写入失败，会让数据在后续读取时凭空消失且难以定位原因。

```js
function savePreference(key, value) {
  try {
    localStorage.setItem(key, value);
    return { ok: true };
  } catch (error) {
    if (error.name === "QuotaExceededError") {
      return { ok: false, reason: "quota" };   // 交给上层降级处理
    }
    return { ok: false, reason: "unknown" };
  }
}

console.log(savePreference("theme", "dark"));   // { ok: true }
```

> 写入失败属于可预期的运行状态而非异常情况：用户设备磁盘紧张、站点数据累积到上限都会触发。把失败路径写进正常流程，比事后排查「数据莫名丢失」更省成本。

**速记**：超配额抛 QuotaExceededError，同步抛出异步回报，必须捕获并降级处理。



### 存储隔离与隐私模式与跨标签通信

存储的边界由源与顶层站点共同划定，通信则要在同一源的多个上下文之间建立通道。这一模块说明隔离的单位、隐私模式下的差异与三种通信机制。

#### 源的存储隔离与第三方分区

**存储隔离**：是浏览器保证一个源无法读取另一个源本地数据的分区机制，与同源策略配套生效。**第三方存储分区**：是把第三方上下文的存储按顶层站点拆分成独立存储桶的做法。

- 按源隔离：不同源的页面无法读取彼此的 Web Storage、IndexedDB 与 Cache Storage。
- 同源共享：同源的不同标签页共享 localStorage、IndexedDB 与 Cache Storage 中的数据。
- 第三方收紧：主流浏览器逐步限制第三方 Cookie，并按顶层站点对第三方上下文的存储进行分区。
- 分区后果：同一段第三方脚本嵌入不同站点时会拿到不同存储桶，跨站点识别与共享状态的能力受限。
- 升级路径：依赖第三方 Cookie 的跨站会话需要改为顶层交互跳转，或走浏览器提供的存储访问申请流程。

```bash
# 第三方嵌入式场景下的分区 Cookie 响应头示例
# set-cookie: sessionId=abc123; SameSite=None; Secure; Partitioned
```

> 隔离单位从「源」逐步走向「顶层站点加源」的组合，是存储区域最明显的一次策略变化。它削弱了跨站追踪能力，也让嵌入型业务需要重新设计状态保存方式。

**速记**：存储按源隔离、同源共享，第三方存储按顶层站点分区，跨站共享能力持续收紧。



#### 隐私模式下的存储行为

**隐私模式**：是不保留本地痕迹的浏览会话，其存储行为的共同点是不写入长期可复用的持久数据。

- 会话内可用：多数实现允许在隐私窗口内正常读写存储，页面的基本功能不受影响。
- 退出即清除：关闭全部隐私窗口后，该会话内写入的本地数据被整体清除。
- 可能拒写：部分实现对存储写入直接拒绝或给出更小的配额，写入失败需要降级路径。
- 影响面：依赖本地登录态与草稿保存的功能，在隐私模式下的行为与普通窗口不同。
- 探测建议：不确定时先做一次写入与删除的探测，再决定走持久路径还是内存路径。

```js
function probeStorage(store) {
  try {
    store.setItem("probe", "1");
    store.removeItem("probe");
    return true;      // 可写入不代表数据会长期保留
  } catch (error) {
    return false;     // 隐私模式或策略限制下可能直接拒绝写入
  }
}

console.log(probeStorage(localStorage));   // true 或 false，两种情况都可能出现
```

> 隐私模式不影响当前会话内的读取一致性：写入后立刻读取仍能得到刚写入的值，变化发生在会话结束之后。需要区分「本次会话可用」与「下次访问仍可用」两个不同的问题。

**速记**：隐私模式会话内可读写，退出后清除，部分实现直接拒写，需要准备降级路径。



#### 跨标签通信：storage 事件

**storage 事件**：是某个文档修改 localStorage 后，同源其他文档收到的事件，事件对象含 key、oldValue、newValue、url 与 storageArea 五个属性。

- 触发范围：同源的其他标签页与窗口收到事件，触发写入的那个文档自身不收到。
- 触发条件：值发生实际变化才触发，写入相同值不触发；removeItem 与 clear 同样会触发。
- 不覆盖 sessionStorage：sessionStorage 的变更不会跨标签页广播，这也是它标签页隔离的体现。
- 事件顺序：updateStorage 之后才派发事件，接收方读到的是已经生效的新值。
- 典型用途：登录态变化、主题切换、缓存版本更新等需要多标签页同步的场景。

```js
window.addEventListener("storage", (event) => {
  console.log(event.key, event.oldValue, event.newValue, event.url);
  // 本页面不接收自己触发的写入，只接收其他同源标签页的修改
});

localStorage.setItem("theme", "dark");   // 在本页面写入不会触发本页面的监听器
```

> 事件只在其他文档中触发这一条，决定了它天然适合单向广播：写入方不需要通知谁，读取方各自订阅即可。若需要本页面也响应变更，应把变更逻辑抽成函数直接调用。

**速记**：storage 事件在同源其他标签页触发、本页不触发，值未变化不触发，sessionStorage 不参与。



#### 跨标签通信：BroadcastChannel 与其他通道

**BroadcastChannel**：是按名称在同一源内的多个上下文之间广播消息的通道，用 new BroadcastChannel(name) 创建，以 postMessage(message) 发送，以 onmessage 接收，以 close() 关闭。

- 消息语义：消息按结构化克隆传递，同源内所有同频道的上下文都会收到，包括同页面的其他实例。
- 生命周期：通道随上下文释放，不落地到磁盘，页面刷新后需要重新建立。
- 与 storage 事件的差别：可传结构化对象、不依赖写入存储，但不会跨会话保留状态。
- SharedWorker：可作为多标签共享的连接中枢，但实现与调试成本更高，需要单独评估。
- 选择顺序：状态同步优先用 BroadcastChannel，需要与存储变更联动时叠加 storage 事件。

```js
const cartChannel = new BroadcastChannel("cart-sync");

cartChannel.onmessage = (event) => {
  console.log("收到购物车变更", event.data);   // { items: 3 }
};

cartChannel.postMessage({ items: 3 });
cartChannel.close();   // 不再需要时关闭通道
```

> 三种通道各有边界：storage 事件只承载存储值的变更且不通知本页，BroadcastChannel 能传任意结构化数据但只在当前会话内有效。需要跨会话同步时，两者都要以持久数据为最终依据。

**速记**：BroadcastChannel 按名称广播结构化消息、不落地磁盘，适合会话内多标签同步。
