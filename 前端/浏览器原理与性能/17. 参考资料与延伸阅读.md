## 参考资料与延伸阅读

### 官方文档与规范

本模块收录浏览器行为的第一手依据：标准文本规定必须满足的约束，官方文档说明当前实现的事实。查证解析、网络、存储与调度细节时以这些来源为准，二手文章只用于检索线索。

#### WHATWG 的 HTML 标准与 DOM 标准

**WHATWG HTML 标准（HTML Living Standard）**：是定义 HTML 语法、解析算法、DOM 树构建与脚本执行时机的持续更新标准，由 WHATWG 以单一活文档维护，不再按 HTML5、HTML6 这样的版本号冻结。

- 解析器的容错规则、脚本元素的阻塞行为与外链资源的加载顺序都写在标准中，本主题第 5 篇（HTML 解析与 DOM 树构建）涉及的 defer、async 与 DOMContentLoaded 触发时机可直接对应到条文。
- **DOM 标准（DOM Standard）**：规定节点接口、事件传播路径与 MutationObserver 的回调时机，事件为什么先捕获再冒泡这类问题以它为准。
- 两份标准只约束可观察行为，不约束引擎内部实现，因此不同内核可以采用不同数据结构而对外表现一致。

> 标准文本与实现存在差异：规范给出的是必须满足的约束，浏览器在测量精度、任务调度粒度与内存回收时点上仍有自由裁量空间，新特性又常先有实现后入标准。遇到行为与标准不符时，先在目标浏览器实测，再回到标准的议题列表确认是否为已知分歧。

**速记**：解析、DOM 与脚本时机查 HTML 与 DOM 两份活标准，实现差异以实测为准。



#### Fetch 标准与 URL 标准

**Fetch 标准（Fetch Standard）**：是定义请求与响应、重定向策略、跨源读取与缓存模式（cache mode）的统一规范，导航、子资源加载与 fetch 调用运行在同一套算法之上。

- 请求的 mode、credentials、redirect 与 cache 选项语义都出自这里，本主题第 4 篇的强缓存与协商缓存判定在标准中以与 HTTP 缓存的交互章节呈现。
- **URL 标准（URL Standard）**：定义 URL 的解析、序列化与同源判定所需的源（origin）概念，本主题第 13 篇的同源策略判定规则以它为基础。
- 标准把 CORS 的浏览器侧行为写成算法步骤，服务端侧的响应头配置写法属于后端主题，两者不可混谈。

> 排查跨源失败时，控制台报错文案与标准的算法步骤一一对应：先确认是请求在发出前被拦截，还是响应到达后被拒绝读取，再决定改哪一侧。

**速记**：导航与跨源行为查 Fetch 标准，源的判定规则查 URL 标准。



#### ECMAScript 规范与 TC39 提案

**ECMAScript 规范（ECMA-262）**：是定义 JavaScript 语言语义的官方标准，由 Ecma International 的 TC39 委员会维护，规定每个内建对象的可观察行为。

- 判断某个操作在运行时的确切语义（属性访问顺序、异常传播方式等）以规范为最终依据。
- **TC39 提案（github.com/tc39/proposals）**：按阶段跟踪语法演进，进入第四阶段的提案会纳入下一年度的规范版本，新语法在各浏览器的落地进度并不一致。
- 语言语义决定引擎能做什么优化，本主题第 10 篇的隐藏类与内联缓存优化都在规范的语义边界内实现。

> 规范与引擎文档的分工是：规范说明结果必须是什么，V8 官方博客说明用什么手段达成。读优化主题时先确认语义，再看实现技巧，顺序颠倒会产生错误的一般化结论。

**速记**：语言语义查 ECMA-262，新语法进度查 TC39 提案的阶段划分。



#### MDN Web Docs 与 web.dev

**MDN Web Docs（developer.mozilla.org）**：是面向开发者的 Web 平台参考，逐条给出接口签名、参数、返回值、浏览器兼容表与可运行示例，是查某个接口怎么用最快的官方来源。

- Performance API、PerformanceObserver、IntersectionObserver 与 requestIdleCallback 等本主题高频接口都有完整条目与示例。
- 每个页面附兼容性表与规范链接，便于从用法跳到标准定义，避免只记结论不知出处。
- **web.dev（web.dev）**：是 Google 维护的性能与最佳实践指南，围绕 Core Web Vitals 组织内容，给出指标口径、阈值与优化路径，本主题第 16 篇的指标定义以它为主要参照。

> MDN 回答接口怎么用，web.dev 回答指标怎么算与怎么优化。两者配合阅读，可避免把「接口调用正确」与「指标已经达标」混为一谈。

**速记**：接口用法查 MDN，指标口径与优化路径查 web.dev。



### 标准与规范组织

本模块说明浏览器相关标准由谁制定、以何种形式发布。掌握归属关系后，遇到某条结论时能直接判断该去哪个仓库或文档核对，而不必依赖搜索结果。

#### WHATWG

**WHATWG（Web Hypertext Application Technology Working Group）**：是维护 HTML、DOM、Fetch、URL、Streams 与 Encoding 等核心标准的开放工作组，产出形式为持续修订的活标准（Living Standard）。

- 与 W3C 的分工结果是 HTML 与 DOM 由 WHATWG 单一维护，避免同一技术存在多个版本快照而造成引用歧义。
- 活标准的含义是只有当前文本有效，引用时不必也不应标注年份版本号。
- 议题处理与勘误在公开仓库中讨论，可查到某个行为争议的最终结论与理由。
- 对读者而言，它的价值是把「浏览器为什么这样表现」追溯到唯一文本。

> 活标准降低了引用歧义，代价是旧译文与旧版图书中的条目可能已经过期。核对时看当前文本，不引用二次转载的节选。

**速记**：核心 Web 标准看 WHATWG 活标准，引用时以当前文本为准。



#### W3C 与 CSS 工作组及 Web 性能工作组

**W3C（World Wide Web Consortium）**：是制定 CSS、可访问性与 Web 性能等规范的标准组织，规范按模块分篇，按工作草案、候选推荐与推荐等阶段推进。

- **CSS 工作组（CSSWG）**：维护 CSS 系列模块，本主题第 6 篇的层叠与继承、选择器匹配与样式计算规则出自 CSS Cascading and Inheritance 与 Selectors 等规范。
- **Web 性能工作组**：维护 Performance Timeline、Navigation Timing、Resource Timing、Paint Timing、Layout Instability、Long Tasks 与 Event Timing 等规范，本主题第 16 篇的指标定义以其为源头。
- 草案阶段的规范可能改名或调整算法，规范阶段高也不代表各引擎已普遍实现。

> 指标的分子与分母定义（以最大内容绘制确定 LCP、以位移比例计算 CLS）写在性能规范中，优化前先读定义，可避免对着口径错误的量做优化。

**速记**：CSS 规则查 CSSWG，性能指标定义查 W3C 的 Web 性能规范。



#### IETF 与 HTTP 系列 RFC

**IETF（Internet Engineering Task Force）**：是制定互联网协议标准的组织，产出以 RFC 文档发布且发布后不再修改，HTTP 与传输层协议的细节以此为准。

- HTTP 语义、缓存与条件请求定义在 RFC 9110 与 RFC 9111，HTTP/1.1 的消息格式定义在 RFC 9112。
- HTTP/2 定义在 RFC 9113，HTTP/3 定义在 RFC 9114，其底层传输协议 QUIC 定义在 RFC 9000。
- 本主题第 3 篇（浏览器网络与 HTTP 协议演进）讨论的浏览器侧连接管理与协议选择以这些文本为协议依据，TCP 与 TLS 握手的细节属于架构领域的范围。

> 引用协议应以 RFC 编号为凭据：同一协议的新编号会取代旧编号，写明编号与取代关系，才能避免引到已废弃的版本。

**速记**：HTTP 与 QUIC 的协议依据查 RFC 编号，引用需写明版本取代关系。



### 经典文章与书籍

本模块收录经得起时间检验的书籍与文章。这类材料的价值在于给出心智模型与判断依据，而不是罗列接口；使用时需注意其技术栈假设与写作年代。

#### 网络与加载类书籍

**网络与加载类书籍**：从协议开销与往返次数出发解释加载慢的根因，适合在排查首屏性能之前建立延迟直觉。

- 《高性能浏览器网络》（High Performance Browser Networking，Ilya Grigorik 著）：系统讲 TCP、TLS、HTTP/1.1 与 HTTP/2 的延迟来源，内容公开在 hpbn.co。
- 其主线是减少往返次数优先于压缩字节数，与本主题第 3 篇的协议演进脉络一致，HTTP/2 多路复用与 HTTP/3 的取舍都由此推得。
- 《HTTP 权威指南》（HTTP: The Definitive Guide）：可作协议与缓存语义的对照读物，成书较早，字段细节需与 RFC 核对。

> 这类书适合先建立「一次请求要花几次往返」的直觉，再回到浏览器侧看哪些机制在减少往返；单独记忆协议字段收效有限。

**速记**：网络类书籍先建立往返预算直觉，旧结论以 RFC 与当前文档更新。



#### 语言与引擎类书籍

**语言与引擎类书籍**：以语言机制与运行期开销为主题，适合在写过一定代码之后建立执行模型。

- 《JavaScript 高级程序设计》（Professional JavaScript for Web Developers，Nicholas C. Zakas 著）：覆盖语法、DOM、事件与异步编程的基础机制，适合作为语言层地基；涉及版本差异处应以 MDN 与标准复核。
- 《高性能 JavaScript》（High Performance JavaScript，同一作者）：专注运行期性能，讲循环、DOM 操作与网络请求的开销来源，其中少访问 DOM、批量更新与避免强制同步布局的结论在本主题第 8 篇（渲染性能：重排、重绘与合成层优化）仍然成立。
- 书中的微观技巧（变量缓存、位运算加速）多已被即时编译覆盖，不必照搬；长期有效的是关于主线程与渲染管线配合的判断。

> 评估旧书建议的判据是先问它针对引擎的哪一层开销：已由引擎优化的部分作废，涉及主线程与渲染配合的部分大体仍适用。

**速记**：语言地基读《JavaScript 高级程序设计》，性能判断读《高性能 JavaScript》并剔除过时技巧。



#### 渲染与调度的经典文章

**渲染与调度经典文章**：把渲染管线与事件循环的开销来源写成可操作的清单，适合在遇到卡顿时按图索骥。

- Paul Irish 整理的强制同步布局操作清单，逐条列出引发读写交替的写法，是本主题第 8 篇（渲染性能：重排、重绘与合成层优化）布局抖动的常见引用来源。
- Addy Osmani 的渲染性能指南讲清像素管线各阶段的对应优化手段，与本主题第 7 篇的渲染管线分解互为印证。
- Jake Archibald 的 In The Loop 演讲及配套文章用可视化方式解释事件循环、渲染帧与任务调度，对应本主题第 9 篇的渲染时机。

> 这些文章的作者多来自浏览器厂商或大型前端团队，立场偏向按引擎实际行为优化；Philip Walton 关于空闲调度的文章可作为 requestIdleCallback 取舍的补充读物，引用具体数值前应确认其测试条件。

**速记**：渲染与调度文章按管线阶段和调度模型各取一读，其中的数值需自行复测。



#### 性能指标与真实用户数据

**性能指标类读物**：解释指标的定义、阈值来源与数据口径，适合在设定优化目标与阶段性复盘时使用。

- web.dev 的 Core Web Vitals 系列给出 LCP、INP 与 CLS 的定义、阈值与优化路径，是本主题第 16 篇的主要参照。
- Chrome UX Report（CrUX）提供按源与页面聚合的真实用户指标数据，用于判断自身指标是否偏离同类站点。
- Chrome 团队的 web-vitals 开源库把指标计算封装为可直接上报的调用，是自建真实用户监控时的常用起点。

> [!NOTE]
> **提醒内容**：指标数值必须连同采集口径一起读，同一站点在不同设备、地域与网络条件下的分布差异，往往大于版本迭代带来的差异。

**速记**：指标读物先读 web.dev 的定义，再看 CrUX 与自建上报的真实数据。



### 工具与在线平台

本模块的工具用于把「感觉慢」变成可定位的证据。选型时先分清实验室数据与真实用户数据：前者可复现、适合定位，后者反映分布、适合判断影响面。

#### Chrome DevTools 的 Performance 与 Memory 面板

**Chrome DevTools（developer.chrome.com/docs/devtools）**：是 Chromium 系浏览器内置的调试工具，Performance 面板与 Memory 面板分别承担主线程时间分析与内存问题排查。

- Performance 面板记录时间窗内的任务、脚本调用栈与渲染帧，可看清长任务、强制同步布局与掉帧发生在哪一帧。
- 火焰图按调用栈展开主线程任务，定位长任务的来源比比较平均耗时更有意义。
- Memory 面板提供堆快照、分配时间线与分离节点（detached DOM）视图，是本主题第 11 篇（内存管理与垃圾回收）泄漏排查的主要手段。

> 录制性能轨迹时把时间窗压到目标交互前后数秒，并开启 CPU 与网络限制模拟中端设备，否则本机的高速环境会掩盖真问题。

**速记**：DevTools 把主线程与内存证据可视化，录制结果只代表当前设备与网络条件。



#### Lighthouse 与 PageSpeed Insights

**Lighthouse（developer.chrome.com/docs/lighthouse）**：是开源的自动化审计工具，按性能、可访问性、最佳实践与 SEO 四类给出评分与改进清单，可运行在 DevTools、命令行与持续集成中。

- 性能评分由 FCP、LCP、TBT 与 CLS 等实验室指标加权而成，权重随版本调整，因此分数不可跨版本直接比较（本主题第 16 篇）。
- **PageSpeed Insights（pagespeed.web.dev）**：在 Lighthouse 之上叠加来自 CrUX 的真实用户字段数据，同时给出实验室诊断与现场分布两类结果。
- 审计结论属于诊断线索：报告指出未使用的 JavaScript 过多时，仍需回到构建主题确认拆包策略，浏览器侧只负责加载优先级。

> 报告中的每一项机会（opportunity）都附带预估节省时间，这些估算基于固定模型与固定网络条件，用于排序而非承诺实际收益。

**速记**：Lighthouse 做实验室诊断，PageSpeed Insights 叠加真实用户数据，分数不跨版本比较。



#### WebPageTest

**WebPageTest（webpagetest.org）**：是基于真实浏览器与真实网络的在线测速平台，可按地点、设备与网络条件配置测试，输出瀑布图与逐帧影片。

- 瀑布图把每个请求的排队、DNS、连接、TLS、首字节与下载分段展示，配合本主题第 3 篇的连接建立过程定位瓶颈环节。
- 影片视图逐帧呈现首屏渲染过程，用于解释指标达标但观感跳跃这类现象。
- 支持多次运行取中位数与自定义脚本（登录、滚动、点击），适合复现带状态的加载路径。

> [!CAUTION]
> **注意内容**：公开测速站点会真实加载被测页面并暴露其地址与请求内容。涉及未公开业务或带登录凭据的页面，应改用自建实例并在测试账号下运行。

**速记**：WebPageTest 用瀑布图与影片定位连接与渲染环节，敏感页面改用自建实例。



#### Can I Use 与 Chrome Platform Status

**特性兼容查询平台**：回答某个能力在目标浏览器能不能用的问题，是技术选型与降级方案设计的前置依据。

- Can I Use（caniuse.com）：按特性汇总各浏览器与版本的支持情况、已知缺陷与全球使用率统计。
- Chrome Platform Status（chromestatus.com）：跟踪 Chromium 的特性状态，从提案、开发、试验到正式发布，可判断某能力是临近可用还是仍处试验。
- 兼容性数据依赖厂商与社区提交，边界情况仍需在目标浏览器实测。

> 兼容查询只回答是否支持，性能是否更好需要另看指标与实测，两者不可互相替代。

**速记**：可用性查 Can I Use，发布进度查 Chrome Platform Status，边界结论以实测兜底。



### 进阶方向

本模块指向规范与实现之间的空白地带：读源码、读设计文档与建立线上度量，是把前面十六篇串成体系的三条路径。三条路径都要求先有具体问题，再动手查证。

#### V8 引擎与运行时内部

**V8 官方博客（v8.dev/blog）**：是 V8 团队发布的实现说明与版本更新记录，用可读的方式解释优化器、垃圾回收与语言特性的落地细节。

- 博客随版本发布，逐条说明性能改进与行为变更，是判断某种写法在当前引擎是否仍被优化的依据（本主题第 10 篇）。
- 垃圾回收相关文章解释新生代与老生代回收的并发与增量策略，对应本主题第 11 篇的回收算法。
- 继续深入可阅读 Chromium 源码中与 V8 相关的目录，从一次具体的去优化日志入手，比按目录顺序通读更有效。

> 引擎实现文章的结论都带版本前提，写清在哪个版本、用什么基准测出，比记住结论本身更重要。

**速记**：引擎内部从 V8 官方博客入手，跟版本读改进记录并理解其前提。



#### 渲染引擎内部与 RenderingNG

**RenderingNG 系列文章（developer.chrome.com/blog/renderingng）**：是 Chromium 渲染团队对新一代渲染架构的说明，讲清渲染管线各阶段的职责与线程分工。

- 系列覆盖布局、绘制、光栅化、合成与 GPU 加速的整体设计，与本主题第 7 篇的管线分解互为印证。
- 它解释了为什么部分 CSS 属性可以只在合成线程处理，从而决定动画性能的判断依据（本主题第 8 篇）。
- 读设计文档的收益在于理解取舍原因，比查单点技巧更容易形成可迁移的判断。

**速记**：渲染引擎内部读 RenderingNG 系列，重点理解各阶段的职责划分理由。



#### 真实用户监控与性能工程

**真实用户监控（Real User Monitoring，RUM）**：是在真实用户环境中采集性能与错误数据的方法，与实验室测试互补，回答影响面有多大的问题。

- 采集侧以 PerformanceObserver 与 web-vitals 库为主，需处理采样率、上报时机与页面卸载时的数据丢失。
- 分析侧按设备、地域、网络与页面分维度看分布，比只看平均值更能定位长尾（本主题第 16 篇）。
- 治理侧以性能预算与回归门禁落地，把关键指标阈值写入持续集成，使性能回退在合并前暴露。

**速记**：线上度量靠采集、分维度分析与预算门禁三步，与实验室测试互补。
