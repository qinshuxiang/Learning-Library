## 项目架构与样式分层

### 目录组织：7-1 模式

Sass 社区最通行的目录结构是 7-1 模式：七个功能目录加一个入口文件。它解决的问题是「样式文件按什么维度切分」，答案是先按职责分层，再按组件细分。

```text
styles/
├── abstracts/
│   ├── _variables.scss
│   ├── _functions.scss
│   ├── _mixins.scss
│   └── _index.scss
├── base/
│   ├── _reset.scss
│   ├── _typography.scss
│   └── _index.scss
├── components/
│   ├── _button.scss
│   ├── _card.scss
│   └── _index.scss
├── layout/
│   ├── _header.scss
│   ├── _grid.scss
│   └── _index.scss
├── pages/
│   ├── _home.scss
│   └── _index.scss
├── themes/
│   ├── _dark.scss
│   └── _index.scss
├── vendors/
│   ├── _normalize.scss
│   └── _index.scss
└── main.scss
```

各目录的职责与依赖方向是固定的：

- abstracts：变量、函数、混合宏，只含定义不含 CSS 输出。可以被称为任何其他层的引用对象。
- vendors：第三方样式，如规范化样式表、插件样式。
- base：全局基础样式，重置、排版、通用元素默认值。
- layout：页面骨架，页头、侧栏、栅格。
- components：可复用组件。
- pages：页面级样式，优先级最高，用于局部覆盖。
- themes：主题令牌定义。



### 入口文件与索引

入口文件只做组装，不写任何样式规则。

```scss
// styles/main.scss
@use "abstracts";
@use "vendors";
@use "base";
@use "layout";
@use "components";
@use "pages";
@use "themes";
```

每个目录下的 _index.scss 把该目录的成员汇总转出，让入口只需引用目录名：

```scss
// styles/abstracts/_index.scss
@forward "variables";
@forward "functions";
@forward "mixins";
```

```scss
// styles/components/_index.scss
@forward "button";
@forward "card";
```

这一层索引的价值在于让外部只依赖目录而非具体文件名：组件重命名、拆分、合并时，只要索引同步更新，入口文件与使用方完全不用改。

> [!IMPORTANT]
> **重要内容**：abstracts 目录下的索引必须用 @forward，不能用 @use。@use 只让成员对当前文件可见，下游拿到的是一个空模块，继续 @forward 会报「成员不存在」。判断标准是：这个文件的作用是转出成员还是自用成员。



### 依赖方向约束

分层架构的有效性取决于依赖方向是否单向。样式表的依赖应为：

```text
abstracts → vendors → base → layout → components → pages
```

下层可以引用上层，上层不得反向引用下层。破坏方向会出现三类具体后果：

- 循环引用：两个文件互相 @use，编译直接报错，且报错位置指向 @forward 链而非真实成因，排查耗时。
- 顺序敏感：pages 中的规则被 components 引用后，产物顺序不再由入口决定，覆盖关系随文件遍历顺序变化。
- 复用困难：组件耦合了页面级样式，同一组件换到另一页面时不得不带入无关样式。

> 依赖方向靠约定维持，编译器不会检查。可行的加固手段是在 CI 中加一条检查：正则匹配 components 目录下的文件是否出现 pages 的模块名，命中即失败。这类检查成本极低，比事后的产物排查有效。



### 与组件框架的配合

使用 Vue、React 一类组件框架时，全局样式与组件样式需要明确分工，避免两套体系互相覆盖。

- 全局层：令牌、重置、排版、布局骨架，由 Sass 编译为一份全局 CSS，在应用入口引入。
- 组件层：组件自己的样式与框架的作用域机制配合，Vue 用 scoped 样式块，React 常用 CSS Modules。

组件需要引用令牌时，把令牌定义成独立模块并让组件按需 @use，而不是依赖全局变量：

```scss
// components/Button.module.scss 或 Vue 的 style 块
@use "abstracts" as token;

.button {
  background: token.$color-primary;
  padding: token.$size-control-padding;
  border-radius: token.$radius-md;

  &:hover {
    background: token.$color-primary-hover;
  }
}
```

三种作用域方案的选择依据：

- 编译期加哈希类名（CSS Modules）：零运行期开销，构建产物可静态分析，缺点是动态类名组合需要额外写法。
- 属性选择器加哈希（Vue scoped）：书写最简洁，作用域穿透需用深度选择器，深度选择器一多即说明组件边界没划清。
- 运行期生成样式（CSS-in-JS）：动态性最强，代价是运行期开销与产物不可静态提取，服务端渲染场景需额外处理。



### 命名与规模控制

三条落地尺度可以避免样式表在半年后失控：

- 选择器层级不超过两层。嵌套只用于表达真实的结构包含关系，其余场景用平铺的类名。
- 单个样式文件不超过 300 行。超出说明该文件承担了多个组件或多种状态，应按组件再拆。
- 单一类名长度不超过 40 字符。BEM 全名很容易超标，超标通常意味着块名承担了过多语义层级。

```scss
// 可接受：块 + 元素 + 修饰符的结构清晰
.card {
  &__title { font-size: 18px; }
  &--featured { border-color: #f60; }
}

// 应避免：三层修饰符叠加，类名失控且权重难以预测
.card--featured--dark--compact { }
```



### 产物与构建

样式表的构建需要明确三个决策点：

- 编译粒度：全局一份入口产物，还是按路由拆分多份。单页应用常用一份，多页或按需加载场景按路由拆分。
- 压缩时机：开发期不压缩以便调试，生产环境启用 --style=compressed，同时保留 source map 供错误上报还原。
- 浏览器前缀：Sass 不生成厂商前缀，需在 Sass 之后接入 PostCSS 的 autoprefixer，链路顺序为先编译再补前缀。

```shell
sass --style=compressed styles/main.scss dist/main.css
```

> [!NOTE]
> **提醒内容**：Sass 编译与 PostCSS 处理的顺序不可颠倒。autoprefixer 需要看到最终 CSS 才能判断哪些属性需要加前缀，如果在 Sass 之前处理，嵌套语法尚未展开，前缀会漏加在正确的声明上。
